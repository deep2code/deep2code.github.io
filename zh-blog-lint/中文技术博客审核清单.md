# 中文技术博客审核清单

> 依据《中文技术文档的写作规范》（阮一峰）、《中文文案排版指北》、主流大厂中文文档风格指南整理。
> 每条规则标注了**执行方**，`[T]` = textlint、`[M]` = markdownlint、`[V]` = Vale、`[L]` = 大模型、`[H]` = 必须人工。
>
> **用法一**：把本文件从「二、审核维度」开始的部分整段贴给大模型当检查清单。
> **用法二**：按标签把规则落到对应工具，剩下的 `[L]`/`[H]` 交给人工复核。

---

## 一、规则分工总览

| 层 | 检查内容 | 主力工具 | 覆盖率 |
|---|---|---|---|
| 排版格式 | 中英空格、数字单位、全半角、标点 | textlint 中文预设 | 高，可 `--fix` |
| 文档结构 | 标题层级、列表、代码块、链接 | markdownlint | 高 |
| 术语一致 | 大小写、写法统一 | Vale + textlint | 中高 |
| 句子长度 | 长句、逗号堆叠 | textlint | 中 |
| 用词规范 | 禁用词、口语化、被动语态 | Vale | 中 |
| 错别字 | 同音、形近、的了得 | **无规则可用** | 需 `[L]`/`[H]` |
| 语义逻辑 | 指代、连贯、矛盾 | **无规则可用** | 需 `[L]` |
| 技术正确性 | 代码、API、版本 | **无规则可用** | 需 `[L]`+`[H]` |
| 事实核查 | 数字、引用、链接 | **无规则可用** | 需 `[H]` |

---

## 二、审核维度

### 层级 1：排版格式 `[T]`

1. 全角中文与半角英文之间加一个半角空格。错误：`在Linux上运行`；正确：`在 Linux 上运行`。
2. 全角中文与阿拉伯数字之间加空格，全文风格须统一，不可混用。错误：`上线时间是2025年`；正确：`上线时间是 2025 年`。
3. 数字与英文单位之间保留空格：`16 GB`、`10 Mbps`、`5 GHz`。
4. 数字与特殊单位之间**不加**空格：`28℃`、`15%`、`90°`。
5. 全角标点前后不加空格。错误：`他的电脑是 MacBook Air 。`；正确：`他的电脑是 MacBook Air。`
6. 中文语境一律使用全角标点（，。；！？、），不得夹用半角逗号句点。
7. 整句英文内部用半角标点，与中文引号自然区分。
8. 使用标准省略号「……」，禁止 `...` 或 `。。。`。
9. 不重复堆砌标点：`牛逼!!!`、`真的吗???` 均不合格（强调场景例外）。
10. 避免 `?!` `?!?` 这类混用标点。
11. 引号、书名号等成对标点按正确顺序配对使用。
12. 行内代码 `code` 与中文之间加空格。错误：使用`grep`命令；正确：使用 `grep` 命令。
13. 全角/半角括号使用统一：括号内含中文用全角，纯英文数字用半角。
14. 清除不可见控制字符与多余空格。

### 层级 2：文档结构 `[M]`

15. 标题从一级递进，禁止跳级（一级下不能直接三级）。
16. 标题最多四级，三级下有并列内容优先用列表替代。
17. 一级标题全篇唯一，即文章标题。
18. 避免孤立编号（同级标题只有一个）。
19. 下级标题不重复上级标题的措辞。
20. 标题不以标点结尾；描述任务时用「动词 + 主题词」，不用名词词组。
21. 同级标题尽量保持相同句式结构。
22. 标题之间应有引导性过渡句，不要标题连标题。
23. 代码块必须标注语言标识。
24. 代码块内终端命令前不需要 `$` 符号。
25. 列表符号全文统一（全用 `-` 或全用 `*`），同级缩进一致。
26. 段落之间空一行；段落开头不空两格（网络排版）。
27. 外部图片须在下方标注来源；引用第三方内容在文末链接原文。
28. 表格、图片在正文中必须被实际提及，不能孤立摆放。
29. 文件名只用小写英文与连词线，不含空格，不用中文。

### 层级 3：句子与可读性 `[T]` `[L]`

30. 不含标点的单句长度控制在 20 字以内；20–29 字可接受；30–39 字须语义明确；**超过 40 字不可接受**。
31. 以逗号分隔的长句，总长不超过 100 字或正文 3 行。
32. 一句话内逗号（，）不超过 3 个，超过说明该拆句。
33. 优先简单句和并列句，避免多层嵌套复合句。
34. 名词前不要堆叠形容词/形式词。错误：`此设备的使用必须在接受过本公司举办的正式的设备培训的技师的指导下进行`。
35. 一段控制在 3–5 行以内，超过就拆段。

### 层级 4：用词规范 `[V]` `[L]`

36. **主动语态优先**，少用被动。错误：`假如此软件尚未被安装`；正确：`假如尚未安装这个软件`。
37. 用对「的」「地」「得」：形容词+的+名词、副词+地+动词、动词+得+副词。
38. 代词「其」「该」「此」「这」必须指代唯一且明确。错误：`从管理系统可以监视中继系统和受其直接控制的分配系统`。
39. 全文人称一致，不反复切换「你」「我们」「笔者」。
40. 尽量用肯定句，不用否定句。错误：`请确认没有接通装置的电源`；正确：`请确认装置的电源已关闭`。
41. 避免双重否定。错误：`没有删除权限的用户，不能删除此文件`。
42. 数字增减表述准确：「增加了/增加到」「降低了/降低到」，**禁止「降低 N 倍」**。
43. 四位以上数值加千分位分隔符。
44. 数值范围用 `~` 或「至」，前后两个值都带单位。
45. 首次出现英文缩写时括号给出中文全称。
46. 禁用口语化表达：`不准`、`……的话`、`就可以了`、`做……用`。
47. 禁用过场句：`众所周知`、`接下来让我们`、`聊到这里`、`继续往下看`、`最后可以用一句话收住`。一句话若只是在主持文章、不承载信息，直接删。
48. 禁用空评价词：`非常`、`十分`、`极其`、`很现实`、`很顺`。改用具体数据、具体约束、具体影响。
49. 禁用黑话堆砌：`赋能`、`抓手`、`闭环`、`打法`、`颗粒度`、`对齐一下`。先停下来问：删掉这句，论证少了什么？没少就删掉。
50. 禁用绝对表述：`一定`、`绝对`、`绝不`、`100% 安全`。
51. 避免反问句、感叹句（高风险警示除外）。
52. 避免拟人、玩笑、网络流行语（长期有效的文章尤其如此）。
53. 避免生僻词、文言词、自造词。
54. 技术专名大小写稳定：`JavaScript` 非 `Javascript`、`GitHub` 非 `Github`、`npm` 非 `NPM`、`iOS`/`macOS`/`HTML5` 按官方写法。
55. 同一概念全文统一用词，不混用近义词（如一会儿「零拷贝」一会儿「零复制」）。
56. 禁用可能含偏见或引发负面情绪的词汇。

### 层级 5：语义与逻辑 `[L]` — 规则工具无法覆盖

57. 每个段落是否有且只有一个中心意思。
58. 段与段之间是否有逻辑推进，还是简单的观点罗列。
59. 开头是否在 3 句内说清读者能获得什么。
60. 结尾是否呼应开篇的承诺，还是草草收尾或另起话题。
61. 是否存在前后矛盾：前文说 A，后文又说非 A。
62. 是否存在逻辑跳跃：从前提到结论中间缺了一环推理。
63. 指代是否可消解：读者能否确定「它」「这个方案」指什么。
64. 篇幅配比是否头重脚轻：铺垫过长、核心内容过短。
65. 是否存在重复表达：同一意思换措辞又说了一遍。

### 层级 6：技术正确性 `[L]` + `[H]`

66. 代码片段能否实际运行，还是伪代码。
67. API 是否过时、参数是否正确、版本是否匹配。
68. 命令、依赖名、配置项是否真实存在。
69. 代码示例是否标注了运行环境与版本要求。
70. 关键注释是否解释「为什么」而非复述「是什么」。
71. 是否遗漏边界条件、异常处理、错误码说明。
72. 示例代码中有无硬编码密钥、注入风险等安全隐患。

### 层级 7：事实核查 `[H]` — 大模型只能提醒，不能裁决

73. 具体数字、百分比、性能数据能否溯源到原始出处。
74. 引用的官方文档/论文是否真的支持文中那句话（**真来源、假结论**是最隐蔽的错误）。
75. 版本号、发布日期、时间敏感表述是否标注了「截至 X 年 X 月」。
76. 所有外链是否有效，链接页面是否真的支撑其后的论断。
77. 引语是否逐字准确、未脱离语境。
78. 单位、量级、百分比是否自洽（如各项占比之和是否为 100%）。

## 三、给大模型的 Prompt

把上面「二、审核维度」的层级 1–7 完整粘贴后，接下面这段指令：

```
你是资深中文技术编辑。请按上面七个层级审核这篇文章。

【执行要求】
1. 先只诊断，不要改写原文。
2. 每条问题输出：位置（引用原文片段）→ 问题 → 为什么是问题 → 建议改法。
3. 按严重程度排序（阻断 > 严重 > 建议 > 细节）。
4. 层级 1-4 逐条核对；层级 5-6 给出你的判断但标注「需人工确认」；
   层级 7 只列出需核查的主张清单，不要自行判定真伪。
5. 最后给出一句话总评：这篇文章最该先改的三件事是什么。

【文章】
（粘贴全文）
```

## 四、落地流水线

```bash
# 1. 排版与格式（可自动修复）
textlint --fix 文章.md

# 2. 文档结构
markdownlint --fix 文章.md

# 3. 用词与术语
vale 文章.md

# 4. 语义、技术、事实：交给大模型 + 人工
```

推荐接入 pre-commit：每次提交前自动跑 1–3 步，把格式问题挡在发布之前。
