抓包分析的方法论与常见误判

🏷️ Wireshark

抓包点位决定你能看到什么

抓包不是「打开工具看流量」，而是先回答一个问题：我要在链路的哪一点观察。每个点位看到的只是这一点的事实，不是整条链路的事实。同一次请求在客户端网卡、代理入口侧、代理上游侧、服务端网卡上的五元组、时间戳甚至包数量都可能不同。绝大多数「抓了半天什么也没看出来」，根因是点位选错了。

不受主机卸载影响"]
点位能证明的事实看不到的事实典型误判
客户端网卡请求是否真的发出、DNS 是否先于建连、SYN 是否重传、TLS 握手参数中间设备是否改写、服务端是否真的收到看到 SYN 重传就报「网络丢包」，实际是服务端 accept 队列溢出丢了 SYN
代理入口侧请求到达代理的时间、请求头原样、客户端是否提前断开上游行为与上游耗时把代理自己生成的 502 当成上游返回的错误
代理上游侧代理是否真的发起了上游请求、上游首字节时延、连接是否复用客户端到代理这段的网络质量上游连接被代理按超时主动 RST，被读成「上游宕机」
服务端网卡请求是否到达内核、响应何时进入内核应用线程何时真正处理完内核已回 ACK 就认定「服务端已处理」，其实数据还堆在接收队列
容器网络命名空间内应用视角的地址与端口地址转换与隧道封装之后的真实五元组按 IP 去关联两端抓包，永远对不上
交换机镜像口双向全量、校验和真实、不受 TSO 影响同主机进程间通信与回环流量以为镜像口一定比主机抓得全，忽略了镜像口本身也会丢包

凡是「谁先断的连接」「延迟出在哪一段」这类问题，单侧抓包给不出结论，必须两侧同时抓，然后用序列号、初始序列号或载荷特征对齐两份文件，而不是用时间戳对齐——两台机器的时钟差经常比你要定位的延迟还大，就算都开了 NTP 也一样。

从网卡到 pcap 文件：三个丢包位置

文件里「少了一个包」有两种完全不同的含义：链路上真的没有这个包，或者采集链路自己把它丢了。分清这两件事是抓包分析的第一道门槛，也是最常被跳过的一步。

丢包位置怎么确认常见原因处理方式
网卡与驱动抓包前后对比 ethtool 统计里的 rx_missed_errors、rx_no_buffer_count软中断处理不过来、驱动环形缓冲太小加大驱动 ring、绑核；这里丢掉的包抓包工具根本看不到
内核共享缓冲tcpdump 退出时打印的 dropped by kernel 非零缓冲默认只有约 2MB，用户态消费慢放大缓冲（选项单位是 KiB）、收紧捕获过滤器、绝不要同时开逐包解码输出
snaplen 截断Wireshark 提示 packet size limited during capture显式把 snaplen 设成了几十字节需要重组、解密、看载荷就必须抓全包；只做时序分析才可以截断
写盘抓包期间磁盘写入饱和、文件增长速率明显低于估算写网络盘或机械盘、单文件过大写本地盘、用环形切片限制总量、必要时在内核侧先过滤掉大流量
分析阶段Wireshark 打开文件卡死或内存耗尽直接用图形界面打开 GB 级文件先用命令行按流切出子集，图形界面只看几十 MB
 
# 生产机上挂着等复现：环形切片 + 足够大的内核缓冲 + 不做任何名字解析
# -i 指定物理网卡，不要用 any：any 走 Linux cooked 封装，VLAN 标签等信息会丢
# -s 0 表示用默认最大 snaplen（tcpdump 4.0 之后默认 262144，足够抓全包；
#    更老的版本默认只有 68 或 96 字节，那种截断会让重组和解密全部失败）
# -B 单位是 KiB，默认约 2MB，高包速场景这里是第一丢包点
# -C 每个文件 200MB，-W 最多 20 个循环覆盖，磁盘占用有硬上界
# -Z 抓完把权限降到普通用户，避免产出文件属主是 root
# -n 关闭反向解析，否则抓包进程自己会产生 DNS 流量并可能阻塞
tcpdump -i eth0 -s 0 -B 8192 -C 200 -W 20 -Z nobody -n \
    -w /var/tmp/cap.pcap \
    'tcp port 8080 or (vlan and tcp port 8080)'

# 停止时必看这三行：captured / received by filter / dropped by kernel
# 只要 dropped by kernel 不为 0，这份文件里的「丢包现象」就不能当证据

# 事后按流切片再交给图形界面，不要直接开整个文件
tshark -r /var/tmp/cap.pcap00 -Y 'tcp.stream eq 17' -w /tmp/stream17.pcap

捕获过滤器与显示过滤器不是同一套东西

两者语法不同只是表面差异，本质差异是执行位置和可见信息量。捕获过滤器是一段 cBPF 程序，在内核里按固定偏移做字节比较，跑在协议解析之前；显示过滤器跑在解析器之后，能引用任何被解析出来的字段，包括跨包重组和解密之后的结果。

维度捕获过滤器（BPF）显示过滤器
执行位置内核，复制到用户态之前用户态，完整解析之后
能否减少丢包能，这是唯一能降低采集压力的手段不能，包已经在文件里了
可用信息固定偏移的头部字节全部解析字段，含重组后的 HTTP 主体、解密后的 TLS 内容
IP 分片只有首片带 TCP 头，按端口过滤会漏掉后续分片重组之后可以正常判断
VLAN 标签偏移前移四字节，按端口过滤直接失效，必须显式写 vlan 关键字vlan.id 与 tcp.port 可以并列使用
隧道封装只能匹配外层，VXLAN 内层要先解封装解封装后内外层字段都能引用
语法形态tcp port 80 and host 10.0.0.1，用 and or nottcp.port == 80 与 ip.addr == 10.0.0.1，用双与号双竖线
典型错误把点号形式的字段名填进捕获过滤器，直接语法报错指望显示过滤器救回内核已经丢掉的包

还有一个容易忽略的点：host 关键字同时匹配源和目的，排查单向问题时应写成 src host 或 dst host，否则你会误以为对端也回了包。同理，只过滤一个端口会把 ICMP 的「端口不可达」「需要分片」全部滤掉，而这类 ICMP 往往正是根因所在——排查 MTU 黑洞时更应该显式把 icmp 加进捕获过滤器。

TCP 现象的正确解读

Wireshark 的专家信息是一组启发式判断，它标出的是「从这个点位看到的模式」，不是根因。下面这张表是我排查时的归因清单。

现象常见错误结论真实候选原因验证方式
大量 TCP Retransmission链路丢包采集自身丢包；回程 ACK 丢失导致的伪重传；监听队列溢出丢 SYN；确实丢包先看 dropped 计数，再看监听队列与重传相关内核计数器，最后两侧对照
Previous segment not captured中间链路丢了包抓包点在丢包位置之前，或者采集缓冲溢出同一时间段的 dropped 计数；换点位重抓
Zero Window网络有问题接收端应用没有及时读取，接收缓冲被填满去接收端看进程状态与连接接收队列长度，而不是继续看网络
通告窗口小得离谱对端内核参数配错抓包漏掉了三次握手，解析器不知道窗口缩放因子重抓时确保覆盖建连；留意 unknown window scaling factor 提示

连续三个 Dup ACK一定丢包了也可能只是乱序，多队列网卡与多路径都会造成乱序看后续有没有快速重传与 SACK 块，乱序通常很快自愈
突然出现 RST服务端拒绝了请求端口未监听；应用关闭时还有未读数据或设了立即关闭；中间设备状态表超时后注入；对端重启后收到旧连接数据两侧对照有没有同一个 RST；比对 RST 的 TTL 与 IP 标识是否和正常回包一致

RST 归因几乎必须双侧抓包。中间设备注入的 RST 有一个明显特征：客户端侧抓到了「来自服务端」的 RST，而服务端侧完全没有发出记录，连接在服务端仍是 ESTABLISHED。

sequenceDiagram participant C as 客户端 participant N as 中间设备或 NAT participant S as 服务端 C->>N: 建连并正常传输 N->>S: 转发 Note over N: 连接空闲超过状态表超时，表项被回收 C->>N: 空闲一段时间后继续发送数据 N->>C: 回 RST，源地址写的是服务端 Note over C,S: 客户端抓到 RST，服务端一侧既没收到数据也没发过 RST C->>N: 只能重新建连才恢复

# 仅在自己控制的测试环境使用：密钥日志等价于明文，不要带出测试环境
export SSLKEYLOGFILE=/tmp/tls_keys.log
curl -sS https://svc.test.internal/api/v1/orders -o /dev/null
# 注意 Go 客户端不读这个环境变量，需要在代码里给 tls.Config 设置 KeyLogWriter

tshark -r cap.pcap -o tls.keylog_file:/tmp/tls_keys.log \
    -Y 'http2.header.value contains "/orders"' \
    -T fields -e frame.time_relative -e tcp.stream -e http2.streamid -e http2.header.value

# 两个硬前提：抓包要从三次握手开始（否则拿不到握手参数），
# 而且要覆盖 HTTP/2 连接开头（否则 HPACK 动态表状态缺失，头部字段解不出来）

HTTP/2 与 gRPC：看帧而不是看请求

迁到 h2 之后，「连接数」「请求数」这些老指标的含义变了：一条 TCP 连接上跑着多个 stream，排队可能发生在 stream 层而不是连接层。抓包时要看的是帧。

帧或字段抓包里的表现对应的工程问题
HEADERS 与 HPACK中途开始抓包时头部完全解不出来抓包必须覆盖连接建立，否则只能看长度和时序
SETTINGS 里的最大并发流新请求不建新连接，而是在客户端排队「连接数正常但延迟升高」的典型来源
WINDOW_UPDATE 稀少而 DATA 停滞数据传输一段一段卡住流级或连接级流控打满，大响应体配慢消费者时很常见
RST_STREAM单个 stream 结束，TCP 连接继续客户端取消或 deadline 到期，不要读成连接断开
GOAWAY 带 last-stream-id服务端宣告不再接受新 stream滚动发布期间失败请求的归因依据
PING 频率异常对端回 GOAWAY 并提示过于激进gRPC keepalive 参数与服务端策略不匹配
trailers 里的 grpc-statusHTTP 状态是 200，但 gRPC 层是失败只按 HTTP 状态码做告警会大面积漏报
DATA 载荷前五字节一字节压缩标志加四字节长度一个 DATA 帧不等于一条消息，消息可以跨帧也可以合帧

内部链路上的明文 h2c 跑在非标准端口时，解析器不会自动识别，需要显式指定解码方式，命令行上用 -d tcp.port==50051,http2。如果这条链路走了 TLS，不解密就只能看帧长度和时序——这时候与其解密，不如让应用侧把 stream 级指标暴露出来。

容器与 Kubernetes：先确定抓哪个网络命名空间

业务镜像里不该有 tcpdump。正确做法是用宿主机的工具进入目标网络命名空间，或者用共享网络命名空间的临时调试容器。

# 1) 通过容器运行时拿到目标容器的进程号（containerd 环境）
CID=$(crictl ps --name api-server -q | head -n 1)
PID=$(crictl inspect "$CID" | python3 -c 'import json,sys; print(json.load(sys.stdin)["info"]["pid"])')

# 2) 用宿主机的 tcpdump 进入该进程的网络命名空间，看到的就是应用视角的地址
nsenter -t "$PID" -n tcpdump -i eth0 -s 0 -n -w /var/tmp/pod.pcap 'tcp port 8080'

# 3) 不想动宿主机，就用临时调试容器共享目标容器的网络命名空间
kubectl debug -it pod/api-server-0 --image=nicolaka/netshoot \
    --target=api-server -- tcpdump -i eth0 -s 0 -n -c 200

# 4) 跨节点流量在宿主机网卡上是封装后的样子，按内层地址过滤不会命中
tcpdump -i bond0 -s 0 -n 'udp port 8472'
场景抓包位置包里的地址注意
Pod 访问 Service源 Pod 的命名空间目的是 Service 的虚拟地址与端口地址转换发生在离开命名空间之后，这里永远看不到后端 Pod 地址
后端 Pod 收到请求目标 Pod 的命名空间目的已改写成 Pod 地址与容器端口，源可能被改写成节点地址同一条流两端五元组不同，按地址关联两份抓包必然对不上，要按序列号与载荷对齐
跨节点转发节点物理网卡隧道外层地址与隧道端口捕获过滤器只能写外层，内层条件留给显示过滤器
Service 没有可用端点源 Pod 命名空间SYN 被拒或被直接丢弃先查端点列表，这种问题不需要抓包
入口网关到后端网关 Pod 的两侧入口是客户端地址，出口是 Pod 地址真实客户端地址在转发头或 proxy protocol 里，不在 IP 头里
带 sidecar 的网格Pod 命名空间，按劫持端口区分同一请求在同一命名空间里出现两次不区分劫持前后，会把一次请求算成两次、把 sidecar 的重试算成客户端重试

什么时候不该抓包

抓包是昂贵动作：占 CPU 与磁盘、可能触碰用户数据、产出需要有经验的人解读。大量「网络问题」在抓包之前就能用计数器定性，而且计数器可以持续采样，抓包只能守着复现。

# 抓包前先花两分钟看计数器，多数问题在这一步就能定性
# 监听队列相关计数上涨：accept 队列满，客户端表现为 SYN 重传，与链路无关
# 重传丢失计数上涨：重传包自己又丢了，这才是链路质量的直接证据
nstat -az TcpExtListenOverflows TcpExtListenDrops TcpExtTCPLostRetransmit TcpRetransSegs

# 单条连接的实时质量：累计重传、往返时延与抖动、拥塞窗口、发送队列积压
ss -tinm state established '( sport = :8080 or dport = :8080 )'

# 网卡层丢包：这里涨说明包没进协议栈，抓包工具也抓不到
ethtool -S eth0

# 连接跟踪表满会静默丢包，内核日志里有记录，表项上限要和并发规模对得上
conntrack -C
sysctl net.netfilter.nf_conntrack_max

并明确结论的适用边界"]
❌
最容易踩的坑

1. 抓完不看 dropped by kernel——采集自己丢的包会伪装成重传和 previous segment not captured，基于这种文件做的丢包结论全是错的。

2. 用 any 接口抓包——Linux cooked 封装下 VLAN 标签等信息缺失，同一个包还可能在多个接口上各出现一次，包数统计直接失真。

3. 在 VLAN 环境里只写端口条件的捕获过滤器——标签让偏移前移四字节，过滤器一个包都不会命中，看起来像「完全没有流量」。

4. 抓包不覆盖三次握手——窗口缩放因子、MSS、TLS 握手参数全部缺失，窗口大小会被算错，加密流量也没法解密。

5. 把本机发送方向的校验和错误当成链路问题——那是网卡卸载留下的占位值；同理 TSO 与 GRO 会让帧长看起来超过 MTU。

6. 把零窗口报成网络故障——它是接收端应用没读数据的信号，正确动作是去接收端看线程与接收队列。

7. 只在一侧抓包就断言「对端发了 RST」——中间设备注入的 RST 只在一侧出现，双侧对照加 TTL 比对才能定性。

8. 按 IP 关联容器两端的抓包——Service 地址转换与源地址转换之后五元组已变，应该按序列号或载荷特征对齐。

9. 抓包时同时开启逐包解码输出——用户态处理速度骤降，内核缓冲直接溢出，等于亲手制造丢包。

10. 把 snaplen 设成几十字节图省空间——载荷截断后重组、解密、看 HTTP 头全部失效，白抓一场。

11. 用图形界面直接打开 GB 级文件——先按流切片再看，否则不是卡死就是内存耗尽。

12. 用两台机器的绝对时间戳比较延迟——时钟差常常大于你要定位的延迟，只能比较各自文件内的相对时间差。
