接口性能优化：从耗时拆解到并发模型

🏷️ API 优化

这篇只讲单个接口的耗时是怎么构成的、以及每一段能用什么手段压下去。度量方法、压测流程、分位数怎么看在后端性能优化的度量与方法论；连接池与 ORM 层面的问题在应用侧的数据库访问优化；SQL 与索引见站内数据库优化；缓存的收益模型与一致性见站内缓存设计；接口的语义、版本、分页规范见站内API 设计；超时之上的熔断与降级见站内限流熔断降级。

先把一次接口耗时拆开

优化接口的第一步不是改代码，是拿到一张按占比排序的耗时构成表。没有这张表就动手，大概率是在优化占总耗时 3% 的那一段。下面是一次典型业务接口的六段构成，百分比是我在多个中等规模系统上看到的常见区间。

💡
一个能立刻用的判据

如果接口总耗时 ≈ 各下游调用耗时之和，说明调用全是串行的，并行化是第一优先级。如果总耗时 ≈ 最慢的那次下游调用，说明已经并行了，接下来要减少的是「调用次数」或让最慢的那个变快。如果总耗时明显大于所有下游耗时之和，中间那部分不是业务逻辑，几乎一定是排队（线程池、连接池或锁）。

串行改并行：收益最大的单项改动

四个互相没有依赖的下游调用，各 50ms。串行是 50 + 50 + 50 + 50 = 200ms，并行是 max(50, 50, 50, 50) + 调度开销 ≈ 55ms。这是所有优化手段里投入产出比最高的一项，因为它不需要改下游、不需要加缓存、不影响正确性，唯一前提是调用之间真的没有数据依赖。

// Go：用 errgroup 做并行下游调用。三个关键点都在注释里。
func (s *OrderService) Detail(ctx context.Context, id int64) (*OrderDetail, error) {
    // 关键点 1：超时预算给的是「整个接口」，不是每次调用。
    // 常见错误是给每个下游各设 300ms，四个串行下来最坏 1.2s，上游早就断开了。
    ctx, cancel := context.WithTimeout(ctx, 300*time.Millisecond)
    defer cancel()

    var (
        order   *Order
        user    *User
        items   []*Item
        coupons []*Coupon
    )

    // 关键点 2：WithContext 让任一调用返回错误时自动取消其余调用，避免白等。
    g, gctx := errgroup.WithContext(ctx)
    // SetLimit 限制同时在飞的调用数，防止某个请求把下游连接池吃光。
    g.SetLimit(8)

    g.Go(func() error {
        var err error
        order, err = s.orderRepo.Get(gctx, id)
        return err // 核心数据，失败就整体失败
    })
    g.Go(func() error {
        var err error
        user, err = s.userCli.Get(gctx, id)
        return err
    })
    g.Go(func() error {
        var err error
        items, err = s.itemCli.ListByOrder(gctx, id)
        return err
    })
    g.Go(func() error {
        // 关键点 3：非核心依赖显式降级，不要让优惠信息挂掉就返回 500。
        c, err := s.couponCli.ListByOrder(gctx, id)
        if err != nil {
            metrics.DegradeCounter.WithLabelValues("coupon").Inc()
            return nil
        }
        coupons = c
        return nil
    })

    if err := g.Wait(); err != nil {
        return nil, err
    }
    // 每个 goroutine 只写自己的那个变量，不并发写同一个 map 或 slice，所以不需要锁。
    return assemble(order, user, items, coupons), nil
}
// Java：CompletableFuture 并行调用。最大的坑是线程池。
public class OrderDetailAssembler {

    // 不要用默认的 ForkJoinPool.commonPool()：它的并行度是 CPU 核数减一，
    // 把阻塞 IO 任务丢进去会互相排队，表现为「代码改并行了但耗时没变」。
    private static final ExecutorService IO_POOL = new ThreadPoolExecutor(
            32, 64, 60L, TimeUnit.SECONDS,
            new ArrayBlockingQueue<>(200),   // 有界队列：满了立刻拒绝，好过无限堆积后 OOM
            new ThreadFactoryBuilder().setNameFormat("order-detail-%d").build(),
            new ThreadPoolExecutor.AbortPolicy());

    public OrderDetail detail(long id) throws Exception {
        CompletableFuture<Order> orderF =
                CompletableFuture.supplyAsync(() -> orderRepo.get(id), IO_POOL);
        CompletableFuture<User> userF =
                CompletableFuture.supplyAsync(() -> userClient.get(id), IO_POOL);
        // 非核心依赖：用 exceptionally 兜底，失败返回空列表而不是让整个 allOf 失败
        CompletableFuture<List<Coupon>> couponF =
                CompletableFuture.supplyAsync(() -> couponClient.list(id), IO_POOL)
                                 .exceptionally(e -> Collections.emptyList());

        // 统一的总预算超时。注意 allOf 本身不带超时，必须在 get 上设。
        CompletableFuture.allOf(orderF, userF, couponF)
                         .get(300, TimeUnit.MILLISECONDS);

        return new OrderDetail(orderF.join(), userF.join(), couponF.join());
    }
}
并行的代价 具体表现 怎么控制
下游瞬时压力放大 N 倍 串行时下游看到的是均匀流量，并行后同一毫秒内 N 个请求同时到达，下游连接池与线程池先被打满 用 SetLimit 或有界线程池限制在飞数量；改造前先和下游确认容量；灰度放量观察下游 P99
线程或协程开销 Java 每个平台线程约 1MB 栈，几千个就吃掉几 GB；Go 协程便宜但无上限地开会压垮调度与下游 Java 用有界池或虚拟线程；Go 用 errgroup 的并发上限，不要裸开 goroutine
错误与超时语义变复杂 一个失败其余要不要取消、部分成功怎么返回、超时是单次还是总预算 统一总预算超时；显式区分核心与非核心依赖；非核心失败降级并打点
❌
并行化最常见的两个事故

第一，把有依赖关系的调用「并行」了：查订单和查订单明细之间需要订单 ID，强行并行会读到空值，而且只在慢的时候才复现。第二，并行后忘了改超时：四个调用各设 300ms 且没有总预算，最坏情况仍然是 300ms，但请求在池里占了 4 个槽位，高并发下线程或连接池的耗尽速度是原来的 4 倍。

N+1 调用：最常见的性能杀手

N+1 的形态永远一样：先查一个列表，再在循环里对每个元素调一次下游。它之所以杀伤力大，是因为它在最贵的那一层（网络往返）做乘法。100 个元素、每次往返 2ms，光往返就是 200ms，而这 200ms 里 CPU 完全是空转的。

sequenceDiagram autonumber participant A as 应用 participant D as 用户服务或数据库 Note over A,D: 改造前 N+1 一次列表查询加 100 次单点查询 A->>D: 查订单列表 返回 100 条 D-->>A: 100 条订单 loop 循环 100 次 每次一个网络往返 A->>D: 查第 i 条订单的用户信息 2ms D-->>A: 单个用户 end Note over A,D: 总计 101 次往返 约 202ms 其中 CPU 全程空转 Note over A,D: 改造后 批量 两次往返 A->>D: 查订单列表 返回 100 条 D-->>A: 100 条订单 A->>D: 批量查 100 个用户 一次请求 5ms D-->>A: 100 个用户 应用内用哈希表组装 Note over A,D: 总计 2 次往返 约 7ms 快约 29 倍
修法 适用场景 改造后耗时 注意事项
批量接口 下游能提供或愿意提供批量查询 2 次往返，约 7ms 批量参数必须有上限（比如一次最多 200 个 ID），否则把 N+1 换成了一个超大请求；下游批量实现里如果还是循环单查，等于没改
预加载后内存组装 关联数据集合可枚举，比如把本页所有用户 ID 去重后一次查回 2 次往返 去重是关键，100 条订单可能只对应 20 个用户；组装用哈希表，不要在内存里再写一遍双层循环
本地缓存 数据变更频率低、基数小，比如配置、类目、地区 首次 2 次往返，之后 0 次 必须设最大容量与过期时间；多实例下缓存不一致要能接受；不要缓存用户维度数据，基数太大

识别 N+1 有三条路子：链路追踪里同一个接口出现几十上百个同名 span；代码评审时把「循环体内出现远程调用或查询」当成红线；监控下游请求数与本接口 QPS 的比值，正常是个位数，出现几十倍就是有放大。ORM 懒加载造成的 N+1 最隐蔽，因为代码上只是访问了一个属性，详见应用侧的数据库访问优化。

超时与重试：设长了等于没设

超时不只是可用性问题，它直接决定失败请求要占用多久的资源。一个下游卡死时，10 秒超时意味着每个请求占住一个线程和一个连接 10 秒，上游线程池在几秒内就会被填满，然后整个服务对所有接口都不可用——包括那些根本不依赖这个下游的接口。

配置 推荐取值思路 配错的后果
连接超时 同机房 200 到 500ms，跨地域按往返时间的 3 到 5 倍 设成几秒时，下游整机宕机会让请求全部挂在建连上
读超时 取该下游 P999 的 1.5 到 2 倍，而不是拍一个 3 秒 大于上游总预算时，超时形同虚设，上游先断开而资源仍被占住
总预算超时 由入口定义，逐层递减向下传递，每层扣掉自己已花的时间 不传递总预算时，下游可能在上游已放弃后还在慢慢干活，纯浪费容量
重试次数 只对连接失败与明确的幂等读重试，最多 1 次，且要有重试预算总量控制 每层各重试 2 次，三层叠加就是 8 倍放大，故障时下游永远起不来

两条容易被忽略的规则：超时必须小于上游留给你的时间，否则你的超时没有任何意义；重试必须只在有剩余预算时才发起，剩 20ms 还去重试一个平均 50ms 的调用，只是浪费下游容量。熔断、隔离、降级这一层的完整机制见站内限流熔断降级。

减少数据传输：响应体是被低估的一段

很多接口慢在「传得太多」而不是「算得太慢」。响应体从 20KB 变成 2MB，序列化 CPU、下行带宽、客户端解析三处一起变差，而且在移动网络下放大得更明显。

手段 收益量级 代价 适用判据
只返回需要的字段 响应体常能降 50% 到 90% 接口会分化出多个视图，要有约定避免膨胀 列表接口返回了详情页才用的大字段（描述、扩展 JSON、富文本）
响应压缩 文本类资源体积降到 20% 到 30% 压缩消耗 CPU，小响应体上压缩成本大于收益 响应体大于 1KB 的文本才压；已压缩的图片、视频、压缩包不要再压
分页设硬上限 把最坏情况从「不可控」变成「可控」 需要导出全量的场景要另外提供接口 所有列表接口，无例外
流式或分块返回 首字节时间从「等全部算完」变成「算多少发多少」 错误处理变难，已经发出的部分无法撤回；中间层缓冲会抵消收益 大导出、日志拉取、AI 流式输出
字段裁剪下沉到下游 省的是「跨服务传输」这一段，收益常被忽略 下游要支持字段选择 从下游取回 50 个字段却只用 3 个 
// 分页参数规范化：不设上限的 limit 是一个人人都能触发的事故开关。
const (
    defaultPageSize = 20
    maxPageSize     = 200 // 硬上限，需要全量导出走专门的异步导出接口
)

func normalizePageSize(v int) int {
    if v <= 0 {
        return defaultPageSize
    }
    if v > maxPageSize {
        return maxPageSize // 截断而不是报错：老客户端传 1000 时仍能工作
    }
    return v
}

// 大结果集用流式输出：边扫边写，内存占用与结果集大小无关。
func (h *ExportHandler) ServeHTTP(w http.ResponseWriter, r *http.Request) {
    w.Header().Set("Content-Type", "application/x-ndjson")
    // 显式声明不缓冲，否则反向代理可能把整个响应攒完再发，流式就白做了
    w.Header().Set("X-Accel-Buffering", "no")

    rows, err := h.db.QueryContext(r.Context(), "SELECT id, name, amount FROM orders WHERE created_at >= ?", h.since)
    if err != nil {
        http.Error(w, "query failed", http.StatusInternalServerError)
        return
    }
    defer rows.Close()

    enc := json.NewEncoder(w)
    flusher, canFlush := w.(http.Flusher)
    n := 0
    for rows.Next() {
        var o Order
        if err := rows.Scan(&o.ID, &o.Name, &o.Amount); err != nil {
            return // 已经发出的部分无法撤回，只能中断并靠客户端按行数校验
        }
        if err := enc.Encode(&o); err != nil {
            return // 客户端断开，及早退出，别继续扫库浪费资源
        }
        n++
        if n%500 == 0 && canFlush {
            flusher.Flush() // 每 500 行刷一次：太频繁会产生大量小包
        }
    }
}

序列化开销：大响应下它不是零

「序列化能有多慢」是个常见的错觉。在小响应体上它确实可以忽略，但响应体到几百 KB 以上时，JSON 编码在单请求 CPU 里占到相当比例是很常见的，而且它产生大量临时对象，会推高 GC 频率，间接抬高所有接口的 P99。

格式 相对体积 编解码 CPU 是否需要 schema 什么时候选它
JSON（标准库） 基准 100% 基准 否 对外开放接口、需要人类可读与调试便利
JSON（高性能库） 100% 通常快 2 到 5 倍 否 不想改协议只想降 CPU，换库是最省事的一步
MessagePack 约 60% 到 80% 略快于 JSON 否 想省体积又不想引入 schema 管理
Protobuf 约 30% 到 50% 明显更低 是 内部服务间高频调用，尤其是大对象与高 QPS

两个实践结论。第一，换序列化库通常比换协议划算：不需要改接口契约，收益却能立刻拿到。第二，序列化优化的真正大头往往不是编码算法，而是少编码点东西：把 50 个字段裁到 8 个，比任何库都有效。Protobuf 的编码细节与兼容规则见站内Protobuf。

缓存与异步化：把工作移出主路径

缓存是最有效的手段，但它的收益完全取决于放在哪一层。放在下游响应这一层，省的是网络往返；放在结果这一层，省的是整段计算；放在片段这一层，省的是可复用的公共部分。命中率模型、多级缓存、一致性策略见站内缓存设计，这里只强调一条容易被忽略的：缓存的收益等于命中率乘以被省掉的耗时，命中率 50% 的缓存只能砍掉一半耗时，却让你多了一整套一致性问题，所以命中率上不去的缓存不如不加。

异步化是另一个方向：把不影响本次响应的工作移出请求路径。判断标准只有一个——调用方的这次响应是否依赖它的结果或成功。

操作 能否异步 原因 异步化的前提
发通知、短信、站内消息 能 响应不依赖它，晚几秒无影响 可靠投递 + 消费端幂等
写审计日志、埋点、更新统计计数 能 不在业务判定路径上 丢失少量可接受，或用可重建的数据源
同步搜索索引、刷新缓存 能 最终一致即可 有补偿与重建机制，能容忍短暂不一致
本次响应要返回的数据 不能 结果是响应的一部分 如果太慢，改成「先返回任务 ID 再轮询」的接口形态
库存扣减、余额变更等资金语义写入 不能 必须与主流程原子，且要能把失败告诉调用方 只能优化它本身，不能移出去
决定接口成败的关键校验 不能 异步等于放弃了拒绝的能力 可以缓存校验结果，但不能跳过
⚠️
异步化不是把问题变没了，是把问题挪了地方

三条硬要求：任务必须可靠投递（丢进内存队列后进程重启就丢的方案不算异步化，算丢数据）；消费端必须幂等，因为重投是常态；必须有积压监控与告警，否则「接口很快」的代价是「通知晚了两小时」，而且没人知道。

连接复用与攒批

不复用连接的代价在高 QPS 下非常可观：每次请求多一次 TCP 握手（同机房约 0.3ms）加一次 TLS 握手（1 到 2 个往返，跨地域时几十毫秒），还会在客户端堆积大量 TIME_WAIT 直到端口耗尽。「接口偶发变慢且伴随大量 TIME_WAIT」几乎就是连接没复用的签名。

// Go 的默认 http.Client 有两个坑：没有超时，且 MaxIdleConnsPerHost 只有 2，
// 高并发下大部分请求实际在新建连接，表现为「明明是内网调用却有几十毫秒抖动」。
var downstream = &http.Client{
    Timeout: 500 * time.Millisecond, // 总超时兜底，永远不要用零值
    Transport: &http.Transport{
        MaxIdleConns:        200,
        MaxIdleConnsPerHost: 100,              // 默认 2，必须按并发量调大
        MaxConnsPerHost:     200,              // 上限，防止把下游连接数打爆
        IdleConnTimeout:     90 * time.Second, // 要小于下游或中间层的空闲关闭时间
        DialContext: (&net.Dialer{
            Timeout:   300 * time.Millisecond, // 建连超时单独设，比读超时短得多
            KeepAlive: 30 * time.Second,
        }).DialContext,
        ForceAttemptHTTP2: true,
    },
}

// 必须做的两件事，漏掉任何一个连接都不会被复用：
//   1. 读完整个 Body：resp.Body 没读干净，连接不会回到空闲池
//   2. 关闭 Body
func call(ctx context.Context, url string) ([]byte, error) {
    req, _ := http.NewRequestWithContext(ctx, http.MethodGet, url, nil)
    resp, err := downstream.Do(req)
    if err != nil {
        return nil, err
    }
    defer resp.Body.Close()
    return io.ReadAll(resp.Body)
}

攒批是典型的「用延迟换吞吐」：把 100 次单条写入合并成 1 次批量写入，往返次数降到百分之一，吞吐能涨一个量级，但每条写入平均要多等半个批次窗口。所以攒批适合写入与异步链路，不适合放在用户等待的读路径上。如果一定要在读路径上攒批，窗口要压到毫秒级并设置「攒够 N 条就立刻发」的双触发条件，同时把窗口时间算进接口的超时预算。

接口性能会随迭代缓慢退化，这是几乎所有长期项目的共同结局：每次需求只多加一个字段、多查一次下游、多一层校验，单次改动小到评审时察觉不到，半年后 P99 翻倍且找不到责任提交。防护手段有三条：核心接口固化压测脚本并定期跑，把与基线的偏差纳入告警；在评审清单里加一项「本次改动新增了几次下游调用」；对关键接口加下游调用次数的断言，测试环境超阈值直接失败。

并行化但不限制并发数 下游瞬时压力放大若干倍，把下游打挂 有界线程池或并发上限，灰度观察下游指标

❌
最容易踩的坑
  • 并行化时给每个下游各设 300ms 却没有总预算：最坏情况耗时没降，但线程与连接被占用的总量翻了几倍。
  • 把有数据依赖的调用并行了：只在高并发或慢的时候才偶发读到空值，排查成本极高。
  • Java 用默认的公共线程池跑 IO 任务：并行度只有核数减一，代码改成并行但耗时几乎不变。
  • Go 里裸开 goroutine 调下游且不限并发：单个请求就能把下游连接池打满。
  • 下游提供了批量接口，但它内部还是循环单查：调用方看着是批量，往返次数一点没少。
  • 批量参数不设上限：N+1 被换成一次超大请求，数据库一次扫出百万行。
  • 忘记读完并关闭 HTTP 响应体：连接不会回到空闲池，实际每次都在新建连接。
  • MaxIdleConnsPerHost 用默认值 2：内网调用出现几十毫秒的莫名抖动。
  • 空闲连接超时大于中间层的空闲关闭时间：拿到已被对端关闭的连接，偶发连接重置错误。
  • 对图片、视频、已压缩文件再开压缩：白烧 CPU，体积几乎不变。
  • 流式返回但中间层开了缓冲：响应被整体攒完才下发，首字节时间一点没改善。
  • 异步化只丢进内存队列：进程重启或崩溃就静默丢数据，事后无法追溯。
  • 加了缓存不看命中率：命中率 30% 的缓存带来了全部的一致性复杂度和三成收益。
  • 在用户读路径上攒批：吞吐好看了，P99 反而被批次窗口抬高。
  • 优化完不做回归防护：几十次迭代后接口回到原来的耗时，且没人知道是哪次引入的。
