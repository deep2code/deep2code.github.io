后端性能优化的度量与方法论

🏷️ 高可用

这篇只讲怎么度量和怎么定位：性能有哪几个互相冲突的维度、为什么必须看分位数、延迟数字的量级直觉、利用率到多少延迟就开始非线性上涨、以及一套不会得出错误结论的压测与定位流程。具体优化手段分散在其它篇：单个接口的耗时拆解与并发改造见接口性能优化，连接池与 ORM 陷阱见应用侧的数据库访问优化，SQL 与索引层面见站内数据库优化，缓存收益模型见缓存设计。限流、熔断、降级是容量用尽之后的保护手段而不是优化手段，站内限流熔断降级已完整展开，本篇不重复。

「性能变差了」这句话没有信息量

性能不是一个数字，而是四个互相拉扯的维度。绝大多数无效的性能讨论，根源是参与讨论的人说的不是同一个维度：做业务的人说延迟，管成本的人说利用率，做容量规划的人说吞吐，做架构的人说可扩展性。优化任何一个维度几乎一定以另一个维度为代价，所以第一步必须把目标写成一句可验证的话，比如「下单接口的 P99 从 800ms 降到 200ms，同时单机吞吐不低于当前值、机器数不增加」。

维度 精确定义 怎么度量 优化它通常牺牲什么
延迟 Latency 单个请求从发出到收到完整响应的时间，它是一个分布而不是一个值 按接口分桶的 P50 / P95 / P99 / P999，必须与成功率一起看 吞吐与成本：不攒批、不排队、预留空闲容量，单位成本上升
吞吐 Throughput 单位时间内成功完成的请求数或字节数 QPS / TPS / MB 每秒，必须标注「在什么延迟约束下」 延迟：攒批、加队列、提高并发度都会抬高单请求耗时
资源利用率 Utilization CPU、内存、磁盘 IO、带宽、连接池的占用比例 CPU 用户态与内核态占比、运行队列长度、IO util、GC 时间占比、池等待时间 延迟稳定性：利用率越高排队越长，抗突发能力越差
可扩展性 Scalability 资源翻倍能换来多少倍吞吐，它是斜率而不是绝对值 用 1 / 2 / 4 / 8 节点实测吞吐曲线，看斜率何时掉头 复杂度与一致性：无状态化、分片、去共享都会引入新的正确性问题

最典型的冲突是攒批。把 100 次单条写入合并成一次批量写入，吞吐可能涨 10 倍，但每条写入平均多等了半个批次窗口，P99 反而变差。这不是 bug，是你选择了吞吐。反过来，为了压低 P99 把每个请求都立刻发出去，就要接受更低的单机吞吐和更高的机器成本。没有「全面变好」的优化，只有「你想牺牲哪个」的选择。

平均值是怎么骗人的：只看分位数

平均响应时间是监控大盘上最常见、也最没用的指标之一。它的问题不是不准，而是会把长尾摊薄到看不见。下面这组数字是同一个接口的四种请求分布，总量都是 1000 个请求。

请求分布 平均值 P50 P90 P99 P999 真实用户感受
1000 个都是 100ms 100ms 100ms 100ms 100ms 100ms 都很快
990 个 100ms 加 10 个 5s 149ms 100ms 100ms 100ms（正好落在边界上） 5s 1% 的用户等了 5 秒，大盘只抬高 49ms
980 个 100ms 加 20 个 5s 198ms 100ms 100ms 5s 5s 2% 的用户基本会直接放弃
900 个 100ms 加 100 个 1s 190ms 100ms 100ms 1s 1s 平均值和上一行几乎一样，但受影响人数多 5 倍

第二行是最值得盯的一行：恰好 1% 的慢请求，连 P99 都可能盖不住。P99 的定义是「把样本从小到大排序后第 99% 位置上的那个值」，1000 个样本里第 990 个还是 100ms，所以 P99 读出来完全正常，只有 P999 才暴露问题。这就是为什么关键接口至少要看到 P999，只挂 P99 的监控对「千分之几的用户彻底卡死」是瞎的。

另一个不断被搞错的点：分位数不可加，多实例的 P99 不能求平均，也不能求和。正确做法是在采集端保留直方图桶，先把各实例同一个桶的计数相加，再从合并后的直方图计算全局分位数。指标体系与直方图桶怎么设计属于可观测性话题，详见站内监控告警篇。

# 正确：先把所有实例同一个 le 桶的增长率相加，再算全局 P99
histogram_quantile(
  0.99,
  sum by (le) (rate(http_server_duration_seconds_bucket{job="order-api"}[5m]))
)

# 正确：按接口分开看。把所有接口混在一起，慢接口和快接口会互相污染
histogram_quantile(
  0.99,
  sum by (le, http_route) (rate(http_server_duration_seconds_bucket{job="order-api"}[5m]))
)

# 错误：先算每个实例的分位数再求平均，结果没有统计意义
avg(histogram_quantile(0.99, rate(http_server_duration_seconds_bucket[5m])))

# 错误：用总耗时除以总请求数当延迟指标，这就是平均值，长尾全被摊平
sum(rate(http_server_duration_seconds_sum[5m])) / sum(rate(http_server_duration_seconds_count[5m]))
⚠️
串行链路会放大长尾

如果一个页面要串行调用 5 个各自有 1% 慢请求的接口，那么「至少命中一次慢调用」的概率是 1 减 0.99 的 5 次方，约 4.9%。单个服务眼里的「千分之几」，在用户侧会被链路长度乘上去。这就是为什么长链路系统必须整体收尾延迟，而不是各自守住自己的 P99 就完事。

延迟数字的量级直觉：先算数量级再动手

性能优化里最容易做错的判断是「花三天优化了一个循环」。下面这张表是必须有直觉的量级，具体数字随硬件浮动，但量级差异是稳定的，它决定了你的时间该花在哪。

操作 典型耗时 相对 L1 的倍数 工程含义
L1 缓存命中 约 1ns 1 倍 循环里的算术、字段访问基本都在这个量级
L2 / L3 缓存命中 约 4ns / 30ns 4 倍 / 30 倍 数据布局与遍历顺序在这一层产生差异
主存随机访问 约 100ns 100 倍 指针跳转密集的结构（链表、深层对象图）在这里吃亏
内存顺序读 1MB 约 20μs 2 万倍 序列化、大对象拷贝的真实成本来源
NVMe SSD 随机读 4KB 约 100μs 10 万倍 一次未命中缓存的磁盘读，抵 1000 次内存随机访问
同机房网络往返 约 0.2 到 0.5ms 约 30 万倍 一次 RPC 的固定地板价，与业务逻辑复杂度无关
同城跨可用区往返 约 1 到 2ms 约 150 万倍 跨可用区部署的代价，主从同步复制要算进写延迟
机械盘一次寻道 约 5 到 10ms 约 700 万倍 随机 IO 打在机械盘上就是灾难
跨地域往返（国内南北） 约 25 到 35ms 约 3000 万倍 一次跨地域调用等于 3000 万次内存访问
跨洲往返 约 150 到 250ms 约 2 亿倍 光速决定下限，任何代码优化都无法补救

结论很直接：消掉一次跨地域往返（30ms）的收益，等于把一个百万次的内存随机访问循环优化掉 300 遍。所以定位阶段的第一个问题永远是「这个请求在网络上走了几趟」，而不是「哪段代码的复杂度高」。同样的逻辑解释了为什么 N+1 查询是性能杀手：它把 1 次往返变成 100 次，是在最贵的那一层做乘法。另外要记住 TLS 握手是多个往返，在长距离链路上握手本身就可能超过服务端处理时间，这也是 CDN 与就近接入收益巨大的原因，详见前端性能：核心指标与后端能做的事。

排队论：利用率是延迟的放大器

「CPU 才 85%，怎么会慢？」这是排查群里最常见的误判。排队论给出的答案是：等待时间与利用率是双曲关系，不是线性关系。用最简单的 M/M/1 模型（请求泊松到达、单服务台、服务时间指数分布），设利用率为 ρ、平均服务时间为 S：

  • 排队等待时间 W = S × ρ / (1 - ρ)
  • 总响应时间 R = S / (1 - ρ)
利用率 ρ 排队时间（倍服务时间） 总响应时间（倍服务时间） 服务时间 10ms 时的实际响应 再加 10% 流量会怎样
30% 0.43 倍 1.43 倍 14ms 几乎无感
50% 1 倍 2 倍 20ms 涨到 25ms
70% 2.33 倍 3.33 倍 33ms 涨到 56ms
80% 4 倍 5 倍 50ms 涨到 100ms，直接翻倍
90% 9 倍 10 倍 100ms 涨到 200ms 以上
95% 19 倍 20 倍 200ms 进入不可控区间
99% 99 倍 100 倍 1000ms 队列无界增长，雪崩

这张表有两个必须记住的事实。第一，80% 利用率下排队延迟已经是服务时间的 4 倍，也就是说监控上「CPU 80%、还有两成余量」的系统，实际上大部分延迟已经花在排队上了。第二，从 80% 到 90% 只多用了 10% 的资源，延迟翻了一倍，这就是为什么容量不能按 100% 利用率规划：无状态服务通常规划在 50% 到 60% 水位，需要抗突发的入口层更低。

M/M/1 是最悲观的模型。多服务台的 M/M/c 会缓和曲线（同样 80% 利用率下，服务台越多排队越短），这解释了为什么把 10 台 1 核机器换成 1 台 10 核机器在延迟上通常更划算。但非线性的性质不会因为服务台变多而消失，只是拐点往右移。而且真实流量是突发的而非泊松的，真实系统会比模型更早开始排队。

stateDiagram-v2 [*] --> Idle Idle : 低载 利用率低于 30% 延迟接近纯服务时间 Healthy : 健康 利用率 40% 到 60% 排队延迟在 1 倍以内 Congested : 拥塞 利用率 75% 到 90% 排队延迟 3 到 9 倍 Queueing : 队列累积 利用率超过 95% 延迟每秒都在涨 Collapse : 雪崩 队列无界 超时率飙升 有效吞吐反向下跌 Idle --> Healthy : 业务流量自然增长 Healthy --> Congested : 大促 或 下游变慢导致服务时间变长 Congested --> Healthy : 扩容 或 缩短服务时间 或 限流生效 Congested --> Queueing : 流量再涨 10% 就够了 Queueing --> Congested : 上游主动降速 队列排空 Queueing --> Collapse : 客户端超时重试 把请求量再放大 2 到 3 倍 Collapse --> Idle : 拒绝流量 清空队列 重启 note right of Congested 这是最危险的区间 CPU 指标看起来仍然健康 但延迟已经主要由排队构成 任何一点抖动都会把系统推进下一个状态 end note

注意从队列累积到雪崩这条边：客户端超时重试会把请求量再乘一遍，这是排队系统崩溃最常见的最后一脚。所以超时和重试策略必须和容量水位一起设计，具体的保护手段见站内限流熔断降级篇。

Amdahl 定律与 USL：加机器的收益上限

「加机器」是最常被建议也最常失效的方案。Amdahl 定律给出上限：如果任务中有比例 σ 的部分必须串行执行，则 N 倍资源带来的加速比是 1 / (σ + (1 - σ) / N)，N 趋于无穷时上限是 1 / σ。

串行比例 σ 4 倍资源 8 倍资源 32 倍资源 理论上限 现实对应
1% 3.88 倍 7.48 倍 24.4 倍 100 倍 接近无共享的无状态服务
5% 3.48 倍 5.93 倍 12.5 倍 20 倍 有共享缓存与少量分布式锁
10% 3.08 倍 4.71 倍 7.8 倍 10 倍 关键路径上有单写点
20% 2.5 倍 3.33 倍 4.44 倍 5 倍 所有写都落在同一个库的同一张表

Amdahl 还算乐观，因为它假设并行部分没有协调成本。通用可扩展性定律（USL）多了一个相干性项 κ，描述节点之间为保持一致而互相协调的开销，这一项随节点数平方增长：C(N) = N / (1 + σ(N-1) + κN(N-1))。它的直接结论是吞吐曲线会先升、达到峰值、再下降，峰值点在 N* = sqrt((1 - σ) / κ)。见过「扩容后 QPS 反而降了」的人，都站在这条曲线的右半边。

import math

def amdahl(sigma: float, n: int) -> float:
    """串行比例 sigma 下，n 倍资源能拿到的理论加速比上限。"""
    return 1.0 / (sigma + (1.0 - sigma) / n)

def usl(n: int, sigma: float, kappa: float) -> float:
    """通用可扩展性定律。sigma 是串行项，kappa 是相干性（节点间协调）项。
    kappa 大于 0 时吞吐曲线存在峰值，超过峰值继续扩容是负收益。"""
    return n / (1.0 + sigma * (n - 1) + kappa * n * (n - 1))

def usl_peak(sigma: float, kappa: float) -> float:
    """吞吐达到峰值的节点数。"""
    return math.sqrt((1.0 - sigma) / kappa)

# 参数不要猜，用真实压测反推：在 1/2/4/8 节点各压一次，记录相对单节点的吞吐倍数。
# 例如实测 [1.0, 1.90, 3.40, 5.20]，最小二乘拟合得到 sigma 约 0.04、kappa 约 0.002。
sigma, kappa = 0.04, 0.002
for n in (1, 2, 4, 8, 16, 32, 64, 128):
    print(f"n={n:4d}  USL={usl(n, sigma, kappa):6.2f}  Amdahl上限={amdahl(sigma, n):6.2f}")
print(f"吞吐峰值出现在约 {usl_peak(sigma, kappa):.0f} 个节点，再加就是花钱买负收益")

# M/M/1 排队：给定利用率，算排队时间是服务时间的几倍
def queue_factor(rho: float) -> float:
    if rho >= 1.0:
        raise ValueError("利用率大于等于 1 时队列无界增长，没有稳态解")
    return rho / (1.0 - rho)

for rho in (0.5, 0.7, 0.8, 0.9, 0.95, 0.99):
    print(f"利用率 {rho:.0%} 时排队时间是服务时间的 {queue_factor(rho):.1f} 倍")

拟合出来的 σ 和 κ 本身就是诊断结论：σ 偏大说明关键路径上有单点串行（单写库、全局序列、分布式锁），κ 偏大说明节点之间协调太多（锁争抢、缓存广播失效、跨节点一致性同步）。这两类问题都不可能靠加机器解决。

三个容易被忽略的细节。第一，基线必须可复现，波动超过 10% 的基线会让你把噪声当成优化效果。第二，一次只改一个变量，同时改连接池大小和加索引，最后无法归因，还可能两个改动互相掩盖。第三，回归验证必须包含正确性：性能优化最常见的事故是为了快而放宽一致性，比如把强一致读改成读从库，压测数字很漂亮，线上出现「下单后查不到订单」。

压测：结论几乎都错在这一步

延迟与成功率分开看 超时请求被计为失败并排除在延迟统计外 延迟曲线纹丝不动，实际上 5% 的请求根本没返回 同一张图上看 P99 与错误率，任一项越线即视为超容量

协调遗漏值得单独画一下，它是最隐蔽的一个：压测客户端在等慢响应时停止了发压，于是这段时间「本该到达的请求」凭空消失了，而真实用户不会因为你慢就少来。

# --latency 打印完整分位数；--timeout 必须显式设置，否则慢请求会一直挂着污染统计
for c in 20 50 100 200 400 800; do
  echo "=== 并发 $c ==="
  wrk -t8 -c"$c" -d180s --latency --timeout 2s \
      -s mixed-scenario.lua https://api.internal.example.com/ | tee "wrk-c$c.txt"
  sleep 60   # 让下游、GC、连接池回到稳态，避免上一档的尾巴污染下一档
done

瓶颈定位的分层顺序

定位的原则是自外向内、逐层排除，每层只看一两个能一票否决的指标，确认这层没问题再往内走。跳层猜测是最浪费时间的做法。

flowchart TB subgraph L1["第 1 层 客户端与网络"] A1["DNS 解析 TCP 握手 TLS 握手"] A2["跨地域往返 弱网重传 带宽打满"] end subgraph L2["第 2 层 接入层与网关"] B1["连接排队 工作进程打满"] B2["响应缓冲落盘 超时参数配置"] end subgraph L3["第 3 层 应用进程内"] C1["线程池或协程调度排队"] C2["垃圾回收停顿 锁竞争"] C3["序列化与压缩的 CPU 开销"] end subgraph L4["第 4 层 下游调用"] D1["串行 RPC 耗时累加 N+1 调用"] D2["连接池耗尽 重试放大"] end subgraph L5["第 5 层 存储"] E1["慢查询 锁等待 磁盘 IO"] E2["缓存击穿 主从延迟"] end L1 --> L2 --> L3 --> L4 --> L5
层 一票否决的指标 怎么看 指向这一层的信号
客户端与网络 握手耗时占总耗时的比例 curl -w 分段计时，对比服务端访问日志里的请求处理时间 服务端日志说 20ms，客户端感知 300ms
接入层与网关 活跃连接数、排队请求数、网关自身 CPU 网关状态接口；上游响应时间与网关总响应时间的差值 后端各实例都不忙，但网关侧 P99 高
应用进程内 GC 停顿时间占比、线程池队列长度、锁等待时间 jstat -gcutil、线程栈采样、Go 的 block 与 mutex profile CPU 不高但延迟高，且有周期性毛刺（典型 GC 特征）
下游调用 单请求的下游调用次数、连接池获取等待时间 链路追踪里的 span 数量与串并行结构 总耗时接近各下游耗时之和，说明全是串行
存储 数据库侧执行时间、锁等待、主从延迟 慢查询日志、数据库自身统计视图 应用侧慢而数据库侧统计是毫秒级，说明问题在连接池而不是 SQL 
# 第 1 层：一条命令看清握手与首字节的耗时构成（跨地域场景常常这里就结案了）
curl -o /dev/null -s -w 'dns=%{time_namelookup} tcp=%{time_connect} tls=%{time_appconnect} ttfb=%{time_starttransfer} total=%{time_total}\n' \
  https://api.internal.example.com/v1/orders/123

# 第 3 层：CPU 不高却慢，优先怀疑排队、GC、锁
vmstat 1 5                    # r 列持续大于核数，说明 CPU 上已经在排队
jstat -gcutil "$PID" 1000 10  # FGC 次数与 FGCT 增长，说明停顿在吃延迟
jcmd "$PID" Thread.print | grep -c 'BLOCKED'   # BLOCKED 线程数持续不为 0 就是锁竞争

# 第 4 层：连接池是不是耗尽（应用慢 数据库快 就看这里）
ss -tn state established '( dport = :3306 )' | wc -l   # 实际建立的连接数
ss -tn state time-wait | wc -l                          # 大量 TIME_WAIT 说明连接没复用

# 第 5 层：确认数据库侧到底花了多久，避免把连接池问题当成 SQL 问题
mysqladmin -h db-host extended-status | grep -E 'Threads_running|Threads_connected|Slow_queries'

最后一层那个判据非常重要，实践中至少一半的「数据库慢」是假的：应用侧观测到 2 秒，数据库侧统计的执行时间只有 3 毫秒，中间那 1997 毫秒花在等连接池。这类问题的完整分析见应用侧的数据库访问优化；确实是 SQL 与索引层面的问题，见站内数据库优化与MySQL 深度原理。

性能与成本：什么时候该加机器，什么时候加了也没用

资深工程师和新手的区别，往往体现在愿不愿意说「这个问题加两台机器就行，不值得花一周优化」。一台 8 核 16G 云主机一年的费用是几千元量级，一名工程师一周的时间成本是同一个量级甚至更高，而且优化改动本身带来回归风险。但必须先判断这个问题加机器有没有用，否则钱花了问题还在。

问题形态 加机器有效吗 原因 真正的解法
无状态服务 CPU 打满、吞吐不够 有效，接近线性 没有共享状态，σ 与 κ 都很小 直接水平扩容，顺手核对连接池与下游容量
单接口 P99 高但 CPU 很闲 无效 瓶颈是串行等待下游，加副本不减少单请求耗时 串行改并行、消掉 N+1、加缓存
写入集中在单库单表 无效 Amdahl 的串行项，只读副本不能分担写 分片或拆写入路径，见站内数据库优化篇
分布式锁或热点键争抢 越加越糟 USL 的相干性项随节点数平方增长 降低锁粒度、分段累加、本地合并后再提交
消息队列积压、消费者无状态 有效但有天花板 并行度受分区数限制，超过分区数的消费者会空转 先扩分区再扩消费者
跨地域调用带来的固定延迟 无效 物理距离与光速决定下限 就近部署、边缘缓存、合并往返次数
GC 停顿导致的周期性毛刺 部分有效 摊薄单机压力能降低分配速率，但停顿模式不变 降低对象分配率、调整堆大小与收集器参数
反模式 为什么错 正确做法
没有基线就开始优化 改完无法证明是否变好，甚至说不出「原来多慢」 先固化可复现的压测脚本与基线数字，再动手
优化不是瓶颈的那一层 占总耗时 5% 的部分优化到 0，整体也只快 5% 先按耗时占比排序，只动占比最大的那一段
用平均值判断效果 长尾被摊平，指标与用户实际感受脱节 看 P99 与 P999，并与成功率一起看
在测试环境得结论 数据量、并发模型、网络拓扑、缓存命中率全都不同 结论必须在生产量级数据与混合流量下复验
为性能牺牲正确性且不声明 改读从库、去掉校验、放宽事务，问题变成偶发数据错误 任何一致性变更都要显式评审并补正确性用例
过早优化与过晚优化 前者把时间花在不存在的问题上，后者让性能债累积到必须重写 架构选型阶段只做量级判断，细节优化等真实数据出现
把压测峰值当容量规划值 峰值处系统已在排队，线上一有抖动就雪崩 取 P99 拐点档位的 50% 到 60% 作为规划水位
❌
最容易踩的坑
  • 用平均响应时间做告警阈值：1% 的请求卡 5 秒，平均值只涨 49ms，告警永远不会响。
  • 对多个实例的 P99 求平均或取最大值当全局 P99：分位数不可加，必须先合并直方图桶再算。
  • 只监控 P99 不监控 P999：恰好 1% 的慢请求在 P99 上正好落在边界，读出来完全正常。
  • 直方图桶边界设得太粗（只有 10ms、100ms、1s、10s 几档）：算出来的 P99 误差能到几十个百分点，却没人知道。
  • 把 CPU 80% 当成「还有两成余量」：按 M/M/1，此时排队延迟已是服务时间的 4 倍，再加 10% 流量延迟翻倍。
  • 压测用小数据集：测试库数据全在内存、索引层高更矮，SQL 快一到两个数量级，上线立刻打回原形。
  • 用闭环压测工具测尾延迟：服务端卡住时客户端也停止发压，协调遗漏能让 P99 低估一个数量级。
  • 压测没预热就开始统计：即时编译未生效、连接池与缓存全空，前一分钟的数据能把整体均值拉高一倍。
  • 没确认压测客户端不是瓶颈就下结论：压测机 CPU 打满或端口耗尽，会完美伪装成「服务端到顶了」。
  • 一次改多个变量：同时调连接池、加索引、加缓存，最后既无法归因，也可能两个改动互相抵消。
  • 只压单接口做容量规划：缓存命中率接近 100%、没有混合流量争抢，容量通常高估 3 到 5 倍。
  • 延迟统计把超时请求排除在外：最慢的样本被丢掉，曲线纹丝不动而用户已经打不开页面。
  • 遇到锁竞争或热点键时选择扩容：USL 的相干性项随节点数平方增长，节点越多吞吐越低。
  • 优化完不做回归防护：关键接口的 P99 会随每次迭代缓慢退化，半年后回到起点且没人察觉。
