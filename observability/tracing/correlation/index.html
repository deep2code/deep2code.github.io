日志指标链路三者关联：traceID、exemplar 与下钻路径

本篇只讲「关联」这一件事：怎么用 traceID 把日志、指标、链路真正串成一条可以一路点下去的排障路径。Span 数据模型与 SpanKind、W3C traceparent 传播协议与断链场景、头部采样与尾部采样、Collector pipeline，都在站内 OpenTelemetry 怎么接 里写透了，本篇不重复；日志字段规范与上下文透传的代码见 结构化日志落地，日志派生指标与告警见 从日志派生指标与告警。

为什么关联比单独任何一支都重要

三大支柱各自回答一个问题：指标告诉你哪里坏了（订单服务 P99 从 200ms 涨到 2s），链路告诉你哪一跳慢（慢在库存服务的一次 DB 查询上），日志告诉你为什么（那次查询命中了一个没走索引的分支，因为灰度配置把某个开关打开了）。任何一支单独存在时，它的回答都在半路上断掉。

三者割裂的具体表现是：拿到告警后，人在三个系统之间用时间戳和 IP 做手工 join。指标面板显示 10:12 有尖刺，于是去日志系统把时间窗设成 10:11 到 10:13，搜出六万条，靠肉眼找可疑的；找到一条可疑日志后拿它的 pod 名和时间点，去链路系统按服务加时间范围翻，翻出几十条 trace，再一条条看哪条对得上。这个过程通常要几十分钟，而且结论经常是错的——时间戳对齐误差、同一秒内多个请求、时钟漂移，都会让你 join 到错误的那一条上。

每一步都是精确匹配不是猜
排障环节三者割裂用 traceID 关联
从告警定位到具体请求只能按时间窗筛，10 至 20 分钟告警里带样本 trace_id，一次点击
确定慢在哪一跳翻多个服务的日志比对时间差火焰图直接看出来，秒级

traceID 是唯一的粘合剂：完整落地清单

关联不需要什么复杂机制，只需要一个在所有系统里都出现、且名字一样的 ID。难的不是原理，是清单里的每一条都要真做到——漏掉任意一条，链条就在那里断掉。

动作做法漏掉的后果
入口生成或继承网关与各服务入口都要处理：有 traceparent 就继承，没有就新建只在网关生成时，内网直连调用与回调入口的链路凭空断开
透传到所有下游HTTP 头、gRPC metadata、MQ 消息头；用 SDK 的自动注入而不是手写某一跳没透传，下游成为孤立 trace，且现场很难发现
定时任务与脚本自行生成任务入口显式开 root span后台任务的日志完全无法与任何链路关联
注入每条日志的固定字段在 logger 封装层自动带 trace_id 与 span_id关联退化成时间窗搜索，本篇全部收益丧失
写进 HTTP 响应头中间件里 Trace-Id 响应头；前端错误页展示用户报障时只能给时间和截图，定位成本高一个量级
错误上报与工单带上前端异常上报、客服工单模板、审批单都留字段跨团队协作时每次都要重新定位
指标的 exemplar 带上直方图观测时附带 trace_id从「P99 高」到「哪条慢」之间仍然是断层
下游数据里留痕关键业务表加一列 trace_id（只对写操作）数据异常时无法回溯是哪一次请求写进去的
✅
把 traceID 返回给客户端，收益极高但极少人做

加一行响应头，用户报障时就能直接给你 traceID，你一次精确查询就还原出完整现场，不用再问「大概几点」「什么账号」。前端把它展示在错误提示里（哪怕是折叠的小字），客服工单模板加一个字段，这件事的总实现量不到半天。担心信息泄露的话：traceID 本身不含业务语义，它只是一个随机的 128 位 ID，泄露它并不能反查任何数据——前提是你的日志查询接口本身有权限控制。

// Go：一个中间件同时做四件事
// 1) 继承或生成 trace 上下文  2) 把 trace_id 注入请求域的 logger
// 3) 把 trace_id 写回响应头  4) 观测耗时时附带 exemplar
package middleware

import (
    "net/http"
    "time"

    "github.com/prometheus/client_golang/prometheus"
    "go.opentelemetry.io/otel"
    "go.opentelemetry.io/otel/propagation"
)

var reqDuration = prometheus.NewHistogramVec(prometheus.HistogramOpts{
    Name:    "http_server_duration_seconds",
    Buckets: prometheus.DefBuckets,
}, []string{"route", "status"})

// propagator 用标准 W3C 格式，不要自己造 X-Request-Id 那一套
var propagator = propagation.TraceContext{}

func Observe(next http.Handler) http.Handler {
    tracer := otel.Tracer("http-server")

    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        // 有 traceparent 头就继承，没有则由 tracer 新建 root span
        ctx := propagator.Extract(r.Context(), propagation.HeaderCarrier(r.Header))
        ctx, span := tracer.Start(ctx, r.Method+" "+routeOf(r))
        defer span.End()

        sc := span.SpanContext()
        traceID := sc.TraceID().String()

        // 关键一步：响应头回带，用户报障时可直接提供
        w.Header().Set("Trace-Id", traceID)

        // 请求域 logger 绑定 trace 字段，业务代码无需手写
        ctx = WithLogger(ctx, Base().With(
            "trace_id", traceID,
            "span_id", sc.SpanID().String(),
        ))

        start := time.Now()
        rec := &statusRecorder{ResponseWriter: w, code: 200}
        next.ServeHTTP(rec, r.WithContext(ctx))

        obs := reqDuration.WithLabelValues(routeOf(r), itoa(rec.code))
        // exemplar 只在被采样的 span 上附带才有意义：
        // 没被采样的 trace 在链路系统里查不到，点过去是空的
        if sc.IsSampled() {
            obs.(prometheus.ExemplarObserver).ObserveWithExemplar(
                time.Since(start).Seconds(),
                prometheus.Labels{"trace_id": traceID},
            )
        } else {
            obs.Observe(time.Since(start).Seconds())
        }
    })
}

exemplar：跨过「P99 高」到「哪一条慢」的鸿沟

直方图是聚合结构，它的设计目的就是丢掉个体。所以「P99 是 2 秒」这句话本身无法继续追问下去，过去只能靠时间窗回日志里翻慢请求，而慢请求在总量里可能只占万分之一。exemplar 的做法很直接：让每个 bucket 附带少量具体样本的 traceID，Grafana 在延迟面板上把它们画成小点，点一下就跳到那条 trace。它解决的是可观测性里最实际的一个断层。

启用环节要点不做的后果
应用侧暴露用 ObserveWithExemplar，并且 metrics 端点必须以 OpenMetrics 格式输出exemplar 在文本格式里没有位置，会被静默丢弃
Prometheus 抓取启用 exemplar-storage 特性，抓取时协商 OpenMetrics抓到了也不存，查询返回空
只给被采样的 span 附带判断 IsSampled()点过去链路系统查不到，用户以为系统坏了
Grafana 面板查询选项里开 exemplar，并配置指向链路数据源的跳转点不动，等于没做
存储量exemplar 是环形缓冲，默认保留量有限，只覆盖最近一段时间回看昨天的尖刺时找不到 exemplar，属正常现象
label 精简exemplar 的标签只放 trace_id塞多余标签会占满缓冲，能保留的样本数下降

从告警到根因的导航路径设计

把「每一跳都可点击」当成硬指标，是可观测性成熟度最实在的衡量方式——它没法靠买产品解决，只能靠把配置一条条做对。路径是固定的五跳：告警 → 看板 → 链路 → 日志 → 代码。

具体配置在 Grafana 里是两个能力：derived fields（Loki 数据源里用正则从日志行提取 trace_id，自动渲染成指向链路数据源的按钮）和 data links / tracesToLogs（从 trace 详情反向跳到按 traceID 过滤的日志查询）。两个方向都要配，因为排障既会从指标往下走，也会从一条可疑日志往上找链路。

# Grafana 数据源 provisioning：把三者双向打通
apiVersion: 1
datasources:
  - name: Loki
    type: loki
    uid: loki-prod
    url: http://loki-gateway.observability:3100
    jsonData:
      # derivedFields：从日志里提取 trace_id 并渲染成跳转按钮
      derivedFields:
        # 结构化日志直接用 JSON 路径，不需要正则，稳定得多
        - name: TraceID
          matcherType: label
          matcherRegex: trace_id
          datasourceUid: tempo-prod
          url: '${__value.raw}'
          urlDisplayLabel: '查看链路'
        # 兼容尚未结构化的老服务：从文本里正则提取
        - name: TraceIDLegacy
          matcherType: regex
          matcherRegex: 'trace_id=([a-f0-9]{32})'
          datasourceUid: tempo-prod
          url: '${__value.raw}'

  - name: Tempo
    type: tempo
    uid: tempo-prod
    url: http://tempo-query.observability:3200
    jsonData:
      # 从 trace 详情跳到该 span 所属服务、按 traceID 过滤的日志
      tracesToLogsV2:
        datasourceUid: loki-prod
        # 只带 service 与 pod 标签，避免生成一个永远查不到结果的过滤条件
        tags:
          - key: service.name
            value: service
        spanStartTimeShift: '-2m'    # 向前留缓冲，日志时间戳与 span 常有偏差
        spanEndTimeShift: '2m'
        filterByTraceID: true
        filterBySpanID: false        # 按 span 过滤常常查不到，日志未必带 span_id
      # 从 trace 跳到该服务的 RED 指标面板
      tracesToMetrics:
        datasourceUid: prom-prod
        queries:
          - name: '该服务 P99 延迟'
            query: 'histogram_quantile(0.99, sum by (le) (rate(http_server_duration_seconds_bucket{service="$${__span.tags["service.name"]}"}[5m])))'

  - name: Prometheus
    type: prometheus
    uid: prom-prod
    url: http://prometheus.observability:9090
    jsonData:
      # exemplar 跳转：延迟面板上的小点直接点到 trace
      exemplarTraceIdDestinations:
        - name: trace_id
          datasourceUid: tempo-prod

跨系统关联的实现细节：字段名与采样

两个细节能让上面所有配置全部失效。

第一是字段名。不同语言的 SDK 与日志库默认输出的 trace 字段名不一样，同一家公司里常见四五种写法并存。字段名不统一时，derived field 规则、跳转链接、查询模板都得按服务写一份，新服务接入必然漏配，而且漏配的表现是「按钮不出现」，很容易被当成 Grafana 的问题。唯一可靠的做法是在内部 logger 封装里把字段名写死，不给业务方选择权。

来源默认字段名统一成
OTel 日志规范 / ECStrace.id 或 trace_idtrace_id
Java 加 OTel 的 MDC 注入trace_id、span_id、trace_flags保持，作为基准
Spring Cloud Sleuth 旧版X-B3-TraceId、traceId迁移时在 encoder 里改名
部分商业 APM agentdd.trace_id 之类带前缀的名字在 Collector 或采集侧 rename
自研网关X-Request-Id保留但另存字段，不要和 trace_id 混用
Node 与 Python 社区库traceId 驼峰写法居多在 formatter 里统一改成下划线

第二是采样导致的「有 traceID 但查不到链路」。这是高频困惑：日志全量保留，trace 按 1% 采样，于是 99% 的 traceID 在链路系统里根本不存在。第一次遇到的人几乎都会认为链路系统在丢数据，然后花时间去查 Collector。它不是故障，是采样的必然结果。

组合现象处理
头部采样 1%，日志全量99% 的 traceID 点过去是空的日志里加 sampled 标记；或对错误请求强制采样
尾部采样未配置错误规则恰恰是出故障的那条 trace 找不到Collector 的尾部采样加 status_code=ERROR 与延迟阈值规则
trace 保留 3 天，日志保留 30 天回看一周前的日志时链路全空保留期对齐，或至少对错误 trace 延长保留
只在网关采样，下游各自决策同一条链路一半的 span 存在一半不存在采样决策必须随上下文传播，下游只遵从不重新决策
exemplar 带了未采样的 trace_id面板上的点全是死链只对 IsSampled() 为真的请求写 exemplar

异步与批处理：用 links，不要硬套父子关系

MQ 消费、定时任务、重试这三类场景，把它们塞成父子关系会得到畸形的 trace：生产者和消费者可能相隔几小时，一条 trace 的时间跨度变成几小时；一个批次消费 500 条消息，这 500 条来自 500 个不同的上游请求，硬套父子等于把 500 棵树粘成一团。OTel 为此提供了 span links：表达「有因果关系，但不是同一次调用」。

场景用父子关系用 links推荐
同步 RPC 调用正确，这就是父子不必要父子
MQ 单条消费trace 时间跨度失真，且生产侧 span 可能已结束上报新 trace 加一个 link 指向生产者links
MQ 批量消费不可能，一个 span 只有一个 parent一个 span 带 N 个 linklinks
定时任务扫表处理无上游可挂每条记录的来源 trace 作为 linkroot span 加 links
失败重试重试挂在原 span 下会让原 trace 一直不结束新 trace 加 link 指向上一次尝试links
扇出后聚合父子可表达不必要父子
 
// Kafka 批量消费：开新 trace，用 links 指回每条消息的生产侧上下文
// 这样既保住了因果可追溯，又不会产生跨越数小时的畸形 trace
func consumeBatch(ctx context.Context, msgs []*kafka.Message) {
    tracer := otel.Tracer("order-consumer")
    prop := propagation.TraceContext{}

    links := make([]trace.Link, 0, len(msgs))
    for _, m := range msgs {
        // 从消息头里取出生产侧写入的 traceparent
        mctx := prop.Extract(context.Background(), kafkaHeaderCarrier(m.Headers))
        if sc := trace.SpanContextFromContext(mctx); sc.IsValid() {
            links = append(links, trace.Link{SpanContext: sc})
        }
    }

    // 注意：是 WithLinks 而不是把某条消息当 parent
    ctx, span := tracer.Start(ctx, "consume order events",
        trace.WithSpanKind(trace.SpanKindConsumer),
        trace.WithLinks(links...),
        trace.WithAttributes(
            attribute.Int("messaging.batch.message_count", len(msgs)),
        ),
    )
    defer span.End()

    log := L(ctx).With(
        "trace_id", span.SpanContext().TraceID().String(),
        "batch_size", len(msgs),
    )

    for _, m := range msgs {
        // 每条消息一个子 span，它的日志能精确定位到这一条
        mctx, ms := tracer.Start(ctx, "handle order event")
        if err := handle(mctx, m); err != nil {
            ms.RecordError(err)
            // 让这条 trace 在尾部采样时必定被保留
            ms.SetStatus(codes.Error, "handle failed")
            L(mctx).Error("handle order event failed",
                "offset", m.TopicPartition.Offset, "err", err)
        }
        ms.End()
    }
    log.Info("batch consumed")
}

关联的成本与取舍

做法成本收益建议
日志加 trace_id 与 span_id 字段每条日志多约 60 字节，日志总量涨 5% 到 10%关联的全部收益都建立在这一条上必做，没有取舍空间
响应头回带 trace_id几乎为零用户报障定位成本降一个量级必做
exemplar少量内存与存储，标签需精简补上「哪一条慢」的断层建议做，只给延迟与错误直方图配
trace 全量采样链路存储成本最高，常是日志的数倍任何 traceID 都查得到不建议；用尾部采样保错误与慢请求
业务表加 trace_id 列一列字符串，写入略增数据异常可回溯到具体请求只对关键写操作表做
trace 与日志保留期对齐链路存储成本上升避免「点过去是空的」折中：错误 trace 延长保留，正常 trace 短留

反模式

反模式后果正确做法
各服务用不同的 trace 字段名跳转规则要按服务写，新服务必然漏配logger 封装里写死字段名，接入即合规
只在网关埋点内网直连、回调、消费者、定时任务全是黑洞每个入口都处理继承或生成
traceID 不返回给客户端用户报障只能给时间和截图响应头回带，前端展示，工单留字段
日志和链路存在两个互不相通的系统关联只能靠人复制粘贴 ID配置双向跳转，两个方向都要通
采样后不保留错误链路出故障的那条 trace 恰好被丢弃尾部采样按错误与延迟强制保留
exemplar 带未采样的 trace_id面板上的点全是死链，用户失去信任判断采样标志后再写 exemplar
把 MQ 消费硬套成父子关系trace 跨越数小时，批量消费无法表达新 trace 加 span links
自造 X-Request-Id 代替 W3C 标准与任何标准 SDK 都对不上，第三方组件无法接入用 traceparent，历史 ID 另存字段
链路留 3 天日志留 30 天回看稍早的日志时链路全空，被当成系统故障保留期对齐或对错误 trace 延长
把 trace_id 放进指标标签时序库基数爆炸，这是最贵的错误之一用 exemplar 承载样本，标签只放低基数维度
❌
最容易踩的坑
  • 日志里有 trace_id 但链路系统查不到，绝大多数是采样导致的正常现象，却几乎每个团队都会先去怀疑 Collector 丢数据。
  • 尾部采样规则里没有 status_code=ERROR 和延迟阈值，结果被保留的全是正常请求，出事的那条恰好丢了。
  • exemplar 没走 OpenMetrics 格式暴露，应用侧调了 ObserveWithExemplar 但数据被静默丢弃，查询永远为空。
  • 给未采样的请求也写 exemplar，面板上的点全是死链，用了两次之后就没人再点。
  • 把 trace_id 当成指标标签，时序库基数瞬间爆炸；trace_id 只能出现在 exemplar 和日志里。
  • 字段名不统一，traceId 与 trace_id 并存，Grafana 的 derived field 按钮在一半服务上不出现。
  • 只在网关生成 traceID，内网直连调用、第三方回调、MQ 消费、定时任务全部成为无法关联的黑洞。
  • MQ 消息头没透传 traceparent，消费侧成为孤立 trace，而生产侧看起来一切正常，很难察觉。
  • 把 MQ 消费硬套成生产者的子 span，一条 trace 时间跨度几小时，火焰图完全不可读。
  • Grafana 的 tracesToLogs 配了 filterBySpanID，而日志里其实没有 span_id 字段，跳过去永远是空结果。
  • trace 保留 3 天、日志保留 30 天，回看上周日志时所有链路链接都是空的，被反复当成故障上报。
  • traceID 不回带给客户端，用户报障后先花二十分钟按时间和账号定位请求，而这一步本来可以是零成本。
  • 日志时间戳与 span 时间存在偏差却没配 spanStartTimeShift，跳过去的日志查询窗口刚好错开，显示没有日志。
