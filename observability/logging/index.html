应用侧日志工程：记什么、分级判据与性能开销

🏷️ 日志

本篇只讲应用侧的日志工程：一行 log.info 该不该写、写成什么级别、会花掉多少 CPU 和多少钱。采集链路与 ELK/EFK 架构选型、索引分片与 ILM、mapping 的 text 与 keyword 之争、容量估算乘法链，都在站内 日志平台架构取舍与容量规划 里写过，本篇不重复；告警方法论、SLI/SLO 与 on-call 见 监控入门。落地细节分三篇：结构化日志 讲字段与各语言库，从日志派生指标 讲日志出告警，三者关联 讲 traceID 串联。

日志有三种读者，于是必须是三种日志

大多数团队的日志治理失败，根因是把三类用途完全不同的日志混在一个文件、一个索引、一套权限里。它们的读者不同：诊断日志给人看，出事时一个人盯着屏幕翻；事件日志给机器看，聚合成计数和分位数；审计日志给合规和安全看，可能几年后才被调阅一次。读者不同，对格式、保留期、权限、能否包含用户数据的要求就完全相反——诊断日志希望尽可能详细，审计日志希望不可篡改，事件日志希望字段稳定到可以按 msg 聚合。

⚠️
审计日志不要走业务日志的异步管道

「日志可以丢」这个前提对审计日志不成立。审计事件应该走独立 logger，或者干脆当成业务数据写库、写事务性消息队列。把它混进和 DEBUG 共享队列的 AsyncAppender 里，一次日志后端抖动就等于审计缺失，而这种缺失通常在被监管问到时才发现。

日志分级：把判据从「感觉」换成「有没有人要做动作」

级别定义人人会背，但落地时全靠感觉，结果是两个极端。第一个极端是全打 INFO：所有人怕漏信息，于是每个方法进出都 INFO，日志量里 90% 是噪声，真正的状态变迁被埋掉，排障时搜出两万行。第二个极端更危险，叫ERROR 满天飞导致告警免疫：参数校验失败打 ERROR、用户输错密码打 ERROR、第三方返回业务失败打 ERROR，于是 ERROR 曲线常年在高位，真出事时曲线从 3000 涨到 3200，没人看得出来，也没人再相信 ERROR 告警。

可操作的判据只有一句：这条日志出现之后，有没有人需要为它做一个动作。有，且要立刻做，是 ERROR；有异常但系统已经自己兜住了（重试成功、降级生效、缓存回源），是 WARN；没有异常，只是关键状态变迁或跨进程交互，是 INFO；其余一切排障细节是 DEBUG，生产默认关闭。

日志与异常处理：同一个异常被记录了五遍

这是应用侧日志最容易做错、也最容易被当成风格问题忽视的地方，而它直接导致告警数量失真和日志成本翻倍。三种典型错法：每层都 catch、记录、再抛出，一次数据库死锁在 DAO、Service、Controller 各留一条带完整堆栈的 ERROR；catch 住只记录不处理，异常被吞掉但流程继续往下走，最后在几十行之后以 NPE 的形式爆炸，真正的根因埋在前面某条日志里；记录时丢了堆栈，写成 log.error(e.getMessage())，线上只看到一行「null」或者「Connection reset」，完全无法定位。

sequenceDiagram participant C as Controller participant S as OrderService participant R as InventoryRepo participant DB as MySQL C->>S: createOrder S->>R: deductStock R->>DB: UPDATE stock SET qty DB--xR: 死锁 错误码 1213 R--xR: catch 后写 ERROR 再抛出 Note over R: 第 1 条 ERROR 带完整堆栈 R--xS: 异常上抛 S--xS: catch 后写 ERROR 再包装成业务异常 Note over S: 第 2 条 ERROR 堆栈完全重复 S--xC: 异常继续上抛 C--xC: catch 后写 ERROR 再返回 500 Note over C: 第 3 条 ERROR
一次故障产生 3 条告警
错误率统计被放大 3 倍

正确原则两句话：要么处理，要么抛出，不要「记录并抛出」；在请求边界统一记录一次，带完整堆栈。边界指全局异常处理器、消息消费者的最外层、定时任务入口、线程池任务 run 方法的最外层——这些地方是异常真正「停下来」的位置，只有这里知道它最终被怎么处理了。底层要做的不是记日志，而是给异常补充业务上下文（哪个订单、哪个 SKU），让边界那一条日志足够定位。

// 反例：每层都记录，一次故障产生 N 条 ERROR，堆栈重复 N 份
public void deductStock(long skuId, int qty) {
    try {
        stockMapper.deduct(skuId, qty);
    } catch (DataAccessException e) {
        log.error("扣减库存失败 skuId=" + skuId, e); // 第 1 条
        throw e;                                    // 上层还会再记一条
    }
}

// 反例：吞掉异常，流程继续，真正的 NPE 在几十行之后爆炸
try {
    user = userClient.get(uid);
} catch (Exception e) {
    log.error("查询用户失败", e);   // 记了，但既没 return 也没抛
}
return user.getName();             // NPE，根因已经被埋在上面

// 正例 1：底层只补上下文并抛出，不记录日志
public void deductStock(long skuId, int qty) {
    int n = stockMapper.deduct(skuId, qty);
    if (n == 0) {
        // 业务语义失败用专门的异常类型，携带定位所需的字段
        throw new InsufficientStockException(skuId, qty);
    }
}

// 正例 2：在请求边界统一记录一次，区分「业务拒绝」与「系统故障」
@RestControllerAdvice
public class GlobalExceptionHandler {

    // 业务规则拒绝：预期结果，不需要人介入，用 WARN 且不打堆栈
    @ExceptionHandler(BizException.class)
    public ResponseEntity<ApiError> onBiz(BizException e) {
        log.warn("业务拒绝 code={} detail={}", e.getCode(), e.getDetail());
        return ResponseEntity.badRequest().body(ApiError.of(e));
    }

    // 系统故障：需要人介入，用 ERROR；必须把 Throwable 作为最后一个参数传入，
    // logback / log4j2 才会打印完整堆栈；写成字符串拼接就只剩 message
    @ExceptionHandler(Exception.class)
    public ResponseEntity<ApiError> onFatal(Exception e) {
        log.error("请求处理失败 uri={} trace_id={}",
                MDC.get("uri"), MDC.get("trace_id"), e);
        return ResponseEntity.status(500).body(ApiError.internal());
    }
}
✅
一条 lint 规则就能拦住 80% 的重复日志

规则内容：同一个 catch 块中同时出现日志调用和 throw 语句就报错。实现成本极低，却能直接消灭「记录并抛出」。配套再加一条：catch 块内的日志调用，最后一个参数必须是 Throwable，避免 e.getMessage() 式的堆栈丢失。

该记什么：以「跨边界」为单位，不是以方法为单位

决定记不记的标准不是这段代码重不重要，而是它是否跨过了一个边界。进程内的方法调用出问题可以靠堆栈定位；跨进程、跨线程、跨时间（定时任务、延迟消息）的调用一旦出问题，堆栈什么都告诉不了你，只能靠日志。

时机 级别 必须带的字段 不记的后果
请求入口 INFO trace_id、路由、调用方标识、关键业务主键 无法确认请求是否到达本服务，扯皮从这里开始
请求出口 INFO 状态码、总耗时、响应大小 只能看网关侧数据，分不清是本服务慢还是网络慢
外部调用（HTTP、RPC、DB、缓存、MQ） INFO 目标地址或方法名、耗时、结果码、重试次数 故障时分不清是谁慢，排障时间基本都耗在这一步
状态变迁 INFO 实体 ID、旧状态、新状态、触发原因 数据错了无法回溯是哪一步改的，对账无从下手
重试与降级触发 WARN 第几次重试、退避时长、降级原因、熔断器状态 看不见系统正在「勉强撑着」，直到彻底崩
定时任务起止 INFO 任务名、分片、处理条数、耗时、成功失败数 任务静默不执行是最难发现的故障之一
启动完成与配置加载 INFO 版本号、生效配置摘要、连接的下游地址 配置漂移导致的诡异问题无法自证
优雅关闭 INFO 收到信号、在处理请求数、等待耗时 发布期抖动无法判定是否来自未排空的请求

绝不能记什么：日志是绕过所有存储层加密的旁路

这一节的核心不是「敏感信息要脱敏」这句人人会说的话，而是一个很少被讲透的事实：日志的访问权限通常远宽于数据库。数据库有字段级加密、脱敏视图、行级权限、访问审计；而 Kibana 往往整个研发团队都能登录、能全文检索、能导出 CSV，还常常给外包和乙方开了只读账号。把身份证号打进日志，等于把数据库上所有安全措施一次性绕过，而且留存副本会跟着索引快照扩散到备份存储里。合规检查真正会追的就是这条路径。

内容 为什么绝对不行 正确做法
密码、密钥、私钥 明文泄露即可直接利用，且被索引长期留存 一个字符都不记；登录失败只记结果与账号标识
完整银行卡号 受卡组织规范约束，属明确违规 只保留前 6 后 4，中间固定长度掩码
身份证号、护照号 强标识个人信息，一次泄露不可撤销 只记内部用户 ID；必要时记末 4 位
手机号、邮箱 可直接用于骚扰与撞库 中间四位掩码，邮箱只留首字符与域名
完整 token、Cookie、Authorization 头 有效期内可直接重放，等于会话劫持 只记前 8 位指纹或哈希，便于关联不便于使用
完整请求体与响应体 既是敏感数据集合，又是日志量第一杀手 记大小与摘要字段；排障时按 trace_id 开临时开关
用户输入原文未过滤 可被用于日志注入与日志伪造 结构化输出，或过滤 CR 与 LF 后截断长度

日志注入值得单独说。如果日志是纯文本行式的，用户在昵称里放一个换行加一段伪造前缀，就能在日志里凭空「造出」一行看起来合法的记录，用来掩盖自己的行为、污染统计，甚至骗过基于关键词的告警规则。纯文本日志必须过滤输入中的 CR 与 LF 并限制长度。JSON 结构化日志天然免疫：换行在序列化时被转义成两个可见字符，一条日志永远只占一行，行边界不可能被用户数据破坏——这是选择结构化日志被严重低估的一个安全收益，落地细节见 结构化日志。

性能开销：日志是少数能把业务拖垮的「辅助功能」

「打日志能有多慢」是普遍的低估。开销分四块：字符串拼接与序列化发生在调用点，即使级别被关掉，参数表达式也已经执行完了；格式化与写出要占 CPU，一条带十几个字段的 JSON 日志在百微秒量级；同步写盘会把业务线程卡在 write 上，容器里写 stdout 还要经过运行时的日志驱动，后者的处理能力常常先成为瓶颈；磁盘 IO 争抢最阴——一个服务把日志量打上去，同机其他容器的 IO 延迟一起劣化，排查时根本想不到根因在别人的 DEBUG 开关上。

if (log.isDebugEnabled()) 的意义就在第一块：它不是防止日志被写出（级别判断本来就会拦住），而是防止参数表达式被求值。log.debug("order=" + order.toJson()) 里的 toJson() 在 DEBUG 关闭时依然会执行。用占位符形式 log.debug("order={}", order) 可以避免拼接，但如果参数本身需要重计算或会触发懒加载，仍然要用级别判断包一层。

采样与限流：一个循环打十万条

日志量失控几乎都不是「每个接口多打了两行」造成的，而是某个循环或某条高频失败路径造成的。下游挂掉时，每秒一万次调用各打一条 ERROR，五分钟三百万条，日志平台的写入队列先崩，然后磁盘满，然后这个服务连同同机的邻居一起挂。这是典型的故障放大：日志本该帮你看清故障，结果成了故障的一部分。

防护手段是采样和聚合，而且要做在应用侧——等到采集侧或平台侧限流，机器上的磁盘已经在写满了。原则是相同的 key 在时间窗内只记录前 N 条，其余只累加计数，窗口结束时补一条「本窗口同类日志被抑制 M 条」。同时把重复失败转成指标：错误计数应该是 counter，而不是十万行日志。

// zap 的采样器：以 (level, message) 为 key 做每秒限流
// First=100 表示每秒前 100 条正常输出，Thereafter=1000 表示之后每 1000 条采样 1 条
// 关键点：key 是 message 模板，所以 message 必须是稳定文本、变量放字段，
// 否则每条 message 都不同，采样器完全失效（这是最常见的踩坑）
package logging

import (
    "os"
    "time"

    "go.uber.org/zap"
    "go.uber.org/zap/zapcore"
)

func NewProdLogger() *zap.Logger {
    encCfg := zap.NewProductionEncoderConfig()
    encCfg.TimeKey = "ts"
    encCfg.EncodeTime = zapcore.RFC3339NanoTimeEncoder
    encCfg.MessageKey = "msg"

    core := zapcore.NewCore(
        zapcore.NewJSONEncoder(encCfg),
        // Lock 保证多 goroutine 写 stdout 时不会交错撕行
        zapcore.Lock(zapcore.AddSync(os.Stdout)),
        zap.NewAtomicLevelAt(zapcore.InfoLevel),
    )

    sampled := zapcore.NewSamplerWithOptions(core, time.Second, 100, 1000)

    // AddStacktrace 只对 Error 及以上抓栈；对 Warn 抓栈会明显拖慢
    return zap.New(sampled,
        zap.AddCaller(),
        zap.AddStacktrace(zapcore.ErrorLevel),
    )
}

// 高频失败路径的正确写法：次数进指标，日志只留样本
func onUpstreamFail(log *zap.Logger, target string, err error) {
    upstreamFailTotal.WithLabelValues(target).Inc() // 指标负责「多少次」
    log.Warn("upstream call failed",                // 日志负责「长什么样」
        zap.String("target", target),
        zap.Error(err),
    )
}

日志量与成本：先算一遍再决定规范

规范之争往往停留在口味上，算一遍量级就没什么可争的了。单条结构化日志按 600 字节到 1 KB 估（带 trace_id、服务名，尤其带堆栈时远超这个数），乘以每请求条数、乘以 QPS、乘以副本数与保留天数，再乘以索引膨胀系数。详细的容量估算乘法链在 日志平台架构取舍与容量规划 里，这里只给应用侧最该记住的对照（按单条 1 KB、1000 QPS、单副本估算）。

场景 每请求日志条数 日增原文量 说明
入口出口各一条 2 约 170 GB 基本是下限
再加 3 次外部调用各一条 5 约 430 GB 有节制的正常水位
每个方法进出都打 INFO 30 以上 约 2.6 TB 成本失控的典型形态
生产误开 DEBUG 100 以上 约 8.6 TB 通常先打满磁盘 IO，再打满磁盘
记录完整请求响应体 2 条但单条 20 KB 约 3.4 TB 条数没涨，字节数涨 20 倍
下游故障时每次失败一条 ERROR 峰值每请求 1 条 5 分钟内 300 万条突发 无采样时足以压垮采集与写入链路

规范怎么真正落地：靠封装和 lint，不靠文档

见过太多团队写了十页日志规范，半年后线上日志依旧五花八门。原因很简单：规范是可选的，而代码是强制的。可行做法是把规范做成一个内部 logger 包，把必备字段、trace_id 注入、脱敏、采样、异常记录方式全部内置成默认行为，业务方拿到的 API 只允许做正确的事；再用 lint 和依赖检查禁止绕过（禁止直接依赖原始日志库、禁止字符串拼接消息、禁止 catch 块内同时记录与抛出）。剩下的靠 CI 里一个日志抽样检查：从预发环境采一千条日志，校验必备字段齐全率和 msg 的唯一值数量——唯一值过多说明变量被拼进了 msg。

反模式 为什么错 怎么改
catch 后记录再抛出 一次故障 N 条 ERROR，告警和错误率全部放大 底层只抛出并补上下文，边界统一记一次
log.error(e.getMessage()) 丢掉堆栈，线上只剩一行无信息量的文本 把 Throwable 作为最后一个参数传入
业务规则拒绝打 ERROR ERROR 基线被抬高，真故障不可见 预期内的拒绝用 WARN 或 INFO，只记结果码
变量拼进 message 无法按 msg 聚合，采样器与告警规则同时失效 msg 固定为模板，变量一律进字段
循环体内逐条打印 单请求上千条，一次批处理打满磁盘 循环外汇总一条，带处理条数与失败条数
把请求响应体整体记录 敏感数据与成本双杀 记大小与摘要，排障时按 trace_id 临时开启
异步 appender 选阻塞策略 日志后端抖动直接变成接口超时 业务日志 neverBlock 为 true，审计日志单独走同步
在容器里写文件再挂盘 轮转、权限、清理三重麻烦，Pod 重建即丢 统一写 stdout，交给运行时与采集器
日志级别写死在代码里 线上要排障只能重新发布 暴露动态调级接口，或接配置中心热更新
用日志替代指标做统计 成本高、延迟大，还会被采样丢掉 能埋点的直接埋点，日志只留可定位的样本
❌
最容易踩的坑
  • Logback 的 AsyncAppender 默认 queueSize=256 且 neverBlock=false：日志后端一抖，业务线程全卡在打日志上，表现为接口批量超时，而火焰图里看不出业务瓶颈。
  • includeCallerData 设为 true 后每条日志都要抓调用栈，吞吐掉一个量级；很多人为了打印类名行号无意中开启了它。
  • log.debug("body=" + toJson(obj)) 在 DEBUG 关闭时依然会执行 toJson，CPU 白烧；改用占位符，参数需要重计算时再套一层 isDebugEnabled()。
  • 把变量拼进 message 导致 msg 基数爆炸：zap 的采样器、按 msg 聚合的统计、基于 message 的告警规则会同时失效。
  • 每层 catch 都记录：一次死锁产生三到五条 ERROR，告警去重失效，错误率指标被放大数倍。
  • catch 住只记录不处理，方法继续往下执行，最终以 NPE 结束，排障时看到的堆栈和根因完全无关。
  • 生产误开 DEBUG 打满磁盘 IO，同机其他容器延迟一起劣化，而监控只显示「邻居变慢了」。
  • 下游故障时每次失败打一条 ERROR，五分钟内突发数百万条，采集器背压后日志开始丢——恰好在最需要日志的时刻。
  • 把身份证、手机号、完整 token 打进日志，等于绕过数据库的字段加密与行级权限，并随索引快照扩散进备份。
  • 纯文本日志不过滤用户输入中的换行，攻击者可以伪造日志行，掩盖行为并骗过关键词告警。
  • 审计日志和 DEBUG 共享同一个异步队列，队列满时审计事件被当成低价值日志丢弃，直到被监管问到才发现。
  • 日志轮转只配了按天切分没配总量上限，遇到突发日志量当天就把磁盘写满，服务进程因写失败而崩。
