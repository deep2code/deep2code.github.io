日志平台架构取舍与容量规划：Kafka 缓冲、索引分片与 ILM

🏷️ ELK

日志平台上线容易，活得久很难。装完 Filebeat 加 Elasticsearch 加 Kibana 只需要一个下午，但三个月后你会遇到：磁盘写满后索引被自动置成只读、字段数量爆到上限导致写入直接报错、一次大促把写入队列打满丢了一整段日志、某个字段想做聚合却发现类型选错了改不了。这些问题的根源全部在架构取舍和索引设计上，而不是在安装步骤上。这篇讲这两件事。

三种架构形态与它们的适用规模

ELK 这个词现在指代的其实是三种不同复杂度的架构。选错的代价很直接：小规模上 Kafka 是浪费，大规模不上 Kafka 是等着丢数据。

为什么中间要加 Kafka，值得单独说清楚，因为这是最常被省掉、也最常被后悔的一层：

  • 削峰。故障时的日志量通常是平时的 5 到 10 倍（堆栈、重试、降级日志同时爆发）。Elasticsearch 的写入线程池队列满了就会拒绝请求，而这恰恰发生在你最需要日志的时刻。Kafka 能把这个尖峰摊到后面几十分钟慢慢消化。
  • 解耦与不丢。Logstash 扩容、ES 滚动升级、索引模板变更，这些操作都要重启下游。有 Kafka 时采集端完全不受影响，重启后按消费位点续传；没有 Kafka 时只能靠 Filebeat 的本地队列硬扛，队列满了就开始丢。
  • 多消费者与重放。同一份日志往往既要进搜索引擎，又要进数仓、实时风控、审计归档。加一层消息队列后各下游独立消费、独立重放；解析规则写错了，重置位点重跑一遍就行。

采集与处理的分工：谁该干什么

一个常见误解是「Filebeat 只是简化版 Logstash」。它们的定位完全不同：Filebeat 负责可靠采集与背压，Logstash 负责重解析与富化。Filebeat 用 Go 写、内存占用几十 MB，可以在每台机器上跑；Logstash 跑在 JVM 上，堆内存通常要 1GB 以上，只适合集中部署几个实例。

组件 运行开销 核心能力 不适合做什么 失败时的行为
Filebeat Go，几十 MB 内存 文件跟踪与位点记录、多行合并、简单 JSON 解析、背压 复杂正则解析、跨事件聚合、调用外部服务富化 输出阻塞时停止读取文件，等下游恢复；位点存在 registry 里，重启续传
Fluent Bit C，几 MB 内存 与 Filebeat 类似，容器元数据补全更强，插件更轻 同上，且插件生态不如 Logstash 丰富 同样支持磁盘缓冲；内存缓冲满了会丢，必须显式开启文件系统缓冲
Logstash JVM，1GB 以上堆 grok 与 dissect 解析、字段变换、地理与字典富化、多路输出、条件分流 部署在每台业务机器上（资源开销不可接受） 无持久队列时重启会丢内存中的批次，必须开启持久队列或依赖 Kafka 位点
ES Ingest Pipeline 复用 ES 节点资源 常见处理器齐全：grok、dissect、date、gsub、remove、set、条件判断 需要跨事件状态、调用外部服务、极重的正则；它和查询抢同一份 CPU 处理失败时按 on_failure 兜底，配不好会整批写入失败

结论很实用：如果应用已经输出 JSON，Logstash 基本可以省掉，把剩下的一点点处理（补时间戳、脱敏、删无用字段）放进 Ingest Pipeline，链路少一个有状态组件。只有当你需要跨多种异构日志格式做重解析、或者要把同一份数据分发到多个异构后端时，Logstash 才值得留。

filebeat.inputs:
  - type: filestream            # 7.14 起推荐，取代已废弃的 log 类型
    id: app-json-log            # filestream 必须有唯一 id；改动这个 id 等于让它从头重读一遍
    paths:
      - /var/log/app/*.json
    parsers:
      - ndjson:
          target: ""            # 解析出的字段平铺到根层级，而不是嵌到某个对象下
          overwrite_keys: true
          add_error_key: true   # 解析失败时打标记，不要静默丢掉
    prospector.scanner.check_interval: 10s
    close.on_state_change.inactive: 5m   # 5 分钟无写入就关闭文件句柄，防止句柄泄漏
    clean_removed: true         # 文件删除后清理位点记录，否则 registry 会无限膨胀

  - type: filestream
    id: app-stacktrace
    paths:
      - /var/log/app/error.log
    parsers:
      - multiline:              # 不做多行合并，一个 Java 异常会变成 40 条互不相关的日志
          type: pattern
          pattern: '^\d{4}-\d{2}-\d{2}'   # 以日期开头的才是新事件

          match: after

  flush.min_events: 2048       # 攒批发送，比逐条发吞吐高一个量级

索引设计：这套系统真正的核心

日志平台的成败几乎全部由索引设计决定。要点有四个：按时间滚动、用模板统一、用 ILM 自动分层、把分片数算对。

按时间分索引的理由不是「好看」，而是：删除整个索引是常数时间操作，而按条件删除文档要走一遍查询加标记删除，代价高且不回收空间；同时时间范围查询可以直接跳过整个索引。日均 100GB 以下按天分，超过就按小时分或者用 rollover 按大小滚动。

分片数怎么定：目标是单个主分片落在 20 到 50GB，日志这种写入后几乎不更新、以时间过滤为主的数据可以取上限。计算方式是「单索引预估主数据量 ÷ 目标分片大小」向上取整，并尽量取数据节点数的整数倍以便均衡分布。

❌
主分片数创建后不可修改

这是硬约束。想改只能 _split（成倍放大）、_shrink（成因子缩小，且要求所有分片先迁到同一节点）或者 reindex 重建，三种方式在数据量大时都很痛。正确的应对是按时间滚动创建索引，让一次错误的规划最多影响一天的数据，而不是影响全部历史。

日均日志量 索引粒度 单索引主数据 建议主分片数 说明
10GB 以下 按天或按周 10 到 70GB 1 到 2 别为了「看起来专业」切成 5 个分片，小分片只会增加开销
50GB 按天 约 55GB 2 单分片约 27GB，落在经验区间中段
200GB 按天 约 220GB 5 或 6 取数据节点数的整数倍，避免某个节点分到两个分片而别的只有一个
1TB 以上 按小时，或按 50GB 做 rollover 按滚动条件控制 用 max_primary_shard_size 交给 ILM 自动决定 手工按天规划一定会失准，必须交给 rollover
任何规模 —— —— 集群总分片数控制在每 GB 堆内存 20 个以内 分片过多会让主节点上的集群状态更新变慢，几万分片时新建索引可能要等几十秒

ILM（索引生命周期管理）把「索引老了要做什么」变成声明式配置，是控制成本的主要手段：

stateDiagram-v2 [*] --> Hot Hot --> Warm: 满足 rollover 条件后进入老化 Warm --> Cold: 通常 7 到 14 天 Cold --> Frozen: 30 天以上，改为可搜索快照 Frozen --> Delete: 到达保留期 Cold --> Delete: 没有 frozen 阶段时直接删除 Warm --> Delete: 短保留期场景跳过冷阶段 Delete --> [*]
阶段 这个阶段做什么 硬件与副本 是否可写 注意点
hot 承接全部写入；按大小或时间 rollover SSD，副本 1 可写可查 只有 hot 阶段的索引在写，所以 SSD 只需买这一层的容量
warm forcemerge 合并段、shrink 减分片、降低分配优先级 SATA 或低配 SSD，副本 1 只读 forcemerge 很吃 IO，要放在低峰期；shrink 要求分片先集中到一个节点
cold 副本降到 0 或转为可搜索快照，进一步压缩 大容量机械盘 只读，查询变慢 副本降到 0 意味着节点故障会丢这段数据，要先确认有快照
frozen 数据主体放对象存储，节点只留元数据 对象存储 只读，查询延迟从秒级到分钟级 适合审计与合规留存，不适合日常排查
delete 整个索引删除，空间立即回收 —— —— 删除前如有留存要求，先确认快照策略已生效

          }
        }
      }

两个参数值得单独解释。refresh_interval 默认是 1 秒，意思是写入后最多 1 秒可被搜索到，代价是频繁生成新段；日志场景把它放宽到 30 秒，写入吞吐通常能提升三成以上，而「日志晚 30 秒能搜到」完全可以接受。index.codec 设成 best_compression 会换用压缩率更高的算法，存储能省两到三成，代价是取原文时 CPU 略高——日志是典型的写多读少，这笔交易很划算。

mapping 的坑：字段爆炸与 text/keyword

动态映射是字段爆炸的源头。默认情况下 ES 见到新字段就自动推断类型并加进 mapping。日志里只要有人把变量拼进了字段名（比如把用户 ID 当成 key），字段数就会无限增长，先是 mapping 变成几 MB 拖慢集群状态同步，接着撞上 index.mapping.total_fields.limit（默认 1000）导致写入直接报错。

三种应对策略："dynamic": true 是默认（危险）；"dynamic": false 表示未声明的字段照样存进原始文档、但不建索引也不能检索（推荐的折中，出问题时至少数据还在）；"dynamic": "strict" 表示遇到未声明字段直接拒绝写入（契约最强，但一次上线加字段忘了改模板就会丢日志）。日志平台建议用 false，并配合 mapping 评审。

需求 字段类型 能否聚合排序 能否全文检索 代价与陷阱
日志正文里搜关键词 text 不能，直接聚合会报「字段数据默认关闭」 能，会分词 倒排索引体积最大；中文需要额外分词器，否则单字切分效果很差
按服务名、级别、状态码统计 keyword 能，默认生成列式结构 不能，只支持整体精确匹配 单值上限约 32766 字节，超长写入失败，必须配 ignore_above
两种都要（正文既搜又统计） text 加 fields 子字段 用子字段聚合 用主字段检索 存两份，体积增加；子字段一定要设 ignore_above 兜住超长正文
耗时、状态码等数值 integer / short / float 能，支持范围查询 不适用 别用 keyword 存数字，范围查询会退化成词项枚举
只存不查的大字段（请求体快照） text 且 "index": false，或存进 _source 不声明 不能 不能 这是省存储最有效的一招，很多团队给所有字段都建了索引
标签式的动态键值 flattened 有限支持 有限 专门用来避免字段爆炸：整个对象只占一个字段，代价是查询能力受限

查询性能：哪些写法会把集群拖垮

反模式 为什么慢 替代做法
前导通配符，例如查 *timeout* 无法利用倒排索引的前缀定位，必须扫描词典里所有词项 正文用 match 走分词检索；确实需要任意位置匹配时改用 wildcard 类型字段
不带时间范围过滤 查询会打到全部索引与分片，保留 30 天就等于扫 30 倍数据 时间范围永远作为第一个过滤条件，放进 filter 子句以便走缓存
把过滤条件写在 must 里 must 参与打分，无法使用过滤缓存 不需要打分的条件全部放 filter，日志检索绝大多数条件都不需要打分
对 text 字段做聚合 需要把倒排索引反转成内存结构，默认被禁止；强行开启会吃掉大量堆内存 用 keyword 子字段聚合；千万不要打开 fielddata
深分页翻到第 10000 条之后 每个分片都要返回前 N 条再全局排序，代价随偏移线性增长 用 search_after 或 point in time 游标，导出场景用滚动查询
高基数字段的 terms 聚合不限 size 每个分片都要维护巨大的桶集合，容易触发熔断 限制 size，或改用 composite 聚合分页
用脚本字段做实时计算 每个文档都要执行一次脚本，无法走索引 写入时就把派生字段算好，例如直接输出 duration_ms 而不是查询时相减

curl -s "localhost:9200/_cat/allocation?v&h=node,disk.percent,disk.avail"
# 判读：超过 85% 停止向该节点分配新分片；超过 90% 开始迁移分片；
#       超过 95% 触发洪泛保护，索引被加上只读阻塞，且清理磁盘后不会自动解除，必须手工放开：
curl -X PUT "localhost:9200/logs-*/_settings" -H 'Content-Type: application/json' \
     -d '{"index.blocks.read_only_allow_delete": null}'

# 四、字段数量是否接近上限（字段爆炸的早期信号）
curl -s "localhost:9200/logs-2026.09.23/_mapping?pretty" | grep -c '"type"'
# 判读：逼近 index.mapping.total_fields.limit（默认 1000）时写入会整批失败。

# 五、把慢查询记下来，而不是等用户抱怨
curl -X PUT "localhost:9200/logs-*/_settings" -H 'Content-Type: application/json' -d '
{
  "index.search.slowlog.threshold.query.warn": "5s",
  "index.search.slowlog.threshold.fetch.warn": "1s"
}'

容量估算与成本控制

容量估算不要拍脑袋，按下面这个链条逐步乘：

步骤 系数 示例（日均 200GB 原始文本） 说明
结构化膨胀 1.2 到 1.3 240GB 转成 JSON 后每条都重复一遍字段名，字段越多越明显
索引膨胀 0.9 到 1.5 约 260GB 全字段索引且不压缩时接近 1.5；开高压缩、关掉无用字段索引后可低于 1
副本 1 加副本数 520GB 1 副本即乘 2。冷阶段把副本降到 0 可以显著省钱，前提是有快照
保留天数 按需 15 天约 7.8TB 审计日志与调试日志分索引、分保留期，是最有效的省钱手段
磁盘可用率 除以 0.7 约 11TB 85% 是低水位线，必须留足余量，不能按 100% 规划
堆内存 物理内存一半，且不超过 31GB 每节点 64GB 内存配 31GB 堆 超过 31GB 会失去对象指针压缩，实际可用反而变少；剩下的留给文件缓存

成本控制的四个抓手，按性价比排：按用途分索引并设不同保留期（调试日志留 3 天、业务日志 15 天、审计日志 180 天，比统一 30 天省一半以上）；冷热分层（只有 hot 层需要 SSD）；关掉不需要检索的大字段的索引；采样低价值日志（比如健康检查的访问日志按 1% 采样，或者干脆在采集层丢掉）。

结构化日志是前提，日志规范是底线

用 grok 正则解析非结构化日志，是整条链路里最脆的一环。它是 CPU 消耗最大的处理器，写得不好会发生灾难性回溯把管道卡死；更要命的是它与日志文案强耦合——开发改一句日志措辞，解析就失配，字段变成未解析状态，往往几周后才有人发现。正确做法是在应用侧直接输出 JSON，把级别、服务、追踪标识、耗时、状态码都作为独立字段，采集端只做透传。

下面这条 Ingest Pipeline 演示了结构化之后处理层还需要做的几件事：脱敏、清掉换行、删无用字段、失败兜底。

curl -X PUT "localhost:9200/_ingest/pipeline/logs-sanitize" -H 'Content-Type: application/json' -d '
{
  "description": "结构化日志的轻量处理：换行清理、脱敏、字段裁剪",
  "processors": [
    { "set": { "field": "ingest_at", "value": "{{{_ingest.timestamp}}}" } },

    { "gsub": { "field": "message", "pattern": "[\\r\\n]+", "replacement": " ", "ignore_missing": true } },

    { "gsub": { "field": "message", "pattern": "(\\d{6})\\d{6,9}(\\d{4})",
                "replacement": "$1******$2", "ignore_missing": true } },

    { "gsub": { "field": "message", "pattern": "(?i)(password|passwd|token|secret)([=:])[^,;\\s]+",
                "replacement": "$1$2***", "ignore_missing": true } },

    { "remove": { "field": ["host.ip", "agent.ephemeral_id"], "ignore_missing": true } }
  ],
  "on_failure": [
    { "set": { "field": "ingest_error", "value": "{{{_ingest.on_failure_message}}}" } },
    { "set": { "field": "_index", "value": "logs-failed" } }
  ]
}'

第二条 gsub 不只是为了好看。日志注入是真实存在的风险：用户输入里带换行符时，一条日志会被采集端切成两条，攻击者可以伪造出一行「看起来像系统日志」的内容，比如伪造一条登录成功记录来污染审计。防御要做两层——应用侧对写进日志的用户输入做转义，采集或处理侧再把残留的换行替换掉。

sequenceDiagram autonumber participant A as 应用进程 participant F as Filebeat harvester participant K as Kafka participant L as 处理层 participant E as Elasticsearch participant U as Kibana 用户 A->>A: 输出一行 JSON，含 trace_id 与 duration_ms F->>F: 读到行尾，更新 registry 中的位点 F->>K: 攒批发送，默认 2048 条或 1 秒触发 Note over F,K: 下游写不进去时 Filebeat 停止读取文件
靠背压保护自己，不会无限吃内存 K-->>F: 确认写入 L->>K: 按消费组拉取，记录位点 L->>L: 脱敏、清换行、删无用字段 L->>E: _bulk 批量写入 Note over E: 写入后要等一个 refresh_interval 才可被搜索
默认 1 秒，日志场景常调到 30 秒 U->>E: 用 trace_id 精确检索整条链路 E-->>U: 返回跨服务的全部日志

与之配套的日志规范，每一条都对应一类真实踩过的坑：

  • 必须有 trace_id：入口生成或从请求头继承，全链路透传并打进每条日志。没有它就只能靠时间加关键词凑，跨服务排查从几分钟变成几小时。
  • 时间戳带时区：统一用带偏移量的 ISO 8601 格式、统一字段名。否则跨机房日志排序错乱，故障时间线拼不起来。
  • 级别语义统一：ERROR 必须是需要人介入的；可预期的业务失败用 WARN 或 INFO。否则 ERROR 每天几万条，基于错误日志的告警彻底失效。
  • 禁止记录敏感信息：密码、完整卡号、身份证、令牌、完整手机号一律不落盘。日志平台权限通常比数据库宽，泄露影响面更大。
  • 用户输入必须转义：换行与制表符等控制字符转义后再写入，否则会发生日志注入——一条日志被切成多条，审计记录可被伪造。
  • 单条日志有长度上限：应用侧截断（比如 8KB），别把整个请求体或大结果集打进去。keyword 字段超过约 32766 字节会写入失败，单条巨型日志还会撑爆整个批次。
  • 按用途分索引：审计、业务、调试日志分开，各自设保留期与权限。混在一起时保留期只能就高不就低，成本翻倍且无法细分权限。

最容易踩的坑

❌
避坑清单
  • 没有缓冲层就上生产：故障时日志量涨 5 到 10 倍，ES 写入队列满后开始拒绝，你最需要日志的那段恰好缺失。
  • 指望改模板修复已有索引：index template 只对之后新建的索引生效，改完必须等下一次 rollover 或手工 reindex 才见效。
  • 分片数拍脑袋定成 5：主分片数创建后不可改，只能 split、shrink 或重建。按单分片 20 到 50GB 反推，并按天滚动兜住误差。
  • 分片切太碎：每天几十个只有几百 MB 的索引，集群分片数上万，主节点的集群状态更新变慢，新建索引都要等十几秒。
  • 动态映射全开：日志里出现以变量命名的字段后，mapping 无限膨胀，撞上字段数上限后写入整批失败。用 "dynamic": false 加 mapping 评审。
  • 对 text 字段做聚合后打开 fielddata 救急：这会把倒排索引反转进堆内存，高基数字段直接把节点 OOM。应该用 keyword 子字段。
  • keyword 字段不设 ignore_above：超过约 32766 字节直接写入失败，而失败的是整个批次，连带好的文档一起丢。
  • 磁盘涨到 95% 后触发只读保护：read_only_allow_delete 不会随磁盘清理自动解除，必须手工置空，很多人清完磁盘还在纳闷为什么写不进去。
  • JVM 堆开到 32GB 以上：失去对象指针压缩，实际可用内存反而变少。上限 31GB，且不超过物理内存的一半，剩下留给文件系统缓存。
  • 用 grok 硬解析非结构化日志：CPU 消耗最大、最容易被一次文案改动搞失效，还可能因正则回溯把管道卡死。应用侧直接输出 JSON。
  • 忘了多行合并：一个 Java 异常堆栈变成 40 条独立日志，既查不全也把文档数放大几十倍。
  • refresh_interval 留默认 1 秒：写入吞吐白损失三成，而日志晚 30 秒可搜索完全可以接受。
  • 查询不带时间范围，或者把过滤条件写进 must：前者扫全部历史索引，后者放弃过滤缓存并做无意义的打分。
  • 前导通配符查询：从词典头扫到尾，一个人查一次就能让集群抖动。需要任意位置匹配就改用 wildcard 类型。
  • 所有日志一个索引一个保留期：调试日志和审计日志混在一起，保留期只能就高不就低，成本翻倍还没法分权限。
  • 日志里记了密码或完整卡号：日志平台的查询权限通常比数据库宽得多，泄露影响面更大。要在应用侧和处理层做两道脱敏。
  • 用户输入不转义直接打日志：换行符会把一条日志切成多条，攻击者能伪造出以假乱真的系统日志行。
