结构化日志落地：字段规范、各语言库与上下文透传

🏷️ 结构化日志

本篇只讲结构化日志在应用侧怎么落地：字段怎么定、各语言库怎么配、上下文怎么自动带上、脱敏在哪一层做。平台侧的索引 mapping、text 与 keyword 的取舍、grok 解析的性能成本论证、ILM 与容量规划都在站内 日志平台架构取舍与容量规划 里；日志该记什么、分级判据、性能开销见 应用侧日志工程。

为什么必须结构化：把解析成本从平台侧搬回应用侧

「结构化日志便于搜索」只是结果，真正的理由是成本归属。非结构化日志把解析工作推给了管道：Logstash 或 Ingest Pipeline 要对每一条日志跑 grok 正则，而 grok 本质是多个正则的顺序尝试，一条复杂 pattern 单条处理成本在几十到上百微秒，乘上每天几十亿条就是一整批常驻的解析节点。更麻烦的是脆：某个开发改了一句日志文案，解析规则静默失配，字段变成 _grokparsefailure，依赖这些字段的看板和告警一起哑掉，而且往往几天后才被发现。

结构化日志把这一步前移到应用进程内：序列化一次 JSON，平台侧只要 json 解码。应用侧多花的 CPU 是微秒级且分摊在成百上千个实例上，平台侧省掉的是集中式的解析集群和它的运维。

格式变更的影响静默失配，字段丢失但不报错字段名是代码里的常量，改动可被静态检查发现

💡
本地开发不要用 JSON 输出

JSON 日志对人不友好，逼着开发在本地也读 JSON 只会让人开始用 System.out.println。正确做法是按环境切 encoder：本地用彩色文本单行输出，测试与生产用 JSON。字段定义不变，只换序列化方式，这样规范不打折、体验也不受损。

字段规范：一份可以直接抄的字段表

字段规范的价值在于跨服务可比。只要全公司的服务名字段都叫 service、trace 字段都叫 trace_id，一条查询就能跨所有索引用；一旦一半服务叫 traceId、一半叫 trace_id、还有一半叫 tid，就得为每个服务单独建看板。这件事必须在第一天定死，它的迁移成本随服务数量线性增长。

msg 必须是稳定模板，变量全部进字段

这是结构化日志里收益最高、也最常被忽略的一条。msg="order created" order_id=123 和 msg="order 123 created" 在人眼里差别不大，在机器眼里差别是天壤：后者的 msg 基数等于订单数量，任何按 msg 的聚合都退化成「每条一个桶」。

能力msg 拼了变量msg 是稳定模板
统计某类事件次数做不到，需要再写一层正则提取按 msg 直接 terms 聚合
日志转指标规则必须写正则，管道 CPU 上升按字段精确匹配即可计数
zap / zerolog 的采样器完全失效，key 每条都不同正常按 key 限流
告警规则稳定性改文案即失效文案是常量，改动可见
ES 索引体积msg 字段基数爆炸，倒排词典膨胀msg 只有有限枚举值，压缩率高
新异常发现无法区分新 msg 和新变量出现未见过的 msg 即新事件

各语言主流库的正确用法

四个语言的共同点是：用 With 类 API 派生一个带请求上下文的子 logger，而不是在每个调用点手写 trace_id。这是结构化日志真正省力的地方，也是多数团队只做了一半的地方——JSON 输出配好了，但每条日志的上下文还靠手传，于是漏得到处都是。

语言推荐库派生上下文的 API上下文载体主要坑

// Go：slog + 自定义 Handler 做统一脱敏 + context 携带 logger
package logctx

import (
    "context"
    "log/slog"
    "os"
    "regexp"
    "strings"
)

type ctxKey struct{}

var phoneRe = regexp.MustCompile(`1[3-9]\d{9}`)

// 字段名黑名单：命中即整体掩码，不看值长什么样
var sensitiveKeys = map[string]bool{
    "password": true, "passwd": true, "token": true,
    "authorization": true, "id_card": true, "card_no": true,
}

// 只扫字符串类型，避免对数字和时间做无用的正则匹配
func maskPhone(s string) string {
    return phoneRe.ReplaceAllStringFunc(s, func(m string) string {
        return m[:3] + "****" + m[7:]   // 前 3 后 4，长度固定不会越界
    })
}

// 脱敏必须放在 Handler 层：调用方怎么写都绕不过去
func redact(groups []string, a slog.Attr) slog.Attr {
    if sensitiveKeys[strings.ToLower(a.Key)] {
        return slog.String(a.Key, "[REDACTED]")
    }
    if a.Value.Kind() == slog.KindString {
        if v := a.Value.String(); phoneRe.MatchString(v) {
            return slog.String(a.Key, maskPhone(v))
        }
    }
    return a
}

func NewLogger(service, env string) *slog.Logger {
    h := slog.NewJSONHandler(os.Stdout, &slog.HandlerOptions{
        Level: slog.LevelInfo,
        // AddSource 会在每条日志上取调用栈帧，热路径上有可观开销，按需开启
        AddSource:   false,
        ReplaceAttr: redact,
    })
    // 进程级固定字段用 With 一次绑定，之后每条日志自动带上
    return slog.New(h).With(
        slog.String("service", service),
        slog.String("env", env),
    )
}

// 请求入口：派生带 trace 上下文的子 logger 并放进 context
func WithRequest(ctx context.Context, base *slog.Logger, traceID, spanID string, uid int64) context.Context {
    l := base.With(
        slog.String("trace_id", traceID),
        slog.String("span_id", spanID),
        slog.Int64("user_id", uid),
    )
    return context.WithValue(ctx, ctxKey{}, l)
}

// 业务代码只认 ctx，永远不需要手写 trace_id
func L(ctx context.Context) *slog.Logger {
    if l, ok := ctx.Value(ctxKey{}).(*slog.Logger); ok {
        return l
    }
    return slog.Default()
}

// 调用点：msg 是稳定模板，变量全部进字段
func createOrder(ctx context.Context, orderID string, amount int64) {
    L(ctx).Info("order created",
        slog.String("order_id", orderID),
        slog.Int64("amount_cent", amount),
    )
}

上下文透传：结构化日志最难的部分

让每条日志自动带上 trace_id 和 user_id，听起来是配置问题，实际是运行模型问题。Go 靠显式传 context，代价是函数签名污染但绝不会串；Java 靠 MDC，写起来最舒服但埋着最大的雷；Python 的 contextvars 和 Node 的 AsyncLocalStorage 是语言层为异步场景提供的「隐式 context」，行为正确但都有边界。

Java 的 MDC 必须单独讲。MDC 底层是 ThreadLocal，而线程池的线程是复用的，于是有两个方向的故障：主线程提交异步任务，任务在池线程里执行，拿不到 MDC，日志里 trace_id 为空；请求 A 结束时没清理 MDC，线程被请求 B 复用，B 的日志带上了 A 的 trace_id——这一类问题比空值危险得多，因为它会把两个请求的日志错误地串成一条链路，排障时得出完全错误的结论。

// Java：Logback + logstash-encoder + MDC，并修掉线程池两个坑
// 1) 请求边界必须 try/finally 清理 MDC
// 2) 提交到线程池的任务必须显式携带 MDC 快照
@Component
public class TraceMdcFilter extends OncePerRequestFilter {

    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse resp,
                                    FilterChain chain) throws ServletException, IOException {
        Span span = Span.current();
        MDC.put("trace_id", span.getSpanContext().getTraceId());
        MDC.put("span_id", span.getSpanContext().getSpanId());
        MDC.put("uri", req.getRequestURI());
        try {
            chain.doFilter(req, resp);
        } finally {
            // 不清理 = 下一个复用该线程的请求会带上这次的 trace_id
            MDC.clear();
        }
    }
}

// 用装饰器统一解决「异步任务丢 MDC」，不要每处手写
public final class MdcTaskDecorator implements TaskDecorator {

    @Override
    public Runnable decorate(Runnable runnable) {
        // 在提交线程上抓快照（此时 MDC 还在）
        Map<String, String> snapshot = MDC.getCopyOfContextMap();
        return () -> {
            Map<String, String> backup = MDC.getCopyOfContextMap();
            if (snapshot != null) {
                MDC.setContextMap(snapshot);
            }
            try {
                runnable.run();
            } finally {
                // 恢复池线程原有状态，避免污染下一个任务
                if (backup != null) {
                    MDC.setContextMap(backup);
                } else {
                    MDC.clear();
                }
            }
        };
    }
}

@Bean
public ThreadPoolTaskExecutor bizExecutor(MdcTaskDecorator decorator) {
    ThreadPoolTaskExecutor ex = new ThreadPoolTaskExecutor();
    ex.setCorePoolSize(16);
    ex.setQueueCapacity(2000);
    ex.setTaskDecorator(decorator);   // 关键一行
    ex.setThreadNamePrefix("biz-");
    ex.initialize();
    return ex;
}

# 关键点：用 contextvars 而不是 threading.local，
# 否则在 asyncio 下多个协程共享同一个线程，上下文会互相覆盖
import logging
import structlog
from structlog.contextvars import bind_contextvars, clear_contextvars, merge_contextvars

SENSITIVE = {"password", "token", "id_card", "card_no", "authorization"}

def redact(logger, method_name, event_dict):
    # 统一脱敏放在 processor 链里，调用方无法绕过
    for k in list(event_dict):
        if k.lower() in SENSITIVE:
            event_dict[k] = "[REDACTED]"
    return event_dict

structlog.configure(
    processors=[
        merge_contextvars,                      # 把 contextvars 里的字段并进每条日志
        structlog.stdlib.add_log_level,
        structlog.processors.TimeStamper(fmt="iso", utc=False),
        redact,
        structlog.processors.format_exc_info,   # 堆栈变成 exception 字段，仍是单行
        structlog.processors.JSONRenderer(),
    ],
    wrapper_class=structlog.make_filtering_bound_logger(logging.INFO),
    cache_logger_on_first_use=True,
)

// 坑：老式回调 API（尤其是把回调交给原生扩展或全局事件总线的）可能跨不过 ALS，
// 表现为某些日志莫名丢 trace_id，排查方向是找那个丢失 async 上下文的边界
import pino from 'pino';
import { AsyncLocalStorage } from 'node:async_hooks';

const als = new AsyncLocalStorage();

const base = pino({
  level: 'info',

脱敏放在 encoder 层，不靠调用方自觉

把脱敏写成一个工具方法然后要求大家调用，是注定失败的方案：新人不知道、老代码没人改、第三方库打印的日志你根本控制不了。唯一可靠的位置是序列化的统一出口——Go 的 ReplaceAttr、pino 的 redact、structlog 的 processor、Logback 的自定义 JsonProvider 或 MessageConverter。判定用两层：字段名白名单/黑名单（password、token、id_card 命中即整体替换）加值正则（手机号、卡号、身份证格式命中即掩码）。两层都要，因为字段名靠不住（有人会叫 pwd2），正则也靠不住（纯数字订单号可能误判成手机号）。

脱敏对象判定方式输出形态注意
密码、token、密钥字段名黑名单，大小写不敏感整体替换为固定标记保留字段本身，便于确认「确实传了」而不是漏传
手机号值正则前 3 后 4 保留，中间掩码正则要限定长度边界，避免切中长数字串中间
银行卡号值正则加 Luhn 校验前 6 后 4只用正则误报率高，加校验位判断可大幅降低
身份证号值正则只留末 4 位18 位含 X 结尾，正则别漏
邮箱值正则首字符加掩码加域名域名保留有助于排查渠道问题
嵌套对象里的敏感字段路径通配同上只扫一层会漏，pino 的 paths 支持通配就是为此
整个请求体不脱敏，直接不记录只记大小与摘要试图「脱敏后记录完整 body」基本都会漏
⚠️
不要在 formatter 里做重计算

encoder / formatter 在每条日志的写出路径上执行，它的开销会乘以日志条数。在这里做复杂正则、反射遍历深层对象、甚至查一次缓存，都会变成全局性的吞吐损失。脱敏正则要预编译、要限定只扫字符串类型字段、要给深度设上限；需要昂贵计算的字段应该在调用点算好再传进来。

多行堆栈与输出目标

纯文本日志里异常堆栈是几十行，采集器必须用 multiline 规则把后续行拼回上一条日志（Filebeat 的 multiline.pattern、Fluent Bit 的 multiline.parser）。这个规则的失效方式很讨厌：换一个框架、换一种语言、堆栈里出现 Caused by 之外的格式，正则就配不上，一个堆栈被拆成几十条孤立日志，而且通常在故障时才暴露。结构化之后这个问题直接消失——堆栈作为 error.stack 一个字符串字段，JSON 里换行被转义，永远单行。

输出目标适用代价
stdout（容器默认选择）所有业务日志受运行时日志驱动吞吐限制；单条过大可能被截断
容器内文件加挂卷审计日志；超大调试输出轮转、权限、清理都要自己管；Pod 重建可能丢
直接从应用发往日志后端几乎不推荐后端不可用时反压业务；应用要承担重试与缓冲
本地 socket 交给 sidecar需要在节点外做统一加工时多一跳，sidecar 崩了日志静默丢失

老系统怎么渐进结构化

一次性切换格式几乎必然出事：解析规则、看板、告警规则、下游数仓任务都绑在旧格式上。可行路径是双写、切采集、下线三段，每段都可独立回滚。

反模式

反模式后果正确做法
把整个对象 toString 塞进一个字段字段值是一坨不可查询的文本，体积还大只挑需要的字段平铺，或用结构化的嵌套对象
每条日志字段名都不一样无法跨服务查询，看板要一个服务建一套必备字段写进 logger 封装，业务字段过 lint
用 message 拼接变量无法聚合，采样器与告警规则同时失效msg 固定模板，变量进字段
高基数字段当索引字段倒排词典与 doc_values 膨胀，写入变慢存但不索引，或只保留可枚举的派生字段
在 formatter 里做重计算开销乘以日志条数，全局吞吐下降预编译正则、限定扫描范围，昂贵计算在调用点做
时间戳不带时区跨区排障时差全靠猜，日志排序错乱RFC3339 带偏移量，或统一 UTC 并在展示层转
error.stack 建全文索引存储翻倍、写入 CPU 飙升，而堆栈几乎不用全文搜设为不索引，只索引 error.type
本地开发也强制 JSON开发绕过 logger 改用打印语句按环境切 encoder，字段定义不变
❌
最容易踩的坑
  • MDC 在请求结束时没清理，线程池复用后下一个请求带上了上一个请求的 trace_id，两条无关链路被错误地串成一条。
  • 往线程池提交任务时没复制 MDC 快照，异步日志里 trace_id 全空，排障时以为是采集丢了。
  • Python 里用 threading.local 存日志上下文，切到 asyncio 后多个协程共享线程，字段互相覆盖且完全没有报错。
  • Node 的回调式 API 跨不过 AsyncLocalStorage 边界，表现为「某几类日志固定丢 trace_id」，很容易被误判成框架 bug。
  • 字段名大小写风格不统一，traceId 与 trace_id 并存，ES 里变成两个字段，看板过滤器永远漏一半数据。
  • 同名不同义：user_id 在某个服务里塞的是第三方 openid，跨服务 join 时数据全对不上。
  • 把变量拼进 msg，导致 msg 基数等于业务量，聚合、采样、告警规则三件事同时失效。
  • error.stack 按 text 全文索引，一次线上异常风暴把索引写入打满，而堆栈几乎没人用全文搜。
  • 时间戳只写本地时间不带时区，容器 TZ 又是 UTC，日志时间比业务时间「早八小时」，排障从一开始就对错了时间窗。
  • 脱敏写在调用方，第三方库和老代码打的日志完全没走这条路，敏感字段照样进索引。
  • 脱敏正则没预编译或没限定字段类型，encoder 变成 CPU 热点，日志量一大就拖慢整个服务。
  • 迁移时忘了双写期日志量会翻倍，采集与存储没留余量，切换当天就触发写入拒绝。
  • Go 里忘记把 context 往下传，子函数拿到的是全局 logger，日志有了但没有 trace_id，比没有日志更迷惑。
