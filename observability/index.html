可观测性与性能

指标 · 日志 · 链路追踪 · 性能优化 · 抓包分析（共 15 篇）

这个分类回答一个问题：系统已经在跑，怎么看清它

系统上线后遇到的几乎所有问题都要经过看到、定位、定因三步。看到依赖指标，定位依赖链路，定因依赖日志——如果三者缺一块，排查过程就会退化为猜测。这个分类把「怎么看清」拆成五个方向：指标回答「现在正不正常、趋势如何」，日志回答「这一次具体发生了什么」，链路追踪回答「这次慢在哪一跳」，性能优化把前三者的产出变成改进行动，抓包在所有工具失效时给出最底层的事实。

与它相邻但不在这里的：告警之后的变更与发布流程在 运维与云原生；应用层的熔断限流在 架构与分布式 / 熔断限流；埋点代码的语言细节（比如 Go 的 slog）在 编程语言与代码功底。这个分类只管「看到」和「定位」。

三支柱的成本驱动因素

三种信号的成本函数形状完全不同，这一点决定了它们的存储策略、保留期和采样方式不可能统一。不区分成本结构地「全都接上」，三个月后账单就会变成技术债。

信号成本由什么驱动与业务流量的关系控制成本的核心手段
指标活跃时间序列数量，等于指标数乘以各标签取值数之积几乎无关——QPS 涨十倍，序列数一条不多标签只放低基数维度（如 status 而非 user_id），热冷分层保存
日志写入量与索引字段数量严格线性——QPS 涨十倍，日志量涨十倍结构化输出、按级别与采样率控制写入、只对检索字段建索引
链路追踪上报的跨度数量（一个请求产生几十个 span）比日志更陡——每条请求放大成多跨度尾部采样保住出错与慢请求的完整链路，常态请求低比例采样

指标体系里最常见的事故是基数爆炸：把 user_id、request_id、完整 URL 这类取值随请求量增长的维度放进标签，序列数从几万跳到几百万，查询和内存同时崩。判断标准很简单——取值数会随业务量增长的维度不能做标签，只能进日志或链路。详细计算方式、乘性爆炸的推演见二级方向 Prometheus 架构与运维 和 PromQL 语义陷阱。

告警设计与分级

告警的价值不是数量多，而是每一条都可行动。三条标准判断一条告警该不该存在：

标准含义不满足时的后果
可行动收到后就知道该做什么；如果结论是「先观察」，它就该降级为看板值班人员每天被几十条无法行动的告警淹没，真正的故障被忽略
基于症状对用户可感知的失败告警（成功率下跌、延迟劣化），而不是对每个原因告警一次故障同时炸出 CPU 高、连接数多、队列长三十条告警，只有「失败率 > 1%」是有用的
有持续约束条件持续满足 N 分钟才触发，避免抓取抖动导致的瞬时误报凌晨三点被叫醒，看了一眼已经恢复了，连续几次之后开始关通知

另一个隐蔽的问题是长期触发的告警。一条告警如果连续几周处于 firing 状态，实际效果比没有更差——它训练值班人员忽略通知。定期审计告警列表，删掉或修正长期触发的那些。告警分级（P1 立刻电话、P2 工作时间处理、P3 周例会回顾）的判据是影响面乘以持续时间，而不是指标种类。

性能问题的定位顺序

性能优化最常见的错误不是用错工具，而是没有先测量就开始优化。正确的顺序是先确认瓶颈在 CPU 还是等待，再决定用什么工具定位，最后再做改动并验证数字变化。等待型延迟（IO、锁、排队）和计算型延迟的改进方式完全不同。

步骤要做的事判据与工具
1. 确认是否真的慢看 P99 而不是平均值；对比基线而不是凭感觉指标看板的分位数曲线，或 APM 的耗时分布
2. 瓶颈在 CPU 还是等待CPU 火焰图如果「很胖」说明计算密集；如果「很窄但很高」说明大量时间在等Go pprof、Java async-profiler、Python py-spy
3. 等待型：定位等谁拆解接口总耗时 = 各段下游调用耗时之和 + 自身处理链路追踪的 span 耗时分布，或手动打日志计时
4. 计算型：定位热点火焰图看哪个函数占比最大CPU profile 加源码定位
5. 改完后验证同样的负载下，确认分位数下降且没有引入新的尾延迟对比改动前后的指标看板

详细的拆解方法见 后端性能优化的度量与方法论 与 接口性能优化；数据访问层面的优化见 应用侧的数据库访问优化。

这个分类各二级方向怎么读

两条常见路线：从零搭监控，先读指标系列建立基线，再读日志系列做结构化规范，最后接链路追踪做跨服务定位；排查一个具体问题，先判断它是性能问题还是功能问题，性能问题进性能优化系列，功能问题先看链路再看日志。

二级方向篇数它解决的问题什么时候该读它

❌
可观测性上最容易走错的判断
  • 把用户标识或请求标识放进指标标签，序列数爆炸后查询和存储一起崩
  • 多台机器的 P99 求平均当成整体 P99，数学上没意义，判断出来的结论是错的
  • 告警绑在原因而不是症状上，一次故障炸出几十条通知，真正有用的那条被淹没
  • 日志量不可控，全量写入并全量索引，三个月后日志平台的成本超过业务本身
  • 链路追踪只在入口埋点，跨服务上下文没传下去，链路断成孤立片段
  • 没有先测量就开始优化，改了半天发现瓶颈根本不在改动的地方
  • 全量采样链路追踪，写入量是日志的好几倍，存储比业务系统本身还贵
