Grafana 工程实践：变量、rate_interval、看板即代码与统一告警

🏷️ Grafana

Grafana 的教程大多停在「点哪个按钮」，而生产环境真正会咬人的是另一批东西：变量里 $__interval 和 $__rate_interval 选错导致缩放时间范围后曲线完全变形、Stat 面板的 Calculation 让数字和数据源对不上、告警规则的 No Data 状态默认不告警导致整段静默、手改看板导致换个环境全部失效。这篇讲这些。

Grafana 在体系里的位置：它不存数据

这是理解所有 Grafana 性能问题的前提：Grafana 是查询与展示层，自身只存看板 JSON、变量定义、告警规则和用户权限，指标数据一个字节都不存。所以「看板很慢」这个现象，九成以上的根因在数据源侧或者查询写法上，扩容 Grafana 通常一点用都没有。

flowchart TB subgraph BR["浏览器端"] V["变量下拉框（query 类型也要发查询）"] P1["面板 A：Time series"] P2["面板 B：Stat"] P3["面板 C：Table"] end subgraph GF["Grafana 服务端"] AU["认证与数据源权限"] PX["数据源代理（access 为 proxy）"] AL["Alerting 引擎（独立于看板运行）"] MD["内置数据库：看板 JSON / 告警规则 / 用户"] end subgraph DS["数据源：真正存数据的地方"] PM["Prometheus / VictoriaMetrics"] LG["Loki / Elasticsearch"] SQ["MySQL / ClickHouse"] end V --> PX P1 --> PX P2 --> PX P3 --> PX PX --> PM PX --> LG PX --> SQ AL --> PM MD --- AU

两个容易被忽略的推论。第一，告警引擎不经过看板：它按自己的时间窗直接查数据源，所以「面板上看着很正常」不代表告警查询也正常，反之亦然。第二，access 模式决定请求从哪里发出——proxy 由服务端转发，浏览器不需要能直连数据源，凭据也不会下发到前端；早期的 direct 模式让浏览器直连，会带来跨域与凭据泄露问题，现在不应再使用。

模板变量：四种类型与刷新时机

变量是看板复用的核心，也是最容易埋雷的地方。四种常用类型的差别不在语法，而在取值来源和什么时候重新求值：

变量类型 取值来源 何时重新求值 典型用法 踩坑点
query 向数据源发查询，如 label_values(up, job) 按 refresh 配置：0 从不、1 打开看板时、2 时间范围变化时 服务名、实例、集群、命名空间 refresh 留成「从不」时，取值会被固化在看板 JSON 里，新上线的服务永远不出现在下拉框
custom 手工写死的逗号分隔列表 不查询，永不变化 分位数 0.5 / 0.9 / 0.99、聚合维度、环境枚举 用它当阈值时容易与告警规则里的阈值不一致，两处要一起改
interval 预设的时间粒度列表，可开启 auto 档 切换时或时间范围变化时 让用户手动控制聚合粒度 它和内置的 $__interval 是两回事；在 rate() 里用自定义 interval 变量同样会踩到窗口过小的坑
datasource 按数据源类型列出所有实例 打开看板时 同一份看板在多机房多集群间切换 面板必须把 datasource 字段也写成变量引用，漏改的面板会一直指向某个固定数据源

变量之间可以串联（instance 的查询里引用 $job），Grafana 会按依赖顺序求值。多选变量在 PromQL 里必须用正则匹配符，也就是 =~"$instance" 而不是 ="$instance"，因为多选值会被渲染成 a|b|c；同时把 allValue 设成 .*，否则勾选「All」时渲染出的巨大正则会显著拖慢查询。

重复面板（repeat）是变量最实用的衍生能力：给面板或行设置 repeat，Grafana 会按变量的每个选中值克隆一份。注意它只在看板加载或变量变化时展开，单纯改时间范围不会重新克隆；另外重复面板会把查询数量乘以变量取值个数，一个变量有 50 个实例就等于一次刷新发 50 个查询，这是数据源被打爆的常见来源。

$__interval 与 $__rate_interval：最容易翻车的一处

Grafana 会把「时间范围」和「面板宽度」换算成一个查询步长：$__interval 约等于时间范围除以 maxDataPoints，而 maxDataPoints 默认取面板的像素宽度，再向上取整到一个友好值，并受面板的 Min interval 限制。也就是说，同一个面板，窗口拉宽、换个屏幕、把时间范围从 1 小时改成 7 天，$__interval 的值都会变。

sequenceDiagram autonumber participant B as 浏览器 participant G as Grafana 服务端 participant P as Prometheus B->>G: 打开看板，先解析模板变量定义 G->>P: 执行 label_values 拿变量候选值 P-->>G: 返回 job 列表 G-->>B: 渲染下拉框并确定当前选中值 Note over B: 面板像素宽度决定 maxDataPoints B->>G: 提交查询，带上 from、to、maxDataPoints、interval Note over G: interval 等于时间范围除以 maxDataPoints
再向上取整，并受 Min interval 约束 G->>P: query_range，step 等于该 interval P-->>G: 返回按 step 抽样后的点集 G-->>B: 经字段变换与单位格式化后绘图 Note over B,P: 一个看板 20 个面板等于 20 个并发查询

问题出在 rate() 这类区间向量函数上：它需要区间内至少两个样本点才能算出斜率。抓取间隔是 15 秒时，如果 $__interval 被算成 15 秒甚至 10 秒，区间里经常只有一个点，rate() 直接返回空，曲线就出现断齿；把时间范围拉大后 $__interval 变成 5 分钟，曲线又变得极度平滑。同一份数据，两种完全不同的形状，很容易被误读成「故障时段指标缺失」。

$__rate_interval 就是为解决这个问题设计的：它取 $__interval 加抓取间隔、与 4 倍抓取间隔两者中的较大值，保证窗口里至少有 4 个样本。结论很简单：所有区间向量函数的窗口都写 $__rate_interval，不要写 $__interval，也不要写死 [5m]（写死会在缩小时间范围时把细节抹掉）。它依赖数据源配置里的 timeInterval（界面上叫 Scrape interval），这个值填错，等于白配。

内置变量 语义 取值依赖 该用在哪 用错的后果
$__interval 查询步长，时间范围除以 maxDataPoints 后取整 时间范围、面板像素宽度、Min interval avg_over_time 等只需对齐步长的场景，或作为 step 使用 用于 rate() 窗口时曲线断齿，缩放后形状剧变
$__rate_interval 专为区间向量设计的安全窗口，至少覆盖 4 个采样点 $__interval 加数据源配置的抓取间隔 所有 rate、irate、increase、区间聚合函数的窗口 数据源没填抓取间隔时退化为默认值，仍可能过小
$__range 当前时间范围长度，形如 6h；另有 $__range_s 与 $__range_ms 时间范围，与面板宽度无关 算整段时间的总量或占比，如 increase(x[$__range]) 误当步长使用，会把整段数据聚成一个点
$__from 与 $__to 时间范围起止的毫秒时间戳，支持 ${__from:date:iso} 等格式化 时间范围 SQL 类数据源拼过滤条件、构造外部跳转链接 SQL 里直接当秒用会差一千倍，时间范围看起来永远为空
图例占位符 {{label}} 按返回序列的标签渲染图例文本 查询结果的标签集 Legend 里只展示有区分度的标签 不设 legendFormat 时图例是完整标签集，一行能占半个屏幕

面板选错不会报错，只会让人得出错误结论，所以危害比报错更大。

看板设计原则与看板即代码

设计上三条硬原则：顶层看板一屏能看完（不超过十二个面板、不需要滚动，只放判断健康与否所必需的指标）；从概览到明细要有下钻路径（用数据链接把当前变量与时间范围一起带到下级看板，避免跳过去还得重新选一遍）；按服务而不是按机器组织（容器环境里实例随时被替换，按机器建的看板会越来越空，要看单实例时用变量或重复面板展开）。

工程上最重要的一条是看板即代码。手工改看板的真实代价不是麻烦，而是不可复现：没有评审、没有历史、换个环境重建不出来、改坏了不知道谁改的。

管理方式 改动可追溯 新环境可重建 适合谁 主要代价
纯界面手改 只有 Grafana 内置的版本列表，无评审 不能，只能靠人工导出 临时排查、探索性分析 看板会逐渐变成无人敢动的黑盒
导出 JSON 入 Git，人工导入 可以 可以，但依赖人记得导入 看板数量少于十几个的小团队 界面仍可改，两边容易不一致
file provisioning 可以，Git 即真相 可以，容器启动即加载 绝大多数团队的默认选择 需要把界面更新关掉，用户会抱怨不能直接保存
Terraform 或 Grizzly 可以，且与其他基础设施同一套流程 可以，含数据源、文件夹、权限、告警规则 多环境多租户、看板上百个 学习成本与状态管理成本
代码生成（Jsonnet 或 SDK） 可以，且能抽象出模板 可以 看板高度同构、服务数量很多 门槛最高，调试不如界面直观 
# /etc/grafana/provisioning/datasources/prom.yaml
apiVersion: 1
datasources:
  - name: prom-main
    uid: prom-main          # 必须显式指定 uid：看板 JSON 引用的是 uid，不写则随机生成，换环境后面板全报找不到数据源
    type: prometheus
    access: proxy           # 由 Grafana 服务端转发请求；浏览器直连模式已废弃，会带来跨域与凭据下发问题
    url: http://prometheus:9090
    isDefault: true
    jsonData:
      timeInterval: 15s     # 界面上叫 Scrape interval，rate_interval 的计算依赖它，填错 rate 曲线就会断齿
      httpMethod: POST      # 大查询用 GET 会超出 URL 长度上限
      queryTimeout: 60s     # 要与数据源自身的查询超时对齐，否则一边超时一边还在算
    editable: false         # 允许界面编辑就会出现「改了没人知道、重启被覆盖」
---

导入社区看板前先做两件事

社区看板的价值是给指标名和布局打样，直接用往往对不上：一是它假设的指标名与你的 exporter 版本或 relabel 规则不同，二是它大量使用写死的 [5m] 和固定数据源名。导入后至少把区间窗口批量改成 $__rate_interval、把数据源改成变量引用，再删掉一半你看不懂也用不上的面板。

Grafana 告警：evaluation group 与 No Data 的默认行为

Grafana 8 之后是统一告警（unified alerting）：告警规则从面板里独立出来，不再依赖某个面板存在，可以跨数据源做表达式运算，并且内置了与 Alertmanager 同构的通知策略与静默。旧版的 dashboard alert 绑在面板上、只支持单查询、改面板就可能改坏告警，已经被移除。

几个必须理解的概念：evaluation group 是评估的调度单位，间隔配在组上而不是规则上，同组内规则顺序评估，所以把上百条规则塞进一个组会导致整体评估延迟；pending period（for）是条件连续为真多久才真正触发；规则自带时间窗（relativeTimeRange），与任何看板的时间范围无关。

stateDiagram-v2 [*] --> Normal Normal --> Pending: 条件求值为真 Pending --> Normal: 待定期内条件恢复，不通知 Pending --> Alerting: 连续为真超过 pending period Alerting --> Normal: 条件恢复，发送 resolved 通知 Normal --> NoData: 查询返回空结果集 Normal --> Error: 数据源报错或查询超时 NoData --> Alerting: noDataState 显式配成 Alerting NoData --> Normal: noDataState 配成 OK 或保留上一状态 Error --> Alerting: execErrState 显式配成 Alerting Error --> Normal: execErrState 配成 OK
状态 什么时候进入 默认行为 由此产生的漏告警 推荐配置
No Data 查询成功但返回空结果，例如目标消失、标签改名、时间窗内无样本 不转 Alerting，而是产出一条 alertname 为 DatasourceNoData 的特殊告警 这条特殊告警的标签与原规则不同，按 severity 路由的通知策略匹配不上，最终无人处理 探活与错误率类规则显式配 Alerting；稀疏指标配 OK 或保留上一状态
Error 数据源 5xx、连接失败、查询超时、表达式语法错 产出 alertname 为 DatasourceError 的特殊告警 数据源整体故障时，几百条规则同时进 Error，全部落到默认接收器把通知刷爆或被忽略 核心规则配 Alerting，并为这两类特殊告警单独配一条通知策略兜底
Pending 条件为真但未满足 pending period 不通知 pending period 写得过长，直接拉长故障发现时间 P0 规则控制在 1 到 2 分钟，靠查询侧加分母门槛来抑制抖动
Alerting 满足条件与 pending period 按通知策略发送，并按分组参数聚合 通知策略的分组键包含实例标签时，一个故障刷出几十条 分组键用 alertname 加 service，不要带 instance
Normal 与 resolved 条件恢复为假 发送恢复通知 指标序列直接消失时（比如实例被销毁）不会走 resolved，告警可能一直挂着 配合 No Data 策略处理，并约定实例下线时清理对应规则或标签 
# /etc/grafana/provisioning/alerting/order.yaml
apiVersion: 1
groups:
  - orgId: 1
    name: order-critical        # evaluation group：间隔配在组上，组内规则顺序评估
    folder: 生产告警
    interval: 1m               # 规则再多也共用这个间隔，规则过多请拆组而不是调大间隔
    rules:
      - uid: order-5xx-high
        title: 订单服务 5xx 占比过高
        condition: C
        for: 2m                # pending period
        noDataState: Alerting  # 默认 NoData，会退化成标签对不上的特殊告警，这里显式改掉
        execErrState: Alerting # 默认 Error，同理
        labels:
          severity: P1
          service: order
        annotations:
          summary: 订单服务 5xx 占比超过 2%
          runbook_url: https://wiki.example.com/runbook/order-5xx
        data:
          - refId: A
            datasourceUid: prom-main
            relativeTimeRange:
              from: 600        # 规则自带时间窗，单位秒，与看板时间范围无关
              to: 0
            model:
              instant: true    # 告警用即时查询；区间查询返回多点还要再 reduce，行为不直观
              intervalMs: 60000  # 告警没有面板宽度概念，步长由这里决定，别指望复制看板表达式就等价
              expr: |
                sum(rate(http_requests_total{job="order",code=~"5.."}[5m]))
                  / sum(rate(http_requests_total{job="order"}[5m]))
          - refId: C
            datasourceUid: __expr__
            model:
              type: threshold
              expression: A
              conditions:
                - evaluator:
                    type: gt
                    params: [0.02]

性能问题排查与预聚合

先建立一个量级直觉：一个看板 20 个面板、开着 10 秒自动刷新、10 个人同时打开，就是每 10 秒 200 个查询打到数据源。再叠加重复面板按 50 个实例展开，数量瞬间上千。这是绝大多数「Grafana 卡」的真实原因。

症状 怎么确认 根因 修法
单个面板转圈很久后报超时 面板菜单进 Query inspector，看 Stats 里的查询耗时与返回行数 表达式在数据源侧展开的序列过多，或时间范围过大 先 sum by 收敛维度再做计算；把重表达式固化成预聚合序列
图画出来了但浏览器卡顿、滚动掉帧 Query inspector 里返回点数上万，或图例有几百条 maxDataPoints 没限制、序列数过多 面板设 Max data points 为 500 到 1000；用 topk 限制序列数
看板一打开数据源 CPU 就打满 观察数据源侧并发查询数与查询耗时分布，Prometheus 看 prometheus_engine_query_duration_seconds 面板数乘以重复展开数乘以并发用户数，超过数据源并发上限 刷新间隔放宽到 1 分钟以上；拆分看板；开启增量查询；必要时前置查询缓存
切到 7 天范围就超时，1 小时正常 对比两种范围下的 step 与扫描样本数 长范围扫描的原始样本量呈线性增长，触发数据源的样本上限 长周期看板改用预聚合序列或降采样存储，不要直接查原始数据
告警评估延迟、规则状态更新慢 看 Grafana 自身指标里的规则评估耗时与评估失败计数 一个 evaluation group 塞了过多规则，串行评估累加 按服务拆分成多个组，把重查询改成预聚合
某个面板偶发无数据，刷新一下就好 查看窗口是否使用了 $__interval 步长接近抓取间隔，rate() 窗口内样本不足 换成 $__rate_interval，并给面板设 Min interval

预聚合（recording rule）是性价比最高的一招：把看板里反复出现的重表达式在数据源侧提前算好，看板只查结果序列。命名习惯上用聚合维度、指标名、操作三段式，便于一眼看出口径：

groups:
  - name: recording-for-dashboards
    interval: 30s              # 比看板刷新间隔小一档即可，过小只是浪费算力
    rules:
      # 看板上每个服务的 P99 都要算一遍 histogram_quantile，代价很高，提前固化
      - record: job:http_request_duration_seconds:p99_5m
        expr: |
          histogram_quantile(0.99,
            sum by (job, le) (rate(http_request_duration_seconds_bucket[5m])))

      # 错误率的分子分母都要全量扫，也提前算好，看板直接相除
      - record: job:http_requests_errors:rate5m
        expr: sum by (job) (rate(http_requests_total{code=~"5.."}[5m]))
      - record: job:http_requests:rate5m
        expr: sum by (job) (rate(http_requests_total[5m]))

      # 注意：预聚合把维度固定死了。这里只保留 job，看板上就再也钻不到 instance，
      # 需要下钻的维度必须在 by 里保留，否则只能回去查原始序列

最容易踩的坑

❌
避坑清单
  • 在 rate() 窗口里用 $__interval：面板宽度和时间范围一变，曲线形状就变，窄窗口下还会整段无数据。所有区间向量一律用 $__rate_interval。
  • 数据源没填 Scrape interval：$__rate_interval 的计算依赖它，留空会退化成默认值，断齿问题照旧。
  • 把窗口写死成 [5m]：看 5 分钟范围时所有细节都被 5 分钟窗口抹平，排查瞬时尖峰时完全看不见。
  • 多选变量用 = 而不是 =~：多选值渲染成 a|b|c，用等号匹配结果永远为空，而且不报错。
  • 勾选 All 但 allValue 留空：Grafana 会把所有取值拼成一个巨大正则塞进查询，实例多时直接把数据源拖垮。
  • query 变量的 refresh 留成「从不」：取值被固化在看板 JSON 里，新服务上线后在下拉框里永远不出现，还会误判为「这个服务没有监控」。
  • Stat 面板不显式设置 Calculation：默认是 Last non-null，一旦被人改成 Mean 或 Max，数字就变成时间范围内的统计值，和数据源里查的对不上。
  • unit 选错：字节配成 short 会显示成 Mil，比例值本来是 0 到 1 却选了 percent(0-100)，把 0.02 显示成 0.02% 而不是 2%，判读时数量级直接错。
  • 用饼图看时间序列：饼图只能表达某一时刻的构成，配区间查询时会被默默聚成一个值，看起来有图其实无意义。
  • 直接画 Counter 原始值：永远是向上斜线，进程重启时垂直掉零，还会被当成「流量归零故障」。
  • 告警规则直接复制看板表达式：告警没有面板宽度，变量与步长的推导方式不同，而且它用自己的 relativeTimeRange，结果经常是看板有图、告警查空。
  • No Data 与 Error 状态留默认：目标消失、标签改名、数据源超时都不会变成告警，而是产出标签对不上的特殊告警，通知策略匹配不到，形成长时间静默。
  • 一个 evaluation group 塞几百条规则：组内串行评估，最后几条的实际评估延迟可能达到数分钟。
  • 允许界面直接保存生产看板：改动没有评审与历史，provisioning 重载时又会被覆盖回去，两边互相打脸。
  • 数据源不指定 uid：看板 JSON 引用 uid，测试环境导到生产后所有面板报找不到数据源，得一个个手改。
  • 自动刷新设 5 秒或 10 秒：看板挂在大屏上一整天，等于给数据源加了一个永不停止的压测任务，而没有人真的需要 5 秒级刷新。
