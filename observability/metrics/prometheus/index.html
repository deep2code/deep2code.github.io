Prometheus 架构与运维：拉模型、TSDB、指标语义与告警链路

🏷️ Prometheus

这一篇只讲 Prometheus 这个系统自己怎么运作、怎么运维：为什么它选拉模型、Pushgateway 的唯一正确用途、四种指标类型的精确语义、TSDB 是怎么把样本落到磁盘上的、relabel 两个阶段的分工、单机容量边界在哪、以及一条告警从表达式变成手机响铃要经过多少个时间参数。可观测性的方法论（基数模型、黄金信号、SLO 与错误预算）见站内 devops/monitoring/ 主干篇；查询语言的语义陷阱见 devops/monitoring/promql/。

一、拉模型与推模型的真实取舍

Prometheus 主动去目标的 /metrics 端点上抓，而不是等目标推过来。这个选择带来四个很难替代的工程收益。

一是抓取失败本身就是存活信号。每次抓取 Prometheus 都会自动写入一条 up 指标，成功为 1、失败为 0。推模型下目标停止推送时，你无法区分「进程挂了」和「它觉得没必要推」，还得额外造一套心跳机制。二是可调试性。任何时候 curl http://target:9100/metrics 看到的就是 Prometheus 看到的，排查链路只有一跳。三是控制权在服务端。抓取间隔、超时、抓哪些目标、丢哪些指标全在 Prometheus 配置里，改这些不需要动应用、不需要重启业务进程。四是与服务发现天然契合。目标列表由 Kubernetes API 或注册中心动态产出，扩缩容时不需要任何额外动作。

代价也很实在：抓取要求网络从 Prometheus 单向可达目标，跨 NAT、跨专线、客户端侧指标这些场景需要额外打通；而生命周期短于抓取间隔的任务根本活不到被抓的时刻——这是 Pushgateway 存在的唯一理由。

维度拉模型（Prometheus 抓取）推模型（客户端上报）
存活探测up 指标天然可用，抓不到即为 0需要额外心跳，静默无法区分挂掉与不推
目标发现由服务发现驱动，扩缩容自动生效客户端需要知道后端地址，改地址要改配置或重启
本地调试直接 curl 端点，所见即所抓要在服务端查有没有收到，链路长
采集频率控制服务端统一配置，可按 job 差异化散落在各客户端，难统一治理
网络要求Prometheus 到目标单向可达，穿透 NAT 困难目标到服务端单向可达，更适合边缘与客户端
流量尖峰抓取节奏由服务端控制，不会被打爆客户端同时上报可能压垮接收端，需要缓冲
短任务抓不到，必须借道 Pushgateway天然支持
指标过期目标消失后序列自然停止更新网关型中转会持有陈旧值，需显式删除
❌
Pushgateway 最常见的误用

把它当成通用推送网关，让常驻服务全部推到 Pushgateway 再被抓。后果有三个：一是指标不会自动消失，实例下线后 Pushgateway 仍然持续暴露它最后推上来的值，这些僵尸序列会被当成现状参与告警计算，必须显式调用 DELETE /metrics/job/xxx 才会清掉；二是 up 只反映 Pushgateway 自己的健康，真实实例的存活彻底失去观测；三是它变成单点，挂掉即全盲。它只该用于「跑完就退出的批处理任务」。

两条容易被忽略的回边值得注意：规则引擎指向 head 的那条边表示 recording rule 的计算结果会作为新的时间序列写回自己，所以预聚合会增加序列数，只是增加得可控；规则引擎指向 Alertmanager 的那条边表示告警是由 Prometheus 判定的，Alertmanager 收到的已经是「确定要发的告警」，它只做通知策略。很多人把告警不发的问题一路查到 Alertmanager，实际上八成是表达式在 Prometheus 侧就没变成 firing。

三、四种指标类型的精确语义

类型不是装饰，它决定了你能对这个指标做什么运算。

Counter 只增不减，进程重启时归零。它的绝对值几乎没有意义——http_requests_total 显示 87263918，这个数字告诉你什么？什么都没有。Counter 必须配 rate() 或 increase() 使用，看的是变化速率。这是新手最高频的错误：在面板上直接画 Counter，得到一条单调上升的斜线，故障期间这条线依然在涨。

Gauge 可增可减，表示某一刻的瞬时值，比如内存占用、队列长度、连接数。它可以直接看、可以取 avg / max，但不能用 rate()（rate 会把下降当成 Counter 重置来处理，结果毫无意义），想看 Gauge 的变化趋势用 deriv() 或 delta()。

Histogram 是预定义桶的累积计数。客户端只做一件事：把每次观测值累加到对应的桶计数器上。一个 Histogram 暴露三组序列：带 le 标签的一系列累积桶（le 是 less-or-equal，桶是累积的，le=0.5 的计数包含了 le=0.1 的所有请求）、xxx_sum 观测值总和、xxx_count 观测总次数。分位数是查询时在服务端估算的，所以桶边界定错，分位数就不准：如果 SLO 是 300 毫秒而桶边界是 0.1 / 0.5 / 1 / 5，那 300 毫秒落在 0.1 到 0.5 桶中间只能靠线性插值猜。另外注意 Histogram 的序列开销是桶数加 2 倍，10 个桶就是 12 条序列，再乘上其他标签的基数，它是最容易撑爆序列数的指标类型。

Summary 在客户端算分位数。它直接暴露带 quantile 标签的序列。好处是不需要预先猜桶边界、分位数在单实例内是精确的；代价是致命的：分位数不可相加，因此 Summary 无法跨实例聚合。十个 Pod 各自上报一个 P99，你没有任何数学方法把它们合成整体 P99——求平均是错的，求最大值是过于保守的。只要服务有多副本，就必须用 Histogram。

四、TSDB：样本从内存到磁盘的完整路径

Prometheus 的本地存储不是通用数据库，它是为「写多读少、时间有序、按序列分片」这个场景专门写的。一条样本的生命周期是这样的：抓取后先追加到 WAL（预写日志，顺序写，用于崩溃恢复），同时写入内存中的 head block；head 累积到约 2 小时的数据后被切出来，压缩成磁盘上一个独立的 block 目录（包含 chunks 数据、倒排索引 index、元信息 meta.json），对应的 WAL 段随之被截断；后台 compaction 会把相邻的小 block 合并成更大的 block，并在合并时丢弃超出 --storage.tsdb.retention.time 的数据。

几个由这套结构直接导出的行为，运维时一定会碰到：重启慢是因为要回放 WAL，序列多的时候几分钟很正常，日志里能看到 replay 进度；删除数据不是行级删除，retention 是按整个 block 目录删的，所以磁盘占用是阶梯式下降而不是平滑下降；降低 retention 不会立刻释放空间，要等下一轮 compaction；不要手工删 block 目录，index 与 meta 不一致会导致启动失败。

五、抓取配置、relabel 与服务发现

relabel 是 Prometheus 最强也最容易写错的机制，关键是记住两个阶段的时机不同：relabel_configs 在抓取之前作用于目标（改地址、改标签、决定抓不抓），服务发现产出的元标签只在这个阶段可见；metric_relabel_configs 在抓取之后、入库之前作用于每条样本（丢指标、删标签、改名），这是对抗基数爆炸最直接的工具。

action作用典型用途坑
replace用正则捕获组写入目标标签，默认动作把 Pod 的 app 元标签变成正式的 app 标签regex 不匹配时整条规则跳过，不会清空标签
keep只保留匹配的目标只抓带特定注解的 Pod多条 keep 是 AND 关系，写多了会把目标全过滤掉
drop丢弃匹配的目标或样本丢掉测试环境目标、丢掉高基数指标在 relabel_configs 里丢的是目标，在 metric_relabel_configs 里丢的是样本，别用错位置
labelmap按正则批量重命名标签把所有 Pod label 一次性映射进来会把无关 label 全带进来，是基数失控的常见源头
labeldrop删除匹配的标签删掉 id、pod_ip 这类高基数标签删掉后如果剩余标签组合重复，会出现重复序列采集错误
labelkeep只保留匹配的标签强制收敛标签集合容易误删 job、instance 导致目标失去身份
hashmod对标签值取哈希再取模多个 Prometheus 实例按目标分片分片数变更会让序列归属漂移，历史数据断裂

Kubernetes 服务发现的 role 决定了你能发现什么对象，选错 role 会导致目标数量差一个数量级。

role发现的对象适用场景注意
node集群所有节点抓 node-exporter、kubelet、cAdvisor目标地址是节点 IP，端口需要 relabel 改写
pod所有 Pod 及其每个声明端口抓应用自身指标，最常用不加 keep 过滤会把全集群 Pod 都抓上，目标数爆炸
endpointsService 背后的实际端点抓有 Service 的服务，可拿到 Service 维度标签Pod 未 Ready 时端点不出现，会出现目标忽隐忽现
serviceService 本身配合 blackbox_exporter 做黑盒探测抓到的是 ClusterIP，负载均衡后无法定位具体实例
ingressIngress 规则对外域名的可用性探测只适合黑盒探测，拿不到应用内部指标

下面是一份可直接抄走的配置，覆盖了注解驱动的 Pod 发现、标签归一化、以及两处对抗基数爆炸的 metric_relabel_configs。

global:
  scrape_interval: 15s        # 决定了 rate() 区间下限，后面所有 rate 至少写 [1m]
  scrape_timeout: 10s         # 必须小于等于 scrape_interval
  evaluation_interval: 15s    # 规则求值间隔，与抓取间隔一致最省心
  external_labels:
    cluster: prod-sh          # 远程存储与联邦时用于区分来源，必须唯一

rule_files:
  - /etc/prometheus/rules/*.yml

alerting:
  alertmanagers:
    - static_configs:
        - targets: ['alertmanager:9093']

scrape_configs:
  # 1. 抓自己，Prometheus 自身指标是排障第一入口
  - job_name: prometheus
    static_configs:
      - targets: ['localhost:9090']

  # 2. 注解驱动的 Pod 发现：只抓显式声明了 prometheus.io/scrape 的 Pod
  - job_name: kubernetes-pods
    kubernetes_sd_configs:
      - role: pod
    relabel_configs:
      # 没打注解的 Pod 直接不抓，避免目标数失控
      - source_labels: [__meta_kubernetes_pod_annotation_prometheus_io_scrape]
        action: keep
        regex: "true"
      # 允许业务用注解覆盖指标路径，默认 /metrics
      - source_labels: [__meta_kubernetes_pod_annotation_prometheus_io_path]
        action: replace
        target_label: __metrics_path__
        regex: (.+)
      # 用注解里的端口替换掉服务发现给的端口，重新拼出地址
      - source_labels: [__address__, __meta_kubernetes_pod_annotation_prometheus_io_port]
        action: replace
        regex: '([^:]+)(?::\d+)?;(\d+)'
        replacement: '$1:$2'
        target_label: __address__
      # 把命名空间与 Pod 名提升为正式标签，注意不要 labelmap 全部 label
      - source_labels: [__meta_kubernetes_namespace]
        target_label: namespace
      - source_labels: [__meta_kubernetes_pod_name]
        target_label: pod
      - source_labels: [__meta_kubernetes_pod_label_app]
        target_label: app
      # 排除测试命名空间，省下的是真金白银的序列数
      - source_labels: [__meta_kubernetes_namespace]
        action: drop
        regex: '(dev|test|sandbox)'
    metric_relabel_configs:
      # 抗基数爆炸一：整类丢掉带原始 URL 路径的指标
      - source_labels: [__name__]
        action: drop
        regex: 'http_request_duration_seconds_bucket_by_full_url.*'
      # 抗基数爆炸二：删掉容器指标里取值无限的 id 与 pod_ip 标签
      - regex: '(id|pod_ip|container_id)'
        action: labeldrop
      # 只保留关心的 Go 运行时指标，其余丢弃
      - source_labels: [__name__]
        action: drop
        regex: 'go_memstats_(frees|lookups|mallocs)_total'

  # 3. 节点指标：role node 拿到的是 kubelet 端口，需要改写成 node-exporter 端口
  - job_name: node-exporter
    kubernetes_sd_configs:
      - role: node
    relabel_configs:
      - source_labels: [__address__]
        regex: '([^:]+):\d+'
        replacement: '$1:9100'
        target_label: __address__
      - source_labels: [__meta_kubernetes_node_name]
        target_label: node

  # 4. 短任务专用：Pushgateway。honor_labels 必须为 true，
  #    否则 Prometheus 会用自己的 job 与 instance 覆盖任务推上来的同名标签
  - job_name: pushgateway
    honor_labels: true
    static_configs:
      - targets: ['pushgateway:9091']

六、单机容量边界与远程存储选型

先给数字。单机 Prometheus 的经验安全边界是活跃时间序列 100 万条以内、样本摄入 20 万到 50 万每秒，配置 16 到 32 GB 内存与 SSD。内存主要花在 head：每条活跃序列的常驻开销大约 3 KB 量级（含 index、标签字符串、末尾 chunk），100 万序列就是 3 GB 左右，再加上查询临时对象和 GC 余量，所以内存要留一倍以上。

超过边界时，第一反应应该是减基数而不是加机器。实际情况几乎总是：前 5 个高基数指标占了一半以上的序列数，删掉或降维就回到安全区。只有当你确实需要「跨集群统一查询」「保留一年以上」「多租户隔离」时，才该引入远程存储。

方案解决的核心问题架构代价什么时候不该选
原生单机加长 retention零额外组件，运维最简单无高可用，磁盘与内存受单机限制需要跨集群全局视图，或需要保留一年以上
Thanos对象存储做无限期存储，Querier 聚合多集群并对两副本去重组件多（sidecar、store、compact、query），查历史依赖对象存储延迟团队没有对象存储，或不愿维护 4 个以上组件
VictoriaMetrics更高压缩率与更低内存，单体模式一个二进制起步与 Prometheus 生态不完全等价，部分函数行为有差异强依赖 Prometheus 原生语义细节的场景需要先验证
Mimir多租户隔离、水平扩展的写入链路、租户级限流组件最多，运维复杂度最高，需要专职投入只有一个团队一套集群时属于过度设计
联邦（federation）用一层上级 Prometheus 汇总下级的聚合指标只适合搬运少量聚合序列，拉全量会把上级打死把它当成通用的全局存储方案，这是最常见的误用
💡
为什么官方不做集群

这是刻意的设计取舍。分布式会引入一致性、成员管理、分区恢复等一整套复杂度，而监控系统必须比被监控系统更简单、更可靠——如果排查故障时先要排查监控集群自己的脑裂，这套体系就失去意义了。官方给出的高可用方案是「两台配置相同的 Prometheus 各自独立抓取同一批目标」，靠冗余而不是靠一致性协议，数据在查询层（Thanos Querier 等）去重。

七、告警链路：从表达式到手机响铃

告警是两个系统的接力。Prometheus 侧按 evaluation_interval 周期性求值规则，表达式有结果就进入 pending，连续满足 for 指定的时长才升级为 firing 并推送给 Alertmanager。for 期间只要有一次求值不满足就直接回到 inactive，计时从零重来——这一点很关键，它意味着抖动型故障永远不会触发长 for 的告警，这既是特性也是陷阱。

stateDiagram-v2 [*] --> Inactive Inactive: 表达式无结果 Pending: 条件已满足 但未达到 for 时长 Firing: 已持续满足 正在推送给 Alertmanager Resolved: 条件不再满足 发送恢复通知 Inactive --> Pending: 某次求值返回了结果 Pending --> Inactive: 中途有一次求值为空 计时清零 Pending --> Firing: 连续满足达到 for 时长 Firing --> Resolved: 表达式返回空 Resolved --> Inactive: 经过 resolve_timeout 后清理 Firing --> Firing: 每次求值持续重发 默认 1 分钟一次

Alertmanager 侧则由三个时间参数控制通知节奏，它们经常被混淆：group_wait 是新分组第一次通知前的等待（默认 30 秒，用来把同时爆发的同组告警攒成一条）；group_interval 是同一分组内出现新成员后再次通知的最小间隔（默认 5 分钟）；repeat_interval 是告警一直没恢复时重复提醒的间隔（默认 4 小时）。

sequenceDiagram participant P as Prometheus 规则引擎 participant A as Alertmanager participant U as 值班手机 P->>P: 第 0 秒 表达式首次满足 进入 pending P->>P: 第 120 秒 连续满足达到 for 设定 P->>A: 第 120 秒 推送 firing 告警 A->>A: 按 group_by 落入分组 等待 group_wait 30 秒 A->>U: 第 150 秒 发出第一条通知 已聚合同组 3 条 P->>A: 第 180 秒 同组新增一条告警 A->>A: 等待 group_interval 5 分钟再合并发送 A->>U: 第 450 秒 发出增量通知 A->>U: 第 4 小时 故障仍未恢复 按 repeat_interval 重提醒 P->>A: 故障恢复 表达式返回空 A->>U: 发送恢复通知 前提是开启了 send_resolved

算一下总延迟：抓取间隔 15 秒 + 求值间隔 15 秒 + for 2 分钟 + group_wait 30 秒 ≈ 3 分钟。如果你的 SLO 要求 1 分钟内响应，那 for 就不能写 2 分钟。「告警太慢」这类问题要把这四个数字一起算，单独调任何一个都没用。

# /etc/prometheus/rules/app.yml
groups:
# recording rule 单独一组：预聚合高频查询，降低告警求值开销
- name: app-recording
  interval: 30s
  rules:
  # 把按实例的错误率预聚合成服务级序列，告警直接读它，求值从秒级降到毫秒级
  - record: job:http_error_ratio:rate5m
    expr: |
      sum by (job) (rate(http_requests_total{code=~"5.."}[5m]))
      /
      sum by (job) (rate(http_requests_total[5m]))

- name: app-alerting
  rules:
  # 症状型告警：面向用户可感知的失败，而不是面向某个原因
  - alert: HighErrorRatio
    expr: job:http_error_ratio:rate5m > 0.005
    for: 3m                   # 至少覆盖 4 个抓取周期，滤掉抖动与滚动重启
    labels:
      severity: critical
    annotations:
      summary: "服务 {{ $labels.job }} 错误率 {{ $value | humanizePercentage }} 超过 0.5%"
      runbook: "https://wiki.internal/runbook/http-error-ratio"

  # 延迟告警：先 rate 再按 le 汇总，最后才 histogram_quantile，顺序不能换
  - alert: HighLatencyP99
    expr: |
      histogram_quantile(
        0.99,
        sum by (job, le) (rate(http_request_duration_seconds_bucket[5m]))
      ) > 0.3
    for: 5m
    labels:
      severity: warning
    annotations:
      summary: "服务 {{ $labels.job }} P99 延迟 {{ $value }} 秒 超过 300ms"

  # 目标失联：注意 up == 0 只能覆盖抓取失败，不能覆盖目标从服务发现里消失
  - alert: TargetDown
    expr: up == 0
    for: 2m
    labels:
      severity: critical
    annotations:
      summary: "抓取目标 {{ $labels.instance }} 已失联 2 分钟"

  # 指标彻底消失：目标从服务发现中被删除时 up 序列也没了，必须用 absent 兜底
  - alert: MetricMissing
    expr: absent(up{job="payment-api"}) == 1
    for: 5m
    labels:
      severity: critical
    annotations:
      summary: "payment-api 的抓取目标整体消失，可能是服务发现或标签配置被改坏"

  # 磁盘预测型告警：基于趋势提前 4 小时报，而不是等到写满
  - alert: DiskWillFillIn4Hours
    expr: |
      predict_linear(node_filesystem_avail_bytes{fstype!~"tmpfs|overlay"}[6h], 4*3600) < 0
      and node_filesystem_avail_bytes / node_filesystem_size_bytes < 0.2
    for: 30m
    labels:
      severity: warning
    annotations:
      summary: "{{ $labels.instance }} 的 {{ $labels.mountpoint }} 预计 4 小时内写满"
# alertmanager.yml
global:
  resolve_timeout: 5m        # Prometheus 停止推送后多久判定为已恢复

route:
  # group_by 决定聚合粒度：千万不要写 instance，否则 100 台机器就是 100 条通知
  group_by: ['alertname', 'cluster', 'job']
  group_wait: 30s            # 新分组首次通知前的攒批时间
  group_interval: 5m         # 同分组新增成员后再次通知的最小间隔
  repeat_interval: 4h        # 一直未恢复时的重复提醒间隔
  receiver: im-default
  routes:
    # critical 走电话，且缩短攒批时间换取响应速度
    - matchers:
        - severity = critical
      receiver: oncall-phone
      group_wait: 10s
      repeat_interval: 1h
      continue: true         # 继续匹配后续路由，让 IM 群也收到一份
    - matchers:
        - severity = warning
      receiver: im-default
      repeat_interval: 12h

# 抑制规则：根因告警存在时，压掉由它派生的下游告警
inhibit_rules:
  # 整个实例都挂了，就不必再报它上面的高延迟、高错误率
  - source_matchers:
      - alertname = TargetDown
    target_matchers:
      - severity =~ "warning|critical"
    equal: ['cluster', 'instance']   # 必须同集群同实例才抑制
  # 数据库挂了，压掉所有依赖它的服务的错误率告警
  - source_matchers:
      - alertname = MySQLDown
    target_matchers:
      - alertname = HighErrorRatio
    equal: ['cluster']

receivers:
  - name: im-default
    webhook_configs:
      - url: 'http://alert-webhook.internal/im'
        send_resolved: true
  - name: oncall-phone
    webhook_configs:
      - url: 'http://alert-webhook.internal/phone'
        send_resolved: false          # 电话不发恢复通知，避免半夜二次骚扰

八、排障：先看这四个入口

Prometheus 自己暴露了足够的自监控信息，八成问题不需要翻源码。

# 0. 改配置后先校验再 reload，别直接重启（重启要回放 WAL，可能几分钟不可用）
promtool check config /etc/prometheus/prometheus.yml
promtool check rules /etc/prometheus/rules/*.yml
curl -X POST http://localhost:9090/-/reload     # 需要启动时带 --web.enable-lifecycle

# 1. 目标为什么没抓到：看 targets 接口的 health 与 lastError 字段
curl -s 'http://localhost:9090/api/v1/targets?state=active' \
  | python3 -m json.tool | grep -E 'health|lastError|scrapeUrl'

# 2. 基数排查：哪些指标占了最多序列，哪些标签取值最多
curl -s http://localhost:9090/api/v1/status/tsdb | python3 -m json.tool

# 3. 抓取是否被截断：目标暴露的指标条数是否触到上限
#    sample_limit 触发时这次抓取整体失败，表现为周期性数据缺口
curl -s http://localhost:9100/metrics | grep -vc '^#'

# 4. 自监控关键指标（在表达式浏览器里查）
#    prometheus_tsdb_head_series                活跃序列数，容量的第一指标
#    rate(prometheus_tsdb_head_samples_appended_total[5m])  摄入速率
#    prometheus_target_scrapes_exceeded_sample_limit_total  被 sample_limit 拒掉的次数
#    prometheus_rule_evaluation_failures_total   规则求值失败，直接导致漏报
#    prometheus_rule_group_last_duration_seconds 规则组耗时，接近 interval 就要预聚合
#    scrape_duration_seconds                     单目标抓取耗时，接近 timeout 就要拆 job
#    prometheus_notifications_dropped_total      发给 Alertmanager 失败的通知数
现象 / 字段判读处理
targets 页面 health 为 down，lastError 含 connection refused端口不对或进程没起核对 relabel 改写后的目标地址，用 curl 直连验证
lastError 含 context deadline exceeded抓取超时，通常是目标指标太多或目标自身慢拆分 job、调大 scrape_timeout（不得超过 interval）、在目标侧减少指标
lastError 含 sample limit exceeded单次抓取样本数超过 sample_limit，本次抓取整体丢弃不要直接调高上限，先用 metric_relabel_configs 丢掉高基数指标
目标数为 0 但配置看起来没问题keep 规则把目标全过滤了，或命名空间权限不足看服务发现页面对比 relabel 前后的标签
status/tsdb 里 seriesCountByMetricName 头部指标占比极高该指标基数失控，通常是带了高基数标签定位标签后 labeldrop，或让业务侧归一化
status/tsdb 里 labelValueCountByLabelName 某标签取值上万典型的 user_id 或 URL 类标签混入整类 drop 该指标，并在代码侧改成日志字段
prometheus_rule_group_last_duration_seconds 接近 evaluation_interval规则求值快跟不上，再涨就会跳过求值导致漏报用 recording rule 预聚合，把告警表达式改成读预聚合序列
重启后很久查不到数据，日志显示 replay WAL正在回放预写日志重建 head，属正常行为序列多时按分钟计等待；高可用靠双副本而不是靠快速重启
磁盘占用不随 retention 调小而下降retention 按整个 block 目录删除，需等下一轮 compaction等待或临时设 retention.size；不要手工删 block 目录

最容易踩的坑

❌
避坑清单
  • 用 Pushgateway 代理常驻服务的指标。实例下线后它仍持续暴露最后推上来的值，这些僵尸序列会被当成现状参与告警计算，必须显式调删除接口才清掉，同时 up 也失去了对真实实例的存活判断能力。
  • 抓 Pushgateway 时忘了写 honor_labels: true。Prometheus 会用自己的 job 和 instance 覆盖任务推上来的同名标签，导致所有批任务的指标混成一坨无法区分。
  • 面板上直接画 Counter 原始值。得到的永远是一条单调上升的斜线，故障期间它照样在涨，什么都看不出来，Counter 必须配 rate 或 increase。
  • 多副本服务用 Summary 采集延迟。客户端算好的分位数不可相加，十个 Pod 的 P99 没有任何数学方法合成整体 P99，只要有副本就必须用 Histogram。
  • Histogram 桶边界照抄库里的默认值。SLO 阈值如果不落在某个桶边界上，分位数只能靠桶内线性插值估算，误差可能成倍；同时 Histogram 的序列开销是桶数加 2 倍，桶开得太细是基数爆炸的常见来源。
  • scrape_timeout 写得比 scrape_interval 大。配置校验直接失败，进程起不来；改成相等也危险，一次慢抓取会挤掉下一轮。
  • 用 labelmap 把 Kubernetes 的所有 Pod label 一次性映射进来。业务随手打的 label 会全部变成指标标签，其中往往就藏着取值无限的那个。
  • 把 metric_relabel_configs 和 relabel_configs 用反。前者在抓取后过滤样本，后者在抓取前过滤目标；想丢掉一个高基数指标却写进了 relabel_configs，结果是什么都没丢。
  • 遇到 sample limit exceeded 就直接调高上限。这次抓取是整体丢弃而非部分丢弃，表现为周期性数据缺口，正确做法是先削减指标数量。
  • Alertmanager 的 group_by 里写了 instance。100 台机器同时出问题就是 100 条通知，分组聚合完全失效，这是告警风暴最常见的配置原因。
  • 混淆 for 与 group_wait。前者在 Prometheus 侧抑制抖动，后者在 Alertmanager 侧攒批；告警慢要把抓取间隔、求值间隔、for、group_wait 四个数加起来算。
  • 只配 up == 0 就以为覆盖了存活告警。目标从服务发现中被删除时 up 序列本身就消失了，表达式返回空集不会触发任何比较，必须再配 absent() 类告警兜底。
  • 把联邦当成全局存储方案。上级 Prometheus 拉下级全量指标会被直接打死，联邦只适合搬运少量已聚合的序列。
  • 手工删除数据目录下的 block。index 与 meta.json 不一致会导致启动失败，清理数据只能通过 retention 参数交给 compaction 做。
  • 规则组求值耗时接近 evaluation_interval 却不处理。求值跟不上会导致跳过周期，直接表现为告警漏报——监控系统在最需要它的时候安静了。
