DocumentLoader 与 metadata：RAG 质量的第一道天花板

解析错了后面全白费。PDF 解析尤其脆弱：扫描件要走 OCR、多栏排版会把两列交织、表格被当成纯文本丢掉结构。loader 帮你调库但不保证解析对，所以每换一种文档类型，第一件事是人工抽查十几条解析结果。

格式推荐 loader常见问题检查方法
文本 PDFPyPDFLoader多栏错序、页眉页脚混入正文抽十页对比原文
扫描 PDFUnstructuredPDFLoader 配 OCR识别率随扫描质量波动大数字与英文字母是重灾区
Word docxDocx2txtLoader表格变平文本、批注丢失含表格的文档单独检查
HTMLBSHTMLLoader导航栏、广告、cookie 弹窗混入检查前几个块是否有正文内容

CSV / ExcelCSVLoader每行变一个 Document，列信息丢失需自定义把列名拼进内容

metadata 是后续过滤与溯源的基础，必须在加载阶段填好。后面补的成本高得多，因为要重新关联已经入库的向量。

from langchain_community.document_loaders import PyPDFLoader

# 加载并补充 metadata
loader = PyPDFLoader("policy/annual-leave-2024.pdf")
docs = loader.load()
for doc in docs:
    doc.metadata.update({
        "doc_id": "policy-annual-leave-2024",   # 文档级唯一标识，增量更新的依据
        "source": "annual-leave-2024.pdf",       # 用户看到的来源名
        "department": "hr",                      # 权限过滤标签
        "doc_type": "policy",                    # 便于按类型区分检索范围
        # page 字段 loader 通常已填，检查一下
    })
    # 人工抽查：打印前 200 字看是否正常

五种 Retriever 形态及其成本

LangChain 提供的几种 Retriever 解决的是不同层次的检索问题。不要先选 Retriever 再看问题，而是先确认你的检索到底差在哪一步。

MultiQueryRetriever用户查询措辞不精准，一种表述检不到让 LLM 改写成三到五个不同表述分别检索再合并1 次改写中

ParentDocumentRetriever 是实用价值最高的一个，因为块大小的两难几乎所有 RAG 项目都会遇到：小块精准但模型看到的只是一句话，大块上下文够但相似度被稀释。它的做法是建两级索引，小块建向量用于检索，检索命中后回到文档存储里拿对应的大块返回给模型。实质是用存储换效果，代价是多一个文档存储的维护。

as_retriever 的参数与 metadata 过滤

as_retriever() 看起来只是一行，但它背后的默认值决定了检索结果长什么样，而这些默认值几乎都不适合直接用在生产上。最常见的症状是默认的纯相似度检索返回高度同质的结果：同一段原文切出来的相邻几块分数都很高，于是四个返回块说的是同一件事，上下文预算浪费掉四分之三，而真正需要的另一个知识点根本没进来。

参数默认值作用调错的后果
search_type 为 similarity默认纯向量相似度排序结果同质，相邻块挤占预算
search_type 为 mmr需显式指定在相关性与多样性之间平衡不调 fetch_k 的话候选池太小，mmr 退化成普通相似度
search_type 为 similarity_score_threshold需显式指定按分数阈值截断阈值依赖 Embedding 模型的分数分布，换模型必须重调；照抄别人的阈值常导致全部被过滤或全部通过
k4返回块数设大了噪声进上下文，设小了漏召回；应由上下文预算反推而不是拍一个数
fetch_k20mmr 的候选池大小太小则多样性无从谈起，太大则重排开销上升
lambda_mult0.5mmr 里相关性与多样性的权重取 1 等于纯相似度，取 0 等于纯多样性，两端都不好用
filter无按 metadata 过滤各向量库语法不同，LangChain 未统一；格式传错时部分实现静默忽略而不报错

另一个必须搞清的是过滤发生在向量检索之前还是之后。前置过滤先按 metadata 缩小候选集再算相似度，结果准确但要求向量库支持带条件的索引查询；后置过滤是先取最相似的 k 个再丢掉不符合条件的，实现简单但很可能过滤完一个都不剩——多租户场景下，全库最相似的前四个块完全可能都属于别的租户。LangChain 的适配层不会告诉你用的是哪一种，必须去看具体向量库的实现代码。权限过滤与多租户的完整做法见站内 RAG 检索侧数据工程一篇。

上下文组装：最该自己写的一步

为什么反复强调这一步不要用封装？因为 RAG 最终效果的好坏，八成取决于模型看到的上下文长什么样。需要控制的至少有五件事：

控制点为什么重要常见错法
token 预算分配塞满窗口不如在预算内最大化信息密度；系统提示与历史也要占预算把所有检索结果都塞进去，撞上下文窗口直接截断
去重块重叠导致同一内容出现多次，占预算不增信息不去重，三段内容两段重复
排序模型对上下文开头和结尾的信息记忆更强随机排列，关键段落被淹没在中间
引用编号用户需要知道答案依据哪一段，不可验证的答案没有产品价值不编号，模型无法在回答里指明来源
截断策略超出预算时丢弃低相关性的段落而不是从尾部截断按字符数硬截，截在段落中间
 
from langchain_core.documents import Document

def build_context(
    docs: list[Document],
    token_budget: int = 2500,
    reserved_for_prompt: int = 500,
) -> tuple[str, list[dict]]:
    """返回拼好的上下文文本与引用列表。
    这个函数不依赖任何框架，可以脱离 LLM 单测。"""
    budget = token_budget - reserved_for_prompt
    seen_keys: set[str] = set()
    parts: list[str] = []
    refs: list[dict] = []
    used = 0

    for doc in docs:
        # 粗粒度去重：取前 120 字做指纹，多数重复来自块重叠
        key = doc.page_content[:120]
        if key in seen_keys:
            continue
        seen_keys.add(key)

        # 中文约 1.5 字对 1 token，用 0.6 做安全系数
        cost = int(len(doc.page_content) * 0.6)
        if used + cost > budget:
            break          # 宁可少塞一段，也不要挤爆预算
        used += cost

        idx = len(parts) + 1
        src = doc.metadata.get("source", "未知")
        page = doc.metadata.get("page", "")
        label = f"{src} p{page}" if page else src

        parts.append(f"[{idx}] 来源：{label}\n{doc.page_content}")
        refs.append({"idx": idx, "source": label,
                     "doc_id": doc.metadata.get("doc_id", "")})

    return "\n\n".join(parts), refs

查询改写是对话式 RAG 的必要条件，不是可选优化。第二轮之后的用户查询几乎必然带指代词或省略主语，直接拿去检索等于在语义空间里随机采样。

from langchain_core.messages import HumanMessage, AIMessage
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser
from langchain_openai import ChatOpenAI

rewrite_prompt = ChatPromptTemplate.from_messages([
    ("system", "你是查询改写器。根据对话历史把最新问题改写成一句独立完整的检索查询。"
               "只输出改写后的查询，不要解释。如果最新问题已经独立完整则原样输出。"),
    ("human", "对话历史：\n{history_text}\n\n最新问题：{question}"),
])

rewrite_chain = rewrite_prompt | ChatOpenAI(
    model="gpt-4o-mini", temperature=0, timeout=15, max_retries=0
) | StrOutputParser()

def format_history_for_rewrite(history: list) -> str:
    """把消息对象列表转成紧凑文本，只用于改写，不进主 prompt。"""
    lines = []
    for m in history[-6:]:
        role = "用户" if isinstance(m, HumanMessage) else "助手"
        lines.append(f"{role}：{m.content[:200]}")
    return "\n".join(lines)

完整 LCEL RAG 链

import asyncio
from langchain_core.prompts import ChatPromptTemplate, MessagesPlaceholder
from langchain_core.runnables import RunnableLambda, RunnableParallel
from langchain_core.output_parsers import StrOutputParser
from langchain_openai import ChatOpenAI

model = ChatOpenAI(
    model="gpt-4o", temperature=0, timeout=30, max_retries=0, max_tokens=1200
)

qa_prompt = ChatPromptTemplate.from_messages([
    ("system",
     "你是知识库问答助手。只依据下方资料回答，在每个论断后用方括号标注资料编号。"
     "资料里没有相关内容就明确说不知道，不要编造。\n\n{context}"),
    MessagesPlaceholder("history"),
    ("human", "{question}"),
])

async def full_rag(question: str, history: list, retriever):
    # 第一步：查询改写（有历史时才走）
    if history:
        rewritten = await rewrite_chain.ainvoke({
            "question": question,
            "history_text": format_history_for_rewrite(history),
        })
    else:
        rewritten = question

    # 第二步：检索
    docs = await retriever.ainvoke(rewritten)

    # 第三步：上下文组装（自己控制）
    context_text, refs = build_context(docs, token_budget=3000)

    # 第四步：生成
    chain = qa_prompt | model.with_retry(stop_after_attempt=3) | StrOutputParser()
    answer = await chain.ainvoke({
        "context": context_text,
        "history": history[-6:],
        "question": question,
    })

    return {"answer": answer, "references": refs}

这段刻意写成显式的四步而不是一条长链，原因是RAG 出问题时必须能分段定位：改写后的查询是什么、检索回来了哪几块、组装后的上下文长什么样、模型看到这些之后答了什么。四步分开写，每一步的中间结果都能打日志、能单独重放；串成一条链之后就只剩输入和输出两端可见。如果确实要用一条链，至少把 build_context 这类纯函数抽出来单测，它是整条链里唯一能被确定性测试覆盖的部分。

最容易踩的坑
  • PDF 多栏排版错序：两栏内容被按行拼接，第一列的第一行接第二列的第一行，语义全乱。必须抽查或换用布局感知的解析器。
  • loader 返回的 page 字段从 0 开始：用户看到的页码从 1 开始，引用标注时如果不加 1，用户翻到错误的页面。
  • chunk_overlap 设得比关键句长：导致完整的关键句同时出现在两个块里，检索返回两个块内容几乎相同，浪费 token 预算。
  • 向量库 filter 传错格式：不同向量库的过滤语法差异大，LangChain 的适配没有统一，传错了不报错只是不过滤。
  • ParentDocumentRetriever 的 docstore 丢数据：默认用内存存储，进程重启大块就没了。必须配持久化存储。
  • 查询改写模型用了太大的模型：改写只需要简单的指代消解，用小模型足够，用大模型白花钱还加延迟。
  • 去重只比了 doc_id：同一文档的不同块 doc_id 相同，去重要比内容指纹。
  • 多语言文档不做语言对齐：中文查询检不到英文段落，Embedding 模型的跨语言能力差异很大。
  • 增量更新时只加不删：文档更新后旧版本的块还在库里，检索会同时命中新旧两个版本，答案自相矛盾。
  • 不测检索质量只测最终答案：答案错了不知道是检索没命中还是模型没理解，问题定位不了。
