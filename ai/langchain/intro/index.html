LangChain 上手：LCEL、消息抽象与结构化输出

上手 LangChain 需要真正搞懂的只有四件事：消息抽象、Prompt 模板、LCEL 组合子、结构化输出。剩下的都是这四件事的排列组合。这篇按这个顺序讲，每一处都标出常见的错法——因为网上教程里的写法有相当比例已经过时或者不可靠。RAG 的装配见站内 LangChain 搭 RAG 一篇，Agent 见站内 LangChain Agent 工程约束一篇。

消息抽象：为什么现在一律用 chat 接口

LangChain 早期有两套模型接口：LLM 收字符串返字符串，ChatModel 收消息列表返消息。现在一律用 ChatModel，原因不是风格偏好，而是LLM 接口拿不到角色区分、拿不到工具调用、拿不到多模态内容块。很多老教程用 OpenAI 而不是 ChatOpenAI，抄过来会发现工具调用根本没法用。

消息类型语义谁产生常见错误
SystemMessage角色设定与硬约束，模型对它的遵从度高于用户消息你的代码把它塞得极长；它会在每一轮都重复计费，也是提示词缓存的首选位置
HumanMessage用户输入，也用来承载检索到的资料用户或你的代码把不可信的外部文本直接拼进来，注入风险最高的位置
AIMessage模型输出，可能只有 tool_calls 而 content 为空模型工具调用轮次里丢掉这条消息，下一轮必然报错或重复调用
ToolMessage工具执行结果，必须带 tool_call_id你的代码用 HumanMessage 代替它，模型会以为工具没执行
AIMessageChunk流式分片，可用加号累积成完整消息模型只收集 content，把分片里的工具调用增量丢了

工具调用的多轮协议是新手最容易拼错的地方，顺序是硬性的：

sequenceDiagram autonumber participant U as 你的代码 participant M as ChatModel 已 bind_tools participant T as 工具函数 U->>M: SystemMessage 加 HumanMessage M-->>U: AIMessage，content 可能为空，携带 tool_calls Note over U: 这条 AIMessage 必须原样追加进历史
丢掉它下一轮就会重复请求同一个工具 U->>T: 按 tool_calls 里的 name 与 args 执行 T-->>U: 返回结果或错误 U->>M: 追加 ToolMessage，tool_call_id 一一对应 M-->>U: AIMessage 最终自然语言回答 Note over M,T: 一次工具调用等于两次模型调用
延迟与成本按往返次数线性增长

Prompt 模板与花括号这个坑

ChatPromptTemplate 值得用的地方是两个：MessagesPlaceholder 让历史成为一个可替换的槽位，以及 few-shot 模板让示例结构化。至于变量替换本身，它没比 f-string 强多少。

from langchain_core.prompts import ChatPromptTemplate, MessagesPlaceholder

# 坑：模板默认按 f-string 解析，单花括号都被当成变量名。
# 下面这行会直接抛错，因为 {"name": ...} 被当成了变量 "name"
# ChatPromptTemplate.from_messages([("system", '输出形如 {"name": "张三"}')])

# 修法一：字面花括号写成双花括号
prompt_a = ChatPromptTemplate.from_messages([
    ("system", '输出形如 {{"name": "张三"}} 的 JSON，不要加任何解释文字。'),
    ("human", "{question}"),
])

# 修法二（更推荐）：长示例当变量传进来，模板里不出现花括号，
# 顺带让 prompt 文本可以独立版本化、独立做灰度对比
prompt_b = ChatPromptTemplate.from_messages([
    ("system", "按下面的示例格式输出，不要加解释文字。\n\n{format_example}"),
    MessagesPlaceholder("history"),      # 历史消息槽位，传入 List 形式的消息
    ("human", "{question}"),
])

msgs = prompt_b.invoke({
    "format_example": '{"name": "张三", "age": 30}',   # 这里的花括号不会被解析
    "history": [],
    "question": "把这句话里的人名和年龄抽出来：李四今年 28",
})
# 调试第一招：先看渲染结果，确认发出去的到底是什么
for m in msgs.to_messages():
    print(m.type, repr(m.content)[:200])
⚠️
花括号踩坑的隐蔽形态

报错还算好事。更麻烦的是模板里写了正则量词、LaTeX、C 风格代码这类含花括号的内容，有些恰好能通过解析，于是变量被替换成空字符串，prompt 静默变形，你看到的只是「模型效果不稳定」。凡是 prompt 里要放代码或 JSON，一律走变量注入。

LCEL 的核心组合子

LCEL 的组合子只有三类：把东西接起来的、把东西并起来的、把东西包起来的。记住这个分类就不会乱。

组合子解决什么典型写法坑
管道符顺序串联，前一步输出即后一步输入prompt | model | parser类型不匹配时报错指向框架内部，不指向拼错的那一行
RunnableParallel并行跑多个分支并合成字典直接写字典字面量即可分支键名必须和下游模板变量完全一致，写错只在运行时暴露
RunnablePassthrough.assign在保留原输入的基础上追加字段检索结果加进原输入与 RunnableParallel 混用容易嵌套出多层字典
RunnableLambda把纯函数纳入链，且能被追踪上下文组装、结果后处理函数只接一个参数，多参数要先合成字典
with_retry瞬时错误自动退避重试挂在模型节点上挂在整条链上会把检索与嵌入一起重跑，成本翻倍
with_fallbacks主路径彻底失败时换备用主模型退到备用厂商或小模型备用模型的输出风格不同，结构化解析可能随之失败
bind固定住部分调用参数model.bind(stop=["\n\n"])绑定后的对象是新对象，原对象不受影响，容易误以为没生效
 
import asyncio
from langchain_core.output_parsers import StrOutputParser
from langchain_core.prompts import ChatPromptTemplate, MessagesPlaceholder
from langchain_core.runnables import RunnableLambda, RunnablePassthrough
from langchain_openai import ChatOpenAI

model = ChatOpenAI(
    model="gpt-4o-mini",
    temperature=0,        # 抽取、分类、改写这类任务一律 0，可复现才好排查
    timeout=30,           # 不设超时是生产事故的常见起点
    max_retries=0,        # 统一交给下面的 with_retry，避免次数叠乘
    max_tokens=800,       # 兜住失控生成，既控成本也控延迟
)

prompt = ChatPromptTemplate.from_messages([
    ("system", "你是客服助手。只依据资料回答；资料没有就说不知道。\n\n资料：\n{context}"),
    MessagesPlaceholder("history"),   # 历史放在系统提示之后、当前问题之前
    ("human", "{question}"),
])

def trim_history(x: dict) -> list:
    """历史裁剪是业务决策，不要交给框架。
    这里保留最近 6 条；生产中通常按 token 预算裁而不是按条数。"""
    return x.get("history", [])[-6:]

def fake_retrieve(x: dict) -> str:
    """真实项目里替换成 retriever 加自写的上下文组装。"""
    return "年假规则：入职满一年起每年 10 天，满三年 15 天。"

chain = (
    # 第一步：把输入补齐成模板需要的三个键。字典字面量就是 RunnableParallel
    {
        "question": lambda x: x["question"],
        "history": RunnableLambda(trim_history),
        "context": RunnableLambda(fake_retrieve),
    }
    | prompt
    # 重试只包住模型这一步，检索不会被重跑
    | model.with_retry(stop_after_attempt=3, wait_exponential_jitter=True)
    | StrOutputParser()
).with_config(tags=["kb-qa"], run_name="kb_qa_chain")   # 打标签便于事后按场景捞日志

async def main():
    # 单次异步调用
    print(await chain.ainvoke({"question": "入职两年有多少年假", "history": []}))

    # 批量：内部并发执行，用 max_concurrency 顶住厂商限流
    qs = [{"question": q, "history": []} for q in ["年假几天", "试用期多久", "加班怎么算"]]
    for r in await chain.abatch(qs, config={"max_concurrency": 4}):
        print(r[:40])

    # 流式：逐分片产出，首个分片到达即可渲染
    async for piece in chain.astream({"question": "年假怎么算", "history": []}):
        print(piece, end="", flush=True)

asyncio.run(main())

结构化输出：别再用提示词硬约束

这是本篇最该纠正的一个流传很广的做法。PydanticOutputParser 的原理是把 JSON Schema 说明塞进 prompt，然后希望模型照做；而 with_structured_output 走的是模型原生的工具调用或 JSON 模式，约束发生在解码阶段，由服务端保证输出可解析。两者可靠性不在一个量级。

方式约束发生在哪可靠性失败表现额外成本
with_structured_output 走工具调用模型解码阶段高，字段名与类型基本不会错偶发字段缺失、枚举值越界schema 描述计入输入 token
with_structured_output 指定 JSON 模式模型解码阶段较高，保证是合法 JSON合法但字段结构可能偏离同上
PydanticOutputParser提示词里的自然语言说明低，长输出与复杂嵌套下明显掉加解释性前缀、中文引号、尾随逗号、截断失败要重试，等于多花一次完整调用
OutputFixingParser 兜底再调一次模型让它修 JSON中修不好就再失败一次每次失败多一次调用，延迟翻倍
自己写宽松解析你的代码字段少时够用字段一多正则就失控维护成本

from typing import Literal, Optional
from pydantic import BaseModel, Field
from langchain_openai import ChatOpenAI

class Ticket(BaseModel):
    """工单分类结果。docstring 与 description 都会进 prompt，
    写清楚等于免费提升准确率，这是最划算的一处优化。"""
    category: Literal["billing", "bug", "feature", "other"] = Field(
        description="工单类别；无法判断时填 other，不要猜"
    )
    severity: int = Field(ge=1, le=4, description="严重度，1 最高 4 最低")
    summary: str = Field(description="不超过 30 字的中文摘要")
    customer_name: Optional[str] = Field(default=None, description="文中未出现则留空")

model = ChatOpenAI(model="gpt-4o-mini", temperature=0, timeout=30)

# include_raw=True：解析失败时不抛异常，而是把原始输出和异常一起返回，
# 这样能记录下失败样本用于改 prompt，而不是只在日志里看到一行栈。
extractor = model.with_structured_output(Ticket, include_raw=True)

def classify(text: str) -> Optional[Ticket]:
    out = extractor.invoke(f"把这条反馈抽成结构化工单：\n{text}")
    if out["parsing_error"] is not None:
        # 必须处理失败：模型不保证一定给出合法结构，哪怕走原生接口也有小概率
        log_bad_sample(text, out["raw"], out["parsing_error"])
        return None
    return out["parsed"]

def log_bad_sample(text, raw, err):
    print("STRUCT_FAIL", {"input": text[:80], "raw": str(raw)[:200], "err": str(err)})

流式输出，以及它和结构化解析的冲突

用户感知到的快慢主要是首个分片到达的时间，不是总生成时长。所以流式不是锦上添花，是延迟工程里性价比最高的一步。但流式和结构化解析在原理上打架：解析需要完整合法的 JSON，流式要求半截就能用。

接口产出什么适合代价
stream / astream链最终输出的增量分片纯文本回答逐字渲染拿不到中间步骤信息
astream_events全链各节点的开始与结束事件，含检索结果与工具结果前端展示正在检索、正在调用工具事件量大，要按 event 与 name 过滤
累积分片后一次解析完整输出需要结构化结果时失去流式收益，等同非流式
分两段调用先文本后结构既要展示又要落库多一次调用，成本与总延迟上升

async def sse_stream(question: str):
    """给前端推两类事件：阶段状态与内容分片。
    阶段状态能显著降低等待焦虑，成本为零。"""
    async for ev in chain.astream_events(
        {"question": question, "history": []}, version="v2"
    ):
        kind = ev["event"]
        if kind == "on_retriever_start":
            yield {"type": "status", "text": "正在检索资料"}
        elif kind == "on_retriever_end":
            docs = ev["data"]["output"]
            # 引用可以在生成开始前就给出，用户先看到依据再看到答案
            yield {"type": "sources",
                   "items": [d.metadata.get("source") for d in docs]}
        elif kind == "on_chat_model_start":
            yield {"type": "status", "text": "正在生成"}
        elif kind == "on_chat_model_stream":
            piece = ev["data"]["chunk"].content
            if piece:
                yield {"type": "delta", "text": piece}
        elif kind == "on_chat_model_end":
            usage = getattr(ev["data"]["output"], "usage_metadata", None)
            # token 用量在这里拿，用于成本归集；流式下部分厂商需显式开启用量统计
            yield {"type": "usage", "usage": usage}

异步与调试

LLM 调用是长耗时 IO，同步接口会把线程或事件循环占住。用 ainvoke 和 abatch 之后，同一进程能撑住的并发高一个数量级。要注意异步必须全链路：链里只要有一个只实现同步方法的组件，框架会把它扔进线程池执行，并发上限重新被线程数卡住——community 里的老组件经常是这种情况。

调试手段能看到什么局限
set_debug(True)每个节点的输入输出全量打印输出量极大，长上下文下基本不可读
set_verbose(True)关键步骤的简要日志看不到渲染后的完整 prompt
渲染后打印消息真正发给模型的消息列表只覆盖 prompt 环节，多步链要逐个加
自定义回调可在 on_llm_end 里拿 token 用量与耗时要自己写落盘与聚合
LangSmith 之类 tracing整次调用的树形视图、每步真实输入输出、token 与耗时、两次调用对比数据出网需评估合规，可换自建 OpenTelemetry 方案

排查「为什么模型答错」只有一个有效路径：看真正发出去的 prompt。十次里有八九次答案就在那里——历史被裁掉了关键一轮、检索片段根本没提到这个事、变量渲染成了空字符串。凭猜测改 prompt 是最浪费时间的做法。

反模式后果正确做法

最容易踩的坑
  • 并行分支键名与模板变量不一致：报错信息指向框架内部的字典取值，极难定位。链拼好后先只跑到 prompt 这一步，打印渲染结果验证。
  • MessagesPlaceholder 传了字符串：它要的是消息对象列表，传字符串会在渲染时炸，错误信息不直观。
  • 历史无限增长：不裁剪历史，输入 token 随轮次线性上涨，第二十轮的成本可能是第一轮的十几倍，还会撞上下文窗口。
  • bind 返回新对象：以为改了原模型，实际原对象没变，表现是参数「没生效」。
  • 流式下拿不到 token 用量：部分厂商在流式响应里默认不返回用量统计，需要显式开启，否则成本统计全是零。
  • 重试挂在整条链外层：一次模型限流触发整链重跑，检索与嵌入的费用白花，还可能把幂等性问题放大。
  • with_fallbacks 掩盖了真实故障：主模型持续失败但接口照常返回，没有告警就不会有人发现，务必对回退次数打指标。
  • 把资料放进 SystemMessage：检索资料每轮都变，放系统提示里会破坏提示词缓存前缀的稳定性，缓存命中率归零。
  • 用 max_tokens 截断结构化输出：上限设小了，JSON 被截在一半，解析必然失败且错误信息只说格式非法。
  • 异步里混入同步组件：框架会包线程池执行，看似正常但并发上限被线程数锁死，压测时才暴露。
