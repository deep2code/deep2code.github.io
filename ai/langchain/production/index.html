LLM 应用生产化：成本、延迟、可靠性与安全

把一个 LLM 原型变成能长期运行的线上服务，要解决的是五类问题：成本、延迟、可靠性、质量、安全。这五类问题有明确的优先级——成本是第一约束，因为它是唯一一个会随流量线性甚至超线性增长、并且可能直接让产品不成立的变量。这篇按这个顺序展开。

成本模型与估算方法

token 计费有三个容易被忽略的特性：输出比输入贵得多（单价通常是三到五倍）、缓存命中的输入有大幅折扣、多步流程的历史是重复计费的。这三条决定了优化方向。

估算维度怎么取值常见低估来源
平均输入 token系统提示加工具 schema 加历史加检索上下文，全部相加检索上下文与历史累积；实际值常是开发者印象的三到五倍
平均输出 token抽样统计实际回答长度模型爱写长答案；不设 max_tokens 时波动极大
单次请求的模型调用次数查询改写、重排、主生成分别算一次Agent 场景下是步数的函数，不是常数
调用量按场景分别统计，不要用全站平均重试与前端重复提交带来的放大
模型档位每个场景绑定一个档位所有场景都用最大模型，这是最常见的浪费
缓存命中率按请求指纹统计不做统计就无法知道缓存是否真的生效

估完之后必须对照真实账单校准一次。偏差通常出在两处：历史累积（对话第二十轮的输入可能是第一轮的十几倍）和检索上下文（塞了十段但真正有用的只有两段）。

提示词缓存：结构决定命中率

提示词缓存按请求前缀匹配，只有从第一个 token 起完全一致的那一段才算命中。这个机制意味着 prompt 的排列顺序直接决定能省多少钱，而多数项目的 prompt 结构恰好是错的——把当前时间、用户名、检索资料放在系统提示里，后面所有内容的缓存全部失效。

延迟工程：首 token 与总时长要分开看

用户感知的是首 token 延迟。只要有流式输出，总生成时长就不太影响体验——用户读前面的内容时后面还在产出。所以延迟优化的优先级很清晰：先接流式，再压首 token 之前的所有工作，最后才考虑总时长。

指标含义用户是否感知优化手段
首 token 延迟请求发出到第一个字出现强感知，这就是「等待时间」流式输出、准备工作并行化、减少前置模型调用、缩短输入
总生成时长完整回答产出完毕有流式则弱感知限制 max_tokens、换更快的模型
端到端 P99包含检索、重排、生成影响超时率各段独立设超时，总和小于网关超时
排队时长客户端限流导致的等待强感知，且用户不知道在排队提高配额、削峰、给出排队提示
首 token 前的串行步数改写加检索加重排直接叠加到首 token 延迟上能并行的并行，非必要的改写去掉
💡
一个被低估的免费优化

在首 token 到达之前，把中间状态推给前端：「正在检索资料」、「已找到 3 篇相关文档」、「正在生成」。这不降低任何实际延迟，但能显著降低等待焦虑，而且可以顺带把引用来源先展示出来。实现方式见站内 LangChain 上手一篇里的事件流部分。

可靠性：厂商限额是真实瓶颈

比模型宕机更常见的是撞上厂商侧的每分钟 token 与请求限额。表现是突发流量下大量 429，而且同一账号下多个服务共享配额，一个批量任务就能把在线服务挤下去。所以客户端限流不是可选项。

import asyncio, time

class TokenRateLimiter:
    """按 token 估算的客户端限流。厂商限额通常同时限请求数和 token 数，
    只按请求数限流时，长 prompt 请求依然会撞限额。"""

    def __init__(self, tokens_per_minute: int, requests_per_minute: int):
        self._tpm = tokens_per_minute
        self._rpm = requests_per_minute
        self._token_budget = tokens_per_minute
        self._req_budget = requests_per_minute
        self._window_start = time.monotonic()
        self._lock = asyncio.Lock()

    async def acquire(self, estimated_tokens: int):
        while True:
            async with self._lock:
                now = time.monotonic()
                if now - self._window_start >= 60:
                    # 固定窗口，简单够用；要更平滑可换滑动窗口或令牌桶
                    self._window_start = now
                    self._token_budget = self._tpm
                    self._req_budget = self._rpm
                if self._token_budget >= estimated_tokens and self._req_budget > 0:
                    self._token_budget -= estimated_tokens
                    self._req_budget -= 1
                    return
                wait = 60 - (now - self._window_start)
            # 排队而不是直接失败：突发流量下排队体验远好于报错
            await asyncio.sleep(min(wait, 1.0))

def estimate_tokens(text: str) -> int:
    """粗估：中文约 1.5 字一个 token，英文约 4 字符一个 token。
    宁可高估，低估会导致限流失效。"""
    cjk = sum(1 for ch in text if "\u4e00" <= ch <= "\u9fff")
    return int(cjk / 1.5 + (len(text) - cjk) / 4) + 32

质量保障：没有评测集就没有判断依据

这是 LLM 应用与传统软件最大的差别。传统软件改一行代码，行为变化是确定的；LLM 应用改一个词的 prompt，效果可能好也可能坏，而且你无法通过阅读代码判断。所以结论很硬：没有评测集，改 prompt、换模型、调检索参数这三类动作全都是赌博。

评测方式建设成本能发现什么局限
人工标注黄金集高，三十到一百条就有用核心场景是否回归，最可信覆盖面有限，需要定期补充线上坏样本
自动指标低格式合规率、解析成功率、拒答率、引用率只测形式不测内容正确性
检索命中率中，需标注相关文档问题出在检索还是生成标注哪些文档相关本身有主观性
LLM 作为评委低大批量粗筛，适合对比两个版本偏好长答案与自身风格，与人工判断的一致性需先验证；不能作为唯一依据
线上反馈低，加个点赞点踩真实分布下的问题反馈率低且偏向极端体验
影子对比中，双跑两个版本换模型前的真实差异成本翻倍，只适合关键变更

关于 LLM 作为评委，一个必须说清的局限：它倾向于给更长、更像自己风格的答案更高分，而且对事实错误的识别能力有限。可以用它做批量粗筛和版本对比，但把它当成质量的最终裁判会被系统性误导。最低可行的组合是：黄金集看核心场景，自动指标看形式合规，线上反馈补充坏样本。

import json, hashlib
from pathlib import Path

# prompt 版本化：prompt 是资产，要有版本号并随调用记录进日志。
# 不然线上效果变化时，没人能回答「上周和这周的 prompt 一样吗」。
PROMPTS = {
    "kb_qa.v3": (
        "你是知识库问答助手。只依据下方资料回答，"
        "在每个论断后用方括号标注资料编号。资料里没有就说不知道。"
    ),
    "kb_qa.v4": (
        "你是知识库问答助手。严格只依据下方资料回答。"
        "每个论断后用方括号标注资料编号。"
        "资料未覆盖的问题回答「资料中未找到相关信息」，不要基于常识补充。"
    ),
}

def prompt_of(name: str) -> tuple[str, str]:
    """返回 prompt 文本与用于日志的指纹，指纹变了就说明 prompt 变了。"""
    text = PROMPTS[name]
    fp = hashlib.sha256(text.encode()).hexdigest()[:8]
    return text, f"{name}+{fp}"

def run_eval(prompt_name: str, golden: Path) -> dict:
    """最低可行的回归：黄金集逐条跑，统计三个自动指标。
    任何 prompt 或模型变更都先过这一步，指标下降就不要上。"""
    total = hit = refused = cited = 0
    for line in golden.read_text(encoding="utf-8").splitlines():
        case = json.loads(line)
        answer = answer_with(prompt_name, case["question"])
        total += 1
        # 关键事实命中：标注里给出必须出现的字符串列表
        if all(k in answer for k in case["must_include"]):
            hit += 1
        if "未找到相关信息" in answer:
            refused += 1
        if "[" in answer:            # 是否带了引用编号
            cited += 1
    return {
        "prompt": prompt_name,
        "n": total,
        "fact_hit_rate": round(hit / total, 3),
        "refusal_rate": round(refused / total, 3),   # 过高说明检索或阈值有问题
        "citation_rate": round(cited / total, 3),
    }

安全：限制权限，而不是过滤输入

❌
提示注入无法彻底防御

指令和数据共享同一个文本通道，任何过滤规则都能被改写、编码、换语言绕过。而且注入源不只有用户输入：检索到的文档、工具返回结果、网页内容同样可能携带指令。所以「加一层敏感词过滤就安全了」是错的。正确思路是假设注入一定会成功，然后让它成功也造不成损害——也就是限制 LLM 的权限。

错误思路为什么不成立正确做法
过滤用户输入里的可疑指令可改写、编码、换语言绕过；且注入可能来自文档假设注入会成功，限制后果
在系统提示里写「不要听用户的指令」系统提示只是文本，优先级不是硬保证作为辅助手段可用，不能当防线
让 LLM 判断请求是否越权权限判定交给可被操纵的组件鉴权在服务端用调用者身份做
LLM 输出直接执行注入成功即等于远程代码执行输出只作为数据，执行前经参数校验与人工确认
LLM 输出直接渲染生成的内容可能含脚本或恶意链接按渲染上下文转义，见站内 XSS 一篇
敏感数据随手进 prompt会被厂商记录，且可能被后续输出泄露进 prompt 前脱敏或用占位符替换

把 LLM 当成不可信的文本转换器：输入可疑，输出也可疑。输出侧的 XSS 是最容易被忽略的一条——很多产品把模型生成的 Markdown 直接当 HTML 渲染，模型只要被诱导输出一个带脚本的链接或图片标签就成了注入入口。渲染前必须按上下文转义，细节见站内 XSS 上下文编码一篇。工具执行侧的边界见站内 LangChain Agent 工程约束一篇。

可观测性与合规

前面所有的优化都依赖一件事：能把每一次调用拆开看。没有这些字段，成本无法归集、质量变化无法归因、故障无法复现。

字段为什么必须有缺失时的症状
请求 ID 与会话 ID串联一次请求内的多次模型调用多步流程的日志散落，无法拼出完整轨迹
模型名与版本厂商会静默更新同名模型效果变了但找不到原因
prompt 版本标识质量指标要能按 prompt 版本分组无法回答「是不是 prompt 改坏了」
输入输出 token 数成本归集与异常请求定位只能看到总账单，不知道钱花在哪个场景
缓存命中标记验证缓存是否真的生效以为在省钱其实命中率为零
各段耗时区分检索慢还是生成慢只知道整体慢，优化无从下手
检索命中的文档 ID答错时判断是检索没找到还是模型没理解问题定位停在「模型答错了」
回退与重试次数主厂商异常的早期信号回退静默生效，故障被掩盖
用户反馈唯一来自真实分布的质量信号只能靠内部用例判断好坏
估算成本按场景与用户维度做预算与告警成本失控只能等月底账单

合规方面有三件事需要在接入前确认清楚，而不是上线后补：数据是否被用于训练（多数厂商的企业条款可关闭，默认设置未必）、数据驻留区域（跨境传输可能受限）、日志脱敏（prompt 里的用户数据会随日志一起长期留存，必须在写日志前脱敏，否则日志系统成了最大的敏感数据集中地）。

import asyncio, json, time, uuid, logging
from dataclasses import dataclass, field

log = logging.getLogger("llm")

# 单价按每千 token 计，输出通常是输入的三到五倍。
# 这张表要跟着厂商调价更新，建议放配置而不是代码。
PRICE = {
    "gpt-4o":      {"in": 0.0025, "out": 0.01,  "cached_in": 0.00125},
    "gpt-4o-mini": {"in": 0.00015, "out": 0.0006, "cached_in": 0.000075},
}

@dataclass
class CallResult:
    text: str
    model: str
    input_tokens: int = 0
    output_tokens: int = 0
    cached_tokens: int = 0
    cost_usd: float = 0.0
    latency_ms: int = 0
    first_token_ms: int = 0
    attempts: int = 0
    fell_back: bool = False
    meta: dict = field(default_factory=dict)


def calc_cost(model: str, in_tok: int, out_tok: int, cached: int) -> float:
    p = PRICE.get(model)
    if not p:
        return 0.0
    fresh_in = max(in_tok - cached, 0)
    return (fresh_in * p["in"] + cached * p["cached_in"]
            + out_tok * p["out"]) / 1000


class LLMClient:
    """生产级封装要素：超时、重试退避、多厂商回退、
    token 与成本统计、结构化日志、限流。"""

    def __init__(self, primary, backup, limiter: TokenRateLimiter):
        self._primary = primary      # 已配置 timeout 且关闭 SDK 内置重试
        self._backup = backup
        self._limiter = limiter

    async def call(self, messages, prompt_version: str,
                   scene: str, request_id: str = "",
                   max_attempts: int = 3) -> CallResult:
        request_id = request_id or uuid.uuid4().hex[:16]
        est = estimate_tokens(json.dumps(messages, ensure_ascii=False))
        await self._limiter.acquire(est)      # 客户端限流，排队优于报错

        started = time.monotonic()
        last_err = None

        for model_obj, is_backup in ((self._primary, False), (self._backup, True)):
            for attempt in range(1, max_attempts + 1):
                try:
                    resp = await model_obj.ainvoke(messages)
                    usage = getattr(resp, "usage_metadata", None) or {}
                    in_tok = usage.get("input_tokens", 0)
                    out_tok = usage.get("output_tokens", 0)
                    cached = (usage.get("input_token_details", {}) or {}).get("cache_read", 0)
                    name = getattr(model_obj, "model_name", "unknown")
                    res = CallResult(
                        text=resp.content, model=name,
                        input_tokens=in_tok, output_tokens=out_tok,
                        cached_tokens=cached,
                        cost_usd=calc_cost(name, in_tok, out_tok, cached),
                        latency_ms=int((time.monotonic() - started) * 1000),
                        attempts=attempt, fell_back=is_backup,
                    )
                    # 结构化日志：字段齐全才谈得上归因与成本归集
                    log.info(json.dumps({
                        "event": "llm_call", "request_id": request_id,
                        "scene": scene, "model": res.model,
                        "prompt_version": prompt_version,
                        "in_tok": in_tok, "out_tok": out_tok,
                        "cached_tok": cached, "cost_usd": round(res.cost_usd, 6),
                        "latency_ms": res.latency_ms, "attempts": attempt,
                        "fell_back": is_backup, "ok": True,
                    }, ensure_ascii=False))
                    return res
                except Exception as e:
                    last_err = e
                    # 指数退避加抖动：固定间隔重试会在上游抖动时造成同步风暴
                    backoff = min(2 ** (attempt - 1), 8) * (0.5 + 0.5 * time.monotonic() % 1)
                    log.warning(json.dumps({
                        "event": "llm_retry", "request_id": request_id,
                        "scene": scene, "attempt": attempt,
                        "fell_back": is_backup, "err": type(e).__name__,
                    }, ensure_ascii=False))
                    if attempt < max_attempts:
                        await asyncio.sleep(backoff)
            # 主模型耗尽重试才换备用；回退次数必须打指标并告警
            log.error(json.dumps({"event": "llm_failover",
                                  "request_id": request_id, "scene": scene},
                                 ensure_ascii=False))

        raise RuntimeError(f"all providers failed: {last_err!r}")

最容易踩的坑
  • 流式下 token 用量为零：部分厂商在流式响应里默认不返回用量统计，需要显式开启，不开的话成本看板全是零。
  • 提示词缓存前缀被时间戳破坏：在系统提示里写「当前时间是 xx」，缓存命中率直接归零，而账单上看不出这个原因。
  • 厂商静默更新同名模型：同一个模型名在不同时期行为不同，效果突然变化却找不到自己的改动。日志里必须记录响应返回的具体版本号。
  • 重试与 SDK 内置重试叠乘：实际请求次数是两层次数相乘，上游抖动时自己把流量放大了几倍。
  • 超时设置层层放大：模型 30 秒、检索 10 秒、网关 30 秒，串起来必然先被网关掐断，前端拿到的是无意义的 504。各段超时之和必须小于网关超时。
  • 缓存键没算上 prompt 版本：改了 prompt 但旧结果还在缓存里返回，看起来像改动没生效。
  • 缓存了个性化内容：把带用户身份的答案缓存给了别人，属于数据泄露。缓存键必须包含权限维度。
  • 拒答率没有监控：检索出问题时表现是大量「未找到相关信息」，功能看似正常，用户默默流失。
  • 日志把完整 prompt 明文落盘：日志系统变成最大的敏感数据集中地，且通常权限宽松、留存很久。
  • max_tokens 设得太小截断结构化输出：JSON 被截在一半，解析失败率上升，错误信息只说格式非法。
  • 用 LLM 评委的分数当唯一质量指标：它偏好长答案与自身风格，优化这个分数可能让真实体验变差。
  • 没有降级路径：模型全挂时直接把异常抛给用户。至少要返回一句明确的说明，或退回到关键词检索这类非 LLM 路径。
