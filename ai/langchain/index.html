LangChain 抽象设计与选型：LCEL、值不值得用、替代方案

🏷️ LangChain

LangChain 是近几年争议最大的框架：一边是最快的上手路径，一边是「抽象过度、调试地狱」的批评。这篇不复述教程，只回答三个工程问题——它到底把什么东西抽象掉了、这些抽象里哪些值得用哪些不如自己写、以及在什么规模下它是资产而不是负债。RAG 的分块与检索算法见站内 RAG 工程化实践一篇，检索侧数据工程见站内 RAG 检索侧数据工程一篇，Agent 的规划范式与多智能体见站内 AI Agent 一篇；本篇只谈框架本身。

LangChain 实际提供的是五层东西

讨论「该不该用 LangChain」之所以经常各说各话，是因为它根本不是一个东西。它是五层独立的东西被打包在一个名字下面，每一层的成熟度和可替代性完全不同，必须分开评估。

看清这张图之后，那句「LangChain 抽象过度」就能翻译成一句更准确的话：第二层的适配是真本事，第四层的组合协议是真价值，争议全部集中在第三层里那些高阶封装上。绝大多数骂它的人骂的是第三层，绝大多数用它爽的人用的是第二层和第四层。

一张值不值得用的判断表

判断标准只有一条，简单到可以当口诀用：这个抽象是否屏蔽了真实存在的差异。屏蔽了真实差异的值得用，因为那些差异你自己也要处理，而且处理起来又脏又琐碎。只是给几行代码换了个名字的不值得用，它没消除任何复杂度，只是把复杂度挪到了你看不见的地方，还额外收你一笔版本升级税。

抽象它屏蔽的真实差异判断理由与残留成本
ChatModel 适配各厂商鉴权方式、消息字段名、工具调用结构、流式分片格式、错误码与限流响应各不相同值得用换厂商只改构造函数。残留：不同模型对同一 prompt 的敏感度不同，换了要重测效果
Embeddings 适配单次批量上限、维度、超长输入截断策略、是否区分查询与文档模式值得用批大小与并发仍要自己控，默认值在大批量灌库时会打爆限流
VectorStore 适配各库 SDK、过滤语法、距离度量命名差异极大有条件值得基础写入与相似度查询好用；索引参数、混合检索、分区与权限过滤还得写库特有代码，选型见站内向量数据库选型一篇
DocumentLoader每种文件格式各有一套解析库和一堆坑值得用省掉选库时间，但解析质量必须人工抽查，它只是帮你调库不保证解析对
Prompt 模板几乎没有，本质是字符串格式化加消息结构轻量值得价值在历史占位符与 few-shot 结构化，不在格式化本身；顺手用，别为它引入框架
LCEL 组合子流式、批量、异步、重试、回退、回调这六件事的统一实现值得用这是目前最值得用的部分，详见下一节
PydanticOutputParser没有。靠 prompt 里塞 JSON Schema 说明加解析重试不值得模型原生的工具调用与 JSON 模式可靠得多，优先用结构化输出接口
RetrievalQA 这类高阶链没有。把检索、拼接、调用三步包成一个类不值得省三行代码，代价是塞几段、怎么排序、怎么截断、引用怎么带全都不可控
AgentExecutor把工具调用循环包起来不值得行为不透明、无法插审批节点、状态不能持久化，改用 LangGraph
旧 Memory 类没有。历史存哪、怎么裁剪本来就是业务决策不值得对话历史涉及存储选型、多端同步、隐私清理，交给框架反而不好改
💡
一个反直觉的结论

LangChain 最值得用的两层，也就是适配层和 LCEL，恰好是最没有「框架感」的两层：它们不规定你的代码怎么组织，只提供统一接口和统一执行语义。而最有「框架感」的高阶链和 Agent 封装，恰好是最该躲开的。谁规定你怎么写业务，谁就是负债。

高阶链的问题不是慢，是藏掉了关键决策

拿 RAG 举例最直观。用高阶链三行就能跑通，但 RAG 的效果几乎全部取决于「检索回来之后怎么组装上下文」，而这一步被封装吃掉了。

# 反面：三行跑通，但关键决策全看不见
from langchain.chains import RetrievalQA

qa = RetrievalQA.from_chain_type(llm=llm, chain_type="stuff", retriever=retriever)
print(qa.invoke("年假有多少天")["result"])
# 看不见也改不了的东西：塞了几段、按什么顺序排、超 token 预算怎么截断、
# 段落之间怎么分隔、重复内容是否去重、答案引用了哪几段。
# 而这些恰好就是决定 RAG 好不好用的全部变量。

# 正面：显式写出来只多十几行，每一步都能改、能打日志、能单测
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.runnables import RunnableParallel
from langchain_core.output_parsers import StrOutputParser

PROMPT = ChatPromptTemplate.from_messages([
    ("system", "只依据资料回答，并在句末用方括号标注资料编号；资料里没有就回答不知道。\n\n{context}"),
    ("human", "{question}"),
])

def build_context(docs, budget: int = 2000) -> str:
    """上下文组装：这是最该自己控制的一步。
    去重、按相关性截断到 token 预算、编号以便模型引用。"""
    seen, parts, used = set(), [], 0
    for i, d in enumerate(docs, 1):
        key = d.page_content[:120]          # 粗粒度去重，多数重复来自块重叠
        if key in seen:
            continue
        seen.add(key)
        cost = len(d.page_content) // 2     # 中文约 1 token 对 1.5 字，留足余量
        if used + cost > budget:
            break                           # 宁可少塞一段，也不要挤爆预算
        used += cost
        src = d.metadata.get("source", "未知")
        parts.append(f"[{i}] 来源：{src}\n{d.page_content}")
    return "\n\n".join(parts)

chain = (
    RunnableParallel(
        context=(lambda x: x["question"]) | retriever | build_context,
        question=(lambda x: x["question"]),
    )
    | PROMPT
    | llm
    | StrOutputParser()
)

多写的这十几行换来的是：上下文预算可调、去重策略可换、引用编号可追溯、build_context 可以脱离 LLM 单元测试。省代码从来不是目标，能改和能测才是。这也给出了一个实用的检验标准：如果某个封装让你无法对其中的纯函数部分写单测，就别用它。

LCEL：统一执行契约，收益与代价

LCEL 常被误解成「一个花哨的管道语法糖」。它的实质是给所有组件规定同一份执行契约：只要实现 Runnable 协议，就必须同时支持同步、异步、批量、流式、事件流五种执行方式，并且能被重试、回退、超时、回调统一包装。管道符只是拼装这份契约的语法。

这才是 tracing 能看到每步真实输入的原因
LCEL 免费给你的能力不用它自己写要付什么它的代价
逐分片流式，且解析器能增量转换每个厂商的分片结构不同，还要处理分片与解析的配合结构化解析与流式天然冲突，需要分段处理
批量并发，自动控并发度手写线程池或信号量，还要处理部分失败默认并发度可能撞厂商限流，要显式配置
同一份链既能同步又能异步同一逻辑写两遍，或者全局改造成异步某些 community 组件只实现了同步，异步会退化为线程池包装
重试与回退可挂在任意子节点上自己写退避、自己判断哪些错误该重试重试点位置很关键，挂错层级会把整条链重跑一遍，包括检索
回调贯穿全链，直接接 tracing手工埋点，且很难拿到框架内部的真实 prompt回调链本身会出现在异常堆栈里，加深调试噪声
并行分支与透传组合手写协程编排与结果合并字典键名错了报错信息很难懂，常见于分支输出与模板变量不匹配

代价最真实的一条是调试体验：一个模板变量名写错，栈里可能出现七八层框架帧，最终异常信息指向 LangChain 内部的字典取值而不是你写错的那一行。所以用 LCEL 就必须配 tracing，靠读堆栈定位 LCEL 问题是低效的。

包拆分与版本风险：采用它的头号成本

LangChain 做过一次彻底的包拆分，这件事对使用者是好消息，它把稳定的抽象和不稳定的集成分开了，让你有机会只依赖稳定的那部分。但前提是你知道哪个包稳定。

包装了什么稳定性使用建议
langchain-coreRunnable 协议、消息类型、prompt、输出解析基类、回调最高，破坏性变更少且有废弃期唯一允许出现在业务代码签名里的包
langchain-openai 等厂商包具体模型与嵌入适配中，跟随厂商 API 变动按需装，锁到补丁位，厂商出新特性时这里最先跟上
langgraph状态图、条件边、检查点存储中高，定位清晰且独立演进有循环或审批需求就直接用它
langchain高阶链、Agent 组装、旧 Memory低，历史上大改过多次尽量不依赖，需要的功能自己写十几行
langchain-community几百个第三方集成最低，大量集成事实上无人维护用前必须去仓库看该集成文件最近一次提交时间
langsmith追踪与评测 SDK与框架解耦可单独用，即使不用 LangChain 也能接
⚠️
community 包的真实风险

community 里的集成以社区一次性贡献居多，上游 SDK 一改就静默坏掉，而且坏法往往是「能跑但结果不对」，比如某个向量库集成把过滤条件悄悄忽略了。上生产前对每个 community 集成做一件事：读一遍它的源码，通常只有一两百行，比排查线上诡异问题便宜得多。

把框架风险关进一个文件

降低破坏性变更伤害的办法不是不升级，而是让升级的影响面可枚举。做法是一层薄适配：业务只认自己的数据类，框架类型不许越过这道门。

# llm_gateway.py —— 整个项目里唯一 import langchain_* 的文件
from dataclasses import dataclass
from typing import Protocol

from langchain_anthropic import ChatAnthropic
from langchain_core.output_parsers import StrOutputParser
from langchain_core.prompts import ChatPromptTemplate
from langchain_openai import ChatOpenAI


@dataclass(frozen=True)
class AnswerResult:
    """业务侧返回类型。不暴露 AIMessage，
    这样将来换掉 LangChain 或换成裸 SDK，调用方一行都不用改。"""
    text: str
    model: str


class Answerer(Protocol):
    """业务代码依赖这个协议而不是具体实现，测试时可注入假实现。"""
    async def answer(self, question: str, role: str) -> AnswerResult: ...


_PROMPT = ChatPromptTemplate.from_messages([
    ("system", "你是{role}，只依据事实回答，不确定就明确说不知道。"),
    ("human", "{question}"),
])


class LangChainAnswerer:
    def __init__(self, model: str = "gpt-4o-mini"):
        primary = ChatOpenAI(
            model=model,
            temperature=0,
            timeout=30,        # 必须显式设；不设超时的慢请求会把连接和协程占死
            max_retries=0,     # 关掉 SDK 内置重试，避免与 with_retry 叠乘成 9 次
        )
        backup = ChatAnthropic(
            model="claude-3-5-haiku-latest", timeout=30, max_retries=0,
        )
        self._model = model
        # 重试挂在模型节点上而不是整条链上：否则一次 429 会把检索也重跑一遍
        self._chain = (
            _PROMPT
            | primary.with_retry(stop_after_attempt=3).with_fallbacks([backup])
            | StrOutputParser()
        )

    async def answer(self, question: str, role: str) -> AnswerResult:
        text = await self._chain.ainvoke({"question": question, "role": role})
        return AnswerResult(text=text, model=self._model)
# 依赖锁定：LangChain 必须锁到补丁位，不要写大于等于
# 理由：包拆分与 LCEL 迁移改过导入路径和默认行为，
# community 里的集成还会跟着上游 SDK 一起静默 break。

LangGraph：链不够用的时候

LCEL 链是有向无环图，数据从一头进从另一头出，中间不能回头。这个限制在单轮流程里很舒服，在需要反复试探的流程里就变成硬墙：Agent 的本质是循环，而循环无法用链表达。硬要用链表达，就得把循环藏进某个执行器里，于是就有了 AgentExecutor 那种不透明的黑盒。

flowchart TB subgraph CH["LCEL 链：有向无环，一次穿过"] C1["输入"] --> C2["prompt 渲染"] C2 --> C3["模型调用"] C3 --> C4["输出解析"] C4 --> C5["返回"] end subgraph LG["LangGraph：显式状态图，允许回边与中断"] G1["START"] --> G2["决策节点"] G2 --> G3{"需要调工具"} G3 -->|是| G4["工具节点"] G4 --> G2 G3 -->|否| G5{"是否高风险操作"} G5 -->|是| G6["人工审批中断"] G6 --> G2 G5 -->|否| G7["END"] G2 --> G8["checkpointer 每步落盘状态"] end

LangGraph 值得单独采用的四个信号：需要断点恢复，用户关掉页面第二天继续，状态必须在存储里而不是在内存里；需要人工审批，图可以在某个节点挂起，等外部输入再继续；需要显式分支与循环，条件边是代码而不是模型的隐式行为；需要观测每一步，每次状态转移都是一条可回看的记录。这四条命中任意一条就不要在链上硬凑。具体实现见站内 LangChain Agent 的工程约束一篇。

框架类型渗透进业务签名与存储模型换框架等于重写，升级影响面不可枚举一层适配，业务只认自己的数据类
拿 Agent 当确定性流程用成本与延迟按步数乘，结果还不稳定能用固定流程写清的就写固定流程
重试挂在整条链上一次模型限流把检索与嵌入全部重跑，成本翻倍重试挂在会失败的那个节点上
不接 tracing 靠打印调试看不到真正发出的 prompt，排查全靠猜开发期就接上追踪，这是唯一有效手段

最容易踩的坑
  • 不设 timeout：模型客户端默认超时很宽松甚至没有，一次上游卡顿就把协程池占满，表现是整个服务不可用而不是单个请求慢。
  • 重试次数叠乘：SDK 自带 max_retries 加上 with_retry，实际请求次数是两者相乘。接入时先把 SDK 侧关掉。
  • 回退模型没重测效果：不同厂商对同一 prompt 的遵从度差别很大，主模型挂了切备用模型，功能还在但输出格式可能全变，结构化解析随之失败。
  • 照抄教程里的 LLMChain：网上大量文章仍在用已被取代的旧接口，抄来能跑但拿不到流式与批量能力，还会在升级时先坏。
  • 只装 langchain 一个包：会顺带拉进一大堆间接依赖，镜像体积和依赖冲突概率都上去了。按需装 core 加厂商包。
  • 把 prompt 写死在链里：prompt 是需要版本化和灰度对比的资产，硬编码在代码里会导致线上效果变化无法归因。
  • 用同步接口跑在异步框架里：同步调用在事件循环里阻塞，压测时并发上不去，看起来像模型慢其实是自己堵死了。
  • 模板变量与并行分支键名不一致：报错信息指向框架内部字典取值，极难定位。链拼好后先用假模型跑一遍验证键名。
  • 把框架升级和业务改动混在一个提交里：效果变差时无法判断是升级还是改动引起的，回滚也没法只回一半。
  • 以为换厂商是零成本：代码层面确实是改一行，但 token 计价、上下文窗口、工具调用格式、限流额度全都变了，属于需要重新压测和重新估算成本的变更。
