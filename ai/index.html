后端工程师需要的 AI 能力地图

这个分类下的文章横跨大模型调用、检索增强、Agent、微调和 AI 编程工具，看着零散，实际是五个由浅到深的接入层次。层次越往下，能力越强，但引入的工程负担、成本和失控风险也越大。选层次的原则很简单：能在上一层解决的问题，不要下沉到下一层——绝大多数团队真正需要的是第一层加第二层，却经常一上手就去做 Agent 和微调。

flowchart TB subgraph A1["第一层：直接调用模型"] N1["分类、抽取、改写、摘要、生成"] N2["真正的约束是延迟、限额与输出不可信"] end subgraph A2["第二层：把你的数据喂给模型"] N3["检索增强：切分、向量化、召回、重排"] N4["效果上限由检索质量决定，不由模型决定"] end subgraph A3["第三层：让模型调用你的系统"] N5["工具调用与多步编排"] N6["风险是步数与成本不可控、工具权限过大"] end subgraph A4["第四层：改造模型本身"] N7["微调与私有化部署"] N8["能稳住格式与风格，补不上知识缺口"] end subgraph A5["旁路：AI 编程工具"] N9["补全、对话、自动改代码"] N10["产出一律走评审、测试与静态检查"] end N2 --> N1 N1 --> N3 N4 --> N3 N3 --> N5 N6 --> N5 N5 --> N7 N8 --> N7 N9 --> N10
层次典型任务主要成本在哪上线前必须先有的东西什么时候不该用这一层
直接调用模型意图识别、字段抽取、文案改写、摘要按 token 计费，长上下文与长输出最贵输出结构校验、超时预算、降级分支、成本埋点输出要求逐字确定、或判错代价无法吸收时
检索增强基于内部文档与工单回答问题数据管道与向量库的运维，而不是模型文档切分策略、召回评测集、权限过滤数据源本身混乱、没人维护时，做了也是错答案
Agent 与工具调用跨系统查询、多步任务、自动化流程步数不可控导致成本与延迟发散最大步数、工具白名单、最小权限凭证、全链路追踪流程已经稳定且可用状态机描述时，写代码更划算
微调与私有化固定格式输出、垂直领域语气、数据不出网数据标注与训练评估的人力，加上推理资源常驻标注规范、评测基线、回滚到基座模型的路径只是想补知识，或提示词还没认真调过时
AI 编程工具补全、重构、写测试、读陌生代码订阅费低，隐性成本是错误代码的返工评审纪律、测试覆盖、明确不许提交的内容边界涉及密钥、未公开业务逻辑、合规敏感代码时

什么问题该用大模型，什么问题不该用

这是最值得先想清楚的一步。大模型的本质是概率性的、不可完全复现的组件，把它放到要求确定性的位置上，后面所有工程手段都只是在给错误的选型打补丁。五个判断维度依次是：确定性要求、可解释性、成本、延迟、数据敏感度。只要有一条明确不满足，就该换方案，而不是「先上了再优化」。

flowchart TB A["一个待解决的需求"] --> B{"输出必须每次完全一致吗"} B -- 是 --> C["用规则、SQL 或传统算法"] B -- 否 --> D{"判错的代价能被兜底或人工吸收吗"} D -- 不能 --> C D -- 能 --> E{"依赖私有或实时数据吗"} E -- 是 --> F["先做检索增强，把数据管道做对"] E -- 否 --> G{"延迟预算有秒级吗"} G -- 没有 --> H["改用小模型，或离线预生成加缓存"] G -- 有 --> I["直接调用模型，加结构校验与降级"] F --> I
判断维度适合交给大模型不适合，应该用传统方案怎么判断
确定性要求同一输入允许有表述差异，语义对就行金额计算、权限判定、状态流转、对账问一句：结果能不能被写成单元测试里的相等断言
可解释性结论能附来源或能被人快速核对需要向监管或用户解释「为什么是这个结果」出错时能否复现并定位到具体规则
成本单次调用价值高，调用量可控高频、低价值、可被缓存或规则覆盖的场景用每次调用的 token 量乘以日调用量先算一遍
延迟秒级可接受，或可流式、可异步同步链路里毫秒级预算的位置看这一步是否挡在用户等待的主路径上
数据敏感度可脱敏、或有合规的私有化部署原始凭证、个人敏感信息、未公开代码问清数据出网边界与供应商的留存策略

把 AI 能力接进现有系统的分层与边界

最常见的落地错误是让业务代码直接去调模型供应商的 SDK。这样一来提示词散落在各处、没有统一的超时与限额、成本无法按业务线归因、换供应商要改几十个文件。正确形态是加一层AI 网关：提示词组装、版本标记、结构校验、计量埋点、降级路由全部收口到这一层，业务服务只传业务参数、只拿结构化结果。

sequenceDiagram participant U as 用户请求 participant S as 业务服务 participant G as AI 网关 participant R as 检索与上下文组装 participant M as 模型供应商 U->>S: 业务请求，先走既有鉴权与限流 S->>G: 只传业务参数，不传原始凭证 G->>R: 按当前用户的权限过滤可见数据 R-->>G: 组装提示词，记录提示词版本 G->>M: 发起调用，带超时预算与幂等键 M-->>G: 流式返回，同时按 token 计量 G->>G: 结构校验、敏感信息过滤、失败则降级 G-->>S: 返回结构化结果与置信标记 S-->>U: 落库并保留可追溯记录后返回
位置应该承担绝对不要放在这里放错的后果
业务服务业务规则、权限判定、事务与落库提示词文本、供应商 SDK 调用、重试策略提示词散落各处，换模型和排查问题都要全局改代码
AI 网关提示词版本、超时与限额、结构校验、计量、降级路由业务分支逻辑、直接访问业务数据库网关变成第二个业务系统，谁都不敢改
检索与上下文组装按权限过滤、召回与重排、上下文裁剪不做权限过滤就把全量文档塞进上下文越权泄露：用户通过提问读到不该看的内容
提示词层任务说明、输出契约、少样本示例把安全规则只写在提示词里当作防线提示词不是安全边界，可被用户输入覆盖
数据与凭证最小权限的下游凭证，逐次授权把管理员令牌交给工具调用一次提示词注入就变成一次真实的越权操作

各子方向怎么读

三条常见路线：先把一次调用做对，从大模型服务化的工程约束开始；要做内部知识问答，直接进 RAG 两篇，重点在数据管道而不是模型；想提升自己的编码效率，从 AI 编程工具的横评与工作流入手。下表给每个子方向一句「什么时候该读它」。

子方向它解决的问题什么时候该读它
大模型服务化延迟拆解、限额、超时重试与幂等、输出校验、成本埋点准备把模型调用接进线上服务，需要先知道有哪些坑时
RAG 原理 与 RAG 工程化切分、向量化、召回重排、评估与权限过滤要做内部文档问答，或现有问答答非所问时
Agent 开发推理与行动循环、工具调用、记忆与多智能体协作任务需要多步决策、并且要真的去操作外部系统时
LangChain 选型框架提供了什么、值不值得引入、替代方案在纠结自己封装还是上框架时
模型微调LoRA 与全参数调优、数据质量、什么时候不该微调提示词已经调到极限、输出格式仍不稳定时
机器学习与框架基础概念、训练推理链路、本地部署需要补机器学习基础，或要在自己机器上跑模型时
Coding Agent 全景 与 工具横评各类 AI 编程工具的能力边界与选型团队要统一工具链、或想知道该为哪个付费时
Prompt 工程 与 工作流怎么描述任务、怎么管上下文、怎么拆解需求工具已经在用，但产出质量忽高忽低时
❌
这个方向上最容易踩的坑
  • 把确定性任务交给模型：金额、权限、状态流转用模型判断，出一次错就是资损或越权
  • 业务代码直接调供应商 SDK，提示词散落各处，换模型时要改几十个文件
  • 检索环节不做权限过滤，用户靠提问就能读到别人的数据
  • 把安全规则只写在提示词里，以为「不要做危险操作」这句话能挡住注入
  • 模型输出不校验就落库或直接执行，脏数据和命令注入同时发生
  • 提示词和模型版本不入版本库，线上质量退化时查不到当时用的是哪一版
  • 成本埋点没有业务线维度，账单涨了只能看到一个总数
  • 没有评测集就开始调提示词，全凭「感觉这次好一点」
  • 先做 Agent 和微调，最基础的调用层可靠性、结构校验和降级都还没有
  • 把 AI 编程工具的产出直接提交，跳过评审和测试，欠债转移到线上
  • 敏感代码、密钥、未公开业务逻辑贴进公网工具，合规问题比技术问题更难收场
