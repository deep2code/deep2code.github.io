RAG 检索增强生成

🏷️ AI与大模型

💡 你在工作中遇到了这个问题，查了很多资料还是没搞懂。或者你面试的时候被问到，答不上来。

什么是 RAG

RAG（Retrieval-Augmented Generation，检索增强生成）把信息检索和大语言模型拼到一起：先从外部知识库捞相关文档，再喂给 LLM 来增强回答，既压幻觉又能给出可溯源的知识。

为什么需要 RAG：纯 LLM 有两个硬伤——不知道你的私有数据，还会一本正经地编造（幻觉）。RAG 的思路是「答案不来自模型的记忆，而来自你给它看过的资料」，这样既能引用私有知识，又能附带来源链接，用户可核对。

RAG 架构总览

一个最小可用的 RAG 分两条线：离线建库（把文档切成块、向量化、存进库）和在线问答（把问题向量化、检索、拼 Prompt、让 LLM 作答）：

flowchart TD A[用户提问] --> B[Query Embedding] B --> C[向量检索 Vector Search] C --> D[Top-K 相关文档] D --> E[构建 Prompt: 问题 + 检索到的上下文] E --> F[LLM 生成回答] F --> G[输出：答案 + 来源引用] subgraph 离线建库 H[文档库] --> I[分块 Chunking] I --> J[Embedding 向量化] J --> K[向量数据库] end C -.-> K

向量嵌入（Embedding）深度解析

Embedding 模型把文本压成一个能代表语义的向量，向量越近语义越像。理解它的训练方式，才知道为什么中文场景要选对模型：

Embedding 模型原理：

  输入文本 → Transformer Encoder → [CLS] 向量（或平均池化）

  关键技术：
  1. 对比学习（Contrastive Learning）
     - 正样本：语义相似的文本对
     - 负样本：语义不同的文本对
     - Loss：InfoNCE = -log(exp(sim(q,p+)/τ) / Σ exp(sim(q,p_i)/τ))
     - τ 是温度参数，控制分布尖锐程度

  2. 难负样本挖掘（Hard Negative Mining）
     - 随机负样本太容易，模型学不到细粒度差异
     - 用 BM25 检索 Top-K 作为难负样本
     - 或用模型自身检索的错误结果作为难负样本

  3. 指令微调（Instruction-tuned Embedding）
     - E5、BGE、GTE 等模型支持查询指令
     - Query: "为这个查询生成向量：{query}"
     - Passage: "为这段文本生成向量：{passage}"
     - 显著提升检索效果

  主流 Embedding 模型对比（2026年）：
  ┌──────────────────┬────────┬──────────┬──────────────┐
  │ 模型             │ 维度   │ 最大长度 │ MTEB 排名    │
  ├──────────────────┼────────┼──────────┼──────────────┤
  │ OpenAI text-3   │ 3072   │ 8191     │ 闭源，高质量 │
  │ BGE-M3           │ 1024   │ 8192     │ 开源，多语言 │
  │ GTE-Qwen2        │ 1536   │ 32768    │ 阿里，长文本 │
  │ E5-Mistral       │ 4096   │ 4096     │ 多语言       │
  │ Jina v3          │ 1024   │ 8192     │ 多语言       │
  └──────────────────┴────────┴──────────┴──────────────┘

  相似度计算：
  - 余弦相似度：cos(a,b) = (a·b) / (||a|| · ||b||)
  - 点积：a·b（向量归一化后等价于余弦）
  - 欧氏距离：||a - b||（越小越相似）
  - 大多数向量数据库用余弦或点积

ANN 近似最近邻搜索算法

向量数量上千万时，暴力算相似度太慢。ANN 用「近似但足够准」的换速度——HNSW 是目前最主流的：

暴力搜索复杂度：O(N · d)，N=向量数，d=维度
  1000 万向量 × 1024 维 = 100 亿次运算/查询 → 太慢

HNSW（Hierarchical Navigable Small World）：
  目前最主流的 ANN 算法，Milvus、Qdrant、Weaviate 默认

  结构：多层有向图
  ┌─────────────────────────────────────────┐
  │  Layer 2:  少量节点，长距离连接           │  快速跳到目标区域
  │  Layer 1:  中等节点数，中距离连接         │  缩小搜索范围
  │  Layer 0:  所有节点，短距离连接           │  精细搜索最近邻
  └─────────────────────────────────────────┘

  搜索过程：
  1. 从最上层的入口节点开始
  2. 在当前层贪心搜索，找到最近的节点
  3. 下降到下一层，从该节点继续搜索
  4. 重复直到最底层，返回 Top-K

  关键参数：
  - M：每个节点的最大连接数（通常 16~64）
  - efConstruction：构建时的搜索宽度（通常 100~500）
  - efSearch：查询时的搜索宽度（通常 50~200）
  - 权衡：efSearch 越大，召回率越高，速度越慢

  性能：
  - 1000 万向量，召回率 99%，查询延迟 < 10ms
  - 内存占用：约 2GB（1000万 × 1024维 × 2 bytes + 图结构）

其他算法：
  - IVF（Inverted File）：聚类分桶，先查聚类中心再查桶内
  - PQ（Product Quantization）：向量压缩，内存节省 10x+
  - ScaNN：Google 的算法，各向异性量化
  - DiskANN：基于磁盘的 ANN，支持十亿级向量

核心组件实战

下面用 LangChain 0.3+ 的写法把「文档处理 → 向量化存储 → 检索生成」串一遍。注意 1.x 之后包结构和链式接口都有变动，按注释里的新写法走。

1. 文档处理与分块

# langchain 0.3+：text_splitter 移入独立包 langchain-text-splitters，DirectoryLoader 移入 langchain-community
from langchain_text_splitters import RecursiveCharacterTextSplitter
from langchain_community.document_loaders import DirectoryLoader

# 加载文档
loader = DirectoryLoader("./docs", glob="**/*.md")
docs = loader.load()

# 文档分块
splitter = RecursiveCharacterTextSplitter(
    chunk_size=500,        # 每块最大 500 字符
    chunk_overlap=50,      # 块之间重叠 50 字符
    separators=["\n\n", "\n", "。", "！", "？", " "],
)
chunks = splitter.split_documents(docs)
print(f"共 {len(chunks)} 个文档块")

2. 向量化与存储

# langchain 0.3+：embeddings/vectorstores 位于 langchain-community 与 langchain-chroma 包
from langchain_community.embeddings import HuggingFaceEmbeddings
from langchain_community.vectorstores import Chroma

# 使用中文 embedding 模型
embeddings = HuggingFaceEmbeddings(
    model_name="BAAI/bge-small-zh-v1.5",
    encode_kwargs={"normalize_embeddings": True},
)

# 存入向量数据库
vectorstore = Chroma.from_documents(
    documents=chunks,
    embedding=embeddings,
    persist_directory="./chroma_db",  # Chroma 0.4+ 自动持久化，persist() 已移除
)

3. 检索与生成

# langchain 1.x 已移除 RetrievalQA 链式接口；此处为 0.2 老写法，新写法见文末更新段
from langchain.chains import RetrievalQA
from langchain.llms import Ollama

# 初始化 LLM
llm = Ollama(model="llama3", temperature=0.3)

# 构建 RAG 链
qa_chain = RetrievalQA.from_chain_type(
    llm=llm,
    chain_type="stuff",
    retriever=vectorstore.as_retriever(search_kwargs={"k": 5}),
    return_source_documents=True,
)

# 提问
result = qa_chain({"query": "Go 语言中 context 的作用是什么？"})
print(result["result"])
for doc in result["source_documents"]:
    print(f"来源: {doc.metadata['source']}")

向量数据库选型

选哪个向量库，取决于数据规模、过滤需求和你已有的技术栈：

数据库类型特点适用场景
Milvus专用向量库分布式、高性能大规模生产环境
Chroma轻量向量库嵌入式、易用原型开发、小规模
Qdrant专用向量库Rust 实现、过滤强需要复杂过滤
PgvectorPostgreSQL 扩展SQL 生态已有 PG 基础设施
Elasticsearch搜索引擎全文+向量混合检索已有 ES 基础设施

选型口诀：原型/小数据用 Chroma；要复杂过滤选 Qdrant；已有 PostgreSQL 直接上 pgvector；大规模生产选 Milvus；要全文+向量混合且已有 ES 就用 Elasticsearch。先用 Chroma 跑通，再按规模迁移。

RAG 评估指标

RAG 必须把「检索得准不准」和「答得好不好」分开评。没有评测集，上线后质量退化都发现不了：

维度指标说明
检索质量Recall@KTop-K 检索结果中包含正确答案的比例
MRR平均倒数排名，正确答案排名越靠前分数越高
nDCG@K归一化折损累计增益，考虑相关性等级
生成质量Faithfulness答案是否忠实于检索上下文（无幻觉）
Answer Relevance答案是否与问题相关
Context Precision检索上下文的精准度
端到端Exact Match答案与标准答案完全匹配
F1 / ROUGE词级重叠度

常见陷阱与优化

下面 5 个是 RAG 上线最容易踩的坑，每个都给了症状和对策：

  • 陷阱1：Chunk 大小不合适——太小上下文不完整、语义被切断；太大噪声多、检索精准度下降。最佳实践：256~512 tokens，重叠 10~20%，按语义边界切分（段落/标题）。
  • 陷阱2：只用向量检索，忽略关键词——向量检索擅长语义匹配，但对专有名词、代码、数字不精准。必须用混合检索（Dense + Sparse），RRF 融合。
  • 陷阱3：不做 Reranking——向量检索的 Top-K 排序不够精准。必须用 Cross-Encoder Reranker 重新排序，从 Top-50 选 Top-5。
  • 陷阱4：忽略查询改写——用户的查询可能模糊、有指代、多轮对话。用 LLM 做查询改写：指代消解、补全上下文、拆分多跳问题。
  • 陷阱5：没有引用溯源——用户无法验证答案来源，降低信任度。必须在答案中标注 [1] [2] 引用，并提供可点击的来源链接。
常见陷阱症状对策
Chunk 大小不当语义被切断或噪声过多256~512 tokens，重叠 10~20%，按语义边界切分
只做向量检索专有名词/代码/数字匹配差混合检索 Dense + Sparse，RRF 融合
不做 RerankingTop-K 排序不准Cross-Encoder 从 Top-50 精选 Top-5
忽略查询改写模糊/指代/多跳查询召回差LLM 查询改写、指代消解、多跳分解
没有引用溯源用户无法验证、信任度低答案标注 [1][2]，附可点击来源

进阶技巧与 2026 工程实践

在跑通最小 RAG 之后，下面这些进阶手段是从 demo 走向生产的关键：

  • 混合检索：BM25 全文检索 + 向量检索一起上，取并集再做重排。
  • Query 重写：用 LLM 把用户查询改写成更适合检索的表达。
  • 重排序（Reranking）：用 Cross-Encoder 对检索结果再排一遍，把精度顶上去。
  • 多路召回：同时从多个知识源捞，结果合并。
  • 动态 chunk：按文档结构（段落、标题）动态切块，而不是死磕固定长度。

下面这段是 2026 年生产标配——向量 + BM25 混合召回，再用 Reranker 精排：

# 混合检索 + Rerank（2026 生产标配）
from langchain_community.retrievers import BM25Retriever
from langchain.retrievers.contextual_compression import ContextualCompressionRetriever
from langchain_community.document_compressors import CohereRerank

# 1. 向量检索
vector_retriever = vectorstore.as_retriever(search_kwargs={"k": 20})

# 2. BM25 关键词检索
bm25_retriever = BM25Retriever.from_documents(chunks)

# 3. 合并结果（Ensemble）
from langchain.retrievers import EnsembleRetriever
ensemble = EnsembleRetriever(
    retrievers=[vector_retriever, bm25_retriever],
    weights=[0.5, 0.5]
)

2026 RAG 生态趋势

  • langchain 1.x / LCEL：RetrievalQA 这类老链式接口已经移除，改用 create_retrieval_chain + create_stuff_documents_chain（或用 LangGraph 做图编排）；按需装 langchain-community、langchain-chroma、langchain-ollama 这些独立包。
  • GraphRAG：知识图谱 + 向量检索混着用（微软 GraphRAG、LightRAG 等）成了企业级 RAG 的新宠，专治多跳关系。
  • 混合检索 + 重排成标配：BM25 / 稀疏向量 + 稠密向量一起召回（比如 Qdrant 稀疏向量、bm25s），再上 Cohere / BGE 系 Reranker 精排。
  • 中文 embedding：BGE-M3（多语言、多粒度）和 Qwen3-Embedding 成了中文场景的默认选项，顶替早期 bge-small-zh 这种单粒度模型。
  • Agentic RAG：多轮「检索 → 反思 → 再检索」的链路，召回不够就自动改写查询或调工具，缓解一次性检索的召回瓶颈。
  • 评测先行：RAGAS、TruLens 这类框架把检索质量和生成质量拆开评，上线前先备好评测集已经成了工程纪律。
  • 本地推理：Ollama + vLLM / llama.cpp 撑起轻量私有化 RAG，Qwen3 系等开源模型是常见基座。

我做 RAG 踩过的最大的坑

说个真实的。2024 年我给公司搭了个客服 RAG，把 2000 篇产品文档全灌进去。第一版上线，测试的时候问啥都对，挺满意。结果上线第三天，客服就来找我了：用户问"你们退款多久到账"，RAG 回答了一堆"退款政策"，就是没说具体到账时间。

我去查，发现问题出在 chunk 切分上。退款到账时间那一段，被切到了 chunk 边界之外，检索的时候根本没被召回。这种坑你不测真实用户问题，光自己测根本发现不了。

最大的教训

RAG 上线前，一定要拿真实用户问题测，别拿你自己编的问题测。你自己编的问题，你知道答案在哪，检索当然准。真实用户的问题千奇百怪，测出来的才是真问题。

RAG 这两年怎么演进的

2024 年大家做 RAG 还停留在"切 chunk + 向量检索 + LLM"三板斧。到 2026 年，这套已经不够用了。我给你梳理下这两年的演进路线：

阶段做法问题
朴素 RAG（2023）切 chunk + 向量检索 + LLM检索不准、chunk 边界丢信息
进阶 RAG（2024）混合检索 + Rerank + 父文档检索多跳问题还是搞不定
Agentic RAG（2025）检索→反思→再检索，多轮调用复杂但成本高
GraphRAG（2026）知识图谱 + 向量检索混合多跳关系理解强，但建图成本高

我的判断是：大多数场景，进阶 RAG（混合检索 + Rerank）就够用了。GraphRAG 听着炫，但建知识图谱的成本很高，除非你真的有复杂的多跳关系问题，否则别上来就上 GraphRAG。

RAG 的成本结构

很多人以为 RAG 就是向量数据库的钱，其实不是。我给你算笔真实账（我们生产环境，日调用 1 万次，参考值）：

环节月度成本说明
Embedding 模型~500 元用 BGE-M3 本地跑，电费为主
向量数据库~800 元Qdrant 集群，100 万 chunk
LLM 生成~3000 元用 Qwen3.8，混合检索后每轮 ~3K token
Rerank 模型~300 元BGE Reranker，本地跑
存储和带宽~200 元云盘 + CDN
合计~4800 元/月比纯 API 调 GPT-4 便宜多了
省钱关键

RAG 最大的成本在 LLM 生成。优化办法：一是检索要准，别给 LLM 塞一堆不相关的文档浪费 token；二是简单问题用小模型，复杂问题才切大模型；三是缓存重复问题的答案。这三招下来成本能砍一半。

常见问题 FAQ

Q1：RAG 会取代微调吗？

不会，它们解决的是不同问题。RAG 是给模型加"外部知识"，微调是给模型加"特定能力或风格"。大多数企业场景 RAG 就够了，但如果你需要模型学会特定输出格式、特定术语习惯，微调还是得做。最好的方案是 RAG + 微调组合。

Q2：向量数据库选哪个？

小规模用 Chroma，简单省事；中等规模用 Qdrant 或 Milvus；大规模生产用 Pinecone（云服务，省心但贵）。2026 年了，别自己造向量数据库轮子，选个成熟的用就行。我们生产用的 Qdrant，开源免费，性能够。

Q3：RAG 回答不对怎么排查？

分两步查：先查检索——把 Query 拿去检索，看找回来的 chunk 对不对。如果找回来的就不对，问题在检索环节（chunk 切分、embedding 模型、检索参数）。如果找回来的对，但 LLM 答得不对，问题在生成环节（Prompt 约束、模型能力）。别一上来就怪 LLM。

Q4：文档更新了 RAG 怎么同步？

这是个工程问题。文档改了，对应的 chunk 要删了重新 embedding 再插。别偷懒全量重建，太贵。做增量索引：文档更新时，找到它对应的 chunk id，删掉旧的，插入新的。我们用 Git 仓库做文档源，文档一提交就自动触发增量索引更新。

Q5：RAG 能处理表格和图片吗？

2026 年可以了。表格的话，转成 markdown 或文本描述再切 chunk。图片的话，用多模态模型把图片内容描述成文字，再 embedding。但表格和图片的检索质量，还是比纯文本差一截。关键的表格内容，最好手动做结构化处理，别指望 RAG 自动搞定。
