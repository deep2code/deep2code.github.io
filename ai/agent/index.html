Agent 架构深度解析

什么是大模型 Agent

我最早接触 Agent 这个词是 2023 年底，当时觉得"不就是让大模型多调几个工具吗"。真在生产里踩过坑才回过味来：Agent 的本质是让大模型当"大脑"——它不一次性把答案吐给你，而是自己感知环境、推理决策、调用工具、看结果再想下一步，跑"思考→行动→观察→再思考"的循环，一步步逼近目标。跟你平时"问一句答一句"的 ChatGPT 最大的区别就在这：Agent 会自己决定下一步干嘛，而不是等你下指令。

一个完整的 Agent 系统包含四个核心组件：

  • 规划器（Planner）：将复杂目标拆解为可执行的子任务序列，决定下一步做什么
  • 记忆系统（Memory）：存储对话历史、中间结果、长期知识，支持上下文检索
  • 工具集（Tools）：Agent 可调用的外部能力（搜索、代码执行、API 调用、数据库查询等）
  • 执行器（Executor）：将 LLM 的决策转化为实际的工具调用，并将结果反馈给 LLM

Agent vs LLM vs RAG 的本质区别

很多人混淆这三者，它们的核心差异在于自主性和交互性：

维度纯 LLMRAGAgent
交互轮次1 轮（输入→输出）1 轮（检索→生成）多轮（思考→行动→观察循环）
外部工具无仅检索任意工具（搜索/代码/API/数据库）
决策能力无（直接回答）弱（固定检索流程）强（自主规划、选择、反思）
状态管理无状态无状态有状态（短期+长期记忆）
错误恢复无无可自我纠错、重试、换策略
延迟低（1 次 LLM 调用）中（检索+1 次 LLM）高（多次 LLM+工具调用）
成本低中高（Token 消耗大）
适用场景问答、翻译、摘要知识库问答复杂任务、自动化、数据分析

Agent 执行循环的底层机制

Agent 的核心是一个循环控制流，每一轮循环包含以下步骤：

  1. 感知（Perceive）：读取当前状态（用户输入、工具返回结果、记忆中的上下文）
  2. 推理（Reason）：LLM 分析当前状态，决定是继续调用工具还是给出最终答案
  3. 行动（Act）：如果需要工具，生成结构化的工具调用指令（Function Call）
  4. 观察（Observe）：执行工具调用，获取结果，追加到上下文中
  5. 检查（Check）：判断是否达到终止条件（任务完成、达到最大轮次、出错）

这个循环的关键设计点是终止条件。没有终止条件的 Agent 会陷入无限循环，消耗大量 Token。常见的终止策略包括：最大迭代次数（如 10 轮）、LLM 主动输出"最终答案"标记、工具返回特定的完成信号、超时机制。

Agent 循环的黄金法则：每一轮"思考→行动→观察"都是一次完整的 LLM 调用。Agent 越复杂，Token 成本和延迟越高——设计时必须预设硬性终止条件（最大轮次 + 超时），否则 Agent 会"跑飞"。

ReAct：推理与行动的协同

ReAct 范式原理

ReAct（Reasoning + Acting）是目前最主流的 Agent 范式，由 Google Research 在 2022 年提出。其核心思想是让 LLM 交替生成"推理轨迹（Thought）"和"行动（Action）"，而不是像 Chain-of-Thought 那样只推理不行动，也不是像传统工具调用那样只行动不推理。

ReAct 的每一步输出包含三个部分：

  • Thought：LLM 对当前状态的分析和推理（"我需要先搜索相关信息，然后..."）
  • Action：选择的工具及参数（"Search[查询关键词]"）
  • Observation：工具执行的结果（由环境返回，不是 LLM 生成）
sequenceDiagram participant U as 用户 participant L as LLM 大脑 participant T as 工具层 participant M as 记忆系统 U->L: 目标/问题 L->>L: Thought: 分析任务，决定策略 L->>T: Action: 调用工具(参数) T->>T: 执行工具 T-->>L: Observation: 返回结果 L->>M: 存储中间结果 L->>L: Thought: 评估结果，决定下一步 alt 需要更多信息 L->>T: Action: 调用另一个工具 T-->>L: Observation: 返回结果 else 任务完成 L->>U: Final Answer: 最终答案 end

ReAct 的工程实现

在工程实现中，ReAct 通常通过系统提示词（System Prompt）+ 工具定义 + 解析器三件套实现：

# ReAct Agent 核心循环（简化版）
def react_agent(user_input, tools, llm, max_steps=10):
    # 1. 构建系统提示词，描述 ReAct 格式
    system_prompt = """你是一个 ReAct Agent。每一步必须遵循以下格式：

Thought: 你对当前状态的分析
Action: 工具名(参数)
Observation: 工具返回结果（由系统填充）

当你认为任务完成时，输出：
Final Answer: 你的最终答案

可用工具：
{tool_descriptions}
"""
    
    # 2. 初始化上下文
    context = [
        {"role": "system", "content": system_prompt.format(
            tool_descriptions="\n".join([t.description for t in tools])
        )},
        {"role": "user", "content": user_input}
    ]
    
    # 3. ReAct 循环
    for step in range(max_steps):
        # 3.1 LLM 推理
        response = llm.chat(context)
        context.append({"role": "assistant", "content": response})
        
        # 3.2 解析输出
        if "Final Answer:" in response:
            return response.split("Final Answer:")[-1].strip()
        
        # 3.3 提取 Action
        action_match = re.search(r"Action:\s*(\w+)\((.*?)\)", response)
        if not action_match:
            # LLM 没有遵循格式，重试或报错
            context.append({"role": "user", 
                "content": "请严格按照 Thought/Action 格式输出"})
            continue
        
        tool_name, tool_args = action_match.groups()
        
        # 3.4 执行工具
        tool = next((t for t in tools if t.name == tool_name), None)
        if tool:
            result = tool.execute(tool_args)
        else:
            result = f"错误：工具 {tool_name} 不存在"
        
        # 3.5 将 Observation 加入上下文
        context.append({"role": "user", 
            "content": f"Observation: {result}"})
    
    return "达到最大迭代次数，任务未完成"

ReAct vs Function Calling

现代 LLM（GPT-4、Claude 3、Qwen 等）都内置了 Function Calling 能力，这与 ReAct 是什么关系？

Function Calling 是 ReAct 的"结构化版本"。传统 ReAct 依赖 LLM 输出自然语言格式的 Action，需要正则解析，容易出错。而 Function Calling 让 LLM 直接输出 JSON 格式的工具调用，由 API 层保证格式正确，解析更可靠。

但 Function Calling 只解决了"行动"的结构化，推理过程（Thought）仍然需要通过提示词引导。最佳实践是结合两者：用 Function Calling 做工具调用，用 System Prompt 引导 LLM 在调用工具前先输出推理过程（即使不展示给用户）。

规划架构：从单步到多步

Plan-and-Execute 架构

ReAct 是"走一步看一步"的反应式架构，适合简单任务。但对于复杂任务（如"调研 5 个竞品并生成对比报告"），ReAct 容易迷失方向，因为它没有全局规划。

Plan-and-Execute 架构将任务分为两个阶段：

  1. 规划阶段（Plan）：LLM 先将复杂目标拆解为有序的子任务列表（Plan）
  2. 执行阶段（Execute）：逐个执行子任务，每个子任务可以是一个 ReAct 循环或直接工具调用
flowchart LR A[复杂目标] --> B[规划器 Planner] B --> C[子任务1] B --> D[子任务2] B --> E[子任务3] B --> F[...] C --> G[执行器 Executor] D --> G E --> G G --> H{需要重新规划?} H -->|是| B H -->|否| I[汇总结果] I --> J[最终输出] style B fill:#e1bee7 style G fill:#bbdefb style J fill:#c8e6c9

Plan-and-Execute 的优势是全局视野，规划器可以看到整个任务的全貌，避免 ReAct 中常见的"短视"问题。但它也有缺点：规划可能不准确，执行中发现计划不可行时需要动态重规划（Re-planning）。

Reflection：自我反思机制

Reflection 是让 Agent 具备"自我批判"能力的机制。在执行完一个或多个步骤后，让 LLM 回顾之前的行动，评估是否有效，如果发现问题则调整策略。

典型的 Reflection 流程：

  1. Agent 执行 N 步后，暂停
  2. 将完整的行动轨迹（Thought/Action/Observation）传给 LLM
  3. LLM 评估："之前的策略有效吗？有没有更好的方法？"
  4. 如果发现问题，生成修正建议，调整后续行动

Reflection 显著提升了 Agent 在复杂推理任务上的成功率，但代价是额外的 LLM 调用和延迟。工程上通常设置反思触发条件：连续失败 N 次、工具返回错误、达到检查点时才触发反思，而不是每步都反思。

工具调用（Tool Use）深度解析

Function Calling 底层原理

Function Calling 不是 LLM "真的"调用了函数，而是 LLM 生成了一个符合特定格式的 JSON 对象，表示它想调用某个函数及参数。实际的函数执行由应用层代码完成，然后将结果传回给 LLM。

整个流程是：

  1. 开发者在 API 请求中定义工具列表（名称、描述、参数 JSON Schema）
  2. LLM 根据用户输入，决定是否需要调用工具
  3. 如果需要，LLM 输出 tool_calls 字段（包含工具名和参数）
  4. 应用层解析 tool_calls，执行对应的函数
  5. 将函数结果以 tool 角色的消息传回 LLM
  6. LLM 根据工具结果生成最终回答
# OpenAI Function Calling 完整流程
from openai import OpenAI

client = OpenAI()

# 1. 定义工具
tools = [
    {
        "type": "function",
        "function": {
            "name": "get_weather",
            "description": "获取指定城市的天气信息",
            "parameters": {
                "type": "object",
                "properties": {
                    "city": {"type": "string", "description": "城市名称"},
                    "unit": {"type": "string", "enum": ["celsius", "fahrenheit"]}
                },
                "required": ["city"]
            }
        }
    }
]

# 2. 第一次请求：LLM 决定是否调用工具
response = client.chat.completions.create(
    model="gpt-4o",
    messages=[{"role": "user", "content": "北京今天天气怎么样？"}],
    tools=tools
)

message = response.choices[0].message

# 3. 如果 LLM 决定调用工具
if message.tool_calls:
    for tool_call in message.tool_calls:
        # 4. 执行工具
        if tool_call.function.name == "get_weather":
            args = json.loads(tool_call.function.arguments)
            result = get_weather(args["city"], args.get("unit", "celsius"))
            
            # 5. 将结果传回 LLM
            messages = [
                {"role": "user", "content": "北京今天天气怎么样？"},
                message,
                {
                    "role": "tool",
                    "tool_call_id": tool_call.id,
                    "content": json.dumps(result)
                }
            ]
            
            # 6. 第二次请求：LLM 根据工具结果生成回答
            final_response = client.chat.completions.create(
                model="gpt-4o",
                messages=messages,
                tools=tools
            )
            print(final_response.choices[0].message.content)

工具设计的最佳实践

工具设计直接影响 Agent 的成功率。以下是经过验证的设计原则：

1. 工具粒度要适中

  • 太粗（如"完成任务"）：LLM 无法有效使用，等于没有工具
  • 太细（如"打开文件"、"读取一行"）：需要多轮调用，延迟高，容易出错
  • 适中：一个工具完成一个有意义的子任务（如"搜索文档"、"执行 SQL"）

2. 工具描述要精确

  • 描述中说明工具的用途、适用场景、不适用场景
  • 参数描述要包含示例和约束（如"日期格式 YYYY-MM-DD"）
  • 避免歧义："搜索" vs "在企业知识库中搜索文档，返回 Top 5 相关片段"

3. 参数 Schema 要严格

  • 使用 enum 限制可选值，避免 LLM 生成无效参数
  • 使用 required 标记必填参数
  • 使用 minimum/maximum 限制数值范围
  • 嵌套对象要完整定义，不能省略

4. 错误信息要可操作

  • 工具执行失败时，返回的错误信息应该告诉 LLM "为什么失败"和"怎么修正"
  • 坏例子："执行失败"
  • 好例子："SQL 执行失败：表 'users' 不存在。可用表：customers, orders, products。请修正表名后重试。"

工具选择与路由策略

当工具数量很多时（如 50+ 个工具），LLM 的工具选择准确率会下降。常见的优化策略：

  • 工具分类（Tool Categorization）：将工具按功能分组，LLM 先选类别再选具体工具
  • 动态工具加载（Dynamic Tool Loading）：根据用户意图，只加载相关的工具子集，减少 LLM 的选择负担
  • 工具检索（Tool Retrieval）：用向量检索从工具库中找到最相关的 Top-K 工具，再传给 LLM
  • 工具调用前置（Tool Call Pre-check）：在 LLM 调用工具前，用规则或小模型验证参数合法性

记忆系统设计

记忆的分类与架构

Agent 的记忆系统借鉴了认知科学的人类记忆模型，分为三类：

记忆类型类比人类记忆存储内容实现方式生命周期

记忆检索策略

长期记忆的核心挑战是检索相关性。不是所有历史记忆都对当前任务有用，需要精准检索：

  • 语义检索（Semantic Retrieval）：用 Embedding 模型将当前查询和记忆都向量化，检索 Top-K 最相似的记忆
  • 时间衰减（Time Decay）：近期的记忆权重更高，远期记忆逐渐降低权重
  • 重要性评分（Importance Scoring）：让 LLM 给每条记忆打重要性分数，检索时优先返回高重要性记忆
  • 混合检索（Hybrid Retrieval）：结合语义检索和关键词检索（BM25），兼顾语义匹配和精确匹配
  • 记忆摘要（Memory Summarization）：当记忆过多时，用 LLM 将多条相关记忆摘要为一条，减少检索噪声

Context Window 管理

LLM 的上下文窗口有限（如 128K Token），但 Agent 的多轮交互很容易超出。Context Window 管理策略：

  • 滑动窗口（Sliding Window）：只保留最近 N 轮对话，丢弃更早的内容
  • 摘要压缩（Summarization）：将早期对话压缩为摘要，保留关键信息
  • 分层上下文（Hierarchical Context）：系统提示词 + 最近对话 + 检索到的相关记忆，分层组织
  • Token 计数与预算：实时计算 Token 用量，在超出前自动触发压缩
# Context Window 管理示例
class ContextManager:
    def __init__(self, max_tokens=100000, llm=None):
        self.max_tokens = max_tokens
        self.llm = llm
        self.messages = []
        self.summary = ""  # 早期对话的摘要
    
    def add_message(self, role, content):
        self.messages.append({"role": role, "content": content})
        self._maybe_compress()
    
    def _maybe_compress(self):
        current_tokens = self._count_tokens()
        if current_tokens > self.max_tokens * 0.8:
            # 保留最近 5 轮，将更早的内容摘要
            keep_recent = self.messages[-10:]  # 5 轮 = 10 条消息
            to_summarize = self.messages[:-10]
            
            if to_summarize and self.llm:
                text = "\n".join([f"{m['role']}: {m['content']}" 
                                  for m in to_summarize])
                self.summary = self.llm.chat([
                    {"role": "system", "content": "请将以下对话摘要为关键信息要点"},
                    {"role": "user", "content": text}
                ])
            
            self.messages = keep_recent
    
    def get_context(self):
        context = []
        if self.summary:
            context.append({"role": "system", 
                "content": f"[历史对话摘要] {self.summary}"})
        context.extend(self.messages)
        return context

Multi-Agent 协作

Multi-Agent 协作模式

当任务复杂度超过单个 Agent 的能力时，需要多个 Agent 协作。常见的协作模式：

1. 流水线模式（Pipeline）

每个 Agent 负责一个阶段，输出作为下一个 Agent 的输入。例如：研究 Agent → 写作 Agent → 审校 Agent。

2. 层级模式（Hierarchical）

一个"管理者 Agent"负责规划和分配任务，多个"工人 Agent"负责执行。管理者将子任务分发给合适的工人，汇总结果。

3. 辩论模式（Debate）

多个 Agent 从不同角度分析问题，互相质疑，最终达成共识。适合需要多角度思考的决策任务。

4. 自主协作模式（Autonomous Collaboration）

Agent 之间可以自由通信，自主决定何时协作、与谁协作。最灵活但也最难控制。

多 Agent 的核心挑战不是"能不能协作"，而是"怎么收敛"：Agent 越多，通信开销越大、错误传播越广。能用单 Agent 解决的问题，不要拆成多 Agent——多 Agent 是复杂度的最后手段，不是第一选择。

Agent 间通信机制

Multi-Agent 系统的核心难点是通信与协调。常见的通信机制：

  • 消息传递（Message Passing）：Agent 之间通过结构化消息通信，类似 Actor 模型
  • 共享内存（Shared Memory）：所有 Agent 共享一个记忆空间，通过读写共享状态协作
  • 黑板模式（Blackboard）：一个中央"黑板"存储中间结果，Agent 从黑板读取信息并写入结果
  • 群聊模式（Group Chat）：所有 Agent 在一个"群聊"中发言，每个 Agent 可以看到其他 Agent 的消息

Multi-Agent 框架对比

  • LangGraph：基于图的 Agent 编排框架，将 Agent 流程建模为有向图，支持循环、条件分支、人工介入。生产就绪度高，是目前最推荐的框架。
  • AutoGen：微软开源的 Multi-Agent 框架，主打"对话式"Agent 协作，支持群聊模式。灵活性高但生产级功能（如持久化、监控）较弱。
  • CrewAI：主打"角色化"Agent，每个 Agent 有明确的角色、目标、工具。上手简单，但复杂流程的表达能力有限。
  • LlamaIndex：以 RAG 为核心，Agent 能力是扩展。适合以数据检索为核心的 Agent 场景。

评估与可观测性

Agent 评估指标

Agent 的评估比纯 LLM 复杂得多，因为它涉及多轮交互和工具调用。核心评估维度：

  • 任务成功率（Task Success Rate）：Agent 是否最终完成了任务目标。这是最核心的指标。
  • 工具调用准确率（Tool Call Accuracy）：LLM 选择的工具和参数是否正确。错误的工具调用会导致后续所有步骤偏离。
  • 平均步骤数（Average Steps）：完成任务平均需要多少轮交互。步骤越多，延迟和成本越高。
  • Token 消耗（Token Usage）：完成任务的总 Token 用量，直接关联成本。
  • 端到端延迟（End-to-End Latency）：从用户输入到最终输出的总时间。
  • 错误恢复能力（Error Recovery）：遇到工具错误或异常时，Agent 能否自我纠正并继续。

Agent 可观测性

Agent 是一个"黑盒"系统，调试困难。生产级 Agent 必须有完善的可观测性：

  • Trace 追踪：记录每一步的完整信息（输入、输出、工具调用、延迟、Token 用量），类似分布式追踪。推荐 LangSmith、Langfuse、OpenTelemetry。
  • 中间状态可视化：能够查看 Agent 在每一步的 Thought、Action、Observation，理解它的决策过程。
  • 成本监控：按任务、按用户、按工具维度统计 Token 消耗和费用。
  • 异常告警：当 Agent 陷入循环、连续失败、Token 消耗异常时触发告警。

Agent 性能优化

延迟优化

Agent 的延迟是用户体验的最大痛点。一个 10 步的 Agent 可能需要 30 秒以上。优化策略：

  • 流式输出（Streaming）：LLM 的每一步输出都流式返回给用户，让用户看到"Agent 正在思考"的过程，降低感知延迟。
  • 并行工具调用（Parallel Tool Calls）：当多个工具调用之间没有依赖时，让 LLM 同时发起多个工具调用，并行执行。GPT-4 支持一次输出多个 tool_calls。
  • 模型分级（Model Routing）：简单的推理步骤用小模型（如 GPT-4o-mini），复杂的决策步骤用大模型（如 GPT-4o）。平均可降低 50% 延迟和成本。
  • 工具结果缓存（Tool Result Caching）：相同参数的工具调用结果缓存起来，避免重复执行。特别是搜索、数据库查询等耗时操作。
  • 提前终止（Early Termination）：当 Agent 已经获得足够信息时，允许它跳过剩余步骤直接给出答案。

成本优化

Agent 的 Token 消耗通常是纯 LLM 问答的 5-10 倍。成本控制策略：

  • Prompt 精简：系统提示词和工具描述尽量简洁，每轮都要发送的内容要严格控制长度。
  • 上下文压缩：及时压缩历史对话，避免无关上下文占用 Token。
  • 工具输出截断：工具返回的结果可能很长（如搜索结果、SQL 查询结果），需要截断或摘要后再传给 LLM。
  • 最大步数限制：设置合理的最大迭代次数，防止 Agent 陷入无限循环烧钱。
  • 小模型路由：如上所述，简单步骤用便宜的模型。

8 大常见陷阱与最佳实践

陷阱 1：没有终止条件，Agent 陷入无限循环

现象：Agent 反复调用同一个工具，或在两个工具之间来回切换，永远不输出最终答案。

根因：提示词中没有明确的"完成"信号，或 LLM 无法判断任务何时完成。

解决方案：

  • 设置硬性最大迭代次数（如 10-15 步），超时强制终止
  • 在系统提示词中明确说明"当你认为任务完成时，必须输出 Final Answer"
  • 检测重复模式：如果连续 3 步调用相同工具且参数相似，强制终止或换策略
  • 添加超时机制（如 60 秒未完成则终止）

陷阱 2：工具描述模糊，LLM 选错工具或参数

现象：LLM 调用了错误的工具，或参数格式不对，导致工具执行失败。

根因：工具描述不够精确，LLM 无法理解工具的适用场景和参数要求。

解决方案：

  • 工具描述包含：用途、适用场景、参数示例、返回值格式
  • 参数使用 enum 限制可选值，使用 required 标记必填
  • 工具数量过多时，先做意图分类，只加载相关工具子集
  • 在工具执行前做参数校验，返回明确的错误信息引导 LLM 修正

陷阱 3：上下文溢出，早期关键信息丢失

现象：多轮交互后，Agent 忘记了用户最初的需求或之前的关键发现。

根因：Context Window 被填满，滑动窗口策略丢弃了重要的早期信息。

解决方案：

  • 实现智能摘要：不是简单丢弃早期内容，而是用 LLM 摘要关键信息
  • 将重要的中间结果写入长期记忆，需要时检索回来
  • 在系统提示词中持续保留"原始任务目标"，每轮都提醒 Agent
  • 监控 Token 用量，在接近上限时提前触发压缩

陷阱 4：工具返回结果过长，浪费 Token 且干扰推理

现象：搜索工具返回 10 篇长文，SQL 查询返回 1000 行数据，全部塞进上下文，Token 爆炸且 LLM 无法聚焦。

根因：没有对工具输出做后处理，直接将原始结果传给 LLM。

解决方案：

  • 工具层做截断：搜索结果只返回 Top 3 摘要，SQL 结果只返回前 50 行
  • 用小模型对工具输出做预摘要，提取关键信息后再传给主 LLM
  • 分页机制：如果结果太多，让 Agent 主动请求"下一页"而不是一次性返回
  • 在工具描述中说明返回值的格式和长度限制

陷阱 5：错误处理缺失，一次失败导致整个任务崩溃

现象：某个工具调用失败（API 超时、网络错误），Agent 直接输出错误信息或卡住，不会重试或换方案。

根因：没有在提示词中引导 Agent 处理错误，工具返回的错误信息不可操作。

解决方案：

  • 工具返回的错误信息要包含：错误原因、可能的修正方法、可用的替代方案
  • 在系统提示词中明确："如果工具调用失败，分析原因后重试或尝试其他工具"
  • 实现自动重试机制：对幂等的工具调用（如搜索）自动重试 2-3 次
  • 设置降级策略：如果核心工具不可用，用备用工具或简化方案完成任务

陷阱 6：Multi-Agent 通信混乱，任务重复或遗漏

现象：多个 Agent 做了重复的工作，或者某个子任务没有 Agent 负责，最终结果不完整。

根因：没有明确的任务分配机制和通信协议，Agent 之间缺乏协调。

解决方案：

  • 使用明确的协作模式（流水线/层级/辩论），不要让 Agent 自由发挥
  • 层级模式中，管理者 Agent 负责明确分配任务，每个子任务有唯一负责人
  • 使用共享状态（如任务看板），所有 Agent 可以看到哪些任务已完成、哪些在进行
  • 设置通信协议：Agent 之间的消息必须有明确的接收者、类型、内容

陷阱 7：安全边界缺失，Agent 执行危险操作

现象：Agent 被提示注入攻击，执行了删除数据、发送邮件、转账等危险操作。

根因：没有对 Agent 的工具调用做权限控制和安全审查。

解决方案：

  • 工具分级：只读工具（搜索、查询）自动执行，写操作（删除、发送）需要人工确认
  • 沙箱执行：代码执行工具必须在隔离的沙箱中运行，限制网络和文件系统访问
  • 输入过滤：对用户输入和工具返回做提示注入检测，过滤可疑内容
  • 操作审计：记录所有工具调用，支持事后追溯和回滚
  • 最小权限原则：Agent 只能访问完成任务所必需的工具和数据

陷阱 8：评估缺失，上线后才发现 Agent 不靠谱

现象：开发时感觉 Agent 表现不错，上线后发现成功率低、经常出错、成本超预期。

根因：没有建立系统化的评估体系，只靠人工抽样测试。

解决方案：

  • 构建评估数据集：覆盖典型任务、边界情况、错误场景，至少 50-100 个测试用例
  • 自动化评估：每次代码变更后自动运行评估集，跟踪成功率、步骤数、Token 消耗的变化
  • 线上监控：记录线上所有 Agent 运行的 Trace，定期抽样人工评估
  • A/B 测试：新策略先小流量上线，对比关键指标后再全量
  • 建立基线：用纯 LLM（不使用 Agent）作为基线，证明 Agent 确实提升了效果

2026 Agent 开发趋势

  • 原生 Agent 模型：GPT-5、Claude 4、Gemini 3 等模型原生支持多步工具调用和长程推理，不再需要复杂的 ReAct 提示词工程。模型内置"思考模式"，可以进行深度推理后再行动。
  • Agent 操作系统：出现专门的 Agent 运行时环境，提供进程管理、内存管理、工具调度、安全沙箱等基础设施，类似"Agent 时代的操作系统"。
  • MCP（Model Context Protocol）：Anthropic 提出的 MCP 协议成为工具接入的标准，工具一次开发、跨平台使用，类似 Agent 时代的"USB 接口"。
  • 人机协作（Human-in-the-loop）：Agent 不是完全自主，而是在关键决策点请求人工确认。人工审核 + Agent 执行成为企业级应用的标配模式。
  • Agent 市场与标准化：出现 Agent 交易市场，开发者可以发布和售卖 Agent 技能。Agent 之间的互操作标准逐渐成熟。
  • 端侧 Agent：小模型（7B-14B）在端侧设备上运行 Agent，隐私数据不出设备，云端大模型处理复杂任务，形成"端云协同"架构。
  • Agent 安全与合规：随着 Agent 执行真实操作，安全审计、权限管理、合规性成为企业选型的核心考量，相关法规和标准逐步出台。
# 2026 生产级 Agent 最小可行架构（LangGraph + MCP）
from langgraph.graph import StateGraph, END
from langgraph.prebuilt import ToolNode
from langchain_openai import ChatOpenAI
from langchain_core.messages import HumanMessage

# 1. 定义工具（通过 MCP 协议接入，一次开发跨平台使用）
tools = [
    web_search_tool,    # 网页搜索
    code_executor,      # 代码执行（沙箱）
    sql_query_tool,     # 数据库查询（只读）
    file_reader,        # 文件读取
]

# 2. 定义 Agent 状态
class AgentState(TypedDict):
    messages: list
    next: str

# 3. 定义 Agent 节点
def agent_node(state):
    """LLM 推理节点：决定调用工具或给出答案"""
    llm = ChatOpenAI(model="gpt-4o", temperature=0)
    llm_with_tools = llm.bind_tools(tools)
    response = llm_with_tools.invoke(state["messages"])
    return {"messages": [response]}

def should_continue(state):
    """条件边：判断是否继续调用工具"""
    last_message = state["messages"][-1]
    if last_message.tool_calls:
        return "tools"
    return END

# 4. 构建图
workflow = StateGraph(AgentState)
workflow.add_node("agent", agent_node)
workflow.add_node("tools", ToolNode(tools))

workflow.set_entry_point("agent")
workflow.add_conditional_edges("agent", should_continue)
workflow.add_edge("tools", "agent")

# 5. 编译运行（带最大步数限制和检查点）
app = workflow.compile(
    checkpointer=MemorySaver(),  # 持久化中间状态
    interrupt_before=["tools"]   # 工具调用前人工确认（Human-in-the-loop）
)

result = app.invoke(
    {"messages": [HumanMessage(content="分析最近一季度的销售数据并生成报告")]},
    config={"recursion_limit": 25}  # 最大 25 步，防止无限循环
)

一个我踩过的 Agent 上线事故

去年我在公司搞了个"自动化周报 Agent"，本意是让它每天早上拉销售数据、跑 SQL、生成一段人话发到群里。demo 跑得很顺，上线第一天就出事了。

问题出在终止条件上。我们当时图省事，没设最大步数，只靠 LLM 自己判断"任务完成没"。那天凌晨 Agent 拉完数据觉得数字对不上，就开始反复查库、反复算，查一次往群里发一次，一早上发了 47 条，群里全是它自言自语的 Thought。更要命的是，每轮都带 2 万 token 的上下文，光那一夜就烧掉小两千块钱。

血的教训

Agent 不设硬终止条件，等于给模型一张无上限信用卡。最大步数、超时、单用户日预算，这三个必须在写第一行代码之前就钉死。

后来我们加了三道闸：单任务最多 15 步、单任务 60 秒超时、每个 API key 每天 token 用量封顶。改完之后它再没闹过事。这个故事我现在还常跟团队讲，因为太典型了——Agent 的坑从来不是"做不出来"，而是"做出来之后刹不住"。

真实的 Token 成本长什么样

很多人对 Agent 的成本没概念，我给个我们线上跑了三个月的真实数据（混合 GPT-4o 和 Qwen3，单位人民币，参考值）：

任务类型平均步数每轮 token单任务成本说明
简单问答（单跳）1 步~2K~0.01 元纯 LLM 调用，不调工具
查库+回答3-4 步~8K~0.15 元跑 SQL、看结果、组织语言
调研+写报告12-18 步~25K~2-4 元多轮搜索、读网页、交叉验证

看出来没？Agent 的成本几乎是纯问答的 10 倍起步，复杂任务能到 100 倍。所以我做项目的第一反应永远是：这事儿真需要 Agent 吗？能不能用"一次检索+一次 LLM"解决？能就别上 ReAct 循环。

我的选型直觉

如果一个任务能用固定 pipeline 写死，就别让 LLM 临场决策。固定 pipeline 可预测、可压测、成本可控；Agent 灵活但贵且飘。80% 的业务场景，pipeline 就够了。

Do / Don't 清单

干了两年 Agent 项目，我总结了一份给团队的 checklist，直接抄：

该做的

  • 先想清楚终止条件再写 Agent：最大步数、超时、完成信号，一个都不能少
  • 工具描述写得像给新人写文档：什么时候用、参数怎么填、返回长什么样、失败了怎么办
  • 工具返回结果必须截断：搜索结果只给 Top3 摘要，SQL 结果只给前 50 行，别把原文糊给 LLM
  • 只读工具放开跑，写操作要人确认：删数据、发邮件、转账这类，必须 human-in-the-loop
  • 上 Trace 工具：Langfuse 或 LangSmith，不然出问题你连它哪步想歪了都不知道

别做的

  • 别让 Agent 处理确定性任务：格式化、算数、正则匹配，用代码写，LLM 只管理解和生成
  • 别一上来就多 Agent：单 Agent 能搞定就别拆，多 Agent 的通信成本和 token 消耗是指数级涨的
  • 别信 demo 的效果：demo 跑 10 次成功 8 次，上线跑 1000 次就会出各种你想不到的 case
  • 别把用户原始输入直接拼进 Prompt：提示注入不是闹着玩的，尤其 Agent 能调工具的时候

常见问题 FAQ

Q1：Agent 和普通的 Function Calling 到底差在哪？

说白了，Function Calling 是"LLM 决定调一个工具，你调完把结果给它，它给答案"，整个流程你写死。Agent 是"LLM 自己决定下一步干啥、要不要再调工具、什么时候收工"，流程是它临场定的。前者可控便宜，后者灵活但贵。我的建议是：先用 Function Calling 把流程写死，跑顺了再考虑要不要让 Agent 自己规划。

Q2：MCP 协议到底要不要现在就上？

MCP（Model Context Protocol）是 Anthropic 推的，本质是给工具定了个标准接口。好处是一次开发，Claude、Cursor、各种 Agent 框架都能接。但 2026 年生态还不算特别成熟，老工具接 MCP 层还得写个 wrapper。我的做法是：新工具直接按 MCP 写，老工具先包一层，不追求一步到位。

Q3：Agent 上线后效果忽好忽坏怎么办？

这几乎是必然的。先别改 Prompt，先上 Trace 看它到底哪步飘了。我见过太多团队一上来就疯狂调 Prompt 玄学，其实问题往往是某个工具返回了脏数据、或者某一步上下文被挤掉了。先观测，再归因，最后才是调参。

Q4：开源模型做 Agent 靠谱吗？

2026 年比前两年靠谱多了。Qwen3.8、GLM-5.2 这些在工具调用榜单上已经不输闭源，而且自己部署能省一大笔钱。但有个坑：开源模型的 Function Calling 格式偶尔会不稳定，偶尔多打个引号少个逗号，你得在工具调用层加个 JSON 修复（比如调一次小模型帮你 parse）。闭源 API 在这方面省心不少。

Q5：一个简单任务，Agent 比直接调 LLM 贵多少？

看复杂度。简单单跳任务，Agent 跟直接调 LLM 差不多；但只要进入多轮循环，成本就是几倍到几十倍。我自己的体感是：一个平均 5 步的 Agent，单次成本大概是纯问答的 8 到 10 倍。所以能用固定流程的，真别硬上 Agent。
