Coding Agent Prompt

🏷️ Coding Agent

为什么 Prompt Engineering 重要

Coding Agent（AI 编程助手）的输出质量，很大程度上取决于你给它的 Prompt（指令）质量。同一个任务，好的 Prompt 能生成高质量、可直接使用的代码；差的 Prompt 可能生成有 bug、不符合规范、需要大量修改的代码。掌握 Prompt Engineering 是高效使用 Coding Agent 的核心技能。

flowchart LR A[Prompt 质量] --> B[输出质量] A --> C[迭代次数] A --> D[Token 消耗] A --> E[开发效率] B --> F[代码质量] C --> F D --> F E --> F G[好的 Prompt] --> G1[一次生成可用代码] G --> G2[符合项目规范] G --> G3[边界条件完善] H[差的 Prompt] --> H1[多次迭代修改] H --> H2[不符合规范] H --> H3[遗漏边界条件]

核心结论：Prompt 质量是 Coding Agent 输出质量的第一杠杆。同一个任务，好 Prompt 一次成型，差 Prompt 要反复返工——这正是本文要系统解决的问题。

核心原则

1. 清晰明确（Clarity）

说清楚你要什么，不要模糊。AI 不会猜你的心思，模糊的指令会得到模糊的结果。

差的 Prompt好的 Prompt
"写个登录功能""实现用户登录 API：POST /api/auth/login，接收 email 和 password，验证后返回 JWT 令牌（有效期 7 天），使用 bcrypt 验证密码，包含输入验证和错误处理"
"优化这个函数""优化这个函数的性能：当前时间复杂度 O(n²)，目标 O(n log n)，保持功能不变，添加性能测试"
"修复 bug""修复这个函数在空数组输入时返回 undefined 的 bug，添加边界条件检查和单元测试"

2. 提供上下文（Context）

AI 不知道你的项目背景、技术栈、编码规范。提供充足的上下文，AI 才能生成符合要求的代码。

  • 项目背景：这是什么项目？目标用户是谁？
  • 技术栈：语言、框架、库、版本
  • 编码规范：命名风格、注释要求、错误处理方式
  • 相关代码：@引用相关文件、函数、类型定义
  • 约束条件：性能要求、兼容性要求、安全要求
  • 示例参考：提供类似的代码作为参考

3. 指定约束（Constraints）

明确告诉 AI 不能做什么、必须做什么，避免生成不符合要求的代码。

# 约束示例
- 使用 TypeScript strict 模式，禁止 any 类型
- 所有函数必须有 JSDoc 注释
- 错误处理使用 try-catch，不使用 throw new Error('error')
- 异步代码使用 async/await，不使用 .then() 链
- 数据库查询必须有超时（10秒）
- 所有外部 API 调用必须有重试机制（3次，指数退避）
- 敏感数据（密码、token）必须加密存储
- 不要修改现有的公共 API
- 不要引入新的依赖（除非必要并说明理由）

4. 结构化输出（Structure）

要求 AI 按特定结构输出，方便审查和使用。

# 结构化输出示例
"实现用户注册功能，按以下结构输出：

## 1. 实现思路
（简要说明实现方案和关键决策）

## 2. 代码实现
（完整的代码，包含注释）

## 3. 测试用例
（单元测试，覆盖正常和异常场景）

## 4. 注意事项
（边界条件、安全考虑、性能影响）"

5. 迭代优化（Iteration）

第一次结果通常不是最优的。通过迭代追问，逐步优化代码质量。

# 迭代示例
第1轮："实现用户登录功能"
第2轮："添加输入验证和错误处理"
第3轮："优化性能，添加数据库连接池"
第4轮："添加单元测试，覆盖率达到 80%"
第5轮："代码审查，修复安全漏洞"
第6轮："重构，提取公共方法，降低复杂度"

上下文管理技巧

精准引用文件

# 差：引用整个目录（上下文太大，AI 抓不住重点）
"看看 src/ 目录，实现登录功能"

# 好：精准引用相关文件
"参考以下文件实现登录功能：
- @src/models/user.py（用户模型，包含 User 类和密码哈希方法）
- @src/utils/jwt.py（JWT 工具，包含 encode_token 和 decode_token）
- @src/api/base.py（基础 API 类，包含统一响应格式和错误处理）
- @tests/api/test_auth.py（现有认证测试，参考测试风格）"

提供代码片段

# 直接粘贴关键代码，比让 AI 自己找更高效
"现有的用户模型如下：
\`\`\`python
class User(Base):
    __tablename__ = 'users'
    id = Column(Integer, primary_key=True)
    email = Column(String(255), unique=True, nullable=False)
    password_hash = Column(String(255), nullable=False)
    created_at = Column(DateTime, default=datetime.utcnow)
    
    def set_password(self, password):
        self.password_hash = bcrypt.hashpw(password.encode(), bcrypt.gensalt())
    
    def check_password(self, password):
        return bcrypt.checkpw(password.encode(), self.password_hash.encode())
\`\`\`

基于这个模型，实现登录 API。"

@router.post('/register')
async def register(data: RegisterSchema, db: Session = Depends(get_db)):
    # 检查邮箱是否已注册

    if existing:

避免上下文噪音

  • 不要引用无关文件（如 node_modules、dist、build 目录）
  • 不要粘贴大段无关代码
  • 不要重复描述同一个需求
  • 及时清除过时的上下文（/clear、/compact）
  • 大任务拆成小对话，每个对话聚焦一个子任务

任务拆解技巧

为什么要拆解

  • 降低复杂度：大任务一次生成容易出错，拆解后每个子任务更简单
  • 便于验证：每步完成后可以验证，及时发现问题
  • 节省 Token：避免反复加载大上下文
  • 提高质量：聚焦的任务生成质量更高

如何拆解

# 大任务："实现一个完整的用户管理系统"

# 拆解为子任务：
第1轮：设计数据模型和数据库表结构
第2轮：实现用户注册 API（含输入验证、密码哈希）
第3轮：实现用户登录 API（含 JWT 令牌）
第4轮：实现用户信息查询和更新 API
第5轮：实现用户删除和注销 API
第6轮：实现权限管理（角色、权限中间件）
第7轮：编写单元测试（覆盖所有 API）
第8轮：编写集成测试
第9轮：性能优化（数据库索引、查询优化）
第10轮：安全审计和修复

# 每个子任务的 Prompt：
"基于之前实现的用户模型，实现 [子任务]。
要求：
- 遵循项目的代码风格（参考 @[相关文件]）
- 包含输入验证和错误处理
- 添加单元测试
- 先分析，再实现，最后测试"

拆解模式

模式说明示例
按功能模块每个功能一个子任务注册、登录、查询、更新、删除
按架构层每层一个子任务模型层 → 数据访问层 → 业务逻辑层 → API 层
按依赖顺序先基础后高级工具函数 → 基础组件 → 业务组件 → 页面
按测试驱动先测试后实现写测试 → 运行（失败）→ 实现 → 运行（通过）
按复杂度先简单后复杂简单 CRUD → 复杂业务逻辑 → 性能优化

常见反模式

1. 模糊指令

# ❌ 差
"写个好的登录功能"
"优化一下代码"
"修复这个问题"

# ✅ 好
"实现 JWT 登录 API，包含输入验证、密码哈希、错误处理，返回有效期7天的令牌"
"优化这个函数的时间复杂度从 O(n²) 到 O(n)，保持功能不变，添加性能测试"
"修复空数组输入时返回 undefined 的 bug，添加边界条件检查和回归测试"

2. 任务过大

# ❌ 差
"用 React + Node.js + MongoDB 写一个完整的电商网站，包含商品管理、购物车、支付、订单、用户系统"

# ✅ 好
拆解为 10+ 个子任务，逐个实现

3. 缺少上下文

# ❌ 差
"修复这个 bug"（没有说明是什么 bug、错误信息、相关代码）

# ✅ 好
"修复登录接口 500 错误：
错误信息：TypeError: Cannot read property 'password' of undefined
相关文件：@src/api/auth.js 第 42 行
复现：发送空 body 的 POST 请求到 /api/login
期望：返回 400 错误，提示缺少 email 和 password"

4. 矛盾的约束

# ❌ 差
"用纯 JavaScript 实现，使用 TypeScript 的类型系统"
"不引入新依赖，使用 lodash 的 debounce 函数"

# ✅ 好
明确选择一个方向，或说明权衡
"用 TypeScript 实现，strict 模式"
"不引入新依赖，自己实现 debounce 函数（参考 lodash 的实现）"

5. 过度指定实现细节

# ❌ 差（限制了 AI 的发挥空间）
"写一个函数，第一行定义变量 a=0，第二行循环 i 从 0 到 n，第三行 a += i，第四行返回 a"

# ✅ 好（指定目标和约束，让 AI 选择实现方式）
"写一个计算 1 到 n 之和的函数，时间复杂度 O(1)，包含输入验证（n 必须为正整数）"

6. 盲目信任输出

# ❌ 差
AI 生成代码后直接合并到主分支

# ✅ 好
1. 审查代码（Diff 视图逐行检查）
2. 运行测试（单元测试 + 集成测试）
3. 手动测试关键路径
4. 安全审查（有无漏洞）
5. 性能检查（有无性能问题）
6. 合并到独立分支，Code Review 后再合并

各工具 Prompt 技巧

Claude Code

  • 写好 CLAUDE.md：项目规范文件，Claude Code 启动时自动读取
  • 使用 @引用：@path/to/file 引用文件，@folder/ 引用目录
  • 分步指令："先分析，再实现，最后测试"，Claude 会按步骤执行
  • 要求验证："实现后运行测试确保通过"，Claude 会自动运行测试
  • 利用 MCP：连接数据库、GitHub、API 等，让 Claude 访问真实数据
  • /compact：上下文快满时压缩历史，释放空间
  • 模型选择：日常用 Sonnet，复杂任务切换 Opus

Cursor

  • .cursorrules：项目规则文件，定义编码规范和命令
  • Tab 补全：写好注释和函数签名，Tab 补全质量更高
  • Cmd+K 内联编辑：选中代码后用自然语言编辑
  • Cmd+L Chat：复杂任务用 Chat，@引用文件和代码
  • Cmd+I Composer：多文件任务用 Composer Agent 模式
  • 代码库索引：大项目中 @codebase 搜索整个代码库
  • 多模型切换：根据任务复杂度选择合适模型

GitHub Copilot

  • 注释驱动：写清晰的注释，Copilot 生成更准确的代码
  • 打开相关文件：Copilot 参考打开的文件的代码风格
  • Copilot Chat：复杂任务用 Chat，比行内补全更强大
  • Agent 模式：多文件任务用 Agent 模式
  • .github/copilot-instructions.md：项目级指令
  • 快捷键：Tab 接受、Esc 拒绝、Alt+] 切换建议
  • 测试驱动：先写测试，让 Copilot 生成通过测试的代码

Aider

  • /add 添加文件：添加相关文件到对话，提供上下文
  • Git 分支：在独立分支上工作，随时可以 /undo 回滚
  • --auto-test：配置自动测试，AI 会根据测试结果修复
  • /diff 审查：每次修改后查看差异
  • 仓库地图：大项目中自动生成代码库地图
  • 模型选择：简单任务用快速模型，复杂任务用强模型
  • 本地模型：敏感代码用 Ollama 本地模型

高级技巧

角色设定

# 让 AI 扮演特定角色，输出更专业
"你是一个有 10 年经验的全栈架构师，擅长高并发系统设计。
请审查这个系统的架构设计，重点关注：
1. 可扩展性（能否支持 10 倍流量增长）
2. 可用性（单点故障、降级策略）
3. 数据一致性（分布式事务、最终一致性）
4. 性能瓶颈（数据库、缓存、消息队列）
5. 安全风险（认证、授权、数据加密）

给出具体的改进建议和优先级排序。"

Prompt 质量检查清单

在发送 Prompt 之前，检查以下各项：

  1. 目标明确：我清楚地说明了要做什么吗？
  2. 上下文充足：AI 有足够的信息理解任务吗？（技术栈、相关代码、约束）
  3. 约束清晰：我说明了不能做什么、必须做什么吗？
  4. 任务大小合适：这个任务是否需要拆解为更小的子任务？
  5. 输出格式：我说明了期望的输出格式吗？（代码、测试、文档、分析）
  6. 验证方式：我说明了如何验证结果吗？（测试、运行命令）
  7. 避免模糊：有没有"好的"、"优化一下"、"修复问题"这类模糊词？
  8. 避免矛盾：有没有相互矛盾的约束？

总结

Coding Agent Prompt Engineering 的核心要点：

  • 清晰明确：说清楚要什么，不要模糊
  • 提供上下文：技术栈、相关代码、约束条件
  • 指定约束：编码规范、性能要求、安全要求
  • 拆解任务：大任务拆成小步骤，逐步验证
  • 结构化输出：要求按特定格式输出，方便审查
  • 迭代优化：第一次结果不是最优，持续追问优化
  • 审查验证：AI 生成的代码必须人工审查和测试
  • 利用工具特性：每个工具有自己的 Prompt 技巧和最佳实践

记住：Garbage in, garbage out。好的 Prompt 是高效使用 Coding Agent 的关键。

我见过的最差 Prompt 和最好的 Prompt

说个真实对比。有次团队新来的同学用 Claude Code，写出来的代码一塌糊涂。我看了他的 Prompt，就一句话："帮我写个用户登录接口"。

这能写出好代码才怪了。技术栈没说、数据库没说、鉴权方式没说、要不要验证码没说、错误码怎么定没说。AI 只能自己瞎猜，猜出来的东西当然不对。

我给他改了一版 Prompt，效果天差地别。同样的任务，好的 Prompt 长这样：

任务：实现用户登录接口

技术栈：Go 1.22 + gin + PostgreSQL + JWT
数据库：users 表已存在，字段为 id, email, password_hash, created_at
鉴权：登录成功返回 JWT access_token（2h）+ refresh_token（7d）
密码校验：用 bcrypt，cost=10
错误处理：
  - 邮箱未注册返回 401，message: "invalid credentials"
  - 密码错误返回 401，message: "invalid credentials"
  - 参数校验失败返回 400
其他要求：
  - 不要写 SQL，用 gorm
  - 加单元测试，覆盖成功和失败两种情况
  - 日志用 zap，记录 email 和耗时

看出来了吧？差的 Prompt 是"帮我搞一下"，好的 Prompt 是把你脑子里的需求全部倒出来。AI 不是你肚里的蛔虫，你说得越清楚，它干得越对。

我的 Prompt 模板

我每次写 Prompt 都套这个结构：任务是什么、技术栈是什么、输入输出是什么、有什么约束、怎么验证。五样东西齐了，出来的东西基本不会跑偏。

Prompt 长短跟成本的关系

很多人不知道，你给 AI 的 Prompt 越长，每次对话都要重新发一遍，token 成本是累积的。我算过一笔账：

Prompt 长度每轮 token10 轮对话成本效果
一句话（~50 token）~50 + 输出~0.001 元跑偏率 80%
中等（~500 token）~500 + 输出~0.01 元跑偏率 30%
详细（~2000 token）~2000 + 输出~0.05 元跑偏率 5%
太啰嗦（~8000 token）~8000 + 输出~0.3 元跑偏率反而升，因为重点被淹没

这就是个 U 型曲线。太短了 AI 瞎猜，太长了重点被淹没。我自己的经验是：详细但不啰嗦，500 到 2000 token 是甜区。把关键信息写清楚，废话别写。

怎么追问才能越改越好

AI 第一次给的东西很少是完美的，追问技巧很重要。我见过很多人追问就是"不对，再改改"，这没用。

好的追问是具体的：不是"不对"，而是"错误处理那块，密码错误和邮箱未注册应该返回不同的 message，你现在都是一样的"。AI 不是人，它听不懂模糊的批评，你得指到具体的点上。

差的追问好的追问
"不对，重写""错误处理里，邮箱未注册和密码错误要区分返回 message"
"这个不好""这个函数太长了，超过 50 行，拆成小函数"
"优化一下""数据库查询那里加个索引，现在是全表扫描"
"不够优雅""这里可以用泛型替代 interface，具体我说下需求"
别在同一个会话里改太多轮

同一个会话改了 10 轮以上，上下文就开始混乱了，AI 会忘了最开始的需求。超过 8 轮，新开个会话，把当前状态摘要一下再继续。比在一个超长会话里硬改效果好得多。

常见问题 FAQ

Q1：Prompt 越长越好吗？

不是。太长了重点会被淹没，AI 反而抓不住你真正要什么。我的经验是 500 到 2000 token 最甜。把关键信息写清楚就行，别把整个项目文档都贴进去。

Q2：我该把整个文件都贴给 AI 吗？

看情况。改小功能贴相关函数就行；大重构才贴整个文件甚至整个模块。贴太多浪费 token 还干扰它，贴太少它看不懂上下文。先用工具的 /add 或 @ 引用文件，比你手动复制粘贴强。

Q3：为什么我跟 AI 说"按我们的规范来"它还是不按？

因为它不知道你们的规范是什么。"按规范来"对 AI 来说是一句空话。你要么把规范写进项目的 CLAUDE.md / AGENTS.md，要么直接在 Prompt 里把规范点列出来。别假设 AI 知道你们公司的规矩。

Q4：同一个 Prompt 换个模型效果差很多吗？

差不少。复杂任务上，Claude 和 GPT 可能给出完全不同的方向。我的做法是：重要任务先用一个模型出初版，再换个模型 review 一遍，经常能发现盲区。不同模型的"思维方式"真的不一样。

Q5：怎么判断一个 Prompt 好不好？

看跑偏率。同一个 Prompt 让 AI 跑三次，三次结果都差不多且符合你的预期，就是好 Prompt；每次跑出来都不一样，说明 Prompt 不够明确。我自己调 Prompt 的标准就是：跑三次，稳定性高的才算过。
