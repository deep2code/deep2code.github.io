大模型服务化的工程约束

🏷️ 大模型

把大模型接进后端系统，难点几乎不在「怎么调通接口」，而在一组与普通无状态服务完全不同的约束：一次请求的开销由两段性质相反的计算组成、延迟不是一个数字而是三个、超时后不能简单重放、限额是多维度的、模型输出本身是不可信输入。本篇只写服务化这一层，检索增强、Agent、微调、提示词工程在文末给站内指向。

推理分两段：prefill 与 decode 压的不是同一种资源

一次生成在推理引擎里被切成两段。prefill 把整段输入（系统提示词、历史对话、检索到的上下文、本轮问题）一次性做前向计算，产出第一个输出 token，同时把每一层的键值状态写进 KV cache。decode 之后逐个 token 迭代，每产出一个 token 都要把已有的 KV cache 重新读一遍。

两段的资源画像几乎相反：prefill 是计算密集，输入越长算得越久，但算力利用率高，适合拼批；decode 每步计算量很小，却要搬运与上下文长度成正比的数据，瓶颈落在显存带宽上。结论是首 token 延迟和吐字速度是两条独立曲线：输入变长只抬高前者，并发变高主要拖慢后者。平均成一个「响应时间」，等于同时丢掉两边的可观测性。

上下文长度、KV cache 与并发是一组互斥资源

长上下文贵在哪里？不是权重——权重固定常驻。贵的是 KV cache，占用大致与上下文 token 数乘以并发请求数成正比（层数、头数、数值精度只是系数）。显存减掉权重后剩下的那块，就是所有在飞请求共享的缓存预算。于是有了那个必定困惑的现象：窗口调长，模型能力没变，最大并发却掉了；反过来把并发拉高，吐字速度先变慢，然后才开始排队。

这里要纠正一条流传很广的说法：「窗口支持很长，就可以放心把资料全塞进去」。窗口是上限不是预算：填满窗口意味着 prefill 变慢、缓存占用变大、有效并发下降、输入侧计费上升，而模型对长上下文中间段的利用率通常明显低于首尾。把检索到的二十段文档整体塞进去，常比精选三段更差也更贵。

另一个后果是字段顺序会影响成本：前缀缓存按「从头开始的最长公共前缀」命中，稳定内容（系统提示词、工具定义、少样本示例）必须排在最前，变动内容排在后面。在系统提示词里塞一个当前时间，等于把整段前缀缓存全部作废。

压力来源先恶化的指标根因可观测信号正确的第一手段

上下文与并发同时增长请求开始被拒或排队KV cache 预算耗尽出现显存不足或调度器主动降低批量给单请求设上下文硬上限，按上下文长度分池

延迟要拆成三个指标，流式改变的是感知而不是耗时

只看「响应时间」会误导所有决策，必须拆成三个：首 token 时间（含排队与 prefill）、每输出 token 时间（反映 decode 速度）、总时长（近似等于前者加上每 token 时间乘以输出长度）。总时长里输出长度是主导项，不设 max_tokens 比任何调参都更能把延迟拖垮。

流式输出常被当成延迟优化，这是误解：它一个 token 都不会缩短总耗时，改变的只是感知延迟。副作用有两个：连接持续有数据，传统读超时永远不触发，必须额外设「相邻 token 间隔上限」与「总时长硬上限」；重试变得可见，用户已看到半段内容，换个答案重来就是内容跳变。

指标定义主要受什么支配有效手段常见误判
首 token 时间请求发出到收到第一个输出 token排队时长、输入长度、前缀缓存命中缩短输入、提高缓存命中、限制排队深度误以为换更快的模型就能解决，其实大头常在排队
每输出 token 时间相邻输出 token 的平均间隔批内并发序列数、上下文长度、显存带宽控制批量上限、按上下文长度分池误以为是网络慢，去优化客户端缓冲
总时长首 token 时间加上吐完全部输出的时间输出 token 数量，其次是吐字速度设 max_tokens、约束输出格式、拆分任务误以为流式输出降低了总时长

吞吐与批处理：连续批处理提高的是谁的收益

批处理的主线只有一条：不要让槽位空转。静态批要求一批一起进、一起出，而各请求输出长度天差地别，短的早早结束却必须等最长的那个。连续批处理（迭代级调度）把调度粒度降到每一步解码之后：完成的立刻退出，排队的立刻补进来，利用率和总吞吐显著提升。

代价要说清楚：吞吐收益由批内请求共同分摊，单请求延迟通常变差。批内序列越多，每步 decode 搬运的缓存越多，吐字越慢。更隐蔽的是 prefill 与 decode 抢同一块资源：一个超长输入插进来做 prefill，正在吐字的请求会卡一下，这正是分块 prefill 与两段分离部署出现的原因。

还有一条常见错误：用 QPS 给 LLM 服务做容量规划。同样 QPS 下输入输出长度变几倍，负载就差几倍。容量单位应该是每秒输出 token 数加上最大并发序列数，压测必须固定长度分布。

策略调度粒度吞吐单请求延迟什么场景会失效
静态批凑满固定批量再开始中等受最慢请求拖累，方差大输出长度差异大时槽位空转严重；低峰期凑批等待反而增加延迟
连续批处理每步解码后重新调度高随批内并发上升而变差长输入请求插入时打断正在吐字的请求；缓存预算耗尽时退化为排队
分块 prefill把长输入切块与解码交错高且更平稳长输入请求自身首 token 时间略增块过小会增加调度开销，收益被吃掉

超时、重试与幂等：LLM 调用不能简单重放

常规重试建立在两个前提上：失败的调用没有产生成本，重放能得到同一结果。LLM 把两条都打破了：温度不为零时同一输入两次输出本就不同；更关键的是即使客户端断开，服务端已完成的 prefill 和已产出的 token 都真实消耗算力并且计费。于是「超时就重试」的效果是成本翻倍、用户先后看到两个答案、限额紧张时还会推进重试风暴。

幂等键要由业务定义，而不是指望服务端。可用组合是业务实体标识 + 提示词版本 + 模型版本（必要时加输入摘要）。换提示词或换模型自然产生新键——那确实是一次新的生成；用户重复点击则命中同一键，直接返回已落库结果。落库时给该键建唯一索引，重试天然收敛。

吐字中途断开不能简单重放已产生，且不可退必须新建键能接受截断就保留部分结果并标记不完整，否则作为新的一次生成并双份计费
 
# 一次可控的流式调用：三段超时 + 幂等键 + 部分输出的成本埋点
import time, uuid, json, httpx

CONNECT_TIMEOUT = 2.0    # 建连超时：网络与 DNS 问题应该秒级暴露，不要和生成时间混在一起
TTFT_BUDGET     = 8.0    # 首 token 预算：超了说明在排队或 prefill 过重，和吐字速度无关
IDLE_BUDGET     = 5.0    # 相邻 token 间隔上限：流式下唯一能识别"中途卡死"的超时
TOTAL_BUDGET    = 60.0   # 总时长硬上限：防止超长输出把上游连接池和线程全部占住

def stream_once(entity_id: str, prompt_version: str, model: str, messages: list) -> dict:
    # 幂等键 = 业务实体 + 提示词版本 + 模型版本。换提示词或换模型就是换实现，
    # 必须产生新键；用户重复点击则命中同一键，直接返回已落库结果。
    idem = f"{entity_id}:{prompt_version}:{model}"
    if (hit := result_store.get(idem)) is not None:
        return hit

    start = time.monotonic()
    first_at = None
    last_at = start
    parts = []
    usage = {"input_tokens": 0, "output_tokens": 0, "cached_tokens": 0}

    try:
        with httpx.stream(
            "POST", "https://api.example.com/v1/chat/completions",
            # read 超时在流式下的语义是"两次数据之间的间隔"，正好用作 idle 超时
            timeout=httpx.Timeout(connect=CONNECT_TIMEOUT, read=IDLE_BUDGET, write=5.0, pool=2.0),
            headers={"Idempotency-Key": idem},
            json={"model": model, "messages": messages, "stream": True,
                  "max_tokens": 1024,            # 必须设：输出长度直接决定总时长和费用
                  "stream_options": {"include_usage": True}},
        ) as resp:
            resp.raise_for_status()
            for line in resp.iter_lines():
                if not line.startswith("data: "):
                    continue
                payload = line[6:]
                if payload == "[DONE]":
                    break
                evt = json.loads(payload)
                if evt.get("usage"):
                    usage.update(evt["usage"])   # 用量事件通常在最后一帧，别提前 break 掉
                delta = evt["choices"][0]["delta"].get("content")
                if not delta:
                    continue
                now = time.monotonic()
                if first_at is None:
                    first_at = now
                    if first_at - start > TTFT_BUDGET:
                        raise TimeoutError("ttft_exceeded")
                last_at = now
                parts.append(delta)
                if now - start > TOTAL_BUDGET:
                    raise TimeoutError("total_exceeded")   # 主动断开，已产出部分仍然计费
    finally:
        # 无论成功失败都上报：断开不会退费，不埋点等于这部分成本永久失踪
        metrics.observe("llm_ttft_seconds", (first_at - start) if first_at else None,
                        tags={"model": model, "prompt_version": prompt_version})
        metrics.observe("llm_tpot_seconds",
                        ((last_at - first_at) / max(len(parts) - 1, 1)) if first_at else None,
                        tags={"model": model, "prompt_version": prompt_version})
        metrics.incr("llm_output_tokens_total", usage["output_tokens"],
                     tags={"model": model, "prompt_version": prompt_version})

    out = {"text": "".join(parts), "usage": usage,
           "prompt_version": prompt_version, "model": model, "truncated": False}
    result_store.put(idem, out)   # 落库时把 idem 建唯一索引，重试天然收敛到同一结果
    return out

限流与配额是三个维度，排队优于重试

限额至少同时存在三种：请求数、token 数、并发数。谁先被打满取决于流量形状——短请求先撞请求数，长上下文先撞 token 数，长输出的流式请求先撞并发。只按请求数限流，另外两个维度毫无防护。

客户端侧必须做本地三维配额：发出前按预估输入 token 加 max_tokens 预扣，结束后用真实用量回填。限额类错误本身也消耗配额和连接，靠指数退避去吃掉它只会让过载的上游更过载。正确形态是有界队列加最大排队时长，队满立刻失败。

限额维度先被打满的流量形状观测信号本地防护撞墙时的错误做法
请求数大量短提示词的高频调用请求速率贴住上限，token 速率还很低按请求数令牌桶，合并批量请求把单次批量拆成更多小请求
token 数少量长上下文请求token 速率贴顶，请求速率不高预扣额度：输入估算加上 max_tokens只统计输出 token，忽略输入侧占用
并发数长输出的流式会话在飞请求数贴顶，排队时长陡增信号量限制在飞请求，超出即排队提高客户端连接池，把压力全推给上游

提示词与模型版本是需要版本化的制品

换提示词、换模型、调温度、改 max_tokens，本质都是换实现。但它们通常活在代码之外——配置中心、数据库、运营后台，于是丢掉了评审、灰度、回滚以及与请求日志的对应关系。质量退化时最常见的窘境是没人说得清当时用的是哪一版提示词。

最低要求四条：每次调用记录提示词版本与模型版本并随结果落库；提示词文本进版本库，或至少进不可变存储并以内容哈希标识；变更按流量比例灰度；守护指标越界能自动回滚。还有一点容易忽略——供应商的模型别名会静默指向新版本，调用时应固定到具体版本号。

模型输出不可信：校验、兜底与执行边界

这条最容易被轻视、后果也最严重。模型输出必须当作不可信的外部输入，走四道关：能否解析、是否符合结构约束（一定要禁止多余字段，否则模型自创的字段会被静默忽略）、字段值是否落在白名单枚举内、业务规则是否成立。

❌
执行边界：这几件事绝对不做

模型输出绝不能直接当代码执行，也绝不能拼进 SQL、shell 命令、文件路径或反序列化入口。工具调用要用代码里写死的语句模板加参数化传值，工具集合与参数取值域用枚举限制，权限靠最小化的下游凭证兜住——而不是在提示词里写一句「不要做危险操作」。提示词不是安全边界。

兜底还有个流行的错误答案：「解析失败就让模型自己再修一次」。这条路把延迟和成本放大一倍以上，成功率还不稳定，失败样本也被顺手丢掉。正确做法是降级到确定性分支，同时把原始输出存进样本库——这是后续改提示词与结构约束唯一可靠的依据。

# 模型输出一律当作不可信外部输入：解析 -> 结构 -> 白名单 -> 业务规则，四道关
import json
from jsonschema import Draft202012Validator, ValidationError

SCHEMA = {
    "type": "object",
    "additionalProperties": False,   # 多出字段直接失败，否则模型自创字段会被静默忽略
    "required": ["intent", "days", "limit"],
    "properties": {
        # 意图和表名一律用枚举，绝不接受自由文本再去拼接
        "intent": {"enum": ["query_order", "query_refund"]},
        "days":   {"type": "integer", "minimum": 1, "maximum": 90},
        "limit":  {"type": "integer", "minimum": 1, "maximum": 200},
    },
}
VALIDATOR = Draft202012Validator(SCHEMA)

# SQL 模板由代码写死，模型只能选择用哪一条、以及填受约束的参数值
SQL = {
    "query_order":  "SELECT id, amount, status FROM orders  "
                    "WHERE user_id = %s AND created_at > NOW() - INTERVAL %s DAY LIMIT %s",
    "query_refund": "SELECT id, amount, reason FROM refunds "
                    "WHERE user_id = %s AND created_at > NOW() - INTERVAL %s DAY LIMIT %s",
}

def handle(model_text: str, user_id: int, cur) -> dict:
    try:
        obj = json.loads(model_text)
        VALIDATOR.validate(obj)
    except (json.JSONDecodeError, ValidationError) as e:

        sample_store.save(model_text, reason=type(e).__name__)
        return deterministic_fallback(user_id)

    cur.execute(SQL[obj["intent"]], (user_id, obj["days"], obj["limit"]))
    rows = cur.fetchall()
    # 第四道关：业务规则。模型可能给出"合法但不该做"的组合
    if obj["intent"] == "query_refund" and not user_has_scope(user_id, "refund:read"):
        return deny("scope_missing")   # 权限判定永远在代码里，不在提示词里
    return {"rows": rows, "intent": obj["intent"]}

成本可观测、评估回归与多模型降级

按 token 计费意味着成本是业务指标而不是基础设施指标，必须在调用处埋点，维度至少包含：模型与具体版本、提示词版本、租户或业务线、输入与输出 token 数、命中缓存的输入 token 数、是否降级。少了业务线维度，账单只剩一个总数。

评估的难点是没有确定性断言：同一输入两次输出不同，断言式测试直接失效。下面几种手段成本与可信度不同，通常组合使用。有个动作必须先做：先测噪声，再设阈值——同一输入多次采样的分数本身有方差，回归阈值必须大于这个区间，否则天天误报。

手段检出什么问题成本可信度适用阶段
金标集加自动指标结构错误、关键字段缺失、明显偏离低，可进流水线每次跑高但覆盖窄提交与合并前的强制门禁
模型评分器表达质量、是否答非所问中，本身也消耗 token中，评分器自身会漂移，需要固定版本提示词与模型变更的离线对比
人工抽检事实错误、语气与合规问题高，无法规模化最高灰度期间按比例抽样
影子双跑新旧版本在真实分布上的差异中，成本翻倍但不影响用户高，输入分布真实换模型或大改提示词之前

路由与降级要分层，核心原则是能不调模型就不调：缓存和规则先拦一道，分类抽取交给小模型，只把需要推理和长上下文的请求送到大模型。降级必须是显式状态：结果要带上由哪个模型、哪个版本产出、是否降级的标记，否则质量下滑时分不清是模型退化还是一直在走备用链路。

# 成本与延迟必须按 model / prompt_version / 业务线三个维度分开看，
# 聚合成一条总曲线时，换模型和换提示词造成的退化会互相抵消掉

# 1) 输出 token 速率：LLM 服务真正的容量单位，不是 QPS
sum by (model, prompt_version) (rate(llm_output_tokens_total[5m]))

# 2) 首 token 时间 P95：排队、prefill 过重、长上下文都先打在这条线上
histogram_quantile(0.95, sum by (le, model) (rate(llm_ttft_seconds_bucket[5m])))

# 3) 每 token 时间 P95：批内并发变高、KV cache 挤压显存带宽时先恶化
histogram_quantile(0.95, sum by (le, model) (rate(llm_tpot_seconds_bucket[5m])))

# 4) 缓存命中的输入 token 占比：提示词前缀被改动后，这个比例会立刻塌下去
sum(rate(llm_cached_input_tokens_total[30m])) / sum(rate(llm_input_tokens_total[30m]))

# 5) 结构校验失败率按提示词版本切分：灰度期间最灵敏的质量守护指标
sum by (prompt_version) (rate(llm_invalid_output_total[5m]))
  / sum by (prompt_version) (rate(llm_requests_total[5m]))

❌
最容易踩的坑
  • 只监控「平均响应时间」，首 token 时间和吐字速度的退化互相掩盖，两种故障都看不出来
  • 不设 max_tokens，一次异常的超长输出把总时长、连接池和账单同时打穿
  • 把当前时间、用户 ID 之类的易变内容写进系统提示词开头，前缀缓存整体失效，成本和首 token 时间一起变差
  • 按上下文窗口的上限去塞内容，并发在压测里直接掉一个档，还以为是模型服务不稳
  • 用 QPS 做容量规划，两次压测的输入输出长度分布不同，结论完全不可比
  • 超时后无条件重试，已经产生的 prefill 和输出照样计费，成本翻倍还可能让用户看到两个答案
  • 幂等键只用业务实体标识，换了提示词或模型之后仍然命中旧结果，灰度等于没做
  • 提示词存在配置中心里随手改，线上质量退化时查不到当时用的是哪一版
  • 模型别名不固定到具体版本，供应商静默升级后行为变化，排查方向全跑偏
  • 把模型输出直接拼进 SQL、shell 或当代码执行，指望提示词里的一句「不要做危险操作」当安全边界
  • 解析失败就让模型重试到成功，延迟与成本翻倍，失败样本还被丢掉，离线无法回归
  • 回归阈值设得比采样噪声还小，评测天天误报，最后整条门禁被所有人忽略
