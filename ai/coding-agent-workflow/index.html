Coding Agent 工作流

🏷️ Coding Agent

为什么需要最佳实践

Coding Agent（AI 编程助手）正在改变软件开发的方式。但工具本身不能保证高质量的输出——如何使用工具、建立什么样的工作流，才是决定效率和质量的关键。没有规范的使用方式，AI 可能引入 bug、安全漏洞、技术债务；有良好的工作流，AI 可以成为生产力倍增器。

flowchart LR A[Coding Agent 工作流] --> B[项目配置] A --> C[Git 工作流] A --> D[代码审查] A --> E[测试策略] A --> F[团队协作] A --> G[安全管理] A --> H[成本控制] B --> B1[规范文件] B --> B2[模型选择] B --> B3[MCP 配置] C --> C1[分支策略] C --> C2[提交规范] C --> C3[回滚机制] D --> D1[人工审查] D --> D2[AI 辅助审查] D --> D3[检查清单] E --> E1[测试驱动] E --> E2[AI 生成测试] E --> E3[覆盖率要求] F --> F1[团队规范] F --> F2[知识共享] F --> F3[培训] G --> G1[数据安全] G --> G2[代码安全] G --> G3[依赖安全] H --> H1[模型选择] H --> H2[用量监控] H --> H3[优化策略]

核心结论：工具决定上限，工作流决定下限。同样的 Agent，规范的分支/审查/测试工作流能让它成为倍增器；放任使用则会把 bug、安全漏洞和技术债务一起量产。

项目配置最佳实践

写好项目规范文件

几乎所有 Coding Agent 都支持项目级配置文件，这是提升 AI 表现的最有效手段。

工具配置文件位置
Claude CodeCLAUDE.md项目根目录 / 子目录

规范文件应包含

  1. 项目概述：项目是什么、技术栈、架构
  2. 编码规范：命名风格、注释要求、错误处理方式
  3. 架构约定：分层结构、设计模式、API 设计
  4. 常用命令：测试、构建、lint、迁移等命令
  5. 注意事项：不能修改的目录、不能提交的文件、安全要求
  6. 测试要求：覆盖率要求、测试框架、测试规范
  7. Git 工作流：分支命名、提交信息规范、PR 流程

多文件配置策略

# 根目录：全局规范
CLAUDE.md（项目概述、全局编码规范、常用命令）

# 子目录：局部规范（覆盖全局）
backend/CLAUDE.md（后端特定规范、Go 编码规范）
frontend/CLAUDE.md（前端特定规范、React 编码规范）
infra/CLAUDE.md（基础设施规范、Terraform 规范）

# 好处：
# - AI 在不同目录工作时自动应用对应规范
# - 避免根目录配置文件过长
# - 团队不同方向可以维护自己的规范

分支策略

# 核心原则：AI 的修改永远在独立分支上

# 推荐分支命名
feature/ai-login          # AI 实现的新功能
fix/ai-auth-bug           # AI 修复的 bug
refactor/ai-user-module   # AI 做的重构
chore/ai-deps-update      # AI 做的依赖更新

# 工作流
1. 从 main 创建 feature 分支
2. 在分支上使用 AI 开发
3. AI 自动提交（或人工审查后提交）
4. 完成后发起 PR
5. CI 运行（测试、lint、安全扫描）
6. 人工 Code Review
7. 合并到 main
8. 删除分支

# 禁止
# - 直接在 main 分支上使用 AI
# - AI 的修改未经审查直接合并
# - 一个分支包含多个不相关的 AI 任务

提交信息规范

# 使用 Conventional Commits 规范
# AI 生成的提交信息也应遵循

feat(auth): 添加 JWT 登录功能
- 实现 POST /api/auth/login
- 添加 bcrypt 密码验证
- 添加输入验证和错误处理
- 添加单元测试

fix(auth): 修复空数组输入时的崩溃
- 添加边界条件检查
- 添加回归测试

refactor(user): 提取用户服务公共方法
- 降低代码重复
- 保持 API 不变

# AI 生成提交信息的 Prompt
"根据当前 git diff，生成符合 Conventional Commits 规范的提交信息：
- 类型：feat/fix/refactor/docs/test/chore
- 范围：相关模块
- 标题：简洁描述（不超过 50 字符）
- 正文：详细说明变更内容和原因"

回滚机制

# AI 可能犯错，需要便捷的回滚机制

# Claude Code：/undo 撤销最后一次 AI 修改
# Aider：/undo 撤销最后一次提交（Git revert）
# Cursor：Cmd+Z 撤销，或 Git revert

# 最佳实践
1. AI 每次修改自动提交（小步提交）
2. 每次提交只包含一个逻辑变更
3. 提交信息清晰描述变更
4. 不满意时 git revert 单个提交
5. 大任务用独立分支，不满意直接删除分支

# 回滚命令
git log --oneline          # 查看提交历史
git revert <commit-hash>   # 撤销指定提交
git reset --hard HEAD~1    # 回退到上一个提交（危险，仅在本地分支）
git branch -D feature/ai-xxx  # 删除不满意的分支

代码审查最佳实践

人工审查不可省略

AI 生成的代码必须经过人工审查，这是不可妥协的原则。AI 会犯错、会幻觉、会遗漏边界条件、会引入安全漏洞。

代码审查检查清单

  1. 正确性：逻辑是否正确？有无 bug？边界条件是否处理？
  2. 安全性：有无 SQL 注入、XSS、CSRF、越权、敏感信息泄露？
  3. 性能：有无 N+1 查询、内存泄漏、O(n²) 复杂度、缺少索引？
  4. 代码质量：命名是否清晰？注释是否充分？复杂度是否合理？有无重复代码？
  5. 可维护性：是否易于扩展？耦合度是否合理？是否易于测试？
  6. 错误处理：异常是否处理？资源是否释放？错误信息是否友好？
  7. 测试覆盖：是否有测试？覆盖率是否足够？是否覆盖异常场景？
  8. 依赖管理：是否引入了不必要的新依赖？依赖版本是否安全？
  9. 规范符合：是否符合项目编码规范？是否符合架构约定？
  10. AI 幻觉检查：是否使用了不存在的 API、库、函数？是否编造了文档？

AI 辅助审查

# 可以用 AI 辅助审查，但不能替代人工审查

# 审查 Prompt
"审查以下代码变更（git diff）：
1. 找出所有潜在的 bug 和逻辑错误
2. 检查安全漏洞（OWASP Top 10）
3. 检查性能问题
4. 检查代码质量问题（命名、注释、复杂度、重复）
5. 检查是否符合项目编码规范（参考 CLAUDE.md）
6. 检查是否有 AI 幻觉（不存在的 API、库、函数）
7. 按严重程度排序（Critical > High > Medium > Low）
8. 每个问题给出：位置、问题描述、修复建议、代码示例

注意：只报告有把握的问题，不要误报。"

# 在 CI 中集成 AI 审查
# - PR 自动触发 AI 代码审查
# - AI 审查意见作为评论发布
# - 人工审查时参考 AI 意见
# - AI 审查不通过不阻塞合并（仅参考）
sequenceDiagram participant Dev as 开发者 participant Agent as Coding Agent participant CI as CI/CD participant AIRev as AI 审查 participant Human as 人工 Reviewer Dev->Agent: '描述任务（独立分支）' Agent->>Agent: '实现 + 自动提交' Agent->>Dev: '提交 PR + 变更摘要' Dev->>CI: '触发流水线' CI-->>AIRev: '推送 diff' AIRev-->>Human: '按严重度列出问题（仅参考）' CI-->>Human: '测试/lint/SAST 结果' Human->>Agent: '打回修改意见' Agent->>Dev: '修复并重新提交' Human->>Dev: '通过，合入 main'

分工原则：AI 负责"生成 + 初筛"，CI 负责"自动化闸门"，人工负责"最终决策"。AI 审查意见只作参考，绝不作为合并的唯一依据。

测试策略最佳实践

测试驱动开发（TDD）with AI

# AI 时代的 TDD 工作流

1. 写测试（人工或 AI 辅助）
   - 明确需求和验收标准
   - 编写测试用例（正常、边界、异常）
   - 运行测试，确认失败

2. AI 实现代码
   - "实现 [功能]，让以下测试通过：[测试代码]"
   - AI 运行测试，根据失败信息迭代修复
   - 直到所有测试通过

3. 人工审查和重构
   - 审查 AI 生成的实现
   - 重构优化（保持测试通过）
   - 补充测试（提高覆盖率）

# 好处
- 测试定义了明确的验收标准
- AI 有明确的目标（让测试通过）
- 测试保证了重构的安全性
- 覆盖率自然提高

AI 生成测试的最佳实践

  1. 先写测试框架：人工搭建测试结构，AI 填充具体用例
  2. 明确测试范围：告诉 AI 测什么、不测什么
  3. 要求覆盖异常场景：AI 倾向于只测正常流程，明确要求边界和异常
  4. 使用 Mock：外部依赖必须 Mock，不要让测试依赖真实环境
  5. 审查测试质量：AI 生成的测试可能有断言不足、测试重复、无意义测试
  6. 检查覆盖率：用覆盖率工具验证，不要只看 AI 说"覆盖了"
  7. 测试也要测试：故意破坏代码，确认测试能捕获问题（变异测试）

覆盖率要求

代码类型行覆盖率分支覆盖率说明
核心业务逻辑≥ 90%≥ 85%必须高覆盖
工具函数≥ 85%≥ 80%高覆盖
API 层≥ 80%≥ 70%中等覆盖
UI 组件≥ 70%≥ 60%快照+交互测试
配置/常量不要求不要求无需测试

团队协作最佳实践

团队统一规范

# 团队应统一的规范

1. 工具选择
   - 团队统一使用 1-2 个 Coding Agent（如 Cursor + Claude Code）
   - 避免每个人用不同工具，规范文件不兼容

2. 配置文件
   - 项目根目录统一维护 CLAUDE.md / .cursorrules
   - 纳入 Git 管理，团队共同维护
   - 定期更新，保持与实际一致

3. 使用规范
   - AI 的修改必须在独立分支
   - 必须经过 Code Review 才能合并
   - 必须有测试
   - 禁止直接在 main 分支使用 AI

4. 安全规范
   - 禁止将敏感信息（API Key、密码）粘贴到 AI
   - 敏感代码使用本地模型或自托管方案
   - 企业数据不发送到第三方 AI 服务

5. 成本管理
   - 统一购买团队/企业版
   - 监控用量，避免浪费
   - 选择合适的模型，不要一直用最强模型

知识共享

  • Prompt 库：团队共享高效的 Prompt 模板（新功能、Bug 修复、重构、审查、测试）
  • 最佳实践文档：记录团队的 AI 编程最佳实践和踩坑经验
  • 定期分享：每周/每月分享 AI 编程技巧和新工具
  • 代码示例库：收集 AI 生成的优质代码和反面案例
  • 培训新人：新人入职时培训 AI 编程规范和技巧

安全管理最佳实践

数据安全

  1. 禁止敏感信息：不要将 API Key、密码、密钥、个人信息粘贴到 AI
  2. 代码脱敏：分享代码前移除敏感信息（用占位符代替）
  3. 本地模型：敏感代码使用本地模型（Ollama、vLLM），数据不离开本地
  4. 自托管方案：企业使用 Continue.dev + vLLM 自托管，数据不离开内网
  5. 企业版：使用企业版（Copilot Business、Cursor Business），数据不用于训练
  6. 审计日志：开启审计日志，监控 AI 使用情况
  7. 数据保留策略：配置数据保留时间，定期清除历史

代码安全

  1. 安全审查：AI 生成的代码必须经过安全审查（SQL 注入、XSS、CSRF、越权）
  2. 依赖扫描：AI 引入的新依赖必须经过安全扫描（SCA）
  3. 秘密扫描：CI 中集成秘密扫描，防止 AI 不小心提交密钥
  4. SAST：静态应用安全测试，自动发现安全漏洞
  5. 安全 Prompt：在项目规范中明确安全要求（输入验证、输出编码、参数化查询）
  6. AI 幻觉检查：AI 可能使用不存在的或有漏洞的库/版本，必须验证

供应链安全

# AI 可能引入不安全的依赖，需要严格管理

1. 依赖白名单
   - 维护团队认可的依赖白名单
   - AI 引入新依赖必须经过审批
   - 优先使用流行、维护活跃的库

2. 版本锁定
   - 使用 lock 文件锁定依赖版本
   - 不要让 AI 使用 latest 或范围版本
   - 定期更新依赖（AI 可以辅助）

3. 安全扫描
   - CI 中集成 SCA 工具（Dependabot、Snyk、Trivy）
   - 发现漏洞自动通知
   - 高危漏洞必须修复才能合并

4. 许可证合规
   - 检查依赖许可证（GPL 等传染性许可证）
   - 避免许可证冲突

成本控制最佳实践

模型选择策略

任务类型推荐模型原因
行内补全快速小模型（GPT-mini、Sonnet、本地模型）延迟敏感，简单任务
代码生成（简单）中等模型（Sonnet、GPT 标准版）性价比高
代码生成（复杂）强模型（Opus、GPT 旗舰版）需要强推理能力
架构设计最强模型（Opus、GPT 旗舰版）需要深度思考
代码审查强模型需要发现细微问题
测试生成中等模型模式化任务
文档生成中等模型模式化任务
重构强模型需要理解全局

用量优化

  1. 及时压缩上下文：Claude Code /compact，避免历史对话占用大量 token
  2. 精准引用文件：只引用相关文件，不要 @整个目录
  3. 拆解大任务：大任务拆成小对话，每个对话聚焦一个子任务
  4. 避免重复：不要反复让 AI 做同样的事情，一次做好
  5. 本地模型：简单任务用本地模型，免费且隐私好
  6. 缓存利用：一些工具支持 prompt 缓存，重复使用相同上下文可省钱
  7. 监控用量：定期查看 API 用量和费用，设置预算告警

成本估算

# 个人开发者月度成本估算

# 方案 A：订阅制
- Cursor Pro: $20/月
- Claude Pro: $20/月
- 总计: $40/月（无限使用，适合重度用户）

# 方案 B：API 按量
- Claude Sonnet: $3/$15 per 1M tokens
- 假设每天 100K input + 20K output = 120K tokens/天
- 月度: 3.6M tokens ≈ $10-15/月
- 适合轻度/中度用户

# 方案 C：混合
- 日常用免费/本地模型
- 复杂任务用 API 按量
- 月度: $5-10/月
- 适合预算有限的用户

# 企业成本
- GitHub Copilot Business: $19/用户/月
- Cursor Business: $40/用户/月
- 自托管 Continue.dev + vLLM: 服务器成本（$100-500/月）
- 适合 10+ 人团队

效率提升技巧

工作流优化

  1. 标准化任务模板：为常见任务（新功能、Bug 修复、重构、审查）创建 Prompt 模板
  2. 快捷键熟练：熟练使用工具的快捷键，减少鼠标操作
  3. 多工具组合：Cursor 做日常编码 + Claude Code 做复杂任务 + Aider 做批量重构
  4. 批量处理：类似的任务批量处理，提高效率
  5. 自动化集成：将 AI 集成到 CI/CD（自动审查、自动测试、自动文档）
  6. 持续学习：关注新工具、新功能、新技巧，持续优化工作流

总结

Coding Agent 最佳实践的核心要点：

  • 项目配置：写好规范文件（CLAUDE.md / .cursorrules），这是提升 AI 表现的最有效手段
  • Git 工作流：AI 修改永远在独立分支，小步提交，便捷回滚
  • 代码审查：人工审查不可省略，使用检查清单，AI 辅助审查
  • 测试策略：TDD with AI，AI 生成测试需审查，覆盖率要求
  • 团队协作：统一规范，知识共享，培训新人
  • 安全管理：数据安全、代码安全、供应链安全，不可忽视
  • 成本控制：模型选择策略，用量优化，监控费用
  • 效率提升：标准化模板，多工具组合，自动化集成
  • 避免陷阱：盲目信任、任务过大、AI 幻觉、安全漏洞、技能退化

记住：AI 是工具，人是主导。好的工作流让 AI 成为生产力倍增器，差的工作流让 AI 成为麻烦制造者。

Git 工作流具体怎么落地

很多人说"AI 改代码放独立分支"，但具体怎么操作没说清楚。我们团队的标准流程是这样的：

  1. 从 main 拉一个 feature 分支，命名规范 ai/功能名-日期
  2. 在这个分支上让 AI 改代码，小步提交，每改完一个小功能就 commit
  3. 改完自己跑一遍测试，确保绿了再 push
  4. 提 PR，request review，reviewer 重点看 AI 生成的那部分
  5. review 通过后合回 main，分支删掉
千万别在 main 上直接让 AI 跑

有次有人图省事，直接在 main 上让 Claude Code 重构，结果改坏了一个核心模块，回滚花了一下午。从那以后我们规定：AI 永远在 feature 分支上跑，main 上不许直接调 AI。

常见问题 FAQ

Q1：团队推 AI 编码，新人老员工反应不一样怎么办？

正常。老员工会觉得"我自己写更快"，新人觉得"AI 帮我好多"。我的经验是别强推，让老员工自己试。有个老工程师一开始嗤之以鼻，后来用 AI 写了一周测试，发现省了他一半时间，自己就真香了。工具好不好，试了才知道。

Q2：AI 生成的代码没人愿意 review 怎么办？

这是个真问题。review AI 代码比 review 人写的代码累，因为你得搞懂它为啥这么写。我们的做法是：把 review AI 代码纳入工作量，不是额外负担。另外用 AI 辅助 review（让另一个 AI 先过一遍），人工只做最终把关。

Q3：怎么衡量 AI 到底帮了团队多少？

别看主观感受，看数据。需求交付周期、bug 率、测试覆盖率、开发者满意度，这四个指标对比着看。我们团队推 AI 前后的数据一摆，老板立刻就支持继续投入了。

Q4：要不要用 AI 做代码 review？

可以做第一道筛子，但别当最终把关。AI review 能帮你发现低级错误、安全漏洞、风格不一致，但业务逻辑对不对、边界情况考虑没考虑到，还得人来看。定位是"初级 review"，不是"终审"。

Q5：AI 编码会让团队技术能力退化吗？

短期会有人变懒，但长期看，如果工作流里强制人工 review 和测试，团队反而会变强——因为大家把省下来的时间花在了架构设计和复杂问题上，而不是重复劳动上。关键是你得把工作流设计成"AI 干杂活，人干难活"，而不是"AI 全包，人签字"。
