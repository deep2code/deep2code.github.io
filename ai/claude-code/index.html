Claude Code 简介

Claude Code 是 Anthropic 于 2024 年 10 月推出的 AI 编程助手，基于 Claude 3.5 Sonnet / Claude 4（Opus/Sonnet）模型。

flowchart LR A[终端输入] --> B[Claude Code CLI] B --> C[Claude 模型 1M 上下文] C --> D[工具调用] D --> E[Read 读文件] D --> F[Edit 编辑文件] D --> G[Bash 执行命令] D --> H[Web 搜索] D --> I[MCP 工具] E --> J[迭代执行] F --> J G --> J H --> J I --> J J --> K[输出结果]

定位：Claude Code 是"CLI 形态的最强 Agent"——靠 1M 上下文 + 原生工具调用 + MCP 接外部世界，把"读文件 → 改文件 → 跑命令 → 验证"串成自主闭环。

核心特性

  • 最强编码能力：SWE-bench 87.6%，业界领先
  • 1M token 上下文：可加载整个代码库，理解全局架构
  • 自主 Agent 模式：规划任务、调用工具、迭代执行、验证结果
  • CLAUDE.md 项目规范：项目级配置文件，让 AI 理解编码规范和架构约定
  • MCP 支持：Model Context Protocol，可连接任意工具和数据源
  • Git 原生集成：自动创建分支、提交代码、生成 PR 描述
  • 记忆系统：跨会话记忆用户偏好和项目上下文
  • 安全设计：命令执行前确认、敏感操作警告、沙箱隔离

CLAUDE.md 项目规范

CLAUDE.md 是 Claude Code 的项目级配置文件，放在项目根目录。Claude Code 启动时会自动读取，让 AI 理解项目的编码规范、架构约定、命令脚本、注意事项等。这是提升 Claude Code 表现的最有效手段。

完整示例

# 项目规范

## 项目概述
这是一个基于 Go + React 的全栈博客平台。
- 后端：Go 1.22 + Gin + GORM + MySQL
- 前端：React 18 + TypeScript + Vite + TailwindCSS
- 部署：Docker + Nginx + 阿里云

## 编码规范
- Go：遵循 Effective Go，使用 gofmt 和 golangci-lint
- TypeScript：strict 模式，禁止 any 类型
- 命名：Go 用 PascalCase，TS 用 camelCase，常量用 UPPER_SNAKE_CASE
- 注释：公共函数必须有注释，使用对应语言的文档注释格式
- 错误处理：Go 必须检查所有错误，不使用 _ 忽略

## 常用命令
- 后端测试：`cd backend && go test ./...`
- 前端构建：`cd frontend && npm run build`
- 启动开发环境：`docker-compose up -d`
- 代码检查：`make lint`
- 数据库迁移：`cd backend && go run cmd/migrate/main.go`

## 架构约定
- 后端分层：handler → service → repository → model
- 前端分层：pages → components → hooks → services → types
- API 设计：RESTful，版本前缀 /api/v1/
- 数据库：软删除用 deleted_at，时间戳用 created_at/updated_at
- 配置：环境变量优先，使用 .env 文件（不提交到 Git）

## 注意事项
- 不要修改 vendor/ 目录
- 不要提交 .env 和 secrets/ 目录
- 数据库迁移必须可回滚
- 前端组件必须支持 SSR
- 所有外部 API 调用必须有超时和重试
- 日志使用结构化日志（zap），不要用 fmt.Println

## 测试要求
- 后端单元测试覆盖率 ≥ 70%
- 前端关键组件必须有测试
- 新功能必须包含测试
- CI 中测试必须全部通过

## Git 工作流
- 分支命名：feature/xxx, fix/xxx, hotfix/xxx
- 提交信息：Conventional Commits（feat:, fix:, docs:, refactor:）
- PR 必须通过 CI 和 Code Review
- main 分支受保护，只能通过 PR 合并

编写技巧

  1. 简洁明了：不要写太长，重点突出，Claude 会自动理解上下文
  2. 命令准确：常用命令必须准确，Claude 会直接执行
  3. 禁止事项：明确列出不能做的事情（如不要修改某目录、不要提交某文件）
  4. 分层放置：根目录放全局规范，子目录可以放局部规范（如 backend/CLAUDE.md）
  5. 持续更新：随着项目演进更新 CLAUDE.md，保持与实际一致

MCP（Model Context Protocol）集成

MCP 是 Anthropic 推出的开放协议，让 Claude Code 可以连接外部工具和数据源。通过 MCP，Claude Code 可以访问数据库、API、文件系统、第三方服务等。

flowchart LR CC[Claude Code] --> MCP[MCP Client] MCP --> FS[filesystem] MCP --> GH[github] MCP --> PG[postgres/mysql] MCP --> FW[fetch] MCP --> MEM[memory] MCP --> PW[playwright] FS --> W1[读写项目文件] GH --> W2[PR/Issue/代码] PG --> W3[查询业务数据] FW --> W4[抓网页文档] MEM --> W5[跨会话记忆] PW --> W6[浏览器自动化验证]

MCP 价值：它把"AI 只能读文本"升级为"AI 能调真实工具"——数据库查询、GitHub 操作、浏览器验证都成了模型可调用的能力，而不是靠你手动转述。

在 ~/.claude.json 或项目的 .mcp.json 中配置：

权限模式

权限模式命令执行风险适用场景
默认（每次确认）逐条人工批准低日常开发、不熟悉的项目
--read-only只读不写极低代码解释、调研、读代码库
ALLOWED_COMMANDS 白名单白名单内自动，其余确认中低常用 git/npm/go 任务
--dangerously-skip-permissions全自动执行高沙箱/CI 内，本机慎用

安全纪律：本机开发用默认确认或白名单模式；只有在隔离沙箱/CI 容器里才用 skip-permissions。越权命令（rm -rf、推送 main）永远人工过一眼。

Prompt 技巧

  1. 明确目标：说清楚要做什么，不要模糊
  2. 提供上下文：@引用文件，说明相关模块
  3. 指定约束：技术栈、性能要求、兼容性要求
  4. 分步执行：大任务拆成小步骤，"先分析，再实现，最后测试"
  5. 要求验证："实现后运行测试确保通过"
  6. 要求解释："解释你的实现思路和关键决策"
  7. 迭代优化：第一次结果不满意，继续追问"优化性能"、"添加错误处理"

成本优化

  1. 选择合适模型：日常用 Sonnet，复杂任务才用 Opus
  2. 及时压缩上下文：/compact 压缩历史，减少输入 token
  3. 避免重复加载：不要反复 @引用大文件，一次加载后上下文会保留
  4. 使用 CLAUDE.md：项目规范放在 CLAUDE.md，不用每次对话重复说明
  5. 小步迭代：不要一次让 AI 做太多，分步执行，减少出错和重试
  6. 监控用量：/cost 查看当前会话费用，避免超支
  7. API 按量付费：高用量用户用 API 直接调用可能比订阅更划算

局限性与注意事项

  • 会犯错：AI 会生成有 bug 的代码，必须人工审查和测试
  • 会幻觉：可能编造不存在的 API、库、文档，遇到不确定的要验证
  • 上下文有限：虽然 1M 很大，但超大代码库仍需选择性加载
  • 不理解业务：AI 只理解代码，不理解业务背景和隐含需求
  • 安全风险：自动执行命令可能有风险，重要操作要确认
  • 成本控制：长时间运行的任务可能消耗大量 token，注意监控
  • 不要盲目信任：AI 是助手不是替代，最终责任在开发者

最佳实践总结

  1. 写好 CLAUDE.md：这是提升表现的最有效手段，投入时间编写和维护
  2. 使用 Git 分支：Claude 的修改放在独立分支，审查后合并
  3. 保持测试覆盖：好的测试是安全重构的基础，让 AI 运行测试验证
  4. 小步快跑：大任务拆小步，每步验证，避免一次性生成大量不可控代码
  5. 人工审查：所有 AI 生成的代码必须人工审查，不要直接合并
  6. 迭代优化：第一次结果通常不是最优，继续追问优化、重构、加测试
  7. 利用 MCP：连接数据库、GitHub、API 等工具，让 AI 访问真实数据
  8. 管理成本：选择合适模型，监控用量，及时压缩上下文

CLAUDE.md 到底怎么写才有效

很多人写 CLAUDE.md 就是复制一段 README，效果很差。我总结了几条实战经验：

该写的例子为什么有效
技术栈和版本"用 Go 1.22，gin 框架，不要用 echo"防止它用错框架
目录结构约定"业务逻辑放 internal/，不要放 pkg/"防止文件乱放
测试命令"跑测试用 go test ./...，不要用 make test"让它自己验证
禁忌事项"不要改 config.yaml 里的生产配置"防止它乱动
代码风格"错误处理用 if err != nil，不要用 panic"统一风格

反过来说，别在 CLAUDE.md 里写空话。"要写出高质量的代码"这种话一点用没有，Claude 不知道你说的"高质量"是什么。要写具体的、可执行的规则。

MCP 在 Claude Code 里怎么用

MCP（Model Context Protocol）是 Anthropic 自己推的协议，所以 Claude Code 对它的支持是原生级的。你配一个 MCP server，Claude 就能直接读你的数据库、查你的 GitHub issue、调你的内部 API。

我自己的玩法是配了三个 MCP：一个查公司内部知识库、一个查 Jira、一个跑只读 SQL。这样我在让它改代码的时候，它能自己去查需求背景，不用我把需求贴来贴去。

// .mcp.json 配置示例
{
  "mcpServers": {
    "jira": {
      "command": "npx",
      "args": ["-y", "@anthropic/mcp-jira"],
      "env": { "JIRA_API_TOKEN": "xxx" }
    },
    "db-readonly": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-postgres", "postgresql://localhost/mydb?readonly=true"]
    }
  }
}
MCP 安全红线

给 Claude 配 MCP server 的时候，权限一定要最小化。数据库只读就只读，别给它写权限；网络访问能限制就限制。它是 AI，被提示注入了之后什么都敢干。我见过有人配了个能删数据库的 MCP，第二天库没了。

常见问题 FAQ

Q1：Claude Code 和 Cursor 到底哪个强？

风格完全不同。Cursor 是"编辑器里的 AI 补全"，你写代码它帮你补；Claude Code 是"命令行里的 Agent"，你说目标它自己跑。写新功能、边写边想用 Cursor 更顺；大型重构、自动化跑测试、跨文件改动用 Claude Code 更爽。我现在两个都开着，看任务选。

Q2：Claude Code 会把我的代码发到 Anthropic 服务器吗？

会。它本质是调 Claude API，你的代码会经过 Anthropic。敏感代码、公司机密项目，你得看你们公司的合规政策。2026 年 Anthropic 有企业版承诺不留存训练数据，但小公司项目还是得自己掂量。真敏感就用本地模型方案。

Q3：为什么 Claude Code 经常卡在某个地方不动？

大概率是上下文太长了，或者它在反复试错。两个办法：一是新开一个会话，把当前进展摘要一下再继续；二是显式告诉它"停，换个思路"。Claude Code 有个 /compact 命令能压缩上下文，上下文满了先 compact 一下。

Q4：CLAUDE.md 写多长合适？

别太长，一页纸到两页纸差不多。太长了它自己也抓不住重点。我个人控制在 200 行以内，只写最关键的规则和背景。太细的东西让它自己去看代码，别全塞进 CLAUDE.md。

Q5：Claude Code 能接 GitLab、GitHub 自动化吗？

能。它有 CLI，可以接 CI/CD。比如我在 GitHub Actions 里跑 Claude Code，让它自动 review PR、自动修小 bug。但跑自动化的时候一定要加权限控制和成本上限，不然它能给你烧出天价账单。
