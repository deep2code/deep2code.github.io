<h3 id="安装运行">安装运行</h3>
<hr>
<pre><code class="language-sh">#memcached依赖libevent
brew install memcached
brew services start memcached</code></pre><blockquote>
<p>启动选项：</p>
</blockquote>
<ol>
<li>-d是启动一个守护进程；</li>
<li>-m是分配给Memcache使用的内存数量，单位是MB；</li>
<li>-u是运行Memcache的用户；</li>
<li>-l是监听的服务器IP地址，可以有多个地址；</li>
<li>-p是设置Memcache监听的端口,默认11211；</li>
<li>-c是最大运行的并发连接数，默认是1024；</li>
<li>-P是设置保存Memcache的pid文件。</li>
<li>-h是显示帮助</li>
</ol>
<h3 id="使用">使用</h3>
<hr>
<pre><code class="language-sh">telnet localhost 11211</code></pre><h3 id="存储命令">存储命令</h3>
<hr>
<pre><code class="language-sh">command &lt;key&gt; &lt;flags&gt; &lt;expiration time&gt; &lt;bytes&gt;
&lt;value&gt;</code></pre><blockquote>
<p>参数说明如下：</p>
</blockquote>
<ol>
<li>command set|add|replace|append|prepend</li>
<li>key     key 用于查找缓存值</li>
<li>flags     可以包括键值对的整型参数，客户机使用它存储关于键值对的额外信息</li>
<li>expiration time     在缓存中保存键值对的时间长度（以秒为单位，0 表示永远）</li>
<li>bytes     在缓存中存储的字节数</li>
<li>value     存储的值（始终位于第二行）</li>
</ol>
<h3 id="expiration-time设置影响">expiration time设置影响</h3>
<ol>
<li>
<p><strong>缓存雪崩:短时间内大量键超时失效</strong></p>
</li>
<li>
<p><strong>缓存击穿:缓存中没有键值</strong></p>
<ol>
<li>确实不存在:用布隆过滤器优化</li>
<li>键超时:设置永不超时,受最大内存限制</li>
</ol>
</li>
</ol>

<h2 id="memcached-2024-update">Memcached 2026 现状与对比</h2>

<h3 id="memcached-maintenance">维护状态：仍在活跃迭代</h3>
<p>Memcached 并未停摆：1.6.x 保持持续发布，<strong>1.6.45（2026-07-09）</strong>为当前稳定版，官方 GitHub 仓库维护节奏正常，生产环境可放心继续使用。</p>
<ul>
<li><strong>EXTSTORE</strong>：SSD 扩展存储，热数据留内存、冷数据落盘，容量大幅扩展</li>
<li><strong>TLS</strong>：1.6 起支持加密传输，公网部署可不再裸奔</li>
<li><strong>Meta 协议</strong>：更高效的读写与 TTL 管理（见下文）</li>
</ul>
<blockquote>
<p>定位始终保持简单：只做 KV 缓存，不做持久化、不玩复杂数据结构——这正是它十年如一日的可靠性来源。</p>
</blockquote>

<h3 id="memcached-meta">Meta 协议与批量读取</h3>
<p>Meta 协议用 <code>mg</code>/<code>ms</code>/<code>ma</code> 等命令替代老式 <code>get</code>/<code>set</code>，一次往返即可完成读取、TTL 刷新与内存管理，比传统命令减少约一半网络往返：</p>
<pre><code class="language-bash"># 批量读取：一次往返拿多个 key
> mg key1 key2 key3
VALUE key1 0 5
hello

# 写入并设置 TTL（60 秒）
> ms key1 60 5
hello</code></pre>
<ul>
<li>省下的往返在超大 Value、热点 Key 场景收益最明显</li>
<li>配合 <code>me</code>/<code>md</code>（带过期语义的读/删）可实现原子化的分布式锁与限流</li>
</ul>

<h3 id="memcached-cluster">集群与扩展方案</h3>
<ul>
<li>官方没有内置集群：水平扩展靠<strong>客户端一致性哈希</strong>（如 ketama）与虚拟节点，故障时只影响少数缓存键</li>
<li>典型拓扑：多台实例 + Twemproxy / 自研代理层或直连客户端分片</li>
<li>相比 Redis Cluster：Memcached 集群更"裸"，没有元数据与 Gossip 开销，适合纯粹的缓存层</li>
</ul>
<blockquote>
<p>实践要点：缓存层设计成"可整体清空重建"，应用侧对缓存缺失做降级，Memcached 节点增减就无痛了。</p>
</blockquote>

<h3 id="memcached-alternatives">替代与竞品：Dragonfly / Valkey（2026）</h3>
<p>如果嫌 Memcached 太朴素，2026 年有两大主流替代：</p>
<ul>
<li><strong>Dragonfly</strong>：多线程共享内存架构，协议同时兼容 Redis 与 Memcached，Memcached 存量应用几乎零改动迁移，单机吞吐在官方基准中数倍于 Redis 单线程</li>
<li><strong>Valkey</strong>（Linux 基金会）：Redis 7.2 的社区分支，命令集兼容，若组织要求"纯开源治理"且想兼顾数据结构能力可评估替换</li>
</ul>

<h3 id="memcached-vs-redis">Memcached vs Redis（2026 更新对比）</h3>
<table>
<thead><tr><th>特性</th><th>Memcached</th><th>Redis</th></tr></thead>
<tbody>
<tr><td>数据结构</td><td>仅 KV（二进制/字符串）</td><td>String/List/Hash/Set/ZSet/Stream/JSON/向量</td></tr>
<tr><td>持久化</td><td>无（纯内存）</td><td>RDB + AOF，可当数据库用</td></tr>
<tr><td>集群</td><td>客户端一致性哈希分片</td><td>原生 Cluster + 分片 Pub/Sub</td></tr>
<tr><td>多线程</td><td>✅ 原生多线程（默认）</td><td>6.0+ IO 多线程，8.x 查询引擎</td></tr>
<tr><td>内存效率</td><td>更高（元数据更少）</td><td>稍低（功能更多、编码更复杂）</td></tr>
<tr><td>协议</td><td>文本 / 二进制 / Meta</td><td>RESP2 / RESP3</td></tr>
<tr><td>许可</td><td>BSD（宽松）</td><td>RSAL/SSPL/AGPL 三选一（8+）</td></tr>
<tr><td>适用场景</td><td>读多写少的纯 KV 缓存</td><td>缓存 + 数据库 + 消息队列 + 向量检索</td></tr>
</tbody>
</table>
<blockquote>
<p>结论：缓存层选 Memcached 简单高效；需要数据结构、持久化、消息或 AI 检索时选 Redis 8.x。</p>
</blockquote>
