  • root 和 alias 的区别

# 请求/abc/123 ==> /var/www/app/static/abc/123
location /abc {
    # In case of the root directive, full path is appended to the root including the location part
    # 请求的path附加上root指定path,组合本地路径
    root /var/www/app/static;
    autoindex off;
}

# 请求/abc/123 ==> /var/www/app/static/123
location /abc {
    # only the portion of the path NOT including the location part is appended to the alias.
    # 请求的path移除掉location的path,再附加上alias指定path,组合本地路径
    alias /var/www/app/static;
    autoindex off;
}

Nginx 常用技巧更新

本节基于 2026-08 现状（mainline 已到 1.31.4、stable 1.30.x）重写旧技巧：先纠正双监听配置里的错误指令，再补充 1.29-1.31 引入的实用新能力。

HTTP/3 + HTTP/2 双监听（纠正版）

旧配置里的 http3 on; 是 不存在的指令 （网上流传很广的误解），启用 HTTP/3 靠 listen 的 quic 参数。而且 1.31.2 修复了 ngx_http_v3_module 的 use-after-free（CVE-2026-42530），生产建议跑在 1.31.x 或对应的 stable：

server {
    listen 443 ssl;                # TCP：HTTP/1.1 + HTTP/2
    listen 443 quic reuseport;     # UDP：HTTP/3（无 http3 on 指令）

    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_early_data on;             # 0-RTT，需 OpenSSL 3.5.1+ 或 BoringSSL/QuicTLS
    quic_retry on;                 # 地址验证

    add_header Alt-Svc 'h3=":443"; ma=86400';  # 浏览器凭该头上探 h3
}

近一年 Nginx 主线把以往要靠商业版或第三方补丁的能力搬进了开源版，几个高价值点：

Nginx 常用技巧

Nginx 常用技巧底层原理深度解析

rewrite 与 location 匹配原理

Nginx 的 location 匹配和 rewrite 规则是配置中最容易出错的部分，理解其底层原理至关重要：

  • location 匹配优先级：Nginx 的 location 有四种修饰符，按优先级从高到低：
    1. =（精确匹配）：location = /path，请求路径必须完全等于 /path。优先级最高，匹配后立即停止搜索
    2. ^~（前缀匹配，优先于正则）：location ^~ /prefix/，请求路径以 /prefix/ 开头。如果匹配，不再检查正则 location
    3. ~ / ~*（正则匹配）：~ 区分大小写，~* 不区分大小写。按配置文件中的顺序依次检查，第一个匹配的生效。注意：正则匹配的顺序很重要，更具体的正则应该放在前面
    4. 无修饰符（前缀匹配）：location /prefix/，请求路径以 /prefix/ 开头。优先级最低，Nginx 选择最长匹配的前缀 location（不是配置顺序，是匹配长度）
    匹配流程：先检查精确匹配（=）→ 再检查前缀匹配（^~ 和无修饰符，选最长）→ 如果前缀匹配是 ^~，停止；否则检查正则匹配（按顺序）→ 正则匹配成功用正则，否则用最长前缀匹配
  • rewrite 规则执行流程：rewrite regex replacement [flag]; 在 server 或 location 块中执行，按配置顺序依次执行。rewrite 修改 URI 后，根据 flag 决定后续行为：
    • last：停止当前 location 的 rewrite，用新 URI 重新搜索 location（相当于内部重定向，重新走 location 匹配流程）。注意：last 会导致重新匹配 location，如果新 URI 又匹配到同一个 location，可能导致无限循环（Nginx 限制 10 次后返回 500）
    • break：停止当前 location 的 rewrite，继续在当前 location 中处理后续指令（不重新匹配 location）。常用于 proxy_pass 前的 URI 重写
    • redirect：返回 302 临时重定向，replacement 必须以 http:// 或 https:// 开头（或使用变量）。客户端会重新请求新 URL
    • permanent：返回 301 永久重定向，浏览器会缓存重定向结果
    注意：rewrite 的 regex 是匹配完整的 URI（不含域名，含查询字符串？不，rewrite 默认不匹配查询字符串，查询字符串在 $args 变量中）。replacement 中可以使用变量（$1、$2 等捕获组）
  • try_files 原理：try_files file1 file2 ... uri; 或 try_files file1 file2 ... =code;。按顺序检查文件/目录是否存在，第一个存在的生效（内部重定向到该文件）。如果都不存在，fallback 到最后一个参数（uri 内部重定向，或 =code 返回状态码）。try_files 是静态站点和前端路由（SPA）的核心：try_files $uri $uri/ /index.html;（如果请求的文件不存在，返回 index.html，由前端路由处理）

proxy_pass 与反向代理原理

  • proxy_pass URI 处理：proxy_pass http://backend;（无 URI）和 proxy_pass http://backend/path/;（有 URI）的行为不同：
    • 无 URI（proxy_pass 后只有主机和端口，没有路径）：Nginx 将完整的请求 URI 传递给后端。如 location /api/ { proxy_pass http://backend; }，请求 /api/users → 后端收到 /api/users
    • 有 URI（proxy_pass 后有路径）：Nginx 用 proxy_pass 的 URI 替换 location 匹配的前缀。如 location /api/ { proxy_pass http://backend/v1/; }，请求 /api/users → 后端收到 /v1/users（/api/ 被替换为 /v1/）
    常见错误：location 是正则匹配（~ /api/(.*)）时，proxy_pass 不能有 URI（因为正则匹配没有固定前缀可替换），需要使用 rewrite 或变量构造 URI
  • 代理缓冲区（Proxy Buffering）：Nginx 作为反向代理时，默认启用代理缓冲：Nginx 从后端读取响应，存储到缓冲区（proxy_buffer_size、proxy_buffers、proxy_busy_buffers_size），缓冲区满或后端响应完成后再发送给客户端。缓冲的好处：后端响应快但客户端慢时，Nginx 可以快速释放后端连接（后端不需要等待慢客户端），提高并发能力。坏处：增加延迟（需要等缓冲区满才发送）、内存占用（每个连接分配缓冲区）。对于流式响应（SSE、视频流、大文件下载），应该禁用缓冲（proxy_buffering off;），Nginx 直接将后端响应同步转发给客户端
  • WebSocket 代理：WebSocket 协议需要 HTTP 升级（Upgrade: websocket，Connection: Upgrade），Nginx 默认不转发这些头。需要配置：proxy_http_version 1.1;（HTTP/1.1 才支持 Upgrade）、proxy_set_header Upgrade $http_upgrade;、proxy_set_header Connection "upgrade";。同时设置较长的 proxy_read_timeout（WebSocket 是长连接，默认 60s 无数据会断开）

8大常见陷阱与最佳实践

  1. location 匹配顺序错误导致请求路由到错误的处理块：Nginx 的 location 匹配不是按配置顺序（正则除外），而是按优先级和匹配长度。常见错误：以为前缀匹配按配置顺序生效（实际是选最长匹配）、正则匹配顺序错误（更通用的正则放在前面导致更具体的正则永远不匹配）、^~ 和正则的优先级混淆。解决：理解 location 匹配优先级（= > ^~ > 正则 > 前缀）。使用 nginx -T 查看完整配置，用 curl -v 测试实际路由。正则 location 按从具体到通用的顺序排列。复杂路由使用精确匹配（=）避免歧义。使用 location / 作为兜底（所有未匹配的请求走这里）。文档注释每个 location 的用途和匹配规则
  2. rewrite 无限循环导致 500 错误：rewrite 使用 last flag 时，会用新 URI 重新匹配 location，如果新 URI 又匹配到同一个 location（或另一个又 rewrite 回来的 location），会形成无限循环。Nginx 限制最多 10 次循环，超过后返回 500 Internal Server Error（错误日志中记录 "rewrite or internal redirection cycle"）。解决：使用 break 替代 last（如果不需要重新匹配 location）。确保 rewrite 后的 URI 不会再次匹配到同一个 rewrite 规则。使用 if 条件避免重复 rewrite（如 if ($uri !~ ^/new/) { rewrite ^/old/(.*) /new/$1 last; }）。测试 rewrite 规则（curl -I 查看重定向链，curl -L --max-redirs 5 限制重定向次数）。避免复杂的 rewrite 链，尽量用 location 匹配直接路由
  3. proxy_pass URI 替换错误导致后端收到错误路径：proxy_pass 有 URI 和无 URI 的行为不同，配置错误会导致后端收到错误的请求路径（404 或路由错误）。常见错误：正则 location 中使用带 URI 的 proxy_pass（Nginx 会报错或行为异常）、location 末尾有 / 但 proxy_pass 末尾没有 /（或反之，导致路径拼接错误）。解决：明确 proxy_pass 是否需要 URI。无 URI 时传递完整请求路径，有 URI 时替换 location 前缀。正则 location 中使用 rewrite 构造 URI（rewrite ^/api/(.*) /$1 break; proxy_pass http://backend;）。注意末尾斜杠：location /api { proxy_pass http://backend; } 请求 /apixxx 也会匹配（因为前缀匹配不需要 / 分隔），建议 location 末尾加 /（/api/）。用 curl -v 测试，查看后端收到的实际请求路径（后端日志或 proxy_set_header X-Request-URI $request_uri;）
  4. HTTPS 配置不完整导致降级或安全警告：HTTPS 配置常见问题：只配置了证书但没有中间证书（chain）导致某些客户端报"证书不受信任"、TLS 版本过低（支持 SSLv3/TLSv1.0 有安全漏洞）、密码套件（cipher suite）不安全、HSTS 未配置导致可被降级攻击、OCSP stapling 未配置导致 TLS 握手慢。解决：使用完整的证书链（fullchain.pem，包含服务器证书 + 中间证书，不要用 cert.pem 只有服务器证书）。配置 ssl_protocols TLSv1.2 TLSv1.3;（禁用 SSLv3/TLSv1.0/TLSv1.1）。使用安全的密码套件（ssl_ciphers ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256:...:!aNULL:!MD5;）。启用 HSTS（add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;）。启用 OCSP stapling（ssl_stapling on; ssl_stapling_verify on;）。使用 SSL Labs Server Test（ssllabs.com/ssltest）评分，目标 A+。HTTP 强制跳转 HTTPS（return 301 https://$host$request_uri;）
  5. gzip 压缩配置不当导致 CPU 过载或压缩无效：gzip 压缩可以减少传输大小（通常 60-80%），但配置不当会有问题：压缩级别过高（gzip_comp_level 9）导致 CPU 占用高（压缩时间长，收益递减，level 6 是性价比最优）、对已压缩的文件（图片、视频、zip）再次压缩（浪费 CPU，且压缩率为负）、未设置 Vary: Accept-Encoding 头导致 CDN/代理缓存错误（压缩版和未压缩版混淆）。解决：gzip on; gzip_comp_level 6;（level 6 是默认，性价比最优）。gzip_types text/plain text/css application/json application/javascript text/xml application/xml application/xml+rss text/javascript image/svg+xml;（只压缩文本类内容，不压缩图片/视频/二进制）。gzip_min_length 1024;（小于 1KB 的文件不压缩，压缩开销大于收益）。gzip_vary on;（添加 Vary: Accept-Encoding 头）。gzip_proxied any;（对代理请求也压缩）。使用 Brotli 压缩（ngx_brotli 模块）比 gzip 更高效（压缩率高 15-25%），但需要编译模块
  6. 静态资源缓存配置错误导致用户看到旧版本：静态资源（CSS、JS、图片）的缓存配置常见问题：缓存时间过长导致更新后用户看到旧版本（浏览器缓存未过期）、缓存时间过短导致重复请求（性能差）、HTML 也被缓存导致内容更新不及时、没有文件版本化（无法区分新旧版本）。解决：使用内容哈希命名（如 app.abc123.js，文件内容变化时哈希变化，URL 变化，自动绕过缓存）。静态资源（带哈希的 CSS/JS/图片）设置长缓存（expires 1y; add_header Cache-Control "public, immutable";，immutable 表示文件不会变，浏览器不需要重新验证）。HTML 设置短缓存或不缓存（add_header Cache-Control "no-cache";，no-cache 表示可以缓存但每次必须验证 ETag/Last-Modified，不是不缓存）。使用 etag on;（默认开启）和 if_modified_since exact; 支持条件请求（304 Not Modified）。更新静态资源时同时更新 HTML 中的引用路径（哈希变化），用户下次请求 HTML 时拿到新 URL。不要对 HTML 使用 expires 长缓存
  7. worker 进程和连接数配置不当导致性能瓶颈：Nginx 的性能相关配置常见问题：worker_processes 设置为 1（无法利用多核）或 auto（auto 会检测 CPU 核心数，通常是最佳选择）、worker_connections 过低（默认 512，高并发场景不够）、worker_rlimit_nofile 未设置（文件描述符限制导致"too many open files"错误）、keepalive_timeout 过长（长连接占用资源）或过短（频繁建立连接）。解决：worker_processes auto;（自动匹配 CPU 核心数）。worker_connections 65535;（高并发场景，每个 worker 最大连接数）。worker_rlimit_nofile 65535;（每个 worker 的文件描述符限制，应该 >= worker_connections）。keepalive_timeout 65;（客户端长连接超时，65 秒是常见值，不要太长）。keepalive_requests 1000;（一个长连接最多处理的请求数，超过后关闭连接，防止单个连接占用过久）。multi_accept on;（worker 一次接受所有新连接，而非一次一个，提高吞吐）。使用 nginx -V 查看编译参数，确保支持 epoll（Linux）/kqueue（BSD）。监控 Nginx 的活跃连接数（stub_status 模块）和 worker 进程 CPU/内存使用
  8. 安全配置缺失导致服务器被攻击：Nginx 安全常见问题：暴露服务器版本号（server_tokens on 默认，响应头 Server: nginx/1.24.0，攻击者可以针对特定版本漏洞）、允许目录列表（autoindex on，暴露文件结构）、未限制请求体大小（导致 DoS，超大请求耗尽内存）、未限制请求速率（暴力破解、爬虫滥用）、敏感文件（.env、.git、备份文件）可被访问。解决：server_tokens off;（隐藏版本号，只显示 Server: nginx）。autoindex off;（默认关闭，不要开启）。client_max_body_size 10m;（限制请求体大小，根据需求调整）。使用 limit_req_zone + limit_req 限制请求速率（防暴力破解和爬虫，如 limit_req zone=api burst=10 nodelay;）。使用 limit_conn_zone + limit_conn 限制单 IP 连接数。禁止访问敏感文件：location ~ /\. { deny all; return 404; }（隐藏文件，如 .git、.env）、location ~* \.(bak|old|sql|log)$ { deny all; }（备份和日志文件）。安装 ModSecurity WAF（Web 应用防火墙）或 Nginx Plus 的 WAF 模块。定期更新 Nginx 版本（安全补丁）
