附录

  • RTMP、RTSP、HTTP 协议理论上都能做视频直播或点播，工程惯例是：直播走 RTMP/RTSP，点播走 HTTP，各取所长。

  • 先说 RTMP

    • 它是 Adobe 定义的流媒体协议，专门承载音视频流与命令通道。
    • RTMP 规范由 Adobe 于 2009 年公开，但整套 Flash/RTMP 生态已随 2020-12-31 Flash 停更而退场，如今只在推流入口（Push）还活着。
    • RTMP 线上一般传输 flv、f4v 封装格式的流，容器与协议绑定得比较紧。
    • RTMP 通常在 TCP 上只用 1 条通道，命令和数据混在一起走，实现简单，但控制面与媒体面不分离。

  • 再看 RTSP

    • 是流媒体控制协议，控制信令与媒体传输分离，结构上更清晰。
    • RTSP 是公开协议，维护由专门机构负责，不像 RTMP 那样依附 Adobe 私有生态。
    • RTSP 一般承载 ts、mp4 格式的流，媒体数据单独流转。
    • RTSP 传输通常需要 2-3 条通道，命令通道和数据通道分离，可控性更强。

  • 然后 HTTP

    • HTTP 本身没有流的语义（无状态），HLS/DASH 只是把媒体切成分片、装进普通 HTTP 文件请求。
    • HTTP 是公开协议、有专门机构维护，天然适合开放生态。
    • HTTP 不限定传输流格式，分片是什么容器都行。
    • HTTP 是请求-响应模型：每个媒体分片对应一次 GET 请求，没有独立命令通道；分片文件天然适合 CDN 缓存与多级分发，这是点播大流量场景都选它的原因。

原版 nginx-rtmp-module但 arut 仓库的官方 tag 还钉在 v1.2.x，多年没发正式版，只剩零星编译修复提交——基本等于停更状态，社区只能依赖 fork（如nginx-http-flv-module）来续命。想在新主线（1.29+/1.31）上继续用这个模块，得自己在目标版本重新编译并回归推拉流，旧二进制不能直接拿过来用

2026 替代方案对照

方案语言定位与要点
SRSC++老牌开源流媒体服务器（Go 编写是常见误传），RTMP/HTTP-FLV/HLS/WebRTC/SRT 全协议，生态与文档完善，适合自建单点直播
MediaMTXGo轻量统一接入层，RTSP/RTMP/HLS/WebRTC/SRT 互转，单二进制易部署，适合把现有 RTSP/RTMP 源转成 WebRTC/HLS 分发
OvenMediaEngineC++韩系商业化开源，主打 LL-HLS 与低延迟 WebRTC 分发，集群与 Edge 架构成熟
ZLMediaKitC++国内社区活跃，RTSP/RTMP/HTTP-FLV/HLS 全覆盖，C API 二次开发友好

何时继续用 nginx-rtmp

如果只是「OBS 推流 → 服务器录制 / 转 HLS 点播」这类轻量内部场景，nginx-rtmp 加hls on分片依然够用：配置熟悉、没有迁移成本，但录制要用record实现 FLV 落地与 HLS 分片（2-4s），兼容和延迟之间做折中。但一旦要上 WebRTC 低延迟分发、多协议互转、集群扩容，就得换上表方案。2026 年的协议版图：RTMP 仍是推流端事实标准（OBS/手机端兼容最好），分发侧已全面转向 HLS/LL-HLS/WebRTC，nginx-rtmp 原生接不上 WebRTC 是它最大的硬伤
