消息队列入门：为什么要发消息？

🏷️ 消息队列

消息队列的价值不是「快」，而是同时切断两种耦合：时间耦合（调用方必须等下游处理完）和空间耦合（调用方必须知道下游是谁、有几个、在哪）。这笔交易换来的是故障隔离和削峰能力，赔进去的是重复投递、乱序、积压、链路可观测性下降，以及一个新增的强依赖中间件。这篇只谈架构决策层面：什么时候值得做这笔交易，什么时候是纯亏损。具体产品的机制见MQ 选型与 RabbitMQ / RocketMQ 机制，可靠投递见可靠投递与消费，Kafka 的内部实现见站内 Kafka 专题。

四个核心价值，以及不用它的具体后果

「解耦、异步、削峰」这三个词被说烂了，但很少有人说清每一条对应的是什么具体故障。下面这张表的第二列才是重点——如果你的系统里找不到第二列描述的场景，那就不需要 MQ。

核心价值 不用 MQ 会怎样（含量级） MQ 的做法 什么情况下这个价值不成立
解耦 订单服务里硬编码了 5 个下游的地址和 SDK；新增一个「下单后同步数仓」的需求要改订单服务代码、走一遍发布流程。一年下来订单服务发布 30 次，其中 20 次是为了别人的需求 订单只发一条 OrderCreated，新下游自己订阅，订单服务代码不动 下游只有一个且不会增加时，MQ 只是多了一跳
异步削峰 秒杀开始 10 秒内涌入 5 万请求，数据库连接池只有 200，请求全部堆在连接等待上，超时雪崩；扩容数据库来抗 10 秒的峰值，之后 23 小时资源闲置 请求先落队列，消费端按数据库能承受的 2000 QPS 匀速消费，5 万请求 25 秒消化完 峰值持续时间长于队列能缓冲的时长时，削峰只是把雪崩延后
广播分发 一条「用户注册成功」要分别调用积分、优惠券、风控画像、推送四个接口，调用方维护 4 份重试逻辑和 4 份失败告警 一条消息，四个消费组各自消费各自重试，互不影响 下游之间有严格先后依赖时，广播变成了隐式时序依赖
缓冲 下游发版重启 3 分钟，这 3 分钟内的调用全部失败，需要业务方自己写重试表补偿 消息留在队列里，下游启动后自己追上来，业务方无感 消息有效期很短（如实时风控决策）时，缓冲出来的是过期数据

同步串联与消息分发的三个差异

先看同步链路。三个下游串行调用，总延迟是三者之和，任何一个失败整个下单失败。

差异体现在三个维度，其中可用性那一栏才是引入 MQ 真正的理由。串行依赖的可用性是相乘，不是取最小值，这个乘法很反直觉：

同步串联的下游数 每个下游可用性 主链路可用性 折合年不可用时长 改为消息分发后
1 个 99.9% 99.9% 8.8 小时 收益有限，不必改
3 个 99.9% 99.70% 26.3 小时 主链路只依赖 DB 与 MQ，约 99.9%，年 8.8 小时
5 个 99.9% 99.50% 43.8 小时 同上，下游故障只表现为积压
10 个 99.9% 99.00% 87.6 小时 同步方案已不可接受，必须异步
3 个，其中一个 99% 99.9% / 99.9% / 99% 98.80% 105 小时 最差的那个下游决定一切，优先把它剥离
⚠️
MQ 不会凭空提升可用性

上表右列写的是「主链路可用性」，不是系统整体可用性。异步化之后 MQ 集群成了新的强依赖，它挂了照样发不出消息、整条链路照样断。MQ 换来的是故障隔离与降级空间：下游挂掉从「下单失败」降级成「积分晚到」。所以引入 MQ 的同时必须把 MQ 集群按核心基础设施来部署（多副本、跨机架、独立监控），并且给「MQ 不可用」准备降级方案，比如生产端投递失败时写本地 outbox 表兜底。

引入 MQ 立刻带来的五个新问题

这五个问题不是「可能出现」，是上线第一天就存在，只是你没发现。写代码前就要有对策，不要等生产事故再补。

新问题 为什么必然发生 缓解方向 无法消除的残留风险
消息会重复 生产端发送超时但服务端已写入，重试产生第二条；消费端处理完但确认前崩溃；重平衡导致未确认消息转给别的实例；主从切换后位点回退 消费端幂等：业务唯一键 + 去重表唯一索引，或状态机只允许单向流转（四种落地方式见站内分布式一致性篇） 去重表本身有保留期，超期后的迟到重复仍会被处理
消息会乱序 多分区 / 多队列并行投递，多消费者并发处理，失败重试的消息排到后面去了 同一业务键路由到同一分区，且该分区单线程消费；或消息里带版本号 / 更新时间，消费端丢弃比当前状态更旧的消息 顺序保证的粒度只能做到单键，跨键无序；单键有序意味着并发上限等于键的数量
消息会积压 生产速率由业务流量决定，消费速率由代码和下游决定，两者本来就不匹配 消费速率监控 + 积压告警阈值 + 预置扩容脚本；消费逻辑里不要有同步远程调用 下游彻底不可用时，任何扩容都无效，只能等或降级
调试链路变长 一次请求变成「生产端日志 + Broker + 若干消费端日志」，出问题时不知道断在哪一段 消息头里透传 traceId 并在消费端还原上下文；记录投递时间戳以便算端到端延迟 消息被重试、进死信、人工重投后，trace 已经断了，只能靠业务键反查
多了一个要运维的中间件 集群要扩容、要升级、磁盘会写满、会触发限流、会有版本兼容问题 优先用云托管版本；磁盘水位、集群节点存活、分区 / 队列不可用要单独告警 它挂了整条链路断，这是引入 MQ 必须接受的代价

什么场景不该用 MQ

比「怎么用」更值钱的是「什么时候别用」。下面四类场景强行上 MQ，结果是复杂度暴涨而收益为零。

场景 强行用 MQ 的后果 该用什么
需要立即拿到结果
（查库存、算价格、鉴权）		 为了拿结果不得不做「发消息 + 轮询结果表 / 等回调」，延迟反而从 20ms 涨到几百毫秒，还多了超时和状态清理逻辑 直接 RPC / HTTP 调用，配熔断与超时
需要强一致
（转账两端余额）		 消息投递本身只能做到最终一致；中间态对用户可见，对账压力全部压给业务 同库本地事务；跨库用 TCC / Saga（见站内分布式一致性篇）
调用方必须知道处理成败 异步化之后返回值只能是「已受理」，失败要靠回查接口或回调通知，等于自己实现了一套 RPC，还更难排查 同步调用；或明确改成任务模型，返回任务 ID 并提供查询接口
系统规模小、下游只有一个 为了一个下游引入一套集群、一套监控、一套幂等和死信机制，运维成本远超收益 线程池异步 + 失败落重试表 + 定时补偿

// 下单接口：同步链路只保留"用户当场必须看到结果"的步骤
// 非核心步骤通过 outbox 表与业务写在同一个本地事务里，
// 避免"订单落库成功但消息没发出去"（本地消息表细节见站内分布式一致性篇）
func (s *OrderService) Create(ctx context.Context, req CreateReq) (*Order, error) {
    tx, err := s.db.BeginTx(ctx, nil)
    if err != nil {
        return nil, err
    }
    defer tx.Rollback() // Commit 之后再 Rollback 返回 ErrTxDone，可安全忽略

    // 同步核心：扣库存 + 落订单，任一失败整单失败，用户立刻看到原因
    if err := s.stock.DeductTx(ctx, tx, req.SkuID, req.Qty); err != nil {
        return nil, err // 库存不足这类结果必须同步返回，不能异步
    }
    order, err := s.orderRepo.InsertTx(ctx, tx, req)
    if err != nil {
        return nil, err
    }

    // 异步旁路：积分、通知、索引、统计全部收敛成一条领域事件
    evt := OutboxRow{
        // 业务唯一键，消费端用它做幂等；不要用随机 UUID，重试会产生新值
        MsgKey:  fmt.Sprintf("%d:OrderCreated", order.ID),
        Topic:   "order.created",
        Payload: mustJSON(order), // 事件携带状态转移：带全量字段，省掉下游回查
        Status:  outboxPending,
    }
    if err := s.outbox.InsertTx(ctx, tx, evt); err != nil {
        return nil, err
    }
    if err := tx.Commit(); err != nil {
        return nil, err // 事务失败则订单与消息一起不存在，不会出现半成品
    }

    s.relay.Kick() // 唤醒投递线程走快路径；唤醒失败无妨，兜底扫表会补发
    return order, nil
}

消息积压是必然会遇到的

积压的本质只有一句话：生产速率持续大于消费速率。瞬时的生产大于消费叫削峰，那是 MQ 的正常工作状态；持续的大于才是故障。判断标准是看积压曲线的斜率而不是绝对值——10 万条但在稳定下降是健康的，1 万条但每分钟涨 2000 条是要出事的。

成因 现场特征 应急动作 为什么常见的做法没用
消费逻辑慢 消费者 CPU 不高，线程都卡在等待；单条处理耗时从 20ms 涨到 2s；日志里有下游超时 先定位慢在哪一步（多半是循环里做单条数据库查询或同步 HTTP 调用），改批量、加缓存、把远程调用挪出消费逻辑 此时加机器收益很小：瓶颈在下游或在慢查询上，加消费者只是让下游更快被打满
并发度不足 消费者进程 CPU 打满或线程数明显不够；分区 / 队列数远大于消费者实例数；部分分区完全没有活跃消费者 扩消费者实例到不超过分区数；提高单实例消费线程数；RabbitMQ 侧同时调大 prefetch 消费者数量超过分区 / 队列数后是纯浪费，多出来的实例永远拿不到消息
下游故障 处理失败率飙升，重试队列和死信同时增长，积压与下游错误率曲线完全同步 先降级：关掉非关键消费组保住核心；把失败消息转存到备份主题，下游恢复后回放 盲目扩消费者会把下游彻底打死，故障范围从「积压」扩大到「下游集群不可用」
❌
积压时最危险的操作是重置位点

把位点重置到最新（跳过积压）等于永久丢弃中间所有消息：它们不会进死信、没有任何记录、事后无法追回，而这批消息里可能有支付回调和退款通知。把位点往前重置则会让已处理的消息全部重放，非幂等的消费逻辑立刻造成重复发券、重复扣款。唯一可接受的用法是：先用一个独立消费组把待跳过区间的消息全量转存到备份主题，记录清楚起止位点和条数，再重置。只要现场还在犹豫，就不要动位点。

# 积压现场第一步：先量清楚"积了多少、斜率多大、有没有活跃消费者"
# 三种 MQ 的字段含义不同，别用同一套经验去读

# RabbitMQ：ready 是待投递，unacked 是已投递未确认
rabbitmqctl list_queues name messages_ready messages_unacknowledged consumers

# unacked 高而 ready 不高 -> 消费者卡在处理逻辑里，看线程栈

扩容消费者时有一个容易被忽略的前提：提高并发度会破坏顺序。如果业务依赖同一订单的消息有序，不能简单地把消息丢给协程池，必须按业务键哈希到固定 worker。

// 积压应急：提升消费并发度，同时保证"同一业务键"仍然串行
// 反例是直接 go handle(msg)，那样同一订单的"创建"和"取消"可能并发执行
type Pool struct {
    chans []chan Message
    wg    sync.WaitGroup
}

func NewPool(workers, buf int, handle func(Message) error) *Pool {
    p := &Pool{chans: make([]chan Message, workers)}
    for i := range p.chans {
        // 每个 worker 一条带缓冲的通道，缓冲太大会在进程被杀时丢掉未处理消息
        p.chans[i] = make(chan Message, buf)
        p.wg.Add(1)
        go func(ch chan Message) {
            defer p.wg.Done()
            for m := range ch {
                if err := handle(m); err != nil {
                    // 处理失败不要在这里 for 循环重试，会阻塞整个 worker
                    // 交给 MQ 的重试队列，超过次数自动进死信
                    m.Nack()
                    continue
                }
                m.Ack() // 只有处理成功才确认，这是不丢消息的底线
            }
        }(p.chans[i])
    }
    return p
}

// 按业务键哈希落到固定 worker：同一订单永远同一条通道，顺序不乱
// 副作用：并发上限等于 worker 数，且热点键会让某个 worker 单独成为瓶颈
func (p *Pool) Submit(m Message) {
    h := fnv.New32a()
    h.Write([]byte(m.Key)) // Key 用订单号 / 用户 ID，不要用消息 ID
    p.chans[int(h.Sum32())%len(p.chans)] <- m
}

选型前必须先量化的六个需求维度

选型从「哪个更快」开始，结论一定是错的——吞吐数字高度依赖消息体大小、批量参数和刷盘策略，厂商的压测数字换个消息体就翻倍或腰斩。正确顺序是先把下面六项填成具体数字，候选产品自然收敛到一两个。

维度 要问出的具体数字 取值不同会导致的分歧
吞吐量级 峰值每秒多少条、平均消息体多大（1KB 和 100KB 是两个世界） 万级以内路由灵活度优先；十万级以上必须选日志型存储
延迟要求 端到端 P99 允许多少毫秒，是否包含消费处理耗时 要求个位数毫秒就不能开同步刷盘，也不能设大批量攒批
有序性 要全局有序还是同一业务键有序，键的基数有多大 全局有序等于单分区单线程，吞吐直接锁死；键有序才是可落地的目标
回溯能力 是否需要重放历史消息，要保留几天，重放时下游能否承受 需要回溯就必须选消息「消费后仍保留」的产品，队列型天然不适合
延迟消息 是否需要定时 / 延迟触发，是固定几档还是任意时间，精度要求多少 需要任意时间精度会直接排除掉一部分产品，或被迫外挂调度器
可靠性等级 允许丢失的概率量级，是否必须配对账，出问题谁背责 零丢失要求会带来同步刷盘或多副本同步复制，吞吐和延迟都要打折

这六项和具体产品的能力映射、以及 RabbitMQ 的 Exchange 路由模型与 RocketMQ 的事务消息机制，见MQ 选型与机制对比。

本地消息表与 MQ 的分工

很多人把这两者当成竞品，其实解决的是链路上完全不同的两段。MQ 负责「消息进了 Broker 之后不丢」，本地消息表（outbox）负责「业务成功了消息一定发得出去」——后者是 MQ 无论怎么配置都覆盖不到的盲区，因为它发生在消息进入 Broker 之前。

失败场景 只靠 MQ 配置能否解决 需要的机制
订单已 Commit，发消息时进程被 kill 不能，Broker 从来没收到过这条消息 本地消息表 / outbox + 投递线程扫表重发
先发消息再写库，结果写库失败 不能，消息已经发出去了，下游按不存在的订单处理 顺序必须是「先落库再发消息」，或用事务消息
Broker 收到消息但未持久化就宕机 能，靠生产端确认 + 多副本 生产确认机制与副本配置，见可靠投递篇
消费端处理失败但已确认 不能，确认时机是消费端代码的责任 处理成功后再确认，失败走重试与死信

本地消息表、事务消息、TCC / Saga 与幂等的四种具体落地写法，站内分布式一致性篇已经展开过，这里不重复。本站的可靠投递与消费接着讲消息进入链路之后每一环怎么不丢。

❌
最容易踩的坑
  • 先发消息再写数据库：消费者拿到消息去查订单，查不到，于是写「重试几次还查不到就忽略」的补丁。正确顺序是业务与 outbox 同事务落库，投递放在 Commit 之后。
  • 把「已受理」当成「已成功」返回给用户：用户看到下单成功，实际支付消息在死信里躺着。凡是用户会追问结果的步骤，必须有查询接口和最终状态通知。
  • 用 MQ 实现同步等结果：发一条消息然后轮询结果表，延迟比 RPC 高一个数量级，还要处理超时、清理临时状态。需要结果就直接调用。
  • 消费端不幂等就上线：任何一次网络超时重发、一次重平衡、一次主从切换都会产生重复。上线前先用同一条消息投递两次做验收测试。
  • 积压时第一反应是重置位点：跳过的消息永久消失且无记录。先转存再跳过，并记录被跳过的区间与条数。
  • 消费者数量加到超过分区 / 队列数：多出来的实例永远分不到消息，白花钱还让人误以为「扩容了但没用」。扩容前先看分区数。
  • 下游故障时盲目扩消费者：把已经半死的下游彻底打死，故障从积压升级成下游不可用。此时该做的是降级和限流。
  • 消费逻辑里做同步 HTTP 调用且不设超时：下游一慢，消费线程全部挂住，积压瞬间起来。消费逻辑里的每个远程调用都要有超时和熔断。
  • 一个主题承载多种语义的消息：消费者被迫写 switch 分发，新增一种类型要改所有消费者，还没法按类型独立扩容和限流。
  • 消息体里塞大对象或整个文件：消息体从 1KB 涨到 1MB，吞吐掉一个数量级，还可能超过 Broker 的单条上限。大内容放对象存储，消息里只带引用。
  • 只监控积压条数，不监控斜率和端到端延迟：阈值告警在大促时天天误报，真正的持续积压反而被忽略。同时监控积压量、增长速率、消息投递到处理完的延迟。
  • 没有死信的人工重投入口：死信堆了几千条，发现时只能写一次性脚本。死信必须告警，并且要有可查询、可重投、可标记忽略的运维界面。
