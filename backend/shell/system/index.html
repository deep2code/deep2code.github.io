Linux 系统管理

🏷️ systemd,系统管理,自动化脚本

系统管理：从命令到自动化脚本

Shell 最终要落到"把系统管好"：服务怎么拉起、进程怎么排查、磁盘满了怎么救、定时任务怎么写。本篇覆盖 systemd、进程/网络/磁盘诊断、跨发行版包管理，并给出可直接用的备份、监控、部署、日志清理脚本。

运维直觉：出问题按"先看资源（CPU/内存/磁盘）→ 再看进程（谁在吃）→ 再看网络（通不通）→ 最后看日志"的顺序排查。我当年排过一次服务卡死的问题，先看 CPU 没打满、内存正常，然后看发现是磁盘满了——日志文件把根分区撑爆了。排查永远从最底层的资源开始。

systemd：服务管理新时代

现代 Linux 几乎都用 systemd 管理服务。安装软件时常自动在 /usr/lib/systemd/system（或软链 /lib）下生成 unit 文件。核心命令：

graph TD A[systemctl start myapp] --> B[systemd 解析 unit] B --> C[按 After 排序依赖] C --> D[fork 启动主进程] D --> E{Type?} E -- simple --> F[进程前台运行即算启动] E -- forking --> G[主进程 fork 后台,父退出算就绪] E -- oneshot --> H[跑完即退,供其他服务依赖] F --> I[Restart=always 崩溃自动拉起] G --> I H --> I I --> J[日志写入 journalctl] style A fill:#0d1117,stroke:#3ec96f,color:#3ec96f style J fill:#0d1117,stroke:#f59e0b,color:#f59e0b
systemctl 命令作用
systemctl start xxx启动服务
systemctl stop xxx停止服务
systemctl restart xxx重启
systemctl enable xxx开机自启
systemctl disable xxx取消自启
systemctl status xxx查看状态
systemctl daemon-reload改 unit 后重载配置

自定义服务写一个 unit 文件，Type 决定进程行为：simple（默认，前台跑）、forking（后台守护）、oneshot（一次性任务）。timer 替代 crontab 做定时任务：

# /etc/systemd/system/myapp.service
[Unit]
Description=My App
After=network.target

[Service]
Type=simple
User=deploy
WorkingDirectory=/opt/myapp
ExecStart=/opt/myapp/app
Restart=always

[Install]
WantedBy=multi-user.target
# 日志查询（journalctl 是 systemd 的日志中心）
journalctl -u myapp              # 看某服务日志
journalctl -u myapp -f           # 实时跟踪
journalctl --vacuum-size=10M     # 只保留 10M 日志（清理磁盘）

进程管理

排查"谁在占资源"的三板斧：

ps aux                              # 所有进程
# 按内存排序取前 20
ps aux | head -1; ps aux | grep -v PID | sort -rn -k4 | head -20
top                                 # 实时（q 退出）
htop                                # 更友好的交互式
pgrep -f "app"                      # 按名找 PID
kill 1234                           # 温和终止（SIGTERM）
kill -9 1234                        # 强制杀（SIGKILL，不到万不得已别用）
nohup ./app > /dev/null 2>&1 &      # 后台运行，退出终端不挂
nice -n 10 ./app                    # 调低优先级运行
uptime                              # 负载/运行时间/登录数
信号编号含义
SIGTERM15请求终止（kill 默认），可被捕获清理
SIGKILL9强制杀死，不可捕获
SIGHUP1挂起，常用来重载配置
SIGINT2Ctrl+C 中断
SIGSTOP19暂停进程

自动化脚本实战

Git 部署更新脚本：先杀旧进程，拉新代码，再起服务：

#!/usr/bin/env bash
set -e
cd ${gitdir}
# 批量杀旧进程（grep 排除 grep 自身，awk 取 PID）
ps -ef | grep xxx | grep -v grep | awk '{print $2}' | xargs kill -9
ps -ef | grep yyy | grep -v grep | awk '{print $2}' | xargs kill -9
git pull
nohup ./xxx.sh >/dev/null 2>&1 &

进程监控守护脚本：循环检测进程在不在，不在就拉起：

#!/usr/bin/env bash
while true; do
  procnum=$(ps -ef | grep "yyy$" | grep -v grep | wc -l)
  if [ "$procnum" -eq 0 ]; then
    cd ${basedir}
    nohup ./yyy >/dev/null 2>&1 &
  fi
  sleep 30
done

编译发布脚本：注入版本号编译，打包后台运行：

#!/usr/bin/env bash
set -e
ps -ef | grep yyy | grep -v grep | awk '{print $2}' | xargs kill -9
hash=$(git rev-parse --short HEAD)
rc=$(date "+%Y-%m-%d_%H:%M:%S")
target=yyy
go build -ldflags "-s -w -X main.GitHash=${hash} -X main.CompileTime=${rc}" \
  -tags=jsoniter -o ${target} ${target}.go
chmod a+x ${target}
rundir=${target}_run
rm -rf ${rundir} && mkdir ${rundir}
mv ${target} ${rundir} && cp -r conf ${rundir}/
cd ${rundir} && nohup ./${target} >/dev/null 2>&1 &

最佳实践

  • 服务用 systemd 不用 nohup 裸跑：崩溃自动重启、日志统一进 journal。
  • 定时任务用 systemd timer 不用 crontab：有日志、可管理、错过开机能补跑。
  • kill 先 15 后 9：先 kill（SIGTERM）给程序清理机会，顽固再 -9。
  • 脚本开头加 set -e，失败立即暴露。
  • 磁盘告警前置：用脚本定期 df，超过阈值就清理 journal/旧日志。

常见问题 FAQ

Q1：改了 unit 文件为什么没生效？

因为 systemd 缓存了旧配置。改完 unit 文件必须 systemctl daemon-reload，再 systemctl restart xxx。只 restart 不 reload 会继续用旧配置。

Q2：ps aux | grep app | xargs kill 为什么把 grep 自己也杀了？

因为 grep 进程的命令行里也含 "app" 这个字符串。加 grep -v grep 排除掉 grep 自身，或用 grep "app$" 锚定结尾。脚本里都是这么写的。

Q3：磁盘满了但 du 看不出哪里占的？

两种常见原因：一是有进程还持有已删除文件的句柄（空间没真正释放），用 lsof | grep deleted 找到对应进程重启；二是 inode 耗尽（小文件太多），用 df -i 看 inode 使用率。

总结

系统管理的核心是"用对工具"：服务交给 systemd，进程用 ps/top 三板斧，网络按 curl/ss/tcpdump 排查，包管理认发行版，自动化脚本用 set -e + nohup + 循环守护。把这套组合拳练熟，日常运维就游刃有余了。至此 Shell六篇完结——从语言核心到底层原理、工具生态、SSH、文本处理到系统管理，你已经有了一套完整的命令行知识体系。
