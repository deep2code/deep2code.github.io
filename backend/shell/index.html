Shell 脚本的工程化：可靠性优先

🏷️ Shell

我见过的 Shell 生产事故，绝大多数不是命令敲错了，而是脚本在异常路径下继续执行。备份脚本里 dump 那一步失败了，后面的「删除七天前旧备份」照跑，结果是新备份 0 字节、旧备份没了。变量名拼错一个字母展开成空串，rm -rf $DIR/ 就成了 rm -rf /。

根因是 Shell 的默认错误哲学：一条命令失败，解释器不当回事，继续读下一行。这在交互式终端里是对的（你敲错一条命令不至于把终端关掉），但在无人值守的自动化里正好相反——我们要的是「出错就停，并且停在能被发现的地方」。

所以工程化的 Shell 不是「知道更多命令」，而是四层依次收紧的防线。

脚本可靠性的四层防线

flowchart TB subgraph L1["第一层 失败即停"] A1["set -e 命令失败即退出"] A2["set -o pipefail 管道失败可见"] A3["set -u 未定义变量报错"] end subgraph L2["第二层 输入校验"] B1["必填参数用冒号问号语法"] B2["危险路径校验非空"] B3["依赖命令存在性预检"] end subgraph L3["第三层 清理与可观测"] C1["trap EXIT 删临时目录"] C2["trap ERR 打印行号与命令"] C3["日志带时间戳写 stderr"] end subgraph L4["第四层 可重入"] D1["先判断再操作"] D2["同分区 mv 做原子替换"] D3["flock 防并发重入"] end L1 --> L2 L2 --> L3 L3 --> L4

这四层的顺序不是随便排的：没有第一层，后面三层的检查都会被跳过；没有第四层，脚本就只能「成功一次」，而生产环境一定会重试。

set -euo pipefail 的精确语义

set -e 的判断对象是简单命令或整条管道，不是「表达式里的每一步」。这句话是后面所有例外的来源。

set -o pipefail：默认 a | b | c 的退出码只看 c。所以 curl -sf "$url" | tar -xz 里 curl 失败、tar 解了个空流，整条管道的退出码依然是 0，事故完全静默。开了 pipefail 后，退出码取最右边一个失败的命令。

set -u：引用未定义变量立刻报错，能拦住绝大多数拼写错误。但它拦不住「定义了但是空字符串」——那是另一类事故，要靠 ${VAR:?message} 显式声明必填。

# -u 只能拦住「没定义」，拦不住「定义了但为空」
# 冒号问号语法：为空时把消息打到 stderr 并以非零退出，适合做必填校验
: "${DEPLOY_ENV:?DEPLOY_ENV is required, e.g. staging or prod}"
: "${TARGET_DIR:?TARGET_DIR is required}"

# 危险操作前再显式校验一次，双保险；两个减号防止路径以减号开头被当成选项
rm -rf -- "${TARGET_DIR:?refuse to rm with empty TARGET_DIR}"/cache

# 想要「未设置就用默认值」用冒号减号；想要「未设置就赋值并使用」用冒号等号
PORT="${PORT:-8080}"
: "${LOG_DIR:=/var/log/myapp}"

加了 set -e 仍然不会退出的六种情况

这是本篇最该记住的一张表。凡是踩过「明明写了 set -e 却没停」的人，原因都在这六行里。

场景示例为什么不退出怎么写才对
作为 if / while / until 的条件if grep -q err f; then ...退出码被当作条件值消费，这是语言设计本就该这样写，不要指望它退出
短路运算符左侧check_disk && deploy左侧失败只是让右侧不执行要退出就写 check_disk || die "disk full"
被感叹号取反! grep -q x f取反后整体退出码变成 0明确用 if ! grep -q x f; then
管道中非最后一段curl -sf "$u" | tar -xz管道退出码默认只取最后一段加 set -o pipefail，或查 ${PIPESTATUS[0]}
local / export / declare 前缀赋值local out=$(false)前缀命令自身退出码为 0，覆盖了替换结果拆两行：local out; out=$(false)（SC2155）
函数被放在条件位置调用my_func || rollback函数体内所有命令的 -e 整体失效，函数会跑到底函数内部显式写 || return 1

第五条和第六条是最常翻车的两条，因为它们看起来完全正常。local out=$(curl ...) 这一行里 local 本身是个命令，它的退出码永远是 0，curl 的失败被彻底吞掉；而「函数被条件调用则整个函数体豁免 -e」意味着你写的 deploy() 一旦用 deploy || rollback 调用，函数内部任何失败都不会中断它，它会一路跑到最后一行再返回。

引号与分词：不加引号的变量不是一个值

Shell 里最高频的 bug 来自一个被反复误解的事实：不加引号的变量不是「一个值」，而是一段待再次解析的文本。它会依次经历单词拆分（按 IFS 切）和路径名展开（*、?、[] 去匹配真实文件）。

所以文件名叫 my report.pdf 时，cp $file dest/ 实际执行的是三参数的 cp my report.pdf dest/；而一个内容恰好是 * 的变量不加引号，会被展开成当前目录的全部文件名。

写法变量展开单词拆分通配符展开典型后果
$var是是是带空格的路径被拆成多个参数；含星号时被展开成文件列表
"$var"是否否正确默认，绝大多数场景都该这么写
'$var'否否否原样字符串，写 awk 程序体、正则、sed 脚本时用它
$(cmd)—是是命令输出含空格立刻崩（SC2046）
"$(cmd)"—否否正确默认，注意末尾换行会被去掉
${arr[@]} 不加引号是是是数组元素含空格就串味，数组必须写 "${arr[@]}"

$@ 与 $* 的差异只在加了双引号之后才显现，而这个差异决定了「参数转发」写得对不对。假设脚本收到两个参数 a b 和 c d：

形态展开成几个词具体结果适用场景
"$@"2保持为 a b 与 c d 两个参数转发参数的唯一正确写法，包装命令必用
$@4a / b / c / d几乎没有正确用途
"$*"1用 IFS 首字符连成 a b c d 一个词拼日志消息、拼提示文本
$*4同 $@ 不加引号无

关于 IFS：默认值是空格、Tab、换行三个字符。很多脚本模板会写 IFS=$'\n\t' 把空格移出分隔符集合，让「按行处理」更安全。这是个有用的补丁，但它不能替代加引号——真正的解法永远是 "$var"，而且 IFS 是全局状态，改了它会影响后面所有 read 和展开行为。

错误处理与清理：trap 是 Shell 唯一的 finally

trap ... EXIT 是脚本里唯一可靠的清理点：不管脚本正常结束、被 -e 打断、还是收到可捕获的信号，它都会跑。下面这段头部模板可以整段抄走。

#!/usr/bin/env bash
# 生产脚本头模板
set -Eeuo pipefail
# -E 等价 errtrace：让 ERR trap 在函数与子 shell 里也生效
# 不加 -E 的话，函数内部失败只会静默退出，打不出行号——这是最影响排障效率的一个开关

SCRIPT_DIR=$(cd -- "$(dirname -- "${BASH_SOURCE[0]}")" && pwd -P)
readonly SCRIPT_DIR
# 两个减号做选项终止符，防止路径以减号开头；pwd -P 解析软链拿到真实绝对路径

log() { printf '[%s] %s\n' "$(date -u +%Y-%m-%dT%H:%M:%SZ)" "$*" >&2; }
die() { log "FATAL: $*"; exit 1; }
# 日志一律写 stderr：stdout 要留给「脚本的真正输出」，否则无法被管道消费

on_err() {
  local code=$?     # 必须是函数第一行，之后任何命令都会覆盖上一条退出码
  log "ERROR at line ${BASH_LINENO[0]}: ${BASH_COMMAND} (exit=${code})"
  exit "$code"      # 保留原始退出码，不要统一成 1，上游重试逻辑依赖它
}
trap on_err ERR

# 工作目录建在目标分区，方便后面做同分区原子 mv
WORK_DIR=$(mktemp -d "${TMPDIR:-/tmp}/deploy.XXXXXX")
cleanup() { rm -rf -- "$WORK_DIR"; }
trap cleanup EXIT

# 依赖预检放最前面，别跑到第 80 行才发现机器上没有 jq
for cmd in jq curl rsync flock; do
  command -v "$cmd" >/dev/null 2>&1 || die "missing dependency: $cmd"
done

: "${DEPLOY_ENV:?DEPLOY_ENV is required}"
log "start deploy env=${DEPLOY_ENV} work=${WORK_DIR}"

但正在等待的外部命令会先跑完
信号 / 伪信号触发时机能否捕获典型用途必须知道的坑
EXIT脚本以任何方式退出—删临时文件、释放锁在 (...) 子 shell 里不继承，子 shell 内的资源不会被清
ERR命令失败且 -e 会导致退出时—打印 BASH_LINENO 与 BASH_COMMAND不加 set -E 时函数内不生效
INT（2）终端按下中断键能提示后以 130 退出只发给前台进程组，后台子进程收不到
TERM（15）kill 默认发送能优雅停机handler 不会打断正在执行的外部命令
KILL（9）kill -9不能—清理逻辑一定不会执行，别把它当常规手段
HUP（1）终端断开能重载配置nohup 与 disown 会屏蔽它

第二个坑值得单独强调：trap handler 不会打断正在执行的外部命令。你 kill 一个正在跑 30 秒 rsync 的脚本，Bash 要等 rsync 自己结束才会执行 handler。所以长时间阻塞的命令该套 timeout 60 rsync ...，而不是指望信号能立刻生效。

幂等与可重入：生产脚本一定会被跑第二次

无人值守的脚本必然被重复执行：cron 上一轮没跑完这一轮又进来、CI 自动重试、人工手动补跑。所以判断一个脚本能不能上生产，问一句就够了——连续跑三次，结果一样吗？

操作非幂等写法第二次执行会怎样幂等写法
建目录mkdir /data/app报 File exists，配 -e 直接中断mkdir -p /data/app
追加配置行echo "$line" >> conf重复追加，文件越跑越长先 grep -qxF "$line" conf 再追加，或整文件渲染后替换
替换文件rm f; cp new f中间有一段文件不存在的窗口cp new f.tmp && mv f.tmp f
建软链ln -s target link报 File existsln -sfn target link
建账号useradd app返回非零直接中断id -u app >/dev/null 2>&1 || useradd app
删文件rm /tmp/x文件不存在则失败rm -f /tmp/x
下载解压每次全量下载后直接解到目标目录半包可能覆盖出损坏的目录下到临时文件校验 sha256，解到临时目录，最后整目录 mv
 
#!/usr/bin/env bash
set -Eeuo pipefail

CONF=/etc/myapp/app.conf
LOCK=/var/lock/myapp-render.lock

# flock 防重入：cron 上一轮还没跑完这一轮又进来时，直接跳过而不是并发写同一个文件
# 200 是文件描述符编号（挑一个没被占用的）；-n 拿不到锁立刻返回，要排队等就用 -w 30
exec 200>"$LOCK"
flock -n 200 || { echo "another run in progress, skip" >&2; exit 0; }

# 1) 临时文件必须建在「目标文件所在目录」：跨文件系统的 mv 不是原子操作
tmp=$(mktemp -- "${CONF}.XXXXXX")
trap 'rm -f -- "$tmp"' EXIT

# 2) 用 envsubst 从模板渲染，而不是在 shell 里手工拼字符串
envsubst < /etc/myapp/app.conf.tmpl > "$tmp"

# 3) 先校验再替换：渲染出错的配置绝不能覆盖线上（正经服务都有类似的 -t 开关）
myapp --config "$tmp" --check-only || { echo "bad config, keep old one" >&2; exit 1; }

# 4) 保留原权限。chmod --reference 是 GNU 扩展，BSD 与 macOS 上没有，所以留一条兜底
chmod --reference="$CONF" "$tmp" 2>/dev/null || chmod 0644 "$tmp"

# 5) 同分区 mv 走 rename 系统调用，对读者是原子的：只会看到旧文件或新文件
mv -- "$tmp" "$CONF"
trap - EXIT   # 文件已经被 mv 走，取消清理 trap，否则会删掉刚上线的新文件

systemctl reload myapp

「原子替换」这一点值得反复说：同一文件系统内的 mv 走的是 rename(2)，对读者没有中间态；而 rm old; cp new old 中间存在一个文件不存在的窗口，服务恰好在这时 reload 就会启动失败。跨分区的 mv 会退化成「拷贝加删除」，原子性彻底消失——这就是为什么临时文件要建在目标目录里，而不是图方便丢到 /tmp。

什么时候该换掉 Shell

Shell 的优势是「调进程、搬文件」的最短路径，劣势是没有类型、没有命名空间、没有异常、只有一维数组。一旦需求越过某条线，它的维护成本会迅速超过 Python 或 Go。

出现这个信号Shell 的具体成本建议
行数超过 150 到 200没有模块化和类型，改一行不敢动换 Python
要给 JSON 或 YAML 建模只有一维数组和关联数组，嵌套只能靠反复调 jq换 Python
需要并发加超时加重试后台加 wait 拿不到单个任务的失败原因，没有原生超时换 Go 或 Python

顺带说一句方向相反的判断：部署和流水线里的编排逻辑不要越写越厚。真正的流水线阶段划分、部署策略与回滚，本站 devops/cicd/ 有专篇；容器与 K8s 场景的排障命令在 devops/kubernetes/。Shell 在这些场景里只该是薄薄的粘合层。

shellcheck 必须进 CI

Shell 没有编译器，shellcheck 就是它的编译器。它能稳定发现人眼最容易漏掉的那几类问题，而这些问题恰好最容易演变成事故。

告警码它在说什么放过之后的真实后果
SC2086变量引用未加双引号带空格路径崩、变量含通配符时被意外展开
SC2046命令替换未加双引号同上，且更难发现，因为输出内容运行时才确定
SC2155local x=$(cmd) 掩盖了退出码set -e 对这一行完全失效
SC2164cd 之后没有判断是否成功后续的 rm -rf ./* 在错误的目录里执行
SC2115删除路径中的变量可能为空rm -rf "$DIR/" 在 DIR 为空时删根
SC2181用上一条退出码变量代替直接判断中间插入任何命令都会让判断失效
SC2012用 ls 的输出做程序化处理文件名含空格或换行时行为完全不可预期
 
# .github/workflows/shell-lint.yml
name: shell-lint
on: [push, pull_request]
jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: shellcheck
        run: |
          sudo apt-get update && sudo apt-get install -y shellcheck
          # -S warning：info 级别太吵，先把 warning 与 error 卡死，存量再逐步收敛
          # -x：跟随 source 进来的文件一起分析
          # -e SC1091：CI 里 source 的外部文件通常不存在，屏蔽这条误报
          # -print0 配 -0：文件名含空格也不会出错
          find . -name '*.sh' -print0 | xargs -0 -r shellcheck -S warning -x -e SC1091
      - name: shfmt
        run: |
          go install mvdan.cc/sh/v3/cmd/shfmt@latest
          # -d 只输出差异不改文件，有差异就返回非零；-i 2 两空格缩进；-ci 缩进 case 分支
          "$(go env GOPATH)"/bin/shfmt -d -i 2 -ci .

配合 shfmt 统一格式之后，代码评审就能只讨论逻辑，而不是反复提醒别人「这里少个引号」。

最容易踩的坑

❌
这些坑每一条都对应过真实事故
  • local out=$(cmd) 让 set -e 对该行完全失效，因为 local 的退出码是 0；必须拆成 local out; out=$(cmd) 两行。
  • 函数一旦以 my_func || handle 或放在 if 条件里被调用，函数体内所有命令的 -e 整体豁免，函数会一路跑到最后一行。
  • 只写 set -e 不写 pipefail：curl -sf "$url" | tar -xz 里 curl 失败会被彻底静默，你得到一个空目录和 0 退出码。
  • 不写 set -E 时 trap ... ERR 在函数里不生效，排障时只能看到「脚本退出了」却不知道死在哪一行。
  • set -u 下访问空数组，在 Bash 4.3 及更早版本会报 unbound variable；兼容写法是 "${arr[@]+"${arr[@]}"}"。
  • rm -rf "$DIR/" 里 DIR 为空就等于 rm -rf /；危险操作一律用 "${DIR:?}" 让空值直接报错。
  • 临时文件建在 /tmp 再 mv 到 /data：跨文件系统，mv 退化成拷贝加删除，不再有原子性。
  • trap cleanup EXIT 在 (...) 子 shell 里不会继承，子 shell 内创建的临时文件不会被清理。
  • kill 脚本时 trap handler 不会打断正在执行的外部命令，长阻塞命令要套 timeout，否则优雅停机等于不会发生。
  • 用 mv new old 做完原子替换后忘记 trap - EXIT，EXIT 清理逻辑会把刚上线的新文件删掉。
  • 把密码写成 mysql -pxxx 或 curl -u user:pass，同机任何用户 ps 一下就能看到，history 里也留了一份。
  • cd 不判断失败，紧接着的 rm -rf ./* 就在你当前所在的目录里执行——这是最经典的删库方式。
