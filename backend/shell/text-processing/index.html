文本处理三件套的正确用法

🏷️ 文本处理,grep,sed,awk

文本处理是命令行里最容易「会用」但最难「用对」的一块。能跑出结果不难，难的是让它在日志格式变了、字段里出现空格、机器从 Linux 换成 macOS、某天一条都没匹配上的时候，仍然给出正确结果而不是静默的错误答案。

这篇不复述选项手册，只讲三件事：什么任务该交给哪个工具、每个工具的边界在哪里、哪些写法在生产里一定会出事。管道与重定向的机制、变量在子进程里丢失这类问题在 ../internals/；引号与分词、参数展开在 ../core/。

先定选择原则：越简单的工具越该优先

一条经验法则，按它选工具几乎不会错：能用 grep 就不用 sed，能用 sed 就不用 awk，超过十行的 awk 就该换 Python。理由不是性能洁癖，而是可读性与可维护性：越简单的工具，语义越窄，别人接手时误读的空间越小。

任务首选为什么不用更重的工具什么时候必须升级

grep：选行，以及那个会让脚本静默退出的返回码

grep 的功能没什么可讲的，值得讲的是它的退出码语义：找到至少一行返回 0，一行都没找到返回 1，真出错（文件不存在、正则非法）返回 2。也就是说「没匹配」在 grep 看来是正常结果，但对 set -e 来说是失败。

这条规则制造了一类极难发现的事故：统计脚本平时都对，某天日志里恰好没有 ERROR，脚本在 count=$(grep -c ERROR app.log) 这一行悄无声息地退出，后面的汇总和告警全都没跑，而退出码看起来「就是失败了」，没人知道失败在哪。

选项作用什么时候必须用注意
-q只要退出码，找到即停止所有「判断存在性」的场景配 if 用，不会触发 set -e
-F模式按固定字符串处理匹配 IP、路径、版本号比正则快，且不怕点与星号
-x -f file整行匹配，模式来自文件用几万个 ID 批量筛日志比循环调 grep 快几个数量级
-r --include --exclude-dir递归并限定范围在代码库里搜符号不限定范围会去扫 vendor 与 node_modules
-o只输出匹配到的片段提取 IP、trace id、版本号配 -E 写清楚边界，否则会贪婪
-PPCRE，支持 \d 与断言本地临时分析脚本里别用：BSD grep 与部分发行版没有
-m1命中一次就停在几十 GB 的日志里找首次 panic省掉大量无用 IO
-c输出匹配行数做计数无匹配时输出 0 但退出码仍是 1
LC_ALL=C关掉 UTF-8 校对处理大文件纯 ASCII 模式下可快数倍

顺便纠正一个常见说法：「grep -E 比 grep 快」。两者用的是同一个引擎，差别只在元字符要不要转义；真正影响速度的是有没有用 -F、有没有限定搜索范围、locale 是不是 UTF-8。

# ① 严格模式下最危险的一行：grep 没匹配到返回 1，脚本会静默退出
count=$(grep -c ERROR app.log)           # 日志干净的那天，这一行直接把脚本干掉
count=$(grep -c ERROR app.log || true)   # 对：把「没匹配」当作正常结果
if grep -q ERROR app.log; then :; fi     # 更好：只做判断就用 -q，找到即返回不读完文件
# 要严格区分三种情况时，显式取退出码：0 有匹配，1 无匹配，2 才是真错误
set +e; out=$(grep -n ERROR app.log); rc=$?; set -e
(( rc <= 1 )) || { echo "grep failed" >&2; exit 2; }

# ② 固定字符串远快于正则，而且不必操心元字符
grep -F '1.2.3.4' access.log             # IP 里的点不会被当成通配符
grep -Fxf ids.txt all.txt                # -f 从文件读模式表，-x 整行匹配，批量筛选专用

# ③ 递归搜代码：限定范围能把耗时降一个量级
grep -rn --include='*.go' --exclude-dir=vendor 'ctx context.Context' .

# ④ 只要匹配的那一段，不要整行
grep -oE '[0-9]{1,3}(\.[0-9]{1,3}){3}' app.log | sort -u

# ⑤ -P 是 PCRE，支持 \d 与断言，但很多发行版没编译它，macOS 自带的 BSD grep 直接报错
grep -P '(?<=trace_id=)[a-f0-9]{32}' app.log   # 脚本里不要依赖，用 -oE 改写

# ⑥ 大文件里找到就够了，别读完
grep -m1 'panic' huge.log

# ⑦ 上下文与文件名控制
grep -n -C3 'Out of memory' /var/log/messages
grep -rl 'DeprecatedAPI' src/            # 只列文件名，不打内容

# ⑧ 速度：关掉 locale。UTF-8 校对在大文件上代价很高，日志过滤根本不需要它
LC_ALL=C grep -F 'ERROR' huge.log

sed：流编辑，以及跨平台脚本第一大地雷

sed 的模型很简单：逐行读入模式空间，对它执行脚本里的命令，默认在行末自动打印，然后读下一行。另有一个保持空间可以暂存内容，这是它能做少量跨行处理的原因——但也仅止于「少量」。

sequenceDiagram participant IN as 输入流 participant PS as 模式空间 participant HS as 保持空间 participant OUT as 输出流 IN->>PS: 读入一行 并自动去掉行尾换行 Note over PS: 按书写顺序执行脚本里的每条命令 PS->>HS: h 覆盖保存 或 H 追加保存 HS->>PS: g 覆盖取回 或 G 追加取回 PS->>PS: x 交换两个空间的内容 IN->>PS: N 追加读入下一行 用于有限的多行匹配 PS->>OUT: 一轮结束自动打印 加了 -n 则只有 p 才输出 Note over PS,OUT: d 删除模式空间并立刻开始下一轮 后面的命令不再执行

真正的坑不在语法，在实现差异。sed -i 是我见过最高频的跨平台事故：同一行命令在 Linux 的 CI 上跑得好好的，同事在 macOS 上执行会把文件改成一团糟，或者莫名多出一堆备份文件。

能力GNU sed（多数 Linux）BSD sed（macOS）兼容写法
原地修改sed -i 's/a/b/' f，后缀可选sed -i '' 's/a/b/' f，后缀必填统一写 -i.bak 再删备份，或封装函数
扩展正则-E 与 -r 都行只有 -E一律写 -E
空白字符类支持 \s \t不支持，会当字面量用 [[:space:]] 与真实制表符
追加与插入sed '2a text'必须换行续写，写法极丑这种需求改用 awk 或 Python
按步长选行支持 0~2 这类 GNU 扩展不支持用 awk 'NR%2==0'
零分隔输入-z不支持换 tr 或 Python
就地改配置两者都有中断后文件半残的风险写临时文件再同分区 mv 原子替换
 
# sed -i 是跨平台脚本第一大坑：两个实现对 -i 的参数规则正好相反
#   GNU sed：备份后缀可选     sed -i    's/a/b/' f     写 sed -i '' ... 会把空串当脚本
#   BSD sed：后缀必须紧跟      sed -i '' 's/a/b/' f     写 sed -i  s/a/b/ f 会把脚本当后缀

# 兼容写法一：统一给后缀，两边行为一致，事后删备份（最省事）
sed -i.bak 's/old/new/g' app.conf && rm -f app.conf.bak

# 兼容写法二：探测一次并封装（脚本里只调 sedi，推荐）
if sed --version >/dev/null 2>&1; then
  sedi() { sed -i "$@"; }        # GNU
else
  sedi() { sed -i '' "$@"; }     # BSD / macOS
fi
sedi 's/old/new/g' app.conf

# 兼容写法三：不原地改，写临时文件再同分区原子替换（改线上配置首选，见 ../ 主干篇）
tmp=$(mktemp -- 'app.conf.XXXXXX')
sed 's/old/new/g' app.conf > "$tmp" && mv -- "$tmp" app.conf

# 分隔符不必是斜杠：处理路径时换成竖线或井号，省掉一堆反斜杠
sed 's|/usr/local/bin|/opt/app/bin|g' env.sh
sed 's#http://old.example.com#https://new.example.com#g' nginx.conf

# 地址范围才是 sed 的强项，比 grep 灵活
sed -n '10,20p' f                       # 只打印第 10 到 20 行
sed -n '/BEGIN CERTIFICATE/,/END CERTIFICATE/p' bundle.pem   # 两个正则之间的整段
sed '1d; $d' f                          # 删首行与末行
sed '/^[[:space:]]*#/d; /^$/d' app.conf # 去注释与空行；这里不用 \s 因为 BSD 不认
sed -E 's/([0-9]{4})-([0-9]{2})-([0-9]{2})/\3-\2-\1/' dates.txt  # -E 两边都有，别用 GNU 专属的 -r
sed '0~2d' f                            # GNU 扩展：删偶数行。用了它就等于放弃跨平台

还有一条边界要明确：sed 不适合多行与嵌套结构。模式空间一次只有一行，跨行要靠 N、D、P 和保持空间手工搭状态机，写出来的东西三天后自己都读不懂。遇到「把 XML 里某个标签整块替换掉」这类需求，直接换语言。

awk：字段模型与关联数组

awk 的心智模型只有两层：记录（默认按换行切，由 RS 控制）和字段（默认按空白切，由 FS 控制）。程序体是一串「模式 加 动作」，对每条记录依次匹配。

stateDiagram-v2 [*] --> B B --> R R --> S: 还有记录 R --> E: 输入耗尽 S --> P P --> A: pattern 为真 P --> R: pattern 为假 直接跳过 A --> R E --> [*] B: BEGIN 块 只跑一次 设置 FS 与 OFS 打印表头 R: 读入下一条记录 按 RS 切分 NR 与 FNR 各自递增 S: 按 FS 切成字段 同时得到字段数 NF P: 用每条规则的 pattern 判断这条记录要不要处理 A: 执行 action 通常往关联数组里累加 E: END 块 只跑一次 遍历数组 输出汇总
变量含义典型用法容易错的地方
$0整条记录原样输出、整行匹配给字段赋值会导致 $0 用 OFS 重建
$1 ... $NF第 n 个与最后一个字段print $NF 取末列$NF-1 是「末列的值减一」，倒数第二列要写 $(NF-1)
NF当前记录字段数过滤格式异常的行行尾多空格会让 NF 变化
NR / FNR累计行号 / 当前文件内行号NR==FNR 做双文件处理单文件时两者相等，容易误以为等价
FS / OFS输入 / 输出分隔符-F, -v OFS='\t'改了 OFS 不重建 $0 就不生效
RS / ORS记录分隔符RS='' 按空行分段读按段读时 FS 会额外把换行当分隔
关联数组键为任意字符串cnt[$9]++ 分组计数for (k in a) 顺序未定义，必须再排序
 
# ① awk 最值钱的用法：关联数组一次扫完做分组统计（Nginx combined 第 9 列是状态码）
awk '{cnt[$9]++} END {for (k in cnt) printf "%8d  %s\n", cnt[k], k}' access.log | sort -rn
#    ^^^^^^^^^^^ 键是状态码，值无需初始化，第一次自增即从 0 开始
#                 ^^^ END 在读完最后一行后执行一次
#                      ^^^^^^^^^^^^^^^ for-in 的遍历顺序是未定义的，所以必须再 sort

# ② 分组求和并排序：按接口统计总耗时与平均耗时（假设 $7 是 URI，最后一列是毫秒）
awk '{sum[$7]+=$NF; n[$7]++} END {for (k in sum) printf "%10.1f %8d %s\n", sum[k], n[k], k}' \
  access.log | sort -rn | head -20
# 注意：算平均要自己维护计数，awk 没有内置聚合；除法前判断 n 不为 0 才安全

# ③ 分位数：先排序再按下标取，比装 datamash 更通用（代价是把数据读进内存）
awk '{print $NF}' rt.log | sort -n \
  | awk '{a[NR]=$1} END {printf "n=%d p50=%s p95=%s p99=%s\n", NR, a[int(NR*0.50)], a[int(NR*0.95)], a[int(NR*0.99)]}'

# ④ 按时间窗口聚合：Nginx 的 $4 形如 [10/Oct/2026:13:55:36，按冒号切出小时与分钟
awk '{split($4, t, ":"); key = t[2] ":" t[3]; c[key]++} END {for (k in c) print k, c[k]}' access.log | sort

# ⑤ 双文件处理：NR==FNR 只在读第一个文件时成立，这是 awk 最有用的惯用法
awk 'NR==FNR {seen[$1]=1; next} !($1 in seen)' known_ids.txt all_ids.txt   # 差集：在后者不在前者
awk 'NR==FNR {name[$1]=$2; next} {print $0, name[$1]}' users.tsv events.tsv  # 用第一份文件补字段

# ⑥ 只用字段就够时不要起 awk：cut 更快，管道更短
cut -d, -f1,3 data.csv          # 但 cut 不认带引号的 CSV，字段里有逗号就错

# ⑦ 输出格式：print 用 OFS 拼接，printf 才能控制宽度与小数位
awk -F'\t' -v OFS=, '{print $2, $1}' in.tsv > out.csv

最后给一条硬边界：awk 程序体超过十行就该换 Python。awk 只有一维关联数组（多维靠拼接键模拟）、没有真正的数据结构、字符串函数有限、调试基本只能靠打印。一行到三行的提取与聚合它无可替代，写成几十行的报表程序则是纯粹的负债。

绝不要用正则解析结构化数据

这是本篇最该记住的一条。JSON、YAML、带引号的 CSV 都是嵌套或有转义规则的格式，而正则是线性的，能力上根本不匹配。危险之处在于它不会报错：管道照样返回 0，只是值错了，而错值往往会被当成真实数据送进下游。

格式用正则会死在哪里正确工具最小可用命令
JSON任意空白与换行、键顺序不保证、值里可含花括号与转义引号、数字带指数jqjq -r '.a.b[0].c' f.json
YAML缩进语义、锚点与别名、多文档分隔、同名键在不同层级yqyq '.spec.replicas' d.yaml
CSV字段内含逗号、引号、换行；cut 与 awk -F, 全部算错csvkit、duckdb、Python 的 csv 模块duckdb -c "select * from 'a.csv' limit 5"
HTML / XML属性顺序、自闭合、实体、嵌套同名标签专用解析库别在 shell 里做
日志（自定义纯文本）基本没问题，这才是三件套的主场grep / awkawk '{c[$9]++} END{for(k in c) print k, c[k]}'
 
# JSON 交给 jq。下面这些是覆盖九成场景的核心用法
jq -r '.items[] | select(.status == "failed") | .id' result.json     # 展开数组 过滤 取字段
jq -r '.data | map(.latency_ms) | add / length' bench.json           # map 加 add 求平均
jq -r '.[] | [.name, .cpu, .mem] | @tsv' pods.json | column -t       # 转 TSV 再对齐，便于肉眼看
jq -r '.metadata.labels.app // "unknown"' pod.json                   # 双斜杠给默认值，字段缺失不报错
jq -n --arg env prod --argjson n 3 '{env: $env, replicas: $n}'       # 构造对象：--arg 自动转义，别手拼字符串
jq -e '(.items | length) > 0' r.json >/dev/null                      # -e 把判断结果映射到退出码，配 if 用
jq -s 'add' part-*.json                                              # -s 把多个输入合并成一个数组
jq -r 'to_entries[] | "\(.key)=\(.value)"' config.json               # 对象转 key=value 行
kubectl get pods -o json | jq -r '.items[] | select(.status.phase != "Running") | .metadata.name'

# YAML 交给 yq，语法与 jq 同源，而且它的 -i 语义统一，没有 sed 的平台差异
yq '.spec.template.spec.containers[0].image' deploy.yaml
yq -i '.spec.replicas = 5' deploy.yaml

最容易踩的坑

❌
下面每一条都能复现
  • grep 无匹配返回 1，在 set -e 下会让脚本静默退出；取计数时必须补 || true，做判断时用 if grep -q。
  • grep -c 无匹配时会打印 0 却仍然返回 1，只看输出不看退出码的封装函数会漏判。
  • sed -i 在 GNU 上后缀可选、在 BSD 上后缀必填，同一条命令在 macOS 会把脚本当成备份后缀，把文件改成一团糟。
  • sed 里用 \s 与 \t：GNU 认，BSD 当字面量，结果是「没报错但一个都没替换」。
  • sed -r 是 GNU 专属，跨平台一律写 -E。
  • awk 里 $NF-1 是「最后一个字段的值减一」，倒数第二列必须写成 $(NF-1)。
  • for (k in arr) 的遍历顺序是未定义的，直接输出会得到每次都不一样的顺序，必须再 sort。
  • 单文件时 NR 与 FNR 相等，于是 NR==FNR 的双文件技巧在只传一个文件时会把所有行都当第一遍处理。
  • 用 cut -d, 或 awk -F, 处理带引号的 CSV，字段里一个逗号就把所有列错位，而且完全不报错。
  • uniq 只合并相邻重复行，不先 sort 就去不掉分散的重复。
  • 在 UTF-8 locale 下对大文件排序或过滤，比 LC_ALL=C 慢数倍，纯 ASCII 数据白付这个代价。
  • grep -P 在 macOS 自带的 BSD grep 和部分精简发行版上根本不存在，写进部署脚本必炸。
  • 用 xargs 不加 -r，上游一行都没输出时下游命令仍会被执行一次，sed -i 这类命令会作用在意料之外的目标上。
  • 拿 awk 算钱：它用双精度浮点，累加大量小数会有误差，金额统计该交给数据库或 Python 的定点类型。
