Shell 的执行机制：进程、重定向与信号

🏷️ Shell原理,性能优化

同一行命令，敲在交互终端里和写进脚本里，行为可能完全不同；同一段重定向，把两个方向调换位置，结果正好相反；同一个 kill，在裸机上能停掉服务，在容器里却只是把连接硬断。这些都不是零散的语法细节，而是同一件事的不同侧面：Shell 本质上是一个进程编排器，它做的全部工作就是把 fork、execve、dup2、pipe、wait、kill 这几个系统调用按你写的顺序组合起来。

理解这层机制的直接收益是：你能预测命令的行为，而不是靠试。本篇只讲执行机制。语法层面的参数展开、数组、[[ 与 ((、函数作用域在 ../core/；严格模式、trap 做清理、幂等与原子替换在 ../，这里涉及时只给结论并指路。

一条命令是怎么跑起来的

你敲下一个名字，Bash 并不会直接去 $PATH 里找。它有一个固定的六级查找顺序，前四级都在当前进程内完成、不产生任何新进程；只有落到后两级才需要 fork 加 execve。

这个顺序解释了几个常见现象。脚本里 alias 默认不展开，所以文档里写 ll 别人照抄进脚本一定报错；函数优先于内建，所以有人定义了 cd() 做日志，后面所有 cd 都会走那个函数；而哈希表位于 PATH 之前，就是「我明明改了 PATH，怎么还在跑旧版本」的全部真相。

cd 必须是内建命令，这不是性能优化而是逻辑必然：工作目录是进程的属性，子进程改自己的工作目录对父进程毫无影响。如果 cd 是 /bin/cd，那它一定在子进程里执行，退出后你还在原地。同理 export、ulimit、umask、trap 也只能是内建的。这也顺带解释了为什么 ./setenv.sh 里的 export 出不来，必须 source。

# 判断一个名字究竟走哪条路，是排障第一步
type -a cd          # cd is a shell builtin
type -a echo        # 既是 builtin 又有 /usr/bin/echo，builtin 优先
type -t grep        # 输出 file，说明是外部命令
command -v jq       # 脚本里做依赖预检用这个：不受 alias 干扰，找不到时返回非零

# 「改了 PATH 却还在跑旧版本」：Bash 把上次找到的绝对路径缓存进了哈希表
hash                        # 看缓存了哪些命令、各命中多少次
export PATH=/opt/python3.12/bin:$PATH
python3 -V                  # 仍是旧版本——命中了缓存，PATH 根本没被重新查
hash -r                     # 清空整张表；只想删一条用 hash -d python3
python3 -V                  # 现在才是新版本

# 绕过别名与函数，直接调到「真身」
builtin cd /tmp     # 强制用内建 cd，忽略同名函数（有人重定义 cd 做日志是常见坑）
command ls          # 忽略 alias 与函数，按正常查找顺序找
\ls                 # 反斜杠只能绕开 alias，绕不开函数
enable -n echo      # 临时禁用内建 echo，让它落到 /usr/bin/echo（测跨平台行为时有用）

重定向的本质是文件描述符复制

每个进程都有一张文件描述符表，0、1、2 分别约定为标准输入、标准输出、标准错误。重定向做的事只有一件：在 execve 之前，把表里某个槽位改指向别处，底层就是 dup2。程序自己完全不知道这件事发生过，它照样往 1 号描述符写。

由此得到一条必须记住的规则：重定向从左到右依次生效，每一步复制的是「执行到这一步时」的指向，而不是最终指向。这就是 cmd >file 2>&1 和 cmd 2>&1 >file 天差地别的原因。

sequenceDiagram participant S as 子进程的 fd 表 participant T as 控制终端 participant F as 日志文件 Note over S,F: 写法一 先改 fd1 再让 fd2 跟随 S->>F: 第一步 fd1 指向日志文件 S->>F: 第二步 fd2 复制 fd1 当前目标 同样指向日志文件 Note over S,F: 结果 正常输出与报错都进文件 Note over S,T: 写法二 顺序颠倒 S->>T: 第一步 fd2 复制 fd1 当前目标 此时 fd1 仍是终端 S->>F: 第二步 fd1 才改指向日志文件 fd2 不会跟着动 Note over S,T: 结果 报错留在终端 日志里只有正常输出
写法展开后的实际效果适用场景坑
cmd >ffd1 指向 f，以 O_TRUNC 打开只要正常输出报错还在终端，CI 里容易漏掉
cmd >>ffd1 指向 f，以 O_APPEND 打开多进程共写一个日志单行超过管道缓冲仍可能交错
cmd >f 2>&1两个 fd 指向同一个打开文件，共享偏移量最常用的全量落盘顺序不能反
cmd 2>&1 >ffd2 留在终端，fd1 进文件几乎没有正当用途被当成上一条的等价写法是高频事故
cmd &>f等价于第三条Bash 脚本里的简写POSIX sh 与 dash 不支持
cmd 2>&1 | less先建管道再复制 fd2，报错也进管道翻看混合输出写成 cmd | less 2>&1 则无效
exec 1>>f 2>&1改当前 shell 自己的 fd 表，此后所有命令继承脚本级日志接管之后想输出到终端必须先备份 fd
<(cmd)启动子进程，把它的 stdout 暴露成 /dev/fd 下的路径喂给只认文件名的命令是 Bash 扩展，且不能对它做 seek
>(cmd)反向：得到一个可写路径，写入的数据进子进程 stdin一份输出分发给多个消费者主进程退出时子进程可能还没写完
 
# 重定向从左到右依次生效，每一步都是一次 dup2，复制的是「当时」的指向
cmd >out.log 2>&1         # ① fd1 指向 out.log ② fd2 复制 fd1 → 两者都进文件（正确）
cmd 2>&1 >out.log         # ① fd2 复制当时的 fd1，也就是终端 ② fd1 才改道文件 → 报错仍在终端
cmd &>out.log             # Bash 专有简写，等价于第一种；POSIX sh 没有，写 #!/bin/sh 时别用
cmd >out.log 2>err.log    # 分开落盘，排障时最好用：正常输出与报错不混在一起
cmd >/dev/null 2>&1       # 全丢；这等于连有用的输出一起丢掉，别当成「静默运行」的默认写法
cmd 2>/dev/null           # 只丢报错，保留正常输出

# 截断与追加的区别在打开文件时的标志位，不在 shell
: >file                   # O_TRUNC：清空但保留 inode 与权限，比 rm 再 touch 安全
: >>file                  # O_APPEND：多进程同时追加短行不会互相撕裂

# 一个高频误解：下面两条不等价
sudo echo x > /root/f     # 错：重定向由当前 shell 完成，普通用户仍无权限写，sudo 白加了
echo x | sudo tee /root/f >/dev/null   # 对：写文件的动作交给以 root 运行的 tee

把这些能力组合起来，就有了两个工程上很实用的模式：用 exec 一次性接管整个脚本的输出，以及用进程替换给只接受文件名参数的命令喂流。后者是进程替换相对管道的核心优势——diff、comm、join 需要两个输入，而管道只能给一个。

#!/usr/bin/env bash
set -Eeuo pipefail

LOG="/var/log/mytask/$(date -u +%Y%m%dT%H%M%SZ).log"
mkdir -p -- "$(dirname -- "$LOG")"

# exec 不带命令时只修改当前 shell 的 fd 表，一次性接管整个脚本的输出，
# 比给每条命令都挂 >>"$LOG" 2>&1 可靠得多（漏挂一条就丢一段日志）
exec 3>&1                 # 先把原始 stdout 备份到 fd 3，后面还要跟人说话
exec 1>>"$LOG" 2>&1       # 顺序不能反：先改 fd1，再让 fd2 跟随

echo "[$(date -u +%FT%TZ)] task start"    # 进日志
printf 'started, log=%s\n' "$LOG" >&3     # 进终端

# 变体：既要落盘又要终端可见时，用进程替换喂 tee，而不是在每行后面接管道
# exec 1> >(tee -a "$LOG" >&3) 2>&1

# 进程替换的真正价值：给「只认文件名参数」的命令喂一个流
diff <(ssh web-01 'md5sum /opt/app/bin/server') <(ssh web-02 'md5sum /opt/app/bin/server')
comm -13 <(sort -u expected.txt) <(sort -u actual.txt)    # 只在 actual 里多出来的行
join -t, <(sort -t, -k1,1 users.csv) <(sort -t, -k1,1 orders.csv)

# /dev/stdin 让「只认文件」的命令读管道：两个文件参数里有一个来自管道时特别有用
curl -sS https://example.com/ids.txt | grep -Fxvf /etc/allowlist /dev/stdin

管道：每一段都是独立子进程

a | b | c 不是「a 跑完给 b」，而是 Bash 先用 pipe 建好两对描述符，然后 fork 出三个子进程同时运行，靠内核管道缓冲区（Linux 默认 64KB）做流控：写满了写端阻塞，读空了读端阻塞。所以 tail -f | grep 能持续输出，而不是等 tail 结束。

但「每段都是子进程」立刻带来一个必须知道的后果：管道里的变量赋值，外面看不到。这是 Shell 排错里最常被误判为「Bash 有 bug」的现象。

开启 lastpipeshopt -s lastpipe 且 set +m需要 Bash 4.2 以上，交互式 shell 里不生效能用但依赖多，只适合脚本

压根不用 shell 变量把统计整个交给 awk 或 grep -c无最快也最可靠，能这样就这样

第二个高频困惑是加了管道就看不到实时输出。这不是 Shell 的问题，是 C 标准库的行为：程序检测到 stdout 不是终端时，会从行缓冲切成 4KB 全缓冲，攒满才吐。解决办法是让上游改回行缓冲：grep --line-buffered、sed -u、awk 里调 fflush()，或者通用地套 stdbuf -oL。注意 stdbuf 靠 LD_PRELOAD 改 libc，对自己管缓冲的程序（比如 Go 写的工具）无效，这时只能用 unbuffer 伪造一个伪终端。

管道的退出码默认只取最后一段，这也是 set -e 失效的经典场景之一；要取各段退出码用 PIPESTATUS 数组，而 set -o pipefail 的精确语义与其他五种 set -e 例外在 ../ 有完整推演，这里不重复。

#!/usr/bin/env bash
set -Eeuo pipefail

# ① 管道里的变量赋值丢失：错误写法
total=0
grep ' 500 ' access.log | while read -r line; do total=$((total + 1)); done
echo "$total"     # 0——自增发生在管道最后一段的子进程里

# ② 修法一（首选）：进程替换，循环体留在当前 shell
total=0
while read -r line; do total=$((total + 1)); done < <(grep ' 500 ' access.log)
echo "$total"     # 正确

# ③ 修法二：lastpipe 让管道最后一段在当前 shell 执行
#    限制：必须先关作业控制，且交互式 shell 里不生效，所以只适合脚本
shopt -s lastpipe
set +m
total=0
grep ' 500 ' access.log | while read -r line; do total=$((total + 1)); done
echo "$total"

# ④ 修法三：根本不需要 shell 变量——让一个进程数完
total=$(grep -c ' 500 ' access.log)

# ⑤ 取管道各段退出码：PIPESTATUS 是数组，会被下一条命令覆盖，必须立刻整体复制
curl -sS "$url" | gunzip | jq -e '.items' >/dev/null
st=("${PIPESTATUS[@]}")
printf 'curl=%s gunzip=%s jq=%s\n' "${st[0]}" "${st[1]}" "${st[2]}"
(( st[0] == 0 )) || { echo 'download failed' >&2; exit 1; }

# ⑥ 「加了管道就看不到实时输出」：上游发现 stdout 不是终端，自动切成 4KB 全缓冲
tail -F app.log | grep --line-buffered ERROR      # grep 自带行缓冲开关
stdbuf -oL -eL myapp | tee run.log                # 通用做法：强制上游行缓冲
# stdbuf 靠 LD_PRELOAD 改 libc 缓冲策略，对自己管缓冲的程序（如 Go 写的工具）无效

子 shell 与当前 shell：什么会留下，什么会消失

「变量没传出来」「cd 没生效」「trap 没执行」这三类问题，答案全在同一张表里：判断这段代码跑在当前 shell 还是子进程里。

写法是否新进程变量与函数修改是否可见工作目录改动是否保留典型用途
{ cmds; }否是是只为分组重定向，不做隔离
( cmds )是，fork 出子 shell否否临时改目录或改 IFS 而不污染外部
$(cmds)是否，只拿 stdout否取命令输出
cmd &是否否后台任务，配 wait
管道每一段是否否流式处理
source x.sh否是是加载配置与函数库
./x.sh是，新的 Bash 进程否否独立执行脚本
exec cmd否，替换当前进程映像不再返回—entrypoint 末尾把 PID 交给应用

两个容易忽略的细节。第一，source 的隔离性为零：被 source 的脚本里一个 exit 会把你当前的 shell 一起关掉，一个 set -e 会改变你后续所有命令的行为，所以函数库文件里不要写 set 和 exit。第二，环境变量的继承是单向的一次性快照：子进程拿到的是父进程 export 过的变量的副本，之后双方各改各的，互不影响；没 export 的普通 shell 变量根本不会进这份副本。

还有一条：trap ... EXIT 不会被 ( ... ) 子 shell 继承，子 shell 内创建的临时文件不会被外层清理逻辑带走。

信号、进程组与 trap 的边界

信号是内核给进程的异步通知。工程上真正需要分清的就那么几个，以及它们各自「能不能被拦」。

信号编号默认动作能否捕获或忽略谁会发它脚本里该怎么应对
SIGTERM15终止能kill 默认、systemd stop、容器停止唯一应该实现优雅关闭的信号
SIGINT2终止能终端中断键，只发给前台进程组清理后以 130 退出
SIGHUP1终止能控制终端断开时发给会话首进程守护进程常借它重载配置
SIGQUIT3终止并转存能终端退出键Java 与 Go 会借它打全量栈
SIGKILL9立即终止不能人工兜底、OOM killer、宽限期结束清理一定不会执行，别当常规手段
SIGSTOP19暂停不能作业控制进程停在 T 状态，占着资源不释放

关于 trap，有一条限制必须知道：Bash 只在两条命令的间隙检查待处理信号。脚本正阻塞在一个外部命令上时收到 SIGTERM，handler 不会立刻执行，Bash 要等那个外部命令自己结束。所以「kill 了半分钟没反应」通常不是 trap 写错，而是它在等一个 rsync。可靠做法有两条：长阻塞命令一律套 timeout；需要能被中断的地方，让命令后台跑再 wait，因为 wait 是可被信号打断的内建命令。

另一个更隐蔽的坑是进程组。kill $pid 只发给那一个进程，它 fork 出的孙子进程会变成孤儿继续跑——这就是「脚本杀掉了但 java 进程还在占端口」的成因。要收掉一整棵树，得对进程组发信号，也就是 kill -TERM -- -$pgid 里那个负号；配合 setsid 让子进程自成进程组，这条路才走得通。

#!/usr/bin/env bash
set -Eeuo pipefail

# 目标：收到 TERM 时，把正在跑的子进程连同它的孙子进程一起干净收掉
child_pid=""

on_term() {
  echo "caught TERM, stopping child ${child_pid:-none}" >&2
  # 杀「整个进程组」要用负号 PID；只杀 child_pid 的话，它 fork 出的孙子进程会变孤儿
  [[ -n $child_pid ]] && kill -TERM -- "-$child_pid" 2>/dev/null || true
  wait || true          # 等子进程把清理做完，别立刻 exit
  exit 143              # 128 + 15，保留「被 TERM 终止」的语义给上游重试逻辑
}
trap on_term TERM INT

# setsid 让子进程自成进程组，上面的负号 PID 才有意义
setsid -w ./long_job.sh &
child_pid=$!

# 关键点：trap 不会打断正在执行的外部命令。
# 所以不要让一个跑一小时的命令占着前台，而是后台跑 + wait；
# wait 是可被信号打断的内建命令，信号才能立刻被处理。
wait "$child_pid"

# 超时控制：-k 表示先发 TERM，宽限 10 秒还不退就补 KILL
timeout -k 10s 5m rsync -a --delete ./dist/ web-01:/opt/app/dist/ || {
  code=$?
  # 124 = 超时被 TERM 掉；137 = 128+9，宽限期后被 KILL
  echo "rsync failed with $code" >&2
  exit "$code"
}

让进程活过终端：nohup、disown、setsid

这三个命令常被混用，但它们作用在不同层面：nohup 改的是信号处置，disown 改的是 shell 的作业表，setsid 改的是会话归属。

手段作用时机做了什么脱离会话输出处理什么时候用
nohup cmd &启动时把 SIGHUP 设为忽略否，仍在原会话stdout 是终端时自动追加到 nohup.out临时跑个批处理
disown -h %1启动后标记该作业不接收 shell 转发的 HUP否不管，需自己提前重定向已经跑起来了才想到要挂着
disown %1启动后直接从作业表移除，jobs 看不到否不管同上，但之后无法 wait 它

tmux 或 screen启动时进程跑在伪终端里，会话服务端常驻是保留可交互的滚动缓冲需要随时回去看、回去敲的长任务
systemd-run --user启动时作为临时单元托管，进 cgroup 与 journal是自动进 journald需要资源限制、日志归集、崩溃重启
flowchart TB S["要在远程机器上跑一个长任务"] --> Q1{"需要长期存活并在崩溃后自动重启"} Q1 -- 是 --> SYS["写成 systemd 单元 或用 systemd-run 临时托管"] Q1 -- 否 --> Q2{"过程中还需要回去交互或看滚屏"} Q2 -- 是 --> TM["tmux 或 screen 会话"] Q2 -- 否 --> Q3{"任务已经在前台跑起来了"} Q3 -- 是 --> D["先暂停 再 bg 转后台 再 disown -h"] Q3 -- 否 --> Q4{"需要自成进程组以便整组终止"} Q4 -- 是 --> SET["setsid 启动 并自行重定向输出"] Q4 -- 否 --> N["nohup 启动 并显式写明输出去向"]

一个实践建议：用 nohup 时别指望 nohup.out，它会落在当前目录、没有轮转、也没有时间戳。正确写法是自己指明去向，把标准输出与标准错误一起追加到带时间戳的日志文件里，并把日志路径打到终端上。

容器里的 PID 1：优雅关闭为什么从来没生效

这是执行机制在真实生产里最值钱的一条推论。容器里的第一个进程拿到 PID 1，它有两项特殊职责：接收编排器发来的停机信号，以及回收孤儿进程。而 CMD node server.js 这种 shell 形式的写法，实际执行的是 /bin/sh -c "node server.js"——PID 1 是 sh，应用只是它的子进程。

sequenceDiagram participant K as 编排器 participant SH as sh 占据 PID 1 participant APP as 应用进程 PID 7 Note over K,APP: shell 形式的启动命令 多出一层 sh K->>SH: 停机 向 PID 1 发送 SIGTERM SH-->>K: sh 没有 handler 自己直接退出 Note over APP: 应用从未收到信号 在处理请求中被硬断 K->>APP: 宽限期结束 容器整体收到 SIGKILL Note over K,APP: 改成 exec 形式后 应用自己就是 PID 1 K->>APP: SIGTERM 直达应用 APP-->>K: 停止接新请求 排空在途请求后正常退出

后果很具体：滚动更新时每批实例都会产生一批 5xx 或连接重置，而监控上看不出任何「进程崩溃」，因为退出码看起来正常。修法只有一句话——让应用成为 PID 1：用 exec 形式写启动命令，或者在 entrypoint 脚本的最后一行用 exec "$@" 把进程映像交给应用。

# ---- 反例：shell 形式的 CMD ----
# 实际执行 /bin/sh -c "node server.js"，sh 是 PID 1，node 是它的子进程。
# 编排器把 SIGTERM 发给 PID 1，sh 不处理也不转发，node 永远等不到停机信号。
# CMD node server.js

# ---- 正例一：exec 形式，应用直接成为 PID 1 ----
CMD ["node", "server.js"]

# ---- 正例二：必须用 entrypoint 做初始化时，脚本末尾一定要 exec ----
COPY entrypoint.sh /usr/local/bin/entrypoint.sh
ENTRYPOINT ["/usr/local/bin/entrypoint.sh"]
CMD ["node", "server.js"]

# ---- 正例三：应用自己会 fork 子进程时，用极小 init 兜住僵尸回收 ----
# docker run --init 等价于注入 tini；K8s 里没有这个开关，要自己打进镜像
# ENTRYPOINT ["/sbin/tini", "--", "/usr/local/bin/entrypoint.sh"]
#!/usr/bin/env sh
# entrypoint.sh —— 用 sh 写，以便在 alpine 这类精简镜像里通用
set -eu

# 初始化：渲染配置、等依赖就绪、做一次性迁移
envsubst < /etc/app/config.tmpl > /etc/app/config.yaml

# 最后一行必须是 exec：用应用的映像替换掉当前 shell 进程，
# 于是应用继承 PID 1，编排器发的 SIGTERM 直达应用本身。
# 漏掉 exec 的话 shell 会留在 PID 1 上 wait，信号被吞，优雅关闭彻底失效。
exec "$@"

第二项职责是僵尸回收。子进程退出后要由父进程 wait 才能释放内核里的进程表项，而孤儿进程会被托孤给 PID 1。真正的 init 会不断回收它们，但你的应用进程通常不实现这个循环，于是僵尸进程会在多进程模型下持续堆积，最终耗尽 pid 上限，表现是「跑几天以后就 fork 失败」。判断方法是进容器看进程状态里有没有大量 Z 状态。解决办法是加一层极小 init：docker run --init 会注入 tini，Kubernetes 里没有这个开关，需要自己把 tini 打进镜像当 ENTRYPOINT。

再往上一层，宽限期设置、preStop 钩子与就绪探针摘流量的先后顺序属于编排器语义，本站 devops/kubernetes/ 有专篇推演，这里不展开；精简镜像里缺少排障命令该怎么办，见 ../modern-unix/。

最容易踩的坑

❌
下面每一条都对应过真实故障
  • cmd 2>&1 >log 与 cmd >log 2>&1 不等价：前者报错留在终端，事故时日志里干干净净什么都查不到。
  • 管道最后一段是 while read 时，循环里累加的计数、设置的标志位、赋值的数组，出了管道全部归零。
  • 改了 PATH 或替换了二进制后不执行 hash -r，同一个 shell 会一直走旧路径，甚至报 No such file or directory。
  • sudo cmd > /root/x 里的重定向由你自己的 shell 完成，权限不够照样失败，别以为加了 sudo 就能写。
  • trap handler 不会打断正在执行的外部命令，脚本阻塞在 rsync 或 curl 上时，kill 要等它跑完才生效。
  • kill $pid 只杀一个进程，它 fork 出的孙子进程会变孤儿继续占着端口与文件锁；要整组收就得对负号 PID 发信号。
  • kill -9 不可捕获，trap、缓冲刷盘、锁文件释放全部跳过，下次启动可能因为残留锁直接起不来。
  • Dockerfile 写 CMD app run 这种 shell 形式，sh 成为 PID 1 吞掉 SIGTERM，滚动更新时每批实例都会撕断在途连接。
  • entrypoint 脚本最后一行漏掉 exec，shell 会一直留在 PID 1 上 wait，优雅关闭同样失效。
  • 多进程模型的容器不带 init，僵尸进程持续堆积直到撞上 pid 上限，表现是「过几天就 fork 失败」。
  • 加了管道之后看不到实时日志，是上游 libc 从行缓冲切到 4KB 全缓冲，不是程序卡住了；要用 stdbuf -oL 或 --line-buffered。
  • trap cleanup EXIT 不被 ( ... ) 子 shell 继承，子 shell 里建的临时目录不会被清理。
  • 被 source 的文件里一个 exit 就能把你的交互式 shell 直接关掉，函数库里只能用 return。
