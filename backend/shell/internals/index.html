Shell 底层原理

🏷️ Shell原理,性能优化

为什么要懂底层：Shell 性能瓶颈从哪来

同样是统计一个日志文件的行数，cat access.log | wc -l 和 wc -l < access.log 只差一个词，耗时却可能差几倍——因为前者多了一次 fork+exec。

我看下来，Shell 脚本慢，99% 不是因为 Bash 本身，而是因为你在循环里反复 spawn 外部进程。理解 Shell 的执行模型，是写出高性能脚本的前提。

性能直觉：内置命令 ~0.01ms，外部命令 ~1-10ms，管道（2 个命令）~10-20ms。循环 1000 次外部命令就是 5-10 秒；而一次 awk 处理 1000 行只要 ~5ms。

Shell 执行模型：从输入到进程

当你敲下一行命令，Shell 不是"直接运行程序"，而是经历一条流水线：

graph LR A[读取输入] --> B[词法分析 Tokenize] B --> C[语法分析 Parse] C --> D[展开 Expansion] D --> E[重定向设置] E --> F{内置命令?} F -- 是 --> G[Shell 内部直接执行] F -- 否 --> H[fork 创建子进程] H --> I[execve 加载程序] I --> J[wait 等待退出码] style A fill:#0d1117,stroke:#3ec96f,color:#3ec96f style G fill:#0d1117,stroke:#f59e0b,color:#f59e0b style I fill:#0d1117,stroke:#3ec96f,color:#3ec96f

外部命令的生命周期是经典的 fork → exec → wait 三步：Shell 调用 fork() 复制出一个子进程，子进程调用 execve() 用目标程序的映像替换自己，Shell 父进程则 wait() 阻塞直到子进程退出，退出码通过 $? 返回。

内置命令 vs 外部命令

type 命令能告诉你一个命令是内置还是外部：

type cd        # cd is a shell builtin（不 fork，直接执行）
type ls        # ls is /bin/ls（要 fork+exec）
type -a echo   # echo 既是 builtin 又有 /bin/echo，builtin 优先

# 命令查找顺序（从先到后）：
# 1.别名 Alias  2.关键字 if/for  3.函数 Function  4.内置 Builtin
# 5.哈希表 hash 缓存  6.PATH 环境变量目录
维度内置命令 Builtin外部命令 External
实现位置Shell 内部代码独立可执行文件
是否 fork否（~0.01ms）是（~1-10ms）
典型cd/echo/export/read/test/[ ]/pwdls/grep/awk/sed/find/cat
改目录cd 生效（本进程）子进程里 cd 对父进程无效

关键推论：cd 必须是内置命令。如果它是外部命令，每次 cd 都在子进程里执行，回到父 Shell 后当前目录纹丝不动。这正是子 Shell 不影响父 Shell的根源。

子 Shell 与环境变量继承

凡是 (cmd)、管道的每个命令、后台任务 cmd &，都运行在子 Shell 中。子进程会继承父进程的环境变量副本，但对变量的修改不会传回父进程：

# 子 Shell：cd 不影响外面
(cd /tmp && pwd)   # 输出 /tmp
pwd                # 仍是原来的目录

# 管道里改计数无效（Bash 默认每条命令一个子 Shell）
count=0
cat file | while read line; do count=$((count+1)); done
echo $count        # 0！修改发生在子 Shell

# 正确：直接重定向，不进子 Shell
count=0
while read line; do count=$((count+1)); done < file
echo $count        # 正确

进程替换 <(cmd) 是子 Shell 的高级用法：把命令输出伪装成文件，底层是命名管道（FIFO）或 /dev/fd/n：

diff <(sort a.txt) <(sort b.txt)   # 比较两个排序结果，不产生临时文件

管道与重定向的底层

管道 | 的底层是 pipe() 系统调用创建的一对文件描述符——写端写入、读端读出，数据在内核缓冲区流转。重定向 >/< 的底层是 dup2()：把目标文件的描述符复制到 0/1/2（stdin/stdout/stderr）：

cmd > file        # dup2: stdout -> file
cmd 2>&1          # dup2: stderr 指向 stdout 当前指向的位置
cmd > file 2>&1   # 正确：先重定向 stdout 到 file，再让 stderr 跟着 stdout
cmd 2>&1 > file   # 错误！顺序反了：stderr 先指向终端，再把 stdout 指向 file

记住顺序：> file 2>&1 是"先把 stdout 改道，再让 stderr 跟过去"；2>&1 > file 是"stderr 先跟着原来的 stdout（终端），然后 stdout 才改道"——两者效果天差地别。

性能优化方法论

用 time / hyperfine 先测量，再优化

time ./script.sh                 # 粗测 real/user/sys
# hyperfine 做基准对比（需安装，更准）
hyperfine 'grep pattern file' 'rg pattern file'

原则一：减少外部命令调用

循环里调用 sed/awk/expr 是性能头号杀手。能用内置参数展开就不用外部工具：

# 慢：每行都 fork 一次 sed（1000 行 = 1000 次 fork）
while read line; do
  echo "$line" | sed 's/foo/bar/g'
done < file

# 快：sed 一次处理整个文件
sed 's/foo/bar/g' file

# 慢：expr 做算术
result=$(expr $a + $b)
# 快：算术展开（内置）
result=$((a + b))

原则二：消灭 UUOC（Useless Use of Cat）

# 慢：cat 多了一次 fork，纯粹是中介
cat file | grep pattern
# 快：直接把文件名传给 grep
grep pattern file
# 或用重定向
grep pattern < file

原则三：一次处理代替逐行循环

# 慢：逐行 awk
while read line; do echo "$line" | awk '{print $1}'; done < file
# 快：awk 一次读完整个文件
awk '{print $1}' file

原则四：并行用 xargs -P 或 GNU parallel

# 串行：逐个 curl
for url in $(cat urls.txt); do curl -s "$url" > /dev/null; done
# 并行 10 路
cat urls.txt | xargs -P 10 -I {} curl -s {} > /dev/null
# GNU parallel（更灵活）
cat urls.txt | parallel -j 10 curl -s {} > /dev/null

最佳实践

  • 先测后优：没有 time/hyperfine 数据就不要盲目优化。
  • 循环体里零外部命令：把循环提出来，让 grep/awk/sed 一次处理整个文件。
  • 能用参数展开就不用 sed：${var//old/new} 是内置的。
  • 杜绝 UUOC：cat f | cmd 永远写成 cmd f 或 cmd < f。
  • IO 密集型任务并行化：xargs -P 并行拉 URL、跑测试。
  • 大文件流式处理：不要 $(cat file) 全读进内存，用 while read 流式。

常见问题 FAQ

Q1：为什么 cd 生效而脚本里的 cd 不影响交互式 Shell？

你运行 ./deploy.sh 时，Bash 会 fork 一个子进程来执行脚本，脚本里的 cd 只改变那个子进程的工作目录，脚本结束子进程消亡，父 Shell 的目录自然不变。想让脚本影响当前 Shell，要用 source deploy.sh（在当前进程里执行）。

Q2：管道里到底跑了几个进程？

在 Bash 中，管道 a | b | c 的每个命令都在各自的子进程里运行（共 3 个），所以任何一个命令里改的变量都传不出来。Bash 4 之后有 lastpipe 选项可让最后一个命令在当前 Shell 运行，但跨发行版不建议依赖。

Q3：为什么 set -e 有时候不生效？

-e 在"命令处于 if、&&/||、管道中非最后一个、或被 ! 取反"时会被豁免。典型坑：set -e; false && echo ok; echo "仍会执行"。关键场景要用 set -euo pipefail 配合显式 || die。

我的性能心得

Shell 的性能本质是进程创建成本：内置命令免费，外部命令昂贵，管道更贵。我优化脚本的全部技巧就三句话：减少 fork 次数、合并外部调用、IO 密集就并行。
