Kafka 分区与副本

🏷️ Kafka,分区,副本,存储引擎

理解存储引擎才能调优 Kafka

大部分开发者只把 Kafka 当消息队列用，从不关心它在磁盘上是怎么存的。但当你遇到"为什么消费延迟突然飙升""为什么 Partition 不均衡""Leader 选举怎么花了这么久"这类问题时，不了解存储层原理根本无法排查。我之前排过一个消费 lag 从 0 飙到 500 万的故障，最后发现是某台 Broker 磁盘 IO 打满导致 Follower 跟不上 ISR。本文深入 Kafka 存储引擎：日志段（LogSegment）、稀疏索引、副本同步协议、ISR 维护和 Leader 选举。

Partition 物理存储结构

每个 Partition 对应文件系统上的一个目录，命名规则是 {topic}-{partition}。目录内由多个日志段（LogSegment）组成，每个日志段包含三个文件：

  • 00000000000000001234.log：消息数据文件，实际存储消息的 key/value 和时间戳
  • 00000000000000001234.index：偏移量索引，记录"第 N 条消息在 .log 文件的字节位置"
  • 00000000000000001234.timeindex：时间戳索引，按时间戳查 Offset

日志段按 log.segment.bytes（默认 1GB）或 log.segment.ms（默认 7 天）滚动。当前活跃段（Active Segment）是唯一一个可写的，旧段只读。

稀疏索引的精妙设计

你可能会问：为什么不为每条消息都建索引？那索引文件会和数据文件一样大，内存都装不下。Kafka 用的是稀疏索引——每写 4KB 数据才在 .index 里记一条索引项。查找时先二分 .index 找到最近的粗索引项，再顺序扫描 .log 文件定位精确 Offset。这个设计把索引内存占用降到极低（通常只有数据量的 1% 左右），而查找成本仍然是 O(log N) 的。

副本机制：Leader 与 Follower

每个 Partition 有一个 Leader 和 N-1 个 Follower。所有读写请求都走 Leader，Follower 只做数据拉取同步。这个设计和 MySQL 主从复制类似，但有几个关键区别：

  • Follower 是主动拉（Pull），不是 Leader 推。这避免了 Leader 被慢 Follower 拖慢，也天然实现了批量传输。
  • 消费者永远不从 Follower 读。即使你在地理上离 Follower 更近，Kafka 也不允许从 Follower 消费——这保证了读取一致性（Leader 是唯一权威）。

ISR：In-Sync Replicas

ISR 是当前与 Leader 保持同步的副本集合。Follower 落后超过 replica.lag.time.max.ms（默认 30 秒）会被踢出 ISR。当 Leader 宕机时，Controller 从 ISR 中选一个新 Leader——只有 ISR 中的副本保证数据不丢。

LEO 与 HW

两个关键水位线：

  • LEO（Log End Offset）：日志末尾的下一条待写入 Offset。每个副本自己维护。
  • HW（High Watermark）：所有 ISR 副本都已复制到的最高 Offset。只有 HW 以下的消息才对消费者可见。

为什么需要 HW？考虑这个场景：Leader 写入消息 Offset=1000，Follower A 同步到了，Follower B 还没同步。此时 Leader 宕机，Follower A 被选为新 Leader。旧 Leader 重启后，它上面 Offset=1000 的消息对新 Leader 来说是"多余的"，需要截断到新 Leader 的 LEO。HW 就是这个截断点的依据——HW 以下的消息一定已被所有 ISR 复制，不会截断。

Leader 选举流程

KRaft 模式下，Controller 监控 Broker 心跳。某个 Broker 挂了，Controller 做以下事情：

  1. 识别该 Broker 上的所有 Partition Leader
  2. 从每个 Partition 的 ISR 列表中选第一个存活副本作为新 Leader
  3. 更新元数据（存到 __cluster_metadata Topic）
  4. 通知所有 Broker 和客户端元数据变更

整个过程通常在 3~5 秒内完成（KRaft 模式）。在这期间，受影响的 Partition 不可写（生产者 acks=all 会超时），但如果生产者配置了重试，会自动切换到新 Leader 继续写。

Topic 与 Partition 运维命令

# 创建 Topic
kafka-topics.sh --bootstrap-server node-1:9092   --create --topic orders   --partitions 12 --replication-factor 3   --config retention.ms=604800000   --config cleanup.policy=delete

# 查看 Topic 详细信息（重点看 ISR 和 Leader）
kafka-topics.sh --bootstrap-server node-1:9092   --describe --topic orders

# 输出示例：
# Topic: orders  Partition: 0  Leader: 1  Replicas: 1,2,3  Isr: 1,2,3
# Topic: orders  Partition: 1  Leader: 2  Replicas: 2,3,1  Isr: 2,3,1
# 如果 Isr 列少于 Replicas 列，说明有副本不同步

# 修改 Topic 配置
kafka-configs.sh --bootstrap-server node-1:9092   --entity-type topics --entity-name orders   --alter --add-config retention.ms=1209600000

# 扩容 Partition（只能增不能减！）
kafka-topics.sh --bootstrap-server node-1:9092   --alter --topic orders --partitions 24

# 删除 Topic
kafka-topics.sh --bootstrap-server node-1:9092   --delete --topic orders

Go 管理客户端（sarama）

package main

import (
    "fmt"
    "log"

    "github.com/IBM/sarama"
)

func main() {
    config := sarama.NewConfig()
    config.Version = sarama.V3_8_0_0

    admin, err := sarama.NewClusterAdmin([]string{"node-1:9092"}, config)
    if err != nil {
        log.Fatal(err)
    }
    defer admin.Close()

    // 创建 Topic
    detail := sarama.TopicDetail{
        NumPartitions:     12,
        ReplicationFactor: 3,
        ConfigEntries: map[string]*string{
            "retention.ms":  sarama.String("604800000"),
            "cleanup.policy": sarama.String("delete"),
        },
    }
    if err := admin.CreateTopic("orders", &detail, false); err != nil {
        log.Printf("创建 Topic 失败（可能已存在）: %v", err)
    }

    // 列出所有 Topic
    topics, err := admin.ListTopics()
    if err != nil {
        log.Fatal(err)
    }
    for name, detail := range topics {
        fmt.Printf("Topic: %s, Partitions: %d, ReplicationFactor: %d
",
            name, detail.NumPartitions, detail.ReplicationFactor)
    }

    // 查看 Broker 列表
    brokers, _, err := admin.DescribeCluster()
    if err != nil {
        log.Fatal(err)
    }
    for _, broker := range brokers {
        fmt.Printf("Broker %d: %s
", broker.ID(), broker.Addr())
    }
}

Partition 规划与副本设计最佳实践

Partition 数量怎么定？

我的血泪教训：有个老系统一开始只给 Topic 建了 3 个 Partition，后来业务量涨了 10 倍才发现消费并行度到顶了。扩容 Partition 后，已存在的消息不会重新分配，新旧 key 的消息混在不同 Partition 里，顺序性直接乱了。Partition 数规划要一步到位，预留 2~3 倍增长空间。

这是 Kafka 运维中最常见的问题。参考公式：

Partition 数 = max(目标消费并行度, 目标生产吞吐 / 单 Partition 生产吞吐)

单 Partition 生产吞吐 ≈ 10 MB/s
单 Partition 消费吞吐 ≈ 20~50 MB/s（取决于业务逻辑）

实际经验值：

  • 中小规模（日消息量 < 10 亿）：Topic 6~12 个 Partition 够用
  • 大规模（日消息量 10~100 亿）：24~48 个 Partition
  • 单 Broker 上 Partition 总数不要超过 2000（每个 Partition 占一个文件句柄和少量堆内存）

副本因子选择

副本因子容忍故障磁盘开销写入延迟推荐场景
RF=10 台1x最低仅开发/测试
RF=20 台（min.insync=2 时挂1台不可写）2x低不推荐生产
RF=31 台3x中生产默认推荐
RF=52 台5x高金融级/跨机房
  • RF=3：默认推荐，容忍 1 台 Broker 故障，磁盘开销 3 倍
  • RF=2：仅测试环境可用。RF=2 时 min.insync.replicas=2，挂 1 台就不可写
  • RF=5+：金融级场景，跨机房部署时考虑。注意 RF 越高，写入延迟越大

机架感知（Rack Awareness）

如果集群跨机架部署，一定要配 broker.rack=rack-1。Controller 分配副本时会确保同一个 Partition 的副本分布在不同机架上，避免单个机架断电导致整个 Partition 不可用。

常见问题 FAQ

Q1：Partition 数为什么只能增不能减？

因为消息路由是按 key 哈希到 Partition 的。如果减少 Partition 数，原来在 Partition 3 的 key 可能会路由到 Partition 1，但 Partition 1 上的历史消息还在那里，新旧 key 的消息混在一起，顺序性就乱了。Kafka 选择"不支持减少"而不是"支持后重新哈希"——后者代价太大且难以保证一致性。所以 Partition 数规划要一步到位，预留 2~3 倍增长空间。

Q2：ISR 频繁收缩是什么原因？

ISR 收缩说明 Follower 跟不上 Leader。常见原因：(1) 网络带宽打满，副本同步 fetch 请求超时；(2) Follower 所在 Broker 磁盘 IO 瓶颈，消息刷盘慢；(3) 频繁 Full GC 导致 Follower 暂停拉取。排查思路：看 UnderReplicatedPartitions 监控指标，定位是哪个 Broker 的副本落后，再查该 Broker 的磁盘 IO、网络带宽和 GC 日志。

Q3：为什么生产环境不建议用 log compaction（日志压缩）？

日志压缩（Compact）只保留每个 key 的最新值，适合 changelog 流（数据库 CDC）。但压缩过程是异步的，可能出现"同一 key 的旧值还没被删，新值已经写入"的中间状态。而且 Compact 后的日志段无法按时间清理，磁盘可能在你不注意时被撑满。除非你明确知道自己在做什么，否则用 Delete 策略（按时间/大小过期）更安全。

总结

Kafka 的存储引擎设计有两个核心思想：顺序追加写 + 稀疏索引让磁盘吞吐接近内存，Leader/Follower + ISR在性能和可靠性之间取得了精妙平衡。理解 LEO 和 HW 的区别、ISR 收缩的含义、Leader 选举的触发条件，是排查 Kafka 生产故障的基本功。下一篇我们聚焦消息可靠性——如何在分布式环境下实现"不丢一条消息"甚至"不重一条消息"。
