Kafka 消息可靠性落地：六个丢消息环节、配置清单与幂等消费

🏷️ Kafka 可靠性

ISR 与 HW 水位的语义、acks 与 min.insync.replicas 的组合推演、幂等 Producer 的 PID 加序列号机制、事务的边界在哪，这些原理详见站内 Kafka 深度原理一篇。这篇只做工程落地：把消息从 send 到业务落库的链路切成六段，一段一段把丢失和重复消灭掉，并且给出怎么验证真的消灭了。

丢点丢失机制怎么防怎么验证防住了
一、Producer 缓冲区send 只是入队，进程被杀时 accumulator 里的数据随内存消失关闭钩子里 flush() 加带超时的 close()；linger.ms 不要设太大；关键链路加本地 WAL压测中对进程发 SIGTERM，按序号核对；再发一次 SIGKILL，观察丢失条数是否等于 linger.ms 窗口内的量级
二、acks 不足acks=0 不等确认，acks=1 只等 leader 落 page cache，leader 换届即丢acks=all 加 enable.idempotence=true用 kafka-configs 确认实际生效值，再 kill leader 观察 Producer 侧是否只出现重试日志而无缺号
三、ISR 收缩ISR 只剩 leader 时 acks=all 等价于 acks=1Broker 端 min.insync.replicas=2，写入宁可失败也不假成功用防火墙阻断 follower 的 Fetch 流量，观察 UnderReplicatedPartitions 大于零且 Producer 收到 NotEnoughReplicas
四、未刷盘Kafka 默认不按条刷盘，靠副本冗余而不是 fsync不要去调 log.flush.interval.messages，而是把副本分散到不同机架或可用区；真正怕整机房断电就上跨机房复制同时断掉同一机架上的多台 Broker，检查是否有数据缺失；机架感知配置用 broker.rack 核对
五、先提交后处理自动提交或手动提交位置写错，位点已推进而消息未处理enable.auto.commit=false，处理完再提交，位点值记得是 offset + 1在处理逻辑中间抛异常并重启，检查这批消息是否被重新消费
六、落库失败业务处理成功、位点已提交，但数据库事务回滚位点写进业务库，与业务数据在同一个本地事务提交在提交事务前后两个位置分别注入崩溃，核对是否分别表现为整批重放和不重复
⚠️
「Kafka 写完就落盘了所以不会丢」是错的

Kafka 默认把刷盘完全交给操作系统，log.flush.interval.messages 默认是一个极大值，也就是不主动 fsync。它的持久化保障来自多副本而不是磁盘同步写。反过来，把刷盘间隔调成 1 条一刷会让吞吐掉一个数量级，还让顺序写退化成频繁 fsync，收益远小于代价。正确的投入方向是副本数、机架分散和 min.insync.replicas。

可以直接抄的三端配置清单

# ============ Producer 端 ============
acks=all                                       # 不配：leader 换届即丢
enable.idempotence=true                        # 不配：重试会产生重复，3.0 起默认 true
max.in.flight.requests.per.connection=5        # 大于 5 且开幂等会启动失败
delivery.timeout.ms=120000                     # 重试的总时间上限，重试次数不是真正边界
request.timeout.ms=30000
retry.backoff.ms=100
max.block.ms=5000                              # 不配：buffer 满时业务线程被拖住 60 秒
linger.ms=10                                   # 攒批，同时也是崩溃丢失窗口的权衡点
compression.type=zstd

# ============ Broker 端 server.properties ============
default.replication.factor=3                   # 不配：默认 1 副本，掉一台就丢分区
min.insync.replicas=2                          # 不配：ISR 收缩时 acks=all 退化成 acks=1
unclean.leader.election.enable=false           # 不配：落后副本可能当选 leader 并截断已确认数据
auto.create.topics.enable=false                # 不配：打错 Topic 名会自动建出 1 副本的 Topic
offsets.topic.replication.factor=3             # 不配：位点 Topic 单副本，掉一台全组位点丢失
transaction.state.log.replication.factor=3
transaction.state.log.min.isr=2
replica.lag.time.max.ms=30000                  # 判定 follower 掉出 ISR 的时间阈值
log.retention.hours=168                        # 保留期要长于最坏情况下的故障处理时间

# ============ Consumer 端 ============
enable.auto.commit=false                       # 不配：默认每 5 秒自动提交，崩溃即丢
auto.offset.reset=latest                       # 对账类任务用 none，宁可报错不要静默跳过
isolation.level=read_committed                 # 上游用事务时不配会读到未提交消息
max.poll.records=100                           # 与单条处理耗时相乘要远小于下面这项
max.poll.interval.ms=300000
❌
三副本加 min.insync.replicas=2 的可用性代价

这个组合意味着最多只能坏一台。坏两台时 ISR 只剩一个，写入会直接被拒绝，可用性换来了一致性。如果业务无法接受写入被拒，唯一正确的做法是把副本数提到 5、min.insync.replicas 保持 2，而不是偷偷把它降回 1。降回 1 等于把丢消息的概率重新打开，而且这种改动往往发生在半夜的应急操作里，事后没人记得改回来。

重复是必然的：消费端幂等的四种实现

只要位点提交和业务处理不在一个原子操作里，重复就无法从协议层消除。Rebalance、消费者重启、提交超时都会让同一批消息被再消费一次。所以可靠性工程的下半场不是「避免重复」，而是让重复不产生副作用。

方案实现要点可靠性什么情况下会失效
数据库唯一索引对业务键或消息 ID 建唯一索引，用插入忽略或冲突时更新最高，互斥由存储引擎保证分库分表后唯一索引只在单库内有效，路由键必须包含唯一键；批量插入时一条冲突可能整批失败，需要逐条或改用 upsert
状态机条件更新更新语句里把当前状态和版本号作为条件，靠影响行数判断是否已处理高，且能顺带解决乱序状态机有环时无法判重；只看影响行数为 0 就当成功，会掩盖真正的数据不存在错误
Redis 去重键用消息 ID 做 SETNX 加过期时间，已存在则跳过中，只能当前置优化Redis 与数据库之间没有原子性：SETNX 成功后进程崩溃，消息永久丢失；Redis 主从切换丢键会放过重复；键过期后老消息重投又会被处理一次
业务天然幂等整体覆盖写、置为终态、幂等的 HTTP PUT 语义高且成本最低只要出现累加、追加、发通知、扣库存这类操作就不再幂等；「把状态改成已支付」幂等，但「余额加 100」不幂等
先查询再插入先 SELECT 判断存在，不存在再 INSERT不是幂等实现并发下两个线程同时查到不存在然后都插入。重复消费往往是成批同时到达的，恰好是最容易触发这个竞态的场景

位点和业务数据放进同一个本地事务

下游是关系型数据库时，这是实现端到端精确一次的唯一可靠路径。Kafka 自带的事务只能保证「读 Kafka、写 Kafka、提交位点」这三件事的原子性，跨到外部数据库它管不了。做法是把位点当作普通业务数据存进业务库，让数据库的事务同时覆盖业务写入和位点推进。

-- 位点表：主键必须是 消费组 + Topic + 分区 三元组
CREATE TABLE consumer_offset (
  consumer_group VARCHAR(128) NOT NULL,
  topic          VARCHAR(191) NOT NULL,
  partition_id   INT          NOT NULL,
  next_offset    BIGINT       NOT NULL,   -- 存的是下一条要读的位点
  updated_at     DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
  PRIMARY KEY (consumer_group, topic, partition_id)
) ENGINE=InnoDB;

-- 业务表：靠唯一索引做幂等，不要靠先查后插
CREATE TABLE order_event (
  id         BIGINT AUTO_INCREMENT PRIMARY KEY,
  order_no   VARCHAR(64) NOT NULL,
  event_type VARCHAR(32) NOT NULL,
  amount     DECIMAL(18,2) NOT NULL,
  UNIQUE KEY uk_order_event (order_no, event_type)
) ENGINE=InnoDB;

-- 幂等写入：重复消费时静默跳过，影响行数为 0
INSERT INTO order_event (order_no, event_type, amount)
VALUES (?, ?, ?)
ON DUPLICATE KEY UPDATE amount = VALUES(amount);

-- 位点推进：与上面的 INSERT 在同一个事务内
INSERT INTO consumer_offset (consumer_group, topic, partition_id, next_offset)
VALUES (?, ?, ?, ?)
ON DUPLICATE KEY UPDATE next_offset = GREATEST(next_offset, VALUES(next_offset));

// 位点存业务库的消费循环：不调用任何 commit 接口，位点只认数据库
public void run() {
    consumer.subscribe(List.of("order.created"), new ConsumerRebalanceListener() {
        @Override
        public void onPartitionsRevoked(Collection<TopicPartition> parts) {
            // 位点在业务库里，这里不需要提交，只需清理本地缓存与限流状态
            localState.clear(parts);
        }
        @Override
        public void onPartitionsAssigned(Collection<TopicPartition> parts) {
            for (TopicPartition tp : parts) {
                Long next = offsetDao.findNextOffset(GROUP, tp.topic(), tp.partition());
                // 库里没有记录说明是首次分配，交给 auto.offset.reset 决定起点
                if (next != null) {
                    consumer.seek(tp, next);
                }
            }
        }
    });

    while (running.get()) {
        ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(500));
        for (TopicPartition tp : records.partitions()) {
            List<ConsumerRecord<String, String>> batch = records.records(tp);
            long nextOffset = batch.get(batch.size() - 1).offset() + 1;
            // 一个分区一个事务：业务写入与位点推进同生共死
            txTemplate.executeWithoutResult(status -> {
                for (ConsumerRecord<String, String> r : batch) {
                    orderDao.upsertEvent(parse(r.value()));   // 唯一索引兜住重复
                }
                offsetDao.advance(GROUP, tp.topic(), tp.partition(), nextOffset);
            });
        }
    }
}
💡
这个方案的三个隐含约束

第一，位点表和业务表必须在同一个数据库实例里，分库了就退化成分布式事务问题。第二，每个分区一个事务，分区多时事务数量上升，要控制 max.poll.records 避免单事务过大导致长事务和锁等待。第三，运维不能再用 kafka-consumer-groups 脚本看 Lag，因为 __consumer_offsets 里根本没有位点，必须自己上报位点与 LEO 的差值到监控。

重试与死信：为什么不能原地阻塞重试

一个分区在同一个消费组内只会被一个成员串行消费，这意味着卡在一条消息上就等于卡住整个分区。原地睡眠重试三次每次五秒，这条消息后面排队的几万条消息就一起延迟十五秒；如果下游是持续故障，等待时间会迅速突破 max.poll.interval.ms，成员被踢出组、触发 Rebalance、分区转给别人后依然卡在同一条消息上，形成一个自我放大的故障循环。

stateDiagram-v2 [*] --> 待消费 待消费 --> 处理中: poll 拉取到 处理中 --> 已完成: 业务成功且位点推进 处理中 --> 重试中: 可重试失败 且本地快速重试已用尽 重试中 --> 处理中: 延迟到期 从重试 Topic 重新投递 重试中 --> 死信: 重试次数超过上限 处理中 --> 死信: 不可重试异常 直接进死信 死信 --> 人工处理: 告警触达值班 人工处理 --> 待消费: 修复后重投原 Topic 人工处理 --> 已丢弃: 确认无需处理并登记 已完成 --> [*] 已丢弃 --> [*] note right of 重试中 消息体里带 retry_count 与首次失败时间 延迟级别递增 例如 5s 30s 2m 10m 30m 重试 Topic 与主 Topic 完全隔离 互不影响吞吐 end note
重试策略实现对分区吞吐的影响顺序性适用场景
本地立即重试同一线程内重试 2 到 3 次，间隔几十毫秒轻微，总耗时可控保持网络抖动、数据库死锁重试这类瞬时故障，必须严格限制总耗时
原地阻塞重试sleep 加循环，直到成功灾难性，分区完全停滞，并极易被踢出组保持不要用
独立重试 Topic失败后带 retry_count 发到 retry Topic，独立消费者按延迟级别重投无影响，主链路继续前进破坏绝大多数业务的推荐方案
分级延迟 Topic为每个延迟级别建一个 Topic，例如 retry-5s、retry-30s无影响破坏需要精确延迟梯度且量大的场景，代价是 Topic 数量膨胀
按 key 暂停失败的 key 记入暂停表，同 key 后续消息直接转存待处理队列，其他 key 正常处理轻微同 key 内保持既要顺序又不能卡分区的折中方案，代价是需要维护暂停状态
死信 Topic超过重试上限后转存，并带上原 Topic、分区、位点、异常栈无影响不适用所有方案的最后一道兜底，必须配告警和重投工具，否则等于垃圾桶

顺序性和重试的冲突没有完美解

这是一对硬矛盾：跳过失败消息会乱序，阻塞重试会卡分区。真正需要做的是先问清楚顺序的粒度。业务上几乎从不需要「全局有序」，通常只需要「同一个订单、同一个用户的事件有序」，这个粒度正好对应按 key 哈希到同一分区。于是折中方案就有了落点：

方案做法代价什么情况下不成立
按 key 暂停某 key 处理失败时把该 key 写入暂停集合，后续同 key 消息直接落库到待处理表，其余 key 照常消费需要维护暂停集合与恢复流程；待处理表要有独立消费者热点 key 占了绝大部分流量时，等价于卡住整个分区
消息版本号兜底消息体带业务版本号或时间戳，消费端用条件更新丢弃旧版本需要下游支持条件更新事件不是幂等的覆盖语义，例如增量扣减
把顺序需求下推到存储消费端只做写入，顺序由数据库的状态机和乐观锁保证数据库压力上升下游不是数据库，比如是第三方接口
整批回退位点失败时不提交位点并 seek 回批次起点，整批重放会重复处理已成功的消息，必须配合幂等故障是持续性的，会变成无限重放打爆下游，需要加熔断

SIGKILL leader BrokerProducer 短暂出现 NotLeaderOrFollower 并自动重试，几秒内恢复序号无缺失，消费端总条数不变有缺号说明 acks 或 unclean.leader.election.enable 配错了

数据盘写满Broker 日志出现 IOException，该 Broker 上的分区下线其他 Broker 上的副本接管，客户端只是短暂报错整个集群写入不可用，说明分区副本分布不均或副本数不足
SIGKILL ConsumerRebalance 后另一成员从上次提交位点继续有重复处理但结果一致，没有跳过有跳过说明位点提交早于处理，或开了自动提交
SIGTERM Producer关闭钩子执行 flush 与 close零丢失有丢失说明关闭钩子没注册，或用了零超时的 close
业务逻辑注入随机异常失败消息进重试 Topic，超限进死信主 Topic 的 Lag 不因失败而堆积Lag 持续上涨说明在做原地阻塞重试

对账是最后一道防线，任何 MQ 方案都要有

上面所有手段加起来，能把丢失概率压到很低，但压不到零。跨系统的最终一致只能靠对账加补偿兜底，这不是 Kafka 的缺陷，换成任何 MQ 都一样。落地上通常是三件事：生产端在发消息的同一个本地事务里记一张待确认表；定时任务扫出超过阈值仍未被下游确认的记录并重投；每天按业务维度做一次全量或增量比对，差异进人工工单。

再加一个容易被忽略的点：死信 Topic 必须配告警和重投工具。只写不读的死信 Topic 等于一个垃圾桶，故障发生一个月后才有人发现里面积了十万条消息，这种事情非常常见。最小可用的工具是一个能按时间范围和错误类型筛选、支持批量重投回原 Topic 的脚本，以及死信条数非零就触发的告警。

❌
最容易踩的坑
  • 只配了 acks=all 没配 min.insync.replicas：ISR 收缩到 1 时静默退化成 acks=1，故障时才发现丢了数据。
  • unclean.leader.election.enable 被打开：为了恢复可用性打开它，落后的副本当选 leader，已经确认给客户端的消息被截断，这是最难解释清楚的一类数据丢失。
  • Topic 级配置覆盖了 Broker 级：Broker 上 min.insync.replicas=2，但某个 Topic 建的时候单独设成了 1，只看 server.properties 永远查不出来，要用 kafka-configs 按 Topic 查。
  • 用 Redis 去重键当幂等保证：SETNX 成功后进程崩溃，这条消息永久丢失，因为下次重投会被去重键拦掉。它只能做前置优化。
  • 先查后插当幂等：并发下两个线程同时查到不存在，然后都插进去。重复消费往往是成批到达的，正是最容易触发竞态的场景。
  • 死信 Topic 没有告警：消息进了死信等于消失，一个月后才被发现。
  • 原地 sleep 重试：卡住整个分区，并且很快超过 max.poll.interval.ms 被踢出组，把局部故障放大成全组 Rebalance。
  • 重试 Topic 不带重试次数：消息在重试 Topic 里无限循环，量大时直接把集群打满。
  • 位点存业务库却还开着自动提交：两套位点互相打架，Rebalance 后从哪里开始完全不可预测。
  • 位点存业务库后不再监控 Lag：__consumer_offsets 里没有位点，运维脚本看到的 Lag 是错的，积压了也没人知道。
  • 调 log.flush.interval.messages 来「保证不丢」：吞吐掉一个数量级，收益远小于把副本分散到不同机架。
  • 补偿任务没有幂等和限流：故障恢复后补偿任务一次性重投几十万条，把刚活过来的下游又打死一次。
