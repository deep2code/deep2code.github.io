Kafka 性能调优的三个层次

很多人觉得 Kafka 性能不行，其实 90% 的情况是配置没调对。Kafka 的性能瓶颈从来不在一个地方——可能是生产者批量太小、可能是 Broker 磁盘打满、也可能是消费者单次拉取太多导致 GC。本文从生产者、Broker、消费者三个维度讲调优，再附上 Kafka / RabbitMQ / RocketMQ 三大消息队列的全面对比。

生产者侧调优

参数默认值调优建议原理
batch.size16KB32KB~128KB批次越大，单次网络请求效率越高，但延迟增加
linger.ms05~20ms等待攒批时间，和 batch.size 是"或"关系，任一满足就发
compression.typenonelz4 / zstdCPU 换网络和磁盘 I/O。文本消息压缩比 5~10 倍
buffer.memory32MB64MB~256MB生产者总发送缓冲区。打满会阻塞 send()
max.in.flight.requests.per.connection55（幂等模式）单连接在途请求数。太高会打乱重试顺序
 
// Go 高性能生产者配置
config := sarama.NewConfig()
config.Producer.RequiredAcks = sarama.WaitForAll
config.Producer.Idempotent = true

// 批量优化
config.Producer.Flush.Bytes = 64 * 1024        // 64KB 批次
config.Producer.Flush.Frequency = 10 * time.Millisecond // 最多等 10ms

// 压缩
config.Producer.Compression = sarama.CompressionLZ4

// 缓冲区
config.Producer.MaxMessageBytes = 1000000       // 单条消息最大 1MB
config.Producer.Retry.Max = 3
config.Producer.Retry.Backoff = 100 * time.Millisecond

Broker 侧调优

关键 Broker 配置

我踩过的坑：有次为了"更安全"，把 log.flush.interval.messages=1 和 log.flush.interval.ms=100 打开了，结果单机吞吐从 80 万 TPS 直接掉到 5 万。Kafka 依赖 OS 页缓存批量刷盘，强行同步刷盘等于把 SSD 当机械盘用。记住：副本机制已经保证了数据安全，不要开同步刷盘。

# ===== 线程模型 =====
num.network.threads=8          # 网络请求处理线程（默认 3，太少会排队）
num.io.threads=16              # 磁盘 I/O 处理线程（默认 8，建议 = CPU 核数）
queued.max.requests=500        # 每个网络线程的请求队列上限

# ===== 页缓存利用 =====
# 不要在 JVM 上分配超过 6~8GB 堆
# 把剩余内存全部留给 OS Page Cache
# JVM 启动参数: -Xms6g -Xmx6g -XX:+UseG1GC

# ===== 刷盘策略（不要改成同步刷盘！）=====
# Kafka 依赖 OS 页缓存刷盘，不要设 log.flush.* 强制同步
# 副本机制已经保证了数据安全，不需要每写一条就 fsync

# ===== 网络 =====
socket.send.buffer.bytes=1048576       # 1MB
socket.receive.buffer.bytes=1048576   # 1MB
socket.request.max.bytes=104857600     # 100MB

# ===== 消费者拉取 =====
fetch.max.bytes=52428800               # 单次 fetch 最大 50MB
max.partition.fetch.bytes=1048576      # 单分区单次最大 1MB

消费者侧调优

# Python 高性能消费者配置
config = {
    'bootstrap.servers': 'node-1:9092',
    'group.id': 'high-throughput-group',

    # 拉取参数：批量拉取，减少网络往返
    'fetch.min.bytes': 1024 * 1024,     # 1MB，攒够才返回
    'fetch.max.wait.ms': 500,           # 最多等 500ms
    'max.poll.records': 1000,           # 每次 poll 最多 1000 条

    # 会话与心跳
    'session.timeout.ms': 30000,
    'heartbeat.interval.ms': 10000,
    'max.poll.interval.ms': 300000,     # 5 分钟处理超时

    # 提交策略
    'enable.auto.commit': False,
    # 手动批量提交，减少 Offset 请求
    # 每处理 100 条提交一次，而非每条都提交

    # 客户端缓冲
    'receive.buffer.bytes': 1048576,
    'send.buffer.bytes': 1048576,
}

消费并行度扩容

消费者吞吐量不够时，扩容路径是：

  1. 先加消费者实例：消费组内 Consumer 数增加，每个 Consumer 分到更少 Partition。上限是 Partition 数。
  2. Partition 数不够了就扩容 Partition：kafka-topics.sh --alter --partitions N。注意：已存在的消息不会重新分配到新 Partition，只影响新消息。
  3. 批量处理：不要逐条处理，攒一批（100~1000 条）批量写数据库/调下游 API。

怎么选？

  • 选 Kafka 当你需要：海量数据（日千亿消息）、流处理管道、数据回溯、和大数据生态（Spark/Flink）集成。
  • 选 RabbitMQ 当你需要：复杂路由（交换机 + 绑定键）、低延迟、消息优先级、已经在用 Spring 生态。
  • 选 RocketMQ 当你需要：金融级事务消息、延迟消息、国内技术支持、阿里系技术栈。

不要陷入"哪个最好"的争论——它们解决的是不同问题。Kafka 是数据管道，RabbitMQ 是服务总线，RocketMQ 是业务消息中枢。

性能调优最佳实践总结

  1. 先压测再调优：用 kafka-producer-perf-test.sh 和 kafka-consumer-perf-test.sh 做基线压测，找到瓶颈点再调。不要凭感觉改配置。
  2. 批量永远是第一优先级：生产者调 batch.size + linger.ms，消费者调 fetch.min.bytes + max.poll.records。批量 I/O 比任何参数调优都有效。
  3. 压缩是免费的性能提升：开启 lz4 或 zstd，CPU 多花 5~10%，网络和磁盘省 50~80%。在千兆网络下收益最大。
  4. 监控先行：没有监控就调优是盲人摸象。至少要有消费 lag、生产吞吐、Broker CPU/磁盘/网络三组监控。
  5. 不要过度调优：默认配置已经覆盖了 80% 场景。只有压测发现瓶颈、且明确知道改这个参数的影响时才改。

常见问题 FAQ

Q1：Kafka 单机到底能跑多少 TPS？

参考 LinkedIn 公开数据：3 节点 NVMe SSD 集群，单 Broker 约 150 万 TPS（1KB 消息）。但这是极限压测数字，生产环境建议按 30~50 万 TPS 规划。影响因素：消息大小（10KB 消息吞吐降一个数量级）、副本因子（RF=3 比 RF=1 慢 30~50%）、是否开启压缩（开启后吞吐反升）。

Q2：为什么我的 Kafka 消费延迟很高（lag 很大）？

消费 lag 增长 = 生产速率 > 消费速率。排查方向：(1) 消费者实例数是不是太少？Partition 数够不够？(2) 单条消息处理是不是太慢（同步调下游 API）？改成批量处理或异步化。(3) 频繁 Rebalance 导致停顿？调大 session.timeout.ms。(4) 消费者 GC 频繁？调小堆内存，用 G1GC。

Q3：什么时候不应该用 Kafka？

Kafka 不是银弹。以下场景不适合：(1) 需要复杂路由（"根据消息头路由到不同队列"）——用 RabbitMQ；(2) 需要消息优先级和死信交换器——RabbitMQ 原生支持；(3) 需要延迟消息/定时投递——RocketMQ 原生支持；(4) 消息量很小（每天几万条）——Kafka 的运维成本不值得，用 Redis List 或数据库表都够了。

总结

做了这么多年 MQ，我的体会是：Kafka 性能调优的核心是批量 + 顺序 + 页缓存三大设计哲学的客户端配合。生产者攒大批次、Broker 顺序写盘 + 利用 OS 页缓存、消费者批量拉取——三者协同才能跑满 Kafka 的设计吞吐。

技术选型上，我从来不争论"哪个 MQ 最好"。根据业务场景做权衡就够了：Kafka 适合大数据管道，RabbitMQ 适合灵活路由的业务消息，RocketMQ 适合金融级事务消息。理解了它们的设计哲学差异，选型就不再是难题。
