Kafka 安装部署

🏷️ Kafka,部署运维,KRaft

💡 你要处理大量的异步消息，用户下单后要发短信、发邮件、更新积分，不能让用户等。或者你要做日志收集，几台服务器的日志要汇总到一起。

部署 Kafka 前的思考

很多人把 Kafka 部署想得很简单——下载 tar 包、改几个配置、启动脚本。但生产环境的 Kafka 部署是一件系统工程：JVM 堆大小、页缓存预留、磁盘选择（SSD/NVMe）、文件描述符限制、swap 关闭、时间...

为什么选 KRaft 而不是 ZooKeeper？ Kafka 3.x 开始 KRaft（Kafka Raft）已经生产可用，4.0 之后彻底移除 ZooKeeper。KRaft 把 Controller 元数据直接存在 Kafka 内部 Topic __cluster_metadata 中，省去了单独维护 ZK 集群的复杂度，启动速度从分钟级降到秒级，Controller 故障切换从 20~40 秒降到 3~5 秒。新项目直接上 KRaft，老项目用内置工具迁移。

OS 层关键调优

# 1. 关闭 swap（避免 Kafka 进程被换出到磁盘）
sudo swapoff -a
sudo sed -i '/swap/d' /etc/fstab

# 2. 提升文件描述符上限（Kafka 每个分区多个文件）
sudo tee -a /etc/security/limits.conf << 'EOF'
kafka  -  nofile  655360
kafka  -  nproc   655360
EOF

# 3. 虚拟内存参数
sudo sysctl -w vm.swappiness=1
sudo sysctl -w vm.max_map_count=262144

# 4. 磁盘调度算法（NVMe 建议 none/mq-deadline）
echo none | sudo tee /sys/block/nvme0n1/queue/scheduler

# 5. 时间同步（副本同步依赖时钟）
sudo timedatectl set-ntp true

三节点 KRaft 集群拓扑

生产环境最小推荐 3 个 Broker，既能容忍 1 台宕机，又有足够的副本分布空间。KRaft 模式下，Controller 角色和 Broker 角色可以混部（小集群）或独立部署（大集群）：

二进制包安装步骤

1. 下载与解压

cd /opt
wget https://archive.apache.org/dist/kafka/3.8.0/kafka_2.13-3.8.0.tgz
tar -xzf kafka_2.13-3.8.0.tgz
ln -s kafka_2.13-3.8.0 kafka

# 创建 kafka 用户
sudo useradd -r -m -d /home/kafka kafka
sudo chown -R kafka:kafka /opt/kafka*

2. 格式化存储目录（KRaft 首次必须）

sudo -u kafka /opt/kafka/bin/kafka-storage.sh format   -t $(/opt/kafka/bin/kafka-storage.sh random-uuid)   -c /opt/kafka/config/kraft/server.properties

注意：kafka-storage.sh format 只在首次部署时执行。重复 format 会清空元数据，导致集群无法启动。

血泪教训：有次帮同事排查集群起不来的问题，查了半小时发现他手抖在三台机器上都跑了 format——因为三台用的同一个 cluster-id 但 format 后元数据不一致，Controller 选举直接挂掉。后来只能清掉所有 log.dirs 重新初始化。format 命令在生产上只执行一次，执行前先确认这台机器是不是全新部署。

3. server.properties 关键配置

# ===== 基础标识 =====
node.id=1
process.roles=broker,controller
controller.quorum.voters=1@node-1:9093,2@node-2:9093,3@node-3:9093

# ===== 监听器 =====
listeners=PLAINTEXT://0.0.0.0:9092,CONTROLLER://0.0.0.0:9093
advertised.listeners=PLAINTEXT://node-1:9092
listener.security.protocol.map=CONTROLLER:PLAINTEXT,PLAINTEXT:PLAINTEXT
controller.listener.names=CONTROLLER
inter.broker.listener.name=PLAINTEXT

# ===== 存储 =====
log.dirs=/data/kafka/1,/data/kafka/2,/data/kafka/3
num.network.threads=8
num.io.threads=16
num.recovery.threads.per.data.dir=2

# ===== Topic 默认 =====
auto.create.topics.enable=false
default.replication.factor=3
min.insync.replicas=2
num.partitions=6

# ===== 日志保留 =====
log.retention.hours=168
log.segment.bytes=1073741824
log.retention.check.interval.ms=300000

# ===== 组协调与事务 =====
offsets.topic.replication.factor=3
transaction.state.log.replication.factor=3
transaction.state.log.min.isr=2
group.initial.rebalance.delay.ms=3000

# ===== 网络 =====
socket.send.buffer.bytes=102400
socket.receive.buffer.bytes=102400
socket.request.max.bytes=104857600
max.connections.per.ip=1000

4. systemd 服务管理

sudo tee /etc/systemd/system/kafka.service << 'EOF'
[Unit]
Description=Apache Kafka
After=network.target

[Service]
Type=simple
User=kafka
Group=kafka
ExecStart=/opt/kafka/bin/kafka-server-start.sh /opt/kafka/config/kraft/server.properties
ExecStop=/opt/kafka/bin/kafka-server-stop.sh
Restart=on-failure
RestartSec=10
LimitNOFILE=655360
LimitNPROC=655360

[Install]
WantedBy=multi-user.target
EOF

sudo systemctl daemon-reload
sudo systemctl enable --now kafka
sudo systemctl status kafka

集群健康验证

# 查看集群 Broker 列表
/opt/kafka/bin/kafka-broker-api-versions.sh --bootstrap-server node-1:9092

# 创建测试 Topic（3 分区 3 副本）
/opt/kafka/bin/kafka-topics.sh --bootstrap-server node-1:9092   --create --topic test-topic --partitions 3 --replication-factor 3

# 查看 Topic 详情（重点看 ISR 列）
/opt/kafka/bin/kafka-topics.sh --bootstrap-server node-1:9092   --describe --topic test-topic

# 期望输出中 ISR 列应该是 (1,2,3) 或类似完整副本列表
# 如果 ISR 少于副本数，说明有副本未同步，需要排查磁盘/网络问题

JVM 堆大小怎么定？

Kafka 官方文档有一个常被误解的建议：堆内存不要超过 6~8GB。原因是 Kafka 重度依赖 OS 页缓存，JVM 堆太大反而挤压页缓存。我第一次部署 Kafka 时傻乎乎地给了 16GB 堆，结果大促时频繁 Full GC，吞吐直接砍半。后来按这个原则把堆降到 6GB，留给页缓存，吞吐立刻回升。经验值：

  • 堆内存：6GB（用 G1GC），通过 KAFKA_HEAP_OPTS="-Xms6g -Xmx6g" 设置
  • 页缓存：把堆之外的所有内存都留给 OS。32GB 机器，堆 6GB，页缓存约 26GB
  • G1GC 调优：-XX:MaxGCPauseMillis=20、-XX:InitiatingHeapOccupancyPercent=35

生产部署检查清单

  • ✅ 至少 3 个 Broker，副本因子 3，min.insync.replicas=2
  • ✅ 关闭 swap，调整 vm.swappiness=1
  • ✅ 磁盘用 NVMe SSD，多块盘用 JBOD（log.dirs 逗号分隔）
  • ✅ 监控：JVM GC、UnderReplicatedPartitions、OfflineReplicaCount、ActiveControllerCount
  • ✅ 日志：Kafka 自身日志级别设为 WARN，应用日志单独收集
  • ✅ 备份：用 MirrorMaker 2 做跨机房/跨集群灾备
  • ✅ 安全：生产环境必须开 SASL/SCRAM 或 mTLS，不要用 PLAINTEXT

常见问题 FAQ

Q1：Kafka 集群最少需要几个 Broker？

开发环境 1 个够了。生产环境最低 3 个——2 个虽然能做副本，但 min.insync.replicas=2 时挂 1 台就不可写，且 Controller 选举需要多数派，2 节点无法容忍任何节点宕机。3 节点能容忍 1 台宕机，Controller 选举 Raft 多数派为 2。更大规模建议 5+ 节点，方便滚动重启和扩缩容。

Q2：JBOD（多块盘）和 RAID 0 怎么选？

强烈推荐 JBOD。Kafka 自己就是冗余系统（副本机制），不需要磁盘级 RAID。JBOD 模式下每块盘挂了只影响该盘上的 Partition，其他盘继续服务；RAID 0 一块盘挂了整个 RAID 组报废。JBOD 还有一个优势：Kafka 会把 Partition 均匀分配到各盘，单盘故障不影响全局。

Q3：ZooKeeper 模式怎么迁移到 KRaft？

Kafka 3.8+ 提供了 kafka-zookeeper-migration.sh 工具，支持在线滚动迁移。核心步骤：(1) 先在 ZK 集群上配置 KRaft controller quorum；(2) 逐台把 Broker 切换为 KRaft 模式；(3) 然后关闭 ZK 集群。整个过程不需要停机。但如果是旧版本（2.x），建议直接搭新 KRaft 集群，用 MirrorMaker 2 同步数据过去，比原地迁移更稳妥。

总结

部署生产级 Kafka，我踩过的坑比装过的机器还多。核心不是安装本身，而是资源规划 + OS 调优 + 配置规范 + 监控覆盖。KRaft 模式去掉了 ZooKeeper 这个重量级依赖，让 Kafka 集群的部署和运维变得轻盈。

记住三个数字：3 节点起步、副本因子 3、min.insync.replicas=2，这是大多数中小团队生产部署的安全底线。下一篇我们进入客户端编程实战，用 Go 和 Python 写真正生产可用的生产者和消费者。
