Kafka 是什么：提交日志模型与选型边界

🏷️ Kafka

几乎所有 Kafka 的误用，都能追溯到同一个起点：把它当成一个「吞吐量特别大的消息队列」。这个类比在前十分钟很好用，在之后的每一次事故里都会害人。这篇不讲实现细节，只解决一个问题——Kafka 是哪一类系统，什么时候该用，什么时候明确不该用。分段日志、稀疏索引、零拷贝、ISR 水位、acks 组合这些机制不在这里展开，详见站内 Kafka 深度原理一篇。

Kafka 的本质是可重放的提交日志，不是队列

用一句话给 Kafka 下定义：它是一个分布式的、可重放的、分区内有序的提交日志（commit log）。「日志」在这里不是 log.info() 那种日志，而是数据库领域的 WAL 概念——一个只能在尾部追加、每条记录有单调递增编号、按编号顺序读取的文件。Kafka 做的事就是把这个结构分布式化、分区化，然后开放给任意多个读者。

队列和日志的区别在于读取是否是破坏性的。队列的出队操作会改变队列本身：消息被取走，别人再也看不到。日志的读取只是「从第 N 个字节开始顺序扫」，扫完什么都没变，另一个读者可以从第 0 个字节重新扫一遍。这个差别听起来很小，但它单方面决定了 Kafka 的几乎全部特性：

  • 消息被消费后不删除。删除的唯一触发条件是保留策略到期，跟有没有消费者完全无关。
  • 位点属于消费方，不属于 broker。Kafka 只是替你把这个数字存在内部主题里，你完全可以自己存到数据库。位点既然是个可读可写的数字，就可以拨回去。
  • 多个消费组能独立读同一份数据。它们各有一份位点，互不干扰，加一个下游不需要生产者做任何改动。
  • 顺序性的粒度是分区，不是 topic。因为「有序」来自单个文件的追加顺序，跨文件无法定义顺序。
  • 天然适合做数据管道和事件溯源。因为它保存的是「发生过什么」的完整序列，而不是「待处理的任务」。
💡
一个能立刻用上的判断标准

如果你的需求是「把一个任务交给某个 worker 处理掉」，那是队列语义，Kafka 只是勉强能做。如果你的需求是「记录下所有发生的事实，让现在和将来的多个系统各自解读」，那是日志语义，Kafka 就是为此设计的。前者选 Kafka 会在延迟消息、单条重试、优先级上处处别扭；后者选 RabbitMQ 会在第二个下游接入时就卡住。

Segment磁盘文件与删除的单位保留策略删的是整个段文件，所以磁盘释放是阶梯式的，不是随时间平滑下降
Producer写入与分区选择的单位分区选择发生在客户端而不是 broker，broker 不会帮你重新路由
Consumer Group订阅的单位订阅关系挂在组上而不是实例上；换 group.id 等于一个全新订阅方，会从 auto.offset.reset 指定的位置开始
Consumer组内并行执行的单位同组内实例数超过分区数时多余实例空转，分区数是并行度天花板
Offset位置的单位在单个分区内唯一且单调递增，跨分区之间没有可比性，不存在「全局第 100 条消息」

⚠️
流传最广的错误说法：Kafka 快是因为它不删消息

顺序写和不逐条删确实有帮助，但「Kafka 比 RabbitMQ 快」的主因是批量化与分区并行：生产端把成百上千条消息攒成一个批次一次网络往返写入，消费端一次 fetch 拉回整个批次，单条消息的协议开销被摊薄到接近零；同时一个 topic 的写入被摊到多个 broker 的多个分区上。如果你把 linger.ms 设成 0、每条消息都同步等待确认、只建一个分区，Kafka 的吞吐会掉到和传统 MQ 同一量级甚至更低。攒批与零拷贝的具体机制详见站内 Kafka 深度原理一篇。

四类真正适合 Kafka 的场景

场景核心诉求为什么必须是 Kafka典型配置取向
日志与埋点收集写入量极大，允许秒级延迟，下游多且会不断新增攒批加分区并行让单集群轻松扛住每秒百万条；同一份日志可被实时告警、离线数仓、ClickHouse 三路独立消费分区数偏大，副本 2 到 3，保留 3 到 7 天，可用 acks=1 换吞吐
数据库变更捕获 CDC严格保持同一行的变更顺序，下游可从任意时点重建按主键做 key 保证同一行落同一分区即天然有序；compact 策略能把日志压成「每个主键的最终态」，新下游可直接从日志重建全量快照key 用主键，cleanup.policy 用 compact，acks=all
流处理与实时指标算子需要重放历史回填状态，需要有序输入状态算子崩溃后可把位点拨回去重算，这一点队列模型根本做不到；Flink 的 exactly-once 依赖的正是可重放的源分区数对齐算子并行度，保留期覆盖最长回溯窗口
服务解耦与事件驱动一个事件多方订阅，上游不该知道下游是谁新增下游只需新增一个 group.id，上游代码零改动；事件日志同时充当审计与对账依据按聚合根做 key，分区数适中，配 Schema Registry 管演进

这四类的共同特征是同一份数据有多个读者，或者需要回溯。只要你的场景里出现了这两个词之一，Kafka 的运维复杂度就买到了对应的价值；两个都没有，就该往下看。

❌
用消费者 sleep 实现延迟，是最危险的一种绕法

很多团队用 Kafka 做延迟消息时，让消费者拉到消息后 sleep 到目标时间再处理。问题是两次 poll 之间的间隔一旦超过 max.poll.interval.ms（默认 5 分钟），协调者会认为这个实例已死并触发重平衡，分区被转给别人，你 sleep 的那条消息会被另一个实例重新拉到并再 sleep 一次，形成无限重平衡加重复处理。重平衡的触发条件详见站内 Kafka 深度原理一篇。

生态组件各自解决什么，为什么多数团队只需要 core

组件解决的具体问题形态与运维成本什么时候值得引入
Kafka Connect外部系统与 Kafka 之间的批量搬运，自带位点管理、失败重试、格式转换distributed 模式需要独立 worker 集群，要管插件版本与 connector 状态机做 CDC 时配 Debezium 很值；只有两三个数据源时自己写生产者更省事

判断标准很简单：这些组件都是为了省掉你自己写的代码，如果你要写的代码比维护它们更少，就别引入。绝大多数业务只用 core 的生产者消费者 API 加一套 Lag 监控，就覆盖了全部需求。

KRaft 取代 ZooKeeper 意味着什么

KRaft 不是「换了个协调服务」，它的思路是把元数据也当成一个 Kafka 日志来存。集群里的主题列表、分区分配、ISR 状态、配置变更全部变成内部元数据主题里的一条条记录，由 controller quorum 用 Raft 协议复制，broker 像普通消费者一样订阅这个日志并增量应用。实际变化有三点：

  • 少一个组件。不用再部署、监控、调优、升级一套 ZooKeeper 集群，也不用再向新人解释「为什么 ZK 挂了 Kafka 还能读写但建不了 topic」。
  • controller 故障切换更快。ZooKeeper 模式下新 controller 上任要从 ZK 全量拉取所有分区的状态，分区数上万时这个过程是秒级甚至十秒级的；KRaft 模式下新 controller 内存里已持有最新元数据，切换是百毫秒级的。
  • 单集群能承载的分区数量级显著提升。瓶颈从「ZK 写入与全量加载」变成「Raft 日志复制」，官方压测从早期的数千分区提升到百万级。

3.5ZooKeeper 模式标记废弃，提供 ZK 到 KRaft 的迁移路径存量集群开始规划迁移，迁移是单向的，无法回退
3.6 到 3.9KRaft 功能补齐，迁移工具成熟迁移的最佳窗口，3.9 是最后一个支持 ZooKeeper 的大版本
4.0 及以后ZooKeeper 支持彻底移除必须先在 3.x 上完成迁移，不能从 ZK 模式直接升到 4.0
✅
新集群不要再纠结这件事

今天搭的任何新集群都应该直接用 KRaft，网上大量「先启动 ZooKeeper 再启动 Kafka」的教程已经过时。存量 ZK 集群的迁移不要拖到 4.0 逼上门再做，因为官方迁移路径只存在于 3.5 到 3.9，跨过这个区间就只能重建集群加数据搬迁。具体的 process.roles、quorum 规划和 kafka-storage.sh format 步骤见站内 Kafka 安装部署一篇。

常见认知误区

流传很广的说法实际情况
Kafka 消息消费完就删了删除只由 retention 或 compact 触发。消费组把 LAG 清零后数据仍完整躺在磁盘上，可以被拨回位点或被新消费组重读
Kafka 保证消息全局有序只保证分区内有序。想要全局有序只能用单分区，代价是吞吐退化成单文件顺序写且无法并行消费
消费者越多消费越快同组内有效消费者数被分区数卡死，多出来的实例完全空转。要提速必须先加分区，而加分区会破坏 key 的顺序性
分区数越多吞吐越高存在明显拐点。每个分区在每台 broker 上占文件句柄，生产端为每个分区维护独立批次缓冲，故障恢复时选举耗时随分区数线性增长。详见站内 Kafka 分区设计一篇
Kafka 不会丢消息默认配置下会丢。acks=1 时 Leader 落盘前宕机即丢；unclean.leader.election.enable=true 时落后副本上任也会丢。可靠性参数组合详见站内 Kafka 深度原理一篇
log compaction 就是压缩compaction 是按 key 去重保留最新值，与压缩算法毫无关系。压缩是 compression.type，取值 gzip、snappy、lz4、zstd
Kafka 延迟一定比 RabbitMQ 高Kafka 的延迟主要来自 linger.ms 攒批，设成 0 后端到端延迟可做到毫秒级，只是吞吐下降。延迟是可调的，不是固有的
位点必须存在 Kafka 内部主题里那只是默认实现。完全可以关掉自动提交，把位点与业务数据写进同一个数据库事务，这是实现端到端 exactly-once 最朴素的办法
❌
入门阶段最容易踩的坑
  • 随手改了 group.id 导致数据从头重放。新 group.id 没有历史位点，按 auto.offset.reset 决定起点。灰度时改组名，等于让下游重刷整个保留期的数据。
  • auto.offset.reset 留默认 latest 导致静默丢数据。消费者停机超过保留期后重启，位点失效，直接跳到队尾，中间数据无声消失，日志里只有一行 WARN。
  • 消费者实例数配得比分区数多。多出的实例不报错也不干活，监控上看到十个 pod 全部 Running，实际只有三个在消费。
  • 指望加消费者实例解决堆积。分区数没变时加实例毫无作用，必须先看每个分区的 LAG 分布，再决定是加分区还是优化单条处理耗时。
  • 以为删除 topic 是同步完成的。删除只是打标记，实际清理受 delete.topic.enable 和文件清理调度影响，删完立刻同名重建可能读到残留数据。
  • 在消费线程里 sleep 做延迟。超过 max.poll.interval.ms 会被踢出组并触发无限重平衡。
  • 没有 key 却指望同一实体的消息有序。无 key 时消息被粘性分区器分散到各分区，同一订单的创建和支付事件可能落在不同分区，顺序完全不保证。
  • 把 retention 设得很短来省磁盘。保留期短于「消费者最长停机时间加故障响应时间」，就等于放弃了重放能力，也就放弃了选 Kafka 的主要理由。
  • 单条消息超过上限导致生产失败。broker 端默认约 1MB，broker、topic、producer、consumer 四处的大小上限必须一起调，只改一处会在另一环节被拒。
  • 只监控总 LAG 不看分区分布。总 LAG 一万可能是均匀堆积，也可能是一个热点分区堆了一万而其余为零，两者的处理方式完全不同。
  • 把 Kafka 当数据库来查。它没有按 key 随机读的能力，只能顺序扫或按 offset 与时间戳定位。需要点查就把数据落到 KV 存储里。
  • 生产环境只部一个 broker。副本数被限制为 1，任何一次重启都是一次数据不可用，磁盘损坏就是永久丢失。
