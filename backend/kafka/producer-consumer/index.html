Kafka 生产者与消费者实战：发送链路、参数矩阵与 poll 循环

🏷️ Kafka

分段日志、ISR 与水位、幂等 Producer 的 PID 加序列号机制、Rebalance 的触发判定，这些原理详见站内 Kafka 深度原理一篇。这里只解决一件事：客户端代码到底怎么写、参数到底怎么配才不出事。参数名统一用 Java 客户端的官方命名，Go 的 sarama 与 confluent-kafka-go 只是换了个壳，语义一一对应，文中会标出映射关系。

send() 不是「发送」，只是「入队」

线上丢消息的故障，一大半的根子在对这一行的误解：producer.send(record) 返回的那一刻，消息极可能还在本进程的堆内存里，一个字节都没出网卡。真实链路是业务线程走完拦截器、序列化、分区器，把消息追加到 RecordAccumulator 中该分区的 batch 双端队列然后立刻返回；真正的 ProduceRequest 由一个独立的 Sender 线程发出。

这张图能直接解释四个现象。第一，Callback 是在 Sender 线程上执行的，你在回调里查数据库、调接口，会把整个 Producer 的发送吞吐拖死。第二，多个分区的 batch 只要 leader 在同一个 Broker 上，就会被合并成一个请求发出，所以分区数变多不一定线性增加请求数。第三，buffer.memory 是所有分区共享的，某个分区的 leader 挂了导致 batch 堆积，会连带拖慢其他分区。第四，进程退出时这块内存里的东西没有任何持久化，谁都救不了。

send() 的三种用法，只有一种是对的

写法代码形态吞吐量级失败时的表现能用吗
fire and forgetproducer.send(record)，返回值直接丢弃最高异常被吞掉，消息丢了没有任何痕迹，监控上看不出来只有埋点、debug 日志这类允许静默丢失的场景可以用
同步阻塞producer.send(record).get()最低，通常只有异步的百分之几抛异常，调用方能感知不可用于高吞吐链路。get 会让攒批彻底失效，每条消息都要等一次完整 RTT
异步加回调producer.send(record, callback)高，与 fire and forget 接近回调拿到 exception，可分流到死信或本地 WAL唯一正确的生产写法
⚠️
同步发送慢的真正原因不是「等 ack」

很多人以为 send().get() 慢是因为多等了一个 acks 的往返。实际更致命的是它把批处理打散了：业务线程在 get 上阻塞，下一条消息根本进不了 accumulator，每个 batch 永远只有一条记录。同样的 acks 配置下，异步加回调能攒出几百条一批，吞吐差出一到两个数量级。

package main

import (
	"errors"
	"log"
	"time"

	"github.com/IBM/sarama"
)

// 生产级 AsyncProducer：攒批 + 压缩 + 幂等 + 回调分流
func newProducer(brokers []string) (sarama.AsyncProducer, error) {
	cfg := sarama.NewConfig()
	cfg.Version = sarama.V3_6_0_0
	cfg.Producer.RequiredAcks = sarama.WaitForAll         // 等价 acks=all
	cfg.Producer.Idempotent = true                        // 幂等，消除重试带来的重复
	cfg.Net.MaxOpenRequests = 1                           // sarama 开幂等时强制要求为 1
	cfg.Producer.Retry.Max = 10
	cfg.Producer.Retry.Backoff = 100 * time.Millisecond
	cfg.Producer.Flush.Bytes = 64 * 1024                  // 等价 batch.size=64KB
	cfg.Producer.Flush.Frequency = 10 * time.Millisecond  // 等价 linger.ms=10
	cfg.Producer.Compression = sarama.CompressionZSTD     // 等价 compression.type=zstd
	cfg.Producer.Return.Successes = true                  // 不开这个，Successes 通道永远是空的
	cfg.Producer.Return.Errors = true
	return sarama.NewAsyncProducer(brokers, cfg)
}

// 必须有常驻 goroutine 把两个结果通道读走。
// 不读 Errors 通道，通道满之后 Input() 会把业务线程整体阻塞住，这是 sarama 最常见的挂起原因。
func drainResults(p sarama.AsyncProducer, toDLQ func(*sarama.ProducerMessage, error)) {
	for {
		select {
		case ok, more := <-p.Successes():
			if !more {
				return
			}
			_ = ok // 需要审计时记录 ok.Topic / ok.Partition / ok.Offset
		case e, more := <-p.Errors():
			if !more {
				return
			}
			switch {
			case errors.Is(e.Err, sarama.ErrMessageSizeTooLarge),
				errors.Is(e.Err, sarama.ErrInvalidTopic),
				errors.Is(e.Err, sarama.ErrTopicAuthorizationFailed):
				// 不可重试：重发一万次结果完全一样，直接进死信并告警
				toDLQ(e.Msg, e.Err)
			default:
				// 可重试错误已被客户端重试到 Retry.Max 仍失败，落本地 WAL 交补偿任务
				log.Printf("produce failed after retries: %v", e.Err)
				toDLQ(e.Msg, e.Err)
			}
		}
	}
}

// 退出路径：AsyncClose 会把累积的 batch 刷出去，再关闭两个结果通道。
// 直接 os.Exit 或被 kill -9，accumulator 里的消息全部无声消失。
func shutdown(p sarama.AsyncProducer) {
	p.AsyncClose()
	time.Sleep(2 * time.Second) // 给 drainResults 收尾的时间，或用 WaitGroup 精确等待
}

Properties props = new Properties();
props.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, "kafka-1:9092,kafka-2:9092");
props.put(ProducerConfig.KEY_SERIALIZER_CLASS_CONFIG, StringSerializer.class.getName());
props.put(ProducerConfig.VALUE_SERIALIZER_CLASS_CONFIG, StringSerializer.class.getName());
props.put(ProducerConfig.ACKS_CONFIG, "all");
props.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, true);
props.put(ProducerConfig.LINGER_MS_CONFIG, 10);            // 默认 0，调到 10ms 收益最大
props.put(ProducerConfig.BATCH_SIZE_CONFIG, 64 * 1024);    // 默认 16KB
props.put(ProducerConfig.COMPRESSION_TYPE_CONFIG, "zstd"); // 默认 none
props.put(ProducerConfig.DELIVERY_TIMEOUT_MS_CONFIG, 120_000); // 重试的总时间上限
props.put(ProducerConfig.MAX_BLOCK_MS_CONFIG, 5_000);      // buffer 满时 send 最多阻塞 5s

KafkaProducer<String, String> producer = new KafkaProducer<>(props);

public void sendOrder(String key, String payload) {
    ProducerRecord<String, String> record =
            new ProducerRecord<>("order.created", key, payload);

    producer.send(record, (meta, ex) -> {
        if (ex == null) {
            // 注意：这里跑在 Sender 线程上，禁止做 IO，禁止加锁等待
            metrics.recordOk(meta.partition(), meta.offset());
            return;
        }
        // 能走到这里，说明客户端内部的重试已经耗尽 delivery.timeout.ms
        if (ex instanceof RecordTooLargeException
                || ex instanceof SerializationException
                || ex instanceof InvalidTopicException
                || ex instanceof AuthorizationException) {
            deadLetter.save(key, payload, ex);   // 不可重试，重发无意义
        } else if (ex instanceof RetriableException) {
            localWal.append(key, payload);        // 集群侧问题，交给补偿任务重投
        } else {
            localWal.append(key, payload);
            alarm.fire("unknown produce error", ex);
        }
    });
}

@PreDestroy
public void shutdown() {
    producer.flush();                       // 显式 flush，卡住时日志里能看出来
    producer.close(Duration.ofSeconds(10)); // 给在途请求 10 秒，不要传 Duration.ZERO
}

异常可重试典型触发原因正确处理
NotLeaderOrFollowerException是Leader 切换，客户端元数据过期不用管，客户端刷新元数据后自动重发。日志里偶发几条是正常的
NotEnoughReplicasException是ISR 收缩到小于 min.insync.replicas不用管，但要告警。持续出现说明副本跟不上，是集群问题
TimeoutException是batch 在 accumulator 里等太久，或 buffer 满导致 send 阻塞超时区分两种：回调里的超时是发送超时；send 直接抛的超时是 max.block.ms 到了，说明 buffer 不够或者 Broker 卡住
RecordTooLargeException否单条超过 max.request.size 或 Broker 的 message.max.bytes进死信。大消息应改为存对象存储只传引用，不要靠调大上限硬顶
SerializationException否对象里有无法序列化的字段，Schema 不兼容进死信并报警。这是代码缺陷，重试只会刷日志
TopicAuthorizationException否ACL 没开，或 SASL 身份错误进死信。上线时最常见的一次性故障，改配置后重启
OutOfOrderSequenceException否幂等 Producer 的序列号断档，通常伴随 Broker 端过期了 PID 状态Producer 已进入不可用状态，必须重建实例。仅靠捕获异常继续发会持续失败
UnknownProducerIdException否消息滞留时间超过 retention，Broker 侧丢掉了该 PID 的序列号重建 Producer。长时间空闲加短 retention 的组合容易触发

关闭 Producer：close 到底会不会丢消息

「close 会丢消息，所以必须先 flush」这个说法只对了一半。Java 客户端的 close() 无参版本本身就会阻塞等待所有已发送记录完成，语义上等价于先 flush 再关。真正丢消息的是下面这几种关闭方式。

关闭方式实际行为结果
close() 无参阻塞等待 accumulator 排空与在途请求返回，回调全部执行完不丢。但如果 Broker 挂了会一直等到 delivery.timeout.ms
close(Duration.ofSeconds(10))最多等 10 秒，超时后放弃剩余记录并给它们回调 TimeoutException推荐写法。超时丢失的部分能在回调里落 WAL，至少有痕迹
close(Duration.ZERO)立即关闭，在途请求和缓冲区全部作废直接丢。有些框架的快速关闭钩子里就是这么写的，需要检查
不调用 close，JVM 自然退出Producer 的 IO 线程是守护线程，进程退出时被直接终止缓冲区里的消息全丢。这是上线后最常见的丢消息原因之一
SIGKILL 或容器 OOMKilled没有任何钩子能执行全丢。只能靠缩短 linger.ms 和本地 WAL 缩小窗口
sarama AsyncProducer 只 Close 不排空通道Close 内部会等待，但如果没人读 Successes 或 Errors 会死锁进程卡死在退出阶段，最后被超时强杀，仍然丢
❌
Kubernetes 场景必须对齐三个超时

Pod 收到 SIGTERM 后有 terminationGracePeriodSeconds（默认 30 秒）的窗口。你的关闭钩子里 close(timeout) 的超时必须明显小于这个值，而 delivery.timeout.ms 又不能大到让 close 等不完。三者不匹配的典型现象是：滚动发布时每次都丢几百条消息，但压测时怎么都复现不出来。

「poll 负责发心跳」是 0.10.0 时代的旧说法

从 0.10.1 起，心跳由独立的后台线程发送，处理消息期间心跳不会断，所以 session.timeout.ms 不再受业务处理耗时影响。真正约束处理耗时的是 max.poll.interval.ms：超过它协调者会认为你卡死并踢出组。这两个参数的分工搞混，就会写出「把 session.timeout.ms 调到 10 分钟来解决处理慢」这种无效修法。

参数默认值调大以后延迟调大以后吞吐注意
fetch.min.bytes1升高，最多多等 fetch.max.wait.ms升高，请求数下降调到 64KB 到 1MB 对流量大的 Topic 效果明显，对低流量 Topic 只会平白增加延迟
fetch.max.wait.ms500升高，是上一项的等待上限略升只有在 fetch.min.bytes 大于 1 时才有意义
max.partition.fetch.bytes1048576，即 1MB基本不变升高必须不小于 Broker 的 message.max.bytes，否则遇到大消息会卡在原地反复拉不动
fetch.max.bytes52428800，即 50MB基本不变升高整个请求的上限。分区多时它比单分区上限更早成为瓶颈

session.timeout.ms45000，3.0 之前是 10000不影响不影响必须在 Broker 的 group.min.session.timeout.ms 与 group.max.session.timeout.ms 之间，且至少为心跳间隔的三倍

auto.offset.reset：一个参数引发的历史消息洪水

取值无已提交位点时位点越界时典型事故
earliest从分区最早的可用位点开始重置到最早位点改了 group.id 或重建集群后上线，瞬间把保留期内的全部历史消息重放一遍，下游数据库被打爆
latest从当前末尾开始，只消费新消息跳到末尾，中间的消息被静默跳过消费者停机超过 retention 后重启，看起来恢复正常，实际上积压的数据全部丢了且无任何日志
none抛 NoOffsetForPartitionException抛异常不会静默出错，但需要你自己写兜底逻辑。对账类、金额类任务应该选它

这个参数只在两个时刻生效：消费组在该分区上没有已提交位点，或者已提交位点已经被 retention 清理掉了。正常运行期间它完全不参与决策，所以「我配了 earliest 会不会每次重启都从头消费」这个担心是多余的——只要位点还在，就从位点续。反过来，一旦你动过 group.id、清理过 __consumer_offsets、或者迁移了集群，它就会立刻生效。稳妥做法是上线前先用脚本把位点摆好：

# 查看消费组当前位点与 Lag 分布，先确认哪些分区落后
kafka-consumer-groups.sh --bootstrap-server kafka-1:9092 \
  --describe --group order-processor

# 新消费组上线前，把位点预置到末尾，避免 earliest 引发历史洪水
# 必须在消费者全部停止的状态下执行，否则报 Assignment can not be reset
kafka-consumer-groups.sh --bootstrap-server kafka-1:9092 \
  --group order-processor --topic order.created \
  --reset-offsets --to-latest --execute

# 事故回放：把位点重置到 30 分钟前，--dry-run 先看会移动到哪
kafka-consumer-groups.sh --bootstrap-server kafka-1:9092 \
  --group order-processor --topic order.created \
  --reset-offsets --by-duration PT0H30M --dry-run

分区内有序保证破坏，除非再按 key 路由到固定 worker保证
位点管理直接 commitSync，几行代码必须自建每分区水位表，是这个方案的主要复杂度来源直接 commitSync
Rebalance 处理简单，回调里提交一次即可复杂，要在 revoke 回调里等任务排空，否则重复消费范围不可控简单
失败重试原地处理，会阻塞分区可以在 worker 内重试不阻塞拉取，但会乱序原地处理，阻塞该实例负责的分区
运维成本最低代码复杂，出问题难排查多占几个 Pod，但故障隔离最好
适用场景低流量、强顺序、逻辑简单分区数无法再扩且单条处理很慢，例如调用外部慢接口绝大多数业务的默认选择
✅
先加分区再加线程

并发度上限等于分区数，一个分区在同一消费组内只会被一个成员消费，加到第 N+1 个实例时它会完全空转。所以扩容顺序是：先确认分区数够不够，再考虑加实例，最后才考虑线程池。只有在「分区数已经因为顺序性或成本原因不能再加，而单条处理耗时又下不来」时，线程池才是合理选项。

优雅关闭、背压与重放

close() 在另一个线程里调用是不安全的，KafkaConsumer 不是线程安全类。唯一允许跨线程调用的方法是 wakeup()，它会让阻塞在 poll 上的线程抛出 WakeupException，从而跳出循环走收尾逻辑。背压用 pause() 而不是 sleep：sleep 会让你逼近 max.poll.interval.ms 触发 Rebalance，而 pause 之后仍然可以正常 poll 维持组成员身份，只是不再返回被暂停分区的数据。

private final KafkaConsumer<String, String> consumer;
private final AtomicBoolean running = new AtomicBoolean(true);
private final Map<TopicPartition, OffsetAndMetadata> pending = new HashMap<>();

public void run() {
    consumer.subscribe(List.of("order.created"), new ConsumerRebalanceListener() {
        @Override
        public void onPartitionsRevoked(Collection<TopicPartition> parts) {
            // 让出分区之前把已处理的位点交上去，能显著缩小重复消费范围
            if (!pending.isEmpty()) {
                consumer.commitSync(pending);
                pending.clear();
            }
        }
        @Override
        public void onPartitionsAssigned(Collection<TopicPartition> parts) {
            // 位点存在业务库时在这里 seek 回去；否则走 __consumer_offsets 自动定位
            for (TopicPartition tp : parts) {
                Long off = offsetStore.load(tp);
                if (off != null) consumer.seek(tp, off);
            }
        }
    });

    try {
        while (running.get()) {
            ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(500));
            for (ConsumerRecord<String, String> r : records) {
                handle(r);  // 业务处理，失败策略见站内可靠性一篇
                pending.put(new TopicPartition(r.topic(), r.partition()),
                            new OffsetAndMetadata(r.offset() + 1)); // 必须加 1
            }
            if (!pending.isEmpty()) {
                consumer.commitSync(pending);   // 先处理后提交，语义是 at-least-once
                pending.clear();
            }
            // 背压：下游积压就暂停拉取，注意仍然要继续调 poll 来保持组成员身份
            if (downstreamDepth() > HIGH_WATER) {
                consumer.pause(consumer.assignment());
            } else if (!consumer.paused().isEmpty() && downstreamDepth() < LOW_WATER) {
                consumer.resume(consumer.paused());
            }
        }
    } catch (WakeupException ignored) {
        // 正常退出路径：别的线程调了 wakeup
    } finally {
        try {
            if (!pending.isEmpty()) consumer.commitSync(pending);
        } finally {
            consumer.close(Duration.ofSeconds(5)); // close 会主动发 LeaveGroup 加快 Rebalance
        }
    }
}

// 供信号处理线程调用：这是唯一能安全打断阻塞在 poll 上的消费线程的方法
public void stop() {
    running.set(false);
    consumer.wakeup();
}

type handler struct{ biz *Service }

func (h *handler) Setup(sarama.ConsumerGroupSession) error   { return nil }
func (h *handler) Cleanup(sarama.ConsumerGroupSession) error { return nil }

// sarama 为每个被分配到的分区起一个 goroutine 调用 ConsumeClaim，
// 分区内天然串行，等价于「每分区一个单线程消费者」，有序性不用自己管。
func (h *handler) ConsumeClaim(s sarama.ConsumerGroupSession, c sarama.ConsumerGroupClaim) error {
	for {
		select {
		case msg, more := <-c.Messages():
			if !more {
				return nil
			}
			if err := h.biz.Handle(msg); err != nil {
				return err // 返回错误会让整个 session 重建，位点不推进，消息会被重投
			}
			s.MarkMessage(msg, "") // 只是标记，真正提交按 Consumer.Offsets.AutoCommit 周期进行
		case <-s.Context().Done():
			// Rebalance 或关闭信号，必须立刻返回，否则会拖住整个组的 Rebalance
			return nil
		}
	}
}

func consume(ctx context.Context, brokers []string) error {
	cfg := sarama.NewConfig()
	cfg.Version = sarama.V3_6_0_0
	cfg.Consumer.Offsets.Initial = sarama.OffsetNewest // 等价 auto.offset.reset=latest
	cfg.Consumer.Offsets.AutoCommit.Enable = false     // 关掉自动提交，出错时自己控制
	cfg.Consumer.Group.Rebalance.GroupStrategies = []sarama.BalanceStrategy{
		sarama.NewBalanceStrategySticky(), // 粘性分配，减少 Rebalance 时的分区搬迁
	}
	group, err := sarama.NewConsumerGroup(brokers, "order-processor", cfg)
	if err != nil {
		return err
	}
	defer group.Close()

	for {
		// Consume 每次返回都意味着经历了一次 Rebalance，必须放在循环里重新进入
		if err := group.Consume(ctx, []string{"order.created"}, &handler{}); err != nil {
			return err
		}
		if ctx.Err() != nil {
			return ctx.Err()
		}
	}
}

重放靠 seek()：按位点用 seek(tp, offset)，按时间用 offsetsForTimes() 先把时间戳换成位点再 seek。注意 seek 只对已经分配给当前成员的分区生效，刚 subscribe 之后立刻 seek 会抛 IllegalStateException，正确位置是在 onPartitionsAssigned 回调里，或者先 poll 一次拿到分配结果再 seek。

❌
最容易踩的坑
  • 提交位点忘了加 1：commitSync 提交的是「下一条要读的位置」，传 r.offset() 而不是 r.offset() + 1，每次重启都会重复消费每个分区的最后一条。
  • 在 Callback 里做 IO：回调跑在 Sender 线程上，里面查一次数据库，整个 Producer 的吞吐直接塌成个位数 QPS。
  • sarama 开了 Return.Errors 却没人读通道：通道满之后 Input() 阻塞，表现是业务线程集体卡在发消息上，且没有任何错误日志。
  • close(Duration.ZERO) 或者压根不调 close：accumulator 里的消息随进程一起消失，日志里一行痕迹都没有。
  • 用 sleep 做背压：处理线程 sleep 超过 max.poll.interval.ms 就被踢出组，接着提交位点失败、Rebalance、重复消费，形成雪崩。要用 pause()。
  • 把 session.timeout.ms 调大来解决处理慢：无效。0.10.1 之后心跳在独立线程，限制处理耗时的是 max.poll.interval.ms。
  • 多线程共用一个 KafkaConsumer 实例：它不是线程安全的，会抛 ConcurrentModificationException。跨线程只能调 wakeup()。
  • 改 group.id 上线时忘了 auto.offset.reset 是 earliest：保留期内的历史消息会被瞬间重放一遍，下游被打爆。
  • 只调大了客户端的 max.request.size：Broker 的 message.max.bytes 和 Topic 级 max.message.bytes 没跟上，大消息在服务端被拒且不可重试。
  • max.partition.fetch.bytes 小于单条消息大小：该分区会永久卡住，反复拉取同一条却永远返回不完整，Lag 只增不减。
  • 消费者实例数超过分区数：多出来的实例完全空转，还会在每次发布时多触发一轮 Rebalance。
  • 线程池消费却按批次提交最大位点：只要有一个 worker 还没跑完，那条消息就永久丢失且无法察觉。必须提交连续完成区间的最小位点。
