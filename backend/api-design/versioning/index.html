API 版本与兼容性演进：兼容判定、版本承载、废弃与下线

🏷️ API 版本

这篇只回答一个问题：怎么在不破坏现有客户端的前提下改接口。注意「不破坏客户端」和「开新版本」是两件不同的事——大部分团队一遇到改动就想开 v2，结果三年后同时维护 v1、v2、v3，每个需求改三遍，而真正的原因只是当初那个改动本来可以做成兼容的。REST 的落地细节见本目录 RESTful 篇，错误结构与分页约定见最佳实践篇。

先分清两件事：版本升级与兼容性演进

判断标准只有一句话：一个完全不改代码的老客户端，在你的改动上线后还能不能正常工作。能，就是兼容性演进，在当前版本直接改；不能，才是版本升级。

最后那条分支最值得强调：「这个字段应该没人用」是线上事故的标准开场白。没有调用方维度的监控数据，任何删除都是赌博，而赌输的代价是第三方系统在没有告知的情况下集体报错。

兼容与不兼容变更的判定表

兼容变更 为什么安全 前提条件（不满足就会变成不兼容）
响应里新增字段 老客户端按名取值，多出来的字段会被忽略 客户端反序列化必须容忍未知字段。部分强类型库默认对未知字段报错，需要确认配置
请求里新增可选参数 不传时行为与原来完全一致 默认值必须等于老行为，不能借机顺手改默认值
新增端点 老客户端根本不会调用它 不能挤占已有路由的匹配优先级，尤其当心把 /orders/export 塞进 /orders/{id} 的模式里
放宽入参校验 原来能过的现在还能过 放宽后的数据不能让响应结构变化，比如原来最多 20 条现在允许 200 条要确认分页语义不变
新增枚举值 老客户端遇到的是未见过的值而不是结构变化 必须先确认客户端对未知枚举的处理：switch 穷举会落进错误分支，强类型反序列化可能直接失败
新增可选的响应头 老客户端不读就不受影响 如果参与缓存键就必须同步配 Vary
性能优化与内部重构 对外行为不变 字段顺序、数组默认排序若被客户端依赖，就已经是隐式契约的一部分
不兼容变更 客户端具体怎么被打挂
删除或重命名响应字段 强类型客户端反序列化时缺必填字段直接抛异常；前端读到 undefined 后渲染崩溃或显示空白
改字段类型 最经典的是把数字 ID 改成字符串以支持雪花 ID，客户端的整型解析溢出或类型断言失败；还有布尔改枚举
改字段语义但不改名 最危险的一类，因为没有任何报错。amount 从元改成分、status 的某个值含义变了，客户端照旧解析，业务数字全错
可选参数变必填 或 校验变严 老客户端不传该参数，从此全部 400；把长度上限从 200 收到 50 会让历史数据的更新请求全部失败
改默认值 不传参数的老客户端行为突变。把 page_size 默认值从 20 改成 10，依赖默认值的调用方少收一半数据却不报错
删除端点或改变 URL 老客户端全部 404。移动端已发版的包无法撤回，影响期等于用户的升级周期，通常是几个月
改错误码或状态码含义 客户端的重试与分支逻辑基于状态码。把并发冲突从 409 改成 500，上游会开始无脑重试
改分页语义 从 offset 改成 cursor、或 total 不再返回，分页组件直接失效；页码的边界行为变化会导致漏数据
把可空字段改成不可空 或 反之 客户端按非空处理时遇到 null 崩溃；按可空处理时又可能漏掉空值判断分支
收紧限流阈值 常被忽略但确实是破坏性变更：批处理调用方会从正常变成大面积 429

四种版本承载方式

维度 URL 路径 如 /v1/orders 查询参数 如 version=1 自定义头 如 X-API-Version Accept 媒体类型协商
可见性与调试 最好。日志里一眼看出版本，链接可直接分享复现 好，但容易和业务参数混在一起被忽略 差。抓包或翻日志才知道，忘带就落到默认版本 最差。头部长且容易写错，排查时几乎没人第一时间去看
缓存友好度 最好。不同版本天然是不同缓存键 好，但要确认 CDN 是否把该参数纳入缓存键 差。必须正确配置 Vary，漏配就会把 v2 响应发给 v1 客户端 差。同样依赖 Vary，且共享缓存对复杂 Accept 的处理参差不齐
路由与灰度实现 最简单。按前缀分流、按版本独立部署、按版本灰度都是现成能力 中。网关按参数路由的支持不如按路径普遍 中。需要网关支持按头路由 最复杂。要解析带 q 值的媒体类型列表并做优先级匹配
是否符合 REST 理念 不符合。同一资源出现了多个地址 不符合，同上 基本符合 最符合。资源地址唯一，表示形式靠协商
客户端接入成本 最低。改一个 base URL 即可 低，但每个请求都要记得带 中。需要在 SDK 或拦截器里统一注入 高。需要手写完整媒体类型字符串
适用场景 对外开放 API、需要长期共存多版本、需要按版本灰度 临时兼容或内部工具，不建议作为主方案 内部服务间、单页应用统一由 SDK 注入的场景 对 REST 规范有强要求的团队，或需要同时协商格式与版本
✅
推荐

对外 API 用 URL 路径版本，务实、好排查、灰度简单，理念上的不纯粹换来的是实打实的运维便利。内部服务间不做 URL 版本，而是靠契约版本加兼容性约束：proto 的 package 带 v1（真正的大改才升 package），日常演进全部走「只加不删」的兼容规则，靠 CI 的破坏性变更检查兜底。版本号只写主版本，不要写 v1.2.3：次版本号意味着兼容变更，而兼容变更本来就不需要让客户端感知。

版本粒度：整体、按资源、还是按端点

粒度 做法 代价 什么时候合适
整体版本 全站一个 v1，升级时整套接口复制成 v2 没变化的接口也要复制一份，v2 里九成代码是重复的；两套代码后续修 bug 要改两处，很容易漏 对外开放平台、SDK 按版本打包发布、接口数量不多
按资源版本 /v2/orders 与 /v1/users 可以并存 调用方需要记住每个资源各自的版本，文档与 SDK 组织变复杂 资源之间耦合弱、演进节奏差异大的大型系统
按端点版本 每个端点独立带版本 版本矩阵爆炸，很快没人说得清「当前线上到底有哪些组合」，测试组合数不可控 基本不推荐，只在极少数超大规模平台上作为过渡手段
不做版本，只做兼容 永远只有一套接口，全部改动按兼容规则演进，废弃字段靠标记与监控逐步退场 对纪律要求最高，需要契约检查与字段级用量统计支撑 内部服务间、GraphQL、以及有能力做契约测试的团队；这也是长期成本最低的方式

实践中最省事的组合是整体版本加兼容性演进：URL 上只有一个 v1，绝大多数改动做成兼容的，只有真正的整体语义重构才开 v2，并且开 v2 的同一天就要写好 v1 的日落时间。

### 废弃阶段：响应仍然正常，但必须把废弃信息带出去
GET /v1/orders/1001 HTTP/1.1
Host: api.example.com

HTTP/1.1 200 OK
Content-Type: application/json
Deprecation: @1767139200
Sunset: Wed, 31 Dec 2026 23:59:59 GMT
Link: <https://docs.example.com/migrate/v1-to-v2>; rel="deprecation"; type="text/html"
Warning: 299 - "v1 将于 2026-12-31 下线，请迁移到 v2"

### 下线之后：用 410 明确区分「曾经存在但已移除」和「路径写错」
GET /v1/orders/1001 HTTP/1.1

HTTP/1.1 410 Gone
Content-Type: application/problem+json

{"type":"https://docs.example.com/probs/version-removed","title":"该 API 版本已下线","status":410,"detail":"v1 已于 2026-12-31 下线，请改用 /v2/orders/1001","sunset":"2026-12-31","migration_guide":"https://docs.example.com/migrate/v1-to-v2"}

Deprecation 与 Sunset 是有标准定义的 HTTP 头，价值在于机器可读：调用方可以在自己的 SDK 或网关里检测它们并打告警，而不是依赖有没有人看到你发的邮件。真实项目里非常值得再做一件事：在服务端把带废弃头的响应按调用方聚合成指标，这样你能直接看到「谁收到了废弃通知却还在调」。

下线一个版本的完整流程

下线难，不是因为技术难，而是因为不知道还有谁在调。没有调用方监控就永远不敢按下按钮，这是版本无限累积的根本原因。

sequenceDiagram autonumber participant M as 用量监控 participant P as 平台方 participant C1 as 已迁移调用方 participant C2 as 沉默调用方 P->>M: 查询 v1 各端点按调用方聚合的调用量 M-->>P: 列出 37 个调用方 其中 5 个占 98% 流量 Note over P,M: 前提是每个请求都能识别调用方
靠应用 ID 或带标识的 User-Agent 强制约束 P->>C1: 发布废弃公告 给出迁移文档与截止日期 P->>C2: 同一封公告 但对方没有人在看 P->>M: 上线后在 v1 响应里加 Deprecation 与 Sunset 头 C1->>P: 完成迁移 v1 调用量归零 P->>M: 按调用方核对剩余流量 M-->>P: 仅剩 C2 且集中在两个端点 P->>C2: 一对一联系 确认负责人与迁移排期 P->>C2: 灰度阻断 按比例返回 410 并保留一键回滚 Note over P,C2: 灰度阻断是最关键一步 它能把
没人看公告的调用方逼出来 同时不制造全量故障 P->>C2: 到期全量下线 返回 410 与迁移指引 P->>M: 保留 v1 的路由与监控三个月 观察残留调用
阶段 关键动作 可执行的判据
摸清调用方 按版本、端点、调用方三维打点，强制调用方携带身份 能回答「过去 30 天有哪些应用调过这个端点，各多少次」才算合格
公告与迁移期 发文档、给差异清单与代码示例、提供并行环境 迁移期长度至少覆盖移动端一个完整发版周期，通常 3 到 6 个月
灰度警告 响应加废弃头，并按调用方聚合「收到警告仍在调用」的量 该指标连续两周不下降，就说明公告没人看，必须升级手段
灰度阻断 按比例或按调用方返回 410，并保留一键回滚开关 从 1% 开始，每级观察一个工作日，出现未知调用方立刻回滚并沟通
全量下线 返回 410 与迁移指引，保留路由与监控一段时间 残留调用量降到零并稳定一个月后，才删代码

内部服务：靠 Protobuf 的编号规则而不是版本号

内部服务的调用方是可控的，但「可控」不等于「可以同时发布」。灰度期间必然出现新服务端对老客户端、老服务端对新客户端两种组合，所以契约必须双向兼容。Protobuf 的兼容规则非常明确，照做就不会出问题。

syntax = "proto3";
package order.v1; // 只在整体语义重构时才升到 order.v2，日常演进不动它

message Order {
  // 铁律一：编号只增不减。线上格式只传编号不传字段名，编号就是唯一标识。
  string order_id = 1;
  int64  amount_cents = 2;   // 金额一律用最小单位整数，避免浮点误差

  // 铁律二：删除字段时用 reserved 把编号和名字一起占住。
  // 曾经有过 string email = 3; 现在删了，但 3 号永远不能再被复用：
  // 老客户端仍按 3 号解析，一旦复用就会把新字段的值填进 email 里，静默串数据。
  reserved 3;
  reserved "email";

  // 铁律三：新增字段一律用新编号，且必须能容忍缺失。
  // proto3 里标量字段没有 has 语义，零值和未设置无法区分，
  // 需要区分时用 optional 关键字（proto3 已支持）或包装类型。
  optional string coupon_id = 8;

  // 铁律四：枚举必须预留零值作为未知，否则新增枚举值时老端会落进错误分支。
  Status status = 4;

  // 编号 1 到 15 只占一个字节的 tag，高频字段优先用小编号；
  // 16 到 2047 占两个字节。别把高频字段排到 16 以后。
}

enum Status {
  STATUS_UNSPECIFIED = 0; // 必须有，且客户端要把它当成未知而不是默认业务态
  STATUS_CREATED = 1;
  STATUS_PAID = 2;
  STATUS_CANCELLED = 3;
}

// 会静默出错的改动清单（CI 必须卡住）：
//   改字段编号、复用已删除编号、改字段类型（int32 换 string）、
//   把 optional 改成 repeated、改 package 名、删除 RPC 方法。
// 相对安全的改动：加字段、加 RPC 方法、加枚举值、int32 与 int64 之间的部分互换。

数据库联动演进与 CI 卡口

API 的不兼容变更往往源自数据库改动。直接 ALTER TABLE ... RENAME COLUMN 意味着代码和表结构必须同时切换，而滚动发布期间新旧代码并存，必然有一方报错。正确做法是扩展、迁移、收缩三阶段。

# CI 里的破坏性变更卡口：让流水线而不是评审人去发现不兼容
# 光靠人看 diff 一定会漏，尤其是删字段和改类型这种一行的改动
name: api-compat
on: [pull_request]
jobs:
  openapi-breaking:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }
      # oasdiff 只把破坏性变更判为失败，新增字段这类兼容变更放行
      - name: OpenAPI 破坏性变更检查
        run: |
          git show origin/main:openapi.yaml > /tmp/base.yaml
          docker run --rm -v /tmp:/spec -v "$PWD":/head tufin/oasdiff \
            breaking /spec/base.yaml /head/openapi.yaml --fail-on ERR

  proto-breaking:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      # buf 的 WIRE_JSON 级别会卡住改编号、改类型、复用 reserved 编号
      - uses: bufbuild/buf-action@v1
        with:
          breaking: true
          breaking_against: 'https://github.com/org/repo.git#branch=main'

  consumer-contract:
    runs-on: ubuntu-latest
    steps:
      # 消费者驱动契约：各调用方把自己实际依赖的字段与断言发布成 pact
      # 提供方每次改动都要用全部已发布的 pact 回放验证
      # 它能发现 OpenAPI 检查发现不了的东西：字段虽在但语义变了
      - name: 回放全部消费者契约
        run: pact-broker can-i-deploy --pacticipant order-api --version "$GIT_SHA" --to-environment production

反模式与最容易踩的坑

反模式 后果 改法
每次改动都开新版本 三年后同时维护四套接口，一个 bug 修四处，测试矩阵指数增长 默认按兼容演进，只有整体语义重构才升主版本
v2 上线后 v1 永不下线 维护成本永久叠加，安全补丁要打多份，新人无法判断该改哪套 开 v2 的同一天就写下 v1 的 sunset 日期并进入生命周期流程
在同一版本里做破坏性变更 老客户端在毫无预警的情况下批量报错，移动端只能等用户升级 破坏性变更必须换版本或换端点；CI 卡口负责拦住偷偷提交的这类改动
用「小改动应该没人用到」赌运气 典型的事故开场白，第三方调用方往往正好依赖那个字段 先补调用方与字段级用量监控，用数据说话
版本号带日期但没有废弃流程 看起来很规范，实则积累出十几个日期版本，没有一个敢下线 版本数量要有硬上限，比如线上最多两个受支持版本
下线时直接返回 404 调用方以为是自己路径写错，反复排查甚至重试，而不去看迁移文档 返回 410 Gone，并在错误体里带 sunset 时间与迁移指引链接
把版本判断散落在业务代码里 到处是按版本分支的 if，删旧版本时根本清不干净 版本差异收敛在入口的适配层，业务层只有一份模型
❌
最容易踩的坑
  • 把金额单位从元改成分却不改字段名，没有任何报错，所有未迁移的调用方数字全错一百倍。
  • 为支持雪花 ID 把数字型 id 改成字符串，JavaScript 客户端本来就在 2 的 53 次方处丢精度，这次直接类型断言失败。
  • 新增枚举值没确认客户端容错，老端 switch 穷举后落进异常分支，页面白屏。
  • 把某个可选参数改成必填，老客户端从此全部 400，而这个改动在 diff 里只有一行。
  • 顺手把 page_size 默认值从 20 调成 10，依赖默认值的调用方少收一半数据且不报错，几天后才被业务发现。
  • proto 里改了字段编号或复用了已删除的编号，老客户端把新字段的值解析进老字段，静默串数据。
  • proto 删字段时只删了行没写 reserved，半年后有人把这个编号又用了一遍。
  • 用请求头承载版本却漏配 Vary，CDN 把 v2 的响应发给了 v1 客户端。
  • 直接 RENAME COLUMN，滚动发布期间新旧代码并存，其中一方查询报字段不存在。
  • 回填历史数据时一条 UPDATE 全表跑，主从延迟飙升，从库读接口全线超时。
  • 只在网关层统计总量不区分调用方，于是永远回答不了「还有谁在用」，v1 从此不可能下线。
  • 下线公告只发邮件不发废弃响应头，没人看邮件，到期直接断掉造成第三方集体故障。
  • 全量下线不走灰度阻断，一次性返回 410，事故范围直接等于所有未迁移调用方。
  • 收紧限流阈值时没当成破坏性变更处理，批处理调用方一夜之间大面积 429。
  • OpenAPI 文档手工维护、与实现脱节，CI 里的兼容性检查检的是一份早就不准的文件。
