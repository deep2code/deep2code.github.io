API 设计深度原理：RESTful 与 GraphQL

🏷️ API 设计

为什么有的 API 好用有的难用？RESTful 到底怎么设计？GraphQL 解决了什么问题？这篇讲透 API 设计底层原理。

核心原理1：RESTful 设计原理

REST 不是规范，是设计风格：用 URL 表示资源，用 HTTP 方法表示操作，用状态码表示结果，无状态。

flowchart LR A[REST 原则] --> B[URL 名词 表示资源] A --> C[HTTP 方法 表示操作] A --> D[状态码 表示结果] A --> E[无状态] B --> B1[/users GET POST] B --> B2[/users/1 GET PUT DELETE]

['HTTP 方法', '操作', 'SQL 对应']

HTTP 方法 操作 SQL 对应
GET 查询 SELECT
POST 新增 INSERT
PUT/PATCH 更新 UPDATE
DELETE 删除 DELETE

核心原理2：REST 常见问题：过度取数

REST 最大的问题：前端要什么后端给什么，经常一个页面要调好几个接口，或者接口返回一堆不需要的字段。

flowchart TD A[REST 问题] --> B[一个页面调 N 个接口] A --> C[返回一堆不需要的字段] A --> D[版本管理麻烦] B --> E[ waterfall 请求 慢]

['问题', '说明', '例子']

问题 说明 例子
过度取数 返回字段太多，前端用不上 /users 返回所有字段
不足取数 字段不够，要再调一次 要先调用户再调订单
多次请求 一个页面调 5 个接口 首页要调用户、推荐、消息...
版本管理 API 改了要兼容老版本 /v1/users /v2/users

核心原理3：GraphQL 解决什么问题？

GraphQL 是 Facebook 开源的，前端声明要什么字段，后端就返回什么字段，一个接口搞定所有数据需求。

flowchart LR A[前端写查询] --> B[声明要的字段] B --> C[GraphQL 接口] C --> D[后端只返回要的字段] D --> E[一个接口 拿所有需要的数据]

['对比', 'REST', 'GraphQL']

对比 REST GraphQL
数据获取 后端决定返回什么 前端决定要什么
请求数量 一个页面多个接口 一个接口拿所有
版本管理 要 v1 v2 不要版本，字段可选弃用
学习成本 低 高，要写查询语法
缓存 HTTP 缓存方便 要自己实现缓存

新手最容易踩的坑

❌
避坑指南
  • URL 用名词，不要用动词，/getUser 不对，应该是 /users
  • 状态码用对，2xx 成功，4xx 客户端错，5xx 服务端错，不要全部返回 200
  • 不要在 URL 里暴露技术细节，比如 /list.php?id=1
  • GraphQL 不是银弹，简单接口用 REST 更简单，复杂前端场景才用 GraphQL
