RESTful 落地细节：资源建模、方法语义、状态码与条件请求

🏷️ RESTful

REST 的入门知识只有三句话：URL 表示资源、方法表示动作、状态码表示结果。难的从来不是这三句，而是落地时那些真会吵架的细节：取消订单这种不是 CRUD 的动作放哪里、PATCH 到底幂等不幂等、校验失败该 400 还是 422、两个人同时改一条数据怎么不互相覆盖、批量操作里一半成功了该返回什么。这篇只讲这些。风格选型见本目录主干篇，版本演进见版本篇，错误结构与分页见最佳实践篇。

成熟度模型：为什么大家都停在 Level 2

Richardson 成熟度模型把 REST 分成四级，它的价值不是让你追求满级，而是让你知道自己在哪一级、以及再上一级要付什么代价。

Level 2 通常就够了，而且对绝大多数团队是性价比最高的位置。HATEOAS 在实践中极少落地，原因很具体：客户端（尤其是移动端和第三方）几乎一定会硬编码 URL，因为它更省事、可离线构造、便于埋点；服务端为了「可以随时改 URL」这个几乎用不到的自由度，要在每个响应里维护一堆 links，序列化体积明显增大；而真正需要的发现能力，用 OpenAPI 文档加代码生成已经解决得更好。所以不必因为没做 HATEOAS 而觉得自己不够 REST。

资源建模：名词、复数、层级不超过两层

基本约定不多：URL 用名词复数（/users 而不是 /user，集合与单体语义一致好记）、路径段用小写加连字符（/order-items 而不是 /orderItems，因为部分服务器路径大小写敏感、部分不敏感，全小写最省事）、不要把技术细节写进 URL（.php、.do、list、query 都不该出现）。

真正需要纪律的是层级深度。用 /users/1/orders 表达归属关系很自然，但 /users/1/orders/1001/items/5/reviews 就开始出问题：中间的 ID 大部分是冗余的（知道 review 的 ID 就能定位它，前面那串只是装饰），每加一层就多一处要校验的归属关系（不校验就是越权漏洞，因为 order 1001 未必属于 user 1），客户端拼 URL 也越来越容易出错。经验规则是层级不超过两层，更深的关系用查询参数表达：把 /users/1/orders/1001/items 改成 /order-items?order_id=1001，同时保留 /orders/1001 作为单体资源地址。

非 CRUD 动作怎么建模：最常见的争论

取消订单、审批通过、重发验证码、解锁账号、重置密码这类动作不是资源的增删改查，它们是 REST 建模里最容易卡住的地方。三种做法各有代价。

做法 写法示例 优势 代价 什么时候用
把动作建成子资源 POST /orders/1001/cancellations 动作本身有了地址，可以 GET 查询这次取消的记录，天然适合带幂等键与审计 命名容易吵（cancellations 还是 cancel-requests），新人看不懂，动作多了 URL 空间膨胀 动作需要留痕、需要审批流、需要重试后查询结果（退款、退货、转账）
改状态字段 PATCH /orders/1001 请求体把 status 改为 cancelled 最符合 REST 教条，接口数量最少 丢语义：取消要校验是否已发货、要退款、要释放库存，这些都不是改字段；而且客户端能直接指定任意状态，等于把状态机交给了前端 状态流转确实简单且没有副作用，比如草稿改成已发布
动词端点 POST /orders/1001/cancel 语义最直白，前后端沟通成本最低，网关按 URL 做限流与鉴权非常清楚 不符合教条，无法用 HTTP 缓存（但这类动作本来就不可缓存） 动作不需要留痕、一次性执行，且团队已统一约定动词端点只用 POST
✅
推荐

需要留痕和重试的资金类、审批类动作用「动作即资源」；其余用动词端点，并写进规范：动词端点必须用 POST、动词必须是祈使式单词、状态机必须在服务端而不是让客户端直接写 status。不要为了看起来 RESTful 而把带副作用的复杂动作压成一个 PATCH status，那会让状态机彻底失控。

方法语义的精确表：安全性、幂等性、可缓存性

这三个属性是独立的，不是一回事。安全指不改变服务器状态（可以被爬虫和预取随意触发）；幂等指执行一次和执行 N 次对服务器状态的影响相同（注意只约束状态，不要求响应码相同）；可缓存指响应可被存储复用。

方法 安全 幂等 可缓存 请求体 关键注意点
GET 是 是 是 不应有 绝不能有副作用。浏览器预取、CDN、企业代理、聊天软件的链接预览都会主动发 GET
HEAD 是 是 是 无 实现了 GET 就应支持 HEAD，用于探测资源是否存在与内容长度
POST 否 否 基本不 有 不幂等，所以网络超时后客户端无法安全重试，创建类接口必须支持幂等键

❌
用 PUT 做局部更新是真实的数据丢失源

前端表单只回填了它关心的三个字段，PUT 上来之后服务端老老实实按全量替换执行，用户的备注、标签、扩展字段全被置空。更糟的是这类事故没有错误日志，往往是用户几天后发现数据不见了才被发现。要么严格按全量替换实现并要求客户端先 GET 再改再 PUT（配合 If-Match 防丢失更新），要么老实用 PATCH。

容易混淆的一组 判断依据 典型错误用法及后果
200 与 201 与 204 有新资源产生就 201 并带 Location；没有响应体就 204；其余 200 创建成功返回 200 且不给 Location，客户端只能再查一次列表去猜哪条是自己刚建的
202 与 200 处理是异步的、返回时还没做完，就必须是 202 导出十万行报表同步返回 200，卡在网关 60 秒读超时上，客户端以为失败反复重试
400 与 422 解析不了或类型不对是 400；解析没问题但业务规则不通过是 422 所有校验失败一律 400，客户端无法区分是自己代码写错了还是该提示用户
401 与 403 没身份是 401，有身份没权限是 403 Token 过期返回 403，客户端不会触发刷新 Token 流程，用户被迫重新登录
403 与 404 访问他人数据用 404，功能权限不足用 403 遍历 ID 时 403 与 404 混用，攻击者据此枚举出全部有效 ID 与业务量级
409 与 412 与 422 状态机不允许是 409；乐观锁版本不匹配是 412；单字段语义错是 422 并发冲突返回 500，上游把它当可重试错误反复重试，同一笔操作被执行多次
503 与 504 自己不可用是 503（可带 Retry-After），等上游超时是 504 下游超时返回 500，监控无法区分是自身缺陷还是依赖抖动，定位方向完全跑偏

条件请求：REST 里最被低估的能力

ETag 在多数团队里只被用来省流量，其实它的另一半能力是乐观并发控制，而这个能力直接决定了你的系统有没有丢失更新问题。

// ETag 不要用整个 body 的哈希去算：那意味着每次都得先把完整响应序列化出来，
// 数据库和 CPU 一点也省不下。用行版本号或 updated_at 拼出来就够了。
func (h *ArticleHandler) Update(w http.ResponseWriter, r *http.Request) {
	id := chi.URLParam(r, "id")

	// If-Match 缺失时的策略要显式选择，不要留默认行为。
	// 对多人协作的资源建议强制要求，缺失就返回 428 Precondition Required
	match := r.Header.Get("If-Match")
	if match == "" {
		problem(w, 428, "precondition-required", "该接口要求携带 If-Match 头")
		return
	}
	ver, ok := parseVersion(match) // 从 v3-9f2a1c 里取出数字 3
	if !ok {
		problem(w, 400, "bad-if-match", "If-Match 格式不合法")
		return
	}

	var in ArticleInput
	if err := json.NewDecoder(r.Body).Decode(&in); err != nil {
		problem(w, 400, "bad-json", "请求体不是合法 JSON")
		return
	}

	// 关键：把版本判断交给数据库的一条原子 UPDATE。
	// 先 SELECT 比较再 UPDATE 之间存在窗口，高并发下照样丢更新。
	res, err := h.db.Exec(r.Context(),
		`UPDATE articles SET title = $1, body = $2, version = version + 1,
		        updated_at = now()
		   WHERE id = $3 AND version = $4`,
		in.Title, in.Body, id, ver)
	if err != nil {
		problem(w, 500, "internal", "更新失败")
		return
	}
	if res.RowsAffected() == 0 {
		// 影响 0 行有两种可能：资源不存在，或版本已变。必须分开回不同状态码
		if !h.exists(r.Context(), id) {
			problem(w, 404, "not-found", "文章不存在")
			return
		}
		problem(w, 412, "stale-write", "资源已被他人修改，请重新获取后再提交")
		return
	}

	// 更新后必须回写新 ETag，否则客户端下一次提交仍带旧版本，从此永远 412
	w.Header().Set("ETag", newETag(ver+1))
	w.WriteHeader(http.StatusOK)
}
Cache-Control 指令 真实含义 常见误用与后果
max-age=N N 秒内缓存可直接使用，不需要问源站 给带登录态的响应设了 max-age 又忘了加 private，共享代理把 A 的数据发给 B
no-cache 可以存，但每次使用前必须向源站验证（配合 ETag 走 304） 误以为是不缓存，于是敏感响应用了 no-cache，其实仍会被写入磁盘缓存
no-store 任何环节都不得存储，这才是真正的不缓存 给所有接口一律加 no-store，连头像和字典数据也不让缓存，白白放大回源流量
must-revalidate 缓存过期后必须验证，不允许在源站不可达时返回过期副本 不加它时某些代理会在源站故障期间继续发陈旧数据，导致故障期数据不一致
private 与 public private 只允许浏览器等私有缓存存储；public 允许 CDN 等共享缓存存储 带 Authorization 的响应默认不被共享缓存存储，但显式写了 public 就会被存，属于典型越权泄露
stale-while-revalidate=N 过期后 N 秒内可先返回旧副本，同时后台异步刷新 没用上它，缓存过期瞬间大量请求同时回源打穿源站

查询参数、内容协商与批量操作

查询参数没有标准，所以更要靠团队约定统一。下面这套命名在多数项目里够用，重点是一次定好就不要在不同接口里换写法。

用途 推荐写法 说明与边界
等值过滤 status=paid&channel=app 多值用重复参数或逗号分隔，二者选一并写进规范；逗号对值本身含逗号的情况不友好
范围过滤 created_from 与 created_to 别发明 created[gte] 这类嵌套语法，网关日志、WAF、CDN 缓存键的处理都容易不一致
排序 sort=-created_at,id 减号表示降序。字段名必须白名单校验，直接拼进 SQL 就是注入面（参数化边界详见站内 SQL 注入篇）
字段选择 fields=id,title,author_name 能缓解过度获取，但响应结构不再固定，缓存键也要带上 fields，需要权衡
分页 page 与 page_size，或 cursor 与 limit 两种分页的适用场景与深分页陷阱见最佳实践篇
全文搜索 q=关键词 和结构化过滤分开命名，避免 q 既当关键词又当过滤条件

内容协商方面，请求用 Content-Type 声明自己发的是什么、用 Accept 声明想收什么；服务端不认识请求体类型时回 415，无法满足 Accept 时回 406。真实项目里 JSON 之外最常见的是导出场景（Accept: text/csv）。用 Accept 头做版本协商在技术上可行，取舍留给版本篇讨论。

批量操作的核心问题是部分失败。两种做法：用 207 Multi-Status 表达里面各项结果不同，或者统一返回 200 并在响应体里逐项给出结果。207 语义上更准确，但绝大多数客户端库、网关和监控系统会把它当成陌生状态码处理，收益有限。更实用的是返回 200 加逐项结果，并给出成功与失败计数，让调用方一眼判断是否需要重试。无论哪种，都要明确这个批量是不是事务性的：如果不是原子的，就必须支持按项重试，因此每一项都要有自己的幂等键。

长耗时操作：202 加任务资源

导出报表、批量导入、视频转码这类操作不能同步返回。网关和负载均衡通常有 30 到 60 秒的读超时，客户端超时后会重试，于是同一个任务被提交多次。标准做法是提交时立刻返回 202，并把任务本身建成资源。

反模式清单

反模式 为什么有害 正确做法
GET 带副作用，例如 GET /orders/1/delete 浏览器预取、CDN、企业代理、聊天软件的链接预览都会主动发 GET，数据会被莫名改掉 任何改状态的操作一律用 POST 或 DELETE，并在网关侧禁止 GET 路由到写接口
所有响应都返回 200，靠 body 里的 code 判断成败 网关与 APM 统计的错误率永远是 0，熔断与告警全部失效；CDN 会缓存错误响应；客户端 SDK 的重试策略也用不上 HTTP 状态码表达协议层结果，业务错误码放响应体（详见最佳实践篇）
URL 里带动词又混用方法，例如 GET /user/updateName 既丢了 REST 语义又丢了一致性，网关按方法做的策略（只对写操作限流）会全部错配 动词端点只用 POST，并且全站统一风格
分页信息只放 body 且每个接口位置都不同 客户端要为每个接口写一套解析逻辑；网关也无法统一做结果裁剪 统一约定位置（统一包装里的 meta 或标准化响应头），全站一致
null 与字段缺失混用 缺失表示没有这个字段，null 表示有字段但值为空；混用后 PATCH 无法表达把某字段清空 规范里明确二者语义；需要区分时用 JSON Merge Patch 并约定 null 表示删除
用 PUT 做局部更新 未传字段被置空，静默丢数据且没有任何日志 局部更新用 PATCH；坚持用 PUT 就必须要求客户端提交全量并配 If-Match
资源层级四五层深 中间 ID 冗余，每层都要校验归属，漏一层就是水平越权 层级不超过两层，更深的关系用查询参数
直接把 ORM 实体序列化返回 自增 ID 可被遍历（配合越权就是批量拖库），内部字段暴露实现细节且以后很难删掉 对外用不可猜测的 ID，响应体字段走显式白名单的 DTO
❌
最容易踩的坑
  • 创建成功返回 200 且不给 Location 头，客户端拿不到新资源地址，只能再查一次列表去猜哪条是自己刚建的。
  • 204 响应里还写了 body，部分客户端库会直接抛解析异常，一些代理也会把它截断。
  • 把 PATCH 实现成相对操作（库存减一）却对外宣称幂等，客户端超时重试后库存扣了两次。
  • PUT 当局部更新用，客户端漏传字段导致备注、标签被静默清空，几天后才被用户发现。
  • 先 SELECT 查版本再比较再 UPDATE，以为实现了乐观锁，实则两步之间存在窗口，高并发下照样丢更新；必须用带 version 条件的单条原子 UPDATE。
  • 更新成功后忘了回写新的 ETag，客户端一直带着旧版本提交，从此永远 412。
  • 把 no-cache 当成不缓存，敏感响应仍被写进磁盘缓存；真要禁存应该用 no-store。
  • 给带登录态的响应加了 Cache-Control public，CDN 把 A 用户的数据当公共资源发给了 B 用户。
  • 水平越权返回 403，攻击者据此枚举出全部有效 ID 与业务量级；这类场景返回 404 更安全。
  • Token 过期返回 403 而不是 401，客户端不触发刷新流程，用户被无谓地踢回登录页。
  • 排序字段直接拼进 ORDER BY，参数化管不到标识符位置，必须走白名单（边界详见站内 SQL 注入篇）。
  • 并发冲突返回 500，上游当成可重试错误反复重试，一笔操作被执行多次。
  • 导出十万行报表同步返回，卡在网关读超时上，客户端超时重试又压上第二次全量查询。
  • 异步任务的提交接口没有幂等键，客户端一超时重试就创建出一串重复任务。
  • 鉴权中间件对 OPTIONS 预检也要求带 Token，浏览器跨域请求全部失败且报错看不出原因。
