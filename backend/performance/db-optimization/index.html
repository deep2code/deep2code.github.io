应用侧的数据库访问优化

🏷️ 数据库优化

这篇只讲「数据库本身没问题，是应用用错了」这一类问题：连接池、ORM 陷阱、批量与 N+1、事务边界、读写分离的应用侧实现。SQL 写法、索引设计、慢查询治理、分库分表全部属于数据库侧，见站内数据库优化四篇；B+ 树、缓冲池、MVCC、加锁范围、执行计划判读见站内MySQL 深度原理；缓存层的设计见站内缓存设计；接口整体的耗时拆解见接口性能优化。

先划清边界：数据库很快，是应用用错了

线上「数据库慢」的报警里，我见过的至少有一半，数据库侧是清白的：慢查询日志空空如也，实例 CPU 百分之二十，执行时间毫秒级，但应用侧的接口 P99 是两秒。这类问题的共同特征是：耗时花在应用到数据库之间的那几层，而不是数据库内部。

连接池：最容易配错的组件

连接池配置的第一个反直觉结论：池不是越大越好，很多系统把池从 200 降到 20 之后吞吐反而上升、P99 下降。原因在数据库侧——连接不是免费的并发度，每个活跃连接在数据库里对应一个工作线程，当活跃连接数超过数据库能真正并行处理的数量后，多出来的连接只带来三样东西：线程上下文切换、缓冲池与锁结构的争抢、以及更长的排队。这正是主干篇里排队论那条曲线的另一种体现，详见后端性能优化的度量与方法论。

经验公式来自 HikariCP 的池大小建议：连接数 = 核数 × 2 + 有效磁盘数。一台 8 核加 SSD 的数据库，对应池大小 15 到 20 就够了。注意两点：这个数是整个应用集群加起来的活跃连接数，20 个实例每个配 50 就是 1000 个连接，很容易撞上数据库的最大连接数；另外如果业务里有大量长事务，瓶颈不是池大小而是事务时长，加池只是把问题推迟。

参数（HikariCP 名称） 默认值 推荐设置思路 配错的后果
maximumPoolSize 10 按核数乘二加磁盘数估算，再用压测验证；集群总量不超过数据库最大连接数的 70% 配成几百：数据库线程争抢，吞吐下降、P99 上升；配得太小：请求排队等连接
minimumIdle 等于 maximumPoolSize 生产建议保持与最大值相同，避免流量突增时现场建连 设得很小：突发流量时大量请求要等建连与握手，表现为「冷启动抖动」
connectionTimeout（获取超时） 30 秒 改成 1 到 3 秒，让池耗尽时快速失败而不是拖死线程 保持 30 秒：池耗尽时所有业务线程挂满 30 秒，整个服务不可用
maxLifetime（最大存活时长） 30 分钟 必须小于数据库 wait_timeout 与所有中间层的空闲超时，留几十秒余量 大于对端超时：拿到已被对端关闭的连接，偶发连接重置错误
idleTimeout 10 分钟 只在 minimumIdle 小于最大值时生效，需大于 maxLifetime 的一半 配置互相矛盾时连接反复创建销毁，建连开销白付
validationTimeout / 连接测试 5 秒 优先依赖驱动的 JDBC4 isValid，不要用 connectionTestQuery 每次借出都发一条 SQL 每次借出都测试：每个请求多一次往返；完全不测试：坏连接直接抛给业务
leakDetectionThreshold（泄漏检测） 0（关闭） 设成 2 到 5 秒，超时未归还就打印持有线程栈 不开：泄漏只能靠猜，拿不到「谁没还连接」的证据
keepaliveTime 0（关闭） 有中间层的场景设成小于对端空闲超时的一半，主动保活空闲连接 不开且有代理：空闲连接被静默回收，业务偶发拿到坏连接

连接泄漏与坏连接：两类最难查的故障

连接泄漏的表现极具误导性：应用侧看是「数据库越来越慢，最后全部超时」，数据库侧看是「一切正常，只是有几个连接一直闲着不干活」。泄漏的来源基本就三种：拿到连接后没有在 finally 里归还、把 ResultSet 或流式查询的游标一直开着、以及手动开启事务后在异常路径上既没提交也没回滚。

观察点 泄漏的特征 池太小的特征 长事务的特征
活跃连接数曲线 单向上升，不随流量回落 随流量起伏，高峰打满 阶梯式上升，与某类操作时间吻合
数据库侧连接状态 大量连接处于 Sleep 且时长持续增长 连接都在执行中 存在长时间处于事务中的连接
重启后表现 恢复正常，运行一段时间后复现 立刻复现 与批量任务的执行时间相关
定位手段 打开泄漏检测阈值，看打印出的持有线程栈 看获取连接的等待时间直方图 查数据库里事务存续时间最长的会话

坏连接是另一类偶发故障，根因几乎总是同一个：应用池里的连接存活时间超过了链路上某一环的空闲超时。链路上可能有云负载均衡（常见空闲超时 300 秒）、数据库代理、以及数据库自身的 wait_timeout（MySQL 默认 28800 秒）。对端单方面关闭连接后并不会通知应用，池里那条连接看起来仍然可用，直到业务借走它并发出第一条语句才报错。三条规则：maxLifetime 取链路上最小空闲超时再减去几十秒余量；开启保活让空闲连接周期性发心跳；依赖驱动的连接有效性检查而不是每次借出都发一条测试 SQL（后者等于给每个请求加一次往返）。

ORM 的六类性能陷阱

ORM 的问题不在于慢，而在于它让昂贵的操作在代码上看起来免费。访问一个属性可能是一次网络往返，保存一个列表可能是一千次插入，加一个注解可能把事务范围扩大十倍。下面六类占了我见过的绝大多数 ORM 性能问题。

陷阱 代码上的样子 实际发生了什么 修法
懒加载 N+1 循环里访问 order.getUser().getName() 每次属性访问触发一条 SQL，100 条订单发 101 条 SQL 用联表抓取（JOIN FETCH）、实体图或显式预加载；一次把关联数据查回来在内存里组装
默认查询全部列 findAll()、SELECT * 风格的自动 SQL 把富文本、扩展 JSON、大字段一起取回，网络与内存双重浪费，还破坏覆盖索引 列表查询用投影（只映射需要的列），大字段拆到单独的表或懒加载列
会话缓存与二级缓存 长生命周期的会话、开启全局二级缓存 查过的对象一直留在会话里导致内存膨胀；多实例下二级缓存与数据库不一致，出现脏读 会话尽量短；二级缓存只用于极少变更的数据，并明确失效策略
自动 SQL 走不上索引 动态条件拼接、日期范围、类型不一致的参数 条件列被套函数或发生隐式类型转换，索引失效走全表；生成的条件顺序无法命中最左前缀 打开 SQL 日志核对实际语句并看执行计划，判读方法见站内 MySQL 篇
批量被拆成逐条 saveAll(list) 看起来是批量 框架在循环里逐条保存，还可能每条都回查主键；驱动没开重写参数时一条一次往返 开启批量语句重写、设置批大小、必要时直接写原生批量语句
事务范围被注解扩大 在类上加事务注解，或在包含远程调用的方法上加 整个方法都在事务里，包括循环、RPC、发消息，锁持有时间暴涨 事务注解只加在「只做数据库写」的最小方法上，注意同类内部调用注解不生效
✅
上线前必做的一件事

在测试环境打开 ORM 的 SQL 打印，跑一遍核心接口，数一下实际发出的 SQL 条数。一个正常的详情接口应该在个位数，出现几十上百条就是 N+1。更进一步的做法是在集成测试里断言「单个接口的 SQL 条数不超过 N」，这是唯一能防住 N+1 悄悄回归的手段。

事务边界：应用侧最大的性能与稳定性问题

一条原则就够了：事务里只包数据库操作。原因是从执行第一条更新语句开始，行锁就被持有直到提交，事务里任何一毫秒的等待都是锁持有时间。一个平均 800ms、偶发 3 秒的第三方接口放进事务，等于让这行数据被锁住同样长的时间。

sequenceDiagram autonumber participant T as 业务线程 事务中 participant D as MySQL participant R as 第三方支付接口 T->>D: BEGIN T->>D: UPDATE account SET balance 减 100 WHERE id 等于 9 Note over T,D: 这一刻起 id 等于 9 这行的行锁被持有 T->>R: 调用支付 平均 800ms 偶发 3s Note over T,R: 锁一直持有 其它要改这行的线程全部排队
排队线程各占一个连接 池很快被耗光 R-->>T: 返回结果 T->>D: UPDATE orders SET status 等于 已支付 T->>D: COMMIT 此时才释放锁 Note over T,D: 结论 外部接口的抖动被放大成数据库锁等待与死锁
而数据库侧看起来只是 锁等待变多了 
// 改造前：事务包住了远程调用，锁持有时间等于外部接口耗时
@Transactional
public void payBad(long orderId) {
    Order o = orderMapper.selectForUpdate(orderId); // 行锁开始持有
    accountMapper.deduct(o.getUserId(), o.getAmount());
    PayResult r = payClient.pay(o);                 // 800ms 到 3s，锁全程持有
    orderMapper.updateStatus(orderId, r.status());
    mqProducer.send(new OrderPaidEvent(orderId));   // 发消息也在事务里，还可能失败后回滚不掉
}

// 改造后：事务内只做数据库操作，外部调用移到事务之外
public void payGood(long orderId) {
    // 第一段事务：本地状态置为「支付中」，并写一条待发送的本地消息
    // 事务很短，只有两条更新，锁持有时间是毫秒级
    PayContext ctx = txTemplate.execute(status -> {
        Order o = orderMapper.selectForUpdate(orderId);
        if (o.status() != OrderStatus.CREATED) {
            return null; // 幂等：重复请求直接返回
        }
        orderMapper.updateStatus(orderId, OrderStatus.PAYING);
        outboxMapper.insert(new Outbox("ORDER_PAYING", orderId)); // 本地消息表
        return PayContext.of(o);
    });
    if (ctx == null) {
        return;
    }

    // 事务之外调用第三方，慢多久都不会持有任何数据库锁
    PayResult r = payClient.pay(ctx.order());

    // 第二段事务：回写结果。必须幂等，因为这一步可能因进程重启而重试
    txTemplate.executeWithoutResult(status -> {
        accountMapper.deduct(ctx.userId(), ctx.amount());
        orderMapper.updateStatusIfPaying(orderId, r.toOrderStatus());
        outboxMapper.markReady("ORDER_PAID", orderId); // 消息由独立线程扫表投递
    });
}
事务里的操作 为什么危险 改造方式
调用 RPC 或第三方 HTTP 网络耗时直接变成锁持有时间，对端抖动引发大面积锁等待与死锁 拆成「事务内改状态 加 事务外调用 加 事务内回写」，用本地消息表或事务消息保证最终一致
发消息队列 消息发成功但事务回滚，下游收到不存在的事件；发消息本身也会阻塞事务 写本地消息表，提交后由独立任务投递；或使用消息中间件的事务消息
循环里逐条写入几千行 事务越长，undo 链越长、锁越多，回滚成本也越高，主从延迟随之上升 分批提交，每批 500 到 1000 行，批与批之间留出间隔
事务里读缓存或调搜索引擎 同样是把外部延迟计入锁持有时间 把读操作提到事务之前，事务内只用已经拿到的数据
在类级别加事务注解 所有方法包括纯查询都开事务，连接被长时间占用 注解下沉到最小的写方法；只读路径显式标注只读或不开事务

顺带纠正一个常见误解：「把事务隔离级别调低就能解决锁等待」是错的。锁等待的根因是锁持有时间太长，隔离级别只影响加锁范围与可见性规则，调低隔离级别可能减少某些间隙锁，但对「事务里等了 800ms 的外部调用」毫无帮助。加锁范围与隔离级别的具体语义见站内MySQL 深度原理。

批量操作：1000 条插入不该是 1000 次往返

最典型的认知错误：以为调用了批量接口就是批量了。JDBC 的 addBatch 与 executeBatch 只是把语句攒在客户端，MySQL 驱动在未开启 rewriteBatchedStatements=true 时仍然逐条发送，1000 条插入就是 1000 次网络往返，同机房按每次 0.5ms 算，光往返就是 500ms。开启之后驱动会把它们改写成一条多值插入语句，一次往返完成，差距通常在 10 倍以上。

// 批量写入的正确姿势。前提：JDBC URL 上带 rewriteBatchedStatements=true，否则以下代码等于逐条插入。
private static final int BATCH_SIZE = 500; // 500 到 1000 是常见甜点区，再大收益递减且单包过大

public void batchInsert(List<Order> orders) throws SQLException {
    String sql = "INSERT INTO orders (id, user_id, amount, status) VALUES (?, ?, ?, ?)";
    try (Connection conn = dataSource.getConnection();
         PreparedStatement ps = conn.prepareStatement(sql)) {

        // 关闭自动提交：否则每条都是一个独立事务，等于多付 N 次提交开销
        conn.setAutoCommit(false);

        int n = 0;
        for (Order o : orders) {
            ps.setLong(1, o.id());
            ps.setLong(2, o.userId());
            ps.setLong(3, o.amount());
            ps.setInt(4, o.status());
            ps.addBatch();

            if (++n % BATCH_SIZE == 0) {
                ps.executeBatch();
                conn.commit();   // 分批提交：避免单个超长事务把 undo 链和锁堆到不可控
                ps.clearBatch();
            }
        }
        ps.executeBatch();
        conn.commit();
    }
}

场景 推荐做法 关键参数 做错的后果
批量插入 开启批量重写，单批 500 到 1000 条，分批提交 rewriteBatchedStatements、autoCommit=false 不开重写：条数次往返；批太大：单个包过大、事务过长、失败重试代价高
插入或更新（upsert） 用 ON DUPLICATE KEY UPDATE 或数据库原生 upsert，一次往返完成 需要唯一键；注意它会影响自增值的消耗 先查再决定插还是改：两次往返，并且在并发下仍然会撞唯一键冲突
大批量更新或删除 按主键范围分批，每批 500 到 1000 行，批间 sleep 限速 批大小、间隔时长、主从延迟阈值 一条语句更新百万行：长事务、锁范围巨大、主从延迟飙到几十秒
批量读取超大结果集 流式读取，按需设置 fetchSize，边读边处理 MySQL 需要配合特定的 fetchSize 才会真正流式 一次性拉回百万行：应用直接内存溢出
批量任务与在线流量共用实例 限速并避开高峰，或在专用从库上跑 每批间隔、监控主从延迟自适应降速 批量任务把缓冲池冲刷一遍，在线接口全部变慢 
-- 大批量更新的正确形态：按主键推进 + 限批 + 观察主从延迟后再继续
-- 错误写法：一条语句更新百万行，长事务 + 巨大锁范围 + 主从延迟飙升
UPDATE orders SET status = 4 WHERE status = 1 AND created_at < '2026-01-01';

-- 正确写法：循环执行，每次只处理一批，应用侧在批与批之间 sleep 50 到 200ms，
-- 并在继续前检查主从延迟，超过阈值就自动降速（延迟指标见站内 MySQL 与数据库优化篇）
UPDATE orders SET status = 4
WHERE status = 1 AND created_at < '2026-01-01' AND id > ?   -- ? 为上一批处理到的最大 id
ORDER BY id
LIMIT 500;

-- 应用侧的游标分页：把偏移量换成条件过滤，耗时与页码无关
-- 错误写法：偏移量越大越慢，数据库要先扫过并丢弃前一百万行
SELECT id, user_id, amount FROM orders WHERE status = 1 ORDER BY id LIMIT 1000000, 20;

-- 正确写法：用上一页最后一行的排序键作为游标
SELECT id, user_id, amount FROM orders
WHERE status = 1 AND id > ?
ORDER BY id
LIMIT 20;
-- 注意：游标分页要求排序键唯一且有序，如果按创建时间排序，必须带上主键做次级排序键，
-- 否则同一时间戳的多行会在翻页时重复或丢失。深分页的原理见站内 MySQL 篇。

读写分离的应用侧实现

读写分离在应用侧真正难的不是路由，而是写后读。主从复制是异步的，写完立刻读从库大概率读不到，表现为「下单成功但订单列表里没有」这类偶发 bug，而且它只在延迟升高时复现，本地和测试环境永远测不出来。

解法 怎么实现 一致性强度 代价 适用场景
关键读强制走主库 在请求上下文里打标记，路由层看到标记就走主库；或在方法上显式声明走主库 强 把流量压回主库，用多了读写分离就失效了 写后立即读、支付与库存等强一致路径
等待复制位点 写事务后取得主库位点，读之前确认从库已追上该位点再读 强 实现复杂，需要中间件支持；读延迟增加 有数据库代理或中间件支持位点等待的系统
会话粘滞 同一用户或会话在一个时间窗口内的读全部走主库，窗口按主从延迟的高分位设置 中 窗口设小了仍会读到旧数据，设大了主库压力上升 大多数以用户为中心的业务，落地成本最低
前端乐观回显 写成功后前端直接用提交的数据渲染，不再回查 弱（只是视觉一致） 数据不完整时会与真实状态不符 评论、点赞这类非关键展示

还有三件事必须说清楚。第一，只读从库不是免费的：它有自己的最大连接数上限，复制线程本身要消耗资源，并且在大批量写入时延迟会显著上升——这时把读切到从库等于把不一致放大。第二，事务内的读必须走主库，哪怕是纯查询，否则同一事务内读到两个不同的数据版本。第三，路由要能按延迟自动摘除：从库延迟超过阈值就临时不分配读流量，否则一个卡住的从库会让部分用户持续看到旧数据。

预编译语句与执行计划缓存

预编译有两层含义，经常被混为一谈。客户端预编译（MySQL 驱动默认行为）只是在客户端做参数拼接与转义，好处是防注入、无额外往返；服务端预编译（useServerPrepStmts=true）会把语句真正发给数据库解析一次并缓存执行计划，之后只传参数。

配置 收益 代价与风险 建议
useServerPrepStmts=false（默认） 一次往返完成，简单 数据库每次都要解析语句 语句种类多、每种执行次数少的场景保持默认
useServerPrepStmts=true 配合语句缓存 省掉重复解析，高频固定语句收益明显 首次多一次往返；数据库侧为每个连接缓存预编译对象，占内存；语句种类过多会撑爆缓存 固定 SQL、高 QPS 时开启，并设置缓存条数与语句长度上限
动态拼接的 SQL 无 每个组合都是一条新语句，预编译缓存命中率极低反而浪费内存 先收敛 SQL 形态（比如把 IN 的参数个数归一到几个档位）再考虑开启

顺带提醒一个和性能无关但更严重的点：预编译的防注入效果来自参数与语句分离，字符串拼接出来的 SQL 即使走了预编译接口也一样能被注入，注入边界的完整讨论见站内安全篇。

❌
最容易踩的坑
  • 把连接池从 20 调到 200 试图提升吞吐：数据库侧线程争抢加剧，结果吞吐下降、P99 上升。
  • 按单实例配池却忘了乘实例数：20 个实例各 50 个连接就是 1000 个，直接撞上最大连接数，扩容时全站报连接失败。
  • 获取连接超时用默认 30 秒：池一耗尽，所有业务线程一起挂 30 秒，连健康检查都失败。
  • maxLifetime 大于云负载均衡的空闲超时：空闲连接被静默回收，业务偶发拿到坏连接，日志里只有一行连接重置。
  • 不开泄漏检测：连接泄漏只能靠重启缓解，永远找不到是哪段代码没归还。
  • 批量插入没开 rewriteBatchedStatements：1000 条插入等于 1000 次往返，代码看起来是批量的。
  • ORM 的 saveAll 当成批量用：框架内部是循环单条保存，还可能每条回查一次主键。
  • 在循环里访问懒加载属性：代码上只是取个名字，实际发了上百条 SQL。
  • 类上加事务注解：连查询方法都开事务，连接被长时间占用，还把 RPC 包了进去。
  • 同类内部方法调用指望事务注解生效：基于代理的实现不会拦截自调用，事务根本没开。
  • 事务里发消息：事务回滚了消息已经发出去，下游处理了一个不存在的订单。
  • 一条 SQL 刷全表状态：主从延迟飙到几十秒，所有读从库的接口开始返回旧数据。
  • 写完立刻读从库：功能测试永远通过，线上偶发「下单成功但列表没有」。
  • 事务内的查询走了从库：同一事务里读到两个数据版本，对账时才发现。
  • 从库延迟高时不摘除：部分用户持续看到过期数据，且没有任何报错。
  • 把「数据库慢」直接甩给 DBA：先用应用侧耗时减去数据库侧执行时间，差值大就说明问题在自己这边。
