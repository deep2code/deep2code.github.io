前端性能：核心指标与后端能做的事

🏷️ 前端性能优化

这篇是从后端工程师视角写的前端性能：重点在网络层、缓存头、资源下发、渲染模式选择，以及接口设计对前端指标的影响。前端构建、框架渲染优化、主线程调度这些只做要点，不展开。度量方法与分位数怎么看见后端性能优化的度量与方法论；接口内部的耗时拆解与并行化见接口性能优化；接口的聚合与版本规范见站内API 设计；反向代理的缓冲、超时、连接复用参数见站内Nginx 深度原理。

Core Web Vitals：后端能影响哪几个

先把指标对齐。现在业界通用的三个核心指标是 LCP、INP、CLS，它们衡量的是三件不同的事：首屏内容多久可见、交互多久有响应、页面是否会乱跳。后端对这三者的影响力差别很大，把力气用在自己能影响的那一个上才有意义。

指标 衡量什么 良好阈值 主要影响因素 后端能做的事
LCP 最大内容绘制 视口内最大那块内容（通常是主图或标题块）渲染完成的时间 2.5 秒以内（按真实用户的 75 分位统计） 首字节时间、首屏关键资源体积、图片尺寸与格式、渲染阻塞资源 影响力最大：降低首字节时间、CDN 就近下发、首屏数据一次返回、图片格式与尺寸适配、缓存头配对
INP 交互到下一次绘制 用户交互到界面给出视觉反馈的延迟 200 毫秒以内 主线程长任务、脚本执行、以及交互要等的接口耗时 影响力中等：把交互路径上的接口 P99 压下来，避免交互触发串行请求
CLS 累积布局偏移 渲染过程中元素位置意外跳动的累积程度 0.1 以内 图片与广告未预留尺寸、字体切换、异步插入的内容 影响力小：接口返回图片的宽高信息，让前端能提前占位
TTFB 首字节时间 从发起导航到收到第一个字节，它不是核心指标但是 LCP 的地板 800 毫秒以内 DNS、连接建立、TLS 握手、服务端处理、边缘缓存命中情况 影响力最大且完全属于后端责任
💡
这三个指标要按分位数看，而且要分组

阈值判定用的是真实用户的 75 分位，不是平均值。更重要的是按地域、设备档位、网络类型分组看：一个总体达标的站点，完全可能在「低端安卓 加 移动网络 加 远端地域」这一组里差 3 倍。为什么不能看平均值、以及分位数为什么不能跨维度求平均，见度量与方法论篇。

TTFB 是后端的直接责任

TTFB 是 LCP 的地板：首字节都要 1 秒才回来，LCP 不可能好。它的构成是六段，而在跨地域场景下，连接建立与 TLS 握手往往比服务端处理还久——这是最值得纠正的一个认知，因为它决定了优化方向是「缩短物理距离与减少往返」而不是「再优化几毫秒的服务端逻辑」。

sequenceDiagram autonumber participant B as 浏览器 participant N as DNS participant E as 边缘节点 或 源站 participant A as 应用与数据库 B->>N: 域名解析 首次 20 到 120ms 有缓存则为 0 N-->>B: 返回 IP B->>E: TCP 三次握手 一个往返 E-->>B: 握手完成 B->>E: TLS 握手 1.3 一个往返 1.2 两个往返 E-->>B: 密钥协商完成 Note over B,E: 跨地域单程 60ms 时 这里已经花掉 120 到 180ms
而服务端处理可能只有 20ms B->>E: 发送 HTTP 请求 E->>A: 边缘未命中则回源 A-->>E: 生成响应 服务端处理时间 E-->>B: 返回第一个字节 TTFB 到此结束 Note over B,A: 优化顺序 先减往返次数与距离 再优化服务端处理
TTFB 构成段 典型耗时 后端或运维能做的事 常见错误
DNS 解析 首次 20 到 120ms，命中缓存为 0 合理的 TTL、减少域名分片、对第三方域名用 dns-prefetch 为了「并发下载」拆出五六个域名，每个都要解析与握手
TCP 握手 一个往返，跨地域几十毫秒 就近接入让往返变短，长连接复用避免重复握手 关闭连接复用，每个请求都重新握手
TLS 握手 TLS 1.3 一个往返，1.2 两个往返 启用 TLS 1.3、会话复用、OCSP stapling、边缘卸载 只在源站终止 TLS，用户与源站隔一整个大洲
请求发送 通常可忽略，大 Cookie 会放大 精简 Cookie，静态资源用无 Cookie 域名 在主域上堆了几 KB 的 Cookie，每个静态请求都带上
服务端处理 10ms 到几百毫秒 首屏数据并行查询、页面级缓存、边缘缓存 HTML 首屏串行调三个下游，用户等在白屏上
首字节返回 取决于是否缓冲整个响应 先把 head 部分刷出去，让浏览器提前开始下载关键资源 中间层缓冲了整个响应，流式渲染完全失效

HTTP 缓存头：后端最容易拿到收益的地方

缓存头是改动最小、收益最大、也最容易配错的一块。先把指令语义对齐，下面这张表里至少有三条是被普遍误解的。

指令 精确语义 常见误解 用在哪
max-age=N 从响应产生时刻起 N 秒内视为新鲜，期间不发任何请求 以为是「从现在起 N 秒」，实际要减去响应在中间缓存里已经待的时间 带内容哈希的静态资源，取一年
no-cache 允许缓存，但每次使用前必须回源校验，校验通过则返回 304 不带响应体 被当成「不要缓存」，于是有人用它来禁用缓存，白白丢掉 304 的收益 HTML 入口文件
no-store 任何环节都不得存储这份响应，每次完整重新下载 与 no-cache 混用，两者语义完全不同 含敏感信息的响应
must-revalidate 一旦过期就必须校验，禁止在断网等情况下使用过期副本 以为它能让资源每次都校验，实际只在过期后生效 对陈旧数据零容忍的页面
immutable 在新鲜期内即使用户点刷新也不发校验请求 以为没用；实际上它正是为了解决「用户一刷新就全量发 304 请求」 内容哈希文件名的静态资源，和长 max-age 一起用
stale-while-revalidate=N 过期后 N 秒内可以先返回旧副本，同时后台异步更新 以为需要客户端支持才有用，实际 CDN 侧支持就能显著降低回源峰值 变更不敏感的接口响应与页面片段
s-maxage=N 只对共享缓存（CDN、代理）生效，会覆盖 max-age 忘了它的存在，导致浏览器与 CDN 的缓存时长无法分别控制 CDN 缓存久一点、浏览器缓存短一点的场景
private / public private 禁止共享缓存存储，public 允许即使带认证头也被缓存 在带登录态的响应上误配 public，导致用户数据被 CDN 缓存并串给别人 登录态响应必须 private 或 no-store

强缓存与协商缓存的关系：强缓存（max-age）根本不发请求，协商缓存（ETag 或 Last-Modified）发一个请求但省掉响应体。前者省一次往返，后者只省流量。所以标准组合是——

# 可以直接抄的 nginx 配置：静态资源长缓存 + HTML 不缓存 + 预压缩
# 前提：构建产物文件名带内容哈希，例如 app.9f3c1a2b.js

# 1) 带内容哈希的构建产物：一年强缓存 + immutable
#    为什么能这么配：内容变了文件名一定变，所以永远不会读到过期内容
#    为什么要 immutable：没有它，用户每次刷新都会为每个资源发一个 304 校验请求，
#    首屏可能因此多出几十个往返，在弱网下非常明显
location ~* "^/assets/.+\.[0-9a-f]{8,}\.(js|css|woff2|png|jpg|webp|avif)$" {
    expires 1y;
    add_header Cache-Control "public, max-age=31536000, immutable" always;
    access_log off;
    # 预压缩：构建时生成 .br 与 .gz，服务端直接发，不在请求路径上烧 CPU
    brotli_static on;
    gzip_static  on;
}

# 2) HTML 入口：必须每次校验，否则发版后用户长期停留在旧版本
#    注意 no-cache 不是不缓存：ETag 命中时返回 304，省掉了响应体
location = /index.html {
    add_header Cache-Control "no-cache" always;
    etag on;
}

# 3) 接口响应：默认不让任何中间环节缓存带登录态的内容
location /api/ {
    add_header Cache-Control "private, no-store" always;
    proxy_pass http://app_upstream;
    # 反向代理的缓冲与超时参数见站内 Nginx 篇，此处只关注缓存语义
}

# 4) 实时压缩兜底（预压缩文件不存在时）
gzip on;
gzip_vary on;                 # 必须开：否则 CDN 可能把压缩版发给不支持的客户端
gzip_comp_level 5;            # 5 到 6 是 CPU 与体积的平衡点，9 的收益不到 2% 但 CPU 翻倍
gzip_min_length 1024;         # 小于 1KB 不压：压缩后可能更大，还白付 CPU
gzip_types text/plain text/css text/xml application/javascript application/json image/svg+xml;
# 不要把 image/jpeg image/png video/mp4 application/zip 写进来：它们已经是压缩格式

两个最常见的事故正好是把这套组合配反了：静态资源不带哈希，于是只能配短缓存，每次发版靠改查询参数或等过期；HTML 配了长 max-age，于是发版后用户拿不到新版本，而且因为强缓存不发请求，连「刷新一下」都救不了，只能等过期或让用户清缓存。

压缩：该压什么，压到什么程度

维度 gzip brotli 结论
文本压缩率 基准 通常再小 15% 到 25% 静态资源优先用 brotli 高等级预压缩
压缩 CPU（高等级） 中等 最高等级极慢，不适合实时 brotli 高等级只用于构建期预压缩，动态响应用低等级
解压 CPU 低 与 gzip 接近 客户端侧都不是瓶颈
兼容性 全兼容 现代浏览器均支持，需按请求头协商 两份都生成，按客户端支持情况下发，并设置 Vary
不该压的内容 JPEG、PNG、WebP、AVIF、MP4、已压缩包、加密流 再压体积几乎不降，纯烧 CPU，还可能变大

三条实践结论。构建时预压缩是最划算的做法：把 .br 与 .gz 一起产出，服务端直接发文件，省掉每次请求的压缩 CPU，而且能用最高压缩等级。动态响应用中等等级，gzip 5 到 6 即可，等级 9 体积只再降百分之一二而 CPU 明显上升。一定要开 Vary 响应头，否则共享缓存可能把压缩过的响应发给不支持该编码的客户端，表现为页面乱码或直接下载文件。

HTTP/2 与 HTTP/3：哪些老优化已经过期

这一节的价值在于纠正三条流传很广但已经过期的建议。

老优化 在 HTTP/1.1 下为什么有效 在 HTTP/2 及之后为什么失效或有害 现在该怎么做
合并所有 JS 与 CSS 每个连接同时只能处理一个请求，同域并发连接数有限，请求数就是成本 多路复用让同连接并行传输，减少请求数收益大幅下降；而单个大包里改一行就导致全量失效，缓存命中率极低 按路由与变更频率拆包，稳定依赖单独成包长期缓存；但也别拆成几百个极小文件
域名分片 绕开浏览器对单域并发连接数的限制 每个额外域名都要多付 DNS 加 TCP 加 TLS，而多路复用已经不需要分片 收敛到一个域名，让连接得到充分复用
图片内联成 base64 省掉一次请求 base64 体积增大约三分之一，且内联进 CSS 或 HTML 后无法单独缓存，改任何一处全量失效 只对极小的关键图标考虑内联，其余正常引用并长缓存

HTTP/2 真正解决的是应用层队头阻塞，但它跑在 TCP 上，一旦丢包，TCP 层的队头阻塞会把同一连接上的所有流一起卡住，这在弱网下反而比多连接的 HTTP/1.1 更糟。HTTP/3 把传输换成 QUIC，流之间相互独立，并且把连接建立压缩到更少的往返，所以它的收益集中在移动网络、弱网、丢包率高的链路，在稳定的内网或优质固网上提升有限。决定要不要上 HTTP/3 之前，先看真实用户监控里移动网络与高丢包用户的占比。
