代码质量工程：静态检查分层、增量门禁与 code review

🏷️ 代码质量

先立一条原则：质量不是靠人盯出来的，是靠工具卡出来的。凡是机器能判定的事情，交给人就是浪费——人会累、会放水、会在同一个问题上给出不一致的判断，而工具不会。人的注意力应该留给机器判断不了的那部分：设计、边界条件、可测性、命名是否表达意图。

四层防线：每一层放什么，取决于它的反馈延迟

把所有检查堆在 CI 里是常见错误：格式问题在 CI 才报，作者要在本地改完再推一次，一次往返几分钟。检查应该尽量左移，放在反馈最快的那一层。

层级时间预算适合放绝不要放
编辑器毫秒，无感格式化、类型检查、高置信规则需要编译整个项目或跑测试的检查
提交前 hook不超过 2 秒格式化自动改写、改动文件的快速 lint、密钥与大文件拦截全量测试、集成测试、全量 lint——超过两三秒大家就会开始绕过它
CI 卡口分钟级全量 lint（只报增量）、类型检查、单测与集成测试、构建需要人工确认的检查；跑一小时的全量端到端
定期扫描小时或天级复杂度与重复率趋势、依赖更新与许可、变异测试阻断合并的硬门禁——趋势类指标不适合卡单个 PR
⚠️
提交前 hook 的时间预算是硬约束

我见过团队在 pre-commit 里跑全量单测，理由是「这样最安全」。实际结果是每次提交等 40 秒，两周后所有人的肌肉记忆都变成了跳过校验的参数，这道防线整体失效，连带格式化也不再执行。hook 只放能在两秒内完成、且能自动修复的东西，需要更久的检查放 CI。

三类静态检查工具别混为一谈

这三类工具的定位完全不同，混在一起谈就会得出「lint 规则太多太烦」这种错误结论——真正烦人的通常是把风格规则设成了阻断。

类别代表工具它回答什么问题该不该阻断构建
格式化gofmt / gofumpt、Prettier、Black、spotless、rustfmt代码长什么样不产生告警，直接自动改写。CI 里只校验「是否已格式化」，不一致就失败
Linter（坏味道与可疑代码）golangci-lint、ESLint、Ruff、SpotBugs、Clippy这段代码是不是可疑、是不是有隐患分两档：高置信规则（漏检 error、资源未关闭、空指针解引用）阻断；风格类规则只提示
类型与静态分析TypeScript、mypy、go vet、NullAway、Infer这段代码在类型与数据流层面是否自相矛盾必须阻断。它的误报率最低，发现的问题也最接近真 bug

格式化必须是自动的，且零配置争论。具体选哪种风格的收益差异接近于零，而讨论它的成本很高。更重要的是：一旦格式问题出现在评审意见里，评审的注意力就被从设计上偷走了。格式化的目标是让格式在人看到之前就已经不存在争议。

规则怎么选：默认起步，逐步收紧，只卡增量

这是老项目落地 lint 最关键的一节。新规则只对增量代码生效——这不是妥协，而是唯一可行的路径。

为什么不能一次性修存量：一个几千文件的纯格式与 lint 改动，评审无法真正进行（没人能逐行看完），它会和所有在飞的分支产生大面积冲突，还会把 git blame 冲掉一层，之后排查历史问题都要多绕一道。最常见的结局是有人受不了，把检查整体关掉。

阶段动作风险与对策
第 0 周只开格式化，全仓一次性跑完并单独提交一个「纯格式化」commit，登记到 blame 忽略列表冲突集中在这一次；选在发布窗口后、在飞分支最少的时候做
第 1 周开默认规则集，但全部设为提示，先观察一周的真实噪音量不要凭想象裁剪规则，用真实数据决定
第 2 周把高置信规则（漏检 error、资源泄漏、空指针、并发误用）改成阻断，并设定基线只卡增量基线必须用 merge-base，否则主干的新提交会被算成你的问题
持续每季度收紧一档；被反复豁免的规则直接删掉，不要留着当噪音豁免必须写理由；无理由的豁免注释在评审里拒绝
存量不专门立项修，随模块被重写自然消化；只对「碰到的文件」要求达标避免出现大量与需求无关的改动混在业务 PR 里

# .golangci.yml —— 老项目能不能落地，全看 issues.new-from-rev 这一行
run:
  timeout: 5m
  tests: true            # 测试代码同样检查：它往往是最先腐烂的部分

linters:
  disable-all: true      # 显式开启，避免升级版本后凭空多出一批规则
  enable:
    - errcheck           # 被忽略的 error 返回值，Go 里性价比最高的一条
    - govet              # 官方分析器：printf 格式串、锁被值拷贝等
    - staticcheck        # 真 bug 检测，误报率低
    - ineffassign        # 赋值了但从未被使用
    - bodyclose          # HTTP 响应体没关，等于连接泄漏
    - rowserrcheck       # 迭代完 sql.Rows 没检查 Err，会静默丢数据
    - errorlint          # 用等号比较 error 而不是 errors.Is，包装后必然失效
    - contextcheck       # context 断链，超时与取消传不下去
    - gosec              # 安全类规则；依赖漏洞扫描与 SBOM 详见站内 OWASP 一篇
    - revive             # 风格规则，替代已归档的 golint

linters-settings:
  errcheck:
    exclude-functions:
      - (*os.File).Close # 只读文件 Close 失败没有可行动作，豁免它减少噪音
  gocyclo:
    min-complexity: 15   # 当信号用，不当硬上限
  revive:
    rules:
      - name: unused-parameter
        severity: warning # 风格类只提示，避免把噪音变成阻断

issues:
  new-from-rev: origin/main  # 核心：只报告基线之后新增的问题，存量代码不动
  max-issues-per-linter: 0   # 不截断，否则你以为只有 50 个问题
  max-same-issues: 0
  exclude-rules:
    - path: _test\.go
      linters: [gosec, errcheck]  # 测试代码里这两类检查适当放宽

# .pre-commit-config.yaml —— 只放「快到无感」的检查，总耗时目标 2 秒内
repos:

      - id: detect-private-key          # 挡住误提交的私钥
      - id: check-added-large-files

  - repo: local

        entry: gofumpt -w
        language: system
        types: [go]

      - id: golangci-lint-fast

# 不要在这里跑全量测试或集成测试。一旦超过两三秒，
# 所有人都会开始用跳过校验的参数，这道防线会连带格式化一起失效。

#!/usr/bin/env bash
# 增量检查的两种口径：按提交基线、按改动行。CI 与本地都用同一个脚本，避免不一致
set -euo pipefail

BASE="${1:-origin/main}"
# 必须用 merge-base：直接和 origin/main 比，会把别人合进主干的新提交算成你的问题
MERGE_BASE="$(git merge-base HEAD "$BASE")"

# 口径一：只报基线之后新增的问题
golangci-lint run --new-from-rev="$MERGE_BASE" ./...

# 口径二：只检查本次改动到的行，语言无关，适合多语言仓库
# -U0 让 diff 不带上下文行，避免把邻近的存量问题也算进来
git diff -U0 "$MERGE_BASE" | reviewdog -f=diff -f.diff.strip=1 -reporter=local -fail-on-error

# Python：只检查改动到的文件
git diff --name-only --diff-filter=ACM "$MERGE_BASE" -- '*.py' | xargs -r ruff check

# 一次性生成存量基线：把当前所有问题的指纹写进文件并入库，之后只比对新增。
# 适合没有 SonarQube 这类平台的团队，成本几乎为零。
golangci-lint run --out-format=line-number ./... 2>&1 | sort > .lint-baseline

复杂度与重复：信号而不是上限

复杂度指标最大的误用是设成硬性上限。硬上限会诱发一种很糟的规避行为：把一个大函数机械切成五个只被调用一次、名字叫 doStepOne 的小函数——指标下去了，可读性更差了，因为你现在要跳五次才能读完一条逻辑。

指标值得留意该动手它真正在提示什么
圈复杂度超过 10超过 15分支太多，测试用例数会指数增长；通常是缺了一张策略表或状态机
函数长度超过 50 行超过 100 行混了多个抽象层级，读的时候要不断切换视角
嵌套深度超过 3 层超过 4 层该用提前返回（卫语句）把错误路径先挡掉
文件长度超过 500 行超过 1000 行职责不清，且这种文件必然是合并冲突的重灾区
参数个数超过 4 个超过 6 个该收成一个参数对象，顺带解决调用处「一串布尔值」的可读性问题
重复块同一段逻辑出现 3 次3 次以上且都要同步改到了该抽象的时刻；出现 2 次时通常还不该抽

关于重复，三次原则值得认真执行：出现两次时不要抽象。两个看起来一样的代码块很可能在下个需求里分道扬镳，过早抽象出来的共用函数会长出一堆布尔参数来区分调用方，那种函数比重复代码难维护得多。可以接受的重复还包括：跨模块边界的重复（为了不引入不该有的依赖）、测试代码里为了可读性的重复、生成代码的重复。

依赖治理

依赖是最容易失控的质量维度，因为引入一个依赖只需要一行，而移除它可能需要一周。几条硬规则：

  • 锁文件必须入库。没有锁文件就没有可重现的构建，「我这儿是好的」这句话有一半来源于此。
  • 版本要钉死。开放区间意味着你的构建结果取决于构建那一刻上游发了什么版本。
  • 引入前看三个数：最近一次提交时间、未决问题数、它自己又拉进来多少间接依赖。一个为了省二十行代码而引入的库带来四十个间接依赖，这笔账是亏的。
  • 许可合规要自动检查。强传染性许可混进闭源产品是法务风险，人工审核一定会漏。
  • 更新要小步高频。用自动化机器人每周提小版本升级 PR，比一年攒一次大升级安全得多。

依赖漏洞扫描（SCA）与物料清单（SBOM）属于安全工程，详见站内 OWASP Top 10 一篇，这里不展开。

code review 该看什么

评审的第一原则：机器能查的绝不留给人。格式、命名规范、未使用变量、简单空指针、资源未关闭，全部交给工具。人只看机器看不了的。

关注点谁来查具体看什么
格式、导入顺序、命名规范工具格式化器与 linter，人不应该在这里留下任何一条意见
未使用变量、漏检 error、资源泄漏工具linter 与静态分析，直接阻断
设计与结构人是否与现有抽象一致、有没有引入不该有的依赖方向、是不是过度设计
边界条件人空集合、零与负数、区间端点、并发、重复请求，有没有对应用例
错误处理人失败后状态是否一致、错误信息是否可定位、有没有把异常吞掉
可测性人新代码好不好测；如果作者自己都测不了，说明设计有问题
命名是否表达意图人名字与实际行为是否一致（这类不一致是最贵的技术债）
数据与安全影响人迁移是否可回滚、日志有没有打印敏感信息、权限校验是否到位

评审反模式也要点出来：只挑格式问题（说明工具没配好，也说明评审没投入）；评审一个跨六十个文件的 PR（注意力在第三百行就耗尽了，等于没审）；无理由地要求改动（意见必须带理由，并区分「必须改」和「建议改」）；批准但没看（这是最坏的一种，它让所有人都误以为这段代码被检查过）。

PR 的大小是质量的最强预测因子

如果只能改一件事来提升代码质量，我会选「把 PR 变小」。经验值是400 行以内，最好 200 行左右。超过之后评审者的注意力衰减很快，剩下能看出来的只有命名和格式，而设计缺陷会完整地进入主干。

sequenceDiagram participant A as 作者 participant CI as 流水线 participant R as 评审人 Note over A,R: 小 PR：一次往返就能合并 A->>CI: 推送 120 行改动 CI-->>A: 4 分钟返回，格式与 lint 已在本地自动通过 A->>R: 请求评审，说明「为什么这么改」 R-->>A: 两条设计意见，指出漏了一个边界条件 A->>R: 补一个用例并回复 R-->>A: 批准合并 Note over A,R: 大 PR：注意力在第三百行就耗尽了 A->>R: 请求评审 2400 行、跨 60 个文件 R-->>A: 隔两天回复，只挑出几个命名问题后批准 Note over A,R: 设计缺陷完整进入主干，回滚时还要拆开无关改动

拆分手法（按可操作性排序）：纯重构和行为变更永远分开提交，这一条能让评审者立刻知道哪些 diff 需要动脑；接口定义与实现分两次；数据库迁移与使用它的代码分两次（顺带解决上线顺序问题）；用开关把未完成的功能藏起来，先把骨架合进主干；把「顺手改的」无关内容单独开一个 PR。

技术债与质量度量

技术债管理失败的典型形态是：代码里散落着三百个 TODO，没有人知道哪些还有效，也没有任何一条会被真正处理。只写在注释里的债等于没记。

stateDiagram-v2 [*] --> spotted spotted --> recorded: 代码里打统一标记并关联工单号 recorded --> scheduled: 排进迭代的固定偿还预算 scheduled --> paid: 偿还完成并删除标记 recorded --> wontfix: 模块即将下线或重写 recorded --> recorded: 定期复评，上调或下调优先级 paid --> [*] wontfix --> [*] note right of recorded 标记必须带工单号与责任人 没有工单号的标记在 CI 里直接拒绝 工单关闭时 CI 提醒清理残留标记 end note

可操作的机制：统一用一个带工单号的标记（比如 TODO(PROJ-1234)），CI 校验格式，没有工单号就不允许合并；每个迭代留固定比例的容量偿还债务，不留预算等于永远不还；定期复评，因为有些债会自己消失。

哪些债不该还：即将下线或重写的模块（花在上面的每一分钱都会被扔掉）、已经稳定几年不再改动且没有安全问题的代码（还它的收益是零，风险却是实的）、只是风格与个人偏好不同的部分。把「不还」明确记录下来，比让它挂在待办列表里消耗注意力更好。

不要用的指标为什么改用
代码行数、提交次数极易优化，且与价值负相关：删掉代码往往是贡献变更失败率：多少次发布需要回滚或紧急修复
测试覆盖率当 KPI可以用无断言测试刷满，理由详见站内测试策略一篇缺陷逃逸率：有多少 bug 是用户报告而非测试发现
关闭工单数鼓励拆小票和挑软柿子从提交到上线的时长：直接反映流程摩擦
lint 告警总数存量噪音会淹没趋势，还会诱发批量豁免增量代码的告警密度：只看新写的代码
人均评审意见数会催生大量无价值的格式类意见平均评审等待时长与 PR 平均大小

依赖版本用开放区间同一份代码不同时间构建结果不同问题无法复现，「我这儿是好的」钉死版本，锁文件入库，机器人小步升级
为降复杂度机械拆函数一堆只被调用一次的 doStepOne指标漂亮，可读性反而更差指标当信号，由人判断是本质复杂还是该重构

最容易踩的坑
  • 增量基线直接和主干比而不用 merge-base。别人合进主干的提交被算成你的问题，PR 莫名其妙红一片。
  • 纯格式化提交没登记到 blame 忽略列表。之后每次追查历史改动都要多跳一层，所有人都得多花时间。
  • 把 lint 的报告条数截断。默认只显示前若干条，你以为只有几十个问题，实际有上千。
  • 测试代码被排除在检查之外。它是最先腐烂的部分，烂了之后整个套件的可信度一起下滑。
  • 在 pre-commit 里跑需要编译整个项目的检查。提交等半分钟，两周后全员绕过校验。
  • 豁免注释不写理由。半年后没人知道这条豁免还需不需要，于是永远留着。
  • 把复杂度设成硬上限。诱发机械拆分，指标下去了但代码更难读。
  • 只出现两次就抽公共函数。下个需求让两处分道扬镳，共用函数长出一串布尔开关参数。
  • 锁文件不入库或被 gitignore。构建不可重现，线上问题在本地永远复现不出来。
  • 许可合规靠人工审核。强传染性许可混进闭源产品，发现时已经发版了。
  • 用行数或提交数度量产出。删代码的贡献被算成负分，团队学会写更长的代码。
  • 批准了却没看。这是评审里唯一真正有害的行为：它让整个团队误以为这段代码被检查过。
