测试策略与可测性设计

🏷️ 测试

先把目的说清楚，后面所有判断才有依据：测试的唯一目的是让改动变得安全。不是证明代码没有 bug（做不到），不是完成某个覆盖率数字（那是副产品），更不是给 code review 交差。一个团队敢不敢在周五下午重构核心模块，就是这套测试的真实分数。

从这个目的能直接推出两条判定标准，本文所有结论都是它俩的推论：

  • 它失败的时候，能不能指出一个明确的问题。如果测试红了你的第一反应是「再跑一遍看看」或者「大概是测试写得不对」，这个测试是负资产。
  • 它通过的时候，能不能让你敢重构。如果你改了内部实现、外部行为一点没变，却要跟着改二十个测试，那测试已经从安全网变成了水泥。

好测试与坏测试：六个可判定的特征

「测试写得好不好」这句话太虚，拆成六个能当场判定的维度就具体了。注意每一行最后一列——那是你今天不管它、半年后要付的账。

维度好测试坏测试放任的代价
关注点断言外部可观察行为：返回值、最终状态、发出的事件断言实现细节：调了哪个方法几次、内部走了哪个分支重构必然大面积改测试，团队干脆不重构了
失败信息名字与断言合起来就是一句结论，不用打开源码只提示 expected true but was false每次排查要反向阅读测试代码，平均多花十几分钟
独立可重复任意顺序、任意并发、跑一百次结果一致依赖前一个用例留下的数据或执行顺序随机失败，最终演变成「红了就重跑」，门禁失效
速度单元测试单个用例低于 10 毫秒，全量套件秒级单测里连数据库、用睡眠同步，单个用例几秒本地没人跑，问题全部推迟到流水线才暴露
维护成本改一条业务规则，只有对应那一两个用例需要改改一个字段名，几十个测试同时编译不过测试代码量增长快于业务代码，团队开始删测试
防御力能复现过去真实发生过的 bug（回归用例）只测了正常路径，边界一个没碰覆盖率很高但线上照样出事，测试信誉破产
💡
一个立刻可用的自检动作

随手挑三个测试，把被测代码里的一行业务判断故意改错（比如把大于号改成大于等于），看有没有测试变红，以及红掉的那条失败信息能不能让你在不看源码的情况下猜到改错了哪里。这是「变异测试」的手工版，比看覆盖率报告有用得多：覆盖率只告诉你代码被执行过，变异测试告诉你代码被真正验证过。

金字塔、蜂巢、冰淇淋：形状由架构决定

测试金字塔被讲成了教条，真正该记住的是它背后的经济学：越靠底层的测试，定位问题越快、维护越便宜、越稳定。所以在能用底层测试覆盖的地方，不要用上层测试去覆盖。但这句话反过来不成立——如果风险本来就不在底层，硬凑底层测试只是自我安慰。

形状分布特征适合什么架构用错时的症状
经典金字塔单元测试占大头，集成测试次之，端到端极少领域逻辑厚、外部依赖少的单体或核心计算服务（计费、风控、排班）套在薄服务上：单测全绿，上线死在 SQL 方言和字段序列化上
蜂巢（中间鼓）集成测试最多，单元测试只覆盖少量复杂算法微服务：单服务逻辑薄，风险集中在数据库、消息、下游契约套在厚逻辑模块上：每个边界条件都要起容器，套件跑一小时
冰淇淋（反模式）端到端与手工测试最多，底层几乎没有没有适合的架构，这是历史欠账的形状随机失败率两位数、一个 bug 要半天定位、改任何东西都要全量回归
钻石（两头小、中间偏上大）集成与接口测试多，单元少，端到端留几条以编排和聚合为主的 BFF、网关层误以为覆盖了业务规则，实际规则在下游服务里从没被测

判断方法不是照抄比例，而是问两个问题：这个模块的 bug 历史上出在哪一层，就把测试补在那一层；这一层的 bug 如果用更底层的测试也能暴露，就下沉。至于金字塔各层在流水线里怎么落位、提交阶段跑哪些、合并后跑哪些、反馈时间怎么切预算，那属于流水线编排，详见站内 CI/CD 专题，本文不重复。

测试替身的五种类型，先分清再谈用不用

日常交流里所有替身都被叫成 mock，这是很多问题的起点——因为五种替身里只有一种天生会把实现细节写进测试，其他四种不会。把名字分清，讨论才能进行。

类型行为典型用途滥用后果
Dummy只为填参数位，从不被真正调用构造函数要五个依赖，本用例只关心一个基本无害；但如果它其实被调用了，你会看到空指针而不是清晰失败
Stub对指定输入返回预设值，不做任何校验让汇率查询固定返回 7.2，好测下游的换算逻辑预设值与真实服务的返回结构脱节，测试通过但线上解析失败
Spy照常执行或空转，同时记录被调用的参数事后断言「邮件发给了正确的收件人」记录太多细节后变质成 Mock，同样绑死实现
Mock调用前预设期望，调用时或结束时校验期望是否满足验证「库存扣减恰好发生一次」这类必须发生的副作用把调用次数、参数顺序、调用链固化成规格，重构必然大面积变红
Fake简化但真实可用的实现内存版仓储、内存版缓存、可快进的假时钟与真实实现语义偏离（比如内存仓储不做唯一约束），测试通过而生产报错

过度使用 Mock 是测试最常见的病

这是我见过最普遍、也最难挽回的问题。典型表现：一个测试文件前二十行全是「当调用 A 时返回 X、当调用 B 时返回 Y」，最后一行断言「C 被调用了一次」。这种测试的本质是把实现步骤抄了一遍——它唯一能发现的 bug 是「你改了实现」，而这恰恰不是 bug。

后果是可测量的：重构成本从「改业务代码」变成「改业务代码加改测试」，于是团队做出理性选择——不重构。测试原本是为了让改动变安全，现在成了阻碍改动的最大摩擦源。这个拐点一旦过去，接下来就是删测试或者关门禁。

❌
流传很广但错的说法：单元测试就是要把所有依赖都 Mock 掉

这句话把「单元」误读成了「一个类」。正确的边界是进程边界与不确定性边界：跨进程的（数据库、HTTP、消息中间件）、不确定的（时间、随机数、机器名、环境变量）才需要替身；同一进程内你自己写的类、值对象、纯计算函数，直接用真的。把自家领域对象也 Mock 掉，测试就只剩一堆连线，验证不了任何业务规则。

可测性是设计出来的，不是测出来的

「这段代码没法测」几乎从来不是测试技巧不够，而是设计问题。下面五条是投入产出比最高的改造，每条都给出「不改会怎样」。

坏写法不改会怎样（具体场景）改造方式
业务逻辑里直接调系统时钟「优惠券在有效期最后一秒仍可用」这条规则只能靠改机器时间来测；跨月、闰年、时区边界永远测不到抽一个只有 Now 方法的时钟接口注入，测试用可快进的假时钟
方法里 new 出依赖（数据库连接、HTTP 客户端）测试一跑就真连外网，CI 里网络不通就红，别人机器上结果还不一样依赖从构造函数传入，生产注入真实实现，测试注入 Fake
构造函数里做 IO（读配置文件、连库、预热缓存）只想测一个纯计算方法，却必须先准备好整套环境；对象在测试里根本创建不出来构造函数只赋值，IO 挪到显式 init 或首次使用时；配置以值的形式传入
静态方法与单例持有可变状态用例之间通过静态字段互相污染，单独跑绿、全量跑红；并行执行直接崩改成实例方法加接口；必须保留静态时提供显式 reset，或改为不可变
副作用和判断混在一个函数里想验证「金额算得对不对」，必须先让数据库有数据、再让邮件发得出去，一个断言拖着三套环境纯函数核心加薄外壳：判断与计算返回「要做什么」，IO 由外壳执行

最后一条是纲，其他四条是它的细则。核心思路是把系统切成两半：内层是没有任何 IO 的纯函数，分支都在这里，用毫秒级单元测试穷举；外层是几乎没有分支的编排壳，用少量集成测试覆盖。

// ========== 反例：时间写死在业务逻辑里，跨天逻辑无法测试 ==========
func IsExpired(o *Order) bool {
    return time.Now().After(o.ExpireAt) // 测试只能改系统时间，或者真的等
}

// ========== 改造：把「现在」当依赖注入 ==========
type Clock interface{ Now() time.Time }

type SystemClock struct{}

func (SystemClock) Now() time.Time { return time.Now() }

// 测试专用时钟：可任意设定与快进，不需要 sleep
type FakeClock struct{ t time.Time }

func (f *FakeClock) Now() time.Time          { return f.t }
func (f *FakeClock) Advance(d time.Duration) { f.t = f.t.Add(d) }

type OrderService struct {
    clock Clock
    rng   *rand.Rand // 随机数同理：种子由外部给，测试里用固定种子保证可重复
}

func (s *OrderService) IsExpired(o *Order) bool {
    return s.clock.Now().After(o.ExpireAt)
}

// 精确测边界：恰好等于过期时刻算不算过期？这是真实出过事故的一行
func TestIsExpired_恰好等于过期时刻(t *testing.T) {
    exp := time.Date(2026, 3, 1, 0, 0, 0, 0, time.UTC)
    c := &FakeClock{t: exp}
    s := &OrderService{clock: c}

    if s.IsExpired(&Order{ExpireAt: exp}) {
        t.Fatal("等于过期时刻时不应算过期：After 是严格大于，这是与产品约定的语义")
    }
    c.Advance(time.Nanosecond) // 快进 1ns，而不是 time.Sleep
    if !s.IsExpired(&Order{ExpireAt: exp}) {
        t.Fatal("超过过期时刻必须算过期")
    }
}

// ========== 纯核心：输入输出全是值，测试不需要任何替身 ==========
type Decision struct {
    NewStatus string
    Emails    []string
    RefundFen int64 // 单位：分，避免浮点
}

func DecideCancel(o Order, now time.Time, p RefundPolicy) (Decision, error) {
    switch o.Status {
    case "shipped":
        return Decision{}, ErrAlreadyShipped
    case "cancelled":
        // 幂等：重复取消不报错也不重复退款，这条规则必须有独立用例
        return Decision{NewStatus: "cancelled"}, nil
    }
    refund := p.Calc(o.PaidFen, now.Sub(o.PaidAt)) // 阶梯退款，分支都在这里
    return Decision{
        NewStatus: "cancelled",
        Emails:    []string{o.BuyerEmail},
        RefundFen: refund,
    }, nil
}

// ========== 薄外壳：只做 IO 编排，几乎没有业务分支 ==========
func (s *OrderService) Cancel(ctx context.Context, id int64) error {
    return s.repo.InTx(ctx, func(tx Tx) error {
        o, err := s.repo.Load(ctx, tx, id)
        if err != nil {
            return err
        }
        d, err := DecideCancel(o, s.clock.Now(), s.policy) // 唯一的业务判断
        if err != nil {
            return err
        }
        if err := s.repo.UpdateStatus(ctx, tx, id, d.NewStatus); err != nil {
            return err
        }
        if d.RefundFen > 0 {
            if err := s.pay.Refund(ctx, id, d.RefundFen); err != nil {
                return err
            }
        }
        for _, to := range d.Emails {
            // 事务内写 outbox 表，避免「邮件发了但事务回滚」
            if err := s.outbox.Enqueue(ctx, tx, to, "order_cancelled"); err != nil {
                return err
            }
        }
        return nil
    })
}

什么该测、什么不该测

测试是有成本的资产，不是越多越好。给每段代码问一句：这里有没有「可能写错的决策」。没有决策的地方写测试，只是在给未来的重构加锁。

代码类型测不测理由
业务规则与边界条件（额度、阶梯、有效期、状态流转）必须测，而且要枚举边界决策密集，规则会随需求反复变，测试就是规格文档
复杂算法（排班、分账、限流计算、路径选择）必须测，配合属性测试人脑难以穷举，出错概率最高且后果最贵
历史上出过 bug 的代码必须测，每个 bug 配一个能复现它的用例同一个坑踩两次是最不可接受的失误
错误处理与降级路径必须测这些分支线上极少走到，唯一被验证的机会就是测试
仓储层 SQL、序列化、事务边界用集成测试，不用单元测试Mock 掉数据库后什么都没验证到，详见站内集成测试一篇
getter、setter、equals、纯 DTO不测没有决策；IDE 生成的代码错不到哪去，测了只增加改字段的成本
框架胶水与注解配置（路由声明、依赖装配）不测，靠一条冒烟用例兜住能启动配置错了启动就失败，单独测每一条配置收益极低
只做一层转发的 controller不单独测并入接口级集成测试，顺带验证序列化与状态码

覆盖率是探测器，不是指标

先纠正一个流传很广的错误：覆盖率不衡量测试质量。把所有测试的断言全部删掉，覆盖率一分不少，因为它只统计「代码被执行过」，不统计「结果被检查过」。它的正确用法只有一个——翻开报告找红色区块，确认那些从没被执行的分支里有没有重要业务规则。

口径含义能发现什么盲区
行覆盖这一行是否被执行过整段死代码、完全没被调用的函数一行 if 只要执行就算达标，假分支可能从未走过
分支覆盖每个判断的真假两侧是否都走过漏测的 else、漏测的错误返回复合条件里的短路项仍可能没被单独验证
条件覆盖复合条件中每个子条件的真假都走过短路求值导致的漏测（前一个条件为假时后面根本没执行）用例数量增长快，通常只对核心算法开
变异得分故意改坏代码后，有多少比例的变异被测试抓住有执行没断言的假测试跑得慢，适合定期对核心模块跑，不适合每次提交

实践建议：看分支覆盖，关注趋势和增量代码而不是全局绝对值，报告当参考不当 KPI。把覆盖率设成流水线硬门禁会引出一串副作用（为了过线写无断言测试、给测试加排除注解、拆分文件绕过统计），这部分详见站内 CI/CD 专题。

测试数据与命名：让失败信息自己说话

测试套件腐烂通常从两个地方开始：一个共享的巨型测试夹具，和一堆叫 test1 的方法。

测试数据用构造器造，不要共享可变夹具。共享夹具的问题是：为了让用例 A 通过而改了夹具的某个字段，用例 B 莫名其妙红了；而且读一个用例时你无法判断哪些字段和当前规则有关。构造器模式给出一组合法默认值，每个用例只显式写自己关心的那一两个字段，噪音归零。

// 测试数据用 Builder 造：默认值合法，用例只写与自己相关的字段
public final class OrderFixture {
    private String status = "paid";
    private long paidFen = 10_000L;                                 // 100 元
    private Instant paidAt = Instant.parse("2026-03-01T00:00:00Z");  // 固定时间，不用 now

    public static OrderFixture anOrder() { return new OrderFixture(); }

    public OrderFixture status(String s)  { this.status = s;  return this; }
    public OrderFixture paidFen(long f)   { this.paidFen = f; return this; }
    public OrderFixture paidAt(Instant t) { this.paidAt = t;  return this; }

    public Order build() { return new Order(status, paidFen, paidAt); }
}

@Test
@DisplayName("已发货的订单取消时，应拒绝并说明原因")
void 已发货订单不允许取消() {
    Order o = anOrder().status("shipped").build(); // 只有这一个字段与本规则有关

    assertThatThrownBy(() -> service.decideCancel(o, FIXED_NOW))
        .isInstanceOf(AlreadyShippedException.class)
        .hasMessageContaining("shipped"); // 断言到具体信息，而不是只断言抛了异常
}

随机数据要慎用。用随机字符串填无关字段是好的（能暴露「测试偷偷依赖了某个具体值」），但用随机数据构造被断言的输入是坏的——失败无法复现。折中做法是固定种子并在失败信息里打印种子，这样任何一次失败都能原样重放。

命名要写清「在什么条件下、做什么、期望什么」。好名字的收益在于：流水线上一行红字就够你判断问题，不需要打开文件。

// 坏：失败时你只知道「有个测试挂了」
func TestCancel1(t *testing.T)       {}
func TestCancelError(t *testing.T)   {}
func TestOrderService(t *testing.T)  {}

// 好：名字本身就是一条规格，失败信息可以直接贴进工单
func Test已支付订单7天内取消_应全额退款(t *testing.T)                   {}
func Test已支付订单超过7天取消_应按阶梯比例退款(t *testing.T)            {}
func Test已发货订单取消_应返回ErrAlreadyShipped且不产生退款(t *testing.T) {}
func Test重复取消同一订单_应幂等且只退款一次(t *testing.T)               {}

// Java 用 @DisplayName 承载同样的信息，中文可读性更好：
// @DisplayName("超过 7 天的已支付订单取消时，按阶梯比例退款")

反模式清单

反模式症状真实后果修法
测试依赖执行顺序单独跑绿，全量跑红；换个框架版本就崩并行执行无法开启，套件时间下不来每个用例自造数据、自清理，禁止共享静态可变状态
断言太宽泛通篇只有「不为 null」「没抛异常」逻辑写错了测试照样绿，覆盖率却很好看断言到具体值、具体状态、具体错误类型与关键信息
一个测试断言十件事用例名叫「测试下单流程」，两百行第三个断言挂了，后面七个的状况完全不可知一个用例一个行为；公共准备抽成构造器
测试里写复杂逻辑测试里有 if、循环、自己算期望值测试自身有 bug 却没人测它，得出错误的绿或红期望值写成字面量常量；分支用表驱动展开成多个用例
为覆盖率写无断言测试调完方法就结束，没有任何断言覆盖率达标但零防御力，给团队虚假安全感每个用例至少一条实质断言；用变异测试抽查
改代码必然改测试纯内部重构引发几十个测试编译不过重构被放弃，代码持续腐化断言行为不断言实现；测试入口提到用例边界
把私有方法改成公开只为了测它一堆只被测试调用的公开方法封装被打破，内部结构被固化，无法自由重构通过公开行为间接覆盖；真的复杂就抽成有独立身份的类
测试代码不做 review业务代码卡得很严，测试随便合测试代码质量最先崩塌，随后拖垮整个套件测试与业务代码同标准 review，详见站内代码质量一篇
❌
最容易踩的坑
  • 用 Mock 替代自己写的纯逻辑。断言全落在「某方法被调了一次」上，删掉一整段业务计算测试依然全绿。
  • 在业务逻辑里直接调系统时钟或随机数。「优惠券最后一秒可用」「月末结算」这类规则从此无法测，只能靠改机器时间。
  • 构造函数里做 IO。对象在测试里根本创建不出来，逼着后人把本该是单测的东西写成集成测试。
  • 共享一个巨型测试夹具。为了让 A 通过改了一个字段，隔天 B 红了，而两者看起来毫无关系。
  • 把覆盖率当质量指标。把所有断言删掉覆盖率不变，这一条自己试一次就懂了。
  • 只看行覆盖不看分支覆盖。错误处理分支通常一次都没跑过，而线上故障恰恰都在那里。
  • 只测正常路径。空集合、单元素、最大值、越界、重复、负数、零一个都没碰，bug 几乎全在这些地方。
  • 断言只写不为 null。这种测试唯一的作用是阻止你重命名字段。
  • 把私有方法改成公开只为了方便测试。封装一破，内部结构就被测试锁死了。
  • 修了线上 bug 却不补回归用例。同一个坑三个月后原样复发，而且通常是同一行代码。
  • 照抄金字塔比例不看架构。薄编排服务硬凑七成单测，最后全部死在数据库方言上。
  • 把随机失败的测试加进跳过名单而不查原因。跳过名单只会变长，半年后门禁形同虚设；随机失败的识别与治理详见站内 CI/CD 专题。
