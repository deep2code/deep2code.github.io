泛型这八年走过的路

Go 1.18 引入泛型，是 1.0 以来最大的语法变更。从 1.18 的类型参数和约束，到 1.23 的迭代器、1.24 的泛型类型别名，再到 1.27 的泛型方法，这块拼图花了八年才补齐。先看时间线：

核心心智模型
泛型解决"算法和数据结构的类型抽象"，接口解决"行为多态"。两者不是替代关系，各管一摊——这也是 Go 刻意不同于 C++ 模板和 Java 泛型的设计取舍。

2025-2026 最新特性

Go 1.23 迭代器

range over func 让函数能当迭代器用。迭代器函数类型签名是 func(yield func(T) bool)：每次产出一个值调 yield，yield 返回 false 表示调用方要提前终止。

func(yield func(int) bool)

func Squares() func(yield func(int) bool) {
    return func(yield func(int) bool) {
        for i := 1; i <= 10; i++ {
            if !yield(i * i) {
                return
            }
        }
    }
}

for sq := range Squares() {
    fmt.Println(sq)
}

迭代器把"惰性遍历"带进标准库：slices.All、maps.Keys 都返回迭代器，配合 range 免去了先切片再遍历的中间分配。

Go 1.24 泛型类型别名

泛型类型别名给泛型命名类型起别名，复杂签名里短一点：

type Map[K comparable, V any] = map[K]V

func Process[K comparable, V any](m Map[K, V]) {
    for k, v := range m {
        fmt.Println(k, v)
    }
}

Go 1.27 泛型方法

以前方法不能有自己的类型参数（只能复用接收者的）。1.27 解除了这个限制：

type Container[T any] struct {
    value T
}

func (c Container[T]) Get() T { return c.value }

// 泛型方法：方法自己声明类型参数 U，和接收者的 T 独立
func (c Container[T]) Map[U any](fn func(T) U) Container[U] {
    return Container[U]{value: fn(c.value)}
}

c := Container[int]{value: 42}
result := c.Map(func(x int) string { return strconv.Itoa(x * 2) })

这一改直接解锁了类型安全 ORM、依赖注入容器这些过去因为"不能泛型方法"被迫用 interface{} 妥协的场景。

基础写法回顾

// 泛型函数
func PrintSlice[T any](s []T) {
    for _, v := range s {
        fmt.Println(v)
    }
}

PrintSlice([]int{1, 2, 3})
PrintSlice([]string{"a", "b", "c"})

// 泛型结构体
type Pair[K any, V any] struct {
    Key   K
    Value V
}

p := Pair[string, int]{Key: "age", Value: 25}

约束决定类型参数能做什么。1.21 起标准库给了 comparable、cmp.Ordered：

type Number interface {
    int | int32 | int64 | float32 | float64
}

func Add[T Number](a, b T) T { return a + b }

func Max[T cmp.Ordered](a, b T) T {
    if a > b { return a }
    return b
}

func Identity[T any](t T) T { return t }

泛型容器实战

用泛型写个线程不安全的栈，再看多类型参数怎么推断：

type Stack[T any] struct {
    items []T
}

func (s *Stack[T]) Push(item T) {
    s.items = append(s.items, item)
}

func (s *Stack[T]) Pop() (T, bool) {
    if len(s.items) == 0 {
        var zero T
        return zero, false
    }
    item := s.items[len(s.items)-1]
    s.items = s.items[:len(s.items)-1]
    return item, true
}

func Map[T any, U any](s []T, fn func(T) U) []U {
    result := make([]U, len(s))
    for i, v := range s {
        result[i] = fn(v)
    }
    return result
}

// 完整显式类型参数
result1 := Map[int, string]([]int{1, 2, 3}, func(i int) string {
    return strconv.Itoa(i)
})
// 自动推断
result2 := Map([]int{1, 2, 3}, strconv.Itoa)
推断经验
尽量让类型参数出现在函数参数里，便于从实参推断。像 func Zero[T any]() T 这种类型参数只出现在返回值的，必须显式写 Zero[int]()。

标准库实战：slices / maps / iter

1.21 起标准库自带全套泛型工具，日常大半"切片/集合操作"不用自己造轮子：

import (
    "cmp"
    "slices"
    "maps"
)

numbers := []int{3, 1, 4, 1, 5, 9, 2, 6}
slices.Sort(numbers)
slices.SortFunc(numbers, func(a, b int) int { return cmp.Compare(a, b) })
slices.Reverse(numbers)

idx := slices.Index(numbers, 5)
found := slices.Contains(numbers, 5)

m := map[string]int{"a": 1, "b": 2, "c": 3}
keys := maps.Keys(m)
values := maps.Values(m)
equal := maps.Equal(m, map[string]int{"a": 1, "b": 2, "c": 3})

Channel 和 Context 的泛型封装类型安全提升明显。下面是经典的 FanIn：

func FanIn[T any](chs ...<-chan T) <-chan T {
    result := make(chan T)
    var wg sync.WaitGroup

    for _, ch := range chs {
        wg.Add(1)
        go func(c <-chan T) {
            defer wg.Done()
            for v := range c {
                result <- v
            }
        }(ch)
    }

    go func() {
        wg.Wait()
        close(result)
    }()

    return result
}

底层：GCShape 单态化与字典

Go 1.18 的泛型实现是 GCShape（GC Shape）单态化 + 字典传递，介于 C++ 模板全单态化和 Java 类型擦除之间：

  • GCShape 分组：不为每个具体类型生成一份代码，把相同"GC Shape"（内存大小、指针位置）的类型分组共享一份代码。int 和 uint 同组，*int 和 *string 同组，但 int 和 string 不同组。
  • 字典传递：同一份分组代码要区分不同类型的操作（比较、哈希、调方法），编译器自动传入类型字典，对程序员不可见。
  • 和接口的区别：接口在运行时装箱（值拷到堆，存类型指针+数据指针）；泛型不装箱，值直接栈上传。这是泛型比接口快的关键。

什么时候用泛型：决策树

flowchart TD Q[要写一段类型无关的逻辑?] --> A{需要对类型做运算 比较 取字段?} A -->|是 且编译期可知| B{行为要随类型多态?} A -->|否 只要能存能取| IFACE[用接口 any 即可 不必泛型] B -->|否 只是数据结构或算法| GEN[用泛型 T comparable 或 Ordered] B -->|是 要调不同方法| IFACE2[用接口 行为多态]

八个常见坑

  1. 泛型方法历史限制：1.27 前方法不能有自己的类型参数。1.27 后可直接写。
  2. GCShape 间接开销：跨 GCShape 调用走字典，无法内联。性能敏感路径可对关键类型提供特化版本。
  3. 泛型类型方法集不满足非泛型接口：Set[T] 的 Contains(x T) bool 满足不了 interface{ Contains(any) bool }。用泛型接口或类型断言。
  4. 类型推断失败：返回值类型无法从参数推断时显式写。设计 API 时让类型参数尽量出现在参数列表里。
  5. 和 reflect 交互：反射无法运行时动态实例化泛型类型。用代码生成或"非泛型包装+接口"。
  6. 递归实例化：func F[T any]() { F[[]T]() } 会无限展开。递归数据结构用指针字段。
  7. 过度泛化：为简单函数加类型参数、嵌套复杂约束组合，可读性骤降。
  8. 标准库版本兼容：slices/maps/cmp 要 Go 1.21+。老版本用 golang.org/x/exp/slices。

FAQ

Q：泛型会让二进制变大吗？
会，但 GCShape 分组比 C++ 模板膨胀小。用 go build -gcflags=-S 观察，必要时收敛类型实参组合。

Q：泛型和 any 怎么选？
要对值做运算/比较/存数据结构，且类型编译期已知 → 泛型；只要"能存任意值、运行期再断言" → any。

Q：1.27 泛型方法出来后老代码要迁吗？
不用急。老写法仍然合法；新写 ORM、DI 容器这类需要方法级类型参数的库时，再用泛型方法收益最大。

我的取舍

我看着 Go 泛型从 1.18 的"能用"走到 1.27 的"好用"：类型参数、约束、迭代器、泛型别名、泛型方法逐块补齐，标准库 slices/maps 把日常操作都泛型化了。

我自己的经验是：理解 GCShape + 字典模型，你在性能和抽象之间就能做清醒的权衡——泛型管算法和数据结构，接口管行为多态，各就各位。别一上来就把老代码全泛型化，重复到第三次再动手。
