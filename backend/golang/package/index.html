Go Modules：go.mod 里每条指令的真实作用

Go 的依赖管理表面上很简单——一个 go.mod、一个 go.sum、没有 lock 文件。但它的行为经常让从其他语言过来的人意外，因为它的选版算法和其他语言是反的。先把 go.mod 的指令过一遍。

指令作用常见误解或陷阱
module声明模块路径 也是导入前缀发布 v2 时必须在这里加斜杠 v2 忘了改是最高频错误
go声明语言版本下限 决定可用的语言特性它不是工具链版本 也会影响部分 GODEBUG 默认值
toolchain声明构建所用工具链版本 Go 1.21 起可以比 go 指令更新 让语言版本保守而工具链跟进
require声明直接与间接依赖及其版本带 indirect 注释的是传递依赖 手改版本号要跑 tidy 验证
replace把某个模块替换成另一个路径或本地目录只在主模块生效 你的库被别人依赖时 replace 完全被忽略
exclude把某个版本从选版候选里排除实际很少用 因为它管不住传递依赖硬要求该版本的情况
retract发布方声明某个已发布版本作废 Go 1.16 起这是库作者撤回错误版本的正确方式 不要删 tag
go.work多模块本地协同开发 Go 1.18 起不要提交进仓库 它是本地开发文件 会干扰 CI
 
module github.com/acme/order-api

// go 指令是语言版本下限，决定哪些语言特性可用
go 1.24

// toolchain 是构建所用的工具链版本（Go 1.21 起）。
// 和 go 指令分开的意义：语言版本可以保守，工具链可以跟进最新
toolchain go1.27.1

require (
    github.com/go-sql-driver/mysql v1.8.1
    github.com/redis/go-redis/v9 v9.7.0 // 路径里的 /v9 不是笔误：v2 及以上必须带
    google.golang.org/grpc v1.68.0
)

require (
    filippo.io/edwards25519 v1.1.0        // indirect
    github.com/cespare/xxhash/v2 v2.3.0   // indirect
)

// replace 只在主模块里生效。你的库被别人依赖时它会被完全忽略，
// 所以绝不能用 replace 来「修复」库的依赖问题——下游根本看不到
// 用途一：本地联调，指向本地目录
// replace github.com/acme/pkg => ../pkg
// 用途二：临时打补丁，指向自己的 fork
replace github.com/some/broken v1.2.3 => github.com/acme/broken v1.2.3-patch1

// exclude 把某版本从候选里剔除，选版会退到它的下一个可用版本。
// 用得少，因为解决不了「传递依赖明确要求这个版本」的情况
exclude github.com/some/lib v1.4.0

最小版本选择：Go 依赖行为的根源

MVS 的规则只有一句：把依赖图里每个模块被 require 过的所有版本收集起来，对每个模块取最大值。注意它取的是「被要求过的最大值」，而不是「可用的最新版本」——即使 libC v1.6.0 已经发布，只要没有任何模块要求它，就绝不会被选中。

行为Go 的 MVSnpm 与 Maven 一类由此产生的差异
选版依据取被要求过的最大版本取满足约束的最新版本Go 不会因为上游发了新版就改变构建结果
可复现性go.mod 本身即可唯一确定构建列表需要 lock 文件锁定Go 不需要 lock 文件
升级方式必须显式执行 go get 才升重新安装就可能升Go 的升级是有意识动作 且会被记录进 go.mod
拿到新版的时机只有自己或依赖方提高 require 才会拿到随时可能拿到Go 里安全补丁不会自动生效 要主动升
版本冲突处理取最大值 假定向后兼容可能安装多份不同版本Go 同一主版本只会有一份 不兼容变更只能靠主版本路径隔离
典型意外某个传递依赖把版本顶高了 而你并不知情装出来的版本和别人不一样Go 侧要用 go mod why 追来源
💡
MVS 的直接推论：安全补丁不会自动生效

因为 MVS 只取「被要求过」的最大版本，某个依赖发了修复 CVE 的新版之后，你的构建结果不会有任何变化，除非你主动 go get。这和「自动取最新」的生态在心智模型上完全不同，所以 Go 项目必须把 govulncheck 放进 CI 常驻，靠工具而不是靠依赖管理器发现问题。

go.sum、GOPROXY 与私有模块

一个常见误解是把 go.sum 当成 lock 文件。它不是：版本由 go.mod 加 MVS 唯一确定，go.sum 只负责校验下载到的内容没被动过。删掉 go.sum 不会改变任何一个依赖的版本。

删掉它不会改变选版结果 只会重新下载并重新记录
环境变量或命令作用典型取值或用法配错的后果
GOPROXY模块下载代理 逗号分隔按序尝试国内用 goproxy.cn 逗号 direct不配的话直连境外 拉依赖极慢或超时
GOPRIVATE声明私有模块路径模式 会同时设定后两项默认值公司域名前缀 支持通配私有代码的模块路径被发到公共代理与校验库
GONOPROXY哪些路径不走代理 直连 VCS一般跟 GOPRIVATE 一致私有仓库走公共代理 必然 404
GONOSUMDB哪些路径跳过校验和数据库核对一般跟 GOPRIVATE 一致私有模块因查不到官方哈希而构建失败
GOMODCACHE模块缓存目录默认在 GOPATH 下的 pkg/modCI 不缓存这个目录会每次重新下载全部依赖
GOFLAGS给所有 go 命令加默认参数CI 里设 -mod=readonly 防止意外改 go.mod构建过程悄悄修改 go.mod 导致不可复现
go mod why -m 模块解释这个模块为什么会被引入排查莫名依赖的第一条命令不用它就只能靠猜
go get -u=patch 模块只升补丁版本 不动次版本安全补丁的最小风险升级方式直接 go get -u 会把一堆依赖顶高
go mod verify校验缓存内容与 go.sum 是否一致怀疑缓存被污染时跑被篡改的依赖可能一直用着

关于 vendor：go mod vendor 把依赖源码复制进仓库，构建时加 -mod=vendor（有 vendor 目录时是默认行为）。它的适用场景只有三个：构建环境完全无外网、需要对依赖打本地补丁且不方便 fork、合规要求全部源码可审计。其他情况下 vendor 只会让每次依赖变更产生几千行 diff，把 code review 变成噪音。

关于语义化导入版本：v2 及以上必须在模块路径里带 /v2，这是 Go 独有的设计。原因是 Go 把不同主版本视为不同的包，这样 v1 和 v2 才能在同一个程序里共存——而「我直接依赖 v2 但某个传递依赖还在 v1」是极常见的情况。代价是升主版本时所有 import 都要改，以及库作者必须记得改 module 行。

包的组织：按业务分层，不要按技术分层

这是 Go 项目结构上影响最大的一个决定。从 MVC 框架过来的人习惯建 models、controllers、services、utils，这在 Go 里会持续产生麻烦。

反模式具体问题推荐做法
models 包放所有结构体所有包都要导入它 它成了循环导入的中心类型定义在使用它的业务包里
controllers 与 services 分层一个功能的代码散在三个包 改动面永远是三处按业务能力建包 一个包含完整一条纵切
utils 或 common 包名字不表达职责 于是什么都往里塞 影响面不可估计按能力命名 如 retry httpx timeutil 一个包一件事
base 或 core 包同 utils 且往往还带全局状态拆成具体职责 全局状态改为显式传递
包名与目录名不一致import 之后引用名和预期不同 阅读成本上升保持一致 单数命名 不用下划线
包名带 pkg 或 lib 前缀导入后写成 pkgorder 全是噪音包名就是业务名 order 就叫 order
一上来就建十几层目录项目还没长出结构 目录先固化了错误的假设从扁平开始 出现三个以上同类文件再拆包

循环导入在 Go 里是编译错误，不是警告。这看起来很严格，实际是好事：它强迫你在设计阶段就理清依赖方向。遇到循环导入时，正确的解法有三种：把共同依赖的类型下沉到一个更基础的包、把接口定义移到消费方（下一节）、或者合并这两个本来就该在一起的包。唯一错误的解法是新建一个 common 包把纠缠的东西塞进去，那只是把循环推迟到下一次。

目录约定含义是否有语言层强制我的建议
cmd/xxx可执行程序入口 每个子目录一个 main无 纯约定有多个二进制时才需要 单二进制项目可以把 main 放根目录
internal/只能被本模块导入的私有代码有 编译器强制默认把所有代码放这里 需要对外暴露时再挪出来
pkg/意图对外暴露的公共库无 纯约定争议最大的一个 单体应用里它等于给每个 import 加一层噪音 不建议用
api/协议定义 如 proto 与 openapi无有 IDL 时有用
configs 与 deployments配置与部署文件无按团队习惯 不影响代码结构
test 或 testdatatestdata 被 go 工具链忽略testdata 有特殊语义固定输入放 testdata 它不会被当成包编译

接口定义在消费方

这条惯例和 Java 相反，原因是Go 的接口是隐式实现——实现方不需要知道接口存在。于是消费方可以只声明自己真正需要的方法，依赖关系从「大接口双向牵连」变成「小接口单向依赖」。

// ===== 反例：接口定义在实现方，Java 习惯 =====
// 文件 internal/storage/store.go
package storage

// 一个大而全的接口，然后自己实现它
type Store interface {
    GetUser(ctx context.Context, id int64) (*User, error)
    SaveUser(ctx context.Context, u *User) error
    ListOrders(ctx context.Context, uid int64) ([]*Order, error)
    // 再加二十个方法……
}

type mysqlStore struct{ db *sql.DB }

func New(db *sql.DB) Store { return &mysqlStore{db: db} }

// 后果：order 包只想用 GetUser，却被迫依赖整个 Store；
// 写单测要 mock 二十多个方法；接口加一个方法，所有假实现全部编译不过


// ===== 正例：接口定义在消费方，只声明自己需要的 =====
// 文件 internal/order/service.go
package order

// 只有一个方法，因为这个包只用到一个。
// storage 包完全不知道 order 包的存在，依赖方向严格单向
type UserGetter interface {
    GetUser(ctx context.Context, id int64) (*User, error)
}

type Service struct {
    users UserGetter
}

func NewService(users UserGetter) *Service { return &Service{users: users} }

func (s *Service) Create(ctx context.Context, uid int64, skus []int64) error {
    u, err := s.users.GetUser(ctx, uid)
    if err != nil {
        return fmt.Errorf("get user %d: %w", uid, err)
    }
    if u.Blocked {
        return ErrUserBlocked
    }
    return s.insert(ctx, u, skus)
}

// 文件 internal/order/service_test.go
// 假实现只需要一个方法，三行搞定；接口以后加方法也不影响这里
type fakeUsers struct{ u *User }

func (f fakeUsers) GetUser(context.Context, int64) (*User, error) { return f.u, nil }

这条原则还有一个连带好处：它天然解决了大部分循环导入。order 需要用户数据、user 需要订单数量做统计，按「接口定义在实现方」的写法这两个包会互相导入；按「定义在消费方」的写法，两个包各自声明一个单方法接口，彼此不导入对方，装配在 main 里完成。

init 的危险与显式装配

init() 的执行顺序是确定的：先递归初始化所有被导入的包，同一个包内先初始化包级变量再执行 init，多个文件按文件名顺序。确定不等于好用——依赖这个顺序就等于依赖了导入图的实现细节。

// ===== 反模式：用 init 做隐式初始化 =====
var db *sql.DB

func init() {
    // 问题一：不能返回 error，只能 panic 或 log.Fatal，后者跳过所有 defer
    // 问题二：只要有人导入这个包就会触发，写纯函数单测也会被迫连数据库
    // 问题三：执行顺序取决于导入图，改一处导入就可能改变行为
    // 问题四：拖慢启动，且报错栈离真正的配置问题很远
    var err error
    db, err = sql.Open("mysql", os.Getenv("DSN"))
    if err != nil {
        log.Fatal(err)
    }
}

// ===== 推荐：显式构造，错误可处理，依赖关系一眼看清 =====
type App struct {
    DB    *sql.DB
    Cache *redis.Client
    Order *order.Service
}

func NewApp(ctx context.Context, cfg Config) (*App, error) {
    db, err := sql.Open("mysql", cfg.DSN)
    if err != nil {
        return nil, fmt.Errorf("open mysql: %w", err)
    }
    db.SetMaxOpenConns(cfg.MaxConns)
    db.SetConnMaxLifetime(30 * time.Minute)
    // sql.Open 不建立任何连接，必须 Ping 才知道配置对不对。
    // 放在启动阶段失败，比线上第一个请求才失败好得多
    if err := db.PingContext(ctx); err != nil {
        return nil, fmt.Errorf("ping mysql: %w", err)
    }

    rdb := redis.NewClient(&redis.Options{Addr: cfg.RedisAddr})
    if err := rdb.Ping(ctx).Err(); err != nil {
        return nil, fmt.Errorf("ping redis: %w", err)
    }

    // 依赖关系全写在这里，谁依赖谁一目了然，不需要读 init 反推
    return &App{
        DB:    db,
        Cache: rdb,
        Order: order.NewService(storage.NewUserRepo(db)),
    }, nil
}

func (a *App) Close() error {
    // errors.Join 让多个 Close 的错误都能带出去（Go 1.20 起）
    return errors.Join(a.DB.Close(), a.Cache.Close())
}

// ===== init 仅有的两个合理用途 =====
func init() {
    // 一：把自己注册到注册表里。database/sql 的驱动就是这个模式，
    // 它的必要性来自「导入即生效」这个语义本身就是设计意图
    sql.Register("mydriver", &myDriver{})
}

// 二：包级变量的复杂初始化。但能用 var 直接写完就不要动 init，
// 下面这行比放进 init 里更清晰，且编译期就能发现正则写错
var emailLike = regexp.MustCompile(`^[^@\s]+@[^@\s]+$`)

最容易踩的坑

1. 以为 go.sum 是 lock 文件：版本由 go.mod 加 MVS 决定，删掉 go.sum 不改变任何版本，它只管完整性校验。

2. 用 replace 修库的依赖问题：replace 只在主模块生效，你的库被别人依赖时它被完全忽略，问题原样暴露给下游。

3. 发布 v2 忘了改 module 行加 /v2：下游 go get 拿到的还是 v1 系列，而且报错信息很难懂。

4. 直接 go get -u ./... 升级：一次把几十个依赖顶高，出问题无法定位。用 -u=patch 或逐个升。

5. 指望依赖管理器自动带来安全补丁：MVS 不会自动升版本，必须把 govulncheck 放进 CI。

6. 私有模块不配 GOPRIVATE：模块路径被发送到公共代理和校验和数据库，内部仓库名泄露，而且构建必然失败。

7. 建 utils 或 common 包：名字不表达职责，最终变成什么都往里塞的垃圾场，还成为循环导入的中心。

8. 用 models 加 controllers 按技术分层：一个功能的改动永远横跨三四个包，循环导入频发。

9. 遇到循环导入就新建一个 common 包：这是把问题推迟而不是解决，正确做法是把接口移到消费方或合并这两个包。

10. 接口定义在实现方且做成大接口：每个消费者被迫依赖全部方法，单测要造一堆假方法，接口加方法就全线编译失败。

11. 用 init() 建数据库连接或读配置：不能返回 error、测试躲不开、顺序依赖导入图、报错离根因很远。改成显式 NewApp。

12. 把 go.work 提交进仓库：它是本地多模块开发文件，进了仓库会让 CI 用到错误的本地路径。

13. 一上来就照搬标准布局建十几层目录：项目还没长出结构，目录先固化了错误假设。从扁平开始，出现三个以上同类文件再拆。

结论

依赖管理这边只需要记住三件事：MVS 取的是「被要求过的最大版本」而不是最新版本，所以构建可复现但安全补丁不会自动来；go.sum 是校验清单不是版本锁；replace 只在主模块生效，不要拿它修库。

包组织这边也只有三件事：按业务能力分包而不是按技术分层，默认把代码放 internal/ 让编译器替你守住边界，接口定义在消费方并保持小。这三条做到了，循环导入基本不会出现，改一个功能通常只动一个包，utils 包也就没有存在的理由了。
