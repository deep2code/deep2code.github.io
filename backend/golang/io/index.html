Go IO 包

🏷️ Go 语言

小接口，大组合

Go 的 io 包是接口设计的典范：每个接口只有一个方法，靠接口嵌入叠加能力。Reader/Writer/Closer/Seeker 四个单方法接口组合出 ReadCloser、ReadWriteCloser 所有变体。

这就是"组合优于继承"在 IO 层的体现——我写函数只声明要 Reader/Writer，谁传进来都行，不用关心底下是文件、网络还是 bytes.Buffer。

Read 黄金法则
先处理 n > 0 的数据，再判断 err。即使 err != nil（比如 io.EOF），本次读取也可能带回了有效字节——顺序反了就丢数据。

核心接口与组合

type Reader interface {
    Read(p []byte) (n int, err error)
}
type Writer interface {
    Write(p []byte) (n int, err error)
}
type Closer interface {
    Close() error
}

type ReadCloser interface {
    Reader
    Closer
}
type ReadWriteCloser interface {
    Reader
    Writer
    Closer
}

接口从单接口组合成双接口、三接口：

接口方法数组合典型用途
Reader1—一切可读数据源
Writer1—一切可写目标
ReadCloser2Reader + CloserHTTP Body，读完即关
ReadWriter2Reader + Writernet.Conn 双向流
ReadWriteCloser3Reader + Writer + Closer完整可读写流

Read 契约与正确读法

Read 的契约是"能读多少算多少"：返回 n < len(p) 且 err == nil 完全合法。调用方必须循环读，不能假设一次填满缓冲：

func readAll(r io.Reader) ([]byte, error) {
    buf := make([]byte, 0, 1024)
    tmp := make([]byte, 1024)
    for {
        n, err := r.Read(tmp)
        if n > 0 {
            buf = append(buf, tmp[:n]...) // 先处理数据
        }
        if err != nil {
            if err == io.EOF {
                return buf, nil // EOF 是正常结束
            }
            return buf, err
        }
    }
}

想确保读满指定字节数，直接用 io.ReadFull；搬粗活用 io.Copy，它自带 32KB 缓冲，还会探测 ReaderFrom/WriterTo 走零拷贝路径。

装饰器模式

io 包用装饰器层层包裹 Reader，每一层都是新的 io.Reader，可继续装饰。看一个三层嵌套怎么从原文件走到最终 Reader：

// 从 gzip 压缩的文件中最多读 1024 字节
f, _ := os.Open("data.gz")
defer f.Close()

r := io.LimitReader(
    gzip.NewReader(f),
    1024,
)
// r 仍是 io.Reader，可传给任何接受 Reader 的函数
装饰器作用
io.TeeReader(r, w)读 r 时镜像写一份到 w
io.MultiReader(r1, r2...)串联多个 Reader 依次读完
io.MultiWriter(w1, w2...)写入广播给所有 writer
io.SectionReader只读指定区间
io.NopCloser(r)给 Reader 套一个空 Close

2026 现代实践

旧 ioutil 写法已废弃，迁移路径固定：

  • ioutil.ReadAll → io.ReadAll
  • ioutil.ReadFile → os.ReadFile
  • ioutil.TempFile → os.CreateTemp
  • io/fs（1.16+）：虚拟文件系统，生产跑 os.DirFS/embed.FS，测试切 fstest.MapFS

errors.Join（1.20）把批量操作的多个错误攒成一个；log/slog（1.21）日志可接到任意 io.Writer，测试时直接断言 buffer 内容。

零拷贝

io.Copy 在检测到 *os.File → *net.TCPConn 时自动用 Linux sendfile，把磁盘数据直接在内核态送到 socket，省去用户态拷贝。

我测过参考值：传输 1GB 文件，传统 read+write 约 500ms，sendfile 约 250ms，直接省一半。

五个常见坑

  • 忘记 Close：文件描述符泄漏，永远 defer r.Close()。
  • 忽略 Read 返回的 n：先处理 n 再判 err。
  • 假设一次 Read 填满：必须循环或用 io.ReadFull。
  • Write 短写：Write 也可能写不满，用 io.WriteString 或循环。
  • ioutil.ReadAll 读大文件：内存爆炸，用流式或 bufio.Scanner。

FAQ

Q：io.Copy 会自己缓冲吗？
会，自带 32KB 缓冲，还会探测 ReaderFrom/WriterTo 走零拷贝。搬数据交给它，别手写循环。

Q：什么时候用 bufio？
逐字节、逐行这种小块频繁读写时。大块一次性传输用 io.Copy 即可，套 bufio 反而可能绕过零拷贝。

Q：io.EOF 是错误吗？
不是，是正常结束标记。Read 返回 EOF 表示读完了，别当错误处理。

我的习惯

我写 Go IO 的精髓就一句："小接口+装饰器组合"。写函数接收 Reader/Writer 而不关心具体实现，搬数据用 io.Copy，小块读写用 bufio，读完必 Close。

我自己反复提醒团队三条：先处理 n 再判 err、别用 ioutil、大文件走流式。抓住这三条，2026 年写 Go IO 基本不踩坑。
