Go 泛型

🏷️ Go 语言

泛型是什么时候进 Go 的

Go 1.18（2022 年 3 月）正式加了泛型，这是 Go 1.0 以来最大的语法变化。我当时写了个 CRUD 服务，以前每种类型要写一遍的 Map/Filter，现在一个函数搞定，确实爽。但它也不是银弹，用过头代码可读性反而下降。

一句话原则
泛型负责"算法和数据结构"（编译期知道怎么操作、不装箱），接口负责"行为多态"（不同类型响应同一组方法）。别用泛型硬套本该用接口的场景。

类型参数怎么写

func Map[T any, U any](s []T, f func(T) U) []U {
    result := make([]U, len(s))
    for i, v := range s {
        result[i] = f(v)
    }
    return result
}

// 调用：编译器自动推断类型参数，不用显式写
nums := []int{1, 2, 3}
strs := Map(nums, func(n int) string { return strconv.Itoa(n) })
  • 类型参数列表：[T any, U any]，每个参数有名字和约束。any 就是 interface{} 的别名。
  • 类型推断：大多数情况编译器能从参数推断；推断不出才显式写 MakeSlice[int](10)。
  • 泛型类型：type Stack[T any] struct{ items []T }，方法用接收者的类型参数。

约束速查表

约束写法含义允许类型典型用途
T any无限制任意类型容器、存取类算法
T comparable可做 == / !=可比较类型map key、去重
T cmp.Ordered可排序整数/浮点/字符串Max/Min、排序
~int底层类型是 intint 及命名类型兼容命名类型的数值算法
int | string类型联合int 或 string 本身精确限定几种类型
Stringer接口约束实现了 String() string要求类型自带某方法
~ 号别忘
~int 把 type MyInt int 也算进来；不带 ~ 只认 int 本身。写数值约束养成带 ~ 的习惯，不然命名类型调用方编不过。

底层：GCShape 字典传递

Go 泛型用的是"基于形状的字典传递"，介于 C++ 单态化和 Java 类型擦除之间。相同形状的类型共享同一份机器码，不同形状生成不同代码。

flowchart TD F[泛型函数 Max T cmp.Ordered] --> GC[GCShape 形状分类] GC --> I[int 版机器码] GC --> S[string 版机器码] GC --> FL[float 版机器码] style F fill:#00add8,stroke:#fff,color:#fff style GC fill:#00add8,stroke:#fff,color:#fff

好处：代码膨胀比 C++ 模板小（同形状共享），运行时比 Java 快（无装箱）。字典在编译期生成静态分配，运行时没反射开销。

该不该上泛型，按这棵决策树走：

flowchart TD S[要写对多种类型都一样的逻辑] --> A[要对值做运算比较取字段?] A -->|要 编译期可知| B[行为要随类型多态?] A -->|不要 只是存取| ANY[用 any 即可 不必泛型] B -->|否 只是数据结构| G[用泛型 T comparable 或 Ordered] B -->|是 要调不同方法| I[用接口 行为多态] style G fill:#00add8,stroke:#fff,color:#fff

1.22 到 1.27 演进

  • Go 1.22：改进类型推断，支持从方法调用推断。
  • Go 1.23：迭代器 iter.Seq[T] 和 range-over-func，泛型函数能返回迭代器。
  • Go 1.24：泛型类型别名转正（type List[T any] = []T）。
  • Go 1.26：类型参数支持自引用，递归约束直接写。
  • Go 1.27：泛型方法转正，方法声明也能带类型参数。

性能影响

对比项差异说明
vs interface{}快 20-50%无需装箱/拆箱
vs 手写具体类型慢 5-10%字典间接调用，小函数内联后差距消失
编译时间增加 10-30%1.21+ 比 1.18 快约 40%
代码膨胀同形状共享标准库泛型函数增加仅几十 KB

五个我踩过的坑

  • 方法不能有自己的类型参数：1.27 前是最大限制，需要时写成独立泛型函数。
  • ~ 近似元素误解：~int 不含 *int；type MyInt = int 别名就是 int 本身。
  • 泛型函数里和 nil 比较：约束是 any 时 v == nil 编译报错；用零值比较 var zero T; v == zero。
  • 过度泛型化：只处理一种类型的代码别为泛型而泛型，先写具体，重复了再泛型。
  • 递归类型推断失败：复杂嵌套泛型推断不出时显式指定类型参数。

FAQ

Q：泛型和接口怎么选？
要编译期类型安全 + 免装箱选泛型；要运行时在同一集合存不同类型选接口。两者可结合。

Q：Go 泛型比 C++ 模板差在哪？
以前不支持泛型方法、不支持特化、类型系统更保守。但换来更简单的编译模型和更可读的错误信息。

Q：老的 interface{} 代码要全改泛型吗？
不必。新代码能用泛型就用；老代码跑得好就先不动。泛型是工具不是迁移目标。

我的看法

站在 1.27 回看，泛型在类型系统上基本收官了。日常写泛型记住约束速查表（any/comparable/Ordered/~），用 GCShape 理解"同形状共享代码"，用决策树区分泛型和接口的职责。别为泛型而泛型，重复到第三次再上。
