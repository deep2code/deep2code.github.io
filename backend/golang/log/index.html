Go slog 日志

🏷️ Go 语言

2026 年 Go 日志选什么

Go 1.21 起标准库多了 log/slog 结构化日志模块，官方推荐用它替换老 log 包。2026 年的结论很明确：新项目闭眼选 slog。

logrus 生态还在但上游近半躺平，zap 在冲性能或要高度自定义输出时更常见。我最看重 slog 的一点：标准库自带——框架、中间件零额外依赖就能统一接到结构化日志上。

选型一句话
默认用 log/slog（标准库、零依赖、性能够用）；极致吞吐上 zap；链式 API 偏好选 zerolog；新项目不要再引入 logrus。

slog 基本用法

import "log/slog"

// 基本使用
slog.Info("user logged in", "user_id", 123, "ip", "10.0.0.1")

// JSON 格式
logger := slog.New(slog.NewJSONHandler(os.Stdout, nil))
logger.Info("request completed",
    "method", "GET", "path", "/api/users", "status", 200,
)

// 自定义 Handler：开 Debug 级别 + 带调用位置
handler := slog.NewTextHandler(os.Stdout, &slog.HandlerOptions{
    Level:     slog.LevelDebug,
    AddSource: true,
})
slog.SetDefault(slog.New(handler))

slog 的分层设计：Logger 负责前端 API（Info/Warn/Debug），Handler 负责后端输出格式（Text/JSON/自定义）。业务代码只依赖 Logger，输出格式可随时切换。

日志级别

LevelDebug-4调试细节、变量值关闭

生产环境最佳实践

线上日志从代码到 ELK 是一条流水线，每个环节都可能出问题：

flowchart LR APP[应用代码 slog.Info] --> HDL[Handler 输出 JSON] HDL --> STD[stdout] STD --> AGENT[Filebeat/Fluent Bit] AGENT --> ELK[Elasticsearch/Loki] ELK --> DASH[Grafana/Kibana 查询] style APP fill:#00add8,stroke:#fff,color:#fff

全局 Logger 用 JSON + 字段重命名，对接日志系统：

func initLogger() {
    handler := slog.NewJSONHandler(os.Stdout, &slog.HandlerOptions{
        Level:     slog.LevelInfo,
        AddSource: true,
        ReplaceAttr: func(groups []string, a slog.Attr) slog.Attr {
            if a.Key == slog.TimeKey { return slog.Attr{Key: "timestamp", Value: a.Value} }
            if a.Key == slog.LevelKey { return slog.Attr{Key: "severity", Value: a.Value} }
            return a
        },
    })
    slog.SetDefault(slog.New(handler))
}

请求级上下文日志，自动带 trace_id：

func middleware(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        logger := slog.Default().With("trace_id", generateID(), "method", r.Method)
        ctx := slog.NewContext(r.Context(), logger)
        next.ServeHTTP(w, r.WithContext(ctx))
    })
}

避免在热路径拼字符串，用 slog 惰性求值：

// 级别不启用时不执行
logger.Debug("处理订单", "order_id", orderID, "amount", amount)

// 更优：先查级别
if logger.Enabled(ctx, slog.LevelDebug) {
    logger.Debug("处理订单", "order_id", orderID, "detail", computeDetail())
}

四个常见坑

  • 敏感信息入日志：密码、Token 用 ReplaceAttr 脱敏。
  • 拼接用户输入导致日志注入：用结构化字段，别拼字符串。
  • 循环里打 Info 日志：高 QPS 打爆磁盘，用采样或聚合。
  • 级别不启用仍执行字符串拼接：用键值对写法或先 Enabled 判断。

FAQ

Q：老 logrus 项目要迁 slog 吗？
新项目直接 slog；老项目 logrus 还能跑就先不动，新模块用 slog，逐步过渡。别一次性全改。

Q：slog 和 zap 性能差多少？
基准上 zap Logger 模式零分配最快，slog JSON 约慢一倍。但绝大多数服务瓶颈不在日志，slog 够用；只有超高吞吐才上 zap。

Q：怎么把日志接到 ELK / Loki？
slog 用 JSONHandler 输出 JSON 到 stdout，由容器平台采集到日志系统。字段名用 ReplaceAttr 对齐 Elastic 规范。

我的结论

2026 年 Go 日志的答案我投给 slog：标准库、零依赖、Handler 接口可插拔。生产用 JSON + AddSource + trace_id 中间件，热路径先判级别，敏感字段脱敏。

我自己的经验：极致性能再考虑 zap，新项目别再碰 logrus。除非你的服务真在打日志上吃 CPU，否则 slog 那一倍差距根本无所谓。
