Go os/exec

🏷️ Go 语言

💡 你要写个高性能的后端服务，并发量很大，用 Python 扛不住。或者你想写个单文件部署的工具，不用装一堆依赖。

1.21 后调外部命令的正确姿势

Go 调用外部命令走标准库 os/exec。1.21 之后我用的标准组合是 exec.CommandContext + WaitDelay：用 context 控制超时，用 WaitDelay 兜底防止管道卡死。

底层是 Linux 的 fork+execve 或 Windows 的 CreateProcess，Go 帮你把这层封装好了。

安全铁律
参数必须切片化传给 exec.Command，禁止拼 sh -c 字符串——这是命令注入的命门。Go 默认不经 shell 执行，参数不会被 shell 解释，这本身就是安全设计。

编译发布：ldflags 注入构建信息

编译发布的精髓全在 -ldflags "-w -s -X"：-w 剥 DWARF 调试信息，-s 清符号表，瘦身 30%-50%；-X main.GitHash=... 在链接期把构建信息灌进变量。

想产出纯静态二进制加 CGO_ENABLED=0（用到 cgo 库时别碰，否则编译出来跑不起来）。

#!/bin/bash
set -x
GITVERSION=$(git describe --tags --always)
GITBRANCH=$(git symbolic-ref -q --short HEAD)
DATETIME=$(date "+%Y-%m-%d_%H:%M:%S")

golangci-lint run --timeout=1h
rm -rf local*

go build -o local -ldflags "-w -s \
  -X main.GitHash=${GITVERSION}-${GITBRANCH} \
  -X main.CompileTime=${DATETIME}" .
./local

执行命令：context 超时 + WaitDelay

一次 CommandContext 从创建到收尸，底层走 fork+execve 这条链：

flowchart TD C[CommandContext 创建] --> P[Start 找可执行文件] P --> F[fork 子进程] F --> E[execve 加载程序] E --> W[主进程等待] W --> T{context 超时或退出?} T -->|正常退出| R[Wait 收尸] T -->|超时| K[发 SIGKILL] K --> W2[WaitDelay 兜底等残留] W2 --> R style R fill:#00add8,stroke:#fff,color:#fff
超时场景不加 WaitDelay加 WaitDelay
子进程正常退出Wait 立即返回Wait 立即返回
子进程卡住不退出Wait 永远阻塞超时后强杀并返回
管道有残留数据Wait 阻塞在 EOFWaitDelay 内收完，超时强杀
 
ctx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
defer cancel()

cmd := exec.CommandContext(ctx, "git", "status")
cmd.WaitDelay = 2 * time.Second // 兜底：超时后强杀残留
output, err := cmd.CombinedOutput()
if err != nil {
    log.Printf("命令执行失败: %v, 输出: %s", err, output)
}

为什么光传 context 不够？子进程再派生的孙进程可能还攥着 stdout/stderr 管道，把 Wait() 卡到死。WaitDelay（Go 1.20 新增）专治这个僵局：取消后 Wait 超过 WaitDelay 没收尾，就先杀进程再返回。

flowchart TD C[exec.Command 命令与参数] --> L[PATH 查找可执行文件] L --> S[Start 底层 fork] S --> EX[execve 加载新程序] EX --> W[选择取输出方式] W -->|同步| WAIT[CombinedOutput 读管道并 Wait] W -->|流式| GO[goroutine 并发读 StdoutPipe] style WAIT fill:#00add8,stroke:#fff,color:#fff

三种等待姿势对比

方式API是否阻塞适用场景风险点
同步Output / CombinedOutput / Run阻塞到命令结束短命令、要完整输出大输出易管道死锁
流式StdoutPipe / StderrPipe不阻塞，边读边处理长时间/大输出需自起 goroutine 读
异步Start + go Wait立即返回后台任务必须有 goroutine 调 Wait

经验值：命令小且快 → CombinedOutput；输出大或长时间运行 → StdoutPipe 起 goroutine 读；后台跑 → Start 后务必 go cmd.Wait()，否则变僵尸。

进程树清理与防注入

Unix 上 CommandContext 取消默认只杀直接子进程，孙进程变孤儿。想端掉整个进程组，自己配 Setpgid：

cmd := exec.CommandContext(ctx, "./worker.sh")
if cmd.SysProcAttr == nil {
    cmd.SysProcAttr = &syscall.SysProcAttr{}
}
cmd.SysProcAttr.Setpgid = true // 子进程自成进程组

// ctx 取消时：负 PID = 整个进程组
_ = syscall.Kill(-cmd.Process.Pid, syscall.SIGKILL)

两条安全铁律：参数切片化禁止拼 sh -c；用户输入别原样塞进参数。Windows 注意 cmd.exe /C 引号转义差异，跨平台脚本优先用 Go 原生实现绕开 shell。

六个常见坑

  • 管道死锁：只捕获 stdout 而 stderr 大量输出，64KB 缓冲区写满子进程阻塞。要分别捕获就用两个 Pipe + 两个 goroutine。
  • 僵尸进程：不调 Wait()，子进程退出变 Z 状态占 PID。异步执行务必 go cmd.Wait()。
  • 命令路径生产找不到：开发机 PATH 有 node，容器里没有。用绝对路径或 exec.LookPath 启动时 fail-fast。
  • 环境变量继承泄漏：默认继承全部环境变量，可能把 API Key 带给子进程。显式设 Cmd.Env 白名单。
  • stdin 未关闭子进程傻等：不需要输入时不设 Stdin（默认 /dev/null）；要写输入，写完必须 Close。
  • 忽略退出码与 stderr：grep 没匹配返回 1 不是错误，要区分"执行失败"和"结果为负"，用 *exec.ExitError 取退出码。

FAQ

Q：exec.Command 会走 shell 吗？
默认不会，直接 execve。所以 exec.Command("ls", "*.txt") 不会展开通配符。需要 shell 功能才显式 sh -c，且绝不能拼不可信输入。

Q：为什么命令超时后进程还在跑？
只杀了直接子进程，孙进程成孤儿。配 Setpgid+负 PID Kill 杀整个进程组，或用 WaitDelay 兜底。

Q：CombinedOutput 和 Output 怎么选？
只要 stdout 用 Output；stdout/stderr 都要且量大，别用 Output（stderr 不读会死锁），用 Pipe+goroutine。混合输出不介意就 CombinedOutput。

我的配方

我调 Shell 的现代配方就一条：CommandContext 管超时、WaitDelay 管管道卡死、Setpgid 管进程树。

我自己反复叮嘱团队：参数切片化防注入、输出大用流式、异步必 Wait、环境变量白名单。做到这四条，就能避开 os/exec 90% 的坑。
