Go Context 的传播、取消与误用

🏷️ Go 语言

context 的四个职责，以及它不负责什么

context.Context 只有四个方法，对应四个职责：取消信号（Done()）、取消原因（Err()）、截止时间（Deadline()）、请求级值传递（Value()）。超时是截止时间的相对写法，本质是同一件事。

比列举方法更重要的是理解它的设计方向：context 是「向下传播取消」的机制，不是「向上返回结果」的通道。信号只能从父流向子，子 context 取消不影响父。想往上传结果就用返回值或 channel，别试图塞进 ctx。

职责对应方法实现载体常见误用
取消信号Done() 返回只读 channelcancelCtx 里的 done，取消时 close拿到 ctx 却从不 select 它，以为运行时会自动中断代码
取消原因Err()取消时写入 Canceled 或 DeadlineExceeded用 == 比较而不是 errors.Is，包装过就判不出来
截止时间Deadline()timerCtx 内嵌 cancelCtx 加一个 time.Timer子调用重新设一个比父剩余时间更长的超时，等于没设

四种派生函数的区别落在「谁触发取消」和「不调 cancel 会漏什么」上：

派生函数取消触发者不调 cancel 的后果继承父 deadline
WithCancel只有显式调 cancel，或父被取消子节点一直挂在父的 children 集合里，父存活多久就泄漏多久是
WithTimeout到时间自动，或显式 cancel，或父被取消timer 要等到超时才释放，高 QPS 下时间堆里堆积大量 timer是，且取两者更早的那个
WithDeadline同上，但用绝对时间同上是；若父 deadline 更早则父生效，此时等价于 WithCancel
WithValue不可取消，取消完全靠父链无（不注册 children、不建 timer）是
WithoutCancel（1.21+）切断父的取消传播，保留 Value无否，deadline 也一并丢弃

取消是协作式的：这是最核心的认知

把一个 ctx 传进函数，不会让这个函数自动具备超时能力。运行时没有任何机制去强制中断一段正在跑的代码。取消生效只有两条路径：被调用方自己 select ctx.Done()，或者把 ctx 继续往下传给一个真正支持它的库（库内部最终还是走第一条路）。

所以「我传了 ctx 但超时没生效」几乎总是因为链条中间断了。下面这张时序图画的是一次正常工作的取消传播：

任意一层把 ctx 换成 context.Background()，图里从那一层往下的虚线全部消失。这是我见过最高频的 context 错误，而且它不会报错、不会崩，只是在压力下让请求悬挂、连接池耗尽。

❌
「传了 ctx 就有超时」是错觉

把 ctx 传给一个不检查它的函数，等于传了个用不上的参数。典型例子：自己写的 for 循环批处理、纯 CPU 计算、调用某些只把 ctx 放在签名里但内部没用的第三方库、以及 os/exec 里用 exec.Command 而不是 exec.CommandContext。判断一个库是否真支持，看它内部有没有 select ctx.Done() 或者把 ctx 往下传给标准库的带 ctx 方法。

超时预算的向下传递

另一个高频错误是每一层都按自己的想法设超时。入口设 1s，service 层调 DB 时设 3s——后者形同虚设，因为父 context 800ms 后就取消了；但更糟的情况是入口没设、每层各设 3s，于是一次请求最长能拖到 3s 乘以串行层数。

正确的模型是超时预算：入口分配总预算，每层往下时取「父剩余时间」和「本层期望上限」的较小值，并预留一点给自己做收尾（写响应、记日志）。

// budget.go：向下传递超时预算的封装，直接可用

// WithBudget 返回一个超时不超过 want 的子 context。
// 如果父 ctx 剩余时间已经少于 want，就沿用父的 deadline，不做无意义的放大。
// reserve 是留给本层收尾的时间，避免下游用满预算后自己来不及写响应。
func WithBudget(ctx context.Context, want, reserve time.Duration) (context.Context, context.CancelFunc) {
    dl, ok := ctx.Deadline()
    if !ok {
        // 父没有 deadline（通常是后台任务或入口漏设），按 want 兜底
        return context.WithTimeout(ctx, want)
    }
    remain := time.Until(dl) - reserve
    if remain <= 0 {
        // 预算已经耗尽，不必再发起下游调用，直接返回一个已取消的 ctx
        c, cancel := context.WithCancel(ctx)
        cancel()
        return c, cancel
    }
    if remain < want {
        want = remain // 取较小值：绝不放大父的预算
    }
    return context.WithTimeout(ctx, want)
}

// 调用侧：每一层都这么写，超时就一定是收敛的
func (s *Service) GetProfile(ctx context.Context, uid int64) (*Profile, error) {
    // 给 DB 最多 300ms，并给本层留 20ms 做序列化与日志
    dbCtx, cancel := WithBudget(ctx, 300*time.Millisecond, 20*time.Millisecond)
    defer cancel() // 必须 defer：否则 timer 要等到 300ms 才释放

    row := s.db.QueryRowContext(dbCtx, "SELECT name, age FROM users WHERE id = ?", uid)
    var p Profile
    if err := row.Scan(&p.Name, &p.Age); err != nil {
        // 区分「是我超时了」还是「上游取消了」，两者的告警级别不同
        if errors.Is(err, context.DeadlineExceeded) {
            return nil, fmt.Errorf("db timeout after budget: %w", err)
        }
        if errors.Is(err, context.Canceled) {
            return nil, fmt.Errorf("upstream gone: %w", err) // 客户端断开，不该算服务端错误
        }
        return nil, err
    }
    return &p, nil
}

注意错误判定要用 errors.Is：DeadlineExceeded 和 Canceled 经常被下游库包装过一层，err == context.Canceled 会漏判。区分这两者在监控上很重要——Canceled 多数是客户端主动断开（用户刷新页面、上游超时重试），不该计入服务端错误率；DeadlineExceeded 才是自己慢了。

WithValue：该放什么，不该放什么

WithValue 的定位很窄：只放请求级的横切元数据——traceID、请求 ID、用户身份、租户标识、语言偏好。判断标准是「这个值是否需要穿过不关心它的中间层」，traceID 要穿过整条调用链才有意义，而业务参数不需要。

不该放的是可选参数与依赖。把 pageSize、数据库句柄、logger 实例塞进 ctx，会带来三个后果：函数签名不再说明它需要什么、类型不安全（取出来要断言且可能是 nil）、编译器和 IDE 完全无法校验。重构时最痛苦的代码往往就是这种——你不知道删掉某个 ctx key 会让哪里在运行时崩。

// ctxkey.go：ctx value 的标准封装模式，每个包自己维护一份

// key 必须是包内私有类型，避免跨包碰撞。
// 用空结构体做 key 零内存开销，且不可能被外部构造出相同的值。
type traceIDKey struct{}
type userKey struct{}

// setter 与 getter 成对导出，外部永远拿不到 key 本身。
func WithTraceID(ctx context.Context, id string) context.Context {
    return context.WithValue(ctx, traceIDKey{}, id)
}

// getter 返回零值而不是 panic：中间件没跑到的路径（比如内部任务）也能安全调用。
func TraceID(ctx context.Context) string {
    v, _ := ctx.Value(traceIDKey{}).(string) // 类型断言用双返回值，别用单返回值
    return v
}

func WithUser(ctx context.Context, u *User) context.Context {
    return context.WithValue(ctx, userKey{}, u)
}

// 身份这类安全相关的值，getter 要明确告知「有没有」，不要让调用方拿零值当匿名用户
func UserFrom(ctx context.Context) (*User, bool) {
    u, ok := ctx.Value(userKey{}).(*User)
    return u, ok && u != nil
}

用 string 当 key 是老代码里的常见写法，问题在于两个包都用 "userID" 时会互相覆盖，而且任何人都能从外部读写你的值。用私有空结构体类型既避免碰撞也做到了封装。

数据库与 HTTP 客户端的真实行为

「ctx 取消了资源就释放了」是个过于乐观的假设。取消的实际效果依赖具体库的实现，而这直接影响你的容量规划。

库 / 场景ctx 取消后发生什么要注意的副作用
database/sql 的 QueryContext连接被标记并尝试中断查询（MySQL 驱动会另开连接发 KILL QUERY）数据库侧可能仍在跑，一条慢 SQL 取消后服务端立即返回，但 DB 的 CPU 还在被它占着。取消不等于释放数据库资源
database/sql 的事务ctx 取消会自动回滚事务回滚也要占连接和时间；长事务里传短超时的 ctx 会让事务半途而废，业务上要能接受
http.Clienttransport 直接关闭这条 TCP 连接连接无法放回连接池复用。所以「频繁超时」会让长连接池持续失效、不停重新握手，TLS 场景下额外开销很大
net.Conn 裸连接不感知 ctx，需要自己用 SetDeadlineSetDeadline 是绝对时间且一次性，读写循环里每次都要重设
os/execCommandContext 会向子进程发 SIGKILL默认是 KILL 不是 TERM，子进程没有清理机会；1.20+ 可以用 Cmd.Cancel 字段自定义
Redis 客户端（go-redis）取消即关闭连接或返回错误和 HTTP 一样有连接池失效问题；Pipeline 中途取消会让部分命令已发出
gRPC取消映射为 CANCELLED 状态码，通过 HTTP/2 RST_STREAM 通知对端唯一能把取消真正传到远端进程的常见协议；服务端能从自己的 ctx 感知到调用方放弃了
⚠️
频繁超时会让连接池失效

这是个容易被忽视的负反馈：下游变慢导致超时增多，每次超时都关闭一条连接，连接池被掏空后每个请求都要重新建连（加上 TLS 握手），这又进一步拉高延迟、造成更多超时。所以给下游设超时的同时，一定要配熔断或限流，不要让系统在这个环上转。连接池本身的参数调优详见站内连接池与 ORM 篇。

服务端的 ctx：r.Context、BaseContext 与优雅关闭

r.Context() 的生命周期绑在这次请求上，客户端断开连接时它会被取消。这带来一个有用的能力：长耗时接口可以据此提前放弃计算，不为已经走掉的客户端做无用功。

但有个边界要注意：响应已经写了一部分时，取消不能简单地 return。HTTP 状态码和已写入的头部无法撤回，流式接口（SSE、chunked、大文件下载）中途放弃只会让客户端拿到截断的响应。这种情况下要么在写第一个字节之前完成所有可能失败的工作，要么用协议层面的手段（SSE 发一个 error 事件、chunked 用尾部标记）告知客户端数据不完整。

flowchart TB R["收到 ctx.Done"] --> Q1{"响应是否已开始写"} Q1 -->|"还没写"| CLEAN["直接返回错误状态码
504 或 499 都可以"] Q1 -->|"已写了一部分"| Q2{"是不是流式响应"} Q2 -->|"是 SSE 或 chunked"| SIG["发一个协议内的错误事件
让客户端知道数据不完整"] Q2 -->|"否 普通响应"| LOG["只能记日志并中断连接
客户端会看到截断的 body"] R --> Q3{"是否有需要完成的副作用"} Q3 -->|"有 写审计日志或发消息"| WOC["用 context.WithoutCancel 派生
再套一个独立超时"] Q3 -->|"没有"| END["释放资源直接退出"]

http.Server 侧还有两个配置点：BaseContext 给所有连接指定一个共同的父 context（常用来注入全局的关闭信号或服务级元数据），ConnContext 能在每条连接建立时往 ctx 里加东西（比如把 net.Conn 本身放进去以便后续拿对端地址）。

// 优雅关闭里 ctx 的三种不同用法，注意它们的父不一样
func main() {
    // 1. 进程级 ctx：收到 SIGTERM 时取消，用来通知所有后台任务停工
    rootCtx, stop := signal.NotifyContext(context.Background(), syscall.SIGINT, syscall.SIGTERM)
    defer stop()

    srv := &http.Server{
        Addr: ":8080",
        // BaseContext 让每个请求的 ctx 都挂在 rootCtx 下
        // 注意：这意味着 SIGTERM 会立刻取消所有正在处理的请求，
        // 想让存量请求跑完就不要这么挂，改用下面 Shutdown 的宽限期
        BaseContext: func(net.Listener) context.Context { return context.Background() },
        Handler:     mux,
    }

    go func() {
        if err := srv.ListenAndServe(); err != nil && !errors.Is(err, http.ErrServerClosed) {
            log.Fatalf("listen: %v", err)
        }
    }()

    <-rootCtx.Done() // 等信号
    log.Println("shutting down")

    // 2. 关闭宽限期用独立的 ctx：它的父必须是 Background，
    //    如果用 rootCtx 派生，此时它已经被取消，Shutdown 会立即强制断连
    shutCtx, cancel := context.WithTimeout(context.Background(), 20*time.Second)
    defer cancel()
    if err := srv.Shutdown(shutCtx); err != nil {
        log.Printf("graceful shutdown timeout, forcing close: %v", err)
        _ = srv.Close()
    }

    // 3. 关闭后的清理（flush 指标、关消息队列消费者）同样要新的 ctx
    flushCtx, cancel2 := context.WithTimeout(context.Background(), 5*time.Second)
    defer cancel2()
    metrics.Flush(flushCtx)
}

第 2 点是优雅关闭最常见的 bug：用已经取消的信号 ctx 去派生 Shutdown 的 ctx，结果 Shutdown 一调用就立即返回，所有存量请求被直接掐断，表现为发版时固定出现一批 502。

错误写法为什么错症状正确做法
把 ctx 存进结构体字段ctx 的生命周期是「一次调用」，结构体通常跨调用复用第二次调用用的还是第一次那个已取消的 ctx，或者并发调用互相干扰ctx 永远作为第一个函数参数传入

最容易踩的坑

❌
避坑清单
  • 结构体里存 ctx：ctx 的粒度是一次调用，存进长生命周期对象后必然用到过期的那个。唯一的例外是显式表示「这个对象只服务于一次请求」的短命结构体。
  • 忘记 defer cancel()：WithTimeout 和 WithCancel 不 cancel 就会泄漏 timer 和 children 引用，直到超时或父被取消。go vet 的 lostcancel 检查器能发现大部分。
  • 链条中途换 context.Background()：最高频的 context 错误，而且完全静默。用 contextcheck 和 noctx 两个 linter 在 CI 里拦。
  • 以为传了 ctx 就自动有超时：取消是协作式的。自己写的循环、纯计算、以及签名里有 ctx 但内部不用的库，都不会因为传了 ctx 而变得可中断。
  • 子调用设比父更长的超时：父 500ms 剩余时子设 3s 完全无效。用取较小值的封装，每层预留收尾时间。
  • 用 WithValue 传依赖和可选参数：函数签名失去表达力，类型不安全，重构只能靠线上崩溃发现。
  • ctx value 的 key 用 string 字面量：跨包碰撞且毫无封装。用包内私有的空结构体类型。
  • 清理与补偿逻辑用已取消的 ctx：请求失败后要写审计、发补偿消息，用原 ctx 会立即失败。用 WithoutCancel 再加独立超时，注意它会同时丢掉 deadline。
  • 优雅关闭时用信号 ctx 派生 Shutdown 的 ctx：信号 ctx 此刻已取消，Shutdown 立即强制断连，发版时固定产生一批 502。必须从 Background 派生。
  • 以为 DB 查询取消就等于 DB 不干活了：驱动只是尝试中断，数据库侧那条慢 SQL 可能还在跑。真正的保护是在 DB 侧配 max_execution_time 之类的语句级超时。
  • 忽视频繁超时对连接池的破坏：http.Client 超时会关连接、无法复用，超时增多会让连接池持续失效并加剧延迟。给下游设超时的同时要配熔断。
  • 把 Canceled 计入服务端错误率：多数 Canceled 是客户端主动断开，混进 5xx 指标会造成告警噪音，也会掩盖真正的 DeadlineExceeded。
