Go 运行时模型：GMP 调度、内存分配与 GC

🏷️ Go

Docker、Kubernetes、etcd、Prometheus、Istio 都是 Go 写的，这件事常被归因为「Go 并发好写」。但真正让 Go 在这个位置站住的不是 go 关键字，而是运行时替你干掉的那几件脏活：把 M:N 调度做进用户态、把 epoll 藏在同步 API 后面、把内存分配拆成每个 P 一份的无锁缓存、把 GC 停顿压到几十微秒。这篇把这四件事拆开讲，重点放在它们各自在什么条件下会失效——因为线上出问题的地方从来不是正常路径。

GMP：三个字母背后的队列结构

Go 的调度器是 M:N 模型，三个核心对象分别是 G、M、P。G 是 goroutine，一个可被调度的执行单元，带自己的栈和寄存器现场。M 是 machine，一个真实的 OS 线程，代码最终在它上面跑。P 是 processor，代表「执行 Go 代码所需的资源与上下文」，数量由 GOMAXPROCS 决定，默认等于机器可见的逻辑核数。

关键点在于：M 想执行 Go 代码，必须先持有一个 P。P 的数量因此成为并行度的硬上限——你开一百万个 G，同一时刻真正在跑的也只有 GOMAXPROCS 个。每个 P 挂着一个容量 256 的本地运行队列，外加一个优先级最高的 runnext 槽（刚被唤醒的 G 会插到这里，少一次排队延迟）；本地放不下的 G 溢出到全局队列。

两个机制决定了这套结构不会退化成「一核有难八核围观」：

work stealing：某个 P 的本地队列空了，它不会闲着，而是随机挑另一个 P 偷走它队列里的一半 G。偷之前会先看全局队列和 netpoller，都没有才去偷。这让负载在 P 之间自动均衡，代价是偷取时的原子操作开销和缓存局部性损失。

handoff：M 陷入系统调用（read 一个普通文件、调一次 cgo 函数）时会阻塞在内核里。此时 sysmon 监控线程发现这个 M 已经超过约 20 微秒没回来，就把它身上的 P 摘下来交给另一个 M（有空闲 M 就复用，没有就新建）。这就是为什么一次阻塞的 cgo 调用不会卡住整个程序。但要记住它的代价：handoff 会创建 OS 线程，大量并发的阻塞 cgo 调用会让线程数暴涨，Go 默认线程上限是 10000，撞到就直接崩。

goroutine 为什么便宜：量级对照

「goroutine 比线程轻」是句正确但没信息量的话，真正该记住的是量级差多少、差在哪。

需要主动纠正一个流传很广的说法：goroutine 栈不是「无限增长」也不是「只增不减」。它的增长方式是检测到栈空间不足时分配两倍大的新栈并整体拷贝，GC 期间也会做栈收缩，把用不到的空间还回去。所以一个曾经递归很深的 goroutine，空闲下来后内存会降回去——但拷贝本身有成本，深递归热路径会反复触发栈增长。

抢占式调度的演进：1.14 是分界线

Go 1.14 之前的抢占是协作式的：编译器只在函数调用、channel 操作、内存分配等位置插入抢占检查点，运行时想抢占某个 G，只能设一个标志位，等它自己走到检查点。后果是——一段没有函数调用的纯计算循环可以永久占着 P 不放：

// Go 1.13 及之前：这段代码在 GOMAXPROCS=1 时会永久卡死
// 因为循环体内没有任何抢占检查点，GC 需要的 STW 永远等不到这个 P 停下
func main() {
    runtime.GOMAXPROCS(1)
    go func() {
        for {
            // 空循环：无函数调用、无内存分配、无 channel 操作
        }
    }()
    time.Sleep(time.Millisecond)
    runtime.GC() // 1.14 之前在这里挂死
    fmt.Println("done")
}

1.14 引入基于信号的异步抢占：sysmon 发现某个 G 已经连续运行超过 10 毫秒，就给它所在的 M 发一个 SIGURG；信号处理函数保存现场，插入一次 asyncPreempt 调用，强制进入调度器。所以上面那段代码在 1.14 之后能正常跑完。

💡
这个改动的副作用

异步抢占用的是 SIGURG，如果程序里有大量 cgo 代码，或者用了对信号敏感的 C 库（例如某些老实现在 EINTR 上不重试），可能会看到诡异的「系统调用被中断」错误。排查时用 GODEBUG=asyncpreemptoff=1 临时关掉异步抢占做对照实验，现象消失就说明是信号打断导致的。但这个参数不要带上生产，它会把 1.14 之前的死循环问题带回来。

netpoller：写起来同步，跑起来异步

这是 Go 做网络服务最大的结构性优势，也是最容易被讲漏的一环。在 C 或 Java NIO 里，想要高并发就得写事件循环和回调，业务逻辑被拆成碎片。Go 的做法是把 epoll 封进运行时：你写 conn.Read(buf)，看起来是同步阻塞调用，实际上所有连接的 fd 都是非阻塞模式并注册在一个 epoll 实例上，阻塞的是 goroutine，不是线程。

sequenceDiagram participant G as 业务 goroutine participant RT as 运行时调度器 participant NP as netpoller participant K as 内核 epoll G->>RT: conn.Read 发现 fd 暂无数据 内核返回 EAGAIN RT->>K: 把 fd 注册进 epoll 关注可读事件 RT->>G: gopark 挂起 G 状态置为 Gwaiting RT->>RT: 同一个 M 立刻取本地队列的下一个 G 继续执行 K-->>NP: 数据到达 epoll_wait 返回该 fd NP->>RT: netpollready 交回等待这个 fd 的 G 列表 RT->>G: goready 置为 Grunnable 放回运行队列 G->>G: 从原来的 Read 调用处继续 对业务代码完全透明 Note over G,K: 一万个连接对应一万个 goroutine 但只需要 GOMAXPROCS 个线程

这个设计的边界很明确：只有网络 fd 和 unix socket 走 netpoller，普通磁盘文件 IO 不走。os.File 的读写是真实的阻塞系统调用，会触发 handoff 并可能创建新线程。所以大量并发读小文件的程序，线程数会比你预期的高得多；真要做高并发磁盘 IO，得自己上工作池限制并发，或者用 io_uring 这类第三方封装。

因为 mcache 绑定 P 而 P 在执行 Go 代码时被 M 独占，小对象分配路径上没有任何锁，这也是 Go 敢在热路径上随手 make 的底气。但 size class 向上取整会带来内部碎片：分配 33 字节实际占 48 字节，浪费 45%。批量分配定长结构体时，把字段按大小重排（大字段在前）能减少 padding，有时能直接落到更小的 size class。

GC：停顿很短，但代价不在停顿上

Go 用的是非分代、非压缩、并发的三色标记清除。三色是抽象描述：白色为未访问（回收候选），灰色为已发现但引用还没扫完，黑色为自身与引用都扫完。标记从根对象（全局变量、各 goroutine 栈、寄存器）出发，把灰色队列不断推进到空。

难点在于标记与业务代码并发跑，业务代码随时可能改指针。Go 用混合写屏障（1.8 引入，把删除屏障与插入屏障组合起来）保证不漏标：被覆盖的旧指针和新写入的指针都会被着色。代价是写屏障开启期间，每次指针写入都多几条指令。

stateDiagram-v2 [*] --> Off Off : GC 关闭 只做分配 无写屏障开销 Off --> SetupMark : 堆达到 GOGC 目标或 GOMEMLIMIT 产生压力 SetupMark : 标记准备 第一次 STW 通常几十微秒 SetupMark --> Marking : 开启写屏障 扫描根对象 Marking : 并发标记 后台 worker 约占四分之一 CPU Marking --> MarkTerm : 灰色队列清空 MarkTerm : 标记终止 第二次 STW 收尾统计 MarkTerm --> Sweeping : 关闭写屏障 计算下一轮触发阈值 Sweeping : 并发清扫 span 惰性回收 分配时顺手清 Sweeping --> Off : 全部 span 清扫完毕 note right of Marking 后台标记 worker 固定拿走约四分之一的 P 时间 分配速率过高时业务 goroutine 会被罚去做 mark assist 这段时间算在业务调用耗时里 却完全不计入停顿指标 所以延迟毛刺和 GC 停顿指标经常是两回事 end note

这是本节最该记住的结论：Go 的 STW 已经压到几十微秒量级，你在监控上看到的 GC 停顿几乎永远是健康的。真正吃延迟的是两处并发成本——后台标记 worker 固定占用约 25% 的 P 时间，以及 mark assist：当某个 goroutine 的分配速率超过标记推进速度，运行时会罚它去帮忙标记一批对象，这部分耗时直接体现在业务函数里。症状就是「P99 有毛刺，但 GC 停顿指标正常，CPU 也没打满」。

解法不是调 GOGC，而是降低分配速率——回到上一节的逃逸分析。把 GOGC 调大只是让 GC 跑得更少但每轮标记的对象更多、堆更大，毛刺变稀疏而单次更重。

容器环境的两个必配项

Go 服务上容器最高频的两个事故，都来自运行时对 cgroup 无感知。

第一个是 GOMAXPROCS 读宿主机核数。宿主机 64 核、Pod 的 CPU limit 只有 2 核时，Go 建 64 个 P，于是有 64 条执行流去争 2 核的时间片。CFS 在每个 100ms 周期内发完配额就把整个 cgroup 冻结到下一周期，表现为周期性延迟尖刺加上很高的限流计数。K8s 侧的 CFS 限流与 QoS 细节详见站内 Kubernetes 篇，这里只给 Go 侧的修法。

第二个是不设 GOMEMLIMIT 就没有内存刹车。GOGC 是相对值，它只关心「存活堆翻倍了没」，完全不知道容器 limit 在哪。流量尖峰下存活堆涨一倍，堆再翻倍才触发 GC，等 GC 跑完时 RSS 已经超过 limit 被内核 kill 了——和 JVM 不设最大堆是一个道理。

package main

import (
    "os"
    "runtime"
    "runtime/debug"

    // 读 cgroup 的 cpu.max 或 cpu.cfs_quota_us 自动设置 GOMAXPROCS
    // 目前最省事的做法：import 进来就生效，不用写任何调用
    _ "go.uber.org/automaxprocs"
)

func init() {
    // GOMEMLIMIT 是软上限：堆逼近它时 GC 会持续加压，而不是报错退出
    // 取容器 memory limit 的 80%，留出 goroutine 栈、mmap、cgo 与运行时元数据的开销
    // 生产上更推荐用 Downward API 注入环境变量，这里是代码内兜底
    if os.Getenv("GOMEMLIMIT") == "" {
        const containerLimit = 2 << 30 // 2GiB，必须与 Deployment 的 limits.memory 对齐
        debug.SetMemoryLimit(containerLimit * 80 / 100)
    }

    // 启动时把实际生效的值打出来，这行日志能省掉未来半天的排查
    println("GOMAXPROCS:", runtime.GOMAXPROCS(0),
        "NumCPU:", runtime.NumCPU(),
        "MemLimit:", debug.SetMemoryLimit(-1)) // 传 -1 表示只读不改
}
# 不想引依赖时，用 Downward API 把 limit 喂给运行时
# GOMAXPROCS 必须是整数，limits.cpu 写 1500m 时会自动向上取整为 2
env:
  - name: GOMAXPROCS
    valueFrom:
      resourceFieldRef:
        resource: limits.cpu
  - name: GOMEMLIMIT_MIB          # 注意：拿到的是纯数字，下面启动脚本要拼上单位
    valueFrom:
      resourceFieldRef:
        resource: limits.memory
        divisor: 1Mi
command: ["/bin/sh", "-c"]
args: ["export GOMEMLIMIT=$(( GOMEMLIMIT_MIB * 80 / 100 ))MiB && exec /app/server"]
resources:
  limits:
    cpu: "2"
    memory: 2Gi
  requests:
    cpu: "1"
    memory: 2Gi                   # 内存 request 与 limit 设成相等，避免被优先驱逐
⚠️
GOMEMLIMIT 用 Downward API 注入时的坑

divisor: 1Mi 拿到的是纯数字 2048，而 GOMEMLIMIT 需要带单位（2048MiB）或者是纯字节数。直接把 2048 赋给它会被理解成 2048 字节，进程一启动就陷入 GC 死亡螺旋：CPU 打满、业务完全跑不动、看日志还以为是死锁。所以要么像上面那样在启动脚本里拼上单位，要么改用代码里 debug.SetMemoryLimit 的方式。另外一定按 limit 的 80% 设而不是 100%，因为它只约束堆，goroutine 栈和运行时元数据不在其中。

Profile回答什么问题默认是否开启判读要点
profile（CPU）CPU 时间花在哪些函数上按需采样，默认 100Hz看累计值而不是自身值找热路径；执行时间远短于采样间隔的函数可能采不到，必要时提高采样率
heap谁在占内存、谁在疯狂分配开启，平均每 512KB 采一次inuse_space 查泄漏与常驻占用，alloc_space 查分配速率也就是 GC 压力来源，两者结论完全不同
goroutine有多少 goroutine、分别卡在哪开启，瞬时快照用 debug=2 拿完整栈和等待时长；同一个栈出现上万次就是泄漏点
blockgoroutine 在同步原语上等了多久默认关，需调 SetBlockProfileRate包含 channel 等待、WaitGroup.Wait、锁等待；采样率设 1 会明显拖慢程序，线上用较大值
mutex哪把锁的持有导致他人等待最久默认关，需调 SetMutexProfileFraction只统计发生争用的锁；配合 block profile 才能区分「等锁」与「等 channel」
trace时间轴上每个 G 何时被调度、被谁打断按需采集唯一能看到调度延迟、GC 各阶段占用、syscall 阻塞的工具，但数据量大，采 3 至 5 秒足够
 
# 前提：服务里 import _ "net/http/pprof" 并在内部端口起一个 http server
# 安全提醒：这个端口绝不能暴露到公网，heap profile 能导出完整堆内存

# 1. CPU：采 30 秒，-http 直接开火焰图页面
go tool pprof -http=:8080 'http://127.0.0.1:6060/debug/pprof/profile?seconds=30'

# 2. 内存：常驻与累计两个维度都要看，前者查泄漏后者查 GC 压力
go tool pprof -http=:8081 http://127.0.0.1:6060/debug/pprof/heap
go tool pprof -sample_index=alloc_space http://127.0.0.1:6060/debug/pprof/heap

# 3. goroutine 泄漏：debug=2 是纯文本完整栈，直接统计就能找到泄漏点
curl -s 'http://127.0.0.1:6060/debug/pprof/goroutine?debug=2' > g.txt
grep -c '^goroutine ' g.txt

# 4. 调度与 GC 细节：trace 是唯一能回答「G 从就绪到被执行等了多久」的工具
curl -s 'http://127.0.0.1:6060/debug/pprof/trace?seconds=5' > trace.out
go tool trace trace.out    # 重点看 Scheduler latency profile 与 GC 区间

# 5. GC 实况：写在启动命令里，每轮 GC 输出一行
GODEBUG=gctrace=1 ./myapp 2>&1 | grep '^gc '
# gc 42 @18.331s 3%: 0.019+4.2+0.008 ms clock, 0.15+1.1/3.9/0+0.06 ms cpu, 92->95->48 MB, 97 MB goal, 8 P
#    轮次 运行时长 GC累计占CPU  两次STW与并发标记耗时    assist/后台/空闲标记CPU   起始-结束-存活   下轮目标 P数

# 6. 两个默认关闭的 profile：采样前先在代码里打开，采完记得关
curl -s 'http://127.0.0.1:6060/debug/pprof/mutex?debug=1' | head -30

gctrace 那行里 0.15+1.1/3.9/0+0.06 ms cpu 中间三段分别是 mark assist、后台标记、空闲标记 的 CPU 时间。第一段占比高就说明业务 goroutine 被拉去帮忙标记了，对应上一节说的延迟毛刺。92->95->48 MB 三个数是 GC 开始堆大小、结束堆大小、存活堆大小，只有存活堆持续上涨才是真泄漏。

最容易踩的坑

❌
避坑清单
  • 容器里不设 GOMAXPROCS：宿主 64 核、limit 2 核时运行时建 64 个 P，CFS 周期性限流造成规律性 P99 尖刺。引 automaxprocs 或用 Downward API 注入。
  • 容器里不设 GOMEMLIMIT：GOGC 是相对值，不知道 limit 在哪，尖峰流量下堆翻倍还没触发 GC 就被 OOMKilled。按 limit 的 80% 设。
  • GOMEMLIMIT 注入成纯数字：Downward API 配 divisor: 1Mi 得到 2048，被解读成 2048 字节，进程启动即陷入 GC 死亡螺旋。必须带单位。
  • 把 GOGC 调大当成优化：GC 次数确实少了，但每轮标记对象更多、堆更大，延迟毛刺只是变稀疏而单次更重。该做的是减少分配。
  • 热路径用 fmt.Sprintf：...any 参数强制装箱逃逸，QPS 上万的接口里这一行就能贡献可观的分配量。换 strconv，日志前先判 level。
  • 以为 STW 短就不用管内存分配：真正吃延迟的是 mark assist 和后台标记占的约 25% CPU，它们完全不体现在 GC 停顿指标上。
  • 把 goroutine 数量当并发度指标却不设上限：无界 fan-out 会同时打爆下游连接池和自己的内存，并发控制写法见站内 Go 并发原语篇。
  • 以为磁盘 IO 也走 netpoller：只有网络 fd 走，文件读写是真阻塞系统调用，会触发 handoff 创建线程，并发读文件会让线程数悄悄涨到几百。
  • 拿 cgo 当常规手段：每次调用要切栈、无法被抢占、阻塞时触发 handoff 建线程、profile 里看不到 C 侧栈，还让交叉编译与静态链接变复杂。
  • 看到 RSS 不降就断定泄漏：Go 归还内存给操作系统是惰性的，先用 heap profile 看 inuse_space 和 gctrace 里的存活堆是否真在涨，再下结论。
  • 用 CPU profile 排查内存问题：CPU profile 里 runtime.mallocgc 靠前只说明分配多，找不出「是谁分配的」，那是 heap profile 的 alloc_space 才能回答的。
  • 把 pprof 端口暴露在公网：/debug/pprof/heap 能导出完整堆内存，里面可能有密钥和用户数据，必须绑内网地址或加鉴权中间件。
