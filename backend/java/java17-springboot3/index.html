Java 17+ 与 Spring Boot 3

🏷️ Java 总览

为什么我把这篇放在第一篇

很多人学 Java 还停留在 Java 8 的心智模型上：匿名内部类写回调、POJO 满篇 getter/setter、线程池手动配。这套写法在 2026 年写新代码，说难听点是在给自己埋雷。这篇我把 Java 17 到 21 这几个 LTS 之间真正写起来爽的特性挑出来，顺便把 Spring Boot 3.x 的变化和升级坑讲清楚。

先看一张时间线，搞清楚每个特性落在哪个版本：

record：干掉 POJO 样板代码

我以前写一个 DTO，要写三个字段、构造器、getter、setter、equals、hashCode、toString——一百多行就为了装几个值。record 一行搞定：

// Java 16+ 正式版
public record OrderQuery(
    Long userId,
    String status,
    LocalDateTime from,
    LocalDateTime to
) {}

// 自动带上：全参构造器、accessor（不是 getXxx 是 userId()）、equals、hashCode、toString
OrderQuery q = new OrderQuery(1L, "PAID", null, null);
System.out.println(q.userId());   // 1
System.out.println(q);           // OrderQuery[userId=1, status=PAID, from=null, to=null]

record 天生不可变，适合做 DTO、值对象、事件。但它是 final 的，不能继承，也别拿来当 JPA 实体（Hibernate 需要无参构造）。我团队里现在 DTO 全用 record，Entity 还得留着 Lombok。

record 的小坑
record 的 accessor 方法是 userId() 而不是 getUserId()，Jackson 默认序列化认不出来。Spring Boot 3 已经内置支持 record 序列化，但如果你用老的自定义 ObjectMapper 配置，记得加 ParameterNamesModule，否则反序列化直接报错。

sealed：把类层次圈死

以前你写个抽象类 Shape，谁都能 extends，你控制不了。sealed 用 permits 明确列出允许的子类，配合 pattern matching 就能写穷尽的 switch：

public sealed interface Shape
    permits Circle, Rectangle, Triangle {}

public record Circle(double radius) implements Shape {}
public record Rectangle(double w, double h) implements Shape {}
public record Triangle(double a, double b, double c) implements Shape {}

// Java 21 switch 模式匹配，编译器能检查分支是否穷尽
public double area(Shape s) {
    return switch (s) {
        case Circle c -> Math.PI * c.radius() * c.radius();
        case Rectangle r -> r.w() * r.h();
        case Triangle t -> {
            double p = (t.a() + t.b() + t.c()) / 2;
            yield Math.sqrt(p * (p - t.a()) * (p - t.b()) * (p - t.c()));
        }
    };
}

这个特性在写"领域建模"时特别爽——一个命令、一个事件的类型集合是封闭的，编译器帮你查漏。写业务状态机的时候，sealed + switch 比一堆 if-else 干净太多。

pattern matching：instanceof 不再强转

// 老写法
if (o instanceof String) {
    String s = (String) o;
    System.out.println(s.length());
}

// Java 16+
if (o instanceof String s) {
    System.out.println(s.length());
}

// 配合 null 直接判断，不用再写 o != null
if (o instanceof String s && s.length() > 3) {
    System.out.println(s);
}

这个改动看似小，实际代码里到处都是。以前那种"instanceof 一下强转一下"的胶水代码，现在一行就完事。

虚拟线程：21 最值得升级的理由

这是 Java 21 最大的杀手锏。以前 Java 的线程是"1:1 绑 OS 线程"，开几千个就把内存和上下文切换压垮了，所以要靠线程池限制并发数。虚拟线程是 JVM 做的"协程"，一个 JVM 开几百万个都行：

// 传统平台线程池：并发数被 pool size 卡死
ExecutorService pool = Executors.newFixedThreadPool(200);

// 虚拟线程：每个任务一个虚拟线程，无需池化
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    IntStream.range(0, 10_000).forEach(i ->
        executor.submit(() -> {
            HttpClient client = HttpClient.newHttpClient();
            client.send(req(i), BodyHandlers.ofString()); // IO 阻塞自动让出
            return null;
        })
    );
} // 自动关闭，等所有任务完成

固定 200 个 OS 线程] --> QUEUE[任务排队等待] VTHREAD[虚拟线程
百万级] --> MOUNT[挂载到少量载体线程] MOUNT --> PARK[IO 阻塞时自动卸载] PARK --> RESUME[IO 就绪后换个载体线程继续] style VTHREAD fill:#10b981,stroke:#fff,color:#fff style PLATFORM fill:#f59e0b,stroke:#fff,color:#fff
虚拟线程的坑：synchronized 钉住载体线程
虚拟线程里如果碰到 synchronized 块，整个载体线程会被钉住不能卸载，等于把虚拟线程的性能优势废掉了。我们上线后吞吐不升反降，火焰图一看全卡在 synchronized。改成 ReentrantLock 立刻恢复。用虚拟线程前，先把公共库里的 synchronized 全排查一遍。

另外 ThreadLocal 在虚拟线程下会膨胀——百万虚拟线程每个都挂 ThreadLocal，内存直接炸。Java 21 推荐用 ScopedValue（预览）替代。别在虚拟线程里无脑传 TraceID 那种 ThreadLocal。

GraalVM Native 我单独说两句。它把 Java 提前编译成机器码，启动从几秒压到几十毫秒，内存占用降到原来的几分之一。代价是：编译慢（一个应用几分钟到十几分钟）、反射受限（你的 JDBC 驱动、Jackson 序列化都得登记 hint）、调试困难。我团队只在 Serverless 函数和边缘场景用，普通常驻服务没必要折腾。

# 打包 Native 镜像
./mvnw -Pnative native:compile

# 或者用 Buildpacks 直接出 OCI 镜像
./mvnw -Pnative spring-boot:build-image

从 Spring Boot 2.x 迁移实战

我们去年迁了一个 30 万行的老系统，踩坑清单给你列出来：

  1. JDK 先升到 17：这是硬门槛，Spring Boot 3 直接拒绝 Java 8/11。
  2. javax → jakarta 全局替换：javax.persistence、javax.servlet、javax.validation 全要换成 jakarta.*。IDE 全局替换 + 手动核对。
  3. 第三方 starter 兼容性：老的 Druid、Swagger 老版本都不支持 jakarta。Druid 换 1.2.20+，Swagger 换 springdoc-openapi 2.x。
  4. Hibernate 5 → 6：JPQL 更严格，老的隐式 join 会报错；hbm2ddl.auto 行为也变了。
  5. 配置属性改名：spring.redis.* 拆成 spring.data.redis.*，旧属性启动直接告警。
  6. 反射/序列化：如果用了 Native，所有用到反射的地方都得注册 reflect-config.json。
迁移顺序别搞反
正确顺序：JDK 8→17 → Spring Boot 2.7（最后一个支持 Java 8 的版本，先在这跑通）→ Spring Boot 3.x。别直接从 2.3 跳到 3.5，中间隔了太多 breaking change。2.7 是官方的"过渡跳板"，先把 deprecation warning 清完。

Observability：内置 OTel 之后的变化

Spring Boot 3 把 Micrometer Observation 做进了核心，一次埋点同时产生 metric 和 trace。你只要引 starter，traceId 自动透传到日志：

# 依赖就这一个
# implementation 'org.springframework.boot:spring-boot-starter-actuator'
# implementation 'io.micrometer:micrometer-tracing-bridge-otel'

logging.pattern.include-traceid=true
management.tracing.sampling.probability=1.0
management.otlp.tracing.endpoint=http://otel-collector:4318/v1/traces

以前你要自己接 Sleuth、自己配 MDC、自己传 header，现在 starter 全帮你做了。日志里自动带 traceId，串日志排问题舒服太多。

FAQ

Q：Java 17 和 21 选哪个？
新项目直接 21，虚拟线程是真生产力。存量系统如果依赖大量老库（比如某些 JDBC 驱动还没测过 21），先上 17，稳定了再升 21。

Q：虚拟线程上线要注意什么？
三件事：排查 synchronized、控制 ThreadLocal 用量、压测验证。别直接全量切，先拿一个 IO 密集型服务灰度。

Q：GraalVM Native 值得上吗？
常驻服务别折腾，启动那几秒不值得换编译时间和反射痛苦。Serverless、CLI 工具、启动敏感场景（比如本地开发快速起服务）非常香。

Q：Spring Boot 2.7 还能维护多久？
2.7 的 OSS 支持已经结束，商业支持到 2028。生产别再用 2.7 新项目，老系统排期迁 3.x。

我的结论

Java 17/21 把过去十年 Java 最被诟病的几个点全补上了：record 干掉样板、sealed 把类型安全做扎实、pattern matching 消除胶水代码、虚拟线程让并发编程回到"一个任务一个线程"的朴素模型。Spring Boot 3 这边，最大的变化不是新功能多炫，而是把 jakarta 迁移、可观测性、Native 编译这些"基础设施级"的事做进了框架。

我的建议很简单：新项目 Java 21 + Spring Boot 3.5 起步；老系统按"8→17→21 + Boot 2.7→3.x"的两步走迁，别图快。下一篇咱们钻进 Spring 内部，看看 IoC 容器和 AOP 到底是怎么回事。
