Spring Boot 核心原理

🏷️ Java 总览

为什么要懂 Spring 原理

写业务代码的时候，Spring 是黑盒；一出问题（循环依赖、AOP 不生效、Bean 找不到），不懂原理就是瞎猜。这篇我把面试常问、线上也真会遇到的四块讲透：IoC 启动流程、Bean 生命周期、AOP 代理、自动配置原理。不堆术语，全是我排查问题时实际走过的路。

IoC 容器启动流程

你跑 SpringApplication.run()，背后干的事按顺序是这些：

flowchart TD START[main 入口] --> SPRING[new SpringApplication 推断应用类型 准备环境] SPRING --> REFRESH[refresh() 核心方法] REFRESH --> BD[BeanDefinition 加载与注册] BD --> INST[实例化 Bean 调用构造器] INST --> POP[属性填充 依赖注入] POP --> INIT[初始化 Aware/BeanPostProcessor/init-method] INIT --> READY[容器就绪 回调 Runner] style REFRESH fill:#00add8,stroke:#fff,color:#fff style INST fill:#f59e0b,stroke:#fff,color:#fff

关键在 refresh() 这个方法，它是 Spring 容器的"总开关"。其中最容易出问题的是实例化和依赖注入阶段——循环依赖、构造器注入死锁、AOP 代理时机，全在这一段。

Bean 生命周期：一次完整的旅程

一个 Bean 从 new 到销毁，经历这几步。我把它画成流程图，再对着源码讲：

flowchart LR INST[实例化 构造器] --> POP[属性填充 @Autowired] POP --> BEAN[BeanNameAware/BeanFactoryAware] BEAN --> BPP1[BeanPostProcessor.before] BPP1 --> INIT[@PostConstruct / InitializingBean / init-method] INIT --> BPP2[BeanPostProcessor.after AOP 代理在这里生成] BPP2 --> USE[Bean 就绪 业务使用] USE --> DESTROY[@PreDestroy 销毁] style BPP2 fill:#dc382d,stroke:#fff,color:#fff

重点看红色那步：AOP 代理是在 BeanPostProcessor 的 after 阶段生成的。这就是为什么你在 @PostConstruct 里调 this.xxx()，AOP 切面不生效——那时候代理对象还没生成，你拿到的是原始 this。

@Service
public class OrderService {

    @PostConstruct
    public void init() {
        // 坑：这里 this 是原始对象，事务/AOP 切面不生效
        this.doSomething();
    }

    @Transactional
    public void doSomething() {
        // ... 数据库操作
    }
}

// 正确做法：注入自己，或者用 ApplicationContext 拿代理
@Autowired
private OrderService self; // 这个是代理对象

@PostConstruct
public void init() {
    self.doSomething(); // 走代理，事务生效
}
this 调用不走 AOP 的经典坑
同一个类里 A 方法调 B 方法，B 方法上的 @Transactional/@Async 都不生效，因为走的是 this 不是代理。新人最容易在 @PostConstruct、同类内部调用上踩这个坑。解法：注入自身代理，或把方法拆到另一个 Bean。

AOP 代理：JDK 动态代理 vs CGLIB

这俩是 Spring 生成代理对象的两种机制，搞混了面试和排障都吃亏。

维度JDK 动态代理CGLIB
代理依据接口继承类
要求目标类必须实现接口目标类不能是 final
生成方式运行时反射生成接口实现ASM 字节码生成子类
性能调用稍慢（反射）调用快（直接字节码）
final 方法不涉及无法覆盖，代理失效
Spring Boot 2.x 默认有接口就用它无接口时用
Spring Boot 3.x 默认—默认 CGLIB（proxyTargetClass=true）

Spring Boot 2.x 之后默认 proxyTargetClass=true，也就是一律用 CGLIB，不管你有没有接口。这带来一个后果：如果你把 Service 类标成 final，或者方法标成 final，AOP 直接静默失效——不报错，就是不生效。我见过有人把 @Service 类写成 final 查了一下午。

// 看下你的代理是哪种
@Configuration
public class AopConfig {
    @Bean
    public Advisor advisor() {
        AspectJExpressionPointcut pointcut = new AspectJExpressionPointcut();
        pointcut.setExpression("execution(* com.example..*Service.*(..))");
        return new DefaultPointcutAdvisor(pointcut, new MyMethodInterceptor());
    }
}

// 运行时确认：如果返回 $Proxy 开头是 JDK 代理，$$ 开头是 CGLIB
System.out.println(orderService.getClass());

自动配置原理：从 spring.factories 到 .imports

@SpringBootApplication 一打开，自动配置就开始了。它本质是三个注解的组合：

@SpringBootConfiguration  // 标记配置类
@EnableAutoConfiguration   // 开启自动配置，关键在这
@ComponentScan            // 包扫描
public class Application { ... }

关键是 @EnableAutoConfiguration。Spring Boot 2.7 之前，它靠 META-INF/spring.factories 加载所有自动配置类；2.7 之后改到了 META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports 文件，3.x 完全用新机制：

// AutoConfiguration.imports 文件内容（每行一个全类名）
com.example.autoconfigure.MyServiceAutoConfiguration
com.example.autoconfigure.RedisAutoConfiguration

// 对应的自动配置类
@AutoConfiguration
@ConditionalOnClass(MyService.class)              // classpath 有这个类才生效
@ConditionalOnMissingBean(MyService.class)        // 用户没自定义才生效
@EnableConfigurationProperties(MyProps.class)
public class MyServiceAutoConfiguration {

    @Bean
    public MyService myService(MyProps props) {
        return new MyService(props.getName());
    }
}
看自动配置到底生效没
启动时加 --debug，控制台会打印"CONDITIONS EVALUATION REPORT"。Positive matches 是生效的，Negative 是没生效的。排查"为什么我的 Bean 没被自动装配"，先看这个报告，别瞎猜。

条件注解：自动配置的开关

自动配置类上那一堆 @ConditionalOnXxx 是灵魂。我列常用的几个：

注解生效条件典型用途
@ConditionalOnClassclasspath 存在指定类有 Redis 驱动才配 Redis 连接
@ConditionalOnMissingBean容器里没有该类型 Bean给默认实现，用户可覆盖
@ConditionalOnProperty配置项满足条件my.feature.enabled=true 才开
@ConditionalOnWebApplication是 Web 应用注册 MVC 相关 Bean
@ConditionalOnExpressionSpEL 表达式为真复杂组合条件

理解了条件注解，你就明白 Spring Boot 的"约定大于配置"是怎么实现的——它不是魔法，就是一堆"如果用户没配置，我给个默认"的条件 Bean。你自己写 starter 也是这个套路。

循环依赖：三级缓存到底在干嘛

Spring 解决单例 set/字段注入的循环依赖，靠的是三级缓存。这个面试必考，线上也真会碰到。我把流程画出来：

flowchart TD A[A 实例化 构造器完成] --> EARLY[提前暴露对象工厂 放进三级缓存] EARLY --> INJ[A 注入 B 开始实例化 B] INJ --> BEARLY[B 实例化 提前暴露] BEARLY --> BINJ[B 注入 A 从三级缓存拿到 A 的早期引用] BINJ --> BDONE[B 完成初始化] BDONE --> ADONE[A 拿到 B 完成初始化] style EARLY fill:#00add8,stroke:#fff,color:#fff style BINJ fill:#10b981,stroke:#fff,color:#fff

关键是三级缓存存的不是对象本身，是一个 ObjectFactory，它能在需要时生成 AOP 代理。这样 B 注入 A 时，拿到的就是 A 的早期代理对象，而不是原始对象。

构造器循环依赖救不了
三级缓存只解决 setter/字段注入的循环依赖。构造器循环依赖（A 构造器要 B，B 构造器要 A）Spring 直接抛 BeanCurrentlyInCreationException，谁也救不了。这是设计上的硬约束——遇到这种循环，说明你的类设计有问题，该拆职责。

另外 Spring Boot 2.6+ 默认禁用了循环依赖（spring.main.allow-circular-references=false），老项目升上来突然报错，十有八九是这个。别图省事改回 true，老老实实拆循环。

FAQ

Q：@Autowired 和构造器注入哪个好？
构造器注入。官方现在也推荐构造器，字段可以 final、依赖一目了然、方便单元测试。Spring 4.3 后单构造器不用加 @Autowired。

Q：Bean 是单例还是多例？
默认单例（@Singleton）。要多例用 @Scope("prototype")。注意：单例 Bean 里注入 prototype Bean，那个 prototype 也只创建一次——要拿新的得用 ObjectFactory 或 @Lookup。

Q：为什么我加了 @Transactional 还是不回滚？
查三件事：方法是不是 public（private 不生效）、是不是同类内部调用（this 不走代理）、异常类型是不是被捕获没抛出去（默认只回滚 RuntimeException 和 Error）。

Q：怎么看某个 Bean 是怎么被创建的？
加 --debug 看自动配置报告，或者打断点在 AbstractAutowireCapableBeanFactory.doCreateBean，一步步跟。

我的结论

Spring 的原理说穿了就是三件事：BeanDefinition 定义元数据、BeanFactory 负责生产、BeanPostProcessor 在前后插刀。AOP 本质是"在 after 阶段把原始对象换成代理"，自动配置本质是"一堆带条件的 @Bean"，循环依赖本质是"提前暴露一个对象工厂让对方能拿到引用"。

懂了这些，遇到"Bean 找不到""事务不生效""AOP 静默失效"这类问题，你就不会再瞎改配置碰运气了。下一篇我们跳出单机，看 Spring Cloud 怎么把这些原理用到分布式场景里。
