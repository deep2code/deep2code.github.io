JVM 运行时原理：内存区域、GC 与类加载

🏷️ Java

线上抛一个 OutOfMemoryError，第一件事不是加 -Xmx，而是看它后面跟的那半句话。Java heap space、Metaspace、Direct buffer memory、unable to create new native thread 指向四个完全不同的内存区域，成因、修法没有一条重合，其中有两种越加堆越容易复发。GC 日志同样如此：不知道分代结构，日志里每一行的数字都读不出意义。这篇讲 JVM 运行时的内存布局、对象生命周期、垃圾判定与回收算法、停顿的来源、类加载与 JIT——它是所有调优动作的地基。具体参数怎么配、现场怎么排查，见站内 JVM 调优实战。

运行时数据区的精确划分

「JVM 内存分为堆和栈」是一句被说了二十年的错话。准确的划分维度是线程私有还是线程共享，因为这决定了它由谁分配、由谁释放、以及能不能被 GC 管到。线程私有区域随线程创建、随线程结束自动销毁，根本不需要垃圾回收器介入；线程共享区域才是 GC 的工作范围。另外还有一类内存既不属于堆也不由 JVM 直接管理，但实打实占着进程的物理内存，它是「进程 RSS 远大于 -Xmx」的主要来源。

同一个 OutOfMemoryError 类名下藏着五种完全不同的故障。把后缀读准，能省掉一半的无效尝试：Java heap space 查对象引用链；Metaspace 查类加载器；Direct buffer memory 查堆外缓冲有没有释放；unable to create new native thread 要减线程数或减 -Xss，而这一条加大堆只会让它更早发生——堆占得越多，留给线程栈的地址空间和物理内存就越少。

堆的分代结构与对象晋升的四条分支

新生代由一个 Eden 和两个 Survivor 组成，默认比例 8:1:1，同一时刻只有一个 Survivor 在用。这个设计的依据是弱分代假说：绝大多数对象在第一次回收时就已经死了，活过多次回收的则倾向于继续活很久。于是 Minor GC 只扫描新生代这一小块，而且用复制算法——只搬运存活的少数对象，死的那批连碰都不用碰，回收成本和存活对象数量成正比，而不是和堆大小成正比。这才是分代的真正价值。

对象分配也不是直接进 Eden。每个线程在 Eden 里有一小块私有的 TLAB，分配时只需移动一个指针，不需要加锁，这是 Java 里 new 一个小对象比想象中便宜得多的原因。只有 TLAB 放不下时才走共享的 Eden 慢路径。

元空间取代永久代：为什么换，以及它为什么会满

JDK 8 之前类元数据放在永久代，它是堆的一部分，受 -XX:MaxPermSize 限制。这个设计有两个硬伤：一是大小必须在启动时定死，而类元数据的用量很难预估，配少了报 PermGen space，配多了白占堆；二是它和堆共用一套回收逻辑，回收时机受堆的回收节奏牵制。元空间改用本地内存，默认不设上限，按需向操作系统申请，从此这类报错在大部分场景下消失了。

但「默认不限」是把内存溢出换成了另一种形态：不再报 Metaspace，而是整个进程的内存被撑爆，在容器里就是无声的 OOMKilled——JVM 连一行日志都来不及打。所以生产上仍然应该设置 -XX:MaxMetaspaceSize，让它以一个能看见的 Java 异常暴露出来，而不是以进程消失的方式暴露。

❌
元空间 OOM 的成因几乎从来不是「类太多」

一个业务服务加载的类数量启动后就收敛了。持续上涨只有三种来源：运行期动态生成类（反射代理、CGLIB 子类、脚本引擎、表达式动态编译，每生成一个就多一份元数据）；反复热部署，每次部署新建一个类加载器，旧的没被回收；类加载器泄漏，加载器被静态字段或线程池中的长生命周期线程持有，它加载的所有类就永远不能卸载。判定方法：同一个类名下出现多个不同加载器的副本，就是泄漏。类的卸载条件是整个类加载器不可达，单个类无法单独卸载，这是最关键的一点。

GC 的两个基础问题：怎么找垃圾，怎么回收

所有收集器的差异都建立在这两个问题的答案上。第一个问题是判定存活。引用计数法看起来简单，但它解决不了循环引用：两个对象互相引用、外界都不再持有它们，计数都不为零，永远回收不掉。所以 HotSpot 用可达性分析——从一组确定活着的根出发遍历引用图，遍历不到的就是垃圾。这组根叫 GC Roots：正在执行的方法栈帧里的局部变量与参数、类的静态字段、运行时常量池里的引用、JNI 全局引用、被 synchronized 持有的锁对象、以及 JVM 内部引用如基本类型对应的 Class 对象。

注意其中最容易被忽略的一条：静态字段是 GC Root。一个 static Map 只往里放不往外删，里面的对象永远可达，这就是最高频的内存泄漏形态，而它在代码审查里长得完全像正常代码。

第二个问题是怎么把死对象的空间拿回来。三种基础算法各有取舍，现代收集器都是把它们按区域混搭使用。

算法怎么做是否移动对象碎片空间开销耗时与什么成正比用在哪

标记整理标记存活后把它们向一端压紧，更新所有指向它们的引用是无无额外存活对象数 + 引用更新量老年代 Full GC、G1 的兜底回收
复制把存活对象整体搬到另一块空闲区，原区一次性清空是无需预留一块空闲区仅存活对象数，死对象零成本新生代，因为存活率低

移动对象带来一个绕不开的约束：对象地址变了，所有指向它的引用都必须同步修正，这件事无法和正在运行的业务线程并发安全地完成（除非引入读屏障与转发指针，这正是 ZGC 与 Shenandoah 的做法）。这就是 STW 的根源。

四种引用类型与它们的真实用途

引用强度决定了对象在什么条件下会被回收。这四种不是面试题，其中两种就藏在你每天用的 ThreadLocal 和缓存里。

类型回收时机真实用途坑
强引用只要可达就绝不回收普通赋值，占代码里 99.9%集合、静态字段、监听器列表里的强引用是泄漏主因
软引用内存不足时回收，时机由 JVM 决定理论上适合做缓存实际上不适合：堆宽松时一直不回收像泄漏，堆紧张时可能整批清空导致缓存命中率归零、回源请求打穿下游，而且延长回收过程。用带容量上限和过期策略的缓存实现替代
弱引用下一次 GC 一定回收，不管内存够不够ThreadLocalMap 的 key、WeakHashMap、各种规范化缓存只有 key 是弱引用，value 仍是强引用，这正是 ThreadLocal 在线程池里必须 remove 的原因
虚引用无法通过它访问对象，仅在对象被回收时收到通知堆外内存释放（DirectByteBuffer 的 Cleaner）、资源清理不要用 finalize 替代，它的执行时机不确定且会拖慢回收
 
// ThreadLocal 在线程池下为什么必须 remove：
// ThreadLocalMap 的 Entry 继承 WeakReference，key 弱引用指向 ThreadLocal 实例，
// 但 value 是强引用。ThreadLocal 实例被回收后，key 变 null，value 却还挂在
// 线程的 ThreadLocalMap 上；而线程池里的线程是复用的、几乎不销毁的，
// 于是 value 指向的对象链永远无法回收 —— 这是最典型的线程池内存泄漏。
private static final ThreadLocal<TraceContext> CTX = new ThreadLocal<>();

public void handle(Request req) {
    CTX.set(TraceContext.from(req));
    try {
        process(req);
    } finally {
        CTX.remove();   // 必须在 finally 里，异常路径同样要清
    }
}

STW 与安全点：停顿到底来自哪里

GC 必须停顿，是因为可达性分析要求引用关系在分析期间保持一致。但 JVM 无法在任意指令处挂起线程——它需要线程停在一个「引用关系已知、栈上数据结构完整」的位置，这个位置叫安全点。安全点由编译器插在方法返回、循环回边、异常抛出、native 调用返回等处，线程执行到那里会轮询一个全局标志，发现置位就主动挂起。

问题就出在这里：如果一段代码里没有安全点，其他线程只能等它。 典型场景是 JIT 编译的可数循环（索引为 int 且边界确定）——编译器认为它会很快结束，把回边上的安全点轮询优化掉了。如果这个循环实际要跑几千万次，那么一次 GC 的真实停顿会被拉长到这个循环跑完为止。

sequenceDiagram participant A as 业务线程 A participant B as 业务线程 B 正在跑长循环 participant V as VM Thread participant G as GC 工作线程 V->>V: 决定发起回收 置位全局安全点标志 A->>A: 下一个轮询点检查到标志 A-->>V: 立即挂起 已进入安全点 Note over B: 可数循环的回边轮询被 JIT 优化掉了

由此推出两条实用结论。一是遇到「回收时间很短但停顿很长」，要去看到达安全点的耗时而不是调收集器；二是除了 GC，还有很多操作需要 STW：抓线程栈、导出堆快照、偏向锁撤销、类重定义，所以诊断动作本身也会造成停顿，在高峰期对着线上进程连续导出堆快照可能直接把接口打超时。

并发领域的 volatile、happens-before、内存屏障属于 Java 内存模型（JMM），它讨论的是多线程间可见性与重排序，和这里讲的运行时数据区是两个不同层面的「内存模型」，别混为一谈——这也是面试里最常被问混的一对概念。

类加载：五个阶段、双亲委派，与它被打破的三种场景

类不是一次性全部加载的，用到才加载。五个阶段里最容易被忽略的是准备和初始化的区别：准备阶段给静态变量分配内存并赋零值，初始化阶段才执行 static 代码块和静态赋值语句给出真正的值。这个差异能解释一类诡异的 null：静态字段被另一个类的静态初始化在更早的时机读到了。

双亲委派的规则是：收到加载请求先交给父加载器，父加载不了自己才加载。它保证了核心类库不会被应用代码替换掉——你写一个 java.lang.String 放进 classpath 也没用，请求会一路委派到 Bootstrap 拿到真正的 String。但这条规则在三类场景下必须被打破。

第三种场景直接关联前面说的元空间泄漏：热部署每次新建加载器，只要旧加载器被任何一个 GC Root 间接持有（最常见的是线程池里的线程、注册了但没注销的监听器、第三方库的静态缓存），它加载的全部类就都卸载不掉，元空间单向上涨。这也是「本地开发反复热部署一会儿就卡死」的真正原因。

JIT 编译与预热：为什么刚发布的实例不能满流量

Java 代码先解释执行，同时统计方法调用次数和循环回边次数。达到阈值的方法被 C1 快速编译成机器码，更热的方法进 C2 做深度优化。这套分层编译的取舍是：C1 编译快、优化浅，让代码尽早脱离解释执行；C2 编译慢、优化深，只投给真正的热点。C2 的关键优化有两个——方法内联把被调方法体直接嵌进调用方，消掉调用开销并为后续优化打开视野（这也是为什么方法体过大会失去内联资格，它有字节码大小限制）；逃逸分析判定一个对象是否只在方法内部使用，如果不逃逸就可以做标量替换、把字段拆成局部变量放在栈上，对象根本不会在堆里出现，也就不产生任何 GC 压力。

# 观察预热过程：看类加载与编译到底花在哪
# 1) 打印每个类由哪个加载器从哪个来源加载，排查 jar 冲突与重复加载
java -Xlog:class+load=info:file=/tmp/classload.log -jar app.jar

# 2) 打印编译事件。输出里 % 表示进入 OSR 栈上替换，n 表示 native 方法，
#    s 表示 synchronized，! 表示方法有异常处理器；
#    同一个方法反复出现 made not entrant 说明发生了去优化重编译
java -XX:+UnlockDiagnosticVMOptions -XX:+PrintCompilation -jar app.jar

# 3) 验证逃逸分析的效果：关掉它再跑同一个基准，对比分配速率
java -XX:-DoEscapeAnalysis -jar app.jar

# 4) 代码缓存用满会导致编译被关闭、性能断崖下跌，压测长跑要盯这个指标
jcmd <pid> Compiler.codecache
⚠️
预热是容器化之后最容易忽略的性能问题

实例刚启动的几十秒里，热点方法还没被 C2 编译、连接池还没建满、本地缓存还是空的、类还在陆续加载。这时候如果就绪探针一通过负载均衡就把它和老实例等权重对待，新实例的响应时间可能是稳定期的数倍，表现为每次发布都有一波超时和错误率尖刺，而监控上看 CPU 和内存都正常。解法是就绪探针里带上预热请求，或在网关侧对新实例做渐进放量。把这个问题归因于「JVM 慢」是错的，它是可以工程化解决的。

反模式与最容易踩的坑

反模式为什么错正确做法
看到 OOM 就加 -Xmx如果是泄漏，加堆只是把爆炸时间推后，而且让每次 Full GC 更慢、heap dump 更大更难分析先判断 Full GC 后老年代是否回落；不回落就是泄漏，加堆无用
用 System.gc() 「释放内存」它触发的是 Full GC，会带来一次完整 STW，且不保证真的回收任何东西生产环境加 -XX:+DisableExplicitGC；注意堆外内存的回收依赖它，禁用前先确认没有依赖
用 finalize 释放资源执行时机完全不确定，由一个优先级很低的单线程处理，队列堵住会直接导致内存泄漏；已被标记废弃try-with-resources 显式关闭，需要兜底用 Cleaner
static Map 当缓存静态字段是 GC Root，里面的对象永远可达，只进不出用带容量上限与过期策略的缓存库，或显式做淘汰
把 -XX:MaxTenuringThreshold 调小「减少 Survivor 复制开销」短命对象被提前推进老年代，老年代增长速率飙升，Full GC 变频繁先看晋升速率，多数情况下该调的是新生代大小
字符串拼接用 + 放在循环里每轮新建一个 StringBuilder 与一个 String，制造大量短命对象推高 Minor GC 频率循环外复用一个 StringBuilder
把 -Xss 调大来解决 StackOverflowError掩盖了递归缺少出口这个真 bug，并且线程数一多就吃掉大量内存，转而触发无法创建线程先读栈轨迹里重复的那一段，修递归逻辑
认为「JVM 内存模型」就是内存分区JMM 讨论的是多线程可见性与重排序，与运行时数据区是两件事说清是哪一个，避免沟通时互相误解
❌
最容易踩的坑
  • 只看 OutOfMemoryError 不看后缀，把 unable to create new native thread 当堆不足处理，加堆后故障来得更快。
  • 元空间不设 MaxMetaspaceSize，元数据无声涨到容器内存上限，进程被 OOMKilled，连一行 Java 异常都没留下。
  • 以为单个类能被卸载。类卸载的前提是整个类加载器不可达，一个静态引用就能钉住整批类。
  • 用软引用做缓存，压测时表现正常，线上内存一紧张缓存整批失效，回源流量瞬间打穿数据库。
  • ThreadLocal 在线程池里 set 后不 remove。key 是弱引用但 value 是强引用，线程复用导致 value 永不释放，还会串到下一个请求读到上一个请求的数据。
  • 把 remove 写在业务逻辑末尾而不是 finally，一抛异常就漏清。
  • 遇到长停顿直接换收集器，没看「到达安全点耗时」。长循环里缺少安全点造成的停顿，换任何收集器都没用。
  • 高峰期对线上进程连续导出堆快照。dump 本身要 STW，几 GB 的堆足以把接口全部打超时。
  • static final 常量被编译期内联到调用方，只改常量所在类不重新编译使用方，线上跑的还是旧值。
  • 在 static 代码块里读远程配置或连数据库，失败后抛 ExceptionInInitializerError，而真实原因藏在 cause 里，日志里只看到 NoClassDefFoundError。
  • 本地反复热部署越来越卡，以为是 IDE 问题，其实是旧类加载器泄漏把元空间堆满了。
  • 发布后必现一波超时，归因为「Java 启动慢」而不做流量预热，每次发布都在重复踩同一个 JIT 预热坑。
