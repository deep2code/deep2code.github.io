我为什么在 2026 年还写 Java

常有人问我："现在都 2026 了，Go、Rust 那么火，Java 还有戏吗？"我的回答很直接：Java 不是最酷的语言，但它是企业级后端最稳的基本盘。Spring 生态、大量遗留系统、金融和电商的核心链路，这些年不是被替代了，而是在 Java 17/21 上焕发了第二春。我手里同时维护着 Go 和 Java 两套服务，Java 这边的坑反而更值得写——因为它的坑藏得更深，踩一次疼三年。

这一系列文章不教你写 System.out.println("hello")。我想把这些年在 Java 后端上踩过的坑、读过的 Spring 源码、调过的 JVM 参数攒成一份地图。如果你刚从别的语言转过来，或者在维护一个老的 Spring Boot 2.x 系统准备升级，这套文章就是给你写的。

版本线：2026 年该用哪个 Java

Oracle 从 Java 9 开始改成每六个月一个版本，LTS（长期支持）版本是 8、11、17、21。到 2026 年，Java 25 已经发布（2025 年 9 月的 LTS），但生产上我团队的标准很明确：

版本类型状态（2026）我的建议
Java 8LTSOracle 免费支持已停新系统别再用，老系统尽早迁
Java 11LTS安全维护末期过渡跳板，不是终点
Java 17LTS生产主力存量升级的第一站
Java 21LTS新系统首选虚拟线程、pattern matching 转正
Java 25LTS尝鲜中新项目可评估，别急着上核心链路
一句话选型
新项目：Java 21 + Spring Boot 3.5+；存量升级：先迁到 17 再迁 21，别跳。Spring Boot 3.x 要求最低 Java 17，这是硬门槛。

我踩过的最大的三个坑

  1. Spring Boot 2.x 升 3.x 没改包名：javax.persistence 全项目报红。光包名替换就跑了一晚上，还漏了几个第三方 starter 没适配。
  2. 把虚拟线程当万能药：Java 21 上线后我急着切虚拟线程，结果遇到 synchronized 块把载体线程钉死，吞吐不升反降。得先把 synchronized 换成 ReentrantLock。
  3. JVM 参数瞎抄：从网上抄了一套 G1 参数，线上 Full GC 一周一次变一天一次。后来用 Arthas 看了一眼才知道堆设太大，young 区回收不及时。
别抄别人的 JVM 参数
每套参数都是别人业务、别人机器、别人堆大小调出来的。你先把默认参数跑起来，用 GC 日志和 Arthas 拿到自己的数据，再动手调。盲目抄参数是调优最大的反模式。

FAQ

Q：Java 21 的虚拟线程真的能替代线程池吗？
日常 IO 密集型服务确实可以，但要小心 synchronized 钉住载体线程、ThreadLocal 膨胀、以及和 synchronized 监控工具的兼容性。CPU 密集型任务别用虚拟线程。

Q：Spring Boot 3 必须用 GraalVM Native 吗？
不是。Native 启动快、内存省，但编译慢、反射受限、调试难。普通服务用 C2 编译就够，Native 适合 Serverless 和启动敏感场景。

Q：Java 还能活多久？
只要企业级系统还在跑、Spring 生态还在迭代，Java 就死不了。它的问题是"老"，不是"死"——2026 年的 Java 21 比五年前轻快太多了。

我的结论

Java 这个生态到 2026 年终于把过去十年欠的技术债还清了：record 干掉了笨拙的 POJO 样板、sealed 把类型安全做扎实了、虚拟线程补上了并发这一课、Spring Boot 3 把可观测性内置了。它不再是那门"臃肿、启动慢、内存大"的老语言，但调优的功夫一点没少。
