MyBatis 与 JPA 实战

🏷️ Java 总览

ORM 选型：MyBatis 还是 JPA

这是个吵架吵了十年的话题。我的结论很务实：国内互联网业务 90% 用 MyBatis-Plus，复杂领域模型/海外项目用 JPA/Hibernate。别问哪个"更先进"，问你的团队和业务长什么样。先把对比摆出来：

维度MyBatis / MyBatis-PlusJPA / Hibernate
SQL 控制力手写 SQL，完全可控自动生成，难优化
开发效率CRUD 要写或靠 MP 生成Repository 接口即开即用
学习曲线低，会 SQL 就会高，注解/状态机/缓存策略一堆
复杂查询XML 或注解写 SQL，爽JPQ/Criteria 写复杂查询痛苦
关联映射手动 join 或嵌套结果@OneToMany 自动映射
调优透明度SQL 一眼看穿自动 SQL 得开日志才看得到
国内生态MyBatis-Plus 一统天下用得少，坑没人填

MyBatis-Plus 常用技巧

MyBatis-Plus（MP）是国内事实标准，它在 MyBatis 上套了一层 CRUD 自动实现。几个我每天都用的：

// 实体类
@Data
@TableName("t_order")
public class Order {
    @TableId(type = IdType.ASSIGN_ID)   // 雪花 ID
    private Long id;
    private String userId;
    private BigDecimal amount;
    @TableField(fill = FieldFill.INSERT)
    private LocalDateTime createTime;
    @TableLogic                          // 逻辑删除
    private Integer deleted;
}

// Mapper 继承 BaseMapper，单表 CRUD 白送
public interface OrderMapper extends BaseMapper<Order> {}

// 条件构造器
List<Order> list = orderMapper.selectList(
    new LambdaQueryWrapper<Order>()
        .eq(Order::getStatus, "PAID")
        .ge(Order::getAmount, new BigDecimal("100"))
        .orderByDesc(Order::getCreateTime)
);

分页插件是 MP 的标配，配置一次就能用：

@Configuration
public class MybatisPlusConfig {
    @Bean
    public MybatisPlusInterceptor mybatisPlusInterceptor() {
        MybatisPlusInterceptor interceptor = new MybatisPlusInterceptor();
        interceptor.addInnerInterceptor(new PaginationInnerInterceptor(DbType.MYSQL));
        return interceptor;
    }
}

// 业务里直接用
Page<Order> page = orderMapper.selectPage(
    new Page<>(1, 20),
    new LambdaQueryWrapper<Order>().eq(Order::getStatus, "PAID")
);

动态 SQL：XML 的真正价值

MyBatis 的杀手锏是动态 SQL。多条件查询、可选排序、批量 in，写在 XML 里比在 Java 里拼字符串优雅一百倍：

<select id="searchOrders" resultType="Order">
    SELECT * FROM t_order
    <where>
        <if test="userId != null">
            user_id = #{userId}
        </if>
        <if test="status != null and status != ''">
            AND status = #{status}
        </if>
        <if test="from != null">
            AND create_time >= #{from}
        </if>
        <if test="ids != null and ids.size() > 0">
            AND id IN
            <foreach collection="ids" item="id" open="(" separator="," close=")">
                #{id}
            </foreach>
        </if>
    </where>
    <choose>
        <when test="orderBy != null">ORDER BY ${orderBy}</when>
        <otherwise>ORDER BY create_time DESC</otherwise>
    </choose>
</select>
#{} 和 ${} 的区别
#{} 是预编译参数，防 SQL 注入，安全；${} 是字符串直接拼接，有注入风险。上面的 orderBy 用 ${} 是因为排序字段不能用占位符——这种场景必须在 Java 层做白名单校验，别直接把前端传的字段名塞进去。

一级缓存和二级缓存

MyBatis 的缓存分两级，搞不清就会踩坑：

flowchart LR REQ[一次 SQL 查询] --> L1[一级缓存 SqlSession 级别
默认开启 同 session 同语句命中] L1 -->|未命中| DB[查数据库] L2[二级缓存 Mapper namespace 级别
需手动开启 跨 session 共享] L1 -.查不到才查.-> L2 style L1 fill:#00add8,stroke:#fff,color:#fff style L2 fill:#10b981,stroke:#fff,color:#fff

一级缓存是 SqlSession 级别的，同一个 session 里相同查询直接命中。但 Spring 里每个请求（或每次事务）就是一个新 SqlSession，所以一级缓存基本"你还没来得及用就没了"。

二级缓存是 namespace 级别，能跨 session 共享。但我强烈不推荐在生产开二级缓存——多表关联、多服务更新同一张表，缓存一致性根本没法保证，出了脏数据你都查不到原因。

二级缓存的脏数据坑
我们早年开了二级缓存，结果订单表被另一个服务直接 update，MyBatis 不知道，业务读到的还是旧数据，撑了三天才定位到。从那以后我只在 Redis 里做业务缓存，数据库缓存一律交给 MyBatis 关闭。

JPA/Hibernate 常用注解

如果你用 JPA，核心是注解把对象映射成表。我列最常用的：

@Entity
@Table(name = "t_order")
@Data
public class Order {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, length = 64)
    private String orderNo;

    @ManyToOne(fetch = FetchType.LAZY)     // 懒加载，避免 N+1
    @JoinColumn(name = "user_id")
    private User user;

    @OneToMany(mappedBy = "order", cascade = CascadeType.ALL)
    private List<OrderItem> items;

    @Enumerated(EnumType.STRING)           // 存枚举名，别用 ORDINAL
    private OrderStatus status;
}

// Repository 接口即查询
public interface OrderRepository extends JpaRepository<Order, Long> {
    List<Order> findByStatusAndUserId(String status, Long userId);
}

N+1 问题：JPA 的天坑

N+1 是 JPA 最著名的坑。你查 100 个订单，每个订单的 user 是懒加载，循环里第一次访问就触发一次单独 SQL——1 次查订单 + 100 次查 user = 101 条 SQL，数据库直接被打挂。

flowchart TD Q1[查询 100 个订单] --> LOOP[遍历每个订单] LOOP --> LAZY[访问 order.user 触发懒加载] LAZY --> Q2[第 1 条查 user] Q2 --> Q3[第 2 条查 user] Q3 --> DOT[... 共 100 条] DOT --> Q100[第 100 条查 user] style Q1 fill:#00add8,stroke:#fff,color:#fff style Q100 fill:#dc382d,stroke:#fff,color:#fff

解法是 join fetch 一次性把关联查出来：

@Query("SELECT o FROM Order o JOIN FETCH o.user WHERE o.status = :status")
List<Order> findWithUser(String status);
// 一条 SQL：SELECT ... FROM t_order o JOIN t_user u ON ...

或者用 EntityGraph 注解：

@EntityGraph(attributePaths = {"user"})
List<Order> findByStatus(String status);
怎么发现 N+1
开启 spring.jpa.show-sql=true 或用 datasource-proxy，看控制台打印的 SQL 条数。正常一次查询应该 1 条，如果你发现翻页时突然冒出几百条重复 SQL，就是 N+1 了。生产关 show-sql，但开发环境一定开着。

多数据源配置

实际项目经常一个服务要连多个库。MyBatis-Plus 多数据源用 dynamic-datasource 这个 starter，加个注解就切换：

spring:
  datasource:
    dynamic:
      primary: master
      datasource:
        master:
          url: jdbc:mysql://主库:3306/order
        slave:
          url: jdbc:mysql://从库:3306/order
        log:
          url: jdbc:mysql://日志库:3306/log
@DS("slave")              // 这个方法走从库
public List<Order> queryFromSlave(Long userId) { ... }

@DS("log")
public void writeLog(LogRecord log) { ... }

@DS 放在 Service 类或方法上，自动切换数据源。读写分离、分库分表、跨库 join 都靠它。注意事务别跨数据源——分布式事务是另一个大坑，下篇不展开。

FAQ

Q：MyBatis 和 JPA 能混用吗？
能，同一个项目里复杂查询用 MyBatis，领域模型用 JPA。但别在同一事务里混着用，两级 session 管理会让你怀疑人生。

Q：MP 的逻辑删除靠谱吗？
@TableLogic 自动在查询加 where deleted=0，靠谱。但注意跨表 join 时别忘了加条件，否则 join 出已删除的数据。

Q：JPA 的 hibernate 一级缓存是什么？
持久化上下文（Persistence Context），同一个事务内相同实体只查一次。事务结束就清空。别把它当业务缓存用。

Q：批量插入用 saveAll 还是 foreach？
JPA 的 saveAll 其实是循环单条 insert，性能差。要真批量，用 JDBC 的 rewriteBatchedStatements=true + 手动 batch，或者干脆用 MyBatis 的 foreach。

我的结论

MyBatis-Plus 是国内业务开发的瑞士军刀——CRUD 快、SQL 可控、分页插件开箱即用，团队上手零门槛。JPA 适合领域驱动设计写得正、团队愿意花时间学的项目，自动映射和 Repository 抽象确实优雅，但 N+1 和自动 SQL 调优是绕不过的坎。

我的建议：新项目先上 MyBatis-Plus，遇到真正复杂的领域模型再局部引 JPA。别一上来就 JPA 全套，等线上 N+1 爆了你再回头学，代价太大。下一篇我们看最底层的 JVM——所有这些框架跑得顺不顺，最后都落在 JVM 上。
