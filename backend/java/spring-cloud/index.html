Spring Cloud 组件演进与 K8s 环境下的取舍

🏷️ Spring Cloud

网上关于 Spring Cloud 的文章有个普遍问题：它们教的是 2018 年的 Spring Cloud。Ribbon、Hystrix、Zuul、Eureka、Config Server、Sleuth 这六个当年的核心组件，现在没有一个还是推荐选项。如果你照着那些教程搭一套新系统，等于一开始就背上一堆已经停止维护的依赖。

这篇不逐个组件讲配置，只讲两件事：哪些组件已经换代、换代的原因是什么，以及在 K8s 上哪些 Spring Cloud 组件属于重复建设。微服务本身该不该拆、怎么拆、DDD 边界怎么划，见站内 微服务的代价模型 与 DDD 拆分；熔断限流的参数怎么定见 熔断与限流；网关的责任边界见 API 网关；注册发现的摘除延迟与保护模式见 服务注册与发现。这些本文只给结论。

六个核心组件全部换代，以及换掉的原因

先把对照表放在最前面。判断一篇 Spring Cloud 教程是否过时，看它有没有提到左边这一列就够了。

在 K8s 上还需要 Spring Cloud 吗

这是本文最重要的结构性判断。把 Spring Cloud 的能力和 K8s 的能力逐项对齐，会发现重叠得相当厉害：服务发现有 Service，负载均衡有 kube-proxy 的 iptables 或 IPVS 规则，配置有 ConfigMap 与 Secret，入口网关有 Ingress 或 Gateway API，健康检查有探针，灰度有多 Deployment 加 Service 选择器。在 K8s 上再搭一套 Eureka 加 Config Server，是把平台已经做好的事在应用层重做一遍。

更麻烦的不是浪费，而是两套健康视图会不一致。K8s 依据探针结果摘除 Endpoints，注册中心依据心跳摘除实例，两者的判定周期和判定条件不同。滚动更新时经常出现这种状况：Pod 已经被 K8s 从 Endpoints 里摘掉，注册中心里还挂着，客户端从注册中心拿到地址直连过去，撞上正在终止的 Pod。探针语义、preShutdown 与滚动更新的时序细节见 Kubernetes 深度剖析。

新项目在 K8s 上的推荐组合

用 K8s 的 Service 做服务发现（Feign 的 url 直接写 Service 名，跨命名空间写完整域名），配置走 ConfigMap 加 Secret 并挂载成文件以便热更新，容错用 Resilience4j 写在应用里（因为只有应用知道业务上什么算可降级），可观测性用 Micrometer 加 OpenTelemetry。不引入注册中心、不引入 Config Server、不引入 Spring Cloud Gateway 做内部路由。这套组合的依赖数量只有全家桶的三分之一，排障链路也短得多。

OpenFeign 的机制与四个高频坑

Feign 值得保留，因为「用接口声明远程调用」这个抽象确实降低了样板代码。但它的默认配置对生产环境相当不友好，下面这张时序图把一次调用拆开，每一层都有坑。

sequenceDiagram autonumber participant B as 业务代码 participant P as Feign 生成的 JDK 动态代理 participant LB as LoadBalancer 或 K8s Service participant HC as HTTP 客户端 participant D as 下游服务 B->>P: 调用接口方法 P->>P: 按注解拼 RequestTemplate
路径 查询参数 请求体编码 P->>LB: 用服务名请求一个实例地址 LB-->>P: 返回具体 ip 与端口 Note over LB: 坑一 这一步的实例列表来自本地缓存
刚下线的实例可能仍在列表里 P->>HC: 发起真实 HTTP 请求 Note over HC: 坑二 默认实现是 JDK HttpURLConnection
没有连接池 每次请求新建 TCP 与 TLS HC->>D: 请求 D-->>HC: 500 或超时 HC-->>P: 响应或异常 P->>P: ErrorDecoder 把非 2xx 转成异常 Note over P: 坑三 默认抛 FeignException
下游的业务错误码信息容易在这里丢失 P-->>B: 抛出异常 Note over B,P: 坑四 若配了 Retryer
上面整段会被重放 非幂等接口会重复执行

坑一是实例列表的新鲜度。Spring Cloud LoadBalancer 默认缓存服务实例列表，缓存过期时间是秒级。下游缩容或重启时，客户端会在一小段时间内继续把请求发给已经不存在的实例，表现为间歇性连接拒绝。这属于注册发现的固有延迟，解法是下游优雅停机加客户端重试幂等接口，详见 服务注册与发现。

坑二是默认没有连接池，这是对性能影响最大的一条。Feign 的默认 Client 实现基于 JDK 的 HttpURLConnection，每次调用都要重新完成 TCP 三次握手，走 HTTPS 还要再加一次 TLS 握手。内网调用的实际延迟里，握手可能占到一半以上。

底层客户端连接池引入方式适用判断
JDK HttpURLConnection无默认，什么都不配就是它只适合低频调用，例如启动时拉一次配置
Apache HttpClient 5有，可配总连接数与每路由连接数加 feign-hc5 依赖并开启开关通用首选，配置项最丰富，社区资料多
OkHttp有，默认保持 5 个空闲连接加 feign-okhttp 依赖并开启开关调用目标少、想少配点参数时更省事
Spring 的 RestClient 或 WebClient取决于底层实现新版本支持用它们作为 Feign 底座想统一项目里所有 HTTP 出站栈时选它

坑三是异常类型的丢失。下游返回 400 带着业务错误码，默认 ErrorDecoder 会统一抛 FeignException.BadRequest，错误码藏在响应体字符串里。上游的全局异常处理拿不到结构化信息，只能按状态码粗粒度处理。正确做法是自定义 ErrorDecoder，把下游的错误响应体反序列化成内部异常类型。

坑四是重试。Feign 默认的 Retryer.NEVER_RETRY 是个正确的默认值，很多文章却把「配上 Retryer」当作优化建议。超时不等于请求没到达下游——很可能下游已经执行成功，只是响应慢或者响应包在网络上丢了。对创建订单、扣减余额这类接口重试，等于制造重复操作。

❌
要重试，先有幂等

只有下游明确幂等时才能开重试，且必须配退避与上限。判断标准不是「这个接口看起来是查询」，而是下游有没有按业务唯一键做去重。幂等的四种落地方式见站内 幂等设计。另外重试要和熔断一起看：下游抖动时，N 倍的重试流量往往就是把它彻底压死的那一下。

Feign 的生产级配置

下面这份配置的每一项都有理由，注释里写了为什么。注意超时是两层：连接超时是建立 TCP 连接的上限，读超时是等待响应的上限，两者语义完全不同，只配一个等于没配。

spring:
  cloud:
    openfeign:
      # 换掉默认的 HttpURLConnection，启用 Apache HttpClient 5 连接池
      httpclient:
        hc5:
          enabled: true
        # 连接池总上限。按 下游数量 乘以 每个下游的并发预估 来算，不要照抄默认值
        max-connections: 400
        # 单个路由（同一目标主机）的连接上限，默认只有 50，高并发下会排队
        max-connections-per-route: 100
      client:
        config:
          # default 是兜底配置，所有未单独声明的客户端都用它
          default:
            # 建连超时：内网建连超过 1 秒基本说明网络或对端有问题，不要设成 5 秒以上
            connect-timeout: 1000
            # 读超时：必须小于上游网关的超时，否则上游先断开，本服务还在傻等占线程
            read-timeout: 3000
            logger-level: basic        # basic 只打方法、URL、状态码、耗时，full 会打请求体，生产别用
          # 按客户端名单独覆盖。这个名字必须和 FeignClient 注解里的 name 或 contextId 完全一致
          order-service:
            read-timeout: 8000        # 这个下游确实慢，单独放宽，而不是把 default 一起放宽

resilience4j:
  circuitbreaker:
    instances:
      order-service:
        sliding-window-type: COUNT_BASED
        sliding-window-size: 100
        failure-rate-threshold: 50      # 具体参数怎么定，见站内熔断与限流那篇
        wait-duration-in-open-state: 10s

配完之后一定要验证生效。最常见的失效原因是配置键前缀的版本差异：老文章里写的是 feign.client.config，较新的版本统一到了 spring.cloud.openfeign.client.config，写错了不会报错，只是默默用默认值。

症状真实原因怎么确认
超时配置完全不起作用配置键前缀是老版本的 feign. 开头，当前版本已改名启动时看有没有 properties 未绑定的提示；或临时把值改成极小值看是否立刻超时
只有部分客户端生效按名配置时 name 写错，或用了 contextId 而配置里写的是 name@FeignClient 上同时有 name 和 contextId 时，配置要用 contextId
明明配了 8 秒，5 秒就断了外层网关或调用方的超时更短，先触发把整条链路上每一跳的超时列出来，必须从外到内逐层递减
压测时大量 TIME_WAIT 与建连耗时连接池没启用，或 per-route 上限太小用 ss -s 看连接状态分布，看连接池的 metrics 指标
下游错误码拿不到用了默认 ErrorDecoder自定义 ErrorDecoder，把响应体解析成内部异常
@Configuration
public class FeignConfig {

    // 显式声明不重试。即使默认值已经是不重试，写出来是为了防止有人「优化」时随手加上
    @Bean
    public Retryer feignRetryer() {
        return Retryer.NEVER_RETRY;
    }

    // 把下游的业务错误码还原成内部异常，避免上游只能按 HTTP 状态码粗粒度处理
    @Bean
    public ErrorDecoder errorDecoder(ObjectMapper mapper) {
        return (methodKey, response) -> {
            // 4xx 一般是调用方参数问题，重试没有意义，转成不可重试的业务异常
            if (response.status() >= 400 && response.status() < 500) {
                try (InputStream body = response.body().asInputStream()) {
                    ApiError err = mapper.readValue(body, ApiError.class);
                    return new DownstreamBusinessException(err.code(), err.message());
                } catch (Exception e) {
                    return new DownstreamBusinessException("UNKNOWN", "下游错误体解析失败");
                }
            }
            // 5xx 和超时交给 Resilience4j 统计失败率，这里保留原始异常类型
            return FeignException.errorStatus(methodKey, response);
        };
    }

    // 透传链路与业务上下文。Micrometer Tracing 会自动传 traceparent，但租户、语言这类业务头要自己传
    @Bean
    public RequestInterceptor contextInterceptor() {
        return template -> {
            String tenant = TenantContext.current();
            if (tenant != null) {
                template.header("X-Tenant-Id", tenant);
            }
        };
    }
}

可观测性：Sleuth 已经退场

如果你的项目里还有 spring-cloud-starter-sleuth，它在 Boot 3 上根本装不起来。Sleuth 的能力已经并入 Micrometer Tracing，底层桥接 Brave 或 OpenTelemetry，对外走 W3C 的 traceparent 头传播。

真正的变化是 Observation API 的引入。以前埋一个关键操作，要在指标侧写一遍 Timer、在链路侧写一遍 Span，两边的标签还容易写得不一致；现在一次 Observation 声明同时产出指标和 span，标签共享。traceId 依然会自动进日志的 MDC，日志里只要在 pattern 里加上占位符就能打出来。指标、日志、链路三支柱怎么关联、采样率怎么定，见站内 分布式链路追踪，本文不展开。

分布式事务：大多数场景不该引入 Seata

Seata 提供 AT、TCC、Saga、XA 四种模式，它们的语义差别和适用边界见站内 分布式事务。这里只给一个工程判断：绝大多数业务应该用本地消息表，而不是引入 Seata。

理由有三条。第一，Seata 的 AT 模式依赖全局锁和 undo_log 表，在高并发下全局锁本身就是瓶颈，而且一旦协调者不可用，业务写入全部阻塞——你为了一致性引入了一个新的单点。第二，它的回滚靠反向 SQL 生成，遇到触发器、存储过程、或者被其他系统并发改过的行，反向 SQL 可能补偿错数据，而这类问题极难在测试阶段发现。第三，调试成本高：一个跨三个服务的事务出问题，要同时看三个服务的日志加协调者日志加 undo 表。

本地消息表的做法是：业务数据和「待发送消息」写在同一个本地数据库事务里，提交后由后台任务扫表投递到 MQ，消费方按业务唯一键幂等处理。没有额外中间件、失败可以无限重放、排查只看两张表。代价是最终一致而非强一致，以及需要消费方真正做到幂等。绝大多数下单、发券、积分场景要的就是最终一致。

配置与启动的两个陷阱

第一个是 bootstrap.yml 不再默认生效。从 Spring Cloud 2020 起，bootstrap 上下文默认关闭，必须显式引入 spring-cloud-starter-bootstrap 依赖，否则 bootstrap.yml 会被完全忽略——现象是配置中心地址读不到、启动时报「找不到配置」，而文件明明躺在那里。更推荐的做法是改用 spring.config.import 声明外部配置源，这是新版本的标准方式，不再依赖 bootstrap 上下文这层特殊机制。

第二个是 @RefreshScope 的作用域陷阱。它的实现是把 Bean 包一层代理，收到刷新事件后销毁目标实例，下次访问时重新创建并重新注入属性。这意味着三件事：

sequenceDiagram autonumber participant CC as 配置中心 participant APP as 应用进程 participant CTX as RefreshScope 容器 participant RB as 标注解的 Bean participant OB as 未标注解的 Bean CC->>APP: 推送配置变更 APP->>CTX: 发布 RefreshEvent CTX->>RB: 销毁缓存的实例 Note over CTX,RB: 下次调用才重建 属于惰性刷新
不是收到事件就立刻生效 OB-->>OB: 构造时已经注入的值保持不变 Note over OB: 陷阱一 已注入到普通单例字段的值不会更新
连接池 线程池这类初始化后不再读配置的组件更是如此 APP->>RB: 业务下次调用 RB->>CTX: 创建新实例 重新读取最新配置 Note over RB: 陷阱二 重建期间的并发调用
可能拿到新旧两个实例 有状态 Bean 会出问题 RB-->>APP: 用新配置继续处理

结论是：@RefreshScope 只适合无状态、且每次调用都重新读取字段值的 Bean。数据库连接池的最大连接数、线程池的核心线程数这类「初始化时读一次」的参数，靠它刷新是无效的，必须用组件自己提供的动态调整 API。配置中心侧的推送机制、长轮询与本地快照兜底见 配置中心。

版本矩阵：Spring Cloud 最大的坑

Spring Cloud 是一个聚合项目，它用「发布列车」的方式锁定内部几十个组件的版本组合，并声明兼容的 Spring Boot 区间。这个对应关系必须严格遵守，没有任何调整空间。Spring Cloud 从 2020 版起改用年份命名（此前是 Hoxton、Greenwich 这类伦敦地铁站名），Boot 3 只能配 2022 年之后的车次。

⚠️
别相信任何文章里写死的版本号，包括这篇

版本对应关系随时间变化，唯一可信来源是 Spring Cloud 官网的发布列车页面和 Maven 仓库里 BOM 的 pom 文件，后者会直接声明它依赖的 Boot 版本。正确的工程做法是：只在父 pom 的 dependencyManagement 里导入 Spring Boot 与 Spring Cloud 两个 BOM，子模块引依赖时一律不写版本号，并且禁止任何人单独升级某个组件的版本。

典型报错真实原因处理方式
启动时抛出版本兼容性校验异常，并打印期望的 Boot 版本区间Spring Cloud 自带的兼容性校验器检测到 Boot 版本不在白名单内按提示调 Boot 版本；不要关闭这个校验器，它是在帮你
NoSuchMethodError 或 NoClassDefFoundError，堆栈指向某个自动配置类某个组件被传递依赖拉成了另一个版本，编译期通过运行期方法签名不匹配mvn dependency:tree 找到冲突来源，用 BOM 或 exclusion 统一
找不到 javax.servlet 相关类Boot 3 已迁到 jakarta 命名空间，某个依赖还是 Boot 2 时代的版本升级该依赖到支持 jakarta 的版本，详见站内 Java 17 与 Spring Boot 3 升级
bootstrap 配置被忽略，配置中心地址读不到没引 spring-cloud-starter-bootstrap，bootstrap 上下文默认关闭引入该依赖，或改用 spring.config.import
配置项在启动日志里提示已废弃或不可识别属性名在新版本被重命名临时加 spring-boot-properties-migrator 依赖，它会打印新旧对照，迁完记得移除
# 排查依赖冲突：先看整棵树里某个包被哪些路径引入、最终选了哪个版本
mvn dependency:tree -Dincludes=org.springframework.cloud

# 只看冲突与被忽略的版本（verbose 会标出 omitted for conflict）
mvn dependency:tree -Dverbose | grep -i "omitted for conflict" | sort -u

# 查全项目里还有没有残留的 javax 依赖，升级 Boot 3 前必做
mvn dependency:list | grep -iE "javax\.(servlet|persistence|validation|annotation)"

# 确认运行时真正生效的自动配置（哪些装上了、哪些没装上以及原因）
java -jar app.jar --debug 2>&1 | sed -n '/CONDITIONS EVALUATION REPORT/,/^$/p'

反模式对照表

反模式后果正确做法
在 K8s 上再搭一套 Eureka 或 Nacos 做注册发现两套健康视图不一致，滚动更新期间请求打到正在终止的 Pod；多一套必须高可用的组件要运维用 Service 加 DNS，Feign 的 host 直接写 Service 名
Feign 当内部 RPC 高频调用却不换连接池每次调用重新握手，内网延迟里握手占大头，压测时大量 TIME_WAIT启用 HttpClient 5 或 OkHttp，按下游并发配 per-route 上限
给非幂等接口配 Retryer超时重放导致重复下单、重复扣款，且下游抖动时重试流量压垮它先做幂等再开重试，配退避与上限
各组件版本各自升级编译通过运行期 NoSuchMethodError，排查成本极高父 pom 统一 BOM，子模块不写版本号
用 Spring Cloud Gateway 写业务逻辑网关变成有状态、需要频繁发布的组件，一次发布影响全部流量；Reactor 里写阻塞代码会打满事件循环线程网关只做路由、认证、限流、协议转换，业务逻辑留在服务里
把 @RefreshScope 加在有状态 Bean 或连接池上刷新期间新旧实例并存导致状态错乱；连接池参数根本刷不动只给无状态 Bean 用；池化组件用它自己的动态调整接口
为了「微服务标准」引入 Seata新增必须高可用的协调者，全局锁成瓶颈，回滚可能补偿错数据本地消息表加消费端幂等，最终一致足够绝大多数业务
logger-level 设成 full 上生产请求体与响应体全量进日志，泄漏敏感数据且日志量爆炸生产用 basic，排查时临时对单个客户端调成 full
✅
最容易踩的坑
  • 还在用 Ribbon、Hystrix、Zuul 1、Sleuth：这四个在 Boot 3 上直接装不起来，不是「能用但不推荐」的关系。
  • Feign 默认没有连接池：不换底层客户端，每次调用都要重新 TCP 握手，HTTPS 还要加 TLS 握手。
  • 只配了 read-timeout 没配 connect-timeout：目标机器网络不可达时，建连阶段会一直挂着，线程被占死。
  • 超时配置键前缀换过名：老文章的 feign.client.config 在新版本失效，写错不报错只是静默用默认值。
  • 链路上的超时没有逐层递减：内层超时比外层长，外层先断开而内层还在跑，线程和连接白占。
  • bootstrap.yml 默认不生效：2020 版本之后必须显式引 bootstrap starter，否则整个文件被忽略。
  • @RefreshScope 是惰性刷新：事件到了不代表值变了，要等下次调用重建 Bean；连接池这类参数根本刷不动。
  • @FeignClient 的 name 与 contextId 混用：两者同时存在时，按名配置必须写 contextId，写 name 无效。
  • 默认 ErrorDecoder 吞掉业务错误码：下游的结构化错误变成一条异常消息字符串，上游只能按状态码处理。
  • 关闭 Spring Cloud 的版本兼容性校验器：它拦住的是必然会在运行期炸的组合，关掉只是把问题推迟到线上。
  • 在 Gateway 的过滤器里写阻塞调用：Netty 的事件循环线程数很少，一次阻塞就会让整个网关吞吐塌陷。
  • 以为服务网格能替代业务降级：Sidecar 能做重试和熔断，但「熔断之后返回什么兜底数据」只有业务代码知道。
