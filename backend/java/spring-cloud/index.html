Spring Cloud 微服务全家桶

🏷️ Java 总览

💡 你要写个企业级后端系统，团队很大，代码要规范、要可维护、要各种框架生态。或者你刚进公司，发现全是 Java 项目。

Spring Cloud 到底是什么

很多人把 Spring Cloud 当成一个框架，其实它是一套规范 + 一堆实现。Spring Cloud 本身只管"接口长什么样"，具体谁来做注册中心、谁来做网关、谁来做熔断，是不同的子项目在实现。

Spring Cloud 官网有一张 compatibility matrix，先定 Boot 版本，再查对应的 Cloud Release Train。别反过来。Gradle 里用 io.spring.dependency-management 插件 import BOM，别自己逐个写版本号，否则一定会错配。

Gateway：统一入口

Spring Cloud Gateway 取代了老的 Zuul。它基于 WebFlux，异步非阻塞，性能比 Zuul 好一个量级。核心概念就三个：Route（路由）、Predicate（断言）、Filter（过滤器）。

spring:
  cloud:
    gateway:
      routes:
        - id: order-route
          uri: lb://order-service       # lb 表示走注册中心负载均衡
          predicates:
            - Path=/api/orders/**
          filters:
            - StripPrefix=1              # 去掉 /api 前缀再转发
            - name: RequestRateLimiter
              args:
                redis-rate-limiter.replenishRate: 100
                redis-rate-limiter.burstCapacity: 200

Gateway 做的事：路由转发、鉴权、限流、日志、协议转换。它和 Nginx 的区别是——Nginx 在七层之上做静态/反向代理，Gateway 在应用层做和 Spring 生态打通的业务级路由（拿得到 JWT、读得到注册中心、能写 Java 过滤器）。

Gateway 别做重业务
Gateway 是异步 WebFlux 模型，如果你在过滤器里写阻塞的 JDBC 调用，整个事件循环被你一个人卡死。网关里只做无阻塞的活（鉴权、限流、改 header），复杂逻辑下沉到业务服务。

注册与配置：Nacos vs Consul

老 Eureka 停维护了，现在主流是 Nacos（国内）和 Consul（国外）。我把两者摆在一起比：

维度NacosConsul
注册中心CP+AP 可切换CP（Raft）
配置中心内置，长推送内置，KV 存储
健康检查心跳+TCP/HTTPAgent 主动探测
多数据中心支持原生多 DC 更强
生态阿里系，国内文档全HashiCorp 系，和 K8s 结合好
运维单机简单，集群要 MySQLGo 二进制，自洽

我团队国内业务用 Nacos，配置中心 + 注册中心一把梭；海外和 K8s 深度集成的项目用 Consul。配置热更新这功能是真香——改一行配置推到 Nacos，业务服务不用重启就生效。

@RestController
@RefreshScope   // 这个注解让配置变更能刷新
public class FeatureController {
    @Value("${feature.new-checkout:false}")
    private boolean newCheckout;
}

OpenFeign：声明式 HTTP 客户端

以前调别的服务，你得 RestTemplate 拼 URL、设 header、解析响应。OpenFeign 让你像调本地方法一样调远程：

@FeignClient(name = "user-service", fallback = UserClientFallback.class)
public interface UserClient {

    @GetMapping("/users/{id}")
    UserDTO getUser(@PathVariable("id") Long id);

    @PostMapping("/users/batch")
    List<UserDTO> batchGet(@RequestBody List<Long> ids);
}

// 直接注入就用
@Autowired
private UserClient userClient;

public void doBiz(Long id) {
    UserDTO u = userClient.getUser(id); // 像本地方法
}

OpenFeign 底层还是 HTTP，但帮你做了：服务发现（从 Nacos 拿实例）、负载均衡、编解码、熔断降级。它和 Resilience4j 是绝配——上面的 fallback 就是熔断后的兜底方法。

Resilience4j：熔断、限流、重试

老 Hystrix 停更了，替代品就是 Resilience4j。它把熔断、限流、重试、超时拆成独立模块，你按需组合。核心 CircuitBreaker：

CircuitBreakerConfig config = CircuitBreakerConfig.custom()
    .failureRateThreshold(50)              // 错误率超 50% 熔断
    .slidingWindowSize(10)                // 最近 10 次调用统计
    .waitDurationInOpenState(Duration.ofSeconds(10)) // 熔断 10 秒后半开探测
    .slowCallRateThreshold(50)            // 慢调用比例
    .slowCallDurationThreshold(Duration.ofSeconds(1))
    .build();

// 用法：装饰你的 Feign 调用
Supplier<UserDTO> supplier = () -> userClient.getUser(id);
Supplier<UserDTO> decorated = CircuitBreaker
    .decorateSupplier(circuitBreaker, supplier);
UserDTO result = Try.ofSupplier(decorated).recover(...)
    .orElse(new UserDTO("兜底"));

熔断不是万能
熔断是"下游挂了别拖死自己"，不是"下游慢了你就能快"。我见过有人把熔断阈值配得很激进（错误率 10% 就断），结果下游正常抖动一下就整个熔断，自己把自己打挂。生产参数要压测定，别拍脑袋。

分布式链路追踪

一个请求经过网关→订单→用户→商品，出问题你怎么知道慢在哪？答案是链路追踪。Spring Boot 3 内置 Micrometer Tracing，接 OTel 协议：

management:
  tracing:
    sampling:
      probability: 1.0   # 全采样，生产建议 0.1
  otlp:
    tracing:
      endpoint: http://otel-collector:4318/v1/traces

traceId 自动在服务间透传（Feign/Gateway 都帮你传 header），日志里自动带上。出问题拿 traceId 去 Jaeger 一查，整条调用链的耗时分布一目了然。

Spring Cloud 和 K8s 的关系

这是个高频困惑。K8s 有 Service 做服务发现、有 Ingress 做网关、有 HPA 做弹性——那 Spring Cloud 还有必要吗？我的看法是两者在不同层，不是替代关系：

能力Spring CloudK8s谁更合适
服务发现Nacos/Consul 客户端CoreDNS + Service纯 K8s 用 Service，跨语言/跨云用 Nacos
网关Gateway 业务级Ingress/Nginx 网络级Gateway 做业务鉴权，Ingress 做流量入口
配置中心Nacos 配置热推ConfigMap（需重启或 reload）要热更新用 Nacos
熔断限流Resilience4j 代码级Service Mesh（Istio）Java 生态用 Resilience4j 更轻
弹性伸缩—HPA/VPAK8s 独占

实际落地：K8s 管部署和网络，Spring Cloud 管业务级的服务治理。别硬上 Service Mesh——Istio 那套对小团队是运维灾难。

FAQ

Q：微服务一定要上 Spring Cloud 吗？
不一定。服务少（3-5 个）、团队小，单体 + 模块化更划算。微服务的复杂度是指数级的，别为了"时髦"拆服务。

Q：Nacos 和 Eureka 怎么选？
Eureka 停维护了，新项目别选。Nacos 注册+配置一体，国内生态好，是事实标准。

Q：OpenFeign 性能怎么样？
比 RestTemplate 略重（多了抽象层），但换来可维护性。高吞吐场景用 HttpClient5 做底层连接池，别用默认的 HttpURLConnection。

Q：熔断和限流区别？
熔断是"下游挂了我先撤"，防雪崩；限流是"我自己扛不住了，挡掉多余请求"，防自己被压垮。两个都要。

我的结论

Spring Cloud 2026 年的状态是：组件收敛了（Gateway 取代 Zuul、Resilience4j 取代 Hystrix、Nacos 取代 Eureka），和 Spring Boot 3 的可观测性打通了。它解决的是"分布式系统的通用问题"——服务发现、路由、容错、追踪，这些事你自己写一遍是不现实的。

但记住：微服务不是银弹。团队小、业务简单，别硬拆。真要拆，先把监控、链路追踪、CI/CD 配齐，再谈服务拆分。下一篇我们看数据层——MyBatis 和 JPA 怎么选。
