JVM 调优与内存管理

🏷️ Java 总览

JVM 调优是干什么

很多人一听 JVM 调优就头大，觉得是高深莫测的黑魔法。其实它就干两件事：让 GC 别停你太久，让内存别爆掉。线上 90% 的"Java 服务变慢了""CPU 飙高""OOM 了"，最后都落到这两件事上。

JVM 内存模型：先搞清楚内存分几块

Java 进程的内存按用途分这几块，你调参数之前必须知道每块放什么：

flowchart TD HEAP[堆 Heap
对象实例 GC 主战场] --> YOUNG[新生代 Eden + S0 + S1] HEAP --> OLD[老年代 Old Gen] META[元空间 Metaspace
类信息 常量] STACK[虚拟机栈 每个线程
栈帧 局部变量] DIRECT[直接内存 Direct ByteBuffer
NIO Netty 堆外] NATIVE[本地方法栈 JNI] style HEAP fill:#00add8,stroke:#fff,color:#fff style DIRECT fill:#f59e0b,stroke:#fff,color:#fff

重点说两个常被忽略的：

  • 元空间（Metaspace）：JDK 8 取代了永久代，放类元信息。默认不设上限，碰到动态类生成（CGLIB 代理、Groovy、动态编译）会一直涨，最后 OutOfMemoryError: Metaspace。生产一定要设 -XX:MaxMetaspaceSize。
  • 直接内存：Netty、NIO 用堆外内存做零拷贝。它不受 -Xmx 控制，受 -XX:MaxDirectMemorySize 管。线上 Netty 服务 OOM 但堆很空，十有八九是直接内存爆了。

GC 算法选型：G1、ZGC、Shenandoah 怎么选

到 Java 21，CMS 彻底没了，主流是这三款。我直接给结论：

GCSTW 目标适用堆大小特点我推荐场景
G1亚秒级4GB-32GB平衡吞吐和延迟Java 9+ 默认，大多数服务
ZGC<1ms（JDK 21 起）8GB-16TB超低延迟，堆大也稳大堆 + 低延迟要求
Shenandoah<10ms大堆RedHat 主导，并发整理和 OpenJDK 有差异的发行版
Parallel秒级小堆吞吐优先，STW 长批处理/非在线
flowchart LR Q[你的场景] --> A{堆 > 32GB?} A -->|是| Z[ZGC 首选] A -->|否| B{延迟敏感?} B -->|P99 要求 < 10ms| Z B -->|常规在线服务| G[G1 默认就好] Q --> C{批处理 不在线?} C -->|是| P[Parallel 吞吐优先] style G fill:#00add8,stroke:#fff,color:#fff style Z fill:#10b981,stroke:#fff,color:#fff

2026 年的结论：Java 21 上如果堆超过 8GB 或对延迟敏感，直接上 ZGC。它的 STW 已经压到亚毫秒，而且 JDK 21 之后 ZGC 已经是生产可用，不再是实验特性。

常用 JVM 参数：我背下来的一套

别抄网上的，我把每个参数为什么设讲清楚，你按自己的情况调：

# 堆大小：初始和最大设成一样，避免运行时扩容抖动
-Xms4g -Xmx4g

# 元空间必须设上限
-XX:MetaspaceSize=256m
-XX:MaxMetaspaceSize=512m

# GC 选择（Java 21）
-XX:+UseG1GC
# 或大堆低延迟用 ZGC：
# -XX:+UseZGC

# G1 细节
-XX:MaxGCPauseMillis=200      # 目标停顿 200ms
-XX:G1HeapRegionSize=16m       # Region 大小

# GC 日志（JDK 9+ 用统一日志）
-Xlog:gc*,gc+age=trace,safepoint:file=/var/log/gc.log:time,uptime,level,tags:filecount=10,filesize=100m

# OOM 时自动 dump 堆快照，别心疼磁盘
-XX:+HeapDumpOnOutOfMemoryError
-XX:HeapDumpPath=/var/log/heapdump/
-XX:+ExitOnOutOfMemoryError

# 直接内存上限
-XX:MaxDirectMemorySize=1g
OOM 时别光重启
线上 OOM 了，第一反应不是"重启一下就好了"，而是赶紧保留现场：Heap Dump 自动生成了没？gc.log 还在不在？重启把现场丢了，下次还会炸。-XX:+HeapDumpOnOutOfMemoryError 必须配，这是事后复盘的唯一线索。

Arthas：线上诊断神器

阿里开源的 Arthas 是我线上排障的第一工具。不用重启、不用改代码、attach 到进程就能看。几个高频命令：

# 启动
java -jar arthas-boot.jar

# 看哪些命令在慢
monitor com.example.OrderService pay -n 5

# 方法调用路径和耗时（最常用）
trace com.example.OrderService pay '#cost > 100'

# 看 JVM 实时内存
memory

# 看 JVM 参数
jvm

# 方法出入参怎么了（抓一次真实调用）
watch com.example.OrderService pay "{params, returnObj}" -x 2

# 线程栈，看谁卡着
thread -n 5

线上服务 P99 突然飙高，我第一件事就是 trace 那个接口，看哪一步慢——是数据库慢、下游 RPC 慢、还是 GC 停了。比你翻日志快十倍。

GC 日志分析：怎么看懂

GC 日志开了之后，别害怕，关键看几样：

# 一条典型 G1 日志（简化）
[2026-09-18T10:00:01.123+0800][gc] GC(42) Pause Young (Normal)
  (Evacuation Pause) 1200M->450M(4096M) 15.234ms
# 意思：年轻代回收，堆从 1200M 降到 450M，停了 15ms

重点看：

  • 回收前后堆大小：450M 是回收后存活的，如果回收后还占堆的 80% 以上，说明老年代要满了。
  • 停顿时间：Young GC 几十毫秒正常，Mixed GC 几百毫秒要警惕，Full GC 秒级就是事故。
  • GC 频率：正常一分钟几次 Young GC 很健康。如果几秒一次，说明新生代太小或对象分配太快。

工具方面，我直接用 gceasy.io 把 gc.log 拖进去，自动出图表，比肉眼分析快多了。

内存泄漏排查：从怀疑到定位

内存泄漏在 Java 里不是"内存不释放"，是"你以为不用了，但有引用还在"。排查流程：

flowchart TD SYMP[现象：堆只涨不跌 Full GC 后也不降] --> DUMP[拿到 Heap Dump] DUMP --> MAT[用 Eclipse MAT 分析 Dominator Tree] MAT --> BIG[找占用最大的对象] BIG --> PATH[看 GC Roots 引用链 谁在持有] PATH --> FIX[定位代码 修掉] style DUMP fill:#00add8,stroke:#fff,color:#fff style FIX fill:#dc382d,stroke:#fff,color:#fff

常见泄漏源：

  1. 静态集合类：static Map 只 put 不 remove，对象永远被引用。
  2. ThreadLocal 没 remove：线程池线程复用，ThreadLocal 里的对象永远不释放。用完一定 try-finally remove()。
  3. 未关闭的资源：Connection、InputStream 没关，被 GC Root 挂着。
  4. 监听器/回调注册了没反注册：事件总线、观察者模式，注销漏了。
  5. 缓存无界：自己写的 Map 当缓存，只加不删，最后 OOM。
Arthas 在线看堆
没等到 OOM 也能看：arthas> heapdump --live /tmp/heap.hprof 在线导一份堆快照，再用 MAT 打开。别在高峰期导，dump 会 STW 几秒，挑低峰做。

线上 OOM 事故复盘

说个我亲身经历的。去年大促前压测，一个订单服务跑着跑着直接 OutOfMemoryError: Java heap space，重启后几小时又炸。

第一步：看 Heap Dump（幸好配了自动 dump）。用 MAT 打开，Dominator Tree 第一名是个 byte[]，占了堆 70%。往上追引用链——是个静态 ConcurrentHashMap，key 是订单 ID，value 是序列化的订单快照。

第二步：看代码。这个 Map 是一个"订单导出临时缓存"，业务代码里导完了忘了 clear。压测批量跑了 10 万单，全堆在这个 Map 里。

第三步：修复。加了 @Scheduled 定时清理，同时换成 Caffeine 带最大容量和过期时间的缓存。压测再跑，堆稳定在 1GB 左右。

复盘教训
1）临时缓存一定用带容量上限的本地缓存（Caffeine），别用裸 Map。2）静态集合是泄漏重灾区，code review 重点查。3）压测不只是压吞吐，也要压"长时间运行内存稳不稳"——跑几小时看堆曲线。

FAQ

Q：Xmx 设多大合适？
容器环境留 1/4 给堆外和元空间。4GB 容器设 Xmx3g。别设成容器上限，直接内存和元空间会把你挤出 OOMKilled。

Q：Full GC 多久一次正常？
正常业务服务 Full GC 应该"天级"甚至"周级"。如果一天好几次，说明老年代回收不下去，要么有泄漏，要么堆太小。

Q：ZGC 什么时候用？
堆 > 8GB，或者 P99 延迟要求特别严（比如交易系统）。小堆 G1 就够，ZGC 不一定更快。

Q：CPU 飙高怎么查？
Arthas thread -n 3 看最忙的线程，再 profiler start 采 30 秒火焰图，谁占 CPU 一眼看穿。别一开始就怀疑 GC。

我的结论

JVM 调优的核心不是背参数，是先测量再动手。开 GC 日志、配 Heap Dump、上 Arthas，拿到你自己服务的数据，再决定调什么。盲目抄参数是最大的反模式——别人的堆大小、别人的业务模型，跟你的没关系。

到 2026 年，ZGC 把大堆低延迟这个老问题解决了，G1 是默认稳妥选择，大多数服务真不用怎么调。把内存泄漏的习惯（裸 Map 当缓存、ThreadLocal 不 remove）改掉，比调十个参数都管用。
