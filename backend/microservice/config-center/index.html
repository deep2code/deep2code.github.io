配置中心与分布式事务

🏷️ 分布式事务

两个必须正视的工程问题

服务跑起来之后，团队会立刻撞上两堵墙：第一堵墙——配置散落在几十个服务的 YAML 和环境变量里，改个数据库连接池大小要发一轮版，周末半夜要调阈值只能 SSH 到生产机器 sed。第二堵墙——一次下单要写订单库、扣库存库、写支付单，其中一个失败了怎么办？数据库本地事务管不到别的库，这就是分布式事务。本篇一次讲清这两件事。

配置中心：从"写死在 YAML"到"热更新"

配置中心（Nacos Config、Apollo、Spring Cloud Config）要解决三个问题：① 配置集中存储、版本管理；② 变更实时推送到所有实例、不重启生效；③ 敏感配置加密、权限审计。它和注册中心常常合一（Nacos 就是典型），但概念上是两回事。

关键工程细节：配置中心与客户端之间用长轮询（Long Polling）保持长连接，配置变更时服务端立刻把变更推给所有订阅客户端，秒级生效、不需要重启。同时客户端本地缓存一份快照，配置中心挂了也能用缓存配置启动。

分布式事务：为什么不能直接用 XA

数据库层面有 XA 两阶段提交（2PC），理论上能跨库保证原子性，但生产中几乎没人用，原因有三：

  1. 性能差：XA 要锁资源直到事务结束，跨三个库时锁持有时间被网络 RTT 拉长，并发一上来就死锁。
  2. 协调者单点：TM（事务协调者）挂了，所有参与方都阻塞等待，没有超时解锁机制。
  3. 不适合微服务：服务是独立部署的，不允许把多个数据库连接塞进同一个分布式事务里——那等于把单体数据库的强一致性又捡回来了。

所以微服务的标准答案是放弃跨库强一致，换业务可接受的最终一致。主流方案有三种：Seata AT、TCC、Saga。

三种分布式事务方案对比

方案一致性侵入性性能适用场景
Seata AT最终一致（一阶段提交、二阶段回滚）低（加 @GlobalTransactional 注解）中通用业务、CRUD 为主
TCC最终一致（Try/Confirm/Cancel）高（每个服务写三个接口）高资金、库存等高并发强一致
Saga最终一致（长事务 + 补偿）中（每步写补偿动作）高跨多服务长流程（下单→支付→物流）

Seata AT 模式原理

Seata 是阿里巴巴开源的分布式事务框架，AT（Automatic Transaction）模式对业务零侵入，核心是全局锁 + undo_log。一个全局事务由 TC（Transaction Coordinator，协调者）、TM（事务管理者，业务代码）、RM（资源管理者，每个数据库侧）组成。

AT 模式的聪明之处在于：一阶段就本地提交并释放本地锁，只持有一把"全局锁"在 TC 上；二阶段提交是异步删 undo_log，回滚才用 undo_log 反向生成补偿 SQL。性能接近本地事务，但代价是全局锁成为热点。

TCC 模式：Try-Confirm-Cancel

TCC 把一个业务动作拆成三个阶段：Try（预留资源）→ Confirm（正式提交）→ Cancel（释放预留）。以转账为例：Try 阶段 A 账户冻结 100 元、B 账户预增 100 元；Try 全成功则 Confirm 真正扣减；任一失败则 Cancel 解冻。它比 AT 灵活，但要求每个服务手写三个接口。

// account-tcc.go —— 以账户服务为例实现 TCC 三个接口
package account

import "context"

// Try：冻结金额，不真正动余额
func (s *AccountService) TryFreeze(ctx context.Context, req *FreezeReq) (*FreezeResp, error) {
    acc, err := s.repo.GetByUserID(ctx, req.UserID)
    if err != nil {
        return nil, err
    }
    if acc.Balance < req.Amount {
        return nil, ErrInsufficientFunds
    }
    // 关键：防悬挂 + 幂等——用事务 ID 记录这次 Try，重复调用直接返回
    if s.repo.ExistsTx(ctx, req.TxID) {
        return &FreezeResp{OK: true}, nil
    }
    acc.Balance -= req.Amount
    acc.Frozen  += req.Amount
    if err := s.repo.Save(ctx, acc, req.TxID); err != nil {
        return nil, err
    }
    return &FreezeResp{OK: true}, nil
}

// Confirm：全部 Try 成功后调用，真正扣掉冻结金额（必须幂等）
func (s *AccountService) Confirm(ctx context.Context, req *ConfirmReq) error {
    return s.repo.CommitFrozen(ctx, req.TxID, req.UserID, req.Amount)
}

// Cancel：任一 Try 失败后调用，解冻回余额（必须幂等 + 防悬挂）
func (s *AccountService) Cancel(ctx context.Context, req *CancelReq) error {
    return s.repo.RollbackFrozen(ctx, req.TxID, req.UserID, req.Amount)
}

Saga 模式：长事务编排

Saga 把长流程拆成一串本地事务 T1, T2, ..., Tn，每个 Ti 都有对应的补偿 Ci。正常顺序执行 T1→T2→...→Tn；某步 Ti 失败，则反向执行 Ci→Ci-1→...→C1。Saga 有两种编排方式：编配式（Choreography）各服务通过事件串联，无中心；编排式（Orchestration）由一个中心协调器指挥每一步。

# order-saga.yaml —— 用编排器定义下单 Saga 流程
name: order-purchase-saga
steps:
  - id: createOrder
    action: order-service/CreateOrder
    compensation: order-service/CancelOrder
  - id: reserveStock
    action: stock-service/Reserve
    compensation: stock-service/Release
  - id: deductBalance
    action: account-service/Deduct
    compensation: account-service/Refund
  - id: shipGoods
    action: shipping-service/CreateShipment
    compensation: shipping-service/CancelShipment
# 任一步骤失败，编排器自动反向调用已完成步骤的 compensation

配置中心实战：Nacos 客户端配置

# application.yml —— Spring Boot 服务接入 Nacos 配置中心
spring:
  application:
    name: order-service
  cloud:
    nacos:
      config:
        server-addr: nacos.internal:8848
        namespace: prod
        group: ORDER_GROUP
        # 支持多数据源配置：主配置 + 共享配置
        shared-configs:
          - data-id: common-db.yml
            refresh: true
          - data-id: common-redis.yml
            refresh: true
        # 业务配置，支持 @RefreshScope 热更新
        extension-configs:
          - data-id: order-business.yml
            refresh: true
      # 配置变更监听：业务代码注册回调，收到变更后重建线程池/连接池

# 用 Nacos OpenAPI 发布一个配置（CI/CD 脚本里常用）
curl -X POST "http://nacos.internal:8848/nacos/v1/cs/configs" \
  -d "dataId=order-business.yml" \
  -d "group=ORDER_GROUP" \
  -d "tenant=prod" \
  -d "type=yaml" \
  --data-urlencode "content=$(cat order-business.yml)"

# 监听配置变更（长轮询，30s 超时）
curl "http://nacos.internal:8848/nacos/v1/cs/configs/listen" \
  -d "dataId=order-business.yml&group=ORDER_GROUP&tenant=prod&md5=旧md5"

最佳实践

我踩过的坑：有次上线 TCC 方案，漏了"空回滚"处理——Cancel 请求先到、Try 请求因为网络延迟后到，结果 Cancel 直接报错回滚失败，整个分布式事务卡住。后来加了事务 ID 记录表，Try 先到就记录、Cancel 来查不到就直接返回成功，才解决。TCC 三防（空回滚、幂等、悬挂）一个都不能少。

  • 配置分级：公共配置（日志级别、JVM 参数）放共享配置；业务差异配置放独立 dataId；密码等敏感配置走加密配置中心或 K8s Secret，不要明文入库。
  • 变更必须可审计可回滚：配置中心保留历史版本，每次变更记录谁改的、改了什么，出问题一键回滚。
  • 分布式事务能不用就不用：优先用本地消息表 + MQ 最终一致（业务表和消息在同一个本地事务写入，后台任务扫表发 MQ），比 Seata/TCC 简单可靠。
  • TCC 必须三防：① 空回滚（Cancel 先到、Try 没到）；② 幂等（Confirm/Cancel 重试）；③ 悬挂（Try 在 Cancel 之后才到，不能再执行）。这三点漏掉任何一个，生产必出资金事故。
  • Saga 补偿不是万能：如果某一步的补偿动作本身可能失败（比如物流单已经发出去了），就要在补偿里加人工兜底流程，不能假设补偿一定成功。

FAQ

Q1：Seata AT 模式对业务代码零侵入，是不是就不用考虑 TCC/Saga 了？

AT 模式确实最省事，但它有边界：① 要求业务表必须有主键；② 全局锁在高并发下是瓶颈；③ 跨语言支持弱（主要是 Java）。如果你的服务是 Go/Node 写的、或者 QPS 极高、或者资源是"库存"这种行级竞争激烈的，TCC 更合适。长流程跨 4 个以上服务、执行时间分钟级，Saga 更合适。

Q2：配置中心和注册中心合并在 Nacos 一套，会不会互相影响？

数据上是分开的（命名空间、group 隔离），但进程共享。如果 Nacos 集群出问题，服务发现和配置一起挂。生产建议：配置中心和注册中心逻辑上分开集群，哪怕用同一套 Nacos 软件，也部署两组独立集群，避免一损俱损。

Q3：本地消息表方案和 Seata 比，到底选哪个？

能接受最终一致（秒级延迟）就用本地消息表：和数据库同事务写、后台任务投递 MQ、消费端幂等。没有额外组件，出问题可对账。Seata 适合需要"一发起就知道成没成"的强一致场景（比如转账），但它引入了 TC 这个必须高可用的新组件。绝大多数互联网业务，本地消息表足够。

Q4：分布式事务会不会拖慢业务？

会，而且不小。AT 模式比本地事务慢 30%~100%（多了 undo_log 和全局锁）；TCC 要写三套代码。所以原则是：能用单服务本地事务解决就不要跨服务，必须跨服务时选最轻量的方案，把分布式事务的范围压到最小。

总结

配置中心解决"配置散落"的运维痛点，分布式事务解决"跨库一致性"的业务痛点。前者是基础设施升级，后者是架构设计的艰难取舍。真正生产落地时，90% 的业务用本地消息表 + 对账兜底，10% 的资金类场景才上 TCC/Seata。下一篇我们讲另一个生产高频话题——服务挂了怎么办：熔断、限流、降级。
