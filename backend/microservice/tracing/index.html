分布式链路追踪

🏷️ 可观测性

没有可观测性的微服务就是盲猜

单体时代出问题，登录一台机器 tail -f app.log 就能看到完整调用栈。微服务时代，一个请求可能经过 API 网关 → 订单服务 → 库存服务 → 支付服务 → 数据库，跨越 5 个进程、3 种语言、2 个机房。

可观测性（Observability）有三大支柱：Metrics（指标）——回答"系统健康吗"；Logs（日志）——回答"发生了什么"；Traces（追踪）——回答"为什么慢/为什么错"。三者必须用同一个 TraceID 串起来，这才是可观测性的完整体。

Trace / Span 模型：追踪的核心抽象

OpenTelemetry（CNCF 标准，取代了早期的 OpenTracing 和 OpenCensus）把一次分布式调用抽象成一棵 Trace 树：

  • Trace：一次完整请求的调用链，全局唯一 TraceID，从用户请求进来到响应出去。
  • Span：Trace 树上的一个节点，代表一次操作（一个 RPC、一次 DB 查询、一次消息发送）。每个 Span 有 SpanID、父 SpanID、开始时间、结束时间、标签（tag）、事件（event）。

关键是 TraceContext 跨进程传递：网关生成 TraceID，通过 HTTP Header（traceparent）或 gRPC metadata 一路带下去，每个服务提取并继续传递，最终所有 Span 在追踪系统里按 TraceID 拼成一棵树。

OpenTelemetry 三大组件

OpenTelemetry 不是一个软件，而是一套标准 + SDK + Collector：

  • API/SDK：各语言库（Go/Java/Python/JS），业务代码里打 Span、加标签、记录异常。
  • OTLP 协议：统一上报协议，业务 SDK 不再直接对接 Jaeger/Zipkin，而是统一发到 Collector。
  • Collector：独立部署的网关组件，接收各服务的 Span，做采样、过滤、批量、转发到 Jaeger/Tempo/ES。它是可观测性的"数据总线"。

采样策略：全量追踪成本太高

我踩过的坑：有次生产环境全量上报 Span，QPS 5 万，Trace 存储一天就撑爆了 500GB 磁盘。而且 Jaeger 查询超时严重。后来改成尾部采样——错误请求全保留、P99 慢请求全保留、成功请求只采 1%，存储成本降了 95%，关键问题一个没漏。生产环境不要全量追踪，尾部采样是最佳选择。

生产环境 QPS 几万，全量上报 Span 成本惊人。采样是必选项：

  • 头部采样（Head-based）：请求进来时就决定采不采。优点是省资源；缺点是采到的 Trace 可能全是成功请求，漏掉错误。
  • 尾部采样（Tail-based）：Collector 等一个 Trace 全部 Span 到齐后，根据规则决定保留（如：错误的全保留、慢的全保留、成功的按 1% 采样）。生产推荐这种，保证"出问题的请求一定能追到"。
  • 父节点采样：如果上游已经决定采样了，下游跟着采；上游没采，下游也不采。保证一个 Trace 要么完整、要么没有，不会出现半截 Trace。

实战一：Go 服务接入 OpenTelemetry

// main.go —— 订单服务接入 OpenTelemetry，上报到 Collector
package main

import (
    "context"
    "go.opentelemetry.io/otel"
    "go.opentelemetry.io/otel/exporters/otlp/otlptrace/otlptracegrpc"
    "go.opentelemetry.io/otel/propagation"
    "go.opentelemetry.io/otel/sdk/resource"
    sdktrace "go.opentelemetry.io/otel/sdk/trace"
    semconv "go.opentelemetry.io/otel/semconv/v1.17.0"
)

func initTracer(ctx context.Context) (*sdktrace.TracerProvider, error) {
    // OTLP gRPC 上报到 Collector（Collector 再转发到 Jaeger）
    exp, err := otlptracegrpc.New(ctx,
        otlptracegrpc.WithEndpoint("otel-collector:4317"),
        otlptracegrpc.WithInsecure(),
    )
    if err != nil {
        return nil, err
    }
    tp := sdktrace.NewTracerProvider(
        // 尾部采样前先在 SDK 层做 20% 头部采样，降低 Collector 压力
        sdktrace.WithSampler(sdktrace.TraceIDRatioBased(0.2)),
        sdktrace.WithBatcher(exp),  // 批量上报，别一个 Span 一次网络
        sdktrace.WithResource(resource.NewWithAttributes(
            semconv.SchemaURL,
            semconv.ServiceName("order-service"),
            semconv.ServiceVersion("v1.4.2"),
        )),
    )
    otel.SetTracerProvider(tp)
    // 关键：注入 TraceContext 到 HTTP/gRPC metadata，跨进程传递
    otel.SetTextMapPropagator(propagation.NewCompositeTextMapPropagator(
        propagation.TraceContext{}, propagation.Baggage{},
    ))
    return tp, nil
}

业务代码里打 Span 的标准姿势——包裹一个数据库调用或一次 RPC：

// 在 handler 里给关键操作加 Span
func (h *Handler) CreateOrder(ctx context.Context, req *OrderReq) (*OrderResp, error) {
    ctx, span := otel.Tracer("order").Start(ctx, "CreateOrder")
    defer span.End()

    span.SetAttributes(
        semconv.DBSystemMySQL,
        attribute.String("order.user_id", req.UserID),
    )

    order, err := h.repo.Insert(ctx, req)  // 这一步自动产生 DB Span
    if err != nil {
        span.RecordError(err)  // 异常自动标记到 Trace
        span.SetStatus(codes.Error, "insert order failed")
        return nil, err
    }
    return order, nil
}

实战二：Docker Compose 一键起追踪栈

# docker-compose.observability.yaml —— Collector + Jaeger + Grafana
version: "3.9"
services:
  otel-collector:
    image: otel/opentelemetry-collector-contrib:0.96.0
    command: ["--config=/etc/otelcol/config.yaml"]
    volumes:
      - ./otel-collector-config.yaml:/etc/otelcol/config.yaml
    ports:
      - "4317:4317"   # OTLP gRPC
      - "4318:4318"   # OTLP HTTP
  jaeger:
    image: jaegertracing/all-in-one:1.55
    environment:
      - COLLECTOR_OTLP_ENABLED=true
    ports:
      - "16686:16686"  # Jaeger UI
  grafana:
    image: grafana/grafana:10.4.2
    ports:
      - "3000:3000"
    volumes:
      - ./grafana-datasources.yaml:/etc/grafana/provisioning/datasources/ds.yaml

# 启动追踪栈
docker compose -f docker-compose.observability.yaml up -d

# 验证：访问 Jaeger UI 应能看到 order-service 的 Trace
open http://localhost:16686

# 发一个测试请求，然后在 Jaeger 里按 trace-id 查询
curl -X POST http://localhost:8080/api/v1/orders \
  -H "Content-Type: application/json" \
  -d '{"user_id":"u1","items":[{"product_id":"p1","quantity":1}]}'

# 用 jaeger 自带 CLI 查询最近的 Trace
docker exec jaeger curl -s "http://localhost:16686/api/traces?service=order-service&limit=5" | jq

三大支柱如何联动

Trace、Metrics、Logs 不是孤立的：在 Grafana 里，一个 P99 延迟升高的监控告警，可以一键跳转到 Jaeger 看是哪段 Span 慢；Jaeger 里的某个错误 Span，可以一键跳转到 Loki 查当时那台机器的结构化日志。这一切的桥梁是 TraceID——所以生产规范要求：每个服务的每一行日志都必须带 TraceID。

# 结构化日志必须带 trace_id/span_id（zap/slog 示例）
# 输出形如: {"ts":"...","level":"error","msg":"db timeout",
#           "trace_id":"abc123","span_id":"def456","sql":"INSERT orders"}
# 这样 ELK/Loki 可以按 trace_id 拉出一次请求的完整日志链

最佳实践

  • 采样策略用尾部采样：错误、超时、慢请求 100% 保留，成功请求按 5% 采样。这样存储成本可控，出问题时又一定能查到。
  • Span 标签要克制：不要把整个请求体塞进 tag（高基数 + 存储爆炸）。只放用户 ID、订单号、错误码这种"高选择性"字段。
  • 关键调用必须打 Span：HTTP handler、gRPC 方法、DB 查询、Redis 调用、MQ 生产/消费——这五类是必打点的，框架一般都有 instrumentation 库自动埋。
  • 告警基于 Red 指标：Request 量、Error 率、Duration（P99）。每个服务必须有这三个面板，SLO 用它们定义。
  • 本地开发也要能看 Trace：起一个 Jaeger all-in-one 容器，开发者本地跑服务就能在 UI 里看到自己这次请求的完整链路，别把追踪当成"上线后才有"的奢侈品。

FAQ

Q1：OpenTelemetry、Jaeger、Zipkin 是什么关系？

OpenTelemetry 是标准和 SDK（埋点、上报协议），Jaeger/Zipkin 是存储和后端。业务代码只依赖 OpenTelemetry，上报到 Collector，Collector 再转发到 Jaeger 或 Zipkin。以后想换后端（比如从 Jaeger 换到 Grafana Tempo），业务代码一行不改。

Q2：全量追踪一台服务一天要多少存储？

经验值：10 万 QPS 的服务，全量追踪一天约 200-500GB（取决于 Span 大小）。所以生产几乎必须采样：头部 10-20% + 错误/慢请求 100% 尾部保留，存储能压到原来的 1/10。

Q3：TraceID 在异步消息（Kafka）里怎么传？

把 TraceContext 放进消息 Header（Kafka header / RabbitMQ headers），消费端从 header 里提取并继续传递。这是 OpenTelemetry 规范明确支持的，不要只在 HTTP 链路传，异步链路断了 Trace 就断了。

Q4：我们日志已经够多了，有了 Trace 还要不要结构化日志？

要。Trace 回答"请求在哪慢了/错了"，日志回答"这一步具体做了什么、入参出参是什么"。两者互补：Trace 是导航地图，日志是路况细节。而且结构化日志带 trace_id 后，可以和 Trace 双向跳转，体验远好于纯文本日志。

总结

可观测性是微服务的"神经系统"：没有它，服务数量越多，系统越是一个不可理解的黑盒。Trace 串起一次请求的完整路径，Metrics 告诉你系统整体健康度，Logs 提供细节现场——三者通过 TraceID 联动，才是完整的可观测性。至此，微服务架构六篇全部完成：从设计原则 → DDD 拆分 → 网关与注册 → 配置与事务 → 熔断降级 → 可观测性，一套完整的微服务工程闭环已经搭好，祝你的下一次上线不再熬夜。
