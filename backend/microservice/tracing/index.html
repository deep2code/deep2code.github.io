链路追踪落地：四类排查场景、依赖拓扑反推与关键路径分析

🏷️ 链路追踪

大部分团队接完链路追踪就停在「能看到瀑布图了」，然后就没人再打开它。原因是没搞清楚这套数据能回答什么问题、不能回答什么问题。这篇不讲 Span 数据模型、SpanKind、W3C 上下文传播的断链细节、头部与尾部采样的对比、Collector pipeline 配置——这些站内 OpenTelemetry 实战已经写透。这篇只讲一件事：拿到链路数据之后能解决什么问题，以及落地时真正卡住你的工程与组织问题。

一、链路能回答而指标和日志回答不了的四类问题

问题为什么指标答不了为什么日志答不了拿到链路后的具体动作
这一次慢请求的时间花在哪一跳指标是聚合值，只能说「入口 P99 从 200ms 涨到 900ms」，无法拆到跳日志是单服务视角的片段，跨服务无法对齐按 traceID 打开瀑布图，按 span 自身耗时排序，找出耗时最大且不含子 span 的那一段
这个接口实际依赖了哪些下游指标只有你主动埋了的调用维度日志里不会系统性记录出向调用按入口 operation 聚合最近 N 条链路里出现过的下游服务集合，与架构图对比
有没有循环调用和 N 加 1 远程调用指标看到的是总调用量，看不出调用模式日志里散落的调用记录无法还原父子关系按 trace 统计同名 span 数量的最大值，以及检查 span 路径上是否出现重复的服务名
某个服务出问题的影响范围有多大指标只能看到该服务自身的错误率日志无法反查调用方用该服务的 span 反查所有包含它的 trace，聚合出入口接口清单与上游服务清单

反过来说，有四类问题不该指望链路：成功率、QPS、延迟分位数（这些必须来自全量指标）、以及某一次失败的详细堆栈（这个属于日志）。三类信号的分工与串联方式：

flowchart TB Q1{"你要回答的是什么问题"} -->|接口的成功率、QPS、延迟分位| M["指标：全量统计、可告警、存储便宜"] Q1 -->|这一次请求的时间花在哪一跳| T["链路：抽样、结构化、只用于定位与分析"] Q1 -->|这次失败的具体原因与堆栈| L["日志：细节最全、量最大、成本最高"] M --> X["三者必须靠 traceID 与 exemplar 串起来
否则每一步都要重新人肉对齐"] T --> X L --> X

二、一次「接口 P99 突然变高」的完整排查路径

sequenceDiagram participant V as 值班工程师 participant G as 指标看板 participant J as 链路后端 participant O as 订单服务日志 participant D as 营销服务日志 V->>G: 收到告警，入口 P99 从 220ms 涨到 900ms G-->>V: 确认异常范围：只有下单接口，错误率没涨 Note over V,G: 错误率不涨而延迟涨
说明下游在变慢而不是报错 V->>G: 从 P99 直方图桶上点开 exemplar G-->>V: 给出几个落在慢桶里的样本 traceID V->>J: 按 traceID 展开瀑布图 J-->>V: 营销服务的 span 占了 620ms，其余各跳正常 V->>D: 用同一个 traceID 过滤营销服务日志 D-->>V: 命中一条慢查询日志，缓存未命中后回源数据库 V->>O: 反查订单服务这一跳是否有重试放大 O-->>V: 无重试，确认根因在营销服务的缓存失效 Note over V,D: 全程三步：指标发现、链路定位、日志下钻
串联它们的唯一钥匙是 traceID

这条路径能走通的前提只有一个：traceID 同时出现在指标的 exemplar、链路数据和日志里。三者缺任何一环，排查就会退化成猜。而其中把 traceID 注入日志是整套可观测性里投入产出比最高的一步——成本是改一行日志格式，收益是把跨服务日志对齐从不可能变成一次过滤。

# Spring Boot 3 + OpenTelemetry Java Agent：Agent 会自动把 trace_id / span_id 写入 MDC，
# 这里只需要把它们打进日志格式。注意 %mdc 的 key 名取决于 Agent 版本与配置，
# OTel Agent 默认是 trace_id 与 span_id，Sleuth 时代是 traceId 与 spanId，升级时容易踩。
logging.pattern.level=%5p [trace_id=%mdc{trace_id} span_id=%mdc{span_id}]

# 结构化日志（推荐）：直接输出 JSON，让采集侧把 trace_id 建成索引字段而不是全文检索
logging.structured.format.console=ecs
logging.structured.ecs.service.name=order-service

# 让 Agent 把日志也一并导出（可选，量大时更适合仍走文件采集）
otel.logs.exporter=otlp
otel.instrumentation.logback-mdc.enabled=true

# 打开 Micrometer 的 exemplar 支持：直方图桶上会挂样本 traceID，
# Grafana 里就能从指标图直接跳到具体链路。这是打通指标与链路的关键开关。
management.metrics.distribution.percentiles-histogram.http.server.requests=true
management.prometheus.metrics.export.properties.exemplars.enabled=true

三、用链路反推依赖拓扑：比架构图准

人工维护的架构图在第二个月就开始失真，而链路数据是从真实流量里长出来的。把最近一段时间的 span 按调用方与被调方聚合，就能自动生成调用拓扑，然后拿它和架构图对比，通常能发现三类问题。

flowchart TB subgraph EXP["架构图上画的依赖"] A1["订单服务"] --> A2["库存服务"] A1 --> A3["支付服务"] end subgraph REAL["链路数据里真实存在的依赖"] B1["订单服务"] --> B2["库存服务"] B1 --> B3["支付服务"] B1 --> B4["用户服务：只为取一个昵称，同步阻塞在主链路上"] B1 --> B5["营销服务：某次活动临时加的，活动早就结束了"] B2 --> B6["风控服务：库存服务自己的人也说不清谁加的"] B3 --> B1 end REAL --> F1["三类可执行的结论"] F1 --> F2["多余依赖：能去掉或改异步的直接砍掉"] F1 --> F3["循环依赖：支付回调订单形成环，必须拆开"] F1 --> F4["跨层调用：底层服务反向依赖上层，分层被破坏"]

这张自动拓扑图还有一个高价值用途：变更影响面评估。要动某个服务的接口时，反查最近 7 天所有经过该 span 的链路，就能得到准确的调用方清单和受影响入口接口清单，比在群里喊「谁在调我这个接口」可靠得多。同样，故障期间拿着出问题的服务反查，能立刻给出影响范围用于对外通告。

四、N 加 1 远程调用：微服务最常见的性能问题

单体时代的 N 加 1 是 N 次 SQL，代价是几毫秒；微服务里的 N 加 1 是 N 次跨网络调用，单次就是几毫秒到几十毫秒，循环 50 次就是秒级。它在指标上完全看不出来（总调用量高但每次都很快），在链路上却极其明显。

维度链路上的表现怎么查修复方向
列表页逐个查详情同一父 span 下几十个同名子 span，每个 5ms 到 20ms，串行排列按 trace 分组统计同名 span 数量的最大值，超过 10 就复查下游提供批量接口，一次取回；这是首选方案
循环里查配置或字典同名 span 数量与列表长度严格成正比对比 span 数量与业务字段数量的相关性本地缓存，配合失效通知；字典类数据缓存收益最大
嵌套循环调用span 数量随两个维度相乘增长，几百个子 span看 span 数量是否出现平方级增长先批量取外层，再批量取内层，必要时冗余数据
改成并行后仍然慢span 数量不变，但变成并行排列，墙上时间下降看下游服务的 QPS 是否同步暴涨这不是修复：下游压力一点没减，只是把串行等待改成瞬时并发冲击
# 1) 用 Jaeger API 捞出 span 数量异常多的链路（span 总数是最简单有效的筛选条件）
curl -s "http://jaeger:16686/api/traces?service=order-service&operation=POST%20/order/create&limit=200&lookback=1h" \
  | jq -r '.data[] | "\(.traceID) spans=\(.spans | length)"' \
  | sort -t= -k2 -nr | head -20
# 正常链路的 span 数应该稳定在一个范围。出现 200 个 span 的链路，
# 基本可以断定是循环里发起了远程调用。

# 2) 对某条链路统计各 operationName 的出现次数，一眼看出是谁被调了 N 次
curl -s "http://jaeger:16686/api/traces/4bf92f3577b34da6a3ce929d0e0e4736" \
  | jq -r '.data[0].spans[].operationName' | sort | uniq -c | sort -nr | head
#   57 GET /user/profile      <- 这就是 N 加 1
#    1 POST /order/create

# 3) 如果 span 存在 ClickHouse（SigNoz、Uptrace 等方案），直接 SQL 更方便做治理报表
clickhouse-client -q "
SELECT service_name, name AS span_name,
       max(cnt) AS max_per_trace, count() AS trace_cnt
FROM (
  SELECT trace_id, service_name, name, count() AS cnt
  FROM signoz_traces.distributed_signoz_index_v2
  WHERE timestamp > now() - INTERVAL 1 HOUR
  GROUP BY trace_id, service_name, name
)
GROUP BY service_name, span_name
HAVING max_per_trace > 10
ORDER BY max_per_trace DESC LIMIT 20"

五、关键路径：一条链路的总耗时不等于各 span 之和

这是看瀑布图时最容易犯的错：把所有 span 耗时加起来找最大的那个去优化。有并行调用时这个做法会把你带偏。

flowchart TB S["入口 span：下单接口，总耗时 800ms"] --> P1["鉴权与参数校验 30ms"] P1 --> PAR{"并行发起三个下游调用"} PAR --> C1["用户服务 40ms"] PAR --> C2["库存服务 180ms"] PAR --> C3["营销服务 620ms"] C1 --> J["汇聚等待：本段耗时等于最慢的一支，即 620ms"] C2 --> J C3 --> J J --> W["写订单与发消息 150ms"] W --> E["关键路径为 30 加 620 加 150 等于 800ms
而各 span 之和为 1020ms，二者不相等"]

结论很直接：只有落在关键路径上的 span 才值得优化。把库存服务从 180ms 优化到 20ms，端到端延迟一点不变，因为它藏在营销服务的 620ms 后面。优化完营销服务之后关键路径会切换——比如营销降到 100ms 后，关键路径变成 30 加 180 加 150，此时库存才轮到优化。所以每轮优化后都要重新做一次关键路径分析，而不是按第一次的排序一路做下去。

六、采样带来的分析限制：绝对量没有统计意义

❌
不要用链路数据算成功率和 QPS

生产采样率通常是 1% 或更低，在这个数据集上做绝对量统计毫无意义：算出来的 QPS 会差两个数量级。成功率更危险——尾部采样策略几乎都会配置为「优先保留出错的和慢的链路」，于是采样后的数据集里错误链路的占比被系统性放大，直接算成功率可能得到 20% 这种荒谬数字，然后有人拿着它去开故障复盘会。能从链路数据得到的是结构信息（依赖关系、调用次数模式、耗时构成、关键路径），不是统计量。统计量一律来自全量指标。

你想算的东西能不能用链路数据正确来源
接口 QPS、调用总量不能，采样后绝对量失真指标（服务端与客户端各埋一份便于交叉验证）
成功率、错误率不能，尾部采样使错误占比被放大指标，按状态码维度
延迟 P50 / P99不建议，头部采样可用但精度不足，尾部采样会严重偏高指标直方图
一次请求的耗时构成能，这是链路的主场链路
依赖拓扑、循环依赖能，只要采样足够覆盖各条路径链路聚合
某模式出现的相对比例（如有多少链路存在 N 加 1）可以做趋势判断，不要报绝对数量链路聚合，并注明采样率

七、采样率与存储成本的量级估算

先把数量级算清楚再谈采样率，否则要么被账单教育，要么把采样率压到没法排查。按一个中等规模系统估算：入口 1000 QPS，一次请求平均产生 25 个 span（含 HTTP 服务端与客户端、RPC、数据库、缓存、消息），每个 span 落盘后约 400 字节。

采样率每秒 span 数每天原始数据量保留 7 天适用
100%25000约 864 GB约 6 TB只适合压测环境或短时排障开窗
10%2500约 86 GB约 600 GB核心链路，或 QPS 较低的系统
1%250约 8.6 GB约 60 GB大多数生产系统的默认档
0.1% 加尾部保留异常25 加异常部分约 1 GB 加异常约 7 GB 加异常超大流量系统，靠尾部采样保住有价值的链路

两条实践经验：采样决策必须整条链路一致，否则会出现半条链路有数据的情况（这类断链的成因与传播细节见站内 OpenTelemetry 篇）；attributes 的体积常常比 span 数量更能决定成本，把请求体、响应体、SQL 全文塞进 attributes，单个 span 能从 400 字节涨到几十 KB，存储直接爆炸。

八、落地的真正难点是组织问题

技术上接一个 SDK 是一天的事，难的是全公司几十上百个服务都接、并且接得一致。这里有一个硬约束：链路只要有一个服务不埋点，就在那里断掉，它后面的服务再完整也拼不回来。所以埋点无法靠「各团队自愿推进」，必须自上而下统一。

治理项错误做法正确做法衡量指标
SDK 与版本各团队自选实现与版本统一 SDK 与基线版本，统一上下文传播格式，升级由平台推动基线版本覆盖率
埋点方式要求业务代码里手动开 span在框架层与基础库默认埋点：HTTP 服务端与客户端、RPC、连接池、MQ 生产消费、定时任务默认埋点框架覆盖率
采样配置各服务自己配，互相不一致平台统一下发，支持按服务和按接口覆盖，但决策整链一致配置一致性巡检通过率
链路完整性无人度量，出事才发现断链把链路完整率做成治理指标：统计有多少比例的链路存在断点，以及断点集中在哪些服务链路完整率，按服务归因
日志关联部分服务打了 traceID，部分没打统一日志格式规范，把 trace_id 作为必填字段并在采集侧建索引日志带 traceID 的比例
异步场景线程池、消息消费不传上下文在统一的线程池封装与 MQ 客户端里内置上下文传递异步断链数量

异步场景是断链最集中的地方，而且它通常不是「没埋点」，而是「上下文没跟着任务走」。下面这段 Go 代码展示了三个最常见的异步坑及其正确写法。

package order

import (
	"context"
	"time"

	"go.opentelemetry.io/otel"
	"go.opentelemetry.io/otel/attribute"
	"go.opentelemetry.io/otel/trace"
)

var tracer = otel.Tracer("order-service")

// 坑一：goroutine 里用 context.Background()，链路直接断在这里
func badAsync(ctx context.Context, id int64) {
	go func() {
		// 错误：新建的根 context 没有 SpanContext，这个 goroutine 的 span 成了孤儿
		_ = sendNotify(context.Background(), id)
	}()
}

// 正确：把父 context 传进 goroutine。注意请求级 ctx 会随响应返回而被取消，
// 所以要剥离取消信号但保留 trace 上下文，否则异步任务会被提前掐断。
func goodAsync(ctx context.Context, id int64) {
	asyncCtx := trace.ContextWithSpanContext(
		context.WithoutCancel(ctx),          // go 1.21+，保留值、去掉取消与 deadline
		trace.SpanContextFromContext(ctx),
	)
	go func() {
		// 异步任务另起一个 span，并用 links 标明它由哪次请求触发，
		// 这样既不会把异步耗时算进同步链路的关键路径，又保留了因果关系
		c, span := tracer.Start(asyncCtx, "async.sendNotify",
			trace.WithLinks(trace.Link{SpanContext: trace.SpanContextFromContext(ctx)}))
		defer span.End()

		c, cancel := context.WithTimeout(c, 3*time.Second) // 异步任务同样必须有超时
		defer cancel()
		if err := sendNotify(c, id); err != nil {
			span.RecordError(err)
		}
	}()
}

// 坑二：往 span 上挂大对象。attributes 会被完整落盘，单 span 从几百字节涨到几十 KB。
// 只记可用于检索和归因的低基数或短值，请求体、响应体、SQL 全文一律不要进 attributes。
func annotate(span trace.Span, req *CreateReq) {
	span.SetAttributes(
		attribute.Int64("order.user_id", req.UserID),   // 可检索、短
		attribute.String("order.channel", req.Channel), // 低基数
		attribute.Int("order.item_count", len(req.Items)),
	)
	// 反例：span.SetAttributes(attribute.String("order.raw_body", string(body)))
}

// 坑三：给每个内部方法都埋 span。span 数量失控后成本暴涨，瀑布图也没法看。
// 判断标准：只给跨进程边界、跨中间件、以及耗时可能超过 10ms 的本地计算埋 span。
✅
链路完整率：一个值得单独建的治理指标

定义为「不存在断点的链路数除以总链路数」。断点的判定方式：某个 span 声明了出向调用（有 client 类型的子 span 或有出向 HTTP 客户端埋点）却找不到对应的 server 端 span。把这个指标按「断点所在服务」归因后，治理对象立刻清晰：排名前十的服务就是接下来要推动埋点的对象。没有这个指标时，链路质量靠感觉，推进埋点靠人情；有了它之后，它可以直接进各团队的技术指标。

九、反模式清单

反模式后果正确做法
把业务数据全塞进 span attributes单 span 体积涨几十倍，存储与查询成本失控，还可能泄露敏感数据只放可检索的短值与低基数字段，大对象放日志并用 traceID 关联
给每个方法都埋 span单链路几百个 span，瀑布图无法阅读，成本暴涨只埋跨进程边界、中间件调用、以及耗时可能超过 10ms 的本地计算
只在网关埋点只能知道「入口慢了」，内部完全是黑盒，等于没有链路框架层默认埋点，保证每一跳都有 span
用链路数据做告警数据是抽样的，告警会既漏报又误报，且链路后端通常不保证实时性告警一律基于指标，链路只用于告警之后的定位
异步任务不传上下文链路断裂，异步失败无法归因到触发它的请求在统一线程池封装与 MQ 客户端里内置上下文传递，并用 links 表达因果
把异步耗时算进同步链路关键路径分析被污染，误判优化方向异步任务独立成 trace 并用 links 关联，不作为子 span 计入父 span 耗时
traceID 不进日志排查链条在最后一步断掉，只能靠时间戳人肉对齐统一日志格式，trace_id 作为必填字段并建索引
各服务采样率不一致出现半条链路有数据的情况，分析时反复怀疑是不是埋点漏了采样决策整链一致，由平台统一下发
❌
链路追踪落地最容易踩的坑

1. 用抽样的链路数据算成功率和 QPS，得出荒谬结论还拿去开复盘会。
2. 只在网关和入口埋点，内部调用全黑盒，出问题只知道慢在「后面」。
3. traceID 没有注入日志，链路定位到某一跳之后无法继续下钻。
4. 升级 SDK 后 MDC 的 key 名从 traceId 变成 trace_id，日志格式没跟着改，traceID 字段变空。
5. 线程池和消息消费不传递上下文，异步部分的链路全部断掉。
6. 用 context.Background() 起 goroutine，span 成孤儿；或直接复用请求 ctx，导致响应返回后异步任务被取消。
7. 把异步任务当同步子 span，父 span 耗时被拉长，关键路径分析完全失真。
8. 把请求体、响应体、SQL 全文写进 span attributes，存储成本涨几十倍还带来数据合规风险。
9. 给每个内部方法都埋 span，单链路几百个 span，既贵又没法看。
10. 拿各 span 耗时之和排序找优化点，结果优化了并行分支上的调用，端到端延迟毫无变化。
11. 把 N 加 1 的串行调用改成并行就宣布优化完成，下游压力一点没降，只是换成了瞬时并发冲击。
12. 用链路数据配告警，抽样导致漏报，尾部采样导致误报。
13. 各服务采样率与采样方式不统一，出现半条链路，排查时反复怀疑埋点有问题。
14. 没有链路完整率指标，链路质量靠感觉，推进埋点靠人情，一年后还是断的。
