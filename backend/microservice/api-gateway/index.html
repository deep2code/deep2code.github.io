API 网关的责任边界：不放业务逻辑、流量治理与重试风暴

🏷️ API 网关

网关是全站唯一一个所有流量都必经的组件，也是最容易被写坏的组件。写坏的方式几乎总是同一个：因为它能看到所有请求，大家就不断往里塞逻辑，直到它变成一个所有团队都要改、谁改都可能全站故障的巨型单点。这篇不讲「网关是统一入口」这种人人都会背的定义，只讲两件事：网关的责任边界到底划在哪里，以及网关自带的那几个危险功能（重试、超时、限流）怎么配才不会把小故障放大成全站故障。

网关底层的 Nginx 实现细节——11 个请求处理阶段与 location 匹配优先级、proxy_buffering 的内存与磁盘行为、上游长连接三件套、limit_req 的三种形态——站内 Nginx 核心原理已经写透，这里不重复，只在需要时引用结论。

一、一个请求穿过网关的完整责任链

把网关拆开看，它其实是一串有严格先后顺序的处理阶段。顺序不能随便调：限流必须在认证之前（否则伪造令牌的洪水会把你的验签 CPU 打满），路由匹配必须在协议转换之前（不知道去哪就不知道转成什么协议），日志必须在最后（否则记不到最终响应码）。

能力归属判定理由放错位置的后果
TLS 终止、证书管理网关与业务语义完全无关，且证书轮换需要集中管理放服务里意味着几十个服务各自续证书，必然漏掉某个
IP 级 / 用户级限流网关为主，服务兜底网关能看到全局流量，但服务必须有自我保护只在网关限流时，内网调用和定时任务能绕过一切保护
认证（你是谁）网关验签逻辑与业务无关，且能挡掉无效流量不进内网放服务里则每个服务都要引验签 SDK，密钥轮换变成跨团队工程
鉴权（你能操作这个资源吗）业务服务需要查资源归属，网关拿不到这个数据网关必须连业务库，从此表结构一改网关就要发版
路由与灰度分流网关只依赖 host、path、header、用户 ID 哈希放服务里则灰度要靠代码里的 if，下线时无人敢删
协议转换网关纯粹的编解码转换，规则由 IDL 生成放服务里等于每个服务都要同时支持两套协议栈

业务规则校验（库存是否充足）业务服务需要读业务状态网关变成业务代码的第二份副本，且永远不同步
响应字段裁剪与多接口聚合BFF跟端的需求变化同频，不该拖慢网关发布网关发布频率被前端需求绑定，成为发布瓶颈
兜底数据、有损降级业务服务只有业务知道什么是可以牺牲的网关返回的兜底数据往往与业务语义不符，引发数据错乱

二、最重要的设计原则：网关里不放业务逻辑

这条原则被说了无数遍，但几乎每个团队都会违反，因为违反它的收益是立刻的（在网关加个 if 半小时上线，改五个服务要一周），代价是延后的。代价长什么样：

  • 发布冲突：网关配置变成所有团队的共享可写资源。A 团队的灰度规则和 B 团队的限流规则在同一次发布里，A 出问题回滚会把 B 的改动一起带走。
  • 故障半径失控：某个业务的一段判断逻辑写错，影响的不是那一个业务，而是全站所有流量。网关上一行代码的空指针，等于整站 502。
  • 无人敢动：两年后网关插件里躺着三百条业务规则，没人知道哪条还有用。删一条要找五个团队确认，最后的选择永远是不删。
❌
网关正在变成业务代码的三个识别信号

信号一：网关配置或插件代码里出现了具体业务字段名，比如 if (body.merchantType == 3)、if (path == "/order/refund" && amount > 10000)。信号二：网关需要访问业务数据库、业务缓存或调用业务 RPC 来做判断，一旦出现这种依赖，网关的可用性就被业务库的可用性绑死了。信号三：网关的发布频率和业务服务一样高，健康的网关一个季度发几次版，如果它一周发三次，说明业务需求已经堵在网关上了。三个信号出现任何一个，就该把逻辑往下推到 BFF 或业务服务。

遇到拿不准的能力，用这张判断图过一遍：

三、认证在网关，鉴权在服务

这是网关责任划分里最常被搞混的一对。认证（Authentication）回答「你是谁」，鉴权（Authorization）回答「你能不能做这件事」。前者的输入是令牌，输出是用户身份，纯计算，与业务无关；后者的输入是用户身份加上具体资源，必须查这个资源归谁、现在什么状态。

维度认证（网关做）鉴权（业务服务做）
输入Authorization 头、Cookie、API Key、mTLS 客户端证书可信用户身份 + 资源 ID + 操作类型
依赖数据公钥或密钥（可缓存，几乎不变）资源归属表、组织架构、角色权限表
典型实现JWT 验签 + 过期校验 + 黑名单查询查订单的 owner 是否等于当前用户，或走 RBAC / ABAC 引擎
失败响应401 Unauthorized403 Forbidden，或为防探测统一返回 404
能否前置到网关必须前置，越早挡掉无效流量越省资源不能，网关不知道资源归属
网关能做的最大粒度路由级：这个接口要不要登录、允不允许外网访问对象级：这个用户能不能退这一笔款

网关认证完要把身份传给下游，这里有一个高频安全漏洞：忘记剥离客户端自己带上来的身份头。如果网关注入 X-User-Id，而下游服务无条件信任这个头，那么攻击者只要自己带一个 X-User-Id: 1，在网关没有覆盖它的情况下就直接变成了管理员。

# 网关侧：注入身份之前，必须先把客户端可能伪造的同名头清空
# 顺序很关键：先置空再赋值。只写 proxy_set_header 赋值在多数场景下也会覆盖，
# 但一旦某条 location 走了不同的 header 传递路径（比如 proxy_pass_request_headers on
# 配合上游自定义逻辑），漏掉置空就会留下伪造入口。显式清空是零成本的保险。
proxy_set_header X-User-Id    "";
proxy_set_header X-User-Roles "";
proxy_set_header X-Tenant-Id  "";

location /api/ {
    # auth_request 把令牌交给认证服务校验，返回 200 才继续
    auth_request      /_auth;
    # 从认证服务的响应头里取出身份，写入变量
    auth_request_set  $authed_user  $upstream_http_x_authed_user;
    auth_request_set  $authed_roles $upstream_http_x_authed_roles;

    # 注入可信身份。下游只信任这几个头，且下游必须部署在网关之后不可直连
    proxy_set_header  X-User-Id    $authed_user;
    proxy_set_header  X-User-Roles $authed_roles;
    # 把 traceID 一并下传，下游日志靠它串联
    proxy_set_header  X-Request-Id $request_id;

    proxy_pass http://backend_upstream;
}

location = /_auth {
    internal;                       # 只允许内部子请求访问
    proxy_pass              http://auth_service/verify;
    proxy_pass_request_body off;    # 认证不需要请求体，省一次内存拷贝
    proxy_set_header        Content-Length "";
    proxy_set_header        X-Original-URI $request_uri;
}
⚠️
「网关已经鉴权了，服务内部就不用校验」是错的

这个假设成立的前提是业务服务绝对不可能被绕过网关访问，而现实里几乎总有旁路：同机房的内网直连、定时任务直接调 Service 名、另一个服务为了省一跳直连你的 Pod、压测流量从内部打入、运维用 kubectl port-forward 调试。只要有一条旁路，纯网关鉴权就等于没有鉴权。正确姿势是网关负责挡掉外部无效流量，服务内部仍然做资源级校验，并且用 mTLS 或内网 Token 保证「这个请求确实来自网关」。

四、网关选型：先问谁运维它

选型讨论最容易跑偏成性能跑分比较，而真实的决定因素通常是「出故障时谁能在五分钟内看懂配置并改对」。下面这张表按实际关心的维度对照。

✅
三条能直接用的选型结论

一、Java 团队、流量在每秒几千级、需要在网关里写少量自定义逻辑，选 Spring Cloud Gateway，同一套 JVM 监控和发布流程省下的运维成本远大于吞吐差距。二、流量上到每秒几万、且要求配置秒级生效并且插件按需拼装，选 APISIX 或 Kong，二者都是 OpenResty 系，差别主要在控制面形态和商业支持。三、已经在用或计划用服务网格，直接上 Envoy 做边缘网关，让边缘和 Sidecar 共用同一套 xDS 配置模型和可观测性口径，否则你会维护两套不一致的流量治理规则。

五、BFF 与网关的分工

BFF（Backend For Frontend）是很多团队上了网关之后仍然缺的一层。它解决的问题网关解决不了：端上一屏需要五个后端接口的数据，直接让 App 发五个请求在弱网下体验极差，而让某个领域服务去聚合又会让它依赖一堆不相关的服务。

维度API 网关BFF
职责横切关注点：安全、流量、路由、可观测端侧适配：多接口聚合、字段裁剪、结构重塑
是否感知业务不感知，看到的是字节流深度感知，知道首屏要哪些字段
实例数量全站一套（可按内外网拆两套）按端拆，iOS / Android / Web / 大屏 各一套或按业务线拆
变更频率低，一个季度几次高，和前端迭代同频，一周多次
谁维护基础架构团队前端团队或端侧业务团队（见下）
故障半径全站单个端或单个业务线
典型技术栈APISIX / Envoy / Spring Cloud GatewayNode.js、Go，或 GraphQL 网关

BFF 该由谁维护是个组织问题：由前端团队维护能让「加个字段」这种需求不用跨团队排期，收益最大，但前提是前端团队具备服务端运维能力（日志、监控、容量、发布回滚、值班）。如果不具备，BFF 会变成一个没人看监控的定时炸弹。折中做法是基础架构提供统一的 BFF 运行时和脚手架（含默认埋点、熔断、限流、发布流水线），前端只写聚合逻辑，运行时的稳定性由平台负责。

六、流量治理：灰度、蓝绿、影子流量

这是网关最有价值的能力，因为它是全站唯一能在不改任何业务代码的前提下改变流量走向的位置。

分流方式配置依据适用场景坑
按 header 分流请求头里的特定标记，如 X-Env: canary内部测试、QA 验证、特定合作方先行头必须在全链路传递，否则灰度只覆盖第一跳
按用户 ID 取模用户 ID 哈希后取模，如 mod 100 小于 5需要「同一个用户始终落同一版本」的灰度未登录请求没有用户 ID，会全部落到默认分支导致比例失真
按百分比随机权重，如 新版 5、旧版 95无状态接口的快速验证同一用户两次请求可能落不同版本，有状态流程会出错
蓝绿切换整组上游一次性切换大版本、数据库结构已兼容双版本需要双倍资源，且回滚时新版写入的数据要能被旧版读懂
影子流量复制一份请求到新版，丢弃其响应性能压测、新实现的正确性比对影子流量绝不能写生产库，必须有独立存储或全链路影子标记

以 APISIX 的 traffic-split 为例，下面这段配置同时做了「内部头优先」和「用户 ID 取模 5%」两层灰度，这是生产上最常见的组合——先让内部验完，再放 5% 真实用户。

{
  "uri": "/api/order/*",
  "plugins": {
    "traffic-split": {
      "rules": [
        {
          "match": [
            { "vars": [ ["http_x_env", "==", "canary"] ] }
          ],
          "weighted_upstreams": [
            { "upstream_id": "order-canary", "weight": 1 }
          ]
        },
        {
          "match": [
            { "vars": [ ["arg_uid", "!", "~~", "^$"] ] }
          ],
          "weighted_upstreams": [
            { "upstream_id": "order-canary", "weight": 5 },
            { "weight": 95 }
          ]
        }
      ]
    },
    "proxy-mirror": {
      "host": "http://order-shadow.internal:8080",
      "sample_ratio": 0.05
    }
  },
  "upstream_id": "order-stable"
}

关于这段配置的三个要点：第一，rules 是有序的，命中第一条就不再往下走，所以内部头规则必须写在百分比规则前面；第二，第二条规则里省略 upstream_id 的那一项表示走路由默认上游，这是 APISIX 表达「剩余 95% 走旧版」的写法；第三，proxy-mirror 复制出的影子请求会被网关忽略响应，但下游是真的收到了——影子集群必须连影子数据库，否则 5% 的写请求会污染生产数据，这个坑踩过的团队不少。

七、重试是网关最危险的功能

重试的直觉是「失败了再试一次，成功率更高」。这个直觉在下游健康时成立，在下游过载时完全反转：重试的流量放大系数等于 1 + 重试次数，而它恰好在下游最脆弱的时刻生效。

sequenceDiagram participant C as 客户端 participant G as 网关 participant O as 订单服务 participant S as 库存服务 C->>G: 稳定 1000 QPS G->>O: 转发 1000 QPS O->>S: 1000 QPS，P99 约 50ms Note over S: 一次慢 SQL 上线
P99 从 50ms 涨到 900ms S--xO: 部分请求超过 800ms 超时 O--xG: 返回 504 G->>O: 网关按配置重试 2 次 O->>S: 实际到达 2800 QPS Note over S: 排队队列变长
更多请求突破超时阈值 G->>O: 超时比例上升，重试量继续上升 O->>S: 压力逼近 3 倍额定容量 Note over G,S: 放大系数 1 加重试次数
下游越慢重试越多，是自我强化的正反馈 S--xO: 全面失败 O--xG: 全面失败 G--xC: 502，且下游即使修好也起不来

最后一句是重点：重试风暴形成后，即使根因（慢 SQL）已经修复，下游也会被持续的三倍流量压住起不来，必须先在网关侧关掉重试或打开熔断，给下游一个恢复窗口。这也是为什么重试开关必须能热切换。

配置项常见错误配法推荐配法原因
重试次数3 次甚至更多1 次，最多 2 次第 2 次之后的成功率提升微乎其微，放大系数却线性增长
重试条件所有 5xx 和超时都重试只重连接失败、连接超时、明确的 503；已发出请求的读超时不重试读超时意味着下游可能已经执行了，重试非幂等操作会造成重复扣款重复下单
重试方法不区分方法只对 GET / HEAD / PUT / DELETE 等幂等方法重试，POST 必须显式带幂等键才重试幂等落地方式见站内 分布式系统核心
退避策略立即重试指数退避加随机抖动，基数 20ms 到 50ms无抖动的退避会让所有重试在同一时刻撞上下游，形成新的尖峰
重试预算不配重试请求占总请求比例上限 10% 到 20%这是唯一能真正封顶放大系数的机制，次数限制做不到
与熔断联动各自独立熔断打开期间禁止重试；重试产生的失败也要计入熔断统计否则熔断刚半开，重试流量就把它重新打死
多层重试网关重试 3 次，RPC 框架重试 3 次全链路只有一层重试，通常放在最接近调用方的一层多层重试是相乘关系，3 乘 3 等于 9 倍流量

Envoy 是把重试预算做成一等公民的少数网关之一，配置长这样：

# Envoy route 级重试策略 + cluster 级重试预算
route:
  cluster: order-service
  timeout: 2s                       # 整条路由的总超时，包含所有重试
  retry_policy:
    retry_on: "connect-failure,refused-stream,unavailable,retriable-status-codes"
    retriable_status_codes: [503]   # 注意没有 500 和 504：它们可能意味着下游已执行
    num_retries: 1                  # 只重一次
    per_try_timeout: 800ms          # 单次尝试超时，必须小于 timeout 的一半
    retry_back_off:
      base_interval: 25ms           # Envoy 自动加抖动，实际间隔在 base 到 max 之间
      max_interval: 250ms
    retry_host_predicate:
      - name: envoy.retry_host_predicates.previous_hosts   # 不要重试到刚失败的那台
    host_selection_retry_max_attempts: 3

clusters:
  - name: order-service
    circuit_breakers:
      thresholds:
        - priority: DEFAULT
          max_connections: 1024
          max_pending_requests: 256   # 排队上限，超了立刻拒绝而不是无限积压
          max_requests: 1024
          max_retries: 32             # 全 cluster 同时在飞的重试请求硬上限
          track_remaining: true       # 暴露剩余额度指标，方便告警
    outlier_detection:                # 被动健康检查：连续失败就把该实例摘掉
      consecutive_5xx: 5
      base_ejection_time: 30s
      max_ejection_percent: 30        # 最多摘 30%，防止把整个集群摘空

max_retries: 32 就是预算的硬实现：无论上游失败多严重，全集群同时在飞的重试请求不会超过 32 个，放大系数被物理封顶。max_ejection_percent: 30 同样重要——如果不设上限，一次全局故障（比如下游依赖的数据库挂了）会让被动健康检查把所有实例都摘掉，等数据库恢复时你的服务反而一台可用实例都没有。

八、超时预算必须从外到内递减

超时配错的典型症状是：监控上服务端成功率 99.9%，用户却在投诉打不开。原因是外层超时比内层各段之和还短，客户端早已断开，内部调用链还在继续跑完，服务端认为自己成功了。

正确做法是自外向内做预算分配，每一层都要给网络往返、序列化、排队留余量。下面是一个总预算 3 秒的分配示例：

层级超时留给下层的预算为什么这么算
客户端（App）3000ms2700ms用户可感知上限，留 300ms 给移动网络首包和 TLS
网关到业务服务2500ms2300ms小于客户端超时，留 200ms 给网关自身处理和日志
业务服务到 RPC 下游（单次）800ms700ms2300 除以串行跳数再打折；如果有重试，乘以 1 加重试次数后仍需小于 2300
RPC 下游到数据库500ms—小于 RPC 超时，否则数据库还在跑而调用方已放弃
缓存读取50ms—缓存慢于 50ms 就该走回源，等它没有意义
💡
比静态分配更好的做法：传递 deadline

静态分配的问题是它假设每一跳都用满预算，实际上前几跳往往很快。把剩余时间随请求向下传递（gRPC 的 grpc-timeout 头原生支持，HTTP 可以自己约定一个 X-Deadline-Ms），每一跳用「剩余时间」而不是固定值作为自己的超时上限，并且在剩余时间已经不够完成一次下游调用时直接快速失败，不再发起注定白跑的调用。这一个改动通常能在故障期间省下 20% 到 40% 的无效下游压力。

九、高可用与可观测性

网关的高可用有三条硬要求：

  • 数据面必须无状态，任何会话状态（比如限流计数、连接亲和）都不能只存在单个节点的内存里，否则滚动重启就会丢限流精度或踢掉长连接。
  • 配置变更不能靠 reload 进程。Nginx 的 reload 在长连接场景下会让老 worker 长时间不退出，内存翻倍；APISIX / Envoy 的动态配置推送才是正解。
  • 控制面挂掉时数据面必须继续按最后一次有效配置工作。这一点和配置中心的兜底要求完全一致，见站内配置中心篇。

限流计数放本地还是放中心，是个明确的取舍：

方案准确性额外延迟失效场景
纯本地计数（阈值除以副本数）低，副本数变化时总阈值漂移0扩缩容后总限流值跟着变；流量不均时某副本提前误限
集中式计数（Redis 原子递增）高每请求一次往返，通常 1ms 到 3msRedis 抖动直接放大成网关抖动；必须配「计数失败时放过」的降级
本地预扣 + 定期同步中高，误差不超过一个配额批次摊薄后接近 0批次给得太大时突发流量会超额；同步周期建议 200ms 到 1s

网关是采集黄金信号（延迟、流量、错误、饱和度）性价比最高的位置，因为它一处埋点就覆盖全站入口，而且它记录的是用户实际感受到的耗时和错误率，比每个服务自己上报的更可信。几条一定要配的查询：

# 1) 入口 P99 延迟，按路由和上游分组，定位到具体接口
histogram_quantile(0.99,
  sum by (le, route, upstream) (
    rate(apisix_http_latency_bucket{type="request"}[5m])
  )
)

# 2) 入口错误率。必须区分 5xx 和 4xx：5xx 是你的问题，4xx 突增通常是客户端或攻击
sum by (route) (rate(apisix_http_status{code=~"5.."}[5m]))
  /
sum by (route) (rate(apisix_http_status[5m]))

# 3) 重试占比。这个指标平时接近 0，一旦超过 10% 就是重试风暴的前兆，必须告警
sum(rate(envoy_cluster_upstream_rq_retry[1m]))
  /
sum(rate(envoy_cluster_upstream_rq_total[1m]))

# 4) 上游连接池饱和度。接近 1 说明连接数不够，请求在网关侧排队
sum by (cluster) (envoy_cluster_upstream_cx_active)
  /
sum by (cluster) (envoy_cluster_circuit_breakers_default_cx_open + 1024)

第三条查询值得单独拎出来：重试占比是最好的早期预警指标，它通常在错误率上涨之前几十秒就开始抬头，因为重试成功的请求不会体现在错误率里，但它已经说明下游在恶化。至于 Span 数据模型、上下文传播与采样策略，站内 OpenTelemetry 实战已有完整展开，这里只强调一点：traceID 必须在网关生成并注入下游和访问日志，这是后续所有排查的起点。

❌
网关上最容易踩的坑

1. 在网关插件里写业务字段判断，半年后没人敢删，且每次业务改字段都要网关发版。
2. 注入 X-User-Id 前不清空客户端同名头，攻击者自带一个就直接越权。
3. 下游服务完全依赖网关鉴权，结果内网直连、定时任务、压测流量全部绕过了所有校验。
4. 网关开 3 次重试且不配重试预算，下游一变慢就收到 4 倍流量，小抖动被放大成全站故障。
5. 网关和 RPC 框架各自配了重试，放大系数相乘，实际到下游是 9 倍。
6. 对 POST 做重试，造成重复下单重复扣款，而且日志里看起来是「用户点了两次」。
7. 外层超时配得比内层各段之和还小，客户端早断了内部还在跑，成功率指标与用户体感完全对不上。
8. 被动健康检查不设 max_ejection_percent，一次全局依赖故障把所有上游实例摘空，根因修复后反而无实例可用。
9. 影子流量直连生产数据库，压测数据污染真实业务表。
10. 限流阈值按副本数均摊后忘了跟随扩缩容调整，缩容一半后总容量也砍半，大促当天直接限流。
11. 用 reload 做配置变更，长连接场景下老 worker 迟迟不退，内存占用翻倍甚至 OOM。
12. 网关只记 5xx 不记上游耗时分布，故障时只能看到「网关 502」，完全无法判断是哪个上游拖的。
