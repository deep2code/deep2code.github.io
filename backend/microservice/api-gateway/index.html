API 网关与服务注册发现

🏷️ API网关

微服务的两道大门：入口与通讯录

服务拆成几十个之后，第一个现实问题马上就来了：移动端 App 到底该把请求发给谁？订单服务扩了 3 个实例，调用方怎么知道新实例的 IP？老实例下线了，怎么把流量摘干净？这两个问题分别由API 网关（API Gateway）和服务注册发现（Service Discovery）解决。前者是整个系统的"正门"，后者是所有服务的"通讯录"。

没有网关的微服务是一场灾难：每个前端都要硬编码几十个后端地址、鉴权逻辑写在每个服务里、限流策略改一处要发几十个服务、某个服务挂了客户端还要自己处理重试。有了网关，这些横切关注点全部下沉。

API 网关的核心职责

现代 API 网关（Kong、APISIX、Spring Cloud Gateway、Envoy）的职责可以归纳为五类：

  • 路由（Routing）：按 URL 前缀、Host、Header、权重把请求转发到后端服务。这是最基本的能力。
  • 横切关注点（Cross-cutting）：鉴权（JWT/OAuth2）、限流、熔断、日志、链路追踪注入——所有不想在每个服务重复写的逻辑。
  • 协议转换：对外暴露 HTTP/JSON，对内转发成 gRPC；或者把外部 HTTP/1.1 升级为 HTTP/2。
  • 聚合（Aggregation）：一个页面需要订单 + 用户 + 购物车三个接口，网关可以并行调用三个后端并合并返回，减少客户端 RTT。
  • 灰度发布（Canary）：按用户 ID 尾号、Header、Cookie 把 5% 流量导到新版本服务，出问题一键回滚。

服务注册发现的两种模式

服务发现有两种经典实现，区别只在"谁来查注册表"：

  • 客户端发现（Client-side Discovery）：调用方自己去注册中心拉服务列表、自己做负载均衡。代表作：Eureka（Netflix，已停更）、Nacos、Consul。优点是省一跳网络；缺点是每个语言都要写一套 SDK，多语言团队很痛苦。
  • 服务端发现（Server-side Discovery）：调用方只发请求到一个固定地址（K8s Service / Nginx / Envoy sidecar），由中间层去注册中心解析并转发。代表作：K8s Service + kube-proxy、Istio + Envoy。优点是业务代码零侵入；缺点是多一跳。

在 K8s 生态里，K8s Service 本身就是服务发现的标准答案：Deployment 的 Pod 标签决定 Service 背后挂哪些 Endpoints，kube-proxy 在每个节点维护 iptables/IPVS 规则，业务代码只需要访问 http://order-service.default.svc.cluster.local 这个 DNS 名字。但如果你不在 K8s 上跑，或者需要跨语言统一治理，Nacos/Consul 仍然是主流选择。

服务注册与心跳的时序

一个新服务实例启动后，从注册到能被调用，完整时序如下：

sequenceDiagram participant P as order-service 新实例 participant R as 注册中心 Nacos participant C as 调用方 user-service participant LB as 本地负载均衡 P->R: 注册 (IP:8080, 元数据 version=v2) R-->>P: 注册成功, 分配 5s 租约 loop 每 5 秒 P->>R: 发送心跳 R-->>P: 续租成功 end C->>R: 订阅 order-service 列表 R-->>C: 推送最新实例列表 C->>LB: 选择一个实例(如 round-robin) LB-->>C: 10.0.3.21:8080 C->>P: gRPC 调用 Note over P,R: 实例崩溃后 15s 未收到心跳
注册中心主动摘除，推送新列表

这里的关键工程细节是租约（Lease）而不是永久注册：实例宕机后注册中心必须能自动感知并摘除，否则调用方会持续打到死实例。租约超时通常设为心跳间隔的 3 倍（心跳 5s → 超时 15s），太短容易误杀，太长摘除不及时。

实战一：APISIX 网关路由配置

APISIX 是基于 OpenResty 的高性能网关，配置用 etcd 存，热更新无需重启。下面是一个完整路由：把 /api/orders/* 转发到订单服务，同时挂 JWT 鉴权和限流插件：

# apisix-route.yaml —— 通过 apisixctl 或 admin API 下发
routes:
  - uri: /api/orders/*
    name: order-route
    methods: [GET, POST, PUT]
    upstream:
      type: chash           # 一致性哈希，按 user_id 分流
      hash_on: header
      key: X-User-ID
      nodes:
        "10.0.3.21:8080": 1
        "10.0.3.22:8080": 1
        "10.0.3.23:8080": 1
    plugins:
      jwt-auth: {}          # 强制 JWT 鉴权
      limit-req:            # 限流：单 IP 每秒 10 次
        rate: 10
        burst: 20
        key_type: var
        key: remote_addr
        rejected_code: 429
      proxy-rewrite:
        regex_uri: ["^/api/orders/(.*)", "/v1/orders/$1"]

用命令行验证路由是否生效：

# 1. 登录获取 JWT
TOKEN=$(curl -s -X POST https://api.example.com/apisix/admin/user/login \
  -H "Content-Type: application/json" \
  -d '{"username":"jack","password":"s3cret"}' | jq -r '.data.token')

# 2. 带 JWT 访问受保护路由，应 200
curl -H "Authorization: Bearer $TOKEN" https://api.example.com/api/orders/A1001

# 3. 不带 token 直接打，应 401
curl -i https://api.example.com/api/orders/A1001 | head -5

# 4. 压测验证限流阈值，应看到 429
ab -n 200 -c 50 -H "Authorization: Bearer $TOKEN" \
  https://api.example.com/api/orders/A1001

实战二：Nacos 服务注册与发现（Go）

Nacos 同时支持注册发现和配置中心（下一篇讲配置）。下面用 Go SDK 演示一个服务实例启动时注册、调用方通过 Nacos 发现实例并发起 gRPC 调用：

package main

import (
    "context"
    "log"

    "github.com/nacos-group/nacos-sdk-go/v2/clients"
    "github.com/nacos-group/nacos-sdk-go/v2/clients/naming_client"
    "github.com/nacos-group/nacos-sdk-go/v2/common/constant"
    "github.com/nacos-group/nacos-sdk-go/v2/vo"
)

func newNacosClient() naming_client.INamingClient {
    sc := []constant.ServerConfig{
        *constant.NewServerConfig("127.0.0.1", 8848,
            constant.WithContextPath("/nacos")),
    }
    cc := constant.NewClientConfig(
        constant.WithNamespaceId("prod"),
        constant.WithNotLoadCacheAtStart(true),
        constant.WithLogLevel("warn"),
    )
    cli, err := clients.NewNamingClient(vo.NacosClientParam{
        ClientConfig:  cc,
        ServerConfigs: sc,
    })
    if err != nil {
        log.Fatal("nacos init failed:", err)
    }
    return cli
}

func registerOrderService(cli naming_client.INamingClient) {
    ok, err := cli.RegisterInstance(vo.RegisterInstanceParam{
        Ip:          "10.0.3.21",
        Port:        8080,
        ServiceName: "order-service",
        GroupName:   "DEFAULT_GROUP",
        ClusterName: "DEFAULT",
        Weight:      10,
        Enable:      true,
        Healthy:     true,
        Ephemeral:   true,  // 临时实例：靠心跳维持，宕机自动摘除
        Metadata:    map[string]string{"version": "v2", "env": "prod"},
    })
    if err != nil || !ok {
        log.Fatal("register failed:", err)
    }
    log.Info("order-service registered to nacos")
}

func discoverAndCall(cli naming_client.INamingClient) {
    // 拉取一个健康实例，生产中建议加本地缓存 + 订阅推送
    instances, err := cli.SelectOneHealthyInstance(vo.SelectOneHealthInstanceParam{
        ServiceName: "order-service",
        GroupName:   "DEFAULT_GROUP",
    })
    if err != nil {
        log.Fatal("discover failed:", err)
    }
    target := fmt.Sprintf("%s:%d", instances.Ip, instances.Port)
    log.Printf("调用 order-service @ %s", target)
    // 实际 gRPC 调用：conn, _ := grpc.Dial(target, ...)
    _ = context.Background()
}

网关的坑：别让它变成新的单点

我踩过的坑：有次网关超时设了 30s，后端服务实际处理超时是 10s。结果后端 hang 死后，网关连接池被占满 30s 才释放，期间所有请求都进不来。网关到后端的超时必须比后端自己的超时短，留够链路时间。我后来改成网关超时 8s、后端超时 10s，问题才消失。

API 网关是所有流量的必经之路，它的故障就是全站故障。生产部署必须做到：

  • 多副本 + 无状态：网关本身不存会话，水平扩 3-5 副本，前置 LVS/CLB。
  • 配置热更新 + 灰度：路由变更走配置中心（etcd）推送，禁止改完手动 reload 所有节点。
  • 超时要短：网关到后端的超时必须比后端自己的超时短，否则后端 hang 死会拖垮网关连接池。
  • 不要在网关写业务逻辑：网关只做横切，"根据用户等级算价格"这种业务规则下沉到服务里，否则网关会重新长成新的单体。

最佳实践

  • 南北向 vs 东西向分离：API 网关管南北向（外部 → 内部）；服务间调用（东西向）通过注册中心 + 客户端负载均衡，不要再绕一遍网关，那是双倍延迟。
  • 注册中心也要高可用：Nacos/Consul 至少 3 节点，别把它当成"挂了就挂了"的次要组件——它挂了等于整个集群失明。
  • 健康检查分级：TCP 探活只能证明进程活着，HTTP /readyz 才能证明依赖就绪。注册中心摘除用 /readyz，不要用 TCP 握手。
  • 元数据驱动路由：实例注册时带上 version、zone、env，网关根据这些元数据做灰度、就近路由，而不是硬编码 IP。
  • 灰度发布先从网关切：新版本先注册到注册中心但不挂流量，确认健康检查通过后，网关按 1% → 10% → 50% → 100% 逐步放量。

FAQ

Q1：Spring Cloud Gateway、Kong、APISIX、Envoy 怎么选？

网关语言/底座性能插件生态适用场景
Spring Cloud GatewayJava中Spring 生态Java 技术栈团队
KongLua/OpenResty高极丰富企业级、多团队
APISIXLua/OpenResty极高丰富（etcd 热更新）高性能、云原生
EnvoyC++极高xDS 动态配置Service Mesh (Istio)

Java 技术栈、团队已经在用 Spring：选 Spring Cloud Gateway，和 Eureka/Nacos 集成顺滑。高性能、插件生态丰富、要纯 Lua/Go 插件：选 APISIX 或 Kong。Service Mesh 场景（Istio）：选 Envoy，它是数据面标准。中小团队想少运维：Nginx + Lua 也够，但限流鉴权要自己写。

Q2：服务发现一定要用 Nacos 吗？K8s 里直接用 Service 不行吗？

K8s 内部用 Service 完全够，而且零额外运维。但当你需要①跨集群/跨命名空间调度、②虚拟机上的老服务也要接入、③需要配置中心二合一、④按元数据精细路由时，Nacos/Consul 比 K8s Service 灵活。K8s 集群内部优先 Service，跨环境再上注册中心。

Q3：注册中心挂了，服务之间还能调用吗？

设计良好的客户端 SDK 会本地缓存服务列表（Nacos 客户端默认持久化一份），注册中心短暂挂掉不影响已有调用；但新实例上线、老实例下线就感知不到了。所以注册中心必须多副本部署，且心跳超时不要太短（否则网络抖动会大面积误摘）。

Q4：网关做了鉴权，服务端还需要再鉴权一次吗？

需要。网关鉴权只能防"未登录用户"，服务端必须校验权限范围——比如用户 A 不能查用户 B 的订单。信任链路是：网关校验 JWT 签名并注入 X-User-ID，服务端根据 X-User-ID 做资源归属校验。永远不要信任网关注入之外的任何用户标识。

总结

API 网关是微服务集群对外的统一门面，服务注册发现是集群内部的"电话簿"。两者配合，解决了"流量从哪进"和"服务在哪找"两个基础设施问题。但服务跑起来之后，还有两个躲不开的硬骨头：配置怎么集中管理、跨服务的数据一致性怎么保证——这就是下一篇的主题。
