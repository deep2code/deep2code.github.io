熔断限流降级

🏷️ 服务治理

💡 你想搞懂这个技术到底是干嘛的，什么时候该用它，什么时候不该用。不想上来就背一堆概念。

雪崩效应：一次调用失败如何拖垮整条链路

，不是某个服务自己挂了，而是一个非核心依赖挂了，把核心服务一起拖死。典型链路：用户请求 → 订单服务 → 库存服务 → 数据库。某时刻库存服务响应变慢，订单服务的线程池被打满，整个下单链路瘫痪。这就是熔断要解决的问题。

解决雪崩靠三件套：熔断（Circuit Breaker）——下游持续失败就先别调了；限流（Rate Limiting）——入口流量太大就快速拒绝；降级（Fallback）——实在扛不住就返回兜底结果。三者合称"雪崩治理三板斧"。

熔断器状态机：三态切换

熔断器（Hystrix 已停更，现在主流是 Resilience4j、Sentinel、Go 的 gresilience/hystrix-go）有三个状态，理解状态机是用好它的前提：

  • CLOSED（关闭）：正常放行，同时统计最近 N 次调用的失败率。失败率超过阈值（如 50%）→ 转到 OPEN。
  • OPEN（打开）：所有调用直接快速失败（走 fallback），不再真的请求下游。等待一个冷却时间（如 5s）后 → HALF_OPEN。
  • HALF_OPEN（半开）：放一小撮请求试探下游是否恢复。成功 → CLOSED；失败 → 回到 OPEN。
stateDiagram-v2 [*] --> CLOSED CLOSED --> OPEN: 失败率 ≥ 阈值(如 50%) OPEN --> HALF_OPEN: 冷却时间到(如 5s) HALF_OPEN --> CLOSED: 试探请求成功 HALF_OPEN --> OPEN: 试探请求失败 CLOSED --> [*]

这个设计的精髓是给下游"呼吸空间"：下游出问题时，继续打流量只会让它死得更透。熔断等于主动断开，让下游有机会恢复；冷却期过后再用少量请求试探，而不是直接全量恢复——避免"下游刚缓过来，全量流量一拥而上又打垮"。

限流算法：令牌桶 vs 漏桶

限流是在入口处控制"每秒最多接多少请求"。两种经典算法：

  • 令牌桶（Token Bucket）：以固定速率往桶里放令牌，每个请求消耗一个令牌，桶满了新令牌丢弃。允许一定程度的突发流量（桶里攒的令牌可以一次性消耗），适合 API 网关入口。
  • 漏桶（Leaky Bucket）：请求进桶排队，桶以固定速率漏水（处理请求），桶满了直接拒绝。输出速率恒定，适合保护下游、把突发流量平滑掉。

实战经验：网关入口用令牌桶（允许突发），调用下游时用漏桶（保护下游）。

熔断 + 限流 + 降级的完整时序

我踩过的坑：有次上线熔断后没配降级兜底，结果下游一挂，熔断器 OPEN 直接抛异常，前端白屏。用户投诉完才发现 fallback 方法是空的。降级要提前想清楚"降级到什么"，并在上线前演练一遍熔断触发时的实际表现。

实战一：Resilience4j（Java/Spring 生态）

Resilience4j 是 Hystrix 的继任者，模块化设计，CircuitBreaker、RateLimiter、TimeLimiter、Retry 可以自由组合。Maven 引入后用注解配置即可：

# application.yml —— Resilience4j 熔断器 + 限流器配置
resilience4j:
  circuitbreaker:
    configs:
      default:
        sliding-window-type: COUNT_BASED
        sliding-window-size: 20           # 最近 20 次调用统计
        failure-rate-threshold: 50        # 失败率 ≥ 50% 打开熔断
        wait-duration-in-open-state: 5s   # OPEN 冷却 5s
        permitted-calls-in-half-open-state: 3  # 半开放放 3 个试探
        slow-call-rate-threshold: 80      # 慢调用率 ≥ 80% 也算失败
        slow-call-duration-threshold: 2s
    instances:
      orderService:
        base-config: default
  ratelimiter:
    instances:
      orderService:
        limit-for-period: 100             # 每 1 秒最多 100 次
        limit-refresh-period: 1s
        timeout-duration: 0               # 拿不到令牌立即拒绝

// OrderServiceClient.java —— 注解式使用：熔断 + 降级 + 重试
@Service
public class OrderServiceClient {

    @CircuitBreaker(name = "orderService", fallbackMethod = "fallbackOrder")
    @RateLimiter(name = "orderService")
    @Retry(name = "orderService", fallbackMethod = "fallbackOrder")
    public OrderDTO getOrder(String orderId) {
        return webClient.get()
            .uri("/orders/" + orderId)
            .retrieve()
            .bodyToMono(OrderDTO.class)
            .block();
    }

    // 降级方法：签名要和原方法一致，额外加一个 Throwable 参数
    private OrderDTO fallbackOrder(String orderId, Throwable t) {
        log.warn("order-service fallback, orderId={}, cause={}", orderId, t.toString());
        // 返回兜底数据：缓存里的旧值、或者默认值
        return OrderDTO.stub(orderId);
    }
}

实战二：Go 用 gresilience 实现熔断器

package main

import (
    "errors"
    "log"
    "time"

    "github.com/beyondeye/gresilience/v2"
)

func callWithCircuitBreaker() (string, error) {
    // 定义熔断器：20 次窗口、50% 失败率打开、5s 冷却
    cb := gresilience.NewCircuitBreaker(
        gresilience.WithWindowSize(20),
        gresilience.WithFailureRateThreshold(0.5),
        gresilience.WithOpenStateTimeout(5*time.Second),
        gresilience.WithHalfOpenMaxCalls(3),
    )

    // 用装饰模式包住真实调用
    result, err := cb.Execute(func() (string, error) {
        return callOrderService()  // 真实 gRPC/HTTP 调用
    })
    if err != nil {
        // 熔断打开时会返回 ErrCircuitOpen，直接走降级
        if errors.Is(err, gresilience.ErrCircuitOpen) {
            log.Println("circuit open, using fallback")
            return "cached-stub-order", nil
        }
        return "", err
    }
    return result, nil
}

func callOrderService() (string, error) {
    // 真实逻辑：gRPC 调用订单服务，带超时
    return "order-A1001", nil
}

Sentinel（阿里开源）是另一个主流选择，它的特色是控制台动态配置规则，不用改代码就能调整限流阈值：

# 推送 Sentinel 限流规则到控制台（生产推荐用 Nacos 作为规则数据源）
curl -X POST "http://sentinel-dashboard:8080/rule/flow" \
  -H "Content-Type: application/json" \
  -d '{
    "app": "order-service",
    "resource": "GET:/api/orders",
    "grade": 1,           // 1=QPS
    "count": 500,         // 每秒 500 次
    "strategy": 0,        // 直接限流
    "controlBehavior": 0  // 快速失败
  }'

超时与重试：熔断之外的两根保险丝

熔断解决"下游持续故障"，但单次调用的超时和重试是另一个独立必须做的事：

  • 超时必须显式设置：Go 的 context.WithTimeout、Java 的 feign.client.config.default.connectTimeout。没有超时的网络调用是定时炸弹，它会一直挂着把连接池耗尽。
  • 重试要加 jitter：固定间隔重试会导致"所有请求同时重试 → 又一次压垮下游"。用指数退避 + 随机抖动（如 Resilience4j 的 waitDuration = 100ms * 2^n + random(0~50ms)）。
  • 重试次数不要超过 2 次：重试越多，放大效应越严重。一次超时 5s，重试 3 次就是 15s，用户早走了。

最佳实践

  • 每个下游依赖独立熔断：不要一个全局熔断器包住所有调用，否则库存服务挂了会连累你调用户服务。每个远程调用目标单独配置熔断器。
  • 降级要提前想清楚"降级到什么"：下单接口降级到"暂存到本地、稍后补单"，商品列表降级到"返回缓存的旧数据"，用户信息降级到"返回匿名视图"。不要写了降级接口却在生产才发现兜底数据是空的。
  • 熔断指标必须监控：熔断器 OPEN 了要立刻告警——这是下游出问题的最早期信号。光有熔断器不看指标，等于装了烟雾报警器却把电池拔了。
  • 限流要分级：网关层限流（防 DDoS）、服务层限流（保护自身）、依赖层限流（保护下游）。只在网关限流没用，服务自身被慢查询拖死时网关挡不住。
  • 避免重试风暴：调用方重试 + 重试 + 重试，下游压力是原来的 N 倍。重试只用于幂等接口，非幂等接口（如创建订单）禁止自动重试。

FAQ

Q1：Hystrix 停更了，老项目还在用怎么办？

能迁就迁到 Resilience4j（Java 生态迁移路径最顺，注解几乎一一对应）；Go 生态用 gresilience 或 go-breaker。Hystrix 核心问题是它把线程隔离（ThreadPool）作为默认方案，线程池切换开销大，Resilience4j 用信号量隔离，性能更好。

Q2：熔断阈值设多少合适？

没有标准答案，经验值：失败率 50% 打开、滑动窗口 20-100 次、冷却 5-30s。必须按下游历史表现调整——支付网关 99.99% 可用性，失败率 1% 就该警惕；推荐服务本来就允许 5% 超时，阈值要放到 20%。上线后通过监控曲线动态调，别拍脑袋。

Q3：限流和熔断是一回事吗？

不是。限流是入口主动控制流量（不管下游好不好，超过阈值就拒），熔断是根据下游健康度被动断开（下游好的时候不限流，下游坏了就断开）。两者互补：限流保护自己，熔断保护下游。

Q4：降级返回兜底数据，用户看到旧数据怎么办？

这是业务取舍。降级时必须在响应里显式标记（如 X-Degraded: true 头），前端据此提示"网络较慢，展示缓存数据"。对一致性敏感的接口（如余额）不要降级返回旧值，宁可报错。

总结

雪崩治理的本质是假设故障一定会发生，把"故障的爆炸半径"限制在最小范围。熔断器在下游出问题时主动断开，限流在入口过载时快速拒绝，降级在最坏情况下提供兜底。三者配合超时和重试，构成微服务的"免疫系统"。但要定位"到底哪个环节出了问题"，还缺一块拼图——分布式链路追踪。
