微服务的代价模型：拆分前先把账算清

🏷️ 微服务

「我们要上微服务」这句话背后，几乎总藏着一个没被验证的假设：单体不好维护，所以拆开就好了。但拆分本身不改一行业务逻辑，它做的只是把进程内的方法调用换成会超时、会重试、会乱序、会部分失败的网络调用，并把一次部署变成 N 次部署。这篇不讲怎么拆（操作步骤见站内《微服务拆分入门》，边界怎么找见《DDD 与服务拆分》），只讲拆之前该算清的那笔账：哪些问题拆分真能解，哪些解不了，拆完要额外付什么，以及付不起的时候退到哪一步。

单体的真实问题是模块边界，不是部署单元

把「单体不好维护」这句话拆成具体症状，通常是四条：改一处崩三处、不敢删任何代码、新人要看三周才敢提需求、发布要排队等别人。前三条全是模块边界问题，只有第四条是部署单元问题。也就是说，四分之三的痛苦和「是不是单体」无关，和「模块之间有没有边界」有关。

更要命的是，边界烂的单体拆成微服务，只会变成边界烂的分布式系统，而且原本编译器能帮你发现的问题会全部变成运行时问题。单体里 A 包和 B 包循环依赖，IDE 会标红、构建工具会报错；拆完变成 A 服务和 B 服务互相 RPC，编译期一片安静，等到线上某个慢查询把 A 的线程池占满，B 调 A 超时、A 调 B 也超时，两边一起雪崩，你才知道那个循环还在。

症状 团队常见归因 真实根因 拆成微服务之后
改订单逻辑，结算和报表一起出错 单体耦合太重 共享可变实体、跨模块直读对方表 变成跨服务隐式契约破坏，报错点从编译期挪到线上
没人敢删的死代码越堆越多 代码量太大 缺调用方追踪与埋点，不知道谁在用 更不敢删，因为调用方在别人的仓库里
新人上手要三周 项目太复杂 没有模块清单与依赖方向约束 上手成本更高，还要额外学网关、注册中心、链路追踪
发布要排队，一周只能上两次 单体部署慢 多团队共用一个部署单元，确实是单体的锅 真正被解决，这是拆分最硬的理由
接口 P99 三秒 单体性能瓶颈 N 加 1 查询、缺索引、大事务 更慢，因为一次慢查询上面又叠了两跳 RPC

先分清：拆分能解的问题和解不了的问题

下面这张表建议在立项会上直接投屏。左列的问题，微服务是对症下药；右列的问题，拆分是在给伤口撒盐。

问题 微服务能不能解 判据（用这个验证，别靠感觉） 误判的后果
多团队抢同一条发布流水线 能解，首要理由 统计一次需求从代码就绪到上线的等待时长，若等待时间超过开发时间，且原因是等别人的功能 不拆则团队规模扩大后吞吐不涨反跌
模块资源画像差异大 能解 看单机火焰图与内存分布：某模块吃满 CPU，某模块常驻大缓存，两者被迫按同一规格扩容 不拆则按最大公约数配机器，资源浪费两到三倍

技术栈必须异构 能解 存在无法用主语言实现的硬需求，例如模型推理依赖 Python 生态、边缘接入需要 Go 协程模型 不拆则被迫做进程外桥接，比直接拆服务更难维护
代码质量差、没测试 解不了 看单测覆盖率与线上缺陷密度，与部署形态无关 拆完变成十个没测试的服务，缺陷总量不变但定位成本上升
需求变更频繁、老改需求 解不了，且会恶化 统计一次需求平均波及几个模块，如果本来就波及五个，拆完就是五次跨团队协同 交付变慢，每次变更多出接口评审与版本兼容工作
系统慢、数据库压力大 解不了 先看慢查询日志与执行计划，九成是 SQL 与索引问题（详见站内 MySQL 索引与执行计划篇） 库还是那个库，只是前面多了两跳网络
希望「架构显得先进」 解不了 如果说不出上面任何一条的量化证据，这就是唯一的真实动机 付出全部成本，收益为零

拆分引入的七类新成本

拆分不是把复杂度消掉，而是把「代码内部的复杂度」换成「系统之间的复杂度」。后者的特点是：它不在你的 IDE 里，你看不见，只能靠工具观测。下面给七类成本的量级和缓解手段，量级按典型同机房部署估。

成本项 单体基线 拆分后量级 缓解手段 消不掉的残余
调用延迟与失败 方法调用约 100 纳秒，失败率近似 0 同机房 gRPC 单跳 0.5 到 2 毫秒，跨可用区 1 到 5 毫秒；网络与下游抖动带来万分之几到千分之几的失败率 合并 chatty 调用、批量接口、本地缓存、并行发起、连接池与长连接复用 每一跳都可能超时，必须写重试与幂等（幂等四种落地详见站内分布式一致性深度原理）
数据一致性 一个本地事务全搞定 变成柔性事务，业务要显式写补偿；不一致窗口从毫秒级变成秒级到分钟级 尽量让一次业务操作只写一个服务的数据；跨服务用本地消息表或事件驱动做最终一致 必须接受中间态，前端与对账都要为它改造；方案对比详见站内分布式一致性深度原理
调试与排障 一个断点跟到底，一份栈能看全 一次请求横跨 5 到 15 个进程，无追踪时定位一次跨服务问题从分钟级变成小时级 全链路 TraceID 贯穿、日志聚合、结构化日志带 trace 与 span 字段 断点调试基本失效，只能靠日志与追踪推断执行路径
本地开发环境 一个进程起来就能写代码 起 8 到 10 个服务外加中间件，常需 12 到 16 GB 内存，冷启动 3 到 10 分钟 容器编排一键起全套、远程共享开发环境、契约打桩替代真实依赖 开发机配置门槛抬高，新人首日环境搭建时间变长
运维对象数量 1 个部署单元、1 套配置、1 条流水线 N 个服务乘以环境数乘以配置项，是乘性增长；10 个服务 4 套环境就是 40 个部署实体 流水线模板化、配置集中管理、基础镜像统一、脚手架生成新服务 维护面积真实变大，SRE 与平台投入是长期支出
跨服务变更协同 一个 MR 改完一起上 一个字段贯通要 3 到 5 次发布，且必须按依赖顺序；一次协同发布窗口通常跨数天 接口先加不删、双写双读过渡、契约测试卡在 CI、消费者驱动契约 顺序约束无法消除，先加字段再用字段这个节奏必须遵守
可观测性门槛 看一份日志 加 一个 APM 就够 指标基数按服务乘接口乘状态码膨胀，追踪存储与采样策略要专门设计 统一 SDK、限制标签基数、按错误与慢请求做尾部采样 监控本身成为一个需要持续运维的子系统

注册发现、配置中心、网关这三样接入不难，难的是链路追踪的埋点覆盖率、告警的归属路由、流水线模板的统一，以及本地联调环境的可用性。这些通常要数月才能达到「拆分之后不至于失明」的水平，远长于一次服务拆分本身。所以正确的顺序是：先在单体时代就把可观测性和交付流水线建起来（单体一样受益），再动手拆。

能力 最低可用标准 不具备时的典型事故
服务注册发现 实例上下线 30 秒内全网感知，摘除不依赖人工改配置 缩容后调用方仍打到已销毁实例，报错持续到有人手改配置
链路追踪 网关入口生成 TraceID，跨服务与跨线程池透传，采样可按错误强制保留 报障说下单慢三秒，五个团队各自看自己的监控，都说「我这边正常」
日志聚合 一次查询能按 TraceID 拉出全链路日志，保留期不少于 7 天 排障要逐台机器登录抓日志，实例已被重建则证据彻底丢失
指标与告警 每个服务默认有请求量、错误率、延迟分位、饱和度四类指标，告警直达 owner 故障由用户先发现；或者告警发到一个没人看的大群
CI-CD 模板 新建服务从模板生成，构建发布步骤零定制 十个服务十套脚本，升级依赖版本要改十遍且没人敢碰
本地联调环境 一条命令拉起全部依赖或指向共享环境，新人当天能跑通主流程 开发每天开工前手动启八个进程，环境问题占用大量时间
配置中心 配置与镜像分离，改配置不重新构建，支持按实例灰度与一键回滚 改一个超时值要重新打包发布全部实例

演进路径与服务粒度：模块化单体是多数团队的终点

从单体直接跳到细粒度微服务，是失败率最高的路线。合理的路径是四步走，每一步都有明确的进入信号和回退条件——注意回退是正常动作，不是耻辱。

模块化单体的关键在于边界必须是可执行的约束而不是文档里的一句话。下面这段 ArchUnit 测试放进 CI，任何人试图跨模块直连对方内部实现，构建就红。这也是拆分前最好的演练：如果这些规则现在跑不过，说明边界还不存在，拆分只会把违规变成隐形的 RPC 依赖。

// ArchUnit 把模块边界变成可执行约束，CI 必跑
// 依赖：com.tngtech.archunit:archunit-junit5:1.3.0
@AnalyzeClasses(packages = "com.shop", importOptions = ImportOption.DoNotIncludeTests.class)
class ModuleBoundaryTest {

    // 规则1：订单模块只能调库存模块暴露的 api 子包，禁止摸 internal
    // 这条规则通过之后，未来把 inventory 拆成服务时，只需替换 api 的实现
    @ArchTest
    static final ArchRule order_must_not_touch_inventory_internal =
        noClasses().that().resideInAPackage("com.shop.order..")
            .should().dependOnClassesThat()
            .resideInAPackage("com.shop.inventory.internal..");

    // 规则2：禁止跨模块复用领域实体。共享实体是共享数据库的前兆，
    // 一旦两个模块共用同一个 JPA Entity，它们就永远拆不开
    @ArchTest
    static final ArchRule no_cross_module_entity_reuse =
        noClasses().that().resideInAPackage("com.shop.order.domain..")
            .should().dependOnClassesThat()
            .resideInAPackage("com.shop.inventory.domain..");

    // 规则3：模块依赖必须无环。单体里的环，拆完就是服务间的互相 RPC
    @ArchTest
    static final ArchRule modules_are_acyclic =
        slices().matching("com.shop.(*)..").should().beFreeOfCycles();

    // 规则4：只有 repository 层能碰 JdbcTemplate，杜绝在 service 里直连别人的表
    @ArchTest
    static final ArchRule only_repository_touches_jdbc =
        classes().that().haveSimpleNameContaining("JdbcTemplate")
            .should().onlyHaveDependentClassesThat()
            .resideInAnyPackage("..repository..", "..infra..");
}

关于粒度，流传最广的两个错误标准是「一个服务不超过 X 行代码」和「一个服务不超过 Y 个接口」。这两个数字和维护成本没有因果关系：一个两千行但需要五个团队一起改的服务，比一个两万行却只有一个团队拥有的服务难维护得多。实用判据只有三条：一个服务应该能被一个五人以内的小队完整拥有（含需求、编码、发布、值班、容量）；它必须有独立的数据，其他服务只能走它的接口，不能直连库表；它的变更原因独立，业务需求变化时通常只改它一个就能上线。三条有一条不满足，边界就划错了，而合并的成本远低于再拆一次——所以宁可先拆粗。

服务间通信方式选型

通信方式决定了耦合度与故障传播范围，这个选择比框架选型重要得多。四种主流方式的差异不在性能数字上，而在「下游挂掉时上游会怎样」。

方式 典型延迟 耦合度 故障传播 调试难度 适用场景
同步 REST 与 JSON 同机房 2 到 10 毫秒，体积大 3 到 10 倍 中，字段靠约定，弱类型容易悄悄破坏 直接传播，下游超时上游必然等 低，抓包和 curl 就能复现 对外开放接口、跨语言跨团队接入、调试友好优先
同步 gRPC 同机房 0.5 到 2 毫秒，长连接多路复用 高，强契约但 proto 变更要双方协同 直接传播，且长连接下游雪崩会瞬间打满上游 中，需要反射或专用工具才能手工调 内部高频调用、延迟敏感、需要流式与强类型

可用性是乘法，延迟是加法

这是拆分成本里最容易被忽略、后果最严重的一条算术。串行的强依赖调用，可用性相乘：五个各自 99.9% 的服务串起来，链路可用性是 0.999 的五次方，约 99.50%。换成时间，单服务每月不可用约 43 分钟，五服务链路每月约 216 分钟，直接差了五倍。而你并没有增加任何功能。

把一跳从强依赖改成可降级的弱依赖，它就不再进入这个乘法。这就是为什么「哪些依赖允许降级」必须在拆分设计阶段就定下来，而不是等故障复盘时再补。下面这段脚本把算式固化，评审时直接跑给大家看。

# 串行同步链路的可用性与尾延迟估算，评审时直接改数字重算
# 用法: python3 chain.py
CHAIN = [
    # (服务名, 单服务可用性, P99 毫秒, 是否强依赖)
    ("gateway",   0.9995, 5,   True),
    ("order",     0.999,  30,  True),
    ("user",      0.999,  20,  False),   # 会员等级取不到就按普通用户算，可降级
    ("inventory", 0.999,  25,  True),
    ("pricing",   0.998,  40,  False),   # 优惠算不出来就用原价，可降级
    ("payment",   0.995,  120, True),
]

hard = [c for c in CHAIN if c[3]]
avail = 1.0
for _, a, _, _ in hard:
    avail *= a                      # 只有强依赖进乘法，弱依赖降级后不影响成功率
p99 = sum(t for _, _, t, _ in CHAIN) # 串行调用延迟是加法，这只是 P99 的下限

print("强依赖跳数 %d / 总跳数 %d" % (len(hard), len(CHAIN)))
print("链路可用性 %.3f%%" % (avail * 100))
print("每月不可用 %.1f 分钟" % ((1 - avail) * 30 * 24 * 60))
print("串行 P99 下限 %d ms" % p99)
# 实测经验: 真实链路 P99 通常比各跳 P99 之和再差 20% 到 50%,
# 因为一次请求要同时躲开每一跳各自的抖动窗口

另一个配套动作是超时预算向下传递。常见错误是每一跳都各自写死超时，于是入口 3 秒的预算被下游 5 秒的超时轻松突破，上游早已返回失败，下游还在埋头计算并占着连接。正确做法是把剩余预算随调用上下文传下去。

// 超时预算向下传递：每跳只能用剩余预算，并为本层收尾留出余量
// 配合 gRPC 时，context 的 deadline 会自动编码进 grpc-timeout 头传给下游
func WithBudget(parent context.Context, want, reserve time.Duration) (context.Context, context.CancelFunc) {
    budget := want
    if dl, ok := parent.Deadline(); ok {
        // reserve 留给本层收尾：序列化响应、写审计日志、上报指标
        remain := time.Until(dl) - reserve
        if remain < budget {
            budget = remain // 绝不允许下游超时大于上游剩余时间
        }
    }
    if budget <= 0 {
        // 预算已耗尽：立刻失败比发出一个必然超时的请求更省资源，
        // 也避免下游白白执行一次已经没人要结果的计算
        ctx, cancel := context.WithCancel(parent)
        cancel()
        return ctx, cancel
    }
    return context.WithTimeout(parent, budget)
}

// 调用侧：弱依赖超时后走降级，不把失败向上传播
func (s *OrderService) priceWithFallback(ctx context.Context, o *Order) Price {
    ctx, cancel := WithBudget(ctx, 1*time.Second, 50*time.Millisecond)
    defer cancel()
    p, err := s.pricing.Calc(ctx, o)
    if err != nil {
        s.metrics.Inc("pricing_fallback") // 降级必须有指标，否则静默降级会掩盖故障
        return Price{Amount: o.OriginalAmount, Degraded: true}
    }
    return p
}

分布式单体：最坏的结果长什么样

分布式单体是拆分失败的终态：付了微服务的全部成本，却一点独立演进能力都没拿到。它比原来的单体严格更差——原来至少还有本地事务和单步调试。识别它不需要架构评审，问三个问题就够了。

识别特征 怎么验证 根因 补救方向
多个服务必须同时发布 翻最近 10 次上线记录，看有多少次需要协调两条以上流水线按顺序走 接口变更没有向后兼容策略，字段先加后用的节奏没建立 强制接口只加不删不改语义，双写双读过渡，契约测试卡 CI
几个服务连同一个库甚至同一批表 统计每张核心表被几个应用账号连接，看有没有跨服务的 join 只拆了代码没拆数据，这是最常见的半途而废 先按 schema 隔离并收回直连权限，再逐表转交唯一所有者
加一个字段要改五个服务 拿最近一个需求数它波及几个仓库 边界按技术分层切的，不是按业务能力切的 按限界上下文重切（方法见站内 DDD 与服务拆分篇），先合并再重拆
某个服务挂了全站不可用 在预发环境把它停掉，看还剩多少功能可用 强依赖链过长，没有降级预案 逐条依赖标注强弱，弱依赖一律加兜底并补降级指标
所有服务用同一个共享 common 包且频繁升版 看 common 包最近半年发了多少版，升级要不要全量重新构建 把工具类和领域模型混在共享库里，共享模型等于共享耦合 共享库只留纯工具与协议定义，领域模型各自持有
没人能独立回滚自己的服务 问一句：你这个服务能不能单独回退一个版本 数据结构与接口变更不兼容，回滚会打断在途流程 所有变更设计成可回滚：先兼容读、再切写、最后清理
✅
一个可以直接用的决策门槛

把三件事写进拆分立项材料：一，用量化证据说明属于「发布冲突 / 资源画像分化 / 独立伸缩 / 技术栈异构」中的哪一类；二，逐项列出七类成本的当前应对手段，标出还缺哪几项基础设施及补齐时间；三，画出拆分后的最长同步强依赖链并算出乘法后的可用性，如果算出来比业务 SLO 还低，就必须先改依赖强弱，而不是先改架构图。三条凑不齐就先做模块化单体，它能解决你八成的痛点，成本不到微服务的十分之一。

最容易踩的坑

❌
这些坑每一条都有人真实踩过
  • 拿「代码太乱」当拆分理由：乱的模块边界拆完变成乱的服务边界，而且从编译期错误退化成线上错误。
  • 先拆服务后补基础设施：第一次线上慢请求就定位不了，然后为了赶进度在代码里写死下游 IP，注册中心从此形同虚设。
  • 代码拆了数据库没拆：多个服务连同一批表，任何一方改表结构都要全员通知，这是分布式单体最典型的形态。
  • 每一跳各自写死超时：入口 3 秒预算，下游写 5 秒超时，上游早返回失败了下游还在算，连接池被这些无主请求占满。
  • 所有下游都当强依赖：不区分强弱，一个可降级的优惠计算服务抖动 1 秒就让整单失败，可用性白白做成乘法。
  • 重试不带幂等：网络超时后重试，下游其实已经执行成功，结果重复扣款重复发货（幂等实现见站内分布式一致性深度原理）。
  • 重试没有退避与上限：下游刚过载，上游三倍重试把它彻底压死，把局部抖动放大成全站故障。
  • 共享 common 包里放领域模型：两个服务共用同一个实体类，从此谁都改不了字段，等于没拆。
  • 用代码行数或接口数量定粒度：真正的判据是能否被一个小队完整拥有、有无独立数据、变更原因是否独立。
  • 一上来就拆细：宁可先拆粗，合并两个服务比拆开一个服务便宜得多，粒度错了合并就行。
  • 接口变更直接改语义或删字段：正确节奏是只加不删、双写双读、灰度切换、最后清理，否则永远只能协同发布。
  • 降级成功但没有指标：静默降级会长期掩盖下游故障，直到某天数据对不上才被发现，必须为每条降级路径埋计数器和告警。
  • 把跨服务查询改成循环调用：列表页对 100 条记录各调一次用户服务，从一次 join 变成 100 次 RPC，延迟和失败率同时爆炸。
