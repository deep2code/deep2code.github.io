微服务深度原理：从单体到拆分

🏷️ 微服务

一个系统从单体拆成几十个微服务，不是简单把代码拆开就行。服务发现、配置中心、熔断限流、链路追踪，一堆配套设施要跟上。这篇从原理讲透微服务。

核心原理1：为什么要拆微服务？

单体系统人少开发快，人多了改一行全量测试、全量部署，发布风险大。拆成微服务，每个服务独立开发部署，技术栈也能不一样。

flowchart LR A[单体架构] --> B[模块多 耦合紧] B --> C[全量部署 风险大] C --> D[拆成微服务] D --> E[独立部署 独立扩展]

对比单体 vs 微服务

对比项 单体 微服务
开发效率 初期快 后期快，各服务独立
部署 全量部署 独立部署
扩展 整体扩展 按服务扩展
技术栈 统一 自由选择
运维复杂度 低 高，需要配套设施

核心原理2：服务发现原理：服务之间怎么找到对方？

服务 IP 老是变，不能硬编码。服务启动了去注册中心注册，调用方从注册中心拿服务列表，缓存到本地。

flowchart TD A[服务提供者] --> B[启动注册] B --> C[注册中心 Nacos/Consul] D[服务消费者] --> E[订阅服务列表] E --> C D --> F[负载均衡 选实例] F --> A A -->|心跳| C

微服务核心组件

组件 作用 常见实现
注册中心 服务注册发现 Nacos / Consul / etcd
配置中心 统一配置管理 Nacos / Apollo
负载均衡 从多个实例选一个 Ribbon / Spring Cloud LB
网关 统一入口 路由鉴权 Spring Cloud Gateway / Kong

核心原理3：熔断降级原理：雪崩怎么防？

一个服务挂了，调用它的服务线程都阻塞等它，一层层往上拖，整个系统雪崩。熔断就是错多了就直接拒绝，不调用了。

flowchart LR A[调用方] --> B{熔断器} B -->|正常| C[调用服务] B -->|错误率高| D[熔断开启 直接降级] C -->|失败| E[错误计数] E -->|超过阈值| D D -->|过一段时间| F[半开 试一下] F -->|成功| B F -->|失败| D

熔断器状态

状态 行为 触发条件
关闭 正常调用 默认状态
开启 直接降级，不调用 错误率/慢调用比例超阈值
半开 放少量请求试 熔断过了冷却时间

新手最容易踩的坑

❌
避坑指南
  • 不是所有系统都要微服务，小团队小项目单体就挺好
  • 拆服务不是按技术拆，是按业务领域拆，DDD 限界上下文
  • 分布式事务是大坑，优先最终一致，别搞强一致
  • 可观测性一定要跟上，日志/指标/链路追踪，不然出问题根本查不到
