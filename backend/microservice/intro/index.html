微服务架构设计

🏷️ 微服务架构

为什么我们需要微服务

2009 年 Netflix 遭遇了著名的"数据库天花板"事件：单体应用被部署在 150+ 台服务器上，任何一次发布都要协调上百个团队、耗时数周；更致命的是，一个团队在视频转码模块的一次内存泄漏就能打垮整个应用，订单服务、用户服务跟着一起挂。也是在那年，Amazon 提出了著名的两个披萨原则（Two-Pizza Teams）：如果一个团队大到两张披萨都喂不饱，那就太大了——而团队的边界，应该和代码的边界对齐。

微服务（Microservices）由此登上历史舞台：把一个原本的单体应用，按业务能力拆成一组小型、独立部署、围绕业务领域构建的服务。每个服务拥有自己的代码仓库、自己的数据存储、自己的生命周期，通过轻量级协议（通常是 HTTP/gRPC + 消息队列）通信。它不是银弹，而是一种用分布式复杂性换取组织与技术演进自由度的权衡。

从单体到微服务：架构演进的三个阶段

真实世界的架构演进很少是一步到位的。绝大多数团队会经历三个阶段，每个阶段都有明确的"触发信号"告诉你该下一步了。

  1. 单体架构（Monolith）：所有业务模块打包在一个进程里，共享一个数据库。优点是开发调试简单、部署一次搞定、本地事务天然保证一致性。缺点是：代码库膨胀到几十 G 后 IDE 卡顿、构建要半小时；一个模块出 bug 全量重启；技术栈被锁死在最初那套语言；团队之间代码互相"踩脚趾"。
  2. 面向服务架构（SOA）：把公共能力抽成独立服务，通过 ESB（企业服务总线）编排。SOA 的问题在于总线本身成了重量级单点，服务治理规则堆在 ESB 上，兜了一圈又变成了一个"巨型单体"——只不过这个单体是网络层的。
  3. 微服务架构：去总线化，服务之间点对点通信；每个服务是独立进程、独立数据库、独立技术栈；治理能力下沉到每个服务进程内（SDK 或 sidecar），而不是集中在一个交换机上。

微服务的核心设计原则

我的经验：不要第一天就拆 40 个服务。我见过太多团队上来就按 DDD 拆出几十个微服务，结果运维成本直接爆炸——每个服务都要配监控、日志、CI/CD，团队精力全花在基础设施上。正确做法是从单体里"绞杀"：先把边界最清晰的模块拆出去，让服务边界在真实业务中自然浮现。

Martin Fowler 与 James Lewis 在 2014 年的经典文章中定义了微服务的特征，结合我多年一线实战，提炼为以下七条必须刻进肌肉记忆的原则：

  • 单一职责（Single Responsibility）：一个服务只负责一个业务能力，"因为修改它的理由只有一个"。如果你的服务需要在 PR 描述里用"和"字连接两个以上业务域，它大概率拆错了。
  • 独立部署（Independent Deployability）：任何一个服务的发布，不应该需要协调其他服务一起上线。这意味着契约（API/事件 schema）必须向后兼容，数据库变更走扩展-收缩（Expand-Contract）模式。
  • 去中心化数据管理（Decentralized Data）：每个服务拥有自己的数据表，其他服务要数据走 API 或事件，禁止跨库 JOIN。这是微服务与 SOA 最大的分歧点，也是最痛苦的一点。
  • 故障是常态（Design for Failure）：网络调用一定会失败、进程一定会 OOM、机房一定会断网。所以每个服务都必须实现超时、重试、熔断、降级（本系列第 5 篇专讲），并把"下游挂了我还能提供什么"当作设计输入，而不是运维事后救火。
  • 进化式设计（Evolving）：不要试图第一天就拆出 40 个服务。从单体里"绞杀（Strangler Fig）"——先把边界最清晰、变更最频繁的模块拆出去，让服务边界在真实业务碰撞中自然浮现。
  • 端到端负责（Own Your Slice）：一个服务从数据库到 API 到监控告警全部由同一个团队负责，不要让 DBA 管表、SRE 管部署、开发管代码却没人对线上表现负责。
  • 可观测性内建（Observability Built-in）：没有链路追踪和结构化日志的微服务，就是一场分布式的盲猜。可观测性不是上线后补的，是写代码时就必须打的桩。

服务间交互：同步调用 vs 异步事件

微服务之间的通信只有两种范式，选错了会在后续每个迭代里反复还债。下面这个时序图刻画了一个"下单"流程中两种范式的差异：

sequenceDiagram participant C as 客户端 participant O as 订单服务 participant I as 库存服务 participant MQ as 消息队列 participant N as 通知服务 C->O: 创建订单 O->>I: 同步扣减库存(gRPC) I-->>O: 扣减成功 O->>MQ: 发布 OrderCreated 事件 MQ-->>N: 投递事件 N-->>N: 发送短信/邮件 O-->>C: 200 订单创建成功 Note over O,MQ: 同步链路只覆盖核心路径
非核心动作走异步事件解耦

经验法则：核心路径用同步（强一致、低延迟要求），非核心动作走异步（削峰、解耦、最终一致）。比如下单时"扣库存"必须同步，因为超卖是资金事故；但"发欢迎短信"完全可以异步，晚 5 秒用户根本不在乎。

快速起步：用 Go 写一个最小微服务骨架

理论说完，我们用 Go 写一个最小可运行的微服务，它包含 HTTP 服务、结构化日志、健康检查端点——这是任何一个生产级微服务都该有的"三件套"：

// main.go —— 一个生产级微服务的最小骨架
package main

import (
    "context"
    "log/slog"
    "net/http"
    "os"
    "os/signal"
    "syscall"
    "time"
)

func main() {
    logger := slog.New(slog.NewJSONHandler(os.Stdout, &slog.HandlerOptions{Level: slog.LevelInfo}))
    slog.SetDefault(logger)

    mux := http.NewServeMux()
    // 业务接口
    mux.HandleFunc("/api/v1/orders", func(w http.ResponseWriter, r *http.Request) {
        w.Header().Set("Content-Type", "application/json")
        w.Write([]byte(`{"order_id":"A1001","status":"created"}`))
    })
    // 存活探针：进程活着就返回 200，K8s livenessProve 用它判断要不要重启
    mux.HandleFunc("/healthz", func(w http.ResponseWriter, r *http.Request) {
        w.WriteHeader(http.StatusOK)
        w.Write([]byte("ok"))
    })
    // 就绪探针：依赖（DB/缓存）都通才返回 200，没就绪前网关不打流量
    mux.HandleFunc("/readyz", func(w http.ResponseWriter, r *http.Request) {
        if err := pingDB(); err != nil {
            w.WriteHeader(http.StatusServiceUnavailable)
            return
        }
        w.WriteHeader(http.StatusOK)
    })

    srv := &http.Server{
        Addr:         ":8080",
        Handler:      mux,
        ReadTimeout:  5 * time.Second,
        WriteTimeout: 10 * time.Second,
        IdleTimeout:  120 * time.Second,
    }

    // 优雅启停：收到 SIGTERM 后先摘流量再处理完在途请求
    go func() {
        slog.Info("order service listening on :8080")
        if err := srv.ListenAndServe(); err != http.ErrServerClosed {
            slog.Error("server error", "err", err)
            os.Exit(1)
        }
    }()

    quit := make(chan os.Signal, 1)
    signal.Notify(quit, syscall.SIGINT, syscall.SIGTERM)
    <-quit
    ctx, cancel := context.WithTimeout(context.Background(), 15*time.Second)
    defer cancel()
    if err := srv.Shutdown(ctx); err != nil {
        slog.Error("graceful shutdown failed", "err", err)
    }
    slog.Info("order service stopped")
}

func pingDB() error { return nil }

对应的 Dockerfile 与 K8s 部署 YAML，体现"镜像 + 探针 + 资源限制"的标准姿势：

# 多阶段构建：构建镜像用大镜像，运行镜像用极简 distroless
FROM golang:1.22 AS builder
WORKDIR /app
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -ldflags="-s -w" -o /out/order-svc .

FROM gcr.io/distroless/static-debian12:nonroot
COPY --from=builder /out/order-svc /order-svc
EXPOSE 8080
USER nonroot:nonroot
ENTRYPOINT ["/order-svc"]

# k8s-deploy.yaml —— 生产级 Deployment 必备要素
apiVersion: apps/v1
kind: Deployment
metadata:
  name: order-service
  labels: { app: order-service }
spec:
  replicas: 3
  selector: { matchLabels: { app: order-service } }
  template:
    metadata:
      labels: { app: order-service }
    spec:
      containers:
        - name: order
          image: registry.example.com/order-service:v1.4.2
          ports: [{ containerPort: 8080 }]
          # 资源请求与上限：避免单个 Pod 吃满节点
          resources:
            requests: { cpu: "100m", memory: "128Mi" }
            limits:   { cpu: "500m", memory: "512Mi" }
          # 两个探针：liveness 决定要不要重启，readiness 决定要不要接流量
          livenessProbe:
            httpGet: { path: /healthz, port: 8080 }
            initialDelaySeconds: 3
            periodSeconds: 10
          readinessProbe:
            httpGet: { path: /readyz, port: 8080 }
            initialDelaySeconds: 1
            periodSeconds: 5

最佳实践

  • 绞杀者模式渐进迁移：不要"大爆炸"式重写。先在旧单体前置一个网关，按业务能力把新流量逐步切到新服务，老系统像藤蔓一样被新树包围，最终下线。
  • 先做观测再做拆分：拆之前先搞清楚调用量、依赖关系、数据库热点。一个没有监控的系统拆完就是地狱——你根本不知道流量打到了哪里。
  • 契约先行（Contract-First）：服务间接口用 protobuf 或 OpenAPI 定义，先评审契约再写实现，避免"我改了个字段你那边挂了"的对齐灾难。
  • 避免分布式单体：如果拆完之后，一次业务请求要同步调 8 个服务、任意一个挂了全链路失败，那你只是把单体从进程内调用换成了网络调用，复杂度翻倍而收益为零。
  • 团队边界 ≈ 服务边界：康威定律说"设计系统的组织，其产生的设计等同于组织内的沟通结构"。想清楚谁为这个服务负责，再去拆代码。

FAQ

Q1：我们团队只有 10 个人，有必要上微服务吗？

绝大多数情况下没必要。微服务的收益在团队规模超过 20-30 人、业务线超过 3-5 条时才开始显现。小团队上微服务，光是维护注册中心、配置中心、链路追踪、CI/CD 这些基础设施就要吃掉一半研发精力。先用模块化单体（Modular Monolith）把业务边界划清楚，等真的遇到"发布互相阻塞"的痛点再拆不迟。

Q2：拆完之后，一次操作要跨多个服务写库，数据一致性怎么保证？

这是微服务最难的问题，没有银弹。原则是：能不用分布式事务就不用，用业务重试 + 对账兜底；实在需要跨服务强一致，用 TCC（短事务、资金类）或 Seata AT（通用）；长流程用 Saga 编排 + 补偿。本系列第 4 篇会展开讲。

Q3：服务拆得越细越好吗？现在我们已经拆了 60 个服务，感觉治理不动了

不是。拆分粒度的合理区间是"一个服务能由一个 6-10 人团队完全拥有并独立交付"。如果一个服务的代码量小到"改一次要动三个服务"，说明拆过细了，可以把强耦合的几个服务合并。拆分和合并都是演进手段，没有终点。

Q4：微服务一定要用 Docker + K8s 吗？

不强制，但强烈建议。微服务的痛点是数量多、部署频繁、环境不一致，容器 + 编排平台正好解决这三件事。没有 K8s 也可以用虚机 + Ansible，但你会在扩缩容、滚动发布、服务发现上重复造轮子。

总结

微服务不是技术潮流，而是一套应对组织与业务复杂度的工程方法论：它把单体应用内部的"编译期耦合"，换成了"运行期网络调用"，用分布式系统的代价（延迟、故障、一致性）换取了独立演进、独立扩缩容、技术栈自由的红利。是否值得这笔交易，取决于你的团队规模和业务复杂度。下一篇我们进入落地第一步——到底按什么标准把单体拆成服务，这正是 DDD 领域驱动设计要解决的问题。
