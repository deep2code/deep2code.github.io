DDD 与服务拆分

🏷️ DDD

拆服务最容易踩的坑：按技术分层拆

我踩过的坑：早年在一个电商项目，团队把单体按 controller/service/dao 三层拆成了三个服务。结果一次下单要跨三个服务同步调用，网络开销是原来的 5 倍，任何一层挂了全站不可用。数据库还是一个库，表之间到处 JOIN。拆了三个月，性能反而比单体还差。服务边界应该对应业务领域边界，不是代码分层边界。

我见过太多团队拆服务的翻车现场：把单体按"controller 层 / service 层 / dao 层"拆成三个服务，或者把 user、order、product 三个模块塞进同一个服务叫"业务中台"。结果就是：拆完之后一次下单要同步调 5 个服务，任何一个挂了全站不可用；数据库还是一个库，表之间到处 JOIN；团队沟通成本比单体时代还高。

问题的根源不在技术，而在边界划错了。服务边界应该对应业务领域的边界，而不是代码分层的边界。这正是 Eric Evans 在 2003 年提出的领域驱动设计（Domain-Driven Design, DDD）要解决的问题：它提供了一套语言和方法论，帮你在复杂业务中识别出"高内聚、低耦合"的边界。

DDD 核心概念速通

DDD 的概念很多，但落到"拆服务"这件事上，真正有用的只有下面四个：

概念含义对微服务的价值
统一语言开发产品测试用同一套词避免理解偏差导致拆错边界
限界上下文同一词在不同上下文含义不同≈ 微服务的候选边界
上下文映射上下文之间的集成关系决定同步调用还是异步事件
聚合根业务一致性单元禁止跨库 JOIN 的理论依据
  • 统一语言（Ubiquitous Language）：开发、产品、测试必须用同一套词说业务。如果产品说"下单"、开发说"创建订单记录"、DBA 说"insert into t_order"，说明你们对业务的理解根本不一致——这种系统拆出来一定歪。统一语言要求在代码里也用业务术语：Order、ShippingAddress、InventoryReservation，而不是 TblOrder、AddressDTO。
  • 限界上下文（Bounded Context）：同一个词在不同上下文里含义不同。比如"客户（Customer）"在销售上下文是"谈判对象"，在财务上下文是"结算对象"，在物流上下文是"收件人"。一个限界上下文 ≈ 一个微服务的候选边界——这是 DDD 对微服务最重要的贡献。
  • 上下文映射（Context Map）：限界上下文之间不是孤立的，它们有集成关系。常见模式有：防腐层（Anticorruption Layer，下游把上游模型翻译成自己的模型）、共享内核（两个上下文共用一块模型，谨慎使用）、发布-订阅（通过事件解耦）、客户-供应商（上下游有明确 SLA）。
  • 聚合与聚合根（Aggregate / Aggregate Root）：一个业务一致性单元。比如"订单 + 订单项"是一个聚合，Order 是聚合根，外部只能通过 Order 操作订单项。聚合之间用 ID 引用，禁止对象图导航——这正是微服务"禁止跨库 JOIN"的理论依据。

事件风暴：把会议室变成战场

DDD 不应该是架构师在白板上拍脑袋的产物，它必须由业务专家 + 开发 + 测试一起在一张大桌子上做出来。最有效的方法是 Event Storming（事件风暴），2015 年由 Alberto Brandolini 提出，操作流程如下：

  1. 拉一面空白墙，贴一张大纸，所有角色到场，2-3 小时。
  2. 用橙色便利贴写"领域事件"（过去时！订单已创建、库存已扣减、支付已完成），从业务流程起点开始贴。
  3. 用蓝色便利贴写触发事件的命令（创建订单、扣减库存），用黄色便利贴写聚合/实体。
  4. 用粉色便利贴标出外部系统（支付渠道、物流商）和角色。
  5. 观察事件自然聚类的区域——每个聚类圈就是一个限界上下文。给它起个业务名字，这就是服务名。

从限界上下文到微服务：时序拆解

有了上下文地图，接下来要决定每个交互走"同步调用"还是"异步事件"。以下单流程为例，正确的拆分时序是：

订单状态机异步流转 end

注意这个时序里的关键决策："扣库存"必须同步，因为超卖是资金事故；"通知物流、发邮件"必须异步，因为它们失败了不该影响下单。这种"同步走核心不变量、异步走副作用"的模式，是拆分服务时最常见的组合拳。

实战：用 Go 实现一个聚合根与仓储

DDD 在代码层面的落地，关键是把"聚合根"这个概念显式表达出来，而不是写成贫血的 set/get 大杂烩。下面是订单聚合根的 Go 实现——所有状态变更都必须通过聚合根的方法，禁止外部直接改字段：

// order.go —— 订单聚合根：业务规则全部内聚在这里
package order

import (
    "errors"
    "time"
)

// 订单状态机：Draft → Paid → Shipped → Completed / Cancelled
type Status string

const (
    StatusDraft    Status = "DRAFT"
    StatusPaid     Status = "PAID"
    StatusShipped  Status = "SHIPPED"
    StatusCompleted Status = "COMPLETED"
    StatusCancelled Status = "CANCELLED"
)

type Order struct {
    ID        string
    UserID    string
    Items     []OrderItem
    Status    Status
    TotalCents int64
    CreatedAt time.Time
}

type OrderItem struct {
    ProductID string
    Quantity  int
    UnitPrice int64
}

// NewOrder 是唯一的构造函数：强制做业务校验，不允许"非法状态"进入系统
func NewOrder(id, userID string, items []OrderItem) (*Order, error) {
    if len(items) == 0 {
        return nil, errors.New("order must have at least one item")
    }
    total := int64(0)
    for _, it := range items {
        if it.Quantity <= 0 {
            return nil, errors.New("item quantity must be positive")
        }
        total += int64(it.Quantity) * it.UnitPrice
    }
    return &Order{
        ID: id, UserID: userID, Items: items,
        Status: StatusDraft, TotalCents: total, CreatedAt: time.Now(),
    }, nil
}

// MarkPaid：状态流转是聚合根的职责，外部不能随便改 Status
func (o *Order) MarkPaid() error {
    if o.Status != StatusDraft {
        return errors.New("only draft order can be paid")
    }
    o.Status = StatusPaid
    return nil
}

// Cancel：取消必须有业务规则——已发货的订单不能取消
func (o *Order) Cancel(reason string) error {
    if o.Status == StatusShipped || o.Status == StatusCompleted {
        return errors.New("shipped/completed order cannot be cancelled")
    }
    o.Status = StatusCancelled
    return nil
}

对应的 protobuf 契约，体现"上下文之间只暴露需要的信息，不泄露内部模型"：

// order/v1/order.proto —— 订单服务对外契约
syntax = "proto3";
package order.v1;

option go_package = "github.com/example/ms/gen/order/v1;orderv1";

service OrderService {
  rpc CreateOrder(CreateOrderRequest) returns (CreateOrderResponse);
  rpc GetOrder(GetOrderRequest) returns (Order);
}

message CreateOrderRequest {
  string user_id = 1;
  repeated OrderItem items = 2;
  string idempotency_key = 3;  // 幂等键，防止重试重复下单
}

message OrderItem {
  string product_id = 1;
  int32 quantity = 2;
  int64 unit_price_cents = 3;
}

message Order {
  string order_id = 1;
  string user_id = 2;
  string status = 3;
  int64 total_cents = 4;
  int64 created_at_ms = 5;
}

生成 Go 桩代码的标准命令（proto 与 gRPC 是微服务契约的工业标准）：

# 安装 protoc 插件（一次）
go install google.golang.org/protobuf/cmd/protoc-gen-go@latest
go install google.golang.org/grpc/cmd/protoc-gen-go-grpc@latest

# 生成 Go 桩代码：--go_out 生成消息结构体，--go-grpc_out 生成服务接口
protoc -I ./proto \
  --go_out=./gen --go_opt=paths=source_relative \
  --go-grpc_out=./gen --go-grpc_opt=paths=source_relative \
  proto/order/v1/order.proto

拆分粒度的决策框架

事件风暴给出了候选边界，但不是每个限界上下文都值得拆成独立服务。实战中我会用下面这张"决策表"判断：

  • 变更频率：这个上下文和其他上下文一起改吗？如果每次改订单都要改库存，说明耦合还在，先别急着拆。
  • 扩缩容差异：库存计算是 CPU 密集、订单查询是 IO 密集吗？如果资源画像完全不同，拆出来可以独立伸缩。
  • 团队归属：这个上下文的代码现在是谁在改？如果三四个团队都在改，说明它已经是"公共泥潭"，必须拆。
  • 数据一致性要求：拆出去之后，跨上下文的事务能接受最终一致吗？如果不能，先在一个进程里把一致性做好。

最佳实践

  • 先做模块化单体，再拆微服务：在单体里用目录结构先模拟限界上下文，包之间通过接口调用、禁止跨包直接查别人的表。边界跑顺了，拆成进程只是"复制粘贴 + 加网络层"。
  • 防腐层保护内部模型：调用第三方或遗留系统时，在自己服务边界加一层 ACL（Anticorruption Layer），把对方的 DTO 翻译成自己的领域模型。不要让外部模型渗透到你的聚合根里。
  • 一个服务一个数据库 Schema：物理隔离比"约定俗成不查别人表"可靠得多。MySQL 可以用同一个实例不同 schema，但权限上要做到业务账号不能跨 schema 访问。
  • 事件 schema 版本化：发布到 MQ 的事件（如 OrderCreated）必须带版本号，新增字段用可选字段，永远不要改历史字段含义——否则下游服务会在你发版第二天凌晨 3 点挂掉。
  • 警惕"共享内核"陷阱：两个上下文共用一段模型看起来省事，但它意味着两边任何改动都要互相协调，半年后你就会怀疑自己当初为什么拆。

FAQ

Q1：我们业务很简单，也要画事件风暴、搞限界上下文吗？

业务简单的意思是"领域小"，但 DDD 的核心价值是统一语言，哪怕不拆服务也值得做：拉产品和开发一起贴两个小时便利贴，把"订单状态到底有几种""退款和退货有什么区别"这些扯皮问题在白板上定下来，比写代码三个月之后再返工便宜得多。

Q2：限界上下文和微服务是一对一的关系吗？

不是一对一，是多对一到一对多的演进关系。一开始一个限界上下文就是一个微服务；上下文内部大到一定程度（比如订单里又拆出售后、退款两个子域），可以再细分；两个小上下文如果变更总是一起上，也可以合并成一个服务。边界是演化的，不是刻在石头上的。

Q3：DDD 听起来很重，小团队用得起吗？

DDD 的战术模式（聚合、值对象、仓储）确实重，但战略模式（限界上下文、上下文映射、统一语言）几乎零成本。小团队只要做到三件事就赚了：① 业务名词在代码里一致；② 模块之间不跨表查；③ 开会时用同一套词。聚合根那一套可以等业务真的复杂了再上。

Q4：拆完之后发现两个服务总是要一起改，是不是拆错了？

很可能。回头检查：它们是不是共享了一个变化的业务规则？如果是，把这个规则下沉成一个独立的"规则服务"，或者把两个服务合并。拆分是手段不是目的，判断标准只有一个：独立交付是否真的变容易了。

总结

服务拆分的本质是业务边界在技术上的投影。DDD 提供了一套从业务语言出发、经过事件风暴识别限界上下文、再通过上下文映射决定集成方式的方法论。记住：先让业务边界清晰，再让代码边界对齐，边界对齐了才谈得上微服务。下一篇我们解决"服务拆出来之后，流量怎么进来、服务怎么互相找到对方"——也就是 API 网关与服务注册发现。
