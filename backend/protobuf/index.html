Protobuf 的编码与模式演进

2026-09-17 后端 / 序列化 约 18 分钟

Protobuf 真正需要吃透的只有两件事：字节层面的编码规则和模式演进的兼容性边界。前者决定了为什么一个 int32 存 -1 要占 10 字节，后者决定了哪些改动可以随手提交、哪些改动会在几周后变成一起数据事故。传输层的多路复用、流控与错误模型不在这篇，见站内 gRPC 的传输机制与工程落地；框架抽象与选型见站内 RPC 框架的抽象层次与选型。

wire format：一条消息在字节层是什么样

Protobuf 的编码模型简单到可以背下来：消息就是一串「tag + payload」的重复，没有消息头，没有字段总数，没有 schema 信息。tag 本身是一个 varint，低 3 位是 wire type，其余位是字段号（tag = 字段号 << 3 | wire type）。解析器靠 wire type 知道后面该读几个字节，靠字段号知道这是哪个字段——所以字段名从头到尾没进过字节流。

举个能手算的例子：int32 age = 4; 赋值 150，编码结果是 20 96 01 三个字节。0x20 是 tag（字段号 4 左移 3 位，wire type 0），96 01 是 150 的 varint。string id = 1; 赋值 "ab" 则是 0A 02 61 62：tag、长度 2、两个字符。

wire type 对应类型 读法 工程含义
0 VARINT int32 / int64 / uint32 / uint64 / sint32 / sint64 / bool / enum 每字节 7 位有效，最高位是延续标志 小数值极省，负数和大数值反而更费
1 I64 fixed64 / sfixed64 / double 固定 8 字节小端 数值普遍很大时比 varint 省，且解析无分支
2 LEN string / bytes / 嵌套 message / packed repeated / map varint 长度 + 内容 嵌套 message 与 bytes 在字节层无法区分，这是二者可互换的原因
3 / 4 SGROUP / EGROUP 已废弃的 group 成对的起止标记 新代码不会用到，但解析器仍需识别，遇到就是老 proto2 遗产
5 I32 fixed32 / sfixed32 / float 固定 4 字节小端 哈希值、定长 ID 用它比 varint 稳定

varint 与 ZigZag：负数的代价

varint 每字节只用 7 位存数据，所以 0-127 占 1 字节，128-16383 占 2 字节。问题出在负数：int32 的负值会先按二进制补码扩展成 64 位再编码，固定占 10 字节。这是「int32 比 int64 省空间」这一常见误解的翻车点——存负数时两者一样费，而且都比 sint32 差一个数量级。

sint32 / sint64 用 ZigZag 把符号折进低位：(n << 1) ^ (n >> 31)，把 -1 映射成 1、1 映射成 2、-2 映射成 3。于是 -1 只占 1 字节。凡是「差值、偏移量、经纬度增量、正负都可能出现」的字段，都该用 sint。

取值特征 推荐类型 为什么 选错的后果
非负且多数很小（计数、状态） uint32 / int32 1-2 字节即可编码 用 fixed32 固定 4 字节，高频字段整体膨胀
正负都有且绝对值不大（差值、增量） sint32 / sint64 ZigZag 让负数与同绝对值正数等价 用 int32 时每个负值 10 字节
数值普遍接近上限（哈希、雪花 ID） fixed64 / sfixed64 定长 8 字节，比 varint 的 9-10 字节更省 用 int64 时几乎每个值都要 9 字节以上
金额、计量 int64 存最小单位 避免浮点误差，跨语言一致 用 double 存金额，对账时必然出现分位误差
枚举 enum（proto3 开放枚举） varint 编码，未知值会被保留 用字符串存状态，体积和校验都亏

字段号：唯一不可回收的资源

字段号的合法范围是 1 到 536870911，其中 19000-19999 被实现自身保留。真正的工程约束是两条：1-15 的 tag 只占一个字节，所以高频字段要优先占这段；任何字段号一旦发布就永久作废，删除后必须 reserved。

为什么复用如此致命？因为解析端只认号。旧版本写出的字节里还留着旧字段，新版本把这个号解释成新字段——如果两者 wire type 恰好相同（比如都是 varint），一个错误都不会报，只是静默写入脏数据。这类事故通常在几周后从对账差异或诡异的业务分支里才浮出水面。

syntax = "proto3";

package order.v1;   // 包名带版本，破坏性变更时新开 v2，不在原地改

message Order {
  // 1-15 的 tag 只占 1 字节，留给高频字段
  string id = 1;
  int64  amount_cents = 2;     // 金额用最小单位的整数，不用 double
  sint64 balance_delta = 3;    // 会出现负数，用 sint 才不会每次 10 字节

  reserved 4, 7 to 9;          // 删掉的字段号永久占位
  reserved "legacy_status";    // 名字也要占位，防止在 JSON 侧复活

  optional bool notify = 5;    // 显式存在性：能区分「没传」和「传了 false」

  map<string, string> labels = 6;  // 等价于 repeated LabelsEntry，顺序不保证

  oneof payment {              // 互斥字段放 oneof，字节层只是普通字段，最后写入的生效
    CardPayment card = 10;
    WalletPayment wallet = 11;
  }

  // proto3 数值 repeated 默认 packed（wire type 2），改回 singular 会读不到
  repeated int64 item_ids = 12;
}

存在性语义：proto3 的零值歧义

这是 Protobuf 最容易埋雷的地方。proto3 的标量字段是隐式存在性：等于默认值时压根不写进字节流。于是「用户把开关关成 false」和「用户没传这个字段」在解析端是同一个结果。批量更新接口如果照着这个语义写，就会出现「想关闭却关不掉」的经典缺陷。

三点需要澄清：message 类型字段永远有显式存在性（nil 与空消息可区分）；repeated 和 map 从来没有存在性概念，空就是空；proto3 的 optional 不是 proto2 的复活，它在实现上是一个合成 oneof，只是给字段加回了显式存在性。另外，2023 年起 protobuf 引入 Editions 取代 syntax 二分法，把 proto2/proto3 的行为差异拆成 field_presence、enum_type、repeated_field_encoding 这类可逐项设置的 feature，wire format 完全没变，所以它是编译期与语义层的演进，不是数据格式升级。

魔法值（-1 表示未设置） 看起来能 零成本 无区别 不要用：约定无法进 schema，新同事必然踩

oneof 与 map 的底层表示

两个语法糖，理解了底层表示就知道它们的兼容性边界在哪。

oneof 在字节层不存在。它的成员就是普通字段，各自有自己的号。互斥是解析器的行为：解码时后出现的成员覆盖前面的，所以两个成员同时出现在字节流里不会报错，只是「最后一个赢」。这意味着把单个已有字段移进一个新建 oneof 是 wire 兼容的，而把多个已有字段合并进同一个 oneof 是不兼容的——老客户端会同时设置它们，新代码只能看到一个。

map 是 repeated message 的糖。map<K, V> 等价于 repeated MapFieldEntry，entry 里键是字段 1、值是字段 2，不 packed。推论有三条：键重复时后者覆盖前者，不会报错；顺序不保证，因此序列化结果不能当指纹或缓存 key；map 与对应的 repeated entry message 之间可以互相改写，wire 层完全兼容，这是给 map 加第三个属性时的正规迁移路径。

模式演进的兼容性矩阵

把常见改动按「旧代码读新数据」和「新代码读旧数据」两个方向拆开看，结论就很清晰了。

改动 旧代码读新数据 新代码读旧数据 结论
新增字段（新号） 忽略并作为未知字段保留 字段缺失，取默认值或 unset 安全，唯一推荐的加字段方式
删除字段并 reserved 号与名 正常 忽略残留的旧字段 安全
删除字段但不 reserved 正常 正常 当下无事，未来被复用时变成事故，等于埋雷
复用旧字段号 / 改字段号 解释成另一个字段 解释成另一个字段 禁止。wire type 相同时静默污染数据
改字段名 二进制不受影响 二进制不受影响 wire 安全，但 JSON、text format、生成代码、按名映射的下游全断
int32 与 int64 / uint / bool 互换 可解析，可能截断 可解析，符号可能翻转 有条件安全，必须确认取值范围
int32 与 sint32 互换 数值错乱 数值错乱 禁止，ZigZag 编码不同
int32 与 fixed32 互换 wire type 不符，落入未知字段 同上 禁止
string 与 bytes 互换 可解析 可解析 安全，前提是内容为合法 UTF-8
嵌套 message 与 bytes 互换 可解析 可解析 安全，二者都是 LEN，常用于延迟解析
singular 数值改 repeated 只取最后一个值 proto3 默认 packed，wire type 变 2，旧 singular 读不到 不安全，要走新字段号迁移
单个字段移入新建 oneof 正常 正常 安全；多个已有字段合并进一个 oneof 则不安全
enum 新增值 proto3 开放枚举保留未知值；proto2 闭合枚举把它丢进未知字段 正常 下发新枚举值前，先确认所有读侧都升级完

未知字段：保留还是丢弃

未知字段就是解析器「不认识但原样收着」的字节。它是灰度发布能成立的基础：中间层用旧 proto 转发新版本消息时，字段不会丢。但这件事在 proto3 上有过一次反转——proto3 早期版本会直接丢弃未知字段，3.5 起恢复保留。至今仍有人按「proto3 不保留未知字段」的旧结论做设计。

场景 未知字段行为 工程后果
proto2 各语言 保留 转发型服务天然安全
proto3，3.5 之前 解析即丢弃 老版本库做网关会静默吃字段
proto3，3.5 及以后 保留 与 proto2 行为一致
JSON 解析 默认报错，开启忽略选项后丢弃，永不保留 proto 转 JSON 再转回来必然掉字段
text format 默认不接受未知字段 配置类场景升级顺序要卡死
Any 字节原样保留，但缺描述符无法解包 中转安全，消费方必须能拿到对应 schema

JSON 映射与跨语言差异

Protobuf 有一套标准 JSON 映射，但它和「把结构体直接 JSON 序列化」差别很大，跨语言联调时一半的问题出在这里。

关注点 标准 JSON 映射规则 容易踩的地方
字段名 默认输出 lowerCamelCase，解析时同时接受原始 snake_case 前端按 snake_case 取值，换库或换语言后取不到
64 位整数 int64 / uint64 / fixed64 输出为字符串 前端当数字处理，超过 2 的 53 次方后精度丢失
bytes 标准 base64 与 URL-safe base64 混用会解码失败
enum 输出名字字符串，解析接受名字与数字 未知数字值的处理各实现不一致
默认值字段 隐式存在性且为零值时被省略 下游按「字段一定存在」写代码；需要时打开输出默认值的选项
Duration / Timestamp 字符串，如 3.5s 与 RFC 3339 的 Z 时间 当成数字秒或本地时间处理
NaN 与 Infinity 输出为字符串形式 标准 JSON 无法表达，严格解析器会直接失败

schema 治理与破坏性变更的 CI 拦截

兼容性规则再清楚也挡不住手滑，唯一可靠的办法是让 CI 来判。buf breaking 把检查分成几档，选档位就是选你的接口边界。

检查档位 拦住什么 适用边界
WIRE 只拦二进制不兼容（改号、改 wire type 等） 纯内部二进制通信，改名自由
WIRE_JSON 二进制加 JSON 名称兼容，改字段名会被拦 有 JSON 网关或前端直连
PACKAGE 包级 API 兼容，删除与改名都拦 proto 作为公共库被多仓引用
FILE 最严格，文件与符号位置变化也拦 同仓统一发布、要求生成代码稳定 
# 1) 手上只有一段字节流：不需要 .proto，直接看 tag 与 wire type
protoc --decode_raw < payload.bin

# 2) 有 .proto 时按 schema 解码，字段名与嵌套结构都能看到
protoc --decode=order.v1.Order order/v1/order.proto < payload.bin

# 3) protoscope 展示最原始的 tag / 长度 / 字节，排查长度前缀错位最好用
protoscope payload.bin

# 4) CI 里拦破坏性变更：与主干比对，档位在 buf.yaml 的 breaking.use 里选
buf breaking --against 'https://github.com/org/repo.git#branch=main'

// 1) 显式存在性：proto3 的 optional 在 Go 里生成指针，nil 才是「没传」
switch {
case o.Notify == nil:
    // 客户端没提这个字段，沿用服务端默认策略

    // 客户端明确传了 false，要真的关掉通知

// 2) 未知字段在 Go 里默认保留，代理型服务转发时不会吃掉新版本字段
raw, _ := proto.Marshal(msg)                  // 未知字段原样带出

// 3) 不要把序列化结果当稳定指纹：map 顺序、未知字段位置、库版本都会影响字节

// Deterministic 只保证同一进程内 map 有序，不是跨语言跨版本的 canonical form
_, _, _ = raw, unknown, canonical

最容易踩的坑

❌
避坑清单
  • 删字段只删定义，不写 reserved。当下毫无异常，等到某次迭代复用了这个号，旧数据就被解释成新字段，且 wire type 相同时一个错都不报。
  • 以为 int32 一定比 int64 省。存负数时两者都是 10 字节，该用的是 sint32 / sint64。
  • 把 ID 或哈希这类接近上限的大整数存成 int64，几乎每个值都要 9 字节以上，fixed64 只要 8 字节且解析更快。
  • 在 proto3 里用零值表达「没传」。开关关不掉、数量改不成 0，这是最高频的业务缺陷来源。
  • 用 -1 或空字符串当 unset 的约定。约定进不了 schema，跨团队协作必然失传。
  • 为了「更规范」批量改字段名。二进制没事，但 JSON 网关、前端、日志采集、数仓任务会同时静默少一列。
  • 把多个已有字段合并进一个新 oneof。老客户端会同时设置它们，新代码只能看到最后一个。
  • 把 singular 数值字段改成 repeated。proto3 的数值 repeated 默认 packed，wire type 从 0 变 2，旧代码直接读不到。
  • 用 map 的序列化结果做签名、去重 key 或幂等键。map 顺序不保证，同一份数据可能产出不同字节。
  • 在链路里插一段 JSON 中转（比如落库或走消息体转换）。未知字段全部消失，灰度期的新字段莫名不生效。
  • 下发新枚举值时没确认读侧版本。proto2 的闭合枚举会把未知值丢进未知字段，业务分支直接走错。
  • 只靠 code review 保证兼容性，不在 CI 里跑 buf breaking。这类错误的特征就是评审时看不出来、上线后很久才爆。
