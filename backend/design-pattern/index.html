设计模式的本质与代价：接缝、SOLID 取舍与现代语言内建能力

🏷️ 设计模式

GoF 二十三个模式的名字不值得背。值得记住的只有一件事：每个模式都是在「预期会变化的地方」切开一道接缝（seam），把变化关进接缝后面，代价是调用方与实现之间多了一层间接。所以真正的问题从来不是「这个场景该用哪个模式」，而是「这个变化真的会发生吗，它发生一次的改动成本能不能抵掉这一层间接带来的长期理解成本和排障成本」。这篇讲模式的本质与代价、SOLID 里哪几条在日常真的有用、组合为什么优于继承，以及哪些模式已经被现代语言和框架吃掉——需要你亲手写的模式，比教科书列出的少得多。

模式的本质：在预期会变化的地方留一道接缝

把三类模式放在一起看，它们隔离的是三种不同的变化：创建型隔离「用哪个实现」，结构型隔离「外部结构与内部模型的差异」，行为型隔离「算法与流程的编排」。共同点是都在调用方和真正干活的代码之间插入了一个中间物——接口、包装类，或者一张注册表。

「接缝」这个词比「解耦」准确得多。解耦是个形容词，谁都可以说自己在解耦；接缝是个名词，它必须指向一个具体的变化假设：我在这里留一道缝，是因为我预期支付渠道会从一家变成三家、预期导出格式会从 CSV 增加到 Excel、预期风控规则要能配置化。写下接缝的同时必须写下这个假设，否则半年后没人知道这层抽象为什么存在，也就没人敢删。

💡
判断一层抽象是否合格的最短问题

「如果这个变化真的来了，我要改几个文件？如果这个变化永远不来，我多付了什么？」两个答案都要能说出具体数字。说不出第二个答案的人，通常是把间接层当成了免费的。

判断标准：这个变化真的会发生吗

绝大多数过度设计都来自一个没被检验的预测。可执行的判断顺序是：先问有没有第二个真实需求，再问变化频率，再问变化是否跨越模块或团队边界（跨边界的变化值得固定接口，因为沟通成本比代码成本高一个数量级），最后问能不能用更轻的手段——传一个函数、查一张配置表——而不是新建一套类层次。

过度设计的成本清单：它贵在排障

「多一层间接」听起来抽象，落到线上就是一连串具体的钱。下面这条链路是很多项目的常态：控制器到门面、门面被事务代理包一层、代理里按渠道选策略、策略执行的处理器又被三个装饰器包着，最后才到仓储。正常路径它跑得很好，出问题时你要在五个文件之间来回跳，而堆栈上半截全是框架生成的类名。

SOLID 的实用解读：只有两条高频有用

把 SOLID 当成五条必须同时满足的戒律是最常见的误读。按实际收益排序，日常真正高频有价值的只有 S 和 D；O 最容易被误用；L 和 I 在以数据流转为主的业务代码里几乎不触发，它们的价值集中在会被广泛继承的基类和对外发布的 SDK。

原则 日常价值 最常见的误用 真正触发的场景
S 单一职责 高。让「修改原因」收敛，直接降低冲突和回归范围 按行数拆类，把一个内聚流程拆成互相调用的碎片 一个类同时被两批人因为两种原因修改
O 开闭 低到中。收益真实但极易过头 为「以后可能扩展」预留抽象，做出永远只有一个实现的接口 插件化、规则频繁上下线、对外提供扩展点
L 里氏替换 低。业务代码继承层次本来就浅 拿它论证「不能用继承」 设计会被外部继承的基类，或重写方法收窄了前置条件
I 接口隔离 低。除非接口是对外契约 把一个 5 方法接口拆成 5 个单方法接口，调用方要注入五个依赖 实现类被迫写一堆空方法或抛不支持异常时
D 依赖倒转 高。可测性和边界隔离的前提 给所有类都加接口，而不只是外部依赖 业务逻辑要摆脱数据库、第三方 SDK、时钟、随机数

D 的正确用法是只对「跨边界的东西」倒转：数据库、消息中间件、第三方 HTTP 接口、当前时间、随机数、文件系统。对这些东西倒转依赖，单测就能在毫秒级跑完且结果稳定；测试替身的五种分类与可测性设计的完整讨论详见站内「后端测试」那篇。而对同一个包里的两个纯计算类倒转依赖，只会多出两个文件。

组合优于继承：脆弱基类的代价是具体的

「组合优于继承」被引用得太多，以至于变成了口号。它的理由其实很具体：继承是编译期绑定，子类拿到的是父类的实现细节而不只是契约，父类内部把一个方法改成调用另一个方法，子类行为就可能错乱——这就是脆弱基类问题。下面是那个经典例子的可运行版本，它在真实项目里以各种变体反复出现。

// 反例：用继承给 ArrayList 加「累计插入计数」
// 脆弱点：父类 addAll 的默认实现会逐个调用 add，于是每个元素被计两次
class CountingList<E> extends java.util.ArrayList<E> {
    private int added;

    @Override public boolean add(E e) {
        added++;
        return super.add(e);
    }

    @Override public boolean addAll(java.util.Collection<? extends E> c) {
        added += c.size();          // 加一次
        return super.addAll(c);     // 父类内部又逐个调 add，再加一次，结果翻倍
    }

    int added() { return added; }
}

// 正解：组合加委托。只依赖 Collection 的公开契约，父类内部怎么实现与我无关
final class CountingCollection<E> {
    private final java.util.Collection<E> delegate;   // 接缝就是这一个字段
    private int added;

    CountingCollection(java.util.Collection<E> delegate) {
        this.delegate = delegate;                     // 测试时可以传入任意实现
    }

    boolean add(E e) {
        added++;
        return delegate.add(e);
    }

    boolean addAll(java.util.Collection<? extends E> c) {
        added += c.size();
        return delegate.addAll(c);                    // 它内部再怎么调 add 都进不到我的计数
    }

    int added() { return added; }
}

第二个理由是维度爆炸。导出功能要支持 CSV 和 JSON、要支持压缩、要支持加密，用继承就得为每种组合建一个类，类数量是各维度的乘积；用组合则是把能力做成可叠加的包装，类数量是各维度的和。第三个理由是多继承的菱形冲突：两条继承路径带来同名成员时，语言要么禁止（Java 只允许单继承类），要么要求显式指定优先级（C++ 虚继承、Python MRO），这些规则本身就是复杂度。

维度 继承 组合加委托
绑定时机 编译期固定，一个对象一辈子只能是一种 运行期装配，可按配置切换与叠加
依赖的东西 父类的实现细节，即哪个方法调了哪个 被委托对象的公开契约
父类改动影响 内部调用顺序一变，所有子类可能行为错乱 只要签名和语义不变，包装类不受影响
多维扩展 类数按维度乘积增长，命名很快失控 类数按维度相加，用装配表达组合
可测性 要测子类必须带上整个父类行为 委托对象可替换成测试替身
样板代码 少，白拿父类所有方法 多，接口方法要逐个转发；Kotlin 的 by、Go 的匿名嵌入可省掉
仍然适用时 稳定的「就是一种」关系；框架里明确文档化了可覆盖点的模板基类 能力可叠加、需要运行期替换、需要跨边界隔离

现代语言已经内建了哪些模式

GoF 成书于 1994 年，目标语言是 C++ 和 Smalltalk，很多模式本质上是在绕语言的缺陷。语言补上能力之后，模式就该退场。下面这张表值得逐行对照自己的代码库，多半能删掉几百行样板。

模式 传统样板 现代语言内建能力 什么时候仍然值得建类
策略 接口加 N 个实现类加工厂 闭包、函数类型、方法引用；Java 的 Function 与 Predicate 策略自身有状态、需要注入依赖、需要按名字被配置引用
命令 Command 接口加 execute 实现类 Runnable、捕获参数的闭包、Go 的 func 值 命令要序列化、要持久化重放、要支持撤销
适配器 显式声明 implements 的包装类 Go 的 interface 隐式实现，方法签名对上就满足接口 要做字段语义与错误码翻译时仍要写，但薄得多
工厂与单例 静态 getInstance、XxxFactory DI 容器管理生命周期与作用域 创建过程依赖运行期入参，容器无法表达
空对象 NullOrder、EmptyList 之类哨兵类 Optional、Rust 的 Option、Kotlin 可空类型 需要给空值挂上默认行为而不只是表示空
迭代器 自己实现 hasNext 与 next for-range、生成器、Iterable 与 Stream 遍历外部资源需要控制分页与关闭时机
Builder 内部 Builder 类加链式 setter record、data class、命名参数与默认参数 需要分步构造并在 build 时校验不变量
模板方法 抽象基类加 protected 钩子 把可变步骤作为函数参数传入 钩子多且彼此有调用顺序约束
观察者 手写 Subject 与监听列表 框架事件总线、channel、响应式流 需要自定义投递顺序、失败重试、事务绑定

一个具体对照：策略模式的现代形态就是「把函数放进 map」。下面这段 Go 代码替掉的是「接口加三个实现类加一个工厂加一个枚举」共五个文件。

// 传统写法：一个 DiscountStrategy 接口外加三个实现类和一个工厂
// 现代写法：策略就是一个函数类型，注册表就是一个 map
type Discount func(cents int64) int64

var discounts = map[string]Discount{
    "none":   func(c int64) int64 { return c },
    "vip":    func(c int64) int64 { return c * 90 / 100 },        // 整数分运算，避免浮点误差
    "coupon": func(c int64) int64 { return maxInt64(c-1000, 0) }, // 满减 10 元，下限 0
}

func Price(kind string, cents int64) (int64, error) {
    f, ok := discounts[kind]
    if !ok {
        // 关键：未知类型必须显式失败。静默回退到不打折会把配置错误变成资损或客诉
        return 0, fmt.Errorf("unknown discount kind %q", kind)
    }
    return f(cents), nil
}

func maxInt64(a, b int64) int64 {
    if a > b {
        return a
    }
    return b
}

代价也要说清楚：map 注册让新增策略不用改主流程，但也让「谁在什么时候调用了哪个策略」无法靠静态搜索得到，排查线上行为异常时只能靠日志把 kind 打出来。这个取舍在行为型那篇会展开。

框架时代：容器接管之后模式怎么变

在 Spring 这类容器里，一半的创建型模式已经被容器实现了，你再手写就是和容器抢生命周期。最典型的错误是「在 Spring 项目里用静态字段实现单例」：这个对象无法参与依赖注入、无法被测试替换、无法收到销毁回调，还常常因为类加载时机早于配置就绪而拿到空配置。

传统模式做法 框架下的正确做法 为什么
静态 getInstance 单例 声明为 Bean，默认作用域就是单例 容器统一管生命周期，可注入、可替换、有销毁回调
XxxFactory 按类型 new 一个带条件的 Bean 定义方法，或注入所有实现的集合 条件装配与配置绑定由容器完成，少一个手写分支
抽象基类做模板方法 把可变步骤作为回调传入，例如把行映射函数交给查询模板 组合代替继承，调用方不必进入类层次
手写代理做日志和事务 声明式注解，由 AOP 自动生成代理 横切逻辑与业务分离；代理机制与自调用失效详见站内 Spring 核心那篇
自己写重试与降级包装 用框架的熔断与舱壁能力 阈值、指标、半开探测都是现成的；原理详见站内熔断与舱壁那篇
自己写事件分发器 容器事件或消息中间件 同步与异步、事务绑定、失败处理有统一约定

顺着这条线还有一层：领域层的边界隔离不是靠「多写一层接口」，而是靠把外部模型挡在适配器外面，聚合与限界上下文的划分方法详见站内 DDD 拆分那篇，这里不重复。

反模式：模式被误用的六种典型形态

反模式 识别信号 后果 修法
为「以后可能扩展」引入抽象 接口注释写着预留扩展，但没有第二个实现 抽象按唯一实现的形状定义，真正第二个实现来时反而要推翻 删掉接口直接用类，第二次改动时再抽
一个接口只有一个实现 清一色的 XxxService 与 XxxServiceImpl 改方法签名要动两个文件，跳转多一跳，毫无收益 只对跨边界依赖保留接口，内部逻辑直接用类
把模式名写进类名 出现 OrderServiceStrategyFactoryImpl 这类名字 类名描述实现手法而不是业务职责，读者要先解码 按业务语义命名，例如 DiscountRules、PaymentGateway
用模式炫技 三十行业务逻辑用了四个模式，评审时作者要讲十分钟 维护者不敢改，只能在边缘打补丁 先写朴素实现跑通，再针对真实出现的变化重构
把所有 if-else 改成策略类 原来一屏能读完的分支变成二十个文件，每个十行 逻辑分散，读完整规则要打开二十个文件，全局搜索找不到调用点 分支少于 5 且稳定就保留 if-else，多且会增删才做注册表
每层都加只做转发的包装 三个类方法签名完全相同，方法体只有一行调用 调用链凭空变长，异常和堆栈都多绕几层 合并转发层，只在有真实翻译或校验时保留一层

  • 为想象中的需求预留扩展点：接口按第一个实现定形，真正的第二个实现来时必须改接口，所有实现一起返工，比当初写死更贵。
  • 在 Spring 项目里用静态字段自己实现单例：拿不到注入的配置，测试无法替换，类加载顺序早于配置就绪时会读到空值。
  • 把接口加在纯内部逻辑上：可测性一点没涨，只是每次改签名要改两个文件，还让跳转到实现多一跳。
  • 用继承复用代码而不是表达类型关系：父类内部把一个方法改成调用另一个方法，子类计数翻倍或校验被跳过，这类 bug 极难定位。
  • 装饰器和代理叠三层以上又各自 catch 重新包装异常：cause 链断掉，线上只看到「系统异常」，根因永远查不到。
  • 用 map 注册策略却对未知 key 静默回退默认值：配置写错一个字母，线上按不打折或最低费率跑，事后对账才发现。
  • 抽象层里悄悄藏了远程调用或序列化：耗时被摊到多层，火焰图看不出尖峰，只能看到接口 P99 高而每层自身耗时都不高。
  • 把一个内聚流程按行数拆成多个类，还声称遵守单一职责：修改原因没有分离，反而要同时改五个文件，冲突概率上升。
  • 接口隔离做过头：五方法接口拆成五个单方法接口，调用方构造器注入五个依赖，装配代码比业务代码还长。
  • 类名堆模式词：名字描述实现手法而非职责，半年后没人记得它在业务里代表什么，也不敢删。
  • 抽象没有写下变化假设：评审时说不出「这层是为了应对什么变化」，后续所有人只能保守地继续加层。
  • 只看抽象的收益不核算固定成本：间接层的排障成本每天都在付，而它防的那个变化可能永远不来。
