结构型模式的边界价值：适配器防腐、装饰器与代理的分野、门面收窄依赖

🏷️ 结构型设计模式

结构型模式在代码上长得几乎一样：都是持有一个同类型对象，然后转发调用。区分它们的不是结构而是意图——适配器翻译语义、装饰器叠加功能、代理控制访问、门面收窄依赖面。意图搞错就会写出一堆只做转发的包装类，这是结构型模式最常见的误用。这篇讲清四种「包一层」各自解决什么压力，以及它们在什么变化下会反过来成为负担。

四种「包一层」的意图差异

把七个结构型模式放在一张表里看意图和现代替代，能省掉很多纠结。真正在后端业务代码里高频出现的只有三个：适配器、代理、门面；装饰器中频；组合只在有树形数据时出现；桥接和享元在业务代码里基本退化成了别的东西。

模式意图调用方是否知道多了一层现代替代或退化形态业务代码频率
适配器把外部模型翻译成内部模型知道，它就是边界层不可替代，但 Go 隐式接口让它更薄高，所有对外集成都要
装饰器在不改原类的前提下叠加功能知道，且通常由它决定顺序函数包装、中间件写法中，缓存与重试包装最常见
代理控制访问，插入横切行为不知道，代理对调用方透明AOP 自动生成，无需手写高，但多由框架实现
门面收窄外部对内部的依赖面知道，它是对外的唯一入口应用服务层、BFF 接口高
组合让单个对象与对象树用同一套接口处理知道无替代，但可用迭代遍历取代递归低到中，菜单与权限树场景
桥接让抽象与实现两个维度独立变化知道实践中就是「持有一个接口字段」的组合极低，几乎不需要单独命名
享元共享不可变对象以省内存不知道常量池、装箱缓存、本地缓存极低，手写场景基本消失

适配器：边界翻译，不是简单转发

适配器是所有结构型模式里最值得写的一个，因为它承担一件别人替不了的事：把外部系统的世界观挡在边界外。它是防腐层的具体实现手段（限界上下文与防腐层的划分方法详见站内 DDD 拆分那篇，这里只讲实现）。合格的适配器至少翻译三样东西：字段语义、错误语义、不确定状态。

sequenceDiagram autonumber participant S as 内部下单服务 participant AD as 支付适配器（边界） participant T as 第三方支付网关 S->>AD: pay(orderId, 金额以分为单位, 幂等键) AD->>AD: 翻译：分转元字符串、时间转对方时区、拼签名 AD->>T: POST 统一下单，带 out_trade_no 幂等键 T-->>AD: 返回 result_code 与 err_code 组合 AD->>AD: 错误码归类：可重试、明确失败、状态未知 AD-->>S: 返回内部枚举 SUCCESS 或 FAILED 或 UNKNOWN Note over AD,T: 关键：网络超时不能当作失败
对方可能已受理，必须落「状态未知」并触发查询对账 S->>AD: 超时后按幂等键发起查单 AD->>T: 查询订单状态 T-->>AD: 已支付 AD-->>S: 纠正为 SUCCESS 
// 内部模型：只有内部语义，绝不出现第三方的字段名与错误码
public enum PayResult { SUCCESS, FAILED, UNKNOWN }        // UNKNOWN 必须存在，否则超时只能瞎猜
public interface PaymentGateway {                          // 内部定义的接口，形状由内部需要决定
    PayResult pay(String orderId, long amountCents, String idempotencyKey);
}

// 适配器：第三方 SDK 的一切怪癖都被关在这个类里
public final class AcmePayAdapter implements PaymentGateway {
    private final AcmeClient client;                        // 第三方 SDK
    private static final java.util.Set<String> RETRYABLE =
            java.util.Set.of("SYSTEMERROR", "BANKERROR", "FREQUENCY_LIMITED");

    public AcmePayAdapter(AcmeClient client) { this.client = client; }

    @Override
    public PayResult pay(String orderId, long amountCents, String idempotencyKey) {
        // 翻译一：字段语义。对方金额是「元」的字符串，内部统一用「分」的 long，避免浮点与单位混用
        AcmeRequest req = new AcmeRequest();
        req.setOutTradeNo(idempotencyKey);                  // 对方用商户订单号做幂等，内部用幂等键，语义要对齐
        req.setTotalFee(String.valueOf(amountCents));       // 该渠道其实收的是分，另一家收元，差异必须锁在适配器内
        req.setTimeExpire(java.time.Instant.now().plusSeconds(1800).toString());
        try {
            AcmeResponse resp = client.unifiedOrder(req);
            // 翻译二：错误语义。对方把业务失败与系统失败混在一个 result_code 里，内部必须拆开
            if ("SUCCESS".equals(resp.getResultCode())) return PayResult.SUCCESS;
            if (RETRYABLE.contains(resp.getErrCode())) return PayResult.UNKNOWN;   // 可重试等价于状态未知
            return PayResult.FAILED;                                               // 明确失败，例如余额不足
        } catch (java.net.SocketTimeoutException e) {
            // 翻译三：不确定状态。超时绝不能当失败，对方可能已受理，必须交给查单对账收敛
            return PayResult.UNKNOWN;
        } catch (AcmeSdkException e) {
            // 不让第三方异常类型泄漏到内部，否则整个工程都会 import 它
            throw new PaymentGatewayException("acme pay failed, orderId=" + orderId, e);
        }
    }
}
对方返回对方含义内部结果后续动作
result_code 为 SUCCESS受理并支付成功SUCCESS推进订单状态，注意用条件更新防重复推进
err_code 为 NOTENOUGH余额不足FAILED直接失败，提示用户换支付方式，不重试
err_code 为 SYSTEMERROR对方系统异常，结果未知UNKNOWN按幂等键查单，指数退避，最多查 N 次后转人工
HTTP 读超时请求可能已到达并被受理UNKNOWN同上，绝不能当失败让用户重下单
连接超时且未发出基本可判定未受理仍按 UNKNOWN 处理代价最低的安全选择，查一次单即可确认
签名校验失败配置或密钥问题抛异常不进业务流程，直接告警，属于部署问题

装饰器与代理：结构相同，意图相反

这两个模式被混淆的频率最高，因为代码长得一模一样。区别只有两条：装饰器是加功能，调用方明确知道自己在装饰，因此能决定叠加顺序；代理是控制访问，对调用方透明，调用方以为拿到的就是原对象。

维度装饰器代理
意图增强行为控制是否、何时、由谁访问
调用方感知知道，装配代码由调用方写不知道，通常由容器或框架注入
可否叠加可以，且顺序影响语义一般一层，多层由框架统一编排
被包装对象的生命周期由外部创建后传入常由代理自己创建或延迟创建
典型用途缓冲流、压缩、加密、缓存、重试、限流包装懒加载、远程调用、权限校验、事务、日志、指标
接口关系与被装饰对象实现同一接口，也允许扩展新方法必须与被代理对象接口一致，不能改变契约
调试难点不知道行为被哪一层改了堆栈里全是生成类，源码里搜不到
 
// 装饰器：同接口、持有下一层、只加一件事。注意顺序敏感
public interface PriceQuery { long quote(String sku); }

// 基础实现：真正去下游拿价格
final class RemotePriceQuery implements PriceQuery {
    public long quote(String sku) { return httpGetPrice(sku); }
}

// 装饰一：缓存
final class CachedPriceQuery implements PriceQuery {
    private final PriceQuery next;
    private final java.util.Map<String, Long> cache;
    CachedPriceQuery(PriceQuery next, java.util.Map<String, Long> cache) { this.next = next; this.cache = cache; }
    public long quote(String sku) {
        Long hit = cache.get(sku);
        if (hit != null) return hit;
        long v = next.quote(sku);
        cache.put(sku, v);       // 只缓存成功结果；如果 next 抛异常，这里不会写入，避免缓存失败态
        return v;
    }
}

// 装饰二：重试
final class RetryingPriceQuery implements PriceQuery {
    private final PriceQuery next;
    private final int maxAttempts;
    RetryingPriceQuery(PriceQuery next, int maxAttempts) { this.next = next; this.maxAttempts = maxAttempts; }
    public long quote(String sku) {
        RuntimeException last = null;
        for (int i = 0; i < maxAttempts; i++) {
            try { return next.quote(sku); }
            catch (RuntimeException e) { last = e; sleepBackoff(i); }
        }
        throw last;
    }
}

// 装配：顺序决定语义，务必集中在一处并写明原因
// 正确：缓存在最外层，命中时完全不进重试，重试只作用于真实远程调用
PriceQuery q = new CachedPriceQuery(new RetryingPriceQuery(new RemotePriceQuery(), 3), cache);
// 错误：重试在最外层，一次失败会把缓存查询也重复执行，且重试期间的缓存写入时机难以推理
// PriceQuery bad = new RetryingPriceQuery(new CachedPriceQuery(new RemotePriceQuery(), cache), 3);

装饰器链的代价集中在排障：堆栈里三层的方法名都叫 quote，看不出是哪一层改了行为；某一层悄悄吞掉异常或替换了参数，问题表现的位置与根因相距很远。可操作的做法是把装配顺序集中在一个配置类里并写注释说明原因，同时让每层在开启调试日志时打印自己的类名与关键决策（命中缓存、第几次重试）。

AOP 就是自动生成的代理

理解这一句，AOP 的一切「诡异行为」都能推导出来：框架在启动时为你的 Bean 生成一个代理对象，注解逻辑写在代理里，只有经过代理的调用才会触发注解。于是同一个类里方法 A 用 this 调方法 B，B 上的事务、缓存、限流注解全部失效，而且没有任何报错——因为这次调用从头到尾没有出过这个对象，代理没有机会介入。

织入方式实现原理限制失效场景
接口动态代理运行期生成实现同一组接口的类目标必须有接口；只有接口上的方法能被代理按具体类型注入会报类型不匹配
子类字节码代理运行期生成目标类的子类并覆盖方法类和方法不能是 final；需要可访问的构造器final 方法、private 方法、static 方法都拦不到
编译期或加载期织入直接改写字节码需要额外的编译插件或 agent配置复杂，但能拦到自调用
手写装饰器显式包装要自己装配不会失效，代价是样板代码

推论也很直接：把需要注解生效的方法放到另一个 Bean 里，或者注入自身的代理再调用。更细的代理生成机制、暴露代理的配置项、以及事务传播行为的对应表详见站内 Spring 核心那篇，这里不重复展开。

门面：收窄依赖面，而不是简化调用

「门面让调用变简单」是个把结果当原因的说法。门面真正的价值是把外部对内部的依赖从 N 个类收窄到 1 个接口，这样内部怎么拆模块、怎么改调用顺序、怎么替换实现，都不会波及调用方。简化调用只是这件事的副产品，而且如果门面只是把五个调用串起来，收益远不如它带来的额外一层。

门面退化的信号为什么危险怎么修
方法数量持续增长，超过 15 个还在加它已经不是一个业务能力的入口，而是所有能力的目录按业务能力拆成多个门面，禁止出现通用门面
开始出现业务判断与分支业务规则从领域层漏到编排层，两处都要维护把规则推回领域对象，门面只做编排与事务边界
被所有模块共同依赖任何改动都要全量回归，门面成为提交冲突热点按调用方拆接口，只暴露各自需要的方法
方法参数是大而全的 Map 或通用请求对象契约失去类型约束，改字段无人知晓按用例定义明确的入参类型
门面方法内部再调另一个门面方法事务边界与重试语义变得不可推理抽出内部服务，门面之间不互相调用
门面里注入了十几个依赖它承担了太多职责，测试需要构造十几个替身按能力拆分，或把编排逻辑下移到领域服务

组合模式：树形结构的真实场景与递归代价

组合模式在业务里有三个真实场景：菜单与导航树、组织与权限树、规则与条件树。它的价值是让「单个节点」和「一棵子树」对调用方长一个样，于是渲染、鉴权、求值都只写一套逻辑。它的代价全在遍历上：递归简洁但受栈深限制，而树的深度往往由数据决定，不由代码决定。

实现选择递归遍历迭代遍历（显式栈或队列）
代码量少，十行以内多一倍，需要自己管栈
深度限制受线程栈限制，默认栈约 512 KB 到 1 MB，深度数千即可能溢出受堆限制，可支撑很深的树
成环保护必须额外传递已访问集合，否则栈溢出同样需要，但更容易在循环体里检查
可中断与限流难，中途退出要靠异常或返回值层层传容易，循环里随时 break 或检查预算
性能主要瓶颈不是递归本身，而是每个节点单独查库同上，先一次查全量再内存建树才是关键优化
推荐场景深度可控的菜单树，且节点已全部在内存深度由用户数据决定的组织树、规则树

桥接与享元：剩下的适用面有多窄

桥接的定义是「让抽象与实现两个维度独立变化」，落到代码就是持有一个接口字段而不是继承一个基类——也就是组合。在业务代码里几乎不需要专门叫它桥接，识别出「这是两个正交维度，不要用继承把它们乘起来」就够了。

享元在业务代码里也基本只剩两种形态：语言内建的常量池与装箱缓存，以及你自己写的本地缓存。手写享元工厂的场景（比如围棋棋子、文本编辑器里的字形）在后端几乎不出现。但语言内建的享元有个必须知道的陷阱：Java 的装箱缓存会让「相同数值的两个包装对象」有时是同一个对象、有时不是。

// 享元在语言层的体现：Integer.valueOf 对小整数返回缓存实例
Integer a = 127, b = 127;      // 走缓存，默认缓存范围是 -128 到 127
Integer c = 128, d = 128;      // 超出缓存范围，各自新建对象
System.out.println(a == b);    // true  ——「碰巧」正确，最危险的那种正确
System.out.println(c == d);    // false ——同样的代码，换个数值就错

// 正确写法：包装类型永远用 equals，或先拆箱再比较
System.out.println(c.equals(d));        // true
System.out.println(c.intValue() == d);  // true，右侧自动拆箱

// 真实事故形态：金额、用户 ID、订单号这类字段天然大于 127
Long amount1 = 200L, amount2 = 200L;
if (amount1 == amount2) { /* 永远进不来，对账差异从这里产生 */ }
// 另外注意：字符串字面量在常量池里共享，但运行期拼接出的字符串不在池中
String s1 = "AB", s2 = "A" + "B";           // 编译期就折叠成字面量，同一对象
String s3 = new StringBuilder("A").append("B").toString();  // 运行期新建，与 s1 不是同一对象
System.out.println(s1 == s2);   // true
System.out.println(s1 == s3);   // false，必须用 equals

再补两条容易被忽略的细节：包装类型与基本类型用等号比较会自动拆箱，此时包装对象为 null 会直接抛空指针；装箱缓存的上界还可以通过启动参数调整，所以不要把「小于 128 就相等」当成稳定行为，不同环境可能不一样。结论只有一条，包装类型一律用 equals 或先拆箱再比。

反模式：无意义的包装与层层转换

反模式识别信号后果修法
每层都加一个只做转发的包装类三个类方法签名完全相同，方法体只有一行调用调用链凭空变长，异常和堆栈多绕几层，读代码要多跳三次删掉纯转发层，只保留有真实翻译、校验或聚合的那一层
DTO 与 VO 与 PO 层层转换但语义完全相同三个类字段一模一样，转换代码靠拷贝工具加一个字段要改三个类加三处转换，漏一处就是字段丢失，且拷贝工具的漏拷贝不报错语义相同就合并；只在对外契约与内部模型之间保留一次转换
把适配器写成纯转发适配器方法直接把参数原样传给第三方 SDK第三方的字段语义、错误码、异常类型全部泄漏进内部，换渠道等于重写适配器必须翻译字段、错误码与不确定状态
用代理替代显式设计关键业务逻辑写在切面里读业务代码看不到它，新人完全无法发现，改动时莫名其妙被拦横切关注点用代理，业务规则必须写在显式调用链上

最容易踩的坑

❌
结构型模式的高频事故清单
  • 把第三方 SDK 的异常类型、错误码枚举、DTO 直接往内部传：整个工程都 import 了对方的包，换渠道时改动面无法收敛。
  • 适配器把超时当成失败：对方其实已受理，用户重新下单造成重复支付，这是最贵的一类适配器 bug。
  • 适配器里混用金额单位：一家渠道按元一家按分，没在适配器里统一，线上金额差一百倍。
  • 同类内部方法自调用还指望注解生效：事务、缓存、限流全部静默失效，没有任何报错，测试环境常因单机而看不出差别。
  • 给 final 类或 final 方法加注解：子类代理无法覆盖，注解同样静默失效。
  • 把关键业务规则写进切面：读主流程完全看不到它，改动时行为莫名变化，排查要先想到有切面存在。
  • 装饰器顺序装配错：重试包在缓存外层，一次失败把缓存查询也重复执行；缓存包在重试内层，失败结果被缓存下来。
  • 装饰器里吞掉异常只打日志：上层以为成功，数据不一致要到对账才发现。
  • 装饰器链叠到五层以上：堆栈里方法名全一样，定位是哪层改了行为只能逐层加日志。
  • 门面退化成上帝类：方法数过百、被所有模块依赖，成为提交冲突与全量回归的源头。
  • 树形结构递归遍历不设深度上限也不记录已访问节点：数据成环时直接栈溢出，且这种脏数据往往来自一次误操作。
  • 遍历树时每个节点单独查库：节点数上千就慢到不可接受，正确做法是一次查全量再在内存建树。
  • 用等号比较包装类型：数值小于 128 时因装箱缓存而「碰巧」正确，上线后金额和 ID 这类大数值全部为假。
  • 误以为所有相同内容的字符串都是同一个对象：运行期拼接出的字符串不在常量池，用等号比较必然为假。
  • 为了「层次完整」在每层都建一个包装类：没有任何翻译或校验，只是把一次调用拆成四次跳转。
