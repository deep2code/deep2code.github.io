后端技术栈的分层地图

这个专题下有 Go、Python、Java、Node.js、Rust、Shell 六种语言，再加上 Kafka、gRPC、Protocol Buffers、GraphQL、微服务这些跨语言的基础设施。按技术名字罗列容易看散，但真正写系统时的顺序是固定的：一个请求从公网进来，要依次穿过接入层、应用层、数据层，而这三层都跑在基础设施层之上。每一层负责的决策类型不同，坏掉时的症状也不同，先记住这张地图，再决定看哪一篇。

语言选型真正受约束的六个维度

关于语言的争论大多停留在语法和性能上，但线上系统里做决定的通常是另外六件事。判断方法很朴素：逐条问一遍，如果没有任何一条明显偏向新语言，就沿用主栈。引入第二语言的成本不是学习成本，而是从此每套工具链、每个中间件客户端、每次安全升级都要做两遍。

约束维度要回答的问题忽略它的真实后果
团队与招聘现有主栈是什么？出问题时半夜能上手改的人有几个？招人时这门语言的候选池有多大新服务写完人走了，一年后没人敢动，最终被整体重写
生态一等公民用到的数据库驱动、消息客户端、链路追踪 SDK、配置中心客户端，在这门语言里是官方维护还是社区孤儿自己维护客户端与埋点，每次中间件升级都要跟一次
运行模型业务是 IO 等待为主还是 CPU 计算为主？阻塞一次的代价是一个协程、一个线程还是整个进程把阻塞写法套进事件循环，或用线程池扛高并发 IO，尾延迟无法收敛
部署形态镜像多大、冷启动多久、常驻内存多少、是否需要预热才进入稳态弹性扩容的速度赶不上流量爬升，扩了也救不了当前这波
线上可观测能不能在不重启的情况下抓到 CPU 火焰图、堆快照、阻塞栈线上问题只能靠重启掩盖，同一个故障反复发生
退出成本如果三年后要换掉它，需要改动多少跨服务边界与运维脚本语言绑死在某个框架的私有约定上，迁移预算等于重写

运行模型如何反过来决定架构

同一套业务需求，用不同运行时写出来的架构不会相同，因为「阻塞一次的代价」不同，容量规划的单位也不同。这张对照表是选型讨论里最该先摊开的一页。

运行时并发单位与调度一次阻塞的代价CPU 密集怎么办部署形态
Gogoroutine，运行时做 M 比 N 调度，初始栈只有几 KB 且按需增长网络 IO 被运行时转为非阻塞并交给网络轮询器；阻塞系统调用会让当前 P 与 M 解绑，代价可控直接开 goroutine，用 GOMAXPROCS 控制并行度，用信号量控制并发单文件二进制，镜像可做到很小，启动即进入稳态
Java平台线程与内核线程一比一（默认栈约 1MB），靠线程池复用；JDK 21 起可用虚拟线程平台线程阻塞就占住一个内核线程，池满即排队；虚拟线程把这个代价降到接近协程线程池加 ForkJoin，JIT 进入稳态后吞吐很高JVM 加堆外预留，需要预热才达稳态，冷启动明显慢于 Go
Python（CPython）线程受 GIL 约束，同一时刻只有一个线程执行字节码；asyncio 是单线程事件循环不释放 GIL 的阻塞调用会让整个进程停摆，而不只是当前线程多进程按 CPU 配额横向堆，或把热点交给 C 扩展解释器加依赖，镜像偏大，容量按「进程数乘以协程数」算
Node.js单线程事件循环加 libuv 线程池（线程池默认 4，由 UV_THREADPOOL_SIZE 控制）同步阻塞直接卡住事件循环，所有在途请求一起变慢worker_threads 或多进程，主循环只做编排单进程按核数起多份，内存占用中等，启动快

几个流传很广但会误导容量规划的说法，值得在这里直接纠正：

⚠️
四个常见误解

goroutine 便宜所以可以无限开：goroutine 便宜，它持有的连接不便宜。真正的上限是连接池与下游容量，并发控制要落在信号量和连接池上。GIL 让 Python 不能并发：GIL 限制的是并行执行字节码，IO 等待期间会释放，纯 IO 服务用协程照样吃满带宽。虚拟线程等于免费的高并发：它只让阻塞变便宜，数据库连接池和下游限额一点没变；早期版本在 synchronized 内阻塞还会固定载体线程，直到 JDK 24 才解决。Node 单线程所以性能差：单线程指的是 JS 执行线程，文件、DNS、压缩、部分加密走 libuv 线程池；真正的风险是大对象序列化、同步加密、正则回溯把事件循环占死。

还有一类问题不属于语言而属于容器：运行时看到的资源和 cgroup 给的资源常常不是一回事。Go 运行时长期只按机器可见 CPU 数设置 GOMAXPROCS，不看 cgroup 的 CPU limit（Go 1.25 起才开始感知容器限制），在此之前限额一核的容器跑在多核宿主机上，会被 CFS 周期性限流打出规律的长尾延迟。JVM 从 8u191 与 JDK 10 起默认开启容器支持，按 cgroup 计算可用处理器数与默认最大堆（约为限额内存的四分之一），所以给容器加内存并不等于给堆加内存。

这个专题各子方向怎么读

不建议按顺序通读。三条常见路线：接手一个存量服务，先读它所用语言的总览，再读该语言的并发与性能篇，然后读微服务里的熔断限流与链路追踪；设计一个新服务，先读上面的选型维度与运行模型两节，再读接口协议对比，最后读 Kafka 的可靠性篇确定异步边界；准备面试或晋升，按能力地图逐域自测，缺哪块补哪块。下表给每个子方向一句「什么时候该读它」。

❌
总览层面最容易走错的判断
  • 把「语言性能」当成选型第一原则，忽略生态一等公民与招聘半径，最后维护成本压过性能收益
  • 压测用宿主机、上线跑容器，两边的 CPU 与内存默认值不同，压测数据完全不可迁移
  • 超时没有预算：每层都设 3 秒，五层串起来客户端要等十几秒，重试还会把它翻倍
  • 重试放在每一层：网关、客户端、业务代码各自重试三次，一次抖动被放大成二十七倍流量
  • 幂等只在数据库唯一索引上做，没有幂等键与结果回放，重复请求返回的结果不一致
  • 拆微服务时按技术分层拆（控制层一个服务、数据层一个服务），结果每个业务改动都要跨服务发布
  • 连接池大小凭感觉设：既没按下游可承载并发反推，也没和线程或协程上限对齐
