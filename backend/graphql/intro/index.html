GraphQL 入门

🏷️ GraphQL

先换个脑子：GraphQL 不是 REST

我带过不少从 REST 转过来的同学，第一周写的 GraphQL 全是"换皮 REST"——一个 type Query 里挂 getUser、listOrders、getArticle，每个字段对应一个老接口。能跑，但完全没用到 GraphQL 的优势。所以入门第一件事不是写代码，是把脑子里的思维模型换掉。

REST 的思维是"我有哪些资源"：GET /users/1、GET /users/1/posts。GraphQL 的思维是"我有一张图"：用户和文章是节点，User.posts 是边，查询就是沿着边走。下面这张图对比一下两种思维下，"看一个用户和他最近三篇文章"这件事长什么样：

REST 思维GraphQL 思维
请求次数2 次（先用户再文章）1 次
响应形状服务端固定客户端声明
数据冗余常带一堆没用字段要什么给什么
契约OpenAPI 文档单独维护schema 即文档即类型

SDL：你的第一份契约

Schema Definition Language 是 GraphQL 的入口。它长得像 TypeScript 的类型声明，但它本身就是可执行的契约。一个最小的博客 schema 长这样：

type User {
  id: ID!
  name: String!
  email: String!
  posts: [Post!]!
}

type Post {
  id: ID!
  title: String!
  content: String!
  author: User!
  comments: [Comment!]!
}

type Comment {
  id: ID!
  body: String!
  author: User!
}

type Query {
  user(id: ID!): User
  post(id: ID!): Post
  posts(limit: Int = 10): [Post!]!
}

type Mutation {
  createPost(title: String!, content: String!): Post!
  deletePost(id: ID!): Boolean!
}

type Subscription {
  postCreated: Post!
}

几个语法点必须先记住：

  • ! 表示非空。[Post!]! 意思是"这个列表本身不能 null，里面每个元素也不能 null"。少写一个 !，前端类型推导就会变成可空，线上一堆空指针。
  • ID 是专门的主键类型，Int/Float/String/Boolean 是标量，自定义对象类型都要显式声明。
  • Query 是只读入口，Mutation 是写操作入口，Subscription 是实时推送入口——三个根类型缺一不可，但 Mutation/Subscription 可以为空。
! 漏写是新手第一大坑
我见过一个老 schema 里 Post.author 没写 !，结果后端某条脏数据 authorId 为空时返回 null，前端 React 直接白屏。GraphQL 的空值是可以被 schema 约束住的，别浪费这个武器。建表前对着业务问一遍：这个字段永远不可能为空吗？是就加 !。

Resolver：每个字段背后都有个函数

schema 只是"形状"，真正取数的是 resolver。GraphQL 最妙的设计是：resolver 是按字段定义的，不是按操作定义的。你查询里要了几个字段，就并行执行几个 resolver。

const resolvers = {
  Query: {
    user: (_parent, { id }, { db }) => db.users.findById(id),
    post: (_parent, { id }, { db }) => db.posts.findById(id),
    posts: (_parent, { limit }, { db }) => db.posts.list({ limit }),
  },
  User: {
    // parent 就是上一级 User 对象
    posts: (parent, _args, { db }) =>
      db.posts.find({ authorId: parent.id }),
  },
  Post: {
    author: (parent, _args, { db }) => db.users.findById(parent.authorId),
    comments: (parent, _args, { db }) =>
      db.comments.find({ postId: parent.id }),
  },
};

注意 resolver 的签名永远是 (parent, args, context, info)。parent 是上一级字段 resolve 出来的对象——查 user.posts 时，User.posts 这个 resolver 拿到的 parent 就是那个 User。这个设计是理解后面 N+1 问题的钥匙，先记住。

flowchart TD Q[客户端 query user(id:1) name posts{title}] --> PARSE[解析+校验 对比 schema] PARSE --> R1[执行 Query.user 拿到 user 对象] R1 --> R2[并行执行 User.name] R1 --> R3[执行 User.posts 用 parent.id 查文章] R2 --> MERGE[按查询形状组装 JSON] R3 --> MERGE MERGE --> RESP[返回与查询同形状的响应] style PARSE fill:#e535ab,stroke:#fff,color:#fff

第一个能跑的服务

2026 年我新项目一律 Apollo Server 4.x，上手最快。先装依赖：

mkdir graphql-demo && cd graphql-demo
npm init -y
npm install @apollo/server graphql
npm install -D typescript tsx @types/node

然后写 index.ts：

import { ApolloServer } from '@apollo/server';
import { startStandaloneServer } from '@apollo/server/standalone';

const typeDefs = `#graphql
  type Book {
    id: ID!
    title: String!
    author: String!
  }
  type Query {
    books: [Book!]!
    book(id: ID!): Book
  }
`;

const books = [
  { id: '1', title: 'GraphQL 入门', author: '资深码农' },
  { id: '2', title: '深度思考', author: '另一作者' },
];

const resolvers = {
  Query: {
    books: () => books,
    book: (_: unknown, { id }: { id: string }) =>
      books.find((b) => b.id === id),
  },
};

const server = new ApolloServer({ typeDefs, resolvers });
const { url } = await startStandaloneServer(server, { listen: { port: 4000 } });
console.log(`🚀 跑在 ${url}`);

跑起来 npx tsx index.ts，浏览器打开 http://localhost:4000 就是内置的 GraphiQL playground——左边写查询，右边出结果，自带 schema 自动补全和文档抽屉。

}

# 响应形状和查询一模一样
{

    ]
  }
}
GraphiQL 是你最好的文档
很多团队上线后把 GraphiQL 关了，我觉得是因噎废食。生产环境可以加个登录才开的开关——前端同学对着右侧 Docs 抽屉点来点去就能搞清楚有哪些字段、哪些参数，比你维护一份 Word 文档靠谱一百倍。

Mutation 和 Subscription

读操作是 Query，写操作是 Mutation。语法几乎一样，只是根类型不同：

mutation CreatePost {
  createPost(title: "第一篇", content: "Hello") {
    id
    title
    createdAt
  }
}

Mutation 默认串行执行，这是规范规定的——多个 mutation 写同一个数据必须有先后顺序，不像 query 可以并行。Subscription 则是基于 WebSocket 的实时推送，走另一条连接：

subscription OnPostCreated {
  postCreated {
    id
    title
    author { name }
  }
}

服务端用 pubsub 发布，客户端收到事件后自动更新。这块在第三篇 Apollo 实战里会给完整的 WebSocket 配置。

context：请求级别的共享数据

每个请求进来，Apollo 会构造一个 context 对象传给所有 resolver。这是放当前登录用户、数据库连接、DataLoader 实例的地方：

const { url } = await startStandaloneServer(server, {
  context: async ({ req }) => {
    const token = req.headers.authorization?.replace('Bearer ', '');
    const user = verifyToken(token); // 自己的鉴权逻辑
    return { user, db: myDb };
  },
  listen: { port: 4000 },
});
context 别放请求级单例
context 是每个请求新建的，别把全局的 DataLoader 实例塞进去——那会导致两个请求共享同一个 loader，互相污染缓存。正确做法是 每个请求 new 一个 DataLoader，这个坑第四篇还会细讲。

和 REST 的思维差异：一张图

flowchart LR subgraph REST[REST 思维] R1[GET /users/1] --> R2[GET /users/1/posts] R2 --> R3[前端自己合并] end subgraph GQL[GraphQL 思维] G1[一次 POST /graphql] --> G2[网关沿图遍历] G2 --> G3[按形状返回] end

理解了这个图，你就理解了 GraphQL 80% 的价值：把"拼数据"这件事从前端代码挪到了网关运行时。代价是网关要承担查询复杂度，这个代价值不值，看后面几篇。

FAQ

Q：GraphQL 必须用 Apollo 吗？
不是。规范是 graphql-js 实现的，Apollo 只是上层封装。但生产环境我建议直接用 Apollo Server 或 Yoga，自己从裸 graphql-js 搭要处理的协议细节太多。

Q：resolver 里能写异步吗？
天生支持。每个 resolver 都可以返回 Promise，Apollo 会等所有字段 resolve 完再组装。并行字段、串行 mutation，调度器都帮你排好了。

Q：GraphQL 一定要用 POST 吗？
查询用 POST 是惯例（因为 query 可能很长），但规范允许 GET。生产环境我建议只读查询走 GET 以便 CDN/HTTP 缓存，写操作走 POST。

我的结论

入门 GraphQL 记住三件事：SDL 是契约（类型即文档）、resolver 是按字段取数的函数、查询响应和查询形状一一对应。别一上来就把 REST 接口翻译过来，先想清楚你的"图"长什么样。
