GraphQL 性能与 N+1 问题

🏷️ GraphQL

N+1 是 GraphQL 的原罪

用 GraphQL 上线三个月内，你一定会撞上 N+1。这不是 bug，是架构的必然——resolver 按字段独立执行，查 100 篇文章的作者，就会调 100 次 findById。我第一次在生产遇到是个后台列表页，本来 200ms 的接口，加了个"作者头像"字段后直接飙到 8 秒，DB CPU 打满。

这篇把 N+1 的成因、DataLoader 怎么救、以及 GraphQL 特有的性能手段（复杂度分析、持久化查询、@defer/@stream、查询缓存）一次讲透。

N+1 到底怎么发生的

看这个查询：

query {
  posts(limit: 100) {
    title
    author { name }
  }
}

没有 DataLoader 时，执行过程是这样的：

  1. 先查 100 篇文章（1 次 SQL）。
  2. 对每篇文章，Post.author resolver 单独跑一次 db.users.findById(post.authorId)（100 次 SQL）。

1 + 100 = 101 次查询，这就是"N+1"——1 次主查询加 N 次关联查询。更糟的是这些查询是串行或半并行的，数据库连接池很快被占满。

flowchart TD Q[查询 posts.author] --> S1[SQL 1: 查100篇文章] S1 --> L1[SQL 2: 查作者1] L1 --> L2[SQL 3: 查作者2] L2 --> L3[... 共100次] L3 --> LN[SQL 101: 查作者100] style LN fill:#dc382d,stroke:#fff,color:#fff

DataLoader 怎么把 101 次变 2 次

DataLoader 的核心是 batch 函数：它在同一个 microtask 周期内把所有 load(id) 攒成一个数组，一次性交给你写的批量查询函数。关键是你要保证返回顺序和请求 id 顺序对齐：

import DataLoader from 'dataloader';

const userLoader = new DataLoader<string, User>(async (ids) => {
  // 一次 SQL：SELECT * FROM users WHERE id IN (...)
  const users = await db.users.find({ id: { $in: [...ids] } });
  const map = new Map(users.map((u) => [u.id, u]));
  // 必须按 ids 顺序返回，缺的用 Error 占位
  return ids.map((id) => map.get(id) ?? new Error(`未找到 ${id}`));
});

接上 DataLoader 后，同样的查询变成：1 次查文章 + 1 次批量查作者 = 2 次 SQL。

flowchart TD Q[查询 posts.author] --> S1[SQL 1: 查100篇文章] S1 --> BATCH[DataLoader 攒100个id] BATCH --> S2[SQL 2: WHERE id IN (1..100)] S2 --> DONE[按id回填 2次查询搞定] style S2 fill:#10b981,stroke:#fff,color:#fff
DataLoader 实例必须每请求新建
这是我踩过最贵的坑。DataLoader 自带请求内缓存，如果你把它做成全局单例，A 用户请求缓存了 User:1，B 用户请求直接命中——权限隔离直接失效。正确做法：context 工厂里 new DataLoader()，请求结束随 context 一起 GC。

还有个细节：DataLoader 的 batch 窗口是"同一 tick"。如果你在 resolver 里 await 了别的东西再 load()，batch 窗口就关了，又退回 N+1。写 loader 时尽量让 load() 调用在同步代码里发起。

查询复杂度分析：防住恶意深查询

N+1 是好心写出来的，还有一种是恶意或无知的深查询：

query {
  users {
    posts {
      comments {
        author {
          posts { comments { author { posts { ... } } } }
        }
      }
    }
  }
}

这种查询能把你数据库扫穿。GraphQL 没有内置限制，你得自己加查询复杂度分析插件。思路是给每个字段算一个"成本分"，查询前先算总分，超阈值直接拒：

import { createComplexityLimitRule } from 'graphql-validation-complexity';

const server = new ApolloServer({
  typeDefs,
  resolvers,
  validationRules: [
    createComplexityLimitRule(1000, {
      onCost: (cost) => console.log('查询复杂度:', cost),
    }),
  ],
});
字段默认复杂度建议
标量字段（name）1保持默认
列表字段（posts）1按数量调，如 10
深层关联（comments.author）1调到 5~20
根 query0起点

阈值别设太小，先从线上采样看真实查询的复杂度分布，再卡一条线。我见过团队一上来设 100，正常业务全被拒。

持久化查询：把长 query 变短

GraphQL 每次都把完整 query 文本发过来，传输和解析都是开销。持久化查询（persisted queries）让前端只发一个 hash：

// 前端注册后
{ "id": "hash-a1b2c3", "variables": { "limit": 10 } }
// 服务端按 hash 找到预存的完整 query

好处：① 报文小 ② 只能跑白名单里的查询，恶意查询根本发不进来 ③ 能对白名单查询做 CDN 缓存。Apollo Server 有官方包 @apollo/persisted-query-lists，配合客户端构建时生成 hash 表。

@defer / @stream：渐进式返回

2026 年 @defer 和 @stream 已经是 GraphQL 规范正式特性。意思是：主数据先回来，慢的字段分块流式返回。前端不用等整个查询跑完就先渲染：

query {
  post(id: 1) {
    title
    author { name }
    comments @stream(initialCount: 5) {
      body
      author { name }
    }
  }
}

效果：标题和作者 50ms 回来，前 5 条评论跟着，剩下的评论一条条流到。列表页再也不用卡在"等全部评论加载完"。

@defer 的前提
用 @defer 必须服务端支持（Apollo Server 4.x 内置），且客户端要能处理多块响应（multipart）。Apollo Client 3.7+ 原生支持。别指望老浏览器 fetch 直接读，得用专用 link。

查询缓存：服务端这一层

除了 DataLoader 的请求内缓存，跨请求的结果缓存我一般分两层：

  • 响应缓存：Apollo Server 自带 responseCache，按查询 + 变量 hash 缓存整个响应。适合只读、更新不频繁的数据（如商品分类）。
  • 实体缓存：在 resolver 里直接套 Redis，key 用 User:123，TTL 30~60s。比整响应缓存灵活，因为能精确到字段。
// 简单的 Redis 实体缓存
async function getCachedUser(id: string) {
  const key = `user:${id}`;
  const cached = await redis.get(key);
  if (cached) return JSON.parse(cached);
  const user = await db.users.findById(id);
  await redis.setEx(key, 30, JSON.stringify(user));
  return user;
}
缓存失效是噩梦
用户改了名字，Redis 里还存着旧的。写操作（Mutation）成功后一定要主动删/更新对应缓存 key。我线上出过一次事故：用户改名后列表页还显示老名字，最后发现是 order 列表里冗余存了 user.name 没刷。缓存 key 的设计要在一开始就想好失效策略，别事后补。

FAQ

Q：N+1 能用 SQL 做 JOIN 解决吗？
能，但 GraphQL 的 resolver 是按字段独立取数的，JOIN 出来的数据要塞回每个对象，要自己写"扁平化"逻辑，不如 DataLoader 通用。多数据源（一个用户在 MySQL、订单在另一个库）时 JOIN 根本做不了，DataLoader 才是正解。

Q：DataLoader 批量大小有限制吗？
默认最多 1000 个 id 一批。WHERE id IN (1000 个) SQL 也会变很慢。可以配 maxBatchSize: 50 拆批，列表分页时尤其要注意。

Q：GraphQL 慢了怎么定位？
Apollo Server 自带 tracing，生产开 engine 插件看每个 resolver 的耗时。先看是不是某个 resolver 慢，再看是不是 N+1，别一上来就怀疑框架。

我的结论

GraphQL 性能问题 90% 是 N+1 和查询失控。N+1 用 DataLoader 治，查询失控用复杂度分析卡，再叠上持久化查询和实体缓存，这套组合打下来，GraphQL 完全能撑住生产量级。别信"GraphQL 天生慢"——那是没加 DataLoader 的人在喊。
