GraphQL 微服务架构

🏷️ GraphQL

单体 GraphQL 够用到什么时候

前面四篇讲的都是"一个 GraphQL 服务"。但当你公司拆了微服务，用户服务、订单服务、商品服务各有各的团队、各有各的数据库，一个单体 GraphQL 网关就成了瓶颈——所有 resolver 都塞在一个仓库里，改个字段要跨团队提 PR，部署互相影响。

这时候就需要把一张大图拆成多张子图，每个团队 owns 自己的那部分。GraphQL 微服务架构的核心就这件事。2026 年的标准答案是 Apollo Federation。

stitching vs Federation：两条路线

早期合并多个 GraphQL schema 有个方案叫 schema stitching：网关在构建期把各服务的 schema 合并成一个大 schema。简单粗暴，但有个致命问题——跨服务的类型扩展很别扭，你想在订单服务里给 User 加个 orders 字段，得在网关层手写拼接逻辑。

Apollo Federation 换了个思路：每个子图用 @key 注解声明"我能按这个字段拿出这种类型"，网关在运行时知道哪个子图负责哪个类型的哪个字段，自动编排跨服务查询。

schema stitchingApollo Federation
合并时机构建期运行时
跨服务扩展网关手写胶水子图用 @extend 自行声明
团队自治弱（网关是单点）强（子图自管）
运行时编排无，静态合并网关自动 plan 查询
维护状态社区方案，渐冷事实标准，活跃
别再选 stitching 了
新项目直接上 Federation。stitching 在 Apollo Server 4.x 里已经不再主推，文档都薄了。除非你只是想把两个现成 GraphQL API 临时缝一下，否则没有理由选它。

Federation 的核心：@key 和实体

Federation 的魔法在 实体（entity）和 @key。用户服务定义 User 类型：

# users 子图
type User @key(fields: "id") {
  id: ID!
  name: String!
  email: String!
}

订单服务想给 User 加订单列表，不用改用户服务，自己在子图里扩展：

# orders 子图
extend type User @key(fields: "id") {
  id: ID! @external
  orders: [Order!]!
}

@external 表示"这个 id 字段不是我定义的，是别的子图定义的，我引用一下"。网关看到 User.orders 就知道要去订单子图取。

真实生产网关架构

这是我团队 2026 年线上跑的一套，给你个完整参照：

flowchart TB WEB[Web/App 客户端] --> CDN[CDN + WAF] CDN --> GW[Apollo Gateway 网关] subgraph 网关职责 GW --> AUTH[鉴权 解析 JWT] AUTH --> PLAN[查询编排 plan] PLAN --> COMPLEX[复杂度校验] end GW --> S1[users 子图] GW --> S2[orders 子图] GW --> S3[products 子图] GW --> S4[reviews 子图] S1 --> D1[MySQL 用户库] S2 --> D2[MySQL 订单库] S3 --> D3[MongoDB 商品库] S4 --> D4[ES 评论索引] GW -.指标.-> OBS[OpenTelemetry 链路追踪] style GW fill:#e535ab,stroke:#fff,color:#fff style OBS fill:#f59e0b,stroke:#fff,color:#fff

几个关键点：

  • 网关只做编排，不写业务。鉴权、复杂度、路由、指标在这里；真正取数全在子图。
  • 子图之间不直接通信。跨服务关联走网关的实体解析，别让订单服务直接调用户服务的 HTTP——那就退化成分布式单体了。
  • 链路追踪必须打通。一个查询横跨 4 个子图，出了问题不知道哪步慢，没有 trace 根本没法查。

跨服务数据关联：@require 和引用

有时候子图需要别的子图先传点数据过来才能查。比如商品要带卖家名字，但订单子图只有 sellerId。用 @requires 声明依赖：

# products 子图
extend type Product @key(fields: "id") {
  id: ID! @external
  sellerId: ID! @external
  seller: User @requires(fields: "sellerId")
}

网关查 seller 时，会先向 products 子图要 sellerId，再把 id 交给 users 子图拿 User。这就是 federated tracing 的价值——你不用手写跨服务调用链。

权限控制：在哪一层做

微服务 GraphQL 的权限最容易乱。我的原则是认证在网关，授权在子图：

  • 网关：验 JWT，把 userId、role 注入到每个子图的请求头。
  • 子图：收到 X-User-Id 后，在自己的 resolver 里判断"这个用户能不能看这条数据"。
// 子图 context 里读网关注入的身份
context: async ({ req }) => ({
  userId: req.headers['x-user-id'],
  role: req.headers['x-user-role'],
})

// resolver 里授权
Query: {
  order: async (_, { id }, { userId, role, db }) => {
    const order = await db.orders.findById(id);
    if (role !== 'ADMIN' && order.userId !== userId) {
      throw new ForbiddenError('无权查看');
    }
    return order;
  },
}
别在网关做字段级授权
网关不知道每个订单属于谁，硬做授权就要把全量数据拉上来判断，性能灾难。授权必须下沉到持有数据的子图。网关只负责"你是谁"，子图负责"你能看什么"。

版本化策略：不用 URL 版本号

REST 里大家习惯 /v1/users、/v2/users。GraphQL 我强烈不建议这么干——一个查询可能跨 10 个服务，你 /v1 和 /v2 混着用，网关层根本没法编排。

正确做法是用 deprecation 渐进演进：

type User {
  oldField: String @deprecated(reason: "用 newField 替代，2026Q4 下线")
  newField: String!
}

新字段先上，老字段标废弃，给前端 2~3 个版本周期迁移，确认没人用了再删。GraphiQL 里废弃字段会灰掉，迁移成本很低。

版本号 URL常见不推荐
字段废弃难做@deprecated 原生
多版本并存天然支持靠子图独立部署

FAQ

Q：Federation 一定要用 Apollo 商业版吗？
核心的联邦路由、子图、实体解析都是开源的。Apollo Studio 的性能追踪、沙盒、协作编辑是付费的。我团队开源版够用，Studio 只在调试时用。

Q：子图能用不同语言写吗？
能。Federation 是协议无关的，只要实现了联邦 spec。Node 用 @apollo/subgraph，Java 用 Netflix DGS 或 Spring GraphQL，.NET 用 Hot Chocolate。我们订单子图是 Java，用户子图是 Node，混着跑。

Q：网关挂了怎么办？
网关是单点，必须多实例 + 负载均衡。子图挂了要做优雅降级——某个子图返回空，整个查询别全挂。Apollo Server 4.x 支持 onResolverError 兜底。

我的结论

GraphQL 微服务的本质是：用一张统一的图，把多个团队独立拥有的服务粘起来，同时不破坏他们的自治。Apollo Federation 通过 @key/实体机制解决了跨服务类型扩展，比 stitching 干净一个时代。

落地记住三条：认证在网关、授权在子图、别在网关写业务；版本化用 @deprecated 而不是 URL；链路追踪从第一天就接上。这套架构从几个服务到几十个服务都能撑住，我自己线上已经跑了三年。
