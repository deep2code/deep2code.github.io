GraphQL vs REST vs gRPC

🏷️ GraphQL

💡 你想搞懂这个技术到底是干嘛的，什么时候该用它，什么时候不该用。不想上来就背一堆概念。

别站队，先搞清楚它们在比什么

网上一搜"GraphQL vs REST"，吵成一锅粥，两边都把对方说得一无是处。我做了五六年 API 设计，现在的看法很简单：这三者不是同一层的替代品，它们解决的是不同问题。

这篇我不站任何一边，就把这些年线上压测和落地的经验摊开，最后给你一张选型决策表。

六维对比表

这张表里我最想让你注意的是缓存和错误语义两行——这是 GraphQL 最容易被低估的两个坑。

性能特征：各自的快和慢

很多人凭印象说"gRPC 最快、REST 最慢、GraphQL 最慢"，这是没压过测。真实情况要看你测的是什么：

  • 单条小请求：gRPC 因为 HTTP/2 多路复用 + Protobuf 二进制，序列化比 JSON 小 3~10 倍，延迟最低。REST 和 GraphQL 都是 JSON，序列化开销差不多。
  • 聚合查询：GraphQL 赢。一个页面要关联数据，REST 要 N 次往返，GraphQL 一次。省的是网络往返，不是 CPU。
  • 极端大报文：gRPC 赢。Protobuf 体积小，反序列化快。GraphQL JSON 文本在几百 KB 以上开始吃力。
  • 缓存命中率：REST 赢。GET /users/1 可以被 CDN、浏览器、Nginx 层层缓存，GraphQL 的 POST 端点基本是"每次都打源站"。
flowchart LR subgraph REST[REST] A1[1次请求拿固定JSON] --> A2[可能过量字段] end subgraph GQL[GraphQL] B1[1次POST 声明字段] --> B2[零冗余 但每请求校验+解析] end subgraph GRPC[gRPC] C1[HTTP/2 多路复用] --> C2[Protobuf 二进制 最小报文] end

给个参考量级（Apple M 系列，单服务空响应，QPS 对比）：gRPC 约 3~5 万，REST/JSON 约 1.5~2 万，GraphQL 约 1~1.5 万。但这是空响应——真实业务瓶颈都在数据库，框架这两三千 QPS 的差距线上根本无感。

GraphQL 的错误语义：最容易踩的认知差

REST 里 404、500 是 HTTP 层的。GraphQL 不管你业务成功失败，HTTP 状态码永远是 200，错误放在响应体的 errors 数组里：

{
  "errors": [
    {
      "message": "User not found",
      "locations": [{ "line": 2, "column": 3 }],
      "path": ["user"],
      "extensions": { "code": "NOT_FOUND" }
    }
  ],
  "data": { "user": null }
}
别拿 HTTP 状态码判断 GraphQL 成败
我前端同事第一版封装直接看 response.ok，结果业务报错时他以为成功了，页面空了都不知道。GraphQL 必须解析 body 里的 errors，这是和 REST 最大的行为差异，封装 fetch/axios 拦截器时第一行就要写这个判断。

另外注意"部分成功"：一个查询里 user.name 成功了，user.posts 报错，data 里仍然有 name，只是 posts 那条是 null。这种半成功语义 REST 里不存在，前端要学会处理。

缓存：GraphQL 先天的短板

REST 的 GET /users/1 天然可缓存——URL 就是 key。GraphQL 所有查询都是 POST /graphql，URL 都一样，CDN 不知道该缓存谁。这是 GraphQL 被诟病最多的一点。

缓存层RESTGraphQL
CDNGET 直接缓存需持久化查询 + 操作名缓存
浏览器/代理HTTP 头原生基本不缓存 POST
客户端自己写Apollo Client 归一化缓存开箱即用
服务端自己写响应缓存/查询结果缓存

GraphQL 的解法是把缓存重心放到客户端：Apollo Client 按对象 id 归一化存，同一个 User 无论从哪个查询来都命中同一份。这个设计很香，但只对自己的前端有效——你给第三方开放 API 时，GraphQL 的缓存劣势就暴露无遗。

翻译成人话：

  • 对外开放 API：REST。生态成熟、CDN 友好、第三方好接入。别用 GraphQL 硬刚。
  • 内部微服务通信：gRPC。跨语言、高性能、流式支持，云原生标配。
  • 自己的 App/多端 + 复杂聚合页面：GraphQL。一次查询拿全数据，前端少写胶水代码。
  • 简单 CRUD 后台：REST。GraphQL 那套 schema/resolver 是过度工程。
最舒服的组合
我团队现在的标配：对外 BFF 用 GraphQL 网关，网关内部调各微服务的 gRPC，老系统留着 REST 让网关去聚合。三种各司其职，不是二选一。

代码对比：同一个"查用户订单"

看一眼三种风格的实际请求长啥样，体感差异最直接：

# REST：两次请求
GET /users/123
GET /users/123/orders?page=1
// gRPC：先定义 proto
service OrderService {
  rpc GetUserOrders (UserRequest) returns (OrderList);
}
message UserRequest { string user_id = 1; }
# GraphQL：一次，字段随便挑
query {
  user(id: 123) {
    name
    orders(limit: 10) {
      id
      total
      items { name price }
    }
  }
}

注意 GraphQL 这一条查询，客户端想加个 orders { createdAt }，不用找后端改任何东西。这是它和前两者最本质的区别——API 的形状由调用方决定。

FAQ

Q：GraphQL 比 REST 慢吗？
空请求是，但真实业务里 GraphQL 因为省往返经常更快。慢的是"每请求都要解析+校验 schema"，这个开销在高 QPS 时才明显，而且可以用持久化查询（第四篇讲）压掉。

Q：gRPC 能直接给浏览器用吗？
不能。浏览器不会讲 HTTP/2 帧，得用 grpc-web 让 Envoy/网关做一层协议转换。新项目浏览器侧我更倾向 GraphQL 或 Connect 协议。

Q：选了 GraphQL 以后老 REST 服务怎么办？
不用推翻重写。GraphQL 网关里 resolver 直接去调老的 REST 接口就行，把它包成 GraphQL 字段。渐进迁移，这是网关模式的好处。

我的结论

REST、gRPC、GraphQL 不是三选一的选择题，是工具箱里的三把工具。开放 API 用 REST，内部高性能通信用 gRPC，多端复杂聚合用 GraphQL。最忌讳的是"学了 GraphQL 看什么都像查询"——简单 CRUD 上 GraphQL 是给自己找性能和调试的麻烦。
