NestJS 架构入门

🏷️ Node.js 总览

我为什么从 Express 迁到 NestJS

2019 年我带团队做一个 SaaS 产品，Express 写了一年多，代码涨到 8 万行。问题不是写不动，是没人敢动。Service 之间互相 require，循环依赖到处都是，改一个函数要全局搜索。新来的同事第一周就问："这个 UserService 到底被谁注入了？"没人答得上来。

后来我们花了三个月迁到 NestJS。不是因为它快——它比 Express 还慢一点。是因为它逼着你把代码组织好。模块边界清晰、依赖注入自动管理、测试时 mock 一个 Provider 就行。2026 年我团队所有新后端项目都用 NestJS 11，Express 只维护老服务。

三件套：Module、Controller、Provider

NestJS 的核心概念就三个，理解了这三个，其他都是细节。

flowchart TD MODULE[Module 模块
组织单元，声明依赖] --> CTRL[Controller 控制器
处理 HTTP 请求] MODULE --> PROV[Provider 提供者
Service/Repository/工厂] CTRL --> PROV PROV --> DB[数据库/外部服务] style MODULE fill:#00add8,stroke:#fff,color:#fff style CTRL fill:#10b981,stroke:#fff,color:#fff style PROV fill:#f59e0b,stroke:#fff,color:#fff
  • Controller：接收 HTTP 请求，调用 Service，返回响应。不写业务逻辑，只做协议转换。
  • Provider：就是 Service、Repository、Factory 这些。写业务逻辑，被注入到 Controller 里。
  • Module：把一组 Controller 和 Provider 打包成一个功能单元。通过 imports 引入别的模块，通过 exports 暴露自己的 Provider。

看一个最小的 UsersModule：

// users/users.module.ts
import { Module } from '@nestjs/common'
import { UsersService } from './users.service'
import { UsersController } from './users.controller'

@Module({
  controllers: [UsersController],
  providers: [UsersService],
  exports: [UsersService], // 别的模块要用 UsersService 就 import 这个模块
})
export class UsersModule {}
// users/users.service.ts
import { Injectable } from '@nestjs/common'

@Injectable() // 标记这是个可注入的 Provider
export class UsersService {
  private users = new Map<number, { id: number; name: string }>()

  findById(id: number) {
    return this.users.get(id)
  }

  create(id: number, name: string) {
    this.users.set(id, { id, name })
    return this.users.get(id)
  }
}
// users/users.controller.ts
import { Controller, Get, Param, Post, Body } from '@nestjs/common'
import { UsersService } from './users.service'

@Controller('users')
export class UsersController {
  constructor(private readonly users: UsersService) {}

  @Get(':id')
  findOne(@Param('id') id: string) {
    return this.users.findById(Number(id))
  }

  @Post()
  create(@Body() body: { id: number; name: string }) {
    return this.users.create(body.id, body.name)
  }
}

依赖注入：DI 容器在背后干什么

很多人第一次看 NestJS 代码，最懵的就是构造函数里突然多了个 private readonly users: UsersService，然后就能直接用。谁 new 的？NestJS 的 DI 容器。

启动时，NestJS 扫描所有 @Module 装饰器，把所有 providers 注册到一个 IoC 容器里。当某个 Controller 声明要依赖 UsersService，容器去构造一个实例传进去。这叫控制反转——你不自己 new，容器给你注入。

flowchart LR SCAN[启动时扫描 Module] --> REG[注册 Provider 到 IoC 容器] REG --> RESOLVE[解析依赖图] RESOLVE --> INST[实例化，单例默认] INST --> INJECT[注入到 Controller 构造函数] style REG fill:#00add8,stroke:#fff,color:#fff style INST fill:#10b981,stroke:#fff,color:#fff

这个机制最大的好处是测试友好。你要测 UsersController，不用连数据库，mock 一个 UsersService 就行：

import { Test } from '@nestjs/testing'
import { UsersController } from './users.controller'
import { UsersService } from './users.service'

describe('UsersController', () => {
  it('findOne 返回用户', async () => {
    // mock 一个 Service
    const mockService = {
      findById: (id: number) => ({ id, name: 'test' }),
    }

    const moduleRef = await Test.createTestingModule({
      controllers: [UsersController],
      providers: [{ provide: UsersService, useValue: mockService }],
    }).compile()

    const controller = moduleRef.get(UsersController)
    const result = controller.findOne('1')
    expect(result).toEqual({ id: 1, name: 'test' })
  })
})
DI 的三个作用域
默认是单例（SINGLETON），整个应用共享一个实例。需要每请求新建一个用 REQUEST 作用域。还有 TRANSIENT，每次注入都 new。我大部分情况用默认单例，只有带请求上下文的拦截器/守卫才用 REQUEST。

装饰器：NestJS 的语法糖

NestJS 重度使用 TypeScript 装饰器。@Controller()、@Get()、@Injectable()——这些不是魔法，就是函数，在类定义时被调用，给类加元数据。

装饰器作用用在哪
@Module()声明模块类
@Controller()声明路由前缀类
@Get()/@Post()声明 HTTP 方法方法
@Injectable()标记可注入类
@Param()/@Body()/@Query()提取请求参数方法参数
@UseGuards()挂载守卫类/方法
@UseInterceptors()挂载拦截器类/方法

你也可以写自定义装饰器。比如从 JWT 里拿当前用户：

import { createParamDecorator, ExecutionContext } from '@nestjs/common'

export const CurrentUser = createParamDecorator(
  (data: string | undefined, ctx: ExecutionContext) => {
    const request = ctx.switchToHttp().getRequest()
    const user = request.user
    return data ? user?.[data] : user // @CurrentUser('email') 直接拿 email
  },
)

用的时候：

@Get('profile')
getProfile(@CurrentUser() user: { id: number; email: string }) {
  return user
}

和 Angular 的关系

NestJS 作者 Kamil Mysliwiec 是 Angular 开发者。NestJS 的很多概念直接从 Angular 抄来的：Module、Component（Controller）、Service、依赖注入、RxJS 拦截器。如果你写过 Angular，NestJS 上手零成本。

NestJSAngular 对应作用
@Module@NgModule组织代码单元
@Controller@Component处理请求/视图
@Injectable@Injectable可注入服务
GuardCanActivate前置权限校验
InterceptorInterceptor请求/响应拦截
PipePipe数据转换/校验

但别被 Angular 的包袱吓到——后端用不到模板、变更检测、Zone.js 那些。你只需要懂 DI 和装饰器，其他都是后端的事。

CLI 生成器：别手写样板代码

NestJS CLI 是我最喜欢的工具之一。它不是一个简单的脚手架，是一个代码生成器——一个命令生成一整套模块、控制器、服务、测试文件：

# 全局装 CLI
npm i -g @nestjs/cli

# 新建项目
nest new my-api --package-manager pnpm

# 生成一个完整模块（controller + service + module + spec）
nest generate module users
nest generate controller users
nest generate service users
# 一行搞定
nest g resource users  # 还会生成 CRUD 路由和 DTO

# 常用简写
nest g mo users    # module
nest g co users    # controller
nest g s users     # service
nest g guard auth  # guard
nest g interceptor log # interceptor
手动建文件容易漏注册
我见过新手手写了个 UsersService，忘了在 module 的 providers 里声明。启动时报"Nest can't resolve dependencies"。用 CLI 生成就不会——它自动帮你把 import 和声明写好。新项目一律用 CLI，别手搓。

第一次跑通 NestJS 项目

# 1. 装项目
nest new nest-demo --package-manager pnpm
cd nest-demo

# 2. 生成一个 CRUD 资源
nest g resource cats
# 选 REST API

# 3. 跑起来
pnpm start:dev
# 访问 http://localhost:3000/cats

生成的项目长这样：

src/
├── app.module.ts        # 根模块

main.ts 是入口：

import { NestFactory } from '@nestjs/core'
import { AppModule } from './app.module'

async function bootstrap() {
  // 默认用 Express，想换 Fastify 就用 NestFactory.createMicroservice
  const app = await NestFactory.create(AppModule, { logger: ['error', 'warn'] })
  app.setGlobalPrefix('api/v1')
  app.enableCors()
  await app.listen(3000)
}

中间件、守卫、拦截器、管道

NestJS 有一套自己的请求生命周期，比 Express 中间件精细得多：

flowchart LR REQ[请求进来] --> MW[Middleware 中间件] MW --> GUARD[Guard 守卫
权限校验] GUARD --> PIPE[Pipe 管道
数据转换/校验] PIPE --> INTERCEPTOR[Interceptor 拦截器
前置/后置处理] INTERCEPTOR --> CTRL[Controller 处理] CTRL --> INTERCEPTOR2[Interceptor 后置] INTERCEPTOR2 --> RES[响应出去] style GUARD fill:#dc382d,stroke:#fff,color:#fff style PIPE fill:#f59e0b,stroke:#fff,color:#fff style INTERCEPTOR fill:#10b981,stroke:#fff,color:#fff

简单说：Guard 管"能不能进"，Pipe 管"参数对不对"，Interceptor 管"请求前后加点什么"。Express 中间件只能在最外层干这些事，NestJS 把它们拆开了，职责清晰。

FAQ

Q：NestJS 性能比 Express 差多少？
空路由大概慢 10-20%，因为 DI 容器和装饰器元数据有开销。但真实业务瓶颈都在数据库，这点差距可以忽略。如果你的服务就是纯转发、没有业务逻辑，用 Fastify 或原生 http 模块。

Q：NestJS 必须用 TypeScript 吗？
技术上支持 JS，但没人这么写。装饰器和 DI 容器是 TS 的类型反射能力撑起来的，用 JS 等于自废武功。新项目老老实实写 TS。

Q：什么时候不该用 NestJS？
三五个接口的小服务、Serverless 函数、CLI 工具——这些场景 NestJS 太重了。用 Fastify 或 Express 直接写，启动快、部署简单。NestJS 是给中大型团队协作准备的。

Q：NestJS 11 有什么新东西？
11 版本默认支持 ESM，CLI 启动快了 40%，新增了流式响应支持。底层还是那套 DI 架构，升级平滑。

我的结论

NestJS 的价值不在性能，在架构纪律。它用 Module/Provider/Controller 三件套和 DI 容器，把"怎么组织代码"这件事从约定变成了强制。小项目可能觉得啰嗦，但团队超过 5 个人、代码超过 2 万行，你会感谢这些约束。

2026 年我团队的标准技术栈是 NestJS 11 + TypeScript 5.8 + Prisma 6 + Pino。下一篇我们深入 TypeScript——NestJS 的地基，怎么配才不裸奔。
