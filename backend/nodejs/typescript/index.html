TypeScript 后端实践

🏷️ Node.js 总览

我对 TypeScript 的态度变化

2018 年我第一次写 TypeScript，觉得它是"带类型的 JavaScript"，多此一举。后端不就写个接口吗，为什么要跟 Java 一样搞类型系统？后来线上出了个事故——前端传过来的 user_id 是字符串 ...

2026 年了，TypeScript 5.8 已经很成熟。Node.js 24 原生支持 type-stripping，NestJS 把 TS 当一等公民。这篇不讲基础语法——网上教程多的是。我讲的是后端项目里真正会用到的配置和踩坑。

flowchart LR TS[TypeScript 源码 .ts] --> TSC[tsc 类型检查 + 转译] TS --> STRIP[Node.js type-stripping
仅擦除类型不检查] TSC --> JS[JavaScript .js] STRIP --> JS JS --> RUN[Node.js 运行] style TSC fill:#00add8,stroke:#fff,color:#fff style STRIP fill:#f59e0b,stroke:#fff,color:#fff

tsconfig 怎么配才不算裸奔

我见过太多人用 tsc --init 生成的默认配置就开写。那个配置等于没配——strict 默认是 false，你写 let x: number = undefined 它都不报错。后端项目必须把 strict 全套打开：

{
  "compilerOptions": {
    "target": "ES2023",
    "module": "node16",
    "moduleResolution": "node16",
    "outDir": "./dist",
    "rootDir": "./src",
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "exactOptionalPropertyTypes": true,
    "noImplicitOverride": true,
    "noFallthroughCasesInSwitch": true,
    "forceConsistentCasingInFileNames": true,
    "esModuleInterop": true,
    "skipLibCheck": true,
    "declaration": true,
    "sourceMap": true,
    "removeComments": false,
    "resolveJsonModule": true,
    "baseUrl": "./src",
    "paths": {
      "@/*": ["*"],
      "@modules/*": ["modules/*"],
      "@common/*": ["common/*"]
    }
  },
  "include": ["src/**/*"],
  "exclude": ["node_modules", "dist", "**/*.spec.ts"]
}
配置项为什么必须开
strict总开关，包含 strictNullChecks 等所有严格检查
noUncheckedIndexedAccess数组索引访问返回 T | undefined，防越界访问
exactOptionalPropertyTypes可选属性不能显式传 undefined，区分"没传"和"传了 undefined"
noImplicitOverride子类重写父类方法必须写 override 关键字，防手滑
skipLibCheck跳过 .d.ts 文件检查，编译速度快 3 倍
strict 不开等于裸奔
不开 strictNullChecks，string 和 string | undefined 一视同仁。你写 user.name.length，user.name 可能是 undefined，运行时直接 crash。我见过线上因为这个挂了三次。strict 一开，编译器帮你拦住。

类型体操：后端需要多深

前端社区流行类型体操——模板字面量类型、递归条件类型、infer 到处飞。后端需要吗？大部分时候不需要。后端的核心类型就三块：API DTO、数据库实体、配置对象。把这三样定义好，业务逻辑写起来就很顺。

// 1. API DTO —— 请求/响应类型
interface CreateUserRequest {
  email: string
  password: string
  nickname?: string
}

interface UserResponse {
  id: number
  email: string
  nickname: string | null
  createdAt: string
}

// 2. 数据库实体 —— 跟 ORM 对齐
interface UserEntity {
  id: number
  email: string
  password_hash: string
  nickname: string | null
  created_at: Date
  updated_at: Date
}

// 3. 用 mapped type 自动从实体推导 DTO，不用手写两份
type UserDTO = Omit<UserEntity, 'password_hash'> & {
  createdAt: string  // Date 序列化成 ISO 字符串
}

真正值得学的类型技巧就三个：Omit/Pick/Partial（工具类型）、typeof 和 keyof（从值推导类型）、Discriminated Union（联合类型加判别字段）。剩下的遇到了再查，别硬背。

// Discriminated Union：API 错误返回的标准写法
type ApiResult<T> =
  | { ok: true; data: T }
  | { ok: false; error: { code: string; message: string } }

// 用法：必须先检查 ok 才能访问 data
function handleResult(result: ApiResult<User>) {
  if (result.ok) {
    console.log(result.data.id) // 这里 result 收窄成成功类型
  } else {
    console.error(result.error.code)
  }
}

路径别名：别写 ../../../

项目深了之后，import x from '../../../common/utils' 这种路径就是灾难。重构一下目录结构，全部 import 都断。用 tsconfig 的 paths 配置路径别名：

"paths": {
  "@/*": ["*"],
  "@modules/*": ["modules/*"],
  "@common/*": ["common/*"],
  "@config/*": ["config/*"]
}

代码里就可以写成：

// 之前：../../../common/logger
import { logger } from '@common/logger'

// 之前：../../modules/users/users.service
import { UsersService } from '@modules/users/users.service'
运行时也要生效
tsconfig 的 paths 只在编译时生效。编译成 JS 后，Node.js 不认识 @common/logger。两个方案：用 tsconfig-paths 在运行时解析，或者用 Node.js 24 的原生 imports 字段（package.json 的 imports 字段）。我团队现在统一用 Node.js 原生方案，不再依赖 tsconfig-paths。 
// package.json —— Node.js 原生路径别名
{
  "imports": {
    "#common/*": "./dist/common/*",
    "#modules/*": "./dist/modules/*"
  }
}

ESLint + Prettier：别再争论缩进

2026 年 ESLint 9 已经稳定了 flat config，不再用 .eslintrc。我团队的标准配置：

// eslint.config.mjs
import eslint from '@eslint/js'
import tseslint from 'typescript-eslint'
import prettier from 'eslint-config-prettier'

export default tseslint.config(
  eslint.configs.recommended,
  ...tseslint.configs.recommendedTypeChecked,
  prettier,
  {
    languageOptions: {
      parserOptions: {
        projectService: true,
      },
    },
    rules: {
      '@typescript-eslint/no-unused-vars': ['error', { argsIgnorePattern: '^_' }],
      '@typescript-eslint/no-explicit-any': 'warn',
      '@typescript-eslint/explicit-function-return-type': 'off',
    },
  },
)

Prettier 只管格式（缩进、分号、引号），ESLint 只管代码质量（未使用变量、any 滥用）。两者不打架。eslint-config-prettier 关掉 ESLint 里跟 Prettier 冲突的规则。

# 提交前自动跑
npx eslint --fix src/
npx prettier --write src/

# 配合 husky + lint-staged
npx husky init
echo "npx lint-staged" > .husky/pre-commit

调试：ts-node-dev 还是 node --watch

老教程教你用 ts-node 跑 TS。2026 年我推荐直接用 Node.js 原生的 --watch + type stripping：

# Node.js 24 原生支持，零依赖
node --watch --experimental-strip-types src/main.ts

# 如果你需要类型检查（type stripping 不做类型检查）
# 另开一个终端跑
tsc --noEmit --watch

要打断点调试，用 VS Code 的 launch.json：

// .vscode/launch.json
{
  "version": "0.2.0",
  "configurations": [
    {
      "name": "Debug NestJS",
      "type": "node",
      "request": "launch",
      "skipFiles": ["<node_internals>/**"],
      "program": "${workspaceFolder}/src/main.ts",
      "runtimeArgs": ["--experimental-strip-types"],
      "env": { "NODE_ENV": "development" }
    }
  ]
}
type stripping 不做类型检查
Node.js 24 的 type-stripping 只是把类型语法擦掉就跑，不检查类型对不对。你写了 let x: number = 'hello'，它照样跑。生产环境部署前必须跑 tsc --noEmit，不然类型错误直接带到线上。

从 JS 迁移到 TS：我的踩坑清单

我们团队从 Express JS 迁到 NestJS TS，花了三个月。总结几个最痛的坑：

flowchart TD JS[纯 JS 项目] --> RENAME[文件改名 .ts] RENAME --> ANY[先全量 any 编译通过] ANY --> GRADUAL[逐步收紧类型] GRADUAL --> NULLCHK[先开 strictNullChecks] NULLCHK --> OTHER[再开其他 strict 项] OTHER --> FULL[全 strict 通过] style ANY fill:#f59e0b,stroke:#fff,color:#fff style FULL fill:#10b981,stroke:#fff,color:#fff
  1. 类型定义滞后：先写代码后补类型，结果类型全是 any。正确做法是先定义接口/类型，再写实现。
  2. 第三方包没有类型：老的 npm 包不带 .d.ts。要么装 @types/xxx，要么自己写个 declarations.d.ts 声明成 any。
  3. this 指向丢失：在 class 方法里用回调，this 变成 undefined。要么用箭头函数属性，要么在构造函数里 bind。
  4. 枚举的陷阱：TypeScript 的 enum 会编译成真实对象，体积大且有运行时开销。2026 年我都用 as const + 联合类型代替 enum。
  5. 严格模式渐进开启：一次性把 strict 全打开，编译报错几百个。先开 strictNullChecks，修完再开其他的，一个一个来。
// 用 as const 代替 enum
// 之前：enum Status { Active = 'active', Inactive = 'inactive' }
const Status = {
  Active: 'active',
  Inactive: 'inactive',
} as const

type Status = typeof Status[keyof typeof Status]
// 等于 type Status = 'active' | 'inactive'

FAQ

Q：TypeScript 编译很慢怎么办？
大项目用 tsc --build --incremental，增量编译快很多。或者用 SWC/esbuild 做转译（不做类型检查），类型检查另开一个进程跑。NestJS 11 已经默认用 SWC 了。

Q：后端要不要学类型体操？
工具类型（Partial/Omit/Pick/ReturnType）必须会。深层递归类型、模板字面量体操，遇到了再学。别花一周时间学类型体操，不如多写两个接口。

Q：Node.js 原生 type stripping 能替代 tsc 吗？
开发环境可以，生产不行。type stripping 不做类型检查，生产必须跑一遍 tsc --noEmit 或者用 SWC 转译。NestJS 项目用 nest build，它内部调 tsc/SWC。

Q：any 和 unknown 怎么选？
永远别用 any——它是逃生舱，用多了 TS 白写。真不知道类型用 unknown，然后在使用处做类型收窄。function parse(x: unknown) { if (typeof x === 'string') { ... } }。

我的结论

TypeScript 后端实践的核心不是"学会类型语法"，是把类型当成文档。你定义好 DTO、实体、配置的类型，团队新人看一眼类型就知道接口长什么样，不用翻文档。strict 全套打开 + 路径别名 + ESLint 配齐，你的 TS 项目就不会变成"带 any 的 JS"。
