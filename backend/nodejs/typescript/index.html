Node.js 项目里的 TypeScript 工程化

🏷️ Node.js 总览

Node 项目里关于 TypeScript 的争论，早就不在「要不要写类型」上了，而在工程链路上：谁负责类型检查、谁负责产出 JavaScript、模块解析按哪套规则走、为什么本地跑得好好的代码到生产就报找不到模块。这篇不讲语法，只讲这条链路里那些编译期看着没事、运行期才炸的接缝。

类型检查和转译是两条独立的流水线

tsc 同时干两件事：构建整个项目的类型图做检查，以及把 TS 语法降级成目标版本的 JavaScript。esbuild 和 swc 只干第二件，而且是逐文件干的——拿到一个文件就能输出结果，不需要知道别的文件长什么样。这不是「实现得更快」，是工作量根本不同：构建跨文件类型图需要把整个依赖图（包括 node_modules 里的 .d.ts）读进来做推导，这部分开销天生无法靠重写语言消掉。

结论很直接：转译器永远替代不了类型检查器，所以工程上要把两件事拆成两条并行的流水线，产物走快的那条，检查走准的那条，用 CI 门禁把它们绑在一起。

Node 从 22.6 起有 --experimental-strip-types，只擦除可擦除语法；enum、namespace、构造函数参数属性这类会生成运行时代码的语法要另外用 --experimental-transform-types。TS 5.8 加了 erasableSyntaxOnly，作用是让编译器直接禁掉这些语法，免得你写完才发现 Node 跑不了。Bun 内置转译、连 tsconfig 的 paths 都认，细节见站内 Bun 专题。

transpile-only 到底漏掉了什么

很多人以为「跳过类型检查」只是少了一道保险，其实还顺带改变了几个语义。下面这些坑都不是理论问题，是单文件转译的必然结果。

语义tsc 的行为单文件转译的行为线上表现规避
跨文件引用 const enum把成员值内联成字面量看不到定义，无法内联取到 undefined 或直接引用了被擦掉的对象开 isolatedModules；用 as const 对象替代
重导出类型 export { User } from './types'知道 User 是类型，整条语句擦掉当成值，保留 import 语句运行时报导出不存在开 verbatimModuleSyntax，写 export type
装饰器元数据写入 design:paramtypesesbuild 不生成，swc 要显式开Nest 报无法解析依赖用 swc 并开 decoratorMetadata
构造函数参数属性展开成字段赋值swc/tsc 支持，Node 原生擦除不支持实例属性是 undefined显式写字段；或开 erasableSyntaxOnly
类型错误本身报错并以非零码退出完全静默任意运行时异常CI 强制 tsc --noEmit

moduleResolution 与 ESM/CJS 双轨

moduleResolution 决定编译器按哪套规则找模块和类型，它必须跟你产物的真实运行方式对齐，否则就会出现「编译过了但 Node 找不到」或者反过来「Node 跑得通但类型报错」。

取值读 exports/imports 字段相对导入要写扩展名对应的运行方式典型报错
node10（旧名 node）否不要求只跑 CJS 的老项目包只在 exports 里声明了 types，于是报 TS2307 找不到声明
node16是ESM 文件里必须写 .js直接交给 Node 跑，语义固定漏写扩展名报 TS2835，并建议你改成 .js
nodenext是同 node16跟随最新 Node 语义随 TS 版本演进，比如 require ESM 的判定会变
bundler是不要求产物还要过 Vite/webpack/esbuild把产物直接给 Node 会 ERR_MODULE_NOT_FOUND

要注意 bundler 只能配合 module 为 esnext 或 preserve 使用，它明确假设「有人会帮你重写模块路径」。如果你的后端没有打包步骤，选它就等于让类型检查和运行时用两套规则，编译期发现不了任何路径问题。TS 5.8 在 nodenext 下才开始允许 require 一个 ESM 模块，对应的正是 Node 22.12 放开的能力——这类版本联动就是为什么 nodenext 要跟着 TS 和 Node 一起升。

sequenceDiagram participant APP as 应用源码 participant TSC as tsc 解析器 participant PKG as 依赖的 package.json participant NODE as Node 运行时解析器 APP->>TSC: 导入某个包的子路径 TSC->>PKG: 按 moduleResolution 查 exports 的 types 条件 PKG-->>TSC: 命中则返回声明文件路径 Note over TSC,PKG: node10 不读 exports，只按目录猜 index.d.ts

能力CJSESM迁移写法
__dirname / __filename有没有Node 20.11+ 用 import.meta.dirname；更老版本用 fileURLToPath

import { readFile } from 'node:fs/promises'
import { fileURLToPath } from 'node:url'
import { createRequire } from 'node:module'
import path from 'node:path'

// ESM 里没有 __dirname。Node 20.11+ 有 import.meta.dirname，
// 留一层兜底是为了同一份代码还能在旧 LTS 上跑
const here = import.meta.dirname ?? path.dirname(fileURLToPath(import.meta.url))

// 顶层 await 只有 ESM 能用：配置读不到就让进程起不来，而不是第一个请求才报错
const cfg = JSON.parse(await readFile(path.join(here, 'config.json'), 'utf8'))

// 必须同步拿一个只发了 CJS 的包时，显式造一个 require
const require = createRequire(import.meta.url)
const legacy = require('some-cjs-only-pkg')

// 反方向：CJS 文件里要用纯 ESM 包，不要 require，用动态 import
// const { default: chalk } = await import('chalk')

export { here, cfg, legacy }

.d.ts、exports 与 types 字段的解析失败

「装了包但类型找不到」这类问题，九成出在包的 exports 与 types 条件怎么写，以及你的 moduleResolution 认不认它。下表是我见过频率最高的几种。

症状根因修法
TS2307 找不到模块或其类型声明，但 node_modules 里明明有包用 exports 声明子路径，moduleResolution 还是 node10升到 node16 / nodenext / bundler
类型正常，运行时 ERR_PACKAGE_PATH_NOT_EXPORTED包没在 exports 暴露这个子路径，只是目录里恰好有文件改用官方入口，别按目录深挖
导入成功但调用时报 not a function包只发了 CJS，ESM 下命名导出没解析出来默认导入整个对象再取属性
自己发的包，下游报没有类型exports 里 types 条件写在 import/require 之后types 必须是条件对象里的第一个键
CJS 消费者拿到了 ESM 形状的类型双轨发布只给了一份 .d.ts分别产出 .d.ts 与 .d.cts，用 arethetypeswrong 自查
报两个同名类型互不兼容依赖树里有两份同一个 @types 包npm ls 定位后用 overrides 收敛版本

顺便纠正一个流传很广的说法：skipLibCheck: true 并不是「编译快三倍」的开关。它的作用是跳过对依赖 .d.ts 内部一致性的检查，让你不至于因为两个第三方包的类型互相打架而无法编译；你自己代码里用到这些类型时，检查照旧进行。它带来的加速取决于依赖声明的体积，可能明显，也可能几乎没有。留着它是为了少受别人的类型 bug 影响，不是为了提速。

strict 的子开关：收益与改造成本

strict 不是一个开关，是八个。另外两个报错量最大的开关不在 strict 里面，这是老项目改造时最常见的误解。

开关属于 strict拦住什么老项目改造成本注意
noImplicitAny是参数和变量隐式退化成 any中，首次开启报错量最大先补函数签名，收益立刻可见
strictNullChecks是对可能为 null/undefined 的值直接解引用高，牵连整个调用链价值最高的一个；很多别的开关依赖它才生效
strictFunctionTypes是参数逆变不安全的回调赋值低只作用于函数类型写法，方法语法仍是双变，这是故意留的口子
strictBindCallApply是bind/call/apply 的参数错配低基本无痛
strictPropertyInitialization是类字段声明非空却没赋值中依赖 strictNullChecks；DI 注入的字段常需断言
noImplicitThis是回调里的 this 变成 any低老 function 写法多的项目会报一批
useUnknownInCatchVariables是catch 变量当 any 直接取 .message低统一加一个 toError 收窄函数即可
alwaysStrict是产物缺少严格模式声明低几乎无感
noUncheckedIndexedAccess否把数组下标和索引签名当成必然存在高，误报感很强循环里改用 for-of 或先解构判空，不要到处加感叹号
exactOptionalPropertyTypes否分不清「没传」和「显式传 undefined」高和不少第三方类型冲突，新项目开、老项目慎开
erasableSyntaxOnly否用了 enum/namespace/参数属性导致原生擦除跑不动低打算用 Node 直接跑 .ts 就该开

改造顺序上，别指望一次全开。可行的路径是：先只开 noImplicitAny 修完，再开 strictNullChecks，这两步吃掉八成收益；剩下的按开关逐个开，每次一个 PR。中间态可以用 tsconfig 的 exclude 或者单独一份 tsconfig.strict.json 只 include 已达标的目录，让 CI 同时跑两套检查、防止已改好的目录退化。

类型只活在编译期，边界仍然要校验

这是最值得反复说的一条：编译产物里没有任何类型检查代码。你写 function f(u: User)，运行时传进来一个 {} 也照样执行。凡是数据来自进程外部，静态类型就只是一句注释。

import { z } from 'zod'

// 单一事实来源：类型从 schema 推导，避免手写 interface 后两边各自漂移
const CreateUser = z.object({
  email: z.string().email(),
  // query string 里一切都是字符串，必须显式 coerce，否则 age 永远校验失败
  age: z.coerce.number().int().min(0).max(150),
  role: z.enum(['admin', 'member']).default('member'),
})
type CreateUser = z.infer<typeof CreateUser>

// 环境变量在启动时就要炸，而不是等第一个请求命中那行代码
const Env = z.object({
  DATABASE_URL: z.string().url(),
  PORT: z.coerce.number().default(3000),
  NODE_ENV: z.enum(['development', 'test', 'production']),
})
export const env = Env.parse(process.env)

export function createUser(raw: unknown) {
  const r = CreateUser.safeParse(raw)
  // 用 safeParse 而不是 parse，是为了把校验失败映射成 4xx 而不是 500
  if (!r.success) return { ok: false as const, issues: r.error.issues }
  return { ok: true as const, data: r.data }   // 到这里 r.data 才真的是 CreateUser
}

同理，as 断言和 JSON.parse 是类型系统里最大的两个洞：前者是你告诉编译器「别管了我说得对」，后者返回 any，一旦赋给有类型的变量，后面所有推导都建立在一个谎言上。想表达「这个对象符合某个类型」但仍要检查，用 satisfies 而不是 as。

source map 与生产排错

栈里全是 dist/main.js:1:23456 的时候，光有 sourceMap 配置不够，还要保证 map 文件真的跟着产物进了镜像，并且进程启用了映射。

配置产物栈帧可读性是否泄漏源码适用
都不开只有 .js行号指向产物，需要人工对照否不推荐
sourceMap: true.js 加 .js.map，产物末尾带引用注释配合 --enable-source-maps 可读map 里只有路径映射默认选择
inlineSourceMapmap 内嵌进 .js同上否单文件脚本、不方便带附属文件时
inlineSources: truemap 里包含 .ts 全文最好，能打印出源码行会把源码发出去内网服务可用，对外产物别开
declarationMap.d.ts.map与栈无关需一起发源码才有意义monorepo 内部包，让 IDE 跳回 .ts

几个容易忽略的点：--enable-source-maps（也可以写进 NODE_OPTIONS）默认不开，不开则栈完全不映射；Docker 镜像里如果只 COPY dist/*.js 而漏掉 .map，映射同样失效；Error.stackTraceLimit 默认是 10，深栈会被截断，排查复杂调用链时先把它调大；异步栈靠 V8 的 async stack trace 串联，跨 setTimeout 之类的宏任务边界仍然会断。要给 APM 上传 map 又不想泄漏映射关系，通常做法是上传后删掉产物里的 sourceMappingURL 注释（tsc 没有对应开关，用 esbuild 的 external 模式或构建脚本处理）。运行时层面的采样与火焰图见站内 Node.js 性能优化一篇。

monorepo：project references 与增量构建

多包仓库有三种组织方式，区别不在「哪个更优雅」，在于增量粒度和运行时解析谁来负责。

方式编译单元增量粒度跨包跳转主要代价
一个 tsconfig include 所有包整仓一个无，改一行全量重检直接到 .ts包之间没有边界，循环依赖无法发现，大仓 tsc 启动慢
paths 别名直指源码整仓一个无直接到 .ts只在编译期生效，运行时要另配解析；发布出去下游用不了
project references + composite每包一个按包，靠 .tsbuildinfo 判定靠 declarationMap必须先构建出 .d.ts，配置更啰嗦

// tsconfig.json（仓库根，只做编排，自己不含文件）
{
  "files": [],
  "references": [
    { "path": "./packages/core" },
    { "path": "./packages/api" }
  ]
}

// packages/api/tsconfig.json
{
  "extends": "../../tsconfig.base.json",
  "compilerOptions": {
    "composite": true,        // 必须开，才会写 .tsbuildinfo 并参与增量判定
    "declaration": true,      // composite 的隐含要求：下游只看 .d.ts
    "declarationMap": true,   // 让 IDE 从 .d.ts 跳回 core 的 .ts 源码
    "rootDir": "src",
    "outDir": "dist",
    "tsBuildInfoFile": "dist/.tsbuildinfo"
  },
  "include": ["src"],
  "references": [{ "path": "../core" }]   // 跨包只能这样连，不要 include 别人的 src
}

用 references 之后，构建命令要换成 tsc -b（或 tsc --build），它会按依赖拓扑序逐个判定。判定依据是输入文件与输出的时间戳加上 .tsbuildinfo 里记录的配置，所以 CI 上如果不缓存 .tsbuildinfo，增量就完全不存在——这是「明明配了 incremental 还是每次全量」最常见的原因。另一个高频坑是同时用了 references 和指向源码的 paths：两套解析规则并存时，编译器可能绕过 .d.ts 直接读源码，于是包边界形同虚设，改一行还是全仓重检。

最容易踩的坑

⚠️
这些都是能复现的
  • 整条链路没有一处跑 tsc --noEmit：开发用 transpile-only、构建用 swc、CI 只跑测试，类型错误零拦截。写一行错误类型试试 CI 会不会红。
  • 用 esbuild 编译 NestJS：装饰器元数据不生成，启动时报无法解析依赖，看起来像 DI 配置错了，实际是转译器选错。
  • const enum 跨文件引用配单文件转译：运行时取到 undefined，且没有任何报错。开 isolatedModules 让编译器提前拦。
  • 老项目留着 moduleResolution: node10：新依赖只在 exports 里声明 types，于是报类型找不到，误以为要装 @types。
  • module: esnext 加 moduleResolution: bundler，但后端没有打包步骤：编译全过，Node 起来就 ERR_MODULE_NOT_FOUND。
  • 把 type: "module" 加进 package.json 却没改代码：__dirname 直接 ReferenceError，相对导入缺扩展名全部解析失败。
  • 在 CJS 里 require 一个含顶层 await 的 ESM 包：新版本 Node 抛 ERR_REQUIRE_ASYNC_MODULE，换成 await import() 才行。
  • 以为 strict: true 把严格检查全开了：noUncheckedIndexedAccess 和 exactOptionalPropertyTypes 根本不在里面。
  • 把 skipLibCheck 当性能开关宣传：它跳过的是依赖声明的自检，不是你代码的检查，加速幅度完全取决于依赖。
  • 相信「有类型所以不用校验」：请求体、环境变量、数据库 JSON 列全都可能不符合声明，边界必须 parse。
  • 用 as 把 JSON.parse 的结果断言成业务类型：后面所有推导都建立在这个断言上，错了也不报。
  • 镜像里只拷了 .js 没拷 .map，或者忘了 --enable-source-maps：线上栈永远是产物行号。
  • CI 不缓存 .tsbuildinfo 却期待增量构建：每次都是全量，还以为 project references 没用。
  • references 和指向源码的 paths 混用：包边界被绕过，增量退化成全量。
