Node.js 事件循环

🏷️ Node.js 总览

事件循环到底是什么

我见过太多 Node.js 开发者，写了两年 Express，说不清楚事件循环怎么转。这不怪他们——文档写得像论文，面试题又全是 console.log 顺序题。

一句话说清：事件循环是一个 while(true) 循环，不断检查有没有事件要处理，有就跑回调，没有就去阻塞等。它由 libuv 实现，跑在主线程上。你写的所有 JS 代码都在这个循环里执行。

flowchart TD START[进入事件循环] --> TIMERS[timers 阶段
执行 setTimeout/setInterval 回调] TIMERS --> PENDING[pending callbacks
上一轮延迟的系统回调] PENDING --> IDLE[idle/prepare
libuv 内部用] IDLE --> POLL[poll 阶段
取新的 IO 事件，阻塞在这里] POLL --> CHECK[check 阶段
执行 setImmediate 回调] CHECK --> CLOSE[close callbacks
socket.on close 等] CLOSE --> START style TIMERS fill:#f59e0b,stroke:#fff,color:#fff style POLL fill:#00add8,stroke:#fff,color:#fff style CHECK fill:#10b981,stroke:#fff,color:#fff

六个阶段，一个都不能少

很多人以为事件循环就是"先执行同步代码，再执行异步回调"。太粗糙了。每个阶段有自己的队列，一个阶段跑完所有回调才进下一个阶段。关键规则：每个阶段的队列清空了（或达到上限）才切换阶段。

阶段处理什么常用 API
timers到期的定时器回调setTimeout, setInterval
pending callbacks上一轮延迟的系统级回调TCP 错误等
idle/preparelibuv 内部用—
poll新 IO 事件，会阻塞等fs.readFile, 网络回调
checksetImmediate 回调setImmediate
close callbacksclose 事件socket.on('close')

重点说 poll 阶段。这是事件循环的"主战场"——如果 poll 队列空了，事件循环会阻塞在这里等新的 IO 事件。但如果有 setImmediate 注册了，它不会傻等，直接跳到 check 阶段。这就是为什么 setImmediate 比 setTimeout(fn, 0) 快——它跳过了 poll 的等待。

microtask 和 macrotask：两套队列

光知道六个阶段还不够。每个阶段之间，Node.js 会先把 microtask 队列全部清空，才进入下一个阶段。这就是为什么 process.nextTick 和 Promise.then 总是比 setTimeout 先跑。

flowchart LR SYNC[同步代码执行] --> MICRO1[清空 nextTick 队列] MICRO1 --> PROMISE1[清空 Promise 队列] PROMISE1 --> MACRO1[执行一个 macrotask
（一个阶段的回调）] MACRO1 --> MICRO2[再次清空 nextTick 队列] MICRO2 --> PROMISE2[再次清空 Promise 队列] PROMISE2 --> MACRO2[下一个 macrotask] style MICRO1 fill:#dc382d,stroke:#fff,color:#fff style MICRO2 fill:#dc382d,stroke:#fff,color:#fff

看个实际的例子，你就明白执行顺序了：

console.log('1: 同步代码')

setTimeout(() => console.log('2: setTimeout'), 0)

setImmediate(() => console.log('3: setImmediate'))

Promise.resolve().then(() => console.log('4: Promise.then'))

process.nextTick(() => console.log('5: nextTick'))

console.log('6: 同步代码结束')

// 输出顺序：1 → 6 → 5 → 4 → 2 → 3
// 注意 2 和 3 的顺序不确定！
// 在 I/O 回调里 setImmediate 一定比 setTimeout(fn,0) 快
// 但在主模块里，取决于机器性能，可能反

process.nextTick vs setImmediate

这是面试必考、线上必踩的坑。两个函数名字很像，行为完全不同。

对比process.nextTicksetImmediate
队列位置当前阶段结束后立刻执行check 阶段执行
优先级比 Promise 还高比 I/O 回调晚
会不会饿死 IO会！递归调用直接卡死不会
典型用途确保回调在同步代码后执行把重活拆到下一轮循环
nextTick 递归能把事件循环卡死
我见过有人在 nextTick 回调里再调 nextTick，以为是"异步"。结果事件循环永远在清空 nextTick 队列，poll 阶段根本进不去，所有 IO 回调全部饿死。整个服务假死，CPU 100%。除非你确实需要最高优先级，否则用 queueMicrotask() 或 Promise.resolve().then()。 
// 危险：这会卡住事件循环
function recursiveNextTick() {
  process.nextTick(recursiveNextTick) // 永不结束
}
recursiveNextTick()

// 安全：setImmediate 每轮循环才执行一次
function safeDefer() {
  setImmediate(safeDefer) // 每轮 event loop 跑一次，不会阻塞 IO
}
safeDefer()

异步 IO 的底层：libuv 线程池

很多人以为 Node.js 的异步 IO 是内核原生的。一半对一半不对。网络 IO（TCP/UDP）确实走内核的 epoll/kqueue，真异步。但文件 IO、DNS 查询、加密计算这些，走的是 libuv 线程池——默认 4 个线程，你可以通过环境变量调大。

flowchart TD APP[你的 Node.js 代码] --> CHECK_IO{什么操作?} CHECK_IO -->|网络请求| NET[内核 epoll/kqueue
真异步，不占线程] CHECK_IO -->|文件读写| POOL[libuv 线程池
默认 4 线程] CHECK_IO -->|DNS 解析| POOL CHECK_IO -->|crypto.pbkdf2| POOL CHECK_IO -->|zlib 压缩| POOL NET --> LOOP[事件循环回调] POOL --> LOOP style POOL fill:#f59e0b,stroke:#fff,color:#fff style NET fill:#10b981,stroke:#fff,color:#fff

这就解释了一个经典现象：同时读 1000 个文件，Node.js 只能同时处理 4 个。不是 Node.js 慢，是你把活全压在 4 个线程上了。调大线程池：

# 在代码最开头设置，必须在任何 IO 调用之前
export UV_THREADPOOL_SIZE=16

// 或者代码里
process.env.UV_THREADPOOL_SIZE = '16'
线程池不是越大越好
我调过 64，结果吞吐量不升反降。为什么？线程切换开销。磁盘 IO 密集型任务，线程数等于磁盘并发上限就够了。CPU 密集型的加密运算，线程数等于 CPU 核数最好。别盲目调大，压测说话。

Worker Threads：真·多线程

Node.js 10 引入 Worker Threads，12 之后稳定。它不是线程池，是真正的 V8 实例——每个 Worker 有自己的事件循环、自己的堆内存。适合跑 CPU 密集任务，不适合跑 IO（IO 有跨线程通信开销）。

// worker.js —— 跑 CPU 密集任务
const { parentPort } = require('worker_threads')

parentPort.on('message, (data) => {
  let result = 0
  for (let i = 0; i < data.iterations; i++) {
    result += Math.sqrt(i)
  }
  parentPort.postMessage(result)
})
// main.js —— 主线程
const { Worker } = require('worker_threads')

const worker = new Worker('./worker.js')

worker.postMessage({ iterations: 10_000_000 })
worker.on('message', (result) => {
  console.log('结果:', result)
})

Worker 之间通过 postMessage 通信，数据是结构化克隆——不是共享内存，是拷贝。所以传大对象性能很差。要共享内存用 SharedArrayBuffer，但那是另一套心智模型了。

阻塞事件循环的常见凶手

我线上出过三次"事件循环被阻塞"的事故，凶手全是下面这些：

  1. 同步 JSON.parse 大字符串：一个 50MB 的 JSON.parse，阻塞主线程 800ms。所有请求排队。
  2. 循环里做同步加密：crypto.pbkdf2Sync 在请求处理里调，每来一个请求就阻塞一下。
  3. 正则回溯爆炸：用户输入触发 Catastrophic Backtracking，CPU 100% 转不出来。
  4. 同步读大文件：fs.readFileSync 在启动时用没问题，在请求路径里用就是灾难。
  5. 监控上报忘了异步：循环里同步写日志，日志写到磁盘慢了，整个服务卡。
怎么发现事件循环被阻塞
用 perf_hooks 监控事件循环延迟。正常应该 <1ms。我在生产环境挂了个监控，超过 50ms 就报警，超过 200ms 直接 dump 堆快照。线上问题 90% 是同步代码阻塞，不是你想象的复杂原因。 
const { monitorEventLoopDelay } = require('perf_hooks')
const h = monitorEventLoopDelay({ resolution: 20 })
h.enable()

setInterval(() => {
  // p50 和 p99 延迟
  console.log('p50:', h.percentile(50) / 1e6, 'ms')
  console.log('p99:', h.percentile(99) / 1e6, 'ms')
  if (h.percentile(99) / 1e6 > 200) {
    console.warn('事件循环阻塞超过 200ms!')
  }
}, 5000)

回调地狱：2026 年还有吗

基本没了。async/await 是 ES2017 的东西，现在谁还写嵌套回调？但有个变种还在——未捕获的 Promise rejection。你写了个 async 函数，里面 throw 了，没 catch，Node.js 24 直接崩进程。

// 这样写，报错了你都不知道
app.get('/user/:id', async (req, res) => {
  const user = await db.find(req.params.id)
  // 如果 db.find 抛错，Promise rejection 未捕获，进程退出
  res.json(user)
})

// 正确做法：全局兜底
process.on('unhandledRejection', (err) => {
  console.error('未捕获 Promise 错误:', err)
  // 别直接 exit，先记录再决定
})

FAQ

Q：setTimeout(fn, 0) 和 setImmediate 哪个先执行？
在主模块里不一定，取决于机器负载。在 I/O 回调里 setImmediate 一定先。别在代码里依赖这个顺序，用 queueMicrotask() 或 process.nextTick 明确表达意图。

Q：事件循环阻塞了，加机器有用吗？
没用。单进程的事件循环堵在一个核上，加机器只是多开几个进程。你要做的是找到阻塞点，把它改成异步，或者丢给 Worker Thread。

Q：Node.js 24 的 event loop 有变化吗？
核心模型没变，但 V8 13.x 优化了 microtask 执行效率，WebSocket 事件处理从 poll 阶段独立出来了。整体逻辑一样，别被新特性吓到。

Q：Worker Thread 和 cluster 有什么区别？
Worker 是单进程内的真线程，共享内存可以用 SharedArrayBuffer，适合 CPU 密集子任务。cluster 是多进程，每个进程独立 V8 实例，适合利用多核跑完整服务。

我的结论

事件循环是 Node.js 设计哲学的浓缩——单线程、非阻塞、事件驱动。理解了六个阶段和 microtask 队列的关系，你就能解释 90% 的"为什么我的代码跑出来顺序不对"。

生产环境我最在意的就两件事：别阻塞事件循环（用 monitorEventLoopDelay 监控），别让 nextTick 递归饿死 IO。剩下的，都是写业务逻辑的事。下一篇我们讲 NestJS——在这个事件循环之上，怎么把一个中大型项目的架构组织好。
