Node.js 性能优化

🏷️ Node.js 总览

我调过最离谱的一次性能事故

2024 年我们有个服务，QPS 从 500 涨到 2000，P99 延迟从 50ms 飙到 3 秒。CPU 才 30%，内存稳定，数据库连接池没满。

这个事故教会我一件事：Node.js 性能问题 90% 不是算法问题，是你写了同步代码阻塞了事件循环。这篇文章讲的就是怎么发现和避免这类问题。

V8 优化原理：隐藏类和内联缓存

你写的 JavaScript 代码，V8 会把它编译成机器码执行。但 V8 不是一上来就优化——它先跑解释器（Ignition），收集类型反馈，热点函数再交给优化编译器（TurboFan）编译成优化机器码。

收集类型反馈] IGNITION --> HOT{热点函数?} HOT -->|是| TURBOFAN[TurboFan 优化编译
生成机器码] HOT -->|否| IGNITION TURBOFAN --> DEOPT{类型变了?} DEOPT -->|是| DEOPT2[Deoptimize
退回解释器] DEOPT -->|否| FAST[高速执行] DEOPT2 --> IGNITION style TURBOFAN fill:#10b981,stroke:#fff,color:#fff style DEOPT2 fill:#dc382d,stroke:#fff,color:#fff

两个关键概念：

  • 隐藏类（Hidden Class）：V8 把对象的形状（有哪些属性、什么顺序）抽象成隐藏类。同一隐藏类的对象，属性访问可以直接用偏移量，不用查字典。如果你给对象动态加属性，隐藏类就变了，V8 要重新建类，性能下降。
  • 内联缓存（Inline Cache, IC）：V8 记住上次 obj.x 这个属性访问在哪个隐藏类上。下次同一个位置访问，如果隐藏类一样，直接用缓存的偏移量，快一个数量级。
// 好：所有对象同一形状，V8 能优化
function createUser(name, age) {
  return { name, age } // 每次都是 {name, age}，隐藏类一致
}

// 坏：动态加属性，隐藏类一直变
function createUserBad(name, age) {
  const user = { name }
  if (age) user.age = age  // 有时有 age，有时没有，隐藏类分裂
  return user
}
写代码的 V8 友好原则
1. 对象初始化时就把所有属性设好，别后面动态加。2. 别用 delete 删属性——它让隐藏类失效。3. 数组尽量放同类型元素，别混着 number 和 string。4. 热点函数别传不同形状的对象。

内存泄漏排查：clinic.js 和 Chrome DevTools

Node.js 内存泄漏不像后端 Java 那么常见，但一旦出了很恶心——服务跑着跑着内存只涨不跌，最后 OOM 被杀。我线上遇到过三次，凶手全是同一个：全局 Map 里存了数据，用完没删。

排查工具首选 clinic.js——Node.js 官方团队出的，一键诊断：

# 安装
npm install -g clinic

# 诊断内存泄漏
clinic heapprofiler -- node server.js

# 诊断事件循环阻塞
clinic doctor -- node server.js

# 诊断火焰图
clinic flame -- node server.js

clinic 会自动跑你的服务，你压测它，然后它生成一个 HTML 报告，告诉你哪里在泄漏。

手动排查用 Chrome DevTools：

# 以调试模式启动
node --inspect server.js

# 打开 chrome://inspect，点击 inspect
# 1. 拍一个堆快照（Heap Snapshot）
# 2. 跑一会儿业务
# 3. 再拍一个堆快照
# 4. 对比两个快照，看什么对象涨了
泄漏模式怎么发现怎么修
全局 Map/Set 只加不删堆快照看 Map 大小加 TTL 或用 LRU 缓存
闭包引用了大对象堆快照看 Retainers用完置 null
事件监听器没移除堆快照看 EventEmitteron 改 once 或 off
缓存无上限监控缓存大小加 max 限制
生产环境抓堆快照
别在生产直接 --inspect——安全风险。用 node --heapsnapshot-near-heap-limit=3，内存快满时自动抓快照。或者在代码里用 v8.writeHeapSnapshot() 手动触发。抓下来的 .heapsnapshot 文件拿回本地用 Chrome DevTools 分析。

GC 调优：别瞎调

V8 的垃圾回收是自动的，分新生代（Scavenge）和老生代（Mark-Compact）。2026 年 Node.js 24 用的 V8 13.x，GC 已经很智能了。大部分情况你不用管。

但如果你服务 GC 频繁（每秒 GC 好几次），可以调几个参数：

# 看 GC 日志
node --trace-gc server.js

# 调新生代大小（默认 16MB，大对象多可以调大）
node --max-semi-space-size=64 server.js

# 调老生代大小（默认约 1.4GB）
node --max-old-space-size=2048 server.js

# 看内存上限
node -e "console.log(require('v8').getHeapStatistics().heap_size_limit / 1024 / 1024, 'MB')"
别 GOGC=off
有人学 Go 那套，想关掉 GC 提升性能。Node.js 没有 GOGC，但你可以调大堆上限让 GC 少跑。结果就是内存只涨不跌，OOM 来得更快。GC 是保护你的，不是你的敌人。

流式处理：别把整个文件读进内存

这是我见过最多的性能反模式——fs.readFile 读一个 500MB 的 CSV，然后 JSON.parse，内存直接爆。正确做法是用 Stream，边读边处理：

// 坏：整个文件读进内存
import fs from 'fs'
fs.readFile('big.csv', 'utf8', (err, data) => {
  const rows = data.split('\n') // 500MB 字符串在内存里
  processRows(rows)
})

// 好：流式处理
import { createReadStream } from 'fs'
import { createInterface } from 'readline'

const rl = createInterface({
  input: createReadStream('big.csv'),
  crlfDelay: Infinity,
})

let count = 0
rl.on('line', (line) => {
  processRow(line) // 一行一行处理，内存恒定
  count++
})
rl.on('close', () => console.log('处理了', count, '行'))

HTTP 响应也是一样——别 res.json(hugeArray)，用流式响应：

// Fastify 流式响应
app.get('/download', async (req, reply) => {
  const stream = createReadStream('./large-file.csv')
  reply.type('text/csv').send(stream)
})

集群模式：利用多核

Node.js 单进程只能用一个核。你的服务器有 16 核，不用 cluster 就是浪费。PM2 帮你搞定了这件事：

# PM2 一键集群模式
pm2 start server.js -i max
# -i max 等于 CPU 核数
# PM2 自动做负载均衡和进程管理

手写 cluster 模块也行，但 PM2 多了日志轮转、自动重启、零停机重启。生产环境用 PM2 就对了：

// 原生 cluster 示例（了解原理用，生产用 PM2）
import cluster from 'cluster'
import os from 'os'

if (cluster.isPrimary) {
  const numCPUs = os.cpus().length
  for (let i = 0; i < numCPUs; i++) {
    cluster.fork()
  }
  cluster.on('exit', (worker) => {
    console.log('worker 挂了，重启')
    cluster.fork()
  })
} else {
  // worker 进程跑你的服务
  import('./server.js')
}

常见性能反模式

  1. 在请求处理里做同步重计算：JSON.parse 大字符串、crypto.pbkdf2Sync、同步读文件。全部改成异步或丢 Worker Thread。
  2. 每次请求新建数据库连接：必须用连接池。Prisma/TypeORM 默认就有，别自己写 new Pool() 忘了复用。
  3. 同步日志打到 stdout：console.log 在高并发下比 Pino 慢 5 倍。换 Pino，异步写入。
  4. 无分页全量查询：SELECT * FROM users 一次拉 100 万行。必须分页或游标。
  5. N+1 查询：循环里查数据库。用 JOIN 或批量查询。
  6. 把大对象存 session：express-session 默认存在内存里，每个请求都序列化。换 Redis session store。

监控：别等用户投诉才发现

性能优化的前提是你知道哪里慢。我在生产环境必挂这几个指标：

import { monitorEventLoopDelay } from 'perf_hooks'
import * as opentelemetry from '@opentelemetry/api'

// 1. 事件循环延迟
const el = monitorEventLoopDelay({ resolution: 20 })
el.enable()

// 2. 内存使用
setInterval(() => {
  const usage = process.memoryUsage()
  console.log('heapUsed:', usage.heapUsed / 1024 / 1024, 'MB')
  console.log('rss:', usage.rss / 1024 / 1024, 'MB')
  if (el.percentile(99) / 1e6 > 200) {
    console.warn('事件循环 p99 > 200ms')
  }
  el.reset()
}, 10000)

// 3. 接入 OpenTelemetry，看每个接口的 P50/P99
// 4. 接入 Prometheus + Grafana，大盘看 QPS/延迟/错误率

FAQ

Q：Node.js 服务内存一直涨正常吗？
先看是不是正常的堆增长——V8 不会一用满就 GC，它会等堆到阈值才收。如果稳定在一个范围内（比如 500MB），正常。如果每小时涨 100MB 不回头，就是泄漏，用 clinic 查。

Q：Worker Thread 能解决 CPU 密集问题吗？
能，但有成本。Worker 之间通信是拷贝，传大对象很慢。适合纯计算任务（比如图片处理、JSON 大对象 parse）。如果是数据库查询，别用 Worker——数据库连接池本身就够并发了。

Q：要不要用 Node.js 内置的 test runner？
2026 年 Node.js 24 的 test runner 已经够用了，但生态不如 Vitest/Jest。我团队新项目用 Vitest，老项目用 Jest。内置 runner 适合 CLI 工具和小脚本。

Q：Bun 比 Node.js 快，为什么还不用？
Bun 确实快——启动快 3 倍，原生 TS 支持。但生产环境我要看生态兼容性、调试工具链、招人成本。Node.js 24 已经够用了，Bun 再成熟一年再说。

我的结论

Node.js 性能优化的第一原则：先 profiling 再优化，别凭感觉。clinic doctor 跑一遍，哪里是瓶颈一目了然。90% 的情况你会发现瓶颈不在你写的代码，在数据库查询、外部 API 调用、或者一个忘了改的同步操作。

第二原则：别阻塞事件循环。用 monitorEventLoopDelay 监控，超过 50ms 就查。同步代码是 Node.js 性能的第一杀手。

第三原则：用集群模式吃满多核。PM2 一行命令的事，别浪费 CPU。

这一系列五篇文章到这就结束了。从事件循环到底层 V8，从 NestJS 架构到框架选型，希望你看完之后再看自己的 Node.js 代码，能多看出几个以前注意不到的坑。
