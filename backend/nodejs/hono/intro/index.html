Hono 的路由与上下文机制

Hono 快的原因不是「代码少」，而是它不在请求时遍历路由表，而是先把路由表编译成匹配器。理解这套机制才能解释三件常见的怪事：为什么换一行 import 就有性能差异、为什么第一个请求明显更慢、为什么加一条正则路由会让框架直接抛异常。框架定位与生态取舍详见站内 Hono 总览篇，这篇只谈路由匹配、上下文对象和类型链路这三层机制。

四个 router 的分工：开销花在注册还是花在匹配

Hono 的 Router 是一个可替换接口，官方内置四个实现加一个调度器。它们的差别不是「谁更快」这种一维排序，而是把开销放在注册阶段还是匹配阶段——这个取舍取决于你的 app 实例能不能跨请求复用。

实现匹配策略注册期开销首个请求开销不支持的模式适用前提
RegExpRouter全部路由合成一个大正则，一次匹配同时得到 handler 链与参数低，只登记高，要构建匹配器，随路由数增长少数无法合并的路径组合，抛 UnsupportedPathErrorapp 能跨请求复用，路由数量可观
TrieRouter按斜杠切段走前缀树逐段下降低中，建树便宜无，覆盖全部模式兜底实现，路径模式复杂时用
LinearRouter按注册顺序线性比对，不做预编译极低无无每个请求都要重建 app 的环境
PatternRouter保存 pattern 列表逐个测试极低无无产物体积有硬上限
SmartRouter持有候选列表，首个请求时试探并锁定一个低一次构建加一次决策取决于候选集合默认选择

RegExpRouter 的一次匹配，与它拒绝的模式

流传最广的误解是「RegExpRouter 就是用正则一条条 test」。事实相反：逐条 test 才是最慢的做法，RegExpRouter 做的是把所有路径合并成一个正则，并在构建期算出每个捕获组对应哪条路由的哪个参数。请求进来只做一次匹配，拿到的是命中路由的 handler 链加参数映射，匹配耗时与路由条数基本脱钩。

合并是有代价的：当两条路径在同一位置产生无法共存的约束时，合并失败，RegExpRouter 会抛 UnsupportedPathError。默认配置下你看不到这个异常——SmartRouter 会吞掉它并回退 TrieRouter，于是你只是静默失去了预编译的收益，性能回归的原因藏在一条路径写法里。

路径写法匹配范围c.req.param() 推导结果容易忽略的点
/users/:id恰好一段，不跨斜杠键 id，类型 string数字 ID 也是字符串，要自己转换并校验
/users/:id?该段可缺省string | undefined下游忘了判空会把字面量 undefined 拼进 SQL 或 URL
/posts/:id{[0-9]+}单段且满足正则仍是 string正则只约束形状不改类型；这类写法是 RegExpRouter 合并失败的高发区
/files/*通配其后全部内容，可跨斜杠不产生命名参数要自己从 c.req.path 切出剩余路径，且必须做路径穿越校验
/:lang/posts/:id多个命名段两个键都被推导出来把 :lang 这种宽参数放在第一段，会和大量静态前缀路由竞争
由变量拼出的路径运行时行为不变退化为宽泛的 string参数名补全与拼错检查全部失效，除非给字面量加 as const

SmartRouter 的决定发生在第一个请求

SmartRouter 不是「智能地按路由特征选实现」，它的逻辑朴素得多：注册阶段把每次 add 转发给所有候选并记账，第一个请求到达时按顺序尝试构建各候选的匹配器，谁先构建成功就永久锁定谁，之后不再重新评估。

这个「延迟到首个请求」的设计带来三个工程后果。一是压测必须预热，首发请求包含匹配器构建，把它算进 P99 就是在测构建速度。二是路由写法问题不会在启动时暴露，CI 里跑得好好的项目上线后性能不如预期，根因可能只是某条路由触发了回退。三是在每个 isolate 都要重新执行顶层代码的边缘环境里，这份构建成本按 isolate 计，路由表越大越明显，这也是边缘部署时要控制路由规模的原因之一，运行时差异见站内 Hono 跨运行时部署篇。

import { Hono } from 'hono'
import { RegExpRouter } from 'hono/router/reg-exp-router'

// Bindings 对应 c.env，Variables 对应 c.set / c.var，
// 两者都声明出来，中间件与 handler 之间才有类型约束可依赖
type Env = {
  Bindings: { DB: D1Database; API_TOKEN: string }
  Variables: { requestId: string; userId?: string }
}

// 显式指定 router，跳过 SmartRouter 的静默回退：
// 路径模式不被支持时会直接抛 UnsupportedPathError 而不是降级
const app = new Hono<Env>({ router: new RegExpRouter() })

app.get('/health', (c) => c.json({ ok: true }))

// 启动自检：主动打一发请求，把匹配器构建和潜在的
// UnsupportedPathError 提前到进程启动阶段暴露，而不是等线上首个请求
export async function selfCheck() {
  const res = await app.fetch(new Request('http://localhost/health'))
  if (res.status !== 200) throw new Error('route self-check failed')
}

export default app

c.req：包装层、bodyCache 与真正的一次性

c.req 是 HonoRequest，一个对标准 Request 的包装层，原始对象在 c.req.raw。「Hono 的 body 只能读一次」这个说法把两层混为一谈了：一次性属于底层的 ReadableStream，而包装层带缓存。只要你始终通过 c.req 的方法读，第一次读取会缓存，换一种形式再读会从缓存重建。

读取方式是否进缓存之后还能换形式读吗典型事故
c.req.json()是可以，但 text 是重新序列化的结果先 json 再 text 去验签，字节与原文不同，签名必然不匹配
c.req.arrayBuffer()是可以，json 与 text 从原始字节重建没配 bodyLimit 时大 body 全量驻留内存
c.req.text()是可以对二进制体做字符串化会破坏字节
c.req.parseBody()是可以multipart 上传会把文件读进内存，大文件直接打爆
c.req.raw.json() / c.req.raw.body否，直接消费底层流不能，后续任何读取都报 body 已被使用中间件图省事用 raw，全站 POST 接口连带崩
c.req.raw.clone()克隆出独立流可以克隆出来的那份不被消费，缓冲会一直挂在内存里
sequenceDiagram participant C as 客户端 participant H as Hono dispatch participant M as 验签中间件 participant Q as HonoRequest bodyCache participant A as 业务 handler C->>H: 带 body 的 POST H->>M: 进入中间件 M->>Q: 读 arrayBuffer Q->>Q: 首次读取，消费底层流并缓存字节 Q-->>M: 原始字节 M->>A: await next A->>Q: 读 json Q->>Q: 命中缓存，从字节重建后解析 Q-->>A: 结构化对象 A-->>C: 返回响应 Note over M,A: 中间件若改用 c.req.raw 直接读
底层流被消费且不入缓存，handler 必报错 
import { createMiddleware } from 'hono/factory'

// Webhook 验签：必须拿原始字节，又不能挡住下游解析
const verifySignature = createMiddleware<Env>(async (c, next) => {
  // 走包装层读字节：结果进 bodyCache，下游还能再读
  const raw = await c.req.arrayBuffer()
  const given = c.req.header('x-signature') ?? ''

  const key = await crypto.subtle.importKey(
    'raw', new TextEncoder().encode(c.env.API_TOKEN),
    { name: 'HMAC', hash: 'SHA-256' }, false, ['sign'],
  )
  const mac = await crypto.subtle.sign('HMAC', key, raw)
  const expect = [...new Uint8Array(mac)]
    .map((b) => b.toString(16).padStart(2, '0')).join('')

  // 注意这里比的是对原始字节算出的摘要，
  // 换成先 json 再 text 拿到的字符串就会因重新序列化而失配
  if (expect !== given) return c.json({ error: 'bad signature' }, 401)
  await next()
})

app.post('/webhook', verifySignature, async (c) => {
  const payload = await c.req.json<{ event: string }>() // 命中缓存
  return c.json({ ok: payload.event })
})

c.var、c.env、c.executionCtx 的作用域与生命周期

这三者经常被当成「上下文里的三个字段」，实际上它们的所有者完全不同：一个属于本次请求，一个属于运行时，一个属于平台调度器。

成员谁提供生存期跨运行时差异常见误用
c.set / c.get / c.var你自己写入单次请求，请求结束即消失无差异当缓存用，把跨请求数据塞进去；类型没在 Variables 里声明导致取出来是 any
c.env运行时注入的绑定Workers 上按请求传入；Node 适配器下承载原生请求与响应对象不是 process.env，内容按平台完全不同把 c.env 存到模块级变量，在别的请求里复用
c.executionCtx平台调度器本次调用的生命周期控制句柄平台不提供时访问即抛错，Node 适配器下不可用公共中间件里直接调 waitUntil，换到 Node 就整站 500
c.resHono从被赋值到响应发出无差异响应已开始流式输出后还改它
c.req.raw运行时单次请求Node 适配器由原生请求转换而来拿它读 body，绕过缓存

要写能同时跑在 Node 与 Workers 上的中间件，对 c.executionCtx 必须做能力探测而不是假定存在，探测写法与边缘侧的后台任务边界见站内 Hono 跨运行时部署篇。

路径参数的类型推导从哪里开始退化

Hono 的路径参数类型不来自任何代码生成，而是从路径字符串的字面量类型里解析出来的。这决定了它的脆弱点：任何让字面量退化成 string 的写法都会让 c.req.param 失去键约束。常见退化来源有三类——把路径抽成普通变量、用数组循环批量注册路由、把路径拼接进模板字符串。想保留推导就给常量加 as const，或者干脆接受退化并在 handler 里显式校验。

另外注意：正则约束 :id{[0-9]+} 只影响匹配，不会把类型变成 number；可选参数会推成联合类型，忘了判空时 undefined 会一路流到查询层。

从 validator 到 hc：类型链路的断点在哪

RPC 不是运行时功能，而是一条从 zod schema 一直连到客户端调用处的类型链。链上任何一环断掉，客户端就只剩下宽泛的类型，而代码依然能跑——这正是它难排查的原因。

import { Hono } from 'hono'
import { hc } from 'hono/client'
import { zValidator } from '@hono/zod-validator'
import { z } from 'zod'

const createUser = z.object({
  name: z.string().min(2),
  email: z.string().email(),
})
// query 里一切都是字符串，要显式 coerce，否则 min/max 全部失效
const listQuery = z.object({
  page: z.coerce.number().int().min(1).default(1),
  size: z.coerce.number().int().max(100).default(20),
})

// 关键：链式注册。写成多条独立的 users.get(...) 语句，
// 类型不会累积回 users 的声明，客户端只能看到部分路由
const users = new Hono()
  .get('/', zValidator('query', listQuery), (c) => {
    const { page, size } = c.req.valid('query') // 已是 number
    return c.json({ page, size, items: [] as { id: string }[] })
  })
  .post('/', zValidator('json', createUser), (c) => {
    // valid 返回的是 zod 处理后的对象：默认会剥掉未声明的键；
    // await c.req.json() 拿到的是未过滤原文，两者不要混用
    const body = c.req.valid('json')
    return c.json({ id: 'u_1', ...body }, 201)
  })

const app = new Hono().route('/users', users)
export type AppType = typeof app
export default app

// 客户端：base 必须包含服务端的挂载前缀，否则类型对但请求 404
const client = hc<AppType>('https://api.example.com/')
const res = await client.users.$post({ json: { name: 'ab', email: 'a@b.c' } })
if (res.ok) {
  const created = await res.json() // 类型来自 c.json 的实参
  console.log(created.id)
}

客户端只补全出部分路径路由分散成多条独立语句，类型没累积回实例子路由内部保持链式，再用 app.route 挂载
c.req.valid('json') 得到 unknown 或报错validator 与 handler 不在同一次方法调用里，或 target 写错validator 必须作为同一次 .post(path, validator, handler) 的中间参数

最容易踩的坑

❌
最容易踩的坑
  • 压测不预热：首发请求包含匹配器构建与实现试探，测出来的是构建速度不是吞吐。
  • 以为 RegExpRouter 是逐条 test 正则，于是刻意减少路由数量去「优化」，方向全错。
  • 某条正则路由触发 UnsupportedPathError，SmartRouter 静默回退 TrieRouter，性能回归查不到原因——上线前用显式 router 做一次启动自检。
  • 在每请求重建 app 的环境里用默认 hono，构建成本每次都付一遍。
  • 中间件里用 c.req.raw.json() 读 body，绕过 bodyCache，下游 handler 全部报 body 已被使用。
  • 验签时先 c.req.json() 再取 text：那是重新序列化的字符串，不是原始字节，签名必然失配。
  • 把 c.env 当 process.env，本地 Node 下读到 undefined 还以为是配置没生效。
  • 把 c.env 或请求派生对象存进模块级变量，在边缘运行时上会出现跨请求串用甚至直接报错。
  • 公共中间件里无条件访问 c.executionCtx，代码切到 Node 适配器后整站 500。
  • 路径抽成变量后没加 as const，参数名拼错不再报错，运行时拿到 undefined。
  • :id? 可选参数忘了判空，字面量 undefined 被拼进查询条件。
  • 把 c.req.valid('json') 和 await c.req.json() 混用：前者已按 schema 剥掉未声明字段，后者是原文，写库的时候就出现多余字段。
  • query 参数不做 coerce：拿到的永远是字符串，数值范围校验形同虚设。
  • 客户端直接引服务端源码做 RPC，路由一多编辑器就卡死——改成引用编译出的声明文件。
