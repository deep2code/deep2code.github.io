Go gRPC 示例

🏷️ 服务端与云

概述：完整示例全景

这是一份我攒的完整 gRPC-Go 入门示例：server + client + proto 定义 + Nginx 反向代理。代码演示一元 RPC（unary RPC）和拦截器（interceptor）的用法。

gRPC 的核心是「一条 HTTP/2 长连接上多路复用多条 Stream」，这也是它比 REST 省连接、低延迟的根本原因：

flowchart LR subgraph Client 侧 C1[Stream 1 调用] C2[Stream 2 调用] C3[Stream N 调用] end subgraph 一条 HTTP/2 长连接 H2[TCP 多路复用 帧读写] end subgraph Server 侧 S1[Service A] S2[Service B] end C1 --> H2 C2 --> H2 C3 --> H2 H2 --> S1 H2 --> S2

gRPC 与 REST/JSON 对照，帮你判断什么场景该用 gRPC：

维度gRPCREST / JSON
传输协议HTTP/2 多路复用HTTP/1.1
消息格式Protobuf 二进制，强 schemaJSON 文本，弱类型
契约管理.proto 强约束，编译期生成 stubOpenAPI 文档，运行期弱校验
调用模式一元 / 服务端流 / 客户端流 / 双向流基本仅请求-响应
序列化性能快约 10x，体积小文本解析开销大、体积大
浏览器支持需 grpc-web / Connect 代理原生支持
典型场景内部微服务、高性能 RPC、流式对外开放 API、Web 前端直连

选型提示：服务之间高频、低延迟、需要流式 → gRPC；要直接给浏览器/第三方调用、对可读性要求高 → REST 或 Connect-RPC（gRPC 兼容又能直接暴露 HTTP/JSON 的折中方案）。

proto 定义与代码生成

先看工具链：.proto 经 protoc 生成 pb.go，再分别给出服务端 stub 与客户端 stub：

flowchart LR P[.proto 文件] --> PC[protoc 编译器] PC --> GO[xxx.pb.go stub 代码] GO --> SVR[服务端 Server stub] GO --> CLI[客户端 Client stub] SVR --> IMPL[业务实现]

proto 文件定义一个 Math 服务，做加法：

syntax = "proto3";

option go_package = "./;common";

service Math {
    rpc Add(AddReq) returns (AddRsp) {}
}

message AddReq {
    int64 left = 1;
    int64 right = 2;
}

message AddRsp {
    int64 result = 1;
}

生成脚本（2026 推荐 buf）：

#!/bin/bash
# --go-grpc_out 启用 protoc-gen-go-grpc 生成 service 代码
protoc --go_out=. --go-grpc_out=. *.proto

# 现代做法：用 buf 统一管理（见 gRPC 主页）
# buf generate

服务端 server

服务端监听端口、注册 MathServer、挂一元拦截器，从 ctx 里取 peer / metadata：

package main

import (
    "context"
    "flag"
    "fmt"
    "log"
    "net"

    "google.golang.org/grpc"
    "google.golang.org/grpc/metadata"
    "google.golang.org/grpc/peer"

    com "xxx.site/myself/grpc-common"
)

var (
    port = flag.Int("port", 8411, "默认端口")
)

// 一元拦截器：鉴权、限流、日志的横切扩展点
func middleware(ctx context.Context, req any,
    info *grpc.UnaryServerInfo, handler grpc.UnaryHandler) (resp any, err error) {
    log.Printf("method=%s req=%v", info.FullMethod, req)
    resp, err = handler(ctx, req)
    log.Printf("resp=%v err=%v", resp, err)
    return
}

type MathServer struct {
    com.UnimplementedMathServer
}

// 上下文信息通过 ctx 的 valueCtx 传递，由不同包解析：peer / metadata
func (ms *MathServer) Add(ctx context.Context, req *com.AddReq) (*com.AddRsp, error) {
    if client, ok := peer.FromContext(ctx); ok {
        log.Printf("client:%v", client)
    }
    if md, ok := metadata.FromIncomingContext(ctx); ok {
        log.Printf("md:%v", md)
    }
    return &com.AddRsp{Result: req.Left + req.Right}, nil
}

func main() {
    flag.Parse()
    // tcp 监听 IPv4/IPv6 双栈；只 IPv4 用 tcp4，强制 IPv6 用 tcp6
    l, err := net.Listen("tcp", fmt.Sprintf(":%d", *port))
    if err != nil {
        log.Fatalf("fail listen: %v", err)
    }
    s := grpc.NewServer(grpc.UnaryInterceptor(middleware))
    com.RegisterMathServer(s, &MathServer{})
    log.Printf("listen: %v", l.Addr())
    if err := s.Serve(l); err != nil {
        log.Fatalf("fail serve: %v", err)
    }
}

2026 提示：多拦截器用 grpc.ChainUnaryInterceptor 链式组合；链路追踪交给 OpenTelemetry 的 gRPC 插桩自动完成，替代手写日志中间件。

客户端 client

客户端用 grpc.NewClient（v1.63 起推荐，grpc.Dial 已废弃），挂客户端拦截器，发起一元调用：

package main

import (
    "context"
    "flag"
    "log"
    "time"

    "google.golang.org/grpc"
    "google.golang.org/grpc/credentials/insecure"

    com "xxx.site/myself/grpc-common"
)

var addr = flag.String("addr", "127.0.0.1:8411", "服务端地址")

func middleware(ctx context.Context, method string,
    req, reply any, c *grpc.ClientConn, invoker grpc.UnaryInvoker,
    opts ...grpc.CallOption) error {
    err := invoker(ctx, method, req, reply, c, opts...)
    log.Printf("method=%s err=%v", method, err)
    return err
}

func main() {
    flag.Parse()
    // 推荐 grpc.NewClient：不再立即阻塞建连，连接管理交给 ConnectParams
    conn, err := grpc.NewClient(*addr,
        grpc.WithTransportCredentials(insecure.NewCredentials()), // 生产换 TLS
        grpc.WithUnaryInterceptor(middleware),
    )
    if err != nil {
        log.Fatalf("dial: %v", err)
    }
    defer conn.Close()

    client := com.NewMathClient(conn)
    req := com.AddReq{Left: 10, Right: 20}
    ctx, cancel := context.WithTimeout(context.Background(), 3*time.Second)
    defer cancel()

    resp, err := client.Add(ctx, &req)
    if err != nil {
        log.Fatalf("add fail: %v", err)
    }
    log.Printf("resp: %v", resp.Result)
}

为什么改用 grpc.NewClient：grpc.Dial（及 WithTimeout 旧选项）自 v1.63 起标记废弃。NewClient 创建时不立即阻塞建连，超时与连接管理交给 ConnectParams / context，语义更清晰。

Nginx 反向代理

gRPC 走 HTTP/2，Nginx 1.13.10+ 原生支持 grpc_pass 反代；TLS 场景用 grpcs://：

server {
    listen 443 ssl http2;
    server_name grpc.xxx.site;

    ssl_protocols TLSv1.2 TLSv1.3;  # TLSv1/1.1 已被 RFC 8996 弃用，2026 不再开启
    ssl_certificate grpc.xxx.site.pem;
    ssl_certificate_key grpc.xxx.site.key;

    location / {
        # grpc_pass localhost:9000; 等价于 grpc://127.0.0.1:8411
        # gRPC over TLS 时带 grpcs:
        grpc_pass grpcs://[xxx]:8411;
        client_max_body_size 200M;
    }
}

2026 更新：Go 1.26 与工具链

现代 gRPC Go 项目建议用 buf 管理 proto（lint + breaking + 生成），Connect-RPC 可直接暴露 HTTP/JSON 端点。gRPC-Go v1.81 起要求 Go 1.25+，Go 1.26.0 已于 2026 年 2 月发布，与本示例直接相关的变化：

  • new(expr)：内置 new 支持表达式参数（p := new(42)），简化 Protobuf 可选字段指针初始化。
  • errors.AsType：泛型化错误断言 errors.AsType[*AppError](err)，编译期类型安全、无反射，替代 errors.As。
  • Green Tea GC 默认启用：8KiB span 批量标记、并行扫描，小对象 GC 开销降 10%~40%，GOEXPERIMENT=nogreenteagc 可回退（1.27 移除）。
  • 后量子加密默认化：新增 crypto/hpke、crypto/mlkem，TLS 默认 X25519MLKEM768 混合密钥交换。

底层实现：连接、序列化与流

ClientConn 管理到后端的连接，内部含 resolver / balancer / transport / 连接状态机。一个 TCP 连接上多路复用多个 Stream，控制帧与数据帧分离处理。连接失败指数退避重连（1s→2s→4s…最大 120s）。

编解码走 Codec 接口（Marshal/Unmarshal/Name），默认 protoCodec。gRPC 消息帧是 Length-Prefixed：1 字节压缩标志 + 4 字节大端长度 + N 字节消息体。

我自己的性能优化经验：大消息 gzip 减 70%+，小消息不压缩，用 proto.Marshal 而非 json，复用 message 对象。

流式 RPC 里服务端循环 SendMsg 每个响应一个 DATA 帧，结束发 trailers + END_STREAM；客户端 Recv 阻塞等下一条，收到 trailers 返回 io.EOF。背压由 HTTP/2 流控窗口实现：窗口满 SendMsg 阻塞，Recv 消费后发 WINDOW_UPDATE。

四种调用模式速查：

调用模式请求 : 响应典型场景
一元 Unary1 : 1普通查询、增删改（本文示例）
服务端流式1 : N日志推送、配置下发、订阅
客户端流式N : 1批量上传、流式写入
双向流式 BidiN : N实时聊天、游戏同步、远程终端

双向流式（Bidi）的完整交互时序：

sequenceDiagram participant C as Client participant S as Server C->>S: HEADERS 帧 创建流 C->>S: DATA 帧 请求消息 S->>S: handler 循环 SendMsg S-->>C: 响应 DATA 帧 1 S-->>C: 响应 DATA 帧 2 C->>C: Recv 阻塞等待下一条 S-->>C: trailers 状态码 加 END_STREAM Note over C,S: HTTP/2 窗口满时 SendMsg 阻塞 Recv 消费后 WINDOW_UPDATE 形成背压

错误处理与状态码

gRPC 错误基于 HTTP/2 trailers + Status proto（Code / Message / Details）。客户端用 status.Convert(err) 还原码与详情：

// 创建带详情的错误
func NotFoundError(id string) error {
    st := status.Newf(codes.NotFound, "user %s not found", id)
    detail := &errdetails.ResourceInfo{ResourceType: "user", ResourceName: id}
    st, _ = st.WithDetails(detail)
    return st.Err()
}

// 客户端解析
err := client.GetUser(ctx, req)
if err != nil {
    st := status.Convert(err)
    fmt.Printf("code=%d message=%s\n", st.Code(), st.Message())
}

可重试码与不可重试码要分清：

类别状态码策略
可重试Unavailable(14)、DeadlineExceeded(4)、ResourceExhausted(8)退避重试（幂等操作）
不可重试InvalidArgument(3)、NotFound(5)、PermissionDenied(7)直接失败，重试无意义

常见陷阱

  • 每次请求新建连接：全局复用 ClientConn，HTTP/2 多路复用。
  • 忽略 context 超时：所有 RPC 都设 context.WithTimeout。
  • 大消息 OOM：调 MaxRecvMsgSize，默认 4MB 可能不够。
  • 流式不关闭：客户端必须 Recv 到 io.EOF，否则连接泄漏。
  • 错误码用错：用 status.Errorf 而非 fmt.Errorf，客户端才能解析码。
  • 拦截器顺序：ChainUnaryInterceptor 按序执行，日志放最外层。
  • 字段编号变更：编号一旦使用不能改，否则破坏兼容性。

FAQ

Q1：grpc.Dial 还能用吗？
v1.63 起标记废弃。新项目用 grpc.NewClient，旧代码仍可跑但建议迁移。

Q2：服务端怎么拿到客户端 IP？
peer.FromContext(ctx) 拿 RemoteAddr；metadata 用 metadata.FromIncomingContext。

Q3：Nginx 反代 gRPC 要注意什么？
必须 HTTP/2 + grpc_pass，TLS 用 grpcs://；调大 client_max_body_size 适配大消息。

我的上手路径

这份示例覆盖了 gRPC-Go 的最小闭环：proto 定义 → protoc/buf 生成 → 服务端注册 + 拦截器 → 客户端 NewClient + 超时调用 → Nginx grpc_pass 反代。

底层是 HTTP/2 多路复用 + Protobuf Length-Prefixed 帧；错误走标准状态码，流式靠 HTTP/2 流控背压。我 2026 年的团队约定：工具链切 buf，连接用 NewClient，每个调用带 deadline。
