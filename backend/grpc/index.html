gRPC 入门：从你遇到的问题出发

🏷️ gRPC 入门

你要做个微服务之间的调用，用 HTTP REST 太啰嗦了，数据量大的时候性能也不好。你想搞个高性能的 RPC 框架。

这篇不讲理论，就讲你真的会遇到的问题，以及 gRPC 怎么帮你解决。

场景一：微服务之间互相调用，写一堆 HTTP 接口太麻烦

你遇到的问题

你做了个微服务架构，用户服务要调订单服务，订单服务要调商品服务。每个服务之间互相调 HTTP 接口，要写一堆 URL、参数、序列化/反序列化，代码重复，还容易出错。

gRPC 怎么解决？你只要定义一个 .proto 文件，写清楚有什么接口、参数是什么，gRPC 自动帮你生成客户端和服务端代码。你像调本地函数一样调远程服务，不用管 HTTP 那些细节。

// user.proto：定义接口
service UserService {
  rpc GetUser (GetUserRequest) returns (User);
}

message GetUserRequest {
  int64 user_id = 1;
}

message User {
  int64 id = 1;
  string name = 2;
  string email = 3;
}
// 服务端，就像写普通函数一样
func (s *Server) GetUser(ctx context.Context, req *pb.GetUserRequest) (*pb.User, error) {
    // 查数据库
    return &pb.User{Id: req.UserId, Name: "张三"}, nil
}

// 客户端，像调本地函数一样
user, err := client.GetUser(ctx, &pb.GetUserRequest{UserId: 123})

现在你不用写 HTTP 接口、不用写 JSON 序列化，直接调函数就行。代码简洁多了。

场景二：接口性能不够，数据量大的时候慢

你遇到的问题

你用 HTTP REST 传 JSON，每次请求都要做 JSON 序列化/反序列化，还要带一大堆 HTTP 头。数据量大的时候，光序列化就占了一半时间。

gRPC 怎么解决？用 Protocol Buffers 序列化，比 JSON 小 3 到 10 倍，序列化速度快 5 倍以上。而且用 HTTP/2，多路复用，连接不用每次都建。性能比 HTTP REST 高很多。

对比HTTP REST + JSONgRPC
数据格式JSON（文本，大）Protobuf（二进制，小）
序列化速度慢快 5-10 倍
HTTP 版本HTTP/1.1HTTP/2
代码生成手动写自动生成
浏览器支持原生支持需要 grpc-web

场景三：你的服务有 Go 写的，有 Java 写的，互相调用

你遇到的问题

你的用户服务是 Go 写的，订单服务是 Java 写的，它们之间要互相调用。你要定义一套接口规范，两边各自实现，很容易不一致，一个改了另一个没跟上，就出问题了。

gRPC 怎么解决？你只要定义一个 .proto 文件，Go 和 Java 都用这个文件生成代码，接口定义永远是一致的。一个改了 proto，两边重新生成代码就行，不会不一致。

新手最容易踩的坑
  • 浏览器不能直接调 gRPC：gRPC 用 HTTP/2，浏览器不支持，要做 gRPC-Web 或者用网关转一下。
  • proto 文件要统一管理：不要一个服务一份 proto，放一个公共仓库里，大家共用。
  • 不要随便改字段编号：proto 里的字段编号改了，旧版本就解析不了了，新增字段可以，改旧字段不行。
  • 错误处理要规范：gRPC 有自己的错误码，不要用 HTTP 的那一套。
