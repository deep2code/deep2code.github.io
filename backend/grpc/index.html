gRPC 深度原理：HTTP/2 + Protobuf

🏷️ gRPC

gRPC 比 REST 快很多，是因为它用 HTTP/2 多路复用和 Protobuf 二进制序列化。这篇讲透 gRPC 原理。

核心原理1：Protobuf 二进制序列化

JSON 是文本格式，体积大解析慢。Protobuf 是二进制，体积小一半，解析快 5 倍。

flowchart LR A[JSON 文本] --> B["{name:'java',age:10}"] B --> C[体积大 解析慢] D[Protobuf 二进制] --> E[二进制流 字段编号] E --> F[体积小 解析快]

JSON vs Protobuf 对比

对比项 JSON Protobuf
格式 文本 二进制
体积 大 小 1/3 ~ 1/10
解析速度 慢 快 5 ~ 10 倍
可读性 好 差，需要 .proto 文件
Schema 无 强类型，.proto 定义

核心原理2：HTTP/2 多路复用原理

HTTP/1.1 一个连接一个请求，HTTP/2 一个连接可以同时跑多个请求，不用开新连接。

flowchart TD A[HTTP/1.1] --> B[连接1 请求1] A --> C[连接2 请求2] A --> D[连接3 请求3] E[HTTP/2] --> F[一个连接] F --> G[流1 请求1] F --> H[流2 请求2] F --> I[流3 请求3]

HTTP/1.1 vs HTTP/2

特性 HTTP/1.1 HTTP/2
连接 一个连接一个请求 一个连接多个流
队头阻塞 有 流级多路复用解决
二进制帧 文本 二进制
服务端推送 不支持 支持

核心原理3：四种调用模式

gRPC 不止普通的请求响应，还有四种模式，适合不同场景。

flowchart TD A[gRPC 四种模式] --> B[Unary 普通调用] A --> C[服务端流式] A --> D[客户端流式] A --> E[双向流式] B --> B1[一请求一响应] C --> C1[一请求多响应] D --> D1[多请求一响应] E --> E1[多请求多响应]

gRPC 四种调用模式

模式 请求响应 适用场景
Unary 一请求一响应 普通接口
服务端流式 一请求多响应 实时推送、日志流
客户端流式 多请求一响应 批量上传
双向流式 多请求多响应 聊天、实时通信

新手最容易踩的坑

❌
避坑指南
  • gRPC 调试不如 REST 方便，用 grpcurl 工具命令行调试
  • Protobuf 字段编号不要改，新增字段加新编号，兼容旧版本
  • 服务端流式长连接要注意超时和重连
  • 浏览器不能直接调 gRPC，要用 gRPC-Web 转一层
