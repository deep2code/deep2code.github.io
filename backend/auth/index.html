认证与授权的协议全景：从 Cookie Session 到 Token 与联邦

🏷️ 安全

关于认证方案的讨论几乎总是被压缩成一句「用 Session 还是用 JWT」，然后迅速跑偏成立场之争。这个问法本身就是错的：它把两个正交的维度混成了一个。真正决定方案的是认证状态放在哪里，以及信任边界有多大。这篇不讲攻防参数，只把从 Cookie 会话到自包含令牌、再到跨组织联邦的各种机制放进同一个坐标系，讲清每一步演进是被什么需求逼出来的、各自付出了什么代价。密码哈希参数、令牌存放位置的攻防、算法混淆与越权的机理，站内安全专题已经写透，本文只在需要的地方指路。

先建立坐标系：状态存在哪，信任边界到哪

第一个维度是认证状态的归属。服务端有状态意味着客户端手里只有一个不可猜测的引用（会话 ID），全部真实信息在服务端；客户端自包含意味着身份信息本身被签名后交给客户端携带，服务端不需要保存任何东西就能验证真伪。第二个维度是信任边界：进程内的单体应用、同一组织内互相信任程度有限的多个服务、以及完全跨组织（用户的身份由别人家的系统认证）。这两个维度交叉出四个象限，每个象限都有明确的主流方案，跨象限硬搬才是大部分事故的来源。

把方案摆进象限之后有个直接的推论：「Token 比 Session 先进」是错的。它们不在同一条进化链上，而是在不同象限里各自最优。真正会随时间演进的是信任边界——当产品从一个 Web 应用长成 Web 加 App 加开放 API 加企业客户 SSO，你会在坐标系里同时占住多个象限，此时需要的是清晰的分层，而不是把所有场景塞进一种机制。

Cookie + Session：它至今仍是大量场景的最优解

机制本身很朴素：登录成功后服务端生成一个高熵随机串作为会话 ID，把用户身份写进服务端存储，再通过 Set-Cookie 把这个 ID 交给浏览器；后续请求浏览器自动携带，服务端用 ID 反查状态。它的三个优势都来自「状态在我手里」：可即时吊销（删掉记录，下一个请求就是未登录）、凭证本身不含信息（拿到 ID 也读不出任何东西）、浏览器自动管理（前端不需要写任何存取逻辑，配上 HttpOnly 后 JS 根本读不到，XSS 想偷也偷不走值）。

// 服务端会话：Cookie 里只放不可猜的 ID，真实状态在 Redis
sid := randomToken(32) // 32 字节 CSPRNG，base64url 后 43 字符；不要用 UUIDv4 当会话 ID
// 登录成功后必须换新 ID（防会话固定），并把旧 ID 从存储里删掉
rdb.Set(ctx, "sess:"+sid, payload, 30*time.Minute) // 空闲超时由 Redis TTL 兜底
http.SetCookie(w, &http.Cookie{
    Name:     "sid",
    Value:    sid,
    Path:     "/",
    Domain:   "",                      // 留空 = 仅当前主机，不要随手写成父域
    HttpOnly: true,                    // 关键：JS 读不到
    Secure:   true,                    // 只在 HTTPS 上发送
    SameSite: http.SameSiteLaxMode,     // 三值语义与取舍见站内 CSRF 篇
    MaxAge:   0,                       // 0 表示会话 Cookie，关掉浏览器即失效
})
// 每次请求命中时刷新 TTL 实现滑动过期，但要另设一个绝对上限
// 比如 idle 30 分钟 + absolute 12 小时，防止长期活跃会话永不过期

什么时候 Session 就够了

同时满足这几条就不要引入令牌体系：只有浏览器客户端；前后端同域部署或能通过反向代理归一到同域；需要随时封禁账号或强制下线；团队规模不大、不想自己维护密钥分发与轮换。这套组合用框架自带能力半天就能上线，而自包含令牌方案的隐性成本（刷新并发、密钥轮换、登出其他设备）往往要在上线三个月后才开始付。

为什么会出现 Token：它解决的是另一组问题

Cookie 会话的前提是「客户端是浏览器，且浏览器愿意自动带 Cookie」。三件事打破了这个前提。一是移动端与前后端分离：原生 App 没有 Cookie 的天然承载，SPA 常常和 API 不同域，跨站带 Cookie 需要放宽 SameSite 并处理预检请求，配置复杂度迅速超过收益。二是微服务的无状态校验：每个服务为了知道「你是谁」都去查一次会话存储，会让会话存储变成全站最热的单点。三是跨组织：用户的身份由别人的系统认证，对方只能给你一份签名断言，不可能给你一个能查的会话 ID。

维度 Cookie + 服务端会话 自包含令牌（JWS 形态的 JWT）
即时吊销 删记录立即生效 做不到；要么等过期，要么维护黑名单（等于放弃无状态）
横向扩展 需共享存储，存储本身要做高可用 任意节点本地验签，零网络调用
跨域与跨端 受同源与 SameSite 约束，App 端不自然 放请求头即可，Web、App、小程序一套逻辑
每请求开销 一次存储读取，0.2-5 ms HS256 验签约几微秒，RS256 约几十微秒
凭证体积 会话 ID 约 40-60 字节 典型 500-1500 字节，每个请求都要重传
权限变更生效 立即 最长滞后一个令牌有效期
实现与运维复杂度 低，框架内置 中高：密钥分发、轮换、刷新并发、时钟偏移都要处理
CSRF 需要 SameSite 或令牌校验配合 放请求头时天然免疫；一旦放回 Cookie 就不免疫

看这张表的正确方式是找你真正在意的那一行。如果业务要求封禁一秒内生效，第一行就已经判定了方案，后面几行的优势都换不回来。令牌的结构、验签必校验项与密钥轮换见站内 JWT 的结构与验签机制，令牌该放哪里、放错会被什么攻击拿走见站内 越权与鉴权安全。

服务间的用户身份传递：可信请求头还是透传令牌

网关校验完令牌之后，下游怎么知道当前用户是谁？两种做法，区别不在性能而在信任模型。可信请求头是「网络边界可信」假设下的产物：网关把 X-Auth-User-Id 之类的头注入进去，下游读头即用。这套方案有一个绝对前提——下游必须无法被外部直连，否则任何人加一个请求头就完成了身份伪造，而且这类越权在日志里看起来和正常请求一模一样。透传令牌则让每个服务各自验签，代价是每跳都要验签、每个服务都要接入密钥分发。

sequenceDiagram participant C as 客户端 participant G as 网关 participant A as 认证服务 participant S1 as 订单服务 participant S2 as 库存服务 C->>G: 请求携带访问令牌 G->>A: 首次拉取公钥集合 A-->>G: 返回公钥与元数据 本地缓存 G->>G: 本地验签 校验有效期与受众 G->>S1: 转发请求 注入身份头 并清空外部同名头 S1->>S2: 服务间调用 用服务自身身份而非用户令牌 S2-->>S1: 返回数据 S1-->>G: 返回业务响应 G-->>C: 返回业务响应 Note over G,S2: 身份头方案的死穴是下游被绕过网关直连
网络策略必须保证网关是唯一入口 
location /api/ {
    # 1) 先把客户端可能伪造的所有身份头清空：置为空串等于不转发
    proxy_set_header X-Auth-User-Id   "";
    proxy_set_header X-Auth-Tenant-Id "";
    proxy_set_header X-Auth-Scope     "";

    # 2) 再写入网关自己校验得出的值（变量由鉴权子请求或 auth_request 产出）
    proxy_set_header X-Auth-User-Id   $auth_user_id;
    proxy_set_header X-Auth-Tenant-Id $auth_tenant_id;
    proxy_set_header X-Auth-Scope     $auth_scope;

    # 3) 原始令牌是否继续透传，取决于下游要不要自己验签
    proxy_set_header Authorization    $http_authorization;

    proxy_pass http://upstream_api;
}
# 排查命令：从外部直接打下游，确认身份头被忽略
#   curl -s -H 'X-Auth-User-Id: 1' http://10.0.0.11:8080/api/me
# 返回 401 才算正确；返回用户 1 的数据说明下游在无条件信任请求头
维度 网关注入可信请求头 透传原始令牌各自验签
下游接入成本 极低，读头即用，非 JVM 非 Go 的小语言服务也能接 每个服务都要接验签库、缓存公钥、处理时钟偏移
伪造风险 下游一旦可被直连即可伪造任意用户 无签名私钥无法伪造
过期与撤销判断 仅网关判断，下游不知道令牌何时失效 每个下游独立判断，长链路更一致
链路中的身份延续 服务再调服务时容易丢失，需要显式约定继续传 令牌可继续透传，但要注意受众校验
每跳开销 下游零验签成本 每跳一次签名校验，长链路上会累积
适用 内网封闭、网关是唯一入口的中小规模系统 零信任、下游可能被其他团队直接调用

服务与服务之间的认证：这里没有用户

上一节讲的是「把用户身份带下去」，这一节讲的是完全不同的一件事：调用方本身就是一个服务，没有用户参与。定时任务去拉数据、订单服务调库存服务扣减、数据同步作业写入数仓，这些调用需要的是服务自己的身份。最常见的错误是复用某个用户的长期令牌，或者写一个永不轮换的静态 API Key 塞进配置中心，后者的后果是密钥泄露后无从追溯也无法快速收回。

机制 身份载体 轮换方式 撤销手段 适用场景
静态 API Key 共享密钥字符串 手工，现实中往往从不轮换 改配置并重启双方 仅遗留系统；新建系统不要选
mTLS 客户端证书，双向校验 证书短有效期自动续签（小时到天级） 吊销列表或干脆靠短有效期 服务网格、跨集群、合规要求强的链路
OAuth2 客户端凭证模式 代表服务主体的访问令牌 令牌几分钟自动换一次 内省端点或短有效期自然失效 已有统一授权服务器，需要 scope 粒度
SPIFFE 与 SVID 按工作负载身份自动签发的证书或 JWT 自动，分钟级 短有效期，不依赖吊销列表 多集群多云需要统一身份命名空间 
# 客户端凭证模式：换一个代表「订单服务」自己的令牌，与任何用户无关
curl -s -X POST https://idp.internal/oauth2/token \
  -u "svc-order:$CLIENT_SECRET" \
  -d 'grant_type=client_credentials' \
  -d 'scope=inventory.read inventory.write' | jq '{expires_in, scope}'
# 典型输出：{"expires_in": 600, "scope": "inventory.read inventory.write"}
# 判读要点：
#   expires_in 一般 300-3600 秒，客户端必须缓存令牌并在到期前 30-60 秒提前续取，
#   否则每个业务请求都去换一次令牌，授权服务器会先被自己人打挂。

# mTLS 自查：确认对端确实校验了客户端证书
openssl s_client -connect inventory.internal:8443 -brief </dev/null 2>&1 | head -20
# 输出里出现 requested client certificate 之类的提示才说明对端开了双向校验；
# 不带证书还能拿到 200，说明 mTLS 只是配了没生效。

联邦身份：SAML 与 OIDC 各自的位置

跨组织场景下，认证发生在别人家。用户在自己公司的身份提供方登录，你的系统只收到一份签名过的断言。这个模型有两套主流协议：SAML 2.0 是 XML 时代的企业标准，OIDC 是构建在 OAuth 2.0 之上的现代身份层。技术上 OIDC 全面更易用，但SAML 不会消失——企业客户的存量身份系统就是 SAML，采购清单常把它列为硬性要求。

维度 SAML 2.0 OIDC
断言格式 XML，需要 XML 数字签名校验 JSON，身份断言就是一个 JWT
传输方式 浏览器 POST 表单或重定向绑定 HTTP 重定向加后端 JSON 端点调用
移动端与单页应用 难用，基本要靠 Web 视图兜 原生支持，配合 PKCE 即可
元数据发现 metadata XML 文件，常靠人工交换 .well-known/openid-configuration 自动发现
实现难点 XML 签名校验实现复杂，历史上有签名包装类漏洞 参数校验容易遗漏，但链路直观
该怎么选 为兼容企业存量而必须支持 新系统的默认选择

工程上的建议是内部只认一种协议：把 OIDC 作为系统内部的统一身份语言，SAML 用一个独立的适配服务承接，转换成内部 OIDC 语义后再进业务。不要让 XML 断言解析和业务代码搅在一起，否则每接一家企业客户都要改业务逻辑。OIDC 的端点、令牌类型与接入清单见站内 OAuth 2.0 与 OIDC 的协议细节。

反模式，以及安全细节该去哪查

反模式 会出什么事 正确做法
为了「无状态」放弃可吊销性，业务却需要即时封禁 违规账号封了还能继续用到令牌过期；最后被迫加黑名单，无状态白追求一场 先确认生效延迟容忍度；容忍度为零就承认需要服务端状态
把大量业务数据塞进令牌 令牌膨胀到几 KB，每请求重传，网关内存和带宽双涨；数据还会过期失真 令牌只放身份与授权必需的最小集合，业务数据现查
Session 与 Token 两套逻辑并存且互不知情 登出只清了一套，用户以为退出了其实还在线；权限判断出现两个真相源 选定一个真相源，另一套只做适配层
服务间直接拿用户令牌互调 审计分不清调用发起方；下游需要更大权限时迫使用户令牌携带过多授权 服务用自己的身份，需要用户上下文时单独传递并在下游校验
下游服务无条件信任身份请求头，同时又能被外部访问 加一个请求头就是任意用户，越权且无痕 下游只监听内网并显式丢弃外部身份头，或改为各自验签
用 OAuth2 当认证协议而不引入 OIDC 把访问令牌当身份凭证，拿到别处签发的令牌也能登录 登录场景用 OIDC 的身份令牌，并校验签发方与受众

避坑清单
  • 登录成功后不重新生成会话 ID：攻击者事先把一个已知 ID 种进受害者浏览器，登录后这个 ID 就成了有效会话。
  • 只设滑动过期不设绝对上限：被盗会话只要有脚本定时发请求就永不失效。建议 idle 30 分钟加 absolute 12 小时双限制。
  • Cookie 的 Domain 随手写成父域：一个子域的 XSS 或一个被接管的子域就能拿到全站会话。不需要跨子域就留空。
  • 改密码只改了密码表，没有失效该用户的所有会话与刷新令牌：旧设备继续在线，这是安全测试必查项。
  • 用 UUIDv4 或递增 ID 当会话 ID：熵不足且可能可预测，会话 ID 必须来自密码学安全随机源，至少 128 位熵。
  • 会话存储单点：Redis 单实例挂掉等于全站集体登出。要做高可用，并给读取设超时与降级策略。
  • 网关验签通过就完全不管受众：一个下游服务签发或接收的令牌被拿去调用另一个服务仍然有效，形成跨服务重放。
  • 下游服务既信任身份请求头又开放了外网端口或被 Service 直接暴露：等于把身份校验整条拆掉。
  • 把服务的静态 API Key 写进代码仓库或镜像：泄露后无法定位使用方，只能全量替换并停机。
  • 令牌有效期设成几天来「减少刷新请求」：把无法吊销的窗口放大到几天，一次泄露的影响面数量级上升。
  • SAML 对接时自己手写 XML 断言校验：XML 签名的边界情况极多，必须用成熟库并开启严格模式。
  • 多端上线后仍沿用同域 Cookie 方案，靠前端手工把 Cookie 值塞进请求头：既失去 HttpOnly 保护，又没有令牌体系的好处，两头落空。
