JWT 认证深度原理：Token 怎么工作的？

🏷️ 认证

JWT 现在前后端分离都用，为什么不用 Session？JWT 结构是什么？为什么能无状态？这篇讲透认证底层原理。

核心原理1：Session vs JWT

Session 是服务端存用户状态，JWT 是把状态存在客户端，服务端不用存，天生分布式友好。

flowchart LR A[Session] --> B[服务端存 Session] B --> C[Cookie 存 SessionID] A2[JWT] --> D[客户端存 Token] D --> E[服务端验签 不存状态]
对比 Session JWT
状态存储 服务端存 客户端存
扩展性 差，多服务要共享 Session 好，服务端无状态
大小 小，只有 ID 大，整个 JSON 都在 Token 里
过期 服务端控制 服务端不好主动过期
适用 单体应用 前后端分离/微服务

核心原理2：JWT 结构原理

JWT 是三段：Header.Payload.Signature，前两段 Base64 编码，第三段用密钥签名，防篡改。

flowchart TD A[JWT] --> B[Header 头部] A --> C[Payload 负载] A --> D[Signature 签名] B --> B1[算法 HS256] C --> C1[用户ID 过期时间] D --> D1[用密钥签名前两段]
部分 内容 说明
Header 算法类型 Base64 编码
Payload 用户信息、过期时间 Base64 编码，不是加密，不能存敏感信息
Signature 签名 防篡改，服务端用密钥验证

核心原理3：OAuth2.0 原理

第三方登录用的就是 OAuth2.0，不用把密码给第三方，第三方拿到授权码，换 Token，访问用户信息。

flowchart LR A[用户] --> B[第三方应用] B --> C[跳转 GitHub 授权页] C --> D[用户同意授权] D --> E[回调带授权码] E --> F[后端用授权码换 Token] F --> G[用 Token 拿用户信息]
角色 作用
资源所有者 用户，同意授权
客户端 第三方应用
授权服务器 GitHub/Google 发 Token
资源服务器 存用户信息

新手最容易踩的坑

❌
避坑指南
  • JWT 不要存敏感信息，Payload 是 Base64 编码不是加密，谁都能解出来
  • JWT 发出去不好主动过期，要存黑名单或者用短有效期 + Refresh Token
  • 密钥一定要保管好，密钥泄漏了别人就能伪造 Token
  • 不要把 JWT 存在 localStorage，容易被 XSS 偷，存在 HttpOnly Cookie 里更安全
