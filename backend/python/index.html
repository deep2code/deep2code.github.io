Python 做后端的适用边界与运行时约束

🏷️ Python

Python 在后端的位置常被两种极端说法带偏：一边说「有 GIL 所以做不了并发」，一边说「上了 asyncio 就能抗万级 QPS」。两句都不准确。这篇只做一件事——把 Python 的运行时约束讲到能用于决策的精度，然后据此回答两个问题：这个需求该不该用 Python 写，上线该用什么部署形态。

GIL 锁住的是字节码，不是并发

准确表述只有一句：同一个 CPython 进程内，同一时刻只有一个线程在执行 Python 字节码。两个限定词都重要。「字节码」意味着线程一旦离开解释器——进入 IO 系统调用，或进入主动释放 GIL 的 C 代码——GIL 就被放开；「同一进程」意味着进程之间根本不存在 GIL 竞争。

所以「Python 不能并发」是错的。IO 密集场景里多线程是真并行：线程 A 卡在 recv 上的时候线程 B 正在跑，吞吐随线程数上升。只有纯 Python 的 CPU 计算会被串行化，而且因为多了 GIL 争抢和线程切换，4 线程跑 CPU 任务通常比单线程更慢，常见劣化 10%~50%，核越多越明显。

切换时机也值得知道：sys.getswitchinterval() 默认 5 毫秒，持有 GIL 的线程到点会被要求让出。这意味着一个在跑纯计算的线程，最多能把同进程内其他请求的响应延迟推高 5 毫秒量级。对普通后台无所谓，对 P99 敏感的接口就是可见的毛刺。

哪些操作持有 GIL，哪些会释放

操作GIL 状态多线程的实际效果
纯 Python 循环、算术、属性访问全程持有完全串行，线程越多越慢
socket 收发、文件读写、数据库驱动的网络等待进入系统调用前释放真并行，吞吐随线程数接近线性上升
time.sleep释放不占 CPU，但仍占着一个线程与其栈内存
hashlib、zlib、bz2 处理大块数据超过内部阈值后释放能吃多核，小数据量则不释放
numpy / pandas / Pillow 的 C 层运算多数实现主动释放能吃多核，这是「Python 科学计算不慢」的原因
json.dumps、正则回溯、序列化持有（C 实现但不释放）串行，属于容易被忽略的 CPU 密集点
不释放 GIL 的第三方 C 扩展 / 同步 ORM 的纯 Python 部分持有一次慢调用能把整个进程按住

验证不用猜，写十几行就能测出来：加速比接近 1 说明被 GIL 串行，接近线程数说明 GIL 被释放了。

import hashlib
import time
from concurrent.futures import ThreadPoolExecutor

BLOB = b"x" * 16 * 1024 * 1024  # 16MB，足够大才会触发 hashlib 释放 GIL

def cpu_task():
    # 纯 Python 循环：全程持有 GIL，无法并行
    total = 0
    for i in range(5_000_000):
        total += i
    return total

def gil_free_task():
    # hashlib 对大块数据会释放 GIL，多线程可真正并行
    return hashlib.sha256(BLOB).hexdigest()

def bench(fn, workers):
    start = time.perf_counter()
    with ThreadPoolExecutor(max_workers=workers) as pool:
        # 提交 workers 个同样的任务，理想情况下总耗时等于单个任务耗时
        list(pool.map(lambda _: fn(), range(workers)))
    return time.perf_counter() - start

for fn in (cpu_task, gil_free_task):
    t1 = bench(fn, 1)
    t4 = bench(fn, 4)
    # 加速比 = 串行总耗时 / 并行总耗时
    print(fn.__name__, "1 线程 %.2fs" % t1, "4 线程 %.2fs" % t4, "加速比 %.2f" % (t1 * 4 / t4))

3.12 到 3.14：GIL 的松动程度

关于「GIL 要没了」的传言每年一轮，实际进度要看清楚两条独立的路线：子解释器各自持锁（PEP 684），以及彻底去掉 GIL 的可选构建（PEP 703）。

版本变化现状实际能指望什么
3.12per-interpreter GIL（PEP 684）：子解释器各自持有独立 GIL仅 C-API 可用，Python 层缺易用入口基本指望不上，且多数 C 扩展不支持多解释器
3.13free-threaded 构建（PEP 703），需要单独的解释器二进制实验特性，默认构建仍带 GIL可以做验证，不建议上生产
3.13+标准库暴露子解释器接口，配合 per-interpreter GIL逐步可用，生态仍薄适合纯 Python、无重 C 依赖的计算型负载做试点
3.14free-threading 从实验转为官方支持，但仍非默认构建单线程性能回退持续收窄，C 扩展需重新编译并显式声明支持新项目可评估，老项目迁移成本主要在依赖链
⚠️
不要把架构押在去 GIL 上

free-threaded 构建不是换个参数就生效：它需要专门的解释器，依赖的每一个 C 扩展都要重新编译并声明支持自由线程，而且原本被 GIL 顺带保护的竞态会暴露出来（大量库的内部缓存并非线程安全）。未来 2~3 年，生产环境吃满多核的可靠手段依然是多进程或多副本。

什么时候 Python 是最优解

判断标准就一条：瓶颈在人力还是在 CPU。瓶颈在人力，Python 的开发速度优势会直接变成交付优势；瓶颈在 CPU 或延迟，语言层面的常数差距靠架构很难补回来。

部署形态：单进程永远吃不满多核

这是 Python 服务最常见的上线事故：8 核机器上跑一个 uvicorn 进程，压测到 CPU 只有 12% 就上不去了。原因很直接——一个进程一个 GIL，纯 Python 代码的计算吞吐上限就是一个核。要用满 N 核就必须有 N 个进程，没有别的办法。

# 形态一：单容器内多 worker，适合虚拟机或单机部署
uvicorn app.main:app --host 0.0.0.0 --port 8000 \
  --workers 4 \
  --timeout-graceful-shutdown 30   # 关闭时等在途请求，配合 SIGTERM

# 形态二：gunicorn 管进程，uvicorn 作为 worker 实现，进程管理更成熟
gunicorn app.main:app \
  -k uvicorn.workers.UvicornWorker \
  -w 4 \
  -b 0.0.0.0:8000 \
  --graceful-timeout 30 \
  --max-requests 2000 --max-requests-jitter 200   # 定期换进程，兜住慢泄漏

# 形态三：容器编排下每 Pod 单 worker，用副本数替代 worker 数
uvicorn app.main:app --host 0.0.0.0 --port 8000 --workers 1
形态吃满多核的方式优点代价
单进程吃不满，上限一个核调试简单只适合本地开发
单容器多 workerworker 数对齐核数资源利用率高，进程间共享镜像页单容器内故障域大，指标要按进程聚合
gunicorn + uvicorn worker同上，进程管理更强有 max-requests、超时杀进程等治理能力多一层组件与配置
每 Pod 单 worker，多副本靠副本数扩展指标与日志按 Pod 干净可归因，滚动更新粒度细每副本一份内存与连接池，总连接数容易超下游上限

worker 数怎么定、优雅关闭怎么配、多进程下 Prometheus 指标为什么会错乱，属于上线细节，在《Python 服务上生产》里展开。容器编排下的探针、preStop 与滚动更新细节见站内 Kubernetes 专题；接口耗时该怎么拆解、连接池怎么定容量见站内后端性能优化专题，这里不重复。

反模式速查

反模式现象正确做法
在 Web 请求里做 CPU 密集计算单个请求把 worker 的事件循环按住，同进程所有请求一起超时丢进程池或异步任务队列，接口只返回任务 ID
用多线程解决 CPU 瓶颈线程加到 8 个反而更慢，CPU 利用率仍不到一个核换多进程；或把计算下沉到释放 GIL 的库
单进程部署却期待多核性能压测 CPU 卡在 1/N，加机器不见效worker 数或副本数对齐核数
worker 数照抄 2*CPU+1内存打满被 OOM kill，或下游连接数被打爆按内存与下游连接上限反推，再压测校准
在 async 接口里调用同步 SDKQPS 上不去且延迟随并发线性恶化换异步客户端，或显式丢线程池
认为 asyncio 能提升计算性能改造完吞吐没变，代码复杂度翻倍asyncio 只解决 IO 等待，不解决计算

最容易踩的坑

❌
避坑清单
  • 把「GIL 导致不能并发」当结论：IO 密集场景多线程是真并行，错判会让你无谓地改造成多进程，白付内存与 IPC 成本。
  • 用线程池跑纯 Python 计算：4 线程通常比 1 线程慢，且把其他请求的 P99 抬高 5 毫秒量级。
  • 忘了 json.dumps、正则回溯、大对象 pydantic 校验也是 CPU 密集：它们不释放 GIL，返回超大列表的接口常因此拖慢同进程所有请求。
  • 单进程上线：CPU 使用率永远卡在 1/N，扩容机器规格完全无效。
  • worker 数直接照抄 2*CPU+1：Python 每 worker 常驻数十 MB 且随依赖增长，内存先爆的概率远大于 CPU 打满。
  • 多 worker 后忘了连接池是按进程算的：4 worker 每个池 20 连接就是 80 条，很容易超过数据库 max_connections。
  • 指望 free-threaded 构建近期解决问题：它需要专门解释器、C 扩展全部重编，且会暴露原本被 GIL 掩盖的竞态。
  • 用多进程绕开 GIL 却传递大对象：跨进程走 pickle 序列化，几十 MB 的 DataFrame 传参可能比计算本身还慢。
  • fork 之后共享已建立的 socket 或数据库连接：两个进程读同一个 fd，表现为随机的协议错乱，连接必须在子进程里重建。
  • 在 3.13 上开线程访问第三方库的模块级缓存：很多库的内部缓存并非线程安全，此前靠 GIL 侥幸正确。
  • 把 asyncio 当性能银弹推广到全站：没有异步驱动的依赖会被同步调用拖住，收益为负还增加排查难度。
  • 做技术选型只比语言基准跑分：真正决定成本的是团队熟练度、生态契合度与运维复杂度，跑分差距常被 IO 等待淹没。
