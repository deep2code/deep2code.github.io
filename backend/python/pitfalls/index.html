Python 常见陷阱

🏷️ Python

概述：8 个踩过必查的坑

下面 8 个陷阱来自我带项目时的真实教训。每条按"问题描述 → 错误写法 → 正确写法 → 原因 → 要点"卡片化呈现，先看错误代码建立直觉，再对照正确写法修正。不要跳过原因段——知道为什么，才能在新场景里举一反三。

这些陷阱的根源只有两个：Python 的对象模型（可变/不可变、引用共享）和它的执行时机（默认参数定义时求值、闭包延迟绑定、异常控制流）。理解这两点，8 个坑其实是同一类问题。

陷阱分类速览

flowchart TD ROOT[Python 陷阱] --> A[对象模型类] ROOT --> B[执行时机类] ROOT --> C[运行环境类] A --> A1[可变默认参数] A --> A2[循环引用泄漏] A --> A3[浮点数精度] A --> A4[闭包延迟绑定] B --> B1[异常处理不当] B --> B2[列表推导副作用] C --> C1[GIL 误用] C --> C2[包管理混乱]

① 可变默认参数在多次调用间累积

问题：默认参数只在函数定义时创建一次，多次调用共享同一个可变对象。

❌ 错误写法
def append_to(item, target=[]):
    target.append(item)
    return target

print(append_to(1))   # [1]
print(append_to(2))   # [1, 2] —— 预期 [2]

✅ 正确写法
def append_to(item, target=None):
    if target is None:
        target = []       # 每次调用新建
    target.append(item)
    return target

print(append_to(1))   # [1]
print(append_to(2))   # [2]

原因：默认参数存在函数对象的 __defaults__ 属性里，定义时就固定了。对不可变对象（int/str）无害，但 list/dict 原地修改就会跨调用累积。

  • 可变默认值一律用 None 哨兵，函数体内新建。
  • 类属性被实例共享时同理：要放实例上而非类上。

② 循环引用导致内存泄漏

问题：对象互相引用形成环，引用计数永不为 0；若还定义了 __del__，旧版 GC 直接放弃回收。

❌ 错误写法
class Node:
    def __init__(self): self.parent = None
    def __del__(self): pass   # 有析构函数更难回收

child = Node()
child.parent = child          # 自引用成环

✅ 正确写法
import weakref
class Node:
    def __init__(self): self._parent = None
    @property
    def parent(self): return self._parent()  # 弱引用，不增计数

child = Node()
child._parent = weakref.ref(child)
# 或用 WeakKeyDictionary / WeakValueDictionary 做缓存

原因：引用计数无法处理环，分代 GC 虽能补，但带 __del__ 的环对象销毁顺序不确定。用弱引用打破环，对象即可被正常回收。

  • 父子双向引用，子对父一律用 weakref。
  • 长驻服务用 tracemalloc / objgraph 查泄漏，别定义 __del__。

③ GIL 下多线程跑 CPU 密集任务反而更慢

问题：从 Java 转来的习惯用多线程加速计算，结果线程争用 GIL，并行不起来。

❌ 错误写法
import threading
def cpu_heavy():
    return sum(i * i for i in range(10_000_000))
ts = [threading.Thread(target=cpu_heavy) for _ in range(4)]
[t.start() for t in ts]; [t.join() for t in ts]  # 并不比单线程快

✅ 正确写法
from concurrent.futures import ProcessPoolExecutor
with ProcessPoolExecutor(max_workers=4) as p:
    list(p.map(lambda n: sum(i*i for i in range(n)), [10_000_000]*4))
# 或数值计算直接用 numpy，底层 C 代码释放 GIL

原因：GIL 保证同一时刻只有一个线程执行字节码，CPU 密集任务在多线程下只是切换更频繁。多进程才有独立 GIL、真正并行。

  • CPU 密集 → 多进程；IO 密集 → 多线程/asyncio。
  • numpy/pandas 运算本身释放 GIL，多线程调用它们能并行。

④ 不测量就优化，方向全错

问题：凭直觉微优化（局部变量缓存、避免点号），却没动真正的 O(n²) 瓶颈。

❌ 错误写法
# 觉得自己手写循环更"Pythonic"
result = []
for item in big_list:
    if item in another_list:   # O(n) 成员判断，整体 O(n²)
        result.append(item)

✅ 正确写法
# 先 cProfile 定位，再换数据结构
another_set = set(another_list)
result = [item for item in big_list if item in another_set]  # O(n)

原因：算法复杂度的差距是数量级级别的，微优化常数项收益极小。先测后优，80% 时间集中在 20% 代码上。

  • 成员判断、去重、存在性用 set/dict，别用 list。
  • 用 cProfile / py-spy 找瓶颈，只优化热点。

⑤ bare except 与 finally return

问题：裸 except: 把 KeyboardInterrupt 也吞了；finally 里的 return 覆盖正常返回值。

❌ 错误写法
def load():
    try:
        return open("f").read()
    except:        # 连 Ctrl+C 都捕获
        pass
    finally:
        return "兜底"   # 覆盖 try 的返回，且吞异常

✅ 正确写法
import logging
def load():
    try:
        with open("f") as f:
            return f.read()
    except FileNotFoundError:
        logging.exception("文件不存在")   # 记日志再决定
        return None

原因：裸 except 捕获一切控制流异常，bug 被静默；finally 总会执行，其中 return 会改写结果。只捕获预期的具体异常并记录。

  • 永远不用 bare except:，用具体异常类型。
  • 资源释放用 with，别在 finally 里 return。

⑥ 包管理与虚拟环境混乱

问题：全局装包污染系统、requirements 不锁版本、conda 与 pip 混用导致依赖冲突。

❌ 错误写法
pip install django                 # 装到了系统 Python
pip freeze > requirements.txt      # 含一堆无关包
conda install pandas
pip install scipy                  # 混用，破坏 conda 解析

✅ 正确写法
uv init myapp && cd myapp
uv add fastapi pydantic            # 写入 pyproject.toml
uv lock && uv sync                 # 锁文件复现
# 一个项目只用一套工具，绝不 conda/pip 混用

原因：全局环境无法隔离多项目依赖，requirements 不记录传递依赖版本，不同时间安装结果不一致。锁文件 + 独立环境才能复现。

  • 每项目一个虚拟环境，全局只放 CLI 工具。
  • 提交锁文件，CI/生产按锁复现。

⑦ 浮点数精度：0.1 + 0.2 ≠ 0.3

问题：二进制浮点无法精确表示十进制小数，直接比较会踩坑。

❌ 错误写法
print(0.1 + 0.2)              # 0.30000000000000004
if 0.1 + 0.2 == 0.3:         # False！
    print("相等")

✅ 正确写法
import math
print(math.isclose(0.1 + 0.2, 0.3))   # True
# 金额等精确场景用 Decimal
from decimal import Decimal
print(Decimal("0.1") + Decimal("0.2"))  # 0.3

原因：float 是二进制近似，十进制 0.1 是无限循环。比较用容差，金融计算用 Decimal。

  • 浮点比较用 math.isclose，别用 ==。
  • 金额一律 Decimal，不用 float。

⑧ 列表推导副作用与闭包延迟绑定

问题：循环里的闭包共享变量，调用时取的是变量最终值，而非定义时的值。

❌ 错误写法
funcs = [lambda: i for i in range(3)]
print([f() for f in funcs])   # [2, 2, 2]，不是 [0, 1, 2]

✅ 正确写法
# 用默认参数在定义时绑定当前值
funcs = [lambda i=i: i for i in range(3)]
print([f() for f in funcs])   # [0, 1, 2]

# 或用生成器函数工厂
def make(i):
    return lambda: i
funcs = [make(i) for i in range(3)]

原因：闭包绑定的是变量本身而非其值，循环结束后 i 已是 2。默认参数在定义时求值，把当前值"冻结"下来。

  • 循环内建闭包，用默认参数立即绑定值。
  • 列表推导保持纯粹，不要在里面塞副作用。

最佳实践总览

  • 把这 8 条做成 pre-commit / code review checklist，提交前自查。
  • 新团队入职先讲"可变默认参数、闭包延迟绑定、浮点比较"三个最高频坑。
  • 踩过的坑要补测试用例，用回归测试防止复发。

FAQ

Q1：这些坑里哪个最容易在生产出事？
包管理混乱（环境不复现）和异常静默（bug 被掩盖），它们不会立刻报错，却会在部署或深夜排障时爆雷。

Q2：闭包延迟绑定为什么不在定义时取值？
Python 的闭包捕获的是变量名（绑定），不是值快照。这是词法作用域设计，不是 bug；用默认参数就能绕过。

Q3：Decimal 有性能代价吗？
有，比 float 慢。只在金额、精度敏感场景用，科学计算仍用 float + numpy。

总结

8 个坑归为三类：对象模型（可变默认、循环引用、浮点、闭包）、执行时机（异常、推导副作用）、运行环境（GIL、包管理）。每条的解法都很轻——None 哨兵、weakref、多进程、先测量、具体异常、虚拟环境、Decimal、默认参数绑定。把它们变成肌肉记忆，Python 代码的稳健性会上一个台阶。下一篇回到生态全局，看 2026 年该选哪个版本、用哪些工具。
