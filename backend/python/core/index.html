Python 语言核心

🏷️ Python

概述：为什么要重新理解 Python 语言核心

Python 的语法门槛很低，但要从"能写"进化到"写得对、写得稳、写得快"，必须回到语言本身的机制。我见过太多 Python 老手写出来的代码充满隐式坑——可变默认参数、is vs ==、GIL 误判。数据模型决定了对象如何被比较、哈希与迭代；类型注解正在把 Python 从纯动态语言推向"渐进式类型"的工程化语言；装饰器、上下文管理器、迭代器则是一切框架（FastAPI、pytest、SQLAlchemy）的底层语法糖。理解这些，你读任何框架源码都不会迷路。

核心心智模型：Python 中"一切皆对象"，函数、类、模块、类型本身都是对象，可以被传递、赋值、放进容器。语法糖只是操作这些对象的快捷方式。

数据模型与对象模型

每个 Python 对象都有三个要素：ob_refcnt（引用计数）、ob_type（类型指针，决定行为）、以及具体的值。可变与不可变的区分是后续一切陷阱的根源：

不可变int / float / str / tuple / frozenset / bytes否（"修改"即新建对象）可以
可变list / dict / set / bytearray / 自定义实例可以不可以（默认）

再用 is 与 == 的区别加深理解：

a = [1, 2]
b = [1, 2]
print(a == b)   # True：值相等
print(a is b)   # False：不是同一个对象（不同内存地址）

t1 = (1, 2)
t2 = (1, 2)
print(t1 == t2, t1 is t2)  # True True（小 tuple 可能被驻留，但不要依赖）

类型注解 Type Hints：PEP 484 / 526 / 649

PEP 484（3.5）引入函数注解，PEP 526（3.6）引入变量注解，PEP 649（3.14）让注解默认惰性求值。注解本质是元数据，运行时不影响逻辑，但 mypy / pyright 依赖它做静态检查，FastAPI 依赖它做请求校验。

from typing import reveal, Sequence, Optional

# 变量注解（PEP 526）
user_ids: list[int] = [101, 102]
count: dict[str, int] = {"alice": 3}

# 函数注解（PEP 484）：冒号后一个空格，箭头左右各一空格
def total_price(items: Sequence[float], tax: float = 0.06) -> float:
    return sum(items) * (1 + tax)

# Optional / Union 的现代写法：| 运算符（3.10+）
def find_user(uid: int) -> dict | None:
    ...

3.14 起 PEP 649 使注解默认惰性求值，不再在定义时立即计算注解表达式——既加快启动，又消除了前向引用导致的循环导入。旧代码里的 from __future__ import annotations 不再必要。

读取注解是元编程的入口：

import typing
print(typing.get_type_hints(total_price))
# {'items': typing.Sequence[float], 'tax': <class 'float'>, 'return': <class 'float'>}

装饰器原理与实战

装饰器本质是"接收函数、返回新函数"的高阶函数，@decorator 只是 func = decorator(func) 的语法糖。理解它的执行时机比背写法重要：

flowchart TD DEF[def 语句执行] -->|把原函数传入| DEC[decorator func] DEC -->|返回包装器| WRAP[新名指向 wrapper] CALL[调用 func] -->|实际执行| WRAP WRAP -->|调用原函数| ORIG[原始逻辑] 
import time
from functools import wraps

def timer(func):
    @wraps(func)  # 保留原函数的 __name__/__doc__
    def wrapper(*args, **kwargs):
        start = time.perf_counter()
        result = func(*args, **kwargs)
        print(f"{func.__name__} 耗时 {time.perf_counter() - start:.4f}s")
        return result
    return wrapper

@timer
def work(n):
    return sum(i * i for i in range(n))

work(1_000_000)

带参数的装饰器只是多包一层：最外层接收参数，中间层接收函数，内层才是真正的包装。这正是 @lru_cache(maxsize=128) 能写成"带括号"的原因。

上下文管理器：资源安全释放

with 语句背后是协议对象：进入时调 __enter__，退出时（无论是否异常）调 __exit__。它比手写 try/finally 更不易遗漏：

class Transaction:
    def __enter__(self):
        print("begin"); return self
    def __exit__(self, exc_type, exc, tb):
        if exc_type is None:
            print("commit")   # 无异常才提交
        else:
            print("rollback:", exc)  # 有异常回滚
        return False  # False = 不吞掉异常

with Transaction():
    raise ValueError("炸了")

标准库 contextlib.contextmanager 可以用生成器更简洁地实现同一协议，是写自定义上下文管理器的首选。

迭代器与生成器

迭代器协议只要求两个方法：__iter__ 返回自身，__next__ 返回下一个值或抛 StopIteration。生成器（带 yield 的函数）自动实现该协议，且是惰性求值——内存占用与元素数量无关：

def read_lines(path):
    with open(path, encoding="utf-8") as f:
        for line in f:
            yield line.strip()   # 一行一行产出，不一次性读入内存

# 生成器表达式：惰性
squares = (x * x for x in range(1_000_000))
print(next(squares))  # 0，按需计算

处理大文件 / 大数据流时永远用生成器，不要用列表推导把全部元素物化进内存——这是 O(n) 内存与 O(1) 内存的差距。

魔术方法精选

魔术方法让自定义类融入 Python 语法体系：

class Money:
    def __init__(self, amount): self.amount = amount
    def __repr__(self): return f"Money({self.amount})"
    def __eq__(self, other): return self.amount == other.amount
    def __lt__(self, other): return self.amount < other.amount
    def __add__(self, other): return Money(self.amount + other.amount)

m1, m2 = Money(10), Money(20)
print(m1 + m2, m1 < m2)  # Money(30) True

最佳实践

  • 装饰器一律用 functools.wraps 保留元信息，否则调试时全是 wrapper。
  • 公共 API 必加类型注解，配合 mypy / pyright 做静态检查；注解写"够用"即可，不要为注解而注解。
  • 资源管理优先 with；需要清理逻辑的类不要指望 __del__。
  • 大数据流用生成器；容器成员判断用 set / dict 而非 list。
  • 可变默认参数、可变全局状态是后续《常见陷阱》篇的重点，写函数时就有预防意识。

FAQ

Q1：注解会影响运行时性能吗？
不会执行类型检查，只是元数据。3.14 前注解在定义时会被求值一次，循环导入可能有开销；3.14 起 PEP 649 惰性求值，开销进一步降低。

Q2：为什么 @decorator 和 @decorator() 效果不同？
前者直接把函数传给装饰器；后者多调用一层，要求装饰器返回一个"真正的装饰器"。带参数的装饰器必须写括号。

Q3：生成器和列表推导怎么选？
只遍历一次、数据量大 → 生成器（省内存）；需要重复索引、需要 len()、数据量小 → 列表。

总结

语言核心不是语法清单，而是一套"对象 + 协议"的契约：数据模型定义对象行为，类型注解把契约形式化，装饰器/上下文管理器/迭代器则是操作这些契约的语法糖。掌握它们，你就拥有了阅读框架源码、写出健壮代码的地基。下一篇进入 CPython 内部，看这些机制在解释器里是如何被执行的。
