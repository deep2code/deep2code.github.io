Python 服务上生产：进程模型、优雅关闭与可观测性

Python 服务上生产要回答的问题和写代码时完全不同：起几个进程、怎么关得干净、内存涨了算不算故障、指标怎么才不串、定时任务在多副本下会不会跑重。这几件事定错了，代码写得再好也会在发布和故障时付出代价。这篇按上线顺序逐个给结论和可抄的配置。为什么必须多进程才能吃满多核，见《Python 做后端的适用边界与运行时约束》。

进程模型：worker 数是被内存决定的

uvicorn --workers N 会由主进程派生 N 个子进程共享监听套接字；gunicorn 加 uvicorn.workers.UvicornWorker 是同一件事，区别在 gunicorn 的进程管理更成熟（有 --max-requests 轮换、worker 静默超时强杀等治理能力）。

「worker 数 = 2 × 核数 + 1」这个公式不要照抄，它来自同步 WSGI 时代。Python 的每个 worker 是独立进程，独占一份解释器与已导入模块，常驻几十到上百 MB，所以真正卡住你的通常是内存和下游连接数，不是 CPU。

形态扩展方式优点代价适用

单进程不能扩展—吃不满多核仅本地开发
 
# ---------- 形态一：虚拟机上用 gunicorn 管进程 ----------
gunicorn myapp.main:app \
  -k uvicorn.workers.UvicornWorker \
  -w 4 \
  -b 0.0.0.0:8000 \
  --graceful-timeout 30 \        # 优雅关闭等待在途请求的上限
  --timeout 60 \                 # worker 静默超时：超过就认为卡死并强杀，必须大于最慢接口
  --max-requests 5000 \          # 处理够这么多请求就换新进程，兜住缓慢的内存增长
  --max-requests-jitter 500 \    # 加抖动，避免所有 worker 同时重启造成容量凹陷
  --access-logfile - \
  --forwarded-allow-ips '*'      # 在反向代理后面才能拿到真实客户端 IP

# ---------- 形态二：K8s 里单 worker，用副本数扩展 ----------
exec uvicorn myapp.main:app \
  --host 0.0.0.0 --port 8000 \
  --workers 1 \
  --timeout-graceful-shutdown 25 \
  --no-access-log                # 访问日志交给网关，避免每请求两条

# ---------- 定 worker 数之前先量单进程内存 ----------
# 启动后打一次流量，看 RSS 稳定在多少（单位 KB）
ps -o rss=,cmd= -p $(pgrep -f 'uvicorn myapp')
# worker 数上限 = (容器内存限额 × 0.8 - 共享部分) / 单进程 RSS
# 连接数上限 = 数据库 max_connections × 0.8 / (worker 数 × 每 worker 池大小)

优雅关闭：四个超时必须对齐

关得不干净的表现是发布期间出现一小波 502 或超时。原因几乎总是同一个：进程收到 SIGTERM 与上游停止转发流量之间存在时间差。端点摘除是异步生效的，等你开始拒绝新连接时，可能还有请求正在路上。

让端点摘除先完成 EP-->>P: 期间仍可能有新请求打进来 P->>P: 停止接受新连接，已有连接继续处理 P->>U: 等在途请求完成，上限 = 优雅超时 U-->>P: 全部完成 P->>P: 执行 lifespan 关闭段
关连接池、flush 缓冲、注销注册中心 P-->>K: 正常退出，退出码 0 Note over K,P: 终止宽限期必须大于
preStop 等待 + 优雅超时

层参数建议值配错的后果
应用lifespan 关闭段关连接池、HTTP 客户端、flush 日志与指标连接不释放，下游看到一批半开连接
uvicorn--timeout-graceful-shutdown略大于最慢接口的 P99，如 25s设太小则在途请求被直接断开
gunicorn--graceful-timeout30s同上；且它与 --timeout 是两件事，后者是卡死判定
编排terminationGracePeriodSeconds大于 preStop 等待 + 优雅超时，如 45s进程正在收尾时被 SIGKILL，在途请求全丢
编排preStop 等待5~10s不加就会有请求被打到正在关闭的实例，表现为发布期 502
代码不吞 CancelledError捕获后必须重抛协程无法被取消，优雅关闭直接失效

内存：只涨不降通常不是泄漏

这是 Python 服务最常见的误判。CPython 的小对象走自带的分配器，按池和区（arena）管理，一个区只有在完全空闲时才可能还给操作系统。实际运行中总有零散的长命对象散落在各个区里，于是 RSS 停在历史峰值附近不再下降。这是分配器行为，不是泄漏。

判断标准是趋势而不是绝对值：流量平稳后曲线走平，就是正常水位；持续单调上涨、没有平台期、重启后又从低位开始重复同样的上涨，才按泄漏查。

import gc
import linecache
import tracemalloc


def start_leak_probe() -> tracemalloc.Snapshot:
    # tracemalloc 会给每次分配记录调用栈，开销明显（内存与 CPU 都涨），
    # 只在排查期临时开启，绝不常驻生产
    tracemalloc.start(10)          # 保留 10 层栈帧，够定位到业务代码
    return tracemalloc.take_snapshot()


def diff_leak_probe(baseline: tracemalloc.Snapshot, top: int = 10) -> None:
    current = tracemalloc.take_snapshot()
    # 按分配位置比较两个时间点的差异：持续为正且不断变大的那几行就是嫌疑
    for stat in current.compare_to(baseline, "lineno")[:top]:
        frame = stat.traceback[0]
        print(f"{frame.filename}:{frame.lineno} +{stat.size_diff / 1024:.1f}KB "
              f"({stat.count_diff:+d} 个对象)")
        print("   ", linecache.getline(frame.filename, frame.lineno).strip())


def object_census(top: int = 10) -> None:
    """不开 tracemalloc 时的轻量手段：看哪类对象在变多"""
    from collections import Counter
    counter = Counter(type(o).__name__ for o in gc.get_objects())
    for name, cnt in counter.most_common(top):
        print(name, cnt)

# ---------- 多进程部署的内存优化 ----------
def before_fork() -> None:
    # 在 fork 出 worker 之前调用：先回收启动期垃圾，再把常驻对象移出 GC 追踪，
    # 避免子进程的 GC 遍历修改对象头的标记位而触发写时复制，
    # 把本来父子共享的内存页变成各自私有
    gc.collect()
    gc.freeze()
现象结论手段
上涨后走平，重启回到低位再走平正常水位按峰值设容器 limit，别追着「优化」
持续上涨无平台期，对象数同步增长真泄漏tracemalloc 差异快照 + objgraph 引用链
对象数平稳但 RSS 持续涨碎片或 C 扩展内部缓存试 MALLOC_ARENA_MAX=2；定期轮换进程
多 worker 时总内存远超预估fork 后共享页被写时复制打散fork 前 gc.freeze()；升级到 3.12 享受不朽对象的收益
某类请求后内存跳升且不回落缓存了大对象检查 lru_cache 有没有 maxsize，模块级 dict 有没有淘汰
OOM 被 kill，日志里什么都没有容器限额被击穿看内核 OOM 记录与容器退出码 137；先降 worker 数止血

可观测性：多进程是最大的坑

默认的 prometheus_client 把指标存在进程内存里。多 worker 下请求被随机分到某个进程，每次抓取只拿到其中一个的数据，计数器会跳变甚至倒退。必须开多进程模式：各进程把指标写成文件，暴露端点时聚合。

import os
from contextlib import asynccontextmanager

from fastapi import FastAPI
from prometheus_client import CollectorRegistry, Counter, Histogram, generate_latest, multiprocess
from starlette.responses import Response

# 必须在导入 prometheus_client 之前就设好这个环境变量（通常在 Dockerfile 或启动脚本里）
#   PROMETHEUS_MULTIPROC_DIR=/tmp/prom
# 而且容器启动时要清空该目录，否则上次运行残留的文件会被算进来
MULTIPROC_DIR = os.environ.get("PROMETHEUS_MULTIPROC_DIR")

REQUESTS = Counter("http_requests_total", "请求总数", ["method", "path", "status"])
LATENCY = Histogram(
    "http_request_duration_seconds", "请求耗时", ["method", "path"],
    # 显式给桶边界：默认桶对 Web 接口太粗，算不准 P99
    buckets=(0.005, 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1.0, 2.5, 5.0),
)


@asynccontextmanager
async def lifespan(app: FastAPI):
    yield
    if MULTIPROC_DIR:
        # 进程退出时标记自己已死，否则它的指标文件会永远被计入总量
        multiprocess.mark_process_dead(os.getpid(), MULTIPROC_DIR)


app = FastAPI(lifespan=lifespan)


@app.get("/metrics")
def metrics() -> Response:
    if MULTIPROC_DIR:
        registry = CollectorRegistry()
        multiprocess.MultiProcessCollector(registry)   # 聚合所有 worker 的文件
    else:
        from prometheus_client import REGISTRY as registry   # 单进程直接用默认注册表
    return Response(generate_latest(registry), media_type="text/plain; version=0.0.4")
维度做法注意
指标prometheus_client，按接口打计数与直方图多进程必须配 PROMETHEUS_MULTIPROC_DIR 并在启动时清空；path 标签要用路由模板，用原始 URL 会标签爆炸
链路OpenTelemetry 自动埋点（FastAPI、httpx、SQLAlchemy 各有 instrumentation）采样率要配，全采样在高 QPS 下开销可观
日志与 trace 关联把 trace_id 注入日志字段用 contextvars 透传；细节见站内日志专题
事件循环健康常驻上报事件循环延迟asyncio 服务最该看的指标，见《asyncio 的性能陷阱》
进程级指标RSS、GC 各代计数、打开的文件描述符数fd 数缓慢上涨往往是连接泄漏的第一个信号
接口耗时拆解按阶段打点方法论见站内后端性能优化专题，这里不重复

健康检查：存活与就绪不是一回事

探针检查什么失败后的动作绝对不要做
存活（liveness）进程还在、事件循环没卡死，返回固定响应即可重启容器查数据库——下游抖动会导致全部实例被反复重启
就绪（readiness）本地初始化是否完成：配置已加载、连接池已建、缓存已预热从端点表摘除，不重启级联下游依赖——下游抖一下所有副本同时不就绪，服务整体不可用
启动（startup）慢启动服务的初始化窗口在此期间不执行存活检查用超长的存活初始延迟代替它

就绪检查为什么不能级联下游、以及服务发现侧的摘除逻辑，见站内 微服务与服务治理专题。

容器化：几个必设的环境变量

FROM python:3.12-slim

# PYTHONUNBUFFERED=1 最关键：不设的话 stdout 是块缓冲，
# 日志会攒在缓冲区里，进程被 kill 时直接丢失，排查故障时什么都看不到
ENV PYTHONUNBUFFERED=1 \
    PYTHONDONTWRITEBYTECODE=1 \
    PYTHONFAULTHANDLER=1 \
    PROMETHEUS_MULTIPROC_DIR=/tmp/prom \
    MALLOC_ARENA_MAX=2

WORKDIR /app
COPY requirements.lock ./
RUN pip install --no-cache-dir -r requirements.lock
COPY src ./src

# 非 root 运行；同时准备指标目录
RUN useradd --create-home --uid 10001 appuser \
 && mkdir -p /tmp/prom && chown -R appuser:appuser /tmp/prom /app
USER appuser

EXPOSE 8000
# 用 exec 形式（JSON 数组）：进程 PID 为 1 且能直接收到 SIGTERM。
# 写成 shell 形式会被 /bin/sh -c 包一层，信号到不了 Python，优雅关闭直接失效
CMD ["uvicorn", "myapp.main:app", "--host", "0.0.0.0", "--port", "8000", \
     "--workers", "1", "--timeout-graceful-shutdown", "25"]
设置作用不设的后果
PYTHONUNBUFFERED=1stdout 不做块缓冲日志延迟出现，进程被杀时缓冲区内容全部丢失
PYTHONDONTWRITEBYTECODE=1不生成 pyc只读文件系统下报错，镜像层里多出无用文件
PYTHONFAULTHANDLER=1段错误时打印 Python 栈C 扩展崩溃时只有一行 Segmentation fault
exec 形式的 CMD进程直接收到 SIGTERM信号被 shell 吞掉，优雅关闭完全不生效
非 root 用户降低容器逃逸影响面安全基线不过，细节见站内安全专题
多阶段构建 + slim 基础镜像镜像从 1GB 级降到 200MB 级拉取慢、扩容慢、攻击面大

定时任务与后台 worker

最容易出事的一条：进程内调度器在多副本下会重复执行。三个副本各跑一个 APScheduler，每天的对账任务就跑三遍；如果任务不幂等，数据直接错。

sequenceDiagram participant S1 as 副本 1 内置调度器 participant S2 as 副本 2 内置调度器 participant S3 as 副本 3 内置调度器 participant DB as 数据库 Note over S1,S3: 00:00 三个副本的定时器同时触发 S1->>DB: 执行对账，写入结果 S2->>DB: 同一批数据再算一遍 S3->>DB: 第三遍 Note over DB: 非幂等任务导致重复扣款或重复发送 Note over S1,S3: 改造：抢分布式锁，只有一个副本执行 S1->>DB: SET lock NX EX 3600 成功，执行 S2--xDB: 抢锁失败，直接跳过 S3--xDB: 抢锁失败，直接跳过
方案多副本安全可观测性适用
进程内 APScheduler，多副本不安全，会重复执行无只有单副本时可用
进程内调度 + 分布式锁安全（锁要带过期时间）一般任务少、不想加组件
独立的调度进程 / CronJob安全好，有独立的成功失败记录推荐，业务副本与任务解耦
Celery beat + worker安全（beat 单实例）好已有 Celery 体系时
队列驱动的后台 worker安全最好，有积压与重试指标异步任务的标准形态，见站内消息队列专题

反模式速查

反模式现象修法
单 worker 部署却期待多核性能CPU 卡在 1/N，升配无效worker 数或副本数对齐核数
不处理 SIGTERM每次发布都有一波 502 与超时配齐四个超时，加 preStop
忘记 PYTHONUNBUFFERED故障时最后几秒的日志全丢Dockerfile 里设为 1
多副本各跑进程内定时任务任务重复执行，数据出错分布式锁或独立调度
tracemalloc 常开内存与 CPU 都被自己的排查工具吃掉只在排查期开，用完关
prometheus 多进程不配目录计数器跳变甚至倒退，告警全靠不住配 PROMETHEUS_MULTIPROC_DIR 并聚合
就绪探针检查数据库下游抖一下，所有副本同时被摘就绪只看本地初始化状态
shell 形式的 CMD信号被 sh 吞掉，优雅关闭失效用 JSON 数组形式

最容易踩的坑

❌
避坑清单
  • 照抄「2 × 核数 + 1」设 worker：Python 每进程独占数十到上百 MB，内存先爆的概率远高于 CPU 打满。
  • terminationGracePeriodSeconds 小于服务器的优雅超时：进程正在收尾时被 SIGKILL，在途请求全丢。
  • 不加 preStop 等待：端点摘除是异步的，SIGTERM 之后仍有请求被打进来，发布期必然出现 502。
  • 忘记 PYTHONUNBUFFERED=1：stdout 块缓冲，崩溃前最关键的那几行日志永远看不到。
  • 把「内存只涨不降」直接当泄漏查：分配器本来就不归还内存，看趋势有没有平台期才是正确判断。
  • tracemalloc 或 asyncio 调试模式常开在生产：排查工具本身成了性能问题。
  • lru_cache 不设 maxsize：参数一多就成了无上限缓存，这是最常见的真泄漏来源。
  • prometheus 多进程模式没配目录、或没在启动时清空目录：指标跳变、上次运行的残留被计入，告警彻底不可信。
  • 指标的 path 标签用原始 URL：带 ID 的路径让标签基数爆炸，能把监控系统打挂。
  • 进程退出时不调 mark_process_dead：死掉的 worker 指标永远留在总量里，数值只增不减。
  • 就绪探针级联下游依赖：下游抖动导致所有副本同时不就绪，把局部故障放大成整体不可用。
  • 多副本各自跑进程内定时任务：对账、发券、清理这类任务被执行多遍，事后对账才发现。
