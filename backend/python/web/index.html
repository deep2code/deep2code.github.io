Python Web 开发

🏷️ Python

概述：从接口契约到生产部署

Python Web 开发的核心是理解两层接口：WSGI / ASGI 规定了 Web 服务器与应用之间怎么对话；框架在这个契约之上提供路由、校验、ORM。选错框架事小，不懂契约事大——我当年部署时为了调通 gunicorn worker 数量和 worker 类型，踩了不少坑才搞明白 WSGI 的 sync/async 区别。调试 502、部署 gunicorn/uvicorn 时处处是它。

WSGI vs ASGI：同步与异步的接口契约

flowchart LR subgraph WSGI 同步 C1[客户端] --> W1[WSGI Server gunicorn] W1 --> A1[WSGI App Django/Flask] A1 --> W1 W1 --> C1 end subgraph ASGI 异步 C2[客户端] --> W2[ASGI Server uvicorn] W2 --> A2[ASGI App FastAPI] A2 -->|async| W2 W2 --> C2 end

WSGI/ASGI 是应用层与协议层之间的契约：服务器解析请求、构造环境，调用应用对象；应用处理完返回响应。WSGI 同步阻塞、难支持 WebSocket；ASGI 在其上引入 asyncio，支持长连接与异步高并发。

# 最原始的 WSGI 应用：两个参数，start_response + 可迭代 body
def application(environ, start_response):
    start_response('200 OK', [('Content-Type', 'text/plain')])
    return [b'Hello, WSGI']

# ASGI 应用：三个参数，scope / receive / send，异步
async def application(scope, receive, send):
    event = await receive()
    await send({"type": "websocket.send", "text": "hi"})

FastAPI 深度实战

FastAPI 的三大支柱：异步原生、Pydantic v2 自动校验、类型驱动的依赖注入与 OpenAPI 文档：

from fastapi import FastAPI, Depends, HTTPException
from pydantic import BaseModel

app = FastAPI(title="Demo")

class Item(BaseModel):
    name: str
    price: float

async def get_token():
    return "dev-token"

@app.get("/items/{item_id}")
async def read_item(item_id: int, token: str = Depends(get_token)):
    if item_id <= 0:
        raise HTTPException(400, "id 必须为正")
    return {"id": item_id, "token": token}

访问 /docs 即自动得到 Swagger UI，/openapi.json 得到规范——这就是类型注解在 Web 层的红利。Pydantic v2 用 Rust 核心重写，校验速度比 v1 快 5–50 倍。

Django 与 Flask 的位置

Django 自带 ORM、Admin、迁移，"电池全含"，适合需要后台管理、ORM 一体的传统业务：

# settings.py 关键配置
LANGUAGE_CODE = "zh-hans"
TIME_ZONE = "Asia/Shanghai"
USE_TZ = True

Flask 则把选择权交给你：路由 + 一个 WSGI 应用，数据库、表单、认证都靠扩展拼装，灵活但要自己选型。新项目做 API 默认选 FastAPI；维护历史系统再看 Django/Flask。

数据层：SQLAlchemy 2.0 异步

SQLAlchemy 2.0 异步支持成熟，配合 asyncpg 是 Python 异步数据层的事实标准：

from sqlalchemy.ext.asyncio import create_async_engine, async_sessionmaker
from sqlalchemy import text

engine = create_async_engine("postgresql+asyncpg://user:pass@localhost/db")
async_session = async_sessionmaker(engine, expire_on_commit=False)

async def fetch_user(uid: int):
    async with async_session() as session:
        result = await session.execute(text("SELECT name FROM users WHERE id=:id"), {"id": uid})
        return result.scalar_one_or_none()

部署：gunicorn / uvicorn + Nginx + Docker

生产部署是"应用服务器 + 反向代理"两层。ASGI 用 uvicorn（配 gunicorn 管理进程），前置 Nginx 做 TLS 终结与静态资源：

# ASGI 生产启动：gunicorn 管 uvicorn worker
gunicorn app:app -w 4 -k uvicorn.workers.UvicornWorker -b 127.0.0.1:8000

FROM python:3.12-slim
WORKDIR /app
COPY pyproject.toml uv.lock ./
RUN pip install uv && uv sync --frozen --no-dev
COPY . .
CMD ["uv", "run", "gunicorn", "app:app", "-k", "uvicorn.workers.UvicornWorker", "-b", "0.0.0.0:8000"]

worker 数量经验值为 CPU 核数的 2 倍左右（IO 密集）；异步框架不要开太多 worker，单 worker + 事件循环即可吃满并发。

最佳实践

  • 新项目 API 默认 FastAPI + uvicorn + Pydantic v2；需要 Admin/ORM 一体再上 Django。
  • 请求/响应模型用 Pydantic BaseModel 约束，不要裸 dict 传递。
  • 异步栈全套异步：asyncpg / aioredis / httpx.AsyncClient，别在异步路由里塞同步阻塞调用。
  • 前置 Nginx 处理 TLS、静态资源、限流，应用服务器只跑业务。
  • 容器化用 slim 镜像 + uv sync --frozen，保证环境可复现。

FAQ

Q1：gunicorn 能跑 FastAPI 吗？
能，但必须用 -k uvicorn.workers.UvicornWorker 把 worker 换成 ASGI 实现。gunicorn 本身是 WSGI 服务器。

Q2：FastAPI 和 Flask 性能差多少？
单看框架开销差距不大；真正差距在异步 IO 模型——FastAPI 原生 async 在高并发 IO 下能维持更优延迟与吞吐。

Q3：什么时候 Django 比 FastAPI 更合适？
需要开箱即用的 Admin 后台、内置 ORM/迁移、表单认证，且团队希望"约定优于配置"时，Django 省事得多。

总结

Web 开发的骨架是 WSGI/ASGI 契约 + 框架 + 数据层 + 部署。2026 年新项目几乎一面倒选 FastAPI/uvicorn/Pydantic v2 的异步栈，Django 守住全栈后台阵地，Flask 退居轻量小工具。把契约、框架、SQLAlchemy、Nginx+Docker 串起来，就是一条完整的生产上线链路。下一篇集中盘点写这些代码时最容易踩的 8 个坑。
