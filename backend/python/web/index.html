Python Web 服务的部署形态：WSGI、ASGI 与进程模型

🏷️ Python

两份契约的形状：WSGI 与 ASGI 差在哪

部署形态的结论全部从契约推出来，所以先把签名摊开。WSGI（PEP 3333）要求应用是一个普通可调用对象，接收 environ 字典与 start_response 回调，返回产出字节串的可迭代对象，请求体从 environ["wsgi.input"] 同步读。ASGI 要求应用是 async def app(scope, receive, send)：scope 描述这次连接（type 取 http、websocket 或 lifespan），receive 与 send 是两个协程，请求体分片、客户端断连、WebSocket 帧、进程启停全部表达成事件。

真正的差别不是「异步」这个词，而是契约里有没有「连接生命周期中的事件」这个位置。WSGI 的一次调用天然等于一次完整请求，服务器没有任何通道告知应用「客户端已经走了」，所以 WebSocket、SSE 的断连感知、请求中途取消在 WSGI 下无法表达——不是实现没做，是签名里没地方放。

维度WSGIASGI工程后果
应用签名同步可调用，两参数async def，三参数WSGI 应用无法被 await，套在 ASGI 服务器上只能经适配器丢线程池

# 最小 WSGI 应用：返回值必须是产出 bytes 的可迭代对象
def wsgi_app(environ, start_response):
    body = b"ok"
    start_response("200 OK", [
        ("Content-Type", "text/plain; charset=utf-8"),
        ("Content-Length", str(len(body))),   # 不给长度，服务器只能靠关连接表示结束
    ])
    return [body]

# 最小 ASGI 应用：三个参数，一切都是事件
async def asgi_app(scope, receive, send):
    if scope["type"] == "lifespan":           # 启停钩子：连接池在这里建、在这里关
        while True:
            msg = await receive()
            if msg["type"] == "lifespan.startup":
                await send({"type": "lifespan.startup.complete"})
            elif msg["type"] == "lifespan.shutdown":
                await send({"type": "lifespan.shutdown.complete"})
                return
    assert scope["type"] == "http"
    body = b""
    while True:                               # 请求体是分片事件流，不是一个文件对象
        msg = await receive()
        if msg["type"] == "http.disconnect":  # 客户端已走，立刻放弃，别再打下游
            return
        body += msg.get("body", b"")
        if not msg.get("more_body", False):
            break
    await send({"type": "http.response.start", "status": 200,
                "headers": [(b"content-type", b"text/plain; charset=utf-8")]})
    await send({"type": "http.response.body", "body": b"ok"})

为什么同步框架套一层 async 得不到并发

并发的前提是有让出点，而且让出之后有人替你继续跑。这两个条件缺任何一个，写了 async def 也只是把同一段同步逻辑包了一层协程壳。

三个具体机制值得记住。第一，WSGI 可调用对象不可 await，服务器只能在某个线程里同步调用它，函数体里怎么写都改不了这件事。第二，Flask 从 2.0 起支持 async def 视图，但实现方式是在当前工作线程里现起一个事件循环，跑完这个协程就关掉；两个并发请求落在两个线程的两个独立循环里，彼此之间没有任何调度关系，并发单元仍然是 worker 的线程数。所以「Flask 改成 async 了所以能扛并发」是错的。第三，Django 的两套适配层是对称的：同步视图跑在 ASGI 服务器下会经 sync_to_async 落到线程池，异步视图跑在 WSGI 服务器下会经 async_to_sync 退化成阻塞等待。

服务器handler 形态实际并发单元失效点
WSGI（gunicorn sync）def进程数一个请求占一个进程直到返回，慢请求直接吃掉容量
WSGI（gunicorn gthread）def进程数 × 线程数CPU 型工作受 GIL 限制，线程加多了只增加上下文切换
WSGIasync def（Flask 2.x 视图）仍是线程数每请求一个临时事件循环，请求之间不共享调度，asyncio 并发收益为零
ASGIdef（Starlette/FastAPI）线程池令牌数框架丢进 anyio 默认线程限流器，令牌数默认 40，超出的请求排队等令牌
ASGIasync def + 全异步驱动在途 Task 数唯一能拿到高并发的组合，但受下游连接池上限约束
ASGIasync def 里写同步阻塞调用退化为 1最坏情况：连线程池都不走，整个 worker 的所有在途请求一起停住

结论是一条链路判定：ASGI 服务器 + 异步 handler + 异步驱动，三环全通才有事件循环级并发；任何一环是同步的，整条链路就退回线程或进程并发。协程调度的内部细节与阻塞源分类，详见站内《FastAPI 异步与性能》。

gunicorn worker 类型的选择矩阵

gunicorn 本身只是进程管理器加 HTTP 解析，能力完全由 worker 类型决定。选错的代价不是慢一点，而是某类请求根本无法工作。先把整条链路的分层摆清楚，再看每一层能换成什么。

最常被误解的一格是异步 worker 的 timeout。很多人以为「配了 timeout 30 就等于请求最多跑 30 秒」，实际上 gunicorn 的 timeout 判定的是 worker 是否还在向 master 上报心跳；异步 worker 的心跳由事件循环上的协程完成，只要循环没被彻底阻塞，一个跑了十分钟的请求不会触发任何重启。请求级超时必须自己在应用里做（asyncio.timeout）或交给反向代理。

进程数、线程数与容器 CPU 配额

一句话结论：GIL 保证同一进程内任一时刻只有一条线程在执行 Python 字节码，所以纯 Python 的 CPU 工作只能靠多进程扩展（机制细节详见站内《Python 并发编程》与《CPython 内部原理与性能优化》）。这条结论之上，真正决定 worker 数的往往不是核数而是内存。

流传最广的 2 × 核数 + 1 来自 gunicorn 文档对 sync worker 的建议，前提是「请求短、单进程内存小、时间主要花在 IO 等待」。它不是通用公式：模型加载类服务每 worker 几百 MB，按这个公式算出来直接 OOM；异步服务单 worker 就能吃满一个核，worker 数按核数取即可，再多只是浪费内存并成倍放大下游连接数。

容器里还有一个几乎必踩的坑：os.cpu_count() 返回的是宿主可见的 CPU 数，与 cgroup 的 CPU 配额无关。在 64 核机器上给容器分 1 核，公式会算出 129 个 worker。3.13 新增的 os.process_cpu_count() 读的是 CPU 亲和性，比前者准，但仍然不等于 cgroup 的配额。稳妥做法是显式用环境变量把 worker 数写死，让编排系统的资源声明成为唯一真相来源。

preload 与写时复制：省下的内存比预期少

preload_app 打开后，master 先 import 应用再 fork，子进程与父进程共享同一批物理页，看起来能把 N 份代码和常量省成 1 份。现实是这份共享会持续退化：CPython 每次触碰对象都要修改对象头里的引用计数，写操作立刻触发页复制；垃圾回收遍历时还会写对象的 GC 字段，把大片只读页一并「写花」（对象模型与内存管理详见站内《CPython 内部原理与性能优化》）。所以 preload 的内存收益是真实的，但远小于按代码体积估算的值，而且会随运行时间衰减。

有两个能实际改善的动作：按 CPython 文档对 gc.freeze() 的建议，在父进程早期 gc.disable()、fork 之前调 gc.freeze() 把长生命周期对象移进永久代、子进程里再 gc.enable()，避免子进程的 GC 去写父进程遗留对象；另外 3.12 起内置单例等不可变对象成为 immortal 对象，引用计数不再变动，这部分共享是稳定的。

preload 带来的变化收益陷阱与表现
代码与常量只加载一次启动更快，初期 RSS 总和下降共享页被引用计数写花，收益随时间衰减；用 ps 的 RSS 会把共享页重复计入，要看 /proc/PID/smaps_rollup 里的 Pss
import 期建立的资源被 fork 继承无数据库引擎、Redis 客户端、HTTP 连接池里的 socket 被多个进程共用，表现为随机的协议错乱、连接被对端重置、响应串到别的请求上
随机源与缓存状态被继承无各 worker 的随机序列一致，抽样与打散逻辑失效
HUP 重载行为改变无未 preload 时 HUP 会加载新代码，preload 时应用在 master 里，HUP 只重启 worker 不换代码，表现为「发布了但代码没生效」
import 期异常的影响面提前暴露配置错误炸的是 master，整个服务起不来，而不是单个 worker 退避重试
与热重载互斥无开发环境同时开 --reload 与 preload 时行为不可预期，应只在生产开 preload
多进程指标采集无进程内计数器各算一份，必须用多进程模式的指标目录，否则拉到哪个 worker 看哪个 worker 的数

判定规则很简单：所有有状态的连接必须在 fork 之后建立。ASGI 的 lifespan 钩子、gunicorn 的 post_fork 钩子就是为此存在的位置；把 create_engine 写在模块顶层，在 preload 下几乎一定出问题。

优雅退出：信号语义与四个超时的对齐

信号语义这一块最容易记反，因为 gunicorn 与 nginx 的约定几乎是相反的。

信号gunicorn masternginx master（对照）踩坑点

反向代理与应用服务器：超时和长连接必须成对设

这一层的错误几乎都表现为「偶发 502 / 504，重试就好了」，而根因通常是两侧参数的相对大小写反了，不是网络抖动。

参数常见默认值建议关系设错的症状
nginx proxy_read_timeout60s大于应用请求超时比应用小的话，nginx 先断开返回 504，应用还在继续跑完，白做功且日志里找不到对应错误
应用请求超时（asyncio.timeout 或框架中间件）无大于所有下游调用超时之和不设的话慢请求会一直占着在途名额，过载时排队无限增长
下游调用超时（DB、HTTP 客户端）多数客户端默认不超时最内层、最小不设超时是雪崩第一原因：一个慢依赖把所有 worker 的名额吃干
gunicorn keepalive2s大于 nginx 上游空闲超时默认组合（应用 2s、nginx 上游 60s）下，nginx 会复用一条服务端已关的连接，表现为无规律 502
nginx upstream keepalive_timeout60s小于应用侧 keepalive同上；规则是让先关连接的一方是代理
nginx proxy_next_upstream含 error timeout非幂等接口移除 non_idempotent 语义POST 请求超时后被重投到另一台，造成重复下单
terminationGracePeriodSeconds30s大于 preStop 等待 + graceful_timeout收尾被 SIGKILL 打断，在途请求变成客户端侧的连接重置

还有两件容易被忽略的事。其一，sync worker 根本不支持 keep-alive，在它前面配 upstream 长连接不会生效，每个请求都是新连接，压测时表现为大量 TIME_WAIT 与偏高的建连延迟；要长连接就得换 gthread 或异步 worker。其二，上游长连接必须三件套齐全（keepalive 数量、HTTP/1.1、清空 Connection 头），少一个就静默退回短连接（nginx 侧细节详见站内《Nginx》）。

upstream app {
    server 127.0.0.1:8000 max_fails=3 fail_timeout=10s;
    keepalive 32;              # 每个 worker 进程保留的空闲长连接数
    keepalive_timeout 30s;     # 必须小于应用侧 keepalive，保证代理先关
    keepalive_requests 1000;
}

server {
    listen 443 ssl;
    server_name api.example.com;

    location / {
        proxy_pass http://app;
        proxy_http_version 1.1;          # 长连接三件套之一，默认 1.0 不支持复用
        proxy_set_header Connection "";  # 清掉 close，否则每次请求后连接被关

        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        proxy_connect_timeout 2s;        # 建连快失败，别把队列堆在代理侧
        proxy_send_timeout 30s;
        proxy_read_timeout 65s;          # 大于应用请求超时，让应用有机会返回业务错误

        proxy_next_upstream error timeout;   # 注意：不要对非幂等接口开启重投
        proxy_buffering on;                  # 缓冲慢客户端，这是 sync worker 的生存前提
    }

    location /events {
        proxy_pass http://app;
        proxy_http_version 1.1;
        proxy_buffering off;             # SSE 必须关缓冲，否则事件被攒住不下发
        proxy_read_timeout 1h;
    }
}

阻塞拖垮事件循环：怎么定位

先用症状做区分，能省掉大半排查时间。事件循环被阻塞的特征是：同 worker 内所有在途请求同时变慢，包括本来毫秒级返回的健康检查；p50 还正常而 p99 爆炸；单进程 CPU 打满但 QPS 不涨。如果是下游变慢，则只有依赖该下游的接口变慢，健康检查不受影响。这一条判据几乎可以直接定性。

可用的手段与判读方式：开 asyncio 调试模式（PYTHONASYNCIODEBUG=1 或 loop.set_debug(True)），超过 slow_callback_duration（默认 0.1 秒）的回调会打出告警日志，日志里的 Handle 就指向罪魁函数；用 py-spy dump --pid 抓活体栈，如果多个采样都停在同一个非 await 的帧上，比如某个同步 HTTP 客户端的 send 或数据库驱动的 execute，那就是同步调用被写进了 async def；py-spy 加 --native 才能看到 C 扩展里的栈，纯 Python 栈会显示成一行看不出问题。另外用 faulthandler.dump_traceback_later 定时转储，对偶发卡死比事后看日志有效得多。

# 事件循环延迟探针：跑在应用里，直接暴露成指标
import asyncio, faulthandler, logging, signal, time

log = logging.getLogger("loop")

async def loop_lag_monitor(interval: float = 0.5, warn_ms: float = 100.0) -> None:
    """每 interval 秒睡一次，实际睡眠超出的部分就是调度延迟。
    延迟持续高于几十毫秒，说明有回调长时间不让出。"""
    while True:
        t0 = time.perf_counter()
        await asyncio.sleep(interval)
        lag_ms = (time.perf_counter() - t0 - interval) * 1000
        if lag_ms > warn_ms:
            log.warning("event loop lag %.1f ms", lag_ms)   # 接 Histogram 更好

def install_debug_hooks() -> None:
    # 给进程发 SIGABRT 即可转储所有线程栈，卡死时不必依赖外部工具
    faulthandler.enable()
    faulthandler.register(signal.SIGABRT, all_threads=True)
    # 偶发卡死用定时转储：超过 10 秒没取消就打栈，repeat 表示持续
    faulthandler.dump_traceback_later(10, repeat=True, exit=False)

# 启动时：asyncio.get_running_loop().set_debug(True) 会启用慢回调告警
# 运行中排查：py-spy dump --pid PID --native   查看真实卡点

修法按代价排序：能换异步驱动就换；不能换就把这类 handler 写成 def 交给框架线程池，或显式 asyncio.to_thread；但要记住框架的默认线程限流器是全局共享的固定令牌数，把大量阻塞调用丢进去只是把拥塞从事件循环搬到线程池，必须自己加信号量限流并设超时。CPU 密集型的活不要丢线程池，交给独立进程池或拆成单独服务。

❌
最容易踩的坑

1. 把 async def 当并发开关：Flask 的异步视图是每请求现起一个事件循环再关掉，请求之间没有共享调度，并发单元仍然是线程数。

2. 在 async def 里调同步客户端（requests、同步数据库驱动、time.sleep），故障面是整个 worker 的所有在途请求，而不只是当前请求。

3. 以为 gunicorn 的 timeout 是请求超时：异步 worker 下它只判心跳，一个跑十分钟的协程不会被重启，请求级超时必须自己设。

4. 用 2 × os.cpu_count() + 1 算 worker 数：容器里它返回宿主核数，直接 OOM 或被 CFS 限流；worker 数应由内存与 cgroup 配额决定。

5. 忘了下游连接数要乘以 worker 数，压测时先把数据库的 max_connections 打满，症状却像应用变慢。

6. 在模块顶层 create_engine 或建 Redis 客户端，配合 preload_app 后多个进程共用一个 socket，出现随机协议错乱和响应串包。

7. 开了 preload 还指望 HUP 热更新代码：应用在 master 里，HUP 只换 worker 不换代码，表现为「发布了但没生效」。

8. 用 ps 的 RSS 之和评估 preload 的内存收益：共享页被重复计入，要看 smaps_rollup 的 Pss。

9. 混淆 gunicorn 与 nginx 的信号约定：gunicorn 的 TERM 是优雅退出、QUIT 是快停，nginx 正好相反。

10. 容器 CMD 写成 shell 形式，PID 1 是 shell 不转发信号，优雅退出永远不触发，每次发布都是硬杀。

11. 不配 preStop 等待：摘除 endpoint 与发送 TERM 是并发的，排空期间仍在收新流量，滚动发布必然出现少量 502。

12. 应用 keepalive（默认 2 秒）小于 nginx 上游空闲超时（默认 60 秒），代理复用已被关闭的连接，产生无规律 502；也不要指望 sync worker 支持 keep-alive。

13. max_requests 不配 jitter，所有 worker 同时重启，监控上是整齐的周期性延迟尖刺。
