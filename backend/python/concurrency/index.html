Python 并发编程

🏷️ Python

💡 你想写个脚本自动处理重复工作，或者快速搭个小服务。语法简单，库又多，写起来快。

概述：三种并发范式，一个核心矛盾

Python 的并发不是"选线程还是选进程"这么简单，而是要在开销、并行能力、编程模型之间做权衡。多线程受 GIL 限制但轻量；多进程真并行但贵；asyncio 单线程调度协程，高并发 IO 场景资源最省。选错模型，轻则白忙活，重则死锁。

我踩过的坑：早年写一个爬虫，用 100 个线程跑得好好的，后来加了个同步数据库写入，结果整个程序卡死。查了半天才发现——数据库写入是阻塞操作，把 GIL 占住了，其他线程全在等。后来把数据库写入改成异步队列，问题才解决。异步代码里绝对不能出现阻塞调用。

进程 vs 线程 vs 协程

模型并行能力切换开销通信成本适用场景
多线程 threading受 GIL 限制（CPU 密集不行）小共享内存，需锁IO 密集、少量并发
多进程 multiprocessing真多核并行大（fork/序列化）IPC / 管道，pickle 开销CPU 密集
协程 asyncio单线程协作式极小（用户态）同线程，无锁高并发 IO（上万连接）

多线程 threading 与 GIL 影响

IO 等待时 GIL 自动释放，所以多线程对网络请求、文件读写有效。但共享可变状态必须加锁：

import threading

counter = 0
lock = threading.Lock()

def worker():
    global counter
    for _ in range(1_000_000):
        with lock:          # 不加锁会因竞态丢更新
            counter += 1

threads = [threading.Thread(target=worker) for _ in range(4)]
[t.start() for t in threads]
[t.join() for t in threads]
print(counter)

counter += 1 看似原子，实际是"读-改-写"三条字节码，线程切换时就会丢更新。这就是竞态条件，不是 GIL 的问题。

多进程 multiprocessing 与 ProcessPoolExecutor

CPU 密集型任务必须绕开 GIL。concurrent.futures.ProcessPoolExecutor 是最省心的入口：

from concurrent.futures import ProcessPoolExecutor

def cpu_heavy(n):
    return sum(i * i for i in range(n))

if __name__ == "__main__":   # 多进程必须有此保护
    with ProcessPoolExecutor(max_workers=4) as pool:
        results = list(pool.map(cpu_heavy, [10_000_000] * 4))
    print(sum(results))

进程间不能直接共享内存，数据要 pickle 序列化传递——所以任务要"独立、数据量可分块"。需要频繁通信时优先考虑多线程或共享内存。

asyncio 深度：事件循环 / 协程 / Task / Future

flowchart LR LOOP[事件循环] --> |调度| T1[协程A] LOOP -->|等待IO挂起| T2[协程B] T1 -->|await IO| WAIT[让出控制权] WAIT --> LOOP T2 -->|IO就绪| LOOP LOOP -->|恢复| T1

事件循环是大脑，协程是任务单元，Task 是调度单位，Future 是异步结果占位。3.11+ 的 asyncio.TaskGroup 提供结构化并发：

import asyncio, httpx

async def fetch(client, url):
    resp = await client.get(url)
    return url, resp.status_code

async def main():
    async with httpx.AsyncClient() as client:
        async with asyncio.TaskGroup() as tg:   # 任一失败自动取消其余
            tasks = [tg.create_task(fetch(client, u))
                     for u in ["https://example.com"] * 5]
        for t in tasks:
            print(t.result())

asyncio.run(main())

异步生态的铁律：事件循环里不能出现阻塞调用。在 async 函数里调 time.sleep() 或同步 requests.get() 会卡住整个事件循环，必须用 asyncio.sleep() 和 httpx.AsyncClient。

并发选型决策树

flowchart TD Q1{任务性质?} --> |CPU 密集| P[多进程 ProcessPoolExecutor] Q1 -->|IO 密集| Q2{并发量级?} Q2 -->|几十~几百| T[多线程 ThreadPoolExecutor] Q2 -->|数千上万连接| A[asyncio + 异步库] A -->|混合阻塞| M[线程池兜底 run_in_executor]

常见坑：死锁 / 竞态 / 异步阻塞调用

# 死锁示例：两个线程以相反顺序拿锁
import threading
lock_a, lock_b = threading.Lock(), threading.Lock()

def task1():
    with lock_a:
        with lock_b: pass
def task2():
    with lock_b:
        with lock_a: pass   # 顺序相反，互相等待

死锁的预防靠"一致的加锁顺序"。竞态靠锁或原子操作。异步阻塞则要把同步库丢进线程池：

async def sync_blocking_in_async():
    loop = asyncio.get_running_loop()
    # 把阻塞的 requests.get 丢线程池，不卡住事件循环
    await loop.run_in_executor(None, blocking_request_get, url)

最佳实践

  • CPU 密集 → ProcessPoolExecutor；IO 密集低并发 → ThreadPoolExecutor；高并发 IO → asyncio。
  • 多进程入口必须 if __name__ == "__main__"，否则 Windows/macOS fork 会递归创建子进程。
  • 共享可变状态加锁，且保持全局一致的加锁顺序以防死锁。
  • async 里只用异步库；不得不调同步阻塞代码时用 run_in_executor。
  • 用 TaskGroup 管理一组协程，异常自动传播、任务自动取消。

FAQ

Q1：为什么多线程跑满不了 CPU 核？
GIL 保证同一时刻只有一个线程执行字节码，CPU 密集任务无法并行，反而因切换变慢。真并行请用多进程或 free-threaded 构建。

Q2：asyncio 比多线程快在哪？
它避免了内核线程切换和 GIL 竞争，在用户态调度协程，单个进程能扛上万并发连接，内存占用远低于"每连接一线程"。

Q3：什么时候该用 run_in_executor？
当你必须在异步代码里调用一个本身就是阻塞的同步库（如老版本 requests、CPU 密集计算）时，把它丢给线程池/进程池，别直接 await 一个同步函数。

总结

并发选型的本质是"按任务性质和并发量级选模型"：CPU 密集用进程，IO 密集按量选线程或协程。真正的坑不在模型本身，而在共享状态忘了加锁、异步循环里塞了阻塞调用、多进程漏了主模块保护。下一篇把视线从运行时转向工程化——怎么用工具链把这些代码管起来。
