Python 包管理与工程化

🏷️ Python

概述：Python 工程化的痛点与 2026 解法

Python 的包管理长期被诟病：pip 解析慢、requirements.txt 不锁传递依赖、venv/conda/pip 混用。我 2023 年带团队时还在手动维护 requirements.txt 和 venv，2024 年全面切到 uv 之后，装包速度从分钟级降到秒级。2026 年生态已经收敛到一套现代范式——pyproject.toml 作单一事实源 + uv 极速装包 + 锁文件复现。这篇把虚拟环境、包管理演进、配置标准、代码质量工具链一次讲清。

虚拟环境：隔离是第一原则

每个项目一个独立环境，绝不往系统 Python 装项目依赖。标准库 venv 最通用，conda 适合科学计算（能管系统级 C 库/CUDA）：

# 标准 venv
python3 -m venv .venv
source .venv/bin/activate      # Windows: .venv\Scripts\activate
pip install -r requirements.txt
deactivate

# 2026 推荐：uv 一键创建并管理
curl -LsSf https://astral.sh/uv/install.sh | sh
uv venv && source .venv/bin/activate
uv pip install fastapi uvicorn

永远不要在全局 Python 里 pip install 项目依赖。全局只装 CLI 工具，且建议用 pipx（隔离安装命令行工具）。

包管理演进：pip → pip-tools → Poetry → uv

工具定位优点短板
pip + requirements.txt最基础零学习成本不锁传递依赖、解析慢、冲突靠人肉
pip-toolspip 的锁定增强compile 出精确版本树仍需手动管 venv
Poetry依赖+打包一体pyproject.toml、poetry.lock、依赖解析强Rust 化前速度一般
uvpip 兼容的极速重写Rust 实现、比 pip 快 10–100 倍、自带 venv 与锁文件较新，团队需熟悉

pyproject.toml 详解（PEP 517 / 518 / 621）

flowchart LR PEP518[PEP 518 构建依赖] --> PEP517[PEP 517 构建后端接口] PEP621[PEP 621 项目元数据] --> PEP517 PEP517 --> HATCH[hatchling / setuptools 构建] HATCH --> WHEEL[.whl 发布 PyPI]

pyproject.toml 是现代 Python 项目的单一配置源：声明构建后端、项目元数据、依赖与开发依赖。一个典型配置如下：

[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"

[project]
name = "myapp"
version = "0.1.0"
requires-python = ">=3.12"
dependencies = [
    "fastapi>=0.110",
    "uvicorn>=0.29",
    "pydantic>=2",
]

[dependency-groups]
dev = ["pytest", "ruff", "mypy"]

依赖锁定靠锁文件复现：uv 生成 uv.lock、Poetry 生成 poetry.lock，记录每一个直接与传递依赖的精确版本和哈希。

# uv 工作流：声明依赖 → 锁定 → 复现
uv add requests
uv lock            # 生成 uv.lock
uv sync            # 按 lock 精确还原环境

代码质量工具链：ruff / mypy / pytest

2026 年 lint 与格式化已收敛到 ruff（Rust 实现，整合 flake8 + isort + black），类型检查用 mypy/pyright，测试用 pytest：

# ruff：检查 + 格式化，一条命令
pip install ruff
ruff check .          # lint
ruff check --fix .    # 自动修复
ruff format .         # 格式化

# mypy 静态类型检查
pip install mypy
mypy src/

# pytest 测试
pip install pytest
pytest -v

# tests/test_sample.py
def inc(x):
    return x + 1

def test_inc():
    assert inc(3) == 4

打包发布与 Python 版本管理

发布物用 Wheel（.whl）而非源码包：安装快、不需编译工具链、不执行任意 setup.py。版本管理用 pyenv / asdf 切换多版本解释器：

# 构建并发布到 PyPI
uv build            # 产出 dist/*.whl 与 *.tar.gz
uv publish          # 上传（需配置 token）

# pyenv 管理多版本
pyenv install 3.13.0
pyenv local 3.13.0  # 写入 .python-version，进入目录自动切换

Wheel 是 zip 包，把 .whl 改后缀 .zip 即可解压查看内部结构。生产环境用锁文件 + wheel 安装，跳过现场编译。

最佳实践

  • 新项目直接 uv init，pyproject.toml 声明依赖，提交锁文件。
  • CI 与生产一律 uv sync / pip install -r requirements.txt 复现锁定环境，禁止"我机器上能跑"。
  • 一个项目只用一套包管理工具，不要 pip 与 conda 混用。
  • pre-commit 钩子里挂 ruff + mypy，提交即检查。
  • 用 pyenv/asdf 管理 Python 版本，远离系统 Python。

FAQ

Q1：pyproject.toml 和 setup.py 还要同时维护吗？
不需要。PEP 621 把项目元数据收进 pyproject.toml，现代后端（hatchling / setuptools 61+）不再需要手写 setup.py。

Q2：uv 和 Poetry 二选一吗？
可以混用：用 Poetry 管理元数据与锁，用 uv 加速安装；也可以全量用 uv（uv 原生支持 pyproject.toml 与 dependency-groups）。团队保持一致即可。

Q3：requirements.txt 还有用吗？
作为最简交付仍可用，但它不记录依赖关系与哈希，复现力弱。新项目优先锁文件方案。

总结

工程化的目标是"可复现、可维护"：虚拟环境隔离、pyproject.toml 声明依赖、锁文件复现、ruff/mypy/pytest 守住质量门。工具链演进的方向始终是更快、更统一——2026 年 uv + ruff 已经把这套体验拉到接近前端 npm 的顺滑。下一篇进入 Web 开发，看这些工程实践如何落地到框架与部署。
