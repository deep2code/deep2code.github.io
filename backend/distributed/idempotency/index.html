幂等的完整工程实现

🏷️ 幂等

幂等的四种落地方式（唯一索引、Token、状态机、去重表）以及它们的取舍，分布式系统主干篇已经列成对照表，本篇不重复。这里给的是一套完整可上线的方案：键怎么设计、记录表怎么建、并发下为什么正确、崩溃在中间怎么办、响应怎么回放、记录什么时候清。幂等出事故几乎都不是因为不知道有哪几种方式，而是因为某个细节缺了一块。

先厘清边界：幂等、去重、并发安全是三件事

「接口幂等」这个词在团队里经常指代三种不同的东西，讨论方案前必须先对齐。它们的判定标准、实现手段、失效表现都不一样：

概念准确定义判定标准实现手段不解决什么
幂等同一请求执行一次或多次，系统最终状态相同比对多次执行后的数据状态幂等键加唯一约束、条件更新不保证只执行一次，也不保证并发请求互不干扰
去重识别并丢弃重复的消息或请求看是否出现第二次处理消费位点、去重表、布隆过滤器前置不保证漏掉的那次业务被正确处理，也无法回放结果
并发安全多个不同请求同时操作同一份数据时结果正确并发压测后数据是否守恒行锁、条件更新、乐观锁版本号完全不解决重复提交问题

两个最常见的混淆值得单独点出。第一，幂等不等于「只执行一次」：转账接口可能真的执行了两次数据库操作（第二次因唯一键冲突回滚），但最终余额只变了一次，这就是幂等。追求严格的恰好一次执行在分布式环境里代价极高且通常不必要。第二，幂等不等于并发安全：给下单接口加了幂等键，两个不同用户抢同一件库存照样会超卖，那是库存扣减的原子性问题，要用条件 UPDATE 解决，跟幂等无关。这两个问题必须分别设计、分别验证。

💡
键的推荐结构

存储时把键规范化成 {tenant}:{userId}:{api}:{clientKey} 这种带命名空间的形式，而不是直接存客户端传来的裸串。好处有三个：天然隔离用户与接口，避免碰撞；排查时一眼能看出这条记录属于谁的哪个接口；将来做分库分表可以直接按前缀路由。

服务端完整流程：抢占、执行、快照、回放

完整流程有三条路径要覆盖：首次请求、重复请求、以及抢占成功但执行中崩溃。第三条是绝大多数实现漏掉的那条。

sequenceDiagram autonumber participant C as 客户端 participant S as 服务端 participant DB as 数据库 Note over C: 首次请求，携带自己生成的幂等键 C->>S: 提交请求，Idempotency-Key 头 S->>DB: 插入幂等记录，状态为处理中 DB-->>S: 插入成功，抢占到执行权 S->>DB: 执行业务，与状态更新同一事务 S->>DB: 回写状态为已完成，保存响应快照 S-->>C: 200 与业务结果 Note over C: 客户端超时重发，实际首次已成功 C->>S: 同一幂等键重发 S->>DB: 插入幂等记录 DB-->>S: 唯一键冲突 S->>DB: 按键读取记录 DB-->>S: 状态已完成，带响应快照 S-->>C: 原样回放首次响应，仍是 200
stateDiagram-v2 [*] --> Processing: 抢占成功（唯一键插入） Processing --> Done: 业务成功，写入响应快照 Processing --> Failed: 业务明确失败，允许重新执行 Processing --> Processing: 同键请求到达，返回 409 让稍后重试 Failed --> [*]: 记录删除或标记，键可再次使用 Done --> Done: 同键请求命中，回放响应快照 Done --> [*]: 超过保留期被归档清理 note right of Processing 进程在这里崩溃是最危险的情况 记录永久停在处理中，键被锁死 必须有巡检任务查业务真实状态并收尾 end note

注意状态机里「处理中」收到同键请求时返回 409 而不是放行。放行会导致两个后果：要么两个请求并发执行同一业务（幂等键根本没起作用），要么第二个请求在第一个提交前读到旧状态做出错误判断。返回 409 并带上 Retry-After，把重试决策交给调用方，是唯一安全的选择。

CREATE TABLE `idempotency_record` (
  `id`            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `idem_key`      VARCHAR(160) NOT NULL COMMENT '规范化后的键：租户:用户:接口:客户端键',
  `state`         TINYINT      NOT NULL COMMENT '0 处理中 1 已完成 2 已失败',
  `request_hash`  CHAR(64)     NOT NULL COMMENT '请求体摘要，用于识别同键不同参的误用',
  `resp_status`   INT          NULL COMMENT '首次响应的 HTTP 状态码',
  `resp_body`     VARCHAR(4000) NULL COMMENT '响应快照，过大时只存关键字段',
  `biz_no`        VARCHAR(64)  NULL COMMENT '业务单号，便于按单号反查',
  `locked_at`     DATETIME(3)  NOT NULL COMMENT '抢占时间，巡检超时依据',
  `expire_at`     DATETIME(3)  NOT NULL COMMENT '保留期，必须大于调用方最长重试窗口',
  `created_at`    DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  PRIMARY KEY (`id`),
  -- 整套方案的正确性基石：并发插入只有一个能成功
  UNIQUE KEY `uk_idem_key` (`idem_key`),
  KEY `idx_state_locked` (`state`, `locked_at`),
  KEY `idx_expire` (`expire_at`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='幂等记录表';

@Service
public class IdempotentExecutor {

    // 业务最长执行时长的若干倍，超过即认为抢占者已死
    private static final long STALE_MILLIS = 60_000;

    public <T> Response<T> execute(IdemContext ctx, Supplier<Response<T>> action) {
        String key = ctx.normalizedKey();   // 租户:用户:接口:客户端键
        String hash = ctx.requestHash();

        // 第 1 步：靠唯一索引抢占。这里绝不能写成「先 SELECT 判断再 INSERT」，
        // 并发下两个请求都会查到不存在，然后都执行业务。
        try {
            recordMapper.insertProcessing(key, hash, ctx.expireAt());
        } catch (DuplicateKeyException e) {
            return replayOrReject(key, hash);
        }

        // 第 2 步：执行业务，并在同一个本地事务里把状态与响应快照写回。
        // 分成两个事务会出现业务成功但快照没落库，重试时只能返回 409。
        try {
            Response<T> resp = txTemplate.execute(st -> {
                Response<T> r = action.get();
                recordMapper.markDone(key, r.getStatus(),
                        json.write(r), r.getBizNo());
                return r;
            });
            return resp;
        } catch (BizException e) {
            // 业务明确失败（如余额不足）：标记失败，允许同键重新执行。
            // 注意只有「确定没有产生任何副作用」的失败才可以这样处理。
            recordMapper.markFailed(key);
            throw e;
        } catch (RuntimeException e) {
            // 未知异常：状态可能已变更，不能标记失败放行，留给巡检判定
            log.error("idem execute unknown error, key={}", key, e);
            throw e;
        }
    }

    private <T> Response<T> replayOrReject(String key, String hash) {
        IdemRecord r = recordMapper.selectByKey(key);
        if (r == null) {
            // 极罕见：刚好被清理任务删掉，让调用方重试
            throw new RetryableException("idempotency record vanished");
        }
        if (!r.getRequestHash().equals(hash)) {
            // 同键不同参：调用方复用了幂等键，属于误用，必须显式报错而不是静默回放
            throw new BadRequestException("idempotency key reused with different payload");
        }
        switch (r.getState()) {
            case DONE:
                // 关键：原样回放首次响应，状态码也一并复原
                return json.read(r.getRespBody(), r.getRespStatus());
            case FAILED:
                throw new BizException("previous attempt failed, submit a new request");
            default:
                // 处理中：返回 409 让客户端稍后重试，绝不放行执行
                throw new ConflictException("request in progress", Duration.ofSeconds(2));
        }
    }

    // 巡检：处理中超时的记录必须收尾，否则这个幂等键被永久锁死
    @Scheduled(fixedDelay = 30_000)
    public void sweepStale() {
        for (IdemRecord r : recordMapper.scanStale(STALE_MILLIS, 200)) {
            BizState real = bizQuery.query(r.getIdemKey()); // 查业务侧真实状态
            if (real == BizState.SUCCESS) {
                recordMapper.markDoneFromSweep(r.getIdemKey(), real.snapshot());
            } else if (real == BizState.ABSENT) {
                recordMapper.deleteByKey(r.getIdemKey());   // 未生效，放开键
            } else {
                alarm.fire("idem_stale_unknown", r.getIdemKey()); // 无法判定，人工介入
            }
        }
    }
}
⚠️
同键不同参必须报错

调用方有时会图省事复用幂等键，比如把用户 ID 当键。如果服务端不校验请求摘要，第二个内容完全不同的请求会拿到第一个请求的响应，表现为「我改了 A 却返回 B 的结果」，排查起来极其困难。加一个 request_hash 比对，遇到不一致直接返回 400 并说明原因。

为什么必须回放首次响应

很多实现在检测到重复请求后返回「重复提交」错误码，这是一个后果被严重低估的设计缺陷。调用方拿到错误会走它自己的失败分支：

重复请求的返回调用方行为最终结果
返回业务错误码「重复提交」判定本次调用失败，回滚本地状态或发起补偿服务端已成功、上游认为失败，产生不一致，资金场景直接变成重复退款
返回 500继续重试，重试又拿到 500无限重试打满链路，最终人工介入
返回 409 且带重试提示稍后重试可接受，但仅适用于「确实还在处理中」
回放首次响应快照与首次成功完全一致地继续后续流程正确：重试多少次上游都看到同一个成功结果与同一个业务单号

快照里必须包含业务单号。上游经常拿返回的单号去做后续调用（查询、发货、对账），如果回放的响应缺了单号，上游会走到空指针或重新下单的分支。响应体过大时可以只存关键字段并在回放时重新组装，但不能退化成「只返回成功标志」。

先查后插为什么不是幂等，以及唯一索引冲突的正确处理

「先 SELECT 看有没有，没有就 INSERT」是最普遍的错误实现。两个请求在同一时刻都查到不存在，于是都插入，两条重复数据。这个窗口只有几毫秒，但在生产高峰期会稳定复现——而且加上事务也没用，常规隔离级别下两个事务的查询都看不到对方未提交的插入。

-- 错误：判断与写入之间存在窗口，并发下必然重复
SELECT id FROM orders WHERE out_trade_no = 'X202609230001';
-- 两个连接都返回空
INSERT INTO orders (out_trade_no, ...) VALUES ('X202609230001', ...);
-- 两条订单都插进去了

-- 正确写法一：直接插入，靠唯一索引拦截，捕获冲突走重复分支
-- 前提：ALTER TABLE orders ADD UNIQUE KEY uk_out_trade_no (out_trade_no);
INSERT INTO orders (out_trade_no, user_id, amount, status)
VALUES ('X202609230001', 1001, 5000, 'UNPAID');
-- 冲突时报 Duplicate entry，应用层捕获后查出已有记录并回放

-- 正确写法二：状态流转类用条件 UPDATE，靠受影响行数判定
UPDATE orders
   SET status = 'PAID', paid_at = NOW(3)
 WHERE order_id = 88001 AND status = 'UNPAID';
-- 受影响行数 1 = 本次流转生效；0 = 已被处理过或状态不匹配，直接返回成功

-- 正确写法三：余额增减用流水表唯一键先占位，再更新余额
INSERT INTO balance_ledger (biz_id, user_id, delta, direction)
VALUES ('refund:88001', 1001, 5000, 'IN');   -- uk(biz_id) 冲突即为重复
UPDATE account SET balance = balance + 5000 WHERE user_id = 1001;
-- 两条语句放在同一本地事务里，流水是幂等凭据，余额变更靠行锁保证并发安全

捕获唯一键冲突时有两个细节要注意。其一，不要用异常信息里的字符串匹配判断是哪个索引冲突，不同数据库版本的错误文本不一样；应该给每张表的关键唯一索引单独设计键名，并通过驱动提供的错误码（MySQL 1062）配合索引名判断。其二，唯一键冲突会消耗自增 ID，InnoDB 的自增值在冲突前已经分配，所以订单号跳号是正常现象，不要因为跳号去排查数据丢失。

创建订单 / 创建用户业务唯一键加唯一索引直接 INSERT，捕获 1062 后查出已有记录回放用先查后插；唯一索引建在可空列上（NULL 不参与唯一约束）

过期与清理：早了和晚了都出问题

业务类型建议保留期依据清理方式
资金交易（支付、退款、转账）3 到 12 个月覆盖人工重放、对账补发与争议处理周期按月分区，过期分区归档后 DROP
订单、履约类30 到 90 天覆盖售后与客诉窗口按天分区，过期分区直接 DROP
一般写接口7 天远大于客户端重试窗口（通常分钟级）按天分区或定时分批删
高频轻量接口（点赞、埋点）几小时重复的业务影响极小Redis 键过期即可，数据库不留
❌
清理过早的具体后果

调用方的重试不一定在几秒内。对账补发、人工重放、离线任务重跑都可能在几小时甚至几天后用同一个幂等键再发一次。如果记录已被清理，这次请求会被当成全新请求执行——表现为「一笔退款隔了三天又退了一次」。保留期必须按所有调用方的最长重试窗口来定，而不是按存储成本来定。

Redis 做幂等只能当前置优化

用 SET key value NX EX seconds 做幂等拦截，性能好、实现简单，但它有三个无法回避的失效点，所以只能当第一道过滤，不能当最终保证：

失效点触发条件表现兜底手段
主从异步复制丢键主节点宕机，未复制的写随之丢失切换后同键请求被放行，业务执行第二次数据库唯一索引拦截
键过期超期重试、对账补发被当成全新请求数据库记录保留期覆盖最长重试窗口
内存淘汰内存吃紧触发 allkeys-lru 逐出键提前消失，幂等失效幂等键放独立实例并用 noeviction，同时靠数据库兜底
# Redis 前置拦截：原子写入 + 过期时间。NX 保证并发只有一个成功。
# 返回 OK = 抢到执行权；返回空 = 重复请求，转去数据库查结果回放。
redis-cli SET "idem:t1:u1001:pay:CK-20260923-001" "PROCESSING" NX EX 3600

# 排查幂等失效时的三个必看指标
redis-cli info replication | grep -E "role|master_link_status|slave_repl_offset"
redis-cli info stats      | grep -E "expired_keys|evicted_keys"
redis-cli info memory     | grep -E "used_memory_human|maxmemory_policy"

# 判读要点：
#   evicted_keys 持续增长        -> 内存不足在逐出，幂等键可能被删，必须换 noeviction 或扩容
#   maxmemory_policy 非 noeviction -> 幂等键有被淘汰风险
#   master_link_status 不是 up    -> 复制断开，切换会丢键
✅
正确的分层

Redis 决定快不快，数据库决定对不对。绝大多数重复请求在 Redis 层就被挡掉，不会触达数据库；少数漏过去的由数据库唯一索引保证不出错。反过来只用数据库也能正确工作，只是重复请求会在冲突时浪费一次事务。

反模式清单

反模式为什么出现实际后果正确做法
服务端按请求内容生成幂等键不想改客户端用户连续发起两笔合法的相同请求，第二笔被静默吞掉幂等键由客户端生成并在重试时原样携带
先查后插直觉上最自然的写法并发窗口内产生重复数据，高峰期稳定复现唯一索引加冲突捕获，或条件 UPDATE 加受影响行数
重复请求返回错误码认为重复就该报错上游判定失败并补偿，产生业务不一致回放首次响应快照，含业务单号
不处理「处理中」状态没想过抢占后会崩溃幂等键被永久锁死，该业务再也无法执行处理中返回 409，并用巡检任务查业务真实状态收尾
幂等记录永不清理担心清理引发重复执行表无限膨胀，唯一索引变慢，拖累主链路按业务分层设保留期，用分区归档清理
只用 Redis 不做数据库兜底追求性能，认为 Redis 够可靠主从切换或键被淘汰时幂等直接失效，且发生在系统最脆弱的时刻Redis 前置拦截，数据库唯一索引兜底
同键不同参不校验没想到调用方会复用键请求 B 拿到请求 A 的响应，跨请求数据串号比对请求摘要，不一致直接返回 400
把幂等当成并发安全两个问题都表现为「数据不对」加了幂等键仍然超卖、仍然余额算错并发安全另用条件更新或行锁解决，分别压测验证
❌
最容易踩的坑
  • 服务端用请求体哈希当幂等键：用户连续给同一主播打赏两次相同金额，第二次被判为重复吞掉，客诉时查不出任何异常日志。
  • 幂等键作用域是全局的：客户端用自增数字当键，不同用户撞到同一个键，A 拿到 B 的响应快照，属于数据泄露级别缺陷。
  • 先查后插并且以为加了事务就安全：常规隔离级别下两个事务的查询互相看不到未提交插入，照样双写。
  • 唯一索引建在可空列上：MySQL 的 NULL 不参与唯一性判定，多行 NULL 可以共存，幂等直接失效。
  • 业务执行与状态回写分成两个事务：业务成功但快照没落库，后续重试永远拿到 409，用户卡死在「处理中」。
  • 受影响行数为 0 当成失败抛异常：条件 UPDATE 返回 0 通常意味着已被处理过，抛异常会让上游无限重试。
  • 不处理抢占后崩溃：没有巡检任务，幂等键停在处理中永久锁死，同一笔业务再也提交不了。
  • 只更新余额不记流水：重复请求无从识别，对账时也无法追溯每一次变动的来源。
  • 幂等记录保留期短于调用方重试窗口：对账补发在三天后用同一键再发一次，被当成新请求，钱退了两遍。
  • 幂等键与业务键放在同一个 Redis 实例且开了 LRU 淘汰：内存吃紧时幂等键被逐出，幂等在最需要它的时刻失效。
  • 在 GET 接口里写数据：让天然幂等的查询变得不幂等，浏览器预取、爬虫、重试都会触发副作用。
  • 只做前端按钮防抖就认为解决了：网络重试、客户端崩溃重发、网关重试都绕过前端，服务端幂等不可省。
