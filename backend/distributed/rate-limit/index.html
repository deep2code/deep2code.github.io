限流实战：别让突发流量打垮系统

🏷️ 限流

大促来了，流量突然翻 10 倍，系统直接崩了。限流就是提前设好阈值，超过了就拒绝一部分请求，保住核心系统。这篇讲常见限流算法和实战方案。

flowchart LR A[请求进来] --> B{是否限流?} B -->|是| C[排队/拒绝] B -->|否| D[正常处理] C --> E[返回降级] C --> F[排队等待]

大促系统直接崩了

⚠️
你遇到的问题

搞个活动，流量突然翻 10 倍，数据库连接池打满，整个系统不可用。

怎么解决？在网关层加限流，超过阈值就直接返回"系统繁忙"，保住核心服务。

# Nginx 限流
limit_req zone=api burst=10 nodelay;

# Redis 令牌桶
SET rate_limit:user:123 10 EX 60

限流太严，正常用户也被拒了

⚠️
你遇到的问题

设了 QPS 1000，结果正常流量高峰期也被限流，用户投诉。

怎么解决？用滑动窗口或令牌桶，更平滑，不会像固定窗口那样突刺。

# 固定窗口问题：1 秒 1000
# 0.9s 来 1000，1.1s 来 1000，2 秒 2000
# 滑动窗口就平滑多了

常见限流算法对比

算法 原理 优点 缺点 适用场景
固定窗口 按时间窗口计数 简单 临界点突刺 简单接口限流
滑动窗口 窗口滑动统计 平滑 实现稍复杂 大多数场景
令牌桶 匀速放令牌，请求拿令牌 允许突发 实现复杂 网关限流
漏桶 请求进水桶，匀速流出 绝对平滑 不允许突发 保护下游

新手最容易踩的坑

❌
避坑指南
  • 限流要分层：网关层粗限流，应用层细限流，别只在一层做
  • 被限流了要友好提示，别直接返回 500，用户体验好点
  • 限流阈值要压测出来，别拍脑袋设，先压测看系统极限再设
  • 核心接口和非核心接口分开限流，非核心的可以限严点
