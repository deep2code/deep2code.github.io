一致性模型的工程含义：从线性一致到会话保证

🏷️ CAP

CAP 三个字母的正确读法、PACELC 对正常态延迟的补充、以及一致性强度谱系的整体排布，分布式系统主干篇已经讲过，本篇不重复。这里只做一件事：把谱系表上的每一档落到实现层——它在真实系统里长什么样、用什么机制实现、怎么验证它真的成立、运维上要付出什么代价。一致性模型之所以难，不是因为定义拗口，而是因为定义和代码之间隔着一层没人讲的工程细节。

线性一致性在真实系统里只有三种实现路径

线性一致性的工程含义是：任何一次读，必须能看到在它开始之前已经成功返回的所有写。注意这里的约束是实时顺序，而不是「逻辑上说得通」。要满足它，实现上只有三条路：所有读写都经过唯一一个决策点、读经过一轮共识确认、或者靠一个有时限的授权把决策点缓存下来。

flowchart TB subgraph S1["路径一：单主承载读写"] A1["客户端"] --> A2["主节点（唯一决策点）"] A2 --> A3["从节点（只做备份，不接读）"] end subgraph S2["路径二：ReadIndex 读确认"] B1["客户端"] --> B2["Leader 记录当前 commitIndex"] B2 --> B3["向多数派发心跳确认仍是 Leader"] B3 --> B4["等本地 applyIndex 追上 commitIndex"] B4 --> B5["返回状态机快照读"] end subgraph S3["路径三：Lease Read"] C1["Leader 持有租约（election timeout 内）"] --> C2["租约期内跳过心跳往返"] C2 --> C3["直接本地读，延迟降到微秒级"] C3 --> C4["代价：依赖时钟漂移有界"] end

三条路的差异全在代价上。单主读最简单，但主节点承载全部读流量，扩容只能靠垂直加机器；ReadIndex 每次读多一轮到多数派的心跳（同机房约 0.5 到 2 毫秒，跨机房 30 毫秒以上），但正确性不依赖时钟；Lease Read 把心跳省掉，代价是把正确性押在时钟漂移不超过某个界上——这是 etcd 默认开启而 TiKV 允许关闭的原因，也是虚拟机大幅时钟跳变时会出现幽灵读的根源。

实现路径额外延迟读扩展性依赖假设失效场景
单主承载读写0不可扩展，主库是瓶颈只需正确的主选举主库 CPU 或连接数打满，读写一起雪崩
Follower Read + ReadIndex一轮多数派心跳，1 到 30 毫秒可线性扩展到所有副本无时钟假设网络抖动时读延迟直接翻倍
Leader Lease Read接近 0只有 Leader 能读时钟漂移小于租约余量VM 挂起恢复、NTP 跳变导致旧 Leader 仍认为持租约
从库读 + 不加任何保证0最好无根本不是线性一致，只是「大概率新」

怎么验证线性一致：Jepsen 的思路

大部分人对一致性的「验证」是写几个用例跑一遍，观察结果对不对。这种做法证明不了任何东西：线性一致性的违反只在并发加故障的窗口里出现，而人工用例既不够并发也不会注入故障。

Jepsen 的方法可以拆成三步。第一步，多个客户端并发读写，把每个操作的调用时刻、返回时刻、结果三元组记录成一份历史。第二步，在过程中注入分区、进程暂停（SIGSTOP）、时钟偏移、节点重启。第三步，把历史交给线性化检查器，尝试寻找一个满足实时约束的串行顺序——找不到就是违反。

这里最容易被误解的是超时的操作不能当成失败。一个写请求超时了，它可能已经在服务端生效，所以在历史里必须标成「结果未知」，检查器会同时考虑生效和未生效两种可能。很多自研系统的一致性测试直接把超时算失败，于是永远测不出问题。

⚠️
「看起来没问题」不等于线性一致

违反线性一致的典型窗口只有几十毫秒：旧主还没意识到自己被降级，仍在应答读请求。稳态压测一万次都不会命中，必须主动分区才能复现。所以任何声称强一致的自研组件，没有在注入故障的并发历史上做过线性化检查，就只能算「没测过」。

会话保证四件套：本篇最值钱的一节

线性一致代价高，而绝大多数业务真正需要的是会话级别的保证。会话保证有四条，工程上各自有明确的实现手段和明确的运维代价。这张表是从需求到代码的直接映射：

保证业务含义用什么实现运维代价什么时候会破
读己之写
Read Your Writes		我改完立刻能看到我的修改写后把该用户的读固定打到主库，维持一段粘滞时间（取复制延迟 P99 的 2 到 3 倍，典型 500 毫秒到 3 秒）主库读流量上升；粘滞状态要放在网关或 Redis 里，多网关实例需共享粘滞时间短于实际延迟；用户换设备或切了另一个网关实例
单调读
Monotonic Reads		刷新页面不会看到数据倒退把同一会话固定路由到同一个副本（按 user_id 或 session_id 做一致性哈希）副本负载不均；副本故障时会话迁移仍会倒退一次副本下线重新路由；连接池随机选后端
单调写
Monotonic Writes		我的两次写按我发出的顺序生效同一会话的写走同一分区并串行化，或在应用层用版本号做条件更新会话内写无法并行；热点会话成瓶颈写被分散到不同分区；客户端并发发出两个写
读写跟随
Writes Follow Reads		基于我读到的状态做的写，不会被别人看成早于那个状态读时记下位点，写时把位点作为前置条件（CAS 或携带版本号）需要贯穿读写链路传递位点，改造面大中间任何一跳丢掉了位点

此外还有两种通用的位点机制，可以同时实现读己之写和单调读，代价比粘滞主库读小得多：

机制做法优点坑
服务端等位点写入返回 GTID / LSN，读请求携带它，从库先等追上再查主库零额外读压力，保证精确从库卡住时读请求会阻塞到超时，必须设上限并降级读主库
客户端缓存自己的写写成功后把新值在客户端缓存几秒，回显直接用缓存服务端零改造只能修「回显」，列表页、聚合统计、他人视角全都修不了

读己之写失败的真实时序，以及怎么修

这个 bug 的报告方式永远是「我改了保存成功，刷新一下又变回去了，过一会儿才对」。根因链条很短但很隐蔽：

用位点修复之后的时序，关键是把位点从写响应带到读请求，并且给等待设上限：

sequenceDiagram autonumber participant U as 浏览器 participant LB as 网关 participant M as 主库 participant S2 as 从库 B U->>LB: 提交修改昵称 LB->>M: 写入主库并取当前 GTID M-->>LB: 成功，返回位点 gtid LB-->>U: 200 OK，响应头带位点 U->>LB: 请求个人页，请求头回传位点 LB->>S2: 先等从库回放到该位点，最多等 1 秒 alt 1 秒内追上 S2-->>LB: 已追上，查询得到新昵称 else 超时未追上 S2-->>LB: 等待超时 LB->>M: 降级读主库，保证正确性 end LB-->>U: 始终看到自己的修改 
// 读己之写：写返回位点，读携带位点。核心是给等待设上限并降级，
// 否则从库一卡住，所有带位点的读都会挂在这里。
const waitTimeoutSec = 1

func (r *Repo) UpdateNick(ctx context.Context, uid int64, nick string) (string, error) {
    tx, err := r.master.BeginTx(ctx, nil)
    if err != nil {
        return "", err
    }
    defer tx.Rollback()
    if _, err = tx.ExecContext(ctx,
        "UPDATE user SET nick = ? WHERE id = ?", nick, uid); err != nil {
        return "", err
    }
    if err = tx.Commit(); err != nil {
        return "", err
    }
    // 提交后取已执行 GTID 集合，作为该会话的读位点下发给客户端
    var gtid string
    err = r.master.QueryRowContext(ctx,
        "SELECT @@GLOBAL.gtid_executed").Scan(&gtid)
    return gtid, err
}

func (r *Repo) GetNick(ctx context.Context, uid int64, gtid string) (string, error) {
    db := r.replica
    if gtid != "" {
        var ret int
        // 返回 0 表示已追上；返回 1 表示超时。注意这里绝不能不设超时，
        // 从库延迟一旦拉大会把所有读请求堵死在连接上。
        err := db.QueryRowContext(ctx,
            "SELECT WAIT_FOR_EXECUTED_GTID_SET(?, ?)", gtid, waitTimeoutSec).Scan(&ret)
        if err != nil || ret != 0 {
            db = r.master // 降级读主库，牺牲主库一点负载换正确性
        }
    }
    var nick string
    err := db.QueryRowContext(ctx, "SELECT nick FROM user WHERE id = ?", uid).Scan(&nick)
    return nick, err
}

排查这类问题时，先确认延迟量级再决定粘滞时间。Seconds_Behind_Master 的精度只有秒且在从库空闲时会误报 0，判断复制延迟应该同时看位点差：

# 1) 从库视角：Seconds_Behind_Master 只能粗看，NULL 表示复制已断
mysql -h replica -e "SHOW REPLICA STATUS\G" | grep -E \
  "Seconds_Behind_Master|Replica_(IO|SQL)_Running|Retrieved_Gtid_Set|Executed_Gtid_Set"

# 判读要点：
#   Replica_IO_Running / Replica_SQL_Running 任一为 No  -> 复制已断，延迟无意义
#   Retrieved_Gtid_Set 远大于 Executed_Gtid_Set        -> 日志已拉到但回放不过来，SQL 线程是瓶颈
#   两者接近但 Seconds_Behind_Master 很大              -> IO 线程拉取慢，通常是带宽或主库压力

# 2) 主库视角：直接比对位点差，比 Seconds_Behind_Master 可靠
mysql -h master -e "SELECT @@GLOBAL.gtid_executed"

# 3) Redis 复制延迟：看 master_repl_offset 与各 slave 的 offset 差值（字节）
redis-cli -h redis-master info replication | grep -E "master_repl_offset|slave[0-9]+"

最终一致的收敛机制：三种，代价差很远

最终一致不是「等一会儿就对了」，而是「必须有一个明确的收敛规则」。没有收敛规则的系统不是最终一致，是数据会永久分叉。

收敛机制原理元数据开销能否保住并发写适用与禁用
Last Write Wins比较时间戳，大的胜出每条记录一个时间戳不能，小时间戳的写被静默丢弃适合缓存、配置、可覆盖的用户资料；禁用于余额、库存、计数
向量时钟 / 版本向量每个副本维护一个计数器，能判定因果先后与真并发与副本数成正比，副本变动后需要裁剪能检出冲突，但解决冲突要交给应用层适合副本数固定且业务愿意处理冲突（如 Dynamo 风格的购物车合并）
CRDT把数据类型设计成操作可交换、可结合、幂等，天然收敛较大，删除通常要留墓碑能，所有并发写都被保留并合并适合计数器、集合、文本协同；无法表达「不能为负」这类全局约束

LWW 的时钟依赖是生产事故高发区：一个时钟快了 5 分钟的节点写入一次，后续 5 分钟内所有正常写入都会被判为旧值丢弃，且日志里完全没有异常。要用 LWW，时间戳至少应由服务端统一生成，并对节点间时钟偏差做监控告警。

CRDT 的边界也常被夸大。它能优雅解决点赞数、在线人数、标签集合、协同文档，但解决不了「库存不能为负」——因为判断是否为负需要一个全局视图，而 CRDT 的前提恰恰是不要全局协调。生产上正确的用法是局部使用：计数走 CRDT，订单和余额走数据库原子操作。

常见组件到底给了什么保证

选组件时真正该问的不是「它是 CP 还是 AP」，而是「它给我的读提供什么保证，读到旧数据的窗口有多大」：

组件默认读保证旧数据窗口量级能升级到更强吗
MySQL 主从（异步复制）读主库线性一致；读从库仅最终一致从库 1 毫秒到数十秒（大事务、DDL 时可到分钟级）读主库、半同步复制、或 GTID 等位点
Redis 主从最终一致，且故障切换会丢已确认的写通常几毫秒到几十毫秒WAIT 命令可等从库确认，但不解决脑裂丢写
Kafka分区内有序；消费者只能读到 HW 之前的数据取决于 ISR 同步，毫秒级acks=all 加 min.insync.replicas=2 保证已确认不丢
etcd / ZooKeeperetcd 默认线性一致读；ZK 读默认只保证顺序一致，需显式 syncetcd 约 0；ZK 读旧数据窗口可达秒级etcd 可选 serializable 换性能；ZK 调 sync 再读
S3 / 对象存储2020 年后新对象与覆盖写均为强一致读约 0（但列举操作与跨区复制仍是最终一致）跨区复制无法变强一致
DNS最终一致，受 TTL 与各级缓存支配TTL 到数小时（部分解析器忽略短 TTL）不能，只能提前降低 TTL
CDN最终一致缓存时长到刷新生效，分钟级主动刷新或带版本号的 URL
💡
ZooKeeper 的读不是强一致

这是流传最广的误解之一。ZooKeeper 的写走 ZAB 全局有序，但读直接由所连接的那台服务器本地应答，可能落后于最新提交。要拿到线性一致读，必须先调 sync 再读。很多「用 ZK 做分布式锁很安全」的方案，恰恰忽略了这一点。

把业务需求翻译成一致性级别

需求方说的话和一致性模型之间需要一层翻译。翻译错了，代价是几倍的基础设施成本：

需求原话真实含义正确方案错误做法与后果
「用户改完必须马上看到」读己之写粘滞主库几秒，或携带位点读从库所有读改成读主库，主库 QPS 翻数倍后打满
「不能超卖 / 不能透支」单行上的原子操作加约束带条件的 UPDATE 加检查受影响行数，由行锁保证分布式锁加先查后改，锁租约过期时照样超卖
「订单状态不能乱跳」单调写加状态机约束UPDATE 里写明前置状态，靠受影响行数判定先查状态再更新，并发下两个请求都通过检查
「报表能接受延迟」最终一致读从库或数仓，页面标明数据时间报表查主库，一条慢聚合拖垮线上
「多端数据要同步」单调读加读己之写按用户会话固定路由，写后带位点随机读副本，用户在两个设备上看到互相矛盾的数据
「配置改了要立刻生效」有界的最终一致加通知长轮询或 watch 推送，同时保留兜底轮询纯轮询 30 秒一次，故障时配置回滚速度不可控

反模式：这些做法比不做保证更糟

反模式为什么出现实际后果正确做法
为了「强一致」把所有读都指向主库把读己之写误解成全局强一致主库 CPU 与连接数打满，读写一起雪崩，从库空转只对写后短窗口内的读粘滞主库，其余读从库
用时间戳做冲突解决但不管时钟同步LWW 实现简单，看起来没问题时钟快的节点写入一次，后续正常写被静默吞掉时间戳服务端统一生成，监控节点间偏差，关键字段改用版本号 CAS
把最终一致的系统当强一致用测试环境延迟接近 0，看不出差别上线后在高峰期集中爆发，且无法稳定复现压测时人为注入复制延迟，把延迟当成正常状态设计
不区分读己之写与全局强一致需求描述里都叫「实时」用最贵的方案解决最便宜的问题逐条需求翻译，见上一节翻译表
用 ZooKeeper 直接读当强一致读以为写有序读也有序读到落后的快照，分布式锁判断出错先 sync 再读，或改用 etcd 的线性一致读
只测正常路径就宣称强一致不知道违反窗口只有几十毫秒故障时才暴露，且现场难以保留注入分区与进程暂停，用线性化检查器验证历史
❌
最容易踩的坑
  • 粘滞时间按平均延迟设定：平均 20 毫秒不代表 P99 是 20 毫秒，大事务或 DDL 期间从库延迟能到几十秒，粘滞窗口至少取 P99 的两三倍并配合位点等待。
  • 位点等待不设上限：WAIT_FOR_EXECUTED_GTID_SET 不带超时参数时会一直等，从库一卡住就把整个连接池占满，比读到旧数据严重得多。
  • 用 Seconds_Behind_Master 当唯一延迟指标：它在 SQL 线程空转时会显示 0，复制中断时显示 NULL，必须同时比对 Retrieved_Gtid_Set 与 Executed_Gtid_Set。
  • Lease Read 用在会被挂起的虚拟机上：VM 暂停恢复、宿主机过载导致时钟跳变，旧 Leader 会在租约「自认为有效」时应答旧数据，云上部署应评估是否改用 ReadIndex。
  • 会话粘滞状态存在单个网关实例的内存里：多实例部署后请求换个实例就丢粘滞，必须放进共享存储或用带位点的方案。
  • 把超时的写当失败处理：写超时的真实状态是未知，客户端如果直接走补偿会造成重复扣款，必须靠幂等键与查询接口确认最终状态。
  • 拿 CRDT 解决带约束的业务：计数器 CRDT 可以保证并发点赞不丢，但保证不了库存不为负，硬用会出现负库存却无法回溯。
  • 客户端生成 LWW 时间戳：客户端时钟完全不可信，手机时间可以被用户任意修改，等于把数据覆盖权交给客户端。
  • 以为 S3 还是最终一致而写重试轮询逻辑：2020 年 12 月之后新对象与覆盖写读取已是强一致，但 LIST 与跨区复制仍是最终一致，两者不能一概而论。
  • 报表页不标数据时间：最终一致的数据不标时间，用户会把延迟当成数据错误，反复提单质疑，沟通成本远高于加一行时间戳。
  • 在事务里做远程调用来「保证一致」：长事务占住行锁和连接，把一致性问题换成了可用性问题，远程调用应移到事务之外并配幂等。
