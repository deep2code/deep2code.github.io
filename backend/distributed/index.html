分布式一致性深度原理：CAP、Raft、2PC 与柔性事务

🏷️ 分布式事务

微服务拆开之后，「一个操作跨多个服务」立刻变成常态。这篇不堆术语，而是把决策链条讲清楚：CAP 到底在说什么（大多数人记错了）→ 一致性有哪些强度档位 → 强一致靠共识算法怎么做到 → 做不到强一致时用哪种柔性事务 → 以及所有方案共同的兜底：幂等。

核心原理一：CAP 不是「三选二」

流行说法「CAP 三个里选两个」是错的，而且这个误解会直接导致错误的架构决策。准确的表述是：当网络分区发生时，必须在 C 和 A 之间选一个。分区没发生的时候，C 和 A 是可以同时拥有的。

常见误解 实际情况
「P 是可以放弃的，所以有 CA 系统」 只要是分布式系统，网络分区就无法避免，P 是前提而非选项。所谓「CA 系统」其实是单机系统，它不在 CAP 的讨论范围内
「选了 CP 就完全不可用」 只有少数派分区不可用。etcd 5 节点挂 2 台，剩下的 3 台照常服务
「选了 AP 就会数据错乱」 AP 是「暂时读到旧值，之后收敛」。用 vector clock、CRDT、last-write-wins 等手段处理冲突，不是任由数据错乱
「CAP 的 C 就是 ACID 的 C」 完全不同。CAP 的 C 是线性一致性（多副本读到同一份最新值），ACID 的 C 是完整性约束（外键、唯一键、check 不被破坏）
「无分区时就没有取舍了」 还有 PACELC 的后半段：为了强一致，每次写都要等多数派确认，这是延迟成本。跨地域部署时这个成本能达到上百毫秒

核心原理二：一致性强度的完整谱系

「强一致」和「最终一致」之间不是二元的，中间有一整排档位。选型时该问的是「业务能接受哪一档」，而不是「要不要强一致」。

一致性模型 保证 业务上的体感 代表实现
线性一致性（Linearizability） 所有操作看起来像在单机上按真实时间顺序依次发生 写完立刻读，任何节点都能读到新值 etcd（ReadIndex 读）、ZooKeeper 的 sync 后读
顺序一致性 所有节点看到相同的操作顺序，但不要求与真实时间一致 可能读到略旧的值，但不会看到矛盾的顺序 ZooKeeper 默认读
因果一致性 有因果关系的操作保持顺序，并发操作可乱序 「回复」不会出现在「原帖」之前 COPS、部分 NoSQL
读己之写 自己写的自己一定能读到 用户改完头像刷新能看到（别人可能还没看到） 读写分离时把该用户路由到主库
单调读 不会读到比之前更旧的值 不会出现「刷新后数据反而退回去了」 同一会话固定路由到同一从库
最终一致性 停止写入后，经过一段时间所有副本收敛 存在不确定长度的不一致窗口 MySQL 主从、Redis 复制、消息驱动架构
💡
「读己之写」往往是真正的需求

产品经理说「必须实时」，多数时候要的其实是读己之写——用户自己的操作要立刻可见，别人晚几百毫秒看到完全没问题。这个需求不需要动用共识算法，只要把「该用户的读请求在写后一小段时间内路由到主库」就能解决，成本是全局强一致的几十分之一。

把需求精确到这个粒度，是分布式架构里性价比最高的一步。

核心原理三：共识算法 Raft 怎么保证不出双主

需要强一致的场景（选主、配置、分布式锁、元数据），答案都是共识算法。Raft 把问题拆成三块：Leader 选举、日志复制、安全性。

150~300ms 随机 Candidate --> Leader: 获得多数派投票
N/2+1 Candidate --> Follower: 收到更高 term 的消息 Candidate --> Candidate: 票被分散
任期递增后重新选举 Leader --> Follower: 发现更高 term
立即退位 Leader --> Leader: 周期发心跳
AppendEntries note right of Candidate 选举超时随机化 是避免反复分票的关键 end note note right of Leader 同一 term 内最多一个 Leader 因为投票是每 term 每节点一票 end note

所以已提交的日志一定在多数派上
机制 解决什么问题
多数派（quorum = N/2+1） 任意两个多数派集合必然有交集，所以不可能存在两组互不相交的节点各自达成不同的决议
Term（任期）单调递增 充当逻辑时钟。收到更高 term 的消息就无条件退位，保证旧 Leader 无法继续发号施令
每个 term 每节点一票 同一 term 内最多产生一个 Leader，从根上排除双主
选举限制 候选人的日志必须不旧于多数派，否则拿不到票。保证新 Leader 一定包含全部已提交日志
日志匹配性质 AppendEntries 携带 prevLogIndex/Term 做一致性检查，冲突则回退覆盖，保证所有节点日志前缀一致
选举超时随机化 避免所有节点同时发起选举导致反复分票、迟迟选不出 Leader
⚠️
网络分区时旧 Leader 会怎样

假设 5 节点分裂成 {A,B} 和 {C,D,E}，A 是旧 Leader。A 仍然认为自己是 Leader 并接受客户端写入，但它永远拿不到 3 个 ack，因此这些写入永远不会被提交，客户端等到超时——数据不会错。同时 {C,D,E} 选出新 Leader 正常服务。分区恢复后 A 发现更高 term，退位并截断掉自己那些未提交的日志。

但要注意：旧 Leader 可以返回旧的读结果。所以 etcd 提供 ReadIndex / lease read 来保证线性一致读——如果你直接读 follower 或者不走线性读接口，读到旧值是预期行为，不是 bug。

核心原理四：2PC 的阻塞点在哪里

2PC 不是「性能差」这么笼统，它有一个明确的、无法靠超时解决的不确定态。看清这个点，就知道为什么生产环境基本不用它做跨服务事务。

sequenceDiagram autonumber participant TM as 事务协调者 participant A as 参与者 A（订单库） participant B as 参与者 B（库存库） Note over TM,B: 阶段一 Prepare TM->>A: prepare A->>A: 执行 SQL，写 undo/redo，持有锁不释放 A-->>TM: yes TM->>B: prepare B->>B: 同样持有锁 B-->>TM: yes Note over TM: 阶段二 Commit TM--xTM: 协调者此刻宕机！ Note over A,B: A 和 B 都处于 prepared 状态
不知道该提交还是回滚
锁一直持有 → 相关数据全部不可写 A->>B: 参与者之间无法互相询问
因为对方也不知道最终决定 Note over A,B: 这是 2PC 的核心缺陷：
不确定态无法通过超时安全地解除
只能等协调者恢复后读它的事务日志
问题 2PC 3PC 的改进 3PC 是否真正解决
同步阻塞 Prepare 后一直持锁到 Commit 引入 CanCommit 预询问，减少无谓的资源锁定 缓解，未消除
协调者单点 宕机则参与者无限等待 参与者也有超时，超时后默认提交 ❌ 网络分区时「默认提交」可能与实际决定相反，导致数据不一致
消息轮次 2 轮 3 轮 延迟更高，所以 3PC 在工程上几乎没人用
性能 锁持有时间 = 整个事务的网络往返 更长 都不适合高并发

MySQL XA 是 2PC 的具体实现，能用，但要清楚代价：prepare 之后的锁要持有到 commit，跨服务网络往返期间这些行全部不可写；一旦协调者与某个分支断连，还会留下悬挂的 prepared 事务，需要 XA RECOVER 人工介入。所以它的合理使用范围是「同机房、同一种数据库、事务极短、并发不高」。

核心原理五：柔性事务四种方案的取舍

放弃强一致后，四种主流方案的差别集中在两点：改造成本和有没有隔离性。

维度 TCC Saga 本地消息表 事务消息（RocketMQ）
核心机制 Try 预留资源 → Confirm 确认 / Cancel 释放 正向 T1..Tn，失败则逆序执行补偿 C1..Cn 业务数据与消息在同一个本地事务写入，再异步投递 半消息对消费者不可见，本地事务成功后再 commit，并支持状态回查
隔离性 ✅ 有：Try 阶段已冻结资源，别人看不到也抢不走 ❌ 无：中间态对外可见，可能脏读 ❌ 无 ❌ 无
改造成本 最高：每个服务要写三个接口 中：每步要写补偿逻辑 低：加一张消息表 低：MQ 提供能力
一致性窗口 短（秒级） 取决于补偿链长度 取决于扫描 / 投递间隔 秒级
典型场景 资金冻结、库存预占、优惠券锁定 跨多服务的长流程（下单、履约、退款） 最常用：异步通知、数据同步 与 MQ 已深度耦合的体系
主要坑 空回滚、悬挂、幂等三件事必须处理 补偿本身可能失败；无隔离性需加语义锁 消息表会膨胀，需归档；投递失败要有重试上限和告警 回查接口必须实现且必须幂等

本地消息表是性价比最高的方案，核心就是「利用本地事务的原子性，把『业务成功』和『消息一定会发出去』绑在一起」：

-- 消息表与业务表同库，才能进同一个本地事务
CREATE TABLE `local_message` (
  `id`          BIGINT UNSIGNED AUTO_INCREMENT,
  `biz_id`      VARCHAR(64)  NOT NULL COMMENT '业务唯一键，用于消费端幂等',
  `topic`       VARCHAR(64)  NOT NULL,
  `payload`     JSON         NOT NULL,
  `status`      TINYINT      NOT NULL DEFAULT 0 COMMENT '0待发送 1已发送 2已死信',
  `retry_count` INT          NOT NULL DEFAULT 0,
  `next_retry_at` DATETIME   NOT NULL,
  `created_at`  DATETIME     NOT NULL,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_biz` (`biz_id`),              -- 生产端幂等
  KEY `idx_scan` (`status`, `next_retry_at`)    -- 扫描任务走这个索引
) ENGINE=InnoDB;

绝不会出现「订单成功但消息丢了」 J->>DB: SELECT WHERE status=0 AND next_retry_at<=now() LIMIT 100 J->>MQ: 投递消息 MQ-->>J: ack J->>DB: UPDATE status=1 Note over J,DB: 若在这里崩溃 → 下轮重发

核心原理六：TCC 三大异常与幂等落地

TCC 在实现时一定会遇到三个问题，它们都源于「网络不保证顺序也不保证只送一次」：

异常 怎么发生的 后果 解法
空回滚 Try 因超时或宕机根本没执行，但协调者判定失败，照样下发 Cancel Cancel 去释放一个从未预留的资源，报错或释放错数据 Cancel 先查事务记录表：没有 Try 记录就直接返回成功，并插入一条空回滚记录
悬挂 Try 的网络包被延迟，Cancel 先到、Try 后到 Try 预留的资源再也没人释放，永久泄漏 Try 执行前检查是否已有空回滚记录，有则直接拒绝执行
幂等 协调者重试，Confirm / Cancel 被调用多次 重复扣减、重复释放 事务记录表用全局事务 ID 做唯一键并记录状态，重复调用直接返回上次结果

再往上一层看，所有分布式方案最后都要落到幂等。常见的四种实现，按可靠性排序：

幂等手段 做法 可靠性 适用
数据库唯一索引 把业务唯一键设为唯一索引，重复插入捕获冲突异常即视为成功 最高：由存储引擎保证，不依赖应用逻辑 创建型操作（下单、发券、记账）
状态机 + 条件更新 UPDATE ... SET status=2 WHERE id=? AND status=1，看 affected_rows 高：数据库行锁天然互斥 状态流转型操作（支付、发货）
乐观锁版本号 UPDATE ... SET v=v+1 WHERE id=? AND v=? 高 并发更新同一行的场景
Redis 去重键 SET biz_id 1 NX EX 86400，已存在则跳过 中：Redis 宕机或过期后失效，只能当前置优化 挡住大部分重复，最终仍需数据库兜底
❌
「先查后插」不是幂等

SELECT 有没有 → 没有则 INSERT 在并发下必然失效：两个请求同时查到「没有」，然后都插入。这段代码在压测时能过，上线后偶发重复——排查起来极其费时。

唯一正确的做法是让数据库来判重：加唯一索引，直接插入，捕获 duplicate key 异常当作成功。把互斥交给存储引擎，而不是自己在应用层拼两条 SQL。

选型决策与运维兜底

场景 推荐方案 理由
服务注册发现、配置中心、分布式锁 etcd / ZooKeeper（CP + Raft/ZAB） 元数据量小、写入频率低，值得付强一致的延迟成本
下单扣库存（同库） 本地数据库事务 能用单库事务解决的，绝不引入分布式事务
下单 + 异步通知履约、发消息、加积分 本地消息表 / 事务消息 本质是异步通知，最终一致足够
资金冻结、库存预占 TCC 需要隔离性：预留阶段就要挡住其他人
跨多个服务的长流程（下单→支付→履约→结算） Saga（编排式，用状态机驱动） 步骤多且各步天然有补偿语义，TCC 的改造成本不可接受
报表、统计、搜索索引 CDC（订阅 binlog） 对业务零侵入，延迟秒级完全够用
任何方案 必须额外有：对账 + 补偿任务 + 告警 分布式系统一定会出现残留的不一致，靠定时对账收口，而不是靠「设计得足够完美」

最容易踩的坑

❌
避坑清单
  • 用「CAP 三选二」做架构论证：P 不是选项。正确表述是「分区发生时在 C 和 A 之间选」，无分区时的真正权衡是延迟与一致性（PACELC）。
  • 把 CAP 的 C 和 ACID 的 C 混为一谈：前者是线性一致性，后者是完整性约束，八竿子打不着。
  • 能用单库事务却上了分布式事务：先问「这两张表能不能放同一个库」。分布式事务的复杂度成本远高于多数人的预估。
  • 不做幂等就上消息队列：至少一次投递意味着重复是必然的。而「先查后插」在并发下不是幂等——要用唯一索引。
  • TCC 只实现了三个接口，没处理空回滚和悬挂：测试环境不会暴露，生产偶发资源泄漏，排查成本极高。
  • Saga 忽略了无隔离性：补偿前中间态对外可见，用户可能看到「订单已创建但库存未扣」。需要业务层语义锁或状态屏蔽。
  • 补偿操作自己不幂等、也不允许失败：补偿同样会被重试，同样可能失败，必须有重试上限 + 死信 + 人工介入入口。
  • 以为共识算法能做到「读一定最新」：Raft 只保证写的线性一致，读 follower 或不走线性读接口照样读到旧值。
  • 用雪花算法却不处理时钟回拨：NTP 校时导致时间倒退，会生成重复 ID。必须检测回拨并拒绝发号或等待。
  • 没有对账：这是最致命的一条。任何最终一致方案都会留下极少量残留不一致，只有定时对账 + 补偿能收口。
