分布式事务深度原理：CAP 与最终一致性

🏷️ 分布式事务

微服务拆分后，一个操作要跨多个服务，怎么保证数据一致？CAP 理论、BASE、两阶段提交、TCC、本地消息表，这些原理要搞懂。

核心原理1：CAP 理论：三选二

分布式系统三个特性：一致性 C、可用性 A、分区容错 P，网络一定会断，P 必须要，所以只能在 C 和 A 之间选。

flowchart TD A[CAP] --> B[一致性 Consistency] A --> C[可用性 Availability] A --> D[分区容错 Partition] D --> D1[网络一定会断 必须选] B --> B1[强一致] C --> C1[高可用]

CAP 组合对比

组合 说明 常见系统
CP 选一致，放弃可用 Zookeeper、etcd
AP 选可用，放弃强一致 Eureka、Cassandra
CA 没有分区，单机 单机数据库

核心原理2：两阶段提交 2PC 原理

两阶段提交：准备阶段问所有参与者，都准备好了再提交，一个失败就回滚。但同步阻塞，性能差。

flowchart LR A[协调者] -->|准备| B[参与者1] A -->|准备| C[参与者2] B -->|同意| A C -->|同意| A A -->|提交| B A -->|提交| C

2PC 两阶段流程

阶段 做什么 问题
准备阶段 所有参与者预提交，锁定资源 同步阻塞
提交阶段 都同意就提交，有一个不同意就回滚 协调者挂了会阻塞
缺点 同步阻塞，单点故障，性能差 生产很少用

核心原理3：最终一致性方案

生产环境不用 2PC，用最终一致性：TCC、本地消息表、Saga，牺牲强一致，换高可用和性能。

flowchart TD A[最终一致性] --> B[TCC Try-Confirm-Cancel] A --> C[本地消息表] A --> D[Saga 长事务] B --> B1[业务层面两阶段] C --> C1[本地事务+MQ 异步通知] D --> D1[拆成多个本地事务 失败回滚]

最终一致性方案对比

方案 原理 适用场景
TCC Try 预留资源，Confirm 确认，Cancel 取消 资金、库存等强一致业务
本地消息表 本地事务写消息，异步发 MQ，消费方消费 异步场景，最常用
Saga 长事务拆成小事务，每步有补偿 跨服务长流程

新手最容易踩的坑

❌
避坑指南
  • 不要追求强一致，大部分业务最终一致就够了
  • 分布式事务一定要做幂等，网络重试会重复执行
  • 本地消息表是最实用的方案，简单可靠，生产用得最多
  • TCC 成本高，Try 阶段要预留资源，只有资金类场景才用
