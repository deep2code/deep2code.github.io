Procedure 设计：输入校验、中间件与鉴权

router 只是命名空间，真正承载业务逻辑和安全边界的是 procedure。tRPC 把 procedure 设计成一条可组合的构建链：.use() 挂中间件、.input() 声明输入 schema、.output() 声明输出 schema、.query() 或 .mutation() 收尾。这条链上每一环都有明确的安全含义，写错一环就是一个漏洞。

input schema 是唯一的运行时防线

这一点必须反复强调：TS 的类型在编译后完全擦除，服务端运行时没有任何类型信息。你的 procedure 收到的就是 JSON.parse 出来的裸对象。没有 input() 的 procedure 不是「输入类型是 undefined」，而是「任何人可以发任何东西进来」。

schema 写法挡住什么不写的后果
z.string().uuid()非法 id 格式拼进查询条件后类型错误，或触发全表扫描
z.number().int().min(1).max(100)越界分页limit 传十万导致单请求拉全表，内存打满
z.string().max(10000)超长文本富文本字段被塞进 10MB 内容，写库超时连带拖垮连接池
z.enum(['asc','desc'])排序字段注入排序参数被直接拼进 SQL 片段，成为注入点
z.coerce.number()字符串数字混用前端传来的字符串参与算术运算得到拼接结果
z.object({}).strict()多余字段多余字段被展开进 ORM 的 data，造成字段覆写提权
z.string().datetime()非法时间Invalid Date 进入查询范围，返回空结果但不报错
import { z } from 'zod'
import { publicProcedure, router } from '../trpc'

// 分页查询的标准输入：上界与默认值都必须显式写出来
const listInput = z.object({
  // 游标分页优于 offset 分页，理由见站内 API 设计篇
  cursor: z.string().uuid().nullish(),
  limit: z.number().int().min(1).max(100).default(20),
  keyword: z.string().trim().max(50).optional(),
  // 排序字段一定用 enum 白名单，绝不能接受任意字符串
  orderBy: z.enum(['createdAt', 'updatedAt', 'title']).default('createdAt'),
  order: z.enum(['asc', 'desc']).default('desc'),
})

// 写操作的标准输入：strict 阻止多余字段被展开进 ORM
const createInput = z
  .object({
    title: z.string().trim().min(1).max(120),
    body: z.string().max(50_000),
    tagIds: z.array(z.string().uuid()).max(10).default([]),
    // 绝不要接受 authorId 之类的归属字段，它必须来自 ctx
  })
  .strict()

export const postRouter = router({
  list: publicProcedure.input(listInput).query(({ input, ctx }) => {
    // input 到这里已经是校验并填过默认值的确定类型
    return ctx.db.post.findMany({
      take: input.limit + 1,
      cursor: input.cursor ? { id: input.cursor } : undefined,
      orderBy: { [input.orderBy]: input.order },
    })
  }),
})
❌
最危险的一行代码

把 authorId、ownerId、role、isAdmin 这类归属或权限字段放进 input schema，然后 ...input 展开写库。调用方只要在请求体里加一个 role: "admin"，就完成了提权。所有归属与权限字段必须从 ctx 取，永远不能从 input 取，并且写操作的 input 建议一律加 .strict()。

output schema：什么时候值得付这个维护成本

output() 的作用是把返回值再过一遍 schema，没声明的字段会被剥掉。它解决的是一个非常现实的泄露路径：ORM 查出来的实体对象往往带着 passwordHash、phone、deletedAt、internalNote，而 return user 会把它们整个下发。

维度声明 output不声明 output
字段泄露风险白名单，新增敏感字段不会自动下发ORM 加一个字段就自动暴露
返回类型来源由 schema 决定，明确但需手写由 resolver 自动推导，省事
加字段成本改 schema 加改 resolver 两处只改 resolver
运行时开销每次响应多一次遍历校验无
对前端的价值契约更明确，重构时不易漏改依赖 resolver 实现细节
建议用户、支付、权限相关 router 强制加内部聚合、报表类接口可以省

middleware：把运行期守卫变成编译期类型收窄

这是 tRPC 设计里最值得称赞的一点。t.middleware 拿到 ctx 和 next，next({ ctx: {...} }) 传入的新 ctx 会把类型向下游传递。于是鉴权中间件在运行期确认 session 存在之后，下游 resolver 里 ctx.user 的类型就从 User | null 收窄成了 User——不是靠断言，是编译器真的知道。

位置ctx.session 类型ctx.user 类型resolver 里需要判空吗
createContext 之后Session | null不存在必须判空
isAuthed 中间件之后SessionUser不需要，编译器已确定非空
isAdmin 中间件之后SessionUser 且 role 已校验不需要
误用 publicProcedure 写需登录逻辑Session | null不存在编译器会报错，这正是我们要的
sequenceDiagram participant A as 适配器 participant L as 日志中间件 participant U as 鉴权中间件 participant V as input 校验 participant R as resolver A->>L: 调用 path 为 post.update L->>L: 记录开始时间戳 L->>U: next 放行 U->>U: 检查 ctx.session 是否存在 U-->>L: 不存在则抛 UNAUTHORIZED U->>V: next 传入 user 字段 类型随之收窄 Note over V: 中间件在 input 校验之前执行
所以中间件里的输入结构不可信 V->>R: 校验通过 输入已是确定类型 R->>R: 查记录并比对 ownerId 做水平权限 R-->>L: 返回结果 L->>L: 计算耗时并按 path 打点上报

// server/trpc.ts 的分层定义，这是 tRPC 社区的事实标准写法
import { initTRPC, TRPCError } from '@trpc/server'
import type { Context } from './context'

const t = initTRPC.context<Context>().create()

// 日志与埋点：所有层都应该挂，必须按 procedure path 打点
const withMetrics = t.middleware(async ({ path, type, next }) => {
  const start = Date.now()
  const result = await next()
  const durationMs = Date.now() - start

  // 关键：维度是 path 而不是 HTTP URL
  // 开启 batch 后多个 procedure 共用一个请求，URL 维度会把它们混在一起
  metrics.timing('trpc.duration', durationMs, { path, type, ok: String(result.ok) })
  if (!result.ok) {
    metrics.increment('trpc.error', { path, code: result.error.code })
    logger.warn({ path, type, durationMs, code: result.error.code })
  } else if (durationMs > 500) {
    logger.warn({ path, type, durationMs, msg: 'slow procedure' })
  }
  return result
})

// 鉴权：这里只做垂直权限（你是谁），不碰资源归属
const isAuthed = t.middleware(({ ctx, next }) => {
  if (!ctx.session?.userId) {
    throw new TRPCError({ code: 'UNAUTHORIZED', message: '请先登录' })
  }
  return next({
    // 传入的新 ctx 会被合并进下游类型：session 从可空变非空，并多出 user
    ctx: { session: ctx.session, user: { id: ctx.session.userId, role: ctx.session.role } },
  })
})

const requireRole = (role: 'admin' | 'operator') =>
  t.middleware(({ ctx, next }) => {
    // 这里能直接读 ctx.user 是因为它挂在 isAuthed 之后，类型已收窄
    if (ctx.user.role !== role) {
      // 有身份但没权限用 FORBIDDEN，不要用 UNAUTHORIZED，否则前端会错误地跳登录
      throw new TRPCError({ code: 'FORBIDDEN' })
    }
    return next()
  })

export const router = t.router
export const publicProcedure = t.procedure.use(withMetrics)
export const protectedProcedure = publicProcedure.use(isAuthed)
export const adminProcedure = protectedProcedure.use(requireRole('admin'))

query、mutation 与 subscription 的真实差异

很多人以为这三者只是命名约定，实际行为差异是硬性的，选错会直接产生线上问题。

维度querymutationsubscription
HTTP 形态POST，可覆写为 GET只能 POSTWebSocket 或 SSE 长连接
可被 HTTP 缓存GET 形态下可以不可以不适用
客户端自动缓存有，按 queryKey 缓存无无，走事件流
失败自动重试默认会重试默认不重试断线自动重连
并发行为并发发出同一 mutation 默认串行排队单连接多路复用
可被预取可以（SSR 预取、悬停预取）不可以不可以
context 计算时机每次请求每次请求只在建连时算一次
适用所有读取所有有副作用的操作需要服务端主动推的场景
⚠️
把写操作写成 query 会同时触发三个问题

一是可能被 GET 缓存命中，副作用被跳过；二是可能被预取或悬停预加载提前触发，用户还没点就执行了；三是失败后被自动重试，副作用重复执行。只要有副作用就必须是 mutation，没有例外。至于幂等性与重试安全的完整讨论，见站内 API 设计最佳实践。

subscription 还有一个容易踩的点：它的 context 只在连接建立时计算一次。长连接跑了两小时后，ctx.session 里的 token 早已过期，但订阅还在推送数据。生产上要么在推送逻辑里定期重新校验会话，要么给连接设置最大存活时间强制客户端重连。

鉴权的两层：垂直权限与水平权限

中间件能解决的只是「你是不是登录用户」「你是不是管理员」这类与具体资源无关的判断，也就是垂直权限。而「这条订单是不是你的」属于水平权限，它必须在 resolver 里查库比对，中间件做不到也不该做：中间件在 input 校验之前执行，输入结构不可信；而且归属规则每个 procedure 都不一样。

export const postRouter = router({
  // 正确：归属条件直接写进 where，一次查询同时完成鉴权与更新
  update: protectedProcedure
    .input(z.object({ id: z.string().uuid(), title: z.string().min(1).max(120) }).strict())
    .mutation(async ({ ctx, input }) => {
      const result = await ctx.db.post.updateMany({
        // authorId 来自 ctx 而非 input —— 这是水平权限的关键
        where: { id: input.id, authorId: ctx.user.id },
        data: { title: input.title },
      })
      if (result.count === 0) {
        // 统一返回 NOT_FOUND 而不是 FORBIDDEN：后者会暴露该 id 是否存在
        throw new TRPCError({ code: 'NOT_FOUND' })
      }
      return { id: input.id }
    }),

  // 需要先读再判的场景：状态机校验与归属校验分开，错误码语义要区分
  publish: protectedProcedure
    .input(z.object({ id: z.string().uuid() }).strict())
    .mutation(async ({ ctx, input }) => {
      const post = await ctx.db.post.findUnique({ where: { id: input.id } })
      if (!post || post.authorId !== ctx.user.id) {
        throw new TRPCError({ code: 'NOT_FOUND' })
      }
      if (post.status !== 'draft') {
        // 前置条件不满足用 PRECONDITION_FAILED，前端据此提示刷新状态
        throw new TRPCError({ code: 'PRECONDITION_FAILED', message: '只有草稿可以发布' })
      }
      return ctx.db.post.update({ where: { id: post.id }, data: { status: 'published' } })
    }),
})

越权的完整分类（水平、垂直、上下文越权）、枚举 id 的防护、以及为什么敏感资源要统一返回 NOT_FOUND，见站内 认证授权与越权防护。

事务与并发：把 mutation 包进事务

「中间件能改写 ctx」这个特性还有一个很实用的落地：写一个事务中间件，把 ctx.db 换成事务句柄。这样 resolver 里所有数据访问自动落在同一个事务里，既不用每个 procedure 手写事务包裹，也不会出现某个分支忘了用事务句柄这种漏网。类型上它同样是一次收窄：下游拿到的 ctx.db 就是事务类型，误用外层连接会直接编译报错。

// 只给 mutation 用：query 包事务纯属浪费，还会白占连接
const withTransaction = t.middleware(async ({ ctx, next, type }) => {
  if (type !== 'mutation') return next()

  return ctx.db.$transaction(async (tx) => {
    // 把 db 替换成 tx，下游 resolver 拿到的类型就是事务句柄
    const result = await next({ ctx: { ...ctx, db: tx } })
    // 关键：next 不会因为业务错误抛异常，它把错误放在返回值里
    // 不显式抛出的话事务照样提交，这是最隐蔽的一类数据不一致
    if (!result.ok) throw result.error
    return result
  })
})

export const txProcedure = protectedProcedure.use(withTransaction)

上面注释里那行是真正的坑：next() 的返回值是一个带 ok 字段的结果对象，resolver 抛出的 TRPCError 不会穿透中间件往上冒，所以你必须自己判断并重新抛出，否则失败的 mutation 也会被提交事务。这个行为与 Express 那种「异常自动冒泡」的直觉相反，写日志和监控中间件时同样要注意——判断成败要看 result.ok，而不是用 try catch 包住 next()。

事务边界写法优点风险
不开事务直接多次写最简单，连接占用时间最短中途失败留下半成品数据
resolver 内手写在需要的 procedure 里包一层边界清晰，只有需要的地方付代价容易漏，嵌套调用时难判断是否已在事务中
中间件统一包做成 txProcedure 分层不会漏，类型上强制使用事务句柄容易把慢的外部调用也圈进事务
跨服务写操作数据库事务用不上不适用必须改成最终一致方案

最后两条必须提醒。第一，事务里绝不能放外部 HTTP 调用：一个三秒超时的第三方接口会让事务持有连接三秒，并发一上来连接池立刻耗尽，症状是全站数据库操作一起变慢，而慢的根因看起来和这个接口毫无关系。第二，tRPC 的 batch 会让多个 mutation 在同一个 HTTP 请求里到达并各自开事务并发执行，如果两个 mutation 以相反顺序更新同样两行记录就会死锁；对策是固定更新顺序，或者把需要原子性的操作合并成一个 procedure。写操作的幂等与重试安全见站内 API 设计最佳实践。

反模式对照

反模式现象为什么危险正确做法
不声明 input schema开发期一切正常运行期完全没有校验，curl 可发任意结构凡接受参数一律声明，用 lint 卡住
把 ownerId 放进 input功能正常调用方可以伪造归属，等于提权归属字段只从 ctx 取，input 加 .strict()

把 mutation 写成 query偶发重复扣款、重复发消息被缓存、被预取、被自动重试有副作用一律 mutation
中间件里抛普通 Error前端拿到 500 和中性文案错误结构不统一，无法做分支处理一律抛 TRPCError 并选对 code

❌
最容易踩的坑
  • 漏掉某个 procedure 的 input schema：一个都不能漏，漏的那个就是入口；review 时优先扫没有 .input() 的调用链。
  • input 里接受 authorId、role、isAdmin：配合 ...input 展开写库就是一键提权。
  • 写操作的 input 没加 .strict()：多余字段被展开进 ORM 的 data，覆写掉不该动的列。
  • 分页 limit 没有上界：单个请求把整表拉进内存，连带打满数据库连接池。
  • 排序字段用 z.string()：等于把排序表达式的控制权交给调用方，部分 ORM 下可构成注入。
  • 以为中间件在 input 校验之后跑：顺序相反，中间件里读输入必须做防御性判断。
  • 把资源归属校验放在中间件：要么做不到，要么让每个接口都多付一次查库。
  • updateMany 不检查 count：where 带上 ownerId 后越权请求会静默返回成功（影响 0 行），必须判 count === 0 并抛 NOT_FOUND。
  • 无权限时抛 FORBIDDEN 暴露资源存在性：攻击者可以据此枚举 id，敏感资源统一用 NOT_FOUND。
  • 把 mutation 当 query 用：缓存、预取、重试三条路径都会让副作用错乱。
  • subscription 里假设 session 一直有效：context 只在建连时算一次，两小时后还在给已登出的用户推数据。
  • 日志中间件挂在鉴权后面：所有 UNAUTHORIZED 请求都不会被记录，恰好丢掉了最该看的那部分流量。
