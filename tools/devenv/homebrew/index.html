Homebrew 的机制与开发环境可复现性

🏷️ Homebrew

Homebrew 在 macOS 上几乎等于默认安装，但多数人对它的认知停留在 brew install 这一行。真正出问题的时候是这样的场景：同一份 Brewfile，同事的机器编译通过、你的机器链接报错；一次 brew upgrade 之后 PostgreSQL 主版本跳了、python3 指向变了、CI 昨天还绿的构建今天红了。这些现象指向同一个根因——Homebrew 是一个滚动更新的系统级包管理器，它在设计上就不提供版本锁定。这篇不讲怎么装、怎么用，只讲机制、边界条件，以及它在「可复现开发环境」这件事上的真实位置与退出成本。

目录模型：Cellar、opt 与逐文件符号链接

Homebrew 的一切行为都由 prefix 决定。brew --prefix 在 Apple Silicon 上默认是 /opt/homebrew，Intel macOS 上是 /usr/local，Linuxbrew 则是 /home/linuxbrew/.linuxbrew。formula 安装后并不直接躺在 prefix/bin 里，而是先解包进 Cellar/名称/版本/，这个目录称为 keg；随后 brew link 把 keg 里的可执行文件、头文件、pkg-config 描述文件逐个做成符号链接，挂到 prefix 下对应的 bin、include、lib 目录。

中间还有一层常被忽略的 opt/名称，它是指向「当前激活版本」的稳定软链。其他 formula 编译时写进二进制 rpath 的是 opt 路径，而不是带版本号的 Cellar 路径——这正是同一个库换版本后依赖方不必重新编译的原因，也是为什么手工 mv 或 rm -rf Cellar 下的目录会让一堆命令突然报 dyld 找不到库。

keg-only 是第二个困惑源。openssl@3、mysql-client、node@18 这类 formula 装完只落在 Cellar 与 opt，不会 link 进 prefix/bin，因为它们会与 macOS 自带版本或其他 formula 争抢同名文件。这不是安装失败，而是刻意的隔离策略，代价是你得自己往 PATH、LDFLAGS、CPPFLAGS、PKG_CONFIG_PATH 里补 opt 路径。安装结束时那段「If you need to have X first in your PATH」的提示就是在说这件事，跳过它后面必然踩坑。

formula 与 cask：两套不同的安装语义

把 cask 理解成「formula 的图形界面版」是最常见的误解。两者只共享 CLI 入口，从元数据格式到升级与卸载语义几乎没有交集。formula 描述的是一次可重复的构建与安装过程；cask 描述的是「把一个已签名的分发包放到系统合适位置」的过程——下载 dmg、zip 或 pkg，把 .app 放进 Caskroom 再软链到 /Applications，或者干脆调用 macOS 的 installer 执行 pkg 内的安装脚本。

后一种情况尤其值得警惕：pkg 类型的 cask 会把文件写到你完全不掌握的位置，而 brew uninstall --cask 只能执行 cask 定义里声明的 uninstall 段。如果定义没写全，卸载后 LaunchDaemon、特权助手、系统扩展、~/Library 下的配置都会留在系统里。--zap 能清得更彻底，但它同样是按定义走的，不是真正的文件追踪。

另一个坑是自动更新打架。很多 GUI 应用自带升级器，对应 cask 会标注 auto_updates true 或把版本写成 :latest。这类 cask 在 brew outdated 里默认不出现，必须加 --greedy 才看得到；而当应用自己更新过之后，Caskroom 里记录的版本与磁盘上真实的 .app 已经不一致，下一次 brew upgrade --cask 可能把它「升级」回 cask 定义里的版本。

bottle 命中与源码编译的触发条件

bottle 是 Homebrew 预编译好的二进制包，按「系统代号 + 架构」打标签，例如 arm64_sequoia、arm64_sonoma、Intel 的 sonoma、Linux 的 x86_64_linux。安装时 brew 用当前系统去匹配 formula 里声明的 bottle 标签：命中则下载解包，秒级完成；匹配不上就退回源码编译，几十分钟甚至更久，并且要求本地有完整的 Command Line Tools。判断走了哪条路不用猜，输出里出现 Pouring 就是 bottle，出现 Building 就是在编译。

bottle 里的二进制含有编译期写死的绝对路径，Homebrew 用 cellar 属性标记可重定位程度：:any 表示可以重定位到任意 prefix，:any_skip_relocation 表示根本不含绝对路径，而写死具体 Cellar 路径的 bottle 只能装进默认 prefix。这是「自定义 prefix 必然大量源码编译」的机制原因，不是哪个配置没调对。把 Homebrew 装到 ~/homebrew 或 /opt/brew 这类非标准位置，等于主动放弃了大部分预编译包。

依赖解析：为什么升级一个会带走一串

Homebrew 的依赖是构建期与运行期混在一张图里的。brew upgrade 不带参数时升级所有 outdated 的 formula；带参数时也会先把目标的依赖拉到 formula 当前声明的版本。更隐蔽的是 revision 机制：当 openssl@3 这类底层库的动态库名变化时，homebrew-core 会给所有链接它的 formula 加一个 revision 并重新打 bottle，于是你只想升 curl，结果十几个包一起被替换。

这不算设计缺陷。系统级包管理器让所有软件共享同一份动态库，要么整体保持一致，要么承受符号缺失导致的 dyld 报错。真正的问题在于 Homebrew 的「整体」跟随的是 homebrew-core 的 HEAD，而它每天都在变——没有任何机制让你回到「上周那个组合」。

排查靠两个方向相反的命令：brew uses --installed --recursive 回答「谁依赖我」，brew deps --tree 回答「我依赖谁」。前者在决定「这个包能不能删」时必看。顺带纠正一个误解：brew autoremove 依据的是「是否被显式安装过」这个标记，而不是文件级引用分析，所以你手工 brew install 过一次的依赖包永远不会被它清掉，看起来「清不干净」是预期行为。

Homebrew 不做版本锁定

这是全篇最要紧的一节。Homebrew 没有 lockfile，homebrew-core 对每个 formula 原则上只维护一个「当前版本」。围绕这一点有三个流传很广的错误认知。

第一，brew pin 不是版本锁定。它的语义只有一条：brew upgrade 批量升级时跳过这个 formula。它不冻结依赖树，不改变别的包安装时的依赖解析——如果新装的包需要更高版本，你得到的是冲突或忽略，而不是自动适配。它也不会在另一台机器上生效，因为 pin 是本地状态而不是仓库里的声明。它是一张「别顺手升级我」的备忘录，不是约束。

第二，@ 版本 formula 是被策展的、有限的、会消失的。python@3.12、node@20、postgresql@16、openjdk@17 之所以存在，是因为维护者判断这些主版本需要长期并存；粒度到主版本或次版本，从来不到补丁级，你写不出 python@3.12.4。更关键的是，当上游 EOL 时这些 formula 会被从 core 移除，你那份跑了两年的 Brewfile 会在某天突然装不上。

第三，降级没有一等支持。旧 bottle 不保证仍可下载，官方路径是 brew extract --version=x.y.z 把历史 formula 抽到自己的 tap 再安装，而抽出来的版本几乎一定没有 bottle，意味着源码编译。把这条当成常规手段的团队，最后都会转向 mise 或 nix。

团队一致性：Brewfile 的边界与务实分层

Brewfile 是清单（manifest），不是锁（lock）。brew bundle dump 产出的是名字列表，回放时装的是执行那一刻 core 里的版本。两个人相隔一周跑同一份 Brewfile，拿到的 Node、Python、protobuf 版本可以完全不同，而且没有任何报错提示这件事发生了——这是「我这能跑你那不行」最常见的来源。

如果组织上只能用 brew，把不一致范围压到最小的分层是：语言运行时全部交给 mise 或 asdf，把 .tool-versions 提交进仓库；构建必需的系统库（protobuf、openssl、pkg-config、cmake）宁可进容器或 nix，也不要指望 brew 给你稳定；Brewfile 里只留编辑器、终端、数据库客户端、GUI 工具这类「版本不影响构建产物」的软件。这样即使 brew 漂移，漂的也只是开发者体验，不是产物。

再补一个常被忽略的参数：brew bundle install 默认会顺手升级已安装的包，加 --no-upgrade 才是「缺什么补什么」。配合 HOMEBREW_NO_AUTO_UPDATE=1，至少能保证一次安装动作不触发元数据刷新，让同一天内的几台机器结果一致。

与 asdf / mise / nix / devbox 的分工

这几类工具解决的是不同层次的问题，应该叠着用而不是二选一：brew 管「这台机器上的系统级软件」，mise 与 asdf 管「这个项目用哪个语言版本」，nix 与 devbox 管「这个项目的完整依赖闭包」，容器镜像管「运行时与生产环境对齐」。把语言版本交给 brew 管，是绝大多数团队环境漂移的起点。

选型时真正该权衡的不是功能表，而是退出成本。brew 的退出成本接近零，删掉 prefix 目录就干净了；mise 只多一个 shim 目录和一个版本文件；nix 一旦进入，flake、overlay、自建 derivation 会变成团队里只有一两个人能维护的资产，迁走时需要重写全部依赖描述。devbox 是 nix 的封装，降低了入门门槛，但底下仍是 nix，出问题依然要懂 nix 的求值模型。

CI 里不该依赖 brew 的四个理由

一是版本漂移。CI 每次运行都会拉到当时最新的 core 元数据，今天装到的 protobuf 和上周不是同一个版本；由于没有 lockfile，构建失败后你连「当时装了什么」都无法回溯。

二是耗时不可控。同步 formula 索引本身就有成本，托管 runner 预装的 brew 版本与最新元数据之间的差异还会触发额外下载与自我升级，这段时间完全不产生业务价值。

三是外部依赖面被放大。bottle 托管在 GitHub Packages，走公网并受速率限制影响；上游一次超时或 403，流水线就因与代码毫无关系的原因变红。

四是 Linux runner 上代价更高。Linuxbrew 的 bottle 覆盖度明显低于 macOS，大量包会在 CI 上现场编译，把分钟级的任务拖成小时级。

替代方案按层替换即可：语言工具链用官方 setup action 或 mise（都能写死精确版本）；系统库与构建工具用固定 digest 的容器镜像；确实只有 brew 提供的 CLI，把它作为固定版本的二进制产物缓存进制品库，而不是每次 brew install。

缓存与磁盘占用治理

Homebrew 吃磁盘有三个来源：Cellar 里的多版本 keg、Caskroom 里的历史版本目录、以及下载缓存（brew --cache，macOS 上默认在 ~/Library/Caches/Homebrew）。第三项最容易长到几十 GB，因为默认清理策略只删超过 HOMEBREW_CLEANUP_MAX_AGE_DAYS（默认 120 天）的下载，而周期性完整清理的间隔由 HOMEBREW_CLEANUP_PERIODIC_FULL_DAYS（默认 30 天）控制。

治理顺序是固定的：先 brew cleanup -n 做 dry run 看清会删什么，再决定是否加 -s（连已安装包的缓存一起删）和 --prune=all（忽略保留天数）。brew autoremove 清的是没有任何显式安装包依赖的 formula，如前所述它按显式安装标记判断，所以结果往往比你预期的少。

目标命令或路径影响面与风险
定位缓存大小du -sh "$(brew --cache)"只读，最先该看的一项
看清会删什么brew cleanup -n只列清单不动文件，务必先跑
清历史版本与过期下载brew cleanup删旧 keg，正在被软链的当前版本不受影响
彻底清下载缓存brew cleanup -s --prune=all下次重装需重新下载，离线环境慎用
清无人依赖的包brew autoremove -n 确认后去掉 -n按显式安装标记判断，可能清不干净
抑制安装时自动更新HOMEBREW_NO_AUTO_UPDATE=1减少版本漂移，但元数据会逐渐过期
抑制安装后自动清理HOMEBREW_NO_INSTALL_CLEANUP=1磁盘增长更快，换来安装耗时可预测
排查双前缀与链接冲突brew doctor输出噪声大，只关注 conflicting 与 unlinked 两类
# 体积盘点：三个来源分别看，不要只看 Cellar
du -sh "$(brew --cache)"
du -sh "$(brew --prefix)/Cellar" "$(brew --prefix)/Caskroom"

# 清理：一定先 dry-run
brew cleanup -n                                  # 只打印将删除的文件
brew cleanup --prune=all -s                      # 确认无误后再执行
brew autoremove -n                               # 列出无人依赖的 formula

# 写进 shell profile 的常用变量
export HOMEBREW_NO_AUTO_UPDATE=1                 # install/bundle 前不自动刷新元数据
export HOMEBREW_NO_INSTALL_CLEANUP=1             # 安装后不自动清理，耗时更可预测
export HOMEBREW_NO_ANALYTICS=1
export HOMEBREW_CLEANUP_MAX_AGE_DAYS=30          # 下载缓存保留天数，默认 120
export HOMEBREW_CLEANUP_PERIODIC_FULL_DAYS=30    # 周期性完整清理间隔，默认 30

# 需要走镜像时只改域名，不要去动 git remote 之外的东西
# export HOMEBREW_BOTTLE_DOMAIN=https://你的镜像地址/bottles
❌
最容易踩的坑
  • 把 brew pin 当成 lockfile：它只让 brew upgrade 跳过该包，是本机状态，不随仓库传播，也不约束依赖解析。
  • 指望 Brewfile 保证版本一致：它只记录装什么。相隔一周执行同一份 Brewfile，语言运行时版本可以完全不同且无任何告警。
  • 忘了 --no-upgrade：brew bundle install 默认会升级已装包，在「只想补一个工具」时会顺手改掉整台机器的环境。
  • Apple Silicon 上遗留 /usr/local 那套：两套 Cellar 互不知晓，命令实际解析到哪个完全由 PATH 顺序决定，表现为版本号忽高忽低。
  • 把 Homebrew 装到非默认 prefix：cellar 属性不可重定位的 bottle 全部失效，等于主动选择长期源码编译。
  • 无视 keg-only 提示：openssl@3 这类包装完不进 PATH，不补 PKG_CONFIG_PATH 与 LDFLAGS，编译期会莫名找不到头文件。
  • 手工挪动或删除 Cellar 目录：其他二进制的 rpath 指向 opt 软链，破坏链接后一批命令直接 dyld 报错。
  • 以为 brew autoremove 能清干净：它按「是否被显式安装过」判断，被你手工装过一次的依赖包永远留着。
  • cask 卸载不带 --zap：pkg 类应用的 LaunchDaemon、系统扩展、~/Library 配置会留在系统里，而 zap 也只按定义清理。
  • 忽略 --greedy：标了 auto_updates 或 :latest 的 cask 不出现在 brew outdated 里，你会以为已经是最新。
  • 在 CI 里 brew install：版本漂移不可回溯、耗时不可控、依赖公网 bottle 源，构建变红的原因经常与代码无关。
  • 只清 Cellar 不清缓存：下载缓存默认保留 120 天，通常是磁盘占用的最大头，而它不在 brew list 的视野里。
