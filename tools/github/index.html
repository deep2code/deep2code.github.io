GitHub 的协作机制与仓库工程化

🏷️ GitHub

GitHub 的界面很友好，但它的协作机制里有一批「不看文档就一定会撞」的规则：合并按钮选哪个会改变你半年后定位 bug 的能力，required checks 的名字是字符串匹配、改个 job 名 PR 就永远卡住，CODEOWNERS 的匹配优先级和 gitignore 一样是最后一条胜出，fork PR 的两个触发事件权限边界完全不同。这篇只讲这些机制本身。

Git 的对象模型、reset 与 reflog 的真实语义见站内 Git 的对象模型与常见操作的真实语义；Actions 流水线本身的设计（缓存、矩阵切分、并发控制）见站内 CI/CD 篇；GitLab 的权限模型见站内 GitLab 篇。

三种合并方式：选的不是风格，是半年后的定位能力

PR 页面上那个下拉框有三个选项，它们对仓库历史的改造方式完全不同，进而决定了 git revert 好不好做、git bisect 能定位到多细、以及签名和作者信息还在不在。

适合需要保留协作拓扑的长期分支、release 分支合并绝大多数功能 PR（默认推荐）提交本身就被精心拆分过、且每个提交都跑过 CI 的仓库

两个常被说错的点。第一，「squash 会丢历史」——丢的是 PR 分支上的中间提交，而 PR 本身、review 记录、diff 都还在 GitHub 上；真正的代价在最后一行：squash 之后原分支的提交不是 main 的祖先，所以同一个长期分支合第二次会把旧改动再演一遍。第二，「rebase 让 bisect 更好用」——只有在每个中间提交都单独跑过 CI 时才成立，否则你会 bisect 到一个编译不过的提交，只能 git bisect skip，把区间越切越模糊。

分支保护与 required checks：名字就是契约

required status checks 的匹配依据是检查的名字字符串。矩阵 job 的检查名是 job 名 (矩阵取值)，所以矩阵一改、job 一改名，原来那个必需检查就永远不会有人来上报，PR 停在 Expected — Waiting for status to be reported，而且没有任何报错提示你配置过期了。

更容易混的是「被跳过」的两种情况，它们的结果完全相反：

# 流水线本身的设计（缓存、矩阵切分、并发取消）见站内 CI/CD 篇
name: ci
on:
  pull_request:
  merge_group:          # 启用合并队列后必须监听，否则队列里等不到检查结果

permissions:
  contents: read        # 工作流级最小权限，需要写的 job 单独提权

jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        go: ['1.22', '1.23']
    steps:
      - uses: actions/checkout@v4
      - run: go test ./...

  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: make lint

  # 分支保护里唯一被设为 required 的检查就是它。
  # 名字固定为 ci-gate，上面的矩阵怎么改、job 怎么增删都不用动分支保护配置。
  ci-gate:
    if: always()            # 关键：上游失败或被跳过时它仍然要运行并上报状态
    needs: [test, lint]
    runs-on: ubuntu-latest
    steps:
      - name: verify upstream results
        run: |
          # skipped 视为通过（路径过滤场景），failure 与 cancelled 才算失败
          for r in "${{ needs.test.result }}" "${{ needs.lint.result }}"; do
            case "$r" in
              success|skipped) ;;
              *) echo "blocking result: $r" >&2; exit 1 ;;
            esac
          done

还有一层容易忽略：现在 GitHub 同时存在经典分支保护和 rulesets 两套规则，两者是叠加的，最严格的那条生效。排查「明明我把分支保护关了还是不让合」时，记得去 rulesets 里也看一眼；反过来，bypass 名单里塞了一堆人或 App，等于保护形同虚设。

CODEOWNERS 的匹配规则与陷阱

CODEOWNERS 的语法「接近」gitignore，但有三处硬差异，每一处都制造过事故：不支持 ! 取反、不支持 [] 字符区间、最后一条匹配的规则胜出。最后这条尤其反直觉，因为 ssh_config 之类的配置是第一条胜出——在 CODEOWNERS 里，兜底规则必须写在最前面。

# .github/CODEOWNERS（放仓库根、.github/ 或 docs/ 三处之一）
# 规则：最后一条匹配的胜出 => 兜底放最上面，越具体的放越下面

*                           @acme/platform

# 目录写法的区别：不带前导斜杠 = 任意层级的同名目录；带斜杠 = 只匹配根下那个
docs/                       @acme/docs-team          # 任何层级的 docs 目录
/infra/                     @acme/sre                # 只有仓库根下的 infra
**/migrations               @acme/dba                # 任意深度的 migrations

# 没有 ! 取反，排除子目录的官方替代写法是「留空所有者」：
# 下面这行让 apps/sandbox 回落到「需要任意有写权限的人批准」
/apps/                      @acme/frontend
/apps/sandbox

# 单个文件也可以指定，用来守护高风险配置
/.github/workflows/         @acme/platform @acme/sre
/Dockerfile                 @acme/sre
规则 / 条件真实语义常见误解
多条规则同时命中最后一条生效，前面的被完全覆盖以为像 gitignore 一样「越具体越优先」，结果兜底规则写在最后把所有精细规则废掉
docs/ 与 /docs/前者匹配任意层级的 docs，后者只匹配根下的写了带斜杠的却期望匹配子模块里的同名目录
排除某个子目录没有 !，只能再写一条「所有者留空」的规则照 gitignore 写 !path，该行不生效
owner 的权限必须对仓库有写权限；团队要写成 @org/team 且该团队对仓库有访问权写了没权限的人或团队，审查请求被静默忽略，看起来像 CODEOWNERS 没生效
取哪个分支的文件用 PR 的 base 分支上的 CODEOWNERS在 PR 里改 CODEOWNERS 期望立即对本 PR 生效
是否强制只有在分支保护里勾了「需要 code owner 审查」才是硬门槛，否则只是自动请求审查以为写了文件就等于强制
作者恰好是唯一 owner自己不能批准自己的 PR单人团队守着一个目录，结果谁都合不了，必须扩容 owner
语法错误仓库里有专门的 CODEOWNERS 错误提示页面，规则可能整体不按预期生效改完不验证，以为生效了

fork PR 的权限边界：secrets 为什么必须不可见

来自 fork 的 PR 携带的是不可信代码——它可以改构建脚本、改依赖、改测试。GitHub 的处理方式是：pull_request 事件下，GITHUB_TOKEN 降为只读，所有 secrets 不下发，并且默认还要求维护者手动批准首次贡献者的工作流运行。

pull_request_target 的防御性用法只有一条铁律：不要检出 PR 的 head，更不要执行它的任何脚本（包括 npm ci 会触发的生命周期钩子、构建脚本里的 make）。确实需要「编译不可信代码 + 用 secrets 做事」时，拆成两段：

# ===== 工作流 A：跑不可信代码，没有任何 secrets =====
name: pr-build
on: pull_request               # fork PR 下 token 只读、secrets 不可见
permissions:
  contents: read
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4        # 默认检出 PR 合并 ref
      - run: npm ci
      - run: npm run build
      - run: mkdir -p out && echo "${{ github.event.number }}" > out/pr-number
      - uses: actions/upload-artifact@v4
        with:
          name: build-out
          path: out/

# ===== 工作流 B：用 secrets 做事，但绝不碰 PR 的代码 =====
name: pr-report
on:
  workflow_run:                # 工作流定义与代码都取自默认分支，可信
    workflows: [pr-build]
    types: [completed]
permissions:
  contents: read
  pull-requests: write         # 只提权到真正需要的这一项
jobs:
  report:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/download-artifact@v4
        with:
          name: build-out
          run-id: ${{ github.event.workflow_run.id }}
          github-token: ${{ secrets.GITHUB_TOKEN }}
      # 把 artifact 内容当「数据」处理：不要拼进 run 的 shell 脚本，
      # 也不要写成 ${{ }} 直接插值，否则 PR 里的内容能改写你的命令
      - run: python3 ./ci/post-comment.py out/pr-number

GITHUB_TOKEN 的最小权限，以及「它不会触发自己」

两件必须知道的事。第一，permissions 是整体替换而不是增量：一旦你在工作流或 job 上写了 permissions 块，所有没列出的权限都变成 none。所以正确姿势是工作流级写 contents: read，个别需要写权限的 job 单独声明。仓库和组织层面还有一个「默认 token 权限」开关，老仓库常常还停在「读写全部」，应该收成只读。

第二，用 GITHUB_TOKEN 推送的提交、创建的 tag，不会触发新的工作流运行。这是平台为防止无限递归做的硬限制，但它常年被误判成 bug：自动打 tag 的流水线跑完了，监听 tag 的发布流水线却一动不动。绕开的办法是用 PAT 或 GitHub App 的 token（后者更可控，可按仓库和权限精细授予，且有过期时间）。

release 与 tag 的关系：两个对象，不是一个

tag 是 Git 里的一个引用，release 是 GitHub 上挂在某个 tag 名字上的平台对象。它们的生命周期是分开的，这导致一批「以为联动其实没联动」的问题。

三个实践建议：其一，不要让下游依赖 latest——那个标记不是按语义化版本算出来的，给老分支补发一个 patch 之后它可能落到你不想要的版本上，下游该钉死具体 tag。其二，on: release / types: [published] 会把预发布也带进来，job 里要判断 prerelease 字段。其三，CI 里 git describe --tags 失败是高频问题：actions/checkout 默认只抓一层历史且不抓 tag，需要显式要求完整历史或显式抓 tag。

Dependabot 与依赖更新策略

先分清两套机制：安全更新由 Dependabot alerts 驱动，是仓库开关，只针对有漏洞的依赖；版本更新必须自己写 .github/dependabot.yml，按生态和目录逐个声明。很多团队只开了前者就以为依赖在自动更新。

另一个专属坑：Dependabot 发起的 PR 触发的工作流拿不到普通 Actions secrets，只能访问 Dependabot 专属的那套 secrets，并且 token 只读。所以「Dependabot 的 PR CI 全红，人工提的同样内容却全绿」，原因通常是 CI 要用私有仓库凭据或私有 registry 凭据——把凭据同时存一份到 Dependabot secrets 里即可。

# .github/dependabot.yml
version: 2
updates:
  - package-ecosystem: gomod
    directory: /
    schedule:
      interval: weekly
      day: monday               # 固定在周一，避免周五合依赖更新
    open-pull-requests-limit: 5 # 默认就是 5，调大会淹掉 review 队列
    groups:                     # 分组：补丁与小版本合成一个 PR，减少噪音
      go-patch-and-minor:
        patterns: ['*']
        update-types: [minor, patch]
    ignore:
      - dependency-name: github.com/some/heavy-framework
        update-types: [version-update:semver-major]   # 大版本手动排期，不自动提

  - package-ecosystem: github-actions
    directory: /                # Actions 的更新也要管：第三方 action 是执行你 CI 的代码
    schedule:
      interval: weekly

  - package-ecosystem: docker
    directory: /
    schedule:
      interval: weekly

安全补丁（有 CVE）立刻CI 全绿可自动合暴露窗口的代价最高
补丁 / 小版本每周分组一次可自动合，但要有回归测试兜底逐个提 PR 会淹没 review
大版本手动排期不可有破坏性变更，需要读 changelog
第三方 GitHub Action每周可自动合，但建议钉到 commit SHA它是在你的 CI 里执行代码的，tag 可被重新指向
基础镜像每周视发布流程镜像更新会影响所有运行时
间接依赖跟随 lockfile可自动合直接指定版本反而会锁死上游

Issue/PR 模板与自动化标签

模板的收益不在「格式统一」，而在把排查所需的信息前置：版本号、复现步骤、环境。用 YAML 的 issue forms（.github/ISSUE_TEMPLATE/*.yml）可以把字段设成必填，比 Markdown 模板可靠得多，因为 Markdown 模板里的提示会被人整段删掉。配套的 config.yml 可以关掉空白 issue 并把提问引流到 Discussions。

能力放在哪限制 / 坑

最容易踩的坑

❌
这些坑每一条都出过事故
  • 把 required check 直接指向矩阵 job：矩阵取值一改，旧检查名永远 Expected，PR 全部卡住。只把一个名字固定的聚合 job 设为必需。
  • 聚合 gate job 忘了 if: always()：上游一失败它自己也被跳过，检查永远不上报，PR 反而更死。
  • 用 paths 过滤掉整个工作流又把它设为必需：工作流被跳过时检查停在 Pending，永远不能合；而 job 被 if: 跳过则上报成功——两者结果相反。
  • 启用合并队列却没在 on: 里加 merge_group：队列里的检查压根不会跑，队列整体卡死。
  • CODEOWNERS 把 * 兜底规则写在文件最后：最后一条匹配胜出，前面所有精细规则全被覆盖。
  • 在 CODEOWNERS 里照 gitignore 写 !path 取反：不支持，排除子目录要再写一条「所有者留空」的规则。
  • CODEOWNERS 里写了没有写权限的人或团队：审查请求被静默忽略，看起来像整份文件没生效。
  • 在 pull_request_target 里 checkout PR 的 head 并执行构建：不可信代码拿到读写 token 和全部 secrets，这是最经典的一类仓库沦陷路径。
  • 把 PR 标题、分支名、评论内容直接插值进 run: 的脚本：这些字段由外部控制，等于命令注入。当成数据传给脚本参数或环境变量。
  • 写了 permissions 块却只列一项：没列出的权限全部变 none，后面的步骤莫名 403。
  • 指望用 GITHUB_TOKEN 打的 tag 去触发发布流水线：平台明确不会为它创建新的工作流运行，必须换 PAT 或 GitHub App token。
  • 删了 release 以为 tag 也没了（或反过来）：两个对象独立，重发同名版本时会撞上残留的 tag。
  • 让下游拉 latest release：它不是按语义化版本排序的，补发老版本 patch 会把下游带到错误的包上。
  • CI 里 git describe --tags 失败：actions/checkout 默认浅克隆且不抓 tag，需要显式要求完整历史或抓取 tag。
  • Dependabot 的 PR CI 全红：它只能拿到 Dependabot 专属 secrets、token 只读，私有 registry 凭据要额外存一份。
  • 第三方 action 用 @v3 这种可变 tag 引用：tag 能被重新指向，等于让别人随时替换在你 CI 里执行的代码，钉到 commit SHA。
  • squash 合并一个长期存在的分支后继续在该分支上开发：原提交不在 main 历史里，下次合并会重放旧改动并制造大量冲突。
  • 选了 rebase 合并却不要求每个中间提交都过 CI：git bisect 会停在编译不过的提交上，只能 skip，定位区间越切越糊。
