PlantUML 的建模表达力与协作流程

🏷️ 代码生图

PlantUML 的价值不在画图，在于把设计写成可评审的文本

PlantUML 的常见介绍是「支持 UML 全系列」，这句话对选型几乎没有帮助。它在工程里真正不可替代的地方是两点：图种的语义覆盖到了 UML 的行为建模（并发、错误分支、临界区、生命周期），以及源文件足够啰嗦，啰嗦到可以被逐行评审。参与者、别名、消息、分组全部写成文本，PR 里改三行就是改三行，评审人能看出改了什么。

它的布局能力不属于它自己——类图、组件图、部署图这些默认由 Graphviz 的 dot 排版，布局为什么「调不动」、rank 与 cluster 真正约束了什么，详见站内《Graphviz 的布局算法与大图治理》。本文只谈建模表达力和团队流程。

哪些图在设计评审里真的有产出

判断标准不是「UML 规范里有没有」，而是「评审现场被追问的那个问题，这张图能不能回答」。下面把问题和图对齐，剩下的图类型不是错，而是产出比太低。

图类型它回答的问题评审里的真实价值典型失效模式
时序图跨进程一次交互的往返顺序、失败后各方语义最高。错误分支和超时一画出来，设计漏洞基本自己暴露只画正常路径；把异步消息画成同步返回；参与者超过六个后无法阅读
状态图对象生命周期、允许的转移、终态高。幂等、重试、补偿的讨论都要落在状态机上状态不互斥（其实是两个正交维度）；缺终态；把动作当条件写在转移上
组件图系统由哪些可替换单元组成、通过什么接口耦合高。它定义了「换掉一个实现要动谁」把部署单元、代码包、类混在一张；接口不画出来只留一堆箭头
部署图代码跑在什么执行环境上、拓扑与边界高，尤其容量与故障讨论副本数一律画成 1；信任边界与网络边界完全不画
类图领域概念之间的关系与基数中。只在刻意限定到领域模型时有效从代码反向生成全量类图，等于把包结构重画一遍，零信息量
用例图谁能对系统做什么低。后端评审里几乎不产生决策被当成需求清单使用，结果和需求文档双份维护、互相矛盾
💡
反向生成类图是最常见的浪费

用工具从代码导出全量类图，得到的是包结构的另一种渲染，而不是设计。它不会告诉你聚合边界在哪、哪个不变量必须成立、哪些字段是外部契约。真有价值的类图是手写的、被刻意裁剪过的领域模型图，通常十个类以内。需要看真实依赖关系时，用生成式的依赖图（见站内 Graphviz 篇）而不是类图。

时序图的表达力边界

时序图是 PlantUML 相对其他文本画图工具优势最明显的地方，因为 UML 的交互片段（combined fragment）它基本都支持。但每个关键字的语义必须用准，用错了图会撒谎。

记法真实语义常见误读评审时该追问什么
alt / else互斥分支的静态穷举以为它描述了某一次实际执行还有没有没列出来的 else，尤其超时和部分成功
par片段之间没有顺序约束当成「开了几个线程」或保证并发并发下有没有共享状态，谁负责合并结果
critical区间内不允许被其他消息插入当成「很重要」的强调互斥靠什么实现，锁的粒度和超时是多少
loop重复执行，次数或条件写在标签里标签只写「重试」，没有上限最大次数、退避策略、放弃后的状态
group纯标签框，零执行语义拿它当 alt 用这个框是想表达分支还是仅仅命名一段
实线实心箭头同步调用，调用方阻塞等结果——超时是多少，超时后是重试还是失败
虚线箭头返回消息被误当成「异步」返回值里有没有区分「失败」与「未知」
细线开箭头异步消息，发出即返回被误当成普通调用消息丢了谁负责补偿，是否至少一次投递

组件图与部署图：两个框代表的不是一类东西

这两种图在架构评审里位置最高，也被混得最多。区别不在画法，在「框代表什么」：组件图的框是可替换的实现单元，部署图的节点是运行时的执行环境。一个服务在组件图里是一个框，在部署图里可能是三个副本分布在两个可用区。

维度组件图部署图C4 容器图
框代表可替换的实现单元与它暴露的接口执行环境：物理机、虚机、容器、运行时可独立部署运行的进程或数据存储
边代表编译期或装配期依赖、接口提供与需求通信通道与协议运行期调用，标注协议与用途
换掉一个框的成本换实现，接口不变即可换机器或换编排方式换一个可独立发布的进程
最容易缺的东西接口本身（只剩一堆无语义箭头）边界与副本（全画成 1）把容器画到了类的粒度

抽象层级混用为什么是致命错误、箭头语义为什么必须统一，是信息设计问题，见站内《技术文档里的图：该画什么，不该画什么》。这里只强调 PlantUML 层面的落地：部署图用嵌套 node 表达可用区与宿主的包含关系，组件图用 () 显式画出接口而不是只连箭头，需要微调相对位置时用 together { } 和 [hidden] 边，别去和布局引擎硬碰。

C4 与 PlantUML 的结合点是「抽象层级的纪律」

C4 不是新的图形规范，也不替代 UML；它提供的是一套强制分层的纪律：上下文、容器、组件、代码四层，每层只允许出现同一量级的元素。PlantUML 的价值在于 stdlib 自带 C4 宏，这些宏把「这一层能画什么」编码成了函数签名——你想在容器图里画一个类，写不出来。

层级读者与用途PlantUML 落地该不该进仓库更新频率
上下文对外沟通、新人第一张图Person、System、System_Ext、Rel该进，半年级别稳定极低，系统边界变了才改
容器技术评审主力图Container、ContainerDb、Container_Boundary该进，且必须随发布单元变化更新中，新增可独立部署的进程时
组件单个容器内部的责任划分Component、Component_Boundary只对复杂容器画，其余不画较高，容易过期，画了就要有人管
代码类与接口理论上用类图基本不该手画随代码变，手画必过期，要看就去看代码

include 与共享样式：让几十张图长得一样

一个仓库里图一多，最先失控的不是内容而是外观：字体不同、颜色不同、同一个服务在三张图里三个名字。解决办法是把样式和领域词汇抽成公共文件，图文件里只留结构。

机制作用适用坑
!include按路径插入整个文件公共样式、公共参与者定义路径相对「当前文件」；CI 的工作目录变了就找不到
!include <stdlib>引用内置库（含 C4、图标集）C4 建模、云厂商图标库随版本变动，升级 jar 可能改变外观
!includeurl 远端从 URL 拉取几乎不该用构建结果依赖外部站点；安全档位收紧后直接失败
style 块CSS 风格选择器，可按图种与元素设定新项目的首选样式手段与 skinparam 混用时优先级容易搞混
skinparam键值式外观参数style 覆盖不到的补漏散落在各图里就是灾难，必须集中到公共文件

渲染依赖：哪些图需要 Graphviz

「PlantUML 要装 Java 和 Graphviz」这句话只对了一半。是否需要原生依赖取决于图种，这直接决定你的 CI 镜像有多大、以及能不能在纯 JVM 环境跑。

图种需要 GraphvizSmetana 替代备注
时序图不需要无关PlantUML 自己排版，位置由书写顺序决定
活动图（新语法）、甘特图、思维导图、WBS不需要无关纯 JVM 可用，适合轻量 CI
类图、对象图需要基本可用缺 dot 时直接报错，不是画得丑

状态图、用例图、ER 图需要基本可用状态图节点少，Smetana 差异不明显

把设计图纳入代码评审

设计图和代码分家，是图必然过期的根本原因。可行的做法只有一个：.puml 与它描述的代码同仓库、同 PR，评审对象是源文件，图片只是它的一个视图。

sequenceDiagram participant A as 作者 participant CI as CI participant V as 渲染产物 participant R as 评审人 A->>CI: PR 中修改 order-pay-seq.puml CI->>CI: 先全量解析，语法错误直接失败 CI->>V: 渲染 SVG 作为构建产物 V-->>R: PR 页面上可直接看图 R->>A: 支付超时那条 alt 的 else 在哪 A->>A: 补超时分支与 critical 块 A->>CI: 再次推送，源文件 diff 只有几行 CI->>V: 命中元数据缓存，只重渲染这一张 R->>A: 图与实现对得上，合入 Note over A,R: 评审的是文本，图只是视图
所以「改了什么」一目了然 
#!/usr/bin/env bash
set -euo pipefail
JAR=tools/plantuml.jar          # 版本跟仓库走，不要用开发机上的随机版本

# 0) 依赖自检：把这行的输出留在构建日志里，后来所有人都省一次排查
java -jar "$JAR" -testdot

# 1) 只校验语法不出图；先全量解析再生成，语法错误让流水线立刻变红
#    PlantUML 自己支持 ** 递归通配，交给它展开比 shell 更可靠
java -jar "$JAR" -checkonly -failfast2 "docs/**/*.puml"

# 2) 渲染：多线程 + 跳过元数据未变化的图，这是产物缓存的关键
#    -o 用绝对路径，否则输出目录是相对每个输入文件的
java -jar "$JAR" -tsvg -nbthread auto -checkmetadata \
     -o "$PWD/build/diagrams" "docs/**/*.puml"

# 3) 收紧安全档位，防止图文件里的远端 include 把外部内容带进构建
#    完全沙箱会连本地 include 一起禁掉，需要共享样式时用白名单档位
#    并只放行公共目录（白名单路径属性名以所用版本文档为准）
java -DPLANTUML_SECURITY_PROFILE=SANDBOX -jar "$JAR" \
     -tsvg -o "$PWD/build/diagrams" "docs/adr/**/*.puml"

大图拆分与命名规范

图失控几乎都是从「再加一个框」开始的。可执行的纪律是两条：一张图只回答一个问题；文件名要能让人不打开就知道里面是什么。

症状机制怎么做注意
时序图参与者超过六七个ref over子流程抽成独立图，主图只留引用占位被引用的图也要进评审，否则等于把复杂度藏起来
确实需要连续阅读的长流程newpage按阶段切页会生成多个带序号的产物文件，引用链接要跟着变
一个文件里多张图@startuml 名字给每张图命名，产物文件名可预测不命名就会得到一串 diagram1、diagram2
找不到某张图命名规范域、视图类型、层级都进文件名，例如 order-seq-pay.puml目录结构要和代码模块对齐，图才不会被遗忘
❌
最容易踩的坑

1. 以为 alt 描述了某次真实执行——它只是互斥分支的静态穷举，评审时该问的永远是「漏了哪条 else」。

2. 用 group 代替 alt——group 只是个带标签的框，没有任何执行语义，读者会误以为那里有分支。

3. 把虚线返回箭头当异步——虚线是 return，异步是细线开箭头；画错会让评审人以为调用方不会阻塞。

4. par 当成线程模型——它只表示片段之间没有顺序约束，既不保证并发也不描述调度。

5. 从代码反向生成全量类图当设计图——它是包结构的另一种渲染，不含聚合边界与不变量，看代码更快。

6. 组件图里混进部署信息，或部署图里混进代码包——两者的框代表的东西根本不同，混了之后「换掉一个框的成本」无法回答。

7. 部署图副本数一律画 1、信任边界不画——容量和故障讨论完全没法在图上进行。

8. C4 容器图画到类的粒度——C4 的全部价值就是层级纪律，破了纪律就只剩一张更乱的框线图。

9. 用远端 URL !includeurl 拉样式或宏——构建结果依赖外部站点，安全档位一收紧就整体失败，而失败信息通常指向不了根因。

10. skinparam 散落在每张图里——改一次外观要动几十个文件；应集中到公共样式文件，新项目优先用 style 块。

11. CI 里只渲染不校验——图渲染成功不代表语法没问题，应先做纯语法检查并开启全量解析后再生成，让错误在生成前暴露。

12. 设计图放在独立的文档仓库——和代码分家的图必然漂移，且没人会在改代码时想起它。
