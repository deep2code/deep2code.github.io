OCR 流水线的工程结构与准确率来源

🏷️ OCR

准确率来自哪里：流水线的责任划分

OCR 项目失败的典型路径是把它当成「调用一个引擎」。实际上引擎只负责其中一段，最终的字段准确率是整条流水线的乘积：取图质量、几何校正、版面分析、字符识别、后处理校验，任一环节掉链子，后面几环再好也补不回来。识别阶段的参数调整通常是收益最小的那一环。

影响因子作用机制影响量级可控手段
字符像素高度文本行会被归一化到固定高度送入网络，原图字太小等于信息不存在，放大只是插值决定性提高扫描分辨率或缩短拍摄距离，测量行高后按目标高度缩放
几何形变倾斜与透视让文本行检测切歪，一行被切成两段或与相邻行粘连决定性先做透视与倾斜校正，再进版面分析
版面结构分栏与表格判断错误会让阅读顺序错乱，单字识别再准输出也不可用决定性裁剪感兴趣区域、按模板切块、固定分割模式
光照与背景阴影、印章、底纹与文字灰度重叠，全局阈值会连带吃掉笔画显著局部自适应阈值、背景估计后相除、形态学去线条
语言与字库匹配训练字体覆盖不到的字形（艺术字、针式打印点阵）解码分布发散显著换更贴近的模型，必要时在自有样本上微调
引擎参数分割模式与引擎模式影响的是切块策略与解码路径边际按版面类型固定一套，不要逐图试参数
后处理约束字段格式、校验位、业务交叉校验把错误拦在系统之外决定性（对业务正确率）每个结构化字段都必须有校验规则与兜底分支

引擎内部：版面分析与序列识别是两件事

Tesseract 4 之后的主力是 LSTM 序列识别器，但版面分析那一套仍然沿用传统的连通域与投影方法。于是会出现一种典型现象：单个字符识别得很准，整页输出的顺序却是错的——错在版面分析，不在识别器。理解这个边界，才知道该改哪一层。

引擎模式实际含义对模型文件的要求适用与限制
传统引擎基于字符切分加特征匹配的老路线模型文件必须包含传统引擎数据，纯神经网络的模型加载会直接失败只在需要字符级切分或兼容历史配置时使用
神经网络引擎整行序列解码，不做硬性单字切分需要 LSTM 数据，主流发行包都带默认选择，对粘连字符和不等宽字体明显更稳
组合模式历史上的两引擎联合要求两套数据同时存在新版本已不建议使用，不要指望它自动取长补短
自动模式按模型文件里实际可用的数据自动选无行为依赖安装包内容，同一条命令在两台机器上可能走不同路径，生产上必须显式指定
精度型模型文件浮点权重，体积大速度慢微调训练只能用这一套准确率优先，或需要在自有样本上继续训练
速度型模型文件整数量化权重不能用于继续训练吞吐优先、字形规整的批量场景

另一个容易踩的边界：字符白名单参数在神经网络引擎下并不可靠，不要指望用它把「只可能是数字」的字段锁死。要约束字符集，正确位置是后处理的正则与词典，或者干脆在自有数据上微调。

页面分割模式：按版面类型固定，而不是逐图试

分割模式引擎做了什么什么时候用失效表现
全自动（默认）完整版面分析，但不做方向与文字方向检测规整的单页文档、分栏明确的印刷品整页旋转时输出几乎全错，因为它根本不判断方向
自动加方向检测先判断旋转角度与书写方向，再做版面分析来源方向不可控的扫描批次额外耗时；小图上方向检测本身不稳
单列可变字号假设只有一列，允许行高不同发票明细、单列清单真有两栏时会把两栏内容交错拼成一行
单一文本块跳过分栏判断，整块按行识别已裁好的区域、表格单元格输入其实是多栏时顺序全乱
单行或单词不做版面分析，直接解码一行或一个词模板化字段裁剪之后裁剪框稍有偏移就会丢字符
稀疏文本寻找散落的文字，不假设版面顺序截图、界面图、地图标注阅读顺序不可依赖，只能按坐标使用

工程结论是：先裁区域，再用固定模式。让引擎对整张复杂票据做自动版面分析，等于把最不可控的一环交给它。模板化单据应该用锚点（印章、表头文字、边框）定位后裁剪，再逐块识别。

预处理的顺序比手段更重要

大多数教程把预处理写成一串操作的集合，却不说顺序。顺序错了会引入不可逆的损伤，最典型的就是先二值化再旋转缩放：二值图做插值会产生锯齿和笔画断裂，而中文的细横竖最怕断裂。

import cv2
import numpy as np

# 顺序固定为：几何校正 - 灰度 - 光照归一 - 去噪 - 缩放 - 二值化
# 关键点：所有几何变换和缩放都在灰度图上做，二值化必须是最后一步
def preprocess(path, target_line_h=32):
    img = cv2.imread(path, cv2.IMREAD_COLOR)
    gray = cv2.cvtColor(img, cv2.COLOR_BGR2GRAY)

    # 1) 倾斜校正：用前景像素的最小外接矩形估角度，只纠正小角度倾斜
    #    大角度旋转属于方向问题，交给方向检测或按业务约定处理
    work = cv2.bitwise_not(gray)
    coords = cv2.findNonZero(cv2.threshold(work, 0, 255, cv2.THRESH_OTSU)[1])
    angle = cv2.minAreaRect(coords)[-1]
    if angle > 45:
        angle -= 90
    if abs(angle) > 0.3:
        h, w = gray.shape
        m = cv2.getRotationMatrix2D((w / 2, h / 2), angle, 1.0)
        # 灰度插值用 cubic，边界补白，避免补出的黑边被当成前景
        gray = cv2.warpAffine(gray, m, (w, h), flags=cv2.INTER_CUBIC,
                              borderMode=cv2.BORDER_CONSTANT, borderValue=255)

    # 2) 光照归一：大核闭运算估计背景，再相除消除阴影与底纹
    #    对手机拍摄的单据，这一步比调对比度有效得多
    bg = cv2.morphologyEx(gray, cv2.MORPH_CLOSE,
                          cv2.getStructuringElement(cv2.MORPH_ELLIPSE, (31, 31)))
    norm = cv2.divide(gray, bg, scale=255)

    # 3) 去噪：椒盐噪点用中值滤波；高斯模糊会让细笔画更糊，别乱用
    norm = cv2.medianBlur(norm, 3)

    # 4) 按实际文本行高缩放到引擎习惯的尺度，而不是照搬某个 DPI 数字
    est_h = estimate_line_height(norm)
    if est_h > 0:
        scale = float(target_line_h) / est_h
        if scale > 1.05 or scale < 0.95:
            interp = cv2.INTER_CUBIC if scale > 1 else cv2.INTER_AREA
            norm = cv2.resize(norm, None, fx=scale, fy=scale, interpolation=interp)

    # 5) 二值化放最后：局部自适应阈值对光照不均更稳
    #    中文笔画细，窗口太小会把笔画切断，常数项太大会掉笔画
    return cv2.adaptiveThreshold(norm, 255, cv2.ADAPTIVE_THRESH_GAUSSIAN_C,
                                 cv2.THRESH_BINARY, 35, 11)

# 用水平投影的前景行段长度中位数估计文本行高
def estimate_line_height(gray):
    bw = cv2.threshold(gray, 0, 255, cv2.THRESH_BINARY_INV + cv2.THRESH_OTSU)[1]
    rows = (bw.sum(axis=1) > 0).astype(np.int8)
    runs, cur = [], 0
    for v in rows:
        if v:
            cur += 1
        elif cur:
            runs.append(cur)
            cur = 0
    if cur:
        runs.append(cur)
    return int(np.median(runs)) if runs else 0
步骤放错位置的后果正确位置
倾斜与透视校正在二值图上旋转产生锯齿与断笔，后续笔画粘连灰度阶段，用双三次插值，边界补白
光照归一跳过它直接用全局阈值，阴影一侧整片变黑或整片丢字灰度化之后、二值化之前
去噪高斯模糊放在缩放之后，会抹掉刚放大出来的笔画细节光照归一之后，优先中值滤波
缩放在二值图上放大只是把锯齿放大，信息没有增加灰度阶段，按测量出的行高定倍数
二值化最先做等于丢掉全部灰度信息，后面每一步都在残次品上操作整条链路的最后一步
去表格线二值化前做会连带削弱笔画二值化之后，用长条结构元素做形态学处理
反色统一浅底深字与深底浅字混批，模型按深字训练，白字黑底会大面积失败入库前统一到深字浅底

中文场景的额外变量

中文类别数是数千级，字形差异又常常只在一两笔上，这带来几个和英文不同的工程结论。第一，语言模型的帮助小得多：英文靠词典能纠正大量拼写错误，中文没有词边界，词典增益有限，识别更依赖图像质量。第二，形近字混淆是系统性的而不是随机的，同一批单据会稳定错同几个字，这类错误适合用业务词表做后处理映射。第三，竖排文本需要专门的模型，用横排模型识别竖排会得到逐字断行的结果。第四，简繁混排、异体字、地名生僻字要么补词表要么走人工，不要指望参数。

# 确认模型文件真的装到位了，报「无法加载语言」基本都是这一步的问题

# 输出 tsv 才能拿到每个词的坐标与置信度，纯文本输出等于丢掉一半信息
tesseract page.png out -l chi_sim+eng --oem 1 --psm 6 \
    -c user_defined_dpi=300 tsv

# 批量处理：引擎内部用 OpenMP 做行内并行，单图加速比很有限。
# 正确做法是把内部线程限制为 1，然后在进程级并行，吞吐明显更高。
export OMP_THREAD_LIMIT=1
ls pages/*.png | xargs -P 8 -I{} sh -c \
    'tesseract "{}" "out/$(basename "{}" .png)" -l chi_sim --oem 1 --psm 6 -c user_defined_dpi=300 tsv'

表格与多栏：为什么这是最难的部分

识别引擎的输出是文本流，表格是二维结构，这个鸿沟不是提高字符准确率能解决的。表格恢复本质上是三个独立问题：找到单元格边界、把文本归属到单元格、还原跨行跨列关系。有框线时可以靠形态学提取横竖线段再求交点；无框线时只能依赖列间空白的垂直投影和对齐关系，而它对倾斜极其敏感——不到一度的倾斜就足以让空白列消失。

还有几个稳定的坑：跨页表格的表头要在拼接阶段处理，不能指望单页识别；合并单元格在文本流里没有任何痕迹，必须靠坐标推断；数字列的小数点与千分位分隔符在低分辨率下互相混淆，这类字段一定要配格式校验。

置信度、复核阈值与下游校验

置信度是最容易被误用的输出。它来自解码器打分，不是标定过的正确概率：形近字错认时分值经常很高，而正确结果遇到少见字体也可能偏低。它的正确用途是排队——决定哪些样本先给人看，而不是断言哪些结果可信。

分档判据组合处置理由
自动放行置信度高 且 格式校验通过 且 交叉校验一致直接入库三重条件同时成立时，残余错误率已低于人工录入
轻量复核置信度高 但 交叉校验不一致只把冲突字段推给人典型是明细求和与合计不等，冲突点明确，复核成本低
强制复核格式校验失败整单进队列格式错说明这一块识别不可信，相邻字段大概率同样有问题
置空不猜置信度低 且 没有可用校验规则字段留空并标记下游拿到空值会走缺失分支，拿到错值会静默算错
整批告警同一批次低置信比例突然上升暂停自动放行通常是上游换了扫描设备、纸张或模板版本
拒绝处理识别不出模板类型返回不支持强行识别会产出看起来合理的错误数据，比拒绝更糟
 
import csv
import re
from datetime import date

AMOUNT_RE = re.compile(r'^-?\d{1,3}(,\d{3})*(\.\d{1,2})?$|^-?\d+(\.\d{1,2})?$')

# 解析 tsv 输出：拿到每个词的文本、置信度和像素坐标。
# conf 为 -1 的行是版面结构行（页 块 段 行），不是识别结果，必须过滤掉。
def load_words(tsv_path, min_conf=0):
    words = []
    with open(tsv_path, encoding='utf-8') as f:
        for row in csv.DictReader(f, delimiter='\t', quoting=csv.QUOTE_NONE):
            conf = float(row['conf'])
            text = (row['text'] or '').strip()
            if conf < 0 or not text:
                continue
            if conf >= min_conf:
                words.append({
                    'text': text, 'conf': conf,
                    'box': (int(row['left']), int(row['top']),
                            int(row['width']), int(row['height'])),
                })
    return words

# 金额字段：先做字符级纠正，再做格式校验，两者都不过就返回 None。
# 宁可给下游一个缺失值，也不要给一个看起来合法的错值。
def normalize_amount(raw):
    fixed = (raw.replace(' ', '')
                .replace('O', '0').replace('o', '0')
                .replace('l', '1').replace('I', '1')
                .replace('，', ','))
    # 低分辨率下小数点常被认成逗号，只在「末两位」这种可判定的形态下才纠
    if re.match(r'^-?[\d,]+,\d{2}$', fixed) and fixed.count(',') == 1:
        fixed = fixed[::-1].replace(',', '.', 1)[::-1]
    if not AMOUNT_RE.match(fixed):
        return None
    return round(float(fixed.replace(',', '')), 2)

# 业务级交叉校验：明细求和必须等于合计，日期必须落在合理区间。
# 交叉校验能抓住置信度看不出来的错误，这是自动放行的前提条件。
def validate_invoice(fields, line_items):
    problems = []
    total = normalize_amount(fields.get('total', ''))
    if total is None:
        problems.append('total_unparsable')
    else:
        items = [normalize_amount(x) for x in line_items]
        if any(v is None for v in items):
            problems.append('line_item_unparsable')
        elif abs(sum(items) - total) > 0.01:
            problems.append('sum_mismatch')
    d = fields.get('issue_date')
    if not d or not (date(2000, 1, 1) <= d <= date.today()):
        problems.append('date_out_of_range')
    return problems

引擎分工与批量处理的资源账

方案擅长明确不擅长工程代价
本地开源引擎规整印刷体、离线与数据不出网、单位成本可控手写体、艺术字、复杂表格结构、严重形变预处理与版面工程量全部自己承担
中文专用检测加识别模型自然场景与中文密集文本，自带文本检测要保吞吐通常依赖 GPU，模型版本管理有成本需要部署与显存规划，微调需要标注数据
云 OCR 接口票据证件等标准模板的结构化输出，免运维数据出网、模板外场景不可控、接口行为随版本变化依赖外部可用性，必须有配额与降级策略
视觉大模型版面理解、键值抽取、非固定格式的语义归一不保证字符级忠实，长数字串与罕见字段容易被「补全」，难给坐标延迟与成本高，必须配格式校验与幻觉拦截
条码与二维码解码库直接得到带校验的数据不是 OCR 的活几乎为零，能用它就不要用识别
人工复核兜底一切异常样本吞吐与一致性必须设计队列、抽检与反馈闭环

批量处理的资源账要按单张峰值算，而不是按平均。一张 A4 用高分辨率渲染出来是千万像素级，灰度图几十兆，彩色再加上处理过程中的多份中间拷贝，单张峰值上百兆很常见。并发数乘以单张峰值就是内存下限，超了就是被内核杀掉。另一个隐藏成本是进程启动与模型加载：用命令行封装的调用每张图都要重新加载模型，长期批量应该改成常驻进程池。

❌
最容易踩的坑

1. 先二值化再旋转或缩放——二值图插值产生锯齿与断笔，中文细笔画首当其冲；几何变换和缩放必须在灰度图上完成。

2. 把 300 DPI 当成硬指标——起作用的是字符实际像素高度，元数据里的 DPI 可以完全不可信，应该测量行高再缩放并显式声明分辨率。

3. 用全局阈值处理手机拍摄的单据——光照不均时一侧整片糊死，必须先做背景估计与光照归一，再用局部自适应阈值。

4. 指望字符白名单锁定数字字段——该参数在神经网络引擎下不可靠，约束字符集要放在后处理的正则与词典里。

5. 不指定引擎模式就上生产——自动模式按安装包里可用的数据选择路径，同一条命令在两台机器上结果可能不一致，问题极难复现。

6. 用横排模型识别竖排中文——会得到逐字断行的结果，竖排必须换专门的模型。

7. 让引擎对整张复杂票据做自动版面分析——模板化单据应该先按锚点裁剪再用固定分割模式，自动分栏是最不可控的一环。

8. 只取纯文本输出——丢掉坐标与置信度之后，字段定位只能靠全文正则，模板稍变就全线崩溃。

9. 把置信度当正确概率用——形近字错认时分值常常很高；它只适合决定复核优先级，不能替代格式与交叉校验。

10. 结构化字段没有兜底分支——识别不确定时宁可置空并标记，给下游一个看起来合法的错值比缺失危险得多。

11. 按平均内存规划并发——要按单张峰值乘以并发数算，高分辨率渲染加多份中间拷贝很容易把进程推到被内核杀掉的边缘。

12. 在引擎内部开多线程提吞吐——行内并行加速比很低，把内部线程限制为 1 再做进程级并行才有效。

13. 用识别引擎读二维码与条码——专用解码库既有校验位又快得多，这不是 OCR 该干的活。
