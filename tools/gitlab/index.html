GitLab 的权限与合并策略模型

🏷️ GitLab

GitLab 的功能面很宽，但真正影响团队协作质量的只有两组模型：一组决定「谁能动什么」，也就是角色、继承与保护规则；另一组决定「代码以什么形状进主干」，也就是合并方式、审批与合并队列。这两组模型都有明确的判定规则，配错的后果通常不是报错，而是安全防线静默失效。流水线语法层面的细节本篇不展开，见站内 CI/CD 篇。

角色与继承：有效权限是「取上界」

GitLab 的成员角色是一组有序的整数：Minimal Access 5、Guest 10、Reporter 20、Developer 30、Maintainer 40、Owner 50。API 里到处出现的 access_level 就是这些数字，读 API 返回值时直接按数值比较。实例管理员不在这套体系里，它是另一个维度，能绕过项目可见性。Ultimate 版另有自定义角色，做法是选一个基础角色再叠加细粒度能力，而不是新造一套数值。

继承规则只有一句话，但违反直觉：后代里的有效角色是「继承来的角色」与「直接授予的角色」中的较大值，不能更小。在子组里给一个顶级组 Owner 设成 Guest 是做不到的，界面上低于继承值的选项根本不可选。这意味着「先把全员加在顶级组图省事，再到各子组细化」这条路从一开始就是错的——顶级组成员列表就是整个权限模型的上界，权限审计必须从那里开始看。

另一条容易被漏掉的路径是共享。组可以被邀请进另一个组，项目可以被共享给组，这两种情况下的有效角色取「邀请时设定的最大角色」与「该用户在被邀请组内的角色」的较小值。共享是唯一能把有效权限压低的机制，也是审计盲区：项目成员列表里看不到通过共享获得访问权的人。

protected branch 与 push rule 不是一回事

这两个机制经常被当成同一件事配，结果两边都留着缺口。protected branch 判定的是操作者对某个 ref 的权限：允许谁推送、允许谁合并、是否允许强推、是否允许删除、是否要求代码所有者批准，匹配粒度是分支名或通配符。免费版只能按角色粒度选择（无人、Maintainer、Developer 与 Maintainer），要指定具体某个人或某个组需要付费版。

push rule 判定的是推上来的内容本身是否合规，它跑在服务端的 pre-receive 钩子里，对项目或整个组的所有分支生效，包括那些没被保护的分支。它能做的是提交消息正则、分支名正则、作者与提交者邮箱校验、拒绝未签名提交、单文件体积上限、禁止的文件路径与文件名。这是付费版功能，免费实例只能靠自建 server hook 近似实现。

还有两个常被忘记的邻居：protected tag 控制谁能创建和删除标签——只保护了分支却没保护标签，发布用的 tag 就可以被任何 Developer 重打；protected environment 控制谁能部署到某个环境，它和分支保护是两套判定，只锁分支不锁环境时，部署凭据仍然可能被非保护分支上的作业取到。

三种合并方式与压缩提交的组合

项目设置里的合并方式只有三个选项，但它们改变的是目标分支历史的形状，选错之后很难回头。

合并方式目标分支历史形状是否要求源分支先变基是否产生合并提交谁负责解决与目标分支的冲突适合的仓库
合并提交（默认）有分叉，合并提交带两个父不要求总是产生合并时由点击者处理，容易变成第三方解冲突需要按分支回溯变更的仓库
半线性历史的合并提交主线线性，但保留合并提交要求，界面提供变基按钮总是产生作者变基时解想让第一父视角干净又保留合并痕迹
fast-forward 合并完全线性，无合并提交要求不产生作者变基时解强制线性历史，用单个提交作为回滚单元
压缩提交（与上面三项正交）源分支被压成一个提交不改变变基要求取决于合并方式不变四档可选：不允许 / 允许 / 鼓励 / 必须

两个容易被忽视的后果。第一，fast-forward 加上必须压缩，等于把「一个合并请求」变成「一个提交」，回滚粒度非常清爽，但分支内的提交粒度彻底消失，二分查找定位问题时只能定位到整个特性；如果一个合并请求动了几千行，这个代价很大。第二，默认的合并提交方式下，如果没人先变基，冲突会落到点合并的人头上，而他往往是最不了解这段代码的人——把变基责任前移给作者是半线性和 fast-forward 的真正价值，而不是「历史好看」。

merge train：把「合并前验证」串成队列

普通流水线跑的是源分支，通过了只能说明「源分支自己没问题」。目标分支在此期间前进了几个提交，合并之后主干构建照样可能挂——这就是合并队列要解决的问题。它的机制是：每个加入队列的合并请求，都会基于「目标分支 + 队列里所有前序合并请求」的合并结果创建一条新流水线，全部通过才依次合入。

代价很直接。队列里任何一个合并请求失败，它会被移出队列，而它后面所有合并请求的流水线都必须作废重建，因为它们的基底变了。所以队列越长、流水线越慢，一次失败的浪费越大，经验上把队列长度控制在个位数、并保证流水线在十分钟量级，才不会出现「排队半小时最后全部重跑」。合并队列属于付费版功能，前置条件是启用合并结果流水线；具体作业配置见站内 CI/CD 篇，本篇只谈策略。

approval rule 与 CODEOWNERS 的叠加

审批规则和代码所有者是两套独立机制，最终判定是两者都要满足。审批规则是「这个合并请求需要 N 个人批，候选人是这些用户或组」；代码所有者是「触及了这些路径，就需要对应的人批」。同一个合并请求动了三个归属不同的目录，就可能同时需要三个不同分节各出一个批准，再加上全局审批规则的名额，实际需要的人数比设置里任何单个数字都多。

CODEOWNERS 有几条硬规则必须记住：文件只在仓库根目录、.gitlab/、docs/ 三个位置被识别；生效的是目标分支上的那一份，你在合并请求里修改它对当前这个请求无效；同一分节内最后匹配的模式生效，所以宽通配符必须写在前面；要把它从「推荐审阅人」变成硬门槛，必须在目标分支的保护分支设置里打开「需要代码所有者批准」。

Runner 注册、tag 匹配与保护标记

注册方式在 GitLab 15.6 之后换过一次：旧的共享注册令牌被废弃，改成先在界面或 API 里创建 Runner、拿到 glrt- 前缀的认证令牌，再用它注册。这个变化带来一个很容易踩的差异——用认证令牌注册时，标签、是否运行未打标签作业、是否仅限保护分支这些属性由 GitLab 侧的配置决定，命令行上传的对应参数不再生效，很多「我明明写了 tag-list 却不匹配」的问题就出在这里。

Runner 有三个作用域：实例级（所有项目共享）、组级、项目级。作业与 Runner 的配对规则简单但不宽容：带 tags 的作业只会被同时拥有全部这些标签的 Runner 领走，标签是超集没问题、少一个就不行；不带 tags 的作业只会被勾选了「运行未打标签作业」的 Runner 领走。两条规则叠在一起，就产生了最常见的「作业永久 pending 而 Runner 在线」。

「仅限保护分支」这个开关是隔离部署凭据的关键：把生产部署用的 Runner 标记为仅保护分支，再把生产凭据配成受保护变量（只在保护分支与保护标签上暴露），任何人在特性分支上写一个打印环境变量的作业也拿不到。只做其中一半是无效的。

# GitLab 16 之后的注册流程：先在界面或 API 创建 Runner 拿到 glrt- 令牌
# 注意：标签、运行未打标签作业、仅保护分支这些属性在 GitLab 侧配置，注册参数不再覆盖
sudo gitlab-runner register --non-interactive \
  --url "https://gitlab.example.com/" \
  --token "glrt-REPLACE_ME" \
  --executor "docker" \
  --docker-image "alpine:3.20"

# 关键排查命令
sudo gitlab-runner verify        # 令牌是否还被服务端认可，失效的会被列出
sudo gitlab-runner list          # 本机注册了哪几个 Runner，对应哪个实例
sudo gitlab-runner --debug run   # 前台运行，能看到它为什么没领到作业
# /etc/gitlab-runner/config.toml
concurrent = 4          # 整个进程同时执行的作业上限，按核数与内存定，超了作业就排队
check_interval = 3      # 轮询服务端的间隔秒数，太小会打爆 API

[[runners]]
  name = "docker-runner-1"
  url = "https://gitlab.example.com/"
  token = "glrt-REPLACE_ME"
  executor = "docker"
  request_concurrency = 1   # 同时向服务端申请作业的并发，通常保持 1
  [runners.docker]
    image = "alpine:3.20"
    privileged = false      # 只有跑 dind 才需要开，等于把宿主机内核交出去
    volumes = ["/cache"]
    pull_policy = "if-not-present"
  [runners.cache]
    Type = "s3"
    Shared = true           # 多 Runner 共享缓存，否则换一台机器缓存全失效

gitlab.rb 与 TLS 证书不包含需要凭记忆重推导全部配置纳入配置管理仓库
SSH 主机密钥不包含换机后全员收到主机指纹变更告警单独备份，迁移时一起还原
Redis不包含会话全部失效，排队中的后台任务丢失，表现为部分 webhook 与邮件不发通常可接受，但要知道会丢队列
Praefect 数据库不在应用备份内集群无法定位仓库副本作为独立数据库单独备份
 
# 1) 应用数据备份：数据库、仓库、上传、构建产物、LFS、软件包
sudo gitlab-backup create STRATEGY=copy CRON=1
# 产物形如 /var/opt/gitlab/backups/1758600000_2026_09_23_17.4.1_gitlab_backup.tar

# 2) 这一步才是关键：上面的包里没有密钥与配置，必须单独取走
sudo cp /etc/gitlab/gitlab-secrets.json /secure/backup/
sudo cp /etc/gitlab/gitlab.rb          /secure/backup/
sudo cp -r /etc/gitlab/ssl             /secure/backup/
sudo cp /etc/ssh/ssh_host_*            /secure/backup/

# 3) 恢复：先装与备份完全同一个版本，版本不一致会直接失败
sudo gitlab-ctl stop puma
sudo gitlab-ctl stop sidekiq
sudo gitlab-backup restore BACKUP=1758600000_2026_09_23_17.4.1
sudo gitlab-ctl reconfigure
sudo gitlab-ctl restart

# 4) 验证：secrets 与数据库是否配套，这一步才能确认 CI 变量没废
sudo gitlab-rake gitlab:doctor:secrets
sudo gitlab-rake gitlab:check SANITIZE=true

权限与保护规则的配置漂移同样需要定期巡检。下面这段直接读 API，比在界面上逐个项目点开快得多，适合放进定时任务：

TOKEN="glpat-REPLACE_ME"
HOST="https://gitlab.example.com"
PID=42

# 保护分支实况：access_level 里 0 表示无人 30 表示 Developer 40 表示 Maintainer 60 表示管理员
curl -sS --header "PRIVATE-TOKEN: $TOKEN" "$HOST/api/v4/projects/$PID/protected_branches" \
  | jq '.[] | {name, allow_force_push, code_owner_approval_required,
               push: [.push_access_levels[].access_level],
               merge: [.merge_access_levels[].access_level]}'

# 审批规则：approvals_required 为 0 的规则等于没有
curl -sS --header "PRIVATE-TOKEN: $TOKEN" "$HOST/api/v4/projects/$PID/approval_rules" \
  | jq '.[] | {name, approvals_required, rule_type}'

# 项目级审批开关：作者能否自批、加新提交是否清空批准
curl -sS --header "PRIVATE-TOKEN: $TOKEN" "$HOST/api/v4/projects/$PID/approvals" | jq

# 成员实况：注意这里默认不含通过组共享获得访问权的人
curl -sS --header "PRIVATE-TOKEN: $TOKEN" "$HOST/api/v4/projects/$PID/members/all" \
  | jq '.[] | {username, access_level}'

最容易踩的坑

❌
这些坑都能在自己的实例上复现
  • 把全员加在顶级组再想去子组降权：做不到，有效角色取较大值。权限规划必须自下而上，顶级组只放真正需要全局权限的人。
  • 审计只看项目成员列表：通过组邀请和项目共享获得访问权的人不在这个列表里。用 members/all 接口或逐项目检查共享关系。
  • 只配了 protected branch 没配 protected tag：发布标签可以被任何 Developer 重打甚至删除，历史版本的可追溯性就没了。
  • 审批规则建好了但所需批准数是 0：界面上看着有规则，实际一个人都不用批。巡检时必须看 approvals_required 的值。
  • 没关掉作者自批和提交者批准：单人或结对就能闭环完成评审，审批流程形同虚设。
  • 没开「新提交后重置批准」：先拿批准再改代码是最容易实施也最难发现的绕过手法。
  • CODEOWNERS 放错目录或指望它自己拦人：只有根目录、.gitlab/、docs/ 生效，且必须在保护分支里打开强制项；生效的是目标分支上的版本。
  • CODEOWNERS 里把宽通配符写在具体路径后面：同分节内最后匹配生效，写在后面的 * 会把前面精确的规则全部覆盖掉。
  • 用认证令牌注册 Runner 时还在命令行传标签参数：这些属性由 GitLab 侧配置决定，命令行传了不生效，表现就是作业永远匹配不上。
  • Runner 没勾「运行未打标签作业」，作业也没写 tags：双向都不匹配，作业永久 pending，而 Runner 列表里显示在线。
  • 生产 Runner 只勾了「仅保护分支」却没把凭据设为受保护变量（或反之）：两个开关缺一个，特性分支上的作业照样能拿到生产凭据。
  • 只备份 gitlab-backup create 生成的 tar：不含 gitlab-secrets.json，恢复后 CI 变量、集成凭据、双因子密钥全部无法解密，只能清空重录。
  • 把 secrets 文件和备份包放在同一个目录同一个桶：一次泄露等于全量泄露，加密字段的保护完全失去意义。
  • 跨版本恢复备份：恢复要求 GitLab 版本与备份时一致，升级过程中的备份必须记清版本号并保留对应安装包。
  • 启用对象存储后以为备份还是全量的：构建产物、LFS、镜像层已经不在 tar 里，桶要单独纳入备份与保留策略。
