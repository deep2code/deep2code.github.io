GitLab 私有化部署

🏷️ GitLab

GitLab 简介

GitLab 2011 年由 Dmitriy Zaporozhets 和 Valery Sizov 开发，定位是一体化 DevOps 平台。

GitHub 和 GitLab 到底怎么选

一句话：开源项目、要社区流量、不在意数据在第三方服务器，选 GitHub；公司内网部署、数据合规、要深度定制流水线，选 GitLab。我见过太多团队一开始图省事用 GitHub，后来因为"代码不能出内网"被迫全量迁到自托管 GitLab，迁移成本很高。

核心功能

  • 代码托管：Git 仓库，支持公共/私有/fork
  • Merge Request：合并请求（GitLab 叫 MR，GitHub 叫 PR，一回事）
  • Issues / Epics：任务追踪 + 史诗级需求管理
  • CI/CD：内置 GitLab CI，.gitlab-ci.yml 配置
  • Container Registry：Docker 镜像仓库
  • Wiki / Snippets：文档和代码片段
  • 自托管：社区版（CE）免费，企业版（EE）付费
flowchart LR A[开发者推送代码] --> B[触发 .gitlab-ci.yml] B --> C[Stage: build 构建] C --> D[Stage: test 测试] D --> E[Stage: deploy 部署] E --> F{部署环境?} F -->|dev| G[开发环境] F -->|staging| H[预发环境] F -->|prod| I[生产环境]

快速开始

注册与创建项目

注册 gitlab.com 或登录自托管实例，创建新项目：

  1. 点 "New project" → "Create blank project"
  2. 填项目名、描述、选公开/私有
  3. 可选初始化 README

SSH 配置与克隆

# 添加 SSH key 到 GitLab Profile → SSH Keys
ssh -T git@gitlab.com  # 测试连接

# 克隆项目
git clone git@gitlab.com:username/project.git
cd project

Merge Request 工作流

GitLab 的 MR 跟 GitHub 的 PR 概念完全一样，我团队的标准流程：

步骤操作
1从 main 创建特性分支
2开发、提交、推送
3在 GitLab 创建 Merge Request
4指定 Reviewer，讨论修改
5CI 通过后合并到 main

GitLab CI/CD

这是 GitLab 的王牌。内置 CI，YAML 描述流水线，不用像 GitHub 那样去市场找 Actions。.gitlab-ci.yml 放在仓库根目录：

stages:
  - build
  - test
  - deploy

build:
  stage: build
  image: node:20
  script:
    - npm ci
    - npm run build
  artifacts:
    paths:
      - dist/

test:
  stage: test
  image: node:20
  script:
    - npm ci
    - npm test

deploy_prod:
  stage: deploy
  image: alpine:latest
  script:
    - echo "部署到生产环境"
  only:
    - main
CI 我常用的三个招
  • 缓存 node_modules：用 cache: 缓存依赖，每次省 30 秒装包时间
  • 分阶段并行：build 和 test 可以并行，deploy 必须串行
  • only/except 控制触发：只在 main 分支触发 deploy，别每个 PR 都部署

GitHub vs GitLab 对比

按部署环境看，两者的流水线设计哲学也不同：

flowchart TD A[需求开发] --> B[特性分支] B --> C[MR 或 PR 审查] C --> D[CI 自动测试] D --> E{CI 通过?} E -->|否| B E -->|是| F[合并主干] F --> G[自动部署] G --> H[监控告警]
维度GitHubGitLab
定位代码托管 + 协作一体化 DevOps 平台
自托管GitHub Enterprise（贵）社区版免费自托管
CI/CDGitHub Actions（市场扩展）内置 GitLab CI
Issue 管理Issues + ProjectsIssues + Epics + Boards（更强）
容器仓库GitHub Packages内置 Container Registry
开源社区最大较小但企业生态强
价格（自托管）Enterprise 很贵CE 免费，EE 按用户付费
适合场景开源项目、外部协作企业内网、合规要求高

最佳实践

  • 用 .gitlab-ci.yml 把 CI/CD 写进仓库，代码即流水线
  • 保护 main 分支，必须 MR + CI 通过才能合并
  • 用环境变量（Settings → CI/CD → Variables）管理密钥，别硬编码
  • 分环境部署：dev → staging → prod 逐级审批
  • 自托管实例定期升级，安全补丁及时打

FAQ

Q：GitLab 社区版够用吗？
绝大多数团队够用。核心功能（仓库、MR、CI/CD、容器仓库）都免费。高级功能（安全扫描、合规审计、多集群部署）才要企业版。

Q：从 GitHub 迁到 GitLab 麻烦吗？
GitLab 有内置导入工具，从 GitHub 一键导入仓库、Issue、PR。CI 要重写成 .gitlab-ci.yml，这是主要工作量。

Q：CI 跑太慢怎么办？
缓存 node_modules、并行跑无关 stage、用更快的 Runner、大仓库开 shallow clone。

总结

GitLab 的定位是"一体化 DevOps"，最大优势是自托管和内置 CI/CD。企业内网、合规要求高的团队选它；开源项目、要社区流量选 GitHub。下一篇 Graphviz，看底层布局引擎。
