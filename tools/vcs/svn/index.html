从 SVN 到 Git：模型差异与迁移路径

🏷️ SVN

两种模型的本质差异：版本标识决定一切

SVN 与 Git 的差别不在命令，而在「什么东西被当作版本标识」。SVN 的版本号是仓库范围内的全局递增整数：一次提交产生一个新的 revision，这个 revision 描述的是整个仓库树在该时刻的状态。Git 用内容哈希标识对象，提交指向树对象，树对象指向子树和文件内容。这一个差别衍生出下游几乎所有行为差异。

Git 侧的对象模型细节、引用与索引的真实语义，站内已有专篇（见 Git 的对象模型与常见操作的真实语义），这里只取结论：Git 的历史是一张由哈希连成的不可变图，分支只是指向其中一个节点的可移动引用；而 SVN 的历史是一条线性的 revision 序列，分支是这条序列里的一次目录拷贝事件。

分支实现目录拷贝，靠 trunk 与 branches 的目录约定识别一等公民引用非标准布局的仓库，自动迁移工具识别不出分支
合并元数据记录在目录属性里，会随合并不断膨胀提交自带多个父指针合并元数据无法翻译，迁移后历史里的合并关系普遍丢失
工作副本状态允许混合版本，不同文件可处在不同 revision整棵树对应唯一提交迁移前必须让副本干净且版本统一，否则导出结果不可解释
空目录是受版本控制的对象不跟踪目录，只跟踪文件迁移后空目录消失，依赖它的构建脚本直接失败
权限粒度可按仓库内路径授权只有仓库级与引用级最容易被低估的迁移阻塞点，见后文
关键字替换与换行属性由文件属性驱动，提交时改写文件内容靠属性文件配置换行，无关键字替换迁移后带标识符占位的文件不再自动更新，需要改构建注入

目录即分支的代价

SVN 建分支是服务端的廉价拷贝，本身几乎不占空间，代价出现在合并侧：分支关系不在提交结构里，而是靠目录属性中的合并信息推断。该属性随反复合并不断细碎化，且挂在目录上——任何目录改名或移动都可能让合并追踪失真，产生 SVN 里最难处理的树冲突。

与之对应的另一个常见误解值得纠正：「Git 必须克隆全部历史」已经不成立。只取最近若干提交的浅克隆、只下载需要的文件内容的部分克隆、以及按目录锥形筛选的稀疏检出，都是成熟能力，CI 场景里几乎是默认做法。因此「仓库太大所以不能用 Git」这条理由在今天需要重新论证，真正站得住的理由是下一节的两条。

命令映射看起来等价语义差异不知道会怎样
提交svn commit 对应 git commit前者一步写到服务端，后者只写本地对象库团队以为提交就等于共享，改动留在本地几天没人看见
更新svn update 对应 git pull前者直接改工作副本且可留下混合版本，后者会产生合并或变基提交把 pull 当 update 用，历史里堆满无意义的合并提交
撤销改动svn revert 对应 git restore前者只作用于工作副本，后者要区分工作区与暂存区两层以为撤销了，实际暂存区里还留着旧内容
切换分支svn switch 对应 git switch前者是把副本重新指向另一个 URL，后者切换的是引用与整棵树期待「切过去改动还在」，结果对未提交改动的处理方式完全不同

SVN 至今仍有优势的两类场景

抛开惯性和合规话术，SVN 真正的技术优势只剩两条，但都很硬：

第一条是路径级权限。SVN 能在一个仓库里对不同目录授予不同读写权限，且对客户端透明——没权限的目录检出时直接不出现。Git 没有等价能力：分布式模型的前提就是完整历史可被复制，权限只能做到仓库级或引用级。想模拟路径隔离只能拆成多个仓库再用子模块拼回来。

第二条是大体积不可合并资产的协作。美术资源、关卡文件这类二进制文件无法三方合并，正确方式是「锁定—修改—解锁」。SVN 用文件属性把它做成了硬约束：标记为需要锁定的文件在本地只读，必须先取锁才能改。Git 侧要依赖 LFS 的锁机制，需服务端支持。

💡
纠正一个流传很广的说法

「SVN 里二进制文件每次提交都全量存储，所以仓库会疯长」并不准确。服务端存的是增量，二进制也做差分压缩。真正的空间问题在客户端：工作副本会为每个文件额外保存一份原始副本，用于在离线状态下计算差异和撤销改动，所以本地占用大约是文件总量的两倍。理解这一点才能解释「检出 10 GB 的目录，磁盘掉了 20 GB」这种现象。

迁移前的决策：先定目标，再选工具

迁移失败的项目八成是从「用哪个工具」开始的。正确顺序是先回答下面几个问题，每个答案都会缩小工具选择范围。

迁移实操：侦察、抓取、清洗、校验

第一步是侦察，不要跳过。仓库的实际布局往往和团队记忆不符。

# 1. 确认布局：顶层是不是标准三目录，分支和标签各有多少
svn info --show-item url https://svn.example.com/repo
svn ls https://svn.example.com/repo
svn ls https://svn.example.com/repo/branches | wc -l
svn ls https://svn.example.com/repo/tags | wc -l

# 2. 抽取全部作者，作为映射文件的输入（提交者用户名往往没有邮箱）
svn log -q https://svn.example.com/repo \
  | awk -F'|' '/^r/ {gsub(/ /,"",$2); print $2}' | sort -u

# 3. 找出分支的起点 revision，判断历史是否被目录重组截断
svn log --stop-on-copy -r 1:HEAD --limit 1 -v \
  https://svn.example.com/repo/branches/release-1.0

# 4. 大文件普查：决定 LFS 规则要在迁移时一次定好
svn ls -R https://svn.example.com/repo/trunk | grep -v '/$' > /tmp/files.txt
while read -r f; do
  sz=$(svn info --show-item repos-size "https://svn.example.com/repo/trunk/$f" 2>/dev/null)
  [ -n "$sz" ] && echo "$sz $f"
done < /tmp/files.txt | sort -rn | head -30

第二步是抓取。网络往返是主要瓶颈，长历史仓库务必先在本地做一份镜像，否则抓取可能要跑上几天，中途断线还得续。抓完之后做三件清洗：转换标签、转换分支、修正忽略规则。

# 作者映射文件格式：SVN 用户名 = 姓名 <邮箱>
# 漏掉任何一个用户名，抓取会直接中断，正好用来强制补全
cat > /tmp/authors.txt <<'EOF'
zhangsan = Zhang San <zhangsan@example.com>
lisi = Li Si <lisi@example.com>
EOF

# -s 按标准三目录布局识别；--no-metadata 用于一次性单向迁移，
# 不保留提交信息里的原始 revision 标记（若要继续双向同步则不能加）
git svn clone -s --no-metadata --authors-file=/tmp/authors.txt \
  --prefix=svn/ file:///srv/mirror/repo newrepo
cd newrepo

# 标签：git-svn 抓成了远端引用，需要转成真正的标签对象
git for-each-ref --format='%(refname:short)' refs/remotes/svn/tags \
  | while read -r t; do
      git tag -a "${t#svn/tags/}" -m "migrated from svn tag ${t#svn/tags/}" "$t"
      git update-ref -d "refs/remotes/$t"
    done

# 分支：同理转成本地分支
git for-each-ref --format='%(refname:short)' refs/remotes/svn \
  | grep -v '^svn/tags/' | grep -v '^svn/trunk$' \
  | while read -r b; do git branch "${b#svn/}" "$b"; done

git checkout -b main svn/trunk
git svn show-ignore > .gitignore    # 把原有忽略属性转成忽略文件
git add .gitignore && git commit -m "chore: 从 svn 忽略属性迁移 gitignore"
git gc --aggressive --prune=now     # 抓取产生的对象很碎，打包后体积能明显下降

第三步是校验。这一步决定了你敢不敢把旧库转只读。校验不是「看起来能构建」，而是逐项对账。

校验项做法通过标准
文件树一致把 SVN 最新版本导出到临时目录，与 Git 检出做递归比较只允许出现忽略文件与空目录两类差异，且每一条都能解释
空目录清单列出 SVN 里所有空目录每个都已加占位文件或已确认构建不依赖它
标签对应逐个标签比对指向的树内容与原 revision 导出结果数量一致且内容逐字节相同
作者完整统计新仓库里的作者列表不存在带仓库标识后缀的伪邮箱
大文件统计最大对象与仓库总体积符合迁移前定下的 LFS 规则，没有漏网的巨型文件进普通对象库

迁移后回退的真正原因：心智模型没迁

技术迁移做完只是开始。我见过的回退案例里，几乎没有一个是因为工具不行，而是团队还在用集中式的习惯操作分布式工具，结果体验比原来更糟，于是得出「Git 不适合我们」的结论。

sequenceDiagram participant O as 旧 SVN 库 participant M as 迁移执行者 participant N as 新 Git 服务 participant T as 团队 M->>O: 侦察布局与作者 抽大文件清单 M->>M: 在本地做一份完整镜像 避免长时间网络抓取 M->>N: 抓取加清洗 转换标签分支与忽略规则 M->>M: 逐项对账 文件树 标签 作者 大文件 M->>T: 先给一周并行期 只读新库 照常用旧库 T-->>M: 反馈缺失的目录权限与构建脚本假设 M->>O: 冻结窗口内确认最后一个 revision M->>N: 增量补齐最后一段提交 并打上切换标签 M->>T: 宣布切换 旧库转只读 T->>N: 全员迁移 提交粒度与分支规范同步落地 M->>O: 保留只读归档 不再接受写入
旧习惯在 Git 上的症状需要建立的新约定
一天攒一次大提交历史不可读，回滚只能整段撤，二分定位失效一个可独立描述的改动一次提交，本地可以先乱提交再整理后推送
只在主线上开发，分支只用于发布主线长期不可构建，多人改同一文件冲突剧烈短生命周期特性分支，配合受保护主线与合并前检查
把更新当同步，冲突交给工具自动处理历史里堆满无意义的合并提交，或反复出现同一冲突明确团队用合并还是变基整理本地提交，并写进文档而不是口头约定
依赖服务端的路径权限做隔离发现新平台管不到目录级，于是认为不安全提前拆仓库或改用代码评审与受保护路径规则，这件事必须在迁移前谈
用全局递增版本号沟通没人能说清「线上是哪一版」发布一律打标签，把标签写进构建产物与运行时版本接口

混合期：双写的成本远高于一次冻结

想要「平滑过渡」而搭双向同步的团队，普遍低估了三件事：循环同步、作者身份往返映射、两边都改同一文件时的冲突裁决——最后一项在工具层面没有正确答案。更现实的策略是让状态单向流动。

stateDiagram-v2 [*] --> SVN可写 SVN可写 --> 并行只读期 : 新库上线 仅供读取与验证 并行只读期 --> SVN可写 : 校验发现问题 回到旧库继续 并行只读期 --> 冻结窗口 : 校验通过 约定停写时间 冻结窗口 --> Git可写 : 补齐最后一段提交 打切换标签 Git可写 --> 只读归档 : 旧库撤销全部写权限 保留可查 只读归档 --> [*] Git可写 --> [*]

归档不等于删除。旧库要保留可查的只读形态，并存好「历史 revision 对应新仓库哪个提交」的映射：保留了原始 revision 标记时它可以随时从提交信息重建，为了历史干净去掉标记的话，就必须在迁移当时单独导出对照表存档。

❌
最容易踩的坑

1. 不做作者映射就开始抓取：全部历史提交的作者变成用户名加仓库标识的伪邮箱，事后修正等于重写全部历史。
2. 直接对着远端 SVN 抓长历史：按 revision 逐条走网络，几万个版本能跑上几天，断线还要续；先做本地镜像再抓。
3. 忘了把标签从远端引用转成真标签：新仓库里看不到任何标签，发布版本无从追溯。
4. 忽略空目录：Git 不跟踪目录，构建脚本假设某个空目录存在时会在新仓库上首次构建就失败，且报错完全不指向版本控制。
5. 没转换忽略规则：首次提交把编译产物、本地配置、IDE 目录一起带进新仓库，之后再清理又要重写历史。
6. 大文件规则拖到迁移之后再定：一旦有人克隆过，改 LFS 规则就要重写历史并让所有克隆失效。
7. 忽略关键字替换与换行属性：依赖占位符自动写入版本号的文件不再更新，跨平台协作时整文件换行全变。
8. 以为路径级权限能在新平台原样实现：这是迁移的硬阻塞点，必须在动手前就决定拆仓库还是改治理方式。
9. 搭双向同步求平滑：循环同步、身份往返映射、双边同文件冲突三个问题叠加，成本远高于一次冻结切换。
10. 只迁工具不迁规范：提交粒度、分支模型、冲突处理方式不同步落地，团队体验比原来更差，三个月后就有人提议迁回去。
11. 迁完立刻删掉旧库：老工单和审计记录里全是旧版本号，没有只读归档和 revision 对照表就再也查不回去。
12. 拿「仓库太大所以不能用 Git」当结论：浅克隆、部分克隆、稀疏检出已经解决了体积问题，真正站得住的理由只有路径权限和不可合并的大资产。
