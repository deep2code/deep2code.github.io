SVN 速查

🏷️ SVN

SVN：被 Git 抢了风头，但还活着

我知道现在说 SVN 有点考古。但我前几年维护一个银行老系统，代码必须放 SVN——合规要求代码不能在开发者本地有完整副本，必须集中管控。这种场景下 SVN 依然是刚需。所以别学完 Git 就鄙视 SVN，集中式和分布式各有各的地盘。

一句话区分

Git 是分布式：每个克隆都是完整仓库，能离线提交、离线分支；SVN 是集中式：必须连服务器才能提交，历史也在服务器上。理解这点，两者命令的差异就顺理成章了。

日常工作流：就四条命令

SVN 的心智模型很简单：你从服务器 checkout 一份工作副本，改完 commit 回去，中间用 update 同步别人的改动。核心就这四条：

命令作用对应 Git
svn checkout URL拉取完整副本git clone
svn update同步服务器最新git pull
svn commit提交改动git commit + push
svn status看本地改动git status

注意一个关键差异：SVN 的 commit 一步就推到服务器了，没有 Git 那种「先本地 commit 再 push」。这就是为什么 SVN 必须联网才能提交——它的设计就是不能离线干活。

# 标准一天流程
svn checkout https://svn.example.com/repo/trunk myproj
cd myproj
# 改完代码
svn status          # 看改了哪些
svn diff            # 看具体改了啥
svn update          # 先同步别人的
svn commit -m "修复登录bug"

为什么集中式设计在合规场景还有市场

flowchart TD subgraph SVN[SVN 集中式] SERVER[中央服务器 唯一完整历史] D1[开发者A] --> SERVER D2[开发者B] --> SERVER end subgraph GIT[Git 分布式] G1[中央裸仓库] A1[开发者A 完整副本] --> G1 B1[开发者B 完整副本] --> G1 end

银行、军工、医疗这些行业要求「代码不离开受控环境」。SVN 的工作副本历史不全、必须连服务器，正好满足这种审计需求。Git 克隆一份就完整历史到手，反而不符合合规。这就是为什么老系统还在 SVN——不是技术落后，是合规要求。

分支和标签：和 Git 完全不同的模型

这是 SVN 最容易把 Git 用户搞懵的地方。SVN 的分支（branch）和标签（tag）本质就是目录拷贝，没有 Git 那种轻量指针概念：

SVNGit
分支本质目录拷贝（svn copy）指针（40 字节）
建分支成本廉价但占空间（copy-on-write）极廉价
合并分支svn merge，易乱三方合并成熟
标签约定目录 /tags/git tag
离线操作不支持全支持

SVN 标准布局是 trunk/ branches/ tags/ 三个目录。建分支就是 svn copy trunk branches/feature-x。我刚从 Git 转过来时，下意识以为分支是轻量的，结果在 SVN 上狂建分支被运维骂——SVN 分支虽然 copy-on-write 不怎么占空间，但合并起来巨痛苦，别滥用。

冲突解决：SVN 比 Git 粗暴

必坑

SVN 冲突比 Git 难处理。流程是这样的：

flowchart TD U[svn update] --> C{有冲突?} C -->|没有| OK[直接 svn commit] C -->|有| M[工作副本留下 .mine .r旧 .r新 三个文件] M --> E[手动比对三版合并] E --> R[svn resolved 标记解决] R --> OK

几个排错命令：

svn info              # 看当前副本的 URL 和版本
svn log -r 123:130    # 看版本历史
svn blame foo.c       # 每行谁改的
svn cleanup           # 卡住了（锁了）就跑这个

svn cleanup 是救命命令——SVN 中断后经常留下锁，下次操作报「working copy locked」，跑 cleanup 就能解。

我的几条实战经验

  • update 在 commit 之前：先同步再提交，能避开 90% 的冲突；
  • 别 svn add 整个目录：先看 status 确认，别把编译产物、IDE 文件加进去；
  • .svn 目录别手删：它是工作副本的元数据，删了副本就废了；
  • 大文件别进 SVN：二进制文件每次都全量存，仓库会疯长，用 Git LFS 或专门的制品库。

FAQ

Q：2026 年了 SVN 还有必要学吗？
如果你不在金融、军工、传统制造行业，基本不用。但这些行业里大量老系统还在 SVN，你可能某天接手一个老项目就得读它。学成本很低——就那几条命令，半天能上手。

Q：SVN 能迁到 Git 吗？
能，git svn clone 可以把 SVN 历史导成 Git 仓库。但分支关系会丢失，迁之前先想清楚。我帮老系统迁过一次，花了一周处理分支映射。

Q：为什么 Git 用户觉得 SVN 难用？
主要是两点：不能离线、分支合并痛苦。Git 用户习惯了随便建分支随便切，到 SVN 上就束手束脚。但这是设计取舍——集中式就是为了管控。

Q：SVN 和 Perforce 比呢？
游戏行业爱用 Perforce（大二进制文件管理强），企业内部系统多用 SVN。2026 年新系统几乎没人新选 SVN 了，都是存量维护。

小结

SVN 不是过时技术，它是集中式版本控制的最后堡垒。你大概率不会新学它，但你可能会维护一个用它的老系统。理解「集中 vs 分布」这个设计差异，比背命令重要。下一篇 Tesseract，看 OCR 怎么把图片里的字认出来。
