Chart.js 的配置模型与容量边界

🏷️ 代码生图

配置树之下：controller、scale、element 的分工

Chart.js 对外只有一个入口，new Chart(canvas, config)，config 里是 data、options、plugins 三棵树。但内部把工作拆给了三类可插拔构件，先看清这个分工，才能判断一个需求「改配置能不能实现」。

DatasetController 把 datasets[i].data 解析成一批 element，并决定每个 element 的几何属性：柱子的 x、y、width、base，点的 x、y、radius。Scale 把数据域映射到像素，同时参与布局——刻度文本要占多宽，直接决定绘图区剩多少。Element 只是几何属性的容器加一个 draw 方法，不含任何数据语义，所以动画才能对它做纯属性插值。外面套一层插件服务分发钩子，最底下是平台层，负责读画布尺寸、绑事件。

这张图给出了第一条边界：配置能改的是同一套「数据到几何」映射的外观、刻度和交互，改不了映射本身。想把数据映射成桑基图的流带，无论 options 怎么写都出不来，那是 controller 的职责范围。

内置类型覆盖的场景，与越界时的表现

Chart.js 的内置 controller 只围绕两种坐标系展开。把需求往这张表上一贴，能不能用它做基本就清楚了。

坐标系内置 type能表达的数据关系越界需求与出路
笛卡尔line、bar、scatter、bubble一个索引轴加一到两个数值轴，第三维只能靠气泡半径或颜色甘特、K 线这种「一个类目对应一个区间」的结构没有内置表达，得自写 controller
径向pie、doughnut、polarArea、radar单层占比、多维量级对比旭日、多层玫瑰这类嵌套层级无内置支持
混合dataset 级别指定 type柱加折线、柱加散点只能在同一坐标系内混，笛卡尔和径向混不了
没有对应坐标系无无地图投影、桑基、树图、矩阵热力、关系图：要么上第三方 controller 包，要么换 ECharts

第三方 controller 包（矩阵、桑基、树图、漏斗等）本质上都是「继承 DatasetController 再注册」，不是插件。这也解释了为什么它们经常跟 Chart.js 主版本绑得很死：它们依赖的是内部接口，不是公开配置。

按需注册：抛错的一类和静默的一类

v3 起 Chart.js 是可摇树的。从 chart.js 主入口引入时什么都不注册，从 chart.js/auto 引入才会全量注册。流传很广的说法是「漏注册就图不出来」，实际上漏注册分两类后果，排查难度差一个数量级。

漏掉的东西现象怎么确认
controller（BarController、LineController…）抛异常，信息形如 bar is not a registered controller控制台第一个异常，构造 Chart 时就炸
scale（CategoryScale、LinearScale、TimeScale、RadialLinearScale）抛异常，形如 category is not a registered scale同上
element（BarElement、PointElement、LineElement、ArcElement）抛异常，提示元素未注册同上
Filler 插件静默：fill 设了也没有面积填充，折线本身正常打印注册表看插件清单
Tooltip、Legend、Title静默：提示框和图例直接消失，无任何报错同上
Decimation 插件静默：降采样配置被忽略，点数照旧同上
日期适配器用 time 轴时抛 This method is not implemented异常出现在 scale 初始化阶段
v2 风格配置options.legend 写在顶层是静默忽略；scales 用 xAxes 数组写法会报 Invalid scale configuration对照 v3 迁移说明逐项核

结论很直接：会抛错的那几类反而安全，真正吃时间的是 Filler、Tooltip、Decimation 这类静默失效。所以按需注册的工程做法是把注册集中在一个模块里，并在开发构建里打印一次注册结果。

// 只注册真正用到的构件。漏 controller/scale/element 会抛错，
// 漏 Filler/Tooltip/Decimation 只是静默失效，后者排查成本高得多。
import {
  Chart, LineController, LineElement, PointElement,
  LinearScale, TimeScale, Filler, Tooltip, Decimation
} from 'chart.js';
import 'chartjs-adapter-date-fns';   // 用 time 轴必须配日期适配器，否则抛 not implemented

Chart.register(
  LineController, LineElement, PointElement,
  LinearScale, TimeScale, Filler, Tooltip, Decimation
);

// 内部结构，仅用于开发期核对：比等用户反馈「图是空的」靠谱得多
if (import.meta.env?.DEV) {
  console.log('plugins:', Object.keys(Chart.registry.plugins.items));
  console.log('scales:', Object.keys(Chart.registry.scales.items));
}

一次 update 走了哪些阶段，动画贵在哪

把 update 当成「重画一遍」会低估它。它的成本主要不在最后的 canvas 绘制，而在刻度重建和数据解析。

sequenceDiagram participant App as 应用代码 participant Chart as Chart 实例 participant Plug as 插件服务 participant Sc as Scale participant Ctl as DatasetController participant Anim as Animator App->>Chart: update 或 update none Chart->>Plug: beforeUpdate 返回 false 可取消 Chart->>Sc: 重建刻度并测量标签宽高 Sc-->>Chart: 绘图区尺寸确定 Chart->>Ctl: 解析数据并同步 element 数量 Ctl-->>Chart: element 目标属性就绪 Chart->>Anim: 按 mode 决定过渡还是直接落值 loop 每帧 requestAnimationFrame Anim->>Chart: 插值后触发重绘 Chart->>Plug: beforeDraw 与 afterDraw end Chart->>Plug: afterUpdate
mode是否重解析数据并重算刻度动画行为典型用途
省略是按 animation 配置过渡，默认时长一秒、easeOutQuart 缓动数据结构变化后的常规刷新
none是无动画，属性直接落到目标值高频刷新、大数据集
resize是走 resize 对应的过渡配置容器尺寸变化
reset是元素回到动画起点状态需要重播入场动画
show / hide是走显隐过渡图例点击、切换数据集可见性
active是走 hover 态过渡自定义多图 hover 联动

注意表里每一行「是否重解析」都是「是」。mode 只决定元素属性怎么过渡到目标值，省不掉解析和刻度重建。想压这部分成本，手段是 parsing: false 加 normalized: true，以及只改真正变了的数据集而不是整体替换 data 对象。

动画的成本模型也很清楚：每帧对每个 element 的每个受动画属性做一次插值，总成本约等于元素数乘属性数乘帧数。所以关动画有三种粒度：animation: false 全关，animations: { colors: false } 按属性关，transitions 按 mode 关。秒级刷新的监控图直接全关并用 update('none')，视觉上不会有任何损失。

响应式、devicePixelRatio 与画布内存账

响应式靠平台层的 ResizeObserver 监听画布父容器。maintainAspectRatio 默认为 true，aspectRatio 默认 2（径向图是 1），所以不显式关掉宽高比时，高度是被宽度算出来的。

stateDiagram-v2 state "已构建，首次 update 完成" as Ready state "动画插值中" as Anim state "布局重算中" as Layout [*] --> Ready Ready --> Anim: update 默认 mode Ready --> Ready: update none 直接落值 Anim --> Ready: 动画结束 Anim --> Anim: 新的 update 打断并重新插值 Ready --> Layout: 容器尺寸变化触发 resize Layout --> Ready: 重新测量刻度并分配绘图区 Ready --> [*]: destroy 解绑监听与事件

模糊和内存这两件事经常被归因错。真相是：Chart.js 会把画布的后备存储尺寸设为 CSS 尺寸乘 devicePixelRatio，再等比缩放 2D 上下文。模糊几乎都是你自己破坏了这个关系——写死了 canvas 的 width/height 属性，或者用 CSS 把画布拉伸到另一个尺寸。

现象根因修法
线条和文字发虚画布栅格尺寸与显示尺寸不一致只用 CSS 控制容器，别碰 canvas 的宽高属性
高清屏下内存明显偏高后备存储字节数等于 CSS 宽乘 CSS 高乘 dpr 平方乘 4把 devicePixelRatio 限到 1.5 或 1，或缩小画布 CSS 尺寸
容器高度每帧增长直到页面卡死maintainAspectRatio 关掉，而父容器高度又由画布高度决定，形成循环父容器给确定高度，用 px 或 flex 计算出的高度
图表被压成一条线在 display 为 none 的容器里初始化，读到 0 尺寸显示后再初始化，或显示后调用 chart.resize()
拖窗口时明显卡顿每次 resize 都要重测刻度文本并重建布局设 options.resizeDelay 做防抖
超大画布整块空白浏览器对画布最大边长和总面积有上限，移动端更紧拆成多张画布，或同时降 dpr 与尺寸
路由切换后内存不回落没有 destroy，ResizeObserver 和事件监听仍持有画布组件卸载时调用 chart.destroy()

一块 1600×900 的 CSS 画布，在 dpr 为 2 的屏幕上后备存储是 3200×1800×4 字节，约 22MB。一个看板放六张图，光画布就是一百多 MB，这通常比你的数据本身大得多。看板类页面把 dpr 限到 1.5 是性价比最高的一刀。

数据量上限：三个独立瓶颈要分开量

「Canvas 渲染所以不怕大数据」是个误解。Canvas 省掉的是 DOM 节点，但每帧仍然要把所有路径重描一遍，点数会线性摊进每一帧。真正要分开量的是三处：解析、绘制、命中测试。

单数据集量级主要瓶颈表现对策
千点以内基本没有默认配置即可不用优化
数千点动画插值与点元素绘制首帧和更新有可感停顿pointRadius 设 0、borderWidth 设 1、关动画
一到数万点解析阶段与每帧路径绘制更新卡顿，鼠标移动掉帧parsing 设 false 加 normalized 设 true，开 Decimation，关命中测试
十万点以上每帧全量重绘无法回避交互不可用在服务端聚合降采样，或换 ECharts 的渐进渲染，详见站内《ECharts 的渲染架构与大数据量优化》
多数据集叠加元素总数与命中测试mousemove 时 CPU 占满interaction.mode 用 index，或直接 events 设空数组

官方 Decimation 插件的前提是硬性的，任一条不满足就静默跳过：只支持折线图；数据必须是 {x, y} 形式的内部格式；parsing 必须为 false；索引轴必须是 x；x 轴必须是线性轴或时间轴。算法有两种，lttb 保留视觉轮廓，min-max 保留极值——监控场景下漏掉毛刺是要出事的，这时选 min-max。还要清楚它只减少绘制的点，不减少你传进来的数组内存，真正的降采样应该在查询层做。

const chart = new Chart(canvas, {
  type: 'line',
  data: {
    datasets: [{
      // parsing:false 要求点是内部格式且按 x 升序，Decimation 也依赖这两点
      data: points,            // [{ x: 1738368000000, y: 12.5 }, ...]
      pointRadius: 0,          // 不画点，省掉每帧上万次 arc 调用
      borderWidth: 1
    }]
  },
  options: {
    parsing: false,
    normalized: true,          // 声明数据已排序且索引唯一，跳过一次内部规整
    animation: false,
    responsive: true,
    maintainAspectRatio: false,  // 高度交给父容器，父容器必须有确定高度
    resizeDelay: 120,            // resize 防抖，避免拖窗口时反复重排刻度
    devicePixelRatio: Math.min(window.devicePixelRatio, 1.5), // 内存按 dpr 平方增长
    scales: { x: { type: 'time' } },
    plugins: {
      decimation: { enabled: true, algorithm: 'min-max' }  // 监控图保极值，别用 lttb
    },
    events: []                 // 只展示不交互时关掉命中测试，省掉每次 mousemove 的遍历
  }
});

插件机制的能力与天花板

插件就是一组生命周期钩子的集合，分四组：安装与销毁（install、start、stop、uninstall、destroy）、更新（beforeUpdate 到 afterDatasetsUpdate、beforeLayout）、绘制（beforeDraw、beforeDatasetsDraw、afterDatasetDraw、afterDraw、afterRender）、事件（beforeEvent、afterEvent）。其中 beforeUpdate、beforeRender、beforeDraw、beforeEvent 返回 false 会取消该阶段。

需求该用的扩展点注意
水印、阈值带、空数据占位afterDraw 或 beforeDatasetsDraw直接用 chart.ctx 画，必须 save 与 restore 配对
自定义提示框样式options.plugins.tooltip.external高频 hover 会产生大量 DOM 操作，需要节流
拦截某次更新或绘制beforeUpdate / beforeRender / beforeDraw 返回 false这是「图表莫名不更新」的常见来源，排查时先搜 return false
新增图表类型继承 DatasetController 后 Chart.register，不是写插件要同时定义 defaults 与用到的 element 类型
新增坐标轴类型继承 Scale 后注册至少要实现刻度生成与值到像素的转换
多图联动afterEvent 里取命中元素后自行派发联动逻辑放插件比散在业务代码里更好复用
矢量输出、GPU 加速、SVG 节点做不到渲染后端只有 2D canvas，导出只有位图

最后一行是 Chart.js 最实在的天花板：它没有 SVG 渲染后端，toBase64Image() 出来的是位图。要印刷质量的矢量图，这条路走不通。

const guardPlugin = {
  id: 'guard',
  defaults: { max: null },   // 业务侧用 options.plugins.guard.max 覆盖

  // 阈值带画在数据集之前，否则会盖住折线
  beforeDatasetsDraw(chart, args, opts) {
    const y = chart.scales.y;
    if (!y || opts.max == null) return;
    const { ctx, chartArea: a } = chart;
    ctx.save();
    ctx.fillStyle = 'rgba(220, 60, 60, 0.12)';
    const top = y.getPixelForValue(opts.max);
    ctx.fillRect(a.left, a.top, a.right - a.left, Math.max(0, top - a.top));
    ctx.restore();   // 不 restore 会污染后续绘制状态
  },

  // 数据全空时盖一层提示，避免用户把空白图当成加载失败
  afterDraw(chart) {
    const empty = chart.data.datasets.every(ds => !ds.data || ds.data.length === 0);
    if (!empty) return;
    const { ctx, chartArea: a } = chart;
    ctx.save();
    ctx.textAlign = 'center';
    ctx.textBaseline = 'middle';
    ctx.fillStyle = '#888';
    ctx.fillText('暂无数据', (a.left + a.right) / 2, (a.top + a.bottom) / 2);
    ctx.restore();
  }
};

Chart.register(guardPlugin);

什么时候该离开 Chart.js

flowchart TD S{"当前需求"} -->|标准折柱饼雷达| A{"数据量级"} A -->|万点以内| K1["留在 Chart.js"] A -->|十万点以上或需渐进渲染| K2["换 ECharts"] S -->|地图 桑基 关系图 K 线| K2 S -->|视觉编码必须完全自定义| K3["换 D3"] S -->|服务端批量出矢量图| K4["换 Python 可视化栈"] S -->|信息本身是三维空间关系| K5["换 Three.js"]
触发条件换到一句理由
要地图、桑基、K 线、关系图，或十万级数据要渐进渲染ECharts这些都是内置系列，且有成套的大数据渲染机制，详见站内《ECharts 的渲染架构与大数据量优化》
视觉编码本身要定制，没有现成图表类型能对应D3它给的是数据到 DOM 的映射原语而不是图表成品，详见站内《D3 的数据绑定模型与使用边界》
出图在服务端批量跑，要矢量与可复现Python 栈浏览器完全不参与，详见站内《Python 可视化栈的分层与场景匹配》
信息本身是三维空间关系Three.js二维图表无法表达视角与遮挡，详见站内《Three.js 的渲染管线与性能预算》
只是想让包更小不用换按需注册后体积主要由用到的 controller 与 scale 决定

反过来说，Chart.js 在它的舒适区里几乎没有替代品：配置面小、默认值合理、交互开箱可用。「够用就好」不是妥协，是明确的选型判断——当需求确实跨出这条线时再换，比一开始就上重型库省事得多。

❌
最容易踩的坑

1. 开发用 chart.js/auto，上线切按需注册却漏了 Filler 和 Tooltip：不报错，只是面积填充和提示框悄悄消失。

2. 抄 v2 的 options.legend、options.title：v3 起它们在 options.plugins 下，写错位置是静默忽略。

3. scales: { xAxes: [...] } 是 v2 写法，v4 会把 xAxes 当成一个 scale id，报 Invalid scale configuration。

4. 用 type: 'time' 不装日期适配器，抛 This method is not implemented，错误信息里完全看不出缺的是适配器。

5. 开了 parsing: false 却把接口原始数组直接塞进去：点必须是 {x, y} 且按 x 升序，否则画出乱线或整段空白。

6. Decimation 配了没效果：只支持折线、要求 parsing 为 false、索引轴为 x、x 轴是线性或时间轴，任一条不满足就静默跳过。

7. maintainAspectRatio: false 配高度 auto 的父容器：画布每帧长高一点，最后把页面撑爆。

8. 在 display: none 的 tab 里初始化，读到 0 尺寸；显示后不 resize 就一直是压扁状态。

9. SPA 里不 destroy()：ResizeObserver、事件监听和画布后备存储都留着，切几次路由内存就上去了。

10. 高频 update() 不传 'none'：每次重启一轮一秒动画并互相打断，看起来像数据一直在抖。

11. 插件里画完不 restore()：污染上下文状态，同一页多图时表现为「另一张图的样式莫名变了」。

12. 拿 toBase64Image() 的结果去印刷：它只有位图，放大必糊，矢量需求得换工具链。
