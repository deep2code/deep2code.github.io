可视化与图表

ECharts · Chart.js · D3 · Three.js · Babylon.js · Python 出图

六篇按渲染面分开，不按库的名气排。二维图表比的是配置模型与一次更新走了哪些阶段；三维比的是提交次数与显存；D3 只提供数据到 DOM 的原语；Python 那一栈按交付形态选。

篇目它管哪一段什么时候读
ECharts 的渲染架构与大数据量优化从 option 到像素的一次 setOption 链路、三种合并语义、Canvas 与 SVG 的成本差、采样与 large 模式、tooltip 与命中测试开销、dispose 与按需引入图卡了、更新整片重画，或数据量上来后首屏变慢
Chart.js 的配置模型与容量边界不报错但不生效的排查顺序、controller 与 scale、element 的分工、按需注册里抛错的一类与静默的一类、devicePixelRatio 与画布内存、Decimation 的硬前提要轻量二维图，或换了配置没反应
D3 的数据绑定模型与使用边界数据到 DOM 的原语集合、join 的语义与退出竞态、scale 是纯函数而 axis 是渲染器、过渡是调度器、与 React 共管 DOM 的三种模式标准图表库画不出要的图，或框架和 D3 抢同一批节点
Three.js 的渲染管线与性能预算一帧里发生什么、draw call 为什么是首要瓶颈、几何体与贴图的显存账、光照与阴影的代价分级、dispose、后处理与降级阶梯要做 3D 展示，或帧率随场景变大掉下去
Babylon.js 3D 游戏引擎Scene 节点树与脏标记跳过哪些重算、动态光的片元成本与光源数上限、物理、粒子、GUI 与 Inspector 调试要引擎级成套工具，或做数字孪生、交互场景
Python 可视化栈的分层与场景匹配这套栈的四层分工、Figure 与 Axes 的对象模型和状态机的代价、后端选择与无显示环境、交付形态带来的约束、批量出图的内存与字体坑出图进报告、论文、大屏或流水线，而不是进网页

两类问题反复出现，两类都跟数据量无关。「更新走了哪些阶段」——卡住多半是合并语义触发了整图重建，不是数据太大；「资源会不会释放」——画布内存按像素密度计，GPU 资源不会自己回收，dispose 是硬要求。

分界也写得具体：元素数量上千、需要逐点自定义绘制，二维图表库就开始赔；交互与物理成体系才值得上引擎，只是摆一个模型用不到那套工具链。

图该不该画、画成哪一类图的方法在 开发工具与工程效率 的文档与图分组，这一组只讲落地那层。
