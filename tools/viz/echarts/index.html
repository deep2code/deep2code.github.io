ECharts 的渲染架构与大数据量优化

🏷️ ECharts

ECharts 的入门门槛很低——拼一个 option 对象丢给 setOption 就有图。代价是绝大多数问题都发生在这层抽象之下：数据变少了旧系列却不消失、十万个点一动就卡、SPA 切几次路由内存翻倍、按需引入后图表一片空白。这些现象各自有明确的机制解释。这篇从 option 到屏幕像素的完整链路讲起，重点是三种合并语义、两种渲染器的选择依据、大数据量的四条手段、命中测试与提示框的开销来源，以及实例生命周期管理。

从 option 到像素：一次 setOption 的链路

ECharts 是声明式的：你不画图，你描述「图应该长什么样」，剩下的交给一条固定的流水线。option 先被解析成模型层（全局模型持有各个组件模型与系列模型），系列模型内部把数据装进一个列式存储结构；接着数据处理阶段按顺序跑过滤、堆叠、采样等处理器；然后是视觉编码阶段，把数值映射成颜色、尺寸、透明度；再由各 chart view 生成图元；最后交给底层图形库 zrender，由 Canvas painter 或 SVG painter 落到屏幕。

理解这条链路能解释两类常见困惑。第一，为什么 dataZoom 缩放会改变另一个坐标轴的范围——因为默认的 filterMode 在数据处理阶段真的把范围外的数据过滤掉了，后续的轴范围计算只看到剩下的数据。第二，为什么某些配置改了没反应——它所属的阶段没有被标记为脏，需要触发对应的更新流程，而不是配置写错了。

setOption 的三种合并语义

这是 ECharts 最容易出错的一处，而错的形式往往是「数据更新了，图上却留着上一次的东西」。setOption 默认是合并：新 option 的字段覆盖同名字段，没提到的保持原样。关键在于组件数组的匹配方式——默认按下标对齐。新的 series 数组从五个变成三个时，第四、第五个旧系列不会消失，它们只是没人更新了。

三条修法各有代价。给每个 series 指定 id，匹配从下标改为标识，这是最干净的做法；在第二个参数里传 replaceMerge: 'series'，声明「新 option 里缺席的同类组件请删除」；直接 notMerge: true 整体重建，但会丢掉 dataZoom 的当前窗口、图例的勾选状态与动画连续性——很多「缩放之后一刷新就跳回去」的问题就是这么来的。

另外两个参数值得知道：lazyUpdate 把渲染推迟到下一帧，适合一次交互里连续调用多次 setOption 的场景；silent 抑制本次更新触发的事件，用来避免「更新触发事件、事件里又更新」的循环。

Canvas 与 SVG 渲染器的选择依据

网上流传的「Canvas 快、SVG 慢」是过度简化。实际的判据是两个独立的量：单张图里的图元数量，以及同一页面上的图表数量。图元多时 Canvas 占优，因为它只维护一张位图，不会产生成千上万个 DOM 节点，也不需要浏览器做布局与合成；图表多而每张数据不多时 SVG 占优，因为每个 Canvas 的位图内存是叠加的，在内存受限的设备上会被系统回收，表现为滚动回来图表变白。

还有几个非性能维度经常决定选择：SVG 是矢量，缩放与打印不失真，可以直接把输出嵌进文档或邮件；SVG 的节点能被辅助技术读到，对无障碍要求高的场景更友好；而 Canvas 侧有一个 SVG 没有的能力——脏矩形渲染，开启后只重绘变化区域，对「一屏很多图、每次只有局部数据变」的监控大屏效果明显，但它是需要显式开启的选项，默认不启用。

大数据量：采样、large 模式与渐进渲染

「十万个点卡」这件事要先分清卡在哪：是一次绘制的长任务把主线程堵住了（表现为交互冻结几百毫秒），还是每帧都画不完（表现为持续掉帧），还是鼠标一动就卡（命中测试问题，见下一节）。对应手段完全不同。

采样处理的是根本问题：屏幕宽度只有一两千像素，十万个点里绝大多数落在同一列。折线系列的 sampling 支持 lttb、average、max、min、sum，其中 lttb 在大幅降点的同时保留折线形状的视觉特征，是趋势图的默认选择；而 max 或 min 适合「不能漏掉尖峰」的监控场景——用 average 会把毛刺抹平，这是监控图最危险的一种失真。

large 模式是换一条绘制路径：散点、柱状、lines 系列开启 large 后走批量绘制，跳过逐图元的对象创建。代价必须清楚——失去单个数据项的样式与强调效果，逐点交互能力也随之退化。largeThreshold（默认 400）控制自动切换的点数门槛。

渐进渲染解决的是长任务：progressive（默认 400）指定每帧绘制多少图元，progressiveThreshold（默认 3000）指定超过多少图元才启用。它不减少总工作量，只是把工作切碎摊到多帧，让页面保持可交互。配合 progressiveChunkMode 可以控制分块顺序——按数据顺序分块会出现「从左往右长出来」的视觉效果，取模分块则是整体逐渐变密。

最后是数据格式：把二维对象数组换成类型化数组（配合 dataset.source 与 dimensions 声明），能显著降低内存占用与解析开销，这一项常常比调参更有效。流式场景用 appendData 追加而不是每次重设整份数据。

参数默认值作用副作用与失效条件

dataset、transform 与数据裁剪

dataset 把数据与「怎么映射到图形」分开：数据放在 dataset.source，系列通过 encode 声明哪一列做 x、哪一列做 y。好处不只是少写代码——多个系列共享同一份 dataset 时，数据在内存里只有一份，而把同一批数据拷进每个 series.data 会成倍占用内存。

transform 在配置层做过滤、排序、聚合与回归。它的价值是把「派生数据」变成声明的一部分，避免在业务代码里维护一堆中间数组；它的边界是——transform 在主线程上执行，大数据量下的重聚合应该放到后端或 Worker，而不是交给它。

dataZoom 的 filterMode 是最容易被忽略却影响正确性的参数。默认的 filter 会把窗口外的数据真正过滤掉，于是另一个坐标轴的范围也跟着变；多系列共用一个缩放时，这会导致「缩放 A 系列，B 系列的纵轴突然跳变」。需要「只改可见窗口、不影响轴范围」时应该用 none，需要「保留数据项但把越界的值置空」时用 empty。

filterMode窗口外的数据对另一个轴范围的影响典型用途
filter（默认）整条数据项被过滤掉会随剩余数据重算单系列趋势图，希望纵轴自适应
weakFilter只有整段都越界的数据项被过滤影响较小区间型数据，如甘特与 K 线
empty保留数据项，越界维度置空不参与范围计算多系列共轴，需要保持其他系列稳定
none不过滤，只改可见窗口完全不影响散点与热力图，轴范围必须固定
// 按需引入：漏注册渲染器是「配置正确但一片空白」的第一大原因

事件与 tooltip 的性能陷阱

「鼠标一动就卡」和「数据量大画得慢」是两个独立问题。指针移动时的开销主要来自命中测试：zrender 需要判断指针落在哪个图元上，成本与参与测试的图元数量相关。对纯展示的系列、背景装饰、标注图形设置 silent: true，可以让它们完全退出命中测试，这是收益最大且几乎无副作用的一项优化。

提示框是第二个来源。按坐标轴触发（trigger: 'axis'）时，每次移动都要为所有系列取值并生成内容；默认的 renderMode: 'html' 会持续产生 DOM 变更与样式重算，换成 'richText' 后内容画在 Canvas 里，代价是失去 HTML 富文本能力。transitionDuration 默认 0.4 秒的跟随过渡在密集移动时会让人觉得「粘手」，设为 0 反而更跟手。enterable: true 会让提示框 DOM 长期存在以便鼠标移入，不需要就别开。

自己注册的事件回调必须节流——ECharts 导出了节流工具，不要在 mousemove 回调里直接做 setOption。另外一个容易忽略的点：setOption 本身会触发事件，如果事件回调里又 setOption，就形成循环，用 silent 参数切断。

dispose 与内存泄漏

这是 SPA 里最常见的 ECharts 问题，而且症状很典型：来回切几次路由，内存曲线阶梯式上涨，DevTools 里能看到已经卸载的容器 DOM 还被引用着。原因是实例会被登记在容器 DOM 上，再加上你自己注册的窗口尺寸监听、内部的动画帧循环，这些引用共同把整棵子树钉在内存里。

正确顺序是：先解除外部监听（移除窗口事件或断开 ResizeObserver），再调用 dispose。注意 clear() 不是 dispose()——前者只清 option，实例与监听都还在。初始化前用 getInstanceByDom 检查是否已有实例，能避免热更新或重复渲染时在同一容器上叠加多个实例（这种情况下控制台会给出提示，但很容易被忽略）。

另一个高频坑与泄漏无关但同样出现在生命周期上：容器处于隐藏状态（父级 display: none）时初始化，宽高为零，图什么都不画，之后显示出来也不会自动恢复，必须手动 resize()。折叠面板、标签页切换、抽屉里的图表基本都会遇到。

// SPA 里的正确生命周期：以 React 为例，Vue 的 onBeforeUnmount 同理
function useChart(ref, option) {
  useEffect(() => {
    const el = ref.current;
    if (!el) return;

    // 1. 避免热更新或重复渲染时在同一容器上叠加实例
    let chart = echarts.getInstanceByDom(el);
    if (!chart) chart = echarts.init(el, null, { renderer: 'canvas' });

    chart.setOption(option, { replaceMerge: ['series'] });

    // 2. 用 ResizeObserver 而不是 window.resize：容器自身变化也能捕获
    const ro = new ResizeObserver(() => chart.resize());
    ro.observe(el);

    return () => {
      // 3. 顺序很重要：先断监听，再 dispose
      ro.disconnect();
      chart.dispose();          // clear() 不释放实例，监听与动画循环还在
    };
  }, [ref, option]);
}

// 容器初始化时处于隐藏状态（宽高为 0），显示后必须补一次 resize
function onPanelShown(el) {
  const chart = echarts.getInstanceByDom(el);
  if (chart) chart.resize();
}

按需引入与打包体积

全量引入方便但代价直接可见：本站 vendor 目录里自托管的完整版 echarts.min.js 约 1 MB（压缩前的文件体积），里面包含二十多种图表、全部组件与两套渲染器，而典型业务页面用得上的不超过三种图表。按需引入要注册三类东西：图表类型、组件、渲染器。

三个必踩的坑：漏注册渲染器——图表完全空白且不报错，这是最常见的；漏注册组件——直角坐标系图表需要网格组件，提示框、图例、缩放条都是独立组件，缺哪个就哪个功能静默失效；地图数据当依赖打包——地理数据往往比图表库本身还大，必须运行时按需加载后注册，不能塞进主 bundle。

要用的能力必须注册的模块类别漏掉后的表现
任意图表Canvas 或 SVG 渲染器容器尺寸正常但完全空白，无报错
折线、柱状、散点对应图表模块 + 网格组件缺网格组件时坐标轴不出现
提示框、图例、标题各自的组件模块配置被忽略，功能静默失效
缩放条与框选缩放dataZoom 相关组件交互无响应
dataset 与 transformdataset 组件与对应 transform数据映射不生效，图为空
地图地图图表 + 运行时注册地理数据把地理数据打进主包会让体积翻倍
标签避让、系列间转场额外的特性模块标签重叠，转场退化为直接重绘

服务端渲染、静态导出与选型边界

需要在邮件、PDF、报表或不执行 JavaScript 的环境里出图时，有两条路。服务端 SVG 渲染：在 Node 里以 SVG 渲染器创建实例并开启服务端模式，直接拿到 SVG 字符串，不依赖浏览器也不需要原生 Canvas 绑定，适合报表与邮件；缺点是动画与交互自然全部失效，部分依赖浏览器测量的文本布局会有细微差异。浏览器端导出位图：用 getDataURL 拿 png 或 jpeg，注意提高像素比否则高分屏上发虚，多图联动时用连接导出把几张图合成一张。

至于与其他库的分界，这里只给结论：需要大量开箱图表类型、中文文档与仪表盘式配置，选 ECharts；只要几种基础图、追求极小体积，Chart.js 更合适（详见站内 Chart.js 轻量图表库）；需要完全自定义的、图表库里没有的可视化形式，用 D3 自己搭（详见站内 D3.js 数据驱动文档）。不要用 D3 去画标准折线柱状，也不要试图把 ECharts 掰成通用绘图框架。

// 一、服务端出图：Node 环境，SVG 渲染器 + 服务端模式，不需要原生 canvas
import * as echarts from 'echarts';

const chart = echarts.init(null, null, {
  renderer: 'svg',
  ssr: true,          // 服务端模式：不绑定 DOM，不启动动画循环
  width: 800,
  height: 400,
});
chart.setOption({
  animation: false,   // 服务端渲染必须关掉，否则拿到的是第一帧
  xAxis: { type: 'category', data: labels },
  yAxis: { type: 'value' },
  series: [{ type: 'bar', data: values }],
});
const svg = chart.renderToSVGString();
chart.dispose();      // 服务端同样要释放，否则是进程级泄漏

// 二、浏览器端导出位图：像素比必须显式提高，否则高分屏上发虚
const url = chart.getDataURL({
  type: 'png',
  pixelRatio: 2,
  backgroundColor: '#fff',              // 默认透明，贴到白底文档里会有边缘问题
  excludeComponents: ['toolbox'],       // 排除工具栏这类不该出现在图片里的组件
});

// 三、等渲染真正完成再导出，否则可能截到渐进渲染的中间帧
chart.on('finished', () => {
  const finalUrl = chart.getDataURL({ type: 'png', pixelRatio: 2 });
  // 这里再上传或下载
});
❌
最容易踩的坑
  • 幽灵系列：setOption 默认按数组下标合并，系列数量变少时旧系列不会消失。给 series 加 id 或用 replaceMerge，别用 notMerge 硬清。
  • 用 notMerge 刷新数据：会连带重置 dataZoom 窗口与图例勾选，用户刚调好的视图被打回原点。
  • 把 clear() 当 dispose()：前者只清 option，实例、尺寸监听与动画帧循环全都还在，内存照样涨。
  • 忘记 dispose：SPA 里切几次路由内存阶梯式上涨，已卸载的容器 DOM 被实例引用而无法回收。
  • 在隐藏容器里 init：宽高为零，图什么都不画，显示出来之后不会自动恢复，必须手动 resize()。
  • 按需引入漏注册渲染器：图表完全空白且不报任何错，排查时容易一直怀疑 option 写错了。
  • 用 average 采样做监控图：尖峰被抹平，告警图上看不到毛刺，这是会误导判断的失真。
  • 开了 large 却还要逐点交互：批量绘制路径没有单图元对象，强调效果与单项样式都会失效。
  • 只调 progressive 不看门槛：图元数低于 progressiveThreshold（默认 3000）时该配置完全不生效。
  • 无视 filterMode：默认 filter 会真的过滤数据，导致缩放一个系列把另一个系列的纵轴带跑。
  • 不给展示性图元设 silent：命中测试对全部图元逐一判断，是「鼠标一动就卡」的首要来源。
  • 在 mousemove 回调里 setOption：不节流会直接打满主线程，还可能与更新事件形成循环。
  • 导出图片不提像素比、不等 finished：高分屏上发虚，或者截到渐进渲染的中间帧。
  • 把地图地理数据打进主包：地理数据常常比图表库本体还大，必须运行时按需加载后注册。
