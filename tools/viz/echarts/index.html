ECharts 的渲染架构与大数据量优化

🏷️ ECharts

ECharts 拼一个 option 丢给 setOption 就有图，问题都出在这层抽象之下：数据变少旧系列却不消失、十万个点一动就卡、SPA 切几次路由内存翻倍、按需引入后图表空白。

每种现象都有机制解释，都在 option 到屏幕像素的链路里：合并语义三种、渲染器两种、大数据量四条手段、命中测试与提示框开销、实例生命周期。

图卡了的排查顺序与按需引入的正确写法

这一层只给动作：图卡了先做什么、按需引入怎么写才不会空白、以及一份能直接跑的完整代码。每条动作为什么有效，见后面的原理层。

图卡了，第一个动作不是加参数，是判断卡在绘制还是命中测试。指针移出图表、停住不动：帧率立刻回升，开销在命中测试与提示框。

鼠标不动照样卡，说明开销在绘制与动画上。这两条路径的手段几乎没有交集，判断反了会花掉一整个下午调不相干的参数。

下面这份代码是「按需引入 + 初始化 + 更新 + 释放」的最小完整形态，注释只说明为什么要这一行：

// 按需引入要注册四类东西：图表类型、坐标系与交互组件、渲染器，缺哪类哪类静默失效
import * as echarts from 'echarts/core';
import { LineChart } from 'echarts/charts';
import { GridComponent, TooltipComponent, DataZoomComponent } from 'echarts/components';
import { CanvasRenderer } from 'echarts/renderers';   // 漏掉这行：容器尺寸正常，图完全空白，控制台不报错

echarts.use([LineChart, GridComponent, TooltipComponent, DataZoomComponent, CanvasRenderer]);

const el = document.getElementById('chart');
// 先查后建：热更新或重复渲染时不会在同一个容器上叠加出第二个实例
const chart = echarts.getInstanceByDom(el) || echarts.init(el);

chart.setOption({
  tooltip: { trigger: 'axis', transitionDuration: 0 },  // 默认 0.4 秒的跟随过渡在密集移动时显得粘手
  xAxis: { type: 'time' },
  yAxis: { type: 'value', scale: true },                // scale 让纵轴不强制从 0 起，趋势的波动才看得见
  dataZoom: [{ type: 'inside', filterMode: 'none' }],   // none 只改可见窗口，不会把别的系列纵轴带跑
  series: [{
    id: 'latency',        // 有 id 才能按标识匹配；否则按数组下标对齐，增删系列必留残影
    type: 'line',
    showSymbol: false,    // 每个数据点省掉一个图元，绘制与命中测试同时受益
    sampling: 'max',      // 监控图用 max 保住尖峰，average 会把毛刺抹平
    data: points,         // 形如 [[ts, value], ...]
  }],
}, { replaceMerge: ['series'] });   // 新 option 里缺席的 series 会被真正移除，而不是留着不更新

// 容器自身尺寸变化 window 的 resize 事件抓不到，必须观察容器
const ro = new ResizeObserver(() => chart.resize());
ro.observe(el);

// 卸载时顺序不能反：先断监听，再释放实例，否则监听回调会打到已释放的实例上
function destroy() {
  ro.disconnect();
  chart.dispose();
}

从 option 到像素：一次 setOption 的链路

ECharts 是声明式的：你只描述图长什么样，交给一条固定流水线。option 解析成模型层，全局模型下挂组件模型与系列模型，系列模型用列式存储装数据。

数据处理阶段按顺序跑过滤、堆叠、采样等处理器；视觉编码把数值映射成颜色、尺寸、透明度；chart view 生成图元；再交给图形库 zrender，由 Canvas painter 或 SVG painter 落到屏幕。

这条链路能解释两类常见困惑。第一，为什么 dataZoom 缩放会改变另一个坐标轴的范围：默认 filterMode 在数据处理阶段过滤掉范围外的数据，轴范围只看剩下的。

第二，为什么某些配置改了没反应——它所属的阶段没有被标记为脏，需要触发对应的更新流程，而不是配置写错了。

setOption 的三种合并语义

常见错误是「数据更新了，图上留着上一次的东西」。setOption 默认合并：新字段覆盖同名，没提到的保持原样，组件数组按下标对齐。

新的 series 数组从五个变成三个时，第四、第五个旧系列不会消失，它们只是没人更新了。

三条修法各有代价。给每个 series 指定 id，匹配从下标改为标识，这是最干净的做法；在第二个参数里传 replaceMerge: 'series'，声明「新 option 里缺席的同类组件请删除」；

直接 notMerge: true 整体重建，但会丢掉 dataZoom 的当前窗口、图例的勾选状态与动画连续性——很多「缩放之后一刷新就跳回去」的问题就是这么来的。

lazyUpdate 把渲染推迟到下一帧，适合一次交互里连续调用多次 setOption；silent 抑制本次更新触发的事件，避免「更新触发事件、事件里又更新」的循环。

Canvas 与 SVG 两种渲染器的成本结构

网上流传的「Canvas 快、SVG 慢」是过度简化。实际的判据是两个独立的量：单张图里的图元数量，以及同一页面上的图表数量。

图元多时 Canvas 占优，因为它只维护一张位图，不会产生成千上万个 DOM 节点，也不需要浏览器做布局与合成；

图表多而每张数据不多时 SVG 占优，因为每个 Canvas 的位图内存是叠加的，在内存受限的设备上会被系统回收，表现为滚动回来图表变白。

非性能维度也决定选择：SVG 是矢量，缩放打印不失真，输出能嵌进文档或邮件；节点能被辅助技术读到，无障碍要求高时更友好。

Canvas 侧有 SVG 没有的能力：脏矩形渲染，只重绘变化区域，「一屏很多图、每次只有局部数据变」的监控大屏效果明显，但默认不启用，要显式开启。

大数据量：采样、large 模式与渐进渲染

「十万个点卡」要先分清卡在哪：一次绘制的长任务堵住主线程（交互冻结几百毫秒）、每帧画不完（持续掉帧），还是鼠标一动就卡（命中测试）。

对应手段完全不同。

采样处理根本问题：屏幕宽度只有一两千像素，十万个点绝大多数落在同一列。折线系列 sampling 支持 lttb、average、max、min、sum，lttb 大幅降点仍保留折线形状，是趋势图默认选择。

而 max 或 min 适合「不能漏掉尖峰」的监控场景——用 average 会把毛刺抹平，这是监控图最危险的一种失真。

large 模式换一条绘制路径：散点、柱状、lines 开启 large 走批量绘制，跳过逐图元建对象。代价：失去单个数据项样式与强调，逐点交互退化。largeThreshold（默认 400）是切换门槛。

渐进渲染拆长任务：progressive（默认 400）定每帧画多少图元，progressiveThreshold（默认 3000）定启用门槛。总工作量没减，只是切碎摊到多帧，页面保持可交互。

配合 progressiveChunkMode 可以控制分块顺序——按数据顺序分块会出现「从左往右长出来」的视觉效果，取模分块则是整体逐渐变密。

二维对象数组换成类型化数组（配合 dataset.source 与 dimensions 声明），内存占用和解析开销都降，常比调参更有效。流式场景用 appendData 追加，不必每次重设整份数据。

参数默认值作用副作用与失效条件
series.sampling不启用按像素密度降点，lttb 保形只对折线类有效；用 average 会抹平尖峰
series.largefalse切换到批量绘制路径失去单项样式与强调，逐点交互退化
series.largeThreshold400自动进入 large 的点数门槛设得过低会让小数据图也失去交互
series.progressive400每帧绘制的图元数不减少总量，只分摊；过小则图出得很慢
series.progressiveThreshold3000启用渐进渲染的图元数门槛低于门槛时该配置完全无效
animationtrue过渡动画大数据量下是主要开销；有自动关闭阈值但别依赖
animationThreshold2000超过该图元数自动关动画只针对单个系列计数，多系列叠加时仍会开着

dataset、transform 与数据裁剪

dataset 把数据与「怎么映射到图形」分开：数据放 dataset.source，系列用 encode 声明哪列做 x、哪列做 y。多个系列共享同一份 dataset 时，数据在内存里只有一份；拷进每个 series.data 就成倍占内存。

transform 在配置层做过滤、排序、聚合与回归。它的价值是把「派生数据」变成声明的一部分，避免在业务代码里维护一堆中间数组；

它的边界是——transform 在主线程上执行，大数据量下的重聚合应该放到后端或 Worker，而不是交给它。

dataZoom 的 filterMode 影响正确性：默认 filter 真把窗口外的数据过滤掉，于是另一个坐标轴的范围跟着变；多系列共用一个缩放时，A 系列缩放完 B 系列纵轴就跳变。

需要「只改可见窗口、不影响轴范围」时应该用 none，需要「保留数据项但把越界的值置空」时用 empty。

filterMode窗口外的数据对另一个轴范围的影响典型用途
filter（默认）整条数据项被过滤掉会随剩余数据重算单系列趋势图，希望纵轴自适应
weakFilter只有整段都越界的数据项被过滤影响较小区间型数据，如甘特与 K 线
empty保留数据项，越界维度置空不参与范围计算多系列共轴，需要保持其他系列稳定
none不过滤，只改可见窗口完全不影响散点与热力图，轴范围必须固定

事件与 tooltip 的开销来源

指针一动就卡和画得慢是两个独立问题：指针移动时 zrender 做命中测试，判断落在哪个图元上，成本随参与测试的图元数上涨。

对纯展示的系列、背景装饰、标注图形设置 silent: true，可以让它们完全退出命中测试，这是收益最大且几乎无副作用的一项优化。

提示框是第二个来源。trigger: 'axis' 时每次移动要为所有系列取值生成内容；默认 renderMode: 'html' 持续产生 DOM 变更与样式重算，换 'richText' 画进 Canvas，代价是失去 HTML 富文本。

transitionDuration 默认 0.4 秒的跟随过渡在密集移动时会让人觉得「粘手」，设为 0 反而更跟手。enterable: true 会让提示框 DOM 长期存在以便鼠标移入，不需要就别开。

setOption 会触发事件，事件回调里再调 setOption 就形成循环，用 silent 切断。自注册的事件回调要节流，别在 mousemove 回调里直接 setOption，用 ECharts 导出的节流工具。

现象主要来源处理代价
指针移动持续掉帧大量图元参与命中测试对展示性系列与装饰图形设 silent这些元素不再响应交互
提示框跟手迟滞过渡时长与 DOM 更新transitionDuration: 0，改用富文本渲染失去 HTML 模板能力
多系列时提示框明显变慢按轴触发要遍历全部系列取值改按项触发，或限制同时显示的系列数信息密度下降
事件回调里卡顿回调内做了重计算或 setOption用节流工具包裹，重活移出回调响应有可感知延迟
更新陷入循环setOption 触发事件，事件里又 setOption更新时传 silent该次更新不再对外广播
首屏白一下再出图渐进渲染分块过小调大每帧绘制量，或首帧关掉渐进首帧可能出现一次长任务

dispose 与内存泄漏

这是 SPA 里最常见的 ECharts 问题，而且症状很典型：来回切几次路由，内存曲线阶梯式上涨，DevTools 里能看到已经卸载的容器 DOM 还被引用着。

原因是实例会被登记在容器 DOM 上，再加上你自己注册的窗口尺寸监听、内部的动画帧循环，这些引用共同把整棵子树钉在内存里。

正确顺序是：先解除外部监听（移除窗口事件或断开 ResizeObserver），再调用 dispose。注意 clear() 不是 dispose()——前者只清 option，实例与监听都还在。

初始化前用 getInstanceByDom 检查是否已有实例，能避免热更新或重复渲染时在同一容器上叠加多个实例（这种情况下控制台会给出提示，但很容易被忽略）。

容器被父级 display: none 隐藏时初始化的坑，和内存泄漏无关：宽高为零画不出东西，显示后不会自动恢复，要手动 resize()。

折叠面板、标签页切换、抽屉里的图表基本都会遇到。

stateDiagram-v2 [*] --> NoInst NoInst: 容器上还没有实例 ZeroSize: 已初始化但容器宽高为零 Live: 实例存活且已设置 option Stale: 组件已卸载但实例未释放 Disposed: 已释放 NoInst --> Live: init 且容器可见 NoInst --> ZeroSize: init 时父级 display 为 none ZeroSize --> Live: 容器显示后手动调用 resize Live --> Live: setOption 增量更新 Live --> Live: clear 清空 option 但实例仍在 Live --> Stale: 组件卸载却没调 dispose Stale --> Stale: 尺寸监听与动画帧循环仍持有 DOM 引用 Live --> Disposed: 先解除监听再 dispose Disposed --> [*] NoInst --> Live: 重复 init 前应先用 getInstanceByDom 检查 
// SPA 里的正确生命周期：以 React 为例，Vue 的 onBeforeUnmount 同理
function useChart(ref, option) {
  useEffect(() => {
    const el = ref.current;
    if (!el) return;

    // 1. 避免热更新或重复渲染时在同一容器上叠加实例
    let chart = echarts.getInstanceByDom(el);
    if (!chart) chart = echarts.init(el, null, { renderer: 'canvas' });

    chart.setOption(option, { replaceMerge: ['series'] });

    // 2. 用 ResizeObserver 而不是 window.resize：容器自身变化也能捕获
    const ro = new ResizeObserver(() => chart.resize());
    ro.observe(el);

    return () => {
      // 3. 顺序很重要：先断监听，再 dispose
      ro.disconnect();
      chart.dispose();          // clear() 不释放实例，监听与动画循环还在
    };
  }, [ref, option]);
}

// 容器初始化时处于隐藏状态（宽高为 0），显示后必须补一次 resize
function onPanelShown(el) {
  const chart = echarts.getInstanceByDom(el);
  if (chart) chart.resize();
}

按需引入与打包体积

全量引入的代价看得见：本站 vendor 目录自托管的 echarts.min.js 约 1 MB（压缩前体积），含二十多种图表、全部组件和两套渲染器，典型业务页面用得上的不超过三种。

按需引入要注册三类东西：图表类型、组件、渲染器。

坑有三个：漏注册渲染器，图表空白且不报错，最常见；漏注册组件，直角坐标系要网格组件，提示框、图例、缩放条是独立组件，缺哪项哪项静默失效；

地图数据当依赖打包——地理数据往往比图表库本身还大，必须运行时按需加载后注册，不能塞进主 bundle。

要用的能力必须注册的模块类别漏掉后的表现
任意图表Canvas 或 SVG 渲染器容器尺寸正常但完全空白，无报错
折线、柱状、散点对应图表模块 + 网格组件缺网格组件时坐标轴不出现
提示框、图例、标题各自的组件模块配置被忽略，功能静默失效
缩放条与框选缩放dataZoom 相关组件交互无响应
dataset 与 transformdataset 组件与对应 transform数据映射不生效，图为空
地图地图图表 + 运行时注册地理数据把地理数据打进主包会让体积翻倍
标签避让、系列间转场额外的特性模块标签重叠，转场退化为直接重绘

出图环境、参数组合与换库判据

邮件、PDF、报表这类不跑 JavaScript 的环境出图有两条路。服务端 SVG 渲染：Node 里用 SVG 渲染器建实例并开服务端模式，直接拿 SVG 字符串，不依赖浏览器和原生 Canvas 绑定；

缺点：动画与交互全失效，靠浏览器测量的文本布局略有差异。浏览器端导出位图：用 getDataURL 拿 png 或 jpeg，像素比要调高，否则高分屏发虚；多图联动用连接导出合成一张。

与其他库的分界：要大量开箱图表类型、中文文档、仪表盘式配置，选 ECharts；只要几种基础图、极小体积，Chart.js 更合适（详见站内 Chart.js 轻量图表库）；

需要完全自定义的、图表库里没有的可视化形式，用 D3 自己搭（详见站内 D3.js 数据驱动文档）。不要用 D3 去画标准折线柱状，也不要试图把 ECharts 掰成通用绘图框架。

// 一、服务端出图：Node 环境，SVG 渲染器 + 服务端模式，不需要原生 canvas
import * as echarts from 'echarts';

const chart = echarts.init(null, null, {
  renderer: 'svg',
  ssr: true,          // 服务端模式：不绑定 DOM，不启动动画循环
  width: 800,
  height: 400,
});
chart.setOption({
  animation: false,   // 服务端渲染必须关掉，否则拿到的是第一帧
  xAxis: { type: 'category', data: labels },
  yAxis: { type: 'value' },
  series: [{ type: 'bar', data: values }],
});
const svg = chart.renderToSVGString();
chart.dispose();      // 服务端同样要释放，否则是进程级泄漏

// 二、浏览器端导出位图：像素比必须显式提高，否则高分屏上发虚
const url = chart.getDataURL({
  type: 'png',
  pixelRatio: 2,
  backgroundColor: '#fff',              // 默认透明，贴到白底文档里会有边缘问题
  excludeComponents: ['toolbox'],       // 排除工具栏这类不该出现在图片里的组件
});

// 三、等渲染真正完成再导出，否则可能截到渐进渲染的中间帧
chart.on('finished', () => {
  const finalUrl = chart.getDataURL({ type: 'png', pixelRatio: 2 });
  // 这里再上传或下载
});

最容易踩的坑

❌
最容易踩的坑
  • 幽灵系列：setOption 默认按数组下标合并，系列数量变少时旧系列不会消失。给 series 加 id 或用 replaceMerge，别用 notMerge 硬清。
  • 用 notMerge 刷新数据：会连带重置 dataZoom 窗口与图例勾选，用户刚调好的视图被打回原点。
  • 把 clear() 当 dispose()：前者只清 option，实例、尺寸监听与动画帧循环全都还在，内存照样涨。
  • 忘记 dispose：SPA 里切几次路由内存阶梯式上涨，已卸载的容器 DOM 被实例引用而无法回收。
  • 在隐藏容器里 init：宽高为零，图什么都不画，显示出来之后不会自动恢复，必须手动 resize()。
  • 按需引入漏注册渲染器：图表完全空白且不报任何错，排查时容易一直怀疑 option 写错了。
  • 用 average 采样做监控图：尖峰被抹平，告警图上看不到毛刺，这是会误导判断的失真。
  • 开了 large 却还要逐点交互：批量绘制路径没有单图元对象，强调效果与单项样式都会失效。
  • 只调 progressive 不看门槛：图元数低于 progressiveThreshold（默认 3000）时该配置完全不生效。
  • 无视 filterMode：默认 filter 会真的过滤数据，导致缩放一个系列把另一个系列的纵轴带跑。
  • 不给展示性图元设 silent：命中测试对全部图元逐一判断，是「鼠标一动就卡」的首要来源。
  • 在 mousemove 回调里 setOption：不节流会直接打满主线程，还可能与更新事件形成循环。
  • 导出图片不提像素比、不等 finished：高分屏上发虚，或者截到渐进渲染的中间帧。
  • 把地图地理数据打进主包：地理数据常常比图表库本体还大，必须运行时按需加载后注册。
