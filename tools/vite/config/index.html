配置与插件机制：钩子、中间件与 SSR

Vite 的配置文件通常很短，但它背后的插件系统信息量不小。理解一件事就够了：Vite 插件就是 Rollup 插件，加上一组只在开发服务器上生效的额外钩子。这个设计让它能直接复用整个 Rollup 插件生态，也解释了为什么某些插件在 dev 下有效在 build 下失效。开发期不打包的模型见 架构篇，产物优化见 生产构建优化。

钩子触发时机典型用途常见误用
config解析配置前按 mode 注入默认配置直接改传入对象而不 return 片段，导致合并策略失效
configResolved配置最终确定后把 command、base、mode 存起来供后续钩子用试图在这里改配置，此时已是只读
resolveId遇到每个 import 说明符实现虚拟模块、自定义解析规则返回值不加空字节前缀，虚拟模块被其他插件当真实文件读
load需要某个 id 的内容时为虚拟模块提供代码对所有 id 都返回内容，把真实文件覆盖掉
transform每个模块被请求或打包时代码改写、注入埋点不按 id 过滤就做重计算，直接拖慢热更新
configureServer开发服务器创建时挂 mock 中间件、加自定义路由路径匹配过宽，把页面请求也吞了
transformIndexHtml返回 HTML 前注入版本号、埋点脚本、预加载标签用字符串拼接破坏 HTML 结构，改用返回标签描述对象更稳
handleHotUpdate文件变更时扩大或缩小热更新影响范围返回空数组想阻止更新，结果连整页刷新也没了，改动完全不生效

组合执行位置适合做什么踩坑点
enforce: 'pre'内置插件之前需要拿到未被处理的原始源码，如自定义语法、宏展开不设 pre 时拿到的是框架插件转换后的代码，正则失配
不设 enforce内置核心插件之后大多数常规转换与其他同级插件的相对顺序取决于数组位置，容易被重排打乱
enforce: 'post'全部之后产物统计、最终文本替换此时代码已压缩，可读性差，做替换要非常小心
apply: 'serve'仅开发mock 服务、开发期日志、调试面板忘了生产也需要同等能力，上线后功能缺失
apply: 'build'仅构建体积分析、产物校验、CDN 上传开发期完全不生效，问题只在 CI 暴露
apply 传函数按配置动态判断只在 SSR 构建或某个 mode 下启用判断条件写错时静默不生效，没有任何报错

写一个自己的插件

下面这个插件做两件真实有用的事：构建时把版本号与构建时间注入 HTML（前端可以据此提示用户刷新，这是解决新版本发布后旧页面报错的常用手段），以及开发期打印慢模块日志。它同时用到了 config、configResolved、transformIndexHtml、configureServer、transform 五个钩子。

// plugins/build-stamp.ts
import type { Plugin, ResolvedConfig } from 'vite'
import { execSync } from 'node:child_process'

export function buildStamp(options: { slowMs?: number } = {}): Plugin {
  const slowMs = options.slowMs ?? 50
  let config: ResolvedConfig
  const commit = (() => {
    try {
      return execSync('git rev-parse --short HEAD').toString().trim()
    } catch {
      return 'unknown'   // CI 里可能是浅克隆，不要让构建因为拿不到 commit 而失败
    }
  })()

  return {
    name: 'app:build-stamp',
    // 不设 enforce 就够了：这里不需要拿原始源码
    config() {
      // 返回片段让 Vite 做深合并，不要直接改入参对象
      return {
        define: {
          // define 是文本替换，值必须是字符串化的 JSON，否则会被当成标识符
          __BUILD_COMMIT__: JSON.stringify(commit),
          __BUILD_TIME__: JSON.stringify(new Date().toISOString()),
        },
      }
    },
    configResolved(resolved) {
      config = resolved   // 后面要用 command 判断 dev 还是 build
    },
    transformIndexHtml() {
      // 返回标签描述数组比字符串拼接安全，不会破坏 HTML 结构
      return [
        {
          tag: 'meta',
          attrs: { name: 'x-build-commit', content: commit },
          injectTo: 'head',
        },
      ]
    },
    transform(code, id) {
      // 关键：先用 id 过滤，否则每个模块都要付这份开销
      if (config.command !== 'serve') return null
      if (!/\.[jt]sx?$/.test(id) || id.includes('node_modules')) return null

      const start = performance.now()
      // 这里只做很轻的工作示意；真正的重计算绝不能放在这里
      const result = code.includes('__BUILD_COMMIT__') ? code : null
      const cost = performance.now() - start
      if (cost > slowMs) {
        this.warn(`transform 耗时 ${cost.toFixed(1)}ms: ${id}`)
      }
      return result
    },
    configureServer(server) {
      server.httpServer?.once('listening', () => {
        // 开发期把构建标记打出来，方便对照线上问题
        server.config.logger.info(`  ➜  build commit: ${commit}`)
      })
    },
  }
}

configureServer：开发期起一个 mock 服务

configureServer 拿到的 server.middlewares 是一个 connect 实例，可以直接 use 中间件。这比单独跑一个 mock 进程省事：不用配代理、不占端口、随 dev server 一起起停。

// plugins/mock.ts —— 只在开发期生效
import type { Plugin } from 'vite'

export function mockApi(): Plugin {
  return {
    name: 'app:mock-api',
    apply: 'serve',        // 必须限定，否则生产构建时这段逻辑毫无意义
    configureServer(server) {
      // 返回一个函数的话，它会在 Vite 内置中间件安装之后才执行
      // 直接 use 则挂在内置中间件之前，要格外小心别吞掉页面请求
      server.middlewares.use(async (req, res, next) => {
        const url = req.url ?? ''
        // 路径判断必须精确：写成 startsWith 斜杠 会把首页也拦掉
        if (!url.startsWith('/mock/')) return next()

        if (url === '/mock/user' && req.method === 'GET') {
          res.setHeader('content-type', 'application/json; charset=utf-8')
          // 必须调用 end 结束响应，否则请求会挂到超时
          res.end(JSON.stringify({ id: '1', name: '张三', role: 'admin' }))
          return
        }

        if (url === '/mock/upload' && req.method === 'POST') {
          // 读请求体要自己收流，中间件层没有 body 解析
          const chunks: Buffer[] = []
          for await (const c of req) chunks.push(c as Buffer)
          const body = JSON.parse(Buffer.concat(chunks).toString() || '{}')
          res.setHeader('content-type', 'application/json; charset=utf-8')
          res.end(JSON.stringify({ ok: true, received: Object.keys(body) }))
          return
        }

        res.statusCode = 404
        res.end(JSON.stringify({ message: 'mock not found' }))
      })
    },
  }
}

SSR：ssrLoadModule 与依赖外部化

Vite 的 SSR 不是一个开箱即用的框架，而是一组原语。开发期的核心是 ssrLoadModule：它把服务端入口以 Node 能执行的形式加载进来，并且带热更新，所以改渲染逻辑不需要重启进程。

sequenceDiagram participant C as 浏览器 participant N as 自建 Node 服务 participant V as Vite 中间件模式实例 participant E as 服务端入口模块 C->>N: GET 某个页面路径 N->>N: 读取根目录 index.html 模板 N->>V: transformIndexHtml 处理模板 V-->>N: 注入客户端脚本与 HMR 连接 N->>V: ssrLoadModule 加载服务端入口 V->>V: 按需转译 外部化 node_modules 依赖 V-->>E: 返回带热更新的模块实例 N->>E: 调用 render 传入路径与上下文 E-->>N: 返回 HTML 片段与预加载信息 N->>N: 把片段塞进模板占位处 N-->>C: 返回完整 HTML Note over N,V: 报错栈默认指向转译后代码
必须调用 ssrFixStacktrace 才能定位源码
依赖类型默认处理为什么需要干预时
普通 CommonJS 依赖外部化，由 Node 直接 requireNode 本来就能跑，省一次转换一般不用管
只提供 ESM 的依赖可能外部化失败Node 的加载方式与 Vite 转换结果冲突写进 ssr.noExternal
需要 Vite 转换的包（含 JSX、Vue SFC）外部化会报语法错误Node 不认识这些语法写进 ssr.noExternal
monorepo 里的本地包默认不外部化需要跟随源码热更新一般不用管，若报错可显式列出
引用了 CSS 的组件库外部化后 Node 无法解析 CSS 导入Node 不认识 CSS 模块ssr.noExternal 加样式收集
只能在浏览器跑的包直接报错，如访问 window服务端没有这些全局对象改成动态导入并判断环境
// server.mjs —— 开发期 SSR 的最小可跑骨架
import fs from 'node:fs/promises'
import express from 'express'
import { createServer as createViteServer } from 'vite'

const app = express()

// 中间件模式：不让 Vite 接管 HTML 服务，由我们自己渲染
const vite = await createViteServer({
  server: { middlewareMode: true },
  appType: 'custom',
})
app.use(vite.middlewares)

app.use('*', async (req, res) => {
  try {
    let template = await fs.readFile('index.html', 'utf-8')
    // 让 Vite 注入客户端脚本与 HMR 连接，否则页面没有热更新
    template = await vite.transformIndexHtml(req.originalUrl, template)

    // 关键 API：加载服务端入口，带热更新，改代码无需重启
    const { render } = await vite.ssrLoadModule('/src/entry-server.tsx')
    const appHtml = await render(req.originalUrl)

    res.status(200)
      .set({ 'Content-Type': 'text/html' })
      .end(template.replace('<!--ssr-outlet-->', appHtml))
  } catch (e) {
    // 不加这一行，报错栈全部指向转译后的代码，完全没法定位
    vite.ssrFixStacktrace(e)
    res.status(500).end(e.message)
  }
})

常用配置项速查与各自的坑

配置项作用默认值坑
base产物里资源的公共前缀斜杠部署到子路径时不改就全部 404；运行时拼路径要用 import.meta.env.BASE_URL
resolve.alias路径别名无必须与 tsconfig 的 paths 同步，否则编辑器与构建行为不一致
define源码级文本替换无值必须是字符串化的 JSON；标识符要足够独特，通常用双下划线包围
envDir 与 envPrefixenv 文件目录与注入前缀根目录，VITE_放宽前缀等于放宽泄露面，不要为了省事改成空前缀
server.proxy开发期反向代理无只在开发生效，生产要靠网关；WebSocket 需单独开 ws
server.warmup启动后预先转译指定文件无大项目首屏慢的有效缓解，但列表写太长会拖慢启动
optimizeDeps.include 与 exclude干预依赖预构建自动扫描动态导入里的依赖扫不到，会在运行时触发重新预构建并刷新页面
build.target产物语法目标较新的基线设太低会引入大量降级代码；设太高老设备白屏
ssr.noExternal强制让依赖参与 SSR 转换空不配会遇到服务端不认识 JSX 或 CSS 的报错
⚠️
define 是文本替换，不是变量注入

写 define: { __VERSION__: pkg.version } 会把版本号当成标识符贴进代码，构建报「未定义」或误引用同名变量。必须写 JSON.stringify(pkg.version)。同理，替换目标要用足够独特的名字（惯例是双下划线包围），否则可能命中业务代码里的同名变量。

配置文件本身的执行环境

有一类问题出在配置文件自己身上，而不是配置内容。vite.config.ts 不是被直接执行的，Vite 会先用 esbuild 把它编译成一个临时文件再由 Node 加载，这带来几个很具体的影响。

现象原因处理
__dirname 报未定义项目声明为 ESM 时不存在这个变量从 import.meta.url 推导，或退而用 process.cwd()
在配置里引用业务代码后报错配置在 Node 里跑，业务代码里的浏览器 API 不存在把需要共享的东西抽成不含运行时依赖的纯数据模块
读不到无前缀的环境变量配置阶段 .env 还没被加载，process.env 里只有系统变量用 loadEnv 显式加载，第三个参数传空字符串
改完配置行为没变配置变更会重启服务器，但依赖它派生的预构建缓存可能仍是旧的必要时加 --force
需要异步拿配置比如构建前要从远端取版本号或路由表defineConfig 支持传入返回 Promise 的函数
同一份配置要区分 dev 与 build两条路径需要的插件不同用函数形式读 command，配合插件的 apply

配置的合并规则也值得说清：插件 config 钩子返回的片段会与用户配置做深合并，对象逐层合并、数组直接拼接、同名标量以用户配置为准。这解释了两个常见困惑——为什么你在插件里设的 define 不会覆盖用户的同名键，以及为什么两个插件各自往 optimizeDeps.include 里加东西不会互相覆盖。反过来说，插件无法通过 config 钩子强制覆盖用户配置，真有这个需求只能在 configResolved 里读到最终值后，在自己的钩子里做相应处理。

还有一个容易被忽略的点：配置文件里的耗时操作会直接计入每次启动时间。在里面同步执行 git 命令、读大文件、甚至发网络请求，会让 dev server 每次启动以及每次配置热重启都多花几百毫秒到几秒。把这类工作加上缓存，或者挪进插件的 buildStart 里只在真正需要时执行。

反模式对照

反模式后果正确做法
插件不设 enforce拿到的是已被框架插件转换过的代码，正则失配且时机不稳定需要原始源码就设 pre，做产物处理就设 post
transform 里做重计算每次保存都付一遍，热更新从几十毫秒退化到几秒先按 id 过滤，缓存结果，一次性工作挪到 buildStart
alias 与 tsconfig paths 不同步编辑器能跳转但构建失败，或反之两处一起改，或用插件从 tsconfig 派生
define 值不做 JSON 序列化构建报未定义标识符，或静默引用到同名变量一律 JSON.stringify
mock 中间件路径匹配过宽把页面请求也吞掉，开发时首页打不开用明确前缀判断，不匹配就 next()
中间件里忘记 res.end()请求挂住直到超时，看起来像后端没响应每条分支都确保结束响应
SSR 里直接访问 window服务端渲染直接抛错，整页 500判断运行环境，或把逻辑放进只在客户端执行的生命周期
SSR 报错不调 ssrFixStacktrace栈指向转译后代码，定位不到源文件catch 里必须调用一次
apply 用错插件在需要的阶段静默不生效，没有任何报错明确它是 serve 专属、build 专属还是两者都要
❌
最容易踩的坑
  • 插件顺序没用 enforce 固定：同级插件的相对顺序取决于数组位置，有人重排一下你的转换就失效了。
  • 在 transform 里读文件或算哈希：这是热更新变慢的头号原因，因为每次保存都会重跑这条链。
  • transform 不做 id 过滤：连 node_modules 里成百上千个模块都会走一遍你的逻辑。
  • define 忘了 JSON.stringify：值被当成标识符，报错信息指向一个你从没写过的变量名。
  • define 的标识符太普通：像 VERSION 这种名字可能命中业务代码里的同名变量，造成无法解释的行为。
  • mock 中间件用过宽的前缀：连首页请求都被拦下，表现是开发服务器起来了但页面全白。
  • 中间件分支漏了 res.end()：请求一直挂着，前端看到的是超时而不是错误。
  • configResolved 里试图改配置：此时配置已只读，改了不报错也不生效。
  • 虚拟模块 id 不加空字节前缀：其他插件会把它当真实文件去读磁盘，报找不到文件。
  • handleHotUpdate 返回空数组：热更新和整页刷新一起被阻止，表现是改代码完全没反应。
  • SSR 忘配 ssr.noExternal：服务端遇到 JSX 或 CSS 导入直接语法报错，错误信息指向 node_modules 深处。
  • 只在 dev 下验证插件：configureServer 这类钩子在 build 时根本不执行，生产行为可能完全不同。
