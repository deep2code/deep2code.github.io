🔧 开发工具与效率

Git · Vim · Hugo · Mermaid · Markdown · 搜索（共 24 篇）

先有判断框架，再谈具体工具

工具类文章最容易变成「安利清单」，但真正影响效率的不是装了多少工具，而是哪些操作被固化下来了。下面五个问题构成一个可复用的判断框架，任何工具进你的工作流之前过一遍，能省掉大量折腾时间。

要问的问题为什么它重要答案不同时的处理方式
这件事一年做几次频率决定投入上限，也决定该不该记住细节每天做：值得配快捷键与别名；每月做：写脚本；一年一次：写一份清单，别写脚本
步骤稳定到可以写死吗步骤不稳定的脚本会变成需要维护的负债稳定就进脚本；不稳定先写成带判断点的清单，稳定后再固化
需要团队统一吗只影响自己的工具可以随便选，影响共同产物的必须统一编辑器与终端个人自由；格式化、提交规范、图的源格式必须统一
能在干净机器上复现吗不可复现的环境等于把配置锁死在一台机器里安装清单、点文件、插件列表、构建入口全部进版本库，并在新环境验证一遍
退出成本有多高迁移成本决定了它值不值得承载核心流程产物是通用文本格式的可以放心用；输出被私有格式绑定的，不要放进关键路径

版本控制：该掌握的是模型，不是命令

大多数人把 Git 当命令集背，于是每遇到新情况就要重新搜一遍。其实只要建立三个心智模型，绝大部分场景都能自己推导出该用什么命令：工作区、暂存区、提交历史是三个独立状态，几乎所有命令都是在它们之间搬东西；分支只是指向某个提交的可移动指针，所以新建和切换都很便宜；提交历史是一张有向图，合并保留真实拓扑，变基则重写历史让它变成直线。

能力「会用」的标准「能负责」的标准
日常提交与分支会提交、切分支、解决冲突能把一次改动拆成若干个自洽的提交，每个提交都能独立通过构建
历史整理知道合并与变基都能把改动带过来清楚变基会重写提交标识，因此只在未共享的分支上做；共享分支用合并
事故恢复知道误操作可能能救回来能用引用日志找回丢失的提交，能判断什么情况下对象确实已经不可恢复
问题定位靠人工回忆是哪次改动引入的用二分查找在提交历史上定位引入问题的提交，并配合可自动判定的脚本
大仓与二进制直接把大文件提交进仓库清楚二进制一旦进历史就会永久占体积，提前用大文件扩展或产物仓库隔离
协作规范各自随意提交统一提交信息规范与评审粒度，把格式化和检查放进提交前或流水线，不靠人盯

编辑器与终端：个人自由，产物统一

编辑器之争没有结论，因为它属于「只影响自己」的那一类。真正值得花时间的是两件事：把高频操作变成不用思考的动作（跳转定义、全局搜索替换、多光标、重复上一个命令），以及把格式化和静态检查从个人习惯里挪到项目配置里——只要它还依赖「每个人记得按一下」，就一定会漂移。

终端侧同理：值得投入的是可复用的东西。命令行的收益来自可组合性，一条管道能把搜索、过滤、结构化提取串起来，这类能力在任何机器上都能用；而记住某个图形工具的菜单位置换机器就归零。另一个常被忽略的点是环境重建：包管理器的安装清单、点文件、插件列表、项目构建入口这四样进了版本库，换机器才是半小时的事，否则就是一整天。

什么图该用什么工具画

选画图工具的第一原则不是好不好看，而是这张图要不要跟着代码一起演进。需要长期维护、随代码评审的，用文本描述的图，因为文本能进版本库、改动在评审里能看出差异；只用一次、需要精确排版的汇报图，拖拽工具更快。第二原则是按要表达的结构选图类型，而不是什么都画成流程图。

要表达什么合适的表达形式产物形态版本控制友好度什么时候别用它
分层架构、模块归属、分类树带分组的流程图纯文本描述，渲染时生成高，差异可读节点上百、需要精确排版时，自动布局会失控
多方交互、协议往返、调用顺序时序图纯文本描述高只想表达静态归属关系时，时序图反而更难读
生命周期与状态流转状态图纯文本描述高状态极多且转移条件复杂时，改用状态转移表更清楚
完整 UML 建模专门的 UML 文本工具文本加渲染服务，通常需要额外运行环境较高，但依赖渲染端团队并不真的做 UML 建模，只是想画个草图时
大规模有向图与依赖关系图布局工具，用描述语言定义节点与边文本描述，自动布局高需要人手控制每个节点位置时
一次性汇报与精确标注拖拽绘图工具图形文件，可导出图片低，差异不可读这张图需要随代码长期演进时
数值分布与趋势数据可视化图表库代码加数据，运行时渲染取决于数据来源只是想表达结构关系，却硬做成图表时

数据可视化内部还有一层分工：需要开箱即用的常见图表类型和交互，选配置式图表库；只要几张轻量图表、不想引入大依赖，选轻量库；要做非标准图形、需要完全控制绘制过程，才值得用底层绘图库；三维场景与模型展示属于渲染引擎的范围，和图表不是同一类问题。

自动化的边界

自动化不是越多越好。判断标准是这件事的判断成本和后果是否稳定：稳定的重复劳动越早自动化越好，含价值判断的决策不该交给脚本，不可逆且缺乏校验的操作应该做成需要人工确认的半自动步骤。

任务特征该不该自动化理由与替代做法
每天重复、输入输出固定该，优先级最高不自动化就是持续付利息；先做成脚本，再考虑接进流水线
偶尔执行但步骤易错、顺序敏感该，但要能干跑价值在于防错而不是省时间；必须支持先预览将要执行的动作
一年一次且每次上下文都不同不该脚本维护成本高于收益；写成清单并记录上次的实际差异
需要人做价值判断不该脚本可以准备材料和给出建议，最终决定留给人
后果不可逆且没有校验手段半自动拆成「生成计划」和「执行计划」两步，中间必须人工确认

另外，自动化脚本自身也有质量门槛，至少满足三条才算合格：可以先干跑看清将要做什么；重复执行结果一致，中断后可以安全重跑；失败时输出足够定位的信息。不满足这三条的脚本比手工操作更危险，因为它执行得更快、影响面更大。

这个专题各子方向怎么读

三条常见路线：刚配新环境，按包管理、终端与文本处理、编辑器、版本控制的顺序过一遍；要给项目补文档和图，先看上面的选图原则，再挑具体工具；临时排查问题，直接找对应的单点工具。下表给每个子方向一句「什么时候该读它」。

子方向它解决的问题什么时候该读它
Git提交模型、分支策略与历史整理需要把混乱的改动整理成可评审的提交、或遇到历史被写坏时
GitHub 与 GitLab托管平台的协作流程与权限要定评审流程与分支保护、或需要把代码托管搬到自建实例时
SVN集中式版本控制的模型与常用操作接手仍在用集中式仓库的老项目时
Homebrew包管理与环境可复现换新机器、或想把开发环境变成一份可执行的清单时
Makefile用统一入口封装构建与常用命令项目里的命令多到需要口口相传、新人跑不起来时
Vim不依赖图形界面的高效编辑经常要在服务器上直接改文件、或想减少手离键盘的次数时
Hugo静态站点生成与内容组织要搭文档站或博客、并希望产物是可托管的纯静态文件时
Markdown轻量标记语法与文档结构要统一团队文档格式、或写可长期维护的技术文档时
Mermaid用文本描述流程图、时序图与状态图图需要跟着代码一起演进、并在评审里看出差异时
PlantUML完整 UML 建模的文本表达确实需要正规 UML 图、且能接受额外渲染环境时
Graphviz用描述语言生成自动布局的有向图节点多、关系复杂，手工排版已经不现实时
代码生图 与 画图工具选型各类生图方案的取舍与工作流团队要定「图的源格式」这件事时
ECharts 与 Chart.js配置式图表与轻量图表的取舍要做看板或报表、需要常见图表类型与交互时
D3.js底层数据绑定与自定义绘制要做的图形超出常规图表类型、需要完全控制绘制过程时
Python 可视化分析过程中的快速出图做数据探查、需要在脚本或笔记本里直接看分布时
Three.js 与 Babylon.js浏览器中的三维渲染要做模型展示或三维交互场景时
Wireshark抓包与协议层面的事实核对双方都说自己没问题、需要用报文证明谁对时
高级搜索检索语法与信息定位效率排查问题时总也搜不到有效资料时
地理编码 与 OCR地址转坐标、图片转文字这类专项转换业务里出现地址解析或纸质材料录入需求时
❌
工具选择上最容易走错的判断
  • 把「装了很多工具」当成效率提升，实际高频操作一个都没固化下来
  • 一年做一次的事也写成脚本，脚本半年后失效，出问题时还不如手工来得快
  • 格式化与检查依赖每个人自觉执行，没有放进项目配置或流水线，风格必然漂移
  • 环境靠手工搭建，没有安装清单和点文件，换机器等于重来一天
  • 长期演进的架构图用拖拽工具画，源文件进了仓库但差异不可读，最终没人敢改
  • 把结构关系硬做成数据图表，或把数值趋势硬画成流程图，图类型和内容对不上
  • 大文件直接提交进版本库，之后仓库体积再也降不回来
  • 在共享分支上重写历史，同事拉取时被迫处理冲突甚至丢提交
  • 脚本不支持干跑、也不幂等，中断后重跑造成二次破坏
  • 用私有格式承载核心流程，等到要迁移时才发现导出的数据不完整
