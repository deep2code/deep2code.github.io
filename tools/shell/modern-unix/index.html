现代命令行工具的替代取舍

🏷️ Modern Unix,终端生态

「替代」分三类，混为一谈才会出事

rg/fd/bat/eza/jq/fzf/delta/sd/dust 这批工具常被打包成一句「Rust 重写，更快更好用」，但它们和被替代对象的关系完全不同，混着用迟早出问题。分清三类：

第一类是同场景替代但语义有差（rg 对 grep、fd 对 find）：常用路径几乎一比一，但默认行为不同、表达能力有裁剪。第二类是只替代「给人看」的那一半（bat 对 cat、eza 对 ls、dust 对 du、delta 对 diff）：它们的输出没有稳定契约，本来就不该被脚本解析。第三类根本不是替代品（jq、fzf）：jq 补上了 Unix 工具链里缺失的结构化数据处理能力，fzf 是交互式选择器，二者都没有对应的传统命令。

工具替代对象能替代的部分替代不了的部分适合写进脚本吗
rggrep -r递归搜索、按类型过滤、多行匹配回溯型正则（后向引用、断言）需 -P；grep -f 大模式文件、POSIX 字符类行为有差异可以，但要显式关掉默认忽略规则
fdfind按名字/扩展名/类型查找，-x/-X 执行find 的表达式语言：-newer、-perm、-prune、-printf、布尔组合可以，注意默认跳隐藏文件
batcat人看文件（高亮、行号、分页）作为管道中间环节的透明性（虽然非 tty 时会退化成 cat）不建议，用 cat
ezals人看目录（Git 状态、树形）不是 ls 的全部选项的超集；ls 输出本来就不该被解析不要
jq—JSON 的查询、变换、聚合不是流式文本工具，需要完整解析每个顶层值适合，但要处理好数字精度与内存
fzf—交互式模糊选择、接管 Ctrl+R无 tty 环境下不可用，脚本里只能用 -f 过滤模式仅 --filter 模式
deltadiff 的阅读层Git diff 的可读性（并排、语法高亮）输出不是合法 patch，不能喂给 git apply/patch不要
sdsed 's/../../'正则替换，分隔符不用转义行地址、多命令编排、hold space、-i.bak 备份语义可以，但复杂编辑仍用 sed
dustdu人看目录占用排行精确字节数输出（脚本要精确值用 du -sk）不要

sed 的地址、hold space 与 awk 的字段处理这类「三剑客」话题，本站另有《文本处理》篇专门展开，这里不重复；引用与参数展开的规则见《Shell 脚本编程》篇。

rg 为什么快：三个机制，以及它换掉的能力

先纠正一个流传很广的说法：「rg 比 grep 快十倍」不是普遍成立的。单文件、简单字面量、LC_ALL=C 的场景下，GNU grep 和 rg 在同一量级，两者都用 SIMD 加速的子串搜索。差距主要出现在「递归搜索一个大代码库」上，来源是三个机制：

第三点值得单独说：Rust 的 regex 引擎是有限自动机实现（惰性 DFA + SIMD 字面量预筛），对输入长度和模式长度都是线性时间，天然免疫「灾难性回溯」——那种让 PCRE 在特定输入上跑到 CPU 打满的正则拒绝服务，在这套引擎上不存在。代价是它放弃了回溯引擎才能提供的特性：后向引用 \1、前后向断言 (?=...) (?<!...)、原子组。需要这些时用 rg -P 切到 PCRE2（官方发布的二进制带 PCRE2；发行版包不一定带），或者用 --engine auto 让它在模式不被默认引擎支持时自动切换。切过去之后，线性时间保证和一部分性能优势就一起没了。

机制带来的收益代价 / 失效条件
按忽略规则剪枝目录大仓库里跳过 node_modules、target、构建产物，减少的是 I/O 总量会漏掉你确实想搜的被忽略文件；仓库本来就没有忽略规则时收益为零
并行目录遍历多核上遍历与搜索重叠进行只搜单个文件时完全用不上；机械盘或网络文件系统上并行可能反而更慢
有限自动机 + SIMD 预筛线性时间，不会灾难性回溯；带长字面量的模式几乎按内存带宽跑不支持断言与后向引用；纯 .* 这类无字面量可筛的模式优势下降
默认 UTF-8 感知\w、大小写折叠对非 ASCII 正确这部分开销是 grep 在 LC_ALL=C 下省掉的，所以「同等条件」的对比要注意 locale

「明明有这个文件却搜不到」：默认忽略规则的完整清单

这是新手最常撞的墙，而且没有任何报错。rg 默认会跳过：.gitignore 命中的文件、.ignore 与 .rgignore 命中的文件、全局 gitignore（core.excludesFile）、.git/info/exclude、隐藏文件与目录、被判定为二进制的文件，以及不跟随符号链接。还有一个更隐蔽的规则：默认只有检测到自己在一个 git 仓库里时才应用 .gitignore（要在非仓库目录里也应用，得加 --no-require-git）。

最典型的三个现场：搜不到 dist/ 里的编译产物（被 gitignore）、搜不到 .env 或 .github/workflows/（隐藏路径）、搜不到 *.min.js 里的字符串（被判二进制或被忽略）。

默认行为差异矩阵：真正会咬人的六项

把新旧工具当同义词用，出事的地方都在默认值上。下表是六个高频差异点，建议在自己的 ~/.zshrc 里贴一份：

维度grep / findrg / fd踩坑形态
大小写区分rg 区分；fd 智能大小写同一套心智模型套两个工具，fd 多匹配出一堆结果
隐藏文件都搜都跳过改配置文件时以为仓库里没有这一项
忽略规则不理解 gitignore默认遵守CI 里 rg 搜不到产物，本地手敲却能搜到（因为路径不同）
符号链接find 默认不跟随；grep -R 跟随默认不跟随，-L 开启软链到别处的代码目录被整体漏掉
匹配对象find -name 匹配基名，-path 匹配全路径fd 默认匹配基名，-p 才匹配全路径写了带斜杠的模式却零结果
退出码0 有匹配 / 1 无匹配 / 2 出错相同set -e 下「没搜到」会直接终止脚本

最后一行是所有 CI 脚本的公共陷阱：set -euo pipefail 加上一句 rg TODO src/，在代码干净（没有 TODO）的时候把流水线判成失败。正确写法是显式接住退出码 1，并且把「出错（2）」和「无匹配（1）」区分开——这也是下面这段代码的重点。

#!/usr/bin/env bash
set -euo pipefail

# 1) 区分「无匹配」和「真出错」：rg/grep 都是 1=无匹配 2=错误
count_todo() {
  local out rc
  set +e
  out=$(rg --no-ignore --hidden -c 'TODO|FIXME' src/ 2>/dev/null)
  rc=$?
  set -e
  case "$rc" in
    0) printf '%s\n' "$out" ;;
    1) echo "no match" ;;   # 干净代码不该让流水线失败
    *) echo "rg failed with $rc" >&2; return "$rc" ;;
  esac
}

# 2) 脚本里永远显式写出忽略策略，不要依赖默认值
#    -uu = --no-ignore --hidden；要连二进制一起搜再加一个 u
rg -uu --glob '!.git/**' --glob '!*.min.js' -n 'AWS_SECRET' .

# 3) 跨进程传文件名一律用 NUL 分隔，别指望文件名里没有空格和换行
fd --hidden --no-ignore --type f --extension go --print0 \
  | xargs -0 -n 50 -P 4 gofmt -l

# 4) 只要文件清单的时候用 rg --files，比 fd 少装一个依赖
rg --files --hidden --glob '!node_modules/**' | wc -l

交互式与脚本的分界：输出契约和 tty 检测

这条界线可以用一个判据划清：这个工具的输出格式，作者承诺过向后兼容吗？grep/find/du 的输出格式几十年没变，POSIX 有规定；bat/eza/dust/delta 的输出是为人眼设计的，小版本之间就可能调整配色、列宽、排序。所以前者可以被解析，后者不行。

好消息是这批工具基本都做了 tty 检测：非终端输出时自动关掉颜色、分页和装饰（bat 会退化成接近 cat 的纯输出，rg/fd/jq 关闭颜色）。所以偶尔把它们放进管道不会立刻炸，但别把「不会立刻炸」当成契约。真要在脚本里稳定行为，就显式写死：bat --style=plain --paging=never、jq -r、rg --color=never --no-heading --with-filename --line-number。

fzf 是个特例：它需要 /dev/tty。在 CI、cron、容器 entrypoint 里没有 tty，交互模式会直接失败或挂住。脚本里只能用它的非交互过滤模式 fzf -f 关键词。同理，把 alias grep=rg 写进 ~/.zshrc 是安全的（非交互 shell 不展开别名），但把 rg 写进 #!/bin/sh 脚本就是把依赖带进了生产环境。

脚本里依赖非 POSIX 工具的真实代价

「反正我机器上装了」是可移植性问题的全部来源。列一下这些工具实际缺席的地方：

运行环境默认有什么rg/fd/jq 是否可用加装的代价
Debian/Ubuntu slim 镜像coreutils、grep、sed、find都没有apt-get 一层，镜像变大且拖慢构建；二进制名还叫 batcat、fdfind
Alpine 镜像BusyBox 版 grep/sed/find（功能是子集）apk 里有，musl 构建BusyBox 的 grep/sed 选项比 GNU 少，反而容易被迫装新工具
distroless / scratch连 shell 都没有只能自己塞静态二进制要自己跟 CVE、自己管版本
生产主机（受管、禁装包）发行版自带的 POSIX 工具通常没有，且申请流程漫长应急脚本必须能只靠 POSIX 跑
macOS 开发机BSD 版 sed/awk/find/dubrew 装了就有BSD 与 GNU 选项差异是另一类坑，详见《文本处理》篇
CI runner（GitHub 托管镜像）预装较全，含 jqjq 有；rg/fd 视镜像与版本依赖预装等于依赖平台不改镜像，迟早翻车

务实的规则是按脚本的「运行地点」分级：只在开发机跑的脚本随便用；CI 里跑的脚本把工具版本固定下来（下载指定版本的静态二进制并校验 checksum，而不是 apt-get install 拿到发行版给的随机版本）；可能在生产机应急执行的脚本只用 POSIX 工具，或者做能力探测 + 回退。

#!/bin/sh
# POSIX sh，不用 bashism。目标：有 rg 就用 rg，没有就退回 grep，行为保持一致。

# 探测时同时兼容 Debian 的改名（fd 叫 fdfind，bat 叫 batcat）
if command -v rg >/dev/null 2>&1; then
  # 显式关掉所有默认忽略，让两条分支的语义对齐
  search() { rg -uuu --color=never --no-heading --with-filename --line-number -e "$1" "$2"; }
elif command -v grep >/dev/null 2>&1; then
  search() { grep -rnI -e "$1" "$2"; }
else
  echo "neither rg nor grep available" >&2
  exit 127
fi

FD_BIN=$(command -v fd || command -v fdfind || true)
list_go_files() {
  if [ -n "$FD_BIN" ]; then
    "$FD_BIN" --hidden --no-ignore --type f --extension go --print0 "$1"
  else
    find "$1" -type f -name '*.go' -print0
  fi
}

search 'panic(' ./cmd || [ $? -eq 1 ]   # 无匹配不算失败
list_go_files . | xargs -0 -n 20 wc -l

jq 的流式处理与内存边界

jq 最常被误解的一点：它不是流式文本工具。默认模式下它按顶层值逐个读取，但每个顶层值必须被完整解析成内存里的树。所以 jq '.[] | .id' 5GB-array.json 会因为那个 5GB 的数组是一个顶层值而吃满内存；而同样 5GB 的 NDJSON（每行一个对象）却毫无压力，因为每个顶层值都很小。-s/--slurp 更是把全部输入收进一个数组，是主动放弃内存边界。

sequenceDiagram participant F as 输入文件 participant P as jq 解析器 participant M as 内存 participant O as 输出 Note over F,O: 模式一 默认 按顶层值解析 F->>P: 读入一个完整顶层值 P->>M: 构建整棵树 峰值约等于该值大小的数倍 M->>O: 求值后输出 Note over F,O: 模式二 slurp 主动放弃边界 F->>P: 读入全部输入 P->>M: 构建一个包含所有值的大数组 Note over M: 输入多大 内存就多大 Note over F,O: 模式三 stream 事件流 F->>P: 按 token 增量解析 P->>O: 发出 路径与叶子值 事件对 Note over M: 峰值只和单条路径深度相关 O->>O: 用 fromstream 与 truncate_stream 重组成对象
读取模式内存峰值能做什么适用规模
默认（逐顶层值）单个顶层值的数倍全部 jq 语法单个值在百 MB 以内
-s / --slurp整份输入的数倍跨值聚合、排序、去重只在输入确定很小时用
-n + inputs单个顶层值逐值处理并累积统计（reduce）NDJSON / 多文档流，可到 GB 级
--stream与路径深度相关，基本恒定抽取字段、过滤数组元素单个超大文档，GB 级
--stream + fromstream单个数组元素把大数组还原成逐个对象再正常处理单个超大数组，首选写法

另一个必须知道的是数字精度：jq 内部用 IEEE 754 双精度，超过 2^53 的整数（雪花 ID、订单号、Twitter ID）在 jq 1.6 里会被悄悄改写。jq 1.7 起对「原样透传、未参与运算」的数字保留字面精度，但一旦你对它做了算术就仍然退化。结论是：大整数 ID 在 JSON 里就该用字符串传；拿不到这个前提时，用 tostring 之前先确认 jq 版本，并且绝不对 ID 做算术。

# 1) 单个超大数组：用 --stream + fromstream 把它拆成逐个对象，内存恒定
#    1|truncate_stream 的含义是剥掉最外层数组这一级路径
jq -n --stream 'fromstream(1|truncate_stream(inputs))' huge-array.json \
  | jq -r '[.id, .status] | @tsv'

# 2) 只要几个字段时连重组都不需要，直接在事件流上过滤
#    事件形如 [路径数组, 叶子值]，下面挑出所有 .[].email
jq -n --stream 'select(length==2 and (.[0][-1]=="email")) | .[1]' huge-array.json

# 3) NDJSON 用 -n + inputs 做流式聚合，内存只装得下一条记录
jq -n 'reduce inputs as $r ({}; .[$r.status] += 1)' events.ndjson

# 4) 外部变量一律用 --arg/--argjson 传，别把 shell 变量拼进 jq 程序
#    拼字符串时对方只要放一个引号或反斜杠，你的过滤器语义就变了
status="pay'ing"
jq -r --arg s "$status" '.items[] | select(.status == $s) | .id' orders.json

# 5) 版本与精度自检：输出不等于输入就说明这个 jq 会改写大整数
jq --version
echo '{"id":9007199254740993}' | jq -c .

单二进制分发与包管理器的取舍

这批工具几乎都是「一个静态二进制、无运行时依赖」，这既是它们能快速铺开的原因，也是版本治理的麻烦来源。

获取方式版本新旧安全更新责任可复现性适合
发行版包（apt/yum）常落后一到两年，选项可能不存在发行版打补丁随镜像 tag 变开发机、可容忍旧版本的场景
Homebrew / apk较新，滚动更新上游 + 打包方差，随时会升个人开发机
GitHub release 静态二进制 + checksum精确到某个 tag自己跟最好CI 镜像、需要可复现的流水线
cargo install（源码编译）最新自己跟受 Rust 版本影响需要特定 feature（如带 PCRE2）时
版本管理器（asdf/mise 一类）可锁定自己跟好，配置文件即版本多人共用同一套工具版本

三个容易忽略的细节：其一，Debian/Ubuntu 会改二进制名——bat 装出来叫 batcat，fd 的包叫 fd-find 而命令叫 fdfind，脚本里硬写名字必挂。其二，发行版编译选项可能裁掉功能，最典型的就是 rg -P 需要的 PCRE2 支持。其三，选项会随大版本变，脚本里用到的每个长选项都应该在固定版本上验证过，别在 CI 里 apt-get install ripgrep 然后指望半年后的版本行为一致。

最容易踩的坑

❌
这些坑每一条都能复现
  • set -euo pipefail 的脚本里直接写 rg PATTERN：代码干净（无匹配，退出码 1）时流水线被判失败。必须显式接住 1，并把 2 当真错误处理。
  • 以为 rg 和 grep 只是快慢之差：rg 默认遵守 .gitignore、跳隐藏文件、跳二进制、不跟随符号链接，四条任一都能让你「搜不到」。脚本里一律显式写 -uu 或 --no-ignore --hidden。
  • rg 默认区分大小写，fd 默认智能大小写：同一心智模型套两个工具，一个漏结果、一个多结果。
  • 在 clone 后删掉 .git 的容器里 debug 忽略规则：rg 默认「不在 git 仓库内就不读 .gitignore」，行为和本地不一致。
  • 把断言正则原样交给 rg：默认引擎不支持，要 -P；而发行版包可能没编译 PCRE2，-P 直接报错。
  • 用 rg -r 以为能改文件：-r 只改输出，文件一个字节都没动。
  • 把 bat/eza/dust 的输出喂给 awk '{print $2}'：这些输出没有稳定契约，升个小版本列就变了。脚本里用 cat、du -sk、rg --files。
  • 把 delta 的输出当 patch 保存：它是阅读层，不是合法 diff，git apply 会失败。生成 patch 用 git diff --no-color。
  • 在 CI 或 cron 里调 fzf 交互模式：没有 /dev/tty，任务挂住或失败。脚本里只用 fzf -f。
  • 在 Debian 系镜像里写 bat/fd：命令实际叫 batcat/fdfind，command -v 探测时要把两个名字都试一遍。
  • jq '.[]' 超大数组.json 把内存吃光：那是一个顶层值，必须 --stream 配 fromstream(1|truncate_stream(inputs))；-s 只会更糟。
  • 让 jq 处理雪花 ID：1.6 会把超过 2^53 的整数改写，1.7 只在数字未参与运算时保留精度。ID 用字符串传，永不对 ID 做算术。
  • 把 shell 变量拼进 jq 过滤器字符串：对方放一个引号就能改写你的过滤器语义，一律 --arg / --argjson。
  • 用管道传文件名却不加 --print0/-0：文件名里的空格、换行、引号会把循环拆错。
