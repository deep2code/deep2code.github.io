系统排查的命令与判读

🏷️ systemd,系统管理,自动化脚本

排障最怕的不是不会敲命令，而是顺序错了——一上来就看 CPU 使用率，或者看到 free 的 free 列很小就断定内存不够。这篇按资源分层给出排查顺序，每层都写清「先跑什么、看哪个字段、什么值算异常」。

需要说明边界：本篇只讲单机上用命令做现场判读。告警规则与指标体系见本站 devops/monitoring/，日志采集与检索见 devops/logging/，容器与 K8s 场景的排障入口见 devops/kubernetes/。

load 高之后的分诊：它可能跟 CPU 毫无关系

uptime 给出的三个数是过去 1、5、15 分钟内处于可运行状态（R）加上不可中断睡眠状态（D）的进程数的指数移动平均。Linux 特有地把 D 状态算了进来（原始 UNIX 只算 R），所以网络文件系统卡住、磁盘变慢、内核路径阻塞都会把 load 顶到几十上百，而此时 CPU 可能一直空闲。

还要除以核心数才有意义：32 核机器上 load 8 是很闲，2 核机器上 load 8 已经排长队了。

内存判读：最容易得出错误结论的一层

三个必须纠正的常见误解：free 列小是健康的、RSS 求和不能当总占用、swap 已用量不等于当前有问题。

free 的列含义能当可用量吗
total物理内存总量—
used总量减去 free 与 buffers 与 cache不能当「应用占用」，里面还有内核 slab 等
free完全没被使用的内存不能。Linux 会把空闲内存拿去做页缓存，这一列小是设计使然
sharedtmpfs 与共享内存注意共享内存目录被写满时，表现出来就像内存不足
buff/cache页缓存加目录项与 inode 缓存有压力时可回收，但脏页要先写回，回收本身有延迟成本
available内核估算的「不引发换页即可分配」的量这才是你该看的那一列
Swap 的 used已用交换区只要换页速率为 0，历史遗留的已用交换不代表当前有问题

关于 RSS：它包含共享库和共享内存映射，多个进程共享同一份物理页时每个都完整计入自己的 RSS。所以把 ps aux 的 RSS 列加起来常常超过物理内存总量，多进程模型（写时复制出一堆 worker）尤其明显。要估真实占用得看 PSS，也就是共享页按共享进程数均摊后的值。

# 真实占用看 Pss，不看 Rss。smaps_rollup 是内核帮你汇总好的，比解析 smaps 快很多
awk '/^(Rss|Pss|Private_Dirty|Swap):/ { printf "%-16s %8d kB\n", $1, $2 }' /proc/1234/smaps_rollup

# 按 Pss 排出真实占用前十的进程（需要 root）
for p in /proc/[0-9]*; do
  pss=$(awk '/^Pss:/ { print $2 }' "$p/smaps_rollup" 2>/dev/null) || continue
  [[ -n ${pss:-} ]] && printf '%8d kB  %s\n' "$pss" "$(tr -d '\0' < "$p/cmdline" | cut -c1-60)"
done | sort -rn | head -10

# 容器里 free 和 top 看到的是宿主机数据，必须读 cgroup。下面是 cgroup v2 的路径
cat /sys/fs/cgroup/memory.current   # 当前用量
cat /sys/fs/cgroup/memory.max       # 上限，max 表示不限
cat /sys/fs/cgroup/memory.events    # oom_kill 计数在这里，比翻日志更直接

# OOM 记录：宿主级在内核日志，容器级表现为退出码 137（128 加信号 9）
(journalctl -k --since '-24h' 2>/dev/null || dmesg -T) \
  | grep -iE 'out of memory|killed process|oom_reaper' | tail -20

# 保护关键进程不被优先杀掉：范围是负一千到一千，负一千表示永不选中
echo -500 > /proc/1234/oom_score_adj
cat /proc/1234/oom_score          # 内核算出的实际得分
sequenceDiagram participant A as 应用进程 participant K as 内核内存子系统 participant R as 回收路径 participant O as OOM killer A->>K: 申请匿名页 触发缺页 K->>R: 水位线告急 唤醒后台回收线程 R-->>K: 回收页缓存 写回脏页 必要时换出到交换区 Note over R: 这一步正是换页速率非零的时刻

容器场景下表现为退出码 137

磁盘：利用率会骗人，等待时间不会

iostat -x 字段含义正常量级怎么判读
r/s w/s每秒读写请求数—配合吞吐算平均请求大小，区分随机小 IO 与顺序大 IO
rMB/s wMB/s吞吐量—对照设备标称带宽，判断是不是打满了带宽
r_await w_await单次 IO 的平均等待加服务时间NVMe 零点几毫秒；SATA 固态小于 1ms；机械盘 5 到 15ms最可靠的饱和指标，明显超出量级就是在排队
aqu-sz平均请求队列长度小于 1持续大于 1 说明请求在等
%util设备上至少有一个请求在处理的时间占比—固态盘和 NVMe 上 100% 不代表饱和，它们能并行处理几十上百个请求；只有机械盘上才近似饱和度
%rrqm %wrqm被内核合并的请求占比—高说明是顺序访问，内核已帮你合并
 
# 容量和 inode 必须分别看：inode 耗尽时空间还剩一大半却写不进文件
df -hT -x tmpfs -x devtmpfs
df -i  -x tmpfs -x devtmpfs

# 原因一：已删除但仍被进程持有句柄的文件。目录里看不到，所以 du 统计不到
lsof -nP +L1 2>/dev/null | awk 'NR == 1 || $NF ~ /deleted/'
# 不能重启进程时，可以把对应的句柄原地截断为零，空间立刻回收
: > /proc/1234/fd/7

# 原因二：inode 耗尽。找出小文件最多的目录
find /data -xdev -type d -printf '%h\n' 2>/dev/null | sort | uniq -c | sort -rn | head

# 原因三：挂载点覆盖。先往目录写了数据，后来把盘挂在同一路径，旧数据被遮住
mkdir -p /mnt/root_view
mount --bind / /mnt/root_view
du -shx /mnt/root_view/data      # 这里能看到被遮住的那份数据
umount /mnt/root_view

# 找当前在打磁盘的进程，比盯着 iostat 猜更直接
pidstat -d 1 3
awk '{ printf "read=%s write=%s\n", $1, $2 }' /proc/1234/io 2>/dev/null | head -2

# 注意 du 默认统计的是「占用的块数」，稀疏文件与压缩文件系统上会和文件大小差很多
du -sh --apparent-size /data/sparse.img; du -sh /data/sparse.img

网络：状态分布比抓包更快给出方向

stateDiagram-v2 [*] --> LISTEN LISTEN --> SYNRECV: 收到握手请求 SYNRECV: SYN-RECV SYNRECV --> ESTAB: 三次握手完成 ESTAB --> FINWAIT1: 本端先关 属于主动关闭 ESTAB --> CLOSEWAIT: 对端先关 收到结束标志 FINWAIT1: FIN-WAIT-1 FINWAIT1 --> FINWAIT2: 收到对端确认 FINWAIT2: FIN-WAIT-2 FINWAIT2 --> TIMEWAIT: 收到对端的结束标志 TIMEWAIT: TIME-WAIT TIMEWAIT --> [*]: 固定等待六十秒 CLOSEWAIT: CLOSE-WAIT CLOSEWAIT --> LASTACK: 应用真正调用了关闭 LASTACK: LAST-ACK LASTACK --> [*]: 收到最后的确认 note right of CLOSEWAIT 堆积在这里说明应用一直没有关闭连接 这是代码缺陷 调内核参数没有任何用 end note note right of TIMEWAIT 只出现在主动关闭的一方 大量存在通常无害 除非本地端口耗尽 end note
状态含义大量出现说明该怎么做
ESTAB连接已建立正常关注是否接近连接池或文件句柄上限
TIME-WAIT主动关闭方的协议等待期，Linux 上固定 60 秒且无法用内核参数调整通常无害只在本地端口耗尽时处理：扩大端口范围、改长连接
CLOSE-WAIT对端已关，本端应用没调关闭应用缺陷，连接池或句柄泄漏查代码。调内核参数完全无效
SYN-RECV收到握手请求但未完成半连接队列不足，或遭到洪泛攻击调大监听队列与半连接队列，开启 syncookies
FIN-WAIT-2本端已关，等对端关对端应用不关连接问题在对端
LAST-ACK等最后一个确认网络丢包看重传计数
LISTEN监听中—确认监听地址是不是只绑了回环导致外部访问不到
 
# 一眼看出方向：各状态计数。CLOSE-WAIT 持续增长就是应用在漏连接
ss -s
ss -tan | awk 'NR > 1 { c[$1]++ } END { for (k in c) print c[k], k }' | sort -rn

# 谁在监听，监听在哪个地址（只绑回环是「本机能连外面连不上」的头号原因）
ss -lntup

# 带内核态指标看单条连接：rtt 抖动、拥塞窗口、重传次数
ss -tni state established '( dport = :443 )' | head -20

# 计数器比抓包快得多：监听队列溢出、半连接丢弃、重传
nstat -az | grep -iE 'ListenDrops|ListenOverflows|TCPSynRetrans|RetransSegs|TCPLostRetransmit'

# 抓包的最小可用命令：不做反解、抓全包长、限量、写文件回本地分析
tcpdump -i any -nn -s0 -c 500 'tcp port 8080 and host 10.0.0.5' -w /tmp/a.pcap
# -nn 不解析主机名与端口名（反解 DNS 会让抓包卡住），-c 限量防止把磁盘写满

# 定位丢包在哪一跳：报告模式、不反解、按 ASN 标注
mtr -rwzbc 100 api.example.com
# 关键判读：中间跳有丢包但最后一跳不丢，几乎总是中间路由对 ICMP 限速，
# 不是真实丢包。只有「从某一跳开始一直丢到最后一跳」才说明链路有问题

进程与句柄

/proc/<pid>/ 下的路径内容用来查什么
limits该进程真实生效的资源上限句柄不够时先看这里，别看 ulimit -n（那是你当前 shell 的）
statusVmRSS、Threads、自愿与非自愿上下文切换次数线程泄漏、内存增长、锁竞争
fd/所有已打开 fd 的符号链接句柄泄漏、找被删除仍占空间的文件
smaps_rollupPss、Private_Dirty 等汇总共享内存场景下估真实占用
wchan 与 stack当前阻塞在哪个内核函数D 状态到底卡在哪
io累计读写字节数哪个进程在打磁盘
cgroup所属 cgroup 路径容器场景下定位限额文件
oom_score 与 oom_score_adjOOM 得分与人工调整值调整被杀优先级
 
# 句柄泄漏：进程实际打开数 与 它真实生效的上限
find /proc/1234/fd -maxdepth 1 -printf . 2>/dev/null | wc -c
grep -E 'Max open files' /proc/1234/limits

# 按类型分组看句柄都用在哪（socket 一直涨就是连接泄漏）
ls -l /proc/1234/fd 2>/dev/null | awk '{ print $NF }' | sed -E 's/\[[0-9]+\]//' \
  | awk -F: '{ print $1 }' | sort | uniq -c | sort -rn | head

# 不可中断睡眠的进程卡在哪个内核函数，这是 load 高而 CPU 空闲的直接证据
ps -eo pid,stat,wchan:32,comm | awk '$2 ~ /^D/'

# strace 的代价必须知道：每个系统调用两次 ptrace 停止，
# 能让目标进程慢 10 到 100 倍，生产上直接挂上去可能把服务压垮。
# 正确姿势：限时、限系统调用、写文件、立刻收手
timeout 10 strace -f -tt -T -e trace=openat,connect,futex -o /tmp/st.log -p 1234
# 更好的选择是低开销的采样与探针工具，通常在百分之一量级的开销
perf top -p 1234                       # 采样热点函数
perf stat -p 1234 -- sleep 5           # 看指令数 缓存缺失 上下文切换

接到告警后五分钟内跑完的分诊脚本

值班时最缺的不是知识而是时间。下面这份脚本按前面的分层顺序把一次现场快照打出来，可以直接粘进工单——注意它故意不加 -e，任何一段命令缺失或失败都不该中断整份快照。

#!/usr/bin/env bash
# triage.sh —— 值班分诊快照。故意只用 -u 不用 -e：缺工具也要把剩下的采完
set -uo pipefail
export LC_ALL=C                      # 统一字节序比较，顺带加速 sort 与 grep

sec()  { printf '\n===== %s =====\n' "$*"; }
have() { command -v "$1" >/dev/null 2>&1; }

sec "0 基本信息"
date -u '+%FT%TZ'; uptime; echo "cores=$(nproc)"

sec "1 运行队列与换页  r 大于核数说明排队  b 非零说明卡在不可中断 IO  si so 非零就是危险信号"
vmstat 1 3

sec "2 CPU 分布  wa 高在等 IO  st 高被宿主抢占  soft 高是收包压力"
if have mpstat; then mpstat -P ALL 1 2; else top -bn1 | head -12; fi

sec "3 内存  只看 available 不看 free"
free -m
awk '/^(MemTotal|MemAvailable|Dirty|Writeback|SwapTotal|SwapFree|Committed_AS):/' /proc/meminfo
[[ -r /sys/fs/cgroup/memory.max ]] && \
  printf 'cgroup current=%s max=%s\n' "$(cat /sys/fs/cgroup/memory.current)" "$(cat /sys/fs/cgroup/memory.max)"

sec "3b 最近的 OOM 记录"
{ journalctl -k --since '-6h' 2>/dev/null || dmesg -T 2>/dev/null; } \
  | grep -iE 'out of memory|killed process|oom_reaper' | tail -10

sec "4 容量与 inode  两个都要看"
df -hT -x tmpfs -x devtmpfs
df -i  -x tmpfs -x devtmpfs

sec "4b IO 延迟  看 await 与队列长度  util 在固态盘上到 100 不代表饱和"
if have iostat; then iostat -x 1 3; else head -5 /proc/diskstats; fi

sec "4c 已删除但仍被进程占用的文件"
have lsof && lsof -nP +L1 2>/dev/null | awk 'NR == 1 || $NF ~ /deleted/' | head -15

sec "5 连接状态分布  CLOSE-WAIT 持续增长就是应用在漏连接"
ss -s
ss -tan | awk 'NR > 1 { c[$1]++ } END { for (k in c) print c[k], k }' | sort -rn

sec "5b 监听端口与进程"
ss -lntup 2>/dev/null | head -25

sec "5c 丢包与队列溢出计数"
have nstat && nstat -az 2>/dev/null | grep -iE 'ListenDrop|ListenOverflow|Retrans|Lost' | head

sec "6 进程 Top10  先按 CPU 再按 RSS"
ps -eo pid,ppid,stat,pcpu,pmem,rss,etimes,comm --sort=-pcpu | head -11
ps -eo pid,ppid,stat,pcpu,pmem,rss,etimes,comm --sort=-rss  | head -11

sec "6b 不可中断睡眠的进程  它们才是 load 高的真凶"
ps -eo pid,stat,wchan:32,comm | awk '$2 ~ /^D/'

sec "7 句柄使用最多的五个进程"
for d in /proc/[0-9]*; do
  n=$(find "$d/fd" -maxdepth 1 -printf . 2>/dev/null | wc -c) || continue
  (( n > 0 )) && printf '%6d  %s  %s\n' "$n" "${d#/proc/}" \
    "$(tr -d '\0' < "$d/cmdline" 2>/dev/null | cut -c1-50)"
done | sort -rn | head -5

sec "完成  把以上输出整段贴进工单"

用 free 的 free 列判断内存Linux 把空闲内存拿去做页缓存，这一列小是健康的看 available，并确认换页速率为 0
把 ps aux 的 RSS 求和当总占用共享页被每个进程重复计入，总和常超物理内存看 smaps_rollup 的 Pss
看到 TIME-WAIT 就调内核参数它是协议要求的正常状态；那个回收选项在 4.12 已被移除，且在地址转换环境下会丢连接只在本地端口耗尽时扩端口范围或改长连接
只看 df -h 不看 df -iinode 耗尽时空间还剩很多却写不进文件两个命令都跑
把 %util 100% 当磁盘饱和固态盘可并行处理大量请求，利用率早就失去饱和度语义看 await 与 aqu-sz
在生产长时间挂 strace每个系统调用两次 ptrace 停止，目标会慢 10 到 100 倍限时限系统调用，优先用采样类工具
容器里用 free / top 判断内存看到的是宿主机的数字读 cgroup 的用量与上限文件
mtr 中间跳丢包就断定链路坏了中间路由对 ICMP 限速是常态只看最后一跳，以及「从某跳起一直丢到最后」的模式
用 ulimit -n 当服务进程的句柄上限那是你当前 shell 的限制，跟服务进程无关读 /proc/<pid>/limits
抓包不加限量和不禁反解反解 DNS 会让抓包卡住，不限量会把磁盘写满-nn 加 -c 加 -w

最容易踩的坑

❌
判读层面的十二个坑
  • load average 把不可中断睡眠的进程也算进去了，所以磁盘卡顿会把它顶到几十而 CPU 一直空闲；而且必须除以核心数才有意义。
  • %wa 高只说明 CPU 在等块设备 IO，不等于磁盘慢——也可能是并发太低导致 CPU 无事可做。
  • %st 在云主机上超过 5% 就要怀疑宿主超卖或突发性能额度耗尽，这时优化自己的代码没用。
  • free 的 free 列小是健康的，该看 available；只有换页速率非零才是真警报。
  • 多进程的 RSS 求和会重复计算共享页，结果可能超过物理内存总量，估真实占用要看 Pss。
  • OOM killer 杀掉的往往不是泄漏的那个进程，而是当时最胖的那个；容器里表现为退出码 137。
  • %util 在固态盘和 NVMe 上到 100% 不代表饱和，可靠指标是 await 与 aqu-sz。
  • df 与 du 不一致的三个原因：已删除但被进程持有的文件、inode 耗尽、挂载点覆盖了旧数据。
  • 只看 df -h 不看 df -i，inode 用满时会得到「还有空间却写不进去」的怪现象。
  • 大量 TIME-WAIT 通常无害且 Linux 上那 60 秒改不了；大量 CLOSE-WAIT 是应用没关连接，调内核参数完全无效。
  • 服务进程的句柄上限在 /proc/<pid>/limits，你在 shell 里敲 ulimit -n 看到的是另一回事。
  • 生产上长时间挂 strace 会让目标慢一到两个数量级，可能直接把服务压垮；抓包忘了 -nn 和 -c 则是卡住加写满磁盘。
