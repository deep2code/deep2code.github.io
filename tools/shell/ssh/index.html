SSH 的工作机制与工程化配置

🏷️ SSH,远程管理

SSH 是三层协议，报错落在哪一层决定了排查方向

SSH-2 不是一个协议，而是三层叠起来的：传输层（RFC 4253）负责算法协商、密钥交换、加密与完整性校验，以及最关键的主机身份验证；认证层（RFC 4252）负责证明「你是你」；连接层（RFC 4254）把这一条加密连接切成多路复用的 channel，shell、exec、端口转发、agent 转发都是 channel。

大部分排查困难来自把三层混着看。no matching host key type found 是传输层的事，去改 authorized_keys 一点用都没有；Permission denied (publickey) 是认证层的事，和加密算法无关；administratively prohibited: open failed 是连接层的事，说明认证早就成功了，是服务端不允许开这个转发 channel。先判层，再动配置，能省掉一大半时间。

主机指纹校验：关掉 StrictHostKeyChecking 到底放弃了什么

密钥交换的产物有两个：会话密钥，以及一个把双方版本串、算法列表、DH 公开值都摘进去的交换哈希。服务端用自己的主机私钥对这个哈希签名，客户端用服务端出示的主机公钥验签——这一步只能证明「对面持有那把主机私钥」，不能证明那把主机私钥是你想连的那台机器的。把公钥和主机名绑起来的，只有 known_hosts 这个首次信任（TOFU）数据库，或者 SSH 证书里的 @cert-authority 条目。

所以 StrictHostKeyChecking no 放弃的不是「一点提示」，而是 SSH 里唯一的身份锚点。剩下的只有「对被动监听保密」，对主动中间人完全裸奔：攻击者接管这条会话，你敲的每条命令、看到的每个文件内容、-L 隧道里的数据库流量、以及 -A 转发进去的签名能力，全归它；如果你还在用密码认证，密码直接送到它手上。

要纠正一个很常见的说法：「我用的是公钥认证，私钥不外传，所以指纹无所谓」。前半句对——私钥确实不离开本地，而且签名内容里绑定了 session id，中间人拿到这个签名没法转发去骗真正的服务器，这是 SSH 设计上的一个正确决策。但指纹校验保护的是会话而不是私钥：中间人无法冒充你登录真机，却可以让你登进一台假机器，看假数据、把生产配置敲进它的 shell。这两件事的危害完全不在一个量级上被抵消。

StrictHostKeyChecking 取值遇到未知主机遇到主机密钥变更是否自动写 known_hosts适用场景
ask（默认）提示指纹让你确认拒绝连接并告警确认后写入交互式日常使用

no / off静默接受仍然放行，只打印告警写入没有安全要求的一次性实验环境

no 这一档还有个容易被忽略的细节：当主机密钥确实变了而检查被关掉时，OpenSSH 会保留连接，但同时禁掉一批依赖「服务端可信」的功能（密码与键盘交互认证、agent 转发、X11 与端口转发），于是你会看到一个「能连上但什么都不好使」的诡异状态。这不是 bug，是它在替你兜底。

正确的工程化做法有三条路：预置（用 ssh-keyscan 抓指纹，和服务器上 ssh-keygen -lf 的输出带外核对后，把 known_hosts 当配置文件下发）、证书化（服务端配 HostCertificate，客户端 known_hosts 里只放一行 @cert-authority *.example.com，此后扩容再多机器都不需要改客户端）、只在真正一次性的环境用 accept-new。三条路都不需要 no。

公钥认证的完整流程：服务端只做验签

authorized_keys 里放的是公钥，服务端从头到尾不需要、也拿不到你的私钥。流程是两阶段的：客户端先发一个不带签名的 publickey 请求，只有算法名和公钥 blob，问「这把钥匙你认不认」；服务端在 authorized_keys 里查到才回 PK_OK；客户端这才用私钥对「session id + 本次请求的各个字段」签名，服务端用同一把公钥验签。

sequenceDiagram participant A as ssh-agent participant C as ssh 客户端 participant S as sshd C->>S: 传输层握手完成 请求 ssh-userauth 服务 S-->>C: 可继续的认证方法列表 C->>A: 列出 agent 中可用的公钥 A-->>C: 返回公钥列表 C->>S: publickey 探测 只发算法名与公钥 blob S->>S: 在 authorized_keys 中查找并检查权限位 S-->>C: PK_OK 表示这把钥匙可以试 C->>A: 请求对 session id 与请求字段签名 A-->>C: 返回签名 私钥不离开 agent C->>S: 带签名的 publickey 请求 S->>S: 用 authorized_keys 里的公钥验签 S-->>C: USERAUTH_SUCCESS Note over C,S: 每次探测失败都消耗一次 MaxAuthTries 服务端默认 6

这个两阶段设计解释了两个高频现象。第一，Too many authentication failures 不是「密码错太多次」，而是 agent 里钥匙太多、在轮到正确那把之前就把 MaxAuthTries 用光了；修法在客户端：IdentitiesOnly yes 配合明确的 IdentityFile，让它只试指定的那一把。第二，签名内容绑定了 session id，所以中间人不能把你的签名转发给真服务器——这是前一节结论的技术依据。

~/.ssh/config 的匹配语义：先出现先生效，不可覆盖

这是最容易被误解的一处。ssh_config 的规则是「每个参数取第一次获得的值」，不是像大多数配置系统那样后面覆盖前面。一个 Host 块能匹配多次，参数却只认最早那一次赋值。直接后果：Host * 这种通用默认必须写在文件最后，写在开头会把后面所有具体 Host 的同名参数全部锁死，而且没有任何报错，表现就是「我明明配了，它就是不生效」。

例外是少数多值指令：IdentityFile、CertificateFile、SendEnv、LocalForward/RemoteForward 这类是累加的，多处出现会按顺序全部生效——这也正是「agent 里钥匙太多」问题的另一个来源。优先级链是：命令行 -o > ~/.ssh/config > /etc/ssh/ssh_config。

不要靠肉眼推演匹配结果，用 ssh -G prod，它会把最终生效的全部参数打印出来，包括你以为改掉了其实没改掉的那些。

ControlMaster 连接复用与 ProxyJump 跳板

一次完整的 SSH 连接要做密钥交换和公钥认证，跨洲链路上 300ms 以上很常见。ControlMaster auto 让第一条连接成为 master 并在本地留一个 unix socket，后续连接直接走这个 socket 复用已有的加密通道，跳过握手与认证——对 git 这种一次操作起好几条 SSH 连接的场景，提速是量级上的。

stateDiagram-v2 state "尚无 control socket" as S0 state "首条连接正在建立 master" as S1 state "master 就绪" as S2 state "有子会话在复用" as S3 state "ControlPersist 保持期" as S4 [*] --> S0 S0 --> S1: 首条连接做完整握手与认证 S1 --> S2 S2 --> S3: 后续连接走 socket 跳过握手 S3 --> S2: 子会话退出 S2 --> S4: 最后一个会话退出 开始计时 S4 --> S3: 计时内又有新连接进来 S4 --> [*]: ControlPersist 到期 master 自行退出 S2 --> [*]: ssh -O exit 或 master 进程被杀 note right of S3 master 断线时所有复用的子会话会同时断开 子会话命令行上新加的转发参数会被静默忽略 end note

复用带来三个必须知道的边界。一是共命运：master 掉了，所有复用它的会话一起死，所以做危险操作时最好用 -S none 或 -o ControlMaster=no 起一条独立连接。二是转发参数被忽略：子会话上写 -L 不会生效，要用 ssh -O forward -L ... 向已有 master 追加。三是socket 路径与权限：unix socket 路径有约 104 字节的上限，用 %r@%h:%p 拼长主机名很容易超；换 %C（哈希）解决。socket 必须落在只有自己可写的目录，能读它的进程就能免认证复用你的连接。

跳板方面，ProxyJump（-J，OpenSSH 7.3 起）取代了 ProxyCommand ssh bastion nc %h %p 这类写法。要点是：客户端会分别对跳板机和目标机各做一次完整的握手、指纹校验和认证，内层会话对跳板机是端到端加密的。这也解释了一个常被误解的运维问题——堡垒机抓不到 ssh -J 内层敲了什么命令，想审计就必须在目标机上做，或者让堡垒机以「终止会话并录制」的方式代理，而不是简单转发 TCP。

三种端口转发的方向、默认绑定与风险边界

-L 和 -R 记反是常事，记住判断依据：看端口监听在哪一端。-L 在本地监听，连接由服务端向目标发起；-R 在服务端监听，连接由客户端向目标发起；-D 在本地监听并提供 SOCKS，目标由每个请求自己决定。

flowchart TB Q1{"流量最终要打到哪一侧"} Q1 -->|"我要访问对面的内网服务"| Q2{"目标是固定的一个还是任意的"} Q2 -->|"固定 host 与 port"| L["用 -L 本地转发"] Q2 -->|"任意目标 整个浏览器都走"| D["用 -D 动态转发 SOCKS"] Q1 -->|"要把本机服务给对面用"| R["用 -R 远程转发"] L --> LG{"要让同网段同事也能连吗"} LG -->|"不要 这是默认"| L1["只绑 127.0.0.1 最安全"] LG -->|"要"| L2["加 -g 或 GatewayPorts 并配防火墙"] R --> RG{"远端要绑 0.0.0.0 吗"} RG -->|"不需要"| R1["默认只绑远端 loopback"] RG -->|"需要"| R2["服务端 GatewayPorts yes 默认是 no"] D --> DG{"这是长期通道还是临时调试"} DG -->|"长期"| D1["改用 VPN 或零信任网关 别用 SSH 兜底"] DG -->|"临时"| D2["用完就关 避免忘在后台"]
方向监听在连接由谁发起默认绑定地址放开到全网卡需要主要风险
-L 本地转发客户端服务端 → 目标127.0.0.1客户端 -g 或 GatewayPorts yes本机其他用户蹭这个口直连生产库
-R 远程转发服务端客户端 → 目标服务端 loopback服务端 GatewayPorts yes（默认 no）把内网服务暴露到公网机器上，忘关就是长期后门
-D 动态转发客户端服务端 → 任意目标127.0.0.1同 -L目标不受限，等于给服务端开了一条任意出网通道
-R 0:...服务端客户端 → 目标服务端动态分配端口—端口号每次不同，容易残留

服务端侧的收紧要点，以及一个必须说清的边界：关掉转发并不能给「有 shell 的用户」增加多少安全性——他完全可以自己上传一个转发程序。AllowTcpForwarding no 的价值在于限制那些只应该做单一用途的账号（跳板账号、Git 账号、备份账号），真正的隔离要靠 no-pty + ForceCommand + 网络策略三件一起上。

agent forwarding 的攻击面与更安全的替代

ForwardAgent yes（-A）会在远端机器上创建一个 unix socket，并把 SSH_AUTH_SOCK 指过去。远端进程通过它请求签名，请求被送回你本地的 agent 完成——私钥确实没有离开本地。问题在于：「使用私钥的能力」被交出去了。在连接存续期间，任何能读到这个 socket 的主体（远端 root、同 uid 的其他进程、被入侵的进程）都能让你的 agent 对任意挑战签名，等于临时借走你的身份，横向登录所有信任这把公钥的机器。私钥不泄漏，但横向移动照样成立。

更要紧的是，绝大多数「我需要 -A」的场景其实不需要它：过跳板机去 git clone、过跳板机连内网机器，用 ProxyJump 就够了，因为认证全在本地完成，跳板机上根本不落 socket。

ssh-add -t 1h（key 生存期）是，时间窗口收窄任意所有场景都该默认加上窗口内仍可被借用
destination constraints（ssh-add -h）是，但只能对指定主机路径签名两端都需 8.9+必须转发 agent 的固定链路版本要求高，链路变更要重加
SSH 证书 + 短 TTL是，但凭据几分钟就过期需自建 CA有规模的团队，统一签发CA 本身成为最高价值目标

连接假死、权限位与主机密钥轮换

「窗口还在，一敲就没反应，过很久才断」的典型原因是中间设备回收了 NAT/会话表项：两端的 TCP 都认为连接还在，中间已经没人转发了。TCPKeepAlive（默认 yes）走的是内核探测，第一次探测往往要等两小时，远大于 NAT 表项常见的 5–30 分钟空闲上限，救不了场。真正有用的是应用层保活 ServerAliveInterval：它走加密通道，会被中间设备记为活动流量，而且在 ServerAliveCountMax 次无响应后客户端会主动断开，让你立刻知道连接没了，而不是无限挂着。

参数位置默认值作用层调错的后果
ServerAliveInterval客户端0（关闭）SSH 应用层不配就会遇到假死；配太小（如 5）在弱网下容易误断
ServerAliveCountMax客户端3SSH 应用层配成 100 等于永不判死，等同没配
TCPKeepAlive两端yesTCP指望它救假死会失望，探测间隔由内核决定
ClientAliveInterval服务端0SSH 应用层兼作空闲超时手段，配小了会踢掉长时间跑任务的会话
ClientAliveCountMax服务端3SSH 应用层设 0 变成到点强制断开，容易被误当成 bug
IPQoS客户端交互 af21，批量 cs1IP 头 DSCP某些老网络设备丢弃带 DSCP 的包，表现为握手后立刻卡死，需显式设 IPQoS throughput

权限位问题的特点是静默：客户端只看到 Permission denied (publickey)，真正的原因只在服务端日志里。StrictModes yes（默认）要求家目录本身不能被组或其他人写，~/.ssh 700，authorized_keys 不能组/其他可写。很多「按教程配了一模一样却登不上」都倒在家目录上——常见于用 usermod 改过 umask、或从备份恢复时带回了 775 的家目录。

known_hosts 的哈希化也值得说清：上游 OpenSSH 的 HashKnownHosts 默认是 no，但 Debian/Ubuntu 在 /etc/ssh/ssh_config 里把它打开了，所以这些系统上的条目是 |1|盐|哈希 形式，用 grep 主机名 永远找不到。对应的正确工具是 ssh-keygen -F host 查询、ssh-keygen -R host 删除。

主机密钥轮换有一个很多人不知道的机制：OpenSSH 8.5 起 UpdateHostKeys 默认为 yes，服务端会在认证后通过扩展把自己所有主机公钥推给客户端，客户端在本次验证成功的前提下静默更新 known_hosts。这让「先给服务器加一把 ed25519 主机密钥，跑一段时间再淘汰旧的 RSA」这种平滑轮换不会引发全员 WARNING，前提是 known_hosts 可写、且本次连接是靠 known_hosts（不是新主机、不是证书）验证通过的。而机器重装导致的指纹变化是另一回事，那必须带外核对新指纹再 ssh-keygen -R，不能用 -o StrictHostKeyChecking=no 糊过去。

# 1) 先看客户端最终生效的配置，直接验证「第一次出现胜出」的结果
ssh -G prod
ssh -G prod | grep -Ei 'identityfile|proxyjump|controlpath|serveralive|forwardagent'

# 2) 分层定位：卡在哪一层
ssh -vv prod 2>&1 | grep -E 'Local version|kex|Host key|Offering|Authentications that can continue'
#   停在 kex 相关行之前  -> 传输层（算法不匹配 / 网络 / MTU）
#   反复 Offering 后 denied -> 认证层（authorized_keys 内容或权限位）
#   登录成功但 open failed  -> 连接层（服务端禁了转发）

# 3) 主机指纹：带外核对，而不是关掉校验
ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub   # 在服务器上算出指纹
ssh-keyscan -t ed25519 prod.example.com            # 在客户端取指纹，人工比对上一行
ssh-keygen -F prod.example.com                     # 哈希化后用它查 known_hosts，grep 查不到
ssh-keygen -R prod.example.com                     # 确认是重装之后再删旧条目

# 4) 权限位导致的静默失败
chmod 700 ~/.ssh && chmod 600 ~/.ssh/id_ed25519 && chmod 600 ~/.ssh/authorized_keys
chmod g-w,o-w ~                                    # StrictModes 还会检查家目录本身
sudo journalctl -u sshd --since '-10min' | grep -E 'Authentication refused|bad ownership'

# 5) 复用连接的运维动作
ssh -O check prod                            # master 还活着吗
ssh -O forward -L 15432:10.0.0.5:5432 prod   # 给已有 master 追加转发（子会话直接写 -L 会被忽略）
ssh -O exit prod                             # 只关这一个 master

最容易踩的坑

❌
这些坑每一条都能复现
  • Host * 写在 ~/.ssh/config 开头：后面所有具体 Host 的同名参数全部被锁死，没有报错。Include 同理，放在 Host * 之后等于没包含。
  • 以为 IdentityFile 写新的会替换旧的：它是累加的，旧的还会被拿去试，撞 MaxAuthTries。
  • 用 StrictHostKeyChecking=no 解决 Host key verification failed：换来一个「能连但端口转发和密码认证都不好使」的怪状态，且中间人防线全部作废。
  • ServerAliveCountMax 配成 100 来「防掉线」：等于永不判死，假死时会挂到天荒地老。
  • 家目录 775：~/.ssh 和 authorized_keys 权限全对也登不上，客户端只报 publickey denied，线索只在服务端日志。
  • 用 grep 在 known_hosts 里找主机名：Debian/Ubuntu 默认哈希化，必须用 ssh-keygen -F。
  • ControlPath 用 %r@%h:%p 撞上 unix socket 约 104 字节路径上限，长域名直接失败；换 %C。
  • 在复用的子会话上写 -L：静默忽略，必须 ssh -O forward。master 一断，所有复用会话同时死。
  • 把 ForwardAgent yes 放在 Host * 下：每台机器的 root 都能在你连着的时候借用你的身份。
  • -R 转发以为默认就能对外提供服务：服务端 GatewayPorts 默认 no，只绑 loopback；反过来一旦开了又忘关，就是长期后门。
  • 直接 systemctl restart sshd 改配置：语法错会把自己关在门外。先 sshd -t，再 reload，并留一个已连接的会话兜底。
  • 老服务器只有 ssh-rsa 主机密钥，OpenSSH 8.8+ 客户端连不上就临时加 -o HostKeyAlgorithms=+ssh-rsa 并写进配置：这是把 SHA-1 签名长期留在信任链里，正确做法是给服务端加 ed25519 主机密钥。
