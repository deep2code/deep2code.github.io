Babylon.js 简介

Babylon.js 是微软的 David Catuhe 2013 年搞出来的开源 3D 引擎，现在微软和社区一起维护。很多人拿它跟 Three.js 比，但我觉得这俩根本不是一个物种：Three.js 给你的是"渲染器加一堆工具函数"，你自己拼装；Babylon.js 直接给你一个能跑起来的引擎壳——物理、粒子、GUI、空间音频、动画、Inspector 调试器全内置，不用你再去外面找七八个库凑一桌。

我怎么选

做工业数字孪生、工厂仿真、教育类 3D，我基本直接上 Babylon.js，省得自己折腾 Havok 物理和 GUI。纯产品展示、官网 3D 模型、创意编码，我还是用 Three.js，包小、API 轻、社区大。不是谁比谁强，是活儿不一样。

核心特性

  • 完整引擎：物理、粒子、GUI、音频、动画、导航网格都自带，不用拼第三方库
  • TypeScript-first：原生 TS，类型定义全，IDE 提示不糊弄
  • WebGPU 优先：8.0 起核心支持 WebGPU + WGSL，9.0 上了 Frame Graph
  • 内置工具：Inspector 调试器、Node Material Editor、Playground 在线编辑器
  • 物理引擎：Havok 的 WASM 版，Xbox 主机同款物理引擎移植，比 Cannon.js 快一个数量级
  • 粒子系统：GPU 粒子，百万级粒子不卡 CPU
  • GUI 系统：2D GUI（按钮/文本/滑块）和 3D GUI（全息按钮）都有
  • glTF 支持：完整支持 glTF 2.0，PBR、动画、变形、扩展全带

场景图架构

Babylon.js 所有可视对象都挂在 Scene 这棵节点树上：相机、灯光、网格都是节点，子节点自动继承父节点的位置旋转缩放。说白了就是一棵变换树，你改根节点，整棵子树跟着动。

一帧渲染背后到底发生了什么

刚用的时候我以为引擎每帧把整个场景重画一遍，后来开了 Inspector 才知道不是那么回事。它内部全靠脏标记（dirty flag）：你不改 position，世界矩阵就不重算；包围盒不变就不做视锥剔除；Draw Call 也只提交可见的。这条链路搞清楚，性能优化才不是瞎调：

  • 变换更新：每帧自顶向下累积世界矩阵，只有真正动过的节点才标 dirty
  • 包围盒重算：世界矩阵 dirty 了才重算 mesh 的世界包围盒
  • 视锥剔除：相机视锥跟包围盒求交，视野外的直接跳过 Draw Call
  • 透明排序：透明物体按距离从远到近排，不然 alpha 混合直接花屏
  • Draw Call 提交：不透明物体先画（从前到后，吃 early-Z），透明物体后画

第一个 3D 场景

下面这段是我每次开新项目都抄一遍的模板：引擎 + 场景 + 轨道相机 + 半球光 + 一个旋转盒子。你可以直接拿去改：

import { Engine, Scene, ArcRotateCamera, Vector3, HemisphericLight, MeshBuilder, StandardMaterial, Color3 } from '@babylonjs/core';

const canvas = document.getElementById('renderCanvas');
const engine = new Engine(canvas, true, { preserveDrawingBuffer: true, stencil: true });

const scene = new Scene(engine);
scene.clearColor = new Color3(0.1, 0.1, 0.18);

// 轨道相机，围绕原点转
const camera = new ArcRotateCamera('camera', -Math.PI / 2, Math.PI / 3, 10, new Vector3(0, 0, 0), scene);
camera.attachControl(canvas, true);
camera.lowerRadiusLimit = 5;
camera.upperRadiusLimit = 20;
camera.wheelPrecision = 50;

// 半球光 + 平行光
const light = new HemisphericLight('light', new Vector3(0, 1, 0), scene);
light.intensity = 0.7;

const box = MeshBuilder.CreateBox('box', { size: 2 }, scene);
box.position.y = 1;
box.material = new StandardMaterial('boxMat', scene);
box.material.diffuseColor = new Color3(0.3, 0.8, 0.8);

engine.runRenderLoop(() => {
    box.rotation.y += 0.01;
    scene.render();
});

window.addEventListener('resize', () => engine.resize());

// PBR 反射环境贴图

// 遍历和查找
console.log(scene.meshes.length);
scene.getNodeByName('box');

灯光（Light）

灯光类型特点阴影
HemisphericLight半球光，模拟环境光无
DirectionalLight平行光，太阳光支持
PointLight点光源，灯泡立方体阴影
SpotLight聚光灯，手电筒支持
这是我踩过最痛的性能坑

每加一盏动态光，片元着色器就多跑一轮光照计算。maxSimultaneousLights 默认 4，超过的灯直接不参与计算——这是引擎故意的保护。我之前在一个项目里给每个设备挂了一盏 PointLight 做高亮，30 盏灯把帧率从 60 干到 15。后来动态光压到 4 盏以内，其余用 emissive 材质模拟高亮，帧率直接回来。

// 软阴影
const shadowGenerator = new ShadowGenerator(2048, dirLight);
shadowGenerator.useBlurExponentialShadowMap = true;
shadowGenerator.blurKernel = 32;

box.receiveShadows = true;
shadowGenerator.addShadowCaster(box);

// 动态光上限
scene.maxSimultaneousLights = 4;

内置几何体

用 MeshBuilder 而不是 Mesh.CreateXxx 创建几何体，前者内部做了复用优化：

const box = MeshBuilder.CreateBox('box', { size: 2 }, scene);

const torus = MeshBuilder.CreateTorus('torus', { diameter: 3, thickness: 0.5 }, scene);
const lathe = MeshBuilder.CreateLathe('lathe', { shape: profile, radius: 1 }, scene);

自定义几何体

程序化生成模型（地形、波形面）就直接操作顶点数据：

const vertexData = new VertexData();
vertexData.positions = [-1, -1, 0,  1, -1, 0,  0, 1, 0];
vertexData.indices = [0, 1, 2];
vertexData.normals = [0, 0, 1, 0, 0, 1, 0, 0, 1];

const mesh = new Mesh('customMesh', scene);

材质系统

材质特点什么时候用
StandardMaterial传统漫反射+高光简单场景、老项目
PBRMaterial金属度+粗糙度物理渲染追求真实感，推荐
ShaderMaterial自定义 GLSL特殊视觉效果
NodeMaterial节点编辑器生成复杂材质，不想写 GLSL

材质选型

追求真实感一律 PBRMaterial，金属度+粗糙度那套，跟 glTF 标准一致。StandardMaterial 只在简单场景用。要自定义效果我先开 Node Material Editor 拖节点，实在拖不出来才手写 GLSL。

PBR 材质那几张贴图——albedo、normal、metallic-roughness、AO、emissive——就是金属度工作流的标准输入：

const pbr = new PBRMaterial('pbr', scene);
pbr.albedoColor = new Color3(1, 0.76, 0.33);
pbr.metallic = 1.0;
pbr.roughness = 0.3;
pbr.albedoTexture = new Texture('textures/albedo.jpg', scene);
pbr.environmentIntensity = 1.0;

// 透明 + 双面
pbr.alpha = 0.5;
pbr.transparencyMode = PBRMaterial.PBRMATERIAL_ALPHABLEND;
pbr.backFaceCulling = false;

物理引擎

Babylon.js 现在主推 Havok，是 C++ 编译成 WASM 的，Xbox 主机同款物理引擎。我之前在项目里对比过三种物理后端，差距很明显：

物理后端实现1000 刚体表现（参考值）建议
Havok (WASM)C++ → WASM稳定 60fps生产首选
Ammo.jsC++ → Emscripten500 刚体还行兼容旧项目
Cannon.js纯 JS200 刚体就开始掉帧轻量 Demo
 
import { HavokPlugin } from '@babylonjs/havok';

const havokInstance = await HavokPhysics();
const havokPlugin = new HavokPlugin(true, havokInstance);
scene.enablePhysics(new Vector3(0, -9.81, 0), havokPlugin);

// 静态地面 mass: 0
const groundAggregate = new PhysicsAggregate(ground, PhysicsShapeType.BOX, { mass: 0 }, scene);

// 动态盒子
const boxAggregate = new PhysicsAggregate(box, PhysicsShapeType.BOX, { mass: 1, restitution: 0.5, friction: 0.5 }, scene);

boxAggregate.body.applyImpulse(new Vector3(5, 0, 0), box.getAbsolutePosition());

// 射线检测
const ray = new Ray(new Vector3(0, 10, 0), new Vector3(0, -1, 0), 100);
const hit = scene.pickWithRay(ray);
if (hit.hit) console.log('击中:', hit.pickedMesh.name);

粒子系统

CPU 粒子和 GPU 粒子的区别，说白了就是粒子更新在哪算：CPU 粒子每帧在 JS 里更新位置，几万就到顶；GPU 粒子把更新丢进着色器，百万级不卡 CPU。

const ps = new ParticleSystem('particles', 10000, scene);
ps.particleTexture = new Texture('textures/flare.png', scene);
ps.emitter = new Vector3(0, 5, 0);
ps.color1 = new Color4(1, 0.5, 0, 1);
ps.color2 = new Color4(1, 0.2, 0, 1);
ps.colorDead = new Color4(0, 0, 0, 0);
ps.minSize = 0.1;
ps.maxSize = 0.5;
ps.emitRate = 1000;
ps.gravity = new Vector3(0, -9.81, 0);
ps.start();

// GPU 粒子，百万级
const gpuPs = new GPUParticleSystem('gpuParticles', { capacity: 1000000 }, scene);

动画系统

三种动画方式按场景选：关键帧动画给美术资源用，Animation Group 管多物体同步，可观测动画做程序化驱动（比如正弦浮动）：

// 关键帧动画
const animation = new Animation('rotation', 'rotation.y', 30, Animation.ANIMATIONTYPE_FLOAT, Animation.ANIMATIONLOOPMODE_CYCLE);
animation.setKeys([{ frame: 0, value: 0 }, { frame: 100, value: Math.PI * 2 }]);
box.animations = [animation];
scene.beginAnimation(box, 0, 100, true);

// 程序化动画（正弦浮动）
scene.onBeforeRenderObservable.add(() => {
    const elapsed = (performance.now() - startTime) / 1000;
    box.position.y = Math.sin(elapsed * 2) * 0.5 + 1;
});

性能优化

减少 Draw Call

Draw Call 是 WebGL/WebGPU 的主要开销。我的经验线：桌面端单屏 200 个 Draw Call 以内流畅，移动端 50 个以内才稳。降 Draw Call 主要靠这几招：

  • 合并网格：Mesh.MergeMeshes() 合并静态物体
  • 实例化：大量相同物体用 InstancedMesh 或 ThinInstance
  • 共享材质：相同材质复用实例，别每个 mesh new 一个
  • Octree 剔除：大场景开八叉树加速视锥剔除
实测数据

同等场景（1000 个盒子），中端笔记本 GPU：合并前大概 1000 个 Draw Call、30fps；InstancedMesh 之后降到 ~10 个 Draw Call、60fps；上 ThinInstance 10 万实例也只要 ~2 个 Draw Call。量级参考，不是精确值。

// 合并静态网格
const merged = Mesh.MergeMeshes([mesh1, mesh2, mesh3], true, true, undefined, false, false);

// InstancedMesh
const sourceMesh = MeshBuilder.CreateBox('source', { size: 1 }, scene);
sourceMesh.isVisible = false;
for (let i = 0; i < 1000; i++) {
    const instance = sourceMesh.createInstance('instance' + i);
    instance.position = new Vector3(Math.random()*50, 0, Math.random()*50);
}

// ThinInstance，10 万级
thinMesh.thinInstanceSetBuffer('matrix', matrixData, 16);

// 八叉树
scene.createOrUpdateSelectionOctree(64, 2);

渲染优化

  • LOD：远距离自动换低多边形模型
  • 像素比限制：Retina 屏别全开，setHardwareScalingLevel(1 / Math.min(devicePixelRatio, 2))
  • 按需渲染：静态场景用 stopRenderLoop()，交互时再渲，省电
// LOD：10 米外用低模，20 米外不显示
mesh.addLODLevel(10, lowPolyMesh);
mesh.addLODLevel(20, null);

// 按需渲染
let needsRender = true;
camera.onViewMatrixChangedObservable.add(() => { needsRender = true; });
engine.runRenderLoop(() => {
    if (needsRender) { scene.render(); needsRender = false; }
});

WebGPU 与 2024-2026 新东西

Babylon.js 8.0 开始核心支持 WebGPU，9.0 上了 Frame Graph。WebGPU 比 WebGL 多了计算着色器，粒子、布料、GPU 寻路这些以前在 CPU 上算的活，现在能全丢 GPU。

一帧的渲染管线

不管底层 WebGL 还是 WebGPU，每一帧都走"更新 → 剔除 → 提交 → 光栅化"这条主链路，性能优化基本都在前两步：

这两年我看到的几个方向：

  • WebGPU + Compute Shader：GPU 粒子、刚体布料、路径寻路全部 GPU 化，CPU 彻底解放
  • Frame Graph（9.0）：渲染管线显式编排，自动管资源生命周期，减少显存碎片
  • TSL：用 TypeScript 写着色器，自动编译成 WGSL/GLSL，不用再手写 GLSL 那套痛苦的东西
  • AI 结合：数字孪生平台开始接 LLM，运营用自然语言查"3 号车间今天能耗多少"，AI 直接在 3D 场景里圈出对应的设备
import { WebGPUEngine } from '@babylonjs/core/Engines/webgpuEngine';

// 检测 WebGPU，不支持就回退 WebGL
if (navigator.gpu) {
    const engine = new WebGPUEngine(canvas, { antialias: true, powerPreference: 'high-performance' });
    await engine.initAsync();
} else {
    const engine = new Engine(canvas, true);
}

数字孪生项目踩坑实录

说个我经手的工厂数字孪生项目。上线后客服反馈"白天挺流畅，下午就卡"，我们查了三天才搞明白，四个坑挨个踩：

  • 没 dispose 旧场景。每天切 20 个楼层场景，旧 mesh 和 texture 从没释放过，显存泄漏累积到下午就 OOM。解法：切场景时遍历 scene.meshes 逐个 dispose()，材质纹理一起释放。
  • 动态光太多。每个设备挂一盏 PointLight 做高亮，30 盏灯把片元着色器打爆。解法前面说过了，emissive 材质模拟高亮。
  • Draco 没配 Worker。大模型加载主线程阻塞 3 秒，操作全卡死。new DracoCompression(4) 起 4 个 worker 并行解码，问题解决。
  • iOS Safari WebGPU 黑屏。iOS 17.4 之前 WebGPU 不稳定，直接 navigator.gpu 检测失败回退 WebGL。

FAQ

Q1：WebGPU 初始化失败 / 黑屏？
WebGPU 必须 await engine.initAsync()，而且浏览器得支持。先判 navigator.gpu，不支持就回退普通 Engine。

Q2：物理不生效，物体直接穿地？
八成是忘了 scene.enablePhysics，或者没挂 PhysicsAggregate。地面 mass: 0，掉的东西给 mass > 0。

Q3：到底用 Babylon 还是 Three.js？
要物理、粒子、GUI、Inspector 这些开箱即用，做数字孪生仿真，选 Babylon；只要轻量产品展示、包体积敏感，选 Three.js。

Q4：实例化上千物体还是慢？
上 ThinInstance，一次性传矩阵 buffer，比 InstancedMesh 还省，再配 Octree 剔除。

Q5：手机上跑一会儿就发烫掉帧？
像素比锁 1.5 以内、阴影贴图降到 1024、关抗锯齿、粒子用 GPU 版、动态光压到 2 盏。

总结

Babylon.js 的定位很清楚：一个包把游戏引擎该有的都给你，代价是包体积大、概念多。做数字孪生和仿真用它，做轻量产品展示用 Three.js，按活儿选就行。生产环境就记三条：及时 dispose、动态光克制、模型纹理压缩。剩下的边做边调。
