Mermaid 的语法边界与工程化用法

🏷️ Mermaid

Mermaid 的定位常被说成「快速画图」，这其实低估了它。用拖拽工具也能很快画出一张图，Mermaid 真正不可替代的地方是图变成了版本库里的文本：能 diff、能在评审里被逐行讨论、能和代码在同一个提交里一起演进，也能在 CI 里被自动校验。代价是你必须接受它的两条硬约束——语法对特殊字符非常敏感，布局完全由算法决定。这篇讲清这两条约束的边界在哪里、越界时的表现是什么，以及把 Mermaid 纳入工程流程的具体做法。

文本即图：可 diff 才是真正的价值

二进制图片和在线白板的问题不是画得慢，而是无法参与代码的生命周期。架构变了，图不会跟着变，因为改图要打开另一个工具、另一个账号、另一份文件；评审时你也没法对一张 PNG 说「这条箭头方向反了」并让改动可追溯。图定义变成仓库里的纯文本之后，这几件事同时成立：改动出现在 diff 里，评审可以定位到具体某一行节点或连线，历史版本可以回溯到任意提交，CI 可以在合入前发现语法错误。

顺带说一个常被忽略的收益：文本图对 AI 辅助友好。把一段业务流程描述丢给模型让它产出 mermaid 初稿、再自己调整，比让它产出图片实用得多，因为输出是可校验、可修改的结构化文本。

图类型的表达力边界与选择

选错图类型的代价比语法错误大得多，因为它不会报错，只会让读者理解成本翻倍。判断依据只有一条：你要表达的信息本质是什么——多方之间的时序往返、同一实体的状态变迁、静态的分层归属，还是判断分支。把这四类信息都塞进 flowchart 是最常见的浪费，尤其是用流程图画「三个服务互相调用」，读者需要在脑子里自己重建时间轴。

另一个要注意的是成熟度分层。flowchart、sequenceDiagram、stateDiagram-v2、classDiagram、erDiagram 是稳定的核心；一部分较新的图类型仍带实验标记，语法可能在小版本之间变化，而且目标平台内置的版本往往不支持。给团队文档定规范时，把可用的图类型限制在核心集合里，比事后追查「为什么这张图在某个平台不显示」便宜得多。

图类型适合表达不适合常见误用
flowchart 加 subgraph分层架构、模块归属、分类树带时间维度的交互用它画服务间调用，读者要自己重建时间轴
flowchart 加菱形节点判断分支、选型决策树、排查路径并发与并行流程画成一条直线的三段流程，等于用图重复一句话

节点标签的引号规则：最高频的渲染失败原因

这一条单独拿出来讲，因为它是实际工作中翻车次数最多的地方，而且失败形态五花八门：整张图报语法错误、节点形状被识别成别的形状、标签被截断、或者报错信息指向一个看起来完全无关的位置。

规则本身很简单：节点标签里只要出现圆括号、方括号、花括号、斜杠、逗号、冒号、分号、井号、尖括号、引号，或者以非字母数字开头，就必须用双引号把整个标签包起来。原因是这些字符在方括号之外都承担语法角色，解析器不知道你是在写标签还是在写形状声明。写 A[延迟 O(1)] 时，那对圆括号会被当成形状语法的一部分。

两个补充规则：标签内部要出现双引号本身时用实体码，反斜杠转义在这里不起作用；标签内换行只能用换行标签，任何其他 HTML 标签（加粗、斜体、span）都不该出现——它们要么被净化掉，要么让 foreignObject 里的排版彻底乱掉。最省心的工程约定是：所有标签一律加引号，不判断该不该加。

标签里出现必须加引号不加引号的实际表现
圆括号必须被当成圆角或体育场形状声明，形状错乱或报错
方括号必须标签提前结束，剩余部分成为无法解析的记号
花括号必须被当成菱形节点声明，整行解析中断
斜杠必须被当成平行四边形或梯形形状，路径类标签基本必踩
逗号、分号必须分号被当成语句分隔符，标签被切断
冒号必须在部分图类型里是属性分隔符，语义被抢走
井号必须被当成实体码起始，后续字符被吞掉
尖括号必须，且只允许换行标签被当成 HTML 解析，净化后标签内容消失
双引号本身用实体码表示提前闭合引号，后面全部错位
以数字或符号开头必须标识符规则不允许，直接报错
纯中文与空格建议加多数情况可用，但混入任何标点就会失败，不如统一加

id 与 label、subgraph 与方向：三个结构层面的坑

id 不是 label。A["网关"] 里 A 是标识符，网关 是显示文本。标识符必须唯一、不能含空格、不能是保留字；一旦在同一张图里重复使用同一个 id 配不同标签，后出现的会静默覆盖前面的，图上少一个节点却没有任何报错——这在大图里极难发现。工程上的解法是用有语义的短 id（GW、DB、CACHE），而不是 A、B、C。

subgraph 的 id 与标题是两件事。subgraph GRP["数据层"] 中 GRP 可以被连线引用，而把连线指向子图标识和指向子图内某个节点，排版结果完全不同：前者会让布局引擎把整个分组当作一个大节点来处理，边的落点与层级都会变。

子图内的 direction 会在特定条件下被忽略。当子图内的节点与子图外的节点有连线时，父级布局接管方向，你写的方向声明不生效，而且不报错。这不是 bug，是分层布局算法的必然结果。想稳定控制方向只有两条路：让子图成为相对封闭的单元，跨子图的连线只发生在子图边界之间；或者拆成多张图。

坑触发写法表现正确做法
保留字作 id用 end 作节点标识整张 flowchart 报错，位置提示误导换成有语义的标识，如 FIN
线端标记误判连线后紧跟以 o 或 x 开头的 id被解析成圆头或叉头连线，目标节点名被吃掉一位连线两侧留空格，或 id 首字母大写
id 重复同一 id 配两个不同标签后者静默覆盖前者，图上少一个节点用有语义的短 id，避免单字母序号
连线指向子图箭头终点写子图标识整个分组被当成一个大节点，层级与落点都变明确区分「指向分组」和「指向组内节点」两种意图
子图方向失效子图内声明方向，同时存在跨子图边界的连线方向被父级接管，无任何提示让子图封闭，或拆图
泛型写法类图里用尖括号写泛型被当成 HTML，类型签名丢失用波浪号包裹类型参数
状态图注释块注释块内出现以冒号开头的行解析中断注释里避免冒号开头，或改用普通状态描述

布局不可控：天花板与换工具的信号

Mermaid 不提供坐标，节点位置由布局算法计算。你能影响它的手段只有三个：节点声明顺序、整图方向、子图划分。默认使用分层布局引擎，v11 起可以注册 ELK 引擎，在大图的分层与连线交叉上明显更好，但仍然不是手动摆放。

判断「该换工具」的信号很明确：你开始为了排版反复调整节点声明顺序。这说明信息密度已经超出算法能自动排好的范围，继续调是负和游戏。此时的选择是把图拆小（一张图只说明一件事），或者换成支持手动布局的工具——但那也意味着放弃 diff 与 review 的能力，这个取舍要想清楚。需要精细控制布局的场景，站内另有专门的画图工具选型讨论（详见 画图工具选型）。

渲染方式：预渲染、运行时加载、平台内置

三种方式解决的问题不同，不是替代关系。构建期预渲染把图定义编译成 SVG 或 PNG，页面零运行时开销，邮件、PDF、不执行 JavaScript 的环境只能走这条路；代价是构建链路里要跑无头浏览器，CI 镜像变重、冷启动变慢。运行时加载把渲染器送到浏览器里执行，好处是图定义与文档同源、改文档不用重新出图；代价是渲染器体积不小，必须懒加载。平台内置最省事，但你要按平台的版本写语法。

本站走的是第二条路，几个决定值得说明：渲染器自托管在 vendor 目录而不是用公共 CDN，原因是版本完全可控、不受外部可用性影响；文件体积在 3 MB 量级（未压缩），所以必须懒加载——用交叉观察器提前若干像素预取，同时设一个兜底超时，避免观察器在某些场景不触发导致图永远不渲染；渲染时关掉自动启动，改为显式逐个渲染，并把原始图定义保存在容器属性上，这样切换深色模式时可以从源码重新渲染而不是去解析已经变成 SVG 的内容；渲染失败时把容器内容替换成可见的错误文本，而不是让它静默空白。

securityLevel 与版本差异

securityLevel 不是无关紧要的开关，它决定了「图定义」这段文本被当成数据还是当成代码。loose 允许标签里写任意 HTML，并允许 click 语句调用页面上的 JavaScript 函数——如果图定义来自用户提交、评论区、外部仓库或任何你不完全掌控的来源，这就是一条实打实的跨站脚本路径。strict 会净化标签并禁用回调；sandbox 把图放进 iframe 隔离，代价是无法继承页面样式、尺寸要自己处理。本站用的是 strict，这也是文中反复强调「标签里只能出现换行标签」的原因。

版本差异是另一个长期成本。代码托管平台内置的版本通常滞后于最新发布，你本地用新语法写的图在平台上可能直接空白。工程上的对策有三条：把校验环节用的版本与目标渲染端对齐；在团队规范里限定可用的语法子集；对外文档只使用核心图类型。

securityLevel标签里的 HTMLclick 回调适用场景风险
strict被净化，仅保留安全内容禁用 JS 回调渲染任何不完全可信的图定义富文本标签写了也不生效，容易以为是语法错
antiscript允许，但移除脚本受限需要一点富文本且来源基本可信净化边界依赖实现，不宜用于公开输入
loose原样允许可调用页面上的函数只渲染自己仓库里的图定义渲染外部内容时等于开放 XSS 入口
sandbox在 iframe 内被 iframe 隔离渲染完全不可信的输入不继承页面样式，高度与响应式要自己算

CI 校验与大图可读性治理

图定义是文本，就该像代码一样在合入前被校验。最低成本的做法是用 parse 接口只做语法检查：不布局、不渲染，速度快。两个前提必须知道——Mermaid v10 起只发布 ESM 包，脚本必须是模块格式，用旧的同步引入方式会直接失败；parse 依赖 DOM，Node 环境下要用 jsdom 垫一层。打开抑制异常的选项，让它返回布尔值而不是抛错，就能一次跑完所有文件再统一汇报。

需要连布局一起验证（比如确认图真的画得出来、没超出配置上限）时才用官方命令行工具，它底层跑无头浏览器，成本高得多，适合放在夜间任务而不是每次提交。

大图的问题分两类。一类是撞上了配置上限：图定义文本长度与边数都有默认上限（文本长度默认在五万字符量级，边数默认在数百量级），超过会直接给出「超出上限」的错误而不是渲染失败——这类错误信息很明确，调高配置或拆图都能解决。另一类是可读性：三十个节点的图在技术上能渲染，但没人看得懂。治理手段按优先级是：一张图只说明一件事，把细节下沉到另一张图；用子图把相关节点框起来并给分组命名；把长标签拆成两行；连线交叉成网时说明分层划分错了，重新组织层级而不是继续加连线。

症状机制原因处理
报「超出最大文本长度」图定义字符数超过配置上限，默认在五万量级拆图；确有必要时调高该项配置
报「超出最大边数」连线数量超过配置上限，默认在数百量级拆图；这个数量级的图本身已不可读
图被横向拉得极宽分层布局把同层节点排在一行换方向；用子图分层；必要时换 ELK 引擎
连线交叉成网层级划分与实际依赖不匹配重新组织分层，而不是继续加连线
节点框被长标签撑爆标签不自动换行用换行标签手动断行，或把说明移到图外正文
渲染明显耗时节点与连线规模导致布局计算变重拆图；首屏之外的图一律懒加载

// scripts/check-mermaid.mjs —— 在 CI 里只做语法校验，成本最低
// 两个前提：1) mermaid v10 起只发 ESM，文件必须是 .mjs 或 package 里声明 module
//          2) parse 依赖 DOM，Node 里要用 jsdom 垫一层
import { readFileSync } from 'node:fs';
import { glob } from 'node:fs/promises';   // Node 22+；旧版本换用 fast-glob
import { JSDOM } from 'jsdom';

const dom = new JSDOM('<!DOCTYPE html><body></body>');
globalThis.window = dom.window;
globalThis.document = dom.window.document;

const mermaid = (await import('mermaid')).default;
// 关键：校验时的 securityLevel 与线上渲染保持一致，否则只在 strict 下暴露的问题查不出来
mermaid.initialize({ startOnLoad: false, securityLevel: 'strict' });

const FENCE = /```mermaid\r?\n([\s\S]*?)```/g;   // 从 Markdown 代码围栏里抽出图定义
let failed = 0;

for await (const file of glob('docs/**/*.md')) {
  const text = readFileSync(file, 'utf8');
  let m, idx = 0;
  while ((m = FENCE.exec(text)) !== null) {
    idx += 1;
    // suppressErrors 让它返回 false 而不是抛异常，便于一次跑完所有文件
    const ok = await mermaid.parse(m[1], { suppressErrors: true });
    if (ok === false) {
      failed += 1;
      console.error(file + ' 第 ' + idx + ' 张图语法错误');
    }
  }
}

process.exit(failed === 0 ? 0 : 1);

find docs -name '*.mmd' -print0 | xargs -0 -I{} npx -y @mermaid-js/mermaid-cli -i {} -o /tmp/out.svg

#   2) 设一个兜底定时器，防止观察器不触发时图永远不渲染

❌
最容易踩的坑
  • 标签含特殊字符不加引号：圆括号、斜杠、逗号、冒号、井号、尖括号都会被当成语法记号。统一给所有标签加双引号，别逐个判断。
  • 在标签里写除换行以外的 HTML：加粗、斜体、span 在 strict 下被净化掉，表现为文字消失或排版错乱，而且不报错。
  • 用 end 当节点 id：它是保留字，会让整张 flowchart 报错，而错误位置提示往往指向别处。
  • 连线后紧跟以 o 或 x 开头的 id：被解析成圆头或叉头连线，目标节点名被吃掉一个字符。加空格或首字母大写。
  • 同一个 id 配两个标签：后者静默覆盖前者，图上少一个节点且完全无提示，大图里极难发现。
  • 以为子图里的 direction 一定生效：存在跨子图边界的连线时父级布局接管方向，声明被忽略且不报错。
  • 把箭头指向子图标识：整个分组被当成一个大节点参与布局，排版结果与指向组内节点完全不同。
  • 类图里用尖括号写泛型：会被当成 HTML 处理，类型签名直接丢失，要用波浪号包裹类型参数。
  • 状态图注释块里写以冒号开头的行：解析中断，错误信息不指向注释本身。
  • 为了排版反复调节点顺序：这是「该拆图或换工具」的信号，不是优化方向，继续调是负和游戏。
  • 渲染外部内容时用 loose：允许任意 HTML 与 JS 回调，等于把跨站脚本入口开给图定义的提供方。
  • 本地用新语法、线上靠平台渲染：平台内置版本滞后，实验阶段的图类型与扩展语法会直接空白。
  • CI 里用同步方式引入 mermaid：v10 起只发 ESM 包，脚本必须是模块格式，并且 parse 需要 DOM 垫层。
  • 运行时加载不设兜底超时：一旦交叉观察器在某些场景不触发，页面上的图会永远停在空白状态。
