文本即图工具的选型矩阵

🏷️ 代码生图

先划清分界：位置信息属不属于内容

「文本即图还是拖拽排版」这个问题，答案不取决于哪个更现代，而取决于一件事：这张图的含义有没有一部分存在于人工摆放的位置里。机架图、机房平面、网络布线图，位置本身就是信息，交给自动布局等于把内容扔掉；而系统间的调用关系、模块包含关系，含义完全落在拓扑上，位置只是呈现，自动布局才是对的。另外两条次级判据是维护者和寿命：有非工程角色参与编辑，或者这张图只为一次汇报而存在，就不值得为它引入一套 DSL 与渲染依赖。

六个工具的横向矩阵

把常被放在一起比的六个工具按维度拆开。注意这里不给分数——分数是假的精确，真正决定选型的是每一格里那句限定条件。

工具表达力布局可控性渲染依赖
Mermaid常见图种齐全，但行为语义弱：时序图没有临界区一类的完整片段语义弱。自动布局为主，可切换布局引擎，几乎没有约束手段浏览器里的 JS，或官方命令行（背后带浏览器内核）
PlantUML最强。UML 行为语义完整，另有 C4 与一批非 UML 图种弱到中。结构图交给 dot，只有位置提示类手段JVM；多数结构图还需要 Graphviz 或其 Java 端口
Graphviz低层。只有点、边、簇，没有「图种」概念最强。多引擎加约束属性，还能把算好的坐标复用原生二进制，无运行时
D2中。以结构图为主，容器、表格类形状、分步展示中。可选布局引擎，最强的那个是闭源且需授权单个二进制，安装简单
Structurizr模型层最强：一个模型派生多张视图，而不是一张张画取决于导出目标，自身可保存人工调整过的视图布局JVM 命令行，或本地容器镜像
draw.io任意，但没有语义约束：工具不知道你画的是什么最强，因为完全人工桌面端或自托管镜像；命令行导出需要图形环境
工具平台内置支持离线与私有化学习曲线退出成本
Mermaid最好，主流代码托管平台的 Markdown 直接渲染纯前端，自托管一份脚本即可完全离线最低中。语法专有，但结构简单，重画代价可控
PlantUML需服务端或插件，部分平台可接渲染服务本地 jar 即可，完全可私有化中，关键字多高。行为语义片段在别处没有对应物
Graphviz无完全离线中高，要理解算法约束最低。DOT 是事实上的中转格式，多数工具能读写
D2基本没有可，但最优布局引擎要授权低中高。特有语法与分步展示无处可去
Structurizr无可，容器镜像本地跑中高，要先接受模型与视图分离低到中。能导出成多种其他 DSL
draw.io无，但双用途 SVG 文件可直接嵌入文档可自托管最低中。含义依赖坐标，无法自动迁到任何 DSL
💡
Structurizr 的本质差别不是画法

其他工具都是「一张图一份源码」，Structurizr 是一个模型多个视图：元素和关系只声明一次，上下文图、容器图、组件图都从同一份模型派生。这解决了最顽固的一类不一致——同一个服务在三张图里三个名字。代价是你必须先接受 C4 的层级纪律（详见站内《PlantUML 的建模表达力与协作流程》），并且它更像建模工具而不是画图工具。

渲染方式决定了工程后果

比语法更该先定的是渲染方式。它决定构建依赖、离线可读性、爬虫可见性，以及出问题时怎么回滚。

✅
本站的取法

本站走的是运行时加载：Mermaid 脚本自托管在站内目录，进入视口再懒加载，安全级别设为最严格的一档，因此图里不能出现任何 HTML 标签与点击脚本。代价是订阅与纯文本场景看不到图，所以关键结论一律同时写进正文。语法边界与工程细节见站内《Mermaid 的语法边界与工程化用法》。

CI 里的语法校验

图的语法错误必须在合并前被拦住，否则文档站上线后才发现某页空了一块。原则是不要自己解析语法，渲染到临时目录只看退出码。

工具校验方式额外依赖注意
PlantUML只校验不出图的开关，配合「先全量解析再生成」JVM结构图仍需布局后端；先跑一次依赖自检
Graphviz渲染到空设备，语法错误非零退出原生二进制警告不改变退出码，要单独抓警告文本
Mermaid官方命令行渲染到临时文件浏览器内核容器里要配免沙箱参数；下载体积大，务必缓存
D2编译到临时文件，另配格式化命令统一风格单二进制格式化结果进库，避免风格 diff
Structurizr导出成任一目标格式即完成解析校验JVM 或容器模型错误（引用不存在的元素）比语法错误更常见
draw.io无语法可校验图形环境只能校验文件能否被导出，价值有限
 
#!/usr/bin/env bash
# 图源语法校验：只看退出码，不自己解析语法
# 所有工具版本都钉死，否则「通过与否」会随基础镜像漂移
set -uo pipefail
TMP=$(mktemp -d); trap 'rm -rf "$TMP"' EXIT
fail=0

while IFS= read -r -d '' f; do
  case "$f" in
    *.puml)
      # -checkonly 不出图；-failfast2 先全量解析，错误在生成前就暴露
      java -jar tools/plantuml.jar -checkonly -failfast2 "$f" || fail=1 ;;
    *.dot)
      # 渲染到空设备即可；注意警告不影响退出码，要单独抓
      dot -Tsvg "$f" -o /dev/null || fail=1
      dot -Tsvg "$f" -o /dev/null 2>&1 | grep -q . && echo "warn: $f" ;;
    *.mmd)
      # mermaid-cli 背后是浏览器内核，容器里必须给免沙箱配置
      mmdc -i "$f" -o "$TMP/out.svg" -p ci/puppeteer.json 1>/dev/null || fail=1 ;;
    *.d2)
      d2 --layout=elk "$f" "$TMP/out.svg" 1>/dev/null || fail=1
      # 格式化结果必须已经入库，否则会有纯风格 diff
      d2 fmt "$f" && git diff --quiet -- "$f" || { echo "fmt: $f"; fail=1; } ;;
  esac
done < <(find docs -type f \( -name '*.puml' -o -name '*.dot' \
          -o -name '*.mmd' -o -name '*.d2' \) -print0)

exit "$fail"

图片产物管理：入库、缓存与 diff 噪音

产物要不要进版本库，是个团队约定问题，但无论选哪种，都必须先解决可重现：同一份源码、同一版工具，两次渲染的字节应当完全一致。做不到这点时入库，每次构建都会产生一堆假改动。

sequenceDiagram participant Dev as 开发者 participant CI as CI participant Cache as 产物缓存 participant R as 渲染器 participant Repo as 版本库 Dev->>CI: 提交图源变更 CI->>CI: 先做语法校验，失败即止 CI->>Cache: 用「工具版本 + 源哈希 + 字体版本」查缓存 Cache-->>CI: 命中则直接取产物 CI->>R: 未命中才渲染 R-->>CI: SVG 产物 CI->>CI: 归一化：去随机 id、版本注释与内嵌元数据 CI->>CI: 重渲一次并比对字节，验证可重现 CI->>Repo: 入库或仅作为构建产物上传 Note over CI,Repo: 不先归一化就入库
每次构建都会制造假改动
策略适用diff 噪音来源缓解手段
只入源码，产物构建时生成有稳定文档流水线无但任何阅读路径都要先构建一次
源码与 SVG 都入库要在合并请求里直接预览、要离线可读随机标识、版本注释、内嵌源码元数据渲染后归一化并验证两次渲染一致
只入库位图消费方无法处理矢量整文件二进制，每次必冲突标成生成文件让平台折叠差异，且只在发布时更新
产物放构建缓存与制品库图多、渲染慢无缓存键必须含工具版本与字体版本，否则会取到旧图
产物入库但不参与评审折中方案，实践中最常见体积增长用版本库属性标记为生成文件，评审只看源码 diff
 
# .gitattributes：让平台知道这些是生成产物，默认折叠其差异
docs/**/*.svg linguist-generated=true
docs/**/*.png binary
# 源码要正常参与 diff，显式声明为文本，避免被误判
docs/**/*.puml text eol=lf
docs/**/*.mmd  text eol=lf
docs/**/*.dot  text eol=lf
docs/**/*.d2   text eol=lf

    path: build/diagrams
    key: diag-${{ runner.os }}-plantuml1.2024.7-graphviz9.0-notocjk2.004-${{ hashFiles('docs/**/*.puml', 'docs/**/*.dot') }}

      diag-${{ runner.os }}-plantuml1.2024.7-graphviz9.0-notocjk2.004-

  run: |
    ./ci/render-diagrams.sh --out build/diagrams2
    diff -r build/diagrams build/diagrams2

混用多个工具的代价

代价是乘法：每多一个工具，就多一套渲染依赖、一套样式体系、一套 CI 校验、一套读者要学的语法，以及一条排查路径。可接受的混用只有一种形态——按产物类型分层，边界清晰且不重叠。

组合可接受吗前提
文档内嵌一种 + 程序生成的关系图一种可以两者职责不重叠，谁管什么写进规范
建模工具一种 + 导出成通用 DSL 渲染可以模型是唯一真相，导出物不手改
同一类结构图两种工具并存不行必然风格不一致、重复维护、互相抄错
每个团队各选一种不行跨团队评审时没人看得懂对方的图
多种 DSL 但渲染集中到一个服务可以依赖收敛到一处，代价是多一个要运维的服务

迁移路径与不可迁移的部分

选型时就该把退出成本当一个维度。迁移的现实是：拓扑能带走，其他基本都得重做。把迁移按「重画」估算工作量，不要指望转换器。

迁移方向能带走一定丢失实际做法
Mermaid 到 PlantUML拓扑与图种大致对应样式；反向还会丢行为语义片段按图重写，顺手补上原本缺失的错误分支
任意 DSL 到 Graphviz拓扑、簇图种概念，时序与状态要自己表达只对结构类图做；DOT 适合当中转格式
Structurizr 到其他可直接导出多种 DSL模型与视图分离这件事本身导出物当只读产物，别手改
draw.io 到任意 DSL几乎只有节点文字人工坐标，也就是图的一半含义当成重画；先判断这张图是否还需要存在
D2 到其他拓扑与容器分步展示、特有形状动画类内容改成多张静态图

本文只谈选型与集成。布局算法与大图治理见站内《Graphviz 的布局算法与大图治理》；UML 语义与评审流程见站内《PlantUML 的建模表达力与协作流程》；该画什么、不该画什么见站内《技术文档里的图：该画什么，不该画什么》；Mermaid 自身的语法边界见站内《Mermaid 的语法边界与工程化用法》。数值型图表是另一条线，不在本文的比较范围。

❌
最容易踩的坑

1. 先挑语法再想渲染方式——渲染方式决定构建依赖、离线可读性和回滚能力，它比语法重要得多。

2. 用文本方案画位置承载语义的图（机架、平面布局）——你会一直在和自动布局较劲，且永远赢不了。

3. 依赖平台内置渲染却用了新语法——本地能渲染、线上是一段报错文本，而构建全绿。

4. 运行时加载还把关键结论只放在图里——订阅、爬虫、纯文本阅读场景全部拿不到，等于没写。

5. 产物不归一化就入库——随机标识、版本注释、内嵌元数据会让每次构建都产生假改动，最后没人看图的 diff。

6. 缓存键不含工具与字体版本——升级后取到旧图，构建「成功」而图是错的。

7. 只在开发机装字体——构建机缺中文字体时，预渲染产物里中文全变方框，流水线不会报错。

8. CI 里只渲染不校验，或用自己写的正则校验语法——渲染器的退出码才是唯一可靠信号。

9. 忘了 Mermaid 命令行背后是浏览器内核——容器里不配免沙箱参数会莫名失败，且首次下载体积很大，必须缓存。

10. 选了需要授权的布局引擎才发现不能商用——开源协议与商业条款在选型阶段就要看，不是上线前看。

11. 同一类图允许两种工具并存——风格不一致、重复维护、互相抄错，是最贵的那种「灵活」。

12. 把迁移当成格式转换来排期——样式、布局提示、行为语义、人工坐标都带不走，实际是按张重画。
