静态站点生成的构建模型与内容架构

🏷️ Hugo

SSG 的能力边界：编译期能算的和不能算的

静态站点生成的全部前提是输出只依赖构建时刻的输入。凡是需要「请求时刻才知道的信息」的功能，SSG 天生做不了，只能外挂。先把边界摊开，再谈内容架构，否则后面所有决策都是拍脑袋。

能力能否纯静态外挂方案真实代价失效模式
全文搜索可以，但索引是构建产物构建后扫描产物生成分片索引，或托管搜索服务自建索引随内容线性增长，首次搜索要下载索引；托管方案有配额与隐私问题索引与页面版本不同步时，搜到的是已删除的页面
评论不行第三方服务或基于代码托管平台 issue 的方案访客需要第三方账号，评论数据不在你手里服务下线或接口变更，历史评论一次性全丢
表单提交不行托管表单端点或一个云函数多出一条需要鉴权与限流的后端路径缺少验证码与频率限制时立刻变成垃圾内容入口
按用户个性化不行边缘函数改写响应，或前端拿到数据后渲染一旦引入就失去了纯静态的缓存优势缓存键没带上区分维度，A 用户看到 B 用户的内容
访问控制不行放在 CDN 或反向代理层做鉴权鉴权逻辑与内容分离，容易漏配路径只保护了列表页，详情页 URL 可猜测直连
内容定时上线算半个构建时按日期过滤，靠定时任务重新构建上线时刻取决于构建频率，不是内容里写的时间没有定时构建，标了未来日期的文章永不出现

内容组织与 URL 是一件事，不是两件事

Hugo 的内容模型只有几个概念，但它们和最终 URL 死死绑在一起：目录结构决定 section，section 决定默认路径与列表页，文件名决定叶子路径。这意味着整理目录等于改 URL，而 URL 是你对搜索引擎和所有外部链接的长期承诺。

文件形态页面类型默认 URL同目录资源典型用途与陷阱
section 目录下的普通 md 文件叶子页section 加文件名不属于该页，需用全站静态目录最省事；但图片只能放全站资源目录，搬文章时图片对不上
目录加 index.md叶子页捆绑目录路径同目录文件成为该页 Resources，可做图片处理推荐形态；注意它是叶子，目录里再放子目录不会生成子页面
目录加 _index.md分支页目录路径同样可挂资源列表页与 cascade 的落点；漏了这个文件，列表页就用不上自定义元数据
taxonomy 配置产生的页面聚合页与词条页分类名加词条 slug无词条由内容里的字段值动态产生，拼写不一致会造出两个词条
标记为不渲染的捆绑只读数据不产出 URL资源可被其他页引用放可复用片段与数据；忘了关列表会在列表页里冒出空白项

URL 的最终形态还要叠加三层：按 section 配置的 permalink 模板、单页 front matter 里的 slug 或 url 字段、以及是否启用「丑 URL」（即输出成带扩展名的文件而不是目录加索引页）。三者优先级搞混是线上 404 的常见来源。另外一条经验：改 URL 时一定顺手留重定向，Hugo 的别名机制会为旧路径生成跳转页，成本极低，但它是客户端跳转，SEO 权重传递不如服务端 301，重要页面还是要在 CDN 层配。

模板查找顺序：困惑的根源是维度乘积

「为什么我的模板不生效」几乎是 Hugo 最高频的问题，根因不是规则复杂，而是查找键是多个维度的组合，而报错只会说「没找到模板」。参与匹配的维度至少有五个：

维度取值来源影响最常见的错法
页面类型由文件形态与位置决定，不可手改决定候选模板的整个族把分支页当叶子页写模板，取不到子页面列表
typefront matter 或所在 section 名选择模板子目录改了 type 却没建对应目录，静默退回默认模板
layoutfront matter 显式指定在同目录内选具体文件指定了不存在的 layout，结果页面空白但构建成功
输出格式输出配置文件名必须带格式后缀写了 rss 模板但没带格式后缀，永远匹配不上
语言多语言配置可为单语言覆盖模板只给默认语言写了模板，其他语言回退到主题版本

还有一个时间维度上的坑：Hugo 在 0.146 版本重构了模板体系，顶层的 page.html、section.html、all.html 这类命名逐步取代过去的默认目录约定，局部目录也改成了带下划线前缀的形式。结果是网上大量教程的目录结构和你装的版本对不上。判断办法很简单：认版本号，不认博客日期。

构建性能：时间花在哪，以及怎么量

「Hugo 很快」是对的，但它快的是模板执行和 Markdown 解析。真正让构建从三秒变三分钟的，几乎总是下面这几件事之一。不要凭感觉优化，先用自带的指标输出定位。

耗时来源增长方式定位手段处理办法
图片处理与「图片数乘尺寸数」成正比，且首次构建最慢看构建日志中处理的图片数量，对比缓存目录大小把生成的资源缓存目录带进 CI 缓存；尺寸档位控制在三档以内
分类词条爆炸页面数等于词条数乘输出格式数乘分页数构建摘要里的页面总数远大于文章数即是信号合并近义词条、给聚合页关掉不必要的输出格式、提高每页条数
模板里的重复计算与页面数乘循环规模成正比开启模板指标与优化提示，看累计耗时和缓存建议把无关页面上下文的片段改成带缓存的局部模板调用
相关内容与全站遍历接近页面数的平方指标里该片段调用次数异常大限制候选集合，或只在详情页计算
构建期远程请求与外部服务耗时线性相关，且不稳定构建卡住且超时报错把数据落盘进仓库，构建只读本地文件
 
# 先量再改：模板指标带优化提示，能直接告诉你哪个片段值得加缓存
hugo --templateMetrics --templateMetricsHints

# 检查两个页面是否写到了同一个目标路径（静默覆盖，最难查的一类问题）
hugo --printPathWarnings

# 清掉不再被引用的资源缓存，避免仓库或 CI 缓存无限膨胀
hugo --gc --minify

# 对比一次「有缓存」和「无缓存」的真实差距，决定要不要把缓存带进 CI
time hugo --quiet
rm -rf resources/_gen && time hugo --quiet

内容模型即 schema：改字段是破坏性变更

front matter 字段是模板、导航、订阅源、搜索索引共同依赖的接口。把它当数据库表结构看待，很多混乱会自动消失：

变更类型谁会受影响失败表现正确做法
字段改名所有读该字段的模板与输出格式不报错，页面上对应位置直接空白批量脚本改全部内容文件，同一个提交里改模板，禁止新老字段并存
类型变化，例如单值改列表模板里的遍历与判断逻辑构建报类型错误，或把字符串逐字符遍历先让模板兼容两种形态，再统一数据，最后删兼容分支
新增必填字段历史全部文件缺字段的页面渲染出空标签用分支页的 cascade 给整棵子树兜底默认值
影响 URL 的字段外部链接与搜索引擎旧地址 404留别名跳转，同时在 CDN 配服务端重定向
影响排序或上线时间的字段列表页与定时发布文章不出现或顺序错乱统一带时区的时间格式，构建环境固定时区

内容的可见性本身也是一组状态，由三个字段和三个构建开关共同决定，搞不清它们的关系就会出现「本地能看到线上没有」这种经典现象：本地预览默认会带上草稿，而生产构建默认不带。

多语言与多环境：两套正交的维度

多语言影响内容与 URL：每种语言是否有独立路径前缀、默认语言要不要也进子目录、各语言版本靠什么键关联。最容易出事的是翻译关联键——靠文件名匹配时，改个文件名就会让语言切换指向首页，显式写关联键才稳。

多环境影响配置：站点根地址、是否压缩、是否输出统计脚本、是否含草稿。配置目录按环境分层合并，而命令行构建与本地预览默认处在不同环境，这是「本地正常、上线却带着调试脚本」的根源。

# config/_default/hugo.yaml 的关键项，注释写的是「为什么」而不是「是什么」
baseURL: https://example.com/          # 生产必须带协议与末尾斜杠，否则资源指纹路径出错
defaultContentLanguage: zh
defaultContentLanguageInSubdir: false  # 改这一项等于全站 URL 迁移，上线后别动
timeout: 60s                           # 默认 30 秒，图片多或数据量大时先放宽再排查
enableGitInfo: true                    # 用提交时间当更新时间，前提是 CI 拉全量历史

permalinks:
  posts: /:section/:slug/              # URL 只依赖 slug，标题改动不影响地址

pagination:
  pagerSize: 30                        # 调小会让分页页面数成倍增长，构建变慢

caches:
  images:
    dir: :resourceDir/_gen             # 这个目录必须进 CI 缓存，否则每次全量重处理
    maxAge: -1                         # 永不过期，靠内容哈希失效

outputs:
  home: [HTML, RSS, JSON]              # JSON 供搜索索引；给聚合页少开格式能显著减少页面数
  section: [HTML]
  taxonomy: [HTML]
  term: [HTML]

发布与缓存失效：顺序错了就是一次事故

静态站的发布不是「把 public 目录同步上去」这么简单。带指纹的资源和引用它们的 HTML 之间存在依赖，上传顺序必须是资源先、HTML 后；缓存失效的顺序恰好相反，只需要失效 HTML 和站点地图，指纹资源天生不需要失效。

sequenceDiagram participant CI as CI 运行器 participant B as 构建产物 participant O as 对象存储 participant E as CDN 边缘节点 participant U as 浏览器 CI->>B: 按锁定版本构建 资源文件名带内容指纹 B->>O: 第一步 上传带指纹的静态资源 B->>O: 第二步 上传 HTML 与站点地图 O-->>E: 回源侧已是完整的新版本 CI->>E: 只对 HTML 与站点地图发失效指令 U->>E: 请求 HTML 命中必须回源校验策略 E-->>U: 返回新 HTML 其中引用新指纹资源 U->>E: 请求指纹资源 命中长期强缓存 E-->>U: 直接返回 无需失效 无需回源
产物类型缓存策略失效方式配错的后果
带指纹的 CSS 与 JS长期强缓存并标记不可变不需要失效，改内容即改文件名不加指纹又长缓存，用户几天内看到旧样式
HTML 页面不缓存或短缓存加回源校验发布后按路径失效强缓存 HTML 会让新文章在部分用户那里长期不可见
站点地图与订阅源短缓存与 HTML 一起失效搜索引擎与订阅客户端长期抓到旧列表
未加指纹的图片中等时长缓存换文件名而不是原地覆盖原地覆盖后新旧版本在不同节点并存

迁出成本与「手写静态 HTML」这条路线

选 SSG 前值得先算一次离开它的成本。真正锁定你的不是 Markdown 正文，而是三样东西：模板语言（不可移植，换工具等于重写）、专有的正文内嵌组件语法（迁移时要写转换脚本，否则正文里留下一堆无意义标记）、以及由目录结构与永久链接规则共同形成的 URL 契约。

本站走的是另一条极端路线：直接手写静态 HTML，没有任何构建步骤。这个选择的取舍很清晰，不是「更好」，而是把成本挪到了不同的地方。

维度手写静态 HTML 无构建SSG 加主题带后台的 CMS
新增一页的成本复制一份现有页面再改，最高写一个 Markdown 文件，最低后台点几下
全站改版成本要写脚本批量改写每个文件，且脚本本身要测改模板，一次生效换主题，受后台能力限制
一致性保障靠纪律与校验脚本，容易出现页面间细微不一致模板天然保证系统保证
工具链风险零依赖，十年后浏览器照样能打开受版本升级影响，主题可能失维护需要持续运维与升级
非工程师参与基本不可能会写 Markdown 就行最友好
产物可审查性diff 就是最终产物，改了什么一目了然diff 是源码，需构建后才知道效果无 diff 可言

页面规模决定路线：几十页且改版不频繁时，零依赖换来长期省心；页面上百或多人协作时，模板化的一致性收益立刻超过构建复杂度。介于两者之间，先加一层只做校验不做生成的脚本，比一步跳到完整 SSG 更容易回退。

❌
最容易踩的坑

1. 把 index.md 和 _index.md 混用：前者是叶子页，目录里的子内容不会生成页面，列表页永远是空的。
2. 为了「整理一下目录」重排 content 结构：等于一次性改掉全站 URL，外链和搜索引擎收录全废。
3. 改标题就改 slug：URL 应该只依赖 slug，标题和地址绑死意味着每次润色文案都在造断链。
4. 模板里给 partialCached 传当前页面当缓存键：等于关掉缓存，还多付一次哈希开销。
5. 在循环里直接取页面级变量：循环内的上下文已经变成当前元素，必须用根上下文或提前存变量。
6. 给非 HTML 输出格式写模板时漏掉格式后缀：文件放对了目录也永远匹配不上，产物静默为空。
7. 把图片资源缓存目录排除在 CI 缓存之外：每次构建全量重处理图片，构建时间从秒级涨到分钟级。
8. 分类词条拼写不统一：同一含义产生多个词条，页面总数成倍增长，聚合页还被拆碎。
9. 本地预览和生产构建用不同环境却不自查：调试脚本、草稿内容跟着上线。
10. 发布时先传 HTML 后传资源：中间窗口里用户拿到的页面引用了还不存在的样式与脚本。
11. 对带指纹的资源做缓存失效、却给 HTML 配长期强缓存：两件事正好做反，新内容长期不可见。
