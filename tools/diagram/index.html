技术文档里的图：该画什么，不该画什么

🏷️ 代码生图

先决定这张图要回答哪一个问题

技术文档里绝大多数无效的图，问题不在工具、不在配色、也不在布局，而在于画之前没人说清楚它要回答什么。一个可以立刻执行的约束：在画图之前，用一句话写出这张图要回答的问题，并把这句话当成图的标题。写不出来就别画；一句话里装了两三个问题，就拆成两三张图。

「系统架构图」这种名词短语不是标题，它没有声明任何问题，于是任何内容都可以被塞进去，最终变成一张谁都看不懂、谁也不敢删的图。换成「订单支付链路中，哪些环节会跨进程、失败后谁负责补偿」，图该画什么、不该画什么立刻就清楚了。

六类图各自最容易表达错的东西

每类图都有一个「结构上表达不了、于是被默默省略」的维度。知道这个盲区在哪，比学任何语法都重要。

类型它擅长回答最容易表达错或被省略的画对了的判定
结构图包含关系、可替换单元、耦合面把部署单元、代码模块、类混进同一张；接口不画出来只剩箭头指着任意一个框能说出「换掉它要动谁」
流程图条件分支、判定与顺序把并发画成顺序；省掉异常与超时分支；人的操作和系统处理混画每个菱形的出边覆盖了所有情况，且互斥
时序图跨进程往返、时间顺序、失败语义异步消息画成同步返回；重试与幂等不体现；参与者太多能指出每次往返的超时值和失败后的状态
状态图生命周期、允许的转移、终态状态其实不互斥（塞进了两个正交维度）；缺终态；转移上写动作不写条件任一时刻对象恰好落在一个状态里
数据模型图实体、关系、基数逻辑模型与物理表混画；基数不标；把索引和分片画进来每条关系都标了一对一、一对多还是多对多
部署拓扑图执行环境、网络与信任边界副本一律画成 1；信任边界与安全组不画；把逻辑调用当成网络连线能回答「哪条线跨了信任边界」和「挂一台会怎样」

抽象层级混用：最常见也最致命的失败

一张图同时出现「用户」「网关」「订单服务」「OrderService 类」「orders 表的 user_id 列」，读者的注意力必须在五个尺度之间换挡，于是这张图什么也没说明。它看起来信息量很大，实际信息密度接近零。

判据比原则好用：同一张图里所有节点，应该能用「换掉它的成本」这一个尺度排序，且大致落在同一量级。换掉一个外部系统、换掉一个可独立部署的进程、换掉一个内部模块、换掉一个类，这是四个量级，混在一起就会出事。

flowchart TB subgraph L1["层级一 系统与外部参与者"] A1["本系统"] A2["支付网关（外部）"] A3["下单用户"] end subgraph L2["层级二 可独立部署单元"] B1["订单 API"] B2["履约 Worker"] B3["订单库"] end subgraph L3["层级三 单元内部模块"] C1["幂等模块"] C2["定价模块"] end subgraph L4["层级四 代码与表结构元素"] D1["OrderService 类"] D2["orders 表的 user_id 列"] end L1 -.->|"相邻层可作为背景出现一层"| L2 L2 -.->|"隔层混画，图立刻失效"| L4 L2 -.->|"只在放大单个单元时单独成图"| L3
层级节点举例可以同图出现的混入之后的后果
系统与外部本系统、外部支付网关、用户相邻的部署单元层可作为背景，且要灰掉混入模块名后，外部读者以为那是对外契约
可独立部署单元API 进程、Worker、数据库实例同层的全部单元，外部系统灰掉混入类名后，无法回答「发布单元是什么」
单元内部模块幂等、定价、风控适配只在为某一个单元单独画一张时和部署单元并列时，读者以为模块是可独立部署的
代码与表结构类、方法、字段、索引几乎不该进架构图必然过期；真要看就去看代码和 DDL

箭头必须有唯一语义

「箭头指向谁」这件事本身没有意义，因为常用的三种语义在同一段代码上方向可能完全相反。这不是抠字眼：评审时如果箭头语义不明，关于依赖方向、故障传播、扇出的所有结论都是错的。

flowchart TB subgraph C1["语义一 运行期调用"] H1["HTTP 处理器"] --> R1["订单仓储接口"] R1 --> P1["数据库驱动实现"] end subgraph C2["语义二 编译期依赖（依赖倒置后）"] P2["数据库驱动实现"] --> R2["订单仓储接口"] H2["HTTP 处理器"] --> R2 end subgraph C3["语义三 一次查询的数据流"] P3["数据库"] --> R3["订单仓储"] R3 --> H3["HTTP 处理器"] end
箭头语义方向怎么定与其他语义冲突的例子图例怎么写
运行期调用发起方指向被调用方依赖倒置后与编译期依赖方向相反实线箭头：A 调用 B，同步等待
编译期或装配期依赖依赖方指向被依赖方实现类指向接口，与调用方向相反虚线箭头：A 引用 B 的定义
数据流数据实际移动的方向读操作里数据从库流向服务，与调用方向相反粗线箭头：数据从 A 流向 B，标注载荷
包含或部署归属用嵌套框表达，不要用箭头用箭头表达「部署在其中」会和调用混淆不用箭头，用容器边框加标题
触发或事件发布方指向事件，事件指向订阅方被误读成同步调用，扇出估计全错开箭头：异步发布，不等待

图与文字的分工

图只擅长表达拓扑：谁连谁、谁包含谁、谁在谁之前。数量、阈值、条件、理由、取舍，图表达不了——硬塞进节点标签，得到的是一张排版很差的段落。

信息类型该放哪理由
拓扑与包含关系、并发结构、时间顺序图文字描述拓扑要读者在脑子里重建，成本极高
为什么这么设计、放弃了哪个方案文字取舍是论证，图里放不下论证
阈值、超时、副本数、容量与配额表格，或图上的少量标注这类值会变，集中放一处才好维护
失败后的语义与补偿责任文字，图上只标出失败分支存在语义需要精确措辞，节点标签写不下
接口契约、字段定义代码或接口定义，文档里引用抄进图里就是第二份真相，必然漂移
关键结论文字（图只是辅证）屏幕阅读器、搜索、纯文本阅读场景都拿不到图里的内容

注定过期的图：该删，不是该更新

图的维护成本是真实成本。留着一张错的图比没有图更糟，因为它会被当成事实引用。所以要在画之前就判断它的半衰期，并据此决定放在哪。

图的内容半衰期该放哪过期时怎么处理
信任边界、对外系统边界年文档库，长期维护值得逐次更新，边界变化本身就是大事
领域模型核心、契约级状态机年文档库，和契约放一起随契约变更同步修改
部署拓扑季度尽量由配置或代码生成让生成器维护，别手工追
服务清单、实例数、端口周不入文档，去查注册中心或编排配置直接删，附一条查询命令即可
迁移方案的中间阶段迁移周期内提案或事故记录里，标注有效期迁移结束即删，不要留成「历史架构」
排障时随手画的推演图天PR 评论或事故复盘，不入库复盘结束即弃，结论转成文字
✅
能自动生成的图不算维护成本

依赖关系、调用关系、基础设施拓扑这类图，正确做法是让工具从真实来源导出，维护对象变成生成器而不是图本身——具体做法见站内《Graphviz 的布局算法与大图治理》。反过来说，凡是必须手工维护的图，都要能说出「六个月后谁更新它」；答不出人名，就按短半衰期处理。

评审一张图的检查清单

评审时不要评论配色，问下面这几个问题就够了。任何一条不通过，图都要改而不是「先这样」。

检查项不通过的表现处置
标题是一个问题标题是「XX 架构图」这类名词短语改成问句或结论句，改不出来说明图没想清楚
只回答一个问题要分两口气才能讲完按问题拆图
抽象层级单一同图出现外部系统和类名拆层，低层单独成图
箭头语义唯一且有图例没有图例，或一种线型表达多种关系补图例，或按语义拆图
没有「其他」框出现「其他服务」「等等」分类没做完，要么补全要么缩小范围
命名与系统一致图里叫「订单中心」，代码仓库叫 order-api统一用系统里的真实名字
删掉它文档仍完整？删掉毫无损失说明图只是装饰，直接删
有明确的维护人答不出六个月后谁更新改成自动生成，或按短半衰期不入库

无障碍与可读性不是加分项

图在真实阅读场景里会遇到深色模式、打印、屏幕阅读器、小屏和色觉差异。前面的信息设计做对了，这一步只需要几条硬规则。

要求具体做法常见违反
颜色不承载唯一信息状态与分类同时用形状、线型或文字标签冗余编码只靠红绿区分成功失败，红绿色觉障碍读者直接失效
足够的对比度图形元素与背景不低于 3:1，正文级文字不低于 4.5:1浅灰描边配白底，投影或打印后什么都看不见
深色模式不写死颜色描边与文字跟随当前文本色，背景交给主题硬编码黑色描边在深色背景上整条线消失
图里是真文本输出矢量格式，文字保持为文本节点贴位图截图，既不能搜索也不能被屏幕阅读器读取
有文字替代与说明图配一段说明，关键结论写在正文里结论只存在于图中，纯文本与订阅场景读者完全拿不到
小屏可读控制节点数，宁可拆图；长标签换行而不是缩字号为了塞进一屏把字号压到看不清，等于没出图

#!/usr/bin/env python3
# 把「图的纪律」变成 CI 检查：图源旁边必须有一句「本图回答」，
# 并且图里的节点名要能在代码仓库里找到，否则读者无法把图落到系统上
import re, subprocess, sys, pathlib

# 从图源里抽出方括号或引号中的标签，工具无关的粗提取足够用
LABEL = re.compile(r'\["([^"]+)"\]|\[([^\]|]+)\]')
# 看起来像系统标识符的标签才对账：含连字符、下划线或全为拉丁字母
IDENT = re.compile(r"^[A-Za-z][A-Za-z0-9_\-]{2,}$")

def repo_has(name: str) -> bool:
    # 只在版本库跟踪的文件里找，避免命中构建产物
    r = subprocess.run(["git", "grep", "-qI", "--", name],
                       capture_output=True)
    return r.returncode == 0

fail = 0
for f in sys.argv[1:]:
    text = pathlib.Path(f).read_text(encoding="utf-8")
    if "本图回答" not in text:
        print("%s: 缺少「本图回答：」说明行" % f); fail += 1
    for m in LABEL.finditer(text):
        label = (m.group(1) or m.group(2)).strip()
        if IDENT.match(label) and not repo_has(label):
            print("%s: 节点名 %s 在仓库里找不到，可能已改名" % (f, label))
            fail += 1
sys.exit(1 if fail else 0)

❌
最容易踩的坑

1. 用「XX 架构图」当标题——名词短语不声明任何问题，于是什么都能往里塞，最后谁也不敢删。

2. 一张图回答多个问题——读者每次只带一个问题来，图越全越没人用得上。

3. 抽象层级混用——外部系统、部署单元、模块、类挤在一张图里，信息密度接近零。

4. 箭头语义不声明——调用、依赖、数据流三种方向可能相反，没有图例的图推不出任何结论。

5. 用箭头表达「部署在其中」——包含关系该用嵌套框，用箭头一定会和调用混淆。

6. 把异步事件画成普通箭头——读者会按同步阻塞去估算延迟与扇出，结论全错。

7. 流程图的菱形出边不互斥或不完备——漏掉超时和部分成功，评审时最该发现的问题恰好被藏住。

8. 状态图里塞两个正交维度——风控标记、发票状态和主状态并列，导致「任一时刻在一个状态」不成立。

9. 图里出现「其他服务」这类框——说明分类没做完，读者无法判断边界。

10. 图里的名字和代码、注册中心不一致——读者无法把图落回系统，图就只是装饰。

11. 手工维护会频繁变的图——实例数、端口、迁移中间态属于短半衰期信息，该查系统而不是查图。

12. 只靠颜色区分状态、又写死了颜色——色觉差异读者读不出区别，深色模式下描边直接消失。
