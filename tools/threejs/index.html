Three.js 的渲染管线与性能预算

🏷️ 代码生图

一帧里到底发生了什么

二维图表库的性能问题基本只有一个变量：元素数量。实时三维不一样，它的成本分布在一条固定的流水线上，而且横跨 CPU、图形驱动和 GPU 三个地方。renderer.render(scene, camera) 这一行背后的顺序是固定的，把它记住，排查就有了顺序。

sequenceDiagram participant App as 应用逐帧回调 participant Scene as 场景图 participant R as WebGLRenderer participant GL as WebGL 驱动 participant GPU as GPU App->>Scene: 修改变换与材质参数 App->>R: render 传入场景与相机 R->>Scene: 重算世界矩阵 R->>R: 按包围球做视锥剔除 R->>R: 不透明由近到远 透明由远到近排序 R->>GL: 按需编译或取用着色器程序 R->>GL: 绑定缓冲与纹理后逐批提交 GL->>GPU: 顶点着色 光栅化 片元着色 GPU-->>GL: 写入帧缓冲 Note over R,GL: 每次材质或缓冲切换都是一次状态切换
提交次数由网格与材质的组合数决定

帧预算是硬的：60 帧对应每帧 16.7 毫秒，30 帧对应 33 毫秒，而这里面还要留给浏览器合成和你自己的业务逻辑。下面这张表把成本拆开，并给出定位顺序——先看提交次数和像素数，最后才看三角面数，这个顺序和大多数人的直觉相反。

场景图与相机投影的两个必知细节

场景图里每个对象持有局部变换和世界矩阵两份数据，默认每帧都会按位置、四元数、缩放重组局部矩阵再向下传播。静态子树把自动更新关掉、手工更新一次，能在节点数上千时省下可观的 CPU 时间。另外 add 保留局部变换（对象会跟着新父节点跳走），attach 保留世界变换——做「把零件挂到机械臂上」这类操作时用错会当场跳飞。

相机这边有两个坑。一是改了视场角、宽高比、近远裁剪面之后必须重算投影矩阵，否则画面拉伸或裁剪异常。二是深度精度由近远裁剪面的比值决定，不是由远裁剪面的绝对值决定：把近裁剪面设成 0.01 只为了能贴近看，代价是远处出现深度冲突的条纹闪烁。正确做法是把近裁剪面尽量推大，实在需要极大跨度再考虑对数深度缓冲，而它本身也有成本。

draw call 为什么是首要瓶颈

每一次提交都要在 CPU 侧准备状态、在驱动侧做校验和状态切换。三角面数是 GPU 的活，现代 GPU 吃得下相当多的面；而提交次数是 CPU 与驱动的活，它在 JS 环境里更容易先到顶。所以「模型面数不高但就是卡」的场景非常常见，几乎都是提交次数失控。

降提交次数的手段都要付代价，代价通常是剔除粒度和独立性：

手段适用代价
合并几何体大量静态且材质相同的物体整块成为一个剔除单元，镜头只看到一角也要全量提交；也失去逐物体变换
InstancedMesh同几何体同材质的大量副本包围球来自几何体本身，不含实例变换，实例分散时整体会被错误剔除
较新版本的 BatchedMesh材质相同但几何体不同的批量需要预分配容量，管理复杂度更高
贴图图集材质仅因贴图不同而分裂UV 要重排，mipmap 层级上可能出现边缘渗色
收敛材质种类参数微小差异导致着色器程序分裂视觉统一度要妥协
LOD 分级远处物体需要多套模型，切换瞬间有跳变

透明物体还有一层隐含成本：它们按距离排序后绘制，重叠多层时无法保证逐像素的正确遮挡，会出现闪烁和穿插。能用不透明加镂空贴图解决的，别用半透明。

const renderer = new THREE.WebGLRenderer({ antialias: true, powerPreference: 'high-performance' });
const capPR = Math.min(window.devicePixelRatio, 2);   // 不设上限时 dpr 3 的手机像素是 dpr 1 的九倍
renderer.setPixelRatio(capPR);

// 静态子树关掉逐帧矩阵重算，只手工更新一次
staticRoot.traverse(o => { o.matrixAutoUpdate = false; });
staticRoot.updateMatrixWorld(true);

// 首次出现的材质会在那一帧编译着色器，表现为进场瞬间的单帧尖峰，提前预热掉
renderer.compile(scene, camera);

const tmp = new THREE.Vector3();   // 循环里不要 new，GC 会变成周期性掉帧
let last = 0, acc = 0, frames = 0, scale = 1;

renderer.setAnimationLoop((t) => {   // 用它而不是裸 requestAnimationFrame，WebXR 下才能被正确接管
  const dt = t - (last || t);
  last = t; acc += dt; frames++;

  if (acc > 1000) {                  // 按实测帧时间调分辨率，比按机型判断可靠：发热降频也能兜住
    const avg = acc / frames, budget = 1000 / 60;
    if (avg > budget * 1.4 && scale > 0.6) scale -= 0.1;
    else if (avg < budget * 1.05 && scale < 1) scale += 0.1;
    renderer.setPixelRatio(capPR * scale);
    acc = 0; frames = 0;
  }

  tmp.set(0, Math.sin(t / 1000), 0);
  target3d.position.copy(tmp);
  renderer.render(scene, camera);
});

// 预算面板：提交次数是首要指标，程序数量能暴露材质分裂
const i = renderer.info;
console.log(i.render.calls, i.render.triangles, i.memory.geometries, i.memory.textures, i.programs.length);

几何体与贴图的显存账

显存是可以手算的，算一遍比任何经验值都可靠。

资源算法举例
顶点位置每顶点三个单精度浮点，12 字节10 万顶点约 1.2MB
法线与 UV每顶点再加 12 加 8 字节同一模型再加约 2MB
索引顶点数超过 65535 必须用 32 位索引，每个 4 字节30 万索引约 1.2MB
未压缩贴图宽乘高乘 4 字节2048 见方约 16MB
mipmap 链在上一行基础上再加约三分之一约变成 21MB
GPU 压缩贴图约每像素 0.5 到 1 字节，取决于转码目标2048 见方约 2 到 4MB
渲染目标宽乘高乘像素比平方乘每像素字节，半浮点再翻倍后处理链按乒乓数量乘

最需要纠正的一条：贴图文件大小和显存占用没有关系。一张 2048 见方的 PNG 压到 300KB，上传后照样是 16MB 加 mipmap，因为 GPU 采样的是未压缩像素。真正减显存只有两条路：贴图换成能在 GPU 上保持压缩状态的格式，以及直接减小贴图尺寸。

手段减小传输减小显存解码成本备注
JPG 或 PNG 贴图是否解码成未压缩像素文件再小，显存都是宽乘高乘 4
KTX2 加通用压缩是是转码到设备原生压缩格式需要随包发转码器，且要在渲染器创建后探测支持情况
Draco 几何压缩是否wasm 解码，建议放工作线程解码回浮点属性，顶点数与显存不变
顶点量化是是很低属性以 16 位或 8 位上传，这才真正省显存
打包成二进制 glb略否无只是打包方式，不是压缩

光照与阴影的代价分级

阴影的成本不在「看起来复杂」，而在它是额外的渲染通道：每一盏投射阴影的光源，都要先从光源视角把场景渲染一遍写进深度贴图。这条规则直接决定了取舍。

配置额外渲染通道每片元成本什么时候接受
环境光与半球光0极低任何场景
环境贴图做间接光0，预处理一次低首选，通常比堆光源更好看也更便宜
方向光不投阴影0低主光源
方向光投阴影1中，取决于采样质量桌面可接受，移动端谨慎
聚光灯投阴影1中局部强调
点光源投阴影6，立方体六个面高尽量避免，用投阴影的聚光灯替代
多盏光源各自投阴影每盏一套线性叠加静态场景改用烘焙

还有两个容易被忽略的点。阴影贴图分辨率和光源的阴影相机范围共同决定精度，范围开太大就必然出现锯齿或漏光，解决办法是把阴影相机的视体收紧到真正需要阴影的区域，而不是一味调大分辨率。静态场景可以关掉阴影贴图的自动更新，只在需要时触发一次，等于把每帧的阴影通道省成一次。

光源数量变化会改变着色器程序的缓存键，所以运行时增删灯光会触发重新编译，表现为交互瞬间的单帧卡死。要做明暗切换就固定灯光个数、只调强度。

资源加载与颜色空间

运行时格式是 glTF，配套的压缩扩展决定了首屏时间。要注意几个顺序性的要求：转码器的支持探测必须在渲染器创建之后做（它要查询 GL 上下文支持哪些压缩格式）；解码器文件要能被缓存；预编译要在模型加入场景之后做。

import { GLTFLoader } from 'three/addons/loaders/GLTFLoader.js';
import { DRACOLoader } from 'three/addons/loaders/DRACOLoader.js';
import { KTX2Loader } from 'three/addons/loaders/KTX2Loader.js';

const draco = new DRACOLoader().setDecoderPath('/vendor/draco/');   // wasm 解码器，放 CDN 并允许长缓存
const ktx2 = new KTX2Loader()
  .setTranscoderPath('/vendor/basis/')
  .detectSupport(renderer);   // 必须在 renderer 创建之后：要问 GL 上下文支持哪些压缩格式

const loader = new GLTFLoader().setDRACOLoader(draco).setKTX2Loader(ktx2);

loader.load('/models/machine.glb', (gltf) => {
  scene.add(gltf.scene);
  renderer.compile(scene, camera);   // 模型进场后预编译，避免第一帧编译卡顿
}, (e) => updateProgress(e.loaded / e.total), (err) => console.error('模型加载失败', err));

// 颜色空间：加载器会按 glTF 规范设置贴图的颜色空间。自己用 TextureLoader 加的要手工设，
// 颜色类贴图标成 sRGB，法线 粗糙度 金属度 环境光遮蔽这类数据贴图必须保持线性，
// 设反了的典型症状是整体发灰发亮，或者凹凸方向看起来不对。
const albedo = new THREE.TextureLoader().load('/tex/albedo.jpg');
albedo.colorSpace = THREE.SRGBColorSpace;
const roughness = new THREE.TextureLoader().load('/tex/rough.jpg');   // 不设，保持线性

dispose：GPU 资源不会自动回收

这是 Three.js 最集中的内存泄漏来源，根因是两套生命周期：JS 对象由垃圾回收管，GPU 侧的缓冲与纹理句柄只能显式释放。从场景图移除不释放任何显存，把变量置空也不会。

// 容器对象没有 dispose，移除也不释放显存，必须自己遍历。
// 多个网格可能共用同一材质或贴图，所以先去重，避免释放掉仍在使用的资源。
function disposeSubtree(root, renderer, composer) {
  const geometries = new Set(), materials = new Set(), textures = new Set();

  root.traverse((obj) => {
    if (obj.geometry) geometries.add(obj.geometry);
    const mats = Array.isArray(obj.material) ? obj.material
               : (obj.material ? [obj.material] : []);
    for (const m of mats) {
      materials.add(m);
      for (const v of Object.values(m)) {
        if (v && v.isTexture) textures.add(v);   // map normalMap envMap 都挂在材质属性上
      }
    }
  });

  root.parent?.remove(root);
  geometries.forEach(g => g.dispose());
  materials.forEach(m => m.dispose());
  textures.forEach(t => t.dispose());

  composer?.dispose?.();          // 后处理链的渲染目标单独释放
  renderer.renderLists.dispose(); // 清掉渲染列表里对已释放对象的引用
}

后处理与分辨率的帧预算

后处理的成本模型很好算：每一个全屏通道都要把整个画面读一遍写一遍，成本正比于像素数乘通道数，而且是带宽密集型。泛光这类效果内部还有多级降采样，一个效果往往是好几个通道。

所以后处理和分辨率是同一份预算里的两项，只能二选一地加码。三条实践结论：开了后处理链之后，默认的多重采样抗锯齿通常不再生效，抗锯齿要改成后处理形式；半浮点渲染目标把带宽直接翻倍，只在确实需要高动态范围时用；把像素比从 2 降到 1.4 带来的收益，往往比砍掉一个效果更大且更不易察觉。

拾取也算在这份预算里：射线检测的成本随参与检测的三角面数增长，高模场景要用简化的代理体或空间加速结构，而不是直接对渲染用的网格做检测。

真正需要三维的场景有共同点：遮挡、装配顺序、空间冲突、尺度关系本身就是要传达的信息——设备拆装、建筑与管线碰撞、地形与城市尺度、需要围着看的产品。反过来，大小比较、趋势、占比、分布这些问题，二维图表一眼可读，做成三维只会引入透视失真和遮挡，读数反而更难。数据类需求的选型详见站内《Chart.js 的配置模型与容量边界》《ECharts 的渲染架构与大数据量优化》和《D3 的数据绑定模型与使用边界》；离线批量出图详见《Python 可视化栈的分层与场景匹配》。

❌
最容易踩的坑

1. 以为从场景移除或把变量置空就释放了显存：容器对象没有释放方法，几何体、材质、贴图、渲染目标都要显式释放。

2. 释放共享资源没去重：把还在被其他网格使用的贴图释放掉，下次渲染又重新上传，白忙一场还多一次卡顿。

3. 用 Draco 压完就以为省了显存：它只减下载体积，解码后顶点数据回到浮点，要省显存得靠贴图压缩格式与顶点量化。

4. 合并几何体降提交次数后忘了代价：整块成为一个剔除单元，镜头只看到一角也要全量提交。

5. InstancedMesh 的实例散布在大范围：包围球仍来自几何体本身，整体被错误剔除，症状是「转个角度东西没了」。

6. 每帧新建向量和矩阵：垃圾回收变成规律性的帧时间尖峰，看曲线很好认。

7. 给点光源开阴影：一盏就是六个面的深度通道，这是最贵的单项配置。

8. 运行时增删灯光或切换材质特性：着色器程序缓存键变了要重新编译，表现为交互时单帧卡死，进场前预编译能挡掉大部分。

9. 手工加载的颜色贴图不设颜色空间：整体发灰发亮；反过来把法线、粗糙度贴图当 sRGB 处理会让光照算错。

10. 像素比直接用设备值不设上限：高倍屏上像素数是基准的好几倍，片元成本直接翻几番。

11. 改了相机参数不重算投影矩阵；近裁剪面为了贴近看设得极小，导致远处深度冲突闪条纹。

12. 只在桌面测并按机型做降级：发热降频会让同一台手机前后表现差很多，降级必须按实测帧时间触发。
