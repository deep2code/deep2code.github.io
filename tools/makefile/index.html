Makefile 构建

🏷️ Makefile

💡 你在工作中遇到了这个问题，查了很多资料还是没搞懂。或者你面试的时候被问到，答不上来。

Makefile 为什么活到了 2026 年

我知道很多人看到 Makefile 的第一反应是「这不就是上个世纪的东西吗」。但你打开任何一个 C/C++ 开源项目——Redis、Linux 内核、ffmpeg——根目录里照样躺着一个 Makefile。

先记住 make 的核心心智模型：它就是一个拓扑排序器。给它一张「目标 → 依赖 → 命令」的图，它按时间戳判断谁过期、再并发执行。

理解了这一点，下面所有花里胡哨的变量和模式规则都是锦上添花。我常画这样一张依赖图给自己看：

flowchart TD APP[app 可执行文件] --> O1[main.o] APP --> O2[foo.o] APP --> O3[bar.o] O2 --> H[foo.h 生成的头文件] O3 --> H O1 --> C1[main.c] O2 --> C2[foo.c] O3 --> C3[bar.c] H --> GEN[codegen 规则 比如 protobuf 生成]

一句话讲清

make = 依赖图调度器。规则是 目标: 依赖\n\ttab 命令，它比较目标和依赖的时间戳，依赖更新了就重跑命令。别把它当成「脚本执行器」，它的全部价值在依赖追踪。

CFLAGS / LDFLAGS 这套变量到底是干嘛的

刚接触 C 项目的人最懵的就是 $(CC)、$(CFLAGS)、$(LDFLAGS) 这一堆。我第一次读 redis 的 Makefile 也头大。其实分工很清晰：

变量放什么典型值
CCC 编译器gcc / clang
CXXC++ 编译器g++ / clang++
CFLAGS编译阶段选项-Wall -O2 -g -I 头文件路径
CPPFLAGS预处理器选项-D 宏定义
LDFLAGS链接阶段选项-L 库路径
LDLIBS要链接的库-lpthread -lm

这里有个我被坑过的细节：CFLAGS 和 LDFLAGS 的顺序不能乱。链接器从左到右处理参数，如果一个 .o 依赖 libfoo，那 .o 必须写在 -lfoo 前面。我早期写 Makefile 把 $(LDLIBS) 放最前面，链接报 undefined reference，折腾半天才发现是顺序问题。下面这张表我贴在工位上当 cheat sheet：

场景放哪例子
头文件目录CFLAGS 或 CPPFLAGS-I./include
宏开关CPPFLAGS-DDEBUG=1
优化级别CFLAGS-O2 -g
库搜索路径LDFLAGS-L./lib
链接哪个库LDLIBS-lm -lpthread

模式规则：别再手写一百条规则

新手最常见的错误是给每个 .c 文件写一条规则。一旦源文件从 5 个涨到 50 个，你的 Makefile 就没法看了。正确做法是用模式规则，一条顶一万条：

CC = gcc
CFLAGS = -Wall -O2 -g

# 模式规则：所有 .o 都从同名 .c 生成
%.o: %.c
	$(CC) $(CFLAGS) -c $< -o $@

# 批量推导出所有 .o
OBJS := $(SRCS:.c=.o)

app: $(OBJS)
	$(CC) $(CFLAGS) $^ -o $@ $(LDLIBS)

里面几个自动变量你必须眼熟：$@ 是目标，$< 是第一个依赖，$^ 是所有依赖。我背不下来，但每次用都得想三秒——记不住就 man make 里搜 Automatic Variables，别硬背。

GNU make 还有一堆内置隐式规则，上面那条 %.c→%.o 其实不用自己写，make 自带。理解这点后你就能看懂别人的 Makefile 为什么短得不像话。

并行编译：-j 背后的并发坑

多核 CPU 出来以后，make -j8 几乎成了标配。但我要提醒你：并行是有代价的，依赖没写全就会偶发性编译失败。

我当年在一个老项目里 make -j$(nproc)，十分钟一次的 CI 里总有两次报「找不到头文件」。本地单线程编译从来没事。最后定位到：某个头文件是另一个规则生成的（比如 protobuf 生成的 pb.h），但源码规则没把它列进依赖，于是并行时 .c 先于 pb.h 被编译，直接 GG。修法很简单——把生成的头文件加进 EXTRA_OBJS 依赖里。

并行编译的铁律

凡是「A 依赖 B 生成的文件」，不管 B 是 .c、.y 还是 .proto，都必须在规则里显式列出来。隐式的、「我知道它会先生成」这种想法在 -j 下一定会咬你。CI 里固定跑 -j$(nproc)，本地也用它，越早暴露竞争越早修。

静态库 / 动态库：.a 和 .so 到底差在哪

这是面试常考、新手常混的点。我的理解是：静态库在链接时就把代码塞进可执行文件，动态库在运行时才加载。两者的制作方式不一样，别用错命令：

# 静态库：ar 归档一堆 .o
libfoo.a: foo.o bar.o
	ar rcs $@ $^

# 动态库：编译成位置无关代码再 -shared
libfoo.so: foo.o bar.o
	$(CC) -shared -fPIC $^ -o $@

关键就两个词：-fPIC（位置无关代码，动态库必须）和 -shared（生成共享对象）。静态库不需要 PIC。我列个对比表：

静态库 .a动态库 .so/.dll
链接时机编译时打包进可执行文件运行时加载
产物体积大（每个程序都带一份）小（共享一份）
更新重新链接换个 .so 即可
编译要求普通 .o-fPIC
典型libc.a（嵌入式）libc.so（桌面）

pkg-config：别再手写 -I 和 -l 了

链接第三方库最烦的是「头文件在哪、库叫什么名」。pkg-config 就是为这事设计的，它读 .pc 文件告诉你答案：

pkg-config --cflags openssl   # 输出 -I/usr/include/openssl
pkg-config --libs openssl     # 输出 -lssl -lcrypto

# 写进 Makefile
CFLAGS += $(shell pkg-config --cflags openssl)
LDLIBS += $(shell pkg-config --libs openssl)

我现在写新 C 项目一律用 pkg-config，再也不靠人肉翻 /usr/lib。它解决的是「库在不同发行版装在不同地方」的移植性问题。

Makefile vs CMake/Meson：我的选型

每次有人问「新项目该用 make 还是 cmake」，我都让他先问自己一句：这个项目需要在多少种平台上编译？

手写 MakefileCMakeMeson
跨平台自己写 ifeq Linux/BSD原生跨平台原生跨平台
学习成本低，但容易写成屎山中（DSL 怪）低（Python-like）
依赖管理靠 pkg-configfind_package封装得最好
构建速度快中快
适合单平台小项目、嵌入式中大型跨平台 C++追求现代体验

我的实际选择：纯 Linux 单平台小工具，手写 Makefile 一两百行搞定，不引入 CMake；一旦要跨 Windows/Android/iOS，直接 CMake 别犹豫。Meson 我很喜欢但生态还不如 CMake 广，开源库用得没那么多。

flowchart TD A{项目规模和目标?} -->|单平台小工具| B[手写 Makefile] A -->|跨平台 C++ 中大型| C[CMake] A -->|追求现代快构建| D[Meson] B --> E[直接 gcc make 完事] C --> F[生成 VS Xcode Makefile 工程] D --> G[依赖封装体验最好]

2026 年的几个实用点

  • .PHONY 必须写：all、clean 这种不产出文件的伪目标，一定要 .PHONY: all clean，否则目录里碰巧有个叫 clean 的文件，make 就说「已是最新」什么都不做；
  • 变量导出：子 make 要继承变量用 export，递归 make（subdir 里再调 make）这是必坑；
  • 第二阶段扩展：make -f config.mk 把配置外置，主 Makefile 只写逻辑，配置和逻辑分离好维护；
  • Linux 25.x 的 make：系统自带 GNU make 4.4+，支持 --shuffle 随机化目标顺序来暴露并行竞争，CI 里开一下很香。

Do / Don't

我建议

✓ 伪目标全部加 .PHONY；✓ 用模式规则 + $(OBJS:.c=.o) 自动推导；✓ 第三方库走 pkg-config；✓ CI 固定 -j$(nproc) 抓竞争。

别这样

✗ 别用 tab 以外的东西缩进 recipe——空格永远不行；✗ 别把 rm -rf 写在没检查的 clean 里；✗ 别在 recipe 里用 shell 函数覆盖 make 变量，心智模型会崩。

FAQ

Q：make 报 "missing separator" 是什么意思？
九成九是你用空格代替了 tab。Makefile 的 recipe 行必须以真正的 Tab 开头。编辑器显示的 Tab 和实际字符不是一回事，把这行删掉手敲一个 Tab 基本就好。

Q：为什么我改了 .c 文件 make 却说 "Nothing to be done"？
检查时间戳。如果你 touch 了 .o 或用了时钟不对的环境，make 会觉得目标比依赖新。用 make -d 看它的判断过程，或 rm 掉 .o 重编。

Q：递归 make（sub-make）有什么坑？
变量默认不传，得 export；并行跨目录时依赖关系是隐式的，跨目录的并行依赖最容易出竞争。Nicholas 那篇《Recursive Make Considered Harmful》建议用一个顶层 make 把所有目标扁平化，大项目值得一读。

Q：2026 年还需要学手写 Makefile 吗？
需要。哪怕你的项目用 CMake 生成 Makefile，你迟早要在某个 C 项目里手读一个；而且读懂 make 的依赖调度模型，反过来能帮你理解 CMake/Ninja 到底在干嘛。这是底层功夫，不是过时知识。

小结

Makefile 老，但老不等于过时。它把「依赖追踪」这件事做到了极致，一百行能写清楚的构建，你没必要为了跨平台去背 CMake 那套怪语法。下一篇 Markdown，看另一篇「语法简单到写了十几年」的工具。
