Make 的依赖图与工程化用法

🏷️ Makefile

Make 被当成脚本入口用了太久，以至于很多人写了几年 Makefile 也没用到它唯一不可替代的能力。它的核心不是「按顺序执行命令」，而是解一张由文件时间戳定义的依赖图：给定一个目标，它递归判断哪些节点过期，只重建过期的部分，并在允许的前提下并发执行。所有让人困惑的行为——Tab、展开时机、每行一个 shell、并行偶发失败——都能从这个模型推出来。

核心模型：时间戳驱动的依赖图

一条规则由三部分组成：target（要生成的文件）、prerequisite（它依赖的文件）、recipe（怎么从依赖生成目标）。make 对每个目标的判定只有两条：目标文件不存在就重建；目标存在但任一依赖的 mtime 比目标新就重建。注意是「比目标新」，时间戳相等不算过期。

由此推出几个反直觉的结论。第一，make 不看内容也不算哈希，所以 touch 能骗过它，改了 CFLAGS 也不会触发重建——参数不是文件。第二，文件系统的时间戳精度会直接影响正确性：ext4 是纳秒精度，而部分网络文件系统和挂载选项只有秒级，同一秒内先后生成的两个文件在 make 眼里时间戳相等，于是「该重建的没重建」。第三，目录也是文件，而目录的 mtime 会随内部增删文件而变化，所以把目录写成普通依赖会导致无限重建——这正是 order-only 依赖存在的原因。

order-only 依赖写在依赖列表的竖线后面：target: 普通依赖 | order-only 依赖。它只保证在构建目标之前先把这些节点建好，完全不参与时间戳比较。创建输出目录是它的标准用法。

.PHONY 为什么必要

伪目标解决三个互不相关的问题，任何一个单独出现都足以让构建行为出错。

一是同名文件冲突。clean、test、docs 这些目标名很容易和仓库里真实存在的目录或文件撞上。一旦撞上，make 发现目标文件存在、又没有依赖比它新，就直接输出「已是最新」什么都不做。仓库里有个 test/ 目录导致 make test 静默跳过，是这个坑最常见的形态。

二是性能。对非伪目标，make 会遍历所有隐式规则，尝试 clean.c、clean.o、clean.sh、RCS 与 SCCS 路径等一长串候选。声明为伪目标后这些搜索全部跳过，大项目里 make -d 的输出能少掉几千行。想彻底关掉，在 Makefile 顶部加 MAKEFLAGS += --no-builtin-rules --no-builtin-variables。

三是传染性，这条最容易反噬。伪目标永远被视为过期，所以任何以伪目标为依赖的真实文件目标，也会每次都被重建。把 version 之类的伪目标塞进 .o 的依赖里，增量构建就彻底失效了。需要「每次都检查但内容不常变」的语义时，正确做法是生成一个 stamp 文件，内容不变就不更新它的 mtime。

变量的四种赋值与展开时机

make 的执行分成两个阶段：读取阶段读入所有 Makefile、求值立即赋值的变量、记录规则（recipe 原文暂不展开）；执行阶段做时间戳判定，并在真的要执行某个 recipe 时才展开其中的变量和函数。赋值运算符的差别，本质上就是「在哪个阶段求值」。

运算符求值时机能否引用后面才定义的变量右侧含 shell 函数时执行几次该用在哪
= 递归展开每次被引用时展开能每次引用各执行一次值必须延迟到执行阶段才确定时
:= 立即展开读到该行时展开一次不能，取到空值一次默认首选，右侧有 shell 时尤其必要
::=与 := 等价不能一次需要 POSIX 兼容写法时
?= 条件赋值仅当变量未定义时，按递归展开语义赋值能同 =允许外部覆盖的默认值；已定义为空串时不会生效
+= 追加原变量是立即展开则立刻求值后追加；是递归展开则原文追加取决于原变量取决于原变量累积编译选项
!= shell 赋值读到该行时执行 shell 一次不能一次等价于 := $(shell ...)，GNU make 4.0 起

最实际的影响是性能。把 SRCS = $(shell find src -name '*.c') 写成递归赋值，之后每次引用 $(SRCS) 都会真的 fork 一个 find；在一个引用了十几次的 Makefile 里，这就是 make 明明什么都不做却要等两秒的原因。规则很简单：默认用 :=，只有确实需要延迟求值时才用 =。

变量来源优先级能否被 Makefile 内的赋值覆盖需要注意的地方
命令行 make VAR=x最高不能，除非用 override会自动通过 MAKEFLAGS 传给子 make
override VAR = x高—专门用来无视命令行传入值
Makefile 内的普通赋值中—同名变量后写的覆盖先写的
环境变量低能加 -e 后环境变量反而高于 Makefile，很少用但会造成诡异差异
目标专属变量 目标: VAR = x在该目标及其全部依赖中生效—「及其依赖」常被忽略，会串到多个目标共享的依赖上
内置默认值最低能-R 可以全部关掉，避免 CC 这类隐含值干扰

# 立即展开：读到这一行就求值一次，后面引用多少次都是同一个值
NOW_IMMEDIATE := $(shell date +%s)
# 递归展开：每次被引用都重新求值，下面 demo 目标里的三次引用会 fork 三个 date
NOW_LAZY       = $(shell date +%s)

# 递归赋值可以引用后面才定义的变量；把下面两行换成 := 会得到 "hello"
GREETING = hello $(NAME)
NAME     = world

# ?= 只在变量完全未定义时生效；若已被定义为空字符串，这一行不起作用
OPT ?= default

# += 的语义取决于原变量类型：原来是立即展开，追加的内容也立刻求值
CFLAGS := -O2
CFLAGS += $(EXTRA)      # $(EXTRA) 在此刻就被展开，此时若还没定义就是空

.PHONY: demo
demo:
	@echo "immediate: $(NOW_IMMEDIATE) $(NOW_IMMEDIATE) $(NOW_IMMEDIATE)"
	@echo "lazy     : $(NOW_LAZY) $(NOW_LAZY) $(NOW_LAZY)"
	@echo "greeting : $(GREETING)"

自动变量与模式规则

模式规则用 % 做通配：$(BUILD)/%.o: src/%.c 一条顶一百条。更安全的写法是静态模式规则 $(OBJS): $(BUILD)/%.o: src/%.c，它把规则的作用域限定在 $(OBJS) 这个明确的目标集合上，不会意外命中其他同后缀文件。模式规则链还会产生中间文件，make 默认在构建结束后删掉它们，需要保留就声明 .SECONDARY，否则每次都重建。

自动变量含义在规则 build/app: build/main.o build/net.o build/net.o 中的值常见误用
$@目标名build/app在模式规则里以为它是模式本身
$<第一个依赖build/main.o用在链接规则上，结果只链进第一个目标文件
$^全部依赖，自动去重build/main.o build/net.o用在编译规则上，把头文件也当源文件传给编译器
$+全部依赖，不去重、保持顺序build/main.o build/net.o build/net.o只有链接顺序敏感的库列表才需要它
$?所有比目标新的依赖随时间戳而变忽略了它的价值：增量归档就该写 ar r $@ $?
$*模式中 % 匹配到的部分仅在模式规则中有意义在显式规则里使用，多数情况下取到空值
$(@D) / $(@F)目标的目录部分 / 文件名部分build / app为了取目录去 recipe 里调 dirname，多一次进程

头文件依赖不要手写，交给编译器：加 -MMD 让它在生成 .o 的同时输出一份 .d 文件（里面就是一条 make 规则），再用 -include 把这些 .d 引进来。-MP 会额外为每个头文件生成一个空的伪目标，这样删掉某个头文件时不会报「没有规则可以制作目标」而是直接重建。这一组参数是并行构建不出偶发失败的前提。

# ---- 这五行决定整个 Makefile 的可靠性，值得逐条抄走 ----
SHELL := /bin/bash
# -e 任一命令失败立即退出；-u 引用未定义变量报错；pipefail 让管道中间失败也算失败
.SHELLFLAGS := -eu -o pipefail -c
# 命令失败时删掉写了一半的目标，否则下次 make 会把半成品当成最新
.DELETE_ON_ERROR:
# 关掉内置隐式规则与内置变量，省掉大量无用的文件试探
MAKEFLAGS += --no-builtin-rules --no-builtin-variables
.DEFAULT_GOAL := help

CC       := gcc
BUILD    := build
SRCS     := $(shell find src -name '*.c')
OBJS     := $(patsubst src/%.c,$(BUILD)/%.o,$(SRCS))
DEPS     := $(OBJS:.o=.d)
# -MMD 让编译器顺手输出头文件依赖，-MP 给头文件补伪目标避免删文件后报错
CPPFLAGS := -Iinclude -MMD -MP
CFLAGS   := -Wall -Wextra -O2 -g
LDLIBS   := -lpthread

.PHONY: help all clean
help:                                   ## 列出所有带说明的目标
	@grep -hE '^[a-zA-Z_-]+:.*?## ' $(MAKEFILE_LIST) \
	| awk -F':.*?## ' '{printf "  %-10s %s\n", $$1, $$2}'

all: $(BUILD)/app                       ## 构建可执行文件

$(BUILD)/app: $(OBJS)
	$(CC) $(CFLAGS) $^ -o $@ $(LDLIBS)

# 竖线后面是 order-only 依赖：只保证目录先存在，目录 mtime 变化不会触发重建
$(BUILD)/%.o: src/%.c | $(BUILD)
	$(CC) $(CPPFLAGS) $(CFLAGS) -c $< -o $@

$(BUILD):
	mkdir -p $(sort $(dir $(OBJS)))

clean:                                  ## 删除全部构建产物
	rm -rf $(BUILD)

# 把编译器生成的头文件依赖引进来；文件不存在时 -include 不报错
-include $(DEPS)

每行一个独立 shell：后果、SHELL 与 .ONESHELL

默认情况下 recipe 的每一行都由一个新的 shell 进程执行，命令行是 $(SHELL) $(.SHELLFLAGS) '这一行'，默认值是 /bin/sh -c。工作目录、shell 变量、函数一律不跨行。更隐蔽的问题是错误处理：-c 不带 -e，所以一行里用分号或管道串起来的多条命令，只有最后一条的退出码决定这一行成败，中间失败会被静默吞掉。

写法实际发生的事正确写法
一行 cd build，下一行 make第二行仍在原目录执行用 $(MAKE) -C build，不要用 cd
一行 X=1，下一行 echo $$X第二行输出空字符串同一行内用分号串联，或改用 make 变量
一行里写 a; b; c，SHELL 为默认值只有 c 的退出码算，a 和 b 失败被吞设 .SHELLFLAGS := -eu -o pipefail -c，或用 && 连接
cmd | tee build.log退出码取自 tee，cmd 失败被吞必须加 -o pipefail，并把 SHELL 指到 bash
声明 .ONESHELL:整个 recipe 交给一个 shell，cd 跨行生效需要 GNU make 3.82+；必须同时设带 -e 的 SHELLFLAGS，否则只看最后一行退出码
行首写 -忽略该行错误继续往下只用在 -rm 这类确实可忽略的场合
行首写 @不回显命令本身调试时用 make -n 仍能看到完整命令

补一个平台差异：macOS 系统自带的是 GNU make 3.81（因为许可证原因没有跟进），.ONESHELL 要 3.82、--output-sync 要 4.0、.WAIT 和 --shuffle 要 4.4。团队里有 macOS 开发机时，要么单独安装新版并统一用 gmake，要么在 Makefile 顶部检查 $(MAKE_VERSION) 直接报错，不要指望「本地能跑」。

并行 -j 与依赖声明不全

并行构建暴露的从来不是 make 的 bug，而是 Makefile 里本来就写错的依赖。串行执行时目标顺序由书写顺序隐式决定，恰好「先生成头文件再编译」；-j 打开后调度器只遵守显式声明的依赖，没声明的就可能并发，于是编译器读到一个只写了一半的生成文件。这类失败在 CI 里偶发、在本地永不复现，是最难查的一类构建问题。

开关 / 特殊目标最低版本作用不用的后果
-j N3.x同时运行 N 个作业构建慢；但依赖不全时 N 大于 1 就开始偶发失败
-j 不带数字3.x无限并发大仓库能把机器内存打爆，CI 里绝对不要这么写
--output-sync=target4.0按目标聚合输出并行日志交错，报错信息对不上是哪个目标
-l N3.x系统负载超过 N 时不再启动新作业与别的构建抢机器时把系统打满
.NOTPARALLEL:3.x整个 Makefile 强制串行发现竞争后无法快速止血
.WAIT4.4在依赖列表中插入一个屏障只能用中间伪目标模拟，写法更绕
--shuffle4.4随机化同级目标的处理顺序缺失的依赖只在 CI 偶发暴露，无法主动复现
$(MAKE) 调子 make3.x传递 jobserver，父子共享总并发额度写死 make 会丢掉 jobserver，子 make 退回单线程并告警
-MMD -MP 加 -include编译器侧自动维护头文件依赖改头文件不重编；生成的头文件在并行下被抢读
 
# 为什么这个目标会重建？--trace 打印触发原因和展开后的完整命令（GNU make 4.0+）
make --trace build/app

# 只看会执行什么，不真的执行；带 @ 前缀的命令也会被显示出来
make -n all

# 打印内部数据库：每个变量的最终值、生效的隐式规则、目标的时间戳判断
make -p 2>/dev/null | less

# 判定过程的完整日志，重点找 Considering / newer than / must remake 这几类行
make -d build/app 2>&1 | grep -E 'Considering|newer|remake'

# 主动暴露依赖声明不全：随机化同级目标顺序，配合清理反复跑
for i in $(seq 1 10); do make clean && make --shuffle -j"$(nproc)" || break; done

# 并行日志交错到看不懂时，按目标聚合
make -j8 --output-sync=target

# macOS 自带的是 3.81，上面一半开关都不支持，装新版并统一用 gmake
brew install make && gmake --version
# 让「编译参数变化」也能触发重建：把参数内容落成一个 stamp 文件
# 思路是内容不变就不更新 mtime，这样才不会每次都全量重编
FLAGS_TEXT  := $(CC) $(CPPFLAGS) $(CFLAGS)
FLAGS_STAMP := $(BUILD)/.flags
$(shell mkdir -p $(BUILD); \
        printf '%s' '$(FLAGS_TEXT)' | cmp -s - $(FLAGS_STAMP) \
        || printf '%s' '$(FLAGS_TEXT)' > $(FLAGS_STAMP))

# 把 stamp 加进依赖，改 CFLAGS 就会重编，改回去也会重编
$(BUILD)/%.o: src/%.c $(FLAGS_STAMP) | $(BUILD)
	$(CC) $(CPPFLAGS) $(CFLAGS) -c $< -o $@

判断只有一个标准：这些命令之间是否存在文件产物依赖，并且需要增量。如果没有，那么写一个全是伪目标的 Makefile 等于只用了 make 的「子命令入口」功能，却要承担展开时机、Tab、每行一个 shell 这些全部历史包袱，这笔交易不划算。

工具基于文件的增量给任务传参安装成本语法复杂度最适合的场景
GNU make有，基于 mtime只能 VAR=x，位置参数要拿 MAKECMDGOALS 变通Linux 普遍自带；macOS 自带 3.81 需另装高：展开时机、Tab、每行独立 shell真的存在产物依赖的构建
just没有，只有任务先后关系原生位置参数与默认值单二进制，需自行安装低项目命令入口，替代「全是伪目标的 Makefile」
Task（Taskfile.yml）有，声明 sources 与 generates，可按内容校验和判定原生 CLI 变量单二进制中，YAML 结构想要增量又不愿碰 make 语义
npm scripts没有用 -- 透传已有 Node 项目零成本低前端项目，不要再套一层 make
CMake + Ninja有，由生成器负责不适合当命令入口需安装，学习成本高高跨平台 C/C++ 的真实构建

最容易踩的坑

❌
这些坑都能稳定复现
  • recipe 用空格缩进：报 missing separator。用 cat -A 确认行首是 ^I，别信编辑器的显示。
  • 改了 CFLAGS 或换了编译器却不重建：make 只比时间戳，不看命令内容。把参数落成 stamp 文件并加进依赖。
  • 把输出目录写成普通依赖：目录 mtime 随内部增删变化，导致每次都重建。必须用竖线后面的 order-only 依赖。
  • 把伪目标写成真实文件目标的依赖：伪目标永远过期，会让那个文件目标每次都重建，增量彻底失效。
  • 忘了 .DELETE_ON_ERROR：命令中途失败留下写了一半的产物，下次 make 认为它已是最新，错误被固化，表现为「清理一下就好了」。
  • recipe 里用 cd 然后指望下一行还在那个目录：每行一个独立 shell。子目录构建用 $(MAKE) -C。
  • 一行里 a; b; c 不设 SHELLFLAGS：只有 c 的退出码算，前面失败被吞。设 .SHELLFLAGS := -eu -o pipefail -c。
  • cmd | tee log 没加 -o pipefail：cmd 失败但整行成功，构建「绿着」输出错误产物。
  • 开了 .ONESHELL 却没同时加 -e：整个 recipe 只看最后一行退出码，中间全挂也算成功。
  • 头文件依赖手写或干脆不写：改了头文件不重编，编出新旧混合的二进制。用 -MMD -MP 加 -include 交给编译器。
  • 并行构建偶发失败就改小 -j：这是掩盖不是修复。用 --shuffle 主动复现，把缺失的依赖补上。
  • 子目录里写死 make 而不是 $(MAKE)：丢掉 jobserver，子 make 退回单线程并打出 jobserver unavailable 告警，整体并发额度也失控。
  • SRCS = $(shell find ...) 用递归赋值：每次引用都 fork 一次 find，空跑一次 make 都要等几秒。改成 :=。
  • 目标专属变量以为只作用于该目标：它会传染到该目标的全部依赖，而依赖往往被多个目标共享，于是构建结果随入口目标而变。
  • 在 macOS 上用系统自带 make 写现代 Makefile：.ONESHELL、--output-sync、--shuffle 都不支持，本地静默降级、CI 上行为不一致。
  • 依赖同秒生成的文件做增量判定：部分文件系统时间戳精度只有一秒，时间戳相等不算过期，该重建的不重建。这类环境下宁可用内容校验和驱动的工具。
