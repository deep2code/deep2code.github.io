Markdown 语法

🏷️ Markdown

💡 你在工作中遇到了这个问题，查了很多资料还是没搞懂。或者你面试的时候被问到，答不上来。

Markdown 不是一种语言，是十种方言

我先泼一盆冷水：你以为的 Markdown 只有一种，其实没有「标准 Markdown」这回事。John Gruber 2004 年写的那份原始规范薄得像张纸，Github、Gitlab、CommonMark 各自扩展了...

这个博客就是从一堆 Markdown 文件渲染出来的。我吃够了方言不一致的苦，所以这篇主要讲「怎么写一份能在大多数地方都不翻车的 Markdown」。

先认清现实

别追求「完美 Markdown」，追求「跨渲染器不翻车」。GFM（GitHub Flavored Markdown）是事实上的最大公约数，你写的时候照着 GFM 的语法来，Github、GitLab、VS Code、大多数静态站都能正确渲染。那些渲染不出的花活，说明它不在 GFM 里。

2026 年 Markdown 界发生了什么

别以为 Markdown 是个没活力的老东西。这两年其实热闹得很，我挑几个和你日常相关的：

方向代表变化
渲染器Marked 17+ESM-only，Node 20+，速度更快
文档站主题MkDocs Material 9.7+AI 搜索、代码注释智能折叠、离线包
个人知识库Obsidian 1.9+Canvas 白板、Dataview 查询、插件生态
LLM 协作llms.txt专门给大模型读的 Markdown 清单
内容格式LLMs.md / .mdxMDX 直接在 Markdown 里嵌组件

我自己最常用的是 Obsidian + MkDocs 这条组合：日常笔记扔 Obsidian，需要对外发布的文档挑出来用 MkDocs Material 生成静态站。Obsidian 的 Dataview 让我能用类 SQL 语法查自己的笔记，这是纯 Markdown 文件本来做不到的事。

数学公式：LaTeX 终于不是黑魔法了

写技术文档的人迟早要写公式。现在主流渲染器都支持 KaTeX 或 MathJax，行内用 $...$，块级用 $$...$$：

行内公式：$E = mc^2$

块级公式：
$$
\int_0^\infty e^{-x^2} dx = \frac{\sqrt{\pi}}{2}
$$

但这里有个我被坑过的细节：GitHub 不支持 LaTeX 数学渲染（它只在部分讨论里支持），而 Obsidian 和 MkDocs 都支持。所以你写一份要同时发到 GitHub 和文档站的文档，公式在 GitHub 上会原样显示成 $$...$$ 源码。我的做法是：公式相关文档就专门走 MkDocs，不往 GitHub README 里塞公式。

渲染流水线：Markdown 到底怎么变成 HTML

理解这个流程能帮你定位「为什么我的语法没渲染」：

flowchart LR A[.md 源文件] --> B[词法分析 Tokenizer] B --> C[AST 抽象语法树] C --> D[渲染规则 Renderer] D --> E[HTML 字符串] E --> F[浏览器显示] G[插件扩展] -.影响.-> C

每一步出问题都有对应的症状：语法没生效是 tokenizer 不认，扩展语法不显示是 renderer 没配插件，显示乱了是 CSS 没接上。

MkDocs Material：我用过最省心的文档站

如果你要给一个项目写正经文档，别自己折腾静态站了，上 MkDocs Material。它的杀手锏是 MDC（Material Design Components）这种 admonition 扩展：

flowchart TD A[写 markdown 源文件] --> B[mkdocs serve 本地预览] B --> C{样式对不对?} C -->|不对| D[改 mkdocs.yml 和 docs] C -->|对| E[mkdocs build] D --> B E --> F[部署到 GitHub Pages / Vercel]

几个我天天用的语法：

# 信息块
!!! note
    这是一条提示。

# 警告块
!!! warning
    注意这个配置项。

# 折叠块
??? question "点我展开"
    这里是默认折叠的内容。

它还有个我特别喜欢的功能：代码块的智能复制和行号，以及「这个文件上次更新时间」自动从 git 读。对一个长期维护的开源文档站来说，这些是刚需。

Markdown vs 富文本 vs 纯 LaTeX

经常有人问「我该用哪个写文档」。我的答案完全取决于用途，下面这张表是我踩过坑后的总结：

维度Markdown富文本 NotionLaTeX
纯文本可 diff是，git 友好否，数据库是
上手成本低极低极高
排版精美度中中极高
协作靠 git实时协作好差
适合技术文档、博客轻量团队笔记论文、书籍

一句话：能进 git、能被 diff 工具读懂的写作，才是工程师的写作。Notion 那种好看但锁在数据库里的文档，我迟早会因为「迁移不出来」而焦虑。

我的几条实战习惯

  • 标题前后空一行：很多解析器要求标题行必须前一空行，否则当成段落；
  • 列表嵌套用两到四个空格，别混用 tab；
  • 代码块指定语言：写 ```python 而不是光秃秃的 ```，否则没高亮；
  • 脚注和锚点谨慎用：这俩跨渲染器差异最大，GitHub 和 Obsidian 行为不一样；
  • 表格别太宽：宽表在手机上直接翻车，超过 5 列就考虑拆。
llms.txt 值得了解

2026 年给网站加一个 llms.txt 正成为新风尚——它是一份纯 Markdown 清单，告诉大模型「这个站有哪些内容、该怎么爬」。我给博客加这个文件只花了十分钟，却能让 AI 搜索更准确地引用我的文章。

FAQ

Q：为什么我写的 Markdown 在 Obsidian 里好好的，发到 GitHub 就变样了？
因为方言不同。Obsidian 支持 Wiki 链接 [[文件名]] 和大量插件语法，GitHub 不认。如果你要双端发布，只用 GFM 子集：标题、列表、代码块、表格、引用、链接、图片。Obsidian 的 [[双向链接]] 就别指望 GitHub 认。

Q：Markdown 能代替 Word 写正式文档吗？
技术文档、内部 wiki、博客没问题。但要交付给不懂技术的甲方、要红头文件那种严格排版，还是得 Word/PDF。Markdown 的强项是纯文本可版本化，弱项是精细排版——别用错地方。

Q：MDX 是什么，要学吗？
MDX = Markdown + JSX，能在 Markdown 里直接嵌 React 组件。它把「文档」和「可交互 demo」合在一起，写组件库文档很爽（很多 UI 库官网就是 MDX）。但它需要构建工具链，纯写作场景用不上。

Q：2026 年 Markdown 会被 AI 写作用什么新格式取代吗？
短期不会。AI 生成内容反而推动了 Markdown——因为大模型最擅长输出的就是 Markdown，llms.txt、RAG 喂料全是 Markdown。它现在是「人机协作写作的公共格式」，这个地位反而更稳了。

小结

Markdown 的生命力在于「够简单、够纯文本、够通用」。它不完美，方言一堆，但你今天写的 .md 文件，十年后任何编辑器都能打开，这点比任何花里胡哨的富文本都值钱。下一篇 Mermaid，看怎么用文字把图画出来。
