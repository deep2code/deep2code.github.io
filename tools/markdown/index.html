Markdown 的方言差异与文档工程化

🏷️ Markdown

不存在「标准 Markdown」：三条谱系与分歧的来源

2004 年 John Gruber 发布的 Markdown 只有一份散文式说明和一个 Perl 脚本 Markdown.pl，没有形式化语法，连「列表项里缩进几格算子列表」这种基本问题都没定义。后来的所有方言都是在补这个洞，于是分成三条谱系：CommonMark 这一支给出了带 600 多条一致性测试的规范；GFM 这一支在 CommonMark 之上加了表格、任务列表、删除线、自动链接、原始 HTML 过滤等扩展；Pandoc 和 Python-Markdown 这一支基本不走 CommonMark，各自维护一套更庞大的扩展集合（定义列表、属性块、citation）。

这件事对工程的真正含义是：Markdown 不是数据格式，它是一组「源码到 HTML」的转换约定。约定不同，同一份字节流在不同渲染器下可以得到结构完全不同的 DOM。你把一份文档同时发到代码仓库、文档站、内网 wiki 和公众号，实际上是让四个编译器编译同一份源码，却从来没人给你看编译警告。

纠正一个过期结论

「GitHub 不支持数学公式」这个说法早就不成立了。GitHub 从 2022 年起在 Markdown 文件、issue、PR 里都支持行内美元符号和 math 代码围栏渲染公式。真正的坑变成了另一个：美元符号是普通字符，写「单价 $9 到 $12」会被当成公式定界符，整段文字被吞进斜体数学模式；而代码块和行内代码里的公式又完全不解析。所以问题从「能不能用」变成了「怎么防止误判」。

标题锚点：跨平台链接最隐蔽的断点

文档里的 [见配置章节](#配置-api_key) 是一条硬编码契约，而每个渲染器生成 ID 的规则都不一样。以 ## 1. 配置 API_KEY 这个标题为例：

GitHub / goldmark 默认转小写，删标点，空格转连字符，保留下划线与中日韩字符，重名追加序号1-配置-api_keyURL 里中文被百分号编码，复制到别处容易被截断

结论很直接：锚点是渲染器的实现细节，不要把它当稳定 API。需要稳定跳转就自己显式写 ID（属性块或一行 HTML 锚），并让链接检查器把「锚点存在性」纳入 CI。仓库里那种跨文件、跨仓库的 #小节标题 链接，是文档腐坏最快的地方。

静默错位：解析器差异不会报错，只会改结构

方言问题里最难查的一类是「渲染成功但结构错了」。这类问题不抛异常、不出警告，往往是别人截图给你看你才知道。

front matter：Markdown 之外的元数据契约

front matter 不属于任何 Markdown 规范，它是 Jekyll 带起来的约定：文件开头由三个连字符包裹的 YAML 块。不同工具的处理方式差别很大——Hugo 同时接受 YAML、TOML、JSON 三种；GitHub 会把 YAML front matter 渲染成一张表格显示出来；不认识它的渲染器会把第一行当成水平分割线，后面的键值对变成正文。所以把 front matter 当成文档的 schema 来治理比纠结语法更重要：

  • 字段即公共接口：模板、搜索索引、导航、RSS 都读它。改名、改类型、删字段都是破坏性变更，必须配迁移脚本，而不是「以后新文档用新字段」。
  • 日期与时区是重灾区：不加引号的日期被解析成日期对象，加引号是字符串，排序行为不同；不写时区的时间在 CI 容器里按 UTC 解释，可能让文章提前或延后一天上线。
  • 必填字段要在提交时校验，不要等构建失败。一个 20 行的校验脚本能省掉大量「线上标题空了」的事故。

文档即代码：把校验搬到提交与 CI

文档工程化的核心不是选工具，是把「人眼 review 才能发现的问题」变成可执行的失败条件。四类检查的职责边界要分清，混在一起跑会让 CI 变成噪音源。

name: docs
on: [pull_request]
jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      # 结构与风格：规则集进仓库，中文文档必须关掉行宽规则 MD013
      - run: npx --yes markdownlint-cli2 "docs/**/*.md"
      # 拼写：词典文件和文档一起 review，新词入库要有人签字
      - run: npx --yes cspell --no-progress --config .cspell.json "docs/**/*.md"
      # 链接：offline 只查相对链接和页内锚点，外链另开定时任务，避免被限流打断 PR
      - run: |
          docker run --rm -v "$PWD:/w" lycheeverse/lychee:latest \
            --offline --include-fragments --no-progress /w/docs

# 提交前的三条高性价比检查，放进 pre-commit
# 1) 中文行尾软换行：渲染后汉字之间会多出空格
rg -n --pcre2 '[\x{4e00}-\x{9fff}]$' docs --glob '*.md' | head -50

# 2) 页内锚点引用，交给链接检查器前先人工过一眼数量级
rg -no '\]\(#[^)]+\)' docs --glob '*.md' | wc -l

# 3) front matter 必填字段校验，不合格直接以非零退出码卡住提交
for f in $(git diff --cached --name-only --diff-filter=ACM -- '*.md'); do
  awk '/^---$/{n++; next} n==1' "$f" \
    | yq -e '.title and .date and .status' - > /dev/null \
    || { echo "front matter 不合格: $f"; exit 1; }
done

大文档的结构、图表与可移植子集

拆分要按「读者的任务」拆，不按字数拆；导航结构用显式的导航配置表达，不要靠标题层级自动推出十层目录。自动目录还有两个约束：它依赖前面说过的不稳定锚点，且深度超过三级基本没人看。

图表方面，文本即图的写法可以进版本控制、能 diff、能在 CI 里校验语法，这是它相对于截图的全部价值所在。Mermaid 的语法细节、渲染时机和常见报错在站内有专篇（见 Mermaid 一篇），几种文本绘图方案的取舍见站内的文本即图选型专篇，这里只强调一条与方言相关的事实：各平台对图表代码围栏的处理完全不同，GitHub 直接渲染 mermaid 围栏，多数文档站要装插件，而不认识的渲染器会把图定义当普通代码块原样显示——这决定了你的图是「无法渲染时退化成可读文本」还是「变成一大坨噪音」。

渲染用户提交的 Markdown：净化的是 HTML，不是源码

只要 Markdown 来自用户（评论、工单、AI 生成的内容），它就是不可信输入，而 Markdown 渲染器本身不是安全边界。三条最常被搞错的事实：

  • 关掉原始 HTML 只挡住了「语法层面的 HTML 透传」，链接目标里的 javascript: 伪协议、图片地址、自动链接功能凭空造出的标签都不在这个开关管辖范围内。
  • 在 Markdown 源码上做关键词黑名单（过滤 script 字样）是无效防护：大小写、实体编码、注释截断、属性换行都能绕过。唯一可靠的位置是渲染之后、插入 DOM 之前，对 HTML 做白名单净化。
  • 输出位置决定剩余风险。同一段「已净化」的 HTML，插入页面、塞进邮件模板、交给无头浏览器打印 PDF，威胁模型完全不同——最后一种还额外引入了本地文件读取和内网请求的风险面。XSS 的上下文编码规则与 SSRF 的判定在站内安全系列有专篇，这里不重复展开。

import MarkdownIt from 'markdown-it';
import createDOMPurify from 'dompurify';
import { JSDOM } from 'jsdom';

// html:false 只关闭源码里的原始 HTML 透传，
// 伪协议链接、图片地址、linkify 生成的标签都还需要后续净化
const md = new MarkdownIt({ html: false, linkify: true, breaks: false });
const DOMPurify = createDOMPurify(new JSDOM('').window);

export function renderUntrusted(src) {
  const raw = md.render(src);
  // 净化对象是渲染后的 HTML；在 Markdown 源码上做黑名单永远能被绕过
  return DOMPurify.sanitize(raw, {
    ALLOWED_TAGS: ['p', 'br', 'strong', 'em', 'del', 'code', 'pre', 'blockquote',
      'ul', 'ol', 'li', 'h2', 'h3', 'h4', 'a', 'img', 'table', 'thead',
      'tbody', 'tr', 'th', 'td', 'hr'],
    ALLOWED_ATTR: ['href', 'title', 'alt', 'src'],
    // 只放行 http https mailto，挡掉 javascript data vbscript file
    ALLOWED_URI_REGEXP: /^(?:https?|mailto):/i,
    FORBID_ATTR: ['style'],
  });
}

转换产线：到 HTML 和 PDF，以及中文排版

把 Markdown 转成交付物是另一条独立产线，失败模式和渲染差异无关，而与字体、分页、度量有关。

目标产物工具链中文字体处理代码块与长行主要失效点
静态 HTML站点生成器或自写渲染脚本交给 CSS 字体栈，注意 fallback 里要有系统中文字体预格式化块横向滚动，不折行中英文混排的行高与标点挤压需要额外 CSS，渲染器不管
PDF 走 LaTeXPandoc 加 XeLaTeX 或 LuaLaTeX必须指定 CJK 主字体，默认 pdfLaTeX 引擎直接报缺字代码块默认不自动换行，长行被裁掉，需要开 breaklines字体名在不同机器上不一致，CI 里要装字体或用容器固定
PDF 走无头浏览器Chromium 打印接口与网页一致，所见即所得用 CSS 控制换行，行为可预测分页控制弱，表格跨页与页眉页脚需要靠打印样式硬调；渲染不可信内容时有额外攻击面
Word 或 富文本渠道Pandoc 加参考模板由模板样式决定代码块样式需在模板里预先定义自定义容器、图表围栏全部丢失，只能降级成纯文本或图片

中文排版还有一个规范层面的细节：全角标点在规范里算标点字符，会参与强调标记两侧的界定判断，强调符号紧贴全角引号或书名号时容易失效，稳妥做法是让强调范围包含或完全避开标点。

❌
最容易踩的坑

1. 用制表符缩进列表：制表符按四列展开，同一份文件在不同编辑器里缩进语义不同，列表随机变代码块。
2. 在示例里嵌三反引号围栏：内层围栏被当成闭合，后面半篇文档全变代码。外层要用四个反引号或波浪号。
3. 中文正文为了行宽在句子中间换行：渲染后汉字之间多出空格，而且 diff 里看不出来。
4. 硬编码跨文件的中文标题锚点：换渲染器或改标题即断链，且 CI 不开锚点检查时永远发现不了。
5. MkDocs 默认 toc 配置下写全中文标题：锚点全部退化成下划线加序号，改任一标题会导致全站锚点整体错位。
6. 正文里写美元金额：在支持公式的渠道上被当成数学定界符，整段被吞进公式模式。
7. 把链接引用定义写在列表项或引用块里：定义不生效，链接原样输出方括号。
8. 在 div 等 HTML 容器里混写 Markdown：CommonMark 不解析容器内的 Markdown，星号和列表按字面输出。
9. 以为关掉原始 HTML 就等于安全：伪协议链接与自动链接不受这个开关约束，必须对渲染后的 HTML 做白名单净化。
10. 在 Markdown 源码上做关键词过滤当作 XSS 防护：编码变形与属性换行都能绕过，纯属自我安慰。
11. 把外链检查和站内链接检查放在同一个 CI 步骤：外链被限流返回 403 让 PR 无故变红，最后所有人加 continue-on-error，站内断链也跟着漏过。
