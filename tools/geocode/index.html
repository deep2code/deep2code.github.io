地理编码与地图服务的数据边界

🏷️ 开发工具与效率

地理编码是模糊匹配，不是查表

把地理编码当成「输入地址、查出坐标」的字典查询，是后面所有麻烦的起点。它的真实形态是：把一段自然语言拆成行政层级与要素，在一个不完整、有歧义、还在持续变化的地名与门址库里召回候选，打分排序，然后返回一个最可能的答案加上它自己对这个答案的信心。既然是打分，就必然有次优解被选中的情况。

三类结构性问题因此永远存在。同名：几乎每个城市都有人民路、中山路、第一人民医院，缺少城市或区级约束时，打分只能靠热度猜，猜错的表现就是坐标落在另一个城市。区划变化：撤县设区、街道合并、门牌重排都在持续发生，去年入库的地址文本今年可能已经匹配不到，历史订单里的区划名与编码也不再有效，所以地址表要存快照而不是只存引用。门牌不存在：小区内部楼栋、新建项目、虚拟门牌在库里没有对应点，服务会按门牌区间在路段上插值，坐标落在路上而不是楼里，误差可以是整条街长度的一部分。

粒度与置信度：必须按 level 分流

各家返回结构的字段名不同，但语义大同小异：都会告诉你这次命中的是门牌、插值、几何中心还是近似区域，以及是否只是部分匹配。业务代码里最危险的写法是无视这些标识，统一取坐标用。

返回粒度典型成因误差量级业务应有的处置
门牌 / 楼栋级门址库里有精确点米到十米可直接用于配送、上门、计费
门牌区间插值门牌号不存在，按路段区间线性推算十米到数百米，取决于路段长度可下单但必须让用户在地图上拖动确认
道路 / 交叉口级只解析出道路，没有有效门牌数百米要求补充门牌或选择附近参照物，不要进入配送计算
POI 名命中匹配到兴趣点而不是地址取决于 POI 本身的点位质量核对 POI 的城市与类型，防止同名 POI 跨城市命中
行政区级只解析出省市区公里级只能用于统计与分区，禁止用于任何位置判定
部分匹配标志为真输入里有服务无法解释的成分不确定无论粒度如何都走人工或用户确认分支

逆地理编码也有同样的问题，只是方向相反：同一个坐标在不同粒度下会给出完全不同的答案，可能是某个 POI 名，也可能是「某街道」。如果展示层不固定粒度，用户会看到地址描述在刷新之间跳变。固定粒度、必要时自己做后处理拼装，比直接展示服务返回的格式化地址更稳。

坐标系：偏移是系统性的，不是精度问题

坐标系混用造成的错位有一个很好认的特征：整批点朝同一个方向偏移，且偏移量随位置缓慢变化。它不是随机误差，不会通过「提高精度」缓解。这类问题在跨系统集成时特别容易出现——定位 SDK、地图底图、第三方地理编码、历史数据库四个来源用了三种坐标系。

坐标系谁在用与卫星定位原始坐标的关系转换特性混用时的症状
WGS84卫星定位输出、开放街图、多数境外服务就是它本身基准坐标，无需转换直接画在国内底图上，整体偏移
GCJ-02国内主流地图底图与地理编码服务在 WGS84 上施加非线性偏移转换算法非公开，工程实现都是近似，往返会有米级残差把它当卫星坐标做距离计算，短距离影响小，与其他来源比对就会系统性错位
BD09某一家国内服务的输出在 GCJ-02 之上再叠一层偏移需要两级转换，误差叠加与其他国内服务的点位互相错开
Web 墨卡托投影坐标瓦片渲染与前端像素计算由经纬度投影而来投影可逆，但高纬度面积严重放大拿投影后的米值当真实距离，纬度越高错得越多
境外区域各家处理不一致不能假设与境内规则相同必须按区域实测跨境业务在境外段出现整体偏移或不偏移，两种都见过

工程上的三条硬规则。第一，存储只存一种坐标系，并且额外存一列来源标记，转换只发生在出口处；混着存早晚会出现分不清的历史数据。第二，不要把一家的坐标叠到另一家的底图上，这既是坐标系问题也是授权问题。第三，转换不是无损的，不要在业务流程里反复来回转，每次都在累积残差，尤其别把转换结果再写回原字段。

精度、截断与存储类型

小数位数纬度方向对应距离能表达的粒度适用场景
2 位约 1.1 公里城市片区热力图、区域统计
3 位约 110 米街区粗粒度聚合、隐私降级后的留存
4 位约 11 米楼栋配送地址够用的下限
5 位约 1.1 米门口、单元入口精细导航与轨迹
6 位约 0.11 米超过消费级定位本身的精度存储保留，展示不必给
7 位及以上厘米级只有测绘级设备能达到业务系统里通常是噪声

经度方向的每度距离要乘以纬度的余弦，在北纬四十度附近大约是纬度方向的百分之七十七，越靠近极地越小。这直接影响两件事：用固定的经纬度差做矩形粗筛时，经度方向的阈值必须按纬度换算；用「度」当半径调用只认平面单位的函数时，结果在高纬度会明显偏窄。

存储类型是另一个高频事故点。单精度浮点存不下经纬度：它的有效十进制位数只有七位左右，经度整数部分吃掉三位，小数只剩四位，等于强行把精度截到十米量级，而且每次读写往返都在制造抖动。正确选择是双精度浮点、定点小数，或者数据库的空间类型。

-- PostGIS：用 geography 类型存点，距离与半径的单位直接是米
-- 用 geometry(4326) 也可以，但那时候半径参数的单位是「度」，是经典错误来源
CREATE TABLE delivery_address (
    id           bigserial PRIMARY KEY,
    user_id      bigint      NOT NULL,
    raw_text     text        NOT NULL,      -- 用户原始输入，永远保留
    norm_text    text        NOT NULL,      -- 归一化后的地址，缓存键就用它
    -- 坐标只存一种坐标系，来源用单独一列标记，出口处再转换
    geog         geography(Point, 4326),
    srs          text        NOT NULL,      -- wgs84 / gcj02 / bd09
    match_level  text        NOT NULL,      -- rooftop / interpolated / street / area
    partial      boolean     NOT NULL DEFAULT false,
    -- 区划快照：只存引用会被区划调整打穿，必须存当时的名称与编码
    adm_code     char(12),
    adm_snapshot jsonb,
    provider     text        NOT NULL,
    data_version text        NOT NULL,
    created_at   timestamptz NOT NULL DEFAULT now()
);

-- GiST 是 R 树家族的索引，支持任意多边形相交与近邻查询
CREATE INDEX idx_addr_geog ON delivery_address USING gist (geog);

-- 注意构造顺序是「经度在前、纬度在后」，与人读的「纬度,经度」相反
-- ST_DWithin 在 geography 上走索引，单位是米；这一步只做粗筛
SELECT id, norm_text, match_level,
       ST_Distance(geog, ST_MakePoint(116.4074, 39.9042)::geography) AS straight_m
FROM   delivery_address
WHERE  match_level IN ('rooftop', 'interpolated')
  AND  ST_DWithin(geog, ST_MakePoint(116.4074, 39.9042)::geography, 3000)
ORDER  BY straight_m
LIMIT  50;
-- 粗筛结果必须再交给路径规划服务算路网距离，直线距离不能作为配送判定依据

距离计算：选错方案的代价是系统性偏差

方案误差来源相对开销可用场景明确不可用于
平面近似（按纬度缩放经度）忽略曲率，随距离变大迅速失准最低同城小范围排序、粗筛跨城市、跨纬度带的比较
球面（半正矢公式）把地球当正球，忽略扁率，相对误差在千分之几量级低绝大多数业务距离展示与粗筛测绘、长距离精算
椭球（大地主题解算）迭代收敛问题，近对径点需特殊处理高需要精确距离的测量场景高频在线调用
投影后平面距离投影本身的变形，墨卡托在高纬度放大明显低小范围内、且已按当地选好投影带跨大范围、直接用瓦片坐标算米
路网距离与时长路网数据新鲜度、路况模型需要外部服务调用配送范围判定、计费、时效承诺高并发全量计算，必须先粗筛

真正要强调的不是公式差异，而是直线距离与路网距离之间没有稳定比值。河流、铁路、高架、封闭园区、单行线都会让同样的直线距离对应完全不同的实际路程。把绕路系数写成一个全局常数，等于在有水系或大型园区的城市里系统性地低估距离。可行做法是：直线距离只用于索引层粗筛与结果排序，判定与计费一律用路网结果；确实需要估算时，按城市与时段统计标定系数，并给出上限保护。

地理围栏：包含判断的退化情况

点在多边形内的判断本身很简单，射线法几行代码就能写出来。工程上出问题的从来不是主路径，而是退化情况和坐标质量。

stateDiagram-v2 [*] --> 围栏外 围栏外 --> 疑似进入: 命中内缩边界一次 疑似进入 --> 围栏外: 定位精度不足或连续命中中断 疑似进入 --> 围栏内: 连续命中达到阈值 围栏内 --> 疑似退出: 落在外扩边界之外一次 疑似退出 --> 围栏内: 重新落回内部 疑似退出 --> 围栏外: 连续未命中达到阈值 note right of 疑似进入 直接用原始边界判定会在边界附近反复抖动 进入用内缩边界 退出用外扩边界 形成滞回 end note 
import math

# 射线法：判断点是否在多边形内。注意三件事：
# 1) 顶点顺序用 (经度, 纬度)，与人读的「纬度,经度」相反，这是最常见的低级错误
# 2) 顶点与边上的点是退化情况，必须显式约定算内还是算外，不能交给浮点运气
# 3) 带孔洞的围栏要拆成外环与内环，点在外环内且不在任何内环内才算命中
def point_in_ring(lng, lat, ring):
    inside = False
    n = len(ring)
    for i in range(n):
        x1, y1 = ring[i]
        x2, y2 = ring[(i + 1) % n]
        if min(y1, y2) < lat <= max(y1, y2) and y1 != y2:
            x_at = x1 + (lat - y1) * (x2 - x1) / (y2 - y1)
            if x_at > lng:
                inside = not inside
    return inside

def point_in_polygon(lng, lat, outer, holes=()):
    if not point_in_ring(lng, lat, outer):
        return False
    return not any(point_in_ring(lng, lat, h) for h in holes)

# 带滞回的围栏状态机：定位噪声会让边界附近的点反复进出，
# 直接把每次判定当事件会产生大量误触发。
class FenceTracker:
    def __init__(self, enter_hits=3, exit_hits=3, max_accuracy_m=50.0):
        self.state = 'outside'
        self.enter_hits, self.exit_hits = enter_hits, exit_hits
        self.max_accuracy_m = max_accuracy_m
        self.streak = 0

    # buffered_in 用内缩边界判定，buffered_out 用外扩边界判定
    def feed(self, inside_shrunk, inside_expanded, accuracy_m):
        # 精度太差的点直接丢弃，否则噪声会驱动状态机
        if accuracy_m is None or accuracy_m > self.max_accuracy_m:
            return self.state
        if self.state == 'outside':
            self.streak = self.streak + 1 if inside_shrunk else 0
            if self.streak >= self.enter_hits:
                self.state, self.streak = 'inside', 0
        else:
            self.streak = self.streak + 1 if not inside_expanded else 0
            if self.streak >= self.exit_hits:
                self.state, self.streak = 'outside', 0
        return self.state

除了抖动，还有几个必须显式处理的情况：自相交多边形在射线法下结果无意义，入库前要做有效性校验；跨一百八十度经线的围栏在经度上会被算成绕地球一圈；大范围围栏的边到底是大圆弧还是等角线，不同实现的答案不同，跨度上百公里时差异可见；相邻围栏共享边界时，必须约定边界归属，否则会出现「两个围栏都不包含」或「都包含」的点。

地理索引：查询形态决定选型

索引原理擅长的查询边界弱点
GeoHash 前缀经纬度交错编码成字符串，公共前缀越长越接近等值分桶、按前缀聚合、纯键值存储里的近邻粗筛相邻点可能没有公共前缀，必须补查周围八个格；格子宽度随纬度变形
S2 单元球面上做希尔伯特曲线编码，单元有层级用单元集合覆盖任意区域，做区域包含与近邻需要额外库支持，覆盖计算本身有开销；层级选择要按业务尺度调
R 树（PostGIS 的 GiST）层次化外接矩形任意多边形相交、最近邻、范围查询更新与膨胀有成本；高维或大量重叠矩形时退化
有序集合上的整数编码（Redis 的地理命令）把编码后的整数当分值存在有序集合里热点数据的半径查询与排行只支持点，不支持多边形；持久化与容量受内存限制
网格分片（自定义方格键）按固定尺寸切格，格号当分片键写入量极大的轨迹类数据格子边界上的查询要扩边；热点城市会造成分片倾斜

索引的具体建法与执行计划判读不在本文展开，站内已有更细的内容：关系库的空间与函数索引见 database/postgresql/index-optimize/，索引设计的通用取舍见 database/design/index-design/，内存态地理集合的结构见 database/redis/。这里只给结论：查询形态决定索引——只做半径查询用编码类索引最省，凡是涉及任意多边形，就必须上 R 树一类的空间索引。

批量、缓存与合规边界

批量地理编码的瓶颈通常不在吞吐，而在缓存命中率和结果的可信度管理。命中率低的第一原因是缓存键没有归一化：同一个地址的全半角、空格、括号写法、别名差异都会各自占一个键。

sequenceDiagram participant U as 客户端 participant A as 业务服务 participant C as 缓存 participant G as 地理编码服务 participant R as 路径规划服务 U->>A: 提交地址文本与所选城市 A->>A: 清洗 归一 生成缓存键 A->>C: 按归一文本与数据版本查询 C-->>A: 命中则返回坐标 粒度 与来源坐标系 A->>G: 未命中才请求 并带上城市约束 G-->>A: 坐标 粒度 是否部分匹配 A->>C: 写入正结果 或写入短时负结果 A->>A: 按粒度分流 区域级直接要求补全 A->>R: 门牌级才去算路网距离与时长 R-->>A: 路径距离与预计时长 A-->>U: 返回可确认的点位与配送判定 Note over A,C: 归一化不做好 缓存键会分裂 命中率上不去
缓存维度正确做法做错的后果
键的构成归一化地址 + 城市约束 + 服务方标识 + 数据版本少了城市约束会把跨城市误匹配固化；少了版本号则数据更新后永远读到旧值
归一化全半角统一、空白压缩、括号与分隔符统一、常见别名映射同一地址分裂成多个键，命中率上不去，调用量虚高
负缓存查不到也要缓存，但存活时间明显短于正结果不做会让错误地址反复打到上游；做成长存活会把「暂时查不到」变成永久失败
失效触发行政区划调整、服务方数据版本变更、模板或业务规则变更时主动作废撤县设区之后旧结果继续生效，区划统计与路由全错
失败处理区分「服务不可用」与「地址无法匹配」，前者退避重试，后者交互补全把无法匹配当故障重试，浪费配额还阻塞用户
合规边界按服务条款限制留存范围与时长，不把缓存沉淀成自有地址库，不跨服务方混用底图与坐标越界使用属于授权与法律风险，不是技术问题能兜住的
 
import hashlib
import re
import unicodedata

CITY_SUFFIX = ('市', '自治州', '地区', '盟')

# 缓存键归一化：目标是让「同一个地址的各种写法」落到同一个键上。
# 不做这一步，缓存键会按输入的排版方式分裂，命中率永远上不去。
def cache_key(raw, city, provider, data_version):
    t = unicodedata.normalize('NFKC', raw)      # 全角转半角，兼容字符归一
    t = re.sub(r'\s+', '', t)                   # 中文地址里的空格没有语义
    t = t.replace('（', '(').replace('）', ')')
    t = re.sub(r'[,，;；]+', ',', t)
    t = re.sub(r'([省市区县镇乡街道])\1+', r'\1', t)   # 去重复行政后缀
    city_norm = city.rstrip(''.join(CITY_SUFFIX)) if city else ''
    payload = '|'.join((provider, data_version, city_norm, t))
    # 键里必须带服务方与数据版本，否则上游数据更新后旧结果会一直命中
    return 'geo:' + hashlib.sha256(payload.encode('utf-8')).hexdigest()[:32]

# 按粒度分流：把「拿到坐标」和「可以用这个坐标」分开，是这一层的核心。
AUTO_OK = {'rooftop'}
NEED_CONFIRM = {'interpolated', 'street', 'poi'}

def decide(result):
    if result.get('partial'):
        return 'user_confirm'
    level = result.get('level')
    if level in AUTO_OK:
        return 'auto'
    if level in NEED_CONFIRM:
        return 'user_confirm'
    return 'reject'          # 行政区级或未知粒度，不允许进入配送计算

坐标数据的隐私处理

坐标一旦能关联到具体的人，它就是个人信息，而且是还原性极强的一类：一个人的居住点与工作点组合起来，在人群中几乎是唯一的，去掉姓名手机号并不等于匿名化。工程上有几条可落地的原则。

按用途选精度。做区域统计只需要网格级，把小数位截断到三位就相当于做了百米级网格化，再配合每格最小样本数的门槛，能显著降低再识别风险。配送履约确实需要米级，那就把高精度坐标限制在履约链路里，分析链路只拿降级后的数据。

分离存储与最小留存。精确坐标与身份标识分表存放，用不可逆的映射关联，访问留审计；轨迹类数据按业务需要设定留存期并自动清理，不要无限期堆在日志里。日志尤其容易出事——把用户标识和完整坐标打在同一行，等于给自己造了一份无访问控制的位置数据库。

出口处再降级。返回给前端、写入分析库、导出给第三方时，各自按需要的最低精度截断；不要用「反正内部系统」当理由传递完整精度。这一条和前面的存储规则并不矛盾：存储层保留精度，出口层控制暴露。

❌
最容易踩的坑

1. 把地理编码当查表用，忽略返回结构里的粒度与部分匹配标志——区域级坐标被当门牌用，配送范围判定从此不可信。

2. 用单精度浮点存经纬度——有效位数不够，小数只剩四位，直接引入十米量级的固定误差。

3. 混着存多种坐标系又不记来源——数据一旦混进历史表，事后无法分辨，只能整体重新地理编码。

4. 把一家的坐标叠到另一家的底图上——偏移方向一致的整体错位，而且通常也不符合授权条款。

5. 反复来回做坐标系转换——转换是近似且不可精确还原的，来回几次残差就累积到米级以上。

6. 顶点顺序写成「纬度在前」——多数空间函数与数据交换格式都是经度在前，写反之后点会落到地球另一侧。

7. 在只认平面单位的类型上传「米」当半径参数，或在按米计算的类型上传「度」——两种都会得到量级完全错误的结果。

8. 用固定的经纬度差做矩形粗筛——经度方向每度距离随纬度收缩，同一个阈值在不同纬度筛出的范围不一样。

9. 用直线距离判定配送范围或计费——河流、高架、封闭园区让绕路系数在城市内部就差异巨大，没有稳定比值可用。

10. 围栏判断不做滞回——定位噪声让边界附近的点反复进出，产生大量误触发事件。

11. 忽略自相交、含孔洞、跨经线、点落在边上这些退化情况——射线法在这些输入上给出的答案没有意义。

12. 缓存键不归一化、不带数据版本——命中率上不去，而且区划调整后旧结果永远读得到。

13. 把查不到的地址当服务故障不停重试——应该短时负缓存加交互补全，而不是把配额烧在无效地址上。

14. 日志里同时打用户标识与完整坐标——等于造了一份没有访问控制的位置数据库，去标识也救不回来。
