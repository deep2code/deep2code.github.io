D3 的数据绑定模型与使用边界

🏷️ 代码生图

D3 不是图表库，是一组映射原语

把 D3 和 ECharts、Chart.js 放在一起比「哪个图表多」是分类错误。D3 里没有「图表」这个概念，它提供的是从数据到 DOM 的一串原语：怎么把数据域折成像素、怎么把数组变成 path 字符串、怎么把节点边表算出坐标、怎么把一个数组和一组 DOM 元素对齐。图表是你用这些原语拼出来的结果。

模块组输入输出明确不负责的事
数据装载与整形URL、文本、数组数组、分组 Map、分箱结果任何绘制
编码（scale、interpolate、format）数据域与值域一个纯函数不知道自己被画在哪，不持有 DOM
几何生成（shape、geo）数据数组或 GeoJSONpath 字符串或 canvas 指令不创建元素
布局计算（hierarchy、force、sankey）节点与边把坐标、角度写回节点对象不创建元素，不管你用 SVG 还是 Canvas
DOM 层（selection、transition、axis）选择集与数据真实 DOM 变更不管数据语义，不做聚合
交互（drag、zoom、brush）指针事件变换矩阵与选区范围不管你拿变换去做什么

这张表解释了 D3 的学习成本为什么高：你要同时做「编码设计」和「DOM 生命周期管理」两件事，而配置驱动的库把后者全吃掉了。也解释了它的上限为什么高：这几层之间没有隐式约定，你可以只用比例尺配 Canvas，也可以只用布局模块把坐标喂给 React。

data 到底做了什么：__data__ 与 key

selection.data(values, key) 做的是集合对齐：把一个数组和一组 DOM 元素配对，配不上的分成两边。配对结果直接写在元素的 __data__ 属性上，这是 D3 唯一的「状态存储」。

sequenceDiagram participant Code as 渲染函数 participant Sel as selectAll 选择集 participant Join as data 绑定 participant Dom as 真实 DOM Code->>Sel: selectAll 匹配现有元素 Sel->>Join: 传入新数组与 key 访问器 Join->>Join: 对每个现有元素的 __data__ 算一次 key Join->>Join: 对每条新数据算一次 key Join-->>Code: update 分组 键在两边都有 Join-->>Code: enter 分组 键只在数据里 Join-->>Code: exit 分组 键只在元素上 Code->>Dom: enter 追加 update 改属性 exit 删除 Code->>Dom: 合并后调用 order 对齐数据顺序

三条容易被忽略的语义：selectAll 不继承父级数据，select 会把父级的 __data__ 传播给子元素；datum() 只设值不参与对齐；key 函数会对两边各调一次，且返回值被强制转成字符串。

key 写法匹配依据后果
省略数组下标数据重排或中间插入一条后全体错位，视觉上是「值突然跳变」而不是「元素移动」
d => d.id业务主键正确写法
d => d对象被转成字符串，全都一样所有数据塌缩到同一个键，最后只剩一个元素
key 每轮都变（随机值、时间戳）每次都是新键每轮全量删除重建，过渡完全失效，性能也最差
数据里存在重复 key第二条匹配不到可用元素重复数据落进 enter，重复元素落进 exit，元素数量虚增或被反复删建
key 返回 undefined 或空转成同一字符串与第三行同样塌缩，且没有任何报错

join 的语义与退出竞态

selection.join(enter, update, exit) 不是新机制，是三段式的封装：默认在 enter 上追加元素、在 exit 上删除元素，最后把 enter 与 update 合并并调用 order()，让 DOM 顺序和数据顺序一致。手写 enter().append().merge() 时最常漏的就是 order()，症状是新元素永远叠在最上层。

还有一条陷阱：一旦你传了自定义的 exit 回调，自动删除就不再发生，必须自己调 remove()。而只要 exit 带了过渡，就会出现竞态——元素还在淡出，下一批数据到了，selectAll 又把它选中当成 update。解法是给退出中的元素打标记并在选择时排除。

// 稳定 key 是一切的前提：必须是业务主键，且能安全转成字符串
const key = d => d.id;

function render(rows) {
  svg.selectAll('circle.node:not(.exiting)')   // 排除正在淡出的元素，避免退出竞态
    .data(rows, key)
    .join(
      enter => enter.append('circle')
        .attr('class', 'node')
        .attr('r', 0)
        .attr('cx', d => x(d.t))
        .attr('cy', d => y(d.v)),
      update => update,                        // 显式写出来，提醒自己这一组不会自动改属性
      exit => exit
        .attr('class', 'node exiting')         // 打标记，下一轮选择集用 not 排除掉
        .transition('fade').duration(200)      // 命名过渡，不会和下面的 move 互相打断
        .attr('r', 0)
        .remove()                              // 传了 exit 回调就必须自己删
    )
    // join 返回的是 enter 与 update 的合并结果，顺序已经 order 过
    .transition('move').duration(400)
    .attr('r', 4)
    .attr('cx', d => x(d.t))
    .attr('cy', d => y(d.v));
}

scale 是纯函数，axis 是渲染器

比例尺是一个带附加方法的函数：给值返回像素，invert 反向，ticks 给刻度建议。它不持有 DOM，也不知道自己被画在哪。坐标轴是另一回事：d3.axisBottom(scale) 返回一个渲染函数，你 call 它时它读一次当前的 scale 状态并生成刻度元素。这个职责分离带来两个必然结论：改了 domain() 必须重新 call(axis)，而 nice() 会修改 domain，所以必须在 call 之前调用。

比例尺有 invert有 ticks典型误用
scaleLinear、scaleTime、scalePow有有默认不 clamp，越界值会被外推到绘图区之外，看起来像数据丢了
scaleLog有有domain 含 0 或跨越 0 时结果非法，日志类指标要先做偏移或改用 symlog
scaleBand无无对它调 axis.ticks 完全无效，只能用 tickValues 自己抽稀；brush 反查类目要手算
scalePoint无无当 band 用会发现 bandwidth 恒为 0，柱子宽度变成 0
scaleOrdinal无无不显式给 domain 时按出现顺序隐式扩展，两次渲染配色不一致
scaleQuantize、scaleQuantile、scaleThresholdinvertExtent无分位数尺依赖全量分布，增量更新必须整体重建

元素数量与渲染成本：什么时候必须转 Canvas

「SVG 超过一万个元素就卡」这种说法太粗。成本不只看数量，还看元素类型：文本要排版和测量，滤镜与半透明会产生额外合成，描边比填充贵，transform 动画与属性动画走的路径也不一样。真正的判据是另一个问题：你还需不需要浏览器替你做命中测试和样式计算。需要，就留在 SVG；不需要，转 Canvas 立刻省掉整棵 DOM 树。

维度SVGCanvas混合：数据层 Canvas 加标注层 SVG
可交互的元素量级（经验值）数千个简单图元十万级可接受数据层不受限，标注层保持在百级
命中测试浏览器负责，事件直接落到元素自己建四叉树，或用离屏画布做颜色索引数据层自己算，标注层用原生事件
过渡d3-transition 直接插值属性自己在逐帧回调里插值并全量重绘标注层仍可用 d3-transition
文本与字体原生排版，可选中可复制需要自己测量，不可选中文本全部放 SVG
导出天然矢量，可直接给印刷位图，放大即糊要分别导出再合成
可访问性可加 title 与 aria 属性没有结构，需要额外提供数据表结构信息放 SVG
设备像素比浏览器处理必须手工乘进画布尺寸只需处理 Canvas 那一层
 
// Canvas 只有一个 DOM 节点：dpr 要自己处理，命中测试要自己建索引
const dpr = Math.min(window.devicePixelRatio || 1, 2);
canvas.width = width * dpr;
canvas.height = height * dpr;
canvas.style.width = width + 'px';
canvas.style.height = height + 'px';
const ctx = canvas.getContext('2d');
ctx.scale(dpr, dpr);        // 之后所有坐标都用 CSS 像素，和比例尺的输出直接对齐

function draw(points) {
  ctx.clearRect(0, 0, width, height);
  ctx.fillStyle = 'steelblue';
  ctx.beginPath();          // 同色同半径的点合成一个 path 一次提交，比每点一次 fill 快得多
  for (let i = 0; i < points.length; i++) {
    const cx = x(points[i].t), cy = y(points[i].v);
    ctx.moveTo(cx + 2, cy);
    ctx.arc(cx, cy, 2, 0, Math.PI * 2);
  }
  ctx.fill();
}

// 把每次 mousemove 的全量遍历换成四叉树局部搜索
const tree = d3.quadtree().x(p => x(p.t)).y(p => y(p.v)).addAll(points);
canvas.addEventListener('mousemove', (event) => {
  const [mx, my] = d3.pointer(event);   // v6 起事件对象从回调参数拿，没有 d3.event
  const hit = tree.find(mx, my, 8);     // 半径必须给，否则永远能找到一个「最近点」
  hit ? showTooltip(hit) : hideTooltip();
});

过渡是调度器，不是动画库

d3-transition 的模型是「每个元素、每个过渡名字」一条调度记录，统一由一个逐帧定时器驱动。理解它的状态机才能解释那些「过渡有时不生效」的现象。

stateDiagram-v2 state "created 已创建" as C state "scheduled 已入调度" as S state "starting 触发 start" as ST state "running 逐帧插值" as R state "ended 触发 end" as E state "interrupted 触发 interrupt" as I [*] --> C C --> S: 同元素同名的旧过渡被取消 S --> ST: 到达 delay ST --> R: 计算 tween 起点与插值器 R --> E: 已用时间超过 duration R --> I: 同元素上又启动了同名过渡 S --> I: 调用 selection interrupt E --> [*] I --> [*]

三个常被误判的现象：未命名过渡共用同一个空名字，所以两段看似无关的代码会互相打断；标签页切到后台时逐帧回调停止而时间基准继续走，切回来时已经超时，过渡直接落到终点；transition.end() 返回的承诺在过渡被中断时是 reject，不捕获就是一条未处理拒绝。另外插值器是按类型猜的，d 属性按字符串里的数字逐个对齐插值——两个路径段数不同时会插出乱线，这种情况要用 attrTween 自己写。

布局模块各自解决什么问题

布局模块的共同点是「只算不画」：输入节点与边，输出写回坐标或角度，画不画、画成什么由你决定。它们的差异在于求解方式，这决定了失效条件。

模块解决的问题用前必须做常见失效
d3-force没有天然坐标的关系数据求可读布局，迭代求解传入副本；给 forceLink 指定 id 访问器它会就地改写你的对象：给节点写入坐标与速度，把边的端点从 id 换成节点引用
d3-hierarchy 的 treemap 与 pack层级数据的面积编码先 hierarchy 再 sum，需要排序时先 sort漏掉 sum 时所有面积为 0，画出来一片空白且不报错
d3-hierarchy 的 tree 与 cluster层级数据的连线布局在 size 与 nodeSize 之间选一个用 size 时整棵树被压进固定框，深树节点重叠
d3-geo球面坐标到平面，含裁剪与重采样选投影并用 fitExtent 套进视口GeoJSON 多边形绕行方向反了会填满整个球面
d3-shape数据数组到 path 字符串选 curve 与 defined 断点判定用会过冲的曲线画非负指标，曲线探到 0 以下
d3-chord 与 d3-sankey流量与关系的带状表达先构造矩阵或节点边表带环的数据让桑基无法分层，需要先拆环

d3-force 还有一条文档里写着但几乎没人读的规则：手工调用 simulation.tick() 不会派发 tick 事件。想在服务端一次性算完布局，就要自己在循环里推进并在循环结束后读坐标，而不是指望监听器被调用。

与 React 共管 DOM 的三种模式

冲突的根源很具体：React 的假设是「DOM 是渲染函数的输出」，D3 的假设是「DOM 是可以就地修改的状态容器」。两边同时写同一棵子树，必然出现 React 覆盖掉 D3 的修改，或者 D3 改了 React 不知道。三种模式各自划清边界。

模式谁拥有 DOM过渡归谁清理函数要做什么适用
D3 只算数学React 渲染全部元素React 或 CSS不需要静态或低频更新的标准图形
ref 加副作用，D3 全包子树D3D3停仿真、中断过渡、解绑事件、进入时清空子树保证幂等force、zoom、brush 等带内部状态的交互
分层：React 画结构，D3 只 call 坐标轴与过渡边界明确地共享D3中断过渡绝大多数业务图表
 
function ForceGraph({ nodes, links }) {
  const ref = useRef(null);

  useEffect(() => {
    // force 会就地改写传入对象，直接用 props 会破坏 React 的不可变假设，必须传副本
    const ns = nodes.map(d => ({ ...d }));
    const ls = links.map(d => ({ ...d }));

    const svg = d3.select(ref.current);
    svg.selectAll('*').remove();   // 严格模式下副作用会执行两次，先清空保证幂等

    const sim = d3.forceSimulation(ns)
      .force('link', d3.forceLink(ls).id(d => d.id))   // 不给 id 访问器时默认按下标匹配
      .force('charge', d3.forceManyBody().strength(-120))
      .force('center', d3.forceCenter(0, 0));

    const link = svg.append('g').selectAll('line').data(ls).join('line');
    const node = svg.append('g').selectAll('circle')
      .data(ns, d => d.id).join('circle').attr('r', 5);

    sim.on('tick', () => {
      link.attr('x1', d => d.source.x).attr('y1', d => d.source.y)
          .attr('x2', d => d.target.x).attr('y2', d => d.target.y);
      node.attr('cx', d => d.x).attr('cy', d => d.y);
    });

    return () => {
      sim.stop();                       // 不停仿真，卸载后回调仍在跑并访问悬空节点
      svg.selectAll('*').interrupt();   // 未结束的过渡同样要中断
    };
  }, [nodes, links]);

  return React.createElement('svg', { ref, viewBox: '-200 -150 400 300' });
}

什么场景值得用 D3，什么场景是浪费

flowchart TD Q1{"有现成图表类型能表达吗"} -->|有| N1["用配置驱动的库"] Q1 -->|没有| Q2{"过渡语义是不是信息"} Q2 -->|是 要让读者看清元素去哪了| Y1["值得用 D3"] Q2 -->|不是| Q3{"元素量级"} Q3 -->|数千以内且要浏览器命中测试| Y2["D3 加 SVG"] Q3 -->|上万且只需最近点提示| Y3["D3 算坐标 加 Canvas 绘制"] N1 --> Q4{"数据量与图表种类"} Q4 -->|标准图表 万点以内| N2["Chart.js"] Q4 -->|地图 关系图 十万级| N3["ECharts"]
场景判断理由
标准折线、柱状、饼图、雷达不值得边距、刻度、图例、提示框、响应式全要自己写一遍，详见站内《Chart.js 的配置模型与容量边界》
十万级数据的商业仪表盘不值得成套的采样与渐进渲染机制自己搭代价太高，详见站内《ECharts 的渲染架构与大数据量优化》
视觉编码没有现成类型值得蜂群图、时间线拼图、地图上的流线这类编码只能自己搭
过渡语义本身承载信息值得排序重排、层级展开这种「元素去了哪里」，只有 key 加 join 能精确表达
服务端生成 SVG有条件值得配 jsdom 可以在 Node 里产出 SVG 字符串；但批量出版级出图更适合 Python 栈，详见站内《Python 可视化栈的分层与场景匹配》
三维场景不适用换渲染管线，详见站内《Three.js 的渲染管线与性能预算》
❌
最容易踩的坑

1. 省略 key 函数：数据重排后是「值错位」不是「元素移动」，过渡看起来全乱。

2. 用 d => d 当 key：对象被转成字符串，所有数据塌缩成一个键，只剩一个元素。

3. 传了 exit 回调却忘了 remove()：join 只在不传 exit 回调时才自动删除，元素会一直堆积。

4. exit 过渡未结束新数据就到：selectAll 把正在淡出的元素当成 update，元素越来越多。给退出元素打标记并在选择器里排除。

5. 改了 domain() 不重新 call(axis)：图形移动了，坐标轴还是旧刻度，读数全错。nice() 也必须在 call 之前调。

6. 连续比例尺默认不 clamp：越界数据被外推到绘图区外，现象是「有几条数据不见了」。

7. 对 scaleBand 调 axis.ticks(n)：无效，band 没有 ticks，类目太密要用 tickValues 自己抽稀。

8. scaleOrdinal 不显式给 domain：配色随数据出现顺序漂移，刷新一次颜色就换一套。

9. 把 React state 里的对象直接喂给 force：它会写入坐标与速度，并把边的端点替换成对象引用，状态当场被污染。

10. 自己循环调 simulation.tick() 却指望 on('tick') 触发：手工 tick 不派发事件。

11. treemap 或 pack 之前漏了 sum()：所有面积为 0，一片空白且没有任何报错。

12. 版本相关的两个硬坑：v7 是纯 ESM，在 CommonJS 里 require 会直接失败；v6 起没有 d3.event，事件对象从回调第一个参数取。
