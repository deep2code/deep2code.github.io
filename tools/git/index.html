Git 深度原理：分布式版本控制

🏷️ Git

Git 不是简单的文件快照，它是分布式版本控制，每个开发者都有完整的仓库历史。这篇讲透 Git 底层原理。

核心原理1：Git 存储原理：快照不是差异

SVN 存的是每次修改的差异，Git 存的是每次提交的完整快照，相同文件只存一份指针。

flowchart TD A[Git 存储] --> B[Blob 文件内容] A --> C[Tree 目录] A --> D[Commit 提交] A --> E[Tag 标签] B --> F[SHA-1 哈希 寻址] C --> F D --> F

Git 对象类型

对象类型 存什么 作用
Blob 文件内容 不存文件名，只存内容
Tree 目录结构 指向 Blob 和子 Tree
Commit 提交元数据 指向 Tree，父 Commit，作者
Tag 标签 给 Commit 起个固定名字

核心原理2：分支原理：为什么分支这么轻？

Git 分支只是一个指向 Commit 的指针，不是复制整个目录，所以创建切换分支都是毫秒级。

flowchart LR A[Commit1] --> B[Commit2] B --> C[Commit3] C --> D[Commit4] E[main 指针] --> D F[feature 指针] --> B

Git vs SVN 分支对比

对比项 SVN Git
分支本质 复制整个目录 一个 40 字节指针
创建分支 几秒 毫秒级
切换分支 复制文件 移动指针
合并 很慢 很快

核心原理3：merge vs rebase 区别

merge 保留完整历史，会产生合并节点；rebase 把提交挪到目标分支后面，历史更干净线性。

flowchart LR A[main] --> B[C1] B --> C[C2] C --> D[C3] E[feature] --> B E --> F[C4] E --> G[C5]

merge vs rebase 对比

操作 历史样子 适用场景
merge 分叉后合并，有合并节点 公共分支，保留真实历史
rebase 线性，把你的提交挪到最新后面 个人分支，整理提交历史
cherry-pick 挑某个提交弄到别的分支 只需要某个 bugfix

新手最容易踩的坑

❌
避坑指南
  • commit 前先 git pull --rebase，不要直接 merge 造成一堆冲突
  • rebase 不要在公共分支上做，会改写历史，别人同步会乱
  • .gitignore 一定要配好，不要把 node_modules、dist 提交进去
  • 大文件不要直接提交 Git，用 Git LFS 或者对象存储
