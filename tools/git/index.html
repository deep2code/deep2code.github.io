Git 的对象模型与常见操作的真实语义

🏷️ Git

Git 的表层命令不算多，语义却经常被口口相传的说法带偏：「Git 存快照不存差异」「rebase 会丢提交」「reset --hard 之后就彻底没救了」。这些说法都只对一半。要把 Git 用准，得先看清底下那套只有四种对象的内容寻址存储，再看每条命令到底动了 HEAD、索引、工作区中的哪一层。

四种对象：一个内容寻址的键值库

.git/objects 本质上是个键值存储：key 是对象内容的哈希，value 是 zlib 压缩后的字节。写入前 Git 会拼一个头部，格式是「类型 空格 字节数 NUL」，再接原始内容，对整体求哈希。因此同样的内容在任何仓库、任何时间点都得到同一个 key，这就是「内容寻址」的含义，也是 Git 去重的全部机制。默认哈希算法是 SHA-1，自 2.13 起用的是带碰撞检测的 sha1dc 实现；新仓库可以用 git init --object-format=sha256 建成 SHA-256 格式，但这类仓库目前还不能和 SHA-1 仓库互相推送。

四种对象里只有三种会被日常提到，第四种（tag 对象）还经常和「轻量标签」混在一起讲，实际上轻量标签根本不产生对象。

对象类型内部存了什么明确不存什么谁引用它探查命令
blob文件的原始字节，一个字节都不多文件名、路径、权限、行号tree 条目git cat-file -p 哈希
tree一组条目：模式 + 对象类型 + 哈希 + 名字内容本身；也无法表示空目录commit、父 treegit cat-file -p HEAD^{tree}
commit根 tree 哈希、0 到 N 个父提交、author、committer、消息任何形式的文件差异引用、其他 commit 的 parent 字段git cat-file -p HEAD
tag（附注标签）被指对象的哈希与类型、tagger、消息、可选 GPG 签名文件内容refs/tags/名字git cat-file -p v1.0
轻量标签（不是对象）refs/tags/ 下一行 40 位十六进制哈希tagger、消息、签名一概没有无git rev-parse v1.0

tree 条目里的模式位是个固定的小集合：100644 普通文件、100755 可执行文件、120000 符号链接、040000 子目录、160000 子模块引用（gitlink，只记一个提交哈希，不递归存内容）。Git 只认「可执行位」这一个权限，别指望它保存 owner、组或者其余 mode 位——部署脚本依赖文件权限时必须自己在流水线里补 chmod。

# 1) HEAD 到底是符号引用还是裸哈希，一条命令判断
git symbolic-ref -q HEAD || echo "当前处于 detached HEAD"

# 2) 任意对象的类型、大小、内容

git cat-file -s HEAD            # 对象字节数，不含头部
git cat-file -p HEAD            # 看 tree 哈希、parent 行、author 与 committer 两个时间

# 4) 看索引的真实内容，第一列就是 stage 号

git ls-files -u                 # 只列 stage 非 0 的冲突条目，冲突残留一眼可见

git count-objects -vH

索引是独立的第三状态，不是「工作区的缓存」

.git/index 是一个二进制文件，对每个被跟踪路径记录：路径名、blob 哈希、文件模式、一份 stat 缓存（设备号、inode、mtime、ctime、uid、gid、文件大小），以及一个 stage 号。stat 缓存的作用是让 git status 在绝大多数文件上不必读内容就能断定「没变」；这也是为什么把仓库放在时间戳不稳定的网络文件系统上时，status 会莫名其妙变慢。

stage 号是理解冲突的关键：正常情况恒为 0；合并冲突时同一路径会同时存在 stage 1（共同祖先）、stage 2（当前分支，ours）、stage 3（对方分支，theirs）三条记录，git add 的作用是把三条折叠成一条 stage 0，这就是「标记为已解决」的全部含义——Git 从不检查你解决得对不对。

由此推出两个常被忽略的事实。第一，git commit 只从索引构建 tree，完全不看工作区；git add 之后再修改文件，提交进去的是 add 那一刻的内容，这正是 git add -p 能拆分提交的原理，也是「我明明改了怎么没进去」的真凶。第二，git status 做的是两次 diff——HEAD 对索引得到「已暂存」，索引对工作区得到「未暂存」，两个区域互不相关，同一个文件可以同时出现在两边。

还有一对被广泛误用的索引标记位。--assume-unchanged 只是给 Git 的性能提示，意思是「你可以不查这个文件」，Git 在切分支、合并时随时可以推翻它并覆盖你的本地改动；真要长期忽略对已跟踪文件的本地修改（典型场景是本地配置文件），应该用 --skip-worktree，它才是语义上的「别碰这个路径」。两者都只存在于本地索引，推送不过去，所以拿它们当团队约定一定会出事。

HEAD、分支与 detached HEAD 的成因

分支不是目录副本，也不是提交序列，它就是 refs/heads/ 下一个 41 字节的文本文件：40 位十六进制哈希加一个换行（打包引用后会被折叠进 packed-refs）。HEAD 是 .git/HEAD 里的一行，正常情况写着 ref: refs/heads/main，这叫符号引用。

于是切分支的真实动作是：改写 HEAD 那一行，再把索引和工作区刷成目标提交的 tree。创建分支是 O(1)，永远是毫秒级；切换分支的成本只和两棵 tree 的差异规模相关，跟仓库总历史大小无关——所以「仓库大所以切分支慢」这个说法不成立，真正的慢因是差异文件多、或者 status 前的 stat 扫描慢。

当 HEAD 里直接写了一个 40 位哈希而不是 ref: 开头的行，就是 detached HEAD。它本身不是错误状态，只是此时新提交没有任何分支指向，一旦切走就只能靠引用日志找回。

成因此时 HEAD 内容在这里提交会不会失去引用正确收尾方式

检出一个标签名标签所指提交的哈希会同上；标签本身不可移动，不能在它上面推进

merge 与 rebase 在提交图上的差异

merge 的算法是三方合并：先用 git merge-base 找共同祖先，再把两侧相对祖先的改动合起来。如果共同祖先就是当前 HEAD，Git 默认走 fast-forward——只移动引用，一个新对象都不产生，所谓「合并」其实什么都没合。这也是很多团队看不到合并提交的原因，要强制留痕得加 --no-ff。真正的合并提交有两个父，且父的顺序有语义：parent 1 是执行合并时所在的分支，git log --first-parent 能靠它把主干拉成一条线。默认合并策略自 Git 2.34 起是 ort，取代了旧的 recursive，在大仓库上快一个数量级，重命名检测也更准。

rebase 的算法完全不同：对每个待重放的提交，计算它与其父提交的差异，逐个应用到新基底上，生成一批全新的 commit 对象。tree 可能和原来一模一样，但 parent 变了、committer 时间戳变了，所以哈希必然变（author 时间会保留，这就是 rebase 后 git log 时间看起来乱序的原因）。原提交对象一个都没删，只是失去了引用——这才是「rebase 丢提交」错觉的来源。

工程上更值得记住的差别是冲突次数：merge 只在合并那一刻解一次冲突；rebase 要在每个被重放的提交上各解一次，10 个提交最多解 10 次。真的绕不开时，开 git config --global rerere.enabled true，Git 会记住冲突解法并在重复遇到时自动套用。

reset 的五种模式，各改哪一层

git reset 被讲成「撤销」，其实它做的事非常机械：把当前分支引用移到指定提交，然后按模式决定是否连带刷新索引和工作区。理解成「三层开关」就不会用错。

模式分支引用索引工作区未跟踪文件丢了能否找回
--soft移动不变不变不动安全，改动全留在索引里，适合重做提交
--mixed（默认）移动重置为新位置不变不动安全，改动落到工作区成为未暂存
--hard移动重置强制覆盖不动，不会删提交过的可找回；未暂存改动永久丢失
--merge移动重置保留未暂存改动，若与被重置的文件相交则整体中止不动较安全，冲突时不执行
--keep移动重置保留未暂存改动，若目标提交会覆盖这些文件则整体中止不动较安全，日常切换比 hard 更该用
git reset 路径不变该路径重置为 HEAD不变不动安全；带路径时不接受 --hard

两个必须纠正的认知。第一，reset --hard 不删除未跟踪文件，清空工作目录的是 git clean -fd，这两条命令经常被当成一条来记，结果该清的没清、不该丢的丢了。第二，--hard 真正不可逆的只有「从未进入对象库的工作区改动」；只要 git add 过，blob 就已经落盘，git fsck --lost-found 能捞出来（代价是只有内容、没有文件名）。

cherry-pick 与 revert：补丁语义，不是「搬提交」

cherry-pick 不会把提交移过来。它取的是「该提交与其父提交之间的差异」，然后以三方合并的方式应用到当前 HEAD，生成一个内容相似但哈希、父提交、时间全都不同的新提交。三个直接后果：提交图上看不出任何关联，除非加 -x 在消息里写一行来源哈希；对合并提交做 cherry-pick 必须用 -m 指明相对哪个父取差异；后续能否识别「这个补丁已经应用过」完全取决于 patch-id 是否一致，差异只要有一点偏移就识别不出来。

revert 同理，它生成的是反向补丁的新提交，历史一行都不改，这也是它唯一适合公共分支的原因。revert 一个合并提交时 -m 1 表示保留第一父（通常是主干）、撤销第二父带进来的改动。这里藏着一个经典坑：把某次合并 revert 掉之后，那条特性分支在图上依然可达，再次 merge 时 Git 认为「已经合过了」，什么都不会带回来；正确做法是 revert 那个 revert 提交，或者把分支重做一遍。

# === 把主干上的修复挑到发布分支 ===
git switch release/1.8
# -x 会在提交消息尾部追加 cherry picked from commit ... 便于日后审计来源
git cherry-pick -x 9f2a1c4

# 挑一个区间，注意 A..B 是左开右闭，不含 A 本身
git cherry-pick -x 9f2a1c4..d41b2ef

# 挑一个合并提交：不指定 -m 会直接报错，1 表示相对第一父取差异
git cherry-pick -m 1 合并提交哈希

# === 线上回滚：对公共分支唯一安全的撤销方式，不改写历史 ===
git revert --no-edit d41b2ef

# 回滚一个合并提交，保留第一父（主干），撤销第二父引入的内容
git revert -m 1 a77c901

# 回滚一个区间并合成单个提交，避免中间态各自冲突
git revert --no-commit d41b2ef~3..d41b2ef && git commit -m "revert: 回滚灰度批次"

# === 判断两条分支之间谁还差哪些补丁，等价性基于 patch-id ===
# 输出里 = 号表示两边都有等价补丁，< 和 > 表示只在一侧
git log --left-right --cherry-mark --oneline main...release/1.8

reflog 与可达性：为什么「丢失」的提交还在

对象的生死只由可达性决定。Git 从一组「根」出发做图遍历：所有 refs/heads、refs/tags、refs/remotes、refs/stash、HEAD、索引，以及引用日志里记录过的每一个旧值。遍历不到的对象才叫 unreachable，而 unreachable 也不等于立刻删除。

引用日志就是「引用的历史位置流水」，存在 .git/logs/HEAD 和 .git/logs/refs/heads/ 下，每次 commit、checkout、reset、merge、rebase 移动引用都会追加一行，带上操作类型和时间。所以 reset --hard 之后，旧提交仍被引用日志引用，仍然可达，gc 根本不会碰它——这就是「救得回来」的机制。

参数默认值作用对象过期之后会发生什么
gc.reflogExpire90 天仍可达提交的引用日志条目条目被删，但提交若还被分支可达，对象不受影响
gc.reflogExpireUnreachable30 天指向已不可达提交的条目条目被删，这些提交随即变成 unreachable
gc.pruneExpire2 weeksunreachable 对象只有超过宽限期且 gc 运行时才真正删除
gc.auto6700 个松散对象是否触发自动 gc超过阈值时，许多日常命令结束后会顺带跑一次 gc --auto
gc.autoPackLimit50 个 packfile是否触发重新打包超过阈值时合并 packfile
git gc --prune=now手动所有 unreachable 对象立即物理删除，这一步之后才真的没救

一个容易误判的点：引用日志是纯本地数据，clone 不会带过来，CI 里的浅克隆更没有。所以「让同事在他机器上帮我找回」这条路通常走不通，除非那些提交真的推送过。

# 1) reset 或 rebase 走歪了：先看 HEAD 都去过哪，别急着再 reset
git reflog --date=iso | head -30
# 每行形如：d41b2ef HEAD@{3}: commit: feat 灰度开关
#          9f2a1c4 HEAD@{2}: reset: moving to HEAD~3
# 操作类型（commit / reset / rebase finish / checkout）就是定位线索

# 2) 不要直接 reset 回去，先在新分支上验证内容，确认无误再动原分支
git switch -c rescue d41b2ef
git log --oneline -5 && git diff --stat main

# 3) 分支删了、引用日志也过期了：绕开日志扫游离对象
git fsck --full --no-reflogs --lost-found
# 游离提交与游离 blob 会落到 .git/lost-found/ 目录，blob 只有内容没有文件名
git fsck --no-reflogs 2>/dev/null | awk '/dangling commit/{print $3}' | xargs -r git log --oneline -1

# 4) 破坏性操作前的自保动作，两条任选其一
git branch backup/before-reset-$(date +%Y%m%d-%H%M%S)
git stash push -u -m "before hard reset"   # -u 连未跟踪文件一起写进对象库

推送的安全语义：--force-with-lease 与 --force

git push --force 是无条件覆盖：远端引用直接被设成你给的值，别人在这期间推上去的提交立刻变成不可达，等远端 gc 跑过就彻底没了。托管平台的 reflog 有时能救，但那是运气不是机制。

--force-with-lease 加了一道乐观锁：只有远端引用的当前值等于你本地记录的远端跟踪引用时才更新，否则以 stale info 拒绝。它的可靠性完全依赖那个「期望值」有多可信，而这正是它的软肋——任何一次 fetch 都会刷新远端跟踪引用，包括 IDE 后台自动 fetch、git pull 内部隐含的 fetch。刷新之后期望值就等于远端最新值，校验必然通过，你依然会覆盖掉刚抓下来却根本没看过的提交。

两个补救手段：显式写出期望哈希 --force-with-lease=分支名:你亲自确认过的哈希；或者叠加 Git 2.30 引入的 --force-if-includes，它额外要求「将被覆盖的远端提交已经出现在你本地引用日志中」，也就是你变基时确实是基于它做的。

# 变基完成、推送之前的三步预检，顺序不要换
# 1) 先抓取，再看这条分支最近是谁在推——确认是否真的独占
git fetch origin
git log --format='%h %an %cr %s' -5 origin/feature/x

# 2) 确认你不会覆盖掉远端独有的提交：左箭头一侧就是远端独有
git log --left-right --oneline origin/feature/x...HEAD

# 3) 双保险推送：租约校验远端当前值，if-includes 校验你确实基于它变基
git push --force-with-lease --force-if-includes origin feature/x

# 明确写出期望值的版本，最不容易被后台 fetch 破防
git push --force-with-lease=feature/x:1a2b3c4 origin feature/x

# 仓库级兜底：把裸 force 从肌肉记忆里去掉
git config --global alias.fpush 'push --force-with-lease --force-if-includes'

最容易踩的坑

❌
这些坑每一条都能复现
  • git reset --hard 前没有做储藏：提交过的能靠引用日志找回，从未 git add 的工作区改动永久消失，因为它从来没进对象库。前置检查是 git status --porcelain 为空，或先 git stash push -u。
  • 把 reset --hard 当成「清空目录」：它不动未跟踪文件。真要清是 git clean -fd，而这条命令没有任何撤销手段，跑之前必须先 git clean -nd 看一遍清单。
  • 用 --force 覆盖共享分支：别人的提交瞬间不可达，远端 gc 后不可恢复。改用 --force-with-lease --force-if-includes，并记住任何 fetch 都会削弱租约。
  • git add 之后又改了文件就直接 commit：进去的是 add 那一刻的快照。提交前用 git diff（比的是索引对工作区）确认没有残留未暂存改动。
  • 拿 --assume-unchanged 忽略本地配置改动：Git 随时可以推翻这个提示并覆盖你的文件。语义正确的是 --skip-worktree，而且两者都只存在本地，不能当团队约定。
  • 在 detached HEAD 上连着提交好几次然后切分支：这些提交没有引用指向，30 天后引用日志过期就会被 gc 回收。发现自己 detached 的第一件事是 git switch -c。
  • revert 掉一次合并之后想重新合入那条分支：图上它仍然可达，merge 什么都不会带回来。必须 revert 那个 revert，或者把分支重做。
  • squash merge 之后不删分支继续在上面开发：合并关系没有记录在图里，下次合并会重放全部旧改动并再冲突一遍。squash 后应当删掉分支重新切。
  • 并行 rebase 一条别人也在推的分支：每次重放都换哈希，对方 pull 时会拿到两套等价提交，patch-id 一旦对不上就要人工解一遍。共享分支只用 merge。
  • 提交了大文件之后才加 .gitignore：对象已经永久存在于历史中，仓库体积降不下来。必须用 git filter-repo 重写历史并让所有人重新 clone，代价极高，所以初始化仓库时就要把忽略规则配好。
  • 以为 CI 里能用引用日志排查：clone 和浅克隆都不带引用日志，HEAD@{1} 在 CI 里通常不存在，脚本里要用显式哈希或 origin/main...HEAD。
  • 用 git checkout 同时干三件事导致误伤：切分支、丢弃改动、恢复文件全靠同一条命令。2.23 之后一律用 git switch 管引用、git restore 管内容，误操作面小得多。
