Git 版本控制

🏷️ Git

Git 简介

Git 是 Linus Torvalds 2005 年给 Linux 内核开发做的分布式版本控制系统。它跟 SVN 那代集中式 VCS 根本区别就一个词：分布式。每个开发者手里都有完整的仓库历史，断网照样提交、分支、合并，这一点到今天还是它的护城河。

我自己用 Git 十几年，最大的感受是：日常 20% 的命令覆盖 80% 的场景，剩下那 20% 的"救急命令"才是拉开差距的地方。这篇文章我就按"日常 → 分支 → 远程 → 进阶 → 救急"来讲。

为什么 Git 快

很多人觉得 Git 快是因为用了 C 写。不对。核心是它把版本历史存成有向无环图（DAG），每个 commit 是一个内容寻址的快照（SHA-1 哈希），不是文件差异。所以切分支、对比历史基本是毫秒级——因为分支就是一个 40 字节的指针，不是复制文件。

flowchart TD A[工作区 Working Directory] -->|git add| B[暂存区 Staging Area] B -->|git commit| C[本地仓库 Local Repository] C -->|git push| D[远程仓库 Remote] D -->|git pull| C C -->|git checkout| A B -->|git reset HEAD| A

安装与配置

先看安装，三平台一行命令的事：

# macOS
brew install git

# Ubuntu / Debian
sudo apt install git

# Windows
winget install Git.Git

# 验证
git --version

装完第一件事，配置身份——这俩不配，commit 出来的作者信息是错的：

git config --global user.name "张三"
git config --global user.email "zhangsan@example.com"

# 默认分支名改成 main（现代习惯）
git config --global init.defaultBranch main

# 好看的 log
git config --global alias.lg "log --graph --oneline --decorate --all"

日常高频配置我列一下，都可以写进 ~/.gitconfig：

配置项作用
user.name / user.email提交者身份
core.editor默认编辑器（如 vim / vscode）
pull.rebasepull 时用 rebase 还是 merge
init.defaultBranch新仓库默认分支名
alias.*命令别名

日常工作流

先看 Git 的四个区域，这是理解所有 Git 操作的基础：

区域说明常用命令
工作区（Working Directory）你看到的项目文件git add
暂存区（Staging Area）下次提交的快照git reset
本地仓库（Local Repository）本地完整历史git commit
远程仓库（Remote Repository）服务器上的仓库git push / pull

新建仓库或者拉取已有仓库，是日常起点：

# 新建本地仓库
mkdir my-project
cd my-project
git init

# 克隆远程仓库
git clone https://github.com/username/repo.git
cd repo

# 克隆指定分支
git clone -b develop https://github.com/username/repo.git

查看状态、添加、提交，是每天都在用的：

git status                    # 看当前状态
git add file.txt               # 添加单个文件
git add .                      # 添加所有变更
git commit -m "feat: 新增登录功能"   # 提交
git commit -am "fix: 修复bug"   # add + commit 一步到位（只对已跟踪文件）
我推荐的 commit message 规范

用 Conventional Commits：feat: 新功能、fix: 修 bug、docs: 文档、refactor: 重构、test: 测试、chore: 杂项。写规范的好处是 changelog 和版本号可以自动生成，我项目里一直这么干。

查看历史

git log                        # 完整历史
git log --oneline              # 简洁模式
git log --graph                # 图形化分支历史
git log -p file.txt            # 看某文件的详细改动
git blame file.txt             # 每行最后修改是谁

分支管理

分支是 Git 的灵魂。新建、切换、合并，三步搞定：

git branch                     # 列出本地分支
git branch feature/login       # 新建分支
git checkout feature/login     # 切换分支
git switch feature/login       # 新版语法（推荐，更直观）
git checkout -b feature/login  # 新建并切换
git merge feature/login        # 合并分支到当前分支
git branch -d feature/login    # 删除已合并的分支
git branch -D feature/login    # 强制删除

合并 vs 变基（rebase）是新手最纠结的，我直接说结论：

操作历史线适用场景
git merge保留分叉和合并点公共分支、要保留真实历史
git rebase线性、干净个人分支整理、合并前变基
 
# rebase：把当前分支的提交"搬到"目标分支最新点之后
git checkout feature/login
git rebase main

# 交互式 rebase：整理最近 3 个提交（合并、修改、重排）
git rebase -i HEAD~3
flowchart LR A[main: C1] --> B[main: C2] B --> C[feature: C3] C --> D[feature: C4] B --> E[main: C5 别人的提交] D --> F{rebase 前} E --> F F --> G[rebase 后 C3 C4 接到 C5 之后]
rebase 的铁律

不要对公共分支（main / develop）做 git rebase！会改写别人已经拉取的历史，造成一团乱麻。rebase 只用于整理自己的本地分支。这是我见新人踩得最多的坑，没有之一。

远程仓库

远程的增删查，以及推送拉取：

git remote -v                          # 查看远程
git remote add origin https://...       # 添加远程
git remote set-url origin git@github.com:...  # 修改远程地址

git push -u origin main                # 首次推送并关联
git push                               # 之后直接推
git push origin feature/login          # 推送指定分支

git pull                               # 拉取并合并
git fetch                              # 只拉取不合并（更安全）

进阶操作

撤销与恢复

"改错了想退回去"是高频需求，三种场景我分清楚：

命令作用场景
git restore file放弃工作区修改改乱了想回到暂存区版本
git reset --soft HEAD~1撤销提交，保留改动在暂存区commit 写错了想改
git reset --hard HEAD~1撤销提交，丢弃改动危险！确定不要这些改动
git revert HEAD新建一个反向提交公共分支上撤销，不改历史
--hard 慎用

git reset --hard 会把工作区未提交的改动全部干掉，我见过新人手贱按了这个，写了半天的代码直接蒸发。按之前一定 git status 看清楚，或者先 git stash 保底。

暂存工作（Stash）

正在改一半，突然要切分支修个紧急 bug——stash 就是干这个的：

git stash                # 暂存当前未提交的改动
git stash save "WIP"     # 带说明暂存
git stash list           # 查看暂存列表
git stash pop            # 恢复最近的暂存并删除
git stash apply stash@{0}  # 恢复指定暂存（不删除）

标签（Tag）

打版本号用 tag：

git tag v1.0.0                  # 轻量标签
git tag -a v1.0.0 -m "Release 1.0"  # 附注标签（推荐）
git push origin v1.0.0          # 推送标签
git push origin --tags          # 推送所有标签

生产案例：一次线上热修的完整流程

说个真事。线上突然出 bug，我正在 feature 分支改新功能，代码写了一半不能提交。完整流程是这样的：

  1. git stash 把半成品收起来
  2. git switch main 切到主干，git pull 拉最新
  3. git switch -c hotfix/xxx 建热修分支，改完 commit
  4. 提 MR / PR 合并到 main，部署上线
  5. 切回 feature 分支，git stash pop 恢复半成品
  6. git rebase main 把热修的提交也变基进来，保持线性历史

这套流程我用了无数次，从来没丢过代码。stash + rebase 是 Git 救急的两把好刀。

常见问题

问题解决方案
Git 提交慢用 SSH 代替 HTTPS、配置代理、检查网络
合并冲突git status 看冲突文件，手动编辑后 git add
误删分支git reflog 找提交哈希，git checkout 恢复
撤销已推送的提交公共分支用 git revert，别用 reset

合并冲突怎么解

git status                 # 看哪些文件冲突
# 手动编辑冲突文件，去掉 <<<<<<< ======= >>>>>>> 标记
git add .
git commit                 # 完成合并
# 或者放弃合并
git merge --abort

最佳实践 Do / Don't

我会这么做我不会这么做
小步提交，一个功能一个 commit攒一堆改动一次大提交
commit message 写清楚做了啥写"update"、"fix"这种废话
公共分支用 merge，个人分支用 rebase在 main 上 rebase
推送前先 pull直接 push 然后被拒
用 SSH key 认证每次输密码

总结

Git 的核心就四块：工作区、暂存区、本地仓库、远程仓库。日常用 add / commit / push / pull 四个命令，分支用 merge 和 rebase，救急用 stash 和 reflog。记住那条铁律——公共分支别 rebase——你就能避开 90% 的 Git 事故。下一篇 GitHub，看看怎么在远程协作。
