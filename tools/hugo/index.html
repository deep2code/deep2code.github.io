Hugo 静态站点生成器

🏷️ Hugo

我为什么还在用 Hugo

先说结论：这个博客本身就是 Hugo 生成的。我试过 Hexo、VuePress、Astro，最后又绕回 Hugo——原因很实际，我不想再为写一篇文章等一个 Node 进程。

Hugo 把 Markdown、Go Template、TOML 配置三样东西编译成一堆纯 HTML，部署到任何静态托管就行。它的心智模型一句话能说清：

核心模型

Hugo = 内容（Markdown）+ 模板（Go Template）+ 配置（TOML）→ 静态 HTML。「写文章」和「设计页面」彻底分家，你写正文时不用碰一行样式。

但「快」不是白来的，它快在两件事：编译成单个 Go 二进制、每个页面在独立 goroutine 里并发渲染。下图就是它的构建流水线，我第一次看懂这张图才明白为什么几千页也能秒出包：

flowchart TD subgraph IN[输入] CONTENT[content/ Markdown] LAYOUTS[layouts/ Go 模板] CONFIG[hugo.toml 配置] ASSETS[assets/ CSS JS 图片] end subgraph ENGINE[Hugo 引擎] PARSE[解析 front matter] RENDER[并发渲染 每个页面一个 goroutine] PIPES[资源管道 指纹 压缩] end subgraph OUT[输出] HTML[public/ 静态 HTML] RSS[rss.xml sitemap.xml] JSON[index.json llms.txt] end CONTENT --> PARSE LAYOUTS --> RENDER CONFIG --> PARSE ASSETS --> PIPES PARSE --> RENDER RENDER --> HTML RENDER --> RSS RENDER --> JSON PIPES --> HTML

五分钟把站点跑起来

我当年照着官方文档踩过第一个坑：git clone hugoDocs && hugo -D server，结果默认开在 localhost:1313，我愣是以为端口被占了找了半天。其实就是这个默认值。

# macOS 安装
brew install hugo

# 建站 + 接 PaperMod 主题
hugo new site mysite && cd mysite
git init
git submodule add https://github.com/adityatelange/hugo-PaperMod themes/PaperMod
echo 'theme = "PaperMod"' >> hugo.toml
hugo server -D        # 本地预览，--buildDrafts 带上草稿

几个我天天用的快捷键：

  • hugo new posts/xxx.md 用 archetypes 模板起一篇新稿；
  • hugo server -D --disableFastRender 改了 baseof.html 不生效时，关掉快速渲染强制全量重渲；
  • hugo --minify 上线前把 HTML/JS/CSS 压一遍。

底层：Hugo 是怎么把 Markdown 变成 HTML 的

很多人停留在「会用 shortcode」就够了，但我建议你搞懂五个阶段的顺序，因为八成的构建报错都出在顺序上：

  1. 配置加载：合并 hugo.toml、环境配置、主题默认值；
  2. 内容扫描：解析每个 .md 的 front matter，建立 Page/Section/Taxonomy 索引；
  3. 模板编译：把 Go Template 预编译成可执行的模板函数；
  4. 页面渲染：并发跑，每个页面独立 goroutine；
  5. 资源管道：图片 .Resize、CSS fingerprint、打包压缩。

这里有个我花了一下午才想通的点：Go Template 里的 . 是会变的。在 {{ range }} 循环里，. 指向当前迭代项，你想访问外层页面变量就得用 $.Page，或者循环前先 {{ $page := . }} 存一份。我第一次写导航循环，死活取不到 .Permalink，打印出来全是当前那篇文章的——就是踩了这个坑。

新手第一个报错

构建报 timed out initializing value，根因不是你配置错了，而是生成耗时超过默认 30s 超时。在 hugo.toml 里加 timeout = 100000（毫秒）放大就行，别去翻模板。

内容模型：先把这几个词搞清楚

Hugo 把一切抽象成 Page，搞懂下面这张表就不会再问「tags 和 categories 到底怎么来的」：

概念对应文件作用
Pagecontent/ 下一个 .md含 front matter + 正文
Sectioncontent/ 子目录自带 _index.md 与列表页
Taxonomyconfig 里定义tags/categories，自动生成聚合页
Page Bundleindex.md 目录页面和图片放一起，支持 .Resize 处理

2026 年 Hugo 到哪了

Hugo 发版很勤，基本一两周一个小版本，2026 年已经在 0.15x 这条线狂奔。我从 0.110 一路跟上来，感受最深的变化是命名规范化——老代码里一堆驼峰写法被一刀切了：

旧写法（已移除）新写法说明
getJsongetJSON函数名统一大写缩写
safeHtmlsafeHTML同上
BaseUrlBaseURL配置键
disablepathToLowerdisablePathToLowerURL 大小写相关

迁移过来其实不难，把上面这几个全局替换一遍基本能跑。从源码编译需要 Go 1.26+；如果你要用 deploy 能力（直接推到 GitHub Pages/Netlify），得装 go install -tags withdeploy github.com/gohugoio/hugo@latest 这个带 deploy 标签的版本，官方二进制默认不含。

生态上有个我觉得值得说的趋势：llms.txt。2026 年 AI 抓静态站成了标配，Hugo 模板可以直接输出一个 llms.txt 给大模型喂上下文。Docsy 主题 0.15.0（2026 年 5 月）已经原生支持了。我自己给博客加 llms.txt 就花了十分钟——写一个 layout 把所有文章标题和摘要拼进去即可。

和其他 SSG 掰掰手腕

经常有人问我「Hugo 还是 Astro」，我的看法是：这俩解决的问题不一样。Hugo 赢在单二进制和构建速度，Astro 赢在组件化和内容岛。下面这张表是我实际用下来的体感，不是官网宣传稿：

维度HugoAstroNext.js
语言/运行时Go，单二进制NodeNode
千页冷构建约 1-3 秒（参考值）约 20-60 秒分钟级
本地预览内存~50MB~300MB+~500MB+
组件能力模板 + shortcodeReact/Vue/Svelte 混用全栈 React
适合海量内容、纯文档、博客要交互组件的文档站要服务端逻辑

那张构建时间是我在同一台 M 系列 MacBook 上、用同一个 2000 页文档站大概测的，Hugo 确实甩开后面一大截。但如果你要在文档页里嵌一个可交互的 React demo，Hugo 就别硬撑了，上 Astro。

flowchart TD A{你要做什么?} -->|纯文档/博客/海量页| B[Hugo 单二进制秒级构建] A -->|文档里要嵌交互组件| C[Astro 内容岛] A -->|要服务端渲染和 API| D[Next.js] A -->|只要极简单二进制| E[Zola] B --> F[GitHub Pages / Netlify 直接托管]

我踩过的几个坑

  • 改了 baseof.html 全站不更新：这是 Hugo 的增量构建在偷懒，日常只改正文只重渲单页。改模板用 --disableFastRender 或直接 rm -rf public/ 重建；
  • 图片不显示：十有八九是没把图片放进 Page Bundle（index.md 同目录），或者用了 ./xxx.png 相对路径却开了 uglyURLs；
  • 线上 404：服务器区分大小写，Hugo 默认把 URL 转小写，Linux 服务器上文件名大小写不一致就 404，加 disablePathToLower = true；
  • 草稿没上线：draft: true 默认不构建，hugo -D 是开发预览，hugo -F 才是带上未来文章。

Do / Don't 清单

我建议这么做

✓ 图片用 .Resize 生成多尺寸配 <picture>；✓ CSS/JS 走 fingerprint 实现长缓存；✓ 主题用 Hugo Modules 管理，别再用 git submodule；✓ 写 shortcode 把重复的 HTML 块封装掉。

别这么干

✗ 别在 shortcode 里写复杂业务逻辑——它是模板不是程序；✗ 别把整个 Node 依赖树搬进来只为了个图表；✗ 别在 static/ 放和 layouts 同名的文件，static 是直接覆盖不合并的；✗ 别拿 hugo server 的结果当生产环境测，生产要用 hugo server -e production。

FAQ

Q：2026 年了，Hugo 还值得入坑吗？
值不值得取决于你要做什么。个人博客、技术文档、上千页的知识库，Hugo 单二进制 + 秒级构建依然没对手。但如果你团队全是 React 背景、文档里要大量交互 demo，那 Astro 更顺手。我是因为受够了 Node 工具链的「装一下就半分钟」才回来的。

Q：从 Jekyll/Hexo 迁过来麻烦吗？
Markdown 正文基本能直接搬，front matter 字段改个名就行。真正要重学的是模板语法——Jekyll 的 Liquid 换成 Go Template，. 的指向规则是最大的思维转变。Ruby 环境依赖整个消失，部署反而变简单了。

Q：构建到一半卡住报 timeout，怎么回事？
先看是不是 hugo.hugo 在跑某个网络请求（比如 getJSON 拉远程数据）慢。本地把 timeout 调大，CI 上要确保能访问外网或把数据成本地缓存。

Q：Hugo 和 AI 结合能玩出什么花？
最实在的就是 llms.txt：把全站结构和摘要吐给大模型，让它能回答「这个站讲了啥」。再进一步，配合 A Gentle Site Search 之类的方案，把 Markdown 直接喂给 RAG，比倒排索引省事。

写在最后

我对 Hugo 的感情很简单：它不花哨，不追新，但它从来不辜负你。你写完文章敲一下命令，三秒钟后所有页面、RSS、sitemap 全齐了，扔到 GitHub Pages 上就完事。这种「工具消失在背后」的感觉，在框架年年换新的当下反而成了稀缺品。下一篇聊 Makefile，看另一个从 1970 年代活到现在还没被淘汰的工具。
