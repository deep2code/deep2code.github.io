# 正文简化 Agent 作业说明

你负责一批 HTML 文章页的**正文改写**，目标是把书面化的 AI 腔改成简洁、直白、好懂的中文。

只改 `<p>` 内的文字。结构、代码、表格、标题、链接全部不动。

## 输入 / 输出

- 输入：一个 JSON 文件（路径由调用方给出），形如
  ```json
  {"id": 3, "files": ["a/b/index.html", ...], "items": [
     {"file": "a/b/index.html", "start": 12345, "end": 12678, "sha1": "…",
      "cjk": 147, "heading": "二、rate 与 irate 的差别", "prev": "上一段纯文本前 80 字",
      "next": "下一段纯文本前 80 字", "html": "<p> 内部的原始 HTML </p>"}
  ]}
  ```
- 输出：写成 JSON 文件（路径由调用方给出），形如
  ```json
  {"items": [{"file": "a/b/index.html", "start": 12345, "end": 12678,
              "sha1": "<原样抄输入里的 sha1>", "new_html": "<改写后的段落 inner HTML>"}],
   "descs": {"a/b/index.html": "新的 meta description"}}
  ```
- `start` / `end` / `sha1` **原样抄**，不要自己算。
- 每条输入 item 必须有一条输出 item，**不许漏**。
- 用 Python 写输出文件（`json.dump(..., ensure_ascii=False)`），不要手写转义。
- 一次性处理整批，不要只做前几条。

## 改写目标

读者是有经验的程序员，但没耐心读绕来绕去的长句。每段应该像同事当面讲清楚一件事。

硬指标（按 item 逐条核对）：

- 平均每句 15–25 个中文字，单句不超过 35 字。
- 每个输出片段 20–50 个中文字，不超过 60 字；原文更长就拆成 2–3 段，用 `</p>\n<p>` 连接。
- **每条 item 改写后总字数（CJK）必须 ≤ 原 `cjk` × 0.78**。
  - 原 `cjk` 在 30 字以上：压到 65%–78%。
  - 原 `cjk` 在 15–29 字：至少删 3 个字，或改成更直白的同义短句。
  - 原段落里的每个句子都要重写，不要只改个别词就交回。
- 整批改写后总字数必须 ≤ 原文的 72%。
- 原文里信息极密、几乎全是数字或代码名的短段，可以少压，但不能原样抄回。

## 怎么改

按优先级：

1. **删套话**：以下模式整句删掉或改成直接陈述：
   - 「搞清 X，能解决『……』」「理解 X，才能……」
   - 「这不是 X，而是 Y」（除非对比本身是技术结论）
   - 「值得注意的是」「需要说明的是」「换句话说」「也就是说」「事实上」
   - 「真正的 X 是」「本质上」「核心在于」「关键在于」
   - 「先说结论」「下面分三点」「综上所述」「首先/其次/最后」
   - 「这件事常被忽略」「很多人不知道」「绝大多数人……」
2. **拆长句**：一句话只留一个主干。把「的」字套娃、连续 `、` 和 `；` 列举拆成短句。
3. **名词变动词**：「进行校验」→「校验」，「实现了过滤」→「过滤掉」，「具备重试能力」→「能重试」，「对……进行处理」→「处理……」。
4. **抽象变具体**：把「这件事」「这种做法」「该机制」「上述问题」换成具体对象；把「性能下降」换成「请求变慢」这类可感知说法。
5. **解释术语**：首次出现的术语，补半句白话解释，解释只能来自原文已有信息，不能编。
6. **删重复**：同一段里换种说法重复的，只留最清楚的一句；与 `prev` / `next` 重复的过渡句直接删。
7. **保留信息**：技术结论、判据、失效条件、数字、单位、`<code>`、`<strong>` 强调点、链接，一个都不能少。

## 语气示例

原文：
> 搞清代价的构成，能解决「到底该不该为了封禁功能放弃无状态」这个必须在设计阶段回答的问题。自包含令牌按设计不可吊销：验签方不需联系任何人就能确认令牌有效，这既是优点也是上限。补救只有三条路，选择标准是业务能容忍多长的生效延迟。

改写：
> 要不要为了封禁放弃无状态？先看三种做法的代价。自包含令牌天生不能吊销：验签方不用联系任何人，就能确认令牌有效。这是优点，也是上限。想补，只有三条路，按业务能忍多久来选。

原文：
> 令牌在每一个请求的请求头里重传，这件事常被忽略。base64url 会让原始字节膨胀约三分之一，签名本身在 RS256 下就有 342 个字符。

改写：
> 令牌每个请求都要重传一次。base64url 会把原始字节撑大约三分之一，RS256 的签名本身还有 342 个字符。

原文：
> response_model 的作用被严重低估：它不只是生成文档，而是按声明的模型过滤输出字段。不声明的话，handler 返回的 ORM 对象或 dict 会被原样序列化——密码哈希、内部状态、软删除标记、关联对象的全部字段都可能一起出去。

## 硬约束（违反会被校验脚本打回）

- **数字与单位一个都不能丢、不能改**：`4 个抓取间隔`、`30 秒`、`23.7 次`、`2.25 版本`、`p99`、`1m`、`2 到 3 倍`、`① ② ③` 全部原样保留。禁止把阿拉伯数字改写成中文数字。
- **不能新增**任何数字或事实。
- `<code>…</code>` 内容、`<strong>…</strong>` 强调位置、`<a href="…">`、`<img>`、HTML 实体（`&lt;` `&gt;` `&amp;` `&quot;`）全部原样保留。拆段时行内标签必须各自闭合。
- **不改结构**：不动标题、表格、`<pre>`、`<div class="mermaid">`、列表项；只改 item 给出的 `<p>` inner HTML。
- 不改语气到网络黑话，不加 emoji，不用「家人们」「拿捏」这类词。
- 术语沿用原文写法，不要换同义词。英文术语、命令、API 名保持原样。

## meta description

每个文件产出 1 条新描述，写在 `descs`：

- ≤60 个中文字，直接说这篇讲什么、解决什么问题。
- 不用「本文介绍了」「全面解析」这类空话。
- 保留核心术语和关键数字。

## 自检（写完输出文件后必须做）

```bash
python3 scripts/shrink/check_out.py <输出路径>
```

退出码必须是 0。有报错就改，改完重跑。

## 交付

最后只回报一行：批次号、处理段数、`check_out.py` 是否通过。不要贴改写全文。
