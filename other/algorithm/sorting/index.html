排序的工程现实：稳定性、内存与外部排序

🏷️ 算法,排序

工程上几乎没人手写排序，但排序相关的线上故障一点都不少：翻页时数据重复、导出文件每次 diff 出一堆伪变更、某个 JVM 服务突然抛出「比较方法违反约定」、离线任务卡在最后一个 reducer 上不动。这些问题的根源都不是「排序算法不会写」，而是稳定性语义、内存约束、比较函数契约和数据分布。这篇只讲这些。

比较排序的下界是怎么来的

「比较排序不可能快过线性对数」不是经验，而是可以证明的。把一次排序看成一棵决策树：每个内部节点是一次比较，每个叶子是一种最终排列。n 个元素有 n 阶乘种排列，所以树至少有这么多叶子；二叉树要容纳这么多叶子，高度至少是它的二进制对数，而这个值近似等于 n 乘以 n 的对数。下面是 3 个元素的完整决策树，6 个叶子，树高 3：

flowchart TB R{"比较 a 与 b"} -->|"a 在前"| N1{"比较 b 与 c"} R -->|"b 在前"| N2{"比较 a 与 c"} N1 -->|"b 在前"| O1["顺序 a b c"] N1 -->|"c 在前"| N3{"比较 a 与 c"} N3 -->|"a 在前"| O2["顺序 a c b"] N3 -->|"c 在前"| O3["顺序 c a b"] N2 -->|"a 在前"| O4["顺序 b a c"] N2 -->|"c 在前"| N4{"比较 b 与 c"} N4 -->|"b 在前"| O5["顺序 b c a"] N4 -->|"c 在前"| O6["顺序 c b a"]

这个下界有两条工程含义。第一，任何声称「线性时间排序」的方案一定没有把键当作只能比较的黑盒——它要么利用了键的位结构，要么假设了分布，要么只是把代价转移到了别处。第二，下界是对比较次数的，不是对时间的：同样的比较次数在不同访存模式下的耗时可以差一个量级，这才是标准库实现之间真正的差距所在。

三种主力排序的真实取舍

只看时间复杂度会得出「快排归并堆排差不多」的错误结论。把维度补全之后，它们几乎没有重叠的适用区间：

算法平均 / 最坏比较次数额外内存稳定访存模式退化触发条件真正适合的场景
快速排序线性对数 / 平方递归栈，对数级否分区是双向顺序扫描，缓存与预取都友好主元选择差；大量重复元素且未做三向切分内存内通用排序，作为混合算法的主体
归并排序线性对数 / 线性对数线性临时数组是顺序读写，适合磁盘与网络流内存不足时退化为原地归并，比较次数升一档需要稳定、需要外部排序、需要可并行的场景
堆排序线性对数 / 线性对数常数否父子跳跃访问，堆一大就频繁未命中基本不退化，但常数始终偏大最坏必须有界；固定大小堆流式求 Top-K
插入排序平方 / 平方，近乎有序时接近线性常数是相邻元素顺序移动，常数极小数据量一大立刻不可用小片段收尾，混合算法的最内层
希尔排序取决于增量序列常数否跨步访问，局部性一般增量序列选得差嵌入式等不能用递归和额外内存的场合
冒泡 / 选择排序平方 / 平方常数冒泡稳定，选择不稳定顺序但交换次数极多无优势区间只用于教学

需要特别澄清的一点：堆排序比快排慢，不是因为复杂度，而是因为随机访存。堆调整时父子下标相差成倍增长，很快就超出缓存行甚至页，每次下沉都可能是一次主存访问；快排的分区始终在连续区间上移动。同理，归并排序的额外内存不是「浪费」，而是换来了顺序访问和稳定性，这也是它能直接扩展成外部排序的原因。

工业默认实现：为什么都是混合算法

没有一个标准库用单一算法。它们的共同结构是：小片段用插入排序压常数，主体用快排或归并，再加一条退化保护。知道你用的语言选了哪套，能解释很多看起来诡异的现象。

库与接口算法稳定额外内存最坏保证必须知道的细节
Go slices.Sort 与 sort.Sortpdqsort，1.19 起替换原实现否递归栈线性对数会检测已有序、逆序、大量重复等模式并走快路径
Go slices.SortStableFunc 与 sort.Stable插入排序加原地对称归并是常数比较次数升到对数平方档用比较次数换内存，比非稳定版慢是预期行为
C++ std::sortintrosort，快排加堆排兜底加插入收尾否对数栈线性对数比较器违反严格弱序是未定义行为，可能越界写内存
C++ std::stable_sort归并，优先申请临时缓冲是线性，申请失败则降级降级后为对数平方档内存紧张时性能会悄悄变差而不报错

稳定性：不要依赖它，要写进比较函数

流传最广的说法是「多级排序要用稳定排序，先排次关键字再排主关键字」。这个做法能跑，但在工程上是个陷阱：稳定性是实现属性，不是跨系统的契约。一旦排序被下推到数据库、被改成并行分片、或者换了语言实现，相同键的相对顺序就会变，而且变得毫无规律。

场景依赖稳定性的写法失效时的现象正确做法
多字段排序排两遍，靠第二遍稳定保住第一遍结果部分数据顺序正确、部分错乱，测试很难覆盖所有级别写进一个比较函数
偏移量翻页按非唯一列排序后用偏移取页同一行在两页重复出现，另一些行被跳过排序键加唯一列兜底，并改用游标分页
前端二次渲染前端按某列重排，依赖后端顺序相同值的行刷新后顺序变化，用户以为数据在跳前端排序也带唯一键兜底
并行或分布式排序依赖单机稳定性同值顺序取决于分片完成顺序，每次跑都不同比较函数里包含唯一键
定时导出与对账两次导出顺序应一致diff 出大量伪变更，掩盖真实差异排序键包含唯一键，导出前显式全序
缓存的列表结果缓存与回源顺序应一致命中缓存和未命中时列表顺序不同结果顺序完全由比较函数决定
 
package rank

import (
	"cmp"
	"slices"
	"strings"
)

type Item struct {
	Sales int    // 销量，降序
	Price int64  // 以分为单位的整数，避免浮点比较
	Name  string
	ID    int64  // 全局唯一，作为最终兜底
}

// SortItems 多级排序的正确写法：把所有级别写进同一个比较函数，
// 最后用唯一键兜底。这样结果与实现是否稳定完全无关，
// 换成数据库排序、并行排序或别的语言都能得到同一个顺序。
func SortItems(items []Item) {
	slices.SortFunc(items, func(a, b Item) int {
		if c := cmp.Compare(b.Sales, a.Sales); c != 0 { // 注意 b 在前 = 降序
			return c
		}
		if c := cmp.Compare(a.Price, b.Price); c != 0 {
			return c
		}
		if c := strings.Compare(a.Name, b.Name); c != 0 {
			return c
		}
		return cmp.Compare(a.ID, b.ID) // 到这里顺序已经完全确定
	})
}

// 只有在无法修改比较逻辑、需要保留调用方既有顺序时，
// 才用稳定版本；它以更多比较次数换取常数级额外内存。
func SortAppendOnly(items []Item, less func(a, b Item) int) {
	slices.SortStableFunc(items, less)
}

比较函数写错：从结果错乱到进程崩溃

排序库对比较函数的要求是严格弱序：元素与自身比较必须为相等、方向可交换、具有传递性，并且「等价」这个关系本身也要可传递。违反之后不是「结果稍微不对」，而是行为没有定义。下面四种写法每天都在被写出来：

package rank

import (
	"cmp"
	"math"
)

type Row struct {
	Price int64
	Score float64 // 可能是 NaN
}

// 错误一：用减法代替比较。int64 相减会溢出，再转 int 还会截断，
// 结果是符号反转，排序结果看起来「大部分是对的」，最难查。
func badSub(a, b Row) int { return int(a.Price - b.Price) }

// 正确：交给 cmp.Compare，或者老老实实写三分支。
func goodPrice(a, b Row) int { return cmp.Compare(a.Price, b.Price) }

// 错误二：把小于等于当成小于。等价元素在两个方向上都返回负数，
// 反对称性被破坏。C++ 里这是未定义行为，标准库可能越界写内存；
// Java 的 TimSort 会抛出比较方法违反约定的异常；Go 里顺序不确定。
func badLessEqual(a, b Row) int {
	if a.Price <= b.Price {
		return -1
	}
	return 1
}

// 错误三：浮点键里有 NaN。NaN 与任何值比较都为假，
// 自反、反对称、传递三条同时被破坏，而且不会报任何错。
func goodScore(a, b Row) int {
	an, bn := math.IsNaN(a.Score), math.IsNaN(b.Score)
	switch {
	case an && bn:
		return 0
	case an:
		return 1 // NaN 统一排到最后，顺序才是确定的
	case bn:
		return -1
	}
	return cmp.Compare(a.Score, b.Score)
}

// 错误四：比较函数带副作用或依赖可变状态，比如读当前时间、
// 读会被并发修改的配置、或者内部累加计数。同一对元素两次比较
// 结果可能不同，等价于破坏传递性，表现是偶发的顺序错乱。
语言比较器违约时的行为能否被发现排查线索
C++ std::sort未定义行为，常见表现是分区越界写内存可能直接崩溃，也可能静默破坏相邻数据用调试版标准库开启比较器校验；崩栈指向 sort 内部
Java 对象排序TimSort 检测到归并前提被破坏时抛异常明确报错，但只在特定数据规模与形状下触发异常栈里出现 TimSort 的 mergeHi 或 mergeLo
Go slices.SortFunc结果顺序不确定，极端情况下 panic通常静默，靠结果异常反推用小规模数据对比较函数做自反与传递性断言
Python sorted不校验，直接给出一个不确定的顺序静默同一输入多次排序结果不一致即可确认

非比较排序：前提比性能重要

计数、基数、桶排序能突破比较下界，代价是对键做了强假设。判断能不能用，只看键的形状，不看数据量。

算法硬前提时间额外内存稳定失效场景
计数排序键是小范围整数，范围已知元素数加键值范围与键值范围成正比用前缀和倒序填充时稳定键范围大或不可控时内存直接爆
基数排序键定长且可按位分段位数乘以每轮的线性代价线性桶空间每轮内部必须用稳定排序，否则整体错有符号整数与浮点未做位变换，符号位让顺序反过来
桶排序键分布已知且大致均匀均匀时接近线性线性取决于桶内排序分布倾斜时退化成单桶内排序
比较排序只需要一个合法比较函数线性对数取决于实现取决于实现无前提，是兜底选择

实际后端场景里，真正跑得动非比较排序的地方比想象中少：状态码、评分、年龄、小时粒度的时间桶这类取值有限的字段可以用计数排序，定长 ID 与定长字符串可以用基数排序。一旦键需要自定义比较逻辑（多级、区域规则、大小写不敏感），就只能回到比较排序。

外部排序：数据量超过内存之后

数据装不进内存时，排序问题从「比较次数」变成「IO 遍数」。标准解法是两阶段多路归并：第一阶段按可用内存切块、块内排序、顺序写成有序段；第二阶段用最小堆同时读多个有序段，边归并边输出。

flowchart TB subgraph P1["第一阶段：生成有序段"] RD["按可用内存切块读入"] SORT["块内排序，用库自带的混合排序"] SPILL["顺序写出一个有序段文件"] end subgraph P2["第二阶段：多路归并"] BUF["每路一个读缓冲，决定顺序读粒度"] HEAP["最小堆维护各路当前最小值"] OUT["输出缓冲，顺序写最终结果"] end subgraph TUNE["两个互相拉扯的参数"] M["单块内存越大，有序段越少"] F["归并路数越多，遍数越少"] end RD --> SORT --> SPILL SPILL --> BUF --> HEAP --> OUT M -->|"决定有序段数量"| F F -->|"路数越多，每路缓冲越小，顺序读退化为随机读"| BUF OUT -.->|"一遍归并不完时结果再作为输入"| BUF

关键取舍就一句话：归并路数与每路缓冲大小共享同一块内存。路数太少要多遍归并，每遍都是一次全量读加一次全量写；路数太多则每路缓冲变小，磁盘上原本顺序的读变成交错的随机读。命令行工具已经把这套逻辑实现好了，直接用比自己写靠得住：

# 外部排序：关键是缓冲大小、临时目录和键的写法
LC_ALL=C sort -S 4G -T /data/tmp --parallel=8 -t $'	'      -k3,3n -k1,1 big.tsv -o sorted.tsv
# LC_ALL=C   按字节序比较，跳过本地化排序规则：更快，且结果可预期
# -S 4G      排序缓冲，决定单个有序段的大小；段越大归并遍数越少
# -T         临时目录必须在容量足够的数据盘上；默认临时目录被写满是最常见的失败原因
# --parallel 并行的是第一阶段块内排序，归并阶段基本受 IO 限制
# -k3,3n     只按第 3 列数值比较；务必写结束列，-k3 的含义是「第 3 列到行尾」
# -k1,1      第二排序键，兼做唯一兜底，保证两次排序结果一致

# 分片已各自有序时只做归并，不要重排，省掉第一阶段
LC_ALL=C sort -m -k3,3n -k1,1 part-*.tsv -o sorted.tsv

# 检查是否已经有序：有序则不输出任何内容，退出码为 0
LC_ALL=C sort -c -k3,3n -k1,1 sorted.tsv && echo ordered

# 只要前 K 条时别做全排序：全排是线性对数，堆是 n 乘以 log K，
# 内存也只占 K；命令行没有现成实现，用语言里的固定大小堆写。

分布式排序与数据倾斜

分布式全序排序的标准做法是范围分区：先采样估计键的分布，切出边界，让每个分区负责一个区间，各分区内部排序后按区间顺序拼接即可。它的软肋也在这里——分布估计错了，就会出现某个分区数据量是别人几十倍的情况，表现为任务进度长时间停在最后一点。

症状成因定位手段修法
绝大多数分区秒级完成，一两个跑几十分钟热点键集中，范围边界切得不均看各分区输入记录数与字节数的分布提高采样率；对热点键单独拆分区
某个分区反复失败重试后拖垮整个作业单分区数据超过单机内存失败任务的内存与落盘量明显高于同批给热点键加随机前缀二次聚合，或改用两阶段
结果整体有序但相同键顺序每次不同依赖了单机排序的稳定性两次运行的结果做 diff比较键里加入唯一列
排序很快但输出阶段极慢输出文件数与分区数不匹配，产生大量小文件观察输出文件数量与平均大小合并输出分区，控制单文件大小
采样阶段本身很慢为估分布做了全量扫描看采样任务的读入量用蓄水池采样或按块抽样，样本量取分区数的几十倍
只需要全局 Top-K 却做了全序需求被翻译成了排序看下游是否只取前若干条各分区先取局部 Top-K，再归并一次

顺带说一个常被忽略的点：「全局有序」和「分区内有序」是两种成本差很多的需求。很多下游其实只需要分区内有序加分区间可枚举，这时候可以完全跳过采样和范围分区，用哈希分区加分区内排序，成本低得多。Top-K 的取舍与堆的用法详见站内栈与队列篇与树篇。

❌
最容易踩的坑
  • 靠「排两遍加稳定排序」实现多级排序：换实现、下推到数据库或改成并行之后，相同键的顺序会变，而且只在部分数据上错。
  • 按非唯一列翻页：第一页末尾的行会在第二页再出现一次，另一些行永远不会被看到。排序键必须补唯一列。
  • 偏移量分页用到很大的偏移：数据库仍要扫过并丢弃前面所有行，代价随页码线性上升，应改成游标分页。
  • 用减法写比较函数：整数相减溢出后符号反转，排序结果「大体正确」，是最难定位的一类问题。
  • 把小于等于当小于：等价元素在两个方向都返回小于，C++ 里是未定义行为可能崩溃，Java 里抛比较方法违约异常。
  • 浮点排序键里混进 NaN：三条序关系同时被破坏，不报错但顺序彻底乱，必须先显式归一化。
  • 比较函数依赖可变状态或带副作用：同一对元素两次比较结果不同，表现为偶发乱序，无法稳定复现。
  • 忘记基数排序每轮内部必须稳定，或者对有符号整数与浮点没做位变换，结果符号位让顺序整段反过来。
  • 用计数排序处理键范围不可控的字段：内存与键值范围成正比，一个异常大的键值就能打爆进程。
  • 外部排序不指定临时目录，默认临时目录写满后任务在跑了几小时之后失败。
  • 调大归并路数却忘了每路都要占读缓冲：顺序读退化成交错随机读，遍数少了但总耗时更长。
  • 只需要 Top-K 却做全量排序：改成固定大小的堆，时间和内存都能降一档。
  • 用 sort -k3 却不写结束列：它的含义是从第 3 列一直比到行尾，和你想要的「只按第 3 列」不是一回事。
  • 忘记设置字节序比较：带本地化规则的排序不仅慢，不同机器的区域设置还会给出不同结果。
