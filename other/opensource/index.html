许可证对比：

SPDX 标识符速查：

SPDX协议全称传染性代表项目
MITMIT License无Rails、Node.js
Apache-2.0Apache License 2.0无Kafka、Spark
BSD-3-ClauseBSD 3-Clause无FreeBSD
GPL-3.0GNU GPL v3.0强Linux 内核、Git
AGPL-3.0GNU AGPL v3.0极强（网络服务）MongoDB、SearXNG
LGPL-3.0GNU LGPL v3.0弱（仅库本身）glibc
MPL-2.0Mozilla Public License 2.0弱（文件级）Firefox

一句话理解传染性：MIT/BSD/Apache 宽松，可闭源；GPL 强传染，用了就得开源；AGPL 最强，连 SaaS 网络服务都要开源。选错协议有法律风险。

兼容性要点：

  • 宽松协议之间自由组合
  • 宽松代码可进 GPL 项目，反之不行
  • Apache 2.0 与 GPL 2.0 不兼容，但与 GPL 3.0 兼容
  • AGPL 传染性最强，任何非 AGPL 项目都别碰

企业用 go-licenses / cargo-license / FOSSA 扫描依赖。

一键扫描项目依赖的许可证

我在公司每次发版前都跑一遍这个脚本，确保没有混入 GPL 协议的依赖：

# Go 项目：扫描所有依赖的许可证
go install github.com/google/go-licenses@latest
go-licenses report ./... 2>/dev/null | awk -F, '{print $2}' | sort | uniq -c

# Python 项目：用 pip-licenses
pip install pip-licenses
pip-licenses --format=markdown

# Node.js 项目：用 license-checker
npx license-checker --summary

参与开源贡献

首次贡献五步：找项目 → 读 CONTRIBUTING.md → 从 good first issue 起步 → Fork/Clone/分支/PR → 响应审查。完整流程：

flowchart LR FIND[找到项目] --> READ[阅读 CONTRIBUTING.md] READ --> ISSUE[浏览 good first issue] ISSUE --> DISCUSS[讨论问题] DISCUSS --> FORK[Fork 仓库] FORK --> CLONE[Clone 到本地] CLONE --> BRANCH[创建功能分支] BRANCH --> CODE[编写代码 加测试] CODE --> COMMIT[Commit 遵循规范] COMMIT --> PUSH[Push 到 Fork] PUSH --> PR[提交 Pull Request] PR --> REVIEW{代码审查} REVIEW -->|通过| MERGE[维护者合并] REVIEW -->|需修改| FEEDBACK[根据反馈修改] FEEDBACK --> PUSH MERGE --> UPSTREAM[同步上游]

贡献黄金法则：先讨论再写代码。在 issue 里说明要做什么，获维护者认可后再开 PR，避免「写两周结果被拒」。

DCO 与 CLA 区别：DCO 是 commit 里加 Signed-off-by 声明（Linux/Git/Apache 用）；CLA 是法律协议，授予版权许可（Google/部分企业项目用）。贡献前确认雇主开源政策。

常见陷阱

  1. 协议选择不当：闭源商业项目别引 GPL/AGPL；动态链接 GPL 也可能触发传染；源文件用 SPDX-License-Identifier 标注。
  2. 不懂 DCO/CLA：PR 被拒常因没签 DCO（git commit -s）；贡献前读 CONTRIBUTING.md。
  3. 维护者倦怠：用户别在 issue 催更，提 PR 修复而非只提 bug，用 Sponsors 资助。
  4. 安全漏洞响应慢：Dependabot/Snyk/Renovate 自动更新；维护者建 SECURITY.md 私下披露，别公开 0day。
  5. fork 导致分裂：先尝试上游贡献；真要 fork 说明原因、保上游同步、换名字（MariaDB/LibreOffice 是成功先例）。
  6. 治理不清：小项目 BDFL 快但依赖个人，大项目上 Apache/CNCF 基金会中立治理。
  7. 文档差：README/API 文档/示例/FAQ 当代码一样 PR 审查，代码变更同步更新文档。
  8. 版本发布不规范：用 SemVer（MAJOR.MINOR.PATCH）+ CHANGELOG + Conventional Commits；破坏性变更先标 deprecated 再下版移除。

FAQ

Q1：闭源商业项目能用开源库吗？
用 MIT/Apache/BSD 没问题；别碰 GPL/AGPL 及其强传染库。

Q2：PR 多久没回应怎么办？
先礼貌 @ 维护者一次；超过合理时间可礼貌 ping 或邮件，别刷催。

Q3：fork 后要和上游同步吗？
除非故意偏离，否则定期 merge 上游 bug 修复，否则自己维护成本极高。

总结

2026 开源生态 AI 工具爆发、Rust 生态成熟、自托管方案丰富。选协议看传染性（宽松→MIT/Apache，强传染→GPL/AGPL）；贡献先讨论再写码、PR 小而专注；项目治理随规模演进，最大风险是维护者倦怠而非技术。

我用开源组件踩过的法律坑

说个真实的。2023 年我们公司一个产品上线后，法务来找我，说我们用的一个开源库是 GPL 协议的，要求我们把整个产品源码公开。我当时就懵了——我们这是个商业闭源产品啊。

后来花了两周，把那个 GPL 库换成了 MIT 协议的替代品，才躲过一劫。从那以后我定了个规矩：引入任何开源库之前，先查协议，MIT/Apache/BSD 随便用，GPL/AGPL 一律不许进商业产品。

GPL 传染不是开玩笑

GPL 是"传染性"协议——你用了 GPL 的库，你的整个产品都得开源。AGPL 更狠，你提供 SaaS 服务都得开源。商业团队引入开源库，法务这关必须过，别心存侥幸。

第一次给开源项目提 PR 的经历

2024 年我第一次给一个开源项目提 PR。那是个 Go 的工具库，我发现一个边界条件下会 panic，就修了一下。提 PR 之前我特别紧张，怕维护者不理我。结果维护者当天就回复了，提了两个修改意见，我改完就合了。整个过程比我想的顺利多了。

常见问题 FAQ

Q1：商业公司用开源软件会被告吗？

合规使用不会。只要你遵守协议——该保留版权声明就保留，该开源就开源，就没问题。出问题的基本都是"忘了看协议"或者"违规用了 GPL"。引入开源组件前走个合规流程，比事后救火强一万倍。

Q2：我能把开源项目拿来改一改卖钱吗？

看协议。MIT/Apache 随便你改、随便卖。GPL 你改了卖也得开源。别把 GPL 项目拿来做闭源商业产品，那是给自己埋雷。

Q3：开源项目没人维护了怎么办？

这叫"维护者倦怠"或"项目死亡"。如果你依赖的开源项目停更了，几个选择：自己 fork 维护、找替代方案、给上游派个维护者。关键是：别把核心业务押在一个只有一个维护者的小项目上，风险太大。

Q4：开源项目的 star 数重要吗？

参考一下就行，别太当真。star 多说明用的人多，但不代表适合你。看 issue 响应速度、看最近提交频率、看社区活跃度，比看 star 实在。一个 500 star 但活跃维护的项目，比一个 5000 star 但两年没动的项目靠谱多了。

Q5：怎么开始参与开源？

从你自己每天用的工具开始。先用熟，发现 bug 就修，写文档就补，从小 PR 开始。别一上来就想给 Linux 内核提 PR，先从你用的小项目开始。参与开源不是为了简历好看，是为了让你自己用的工具变得更好。
