ET 框架概述

ET（Entity Threading）是一个开源的游戏服务器框架，使用 C# 开发，支持热更新。框架设计理念是"简单、易用、功能强大"，广泛应用于手游服务端开发。

核心特性

  • 双端合一：客户端和服务端使用同一套代码，逻辑可复用
  • ECS 架构：Entity-Component-System 设计模式
  • 热更新：支持运行时更新代码，无需重新启动
  • 高并发：基于 KCP 的可靠 UDP 通信
  • 多线程：Actor 模式支持多线程处理

public class Player : Entity

快速开始

环境要求

  • .NET 8.0+
  • Unity 2021.3+
  • MySQL 8.0+ 或 MongoDB

克隆项目

# 克隆 ET 仓库
git clone https://github.com/egametang/ET.git

# 切换到对应版本
cd ET
git checkout release/7.0

# 还原依赖
dotnet restore

运行服务器

# 启动 Gate 服务器
cd ./Server/Model/Module/Message/
dotnet run --project ET.exe -- --AppType=Gate

# 启动 Map 服务器
dotnet run --project ET.exe -- --AppType=Map

# 启动 Manager 服务器
dotnet run --project ET.exe -- --AppType=Manager

运行客户端

在 Unity 中打开 ./Unity/Assets/Bundles/ET.Client 项目，加载 Scenes 目录下的启动场景即可运行。

message C2G_LoginGateRequest

KCP 协议

ET 使用 KCP（可靠 UDP）作为底层传输协议，相比 TCP 具有更低的延迟：

  • RTO 优化：快速重传机制
  • 拥塞控制：自适应拥塞窗口
  • 流式传输：支持大文件分片

消息分发

// 消息处理示例
[MessageHandler]
public class C2G_LoginGateHandler : AMHandler
{
    protected override async ETTask Run(Session session, C2G_LoginGateRequest request)
    {
        // 处理登录逻辑
        var response = new G2C_LoginGateResponse
        {
            Error = 0,
            PlayerId = session.PlayerId
        };
        session.Reply(response);
    }
}

HybridCLR 热更新

HybridCLR 简介

HybridCLR 是 Unity 的 C# 原生运行时热更方案，基于 IL2CPP 解释器实现：

  • 完全兼容：99% 代码兼容 IL2CPP
  • 高性能：解释器性能优化
  • 无缝集成：与 Unity 编辑器完美配合

配置步骤

  1. 从 Package Manager 安装 HybridCLR
  2. 在 Player Settings 中启用 IL2CPP
  3. 配置热更程序集
  4. 打包时勾选 "HybridCLR Data"

使用方法

// 加载热更程序集
var assembly = HybridCLR.RuntimeApi.LoadAssemblyForHotUpdate("HotUpdate.dll");

// 调用热更方法
var type = assembly.GetType("HotUpdate.TestClass");
var method = type.GetMethod("HotUpdateMethod");
method.Invoke(null, null);

ET 框架架构深度解析

ET 框架核心设计

ET 框架是 Unity 的一个开源 C# 客户端-服务端双端框架，由 Excel 开发（原腾讯程序员），特点是使用 C# 协程（async/await）代替传统的回调，实现类协程的异步编程，且客户端和服务端共享代码（逻辑代码可以双端运行）：

  • 组件式架构（Component System）：ET 框架的核心是组件式设计（类似 Unity 的 GameObject-Component，但更轻量）：
    • Entity（实体）：游戏中的基本对象（如玩家、怪物、道具、场景），本身只有 Id（唯一标识）和 Parent/Children（层级关系），没有任何业务逻辑。Entity 是组件的容器，可以挂载多个 Component
    • Component（组件）：附加到 Entity 上的功能模块，包含数据和逻辑。ET 的组件是纯 C# 类（不继承 MonoBehaviour），比 Unity 的 Component 更轻量（不需要序列化、不依赖 Unity 引擎，可以在服务端运行）。组件通过 entity.AddComponent<T>() 添加，entity.GetComponent<T>() 获取
    • Event（事件系统）：ET 的事件系统是解耦的核心——组件之间不直接引用，通过事件通信。定义事件（[Event(EventIdType.XXX)] 特性标记的类实现 IEvent 接口），发布事件（Game.EventSystem.Publish(EventIdType.XXX, args)），事件系统自动调用所有订阅了该事件的处理类。事件系统使得组件可以独立开发、测试、替换
    • Awake/Start/Update 生命周期：ET 的组件有类似 Unity 的生命周期：IAwake（组件添加时调用一次，类似 Awake）、IAwake<T>（带参数的 Awake）、IStart（第一帧 Update 前调用）、IUpdate（每帧调用，需要组件实现 IUpdate 接口才会被调用，不是所有组件都有 Update——减少开销）、IDestroy（组件销毁时调用）。ET 的 Update 是通过事件系统分发的（每帧发布 Update 事件，实现 IUpdate 的组件响应），比 Unity 的反射调用更高效
  • 异步编程模型（async/await 协程）：ET 框架最大的特色是使用 C# 的 async/await 实现类协程的异步编程，替代传统的回调地狱（Callback Hell）：
    • ETTask：ET 自定义的轻量级 Task 类型（类似 C# 的 Task，但更轻量、无 GC、与 Unity 主线程集成）。异步方法返回 ETTask（async ETTask Foo()），使用 await 等待异步操作完成。ETTask 是值类型（struct），不产生 GC（C# 的 Task 是引用类型，每次创建都有 GC 分配）
    • ETTask<T>：带返回值的异步任务（async ETTask<int> GetValue()），await 后返回 T 类型的值
    • 等待机制：await TimerComponent.Instance.WaitAsync(1000)（等待 1000 毫秒）、await SceneType.Scene.GetComponent<T>().XXXAsync()（等待异步 RPC 调用）、await ETTask.WhenAll(task1, task2)（等待所有任务完成）、await ETTask.WhenAny(task1, task2)（等待任一任务完成）。ET 的 await 会自动回到 Unity 主线程（不需要 ConfigureAwait），可以安全访问 Unity API
    • 取消机制：使用 ETCancellationTokenSource 取消异步任务（var cts = new ETCancellationTokenSource(); async ETTask Foo(ETCancellationToken token) { await Timer.WaitAsync(1000, token); }，调用 cts.Cancel() 后，await 会抛出 OperationCanceledException 或立即返回）。ET 的取消是协作式的（需要异步方法检查 token）
    ET 的 async/await 让异步代码看起来像同步代码（顺序执行，没有回调嵌套），极大提高了可读性和可维护性。例如传统的回调式网络请求需要嵌套 3-4 层回调，ET 只需要一行 await。
  • 网络架构（服务端-客户端通信）：
    • 服务端架构：ET 服务端是基于 .NET 的多进程架构（可以分布式部署），包含：AppManager（进程管理，启动/监控子进程）、Game（进程内的游戏世界，包含 Scene 和 Entity）、Scene（场景，如 LoginScene、MapScene、BattleScene，每个 Scene 是独立的实体世界）。服务端支持多进程（每个进程一个 Scene，如登录进程、网关进程、地图进程、战斗进程），进程间通过内部消息通信（基于 TCP/KCP）
    • 消息系统（Message）：ET 的消息是客户端-服务端通信的基本单元，使用 Protobuf（Protocol Buffers）序列化。消息分为：Request（请求，客户端发送，需要服务端响应）、Response（响应，服务端返回，对应 Request）、Message（消息，单向发送，不需要响应，如服务端推送）。消息定义在 .proto 文件中，用 protoc 生成 C# 代码。消息有唯一的 Opcode（操作码，用于路由）
    • RPC 调用：客户端调用服务端方法使用 await session.Call(request)（发送 Request，等待 Response），服务端处理 Request 后返回 Response。ET 的 RPC 是类型安全的（Request 和 Response 类型一一对应，编译时检查）。服务端的消息处理类实现 AMHandler<Request, Response>（带响应的处理器）或 AMHandler<Message>（单向消息处理器），框架自动路由消息到对应的处理器
    • 网络协议：ET 支持 TCP（可靠传输，适合大多数场景）和 KCP（快速可靠 UDP 协议，低延迟，适合实时对战游戏，如 MOBA/FPS）。KCP 是基于 UDP 的可靠传输协议，比 TCP 延迟低（TCP 的拥塞控制和重传机制导致延迟高），适合对实时性要求高的游戏。ET 的网络层是抽象的（INetwork），可以切换 TCP/KCP/WebSocket

8大常见陷阱与最佳实践

  1. 组件生命周期管理不当导致空引用和内存泄漏：ET 的组件（Component）是纯 C# 对象，由 Entity 管理生命周期。管理不当会导致：组件已销毁但仍被引用（访问已销毁的组件抛出 NullReferenceException 或访问无效数据）、组件未正确销毁（从 Entity 移除但引用仍在，GC 无法回收，内存泄漏）、Awake/Start 中访问未初始化的组件（时序问题）、父子 Entity 层级混乱（Parent 设置错误导致销毁时级联销毁错误的对象）。解决：组件的获取与缓存：不要长期缓存 Component 引用（特别是可能被销毁的组件），每次使用时通过 entity.GetComponent<T>() 获取（GetComponent 是 O(1) 字典查找，性能好）。如果需要缓存，在组件的 OnDestroy 中将引用置空。组件销毁：使用 entity.RemoveComponent<T>() 移除组件（会调用组件的 Destroy 生命周期，从 Entity 的组件字典中移除）。不要直接将组件引用置 null（不会触发 Destroy 生命周期，且 Entity 的字典中仍有引用，GC 无法回收）。Entity 销毁时（entity.Dispose()）会自动销毁所有子组件和子 Entity（级联销毁），不需要手动逐个移除。生命周期时序：Awake 在组件添加时立即调用（此时同 Entity 的其他组件可能还未添加），不要在 Awake 中依赖其他组件。Start 在第一帧 Update 前调用（此时同 Entity 的所有组件的 Awake 都已完成），可以在 Start 中获取和依赖其他组件。如果需要在添加组件时立即访问其他组件，使用带参数的 Awake 或在添加后手动调用初始化方法。父子层级：Entity 的 Parent/Children 是层级关系，父 Entity 销毁时会级联销毁所有子 Entity。设置 Parent 时使用 entity.Parent = parentEntity（会自动从旧 Parent 的 Children 中移除，添加到新 Parent 的 Children）。不要手动修改 Children 列表。注意：ET 的 Entity/Component 是引用类型（class），由 GC 管理内存。Dispose 只是逻辑销毁（标记为已销毁、触发 Destroy 事件、从父级移除），内存回收由 GC 完成。如果已销毁的 Entity 仍被其他对象引用，GC 无法回收（内存泄漏），所以要确保 Dispose 后清除所有引用
  2. async/await 异步方法中的异常处理不当导致静默失败：ET 的 async/await 让异步代码简洁，但异常处理有陷阱：异步方法中的异常如果没有被 catch，会被吞掉（静默失败，不会像同步代码那样崩溃，而是异步方法终止，后续代码不执行，且没有任何错误提示——难以排查）。async void 方法的异常会导致崩溃（但 ET 中不应该用 async void）。await 调用的异常会传播到调用方，但如果调用方也是 async 且没有 catch，异常会一直向上传播，直到被某个 catch 捕获或到达顶层（被 ET 的异常处理器记录）。解决：异步方法的异常处理：在异步方法的顶层（如事件处理、UI 按钮点击、消息处理）使用 try-catch 包裹，捕获并记录异常（try { await DoSomethingAsync(); } catch (Exception e) { Log.Error(e); }）。不要在每个异步方法中都 try-catch（会吞掉异常，隐藏 bug），只在需要处理特定异常的地方 catch，其他地方让异常向上传播到顶层统一处理。不要用 async void：async void 方法的异常无法被 await 捕获（会直接抛出到 SynchronizationContext，可能导致崩溃），且无法等待完成。ET 中所有异步方法应该返回 ETTask 或 ETTask<T>。事件处理方法如果需要异步，使用 async ETTask 并在调用处 await（ET 的事件系统支持异步事件处理器）。取消异常：await 被取消时会抛出 OperationCanceledException（或 ET 的 OperationCanceledException），如果不希望取消被当作错误，在 try-catch 中单独处理（catch (OperationCanceledException) { /* 正常取消，不记录错误 */ }）。ETTask 的异常：ETTask 内部会捕获异常并存储，await 时重新抛出。如果一个 ETTask 发生异常但从未被 await（fire-and-forget），异常会被吞掉（静默失败）。所以不要 fire-and-forget 异步方法——要么 await，要么用 CoroutineManager.Instance.StartCoroutine()（ET 的协程管理器，会记录未处理的异常）。注意：ET 框架有全局异常处理器（会记录未捕获的异步异常到日志），但不要依赖它——应该在代码中主动处理可能的异常。排查异步问题时，先看日志中的异常堆栈（ET 会记录完整的异步堆栈）
  3. 事件系统滥用导致逻辑分散难以追踪：ET 的事件系统是解耦的强大工具，但滥用会导致：逻辑过度分散（一个功能的代码分布在多个事件处理类中，难以理解完整流程）、事件命名混乱（事件 ID 重复或语义不清）、事件参数不明确（用 object 传参，需要拆箱，类型不安全）、事件发布后无人处理（拼写错误的事件 ID 导致静默失败）、循环事件（事件 A 触发事件 B，事件 B 又触发事件 A，导致死循环或堆栈溢出）。解决：合理使用事件：事件系统适合：跨模块/跨层级的通知（如"玩家升级"事件，多个系统响应——UI 更新、成就检查、奖励发放）、解耦不需要直接引用的组件（如 UI 层监听业务层事件，不直接引用业务对象）。不适合：组件内部的逻辑调用（直接方法调用更清晰）、有返回值的调用（事件是单向的，不能返回值——需要返回值用方法调用或 RPC）、紧密耦合的时序逻辑（事件的执行顺序不确定，不适合需要严格顺序的流程）。事件定义规范：事件 ID 使用枚举（EventIdType 枚举，避免字符串拼写错误），命名清晰（动宾结构，如 PlayerLevelUp、ItemAdded、BattleStart）。事件参数使用强类型类（定义专门的事件参数类，如 class PlayerLevelUpEventArgs { public Player Player; public int OldLevel; public int NewLevel; }），不要用 object 或 tuple。事件处理类：每个事件处理类用 [Event(EventIdType.XXX)] 标记，实现 IEvent<TEventArgs> 接口（ET 支持泛型事件，类型安全）。处理类的命名清晰（如 PlayerLevelUp_UpdateUI、PlayerLevelUp_CheckAchievement），一个处理类只做一件事（单一职责）。避免循环事件：事件处理中发布新事件时，注意是否会形成循环（A→B→A）。如果需要链式事件，确保有终止条件（如状态检查，满足条件才发布事件）。事件调试：ET 的事件系统可以在发布时打印日志（Log.Debug($"Publish event: {eventId}")），排查事件是否被发布、是否有处理类响应。注意：事件系统的优势是解耦，但解耦的代价是可追踪性降低——调用关系从编译时可见的方法调用变成运行时的事件发布/订阅。团队应该约定事件的使用规范，不要为了解耦而解耦
  4. 服务端多进程/分布式部署时的状态同步问题：ET 服务端支持多进程（每个进程一个 Scene，如登录进程、网关进程、地图进程、战斗进程），进程间通过内部消息通信。多进程部署时常见问题：进程间状态不同步（玩家数据在登录进程修改后，地图进程不知道）、消息路由错误（消息发送到错误的进程）、进程崩溃导致数据丢失（玩家数据只在内存中，进程崩溃后丢失）、跨进程调用延迟（RPC 调用需要网络传输，比进程内调用慢）。解决：进程划分：合理划分进程职责：网关进程（Gate，负责客户端连接、消息转发，无状态）、登录进程（Login，负责登录验证，无状态或轻状态）、地图进程（Map，负责游戏世界逻辑，有状态——玩家位置、NPC、怪物）、战斗进程（Battle，负责战斗逻辑，有状态）、数据库进程（DB，负责数据库读写，无状态，通过消息队列异步处理）。无状态进程可以水平扩展（多实例负载均衡），有状态进程需要按区域/玩家 ID 分片（如地图进程按地图 ID 划分，玩家进入哪个地图就由哪个地图进程管理）。状态同步：玩家数据（等级、道具、属性）是全局状态，应该存储在数据库中，各进程需要时从数据库加载（或通过 DB 进程查询），修改后写回数据库。不要在多个进程中缓存玩家数据（会导致数据不一致）。进程间需要同步的实时状态（如玩家位置、聊天消息）通过消息广播（进程间消息，服务端内部的发布-订阅）。ET 的 Actor 模型（ET 7.0+ 引入了 Actor 机制，每个 Entity 可以是一个 Actor，有自己的邮箱和消息队列，消息按顺序处理，天然支持跨进程通信）可以简化跨进程状态同步——Actor 的位置对调用方透明（框架自动路由到 Actor 所在的进程）。数据持久化：重要数据（玩家数据、游戏进度）必须持久化到数据库（MySQL/MongoDB/Redis），不要只存在内存中。定时保存（如每 5 分钟自动保存）+ 关键操作立即保存（如道具消耗、等级提升）。进程退出前保存所有数据（OnExit 中保存）。使用 Redis 作为缓存（热数据存在 Redis，减少数据库查询），数据库作为持久化存储。跨进程调用优化：减少跨进程 RPC 调用（跨进程调用有网络延迟，比进程内调用慢 10-100 倍）。将相关逻辑放在同一个进程（如玩家的移动和战斗逻辑都在地图/战斗进程，不需要跨进程）。批量调用（一次 RPC 获取多个数据，而不是多次细粒度调用）。缓存跨进程查询结果（短时间内缓存，减少重复查询）。注意：多进程/分布式架构增加了系统复杂度（进程间通信、状态同步、部署运维、故障排查），只有在单进程性能不够时才需要多进程。小型游戏（同时在线几千人）单进程足够，不要过早分布式
  5. 客户端热更新（HybridCLR/ILRuntime）集成问题：Unity 游戏通常需要热更新（不通过应用商店审核，直接更新游戏逻辑），ET 框架常用的热更新方案是 HybridCLR（原 huatuo，原生 C# 热更新，AOT 平台直接执行热更新 DLL）或 ILRuntime（解释执行 C# DLL）。集成热更新时常见问题：热更新代码中无法访问 AOT 代码的某些类型（泛型共享问题）、热更新 DLL 加载失败（路径错误、版本不匹配）、热更新代码的 GC/性能问题（ILRuntime 解释执行比原生慢 3-10 倍）、热更新与编辑器模式冲突（编辑器下不需要热更新，但代码逻辑要兼容）。解决：HybridCLR（推荐）：HybridCLR 是 Unity 的原生 C# 热更新方案（AOT 平台直接 JIT/解释执行热更新 DLL，性能接近原生 AOT 代码，比 ILRuntime 快很多）。ET 框架官方推荐 HybridCLR。集成步骤：安装 HybridCLR 包（Package Manager 添加 Git URL）、配置热更新程序集（在 HybridCLR 设置中添加热更新 DLL 名称）、构建时生成 AOT 泛型补充元数据（AOT 泛型类在热更新中使用时需要补充元数据，否则会报错——HybridCLR 提供自动扫描和生成工具）、加载热更新 DLL（从服务器下载 DLL，用 Assembly.Load 加载，然后反射调用热更新代码的入口方法）。ILRuntime（备选）：ILRuntime 是解释执行 C# DLL 的热更新方案（兼容性好，支持所有 Unity 版本和平台，但性能比 HybridCLR 差——解释执行有开销，特别是频繁调用的方法）。ILRuntime 需要：创建 AppDomain（ILRuntime 的应用域）、加载 DLL（appDomain.LoadAssembly(fs)）、注册委托适配器（热更新代码中使用 AOT 的委托类型需要注册适配器，如 Action、Func、UnityAction）、注册值类型绑定（常用值类型如 Vector3、Quaternion 建议绑定，减少装箱开销）、调用热更新方法（appDomain.Invoke("类名.方法名", instance, args)）。热更新代码规范：热更新代码（Hotfix 程序集）和非热更新代码（AOT 程序集，Model/Module）分离。AOT 程序集定义接口和基类（不热更新），热更新程序集实现接口（可以热更新）。热更新代码不要直接引用 AOT 的具体实现类（依赖接口，便于替换）。注意泛型问题：AOT 程序集中的泛型类（如 List<T>、Dictionary<K,V>）在热更新中使用时，如果 T 是热更新中定义的类型，需要 AOT 泛型补充元数据（HybridCLR）或 ILRuntime 的适配。热更新流程：版本检查（客户端启动时请求服务器最新版本号）、下载热更新资源（DLL + 配置表 + 资源 AssetBundle，用差异下载只下载变化的文件）、校验（MD5/SHA 校验文件完整性，防止下载损坏或被篡改）、加载（加载 DLL 和资源，进入游戏）。热更新资源放在 CDN（加速下载，减轻服务器压力）。注意：热更新是手游的标配，但增加了开发复杂度（双程序集、接口设计、调试困难——热更新代码的断点调试需要特殊配置）。建议项目初期就规划好热更新架构，不要后期再加（改动大）
