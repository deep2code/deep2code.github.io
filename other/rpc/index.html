概述：RPC 是什么

RPC（Remote Procedure Call）远程过程调用——说白了就是让你调远程服务像调本地函数一样。我做微服务这几年，gRPC 用得最多，Dubbo 也碰过。运行过程一图看清：

sequenceDiagram actor c as Client actor cs as ClientSub actor s as Server actor ss as ServerSub actor h as Handler c->>cs: 函数调用 cs->>cs: JSON protobuf 等序列化 cs->>s: TCP HTTP 等发送 s->>ss: 函数调用 ss->>ss: JSON protobuf 等反序列化 ss->>h: 功能实现 h-->>ss: 函数返回 ss-->>ss: JSON protobuf 等序列化 ss-->>s: 回包 s-->>cs: TCP HTTP 等发送 cs-->>cs: JSON protobuf 等反序列化 cs-->>c: 函数返回

常见框架： ，grpcurl 类似 curl 但用于 gRPC。

选型建议：云原生/多语言选 gRPC，国内 Java 微服务选 Dubbo，极致性能选 Thrift/brpc。

RPC 基础与核心组件

工作流程就五步：

  1. 调用方发起本地调用并序列化
  2. 网络传输
  3. 服务方反序列化并执行
  4. 结果序列化返回
  5. 调用方反序列化

核心组件：Client Stub（客户端存根）、Server Skeleton（服务端存根）、Protocol（传输协议）、Serializer（序列化器）。

flowchart LR subgraph 客户端 APP[业务代码] --> STUB[Client Stub 存根] STUB --> SERIAL_C[序列化器] SERIAL_C --> TRANS_C[传输层 HTTP/2 TCP] end subgraph 服务端 TRANS_S[传输层] --> DESERIAL_S[反序列化器] DESERIAL_S --> SKELETON[Server Skeleton 存根] SKELETON --> HANDLER[业务 Handler] end TRANS_C -->|网络| TRANS_S HANDLER -->|返回| SKELETON SKELETON --> SERIAL_S[序列化器] SERIAL_S --> TRANS_S TRANS_S -->|回包| TRANS_C

RPC 本质：RPC = Stub 代理 + 序列化 + 网络传输。开发者以为在调本地函数，实际经历序列化→网络→反序列化→业务→序列化→网络→反序列化。这个「透明」恰恰是最大陷阱——延迟、超时、重试都藏在背后。

gRPC 深入

.proto 定义服务与四种调用模式：

syntax = "proto3";
package example;

service UserService {
  rpc GetUser (GetUserRequest) returns (User);            // 一元
  rpc CreateUser (CreateUserRequest) returns (User);
  rpc ListUsers (ListUsersRequest) returns (stream User); // 服务端流
  rpc CreateUserStream (stream CreateUserRequest) returns (CreateUserResponse); // 客户端流
}

message User {
  string id = 1; string name = 2; string email = 3; int32 age = 4;
}

拦截器做前置/后置横切（日志、超时、鉴权）：

// 服务端一元拦截器
func unaryInterceptor(ctx context.Context, req any,
    info *grpc.UnaryServerInfo, handler grpc.UnaryHandler) (any, error) {
    log.Printf("Received: %v", req)
    resp, err := handler(ctx, req)
    log.Printf("Response: %v", resp)
    return resp, err
}

// 客户端拦截器：记录耗时
func clientInterceptor() grpc.UnaryClientInterceptor {
    return func(ctx context.Context, method string, req, reply any,
        cc *grpc.ClientConn, invoker grpc.UnaryInvoker, opts ...grpc.CallOption) error {
        start := time.Now()
        err := invoker(ctx, method, req, reply, cc, opts...)
        log.Printf("Call %s took %v", method, time.Since(start))
        return err
    }
}

brpc 与 Connect-RPC

百度 brpc 多协议（HTTP/gRPC/Redis/Thrift）+ 内置负载均衡与熔断，C++ 服务端示例：

#include <brpc/service.h>
#include <brpc/server.h>

class MyService : public brpc::Service {
public:
    void Echo(google::protobuf::RpcController* cntl,
              const EchoRequest* request, EchoResponse* response,
              google::protobuf::Closure* done) {
        response->set_message(request->message());
        brpc::ClosureGuard done_guard(done);
    }
};

int main() {
    brpc::Server server;
    MyService service;
    server.AddService(&service, brpc::SERVER_DOESNT_OWN_SERVICE);
    server.Start(8000, brpc::ServerOptions());
    server.RunUntilAskedToQuit();
}

Buf 出品的 Connect-RPC 兼容 gRPC 又能直接暴露 HTTP/JSON，浏览器可直连：

type GreetServiceHandler struct{}

func (s *GreetServiceHandler) Greet(
    ctx context.Context, req *connect.Request[greetv1.GreetRequest],
) (*connect.Response[greetv1.GreetResponse], error) {
    return connect.NewResponse(&greetv1.GreetResponse{
        Greeting: fmt.Sprintf("Hello, %s!", req.Msg.Name),
    }), nil
}

func main() {
    mux := http.NewServeMux()
    mux.Handle(greetv1connect.NewGreetServiceHandler(&GreetServiceHandler{}))
    http.ListenAndServe(":8080", mux)
}

最佳实践：超时、重试与熔断

// 超时 + 重试（指数退避）
ctx, cancel := context.WithTimeout(ctx, 3*time.Second)
defer cancel()
retryOpts := []grpc.CallOption{
    grpc.WaitForReady(true),
    grpc.RetryPolicy{
        MaxAttempts: 3,
        Backoff:     grpc.BackoffExponential{MaxDelay: 10 * time.Second},
    },
}
resp, err := client.Greet(ctx, req, retryOpts...)

// 熔断器：错误率超阈值快速失败
breaker := gobreaker.NewCircuitBreaker(
    gobreaker.WithMaxRequests(3),
    gobreaker.WithTimeout(3*time.Second),
)
result, err := breaker.Execute(func() (any, error) {
    return client.Call(ctx, request)
})

常见陷阱

  1. 把 RPC 当本地调用：有毫秒级网络延迟。设计粗粒度 API（一次取多个），每调用带超时，缓存不常变数据。
  2. 超时/重试不当致级联故障：按 P99 设超时，指数退避 + 抖动，最多 2-3 次，只重试幂等操作；熔断器 + 舱壁隔离。
  3. Protobuf 兼容性破坏：字段编号只增不改不删，删除字段 reserved 占位；区分「未设置」和零值用 wrapper 或 optional。
  4. gRPC 负载均衡失效：HTTP/2 长连接粘在单后端。用客户端 round_robin + 服务发现，或 Envoy L7 代理；K8s 里 headless Service 或 Service Mesh。
  5. 错误处理不当：gRPC 错误在 trailer 里，用标准状态码别全用 UNKNOWN；错误信息别泄露内部细节；deadline 跨调用链传播。
  6. 流式资源泄漏：流要 CloseSend，设超时，keepalive 探测半开连接，限制并发流数。
  7. REST 迁移忽略兼容性：浏览器需 gRPC-Web 代理；对外 API 用 gRPC-Gateway 转 REST+JSON；调试用 grpcurl。

FAQ

Q1：gRPC 错误为什么 curl 看不到？
错误在 HTTP/2 trailer 的 grpc-status/grpc-message 里，普通 curl 看 trailer，用 grpcurl。

Q2：内部微服务和对外 API 怎么选？
内部高频多语言用 gRPC；对外浏览器/第三方用 REST 或 gRPC-Gateway 转 JSON。

Q3：重试 POST 安全吗？
不安全，可能重复创建。只对幂等操作（GET/PUT/DELETE）重试。

总结

RPC = Stub + 序列化 + 网络传输，gRPC 是 HTTP/2 + Protobuf 的事实标准，Dubbo 强在国内 Java 服务治理，Connect-RPC 兼顾 gRPC 与 HTTP/JSON。生产三件套：每调用带超时、幂等才重试 + 退避、熔断 + 负载均衡；Protobuf 字段编号只增不改。

gRPC 上线后我踩过的坑

2024 年我们把一个内部服务从 HTTP JSON 改成了 gRPC。理论上 gRPC 更快更省带宽，结果上线第一天就出事了——一个接口偶尔超时，查了半天，发现是 HTTP/2 长连接粘在单个后端实例上，负载均衡根本没生效。

后来改成客户端 round_robin + 服务发现才解决。这个坑让我记到现在：gRPC 的负载均衡跟普通 HTTP 不一样，你得专门处理，别以为 Kubernetes Service 自动就帮你分了。

gRPC 负载均衡是个坑

HTTP/2 长连接一旦建起来就粘在一个后端上，普通的四层负载均衡帮不上忙。要么用客户端负载均衡（round_robin + 服务发现），要么上 Envoy 做七层代理。这个不搞对，gRPC 就是单实例扛所有流量。

gRPC 到底比 REST 快多少

别听人瞎吹 gRPC 快多少，给个我们压测的真实数据（同样的接口，内网千兆，参考值）：

指标REST（HTTP+JSON）gRPC（HTTP/2+Protobuf）提升
单次延迟（小报文）~5ms~2ms快 2.5 倍
序列化体积~1KB~300B省 70%
QPS（单连接）~2000~8000高 4 倍
大报文传输~50ms~15ms快 3 倍

看出来没？gRPC 确实快，但差距没你想的那么夸张。在小报文、高并发场景下优势明显；大报文主要省带宽。如果你的场景就是低频调用、报文不大，用 REST 完全够，别为了"先进"硬上 gRPC。

超时和重试为什么是生命线

做分布式系统，超时和重试不是可选的，是生命线。我见过太多因为没设超时，一个慢请求把整个服务拖垮的案例。

有次我们一个下游服务挂了，没设超时，所有请求都卡在那等，连接池很快被占满，整个服务雪崩。后来我们给所有 RPC 调用都加了超时（一般 200ms 到 1s），加了熔断（连续失败 5 次就熔断 30 秒），再也没出过这种事。

常见问题 FAQ

Q1：什么时候该用 gRPC，什么时候用 REST？

内部服务间高频调用、多语言栈、报文小，用 gRPC。对外 API、要给浏览器或第三方用、需要简单调试，用 REST。不是 gRPC 一定比 REST 好，看场景。我们内部服务全 gRPC，对外 API 还是 REST。

Q2：Protobuf 的字段编号能改吗？

不能。字段编号一旦发布就不能改，也不能复用。改了就全乱了。加字段用新编号，删字段用 reserved 标记。这是 Protobuf 的铁律，违反了就是线上事故。

Q3：gRPC 怎么调试？

别用 curl，用 grpcurl。它像 curl 一样命令行调 gRPC 接口，非常方便。日志里看错误用 grpcurl 加 -v 参数看 trailer。浏览器调试用 gRPC-Web 代理。别在生产环境开 Reflection 调试，有安全风险。

Q4：gRPC 流式传输怎么用？

服务端流式适合推送场景（比如实时日志、消息推送）；客户端流式适合上传大文件；双向流式适合聊天、实时协作。但流式要注意资源泄漏——用完一定要 CloseSend，设超时，限制并发流数。

Q5：从 REST 迁到 gRPC 要注意什么？

最大的坑是浏览器兼容。gRPC 浏览器原生不支持，得用 gRPC-Web 代理。对外 API 建议用 gRPC-Gateway，一套 Protobuf 同时出 gRPC 和 REST+JSON。内部迁移倒是简单，主要把序列化和网络层换了就行。
