    • TCP 的慢启动

  • HTTP2 改进

    • 二进制分帧层
    • 请求的优先级
    • 服务器推送
    • 头部压缩

  • HTTP2 问题

    • 有序字节流引出的队头阻塞（Head-of-line blocking），使得 HTTP2 的多路复用能力大打折扣
    • TCP 与 TLS 叠加了握手时延，建链时长还有 1 倍的下降空间
    • 基于 TCP 四元组确定一个连接，这种诞生于有线网络的设计，并不适合移动状态下的无线网络，这意味着 IP 地址的频繁变动会导致 TCP 连接、TLS 会话反复握手，成本高昂。

  • HTTP3 改进

    • HTTP3 基于 UDP 协议重新定义了连接，在 QUIC 层实现了无序、并发字节流的传输，解决了队头阻塞问题
    • HTTP3 重新定义了 TLS 协议加密 QUIC 头部的方式，既提高了网络攻击成本，又降低了建立连接的速度
    • HTTP3 将 Packet、QUIC Frame、HTTP3 Frame 分离，实现了连接迁移功能，降低了 5G 环境下高速移动设备的连接维护成本

    sequenceDiagram actor u as 用户 actor l as 断路器 actor s as 服务 u->>l: 请求 l->>s: 转发请求 s-->>l: 成功回包 l-->>u: 转发成功回包 u->>l: 请求 l->>s: 转发请求 s-->>l: 失败 l->>l: 累计失败，达到阀值 l-->>u: 转发失败 u->>l: 请求 l->>l: 检查服务恢复? l-->>u: 回包失败
    • 服务熔断是指调用方访问服务时通过断路器做代理进行访问，断路器会持续观察服务返回的成功、失败的状态，当失败超过设置的阈值时断路器打开，请求就不能真正地访问到服务了。
    • CLOSED：默认状态。断路器观察到请求失败比例没有达到阈值，断路器认为被代理服务状态良好。
    • OPEN：断路器观察到请求失败比例已经达到阈值，断路器认为被代理服务故障，打开开关，请求不再到达被代理的服务，而是快速失败。
    • HALF OPEN：断路器打开后，为了能自动恢复对被代理服务的访问，会切换到半开放状态，去尝试请求被代理服务以查看服务是否已经故障恢复。如果成功，会转成 CLOSED 状态，否则转到 OPEN 状态

  • 降级——采用预设方案行动，针对非核心、非必要服务

浏览器渲染架构与关键路径

理解浏览器如何将 HTML/CSS/JS 转换为屏幕上的像素，是 Web 性能优化的基础。现代浏览器的渲染管线经历了多年演进，核心目标是在 16.7ms（60fps）内完成一帧的渲染。

渲染流水线（Rendering Pipeline）

浏览器的渲染过程分为六个阶段：

  1. HTML 解析（Parsing）：将 HTML 字节流转换为 DOM 树。解析器是增量式的，边接收边解析，遇到 <script> 会阻塞（除非有 async/defer）
  2. CSS 解析（Style）：将 CSS 转换为 CSSOM（CSS Object Model）。CSS 解析不会阻塞 HTML 解析，但会阻塞渲染（因为需要 CSSOM 才能构建渲染树）
  3. 渲染树构建（Layout Tree）：将 DOM 和 CSSOM 合并为渲染树（Render Tree），只包含可见元素（display:none 的元素不在渲染树中）
  4. 布局（Layout/Reflow）：计算每个元素的几何位置和尺寸。从根节点开始递归计算，使用盒模型（Box Model）和包含块（Containing Block）规则
  5. 绘制（Paint）：将渲染树的每个节点绘制为像素。包括文字、颜色、边框、阴影、图片等。绘制是按层（Layer）进行的
  6. 合成（Composite）：将多个图层合并为最终屏幕图像。在 GPU 上执行，通过纹理映射（Texture Mapping）实现

关键优化点：布局和绘制是最昂贵的阶段。现代浏览器通过分层（Layer Promotion）和 GPU 合成来避免重复布局/绘制。使用 transform 和 opacity 动画只会触发合成，不触发布局和绘制。

关键渲染路径（Critical Rendering Path）

关键渲染路径是浏览器从接收 HTML 到首次渲染的完整路径。优化目标是缩短首次内容绘制（FCP）和最大内容绘制（LCP）的时间。

关键资源：

  • HTML：阻塞解析，必须完全下载和解析
  • CSS：阻塞渲染，必须在首次绘制前加载完成（除非是 media="print" 等非匹配媒体）
  • 同步 JS：阻塞 HTML 解析，因为 JS 可能修改 DOM

优化策略：

  • 内联关键 CSS（Above-the-fold CSS），减少外部请求
  • 使用 media 属性标记非关键 CSS，实现条件加载
  • JS 使用 async（异步下载，下载完立即执行）或 defer（异步下载，HTML 解析完后按顺序执行）
  • 预加载关键资源：<link rel="preload">、<link rel="preconnect">、<link rel="dns-prefetch">

JavaScript 引擎：V8 架构深度解析

V8 是 Chrome 和 Node.js 使用的 JavaScript 引擎，其性能来自多层编译架构和高效的垃圾回收。

V8 的执行流水线：

  1. 解析（Parser）：将 JS 源码解析为 AST（抽象语法树）。使用延迟解析（Lazy Parsing），只解析当前需要的函数，函数体在首次调用时才解析
  2. Ignition 解释器：将 AST 编译为字节码（Bytecode），直接解释执行。字节码比机器码小 3-5 倍，减少内存占用
  3. TurboFan 优化编译器：对热点函数（执行次数多的）进行 JIT 编译，生成优化的机器码。使用类型反馈（Type Feedback）假设变量类型，生成特化代码
  4. 去优化（Deoptimization）：如果类型假设失败（如变量类型改变），回退到解释器执行，重新收集类型信息

性能建议：保持变量类型稳定（不要在运行时改变对象的 shape），避免在循环中创建函数，使用 Array 而不是 arguments，这些都能帮助 V8 生成更优的代码。

性能指标与优化实战

Core Web Vitals 深度解析

Google 定义的 Core Web Vitals 是衡量用户体验的核心指标：

  • LCP（Largest Contentful Paint）：最大内容绘制时间，衡量加载性能。目标 < 2.5s。LCP 元素通常是图片、视频封面或大段文字。优化：优化服务器响应时间（TTFB）、预加载关键资源、优化图片（压缩、WebP/AVIF、响应式图片）、延迟加载非关键资源
  • INP（Interaction to Next Paint）：交互到下一次绘制的时间，衡量响应性。目标 < 200ms。2024 年 3 月替代 FID。优化：拆分长任务（Long Task > 50ms）、使用 requestIdleCallback 处理非紧急工作、避免主线程阻塞、使用 Web Worker 处理计算密集型任务
  • CLS（Cumulative Layout Shift）：累积布局偏移，衡量视觉稳定性。目标 < 0.1。优化：为图片和视频设置 width/height 属性（或 aspect-ratio）、为广告和嵌入内容预留空间、避免在已有内容上方插入内容、使用 font-display: swap 避免 FOIT

网络协议与加载优化

现代 Web 的网络层经历了多次演进：

  • HTTP/1.1：文本协议，队头阻塞（Head-of-Line Blocking），同一域名最多 6 个并发连接。优化：域名分片（Sharding）、资源合并（Spriting、Concatenation）
  • HTTP/2：二进制协议，多路复用（Multiplexing），头部压缩（HPACK），服务器推送（Server Push，已废弃）。一个连接可以并行传输多个请求/响应
  • HTTP/3：基于 QUIC（UDP），解决 TCP 层的队头阻塞，支持 0-RTT 握手，连接迁移（网络切换不中断）。2024 年全球使用率超过 30%

缓存策略：

  • 强缓存：Cache-Control: max-age=31536000, immutable，浏览器直接使用本地缓存，不发请求。适用于带哈希文件名的静态资源
  • 协商缓存：ETag / Last-Modified，浏览器发请求验证资源是否变化，未变化返回 304。适用于频繁更新的资源
  • Service Worker：可编程的缓存层，可以实现离线访问、缓存策略定制（Cache First、Network First、Stale-While-Revalidate）

8大常见陷阱与最佳实践

  1. 布局抖动（Layout Thrashing）：在 JavaScript 中交替读取和写入 DOM（如循环中先读 offsetWidth 再修改样式），会强制浏览器多次同步布局。解决：先批量读取，再批量写入，或使用 requestAnimationFrame
  2. 同步 XHR 阻塞：XMLHttpRequest 的同步模式会完全阻塞主线程，包括用户交互。永远使用异步请求，或使用 fetch API
  3. 图片未设置尺寸：图片加载前不知道尺寸，加载后会推开其他内容，导致 CLS。始终设置 width 和 height，或使用 CSS aspect-ratio
  4. 第三方脚本阻塞：广告、分析、社交媒体等第三方脚本通常体积大且加载慢，会阻塞渲染。使用 async/defer，或延迟到交互后加载（如 requestIdleCallback）
  5. 过度使用 CSS 动画：动画 width、height、top、left 等属性会触发布局，性能差。只动画 transform 和 opacity，这两个属性只触发合成
  6. 内存泄漏：未移除的事件监听器、未清理的定时器、闭包引用的 DOM 元素、全局变量累积，都会导致内存泄漏。使用 WeakMap/WeakSet，在组件卸载时清理资源
  7. 事件委托误用：在 document 上绑定大量事件监听器，每次事件都要冒泡到顶层并执行匹配逻辑，影响性能。在最近的共同祖先上绑定，而不是 document
  8. 忽略移动端性能：移动端 CPU 性能通常是桌面的 1/3 到 1/5，内存也更有限。在真实设备上测试（不是 Chrome DevTools 的模拟），控制 JS 体积（< 150KB gzip），避免长时间运行的计算
