算法与数据结构在工程中的真实位置

关于算法有两种同样错误的说法：一种是「面试造火箭、工作拧螺丝，学了没用」，另一种是「刷够题就能写出好系统」。真实情况在中间：你极少手写红黑树，但每天都在为选错容器付代价。真正会影响线上表现的是三件事——选对容器、估对量级、以及知道哪一步的复杂度会随数据增长爆炸。

结构日常工程里的真实落点关键代价选错的典型后果
数组与切片批量数据处理、缓存行友好的顺序遍历随机插入删除要搬移元素在循环里往中间插入元素，复杂度从线性变成平方
哈希表去重、索引、本地缓存无序、扩容时有一次性开销、键要可哈希用它做范围查询或有序输出，只能全量扫描再排序
链表LRU 淘汰链、任务队列的内部实现缓存不友好，随机访问是线性当成数组来按下标访问，遍历开销被放大
栈与队列递归改迭代、限流与缓冲、括号与表达式解析无界队列会把背压变成内存溢出队列不设上限，故障时内存先被打爆
树数据库索引、目录与权限继承、配置合并树高决定查询次数，失衡就退化用递归遍历深层结构，遇到深度异常直接栈溢出
图服务依赖、调用链、任务编排、权限传播环与重复访问必须显式处理依赖里有环却没检测，部署顺序推导或初始化直接死循环

复杂度分析的正确用法不是背记号，而是动手前先做一次量级估算：数据量是千、万还是亿，单次操作要走几趟网络。一个平方复杂度的实现在测试库的一千条数据上毫无问题，上线后数据涨到十万条就直接超时——这类事故几乎全部能在动手前十分钟算出来。

跨服务通信：先选范式，再选框架

很多「架构分歧」本质上是范式没选对就开始比框架。范式的选择只看三个问题：调用方需不需要立刻拿到结果、失败时谁负责重试、以及双方能不能同时升级。答清这三问，用什么框架就是次要问题。RPC 的原理与实现细节在子篇里展开，这里只给横向对照。

范式调用语义耦合与演进失败处理责任适合的场景
进程内函数调用同步，失败即异常编译期绑定，一起发布调用方直接处理同一业务边界内，没必要拆开的逻辑
REST 接口同步请求响应，基于资源语义接口靠文档与约定，容错性高调用方重试，需要幂等设计对外开放、跨团队、浏览器直连
RPC同步，像调本地方法一样调远端接口定义文件是强契约，需同步更新调用方重试，框架提供超时与熔断内部服务间高频调用，看重性能与强类型
消息队列异步，发出即返回解耦，双方可独立发布消费方重试，必须做幂等与死信削峰、耗时任务、失败允许延后重试
事件驱动异步广播，发布者不关心订阅者最松耦合，但全链路难追踪各订阅方各自兜底一次业务动作要触发多个下游时

开源参与与许可证常识

参与开源的门槛比多数人想的低，最有价值的第一步不是提交代码，而是提交一个能复现的问题报告：版本号、最小复现步骤、期望行为与实际行为。维护者最缺的从来不是想法，而是可验证的信息。

许可证则是必须知道边界的部分。下表按传染性强度排列，给出工程上最常被问到的那几个点。这是工程视角的速查，不构成法律意见，落地前以许可证原文与公司法务口径为准。

许可证传染范围闭源商用必须注意
MIT 与 BSD无可以保留版权声明与许可证文本
Apache-2.0无可以含显式专利授权；修改文件要标注，要保留 NOTICE 文件
MPL-2.0文件级弱传染可以你改动的那些源文件本身要以同许可证公开
LGPL库本身可以，但有条件动态链接时自身可闭源；改了库要开源，还要允许用户替换该库
GPL整个衍生作品分发时不行只要对外分发二进制，整个作品要以同许可证开放源码
AGPL整个衍生作品，含网络提供服务提供网络服务即触发不分发二进制、只对外提供服务同样要开源

最常见的误解是「只在服务器上用、不分发二进制，就不受约束」。这条对 GPL 大致成立，但对 AGPL 恰恰相反：通过网络向用户提供功能本身就构成触发条件。另一个误解是「宽松许可证就可以直接抄代码进项目」——即使是 MIT，也必须保留版权与许可证文本。

各子方向的阅读路径

三条路线：面试或系统补基础，按复杂度、线性表、栈队列、树、图、排序、动态规划、贪心回溯的顺序读；要做服务拆分，先看通信范式再进 RPC；想参与开源或评估依赖，直接看开源那篇。

子方向它解决的问题什么时候该读它
算法与数据结构总览 与 复杂度分析量级估算与选型判据动手前想知道这个实现能不能扛住数据增长时
数组与链表 与 栈与队列线性结构的取舍与经典技巧需要搞清容器选择对性能的实际影响时
树与二叉树 与 图论遍历、平衡、最短路与依赖关系处理层级数据、依赖分析或调用链问题时
排序算法稳定性、原地性与实际库实现的取舍要理解标准库排序为什么这么设计时
动态规划 与 贪心与回溯状态定义、剪枝与最优子结构准备面试，或遇到组合优化类问题时
RPC 原理与实现序列化、接口契约、常见框架对比要在内部服务间选通信方案时
开源软件入门从使用到贡献的完整路径想参与社区，或需要评估一个依赖是否可用时
❌
这些基础能力上最容易踩的坑
  • 在循环里对切片做中间插入或删除，复杂度悄悄从线性变成平方
  • 拿哈希表做范围查询和有序输出，最后靠全量扫描加排序兜着
  • 队列和缓冲区不设上限，故障时背压变成内存溢出
  • 用递归处理深度不可控的树或图，线上遇到异常数据直接栈溢出
  • 依赖图里存在环却不做检测，初始化或部署顺序推导陷入死循环
  • 只在小数据集上验证就上线，量级估算这一步整个跳过
  • 把同步调用当默认选项，下游一慢就整条链路一起拖死
  • 用了消息队列却不做幂等和死信，重复消费和消息黑洞同时出现
  • RPC 接口定义文件单方面改动，忘了旧客户端还在跑
  • 以为只在服务端使用就不受许可证约束，忽略了 AGPL 对网络服务的触发条件
  • 宽松许可证的代码直接复制进项目，版权声明与许可证文本一并删掉
  • 提 issue 不给版本号和最小复现步骤，来回几轮后被自动关掉
