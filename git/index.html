命令介绍

  • git rm，删除 WorkDictory 和 Staged/Index 的文件

    • 命令快照
    git rm [--cached] <pathspec>...
    • 带上 --cached，则只删除 Staged/Index，否则 WorkDictory 也删除

  • restore，从指定源恢复

    • 命令快照
     git restore [<options>] [--source=<tree>] [--staged] [--worktree] [--] <pathspec>...
    • 没有带上 --staged，则直接从 Staged/Index 恢复到 WorkDictory
    • 带上 --staged，则从 repo（head 或者 source 指定 commit 或 tag）恢复到 Staged/Index。如果同时要恢复 WorkDictory，则带上 --worktree
    • --source 默认值为 head
    • restore 是 Git 2.23+ 从 checkout/reset 拆分出的恢复命令，现已稳定；旧版本用 checkout/reset 实现同样效果

  • reset，设置 head，Reset current HEAD to the specified state

    • 命令快照——格式 1
     git reset [-q] [<tree-ish>] [--] <pathspec>

    • 从指定的 tree-ish 恢复到 staged/index，tree-ish 不指定就用 head

    • 命令快照——格式 2

     git reset [<mode>] [<commit>]
         This form resets the current branch head to <commit> and possibly updates the index (resetting it to the tree of <commit>) and the working tree depending on <mode>. If
         <mode> is omitted, defaults to --mixed. The <mode> must be one of the following:
    • 把 head 指向 tree-ish
    • mode 不同值含义不同
      • --soft，仅改动 head
      • --mixed（默认值），改动 head 并且 staged/index 恢复为指定 tree-ish，workdictory 不改
      • --hard，改动 head 并且 staged/index、workdictory 都恢复为指定 tree-ish

  • checkout，切换分支或恢复出指定文件

    • 命令快照——格式 1
    git checkout [-f|--ours|--theirs|-m|--conflict=<style>] [<tree-ish>] [--] <pathspec>

    • 没有带上 tree-ish，则直接从 Staged/Index 恢复到 WorkDictory

    • 带上 tree-ish，则从 repo（tree-ish）恢复到 Staged/Index 和 WorkDictory

    • tree-ish 通常是 head、commit 值或 tag 之类

    • 命令快照——格式 2

    git checkout [-q] [-f] [-m] [[-b|-B|--orphan] <new_branch>]

    • 没有带上 -b，则直接切换指定分支，分支必须存在

    • 带上 -b，则创建新分支，并立即切换过去

    • 命令快照——格式 3

    #从远程仓库/分支,创建本地分支,分支名同远程分支一样,两者建立跟踪关系
#切换到新分支,简化操作
git checkout --track remoteRepo/repoBranch

  • revert 返祖，产生新的提交 commit 来回到过去的特定提交

    • 命令快照
     git revert [--[no-]edit] [-n] [-m parent-number] [-s] [-S[<keyid>]] <commit>
 # 撤销最近一次提交：生成一个反向提交，历史不回退
 git revert HEAD
 # 撤销合并提交时必须用 -m 指定保留哪个父分支：-m 1 保留主线，-m 2 保留被合并分支
 git revert -m 1 HEAD

  • rebase 变基原则

    • 只对尚未推送或分享给别人的本地修改执行变基操作清理历史。
    • 绝不对已推送至别处的提交执行变基操作。

# 完全清除git中大文件提交
# 查看大文件
# 使用verify-pack命令查看, pack包里面的最大的10个文件对应的hash值
# 根据rev-list命令来查看, 最大的文件的文件名是什么
git rev-list --objects --all | grep "$(git verify-pack -v .git/objects/pack/*.idx | sort -k 3 -n | tail -10 | awk '{print$1}')"

# 删除大文件
# 注:filter-branch 是旧方案,新仓库一律用 git-filter-repo（见上文「采用工具」一节）——更安全、更快

# 删除大文件（旧方案）

git gc --prune=now
git gc --aggressive --prune=now

# 强制推到远程

# git push origin –-force --tag
git remote prune origin

Git 2025-2026：2.5x 时代与 20 周年

版本节奏与大事记

Git 保持一年约 4 个版本的季度节奏。2025-04-07 恰逢 Git 20 周年（Linus 于 2005-04-07 发布首个版本），GitHub 在 2025-10 举行 Git Merge 2025 庆祝并讨论未来方向。当前最新稳定版为 Git 2.55（2026-06-29，随 Windows 版附带 Git Credential Manager 2.9）。

2024-2026 值得关注的新特性

  • reftable（实验性）：2.45 起实验性支持 reftable 引用后端，超大仓库引用更新更快。
  • SHA-256 互操作：2.45 起支持 SHA-256 仓库的实际互操作，为彻底迁移铺垫。
  • pseudo-merge bitmaps：2.46，合并位图按伪合并分组，大仓库 fetch/merge 提速。
  • 增量多包索引（MIDX）：2.47，incremental multi-pack-indexes，巨仓多包场景索引开销大幅下降。
  • credential helper 增强：2.46 起支持更复杂的安全助手协议，与 GitHub CLI / Credential Manager 集成更深。
  • triangular workflow + gh：2025-04 起 GitHub CLI 支持三角工作流（fork + 主仓 PR 基线）配置，开源协作更顺。

安全台账

  • 2025-01-14：例行安全公告，修复越界读 / 命令注入类问题，建议全版本升级。
  • 2025-07-08：一次公告修复 7 个安全漏洞（影响所有旧版本），修复自 2.50.1 起，务必升级。
  • CVE-2026-32631（Git for Windows）：clone 符号链接指向网络盘会触发 NTLM 认证、泄露 NTLMv2 哈希，修复于 2.53.0.3。
  • 建议始终用当前 stable；内网受控环境至少跟上最近两个大版本并定期跟进安全公告。

AI 编码代理与 Git 的未来（Git Merge 2025）

  • worktrees 普及：并行任务和多分支验证场景广泛使用 worktree，官方和 GitHub 持续推荐。
  • AI coding agents：Cursor、Claude Code 等代理操作 Git 的规范和认证成为议题，Git Merge 2025 专门讨论 AI 代理对 Git 的影响。
  • 下一个 20 年：官方路线聚焦性能优化和新后端（reftable / SHA-256 全面化）、更安全的默认配置、巨仓支持成为常态。

Git 2.40+ 基础新特性

  • git switch / git restore：分离 checkout 的功能，语义更清晰。
    git switch feature-branch  # 切换分支
git switch -c new-feature  # 创建并切换
git restore file.txt       # 恢复文件
git restore --staged file.txt  # 取消暂存
  • --force-with-lease：比 --force 更安全的强制推送，如果远程有新提交会拒绝。
    git push --force-with-lease  # 安全的强制推送
  • 稀疏检出（Sparse Checkout）：只检出部分目录，适合大型仓库。
    git sparse-checkout init --cone
git sparse-checkout set src/api src/web  # 只检出这两个目录
  • 部分克隆（Partial Clone）：按需下载对象，减少初始克隆时间。
    git clone --filter=blob:none --no-checkout https://github.com/repo.git
  • git merge-tree：无需实际合并即可预览合并结果。
  • SCM 管理的 hook：core.hooksPath 可以指定 hook 目录，便于团队共享。

Git 底层原理深度解析

Git 对象模型：Blob、Tree、Commit、Tag

Git 是一个内容寻址文件系统（Content-Addressable File System）：

  .git/objects/ 目录存储所有对象，按 SHA-1 哈希前 2 位分目录：
  .git/objects/
  ├── 01/
  │   └── 55ebc5...  # 对象内容
  ├── 0a/
  │   └── 2c3b4d...
  └── ...

  四种对象类型：

  1. Blob（二进制大对象）
     - 存储文件内容，不存储文件名
     - 内容 = "blob \0" + 文件内容
     - 哈希 = SHA1(内容)
     - 相同内容的文件只存一份（内容寻址）
     - 示例：echo "hello" | git hash-object --stdin
       → ce013625030ba8dba906f756967f9e9ca394464a

  2. Tree（树对象）
     - 存储目录结构，指向 Blob 或子 Tree
     - 每条记录：  \t
     - mode：100644(普通文件)、100755(可执行)、120000(符号链接)、040000(目录)
     - 示例：
       100644 blob ce0136...\tREADME.md
       100644 blob a1b2c3...\tmain.go
       040000 tree d4e5f6...\tsrc

  3. Commit（提交对象）
     - 存储提交元信息，指向一个 Tree
     - 内容：
       tree            # 根目录树
       parent          # 父提交（可多个，合并提交有2个）
       author    
       committer    
       
       
     - 初始提交没有 parent
     - 合并提交有 2 个 parent

  4. Tag（标签对象）
     - 存储带注释的标签，指向一个 Commit
     - 内容：
       object 
       type commit
       tag v1.0.0
       tagger   
       
       
     - 轻量标签（lightweight）只是一个引用，不是对象

  对象关系图：
  Commit → Tree → Blob（文件内容）
    ↓ parent
  Commit → Tree → Blob
    ↓ parent
  Commit → Tree → Blob

  关键特性：
  - 内容寻址：相同内容永远有相同的 SHA-1
  - 不可变：对象一旦创建就不能修改（修改会产生新哈希）
  - 完整性：SHA-1 哈希保证数据不被篡改
  - 去重：相同内容的文件只存一份

Pack 文件与增量存储

Git 松散对象（loose object）的问题：
- 每个对象一个文件，大量小文件影响性能
- 相同文件的不同版本存储完整内容，浪费空间

解决方案：Pack 文件（Packfile）
- 将多个对象打包到一个 .pack 文件中
- 使用增量编码（delta compression）存储相似对象
- 索引文件 .idx 用于快速查找

  .git/objects/pack/
  ├── pack-abc123.idx    # 索引文件（快速查找）
  └── pack-abc123.pack   # 打包文件（对象内容）

  Pack 文件格式：
  - 头部：签名 "PACK" + 版本号 + 对象数量
  - 对象序列：每个对象包含
    - 类型（OBJ_COMMIT/OBJ_TREE/OBJ_BLOB/OBJ_TAG/OBJ_OFS_DELTA/OBJ_REF_DELTA）
    - 大小（压缩前）
    - zlib 压缩的内容（或 delta 数据）
  - 尾部：整个 pack 的 SHA-1 校验和

  增量编码（Delta）：
  - OBJ_OFS_DELTA：基于偏移量引用（相对当前对象的偏移）
  - OBJ_REF_DELTA：基于哈希引用（直接引用基础对象的 SHA-1）
  - Delta 格式：
    - 基础对象大小
    - 目标对象大小
    - 指令序列：
      - 复制指令（Copy）：从基础对象复制 [offset, size] 范围
      - 插入指令（Insert）：插入新数据
  - Git 自动选择最佳的基础对象（相似内容、大小接近）

  触发打包的时机：
  1. git gc：手动垃圾回收和打包
  2. git push：推送前自动打包
  3. 自动：松散对象超过阈值（默认 6700 个）
  4. git repack：手动重新打包

  查看 pack 内容：
  $ git verify-pack -v .git/objects/pack/pack-*.idx
  # 显示每个对象的 SHA-1、类型、大小、偏移量、delta 基础

  性能优化：
  - 大仓库使用 git gc --aggressive（更彻底的打包，耗时更长）
  - 二进制文件使用 Git LFS（大文件存储，不纳入 pack）
  - .gitattributes 配置二进制文件不做 delta（压缩收益低）

合并算法：3-way merge 与 rebase 原理

Git 合并（Merge）的核心是 3-way merge（三路合并）：

  为什么需要 3-way merge？
  - 2-way merge（直接对比两个文件）无法判断谁改了什么
  - 3-way merge 引入共同祖先（base），可以判断每一方的修改
  
  3-way merge 算法：
  输入：base（共同祖先）、ours（当前分支）、theirs（合并分支）
  
  对每个文本块：
  - base == ours == theirs → 无冲突，取该内容
  - base != ours, base == theirs → ours 修改，取 ours
  - base == ours, base != theirs → theirs 修改，取 theirs
  - base != ours, base != theirs, ours == theirs → 双方相同修改，取该内容
  - base != ours, base != theirs, ours != theirs → 冲突！需要人工解决

  冲突标记：
  <<<<<<< HEAD（ours）
  当前分支的内容
  =======
  合并分支的内容
  >>>>>>> branch-name（theirs）

  查找共同祖先（Merge Base）：
  - Git 使用 Lowest Common Ancestor（LCA）算法
  - 在提交图中找到两个分支的最近共同祖先
  - 可能有多个 LCA（criss-cross merge），此时递归合并
  
  递归合并（Recursive Merge，Git 默认策略）：
  - 当有多个共同祖先时，先合并这些祖先生成一个虚拟 base
  - 然后用这个虚拟 base 做 3-way merge
  - 这是 Git 的默认合并策略（-s recursive）

  合并策略（Merge Strategies）：
  1. recursive（默认）：3-way merge，处理多个祖先
  2. resolve：简单 3-way merge，只取一个祖先
  3. octopus：合并超过 2 个分支（git pull 多个远程）
  4. ours：保留当前分支内容，忽略合并分支（记录合并历史）
  5. subtree：子树合并，将合并分支当作子目录

  Rebase 原理：
  - 将当前分支的提交"重新播放"到目标分支之上
  - 步骤：
    1. 找到当前分支和目标分支的共同祖先
    2. 将当前分支从祖先之后的提交保存为补丁（patch）
    3. 将当前分支指针移动到目标分支最新提交
    4. 依次应用每个补丁（生成新的提交，新的 SHA-1）
  - 结果：线性历史，没有合并提交
  - 注意：rebase 会改变提交历史（SHA-1 变化），不要 rebase 已推送的提交

  Merge vs Rebase 选择：
  - Merge：保留完整历史，包含合并提交，适合协作分支
  - Rebase：线性历史，干净，适合个人特性分支
  - 黄金法则：不要 rebase 已经推送到共享仓库的提交
  - git pull --rebase：拉取时 rebase，避免无意义的合并提交

引用、HEAD 与 reflog

Git 引用（Refs）：

  .git/refs/ 目录存储所有引用：
  .git/refs/
  ├── heads/           # 本地分支
  │   ├── main         # 内容：提交 SHA-1
  │   └── feature-x
  ├── tags/            # 标签
  │   ├── v1.0.0       # 轻量标签：提交 SHA-1
  │   └── v2.0.0       # 附注标签：标签对象 SHA-1
  └── remotes/         # 远程跟踪分支
      └── origin/
          ├── main
          └── feature-x

  特殊引用：
  - HEAD：指向当前分支或提交（.git/HEAD）
    - 正常状态：ref: refs/heads/main（指向分支）
    - 分离头指针：直接是提交 SHA-1
  - ORIG_HEAD：危险操作前的 HEAD 位置（merge、rebase、reset）
  - FETCH_HEAD：最近一次 git fetch 的结果
  - MERGE_HEAD：正在合并的分支提交

  reflog（引用日志）：
  - 记录 HEAD 和分支的所有移动历史
  - 存储在 .git/logs/ 目录
  - 格式：    
  - 默认保留 90 天（可达引用）或 30 天（不可达引用）
  
  示例：
  $ git reflog
  a1b2c3d (HEAD -> main) HEAD@{0}: commit: add feature
  d4e5f6g HEAD@{1}: commit: fix bug
  h7i8j9k HEAD@{2}: checkout: moving from feature to main
  
  reflog 的救命作用：
  - 误删分支：git reflog 找到提交，git branch   恢复
  - 误 reset --hard：git reflog 找到之前的 HEAD，git reset --hard 
  - 误 rebase：git reflog 找到 rebase 前的状态，git reset --hard 恢复
  - 黄金法则：只要提交过，Git 几乎总能恢复（除非 gc 清理了）

  查看对象内容：
  $ git cat-file -p     # 查看对象内容
  $ git cat-file -t     # 查看对象类型
  $ git ls-tree         # 查看 tree 对象内容
  $ git show            # 查看提交详情

  Git 内部命令（Plumbing）：
  - git hash-object：计算对象哈希
  - git cat-file：查看对象
  - git update-index：更新索引
  - git write-tree：从索引创建 tree
  - git commit-tree：创建 commit
  - git update-ref：更新引用
  - 日常使用的是 Porcelain（高级命令），底层是 Plumbing

Git 常见陷阱与最佳实践

  • 陷阱1：提交敏感信息 → 密码/密钥不要提交；已提交用 git filter-repo 清除历史；用 .gitignore + pre-commit hook 预防
  • 陷阱2：force push 到共享分支 → 不要 git push --force 到 main/master；用 --force-with-lease 更安全；个人分支可以 force push
  • 陷阱3：大文件提交 → 超过 50MB 的文件用 Git LFS；已提交的大文件用 git filter-repo 清理；.gitignore 排除构建产物
  • 陷阱4：不写提交信息 → 提交信息要清晰：第一行 50 字符内摘要，空行后详细说明；遵循 Conventional Commits（feat/fix/docs/chore）
  • 陷阱5：merge 冲突不理解 → 理解 3-way merge；用 git mergetool；冲突后用 git diff --check 检查残留标记；不要盲目接受一方
  • 陷阱6：rebase 已推送的提交 → 不要 rebase 已推送到共享仓库的提交；rebase 后需要 force push，会影响协作者；个人特性分支可以 rebase
  • 陷阱7：不理解 detached HEAD → 分离头指针状态下的提交会丢失（除非创建分支）；看到 "detached HEAD" 警告要注意；git switch -c 保存提交
  • 陷阱8：git add . 不加选择 → 用 git add -p 交互式选择要暂存的修改；避免把无关修改或调试代码提交；提交前用 git diff --cached 检查
