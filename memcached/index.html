官方文档

Memcached 是读多写少「纯 KV 缓存」场景的首选：协议简单、内存效率高、原生多线程。本页覆盖安装、命令协议、内部结构，以及 2026 年的现状（v1.6.45、Meta 协议、Dragonfly/Valkey 对比），文末可直接查替代选型。

  3. -u 是运行 Memcached 的用户；

  5. -p 是设置 Memcached 监听的端口，默认 11211；

存储命令

command <key> <flags> <expiration time> <bytes>
<value>

参数说明如下：

  1. command set|add|replace|append|prepend
  2. key key 用于查找缓存值
  3. flags 可以包括键值对的整型参数，客户机使用它存储关于键值对的额外信息
  4. expiration time 在缓存中保存键值对的时间长度（以秒为单位，0 表示永远）
  5. bytes 在缓存中存储的字节数
  6. value 存储的值（始终位于第二行）

过期时间规则：expiration ≤ 30 天按相对秒数（60 = 60 秒后过期）；> 30 天按 Unix 时间戳解析。写超大过期值时注意别误传成时间戳，这是最常见的「一写就过期」原因。

expiration time 设置影响

  1. 缓存雪崩：短时间内大量键同时超时失效

  2. 缓存击穿：单个热点 key 失效瞬间被并发打穿

    1. 确实不存在：用布隆过滤器挡在缓存前
    2. 键超时：热点 key 设置永不超时 + 后台异步更新，受最大内存限制

命令 功能
set 没有则新增，有则更新，相当于 add+replace
add 新增键值，有则不操作
replace 替换已存在的键值，不存在则不操作
append 向已存在的键值后面追加数据，不存在则不操作
prepend 向已存在的键值前面追加数据，不存在则不操作

内部结构

Slab Allocator 解决了内存碎片 问题，但按固定大小分配内存块，会有一定的内存浪费（内部碎片）

数据存储与内存结构

Memcached 是纯内存键值存储，没有持久化，重启后数据全部丢失。它使用 Slab 分配器管理内存，通过哈希表和 LRU 链表实现高效查找和淘汰。

无持久化设计

  • 纯内存：所有数据存储在 RAM 中，进程退出即丢失
  • 无磁盘 I/O：读写完全在内存中完成，延迟极低（亚毫秒级）
  • 无快照：不提供 RDB/AOF 等持久化机制
  • 适用场景：缓存、Session 存储、计数器等可丢失数据
  • 配置文件：仅 memcached.conf（启动参数），不存储数据

Slab 分配器

Memcached 将内存划分为不同大小的 Slab Class，每个 Class 管理固定大小的 Chunk，避免内存碎片。

内存分配层级：

  总内存（如 64MB）
  │
  ├── Slab Class 1: Chunk 大小 = 96 bytes
  │   ├── Page 1 (1MB) → 10922 个 Chunk
  │   ├── Page 2 (1MB) → 10922 个 Chunk
  │   └── ...
  │
  ├── Slab Class 2: Chunk 大小 = 120 bytes (96 * 1.25)
  │   ├── Page 1 (1MB) → 8738 个 Chunk
  │   └── ...
  │
  ├── Slab Class 3: Chunk 大小 = 152 bytes (120 * 1.25)
  │   └── ...
  │
  └── Slab Class N: Chunk 大小 = 1MB（最大）

增长因子（growth factor）默认 1.25：
  Class 1: 96 bytes
  Class 2: 96 * 1.25 = 120 bytes
  Class 3: 120 * 1.25 = 150 bytes
  ...
  每个 Item 选择 >= 实际大小的最小 Chunk（内部碎片）

Item 数据结构

typedef struct _stritem {
    struct _stritem *next;      // 哈希表冲突链 next
    struct _stritem *prev;      // 哈希表冲突链 prev
    struct _stritem *h_next;    // 哈希表桶链表 next
    rel_time_t time;             // 最近访问时间（LRU）
    rel_time_t exptime;          // 过期时间
    int nbytes;                  // value 长度
    unsigned short refcount;     // 引用计数
    uint8_t nsuffix;             // flag+key 长度
    uint8_t it_flags;            // Item 标志
    uint8_t slabs_clsid;         // 所属 Slab Class
    uint8_t nkey;                // key 长度
    // 后面紧跟实际数据：
    // [flag (2 bytes)] [key (nkey bytes)] [value (nbytes bytes)]
} item;

哈希表（查找）

哈希表结构：
  item **primary_hashtable;   // 主哈希表（桶数组）
  item **old_hashtable;       // 旧哈希表（扩容时迁移）

  桶数量：默认 16，动态扩容（2 的幂）
  哈希函数：MurMurHash 3（非加密哈希，分布均匀）

  查找流程：
    1. hash(key) & (bucket_count - 1) → 桶索引
    2. 遍历桶链表（h_next），比较 key
    3. 找到返回 item，未找到返回 NULL

  渐进式扩容：
    - 当负载因子 > 1.5 时触发扩容
    - 新表大小 = 旧表 * 2
    - 每次操作迁移部分桶，避免一次性迁移阻塞

LRU 链表（淘汰）

每个 Slab Class 维护独立的 LRU 链表：

  HOT_LRU（热数据）
    ↓ 访问频繁，短期不被淘汰
  WARM_LRU（温数据）
    ↓ 访问中等
  COLD_LRU（冷数据）
    ↓ 访问最少，优先淘汰
  TEMP_LRU（临时数据）
    ↓ 不参与 LRU 排序（如 get 后立即删除）

淘汰策略：
  1. 新 Item 插入时，如果 Slab Class 没有空闲 Chunk
  2. 从 COLD_LRU 尾部淘汰最久未访问的 Item
  3. 如果 COLD_LRU 为空，尝试 WARM_LRU、HOT_LRU
  4. 被淘汰的 Item 从哈希表中移除，Chunk 回收

  LRU 爬虫（LRU Crawler）：
  - 后台线程定期扫描 LRU 链表
  - 清理已过期的 Item（惰性过期 + 主动过期结合）

内存回收机制

  • 惰性过期：get 时检查 Item 是否过期，过期则删除并返回 NOT FOUND
  • LRU 淘汰：内存不足时淘汰最久未访问的 Item（即使未过期）
  • Slab 内回收：被淘汰/删除的 Item 的 Chunk 放回当前 Slab Class 的空闲链表
  • 不跨 Slab 回收：一个 Slab Class 的空闲 Chunk 不能给其他 Class 使用（可能导致内存浪费）
  • 内存不会归还 OS：一旦分配给某个 Slab Class，就不会释放回操作系统

Memcached 2026 现状与对比

维护状态：仍在活跃迭代

Memcached 并未停摆：1.6.x 保持持续发布，1.6.45（2026-07-09） 为当前稳定版，官方 GitHub 仓库维护节奏正常，生产环境可放心继续使用。

  • EXTSTORE：SSD 扩展存储，热数据留内存、冷数据落盘，容量大幅扩展
  • TLS：1.6 起支持加密传输，公网部署可不再裸奔
  • Meta 协议：更高效的读写与 TTL 管理（见下文）

定位始终保持简单：只做 KV 缓存，不做持久化、不玩复杂数据结构——这正是它十年如一日的可靠性来源。

Meta 协议与批量读取

Meta 协议用 mg / ms / ma 等命令替代老式 get / set，一次往返即可完成读取、TTL 刷新与内存管理，比传统命令减少约一半网络往返：

# 批量读取：一次往返拿多个 key
> mg key1 key2 key3
VALUE key1 0 5
hello

# 写入并设置 TTL（60 秒）
> ms key1 60 5
hello
  • 省下的往返在超大 Value、热点 Key 场景收益最明显
  • 配合 me / md（带过期语义的读/删）可实现原子化的分布式锁与限流

集群与扩展方案

  • 官方没有内置集群：水平扩展靠客户端一致性哈希（如 ketama）与虚拟节点，故障时只影响少数缓存键
  • 典型拓扑：多台实例 + Twemproxy / 自研代理层或直连客户端分片
  • 相比 Redis Cluster：Memcached 集群更「裸」，没有元数据与 Gossip 开销，适合纯粹的缓存层

实践要点：缓存层设计成「可整体清空重建」，应用侧对缓存缺失做降级，Memcached 节点增减就无痛了。

替代与竞品：Dragonfly / Valkey

如果嫌 Memcached 太朴素，2026 年有两大主流替代：

  • Dragonfly：多线程共享内存架构，协议同时兼容 Redis 与 Memcached，Memcached 存量应用几乎零改动迁移，单机吞吐在官方基准中数倍于 Redis 单线程
  • Valkey（Linux 基金会）：Redis 7.2 的社区分支，命令集兼容，若组织要求「纯开源治理」且想兼顾数据结构能力可评估替换

架构与多线程模型深度解析

Memcached 是一个高性能的分布式内存对象缓存系统，其设计哲学是简单、快速、无状态。与 Redis 不同，Memcached 不提供持久化、集群、复杂数据类型，而是将这些功能交给客户端实现，自身专注于极致的缓存性能。

多线程架构

Memcached 使用多线程模型（Redis 6.0 前是单线程），充分利用多核 CPU：

  • 主线程（Main Thread）：监听端口，接受新连接，将连接分配给工作线程
  • 工作线程（Worker Thread）：默认 4 个（-t 参数调整），每个线程处理一部分连接的请求。每个工作线程有独立的事件循环（libevent），独立的连接队列
  • 线程间通信：使用管道（Pipe）进行线程间通信。主线程通过管道向工作线程发送新连接，工作线程通过管道向主线程发送统计信息。避免了复杂的锁机制
  • 全局锁：Memcached 的核心数据结构（哈希表、LRU）是全局共享的，操作时需要获取全局锁。这是多线程模型的瓶颈，但由于 Memcached 的操作都是 O(1) 且极快，锁竞争通常不是问题。1.4.0+ 引入了分片锁（每 LRU 队列一个锁），减少锁竞争

事件驱动：Memcached 使用 libevent 库实现异步 IO，每个工作线程运行一个事件循环。连接建立后注册读事件，请求到达时触发回调处理，处理完注册写事件发送响应。这种模型可以在单线程中处理数千个并发连接（C10K 问题的经典解决方案）。

协议与命令格式

Memcached 支持两种协议：

  • 文本协议（Text Protocol）：默认，人类可读，便于调试。命令格式：<command> <key> <flags> <exptime> <bytes> [noreply]\r\n，然后是数据块 <data block>\r\n。响应：STORED、NOT_STORED、EXISTS、NOT_FOUND、VALUE <key> <flags> <bytes>\r\n<data>\r\nEND\r\n
  • 二进制协议（Binary Protocol）：1.3+ 支持，更紧凑、解析更快、支持更多特性（如无返回值操作、批量获取的版本信息）。请求/响应头 24 字节，包含魔数、操作码、键长度、额外信息长度、数据类型、状态、总字节数、Opaque、CAS 值。二进制协议的解析开销比文本协议低约 30%

核心命令：

  • 存储命令：set（覆盖存储）、add（不存在才存储）、replace（存在才替换）、append/prepend（追加/前置数据）、cas（Check And Set，乐观锁）
  • 检索命令：get（获取，支持多 key）、gets（获取带 CAS 值）、gat（Get And Touch，获取并更新过期时间）
  • 删除：delete（删除 key）
  • 自增自减：incr/decr（对 64 位无符号整数操作，非数字值会报错）
  • 统计：stats（通用统计）、stats items（各 Slab 的 item 统计）、stats slabs（Slab 详细统计）、stats settings（配置参数）

内存管理：Slab Allocator 深度解析

Slab 分配机制

Memcached 使用Slab Allocator管理内存，解决了传统 malloc/free 的内存碎片问题：

  • Slab Class：Memcached 将内存分为多个 Slab Class，每个 Class 对应固定大小的 Chunk（数据块）。默认从 96 字节开始，按 1.25 倍增长（-f 参数调整增长因子），直到达到最大 1MB（-I 参数调整，最大支持 128MB）。例如：96B、120B、152B、192B、240B... 1MB
  • Page：每个 Slab Class 以 Page（默认 1MB，-I 同时影响 Page 大小）为单位向系统申请内存。一个 Page 被切分为多个固定大小的 Chunk。例如 1MB Page / 96B Chunk = 约 10922 个 Chunk
  • Chunk：存储实际数据的最小单元。存储数据时，选择能容纳数据的最小 Chunk 大小的 Slab Class。例如 100 字节的数据存在 120 字节的 Chunk 中，浪费 20 字节（内部碎片）
  • 内存分配流程：新数据到达 → 计算数据大小 → 选择最小的能容纳的 Slab Class → 该 Class 有空闲 Chunk 则直接使用 → 没有空闲 Chunk 则申请新 Page（如果还有内存）→ 没有内存则从该 Class 的 LRU 尾部淘汰一个 item

Slab Allocator 的优缺点：

  • 优点：无外部碎片（内存都是 Page 对齐的）、分配/释放 O(1)、内存复用（Chunk 不会归还系统，只会在 Slab 内复用）
  • 缺点：内部碎片（数据小于 Chunk 时浪费空间）、Slab 间内存不共享（一个 Slab 占满内存后，其他 Slab 无法使用，即使有空闲 Chunk）、增长因子设置不当会导致大量浪费

LRU 淘汰与过期机制

Memcached 的 LRU（Least Recently Used）淘汰机制：

  • 每个 Slab Class 独立的 LRU 队列：不是全局 LRU，而是每个 Slab Class 维护自己的 LRU 链表。这意味着：如果 1MB 的 Slab 占满了，即使 96B 的 Slab 有大量空闲，也不会从 96B 的 Slab 借内存，而是淘汰 1MB Slab 中的 item
  • LRU 操作：get 操作将 item 移到 LRU 头部（最近使用），新插入的 item 也在头部。内存不足时从 LRU 尾部（最久未使用）淘汰
  • 过期机制：Memcached 是惰性过期（Lazy Expiration），不会主动扫描过期 item。get 时检查 item 是否过期，过期则返回 NOT_FOUND 并标记为可回收。过期的 item 占用的内存不会立即释放，而是在新数据需要空间时被覆盖（Slab 内的 Chunk 复用）
  • LRU 爬虫（LRU Crawler）：1.4.11+ 引入的后台线程，定期扫描 LRU 队列，回收过期 item。可以通过 lru_crawler 命令启动/停止，lru_maintainer 命令启用自动维护（自动调整 LRU、回收过期、处理 Slab 内存平衡）

CAS 机制与分布式架构

CAS（Check And Set）乐观锁

CAS 是 Memcached 提供的乐观并发控制机制，解决并发更新时的竞态条件：

  • 原理：每个 item 有一个 64 位的 CAS 值（版本号），每次修改 item 时 CAS 值递增。客户端用 gets 获取数据和 CAS 值，修改后用 cas 命令提交，携带获取时的 CAS 值。如果服务端的 CAS 值与客户端携带的一致，说明期间没有被修改，更新成功；如果不一致，返回 EXISTS，更新失败
  • 使用场景：计数器（先 get 当前值，加 1 后 cas 提交，失败则重试）、配置更新（防止覆盖他人的修改）、库存扣减等需要原子性的读-改-写操作
  • 与 Redis 对比：Redis 的 WATCH/MULTI/EXEC 提供类似的乐观锁，但 Redis 还支持 Lua 脚本实现更复杂的原子操作。Memcached 的 CAS 只支持单 key 的读-改-写原子性

分布式：客户端分片与一致性哈希

Memcached 本身是无状态的单节点服务，分布式能力完全由客户端实现：

  • 客户端分片（Client-Side Sharding）：客户端根据 key 的哈希值选择目标节点。最简单的算法是 hash(key) % N（N 是节点数）。这种算法的问题：节点数变化时（扩容/缩容/故障），几乎所有 key 的映射都会改变，导致缓存雪崩
  • 一致性哈希（Consistent Hashing）：将哈希空间（0 到 2^32-1）组织成一个环，每个节点在环上有多个位置（虚拟节点，通常 100-200 个）。key 哈希后在环上顺时针找到最近的节点。节点变化时只影响相邻节点的 key（约 1/N 的数据需要迁移）。虚拟节点解决了节点数据不均的问题
  • 主流客户端支持：spymemcached（Java）、xmemcached（Java）、pylibmc（Python）、libmemcached（C/C++）、go-memcached（Go）等都支持一致性哈希。部分客户端还支持故障转移（节点故障时自动切换到备用节点）和连接池
  • Memcached 不支持的特性：没有主从复制、没有持久化、没有集群管理、没有事务、没有复杂数据类型（只有 String）。这些特性需要在应用层或通过其他组件实现。这是 Memcached 的设计选择：简单的核心，极致的性能

8大常见陷阱与最佳实践

  1. Slab 内存不共享导致的浪费：如果数据大小分布集中在某个 Slab Class，该 Class 会占满所有内存，其他 Class 即使有需求也无法分配。例如大量 1MB 的视频缓存占满内存后，96B 的小缓存无法存储。解决方案：合理设置增长因子 -f（数据大小均匀用 1.25，集中用 1.1），监控 stats slabs 中各 Slab 的 free_chunks 和 evicted，使用 LRU Maintainer（lru_maintainer）在 Slab 间平衡内存
  2. 大 Value 导致的性能问题：默认最大 Value 是 1MB，超过会报错 CLIENT_ERROR bad command line format 或 SERVER_ERROR object too large for cache。大 Value 会：占用大 Chunk（浪费空间）、网络传输慢、序列化/反序列化开销大。最佳实践：Value 控制在 100KB 以内，大对象拆分存储（如用 Hash 结构，但 Memcached 只有 String，需要应用层拆分），或增大 -I 参数（如 -I 5m）
  3. 缓存雪崩（节点故障）：Memcached 节点故障时，该节点的所有缓存同时失效，请求打到数据库。一致性哈希只能减少影响范围（约 1/N），不能完全避免。解决方案：使用一致性哈希 + 虚拟节点减少迁移量、应用层熔断降级、数据库读写分离、缓存预热（节点上线后主动加载热点数据）、使用 Magagent（代理层，支持一致性哈希和故障转移）
  4. 过期时间设置不当：Memcached 的过期时间（exptime）有特殊规则：≤ 30 天（2592000 秒）时视为相对时间（从当前时间起算），> 30 天时视为绝对时间（Unix 时间戳）。如果误将 3600 秒（1小时）当作绝对时间，会立即过期。另外，exptime=0 表示永不过期（但仍可能被 LRU 淘汰）。注意：Memcached 的最大过期时间是 30 天（相对）或任意未来时间（绝对），不要设置为过去的时间戳
  5. 多线程下的 CAS 竞态：CAS 是乐观锁，高并发下可能频繁失败（EXISTS），需要客户端重试。但重试次数过多会导致 CPU 飙升。最佳实践：CAS 操作设置最大重试次数（如 3-5 次），失败后回退到数据库或返回默认值；对于计数器场景，使用 incr/decr（原子操作，不需要 CAS）；避免在 CAS 循环中执行耗时操作
  6. Stats 命令影响性能：stats、stats items、stats slabs 等命令需要遍历全局数据结构，在大内存实例（>10GB）上可能阻塞数百毫秒。不要在业务代码中频繁调用 stats，监控系统应降低采集频率（如每 30 秒一次）。使用 stats cachedump 命令（调试用）会遍历 LRU 队列，生产环境禁止使用
  7. Key 设计不规范：Memcached 的 key 最大 250 字节，不能包含空格和控制字符（\r\n 等）。key 设计应：有前缀标识业务（如 user:1001:profile）、长度适中（过长浪费内存和网络）、避免特殊字符（用 MD5 哈希长 key）、不要包含敏感信息（key 以明文存储，stats 命令可能泄露）。注意：Memcached 是二进制安全的 Value，但 key 不是
  8. 不监控命中率导致的资源浪费：Memcached 的核心价值是缓存命中率，命中率低意味着大量请求打到数据库，同时浪费了 Memcached 的内存和 CPU。用 stats 查看 get_hits 和 get_misses，命中率 = get_hits / (get_hits + get_misses)，应 > 90%。命中率低的原因：缓存容量不足（LRU 频繁淘汰）、过期时间太短、key 设计不合理（大量一次性查询）、数据更新频繁。优化：增大内存、调整过期时间、优化 key 设计、对不常变化的数据用更长 TTL
