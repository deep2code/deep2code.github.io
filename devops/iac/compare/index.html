IaC 工具对比

🏷️ IaC / 选型

2026 年的 IaC 江湖

前四篇都在讲 Terraform，但 IaC 世界早不是一家独大了。2023 年 HashiCorp 把 Terraform 从 MPL 改成 BSL 协议（商业源码许可），社区反弹很大——Linux 基金会接手搞了个 OpenTofu，把 Terraform 1.5 的代码 fork 出来继续走真正开源路线。再加上一直存在的 Pulumi、AWS 自家的 CloudFormation，和 K8s 阵营的 Crossplane，2026 年选 IaC 工具真要好好比一比。

我这几年五个都用过，这篇把真实使用感受摆出来，帮你少走弯路。

语法对比：同一个 VPC 怎么写

最直观的方式是看同一件事怎么写。下面是建一个 VPC 的代码对比：

# Terraform / OpenTofu (HCL)
resource "aws_vpc" "main" {
  cidr_block = "10.0.0.0/16"
  tags = { Name = "main" }
}
// Pulumi (TypeScript)
const vpc = new aws.ec2.Vpc("main", {
  cidrBlock: "10.0.0.0/16",
  tags: { Name: "main" },
});
# CloudFormation (YAML)
Resources:
  VPC:
    Type: AWS::EC2::VPC
    Properties:
      CidrBlock: 10.0.0.0/16
      Tags:
        - Key: Name
          Value: main

看出区别了吧：HCL 和 YAML 都是声明式配置，Pulumi 是用真代码写——你可以用 if/else、循环、函数，灵活度高很多。我个人觉得 HCL 对新手最友好，因为它就是配置；但老程序员会嫌它"图灵完备性不够"，写复杂逻辑很别扭，那种团队用 Pulumi 会爽很多。

状态管理：各家差异最大的地方

这是 IaC 工具之间最本质的区别，直接决定你的运维成本：

CloudFormation 是最省心的——它根本没有 state 文件这个概念，AWS 自己管"堆栈"状态。但代价是只能用 AWS，资源编排能力也受 AWS API 限制。Terraform 灵活但你得自己操心 state。Pulumi 介于中间。

我的真实经历
我们团队 2024 年从 Terraform 切到 OpenTofu，原因就是 BSL 协议——客户问我们"你们用的工具许可证安全吗"，我们答不上来。切过去之后发现几乎零成本：命令从 terraform 换 tofu，代码一行没改，state 直接兼容。现在新仓库默认 tofu。

K8s 集成：别忽略这个维度

如果你团队已经在用 K8s，IaC 工具的 K8s 集成能力很关键：

  • Terraform/OpenTofu：有官方 kubernetes provider，可以用 HCL 管 K8s 资源。但通常只用来"建集群"，集群内资源还是用 Helm/Kustomize。
  • Pulumi：对 K8s 支持很好，能和你的 TypeScript 应用代码放一起。
  • CloudFormation：能建 EKS，但管不了集群内部的 K8s 资源，要配 eksctl 或其他工具。
  • Crossplane：这是它的主场。它把云资源抽象成 K8s CRD，你 kubectl apply 一个 RDS 声明，Crossplane 自动在云上开 RDS。和 ArgoCD Flux 这种 GitOps 工具天然契合。
别用 Terraform 管一切
很多团队一开始想用 Terraform 既管云资源又管 K8s 内部 deployment，结果 K8s 资源更新频繁，state 越来越大，plan 越来越慢。正确分工：Terraform 管集群和外部云资源，K8s 用 Helm/ArgoCD 管集群内部。我踩过这个坑，state 膨胀到几百 MB 之后每次 plan 要跑五分钟。

2026 年选型建议

站在 2026 年，我的判断很明确。先跑一遍这棵决策树，两分钟能定方向：

flowchart TD START[要做 IaC 选型] --> Q1{只用 AWS 吗?} Q1 -->|是| Q2{团队熟 K8s GitOps?} Q2 -->|是| CP[Crossplane] Q2 -->|否| CF[CloudFormation] Q1 -->|多云/多厂商| Q3{团队是纯软件工程师?} Q3 -->|是 会 TS/Python| PU[Pulumi] Q3 -->|否 要通用标准| OF[OpenTofu] OF --> R[先跑通 hello world 再定] PU --> R CF --> R CP --> R
  1. 新项目，多云团队：直接 OpenTofu。真开源、语法兼容 Terraform、CNCF 背书，长期不担心许可证问题。
  2. 存量 Terraform 项目：不急着迁。Terraform 1.x 还能继续用，OpenTofu 兼容，需要时再切。
  3. 纯 AWS、规模不大：CloudFormation 起步，省事免费。等规模大了、要多环境了，再考虑 Terraform。
  4. 团队是纯软件工程师，想写代码：Pulumi。用 TypeScript 写基础设施，享受代码的一切好处（测试、重构、复用）。
  5. 已经 K8s GitOps 重度用户：Crossplane。把云资源也纳入 K8s 统一管控，一套 kubectl 走天下。

最后一句话：没有完美的工具，只有适合你团队的工具。先花一天把每个工具的 hello world 跑一遍，比看十篇评测都管用。

FAQ

Q：Terraform 和 OpenTofu 真的能无缝互操作吗？
语法和 state 格式完全兼容。你可以用 tofu init 一个 terraform 项目，也可以用 terraform init 一个 tofu 项目。唯一要注意的是 registry Module 的路径，有些 OpenTofu Module 在 OpenTofu 自己的 registry 上。

Q：Pulumi 不用自己管 state 是不是更好？
省心是省心，但你把 state 交给 Pulumi SaaS，本质上是多了一个外部依赖。敏感团队选自托管后端。而且 Pulumi 的调试体验不如 HCL 直白——报错是 TypeScript 堆栈，不如 HCL 那种"第几行错了"清楚。

Q：CloudFormation 真的不够用吗？
AWS 自己的服务它都支持，而且新服务通常 CloudFormation 最先支持。短板是跨云、跨账户编排能力弱，复杂架构写 YAML 很痛苦。纯 AWS 小团队真够用。

Q：Crossplane 能替代 Terraform 吗？
在 K8s 生态里可以，但它学习门槛高——你得先懂 K8s CRD、controller、reconcile 那一套。非 K8s 团队别上来就 Crossplane，会头大。

Q：我该学哪个？
学 Terraform/OpenTofu 的 HCL。它是行业通用语，学会了转 Pulumi/CloudFormation 都快。反过来先学 CloudFormation，转 Terraform 也要重新学概念。HCL 是最大公约数。

我的结论

这五篇从入门到选型走完了。总结一下我的路线图：新手学 HCL → 用 OpenTofu 或 Terraform 跑通第一个例子 → 把 state 搬到远程 → 编一套 VPC+ECS+RDS → 抽 Module 进 CI/CD → 需要时再评估要不要换 Pulumi 或 Crossplane。

2026 年 IaC 已经是云原生的基本功，不是加分项。别再手动点控制台了——把你下一次开机器的操作写成代码，就是你 IaC 之路的第一步。祝玩得开心，账单别吓一跳。
