IaC 工具选型：先分清管哪一层

🏷️ IaC 对比

「Terraform 还是 Ansible」这种问题一年能被问上百次，而它问错了：这两个工具不在同一层，不构成替代关系。选型讨论要有结论，第一步永远是先把层次分清楚。本文只谈工具的定位与取舍；声明式模型和协作纪律见同专题主干篇，状态后端与加锁细节详见站内 Terraform 状态管理篇。

先按管什么层分类

层回答的问题代表工具用错层会怎样
资源编排层有哪些云资源、彼此依赖关系、删除时该连带删什么Terraform 与 OpenTofu、Pulumi、CloudFormation、ROS用它去管机器内部配置，就会堆满 local-exec 和远程执行，退化成命令式脚本
配置管理层机器里装了什么、配置文件内容、服务按什么顺序重启Ansible、Chef、Puppet、SaltStack用它管云资源生命周期，无法回答现在有哪些资源，也做不出可靠的删除计划
容器编排层应用怎么调度、怎么灰度、怎么回滚K8s 清单、Helm、ArgoCD（详见站内 Kubernetes 篇）把应用发布塞进资源编排，发一次版要跑全量计划，谁都不敢按确认

三层最本质的差别在管理对象的粒度和生命周期：云资源是外部系统里的实体，需要一份清单来追踪；机器内部状态没法列成清单，只能每次现场探测再收敛；容器应用则是高频替换的，根本不需要长期身份。分不清这点，就会出现「用 Ansible 建 VPC 结果没人知道有哪些 VPC」「用 Terraform 部署应用结果每次发版都在改基础设施仓库」这类经典错位。

Terraform 与 OpenTofu 的分叉

2023 年 Terraform 从 MPL 改为 BSL 许可，核心限制是不允许用它构建与官方竞争的商业产品。企业内部自用基本不受影响，受冲击的是把 IaC 能力封装成平台对外售卖的厂商，社区因此分叉出 OpenTofu，目前由 Linux 基金会托管。

关注点TerraformOpenTofu选型时怎么判断
许可BSL，限制构建竞品开源许可，基金会治理只要你的产品会内嵌 IaC 引擎，就必须走法务评估
配置语法与状态格式HCL与分叉点保持兼容，命令行参数基本一致迁移成本主要在流水线与工具链，而不是配置文件
provider 生态官方 registry 最全可直接使用同一批 provider，另有自己的 registry先确认你依赖的冷门 provider 和私有 module 拉取方式是否可用
版本演进官方主导，新特性先落地社区主导，部分特性实现不同两边都在演进，跨版本特性差异要按当时实际版本核对，不要凭印象
商业配套官方托管平台与企业版功能完整依托第三方平台与自建方案如果重度依赖官方平台的策略与工作流，迁移代价远大于换个二进制

实操上迁移是「换二进制加校验」而不是「改代码」，但必须在非生产环境完整验证一遍，重点是状态可读、provider 可解析、plan 结果与原来一致。

#!/usr/bin/env bash
# 迁移前的等价性验证：在隔离环境跑，全程只读，别碰生产状态
set -euo pipefail

# 1. 把远端状态拉一份到本地做只读比对，并立即备份
terraform state pull > state.baseline.json
cp state.baseline.json "state.backup.$(date +%s).json"

# 2. 用原工具产出基线计划（转 JSON 便于结构化比较）
terraform init -input=false -no-color
terraform plan -input=false -no-color -out=a.plan
terraform show -json a.plan > a.json

# 3. 用候选工具在同一份代码与状态上再跑一次
tofu init -input=false -no-color
tofu plan -input=false -no-color -out=b.plan
tofu show -json b.plan > b.json

# 4. 只比对资源变更集合：字段顺序和元信息差异是噪音，不要直接 diff 全文
for f in a b; do
  python3 -c "
import json,sys
d=json.load(open(sys.argv[1]))
rows=[(r['address'], ','.join(r['change']['actions'])) for r in d.get('resource_changes',[])]
print('\n'.join(sorted('%s %s' % x for x in rows)))
" "$f.json" > "$f.txt"
done

# 两份计划的资源与动作必须完全一致，有差异就逐个查明原因再决定迁不迁
diff -u a.txt b.txt && echo "plan 等价，可以进入灰度迁移"

漂移检测强，refresh 后计划即报告，退出码可判定强，机制同前有漂移检测能力，粒度受服务实现限制弱，只能用检查模式试跑推断
删除与依赖管理强，依赖图求解，能算出销毁顺序强，机制同前强，栈内资源统一编排弱，删除要自己写任务且顺序自己保证

用通用编程语言写 IaC 的取舍

Pulumi 和 CDK 最吸引人的是「终于能写循环和抽象了」。这确实解决了 HCL 的表达力痛点，但请先想清楚代价：基础设施代码的读者不是写它的人，而是凌晨三点被叫起来的值班人。

// 通用语言的优势：类型安全、能抽象、能写单测
interface TierSpec {
  name: string;
  cidr: string;
  public: boolean;
}

// 合理的抽象：一层薄封装，参数显式，读者一眼能推出会建出什么
function makeSubnet(vpcId: pulumi.Input<string>, spec: TierSpec) {
  return new aws.ec2.Subnet(`subnet-${spec.name}`, {
    vpcId,
    cidrBlock: spec.cidr,
    mapPublicIpOnLaunch: spec.public,
    tags: { Name: `subnet-${spec.name}`, ManagedBy: "pulumi" },
  });
}

// 危险的抽象：资源名由多层配置动态拼出，plan 里的资源地址无法反查来源。
// 出故障时想知道某个子网是谁建的，得先在脑子里跑一遍这段代码
const subnets = tiers.flatMap((t) =>
  regions.map((r) =>
    makeSubnet(vpcs[r].id, {
      ...t,
      name: `${r}-${t.name}-${hash(r + t.name).slice(0, 4)}`,
    })
  )
);

// 底线规则：资源的逻辑名必须是稳定且可预测的字符串。
// 名字一变，工具就认为是新资源，等于销毁重建，有状态资源直接丢数据
取舍点通用编程语言（Pulumi、CDK）受限 DSL（HCL、模板 YAML）
表达复杂逻辑循环、条件、函数、类型系统随便用只能用表达式和有限函数，复杂逻辑写起来别扭
测试手段可以写单元测试与属性测试，接入现成测试框架主要靠静态校验、策略规则和计划快照比对
代码可读下限低，容易演化成多层继承与动态拼装高，结构扁平，改哪儿就看哪儿
资源身份稳定性逻辑名容易被动态拼接，一改就触发重建地址由块名与键构成，稳定且好推断
团队协作成本要求评审者同时懂语言与基础设施运维与开发都能读懂，评审门槛低
依赖管理多了一整套包管理与运行时版本问题只需管 provider 版本与锁文件
💡
HCL 的表达力受限，某种程度上是特性

基础设施配置的第一需求是可审阅：任何人打开都能看出会建出什么、改动影响谁。受限的 DSL 迫使配置保持扁平，抽象只能通过 module 这种粗粒度手段完成，反而挡住了「聪明代码」。用通用语言时这道天然护栏没有了，必须自己加规矩：资源逻辑名必须是静态可预测的字符串，抽象层级不超过两层，任何动态生成名字的写法都要在评审时被质疑。

Ansible 的定位要写准

关于 Ansible 有两个说法要纠正。第一，它的幂等不是语言保证的，而是各个模块自己实现的：包管理、文件、服务这类模块会先探测状态再决定动不动，而 shell 与 command 模块只是执行你给的命令，天然不幂等。第二，它不擅长管云资源的生命周期——虽然有云模块，但它没有状态清单，回答不了「现在总共有哪些资源」，也算不出可靠的删除顺序。

- name: 演示幂等由模块保证，而不是由 YAML 保证
  hosts: app
  serial: 2                 # 滚动执行：每批两台，这才是 Ansible 的主场
  max_fail_percentage: 0    # 任一台失败立即停整批，避免坏配置铺开
  become: true

  tasks:
    # 天生幂等：模块会先查当前状态，已达成就跳过
    - name: 安装依赖包
      ansible.builtin.package:
        name: [nginx, jq]
        state: present

    - name: 下发配置文件
      ansible.builtin.template:
        src: nginx.conf.j2
        dest: /etc/nginx/nginx.conf
        validate: nginx -t -c %s    # 校验失败就不落盘，避免把服务配挂
      notify: reload nginx          # 只有内容真变了才触发处理器

    # 反面示例：shell 模块重复执行会重复初始化，没有任何保护
    # - name: 初始化数据目录（错误写法）
    #   ansible.builtin.shell: /opt/app/init-data.sh

    # 正确写法一：用 creates 声明产物，存在就跳过
    - name: 初始化数据目录
      ansible.builtin.shell: /opt/app/init-data.sh
      args:
        creates: /var/lib/app/.initialized

    # 正确写法二：命令本身无法避免重复执行时，明确定义什么算变更、什么算失败
    - name: 同步索引
      ansible.builtin.command: /opt/app/sync-index --dry-run=false
      register: sync
      changed_when: "'updated' in sync.stdout"
      failed_when: sync.rc != 0 and 'already running' not in sync.stderr

  handlers:
    - name: reload nginx
      ansible.builtin.service:
        name: nginx
        state: reloaded
任务类型幂等性必须补的约束不补的后果
包、文件、模板、服务、用户等原生模块模块内部已保证无—
shell 与 command 模块完全不保证用 creates 或 removes 声明产物；用 changed_when 定义变更重跑就重复执行，报告里永远显示已变更，看不出真实差异
拼接文本追加到配置文件不保证改用模板整体渲染，或用行级模块加正则定位跑几次配置文件里出现多份重复段落，服务启动失败
云资源类模块部分保证自己维护资源标识与查询逻辑没有清单可追踪，资源泄漏后无人发现，删除也无从下手
依赖执行顺序的编排（滚动重启、批量补丁）顺序是 Ansible 的强项配 serial 与失败百分比阈值一次性推到全部机器，坏配置瞬间铺满集群

云原生方案与第三方的取舍

维度云原生（CloudFormation、ROS）第三方（Terraform、OpenTofu、Pulumi）
新服务与新特性支持通常最快，发布日即可用要等 provider 跟进，冷门属性偶尔滞后
与云权限体系集成原生，能直接对接云上的角色、审计与事件需要自己设计执行角色与凭证下发
状态与并发服务托管，无需自建后端与锁要自己搭远端后端、开加密与版本化
跨云与跨账号统一抽象做不到，换云等于重写同一套代码组合多个 provider，抽象可复用
迁移成本模板与栈概念绑定该云，迁移基本是重写换云仍要改资源定义，但工具链与流程可保留
异常处理手段栈进入异常状态时可操作空间有限可直接操作状态条目做精细修复，但也更容易改坏
适合谁单云、团队小、重度依赖该云托管服务多云或多账号、有平台团队、需要统一治理

顺序很重要：先定是否多云（这决定了能不能用原生方案），再看团队语言栈与维护意愿（决定 DSL 还是通用语言），然后是已有投入（迁移成本常常是压倒性的），接着判断是否需要管机器内部状态（决定要不要叠加配置管理层），最后按团队规模与治理要求决定要不要引入策略即代码、私有 module 仓库和审批流。

典型组合各自负责交接点容易出错的地方
资源编排加配置管理前者建主机与网络，后者进机器装包改配置前者输出主机清单或标签，后者按标签动态取清单清单手工维护导致新机器漏配，必须走动态清单
资源编排加 GitOps前者建托管集群与节点池，后者部署应用前者输出集群凭证，注入到 GitOps 控制器把 Helm 发布也写进资源编排，发版和基建改动纠缠在一起
原生模板加第三方工具账号治理与基础网络用原生，跨云抽象用第三方原生栈输出，第三方用 data 源只读引用两套系统管同一个资源，互相覆盖且都检测到漂移
资源编排加策略即代码前者描述资源，后者在计划阶段做合规校验对计划文件的结构化输出做规则判定规则只在本地跑、CI 里没接，等于没有约束

最后说一句不要自研 IaC 框架。真要做，你得重新实现依赖图求解、状态管理与加锁、增量 diff、失败恢复，还要跟着云 API 持续维护适配层——这些都是没有护城河的长期成本，而且一旦作者离职，全公司的基础设施就押在一份没人看得懂的代码上。正确姿势是在现成工具上做约束：把常用组合封成经过评审的 module 或组件库、用策略即代码卡住合规项、用流水线固化流程。降低门槛的同时，逃生通道还在。

❌
选型时最容易踩的坑
  • 拿不同层的工具比优劣：资源编排、配置管理、容器编排解决的不是同一个问题，讨论前先确认对方说的是哪一层。
  • 用 Ansible 管云资源生命周期：没有状态清单，半年后没人知道总共有哪些资源，删除也无从下手。
  • 以为 Ansible 剧本天生幂等：shell 与 command 模块不幂等，必须配 creates 或 changed_when。
  • 因为许可问题仓促迁移：内部自用受影响极小，先做等价性验证再决定，别为了政治正确制造一次全量迁移风险。
  • 用通用语言写出三层继承的基础设施代码：值班人半夜读不懂，故障时间直接翻倍。
  • 动态拼接资源逻辑名：名字一变工具就当新资源，等于销毁重建，有状态资源直接丢数据。
  • 单云团队为了将来可能多云而上重型方案：多云需求常年停留在 PPT 上，先解决当下的治理问题更实在。
  • 两套工具管同一个资源：互相覆盖，两边都报漂移，谁也修不好。所有权必须唯一，跨系统只用只读引用。
  • 把应用发布塞进资源编排：发一次版跑一遍全量计划，回滚还要走基础设施审批，发布速度直接崩掉。
  • 只看工具本身不看生态：你依赖的冷门服务有没有 provider、私有 module 怎么托管、能不能接策略校验，比语法优雅重要得多。
  • 低估状态管理的隐性成本：自管状态意味着你要负责加密、版本化、权限与加锁，没有平台团队时这部分很容易长期欠账。
  • 自研引擎：依赖图、状态、加锁、diff、失败恢复都要重写，且要永久跟进云 API 变化，收益远低于成本。
