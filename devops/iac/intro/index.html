第一个 Terraform 项目与日常工作流

🏷️ IaC

这篇是动手篇：把第一个能跑的项目搭出来，并把日常会反复用到的命令、语法和排错手段过一遍。声明式模型、漂移治理、协作纪律那些「为什么」在同专题的主干篇里讲；状态后端与加锁的配置细节详见站内 Terraform 状态管理篇；module 怎么设计、怎么做版本管理详见站内 Module 与最佳实践篇，本文只在需要时提一句。

最小可用项目的结构

一个目录下所有 .tf 文件会被合并解析，文件名对工具没有任何语义——拆文件纯粹是给人看的。但这个约定收益很大：评审时能立刻看出改的是资源、是输入契约还是版本约束；合并冲突也少得多，因为不同人改的往往不是同一类东西。

文件放什么不要放什么为什么单独拆
versions.tfrequired_version、required_providers、provider 块业务资源版本约束是全局前提，改它影响所有人，单独一个文件便于盯
main.tfresource、module、data、locals硬编码的账号 ID、环境专属取值这是评审的主战场，其他噪音越少越好
variables.tfvariable 声明，带 type、description、validation具体取值它是这个根模块或 module 的对外契约，等同接口定义
outputs.tf下游或其他项目需要的 id、地址、名称敏感明文（如口令）输出是给外部消费的，和内部实现分开才能稳定演进
terraform.tfvars本环境的具体取值任何密钥（会进 git 历史）取值随环境变，与代码解耦；生产取值建议按环境目录分开放

一份能直接跑的最小示例

下面这套配置创建一个 VPC、两个可用区的子网、一个安全组和一台实例，带变量与输出。它刻意用了 for_each、data 源、validation、default_tags，这些都是日常真正会用到的写法。

# ---------- versions.tf ----------
terraform {
  # 限定 CLI 大版本，避免同事用差别过大的版本产生不兼容的状态
  required_version = ">= 1.6.0, < 2.0.0"

  required_providers {
    aws = {
      source = "hashicorp/aws"
      # 波浪号加大于号只允许最右一位递增：这里放行 5.60.x 到 5.x，
      # 但不会跳到 6.x。大版本升级必须单独提 PR 并看 plan
      version = "~> 5.60"
    }
  }
}

provider "aws" {
  region = var.region

  # 给所有资源自动打标：排查时能一眼分清哪些是 IaC 管的
  default_tags {
    tags = {
      Env       = var.env
      ManagedBy = "terraform"
      Repo      = "infra-demo"
    }
  }
}

# ---------- variables.tf ----------
variable "region" {
  type        = string
  description = "资源创建的地域"
}

variable "env" {
  type        = string
  description = "环境标识，会进资源名与标签"

  # validation 在 plan 之前就报错，比 apply 到一半失败便宜得多
  validation {
    condition     = contains(["dev", "staging", "prod"], var.env)
    error_message = "env 只能是 dev staging 或 prod。"
  }
}

variable "vpc_cidr" {
  type    = string
  default = "10.20.0.0/16"
}

# map 的 key 是可用区，value 是网段。用 map 而不是 list，
# 是为了让 for_each 能用稳定的 key 做资源标识
variable "subnets" {
  type = map(string)
  default = {
    "a" = "10.20.1.0/24"
    "b" = "10.20.2.0/24"
  }
}

variable "ssh_allow_cidrs" {
  type        = list(string)
  description = "允许 ssh 的来源网段，禁止填全网"
  validation {
    condition     = !contains(var.ssh_allow_cidrs, "0.0.0.0/0")
    error_message = "不允许对全网放开 22 端口。"
  }
}

variable "instance_type" {
  type    = string
  default = "t3.small"
}
# ---------- main.tf ----------
resource "aws_vpc" "main" {
  cidr_block           = var.vpc_cidr
  enable_dns_hostnames = true
  tags                 = { Name = "${var.env}-vpc" }
}

# 这里引用了 aws_vpc.main.id，隐式依赖已经建立，不需要写 depends_on
resource "aws_subnet" "app" {
  for_each          = var.subnets
  vpc_id            = aws_vpc.main.id
  availability_zone = "${var.region}${each.key}"
  cidr_block        = each.value
  tags              = { Name = "${var.env}-app-${each.key}" }
}

resource "aws_security_group" "app" {
  # 用 name_prefix：将来改命名不会因为重名而 apply 失败
  name_prefix = "${var.env}-app-"
  vpc_id      = aws_vpc.main.id

  ingress {
    description = "ssh from office"
    from_port   = 22
    to_port     = 22
    protocol    = "tcp"
    cidr_blocks = var.ssh_allow_cidrs
  }

  egress {
    from_port   = 0
    to_port     = 0
    protocol    = "-1"
    cidr_blocks = ["0.0.0.0/0"]
  }

  lifecycle {
    # 安全组改名会触发重建，先建新的再删旧的，避免中间没有放行规则
    create_before_destroy = true
  }
}

# data 源：镜像不是我们管的资源，用查询而不是硬编码 ID，
# 硬编码 ID 换地域就用不了，而且没人知道那串 ID 是什么
data "aws_ami" "al2023" {
  most_recent = true
  owners      = ["amazon"]
  filter {
    name   = "name"
    values = ["al2023-ami-*-x86_64"]
  }
}

resource "aws_instance" "app" {
  ami                    = data.aws_ami.al2023.id
  instance_type          = var.instance_type
  subnet_id              = aws_subnet.app["a"].id
  vpc_security_group_ids = [aws_security_group.app.id]

  # 根卷加密，删实例时随之删除
  root_block_device {
    encrypted   = true
    volume_size = 20
  }

  lifecycle {
    # 镜像有新版时不要自动重建实例，升级由发布流程决定
    ignore_changes = [ami]
  }

  tags = { Name = "${var.env}-app-1" }
}

# ---------- outputs.tf ----------
output "vpc_id" {
  value       = aws_vpc.main.id
  description = "供其他项目用 data 源引用"
}

output "subnet_ids" {
  # for 表达式把 map 转成 id 列表，够用就好，别写成炫技的嵌套推导
  value = [for s in aws_subnet.app : s.id]
}

output "app_private_ip" {
  value = aws_instance.app.private_ip
}

日常工作流的五个命令

命令什么时候必须跑关键参数典型报错与含义
init首次进目录、改了 provider 版本、改了后端配置、加了新 module-upgrade 才会在版本约束内拉新版并更新锁文件；-reconfigure 用于后端配置变了且不想迁移旧状态；-migrate-state 用于要把状态搬到新后端提示 provider 未安装，多半是换了机器没 init；提示后端配置已变更，就是该加 -reconfigure 或 -migrate-state 了
validate提交前，CI 里必跑纯本地校验，不联网、不读后端类型不匹配、引用了不存在的变量。它查不出云端权限和配额问题
fmt提交前-check -recursive 用于 CI 里只检查不改写唯一作用是消除对齐引起的无意义 diff，让评审只看到真实改动
plan每次变更，且要贴进 PR-out 保存计划文件供 apply 复用；-detailed-exitcode 让脚本判断有无差异；-target 只在排障时用计划里出现大量意外变更，通常是 provider 升级或发生了漂移
apply评审通过后由流水线执行直接传入已保存的计划文件，不要在生产用自动批准报资源已存在通常是状态里没有但云上已有，需要 import 纳管

读懂 plan 的符号是入门阶段最值钱的一件事。整个 plan 输出可以只看两处：每个资源块上方的动作描述，以及左侧的符号。

符号含义风险等级看到它该做什么
加号新建资源低，但要核对数量确认数量与预期一致，别因为变量写错一次建出 50 台
波浪号原地更新属性低到中确认改的属性是否影响线上流量，例如安全组规则、超时时间
减号销毁资源高确认是不是配置里被误删了某段；有状态资源必须先确认备份
减号加斜杠加号销毁后重建最高立刻停下，去属性后找 forces replacement，判断能否绕开
小于等于号读取 data 源无不改动任何东西，只是说明本次会去查询
结尾汇总行新增 修改 销毁三个计数—把它当成变更影响面的第一道闸门，数字异常就不要 apply

变量的四种来源与优先级

优先级从低到高：变量默认值 < 环境变量 TF_VAR_xxx < 自动加载的 tfvars < 显式指定的 tfvars 文件 < 命令行直接传值。踩坑最多的是环境变量，它不出现在任何代码和命令里，一旦本地残留，你的 plan 和同事的就不一样。

来源写法适合场景风险
变量默认值variable 块里的 default确实有合理默认值的参数，如实例规格给环境相关参数设默认值很危险，写错环境也能跑通
环境变量以 TF_VAR_ 开头的同名环境变量流水线注入密钥类输入不可见、易残留，本地与 CI 行为不一致时优先查这里
自动加载的 tfvarsterraform.tfvars 与以 auto.tfvars 结尾的文件单环境目录里的固定取值文件名拼错就静默不生效，要靠 plan 结果反推
显式指定的 tfvarsplan 或 apply 时用 -var-file 指定多环境共用一套代码时指定环境取值忘记带参数会退回默认值，务必在脚本里固定写死
命令行传值plan 或 apply 时用 -var 指定临时覆盖单个值做验证优先级最高，会盖掉所有文件配置，别在生产流程里用
⚠️
sensitive 只是遮眼罩

给变量或输出加 sensitive 之后，终端和计划输出里会显示成被隐藏的占位符，避免密码被贴进 PR 或 CI 日志。但它不加密、不脱敏存储：状态文件里那个属性仍是明文，保存下来的计划文件里也是明文。真正的做法是敏感值由流水线从密钥管理服务注入，或让资源生成随机口令后写入密钥托管服务，同时把状态存储本身当机密资产管理。

provider 与版本约束

「昨天能 apply，今天同一份代码报错」几乎都是版本没锁。provider 是独立发布的二进制，新版本可能改默认值、废弃参数，甚至把某个属性从可原地更新改成触发重建。两道防线：required_providers 里的版本约束负责划定范围，.terraform.lock.hcl 负责把范围内的精确版本和校验和钉死。

约束写法放行范围适用风险
不写版本任何版本，每次 init 都可能不同无最常见的翻车原因，团队之间行为不一致
大于等于某版本该版本以上全部，含大版本跃迁不推荐某天自动跨大版本，语法与属性都可能不兼容
波浪号加大于号写到小版本只放行最右一位递增，例如 5.60 之后的 5.x推荐的日常写法仍会拿到新的小版本，所以锁文件必须入库
等号精确到补丁号只此一个版本合规要求极严的环境升级要改代码，安全补丁跟得慢
锁文件入库钉死精确版本与各平台校验和必须做不入库等于前面的约束只挡了一半

升级 provider 的正确姿势是单独一个 PR：跑 init -upgrade 更新锁文件，然后逐个环境跑 plan。如果升级后 plan 突然出现一堆没人改过的变更，先别当成漂移，多半是新版 provider 对某些属性的默认值或读取方式变了。锁文件还要注意一点：如果团队里有人用不同 CPU 架构或操作系统，init 时带上对应平台参数把多平台校验和都写进锁文件，否则 CI 上会报校验和缺失。

依赖关系与 data 源的边界

执行顺序不是靠你在文件里的书写顺序，而是靠依赖图。引用另一个资源的属性就自动建立了依赖，这是隐式依赖，也是绝大多数情况该用的方式。只有当两个资源之间有真实先后关系但没有任何属性引用时，才用 depends_on——典型场景是权限策略必须先生效，实例启动后才能调用相应接口。

依赖图可以导出来看：terraform graph 输出 DOT 格式，管道给图形工具渲染即可。真正需要它的场合是排查「为什么这两个资源被串行创建」或者「为什么删除顺序不对」。

data 源还承担一个治理职责：不属于你管的资源，必须用 data 引用，不能写成 resource。写成 resource 等于宣称所有权，两边 apply 会互相覆盖；更糟的是你哪天删掉这段配置，plan 会计划销毁别人的资源。

count、for_each 与 lifecycle

这是实践中最重要的一个选择题。两者的差别不在语法，而在资源地址怎么生成：count 用下标，for_each 用键。下标是位置相关的，删掉列表中间一个元素，后面所有元素的地址都会前移——于是它们全部被销毁重建。

# 反面例子：三个环境用 count 创建，删掉中间的 staging
variable "envs" { default = ["dev", "staging", "prod"] }

resource "aws_s3_bucket" "logs_bad" {
  count  = length(var.envs)
  bucket = "logs-${var.envs[count.index]}"
}
# 删掉 staging 后，列表变成 [dev, prod]
#   下标 1 从 staging 变成 prod  -> prod 桶被销毁重建
# plan 会显示 1 destroy 加 1 replace，而你只想删一个

# 正确写法：用 for_each，地址是稳定的键
resource "aws_s3_bucket" "logs" {
  for_each = toset(var.envs)
  bucket   = "logs-${each.key}"
}
# 删掉 staging 只影响 aws_s3_bucket.logs["staging"]，其余资源不动

# for_each 也可以作用在 module 上，成套复制一组资源
module "app" {
  for_each = var.app_regions      # map，key 是地域简称
  source   = "./modules/app"
  region   = each.key
  size     = each.value.size
}

# 已经用 count 写了有状态资源，要换成 for_each 不能直接改代码，
# 必须先迁移状态里的资源地址，否则 apply 会销毁重建：
#   terraform state mv 'aws_s3_bucket.logs_bad[0]' 'aws_s3_bucket.logs["dev"]'
# 操作前务必备份状态（细节详见站内 Terraform 状态管理篇）
flowchart TB Q1{"这批资源彼此完全同质吗"} -->|"同质 且数量会增减"| Q2{"删掉中间一个 能接受后面全部重建吗"} Q1 -->|"每个都有稳定名字或键"| FE["用 for_each 以键作资源标识"] Q2 -->|"不能 有状态或有流量"| FE Q2 -->|"能 例如临时压测机"| CN["才可以用 count 以下标作标识"] FE --> M{"要成套复制一组资源吗"} M -->|"是"| MOD["for_each 作用在 module 上"] M -->|"否"| RES["for_each 作用在 resource 上"]
维度countfor_each
资源地址方括号加下标，位置相关方括号加键，与位置无关
删除中间一个元素后续所有资源销毁重建，这是最大的坑只影响被删的那一个
输入类型数字map 或字符串集合
每个实例差异化配置要靠下标去列表里取，可读性差用 each.key 与 each.value，直观
适合场景同质、无状态、整体重建无影响，如临时压测机几乎所有其他场景，尤其是有状态资源
做条件创建写成 0 或 1，是社区通行做法用空集合或单元素集合，稍绕但同样可行
lifecycle 子项解决什么问题什么时候用误用后果
create_before_destroy重建时先建新的再删旧的，避免删除失败和服务空窗安全组、目标组、启动模板等被引用的无状态资源对名称唯一的资源用它会因重名冲突失败，要配 name_prefix
prevent_destroy任何会销毁该资源的计划直接报错退出数据库、云盘、对象存储桶等有状态资源需要正常下线时得先改代码去掉它，属于预期成本
ignore_changes忽略指定属性的外部改动，消除 plan 噪音厂商自动改的属性、交给伸缩策略管的副本数范围写太宽等于资源脱管，漂移永远发现不了
replace_triggered_by指定的其他资源变化时，主动重建本资源配置变更后必须重启才生效的场景指向了频繁变化的资源，会导致意外的反复重建

在流水线里跑 plan 并贴回 PR

协作纪律的技术落点就是这段脚本：PR 阶段只做只读的 plan 并把摘要贴回评论，apply 留到合并后由带审批的任务执行。注意计划文件里含明文属性，所以贴的是摘要不是全文。

#!/usr/bin/env bash
# PR 阶段的只读检查：fmt + validate + plan，结果贴成 PR 评论
set -euo pipefail
ENV_DIR="envs/${TARGET_ENV:?必须指定目标环境}"
cd "$ENV_DIR"

terraform fmt -check -recursive -no-color   # 只检查不改写，格式不对直接失败
terraform init -input=false -no-color
terraform validate -no-color

# 保存计划文件：apply 阶段复用它，保证执行的就是评审过的内容
set +e
terraform plan -input=false -no-color -lock-timeout=5m \
  -var-file="${TARGET_ENV}.tfvars" -detailed-exitcode -out=tf.plan
CODE=$?
set -e
[ "$CODE" -eq 1 ] && { echo "plan 失败"; exit 1; }

# 结构化输出比解析正文可靠：用 JSON 统计各类动作数量
terraform show -json tf.plan > tf.plan.json
python3 - <<'PY' > summary.md
import json
acts = {}
rep = []
d = json.load(open("tf.plan.json"))
for r in d.get("resource_changes", []):
    a = ",".join(r["change"]["actions"])
    acts[a] = acts.get(a, 0) + 1
    # create 与 delete 同时出现就是销毁重建，必须在评论里点名
    if set(r["change"]["actions"]) == {"create", "delete"}:
        rep.append(r["address"])
print("### Terraform Plan 摘要")
print("")
for k, v in sorted(acts.items()):
    print("- " + k + ": " + str(v))
if rep:
    print("")
    print("**以下资源会被销毁重建，需要显式确认：**")
    for a in rep:
        print("- " + a)
PY

# 贴成评论；计划全文不要贴，里面可能有明文敏感属性
gh pr comment "$PR_NUMBER" --body-file summary.md
# 有销毁重建时给 PR 打标签，配合分支保护要求额外审批人
grep -q "销毁重建" summary.md && gh pr edit "$PR_NUMBER" --add-label "needs-infra-approval"
exit 0

排错思路

症状最可能的原因怎么确认处理
plan 出现一大堆没人改过的变更provider 被升级，或线上发生漂移看锁文件是否刚变过；用 state show 对比某个资源的状态与云上实际值provider 问题就先回退版本再逐项评估；漂移则判断该补配置还是收敛
apply 报资源已存在云上已有该资源但状态里没有到控制台按名称查是否真实存在用 import 纳管，再 plan 直到无差异；不要手工删线上资源图省事
apply 中途失败，再跑又报错状态与现实不一致，部分资源半成品备份状态后跑 plan，看工具认为还差什么缺状态的用 import 补，状态里有而云上没了的移除对应条目
plan 长时间卡住不动在等状态锁，或者 provider 在重试云 API看输出里是否提示正在获取锁；加日志级别环境变量看请求详情确认无人变更后再按提示解锁（务必先确认，细节详见状态管理篇）
同一份代码本地与 CI 结果不同本地残留 TF_VAR_ 环境变量，或凭证指向了不同账号清空相关环境变量重跑；打印当前调用者身份确认账号把变量来源固定成 tfvars 文件，凭证统一走角色
删除资源时失败仍被其他资源引用，或有删除保护、桶非空读报错里的依赖提示先解引用或清空内容；对需要平滑替换的资源加 create_before_destroy
❌
新手最容易踩的坑
  • 对有状态资源用 count：删掉列表中间一个元素，后面的资源全部销毁重建，数据库和存储桶会直接丢数据。默认就用 for_each。
  • 不提交锁文件：每个人 init 到的 provider 版本都不一样，于是出现「我这儿能跑」的经典场面。
  • 把 apply 的自动批准写进脚本图省事：等于放弃了 plan 这道唯一的预览关卡。
  • 硬编码镜像 ID、账号 ID、可用区：换地域或换账号全线报错。该用 data 源查询，或提成变量。
  • 把密码写进 tfvars 并提交：git 历史删不掉，只能当作已泄露去轮换密钥。
  • 以为加了 sensitive 就安全：状态文件和计划文件里仍是明文。
  • 用 -target 当日常手段：它会跳过部分依赖的刷新，容易让状态与现实进一步偏离。只在排障时临时用。
  • 安全组和目标组用固定 name：以后任何改名都触发重建，还会因为新旧重名而 apply 失败。用 name_prefix。
  • 用 destroy 删单个资源：它默认销毁整个根模块的全部资源。删单个应当改配置后 apply。
  • ignore_changes 直接忽略整个资源：等于让这个资源脱离管理，漂移检测彻底失效。
  • 为了 DRY 把 locals 写成层层嵌套的表达式：半年后没人能算出某个值是怎么来的，出问题时连排查入口都找不到。
  • apply 失败后凭直觉重跑或手改状态：任何状态操作前先备份，并确认没有第二个人同时在变更。
