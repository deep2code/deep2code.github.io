Terraform 入门与 HCL 语法

🏷️ IaC / Terraform

从零跑通第一个例子

这篇不讲概念，直接带你从零写一个能跑的 Terraform 配置。我假设你已经装好 terraform CLI（2026 年我用 1.10.x，OpenTofu 用户命令把 terraform 换成 tofu 即可，语法完全一样），并且手上有一个 AWS 账号或者阿里云账号。

先建个工作目录，所有 .tf 文件放一起——Terraform 会把当前目录下所有 .tf 当作一个整体来解析：

mkdir demo && cd demo
touch main.tf variables.tf outputs.tf
# 配好你的云凭证，我习惯用 profile 而非硬编码 key
export AWS_PROFILE=dev

四个命令的循环

Terraform 日常就是四个命令来回跑：init、plan、apply、destroy。先把这个循环刻进脑子里：

flowchart TD INIT[init
初始化 下载 provider 插件] --> PLAN[plan
对比代码与 state 输出 diff] PLAN --> APPLY[apply
按 diff 创建/更新/删除资源] APPLY --> LOOP{还要改?} LOOP -->|改代码| PLAN LOOP -->|不要了| DESTROY[destroy
清空所有资源] DESTROY --> END[结束]

每个命令干什么：

命令干什么会不会动云资源我什么时候用
init下载 provider 插件、初始化后端不会第一次进目录、换了 provider 版本后
plan计算代码与 state 的差异不会每次改完代码先跑它
apply真正调云 API 变更资源会确认 plan 没问题后
destroy把 state 里的资源全删掉会（全删）测试完清场
plan 不是走过场
我见过有人把 apply -auto-approve 设成别名，结果一次改实例规格时 plan 里藏着"force new RDS"——因为他改了一个会触发重建的参数。RDS 一重建，数据盘就没了。plan 必须人工看，尤其出现 -/+（销毁重建）标记时要停下来想清楚。

HCL 语法：四种块

HCL（HashiCorp Configuration Language）看着像 JSON 的亲戚，但它不是 JSON。你日常打交道的就四种块：resource、variable、output、locals。

resource：你要什么资源

resource 是核心，声明"我要一个什么类型的资源，叫什么名字，参数是什么"：

resource "aws_instance" "web" {
  ami           = "ami-0c55b159cbfafe1f0"
  instance_type = "t3.micro"
  count         = 1

  tags = {
    Name = "demo-web"
    Env  = "dev"
  }
}

格式是 resource "资源类型" "本地名字"。aws_instance.web 这个组合在代码里唯一标识这个资源，别的地方引用它就写 aws_instance.web.id。

variable：把可变的东西抽出来

别把环境相关的东西硬编码在 resource 里。变量就是参数：

# variables.tf
variable "aws_region" {
  description = "部署区域"
  type        = string
  default     = "ap-southeast-1"
}

variable "instance_type" {
  description = "EC2 规格"
  type        = string
  default     = "t3.micro"

  validation {
    condition     = can(regex("^t3\\.", var.instance_type))
    error_message = "我 demo 里只允许 t3 系列。"
  }
}

variable "tags" {
  type    = map(string)
  default = {}
}

locals：中间计算变量

有些值你不想暴露成 variable，也不想每次重复算，就放 locals：

locals {
  common_tags = {
    Project     = "demo"
    ManagedBy   = "terraform"
    CostCenter  = "dev-team"
  }
  full_tags = merge(local.common_tags, var.tags)
}

output：把结果吐出来

apply 完你想拿到机器 IP、DNS 这种值，就用 output：

# outputs.tf
output "web_public_ip" {
  description = "EC2 公网 IP"
  value       = aws_instance.web.public_ip
}

output "web_public_dns" {
  value       = aws_instance.web.public_dns
  description = "EC2 公网 DNS"
}

provider：告诉 Terraform 你要管哪个云

provider 是 Terraform 和云厂商之间的适配器。你要管 AWS 就装 aws provider，管阿里云就装 alicloud provider。2026 年我推荐用 required_providers 块锁版本：

terraform {
  required_version = ">= 1.10"

  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.70"
    }
  }
}

provider "aws" {
  region = var.aws_region
  # 凭证走环境变量或 ~/.aws/credentials，别写在这里
}
版本约束怎么写
~> 5.70 意思是"5.70.x，不跨次版本"。生产环境我都这么锁，避免某天 provider 自动升级到 5.80 行为变了把你坑了。required_version 锁 Terraform 自身版本，团队所有人跑同一个版本最省心。

第一个 EC2：完整跑一遍

把上面拼起来，main.tf 长这样：

terraform {
  required_version = ">= 1.10"
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.70"
    }
  }
}

provider "aws" {
  region = var.aws_region
}

resource "aws_instance" "web" {
  ami           = data.aws_ami.ubuntu.id
  instance_type = var.instance_type

  tags = local.full_tags
}

# 数据来源：动态查最新 Ubuntu AMI，别硬编码
data "aws_ami" "ubuntu" {
  most_recent = true
  owners      = ["099720109477"] # Canonical

  filter {
    name   = "name"
    values = ["ubuntu/images/hvm-ssd/ubuntu-24.04-amd64-server-*"]
  }
}

然后按顺序跑：

# 1. 初始化，下载 aws provider 插件
terraform init

# 2. 看计划：会建一台 EC2，不动手
terraform plan

# 3. 确认没问题，真正建
terraform apply
# 输入 yes，或者自动确认：terraform apply -auto-approve

# 4. apply 完看输出
terraform output
# 会打印 web_public_ip

# 5. 测试完清场（重要！别让测试机器一直计费）
terraform destroy

整个过程的数据流：你写的 HCL → Terraform 读 state → 调 provider → provider 调云 API → 资源建出来 → provider 把真实属性回写给 Terraform → 写进 state。

flowchart LR HCL[.tf 代码] --> TF[Terraform Core] STATE[terraform.tfstate] --> TF TF --> PROVIDER[aws provider 插件] PROVIDER --> API[AWS API] API --> RESOURCE[真实 EC2] RESOURCE -.回写属性.-> STATE

state 文件到底是什么

跑一次 apply 之后，你会发现目录里多了个 terraform.tfstate。这玩意儿是 Terraform 的"记忆"——它记录云上现在有哪些资源、各自的属性是什么、和你代码里的 resource 怎么对应。

没有 state，Terraform 就是个瞎子。它每次 plan 都要拿 state 和你代码对比，算出差异。state 长这样（简化）：

{
  "resources": [
    {
      "mode": "managed",
      "type": "aws_instance",
      "name": "web",
      "instances": [
        {
          "attributes": {
            "id": "i-0abc123def",
            "public_ip": "54.123.45.67",
            "ami": "ami-xxx"
          }
        }
      ]
    }
  ]
}
两个铁律
1. state 永远不要提交 Git。里面有密钥、密码哈希、IP，是敏感数据。
2. state 永远不要本地单机玩完就完事。单机的 state 在你电脑上，同事没法协作，电脑坏了 state 就没了。正确做法是搬到远程——第二篇专门讲。

.terraformignore：别让缓存混进 state

terraform init 会在当前目录建一个 .terraform/ 文件夹，里面是下载好的 provider 插件和模块缓存。这个目录巨大，还会因为环境不同变化。你用 terraform plan 之类的命令时，Terraform 默认会扫描当前目录所有文件——虽然 .terraform 不会进 state，但加个忽略文件是好习惯，类似 .gitignore：

# .terraformignore
.terraform/
.terraform.lock.hcl
*.tfstate
*.tfstate.backup
*.log
.secrets/

另外别忘了 .gitignore 也加一份：

# .gitignore
.terraform/
*.tfstate
*.tfstate.backup
*.tfvars
!example.tfvars

新手常犯的五个错

  1. 硬编码 AMI ID：AMI 是 region 级的，换个 region 就找不到了。用 data "aws_ami" 动态查。
  2. 凭证写进代码：AK/SK 写在 provider 块里还提交 Git，等于裸奔。走环境变量或 ~/.aws/credentials。
  3. 改了代码不 plan 就 apply：前面说过了，plan 是安全网。
  4. state 文件提交 Git：泄露敏感信息，还会多人冲突。
  5. 测试完不 destroy：测试机器一直跑着，月底账单吓一跳。我每次 demo 完第一件事就是 destroy。

FAQ

Q：Terraform 和 OpenTofu 命令能通用吗？
几乎完全通用。把 terraform 换成 tofu 就行，.tf 文件、state 格式、provider 插件都兼容。存量项目迁过去就是换个命令的事。

Q：我一个目录里放多少个 .tf 文件合适？
新手建议按职责分：main.tf（资源）、variables.tf（变量）、outputs.tf（输出）、providers.tf（provider 配置）。资源多了再按模块拆，第四篇讲。

Q：count 和 for_each 选哪个？
count 适合"开 N 个一模一样的"，for_each 适合"每个名字不一样"。我倾向尽量用 for_each，count 改中间一个会导致后面的资源全部重建，坑过很多次。

Q：.terraform.lock.hcl 要不要提交？
要。它锁定 provider 版本，保证团队每个人 init 下来的版本一致。它不是敏感文件。

我的结论

Terraform 入门其实不难，核心就是 init → plan → apply → destroy 这个循环加 resource/variable/output/locals 四种块。HCL 语法十分钟能学会，真正要花时间的是理解 state 的作用和理解 provider 调 API 的语义。

我建议你今天就花半小时把这篇的 EC2 例子跑一遍——从 init 到 destroy 完整走一次。有了手感，第二篇讲远程 state 和多人协作，你才知道为什么要把 state 从本地搬走。
