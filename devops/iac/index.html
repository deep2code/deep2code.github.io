IaC 核心模型与工程纪律：声明式、状态与漂移

🏷️ IaC

这是 IaC 专题的主干篇，讲核心模型与工程纪律：声明式为什么天然幂等、配置与状态与真实资源三者的关系、漂移怎么治、为什么幂等不等于可回滚、团队协作要立哪些规矩。想从零跑通第一个项目、掌握日常命令，看同专题的第一个 IaC 项目与工作流那篇。状态后端配置与加锁的细节见站内 Terraform 状态管理篇，module 的设计与版本管理见站内 Module 与最佳实践篇，本文对这两处只给结论不展开。

声明式与命令式的本质差异

「IaC 就是用代码创建服务器」是流传最广的误读。按这个说法，一段调用 aws ec2 run-instances 的 shell 脚本也算 IaC，可它跟 Terraform 差的不是语法，而是描述的对象：命令式描述「怎么做」，声明式描述「要什么」。

命令式脚本里每一行都是一个动作。动作没有身份概念，脚本不知道上次执行的产物还在不在，跑第二遍就再建一台机器。想让它幂等，你得自己写「先查存不存在、存在就跳过、属性不一致还要算出改哪几个字段」——这套逻辑写全了，其实就是在手写一个简陋的 IaC 引擎。

声明式配置里每个资源有稳定的地址（比如 aws_instance.app）。工具用这个地址去状态里查已知现实，把「配置里写的」和「已经存在的」做属性级 diff，算出新建、原地更新、销毁重建、删除四类操作再执行。幂等不靠自觉，是模型自带的。

场景命令式 shell 脚本声明式 IaC
同一份代码执行两次建出两套重复资源，账单翻倍，还要人工分辨哪套在用第二次 plan 输出无变更，不做任何动作
执行到一半失败后重跑在半成品上继续叠加，前面成功的部分被重复创建，通常需要人工清场refresh 后重新 diff，只补齐缺失部分，已建成的资源原样保留
执行前想知道会发生什么只能读脚本猜，唯一验证方式是真跑一遍plan 列出每个资源的动作和触发原因，可保存成计划文件后审
多人同时改同一套资源脚本互相覆盖，线上最终是谁的版本取决于谁跑得晚改动走代码评审，执行期靠状态锁串行化（细节详见站内状态管理篇）
把资源改回上个版本要反向手写删除与回退脚本，删除顺序极易搞错配置回退到旧版本再 apply，工具自己算差异与依赖顺序

三段核心机制：配置、状态、真实资源

记住一件事就能理解绝大多数 IaC 事故：系统里同时存在三份「真相」——你写的配置（期望状态）、工具维护的状态文件（它以为的现实）、云上的真实资源（实际的现实）。事故的共同形态都是这三者不一致。

顺着这张图看故障就清楚了：状态文件丢了，工具认为什么都没建过，下一次 apply 会把线上已有资源再建一遍，或者因为名字冲突直接失败；有人在控制台手改，状态与现实不一致，plan 里会冒出你没提交过的变更；状态被两个进程并发写坏，资源地址与云端 ID 的映射错乱，这是最难收拾的一类。所以 plan 的本质就一句话：先 refresh 让状态贴近现实，再把配置与状态做 diff。plan 不改动任何资源，但它要读后端状态、要调云的只读接口，所以在流水线里跑 plan 同样需要凭证和网络可达。

漂移的产生与治理

漂移（drift）指现实偏离了代码定义。来源无非几种，处置方式完全不同，关键是先判断「这次手改是否合理」，再决定让代码追现实、还是让现实回代码。

漂移来源典型表现正确处置预防手段
人工在控制台改（应急扩容、临时放行端口）plan 出现没人提交过的原地更新改动合理就补写进配置让代码追上，不合理才 apply 收敛收回控制台写权限，只留只读账号与需审批的应急角色
云厂商自动改（小版本升级、维护窗口、自动打标）每次 plan 都有同样几行噪音用 ignore_changes 精确忽略这几个属性把 ignore_changes 写进代码并注明原因，避免后人误删
另一套自动化在改（弹性伸缩、K8s 控制器、运维脚本）实例数、目标组成员来回变化该属性交给对方管，IaC 侧忽略或改用 data 只读引用明确所有权，同一属性只允许一个系统写
资源被别人删掉plan 里出现大量新建，且是你没加过的资源先停手确认是误删还是状态问题，再决定重建关键资源开云端删除保护并配 prevent_destroy
已有资源从未纳管apply 报资源已存在而失败用 import 把现存资源写入状态，再补配置直到 plan 干净新项目先盘点存量，定好哪些纳管、哪些只用 data 引用

巡检不要去 grep plan 的正文输出，格式随版本变。用 -detailed-exitcode：0 无差异、1 出错、2 有差异。下面这段可以直接挂定时任务，发现会被销毁重建的资源就升级告警等级。

#!/usr/bin/env bash
# 生产环境漂移巡检：全程只读，不做任何变更
set -euo pipefail
cd "$(dirname "$0")/envs/prod"

# -input=false 禁止交互式提问，否则定时任务会挂在等输入上
terraform init -input=false -no-color >/dev/null

# -lock=false 让巡检不跟正常变更抢状态锁（仅只读场景可以这么用）
# -detailed-exitcode 是唯一可靠的差异判定方式，别去解析输出文本
set +e
terraform plan -input=false -no-color -lock=false \
  -detailed-exitcode -out=drift.tfplan
code=$?
set -e

case "$code" in
  0) echo "drift=none" ;;
  2) terraform show -no-color drift.tfplan > drift.txt
     # must be replaced 是销毁重建，比普通更新危险一个量级
     replace=$(grep -c "must be replaced" drift.txt || true)
     destroy=$(grep -c "will be destroyed" drift.txt || true)
     echo "drift=yes replace=$replace destroy=$destroy"
     if [ "$replace" -gt 0 ] || [ "$destroy" -gt 0 ]; then exit 9; fi
     exit 8 ;;
  *) echo "plan failed"; exit 1 ;;
esac

治漂移最有效的一招不是工具

是把控制台的写权限收掉。只要还有人能在网页上点改，再勤的巡检也只是事后发现。落地方式：日常账号只给只读策略，变更能力只授予流水线使用的角色；保留一个需要工单审批、自动过期的应急角色，用完自动回收，并把它的每次操作推到审计告警。权限一收，漂移的绝大部分来源就消失了。

幂等不等于可回滚

「用了 IaC 就能随时回滚」是第二个流传很广的误解。IaC 的回滚只是把配置改回旧版本再 apply 一次，它算的是从当前现实到旧配置的正向差异，而这个差异里可能包含销毁。很多属性在云 API 上不可变，改它等于删了重建，plan 里显示为 -/+ 并在属性后标注 forces replacement。有状态资源一旦重建，数据就没了，这不是回滚，这是事故。

改动的属性看起来像实际行为后果正确做法
计算实例的可用区或子网挪个位置销毁重建，得到新实例 ID 与新私网 IP本地盘数据丢失，依赖该 IP 的配置全部失效新增一批实例，流量切过去后再下旧的
计算实例的启动脚本只改了初始化脚本一行默认触发重建，部分 provider 才有关闭开关为改一行脚本把整台机器换掉确认 provider 是否支持只更新不重建，或把初始化逻辑外置
数据库实例的标识、字符集、大版本回退改个名字或版本号销毁重建整库数据丢失，而 plan 里只是一行属性变化加 prevent_destroy，版本变更走厂商原生升级流程
云盘的类型或加密开关换个规格多数厂商需要重建卷盘上数据丢失先做快照，新建卷后挂载迁移
对象存储桶名重命名删旧建新，而非空桶通常删不掉要么数据没了，要么 apply 卡在删除失败桶名视为不可变，改名就新建加数据迁移
安全组的 name（不是 description 或规则）整理命名规范销毁重建整个安全组重建瞬间引用它的实例可能失去放行规则用 name_prefix 并配 create_before_destroy
IAM 角色名、数据库子网组成员小改动重建依赖它的资源级联重建，影响面扩散先看 plan 汇总里的资源数变化，超出预期就停

两个 lifecycle 参数是保命用的。prevent_destroy = true 让任何会销毁该资源的计划直接报错退出，包括「手滑把这段配置删了」这种情况；create_before_destroy = true 把默认的先删后建换成先建后删，避免删除时因仍被引用而失败，也避免中间出现服务空窗。

resource "aws_db_instance" "orders" {
  identifier        = "prod-orders"
  engine            = "postgres"
  engine_version    = "16.3"
  instance_class    = "db.m6g.large"
  storage_encrypted = true

  # 删除前强制留快照，和 prevent_destroy 一起构成双保险
  skip_final_snapshot       = false
  final_snapshot_identifier = "prod-orders-final"

  lifecycle {
    # 任何导致销毁的计划直接失败退出，包括手滑删掉这段配置
    prevent_destroy = true

    # 这两个属性云厂商会自己动：小版本自动升级、维护窗口调整。
    # 不忽略的话每次 plan 都有噪音，评审时容易把真正的变更看漏
    ignore_changes = [engine_version, maintenance_window]
  }
}

resource "aws_lb_target_group" "api" {
  # 用 name_prefix 而不是 name，重建时新旧名字不会冲突
  name_prefix = "api-"
  port        = 8080
  protocol    = "HTTP"
  vpc_id      = var.vpc_id

  lifecycle {
    # 先建新的再删旧的。否则删除会因为仍被 listener 引用而失败，
    # 中途还会出现一段没有可用目标组的空窗
    create_before_destroy = true
  }
}
❌
评审计划时必须用眼睛扫的三处

一是结尾汇总行的三个数字，看新增、修改、销毁是否符合预期，销毁不为零时要逐个交代；二是每个资源块上方的注释行，出现 must be replaced 就必须确认是哪个资源；三是属性后面的 forces replacement 标记，它指出触发重建的具体字段。这三处任意一处超出预期，正确反应是关掉终端去查原因，不是按确认。

代码组织与环境分离

环境分离是结构性决策，事后改造代价很高，一开始就要选对。三种做法的区别不在方便程度，而在误操作能不能打穿隔离。

方案隔离强度状态与后端环境差异如何表达主要风险
目录分环境（推荐）强，每个环境独立根模块与后端配置，可用不同账号凭证一环境一后端一状态各自的 tfvars，共用逻辑抽成 module目录间有少量重复，需要靠 module 约束一致性
workspace弱，同一后端下多个状态，靠当前选中的 workspace 区分一份后端配置，状态按 workspace 分键条件表达式与查表变量，容易越写越绕切错 workspace 就把生产当测试改，凭证也难分离
git 分支分环境看着强，实际最差取决于分支里的配置，容易配错分支之间的代码差异代码长期分叉，合并时漏掉环境专属改动，主干与线上对不上

协作纪律是 IaC 成败的关键

IaC 项目失败很少是技术问题，基本都是纪律问题：有人图快在本地对生产 apply 了一把、有人跳过评审直接合了、两个人同时 apply 把状态写坏。工具能提供的机制只有状态锁一项，剩下全靠流程。

sequenceDiagram participant Dev as 开发者 participant Repo as 代码仓库 participant CI as 流水线 participant Rev as 评审与审批人 participant Cloud as 云 API Dev->>Repo: 提 PR 修改基础设施配置 Repo->>CI: 触发只读检查任务 CI->>Cloud: fmt validate 与 refresh 读取现状 Cloud-->>CI: 返回真实属性 CI->>CI: 生成计划文件并转成可读文本 CI-->>Repo: 把计划摘要贴成 PR 评论 Repo->>Rev: 请求评审 Rev->>Repo: 核对增删数量 是否有重建 是否触及网络与权限 Rev-->>Repo: 批准并合并 Repo->>CI: 主干触发 apply 任务 CI->>Rev: 生产环境等待人工审批 Rev-->>CI: 审批通过 CI->>Cloud: 按已保存的计划文件执行变更 Cloud-->>CI: 返回执行结果 CI-->>Dev: 归档日志与新的状态版本号 Note over CI,Cloud: 个人凭证不持有生产写权限 apply 只能由流水线发起
纪律不守会发生什么怎么强制
所有变更走 PR，并在 PR 里展示计划评审只看到配置改了三行，看不到它会重建数据库分支保护加必需检查，计划摘要缺失就不允许合并
禁止本地对生产执行 apply线上出现一次没人知道、也没有日志的变更，事后无法复盘生产写权限只授给流水线角色，个人凭证只读
apply 使用评审时保存的计划文件合并到执行之间现实变了，实际执行的和评审过的不是一回事apply 阶段传入计划文件，而不是现场重新生成
并发变更靠状态锁串行化两个 apply 同时写状态，资源与 ID 映射错乱，最难修复使用支持加锁的远程后端（配置细节详见站内状态管理篇）
生产 apply 需人工审批并限定变更窗口半夜自动 apply 了一个会重建负载均衡的改动流水线环境保护规则加审批人，窗口外任务直接拒绝
巡检发现漂移时不许强行合并新改动主干与线上长期不一致，下一个人的无关改动会顺带 apply 出意外漂移即开工单处理，主干始终保持 plan 干净

密钥不能进代码，也守不住状态文件

这点最常被忽略：状态文件里会以明文保存部分敏感属性。数据库初始口令、生成的随机密码、部分服务的连接串，只要它是资源属性，就会被写进状态。给变量加 sensitive = true 只屏蔽终端与计划输出的展示，对状态文件毫无作用。所以状态存储本身必须按机密资产管理。

敏感数据可能出现的位置是否明文对策
提交进仓库的 tfvars 或 tf 文件是，且会永久留在 git 历史里绝对不写；已经写过的按已泄露处理，轮换密钥而不只是删文件
状态文件里的资源属性是，标了 sensitive 也挡不住后端开服务端加密、版本化、最小权限、访问审计
plan 保存出来的计划文件是，包含将要写入的属性值当作机密产物：加密存储、设短保留期、不要把全文贴进 PR
流水线日志取决于是否被掩码用 CI 的密钥掩码功能，执行时加 -no-color 并避免打印变量
由 IaC 生成的随机口令状态里是明文生成后立即写入密钥托管服务，应用只从托管服务取
provider 的访问凭证不应落盘用角色扮演、OIDC 联邦或实例元数据，不要把长期密钥写进配置

IaC 的适用边界与反模式

不是所有东西都该进 IaC。判断依据是生命周期长度与变更频率：长生命周期、低频变更、依赖关系强的适合；高频变更、需要秒级回滚的交给别的体系。

反模式会出什么事正确做法
在控制台手改，事后不回写代码漂移累积到某天 plan 冒出几十条意外变更，没人敢 apply收回控制台写权限，手改必须补回配置
状态文件放本地，或提交进 git换台机器就丢状态，多人协作必冲突，还把明文敏感属性传遍所有克隆使用带锁的远程后端，详见站内状态管理篇
一个巨型根模块管所有环境改测试环境要跑全量 plan，一次误操作能打穿到生产按环境切根模块，共用逻辑抽成 module
apply 不看计划，直接自动批准把数据库重建了才知道那个属性不可变生产禁用自动批准，apply 必须使用评审过的计划文件
把 IaC 当一次性搭建工具，搭完不管半年后代码与线上完全脱节，等于没有 IaC，还多了一份误导人的假文档定时漂移巡检，主干始终保持 plan 干净
大量使用 local-exec 塞 shell声明式退化回命令式：不幂等、无法预览、失败后状态不可信优先找原生资源或 provider，实在没有就把脚本收敛到初始化阶段并自己保证幂等
把别人管的资源写成 resource两套系统争夺同一资源的所有权，互相覆盖用 data 源只读引用，所有权归对方
为了消除重复搞三层嵌套 module改一个端口要翻四个文件，新人一周看不懂，plan 输出的资源地址长到读不下去抽象层数控制在两层以内，宁可容忍少量重复
❌
最容易踩的坑
  • 把 plan 的无变更当成一切正常：如果 refresh 被跳过（加了 -refresh=false，或直接看旧的计划文件），漂移根本不会被发现。巡检必须走真实 refresh。
  • 看到 -/+ 还是按了确认：这个符号是销毁重建。数据库、云盘、对象存储桶出现它，等同于数据删除确认框。
  • 用 name 而不是 name_prefix 命名安全组和目标组：后续任何改名都会重建，且新旧同名冲突会让 apply 直接失败。
  • 有状态资源漏掉 prevent_destroy：一次误删配置段落、一次 workspace 切错，就足够把生产库带走。
  • 用 workspace 隔离生产与测试：切换依赖当前会话的隐式状态，命令行上没有任何视觉提示，切错的代价是全量误改。
  • 在本地对生产 apply 救火：没有日志、没有评审、状态版本与主干脱节，事后复盘直接断线。
  • 用 destroy 来「只删一个资源」：destroy 默认作用于整个根模块的全部资源。靶向删除应当改配置后 apply，或用 -target 并反复确认范围。
  • 以为标了 sensitive 就安全：它只屏蔽输出展示，状态文件与计划文件里仍是明文。
  • 状态存储没开版本化：状态一旦被写坏或误删，没有历史可回退，只能逐个 import 重建映射，几百个资源足够加班到天亮。
  • ignore_changes 范围写得过宽：忽略整个资源等于该资源脱管，漂移永远检测不到。只忽略具体属性，并注明原因。
  • 评审只看配置 diff 不看计划：改一个变量默认值可能连带重建十几个资源，这在代码 diff 里完全看不出来。
  • apply 中途失败后直接重跑第二遍：先跑 plan 确认状态与现实的偏差，必要时 import 或移除状态条目，操作前务必备份状态；盲目重跑可能在半成品上叠加出重复资源。
