IaC 基础设施即代码总览

🏷️ IaC / Terraform

我为什么写这系列

刚入行那会儿，我管服务器是这样的：登控制台点鼠标，开机器、配安全组、挂磁盘，全靠截图和脑子记。换个人接手？文档里写着"密码在某个飞书群的文件里"。后来一次误操作——同事在生产环境手动改了安全组规则，把数据库端口敞给了 0.0.0.0——我们通宵守了两夜。从那以后我下定决心：基础设施必须代码化，一切变更走 Git，不许点鼠标。

这系列就是我这几年用 Terraform 管 AWS 和阿里云攒下来的实战笔记。不讲什么"基础设施即代码的哲学意义"，直接讲怎么上手、怎么不把自己搞死、多人协作怎么搞、2026 年了 OpenTofu 和 Pulumi 到底该怎么选。

一句话说清 IaC

IaC（Infrastructure as Code）就是用声明式代码描述你要什么基础设施，工具负责把它变成真实的云资源。你写"我要一台 2C4G 的 ECS，在深圳 region"，工具自己去调 API 开机器；你改代码说"升到 4C8G"，工具对比差异，只改变化的部分。核心三件事：声明式、幂等、可审计。

和传统脚本的区别
Shell 脚本是命令式——你告诉工具"第一步干嘛第二步干嘛"，重跑一遍可能就炸了。IaC 是声明式——你只描述"最终状态应该是什么样"，工具自己算怎么达到。跑十遍和跑一遍结果一样，这才是幂等。

2026 年的 IaC 生态长什么样

站在 2026 年回看，Terraform 早就不是 HashiCorp 一家独大了。2023 年 HashiCorp 改 BSL 协议之后，Cloud Native Computing Foundation 接盘搞了个 OpenTofu——代码几乎和 Terraform 兼容，但走真正的开源路线。现在我团队新项目基本默认 OpenTofu，老项目继续 Terraform 1.x，两边语法差别不大，迁移成本很低。

工具语法状态管理多云我的定位
Terraform 1.xHCL 声明式state 文件/远程后端全平台事实标准，生态最厚
OpenTofuHCL 兼容同 Terraform全平台CNCF 托管的开源 fork
Pulumi通用语言(TS/Python/Go)自带后端全平台想写代码不想学新 DSL
CloudFormationYAML/JSONS3 原生仅 AWSAWS 深度用户首选
CrossplaneK8s CRDK8s etcd全平台已经重度 K8s 的团队
第一个大坑先打个预防针
state 文件是 Terraform 的命根子。它记录着"云上现在有什么"，一旦丢了或坏了，Terraform 就不知道哪些资源是它管的——你再 apply 会重新建一遍，生产环境等于双重开机器。第二篇专门讲怎么保护它。

我的建议路线

别一上来就学 Module 和 CI/CD。先花半天跟第一篇走通"写一个 .tf → init → plan → apply → 看到 EC2 跑起来"这个完整闭环。有了手感再往下看。我带过不少新人，上来就啃 Module 文档，三天还没写出第一台机器，直接放弃了。

  1. 第 1 天：跟着第一篇，本地跑通第一个 EC2/ECS 实例。
  2. 第 2-3 天：把 state 搬到远程（第二篇），理解锁机制。
  3. 第 1 周：用第三篇的代码模板，把一个测试环境完整编排出来。
  4. 第 2 周：抽 Module（第四篇），接进 GitLab CI/GitHub Actions。
  5. 选型时：翻第五篇对比表，按团队技术栈做决定。

FAQ

Q：我只会 AWS，有必要学 Terraform 吗？直接用 CloudFormation 不行？
单一云、规模不大，CloudFormation 完全够用，还免费、原生。但只要你未来有一天要碰第二个云、或者要把同一套东西复用到另一个项目，Terraform/OpenTofu 的抽象能力就值回来了。

Q：Terraform 和 OpenTofu 选哪个？
新项目我倾向 OpenTofu：纯开源、CNCF 背书、语法 99% 兼容。存量 Terraform 项目不急着迁，两边可以并存。第五篇有详细对比。

Q：学这个要会编程吗？
HCL 不是编程语言，是配置语言，会写 JSON/YAML 就能上手。但要把 Module 写好、做复杂编排，会一门通用语言（最好是 Python 或 Go）会轻松很多。

Q：state 文件到底能不能提交到 Git？
绝对不能。它里面有敏感信息（密钥、密码哈希），而且多人同时改会冲突。第二篇详细讲正确做法。

我的结论

IaC 不是什么新潮概念，它解决的就是"手工操作不可重复、不可审计、不可协作"这三个老问题。Terraform 把这件事做到了行业标准，OpenTofu 让它真正开源，Pulumi 和 Crossplane 代表了另外两条路线。

我自己的判断：2026 年新项目，多云团队选 OpenTofu，纯 AWS 团队可以 CloudFormation 起步，重度 K8s 团队看 Crossplane，想用通用语言写的选 Pulumi。别纠结，先跑通一个最小例子，比读十篇选型文章都管用。下面就从第一篇开始。
