云资源的声明式管理：状态、漂移与多环境

🏷️ IaC / Terraform

声明式管理本身的机制（配置、状态、真实资源三段关系，幂等与回滚的区别，代码组织与协作纪律）在总览篇里，状态文件的细节在状态管理篇。这一篇只讲一件事：当被管理的对象是「云 API 背后的真实资源」时，多出来的那些问题——它们不是工具的 bug，而是云平台本身的性质。

「创建成功」有四种含义

最常见的困惑是：上一个资源明明返回成功了，下一个资源引用它却报不存在。云 API 大多是最终一致的，创建接口返回成功只代表请求被受理、标识被分配，既不代表所有区域端点都能查到它，更不代表数据面可用。这四层含义必须分开看。

「成功」的层次典型资源真正可用的判定依据不判定的症状
API 受理并返回标识几乎所有异步创建的资源轮询状态字段直到可用下一个资源引用时报不存在
控制面记录可查IAM 角色与策略、标签、DNS 记录再次查询确认，或显式等待传播偶发 404，重跑一次又好了
数据面就绪数据库实例、托管集群、消息队列状态字段 + 实际连一次端点应用启动瞬间连接被拒
证书签发与解析生效证书、域名记录、CDN 配置官方提供的等待型资源HTTPS 监听器创建失败
变更真正落地数据库规格与参数变更是否立即生效的开关代码里已经改完，实际要等下个维护窗口
stateDiagram-v2 state "已提交：apply 发出创建请求" as Sent state "API 已受理：返回了资源标识" as Accepted state "控制面可查：查询接口能查到记录" as Described state "数据面就绪：端点可连、证书已签发" as DataReady state "健康：探活连续通过" as Healthy state "判定失败：超时或状态异常" as Failed [*] --> Sent Sent --> Accepted: 同步返回成功 Accepted --> Described: 最终一致，秒级到分钟级延迟 Accepted --> Failed: 立刻查询报不存在 Described --> DataReady: 状态字段翻到可用 Described --> Failed: 长时间卡在创建中 DataReady --> Healthy: 探活通过 DataReady --> Failed: 端点能解析但连不上 Healthy --> [*] Failed --> [*]

「重跑一次 apply 就好了」是危险的成功经验：它把最终一致性问题掩盖成了随机失败，等到某次流水线不允许重跑，或者重跑正好落在一个半成品状态上，就会变成真事故。就绪判定要写进代码。

依赖顺序：显式图之外的隐式依赖

工具能从「A 引用了 B 的属性」自动推出依赖顺序，但云平台里有大量依赖是引用关系表达不出来的。

sequenceDiagram participant T as terraform apply participant I as IAM 全局服务 participant R as 区域内的服务端点 T->>I: 创建角色与策略 I-->>T: 返回成功与角色标识 T->>R: 用这个标识创建函数或集群 R-->>T: 报错，说该角色不存在或不可假扮 Note over I,R: 全局服务是最终一致的
标识已经返回，但还没传播到区域端点 T->>T: 显式等待，或依赖 provider 的内置重试 T->>R: 重新提交同一请求 R-->>T: 创建成功 Note over T,R: 不要靠重跑 apply 碰运气
把等待写进代码里
隐式依赖依赖图能看出来吗症状修法
角色创建后立刻被区域服务引用能看出引用，看不出传播延迟报角色不存在或不可假扮显式等待资源，或确认 provider 有重试
安全组的内联规则与独立规则资源混用完全看不出两次 apply 互相删对方的规则，plan 永远不收敛一个安全组只用一种写法，二选一
销毁安全组时仍被网卡引用看不出，网卡是托管服务建的销毁卡在依赖冲突上先删引用方，给托管服务留清理时间
路由表、网关与对等连接能看出引用路由建好了但流量不通等网关状态可用再建路由，并做连通性断言
可用区库存看不出实例创建报该可用区无库存准备候选规格与多可用区，失败即换
依赖只体现在 data 源里data 在计划阶段求值，看不到还没创建的资源plan 报找不到，或者拿到过期的值改成直接引用资源属性，别用 data 兜

第二行值得单独强调，因为它制造的是「plan 永远不干净」这种慢性病：同一个安全组既写了内联规则、又建了独立的规则资源，两者都认为自己拥有完整的规则集，于是每次 apply 都在删对方加的规则。团队里通常要花几周才反应过来这不是 bug 而是写法冲突。

# 1) 就绪判定：创建返回成功不等于可用。能用官方的「等待型」资源就别自己轮询。
resource "aws_acm_certificate" "site" {
  domain_name       = var.domain
  validation_method = "DNS"
  lifecycle {
    create_before_destroy = true   # 证书被监听器引用，必须先签发新的再摘旧的
  }
}

# 这个资源本身不创建任何东西，它的全部价值就是「阻塞到证书真的签发完成」。
# 少了它，下面的 HTTPS 监听器会用一张还没生效的证书，创建直接失败。
resource "aws_acm_certificate_validation" "site" {
  certificate_arn         = aws_acm_certificate.site.arn
  validation_record_fqdns = [for r in aws_route53_record.validation : r.fqdn]
}

# 2) 传播延迟：IAM 是全局最终一致的服务，ARN 已经返回，区域端点还认不出这个角色。
resource "time_sleep" "iam_propagation" {
  depends_on      = [aws_iam_role.task]
  create_duration = "20s"   # 不优雅，但比让 apply 随机失败、靠重跑碰运气强得多
}

# 3) 依赖图看不出来的顺序，用 depends_on 显式钉死
resource "aws_ecs_service" "app" {
  name    = "${var.env}-app"
  cluster = aws_ecs_cluster.main.id
  depends_on = [
    time_sleep.iam_propagation,
    aws_acm_certificate_validation.site,
    aws_lb_listener.https,   # 监听器没就绪，服务注册目标组会失败
  ]

  lifecycle {
    # 这两个字段的所有权在弹性伸缩和发布系统手里，不划界就会和它们互相覆盖，
    # 表现是每次 plan 都想把实例数改回代码里的值。
    ignore_changes = [desired_count, task_definition]
  }
}

# 4) 有状态资源：配置层和云侧双保险
resource "aws_db_instance" "main" {
  identifier          = "${var.env}-app"   # 改这个字段等于删库重建，不是改名
  engine              = "mysql"
  engine_version      = "8.0"
  instance_class      = var.db_class
  deletion_protection = var.env == "prod"  # 云侧开关，控制台删也拦得住
  skip_final_snapshot = var.env != "prod"  # 生产强制留最终快照

  # 口令一次都不经过 Terraform：云侧生成、密钥服务托管并自动轮转，
  # 因此状态文件里不存在这个明文。这是比「随机生成再存进状态」好得多的路线。
  manage_master_user_password = true

  lifecycle {
    prevent_destroy = true              # 任何会销毁或重建它的 plan 直接报错
    ignore_changes  = [engine_version]  # 小版本由维护窗口自动升，别跟它抢
  }
}

不可变字段：一次改名就是一次重建

云资源有相当多的字段在创建后不可修改，改它们等于「销毁 + 新建」。危险之处在于 plan 的输出很含蓄——一行 forces replacement 混在几十行 diff 里，很容易被 apply 过去。对有状态资源来说，这一行就是数据丢失。

典型不可变字段为什么不可变数据面风险怎么绕
资源标识符与名称云侧以名字为主键数据库改名即删库重建只是代码里换地址就用 moved 块；真要改名走云侧迁移
所在子网或可用区网卡固定在子网上实例重建，本地盘数据丢失先在新子网扩容，再摘掉旧的
网段 CIDR路由与地址已分配整个专有网络重建一开始就按环境规划不重叠网段并预留增长
磁盘类型与加密开关底层介质与密钥不同卷重建打快照，新建加密卷再挂载迁移
引擎大版本数据格式不同视厂商，可能重建走云侧升级流程，事后 import 对齐
实例规格族跨虚拟化类型底层虚拟化不同实例重启或重建用弹性伸缩滚动替换，不要原地改
flowchart TB S["plan 里出现 forces replacement"] --> Q1{"这个资源持有数据吗"} Q1 -->|"无状态：实例、安全组、监听器"| Q2{"能不能先建新的再删旧的"} Q2 -->|"名字必须唯一，两份并存会冲突"| PRE["改成名称前缀加随机后缀，再开 create_before_destroy"] Q2 -->|"可以并存"| CBD["开 create_before_destroy，并确认流量已经切过去"] Q1 -->|"有状态：数据库、对象存储、磁盘"| Q3{"变的只是它在代码里的地址吗"} Q3 -->|"只是重命名或挪进模块"| MOVED["用 moved 块改地址，不产生任何真实变更"] Q3 -->|"真的改了不可变字段"| Q4{"云侧有原地迁移能力吗"} Q4 -->|"有，例如只读实例升主"| MIG["走云侧迁移流程，Terraform 事后 import 对齐"] Q4 -->|"没有"| STOP["停下来写迁移方案，先加 prevent_destroy 防手滑"]

三个必须形成肌肉记忆的动作：有状态资源一律先加禁止销毁；代码重构造成的地址变化用 moved 块表达，不要让它变成销毁重建；流水线里把「计划中包含 delete 或 replace 动作」做成单独的审批门，而不是和普通变更走同一个审批。

配额与区域差异

「同一份代码换个区域跑一遍」听起来是声明式管理的天然能力，实际上这是失败率最高的操作之一。原因是代码里隐含了一堆区域相关的假设。

差异维度典型症状提前暴露的方式
弹性公网 IP 数量配额（多数账号默认每区域个位数）建 NAT 网关时报超限，且是在 apply 中途上线前查配额中心，按环境数量提前提工单
专有网络数量配额新环境根本建不出来同上；新环境评审时把配额作为必查项
实例规格在某可用区无库存偶发创建失败，重试有时能过准备候选规格列表，代码支持多可用区
服务未在该区域上线provider 报未知资源类型或端点不可达先对照区域服务清单，再决定架构
独立分区（中国区是单独分区）资源标识前缀不同、账号体系独立、部分服务缺失中国区单独一套代码与独立后端，不要试图共用
可用区标识不通用写死可用区的 tfvars 换区域直接失败用 data 源动态取可用区列表
组织策略造成的默认值差异（强制加密、强制标签）每次 plan 都有一堆无意义 diff用 provider 默认标签，或精确到键的 ignore_changes

配额这一项特别值得把检查前移：它的失败点在 apply 中途，此时一半资源已经建好，状态文件里是个半成品，回滚还要额外一轮销毁。相比之下在评审阶段花十分钟查配额便宜太多。

漂移：手工改动怎么进来，怎么收回

漂移的通用原理在总览篇讲过，这里只说云环境里的落地手段。核心判断是：漂移不是靠纪律消除的，是靠权限消除的。只要控制台还能写，就一定会有人在半夜为了止损点进去改一下。

flowchart TB D["线上真实资源与代码不一致"] --> P1 subgraph P1["预防：让手工改不了"] A1["控制台默认只发只读账号"] A2["写权限只发给流水线的角色"] A3["应急改动走临时提权，自动留痕并开工单"] end subgraph P2["检测：让漂移看得见"] B1["定时跑 plan，按退出码报警"] B2["refresh-only 单独看状态与真实资源的差"] B3["按标签巡检没有被任何代码管理的资源"] end subgraph P3["收回：把资源纳回代码"] C1["import 块加生成配置，先 plan 到零变更"] C2["确实该由外部管的字段用 ignore_changes 划界"] C3["彻底不该管的资源用 removed 块脱管而不销毁"] end P1 --> P2 P2 --> P3
漂移来源检测方式收回方式预防
控制台手工改参数定时 plan 退出码为 2把改动反向写进代码再 apply控制台只读
应急扩容改了实例数plan 显示要缩回代码里的值代码同步，或把该字段交给伸缩策略并划界扩容也走流水线
厂商自动打标签、自动升小版本每次 plan 都有相同的 diff精确到键的 ignore_changes统一用 provider 默认标签
别的团队在同一账号里建了资源按标签巡检无主资源import 纳管，或移交并划清边界按账号或项目做硬隔离
被其他控制器接管的字段refresh-only 的差异ignore_changes 明确所有权设计阶段就写清哪些字段归谁
资源被手工删除plan 显示要新建直接 apply 重建，注意数据不会回来删除保护 + 审计告警
 
# 漂移检测流水线：只读凭证 + plan，永远不 apply。判读全靠退出码。
# -detailed-exitcode: 0 = 无差异, 1 = 执行失败, 2 = 有差异（漂移，或代码改了还没发）
terraform plan -detailed-exitcode -lock=false -input=false -out=drift.tfplan
code=$?
case $code in
  0) echo "no drift" ;;
  2) echo "DRIFT or unreleased change" ;;
  *) echo "plan failed"; exit 1 ;;   # 关键：1 绝不能当成「没漂移」
esac

# 只想看「状态与真实资源」的差，不想看「代码与状态」的差，用 refresh-only
terraform plan -refresh-only -detailed-exitcode

# 把计划转成机器可读，只对含删除或重建动作的条目告警 —— 这才是危险漂移
terraform show -json drift.tfplan \
  | jq -r '.resource_changes[]
           | select(.change.actions | index("delete"))
           | "\(.address) => \(.change.actions | join(","))"'

# 收回手工创建的资源：1.5 起用 import 块，能先在 plan 里看清楚再落地
cat >> imports.tf <<'EOF'
import {
  to = aws_security_group.legacy_bastion
  id = "sg-0123456789abcdef0"
}
EOF
terraform plan -generate-config-out=generated.tf  # 生成初版配置，必须人工逐字段审
terraform plan    # 目标是这个资源「零变更」；还有变更说明配置和现状没对齐
terraform apply   # 只写状态文件，不动真实资源

# 反向操作：资源要交给别的团队或别的工具管，但不能销毁。
# 1.7 起用 removed 块声明脱管，比 terraform state rm 可审计（它是代码，能进 review）
# removed { from = aws_security_group.legacy_bastion
#           lifecycle { destroy = false } }

ignore_changes 是这里最容易被滥用的工具。它的正确语义是声明字段所有权归属外部，不是「让 plan 闭嘴」。把它写成整个 tags 而不是 tags["某个键"]，或者一口气忽略十几个字段，等于把这些字段从管理范围里删掉——之后谁改了都不会被发现。

口令与凭证在声明式管理里的处置

这里有两件不同的事经常被混在一起：跑 apply 的那份凭证，和被管理资源里的那些口令。

前者的结论很明确：不要在流水线里放长期访问密钥，用与云厂商建立的联合身份换取短期凭证；并且把权限拆成两份——定时漂移检测和 PR 上的 plan 用只读角色，apply 用带写权限的角色且只在审批后可用。这样即使检测流水线被攻破，也改不了任何东西。

后者的关键是不让口令经过工具。只要它从配置里过一遍，就会明文落进状态文件，而状态文件的防护级别通常低于密钥服务（状态文件里的敏感数据问题见状态管理篇）。优先级从高到低是：让云侧自己生成主账号口令并交给密钥服务托管轮转（配置里只打开开关）；其次是由密钥服务生成、应用运行时按身份去取、配置里只引用资源标识；再次是用较新版本提供的临时值与只写参数机制，让敏感值参与 apply 但不落状态。最差的是用随机口令资源生成再写进数据库配置——它看起来很自动化，实质是把明文口令永久存进了状态文件。

多环境差异的表达方式与反模式

多环境的目标不是「少写代码」，而是让生产环境跑的每一条代码路径都已经在别的环境跑过。用这个标准去衡量，几种常见写法的差距就很明显了。

表达方式生产路径是否被预演过爆炸半径适用场景主要风险
每环境一个目录 + 带版本的共享模块 + 独立后端键是，模块可灰度升级小推荐默认目录之间会慢慢分叉，要靠模块版本对齐
单目录 + 每环境一份 tfvars是，但差异只能靠变量大，一份代码一个状态小项目起步很容易用错 var-file 把开发的值打到生产
工作区（workspace）是大，共享后端与代码临时并行实验不适合做环境隔离，原因见状态管理篇
用 count 条件开关控制资源是否存在否，生产分支从没跑过大反模式第一次执行就发生在生产上
一个大映射塞所有环境的值是大反模式改开发的值会让生产 plan 一起变，全靠人不手滑
复制粘贴生产目录再手工微调否小反模式两边永久分叉，修一个 bug 要修两遍且会漏
 
# 推荐形态：每个环境一个目录，共享同一个带版本号的模块，后端状态键各自独立。
# 环境之间唯一允许的差异是「参数值」，不是「代码分支」。

# envs/prod/main.tf
terraform {
  required_version = ">= 1.9.0"
  backend "s3" {
    bucket         = "acme-tfstate"
    key            = "prod/network/terraform.tfstate"  # 每环境独立键，爆炸半径隔离
    region         = "ap-northeast-1"
    dynamodb_table = "acme-tfstate-lock"
  }
}

# 区域之间可用区标识不通用，写死 zone id 换个区域必然失败，动态取
data "aws_availability_zones" "available" {
  state = "available"
}

module "network" {
  # 固定到 tag：开发环境先升 v3.3.0 验一周，生产再跟上，这样模块升级才有灰度
  source = "git::ssh://git@github.com/acme/tf-modules.git//network?ref=v3.2.1"

  env                = "prod"
  cidr_block         = "10.3.0.0/16"   # 各环境网段不重叠，将来做对等连接或专线才通
  availability_zones = data.aws_availability_zones.available.names
  nat_per_az         = true            # 开发环境一个 NAT 省钱，生产每个可用区一个保可用
}

# 反模式一：用条件开关表达环境差异。
# 后果是生产独有的那条分支在开发环境一次都没被执行过，第一次跑就是在生产上跑。
# resource "aws_nat_gateway" "extra" {
#   count = var.env == "prod" ? 2 : 0
# }

# 反模式二：一个大映射塞所有环境。
# 改开发的值会让生产的 plan 一起变，而且生产的正确性依赖「没人手滑改错 key」。
# locals {
#   sizes = { dev = "t3.small", staging = "t3.medium", prod = "m6i.xlarge" }
#   size  = local.sizes[var.env]
# }

另外三条云资源侧的硬约束：各环境网段不重叠（否则将来做对等连接或专线直接没法通，这是事后无法补救的决策）；不要写死可用区标识（区域之间不通用）；规格差异用参数表达，可用性结构差异要慎重——生产每个可用区一个网关、开发只有一个，这属于可接受的参数差异；但生产有个额外的组件而开发完全没有，那部分代码就永远得不到验证。

删除保护与销毁演练

这两件事必须成对做。只有删除保护而没演练过重建，等于有了保险柜却不知道钥匙在哪；只演练重建而没有删除保护，迟早会有人在生产上演练。

机制生效位置拦得住拦不住
prevent_destroy计划期，工具内部销毁，以及任何会导致重建的变更把这行代码删掉再 apply
云侧删除保护开关云 API任何来源的删除，包括控制台先关开关再删；也会让正常的 destroy 报错
强制最终快照云 API 删除时数据彻底丢失快照本身的保留策略与配额
后端版本化与防误删状态存储状态文件丢失或被覆盖已经执行完的真实销毁
流水线审批、禁用按目标执行CI误操作与越权变更有权限的人在本地直接跑
组织级删除策略云账号策略批量删除策略覆盖范围之外的资源

销毁演练的做法：开发环境定期整体销毁再重建，把「这套代码能从零把环境建起来」变成持续验证的事实，而不是一个假设。它能暴露出三类平时看不见的问题：被手工创建过、从来不在代码里的资源；只在第一次创建时能跑通、重建时会撞名字冲突的资源；以及依赖顺序在销毁方向上不成立（例如网卡还挂着就删安全组）。生产环境不做真销毁，但要定期跑一次 plan -destroy 并人工审阅输出——它能告诉你哪些资源其实已经脱离了代码管理。

最后一条原则：数据和资源的生命周期不该绑在一起。备份、快照、对象存储里的业务数据，不要让它们的存在依赖某次 apply 的正确性；要么放在一个单独的、权限更严的状态里，要么彻底交给别的流程管，用 removed 块脱管而不销毁。

❌
最容易踩的坑
  • 把「重跑一次 apply 就好了」当成解决方案。那是最终一致性在报警，就绪判定要写进代码，否则总有一次重跑不了。
  • plan 里那行 forces replacement 被忽略。对数据库、磁盘、对象存储来说这一行就是数据丢失，必须做成单独的审批门。
  • 改资源名当成「重命名」。云侧以名字为主键，改名是删了重建；代码里换地址请用 moved 块。
  • 安全组同时用内联规则和独立规则资源。两者互删对方的规则，plan 永远不收敛，而且没有任何报错提示。
  • 写死可用区标识。换区域直接失败，用 data 源动态取。
  • 上线前不查配额。公网 IP、网络数量这类配额的失败点在 apply 中途，留下一堆半成品。
  • 用随机口令资源生成数据库口令。明文永久落进状态文件；优先让云侧生成并交给密钥服务托管。
  • 流水线里放长期访问密钥，而且 plan 和 apply 用同一份。检测流水线一旦被攻破就等于拿到了写权限。
  • ignore_changes 写成整个 tags 或一长串字段。那是把字段移出管理范围，之后谁改都发现不了。
  • 用 count = env == "prod" ? 1 : 0 表达环境差异。生产独有的那条路径第一次执行就发生在生产上。
  • 各环境网段重叠。将来做对等连接或专线时无法补救，只能重建网络。
  • 开了 create_before_destroy 却没处理名字唯一性。新旧同名直接冲突，apply 卡在中间态。
  • 只有删除保护，从没演练过重建。开发环境定期销毁重建，才能暴露那些只在第一次创建时能跑通的资源。
  • 让业务数据的生死依赖某次 apply。数据和资源的生命周期要拆开，脱管用 removed 块而不是销毁。
