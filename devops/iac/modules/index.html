Terraform 模块设计与版本管理

🏷️ Terraform Modules

模块是 Terraform 里唯一的抽象手段，也是最容易被滥用的一个。团队通常会经历两个极端：先是所有东西平铺在一个目录里复制粘贴，然后是「什么都抽成模块」，最后得到一堆参数几十个、比直接写资源更难读的封装。模块的价值不在于消除重复，而在于把一组决策固化下来，让调用方少犯错。

本文只讲模块的设计、版本与测试。HCL 语法与第一个项目见站内《Terraform 入门与 HCL 语法》，state 与拆分见《Terraform 状态管理》，工具选型见《IaC 工具对比》，IaC 的核心模型与漂移见《IaC 基础设施即代码总览》。

一、先判断要不要抽：过早抽象的代价

flowchart TB S["有一段基础设施代码，要不要抽成模块"] --> Q1{"同一套资源组合
会被复用三次以上吗"} Q1 -->|"会"| Q2{"每次复用的差异
能用几个参数说清吗"} Q1 -->|"不会"| Q3{"需要对外强制约束吗
比如必须加密必须打标签"} Q2 -->|"能"| Y["抽模块，接口按业务意图设计"] Q2 -->|"差异很多且结构不同"| N1["不要抽
抽出来会变成开关的集合"] Q3 -->|"需要"| Y2["抽成带约束的封装
哪怕只用一次也值得"] Q3 -->|"不需要"| N2["直接写在根模块里
等第三次复用再抽"] Y --> C{"封装后调用方代码
变短了或变安全了吗"} Y2 --> C C -->|"是"| K["保留"] C -->|"否"| D["这个模块没有价值
把它内联回去"]
判定项该抽不该抽
复用次数已经出现三次以上，或已确定的三个环境都要用只有一处在用，「以后可能会复用」
差异的形态差异是少量标量（名字、规格、副本数）差异是结构性的（有的环境要多两类资源）
是否带约束能强制加密、强制标签、禁止公网、统一命名只是把资源原样包了一层
调用方视角调用方不需要读模块源码就会用必须读源码才知道哪些变量要一起传
变更耦合这几处确实应该一起变各处的演进节奏不同，抽在一起会互相牵制
规模包住的是一个有意义的整体（一个 VPC、一个带备份与告警的数据库）包住的是单个资源加一个变量，纯属增加一层间接

二、接口设计才是模块的核心

模块的接口就是它的全部价值。变量应该表达业务意图，而不是把 provider 的参数全透传。一个暴露五十个可选变量的模块等于没有封装：它把所有决策又推回给调用方，还额外多了一层间接性，同时任何一个错误的默认值都会被复制到所有使用方。

维度坏接口好接口
变量数量五十个可选变量，覆盖 provider 的每个字段三到五个必填的业务参数，加少量有安全默认值的可选项
抽象层次enable_encryption、encryption_algorithm、kms_key_id 全部开放加密直接定死为开，只允许传入自带的 KMS key
规格表达instance_type、volume_type、iops、throughput 各自一个变量一个 size 取 small / medium / large，内部映射成具体配置
默认值默认值是 provider 的默认（通常最不安全）默认值是团队认可的安全基线，要放宽必须显式传参
类型约束type = any 或干脆是字符串拼 JSON精确的 object 类型加 validation，错误拦在 plan 之前
逃生口没有，遇到没覆盖的字段只能 fork 模块留一到两个受控扩展点，比如 extra_tags、extra_ingress_rules
输出把整个资源对象 = aws_db_instance.this 输出只输出下游真正需要的 ID、地址、端口
# ---------- modules/postgres/variables.tf ----------
variable "name" {
  description = "业务名，会作为所有资源的命名前缀"
  type        = string

  validation {
    # 把错误拦在 plan 之前，比 apply 到一半失败便宜得多
    condition     = can(regex("^[a-z][a-z0-9-]{2,23}$", var.name))
    error_message = "name 只允许小写字母、数字和连字符，长度 3 到 24，且以字母开头。"
  }
}

variable "env" {
  description = "环境标识，决定备份与高可用策略"
  type        = string

  validation {
    condition     = contains(["dev", "staging", "prod"], var.env)
    error_message = "env 只能是 dev、staging 或 prod。"
  }
}

variable "size" {
  description = "容量档位。刻意不暴露实例规格，由模块统一映射，避免各团队各选一套"
  type        = string
  default     = "small"

  validation {
    condition     = contains(["small", "medium", "large"], var.size)
    error_message = "size 只能是 small、medium 或 large。"
  }
}

# 复杂输入用 object 加 optional（1.3+），既有结构约束又不逼调用方写全
variable "backup" {
  description = "备份策略。不传时按 env 取安全默认值"
  type = object({
    retention_days    = optional(number, 7)
    window            = optional(string, "17:00-18:00")
    copy_tags         = optional(bool, true)
    final_snapshot    = optional(bool, true)
  })
  default = {}

  validation {
    condition     = var.backup.retention_days >= 1 && var.backup.retention_days <= 35
    error_message = "retention_days 必须在 1 到 35 之间。"
  }
}

variable "extra_tags" {
  description = "受控的逃生口：允许追加标签，但模块自己的标签不可被覆盖"
  type        = map(string)
  default     = {}
}

# ---------- modules/postgres/main.tf 片段 ----------
locals {
  # 档位到规格的映射集中在一处，调整规格不需要动任何调用方
  sizes = {
    small  = { instance_class = "db.t4g.medium", storage = 100 }
    medium = { instance_class = "db.r6g.large",  storage = 500 }
    large  = { instance_class = "db.r6g.2xlarge", storage = 2000 }
  }
  # 模块强制的标签放在后面，确保不会被 extra_tags 覆盖掉
  tags = merge(var.extra_tags, {
    Name      = "${var.name}-${var.env}"
    ManagedBy = "terraform"
    Env       = var.env
  })
  multi_az = var.env == "prod"   # prod 强制多可用区，不给关掉的开关
}

# ---------- modules/postgres/outputs.tf ----------
output "endpoint" {
  description = "连接地址，下游应用唯一需要的东西"
  value       = aws_db_instance.this.address
}

output "port" {
  value = aws_db_instance.this.port
}

output "security_group_id" {
  description = "供下游把自己的安全组加进白名单"
  value       = aws_security_group.db.id
}

三、版本管理：引用方式决定可复现性

source 写法可复现适合风险
./modules/xxx 本地路径随仓库一起版本化单仓库内的私有模块跨仓库复用时只能复制
git::https://...//path?ref=v1.2.0可，tag 通常不动私有 Git 上的共享模块tag 可以被强推覆盖，严格场景直接锁 commit
git::https://...?ref=main不可不要用别人合一次代码，你的下一次 plan 就变了，而你的仓库毫无改动
registry 源加 version = "1.2.3"可公共或私有 registry需要 registry 可用；私有网络要配镜像
registry 源加 version = "~> 1.2"部分内部低环境会自动吃到 1.x 的新小版本，命名调整就可能触发替换
不写 version 约束不可无每次 init -upgrade 都可能换版本
# ---------- 调用方：environments/prod/main.tf ----------
module "orders_db" {
  # Git 源锁 tag。双斜杠表示仓库内的子目录，这是最容易写错的地方
  source = "git::https://git.internal/infra/terraform-modules.git//postgres?ref=v1.4.2"

  name = "orders"
  env  = "prod"
  size = "large"

  backup = {
    retention_days = 30
  }

  extra_tags = {
    CostCenter = "payments"
  }
}

module "vpc" {
  # registry 源用精确版本。生产不要写只锁大版本的约束，
  # 因为小版本里的资源命名调整同样会触发替换。
  source  = "terraform-aws-modules/vpc/aws"
  version = "5.13.0"

  name = "acme-prod"
  cidr = "10.20.0.0/16"
}

# ---------- 模块侧：声明需要什么 provider，但不配置它 ----------
terraform {
  required_version = ">= 1.5"

  required_providers {
    aws = {
      source = "hashicorp/aws"
      # 模块用范围约束，留出升级空间；根模块用 lock 文件锁死实际版本
      version = ">= 5.0, < 6.0"
    }
  }

  # 需要第二个 provider 实例时这样声明，而不是在模块里写 provider 块
  configuration_aliases = [aws.replica]
}
❌
模块里绝对不要写 provider 块

模块内部自己配置 provider，会带来三个后果：调用方无法决定它用哪个 region、哪个账号、哪套凭证，多 region 复用直接失效；这个模块无法被 count 或 for_each 调用，Terraform 会报错；销毁时还可能出现 provider 配置已消失而资源还在的僵局。正确形态是模块只在 required_providers 里声明依赖，需要多个实例时用 configuration_aliases，由根模块通过 providers = { aws = aws.us_east } 显式传入。

四、哪些改动是破坏性的

stateDiagram-v2 [*] --> v0x v0x --> v0x: 接口随便改，使用方只有自己 v0x --> v100: 接口稳定，对外宣布可用 v100 --> v1y: 加可选变量或加输出，向后兼容 v1y --> v1y: 修 bug 与内部实现优化 v1y --> v200: 改变量名、删输出、改资源地址 v200 --> v2y: 新主线继续演进 v1y --> deprecated: 宣布废弃并给迁移窗口 deprecated --> [*] v200 --> moved: 模块内附 moved 块 moved --> v2y: 下游升级时自动完成地址迁移
改动下游 plan 的表现严重度缓解办法
新增带默认值的可选变量无变化兼容正常发小版本
新增输出无变化兼容正常发小版本
删除或重命名变量init 或 plan 直接报错破坏性发大版本；旧变量先保留一版并标记废弃
删除或重命名输出引用它的下游代码报错破坏性发大版本，changelog 明确列出
收紧 validation 或改变量类型原本合法的输入被拒破坏性发大版本，并提前统计现有取值
改资源在模块内的地址（改名、再包一层子模块）销毁加新建最危险模块内写 moved 块，下游升级时自动迁移
改命名规则（前缀、拼接方式）资源名变化，多数资源会被替换最危险发大版本；有状态资源要人工评估数据
count 换成 for_each索引变 key，全部资源被替换最危险逐个写 moved 块
提高 required_version 或 provider 下限低版本环境 init 失败破坏性发大版本，先确认所有使用方的版本

五、嵌套深度、count 与 for_each

flowchart TB subgraph L0["根模块：环境目录，只做装配"] R1["environments/prod/main.tf
传参与 provider 配置"] end subgraph L1["组合模块：一个业务域的完整形态"] M1["service-stack
应用 + 数据库 + 缓存 + 告警"] end subgraph L2["基础模块：单一职责"] B1["postgres"] B2["redis"] B3["alb"] B4["alarms"] end R1 --> M1 M1 --> B1 M1 --> B2 M1 --> B3 M1 --> B4 R1 --> B3 M1 -.->|"再往下嵌一层就到三层
plan 里的资源地址会长到读不动"| X["不要有 L3"]

两层是经验上的上限：根模块装配、组合模块表达业务域、基础模块负责单一职责。超过两层会同时出现三个问题——plan 输出里的资源地址变成 module.a.module.b.module.c.aws_instance.x[0] 这种长度，定位问题要横向滚屏；每加一个变量都要在每一层的 variables.tf 里透传一遍，改一个参数要动四五个文件；出错时你无法判断是哪一层的默认值生效了。

维度countfor_each
state 里的地址module.x[0]，位置索引module.x["orders"]，稳定的 key
删掉中间一个元素后面所有元素索引前移，全部被替换重建只影响被删的那一个
输入形态数字，通常配合列表取下标map 或 set of string
适合只用来表达「要不要创建」这一个开关表达「有哪些实例」，绝大多数场景
可读性plan 里只有数字，看不出是哪个业务plan 里带 key，一眼知道动的是谁
坑列表顺序来自变量，顺序一变全部重建key 必须是已知的静态值，不能依赖 apply 时才产生的属性，否则报错要求先分步 apply

结论很直接：count 只用于 0 或 1 的条件创建，凡是「多个实例」都用 for_each。已经用了 count 又想改的，必须逐个写 moved 块把下标搬成 key，否则一次 apply 就是全量重建。

六、模块的测试

手段能测到什么测不到什么成本
fmt -check 与 validate语法、类型引用、未声明的变量任何逻辑与默认值是否合理秒级，必进 CI
tflint 与 tfsec 或 checkovprovider 层面的错误用法、安全基线（未加密、公网暴露）业务约定秒级，必进 CI
terraform test 的 plan 用例（1.6+ 内置）渲染出的属性值、命名规则、validation 是否真的拦住非法输入provider 的真实行为、依赖顺序秒级且不产生费用，性价比最高
terraform test 的 apply 用例真实创建与销毁、依赖顺序、provider 的隐式行为跨系统的连通性分钟级，产生真实费用，只给核心模块做
Terratest（Go）端到端：HTTP 探活、连接数据库、故障注入—最高，需要 Go 与专用测试账号
plan 快照对比模块升版本后下游 plan 的 diff 是否符合预期—低，升级模块前的必做动作
# ---------- modules/postgres/tests/defaults.tftest.hcl ----------
# terraform test（1.6+ 内置）。只跑 plan 的用例不创建资源，秒级反馈。

variables {
  name = "orders"
  env  = "dev"
}

run "命名与默认值" {
  command = plan

  assert {
    condition     = aws_db_instance.this.identifier == "orders-dev"
    error_message = "命名规则被改动了，这属于破坏性变更"
  }

  assert {
    condition     = aws_db_instance.this.storage_encrypted == true
    error_message = "加密必须默认开启，不允许由调用方关闭"
  }

  assert {
    condition     = aws_db_instance.this.multi_az == false
    error_message = "dev 环境不应该开多可用区，成本没必要"
  }
}

run "prod 强制多可用区与长备份" {
  command = plan

  variables {
    env    = "prod"
    name   = "orders"
  }

  assert {
    condition     = aws_db_instance.this.multi_az == true
    error_message = "prod 必须开多可用区"
  }
}

run "非法输入必须被 validation 拦住" {
  command = plan

  variables {
    name = "Orders_DB"   # 大写和下划线都不合法
  }

  # 断言校验真的生效了。没有这类用例时，validation 写错了没人会发现
  expect_failures = [var.name]
}

配套的工程约定同样重要：examples/ 目录下放最小可用示例（没有示例的模块没人敢用，因为调用方无法确认哪些变量必须一起传），README 用 terraform-docs 从变量与输出注释自动生成并在 CI 里校验是否最新，每个模块维护一份 CHANGELOG 明确标注破坏性变更。仓库组织上，单仓多模块的优点是跨模块重构方便、CI 配置只写一次，缺点是 tag 必须带模块名前缀（形如 postgres/v1.4.2）否则版本语义会互相污染；每模块一仓的版本边界最干净，代价是十几个仓库的 CI 与权限都要维护，通常只在模块数量少且对外发布时才划算。

七、反模式

反模式典型现场代价正确做法
把整个环境写成一个巨型模块module "prod" { ... } 内含上百个资源变量列表爆炸，任何小改动都要在整个环境上 plan，爆炸半径等于环境按业务域拆成组合模块，环境目录只做装配
模块里写死账号或 regionprovider "aws" { region = "cn-hangzhou" }无法多 region 复用，也无法被 for_each 调用模块只声明 required_providers，由根模块传入
引用模块不锁版本?ref=main 或不写 version别人合一次代码你的 plan 就变，事故无法复盘锁 tag 或精确版本，升级作为一次可评审的提交
模块里用 local-exec 调 shell用脚本补 provider 没覆盖的能力不幂等、不进 state、plan 看不到影响，换台机器就跑不通用官方资源或写 provider；实在没有就把这步移出 Terraform
输出整个资源对象output "db" { value = aws_db_instance.this }下游耦合内部结构，模块内部重构变成破坏性变更，敏感属性还会落进下游 state只输出 ID、地址、端口这类稳定契约
模块层层嵌套四五层为了「更 DRY」plan 地址长到读不动，变量层层透传，默认值来源不明控制在两层
用几十个布尔开关表达差异enable_a、enable_b、create_c组合数爆炸，没有任何一条路径被测过档位化参数，或拆成两个各自内聚的模块
模块没有 examples 与文档只有作者会用使用方靠读源码猜，猜错就是线上事故examples 目录加自动生成的文档，并在 CI 里校验
❌
最容易踩的坑
  • Git 源忘了写双斜杠子目录（...git//postgres?ref=v1 里的那两个斜杠），Terraform 会把整个仓库当模块，报找不到资源却看不出原因。
  • ?ref=main 一路用到生产，某天同事往模块仓库合了一个提交，毫不相关的环境在下一次 plan 里出现了资源替换。
  • 单仓多模块却用了不带模块名的 tag，v2.0.0 对某个模块是破坏性变更，对其他模块却什么都没改，所有使用方被迫一起升级。
  • 模块内部把资源改了个名字就发小版本，下游 plan 显示销毁加新建，有人没细看就 apply，数据库被重建。
  • 把 count 当多实例用，删掉中间那个元素后索引前移，后面所有实例被替换重建。
  • for_each 的 key 用了 apply 时才知道的属性（比如另一个资源的 ID），报错要求先分步 apply，只能临时拆成两次。
  • 模块里写了 provider 块，直到某天想用 for_each 调用它才发现根本不允许，此时已有十几处在用。
  • 变量类型写成 any，调用方传了个字符串进去，错误直到 apply 调云 API 时才暴露，前面的资源已经创建了一半。
  • validation 写了但从没测过，条件表达式本身有误，非法输入照样通过——需要 expect_failures 这类用例来保证校验真的生效。
  • 默认值沿用 provider 的默认（未加密、公网可访问），十几个环境同时缺少加密，合规检查一次性报出一大片。
  • 模块里 merge 标签时把 var.extra_tags 放在后面，调用方一个同名标签就覆盖掉了模块强制的 ManagedBy 与 Env。
  • 模块里用 local-exec 跑脚本，本地能过而 CI 镜像里没那个命令，plan 阶段完全看不出问题，apply 才失败。
