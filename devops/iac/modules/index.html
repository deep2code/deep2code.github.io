Terraform Module 与最佳实践

🏷️ IaC / Terraform

为什么需要 Module

写过几个环境之后你会发现：每个项目都在重复写 VPC、安全组、ECS 这套模板。改个标签规范，要在十个地方改。这就是 DRY（Don't Repeat Yourself）原则要解决的问题——Module 就是 Terraform 的"函数"，把一坨资源封装成可复用的黑盒。

Module 不是什么高深概念。你一直在用——resource "aws_instance" 本身就是一个 Module，只是它由 provider 提供。你也可以自己写 Module，给团队用、给公司用、甚至发布到公开 registry 给全世界用。

Module 的标准结构

一个正经的 Module 至少三个文件：main.tf（资源定义）、variables.tf（输入变量）、outputs.tf（输出值）。这和你之前写的工作目录结构一模一样——其实工作目录本身就是一个 Module，根 Module。

modules/
├── vpc/
│   ├── main.tf        # 建 VPC、子网、网关
│   ├── variables.tf   # 输入：环境名、网段、AZ
│   └── outputs.tf     # 输出：vpc_id、子网 ID
├── ecs/
│   ├── main.tf
│   ├── variables.tf
│   └── outputs.tf
└── rds/
    ├── main.tf
    ├── variables.tf
    └── outputs.tf

拿一个 VPC Module 举例，variables.tf 定义输入：

# modules/vpc/variables.tf
variable "env" {
  description = "环境名"
  type        = string
}

variable "vpc_cidr" {
  description = "VPC 网段"
  type        = string
  default     = "10.0.0.0/16"
}

variable "private_subnet_cidrs" {
  description = "私网子网列表"
  type        = list(string)
  default     = ["10.0.1.0/24", "10.0.2.0/24"]
}

outputs.tf 定义输出：

# modules/vpc/outputs.tf
output "vpc_id" {
  description = "创建的 VPC ID"
  value       = alicloud_vpc.main.id
}

output "private_subnet_ids" {
  description = "私网子网 ID 列表"
  value       = alicloud_vswitch.private[*].id
}

上层调用就变成一行：

# 根目录 main.tf
module "vpc" {
  source = "./modules/vpc"

  env               = var.env
  vpc_cidr          = "10.1.0.0/16"
  private_subnet_cidrs = ["10.1.1.0/24", "10.1.2.0/24"]
}

# 别的 Module 引用 VPC Module 的输出
module "ecs" {
  source = "./modules/ecs"

  vpc_id    = module.vpc.vpc_id
  subnet_ids = module.vpc.private_subnet_ids
}
Module 的边界
Module 只暴露"输入变量"和"输出值"，内部细节对外黑盒。上层不需要知道你建了几个子网、怎么配的路由表，只用 module.vpc.vpc_id 就行。这就是封装。

Public Registry：别什么都自己写

Terraform 有官方的公共 Module 仓库 Terraform Registry（registry.terraform.io），里面有海量现成 Module。你要建 VPC、EKS、RDS，别从零写——先搜一下官方或社区维护的 Module，质量比你自己写的高。

调用公开 Module：

# 用官方 VPC Module
module "vpc" {
  source  = "terraform-aws-modules/vpc/aws"
  version = "~> 5.0"

  name = "${var.env}-vpc"
  cidr = "10.0.0.0/16"

  azs             = ["ap-southeast-1a", "ap-southeast-1b"]
  private_subnets = ["10.0.1.0/24", "10.0.2.0/24"]
  public_subnets  = ["10.0.101.0/24", "10.0.102.0/24"]
}

source 指向 registry 的 Module，version 锁版本。这和你引用 provider 一模一样——别人写好的轮子，你直接用。

版本约束：Module 也有版本

公开 Module 会持续更新，你不锁版本，今天跑通的代码明天可能就因为 Module 升级而行为变了。版本约束写法：

写法含义我的建议
~> 5.05.0.x，不跨次版本生产环境首选
>= 5.05.0 以上任意开发环境可以
5.0.0钉死一个版本最严格，问题最少
不写随便拉最新别这么干
自动升级的坑
我有次没锁 Module 版本，CI 拉了个新版本的 VPC Module，默认多开了 NAT 网关，账单多了两千刀。从那以后生产环境我都钉死版本，要升级专门开 PR review。.terraform.lock.hcl 帮你锁定实际解析的版本，提交 Git。

Module 组合模式

大型项目的 Module 不是平铺的，是分层组合的。典型结构是"根 Module 调用子 Module"，子 Module 再调用更细的 Module：

flowchart TD ROOT[根 Module
业务组合层] ROOT --> VPC[vpc Module
网络基础] ROOT --> SG[security-group Module
防火墙] ROOT --> ECS[ecs Module
应用服务器] ROOT --> RDS[rds Module
数据库] ECS --> VPC ECS --> SG RDS --> VPC RDS --> SG

依赖方向很清楚：根 Module 是"装配车间"，决定用哪些子 Module、怎么传参；子 Module 只管自己那块资源。改安全组策略只动 sg Module，不用碰别的。这就是关注点分离。

环境分离的正确姿势

第三篇讲过 tfvars 按环境分。配合 Module，环境分离变成这样：

infra/
├── environments/
│   ├── dev/
│   │   ├── main.tf       # 调 Module，传 dev 参数
│   │   └── backend.tf    # dev 的 state 配置
│   ├── staging/
│   │   ├── main.tf
│   │   └── backend.tf
│   └── prod/
│       ├── main.tf
│       └── backend.tf
└── modules/               # 所有环境共用的 Module

每个环境一个独立目录、独立 state、独立 backend 配置。dev 和 prod 用同一套 Module，只是参数不同。改 Module 逻辑同时影响所有环境，但参数和 state 完全隔离。

.tfvars 组织策略

tfvars 文件别乱放。我团队的约定：

  • 通用默认值：放在 variables.tf 的 default 里，所有环境共用。
  • 环境差异值：放 environments/{env}.tfvars，只写和默认值不同的部分。
  • 敏感值：绝不上 Git。用环境变量或 CI/CD 的 secret 注入，terraform apply -var="db_password=$DB_PASS"。
# 本地跑 dev，指定 tfvars
terraform apply -var-file=environments/dev.tfvars

# CI 跑 prod，敏感值从 secrets 注入
terraform apply \
  -var-file=environments/prod.tfvars \
  -var="db_password=${DB_PASSWORD}"

CI/CD 里跑 Terraform

手工 apply 是不可持续的。成熟做法是把 Terraform 接进 CI/CD：每次改代码提 PR，流水线自动跑 plan，把 plan 结果贴到 PR 评论里；合并后自动 apply。

flowchart LR PR[提 PR 改代码] --> PLAN[CI 自动跑 plan] PLAN --> COMMENT[plan 结果贴 PR 评论] COMMENT --> REVIEW[人工 review 批准] REVIEW --> MERGE[合并到 main] MERGE --> APPLY[CI 自动跑 apply] APPLY --> NOTIFY[通知 Slack 成功/失败]

GitHub Actions 大致这样：

# .github/workflows/terraform.yml
name: Terraform
on: [pull_request, push]

jobs:
  plan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: hashicorp/setup-terraform@v3
      - run: terraform init
      - run: terraform plan -var-file=environments/dev.tfvars
我团队的规矩
dev 环境合并即自动 apply，staging 要 Tech Lead 手动确认，prod 要两个人审批。流水线里强制 terraform plan 必须先跑过、PR 评论里能看到完整 diff，才允许合并。这把"plan 必须人工看"这条铁律固化成了流程。

pre-commit hooks：提交前先查一遍

代码提交到 Git 之前，先跑一遍格式化和静态检查。我用 pre-commit 框架 + terraform 插件：

# .pre-commit-config.yaml
repos:
  - repo: https://github.com/antonbabenko/pre-commit-terraform
    rev: v1.90.0
    hooks:
      - id: terraform_fmt
      - id: terraform_validate
      - id: terraform_docs
      - id: terraform_tflint

装一次，以后每次 git commit 自动跑：terraform fmt 格式化、terraform validate 语法检查、tflint 查最佳实践违规。写错了直接拦住，不用等到 CI 才报错。

FAQ

Q：Module 写多深合适？
别为了拆而拆。一个 Module 超过 500 行再考虑拆。拆太细会导致 Module 之间传参爆炸，调用方看不懂。先写一坨，重复三次以上再抽。

Q：本地 Module 和 registry Module 怎么选？
通用能力（VPC、EKS）用 registry 的，别自己写。业务定制强的（你们公司特有的标签规范、监控对接）用本地 Module。

Q：Module 版本升级怎么测？
在 dev 环境先升，跑一遍 plan，看 diff 是不是预期的。没问题再升 staging、prod。别一上来就动 prod。

Q：Module 里能写 provider 配置吗？
尽量不要。provider 应该在根 Module 统一配，子 Module 只消费。子 Module 配 provider 会造成嵌套冲突，除非你要多 provider（多云），那用 providers 显式传。

我的结论

Module 是 Terraform 从"能跑"到"可维护"的关键一跃。核心就三句话：重复三次才抽 Module、用 registry 的现成轮子、版本锁死在 tfvars 里。配合 pre-commit 和 CI/CD，你的基础设施代码就和应用代码一样有工程纪律了。

我团队现在的模式：通用基础设施用 registry Module，业务封装用本地 Module，每个环境独立目录独立 state，PR 流程强制 plan review。这套流程跑下来，线上事故率降了一大半。下一篇做最后的选型对比——Terraform、OpenTofu、Pulumi、CloudFormation、Crossplane 到底怎么选。
