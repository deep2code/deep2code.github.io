Terraform State 管理：远端后端、锁与拆分

🏷️ Terraform State

Terraform 的所有魔力都建立在一个前提上：它知道「上一次我造出来的东西长什么样」。这份记忆就是 state。没有 state，plan 无法区分「这个资源需要新建」和「这个资源已经存在只是属性变了」，整个声明式模型直接崩塌。所以 state 不是缓存、不是临时文件，它是与云上真实资源同等重要的生产资产。

本文只讲 state。Terraform 的基本语法与第一个项目见站内《Terraform 入门与 HCL 语法》，IaC 的核心模型与漂移概念见《IaC 基础设施即代码总览》，Terraform 与 Pulumi、CloudFormation、Ansible 的取舍见《IaC 工具对比》，模块的接口与版本设计见《Terraform Module 与最佳实践》。

三条容易被忽略的事实。第一，dependencies 是存在 state 里的，不只在代码里——这就是为什么你删掉代码里的依赖关系后，销毁顺序依然按老的来。第二，lineage 保证你不会把 A 项目的 state 推到 B 项目的后端上（推错时 Terraform 会明确拒绝）。第三，serial 是并发保护的最后一道防线，两个人拿到同一个 serial 各自写回时，后写的会覆盖前者，这也是为什么锁不可省。

state 丢失后的现象资源类型举例实际后果
plan 显示全量新建—Terraform 认为自己一无所有
apply 因撞名失败S3 桶、IAM 角色、VPC 名称唯一的资源看起来是「安全地失败」，但会执行到一半，留下半套资源
apply 真的创建成功ECS 实例、安全组、负载均衡造出一整套重复资源，账单翻倍，流量被新 LB 分走一部分，现象诡异难排查
旧资源脱管全部原来的资源没人管了，删不掉也改不动，只能人工 import 回来

二、远端后端是生产上唯一可接受的做法

后端锁机制版本历史静态加密权限粒度适合
S31.10 起支持 use_lockfile 原生锁；此前依赖 DynamoDB 表（1.11 起该参数已废弃）靠桶的版本控制，需自己开SSE 加 KMS，强烈建议专用 keyIAM 策略可按对象前缀细分AWS 上的默认选择
Terraform Cloud 或 Enterprise内置，且有排队机制内置，带 diff 与操作人平台负责工作区级别的 RBAC团队多、需要审计与审批流
GCS基于对象的原生锁，无需额外组件桶的对象版本控制默认加密，可换 CMEKIAM 加条件GCP 上最省事
阿里云 OSS可选 TableStore 表做锁（新版也支持基于 OSS 的锁文件）OSS 版本控制KMS 加密RAM 策略按路径国内云
Consul 或 etcd有会话锁，但会话超时语义容易踩坑无需自建ACL token不推荐用于新项目
本地文件只有同机文件锁只有一个 backup 文件无无只适合一次性实验
# ---------- backend.tf ----------
terraform {
  required_version = "~> 1.9"

  backend "s3" {
    # 后端配置里不能引用变量或 locals，这是硬限制。
    # 需要多环境时用 partial configuration：这里只写公共部分，
    # 其余通过 terraform init -backend-config=env/prod.hcl 传入。
    bucket = "acme-tfstate-prod"
    key    = "platform/network/terraform.tfstate"   # 一个 key 就是一份 state，按业务域规划路径
    region = "ap-northeast-1"

    encrypt    = true
    kms_key_id = "arn:aws:kms:ap-northeast-1:111122223333:key/abcd-1234"

    # Terraform 1.10+ 的原生锁：在 key 旁边写一个 .tflock 对象，不再需要 DynamoDB。
    # 1.10 之前请保留 dynamodb_table，且该表的主键必须叫 LockID。
    use_lockfile = true

    # 让这份 state 只能被指定角色写，比在 IAM 用户上开放权限安全得多
    role_arn = "arn:aws:iam::111122223333:role/terraform-platform"
  }
}

⚠️
别把后端配置做成「运行时才知道指向哪」

后端块里不允许引用变量，这是 Terraform 的有意设计——如果 state 的位置可以被变量决定，那么「我这次操作的是哪个环境」就成了运行时才确定的事，一个环境变量写错就把生产的 state 覆盖了。需要多环境时只能用 partial configuration，而且 -backend-config 文件必须入库并被评审。更稳的做法是每个环境一个目录，backend 块里把 bucket 和 key 写死。

三、状态锁：它拦住的到底是什么

sequenceDiagram participant A as 同事 A participant L as 锁（DynamoDB 或 tflock 对象） participant S as state 对象存储 participant B as 同事 B A->>L: apply 开始，尝试获取锁 L-->>A: 获取成功，写入持锁者与操作 ID A->>S: 读取 state，serial 为 42 B->>L: 几乎同时发起 apply L-->>B: 拒绝，返回持锁者、操作类型与锁 ID Note over B: 正确反应是等待，而不是 force-unlock A->>A: 调用云 API 创建资源 A->>S: 写回 state，serial 变成 43 A->>L: 释放锁 B->>L: 重试获取锁，成功 B->>S: 读到 serial 43 的最新 state Note over A,B: 如果 B 当时强行解锁并写回基于 serial 42 的 state，A 创建的资源就会从记录里消失

锁保护的不是云上的资源，而是那一次 state 读改写的原子性。它防的是「两个人基于同一份旧 state 各自计算并写回」这种丢失更新。所以没有锁的后端（纯 S3 且未开 use_lockfile、也没配 DynamoDB）在单人使用时看不出问题，一旦两条流水线同时跑就会静默地把资源写丢。

情况该怎么做不要做什么
报锁冲突，持锁时间只有几分钟等它跑完，或看 CI 上那条流水线直接解锁
apply 被 Ctrl-C 或 CI 超时杀掉，锁残留先确认进程真的没了（查 CI 任务状态），再用报错里给出的那个具体锁 ID 解锁，解锁后立刻跑一次 plan 确认 state 与现实一致跳过确认直接解锁；用猜的锁 ID
apply 中途被杀，资源已创建但 state 未写回plan 会显示要重新创建，需要 import 把已创建的资源纳管回来直接 apply，那会创建出重复资源
经常撞锁这是该拆 state 的信号，不是该常态化解锁的信号把 force-unlock 写进流水线的重试逻辑

四、state 里有明文敏感数据

来源典型字段sensitive 标记有用吗该怎么办
数据库资源的初始密码password只影响命令行输出与 output，state 里照旧明文密码由密钥服务生成，Terraform 只引用；或创建后立刻轮转
Terraform 生成的私钥tls_private_key 的 private_key_pem同上尽量不要用 Terraform 生成长期私钥
访问密钥与连接串secret_access_key、connection_string同上交给密钥服务，state 里只留 ARN 或路径
从密钥服务读出来的值data 源的返回无用，data 的结果一样会落进 state这是最反直觉的一点：读一次就等于抄了一份到 state
output 输出被下游 terraform_remote_state 读取的值无用不要把密文放 output
❌
sensitive 不是加密

sensitive = true 做的唯一一件事是让 Terraform 在终端和 plan 输出里把值打成掩码，写进 state 时仍然是明文。同理，用 data 源从密钥服务里读出一个密码，这个密码就已经落进 state 了。因此结论只有一条：后端必须开加密、开版本控制并严格收口访问权限，*.tfstate 与 *.tfstate.backup 必须写进 .gitignore，能读这个 state 的人等于能读到环境里所有的密钥。

五、state 操作命令：什么时候用，误用会怎样

命令做什么什么时候用误用的后果
state list列出所有资源地址任何操作前先看地址长什么样无风险，建议养成习惯
state show打印某个资源在 state 里的全部属性确认云上真实 ID、排查漂移会把敏感字段打到终端和 CI 日志里
state mv在 state 内改资源地址最有用的一条：重命名资源、移进或移出 module 时避免重建地址写错会让 Terraform 认为资源不存在，下次 apply 重复创建；且是命令式操作，没有评审痕迹
state rm只从 state 移除，不删真实资源要把某个资源交给别的 state 或改为手工管理移除后忘记 import，资源变成谁都不管的孤儿，且下次 apply 会新建一个同类资源
import把已存在的资源纳入管理接管手工创建的资源、救 state 丢失导入后必须跑 plan 并把差异抹平，否则第一次 apply 就会按代码把资源改掉；1.5 起建议用 import 块，可以在 plan 里预览
taint 与 untaint在 state 里标记资源为「已污染」，下次 apply 时替换已被 apply -replace 取代，不建议再用标记后忘记 apply，别人的一次无关 apply 会顺手替换掉这个资源
apply -replace=ADDR本次计划中强制替换某资源需要重建单个资源时的正确姿势，意图写在命令里而不是留在 state 中替换有状态资源（数据库、带数据的磁盘）会真的销毁数据
state pull 与 state push下载与上传整份 state备份、离线修补、跨后端迁移push 会整体覆盖；lineage 或 serial 不匹配时强推等于丢掉别人的变更
refresh只用云上现状刷新 state排查漂移。注意它是 plan -refresh-only 的旧形态单独 refresh 会把漂移直接写进 state，掩盖掉「有人手改过」这个事实
#!/usr/bin/env bash
set -euo pipefail

# 0) 任何 state 手术之前，先留一份带时间戳的备份。这一步不能省。
terraform state pull > "state-backup-$(date +%Y%m%d-%H%M%S).json"

# 1) 先看地址。for_each 的地址带方括号和引号，复制的时候极容易漏引号
terraform state list | grep -i 'aws_instance'
terraform state show 'module.web.aws_instance.app["blue"]'

# 2) 重命名或搬家：单引号包住地址，避免 shell 吃掉引号和方括号
terraform state mv 'aws_instance.web' 'module.web.aws_instance.app'

# 3) 纳管一个手工创建的资源，然后立刻确认差异
terraform import 'aws_s3_bucket.logs' 'acme-prod-logs'
terraform plan   # 目标是零变更；有变更说明代码与现状不一致，先改代码而不是改云上

# 4) 排查漂移：只刷新不改动，把差异打出来给人看
terraform plan -refresh-only

# 5) 锁残留的处理顺序：读报错里的锁 ID -> 确认持锁进程已死 -> 用该 ID 解锁 -> 立刻 plan 核对
terraform force-unlock 8f2c4e91-6b3d-4a17-9c52-0d7e1a3b8f04

# 6) 后端迁移（比如从本地迁到 S3）：改完 backend 块后
terraform init -migrate-state   # 会提示是否把现有 state 复制过去，看清再回车

# 7) 清掉某个资源的管理关系但保留云上资源（交接给别的 state 时）
terraform state rm 'aws_route53_zone.legacy'
# 别忘了在新的 state 里 import 回来，否则它就成了孤儿资源

六、代码重构与 state 的对应关系

Terraform 认的是 state 里的资源地址，不是资源的名字或用途。任何让地址发生变化的重构（重命名、移进 module、把 count 换成 for_each），在 Terraform 眼里都是「旧地址的资源消失了、新地址的资源需要创建」，plan 会显示销毁加新建。

# ---------- 重构的正确写法：moved 块（Terraform 1.1+） ----------
# 场景一：单纯改名
moved {
  from = aws_instance.web
  to   = aws_instance.api
}

# 场景二：把资源收进 module
moved {
  from = aws_security_group.app
  to   = module.app_network.aws_security_group.app
}

# 场景三：count 换成 for_each，下标变成 key，必须逐个声明
moved {
  from = aws_subnet.private[0]
  to   = aws_subnet.private["ap-northeast-1a"]
}
moved {
  from = aws_subnet.private[1]
  to   = aws_subnet.private["ap-northeast-1c"]
}

# ---------- 纳管已有资源的正确写法：import 块（Terraform 1.5+） ----------
# 相比 terraform import 命令，它能在 plan 阶段预览，而且这份声明会留在仓库里
import {
  to = aws_s3_bucket.logs
  id = "acme-prod-logs"
}

resource "aws_s3_bucket" "logs" {
  bucket = "acme-prod-logs"
  # 导入后第一次 plan 一定要是零变更。如果显示要改属性，
  # 说明代码写得和云上现状不一致，改代码去贴合现状，而不是让 apply 去改线上。
}

moved 块相比 state mv 的优势在于它是声明式且进仓库的：所有人 apply 一次之后都会自动完成搬迁，不需要每个人手工敲命令；变更还能在 PR 里被看到。moved 块在完成迁移并且所有环境都 apply 过之后可以删掉，但不着急删也没有副作用。

七、拆分 state：按爆炸半径而不是按目录好看

单一巨型 state 的症状根因拆分后的改善
plan 要等三到十分钟每次都要刷新全部资源，provider 的 API 调用量与资源数成正比只刷新本 state 内的资源
网络组改 DNS 把应用组的发布卡住锁是整份 state 的各自持有各自的锁
一次误操作毁掉整个环境爆炸半径等于 state 范围爆炸半径收敛到单个业务域
谁都能改数据库权限只能按整份 state 给按 state 的对象前缀分配 IAM 权限
state 文件几十 MB，命令卡顿单个 JSON 过大，每次读写全量传输回到 MB 以内

跨 state 取值有两条路。terraform_remote_state 直接读上游 state 的 output，代价是下游被上游的 output 结构绑死，上游改一个 output 名字下游就崩，而且下游需要上游 state 的读权限（等于能读到上游的所有敏感值）。更好的做法是用 data 源按标签或名字查询云上的真实资源——它只依赖「资源存在且带着约定的标签」这个弱契约，也不需要跨 state 的权限。

# ---------- 推荐：data 源按约定标签查询，不依赖上游 state ----------
data "aws_vpc" "main" {
  filter {
    name   = "tag:Name"
    values = ["acme-prod"]
  }
}

data "aws_subnets" "private" {
  filter {
    name   = "vpc-id"
    values = [data.aws_vpc.main.id]
  }
  tags = {
    Tier = "private"   # 弱契约：只要求标签规范稳定，上游怎么重构都不影响下游
  }
}

# ---------- 次选：terraform_remote_state，只在真的没法查询时用 ----------
data "terraform_remote_state" "network" {
  backend = "s3"
  config = {
    bucket = "acme-tfstate-prod"
    key    = "platform/network/terraform.tfstate"
    region = "ap-northeast-1"
  }
  # 代价一：需要上游 state 的读权限，等于能读到上游全部敏感属性
  # 代价二：下游代码绑死了上游的 output 名字与结构，上游重命名 output 就是破坏性变更
}

resource "aws_instance" "app" {
  subnet_id = data.terraform_remote_state.network.outputs.private_subnet_ids[0]
  # 上面这行还额外依赖了「列表顺序稳定」这个假设，顺序一变机器就会换子网重建
}

八、workspace 不适合做环境隔离，以及灾备

隔离手段state 是否物理分离后端与凭证误操作到错误环境的可能建议
workspace同一后端同一前缀下的不同 key完全共用高：只差一次 select，命令行没有任何视觉区分只用于临时评审环境或短期实验
每环境一个目录加独立 backend是可按目录配不同角色低：当前目录就是环境推荐
每环境一个云账号是完全隔离，凭证也不通最低生产强隔离的最佳形态
靠 tfvars 区分否共用极高：忘传 -var-file 就用默认值打到别的环境只能作为目录隔离之上的补充

灾备不是「开了版本控制就等于有备份」。真正需要的是三件事：后端开对象版本控制并设保留策略；CI 在每次 apply 前把 state pull 的结果归档到另一个账号或另一个桶（防止有人有权限把桶和版本一起删了）；每季度做一次恢复演练——在隔离环境里用备份 state 加当前代码跑一次 plan，确认输出是零变更。没演练过的备份不能算备份，常见的翻车是备份里的 lineage 与后端现有的不一致，恢复时被 Terraform 拒绝，而这件事只有演练过才会提前知道。

九、反模式

反模式为什么会发生代价正确做法
state 放本地或提交进 Git「先跑起来再说」敏感数据永久留在仓库历史；多人协作必然覆盖丢数据第一天就配远端后端，tfstate 进 gitignore
后端没有锁只配了对象存储，没开 use_lockfile 也没建锁表并发 apply 静默丢失资源记录，事后无法解释资源为何脱管确认后端的锁真的生效，并在 CI 里做一次并发测试
把 force-unlock 当常规操作撞锁太频繁，图快迟早在对方 apply 中途解锁，造成资源脱管与 state 回退频繁撞锁是拆 state 的信号
一个 state 管所有环境省事改 dev 需要刷新 prod 的全部资源，一次 apply 打错就伤生产环境目录加独立后端，甚至独立账号
随手 state rm 之后忘了 import只想「让这个报错消失」孤儿资源长期在账单上，且下次 apply 新建一个同类资源rm 与 import 成对出现，并写在同一个变更单里
后端配置写成变量或靠环境变量决定想让一套代码跑所有环境init 时才知道指向哪个 state，一次失误覆盖生产partial configuration 且配置文件入库评审
用单独的 refresh 掩盖漂移plan 有杂音，想让它干净把别人的手改静默写进 state，审计线索消失用 plan -refresh-only 看清后回到代码里表达
把密文放 output 给下游读为了跨 state 传参方便下游 state 也存了一份明文，泄露面翻倍下游直接从密钥服务读，state 之间只传 ID 与地址
❌
最容易踩的坑
  • 以为 sensitive = true 能加密 state。它只影响终端输出，state 里仍是明文，包括你用 data 源读出来的密码。
  • S3 后端只开了桶不开版本控制，某次误 state push 覆盖之后无法回到上一版，只能人工 import 几百个资源。
  • Terraform 1.10 之前的 S3 后端没配 DynamoDB 锁表，单人用毫无感觉，接了 CI 之后两条流水线并发 apply，一批资源从 state 里凭空消失。
  • DynamoDB 锁表的主键名不是 LockID，init 能过但加锁时报错，错误信息指向权限问题，容易查错方向。
  • apply 被 Ctrl-C 打断，资源其实已经创建，直接重跑 apply 于是创建了第二份；正确处理是先 import 再 plan。
  • 把资源移进 module 却没写 moved 块，plan 显示销毁加新建，有人没细看就 apply，数据库被重建。
  • count 改 for_each 时只搬了部分索引，剩下的资源在 plan 里表现为销毁，中间那台机器被删掉。
  • 操作 for_each 资源的地址时没用单引号，shell 把方括号和引号吃掉，state mv 作用到了错误的地址上。
  • 用 terraform_remote_state 读上游的列表输出并按下标取值，上游子网顺序一变，下游机器全部换子网重建。
  • 以为 workspace 能隔离环境，某次忘了 workspace select，把 dev 的变更 apply 到了生产。
  • 备份 state 从没做过恢复演练，真出事时才发现 lineage 不匹配，Terraform 拒绝推送。
  • 在 CI 日志里跑 state show 或 output 打印了数据库密码，日志的保留期限比密码的轮转周期长得多。
