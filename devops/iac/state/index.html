Terraform 状态管理

🏷️ IaC / Terraform

state 为什么是命根子

第一篇我说过，state 是 Terraform 的"记忆"。但那只是入门理解。这篇把它讲透：state 本质上是一张资源账本，记着"我在云上管了哪些资源、每个资源的真实 ID 是什么、和我代码里的哪个 resource 块对应"。

为什么必须有这张账本？因为云资源没有"名字"这种全局唯一标识。你代码里写 aws_instance.web，云上那台机器的真实身份是 i-0abc123def——这个映射只能靠 state 记。没有 state，Terraform 根本不知道哪台机器是它开的，你再 apply 就会重新开一台。

本地 state 为什么不行

新手都是本地跑，state 存在你电脑上的 terraform.tfstate。一个人玩没问题，一旦多人协作就全是坑：

  1. 各自为政：同事改了代码 apply 完，他的 state 在他电脑上，你电脑上的 state 还是旧的。
  2. 并发 apply 撞车：你和同事同时 apply，两个进程都改同一份资源，云资源被改两次。
  3. 电脑丢了 state 就没了：换电脑、硬盘坏了，Terraform 失忆。
  4. CI/CD 跑不了：流水线是无状态的，每次都拿不到你本地的 state。

解决方案只有一个：把 state 搬到远程，所有人和流水线共用一份，再加分布式锁。

远程 state：S3 + DynamoDB 锁

AWS 生态最经典的组合是 S3 存 state 文件 + DynamoDB 做锁。S3 负责持久化和版本管理，DynamoDB 负责"同一时间只允许一个人 apply"。

先建 S3 bucket 和 DynamoDB 表（这俩可以也用 Terraform 建，但第一次得手动或用 bootstrap 配置）：

# 建 S3 bucket（开版本控制 + 加密）
aws s3api create-bucket --bucket my-tfstate-2026 \
  --region ap-southeast-1 \
  --create-bucket-configuration LocationConstraint=ap-southeast-1
aws s3api put-bucket-versioning --bucket my-tfstate-2026 \
  --versioning-configuration Status=Enabled

# 建 DynamoDB 锁表
aws dynamodb create-table \
  --table-name my-tf-locks \
  --attribute-definitions AttributeName=LockID,AttributeType=S \
  --key-schema AttributeName=LockID,KeyType=HASH \
  --billing-mode PAY_PER_REQUEST

然后在你的 Terraform 代码里配置 backend：

terraform {
  backend "s3" {
    bucket         = "my-tfstate-2026"
    key            = "dev/network/terraform.tfstate"
    region         = "ap-southeast-1"
    dynamodb_table = "my-tf-locks"
    encrypt        = true
  }
}

配完 terraform init，Terraform 会问你要不要把本地 state 迁到 S3。确认后，以后所有人 init 都从 S3 拉 state。

key 的设计
key 是 S3 里的文件路径，我按 环境/项目/ 分：dev/network/、prod/network/、dev/app/。不同环境用不同 key，state 互相隔离，一个环境炸了不影响另一个。别图省事全用一个 key。

远程 state：阿里云 OSS + TableStore

阿里云对应的组合是 OSS 存 state + TableStore（OTS）做锁。配置类似：

terraform {
  backend "oss" {
    bucket              = "my-tfstate-2026"
    key                 = "dev/ecs/terraform.tfstate"
    region              = "cn-shenzhen"
    tablestore_endpoint = "https://my-tf-lock.cn-shenzhen.ots.aliyuncs.com"
    tablestore_table     = "tf-locks"
    encrypt             = true
  }
}

注意阿里云 backend 用的是 oss 而不是 s3，锁表是 TableStore 不是 DynamoDB。功能对等，只是云厂商不同。我团队在国内业务跑阿里云就用这套。

组件AWS阿里云作用
state 存储S3 bucketOSS bucket持久化 state 文件，支持版本
锁服务DynamoDBTableStore分布式锁，防并发 apply
加密S3 SSEOSS 服务端加密state 落盘加密
版本历史S3 VersioningOSS 版本控制误删可回滚

锁机制怎么工作

多人协作的核心是同一时间只允许一个人操作 state。当你跑 terraform apply，Terraform 第一步是去 DynamoDB/TableStore 抢锁：

别人这时再跑 apply，会发现锁已存在，直接报错退出。这避免了两个人同时改 state 导致的冲突。但有个坑：如果你 apply 中途 Ctrl+C 或者机器断网，锁可能没释放。下次别人跑就一直被卡。

锁卡死了怎么办
我遇到过好几次 CI 跑一半超时，锁没释放，后面的流水线全卡在"Waiting for state lock"。手动释放：terraform force-unlock <lock-id>。lock-id 在报错信息里能找到。但force-unlock 之前先确认真的没人在跑，别把别人正在跑的 apply 强行打断了。

state 命令：日常运维工具集

远程 state 配好后，你会经常用到一组 terraform state 子命令来查看和修正 state：

命令干什么典型场景
terraform state list列出 state 里所有资源看当前管了哪些东西
terraform state show aws_instance.web看某个资源的详细属性排查为什么属性不对
terraform state pull把远程 state 下载到本地 stdout备份、审查
terraform state push把本地 state 推上去急救（谨慎）
terraform state rm aws_instance.web把资源从 state 里移除（不删云上资源）手动接管某资源、换 Terraform 管
terraform state mv把资源在 state 里改名/搬家重构 Module 后保持资源不重建

举个真实场景：你重构了 Module，把 aws_instance.web 挪进了一个子模块，路径变了。如果直接 apply，Terraform 会认为旧资源要删、新资源要建——EC2 一删一建，IP 变了、数据没了。正确做法是用 mv 在 state 里把"旧名字"映射到"新名字"：

# 重构前: aws_instance.web
# 重构后: module.app.aws_instance.web
terraform state mv aws_instance.web module.app.aws_instance.web

state 迁移：从本地搬到远程

如果你已经本地跑了一阵子，现在要搬 S3，步骤是：

  1. 先在代码里加好 backend "s3" {} 块。
  2. 跑 terraform init，Terraform 检测到 backend 变了，会问你要不要迁移。
  3. 选"yes"，它自动把本地 state 推到 S3。
  4. 验证：terraform state list 看资源还在不在。

跨云迁移（比如从 S3 搬到阿里云 OSS）麻烦一点，要先 terraform state pull 导出 JSON，改 backend 配置，再 terraform state push 上去。这种操作我建议先在测试环境演练一遍。

state 损坏了怎么救

state 文件可能因为各种原因损坏：磁盘故障、push 中断、手贱编辑。我经历过一次——同事 terraform state push 推了个半截文件上去，state JSON 不完整，所有命令直接报错。

好在 S3 开了版本控制，能救：

# 列出所有版本
aws s3api list-object-versions --bucket my-tfstate-2026 \
  --prefix dev/network/terraform.tfstate

# 找到正常版本的 VersionId，下载它
aws s3api get-object --bucket my-tfstate-2026 \
  --key dev/network/terraform.tfstate \
  --version-id <VERSION_ID> \
  terraform.tfstate

# 推回去
terraform state push terraform.tfstate

# 验证
terraform state list
我的保命习惯
每次大改动前，先 terraform state pull > backup-$(date +%F).tfstate 存一份。S3 版本控制是第二道防线。别嫌麻烦，state 丢一次你就知道疼了。

FAQ

Q：state 里真的有密码吗？
有。你用 aws_db_instance 设了 password 属性，state 里会明文存一份（虽然 apply 后敏感字段会被标记，但历史版本里可能有）。所以 S3 必须开加密、开版本控制、严格控制 bucket 访问权限。

Q：团队每个人都要能访问 S3 bucket 吗？
要。跑 terraform 的人（和 CI 机器的 IAM role）都要有该 bucket 的读写权限和 DynamoDB 锁表权限。用 IAM 策略精确控制，别给全账号 admin。

Q：force-unlock 安全吗？
危险操作。确认没人在跑了再用。我团队规矩是 force-unlock 必须群里喊一声，确认没人的流水线在跑。

Q：state 太大了怎么办？
一个 state 管太多资源会慢。按环境和项目拆分多个 state 文件是正路——第三篇讲环境隔离时会展开。

我的结论

state 管理是 Terraform 从"个人玩具"到"团队工具"的分水岭。核心就三句话：state 必须远程存、必须加锁、必须有版本历史。S3+DynamoDB（AWS）或 OSS+TableStore（阿里云）是标准答案，别自己发明轮子。

日常用好 state list/show/mv/rm 这几个命令，重构 Module 前先 mv 保平安，大改动前先 pull 备份一份。state 这关过了，你才算真正能在团队里用 Terraform 管生产环境。下一篇讲怎么用它编排一套真实的 VPC + ECS + RDS。
