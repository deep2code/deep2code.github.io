运维与云原生

Nginx · Docker · Harbor · 自托管 · 云平台 · Terraform · IaC

主线：一次变更如何安全到达生产

这一组文章横跨云平台、容器、Nginx、Kubernetes、CI/CD、可观测与基础设施即代码，看起来互不相干，但它们串在同一条线上：一次代码变更如何被安全地送到生产，并且在出问题时能退回来。整条线只有五个阶段，每个阶段都必须让某个性质成立，缺一个环节，风险就会被推到更晚、更贵的位置。

flowchart TB subgraph P1["构建：让结果可复现"] B1["同一提交只构建一次"] B2["依赖锁定与多阶段构建"] end subgraph P2["制品：让来源可追溯"] A1["镜像入私有仓库并按摘要引用"] A2["扫描漏洞与签名"] end subgraph P3["部署：让影响面可控"] D1["声明式清单与环境差异注入"] D2["灰度或蓝绿，按比例放量"] end subgraph P4["观测：让好坏可判断"] O1["错误率与延迟分位对比"] O2["发布门禁与自动暂停"] end subgraph P5["回滚：让代价可承受"] R1["回退到上一个已知良好摘要"] R2["配置与开关先回，代码再回"] end B1 --> B2 B2 --> A1 A1 --> A2 A2 --> D1 D1 --> D2 D2 --> O1 O1 --> O2 O2 --> R1 R1 --> R2 O2 -.-> D2
阶段必须成立的性质不成立时的后果可以检查的证据
构建可复现：同一提交构建出的制品内容一致，依赖版本被锁定测试环境好的版本到生产就崩，问题无法在本地复现两次构建的镜像摘要是否一致、依赖锁文件是否入库
制品可追溯：运行中的实例能反查到提交、构建记录与镜像摘要线上跑的是哪份代码要靠问人，安全漏洞无法定位影响范围部署清单里引用的是摘要还是浮动标签、镜像是否带构建元信息
部署影响面可控：能先影响一小部分流量，并能立刻停手一次错误变更等于全量事故，止损只能靠回滚全集群是否有分批或按比例放量、暂停机制是否可用
观测好坏可判断：发布后几分钟内能用指标而不是感觉判断问题在几小时后由用户报出来，损失已经发生是否有新旧版本分开的错误率与延迟分位对比
回滚代价可承受：路径事先演练过，不依赖临时手工操作知道要回滚但不敢回，只能带着故障向前修上一次演练时间、平均回滚耗时、数据变更是否向前兼容

这条主线上最贵的误解是把「有流水线」等同于「变更安全」。流水线只保证前两个阶段，后三个阶段是运维体系的真正内容：放量策略、判断依据、退路。

环境、配置与密钥的边界

划边界的判据只有两条：变更频率和敏感程度。跟着代码走、各环境一致的东西进镜像；各环境不同但不敏感的进配置；敏感凭证进密钥管理。放错位置的代价不是麻烦，而是让制品失去可比性。

内容放在哪里怎么变更放错位置的后果
依赖与运行时版本镜像（多阶段构建，产物层与构建层分开）改代码并重新构建，走完整流水线放到启动时安装，会让部署依赖外网且每次结果都不同
下游地址、超时、开关默认值配置对象，按环境注入改配置并重启或热加载，可单独回滚打进镜像，于是每个环境单独构建，制品不可比，问题无法复现
数据库口令、访问令牌、私钥密钥管理，挂载为文件或注入为环境变量轮转加重新下发，全程审计写进代码仓库或镜像层，历史提交里永久留痕，泄露后无法撤回
限流阈值、降级开关、灰度名单运行时开关，进程内可热更新改开关即生效，无需发布做成必须重启的静态配置，故障时止损速度慢一个数量级
副本数、资源限额、探针参数声明式部署清单，纳入版本控制改清单并走审核，效果可对比线上手工改动，与代码仓库产生漂移，下一次部署被悄悄覆盖

可观测性三支柱与它们的成本

三类信号回答的问题不同，成本结构也完全不同。不区分成本结构地「全都接上」，账单会在三个月后变成技术债。

信号回答什么问题成本由什么驱动控制成本的手段最常见的误用
指标现在正常吗、趋势如何、要不要扩容活跃时间序列数量，等于各标签取值的组合数标签只放低基数维度，热存储周期分级，聚合后再长期保存把用户标识、请求标识、完整 URL 放进标签，序列数爆炸并拖垮查询
日志这一次具体发生了什么写入量与索引量结构化输出、按级别采样、热冷分层、只对需要检索的字段建索引把日志当指标用，靠全量文本统计做告警，既慢又贵
链路追踪这次慢在哪一跳、依赖拓扑是什么样上报的跨度数量尾部采样保住出错与慢请求的完整链路，常态请求低比例采样只在入口埋点，跨服务上下文没传下去，链路断成孤立片段

另有一条实践判据：告警应该绑在用户可感知的症状上，而不是绑在中间指标上。处理器使用率高本身不是故障，请求失败率和延迟超标才是。指标告警太多、噪声比过高，最终结果是没人看告警。

变更风险分级与对应的灰度手段

不是所有变更都值得同一套流程。用「能不能回滚」和「影响面有多大」两个维度分级，再决定允许的发布方式，能把审批成本花在真正危险的地方。

风险级别典型特征合适的发布方式必须事先准备的退路
低无状态服务的代码或配置变更，回滚即恢复金丝雀，按比例放量，指标异常自动暂停上一个已知良好的镜像摘要保持可用
中需要多个服务协同生效，接口有新增字段功能开关：先部署、后启用、按服务打开开关可在不发布的前提下关闭，且关闭后旧路径仍完整
高数据结构或数据内容变更，写坏无法逆转多步向前兼容：加字段、双写、校验一致、再切读、最后清理每一步都能单独停下；有数据校验脚本与备份恢复演练记录
高网络策略、权限模型、证书与域名变更低峰窗口逐台执行，先在小范围验证连通性旧配置可一条命令恢复；准备好带外访问通道，避免把自己锁在外面

容量、弹性与故障处理的分工

容量这件事上，运维和后端的分歧通常来自一个误会：限额不是性能上限，而是调度和隔离的输入。容器上设了处理器限额后，配额在周期内用完就会被限流，表现是规律性的尾延迟毛刺，而平均使用率看着并不高。所以限额必须和进程内的并行度设置对齐：按限额设置运行时的并行线程数或工作进程数，而不是按宿主机核数。

弹性的现实约束是时间。指标采集窗口、扩容冷却、调度与拉镜像、进程预热加起来往往几十秒到几分钟，流量爬升常常比它更快。因此自动扩容只能是补充手段，真正的保护来自预留缓冲、按日历提前扩容，以及入口限流与排队。另外指标要选对：等待型服务按处理器使用率扩容基本不会触发，应该按并发数、队列积压或每秒请求数来扩。

故障处理上，最有效的两条纪律很朴素：先止损再定位——回滚、摘流量、限流、关开关，这四招都不需要知道根因；角色分开——有人负责决策与对外沟通，有人负责动手操作，避免同一个人一边被追问一边敲命令。演练的价值也不在于验证方案文档存在，而在于测出回滚到底要几分钟、以及谁手上缺权限。

这个专题各子方向怎么读

三条常见路线：从零搭一套交付链路，按容器、镜像仓库、编排、流水线、可观测的顺序读；只想解决入口层问题，直接进 Nginx 系列；要治理已有环境的漂移，从基础设施即代码与 GitOps 入手。下表给每个子方向一句「什么时候该读它」。

子方向它解决的问题什么时候该读它
Docker容器隔离原理、镜像分层与多阶段构建镜像太大、构建太慢，或需要搞清容器与宿主机的资源关系时
Harbor私有镜像仓库、权限与漏洞扫描制品需要留存、审计与扫描，不能再依赖公共仓库时
Kubernetes声明式编排、调度、探针与资源模型服务开始需要自动重启、滚动发布与水平扩容时
CI/CD流水线编排、制品流转与门禁发布还依赖手工步骤、或同一提交在不同环境构建结果不一致时
GitOps用版本库作为期望状态的唯一来源线上手工改动频繁、环境与仓库已经漂移时
Nginx 系列反向代理、超时与缓冲、限流、灰度与流媒体入口层出现超时、长连接、压缩缓冲或灰度路由问题时
Nginx 高级玩法灰度发布、访问控制与常见防护配置需要在入口层做按比例放量或临时止损时

Web 安全常见攻击面与防护落点做安全评审、或需要确认入口层与应用层各自该防什么时
基础设施即代码用代码描述云资源，管理状态与漂移云资源靠控制台点出来、没人说得清现状时
阿里云 与 腾讯云具体云平台的产品选择与踩坑要在某家云上落地方案、需要知道哪些默认值会坑人时
自托管自建代码仓库、制品与协作服务数据必须留在自己机房、或要评估自建与托管的总成本时
❌
这条主线上最容易踩的坑
  • 部署清单引用浮动标签而不是镜像摘要，同一份清单在不同时间部署出不同版本
  • 各环境分别构建镜像，于是测试通过的制品和生产运行的制品根本不是同一个
  • 存活探针里做了数据库查询，数据库一抖导致整个集群滚动重启并放大故障
  • 就绪探针和优雅退出没配好，滚动发布期间出现连接被重置的瞬时错误
  • 处理器限额和进程内并行度不匹配，被周期性限流打出规律的尾延迟毛刺
  • 指标标签里放了用户标识或请求标识，时间序列数量爆炸，账单和查询一起变差
  • 告警绑在中间指标上，噪声比过高，真正的故障告警被淹没
  • 数据库变更和代码变更同一批上线，代码能回滚但数据回不去
  • 只演练过「能否发布」，从没测过「回滚要几分钟、谁有权限」
  • 把自动扩容当作唯一的容量保障，忽略扩容链路本身有分钟级延迟
  • 基础设施状态文件和线上手工改动长期漂移，下一次执行时把人工修复悄悄覆盖
