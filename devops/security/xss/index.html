XSS 防御：上下文输出编码、DOM Sink 清单与 CSP 实战

🏷️ XSS

XSS 的中文名叫「跨站脚本攻击」，这个名字把人带偏了二十年。它的本质跟「跨站」关系不大，真正的机制是：一段数据被放进了某个解析器的输入流，解析器把它当成了代码而不是数据。HTML 解析器、JS 解析器、URL 解析器、CSS 解析器，四种解析器的逃逸字符完全不同，这就是为什么 XSS 修不干净——大部分团队只处理了 HTML 解析器这一种情况。

一、根因：不是「没过滤 script」，而是解析上下文错配

先纠正一个流传极广的说法：「XSS 就是没过滤 script 标签」。线上真正被打穿的案例里，带 script 字样的 payload 占比很低，因为任何 WAF 和黑名单都会拦它。真正好用的 payload 是这些：

payload用到的机制为什么黑名单拦不住
<img src=x onerror=alert(1)>图片加载失败触发事件属性没有 script 字样，img 标签又不能禁
<svg onload=alert(1)>SVG 根元素的 load 事件富文本场景常常允许 svg
<details open ontoggle=alert(1)>HTML5 新增事件属性黑名单写于 2015 年，没收录这个属性
" autofocus onfocus=alert(1) x="属性值逃逸，不需要任何新标签输出点在属性里，没有尖括号也能打
javascript:alert(1)URL 上下文的伪协议字符串本身完全合法，只是位置不对
';alert(1);//内联 JS 字符串闭合HTML 实体编码对它毫无作用

看最后两行：javascript:alert(1) 里一个特殊字符都没有；';alert(1);// 做完 HTML 实体编码之后在 JS 上下文里照样生效。所以决定安全与否的不是字符串内容，而是它被插到了哪里。同一个字符串放进 <div> 是无害文本，放进 href 就是可执行代码。

💡
一句话判断有没有 XSS 风险

拿着任意一段用户可控数据问自己：它最终进入了哪个解析器？如果进入 HTML 解析器，它能不能提前结束当前标签或属性？如果进入 JS 解析器，它能不能提前闭合字符串？答案是能，就有 XSS。「我这里过滤了危险词」不构成答案，因为过滤的是字符，逃逸靠的是语法位置。

二、三种类型的攻击链路差异

存储型、反射型、DOM 型的划分不是为了考试，它决定了三件非常实际的事：影响面有多大、日志里能不能查到、修复要改前端还是后端。

存储型最值得警惕的不是「危害大」，而是它的写入点和渲染点通常不是同一个人写的。后端同学存了一个昵称字段，觉得这只是一段文本；三个月后有人做了个运营后台，用 innerHTML 把昵称渲染到列表里——漏洞在这一刻才成立，而单独看两边代码都没问题。这也是为什么安全责任必须落在输出点：只有输出点知道自己处在什么上下文。

⚠️
反射型不等于「只在查询串里」

很多人以为反射型只能用 GET 链接打，于是把接口改成 POST 就觉得安全了。实际上攻击者可以在自己页面上放一个自动提交的表单完成 POST 反射，配合 CSRF 一起用。另外「只有查询参数需要检查」也是错的：请求头同样会被回显，把 Referer、User-Agent、自定义租户头打进错误页或监控面板，都是真实出现过的反射型入口。

三、为什么「输入时统一过滤」是错的做法

最常见的架构级错误是在网关或者 Filter 里加一层「全局 XSS 过滤」，把所有请求参数里的尖括号、引号、关键字统一替换掉，然后宣布全站免疫。这个方案有四个硬伤：

问题具体表现后果
出口数量远多于入口同一条昵称要输出到 HTML、JSON、CSV、短信、PDF、日志入口做的那一种编码，在其他出口全是错的
破坏合法数据用户名 O'Neil 被吃掉引号，技术文章里的小于号被删数据永久损坏且不可逆，客服工单不断
覆盖不到非 HTTP 入口MQ 消息、批量导入、第三方回调、直接刷库存储型 payload 从侧门进来，过滤层看不见
制造虚假安全感新同学看到有全局过滤，渲染时不再做编码过滤层一旦被绕过，全站同时裸奔
❌
编码是输出侧的责任，不是入口的责任

入口只做业务校验：长度上限、格式正则、枚举白名单、类型转换，校验不通过就整体拒绝，而不是偷偷改数据。数据库里应该存用户真正输入的原文，因为你不知道它下一次会被渲染到哪里。编码动作放在每一个输出点，由那个位置的上下文决定用哪个函数。这条规则的额外好处是：以后新增任何渲染出口，作者都必须显式选一种编码方式，漏了在 Code Review 里一眼能看出来。

四、五种输出上下文与各自的编码方式

这是整篇文章最核心的一张表，也是实际工程中最常做错的地方。五种上下文需要五种完全不同的编码，互相不能替代。

输出上下文示例位置必须处理的内容正确做法典型逃逸 payload常见错误
HTML 文本节点<div>这里</div>& < > " 'HTML 实体编码，五个字符全转<img src=x onerror=alert(1)>只转尖括号，漏掉引号
HTML 属性值<input value="这里">实体五字符 + 引号包裹实体编码后用双引号包住属性值1 autofocus onfocus=alert(1)属性值不加引号，一个空格即可逃逸
URL 上下文<a href="这里">协议名 + 参数分隔符协议白名单 + 参数百分号编码javascript:alert(1)以为做了实体编码就够了
内联 JS 字符串<script>var s='这里'</script>' " \ 换行、</script用 JSON 序列化整个值，不手写拼接';alert(1);// 或 </script>用 HTML 实体编码处理 JS 字符串
CSS 值<div style="width:这里">( ) " ' ; { } \只允许数字与枚举值，不拼字符串expression(alert(1))、url(javascript:...)让用户控制整段 style

三个必须记住的边界条件：

1. HTML 实体编码在 URL 上下文里无效。浏览器的解析顺序是先做 HTML 实体解码、再交给 URL 解析器，所以把 javascript 后面的冒号写成 &#58; 放进 href，实体解码后协议名恢复完整，点击照样执行；协议名中间还能插 Tab、换行、回车来对抗关键字匹配。URL 上下文唯一可靠的做法是解析后做协议白名单：只放行 http、https，或只放行以单个斜杠开头的站内路径。

2. HTML 实体编码在 JS 上下文里同样无效。<script> 内部是 raw text 区域，HTML 解析器不做实体解码，&#39; 传到 JS 引擎里就是六个普通字符不会闭合字符串；反过来真正的单引号却能闭合。而在 JS 里唯一必须处理的 HTML 序列是 </script——它会提前结束脚本块。所以内联数据的正确姿势是 JSON.stringify 再额外转义尖括号。

3. 编码不能叠加两次，也不能只做一次走遍全场。先实体编码再 URL 编码，正常链接会变成乱码；先 URL 编码再实体编码，属性里的百分号被再编码一遍，跳转直接 404。这类「双重编码」bug 在老项目里非常常见，通常就是入口过滤和出口编码各做了一次。

Go 的 html/template 是少数把上下文感知做对的模板引擎，值得当成标准答案看一遍：

package main

import (
    "encoding/json"
    "html/template" // 关键：不要用 text/template，后者完全不做转义
    "net/http"
    "net/url"
    "strings"
)

// html/template 会先解析模板、判断每个插值点所处的上下文，
// 再自动挑选 htmlEscaper / attrEscaper / urlFilter / jsValEscaper。
// 同一个 .Name 在下面四个位置的转义结果是完全不同的。
var page = template.Must(template.New("p").Parse(`
<div>{{.Name}}</div>
<input value="{{.Name}}">
<a href="{{.Link}}">跳转</a>
<script>var profile = {{.Profile}};</script>
`))

// 1) 文本节点：尖括号转成实体，浏览器当文字显示
// 2) 属性值：额外转义引号，无法逃出 value=".."
// 3) href：非 http/https/mailto 等安全协议会被整体替换成 #ZgotmplZ
//    页面上看到 #ZgotmplZ 不是 bug，而是拦截生效了
// 4) script 内：.Profile 序列化成 JSON 字面量并自动加引号，
//    同时把 < 以及 U+2028 U+2029 这些能破坏脚本的字符一起处理掉

// 反例：这三种写法让上面所有保护全部失效
func bad(w http.ResponseWriter, name string) {
    // 失效一：手写字符串拼接，绕过模板引擎
    w.Write([]byte("<div>" + name + "</div>"))

    // 失效二：template.HTML 的语义是「我保证这段已经安全」，
    // 把用户输入强转成它，等于亲手关掉转义
    _ = template.HTML(name)

    // 失效三：用 text/template 渲染 HTML，一个字符都不会转义
}

// URL 上下文的协议白名单：代码自己拼出来的 URL 模板引擎兜不住
func safeURL(raw string) string {
    u, err := url.Parse(strings.TrimSpace(raw))
    if err != nil {
        return ""
    }
    switch strings.ToLower(u.Scheme) {
    case "http", "https":
        return u.String()
    case "": // 相对路径：必须排除 //evil.com 这种协议相对写法
        if strings.HasPrefix(raw, "/") && !strings.HasPrefix(raw, "//") {
            return raw
        }
    }
    return "" // javascript:、data:、vbscript: 全部丢弃
}

// 内联 JSON 数据：比字符串拼接更稳的是放进 data 属性由 JS 读取
func embedJSON(v any) (string, error) {
    b, err := json.Marshal(v)
    if err != nil {
        return "", err
    }
    // 即使在 script 标签内，也要处理这三个字符，避免提前闭合脚本块
    return strings.NewReplacer(
        "<", `\u003c`, ">", `\u003e`, "&", `\u0026`,
    ).Replace(string(b)), nil
}

⚠️
「innerHTML 里的 script 不执行，所以 innerHTML 安全」是彻底错的

规范确实规定通过 innerHTML 插入的 script 元素不会执行，但这只堵了一条路：<img src=x onerror=...>、<svg onload=...>、<iframe srcdoc=...>、<body onpageshow=...> 全部照常触发，HTML5 的事件属性有上百个。另外 jQuery 的 .html() 和 .append() 为了兼容性会主动把其中的脚本抽出来执行，比原生 innerHTML 更危险。结论：innerHTML 只应该接收常量模板或 DOMPurify 的输出。

六、CSP：只有 nonce 加 strict-dynamic 才算真加固

CSP 的定位要摆正：它不修漏洞，它是编码漏了一处时让漏洞无法利用的第二道网。把 CSP 当主防线的团队，最后通常配出一条毫无作用的策略。落地路径应该是这样：

stateDiagram-v2 state "无 CSP" as S0 state "Report-Only 观察期" as S1 state "清理内联脚本与事件属性" as S2 state "nonce 强制模式" as S3 state "nonce 加 strict-dynamic" as S4 state "加了 unsafe-inline 的假加固" as BAD [*] --> S0 S0 --> S1: 先下发 Report-Only 只上报不拦截 S1 --> S2: 按上报清单逐个改造 S2 --> S3: 内联改外链或补 nonce 属性 S3 --> S4: 动态插入的脚本靠信任传递放行 S4 --> [*]: 强制模式稳定运行 S3 --> S2: 发现漏改的内联脚本回退修复 S1 --> BAD: 为了让控制台不报错抄了一条宽松策略 BAD --> [*]: 防 XSS 能力基本归零
指令或关键字作用推荐值配错的后果
default-src未显式声明的资源类型的兜底'self'不设则未覆盖的类型完全不受限
script-src脚本来源白名单，防 XSS 的主力'nonce-xxx' 'strict-dynamic'用域名白名单时，白名单里的 JSONP 接口即可绕过
'unsafe-inline'放行内联脚本与事件属性不要用直接让 CSP 对 XSS 失效
'unsafe-eval'放行 eval 与字符串 setTimeout不要用eval 类 sink 与模板注入重新可用
'nonce-随机值'只放行带匹配 nonce 属性的脚本每次响应重新生成，至少 128 位nonce 固定或可预测等于没有；HTML 被缓存会泄露 nonce
'strict-dynamic'已受信脚本动态创建的脚本自动受信与 nonce 同时使用不加则第三方 SDK 动态插脚本全挂
object-src限制 object embed applet'none'插件类元素历史上是稳定绕过点
base-uri限制 base 标签改写相对路径基准'none'注入 base 可劫持所有相对路径脚本
frame-ancestors谁能把本页嵌进 iframe'none' 或指定域点击劫持；它已取代 X-Frame-Options
require-trusted-types-for从机制上禁止字符串直接进 sink'script'不配则 DOM 型仍需靠人工审计
report-uri / report-to违规上报必配，灰度期尤其重要没有上报就不知道策略是否拦错业务

nonce 必须每次响应重新生成，所以它天生和「HTML 被 CDN 缓存」冲突：如果页面 HTML 走了共享缓存，要么给 HTML 设 no-store，要么改用 hash 模式列出所有内联脚本的 sha256。下面是可直接抄走的 Go 中间件：

package main

import (
    "context"
    "crypto/rand"
    "encoding/base64"
    "fmt"
    "html/template"
    "net/http"
)

type nonceKey struct{}

// 每个响应生成一个一次性 nonce：16 字节即 128 位，符合 CSP 规范建议
func nonceMiddleware(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        b := make([]byte, 16)
        if _, err := rand.Read(b); err != nil { // 必须 crypto/rand，math/rand 可预测
            http.Error(w, "internal error", http.StatusInternalServerError)
            return
        }
        nonce := base64.RawStdEncoding.EncodeToString(b)

        // strict-dynamic 的作用：放弃域名白名单，改成「信任传递」——
        // 带对 nonce 的脚本用 createElement 动态插入的脚本也自动受信，
        // 既兼容第三方 SDK，又不会因为白名单域上有 JSONP 接口而被绕过。
        // 末尾的 https: 与 unsafe-inline 是给不支持 strict-dynamic / nonce
        // 的老浏览器的降级，现代浏览器会忽略它们。
        csp := fmt.Sprintf(
            "default-src 'self'; "+
                "script-src 'nonce-%s' 'strict-dynamic' https: 'unsafe-inline'; "+
                "style-src 'self' 'unsafe-inline'; "+ // 样式内联风险远低于脚本，可先放行
                "img-src 'self' data: https:; "+
                "connect-src 'self' https://api.example.com; "+
                "object-src 'none'; base-uri 'none'; frame-ancestors 'none'; "+
                "require-trusted-types-for 'script'; "+
                "report-uri /csp-report", nonce)

        // 灰度期换成 Content-Security-Policy-Report-Only，只上报不拦截；
        // 观察一到两周、违规清零后再切成下面这个强制头
        w.Header().Set("Content-Security-Policy", csp)

        // HTML 里含一次性 nonce，绝不能进共享缓存
        w.Header().Set("Cache-Control", "no-store")

        ctx := context.WithValue(r.Context(), nonceKey{}, nonce)
        next.ServeHTTP(w, r.WithContext(ctx))
    })
}

// 模板里每个内联 script 都要带上同一个 nonce
var tpl = template.Must(template.New("i").Parse(
    `<script nonce="{{.Nonce}}">window.__BOOT__ = {{.Boot}};</script>`))

func index(w http.ResponseWriter, r *http.Request) {
    nonce, _ := r.Context().Value(nonceKey{}).(string)
    _ = tpl.Execute(w, map[string]any{
        "Nonce": nonce,
        "Boot":  map[string]string{"env": "prod"},
    })
}

七、富文本：必须白名单，不能黑名单

需要保留用户 HTML 的场景（编辑器、邮件正文、商品详情）没法靠编码，只能清洗。这里只有一条铁律：用成熟的白名单库，不要自己写正则。自己写的黑名单会被这些手法逐一击穿：大小写混写、用斜杠代替空格、属性值里插 Tab 和换行、嵌套标签让正则替换一次后反而拼出新标签、十进制与十六进制实体混写、畸形标签靠浏览器容错自动修复。

import DOMPurify from 'dompurify';

// 白名单配置的原则：从空集开始逐项添加，而不是从全集开始逐项删除
const PROFILE = {
  ALLOWED_TAGS: [
    'p', 'br', 'strong', 'em', 'u', 's', 'blockquote',
    'ul', 'ol', 'li', 'h2', 'h3', 'h4',
    'a', 'img', 'code', 'pre', 'table', 'thead', 'tbody', 'tr', 'th', 'td',
  ],
  ALLOWED_ATTR: ['href', 'title', 'src', 'alt', 'width', 'height', 'colspan', 'rowspan'],

  // 只放行安全协议：data: 也能承载 HTML，必须显式收紧
  ALLOWED_URI_REGEXP: /^(?:https?:|mailto:|\/(?!\/))/i,

  // 关键：禁止用户注入 id 与 name，否则可通过 DOM clobbering 覆盖全局变量，
  // 让业务代码里的 window.config 之类引用指向攻击者控制的元素
  FORBID_ATTR: ['id', 'name', 'style', 'srcdoc', 'formaction', 'ping'],
  FORBID_TAGS: ['style', 'form', 'input', 'button', 'iframe', 'object', 'embed', 'template'],

  // 不开 MathML 与 SVG：命名空间混淆是历史上反复出现的绕过面
  USE_PROFILES: { html: true },
  ALLOW_DATA_ATTR: false,
  RETURN_TRUSTED_TYPE: true, // 与 require-trusted-types-for 'script' 配合
};

// 额外加固：所有外链强制 rel，避免 tabnabbing
DOMPurify.addHook('afterSanitizeAttributes', (node) => {
  if (node.tagName === 'A' && node.hasAttribute('href')) {
    node.setAttribute('target', '_blank');
    node.setAttribute('rel', 'noopener noreferrer nofollow');
  }
});

export function renderRichText(el, dirtyHtml) {
  el.innerHTML = DOMPurify.sanitize(dirtyHtml, PROFILE);
  // 清洗后读一次 DOMPurify.removed 并打点上报，
  // 被删内容量突然暴涨通常意味着有人在批量试 payload
}
✅
清洗放在输出侧，而且前后端共用同一份配置

很多团队只在编辑器保存时清洗一次（输入侧），这有两个问题：历史脏数据不会被处理；DOMPurify 升级修掉的绕过对已入库内容无效。更稳的做法是入库存原文、渲染时清洗，升级库即等于修复历史数据。需要服务端渲染时，Node 侧用 DOMPurify(new JSDOM('').window) 复用同一份 PROFILE，Java 侧可用 OWASP Java HTML Sanitizer，但要保证两侧白名单一致，否则会出现「前端能显示、后端被过滤」的诡异 bug。

// 1. href 直接吃用户数据：javascript 伪协议照样执行，React 只在控制台警告

// 3. 属性展开：userProps 里若含 onClick / onMouseOver 就直接成了事件绑定

// 4. style 吃字符串：可注入 url 以及读取页面数据的 CSS 变量

const SAFE_SCHEME = /^https?:$/i;

// 协议白名单：要处理前后空白、大小写，以及 //evil.com 这种协议相对 URL
export function safeHref(raw) {
  if (typeof raw !== 'string') return undefined;
  const v = raw.trim();
  if (v.startsWith('//')) return undefined;             // 协议相对，会跳到外站
  if (v.startsWith('/') || v.startsWith('#')) return v; // 站内路径与锚点
  try {
    const u = new URL(v);                               // 没有协议会抛错，正好拦掉畸形输入
    return SAFE_SCHEME.test(u.protocol) ? u.href : undefined;
  } catch {
    return undefined;                                   // javascript: data: vbscript: 一律丢弃
  }
}

// href 为 undefined 时 React 不渲染该属性，标签退化成不可点击文本，是安全降级
<a href={safeHref(item.website)} target="_blank" rel="noopener noreferrer nofollow">
  {item.name}
</a>

// 富文本：清洗后再交给框架
<div dangerouslySetInnerHTML={{ __html: DOMPurify.sanitize(post.contentHtml, PROFILE) }} />

// 数值型样式：只接受数字，单位由代码自己拼
<div style={{ width: `${Number(user.width) || 0}px` }} />

❌
上线前的避坑清单
  • 别在入口做全局过滤：入口只做业务校验，数据库存原文，编码放在每个输出点按上下文做。
  • 别用一个 escapeHtml 走遍全场：它在 href 与 script 内部都无效，URL 要协议白名单，JS 要 JSON 序列化。
  • 别相信「innerHTML 里的 script 不执行」：事件属性、svg onload、iframe srcdoc 全都能触发，jQuery 的 .html() 还会主动执行脚本。
  • 别自己写正则清洗富文本：大小写变形、斜杠代空格、实体混写、嵌套标签重组，任何一条都能绕过，上 DOMPurify 或 OWASP Sanitizer。
  • 别在 CSP 里留 unsafe-inline：它正好取消了 CSP 拦 XSS 的唯一机制；nonce 要 crypto 随机、每响应一次，并给 HTML 设 no-store。
  • 别把 HttpOnly 当成防 XSS：它只防偷 Cookie，不防脚本用你的身份调接口，敏感操作必须二次验证。
  • 别忘了非 HTML 出口：CSV 导出的公式注入、Markdown 渲染器、邮件模板、移动端 WebView 的 loadUrl，都是同一类问题的不同外壳。
