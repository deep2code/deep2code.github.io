认证授权安全

🏷️ Web安全,网络安全,安全实践

认证与授权：现代 Web 的门面，也是最常被拆错的门

认证（Authentication，你是谁）与授权（Authorization，你能做什么）是两个被反复混淆的概念：登录是认证，"这个用户能不能删这篇文章"是授权。

过去十年，业界从 Session-Cookie 演进到 JWT、从平台账号演进到 OAuth 2.0 第三方登录、再到 OIDC 把身份层补回来，每一步都是在解决上一代方案的真实事故。但事故并没有消失——2023 年某大厂 OAuth 实现缺陷导致任意账号接管、2024 年某 JWT 库 alg=none 绕过 CVE，本质都是把协议当黑盒用，没理解每个字段的安全含义。

本篇不讲 RFC 全文，只讲工程师在设计登录、接入第三方登录、签发令牌时必须知道的陷阱与正确姿势。

JWT：结构、签名与三大陷阱

JWT（JSON Web Token）由三段 Base64URL 组成：Header.Payload.Signature。它的核心承诺是签名——服务端用私钥签、用公钥验，任何篡改都会验签失败。但 JWT 有三个著名陷阱：

GET /orders Authorization: Bearer ＜jwt＞ API->>API: 4. 验证签名 + 过期时间 + iss/aud alt 验签通过 API-->>C: 5. 200 业务数据 else 验签失败/过期 API-->>C: 401 C->>AS: 6. 用 refresh_token 换新 access_token end 
// 一个标准 JWT 解码后长这样（Payload 只是 Base64，不是加密！）
// Header:  {"alg": "RS256", "typ": "JWT"}
// Payload: {"sub": "10086", "name": "junjun", "role": "admin",
//           "iat": 1726512000, "exp": 1726515600,
//           "iss": "https://sso.example.com", "aud": "api.example.com"}
// ⚠️ Payload 任何人都能 Base64 解码，不要放密码、身份证等敏感信息

三大陷阱：

  1. alg=none 绕过：老库允许客户端把 alg 改成 none 并去掉签名，服务端就直接信任。修法：服务端写死接受的算法列表，绝不读 Header 里的 alg。
  2. 把 RS256 改成 HS256 用公钥当密钥：攻击者拿到 JWKS 里的公钥后，用公钥做 HMAC 密钥自签 Token。修法：签名算法与密钥类型绑定校验。
  3. 不过期、不校验 iss/aud：Token 一旦泄露永久有效。修法：access_token 短期（5~15 分钟）+ refresh_token 长期并可吊销。
// Go 正确的 JWT 校验：白名单算法 + 校验 iss/aud/exp
import "github.com/golang-jwt/jwt/v5"

var keyfunc = func(t *jwt.Token) (interface{}, error) {
    // ✅ 显式校验 alg，拒绝 none 和意外算法
    if _, ok := t.Method.(*jwt.SigningMethodRSA); !ok {
        return nil, fmt.Errorf("unexpected signing method: %v", t.Header["alg"])
    }
    return publicKey, nil
}

func parseToken(tokenString string) (*Claims, error) {
    claims := &Claims{}
    tok, err := jwt.ParseWithClaims(tokenString, claims, keyfunc,
        jwt.WithIssuer("https://sso.example.com"),       // ✅ 校验 iss
        jwt.WithAudience("api.example.com"),             // ✅ 校验 aud
        jwt.WithLeeway(30*time.Second),                  // 时钟偏移容忍
    )
    if err != nil || !tok.Valid {
        return nil, err
    }
    return claims, nil
}

OAuth 2.0 与 OIDC：别把 OAuth 当登录用

OAuth 2.0 解决的是授权（"第三方 App 能访问你 GitHub 的公开仓库"），它本身不负责认证。OIDC 在 OAuth 之上加了一层 id_token（一份带签名的身份声明），这才是"用 GitHub 账号登录"的标准协议。国内大量"微信扫码登录"本质是 OIDC 的变种。

flowchart LR subgraph 授权码流程[Authorization Code + PKCE（推荐）] A[用户] --> |1. 点击'用 GitHub 登录'| B[你的 App] B -->|2. 跳转 GitHub /authorize?code_challenge=...| GH[GitHub] GH -->|3. 用户同意| B B -->|4. 拿 code + code_verifier 换 token| GH GH -->|5. 返回 access_token + id_token| B B -->|6. 验 id_token 签名| USER[建立本地会话] end

四种授权模式的选型：

  • 授权码 + PKCE：Web、移动端、SPA 全部用它，2026 年的唯一推荐。
  • 隐式（Implicit）：已废弃，不要用。
  • 密码模式（Resource Owner Password Credentials）：仅用于你自己的第一方 App。
  • 客户端凭证（Client Credentials）：服务对服务（M2M），不涉及用户。

我踩过的坑：JWT 放 localStorage 被 XSS 偷了

2022 年我们做了个 SPA，JWT 存在 localStorage 里。有次评论区没过滤干净，攻击者注入了一段 JS，把所有在线用户的 JWT 全外带了。事后我们做了三件事：① JWT 改放 HttpOnly Cookie；② 上了 CSP 头；③ access_token 从 7 天缩到 15 分钟。localStorage 里放 JWT 等于在门口放钥匙，别图省事。

# FastAPI 接入 OIDC：校验 id_token 而不是只看 access_token
from fastapi import Depends, HTTPException
import jwt

JWKS = fetch_jwks("https://sso.example.com/.well-known/jwks.json")

async def require_login(authorization: str = Header(None)):
    if not authorization or not authorization.startswith("Bearer "):
        raise HTTPException(401)
    token = authorization[7:]
    try:
        # ✅ 验签 + iss/aud/exp 全套校验
        claims = jwt.decode(token, JWKS,
                            algorithms=["RS256"],
                            issuer="https://sso.example.com",
                            audience="api.example.com")
    except jwt.PyJWTError as e:
        raise HTTPException(401, str(e))
    return claims["sub"]   # user_id

会话与密码：最容易被忽视的基础

// 密码哈希：用 bcrypt/argon2，永远不要 MD5/SHA1/SHA256
import "golang.org/x/crypto/bcrypt"

func hashPassword(raw string) (string, error) {
    // ✅ cost=12 是 2026 年的合理基线（约 250ms 一次）
    b, err := bcrypt.GenerateFromPassword([]byte(raw), 12)
    return string(b), err
}

func verifyPassword(hash, raw string) bool {
    return bcrypt.CompareHashAndPassword([]byte(hash), []byte(raw)) == nil
}

最佳实践

  • JWT 放 HttpOnly; Secure; SameSite=Lax 的 Cookie，不要放 localStorage（XSS 一偷一个准）。
  • access_token 短命（5~15 分钟），refresh_token 存服务端可吊销，轮换时一次性。
  • OAuth 接入一律用 Authorization Code + PKCE；state 参数必须随机且绑定会话。
  • 密码用 argon2id / bcrypt，cost 每年上调；禁止自己发明哈希算法。
  • 登录、改密、绑邮箱、解绑 MFA 这些关键动作必须二次确认（重新输密码或 MFA）。
  • 授权设计：默认拒绝（Deny by Default），每个接口都做 ownership 检查（呼应 A01）。
  • 管理后台单独 SSO、独立域、独立 MFA 强制，不要和普通用户共用登录态。

常见问题 FAQ

Q1：JWT 存在 localStorage 还是 HttpOnly Cookie？

优先 HttpOnly Cookie。localStorage 任何 XSS 都能读走，Cookie 配 HttpOnly 后 JS 读不到，XSS 最多发请求拿不到令牌本身。当然最佳是 XSS 本身被 CSP 挡住，但纵深防御永远不嫌多。

Q2：JWT 无状态，怎么实现"登出即失效"？

短 access_token（5 分钟）+ 服务端维护一个吊销列表（Redis 存已登出的 jti 直到 exp），登出时把 jti 写进去。牺牲一点无状态性，换可控的实时失效。

Q3：OAuth 2.0 不能做登录吗？为什么还要 OIDC？

OAuth 2.0 的 access_token 是"给资源服务器用的令牌"，不是"用户身份"。早期很多团队直接用 access_token 当登录凭证，导致 token 泄漏后身份被盗。OIDC 增加了 id_token（一份标准化、带签名的身份声明），并规定了 userinfo 端点，登录这件事才有了标准协议。

Q4：密码 BCrypt 这么慢，会不会被暴力破解反而更容易？

慢是故意的。bcrypt/argon2 设计就是"正常用户登录花 200ms 无所谓，但攻击者跑字典要花几万年"。MD5 一秒能算几十亿次，bcrypt 一秒只能算几次，这就是设计目的。

总结

认证授权的安全，一半在协议选对（OIDC + PKCE），一半在细节做对（算法白名单、短期令牌、HttpOnly Cookie、密码慢哈希、按请求做授权检查）。下一篇是本系列最后一篇：把视线从应用层拉到传输层，看 HTTPS、TLS 握手、HSTS、CSP 这些"协议级护栏"如何兜底，以及一份可直接上线的 nginx 安全基线长什么样。
