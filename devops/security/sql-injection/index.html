SQL 注入防护

🏷️ Web安全,网络安全,安全实践

💡 你想搞懂这个技术到底是干嘛的，什么时候该用它，什么时候不该用。不想上来就背一堆概念。

SQL 注入：一个 1998 年被披露的漏洞，为什么 2026 年还在刷榜

SQL 注入（SQLi）是 Web 安全里历史最久、原理最简单、危害最直观的漏洞。1998 年 Rain Forest Puppy 在 Phrack 杂志上披露了第一个完整的 SQLi 利用过程；25 年后，它依然是 O...

2019 年某社交平台 5 亿用户数据泄露、2022 年某 ERP 厂商被勒索，根因都是 SQLi。原因不复杂：只要你还在拼字符串写 SQL，你就在赌"用户输入永远不包含引号"。

SQLi 的本质是控制流与数据流混淆：程序员期望变量是"数据"（一个 ID、一个名字），攻击者把它变成了"控制流"（一段新的 SQL 语句）。一旦数据库把攻击者的输入当成 SQL 语法的一部分来解析，整个数据库的防线就塌了。

攻击原理：从一个引号到拖库

flowchart TB APP[应用代码] -->|拼接 SQL 字符串| DB[(数据库)] ATT[攻击者输入 单引号 OR 永真] --> APP DB -->|拼接后变成永真条件| RESULT[返回全表] ATT2[UNION 注入 查询用户表] --> DB DB -->|拖出凭据表| CREDS[管理员密码泄露] ATT3[盲注 SLEEP 时间延迟] --> DB DB -->|根据响应时间逐位猜数据| BLIND[盲出整列数据]

攻击演示：三种典型注入手法

# 漏洞代码：字符串拼接 SQL
@app.route("/user")
def user():
    uid = request.args.get("id")
    # ❌ 用户输入直接拼进 SQL
    sql = "SELECT id, name, email FROM users WHERE id = " + uid
    row = db.execute(sql).fetchone()
    return jsonify(dict(row) if row else {})

攻击者访问 /user?id=1 OR 1=1 就能拿到全表；访问 /user?id=1 UNION SELECT username,password,role FROM admins-- 就能拖出管理员凭据。如果页面不直接返回数据（只显示成功/失败），还能用盲注：

# 布尔盲注：页面有差异
curl "https://example.com/user?id=1 AND SUBSTRING((SELECT password FROM admins LIMIT 1),1,1)='a'"

# 时间盲注：通过响应时间逐字符猜
curl "https://example.com/user?id=1 AND IF(SUBSTRING((SELECT password),1,1)='a',SLEEP(3),0)"
# 响应耗时 3 秒 → 第一位是 'a'；以此类推

更隐蔽的是二阶注入：用户注册时名字被正常转义入库，后续业务代码从数据库再读出来拼进 SQL，此时字符串已经"合法"过一次，静态扫描很难发现。

防御第一层：参数化查询（Prepared Statement）

参数化查询的关键是：SQL 语法先于数据发送给数据库编译，数据永远以独立参数绑定，不会被解析为语法。这是根治 SQLi 的唯一手段。

// Go database/sql：占位符 + 参数绑定
import "database/sql"

func getUserByID(db *sql.DB, id string) (*User, error) {
    u := &User{}
    // ✅ ? 是占位符，id 永远作为参数传入，不会进入 SQL 语法解析
    err := db.QueryRow(
        "SELECT id, name, email FROM users WHERE id = ?",
        id,
    ).Scan(&u.ID, &u.Name, &u.Email)
    return u, err
}

// 批量查询同样安全
func listUsers(db *sql.DB, ids []int) ([]User, error) {
    placeholders := make([]string, len(ids))
    args := make([]interface{}, len(ids))
    for i, id := range ids {
        placeholders[i] = "?"
        args[i] = id
    }
    query := "SELECT id, name FROM users WHERE id IN (" +
        strings.Join(placeholders, ",") + ")"
    rows, err := db.Query(query, args...)
    // ...
}

# Python：psycopg2 / sqlite3 同样用参数化（注意不是字符串拼接！）
import psycopg2

def get_user(conn, uid: str):
    # ✅ 用 %s 占位符 + 参数元组
    with conn.cursor() as cur:
        cur.execute("SELECT id, name, email FROM users WHERE id = %s", (uid,))
        return cur.fetchone()

# ❌ 反面教材：f-string 拼接，任何输入都能注入
# cur.execute(f"SELECT * FROM users WHERE id = '{uid}'")

# ORM（SQLAlchemy）默认也是参数化的：
from sqlalchemy import text
db.session.execute(text("SELECT * FROM users WHERE id = :uid"), {"uid": uid})

防御第二层：ORM 与查询构造器

// GORM：链式 API 默认参数化
db.Where("id = ?", uid).First(&user)
db.Where("id IN ?", []int{1, 2, 3}).Find(&users)

// ⚠️ 注意：GORM 的 Order/Where 原生字符串仍可能有风险
// db.Order("name " + userInput)   // ❌ 攻击者可注入 "id; DROP TABLE users;--"
// 正确做法：白名单排序字段
allowedSorts := map[string]bool{"name": true, "created_at": true}
if !allowedSorts[sortBy] { sortBy = "created_at" }
db.Order(sortBy)

防御第三层：最小权限与数据库侧兜底

-- 应用账号只给业务库的 CRUD，不给 DDL、不给 super
CREATE USER 'app_rw'@'%' IDENTIFIED BY 'strong-password';
GRANT SELECT, INSERT, UPDATE ON appdb.orders TO 'app_rw'@'%';
GRANT SELECT ON appdb.orders TO 'app_ro'@'%';  -- 只读副本账号
-- 禁止文件读写、禁止存储过程：
-- FILE / PROCESS / SUPER 权限一律不给
-- 即使被注入，攻击者也无法 SELECT ... INTO OUTFILE 写 WebShell

# Kubernetes Secret + 按命名空间分发数据库凭据（最小权限落地）
apiVersion: v1
kind: Secret
metadata:
  name: orders-db-credentials
type: Opaque
stringData:
  username: app_rw
  password: ${DB_PASSWORD_FROM_VAULT}
---
apiVersion: apps/v1
kind: Deployment
# ... 容器以非 root 运行，只挂载本服务需要的 Secret

最佳实践

防御层手段效果是否根治
第一层参数化查询（Prepared Statement）数据与语法分离✅ 根治
第二层ORM / 查询构造器默认参数化，但 raw() 有风险⚠️ 需审查
第三层数据库账号最小权限即使注入也无法 DROP/写文件兜底
第四层WAF（ModSecurity CRS）挡已知 Payload 和扫描器❌ 可绕过
我踩过的坑：GORM 的 Order 注入

有次排序功能用了 db.Order(c.Request.Query("sort"))，以为 GORM 就安全。结果有人传了 sort=id; DROP TABLE users;--。还好我们是 MySQL，多语句执行默认关闭，没炸库。从那以后排序字段全走白名单。ORM 的链式 API 安全，但 Order/Where 里拼用户输入就是自己给自己挖坑。

  • 永远不用字符串拼接 SQL，code review 里见 f"...{var}..." 拼 SQL 直接打回。
  • ORM 不是万能的：raw()、Order(用户输入)、Where(原生字符串) 三个口子要重点审。
  • 数据库账号最小权限：应用账号不给 DROP/ALTER/FILE/SUPER，只读报表用只读账号。
  • 错误信息不要回显 SQL 原文（"You have an error in your SQL syntax"），统一返回 500。
  • 预发环境用 OWASP ZAP / sqlmap 自动跑一遍，重点测搜索、详情、筛选、排序参数。
  • WAF 作为兜底（ModSecurity OWASP CRS 规则集），但不要替代参数化。
  • 对 LIKE 查询做特殊处理：%、_ 是通配符，要转义，否则会变成慢查询攻击。

常见问题 FAQ

Q1：用了 ORM 是不是就彻底没有 SQL 注入了？

不是。ORM 的链式 API 默认安全，但只要你调用 raw() / 原生 SQL 片段 / 把用户输入拼进 ORDER BY / 表名 / 列名，注入就回来了。ORM 挡不住"你主动绕过它"的场景。

Q2：预编译能防 LIKE 注入吗？% 怎么办？

预编译能防引号闭合类注入，但 % 和 _ 是 SQL 通配符，不是注入字符。如果不希望用户输入通配符，需要在应用层把 % _ 转义成 \% \_，否则会导致全表扫描式慢查询。

Q3：NoSQL（MongoDB）就没有注入问题了吗？

有，只是形式不同。MongoDB 的 $where 接受 JS 表达式、$gt 操作符可以从请求体注入（{"password": {"$ne": null}} 绕过登录）。Mongoose 默认会过滤查询对象，但如果你用 Mixed 类型或 $where，一样要小心。

Q4：参数化查询会影响性能吗？

现代数据库对预编译语句有执行计划缓存，重复执行的性能比拼接 SQL 还好——因为拼接每次都要硬解析。只有首次编译略有开销，这点开销相对于安全收益可以忽略。

总结

SQL 注入的修复只有一条铁律：数据与 SQL 语法必须分离，参数化是唯一根治方案。ORM 是加速器不是替代品，最小权限是兜底，WAF 是最后一道墙。下一篇我们离开数据层，进入攻击者最爱突破的门面——认证授权，看 JWT、OAuth 2.0、OIDC 这三个常被误解的协议各自解决什么问题、又在哪里被误用。
