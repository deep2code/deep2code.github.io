SQL 注入防护：参数化查询的能力边界与纵深防御

🏷️ SQL 注入

SQL 注入被讲了二十多年，防御手段也早就有了标准答案，但它至今还在 OWASP 榜单上，原因不是大家不知道要用参数化查询，而是参数化查询有一圈明确的能力边界：表名、列名、ORDER BY 字段、LIMIT 值、IN 列表全都无法参数化。真实线上漏洞绝大多数就落在这圈边界上，以及 ORM 里那几个「看起来很安全其实在拼字符串」的入口。

一、根因：数据被当成代码解析

注入的本质和 XSS 完全同源：一段本该是数据的内容，被送进了解析器的语法分析阶段，于是改变了语句结构。数据库拿到的只是一个字符串，它无法知道其中哪一段是程序写的、哪一段是用户填的。

看一条最经典的登录查询。程序员脑子里的结构是「用户名等于某个值」，而字符串拼接交给数据库之后，语法树可能长成完全不同的样子：

-- 程序拼出来的字符串：SELECT id FROM users WHERE name = '$name' AND pwd = '$pwd'
-- 用户在 name 里填了：  admin' --
-- 数据库实际收到的语句：
SELECT id FROM users WHERE name = 'admin' -- ' AND pwd = 'whatever'
--                                       ^ 从这里开始整行被注释掉，密码校验消失

-- 用户填 ' OR '1'='1' -- 时，WHERE 条件恒为真，返回全表第一行
-- 用户填 ' UNION SELECT 1,version(),3 -- 时，返回的是攻击者自选的数据
💡
判断一处代码有没有注入风险，只看一件事

用户数据是在 SQL 文本里，还是在 SQL 文本之外。凡是参与了 SQL 字符串构造的，都有风险，无论中间做了多少层过滤；凡是通过绑定参数送过去的，天然没有风险，哪怕内容是一整段 DROP TABLE。这条判据比「有没有过滤引号」可靠得多——判断依据是数据传输的通道，而不是数据的内容。

二、参数化查询为什么能根治

参数化查询不是「帮你自动加转义」，这是最常见的理解偏差。它的机制是把一次查询拆成两次独立的通信：先把带占位符的 SQL 模板发给数据库，数据库完成词法分析、语法分析、生成执行计划——此时语法树已经定型，占位符的位置被标记为「值槽」；然后再把参数值按二进制协议单独发过去，填进值槽。参数值从来没有经过 SQL 解析器，所以它里面写什么都只是值。

「用了参数化就一定是服务端预编译」不成立

很多驱动为了减少一次网络往返，默认或可选走客户端拼接：Go 的 MySQL 驱动加上 interpolateParams=true 后，参数是在驱动里转义后拼进 SQL 文本再发出去的；PHP PDO 历史上默认开启模拟预编译。这些实现本身写得不错，但它们把安全性重新压回到「转义是否正确」上，于是对连接字符集敏感——这正是宽字节注入的土壤。结论：追求确定性就关掉模拟预编译，并把连接字符集统一为 utf8mb4。

三、参数化的能力边界：哪些位置根本不能绑参数

这是全篇最实用的一节。占位符只能出现在「值」的位置，因为执行计划在预编译阶段就要确定读哪张表、用哪个索引、按哪列排序。凡是影响语法结构的位置都不能绑参数，只能用白名单映射。

❌
「先过滤再拼表名」不是白名单

常见的错误补救是给表名做一次正则过滤，比如只允许字母数字下划线。这确实能挡住引号和空格，但它挡不住越权访问：攻击者把表名换成另一个租户的分表、或者换成 users，正则完全放行。白名单的含义是「值必须来自程序内定义的常量集合」，输入只能是这个集合的 key，SQL 里出现的永远是程序里写死的标识符。这一条同时解决了注入和越权两个问题，而过滤只解决了半个注入。

package main

import (
    "context"
    "database/sql"
    "fmt"
    "strings"
)

// ========== 1. 值的位置：直接用占位符 ==========
// MySQL 与 SQLite 用 ?，PostgreSQL 用 $1 $2，Oracle 用 :name
func getUser(ctx context.Context, db *sql.DB, name string) (int64, error) {
    var id int64
    // 正确：name 里写什么都只是值，哪怕是 ' OR 1=1 --
    err := db.QueryRowContext(ctx, "SELECT id FROM users WHERE name = ?", name).Scan(&id)
    return id, err
}

func badGetUser(ctx context.Context, db *sql.DB, name string) {
    // 错误：Sprintf 一出现，参数化就已经失效，加多少层过滤都是补丁
    q := fmt.Sprintf("SELECT id FROM users WHERE name = '%s'", name)
    _, _ = db.QueryContext(ctx, q)
}

// ========== 2. ORDER BY：白名单映射，而不是过滤 ==========
// key 是对外暴露的业务字段名，value 是程序写死的 SQL 标识符
var orderable = map[string]string{
    "created": "created_at",
    "price":   "price",
    "sales":   "sales_count",
}
var directions = map[string]string{"asc": "ASC", "desc": "DESC"}

func listGoods(ctx context.Context, db *sql.DB, sortKey, dir string, limit, offset int) (*sql.Rows, error) {
    col, ok := orderable[sortKey]
    if !ok {
        return nil, fmt.Errorf("invalid sort field: %s", sortKey) // 宁可报错，不要默认兜底
    }
    d, ok := directions[strings.ToLower(dir)]
    if !ok {
        d = "ASC"
    }
    // 关键点：col 与 d 都来自上面的常量表，绝不可能包含用户字符
    // limit/offset 走占位符，同时在业务层裁剪上限，避免一次拉全表
    if limit <= 0 || limit > 200 {
        limit = 50
    }
    q := fmt.Sprintf("SELECT id, name, price FROM goods ORDER BY %s %s LIMIT ? OFFSET ?", col, d)
    return db.QueryContext(ctx, q, limit, offset)
}

// ========== 3. IN 列表：按长度动态生成占位符 ==========
func getByIDs(ctx context.Context, db *sql.DB, ids []int64) (*sql.Rows, error) {
    if len(ids) == 0 {
        return nil, fmt.Errorf("empty ids")
    }
    if len(ids) > 1000 { // 占位符过多会拖慢预编译，也容易撞上驱动上限
        return nil, fmt.Errorf("too many ids")
    }
    ph := strings.TrimRight(strings.Repeat("?,", len(ids)), ",") // ?,?,?
    args := make([]any, 0, len(ids))
    for _, v := range ids {
        args = append(args, v)
    }
    q := "SELECT id, name FROM users WHERE id IN (" + ph + ")"
    return db.QueryContext(ctx, q, args...)
}

// ========== 4. LIKE：通配符拼在值里，并转义用户输入中的通配符 ==========
func searchByName(ctx context.Context, db *sql.DB, kw string) (*sql.Rows, error) {
    r := strings.NewReplacer(`\`, `\\`, "%", `\%`, "_", `\_`) // 否则用户输入 % 可匹配全表
    return db.QueryContext(ctx,
        "SELECT id, name FROM users WHERE name LIKE ? ESCAPE '\\\\' LIMIT 50",
        "%"+r.Replace(kw)+"%")
}

下面这张表把「看起来差不多、实际一个安全一个致命」的写法并排放在一起。凡是用字符串格式化或加号拼出 SQL 的，都是错的，不存在例外。

import re
import pymysql

# ========== 正确：占位符 + 参数元组 ==========
def get_user(conn, name: str):
    with conn.cursor() as cur:
        # %s 是 DB-API 的占位符，由驱动负责按类型发送参数
        # 不要写成 '%s'，加了引号反而破坏参数化
        cur.execute("SELECT id, name FROM users WHERE name = %s", (name,))
        return cur.fetchone()

# ========== 错误：f-string 是本文最常见的漏洞来源 ==========
def bad_get_user(conn, name: str):
    with conn.cursor() as cur:
        cur.execute(f"SELECT id FROM users WHERE name = '{name}'")  # 直接可注入
        return cur.fetchone()

# ========== IN 列表：按长度生成占位符，不要拼 id 串 ==========
def get_by_ids(conn, ids):
    ids = [int(i) for i in ids]          # 先做类型收敛，非整数直接抛异常
    if not ids or len(ids) > 1000:
        raise ValueError("bad ids")
    ph = ",".join(["%s"] * len(ids))     # %s,%s,%s
    with conn.cursor() as cur:
        cur.execute(f"SELECT id, name FROM users WHERE id IN ({ph})", ids)
        return cur.fetchall()

# ========== 标识符：白名单映射，PostgreSQL 可用 psycopg2.sql.Identifier ==========
SORTABLE = {"created": "created_at", "price": "price", "sales": "sales_count"}
DIRECTION = {"asc": "ASC", "desc": "DESC"}

def list_goods(conn, sort_key: str, direction: str, limit: int = 50):
    col = SORTABLE.get(sort_key)
    if col is None:
        raise ValueError("invalid sort field")   # 不做默认兜底，避免掩盖调用方 bug
    d = DIRECTION.get((direction or "").lower(), "ASC")
    limit = max(1, min(int(limit), 200))
    sql = f"SELECT id, name, price FROM goods ORDER BY {col} {d} LIMIT %s"
    with conn.cursor() as cur:
        cur.execute(sql, (limit,))
        return cur.fetchall()

# 附：如果实在要允许动态列名，也必须是「先校验再从白名单取值」，
# 而不是下面这种过滤——它挡得住引号，挡不住越权读其他列
UNSAFE_PATTERN = re.compile(r"^[A-Za-z0-9_]+$")

Java 侧的重点不在 JDBC 本身，而在 MyBatis 的两种占位符。#{} 生成的是 ?，走预编译；${} 是字符串直接替换，等价于拼接：

String sql = "SELECT id, name FROM users WHERE dept_id = ? AND status = ?";
try (PreparedStatement ps = conn.prepareStatement(sql)) {
    ps.setLong(1, deptId);      // 按类型绑定，值不参与语法分析
    ps.setString(2, status);
    try (ResultSet rs = ps.executeQuery()) { /* ... */ }
}

// 反例：用了 PreparedStatement 但仍然拼接，等于没用
String bad = "SELECT id FROM users WHERE name = '" + name + "'";
conn.prepareStatement(bad).executeQuery();

⚠️
ORM 不等于安全，它只是把危险入口收窄到几个方法上

用了 ORM 之后注入面确实小了，但风险集中在这些入口：GORM 的 Raw、Exec、以及 Order、Select、Group、Having、Joins 这几个参数会被原样拼进 SQL 的方法；Where 传单个字符串而不用占位符时同样危险。Code Review 的检查点非常明确：搜索代码里所有 SQL 关键字附近的字符串格式化，在 Go 里搜 fmt.Sprintf，在 Python 里搜 f-string 和 %，在 Java 里搜 ${} 和字符串加号。这条规则比读一遍业务逻辑有效得多，也容易做成 CI 里的静态检查。

五、注入类型分类：利用条件与外部特征

知道类型分类的实际用途有两个：估算漏洞的严重程度（能不能直接拖库、要多久），以及在日志和监控里认出正在被打。

类型利用前提攻击者看到的反馈拖一张表的量级日志与监控特征
联合查询注入查询结果直接回显，列数可对齐页面上直接显示数据分钟级请求里出现 union、order by 递增探测列数
报错注入数据库报错信息返回给前端错误消息里带查询结果分钟到小时级5xx 或错误页激增，SQL 语法错误日志密集
布尔盲注页面只有两种状态，如存在与不存在真假两种响应小时级，每字符多次请求同一 URL 高频请求，参数尾部规律变化
时间盲注无任何内容差异，但能观察响应耗时响应变慢与否小时到天级大量耗时接近整数秒的慢请求
带外注入数据库能发起外部请求，如 DNS 或 UNC攻击者自己的服务器收到回连分钟级数据库主机出现异常 DNS 查询
二次注入入库时被转义，取出后再次拼进 SQL延迟生效，与提交点不在同一接口取决于二次拼接点最难发现，请求本身完全正常

二次注入是最容易被漏掉的一类，因为它完全绕开了「入口做一次转义」的思路。数据在入口被正确转义、正确入库；真正的问题出在读出来之后——程序默认「数据库里的数据是可信的」，于是把它拼进另一条 SQL。下面这张图画的是同一条数据的状态变化：

从二次注入得到的通用结论

「可信数据源」这个概念在 SQL 层面不存在。不管数据来自用户、数据库、缓存、消息队列还是内部服务，只要它进入 SQL 文本，就一样危险。所以防御规则不应该写成「对用户输入做处理」，而应该写成「所有进入 SQL 的动态内容都走绑定参数或白名单」。后者是可以机械检查的，前者永远依赖判断力。

六、为什么转义和黑名单靠不住

转义与关键字黑名单是 2010 年前的主流方案，现在还大量留在老项目里。它们不可靠不是因为写得不够仔细，而是因为防御方需要穷举所有变形，攻击方只需要找到一种。

绕过手法示例为什么有效参数化是否受影响
宽字节注入连接字符集为 GBK 时，用 %df%27 吃掉转义符转义加的反斜杠与前一字节组成一个合法汉字，单引号重获语法意义服务端预编译不受影响
注释截断--、#、/**/、/*!50000 ...*/注释可截断后续条件，内联注释还能绕关键字匹配不受影响
大小写与空白变形UnIoN、union/**/select、Tab 与换行代替空格黑名单多用固定字符串或简单正则匹配不受影响
编码变形URL 双重编码、十六进制字面量、char() 拼字符串过滤层与数据库解码阶段不一致不受影响
关键字等价替换用 || 代替 OR、CONCAT_WS 代替 CONCAT黑名单不可能穷举等价写法不受影响
数字型注入参数不带引号时，无需任何引号即可注入转义函数只处理引号类字符，对数字位置毫无作用不受影响
二次解码入库时转义、取出后拼接转义只在写入通道生效，原文仍是原文只要每个出口都绑定参数即可
❌
数字型参数没有引号，转义函数完全失效

WHERE id = $id 这种写法里，攻击者不需要任何引号：直接传 1 OR 1=1 或 1 UNION SELECT ... 即可，转义函数处理的那些字符一个都用不上。所以老项目里做安全评估时，数字型参数的优先级要排在字符串型前面，尤其是 id、page、size、status 这类看起来没风险的字段。补救的最小成本做法是先强制类型转换：Go 里用 strconv.ParseInt，Python 里用 int()，转换失败直接返回 400，这一步就能把绝大多数历史遗留的数字型注入挡掉。

七、纵深防御：假设某处一定会漏

参数化是修复，剩下的都是限制爆炸半径。目标很明确：即使某个接口真的被注入了，攻击者也只能读到有限的数据、无法写入、无法落地 WebShell、并且你能在几分钟内发现。

绑定参数与白名单所有注入类型-中，需要逐个接口改造
最小权限账号写入篡改、DDL、读其他库、写文件落 WebShell读取本业务库的数据低，改授权与连接串

-- ========== 业务账号：只给用得到的权限 ==========
-- 反例：很多项目图省事直接给 GRANT ALL PRIVILEGES ON *.*，
-- 一旦被注入，等于把整台实例交出去：可读其他库、可写文件、可提权
CREATE USER 'app_rw'@'10.0.%' IDENTIFIED BY '强随机口令';
GRANT SELECT, INSERT, UPDATE, DELETE ON shop.* TO 'app_rw'@'10.0.%';
-- 不给 DROP / ALTER / CREATE：应用不需要在运行期改表结构
-- 不给 FILE：这是写 WebShell 与读服务器文件的关键权限
-- 不给 SUPER / PROCESS：避免被 kill 其他会话或看到全局连接信息

-- 只读接口用独立账号，注入后无法写数据
CREATE USER 'app_ro'@'10.0.%' IDENTIFIED BY '另一个强随机口令';
GRANT SELECT ON shop.* TO 'app_ro'@'10.0.%';

-- 列级授权：敏感列干脆不让业务账号看见
GRANT SELECT (id, name, dept_id) ON shop.users TO 'app_ro'@'10.0.%';

-- 全局禁用文件导入导出，secure_file_priv 设为 NULL 即完全禁止
-- my.cnf: secure_file_priv = NULL
-- my.cnf: local_infile = 0

-- ========== 监控：把时间盲注变成可告警事件 ==========
-- 慢查询里出现 SLEEP 或 BENCHMARK，基本可以判定正在被探测
SELECT start_time, user_host, query_time, LEFT(sql_text, 200) AS sql_head
FROM mysql.slow_log
WHERE sql_text REGEXP 'SLEEP\\(|BENCHMARK\\(|pg_sleep'
ORDER BY start_time DESC
LIMIT 50;

-- 正在执行的可疑长查询：注入探测常表现为大量同构长耗时语句
SELECT id, user, host, time, LEFT(info, 200) AS sql_head
FROM information_schema.processlist
WHERE command = 'Query' AND time > 3
ORDER BY time DESC;
✅
报错信息的处理方式，比大多数团队想的更重要

把数据库原始错误返回到前端，等价于送给攻击者一个交互式调试器：报错注入可以直接把查询结果塞进错误消息，列数、类型、表名全都能试出来。正确做法是错误分层：对外只返回统一错误码与请求 ID，详细的 SQL 与堆栈只进服务端日志，通过请求 ID 关联。顺带一个容易忽略的点——响应时间和返回行数也是信息通道，所谓盲注就是靠这两个通道工作的，所以哪怕错误信息已经统一，监控上仍然需要覆盖「同一接口高频请求且响应耗时规律变化」这种模式。

八、上线检查清单

把前面的内容压缩成一份可以直接拿去做 Code Review 和上线评审的清单：

检查项怎么查不达标的后果
SQL 附近是否存在字符串格式化搜 fmt.Sprintf、f-string、% 拼接、字符串加号、${}直接可注入，优先级最高
排序与分页字段是否白名单搜 ORDER BY、Order(、order_by最高频的真实漏洞位置
IN 列表是否按长度生成占位符搜 IN ( 与 join 逗号的代码批量接口常见注入点
数字参数是否强制类型转换检查 id、page、size、status 的解析无需引号即可注入
从数据库读出的数据是否再次拼进 SQL审后台任务、数据同步、报表模块二次注入，最难发现
数据库账号权限是否最小化SHOW GRANTS 逐个账号核对注入直接升级为服务器失陷
生产是否关闭详细报错造一次故障看响应体报错注入效率翻倍
是否有异常 SQL 告警检查慢查询与错误率看板被拖库数周无人发现
❌
最容易出问题的六个认知误区
  • 「用了 ORM 就安全」：Raw、Exec、Order、Select、Having 以及 MyBatis 的 ${} 都是原样拼接，ORM 只是把风险收窄到了几个方法上。
  • 「参数化能防住一切」：表名、列名、ORDER BY、IN 列表都不能绑定参数，这些位置必须白名单映射，而不是过滤。
  • 「转义函数够用了」：宽字节、注释、编码变形、数字型参数，任一条就能绕过；转义还需要连接字符集正确才成立。
  • 「内部数据是可信的」：二次注入就是这么来的，所有进入 SQL 的动态内容一视同仁。
  • 「有 WAF 就不着急改代码」：WAF 挡的是公开 payload，对定制变形和二次注入基本无效，它只是补充。
  • 「注入最多就是数据泄露」：配上高权限账号与 FILE 权限，注入可以写文件、落 WebShell、横向移动，损失完全不在一个量级。
