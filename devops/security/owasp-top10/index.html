OWASP Top 10

🏷️ Web安全,网络安全,安全实践

为什么每个后端工程师都必须读 OWASP Top 10

OWASP（Open Worldwide Application Security Project）是一个由全球安全研究者维护的非盈利组织，其 Top 10 榜单每三四年更新一次，统计的是 Web 应用中发生频率最高、危害最大的十类风险。它不是 CVE 清单，而是缺陷模式（Weakness）清单——告诉团队"代码应该在哪个环节停下来自查"。

对一线工程师而言，把 Top 10 当作代码评审 checklist，比事后应急响应的成本低一个数量级：Equifax 泄露 1.43 亿人数据、TikTok 早年越权访问接口，根因都落在 Top 10 反复出现的老问题上。

2021 版相对 2017 版最大的变化有三点：一是把"失效的访问控制"从第 5 位跃升到第 1 位，因为云原生 API 化之后，授权逻辑散落在每个微服务里，越权成了最普遍的问题；二是合并了"失效的认证"与"敏感数据暴露"的边界讨论，强调架构级防御而非单点修补；三是新增"软件和数据完整性故障"（A08），对应 CI/CD 投毒、依赖混淆、不安全的反序列化这类供应链与运行时完整性问题。

我的 CR 检查清单

每次 Code Review 我都会过一遍这三个问题：① 新接口做了 ownership 校验吗（A01）？② 用户输入拼进 SQL 了吗（A03）？③ 新依赖是最新的吗（A06）？就这三条，拦下了我团队 80% 的线上安全问题。OWASP Top 10 不是用来背的，是用来当 checklist 的。

  • A01 失效的访问控制（Broken Access Control）：最常见也最贵的漏洞。典型形式是 IDOR（Insecure Direct Object Reference）——接口 /api/order?id=1001 只校验了"你登录了"，没校验"这张订单属于你"。修复原则：默认拒绝，每次资源访问都在服务端做 ownership 检查，绝不能信任前端传来的角色字段。
  • A02 加密机制失效（Cryptographic Failures）：明文传输密码、用 MD5 存口令、JWT 用 none 算法、TLS 被降级。本质是"以为加密了，实际没有或可被绕过"。
  • A03 注入（Injection）：SQL 注入、命令注入、LDAP 注入、NoSQL 注入。根因统一：把用户输入拼进了命令/查询的语法。预编译参数化是根治手段。
  • A04 不安全的设计（Insecure Design）：业务逻辑本身有缺陷，例如验证码可重放、密码重置令牌与邮箱不绑定、秒杀接口不做服务端限流。这类问题靠代码扫描扫不出来，必须在威胁建模（Threat Modeling）阶段发现。
  • A05 安全配置错误（Security Misconfiguration）：生产环境开着 debug 模式、.env 被部署到 Web 目录、Nginx 目录遍历、默认口令 admin/admin、CORS 配置成 * 还允许携带凭证。云环境下 S3 bucket 公开也是这类。
  • A06 易受攻击和过时的组件（Vulnerable & Outdated Components）：Log4j2、Spring4Shell、Log4j 的爆发都是这类。SCA（Software Composition Analysis）工具持续扫描依赖，比人肉升级可靠得多。
  • A07 身份认证和身份校验失败（Identification & Authentication Failures）：弱密码策略、会话不失效、JWT 校验不严、找回密码逻辑可被枚举。
  • A08 软件和数据完整性故障（Software & Data Integrity Failures）：CI 流水线被投毒、npm 依赖混淆、不安全的反序列化（Java 原生序列化、Python pickle）、自动更新不校验签名。
  • A09 安全日志和监控失败（Security Logging & Monitoring Failures）：不是被黑不慌，是被黑了半年不知道。日志里没有登录失败、没有越权尝试、没有管理操作审计，事故响应时间从小时级拖到月级。
  • A10 服务端请求伪造 SSRF（Server-Side Request Forgery）：服务端按用户提供的 URL 去请求资源，攻击者让它访问内网元数据接口（如云厂商 169.254.169.254）或打穿内网。

攻击演示：一个典型的 A01 + A03 复合漏洞

下面这段 Python（Flask）代码同时踩了两个坑：直接拼接 SQL 字符串，且 user_id 从 URL 取出来后没有校验资源归属。攻击者只需遍历 order_id 就能看到别人的订单。

# 漏洞代码：SQL 字符串拼接 + 缺少 ownership 校验
from flask import Flask, request, g
app = Flask(__name__)

@app.route("/api/order/<int:order_id>")
def get_order(order_id):
    # 用户已登录，g.user_id 来自会话
    # ❌ 直接拼接 order_id 进 SQL，且没有 WHERE user_id = 当前用户
    sql = f"SELECT * FROM orders WHERE id = {order_id}"
    row = g.db.execute(sql).fetchone()
    if row is None:
        return {"error": "not found"}, 404
    return {"order": dict(row)}

防御代码：参数化查询 + 强制所有权检查

# 修复代码：参数化查询（治 A03 注入）+ 服务端 ownership 检查（治 A01 越权）
@app.route("/api/order/<int:order_id>")
def get_order(order_id):
    # ✅ 参数化：order_id 永远作为参数绑定，不进入 SQL 语法
    row = g.db.execute(
        "SELECT * FROM orders WHERE id = ? AND user_id = ?",
        (order_id, g.user_id),          # ✅ 当前用户绑定到查询条件
    ).fetchone()
    if row is None:
        # 统一返回 404，避免通过响应差异枚举订单是否存在
        return {"error": "not found"}, 404
    return {"order": dict(row)}

纵深防御：把 Top 10 落到工程流程

单点修复任何一条都不够，OWASP 强调纵深防御（Defense in Depth）：入口有 WAF、网关有认证、应用有授权、数据层有加密、运行时有沙箱、发布前有扫描。下面是一套可直接进 CI 的 nginx 基线，覆盖 A05 配置错误与传输层风险：

# nginx 安全基线：同时缓解 A05 配置错误 / A02 加密失效 / 点击劫持
server {
    listen 443 ssl http2;
    server_name api.example.com;

    ssl_certificate     /etc/nginx/ssl/fullchain.pem;
    ssl_certificate_key /etc/nginx/ssl/privkey.pem;
    ssl_protocols       TLSv1.2 TLSv1.3;          # 禁用 SSLv3/TLSv1.0/1.1
    ssl_ciphers         ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256;
    ssl_prefer_server_ciphers on;
    ssl_session_cache   shared:SSL:10m;

    # 隐藏版本号，避免指纹泄露（A05）
    server_tokens off;

    # 安全响应头（详见本系列最后一篇）
    add_header X-Content-Type-Options nosniff;
    add_header X-Frame-Options DENY;
    add_header Referrer-Policy strict-origin-when-cross-origin;
    add_header Strict-Transport-Security "max-age=63072000; includeSubDomains" always;

    # 禁止访问敏感文件
    location ~ /\.(git|env|svn) { return 404; }
    location ~* \.(sql|bak|config\.yml)$ { return 404; }
}

最佳实践

  • 威胁建模前置：新功能设计阶段用 OWASP Threat Dragon 或简单的 STRIDE 表过一遍，把 A01/A04/A10 在架构图上标出来。
  • 把 Top 10 写进 Code Review 清单：新增 SQL 查询必须问"参数化了吗"；新增资源接口必须问"ownership 校验了吗"；新增外部 URL 必须问"会不会 SSRF"。
  • 自动化扫描常驻：SAST（Semgrep/CodeQL）扫代码、SCA（Dependabot/Trivy）扫依赖、DAST（OWASP ZAP）在预发环境跑一遍，三者覆盖不同阶段。
  • 默认拒绝（Deny by Default）：授权、CORS、入站网络全部默认关闭，需要哪个开哪个。
  • 统一错误响应：不要让 404/403/500 的响应体差异帮攻击者枚举资源。

常见问题 FAQ

Q1：OWASP Top 10 是不是就是一份"必背面试题"？对日常开发有什么实际价值？

它的价值不在于背诵，而在于提供了一张自查地图。每次写新接口时过一遍：这个接口做了所有权校验吗（A01）？用户输入拼进查询了吗（A03）？会话处理对吗（A07）？依赖是新的吗（A06）？实战中 80% 的线上漏洞都能在写代码的那五分钟里靠这张地图拦下。

Q2：用了框架（Spring/Laravel/Django）是不是就自动免疫 Top 10？

不是。框架默认帮你挡掉一部分（例如 Django 的 ORM 参数化），但只要你绕过框架（拼原生 SQL、用 raw()、自己拼 HTML 模板），漏洞立刻回来。框架是护栏，不是保镖——你翻过去它管不了。

Q3：WAF 能不能替代代码层面的修复？

不能。WAF 是速度限制器，能挡掉扫描器和已知 Payload，但绕 WAF 的技巧日新月异（编码、分块、变异）。正确姿势是 WAF 做第一道，代码做第二道，日志做第三道——任何一层单独都不够。

Q4：Top 10 多久更新一次？现在学 2021 版会过时吗？

约三到四年更新一次，2025 版正在征求意见。但 Top 10 的思维方式（默认拒绝、输入不可信、纵深防御）十年没变，具体条目会随攻击热点调整。学 2021 版打底，再关注新版变化即可。

总结

OWASP Top 10 的本质是把"攻击者会怎么想"翻译成"工程师该怎么写"。A01 越权和 A03 注入是工业界最高发的两块，也是本系列接下来四篇的重点；A07 认证与 A02/A08 加密/完整性放在最后两篇统一讲。下一篇我们从注入家族里最经典、危害最大的 XSS 开刀，看浏览器侧的信任机制是怎么被一点点攻破的。
