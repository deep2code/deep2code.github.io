CSRF 与点击劫持

🏷️ Web安全,网络安全,安全实践

浏览器的"善意"是怎么变成攻击面的

CSRF（Cross-Site Request Forgery，跨站请求伪造）和点击劫持（Clickjacking）利用的都是同一个浏览器设计假设：浏览器会在跨站请求时自动带上目标站的 Cookie。这个假设在 1995 年很美好——用户登录一次就能逛全网；但在 2026 年，它意味着只要你能诱导用户访问一个恶意页面，这个页面发出的任何"浏览器同源策略允许的请求"都会带着你的身份。

2017 年某比特币交易所就因为 CSRF 漏洞，被人通过一张图片链接清空了用户的 API 密钥；2023 年某政务 App 的"一键解绑"接口被 CSRF 扫库。

CSRF 与 XSS 的本质区别要搞清楚：XSS 是往 A 站注入脚本；CSRF 是利用 A 站对浏览器 Cookie 的信任，从 B 站伪造 A 站请求。CSRF 不需要执行任何脚本，只需要让浏览器"自己"发请求。这也是为什么防御手段不是"过滤输入"，而是"证明这个请求是用户主动发起的"。

关键在第 3 步：浏览器的同源策略不阻止跨站请求发送，只阻止跨站读取响应。所以恶意页面可以随便 POST 到你的银行，只是读不到返回——但转账本身已经成功了。

防御方案一：CSRF Token（服务端签发、每次请求校验）

// Go 中间件：基于同步器模式（Synchronizer Token Pattern）
// 1. 渲染表单时把随机 token 写进页面 & 种到会话
// 2. POST 请求必须 header 或 form 里带回这个 token，服务端比对
func CSRFToken(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        session := getSession(r)
        token := session.CSRFToken          // 登录时已生成并存入 session
        if token == "" {
            token = generateRandomToken()   // 32 字节随机
            session.CSRFToken = token
        }
        // 注入模板/响应头，供前端读取
        w.Header().Set("X-CSRF-Token", token)

        if r.Method == "POST" || r.Method == "PUT" || r.Method == "DELETE" {
			// 从 header 或 form 取客户端提交的 token
			got := r.Header.Get("X-CSRF-Token")
			if got == "" {
				got = r.PostFormValue("csrf_token")
			}
			if subtle.ConstantTimeCompare([]byte(got), []byte(token)) != 1 {
				http.Error(w, "invalid csrf token", http.StatusForbidden)
				return
			}
		}
		next.ServeHTTP(w, r)
	})
}

关键点：Token 必须与会话绑定，不能全站共用一个静态 Token；比较时用 subtle.ConstantTimeCompare 防时序侧信道。

防御方案二：SameSite Cookie + Origin/Referer 校验

现代浏览器的 SameSite 属性已经能挡掉大部分跨站 Cookie 携带场景，是 CSRF 防御的"免费午餐"：

// 会话 Cookie 设置 SameSite=Lax（宽松）或 Strict（严格）
http.SetCookie(w, &http.Cookie{
    Name:     "session_id",
    Value:    token,
    HttpOnly: true,
    Secure:   true,
    SameSite: http.SameSiteLaxMode,  // ✅ 跨站 POST 不带 Cookie
    Path:     "/",
    MaxAge:   3600 * 8,
})

# Python/FastAPI 中间件：关键写操作二次校验 Origin
from fastapi import Request, HTTPRequest

SAFE_ORIGINS = {"https://app.example.com", "https://admin.example.com"}

async def csrf_origin_check(request: Request):
    if request.method in ("POST", "PUT", "DELETE", "PATCH"):
        origin = request.headers.get("origin")
        # 兼容老浏览器可能没有 Origin，此时兜底看 Referer
        if origin is None:
            origin = request.headers.get("referer", "")
        if origin and origin not in SAFE_ORIGINS:
            raise HTTPException(status_code=403, detail="cross-site request forbidden")

防御点击劫持：X-Frame-Options 与 CSP frame-ancestors

点击劫持的防御思路很直接：禁止你的页面被任何 iframe 嵌入。

# nginx 一行配置同时覆盖老浏览器与现代浏览器
add_header X-Frame-Options DENY always;                    # IE/老 Chrome
add_header Content-Security-Policy "frame-ancestors 'none';" always;  # 现代浏览器

# 如果必须被自己的子域嵌入，改成：
# add_header Content-Security-Policy "frame-ancestors 'self' https://*.example.com;" always;

注意 X-Frame-Options 只支持 DENY / SAMEORIGIN，无法指定具体域名，需要细粒度白名单就必须用 CSP 的 frame-ancestors。JS 层面的 frame-busting（if (top !== self) top.location = self.location）在 X-Frame-Options 面前是冗余的，但作为老浏览器兜底可以保留。

我踩过的坑：GET 请求做了状态变更

早期写了个"注销账号"接口用 GET，以为登录后点链接才会触发。结果被人在论坛帖子里塞了个 <img src="https://mysite.com/delete-account">，所有在线用户一打开帖子就被注销了。从那以后我定了条铁律：GET 只读，POST 写，DELETE 删，绝不混淆。

  • 写操作（POST/PUT/DELETE）必须三选一以上防御：CSRF Token 是主防线，SameSite=Lax 是兜底，Origin 校验是第二道。
  • GET 请求绝对不能做状态变更（CRUD 里的 CUD 绝不放 GET），否则 CSRF Token 都救不了。
  • SameSite 选择：Strict 安全性最高但会影响从邮件/IM 点进来的首次登录体验；Lax 是绝大多数站点的合理默认。
  • 不要把 API 设计成"只要有 Cookie 就能调"，对纯 API 服务优先用 Authorization: Bearer 头（不会自动带）。
  • 点击劫持防御不要用 JS 检测嵌套——现代浏览器直接用响应头，JS 可以被 sandbox iframe 绕开。
  • 对 OAuth 回调、支付回调这类 GET 跳转接口，单独做 state/nonce 校验，不能仅靠 SameSite。

常见问题 FAQ

Q1：SameSite=Lax 之后是不是就不用 CSRF Token 了？

不能这么乐观。SameSite 是浏览器行为，老版本 Safari/旧 WebView 不支持；且 Lax 允许顶级导航 GET 请求带 Cookie。对状态变更接口，Token 仍然是必须的，SameSite 只是多一层兜底。

Q2：单页应用（SPA）怎么存 CSRF Token？放 localStorage 安全吗？

SPA 常见做法是后端种一个不设 HttpOnly 的 XSRF-TOKEN Cookie（前端可读），前端读出来放到 X-CSRF-Token 请求头。这个 Cookie 不需要保密——攻击者拿不到它之外的任何东西；真正的安全来自它与 HttpOnly 会话 Cookie 的绑定校验。

Q3：API 用 Bearer Token 还需要防 CSRF 吗？

基本不需要。因为 Authorization: Bearer 头不会被浏览器自动携带，跨站请求带不上这个头，CSRF 就失去了"借身份"的前提。但如果你同时支持 Cookie 认证，就还是要防。

Q4：点击劫持和普通的钓鱼页面有什么区别？

普通钓鱼是伪造一个长得像银行的页面骗你输入密码；点击劫持是真的把银行页面嵌进 iframe，只是让用户"看不见按钮背后是什么"，从而在已登录状态下被诱导点击。它的危害是用户在完全真实的站点上做出了非本意的操作。

总结

CSRF 与点击劫持的核心洞察是：浏览器默认信任用户已登录的站点，这种信任必须由服务端用额外信号来验证。CSRF Token 证明请求来自你的页面，SameSite 让跨站请求不带 Cookie，Origin 校验证明请求来自你的域名，X-Frame-Options/CSP 阻止你的页面被当诱饵。下一篇我们看 Web 安全的"祖师爷"——SQL 注入，理解为什么参数化查询是不可妥协的红线。
