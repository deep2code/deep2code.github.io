CSRF 与点击劫持：成立前提、SameSite 精确语义与防护失效边界

🏷️ CSRF

CSRF 至今仍被大量文章描述成「Cookie 被盗用」。这是错的：攻击者从头到尾拿不到 Cookie 的值，也读不到响应体。他利用的是浏览器的一条基础规则——只要请求的目标域匹配 Cookie 的作用域，浏览器就会自动把 Cookie 附上，完全不关心这个请求是从哪个页面发起的。真正被盗用的是「浏览器代表用户发请求」这个能力。把这一点想清楚，才能判断每种防护手段堵住的是链条上的哪一环，以及它在什么条件下会失效。

CSRF 成立的三个前提，缺一不可

一个接口是否存在 CSRF 风险，不取决于它是 GET 还是 POST，而取决于下面三个条件是否同时满足。任何有效的防护，本质都是在打破其中一个。

前提具体含义不满足时会怎样对应的防护手段
凭证自动携带身份凭证放在 Cookie 里，浏览器按域名自动附加，无需页面参与凭证放 Authorization 头，跨站页面无法让浏览器自动附加Token 放 Header、SameSite=Strict
服务端仅凭凭证判定身份后端看到有效会话 Cookie 就认为是本人的主动操作，不再验证请求来源后端还要求一个跨站页面拿不到的秘密值Synchronizer Token、Double Submit
请求可被完整预测URL、方法、参数结构固定，攻击者能离线构造出一份合法请求请求中含一次性、无法预测的字段一次性令牌、二次确认、动态签名

第三个前提常被忽略，但它解释了为什么「敏感操作要二次验证」是有效防护：短信验证码、支付密码这些字段攻击者猜不到，请求就无法预测。反过来，如果你的「二次确认」只是前端弹一个确认框，请求结构没变，那它对 CSRF 毫无价值。

所以那句流传很广的「重要操作用 POST 不要用 GET 就安全了」是错的。HTML 表单天生就能跨站发出 POST，连 JavaScript 都不需要，只要一个 form 加上自动提交脚本即可。GET 和 POST 的区别只影响攻击者构造的难度（GET 可以藏在 img 标签里，连页面停留都不需要），不影响 CSRF 是否成立。

下表把各种跨站发起方式的能力摊开对照。看清「能否发出」和「能否读取响应」是两件独立的事，就不会再把 CORS 当成 CSRF 的防线。

HTML 表单 POST（urlencoded）带（Lax 会拦，它只放行导航 GET）不能否不能能
表单 POST（multipart 或 text/plain）带不能否不能能，常用于绕过只校验 Content-Type 的后端

⚠️
multipart 与 text/plain 是常见绕过口

很多后端框架对 Content-Type 的解析比规范宽松。表单把 enctype 设为 text/plain 提交一段形如 {"amount":1000} 的内容，服务端照样能解析成 JSON。如果你的 CSRF 防护逻辑是「只要 Content-Type 不是 application/json 就认为不可能是我们前端发的，直接放行」，这条路就被打穿了。判定必须基于凭证与来源，不能基于 Content-Type。

为什么 JWT 放 Header 免疫、放 Cookie 不免疫

这是最容易被搞混的一点。「用了 JWT 就不用管 CSRF」这句话只有在特定前提下才成立，而那个前提跟 JWT 这个格式毫无关系。

免疫的根源是：Authorization 头必须由页面里的 JavaScript 主动写入，浏览器不会自动补。evil.com 上的脚本受同源策略约束，读不到 bank.com 域下的 localStorage，也没法凭空生成一个合法令牌，所以它构造出来的请求就是一个匿名请求，后端直接返回 401。而一旦把同一个 JWT 塞进 Cookie，浏览器的自动携带规则立刻重新生效，第一个前提被满足，CSRF 原封不动地回来了。

凭证承载方式跨站请求是否自动带上CSRF 风险XSS 后果是否需要额外 CSRF 防护
Session ID 存 Cookie自动带高HttpOnly 可防脚本读取，但脚本仍能带着 Cookie 发请求必须做
JWT 存 Cookie自动带与 Session 完全相同，高同上必须做，JWT 不提供任何豁免
JWT 存 localStorage，手动写 Authorization 头不会自动带基本为零令牌可被脚本直接读走外带，风险更大不需要，但必须严防 XSS
访问令牌存内存变量，刷新令牌存 HttpOnly Cookie访问令牌不带，刷新接口的 Cookie 会带仅刷新接口有风险刷新令牌脚本读不到，泄露面最小刷新接口需单独做防护
Cookie 存令牌并要求请求头回传同一值Cookie 自动带，头需手动写低，等价于 Double Submit脚本可读取并伪造依赖 Cookie 不可被子域写入
❌
别把「免疫 CSRF」当成净收益

把令牌从 HttpOnly Cookie 挪到 localStorage，是用「XSS 之后令牌被完整外带、攻击者可在任意机器上离线重放直到过期」换来「免疫 CSRF」。HttpOnly Cookie 遭遇 XSS 时攻击者只能在受害者浏览器里发请求，拿不走凭证本身。第四种方案（访问令牌放内存、刷新令牌放 HttpOnly Cookie 并对刷新接口单独做 CSRF 防护）才是两头都收紧的做法。

SameSite 三个取值的精确语义

SameSite 是浏览器侧最省事的一层防护，但它的行为边界经常被简化成「Lax 差不多等于 Strict」。真实差异在下表里。注意「同站」判定用的是 eTLD+1（可注册域），也就是说 a.example.com 与 b.example.com 互为同站，而 example.com 与 example.cn 是跨站。

点链接跳转过来（顶级导航 GET）不带带带
跨站表单 POST 提交不带不带带
跨站发起的 PUT、DELETE、PATCH不带不带带
iframe 嵌入、img 加载等子资源不带不带带
fetch 带 credentials 的跨站请求不带不带带
window.open 打开（属顶级导航 GET）不带带带
是否强制要求 Secure 属性否否是，缺 Secure 该 Cookie 直接被丢弃
典型副作用从外站点进来会显示未登录，体验割裂体验正常，防护有缺口无防护，必须配套令牌校验

Lax 的放行规则可以精确概括为一句话：只放行「安全方法 + 顶级导航」的组合。安全方法指 GET、HEAD、OPTIONS、TRACE 这些按语义不应有副作用的方法；顶级导航指整个标签页的地址栏发生跳转，而不是页面内的某个子资源在加载。两个条件必须同时满足，缺一个就不带 Cookie。

Chrome 从 80 版本起把没有显式声明 SameSite 的 Cookie 默认按 Lax 处理，这确实消灭了大量老式表单 CSRF。但把它理解成「CSRF 已经解决了」是危险的，下表列出实际残留的缺口。

Cookie 属性怎么写才算收紧

下面是一套可以直接抄的响应头。重点在 __Host- 前缀，它是 Double Submit 方案能不能站住脚的关键。

HTTP/1.1 200 OK
Set-Cookie: __Host-session=s%3A7f9c...; Path=/; Secure; HttpOnly; SameSite=Lax; Max-Age=7200
Set-Cookie: __Host-csrf=3a1f9e2b...; Path=/; Secure; SameSite=Lax; Max-Age=7200

# __Host- 前缀是浏览器强制执行的约束，满足全部条件才会被接受：
#   1. 必须带 Secure（仅 HTTPS 传输）
#   2. Path 必须是 /
#   3. 禁止出现 Domain 属性   <-- 这条最关键
# 禁止 Domain 意味着这个 Cookie 被锁死在精确的主机名上，
# 任何子域都无法覆盖或写入它，Double Submit 的子域绕过路径被堵死。
#
# 两个 Cookie 的属性差异是刻意的：
#   session 带 HttpOnly，脚本读不到，防 XSS 直接外带凭证；
#   csrf 不带 HttpOnly，因为前端 JS 需要读出来写进请求头；
#   csrf 的值本身不是秘密，它的价值在于跨站页面读不到、也写不进。

「每个请求换一个新令牌」听起来更安全，实际会让用户打开两个标签页就必有一个失效，工单里的「提交时提示请刷新页面重试」大多源于此。除支付、改密这类单一流程外，用会话级令牌（整个会话内不变，登录和提权时重新生成）已经足够，安全收益的差距远小于可用性代价。

Origin、Referer 与 Sec-Fetch-Site 的可靠性排序

来源校验是零成本的一层，但必须清楚每个头在什么时候会消失，以及消失时该怎么处理。

请求头由谁填写JS 能否伪造缺失场景缺失时的处理
Sec-Fetch-Site浏览器，属禁止修改的头不能较老的浏览器完全不发送回退到 Origin 判定，不可直接放行
Origin浏览器不能，在 fetch 中属禁止头同源 GET 通常不带；部分历史版本浏览器同源 POST 不带回退到 Referer；仍为空则对写接口拒绝
Referer浏览器，含完整路径不能伪造，但可被策略整段去掉Referrer-Policy 设为 no-referrer、HTTPS 降级到 HTTP、隐私模式、企业代理剥离按拒绝处理；绝不能写成为空就放行
Host客户端非浏览器环境可任意伪造不缺失不能用于来源判定，只用于路由

一个非常常见的实现缺陷是用字符串前缀匹配做白名单：判断 Origin 是否以 https://example.com 开头，会让 https://example.com.evil.com 通过；改成「包含」判断则连 https://evil.com/?x=https://example.com 都放行。Origin 只有协议、主机、端口三段，必须做完整字符串的精确相等比较。

// csrf.go —— 三层校验中间件：Sec-Fetch-Site 到 Origin/Referer 再到同步器令牌
// 设计取舍：三层都是「信息缺失即拒绝」，绝不因为拿不到头就放过写操作。
package middleware

import (
    "crypto/subtle"
    "net/http"
    "net/url"
)

// 安全方法按 RFC 7231 语义不应有副作用，跳过校验。
// 这条豁免的前提是你真的没写「访问即注销」这类接口，先去把它们改掉。
var safeMethods = map[string]bool{
    "GET": true, "HEAD": true, "OPTIONS": true, "TRACE": true,
}

// 精确相等匹配，不做任何前缀或包含判断。
var allowedOrigins = map[string]bool{
    "https://www.example.com": true,
    "https://app.example.com": true,
}

func CSRFGuard(store SessionStore) func(http.Handler) http.Handler {
    return func(next http.Handler) http.Handler {
        return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
            if safeMethods[r.Method] {
                next.ServeHTTP(w, r)
                return
            }

            // 第一层：Sec-Fetch-Site 由浏览器填写且属禁止修改的头，JS 无法伪造。
            // same-origin 同源；same-site 同站（子域，不能信）；
            // none 表示用户直接输地址或点书签打开；cross-site 直接拒绝。
            switch r.Header.Get("Sec-Fetch-Site") {
            case "same-origin", "none":
                // 通过，但仍继续后面两层，做纵深防御
            case "":
                // 老浏览器不发这个头，落到第二层
            default:
                http.Error(w, "cross-site request rejected", http.StatusForbidden)
                return
            }

            // 第二层：Origin 精确白名单，Origin 为空才退化到 Referer。
            origin := r.Header.Get("Origin")
            if origin == "" {
                if ref := r.Header.Get("Referer"); ref != "" {
                    if u, err := url.Parse(ref); err == nil && u.Host != "" {
                        origin = u.Scheme + "://" + u.Host
                    }
                }
            }
            if origin == "" || !allowedOrigins[origin] {
                // 注意这里「空也拒绝」。若写成空则放行，
                // 攻击者只要让 Referrer-Policy 生效或走 HTTPS 降级就能绕过整层。
                http.Error(w, "bad or missing origin", http.StatusForbidden)
                return
            }

            // 第三层：同步器令牌。用常量时间比较，避免按字节短路产生计时侧信道。
            sess, err := store.Get(r)
            if err != nil {
                http.Error(w, "no session", http.StatusUnauthorized)
                return
            }
            sent := r.Header.Get("X-CSRF-Token")
            if sent == "" {
                sent = r.PostFormValue("csrf_token") // 兼容传统表单提交
            }
            if subtle.ConstantTimeCompare([]byte(sent), []byte(sess.CSRFToken)) != 1 {
                http.Error(w, "csrf token mismatch", http.StatusForbidden)
                return
            }

            next.ServeHTTP(w, r)
        })
    }
}

CORS 不是 CSRF 的防御手段

这两个机制经常被混为一谈，但它们管的方向完全不同：CORS 决定「脚本能不能读到响应」，CSRF 关心「请求能不能被发出并产生副作用」。宽松的 CORS 配置会额外泄露数据，但把 CORS 收紧到只允许自己的域，也拦不住表单 CSRF，因为表单提交根本不走 CORS 检查。

唯一的交集在预检请求：当请求「不简单」时，浏览器会先发一个 OPTIONS 去问，被拒绝则真实请求根本不会发出。所以搞清楚什么条件下会触发预检，就知道哪些接口能借到这层顺带的保护。

flowchart TB R["跨站请求"] --> M{"方法是否属于

由此可以推出一条实用结论：把写接口统一要求 JSON 请求体加一个自定义请求头，就能保证所有跨站写请求必须先过预检，只要 CORS 配置里没有放行外部 Origin，真实请求就发不出来。这不是严格意义上的 CSRF 防护，而是一道低成本的结构性约束。前提是后端必须严格拒绝非 JSON 的 Content-Type，否则前面说的 text/plain 绕过会让这层直接失效。

❌
两个致命的 CORS 配置

第一，把 Access-Control-Allow-Origin 直接回显请求带来的 Origin，同时 Access-Control-Allow-Credentials 为 true——这等于允许任意站点带着用户凭证读你的接口响应，比 CSRF 更严重，因为数据也一起泄露了。规范禁止 Allow-Origin 取通配符时携带凭证，但回显 Origin 恰好绕开了这条限制，所以必须用固定白名单。第二，放行 null 这个 Origin——沙箱 iframe 和本地文件页面的 Origin 就是 null，放行它等于放行任意人。

点击劫持：X-Frame-Options 与 frame-ancestors

点击劫持和 CSRF 是同一类问题的另一种形态：CSRF 伪造的是请求，点击劫持借用的是用户真实的鼠标点击。攻击者把你的页面用透明 iframe 叠在自己的诱导页上方，用户以为在点「领取优惠券」，实际点中的是你页面里的「确认转账」按钮。因为点击真实发生在你的页面上，CSRF 令牌、Origin 校验、SameSite 全部正常通过——这就是它必须用独立手段防护的原因。

<!-- 一个最小可用的点击劫持页面，用来自测你的站点是否可被嵌入 -->
<style>
  /* 目标页面透明但可交互：opacity 不为 0，元素仍然接收点击事件 */
  #target {
    position: absolute; top: 0; left: 0;
    width: 100%; height: 700px;
    opacity: 0.0001;   /* 肉眼不可见 */
    z-index: 2;        /* 压在诱饵上面，点击落到 iframe 里 */
    border: 0;
  }
  /* 诱饵按钮的坐标要与目标页面真实按钮的位置对齐 */
  #bait { position: absolute; top: 320px; left: 180px; z-index: 1; }
</style>

# 反向代理层统一下发，注意 always 参数：
# 不加 always 时，nginx 对 4xx/5xx 响应不会附加这些头，
# 于是错误页可被嵌套利用（登录失败页、二次确认页常是攻击目标）。
add_header X-Frame-Options "SAMEORIGIN" always;

# frame-ancestors 优先级高于 X-Frame-Options，两者语义必须保持一致，
# 否则现代浏览器只按这里的策略执行，上面那行形同虚设。
add_header Content-Security-Policy "frame-ancestors 'self' https://partner.example.com" always;

# 配套项：点击劫持常与拖放劫持、UI 遮罩组合使用。
add_header Referrer-Policy "strict-origin-when-cross-origin" always;
add_header X-Content-Type-Options "nosniff" always;

# 排查提示：任何 location 块里只要出现一条 add_header，
# 就会完整覆盖 server 级的全部 add_header（nginx 的继承规则不是合并）。
# 「首页有这些头、详情页没有」的问题九成出在这里。

落地顺序建议

按投入产出排：先把有副作用的 GET 接口全部改成 POST 或 PUT；再给会话 Cookie 加上 __Host- 前缀、Secure、HttpOnly、SameSite=Lax；然后在所有写接口上统一挂来源校验中间件（Sec-Fetch-Site 加 Origin 精确白名单）；最后对支付、改密、绑定手机号这类高危操作补上会话级同步器令牌与二次身份验证。frame 防护头在反代层一次性配好，并用真实浏览器抽查关键路由。
