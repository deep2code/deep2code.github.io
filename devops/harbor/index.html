Harbor：私有镜像仓库的架构与治理

🏷️ Harbor

Harbor 常被当成「一个能存镜像的网站」，于是运维时全靠界面点，遇到磁盘不降、节点拉不动、扫描拦不住就只能重启。它其实是一组分工明确的服务：接入层做转发，core 做认证授权与令牌签发，registry 只负责按内容寻址存取 blob，jobservice 跑复制、扫描与回收这些异步任务，状态只落在 PostgreSQL、Redis 和存储后端。把请求路径与状态边界画清楚，多数问题都能直接定位到组件。

组件构成与一次 pull 的完整路径

组件职责是否有状态它挂掉时的表现
nginx / proxy统一入口、TLS 终止、按路径分流无整站不可用；大层上传失败多半是这里的请求体上限或超时
portal前端静态资源无界面打不开，但 docker pull 与 push 照常
core用户与项目、权限判定、令牌签发、策略检查、Webhook无（状态在 PG）登录与换发令牌全失败，表现为所有拉取推送 401
jobservice执行复制、扫描、保留、GC 等异步任务本地任务日志界面能用，但任务一直排队不执行
registryOCI distribution 实现，按 digest 存取 manifest 与 blob无（数据在存储后端）manifest 与 blob 全挂，界面还能看到元数据
trivy-adapter扫描器适配，维护漏洞库本地漏洞库扫描报错；隔离网络里表现为漏洞库长期过期
PostgreSQL项目、用户、制品元数据、策略、配额有整站不可用，且这是唯一必须做主从与备份的部件
Redis会话、缓存、jobservice 队列有登录态丢失，正在跑与排队的任务一起丢
存储后端层数据本体有元数据还在但拉不到层，界面上看着「有镜像」实际不可用

拉取路径遵循 OCI distribution 的令牌认证规范，而不是简单的 HTTP Basic：客户端先裸请求拿到 401 与令牌服务地址，再带着 scope 去 core 换一个带访问声明的 JWT，registry 用公钥验签后才放行。理解这一步很重要——项目级的阻断策略就是在换发令牌这一步生效的，不是在 registry 里。

sequenceDiagram participant C as docker 或 containerd participant N as nginx participant CO as core participant R as registry participant S as 存储后端 C->>N: 请求 manifest N->>R: 转发 R-->>C: 401 并告知令牌服务地址与 scope C->>CO: 用机器人账号换令牌 CO->>CO: 判定项目角色，检查部署安全策略 CO-->>C: 返回带访问声明的 JWT C->>R: 带令牌重新请求 manifest R->>CO: 用公钥校验令牌签名 R-->>C: 返回 manifest C->>R: 按 digest 逐个取 blob R->>S: 读取 blob S-->>C: 直接返回，或 302 重定向到对象存储 Note over CO,R: 未扫描、漏洞超阈值或未签名
在换发令牌这一步就被拒绝
registry 本身不做业务判断 
# Docker 读的是「主机名加端口」命名的目录，不要图省事写 insecure-registries
sudo mkdir -p /etc/docker/certs.d/registry.internal:443
sudo cp harbor-ca.crt /etc/docker/certs.d/registry.internal:443/ca.crt

# K8s 节点走 containerd，配置路径和 Docker 完全无关，这是最常见的误配
sudo mkdir -p /etc/containerd/certs.d/registry.internal
sudo tee /etc/containerd/certs.d/registry.internal/hosts.toml >/dev/null <<'EOF'
server = "https://registry.internal"

[host."https://registry.internal"]
  capabilities = ["pull", "resolve"]
  ca = "/etc/containerd/certs.d/registry.internal/harbor-ca.crt"
EOF

# 分段排查：先确认 TLS 链与 401 应答，再确认令牌能不能换出来
curl -sSI 'https://registry.internal/v2/' | head -5
curl -sS -u 'robot$team-app+ci-pull:'"$SECRET" \
  'https://registry.internal/service/token?service=harbor-registry&scope=repository:team-app/api:pull' | head -c 120

权限模型：项目、角色与机器人账号

Harbor 的授权单位是项目，不是仓库。同一个项目内的所有仓库共享成员与策略，所以项目划分本质上是权限划分——按团队或按信任级别切，不要按镜像名切。项目可以是公开（任何人可拉）、私有，或者代理缓存类型。认证源可以是本地库、LDAP 或 OIDC；用 OIDC 时命令行登录要用界面上生成的 CLI 密码，直接拿 SSO 密码登录必然失败。

角色拉取推送删除制品触发扫描改项目策略与成员典型用途
Limited Guest是否否否否外部协作方，连成员列表和日志都不该看到
Guest是否否否否只读使用方、跨团队查看
Developer是是否否否日常开发与本地推送
Maintainer是是是是否负责该项目镜像清理与扫描的人
Project Admin是是是是是管成员、保留策略、CVE 允许清单、不可变规则
System Admin是是是是是（含系统级）GC、复制端点、扫描器、配额，不应出现在流水线里
凭据类型权限粒度有效期适合谁用泄露后的处置
普通用户密码跟随该用户在所有项目的角色长期人，在界面与本地使用改密码，但该用户所有项目一起受影响
CLI 密码（OIDC 模式）同上可重新生成人，命令行登录重新生成即失效
项目级机器人账号项目内按动作勾选，可只给拉取可设到期时间流水线、部署侧、节点删掉单个机器人，影响面收敛在一个项目
系统级机器人账号可跨项目，按动作勾选可设到期时间平台级工具，如全局同步器影响面大，应尽量避免使用
管理员账号全部长期只应在应急运维时使用等于仓库全量失守，必须立刻轮换

机器人账号的凭据只在创建时显示一次，找不回只能重建，所以创建时就要落到密钥管理里。命名形如 robot$项目名+用途，注意名字里的美元符号在 shell 里必须用单引号包住，否则会被当变量展开成空字符串，报错却是「用户名密码错误」。

供应链控制：扫描与签名放在流水线的哪一步

顺序是固定的：先推送得到 digest，再基于 digest 扫描和签名，最后部署时按 digest 拉取并验签。所有动作都必须锚定 digest，不能锚定 tag——tag 是可变引用，签完名再覆盖一次 tag，签名就和实际运行的镜像脱钩了。防止覆盖的手段是项目级的不可变 tag 规则，它让匹配到的 tag 无法被重新推送或删除。

# 推送用只有 push 权限的机器人；名字里的美元符号必须单引号包住
echo "$HARBOR_ROBOT_SECRET" | docker login registry.internal \
  -u 'robot$team-app+ci-push' --password-stdin

docker buildx build -t registry.internal/team-app/api:$GIT_SHA --push .

# 取回不可变的 digest，后续所有环节都用它，不要再用 tag
DIGEST=$(docker buildx imagetools inspect \
  registry.internal/team-app/api:$GIT_SHA --format '{{.Manifest.Digest}}')

# 签名对象是 digest；签名会作为 OCI 附属件推回同一个仓库
cosign sign --key env://COSIGN_KEY registry.internal/team-app/api@$DIGEST

# 部署前显式验签并显式判读扫描结果，不达标就让流水线失败
cosign verify --key env://COSIGN_PUB registry.internal/team-app/api@$DIGEST
curl -sS -u "$HARBOR_ROBOT" \
  "https://registry.internal/api/v2.0/projects/team-app/repositories/api/artifacts/$DIGEST?with_scan_overview=true"

阻断策略：在哪一层拦才真的拦住

Harbor 的项目配置里能打开「阻止有漏洞的镜像被拉取」和「要求内容可信」，但它们的作用域只有「经过 Harbor 的这一次拉取」。节点上已有同名镜像、拉取策略是有则不拉时，这两道检查根本不会被触发。所以阻断必须做两层：流水线里显式判定并中断，集群侧再用准入控制限制来源与签名。

检查项配置位置拦在什么时刻失效场景补强方式
漏洞严重级别阈值项目配置的部署安全策略换发令牌时节点已缓存镜像；换个镜像名从别处拉流水线里读扫描结果自行判定
必须已扫描同上换发令牌时漏洞库过期导致「扫过但结论陈旧」监控漏洞库更新时间，隔离网准备离线库
内容可信（签名）同上换发令牌时只签了 tag、签名与实际 digest 不一致按 digest 签名与验签，开启不可变 tag
CVE 允许清单系统级与项目级判定阈值时叠加加了没设到期时间，永久豁免被忘掉每条豁免都设到期日并定期复核
不可变 tag 规则项目配置推送时规则只匹配部分 tag 模式发布用的 tag 全部纳入匹配
准入控制集群侧，不在 Harbor创建工作负载时没启用，或放行了旧命名空间只允许可信仓库前缀加带签名的制品

复制、代理缓存与多地域分发

复制规则有推送与拉取两种模式，触发方式分手动、定时和事件触发，过滤条件可以按仓库名、tag、标签和制品类型，并且能限带宽。代理缓存项目是另一回事：它绑定一个上游端点，第一次拉取时回源并留下副本，之后本地命中——但副本是缓存不是归档，会被周期性清理，不能当唯一副本。

分发方式数据方向触发适合的场景限制与代价
推送模式复制本端到远端手动、定时、事件自建制品下发到多机房远端应设为只读，否则两端都能写就会互相覆盖
拉取模式复制远端到本端手动、定时从云仓库或合作方仓库同步不支持事件触发，存在同步延迟窗口
代理缓存项目按需回源首次拉取加速上游公共镜像副本会被清理，不能推送，不可当归档
每机房独立实例各自为主各自流水线强隔离、跨境合规场景治理策略要复制多份，容易漂移

保留策略与 GC：为什么删了 tag 磁盘没降

这是最高频的疑问，答案在于职责切分：保留策略只动数据库里的引用，GC 才删存储上的 blob。保留策略按仓库模式配置规则（保留最近推送的 N 个、最近拉取的 N 个、最近若干天内推送的），建议先用试运行看清将被删掉什么；GC 是系统级任务，回收不再被任何 manifest 引用的 blob，且运行期间 registry 会进入只读，推送会失败，所以要安排在低峰。

stateDiagram-v2 [*] --> Pushed: docker push Pushed --> Scanned: 自动扫描或手工触发 Scanned --> Signed: 流水线按 digest 签名 Signed --> Pullable: 满足项目部署策略 Scanned --> Blocked: 漏洞超过阈值 Pushed --> Blocked: 策略要求必须扫描或签名 Pullable --> Immutable: 命中不可变 tag 规则 Pullable --> Untagged: 保留策略删掉 tag Untagged --> Removed: GC 回收不再被引用的 blob Removed --> [*] note right of Untagged 此时磁盘占用完全没变 数据库里的引用被摘掉了 blob 仍在存储后端上 end note
磁盘没降的原因怎么确认处置
只删了 tag，manifest 还被别的 tag 引用看该 digest 下的 tag 列表是否为空删到 artifact 层面，而不是逐个删 tag
产生了无 tag 制品，但 GC 没勾选回收它们项目里按「无 tag」筛选还能看到制品GC 任务参数打开删除无 tag 制品
根本没跑过 GC系统页面里 GC 历史为空配置定时 GC，放在低峰窗口
层被其他项目或仓库共享引用GC 日志里释放字节数接近 0正常现象，内容寻址的层只存一份
对象存储开了版本控制或延迟删除桶里仍能看到历史版本配生命周期规则清理历史版本
GC 会跳过刚刚推送的数据刚推完的大层没被回收正常保护机制，避免与在传上传竞争，等下一轮
保留策略一直开着试运行执行记录里 dry run 为真确认清单后关掉试运行
配额数字与实际占用不一致项目用量与存储实际占用差距明显以存储后端用量为准，配额是记账值
 
# 项目用量：配额按 blob 记账，跨项目共享的层只算一次，和桶用量不会完全相等
curl -sS -u "$HARBOR_USER:$HARBOR_PASS" \
  'https://registry.internal/api/v2.0/projects/team-app/summary'

# 保留策略最近一次执行：先看试运行结果，确认要删的对象再关掉 dry run
curl -sS -u "$HARBOR_USER:$HARBOR_PASS" \
  'https://registry.internal/api/v2.0/retentions/12/executions?page_size=5'

# 触发一次 GC，delete_untagged 决定是否连无 tag 的制品一起回收
curl -sS -u "$HARBOR_USER:$HARBOR_PASS" -X POST \
  -H 'Content-Type: application/json' \
  -d '{"schedule":{"type":"Manual"},"parameters":{"delete_untagged":true}}' \
  'https://registry.internal/api/v2.0/system/gc/schedule'

# 判读依据：GC 日志里「释放了多少字节」才是结论，为 0 说明 blob 仍被引用
curl -sS -u "$HARBOR_USER:$HARBOR_PASS" \
  'https://registry.internal/api/v2.0/system/gc/1024/log' | tail -20

存储后端与高可用的有状态点

registry 支持本地文件系统与多种对象存储。选型的关键不是容量而是两件事：多副本时存储必须是共享的，以及客户端能否直连对象存储。后者对应一个开关：默认情况下拉取 blob 会被 302 重定向到对象存储地址，如果节点网络到不了那个地址，就必须关闭重定向让流量回到 Harbor 转发——代价是 Harbor 自己要承担全部 blob 带宽，容量规划完全变样。

存储后端支持多副本共享关键注意点适用
本地文件系统不支持单盘容量与 inode 上限，备份只能靠快照单机部署、测试环境
网络文件系统勉强锁语义与延迟放大，大量小文件性能差不建议用于生产
S3 兼容对象存储支持分片上传阈值、重定向开关、桶生命周期规则生产首选
云厂商对象存储支持各自的 driver 参数与访问凭据模型已在该云上时的自然选择
分布式文件系统支持自身运维负担高于 Harbor 本体已有平台可复用时
 
# harbor.yml 片段：外置这三样之后，其余组件才可以随意加副本
database:
  type: external
external_database:
  harbor:
    host: pg-primary.internal
    port: 5432
    db_name: registry
    ssl_mode: verify-full
external_redis:
  # jobservice 的队列也在 Redis 里，丢 Redis 等于丢掉在跑的复制与扫描任务
  host: redis-sentinel.internal:26379
  sentinel_master_set: harbor
  registry_db_index: 1
  jobservice_db_index: 2
storage_service:
  s3:
    region: cn-north-1
    bucket: harbor-prod
    regionendpoint: https://s3.internal
    secure: true
  redirect:
    # 客户端网络到不了对象存储时必须关掉，否则拉取会卡在重定向后的地址上
    disable: true
jobservice:
  max_job_workers: 10

多副本部署时还有两个容易漏的点：jobservice 的任务执行日志默认写本地磁盘，多副本下界面查不到另一副本的日志，要改成数据库存储；GC 与保留是系统级单例任务，加副本不会让它们并行，只会让调度归属更难判断。跨地域的真正高可用不要指望单实例，用独立实例加复制规则来做。

最容易踩的坑

❌
这些坑几乎每个自建仓库都会遇到一次
  • 删了一堆 tag 以为能腾出空间：没跑 GC 的话磁盘一个字节都不会降，且 GC 期间 registry 只读、推送会失败
  • GC 勾了但没打开「删除无 tag 制品」：被保留策略摘掉 tag 的那些制品永远留在磁盘上
  • 流水线里直接用管理员账号：一旦变量泄露等于整个仓库失守，机器人账号才能把影响面收敛在一个项目
  • 机器人名里的美元符号没用单引号包住：shell 展开成空串，报错却显示「用户名或密码错误」
  • 按 tag 签名：tag 被覆盖后签名与运行镜像脱钩，必须按 digest 签并配合不可变 tag 规则
  • 指望项目阻断策略挡住一切：节点已缓存或换个来源拉取时它完全不生效，必须加集群侧准入控制
  • 隔离网络里不管漏洞库：扫描一直「成功」但结论早就过期，要监控漏洞库更新时间并准备离线库
  • 只改了 Docker 的证书目录：K8s 节点用 containerd，读的是自己的仓库配置，改错地方会一直报证书不可信
  • 用对象存储却没管重定向开关：客户端直连不到桶时拉取卡住，日志里只看到 302 而没有失败原因
  • 复制规则两端都可写：同名 tag 互相覆盖，最终谁赢取决于最后一次同步，排查极其痛苦
  • 把代理缓存项目当归档仓库：缓存副本会被清理，上游删了镜像之后你也没有了
  • 推大镜像失败只怀疑 registry：先看接入层的请求体上限与读写超时，多数是 nginx 层拦下来的
