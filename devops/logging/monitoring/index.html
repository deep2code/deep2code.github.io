从日志派生指标与告警：log-based metrics 的三条路径

🏷️ 监控告警

本篇只讲一件事：从日志里派生指标和告警（log-based metrics）。监控方法论、黄金信号、RED 与 USE、SLI/SLO 与错误预算、告警分级与 on-call 排班、MTTD 与 MTTR，全部在站内 监控入门 和 可观测性三大支柱 里；Prometheus 架构与告警链路见 Prometheus 架构与运维，日志平台的索引与容量见 ELK 篇。这里假定你已经有一套指标系统，讨论的是日志和它之间那条转换管道。

先回答：什么时候该从日志出指标

结论先摆出来：直接埋点永远优于从日志派生。指标是聚合后的时间序列，单条几十字节、延迟十几秒、可以按标签精确切分；日志派生要先把原始文本搬一遍再算，成本高一到两个量级，还多了采集丢失和延迟这两个风险源。很多团队反过来做——因为「反正日志都有了」——结果是指标系统形同虚设，全部告警都压在日志平台上，日志平台一抖动整个监控就瞎。

但确实有三种情况只能靠日志：改不了代码（第三方组件、遗留系统、云服务的访问日志、Nginx 与网关的日志）；事后才发现需要这个指标，而历史日志还在保留期内，可以回溯算出过去两周的数值；需要携带高基数上下文去定位具体样本，比如不只要知道失败了 137 次，还要知道是哪 137 个订单号。

适合放进告警规则适合，评估开销恒定取决于实现路径，平台侧查询不适合高频评估

三条实现路径：采集侧转换、平台侧查询、专用工具

同一个「从日志出指标」的需求，落地位置不同，成本差几十倍。绝大多数团队默认走了最贵的那条（平台侧查询），因为它最直观：日志已经在 ES 或 Loki 里了，写个查询就出数。但每次告警评估都要扫一遍日志，评估周期 30 秒、规则 200 条，日志平台就被自己的监控打爆了。

# Vector：在采集侧把结构化日志转成指标，只把聚合结果发往 Prometheus
# 关键设计：tags 里只放低基数字段（service/route/status_class/level），
# 绝不要把 order_id、user_id、trace_id 放进 tags，那会直接引爆指标基数
sources:
  app_logs:
    type: kubernetes_logs

transforms:
  parsed:
    type: remap
    inputs: [app_logs]
    source: |
      . = parse_json!(string!(.message))
      # 把 HTTP 状态码归并成 2xx/4xx/5xx 三类，基数从数百降到 3
      .status_class = to_string(floor(to_float(.status ?? 0) / 100) ?? 0) + "xx"

  # 计数类指标：每条匹配的日志加 1
  log_counters:
    type: log_to_metric
    inputs: [parsed]
    metrics:
      - type: counter
        field: msg
        name: app_log_events_total
        namespace: logderived
        tags:
          service: "{{ service }}"
          level: "{{ level }}"
          msg: "{{ msg }}"            # msg 是稳定模板才能当标签用
      - type: counter
        field: status_class
        name: app_http_requests_total
        tags:
          service: "{{ service }}"
          route: "{{ route }}"
          status_class: "{{ status_class }}"
      # 耗时分布：histogram 的 bucket 由后端按 distribution 计算
      - type: histogram
        field: duration_ms
        name: app_request_duration_ms
        tags:
          service: "{{ service }}"
          route: "{{ route }}"

sinks:
  prom:
    type: prometheus_exporter
    inputs: [log_counters]
    address: 0.0.0.0:9598
    # flush_period_secs 决定 counter 的重置行为，设太短会让 rate 计算失真
    flush_period_secs: 60

日志告警的四类模式，以及各自的陷阱

模式怎么做陷阱修法
关键词命中日志里出现某个字符串就告警最容易做也最容易泛滥；一条 ERROR 一个告警，几分钟几百条，通道被屏蔽只对真正稀有且必须人工介入的关键词用，例如 OOM、数据一致性校验失败；其余转成比率
错误率阈值错误日志数除以总请求数超过阈值没有分母门槛时，低流量时段 3 次请求 1 次失败就是 33%，必然误报表达式里同时要求总量超过最小值，低流量接口改用绝对数量或拉长窗口
日志量突增与上周同期或前一小时比较，倍数超阈值发版、活动、批处理都会造成合法突增与上周同期比而不是与一小时前比；发布窗口内自动抑制
日志量突降量低于基线的某个比例最常被漏掉的一条；它比突增严重得多必须配，见下方说明
模式识别与新异常对 msg 做聚类，出现未见过的模板即提醒误报率高，容易在发版后刷一片新模板只作为低优先级提醒进日报，不进 on-call 通道
❌
日志量突降往往比突增更严重

突增意味着「有东西在刷屏」，这件事通常还有别的信号能发现。突降意味着两件事之一：服务已经不工作了（没有请求进来，所以没有日志），或者采集链路断了（agent 挂了、日志路径变了、磁盘满了、格式改了导致解析全丢）。第二种情况最危险，因为此时所有基于日志的告警都会静默不触发，看板一片绿，而你实际上已经失明。突降告警和关键词告警的优先级应该反过来。

为什么「出现 ERROR 就告警」是错的

这条规则几乎是每个团队日志告警的第一版，也几乎每个团队都在三个月内把它关掉了。原因不在规则本身，而在ERROR 这个级别在多数代码库里已经被污染了：参数校验失败、用户输错密码、第三方返回业务失败、重试后成功的那次失败，全都在打 ERROR（判据见 应用侧日志工程）。于是 ERROR 基线常年在每分钟几百条，一条一个告警等于自杀。

更根本的问题是告警对象错了。运维需要知道的是「用户受影响了吗、影响多大、在变好还是变坏」，这是一个带分母、有持续时间、可分级的比率；而「日志里出现了某行文本」是一个离散事件，它既不能表达严重程度，也不能表达趋势。正确的演进路径是把关键词规则逐步替换成比率规则，只给少数几个真正稀有的关键词保留即时告警。

# Prometheus 告警规则：基于采集侧派生出来的指标，而不是每次扫日志
# 三个要点：1) 比率必须有分母门槛 2) for 过滤瞬时抖动 3) 注解里带下钻链接
groups:
  - name: log-derived
    rules:
      # 先把比率算成一条记录规则，告警和看板复用同一份定义
      - record: job:log_error_ratio:5m
        expr: |
          sum by (service, route) (rate(app_log_events_total{level="ERROR"}[5m]))
          /
          sum by (service, route) (rate(app_http_requests_total[5m]))

      - alert: LogErrorRatioHigh
        expr: |
          job:log_error_ratio:5m > 0.02
          and
          sum by (service, route) (rate(app_http_requests_total[5m])) > 0.33
        for: 10m
        labels:
          severity: P1
        annotations:
          summary: "错误率超过 2% 且持续 10 分钟"
          # 分母门槛 0.33/s 约等于每分钟 20 次请求，低于这个量比率没有意义
          # 告警必须能一键下钻，否则收到告警的人还要自己拼查询、自己猜时间窗。
          # 这里用 Grafana 的 Explore 短链形式，时间范围由告警时间自动带入
          logs_url: 'https://grafana.internal/d/logs-drilldown?var-service={{ $labels.service }}&var-route={{ $labels.route }}&var-level=ERROR&from=now-30m&to=now'
          runbook: 'https://wiki.internal/runbook/log-error-ratio'

      # 突降：日志量跌到上周同期的三成以下，说明服务或采集链路出问题
      - alert: LogVolumeDrop
        expr: |
          sum by (service) (rate(app_log_events_total[10m]))
          <
          0.3 * sum by (service) (rate(app_log_events_total[10m] offset 1w))
        for: 15m
        labels:
          severity: P1
        annotations:
          summary: "日志量跌至上周同期 30% 以下，检查服务存活与采集链路"

      # 稀有关键词：这类才适合即时告警，因为它本身几乎不会出现
      - alert: OutOfMemoryLogged
        expr: increase(app_log_events_total{msg="java heap space"}[5m]) > 0
        labels:
          severity: P0
        annotations:
          summary: "出现 OOM 日志，实例可能已不可用"

实现要点：去重、抑制、以及必须带下钻链接

日志告警的可用性取决于三件工程细节，而它们通常被当成「以后再优化」。

要点不做的后果怎么做
聚合窗口与去重同一问题每个评估周期发一条，十分钟四十条按 service 加 msg 分组；Alertmanager 的 group_by 加 group_interval 控制重复节奏
抑制（inhibition）一个根因引发五种错误日志，五条告警同时炸配置抑制规则：实例不可用时抑制该实例的全部业务错误告警

携带 traceID只知道「错了」，不知道「哪一次错了」告警里带一个样本 trace_id，详见 日志指标链路关联
持续时间判定网络抖一下就告警，然后自动恢复for 至少覆盖两个评估周期；P0 可以短，P2 应该长
发布窗口抑制每次发版都收一批告警，久而久之全靠忽略CI 在发布期间打静默标记，或按 version 标签自动抑制

采集链路自身的可观测性

「采集断了而没人知道」是最常见的可观测性事故，而且它有一个恶性特征：依赖日志的告警会一起静默，所以现象不是「告警变多」而是「异常地安静」。必须给采集链路本身配一套独立的、不依赖日志的监控，并且它的告警通道要和业务告警分开。

监控项怎么取判读
agent 读取位置是否推进Filebeat 的 harvester 状态、Vector 的 component_received_events_total速率长时间为 0 而服务仍在跑，说明卡住或文件路径失配
管道丢弃计数Vector 的 component_discarded_events_total、Fluent Bit 的 retries_failed任何非零增长都要看；持续增长意味着正在丢数据
发送失败与重试agent 的 sink 错误计数与后端写入拒绝对照，能区分是网络还是后端限流
后端写入拒绝ES 的 rejected 线程池计数、Loki 的 discarded_samples_total非零就说明容量不足或标签基数超限
端到端延迟定期打一条带时间戳的心跳日志，平台侧查它的到达时间差这是唯一能覆盖整条链路的指标，其余都是局部
agent 自身资源容器 CPU 与内存、重启次数OOMKilled 反复重启时，每次重启都可能重复或丢失一段
日志量基线按 service 的日志条数速率配突降告警，这是采集故障最直接的兜底信号

Loki 与 ES 在「日志转指标」上是两套成本模型

这一点经常被混着讲，导致选型时算错账。ES 对所有字段建索引，查询靠倒排索引定位，任意字段过滤都快，代价是写入放大、存储成本高、且高基数字段会让索引膨胀。Loki 只索引标签，日志内容按块压缩存储，查询时先用标签选出块再暴力扫描内容，所以存储便宜得多，但「扫多少」直接决定查询成本和速度。

由此得出一条容易被踩的结论：Loki 的标签基数必须严格控制。把 trace_id 或 pod 以外的高基数字段放进标签，会产生海量的小 stream，写入端内存暴涨、查询端要合并成千上万个块，性能比 ES 更糟。在 Loki 里高基数字段应该留在日志正文里，靠 | json | field="x" 这种过滤表达式在扫描时筛。

索引范围全字段（按 mapping）只索引标签，内容不建索引
存储成本高，常见为原文的 1 倍以上低，压缩块存对象存储
任意字段过滤快，走倒排慢，要扫内容
高基数字段可索引但会膨胀，可设为不索引放标签会炸 stream，必须留在正文
做日志派生指标聚合查询，开销随命中文档数增长rate() 与 count_over_time()，开销随扫描字节数增长
适合高频告警评估都不适合；两者都应改为采集侧派生指标同左
选型倾向需要复杂条件检索与全文分析成本敏感、查询以「按标签加时间窗看原文」为主
 
# Loki：LogQL 里把日志转成速率，适合排查与临时看板，不适合放进高频告警
# 第一步用标签选流（这一步决定要扫多少字节），第二步才做内容过滤
sum by (route) (
  rate({service="order-api", env="prod"} | json | level = "ERROR" [5m])
)

# 带分母的错误率：分子分母都用同一个 stream，避免两次不同范围的扫描
sum(rate({service="order-api"} | json | level = "ERROR" [5m]))
/
sum(rate({service="order-api"} | json | msg = "request completed" [5m]))

# 从日志字段算分位数（unwrap 把字段当数值）
quantile_over_time(0.99,
  {service="order-api"} | json | unwrap duration_ms [5m]
) by (route)

# 反面示例：不加标签选择器、时间范围又开到 7 天，
# 这条查询会扫过全部日志块，是把 Loki 打挂的标准姿势
sum(count_over_time({env="prod"} |= "timeout" [7d]))

日志告警没有分母低流量时段必然误报，夜班被无效叫醒比率加最小请求量门槛，或低流量接口改绝对值
告警不带上下文链接处理人还要自己拼查询、猜时间窗，MTTR 直接翻倍注解里带预填过滤条件与时间范围的日志链接和样本 trace_id
用日志量当唯一健康指标日志量正常但业务已经全失败（比如全部返回缓存兜底）日志量只作为采集链路的兜底信号，业务健康看比率与延迟
日志派生指标不做采样与基数控制把 order_id 放进标签，指标基数爆炸拖垮时序库标签只放可枚举字段；高基数上下文靠 exemplar 或日志本身承载
只监控业务不监控采集链路采集断了所有日志告警一起静默，故障期间完全失明配 agent 背压、丢弃计数、写入拒绝与端到端心跳
把高频告警规则挂在 ES 或 Loki 查询上监控系统自己成为日志平台的最大负载需要进告警的指标一律前移到采集侧派生
只告突增不告突降服务静默死亡或采集断链无人发现两个方向都配，突降优先级不低于突增
❌
最容易踩的坑
  • 把高频告警规则挂在 ES 聚合或 LogQL 查询上，200 条规则每 30 秒扫一遍日志，监控系统成了日志平台的最大负载源。
  • 日志派生指标时把 order_id、trace_id 放进标签，时序库基数瞬间爆炸，这是比日志本身贵得多的错误。
  • 在 Loki 里把高基数字段设成标签，产生海量小 stream，写入端内存暴涨、查询端要合并上万个块。
  • 只配日志量突增告警不配突降，服务静默死亡或 agent 挂掉时所有日志告警一起静默，看板全绿。
  • 错误率告警没有分母门槛，凌晨三次请求一次失败就报 33%，连续几周误报后这条规则被永久静默。
  • msg 里拼了变量，导致按 msg 做的派生指标标签基数等于业务量，且规则完全无法复用。
  • Vector 或 Fluent Bit 的 counter 刷新周期设得比 Prometheus 抓取间隔短，counter 被重置，rate() 算出的值系统性偏低。
  • 只监控 agent 进程存活，不监控读取偏移是否推进；agent 活着但卡在一个被删除的文件句柄上，日志静默停止。
  • 告警没带下钻链接和样本 trace_id，收到告警的人先花五分钟拼查询，MTTR 的大头浪费在这里。
  • 一个根因引发多类错误日志，没配抑制规则，五条告警同时炸，on-call 先花时间判断它们是不是同一件事。
  • 发布期间不做静默，每次上线都收一批日志告警，久而久之整个通道被当成噪声。
  • 把日志派生指标当成埋点的替代品长期使用，指标系统始终建不起来，日志平台一抖动整个监控就瞎。
