日志体系：从散落到集中

🏷️ 日志

线上报错了，要登好几台服务器 grep 日志，找半天找不到。日志集中管理，一个地方搜所有日志，效率高很多。

flowchart LR A[应用日志] --> B[Filebeat] B --> C[Kafka] C --> D[Logstash] D --> E[Elasticsearch] E --> F[Kibana 搜索]

线上报错，找日志找半天

⚠️
你遇到的问题

用户说报错了，你要登 5 台服务器，一台台 grep，找半小时。

怎么解决？搭一套日志收集系统，所有日志集中到 Elasticsearch，按 trace_id 一搜就出来。

# ELK 栈
Filebeat：采集日志
Kafka：缓冲
Logstash：处理
Elasticsearch：存储搜索
Kibana：展示

日志太多，磁盘满了

⚠️
你遇到的问题

日志越写越多，服务器磁盘满了，服务直接挂了。

怎么解决？配置日志轮转，保留 7-14 天，自动删老日志，别让日志把磁盘吃满。

# Linux 日志轮转
/etc/logrotate.d/myapp
按天切分，保留 14 天，自动压缩

日志级别

级别 什么时候用 例子
DEBUG 开发调试用 变量值、流程节点
INFO 正常业务流程 用户登录、下单成功
WARN 不影响流程但要注意 重试了一次、缓存未命中
ERROR 出错了要处理 接口报错、数据库连接失败

新手最容易踩的坑

❌
避坑指南
  • 日志一定要加 trace_id，不然跨服务调用根本串不起来
  • 别把敏感信息打到日志里，密码、身份证、手机号要脱敏
  • ERROR 一定要真的是错误，别啥都打 ERROR，不然没人看
  • 日志格式要规范，用 JSON，方便机器解析
