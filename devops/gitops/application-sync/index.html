Argo CD 同步机制与漂移自愈

🏷️ 应用同步

Argo CD 的同步（sync）常被理解成「Git 一改就 kubectl apply 一遍」。这个理解会让你在第一次遇到「明明没人动过，应用却永远显示 OutOfSync」时彻底失去方向。同步的本质是一个持续收敛的三方 diff，而它最难的部分不是把清单推上去，而是判断集群里的某个字段变化算不算漂移。

本文只讲同步机制本身：diff 从哪来、三个同步开关的精确语义、状态机、波次与 hooks、性能、救火姿势和失败排查。GitOps 的原则与协作纪律、从传统流水线迁移的步骤、Argo CD 自身的高可用部署，分别见站内《GitOps 核心原则》《ArgoCD 安装配置》两篇；滚动更新、探针、金丝雀这些部署策略层面的内容见站内 Kubernetes 与 CI/CD 部署策略两篇，这里不展开。

一、同步到底在比较什么

application-controller 每个周期（默认 timeout.reconciliation 为 180 秒，配了 webhook 则由事件触发）做三件事：让 repo-server 把仓库渲染成最终清单、从集群缓存里取出对应的 live 对象、结合上次同步留下的所有权记录算出差异。渲染是必经步骤——仓库里放的是 Helm chart 或 kustomize 目录，diff 比较的是渲染产物而不是文件文本，所以「文件没变」并不代表「渲染结果没变」（values 引用了外部文件、chart 依赖没锁版本都会让渲染结果漂移）。

第三方（所有权记录）是最容易被忽略的一环。客户端 apply 时，Argo CD 靠 kubectl.kubernetes.io/last-applied-configuration 判断「哪些字段是我写的」，只有我写过的字段才参与三方合并；切到 Server-Side Apply 后，这个职责交给 API Server 的 managedFields。没有这一份记录，任何别人加的字段都会被当成漂移。

二、「永远 OutOfSync」的真正原因：谁改的字段不算漂移

这是 Argo CD 运维里最高频的问题。它几乎从来不是 Argo CD 的 bug，而是集群里有好几个写入者在同一个对象上留下痕迹：

差异字段谁写进去的典型表现算漂移吗处理方式
spec.replicasHPA 控制器仓库写 2，集群是 7，diff 永不为空不算仓库里干脆删掉 replicas 字段；或 ignoreDifferences 忽略 /spec/replicas
多出一个容器Istio / Linkerd 的注入 webhookcontainers 数组长度不一致不算jqPathExpressions 精确剔除注入的容器；或开 SSA 让 webhook 拥有该元素
service 的云厂商 annotation、status.loadBalancer云 service 控制器LB ID、EIP 等被回填不算忽略对应 annotation 前缀
protocol: TCP、terminationMessagePath、imagePullPolicyAPI Server defaulting清单里没写但 live 里有不算Argo CD 内置 normalizer 已处理大部分；开 SSA 后基本绝迹
caBundlecert-manager 的 ca-injectorwebhook 配置反复变绿变黄不算按 jqPathExpressions 忽略 .webhooks[]?.clientConfig.caBundle
有人 kubectl edit 改的镜像人集群比仓库新算selfHeal 改回去，并要求当事人回写仓库
集群里有、仓库里没有的对象历史遗留或人手工创建被标为需要 prune算确认后 prune，或纳入仓库管理

忽略配置写在 Application 的 ignoreDifferences 里。两种定位方式的取舍是：jsonPointers 简单但处理数组几乎无能为力（下标会随注入顺序变化），jqPathExpressions（v2.1+）能按条件筛选数组元素，代价是表达式本身要测。

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: payment-api
  namespace: argocd
spec:
  project: payments
  source:
    repoURL: https://git.internal/infra/payment-api.git
    targetRevision: main          # 生产建议锁 tag 或 commit，不要长期跟分支
    path: overlays/prod
  destination:
    server: https://kubernetes.default.svc
    namespace: payment
  syncPolicy:
    automated:
      prune: true                 # 仓库删了就删集群，第一次开必须先 dry-run
      selfHeal: true              # 集群被手改会被改回去
      allowEmpty: false           # 渲染结果为空时拒绝同步，防止一次性删光（关键保险）
    syncOptions:
      - ServerSideApply=true      # 字段所有权交给 API Server 仲裁
      - RespectIgnoreDifferences=true   # 同步时也不要把被忽略的字段写回去
      - ApplyOutOfSyncOnly=true   # 只提交有差异的对象，大应用省一大截时间
      - PruneLast=true            # 删除动作排在新资源创建成功之后
      - PrunePropagationPolicy=foreground
      - CreateNamespace=false     # 命名空间建议由平台侧统一管，不要让应用自己造
    retry:
      limit: 5
      backoff:
        duration: 10s
        factor: 2
        maxDuration: 5m           # 指数退避，避免 webhook 抖动时把 API Server 打爆
  ignoreDifferences:
    # HPA 管 replicas：按 jsonPointer 忽略最稳
    - group: apps
      kind: Deployment
      jsonPointers:
        - /spec/replicas
    # sidecar 注入：用 jq 精确剔除注入进来的那个容器再比对
    - group: apps
      kind: Deployment
      jqPathExpressions:
        - '.spec.template.spec.containers[] | select(.name == "istio-proxy")'
    # cert-manager 回填的 caBundle
    - group: admissionregistration.k8s.io
      kind: ValidatingWebhookConfiguration
      jqPathExpressions:
        - '.webhooks[]?.clientConfig.caBundle'
    # 更省事的写法：凡是这个 manager 写的字段都不算漂移（v2.6+）
    - group: apps
      kind: Deployment
      managedFieldsManagers:
        - kube-controller-manager
⚠️
只配 ignoreDifferences 是半个方案

ignoreDifferences 只影响差异计算，不影响实际写入。也就是说状态会变成 Synced，但下一次同步依然会把 spec.replicas 按仓库里的值写回去，于是 HPA 扩到 7、Argo CD 压回 2、HPA 再扩上去——你会在监控上看到副本数反复抖动。必须同时加 RespectIgnoreDifferences=true，这一条漏掉的概率极高。

维度ignoreDifferencesServer-Side Apply
作用点只改变 diff 结果改变实际提交的字段集合
粒度手工指定 group/kind/name 与路径按 field manager 自动仲裁，无需枚举
数组字段jsonPointer 基本无解，需要写 jq声明了 listType=map 的数组能按 key 正确合并
大对象限制仍受 last-applied 注解 262144 字节上限不写该注解，可绕开上限（大 CRD 的唯一解）
版本要求全版本；jqPathExpressions 需 v2.1+Argo CD v2.5+ 稳定，K8s 1.22+
典型副作用忽略范围写宽了会把真实漂移一起藏掉首次切换时会有一次 field manager 迁移造成的 diff，需要人工确认一遍

三、automated、prune、selfHeal 的精确语义

三个开关经常被含糊地说成「自动化程度」，实际上它们管的是三件完全不同的事，而且默认全部关闭。

开关默认精确语义不开的后果开了的风险
automated关检测到 desired 与 live 有差异时自动发起一次同步Git 合了但集群不变，只是标 OutOfSync，漂移长期积压坏提交会在几十秒内自动上线，必须靠 PR 评审和渲染校验兜住
prune关删除「属于本 Application 但渲染产物里已不存在」的对象仓库里删掉的资源会永远留在集群里，成为没人知道来历的幽灵对象渲染出错导致清单为空时会尝试删掉整个应用，必须配 allowEmpty: false
selfHeal关live 被非 Argo CD 的写入者改动后，主动改回仓库状态（默认 5 秒抖动窗口）手改能长期存活，集群与仓库悄悄分叉救火时你的临时改动会被吃掉，调试前必须先暂停
allowEmptyfalse允许渲染结果为空时仍然同步—设成 true 且开了 prune，等于给自己装了一个删库开关
组合运维模式行为适用要留心什么
三个都关纯人工闸门只做差异可视化，同步由人触发强审批的金融类生产、灰度期漂移会堆积，需要给 OutOfSync 时长配告警
automated自动上线、不自愈Git 是唯一变更入口，但手改不会被纠正staging、联调环境最容易积累「只有集群里有」的配置，事故复盘时找不到来源
automated + selfHeal推荐的生产基线集群任何手改都会被拉回仓库状态大部分生产应用调试必须先改手动或打暂停注解
automated + selfHeal + prune完整 GitOps仓库是绝对真相，多余资源会被删平台组件、整套环境首次开启先 dry-run；对 PVC、Secret、CRD 单独加保护注解

资源级的保护注解比全局开关更实用：在不希望被删的对象上加 argocd.argoproj.io/sync-options: Prune=false，即使 Application 开了 prune 也会跳过它。同理，Delete=false 能让这个对象在 Application 被删除时保留下来——数据库的 PVC 一定要加这两条。

sequenceDiagram participant Dev as 值班工程师 participant API as K8s API Server participant Ctl as application-controller participant Git as Git 仓库 Dev->>API: kubectl edit deploy 临时把镜像换成 hotfix API-->>Ctl: watch 事件，live 对象已变化 Ctl->>Ctl: 重算三方 diff，标记 OutOfSync Note over Ctl: selfHeal 开启，默认 5 秒抖动窗口后触发同步 Ctl->>Git: 取 HEAD 渲染期望清单 Ctl->>API: apply 把镜像改回仓库里的旧版本 API-->>Dev: 线上又回到了故障版本 Note over Dev,Git: 正确顺序是先把 Application 改手动或打暂停注解，改完再回写仓库

四、状态机，以及同步状态与健康状态必须分开看

stateDiagram-v2 [*] --> Synced Synced --> OutOfSync: 新提交或集群漂移 OutOfSync --> Syncing: automated 触发或人工点击 Syncing --> Synced: 全部对象 apply 成功 Syncing --> SyncFailed: apply 被拒绝或 hook 失败 SyncFailed --> Syncing: 按 retry 退避重试 SyncFailed --> OutOfSync: 重试次数耗尽，等人介入 Synced --> Progressing: 滚动更新进行中 Progressing --> Healthy: 新副本全部就绪 Progressing --> Degraded: 探针失败或超过 progressDeadlineSeconds Degraded --> OutOfSync: 修复提交合入 Synced --> Paused: 改手动同步或打暂停注解 Paused --> OutOfSync: 恢复自动同步 Healthy --> Synced: 回到稳定态

Argo CD 的界面上有两个独立的灯：Sync Status 说的是「集群里的对象和仓库渲染结果一致吗」，Health Status 说的是「这些对象实际跑起来了吗」。把它们混为一谈是线上事故的常见诱因。

组合实际含义该不该告警
Synced + Healthy正常稳态不告警
Synced + Progressing清单已生效，副本在替换持续超过 10 分钟才告警（对齐 progressDeadlineSeconds）
Synced + Degraded最危险的组合：清单完全正确，但镜像拉不到 / 探针不过 / OOM 反复重启必须告警，这是「同步成功但服务挂了」
OutOfSync + Healthy手动模式下有待同步变更，或忽略规则没配好手动模式下正常；自动模式下持续 OutOfSync 说明同步失败或忽略缺失
Unknown仓库拉不动、凭证过期、渲染报错、集群连不上必须告警，通常是平台侧问题
Missing渲染里有但集群里建不出来：CRD 未注册、命名空间不存在、被策略引擎拦下必须告警

自定义资源是健康判定的盲区：Argo CD 内置了 Deployment、StatefulSet、Ingress 等常见 kind 的健康逻辑，但对你自己或 Operator 引入的 CR，没有健康检查时默认判为 Healthy。于是出现「Synced + Healthy 一片绿，实际 Redis 集群根本没起来」的假绿。补法是在 argocd-cm 里给这个 kind 写一段 Lua：

apiVersion: v1
kind: ConfigMap
metadata:
  name: argocd-cm
  namespace: argocd
data:
  # 键名格式：resource.customizations.health.<group>_<kind>
  resource.customizations.health.redis.redis.opstreelabs.in_RedisCluster: |
    hs = {}
    -- 没有 status 说明 Operator 还没处理，判为 Progressing 而不是 Healthy
    if obj.status == nil then
      hs.status = "Progressing"
      hs.message = "等待 Operator 写入 status"
      return hs
    end
    if obj.status.readyLeaderReplicas == nil or obj.status.readyFollowerReplicas == nil then
      hs.status = "Progressing"
      hs.message = "副本数尚未上报"
      return hs
    end
    if obj.status.readyLeaderReplicas == obj.spec.clusterSize then
      hs.status = "Healthy"
      hs.message = "leader 副本全部就绪"
      return hs
    end
    hs.status = "Degraded"
    hs.message = "leader 就绪数不足"
    return hs
  # 顺带把巨型 CRD 的 diff 噪声压掉
  resource.compareoptions: |
    ignoreAggregatedRoles: true

五、同步波次与 hooks：顺序是怎么来的

Argo CD 内部先按 kind 有一个固定的默认顺序（Namespace、CRD 之类的基础对象排在前面），但跨 kind 的业务依赖必须靠 argocd.argoproj.io/sync-wave 显式表达。波次是整数，可以为负，同一 wave 内部并发提交，上一个 wave 的资源达到 Healthy 后才进入下一个 wave——这也意味着 wave 用多了同步耗时会线性增长。

wave放什么为什么必须在前
-3Namespace、ResourceQuota、PriorityClass后面所有对象都要落在命名空间里
-2CRD、Operator 本身CR 在 CRD 注册完成前提交会直接报 no matches for kind
-1ServiceAccount、RBAC、Secret、ConfigMap、PVCPod 启动时就要挂载，晚了会卡在 ContainerCreating
0（默认）Deployment、StatefulSet、Service主体工作负载
1Ingress、HPA、PDB、ServiceMonitor要引用已经存在的 Service
2CronJob、数据初始化任务依赖服务已可用
hook 阶段执行时机失败后果适合放不要放
PreSync所有普通资源提交之前阻塞整次同步，应用完全不更新幂等、可重跑、向后兼容的数据库迁移（加列、加索引）删列改类型的破坏性迁移、不可重跑的一次性脚本
Sync与普通资源一起按 wave 穿插执行影响所在 wave 及之后的 wave需要卡在特定波次之间的初始化耗时超过几分钟的任务
PostSync所有资源变为 Healthy 之后不会回滚已生效的变更，只把 Application 标成 SyncFailed冒烟测试、缓存预热、发布通知长耗时批处理，会让应用长期停在 Syncing 阻塞后续同步
SyncFail同步失败后—告警、清理中间产物、解锁迁移表自动回滚（回滚应由人决策）
PostDeleteApplication 被删除后（v2.10+）—清理外部资源，比如云上的 DNS 记录删数据库这类不可逆动作
apiVersion: batch/v1
kind: Job
metadata:
  name: payment-db-migrate
  annotations:
    argocd.argoproj.io/hook: PreSync
    # 成功后删掉旧 Job，否则同名 Job 会因为 spec 不可变而 apply 失败
    argocd.argoproj.io/hook-delete-policy: BeforeHookCreation
    argocd.argoproj.io/sync-wave: "-1"
spec:
  backoffLimit: 2          # 失败重试 2 次；前提是迁移脚本幂等
  activeDeadlineSeconds: 600   # 必须设，否则卡住的迁移会让同步永远悬着
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: migrate
          image: registry.internal/payment-api:v2.14.3   # 与应用同一镜像，避免版本错配
          command: ["/app/migrate", "up"]
          env:
            - name: DB_DSN
              valueFrom:
                secretKeyRef:
                  name: payment-db
                  key: dsn
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: payment-data
  annotations:
    # 双保险：开了 prune 也不删，Application 删除时也保留
    argocd.argoproj.io/sync-options: Prune=false,Delete=false
spec:
  accessModes: ["ReadWriteOnce"]

    requests:

六、大资源集的同步性能

同步耗时几乎与「对象数」线性相关，因为默认每个对象都要走一次服务端预演加一次提交。下面这几种症状对应的是完全不同的瓶颈，别一上来就加副本：

症状瓶颈在哪处理手段量级参考
Application 数量上千后控制器 CPU 常态打满每个 app 按 180 秒周期做全量 refresh配 Git webhook 改成事件驱动，并调大 timeout.reconciliation；按 shard 拆控制器副本轮询压力可降一个数量级
单个 app 同步要好几分钟对象数多，每个都做预演加提交ApplyOutOfSyncOnly=true对象数千、真实变更只有几个时，耗时从分钟级回到秒级
点了刷新半天不出 diffrepo-server 渲染慢或缓存没命中加 repo-server 副本；固定 chart 依赖版本；避免每次渲染都去拉外部资源渲染是 CPU 密集，副本数按并发 app 数估
提交大 CRD 报 annotation too longlast-applied 注解受 262144 字节上限开 ServerSideApply=true，或对该资源加 Replace=trueschema 上 MB 的 CRD 必踩
同步过程中 API Server 限流报 429并发提交过猛降低 kubectl.parallelism.limit，拉长 retry 退避默认并行度 16
一次误同步影响整个环境所有服务塞在一个 Application 里按团队或组件拆 Application，用 ApplicationSet 批量生成爆炸半径从「整个环境」缩到「单个服务」

七、救火时怎么正确地「停下来」

❌
不要把 application-controller 缩容到 0

这是流传很广的应急做法，代价极大：所有应用同时失去自愈和状态上报，界面上的健康状态全部变成陈旧数据，你连「现在集群是什么样」都看不到；恢复副本的瞬间又会涌入一大批积压的同步，把 API Server 打满。正确做法是只针对出问题的那个 Application 关掉自动同步，影响范围收敛到一个应用。

场景常见错误做法正确做法
要临时改一个线上参数直接 kubectl edit，被 selfHeal 吃掉先把该 app 的 sync-policy 设为 none，再改集群，救火结束后立刻把改动回写仓库并恢复自动同步
要冻结一批应用的变更停控制器逐个改手动同步，或在 AppProject 上加同步窗口（sync window）限制变更时段
发了坏版本要退在集群里把镜像改回去git revert 那次提交再同步；实在来不及可以 argocd app rollback，但它会让集群与仓库不一致，事后必须补一次 revert 提交
误删了资源手工从备份重建直接同步一次，仓库还在，资源就会被重建（这正是 GitOps 的价值）
prune 删错了东西手工 apply 旧清单revert 那次删除提交后同步，保持仓库为唯一真相
hook Job 卡住不动，同步悬挂反复点 Terminate先 terminate 同步操作，再删掉卡住的 Job，修好 activeDeadlineSeconds 后重新同步

# 1) 先看整体：sync 状态、health 状态、conditions 三样一起看
argocd app get payment-api --show-operation

# 2) 到底差在哪个字段。--local 可以拿本地目录先比，改之前就知道会产生什么 diff
argocd app diff payment-api
argocd app diff payment-api --local overlays/prod

# 3) 不确定 prune 会删什么，一定先预演。输出里 pruned 开头的行就是待删对象
argocd app sync payment-api --prune --dry-run

# 4) 救火：关掉自动同步（只影响这一个应用），改完再开回来
argocd app set payment-api --sync-policy none
# ... 处理完成后 ...
argocd app set payment-api --sync-policy automated --self-heal --auto-prune

# 5) 没有 CLI 时用 kubectl 读关键字段，适合放进巡检脚本
kubectl -n argocd get application payment-api \
  -o jsonpath='{.status.sync.status}{"  "}{.status.health.status}{"  "}{range .status.conditions[*]}{.type}={.message}{"\n"}{end}'

# 6) 卡在 Syncing：先终止当前操作，再查是哪个 hook 没退出
argocd app terminate-op payment-api
kubectl -n payment get jobs -l argocd.argoproj.io/instance=payment-api

# 7) 渲染类报错去 repo-server；apply 类报错去 application-controller
kubectl -n argocd logs deploy/argocd-repo-server --tail=200 | grep -i payment-api
kubectl -n argocd logs sts/argocd-application-controller --tail=200 | grep -i payment-api

# 8) 发布历史与回滚（回滚后必须补一次 git revert，否则仓库与集群长期不一致）
argocd app history payment-api
argocd app rollback payment-api 42

argocd app get 的输出里，最值得先看的是 CONDITIONS 一列：ComparisonError 指向渲染或仓库访问，SyncError 指向 apply 被拒，SharedResourceWarning 说明同一个对象被两个 Application 同时纳管（这会导致两边互相覆盖，必须先解决归属），OrphanedResourceWarning 说明命名空间里有不属于任何 Application 的对象。

九、反模式

反模式为什么出现真实代价该怎么做
应用永远 OutOfSync，索性把告警关掉不知道是别的控制器写的字段真实漂移彻底失去可观测性，事故时才发现集群早已分叉定位字段后配 ignoreDifferences 加 RespectIgnoreDifferences，把状态治理干净再恢复告警
开了 prune 但没做资源保护照抄示例配置一次渲染错误或路径写错就可能删掉 PVC 和 SecretallowEmpty: false + 关键资源 Prune=false,Delete=false + 首次 dry-run
集群里手改完不回写仓库救火后没人收尾下一次同步把修复覆盖掉，故障二次复发把「回写仓库」写进故障处理流程的关闭条件
整个环境几十个服务放一个 Application图省事一次同步失败全环境标红，diff 巨大无法评审，同步耗时几分钟按服务或团队拆，用 ApplicationSet 批量生成
用 PostSync 跑长耗时任务把 hook 当定时任务用应用长期停在 Syncing，后续同步全部堆积长任务改成独立 CronJob 或工作流引擎，hook 只做短校验
救火时停掉 application-controller以为这是最快的止血全量应用失去自愈与状态上报，恢复时同步风暴只对目标应用关自动同步
targetRevision 长期指向 main 分支方便无法回答「现在生产跑的是哪次提交」，别人合入即上线生产锁 tag 或 commit，由 promote 动作显式推进
自定义资源不写健康检查不知道默认判 Healthy一片绿的假象，组件根本没起来在 argocd-cm 里补 Lua 健康检查
❌
最容易踩的坑
  • 配了 ignoreDifferences 忽略 spec.replicas，却忘了 RespectIgnoreDifferences=true，结果 Argo CD 和 HPA 互相改副本数，线上副本数来回抖动。
  • allowEmpty 保持默认 false 才安全。一旦设成 true 又开了 prune，任何让渲染产物变空的错误（path 写错、分支被删）都会删光整个应用。
  • CRD 没有设负数 sync-wave，第一次部署 Operator 时 CR 先提交，同步失败并报 no matches for kind，重试几次侥幸成功，于是这个隐患一直留着。
  • PreSync 的迁移 Job 不加 hook-delete-policy: BeforeHookCreation，第二次同步时同名 Job 因为 spec 不可变直接 apply 失败，整次同步被阻塞。
  • 迁移 Job 不设 activeDeadlineSeconds，脚本拿不到锁时会永远等下去，Application 悬在 Syncing，后续所有提交都上不去。
  • 两个 Application 纳管了同一个对象（常见于 base 被两个 overlay 同时引用），两边轮流把对方的写入覆盖掉，界面上表现为状态反复跳动，看 SharedResourceWarning 才能定位。
  • 把 Synced 当成「发布成功」。Synced + Degraded 才是最该告警的组合：清单完全正确，但镜像拉不到或探针不过，服务实际不可用。
  • 自定义资源没写健康检查，Argo CD 直接判 Healthy，于是 PostSync 的冒烟测试在组件还没起来时就跑了，测出一堆莫名其妙的失败。
  • 大 CRD 走客户端 apply，报 metadata.annotations: Too long: must have at most 262144 bytes，很多人以为是 CRD 写错了，其实只要换成 Server-Side Apply。
  • retry 没配退避，webhook 抖动期间 Argo CD 每秒重试，把 API Server 的请求队列打满，连带影响其他控制器。
  • 数据库 PVC 没加 Delete=false，有人误删 Application，级联把 PVC 一起带走了。
  • argocd app rollback 之后没有补 git revert，仓库还是坏版本，下一次任何人触发同步都会把故障版本再发一遍。
