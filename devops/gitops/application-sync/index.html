Application 管理与同步策略

🏷️ ArgoCD,持续交付

Application CRD：GitOps 的基本单元

装完 ArgoCD 之后，你管理的最小对象不是 Deployment、不是 Pod，而是 Application——ArgoCD 定义的 CRD。

一个 Application 描述了"Git 仓库里的哪个目录"应该"部署到集群的哪个命名空间"。同步策略、健康检查、回滚、自动调谐，全挂在这个对象上。我的经验是把它理解成一个"部署单元"比理解成"应用"更准确——它可以是一个微服务，也可以是一组 CRD，甚至是整个命名空间的所有资源。

Application 的设计遵循 K8s 的标准范式：spec.source 是期望（从哪来），spec.destination 是去哪，status 是观测（当前同步状态、健康状态）。application-controller 持续做 diff，这就是上一篇讲的调谐循环的具体落地。

同步状态机：从 Unknown 到 Synced

每个 Application 有两个正交状态：Sync Status（是否与 Git 一致）和 Health Status（部署是否健康）。理解这个二维矩阵是排查一切问题的钥匙。

四个组合各自的含义和我平时的处理优先级：

Sync StatusHealth含义我怎么处理
SyncedHealthyGit 与集群一致，资源正常不用管，这就是目标态
SyncedDegradedmanifest 已 apply，但 Pod 起不来kubectl describe 看 events，多半是探针/镜像问题
OutOfSyncHealthyGit 有新提交还没部署确认是预期内延迟还是同步卡住
OutOfSyncDegraded既有差异又不健康最棘手，先修 Degraded 再谈同步

同步策略：自动 vs 手动，何时开启 selfHeal

Application 的 syncPolicy 是整个 GitOps 自动化的开关。它有三个关键旋钮：

  • automated：开启后，Git 一有新提交就自动同步。不开就只能在 UI/CLI 手动点 Sync。
  • prune：开启后，Git 里删掉的资源也会被从集群删除。不开则只增不删，容易留垃圾。
  • selfHeal：开启后，集群里被手动 kubectl edit 改过的漂移会被自动纠正。生产环境强烈建议开启，这是 GitOps"持续调谐"原则的直接落地。
# 完整的 Application 定义：自动同步 + 自愈 + 裁剪
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: checkout-service
  namespace: argocd
spec:
  project: production
  source:
    repoURL: https://github.com/example/gitops-config.git
    targetRevision: main
    path: overlays/production/checkout
  destination:
    server: https://kubernetes.default.svc
    namespace: checkout
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=true          # 命名空间不存在自动建
      - PrunePropagationPolicy=foreground
      - PruneLast=true                 # 先建新再删旧，减少中断
    retry:                             # 同步失败自动重试
      limit: "3"
      backoff:
        duration: 5s
        factor: 2
        maxDuration: 3m

实战中容易踩坑的是 PruneLast=true：它让 ArgoCD 先 apply 新资源、等健康后再删除旧资源，避免滚动更新时短暂中断。但如果你部署的是 StatefulSet，要谨慎——StatefulSet 的更新顺序由它自己控制，PruneLast 对它意义不大。

我踩过的坑：selfHeal 把紧急修复冲掉

有次生产事故，我紧急 kubectl scale 把副本数从 3 临时调到 5 顶住流量，结果 3 分钟后 ArgoCD 检测到漂移，自动把副本数改回 3，流量直接打满。正确姿势是先 argocd app pause <name> 再动手，救完把改动写回 Git 再 resume。临时救急不写回 Git，就是在制造下一次事故。

Sync Waves：控制多资源部署顺序

一个 Application 经常包含几十上百个资源（Namespace、CRD、Deployment、Service、ConfigMap）。ArgoCD 默认按字母序 apply，但真实世界里必须先建 Namespace 再建 Deployment、先装 CRD 再装 CR。这就是 Sync Waves 的用武之地——用注解给资源分组，数字小的先 apply。

# 用注解 argocd.argoproj.io/sync-wave 控制顺序
# wave=0: 先建命名空间和 CRD
apiVersion: v1
kind: Namespace
metadata:
  name: checkout
  annotations:
    argocd.argoproj.io/sync-wave: "0"
---
apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: checkouts.checkout.example.com
  annotations:
    argocd.argoproj.io/sync-wave: "0"
spec:
  group: checkout.example.com
  names: {kind: Checkout, plural: checkouts}
  scope: Namespaced
  versions: [{name: v1, served: true, storage: true}]
---
# wave=1: 再部署 ConfigMap 和 Secret（应用启动要读配置）
apiVersion: v1
kind: ConfigMap
metadata:
  name: checkout-config
  namespace: checkout
  annotations:
    argocd.argoproj.io/sync-wave: "1"
data:
  LOG_LEVEL: info
---
# wave=2: Deployment 排在这一波（依赖前面所有资源就绪）
apiVersion: apps/v1
kind: Deployment
metadata:
  name: checkout
  namespace: checkout
  annotations:
    argocd.argoproj.io/sync-wave: "2"
spec:
  replicas: 3
  selector: {matchLabels: {app: checkout}}
  template:
    metadata: {labels: {app: checkout}}
    spec:
      containers:
        - name: checkout
          image: registry.example.com/checkout:v1.4.2
          ports: [{containerPort: 8080}]

Waves 不仅控制 apply 顺序，还控制 prune 顺序——删除时 wave 大的先删。理解这一点，你就能优雅地实现"先下线流量再删 Pod"这类编排。

用 CLI 做日常运维

Web UI 适合看，脚本化运维还是要靠 CLI。下面是日常高频操作：

# 列出所有 Application 及其状态
argocd app list

# 查看某个应用的详细同步状态和健康状况
argocd app get checkout-service

# 手动触发一次同步（不开 automated 时用）
argocd app sync checkout-service

# 强制丢弃集群中的漂移，完全按 Git 重建（危险操作前确认）
argocd app sync checkout-service --prune

# 回滚到上一次成功的同步版本
argocd app rollback checkout-service

# 暂停/恢复自动同步（紧急止血时用）
argocd app pause checkout-service
argocd app resume checkout-service

# 查看应用的部署历史
argocd app history checkout-service

最佳实践

  • 生产环境默认开启 selfHeal + prune：这两个开关是 GitOps"持续调谐"原则的执行器。不开启 selfHeal，GitOps 就退化成"半自动部署"，漂移无人管。
  • 用 Sync Wave 编排复杂依赖：涉及 CRD、数据库迁移、配置下发的场景，显式声明 wave 比依赖字母序可靠得多。
  • 给同步失败配置告警：ArgoCD 自带 metrics（argocd_app_sync_status、argocd_app_health_status），接到 Prometheus + Alertmanager，同步失败 5 分钟未恢复就告警。
  • 避免一个 Application 管太多资源：单个 Application 包含的资源建议不超过 100 个。否则一次同步会触发大规模 apply，排错困难，同步耗时也长。按微服务拆分。
  • 用 retry 应对短暂失败：镜像拉取超时、CRD 尚未就绪这类短暂错误，靠 retry + backoff 自动恢复，比人工介入更高效。

常见问题 FAQ

Q1：开启了 automated 同步，为什么 Git 推了变更集群却没反应？

按这个顺序排查：(1) ArgoCD 能访问到你的 Git 仓库吗？argocd repo list 看连接状态；(2) Application 的 spec.source.targetRevision 指对分支了吗？默认是 master，你的仓库可能是 main；(3) 是不是被 syncPolicy 里的 manual 模式挡住了？(4) ArgoCD 默认 3 分钟轮询一次，开 Webhook 才能秒级同步。

Q2：selfHeal 会不会把我紧急修复的配置也冲掉？

会，这是它的设计预期。如果你确实需要临时改集群救急，先 argocd app pause <name> 暂停自动同步，改完验证后，要么把改动写回 Git 再 resume，要么直接 resume 让它把你的临时改动覆盖掉。临时救急不写回 Git，就是在制造下一次事故。

Q3：Sync 失败卡在 OutOfSync 状态，怎么定位？

用 argocd app get <name> 看哪些资源报错。常见原因：(1) RBAC 不足——ArgoCD 的 ServiceAccount 没有创建该资源的权限；(2) CRD 未安装——你部署了某个 CRD 的 CR，但 CRD 本身还没装；(3) 资源配额不足——命名空间 ResourceQuota 卡住了。Web UI 的 Resource Tree 视图能直接看到红色报错节点。

Q4：可以只同步部分资源吗？不想每次都把所有资源重新 apply。

可以。argocd app sync <name> --resource Deployment:checkout 只同步指定类型的资源。更常见的做法是用 syncOptions 里的 Replace=true 或 ServerSideApply=true，让 ArgoCD 只处理有差异的字段。默认情况下 ArgoCD 就是做 diff 的，没变化的资源不会重复 apply。

总结

Application 是 ArgoCD 的灵魂，syncPolicy 是自动化的开关，Sync Wave 是编排的手。三者组合起来，你就拥有了一个"Git 一变、集群自动跟着变、漂移自动纠正、失败自动重试"的部署系统。下一篇我们把视角放大——一个仓库、多个环境、几十个微服务，怎么组织才不会乱成一锅粥。
