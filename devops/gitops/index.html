GitOps 的模型与纪律：拉取式交付的四条原则与治理边界

🏷️ GitOps

关于 GitOps 最流行的误解是把它等同于「把 YAML 放进 Git 仓库，然后让流水线去 apply」。按这个理解做完，你会发现它既没有解决版本混乱，也没有降低凭证风险，只是给原来的部署脚本换了个说法。GitOps 真正的内核是一套控制论意义上的闭环：期望状态在仓库里，实际状态在集群里，一个常驻控制器不停地比较两者并驱动收敛。这篇讲模型和纪律——四条原则怎么逐条落到工程约束上、拉取式相比推送式究竟换来了什么、以及配套的治理规则和它明确不适合的边界。

四条定义性原则，以及只做到一半的样子

OpenGitOps 把 GitOps 归纳为四条原则。这四条的价值不在于背下来，而在于每一条都能反过来当成检查项：做到一半会长什么样，缺了会付出什么代价。

原则工程含义常见的半成品状态缺失后的代价
声明式描述系统的期望状态用数据表达，而不是用一串操作步骤表达清单里还留着 initContainer 跑自定义脚本拼配置，或者部署前要人工执行三条命令期望状态无法被机器完整比较，diff 永远不准，自愈也就无从谈起
版本化且不可变期望状态存在带完整历史的仓库里，每次变更都是一次新提交用 latest 或可移动的分支名当镜像 tag；有人 force push 覆盖历史同一个提交在不同时间渲染出不同结果，回滚到某个提交不能保证回到当时的运行态
自动拉取并应用集群内的控制器主动取仓库内容并应用，无需外部推送仓库变更后靠 webhook 触发 CI 去执行 apply凭证仍在集群外，私有网络集群仍需开放入口，本质还是推模式
持续调和控制器循环比较期望与实际，差异存在就持续纠正只在仓库有新提交时同步一次，集群侧漂移不检测手工改动长期存活形成雪花配置；故障恢复后集群状态不确定

第四条最容易被跳过，也最能体现 GitOps 与传统 CD 的差异。它不是「部署一次」，而是「持续维持」。这套调和思路本身就是 Kubernetes 控制器的工作方式，GitOps 只是把控制循环的输入源从集群内的 etcd 换成了集群外的 Git 仓库。控制循环与水平触发的实现细节详见站内 Kubernetes 专题，这里不再展开。

推送式与拉取式：最本质的差异是谁发起部署

很多对比文章会列一堆「可追溯、易回滚」之类的好处，但那些收益本质上来自「配置进了版本库」，跟拉取式没有必然关系。真正只有拉取式才能拿到的收益，是生产集群凭证不出集群。

维度推送式（CI 执行部署）拉取式（集群内控制器同步）
谁发起部署集群外的流水线，部署是一次性事件集群内的控制器，部署是持续过程
生产 kubeconfig 在哪存在 CI 的凭证系统里，每个需要部署的流水线都要配一份不存在于集群外，控制器用自己的 ServiceAccount
凭证外泄面随流水线数量线性增长，第三方插件或 Action 都可能读到集群外只剩配置仓库的只读凭证和镜像拉取凭证
集群网络要求集群 API Server 必须对 CI 网络可达集群只需能出网访问仓库，API Server 可完全不暴露
新增一个集群新建凭证、改流水线、加一套部署任务在新集群装控制器并指向同一仓库目录
漂移检测没有，apply 完就结束每个调和周期都在做，默认量级三分钟
部署失败的可见性流水线红了，但集群里可能停在半成功状态应用持续停在 OutOfSync 或 Degraded，状态随时可查
审计入口翻 CI 构建日志，受日志保留期限制查配置仓库 git log，历史与仓库同寿
💡
判断一个方案是不是 GitOps，只问一句

生产集群的写权限凭证，是否还需要交给集群外的系统保管。如果答案是「是」，那么无论配置放在哪、工具叫什么名字，它都还是推送式部署。流水线分层、一次构建多处部署、金丝雀自动判定这些工程实践在两种模式下都有效且必要，详见站内 CI/CD 专题 与 部署策略 篇。

这里有个细节值得强调：控制器做的是三方 diff——仓库里的期望清单、集群里的实际对象、以及上一次应用时记录的配置。只做两方比较会把 Kubernetes 自己填充的默认字段（如 clusterIP、被 HPA 改写的 replicas、准入控制器注入的 sidecar）全部误判成漂移，导致应用永远显示 OutOfSync。真实落地时必须显式声明哪些字段不参与比较，这是新装环境第一周最常处理的一类噪声。

配置仓库与代码仓库为什么必须分开

技术上完全可以把 deploy/ 目录放在业务代码仓库里，控制器也能正常工作。但规模一上来，三个问题会同时出现。

发布节奏不同。业务仓库一天几十次提交，其中绝大多数与部署配置无关。控制器盯着这个仓库，每次提交都要重新克隆、渲染、diff 一遍，而 99% 的渲染结果与上次完全相同。仓库体积大了之后，克隆和渲染本身就成了负担。

权限边界不同。能写业务代码的人，不一定应该能改生产环境的资源限额、副本数、网络策略。分仓库之后才能给生产目录配单独的 review 规则和 CODEOWNERS，让平台或 SRE 守住生产入口，而不必限制业务仓库的日常协作。

回滚语义不同。配置仓库里的一次 git revert 就是一次干净的部署回滚，不牵扯代码。混在一起时，revert 会把代码变更一起退掉，而镜像其实已经发出去了，语义立刻混乱。

镜像 tag 从 CI 回写到配置仓库，是这套分离架构里唯一的跨仓库动作，也是选择最多的一步。

回写方式机制构建完成到生效的延迟谁持有配置仓库写权限适用场景
CI 直接 commit构建成功后 CI 改 tag 并 push 到目标分支秒级CI 的机器人账号，需要写权限非生产环境、迭代快、团队规模小
镜像更新控制器扫描集群内控制器按策略扫描镜像仓库的 tag 列表，匹配到新版本后自己回写仓库取决于扫描周期，分钟级集群内控制器，CI 完全不需要写权限希望 CI 侧零集群与仓库权限，配 semver 或时间戳策略
CI 开 PR 人工合并CI 建分支改 tag 并开 PR，由值班或负责人合并取决于人，小时级机器人只能建分支，合并权限在人生产环境、受监管场景、需要发布窗口

实践中常见的组合是：非生产用 CI 直接 commit 换速度，生产用 PR 方式换控制点。这样「谁批准了这次生产发布」自然落在 PR 的 approve 记录上，不需要另建审批系统。

自愈是双刃剑：治理红利与故障现场的冲突

自愈的治理价值很直接：它让「在集群里手改一下」这件事从有效操作变成无效操作，雪花配置从源头被消除。但同一个机制在故障现场会变成阻力——值班工程师改了副本数救火，三分钟后被改回去，而且现场往往一时想不到是控制器干的。

stateDiagram-v2 [*] --> Synced Synced --> OutOfSync: 配置仓库出现新提交 Synced --> OutOfSync: 集群侧资源被手工修改 OutOfSync --> Syncing: 自动同步触发或人工触发 Syncing --> Synced: 应用成功且健康检查通过 Syncing --> Degraded: 应用成功但 Pod 起不来 Syncing --> Failed: 应用报错或超时 Degraded --> Syncing: 修复配置后重新同步 Failed --> OutOfSync: 退避重试 OutOfSync --> Suspended: 应急时关闭该应用的自动同步 Suspended --> OutOfSync: 处置完成后恢复 note right of Suspended 暂停的粒度是单个应用 不要卸载控制器或把副本缩容为零 否则全集群失去漂移检测与告警 end note

预案的关键是暂停的粒度。把控制器整体停掉，等于让所有应用同时失去调和和漂移可见性，恢复时没人知道停机窗口内集群被改了什么。正确做法是只摘掉目标应用的自动同步开关，保留 diff 能力——你依然能看到「现在集群和仓库差了什么」，这在事后补提交时非常有用。

# 反面做法：把控制器缩容到 0，全集群所有应用同时失去调和与漂移告警
# kubectl -n argocd scale deploy/argocd-application-controller --replicas=0

# 做法一：只关掉单个应用的自动同步，diff 与告警仍然可见
argocd app set payment-prod --sync-policy none

# 做法二：没装 CLI 时直接 patch 掉 syncPolicy.automated 字段
kubectl -n argocd patch application payment-prod --type merge \
  -p '{"spec":{"syncPolicy":{"automated":null}}}'

# 做法三：让特定字段脱离比较（例：副本数交给 HPA，不参与 diff）
#   写进 spec.ignoreDifferences 比在资源上打注解更稳妥，注解本身也会漂移
kubectl -n argocd patch application payment-prod --type merge -p '{
  "spec": {"ignoreDifferences": [
    {"group": "apps", "kind": "Deployment", "jsonPointers": ["/spec/replicas"]}
  ]}}'

# 处置完成后：先把线上真实改动补回配置仓库，再恢复自动同步与自愈
argocd app set payment-prod --sync-policy automated --self-heal
⚠️
应急预案要写进值班手册，而不是靠临场判断

手册里必须明确三件事：暂停命令的准确写法（含应用名清单）、暂停后由谁在多长时间内把改动补回仓库、以及恢复自动同步前的检查项。见过的真实事故是：值班暂停了同步救了火，但没人补提交，两周后另一个人恢复自动同步，控制器直接把线上回退到两周前的配置。

Git 成为唯一入口之后的治理变化

一旦生产变更只能经由仓库进入，治理重心就从「管住谁能登录集群」转移到「管住谁能合并到生产目录」。这带来几处实质变化。

治理动作推送式时代的做法GitOps 下的做法落地要点
变更审批发布系统里点审批，记录在发布平台PR 的 approve 记录生产目录要求至少一名 CODEOWNERS 批准，且禁止自己批自己的 PR
防止绕过限制谁有发布权限限制谁有仓库写权限，并禁用 force push保护分支必须关掉 force push 和直接 push，否则历史可被重写
变更审计查发布平台与集群操作日志，受日志保留期限制查 git log，历史长期保留提交信息带工单号；禁止机器人把多次变更压成一条无描述提交
紧急变更直连集群操作仍走仓库，但允许单人批准的加急通道加急通道要留痕并有事后复盘，不能变成常态
权限回收收回 kubeconfig移除仓库协作者，集群侧本就无人有写权限离职流程要覆盖仓库权限，而不只是集群账号
# 审计从翻操作日志变成查 git log：谁在什么时候改了生产的镜像 tag
git log --follow -p --pretty='%h %ad %an %s' --date=iso \
  -- envs/prod/payment/kustomization.yaml

# 故障时间窗内所有落到生产目录的提交，定位可疑变更的第一条命令
git log --since='2026-09-20 14:00' --until='2026-09-20 16:00' \
  --pretty='%h %ad %an %s' --date=iso -- envs/prod/

# 回滚用 revert 而不是 reset：保留正向历史，控制器会把集群拉回上一个期望状态
git revert --no-edit 9ddb2c9 && git push origin main

# 核对仓库期望与集群实际是否一致。判读：输出为空才说明真的收敛了
argocd app diff payment-prod --local envs/prod/payment

GitOps 不适合的场景：擅长声明状态，不擅长描述过程

这是被吹得最少、踩坑最多的部分。声明式模型的前提是「存在一个稳定的期望状态」。当任务本身是一个有先后依赖的过程、或者期望状态每分钟都在变，模型就不成立了。

场景为什么声明式模型不成立更合适的做法
一次性数据修复、批量补偿任务没有稳定期望状态。Job 跑完即终态，控制器会认为它不该消失而反复重建留在命令式流水线；或用带 ttlSecondsAfterFinished 的一次性 Job 并从调和范围排除
有状态组件的复杂升级需要按序停写、备份、迁 schema、切主，步骤间有依赖和人工确认点用 Operator 把过程封装成控制器，GitOps 只声明目标版本；或走独立运维手册
需要中途判断的发布流程「观察五分钟指标再决定是否继续放量」无法表达为一个静态期望状态引入渐进式交付控制器，把判定规则本身声明化；判定逻辑详见站内部署策略篇
秒级动态伸缩副本数由 HPA 实时改写，与仓库里的静态值必然不一致把 replicas 从 diff 中排除，仓库里只声明 HPA 的上下界
集群引导的第一步控制器自己还没装，无法靠自己把自己拉起来用基础设施即代码完成集群与控制器初装，之后交给 GitOps；Terraform 的状态与漂移详见站内 IaC 专题

密钥：GitOps 最大的现实难题

期望状态要全部进仓库，可密钥不能进仓库——这是 GitOps 唯一没有优雅解的地方。必须先说清一件事：Git 历史是永久的。把误提交的明文密钥删掉再提交，只是新增一条删除记录，旧的 blob 仍然能被检出，任何克隆过仓库的人手上都有一份。一旦发生，唯一正确的处置是立刻轮换那个密钥，而不是清理历史。

方案密钥本体是否进 Git解密发生在哪轮换成本主要风险适用场景
Sealed Secrets进，密文形式集群内控制器，用它自己持有的私钥要重新加密并提交控制器私钥丢失则所有历史密文永久作废，必须单独备份；密文与集群绑定，换集群要重新封装单集群、密钥数量少、不想引入外部依赖
SOPS 配 age 或云 KMS进，字段级密文控制器侧插件解密，也可在本地解密查看要重新加密并提交，支持多收件人本地能解密意味着私钥管理责任转移到人；文件结构可见，字段名与层级会泄露需要人工核对配置、多人共享解密权限
External Secrets Operator不进，仓库里只有引用路径不解密，直接从外部密钥服务取值生成 Secret只改外部服务，Git 不用动引入对外部密钥服务的运行时依赖，服务不可用时新建 Secret 会失败推荐默认选择，尤其已有集中式密钥管理的组织
# 推荐路线的样子：仓库里只有引用关系，密钥本体从不进 Git
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: payment-db
  namespace: prod
spec:
  refreshInterval: 1h            # 轮询周期。外部改了密钥，最长 1h 生效
  secretStoreRef:
    name: vault-backend          # 指向 SecretStore 或 ClusterSecretStore
    kind: ClusterSecretStore
  target:
    name: payment-db-secret      # 渲染出来的 K8s Secret 名字
    creationPolicy: Owner        # ExternalSecret 删除时连带回收 Secret
  data:
    - secretKey: password        # Secret 里的 key
      remoteRef:
        key: prod/payment/db     # 外部密钥服务里的路径
        property: password
# 注意：Secret 内容更新不会自动重启 Pod。要让新密钥真正生效，需要配合
# checksum 注解或 reloader 类组件触发滚动更新，否则密钥轮换了但进程还在用旧值

密钥的存储后端选择、轮换周期、供应链签名与准入校验这些更上游的话题，站内 安全专题 已有完整讨论，这里只谈它与 GitOps 模型的耦合点。

工具选型，以及关于 Helm 的一个常见误解

先纠正误解：Argo CD 和 Flux 都不替代 Helm 或 Kustomize，它们是消费者。控制器拉到仓库内容后，识别清单类型，内部调用渲染逻辑（等价于 helm template 或 kustomize build）得到最终 YAML，再去 diff 和 apply。这意味着：helm list 看不到由 Argo CD 管理的应用，因为控制器只用了模板渲染，没有走 Helm 的 release 机制，也就没有 release 记录和 helm rollback——回滚的责任回到了 Git。

成熟度自检与反模式

下面这张清单可以直接当评审表用。全部命中才算真正跑起来了 GitOps，而不只是把 YAML 挪进了仓库。

自检项判定方式未达成的典型表现
集群外无生产写凭证检查 CI 的凭证列表与集群 RBAC 里 CI 账号的权限流水线里还留着 kubeconfig，理由是「偶尔要用」
漂移可见且会被纠正手工改一个测试环境的副本数，看多久被改回、是否有告警改完一直不变，说明只做了同步没做调和
镜像 tag 不可变检查仓库里是否存在 latest 或可移动 tag推了新镜像但控制器检测不到变化，因为 tag 字符串没变
回滚只靠 Git随机挑一个应用，只用 revert 完成一次回滚演练回滚要登集群或跑特殊流水线
密钥不以明文存在于任何提交对仓库全历史跑一次密钥扫描历史里有明文，且从未做过轮换
同步单元粒度合理观察单次同步耗时与参与 diff 的资源数量单个应用管上千个资源，一次同步要几分钟
控制器自身也被纳管检查控制器的配置是否来自仓库控制器配置是当初手工 apply 的，没人知道后来改过什么
反模式具体表现后果正确做法
在集群里手改临时改了副本数或环境变量，不回写仓库改动被自愈覆盖；或关掉自愈后形成长期雪花配置改动一律先进仓库；应急改动必须在处置单里带补提交任务
配置与代码混一个仓库部署清单放在业务仓库的 deploy 目录每次代码提交都触发全量渲染与 diff；权限与回滚语义混乱拆出独立配置仓库，生产目录单独配 CODEOWNERS
用 latest 标签镜像写成 app:latest期望状态没有变化，控制器检测不到新镜像，必须手动重启才生效用版本号或镜像摘要，保证 tag 不可变
把 CI 的 apply 改名叫 GitOps仍由流水线执行 kubectl apply，只是配置进了仓库凭证风险与漂移问题一个都没解决，却背上了流程负担把 apply 的发起方移到集群内控制器，同时收回 CI 的集群凭证
密钥明文进 GitSecret 的 base64 值直接提交base64 不是加密；历史永久留存，所有克隆者可见三条密钥方案任选其一；已发生的立刻轮换而不是改历史
一个应用管整个集群单个同步单元指向仓库根目录，覆盖全部命名空间同步耗时失控、一处语法错误阻塞全部变更、权限无法按团队切分按团队或按服务拆分同步单元，用批量生成机制管理数量

同步策略的具体开关语义与自愈实现细节，见同专题 Application 管理与同步策略；多环境的仓库结构与环境间配置差异管理，见 多环境与 K8s；从现有 CI/CD 迁过来的分步路径与检查项，见 从 CI/CD 迁移到 GitOps；Argo CD 的对象模型与生产化配置，见 Argo CD 部署与生产化。

❌
最容易踩的坑

1. 把控制器缩容到零当作暂停同步，全集群同时失去调和与漂移告警，恢复时无人知道停机窗内集群被改了什么。正确做法是只摘掉目标应用的自动同步开关。

2. 应急手工改了线上但没补提交，几周后别人恢复自动同步，集群被直接拉回几周前的期望状态。

3. 镜像用可移动 tag。推了新镜像但仓库里的字符串没变，期望状态没有差异，控制器不做任何事，表现为「发布了但没生效」。

4. 没排除 Kubernetes 自动填充的字段和 HPA 改写的副本数，应用永远 OutOfSync，久而久之团队对告警脱敏。

5. 明文密钥误提交后用删文件加提交来「清理」，以为解决了。旧 blob 仍可检出，唯一有效处置是轮换密钥。

6. 把 base64 当成加密。Secret 里的值只是编码，任何人 decode 一下就能读。

7. 单个同步单元指向仓库根目录，一个 YAML 语法错误就让全集群所有变更卡住，同步一次要几分钟。

8. 保护分支没关闭 force push，历史可被重写，「版本化且不可变」这条原则直接失效，审计链断裂。

9. 把 Helm 渲染等同于 Helm release，事后发现 helm list 看不到应用、helm rollback 也用不了，因为控制器只用了模板渲染。

10. 用一次性 Job 表达数据修复任务并交给调和管理，Job 跑完被回收后控制器认为状态缺失又重建一遍，数据被重复处理。

11. 控制器装在它所管理的唯一集群里，且控制器配置从未入仓。集群整体故障时既没有配置可参照，也没有第二个控制面可以驱动恢复。

12. 密钥轮换后没有触发工作负载滚动更新，Secret 内容变了但进程内存里还是旧值，表现为「改了密码但连接还在用旧的」。
