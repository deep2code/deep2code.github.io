GitOps 核心原则

🏷️ GitOps,云原生

从 CI/CD 到 GitOps：一次部署范式的迁移

2017 年 Weaveworks 的 Alexis Richardson 提出 GitOps 一词之前，云原生团队的发布链路是这样的：CI 流水线打完镜像标签 → 手动 kubectl apply → 人工检查滚动状态 → 出了问题手动回滚。

更隐蔽的问题是状态漂移：开发者通过 kubectl edit 临时改了一个副本数，Git 里的 YAML 却没有同步，下次流水线再跑又把它改回去——没人说得清集群里到底跑着什么。

GitOps 的回答极其优雅：把 Git 仓库变成集群状态的唯一事实来源（Single Source of Truth）。你不再把变更"推"进集群，而是让集群里的 Agent 主动"拉"取 Git 中声明的期望状态，并持续把实际状态收敛过去。CI 只负责构建镜像和更新 Git 中的版本号，部署动作完全发生在集群内部。这条边界一旦划清，安全、审计、回滚、环境一致性全部被 Git 这一成熟工具链天然解决。

四大核心原则：CNCF 官方定义

CNCF GitOps WG 在 2024 年发布的白皮书里把 GitOps 归纳为四条必须同时满足的原则，缺一条都只能叫"用 Git 做发布"，不能叫 GitOps：

  • 声明式（Declarative）：系统中所有被管理的内容（应用配置、基础设施、网络策略）都必须以声明式描述存储在 Git 中。命令式脚本（kubectl run、sed 改配置）不属于 GitOps 范畴，因为它们无法做 diff、无法审计、无法回放。
  • 版本化且唯一来源（Versioned & Single Source of Truth）：期望状态只存在于一个 Git 仓库，不可在多个仓库间分裂。Git 的提交历史天然提供了不可篡改的审计日志，每一次变更都有作者、时间、评审记录。
  • 自动拉取（Automated Pull）：Agent 在集群内运行，主动从 Git 拉取期望状态，而不是被外部系统推送。这意味着集群不需要暴露给 CI Runner，安全边界从"谁能连集群"变成了"谁能合并 PR"。
  • 持续调谐（Continuous Reconciliation）：Agent 持续对比实际状态与期望状态，任何漂移（手动改副本数、恶意篡改、故障恢复后残留）都会被自动纠正。这一点与 Kubernetes 控制器模式一脉相承。

架构原理：GitOps 控制回路

理解 GitOps 的关键是把它看作 Kubernetes 调谐循环的延伸。K8s 控制器对比"etcd 里的 spec"与"实际 Pod"；GitOps Agent 对比"Git 里的 YAML"与"集群里的资源"。两者都是电平触发、可自愈、幂等的。

ArgoCD / Flux] AGENT -->|Apply| K8S[(K8s API)] K8S -->|Watch 状态| AGENT end Bump --> REPO AGENT -.->|Watch Pull| REPO K8S -->|实际状态| AGENT AGENT -->|不一致则收敛| K8S

注意图中的关键边界：CI 流水线从不直连集群。它只做两件事——构建镜像、把新镜像 tag 写回 GitOps 仓库。集群侧的 Agent 通过 Webhook 或轮询感知到新提交，自行完成部署。这个"推拉反转"是 GitOps 安全模型的根基：攻击面从"整个 CI 系统"收缩为"一个经过 Code Review 的 PR 合并动作"。

我的选型建议

团队里有专职值班同学、应用数量在 20~200 之间，直接上 ArgoCD——UI 能省掉大量排查时间。如果是平台团队想把 GitOps 做成底座、所有服务统一由 YAML 描述，Flux 更轻更贴合 K8s 习惯。别迷信"哪个更流行"，问自己一句：谁每天要看部署状态？ 有人看就选 ArgoCD，没人看就选 Flux。

主流实现：ArgoCD vs Flux CD

两条路线都满足四大原则，但设计哲学差异很大。我做过两个团队的选型，对比如下：

维度ArgoCDFlux CD
核心抽象Application CRDKustomization / HelmRelease 等多 CRD
Web UI自带，可视化强无独立 UI，靠 Git 看
学习曲线友好，值班同学能上手陡峭，偏平台工程团队
生态位Argo 项目组（含 Rollouts/Workflows）CNCF 毕业项目
适合场景应用数量中等、需要界面操作把 GitOps 当底座、不需要图形界面

实战：传统部署 vs GitOps 部署对比

先看一个典型的传统 Push 模式脚本，它把生产集群凭证烧在 CI 变量里：

# ❌ 传统 Push 模式：CI Runner 直连生产集群
# 凭证来自 CI Secret，任何有仓库写权限的人都能触发
docker build -t registry.example.com/api:$CI_COMMIT_SHA .
docker push registry.example.com/api:$CI_COMMIT_SHA

# 直接 kubectl apply 到生产 —— 集群 kubeconfig 放在 CI Secret 里
kubectl set image deployment/api api=registry.example.com/api:$CI_COMMIT_SHA     --record -n production

# 问题：1) 集群凭证泄露面大 2) 无法审计谁改了什么
#      3) 漂移无感知 4) 回滚靠重新部署上一个版本

GitOps 模式下，CI 只负责产出镜像和更新配置仓库，部署由集群内 Agent 完成：

# ✅ GitOps 仓库中的 application.yaml —— 唯一事实来源
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: api-production
  namespace: argocd
spec:
  project: production
  source:
    repoURL: https://github.com/example/gitops-config.git
    targetRevision: main
    path: overlays/production
  destination:
    server: https://kubernetes.default.svc
    namespace: production
  syncPolicy:
    automated:
      prune: true        # Git 里删掉的资源也会被清理
      selfHeal: true     # 手动 kubectl edit 的漂移会被自动纠正
    syncOptions:
      - CreateNamespace=true

CI 流水线对应变成了纯粹的"构建 + 提 PR"：

# ✅ GitOps 模式：CI 不碰集群，只更新配置仓库
docker build -t registry.example.com/api:$CI_COMMIT_SHA .
docker push registry.example.com/api:$CI_COMMIT_SHA

# 用 yq 或 sed 更新配置仓库中的镜像 tag，提一个 MR
git clone https://github.com/example/gitops-config.git
cd gitops-config
yq -i '.images[0].newTag = strenv(CI_COMMIT_SHA)'     overlays/production/kustomization.yaml
git commit -m "chore: deploy api $CI_COMMIT_SHA"
git push origin main
# ArgoCD Watch 到 main 分支变更，自动完成同步 —— CI 到此结束

对比之下，GitOps 模式的 CI 流水线完全没有集群凭证，攻击面收敛到 Git 仓库权限；每一次部署都是一次 Code Review，回滚 = git revert；漂移被 selfHeal 自动纠正。

最佳实践

  • 配置与代码分仓：应用代码仓库（开发关心逻辑）和 GitOps 配置仓库（运维关心部署）分开。镜像版本通过 CI 自动写入配置仓库，避免开发和发布混在一个 PR 里互相阻塞。
  • 主分支只放不可变 tag：GitOps 仓库的 main 分支应只记录具体镜像 digest（@sha256:...），不要用 latest 这类浮动 tag，否则 Agent 无法判断"该不该重新部署"。
  • 禁止 kubectl 直改生产：把集群的写入权限只授予 GitOps Agent 的 ServiceAccount，开发者只能在 Git 里改 YAML。临时调试用独立命名空间，调试完立即回收。
  • 用分支模型表达环境：main → staging，release-* → production。合并即部署，环境晋升靠 PR 从 main 合到 release 分支，审计天然成立。
  • 把漂移监控当作一等公民：ArgoCD 的 OutOfSync 状态、Flux 的 drift detection 都应接入告警。漂移本身不一定是事故，但"漂移长期无人知晓"一定是事故。

常见问题 FAQ

Q1：GitOps 和 Infrastructure as Code（Terraform）是什么关系？

两者都强调声明式 + Git 管理，但作用域不同。Terraform 管的是基础设施（VPC、数据库、负载均衡器、DNS），GitOps 管的是集群内部的工作负载。成熟的组合是：Terraform 负责"把集群建出来"，GitOps 负责"把应用装进集群"。也有团队用 Crossplane 把云资源也纳入 GitOps 模型，但那是另一层复杂度。

Q2：我的团队已经用了 CI/CD 流水线，为什么还要引入 GitOps？

CI/CD 流水线解决的是"如何自动化执行部署动作"，GitOps 解决的是"部署之后谁来保证状态不漂移、出了问题怎么快速回滚"。如果你已经遇到过"流水线成功但线上配置不对"、"有人手工改了副本数没人知道"、"回滚要重跑一遍流水线"这类问题，GitOps 就是对症下药。如果团队只有两三个服务且变更极少，现有流水线也能跑，不必过度工程化。

Q3：GitOps 适合多集群管理吗？

非常适合，这正是 GitOps 的强项。一个 Git 仓库可以声明"集群 A 跑这套、集群 B 跑那套"，每个集群各跑一个 Agent 各自收敛。跨集群的灰度发布（先在 5% 集群上验证）本质就是在 Git 里改一个副本比例。ArgoCD 的 ApplicationSet、Flux 的 Kustomization 都原生支持这种多集群模型。

Q4：GitOps 的"自动拉取"会不会有延迟？实时性够吗？

取决于实现。ArgoCD 默认每 3 分钟轮询一次 Git，也可以配置 Webhook（推送事件触发）把延迟压到秒级。对绝大多数发布场景这个粒度足够——真正需要秒级扩缩容的是 HPA/VPA，不是 GitOps。如果你需要"推完立刻看到效果"，用 Webhook + ArgoCD 的主动同步即可。

总结

GitOps 不是又一个 CI/CD 工具，而是一次部署责任的重新划分：CI 负责构建，Git 负责记录意图，集群内的 Agent 负责收敛状态。它把"发布"从一种需要权限的危险操作，降级为一次普通的 Code Review。理解了这一层，你再去看 ArgoCD 的 Application、Flux 的 Kustomization，就会发现它们都只是在实现同一个控制回路的不同切片。下一篇我们动手把 ArgoCD 真正装进集群，看清它内部的每一个组件在做什么。
