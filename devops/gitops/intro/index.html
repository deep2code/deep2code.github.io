从现有 CI/CD 迁移到 GitOps：五阶段落地路径与凭证收回

🏷️ GitOps

已经有一套能用的 CI/CD，怎么平滑迁到 GitOps，这是绝大多数团队面对的真实问题——而不是从零搭一套。迁移失败的典型姿势是：周五装好控制器，把所有环境一次性切成自动同步，周一发现线上版本在两个值之间来回跳。这篇只讲落地路径：迁移前要满足什么条件、分几步走、每步怎么判定完成和怎么回退、以及最容易卡住的镜像 tag 回写和凭证收回。GitOps 的原理、四条原则和推拉模式的差异见 GitOps 的模型与纪律，这里不重复。

迁移前的三项前置条件

这三条不满足就开始装控制器，后面每一步都会返工。它们之间没有替代关系，必须全部具备。

前置条件自检方式不满足时的症状补齐动作
部署配置已完全声明式化在本地空目录里只用仓库内容渲染一次，看能否得到与线上一致的完整清单diff 永远对不上，应用长期停在 OutOfSync，团队开始无视告警把手工 kubectl 命令、sed 拼 YAML、运行时组装配置的逻辑全部改成清单字段
镜像构建与部署已解耦检查同一个镜像能否不重新构建就部署到另一个环境每个环境都要重新构建，制品与环境绑定，迁移后仓库里的 tag 无法跨环境流转构建产物只产出一次并带不可变 tag，部署只消费 tag；流水线分层详见站内 CI/CD 专题
有可用的配置仓库与权限模型确认谁能写生产目录、保护分支规则是否已生效迁移后所有人都能改生产，治理反而比迁移前更松建独立配置仓库，生产目录配 CODEOWNERS，禁用 force push 与直接 push
⚠️
第一条是硬门槛，不能边迁边补

声明式化没做完就装控制器，你会陷入一个恶性循环：清单不完整导致 diff 有噪声，团队为了让界面变绿而不断往忽略列表里加字段，最后忽略列表覆盖了真正重要的字段，漂移检测形同虚设。宁可多花两周把清单补完整，也不要带着半成品进入下一阶段。

五阶段迁移路径：每步的完成判定与回退

关键在于每个阶段都是可停留、可回退的稳定态。任何一步卡住都不影响正常发布，这是说服团队接受迁移的前提。

stateDiagram-v2 [*] --> S0 S0: 现状 CI 持有各环境凭证并直接 apply S0 --> S1: 抽出配置仓库 S1: 清单集中到配置仓库 仍由 CI 执行 apply S1 --> S2: 非生产接入控制器 S2: 非生产环境拉取式同步 生产仍为推送式 S2 --> S3: 生产只读接入 S3: 生产只做 diff 与漂移观察 不自动应用 S3 --> S4: 生产启用自动同步 S4: 生产自动同步与自愈 CI 集群凭证已收回 S4 --> [*] S1 --> S0: 回退 清单放回代码仓库 S2 --> S1: 回退 关闭控制器同步并恢复 CI apply S3 --> S2: 回退 删除生产应用定义 S4 --> S3: 回退 关闭自动同步降为只读 note right of S3 这个阶段停留时间最长 目标是把漂移清单降到零 看清楚线上到底有多少配置从未入仓 end note
阶段动作完成判定回退方式典型停留时长
S1 抽仓库把各环境清单从代码仓库搬到独立配置仓库，CI 改为 clone 配置仓库后 apply连续一周所有环境的发布都从配置仓库取清单，代码仓库里再无部署清单把清单目录还原回代码仓库，改回原来的 apply 步骤1 至 2 周
S2 非生产拉取在测试与预发集群装控制器，指向对应目录并开启自动同步非生产环境的发布不再经过 CI 的 apply；手改一个副本数能在一个调和周期内被纠正关闭控制器的自动同步，恢复 CI 的 apply 步骤，两者不会冲突因为清单同源2 至 4 周
S3 生产只读在生产集群装控制器，创建生产应用但不开自动同步，只看 diff生产的 diff 连续三天为空，说明仓库内容与线上完全一致删掉生产的应用定义，控制器不再观察生产，对线上零影响2 周以上，直到 diff 归零
S4 生产自动同步开启自动同步与自愈，同一次操作里关闭 CI 的生产 apply一次完整发布只靠合并 PR 完成；一次回滚只靠 revert 完成把自动同步降回只读，重新启用 CI apply（需临时恢复凭证）稳定态
S5 收凭证删除 CI 里的集群凭证，回收 RBAC 写权限权限探测命令对 Deployment 的 create 与 patch 都返回否不建议回退。如需临时权限，走审批并设有效期稳定态

S3 是整个迁移里信息量最大的一步。生产 diff 第一次跑出来，通常会暴露十几到几十项从未入仓的配置：某次故障临时加的环境变量、手工扩过的副本数、别人加的 annotation、早期用 kubectl edit 改过的资源限额。把这些逐条确认并补进仓库的过程，本身就是一次生产环境的配置审计。

配置仓库的目录结构怎么设计

三种常见结构，判据是环境之间差异的性质而不是团队偏好。

结构适用条件改公共配置的成本主要缺点同步单元划分
base 加 overlay各环境只差镜像 tag、副本数、域名、资源限额改一处 base 即覆盖所有环境base 改错会同时影响所有环境，必须有渲染校验；patch 层数一多就难追溯最终值每个 overlay 目录一个同步单元
按环境独立目录环境间结构不同，例如生产多一套灰度工作负载与独立网关要逐个环境改，有遗漏风险重复度高，配置漂移靠人工对齐每个环境目录下按应用再拆
按应用分目录，环境作为子目录应用数量多、团队按服务划分、权限要按服务隔离公共部分要靠共享 base 或组件复用跨应用的统一变更（如统一加标签）要改很多处每个应用一个同步单元，权限天然对齐团队

Kustomize 与 Helm 的角色分工

这两个工具在 GitOps 里不是二选一，它们解决的是不同问题。判据是配置的可变点由谁定义：自己的服务由自己定义，用 overlay 表达增量最直接；第三方组件的可变点由 chart 作者定义，用 values 填空最省事。

维度Kustomize base 加 overlayHelm chart 加 values
擅长表达同一份配置在多环境做少量差异参数化的第三方组件，可变点由 chart 预先定义
变更方式写 patch，只描述增量改 values，填 chart 预留的空
能改的字段范围任意字段，包括 chart 没暴露的仅限 chart 模板里引用了 values 的字段
最终值的可读性层数多了要靠渲染命令才能看清最终值values 是扁平的，但模板里的条件分支会让结果不直观
升级第三方组件要自己跟踪上游 YAML 变化改 chart 版本号即可，上游维护
在 GitOps 里的坑overlay 引用路径写错会渲染出空清单，而空清单配上删除开关很危险控制器只做模板渲染，不产生 Helm release，helm list 看不到、helm rollback 用不了
推荐用于自己团队的业务服务ingress、监控、密钥同步等第三方组件

# 混用的标准写法：先 helm 渲染，再 kustomize patch
# 用途是给第三方 chart 补它没暴露出来的字段，比如注入自定义注解或调度约束
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
namespace: ingress-nginx

helmCharts:
  - name: ingress-nginx
    repo: https://kubernetes.github.io/ingress-nginx
    version: 4.11.3            # 必须锁版本，否则渲染结果会随上游漂移
    releaseName: ingress-nginx
    valuesFile: values.yaml
    includeCRDs: true          # CRD 默认不渲染，用到时必须显式打开

patches:
  # chart 没有暴露这个字段时，只能在渲染后 patch
  - target:
      kind: Deployment
      name: ingress-nginx-controller
    patch: |-
      - op: add
        path: /spec/template/spec/topologySpreadConstraints
        value:
          - maxSkew: 1
            topologyKey: topology.kubernetes.io/zone
            whenUnsatisfiable: DoNotSchedule
            labelSelector:
              matchLabels:
                app.kubernetes.io/name: ingress-nginx
# 注意：启用 helmCharts 需要渲染端允许执行 helm，控制器侧要开对应开关，
# 否则会渲染失败并报 must specify --enable-helm 之类的错误

镜像 tag 回写：迁移里最容易卡住的一步

配置抽出去之后，CI 必须把新镜像 tag 写回配置仓库。看着简单，实际有三个必须处理的问题：改文件的方式、并发 push 冲突、以及 CI 自触发死循环。

#!/usr/bin/env bash
set -euo pipefail

# 入参用不可变 tag（版本号或镜像摘要），绝不能用 latest，
# 否则仓库里的字符串不变，控制器认为期望状态没变，发布不会生效
ENV_DIR="envs/staging/payment"
NEW_IMAGE="registry.example.com/payment:1.24.3"

# 只克隆一层，配置仓库历史可能很长，全量 clone 会明显拖慢流水线
git clone --depth 1 --branch main "$CONFIG_REPO_URL" cfg
cd cfg

# 用 kustomize edit 改：它按结构改字段，比 sed 按文本匹配安全得多
( cd "$ENV_DIR" && kustomize edit set image "payment=$NEW_IMAGE" )

# 没有 kustomize 时用 yq。路径必须精确到字段，否则会改到同名的其他容器
# NEW_IMAGE="$NEW_IMAGE" yq -i \
#   '.spec.template.spec.containers[] | select(.name=="payment") | .image = strenv(NEW_IMAGE)' \
#   "$ENV_DIR/deployment.yaml"

# tag 没变化就直接退出，避免产生空提交把仓库历史刷满
if git diff --quiet; then echo "tag 未变化，跳过提交"; exit 0; fi

# 提交信息里的跳过标记用来打断 CI 自触发死循环（见下文）
git -c user.name=ci-bot -c user.email=ci-bot@example.com \
    commit -am "chore(staging): payment 升级到 1.24.3 [skip ci]"

# 并发冲突：多条流水线同时回写同一仓库，后到的 push 会被拒绝。
# 必须 rebase 重试，绝不能用 force push，那会直接丢掉别人刚推的提交
for i in 1 2 3 4 5; do
  if git push origin main; then exit 0; fi
  git fetch origin main && git rebase origin/main
  sleep $(( i * 2 ))
done
echo "连续 5 次 push 失败，需要人工介入" >&2
exit 1
❌
CI 提交配置仓库又触发了 CI，这个死循环是真实会踩的坑

流水线构建完镜像，回写 tag 到配置仓库；这次提交被 webhook 当成新提交，又触发一次流水线；新流水线再构建、再回写……镜像仓库里迅速堆出几十个同源镜像，流水线队列被占满。如果回写脚本里还有「tag 变了才提交」的短路判断，循环会在第二轮自然停下；没有这层判断的话，它会一直转下去。

解法做法可靠性代价
提交信息加跳过标记提交信息里带 [skip ci] 一类平台约定的标记中。依赖平台支持，且不同平台标记不同；有人改了提交信息模板就失效几乎为零，改一行脚本
配置仓库不配 CI 触发器配置仓库与代码仓库物理分离，前者根本不接 CI高。从结构上消除循环可能需要跨仓库凭证与两套权限模型
路径过滤流水线只在源码目录变更时触发，清单目录变更不触发中高。单仓库场景下最实用路径规则要随目录调整维护
排除机器人账号触发条件里过滤掉 CI 机器人的提交中。有人用自己账号跑脚本就绕过了需要平台支持按提交者过滤
改用镜像更新控制器CI 不回写，由集群内控制器扫描镜像仓库后自己提交高。CI 完全不碰配置仓库多一个组件；生效延迟取决于扫描周期

双轨期的风险：两个写入方必须有明确切换时点

S2 到 S4 之间，同一个环境理论上可能同时被 CI 和控制器写入。这是整个迁移里唯一会造成线上异常的窗口，必须靠流程消除而不是靠运气。

sequenceDiagram participant CI as CI 流水线 旧通道 participant Repo as 配置仓库 participant Ctrl as 集群内控制器 participant API as 集群 API Server CI->>API: apply 新版本 v2 Note over API: 集群当前运行 v2 Ctrl->>Repo: 按周期拉取期望状态 Repo-->>Ctrl: 仓库里仍是 v1 Ctrl->>API: diff 发现差异 把镜像改回 v1 Note over API: 线上被静默回退 且无人收到发布失败通知 CI->>API: 下一次流水线又 apply v2 Ctrl->>API: 下一个周期再改回 v1 Note over CI,Ctrl: 现象是线上版本在两个值之间来回跳
风险表现根因消除方式
版本来回跳线上镜像在新旧版本间反复切换CI 推了新版本但仓库里还是旧值，自愈把它改回去切换必须在同一次操作里完成：关闭 CI 部署步骤与开启自动同步同时做
配置莫名消失CI 加的 annotation 或环境变量过一会儿不见了CI 推的字段仓库里没有，被自愈按多余资源处理切换前先把线上全部实际配置补进仓库，确认 diff 为空
回滚失效用 CI 回滚成功后又被改回故障版本回滚只改了集群没改仓库双轨期明确规定：回滚一律走仓库 revert，不用 CI 回滚
发布静默失败流水线绿灯但线上没变化控制器已接管，CI 的 apply 被覆盖，且 CI 不知道切换后立刻从流水线里删除 apply 步骤，不要只是注释掉
两套清单不同源CI 用的清单与仓库里的不一致S1 阶段没做完就进 S2，CI 还在用本地清单严格按阶段推进，S1 的完成判定就是 CI 只从配置仓库取清单

收回集群凭证：迁移完成的唯一硬标志

只要 CI 还留着一条能直连生产的通道，团队就一定会在某次赶时间的时候用它，于是漂移、绕过审计、版本不可追溯这些问题会原样回来。凭证收回不是收尾工作，它就是迁移完成的定义。

检查项验证命令或方式期望结果常见残留
CI 凭证里无 kubeconfig逐个检查流水线的 secret 与变量列表不存在任何目标集群的 kubeconfig、token 或云厂商集群访问凭证「应急用」的 break-glass 凭证长期挂在共享变量组里
集群 RBAC 无 CI 写权限用权限探测命令对 CI 账号做主体访问评估对 Deployment 的 create、patch、delete 全部返回否CI 账号仍绑着 edit 或 cluster-admin 角色
流水线定义无直连步骤在仓库里搜索操作集群的命令再无 kubectl apply、helm upgrade、kubectl rollout 之类步骤步骤被注释掉但代码还在，随时可被取消注释
镜像仓库权限最小化检查 CI 的镜像仓库权限只有推送权限，集群侧只有拉取权限CI 与集群共用一个全权限账号
配置仓库权限分级检查生产目录的 CODEOWNERS 与保护分支机器人只能建分支，合并到生产目录需人工批准机器人有主分支直接 push 权限
# 1. 确认 CI 账号对生产命名空间已无写权限。判读：三条都应输出 no
kubectl auth can-i create deployments -n prod \
  --as=system:serviceaccount:ci:deployer
kubectl auth can-i patch deployments -n prod \
  --as=system:serviceaccount:ci:deployer
kubectl auth can-i delete deployments -n prod \
  --as=system:serviceaccount:ci:deployer

# 2. 列出该账号实际还绑着哪些角色（输出为空才算干净）
kubectl get rolebindings,clusterrolebindings --all-namespaces -o json \
  | jq -r '.items[] | select(.subjects != null)
      | select(.subjects[]?.name == "deployer")
      | [.kind, .metadata.namespace // "-", .metadata.name, .roleRef.name] | @tsv'

# 3. 确认控制器自己用的是集群内 ServiceAccount，而不是挂载的外部 kubeconfig
kubectl -n argocd get deploy argocd-application-controller \
  -o jsonpath='{.spec.template.spec.serviceAccountName}{"\n"}'

# 4. 扫一遍流水线定义里是否还有直连集群的残留（包含被注释掉的）
grep -rnE 'kubectl (apply|delete|rollout)|helm (upgrade|install)' .gitlab-ci.yml .github/
✅
保留一条受控的应急通道，而不是零通道

完全没有应急手段会让团队在真出事时私下留后门。更现实的做法是：保留一个需要双人审批、自动过期、每次使用都产生告警和复盘记录的临时提权流程。关键是它必须是「一次性申请」，而不是「常驻凭证」。

常见迁移失败原因

失败原因表现为什么会发生正确做法
跳过声明式化直接装控制器应用长期 OutOfSync，忽略列表越加越长以为工具能兼容现有的半命令式流程先把清单补完整，本地渲染结果必须等于线上实际
一次性全环境切换生产在周一被静默回退到上周的配置没有 S3 只读观察阶段，不知道线上有多少配置没入仓按五阶段推进，生产 diff 归零后再开自动同步
忘记关 CI 的 apply版本来回跳，发布结果不确定切换时只做了「开启同步」，没做「关闭推送」把两个动作绑成一次变更，并在发布记录里双人确认
tag 用可移动标签推了新镜像但控制器无动作，发布没生效沿用了原来 CI 直接 apply 加 imagePullPolicy 强制拉取的习惯改用版本号或镜像摘要，保证期望状态字符串会变化
回写脚本用 force push别人的提交被覆盖，某个环境配置退回到几小时前为了解决并发 push 冲突图省事用 fetch 加 rebase 重试，失败到上限就报警人工介入
CI 自触发死循环没处理镜像仓库堆出几十个同源镜像，流水线队列打满配置与代码在同一仓库且没有路径过滤分仓库，或加跳过标记与路径过滤，并保留 tag 未变化就退出的短路判断
密钥仍走原来的注入方式迁移后应用起不来，报找不到 Secret原来密钥由 CI 在部署时注入，仓库里没有对应声明迁移前先把密钥方案换成外部密钥同步或密文入仓，再切同步
同步单元一开始就划太粗一次同步几分钟，一处语法错误卡住所有变更贪图省事把整个仓库交给一个应用管按服务或团队拆分，并用批量生成机制避免手写大量定义

装完控制器之后还要补哪些生产化配置（RBAC 设计、对象模型、同步波次、规模化调参），见同专题 Argo CD 部署与生产化。

❌
最容易踩的坑

1. 声明式化没做完就装控制器。diff 噪声会迫使团队不断扩大忽略列表，最后连重要字段都被忽略，漂移检测形同虚设。

2. 跳过生产只读阶段。第一次跑生产 diff 通常会暴露十几到几十项从未入仓的配置，直接开自动同步等于把这些改动全部抹掉。

3. 切换时只开了自动同步，忘了删 CI 的 apply 步骤。两个写入方互相覆盖，现象是线上版本来回跳，而流水线一直是绿的。

4. apply 步骤只是注释掉没删除。几个月后有人取消注释，双轨问题重新出现且无人能立刻定位。

5. 回写脚本用 sed 按文本匹配改 tag。多容器或 initContainer 里有同名镜像时会一起改掉。

6. 用 force push 解决并发冲突，直接丢掉别人刚推的提交，表现为某个环境配置莫名退回。

7. 没有「tag 未变化就退出」的短路判断，仓库被空提交刷满，且在死循环场景下无法自然收敛。

8. 全量 clone 配置仓库。历史长了之后每次流水线要多花几十秒到几分钟，用浅克隆即可。

9. overlay 的引用路径写错，渲染出空清单。如果同步单元同时开了删除多余资源的开关，这会真的清空一个命名空间。

10. 混用 Helm 与 Kustomize 后仍指望 helm rollback。控制器只做模板渲染，没有 release 记录，回滚只能靠 Git。

11. 第三方 chart 版本没锁定。渲染结果随上游变化，同一个提交在不同时间渲染出不同清单，直接破坏可重现性。

12. 密钥方案留到最后再改。迁移当天应用起不来，被迫临时把密钥明文塞进仓库救急，留下永久性历史污染。
