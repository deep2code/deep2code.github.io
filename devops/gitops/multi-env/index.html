GitOps 多环境与配置差异管理

🏷️ GitOps

多环境管理的难点从来不是「怎么部署到四个集群」，而是怎么让环境之间的差异保持少、可见、可审计。绝大多数「测试环境好的、生产环境挂了」都能归结到同一个根因：生产上跑的东西和你验证过的东西，在某个没人注意的地方不一样。

本文只讲仓库模型、配置差异与 promote。GitOps 的基本纪律见站内《GitOps 核心原则》，Argo CD 自身的部署见《ArgoCD 安装配置》，同步开关、漂移自愈与 sync-wave 见站内《Argo CD 同步机制与漂移自愈》，金丝雀与数据库兼容演进见站内 CI/CD 部署策略一篇。

一、三种仓库模型，以及为什么别用分支表示环境

维度单仓库多目录（推荐）每环境一个分支每环境一个仓库
差异可见性最好：diff overlays/staging overlays/prod 一眼看完最差：差异藏在分支间的历史里，要靠 git diff staging..prod 并区分「还没合的」和「故意不同的」差；跨仓库比对需要额外工具
promote 的形态改一个文件里的 image digest，一次提交分支间 merge 或 cherry-pick跨仓库同步提交
review 粒度能按目录设 CODEOWNERS，prod 目录单独要求双人评审只能按分支设保护规则，粒度粗按仓库，最粗但最硬
权限隔离目录级，依赖 CODEOWNERS 与分支保护，权限模型偏软分支级最强：生产仓库可以只给少数人写权限
配置漂移风险低：base 共享，结构天然一致高：merge 会带过去不该带的环境差异高：三份配置各自演化，久了结构完全分叉
适合谁绝大多数团队不推荐强合规要求、生产由独立团队把关
❌
「用分支表示环境」是最常见的错误做法

这个方案看起来很自然：dev 分支对应开发集群、main 分支对应生产。问题出在 merge 的语义上——分支合并会把源分支的全部差异带过去，而环境差异（副本数、域名、日志级别、调试开关）恰恰是不该跟着走的那部分。于是每次 promote 都变成人工挑拣：漏挑一个，dev 的 debug 日志级别或者压测用的资源配额就进了生产。反方向也一样难受，生产热修复往回合会造成长期分叉，同一个文件反复冲突。正确做法是让环境差异以静态文件的形式并列存在，promote 只推进镜像版本这一个变量。

三、Kustomize 的 base 加 overlay：patch 顺序与 hash 后缀

kustomize build 是一次纯函数式的渲染：读入 base 的对象，按顺序应用 components、patches、generators、名字与镜像的变换，输出最终 YAML。理解它的关键是顺序：patch 的 target 匹配用的是变换前的原始名字，而 namePrefix、nameSuffix 与 labels 是在最后统一施加的。很多人把 patch 的 target 写成带前缀的名字，结果 patch 静默不生效（kustomize 默认不会因为 target 没命中而报错，这一点非常容易踩）。

写法状态擅长坑
patches + target + pathv5 起的唯一推荐写法用 kind/name/labelSelector/annotationSelector 精确选中一批对象target 没匹配到任何对象时默认不报错，patch 白写；CI 里要加渲染结果断言
patchesStrategicMerge已废弃，仍可用但会告警按对象整体合并，写起来直观数组字段的合并规则依赖 patch 策略元信息，容器列表按 name 合并、env 按 name 合并，但很多字段是整体替换
patchesJson6902已废弃，仍可用但会告警精确改数组下标下标是位置依赖的，base 里插入一个容器就全错位
replicas / images专用字段改副本数与镜像，语义清晰无需写 patchimages 只改 image 字段，不会改 sidecar 注入器后加进来的容器
namePrefix / nameSuffix常用同集群里多份部署共存名字受 63 字符限制；引用会被同步改写，但写在 ConfigMap 内容里的服务名不会被改
componentsv4.1+可选特性组合，自身可以包含 resources 与 patches被引用多次时变换会叠加，要确认是幂等的

接下来是 configMapGenerator 的 hash 后缀，这是多环境里最实用的一个机制。「ConfigMap 改了，Pod 没重启，配置没生效」是 K8s 里最经典的困惑。原因很直接：Deployment 的 pod 模板一个字节都没变，控制器没有任何理由重建 Pod。

注入方式改 ConfigMap 后的行为生效时机
env / envFrom 环境变量已运行的容器完全不受影响永不生效，必须重建 Pod
卷挂载整个 ConfigMapkubelet 周期性同步，文件内容会更新分钟量级（取决于 kubelet 同步周期与缓存 TTL），且要求应用自己监听文件变化
卷挂载 + subPath永远不会更新必须重建 Pod，这是最隐蔽的一种
configMapGenerator 生成内容变则名字变，pod 模板随之变化立即触发一次标准滚动更新
# base/kustomization.yaml 片段
configMapGenerator:
  - name: payment-config
    files:
      - application.yaml        # 内容变化 -> 名字后缀变化 -> Deployment 引用被改写 -> 滚动更新
    literals:
      - LOG_LEVEL=info
secretGenerator:
  - name: payment-tls
    type: kubernetes.io/tls
    files:
      - tls.crt
      - tls.key
# generatorOptions:
#   disableNameSuffixHash: true   # 除非有外部系统按固定名字引用，否则不要加这一行
#                                 # 加了之后配置改动不再触发重启，等于把这个机制关掉了
✅
hash 后缀带来的两个副作用要一起处理

第一，旧的 ConfigMap 不会自动消失，改十次就留十个历史对象——在 Argo CD 里开 prune 会自动清理，纯 kubectl apply 的场景需要自己按 label 定期清。第二，不要让集群外的东西（比如另一个团队手写的 Pod、或某个脚本）按固定名字引用被 generator 管理的 ConfigMap，名字会变。真的需要固定名字时，把这个 ConfigMap 从 generator 里拿出来当普通资源写，并显式在 pod 模板里加一个内容摘要的 annotation 来触发更新。

四、Helm 在多环境下的做法，以及和 Kustomize 混用

Helm 的多环境靠 values-{env}.yaml，值的优先级从低到高是：chart 自带的 values.yaml、按顺序传入的多个 -f 文件（后者覆盖前者）、--set、--set-string 与 --set-file。数组是整体替换而不是合并，这是最常见的误判——你在 env values 里只想加一个 tolerations，结果把 chart 默认的那几条全覆盖掉了。

维度KustomizeHelm混用（推荐形态）
差异表达方式对最终对象做 patch，所见即所得模板参数，最终形态取决于 chart 作者留了什么口子三方 chart 用 Helm 渲染，自己的补丁用 Kustomize 叠在渲染结果上
chart 没暴露的字段能改任意字段改不了，只能 fork chart混用的核心价值就在这里
值的可读性overlay 之间可直接 diff要 helm template 之后才能比CI 统一比渲染结果
版本与可复现性base 与 overlay 同仓库，天然一致依赖 chart 版本与 repo 可用性，必须锁版本并考虑私有镜像仓chart 锁精确版本，禁止用 latest
密钥secretGenerator 会把密文写进仓库，不要用values 里写密码同样等于入库两者都交给 External Secrets，仓库里只放引用

混用的具体形态是在 Kustomization 里用 helmCharts 字段做 inflate（需要 --enable-helm），或者在 Argo CD 里配 kustomize.buildOptions: --enable-helm。要注意这条命令行开关必须在服务端也打开，否则本地渲染正常、Argo CD 侧报 must specify --enable-helm。

五、promote 到底该推进什么

sequenceDiagram participant CI as CI 流水线 participant Reg as 镜像仓库 participant Repo as 配置仓库 participant Argo as Argo CD participant K8s as staging 与 prod 集群 CI->>Reg: 构建并推送镜像，拿到不可变的 digest CI->>Repo: 提交，改 overlays/staging 的 image digest Repo-->>Argo: webhook 通知 Argo->>K8s: 同步 staging CI->>K8s: 跑集成与冒烟测试 Note over CI,K8s: 验证对象是这个 digest 对应的镜像，不是某个 tag CI->>Repo: 机器人开 PR，只改 overlays/prod 的同一个 digest Repo->>Repo: CODEOWNERS 要求生产负责人评审 Repo-->>Argo: 合并后 webhook 通知 Argo->>K8s: 同步 prod，逐个 wave 推进 Note over Repo,K8s: 任何时候都能用一次提交回答「生产在跑哪个镜像」
promote 的做法问题
推进已验证的 image digest（正确）无。二进制与验证对象严格一致，回滚就是把 digest 改回去
为 prod 重新构建一次镜像构建不可能完全可复现：依赖解析、时间戳、基础镜像的 latest 都会变，你上线的不是你测过的东西
推进浮动 tag（v2、stable）tag 可以被覆盖，同一个 tag 在不同时间指向不同镜像，回滚与取证都失效
把 staging overlay 整个复制到 prod会把 staging 的副本数、配额、影子域名、调试开关一起搬进生产
在 Argo CD 界面点击同步到 prod变更没有经过仓库，git 历史缺一条记录，下一次同步会被覆盖
用 Image Updater 自动改 prod digest低环境可以，生产不建议：等于绕过了人工评审这道闸门，且不可预期的时间点发布

六、哪些环境差异合法，哪些是危险信号

合法的环境差异为什么合法
副本数、HPA 上下限流量量级本来就不同
resources 的 requests 与 limits低环境为了省资源必然更小
Ingress host、证书、外部依赖地址域名和下游服务本身就不同
日志级别、采样率生产要控成本，低环境要细节
feature flag 的默认值灰度推进的正常手段
存储 class 与容量、备份策略成本与 SLA 不同
危险信号它意味着什么怎么消除
各环境镜像不是同一个 digest生产跑的二进制从未被验证只 promote digest，CI 里断言三个 overlay 的 digest 单调推进
prod 独有的资源类型或 CRD这部分配置在任何低环境都没跑过，第一次真实运行就在生产把它下沉到 staging，哪怕规模缩小
渲染结果的字段路径集合不一致结构性差异，通常是某次生产救火直接改了 prod overlay 却没回灌定期比对结构指纹，差异必须有 PR 说明
prod 的 base 是另一份拷贝base 已经分叉，共享结构的前提不存在了合回同一个 base，差异下沉到 overlay 或 components
prod overlay 里出现整段复制的对象有人用复制代替 patch，以后 base 的改动不会传导到生产改成最小 patch
只有 prod 关掉了某个探针或降低了超时往往是为了掩盖一个真实问题回到根因，不要用配置差异掩盖

第一个方向有现成的机制兜底（selfHeal），第二个方向完全没有——它不会触发任何告警，只会在某次生产发布时以一个莫名其妙的失败暴露出来。所以要在 CI 里主动生成「结构指纹」做比对：

#!/usr/bin/env bash
set -euo pipefail

# 1) 每个 overlay 渲染一次，失败即退出（渲染不过等于这个环境根本发不出去）
for e in dev staging prod; do
  kustomize build --enable-helm "overlays/$e" > "/tmp/render-$e.yaml"
done

# 2) 指纹一：对象清单。谁多了谁少了一目了然
for e in dev staging prod; do
  yq -r '[.kind, .metadata.name] | join("/")' "/tmp/render-$e.yaml" | sort -u > "/tmp/kinds-$e.txt"
done
echo "== staging 与 prod 的对象差异（prod 独有的要重点看）=="
diff /tmp/kinds-staging.txt /tmp/kinds-prod.txt || true

# 3) 指纹二：字段路径集合。只比结构不比值，值不同是合法的
for e in staging prod; do
  yq -r '.. | select(tag != "!!seq") | path | join(".")' "/tmp/render-$e.yaml" \
    | sed -E 's/\.[0-9]+/.N/g' | sort -u > "/tmp/paths-$e.txt"
done
echo "== 结构性差异（每一条都应该能说清原因）=="
diff /tmp/paths-staging.txt /tmp/paths-prod.txt || true

# 4) 硬断言：prod 的镜像必须是 digest 形式，禁止浮动 tag
if ! yq -r '.spec.template.spec.containers[]?.image' /tmp/render-prod.yaml \
     | grep -v '^null$' | grep -q '@sha256:'; then
  echo "prod 存在非 digest 引用的镜像，拒绝合并" >&2
  exit 1
fi

八、分环境的密钥与 ApplicationSet 批量生成

密钥的第一原则是overlay 里只能出现引用，不能出现密文。如果用 SOPS 之类的方案加密入库，关键在于每个环境必须用独立的密钥：共用一把密钥时，任何能解开 dev 的人就能解开 prod，环境隔离在密钥层面直接失效。更省事的形态是 External Secrets，仓库里放一个指向远端路径的对象，按环境配不同的 SecretStore：

# overlays/prod/external-secret.yaml —— 仓库里没有任何密文
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: payment-db
spec:
  refreshInterval: 1h          # 轮转后多久生效；调太短会打满密钥服务的配额
  secretStoreRef:
    name: vault-prod           # 每环境一个 SecretStore，各自的凭证与权限互不相通
    kind: SecretStore
  target:
    name: payment-db
    creationPolicy: Owner
  data:
    - secretKey: dsn
      remoteRef:
        key: secret/data/prod/payment/db   # 环境体现在路径上，overlay 之间只有这一行不同
        property: dsn
---
# ApplicationSet：按环境批量生成 Application，避免三份几乎一样的 YAML
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: payment-api
  namespace: argocd
spec:
  goTemplate: true
  goTemplateOptions: ["missingkey=error"]   # 模板引用了不存在的键就报错，不要静默生成空值
  generators:
    - list:
        elements:
          - env: dev
            cluster: https://kubernetes.default.svc
            selfHeal: "true"
          - env: staging
            cluster: https://staging.k8s.internal
            selfHeal: "true"
          - env: prod
            cluster: https://prod.k8s.internal
            selfHeal: "false"     # 生产先用人工闸门，稳定后再打开
  template:
    metadata:
      name: 'payment-api-{{ .env }}'
    spec:
      project: 'payment-{{ .env }}'   # 用 AppProject 做集群与资源白名单的硬隔离
      source:
        repoURL: https://git.internal/infra/payment-api.git
        targetRevision: main
        path: 'overlays/{{ .env }}'
      destination:
        server: '{{ .cluster }}'
        namespace: 'payment-{{ .env }}'
      syncPolicy:
        automated:
          prune: true
          selfHeal: true
          allowEmpty: false
  syncPolicy:
    preserveResourcesOnDeletion: true   # 删掉 ApplicationSet 时不要级联删掉生产资源

另一种常见写法是 git directory generator：扫描 overlays/* 自动生成 Application，新增一个环境目录就自动多一套应用。它的便利和危险是同一件事——删掉或改名一个目录会导致对应 Application 消失，配合 prune 就是一次批量删除，所以 preserveResourcesOnDeletion 在生产环境必须打开。

九、反模式

反模式典型现场代价该怎么做
生产配置从测试配置手工复制「照着 staging 改一份就行」把低环境的配额、域名、调试开关带进生产，且以后 base 改动不再传导共享 base，prod 只写差异
环境差异靠模板里的 if 判断{{ if eq .Values.env "prod" }} 层层嵌套渲染结果无法直接阅读，分支组合爆炸，测不全差异外置成 overlay 或 components，模板保持无分支
密文写进 overlaystringData 直接写库密码仓库历史里永久留存，轮转等于没有External Secrets 或分环境密钥的 SOPS
prod 目录没人评审就能合仓库只设了 main 分支保护生产变更没有第二双眼睛CODEOWNERS 按目录要求生产负责人评审
每个环境的 base 各自演化为了「不影响别的环境」复制了一份 base共享结构的前提消失，差异不可控强制单一 base，差异下沉
用分支表示环境dev/test/main 三条长期分支merge 带过去不该带的差异，反向修复造成长期分叉单仓多目录
渲染产物提交回仓库「把 build 结果也存一份方便看」两份真相，人改了产物没改源，下一次渲染覆盖掉产物只在 CI 里生成用于比对
❌
最容易踩的坑
  • patch 的 target 写了带 namePrefix 的名字，匹配不上，kustomize 默认不报错，patch 静默失效，直到发现生产的资源配额根本没生效。
  • 把 disableNameSuffixHash: true 当默认配置抄进来，于是 ConfigMap 改了 Pod 不重启，排查半天最后归因成「K8s 不支持热更新」。
  • 用 subPath 挂配置文件，认为卷挂载会自动更新，实际上 subPath 挂载永远不更新，只有重建 Pod 才生效。
  • Helm 的 env values 里写了一条 tolerations，把 chart 默认的几条全覆盖了——数组是整体替换而不是合并。
  • labels 配了 includeSelectors: true，上线后又改了这个 label 的值，导致 Deployment 的 selector 变化，K8s 报 selector 不可变，只能删对象重建。
  • prod overlay 用浮动 tag 而不是 digest，某天基础镜像被同 tag 覆盖，两个可用区的 Pod 跑着不同的二进制。
  • 为 prod 重新构建镜像，构建时依赖解析到了新版本的间接依赖，测过的和上线的不是一个东西。
  • SOPS 所有环境共用一把密钥，权限上「能看 dev 就能看 prod」，审计时才发现环境隔离只是目录上的。
  • ApplicationSet 用 git directory generator，有人重命名了一个 overlay 目录，对应 Application 连带资源被 prune 掉；preserveResourcesOnDeletion 没开。
  • CI 只校验 YAML 语法不跑 kustomize build，结果 patch 路径写错、components 引用不存在这类问题一路合进生产才暴露。
  • 只监控了集群相对仓库的漂移，从没比对过环境之间的结构差异，prod 独有的那段配置一直没人发现从未被测试。
  • namePrefix 叠加后资源名超过 63 字符，Service 创建失败，报错信息指向的却是 DNS 标签长度限制，容易误判。
