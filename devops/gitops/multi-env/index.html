多环境与 K8s

🏷️ GitOps,Kustomize

多环境管理的本质：同一份代码，不同的参数

真实团队的发布链路永远不是"一次部署"，而是"开发 → staging → production"的晋升（Promotion）。环境之间的差异往往只有三处：副本数、镜像 tag、外部依赖地址。如果每个环境都维护一套完整的 YAML，三个环境就有三份 Deployment，改一个端口要动三个文件，必然漏改——这就是环境配置漂移的根源。

GitOps 社区的标准答案是 Base + Overlay 模型（Kustomize 原生支持）：把不变的部分（Deployment 模板、Service 定义）抽到 Base，把变化的部分（副本数、镜像 tag、环境变量）按环境写成 Overlay。晋升时只需要改 Overlay 里的镜像 tag，Base 永远不变。这种"单一事实来源 + 差异化覆盖"正是 GitOps 多环境管理的核心思想。

仓库结构：App-of-Apps 模式

当应用数量超过十个，再用一个 Application 管所有资源就难以维护。社区演化出 App-of-Apps 模式：仓库顶层放一个"元 Application"，它不部署业务，只部署一堆 Application 定义。ArgoCD 自己管自己的子应用——这是一种递归的组合模式。

这个结构的关键收益：新增一个微服务时，你不需要登录 ArgoCD 创建任何 Application，只要在 bootstrap/ 目录加一个 YAML，root Application 自动把它拉起来——Git 就是你的控制平面。

实战：Kustomize Base + Overlay

先看一个微服务的 Base 模板，它对所有环境通用：

# apps/base/api/kustomization.yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
  - deployment.yaml
  - service.yaml
images:
  - name: registry.example.com/api
    newTag: v1.0.0        # 默认 tag，被 overlay 覆盖

生产环境的 Overlay 只写差异：

# overlays/prod/api/kustomization.yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
namespace: prod
resources:
  - ../../../apps/base/api
patches:
  - target:
      kind: Deployment
      name: api
    patch: |-
      - op: replace
        path: /spec/replicas
        value: 6                # 生产 6 副本
      - op: add
        path: /spec/template/spec/containers/0/resources
        value:
          requests: {cpu: "500m", memory: "512Mi"}
          limits:   {cpu: "2",    memory: "2Gi"}
images:
  - name: registry.example.com/api
    newTag: v1.4.2              # 生产镜像 tag

开发环境 Overlay 几乎只改副本数和 tag：

# overlays/dev/api/kustomization.yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
namespace: dev
resources:
  - ../../../apps/base/api
patches:
  - target:
      kind: Deployment
      name: api
    patch: |-
      - op: replace
        path: /spec/replicas
        value: 1                # 开发 1 副本省资源
images:
  - name: registry.example.com/api
    newTag: v1.5.0-rc3          # 开发用预发布 tag

现在升级一个镜像，你只需要改 prod overlay 里的 newTag，其他地方一律不动——Base 模板零改动。三个环境的典型差异一表清：

维度devstagingprod
副本数126
镜像 tagv1.5.0-rc3（预发布）v1.4.2（待晋升）v1.4.2（已晋升）
资源 limit不设1C/1Gi2C/2Gi
数据库共享开发库独立 staging 库独立生产库
自动同步开开开 + 审批

App-of-Apps：用一个 Application 管所有应用

下面是 root Application 的定义，它扫描 bootstrap/ 目录，把里面每个 YAML 当作一个子 Application 创建出来：

# bootstrap/root-app.yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: root
  namespace: argocd
  finalizers:
    - resources-finalizer.argocd.argoproj.io
spec:
  project: default
  source:
    repoURL: https://github.com/example/gitops-config.git
    targetRevision: main
    path: bootstrap/applications
  destination:
    server: https://kubernetes.default.svc
    namespace: argocd
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=true
      - ApplyOutOfSyncOnly=true

子 Application 之一（prod 环境的 api 服务）：

# bootstrap/applications/api-prod.yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: api-prod
  namespace: argocd
spec:
  project: production
  source:
    repoURL: https://github.com/example/gitops-config.git
    targetRevision: main
    path: overlays/prod/api
  destination:
    server: https://kubernetes.default.svc
    namespace: prod
  syncPolicy:
    automated:
      prune: true
      selfHeal: true

从此新增一个微服务 = 在 bootstrap/applications/ 加一个 YAML 文件 + 在 overlays/ 写环境差异，ArgoCD 全自动拉起。这就是平台工程追求的"自助式交付"。

环境晋升：从 staging 到 production

有了 Base/Overlay 结构，环境晋升就退化成"把 staging 的 tag 复制到 prod"。写一个简单脚本就能完成：

#!/usr/bin/env bash
# promote.sh —— 把 staging 验证过的版本晋升到 production
set -euo pipefail
APP=${1:?"用法: ./promote.sh <app-name>"}
REPO=git@github.com:example/gitops-config.git

git clone $REPO /tmp/gitops-promote
cd /tmp/gitops-promote

# 从 staging overlay 读出当前镜像 tag
TAG=$(yq '.images[0].newTag' overlays/staging/$APP/kustomization.yaml)
echo "Promoting $APP to production, version: $TAG"

# 写进 production overlay
yq -i ".images[0].newTag = "$TAG"" overlays/prod/$APP/kustomization.yaml

git add overlays/prod/$APP/kustomization.yaml
git commit -m "release: promote $APP $TAG staging -> prod"
git push origin main

echo "Done. ArgoCD will sync production within 3 minutes."

这个脚本的好处是：晋升动作本身也是一次 Git 提交，审计链完整。staging 验证了什么版本，prod 就晋升什么版本，杜绝了"prod 上跑的镜像从来没在 staging 验证过"这种最危险的情况。

多集群与环境隔离

当团队规模上来后，环境不再是"同一集群的不同命名空间"，而是不同的集群甚至不同的云账号。ArgoCD 用 Cluster CRD 注册外部集群，每个 Application 通过 destination.server 指定部署到哪：

# 注册一个外部生产集群（argocd cluster add 生成的 YAML）
apiVersion: v1
kind: Secret
metadata:
  name: prod-cluster-credentials
  namespace: argocd
  labels:
    argocd.argoproj.io/secret-type: cluster
type: Opaque
stringData:
  name: prod-cluster
  server: https://prod.example.com:6443
  config: |
    {"tlsClientConfig": {"insecure": false}}
---
# 部署到 prod-cluster 而不是本地集群
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: api-prod
  namespace: argocd
spec:
  destination:
    name: prod-cluster          # 用名字引用外部集群
    namespace: prod
  source:
    repoURL: https://github.com/example/gitops-config.git
    path: overlays/prod/api
  # ...

这种"一个 ArgoCD 实例管理多集群"的模式，比在每个集群都装一套 ArgoCD 更统一——你在一个面板就能看到所有环境的同步状态。

最佳实践

  • Base 模板只放不变量：副本数、资源配额、镜像 tag、域名这些按环境变化的，一律放 Overlay。Base 里出现 production 字样就是设计 smell。
  • 用 App-of-Apps 管理应用生命周期：不要在 ArgoCD UI 里手动创建 Application——所有 Application 定义本身也应该是 Git 里的 YAML。否则 ArgoCD 就成了新的"需要 SSH 登录的服务器"。
  • 环境晋升走 Git 提交：任何从 staging 到 prod 的动作都必须留下 Git commit。不要用 argocd app set 直接改运行时配置——那会制造漂移。
  • Secret 单独管理：不要把生产密码、API Key 提交到 Git 仓库。用 Sealed Secrets、Bitnami SOPS 或 External Secrets Operator 把敏感信息加密存 Git，运行时由控制器解密注入。
  • 给每个环境配置独立的 Project：prod Project 限定只能访问 prod overlay、只能部署到 prod 命名空间。dev 同学就算想推 prod 也没权限——RBAC 在 Project 层就拦住了。
我踩过的坑：明文 Secret 进 Git

早期团队图省事，把数据库密码直接 base64 写在 overlay 里提交了 Git。半年后有人离职，仓库又 forks 出去做开源审计，密码直接泄露。后来全量迁到 Sealed Secrets——Git 里存的是加密后的密文，只有集群里的控制器私钥能解。离职、fork、审计都不用担心。任何能 kubectl get secret -o yaml 还原的明文，都不算 Secret。

常见问题 FAQ

Q1：Base + Overlay 和 Helm Chart 的 values.yaml 有什么区别？

两者解决的是同一类问题——模板复用 + 参数化。Helm 更适合"打包分发"（把 Chart 发给别人用），Kustomize 更适合"在自家仓库里组合多个现成资源"。实际项目里常混用：用 Helm 部署第三方组件（Prometheus、Ingress-NGINX），用 Kustomize 管理自己写的业务 YAML。不要为了统一而硬选一个。

Q2：多环境下，dev 环境经常改配置，prod 很稳定，怎么避免互相干扰？

用分支模型隔离。main 分支跟 dev，release-prod 分支跟 prod。dev 随便往 main 提 PR，prod 只接受从 main 合到 release-prod 的 cherry-pick。这样 dev 的频繁变更不会污染 prod 的 Git 历史。也可以用同一个仓库的不同 overlay 目录配合分支，关键是"变更路径单向"。

Q3：App-of-Apps 模式下，root Application 挂了会怎样？

root Application 负责创建和维护子 Application 定义。它挂了，已经运行的子 Application 不受影响，业务继续跑。但你在 bootstrap 目录新增的微服务不会被自动创建——必须手动 argocd app sync root。所以生产环境 root 也要开 automated + selfHeal，它自己也应该有一个 Application 管自己（bootstrap bootstrap）。

Q4：K8s 集成时，CRD 的 CR 依赖 CRD 本身，部署顺序怎么保证？

两种方式：(1) 用 Sync Wave，CRD 放 wave 0，CR 放 wave 1；(2) 用 ArgoCD 的 ignoreDifferences 忽略 CRD 的某些字段，并在部署 CR 前加 kubectl wait --for=condition=Established。生产环境推荐方案 1，它纯声明式，不需要外部脚本。

总结

多环境 GitOps 的核心就三件事：Base 模板抽不变量、Overlay 表达差异、App-of-Apps 把应用生命周期也纳管。环境晋升从"执行一堆命令"变成"改一个 tag + 提一个 PR"。结合 K8s 的声明式 API 和 ArgoCD 的调谐循环，整个交付链路就闭环了：代码提交 → CI 构建 → 更新 Git tag → ArgoCD 自动同步 → 集群状态收敛。这套链路跑顺之后，你会发现"发布"不再是一个需要熬夜盯的高危动作，而是一次普通的 Code Review。
