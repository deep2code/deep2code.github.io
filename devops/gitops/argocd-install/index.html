ArgoCD 安装配置

🏷️ ArgoCD,Kubernetes

ArgoCD 是什么：Kubernetes 原生的 GitOps 持续交付工具

ArgoCD 是一个遵循 GitOps 四大原则的 Kubernetes 声明式 GitOps 控制器，2018 年由 Intuit 开源，2020 年成为 CNCF 毕业项目。

与通用 CI 工具不同，ArgoCD 的整个产品就是一个跑在 K8s 里的控制器套件——你装它不需要外部数据库，不需要独立的部署服务器，一切状态都存在 K8s 的 etcd 里。

对于已经有 K8s 集群的团队，安装 ArgoCD 的成本极低：一条 kubectl apply 命令拉取它的 CRD 和控制器 Deployment，几分钟之内就能在浏览器里看到一个可视化的应用交付面板。这个"开箱即用"的体验正是它成为 GitOps 事实标准的原因。

核心架构：五大组件各司其职

很多人把 ArgoCD 当成一个单体应用，实际上它是一组微服务协作的分布式系统。理解每个组件的职责，是后续排查性能问题、做高可用部署的前提。

安装配置：从一条命令到生产高可用

官方安装方式是直接 apply 一份 Kustomize base，它会创建 argocd 命名空间、安装 CRD、部署所有组件：

# 1. 创建命名空间并安装 ArgoCD（最新稳定版）
kubectl create namespace argocd
kubectl apply -n argocd -f \
    https://raw.githubusercontent.com/argoproj/argo-cd/stable/manifests/install.yaml

# 2. 观察所有 Pod 进入 Running
kubectl get pods -n argocd -w

# 3. 初始 admin 密码存在名为 argocd-initial-admin-secret 的 Secret 里
kubectl -n argocd get secret argocd-initial-admin-secret \
    -o jsonpath="{.data.password}" | base64 -d; echo

# 4. 把 server 从 ClusterIP 改成 NodePort（生产环境用 Ingress + HTTPS）
kubectl -n argocd patch svc argocd-server -p '{"spec":{"type":"NodePort"}}'
第一台 ArgoCD 我踩过的两个坑
  • 忘了删初始 admin secret：那个 argocd-initial-admin-secret 里的密码是固定的随机串，很多人装完忘了删，谁拿到密码谁就能登录。我装好配完 SSO 第一件事就是 kubectl delete secret argocd-initial-admin-secret -n argocd。
  • UI 打开 502：90% 是因为 server 还是 ClusterIP 没暴露，或者 Ingress 没配 backend-protocol: HTTPS。本地先 kubectl port-forward 验证功能，再配 Ingress。

生产环境不能用 NodePort 裸奔，需要一个带 TLS 终止的 Ingress。下面是一个最小可用的 Ingress 配置，配合 cert-manager 自动签发证书：

# argocd-ingress.yaml —— 生产环境 HTTPS 入口
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: argocd-server
  namespace: argocd
  annotations:
    nginx.ingress.kubernetes.io/ssl-redirect: "true"
    nginx.ingress.kubernetes.io/backend-protocol: "HTTPS"
    cert-manager.io/cluster-issuer: "letsencrypt-prod"
spec:
  ingressClassName: nginx
  rules:
    - host: argocd.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: argocd-server
                port:
                  number: 443
  tls:
    - hosts:
        - argocd.example.com
      secretName: argocd-server-tls

登录后第一件事是改掉初始密码并配置 RBAC。ArgoCD 的 RBAC 模型基于 ConfigMap/argocd-rbac-cm，语法沿用 Casbin：

# 用 CLI 登录（生产环境建议配置 SSO，不要长期用本地账号）
argocd login argocd.example.com --username admin --password '初始密码'

# 修改 admin 密码
argocd account update-password

# 创建一个只允许管理 production 项目的只读角色
argocd proj role create production prod-readonly --description "生产只读"
argocd proj role add-policy production prod-readonly \
    --action get --object '*' --allow

# 配置 Git 仓库访问凭证（私有仓库用 deploy key 或 PAT）
argocd repo add https://github.com/example/gitops-config.git \
    --username gituser --password $GIT_TOKEN

高可用与资源规划

默认安装是单副本的，生产环境必须开启 HA 模式。官方提供了一份 overlays：把 server、repo-server、application-controller 都扩成多副本，redis 换成哨兵模式。关键是 repo-server 和 application-controller 的资源配额——这两个组件在应用数量超过 100 个时会成为瓶颈，下面是一个推荐的生产 requests/limits：

# 在 ArgoCD 的 kustomization.yaml 中 patches 覆盖
# repo-server: CPU 密集，渲染模板吃 CPU
- target:
    kind: Deployment
    name: argocd-repo-server
  patch: |-
    - op: replace
      path: /spec/template/spec/containers/0/resources
      value:
        requests: {cpu: "500m", memory: "1Gi"}
        limits:   {cpu: "2",    memory: "4Gi"}
# application-controller: 内存密集，每个 Application 都要占一份 watch 连接
- target:
    kind: Deployment
    name: argocd-application-controller
  patch: |-
    - op: replace
      path: /spec/template/spec/containers/0/resources
      value:
        requests: {cpu: "1", memory: "2Gi"}
        limits:   {cpu: "4", memory: "8Gi"}

最佳实践

  • 把 ArgoCD 自己也用 GitOps 管起来：安装 manifest、RBAC、Ingress 都放进 Git 仓库，用一个 bootstrap Application 管理 ArgoCD 本身。这样 ArgoCD 的配置变更也走 Code Review。
  • 禁用匿名访问和初始 admin 密码：装好后立刻删除 argocd-initial-admin-secret，配置 SSO（OIDC），用企业账号登录。本地 admin 只用于紧急恢复。
  • 按团队拆 Project：ArgoCD Project 是资源隔离边界——一个团队一个 Project，限定它能访问哪些 Git 仓库、哪些命名空间、哪些资源类型。不要所有应用堆在 default Project 里。
  • 限制 Application 数量：单个 ArgoCD 实例管理的 Application 建议不超过 2000。超过就拆成多实例（按环境/按团队），避免 repo-server 渲染排队拖慢同步。
  • 备份 ArgoCD 配置：ArgoCD 的应用定义、项目定义都存在 etcd 里。定期 argocd admin export 导出全量配置到 Git，集群重建时一条 argocd admin import 恢复。

常见问题 FAQ

Q1：ArgoCD 装完 Web UI 打不开，Pod 都 Running 了还是 502？

最常见原因是忘了把 server Service 改成对外暴露的类型。默认安装 argocd-server 是 ClusterIP，只能集群内访问。如果你没配 Ingress，只能 kubectl port-forward svc/argocd-server 8080:443 -n argocd 临时访问。生产环境务必走 Ingress，并配置 backend-protocol: HTTPS 注解——ArgoCD server 默认监听 HTTPS。

Q2：ArgoCD 自己挂了，会影响正在运行的业务吗？

不会。ArgoCD 是一个"观察者 + 主动操作者"，它挂掉期间，已经运行的业务 Pod、Service、Ingress 都不受影响。失去的只是"自动同步"能力——Git 里有新提交，集群不会自动部署，直到 ArgoCD 恢复。这正是 GitOps 的优雅之处：控制面故障不会立刻传导到数据面。

Q3：ArgoCD 支持非 Kubernetes 的工作负载吗？

原生只支持 K8s 资源。它通过把 manifest 渲染成 YAML 然后 kubectl apply，本质是对 K8s API 的声明式提交。如果你要管虚拟机、数据库实例，那是 Crossplane 或 Terraform Controller 的领域，ArgoCD 可以作为上层编排器调用它们。

Q4：repo-server 经常 OOM 被 kill，怎么办？

典型症状是 Web UI 打不开某个应用的 manifest、同步报错 out of memory。原因是某个 Helm Chart 模板渲染时生成了巨量 YAML（比如模板里循环渲染了几千个 ConfigMap）。先把 repo-server 的内存 limit 临时调高观察，再去精简模板。长期方案是把大模板拆成多个 Application，或者用 Helm 的 --set 限制渲染范围。

总结

ArgoCD 的架构本质是"一个调谐引擎 + 一个渲染引擎 + 一个网关"。application-controller 是大脑，repo-server 是双手（负责把 Git 里的模板变成真实资源清单），server 是脸（给人看的）。安装本身不复杂，难的是生产化——HA、资源配额、RBAC、SSO。下一篇我们深入 Application CRD，看看"同步"这个动作到底是怎么一步步发生的。
