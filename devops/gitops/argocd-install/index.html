Argo CD 部署与生产化：对象模型、RBAC 与规模化调参

🏷️ ArgoCD

装 Argo CD 本身是一条命令的事：kubectl apply 官方清单，端口转发，用初始密码登进去。真正的工作量在「装完」到「能生产用」之间——默认配置里有一个全权限的 admin 账号、没有 TLS、任何登录者都能对任意应用点 sync、自身配置完全脱离 GitOps 管理。这篇只讲这段距离：对象模型怎么设计、装完立刻要改什么、RBAC 怎么切、哪些字段开错会直接删掉线上资源、以及规模化之后会在哪里撞墙。GitOps 的原理见 GitOps 的模型与纪律，从现有流水线迁过来的路径见 从 CI/CD 迁移到 GitOps。

核心对象模型：三个 CRD 与五个组件

Argo CD 的全部声明式入口只有三个自定义资源。把它们的职责分清楚，后面的权限设计和规模化才有地方落。

对象它是什么解决的问题用错的典型后果
Application一个同步单元：指向仓库的某个路径、某个 revision，以及目标集群与命名空间把「哪份配置同步到哪里」声明化粒度划太粗，一个 Application 指向仓库根目录，同步耗时失控、一处语法错误阻塞全部变更
ApplicationSet一个模板加一组 generator，展开成多个 Application20 个服务乘 3 个环境等于 60 个 Application，手写维护不现实默认删除 ApplicationSet 会级联删掉生成的 Application 及其管理的资源
AppProject权限与资源白名单边界：允许哪些仓库、哪些目标集群命名空间、哪些资源类型多团队共用一套 Argo CD 时的隔离全都丢进 default 项目，等于没有边界，任何应用可以往任意命名空间写任意资源

ApplicationSet 的 generator 该怎么选

ApplicationSet 存在的唯一理由是消灭手写重复。选 generator 的判据是「这批应用的差异从哪里来」：来自目录结构就用 Git Directory，来自集群列表就用 Cluster，来自两者的组合就用 Matrix。

apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: services-all-envs
  namespace: argocd
spec:
  # 用 Go 模板而不是旧的双花括号语法，后者与 Helm 模板容易互相干扰
  goTemplate: true
  goTemplateOptions:
    - missingkey=error          # 参数缺失时直接报错，而不是渲染出空字符串
  generators:
    - matrix:                   # 笛卡尔积：服务目录列表 乘 环境列表
        generators:
          - git:                # 自动发现 apps 下每个服务目录，新增即自动纳管
              repoURL: git@git.example.com:platform/config-repo.git
              revision: main
              directories:
                - path: apps/*
          - list:
              elements:
                - env: staging
                  cluster: https://staging.k8s.example.com
                  revision: main            # 非生产跟分支，push 即生效
                - env: prod
                  cluster: https://prod.k8s.example.com
                  revision: release-2026.09.3   # 生产跟 tag，发布是显式动作
  template:
    metadata:
      name: 'app-{{.path.basename}}-{{.env}}'
    spec:
      project: '{{.path.basename}}'
      source:
        repoURL: git@git.example.com:platform/config-repo.git
        targetRevision: '{{.revision}}'
        path: 'envs/{{.env}}/{{.path.basename}}'
      destination:
        server: '{{.cluster}}'
        namespace: '{{.env}}'
      syncPolicy:
        automated:
          prune: true
          selfHeal: true
  # 关键安全阀：默认删掉 ApplicationSet 会级联删除它生成的所有 Application
  # 及其管理的线上资源。生产上先保住资源，确认无误后再决定是否放开
  syncPolicy:
    preserveResourcesOnDeletion: true
❌
Git Directory generator 加通配符是一把快刀

它的好处是新增服务目录就自动多一个应用，不用改任何定义。风险是反过来也成立：有人误删或改名了 apps/ 下的目录，对应的 Application 就消失了，而 Application 消失会带走它管理的线上资源。生产环境务必配 preserveResourcesOnDeletion，并给 apps/ 目录加保护规则。

装完立刻要做的六件事

官方清单装出来的是一个「能跑通演示」的配置，不是可以对外提供服务的配置。下面六项在第一天做完，成本最低。

动作为什么必须做关键配置点不做的后果
改初始密码并关闭 admin 账号初始密码以明文存在一个 Secret 里，admin 拥有全部权限且不受 RBAC 约束argocd-cm 里设 admin.enabled: false，并删除初始密码 Secret共享 admin 账号会让所有审计记录都指向同一个身份，出事查不到人
接 SSO 并按组授权本地账号无法对应组织的人员流动，离职后需要手工清理配 OIDC 提供方，scopes 里带上 groups，RBAC 里绑组而不绑人权限随人数膨胀，回收靠记忆
仓库凭证用只读 deploy keyArgo CD 只需要读配置仓库，给写权限毫无必要用 SSH deploy key 并在仓库侧勾选只读；镜像更新组件单独用另一把有写权限的 key控制器被攻破后可以直接改仓库，等于同时拿下期望状态与实际状态
启用 TLS 与 Ingress默认自签证书，且很多教程让人用不安全模式直接暴露用正式证书终止 TLS；gRPC 与 HTTP 走同一端口时注意网关的协议配置登录凭证与 token 在链路上可被截获
把 Argo CD 自身纳入 GitOps 管理控制器的配置本身也是配置，脱离管理就成了最大的雪花节点建一个指向 platform/argocd 目录的 Application 来管自己，先手工 apply 一次完成引导没人知道 ConfigMap 被谁改过；重建集群时配置无法复现
配置通知拉取式部署没有流水线红灯，失败是静默的对同步失败、健康状态降级、长期 OutOfSync 三类事件分别配订阅发布失败几小时后才被用户发现
# 1. 改掉初始 admin 密码，然后彻底关闭该账号，全部走 SSO
argocd account update-password --account admin
kubectl -n argocd patch cm argocd-cm --type merge -p '{"data":{"admin.enabled":"false"}}'
kubectl -n argocd delete secret argocd-initial-admin-secret   # 明文初始密码不该长期留着

# 2. 仓库凭证用只读 deploy key，绝不要用个人的有写权限 token
argocd repo add git@git.example.com:platform/config-repo.git \
  --ssh-private-key-path ./deploy_key_readonly

# 3. 第一次开启 prune 之前必须看清它要删什么。带减号的行就是待删除资源
argocd app diff payment-prod --revision release-2026.09.3
argocd app sync payment-prod --dry-run --prune

# 4. 判读两个独立维度的状态，只看 Synced 会误判发布成功
argocd app get payment-prod -o wide

# 5. 确认 Argo CD 自己也被纳管了（self-management 是否真的生效）
argocd app get argocd-self -o json | jq -r '.status.sync.status, .spec.source.path'

# 6. 查最近的同步历史与触发者，排查谁点了 sync
argocd app history payment-prod

RBAC 设计：sync 权限等于发布权限

生产化里最该花时间的就是这一块。核心认知是：sync 不是刷新，sync 是发布。点一次 sync 就把仓库当前内容推到目标集群，如果仓库里已经合入了还没排期的变更，这一下就带进了生产，且绕过了所有发布窗口。对配了 prune 的应用，误触的 sync 还可能连带删除资源。

角色能看能 sync能改 Application 定义能进容器执行命令适用人群
viewer全部应用与日志不能不能不能默认角色，全员
dev本项目应用仅本项目非生产应用不能仅非生产，且建议关闭业务开发
releaser本项目应用本项目含生产不能不能值班与发布负责人
platform全部全部能，含 Project 与集群注册能，需单独审批平台与 SRE
apiVersion: v1
kind: ConfigMap
metadata:
  name: argocd-rbac-cm
  namespace: argocd
data:
  # 默认只读：未匹配任何策略的登录用户什么都改不了。这一行是整份配置的安全底线
  policy.default: role:readonly
  scopes: '[groups, email]'          # 从 SSO 取 groups，才能按组绑定
  policy.csv: |
    # 查看者：能看能读日志，但 sync 一律不给（sync 等于发布）
    p, role:viewer, applications, get, */*, allow
    p, role:viewer, logs, get, */*, allow

    # 开发者：只能同步自己项目下的非生产应用
    p, role:dev, applications, get, payment/*, allow
    p, role:dev, logs, get, payment/*, allow
    p, role:dev, applications, sync, payment/app-payment-staging, allow
    p, role:dev, applications, action/*, payment/app-payment-staging, allow
    p, role:dev, exec, create, payment/*, deny

    # 发布者：可以同步生产，但不能改 Application 定义本身，
    # 否则可以把 targetRevision 指到任意分支，绕过所有发布控制
    p, role:releaser, applications, get, payment/*, allow
    p, role:releaser, applications, sync, payment/app-payment-prod, allow
    p, role:releaser, applications, update, payment/*, deny
    p, role:releaser, applications, delete, */*, deny

    # 平台管理员：管 Project、仓库凭证、集群注册
    p, role:platform, projects, *, *, allow
    p, role:platform, repositories, *, *, allow
    p, role:platform, clusters, *, *, allow
    p, role:platform, applications, *, */*, allow

    # 绑定到 SSO 组而不是个人，人员变动无需改这份配置
    g, platform-sre,       role:platform
    g, payment-oncall,     role:releaser
    g, payment-developers, role:dev
    g, all-employees,      role:viewer
⚠️
给了 update 权限等于给了全部权限

能改 Application 定义的人，可以把 targetRevision 指向自己的分支、把 path 指向任意目录、把 destination 换成别的命名空间。所以「能 sync 生产」和「能改生产应用定义」必须分开：发布者只拿 sync，定义的变更走配置仓库的 PR。另外 exec 权限意味着能进生产容器执行命令，它绕过了 Git 审计链，默认应当拒绝。

Application 的关键字段与它们的坑

字段取值与默认开错的后果建议
targetRevision分支名、tag、commit 摘要，默认 HEAD写分支意味着任何人 push 到该分支就立刻进入这个环境，回滚要靠再推一次提交非生产跟分支，生产跟 tag 或 commit，让发布成为显式动作
syncPolicy.automated.prune默认 false会真的删除仓库里不再存在的资源。渲染出空清单时会整批删除被管资源第一次开启前必须 dry-run 确认待删列表；同时配 allowEmpty: false 与 PruneLast
syncPolicy.automated.selfHeal默认 false开了之后集群侧手工修改会被改回，救火时会与值班操作打架开启，但值班手册里要写清暂停单个应用同步的正确姿势
syncPolicy.automated.allowEmpty默认 false设为 true 且开了 prune 时，路径写错渲染出空清单会清空整个命名空间保持 false，这是防误删最有效的一道闸
syncOptions: CreateNamespace默认关闭目标命名空间不存在时同步直接失败开启；需要给命名空间打标签时配合 managedNamespaceMetadata
syncOptions: ServerSideApply默认关闭，用客户端 apply大型 CRD 会因为注解里存全量配置而超过对象大小上限，报注解过长开启，尤其是管理 CRD 或大清单时；它也让字段归属更清晰
syncOptions: ApplyOutOfSyncOnly默认关闭，每次全量 apply资源数量大时每次同步都把全部对象推一遍，拖慢调和并给 API Server 压力资源数超过几百时开启，只应用有差异的对象
ignoreDifferences默认空不排除 HPA 改写的副本数等字段，应用永远 OutOfSync，自愈还会把副本数改回去显式排除由其他控制器管理的字段，并配 RespectIgnoreDifferences 让同步阶段也遵守
finalizers默认无删除 Application 后它管理的资源变成无主对象，留在集群里没人管加资源回收 finalizer，但要清楚它意味着删应用就删资源
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: app-payment-prod
  namespace: argocd
  finalizers:
    # 删除 Application 时级联清理它管理的资源，否则会留下无主对象
    - resources-finalizer.argocd.argoproj.io
spec:
  project: payment              # 必须指定项目。default 项目没有任何白名单限制
  source:
    repoURL: git@git.example.com:platform/config-repo.git
    targetRevision: release-2026.09.3   # 生产用 tag，用分支等于任何 push 直接上线
    path: envs/prod/payment
  destination:
    server: https://kubernetes.default.svc
    namespace: prod
  syncPolicy:
    automated:
      prune: true               # 危险开关，第一次开启前必须 dry-run 看待删列表
      selfHeal: true
      allowEmpty: false         # 渲染出空清单时拒绝同步，防止路径写错清空命名空间
    syncOptions:
      - CreateNamespace=true
      - ServerSideApply=true    # 管理大 CRD 时必开，否则注解会超长度上限
      - ApplyOutOfSyncOnly=true # 只应用有差异的对象，资源多时显著降低调和耗时
      - PruneLast=true          # 删除动作放在最后，新资源就绪后再清理旧的
      - RespectIgnoreDifferences=true
    retry:
      limit: 3
      backoff:
        duration: 10s
        factor: 2
        maxDuration: 3m
  ignoreDifferences:
    # 副本数由 HPA 实时改写，不排除的话每次扩缩容都判定为漂移且会被自愈改回
    - group: apps
      kind: Deployment
      jsonPointers:
        - /spec/replicas
  revisionHistoryLimit: 10      # 保留的历史版本数，过大会让对象体积膨胀

同步状态与健康状态是两回事

界面上那两个徽标经常被当成一个东西看，但它们是完全独立的两个维度。Synced 只说明清单已经成功提交给集群 API Server，也就是期望状态写进去了；Healthy 才说明这些资源真的可用，比如 Deployment 的就绪副本数达到期望值、Service 有可用端点。只看 Synced 就宣布发布成功，是最常见的误判。

Sync 状态Health 状态实际含义第一步该查什么
SyncedHealthy正常稳定态无需处理
SyncedProgressing清单已应用，滚动更新还在进行中等待；超过预期时长就看 Pod 事件与探针配置
SyncedDegraded配置应用成功但资源起不来，例如镜像名写错、探针一直失败看 Pod 事件与容器日志，问题在清单内容而不在同步机制
OutOfSyncHealthy线上是好的，但与仓库有差异。可能是新提交未同步，也可能是集群侧漂移看 diff 输出判断差异来自哪一侧
OutOfSyncMissing仓库里声明了但集群里不存在，通常是从未同步过或被人删了确认是否被 prune 删除，查同步历史
UnknownUnknown无法取到仓库或目标集群，或渲染失败看 controller 与 repo-server 日志，多为凭证、网络或渲染错误
SyncedUnknown自定义资源没有健康判定逻辑，控制器不知道它算不算好为该 CRD 写 Lua 健康检查，否则整个应用的健康状态永远是未知

最后一行是接入 Operator 之后必然会遇到的问题。内置健康检查只覆盖常见的内置资源，自定义资源默认返回未知状态，而应用的整体健康是各资源健康的聚合，一个未知就会让整体判定失去意义，通知也就无从触发。解决办法是在 argocd-cm 里为该资源类型注册一段 Lua 脚本。

# argocd-cm 片段：给自定义资源补健康判定，否则它永远是 Unknown
data:
  resource.customizations.health.db.example.com_Database: |
    hs = {}
    -- obj 就是该资源的完整对象，按它的 status 约定写判定逻辑
    if obj.status ~= nil and obj.status.conditions ~= nil then
      for i, condition in ipairs(obj.status.conditions) do
        -- 先判失败态：失败要立刻上报，不能等超时
        if condition.type == "Failed" and condition.status == "True" then
          hs.status = "Degraded"
          hs.message = condition.message
          return hs
        end
        if condition.type == "Ready" and condition.status == "True" then
          hs.status = "Healthy"
          hs.message = "数据库实例就绪"
          return hs
        end
      end
    end
    -- 没有任何结论时返回 Progressing，而不是 Healthy。
    -- 返回 Healthy 会让同步波次提前推进到下一波，依赖顺序就失效了
    hs.status = "Progressing"
    hs.message = "等待实例就绪"
    return hs

同步波次与 hooks：把顺序声明出来

一次同步默认是并发应用所有资源的，顺序不确定。当资源之间有真实依赖（CRD 必须先于使用它的自定义资源、数据库迁移必须先于新版本代码、配置必须先于消费它的工作负载），就要用 sync-wave 注解显式排序：波次值从小到大依次应用，前一波全部健康之后才进入下一波，未标注的默认为 0，允许负数。

stateDiagram-v2 [*] --> PreSync PreSync: PreSync hook 例如数据库迁移 Job PreSync --> WaveLoop: hook 成功退出 PreSync --> SyncFailed: hook 失败 整次同步中止 WaveLoop: 按 sync-wave 从小到大逐波应用 WaveLoop --> WaveLoop: 当前波全部健康后进入下一波 WaveLoop --> SyncFailed: 某一波超时或资源降级 WaveLoop --> PostSync: 所有波次完成 PostSync: PostSync hook 例如冒烟测试 PostSync --> Done: 检查通过 PostSync --> SyncFailed: 检查失败 SyncFailed --> Cleanup: SyncFail hook 做清理与告警 Cleanup --> [*] Done --> [*] note right of PreSync 迁移必须幂等可重跑 自愈触发的同步也会重跑它 失败会阻塞整次同步 新版本上不去而旧版本仍在跑 因此迁移必须与旧版本代码兼容 end note

典型的波次安排是：负数波放 CRD 与命名空间级资源，0 波放 ConfigMap 与 Secret 引用，1 波放工作负载，2 波放 Ingress 与对外暴露。hook 则挂在同步生命周期上：PreSync 在所有波次之前跑，PostSync 在全部完成后跑，SyncFail 只在失败时跑。

⚠️
把数据库迁移放进 PreSync 之前，先确认三件事

一是幂等性：hook 会在每次同步时重跑，包括自愈触发的同步，所以迁移必须用版本表记录已执行变更，重复执行是常态而非异常。二是失败会阻塞整次同步：新版本代码上不去，而旧版本仍在服务，如果迁移已部分执行，数据库会处于中间状态。三是必须向后兼容：从迁移完成到新版本 Pod 全部就绪之间有一个窗口，旧代码还在读写新结构，加字段安全，删字段和改类型必须拆成多次发布。数据库兼容演进的详细做法见站内 部署策略 篇。

规模化之后会在哪里撞墙

几十个 Application 的时候一切都好。到几百个、跨十几个集群时，瓶颈会集中在 repo-server 的渲染和 application-controller 的调和上，表现为界面卡、状态延迟、同步排队。

症状根因调整手段该盯的指标
同步排队，状态更新延迟几分钟单个 controller 处理不完所有集群的调和开启 controller 分片，按集群哈希分片，副本数与集群数匹配；调 --status-processors 与 --operation-processorsargocd_app_reconcile_bucket 的 P99，超过 30 秒就要动手
渲染超时，应用报无法获取清单大仓库克隆慢或渲染进程被打满调大 --repo-server-timeout-seconds（默认 60），扩 repo-server 副本，限制并发渲染数argocd_git_request_total 按请求类型分组的速率
仓库拉取次数居高不下渲染缓存命中率低，常见于 targetRevision 用分支导致 revision 频繁变化生产改用 tag；延长缓存过期时间；为同一仓库的多个应用复用缓存缓存未命中导致的 ls-remote 调用速率
单次同步耗时几分钟单个 Application 管的资源数过多，每次全量 apply拆分 Application 粒度；开 ApplyOutOfSyncOnly；开 ServerSideApply单应用资源数量与同步耗时的关系
内存持续增长直到被驱逐集群内资源对象总量大，controller 要缓存全量资源树用资源排除配置把不需要纳管的类型排除；给 controller 加内存上限并观察controller 容器的工作集内存与 OOM 次数
大仓库首次克隆极慢历史长、文件多，每个 repo-server 副本都要完整克隆启用浅克隆与稀疏检出，只拉需要的子目录；或按业务域拆分配置仓库克隆耗时与 repo-server 磁盘用量

自身的高可用与灾备

这里有一个相对于传统 CD 工具的结构性优势：Argo CD 几乎没有自己的持久状态。Application 定义是集群里的 CRD 对象，期望状态在 Git 里，Redis 里全是可重建的缓存。所以灾备方案可以很简单——备份 CRD 对象（或者干脆把它们也放进 Git，由 bootstrap 定义生成），重装一遍控制器，指向同一个仓库，状态自然恢复。需要单独保管的只有仓库凭证、集群注册信息和 SSO 配置这些无法从 Git 重建的密钥类数据。

关注点做法为什么
组件高可用API Server 与 repo-server 多副本无状态扩容；controller 用分片而不是简单多副本controller 对同一集群必须单写，靠分片划分职责而不是靠选举抢锁
Redis用 HA 模式但不必追求强持久化里面全是缓存，丢了只导致一次全量重新渲染
灾备恢复把 bootstrap 定义与自身配置都放进 Git，只手工引导一次恢复过程等于重跑引导，不依赖任何备份文件
控制面位置不要把 Argo CD 只装在它所管理的唯一集群里该集群整体故障时，既没有控制面驱动恢复，也拿不到它管理的状态视图
版本升级先读版本说明里的 CRD 变更与默认值变更，按次版本逐级升；升级前导出 Application 对象跨多个次版本直升容易遇到 CRD 字段不兼容；默认值变更曾导致同步行为静默改变
升级顺序先在非生产集群升，观察一个完整调和周期与一次真实发布渲染行为和健康判定的细微变化只有在真实同步时才暴露

反模式

反模式表现后果正确做法
全员共用 admin把初始 admin 密码发到群里所有审计记录指向同一身份，出事查不到人；admin 不受 RBAC 约束关闭 admin，接 SSO 按组授权，默认角色设为只读
关掉 selfHeal 又不管漂移嫌自愈碍事直接关掉，也没配漂移告警退化成「只同步不调和」，手工改动长期存活，仓库不再代表线上保留自愈，把暂停同步的正确姿势写进值班手册
一个 Application 管整个集群指向仓库根目录，覆盖所有命名空间同步耗时几分钟，一处语法错误阻塞全部变更，权限无法按团队切分按服务或团队拆分，用 ApplicationSet 管理数量

开 prune 不看 dry-run照教程把 prune 和 allowEmpty 一起打开路径写错渲染出空清单时，整个命名空间被清空先 dry-run 确认待删列表，allowEmpty 保持 false，加 PruneLast
所有应用都丢进 default 项目不建 AppProject没有仓库与目标命名空间白名单，任何应用能往任意位置写任意资源按团队或业务域建 Project，限定仓库、目标与资源类型

❌
最容易踩的坑

1. 第一次开 prune: true 没做 dry-run。仓库路径写错或 overlay 引用断裂渲染出空清单时，所有被管资源都成了多余资源，会被整批删除。

2. 把 allowEmpty 设成 true 图省事。它和 prune 组合起来就是清空命名空间的开关。

3. 生产 targetRevision 写分支名。任何人往该分支 push 都会在一个调和周期内直接进生产，发布完全不可控。

4. 只看 Synced 就宣布发布成功。Synced 只代表清单已应用，Healthy 才代表 Pod 起来了；镜像名写错时状态是 Synced 加 Degraded。

5. 接了 Operator 却没写 Lua 健康检查。自定义资源一直是 Unknown，拖累整个应用的健康聚合，通知条件永不触发。

6. Lua 健康检查在拿不到结论时返回 Healthy。同步波次会提前推进到下一波，依赖顺序形同虚设。

7. 数据库迁移 hook 不幂等。自愈触发的同步会重跑 PreSync，非幂等脚本第二次执行就报错或重复处理数据。

8. 忘记加 CreateNamespace=true，新环境首次同步直接失败，而错误信息看起来像权限问题。

9. 管理大型 CRD 时没开 ServerSideApply，客户端 apply 把全量配置塞进注解，超过对象大小上限后同步失败。

10. 给发布者开了 update 权限。他可以把 targetRevision 指向自己的分支，绕过全部发布控制。

11. 删 ApplicationSet 时没配 preserveResourcesOnDeletion，级联删掉了它生成的所有 Application 及线上资源。

12. 跨多个次版本直接升级。CRD 字段与默认值的变更会让同步行为静默改变，必须逐级升并先在非生产验证一次真实发布。
