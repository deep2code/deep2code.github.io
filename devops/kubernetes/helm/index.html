Helm 的模板机制与它的适用边界

🏷️ Helm

Helm 的所有行为，包括那些让人摸不着头脑的报错，都能用两件事解释清楚：它是一个文本模板渲染器，外加一套 Release 状态跟踪机制。把这两点想透，缩进为什么会错、rollback 到底回滚了什么、为什么有人改了线上 Helm 不知道，全都是推论。这篇先给能直接跑的最小 chart 与一条完整的发布命令序列，再往下拆渲染与 Release 机制，最后回答「什么时候该用 Helm、什么时候用 Kustomize、什么时候只把它当渲染器」。

💡
这篇怎么读
  • ① 用法：最小可用的 chart 目录与四个文件的内容、一条从 lint 到 install 到 upgrade 到 rollback 的完整命令序列、一张「要做什么 → 用哪个命令或写在哪」对照表，以及 -f、--set、--atomic、--wait、--timeout 的「不加会出什么现象」速查。
  • ② 原理：渲染是纯文本替换因而缩进全归你负责、values 多层合并与列表整体替换、Release 快照与六个状态的流转、三向合并补丁为什么会改回手工改动、hooks 不受回滚保护、依赖锁文件与该参数化什么。
  • ③ 场景：Helm 与 Kustomize 与「只渲染不安装」三条路的取舍矩阵，以及七条反模式对应的正确做法。

① 用法 · 最小可用 chart 与一条完整的发布序列

先把结构立起来。一个自有应用的 chart 只需要四个文件，多出来的每一个都是后面要维护的负担：

charts/api/
├── Chart.yaml          # 名字、chart 版本、appVersion、依赖声明
├── values.yaml         # 默认值。它就是这个 chart 的对外契约，写进来就等于承诺支持
├── .helmignore         # 打包时排除的文件；不写会把本地 values-prod.yaml 一起打进包里
└── templates/
    ├── _helpers.tpl    # 命名与标签的命名模板，避免每个文件各写一套导致 selector 对不上
    ├── deployment.yaml
    └── service.yaml

下面是这四个文件的最小可用内容。注释只说明为什么要这行：

# ---------- Chart.yaml ----------
apiVersion: v2
name: api
version: 0.1.0            # chart 自身版本，改了模板就要改它，否则仓库缓存认不出变化
appVersion: "9f3c2a1"     # 应用版本，必须写成字符串，否则数字型 tag 会被 YAML 变形
---
# ---------- values.yaml：只放「不同安装之间会取不同值」的字段 ----------
image:
  repository: registry.example.com/api
  tag: ""                 # 留空则回退到 Chart.appVersion，避免两处版本号打架
replicaCount: 2
service:
  port: 80
  targetPort: 8080
resources:
  requests: {cpu: 200m, memory: 256Mi}
  limits: {memory: 512Mi}
extraEnv: []              # 必须留这个追加口，原因见原理层「列表是整体替换」
---
# ---------- templates/_helpers.tpl 的等价内容（实际写在 .tpl 文件里） ----------
# {{- define "api.name" -}}{{ .Chart.Name }}{{- end }}
# {{- define "api.selectorLabels" -}}
# app.kubernetes.io/name: {{ include "api.name" . }}
# app.kubernetes.io/instance: {{ .Release.Name }}
# {{- end }}
---
# ---------- templates/deployment.yaml ----------
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ .Release.Name }}-api
spec:
  replicas: {{ .Values.replicaCount }}
  selector:
    matchLabels:
      {{- include "api.selectorLabels" . | nindent 6 }}   # selector 创建后不可改，只放恒定键
  template:
    metadata:
      labels:
        {{- include "api.selectorLabels" . | nindent 8 }} # 必须与上面 selector 完全一致
    spec:
      containers:
        - name: api
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag | default .Chart.AppVersion }}"
          ports:
            - containerPort: {{ .Values.service.targetPort }}
          resources:
            {{- toYaml .Values.resources | nindent 12 }}  # 插结构化块必须带缩进，原因见原理层
          {{- with .Values.extraEnv }}
          env:
            {{- toYaml . | nindent 12 }}
          {{- end }}
---
# ---------- templates/service.yaml ----------
apiVersion: v1
kind: Service
metadata:
  name: {{ .Release.Name }}-api
spec:
  selector:
    {{- include "api.selectorLabels" . | nindent 4 }}     # 与 Deployment 用同一个命名模板
  ports:
    - port: {{ .Values.service.port }}
      targetPort: {{ .Values.service.targetPort }}

然后是发布。下面这条序列可以原样抄进流水线，顺序本身就是防线——每一步都是在「还能便宜地发现问题」的阶段发现问题：

# 1. 语法与最佳实践检查。它发现不了缩进以外的语义问题，但成本最低
helm lint ./charts/api -f values-prod.yaml

# 2. 渲染出来自己看。排查模板问题的第一步永远是看渲染结果，不是盯着模板猜
helm template api ./charts/api -f values-prod.yaml | less
helm template api ./charts/api -f values-prod.yaml | kubectl apply --dry-run=server -f -

# 3. 看清这次到底会改什么（helm-diff 插件，强烈建议装）
helm diff upgrade api ./charts/api -f values-prod.yaml -n prod

# 4. 首次安装。install 与 upgrade 合成一条，流水线里不需要判断是否首次
helm upgrade --install api ./charts/api -f values-prod.yaml \
  -n prod --create-namespace \
  --atomic --wait --timeout 10m

# 5. 确认状态与版本历史。REVISION 与 STATUS 两列是后面回滚的依据
helm -n prod status api
helm -n prod history api

# 6. 回滚到上一个 deployed 的 revision。注意它只重放渲染快照，不撤销数据变更
helm -n prod rollback api 6 --wait --timeout 10m

# 7. 卸载。默认会删掉 Release 记录，加 --keep-history 才留下可回滚的痕迹
helm -n prod uninstall api --keep-history

日常操作按下表查表就能干活，左列是你真正要做的事：

处理卡在 pending-upgrade 的 Releasehelm history 找到最后一个 deployed，再 helm rollbackrollback 也被拒时删掉最后那条 Release Secret，原因见原理层

values 的覆盖顺序从低到高是：子 chart 的 values → 父 chart 的 values → 各个 -f 文件（按命令行先后，后面覆盖前面）→ --set 系列。加上下面几个参数的行为，构成了「为什么我设了却没生效」的全部答案：

参数作用不加或用错会出什么现象
-f 的顺序多个值文件按命令行顺序叠加把通用文件写在环境文件后面，通用值会反向覆盖掉环境特有值，且渲染结果完全合法，不报任何错
--set 与 --set-string命令行覆盖，优先级最高--set image.tag=1.28 被当成浮点数，渲染出 1.28 以外的形态或直接报无法反序列化；tag 一律用 --set-string
--reuse-values以上一次 Release 的 values 为基础再叠加本次你从值文件里删掉一项不会生效，因为旧值还在；越用越糊，最后没人知道当前生效的是什么
--atomic失败时自动回滚到上一个 revision不加时失败现场停在中间态：一半对象是新的一半是旧的，且 Release 可能卡在 pending-upgrade
--wait等对象真正就绪才算成功不加时提交完对象就返回成功，流水线绿灯而 Pod 正在 CrashLoopBackOff，故障延后暴露
--timeout等待就绪的上限，默认 5 分钟默认值对慢启动应用偏紧，超时后 Release 进入 failed；而 CI 侧超时杀掉 helm 进程会让它卡在 pending-upgrade
--create-namespace命名空间不存在时创建不加时首次安装直接报命名空间不存在，流水线首跑必失败一次
--dry-run=server提交给 apiserver 做校验但不落库不做这一步时字段类型错误、准入策略拒绝要等到真正 apply 才暴露

上面这些参数的默认值随 Helm 版本变化（尤其是 --timeout 与 --wait 的等待判定范围），落地前用 helm upgrade --help 核对你手上这个版本的实际行为。为什么缩进要自己管、为什么 rollback 不撤销数据、为什么手工改动会被改回去，都在下面几节。

② 原理 · Helm 的两个核心

搞清这一节能解释一整类报错：为什么 Helm 会说「mapping values are not allowed in this context」而你的模板看起来毫无问题。Helm 解决的问题是：把一组 K8s 对象打包成可参数化、可版本化、可一键安装卸载的单元。实现方式非常朴素——先把 values 逐层合并，再用 Go template 把 templates/ 下的文件渲染成字符串，最后把字符串交给 YAML 解析器，得到对象提交给 apiserver，同时把这份渲染结果原样存下来当作 Release 记录。声明式交付与 Argo CD 的部分见 GitOps 系列，流水线里怎么串这些命令见 CI 与流水线。

flowchart TB subgraph CHART["chart 目录：输入"] CY["Chart.yaml 元数据与 dependencies"] VY["values.yaml 默认值"] TPL["templates 目录下的模板文件"] HLP["_helpers.tpl 命名模板"] SUB["charts 目录：子 chart 与打包好的依赖"] end subgraph RENDER["渲染阶段：纯文本处理，不理解 YAML 结构"] MERGE["values 多层合并成一棵值树"] GO["Go template 引擎逐文件渲染成字符串"] PARSE["把渲染出的字符串当 YAML 解析"] end subgraph OUT["两个产物"] OBJ["提交到 apiserver 的对象"] REL["Release 记录：整份渲染结果存成 Secret"] end CY --> MERGE VY --> MERGE SUB --> MERGE MERGE --> GO TPL --> GO HLP --> GO GO --> PARSE PARSE --> OBJ PARSE --> REL

注意 PARSE 那一步在 GO 之后：渲染期间 Helm 完全不知道自己在生成 YAML。缩进、引号、类型全部由你在模板里负责。这一个事实就能解释大半的 Helm 报错。

② 原理 · 模板的实质是字符串替换

搞清这一节能解决「模板看着对但渲染结果结构错了」这类问题，下表每一行都是一次真实的排查。

需求正确写法写错会发生什么
把一个结构化对象插到指定缩进层级{{- toYaml .Values.resources | nindent 12 }}只写 toYaml 不加缩进，渲染出的块从第一列开始，解析报 mapping values are not allowed in this context
选 indent 还是 nindent前面已有换行用 indent，否则用 nindent（它先补一个换行）用错会让键粘在上一行末尾，或多出一个空行让块脱离父级
值可能是纯数字或布尔样式{{ .Values.image.tag | quote }}1.28 被解析成浮点、true 和 on 被解析成布尔、0755 前导零丢失，报 cannot unmarshal number into Go struct field
缺省值{{ .Values.port | default 8080 }}值为空时渲染出空串，字段变成 null，apiserver 报字段类型错误
必填项{{ required "image.tag 必须显式指定" .Values.image.tag }}渲染出空值，一路提交到集群才报错，排查要绕一大圈
去掉控制语句留下的空行统一写 {{- if ... }} 与 {{- end }}产生大量空行，极端情况下出现只有空白的文档，被解析成 null 对象

apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ include "api.fullname" . }}
  labels:
    {{- include "api.labels" . | nindent 4 }}
spec:
  {{- if not .Values.autoscaling.enabled }}
  replicas: {{ .Values.replicaCount }}   {{/* 用 HPA 时绝不要渲染 replicas，否则每次 upgrade 打回初始值 */}}
  {{- end }}
  selector:
    matchLabels:
      {{- include "api.selectorLabels" . | nindent 6 }}
  template:
    metadata:
      annotations:
        {{/* 配置内容哈希：ConfigMap 变了才触发滚动更新，做法见配置与密钥篇 */}}
        checksum/config: {{ include (print $.Template.BasePath "/configmap.yaml") . | sha256sum | trunc 8 }}
      labels:
        {{- include "api.selectorLabels" . | nindent 8 }}
    spec:
      {{- with .Values.imagePullSecrets }}
      imagePullSecrets:

      {{- end }}

          resources:
            {{ toYaml .Values.resources }}

values 的覆盖是分层的，理解顺序才能解释「我明明设了为什么没生效」：

优先级来源说明
最低子 chart 自己的 values.yaml依赖组件的默认值
↓父 chart 的 values.yaml覆盖子 chart 要写在以子 chart 名（或 alias）为键的子树下
↓-f 指定的文件多个 -f 按命令行顺序生效，后面的覆盖前面的
最高--set、--set-string、--set-file会覆盖一切；--set-string 强制当字符串，避免 tag 被当数字
特殊--reuse-values以上一次 Release 的 values 为基础再叠加本次；它会让「删掉一个 values 项」失效，因为旧值还在
⚠️
列表不是合并而是整体替换

values 合并对 map 是逐键深合并，但对列表是整体替换。所以你想「在默认的 env 列表里再加一项」时，实际结果是把默认那几项全部干掉只剩你加的那一项。想追加就必须由 chart 提供一个专门的 extraEnv 之类的字段，而不是覆盖原字段。

② 原理 · Release 与状态：rollback 到底回滚了什么

搞清这一节能解决两个现象：Release 卡在 pending-upgrade 后所有操作都被拒，以及回滚之后应用行为并没有完全回到旧版本。Helm 3 把每次操作的渲染结果存成一个 Secret，名字形如 sh.helm.release.v1.api.v7，带 owner=helm 标签，默认放在 Release 所在的命名空间。helm rollback 的实现就是取出旧 revision 的那份渲染快照重新应用一遍——它不做任何逆向推导，也不知道你的应用语义。

stateDiagram-v2 [*] --> pending_install state "pending-install" as pending_install state "deployed" as deployed state "failed" as failed state "pending-upgrade" as pending_upgrade state "superseded" as superseded state "uninstalling" as uninstalling pending_install --> deployed: 全部对象创建成功 pending_install --> failed: 任一对象创建失败或超时 deployed --> pending_upgrade: helm upgrade 开始写入新 revision pending_upgrade --> deployed: 新 revision 成功，上一个转为 superseded deployed --> superseded: 被更新的 revision 取代 pending_upgrade --> failed: 超时、校验失败或 hook 失败 failed --> pending_upgrade: 再次执行 upgrade deployed --> uninstalling: helm uninstall uninstalling --> [*] note right of pending_upgrade CI 的超时把 helm 进程杀掉，Release 就永久停在这里 再次 upgrade 会报另一个操作正在进行中 先 helm history 看清 revision，再 rollback 到上一个 deployed 的版本 rollback 也被拒绝时，删掉最后那条处于 pending 状态的 Release Secret end note
状态含义典型原因处理动作
deployed当前生效的 revision正常无
superseded已被新 revision 取代的历史版本正常作为 rollback 目标存在
pending-install首次安装未收尾进程被杀、镜像拉不下来导致等待超时helm uninstall 后重装；首次安装没有可回滚的目标
pending-upgrade升级未收尾最常见：CI 任务超时杀掉了 helm 进程helm rollback 到上一个 deployed 的 revision；不行则删掉该条 Release Secret
failed操作明确失败对象被 apiserver 拒绝、hook 返回非 0、等待就绪超时看清失败对象再修 chart；加 --atomic 可让失败自动回滚
uninstalling卸载中有对象带 finalizer 卡住先处理卡住的 finalizer，见 主干篇

由「Release 是一份快照」还能推出另一个结论：如果有人用 kubectl edit 改了线上，Helm 的记录里完全没有这件事。helm get manifest 给你的是上次渲染结果，不是集群现状。想知道差异只能自己比。

② 原理 · 三向合并补丁

搞清这一节能解决一个很隐蔽的现象：每次发布副本数先掉回初始值，几分钟后才被 HPA 扩回来，而发布窗口正好是流量高峰。

sequenceDiagram autonumber participant Helm as helm upgrade participant Store as Release 记录 Secret participant API as apiserver Helm->>Store: 取出上一个 revision 的渲染结果，记作 old Helm->>Helm: 用本次 values 渲染出 new Helm->>API: 读取集群中对象的当前状态，记作 live Helm->>Helm: 比较 old、live、new 三者生成补丁 Note over Helm: old 有而 new 没有的字段，生成删除指令 Note over Helm: new 与 old 不同的字段，以 new 为准 Note over Helm: chart 里声明过的字段，即使 live 被手工改过也会被改回 new Note over Helm: chart 从未声明的字段，保留 live 上的值不动 Helm->>API: 提交补丁 Note over Helm,API: 因此用 HPA 管副本数时，chart 里千万不要渲染 replicas

Helm 2 用的是两向合并，只比 old 与 new，所以手工改过的字段能一直存活。Helm 3 引入三向合并后，线上手工改动会在下一次 upgrade 时被拉回 chart 声明的值——这通常是好事，但在两个场景下会咬人：一是 chart 写了 replicas 而副本数由 HPA 管，每次发布都会先把副本打回初始值，容量塌一下再由 HPA 扩回来；二是某些控制器会往对象上写字段（例如注入 sidecar 或补默认注解），如果 chart 恰好也声明了同名字段，就会出现两边来回改写的抖动。

② 原理 · hooks：能跑迁移，但不受回滚保护

搞清这一节能避免 Helm 使用中最容易造成真实事故的一处：回滚之后旧代码面对的是新表结构。

hook时机典型用途要注意什么
pre-install渲染完成、对象创建之前初始化数据库 schema失败会让整次安装失败并可能停在 pending-install
pre-upgrade新对象提交之前数据库迁移迁移必须幂等且向后兼容旧版本代码，因为此刻旧 Pod 还在跑
post-upgrade对象提交之后缓存预热、通知此时新 Pod 可能还没全部就绪
pre-rollback 与 post-rollback回滚前后反向迁移需要你自己写反向逻辑，Helm 不会替你撤销任何数据变更
testhelm test 时冒烟检查不在 install 与 upgrade 流程里自动执行

最需要记住的一条：hook 产生的资源不属于 Release 的托管范围，也不参与三向合并。这意味着 helm rollback 会把 Deployment 换回旧镜像，但 pre-upgrade 里已经执行完的数据库迁移不会被撤销。于是回滚之后旧版本代码面对的是新版本的表结构——如果迁移不是向后兼容的，这一步就直接出故障。另外 helm.sh/hook-delete-policy 默认是 before-hook-creation，意思是下次创建时才删上次的，所以集群里会长期留着最后一次的 hook Job；要立刻清理就加 hook-succeeded。

② 原理 · 依赖管理与该参数化什么

搞清这一节能解决「同一个 commit 在不同时间渲染出不同结果」以及「values.yaml 涨到几百行之后没人敢改」这两类长期问题。

# Chart.yaml：依赖声明与版本约束
apiVersion: v2
name: api
version: 1.4.2          # chart 自身版本，改模板就要改它
appVersion: "9f3c2a1"   # 应用版本，写成字符串避免被当数字
dependencies:
  - name: redis
    version: 19.6.4     # 固定到补丁版本；写 ^19.0.0 会让不同时间构建出不同结果
    repository: https://charts.bitnami.com/bitnami
    condition: redis.enabled        # 由 values 控制是否安装，比注释掉整段干净
  - name: postgresql
    version: 15.5.20
    repository: https://charts.bitnami.com/bitnami
    condition: postgresql.enabled
    alias: maindb                   # 有 alias 时，覆盖路径变成 maindb 而不是 postgresql
---
# values.yaml：覆盖子 chart 的值必须写在以子 chart 名或 alias 为键的子树下
redis:
  enabled: true
  architecture: standalone          # 这些键会传给 redis 子 chart
  auth:
    existingSecret: redis-auth      # 密钥来源见配置与密钥篇，不要写明文
maindb:
  enabled: false
# 自有应用的值放在顶层
image:
  repository: registry.example.com/api
  tag: ""                           # 留空则回退到 Chart.appVersion
resources:
  requests: {cpu: 300m, memory: 512Mi}
  limits: {memory: 1Gi}
autoscaling:
  enabled: true                     # 开了它，模板里就不要渲染 replicas
extraEnv: []                        # 提供追加口，因为列表覆盖是整体替换而不是合并

helm dependency update 会按上面的声明拉取依赖到 charts/ 并生成 Chart.lock。锁文件必须入库——它记录了依赖的精确版本和摘要，不入库就等于放弃了构建可复现性，几个月后同一个 commit 渲染出来的东西可能已经变了。

关于「该参数化什么」，唯一有用的判断标准是：这个字段会不会在不同安装之间取不同的值。会，才做成 values；不会，直接写死在模板里。把每个字段都做成 values 的结果是模板比原始 YAML 更难读，而且 values 的组合空间大到无法测试。一个实用的分界：镜像、副本与伸缩、资源规格、对外暴露方式、依赖开关、存储大小与 StorageClass 这几类必须参数化；探针路径、标签规范、安全上下文这些全公司统一的东西写死更好。

# Release 记录就是一批带 owner=helm 标签的 Secret
kubectl -n prod get secret -l owner=helm,name=api --sort-by=.metadata.creationTimestamp

# 卡在 pending-upgrade 的处理顺序
helm -n prod history api                      # 找到最后一个 deployed 的 revision
helm -n prod rollback api 6                   # 回到该 revision，状态会推回正常
# 若 rollback 也被拒绝，删掉最后那条 pending 的 Release Secret 再重试
kubectl -n prod delete secret sh.helm.release.v1.api.v8

# 对比「Helm 认为的清单」与「集群实际状态」，找出被手工改过的地方
helm -n prod get manifest api | kubectl diff -f -

# 看这次 upgrade 实际用的完整 values（排查「子 chart 的值写在顶层」时最有用）
helm -n prod get values api --all

③ 场景 · 选 Helm、选 Kustomize，还是只把 Helm 当渲染器

这三条路不是竞品关系，而是三种不同的职责划分。先看「只渲染不安装」这条路放弃了什么：

维度helm install 与 upgradehelm template 加 kubectl apply
Release 跟踪有，helm list、helm history 可用完全没有，helm 侧看不到任何记录
回滚方式helm rollback 重放旧快照回退 Git 提交，由控制器重新同步
删除已移除的对象Helm 依据 old 与 new 的差集自动删需要 kubectl apply --prune 或由控制器按标签跟踪
hooks按时机执行不执行，迁移要改成控制器的同步钩子或独立 Job
三向合并Helm 自己算补丁交给 apiserver 的服务端应用与字段所有权机制
适合手工安装第三方组件、本地实验声明式交付，见 GitOps 系列

在声明式交付下，主流做法是只把 Helm 当渲染器，应用与纠偏交给控制器。这个取舍要想清楚：你放弃了 Release 跟踪，换来单一事实来源和自动纠偏。放弃之后 helm list 不再反映真实情况，任何依赖 Release 记录的运维习惯都要改掉。

flowchart TB START["要管理一组 K8s 清单"] --> Q1{"是第三方组件还是自有应用"} Q1 -- 第三方组件 --> HELM["直接用社区 chart，values 就是它的对外契约"] Q1 -- 自有应用 --> Q2{"需要分发给外部使用者安装吗"} Q2 -- 需要 --> HELM2["写成 chart，把可配置项收敛成 values"] Q2 -- 不需要 --> Q3{"环境差异是少量字段还是结构性差异"} Q3 -- 少量字段 --> KUST["Kustomize overlay，清单保持原生可读 YAML"] Q3 -- 结构性差异 --> Q4{"差异能否用 patch 表达"} Q4 -- 能 --> KUST Q4 -- 不能 --> BOTH["先 helm template 渲染再用 Kustomize 后处理"]
维度HelmKustomize
参数化能力强，有条件、循环、函数，能表达任意逻辑弱，只能打补丁、改镜像、加前后缀、生成配置对象
可读性模板本身不是合法 YAML，必须渲染后才能看基线就是能直接 kubectl apply 的原生 YAML
是否引入新语言是，Go template 加 Sprig 函数库否，只有一份声明式的 kustomization 配置
适合场景分发与安装第三方组件管理自有应用的多环境差异
与声明式交付的配合控制器一般只用它渲染，Release 跟踪被放弃天然契合，控制器原生支持覆盖层
多环境表达多个 values 文件，差异分散在模板的条件分支里overlay 目录，差异集中且可直接 diff
调试方式helm template 看渲染结果kubectl kustomize 看合并结果
依赖管理有，Chart.yaml 的 dependencies 加锁文件无包概念，靠远程 base 的 Git 引用

把上面的判断按具体处境收成一张表，代价那一列是真正决定选择的东西：

场景该怎么做为什么代价
装第三方组件（Ingress Controller、Prometheus、数据库 Operator）直接用社区 chart，把 values 入库values 就是它的对外契约，升级路径由维护者负责要跟着上游的 values 结构变化改；大版本升级常伴随字段重命名
自有应用，环境差异只有镜像标签、副本数与几个开关Kustomize overlay，清单保持原生 YAML基线可直接 apply，差异集中在一个目录里，可直接 diff 评审表达能力弱，遇到需要条件与循环的结构性差异就撑不住
自有应用要分发给别的团队或客户安装写成 chart，把可配置项收敛成 values使用者只需要懂 values，不需要读你的清单你要为 values 的每个字段做长期兼容承诺，删字段就是破坏性变更
几十个服务共用同一套部署形态一个公共 library chart 加每个服务一份 values探针、标签、安全上下文这类全公司统一的东西只写一次公共 chart 变成核心依赖，改它等于同时改几十个服务，必须有灰度机制
已经在做声明式交付，集群由控制器纠偏只把 Helm 当渲染器，应用与回滚交给控制器换来单一事实来源与自动纠偏放弃 Release 跟踪与 hooks，helm list 不再反映真实情况，迁移要改成独立 Job
需要在部署过程中跑数据库迁移pre-upgrade hook，且迁移必须幂等且向后兼容它是唯一能卡在「新对象提交之前」的时机hook 不受回滚保护，破坏性变更必须拆成多次发布
生产发布要求失败不留中间态--atomic --wait --timeout 三件套一起加失败自动回滚，且「成功」的定义变成对象真的就绪发布耗时变长；超时值设太短会把慢启动应用判成失败并触发回滚
只是想在本地跑一下看看helm template 看渲染结果，别装进集群渲染是纯本地操作，零副作用看不到准入策略与字段校验的结果，需要时再加 --dry-run=server

不适用边界：Helm 不负责「集群里该有哪些对象」这件事的正确性——工作负载怎么选与字段怎么填在 工作负载对象的选择与编写，配置与密钥不要写进 values 的理由在 配置与密钥在集群里的落地；镜像的构建与标签策略在 Docker，流水线怎么串这些命令在 CI 与流水线；多环境的单一事实来源与自动纠偏在 GitOps 系列；发布之后「这次上线有没有把指标搞坏」的判断在 可观测性系列。

③ 场景 · 反模式

反模式症状后果正确做法
把每个字段都做成 valuesvalues.yaml 几百行，模板里满是 with 与 if比直接写 YAML 更难读，组合空间大到无法测试只参数化「不同安装之间会取不同值」的字段
模板里写复杂逻辑嵌套的 range 套 if，还有字符串拼接出的 key渲染结果无法预测，改一行要靠反复 helm template 试逻辑上移到 values 结构或 CI 生成，模板只做填空
用一堆 --set 发布发布命令是一行几百字符的 --set a=1 --set b=2不可复现、无法评审、出事后不知道当时传了什么values 文件入库，用 -f 引用；命令行只留 namespace 这类环境参数
hooks 里跑不幂等的迁移重试一次 upgrade 就报唯一键冲突回滚后旧代码面对新表结构，直接故障迁移必须幂等且向后兼容；破坏性变更拆成多次发布
生产用 helm install 但不记录 values只有操作者本机有那份 values 文件换人接手无法复现，--reuse-values 越用越糊values 一律入库，或直接改用声明式交付
依赖不锁版本Chart.lock 不入库，依赖写 ^19.0.0同一个 commit 在不同时间渲染出不同结果依赖固定到补丁版本，锁文件入库
用 HPA 却在 chart 里渲染 replicas每次发布副本数先掉回初始值发布窗口容量塌陷，HPA 再慢慢扩回来开了 autoscaling 就用条件语句把 replicas 整行去掉

本篇在这条路径上负责把清单的重复消除掉、把发布变成可回滚的动作。Helm 的两个核心——纯文本渲染与 Release 快照——足以推出几乎所有它的行为与边界。路径走到这里，集群上跑什么、配置怎么给、数据放哪、流量怎么进、清单怎么复用都有了答案，剩下的就是它真的出问题时该怎么查。

✅
最容易踩的坑
  • 模板不理解 YAML 结构：渲染是纯文本替换，缩进完全由你负责，插块一律 toYaml 加 nindent。
  • image tag 忘了 quote：1.28 被当浮点、true 和 on 被当布尔、0755 前导零丢失，报 cannot unmarshal number 就是这个原因。
  • values 里列表是整体替换不是合并：想追加一项却把默认几项全干掉了，chart 要单独提供 extraEnv 这类追加口。
  • 多个 -f 的顺序决定结果：后面的覆盖前面的，把通用文件写在后面会反向覆盖掉环境特有值。
  • --reuse-values 让删除值失效：你从 values 里删掉一项不会生效，因为它以上一次的 values 为基础叠加。
  • 不加 --wait 就当发布成功：对象提交完就返回 0，流水线绿灯而 Pod 正在 CrashLoopBackOff。
  • 卡在 pending-upgrade：CI 超时杀进程的典型后果，再次 upgrade 会被拒。先 helm history 再 rollback，必要时删掉最后那条 Release Secret。
  • helm rollback 不撤销数据变更：它只是重放旧渲染快照，pre-upgrade 里跑过的数据库迁移仍然生效，回滚后旧代码面对新表结构。
  • 三向合并会改回手工改动：只要字段在 chart 里声明过，kubectl edit 的结果会在下次 upgrade 时被覆盖。
  • 用 HPA 却渲染了 replicas：每次 upgrade 都把副本数打回初始值，发布期间容量塌一下。
  • hook Job 长期残留：hook-delete-policy 默认 before-hook-creation，上次的 Job 要等下次创建时才删。
  • 锁文件不入库：Chart.lock 不进 Git，等于放弃构建可复现性。
  • 在渲染模式下还指望 hooks：helm template 不执行任何 hook，迁移必须改成控制器的同步钩子或独立 Job。
  • 子 chart 的值写在顶层：覆盖子 chart 必须写在以子 chart 名或 alias 为键的子树下，写在顶层会被静默忽略。
