Helm 包管理

🏷️ Kubernetes,云原生

为什么需要 Helm：K8s 的包管理器

当你用 K8s 部署一个真实应用，往往要写 Deployment + Service + Ingress + ConfigMap + Secret + HPA 一堆 YAML，几十上百行。多环境部署时，这些 YAML 里的镜像 tag、副本数、资源配额各不相同——靠复制目录 + sed 替换？既容易出错又没法回滚。

Helm 就是 K8s 生态的 apt/yum/Homebrew：把一组相关 YAML 打包成 Chart，用 values.yaml 统一管理变量，支持模板渲染、版本化、一键升级回滚。Helm 3 砍掉了服务端 Tiller，纯客户端 CLI + CRD，安全模型干净得多。

Helm 核心概念

flowchart LR CHART[Chart 包
模板+默认values] --> TPL[模板渲染引擎
Go template/sprig] VAL[values.yaml
环境变量覆盖] --> TPL TPL --> YAML[渲染后的 K8s YAML] YAML -->|helm install/upgrade| API[K8s apiserver] API --> RELEASE[Release 实例
含版本历史]
概念类比 apt说明
Chartapt 包模板 + 默认 values 的目录打包
Release安装实例Chart 的一次部署，同 Chart 可装多次
values.yaml配置文件默认变量，部署时用 -f / --set 覆盖
helm repoapt 源Chart 仓库，add/update/search

实战：开发一个最简 Chart

用 Helm 命令生成骨架，再看关键文件：

# 创建 Chart 骨架
helm create myapp
tree myapp
# myapp/
# ├── Chart.yaml          # Chart 元信息
# ├── values.yaml         # 默认变量
# ├── templates/
# │   ├── deployment.yaml
# │   ├── service.yaml
# │   ├── ingress.yaml
# │   └── _helpers.tpl    # 模板函数
# └── charts/             # 子 Chart 依赖

templates/deployment.yaml 用 Go template 语法把变量注入 YAML：

apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ .Release.Name }}-web
  labels:
    app: {{ .Chart.Name }}
    release: {{ .Release.Name }}
spec:
  replicas: {{ .Values.replicaCount }}
  selector:
    matchLabels:
      app: {{ .Chart.Name }}
      release: {{ .Release.Name }}
  template:
    metadata:
      labels:
        app: {{ .Chart.Name }}
    spec:
      containers:
        - name: web
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
          resources:
{{ toYaml .Values.resources | indent 12 }}
          {{- with .Values.env }}
          env:
            {{- toYaml . | nindent 12 }}
          {{- end }}

对应的 values.yaml：

replicaCount: 2
image:
  repository: registry.example.com/myapp
  tag: "v1.2.0"
resources:
  requests:
    cpu: 100m
    memory: 128Mi
  limits:
    cpu: 500m
    memory: 256Mi
env:
  - name: LOG_LEVEL
    value: info

本地渲染验证（不真正部署）与安装：

# 渲染查看最终 YAML，dry-run 排错利器
helm template myapp ./myapp -f prod-values.yaml

# 安装到集群
helm install myapp-prod ./myapp -f prod-values.yaml -n prod --create-namespace

# 升级（修改 values 后）
helm upgrade myapp-prod ./myapp -f prod-values.yaml --set image.tag=v1.3.0

# 查看 Release 历史与回滚
helm history myapp-prod
helm rollback myapp-prod 1

# 从官方/第三方仓库安装现成 Chart
helm repo add bitnami https://charts.bitnami.com/bitnami
helm install redis bitnami/redis --set auth.password=xxx

最佳实践

  • Chart 与应用代码同仓库：Chart 跟着应用版本走，CI 里 helm package 后推到私有 Chart Museum/OCI Registry。
  • values 分层：Chart 自带默认 values.yaml，环境差异用独立的 values-prod.yaml 覆盖，不要改默认文件。
  • 用 helm-docs 自动生成 values 注释文档：values 多了以后，自动从注释生成 README，降低协作成本。
  • 生产用 --wait --timeout：helm upgrade --wait --timeout 5m，确保所有资源 Ready 才算发布成功，避免"命令成功但 Pod 还在 CrashLoop"。
  • 避免在模板里写复杂逻辑：模板应该是"渲染"，不是"编程"。复杂逻辑放应用侧或 Operator。
  • 敏感值用 --set 或外部 Secret：不要把密码写进 values.yaml 提交到 Git，用 sealed-secrets 或 external-secrets。

常见问题 FAQ

Q1：helm install 报 rendered manifests contain a resource that already exists

说明同名资源已存在但不归当前 Helm 管理。这是典型的"先用 kubectl apply 又用 helm"混用导致。用 helm adopt 或先手动删除旧资源再装；更干净的做法是全量改用 Helm 管理。

Q2：values.yaml 里改了镜像 tag，为什么升级不生效？

检查模板里镜像 tag 是否真的引用了 .Values.image.tag。常见错误：写死了 tag、或 --set 的 key 路径写错。先 helm template 渲染出来肉眼确认。

Q3：helm rollback 真的能完全回滚吗？

Helm 回滚的是上一版本的 manifests，并重新 apply。但它不会回滚 PV 里的数据、也不会回滚已经执行过的数据库迁移。有状态变更必须靠应用自身的回滚能力。

我的教训：helm rollback 救不了数据库迁移

有次发了个带 schema 变更的版本，执行了 ALTER TABLE，新版本上线后业务报错，helm rollback 回退了 Deployment YAML，但表结构已经改不回去了，只能人工回滚数据库。从那以后我所有 schema 变更都走"扩展-双写-切读-删旧列"四步，绝不做不可逆的 DDL。Helm 管的是 YAML，不是数据。

Q4：Helmfile 是什么？和 Helm 什么关系？

Helmfile 是 Helm 的声明式封装：用一个 helmfile.yaml 描述"在哪些环境装哪些 Chart、用哪些 values"，一条命令批量部署多个 Release，适合 GitOps 场景。如果你开始管理十几个 Release，是时候引入它了。

总结

Helm 把"一组 YAML + 变量 + 版本"打包成可复用的 Chart，用 values 做多环境差异化，用 Release 历史做升级回滚。它不是万能的——简单服务直接 Kustomize 可能更轻，但当应用超过 5 个资源对象、需要多环境复用时，Helm 的收益立刻显现。下一篇进入生产运维的收尾环节：监控与排障。
