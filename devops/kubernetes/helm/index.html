Helm 的模板机制与它的适用边界

🏷️ Helm

Helm 的所有行为，包括那些让人摸不着头脑的报错，都能用两件事解释清楚：它是一个文本模板渲染器，外加一套 Release 状态跟踪机制。把这两点想透，缩进为什么会错、rollback 到底回滚了什么、为什么有人改了线上 Helm 不知道，全都是推论。声明式交付与 Argo CD 的部分见 GitOps 系列，本篇聚焦 Helm 自身的机制与边界。

Helm 的两个核心

Helm 解决的问题是：把一组 K8s 对象打包成可参数化、可版本化、可一键安装卸载的单元。实现方式非常朴素——先把 values 逐层合并，再用 Go template 把 templates/ 下的文件渲染成字符串，最后把字符串交给 YAML 解析器，得到对象提交给 apiserver，同时把这份渲染结果原样存下来当作 Release 记录。

flowchart TB subgraph CHART["chart 目录：输入"] CY["Chart.yaml 元数据与 dependencies"] VY["values.yaml 默认值"] TPL["templates 目录下的模板文件"] HLP["_helpers.tpl 命名模板"] SUB["charts 目录：子 chart 与打包好的依赖"] end subgraph RENDER["渲染阶段：纯文本处理，不理解 YAML 结构"] MERGE["values 多层合并成一棵值树"] GO["Go template 引擎逐文件渲染成字符串"] PARSE["把渲染出的字符串当 YAML 解析"] end subgraph OUT["两个产物"] OBJ["提交到 apiserver 的对象"] REL["Release 记录：整份渲染结果存成 Secret"] end CY --> MERGE VY --> MERGE SUB --> MERGE MERGE --> GO TPL --> GO HLP --> GO GO --> PARSE PARSE --> OBJ PARSE --> REL

注意 PARSE 那一步在 GO 之后：渲染期间 Helm 完全不知道自己在生成 YAML。缩进、引号、类型全部由你在模板里负责。这一个事实就能解释大半的 Helm 报错。

模板的实质是字符串替换

需求正确写法写错会发生什么
把一个结构化对象插到指定缩进层级{{- toYaml .Values.resources | nindent 12 }}只写 toYaml 不加缩进，渲染出的块从第一列开始，解析报 mapping values are not allowed in this context
选 indent 还是 nindent前面已有换行用 indent，否则用 nindent（它先补一个换行）用错会让键粘在上一行末尾，或多出一个空行让块脱离父级
值可能是纯数字或布尔样式{{ .Values.image.tag | quote }}1.28 被解析成浮点、true 和 on 被解析成布尔、0755 前导零丢失，报 cannot unmarshal number into Go struct field
缺省值{{ .Values.port | default 8080 }}值为空时渲染出空串，字段变成 null，apiserver 报字段类型错误
必填项{{ required "image.tag 必须显式指定" .Values.image.tag }}渲染出空值，一路提交到集群才报错，排查要绕一大圈
去掉控制语句留下的空行统一写 {{- if ... }} 与 {{- end }}产生大量空行，极端情况下出现只有空白的文档，被解析成 null 对象

values 的覆盖是分层的，理解顺序才能解释「我明明设了为什么没生效」：

优先级来源说明
最低子 chart 自己的 values.yaml依赖组件的默认值
↓父 chart 的 values.yaml覆盖子 chart 要写在以子 chart 名（或 alias）为键的子树下
↓-f 指定的文件多个 -f 按命令行顺序生效，后面的覆盖前面的
最高--set、--set-string、--set-file会覆盖一切；--set-string 强制当字符串，避免 tag 被当数字
特殊--reuse-values以上一次 Release 的 values 为基础再叠加本次；它会让「删掉一个 values 项」失效，因为旧值还在
⚠️
列表不是合并而是整体替换

values 合并对 map 是逐键深合并，但对列表是整体替换。所以你想「在默认的 env 列表里再加一项」时，实际结果是把默认那几项全部干掉只剩你加的那一项。想追加就必须由 chart 提供一个专门的 extraEnv 之类的字段，而不是覆盖原字段。

Release 与状态：rollback 到底回滚了什么

Helm 3 把每次操作的渲染结果存成一个 Secret，名字形如 sh.helm.release.v1.api.v7，带 owner=helm 标签，默认放在 Release 所在的命名空间。helm rollback 的实现就是取出旧 revision 的那份渲染快照重新应用一遍——它不做任何逆向推导，也不知道你的应用语义。

stateDiagram-v2 [*] --> pending_install state "pending-install" as pending_install state "deployed" as deployed state "failed" as failed state "pending-upgrade" as pending_upgrade state "superseded" as superseded state "uninstalling" as uninstalling pending_install --> deployed: 全部对象创建成功 pending_install --> failed: 任一对象创建失败或超时 deployed --> pending_upgrade: helm upgrade 开始写入新 revision pending_upgrade --> deployed: 新 revision 成功，上一个转为 superseded deployed --> superseded: 被更新的 revision 取代 pending_upgrade --> failed: 超时、校验失败或 hook 失败 failed --> pending_upgrade: 再次执行 upgrade deployed --> uninstalling: helm uninstall uninstalling --> [*] note right of pending_upgrade CI 的超时把 helm 进程杀掉，Release 就永久停在这里 再次 upgrade 会报另一个操作正在进行中 先 helm history 看清 revision，再 rollback 到上一个 deployed 的版本 rollback 也被拒绝时，删掉最后那条处于 pending 状态的 Release Secret end note
状态含义典型原因处理动作
deployed当前生效的 revision正常无
superseded已被新 revision 取代的历史版本正常作为 rollback 目标存在
pending-install首次安装未收尾进程被杀、镜像拉不下来导致等待超时helm uninstall 后重装；首次安装没有可回滚的目标
pending-upgrade升级未收尾最常见：CI 任务超时杀掉了 helm 进程helm rollback 到上一个 deployed 的 revision；不行则删掉该条 Release Secret
failed操作明确失败对象被 apiserver 拒绝、hook 返回非 0、等待就绪超时看清失败对象再修 chart；加 --atomic 可让失败自动回滚
uninstalling卸载中有对象带 finalizer 卡住先处理卡住的 finalizer，见 主干篇

由「Release 是一份快照」还能推出另一个结论：如果有人用 kubectl edit 改了线上，Helm 的记录里完全没有这件事。helm get manifest 给你的是上次渲染结果，不是集群现状。想知道差异只能自己比。

三向合并补丁

sequenceDiagram autonumber participant Helm as helm upgrade participant Store as Release 记录 Secret participant API as apiserver Helm->>Store: 取出上一个 revision 的渲染结果，记作 old Helm->>Helm: 用本次 values 渲染出 new Helm->>API: 读取集群中对象的当前状态，记作 live Helm->>Helm: 比较 old、live、new 三者生成补丁 Note over Helm: old 有而 new 没有的字段，生成删除指令 Note over Helm: new 与 old 不同的字段，以 new 为准 Note over Helm: chart 里声明过的字段，即使 live 被手工改过也会被改回 new Note over Helm: chart 从未声明的字段，保留 live 上的值不动 Helm->>API: 提交补丁 Note over Helm,API: 因此用 HPA 管副本数时，chart 里千万不要渲染 replicas

Helm 2 用的是两向合并，只比 old 与 new，所以手工改过的字段能一直存活。Helm 3 引入三向合并后，线上手工改动会在下一次 upgrade 时被拉回 chart 声明的值——这通常是好事，但在两个场景下会咬人：一是 chart 写了 replicas 而副本数由 HPA 管，每次发布都会先把副本打回初始值，容量塌一下再由 HPA 扩回来；二是某些控制器会往对象上写字段（例如注入 sidecar 或补默认注解），如果 chart 恰好也声明了同名字段，就会出现两边来回改写的抖动。

hooks：能跑迁移，但不受回滚保护

hook时机典型用途要注意什么
pre-install渲染完成、对象创建之前初始化数据库 schema失败会让整次安装失败并可能停在 pending-install
pre-upgrade新对象提交之前数据库迁移迁移必须幂等且向后兼容旧版本代码，因为此刻旧 Pod 还在跑
post-upgrade对象提交之后缓存预热、通知此时新 Pod 可能还没全部就绪
pre-rollback 与 post-rollback回滚前后反向迁移需要你自己写反向逻辑，Helm 不会替你撤销任何数据变更
testhelm test 时冒烟检查不在 install 与 upgrade 流程里自动执行

最需要记住的一条：hook 产生的资源不属于 Release 的托管范围，也不参与三向合并。这意味着 helm rollback 会把 Deployment 换回旧镜像，但 pre-upgrade 里已经执行完的数据库迁移不会被撤销。于是回滚之后旧版本代码面对的是新版本的表结构——如果迁移不是向后兼容的，这一步就直接出故障。这是 Helm 使用中最容易造成真实事故的一处。另外 helm.sh/hook-delete-policy 默认是 before-hook-creation，意思是下次创建时才删上次的，所以集群里会长期留着最后一次的 hook Job；要立刻清理就加 hook-succeeded。

只渲染不安装：helm template 的用法与取舍

维度helm install 与 upgradehelm template 加 kubectl apply
Release 跟踪有，helm list、helm history 可用完全没有，helm 侧看不到任何记录
回滚方式helm rollback 重放旧快照回退 Git 提交，由控制器重新同步
删除已移除的对象Helm 依据 old 与 new 的差集自动删需要 kubectl apply --prune 或由控制器按标签跟踪
hooks按时机执行不执行，迁移要改成控制器的同步钩子或独立 Job
三向合并Helm 自己算补丁交给 apiserver 的服务端应用与字段所有权机制
适合手工安装第三方组件、本地实验声明式交付，见 GitOps 系列

在声明式交付下，主流做法是只把 Helm 当渲染器，应用与纠偏交给控制器。这个取舍要想清楚：你放弃了 Release 跟踪，换来单一事实来源和自动纠偏。放弃之后 helm list 不再反映真实情况，任何依赖 Release 记录的运维习惯都要改掉。

Helm 与 Kustomize

依赖管理与写 chart 的判断

# Chart.yaml：依赖声明与版本约束
apiVersion: v2
name: api
version: 1.4.2          # chart 自身版本，改模板就要改它
appVersion: "9f3c2a1"   # 应用版本，写成字符串避免被当数字
dependencies:
  - name: redis
    version: 19.6.4     # 固定到补丁版本；写 ^19.0.0 会让不同时间构建出不同结果
    repository: https://charts.bitnami.com/bitnami
    condition: redis.enabled        # 由 values 控制是否安装，比注释掉整段干净
  - name: postgresql
    version: 15.5.20
    repository: https://charts.bitnami.com/bitnami
    condition: postgresql.enabled
    alias: maindb                   # 有 alias 时，覆盖路径变成 maindb 而不是 postgresql
---
# values.yaml：覆盖子 chart 的值必须写在以子 chart 名或 alias 为键的子树下
redis:
  enabled: true
  architecture: standalone          # 这些键会传给 redis 子 chart
  auth:
    existingSecret: redis-auth      # 密钥来源见配置与密钥篇，不要写明文
maindb:
  enabled: false
# 自有应用的值放在顶层
image:
  repository: registry.example.com/api
  tag: ""                           # 留空则回退到 Chart.appVersion
resources:
  requests: {cpu: 300m, memory: 512Mi}
  limits: {memory: 1Gi}
autoscaling:
  enabled: true                     # 开了它，模板里就不要渲染 replicas
extraEnv: []                        # 提供追加口，因为列表覆盖是整体替换而不是合并

helm dependency update 会按上面的声明拉取依赖到 charts/ 并生成 Chart.lock。锁文件必须入库——它记录了依赖的精确版本和摘要，不入库就等于放弃了构建可复现性，几个月后同一个 commit 渲染出来的东西可能已经变了。

关于「该参数化什么」，唯一有用的判断标准是：这个字段会不会在不同安装之间取不同的值。会，才做成 values；不会，直接写死在模板里。把每个字段都做成 values 的结果是模板比原始 YAML 更难读，而且 values 的组合空间大到无法测试。一个实用的分界：镜像、副本与伸缩、资源规格、对外暴露方式、依赖开关、存储大小与 StorageClass 这几类必须参数化；探针路径、标签规范、安全上下文这些全公司统一的东西写死更好。

# 渲染出来自己看，这是排查模板问题的第一步，不要盯着模板猜
helm template api ./charts/api -f values-prod.yaml | less

# 只看某个文件的渲染结果，加 --debug 能看到合并后的完整 values
helm template api ./charts/api -s templates/deployment.yaml --debug

# 升级前看清将要改什么（需要 helm-diff 插件，强烈建议装）
helm diff upgrade api ./charts/api -f values-prod.yaml

# 不用插件时的等价做法：拿渲染结果去跟集群做服务端 diff
helm template api ./charts/api -f values-prod.yaml | kubectl diff -f -

# 生产升级的推荐参数：失败自动回滚，超时给足，等对象真正就绪
helm upgrade --install api ./charts/api -f values-prod.yaml \
  --namespace prod --atomic --timeout 10m --wait

# Release 记录就是一批带 owner=helm 标签的 Secret
kubectl -n prod get secret -l owner=helm,name=api --sort-by=.metadata.creationTimestamp

# 卡在 pending-upgrade 的处理顺序
helm -n prod history api                      # 找到最后一个 deployed 的 revision
helm -n prod rollback api 6                   # 回到该 revision，状态会推回正常
# 若 rollback 也被拒绝，删掉最后那条 pending 的 Release Secret 再重试
kubectl -n prod delete secret sh.helm.release.v1.api.v8

# 对比「Helm 认为的清单」与「集群实际状态」，找出被手工改过的地方
helm -n prod get manifest api | kubectl diff -f -

反模式

反模式症状后果正确做法
把每个字段都做成 valuesvalues.yaml 几百行，模板里满是 with 与 if比直接写 YAML 更难读，组合空间大到无法测试只参数化「不同安装之间会取不同值」的字段
模板里写复杂逻辑嵌套的 range 套 if，还有字符串拼接出的 key渲染结果无法预测，改一行要靠反复 helm template 试逻辑上移到 values 结构或 CI 生成，模板只做填空
用一堆 --set 发布发布命令是一行几百字符的 --set a=1 --set b=2不可复现、无法评审、出事后不知道当时传了什么values 文件入库，用 -f 引用；命令行只留 namespace 这类环境参数
hooks 里跑不幂等的迁移重试一次 upgrade 就报唯一键冲突回滚后旧代码面对新表结构，直接故障迁移必须幂等且向后兼容；破坏性变更拆成多次发布
生产用 helm install 但不记录 values只有操作者本机有那份 values 文件换人接手无法复现，--reuse-values 越用越糊values 一律入库，或直接改用声明式交付
依赖不锁版本Chart.lock 不入库，依赖写 ^19.0.0同一个 commit 在不同时间渲染出不同结果依赖固定到补丁版本，锁文件入库
用 HPA 却在 chart 里渲染 replicas每次发布副本数先掉回初始值发布窗口容量塌陷，HPA 再慢慢扩回来开了 autoscaling 就用条件语句把 replicas 整行去掉
✅
最容易踩的坑
  • 模板不理解 YAML 结构：渲染是纯文本替换，缩进完全由你负责，插块一律 toYaml 加 nindent。
  • image tag 忘了 quote：1.28 被当浮点、true 和 on 被当布尔、0755 前导零丢失，报 cannot unmarshal number 就是这个原因。
  • values 里列表是整体替换不是合并：想追加一项却把默认几项全干掉了，chart 要单独提供 extraEnv 这类追加口。
  • 多个 -f 的顺序决定结果：后面的覆盖前面的，把通用文件写在后面会反向覆盖掉环境特有值。
  • --reuse-values 让删除值失效：你从 values 里删掉一项不会生效，因为它以上一次的 values 为基础叠加。
  • 卡在 pending-upgrade：CI 超时杀进程的典型后果，再次 upgrade 会被拒。先 helm history 再 rollback，必要时删掉最后那条 Release Secret。
  • helm rollback 不撤销数据变更：它只是重放旧渲染快照，pre-upgrade 里跑过的数据库迁移仍然生效，回滚后旧代码面对新表结构。
  • 三向合并会改回手工改动：只要字段在 chart 里声明过，kubectl edit 的结果会在下次 upgrade 时被覆盖。
  • 用 HPA 却渲染了 replicas：每次 upgrade 都把副本数打回初始值，发布期间容量塌一下。
  • hook Job 长期残留：hook-delete-policy 默认 before-hook-creation，上次的 Job 要等下次创建时才删。
  • 锁文件不入库：Chart.lock 不进 Git，等于放弃构建可复现性。
  • 在渲染模式下还指望 hooks：helm template 不执行任何 hook，迁移必须改成控制器的同步钩子或独立 Job。
  • 子 chart 的值写在顶层：覆盖子 chart 必须写在以子 chart 名或 alias 为键的子树下，写在顶层会被静默忽略。
