配置与密钥在集群里的落地

🏷️ Kubernetes,云原生

配置这件事在 K8s 里之所以反复出问题，不是因为 ConfigMap 难懂，而是因为四种注入方式的热更新行为完全不同，而清单上看起来差别很小。本篇的核心就是那张对照表。应用侧的配置热更新范式、配置中心服务端机制分别见 微服务配置中心篇 与 配置中心系列，本篇只讲集群内的落地方式与密钥安全。

💡
这篇怎么读
  • ① 用法：挂载与环境变量注入两种方式的最小可用清单、日常操作命令，以及一张「配置变了到底要不要重启」的对照表。
  • ② 原理：四种注入方式的行为差异、卷挂载的符号链接原子切换与 subPath 为何永不更新、让变更生效的几条路、Secret 的真实保护边界与密钥来源方案、ServiceAccount 与云 IAM 联邦、大小限制与不可变配置。
  • ③ 场景：什么该进镜像、什么进 ConfigMap、什么必须走外部密钥服务，以及多环境差异与七种反模式。

① 用法 · 挂载与注入的两个最小示例，以及改了配置要不要重启

集群里落地配置只有两种基本姿势：挂成文件（能自动同步，但应用必须自己重读）和注入成环境变量（最省事，但改了必须重启）。下面两份清单都可以直接 apply，注释只说明为什么要这行。

# ========== 方式一：卷挂载。改了 ConfigMap 会自动同步进文件（分钟级延迟）==========
apiVersion: v1
kind: ConfigMap
metadata: {name: api-config}
data:
  app.yaml: |               # 一个 key 就是挂载后的一个文件名
    server:
      port: 8080
    log:
      level: info
---
apiVersion: v1
kind: Secret
metadata: {name: api-secret}
type: Opaque
stringData:                 # 用 stringData 写明文，apiserver 自己做 base64；不要手工编码再填 data
  password: change-me-in-your-secret-store
---
apiVersion: apps/v1
kind: Deployment
metadata: {name: api}
spec:
  replicas: 2
  selector:
    matchLabels: {app: api}
  template:
    metadata:
      labels: {app: api}
      annotations:
        checksum/config: "3f9a1c04"   # 配置内容哈希：它一变，模板即变，滚动更新自动发生
        checksum/secret: "b71e5d92"   # 密钥要单独算一份，否则轮转不触发重启
    spec:
      containers:
        - name: api
          image: registry.example.com/api:9f3c2a1
          volumeMounts:
            - {name: config, mountPath: /etc/app, readOnly: true}
            - {name: secret, mountPath: /etc/app/secret, readOnly: true}
      volumes:
        - name: config
          configMap:
            name: api-config
            defaultMode: 0444         # 卷挂载能控制文件权限，环境变量没有这个概念
        - name: secret
          secret:
            secretName: api-secret    # Secret 卷挂在内存文件系统上，不落节点磁盘
---
# ========== 方式二：环境变量注入。最省事，但改了配置必须重启才生效 ==========
apiVersion: apps/v1
kind: Deployment
metadata: {name: worker}
spec:
  replicas: 2
  selector:
    matchLabels: {app: worker}
  template:
    metadata:
      labels: {app: worker}
    spec:
      containers:
        - name: worker
          image: registry.example.com/worker:9f3c2a1
          env:
            - name: LOG_LEVEL       # 单个 key 注入，可以改名
              valueFrom:
                configMapKeyRef: {name: api-config, key: log.level}
            - name: DB_PASSWORD
              valueFrom:
                secretKeyRef: {name: api-secret, key: password}
          envFrom:
            - configMapRef: {name: api-config}   # 整体导入，key 名原样照搬
            - secretRef: {name: api-secret}      # 名字不是合法环境变量名的 key 会被静默跳过

日常操作就这几条命令：

# 创建：从文件或字面量生成，比手写 base64 可靠
kubectl create configmap api-config --from-file=app.yaml
kubectl create secret generic api-secret --from-literal=password='change-me'

# 想要清单文件又不想自己算 base64：先 dry-run 出来
kubectl create configmap api-config --from-file=app.yaml --dry-run=client -o yaml > cm.yaml

# 更新已存在的对象（apply 要求完整清单，用 dry-run 管道最省事）
kubectl create configmap api-config --from-file=app.yaml --dry-run=client -o yaml | kubectl apply -f -

# 看集群里真正生效的值：Secret 的 base64 一条命令就能还原，它不是加密
kubectl get cm api-config -o jsonpath='{.data.app\.yaml}'
kubectl get secret api-secret -o jsonpath='{.data.password}' | base64 -d; echo

# 让 env 或 subPath 注入的配置生效：只有重启一条路
kubectl rollout restart deploy/api

接下来这张表是本篇最实用的一张：改完配置之后，到底要不要动 Pod。

你改了什么这个值是怎么注入的要不要重启怎么让它生效
改一个开关（日志级别、限流阈值）整卷挂载，且应用监听配置目录不用等 kubelet 同步，分钟级；先确认应用监听的是目录而不是单个文件
改一个开关，但应用启动时只读一次整卷挂载要更新模板注解里的配置哈希，或 kubectl rollout restart
改被 env 或 envFrom 引用的 key环境变量必须同上。不重启的话进程里永远是旧值，没有任何机制能改
改用 subPath 挂进去的那个文件subPath 单文件挂载必须同上。这是最反直觉的一条，原因见原理层
轮转数据库口令任意方式看应用能不能重建连接池要单独算一份 checksum/secret，只算 config 的哈希不会触发重启
给 ConfigMap 加了一个新 key没有任何地方引用它不用加 key 本身没有任何效果，要在清单里引用才算数
改一个 immutable: true 的对象任意方式必须apiserver 会直接拒绝编辑，只能换一个新名字，配合内容哈希命名
引用了一个还不存在的 ConfigMap任意方式—Pod 会卡在 ContainerCreating，先看事件；确实可选的话显式写 optional: true

清单里几个字段值得单独记一下：

字段作用默认值什么时候需要写
stringData直接写明文，由 apiserver 转成 base64 存进 data无手写 Secret 清单时一律用它，避免自己编码出错
items只挑选部分 key 挂载，并可改文件名不写则全部 key 铺开一个对象里混着多个用途的 key 时
defaultMode挂载后的文件权限0644（受 fsGroup 与 umask 影响）应用要求配置文件不可组读，或以非 root 运行时
optional引用的对象不存在时是否允许 Pod 启动false确实可选的配置才写 true，否则会把打错名字的错误藏起来
immutable禁止修改，并让 kubelet 不再 watch 该对象false配合内容哈希命名时建议全开，原因见原理层
automountServiceAccountToken是否把 SA token 投进容器true不访问 apiserver 的应用显式关掉，减少一处可被利用的凭证

上面的默认值以你集群版本的 kubectl explain pod.spec.volumes.configMap 输出为准。为什么卷挂载会更新而 subPath 不会、Secret 到底保护了什么，都在下面几节。

② 原理 · 四种注入方式的行为差异

注入方式写法能否热更新应用要做什么粒度权限与风险
环境变量（单个 key）env[].valueFrom.configMapKeyRef 或 secretKeyRef永不更新。环境变量在进程创建时写入进程内存，没有任何机制能改什么都不用做，启动时读一次单个 key，可改名值会出现在 kubectl describe pod 与很多 APM 的进程信息里
envFrom 整体导入envFrom[].configMapRef 或 secretRef永不更新什么都不用做整个对象的所有 key，名字原样照搬key 名不符合环境变量命名规则时会被静默跳过，只在 Pod 事件里留一行；且无法只导入一部分
卷挂载（整个对象）volumes[].configMap 加 volumeMounts会更新，分钟级延迟。kubelet 按同步周期刷新，默认 1 分钟，叠加缓存 TTL 后最坏两倍多必须自己监听文件或定时重读，否则文件变了行为不变每个 key 一个文件，可用 items 挑选与改名可用 defaultMode 控制权限；Secret 卷挂在内存文件系统上，不落盘
subPath 挂载（单个 key）volumeMounts[].subPath永不更新。这是最反直觉的一项无从下手，只能重启单个文件，可挂到任意已有目录里而不覆盖该目录唯一能「往已有目录里塞一个文件」的方式，代价就是丧失更新能力

# 同一个 Pod 里把四种方式写全，用来对照它们的行为差异
apiVersion: v1
kind: Pod
metadata:
  name: inject-demo
spec:
  containers:
    - name: app
      image: registry.example.com/api:9f3c2a1
      env:
        # 方式一：单个 key 到环境变量。永不更新，改了必须重启
        - name: LOG_LEVEL
          valueFrom:
            configMapKeyRef: {name: api-config, key: log.level}
        - name: DB_PASSWORD
          valueFrom:
            secretKeyRef: {name: api-secret, key: password}
      envFrom:
        # 方式二：整体导入。key 名不是合法环境变量名的会被静默跳过
        - configMapRef: {name: api-config}
        - secretRef: {name: api-secret}
      volumeMounts:
        # 方式三：整卷挂载。会更新，分钟级延迟，应用需监听目录
        - name: config
          mountPath: /etc/app
          readOnly: true
        # 方式四：subPath 挂到已有目录里的单个文件。永不更新
        - name: config
          mountPath: /etc/nginx/conf.d/upstream.conf
          subPath: upstream.conf
  volumes:
    - name: config
      configMap:
        name: api-config
        defaultMode: 0444        # 卷挂载可以控制文件权限，环境变量没有这个概念
        items:                   # 只挑需要的 key 并改名，避免把整个对象铺开
          - {key: app.yaml, path: app.yaml}
          - {key: upstream.conf, path: upstream.conf}

② 原理 · 为什么卷挂载会更新而 subPath 不会

把卷挂载的目录 ls -la 一下就明白了：容器里看到的 app.yaml 是一条符号链接，指向 ..data/app.yaml，而 ..data 本身又是一条指向带时间戳目录的符号链接。kubelet 更新配置时，先写一个全新的时间戳目录，然后原子地把 ..data 这条符号链接指过去——这样应用永远不会读到写了一半的配置。

flowchart TB subgraph KUBELET["kubelet 侧"] W["watch 到 ConfigMap 版本变化"] SYNC["按同步周期落盘，默认 1 分钟，叠加缓存后最坏两倍多"] end subgraph VOLDIR["容器内配置目录的真实结构"] TS1["带时间戳的旧目录，例如 ..2026_09_23_10_00_00"] TS2["带时间戳的新目录，例如 ..2026_09_23_10_01_00"] DATA["..data 符号链接，原子切换指向新目录"] KEY["app.yaml 是指向 ..data/app.yaml 的符号链接"] end subgraph SUB["subPath 挂载走的是另一条路"] SPB["容器内路径在创建时直接绑定到当时那个文件"] SPN["kubelet 换的是目录符号链接，绑定关系不受影响，因此永远看不到新内容"] end W --> SYNC SYNC --> TS2 TS1 --> DATA TS2 --> DATA DATA --> KEY SYNC --> SPN SPN --> SPB
⚠️
监听文件变化要监听目录，不是文件

因为更新是通过替换符号链接完成的，对单个文件下 inotify 只会收到一次 IN_IGNORED 之后再也收不到任何事件。正确做法是监听整个挂载目录的 IN_CREATE 与 IN_MOVED_TO，或者干脆定时重读文件比较内容哈希。很多配置库在裸机上工作良好、进了 K8s 就不热更新了，原因就在这里。

② 原理 · 让配置变更真正生效的两条路

做法触发机制优点代价
Pod 模板加配置内容哈希注解注解变化即 spec.template 变化，Deployment 生成新 ReplicaSet 并滚动更新确定性最强，变更可审计、可回滚，与声明式交付天然一致每次配置变更都要重启一轮，发布窗口内容量有抖动
Kustomize 的 configMapGenerator生成带内容哈希后缀的 ConfigMap 名字，引用处自动替换，模板随之变化完全自动，旧 ConfigMap 还在，回滚只是切回旧名字旧 ConfigMap 会堆积，需要定期清理；名字带随机后缀，手工排查时要多看一眼
应用监听文件变化inotify 或定时重读，进程内热加载不重启，适合日志级别、限流阈值这类高频开关只对整卷挂载有效；应用必须保证重载是原子的；连接池、线程池这类资源往往重载不干净
Reloader 一类控制器控制器 watch ConfigMap，变化时自动给 Deployment 打注解不用改流水线，存量服务接入成本最低多一个控制器；在声明式交付下它写入的注解会与仓库里的期望状态产生持续漂移
 
# 做法一：手工在 Pod 模板注解里放配置内容哈希
# 生成方式：kubectl create cm api-config --dry-run=client -o yaml | sha256sum | cut -c1-8
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
spec:
  template:
    metadata:
      annotations:
        checksum/config: "3f9a1c04"   # 这个值一变，模板即变，滚动更新自动发生
        checksum/secret: "b71e5d92"   # 密钥也要单独一个，否则轮转不会触发重启
    spec:
      containers:
        - name: api
          image: registry.example.com/api:9f3c2a1
          volumeMounts:
            - {name: config, mountPath: /etc/app, readOnly: true}
      volumes:
        - name: config
          configMap: {name: api-config}
---
# 做法二：交给 Kustomize 生成带哈希后缀的名字（推荐，不用自己算）
# kustomization.yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
configMapGenerator:
  - name: api-config
    files:
      - app.yaml                    # 生成 api-config-7d4f2b9c8k 这样的名字
    options:
      disableNameSuffixHash: false  # 千万不要设 true，设了就退化成「改内容不改名」
secretGenerator:
  - name: api-secret
    envs:
      - secret.env                  # 本地文件，不入库；入库的版本用外部密钥方案
generatorOptions:
  immutable: true                   # 与内容哈希命名天然搭配，见下文不可变配置

② 原理 · Secret 的真相

❌
base64 不是加密，默认情况下 etcd 里是明文

data 字段的 base64 只是为了能承载二进制内容，一条 base64 -d 就能还原。如果没有开启静态加密，Secret 的值在 etcd 的数据文件和每一份备份里都是可以直接 grep 出来的明文。所以 Secret 这个类型给你的不是保密性，而是三件事：不进镜像、可以按对象名做 RBAC 授权、卷挂载时放在内存文件系统上不落盘。

防护层具体手段挡住什么挡不住什么怎么验证
etcd 静态加密apiserver 的 --encryption-provider-config，用 aescbc 或对接云 KMSetcd 数据文件与备份被拖走、磁盘被取走任何有 API 读权限的主体，因为 apiserver 会解密后返回直接用 etcdctl 读该 key，看不到明文才算生效
RBAC 最小授权不给 get、list、watch secrets 的通配权限，只按 resourceNames 授到具体对象同命名空间的其他人、被攻破的应用横向读取能在该命名空间创建 Pod 的人——他挂载一下就能打印出来kubectl auth can-i get secrets -n prod --as=...
审计审计策略对 secrets 资源至少记 Metadata 级别事后追溯：谁在什么时候读过哪个 Secret不阻断任何行为，只是留痕在审计日志里能查到对应的 get 记录

第二行右边那一格是最值得记住的纠正：create pod 权限本身就等价于该命名空间的 Secret 读权限。同理，能改 Deployment、能创建 Job、能 exec 的人也都有等效能力。所以「把 get secret 权限收了」并不构成隔离，真正的隔离是按命名空间切分，并且让凭证短期化。

② 原理 · 密钥的正确来源：不要手写进仓库

方案密钥以什么形式进 Git解密发生在哪轮转灾难场景适用
Sealed Secrets用集群内控制器的公钥加密后的密文集群内控制器解密并生成真正的 Secret要重新加密并提交控制器私钥丢失则所有历史密文全部作废，必须单独备份私钥单集群、想要最简单的入门方案
SOPS用外部 KMS 加密过字段的 YAML，结构可读可 diff流水线或控制器在应用前解密改文件重新加密依赖 KMS 可用性；解密环节多一处凭证要管希望在 Git 里看清配置结构、且已有 KMS
External Secrets Operator只进引用路径，密钥本体完全不进 Git控制器用自己的身份从外部密钥管理系统拉取并写成 Secret按 refreshInterval 自动同步，外部轮转即生效依赖外部系统与网络可达性；控制器自身权限是新的高价值目标推荐，尤其是多集群多环境
手写 Secret 进仓库base64 明文不需要解密，任何有仓库读权限的人都能看无一旦提交，即使删除也永远留在 Git 历史里没有适用场景
sequenceDiagram autonumber participant Git as Git 仓库 participant API as apiserver participant ESO as External Secrets Operator participant KMS as 外部密钥管理系统 participant Pod as 业务 Pod Git->>API: 提交 ExternalSecret，内容只有密钥的引用路径 API->>ESO: 通知有新的 ExternalSecret 对象 ESO->>KMS: 用控制器自己的身份按路径读取 KMS-->>ESO: 返回密钥值 ESO->>API: 创建或更新同名 Secret API->>Pod: 按原有方式注入，业务侧完全无感 Note over Git: 仓库里从头到尾没有任何密钥明文 Note over ESO,KMS: refreshInterval 到点重新拉取，外部轮转后集群自动跟上 
# ExternalSecret：Git 里只有引用，没有值
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: api-secret
  namespace: prod
spec:
  refreshInterval: 1h            # 外部轮转后最多 1 小时集群内跟上
  secretStoreRef:
    name: vault-prod             # 指向一个 SecretStore，它持有访问外部系统的身份
    kind: SecretStore
  target:
    name: api-secret             # 生成的 Secret 名字，业务 Pod 照旧引用它
    creationPolicy: Owner        # 由 ExternalSecret 拥有，删除它时一并清理
    template:
      metadata:
        annotations:
          reloader.stakater.com/match: "true"
  data:
    - secretKey: password        # 生成的 Secret 里的 key
      remoteRef:
        key: prod/api/db         # 外部系统里的路径
        property: password

② 原理 · ServiceAccount 与云 IAM 的联邦

上面所有方案解决的都是「密钥怎么安全地送到集群」。但对云平台凭证来说，更好的答案是根本不要有长期密钥。IRSA 与 Workload Identity 的做法是：kubelet 往容器里投一个有效期一小时的 ServiceAccount token，云端的 STS 用集群的 OIDC 公钥校验它，然后换给 Pod 一份短期凭证。

sequenceDiagram autonumber participant KUBE as kubelet participant Pod as 业务容器 participant STS as 云平台 STS participant OIDC as 集群 OIDC 提供方 participant S3 as 对象存储 KUBE->>Pod: 按 projected volume 投递有效期 1 小时的 token 到容器内文件 Pod->>STS: 携带该 token 与 ServiceAccount 上标注的角色请求换取凭证 STS->>OIDC: 用 issuer 与公钥校验 token 签名和受众 OIDC-->>STS: 校验通过，确认是哪个命名空间的哪个 ServiceAccount STS-->>Pod: 返回十几分钟到一小时有效的临时凭证 Pod->>S3: 用临时凭证访问，SDK 到期自动续 Note over KUBE,S3: 集群里不存在任何长期访问密钥，泄露窗口被压到小时级 Note over STS,OIDC: 授权模型从「谁拿到了密钥」变成「哪个 ServiceAccount 能扮演哪个角色」 
# 把云角色绑在 ServiceAccount 上，Pod 只要用这个 SA 就自动拿到临时凭证
apiVersion: v1
kind: ServiceAccount
metadata:
  name: api
  namespace: prod
  annotations:
    # AWS 写法；GCP 用 iam.gke.io/gcp-service-account，Azure 用 azure.workload.identity/client-id
    eks.amazonaws.com/role-arn: arn:aws:iam::123456789012:role/prod-api
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
  namespace: prod
spec:
  template:
    spec:
      serviceAccountName: api             # 关键一行，不写就用 default SA，拿不到角色
      automountServiceAccountToken: true  # 默认 true；对不需要访问 API 的应用应显式关掉
      containers:
        - name: api
          image: registry.example.com/api:9f3c2a1
          # 注意这里没有任何 AWS_ACCESS_KEY_ID，SDK 会自动读取投影 token 去换凭证

② 原理 · 大小限制与不可变配置

ConfigMap 与 Secret 的单对象上限约 1 MiB，这个限制来自 etcd 的单值大小限制（默认 1.5 MiB）。更实际的约束是：每个引用它的 Pod 所在节点的 kubelet 都会缓存它，几百 KB 的对象乘上几百个节点就是可观的内存与 watch 流量。

配置体量放哪理由与代价
几 KB 到 100 KBConfigMap，按变更频率拆成多个高频变更的开关单独一个对象，改它不会牵动整份配置的滚动
100 KB 到 1 MiB勉强能放，但要设 immutable: true接近上限时任何一次编辑都可能被 apiserver 拒绝；kubelet 缓存压力明显
超过 1 MiB 的静态资源打进镜像，或用 initContainer 从对象存储拉取到 emptyDir镜像方式最简单但改配置要重新构建；initContainer 方式增加启动期外部依赖
体量大且需要多 Pod 共享读对象存储或只读 PVC，见 存储篇多了存储插件依赖，但避免了 etcd 承载大对象
规则类、需要频繁下发配置中心客户端长轮询拉取机制与取舍见 配置中心系列
维度普通 ConfigMapimmutable: true
修改方式直接改 data不能改，只能删除重建，或者换一个新名字
kubelet 行为持续 watch 该对象以便同步到卷不再 watch，显著降低 apiserver 的 watch 连接数与 kubelet 内存
热更新卷挂载有分钟级延迟不存在热更新这件事，变更必然伴随新名字与滚动更新
误改风险有人 kubectl edit 就改了，且不留痕apiserver 直接拒绝，杜绝线下改配置
适合需要热更新的少量开关与内容哈希命名配合使用的绝大多数配置

② 原理 · 把上面的结论逐条验证一遍

# Secret 根本不是加密的：一条命令还原明文
kubectl -n prod get secret api-secret -o jsonpath='{.data.password}' | base64 -d; echo

# 确认 etcd 里到底是不是明文（需要控制面机器权限）
kubectl -n prod create secret generic probe --from-literal=k=canary-value-9f3c
sudo ETCDCTL_API=3 etcdctl get /registry/secrets/prod/probe | strings | grep canary-value-9f3c
# 能 grep 出来就说明静态加密没开；开了之后应当看到 k8s:enc: 前缀的密文

# 谁能读这个命名空间的 Secret，先摸清现状再收口
kubectl auth can-i get secrets -n prod --as=system:serviceaccount:prod:default
kubectl auth can-i create pods -n prod --as=system:serviceaccount:prod:default   # 这一条同样等于能读 Secret

# 看卷挂载的真实结构，理解为什么 subPath 不更新
kubectl -n prod exec deploy/api -- ls -la /etc/app
# 期望看到 app.yaml 指向 ..data/app.yaml，而 ..data 指向带时间戳的目录

# 找出体量接近上限的 ConfigMap（单位字节，越大越危险）
kubectl get cm -A -o json | python3 -c 'import json,sys
for i in json.load(sys.stdin)["items"]:
    n = sum(len(v) for v in (i.get("data") or {}).values())
    if n > 100000:
        print(n, i["metadata"]["namespace"], i["metadata"]["name"])'

# 找出用 env 注入却期待热更新的 Deployment（有 configMapKeyRef 但没有卷挂载）
kubectl get deploy -A -o json | python3 -c 'import json,sys
for d in json.load(sys.stdin)["items"]:
    sp = d["spec"]["template"]["spec"]
    env_ref = any(e.get("valueFrom", {}).get("configMapKeyRef") for c in sp["containers"] for e in c.get("env") or [])
    vol_ref = any(v.get("configMap") for v in sp.get("volumes") or [])
    if env_ref and not vol_ref:
        print(d["metadata"]["namespace"], d["metadata"]["name"], "只用 env 注入，配置变更必须重启")'

③ 场景 · 什么进镜像、什么进 ConfigMap、什么必须走外部密钥服务

判断标准只有两条：这个值会不会随环境变化、泄露之后损失多大。下表把常见配置按这两条落到位置。

场景该放哪为什么代价
所有环境都一样的默认值、静态资源、模板文件打进镜像随镜像版本一起被固定和审计，启动期零外部依赖改它要重新构建与发版
随环境变化的非敏感配置：监听端口、超时、日志级别、功能开关ConfigMap，按变更频率拆成多个对象同一个镜像可以跑遍所有环境，这是上集群的前提条件对象数量增加，多环境差异要靠覆盖层管理
应用自己的口令、API key、TLS 私钥Secret，但值必须来自外部密钥系统（ESO / SOPS）Secret 提供的是「不进镜像、可按对象授权、卷挂载不落盘」，不是保密性多一个控制器与外部系统依赖，控制器权限本身成为高价值目标
云平台访问凭证（对象存储、消息队列、数据库 IAM）不要存，改用 ServiceAccount 与云 IAM 联邦长期 AK 不过期、泄露无感、轮转要改所有引用需要集群 OIDC 与云端角色信任关系的一次性配置
体量超过约 1 MiB 的规则表、词典、证书链集合对象存储或只读 PVC，用 initContainer 拉到 emptyDiretcd 单值有上限，且每个相关节点的 kubelet 都缓存一份启动期多一个外部依赖，见 存储篇
需要秒级下发、按实例灰度的动态规则配置中心客户端长轮询卷挂载是分钟级同步，做不到秒级与灰度引入客户端 SDK 与一套服务端，机制见 配置中心系列
多个命名空间需要同一份口令各命名空间各自从外部系统同步一份复制 Secret 会让轮转要改多处，任一命名空间被攻破即全部泄露外部系统的读取次数与配置条目增加

不适用边界：ConfigMap 不是配置中心，没有灰度、没有版本审批、没有客户端推送；Secret 不是保险箱，能在该命名空间创建 Pod 的人就等于能读它，收口要靠命名空间切分与短期凭证。清单的模板化与多环境覆盖在 Helm 与 GitOps 系列；配置变更要不要走流水线审批属于交付流程，见 CI 流水线；配置改坏之后的现象定位在 节点与集群级故障排查。

③ 场景 · 多环境差异管理：一句结论

结论是：用同一份基线加环境覆盖层，不要给每个环境各写一份完整清单，也不要靠命名前缀在同一个命名空间里区分环境。具体怎么组织目录、怎么做覆盖层、怎么跟自动同步配合，见 GitOps 系列的多环境篇；用 Helm 的 values 做参数化还是用 Kustomize 做覆盖层，取舍见 Helm 篇。

③ 场景 · 反模式

反模式症状后果正确做法
Secret 明文进 Git仓库里能 grep 到 base64 的 data 字段删掉也留在 Git 历史里，等于永久泄露；所有有仓库读权限的人都拿到了生产口令用 External Secrets Operator，Git 里只留引用路径
用环境变量注入却期待热更新改了 ConfigMap，等了半小时行为还是旧的误判成「K8s 的同步延迟」，浪费大量排查时间要热更新只能整卷挂载；否则改完就滚动更新
subPath 挂载后困惑为什么不更新同一个 ConfigMap，整卷挂的那份更新了，subPath 那份没动同一个 Pod 内出现两份不一致的配置接受 subPath 永不更新的事实，把需要更新的 key 改成整卷挂载
整个配置文件塞进一个 key一个 ConfigMap 只有一个 key，值是几百行 YAML改一个开关就重启全部相关服务；diff 是整块替换，评审时看不出改了什么按变更频率拆分对象，高频开关单独放
给应用的 ServiceAccount 过大权限SA 绑了 cluster-admin 或 secrets 的通配读权限应用被攻破即等于集群失守；能创建 Pod 就能读遍命名空间的 Secret按 resourceNames 授到具体对象；不访问 API 的应用关掉 token 自动挂载
同一个 Secret 跨命名空间共享用工具把一个 Secret 复制到十个命名空间轮转要改十处且容易漏；任一命名空间被攻破即全部泄露每个命名空间由 ExternalSecret 各自从外部系统同步，来源同一个但副本独立
把云平台 AK 存成 SecretDeployment 里有 AWS_ACCESS_KEY_ID 这类环境变量长期凭证不过期、泄露无感、轮转要改所有引用改用 ServiceAccount 与云 IAM 联邦，让 Pod 换取临时凭证

✅
最容易踩的坑
  • 环境变量注入永不更新：环境变量在进程创建时固化在进程内存里，改 ConfigMap 不可能影响已运行的进程，只能重启。
  • subPath 挂载同样永不更新：它绑定的是创建时那个文件，kubelet 换的是目录符号链接，绑定不受影响。这是最反直觉的一条。
  • 卷挂载的更新有分钟级延迟：默认同步周期 1 分钟，叠加缓存 TTL 后最坏两倍多，别等十秒就断定「没生效」。
  • 监听单个配置文件收不到 inotify 事件：更新靠替换符号链接完成，必须监听整个挂载目录的 CREATE 与 MOVED_TO。
  • envFrom 会静默跳过非法 key 名：带点号或减号的 key 不是合法环境变量名，会被直接丢掉，只在 Pod 事件里留一行，应用侧表现为「配置项莫名其妙不存在」。
  • base64 不是加密：没开静态加密时，Secret 的值在 etcd 数据文件和每一份备份里都能直接 grep 出来。
  • 能创建 Pod 就等于能读 Secret：把 get secret 权限收掉但留着 create pod，隔离等于没做。exec、改 Deployment、建 Job 都有等效能力。
  • Sealed Secrets 的控制器私钥必须单独备份：私钥丢了，Git 里所有历史密文一起作废，且没有任何恢复手段。
  • configMapGenerator 关掉哈希后缀：disableNameSuffixHash: true 会让内容变化不产生新名字，滚动更新也就不再触发，等于白用了这个特性。
  • 只给 ConfigMap 打了哈希注解，忘了 Secret：密钥轮转不会触发重启，导致应用继续用旧口令直到下次发布。
  • 不可变配置改内容：设了 immutable: true 之后 kubectl edit 会被 apiserver 拒绝，必须换新名字，这一点要在流水线里提前考虑。
  • ConfigMap 撑到接近 1 MiB：上限来自 etcd 单值大小，而且每个相关节点的 kubelet 都缓存一份，大对象会同时推高 apiserver 与 kubelet 的内存。
  • 引用不存在的 ConfigMap：默认 optional: false，Pod 会一直卡在 ContainerCreating，事件里写得很清楚但很多人只看 Pod 状态。
