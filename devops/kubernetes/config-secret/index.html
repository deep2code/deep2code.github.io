ConfigMap 与 Secret 配置管理

🏷️ Kubernetes,云原生

为什么要配置与镜像分离

十二要素应用（The Twelve-Factor App）第三条明确要求配置与代码严格分离。同一个镜像在 dev/staging/prod 三套环境之间不应该有任何差异——差异全部来自外部注入的配置。

ConfigMap 与 Secret 的本质

两者都是键值对存储，区别在于：ConfigMap 存明文非敏感配置，Secret 存敏感信息（默认 base64 编码，不是加密）。

对比项ConfigMapSecret
用途非敏感配置（端口、日志级别）敏感信息（密码、Token、TLS 证书）
编码明文base64（编码，非加密）
大小上限1 MiB1 MiB
etcd 存储明文默认 base64，可开启静态加密
推荐外置直接用生产用 Vault / External Secrets

它们都可以通过三种方式注入 Pod：

  • 环境变量：把 key 映射为容器环境变量，应用启动时读取。
  • 卷文件挂载：把整个 ConfigMap/Secret 挂成目录，每个 key 是一个文件。
  • subPath 单项挂载：只挂某一个 key 到指定路径。

实战：定义与挂载

下面是一个同时使用 ConfigMap（配置文件）和 Secret（数据库密码）的完整示例。注意 Secret 虽然叫"Secret"，但默认只是 base64——任何人用 kubectl get secret -o yaml 就能还原，生产必须开启静态加密（EncryptionConfiguration）或外部 KMS。

# 1. ConfigMap：非敏感配置
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  app.properties: |
    server.port=8080
    log.level=info
    feature.flag.newcheckout=true
  tz: Asia/Shanghai
---
# 2. Secret：敏感信息（值需先 base64 编码）
apiVersion: v1
kind: Secret
metadata:
  name: db-credentials
type: Opaque
data:
  username: YWRtaW4=          # echo -n 'admin' | base64
  password: cGFzc3dvcmQxMjM=  # echo -n 'password123' | base64
---
# 3. 在 Pod 中同时挂载两者
apiVersion: v1
kind: Pod
metadata:
  name: demo-app
spec:
  containers:
    - name: app
      image: my-app:v1
      # 方式一：Secret 注入为环境变量
      env:
        - name: DB_USER
          valueFrom: {secretKeyRef: {name: db-credentials, key: username}}
        - name: DB_PASSWORD
          valueFrom: {secretKeyRef: {name: db-credentials, key: password}}
      # 方式二：ConfigMap 挂成文件
      volumeMounts:
        - name: config-vol
          mountPath: /etc/config
          readOnly: true
  volumes:
    - name: config-vol
      configMap:
        name: app-config
        items:
          - key: app.properties
            path: app.properties

用 kubectl 命令行快速生成，避免手算 base64：

# 从字面值生成 Secret
kubectl create secret generic db-credentials \
  --from-literal=username=admin \
  --from-literal=password='Str0ng!Pass'

# 从文件生成
kubectl create configmap app-config --from-file=./app.properties

# 查看真实值（自动解码）
kubectl get secret db-credentials -o jsonpath='{.data.password}' | base64 -d

# 修改后自动滚动重启（ConfigMap 更新不会自动重启 Pod！）
kubectl rollout restart deployment/demo-app

在应用代码中读取配置

下面这段 Go 代码展示了"环境变量优先、文件兜底"的配置读取模式，是云原生应用推荐的写法——本地开发用环境变量，K8s 里由 ConfigMap/Secret 注入：

package main

import (
	"fmt"
	"os"
)

type Config struct {
	DBUser     string
	DBPassword string
	AppEnv     string
}

func LoadConfig() (*Config, error) {
	cfg := &Config{
		// 环境变量由 Secret/ConfigMap 注入；缺省给开发默认值
		DBUser:     getEnv("DB_USER", "root"),
		DBPassword: getEnv("DB_PASSWORD", ""),
		AppEnv:     getEnv("APP_ENV", "development"),
	}
	if cfg.DBPassword == "" {
		return nil, fmt.Errorf("DB_PASSWORD is required")
	}
	return cfg, nil
}

func getEnv(key, fallback string) string {
	if v, ok := os.LookupEnv(key); ok && v != "" {
		return v
	}
	return fallback
}

一个容易踩的坑：ConfigMap 热更新

通过 volume 挂载的 ConfigMap，在 ConfigMap 更新后，容器内文件会在约 1 分钟内同步更新（通过符号链接原子替换实现）。但环境变量注入的配置不会更新——因为环境变量是进程启动时固化的。更隐蔽的是：即使文件更新了，应用进程也不会自动重新加载，除非你监听文件变更（如 inotify）或配合 Reloader 类工具触发滚动重启。这就是为什么上面命令里有 kubectl rollout restart。

我踩过的坑：改了配置没生效

有次改了 ConfigMap 里的日志级别，等了十分钟还是 debug 输出。后来发现应用是用 env 注入的——环境变量启动即固化，文件再怎么同步都没用。我的教训：需要热更新的配置一律走 volume 挂载，env 注入只用于启动即固定的值。改完配置不放心就直接 kubectl rollout restart，别赌应用自己会 reload。

最佳实践

  • 开启 Secret 静态加密：修改 apiserver 启动参数 --encryption-provider-config，配置 aes-cbc 或 kms provider，防止 etcd 被拖库后密码明文泄露。
  • 敏感信息用外部 KMS/Vault：生产环境推荐 External Secrets Operator 或 Vault Agent Injector，避免 Secret 直接落 etcd。
  • 使用不可变 ConfigMap：immutable: true 禁止更新，避免被误改；需要变更就新建一个 v2 并滚动切换。
  • 按环境拆分命名空间：dev/prod 各自独立的 ConfigMap/Secret，不要靠同名前缀区分。
  • 控制 ConfigMap 大小：单个 ConfigMap 上限 1MiB。超大配置（如完整 nginx.conf）考虑用 Git 仓库 + initContainer 拉取。
  • 最小权限：用 RBAC 限制谁能 get secret，审计日志（Audit Log）开启对 Secret 的访问记录。

常见问题 FAQ

Q1：修改 ConfigMap 后 Pod 里为什么没变？

两种情况：(1) 你用的是 env 注入——环境变量启动即固化，永远不会变，必须重启 Pod；(2) 用 volume 挂载——文件会更新，但有 ~1 分钟延迟，且应用必须重新读文件才生效。最稳妥的做法：改完执行 kubectl rollout restart deployment/xxx。

Q2：Secret 真的安全吗？base64 算加密吗？

不算。base64 是编码不是加密，echo xxx | base64 -d 一秒还原。默认情况下 etcd 里存的就是 base64 值。要真正安全必须：(a) apiserver 开启静态加密；(b) 启用 RBAC 严格控制读权限；(c) 高敏场景用 Vault/KMS 外挂。

Q3：ConfigMap 里放 N 份还是一个大 ConfigMap？

按"变更频率"拆分。频繁变更的（功能开关、灰度配置）单独放，低频不变的（时区、公共字典）合并放。这样改一个开关不会触发全量配置滚动。

Q4：Pod 一直 ContainerCreating，报 configmap not found？

说明 Pod 引用的 ConfigMap/Secret 还没创建，或名字/命名空间写错。kubectl get cm -n <ns> 确认存在；若用了 optional: false（默认），缺失就会卡住。

总结

ConfigMap 与 Secret 是 K8s 实现"一份镜像跑遍环境"的基石：非敏感配置走 ConfigMap 文件挂载，敏感信息走 Secret 并配合静态加密/KMS。记住两个关键事实——环境变量不热更新、volume 文件更新需要应用自己重读——再配合 rollout restart，配置管理就稳了。下一篇解决"数据怎么持久化"。
