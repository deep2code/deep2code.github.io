Volume 与持久化存储

🏷️ Kubernetes,云原生

容器的短暂性与持久化存储的需求

容器文件系统是临时的（Ephemeral）：容器重启后写入的文件全部丢失，Pod 调度到新节点后更是彻底失联。对于无状态应用这无所谓，但 MySQL、Redis、ES、Kafka 这类有状态服务必须解决"数据跟着 Pod 走"的问题。

三层抽象的工作原理

flowchart TB SC[StorageClass
存储类/Provisioner] -.动态创建.-> PV[(PersistentVolume
网络磁盘/NFS/Ceph)] PVC[PersistentVolumeClaim
用户申请 5Gi RWO] -->|绑定| PV POD[Pod] -->|mount| PVC subgraph 临时卷 ED[emptyDir
Pod 生命周期] HOST[hostPath
节点本地目录] end POD --> ED POD --> HOST

核心概念一句话：

抽象层生命周期谁管典型场景
emptyDir跟随 Pod系统自动建/删缓存、临时文件、Sidecar 共享
hostPath跟随节点挂载节点目录本地 SSD、性能敏感
PV集群级，独立于 Pod管理员预置或 SC 动态建持久化数据盘
PVC用户申请单用户写申请"我要 5Gi RWO"
StorageClass动态供给规则管理员定义CSI 调云 API 自动建盘

访问模式：RWO（单节点读写）、ROX（多节点只读）、RWX（多节点读写）。大多数云硬盘是 RWO，NFS/CephFS 才能 RWX。

实战：静态 PV + PVC + Pod

先用 NFS 后端做一个完整示例。管理员先创建 PV，用户再写 PVC 申请：

# 1. 管理员预置 PV（NFS 后端）
apiVersion: v1
kind: PersistentVolume
metadata:
  name: nfs-pv-1
spec:
  capacity:
    storage: 5Gi
  accessModes:
    - ReadWriteOnce
  persistentVolumeReclaimPolicy: Retain
  nfs:
    server: 192.168.10.100
    path: /export/data
---
# 2. 用户申请 PVC
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: data-pvc
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 5Gi
---
# 3. Pod 挂载 PVC
apiVersion: v1
kind: Pod
metadata:
  name: mysql-pod
spec:
  containers:
    - name: mysql
      image: mysql:8.0
      volumeMounts:
        - name: data
          mountPath: /var/lib/mysql
  volumes:
    - name: data
      persistentVolumeClaim:
        claimName: data-pvc

动态供给：StorageClass + StatefulSet

生产环境几乎不用静态 PV——每次手动建盘太累。用 StorageClass 实现"写 PVC 自动建盘"。下面以云厂商 CSI 为例，配合 StatefulSet 部署 MySQL：

# StorageClass：以阿里云云盘 CSI 为例
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast-ssd
provisioner: diskplugin.csi.alibabacloud.com
parameters:
  type: cloud_ssd
reclaimPolicy: Delete
volumeBindingMode: WaitForFirstConsumer
---
# StatefulSet：MySQL 主从，每个实例绑定独立 PVC
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: mysql
spec:
  serviceName: mysql-headless
  replicas: 2
  selector:
    matchLabels: {app: mysql}
  template:
    metadata: {labels: {app: mysql}}
    spec:
      containers:
        - name: mysql
          image: mysql:8.0
          volumeMounts:
            - name: data
              mountPath: /var/lib/mysql
  volumeClaimTemplates:
    - metadata: {name: data}
      spec:
        accessModes: ["ReadWriteOnce"]
        storageClassName: fast-ssd
        resources:
          requests: {storage: 100Gi}

注意 volumeClaimTemplates：StatefulSet 会为每个序号 Pod（mysql-0、mysql-1）自动创建独立 PVC，Pod 重建后名字不变，原 PVC 自动挂回，这就是"数据跟着身份走"的关键。

# 观察动态供给全过程
kubectl get sc,pvc,pv
kubectl describe pvc data-mysql-0

# 扩缩容 PVC 容量（需 CSI 支持）
kubectl patch pvc data-mysql-0 -p '{"spec":{"resources":{"requests":{"storage":"200Gi"}}}}'

最佳实践

  • 区分临时数据与持久数据：缓存、上传临时文件用 emptyDir 或 memory: true（tmpfs）；真实业务数据必须走 PVC。
  • reclaimPolicy 选 Retain 还是 Delete：动态盘用 Delete（PVC 删了盘也删，避免浪费）；重要数据用 Retain，防止误删 PVC 把生产数据抹掉。
  • WaitForFirstConsumer：让 PVC 延迟到 Pod 真正调度时才绑定，这样磁盘能就近创建到 Pod 所在可用区，避免跨可用区流量费用。
  • StatefulSet 必须配 Headless Service：Pod DNS 形如 mysql-0.mysql-headless.default.svc，主从选举靠这个稳定标识。
  • 备份重于一切：PVC 不自动备份。用 Velero 或云厂商快照定期备份，演练恢复流程。
  • 监控磁盘 IOPS 与容量：云盘有 IOPS 上限，数据库场景选高 IOPS 规格，并用 Prometheus 监控 node_filesystem_* 指标。
我踩过的坑：Delete 策略误删生产数据

早期用云盘 CSI，默认 reclaimPolicy 是 Delete。有次误删了一个 staging 命名空间，整个命名空间的 PVC 跟着被删，底层云盘直接被回收。还好是 staging，数据不重要。生产环境我全部改成 Retain——PVC 删了盘还留着，确认不需要再手动删云盘。动态盘省的是管理成本，Delete 策略省的是盘钱，但一次误删就够你吃一年。

常见问题 FAQ

Q1：PVC 一直 Pending 怎么排查？

kubectl describe pvc 看 Events。常见原因：(a) 没有匹配的 StorageClass 或集群里没装 CSI；(b) 请求的容量超过现有 PV；(c) 访问模式不匹配（你要 RWX 但只有 RWO 的盘）；(d) WaitForFirstConsumer 模式下 Pod 还没被调度。

Q2：Pod 删了数据还在吗？

走 PVC/PV 的话：在。PVC 与 Pod 解耦，只要 PVC 没删、PV reclaimPolicy 是 Retain，数据就一直在，新 Pod 挂载同一个 PVC 即可看到。emptyDir/hostPath 则随 Pod 删除丢失。

Q3：RWO 的盘能挂给两个节点吗？

不能同时读写。RWO = ReadWriteOnce，只允许一个节点挂载。两个 Pod 在不同节点想用同一份数据，必须用 RWX（NFS/CephFS/云文件存储）。强行调度会导致第二个 Pod 一直 ContainerCreating。

Q4：StatefulSet 缩容后 PVC 会跟着删吗？

默认不会。StatefulSet 缩容只删 Pod，PVC/PV 保留。这是好事（保护数据），但也意味着如果你直接 kubectl delete sts，PVC 会残留，需要手动清理。

总结

存储在 K8s 里是"管理员/系统管供给，用户只管申请"的分层模型：emptyDir 救临时、PV/PVC 管持久、StorageClass 自动化、StatefulSet 保身份。选型时先想清楚"数据要不要跨 Pod 漂移、要不要多节点共享"，再决定后端类型。下一篇我们看流量怎么从集群外进来。
