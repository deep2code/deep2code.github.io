Kubernetes 存储抽象与有状态服务的现实

🏷️ Kubernetes,云原生

存储是 K8s 里唯一「写错了改不回来」的一层：Deployment 选错可以删了重建，PVC 删错就是数据没了。而真正咬人的不是复杂功能，是三个默认值——回收策略默认 Delete、绑定模式默认 Immediate、扩容开关默认关闭。这篇先给能直接 apply 的最小持久化清单和「要存什么 → 用哪种卷」的查表路径，再往下拆抽象与物理事实，最后回答有状态服务到底该不该上集群。

💡
这篇怎么读
  • ① 用法：最小可用的 PVC 加 Deployment、StatefulSet 的 volumeClaimTemplates 清单，一张「要存什么 → 用哪种卷」对照表，以及 StorageClass 三个关键字段的「设错会出什么现象」速查。
  • ② 原理：StorageClass 与 PV 与 PVC 的职责切分与 PV 状态机、访问模式为什么是节点级而不是 Pod 级、reclaimPolicy 怎么把删命名空间变成删库、七类卷在性能与故障域上的差异、StatefulSet 与 PVC 的绑定规则、扩容与可用区拓扑的硬限制、快照与备份的本质区别。
  • ③ 场景：哪些有状态组件上集群收益明显、哪些是在自找麻烦，以及十条反模式对应的正确做法。

① 用法 · 两份最小可用清单与「要存什么 → 用哪种卷」

先把清单跑起来。下面两份是「能直接 apply 且不会在第二周变成故障」的最小版本，注释只说明为什么要这行：

# ---------- 1) 单副本服务要一块持久盘：PVC 加 Deployment ----------
apiVersion: v1
kind: PersistentVolumeClaim
metadata: {name: app-data}
spec:
  accessModes: ["ReadWriteOnce"]      # 云块存储只有这一种；要多节点同时读写见下面的对照表
  storageClassName: db-ssd            # 不写就落到集群默认 SC，而默认 SC 的回收策略通常是 Delete
  resources:
    requests: {storage: 20Gi}         # 只能扩不能缩，别为了省钱开太小
---
apiVersion: apps/v1
kind: Deployment
metadata: {name: app}
spec:
  replicas: 1                         # RWO 卷跨不了节点，多副本要么改 StatefulSet 要么共享失败
  strategy: {type: Recreate}          # 默认 RollingUpdate 会让新旧 Pod 同时持卷，落到两台机器就卡住
  selector:
    matchLabels: {app: app}
  template:
    metadata:
      labels: {app: app}
    spec:
      containers:
        - name: app
          image: registry.example.com/app:9f3c2a1
          volumeMounts:
            - name: data
              mountPath: /var/lib/app
              subPath: app            # 避开新建 ext4 卷根目录里的 lost+found
      volumes:
        - name: data
          persistentVolumeClaim: {claimName: app-data}
---
# ---------- 2) 每个副本各一块盘：StatefulSet 的 volumeClaimTemplates ----------
apiVersion: v1
kind: Service
metadata: {name: pg-headless}
spec:
  clusterIP: None                     # Headless Service 是 Pod 级稳定 DNS 名的前提
  selector: {app: pg}
  ports: [{port: 5432}]
---
apiVersion: apps/v1
kind: StatefulSet
metadata: {name: pg}
spec:
  serviceName: pg-headless            # 写错就没有 Pod 级域名，peer 互相找不到
  replicas: 3
  selector:
    matchLabels: {app: pg}
  template:
    metadata:
      labels: {app: pg}
    spec:
      terminationGracePeriodSeconds: 60      # 数据库需要刷盘时间，默认 30 秒偏紧
      containers:
        - name: pg
          image: postgres:16.3
          volumeMounts:
            - {name: data, mountPath: /var/lib/postgresql/data, subPath: pgdata}
  volumeClaimTemplates:               # 自动生成 data-pg-0 / data-pg-1 / data-pg-2
    - metadata: {name: data}
      spec:
        accessModes: ["ReadWriteOnce"]
        storageClassName: db-ssd
        resources:
          requests: {storage: 100Gi}
# 这里的容量以后改不了：apply 会直接报字段不可变，只能逐个 patch PVC，原因见原理层

清单之前真正要做的判断是「这份数据该放哪」。下表按「要存什么」查，右两列直接给丢数据的条件：

要存什么用哪种卷什么时候会丢还要注意什么
请求处理中的临时文件、解压中转目录emptyDir: {}Pod 删除即丢；容器重启不丢算进节点 ephemeral-storage，写多了触发节点磁盘压力把自己驱逐，务必设 sizeLimit
同 Pod 内两个容器交换数据emptyDir: {}同上这是它的首要用途；sidecar 采日志、initContainer 下载产物都靠它
需要极快读写的解密后文件、小缓存emptyDir 加 medium: MemoryPod 删除或机器重启即丢占的是容器内存额度，写 2Gi 而 limit 只给 1Gi 就是 OOMKilled
节点自身的日志、指标、设备、运行时 sockethostPath节点被替换即丢安全上等同给容器 root 权限，只用于监控类 DaemonSet，不要拿它做业务持久化
数据库、消息队列、任何重启后必须还在的数据PVC（云块存储 CSI）删 PVC 且回收策略为 Delete 时连云盘一起销毁绑定单一可用区；多副本各自一块盘要走 volumeClaimTemplates
多个节点上的 Pod 要同时读写同一份目录PVC（NFS 或云文件存储，RWX）取决于服务端，单点 NFS 就是单点元数据慢、延迟高，不要在上面跑数据库，锁与 fsync 语义不完整
配置文件、证书、口令ConfigMap 或 Secret 卷挂载不适用，它们是集群对象容量上限约 1 MiB，热更新与 subPath 的坑见 配置与密钥在集群里的落地
Kafka、ES、ClickHouse 这类自带多副本的组件local PV节点故障即数据不可达必须配节点亲和与 WaitForFirstConsumer，且应用层必须真有副本
备份、静态资源、离线数据对象存储，优先让应用直接走 SDK区域级冗余，最不容易丢强行挂成文件系统会在 rename 与随机写上出问题

选定 PVC 之后，决定成败的不是 PVC 本身而是它背后的 StorageClass。集群交付时把下面三个字段核对一遍，比事后任何补救都便宜：

StorageClass 字段作用常见默认值设错会出什么现象
reclaimPolicy删 PVC 时底层卷是保留还是销毁动态供给继承 SC，主流云厂商的默认 SC 给的是 Delete留默认时一条 kubectl delete ns staging 级联删掉全部 PVC，云盘在云侧销毁且无回收站
volumeBindingMode先建盘再调度，还是先调度再建盘Immediate留默认时盘落在 A 区而只有 B 区有余量，Pod 永久 Pending；改成 WaitForFirstConsumer 后 PVC 在没有 Pod 引用前一直 Pending，这是正常现象不是故障
allowVolumeExpansion允不允许在线扩容不写即 false没开时盘满了只能迁数据，业务要停机；kubectl patch pvc 会直接被拒绝
parameters 里的磁盘规格决定 IOPS 与吞吐档位随厂商与驱动变化很多云的 IOPS 与容量挂钩，小盘跑不到需要的性能，表现为「明明是 SSD 却很慢」
provisioner指定哪个 CSI 驱动响应无默认，必填写错或对应 CSI 没装，PVC 一直 Pending 且事件里没有任何 provisioner 响应记录

这些字段的确切默认值随集群版本与 CSI 驱动变化，落地前用 kubectl explain storageclass 与 kubectl get sc -o yaml 核对你集群的实际取值，不要照抄文档。为什么这三个默认值都指向同一个方向的风险，在下面几节展开。

② 原理 · 三层抽象：谁定义规则、谁是真实存储、谁在申领

搞清这三层的归属，能直接解释「为什么删命名空间会把数据删掉」以及「为什么 PVC 挪不到别的命名空间」。K8s 存储的设计目标是把「运维懂的事」和「开发懂的事」切开：开发只声明「我要 100Gi 可读写的盘」，运维决定这块盘用什么后端、什么性能档、删了之后怎么处置。三个对象各司其职：

  • StorageClass：一条供给规则。规定用哪个 CSI 驱动、什么磁盘类型、绑定时机、回收策略、能不能扩容。它是集群级对象。
  • PV：一块真实存在的存储。有容量、访问模式、拓扑标签、回收策略，也是集群级对象——它不属于任何命名空间。
  • PVC：一份申领单，命名空间级。Pod 只认 PVC，永远不直接写 PV。

这个层级关系解释了一个常见困惑：为什么删命名空间会把数据删掉？因为 PVC 在命名空间里、PV 在集群级，删命名空间级联删掉 PVC 之后，PV 的回收动作被触发，如果回收策略是 Delete，集群级的 PV 和底层云盘就一起消失了。

PV 不是「一直在那里等着」的静态资源，它有明确的状态机，而 Released 这个状态是很多人被卡住的地方：

② 原理 · 访问模式的真实含义

搞清这一节能解决两类事故：多副本 Pod 卡在 ContainerCreating 报多重挂载错误，以及两个 Pod 同写一块盘把数据文件写坏。访问模式是整篇里误解最多的概念，它描述的是节点级挂载并发度，不是 Pod 级：

访问模式准确语义同节点多 Pod 能共享吗后端支持情况典型误用
ReadWriteOnce（RWO）同一时刻只能被一个节点挂载为读写能，同节点多个 Pod 可同时读写同一个卷所有云块存储、local PV以为 RWO 天然互斥，于是两个副本落到同节点后同时写数据文件，把库写坏
ReadOnlyMany（ROX）可被多个节点同时挂载为只读能文件存储、部分块存储的只读快照卷指望只读卷还能写入日志
ReadWriteMany（RWX）可被多个节点同时挂载为读写能仅文件存储：NFS、CephFS、云文件存储；云块存储不支持给云盘 PVC 写 RWX，PVC 直接 Pending 或绑定后第二个节点挂不上
ReadWriteOncePod（RWOP）整个集群只有一个 Pod能挂载读写，这才是真正的独占不能，这是它的目的需要 CSI 驱动支持，1.22 引入、1.29 稳定老集群直接写 RWOP 导致 PVC 无法绑定

需要特别点出的是：访问模式不是强制锁，而是调度与挂载阶段的约束声明。RWO 卷被节点 A 挂上后，调度器不会把引用同一 PVC 的 Pod 放到节点 B（放上去也会卡在 ContainerCreating，报 Multi-Attach error）；但对同节点的 Pod，它不做任何限制。需要「同一份数据只允许一个进程写」的语义，靠的是 RWOP 或应用自己的文件锁，不是 RWO。

② 原理 · reclaimPolicy：一条默认值引发的删库

搞清这一节能解决的是最贵的那类现象：清理环境之后数据永久消失，且没有任何回收站可翻。

回收策略删 PVC 后发生什么数据后续操作适用
DeletePV 被删除，CSI 调用 DeleteVolume，底层云盘一起销毁不可恢复无CI 环境、缓存类数据、明确可重建的数据
RetainPV 保留并进入 Released，底层卷保留仍在需人工清 claimRef 才能复用，或手工删云盘所有生产有状态数据
Recycle早期行为：清空数据后重新 Available被擦除已废弃，不要用无

关键事实：动态供给的 PV 继承 StorageClass 的 reclaimPolicy，而主流云厂商 StorageClass 的默认值是 Delete。这意味着一条 kubectl delete ns staging 会级联删掉命名空间里所有 PVC，然后所有数据盘在云侧被销毁。这类事故在我见过的团队里出现的频率高得离谱，而且往往在「清理环境」这种低风险动作里发生。

❌
默认 Delete 的三重叠加风险

第一重：默认值不显眼，PVC YAML 里看不到 reclaimPolicy，它藏在 StorageClass 里。第二重：删除动作会级联，删命名空间、删 Helm release、kubectl delete -f ./ 都会带走 PVC。第三重：云侧删除通常不进回收站，块存储删掉就是删掉。防线要放三层：重要数据的 StorageClass 设为 Retain；给关键 PVC 打上准入策略或 finalizer 阻止误删；云侧开启磁盘删除保护。

② 原理 · 卷类型的选择矩阵

用法层那张表给的是结论，这张表给的是每类卷背后的性能、共享能力与故障域，用来解释结论为什么成立、以及在什么条件下会翻转。

卷类型性能共享能力故障域扩容适用与注意
emptyDir取决于节点盘同 Pod 内多容器共享随 Pod 消失（Pod 删除即丢，容器重启不丢）可设 sizeLimit，超了 Pod 被驱逐临时文件、多容器交换数据；算进节点 ephemeral-storage，写太多会触发 DiskPressure
emptyDir + medium: Memory最高（tmpfs）同上随 Pod 消失，且机器重启丢受 sizeLimit 与节点内存限制高速缓存、放解密后的敏感文件；占用的是容器内存额度，会把 Pod 顶成 OOMKilled
hostPath高（本地盘直通）同节点所有 Pod 都能读写绑死单节点，节点没了数据就没了无管理能力安全上等同越权：挂宿主根目录或运行时 socket 等于给容器 root；只用于监控类 DaemonSet
云块存储（CSI）中到高，有 IOPS 与吞吐档位上限RWO，单节点可用区级冗余，绑定单一可用区支持在线扩容（需 allowVolumeExpansion）数据库、消息队列的默认选择；注意 IOPS 常与容量挂钩，小盘可能跑不到需要的性能
NFS 与云文件存储低到中，元数据操作慢，延迟高RWX，多节点读写取决于服务端，单点 NFS 就是单点故障通常弹性容量共享上传目录、多副本共享静态资源；不要跑数据库，锁与 fsync 语义会出问题
对象存储（CSI 或 SDK）吞吐好、延迟高、无 POSIX 语义天然多端共享区域级冗余，最可靠近乎无限备份、静态资源、大数据；强行挂成文件系统会在 rename 与随机写上出问题，优选让应用直接走 SDK
local PV最高（本地 NVMe）RWO 且不可跨节点节点级单点，节点挂了数据不可达不支持在线扩Kafka、ES、ClickHouse 这类自己做多副本的组件；必须配 WaitForFirstConsumer 与节点亲和，应用层必须有副本

② 原理 · StatefulSet 与 PVC 的绑定关系

搞清这一节能解决「缩容之后账单没降」「扩容改不动容量」「重建后挂到了别人的数据」这三类现象。StatefulSet 的核心价值是「身份稳定」，存储上体现为 volumeClaimTemplates：它为每个序号 Pod 生成独立且名称可预测的 PVC，格式是「卷名-StatefulSet名-序号」，例如 data-mysql-0。Pod 被删、被重建、被调度到另一台机器，只要序号不变，挂回来的就是同一块盘。工作负载对象本身怎么选见 工作负载对象的选择与编写。

# StorageClass：生产上这三个字段比 type 更重要
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: db-ssd
provisioner: disk.csi.aliyun.com          # 换成你的 CSI，如 ebs.csi.aws.com
parameters:
  type: cloud_essd
  fsType: ext4
reclaimPolicy: Retain                      # 生产数据不要留默认 Delete
allowVolumeExpansion: true                 # 不开这个，以后想扩容只能迁数据
volumeBindingMode: WaitForFirstConsumer    # 先调度再建盘，避免可用区错配
---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: mysql
spec:
  serviceName: mysql-headless              # 必须配 Headless Service 才有稳定 DNS
  replicas: 3
  podManagementPolicy: OrderedReady        # 默认按序启动；要并行启动改成 Parallel
  selector:
    matchLabels: {app: mysql}
  template:
    metadata:
      labels: {app: mysql}
    spec:
      terminationGracePeriodSeconds: 60    # 给数据库留足刷盘时间
      containers:
        - name: mysql
          image: mysql:8.0.36
          volumeMounts:
            - name: data
              mountPath: /var/lib/mysql
              subPath: mysql               # 用 subPath 避开 lost+found 导致的初始化失败
          resources:
            requests: {cpu: "2", memory: 8Gi}
            limits: {cpu: "4", memory: 8Gi}
  volumeClaimTemplates:
    - metadata:
        name: data
      spec:
        accessModes: ["ReadWriteOnce"]
        storageClassName: db-ssd
        resources:
          requests: {storage: 200Gi}
# 生成的 PVC 名称固定为 data-mysql-0 / data-mysql-1 / data-mysql-2
# 注意：删除 StatefulSet 与缩容都不会删这些 PVC，云盘会继续计费

四条容易踩的规则：

操作PVC 会怎样数据你需要做什么
删除单个 Pod保留保留，新 Pod 挂回同一 PVC什么都不用做，这是设计意图
缩容（replicas 从 3 到 1）data-mysql-1 与 data-mysql-2 保留保留确认不再需要后手工删 PVC，否则云盘一直计费；再扩容回去会自动复用
删除整个 StatefulSet全部 PVC 保留保留这是保护机制；1.27 起可用 persistentVolumeClaimRetentionPolicy 声明删除时一并清理
改 volumeClaimTemplates 的容量对已存在 PVC 无效不变该字段不可变，apply 会直接报错；只能逐个 patch PVC 扩容，或删 StatefulSet 保留 PVC 后重建

② 原理 · 扩容与拓扑约束

搞清这一节能解决两个现象：patch 了容量但 df 里没变大，以及盘建好了 Pod 却永久 Pending。

卷扩容有三条硬限制：只能扩不能缩；StorageClass 必须 allowVolumeExpansion: true；文件系统层扩容要么由 CSI 在线完成，要么需要重启 Pod 才能生效（FileSystemResizePending 状态就是在等重启）。所以「先开小盘省钱，以后再缩」这个想法在 K8s 上不成立。

拓扑约束来自云块存储的物理事实：一块盘只存在于一个可用区，挂载它的节点必须在同一可用区。绑定模式决定了「先建盘」还是「先选节点」：

sequenceDiagram participant U as 开发者 participant API as apiserver participant SCH as 调度器 participant PRV as external-provisioner 与 CSI participant CSP as 云存储 API U->>API: 创建 PVC 引用 StorageClass Note over PRV: Immediate 模式在这里就建盘
可用区由云侧随机挑
后面调度器只能被动服从 API->>SCH: Pod 待调度 PVC 仍未绑定 SCH->>SCH: 按 CPU 内存 亲和 拓扑标签选出节点 SCH->>API: 给 PVC 打注解 selected-node API->>PRV: 触发按选定节点供给 PRV->>CSP: 在该节点所在可用区创建卷 CSP-->>PRV: 返回卷 ID 与拓扑信息 PRV->>API: 创建 PV 并完成绑定 API->>SCH: 绑定成功 Pod 正式落到该节点 Note over SCH: WaitForFirstConsumer 的收益
调度决策先行 不会出现盘在 A 区
而只有 B 区有资源的死局 
# 扩容：改 PVC 的 requests.storage 即可，注意只能变大
kubectl patch pvc data-mysql-0 -p '{"spec":{"resources":{"requests":{"storage":"400Gi"}}}}'

# 判读扩容是否卡住：看 Conditions
kubectl describe pvc data-mysql-0 | tail -20
# Resizing                = CSI 正在扩底层卷
# FileSystemResizePending = 底层已扩，等 Pod 重启才能扩文件系统
# 出现后者时重建 Pod：kubectl delete pod mysql-0

# PVC Pending 的定位顺序：先事件，再 provisioner 日志
kubectl get pvc -A | grep -v Bound
kubectl describe pvc data-mysql-0
kubectl -n kube-system logs deploy/csi-provisioner --tail=100   # 云侧配额或库存不足只在这里报

# 卷挂不上时看 VolumeAttachment 与 Pod 事件
kubectl get volumeattachment | grep pv-xxxx
kubectl describe pod mysql-0 | grep -A5 Events
# Multi-Attach error = RWO 卷被另一个节点占着，通常是老节点失联后未解绑

# 巡检孤儿 PVC：没有任何 Pod 引用却还在计费的盘
kubectl get pvc -A -o json | python3 -c '
import json,sys,subprocess
pvcs={(i["metadata"]["namespace"],i["metadata"]["name"]) for i in json.load(sys.stdin)["items"]}
used=set()
pods=json.loads(subprocess.check_output(["kubectl","get","pods","-A","-o","json"]))
for p in pods["items"]:
    ns=p["metadata"]["namespace"]
    for v in p["spec"].get("volumes",[]):
        c=v.get("persistentVolumeClaim")
        if c: used.add((ns,c["claimName"]))
for x in sorted(pvcs-used): print("orphan pvc:", x[0], x[1])
'

② 原理 · 快照不是备份

搞清这一节能避免最坏的一种发现：出事当天才知道手里那批快照恢复不了。

能力VolumeSnapshot应用层备份（mysqldump、pg_basebackup、引擎快照）
创建速度秒级，增量分钟到小时，取决于数据量
一致性块级崩溃一致，不保证应用一致（内存脏页与未提交事务不可控）可做到事务一致
故障域与源卷在同一存储系统，存储整体故障或账号被删则一起丢可落到另一个账号、另一个区域、另一种介质
跨集群与跨云恢复基本不行，依赖同一 CSI 与同一存储可以
恢复粒度整卷可到库、表、时间点（配合 binlog 或 WAL）
定位快速回退、克隆测试环境灾难恢复的唯一可靠手段
 
# 快照的正确用途：克隆一份生产数据到测试环境，或变更前的快速回退点
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshotClass
metadata:
  name: csi-snapclass
driver: disk.csi.aliyun.com
deletionPolicy: Retain          # 删 VolumeSnapshot 对象时保留底层快照
---
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshot
metadata:
  name: mysql-0-before-upgrade
spec:
  volumeSnapshotClassName: csi-snapclass
  source:
    persistentVolumeClaimName: data-mysql-0
---
# 从快照恢复：新建一个 PVC，dataSource 指向快照（容量不能小于原卷）
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: data-mysql-restore
spec:
  storageClassName: db-ssd
  accessModes: ["ReadWriteOnce"]
  resources:
    requests: {storage: 200Gi}
  dataSource:
    name: mysql-0-before-upgrade
    kind: VolumeSnapshot
    apiGroup: snapshot.storage.k8s.io
# 打快照前，数据库侧最好先加读锁或用引擎自身的一致性快照能力，否则只是崩溃一致

③ 场景 · 有状态服务该不该上 K8s

这个问题的常见答案是「云原生就该全上」，这不是工程判断。先把收益说清楚：上 K8s 换来的是统一编排、统一监控、声明式扩缩容与更快的环境交付，而不是性能——经过 CSI、容器文件系统与容器网络，性能只可能持平或略降。所以判断标准应该是运维能力，而不是技术时髦度：

flowchart TB S{"这个组件有成熟 Operator 吗"} -->|"没有 需要自己写主从切换逻辑"| NO["不要上
用云托管服务或物理机"] S -->|"有 如 PostgreSQL Redis 的主流 Operator"| T{"团队能独立处理存储层故障吗"} T -->|"不能 遇到卷挂不上只能提工单"| NO T -->|"能 会看 VolumeAttachment 与 CSI 日志"| R{"恢复路径演练过吗"} R -->|"没演练 备份从未恢复过"| WAIT["先补备份与演练
再谈上线"] R -->|"演练过 有 RTO 与 RPO 数字"| YES["可以上
local PV 或云盘 加 Operator 加 PDB"] YES --> G["额外要求
反亲和打散 跨可用区副本
Retain 回收策略 独立监控"]

一条实用的分界线：自己就有多副本与故障转移能力的组件（Kafka、ES、ClickHouse、Redis Cluster）上 K8s 收益明显，因为它们不依赖存储层做高可用，节点挂了靠应用层副本兜底；依赖单块盘存活的核心交易库上 K8s 收益有限而风险集中，用云托管数据库更理性。下表把常见诉求逐条对号入座：

场景该怎么做为什么代价
核心交易数据库，团队没有专职 DBA用云托管数据库，集群里只放应用高可用与备份恢复由厂商兜底，存储层故障不用你处理成本更高、参数可调空间小、跨云迁移被锁定
Kafka、ES、ClickHouse 这类自带副本的组件上集群，用 local PV 加节点亲和，配 PDB 与反亲和高可用在应用层，存储只需要快，不需要跨节点可达节点替换要走应用层数据重平衡，扩容不是加盘而是加节点
Redis 或 PostgreSQL 有成熟 Operator 且团队愿意维护上集群，云块存储加 Operator，回收策略 RetainOperator 接管主从切换、备份与版本升级，声明式收益最大多一层 Operator 要跟着升级；Operator 的 bug 会变成你的数据风险
只是想要一块「重启不丢」的盘存上传文件优先改成对象存储，让应用走 SDK省掉可用区绑定、扩容、备份、多副本共享这一整串问题需要改应用代码，本地开发要接 mock 或 MinIO
多个副本要共享同一个上传目录用 RWX 文件存储，且只放静态资源与上传件只有文件存储支持多节点同时读写延迟高、元数据操作慢，绝不能在上面跑数据库
缓存或可重建的中间结果用 emptyDir 并设 sizeLimit，或干脆用外部 Redis数据可重建就不该占用持久化与备份的复杂度预算Pod 重建后要重新预热，冷启动期性能下降
临时环境、CI、评审环境StorageClass 用 Delete，并给命名空间配 TTL 清理这些数据本来就该跟着环境一起消失误把生产命名空间指到这个 SC 就是删库，SC 命名必须一眼可辨
已经用 Deployment 挂 PVC 跑了数据库迁到 StatefulSet 或托管数据库，过渡期先把副本数锁到 1RWO 卷不能跨节点，多副本永远起不来；Pod 重建后 peer 地址也会失效迁移要停写或双写，PVC 里的数据需要手工搬运

不适用边界：这篇解决不了「要不要上集群」这个更上层的问题，那一层在 K8s 的抽象层次与该不该上；镜像与容器文件系统本身的分层在 Docker；PV 容量与 inode 的水位监控、节点磁盘压力的排查在 Kubernetes 节点与集群级故障排查 与 可观测性系列；StorageClass 与 PVC 在多环境之间的差异化交付在 GitOps 系列；有状态服务的副本、选主与一致性这类架构问题不在存储层，见 分布式系统系列。

③ 场景 · 反模式对照

反模式会怎么出事正确做法
用 hostPath 做持久化数据绑死一台机器，节点被替换就没了；同时把宿主文件系统暴露给容器，是权限提升通路用 local PV（带节点亲和与 WaitForFirstConsumer）或网络存储
RWO 卷期望跨节点共享第二个 Pod 永远 ContainerCreating，报 Multi-Attach error确实要多节点读写就上文件存储（RWX），或把写入收敛到单副本
以为 RWO 能防止两个 Pod 同时写同节点两个 Pod 一起写数据文件，数据库文件损坏需要独占用 RWOP，或由应用层加锁
reclaimPolicy 留默认 Delete删命名空间或删 Helm release 直接销毁云盘生产 StorageClass 显式 Retain，并开云侧删除保护
把快照当备份存储系统整体故障或账号被删时快照与数据一起消失应用层逻辑备份加跨账号跨区域对象存储，并做恢复演练
emptyDir 存重要数据Pod 重建即丢；写太多还会触发节点 DiskPressure 把自己驱逐只放可重建的临时数据，并设 sizeLimit
忘记清理孤儿 PVCStatefulSet 删了、缩容了，云盘还在按小时计费，一年下来是真金白银定期巡检无引用 PVC，或用 persistentVolumeClaimRetentionPolicy
StorageClass 不开 allowVolumeExpansion盘满了只能迁移数据，业务停机建集群时就统一打开
用云盘却留 Immediate 绑定模式盘落在 A 区而只有 B 区有资源，Pod 永久 Pending一律用 WaitForFirstConsumer
有状态服务不评估存储故障就上节点失联后卷解绑失败，Pod 起不来，既不会自愈也没人会修先有 Operator、演练与 runbook，再迁

存储是 K8s 里抽象最漂亮、现实最扎实的一块：StorageClass 定规则、PV 是真实的盘、PVC 是申领单，三层解耦让开发不必关心后端。但抽象挡不住物理事实——盘绑在可用区、RWO 绑在节点、Delete 策略绑着你的数据。落地时把四个默认值改对（Retain、allowVolumeExpansion、WaitForFirstConsumer、sizeLimit），把两个误解纠正（RWO 不是单 Pod、快照不是备份），存储层的事故就少掉八成。本篇在这条路径上负责把数据放对地方；数据落定之后，下一步是让集群外的流量能准确走到这些 Pod 上。

✅
最容易踩的坑
  • 删命名空间顺手删了数据盘：StorageClass 默认 Delete，PVC 级联删除，云盘同步销毁，无回收站。
  • PV 是 Retain，新 PVC 却一直 Pending：PV 卡在 Released，必须先清掉 spec.claimRef 才能重新 Available。
  • 给云块存储写 ReadWriteMany：PVC 要么 Pending，要么绑上后第二个节点挂载失败，错误信息藏在 CSI node 插件日志里。
  • 以为 RWO 提供互斥：同节点双 Pod 同写把数据写坏，排查时完全看不出 K8s 层异常。
  • 挂载 ext4 云盘到数据库数据目录不加 subPath：目录里的 lost+found 让 MySQL 初始化判定「目录非空」直接退出。
  • medium: Memory 的 emptyDir 把 Pod 打成 OOMKilled：tmpfs 占用计入容器内存，写 2Gi 缓存却只给了 1Gi limit。
  • 改 StatefulSet 的 volumeClaimTemplates 容量：字段不可变，apply 直接报错；必须逐个 patch PVC。
  • 缩容 StatefulSet 以为盘会回收：PVC 全留着继续计费，半年后才在账单里看到。
  • 扩容后容量没变：卡在 FileSystemResizePending，需要重建 Pod 才会扩文件系统。
  • Deployment 挂 PVC 还用默认滚动更新：新旧 Pod 同时持卷，落到两台机器时新 Pod 永远挂不上，必须改成 Recreate。
  • local PV 不配节点亲和：Pod 被调度到别的节点，卷永远挂不上；节点故障后数据不可达且没有应用层副本兜底。
  • NFS 上跑数据库：文件锁与 fsync 语义不完整，表现为偶发数据损坏或启动时锁等待超时。
  • 备份从没恢复过：真出事时才发现快照跨不了集群、逻辑备份缺 binlog、恢复时间远超业务容忍度。
