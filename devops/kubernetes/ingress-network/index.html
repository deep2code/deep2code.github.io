Ingress 与网络策略

🏷️ Kubernetes,云原生

四层 Service 与七层 Ingress 的分工

前面讲的 Service（ClusterIP/NodePort/LoadBalancer）工作在 OSI 第四层（TCP/UDP）：它只做端口转发，不理解 HTTP。

Ingress 就是为此而生的七层路由规则：它本身只是一段 YAML（声明 host/path → service 的映射），真正干活的是 Ingress Controller（nginx-ingress、traefik、apisix 等）。Controller 监听 Ingress 对象变化，动态生成 Nginx/Tengine 配置并 reload。常见 Controller 选型：

Controller特点适合场景
ingress-nginx官方，生态最成熟大多数团队的默认选择
traefik自动 HTTPS，配置简单中小团队、快速上手
apisix国产，性能高，插件丰富API 网关、微服务治理
CiliumeBPF，L7 语义追求性能和可观测性

nginx-ingress Pod] IC -->|host api.example.com| S1[Service api] IC -->|host admin.example.com| S2[Service admin] IC -->|path /static/*| S3[Service static] S1 --> P1[api Pod] S2 --> P2[admin Pod] S3 --> P3[static Pod]

实战：安装 Ingress-Nginx 与路由规则

先安装 Ingress Controller（以官方 ingress-nginx 为例），它会创建一个 LoadBalancer 类型的 Service 作为集群入口：

# 安装 ingress-nginx Controller（含默认 Backend、配置 ConfigMap）
kubectl apply -f https://raw.githubusercontent.com/kubernetes/ingress-nginx/controller-v1.10.0/deploy/static/provider/cloud/deploy.yaml

# 确认 Controller Pod 与入口 Service
kubectl get pods -n ingress-nginx
kubectl get svc -n ingress-nginx ingress-nginx-controller
# 记下 EXTERNAL-IP，后续 DNS 解析到这里

然后定义 Ingress 路由规则，把两个域名分别路由到后端 Service：

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web-ingress
  annotations:
    nginx.ingress.kubernetes.io/ssl-redirect: "true"
    nginx.ingress.kubernetes.io/proxy-body-size: "10m"
    nginx.ingress.kubernetes.io/rewrite-target: /
spec:
  ingressClassName: nginx
  tls:
    - hosts:
        - api.example.com
        - admin.example.com
      secretName: example-tls
  rules:
    - host: api.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: api-svc
                port: {number: 8080}
    - host: admin.example.com
      http:
        paths:
          - path: /dashboard
            pathType: Prefix
            backend:
              service:
                name: admin-svc
                port: {number: 80}

NetworkPolicy：东西向流量隔离

Ingress 解决南北向（外部进来），NetworkPolicy 解决东西向（Pod 之间互相访问）。默认 K8s 集群里所有 Pod 都能互通，这在多租户环境是安全隐患。NetworkPolicy 用标签选择器定义"谁能访问我"。

# 只允许带 app=frontend 的 Pod 访问 app=db 的 Pod 的 5432 端口
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: db-policy
  namespace: prod
spec:
  podSelector:
    matchLabels: {app: db}      # 作用于哪些 Pod
  policyTypes: [Ingress]
  ingress:
    - from:
        - podSelector:
            matchLabels: {app: frontend}
      ports:
        - protocol: TCP
          port: 5432
---
# 默认拒绝命名空间所有入站流量（白名单模式）
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
  namespace: prod
spec:
  podSelector: {}
  policyTypes: [Ingress]

注意：NetworkPolicy 不是 K8s 内核强制的，必须 CNI 插件支持（Calico、Cilium 支持，Flannel 默认不支持）。用 Flannel 的集群写了 NetworkPolicy 也不会生效。

我踩过的坑：Flannel 上写 NetworkPolicy 不生效

早期用 Flannel 搭了个测试集群，写了 default-deny 策略，结果 Pod 之间照样能互通，排查了半天才知道 Flannel 根本不实现 NetworkPolicy 语义。后来生产全换 Cilium——不仅策略生效，还能通过 Hubble 看到每条流量的 L7 记录。写 NetworkPolicy 之前先确认你的 CNI 支持，否则等于白写。

最佳实践

  • 生产用 Cilium 替代 iptables：基于 eBPF，NetworkPolicy 语义更全（L7 规则）、性能更好、可观测性更强。
  • TLS 证书用 cert-manager 自动签发续期：cert-manager + Let's Encrypt，配 cert-manager.io/cluster-issuer 注解，证书自动续期，不要手工管。
  • Ingress 与 Service 解耦：路由规则集中在 Ingress YAML，后端只管 Service，便于统一治理限流/认证/重写。
  • 设置合理的超时与 body 大小：默认 nginx 60s 超时、1m body，上传大文件/长轮询业务必须调。
  • 默认拒绝 + 白名单：在生产命名空间先打一个 default-deny-ingress，再逐个服务放行，遵循最小权限。
  • 灰度发布用 Ingress 注解：nginx-ingress 支持按 header/cookie 权重分流，可做金丝雀发布。

常见问题 FAQ

Q1：Ingress 创建了但访问返回 503？

503 = no available upstream，即 Ingress Controller 找不到后端 Ready 的 Pod。检查：(a) 后端 Service 的 label selector 是否选中了任何 Pod（kubectl get endpoints）；(b) 后端 Pod 的 readinessProbe 是否通过；(c) Service port 与 Ingress backend port 是否一致。

Q2：域名解析正常，但 curl 一直超时？

先分清是 Ingress 层还是网络层：curl -v http://<node-ip>:<nodeport> 直接打 Controller。通了说明是 DNS/云 LB 问题；不通说明 Controller Pod 本身有问题（看日志 kubectl logs -n ingress-nginx）。

Q3：NetworkPolicy 写了但 Pod 之间还能互通？

你的 CNI 不支持 NetworkPolicy。Flannel 不支持，换 Calico/Cilium。另外 NetworkPolicy 是"放行规则"，必须先有 default-deny 或明确策略才会生效，没有任何规则时默认全通。

Q4：一个 Ingress 能配多个域名吗？

能，一个 Ingress 的 rules 数组里可以写多个 host，TLS 段也可以配多个 secretName（或用通配符证书）。实践中常按"一个团队/业务域一个 Ingress"来组织。

总结

Ingress 把七层 HTTP 路由从应用代码里抽出来，交给声明式配置；NetworkPolicy 把东西向流量从"默认全通"收紧到"白名单"。两者配合，集群才有真正的入口治理与安全边界。下一篇我们解决"一堆 YAML 怎么管理"——Helm。
