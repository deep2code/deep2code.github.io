Kubernetes Pod 网络模型、Ingress 与网络策略

🏷️ Kubernetes,云原生

网络模型的三条硬要求

Kubernetes 对网络的规定短得惊人，只有三条：

  1. 每个 Pod 有自己独立的 IP，Pod 内所有容器共享这个网络命名空间；
  2. 任意两个 Pod 之间可以用这个 IP 直接互通，中间不做 NAT——即 A 看到的源地址就是 B 的真实 Pod IP；
  3. 节点上的进程（含 kubelet、DaemonSet）能直接访问本节点与其他节点的 Pod。

注意：Kubernetes 自己一行代码都不实现这三条。它只定义 CNI 接口，分 IP、建虚拟设备、跨节点转发全部由插件完成。这解释了两个现象：kubeadm init 之后节点一直 NotReady（kubelet 在等 CNI 就绪），以及换 CNI 的代价为什么接近重建集群。

Service 的虚拟 IP 机制、kube-proxy 的 iptables 与 IPVS 实现对照、Service 四种类型的差异，主干篇 Kubernetes 架构与核心机制 已经写透，这里不重复。本篇只讲它下面那一层——包是怎么从一个 Pod 真正走到另一个节点的 Pod 的。

CNI 的两大流派：封装还是路由

抛开插件名字，实现只有两条路：把 Pod 的包再套一层外层头发给对端节点（Overlay），或者让底层网络知道每个 Pod 网段在哪台机器上（路由）。

维度Overlay 封装（VXLAN / IPIP / Geneve）路由模式（BGP / 云 VPC 路由）云 VPC 原生（弹性网卡辅助 IP）
数据平面Pod 包被封进外层 UDP 或 IP 包，节点间点对点隧道Pod 网段作为路由条目注入底层网络，包裸奔Pod 直接使用 VPC 内的真实 IP
性能吞吐损耗约 10% 到 20%，小包场景 CPU 开销明显接近裸机最好，且可用安全组
对底层网络要求几乎没有，只要节点间三层可达需要能注入路由：同二层、BGP 邻居或可写 VPC 路由表绑定特定云厂商
MTU必须调小，配错就是隐蔽故障与底层一致，无需调整与 VPC 一致
可观测性抓包看到的是外层隧道，需要解封装才能看清抓包即真实 Pod IP，最直观直观，且能用云侧流日志
每节点 Pod 数限制受节点 CIDR 掩码限制同左受网卡规格限制，小规格机器只能跑十几个 Pod
NetworkPolicyFlannel 默认不支持；Calico 的 VXLAN 模式支持Calico 支持且策略能力强取决于厂商插件，通常支持
代表插件Flannel、Calico 的封装模式、Cilium 的隧道模式Calico BGP、Cilium Native RoutingAWS VPC CNI、阿里云 Terway、GKE 原生

选型的判断很简单：能注入路由就别用封装。跨机房、跨 VPC、底层网络不受你控制时才被迫上 Overlay。混合场景可以用 Calico 的 CrossSubnet 模式——同子网走路由，跨子网才封装。

⚠️
MTU 配错：小包全通、大包全挂

Overlay 封装要吃掉有效载荷：VXLAN 占 50 字节、IPIP 占 20 字节、再叠 WireGuard 还要更多。若物理链路 MTU 是 1500 而 Pod 网卡仍是 1500，封装后超限，需要分片或依赖「需要分片」的 ICMP 做路径 MTU 发现，而云环境和防火墙经常把这类 ICMP 丢掉。结果是：ping 通、TCP 握手通、小接口正常，一旦返回大 JSON、上传文件、或 TLS 证书链偏大，连接就永久挂住不返回。

对照关系：物理 1500 时，VXLAN 下 Pod MTU 取 1450、IPIP 下取 1480、VXLAN 叠 WireGuard 取 1370 左右；若底层支持巨帧 9000，则相应放大。定位命令是禁止分片的定长 ping 做二分：ping -M do -s 1422 对端PodIP（1422 加 28 字节头等于 1450），能通说明 1450 以内没问题，换成 1472 不通就确认是 MTU 问题。

Cilium 与 eBPF 为什么成了趋势

传统数据平面把规则写进 iptables，Service 与策略数量一多，规则链呈线性增长，变更时要整表替换，节点上几万条规则的集群会出现 kube-proxy 同步延迟数十秒的现象。eBPF 的做法是把转发与策略逻辑作为程序挂在内核钩子上，用哈希表查目标，查找复杂度与 Service 数量基本无关。

能力iptables 系数据平面eBPF（Cilium）
规则规模扩展性规则数随 Service 与 Endpoint 线性增长，更新要整表替换哈希表查找，规模无关，增量更新
策略粒度三层与四层，即 IP 与端口在此之上支持七层：HTTP 方法与路径、gRPC 方法、Kafka topic
身份模型基于 IP 与 ipset基于标签派生的安全身份，Pod 换 IP 策略不失效
可观测性只能靠计数器与抓包Hubble 可直接看到「谁访问谁、被谁拒绝」的流级记录
额外能力无可替换 kube-proxy、透明加密、集群网格、带宽管理
代价成熟、人人会看要求较新内核，排障需要新工具链，团队学习成本真实存在

务实的结论：新集群且团队愿意学，直接上 Cilium 收益最大（尤其是需要七层策略与流量可观测性的场景）；已有集群跑着 Calico 且没有具体痛点，不必为了架构时髦做一次高风险替换。iptables 与 IPVS 两种 kube-proxy 模式的具体差异见主干篇。

apiVersion: v1
kind: Pod
metadata:
  name: crawler
spec:
  dnsPolicy: ClusterFirst      # 仍走 CoreDNS，保留集群内服务发现能力
  dnsConfig:
    options:
      - name: ndots
        value: "2"             # 关键：把 5 调到 2，两个点以上直接按绝对域名查
      - name: single-request-reopen
        value: ""              # 缓解 A 与 AAAA 并发查询在某些内核上的丢包问题
      - name: timeout
        value: "2"             # 默认 5 秒太长，一次丢包就是 5 秒毛刺
      - name: attempts
        value: "3"
    searches:                  # 裁剪 search 列表，只留真正需要的
      - default.svc.cluster.local
      - svc.cluster.local
  containers:
    - name: app
      image: my-crawler:1.0
---

Ingress 的本质与 Gateway API

必须先说清楚：Ingress 对象本身什么也不做，它是一份声明式的路由规则表，真正干活的是 Ingress Controller——一个跑在集群里的 Pod（或云侧 LB），它 watch Ingress 对象，把规则翻译成自己的配置。所以「Ingress 创建成功但访问不通」的第一反应应该是「有没有控制器、ingressClassName 是否匹配」，而不是检查 YAML 语法。

Ingress 的标准字段只覆盖 host 与 path。其余一切能力都靠注解：重写、限流、超时、灰度、认证、CORS、body 大小。而注解是各控制器私有的，ingress-nginx 的注解在 Traefik 上完全无效。这就是 Ingress 可移植性差的根因，也是 Gateway API 诞生的理由。

维度IngressGateway API
表达能力仅 host 与 path，其余靠注解标准字段涵盖请求头、query、method 匹配，按权重分流、请求镜像、超时、重定向与重写
角色分离无，一份 YAML 混了基础设施与业务路由，RBAC 难切GatewayClass、Gateway、Route 三层，各自独立 RBAC
跨命名空间难以安全地把域名授权给别的命名空间ReferenceGrant 显式授权，支持多团队共享同一 Gateway
协议支持以 HTTP 与 HTTPS 为主，TCP 与 UDP 靠控制器扩展HTTPRoute、GRPCRoute、TLSRoute、TCPRoute、UDPRoute 都是标准资源
可移植性差，换控制器等于重写路由好，核心字段跨实现一致；实验字段仍有差异
成熟度GA 已久，生态与文档最全核心资源已 GA，各控制器实现程度不一，部分高级能力仍是实验特性
建议存量继续用，别再往注解里堆逻辑新业务优先；先迁注解最多、最容易被锁死的那些路由
 
# Gateway API：平台团队只管 Gateway，业务团队只管 HTTPRoute
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: shared-gw
  namespace: infra
spec:
  gatewayClassName: cilium            # 或 istio nginx-gateway-fabric 等实现
  listeners:
    - name: https
      protocol: HTTPS
      port: 443
      tls:
        mode: Terminate
        certificateRefs:
          - name: wildcard-tls        # 证书由平台团队统一管理
      allowedRoutes:
        namespaces:
          from: Selector              # 只允许带指定标签的命名空间挂载路由
          selector:
            matchLabels: {gateway-access: "true"}
---
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: api-route
  namespace: team-a
spec:
  parentRefs:
    - name: shared-gw
      namespace: infra
  hostnames: ["api.example.com"]
  rules:
    # 规则 1：按请求头灰度，这在 Ingress 里只能靠私有注解
    - matches:
        - path: {type: PathPrefix, value: /v1}
          headers:
            - name: x-canary
              value: "true"
      backendRefs:
        - name: api-canary
          port: 8080
    # 规则 2：按权重分流加标准超时字段
    - matches:
        - path: {type: PathPrefix, value: /v1}
      timeouts:
        request: 10s
        backendRequest: 8s
      backendRefs:
        - name: api-stable

        - name: api-canary

NetworkPolicy：默认全通，不写等于没有边界

NetworkPolicy 的语义有四条必须记牢，每一条都对应一类「配了却没用」的事故：

语义准确含义配错的后果
默认全通没有任何策略时，集群内所有 Pod 互通，也能出公网以为「没配就是禁止」，实际零隔离
只对被选中的 Pod 生效一个 Pod 只要被至少一条策略的 podSelector 命中，就进入白名单模式；没被命中的 Pod 仍然全通只给数据库配了策略，其他 Pod 之间照旧全通，横向移动路径还在
多条策略取并集策略是白名单叠加，不存在「拒绝」规则；新加严格策略不会收紧已有的宽松策略以为新策略会覆盖旧策略，结果放通面只增不减
需要 CNI 实现策略对象由 apiserver 存储，但下发到数据平面靠 CNI。默认配置的 Flannel 不实现，配了完全无效且无任何报错静默失效，安全审计能通过而实际零防护
 
# 第一步：命名空间级默认拒绝（入站加出站），这是一切的前提
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-all
  namespace: prod
spec:
  podSelector: {}                 # 空选择器等于命名空间内所有 Pod
  policyTypes: [Ingress, Egress]  # 只写 Ingress 的话出站仍然全通
---
# 第二步：必须先放通 DNS，否则所有域名解析全断（最高频的自伤）
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-dns-egress
  namespace: prod
spec:
  podSelector: {}
  policyTypes: [Egress]
  egress:
    - to:
        - namespaceSelector:
            matchLabels: {kubernetes.io/metadata.name: kube-system}
          podSelector:
            matchLabels: {k8s-app: kube-dns}
      ports:
        - {protocol: UDP, port: 53}
        - {protocol: TCP, port: 53}
---
# 第三步：按需放通业务链路。注意 from 下面两个选择器的写法差异
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: db-allow-from-api
  namespace: prod
spec:
  podSelector:
    matchLabels: {app: postgres}
  policyTypes: [Ingress]
  ingress:
    - from:
        # 同一个列表项内的两个选择器是「与」：prod 命名空间里且带 app=api 标签
        - namespaceSelector:
            matchLabels: {kubernetes.io/metadata.name: prod}
          podSelector:
            matchLabels: {app: api}
        # 另起一个列表项是「或」：再放通监控命名空间的采集器
        - namespaceSelector:
            matchLabels: {kubernetes.io/metadata.name: monitoring}
      ports:
        - {protocol: TCP, port: 5432}
---
# 出站放通到集群外部时只能用 ipBlock，不能写域名（域名策略是 Cilium 等的扩展能力）
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: api-egress-allowlist
  namespace: prod
spec:
  podSelector:
    matchLabels: {app: api}
  policyTypes: [Egress]
  egress:
    - to:
        - ipBlock:
            cidr: 0.0.0.0/0
            except:
              - 169.254.0.0/16      # 屏蔽云元数据服务，防 SSRF 偷凭证
              - 10.0.0.0/8          # 屏蔽内网横向
      ports:
        - {protocol: TCP, port: 443}

东西向与南北向的加密

只讲要点：NetworkPolicy 管的是「谁能连谁」，不管「链路上的数据有没有被看到」。要做传输加密有三条路——CNI 层透明加密（Cilium 或 Calico 的 WireGuard，对应用零侵入，但只加密节点间流量）、服务网格 mTLS（sidecar 或 ambient 模式，附带身份、细粒度授权与可观测性，代价是延迟与运维复杂度）、应用自己做 TLS（控制力最强、改造量最大）。南北向的 TLS 终止位置与证书自动化（cert-manager）属于网关职责，网关选型与容量规划见 API 网关选型与流量治理，TLS 握手与证书信任链见 认证授权与加密基础。

网络问题的分层排查路径

网络排障最忌讳「随机试」。固定按层级往外走，每一层只回答一个问题：

层级验证命令输出怎么判读
Pod 内kubectl exec POD -- ss -lntp只看到 127.0.0.1:8080 说明应用绑了回环，外部永远连不上，要改成 0.0.0.0
同节点用 netshoot Pod 执行 nc -zv 目标PodIP 端口不通且目标进程在监听，说明是本节点 CNI 或策略问题；先 kubectl get netpol -A
跨节点ping -M do -s 1422 目标PodIP 与 ip r get 目标PodIP小包通大包不通就是 MTU；路由查不到下一跳说明 CNI 未同步该节点网段；均正常则查安全组
Servicekubectl get endpointslice -l kubernetes.io/service-name=SVC为空说明 selector 与 Pod 标签不匹配或 Pod 未 Ready；非空仍不通再查 kube-proxy
DNSnslookup svc.ns.svc.cluster.local 与 CoreDNS 日志解析慢看 ndots 放大与 max_concurrent 是否打满；间歇失败看 CoreDNS 副本数与 CPU 限流
Ingresskubectl describe ing NAME 与控制器日志Address 为空说明没有控制器接管或 class 不匹配；503 是后端无 Ready 端点；504 是后端超时
外部直连 NodePort 或控制器 Pod IP直连通而域名不通是 DNS 或云 LB 健康检查问题；都不通说明控制器本身异常

反模式对照

反模式会怎么出事正确做法
不配 NetworkPolicy任一 Pod 被拿下即可横向扫描全集群，还能直连云元数据服务偷凭证每个生产命名空间先下默认拒绝，再按链路放通
配了策略但 CNI 不支持静默失效，审计通过而实际零防护，是最危险的一类上线前用两个不同标签的 probe Pod 实测通与不通
默认拒绝忘了放通 DNS全命名空间域名解析失败，表现为所有服务同时报连接超时默认拒绝与放通 DNS 的策略成对提交
MTU 不匹配小包正常大包卡死，最难定位的一类故障按封装类型设定 Pod MTU，变更隧道模式时同步调整并做定长 ping 验证
Ingress 注解越堆越多路由逻辑锁死在某控制器，换控制器等于重写新业务上 Gateway API，把限流与认证下沉到网关或网格的标准能力
CoreDNS 不做容量规划副本不足或被 CPU 限流，表现为全站随机 5 秒毛刺配 requests 与 limits、按 QPS 扩副本、上 NodeLocal DNSCache、缓存 NXDOMAIN
容器里写死 Pod IP 或节点 IPPod 重建 IP 就变，故障后配置全废一律用 Service 名，跨集群用统一域名
依赖源 IP 做鉴权经过 Service 或 LB 后源地址可能被改写，鉴权时通时不通用 mTLS 身份或应用层令牌；需要真实源 IP 时配 externalTrafficPolicy: Local 并接受其取舍
把 Overlay 当默认答案白付 10% 到 20% 的吞吐损耗，还引入 MTU 与抓包困难同 VPC 或同二层优先路由模式，必要时用 CrossSubnet 混合
❌
最容易踩的坑

1. 写完 NetworkPolicy 没验证就当完成：Flannel 上完全无效，而 kubectl get netpol 显示一切正常。
2. 默认拒绝出站后忘放 DNS 的 53 端口：所有服务同时「挂掉」，看起来像集群故障，其实是自己把解析断了。
3. 以为新策略能覆盖旧策略：策略只做并集，越加越松；要收紧必须删掉旧的宽松策略。
4. from 列表里把 namespaceSelector 与 podSelector 的「与、或」关系搞反：同一列表项内是与，另起一项是或，写错就是放通范围扩大一整个命名空间。
5. MTU 没跟着隧道类型改：上线后小接口全好，一个返回大列表的接口永久挂起。
6. 切换 Calico 的 IPIP 与 VXLAN 模式没同步 MTU 与安全组：VXLAN 走 UDP 4789、IPIP 走 IP 协议号 4，安全组没放通就是跨节点全断。
7. 外部域名不写绝对域名：ndots 为 5 时每次解析多打四五个无效查询，QPS 一高 CoreDNS 直接成瓶颈。
8. CoreDNS 只给 2 个副本又不设 requests：节点一忙就被 CPU 限流，业务侧表现为随机 5 秒超时，非常难和业务问题区分。
9. Ingress 没写 ingressClassName：多控制器共存时没人接管，地址一直为空，或被两个控制器同时接管导致行为诡异。
10. Ingress 返回 503 时去查证书和 DNS：503 基本都是后端没有 Ready 端点，先看 EndpointSlice 再看探针。
11. 没屏蔽 169.254.169.254 的出站：一个 SSRF 就能读到节点角色凭证，这是云上最常见的提权路径。
12. 把 Pod IP 写进配置或白名单：重启即失效；跨集群访问更要用域名与网关而不是 IP 列表。

小结

集群网络的层次很清晰：CNI 保证三条硬要求成立（每 Pod 一个 IP、Pod 间不 NAT 互通、节点可达 Pod），Service 与 kube-proxy 在它上面做虚拟 IP 与负载均衡（详见 Kubernetes 架构与核心机制），DNS 让这些虚拟 IP 变成可读的名字，Ingress 或 Gateway 负责南北向入口，NetworkPolicy 负责东西向边界。落地时最该先做的三件事：确认 CNI 支不支持策略并下默认拒绝、把 MTU 与 ndots 这两个默认值核对一遍、给 CoreDNS 做容量规划。这三件事覆盖了我见过的大部分集群网络事故。
