K8s 深度原理：控制循环、调度、探针与 Service 实现

🏷️ K8s

K8s 的概念多到让人放弃，但它只有一个核心思想：你描述期望状态，一堆控制器不停地把现实拉向它。把这条主线抓住，Pod、Service、探针、QoS、滚动更新全都是它的推论。这篇按「控制循环 → 一次 apply 的完整链路 → 调度 → 生命周期与探针 → 资源与 QoS → Service 的真实实现 → 滚动更新与排障」展开。

核心原理一：控制循环——为什么删掉的 Pod 会自己回来

每个控制器都在跑同一个死循环：读期望状态 → 读实际状态 → 算差异 → 采取行动。这就是为什么 kubectl delete pod 之后 Pod 又出现了：你删的是实际状态，期望状态（Deployment 的 replicas=3）没变，ReplicaSet 控制器发现少了一个，立刻补一个。

设计选择 含义 带来的实际好处
声明式而非命令式 你说「要 3 个副本」，不说「创建一个副本」 操作天然幂等，重复 apply 同一份 YAML 结果一致
水平触发（level-triggered） 控制器看的是当前完整状态，不是「发生了什么事件」 即使丢了事件、组件重启、网络中断，下一轮循环照样收敛。这是 K8s 自愈能力的根
List-Watch + 本地缓存 Informer 先全量 List，再 Watch 增量，本地 Indexer 缓存对象 控制器读对象不打 apiserver，万级对象规模下仍然轻量
乐观并发（resourceVersion） 更新时带上版本号，版本不匹配则返回 409 冲突 多个控制器并发改同一对象不会互相覆盖
Finalizer 删除时先置 deletionTimestamp，等 finalizer 清空才真正删 保证外部资源（云盘、负载均衡器）被清理。这也是「namespace 卡在 Terminating」的唯一原因
💡
理解这一层就能解释一堆现象

「手动改了 Deployment 创建出来的 Pod，重启后改动没了」——因为期望状态在 Deployment 里，Pod 只是实际状态的载体。
「namespace 删不掉，一直 Terminating」——某个资源的 finalizer 没被清理，去 kubectl get ns xxx -o yaml 看 finalizers 字段。
「apiserver 短暂不可用，集群却没崩」——水平触发让所有控制器在恢复后自动补齐，不依赖事件不丢。

核心原理三：调度器的两阶段决策

调度器的工作可以精确概括为一句话：给 Pod 的 spec.nodeName 填一个值。填值的过程分两阶段：先把不能用的节点排除（Filter），再给剩下的打分排序（Score）。

flowchart TB POD["待调度 Pod"] --> ALL["全部节点：node-1..node-100"] ALL --> F["Filter 阶段（硬性条件，不满足直接排除）"] F --> F1["节点资源够不够
按 requests 算，不是按实际用量"] F --> F2["nodeSelector / nodeAffinity 匹配吗"] F --> F3["污点 Taint 是否被容忍"] F --> F4["端口冲突 / 卷能否挂载"] F --> F5["podAntiAffinity 冲突吗"] F1 & F2 & F3 & F4 & F5 --> FEAS["可行节点：node-7, node-23, node-58"] FEAS --> S["Score 阶段（软性偏好，打分 0~100）"] S --> S1["资源均衡
LeastAllocated / BalancedAllocation"] S --> S2["镜像本地已存在则加分"] S --> S3["拓扑分布 topologySpreadConstraints"] S --> S4["亲和性权重 preferredDuringScheduling"] S1 & S2 & S3 & S4 --> WIN["总分最高：node-23"] WIN --> BIND["Bind：写入 spec.nodeName"]
调度控制手段 硬性还是软性 用来表达什么 注意
nodeSelector 硬性 「必须跑在打了某标签的节点上」 语法简单但只能等值匹配，新代码建议用 nodeAffinity
nodeAffinity required 硬性 支持 In/NotIn/Exists 等操作符 不满足则 Pending
nodeAffinity preferred 软性 「尽量放在 SSD 节点」 满足不了也能调度成功，只是分低
podAntiAffinity 可硬可软 「同一应用的副本不要挤在一个节点/机架」 硬性反亲和 + 副本数 > 节点数 = 永久 Pending
topologySpreadConstraints 可硬可软 「跨可用区均匀分布，倾斜不超过 1」 比反亲和更精确，能表达「均匀」而不只是「不同」
Taint + Toleration 硬性（反向） 节点主动排斥：「除非你明确容忍，否则别来」 用于专用节点池、GPU 节点、故障隔离
priorityClassName — 资源不足时，高优先级 Pod 可抢占低优先级 Pod 抢占会真的驱逐别人，生产上要谨慎划分等级
⚠️
调度看的是 requests，不是实际用量

节点「资源够不够」判断的是已分配 requests 之和与 Allocatable 的关系，和节点当前真实使用率毫无关系。所以会出现两种反直觉现象：

① 节点 CPU 实际只用了 10%，却调度不进新 Pod——因为已有 Pod 的 requests 总和已经占满。
② 节点 CPU 实际跑到 95%，新 Pod 照样被调度进来——因为大家 requests 都填得很小。第二种情况会直接导致所有 Pod 一起变慢。

所以 requests 必须填真实的日常水位，它是调度和容量规划的唯一依据；Allocatable = Capacity − kube-reserved − system-reserved − eviction-threshold，永远小于机器标称配置。

核心原理四：生命周期、三种探针与优雅退出

stateDiagram-v2 [*] --> Pending: 对象已创建 Pending --> Pending: 等待调度 / 拉镜像 Pending --> Running: 所有容器已启动 Pending --> Failed: 镜像拉不到且不再重试 Running --> Running: startupProbe 通过后
liveness 与 readiness 开始工作 Running --> Succeeded: Job 类任务正常退出 Running --> Failed: 容器非零退出且 restartPolicy=Never Running --> Terminating: 收到删除请求 Terminating --> [*]: 并行做两件事
① 从 EndpointSlice 摘除
② preStop → SIGTERM → 宽限期 → SIGKILL note right of Running liveness 失败 = 重启这个容器 readiness 失败 = 摘流量 但不重启 startup 失败 = 按启动失败处理 end note
探针 失败后的动作 该检查什么 绝对不能检查什么
livenessProbe 重启容器 只检查进程自身是否死锁/假死，比如一个极简的 /healthz 直接返回 200 绝不能检查数据库、Redis、下游服务。下游一挂，全部副本被判定不健康并同时重启，把局部故障放大成全面雪崩
readinessProbe 从 Service 后端摘除，不重启 可以检查关键依赖是否就绪（这里检查下游是合理的——摘流量而不是重启） 别把它和 liveness 配成同一个接口
startupProbe 按启动失败处理 专门给启动慢的应用（JVM、大模型加载）留足时间 有了它就不该再用 initialDelaySeconds 硬等 
spec:
  terminationGracePeriodSeconds: 45   # 必须 > preStop + 应用真实排水时间
  containers:
    - name: app
      # 启动慢的应用用 startupProbe 兜住，最多容忍 30×10=300 秒
      startupProbe:
        httpGet: { path: /healthz, port: 8080 }
        periodSeconds: 10
        failureThreshold: 30
      # liveness 只看自己，不碰任何外部依赖
      livenessProbe:
        httpGet: { path: /healthz, port: 8080 }
        periodSeconds: 10
        timeoutSeconds: 3
        failureThreshold: 3
      # readiness 可以包含依赖检查，失败只摘流量
      readinessProbe:
        httpGet: { path: /ready, port: 8080 }
        periodSeconds: 5
        failureThreshold: 2
      lifecycle:
        preStop:
          exec:
            # 关键：等 kube-proxy / Ingress 的转发规则真正把自己摘掉
            command: ["sh", "-c", "sleep 5"]
❌
滚动更新期间出现 502 的真正原因

Pod 被删除时，「从 EndpointSlice 摘除」和「给容器发 SIGTERM」是并行且无先后保证的两条路径。摘除还要经过 EndpointSlice 控制器 → kube-proxy → 每个节点的 iptables/IPVS 规则更新，这中间有几百毫秒到数秒的传播延迟。如果容器已经退出但规则还没更新完，流量仍会被转发到死掉的 Pod —— 于是客户端收到 502。

解法就是上面那个 preStop: sleep 5：它让容器在收到 SIGTERM 前先「装死」几秒，把时间差让给规则传播。这是零改造成本的一招，几乎所有对外服务都该加。另外要确保 terminationGracePeriodSeconds 大于 preStop 时间加上应用处理完存量请求的时间，否则会被 SIGKILL 直接砍断。

核心原理五：QoS 与 CPU 限流的隐形代价

requests 和 limits 的组合决定了 Pod 的 QoS 等级，而 QoS 等级决定了节点资源紧张时谁先被驱逐。

QoS 等级 条件 驱逐顺序 适用
Guaranteed 每个容器的 cpu 和 memory 都设了，且 requests == limits 最后被驱逐 核心服务、有状态组件
Burstable 至少设了一个 requests，但不满足 Guaranteed 其次 绝大多数业务应用
BestEffort 什么都没设 最先被驱逐 ❌ 生产环境不该出现
资源 超出 limits 的行为 可压缩吗 症状
CPU 被限流（throttle），不会被杀 可压缩 P99 延迟出现规律性毛刺，但 CPU 使用率看着不高
Memory 直接 OOMKilled（退出码 137） 不可压缩 容器突然重启，describe 里 Last State 显示 OOMKilled
临时存储 Pod 被驱逐（Evicted） 不可压缩 日志写满 emptyDir 导致 Pod 消失
⚠️
CPU limit 的 CFS quota 陷阱

limits.cpu: "1" 在内核层面被翻译成 CFS quota：每 100ms 周期内最多用 100ms CPU 时间。问题在于用完就立刻停到下个周期——哪怕整台机器空闲。对于多线程应用，4 个线程同时跑 30ms 就耗尽了额度，剩下 70ms 全在挨饿，表现为周期性的延迟毛刺，而监控上的平均 CPU 使用率可能只有 40%，看起来完全正常。

# 确认是否在被限流：throttled 次数持续增长就是
kubectl exec -it POD -- cat /sys/fs/cgroup/cpu.stat
# nr_throttled 与 throttled_usec 在涨 → 就是 CPU limit 打的

# Prometheus 里对应的指标
# rate(container_cpu_cfs_throttled_periods_total[5m])
#   / rate(container_cpu_cfs_periods_total[5m]) > 0.1 说明问题严重

对延迟敏感的服务，常见做法是只设 requests 不设 cpu limits（靠 requests 保证下限，允许突发占用空闲 CPU），或者把 limit 设到远高于日常水位。内存则相反：limits 必须设，否则一个内存泄漏的 Pod 能把整个节点拖垮。

核心原理六：Service 的 ClusterIP 其实不存在

核心原理七：滚动更新与可用性保障

滚动更新的本质是「新建一个 ReplicaSet，然后一边给它加副本一边给老的减副本」。两个参数控制这个节奏：

参数 含义 设成 0 会怎样
maxSurge（默认 25%） 允许临时超出期望副本数多少 设 0 则必须先停旧的才能起新的，更新期间容量必然下降
maxUnavailable（默认 25%） 允许同时有多少副本不可用 设 0 则必须新 Pod Ready 后才停旧的，容量不下降，最安全
minReadySeconds 新 Pod Ready 后还要稳定多久才算成功 设 0 时，一个「刚 Ready 就崩」的版本会被快速铺满全集群
progressDeadlineSeconds 多久没进展就标记更新失败 默认 600 秒，失败后不会自动回滚，需要手动 rollout undo

零容量损失的组合是 maxUnavailable: 0 + maxSurge: 1（或百分比），代价是更新变慢且需要额外资源余量。另外要区分两类中断：

中断类型 例子 PodDisruptionBudget 管得了吗
自愿中断 kubectl drain、集群升级、节点缩容、HPA 缩容 ✅ PDB 的 minAvailable 会阻止过度驱逐
非自愿中断 节点宕机、内核 panic、OOM、网络分区 ❌ 管不了。PDB 不是高可用方案，跨可用区 + 多副本才是

# 第一站永远是 describe 的 Events 段，90% 的问题在这里有答案

❌
避坑清单
  • livenessProbe 里检查了数据库或下游服务：下游抖一下，全部副本同时被重启，局部故障被放大成全面雪崩。liveness 只能检查进程自己，依赖检查放 readiness。
  • 没配 preStop：摘流量和杀进程是并行的，滚动更新必然出现一小波 502。加一个 sleep 5 就能解决，零成本。
  • 给延迟敏感服务设了紧的 limits.cpu：CFS quota 会在额度用尽时硬停到下个周期，造成周期性延迟毛刺，而平均 CPU 使用率看着很正常。查 cpu.stat 的 nr_throttled。
  • 不设 limits.memory：内存不可压缩，一个泄漏的 Pod 能把整台节点拖到 OOM，连累同节点所有服务。
  • requests 随手填个很小的值：调度只看 requests，填小了会让节点被严重超卖，所有 Pod 一起变慢。它必须反映真实日常水位。
  • 以为 PDB 能防节点宕机：PDB 只约束自愿驱逐。抗节点故障靠多副本 + 跨可用区拓扑分布。
  • 硬性 podAntiAffinity + 副本数大于节点数：多出来的副本永久 Pending。要么改成 preferred，要么用 topologySpreadConstraints。
  • 手动修改由 Deployment 管理的 Pod：期望状态在 Deployment 里，你的改动下一轮调和就被抹掉。
  • 用 latest 标签：没有版本可追溯，回滚无从下手，不同节点还可能拉到不同镜像。
  • Service 数量上千还在用 iptables 模式：规则匹配是 O(n)，规则刷新要数秒，后端变化的生效延迟肉眼可见。切 IPVS。
  • namespace 卡在 Terminating 就去强删：原因一定是某个资源的 finalizer 没清理。强制移除 finalizer 会留下无人回收的云资源（磁盘、LB），要先查清是谁卡住。
  • 小项目直接上 K8s：单机几个服务用 Docker Compose 的总成本远低于 K8s。等到需要多节点调度、自动扩缩、滚动发布时再上。
