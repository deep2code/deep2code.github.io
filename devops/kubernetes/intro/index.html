Kubernetes 架构原理

🏷️ Kubernetes,云原生

为什么是 Kubernetes：从 Borg 说起

2014 年 Google 将内部大规模集群管理系统 Borg 的经验开源为 Kubernetes（K8s），其背后是十年以上在数百万核 CPU 上调度真实业务沉淀出的工程哲学。在 K8s 出现之前，运维面对的是 shell 脚本 + SSH + 手工编排 的时代：服务扩缩容靠人肉执行命令，故障恢复靠登录机器重启进程，环境一致性靠"我这台机器能跑"的口口相传。Docker 解决了打包一致性问题，但容器数量一多，谁来调度、谁来服务发现、谁来滚动升级，就成了新的复杂度。

Kubernetes 的核心价值不在于"跑容器"，而在于提供了一套声明式（Declarative）的集群操作系统：你描述"我期望系统长什么样"（What you want），K8s 负责把当前状态不断向期望状态收敛（Reconcile）。这种控制回路（Control Loop）思想贯穿了它的所有设计，也是它区别于 Puppet/Ansible 这类"执行完就结束"的命令式工具的根本所在。2015 年 CNCF 成立后，K8s 成为首个托管项目，如今已是云原生事实标准。

整体架构：控制面与数据面

Kubernetes 采用经典的主从（Master/Worker）分离架构。控制面（Control Plane）是"大脑"，负责全局决策与响应集群事件；工作节点（Worker Node）是"手脚"，真正运行业务容器。理解每个组件的职责与交互时序，是排查一切集群问题的前提。

各组件职责一句话总结：

组件跑在哪职责
kube-apiserver控制面唯一接触 etcd 的网关，所有组件都通过它读写状态
etcd控制面Raft 分布式 KV，存集群全部状态，生产必须 3/5 节点
kube-scheduler控制面给未绑定的 Pod 选最优节点（过滤→打分）
kube-controller-manager控制面跑一堆调谐控制器（Deployment/Node/Endpoint）

声明式 API 与调谐循环

Kubernetes 的所有对象（Pod、Deployment、Service…）都存储在 etcd 中，由三部分组成：apiVersion、kind、metadata、spec（期望状态）与 status（观测状态）。控制器的工作就是不断做diff。下面用一个极简 Go 伪代码展示调谐循环的本质——这也是阅读 Operator 源码的钥匙：

// reconcile 是所有 K8s 控制器的核心思想：对比期望与观测，收敛偏差
func (c *Controller) reconcile(ctx context.Context, key string) error {
    // 1. 从 apiserver 拉取"期望状态"（spec）
    deployment, err := c.client.AppsV1().Deployments(ns).Get(ctx, key, metav1.GetOptions{})
    if err != nil {
        return err
    }
    desired := *deployment.Spec.Replicas

    // 2. 列出当前"观测状态"下实际运行的 Pod
    pods, _ := c.podLister.Pods(ns).List(deployment.Spec.Selector.MatchLabels)
    running := int32(len(pods))

    // 3. 偏差不为零就采取行动，直到 running == desired
    if running < desired {
        return c.scaleUp(ctx, deployment, desired-running)
    } else if running > desired {
        return c.scaleDown(ctx, deployment, running-desired)
    }
    return nil
}

注意这个循环里没有任何"业务专属逻辑"——它只是不断地读写 apiserver。这种 Level Triggered（电平触发）设计意味着：即使控制器重启、事件丢失，只要重新拉取状态就能自愈，这就是 K8s"自愈能力"的工程本质。

快速验证你的第一个集群

先用一条命令确认集群可用，再观察节点与系统组件的分布，建立对"集群由哪些进程构成"的直观认识：

# 查看节点状态与角色
kubectl get nodes -o wide

# 看控制面 Pod 是否都 Running（kube-system 命名空间）
kubectl get pods -n kube-system

# 实时观察一次 Pod 创建全过程：调度 -> 拉镜像 -> 启动
kubectl get events --watch

# 查看集群详细信息与组件健康端点
kubectl get --raw='/readyz?verbose' | head -20

输出中重点关注：节点 STATUS 是否为 Ready、ROLES 是否区分 control-plane 与 worker、系统 Pod 是否全部 Running。若某个 kube-system Pod 一直 ContainerCreating 或 CrashLoopBackOff，基本可以断定 CNI/容器运行时/镜像拉取存在问题。

最佳实践与性能优化

  • 给每个容器设置 requests/limits：没有 requests 的 Pod 会被调度器当作"可压缩资源"随意摆放，容易引发节点资源争抢与 OOM。生产环境务必为 CPU/Memory 同时设置 requests 与 limits。
  • 控制单集群规模：单个集群 Pod 数建议不超过 5000、Node 不超过 500。超大集群应拆分为多集群（多租户/多环境隔离），而非硬撑单集群。
  • 关注 apiserver 性能：apiserver 是所有操作的瓶颈。给它配置适当的 QPS/Burst（如 controller 的 --kube-api-qps=50），并启用 Watch 缓存而非频繁 List。
  • etcd 独立部署：不要把 etcd 和业务混部，使用 SSD、独立网络，定期备份（etcdctl snapshot save）。
  • 命名与标签规范：统一使用 app、app.kubernetes.io/name、version 等标准标签，为后续 Service 选择与监控聚合打下基础。
我的教训：etcd 没备份，集群重建了

有次测试集群 etcd 盘满了，整个集群状态全丢。因为没做快照，只能重新 kubeadm init 重建——所有 Deployment、Service、Ingress 全靠 Git 里的 manifest 重新 apply，业务停了两小时。从那以后我给每个 etcd 集群配了每日快照 + 异地备份，etcdctl snapshot save 到对象存储，恢复流程跑通过一次才算数。etcd 是集群唯一的"硬盘"，没备份等于裸奔。

常见问题 FAQ

Q1：Kubernetes 和 Docker 是什么关系？是替代品吗？

不是。Docker（containerd）是容器运行时，负责真正把镜像跑成进程；Kubernetes 是编排系统，负责决定"哪个 Pod 跑在哪个节点、故障了在哪重启"。K8s 通过 CRI（Container Runtime Interface）与 containerd/CRI-O 通信，Docker Desktop 也可以作为本地开发运行时。

Q2：为什么我的 Pod 一直停在 Pending 状态？

Pending 意味着调度器还没把它绑定到任何节点。常见原因：节点资源不足（CPU/内存 requests 超过可分配量）、节点亲和性/污点与容忍度不匹配、PVC 未就绪、镜像拉取 Secret 缺失。用 kubectl describe pod <name> 看 Events 字段，调度失败原因会直接写在那里。

Q3：K8s 是不是过度设计？小团队有必要用吗？

若服务只有两三个实例且变更不频繁，用 Docker Compose 或 systemd 确实更轻。但当你需要自动扩缩容、多环境一致性、滚动发布、配置集中管理、跨云迁移时，K8s 的声明式模型会把这些复杂度收敛成 YAML。判断标准：你的运维重复劳动是否已经高到值得一次性学习曲线？

Q4：控制面挂了业务还能跑吗？

能短暂跑。控制面（apiserver/scheduler/controller）挂了，已经运行在节点上的 kubelet 与 Pod 不会立即停止，现有 Service 转发也继续工作。但此时无法创建新 Pod、无法调度故障 Pod、无法更新配置——所以生产必须多副本控制面 + 外部负载均衡。

总结

Kubernetes 的本质是一个分布式状态机收敛系统：etcd 存状态、apiserver 做网关、scheduler 做放置、各类控制器做调谐、kubelet 落地执行。理解了"声明式 + 调谐循环"这一条主线，后续的 Deployment、Service、Storage 都只是这条主线在不同资源类型上的具体实现。下一篇我们动手搭建一个真实可用的集群。
