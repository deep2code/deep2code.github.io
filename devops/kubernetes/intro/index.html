K8s 的抽象层次与该不该上

🏷️ K8s

决定要不要上 Kubernetes 之前，先把它卖的是什么想清楚。它不是「更好用的 Docker」，也不是「会自动扩容的虚拟机管理器」。它真正做的一件事是：把机器、网络、存储、发布这四类基础设施能力，收敛成一组稳定的 API 对象，让你的部署描述不再绑死在某台机器、某家云上。至于声明被写进 etcd 之后是怎么变成运行中的容器的——控制循环、调度两阶段、探针与优雅退出——都在 Kubernetes 主干篇，本篇不重复，只谈抽象层次和「值不值得上」这两件决策性的事。

K8s 标准化的是接口，不是容器

容器是 Docker 已经解决的问题。K8s 解决的是容器之上那一层：一台机器变成 Node，一段网络能力变成 Service 与 Ingress，一块盘变成 PVC 加 StorageClass，一次发布变成 Deployment 的模板变更。这些对象的字段在任何符合规范的集群上语义都一样，于是你的部署描述获得了可移植性——这是它最值钱的地方，也是它全部复杂度的来源。

flowchart TB subgraph PHY["物理与云资源：各家都不一样"] M["服务器与虚拟机"] N["网卡、交换机、云负载均衡"] D["本地盘、云盘、NAS"] R["镜像仓库"] end subgraph ADAPT["适配层：把差异翻译掉"] KUBELET["kubelet + 容器运行时"] CNI["CNI 插件"] CSI["CSI 驱动"] CLOUD["cloud-controller-manager"] end subgraph API["K8s API 抽象：各家都一样"] NODE["Node / Namespace / ResourceQuota"] SVC["Service / Ingress / NetworkPolicy"] PVC["PVC / StorageClass / VolumeSnapshot"] WL["Deployment / StatefulSet / Job"] end subgraph DECL["你唯一需要写的东西"] YAML["声明式清单，进 Git 仓库"] end M --> KUBELET R --> KUBELET N --> CNI D --> CSI KUBELET --> NODE KUBELET --> WL CNI --> SVC CSI --> PVC CLOUD --> SVC NODE --> YAML SVC --> YAML PVC --> YAML WL --> YAML

看这张图要抓住一点：适配层的存在，正是账单所在。CNI 让你不用关心底层网络是 VXLAN 还是 BGP，代价是网络不通时你要多排查一层；CSI 让你不用关心是云盘还是 Ceph，代价是卷挂不上时多一个组件要看。抽象不会消灭复杂度，只会把它挪到你不熟悉的地方——这句话就是判断要不要上 K8s 的核心依据。

被严重低估的一项：监控必须从零重建

很多团队迁移时只算了「学 YAML 要多久」，完全没算监控。容器会被随时销毁重建，基于主机名和进程的旧监控在 K8s 里全部失效：告警会因为 Pod 名字变化而炸成一片，日志会随容器删除而消失。迁移的第一天你就会失去线上可观测性，所以这件事必须在迁移之前做完，不是之后。

前置条件怎么验证缺了会怎样先补什么
已容器化且配置不在镜像里同一个镜像只换环境变量就能跑另一套环境每个环境一个镜像，回滚时对不上版本把启动参数与连接串挪到环境变量或外部配置文件
进程无状态压测中随机 kill 一个副本，错误率不应上升滚动更新就掉会话、丢内存里的任务会话与缓存外移，本地上传目录改对象存储

镜像标签唯一生产清单里 grep 不到 latest无法确认线上跑的是哪次提交，回滚失效CI 用 commit sha 打标签，环境只引用 sha
配置与密钥外置仓库里 grep 不到明文密码Secret 会被手写进 Git，后患无穷见 配置与密钥篇
日志集中删掉一个 Pod 后仍能查到它最后 5 分钟的日志容器一重建，故障现场就消失了日志全部写 stdout，由采集器统一收走
监控覆盖两层能同时回答「接口 P99 是多少」和「节点还剩多少可调度内存」出事只能等用户来报Prometheus 加 kube-state-metrics，先把集群层建起来

下面几条命令可以在迁移之前把上面大半项验证掉，不需要任何 K8s 环境：

# 1. 镜像里有没有夹带环境配置或密钥（最常见的不合格项）
docker run --rm registry.example.com/api:9f3c2a1 env \
  | grep -iE 'password|token|secret|jdbc|://' || echo "镜像环境干净"

# 2. 进程会不会优雅退出：用满 10 秒说明它是被 SIGKILL 杀的，不合格
cid=$(docker run -d registry.example.com/api:9f3c2a1)
time docker stop -t 10 "$cid"

# 3. 日志是否全部走 stdout（写进容器内文件的日志上集群后会随容器消失）
docker exec "$cid" sh -c 'ls /app/logs 2>/dev/null && echo "有本地日志文件，需要改造" || echo "只写 stdout，合格"'

# 4. 无状态验证：起两个副本，压测过程中杀掉一个，观察错误率
docker compose up -d --scale api=2
docker compose kill --signal SIGKILL api   # 另一个终端同时压测，错误率应当只有瞬时抖动

对象数量的膨胀：同一套服务的两种写法

成本清单里最不直观的一项是「YAML 与模板维护」。用同一组服务的两种描述做对照最直接。先是 Compose 的起点：

# 单机 Compose：两个服务的全部部署描述就这一份文件
services:
  api:
    image: registry.example.com/api:9f3c2a1   # 不用 latest，回滚时你会需要这个 sha
    env_file: [./env/prod.env]
    ports: ["8080:8080"]
    restart: always                           # 单机环境下唯一的自愈手段
    deploy:
      resources:
        limits: {memory: 1G}
  redis:
    image: redis:7.2-alpine
    volumes: ["redis-data:/data"]
volumes:
  redis-data:

搬到 K8s，仅 api 这一个服务的最小可用描述就是下面三个对象；redis 还要 StatefulSet、Headless Service、PVC 三件，再加 ServiceAccount、PodDisruptionBudget、NetworkPolicy 就是十个出头：

apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
  labels:
    app.kubernetes.io/name: api
    app.kubernetes.io/version: "9f3c2a1"
spec:
  replicas: 2
  selector:
    matchLabels:
      app.kubernetes.io/name: api        # 创建后不可修改，命名一次定终身
  template:
    metadata:
      labels:
        app.kubernetes.io/name: api
    spec:
      containers:
        - name: api
          image: registry.example.com/api:9f3c2a1
          envFrom:
            - configMapRef: {name: api-config}   # 原来一份 prod.env 拆成两个对象
            - secretRef: {name: api-secret}
          ports:
            - {name: http, containerPort: 8080}
          resources:
            requests: {cpu: 200m, memory: 256Mi}
            limits: {memory: 512Mi}   # 只限内存不限 CPU，避免 CFS 限流，原理见主干篇
---
apiVersion: v1
kind: Service
metadata:
  name: api
spec:
  selector:
    app.kubernetes.io/name: api
  ports:
    - {name: http, port: 80, targetPort: http}
---
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: api
spec:
  ingressClassName: nginx
  rules:
    - host: api.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: api
                port: {name: http}

从 15 行变成 60 行，从 1 个文件变成 3 个对象，这个倍率会在 20 个服务上如实放大。这不是 K8s 设计得啰嗦，而是它把原本隐含在运维习惯里的东西——谁做负载均衡、谁做健康检查、配置从哪来——全部显式化了。显式化的好处是可审计、可回滚、可复制，坏处就是这张账单。

核心概念速查

对象一句话定位细节去哪看
Pod调度与生命周期的最小单位，一组共享网络与存储命名空间的容器主干篇：启动链路、探针、优雅退出
Deployment无状态副本的期望状态声明，通过 ReplicaSet 实现版本化与回滚工作负载篇
StatefulSet给每个副本稳定编号、稳定 DNS 名和固定 PVC，代价是有序启停工作负载篇
Service一组 Pod 的稳定虚拟 IP 与 DNS 名，本质是节点上的转发规则而不是代理进程主干篇
Ingress集群外 HTTP 流量的七层入口与 TLS 终结点，由 Ingress 控制器实现网络篇
ConfigMap 与 Secret外置配置与凭证的载体，注入方式直接决定能不能热更新配置与密钥篇
PVC 与 StorageClass对「我要一块多大、什么性能的盘」的声明，由 CSI 驱动实际供给存储篇
Namespace名字与配额的隔离域，不是安全边界，跨命名空间网络默认互通网络篇的 NetworkPolicy
Helm 与 Kustomize把上面这堆对象打包、参数化、管多环境差异的两种思路Helm 篇、GitOps 系列

最容易踩的坑
  • 用流量而不是服务数量做判断：单个高流量服务用云负载均衡加伸缩组更省事；K8s 的收益来自服务数量与依赖复杂度，不是 QPS。
  • 算了机器成本没算人力成本：托管集群每月的管理费通常远低于一个人两周的时间，而自建省下的恰恰只是这笔管理费。
  • 忘了集群升级是周期性工程：社区一年 3 个小版本、每版本维护期约 14 个月，意味着你每年至少排一次升级，并扫描清单里被移除的 API 版本。
  • 以为 Namespace 是安全边界：它只隔离名字和配额，跨命名空间的 Pod 默认网络互通，也默认能解析彼此的 Service DNS，要隔离必须写 NetworkPolicy。
  • 生产镜像用 latest：Pod 重建时可能拉到不同的镜像内容，同一个 Deployment 的副本跑着不同代码，而且无法回滚。
  • 不设 requests 就上生产：调度器按 requests 做装箱，不填等于告诉它「我不占资源」，节点会被超卖到内存耗尽。
  • 把日志写进容器内文件：容器删除即丢失，而 K8s 删容器比你现在的环境频繁得多。日志一律写 stdout。
  • 先迁数据库：有状态组件把存储、备份、有序启停的难题一次性全给你，是迁移顺序里最该放最后的东西。
  • 没有人专责平台：证书过期、节点磁盘被镜像写满、版本脱离维护期，这三件事一定会发生，而且都不会自己好。
  • 照搬网上的 YAML 却不看版本：extensions/v1beta1 这类 API 早已移除，旧教程里的 Ingress 和 PodSecurityPolicy 清单在新集群上直接报错。
  • 把「能跑起来」当迁移完成：真正的验收标准是能优雅发布、能一键回滚、故障时能在五分钟内定位到出问题的那一层。
  • 用 exec 进容器修问题：修好的那一刻你就制造了一个与仓库不一致的线上状态，下一次重建它会原样复发。
