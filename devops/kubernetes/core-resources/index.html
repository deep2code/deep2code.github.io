工作负载对象的选择与编写

🏷️ Kubernetes,云原生

写 K8s 清单最常见的浪费，是一上手就抄一份 Deployment 然后改字段。真正决定后面半年会不会天天救火的，是在动手之前先把对象选对：这个东西是不是一次性的、是不是每个节点要一份、副本之间有没有身份差异。选错对象之后再怎么调参数都是在补窟窿。本篇只讲工作负载对象的选择与编写；控制循环、调度两阶段、探针语义、QoS 与限流、Service 的实现细节都在 Kubernetes 主干篇。

五种工作负载：先选对象，再写字段

flowchart TB START["要部署一个东西"] --> Q1{"是跑完就结束的一次性任务吗"} Q1 -- 是 --> Q2{"需要按时间表周期触发吗"} Q2 -- 是 --> CRON["CronJob"] Q2 -- 否 --> JOB["Job"] Q1 -- 否 --> Q3{"需要每个节点都跑一份吗"} Q3 -- 是 --> DS["DaemonSet"] Q3 -- 否 --> Q4{"副本之间需要稳定网络标识或各自独占存储吗"} Q4 -- 是 --> STS["StatefulSet 加 Headless Service"] Q4 -- 否 --> DEP["Deployment"]
对象选它的判断依据Pod 名字与网络标识存储更新与扩缩容顺序典型用途
Deployment副本之间完全对等，随便杀哪个都一样随机后缀，重建即变共享或无状态，通常不挂 PVC并行，受 maxSurge 与 maxUnavailable 控制无状态 HTTP 服务、消费者进程
StatefulSet副本有身份：需要稳定 DNS 名或独占数据盘固定 name-0 到 name-N，重建后名字不变volumeClaimTemplates 按序号绑定，PVC 不随 Pod 漂移默认按序号逐个进行，可用 podManagementPolicy 放宽启动数据库、消息队列、需要 peer 发现的集群组件
DaemonSet每个（或每类）节点恰好一份随机后缀，但与节点一一对应常挂 hostPath 采数据按节点滚动，受 maxUnavailable 控制日志采集、节点监控、CNI 与 CSI 组件
Job跑到成功次数达标就结束随机后缀按需由 completions 与 parallelism 决定数据迁移、批量导入、一次性校验
CronJobJob 加上时间表Job 名带时间戳后缀按需受 concurrencyPolicy 控制是否重叠定时对账、清理、报表
❌
最常见的选错：用 Deployment 跑有状态服务

把 Redis 主从或 MySQL 写成 Deployment 挂一个 PVC，看起来能跑。问题在两处：多副本会抢同一个 ReadWriteOnce 卷，第二个 Pod 永远挂不上；而 Pod 重建后名字变了，配置里写死的 peer 地址全部失效，主从关系需要人工重新指定。这类需求要么用 StatefulSet，要么直接用云上的托管数据库。

Deployment 与 ReplicaSet：版本是怎么被留下来的

Deployment 自己不管 Pod。它管的是 ReplicaSet：每次 spec.template 发生变化，Deployment 就按模板内容算出一个哈希，新建一个带该哈希后缀的 ReplicaSet，然后一边把新 RS 扩容、一边把旧 RS 缩容。旧 RS 副本数归零之后不会被删掉——它保存着完整的旧 Pod 模板，kubectl rollout undo 就是把它重新扩回来。

stateDiagram-v2 [*] --> S0 state "rs-abc 3 副本，新 RS 尚未创建" as S0 state "rs-def 扩到 1，rs-abc 保持 3，总数 4" as S1 state "rs-def 的 Pod 通过就绪检查" as S2 state "rs-abc 缩到 2，总数回到 3" as S3 state "rs-def 3 副本，rs-abc 归零但对象保留" as S4 S0 --> S1: 模板变更，按模板哈希新建 rs-def S1 --> S2: maxSurge 1 允许总数临时超出期望值 S2 --> S3: maxUnavailable 0 要求先 Ready 再缩旧的 S3 --> S1: 重复这一轮直到新 RS 达到期望副本 S3 --> S4: 最后一批替换完成 S4 --> S0: kubectl rollout undo 把 rs-abc 反向扩回来 S4 --> [*]: 超出 revisionHistoryLimit 的最老 RS 被清理 note right of S4 旧 ReplicaSet 副本数为 0 但对象保留，这是回滚能力的物理基础 revisionHistoryLimit 默认 10，被清理掉的版本就再也回不去了 如果新 Pod 起不来，滚动会卡在中间态，此时新旧两个 RS 都有副本在跑 end note
字段默认值作用调错的后果
revisionHistoryLimit10保留多少个副本数为 0 的旧 ReplicaSet设成 0 则完全无法回滚；设得很大会让 RS 对象堆积，kubectl get rs 刷屏
strategy.rollingUpdate.maxSurge25%允许临时超出期望副本的数量设 0 时必须先缩旧的才能起新的，等于接受容量下降
strategy.rollingUpdate.maxUnavailable25%允许同时不可用的副本数要零容量损失就设 0；与 maxSurge 同时为 0 会导致滚动永远无法开始
minReadySeconds0新 Pod Ready 后还要稳定多久才算可用为 0 时进程起来就算成功，掩盖了启动即崩溃的问题
progressDeadlineSeconds600多久没进展就把 Deployment 标记为 Failed不改的话卡住的发布要等 10 分钟才在 status 里体现，CI 会误判成功
spec.selector无默认，必填认领哪些 ReplicaSet 与 Pod创建后不可修改，里面放了会变的标签就只能重建 Deployment

StatefulSet 的三个保证与它们的代价

保证具体表现你付的代价什么时候会咬你
稳定的名称与 DNSPod 叫 mysql-0 到 mysql-2，配合 Headless Service 得到 mysql-0.mysql.ns.svc 这样的 Pod 级域名必须额外建一个 clusterIP: None 的 Service忘了建 Headless Service，Pod 域名解析不出来，集群组件互相找不到
稳定的存储绑定volumeClaimTemplates 为每个序号生成独立 PVC，Pod 重建后挂回同一块盘PVC 生命周期独立，删除 StatefulSet 不会删 PVC缩容后留下的 PVC 持续计费；再扩容回来时新 Pod 挂上旧数据
有序启停创建按 0、1、2 顺序且前一个 Ready 才起下一个；删除与滚动更新按逆序滚动更新慢，副本多时一次发布要很久；一个 Pod 卡住后面全部堵死mysql-0 因为镜像拉不下来卡住，整个集群的更新停在第一个

第二条是最容易引发困惑的：它既是保护也是陷阱。1.27 起可以用 persistentVolumeClaimRetentionPolicy 显式声明缩容和删除时怎么处置 PVC，在此之前只能手工清理。滚动更新太慢的问题可以用 podManagementPolicy: Parallel 缓解，但要注意它只放宽创建与删除的并行度，不改变滚动更新仍然逐个进行的行为。

# Headless Service：给每个 Pod 一个可解析的独立域名
# clusterIP: None 表示不分配虚拟 IP，DNS 直接返回 Pod IP 列表
apiVersion: v1
kind: Service
metadata:
  name: mysql              # Pod 域名形如 mysql-0.mysql.default.svc.cluster.local
spec:
  clusterIP: None
  selector:
    app.kubernetes.io/name: mysql
  ports:
    - {name: mysql, port: 3306}
---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: mysql
spec:
  serviceName: mysql       # 必须指向上面那个 Headless Service，写错就没有 Pod 级 DNS
  replicas: 3
  podManagementPolicy: OrderedReady   # 默认值；改成 Parallel 只影响创建删除并行度
  selector:
    matchLabels:
      app.kubernetes.io/name: mysql
  persistentVolumeClaimRetentionPolicy:
    whenScaled: Delete     # 1.27+ 缩容时删掉对应 PVC，不设则永久保留并持续计费
    whenDeleted: Retain    # 删除 StatefulSet 时保留数据盘，这是数据库该有的选择
  template:
    metadata:
      labels:
        app.kubernetes.io/name: mysql
    spec:
      terminationGracePeriodSeconds: 60   # 数据库要留足时间刷盘，细节见主干篇
      securityContext:
        runAsNonRoot: true
        fsGroup: 999                      # 让挂载的卷属主变成容器用户，否则写不进去
      containers:
        - name: mysql
          image: mysql:8.0.36
          ports:
            - {name: mysql, containerPort: 3306}
          volumeMounts:
            - {name: data, mountPath: /var/lib/mysql}
          resources:
            requests: {cpu: "1", memory: 4Gi}
            limits: {memory: 4Gi}         # 内存 limit 等于 requests，进 Guaranteed 避免被驱逐
  volumeClaimTemplates:
    - metadata:
        name: data                        # 生成的 PVC 名为 data-mysql-0、data-mysql-1 ...
      spec:
        accessModes: ["ReadWriteOnce"]
        storageClassName: ssd
        resources:
          requests:
            storage: 100Gi

Job 与 CronJob：最容易长期积压的两个对象

sequenceDiagram autonumber participant CJ as CronJob 控制器 participant API as apiserver participant J1 as Job 本次 participant J2 as Job 下一次 CJ->>API: 到达 schedule，创建 Job 本次 API->>J1: 拉起 Pod，预期 2 分钟跑完 Note over J1: 下游变慢，实际跑了 9 分钟 CJ->>API: 下一个时间点到了，读取 concurrencyPolicy API->>J2: 默认值 Allow，于是又创建一个 Job Note over J1,J2: 两个任务同时读写同一张表，出现重复处理与锁等待 CJ->>API: 若为 Forbid，则跳过本次并记录 JobAlreadyActive 事件 CJ->>API: 若为 Replace，则先删除 J1 再创建新的 Note over CJ,API: 若未设 ttlSecondsAfterFinished，J1 与 J2 完成后仍长期留在集群
参数默认值不管它会怎样建议
restartPolicy（Job）无默认，必填写 Always 会被 apiserver 拒绝，Job 只接受 OnFailure 与 Never要保留失败现场用 Never（每次失败留一个 Failed Pod）；省调度开销用 OnFailure（原地重启，旧容器日志会丢）
backoffLimit6失败任务重试 6 次，间隔从 10 秒指数退避到 6 分钟，可能拖很久确定不可能自愈的任务设 0 到 2，让它快速失败并告警
activeDeadlineSeconds无卡住的任务会一直占资源，backoffLimit 管不到「一次跑不完」这种情况一定要设，取正常耗时的 3 到 5 倍，超时直接终止
ttlSecondsAfterFinished无已完成的 Job 与 Pod 永久堆积，几个月后 kubectl get pod 上万行，etcd 对象数跟着涨一律设置，一般 86400（保留一天用于查日志）
completions 与 parallelism都是 1批量任务串行跑，慢可并行的按分片数设 parallelism；用 Indexed 模式让每个 Pod 从环境变量拿到自己的分片号
concurrencyPolicyAllow上一次没跑完，下一次照样起，同时写同一份数据非幂等任务用 Forbid；只关心最新结果的同步任务用 Replace
startingDeadlineSeconds无控制器停机期间错过的调度会在恢复后补跑；若累计错过超过 100 次，CronJob 会直接停止调度并报错设成小于调度间隔的值，明确「错过就算了」
successfulJobsHistoryLimit / failedJobsHistoryLimit3 / 1失败历史只留 1 个，排查时现场可能已经没了排查期临时调大 failedJobsHistoryLimit
timeZone无，按 kube-controller-manager 所在时区（通常 UTC）写 0 2 * * * 以为是凌晨两点，实际是 UTC 两点即北京时间十点1.27 起该字段 GA，显式写 Asia/Shanghai
 
apiVersion: batch/v1
kind: CronJob
metadata:
  name: daily-reconcile
spec:
  schedule: "0 2 * * *"
  timeZone: "Asia/Shanghai"      # 1.27+ GA。不写就是控制器所在时区，通常是 UTC
  concurrencyPolicy: Forbid      # 默认 Allow 会让上一次没跑完时又起一个，对账任务必须禁掉
  startingDeadlineSeconds: 600   # 控制器重启后超过 10 分钟的错过调度就放弃，不要补跑
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 3      # 默认只留 1 个失败记录，排查时往往已经没现场了
  jobTemplate:
    spec:
      backoffLimit: 2                  # 默认 6 次会拖到半小时以上
      activeDeadlineSeconds: 1800      # 单次最多跑 30 分钟，卡住就杀掉
      ttlSecondsAfterFinished: 86400   # 关键：不设就永久堆积已完成的 Job 与 Pod
      template:
        spec:
          restartPolicy: Never         # Job 只能 OnFailure 或 Never；Never 保留失败现场
          containers:
            - name: reconcile
              image: registry.example.com/reconcile:9f3c2a1
              args: ["--date=yesterday", "--idempotent-key=daily-reconcile"]
              envFrom:
                - secretRef: {name: reconcile-db}
              resources:
                requests: {cpu: 200m, memory: 512Mi}
                limits: {memory: 1Gi}  # 批处理最容易吃内存，limit 必须设

Pod 模板里真正值得花时间的几项

flowchart TB subgraph META["metadata：决定谁能选中它"] LBL["labels：Service 与控制器的选择依据"] ANN["annotations：配置哈希、抓取开关等元数据"] end subgraph INIT["initContainers：串行执行，前一个成功才跑下一个"] I1["wait-for-db：等依赖就绪"] I2["fix-permission：修正卷属主"] I3["原生 sidecar：restartPolicy 为 Always 的 initContainer"] end subgraph MAIN["containers：并行启动，彼此没有顺序保证"] C1["主容器"] C2["传统 sidecar：日志采集或网格代理"] end subgraph POD["Pod 级字段"] SC["securityContext：非 root、只读根文件系统"] TG["terminationGracePeriodSeconds"] TSC["topologySpreadConstraints"] end META --> INIT I1 --> I2 I2 --> I3 INIT --> MAIN MAIN --> POD
写法启动顺序退出行为适用版本要求
普通 initContainer按声明顺序串行，全部成功后主容器才启动跑完就退出，退出码非 0 会按 Pod 的 restartPolicy 重试等依赖、初始化数据、改卷权限、拉配置一直都有
原生 sidecar（restartPolicy: Always 的 initContainer）先于后续 initContainer 和主容器启动，并保持运行在所有主容器退出之后才被终止，不会阻塞 Job 完成网格代理、日志采集、凭证刷新1.28 需开 SidecarContainers 门控，1.29 默认开启
传统 sidecar（并列写在 containers 里）与主容器并行启动，没有先后保证可能比主容器先退出导致最后一批日志丢失；在 Job 里不退出会让 Job 永远不完成老集群的唯一选择任意版本

另外两项常被跳过但性价比极高：securityContext 里把 runAsNonRoot、allowPrivilegeEscalation: false、readOnlyRootFilesystem: true 打开，等于免费拿到容器逃逸的第一道防线——注意只读根文件系统需要给临时目录单独挂 emptyDir，否则应用写临时文件会失败。terminationGracePeriodSeconds 与 preStop 的配合决定发布会不会掉请求，机制在 主干篇。

requests 与 limits 怎么填

方法论只有一句：requests 按实际用量的 P95 填，limits 给突发留余量。观察窗口至少覆盖一个业务周期（含日峰和周峰），不要拿压测峰值当 requests，那会让节点利用率长期停在 30%。QoS 分级、CFS 限流、OOMKilled 的机制见 主干篇，这里只给填法。

场景requestslimits为什么这么填
常规无状态服务CPU 取 P95，内存取 P95 再加 20%只设内存 limit，约 requests 的 1.5 到 2 倍；CPU limit 留空CPU 超限只会被限流拖长尾延迟，内存超限是直接 OOMKilled，两者严重程度不同
JVM 或其他带堆的运行时内存至少是堆上限加 512Mi内存 limit 等于 requests元空间、线程栈、直接内存都不在堆里，只按 Xmx 填一定 OOM
延迟敏感服务CPU 与内存都等于 limits同 requests进 Guaranteed 档，节点压力时最后才被驱逐
批处理 JobCPU 给低，让它去填集群空隙内存 limit 必须设失控的批任务是节点 OOM 的头号来源
DaemonSet 类组件按最繁忙节点的用量填内存 limit 设足它在每个节点都占一份，填大了等于全集群浪费
什么都不填——QoS 归为 BestEffort，调度器认为它不占资源，节点压力时第一个被驱逐

标签与选择器的设计

分工很清晰：labels 用来被选中，annotations 用来携带信息。凡是会出现在某个 selector 里的键，就必须是永不变化的；凡是每次发布都变的值，只能放 labels 里给人看或放 annotations，绝不能进 selector。

键值示例用途能不能变
app.kubernetes.io/nameapiService 与控制器 selector 的核心键不能，selector 创建后不可改
app.kubernetes.io/instanceapi-prod区分同一应用的多个部署实例谨慎，进了 selector 就锁定
app.kubernetes.io/componentbackend、cache、worker按层聚合查询与告警分组一般不变
app.kubernetes.io/version9f3c2a1只用于查询和看板，不要进任何 selector每次发布都变
app.kubernetes.io/managed-byhelm、argocd标记谁在管这个对象，排查配置漂移时第一眼要看换工具时变
app.kubernetes.io/part-oforder-platform标记所属业务域，做成本归集基本不变
注解 checksum/configsha256 的前 8 位配置变化时触发滚动更新，做法见 配置与密钥篇每次配置变更都变

一份生产级 Deployment 全注释

apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
  labels:
    app.kubernetes.io/name: api
    app.kubernetes.io/component: backend
    app.kubernetes.io/version: "9f3c2a1"      # 只展示用，不进 selector
    app.kubernetes.io/managed-by: argocd
spec:
  replicas: 4
  revisionHistoryLimit: 5                     # 默认 10，留 5 个版本足够回滚
  minReadySeconds: 10                         # Ready 后再稳 10 秒才算可用，挡住起来就崩的版本
  progressDeadlineSeconds: 300                # 5 分钟没进展就标记 Failed，CI 才能及时判定失败
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0                       # 与 maxSurge 不能同时为 0，否则滚动无法开始
  selector:
    matchLabels:
      app.kubernetes.io/name: api             # 创建后不可修改，只放永不变的键
  template:
    metadata:
      labels:
        app.kubernetes.io/name: api
        app.kubernetes.io/version: "9f3c2a1"
      annotations:
        checksum/config: "3f9a1c04"           # 配置内容哈希，变了才触发滚动更新
    spec:
      terminationGracePeriodSeconds: 45       # 要大于 preStop 睡眠时间加最长请求耗时
      securityContext:
        runAsNonRoot: true
        runAsUser: 10001
        fsGroup: 10001
        seccompProfile: {type: RuntimeDefault}
      topologySpreadConstraints:              # 让副本分散到不同可用区，避免单区故障全挂
        - maxSkew: 1
          topologyKey: topology.kubernetes.io/zone
          whenUnsatisfiable: ScheduleAnyway   # 用 DoNotSchedule 会在区数不足时直接挂起 Pod
          labelSelector:
            matchLabels:
              app.kubernetes.io/name: api
      initContainers:
        - name: wait-for-db                   # 串行执行且必须成功，否则主容器不会启动
          image: busybox:1.36
          command:
            - sh
            - -c
            - |
              # 只等有限次，不要写 while true，否则依赖永不来时 Pod 会永远卡在 Init
              for i in $(seq 1 30); do
                nc -z db 3306 && exit 0
                sleep 2
              done
              echo "db not ready after 60s" >&2
              exit 1
      containers:
        - name: api
          image: registry.example.com/api:9f3c2a1   # 用 commit sha，不用 latest
          imagePullPolicy: IfNotPresent
          ports:
            - {name: http, containerPort: 8080}
          envFrom:
            - configMapRef: {name: api-config}
            - secretRef: {name: api-secret}
          resources:
            requests: {cpu: 300m, memory: 512Mi}    # 按 P95 实测填
            limits: {memory: 1Gi}                   # 不设 CPU limit，避免 CFS 限流拖尾延迟
          startupProbe:                             # 慢启动应用靠它兜住，别去放宽 liveness
            httpGet: {path: /healthz, port: http}
            periodSeconds: 5
            failureThreshold: 24                    # 最长容忍 120 秒启动
          readinessProbe:
            httpGet: {path: /readyz, port: http}    # 要检查依赖是否可用
            periodSeconds: 5
          livenessProbe:
            httpGet: {path: /healthz, port: http}   # 只检查进程自身，不要查依赖
            periodSeconds: 10
            failureThreshold: 6
          lifecycle:
            preStop:
              exec:
                command: ["sh", "-c", "sleep 10"]   # 等转发规则摘除完成，机制见主干篇
          securityContext:
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true            # 需要写临时文件就挂 emptyDir
            capabilities: {drop: ["ALL"]}
          volumeMounts:
            - {name: tmp, mountPath: /tmp}
      volumes:
        - name: tmp
          emptyDir: {}

反模式与排查

反模式症状后果正确做法
用 Deployment 跑有状态服务多副本时第二个 Pod 卡在 ContainerCreating，事件里是卷多重挂载错误数据盘抢占、peer 地址失效换 StatefulSet 加 Headless Service，或直接用托管数据库
不设 resourceskubectl describe node 里 Allocated 远低于实际用量QoS 为 BestEffort，节点压力时第一批被驱逐；节点被超卖到 OOM至少填 requests，内存必须填 limits
CronJob 不设 concurrencyPolicy 与 ttlkubectl get pod 上千行 Completed；同一任务多个实例并行重复处理数据、etcd 对象数膨胀Forbid 或 Replace，并设 ttlSecondsAfterFinished
Job 失败无限重启RESTARTS 持续增长，日志里同一个报错重复出现占用配额，掩盖真实失败原因把 backoffLimit 调小并设 activeDeadlineSeconds，失败要告警而不是重试
selector 里放会变的标签想改 version 选择器时 apiserver 报字段不可变只能新建 Deployment 再切流量selector 只放 app.kubernetes.io/name 这类恒定键
initContainer 里等一个永远不来的依赖Pod 长期 Init:0/1，没有任何报错发布静默卡死，因为 initContainer 的失败不触发探针告警循环加次数上限，超时就以非 0 退出码失败，让 Pod 进入可见的失败状态
把 sidecar 并列写在 containers 里跑 JobJob 的 Pod 一直 Running，主容器早已 CompletedJob 永远不完成，CronJob 的 Forbid 策略随之全部跳过1.29+ 用原生 sidecar；老版本让 sidecar 监听主容器退出后自杀

kubectl get deploy,rs,pod -l app.kubernetes.io/name=api -o wide

# 看版本历史与每一版的变更说明（CHANGE-CAUSE 来自 kubernetes.io/change-cause 注解）
kubectl rollout history deployment/api

kubectl get deploy api -o jsonpath='{range .status.conditions[*]}{.type}={.status} {.reason}{"\n"}{end}'

# 找出堆积的已完成 Pod（ttlSecondsAfterFinished 没设的典型现象）
kubectl get pod -A --field-selector=status.phase==Succeeded | wc -l

# 找出所有没设内存 limit 的容器，这是节点 OOM 的主要来源
kubectl get pod -A -o jsonpath='{range .items[*]}{range .spec.containers[*]}{.name}{" "}{.resources.limits.memory}{"\n"}{end}{end}' \
  | awk 'NF==1 {print $1" 缺少内存 limit"}'

kubectl get pvc -l app.kubernetes.io/name=mysql --sort-by=.metadata.creationTimestamp
✅
最容易踩的坑
  • CronJob 的 concurrencyPolicy 默认是 Allow：上一次没跑完下一次照样起，对账、结算这类任务必须显式改成 Forbid。
  • 不设 ttlSecondsAfterFinished：已完成的 Job 和 Pod 永久留在集群里，半年后 kubectl get pod 能刷出上万行，etcd 对象数也跟着涨。
  • CronJob 的时区不是你的时区：不写 timeZone 就按 kube-controller-manager 所在时区（通常 UTC），0 2 * * * 实际是北京时间上午十点。
  • Job 写 restartPolicy: Always：apiserver 直接拒绝创建，Job 只接受 OnFailure 与 Never。
  • 删 StatefulSet 不删 PVC：这是保护机制不是 bug。缩容遗留的 PVC 会持续计费，且再扩容时新 Pod 会挂上旧数据。
  • StatefulSet 忘了建 Headless Service：serviceName 指向一个不存在或有 ClusterIP 的 Service，Pod 级域名就解析不出来。
  • Deployment 的 selector 创建后不可改：把 version 或环境写进 selector，之后只能新建 Deployment 再切流量。
  • maxSurge 与 maxUnavailable 同时设为 0：既不允许多起也不允许少一个，滚动更新永远无法开始。
  • revisionHistoryLimit 设成 0：等于关掉回滚能力，kubectl rollout undo 会报没有可回滚的版本。
  • initContainer 里 while true 等依赖：依赖永远不来时 Pod 卡在 Init 状态且不产生任何告警，必须加次数上限并以非 0 退出。
  • 只读根文件系统没配临时目录：readOnlyRootFilesystem: true 之后应用写 /tmp 失败，要额外挂一个 emptyDir。
  • whenUnsatisfiable: DoNotSchedule 用在可用区不足的集群：拓扑约束无法满足时 Pod 直接挂起在 Pending，扩容反而失败。
  • 只按 JVM 的 Xmx 填内存 requests：元空间、线程栈、直接内存都不在堆里，容器实际占用比堆上限高出几百 MB，必然 OOMKilled。
