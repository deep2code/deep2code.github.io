K8s 核心资源

🏷️ Kubernetes,云原生

为什么是这三个资源：K8s 的"三件套"

如果只让你学 Kubernetes 的三个资源，一定是 Pod、Service、Deployment。它们分别回答三个问题：容器跑在哪（Pod）、怎么访问（Service）、怎么保证副本数与升级（Deployment）。理解这三者的协作关系，就理解了 K8s 80% 的日常工作。三者的血缘关系如下：Deployment 管 ReplicaSet，ReplicaSet 管 Pod，Service 通过 label selector 把 Pod 聚合成一个稳定入口。

Pod：K8s 调度的最小单位

Pod 不是"容器"，而是一组共享网络与存储的容器集合。同一个 Pod 里的所有容器共享同一个 network namespace（即 localhost 互通）、同一个 UTS、可以共享 emptyDir 卷。最常见的模式是"主容器 + Sidecar"：主容器跑业务，Sidecar 跑日志收集、服务网格代理、配置热加载。

Pod 的生命周期由几个关键状态机驱动：Pending → Running → Succeeded/Failed，配合 restartPolicy（Always/OnFailure/Never）。真正决定 Pod 生死的是探针（Probe）：

探针失败动作什么时候用
livenessProbe重启容器死锁、死循环这类"活着但坏了"
readinessProbe从 Service 摘除，不重启启动慢、临时不可用
startupProbe宽限期内不跑 livenessJVM/大模型推理等慢启动应用
我踩过的坑：liveness 配太紧导致重启风暴

早期给一个 Java 服务配了 livenessProbe 的 periodSeconds: 2 + failureThreshold: 3，GC 一停顿就连续失败三次，Pod 被重启。重启后 JVM 又花 30 秒预热，又触发 liveness 失败——形成重启风暴，整个服务雪崩。

后来改成 startupProbe 给 120 秒宽限，liveness 放宽到 periodSeconds: 10, failureThreshold: 6，问题消失。liveness 宁可宽不可紧，重启是真杀进程。

实战：一个带探针的 Deployment

下面是一个生产级 Nginx Deployment 的完整 YAML，包含资源限制、探针、优雅终止、滚动更新策略——这是绝大多数 Deployment 可以直接复用的模板：

apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  labels:
    app: web
    version: v1
spec:
  replicas: 3
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1          # 滚动更新时最多多出 1 个副本
      maxUnavailable: 0    # 不允许任何副本不可用（零停机）
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
        version: v1
    spec:
      terminationGracePeriodSeconds: 30   # 优雅退出宽限
      containers:
        - name: nginx
          image: nginx:1.25
          ports:
            - containerPort: 80
          resources:
            requests: {cpu: "100m", memory: "128Mi"}
            limits:   {cpu: "500m", memory: "256Mi"}
          readinessProbe:
            httpGet: {path: /healthz, port: 80}
            initialDelaySeconds: 3
            periodSeconds: 5
          livenessProbe:
            httpGet: {path: /healthz, port: 80}
            initialDelaySeconds: 10
            periodSeconds: 10
            failureThreshold: 3
          lifecycle:
            preStop:
              exec:
                command: ["/bin/sh", "-c", "sleep 5"]

配套的 Service，把这组 Pod 暴露成稳定 VIP：

apiVersion: v1
kind: Service
metadata:
  name: web-svc
spec:
  selector:
    app: web          # 必须与 Pod labels 匹配
  ports:
    - port: 80
      targetPort: 80
  type: ClusterIP

应用与日常滚动更新命令：

# 应用
kubectl apply -f web-deploy.yaml

# 查看 Deployment/ReplicaSet/Pod 三层关系
kubectl get deploy,rs,pod -l app=web

# 把镜像升级到 1.26，触发滚动更新
kubectl set image deployment/web nginx=nginx:1.26 --record

# 实时观察滚动更新过程（新 RS 逐渐副本数上升）
kubectl rollout status deployment/web

# 出问题一键回滚到上一版本
kubectl rollout undo deployment/web

用 client-go 编程式管理 Deployment

运维到一定阶段必然要写 Operator/自动化脚本。下面这段 Go 代码演示如何列出所有 Pod 并按标签筛选，是理解 client-go 用法的最小可运行骨架：

package main

import (
	"context"
	"fmt"
	"path/filepath"

	metav1 "k8s.io/apimachinery/pkg/apis/meta/v1"
	"k8s.io/client-go/kubernetes"
	"k8s.io/client-go/tools/clientcmd"
)

func main() {
	// 优先使用 kubeconfig；集群内运行则用 InClusterConfig
	kubeconfig := filepath.Join("home", "jun", ".kube", "config")
	cfg, err := clientcmd.BuildConfigFromFlags("", kubeconfig)
	if err != nil {
		panic(err)
	}
	clientset, err := kubernetes.NewForConfig(cfg)
	if err != nil {
		panic(err)
	}

	// 列出 default 命名空间下 app=web 的 Pod
	pods, err := clientset.CoreV1().Pods("default").List(
		context.TODO(), metav1.ListOptions{
			LabelSelector: "app=web",
		},
	)
	if err != nil {
		panic(err)
	}
	for _, p := range pods.Items {
		fmt.Printf("Pod=%s Node=%s Status=%s\n",
			p.Name, p.Spec.NodeName, p.Status.Phase)
	}
}

Service 的四种类型与负载均衡原理

Service 的本质是一组 Pod 的稳定访问入口，因为 Pod IP 重建后就会变。它的实现不是靠"代理转发"，而是 kube-proxy 在每个节点上写 iptables/IPVS 规则，把目标为 ClusterIP 的 DNAT 到某个 Pod IP。四种类型：

  • ClusterIP（默认）：仅集群内可达。
  • NodePort：在每个节点开一个固定端口（30000-32767）对外暴露。
  • LoadBalancer：云厂商额外分配一个公网 LB IP。
  • ExternalName：DNS CNAME 到外部域名，无代理。

生产建议优先用 IPVS 模式：iptables 在数万条规则时性能线性下降，IPVS 基于哈希表查找，万级后端无压力。切换方法：kube-proxy --proxy-mode=ipvs。

最佳实践

  • readiness 与 liveness 分离：启动慢的应用用 startupProbe 兜底，readiness 只管"现在能不能接流量"，liveness 只管"是否需要重启"。
  • 避免 liveness 过严：readiness 短暂失败摘流量即可，liveness 失败会真重启，配置 failureThreshold 给足余量。
  • 滚动更新零停机组合：maxUnavailable: 0 + maxSurge: 1 + preStop sleep + readinessProbe 四件套，缺一不可。
  • 不要把 Deployment 当无状态用：有状态应用（MySQL、Kafka）必须用 StatefulSet，它提供稳定网络标识与有序部署。
  • 优雅终止：容器收到 SIGTERM 后必须在 terminationGracePeriodSeconds 内退出，否则被 SIGKILL。preStop sleep 5 是为了等 Service 摘除完成。

常见问题 FAQ

Q1：Pod 重启次数（RESTARTS）一直增长怎么办？

先 kubectl logs <pod> --previous 看上一次崩溃的日志，再 kubectl describe pod 看 Events 里的退出码。退出码 137 = OOM 被杀（调大 memory limit）；退出码 1 = 应用自身 panic；CrashLoopBackOff 期间 kubelet 会指数退避（10s→20s→…→5min）。

Q2：Service 创建了但访问不通？

按四层排：(1) label selector 与 Pod labels 是否真匹配 kubectl get endpoints <svc> 应为非空；(2) Pod 内 curl localhost:port 是否正常；(3) 另一个 Pod curl <svc> 是否通；(4) kube-proxy 是否 Running、节点间 CNI 是否正常。

Q3：滚动更新一直卡住不结束？

典型症状：新 Pod 一直 NotReady。九成是 readinessProbe 失败——新镜像启动后健康检查没通过，Service 不把它加入 Endpoints，旧 Pod 也不敢下。kubectl describe pod <new> 看 Readiness 字段。

Q4：可以直接删 Pod 让它重建吗？

可以，但 Deployment 会立刻补一个新的。如果你是想"清掉坏 Pod"，kubectl delete pod 没问题；如果是想"改配置生效"，应该改 Deployment 然后 kubectl apply，让滚动更新接管。

总结

Pod 是运行单元，Service 是稳定入口，Deployment 是副本与升级控制器——三者构成了无状态应用在 K8s 上的最小闭环。掌握探针、滚动更新参数、优雅终止，就能 cover 90% 的日常发布与排障。下一篇我们解决"配置和密钥怎么放"的问题。
