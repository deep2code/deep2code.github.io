Kubernetes 安装部署

🏷️ Kubernetes,云原生

三种部署方式的选型

很多人学 K8s 第一步就卡在"装哪个"。现实中只有三条主流路径，选错了会浪费大量时间：

方式适用场景资源开销与生产相似度
minikube本地单机学习、演示低（VM/容器）中
kindCI 流水线测试、多节点模拟极低（Docker 容器跑节点）高
kubeadm生产/预生产集群高（3 控制面 + N worker）完全一致

选型建议：学原理用 kind（能起多节点、秒级重建），摸生产用 kubeadm（云厂商托管 EKS/ACK/GKE 本质也是 kubeadm 封装）。minikube 适合只想体验一下 GUI 的人。本文重点讲 kubeadm 全流程，并给出 kind 的一键配置。

kubeadm 初始化全流程

kubeadm 的设计哲学是"引导（bootstrap）"：它不替你装 docker、不替你配网络、不替你管升级，只负责把控制面组件用静态 Pod 的方式拉起，并生成加入令牌。理解它每一步在做什么，出问题才能定位。

flowchart LR A[安装 containerd
kubelet kubeadm kubectl] --> B[kubeadm init
初始化控制面] B --> C[生成证书与 kubeconfig] C --> D[启动静态 Pod
apiserver/etcd/scheduler/CM] D --> E[安装 CNI 网络插件
Calico/Flannel] E --> F[kubeadm join
加入 worker 节点] F --> G[集群 Ready]

前置准备（所有节点）

无论控制面还是 worker，都必须先完成这些基线配置，否则 kubeadm init 会直接报错：

# 1. 关闭交换分区（kubelet 强制要求）
sudo swapoff -a
sudo sed -i '/ swap / s/^/#/' /etc/fstab

# 2. 加载内核模块与转发参数（CNI 依赖）
cat <<'EOF' | sudo tee /etc/modules-load.d/k8s.conf
overlay
br_netfilter
EOF
sudo modprobe overlay && sudo modprobe br_netfilter

cat <<'EOF' | sudo tee /etc/sysctl.d/k8s.conf
net.bridge.bridge-nf-call-iptables  = 1
net.bridge.bridge-nf-call-ip6tables = 1
net.ipv4.ip_forward                 = 1
EOF
sudo sysctl --system

# 3. 安装容器运行时 containerd（使用 apt 或 yum，这里以 Ubuntu 为例）
sudo apt-get update && sudo apt-get install -y containerd
containerd config default | sudo tee /etc/containerd/config.toml
# 必须把 sandbox_image 改为国内可拉取的 pause 镜像
sudo sed -i 's#registry.k8s.io/pause:3.8#registry.aliyuncs.com/google_containers/pause:3.9#' /etc/containerd/config.toml
sudo systemctl restart containerd

初始化控制面与加入 Worker

完成前置准备后，在第一台机器上执行初始化。注意 --pod-network-cidr 必须与后续 CNI 插件要求一致（Calico 默认 192.168.0.0/16，Flannel 默认 10.244.0.0/16）：

# 初始化控制面（单节点演示，生产建议 --control-plane-endpoint 指定 VIP）
sudo kubeadm init \
  --apiserver-advertise-address=192.168.10.10 \
  --pod-network-cidr=192.168.0.0/16 \
  --image-repository registry.aliyuncs.com/google_containers

# 配置 kubectl
mkdir -p $HOME/.kube
sudo cp -i /etc/kubernetes/admin.conf $HOME/.kube/config
sudo chown $(id -u):$(id -g) $HOME/.kube/config

# 安装 CNI（这里用 Calico，Pod 网络才会真正通）
kubectl apply -f https://raw.githubusercontent.com/projectcalico/calico/v3.27.0/manifests/calico.yaml

# 在其他节点上执行 join（kubeadm init 结尾会打印完整命令）
sudo kubeadm join 192.168.10.10:6443 --token <token> \
  --discovery-token-ca-cert-hash sha256:<hash>

# 若忘记 join 命令，可重新生成
kubeadm token create --print-join-command

本地多节点模拟：kind 配置

没有三台机器也能模拟"1 控制面 + 2 worker"的真实拓扑。kind（Kubernetes in Docker）把每个节点跑成一个 Docker 容器，非常适合在 CI 里跑端到端测试：

# kind-config.yaml —— 一个控制面 + 两个 worker 的多节点集群
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
nodes:
  - role: control-plane
    image: kindest/node:v1.29.2
  - role: worker
    image: kindest/node:v1.29.2
  - role: worker
    image: kindest/node:v1.29.2
  - role: worker
    image: kindest/node:v1.29.2
# 把宿主机 80/443 端口映射到 control-plane，方便测试 Ingress
extraPortMappings:
  - containerPort: 80
    hostPort: 80
  - containerPort: 443
    hostPort: 443

一条命令拉起并验证：

kind create cluster --config kind-config.yaml --name dev
kubectl get nodes   # 应看到 1 个 control-plane + 3 个 worker
kind delete cluster --name dev   # 用完即毁，零残留

最佳实践

  • 控制面至少 3 节点：etcd 需要奇数节点保证 Raft 多数派。单控制面集群只用于测试。
  • 使用控制面 VIP/负载均衡：生产上 apiserver 前面必须挂 LB（云厂商 CLB 或 keepalived+haproxy），否则升级/摘除某个控制面节点时 kubectl 会断连。
  • 预留系统资源：给 kubelet 配置 --reserve-cpu / --reserve-memory，避免业务 Pod 把节点资源吃光导致 kubelet 自身 OOM。
  • 版本一致性：控制面与节点 kubelet 版本差不超过 2 个小版本（kubelet 可以比 apiserver 旧一个版本）。
  • 用 ansible/Terraform 固化安装流程：不要手工敲命令，把上面的步骤写成 Infrastructure as Code。
我踩过的坑：国内拉不到 k8s.gcr.io 镜像

第一次在国内服务器上 kubeadm init，卡在 [wait for the control plane to come up] 十分钟没动。kubectl -n kube-system get pods 看到 coredns 一直 ErrImagePull——默认镜像源 registry.k8s.io 国内根本连不上。

后来加了 --image-repository=registry.aliyuncs.com/google_containers 重跑，5 分钟就起来了。国内装 K8s，第一件事就是改镜像源。

常见问题 FAQ

Q1：kubeadm init 一直卡在 [wait for the control plane to come up]

99% 是镜像拉不下来。国内环境必须加 --image-repository 指定国内镜像源，或提前 ctr images pull 手动导入。用 kubectl -n kube-system get pods 看哪个 Pod 不是 Running，再 describe 看具体错误。

Q2：节点 NotReady，describe 显示 CNI not ready

说明你忘了装 CNI 插件。kubeadm 只负责起控制面，Pod 网络完全由 CNI 插件提供。装完 Calico/Flannel 后等 1~2 分钟，Node 会自动变为 Ready。

Q3：master 节点上怎么也能调度 Pod？

默认控制面节点有 node-role.kubernetes.io/control-plane:NoSchedule 污点，不会调度普通 Pod。测试想在 master 跑，执行 kubectl taint nodes --all node-role.kubernetes.io/control-plane-（末尾减号表示移除）。

Q4：如何重置一个节点重新 join？

在该节点执行 sudo kubeadm reset -f，然后 rm -rf /etc/cni/net.d /var/lib/cni /var/lib/etcd，再重新跑 join 命令。这是干净重来的标准姿势。

总结

kubeadm 的价值在于把"造集群"标准化：前置系统配置 → 初始化控制面 → 装 CNI → join worker，四步走完就是一个生产可用的集群。本地学习用 kind 多节点配置模拟，成本几乎为零。下一篇进入集群最核心的三个资源：Pod、Service、Deployment。
