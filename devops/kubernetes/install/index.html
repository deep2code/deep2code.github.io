Kubernetes 集群部署形态与生产化配置

🏷️ Kubernetes,云原生

先决定谁来背控制面

「装 K8s」这件事的技术含量不在敲命令，而在两个决策：控制面的运维责任归谁、哪些参数一旦定了就很难改。第一个决策决定你未来三年每次升级要花多少人力，第二个决策决定你会不会在半年后被迫重建集群。命令行步骤网上一搜就有，这两件事搜不到。

现实中的部署形态就四类，下表按「你要为什么买单」来对照，而不是按功能列清单：

维度kubeadm 自建托管集群 EKS / GKE / ACK轻量发行版 k3s / k0s本地 kind / minikube
控制面运维责任全在你：etcd 备份、证书轮换、组件升级、容量云厂商负责 apiserver 与 etcd 的可用性与升级在你，但组件被打包成单二进制，运维面小很多无，用完即毁
升级方式kubeadm upgrade 逐节点手工编排，一次一个小版本控制台或 API 一键升级，节点池滚动替换替换二进制 + 重启服务删了重建
控制面成本3 台机器常驻（一般 4C8G 起）按集群收管理费 + 节点费，控制面机器不用你出可与业务混跑，1C2G 能跑零（跑在开发机上）
可定制性最高：apiserver 启动参数、审计策略、准入插件、etcd 调参全开放受限：很多 apiserver flag 与 etcd 参数不开放中：默认换掉了 etcd（用 SQLite 或嵌入式 etcd）与部分组件高但不代表生产
etcd 可见性完全可见可调、可自己备份通常不可见，备份由厂商托管（要确认 RPO 与恢复方式）单机默认 SQLite，HA 模式才用嵌入式 etcd不关心
适用场景合规要求高、需要深度定制、机房自建绝大多数业务团队的默认答案边缘、IoT、小规模内部系统、CI 环境本地开发、端到端测试

需要纠正一个很流行的说法：「托管集群就是别人帮你跑 kubeadm」并不准确。主流托管服务的控制面是厂商自研的多租户架构，etcd 往上做了隔离与自动扩容，你拿不到 apiserver 所在机器，也改不了大部分启动参数。所以选托管之前必须确认三件事：需要的准入插件和 feature gate 是否开放、审计日志能不能导出、etcd 备份与恢复的 SLA 是什么。

控制面高可用：三主拓扑与 etcd 的奇数要求

控制面高可用的本质是两件独立的事：etcd 的 Raft 多数派和apiserver 的无状态多副本。前者要求奇数成员，后者只要求前面挂一个负载均衡。把这两件事混在一起想，就会得出「3 台控制面所以能挂 2 台」这种错误结论——3 成员 etcd 只允许挂 1 台。

关于 etcd 成员数的账要算清楚：Raft 要求写入被多数派持久化才算提交，N 个成员的多数派是 N/2 + 1，能容忍的故障数是 (N-1)/2 向下取整。3 成员容忍 1 台，4 成员也只容忍 1 台但每次写要等 3 台确认，偶数成员是纯亏。5 成员容忍 2 台，代价是写延迟变高、跨可用区流量翻倍，只在跨三可用区部署且集群规模很大时才值得。

etcd 和 apiserver 是否同机，是自建时的第二个取舍：

维度etcd 与控制面同机（kubeadm 默认 stacked）etcd 独立集群（external）
机器数3 台6 台（3 控制面 + 3 etcd）
故障耦合一台宕机同时损失一个 apiserver 和一个 etcd 成员控制面故障不影响 etcd 多数派，反之亦然
IO 争抢apiserver 的 watch 序列化与 etcd 的 WAL fsync 抢同一块盘etcd 独占磁盘，fsync 延迟可控
升级复杂度低，kubeadm upgrade 一起带走高，etcd 要单独维护版本与证书
适用规模节点数百台以内、对象数不大的集群大集群、etcd 写压力大、或对控制面 SLA 要求极高

实践结论：200 节点以内的自建集群用 stacked 就够，把力气花在给 etcd 单独挂一块 SSD 上，收益远大于拆成 6 台机器。真正需要 external etcd 的信号是 etcd_disk_wal_fsync_duration_seconds 的 p99 已经被 apiserver 的 IO 拖到 10 毫秒以上。

etcd 是整个集群的命门

集群里所有对象只存在 etcd 一处，没有第二份副本，也没有 binlog 可以回放。apiserver 挂了业务还在跑，etcd 数据没了集群就真的没了。所以 etcd 的四个问题必须在交付前解决：磁盘、容量、压缩、备份。

关注点参数 / 指标推荐值配错的后果
磁盘延迟etcd_disk_wal_fsync_duration_secondsp99 小于 10ms，本地 SSD / NVMe 独占Raft 心跳超时 → leader 反复切换 → apiserver 写超时 → 集群大面积不可变更
容量上限--quota-backend-bytes默认 2GiB，生产建议 8GiB（上限 8GiB，超过官方不保证）触顶后 etcd 报 NOSPACE 并拒绝所有写，集群变只读，只能先 defrag 再解除告警
历史版本压缩--auto-compaction-mode=periodic 与 --auto-compaction-retentionperiodic + 保留 1h 或 12hrevision 无限堆积，db 持续膨胀直到触顶
物理空间回收etcdctl defrag每周或 db 使用率低于 50% 时逐成员执行compact 后文件仍不缩小，磁盘占用只增不减
心跳与选举--heartbeat-interval / --election-timeout100ms / 1000ms，跨可用区可放宽到 300ms / 3000ms同机房调太松掉主发现变慢，跨机房调太紧导致无故选举
灾难恢复snapshot save + 恢复演练每小时快照、异地保存、每季度演练没演练过的备份等于没有备份，真出事时才发现证书或 peer URL 对不上
 
# 1. 定时快照：每小时一次，快照必须落到集群之外（对象存储或异机）
ETCDCTL_API=3 etcdctl \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/healthcheck-client.crt \
  --key=/etc/kubernetes/pki/etcd/healthcheck-client.key \
  snapshot save /backup/etcd-$(date +%F-%H%M).db

# 2. 快照必须校验，否则等于没备份
etcdutl snapshot status /backup/etcd-2026-09-23-0200.db --write-out=table
# REVISION 或 TOTAL KEYS 为 0 说明快照是坏的，报警而不是静默归档

# 3. 看是否已经在膨胀：DB SIZE 与 DB SIZE IN USE 差得多 就该 defrag
etcdctl endpoint status --write-out=table --cluster
# 同时确认 ALARM 列为空；出现 NOSPACE 说明已经触顶在拒绝写入
etcdctl alarm list

# 4. 手动压缩 + 碎片整理（有自动 compact 时只需要 defrag）
REV=$(etcdctl endpoint status --write-out=json | grep -o 'revision":[0-9]*' | head -1 | cut -d: -f2)
etcdctl compact $REV
# defrag 会阻塞该成员的读写，务必逐个成员做，不要加 --cluster 并发整
etcdctl --endpoints=https://10.0.1.11:2379 defrag
etcdctl alarm disarm   # NOSPACE 告警在 defrag 后需要手动解除

# 5. 恢复演练：停掉全部控制面静态 Pod，每个成员各自 restore 后再一起启动
etcdutl snapshot restore /backup/etcd-2026-09-23-0200.db \
  --name etcd-1 \
  --initial-cluster etcd-1=https://10.0.1.11:2380,etcd-2=https://10.0.1.12:2380,etcd-3=https://10.0.1.13:2380 \
  --initial-advertise-peer-urls https://10.0.1.11:2380 \
  --data-dir /var/lib/etcd-restore
⚠️
恢复是全集群操作，不是单点修复

etcd 快照恢复会生成一个全新的集群 ID，所以不能只恢复一个成员再让它加入老集群——三个成员必须用同一份快照分别 restore，然后同时启动。恢复后集群时间点回退到快照时刻，这期间创建的对象全部消失，Pod 会按旧状态被重新对齐。演练时要一并验证：证书是否还在有效期、kubeadm-config ConfigMap 是否一致、CNI 的 IPAM 记录是否需要清理。

节点规划：规格、Pod 密度与系统预留

节点规格的取舍没有标准答案，但有清晰的权衡结构：

维度少量大节点（如 32C128G × 5）大量小节点（如 4C16G × 40）
系统预留占比低，预留 1C2G 只占 3%高，同样预留占掉 25% 的 CPU
资源碎片少，大 Pod 也能装下多，8G 的 Pod 在 16G 节点上很难拼满
单点故障影响面大，一台挂掉上百个 Pod 同时重调度，可能引发连锁 Pending小，损失 2.5% 容量
Pod 数上限受 maxPods（默认 110）与节点 CIDR 掩码硬限制，规格再大也放不下更多总 Pod 容量反而更高
控制面压力低，节点对象少，kubelet 连接少高，watch 连接与心跳成倍增长
扩缩容粒度粗，扩一台就多一大坨闲置细，贴合弹性需求

每节点 Pod 数上限不是只看 maxPods：CNI 给每个节点分配一段 Pod CIDR，掩码决定可用 IP 数。集群用 --pod-network-cidr=10.244.0.0/16 配合每节点 /24，则单节点最多 254 个 Pod IP，且整个集群最多 256 个节点——这个上限在初始化时就写死了，后期扩容到第 257 台机器时才发现就非常难受。规划时把「三年后的节点数」乘以 2 再选掩码。

系统预留是最容易被跳过、后果最直接的一项。不预留时，业务 Pod 可以把节点内存吃到只剩几十 MB，kubelet 和容器运行时会和业务进程一起被内核 OOM Killer 挑中，kubelet 一死节点立刻 NotReady，上面所有 Pod 被标记驱逐，然后这批 Pod 涌向其他节点把下一台也挤死——这就是雪崩式 NotReady 的标准剧本。

# /var/lib/kubelet/config.yaml 片段 —— 以一台 8C32G 工作节点为例
apiVersion: kubelet.config.k8s.io/v1beta1
kind: KubeletConfiguration
# 给 kubelet 与容器运行时预留（不留就是拿节点稳定性赌运气）
kubeReserved:
  cpu: "500m"
  memory: "1Gi"
  ephemeral-storage: "2Gi"
# 给 sshd / systemd / journald / 监控 agent 等系统进程预留
systemReserved:
  cpu: "500m"
  memory: "1Gi"
  ephemeral-storage: "2Gi"
# Allocatable = Capacity - kubeReserved - systemReserved - evictionHard
# 上面这套配置下，32Gi 的机器对外只报约 29.5Gi 可分配，这是正确的
evictionHard:
  memory.available: "500Mi"
  nodefs.available: "10%"
  nodefs.inodesFree: "5%"
  imagefs.available: "15%"
# 软驱逐先给宽限期，避免瞬时抖动直接杀 Pod
evictionSoft:
  memory.available: "1Gi"
evictionSoftGracePeriod:
  memory.available: "2m"
# 单节点 Pod 上限：默认 110，必须与节点 CIDR 掩码匹配（/24 给不出 300 个 IP）
maxPods: 110
# 镜像 GC：磁盘超 85% 开始回收，降到 75% 停；不配就等着 DiskPressure
imageGCHighThresholdPercent: 85
imageGCLowThresholdPercent: 75
# 容器日志轮转，防止单个 Pod 写满节点盘
containerLogMaxSize: "100Mi"
containerLogMaxFiles: 5

网络与存储插件：哪些决策是不可逆的

集群初始化时有一批决策的更改成本接近重建集群，必须在第一天就想清楚：

决策项事后能改吗更改代价第一天要问自己什么
CNI 插件几乎不能要清空所有节点的网络配置与 iptables / eBPF 残留、重启全部 Pod，网络中断，风险接近重建要不要 NetworkPolicy？底层网络支持 BGP 或 VPC 路由吗？需要 eBPF 可观测性吗？
Pod CIDR 与 Service CIDR不能改掉等于新建集群三年后多少节点、多少 Pod、多少 Service？与公司内网和其他集群会不会网段冲突？
CNI 数据平面模式（Overlay / 路由）部分插件支持切换切换期间跨节点流量可能中断，MTU 要同步改能接受封装带来的吞吐损耗吗？跨机房还是同机房？
容器运行时能逐节点排空后替换，可滚动完成containerd 是默认答案，除非有特殊需求
存储后端（云盘 / 自建 Ceph / NFS）能新增，难迁移需要应用层数据迁移，无法透明切换要不要 RWX？能不能接受可用区绑定？团队能不能处理存储层故障？
集群 DNS 域名（cluster.local）不能所有服务发现名称全变有跨集群服务发现或与已有域名冲突的需求吗？

CNI 与网络策略的细节在 Pod 网络模型、Ingress 与网络策略 一篇里展开，存储后端选型在 存储抽象与有状态服务的现实 一篇里对照，这里只强调时机：这两项都属于「初始化窗口内的决策」，错过窗口就只能带着代价活下去。

集群升级：版本偏差与回滚边界

升级出事的原因通常不是命令敲错，而是三件事没做：没扫废弃 API、跨了多个小版本、没有回滚边界的定义。先把版本偏差规则记牢：

组件相对 apiserver 的允许偏差违反后的现象
kube-apiserver（多副本之间）最多相差 1 个小版本滚动升级中长期停在混版状态会出现行为不一致
kube-controller-manager / kube-scheduler不能比 apiserver 新，最多旧 1 个小版本新字段不被识别，控制器行为退化
kubelet不能比 apiserver 新，最多旧 2 到 3 个小版本（随版本演进放宽）节点注册失败或 API 字段不兼容，Pod 无法正常创建
kubectl与 apiserver 相差 1 个小版本内新命令或字段不可用，输出字段缺失
kube-proxy与所在节点 kubelet 同版本Service 规则下发异常

升级顺序是由内到外：etcd → 控制面组件 → 节点池。原因是 apiserver 必须能读写升级后的 etcd，而 kubelet 必须连上已升级的 apiserver。反过来先升 kubelet 就直接违反偏差规则。

# 0. 预检：先扫废弃 API，这是跨版本升级最常见的翻车点
pluto detect-all-in-cluster --target-versions k8s=v1.29.0
kubectl-convert -f ./legacy-ingress.yaml --output-version networking.k8s.io/v1
# 也要检查 CRD 与准入 webhook 是否声明了即将移除的版本
kubectl get crd -o json | grep -c 'v1beta1'

# 1. 版本偏差自查：kubelet 不能比 apiserver 新
kubectl get nodes -o wide          # 看 VERSION 列是否一致
kubectl version

# 2. 升级首个控制面：一次只跨一个小版本（1.28 -> 1.29，不要 1.28 -> 1.30）
apt-get update && apt-get install -y --allow-change-held-packages kubeadm=1.29.6-1.1
kubeadm upgrade plan               # 会列出目标版本与需要手工处理的项
kubeadm upgrade apply v1.29.6
# 其余控制面节点只能用 upgrade node，不要重复 apply
kubeadm upgrade node

# 3. 节点池逐批升级：先排空，再换 kubelet，最后放回调度
kubectl drain node-1 --ignore-daemonsets --delete-emptydir-data --timeout=600s
apt-get install -y --allow-change-held-packages kubelet=1.29.6-1.1 kubectl=1.29.6-1.1
systemctl daemon-reload && systemctl restart kubelet
kubectl uncordon node-1

# 4. 证书有效期：kubeadm 默认签一年，长期不升级的集群必须自己盯
kubeadm certs check-expiration
kubeadm certs renew all && systemctl restart kubelet   # 续期后要重启控制面静态 Pod

kubeadm 默认一年"] end 
# 每个业务命名空间都必须有这两个对象，否则一个命名空间可以吃光整个集群
apiVersion: v1
kind: ResourceQuota
metadata:
  name: ns-quota
  namespace: team-a
spec:
  hard:
    requests.cpu: "40"
    requests.memory: 80Gi
    limits.cpu: "80"
    limits.memory: 160Gi
    persistentvolumeclaims: "20"        # 限制 PVC 数量，防止云盘费用失控
    requests.storage: 2Ti
    count/deployments.apps: "50"
    pods: "200"
---
apiVersion: v1
kind: LimitRange
metadata:
  name: ns-defaults
  namespace: team-a
spec:
  limits:
    - type: Container
      # 没写 requests 的容器会被当成 BestEffort，节点一紧张就先被驱逐
      defaultRequest: {cpu: 100m, memory: 128Mi}
      default: {cpu: "1", memory: 1Gi}
      max: {cpu: "8", memory: 16Gi}
      # 限制 limit 与 request 的比值，避免超卖过头
      maxLimitRequestRatio: {cpu: "10", memory: "4"}
---
# 默认拒绝入站：注意这条只有在 CNI 支持 NetworkPolicy 时才真正生效
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
  namespace: team-a
spec:
  podSelector: {}
  policyTypes: [Ingress]

反模式对照

反模式为什么危险正确做法
单 etcd 节点跑生产零容错，机器一挂集群数据全靠备份，RPO 等于上次快照间隔3 成员起步，跨机架或跨可用区分布
etcd 与业务负载同盘WAL fsync 被业务 IO 拖慢 → 心跳超时 → leader 抖动 → 集群写不动etcd 独占本地 SSD，监控 fsync p99
不做 compact / defragdb 持续膨胀触到 quota 后 etcd 拒绝所有写，集群变只读开自动 compact，定期逐成员 defrag，监控 db 大小
不预留系统资源kubelet 与系统进程被业务挤死，节点 NotReady 并引发驱逐雪崩配 kubeReserved 与 systemReserved 以及驱逐阈值
一次跨多个小版本升级违反版本偏差约束，API 转换与存储迁移出现空档，故障不可回滚逐个小版本升，每一步验证后再继续
CNI 随便选，想着以后再换换 CNI 的代价接近重建集群，且 Flannel 这类插件不支持 NetworkPolicy初始化前确认策略、可观测性与底层网络能力
CIDR 掩码按当前规模掐着定节点数或 Pod 数触到上限时无法扩容，只能重建按三年规模乘 2 规划 Pod / Service CIDR
装完不配 ResourceQuota / LimitRange单个命名空间可以吃光集群，无 requests 的 Pod 全是 BestEffort命名空间创建流程里内置配额与默认值
备份从不恢复演练真出事才发现快照损坏、证书过期、peer URL 不匹配季度演练，演练结果写进 runbook
❌
最容易踩的坑

1. etcd 用了 4 个成员：以为越多越可靠，实际容错数和 3 成员一样，写延迟却更高。
2. etcd 放在网络盘或云盘共享 IOPS 上：平时没事，业务高峰 IO 被抢，leader 每隔几分钟切换一次，apiserver 大量 5xx。
3. --quota-backend-bytes 留默认 2GiB：对象一多就触顶，etcd 直接拒绝写入，此时 kubectl apply 全部失败而 get 正常，很容易误判为 apiserver 故障。
4. 只 compact 不 defrag：db size 不降反升，盘满后 etcd 起不来。
5. 快照存在集群自己的 PVC 里：集群挂了连备份都拿不到，快照必须落到集群外。
6. apiserver 前面没挂 LB，kubeconfig 直连某台控制面 IP：那台机器维护时所有 kubelet 与 CI 全部失联。
7. 不配 --control-plane-endpoint 就初始化：单控制面集群后续无法平滑扩成三主，证书里没有 VIP 的 SAN，只能重签或重建。
8. Pod CIDR 按当前 20 台机器规划成 /22：扩容到几十台就分不出网段，报 failed to allocate。
9. 忘了系统预留：节点一次抖动后 Pod 涌向邻居，连锁 NotReady，是最典型的集群级雪崩。
10. 证书没有到期告警：kubeadm 默认签一年，一年后全集群 kubelet 认证失败，节点集体 NotReady，而且此时 kubectl 也用不了，只能上机器手工 kubeadm certs renew。
11. 升级前不扫废弃 API：升完发现 Ingress 或 CRD 的旧版本已被移除，对象读不出来，控制器全线报错。
12. 节点排空不加 --ignore-daemonsets 与超时：drain 卡在 DaemonSet 或没有 PDB 的单副本应用上，变更窗口被拖爆。

小结

部署一个集群的真正工作量分布是：选形态占 10%、跑命令占 10%、把 etcd 的磁盘与备份做对占 30%、把节点预留与容量护栏配齐占 30%、把升级流程固化成可回滚的剧本占 20%。kubeadm 的命令一小时能学会，上面这四件事决定集群能不能活过三年。控制面各组件的协作机制与控制循环原理见 Kubernetes 架构与核心机制，节点级与集群级故障的排查路径见 节点与集群级故障排查。
