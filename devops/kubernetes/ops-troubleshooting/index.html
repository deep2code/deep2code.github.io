🏷️ Kubernetes,云原生

生产级 K8s 的可观测性三支柱

上线只是开始，运维才是 K8s 长期价值的试金石。生产环境的可观测性围绕三支柱展开：Metrics（指标）→ Prometheus + Grafana、Logs（日志）→ EFK/Loki、Traces（链路）→ Jaeger。没有监控的集群就是黑盒，故障只能靠用户投诉才知道。本文聚焦最常踩坑的监控告警与排障方法论。

关键监控指标与告警规则

不要一上来就装一堆看板，先把"必看黄金指标"管住。下面是生产环境必备的 Prometheus 告警规则 YAML：

apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: k8s-alerts
  namespace: monitoring
spec:
  groups:
    - name: general.rules
      rules:
        - alert: PodCrashLooping
          expr: rate(kube_pod_container_status_restarts_total[15m]) > 0
          for: 5m
          labels:
            severity: warning
          annotations:
            summary: "Pod {{ $labels.pod }} is crash looping"
        - alert: NodeDiskPressure
          expr: (node_filesystem_avail_bytes{mountpoint="/"} / node_filesystem_size_bytes{mountpoint="/"}) < 0.15
          for: 10m
          labels:
            severity: critical
        - alert: HighPodCPU
          expr: sum(rate(container_cpu_usage_seconds_total{container!=""}[5m])) by (pod) / sum(kube_pod_container_resource_requests{resource="cpu"}) by (pod) > 0.9
          for: 10m
        - alert: KubePodNotReady
          expr: sum by (namespace, pod) (kube_pod_status_ready{condition="false"}) > 0
          for: 10m

配套必看指标：节点层面 node_cpu_seconds_total、node_memory_MemAvailable_bytes、node_filesystem_avail_bytes；Pod 层面 container_cpu_usage_seconds_total、container_memory_working_set_bytes；集群层面 kube_node_status_condition、kube_pod_status_phase。

排障方法论：一条命令定位 80% 的问题

面对一个"服务不正常"的工单，按固定顺序排查，不要乱试。下面这套 bash 命令是运维日常的肌肉记忆：

# 第 1 步：Pod 现在什么状态？
kubectl get pods -n <ns>
# Pending=调度不了；ImagePullBackOff=镜像拉不到；CrashLoopBackOff=启动就崩；
# Error=探针失败/退出码非零；ContainerCreating=卷/网络还没就绪

# 第 2 步：为什么是这个状态？看 Events
kubectl describe pod <pod> -n <ns>

# 第 3 步：日志（含上一次崩溃的日志用 --previous）
kubectl logs <pod> -n <ns> --previous --tail=100

# 第 4 步：跨 Pod 连通性测试（临时起一个 debug 容器）
kubectl run tmp-shell --rm -it --image=busybox --restart=Never -- nslookup <svc>
kubectl exec -it <pod> -- curl -v http://<svc>:8080/healthz

# 第 5 步：资源是否被打满
kubectl top nodes
kubectl top pods -n <ns> --sort-by=cpu

# 第 6 步：节点本身是否健康
kubectl get nodes
kubectl describe node <node>   # 看 Allocated resources、Taints、Conditions

在应用里做好健康检查与优雅退出

监控只能告诉你"坏了"，真正让故障自愈的是应用侧的信号。下面这段 Go HTTP 服务同时提供 readiness/liveness/启动探针，是生产应用的标准姿势：

package main

import (
	"context"
	"net/http"
	"os"
	"os/signal"
	"syscall"
	"time"
)

func main() {
	mux := http.NewServeMux()

	// readiness：依赖（DB/缓存）就绪才接流量
	mux.HandleFunc("/ready", func(w http.ResponseWriter, r *http.Request) {
		if dbPing() != nil {
			w.WriteHeader(http.StatusServiceUnavailable)
			return
		}
		w.WriteHeader(http.StatusOK)
	})
	// liveness：进程活着就 200
	mux.HandleFunc("/healthz", func(w http.ResponseWriter, r *http.Request) {
		w.WriteHeader(http.StatusOK)
	})

	srv := &http.Server{Addr: ":8080", Handler: mux}
	go func() {
		if err := srv.ListenAndServe(); err != http.ErrServerClosed {
			panic(err)
		}
	}()

	// 捕获 SIGTERM，优雅退出（配合 K8s preStop + terminationGracePeriodSeconds）
	quit := make(chan os.Signal, 1)
	signal.Notify(quit, syscall.SIGINT, syscall.SIGTERM)
	<-quit

	ctx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
	defer cancel()
	srv.Shutdown(ctx) // 等待 in-flight 请求处理完
}

最佳实践

  • 告警要可行动：不要为"CPU 偶尔 80%"告警，要为"持续 10 分钟超过阈值且影响 SLA"告警。告警疲劳比没告警更致命。
  • 用 Kube-Prometheus-Stack 全家桶：kube-prometheus Helm chart 一键装 Prometheus + Alertmanager + Grafana + 一堆开箱看板，不要从零搭。
  • 日志走 sidecar 或 DaemonSet：不要让应用自己写文件，stdout/stderr 输出，由 Fluent Bit Vector 采集到 Loki/ES。
  • 定期演练故障：Chaos Mesh 或人工 kubectl delete pod，验证自愈与告警真的工作。
  • etcd 定期备份：etcdctl snapshot save，每小时一次，保留 7 天，每季度演练恢复。
  • 记录 Runbook：每条告警对应一份排障手册，写清楚"看哪个指标、跑哪条命令、联系谁"。
我踩过的坑：退出码 137 不是应用 bug

有次一个 Pod 反复 CrashLoopBackOff，我翻了半天应用日志没看出异常，最后 kubectl describe pod 看到 Last State 的 Reason 是 OOMKilled、Exit Code 137——容器内存 limit 设太低，JVM 堆一上来就被 OOM Killer 杀了。把 limit 从 256Mi 调到 1Gi 立刻稳定。看到 137 先别怀疑代码，先看资源限制。

常见问题 FAQ

Q1：Pod 重启了怎么排查上一次为什么挂？

kubectl logs <pod> --previous 拿到上一个容器实例的日志；再看退出码：137 = OOMKilled（内存超限），130 = SIGINT，1 = 应用错误。kubectl describe pod 里 Last State 的 Exit Code 与 Reason 是第一手线索。

Q2：kubectl 超时/卡死，是不是集群挂了？

先看 kubectl get --raw='/readyz'。若控制面没挂，可能是你本地 kubeconfig 的 apiserver 地址不通（VPN 断了/控制面 LB 挂了）。业务 Pod 仍在跑，不影响线上，但你失去了管控能力，这是为什么控制面要多副本 + LB。

Q3：监控数据有延迟/不准？

Prometheus 默认 15s 抓取间隔，采集到展示有秒级延迟正常。若指标大面积缺失：检查 kubelet 的 --authentication-token-webhook、Node 的防火墙是否放通 10250/9100、Prometheus 的 ServiceMonitor selector 是否匹配。

Q4：磁盘快满了怎么紧急处理？

先看 df -h 定位大目录：容器日志在 /var/lib/docker/containers，镜像层在 /var/lib/containerd。紧急清理 crictl rmi --prune 删未使用镜像；长期方案是配 kubelet 的 --image-gc-high-threshold 自动回收。

总结

运维 K8s 的核心不是背命令，而是建立"现象→假设→验证"的闭环：监控发现异常 → describe/logs/exec 验证假设 → 定位根因 → 修复并加告警。三支柱（Metrics/Logs/Traces）+ 固定排障顺序 + 完善 Runbook，集群就从"玄学"变成"工程"。至此，Kubernetes八篇完结，从架构到安装、核心资源、配置、存储、网络、包管理、运维，构成了一个工程师上手 K8s 生产实践的完整闭环。
