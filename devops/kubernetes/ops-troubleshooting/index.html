先定位层级，再动手

排障最贵的不是修，是在错误的层级上花掉半小时。单个 Pod 崩掉和全集群不能创建 Pod 的处理路径完全不同，但两者一开始给到你的信息可能都只是「服务不可用」。所以第一个动作永远是判断影响面：一个 Pod、一个节点上的一批 Pod、还是跨节点的大面积。

Pod 级排查（状态含义、事件、日志、退出码、exec 进容器验证）的命令速查表在主干篇 Kubernetes 架构与核心机制 里，本篇不重复；这里专注节点级与集群级——那些「重启 Pod 没用」的问题。

节点 NotReady 的成因清单

kubectl describe node 的 Conditions 与 Taints 两段是唯一正确的第一入口——它们是 kubelet 自己上报的判断结果，比任何猜测都准。Ready 为 Unknown 意味着心跳丢失（问题在 kubelet 进程或它到 apiserver 的链路），为 False 则是 kubelet 活着但自认为不健康（通常是 CNI 或运行时）。

成因识别信号验证命令处置
kubelet 进程挂了或被 OOMConditions 全部变 Unknown，最后心跳时间停住systemctl status kubelet；dmesg -T | grep -i 'killed process'拉起 kubelet；根因是没配 kubeReserved 与 systemReserved，补上预留（见 集群部署形态与生产化配置）
磁盘压力DiskPressure=True，并出现 node.kubernetes.io/disk-pressure 污点df -h 与 df -hi（inode 独立耗尽）；crictl images清未用镜像与日志；配 imageGCHighThresholdPercent 与容器日志轮转
内存压力MemoryPressure=True，伴随低优先级 Pod 被驱逐free -g；kubectl top node；dmesg 看 OOM收紧超卖、补 requests、检查是否有 Pod 用 tmpfs 型 emptyDir 吃内存
PLEG 超时日志出现 PLEG is not healthy，节点在 Ready 与 NotReady 间反复抖动journalctl -u kubelet | grep -i pleg；crictl ps 是否卡住不返回容器运行时响应过慢：节点上 Pod 数过多、磁盘 IO 打满或运行时 bug；重启 containerd，长期要降 Pod 密度
网络插件异常Ready=False，message 含 cni plugin not initializedkubectl -n kube-system get pod -o wide | grep 节点名；看 CNI DaemonSet 日志修复 CNI Pod；新节点常见于配置未下发或镜像拉不到
证书过期kubelet 日志报 TLS 认证失败，往往是全集群节点同时 NotReadykubeadm certs check-expiration；openssl x509 -enddate -noout -in /var/lib/kubelet/pki/kubelet-client-current.pemkubeadm certs renew all 后重启控制面静态 Pod 与 kubelet；开启 kubelet 证书自动轮换
时钟偏移认证间歇失败、审计与事件时间线错乱、证书「尚未生效」chronyc tracking 或 timedatectl status修 NTP；偏移超过几分钟就会破坏 TLS 与令牌校验
节点被人工封锁SchedulingDisabled，存在 node.kubernetes.io/unschedulable 污点kubectl get node -o wide；kubectl describe node | grep Taints上次变更 drain 后忘了 uncordon，这是「容量莫名不足」的常见原因

资源耗尽与驱逐

驱逐是 kubelet 的自保机制：先杀 Pod，保住节点。理解它的触发条件才能解释「为什么我的 Pod 半夜突然没了」。

驱逐信号默认硬阈值含义与常见根因先看什么
memory.available100Mi节点可用内存见底。超卖过头或有 Pod 无 limitskubectl top node；有无 BestEffort 大户
nodefs.available10%kubelet 根分区告急。最常见是容器日志与 emptyDirdu -sh /var/log/pods/* 排序
nodefs.inodesFree5%inode 耗尽：小文件海量。此时 df -h 看容量很空，极易误判df -hi
imagefs.available15%镜像层分区告急，多版本镜像长期堆积crictl images | wc -l；镜像 GC 阈值
pid.available需显式配置进程数耗尽，常见于应用疯狂 fork 或僵尸进程ps -eLf | wc -l

驱逐顺序按 QoS 等级：BestEffort 先走，其次是 Burstable 中超出 requests 最多的，Guaranteed 最后。QoS 的判定规则与 CFS 限流机制见主干篇，这里只强调一个推论：不写 requests 的 Pod 就是驱逐名单上的第一名，所以 LimitRange 给默认 requests 不只是容量管理，也是稳定性措施。另外要区分两种「被杀」：驱逐是 kubelet 的主动行为，有 Evicted 事件；OOMKilled 是内核行为，退出码 137，只在容器状态里看得到。

# ===== 节点磁盘巡检（DiskPressure 的标准处置流程）=====
# 1. 容量和 inode 都要看，inode 耗尽时 df -h 完全看不出来
df -h /var/lib /var/log && df -hi /var/lib /var/log

# 2. 定位大头：容器日志 / 镜像层 / emptyDir 三个方向
du -sh /var/log/pods/* 2>/dev/null | sort -rh | head -10
du -sh /var/lib/containerd 2>/dev/null
du -sh /var/lib/kubelet/pods/*/volumes/kubernetes.io~empty-dir/* 2>/dev/null | sort -rh | head -10

# 3. 清理未被任何容器引用的镜像（安全，不会动正在用的）
crictl images | wc -l
crictl rmi --prune
# journal 也常年不清
journalctl --disk-usage && journalctl --vacuum-size=500M

# 4. 确认驱逐阈值与镜像 GC 是否配了（没配就是在等事故）
grep -E 'evictionHard|imageGC|containerLogMax' /var/lib/kubelet/config.yaml

# ===== 集群侧查驱逐与 OOM 的历史 =====
kubectl get events -A --field-selector reason=Evicted --sort-by=.lastTimestamp | tail -20
# 被驱逐的 Pod 对象会留下 Failed 状态的壳，积多了会拖慢 apiserver 列举
kubectl get pods -A --field-selector status.phase=Failed | head
kubectl delete pods -A --field-selector status.phase=Failed   # 确认后再清

# ===== kubelet 挂了 或 apiserver 不可达时 用 crictl 直连运行时兜底 =====
export CONTAINER_RUNTIME_ENDPOINT=unix:///run/containerd/containerd.sock
crictl ps -a                   # 容器还在不在，退出码是什么
crictl logs --tail 100 容器ID   # 此时 kubectl logs 已经不可用
crictl inspect 容器ID | head -40
crictl stats                   # 节点上谁在吃资源

控制面故障

控制面故障的共同特征是业务还在跑，但集群失去了变更与自愈能力——这比业务直接挂掉更危险，因为它对用户是静默的，直到某个 Pod 崩掉却再也没被重建。

故障现象业务影响验证命令
apiserver 不可用kubectl 全部超时；HPA、控制器、Service 端点更新全停现有 Pod 与流量正常，但不能部署、不能扩缩容、Pod 挂了不会重建kubectl get --raw='/readyz?verbose'；控制面机器上 crictl ps | grep apiserver
apiserver 过载 / 被限流请求 p99 飙升，大量 429；日志出现 APF 相关拒绝变更变慢、控制器同步延迟、watch 断连重建风暴看 apiserver_flowcontrol_rejected_requests_total；kubectl get flowschemas 定位是哪个客户端在刷
etcd 写超时etcdserver: request timed out；apiserver 写失败而读正常不能创建修改任何对象etcdctl endpoint status --cluster -w table；看 fsync 延迟指标
etcd leader 频繁切换日志大量 leader changed，集群响应周期性抖动间歇性变更失败磁盘 IO 争抢或网络抖动，查 etcd_server_leader_changes_seen_total
etcd 容量触顶NOSPACE 告警，集群变只读读正常、写全挂，极易误判为 apiserver 故障etcdctl alarm list；db 大小与 --quota-backend-bytes 比值
证书过期全集群节点同时 NotReady，kubectl 报证书错误失去全部管控能力，需登机器手工续期kubeadm certs check-expiration
聚合 API 不可用kubectl top 报错；某些资源列举失败，命名空间删不掉metrics 缺失、HPA 失效、清理流程卡住kubectl get apiservices | grep -v True
 
# ===== 控制面健康巡检（每次变更前后都值得跑一遍）=====
kubectl get --raw='/readyz?verbose' | grep -v ok      # 只看不 ok 的检查项
kubectl get --raw='/livez?verbose' | tail -5
kubectl get apiservices | grep -v 'True'             # 聚合 API 有没有掉的
kubectl get componentstatuses 2>/dev/null            # 已废弃但老集群还能参考

# 证书：把剩余天数做成监控指标，30 天前告警
kubeadm certs check-expiration
# kubelet 客户端证书单独看（自动轮换没开时最容易过期）
openssl x509 -enddate -noout -in /var/lib/kubelet/pki/kubelet-client-current.pem

etcdctl endpoint health --cluster

集群级现象与根因对照

现象最可能的三个原因验证顺序
Pod 大面积 Pending① 节点资源被 requests 占满（注意是分配率不是使用率）② 节点被 cordon 或带了未被容忍的污点 ③ 命名空间 ResourceQuota 用尽，或 PVC 绑不上describe pod 看调度器给的 message → kubectl describe node | grep -A5 'Allocated resources' → kubectl get quota -A → kubectl get pvc -A | grep -v Bound
Pod 大面积重启① 节点内存压力触发驱逐或 OOMKill ② liveness 探针过严 + 依赖变慢导致集体自杀 ③ 配置或镜像刚变更引入崩溃先分辨 Evicted（kubelet 行为）还是退出码 137（内核 OOM）→ 看探针参数与依赖延迟 → 查最近一次 rollout 时间点
Service 间歇性不通① 后端 Pod 频繁 Ready 抖动使端点反复增删 ② 滚动更新期间旧 Pod 未配 preStop，连接被直接切断 ③ CoreDNS 解析偶发超时kubectl get endpointslice -w 观察是否抖动 → 看 Deployment 的滚动参数与 preStop（详见主干篇）→ 查 CoreDNS 副本与限流
apiserver 响应慢① etcd fsync 慢或容量触顶 ② 某客户端全量 LIST 大资源（无 resourceVersion 的 list 直接压 etcd）③ 准入 webhook 拖慢每次写请求先看 etcd 指标 → 看 APF 拒绝与请求量按 client 分布 → kubectl get mutatingwebhookconfigurations 逐个看延迟
节点频繁 NotReady 抖动① PLEG 超时（Pod 密度过高或磁盘 IO 打满）② 未预留系统资源导致 kubelet 被挤 ③ 网络抖动使心跳丢失journalctl -u kubelet | grep -i pleg → 查 kubeReserved 配置 → 看节点到 apiserver 的丢包与 LB 健康检查
命名空间删不掉（Terminating）① 某 CRD 实例的 finalizer 等一个已卸载的控制器 ② 聚合 API 不可用导致资源列举失败 ③ 云资源（LB、盘）清理失败kubectl get ns X -o json | grep -A10 conditions → kubectl get apiservices | grep -v True → 找残留对象的 finalizer；不要强删命名空间
全集群不能创建 Pod① 准入 webhook 不可用且 failurePolicy: Fail ② etcd 只读（NOSPACE）③ 证书过期看错误信息里有没有 webhook 名字 → etcdctl alarm list → kubeadm certs check-expiration

事件与日志在哪

一个必须记住的事实：Kubernetes 的 Event 默认只保留 1 小时（apiserver 的 --event-ttl），并且在事件风暴时会被聚合与丢弃。也就是说，凌晨三点的驱逐与重启，等你早上来看时kubectl get events 已经什么都没有了。重要事件必须采集进日志系统，这是事后复盘的唯一依据。

信息源位置 / 命令保留期注意
集群事件kubectl get events -A --sort-by=.lastTimestamp默认仅 1 小时--sort-by 是客户端排序，事件多时很慢；必须用 event-exporter 或日志采集器落库
容器 stdoutkubectl logs；节点上 /var/log/pods/受 containerLogMaxSize 与轮转份数限制Pod 对象被删后日志随之消失，采集必须在节点侧做
kubelet 日志journalctl -u kubelet --since '30 min ago'受 journal 配额限制节点级问题的第一现场，PLEG、驱逐、挂载错误都在这里
容器运行时日志journalctl -u containerd同上镜像拉取、快照、cgroup 相关错误
控制面组件日志静态 Pod：kubectl -n kube-system logs；失联时 crictl logs 或 /var/log/containers/随容器apiserver 挂掉时只能走 crictl 这条路

内核日志dmesg -T环形缓冲OOM Killer、网卡、文件系统错误；killed process 是定位 OOM 的关键行

变更引发的故障：webhook 是最锋利的那把刀

集群级事故里，变更引发的占比远高于硬件故障。升级、CNI 更新、准入 webhook 上线是三大高危动作，其中 webhook 的破坏力最强，因为它横在每一次写请求的路径上。

sequenceDiagram participant U as 任意写请求 participant API as apiserver participant WH as 准入 webhook 服务 participant E as etcd U->>API: 创建或更新对象 API->>API: 认证 鉴权 内置准入 API->>WH: 调用 mutating 与 validating webhook Note over WH: webhook 自己也是集群里的 Pod
副本全挂 节点故障 证书过期 或被网络策略拦住 都会无人应答 WH--xAPI: 超时 默认 10 秒 Note over API: failurePolicy 为 Fail 时直接拒绝 API--xU: 返回失败 对象无法写入 Note over API,E: 恶性循环
匹配范围过宽时 webhook 自己的 Pod 也创建不出来
集群失去自愈能力 只能手工删除 webhook 配置 U->>API: 紧急恢复 删除 webhook 配置对象 API->>E: 写入成功 因为删除 webhook 配置本身不经过它 Note over API: 恢复后再修 webhook 并补上 namespaceSelector 与多副本 
# 准入 webhook 的安全配置：四道防线一个都不能少
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingWebhookConfiguration
metadata:
  name: policy-validator
webhooks:
  - name: validate.policy.example.com
    admissionReviewVersions: ["v1"]
    sideEffects: None
    # 防线 1：超时调小。默认 10 秒，乘上并发写请求足以把 apiserver 拖慢
    timeoutSeconds: 3
    # 防线 2：把控制面与自身所在命名空间排除，避免把自己锁死
    namespaceSelector:
      matchExpressions:
        - key: kubernetes.io/metadata.name
          operator: NotIn
          values: ["kube-system", "kube-node-lease", "webhook-system"]
    # 防线 3：只匹配真正需要校验的资源与操作，不要写 apiGroups 全通配
    rules:
      - apiGroups: ["apps"]
        apiVersions: ["v1"]
        operations: ["CREATE", "UPDATE"]
        resources: ["deployments", "statefulsets"]
        scope: Namespaced
    # 防线 4：failurePolicy 的取舍要显式决策
    # Fail   = 安全优先，webhook 挂了就拒绝写入，必须配多副本 + 反亲和 + PDB
    # Ignore = 可用性优先，webhook 挂了放行，适合非强安全用途的注入类 webhook
    failurePolicy: Ignore
    clientConfig:
      service:
        name: policy-webhook
        namespace: webhook-system
        path: /validate
        port: 443
      caBundle: LS0tLS1CRUdJTi...        # 证书轮换要与 caBundle 同步，否则静默失效
---
# webhook 服务自身的可用性保障
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: policy-webhook-pdb
  namespace: webhook-system
spec:
  minAvailable: 2                        # 至少 3 副本才谈得上 minAvailable 2
  selector:
    matchLabels: {app: policy-webhook}

应急预案

预案的价值在于「事发时不用思考」。四个高频场景的正确动作：

场景正确动作常见错误
安全排空一个节点先 cordon 停止新调度，确认关键应用有 PDB 与多副本，再 drain 并设超时；完成后记得 uncordon不加 --ignore-daemonsets 直接卡住；对单副本无 PDB 的应用直接 drain 造成中断；忘了 uncordon 导致容量长期缺一台
紧急扩容优先横向加节点（云上用节点池弹性）；来不及时先降级：调低非核心服务副本、放宽 HPA 上限、临时下调 requests直接删「看起来不重要」的 Pod；把 limits 调大反而加剧节点内存压力
控制面不可用时保业务不要动数据面：不重启节点、不重启 kubelet、不删 Pod。现有 Pod 会继续运行，先专心修控制面「重启试试」——此时 kubelet 拿不到配置，重启后 Pod 可能起不回来，把一次控制面故障升级成业务故障
命名空间卡 Terminating查 status.conditions 找出哪类资源没清完，再定位持有 finalizer 的对象，修控制器或在确认底层资源已清理后移除 finalizer直接强删命名空间对象：残留云盘与 LB 既看不见也删不掉，还继续计费（机制与命令见主干篇）
 
# ===== 安全排空节点 =====
kubectl cordon node-7                                   # 先止血：不再调度新 Pod 进来
kubectl get pdb -A                                      # 确认关键应用有 PDB 保护
kubectl get pods -o wide --all-namespaces --field-selector spec.nodeName=node-7
kubectl drain node-7 --ignore-daemonsets --delete-emptydir-data \
  --timeout=600s --grace-period=60                      # 超时必须给，否则窗口被拖爆
# 若卡住，看是谁不肯走（通常是无 PDB 的单副本或 PDB 已达下限）
kubectl get events --field-selector reason=EvictionBlocked -A | tail
kubectl uncordon node-7                                 # 维护完成后务必恢复调度

# ===== 大面积 Pending 时的容量速判 =====
kubectl describe nodes | grep -A6 'Allocated resources'  # 看 requests 分配率而非使用率
kubectl get pods -A --field-selector status.phase=Pending -o wide | head -20
kubectl get nodes -o custom-columns='NAME:.metadata.name,SCHED:.spec.unschedulable,TAINTS:.spec.taints[*].key'

# ===== webhook 把集群锁死时的紧急解除 =====
kubectl get validatingwebhookconfigurations
kubectl get mutatingwebhookconfigurations
# 先备份再删除，恢复后必须补 namespaceSelector 与多副本再装回
kubectl get validatingwebhookconfiguration policy-validator -o yaml > /tmp/wh-backup.yaml
kubectl delete validatingwebhookconfiguration policy-validator

# ===== 命名空间 Terminating 的定位（不要强删）=====
kubectl get ns stuck-ns -o json | python3 -c 'import json,sys; print(json.load(sys.stdin)["status"])'
kubectl api-resources --verbs=list --namespaced -o name \
  | xargs -n1 -I{} kubectl get {} -n stuck-ns --ignore-not-found -o name | head -30
kubectl get apiservices | grep -v 'True'                # 聚合 API 挂了也会卡住删除

反模式对照

反模式会怎么出事正确做法
直接重启节点当万能解掩盖根因，把一次可控的节点问题变成 Pod 批量迁移；控制面故障期间重启更会让 Pod 起不回来先按 Conditions 定位，再决定是修 kubelet、清磁盘还是排空替换
事件不采集事件只留 1 小时，凌晨的驱逐与重启第二天查无实据，复盘只能靠猜用 event-exporter 或日志采集器把事件落库并保留 30 天以上
证书不监控kubeadm 默认一年，到期时全集群节点同时 NotReady 且 kubectl 不可用把剩余天数做成指标，30 天告警，开启 kubelet 证书自动轮换
webhook 用 Fail 策略且单副本webhook 一挂全集群不能创建 Pod，连它自己也起不来，必须手工删配置多副本 + 反亲和 + PDB + namespaceSelector 排除控制面，非强安全场景用 Ignore
驱逐阈值留默认默认 memory.available 只有 100Mi，留给内核的余量太薄，常来不及驱逐就整机 OOM按节点规格调高硬阈值，并配软驱逐给宽限期
没有集群级容量告警只盯 CPU 使用率，分配率早已 95%，扩容需求发现得太晚监控 requests 分配率、Pod 数比例、PV 与 etcd 水位
只监控业务不监控控制面apiserver 挂了业务还在跑，故障静默，直到某个 Pod 崩掉没人重建才爆发apiserver 可用性、etcd 健康、节点 Ready 数单独告警
排障不记录，全凭个人记忆同一个故障每次都要重新摸一遍，交接即失传每类告警配 runbook：看哪个指标、跑哪条命令、怎么判读、何时升级
强删卡住的资源命名空间、PV、Pod 强删后留下真实资源孤儿，云侧继续计费且无法被管理查 finalizer 定位持有者，修控制器或确认清理后再移除 finalizer
❌
最容易踩的坑

1. 看到 NotReady 就直接重启节点：根因可能是磁盘满或证书过期，重启只会让问题在半小时后原样回来，还搭上一次 Pod 批量迁移。
2. DiskPressure 时只看 df -h：inode 耗尽的节点容量看着很空，必须加 df -hi。
3. 把 Evicted 当成 OOMKilled：前者是 kubelet 驱逐（有事件、有 Failed 壳），后者是内核杀进程（退出码 137），处置方向完全不同。
4. 被驱逐的 Pod 壳从不清理：几万个 Failed Pod 会让 LIST 变慢并推高 etcd 体积。
5. PLEG 报错去查网络：PLEG 不健康几乎总是容器运行时响应慢——Pod 密度过高或磁盘 IO 打满。
6. drain 忘了 uncordon：一台机器长期不参与调度，几个月后才在「容量怎么老是不够」时发现。
7. 控制面挂了还去重启 kubelet 或删 Pod：此时拿不到 apiserver 配置，很可能把一次纯管控故障升级为业务故障。
8. etcd 触顶后只看 apiserver 日志：现象是读正常写全挂，真正的线索在 etcdctl alarm list 的 NOSPACE。
9. webhook 的 caBundle 与证书轮换不同步：证书换了 caBundle 没换，webhook 静默失效，配了 Fail 就是全集群写入失败。
10. 事件不采集、审计不开：「谁删了这个 Deployment」永远查不到，事后复盘只能停在猜测。
11. 命名空间卡 Terminating 就强删：留下一堆不可见的云盘与负载均衡器，账单和安全审计都会找上来。
12. 没有 PDB 就做滚动维护：drain 会把单副本应用直接打没，或者被 PDB 无限阻塞，两种结果都很难看。

小结

节点与集群级排障的核心是先分层、再看第一入口、最后才动手：影响面决定层级；节点级的第一入口是 describe node 的 Conditions 与 Taints，集群级的第一入口是 readyz 与 etcd 的 alarm 与 fsync。真正能减少事故的三件事不在排障阶段：把系统预留与驱逐阈值配对（见 集群部署形态与生产化配置）、把事件与审计采集起来、把证书与 etcd 水位做成告警。至于 Pod 级的命令速查，主干篇 Kubernetes 架构与核心机制 已经列全，本篇负责的是它上面那两层。
