自托管服务的取舍与运维基线

🏷️ 自托管

自建与托管的争论常在错误的层面展开：一边说「便宜」，一边说「不稳」。真正该比的是成本结构——托管方案的费用里打包了可用性承诺、版本升级、备份能力、合规材料和值班；自建把它换成人力、注意力和责任，而这三项不开发票，所以几乎从不出现在对比表里。

成本结构：账单只是其中一项

成本项托管方案里的形态自建之后的形态最容易被漏算的地方
基础设施包含在订阅里机器、存储、带宽、备份存储备份与异地副本的存储常被忘掉，它不是可选项
人力基本为零安装、升级、排障、容量规划、值班不是一次性投入，是每月都在发生的注意力占用
可用性责任由服务方承担并有约定完全自己承担单机自建的可用性上限受宿主机、磁盘、网络、机房共同约束，不要对内承诺超出这个上限的指标
合规与审计现成的报告与材料自己实现审计日志、留存期限、访问记录审计要求往往在出事或过审时才被提出，临时补代价最高
退出成本取决于导出能力取决于数据格式与迁移窗口自建也有退出成本，数据格式私有时同样搬不走

判断矩阵：什么适合自建

判断只需要四个问题：停一两个小时业务是否停摆、丢一小时数据是否可接受、这件事依赖的是外部声誉还是纯算力存储、数据能不能用标准格式导出。第三个问题最关键——邮件投递与权威域名解析依赖的是长期积累的外部声誉与极高可用性，出了问题不是加机器能解决的；而代码仓库、镜像仓库、文档这类依赖的只是算力与存储。

组件类别有状态程度可接受的数据丢失窗口升级破坏性结论
代码仓库中，仓库本身是标准格式分钟到小时级，开发者本地还有副本低到中适合自建，是自建收益最高的一类
镜像仓库与制品库中，多数内容可重建小时级低适合自建，注意存储回收策略，详见站内 Harbor 一篇
文档与知识库高，且附件与全文索引并存小时级中，常有数据结构迁移可自建，但必须先验证导出与恢复
监控与日志栈高，但数据可部分丢失可丢失近期数据中可自建，主要负担是存储膨胀与保留策略，详见站内监控与日志相关文章
关系数据库很高接近零高谨慎，自建等于把最严格的恢复目标拿到自己手上
身份认证系统高，且是全局单点接近零高谨慎，自建前必须准备好它不可用时的降级入口
邮件发送中小时级低不建议自建，投递声誉不是技术问题
权威域名解析低接近零低不建议自建，一次配置失误即全局不可达
运维负担典型组件负担的主要来源需要的关注节奏
很低静态站点、反向代理证书续期与配置变更季度级检查即可
低无状态小服务、构建执行器镜像更新与磁盘清理月级
中代码仓库、镜像仓库、文档系统备份验证、版本升级、存储增长月级加每次升级前的演练
高关系数据库、监控与日志栈容量与保留策略、慢查询与索引、数据结构迁移周级关注，容量趋势要看曲线
很高身份认证、对象存储集群、容器编排平台高可用与一致性、证书与密钥体系、版本兼容矩阵需要专人，详见站内 Kubernetes 相关文章

退出成本：先问「怎么搬走」

自建常被当成「摆脱锁定」的手段，但锁定的根源是数据格式而不是托管方。退出成本看三点：数据是不是标准格式（版本库是，带私有结构的应用库不是）；导出接口是否覆盖附件与历史；外部是否已经引用了这套系统生成的标识符与链接。第三点最容易被低估——工单号和文档链接一旦被写进几百个地方，迁移就从技术问题变成组织问题。上线前把导出跑通一次，比上线后再补便宜得多。

单机自建的最小可靠基线

下面这四层缺任何一层都不能算上线。注意顺序：数据层的可恢复性优先于运行层的高可用，因为多副本防的是机器故障，防不了误删和错误变更。

# 自建服务的 compose 基线：端口不直接对公网，状态边界写清楚，日志有上限
services:
  app:
    image: git.example.com/team/app:1.9.3   # 钉版本，不用 latest，回滚才有目标
    restart: unless-stopped
    # 只绑回环地址，公网访问统一由反向代理进来
    ports:
      - "127.0.0.1:8080:8080"
    env_file: [ ./secrets.env ]             # 密钥走 env_file，不进版本库
    volumes:
      - app-data:/var/lib/app               # 需要备份的状态只在这里
      - ./config:/etc/app:ro
    healthcheck:
      test: ["CMD", "curl", "-fsS", "http://localhost:8080/healthz"]
      interval: 30s
      timeout: 3s
      retries: 3
      start_period: 40s
    logging:
      driver: json-file
      options: { max-size: "50m", max-file: "3" }
    deploy:
      resources:
        limits: { memory: 1g, cpus: "1.5" }

  db:
    image: postgres:16.4
    restart: unless-stopped
    # 数据库不暴露任何主机端口，只走 compose 网络
    volumes:
      - db-data:/var/lib/postgresql/data
    environment:
      POSTGRES_DB: app
    env_file: [ ./secrets.env ]
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 20s

volumes:
  app-data:
  db-data:

备份：没验证过恢复的备份不算备份

备份失败的方式远比想象中多：直接复制正在写入的数据库目录得到的是不一致副本；转储时锁冲突让某些表被跳过却仍然返回成功；加密备份的密钥只存在那台已经烧掉的机器上；恢复需要的版本号从没被记录，而新版本程序读不了旧结构。所以备份的验收标准不是「任务成功」，而是「在一台干净机器上把服务恢复出来并通过校验清单」。

手段能恢复到什么恢复粒度与速度防不住什么
宿主快照整台机器某个时刻整机粒度，恢复快防不住逻辑损坏；数据库未静默时快照可能不一致
数据库逻辑转储一致的数据库内容可按库按表，恢复较慢不含文件附件；大库转储窗口长
数据卷文件级备份附件、配置、上传内容可按路径恢复直接复制运行中的数据库目录会得到损坏副本
异地副本本机与本机房全毁后的数据取决于带宽同步式复制会把误删一起同步过去
只追加的备份仓库凭据被盗后仍存在的历史版本按快照恢复不防应用层的逐步损坏，仍需保留足够长的历史
恢复演练记录真实的恢复时间与缺失步骤无什么都不防，但它是上面所有手段唯一的验收方式
 
#!/usr/bin/env bash
set -euo pipefail   # 任何一步失败立刻退出，否则失败的备份会被记成成功

# 1) 数据库用逻辑转储，流式直接进备份仓库，不落中间文件
#    加 --clean 让恢复时先删除同名对象，避免恢复到脏库上
docker compose exec -T db pg_dump -U postgres --clean --format=custom app \
  | restic backup --stdin --stdin-filename app-db.dump --tag db

# 2) 文件类数据单独备份，注意排除缓存与临时目录
restic backup /var/lib/docker/volumes/app-data/_data --tag files \
  --exclude '*/cache/*' --exclude '*.tmp'

# 3) 保留策略：近期密、远期疏；prune 才真正回收空间
restic forget --keep-daily 14 --keep-weekly 8 --keep-monthly 12 --prune

# 4) 完整性校验：只验索引不够，抽样读真实数据块
restic check --read-data-subset=5%

# 5) 把「上次成功时间」上报给监控，让备份没跑也能告警
date +%s > /var/lib/node_exporter/textfile/backup_last_success.prom.tmp
mv /var/lib/node_exporter/textfile/backup_last_success.prom.tmp \
   /var/lib/node_exporter/textfile/backup_last_success.prom

备份仓库的凭据要用只能追加、不能删除的权限，这样即便应用侧凭据泄露，历史快照也删不掉——这一条是勒索场景下唯一还站得住的防线。

入口收口与证书轮换

暴露面不靠逐个加固控制，而是靠收口：对外访问全部经过一个反向代理，代理之后的服务只监听回环或内网地址；管理后台、数据库、指标接口不出内网；防火墙默认拒绝。这套做法的价值在于「默认安全」——新加的服务默认不可达，必须显式放行。

入口项基线做法不做的后果
服务端口只绑回环或内网地址，由反向代理转发容器发布端口会绕过主机防火墙规则，直接对公网可达
管理后台与安装向导限制来源网段，安装完成后关闭初始化入口初装页面长期开放，是自建服务最常见的失守入口
远程登录只允许密钥、禁用口令与直接 root 登录持续被自动化口令尝试消耗资源与运气
TLS统一在代理层终止，只启用现代协议版本与套件，开启 HSTS证书与协议配置分散在各服务里，升级时必然漏改
证书续期自动续期加重载钩子，并从外部探测到期时间续期成功但服务没重载，到期当天整站握手失败
凭据密钥文件不进版本库，按服务最小权限拆分一份凭据泄露波及全部服务

# 反向代理基线：统一终止 TLS，管理路径限制来源，超时全部显式写出来
server {
    listen 443 ssl;
    http2 on;
    server_name app.example.com;

    ssl_certificate     /etc/letsencrypt/live/app.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/app.example.com/privkey.pem;
    # 只保留现代协议版本，关闭会话票据以降低前向保密风险
    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_prefer_server_ciphers off;
    ssl_session_tickets off;
    add_header Strict-Transport-Security "max-age=31536000" always;

    client_max_body_size 200m;   # 附件上传类服务必须显式放大，默认值只有 1m

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 60s;
        proxy_send_timeout 60s;
    }

    # 管理与指标接口不对公网：先拒绝再按需放行内网网段
    location /admin/ {
        allow 10.0.0.0/8;
        deny all;
        proxy_pass http://127.0.0.1:8080;
    }
    location /metrics {
        deny all;
    }
}

证书与代理的细节（超时参数全景、限流形态、缓冲行为）详见站内 Nginx 一篇，这里只强调一条：续期的监控对象不是脚本退出码，而是从外部握手拿到的证书剩余天数。

更新策略：可以回滚的是代码，不可回滚的是数据

变更类型策略前置条件回滚可行性
安全补丁与同小版本更新可自动化，低峰执行健康检查可信、镜像版本可回退高，换回旧版本即可
跨次版本更新人工确认变更说明后执行升级前留一份可用冷备中，取决于是否含数据结构迁移
跨大版本更新当成项目做，先在演练环境跑通确认是否必须逐级过渡，不能跨版本直跳低，多数只能靠冷备回退
数据库大版本升级独立窗口，单独演练数据目录格式变化需要专门的升级流程低，回退等于重新导入

核心认知只有一句：镜像可以换回去，数据结构迁移往往不可逆。迁移完成之后旧版本程序可能连启动都失败，此时唯一的退路是升级前那份冷备——所以「升级前做一次可恢复的备份」不是流程装饰，它就是回滚方案本身。

数据丢失的真实来源排序

按实际发生频率排，硬盘损坏远不是第一名。把投入顺序按这张表排，比盲目追求多副本有效得多。

排序来源典型形态有效防御
1人为误操作删错目录、清错库、把测试配置指到生产、一条没加条件的更新语句备份可恢复、危险操作二次确认、生产与测试凭据完全分离
2应用与升级引入的破坏数据结构迁移中断、版本不兼容、后台任务批量写坏数据升级前冷备、演练环境先跑、迁移期间禁写
3备份本身无效只备容器不备卷、转储不一致、密钥与数据同机、从未演练恢复演练、备份新鲜度告警、异机异地存放密钥
4凭据泄露与勒索数据与备份一起被删或加密只追加的备份仓库、最小权限凭据、足够长的历史保留
5介质与文件系统损坏磁盘故障、掉电后文件系统损坏冗余磁盘、定期校验、监控磁盘健康指标
6机房级灾难整个可用区不可用异地副本，且确认异地副本可以独立恢复

最容易踩的坑

❌
这些都是自建现场反复出现的问题
  • 只备份了容器却没备份卷：重建容器后发现数据目录是空的，而备份任务一直显示成功
  • 直接复制运行中的数据库数据目录：得到的副本无法启动，恢复时才发现，而那时原库已经没了
  • 备份存在同一台机器的另一个目录：机器故障时数据与备份一起消失，这不叫备份叫副本
  • 备份加密的密钥只存在被恢复的那台机器上：快照完好但无法解密
  • 从没做过恢复演练：真正需要时才发现缺版本号、缺配置文件、缺一条只有某个人知道的步骤
  • 容器发布端口时以为有防火墙保护：发布端口会绕过主机层规则，服务实际直接对公网可达
  • 安装向导与初始化入口装完没关：这是自建服务最常见的失守入口
  • 证书续期任务成功但服务没重载：到期当天整站握手失败，日志里一切正常
  • 监控只看进程活着：进程在、端口开，但依赖的数据库连不上，用户侧早就全 5xx，必须有从外部发起的黑盒探测
  • 告警只写进面板不投递到人：等于没有告警，磁盘写满通常就是这样发生的
  • 升级前不看变更说明就直跳大版本：数据结构迁移完成后旧版本起不来，唯一退路是冷备
  • 把「省钱」当唯一理由自建：一次数据丢失或一次长时间不可用，代价通常远高于当初想省的部分
