阿里云上的后端架构落地要点

🏷️ 阿里云

在云上做架构最容易犯的错误是按产品目录选型——打开控制台看到几百个产品，挑几个眼熟的拼起来。正确的顺序是反过来的：先确定这一层需要什么能力（承载什么流量、容忍多长的中断、数据丢多少算可接受），再去看哪个产品提供这个能力，最后才看它的计费维度。这篇按计算、网络、存储、数据库、可观测五个能力域来讲阿里云上的落地判断，重点放在边界条件和那些不踩一次就想不到的细节上。Kubernetes、Terraform、CI/CD、日志与监控体系的通用原理站内已有专篇，这里只讲和阿里云绑定的部分。

先按能力域拆，再落到产品

能力域先回答的问题典型选择边界与注意
计算负载是长驻还是脉冲？是否需要固定 IP 与本地盘长驻服务用 ECS 或 ACK；脉冲与批处理用 ECI；事件驱动用函数计算突发性能实例靠 CPU 积分，积分耗尽后性能会被压制，不适合持续高负载
网络哪些东西必须能从公网访问只让负载均衡与 EIP 暴露公网，应用机统一走 NAT 网关出网VPC 网段创建后不可改，vSwitch 绑定单个可用区，跨可用区必须每个区各建一个
存储数据是块、文件还是对象系统与数据库盘用 ESSD；多机共享文件用 NAS；用户上传与静态资源用 OSS云盘的 IOPS 上限随容量线性增长（PL1 约为 1800 加 50 乘容量 GiB，上限 5 万），小盘拿不到高 IOPS
数据库谁负责备份恢复与主备切换演练没有专职 DBA 就用 RDS 或 PolarDB托管意味着参数与内核可调范围受限，详见下文边界表
可观测要排查的是云产品异常还是应用异常云产品指标看云监控，应用指标与链路看 ARMS，日志进 SLSSLS 的成本由写入量乘索引比例乘保存天数决定，不要对全部字段建索引

VPC 与安全组：把开放面压到最小

网络是云上最难改的一层。VPC 网段在创建后不能修改，vSwitch 属于且只属于一个可用区，所以规划阶段就要按「可用区 × 分层」画好网段表，给未来的可用区和层次留出空间。一个稳定的做法是按接入层、应用层、数据层切三组 vSwitch，每个可用区各一套，再用安全组做层间访问控制。

安全组规则的来源可以直接填另一个安全组 ID，这是最被低估的用法：一旦按安全组互相引用，扩缩容时不需要维护任何 IP 列表，而按网段放行的规则总会在几次扩容后变成「为了省事放行整个 VPC」。

组件作用位置是否有状态最小开放面做法常见错误
安全组实例网卡级有状态，回程流量自动放通按层建组，规则来源填对端安全组 ID；只放行必需端口为了排查临时放行 0.0.0.0/0 后忘记收回
网络 ACLvSwitch 级无状态，出入方向都要显式放行只在需要子网级黑名单时使用只配了入方向，回包被拦，现象像丢包
NAT 网关VPC 出公网—统一出网出口，便于审计与固定出口 IP同时给应用机挂 EIP，等于绕开了统一出口
EIP 与公网带宽实例或网关—只给必须被公网访问的入口分配给数据库或内部服务挂 EIP，直接暴露到互联网
PrivateLink 与内网域名VPC 到服务—访问云服务走内网端点，避免流量绕公网用公网地址访问同地域 OSS，既慢又产生公网流量
负载均衡健康检查源入方向—安全组显式放行 100.64.0.0/10只放行业务网段，导致后端被全部摘除

负载均衡：ALB、NLB、CLB 与健康检查

维度ALB 应用型NLB 网络型CLB 传统型
工作层七层 HTTP/HTTPS四层 TCP/UDP四层加七层
内容路由支持按域名、路径、请求头、参数转发与重写不支持七层监听支持有限的转发规则
协议能力HTTP/2、gRPC、WebSocket、QUIC纯 TCP/UDP，延迟更低以 HTTP/1.1 与 TCP 为主
客户端真实地址七层通过 XFF 传递，只能信任最后一跳可保留客户端源地址七层靠 XFF，四层按监听配置
选择结论新系统的 HTTP 入口默认选它长连接、非 HTTP 协议、要真实源 IP存量继续用，新建不优先

健康检查有三条容易被忽略的规则。第一，健康检查端点不要串联下游依赖：如果 /health 里查了数据库，数据库一抖动，全部后端同时变不健康，故障从「部分请求变慢」升级为「整站 503」。第二，七层检查判定的是返回码，业务给 302 跳转或 401 都算失败，要专门留一个匿名可访问的检查路径。第三，不健康阈值乘以检查间隔就是故障摘除的实际耗时，配得太宽松时故障节点会继续接流量，配得太激进会在偶发超时时误摘。

OSS：一致性模型与访问控制

先纠正一个从早期 S3 传下来的认知：OSS 是强一致的——上传返回成功后立即可读，覆盖写是原子的，不存在「要等一会儿才一致」的窗口。需要小心的是另一类语义：OSS 没有跨对象的原子操作，并发覆盖同一个对象是后写者胜，所以它不能当分布式锁或计数器用；分片上传在合并完成前对外不可见，中断的分片会一直占存储，必须用生命周期规则清理。防误删的手段是版本控制，不是备份脚本。

访问控制上只有一条硬规则：桶保持私有，长期 AccessKey 绝不下发到进程之外。公共读写的桶等于把数据公开在互联网上，并且会被扫描器持续遍历。推荐的凭证获取方式按场景分层，核心都是拿有效期短、权限窄的临时凭证。

# ECS 上的服务用实例 RAM 角色取临时凭证，不需要在机器上放任何 AccessKey
# 必须用加固模式：先 PUT 取 token，再带 token 读凭证
# 这样即使应用存在 SSRF 漏洞，攻击者用一个普通 GET 也拿不到凭证（SSRF 详见站内安全专篇）
TOKEN=$(curl -s -X PUT 'http://100.100.100.200/latest/api/token' \
  -H 'X-aliyun-ecs-metadata-token-ttl-seconds: 300')

curl -s -H "X-aliyun-ecs-metadata-token: $TOKEN" \
  'http://100.100.100.200/latest/meta-data/ram/security-credentials/AppOssReadRole'

# 审计安全组：把入方向规则拉出来，逐条确认没有 0.0.0.0/0 放行数据库端口
aliyun ecs DescribeSecurityGroupAttribute --RegionId cn-hangzhou \
  --SecurityGroupId sg-xxxxxxxx --Direction ingress \
  --output cols=IpProtocol,PortRange,SourceCidrIp,SourceGroupId,Policy,Priority rows=Permissions.Permission

# 确认桶没有被设成公共读写，以及是否开了版本控制
ossutil stat oss://my-bucket
ossutil bucket-versioning --method get oss://my-bucket
凭证方式适用场景有效期与轮转风险点
长期 AccessKey仅限本地开发与一次性运维脚本手工轮转，通常永不轮转进代码库、进镜像、进前端，是云上泄露事故的第一来源
实例 RAM 角色运行在 ECS 上的服务由元数据服务自动轮转不用加固模式时，SSRF 可直接读走凭证
RRSA（ACK 内基于 OIDC）K8s 工作负载随 ServiceAccount 令牌轮转把角色绑到节点而不是 ServiceAccount，等于同节点所有 Pod 共享权限
STS 临时凭证移动端与浏览器直传分钟级到小时级签发时不加资源前缀与操作限制，等于给了全桶权限
签名 URL单个对象的临时下载或上传由过期时间控制有效期设得过长，链接被转发后长期有效
Bucket Policy跨账号或按前缀授权长期生效写成 Principal 通配，等价于公开

跨可用区、跨地域与容灾等级

容灾必须先说清「防的是哪一级故障」，否则讨论会一直停在「我们要高可用」这种没有验收标准的句子上。可用区是故障隔离的基本单位，同地域跨可用区的网络延迟通常在毫秒级，可以做同城双活；跨地域延迟是十毫秒以上量级，通常只做异步的灾备而不是双活。

等级部署形态能覆盖的故障不覆盖的故障依赖的能力
单可用区多实例同区多台 ECS 加负载均衡单机、单进程、单机架故障整个可用区断电或网络隔离负载均衡与健康检查
跨可用区每个可用区一套 vSwitch，负载均衡多可用区，RDS 主备跨区单可用区整体不可用地域级故障、误删数据、配置错误每个可用区都要有足够余量，否则切过去就被压垮
跨地域灾备OSS 跨区域复制、DTS 同步数据库、CEN 打通网络地域级故障逻辑错误（错误的发布会同步到灾备）需要明确 RPO 与 RTO，并定期做切换演练
数据可恢复性备份加版本控制加异地副本误删、误更新、勒索加密无唯一验收标准是「演练时真的恢复出来过」

两个实操细节：ECS 实例不能直接换可用区，跨区迁移要走镜像重建，所以容量规划阶段就该把实例分散开；跨可用区部署的前提是每个可用区都留了余量，两区各跑 50% 容量却没留 buffer 时，一个区挂掉只会让另一个区跟着被打死。

成本的结构性因素（不谈具体价格）

云成本优化的第一步不是砍规格，而是看清每个产品按什么维度计费，然后判断架构里哪些决定会成倍放大这些维度。具体金额随地域、规格、折扣变化，请直接用官方定价计算器按你的真实配置试算。

结构性因素放大成本的架构决定可用的杠杆
计费维度的组合只盯实例规格，忽略云盘容量与性能等级、快照、公网带宽、日志索引等附加维度先把账单按产品与维度拆开，再定优化顺序
流量方向静态资源从 ECS 公网直出；同地域服务之间用公网地址互访；跨地域频繁同步静态资源交 CDN 与 OSS；内部调用一律走内网端点；跨地域只同步必要数据
实例族与代际长期停留在旧代际；把持续高负载放在突发性能实例上按负载特征选通用、计算或内存型；定期评估代际替换
存储分层所有对象都放标准存储并永久保留用生命周期规则按访问频率下沉，但要注意低频与归档类型的最短存储时长与取回开销
付费方式把波峰容量也用长期付费方式买下来稳定基线用长期方式，波峰用按量加弹性伸缩，可中断任务用抢占式实例
可观测数据量全量日志开全字段索引并长期保留只对需要检索的字段建索引，其余投递到对象存储冷存
❌
最容易踩的坑
  • 安全组没放行 100.64.0.0/10，负载均衡健康检查全失败，后端被整组摘除，对外 503 而应用日志里没有任何请求。
  • 健康检查端点里查数据库，数据库一抖动就把所有后端同时判为不健康。
  • VPC 网段随手选了 172.16.0.0/16，后来要和公司内网或其他 VPC 互联时网段冲突，而网段不可改。
  • 忘了 vSwitch 绑定单个可用区，只建了一个 vSwitch，所谓「多机高可用」全部实例都在同一个可用区。
  • 数据库连接串写 IP 不写内网域名，RDS 主备切换后应用永久连不上。
  • JDBC 没配 connectTimeout 与 socketTimeout，切换或网络抖动时线程全挂在死连接上，线程池被打满。
  • 给应用机挂 EIP 做临时调试，之后忘记摘掉，统一出网与审计形同虚设。
  • RDS、Redis 开了公网地址方便本地连，等于把数据库暴露给全网扫描器。
  • 长期 AccessKey 写进配置文件、镜像或前端代码；或在 ECS 上用非加固模式读元数据，一个 SSRF 就能拿走凭证。
  • OSS 桶设成公共读写来「省事」，或签名 URL 有效期设成一年。
  • 以为 OSS 需要处理最终一致性而写了重试轮询逻辑，却忽略了真正的问题是并发覆盖后写者胜与分片上传残留。
  • 只做了跨可用区部署但没留余量，一个可用区故障后另一个区被全量流量压死。
  • 把「有备份」当成「能恢复」，从没做过一次真实的恢复演练。
  • SLS 对全部字段开索引并长期保留，日志成本悄悄超过计算成本。
