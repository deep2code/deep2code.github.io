Nginx 深度原理：进程模型、代理缓冲、限流与调优

🏷️ Nginx

「Nginx 快是因为事件驱动」讲完就停，解决不了任何线上问题。真正会用的标志是：能说清 location 的匹配优先级、知道 proxy_buffering 为什么让 SSE 不工作、知道 limit_req 加不加 nodelay 是两种完全不同的限流行为、看到 502/504 能立刻分清是谁的问题。这篇就按这些实际问题来组织。

进程 权限 职责 为什么这么设计
master root 绑定 80/443 特权端口、fork worker、处理信号 只有绑端口需要 root，把特权操作收拢到一个不处理请求的进程里
worker nginx / www-data 真正处理所有连接和请求 降权运行，即使被攻破也拿不到 root
cache manager 普通 按 max_size 和 inactive 淘汰缓存文件 磁盘清理是 IO 密集操作，不能占用 worker
cache loader 普通 启动时扫描缓存目录建立内存索引，完成后退出 避免启动时阻塞服务

核心原理一：事件驱动、惊群与连接数上限

epoll 相对 select/poll 的三个本质改进，决定了 Nginx 的并发能力：

对比 select / poll epoll
fd 集合传递 每次调用都要把全部 fd 从用户态拷到内核态 一次 epoll_ctl 注册，内核用红黑树长期维护
就绪结果 返回后需遍历全部 fd 找出就绪的，O(n) 内核维护就绪链表，直接返回就绪的那些，O(就绪数)
fd 数量上限 select 受 FD_SETSIZE（通常 1024）限制 只受进程 fd 上限约束
结论 连接数一多就被遍历开销拖死 10 万连接里只有 100 个活跃时，开销只和这 100 个相关
💡
惊群问题与 reuseport

多个 worker 都在监听同一个 socket，新连接到来时内核可能唤醒所有 worker，但只有一个能 accept 成功——其余都是无用唤醒，这就是惊群。

Nginx 早期用 accept_mutex（互斥锁，让 worker 轮流 accept）解决，代价是引入了串行化和额外延迟。1.11.3 之后默认 accept_mutex off，改用更好的方案：

# 让内核直接把连接分发到各 worker 的独立监听队列
# 彻底消除惊群，同时负载更均衡（内核按四元组哈希）
listen 80 reuseport;

注意 reuseport 在 reload 时有短暂的连接分配抖动，且同一端口只需在一处声明。

连接数上限是个容易算错的数字。反向代理场景下，一个请求要占用两个连接（客户端侧 + 上游侧）：

worker_processes auto;              # = CPU 核数
worker_rlimit_nofile 65535;         # 必须 ≥ worker_connections，否则白设
events {
    use epoll;
    worker_connections 10240;       # 默认只有 512，几乎必须调
    multi_accept on;                # 一次事件循环尽可能多接连接
}

# 理论最大并发：
#   纯静态：worker_processes × worker_connections
#   反向代理：worker_processes × worker_connections ÷ 2
# 8 核 × 10240 ÷ 2 ≈ 4 万并发请求
# 还要确认系统级限制：ulimit -n、net.core.somaxconn、net.ipv4.ip_local_port_range

核心原理二：请求处理的 11 个阶段与 location 匹配

Nginx 处理一个请求要走固定的 11 个阶段，各个模块挂在不同阶段上。很多「配置了但不生效」的怪问题，根因都是指令所属阶段和你以为的不一样。

location 的匹配优先级和「配置文件里的先后顺序」基本无关，这是最常被搞错的地方：

优先级 语法 含义 匹配规则
1（最高） location = /path 精确匹配 命中即停止，不再看其他任何 location
2 location ^~ /path 前缀匹配且阻止正则 最长前缀命中后直接使用，跳过所有正则 location
3 location ~ /re（区分大小写）
location ~* /re（不区分）		 正则匹配 按配置文件中的书写顺序，第一个匹配上就用——这里顺序才重要
4（最低） location /path 普通前缀匹配 取最长匹配的那个，与书写顺序无关 
# 静态资源用 ^~ 挡住后面的正则，省掉每个请求的正则匹配开销
location ^~ /static/ {
    root /var/www;
    expires 30d;
    access_log off;                 # 静态资源不记日志，省大量磁盘 IO
}

# 健康检查用精确匹配，优先级最高且开销最小
location = /healthz {
    return 200 "ok\n";
}

location /api/ {
    proxy_pass http://backend/;     # 末尾斜杠决定是否剥离 /api/ 前缀
}
❌
proxy_pass 尾部斜杠的差异，以及 if is evil

斜杠问题：location /api/ { proxy_pass http://backend/; } 请求 /api/users 转发为 /users（剥离前缀）；去掉 proxy_pass 末尾的斜杠写成 http://backend，则转发为 /api/users（保留前缀）。一个字符导致后端 404，是最高频的配置事故。

if 问题：if 只在 rewrite 阶段执行，它内部只有 return 和 rewrite 是完全可靠的。像 if 里面写 proxy_pass、add_header、set 会产生难以预料的行为（官方文档明确标注了这一点）。多数 if 都能用 map、try_files 或拆分 location 来替代。

核心原理三：反向代理的缓冲机制

proxy_buffering 默认开启，它的含义是：Nginx 先把上游响应完整收进缓冲区（必要时落临时文件），再发给客户端。这个默认值在 99% 的场景是对的，但在流式场景下是灾难。

flowchart TB subgraph ON["proxy_buffering on（默认）"] O1["上游全速返回响应"] --> O2["Nginx 收进 proxy_buffers
超出则写 proxy_temp_path 临时文件"] O2 --> O3["上游连接尽早释放
后端不被慢客户端拖住"] O3 --> O4["Nginx 按客户端速度慢慢发"] O4 --> O5["✅ 适合：普通 API、页面、文件下载"] end subgraph OFF["proxy_buffering off"] F1["上游返回一点"] --> F2["Nginx 立刻转发一点
只用一个 buffer"] F2 --> F3["上游连接必须保持到客户端收完
慢客户端会占住后端"] F3 --> F4["✅ 适合：SSE、流式 LLM 输出、
实时日志推送、大文件直传"] end 
location /api/ {
    proxy_pass http://backend;
    proxy_http_version 1.1;

    # 缓冲区：第一个存响应头，proxy_buffers 存响应体
    proxy_buffer_size    8k;        # 响应头过大时报 upstream sent too big header
    proxy_buffers        8 16k;
    proxy_busy_buffers_size 32k;
}

# 流式接口必须单独关掉缓冲，否则客户端会一直等到全部生成完才收到内容
location /api/stream {
    proxy_pass http://backend;
    proxy_http_version 1.1;
    proxy_buffering off;            # 关键
    proxy_cache off;
    chunked_transfer_encoding on;
    proxy_read_timeout 3600s;       # 长连接场景要放宽
    add_header X-Accel-Buffering no;
}
⚠️
上游长连接的「三件套」，缺一个都等于没配

默认情况下 Nginx 到上游用的是 HTTP/1.0 短连接，每个请求都要重新 TCP 握手 —— 高 QPS 下光握手就吃掉可观的延迟，还会大量消耗本地端口（可能撞上 TIME_WAIT 耗尽）。开启长连接必须同时写三行：

upstream backend {
    server 10.0.0.1:8080;
    server 10.0.0.2:8080;
    keepalive 64;                   # ① 每个 worker 保持的空闲长连接数
    keepalive_timeout 60s;
    keepalive_requests 1000;
}

location / {
    proxy_pass http://backend;
    proxy_http_version 1.1;         # ② 1.0 不支持长连接
    proxy_set_header Connection ""; # ③ 清掉默认带的 Connection: close
}

只写 keepalive 64; 而漏掉 ② ③ 是极常见的情况——配置看起来生效了，实际上每个请求仍在新建连接。验证方法：上游机器上看 ss -s 的 TIME_WAIT 数量有没有下降。

核心原理四：负载均衡与健康检查的真实能力

策略 指令 适用 坑
加权轮询（默认） server x weight=3; 后端性能一致或按配比分流 不感知后端实际负载
最少连接 least_conn; 请求耗时差异大、长连接 只看连接数，不看请求轻重
IP 哈希 ip_hash; 需要会话粘滞 经过 CDN/NAT 后源 IP 集中，会严重倾斜；且增删节点会导致大面积重新映射
一致性哈希 hash $request_uri consistent; 缓存节点分流、需要按 key 固定路由 加 consistent 才能让扩缩容只影响少部分 key
随机 random two least_conn; 大规模集群 「二选一取较优」在超大集群下比全局 least_conn 更省开销
⚠️
开源版 Nginx 只有被动健康检查

max_fails 和 fail_timeout 是被动的：必须先有真实请求打到故障节点并失败，才会把它标记为不可用。这意味着后端挂掉后，总会有一部分用户请求真实地失败一次。

upstream backend {
    # 10 秒内失败 3 次则摘除，摘除 10 秒后再放一个请求试探
    server 10.0.0.1:8080 max_fails=3 fail_timeout=10s;
    server 10.0.0.2:8080 max_fails=3 fail_timeout=10s;
    # 所有节点都挂时的兜底
    server 10.0.0.3:8080 backup;
}

location / {
    proxy_pass http://backend;
    # 哪些情况算失败、可以重试下一台
    proxy_next_upstream error timeout http_502 http_503;
    proxy_next_upstream_tries 2;
    proxy_next_upstream_timeout 5s;
}

要主动健康检查（无请求也定期探测），需要 Nginx Plus、nginx_upstream_check_module 第三方模块，或者干脆把这件事交给上层（K8s 的 readinessProbe、服务网格）。别以为配了 max_fails 就等于有健康检查。

另外注意：proxy_next_upstream 里加 non_idempotent 才会重试 POST。默认不重试非幂等请求是正确的设计——别为了「提高成功率」随手加上，那会造成重复下单。

核心原理五：超时参数全景与 502/504 定位

Nginx 的超时参数有十来个，分不清就无法定位问题。按「请求流经的位置」来分类记就清楚了：

参数 默认 管哪一段 超时后返回
client_header_timeout 60s 客户端 → Nginx：读请求头 408
client_body_timeout 60s 客户端 → Nginx：读请求体（两次读之间的间隔） 408
proxy_connect_timeout 60s Nginx → 上游：建立 TCP 连接 502（上限 75s，设更大无效）
proxy_send_timeout 60s Nginx → 上游：发送请求 504
proxy_read_timeout 60s Nginx ← 上游：两次读取之间的间隔（不是响应总时长） 504
send_timeout 60s Nginx → 客户端：两次写之间的间隔 连接关闭
keepalive_timeout 75s 客户端长连接空闲保持时长 关闭连接
状态码 含义 常见原因 怎么确认
502 Bad Gateway Nginx 连不上上游，或上游返回了非法响应 上游进程没起来 / 端口错 / 上游崩溃 / 响应头超过 proxy_buffer_size error.log 里的 connect() failed 或 upstream sent too big header
504 Gateway Timeout 上游连上了但迟迟不返回 后端慢 SQL、下游阻塞、死锁 日志里 $upstream_response_time 接近 proxy_read_timeout
413 Payload Too Large 请求体超限 client_max_body_size 默认只有 1m 上传接口必须显式调大
499 Nginx 自定义码：客户端主动断开 后端太慢，用户/上层网关先超时走了 看到大量 499 要去查后端耗时，而不是查 Nginx
400 请求非法 请求头过大（large_client_header_buffers）、Cookie 过长 error.log 的 client sent too long header 
# 日志里必须有这三个时间，否则「慢」只能靠猜
log_format timed '$remote_addr - $host "$request" $status $body_bytes_sent '
                 'rt=$request_time uct=$upstream_connect_time '
                 'uht=$upstream_header_time urt=$upstream_response_time '
                 'up=$upstream_addr "$http_user_agent"';

# 判读方法：
#   request_time 大但 upstream_response_time 小 → 慢在客户端网络或 Nginx 自身
#   两者都大                                    → 慢在后端应用
#   upstream_connect_time 大                    → 上游连接建立慢，查网络或后端 accept 队列

核心原理六：限流三种形态与缓存防击穿

limit_req 是漏桶算法。同一个 rate=10r/s，加不加 burst、加不加 nodelay，是三种完全不同的对外行为——这是最容易配错的地方。

flowchart TB IN["瞬间到达 20 个请求
配置 rate=10r/s（即每 100ms 放 1 个）"] IN --> A["① 不加 burst
limit_req zone=z"] IN --> B["② burst=20
limit_req zone=z burst=20"] IN --> C["③ burst=20 nodelay
limit_req zone=z burst=20 nodelay"] A --> A1["第 1 个通过
其余 19 个立刻 503
最严格 用户体验最差"] B --> B1["20 个全部排队
每 100ms 放行一个
平滑但第 20 个要等约 2 秒"] C --> C1["20 个立刻全部通过
令牌按 10r/s 恢复
允许突发 长期速率仍受限"] C1 --> C2["✅ 面向真实用户的接口
通常要的就是这个"] 
http {
    # 按客户端 IP 限速，10MB 共享内存约能存 16 万个 IP 的状态
    limit_req_zone $binary_remote_addr zone=perip:10m rate=10r/s;
    # 按域名限总量
    limit_req_zone $server_name        zone=perhost:10m rate=1000r/s;
    # 并发连接数限制（和请求速率是两个维度）
    limit_conn_zone $binary_remote_addr zone=conn_perip:10m;

    limit_req_status 429;              # 默认是 503，429 语义更准确
    limit_req_log_level warn;
}

location /api/ {
    limit_req  zone=perip burst=20 nodelay;
    limit_req  zone=perhost burst=200;
    limit_conn conn_perip 20;
    limit_rate 2m;                    # 单连接带宽上限，防单用户吃满出口
    proxy_pass http://backend;
}

反向代理缓存能挡掉大部分回源流量，但要配对两个指令才能防住缓存击穿：

http {
    # levels 是目录分级（避免单目录文件过多），keys_zone 存元数据索引
    proxy_cache_path /var/cache/nginx levels=1:2
                     keys_zone=api_cache:100m
                     max_size=10g inactive=60m use_temp_path=off;
}

location /api/list {
    proxy_cache api_cache;
    proxy_cache_key "$scheme$request_method$host$request_uri";
    proxy_cache_valid 200 302 5m;
    proxy_cache_valid 404 1m;               # 负缓存，挡住对不存在资源的反复请求

    # ① 防击穿：缓存失效瞬间只放一个请求回源，其余等它回填
    proxy_cache_lock on;
    proxy_cache_lock_timeout 5s;

    # ② 防雪崩：回源失败或正在更新时，直接返回过期内容
    proxy_cache_use_stale error timeout updating http_500 http_502 http_503;
    proxy_cache_background_update on;       # 后台异步刷新，前台立即返回旧值

    add_header X-Cache-Status $upstream_cache_status;  # HIT/MISS/EXPIRED/STALE，调试必备
}

实战：静态资源与调优基线

# ---------- 零拷贝与小包合并 ----------
sendfile on;          # 静态文件从 page cache 直接进网卡，不经用户态
tcp_nopush on;        # 与 sendfile 配合：攒满一个 MSS 再发，减少小包
tcp_nodelay on;       # 禁用 Nagle：长连接上的小响应能立即发出
                      # 这两个看似矛盾，Nginx 会在发完文件体后自动切换

# ---------- 文件描述符缓存 ----------
open_file_cache max=200000 inactive=20s;   # 缓存 fd 和 stat 结果
open_file_cache_valid 30s;
open_file_cache_min_uses 2;
open_file_cache_errors on;

# ---------- 压缩 ----------
gzip on;
gzip_comp_level 5;    # 6 以上收益迅速衰减而 CPU 显著上升
gzip_min_length 1024; # 小文件压缩后可能更大，且白耗 CPU
gzip_vary on;
gzip_proxied any;
gzip_types text/plain text/css application/json application/javascript
           application/xml image/svg+xml;
# 注意：jpg/png/mp4/zip 已经是压缩格式，再压缩纯属浪费

# ---------- 真实客户端 IP ----------
# 前面有 CDN 或 LB 时，不做这个配置，日志里全是 LB 的 IP，限流也会失效
set_real_ip_from 10.0.0.0/8;
real_ip_header X-Forwarded-For;
real_ip_recursive on;

# ---------- 平滑退出 ----------
worker_shutdown_timeout 30s;   # reload 时老 worker 最多再等 30 秒
💡
reload 为什么是「无损」的

nginx -s reload 的过程：master 校验并加载新配置 → 用新配置 fork 出新的 worker → 向老 worker 发送优雅关闭信号 → 老 worker 停止接受新连接，但继续处理完手上的存量请求后才退出。所以整个过程没有连接被强杀。

两个前提：① 先用 nginx -t 验证配置，配置有语法错误时 master 会拒绝加载并保持原样运行（这也是它比 restart 安全的地方）；② worker_shutdown_timeout 要够长，否则长连接和流式请求会被强制掐断。频繁 reload 时如果老 worker 迟迟不退出，会看到 worker 进程数远超 worker_processes，这是有长连接没结束的信号。

最容易踩的坑

❌
避坑清单
  • proxy_pass 末尾斜杠写错：带斜杠剥离 location 前缀，不带则保留。一个字符导致后端全 404，最高频的配置事故。
  • 只写 keepalive 64; 就以为开了上游长连接：必须同时配 proxy_http_version 1.1 和 proxy_set_header Connection ""，缺一个都还是短连接。
  • 流式接口忘了关 proxy_buffering：SSE、流式 LLM 输出会被缓冲到全部生成完才吐给客户端，看起来像「接口卡死」。
  • 以为 max_fails 就是健康检查：它是被动的，必须有真实请求失败才摘节点。开源版没有主动探测。
  • limit_req 不加 nodelay：请求会被排队延迟释放，用户感受到的是「变慢」而不是「被限流」，比直接返回 429 更难排查。
  • 忘了调 client_max_body_size：默认只有 1MB，上传功能直接 413。
  • 没配 real_ip：CDN/LB 后面所有日志的源 IP 都是 LB 的，按 IP 限流全部作用在同一个「用户」上，等于全局限流。
  • 对图片视频开 gzip：这些格式已压缩过，再压是纯 CPU 浪费；gzip_comp_level 9 同理，收益极小而 CPU 翻倍。
  • 在 if 里写 proxy_pass、add_header、set：if 只在 rewrite 阶段可靠执行，官方明确警告过。用 map 或拆 location 替代。
  • worker_connections 留在默认 512：反代场景一个请求占两个连接，8 核默认配置理论上限才两千出头。同时别忘了 worker_rlimit_nofile 和系统 ulimit -n。
  • 看到大量 499 就去查 Nginx：499 是客户端主动断开，真正原因在后端太慢或上层网关超时更短。
  • 日志里没有 $upstream_response_time：出现慢请求时无法区分是 Nginx、网络还是后端的问题，只能靠猜。
