Nginx 深度原理：为什么能扛 10 万并发？

🏷️ Nginx

很多人用 Nginx 只会配个反向代理，但不知道为什么它能扛 10 万并发，比 Apache 高这么多，也不知道事件驱动、worker 进程模型怎么回事。这篇从底层原理讲透 Nginx。

核心原理1：事件驱动模型：为什么这么高并发？

Apache 一个连接一个线程，10 万连接要 10 万线程，上下文切换开销巨大。Nginx 事件驱动，一个 worker 处理上万连接。

flowchart TD A[Nginx 架构] --> B[Master 进程] B --> C[Worker 1] B --> D[Worker 2] B --> E[Worker 3] C --> F[epoll 事件驱动] D --> F E --> F F --> G[万级连接]

对比 Apache

对比项 Apache 进程/线程 Nginx 事件驱动
连接模型 一连接一线程 一 worker 多连接
并发能力 几千就扛不住 几万到几十万
内存占用 每个线程几 MB 每个 worker 几 MB
上下文切换 频繁切换开销大 极少切换
适合场景 动态内容 静态资源、反向代理

核心原理2：反向代理原理：请求怎么转发的？

反向代理就是用户访问 Nginx，Nginx 再把请求转发给后端服务器，后端返回结果再给用户。

flowchart LR A[用户] -->|请求| B[Nginx] B --> C{负载均衡} C -->|轮询| D[后端服务器1] C -->|轮询| E[后端服务器2] C -->|轮询| F[后端服务器3] D --> G[返回结果] E --> G F --> G G --> B --> A

负载均衡策略

策略 原理 适用场景
轮询 挨个分配 通用场景
权重 按权重分配 服务器性能不一样
ip_hash 同一个 IP 固定到同一台 需要会话保持
least_conn 分给连接数最少的 长连接场景

核心原理3：动静分离原理

静态资源（图片、CSS、JS）Nginx 直接返回，动态请求转发给后端应用，性能差 10 倍。

flowchart LR A[请求] --> B{Nginx} B -->|静态文件 .jpg/.css| C[直接读磁盘 返回] B -->|动态请求 /api/*| D[转发给后端应用]

动静分离优势

优势 说明
性能高 静态资源 Nginx 直接返回，不用走应用
省资源 应用只处理动态请求，省资源
可缓存 静态资源可以加 CDN，进一步加速
解耦 前后端分离，前端部署静态资源
