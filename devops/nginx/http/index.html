Nginx 请求处理的 11 个阶段

理解 Nginx 为什么这么配，得先搞懂一个请求从进来出去经历了哪些阶段。Nginx 把 HTTP 请求处理分成 11 个阶段，每个阶段挂不同的 handler。看懂这张图，你就知道为什么 rewrite 在 access 之前、为什么 try_files 属于 precontent。

最常出问题的几个点：

  • rewrite 为什么不生效：因为你写在了 access 阶段之后？不对，rewrite 在 REWRITE 阶段，比 ACCESS 早。但如果你用 last flag，会重新走 FIND_CONFIG 阶段，可能匹配到不同的 location
  • limit_req 为什么在 rewrite 之后：因为限流需要知道请求要走哪个 location，按 location 级别配限流规则
  • try_files 为什么不匹配 rewrite：try_files 属于 PRECONTENT 阶段，rewrite 已经跑完了。想在 try_files 之前改 URI，得用 rewrite

事件驱动：Nginx 高并发的秘密

Nginx 为什么能扛 C10K？核心就是事件驱动。每个 Worker 是单线程，用 epoll 同时监听几万个连接。有数据可读就处理，没数据就等。不像 Apache prefork 那样每个请求开一个进程。

10K 连接内存~100MB~1GB

CPU 切换开销几乎没有大量上下文切换
适合场景I/O 密集（Web/代理）CPU 密集（.mod PHP）

Master-Worker 进程模型

Master 进程以 root 跑，负责绑定 80/443 特权端口、读配置、fork Worker。Worker 用普通用户跑，实际处理请求。

好处是：Worker 崩了 Master 自动重启，不影响其他 Worker。热加载配置（nginx -s reload）也是 Master 重新 fork 新 Worker，旧 Worker 优雅退出。

算法指令原理适用场景

upstream backend {
    least_conn;
    server 10.0.0.1:8080 max_fails=3 fail_timeout=10s;
    server 10.0.0.2:8080 max_fails=3 fail_timeout=10s;
    keepalive 32;
}

max_fails=3 意思是失败 3 次就把这个后端标记为不可用，10 秒后再试。这是被动健康检查——根据实际请求结果判断。主动健康检查是 Nginx Plus 的商业功能。

FastCGI：Nginx 怎么跑 PHP

老 CGI 每个请求 fork 一个 PHP 进程，性能极差。FastCGI 让 PHP-FPM 常驻进程池，Nginx 通过 socket 通信。这就是为什么 LAMP 架构变成了 LNMP。

HTTP/1.1 vs HTTP/2 vs HTTP/3

HTTP/1.1HTTP/2HTTP/3
传输协议TCPTCPUDP（QUIC）
多路复用❌ 队头阻塞✅ 二进制分帧✅ 独立流，无队头阻塞
连接建立TCP+TLS 2-3 RTTTCP+TLS 2-3 RTT1-RTT，支持 0-RTT

HTTP/2 解决了应用层的队头阻塞，但 TCP 层的丢包还是会阻塞所有流。HTTP/3 跑在 UDP 上，真正解决了端到端的多路复用问题。

性能调优关键参数

worker_processes auto;
worker_cpu_affinity auto;
worker_rlimit_nofile 65535;

events {
    worker_connections 10240;
    use epoll;
    multi_accept on;
}

http {
    sendfile on;           # 零拷贝
    tcp_nopush on;         # 合并小包
    tcp_nodelay on;        # 禁用 Nagle
    keepalive_timeout 65;
    keepalive_requests 1000;
}

最大并发 = worker_processes × worker_connections。8 核 10240 = 81920 并发连接，跑静态文件能到 5 万 QPS。

8 个常见坑

我踩过的最狠的坑：worker_connections 没跟上 ulimit

有次大促前压测，Nginx 突然开始报 "too many open files"。查了半天发现 worker_connections 设了 65535，但系统 ulimit -n 才 1024。Nginx 打开文件数超限直接拒连接。改了 worker_rlimit_nofile 65535 和系统 ulimit 才解决。调 worker_connections 之前先看 ulimit -n，这俩必须对齐。

  1. worker_processes 设成 1：单核跑，多核浪费。直接设 auto
  2. 文件描述符不够：报 "too many open files"。worker_rlimit_nofile 要 >= worker_connections
  3. proxy_buffer_size 太小：后端响应头太大时 502。调到 16k
  4. HTTPS 配了弱加密套件：SSL Labs 评分 B。用 TLS 1.2+，ECHDE 套件
  5. client_max_body_size 默认 1m：上传文件 413。按需调大
  6. access_log 不缓冲：高频写盘。加 buffer=32k flush=5s
  7. 没开 sendfile：静态文件性能差一半。sendfile on 零拷贝
  8. upstream 不配 keepalive：每个请求新建后端连接。upstream 里 keepalive 32，location 里 proxy_http_version 1.1 + Connection 空

FAQ

Nginx 为什么比 Apache 快？

不是 Nginx 代码写得好，是架构不同。Apache prefork 每请求一进程，Nginx 单进程 epoll 处理几万连接。内存占用差 10 倍，性能差 10 倍。

worker_connections 设多少？

10240 是常用值。C10K 场景。注意这个值不能超过系统的 ulimit -n（文件描述符限制）。

Nginx 支持 HTTP/3 上游吗？

不支持。Nginx 只终止客户端侧的 HTTP/3，向上游发请求还是 HTTP/1.1 或 HTTP/2。要全链路 HTTP/3 得用 Caddy 或 Envoy。

怎么验证 HTTP/3 生效了？

access log 加 $http3 变量。Chrome 打开 chrome://net-internals/#quic 看域名状态。或者 curl --http3。
