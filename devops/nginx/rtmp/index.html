Nginx 流媒体与四层代理：RTMP、HLS 与 stream 模块

🏷️ Nginx RTMP

谈 Nginx 基本都在谈七层 HTTP，但它还有两块能力很少被提起：官方的 stream 模块能做 TCP 与 UDP 的四层代理，第三方的 rtmp 模块能做直播推流接收与 HLS 切片。主干篇讲的进程模型、请求阶段、location 匹配、代理缓冲那一整套，在这两块里大部分都不适用——因为四层根本不解析应用协议，而 RTMP 走的是完全独立的配置块。这一篇专门补这两块。

stream 模块：四层代理能做什么、不能做什么

维度七层 http四层 stream
是否解析应用协议是，能读能改请求行与头部否，只看得到字节流
路由依据Host、路径、头、Cookie、任意变量只有监听端口，加上 ssl_preread 后可用 SNI 与 ALPN
能否改写能改 URI 与头完全不能
支持的协议HTTP 系列、gRPC、WebSocket、FastCGI任何 TCP 协议，以及 UDP
性能要解析与缓冲，开销较高路径更短，同等硬件吞吐更高，长连接场景差距明显
可观测性状态码、URI、上游耗时全都有只有连接级的字节数与时长，没有状态码可看
健康检查被动摘除（开源版）同样只有被动摘除，补法见本组 ../install/
失败重试可按状态码与错误类型重试只能在建连失败时换下一台，连接建立后无法重试
# stream 与 http 同级，不能写在 http 里面
stream {
    log_format basic '$remote_addr [$time_local] $protocol $status '
                     '$bytes_sent $bytes_received $session_time $upstream_addr';
    access_log /var/log/nginx/stream.log basic;

    # 1. MySQL 只读副本入口：应用只连一个地址，后端可平滑换机器
    upstream mysql_ro {
        least_conn;                       # 长连接场景轮询不均，按连接数更合适
        server 10.0.3.11:3306 max_fails=2 fail_timeout=10s;
        server 10.0.3.12:3306 max_fails=2 fail_timeout=10s;
    }
    server {
        listen 3307;
        proxy_pass mysql_ro;
        proxy_connect_timeout 2s;
        proxy_timeout 300s;               # 四层的空闲超时，默认 10m，别按 HTTP 的直觉配
        # 注意：数据库看到的客户端 IP 是 Nginx 的，除非后端支持 proxy_protocol
        # proxy_protocol on;
    }

    # 2. UDP 转发：DNS 或 syslog
    upstream dns_pool {
        server 223.5.5.5:53;
        server 1.1.1.1:53;
    }
    server {
        listen 53 udp;
        proxy_pass dns_pool;
        proxy_responses 1;                # UDP 无连接，需告知期望几个响应包
        proxy_timeout 3s;
    }
}
典型用途为什么用四层注意
数据库与 Redis 统一入口协议不是 HTTP，七层无能为力后端看到的是 Nginx 的 IP，要真实 IP 得靠 proxy_protocol 且后端支持
TLS 直通不解密、不持有私钥就能分流配 ssl_preread，见下一节
SMTP、IMAP 等长连接协议只需要端口级转发proxy_timeout 要按协议特性放大
UDP 服务（DNS、syslog、游戏）七层完全不支持 UDP必须设 proxy_responses，否则 Nginx 会一直等
Kubernetes 集群外的 apiserver 入口需要 TLS 直通到 apiserver配合 proxy_protocol 才能在审计日志里看到真实来源

ssl_preread：不解密就按 SNI 分流

TLS 握手的第一个报文 ClientHello 是明文的，里面的 SNI 扩展写着客户端要访问哪个域名。ssl_preread 就是只窥探这个报文、取出 SNI 与 ALPN 存进变量，然后把整条连接原样转给对应后端。Nginx 自己不参与加解密，也不需要任何证书和私钥。

sequenceDiagram participant C as 客户端 participant N as Nginx stream 层 participant A as 后端 A 持有 a.com 证书 participant B as 后端 B 持有 b.com 证书 C->>N: TCP 连接到 443 C->>N: ClientHello 明文，SNI 为 b.com Note over N: ssl_preread 只读这一个报文
取出 SNI 存进变量，不解密 N->>B: 建连后把 ClientHello 原样转发过去 B-->>C: 由后端 B 完成 TLS 握手并返回自己的证书 Note over C,B: 之后的加密数据 Nginx 只做字节搬运
看不到任何明文，也看不到 URI 
stream {
    # SNI 到后端的映射；没命中就给一个兜底
    map $ssl_preread_server_name $tls_backend {
        default              127.0.0.1:8443;
        "a.example.com"      10.0.4.11:443;
        "b.example.com"      10.0.4.12:443;
        "~^.+\.k8s\.internal$" 10.0.5.10:6443;
    }

    # 还能按 ALPN 分流：把 gRPC 流量和普通 HTTPS 分开
    map $ssl_preread_alpn_protocols $alpn_backend {
        default        127.0.0.1:8443;
        "~\bh2\b"      10.0.6.10:443;
    }

    server {
        listen 443;
        listen [::]:443;
        ssl_preread on;            # 必须开，否则上面两个变量恒为空
        proxy_pass $tls_backend;
        proxy_connect_timeout 3s;
        proxy_timeout 10m;
        # 后端要拿到真实客户端 IP，就开 proxy_protocol，后端必须同步支持
        proxy_protocol on;
    }
}
💡
什么时候真的需要它

三种情况：一台机器的 443 要同时服务多个由不同团队维护、各自管证书的服务；出于合规要求私钥不能出现在网关上；要把 HTTPS 和 gRPC（ALPN 为 h2）分到不同集群。如果这些都不成立，直接用七层终止 TLS 更好——四层看不到 URI，等于放弃了路径路由、缓存、WAF 和按接口的限流。

RTMP 模块的能力边界与一条直播链路

nginx-rtmp-module 是第三方静态模块，要编译进去（见本组 ../install/）。它做四件事：接收 RTMP 推流、把流转推到别的服务器、录制成 flv 文件、把流转封装成 HLS 或 DASH 切片交给 http 块分发。

# rtmp 块与 http 同级
rtmp {
    server {
        listen 1935;
        chunk_size 4096;                 # RTMP 分块大小，4096 是通用值

        application live {
            live on;
            # 关掉记录，录制单独在 record 块里控制
            record off;

            # 推流鉴权：非 2xx 直接拒绝推流，这是防盗推的唯一有效手段
            on_publish      http://127.0.0.1:8080/rtmp/on_publish;
            on_publish_done http://127.0.0.1:8080/rtmp/on_publish_done;
            # 播放鉴权（拉 RTMP 流时生效；HLS 播放走 http 层的 secure_link）
            on_play         http://127.0.0.1:8080/rtmp/on_play;

            # 转封装成 HLS，不是转码，几乎不耗 CPU
            hls on;
            hls_path /data/hls;
            hls_fragment 2s;             # 单个切片时长，直接决定固有延迟下限
            hls_playlist_length 12s;     # 播放列表保留时长，影响可回看窗口与首屏选择
            hls_fragment_naming system;  # 用系统时间命名，重启后不会覆盖旧切片
            hls_nested on;               # 每路流一个子目录，便于清理与权限控制

            # 转推到备份集群或第三方平台
            push rtmp://backup.internal/live;

            # 拉起 ffmpeg 做多码率转码：注意这只是启动外部进程，
            # 真正的 CPU 消耗在 ffmpeg 上，生产环境应该推到独立的转码机
            # exec ffmpeg -i rtmp://127.0.0.1/live/$name
            #   -c:a copy -c:v libx264 -b:v 1000k -s 854x480
            #   -f flv rtmp://127.0.0.1/live-480p/$name;
        }

        application live-480p {
            live on;
            hls on;
            hls_path /data/hls-480p;
            hls_fragment 2s;
        }
    }
}

http {
    server {
        listen 80;
        server_name live.example.com;

        # m3u8 绝对不能缓存，它每个切片周期都在变
        location /hls/ {
            types {
                application/vnd.apple.mpegurl m3u8;
                video/mp2t ts;
            }
            root /data;
            add_header Cache-Control "no-cache" always;   # 对 m3u8 关键
            add_header Access-Control-Allow-Origin "*" always;  # 播放器跨域取流
        }

        # 切片本身内容不变，可以长缓存
        location ~* \.ts$ {
            root /data;
            expires 1h;
            add_header Cache-Control "public" always;
        }

        # 运行状态页：当前有几路流、每路的码率与客户端数
        location /rtmp-stat {
            rtmp_stat all;
            rtmp_stat_stylesheet stat.xsl;
            allow 10.0.0.0/8;
            deny all;                    # 一定要限制来源，否则流信息全公开
        }
    }
}

直播延迟的构成与量级

环节典型量级能压到多少说明
采集与编码100 到 500ms50ms关掉 B 帧、用 zerolatency 预设能明显降低
推流端缓冲200ms 到 2s100msOBS 的关键帧间隔设成 1 到 2 秒，别用默认的 4 秒
服务端切片等于一个 hls_fragment1s必须收满整片才写文件，这是 HLS 的固有延迟来源
CDN 回源与分发200ms 到 1s200ms首次回源最慢，之后边缘命中
播放器缓冲通常 3 个切片1 个切片减少缓冲片数会显著提高卡顿率，这是延迟与流畅度的直接取舍
端到端合计HLS 切片 4s 时约 15 到 25s切片 1s 时约 4 到 6s再往下就只能换协议

结论很直接：HLS 的延迟被切片时长乘以播放器缓冲片数锁死了，调参数只能在这个框里挪。切片压到 1 秒是常见的下限，再小则文件数与请求数成倍增长，CDN 回源压力、m3u8 刷新频率和卡顿率一起恶化。要真正进入秒级以内必须换协议。

方案典型延迟兼容性适用
HLS，切片 4s15 到 25s最好，所有浏览器与 iOS 原生支持大型赛事、课程回放、对延迟不敏感的分发
HLS，切片 1 到 2s4 到 8s好大多数电商直播的实际选择
HTTP-FLV2 到 4s需播放器支持，iOS 需额外处理自建场景里性价比很高，SRS 与 mediamtx 都支持
LL-HLS2 到 4s较好，需要服务端与播放器都支持分块传输想保留 HLS 生态又要降延迟
SRT回传链路 200 到 800ms主要用于推流回传，不是面向观众的分发协议弱网下的远程制作与素材回传
WebRTC100 到 500ms浏览器原生，但服务端复杂度最高连麦、互动、拍卖、云游戏

鉴权与防盗链

推流地址泄漏导致画面被顶替，是自建直播最常见的事故。仅靠「地址保密」等于没有鉴权，必须做两层：推流侧用 on_publish 回调校验签名，播放侧用 secure_link 给切片 URL 加时效签名。

http {
    # 播放防盗链：URL 形如 /hls/room1/index.m3u8?md5=xxx&expires=1790000000
    # 签名 = base64url( md5( 过期时间 + URI + 客户端 IP + 服务端密钥 ) )
    location /hls/ {
        secure_link          $arg_md5,$arg_expires;
        secure_link_md5      "$arg_expires$uri$remote_addr SERVER_SECRET_CHANGE_ME";

        if ($secure_link = "")  { return 403; }   # 签名不匹配
        if ($secure_link = "0") { return 410; }   # 签名对但已过期

        root /data;
        add_header Cache-Control "no-cache" always;
    }
}
回调触发时机业务侧该做什么返回非 2xx 的效果
on_publish收到推流请求校验流名与签名、检查该房间是否允许开播、标记直播开始拒绝推流，这是防盗推的关键一环
on_publish_done推流断开标记直播结束、触发录制转存、发断流告警无影响，只是通知
on_play有人拉 RTMP 流校验播放凭证、统计在线人数拒绝播放；注意 HLS 播放不走这里
on_record_done录制文件写完把 flv 转 mp4 并上传对象存储无影响
secure_link每次请求 m3u8 或 ts业务侧按用户与房间生成带过期时间的签名403 表示签名错，410 表示已过期
⚠️
签名里带不带客户端 IP 是个取舍

带上 $remote_addr 能防止链接被转发到别处使用，但移动网络切换基站或在 Wi-Fi 与 4G 之间漂移时 IP 会变，正在观看的用户会突然 403。折中做法是只取 IP 的网段部分参与签名，或者干脆不带 IP、把有效期压到几分钟并配合播放器自动续签。

录制、转码与部署边界

必须区分两个词：转封装只是换容器格式（RTMP 流变成 ts 切片），几乎不消耗 CPU；转码要完整解码再重新编码，一路 1080p 软编能吃掉好几个 CPU 核。Nginx RTMP 模块只会转封装，它的 exec 指令做的事情仅仅是拉起一个 ffmpeg 进程。

能力Nginx RTMP 自己能做CPU 开销部署建议
接收推流能低，主要是网络与内存接流层可与 HLS 切片同机
转推到其他服务器能低同上
录制 flv能低，但吃磁盘 IO 与空间录制盘单独挂，别和切片目录抢 IO
转封装成 HLS 或 DASH能低切片目录建议放 tmpfs 或高速盘
转码与多码率不能，靠 ffmpeg极高，一路 1080p 数个核必须独立成转码池，按并发路数容量规划
截图与水印不能中到高同样归入转码池

自建的账很容易算错，因为机器成本只是小头。真正的大头是带宽：一路 3Mbps 的码率，一万人同时看就是 30Gbps 的出口需求，这个量级自己拉专线的单价通常高于云厂商的阶梯价。第二块是转码算力，多码率意味着每路流乘以档位数的 CPU。第三块是运维：断流告警、区域调度、录制转存、鉴权系统、播放质量监控，每一项都要人做。并发小、流数少、或者合规上必须自有机房时自建合理；反之用云服务几乎总是更便宜。

反模式对照

反模式症状正确做法
把四层代理当七层用想按 URL 路径分流，发现根本没有路径可用需要路径路由就用 http 块；四层最多按 SNI 与 ALPN 分
用 HLS 却要求秒级延迟怎么调都下不来，一味压小切片导致大量卡顿接受 HLS 的量级，或换 HTTP-FLV、LL-HLS、WebRTC
推流不做鉴权推流地址泄漏后画面被陌生人顶替on_publish 回调校验带时效的签名
m3u8 被 CDN 缓存播放列表不更新，画面卡在某一刻m3u8 配 no-cache，只让 ts 切片长缓存
转码与接流同机一场直播把 CPU 打满，所有流一起卡，同机业务被拖垮转码独立成池，按并发路数容量规划
UDP 代理不设 proxy_responses会话一直挂着不释放，连接数缓慢增长按协议设期望响应包数与超时
rtmp_stat 不做访问控制所有流名、客户端 IP、码率对外公开allow 内网加 deny all
自建直播不算带宽成本上线后账单远超预期，被迫紧急迁云先按峰值并发乘码率估出口带宽再决策
新项目仍选 nginx-rtmp-module升级 Nginx 时编译失败，缺 WebRTC 与 SRT 能力自建优选 SRS 或 mediamtx
❌
最容易踩的坑
  • stream 块写进了 http 里：两者同级，嵌套会直接报配置错误。
  • 指望四层代理能看到 URI：四层日志里没有状态码也没有路径，出问题时排查手段比七层少一大截。
  • 四层代理后端拿不到真实 IP 就硬查日志：要么开 proxy_protocol 并让后端支持，要么接受只有网关 IP。
  • UDP 代理漏配 proxy_responses：Nginx 一直等后续响应包，会话不释放。
  • ssl_preread 忘记写 on：SNI 变量恒为空，所有流量都落到 default 后端。
  • 把 hls_fragment 设得很大又抱怨延迟高：切片时长直接决定固有延迟下限，4 秒切片端到端二十秒是正常的。
  • 切片压到亚秒级：文件数与请求数爆炸，m3u8 刷新频率翻倍，卡顿率反而上升。
  • m3u8 和 ts 用同一套缓存策略：播放列表被缓存后画面会停在某个时刻不再前进。
  • 只靠推流地址保密当鉴权：地址一泄漏就能被顶播，必须上 on_publish 回调。
  • secure_link 签名里带完整客户端 IP：移动网络换网就 403，正在看的人被踢。
  • 把 exec ffmpeg 当成「Nginx 会转码」：干活的是 ffmpeg，CPU 全算在这台机器上，和接流同机必然互相拖累。
  • HLS 切片目录不做清理：hls_playlist_length 只控制播放列表，历史切片与录制文件会把磁盘写满，必须另配清理任务。
