Nginx 的编译、模块与版本选型

🏷️ Nginx 安装

怎么装 Nginx 看起来是个包管理器的口味问题，其实是被它的模块机制反向决定的。Nginx 的功能几乎全部以模块形式存在，而传统模块必须在 configure 阶段链接进那唯一一个二进制文件，运行期没有任何插件机制。这条约束带来一个非常具体的后果：装完上线才发现少了 GeoIP、少了 Brotli、少了主动健康检查，不是装个扩展包就能补上的，而是要重新编译、重新替换二进制、重新走一次发布。所以安装方式的选择，本质上是在赌「以后还会不会需要新模块」。

本篇只讲构建期与部署期的事：模块形态、四条安装路线、第三方模块清单、configure 参数、TLS 库选择、不停机换二进制。运行期的 master/worker 进程模型、11 个请求处理阶段与 location 匹配优先级、代理缓冲与超时参数全景，都在 ../ 主干篇里，这里不重复。

模块的三种形态决定了改动成本

flowchart TB subgraph CORE["核心层：无法裁剪"] C1["ngx_core / ngx_conf"] C2["事件模块 epoll / kqueue"] end subgraph DEFAULT["默认就编译进去的 HTTP 模块"] D1["http_core / http_rewrite"] D2["http_proxy / http_upstream"] D3["http_gzip / http_log / http_headers"] end subgraph OPTIN["必须显式 with 开启，否则没有"] O1["http_ssl_module"] O2["http_v2_module / http_v3_module"] O3["http_realip_module"] O4["http_auth_request_module"] O5["stream 四层代理"] end subgraph THIRD["第三方与动态模块"] T1["add-module：静态链接进二进制"] T2["add-dynamic-module：产出 so"] T3["load_module 启动时加载"] end CORE --> DEFAULT DEFAULT --> OPTIN OPTIN --> THIRD T2 --> T3

最容易踩的一类事故是「以为默认就有」。--with-http_ssl_module、--with-http_realip_module、--with-http_auth_request_module、--with-stream 全都不是默认开启的；源码编译时漏一个，等到要上 HTTPS 或者要做子请求鉴权时才发现，只能重来。反过来，gzip、rewrite、proxy 是默认就在的，不需要专门加参数。

模块形态加入时机后期增加的代价版本约束典型例子
默认静态模块编译期自动带上无需操心无rewrite、proxy、gzip、log
可选静态模块编译期 --with-xxx重新编译并替换二进制无ssl、v2、v3、realip、stream
第三方静态模块编译期 --add-module重新编译，还要盯第三方是否适配新版模块源码要兼容该版本内部 APIvts、substitutions_filter
动态模块编译期 --add-dynamic-module，启动时 load_module只替换 so 并重启，不动主二进制1.9.11 起支持；so 必须与主二进制同版本同参数brotli、geoip2、image_filter
⚠️
动态模块不是「通用插件」

动态模块只解决了「不必重编主二进制」，没解决二进制兼容。so 必须用完全相同的 Nginx 版本号和几乎相同的 configure 参数编译，否则启动直接报 module ... is not binary compatible。这也是为什么升级 Nginx 小版本时，所有第三方动态模块都要跟着重编一遍——发行版把它们打成独立的 nginx-module-* 包并做版本绑定，就是为了自动处理这件事。

我的默认建议是：先用官方仓库，需要第三方模块再转自编译。发行版仓库的问题不只是旧，而是「旧得让你用不上新特性」——比如 1.25.1 才把 HTTP/2 改成独立的 http2 on; 指令，1.25.0 起才有可用的 HTTP/3，Debian 或 CentOS 仓库里的老版本连这些配置都解析不了。

分支包含内容发布节奏什么时候选它
mainline新特性、所有 bug 修复、性能改进一到两个月一个版本官方推荐的默认选择，新部署直接用
stable只回合严重 bug 与安全修复，不合并新特性，也不合并大多数普通修复一年一个分支，期间只出补丁版依赖的第三方模块只适配了旧 API，或内部有强制的版本冻结要求

很多人把 stable 理解成「更稳」，这是个流传很广的误解。Nginx 的 stable 更接近「冻结的功能集」，它的普通 bug 修复反而比 mainline 少得多。真正的稳定性来自你自己的灰度流程：固定版本号、先在小流量集群跑一周、再全量替换。

常用第三方模块清单

模块解决什么问题形态注意点
ngx_http_geoip2_module按 IP 查国家、省份、ASN，做地域路由、地域限流、风控打标动态依赖 libmaxminddb 与 mmdb 库文件，mmdb 要定期更新；老的 GeoIP1 模块已随数据库停更而废弃
ngx_brotliBrotli 压缩，同等 CPU 下比 gzip 小 15% 到 20%，还支持 brotli_static 直接发 br 文件动态需要 brotli 库源码；对不支持 br 的老客户端要保留 gzip 兜底
nginx-module-vts按 server、upstream、缓存区维度输出流量与状态码指标，弥补 stub_status 只有几个连接数的不足静态指标存共享内存，要配 vhost_traffic_status_zone；暴露端点必须做访问控制
headers-more-nginx-module能删除和改写请求头与响应头，原生 add_header 只能加不能删静态清理后端泄漏的 Server、X-Powered-By 时很好用
ngx_http_substitutions_filter_module在响应体里做正则替换，比原生 sub_filter 强（支持正则与多行）静态会破坏流式响应并吃 CPU，只在改不了后端时用
nginx_upstream_check_module给 upstream 加主动健康检查，主干篇说的开源版只有被动检查，这就是补法静态，需打补丁与主线版本适配滞后，升级 Nginx 时最容易卡在这个模块上
lua-nginx-module让配置具备可编程能力静态自己编容易踩依赖，直接用 OpenResty 更省事

OpenResty：什么时候值得换

OpenResty 不是 Nginx 的分支，而是 Nginx 加 LuaJIT 加一批成熟 Lua 库的打包发行版。它的价值在于把 Nginx 从「配置驱动」变成「可编程」：在 access_by_lua_block 里查 Redis 判断 token，在 balancer_by_lua_block 里动态挑上游而不需要 reload，在 content_by_lua_block 里直接返回聚合结果。

换 OpenResty 的收益对应的代价
上游列表可动态变更，不需要 reload共享内存与 Lua 状态成为新的故障点，排查要会 Lua 栈
鉴权、限流、灰度逻辑能写成代码，条件表达能力远超 if 与 map任何阻塞调用都会卡死整个 worker，必须全程用 cosocket 版本的库，禁用 os.execute、阻塞式 MySQL 驱动、同步文件读
能在网关做 WAF、签名校验、协议改写CPU 密集逻辑写在 Lua 里会直接拉高 P99，正则与 JSON 解析尤其明显
生态成熟，有 lua-resty 系列库版本跟随滞后，新 Nginx 特性要等 OpenResty 发版

源码编译的完整流程

# 依赖：正则、压缩、TLS。Debian 系
apt install -y build-essential libpcre2-dev zlib1g-dev
# 取 mainline 源码，版本号固定写死，方便复现
cd /usr/local/src
wget https://nginx.org/download/nginx-1.30.1.tar.gz
tar -zxf nginx-1.30.1.tar.gz

# 第三方模块源码先备好
git clone --recursive https://github.com/google/ngx_brotli.git
git clone https://github.com/vozlt/nginx-module-vts.git

cd nginx-1.30.1
./configure \
  --prefix=/usr/local/nginx \
  --sbin-path=/usr/sbin/nginx \
  --conf-path=/etc/nginx/nginx.conf \
  --pid-path=/var/run/nginx.pid \
  --error-log-path=/var/log/nginx/error.log \
  --http-log-path=/var/log/nginx/access.log \
  --user=nginx --group=nginx \
  --with-http_ssl_module \
  --with-http_v2_module \
  --with-http_v3_module \
  --with-http_realip_module \
  --with-http_auth_request_module \
  --with-http_gzip_static_module \
  --with-http_stub_status_module \
  --with-http_sub_module \
  --with-stream \
  --with-stream_ssl_module \
  --with-stream_ssl_preread_module \
  --with-threads \
  --with-file-aio \
  --with-openssl=/usr/local/src/openssl-3.5.0 \
  --add-module=/usr/local/src/nginx-module-vts \
  --add-dynamic-module=/usr/local/src/ngx_brotli

make -j"$(nproc)"
# 首次安装用 make install；升级场景不要用它覆盖配置，见下一节
make install

# 把编译参数存档，这是能否复现的关键
/usr/sbin/nginx -V 2>&1 | tee /etc/nginx/BUILD-ARGS.txt
参数作用不加会怎样
--prefix安装根目录，其余相对路径都基于它默认落到 /usr/local/nginx，与发行版布局不一致
--sbin-path二进制位置，平滑升级要替换的就是这个文件平滑升级脚本找不到该覆盖哪个文件
--pid-pathpid 文件位置，USR2 升级依赖它生成 .oldbin信号发不到正确的 master
--user / --groupworker 降权身份；master 仍以 root 启动才能绑 80 与 443默认 nobody，静态文件权限容易配错
--with-http_ssl_moduleHTTPS 能力ssl_certificate 直接报未知指令
--with-http_v2_moduleHTTP/2http2 on 无法识别
--with-http_realip_module从 X-Forwarded-For 还原真实客户端 IP日志与限流看到的全是前置 LB 的 IP
--with-http_auth_request_module子请求鉴权auth_request 不可用
--with-threads线程池，配合 aio threads 把磁盘读卸载出事件循环大文件冷读会阻塞 worker
--with-file-aio异步文件 IO，配合 directio 服务大文件aio on 无效
--with-stream 系列四层代理与按 SNI 分流stream 块无法解析，见本组 ../rtmp/
--with-openssl=DIR指定 TLS 库源码，决定协议上限用系统 OpenSSL，版本可能不支持 TLS 1.3 或 QUIC
TLS 库TLS 1.3QUIC 与 HTTP/3说明
OpenSSL 1.0.2 及更早不支持不支持配了 TLSv1.3 也静默无效，别指望它
OpenSSL 1.1.1支持不支持很多老发行版停在这里
OpenSSL 3.0 至 3.4支持只有客户端方向，服务端不可用编 v3 模块能过，但跑不起来
OpenSSL 3.5 及以上支持支持当前自编译 HTTP/3 的主流选择
BoringSSL / quictls支持支持QUIC 支持最早，但 API 不稳定，需跟着上游走

排查 TLS 问题时记住：nginx -V 输出里的 built with OpenSSL x.y.z 是编译期链接的版本，和系统 openssl version 可能完全不同。静态链接自编译的 OpenSSL 时，系统升级 OpenSSL 补丁并不会修掉你 Nginx 里的漏洞，必须重编。

平滑升级：不停机换二进制

这是 Nginx 很少被用到但非常实用的能力：在不断开任何连接的前提下把可执行文件换掉。原理是新旧两代 master 共享同一批已经 bind 的监听 socket，通过环境变量 NGINX 传递 fd 列表，所以升级期间新旧版本同时在处理请求。

stateDiagram-v2 [*] --> Running: 旧 master 加旧 worker 正常服务 Running --> TwoGen: 覆盖新二进制后发 USR2 note right of TwoGen pid 文件改名为 nginx.pid.oldbin 新 master 用新二进制启动新 worker 两代进程共享同一批监听 fd end note TwoGen --> Draining: 给旧 master 发 WINCH note right of Draining 旧 worker 不再接受新连接 处理完在途请求后退出 旧 master 仍然活着，可随时回滚 end note Draining --> NewOnly: 观察通过后给旧 master 发 QUIT NewOnly --> [*]: 升级完成，删除 oldbin Draining --> Rollback: 发现异常 TwoGen --> Rollback: 发现异常 Rollback --> Running: 给旧 master 发 HUP 重拉 worker
再 QUIT 掉新 master 
OLD=$(cat /var/run/nginx.pid)

# 0. 备份旧二进制，覆盖新二进制到 sbin-path 指向的同一路径
cp -a /usr/sbin/nginx /usr/sbin/nginx.old
cp -a /usr/local/src/nginx-1.30.1/objs/nginx /usr/sbin/nginx
/usr/sbin/nginx -t          # 新二进制解析现有配置，必须先过

# 1. 拉起第二代 master：旧 pid 文件被改名为 nginx.pid.oldbin
kill -USR2 "$OLD"
sleep 2
ls /var/run/nginx.pid /var/run/nginx.pid.oldbin
ps -ef | grep 'nginx: master'   # 应当看到两个 master

# 2. 让旧 worker 优雅退出，此时流量全部由新版本承接
kill -WINCH "$OLD"
# 观察窗口：错误日志、5xx 比例、上游耗时，建议至少几分钟
tail -f /var/log/nginx/error.log

# 3a. 一切正常，终结旧 master
kill -QUIT "$OLD"
rm -f /usr/sbin/nginx.old

# 3b. 如果异常，回滚：旧 master 重新拉起 worker，再干掉新 master
# kill -HUP "$OLD"
# kill -QUIT "$(cat /var/run/nginx.pid)"
# cp -a /usr/sbin/nginx.old /usr/sbin/nginx
信号等价命令行为回滚点
HUPnginx -s reload重读配置，启新 worker，旧 worker 优雅退出配置错误时 reload 会失败但老配置继续服务
USR2无用当前 sbin-path 的二进制启动新 master此时两代并存，最安全的观察窗口
WINCH无优雅关闭本代 worker，master 保留旧 master 还能用 HUP 复活
QUITnginx -s quit优雅退出（等在途请求处理完）发完就没有回滚余地
TERMnginx -s stop立即退出，直接断连接生产环境不要用
USR1nginx -s reopen重新打开日志文件，日志轮转必用详见本组 ../http/
💡
用 systemd 管理时的注意点

官方包的 unit 文件把 ExecReload 指向 nginx -s reload，但平滑升级的 USR2 流程会让 systemd 跟踪的主 PID 失效：新 master 不是 systemd 拉起来的子进程。自建 unit 要么用 Type=forking 加 PIDFile 并接受升级后需要 systemctl daemon-reload 的现实，要么干脆在容器化场景放弃平滑升级——K8s 里正确做法是滚动更新 Pod，而不是在容器内换二进制。

配置目录规范与三个检查命令

两种主流布局：Debian 系的 sites-available 加 sites-enabled 软链，和官方包的 conf.d/*.conf 平铺。前者能「下线一个站点但保留配置」，后者更简单、更适合用配置管理工具全量渲染。混用两套是最糟的选择，因为 include 顺序一乱，default_server 落到哪个 server 就说不清了。

# /etc/nginx/nginx.conf 的骨架
# 动态模块必须在最顶层、events 之前加载，写在 http 块里会报错
load_module modules/ngx_http_brotli_filter_module.so;
load_module modules/ngx_http_brotli_static_module.so;

user  nginx;
worker_processes auto;
error_log /var/log/nginx/error.log warn;
pid       /var/run/nginx.pid;

events { worker_connections 10240; }

http {
    include /etc/nginx/mime.types;
    default_type application/octet-stream;

    # 顺序有讲究：公共片段先 include，站点配置后 include，
    # 这样站点里的同名指令才能覆盖公共默认值
    include /etc/nginx/common/*.conf;
    include /etc/nginx/conf.d/*.conf;
}

# stream 块与 http 同级，不能嵌在 http 里
stream {
    include /etc/nginx/stream.d/*.conf;
}
命令输出什么时候用
nginx -t只报语法是否通过每次 reload 前，必须
nginx -T检查语法并打印展开所有 include 之后的完整配置排查「我明明改了却不生效」，或想知道某指令最终落在哪个 server
nginx -V版本、编译器、TLS 库、全部 configure 参数确认模块有没有编进去，复现构建环境
nginx -t -c /path/new.conf校验指定文件灰度新配置，不覆盖线上文件

反模式对照

反模式会发生什么正确做法
用发行版老版本，却要上 HTTP/3 或新 http2 on 语法配置报未知指令，或 TLS 1.3 静默不生效官方仓库装 mainline，或自编译并选对 TLS 库
上线后才发现缺模块要重新编译加发布，紧急场景下最容易出错编译时把 realip、auth_request、stream、v2 一次带齐
编译参数没存档半年后升级时无法复现，动态模块也编不出兼容的 songinx -V 输出入版本库，或直接用 Dockerfile 固化
升级用 systemctl stop 再 start期间连接全断，长连接与上传请求直接失败走 USR2 / WINCH / QUIT 平滑升级
不跑 nginx -t 直接 reload语法错时 reload 失败（老配置还在跑，但你以为已生效）nginx -t && nginx -s reload 写成一条
升级 Nginx 不重编第三方动态模块启动报 not binary compatible，服务起不来把主二进制与所有 so 作为一个整体版本发布
自编译静态链接 OpenSSL 后靠系统更新修漏洞漏洞一直在，扫描工具还报「已修复」把 TLS 库版本纳入自己的重编流水线
❌
最容易踩的坑
  • 以为 ssl 默认编译进去了：源码编译漏 --with-http_ssl_module，等到配证书才发现，只能重编。
  • 动态模块跨版本复用：拿 1.28 编的 so 给 1.30 用，启动直接失败，报 not binary compatible。
  • load_module 写进 http 块：它只能出现在配置文件最顶层且在 events 之前，位置错了报 unknown directive。
  • 把 stable 当成「更可靠」：stable 不合并新特性也不合并多数普通修复，官方自己推荐 mainline。
  • 平滑升级时新二进制没放到 --sbin-path 的路径：USR2 拉起来的还是旧版本，看日志以为升级成功了。
  • 发完 WINCH 就直接 QUIT 旧 master：放弃了唯一的回滚点，新版本出问题只能重启。
  • 用 make install 做升级：会覆盖 conf 和 html 目录里的文件，线上配置可能被默认配置顶掉。
  • 忘了记录 nginx -V：换人接手或换机器重建时参数全靠猜，动态模块再也编不出兼容版本。
  • 混用 sites-enabled 与 conf.d：include 顺序不确定，default_server 归属和同名 server 的覆盖关系变得无法推理。
  • OpenSSL 版本不够却配 HTTP/3：3.0 到 3.4 只有 QUIC 客户端接口，编译能过但服务端跑不起来。
  • 在 OpenResty 里用阻塞库：一个同步 MySQL 查询或 os.execute 就能让整个 worker 的所有连接一起卡住。
  • 指望开源版有主动健康检查：原生只有被动摘除，要主动探测得上 nginx_upstream_check_module、OpenResty 健康检查库，或把成员列表交给服务发现。
