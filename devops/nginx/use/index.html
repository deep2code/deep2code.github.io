Nginx 常用技巧：从实际问题出发

🏷️ Nginx 实战

你写了个网站，跑在 8080 端口。现在来了几个问题：

  • 用户要在网址后面加 :8080 才能访问，能不能直接用域名？
  • 网站访问的人多了，一台服务器扛不住，怎么办？
  • 用户上传的图片太大，打开很慢，能不能自动缩小？
  • 晚上想偷偷上线新版本，不想让用户看到报错的页面，怎么办？

这些问题，Nginx 全能解决。这篇文章不讲理论，就讲你真的会遇到的问题，以及怎么配。

场景一：用户访问你的网站，要加 :8080 才打得开

你遇到的问题

你用 Node.js / Python 写了个网站，跑在 8080 端口。用户输入 www.example.com，浏览器默认找 80 端口，结果连不上，必须加 :8080 才行。这也太不专业了。

Nginx 怎么解决？让 Nginx 监听 80 端口，把请求转发给你跑在 8080 的后端。用户只知道访问 www.example.com，根本不知道后面还有个 8080 的服务。这就是反向代理。

flowchart LR U[用户浏览器] -->|访问 www.example.com| N[Nginx
监听 80 端口] N -->|转发请求| B[你的后端
Node.js / Python
跑在 8080] style N fill:#e3f2fd 
server {
    listen 80;
    server_name www.example.com;

    location / {
        proxy_pass http://127.0.0.1:8080;
    }
}

就这么简单。现在用户直接输入 www.example.com 就能访问你的网站了，不用加端口号。

场景二：访问的人突然多了，一台服务器扛不住了

你遇到的问题

你的网站火了，同时在线的人从 100 涨到了 1000。你的服务器 CPU 100%，请求开始超时，用户开始骂。你加了一台服务器，但怎么让两台服务器一起干活？

Nginx 怎么解决？把两台服务器都放到 Nginx 后面，Nginx 自动把请求分给两台服务器，这就是负载均衡。用户根本不知道有几台服务器，只知道网站变快了。

upstream myapp {
    # 两台服务器，按权重分流量
    server 10.0.0.1:8080 weight=3;  # 性能好的，多分点
    server 10.0.0.2:8080 weight=1;  # 性能差点的，少分点
}

server {
    listen 80;
    server_name www.example.com;

    location / {
        proxy_pass http://myapp;
    }
}
分配方式什么时候用
轮询（默认）两台服务器性能差不多
加权轮询（weight=）服务器性能不一样，性能好的多分点
ip_hash同一个用户的请求总是打到同一台服务器（比如有登录状态）

场景三：浏览器提示"不安全"，SEO 排名也上不去

你遇到的问题

你的网站还是 HTTP，浏览器地址栏旁边有个"不安全"的提示。用户一看就不敢用了，搜索引擎也把你的排名往下压。你想换成 HTTPS，但不想改后端代码。

Nginx 怎么解决？SSL 证书只放在 Nginx 上，后端还是用 HTTP。用户和 Nginx 之间是加密的，Nginx 和后端之间是内网，不用加密。这就是SSL 终止，后端代码一行都不用改。

server {
    listen 80;
    server_name www.example.com;
    # HTTP 自动跳转到 HTTPS
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl http2;
    server_name www.example.com;

    ssl_certificate     /path/to/fullchain.pem;
    ssl_certificate_key /path/to/privkey.pem;

    location / {
        proxy_pass http://127.0.0.1:8080;
    }
}

现在用户输入 www.example.com，自动跳转到 https://www.example.com，浏览器也不提示不安全了。后端还是跑在 8080，啥都不用改。

场景四：用户上传的图片太大，打开很慢

你遇到的问题

用户上传了几张 5MB 的原图，手机用户打开页面要等 10 秒，都跑光了。你想把图片自动缩小成 800px 宽，再发给用户，但你不想写图片处理的代码，也不想存两份图片。

Nginx 怎么解决？用 Nginx 的 image_filter 模块，自动把大图缩小成小图，用户访问的时候才生成，还能缓存。不用改后端，不用存两份文件。

location ~* /uploads/.*_small\.(jpg|png)$ {
    alias /path/to/uploads/;
    image_filter resize 800 -;  # 宽度800，高度自动
    image_filter_jpeg_quality 85;
    image_filter_buffer 10M;

    # 缓存生成的小图
    expires 7d;
}

用户访问 /uploads/photo.jpg 就是原图，访问 /uploads/photo_small.jpg 就是自动缩小到 800px 宽的小图。手机端用小图，PC 端用原图，完美。

场景五：晚上想偷偷上线新版本，不想让用户看到报错

你遇到的问题

你想上线新版本，但万一新版本有 bug 怎么办？用户正在付钱的时候你更新了，页面报错了，用户就跑了。你想先让 10% 的用户用新版本，没问题再全量上线。

Nginx 怎么解决？这就是灰度发布（也叫金丝雀发布）。Nginx 按比例把流量分给旧版本和新版本，出问题随时切回去。

upstream app_old {
    server 10.0.0.1:8080;  # 旧版本
}
upstream app_new {
    server 10.0.0.2:8080;  # 新版本
}

server {
    listen 80;
    server_name www.example.com;

    # 10% 的用户访问新版本
    split_clients "$remote_addr$request_id" $app {
        10%     app_new;
        *       app_old;
    }

    location / {
        proxy_pass http://$app;
    }
}

现在 90% 的用户还是用旧版本，10% 的"幸运儿"用新版本。观察几天没问题，把比例调到 100% 就全量上线了。出问题？改回 0%，1 分钟切回旧版本。

场景六：CSS、JS、图片太多，后端服务器扛不住了

你遇到的问题

你的网站有 100 个 JS 文件，每个用户打开要加载 2MB 的静态资源。你的后端服务器既要处理动态请求，又要发静态文件，CPU 全花在发文件上了，动态请求反而变慢了。

Nginx 怎么解决？静态文件直接让 Nginx 发，根本不经过后端。Nginx 发静态文件比后端快 10 倍，还能开 gzip 压缩。

server {
    listen 80;
    server_name www.example.com;

    # 静态文件，直接让 Nginx 发
    location /static/ {
        root /path/to/your/project;
        expires 30d;  # 缓存30天
        add_header Cache-Control "public, immutable";
    }

    # 动态请求，才转发给后端
    location / {
        proxy_pass http://127.0.0.1:8080;
    }
}

现在 CSS、JS、图片都由 Nginx 直接发，后端只处理登录、下单这些动态请求，服务器压力瞬间小了一大半。

场景七：有人恶意爬你的网站，把你服务器流量跑满了

你遇到的问题

你发现日志里有个 IP 每秒请求 100 次，在爬你的商品数据，服务器带宽都被他一个人占了。你想封掉他，但不想一个个封 IP。

Nginx 怎么解决？用 limit_req 模块，限制每个 IP 的请求频率，超过的直接拒绝。

http {
    # 定义限流区域：每个IP最多每秒10个请求
    limit_req_zone $binary_remote_addr zone=api_limit:10m rate=10r/s;

    server {
        location /api/ {
            limit_req zone=api_limit burst=20 nodelay;
            # 超过频率的，返回429错误
            limit_req_status 429;

            proxy_pass http://backend;
        }
    }
}

现在普通用户正常访问没问题，爬虫一秒钟发 100 个请求？直接被拒绝。不用改后端，Nginx 直接帮你挡掉了。

场景八：想测试两个版本的页面，哪个转化率更高

你遇到的问题

你做了两个版本的首页，一个是红色按钮，一个是绿色按钮。你不知道哪个点击量更高，想让一半用户看红色，一半看绿色，统计一下数据。

Nginx 怎么解决？和灰度发布类似，Nginx 把请求分成两组，分别转发给两个版本的后端。

upstream app_red {
    server 10.0.0.1:8080;  # 红色按钮版本
}
upstream app_green {
    server 10.0.0.2:8080;  # 绿色按钮版本
}

server {
    listen 80;
    server_name www.example.com;

    # 按用户ID哈希，同一个用户总是看到同一个版本
    split_clients "$cookie_user_id" $app_version {
        50%     app_red;
        *       app_green;
    }

    location / {
        proxy_pass http://$app_version;
    }
}

现在 50% 的用户看红色按钮，50% 看绿色按钮。统计一周数据，哪个转化率高就用哪个。

场景九：网站要维护，想给用户看个友好的提示

你遇到的问题

你要更新数据库，预计 10 分钟。用户现在访问的话，会看到一堆报错的页面，体验很差。你想显示一个"网站维护中，10分钟后回来"的页面。

Nginx 怎么解决？一个 maintenance 开关就行，不用改后端代码。

server {
    listen 80;
    server_name www.example.com;

    # 维护开关：存在 maintenance.html 就显示维护页面
    if (-f $document_root/maintenance.html) {
        return 503;
    }

    error_page 503 /maintenance.html;
    location = /maintenance.html {
        root /path/to/your/project;
    }

    location / {
        proxy_pass http://127.0.0.1:8080;
    }
}

维护的时候，在项目根目录放一个 maintenance.html 文件，所有用户访问都看到"网站维护中"。维护完了，删掉这个文件，自动恢复正常。

常用配置参数速查

参数作用什么时候用
proxy_pass把请求转发给后端反向代理
upstream定义一组后端服务器负载均衡
server_name匹配域名一个 Nginx 跑多个网站
location匹配 URL 路径不同路径用不同处理方式
gzip on开启压缩减少传输体积，加快加载
expires 30d设置缓存静态文件让浏览器缓存
limit_req限流防止恶意爬虫
return 301永久跳转HTTP 跳 HTTPS
新手最容易踩的坑
  • 改完配置一定要测试：nginx -t 测试语法，没问题再 nginx -s reload 重载。改坏了网站就挂了。
  • 静态文件 location 要放在前面：Nginx 是按优先级匹配的，把 location /static/ 放在 location / 前面。
  • gzip 不要压图片视频：图片视频本身已经是压缩格式了，再压只会浪费 CPU。
  • 不要把 access_log 放在 RAM 盘：日志很大，放系统盘就行，别放内存盘把内存占满了。
