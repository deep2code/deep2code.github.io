Nginx 常用技巧

🏷️ Nginx 实战

反向代理：Nginx 最核心的用法

Nginx 做反向代理，说白了就是客户端以为自己在跟服务器说话，实际上 Nginx 在中间把请求转发给后端。我用得最多的配置就是这个。

flowchart LR CLIENT[客户端] -->|HTTP| NGINX[Nginx] NGINX -->|proxy_pass| APP1[后端应用 1] NGINX -->|proxy_pass| APP2[后端应用 2] NGINX -->|proxy_pass| APP3[后端应用 3] style NGINX fill:#e3f2fd 
upstream backend {
    server 10.0.0.1:8080 weight=3;
    server 10.0.0.2:8080 weight=2;
    keepalive 32;  # 复用后端连接
}

server {
    listen 443 ssl http2;
    server_name example.com;

    location / {
        proxy_pass http://backend;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_http_version 1.1;
        proxy_set_header Connection "";  # 必须，否则 keepalive 不生效
    }
}

正向代理 vs 反向代理

正向代理反向代理
代理谁代理客户端代理服务端
客户端知道吗知道（手动配代理）不知道（以为 Nginx 就是服务器）
典型用途翻墙、访问控制负载均衡、SSL 终止
Nginx 支持1.31.0+ 内置原生支持

HTTP 跳转 HTTPS

server {
    listen 80;
    server_name example.com;
    return 301 https://$host$request_uri;
}

用 $host 而不是 $server_name，因为 $host 是客户端请求的原始域名，泛域名场景不会出问题。

gzip 压缩

gzip on;
gzip_vary on;
gzip_comp_level 6;  # 默认就是6，性价比最高
gzip_min_length 1024;  # 小于1KB不压
gzip_types text/plain text/css application/json
           application/javascript text/xml image/svg+xml;
gzip_comp_level 的坑

level 1 到 9，level 6 是性价比拐点。从 6 到 9，压缩率只多 2%，但 CPU 翻三倍。别图省带宽把 CPU 吃满。图片视频已经是压缩格式了，不要再 gzip。

location 匹配：最容易搞混的部分

flowchart TD A[请求进来] --> B{= 精确匹配？} B -- 是 --> C[立即用这个 location] B -- 否 --> D{^~ 前缀匹配？} D -- 是 --> E[用最长前缀匹配] D -- 否 --> F{正则 ~ ~* 匹配？} F -- 第一个匹配 --> G[用正则 location] F -- 都不匹配 --> E style A fill:#e3f2fd

优先级：=（精确）> ^~（前缀优先）> ~/~*（正则，按顺序）> 无前缀（最长匹配）。

# 这些写法的区别
location = /favicon.ico { ... }     # 精确匹配，只匹配 /favicon.ico
location ^~ /static/ { ... }       # 前缀匹配，匹配到就不再检查正则
location ~ \.php$ { ... }           # 正则匹配，区分大小写
location ~* \.jpg$ { ... }          # 正则匹配，不区分大小写
location /api/ { ... }              # 普通前缀，最长匹配胜出

root 和 alias 的区别

这个我每次都要查一遍。简单说：

rootalias
行为完整路径拼到 root 后面替换 location 前缀
请求 /abc/123 + root /var/www找 /var/www/abc/123—
请求 /abc/123 + alias /var/www—找 /var/www/123

限流和连接数控制

# 限流：每个 IP 每秒 10 个请求
limit_req_zone $binary_remote_addr zone=api:10m rate=10r/s;

# 限连接：每个 IP 最多 20 个并发
limit_conn_zone $binary_remote_addr zone=conn:10m;

location /api {
    limit_req zone=api burst=20 nodelay;
    limit_conn conn 20;
    proxy_pass http://backend;
}

burst=20 意思是允许瞬间多过 20 个请求排队。nodelay 表示不排队，直接处理。不加 nodelay 的话，突发请求会排队等待，客户端感觉就是卡顿。

流量镜像

location / {
    mirror /mirror;
    proxy_pass http://production;
}

location = /mirror {
    internal;
    proxy_pass http://test_backend$request_uri;
}

mirror 把生产流量复制一份到测试环境，用来做灰度验证。回包被忽略，不影响主请求。我做过全链路压测的影子流量，用这个方法把生产流量 1:1 复制到预发环境。

WebSocket 代理

location /ws {
    proxy_pass http://backend;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_read_timeout 3600s;  # WebSocket 长连接，默认60s会断
}
WebSocket 超时的坑

我刚开始配 WebSocket，连上之后每隔 60 秒就断一次。查了半天发现是 proxy_read_timeout 默认 60 秒。WebSocket 是长连接，如果 60 秒内没有数据传输，Nginx 就把连接关了。设成 3600 秒就好。

gRPC 代理

location /greeter.Greeter {
    grpc_pass grpc://grpc-backend:50051;
    grpc_set_header X-Real-IP $remote_addr;
}

gRPC 基于 HTTP/2，Nginx 从 1.13.6 开始原生支持 grpc_pass。注意后端必须是 HTTP/2。

HTTP/3 配置（纠正版）

server {
    listen 443 ssl;                # TCP：HTTP/1.1 + HTTP/2
    listen 443 quic reuseport;     # UDP：HTTP/3
    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_early_data on;             # 0-RTT
    quic_retry on;                 # 地址验证
    add_header Alt-Svc 'h3=":443"; ma=86400';  # 告诉浏览器支持h3
}

没有 http3 on; 这个指令。网上很多教程写错了。启用 HTTP/3 靠的是 listen 的 quic 参数。

8 个配置坑

  1. location 匹配顺序搞错：以为按配置顺序匹配，实际是按优先级。正则 location 一定要从具体到通用排列
  2. rewrite 无限循环：用 last 会重新匹配 location，如果新 URI 又匹配到同一个 rewrite 规则，循环 10 次后 500
  3. proxy_pass 带不带 URI：带 URI 会替换 location 前缀，不带则完整转发。搞混了后端收到的路径就错了
  4. HTTPS 证书链不完整：只配了服务器证书，没配中间证书，部分浏览器报"证书不受信任"。用 fullchain.pem
  5. gzip 压图片：图片视频已经是压缩格式，再 gzip 纯浪费 CPU
  6. 静态资源缓存策略不对：HTML 不该长缓存，带 hash 的 JS/CSS 可以永久缓存。更新了用户还看到旧版就是这个原因
  7. client_max_body_size 太小：默认 1m，上传文件报 413。按需调大
  8. 暴露 Nginx 版本号：响应头 Server: nginx/1.24.0，攻击者知道你版本就能找漏洞。server_tokens off;

有创意的高级玩法

灰度发布 / 蓝绿部署

用 Nginx 做流量切分，按比例把新版本放出去。我做过 1% → 10% → 50% → 100% 的灰度流程，出问题秒回滚。

upstream v1 {
    server 10.0.0.1:8080;
    server 10.0.0.2:8080;
}
upstream v2 {
    server 10.0.0.3:8080;  # 新版本
    server 10.0.0.4:8080;
}

server {
    location / {
        # 90% 走 v1，10% 走 v2
        set $group "v1";
        if ($request_uri ~* "/new-feature/") { set $group "v2"; }
        proxy_pass http://$group;
    }
}
按 Cookie 灰度

更精细的做法：把命中灰度的用户种一个 cookie，下次还走新版本。这样用户体验一致，不会一会新一会旧。

A/B 测试分流

# 按 User-Agent 或 Cookie 分流
split_clients "$http_user_agent$request_id" $variant {
    50.0%    A;
    50.0%    B;
}

location / {
    proxy_pass http://backend_$variant;
    add_header X-Experiment $variant;  # 告诉前端走的哪个版本
}

图片动态处理

装了 nginx-image-filter 模块之后，Nginx 直接在传输中裁剪、压缩、转 WebP。不用后端介入，前端请求 /img/test.jpg!w800 自动出 800px 宽的图。

location ~* ^/img/(.*)!w(\d+)$ {
    image_filter resize $2 -;
    image_filter_jpeg_quality 85;
    root /var/www/images;
}

接口 Mock / 调试

前端联调时，后端接口没好，Nginx 直接返回 mock 数据：

location /api/user/ {
    # 后端没好之前，先返回假数据
    default_type application/json;
    return 200 '{"id":1,"name":"测试用户","email":"test@example.com"}';
}

静态资源 hash 缓存策略

带 hash 的 JS/CSS 永久缓存，HTML 不缓存，解决"更新了用户还看到旧版"的问题：

# 带 hash 的静态资源永久缓存
location ~* \.(js|css|png|jpg|webp|woff2?)$ {
    expires 1y;
    add_header Cache-Control "public, immutable";
}

# HTML 不缓存，每次都拉最新
location ~* \.html$ {
    expires -1;
    add_header Cache-Control "no-cache, must-revalidate";
}

安全防护（基础 WAF）

# 禁止访问隐藏文件
location ~ /\. {
    deny all;
    return 404;
}

# 拦截常见 SQL 注入特征
if ($query_string ~* "union.*select|information_schema|sleep\(") {
    return 403;
}

# 只允许指定 IP 访问管理后台
location /admin/ {
    allow 10.0.0.0/8;
    allow 192.168.0.0/16;
    deny all;
    proxy_pass http://backend;
}

降级兜底

后端挂了怎么办？Nginx 直接返回静态兜底页面，用户体验不至于 502：

location / {
    proxy_pass http://backend;
    proxy_intercept_errors on;
    error_page 502 503 504 /fallback.html;
}

location = /fallback.html {
    root /var/www/static;
}

访问日志自定义格式

log_format custom '$remote_addr - $remote_user [$time_local] '
                  '"$request" $status $body_bytes_sent '
                  '"$http_referer" "$http_user_agent" '
                  'rt=$request_time uct="$upstream_connect_time" '
                  'urt="$upstream_response_time"';

access_log /var/log/nginx/access.log custom;

加上 $upstream_response_time 就能直接看到后端耗时，不用再去后端日志里翻。

CORS 跨域配置

前后端分离跨域是刚需，Nginx 直接配，不用后端处理：

location /api/ {
    # 允许的源
    add_header Access-Control-Allow-Origin $http_origin always;
    add_header Access-Control-Allow-Methods "GET, POST, PUT, DELETE, OPTIONS" always;
    add_header Access-Control-Allow-Headers "Content-Type, Authorization, X-Requested-With" always;
    add_header Access-Control-Max-Age 86400 always;

    # 预检请求直接返回 204
    if ($request_method = OPTIONS) {
        return 204;
    }

    proxy_pass http://backend;
}

location ~* \.(jpg|png|webp|gif)$ {

大文件分片上传

上传大文件时，Nginx 临时目录写满磁盘是常见事故。优化一下：

http {
    client_body_buffer_size 10M;      # 10M 以内直接走内存
    client_max_body_size 10G;         # 最大 10G
    client_body_temp_path /data/nginx/tmp 1 2;  # 放大盘
    proxy_request_buffering off;       # 流式转发，不缓冲整个请求
}

SSE 流式响应

AI 大模型输出、实时日志推送，必须关缓冲：

location /sse {
    proxy_pass http://backend;
    proxy_http_version 1.1;

    # 关键：关掉所有缓冲
    proxy_buffering off;
    proxy_cache off;
    gzip off;

    # SSE 专用头
    proxy_set_header Connection "";
    chunked_transfer_encoding on;

    # 长连接超时
    proxy_read_timeout 1h;
}

参数默认值建议值说明

健康检查

Nginx Plus 有主动健康检查，开源版用被动检查：

upstream backend {
    server 10.0.0.1:8080 max_fails=3 fail_timeout=30s;
    server 10.0.0.2:8080 max_fails=3 fail_timeout=30s;
    server 10.0.0.3:8080 backup;  # 备用节点，主节点全挂才上
    keepalive 32;
}

max_fails=3：连续失败 3 次就摘下来。fail_timeout=30s：摘下来 30 秒后再试。

动态上游（服务发现）

配合 Consul / Nacos 做服务发现，不用改 Nginx 配置：

upstream backend {
    zone backend 64k;  # 共享内存，支持运行时改
    server 127.0.0.1:81;
    # 实际用 nginx-upsync-module 从 Consul 拉节点
}

错误页面美化

error_page 404 /404.html;
error_page 500 502 503 504 /50x.html;

location = /50x.html {
    root /usr/share/nginx/html;
    internal;  # 只能内部跳转，不能直接访问

静态站点部署

纯静态博客、文档站，Nginx 配置：

server {
    listen 80;
    server_name blog.example.com;
    root /var/www/blog;
    index index.html;

    # 干净 URL：/about -> /about.html
    location / {
        try_files $uri $uri.html $uri/ =404;
    }

    # gzip 压缩
    gzip on;
    gzip_types text/css application/javascript image/svg+xml;
}

FAQ

Nginx 怎么查看当前请求走的是哪个 location？

开 debug 日志，或者在每个 location 里配不同的 access_log 文件。nginx -T 能看完整配置，配合 curl -v 测试。

proxy_buffering 什么时候关？

流式响应（SSE、视频流、大文件下载）要关。关了之后 Nginx 不缓冲后端响应，直接转发给客户端，延迟低。但后端会被慢客户端拖住。

keepalive_timeout 设多少合适？

65 秒。太长了占连接资源，太短了频繁建连。上游 keepalive 是另一回事——upstream 块里 keepalive 32 是复用后端连接的数量。

Nginx 能做正向代理吗？

1.31.0 以后原生支持。之前要第三方模块。但说实话正向代理场景用 Squid 或者 dante 更合适。
