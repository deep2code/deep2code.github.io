Nginx 典型场景配置手册：反代、重写、跨域、鉴权、灰度

🏷️ Nginx 实战

这一篇是配置片段集：每个场景给出可以直接抄进生产的写法，同时说清「为什么这么写」和「大多数人是怎么写错的」。请求处理的 11 个阶段、location 匹配优先级、proxy_pass 尾斜杠语义、缓冲与超时参数、限流与缓存，都在 ../ 主干篇，这里只引用结论。

反向代理的必备请求头

Nginx 终止 TLS 后用明文回源，后端因此丢掉了三样信息：客户端真实 IP、客户端请求的域名、客户端用的协议。四个头是最小完备集，少一个就会出一类特定故障。

请求头建议值不传会发生什么
Host$host默认会被换成 proxy_pass 里的地址，后端多站点路由错乱、生成的链接域名错误、Cookie 域写错
X-Real-IP$remote_addr后端只能看到 Nginx 的内网 IP，风控与审计日志全废
X-Forwarded-For$proxy_add_x_forwarded_for多层代理时链路断掉；这个变量会把已有值加逗号后追加，所以它是可被客户端伪造的，取真实 IP 要靠 real_ip 模块从右往左数可信跳数
X-Forwarded-Proto$scheme后端生成 http 开头的绝对地址，被全站 301 跳回 https，形成重定向死循环，这是最高频的线上事故
X-Forwarded-Port$server_port非标端口场景后端拼出的链接丢端口
sequenceDiagram participant B as 浏览器 participant N as Nginx participant A as 后端应用 B->>N: GET https://a.com/profile N->>A: GET /profile 明文回源，未带 X-Forwarded-Proto Note over A: 框架看到协议是 http
于是把绝对地址拼成 http 开头 A-->>N: 302 Location 指向 http 开头的地址 N-->>B: 302 到 http 地址 B->>N: GET http 版本的同一个地址 N-->>B: 301 强制跳回 https B->>N: 又回到第一步 Note over B,N: 浏览器报重定向次数过多
而两侧日志看起来都正常 
# /etc/nginx/common/proxy-headers.conf —— 所有反代 location 都 include 它
proxy_http_version 1.1;                 # 默认 1.0，不改则上游长连接与分块传输都不可用

proxy_set_header Host              $host;
proxy_set_header X-Real-IP         $remote_addr;
proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
proxy_set_header X-Forwarded-Proto $scheme;   # 少了这行就会有重定向死循环
proxy_set_header X-Forwarded-Host  $host;
proxy_set_header X-Forwarded-Port  $server_port;

# 把 Nginx 生成的请求 ID 透传给后端，用于日志与链路关联
proxy_set_header X-Request-Id      $request_id;

# 下面这些是「先清空」，防止客户端伪造鉴权结果，详见本文鉴权一节
proxy_set_header X-Auth-User       "";
proxy_set_header X-Auth-Roles      "";

后端侧也要配合：Spring Boot 要设 server.forward-headers-strategy=framework，Django 要设 SECURE_PROXY_SSL_HEADER，Node 的 Express 要 app.set('trust proxy', 1)。只在 Nginx 侧传头、后端不信任，等于没传。反过来，如果后端无条件信任 X-Forwarded-For 的最左值，攻击者可以随意伪造来源 IP 绕过基于 IP 的限制。

URL 重写：四个 flag 与循环重定向

flag行为是否重新匹配 location客户端可见典型用途
last改写 URI 后重新发起一轮 location 匹配是否需要换到另一个 location 处理
break改写 URI 后停止后续 rewrite，继续在当前 location 执行否否改完 URI 直接交给本 location 的 proxy_pass
redirect返回 302—是临时跳转，或目标含变量
permanent返回 301—是永久跳转，但能用 return 301 就不要用它
无 flag继续执行同级后面的 rewrite 指令否否多步改写的中间步骤
flowchart TB S["请求进入 server 块"] --> SR["server 级 rewrite 依次执行"] SR --> M["选择 location"] M --> LR{"location 内 rewrite 用了哪个 flag"} LR -->|"last"| BACK["带新 URI 回到 location 选择"] LR -->|"break"| GO["留在当前 location
继续走 proxy_pass 或 root"] LR -->|"redirect 或 permanent"| OUT["直接给客户端 302 或 301"] BACK --> M BACK --> CNT{"内部重定向次数是否超过 10"} CNT -->|"超过"| ERR["报 rewrite or internal redirection cycle
返回 500"] CNT -->|"未超过"| M 
# 1. 纯跳转用 return，不要用 rewrite：更快，语义也更清楚
server {
    listen 80;
    server_name old.example.com;
    return 301 https://new.example.com$request_uri;   # 保留原路径与查询串
}

# 2. 需要正则捕获时才用 rewrite，注意 $1 与结尾的 flag
location /old-api/ {
    # 把 /old-api/users/3 改写成 /v2/users/3 后交给本 location 的 proxy_pass
    rewrite ^/old-api/(.*)$ /v2/$1 break;
    proxy_pass http://backend;
    include /etc/nginx/common/proxy-headers.conf;
}

# 3. 反面教材：下面这条会自己匹配自己，10 轮后 500
# location /img/ {
#     rewrite ^/img/(.*)$ /img/$1 last;   # 改写结果还在 /img/ 里，无限循环
# }

# 4. 目标里带变量、或需要条件判断时，用 map 代替一堆 if
map $http_user_agent $is_mobile {
    default        0;
    "~*Mobile|Android|iPhone" 1;
}
location = / {
    if ($is_mobile) { rewrite ^ /m/ last; }   # if 仅限这种单条件场景，理由见主干篇
}

location 与 rewrite 谁先执行是另一个高频困惑：server 级的 rewrite 在 location 选择之前执行，location 级的 rewrite 在选中之后执行，两者都属于 rewrite 阶段，而 rewrite 阶段早于 access 阶段——这就是为什么在 rewrite 里做不到「先鉴权再改写」。阶段划分见主干篇的 11 阶段图。

CORS：完整配置与边界

响应头作用常见错误
Access-Control-Allow-Origin允许的来源带凭证时不能用星号；直接回显 $http_origin 等于允许任意站点带 Cookie 访问
Access-Control-Allow-Credentials允许携带 Cookie与星号同时出现时浏览器直接拒绝，控制台报错但很多人以为是 Nginx 没生效
Access-Control-Allow-Methods预检放行的方法只在预检响应里有意义，实际请求里给了也没用
Access-Control-Allow-Headers预检放行的自定义头漏了 Authorization 或自定义 trace 头，导致预检通过而实际请求被拦
Access-Control-Max-Age预检结果缓存秒数不配则每个跨域请求都多一次 OPTIONS 往返
Vary: Origin告知缓存按 Origin 区分动态回显 Origin 却不加 Vary，CDN 会把 A 站的响应头发给 B 站
# 白名单用 map 维护，避免无脑回显 Origin
map $http_origin $cors_origin {
    default                      "";
    "https://app.example.com"    $http_origin;
    "https://admin.example.com"  $http_origin;
    "~^https://[a-z0-9-]+\.example\.com$" $http_origin;   # 受控通配
}

location /api/ {
    # 预检单独处理：直接返回 204，不要透传给后端
    if ($request_method = OPTIONS) {
        add_header Access-Control-Allow-Origin      $cors_origin always;
        add_header Access-Control-Allow-Credentials true      always;
        add_header Access-Control-Allow-Methods     "GET, POST, PUT, PATCH, DELETE" always;
        add_header Access-Control-Allow-Headers     "Authorization, Content-Type, X-Request-Id" always;
        add_header Access-Control-Max-Age           86400 always;
        add_header Vary                             Origin always;
        add_header Content-Length 0;
        return 204;
    }

    # 实际请求：always 保证 4xx 与 5xx 响应也带上，否则前端看到的是跨域错误
    # 而不是真实的错误码，排查方向会被完全带偏
    add_header Access-Control-Allow-Origin      $cors_origin always;
    add_header Access-Control-Allow-Credentials true      always;
    add_header Access-Control-Expose-Headers    "X-Request-Id" always;
    add_header Vary                             Origin always;

    proxy_pass http://backend;
    include /etc/nginx/common/proxy-headers.conf;
}
在哪一层做 CORS优点代价建议
Nginx 层统一维护，后端无感；预检不打到后端，省一半请求白名单改动要 reload；无法按用户或资源做细粒度判断白名单稳定、多个后端共用时选它
应用层能按路由、按租户动态决定；与业务鉴权逻辑放一起每个服务都要实现一遍，容易漏 Vary；预检也要消耗后端资源来源集合动态变化时选它
两层都配—响应头重复，浏览器直接判定非法明确只在一层配
⚠️
CORS 不是 CSRF 防御

CORS 是放宽同源策略的机制，它决定「别的站点的 JS 能不能读到你的响应」，而 CSRF 利用的是浏览器自动携带 Cookie 发起的写操作，这类请求根本不需要读响应。把 CORS 配严了不等于防住了 CSRF；反过来，把 CORS 配松（回显任意 Origin 加允许凭证）会把原本读不到的数据也暴露出去。CSRF 要靠 SameSite 与 Token，见站内 ../../security/ 的 CSRF 篇。

auth_request：在网关做子请求鉴权

auth_request 让 Nginx 在放行主请求前先向内部鉴权接口发一个子请求：2xx 放行，401 与 403 原样返回给客户端，其他状态码一律 500。它的价值是把鉴权从每个后端服务里抽出来，也能给那些自身没有鉴权能力的服务（静态文件、内部面板、第三方组件）套上统一入口。

sequenceDiagram participant C as 客户端 participant N as Nginx participant A as 鉴权服务 /auth participant U as 业务后端 C->>N: GET /api/orders 携带 Cookie 或 Bearer Note over N: 入口先把 X-Auth-User 等注入头清空
防止客户端伪造身份 N->>A: 子请求，只带头不带请求体 A-->>N: 204 并返回 X-Auth-User 与 X-Auth-Roles Note over N: auth_request_set 把响应头存进变量 N->>U: 转发主请求，注入可信的身份头 U-->>N: 200 业务数据 N-->>C: 200 C->>N: 另一个请求，Token 已过期 N->>A: 子请求 A-->>N: 401 N-->>C: 401 直接返回，主请求不会到达后端 
location /api/ {
    auth_request      /_auth;
    # 把鉴权服务返回的头取出来存成变量
    auth_request_set  $auth_user  $upstream_http_x_auth_user;
    auth_request_set  $auth_roles $upstream_http_x_auth_roles;

    # 关键：先清空，再注入。清空动作必须在同一个 location 里显式写出来，
    # 否则鉴权服务在某个分支没返回该头时，变量为空 Nginx 就不发送这个头，
    # 客户端自己伪造的同名头可能被透传给后端，等于身份伪造。
    proxy_set_header  X-Auth-User  $auth_user;
    proxy_set_header  X-Auth-Roles $auth_roles;

    proxy_pass http://backend;
    include /etc/nginx/common/proxy-headers.conf;
}

# 内部鉴权端点：只能被子请求访问
location = /_auth {
    internal;                                  # 外部直接访问返回 404
    proxy_pass              http://auth-svc/verify;
    proxy_pass_request_body off;                # 鉴权不需要请求体
    proxy_set_header        Content-Length "";
    proxy_set_header        X-Original-URI    $request_uri;
    proxy_set_header        X-Original-Method $request_method;
    proxy_set_header        X-Real-IP         $remote_addr;

    # 鉴权服务是全链路的单点，超时必须收紧，否则它慢会把整站拖死
    proxy_connect_timeout 200ms;
    proxy_read_timeout    500ms;

    # 同一个 token 短时间内复用鉴权结果，降低鉴权服务压力
    proxy_cache            auth_cache;
    proxy_cache_key        "$http_authorization$cookie_session";
    proxy_cache_valid      200 204 30s;
    proxy_cache_valid      401 403 5s;
}

# 401 时给前端一个统一的登录跳转
error_page 401 = @login;
location @login {
    return 302 https://sso.example.com/login?redirect=https://$host$request_uri;
}
❌
auth_request 的三个硬限制

第一，子请求不携带请求体，鉴权服务无法基于 body 做判断（比如按订单号鉴权），只能用 URI、方法和头。第二，鉴权服务成为全链路串行依赖，它的 P99 会直接叠加到每个请求上，超时必须配成毫秒级并加缓存。第三，auth_request 属于 access 阶段，它晚于 rewrite 阶段，所以无法用它决定要不要改写 URI。

灰度与分流

分流依据实现稳定性适用场景
Cookie 或请求头map $cookie_ver $backend稳定，由客户端携带内部测试、白名单用户、QA 指定版本
用户 ID 哈希百分比split_clients "$cookie_uid" $bucket稳定，同一用户永远同一侧标准灰度放量
随机数split_clients "$request_id" ... 或自造随机不稳定，同一用户来回跳只适合无状态的压测流量染色
客户端 IPsplit_clients "$remote_addr"稳定但分布差不推荐，NAT 出口会让整栋楼落在同一侧，比例严重失真
地域geoip2 变量稳定按省份分批放量，模块见本组 ../install/
flowchart TB R["请求到达"] --> W{"命中内部白名单 Cookie 吗"} W -->|"是"| NEW["强制走新版本，方便 QA 验证"] W -->|"否"| U{"取得稳定标识了吗
登录用户 ID 或持久 Cookie"} U -->|"没有"| SET["先下发一个持久标识
再按它分流，避免每次都变"] U -->|"有"| SP["split_clients 对标识做哈希"] SET --> SP SP -->|"落入 5% 桶"| NEW SP -->|"落入其余桶"| OLD["老版本"] NEW --> OB["观察新版错误率与耗时
异常就把百分比改回 0 并 reload"] 
# 稳定百分比分流：对同一个 uid，哈希结果固定不变
split_clients "${cookie_uid}canary-v3" $canary_bucket {
    5%      "new";           # 先放 5%
    *       "old";
}

# 白名单优先级高于百分比
map $cookie_x_env $forced {
    default  "";
    "canary" "new";
    "stable" "old";
}

map "$forced:$canary_bucket" $target_pool {
    default        "pool_old";
    "~^new"        "pool_new";     # forced 为 new，或桶为 new
    "~^:new$"      "pool_new";
    "~^old"        "pool_old";
}

upstream pool_old { server 10.0.1.11:8080; server 10.0.1.12:8080; keepalive 32; }
upstream pool_new { server 10.0.2.11:8080; keepalive 16; }

location /api/ {
    proxy_pass http://$target_pool;      # 变量形式的 proxy_pass 需要 resolver 或写死 upstream 名
    include /etc/nginx/common/proxy-headers.conf;
    # 把命中的版本记进日志，否则没法按版本对比错误率
    add_header X-Canary $canary_bucket always;
}

静态资源与 API 共存的路由设计有一条省心的规则：用 ^~ 给 API 前缀挡住后面的正则 location，这样 /api/xxx.js 这类路径不会被「按扩展名匹配静态资源」的正则抢走。前缀与正则的优先级细节见主干篇。

灰度的回滚能力比放量能力更重要。百分比必须能一条命令改回 0 并 reload，这意味着比例不要散落在多处，最好集中在一个单独 include 进来的片段里。同时日志一定要带上命中的桶名，否则放量后错误率上升时，没法判断是新版本引起的还是恰好赶上业务高峰。监控面板也要按桶分开看错误率与 P99：只看总量会被 95% 的老流量稀释——新版本那 5% 全挂了，总错误率也只有 5%，很容易被当成正常波动放过去。

WebSocket、文件上传与降级

# Upgrade 与 Connection 是逐跳头，Nginx 默认不转发，必须显式传
map $http_upgrade $connection_upgrade {
    default upgrade;
    ""      close;              # 普通 HTTP 请求不要被标成 upgrade
}

location /ws/ {
    proxy_pass http://ws_backend;
    proxy_http_version 1.1;                       # 1.0 不支持协议升级
    proxy_set_header Upgrade    $http_upgrade;
    proxy_set_header Connection $connection_upgrade;
    proxy_set_header Host       $host;

    # 默认 60s：长连接没消息就被切断，表现为「连上一分钟必掉线」
    proxy_read_timeout  3600s;
    proxy_send_timeout  3600s;
    proxy_buffering     off;                      # 实时消息不能被缓冲
}

location /upload {
    client_max_body_size    2g;      # 默认 1m，超了返回 413
    client_body_buffer_size 1m;      # 超过这个值写磁盘临时文件，磁盘要有空间
    client_body_timeout     300s;    # 慢网络大文件容易在这里被判超时

    # 关闭请求体缓冲：Nginx 边收边转，内存与磁盘占用小、后端能实时感知进度，
    # 代价是后端一旦失败无法重试到另一台上游，因为请求体已经流走了
    proxy_request_buffering off;
    proxy_pass http://upload_backend;
    include /etc/nginx/common/proxy-headers.conf;
}
场景关键参数默认值不调的后果
WebSocket 长连接proxy_read_timeout60s无消息一分钟后被 Nginx 主动断开
WebSocket 协议升级proxy_http_version1.0握手失败，返回 400 或 502
大文件上传client_max_body_size1m413 Request Entity Too Large
上传落盘client_body_buffer_size8k 或 16k大量请求写 client_body_temp，磁盘 IO 打满
流式上传proxy_request_bufferingon开着时整个文件先落 Nginx 磁盘，后端才收到，体验差且占空间；关掉则失去上游重试能力
SSE 流式响应proxy_bufferingon响应被攒着不发，前端等到超时，细节见主干篇
# 后端全挂时返回静态降级页，而不是 Nginx 默认的白底 502
location / {
    proxy_pass http://backend;
    include /etc/nginx/common/proxy-headers.conf;

    proxy_intercept_errors on;      # 让后端返回的 4xx/5xx 也走下面的 error_page
    error_page 500 502 503 504 /maintenance.html;
}

location = /maintenance.html {
    root /data/static/fallback;
    internal;                       # 不允许外部直接访问
    add_header Retry-After 120 always;
    # 降级页本身绝不能缓存，否则恢复后用户还在看维护页
    add_header Cache-Control "no-store" always;
}

# 用后备 upstream 兜底：主池全挂时打到一台只返回静态内容的机器
upstream backend {
    server 10.0.1.11:8080 max_fails=3 fail_timeout=10s;
    server 10.0.1.12:8080 max_fails=3 fail_timeout=10s;
    server 10.0.9.99:8080 backup;    # 全部主节点不可用时才启用
    keepalive 64;
}
💡
proxy_intercept_errors 是双刃剑

打开它之后，后端返回的 404、403 也会被 Nginx 的 error_page 接管。如果后端是 API，它原本返回的 JSON 错误体会被替换成 HTML，前端解析直接失败。所以要么只在纯页面的 location 上开，要么用 error_page 精确列出只接管 5xx。

调试手段

$request_id 是 Nginx 自动生成的 16 字节随机十六进制串，每个请求唯一。把它同时写进访问日志、透传给后端、放进响应头，就用最低成本打通了「用户截图 → Nginx 日志 → 后端日志 → 链路追踪」。三支柱之间怎么关联见站内可观测性篇。

log_format main escape=json
  '{"time":"$time_iso8601","rid":"$request_id","host":"$host",'
  '"addr":"$remote_addr","xff":"$http_x_forwarded_for",'
  '"method":"$request_method","uri":"$request_uri","status":$status,'
  '"bytes":$body_bytes_sent,"rt":$request_time,'
  '"urt":"$upstream_response_time","uaddr":"$upstream_addr",'
  '"ustatus":"$upstream_status","canary":"$canary_bucket"}';

access_log /var/log/nginx/access.log main;

server {
    # 让用户能把这个 ID 报给客服，也方便前端把它打进埋点
    add_header X-Request-Id $request_id always;
}

# 只对指定 IP 开 debug 日志：全局开 debug 会瞬间写满磁盘并明显拖慢 worker
# 前提是编译时带了 --with-debug
error_log /var/log/nginx/error.log warn;
events {

反模式对照

反模式症状正确做法
不传 X-Forwarded-Proto浏览器报重定向次数过多，两侧日志都「正常」传 $scheme，并让后端框架信任转发头
在 location 里用 rewrite ... last 改写成还能匹配自己的路径10 轮后 500，error.log 报 redirection cycle改用 break，或让改写结果落到别的 location
CORS 用星号又带 Allow-Credentials浏览器直接拒绝，看起来像 Nginx 没生效用 map 白名单回显具体来源，并加 Vary: Origin
add_header 不加 always4xx 与 5xx 响应没有 CORS 头，前端看到跨域错误而非真实错误码CORS 相关头统一加 always
灰度用随机数同一用户在新旧版本间来回跳，问题无法复现split_clients 对稳定标识哈希
WebSocket 不传 Upgrade 与 Connection握手 400 或 502用 map 联动 $connection_upgrade，并设 proxy_http_version 1.1
auth_request 注入头前不清空客户端自带同名头可能被透传，造成身份伪造入口 location 里对所有注入头先 proxy_set_header 成空串
鉴权子请求不设超时不加缓存鉴权服务抖动时全站 P99 一起抖毫秒级超时加 proxy_cache
对 API location 开 proxy_intercept_errors后端 JSON 错误体被换成 HTML，前端解析失败只对页面类 location 开，或精确只接管 5xx
降级页被 CDN 缓存后端恢复后用户还在看维护页降级页加 Cache-Control: no-store
❌
最容易踩的坑
  • 忘传 X-Forwarded-Proto：后端生成 http 绝对地址，与全站 301 互相弹，形成重定向死循环。
  • 后端无条件信任 X-Forwarded-For 最左值：攻击者一行头就能伪造来源 IP，绕过按 IP 的限制。
  • proxy_http_version 留默认 1.0：上游长连接、分块传输、WebSocket 升级全都不工作。
  • 用 rewrite ... permanent 做纯跳转：多走一遍正则，能用 return 301 就别用它。
  • last 与 break 用混：要么陷入内部重定向循环，要么改写后没走到期望的 proxy_pass。
  • 预检 OPTIONS 透传给后端：后端没实现 OPTIONS 直接 405，跨域一直失败。
  • 动态回显 Origin 却不加 Vary: Origin：CDN 把 A 站点的响应头发给 B 站点，偶发且极难复现。
  • Nginx 和应用同时配 CORS：响应头出现两份，浏览器判定非法。
  • 灰度键用 $remote_addr：NAT 出口让一整个办公楼落在同一侧，5% 可能变成 30%。
  • client_max_body_size 留默认 1m：上传稍大的文件就 413，而且错误出在 Nginx，后端日志里什么都没有。
  • 关掉 proxy_request_buffering 后还指望上游重试：请求体已经流走，失败就是失败，重试不可能。
  • 全局开 error_log debug：磁盘几分钟写满，worker 明显变慢；要用 debug_connection 只对自己的 IP 开。
