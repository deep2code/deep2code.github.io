容器的实现机制与镜像工程

🏷️ Docker

容器在 Linux 上没有对应的内核对象。内核里既没有 struct container，也没有 create_container() 这样的系统调用。容器是用户态把三组早就存在的机制拼起来之后、对外呈现出的一个抽象：namespace 负责「看不见」，cgroup 负责「用不到」，联合文件系统负责「根目录长什么样」。把这句话吃透，容器的大部分怪问题都可以自己推导出来——凡是这三组机制没覆盖到的东西，就一定是漏到宿主上去的。

容器是怎么被拼出来的

一次 docker run 的实质是：新建若干 namespace、在 cgroup 里写下额度、把镜像层 mount 成 overlayfs 并 pivot_root 过去、丢弃多余 capability、装载 seccomp 规则，然后 execve 业务二进制。这些动作由 runc 按 OCI config.json 执行，runc 本身执行完就退出，留下 containerd-shim 作为常驻父进程。

容器不是虚拟机：共享内核的具体后果

「容器更轻」只是结论，工程上真正要关心的是它轻在哪里、代价是什么。内核是共享的，所以镜像里换成什么发行版都只是换了用户态的 libc 与工具链，内核特性（overlayfs 版本、cgroup 版本、io_uring、eBPF 能力）完全取决于宿主。「镜像能跑起来」不等于行为一致。

下图只是量级上的相对对比，不是基准数据，隔离性一栏尤其粗糙：容器与虚拟机之间差的是攻击面维度，不是一个分数。

更值得记住的是可见性问题。容器里的 /proc 与 /sys 绝大部分仍是宿主的，运行时按它们做自适应就会算错。

容器里读到的实际来源被带偏的典型行为正确做法
nproc、runtime.NumCPU、os.cpus宿主 CPU 核数线程池与 GOMAXPROCS 远大于配额，上下文切换与限流同时变重Go 显式设 GOMAXPROCS 或引入 automaxprocs；JVM 自 8u191 与 10 起默认读 cgroup
free、/proc/meminfo宿主内存总量按「总内存百分比」算堆，直接超过 memory.max 被杀JVM 用 MaxRAMPercentage；其他语言读 /sys/fs/cgroup/memory.max
uptime、load average宿主负载误判自身压力，自适应限流策略乱抖看 cpu.stat 的 throttled_usec 与 PSI
date、时钟宿主时钟需要「时间穿越」的测试无法在容器内单独完成用 libfaketime 之类在进程层伪造，不要给 SYS_TIME
uname -r宿主内核依赖较新系统调用的库在老内核宿主上运行异常把宿主内核版本纳入部署前置检查
/dev/shm默认 64MB 的 tmpfsPostgreSQL、Chromium 这类重度使用共享内存的进程直接崩按需调 --shm-size

内核参数分两类，这条界线每年都有人踩：namespaced 的参数（net.*、kernel.shm*、fs.mqueue.*）可以用 --sysctl 在单个容器里设；非 namespaced 的参数（vm.max_map_count、vm.swappiness、fs.file-max、kernel.pid_max）只能在宿主上改，Elasticsearch 在容器里起不来九成是这一条。真正需要内核级隔离边界时，换 gVisor 或 Kata 这类运行时，代价是系统调用路径变长。

镜像分层：内容寻址与缓存失效规则

一个镜像等于「一份 manifest + 一份 config + N 个 layer blob」。blob 按内容寻址，因此相同的层在同一台机器或同一个仓库里只存一份。注意 config 里的 diff_ids 是解压后 tar 的摘要，而 manifest 里的 digest 是压缩后 blob 的摘要，两者本来就不相等——这就是本地 image ID 和仓库里 digest 对不上的原因。

overlayfs 侧的规则只有两条，但后果很大：写已有文件会触发 copy-up，改 1GB 文件中的一个字节也要先把整个文件复制到可写层；删除文件是在上层写 whiteout 标记，下层数据仍然占体积。所以「先装后删」不缩小镜像，除非删在同一层里。

指令缓存键取自什么什么时候必然失效要点
FROM image:tag解析后的镜像 digest上游把同一个 tag 重新推了一次需要可复现就钉 digest，而不是钉 tag
RUN指令字符串逐字节比较多一个空格、改了换行位置都算变缓存键和文件系统实际内容无关，所以 apt 索引会「缓存着过期」
COPY 与 ADD 本地路径文件内容校验和加路径、权限、uid/gid内容变化，或 CI 检出把权限位改了mtime 不参与判断。「碰一下时间戳缓存就失效」是 Docker 1.8 之前的老说法
ADD 远端 URL远端响应内容每次构建都要重新拉取校验改用 RUN 下载并校验摘要，行为更可控
被引用的 ARG参数取值参与后续层的键传入了不同的值没被任何指令引用的 ARG 不影响缓存；把构建时间戳一类参数尽量后移
任意一层失效无其后所有层全部重算因此最易变的 COPY 必须放在最后
RUN --mount=type=cache挂载目录不进入镜像层不参与镜像 digest包管理器下载缓存的正确写法，跨构建复用又不污染体积

多阶段构建与镜像体积的真实来源

体积优化经常被简化成「换 alpine」，但真正的大头往往不在基础镜像。先按来源拆开看。

体积来源量级为什么容易被忽略处置方式
基础镜像自带的发行版几十到几百 MB只盯着自己 COPY 进去的产物换 distroless、static 或 scratch；确认真的不需要 shell 与证书包
包管理器索引与缓存几十 MB清理命令写在了下一个 RUN 里同一个 RUN 内清掉，或用 cache mount 让它根本不进层
构建期工具链几百 MB直接把构建镜像当运行镜像多阶段，只 COPY --from 拷产物
调试符号与静态库几十 MB默认就带着Go 加 -s -w 链接参数，C/C++ 走 strip
已删除但仍在下层的文件等于被删文件本身大小以为 rm 之后就小了在同层删除，或在干净的运行阶段重建
多架构 manifest list每个架构一份看仓库总占用时才发现翻倍只构建实际需要的平台；跨架构构建用 buildx 的原生节点而非全程模拟

alpine 也不是无条件更优：musl 与 glibc 在 DNS 解析和 NSS 行为上有差异，Python 生态的预编译 wheel 大多只发 glibc 版本，落到 alpine 上会退化成源码编译，构建时间和最终体积双双变差。Go 这类可以静态链接的语言才是 scratch 与 distroless 的最佳搭配。

# syntax=docker/dockerfile:1.7
# 构建阶段：基础镜像钉到小版本，避免上游 tag 漂移导致整条缓存链失效
FROM golang:1.22-bookworm AS build
WORKDIR /src

# 先只拷依赖清单，代码变更时这一层仍然命中
COPY go.mod go.sum ./
# cache mount 的内容不会进入任何镜像层，也不参与 digest
RUN --mount=type=cache,target=/go/pkg/mod \
    go mod download

COPY . .
# CGO_ENABLED=0 才能进 scratch 或 static 运行镜像
# -s -w 去掉符号表与调试信息，trimpath 让构建结果可复现
RUN --mount=type=cache,target=/go/pkg/mod \
    --mount=type=cache,target=/root/.cache/go-build \
    CGO_ENABLED=0 GOFLAGS=-trimpath \
    go build -ldflags "-s -w" -o /out/app ./cmd/app

# 运行阶段：static 镜像里没有 shell，也没有包管理器，排查要靠 ephemeral 调试容器
FROM gcr.io/distroless/static-debian12:nonroot
# 用数字 uid 而不是用户名，K8s 的 runAsNonRoot 只认数字
USER 65532:65532
COPY --from=build /out/app /app
# exec 形式，保证业务进程就是 PID 1，能直接收到停止信号
ENTRYPOINT ["/app"]

下图是「同一个 Go 服务，带完整工具链的单阶段镜像 vs 多阶段加 distroless」的典型量级差距，具体数字取决于依赖，重点看的是数量级。

CI 里构建缓存为什么总不命中

根因通常与 Dockerfile 无关：CI runner 是一次性的，而 BuildKit 默认只使用 builder 的本地缓存，机器销毁缓存就一起消失。第二位的原因是导出模式选错——默认的 inline 模式只带最终阶段的层，多阶段构建的中间层一个都不复用。

非 root 运行与 capability 收口

默认情况下容器进程是 uid 0，带着一组保留的 capability，外面套着默认 seccomp 规则与 AppArmor 配置。--privileged 一次性把这三层全部关掉，因此它不该出现在任何业务容器的启动参数里。要澄清两个流传很广的说法：第一，容器里的 root 并不是「假 root」，在没开 user namespace 时它就是宿主的 uid 0，只是能力被裁剪，所以把宿主的 docker 套接字挂进容器等于交出宿主 root；第二，USER 写用户名在 Docker 下能跑，但 K8s 的 runAsNonRoot 只认数字 uid，写名字会因为无法解析而拒绝启动。

capability默认是否保留拿到它能做什么建议
NET_RAW保留构造原始报文，可做 ARP 与 DNS 欺骗明确丢弃，代价只是容器内 ping 不可用
NET_BIND_SERVICE保留绑定 1024 以下的特权端口监听 8080 一类高位端口时不需要，直接丢
DAC_OVERRIDE保留绕过文件读写权限检查丢弃，否则精心设置的文件权限形同虚设
SETUID 与 SETGID保留切换用户身份，配合 setuid 文件形成提权链应用不需要切换用户就丢弃，并开 no-new-privileges
MKNOD保留创建设备节点丢弃
SYS_ADMIN不保留挂载、改 namespace，基本等价于越狱永远不要加
SYS_PTRACE不保留调试与读取同 pid namespace 内其他进程只在临时调试容器上加
SYS_TIME不保留修改系统时钟，会影响整台宿主永远不要加

docker run -d --name app \
  --user 65532:65532 \
  --cap-drop ALL \
  --security-opt no-new-privileges:true \
  --read-only \

PID 1、信号转发与容器停不下来

PID 1 在内核里有特殊语义：对于它没有安装处理函数的信号，内核不会执行默认动作。于是业务进程作为 PID 1 却没注册 SIGTERM 处理时，docker stop 发出的信号等于被丢掉，等满默认 10 秒超时后改发 SIGKILL，退出码 137。同一个坑的另一半是 shell 形式的 CMD：它会被包成 /bin/sh -c，此时 sh 是 PID 1，多数 shell 不会把信号转发给子进程。

stateDiagram-v2 [*] --> Created Created --> Running: start Running --> Paused: pause 走 cgroup freezer Paused --> Running: unpause Running --> Stopping: docker stop 发出 STOPSIGNAL Stopping --> Exited: 进程自己退出，退出码 143 Stopping --> Killed: 超过停止超时，内核发 SIGKILL Running --> Killed: cgroup 内存超限，内核直接杀 Killed --> Exited: 退出码 137 Exited --> Running: 命中 restart 策略 Exited --> [*]: docker rm 一并删掉可写层 note right of Stopping 默认停止超时是 10 秒 PID 1 没有安装处理函数时 内核不会执行默认终止动作 所以这里必然等满超时 end note

三种修法按优先级排：用 exec 形式的 ENTRYPOINT 让业务进程直接成为 PID 1；必须用入口脚本时，最后一行写 exec 替换自身；容器内确实会拉起多个进程时加 --init，注入一个最小 init 负责转发信号并回收僵尸进程——僵尸堆积会吃满 pids.max，这是长跑容器莫名 fork 失败的常见原因。另外 STOPSIGNAL 可以改默认信号，nginx 收到 SIGQUIT 才是优雅退出，收 SIGTERM 是快速退出。优雅退出与流量摘除如何配合（preStop、终止宽限期）详见站内 Kubernetes 一篇。

日志驱动与磁盘写满

默认的 json-file 驱动不做任何轮转，只要应用往标准输出写，文件就一直涨。这个配置只对新建容器生效，改完守护进程配置必须重建容器才算生效——这是「我已经配了 max-size 为什么还涨」的答案。docker logs 只对 json-file 与 local 驱动可用，切到 fluentd、syslog 之类之后这条命令直接失败，排查手感会变差，本地开发环境不建议换。另外默认的阻塞投递模式下，日志后端变慢会反压到应用线程；换成非阻塞模式则要接受缓冲区满时丢日志。

{
  "log-driver": "local",
  "log-opts": { "max-size": "50m", "max-file": "3", "compress": "true" },
  "live-restore": true,
  "default-ulimits": { "nofile": { "Name": "nofile", "Soft": 65535, "Hard": 65535 } },
  "default-address-pools": [ { "base": "10.201.0.0/16", "size": 24 } ]
}

排查磁盘用 docker system df -v：它会把镜像、容器可写层、卷、构建缓存分开列出，绝大多数「莫名其妙没空间」是构建缓存和卷。注意 docker system prune 默认不删卷，也不删正在被引用的构建缓存；docker rm -f 更不会删卷。还有一条容易白忙半天的：不要手工 rm 正在被写入的日志文件，dockerd 仍持有文件描述符，空间不会释放，只有重建容器或重启守护进程才回来。日志集中采集的链路设计详见站内日志与监控相关文章。

  • 在后面的 RUN 里删文件想瘦身：下层 blob 还在，只是多了一个 whiteout 标记，镜像一个字节都没小
  • 把 vm.max_map_count 写进 --sysctl：它不是 namespaced 参数，容器会直接启动失败，必须在宿主上改
  • Go 服务不设 GOMAXPROCS：它读的是宿主核数，容器只有 1.5 核时线程数量级失配，限流与调度开销一起上来
  • JVM 用固定 -Xmx 却按宿主内存估算：一旦超过 memory.max 就是 137 退出，日志里往往什么都没留下
  • shell 形式的 CMD：PID 1 变成 sh，不转发信号，每次发布都要等满 10 秒超时才被 SIGKILL
  • USER appuser 写成用户名：Docker 下正常，K8s 开了 runAsNonRoot 之后直接拒绝启动
  • 把宿主 docker 套接字挂进容器做「容器内构建」：等价于把宿主 root 交出去，用 buildx 独立 builder 或 rootless 方案替代
  • 只配 --memory 不配 --memory-swap：容器吃到宿主 swap，不被杀但延迟塌掉，比直接 OOM 更难查
  • CI 里指望默认缓存：一次性 runner 没有本地缓存，不配 cache-to 就是每次全量构建，配了却用默认 inline 模式则中间阶段照样全丢
  • json-file 驱动不配轮转：磁盘写满后 dockerd 与所有容器一起出问题，且手工删日志文件不释放空间
  • 以为 docker system prune 会清干净：卷和被引用的构建缓存都不在默认清理范围内，要用 -v 参数与 builder prune 单独处理
