Jenkins 实战：Declarative Pipeline、Kubernetes 动态 agent、共享库与运维要点

🏷️ Jenkins

Jenkins 在 2026 年依然是绕不开的话题，不是因为它好用，而是因为存量太大、插件生态无可替代、并且它能跑在完全隔离的内网里——后者是很多金融、制造、政企场景下托管 CI 根本进不来的硬约束。但同时要承认它的根本问题：插件版本地狱、Groovy 脚本难维护、controller 单点且状态全在磁盘、UI 配置无法版本化。这篇讲怎么把 Jenkins 用对，以及什么时候该迁走。流水线设计原则与部署策略详见站内《CI/CD 工具选型》与《容器化部署策略》。

Jenkins 的价值与它的四个结构性缺陷

缺陷具体表现缓解手段无法根治的部分
插件版本地狱几百个插件互相依赖，升级一个插件导致流水线语法报错或 UI 白屏控制插件数量在必要范围内；升级前在测试实例验证同样组合插件由不同作者维护，兼容性矩阵没人保证
Groovy 难维护Jenkinsfile 上千行、脚本式里塞满 try/catch 与反射，没人敢动强制 Declarative；逻辑下沉到共享库的 src/ 里做单测Pipeline 的 CPS 转换语义（每步序列化）与普通 Groovy 有差异，踩坑无法避免
controller 单点与磁盘状态配置、job、凭证、构建历史全在 JENKINS_HOME，重启即中断，扩容只能垂直JCasC 把配置版本化；定期备份 JENKINS_HOME；agent 全部外置controller 本身没有真正的高可用（社区版）
UI 配置无法版本化关键逻辑点在网页表单里，没人知道谁改了什么、怎么回滚Pipeline as Code + Configuration as Code 插件部分插件的配置项仍只能在 UI 里点

Pipeline as Code：Declarative 优先，Scripted 只在必要时

第一条铁律：不要用 UI 配置 job。自由风格 job 的构建步骤写在网页表单里，既不能 review、不能回滚，也无法随分支演进。所有逻辑必须落在仓库里的 Jenkinsfile，配合 Multibranch Pipeline 让每个分支和 MR 自动获得流水线。

第二条：优先 Declarative。它有固定的结构（agent、options、environment、stages、post），能在运行前做语法校验，post 块提供了可靠的 always/failure/unstable/cleanup 钩子，Blue Ocean 与阶段视图也只对它完整生效。Scripted 是纯 Groovy，灵活但极易长成无人敢碰的怪物。实践中最好的组合是：Declarative 作为骨架，复杂逻辑封到共享库里，需要动态生成 stage 时才在 script 块里局部用脚本式。

维度DeclarativeScripted
结构固定小节，解析期即校验，写错立刻报任意 Groovy，错误往往要跑到那一步才暴露
失败后处理post 块的 always/failure/unstable/cleanup要自己写 try/catch/finally，容易漏
并行parallel 小节，每个分支可各自指定 agentparallel 传 Map，灵活但要手动管工作区
动态生成 stage不支持，需要在 script 块里降级天然支持，for 循环里拼 stage
可读性与治理结构统一，几十条流水线也能对齐规范每个人写法不同，最终不可维护
推荐用法默认选它只在共享库内部或确实需要动态结构时用
// Jenkinsfile —— Declarative Pipeline，可直接改用
pipeline {
  agent none                        // 顶层不占 agent；绝不要写 agent any 让构建落到 controller 上
  options {
    timeout(time: 40, unit: 'MINUTES')           // 不设超时的 build 会永久占着 executor
    buildDiscarder(logRotator(numToKeepStr: '30', artifactNumToKeepStr: '5'))  // 不清理迟早写满磁盘
    disableConcurrentBuilds(abortPrevious: true) // 同一分支连续提交时掐掉旧构建
    timestamps()
    skipDefaultCheckout(true)                    // 自己控制 checkout 时机，避免每个 agent 都拉一次
  }
  environment {
    REGISTRY = 'registry.internal:5000'
    APP      = 'order-service'
  }
  parameters {
    choice(name: 'DEPLOY_ENV', choices: ['staging', 'prod'], description: '部署目标环境')
    booleanParam(name: 'SKIP_IT', defaultValue: false, description: '跳过集成测试')
  }
  triggers {
    // 优先用 Git webhook；轮询只在网络单向不可达时兜底，H 让负载在小时内散开
    pollSCM('H/10 * * * *')
  }
  stages {
    stage('Checkout') {
      agent { label 'linux && docker' }
      steps {
        checkout scm
        script {
          env.GIT_SHA = sh(script: 'git rev-parse --short HEAD', returnStdout: true).trim()
        }
        // 不同 stage 可能落在不同 agent 上，工作区不共享，必须 stash/unstash 传递
        stash name: 'src', includes: '**', useDefaultExcludes: false
      }
    }
    stage('Verify') {
      parallel {
        stage('Unit') {
          agent { label 'linux' }
          steps {
            unstash 'src'
            sh './gradlew --no-daemon test'
          }
          post {
            always { junit testResults: 'build/test-results/**/*.xml', allowEmptyResults: false }
          }
        }
        stage('Integration') {
          when { expression { return !params.SKIP_IT } }
          agent { label 'linux && docker' }
          steps {
            unstash 'src'
            sh './gradlew --no-daemon integrationTest'
          }
        }
      }
    }
    stage('Image') {
      agent { label 'linux && docker' }
      steps {
        unstash 'src'
        withCredentials([usernamePassword(credentialsId: 'registry-cred',
                                          usernameVariable: 'REG_USER',
                                          passwordVariable: 'REG_PASS')]) {
          // 用单引号的 Groovy 字符串，让 shell 自己展开变量。
          // 写双引号会让 Groovy 先把密码插值进命令行，泄进 ps 输出与异常堆栈
          sh '''set -euo pipefail
            echo "$REG_PASS" | docker login "$REGISTRY" -u "$REG_USER" --password-stdin
            docker build -t "$REGISTRY/$APP:$GIT_SHA" .
            docker push "$REGISTRY/$APP:$GIT_SHA"
          '''
        }
        archiveArtifacts artifacts: 'build/libs/*.jar', fingerprint: true
      }
    }
    stage('Approve') {
      when { expression { return params.DEPLOY_ENV == 'prod' } }
      agent none                    // 审批阶段不需要占 executor
      steps {
        timeout(time: 30, unit: 'MINUTES') {   // input 不包 timeout 会永久挂着等人
          input message: '确认发布到生产？', ok: '发布', submitter: 'release-managers'
        }
      }
    }
    stage('Deploy') {
      agent { label 'deploy' }
      steps {
        sh "./deploy.sh ${params.DEPLOY_ENV} ${env.GIT_SHA}"
      }
    }
  }
  post {
    always   { cleanWs() }          // 静态 agent 上不清理，下次构建就会读到上次的残留
    failure  { echo "构建失败：${env.BUILD_URL}" }
    unstable { echo '测试不通过，记为 unstable 而不是 failure' }
  }
}

执行模型：controller 调度，构建必须下沉到 agent

Jenkins 的架构是一个 controller 加若干 agent。controller 负责调度、存状态、渲染 UI；agent 提供 executor 与工作区，真正跑构建。绝不要在 controller 上跑构建：构建脚本运行在 controller 的 JVM 环境与文件系统里，一次 rm -rf 或一个失控进程就能拖垮整个 Jenkins，而且构建脚本能直接读到 JENKINS_HOME 里的凭证文件。正确做法是把 controller 的 executor 数设为 0（JCasC 里一行 numExecutors: 0），强制所有 job 通过 label 落到 agent。

另一个高频困惑：同一条流水线的不同 stage 可能落在不同 agent 上，工作区互不相通。跨 stage 传文件要用 stash 与 unstash（小文件，存在 controller 上）或 archiveArtifacts（正式产物）。把大目录 stash 会把 controller 磁盘和网络吃满，依赖目录应该靠 agent 侧的持久化缓存卷解决。

agent 接入方式连接方向环境隔离适用坑
SSH（controller 主动连）controller → agent无，工作区跨构建复用固定构建机、需要宿主机工具链环境漂移；忘记 cleanWs() 就读到上次残留
JNLP / inbound（agent 反连）agent → controller 的 50000 端口同上agent 在 NAT 后、单向可达端口与 agent 协议要显式开；密钥泄露等于任何人可接入成为 agent
Docker agent（agent { docker }）宿主机上起容器容器级工具链版本多样的团队需要宿主 docker 权限，等于把宿主机交给流水线
Kubernetes 动态 PodPod 内 agent 反连Pod 级，一次性已有 K8s，追求弹性与干净环境冷启动（调度 + 拉镜像）；缓存要挂 PVC 否则每次重下依赖
在 controller 上直接跑—无没有适用场景构建脚本能读 JENKINS_HOME 里的凭证，等于没有安全边界

Kubernetes 动态 agent：现代 Jenkins 的标准形态

「agent 环境污染」是 Jenkins 最古老的问题：静态 agent 上装了三个 JDK、两个 Node、还有上个项目留下的全局 npm 包，某天有人手动改了 PATH，构建就开始随机失败，而且没人记得这台机器上到底装了什么。Kubernetes plugin 从根上解决它：用 podTemplate（或 Declarative 里的 agent { kubernetes { yaml ... } }）声明这次构建需要哪些容器，每次构建创建一个全新 Pod，构建结束销毁，环境完全由镜像定义、随代码一起版本化。

sequenceDiagram autonumber participant Q as 构建队列 participant CT as Controller participant K8 as Kubernetes API participant PD as agent Pod participant GT as Git 与 Registry Q->>CT: 新构建入队，需要 kubernetes agent CT->>K8: 按 podTemplate 创建 Pod K8-->>PD: 调度节点，拉起 jnlp 容器与各工具容器 PD->>CT: 通过 JNLP 端口反向连接，注册为在线 agent CT->>PD: 逐个 step 下发，在指定 container 里 exec PD->>GT: checkout 代码、构建、推送镜像 PD-->>CT: 回传日志、junit 报告与归档产物 CT->>K8: 构建结束，删除 Pod Note over CT,PD: Pod 一次性使用，彻底消除环境污染
代价是每次构建多出调度与拉镜像的冷启动时间 
// Kubernetes plugin 动态 agent：每次构建起一个 Pod，构建完销毁
pipeline {
  agent {
    kubernetes {
      defaultContainer 'gradle'     // 不写的话 step 默认落在 jnlp 容器里，工具全都找不到
      yaml '''
apiVersion: v1
kind: Pod
spec:
  securityContext:
    runAsUser: 1000
    runAsNonRoot: true
  containers:
    - name: gradle
      image: gradle:8.7-jdk21
      command: ["sleep"]           # 容器必须常驻，Jenkins 是往里 exec 执行每个 step
      args: ["9999999"]
      resources:
        requests: {cpu: "1", memory: "2Gi"}
        limits: {memory: "4Gi"}    # 不设 limits，一个失控构建能把整个节点 OOM
      volumeMounts:
        - name: gradle-cache
          mountPath: /home/gradle/.gradle
    - name: kaniko                 # 用 kaniko 构建镜像，不需要 privileged 的 dind
      image: gcr.io/kaniko-project/executor:v1.23.2-debug
      command: ["sleep"]
      args: ["9999999"]
  volumes:
    - name: gradle-cache
      persistentVolumeClaim:
        claimName: gradle-cache    # 依赖缓存要持久化，否则每次全新 Pod 都重新下载
'''
    }
  }
  stages {
    stage('Build') {
      steps { sh './gradlew --no-daemon build' }      // 落在 defaultContainer
    }
    stage('Image') {
      steps {
        container('kaniko') {                          // 显式切换容器
          sh '/kaniko/executor --context $WORKSPACE --dockerfile Dockerfile --destination $IMAGE --cache=true'
        }
      }
    }
  }
}
💡
动态 agent 的三个必配项

一是 defaultContainer：不指定时所有 sh 都在 jnlp 容器里执行，表现为「明明装了 gradle 却报 command not found」。二是资源 requests/limits：不设 limits 时一个失控构建能把节点打爆，设得过小又会让编译进程被 OOMKilled，表现为构建「无原因中断」。三是依赖缓存卷：Pod 一次性意味着每次都重新下依赖，必须挂 PVC 或指向内网镜像仓库代理，否则提速的收益会被下载时间吃光。

共享库：治理几十条流水线的唯一可行方式

当流水线数量到十几条，复制粘贴的 Jenkinsfile 就变成灾难：改一处安全扫描规则要改二十个仓库。共享库（Shared Library）是 Jenkins 给出的答案，结构上分两块：vars/ 里每个 .groovy 文件暴露一个全局步骤（入口方法必须叫 call），src/ 放标准 Groovy 类承载复杂逻辑（可以脱离 Jenkins 做单元测试）。resources/ 放静态文件，用 libraryResource 读取。

两个关键实践：引用必须版本化，@Library('platform-ci@v2.4.0') 指向 tag 或 commit，写 master 意味着平台团队一次提交就能同时改掉所有项目的流水线行为；src/ 里的类要实现 Serializable，因为 Pipeline 在每个 step 之后会把执行状态序列化落盘（这是 controller 重启后能续跑的原因），持有不可序列化对象会抛 NotSerializableException，这个报错的成因几乎所有人第一次都想不通。

// ---- 共享库仓库结构 ----
// (root)
//  ├── vars/
//  │    ├── stdBuild.groovy          一个文件就是一个全局步骤，入口必须是 call()
//  │    └── stdBuild.txt             可选文档，会出现在 Pipeline Syntax 页面
//  ├── src/com/acme/ci/Docker.groovy 普通 Groovy 类，放复杂逻辑，便于单测
//  └── resources/deploy/values.yaml  用 libraryResource 读取的静态文件

// vars/stdBuild.groovy
def call(Map cfg = [:]) {
  String label = cfg.get('label', 'linux')
  node(label) {                       // 共享库内部通常写脚本式，控制流更自由
    try {
      stage('Checkout') { checkout scm }
      stage('Build')    { sh cfg.get('buildCmd', './gradlew --no-daemon build') }
      stage('Publish')  {
        new com.acme.ci.Docker(this).buildAndPush(cfg.image, env.GIT_COMMIT.take(12))
      }
    } finally {
      cleanWs()
    }
  }
}

// src/com/acme/ci/Docker.groovy
package com.acme.ci

// 必须 Serializable：Pipeline 在每个 step 之后把程序状态序列化到磁盘，
// 这样 controller 重启后能续跑；持有不可序列化对象会抛 NotSerializableException
class Docker implements Serializable {
  private final def steps
  Docker(steps) { this.steps = steps }

  void buildAndPush(String repo, String tag) {
    steps.sh "docker build -t ${repo}:${tag} ."
    steps.sh "docker push ${repo}:${tag}"
  }
}

// ---- 在 Jenkinsfile 里版本化引用 ----
// 一定要 pin 到 tag 或 commit；写 master 等于所有流水线跟着库的每次提交一起变
@Library('platform-ci@v2.4.0') _

stdBuild(
  label: 'linux && docker',
  image: 'registry.internal:5000/order-service',
  buildCmd: './gradlew --no-daemon build -x test'
)

凭证与安全：Jenkins 是内网横向移动的经典跳板

凭证一律放 Credentials 插件，在流水线里用 withCredentials 块注入，作用域限制在需要它的最小范围内。Jenkins 会尝试把凭证值在日志里替换成星号，但这只是文本匹配：脚本里 base64 一下、逐字符打印、或把它写进 archiveArtifacts 的文件，打码就完全失效。所以不要依赖打码，而要依赖不打印和凭证作用域。同理，用双引号的 Groovy 字符串拼 shell 命令会让密码被插值进命令行，出现在 ps 输出和异常堆栈里；正确写法是用单引号字符串让 shell 自己展开环境变量。

安全侧还有三件事必须做：关闭匿名访问与开放注册（Jenkins 常年是内网扫描的首要目标，未授权访问加脚本执行等于直接拿到一台内网机器）；保留 Script Security 的沙箱机制，不要为了省事把任意方法签名加进 Script Approval；网络上隔离 Jenkins，限制它能主动访问的范围，并把插件数量压到必要范围——每个插件都是一份第三方代码，跑在 controller 的 JVM 里。

凭证类型流水线里怎么用典型场景易错点
Username with passwordwithCredentials([usernamePassword(...)])镜像仓库、私有包仓库登录用双引号插值导致密码进命令行
Secret textwithCredentials([string(...)])API token、webhook 密钥直接 echo 排查，打码被 base64 绕过
Secret filewithCredentials([file(...)])kubeconfig、服务账号 JSON忘了它是临时文件，块外引用路径就没了
SSH private keysshagent(['id'])拉私有仓库、部署到远端key 带口令时要一并配置，否则卡在交互式提示
凭证作用域System / Global / 文件夹级按团队隔离全放 Global，任何 job 都能取到生产凭证

运维要点：JENKINS_HOME 就是全部状态

理解这一句就理解了 Jenkins 运维的全部：配置、job 定义、凭证与加密密钥、插件、构建历史，全都是 JENKINS_HOME 下的文件。它带来两个直接推论：备份 JENKINS_HOME 等于备份整个 Jenkins（尤其 secrets/ 与 credentials.xml 必须一起备，缺了 secrets 恢复后所有凭证都解不开）；磁盘写满等于 Jenkins 挂掉，而构建历史与工作区是最主要的增长源。更好的方向是 Configuration as Code 插件，把实例配置写成 YAML 放进 Git，让配置可 review、可回滚、可重建。

运维项不做的后果怎么做判读信号
JENKINS_HOME 备份机器挂了全部流水线与凭证一起消失每日备份 config、jobs 的 config.xml、users、nodes、secrets/恢复演练是否能在新机器上跑通一条流水线
配置版本化没人知道谁改了什么，回滚靠记忆装 configuration-as-code 插件，casc.yaml 进 GitUI 上出现「该配置由 JCasC 管理」提示
构建历史清理磁盘写满，Jenkins 直接不可用且难恢复每个 job 配 buildDiscarder；大产物改推包仓库du -sh jobs/*/builds 排序看头部
插件升级升一个插件导致所有流水线语法报错先在测试实例装同样组合跑主力流水线；固化插件清单升级后 Manage Jenkins 是否有插件失败告警
JVM 内存UI 卡死、构建随机失败、日志出现 GC overhead按 job 数与并发给堆（常见 4 到 8 GB），用 G1GC 日志停顿时间、jstat 老年代占用
controller executor构建跑在 controller 上，能读凭证、能拖垮实例numExecutors: 0，所有 job 走 labelManage Nodes 上 built-in node 的 executor 数
agent 清理静态 agent 磁盘涨满、工作区互相污染post { always { cleanWs() } }，或直接换动态 agentagent 上 workspace 目录数量与体积

# ---- Jenkins 运维：JENKINS_HOME 就是全部状态 ----

# 1) 先看清磁盘被什么占了：builds 与 workspace 通常是大头
du -sh /var/lib/jenkins/* | sort -h | tail -15
du -sh /var/lib/jenkins/jobs/*/builds | sort -h | tail -10

# 2) 最小可恢复备份集：不含 workspace 与 builds 时通常只有几十 MB。
#    secrets 目录与 credentials.xml 必须一起备份，否则恢复后所有凭证都解不开
tar czf "jenkins-cfg-$(date +%F).tgz" -C /var/lib/jenkins \
  config.xml credentials.xml secrets users nodes jobs \
  --exclude='jobs/*/builds' --exclude='jobs/*/workspace'

# 3) 把插件清单固化下来，重建时按这份装，避免"能跑的版本组合"丢失
java -jar jenkins-cli.jar -s http://jenkins.internal -auth @token \
  list-plugins | awk '{print $1":"$NF}' | tr -d '()' > plugins.txt

# 4) Configuration as Code：让配置也版本化，从"配置即磁盘状态"里逃出来
#    JENKINS_HOME/casc.yaml 片段（装 configuration-as-code 插件后生效）
# jenkins:
#   numExecutors: 0                # controller 上 0 个 executor，禁止在它上面跑构建
#   remotingSecurity: {enabled: true}
#   authorizationStrategy: {roleBased: {}}
#   securityRealm: {ldap: [{server: "ldaps://ldap.internal"}]}

# 5) JVM 参数：堆不足表现为 UI 卡死与构建随机失败，先看 GC 再决定加内存
# JAVA_OPTS="-Xms4g -Xmx4g -XX:+UseG1GC -Djava.awt.headless=true"

# 6) 升级前必做：在测试实例上装同样的插件组合，跑一遍主力流水线。
#    回滚只有一条路：停服务、还原 JENKINS_HOME 与 plugins 目录
systemctl stop jenkins && tar xzf jenkins-cfg-2026-09-01.tgz -C /var/lib/jenkins

迁移判断：什么时候该离开 Jenkins

flowchart TB Q1{"构建必须跑在完全隔离的内网吗"} -->|是| Q2{"托管 CI 的自托管 runner 能接进来吗"} Q2 -->|不能| J["留在 Jenkins，但要改造：JCasC、K8s 动态 agent、共享库"] Q2 -->|能| Q3{"流水线依赖多少插件特有能力"} Q1 -->|否| Q3 Q3 -->|"很少，只是构建测试部署"| M1["迁到 GitHub Actions 或 GitLab CI，配置与代码同仓"] Q3 -->|"很多：老插件、复杂审批链、特殊矩阵"| Q4{"有专人运维 Jenkins 吗"} Q4 -->|有| J Q4 -->|没有| M2["分批迁移：新项目直接用托管 CI，老项目冻结只维护"]

迁移路径上有个务实的次序：先把 Jenkins 里的 job 全部改成 Jenkinsfile（这一步无论迁不迁都值得做），再把构建脚本从 Groovy 里挖出来变成仓库内的 make 或 shell 脚本——这样流水线平台只负责调度，迁移时改的只是几十行 YAML 而不是重写业务逻辑。最后按项目分批切换，保留 Jenkins 处理那些确实只有插件能做的事。

反模式后果正确做法
在 UI 里手点配置自由风格 job无法 review、无法回滚、换人即失传Jenkinsfile + Multibranch Pipeline
所有 job 跑在 controller 上构建能读凭证、能拖垮实例，无隔离numExecutors: 0，全部下沉到 agent
插件装到几百个升级互锁、启动变慢、攻击面膨胀只留必要插件，定期清理无用项
把密钥写进 Groovy 或参数默认值明文进 Git 与构建日志Credentials 插件 + withCredentials
不清理构建历史磁盘写满，实例不可用buildDiscarder + 大产物外置
一条 Jenkinsfile 上千行没人敢改，改了没人能验证Declarative 骨架 + 共享库承载逻辑
共享库引用 master库一提交，全公司流水线同时变引用 tag 或 commit，按项目灰度升级
input 不包 timeout等人的构建永久占着 executor 与队列外包 timeout，并限制 submitter
❌
最容易踩的坑

1）用 agent any 让构建落在 controller 上：构建脚本能读到 JENKINS_HOME 里的凭证，等于没有安全边界。
2）以为同一条流水线的 stage 共享工作区：换 agent 就是新工作区，必须 stash/unstash 或归档。
3）把整个依赖目录 stash：stash 走 controller，几百 MB 会把它的磁盘与网络打满。
4）Kubernetes agent 不写 defaultContainer：step 落进 jnlp 容器，报 command not found。
5）动态 Pod 不设资源 limits：构建把节点 OOM；设得太小则编译被 OOMKilled，表现为无故中断。
6）用双引号 Groovy 字符串拼带密码的命令：密码被插值进命令行，出现在 ps 与异常堆栈。
7）依赖日志打码保护密钥：打码只是文本替换，base64 或逐字符打印即可绕过。
8）input 不包 timeout：没人点的审批永久占着 executor。
9）不配 buildDiscarder：构建历史把磁盘写满，Jenkins 挂掉且恢复困难。
10）备份时漏掉 secrets/：恢复后所有凭证解密失败，等于凭证全丢。
11）共享库或插件不 pin 版本：一次上游变更让几十条流水线同时出问题。
12）为了省事把方法签名加进 Script Approval：沙箱被打穿，任何有 job 编辑权限的人都能在 controller 上执行任意代码。
13）静态 agent 不 cleanWs()：上次构建的残留文件让这次「莫名其妙」通过或失败。
