Jenkins Pipeline

🏷️ Jenkins,CI/CD

一、Jenkins 的定位：灵活到"什么都能做"

Jenkins 诞生于 2011 年（前身 Hudson），是 CI/CD 领域的"活化石"。它没有被 GitHub Actions、GitLab CI 这些后来者淘汰，靠的是两个不可替代的特质：完全自托管（数据不出内网）+ 插件生态（1800+ 插件，几乎能对接任何系统）。银行、国企、大型互联网公司的核心系统，至今大量跑在 Jenkins 上——因为合规要求流水线必须留在自己机房，而 Jenkins 恰好满足。代价是：它需要有人维护，插件冲突、升级地狱是真实存在的成本。

二、核心概念与 Pipeline as Code

现代 Jenkins 的正确用法不是在 UI 上点配，而是用 Jenkinsfile 描述流水线并提交进代码仓库（Pipeline as Code）。Jenkinsfile 有两种语法：

  • Declarative Pipeline（声明式）：结构化、受校验、推荐用于大多数场景，结构是 pipeline { agent any stages { stage('Build') { steps { ... } } } }。
  • Scripted Pipeline（脚本式）：基于 Groovy 的命令式写法，灵活但难维护，只在需要复杂逻辑（动态分支、条件循环）时使用。

核心术语：agent（执行节点）、stage（阶段，对应流水线可视化上的一个方块）、steps（步骤）、post（后置处理，无论成功失败都执行清理/通知）、environment（环境变量与凭证绑定）。

三、安装：用 Docker 快速起一套

不推荐在裸机上裸装，Docker 方式最干净，升级、迁移、备份都容易：

# 1. 拉取 LTS 镜像并启动，挂载数据目录
docker run -d --name jenkins \
  -p 8080:8080 -p 50000:50000 \
  -v jenkins_home:/var/jenkins_home \
  -v /var/run/docker.sock:/var/run/docker.sock \
  jenkins/jenkins:lts-jdk17

# 2. 查看初始管理员密码
docker exec jenkins cat /var/jenkins_home/secrets/initialAdminPassword

# 3. 浏览器打开 http://localhost:8080，选择 "Install suggested plugins"
# 4. 安装必备插件：Pipeline、Git、Docker、Kubernetes Credentials、Role-based Authorization Strategy
# 5. 新建任务 → 选择 Pipeline → Definition 选 "Pipeline script from SCM"，指向仓库里的 Jenkinsfile

把 /var/run/docker.sock 挂进容器，是为了让 Jenkins 容器内部能调用 Docker（即"Docker outside Docker"模式）来构建镜像。生产环境更推荐 Kubernetes 插件：让每个流水线动态申请一个 Pod 作为 agent，用完即毁，比固定机器资源利用率高得多。

我踩过的坑：插件地狱

有次我升级 Jenkins，点了"全部更新插件"，结果 Pipeline 插件和某个旧插件版本不兼容，整个流水线全部挂掉。回滚都来不及——备份忘了做。从那以后我定了三条规矩：① 升级前先在测试实例跑一遍；② 插件更新逐个来，别一键全更；③ 每周备份一次 JENKINS_HOME。Jenkins 本身不难，难的是养它。

四、实战示例 1：声明式 Jenkinsfile 完整流水线

下面是一个 Java/Maven 项目的标准流水线：拉代码 → 编译测试 → 构建镜像 → 部署测试环境 → 等待人工审批 → 生产发布。所有凭证通过 credentials() 注入，绝不明文：

pipeline {
  agent any
  options {
    timestamps()
    buildDiscarder(logRotator(numToKeepStr: '20'))
    timeout(time: 30, unit: 'MINUTES')
  }
  environment {
    IMAGE = "registry.example.com/app:${BUILD_NUMBER}"
  }
  stages {
    stage('Checkout & Test') {
      steps {
        checkout scm
        sh 'mvn -B -DskipTests=false clean test'
      }
    }
    stage('Build Image') {
      steps {
        sh 'mvn -B package -DskipTests'
        sh "docker build -t ${IMAGE} ."
        withCredentials([usernamePassword(credentialsId: 'registry-cred',
                                         usernameVariable: 'REG_USER',
                                         passwordVariable: 'REG_PASS')]) {
          sh 'echo $REG_PASS | docker login registry.example.com -u $REG_USER --password-stdin'
          sh "docker push ${IMAGE}"
        }
      }
    }
    stage('Deploy Staging') {
      steps {
        sh "kubectl set image deployment/app app=${IMAGE} -n staging"
      }
    }
    stage('Approve & Deploy Prod') {
      steps {
        input message: '确认发布到生产？', ok: '发布'
        sh "kubectl set image deployment/app app=${IMAGE} -n production"
      }
    }
  }
  post {
    success { echo 'Pipeline succeeded' }
    failure { echo 'Pipeline failed, notify on-call' }
    always  { sh 'docker image prune -f || true' }
  }
}

几个关键点：options 里的 buildDiscarder 自动清理历史构建，防止磁盘写满；input 步骤天然实现"人工卡点"，比外部审批系统更内聚；post.always 保证无论成败都清理悬空镜像——这是 Jenkins 跑久了磁盘爆掉的最常见原因。

五、实战示例 2：Dockerfile 与多分支并行

配合上面流水线使用的多阶段 Dockerfile，以及多分支流水线配置：

# ---- 构建阶段 ----
FROM maven:3.9-eclipse-temurin-17 AS build
WORKDIR /src
COPY pom.xml .
RUN mvn -B dependency:go-offline          # 先缓存依赖层
COPY src ./src
RUN mvn -B package -DskipTests

# ---- 运行阶段 ----
FROM eclipse-temurin:17-jre-alpine
RUN addgroup -S app && adduser -S app -G app
WORKDIR /app
COPY --from=build /src/target/*.jar app.jar
USER app
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "/app/app.jar"]
// Jenkinsfile 顶部添加：按分支决定行为
pipeline {
  agent any
  stages {
    stage('Build') {
      steps { echo "building branch=${env.BRANCH_NAME}" }
    }
    stage('Deploy') {
      when {
        branch 'main'          // 只有 main 分支才部署
      }
      steps { echo 'deploy to prod' }
    }
    stage('Preview') {
      when {
        allOf { branch 'feature/*'; environment name: 'RUN_IT', value: 'true' }
      }
      steps { echo '部署预览环境' }
    }
  }
}

when { branch 'main' } 实现了"只在主干部署"，feature 分支只跑构建测试；结合 Multibranch Pipeline 任务，Jenkins 会自动为每个分支/PR 建一条流水线，这就是企业级"分支即环境"的基础。

六、最佳实践

  • Jenkinsfile 入库：流水线和代码同仓，改动走 review，UI 只留触发器和凭据。
  • 用 Kubernetes Agent：固定 agent 机器资源利用率低且堆积脏状态，动态 Pod agent 按需启停。
  • 插件治理：插件越多越脆。定期用 "Plugin Installation Manager" 清理未用插件，升级前先在测试实例验证，千万别在凌晨点"全部更新"。
  • 凭证集中管理：所有密钥走 Credentials 绑定 ID，Jenkinsfile 里只引用 ID，禁止 export PASS=xxx。
  • 主从分离 + 备份：Master 只做调度，构建全放 agent；定期备份 JENKINS_HOME（任务、凭据、历史都在这里）。
  • 共享库复用：团队多项目时把公共步骤抽成 Shared Library，各仓库 Jenkinsfile 只写业务差异。

七、常见问题 FAQ

Q1：Jenkins 构建动不动卡住，日志不更新怎么办？

先看"Executor 数量"是否被占满：系统管理 → 节点管理，看是否所有 executor 都在跑，卡住的任务是否僵尸进程。常见根因：① 某个 step 在等输入（比如交互式命令）；② Docker daemon 卡死，挂 socket 的 Jenkins 跟着挂；③ 磁盘满导致写日志阻塞。排查顺序：看系统日志、磁盘空间、Docker 状态，必要时重启 agent 而非 Master。

Q2：Jenkins 和 GitHub Actions 怎么选？

三个判断维度：代码在 GitHub 且无强私有化要求 → GHA；代码在 GitLab 自建 → GitLab CI；必须内网、需要对接企业自有系统（如内部制品库、堡垒机审批、国产化平台）→ Jenkins。Jenkins 的隐性成本是"有人维护"，如果团队没有全职运维 CI 的人，选托管方案能省一半心。

Q3：多分支流水线里，每个 PR 都部署一个环境会不会太浪费？

直接给每个 PR 起一套完整环境确实贵，常见折中：① PR 阶段只跑构建+测试，不部署；② 需要联调时手动触发部署到"预览命名空间"，用 K8s 的 namespace + 域名前缀隔离，用后即毁；③ 资源按命名空间设 limit，防止单个 PR 吃满集群。

八、总结

Jenkins 的价值在于"完全可控"：声明式 Pipeline 把流程结构化，Kubernetes Agent 把执行环境弹性化，插件生态把一切系统接进来。它的门槛不是语法，而是运维——插件治理、备份、权限、性能，这些是把 Jenkins 用稳的真功夫。
