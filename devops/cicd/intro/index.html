CI/CD 工具选型

🏷️ CI/CD,DevOps

一、为什么需要 CI/CD：从手工发版到自动化流水线

十年前，一个典型的发布动作是这样的：开发在本地打包，把产物 scp 到生产服务器，手动停服务、替换文件、起进程、看日志，整个过程依赖一两个"资深运维"的经验。当代码仓库只有几十个人维护时，这种方式勉强可行；但在微服务时代，一个版本可能牵动几十个仓库、上百个服务，手工发版慢得离谱，每次都在赌运气——忘了传一个配置文件、生产包不是干净分支构建的、回滚靠人肉记忆，任何一处纰漏都是一次线上事故。

CI/CD 就是为了消灭这种"人肉环节"而生的工程实践。它的核心思想朴素而深刻：把构建、测试、打包、部署的过程固化成代码（Pipeline as Code），每次代码变更都自动执行一遍，任何一步失败立刻阻断。这样一来，问题在提交后几分钟内就会暴露，而不是等到凌晨两点用户投诉时才发现。

二、CI/CD 的演进脉络

理解工具选型之前，先理清概念演进的三个阶段，很多人混淆"持续交付"和"持续部署"，其实它们是成熟度阶梯上的不同层级：

  • 持续集成（Continuous Integration, CI）：开发者频繁地将代码合入主干，每次合入都自动触发构建与测试。目标是尽早暴露集成冲突，保证主干永远可编译、可测。
  • 持续交付（Continuous Delivery, CD）：在 CI 基础上，自动把通过测试的产物部署到类生产环境，做到"随时可发布"，但是否点击生产发布按钮仍由人决定。这是绝大多数团队的现实目标。
  • 持续部署（Continuous Deployment）：更进一步，通过全部自动化门禁（含生产验收指标）后直接发布到生产，无需人工干预。对测试完备性和可观测性要求极高。

三、核心概念拆解

无论用哪款工具，下面这些概念是通用的，先建立统一词汇表：

  • Pipeline（流水线）：一条从代码变更到交付的有向无环图，由若干阶段（Stage）和步骤（Step）组成。
  • Stage / Stage Gate：逻辑分组（如 build → test → deploy），Stage 之间通常是串行依赖。
  • Runner / Agent：真正执行命令的计算资源。工具只负责调度，干活的是 Runner——这就是为什么自托管 Runner 能解决内网资源访问问题。
  • Artifact（制品）：构建产出的不可变产物，如 Docker 镜像、jar 包。制品一旦产出就不该重新构建，而应该在各环境间流转。
  • Cache vs Artifact：Cache 用于加速（如 node_modules、~/.m2），可丢失；Artifact 是阶段间传递的交付物（如编译产物），不可丢失。
  • Trigger（触发器）：什么事件启动流水线——push、PR、tag、定时、手动、外部 Webhook。
  • Secret（密钥）：部署凭证、镜像仓库密码，必须加密存储，禁止写进 YAML。

四、主流工具生态与选型

当下主流 CI/CD 工具可以分三档：

工具定位优势适用团队
GitHub Actions云托管，与 GitHub 深度集成配置即仓库文件，市场 Action 生态丰富，开源项目首选GitHub 托管项目、中小团队、开源
GitLab CI一体化 DevOps 平台内置代码托管+CI+CD，Runner 自托管灵活，企业私有化成熟用 GitLab 自建/企业版的团队
Jenkins老牌自托管自动化服务器插件 1800+，最灵活，可定制任何流程复杂企业场景、需要深度定制
云厂商流水线CodePipeline / 云效 / CODING与云资源天然打通，免运维重度使用某云的企业

选型时不要迷信"哪个最火"，问自己三个问题：代码托管在哪里？团队是否愿意维护一套 CI 服务器？流水线是否需要跨团队复用与权限隔离？ 代码在 GitHub 就别硬上 Jenkins，除非有强合规要求；企业内网且用 GitLab，GitLab CI 几乎是零额外成本的最优解；只有当流水线复杂到需要自定义插件、多系统编排时，Jenkins 的灵活性才值回它的维护成本。

我的选型教训

2019 年我在一家创业公司，团队只有 5 个人，代码都在 GitHub 上。当时我"听说 Jenkins 最强大"，花了两周搭了一套 Jenkins Master + 3 个 Agent，配了 20 多个插件。结果呢？每周都在修 Jenkins 本身的问题——插件冲突、磁盘满、内存泄漏。后来迁到 GitHub Actions，配置文件提交到仓库就完事，我再也不用操心 CI 服务器了。5 人团队用 Jenkins 是给自己找活干。

五、最小可用流水线：一个通用骨架

无论工具差异多大，一条健康的流水线永远遵循"提交 → 构建 → 测试 → 制品 → 部署"的骨架。下面以 GitHub Actions 风格的 YAML 展示其结构（下一篇会深入语法）：

name: ci
on:
  push:
    branches: [main]
  pull_request:
jobs:
  build-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: '20' }
      - run: npm ci
      - run: npm run lint
      - run: npm test -- --coverage
      - run: npm run build

  package:
    needs: build-test
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: docker build -t myapp:${{ github.sha }} .
      - run: echo "${{ secrets.REGISTRY_TOKEN }}" | docker login -u ci --password-stdin registry.example.com
      - run: docker push registry.example.com/myapp:${{ github.sha }}

在提交前用同一个脚本在本地跑一遍，能避免"push 上去才发现 lint 没过"的低效循环。下面这个 pre-push 钩子把检查固化在本地，红灯在你按回车之前就亮：

#!/usr/bin/env bash
# .git/hooks/pre-push —— 本地预检查，等价于 CI 前半段
set -e
echo "[pre-push] lint..."
npm run lint
echo "[pre-push] unit test..."
npm test -- --coverage
echo "[pre-push] build..."
npm run build
echo "[pre-push] ok, pushing..."

注意三个设计要点：① needs 显式声明依赖，测试不通过就不会进入打包；② 镜像 tag 用 git commit SHA 而非 latest，保证任何线上版本都能追溯到具体代码；③ 凭证通过 secrets 注入，绝不硬编码。

六、最佳实践

  • 流水线即代码：Pipeline 配置必须和业务代码同仓管理，走 code review，禁止在 UI 上点点点维护流程。
  • 主干开发 + 短分支：CI 的价值随分支生命周期缩短而放大。分支活一周，CI 就只是个形式。
  • 快速失败：把最快、最便宜的检查（lint、单测）放最前面，集成测试和部署放后面，让红灯在一分钟内亮起。
  • 不可变制品：一次构建产物在所有环境复用，环境差异只通过配置注入（环境变量、配置中心），绝不重新打包。
  • 流水线权限最小化：CI 用的部署账号只给必要环境的必要权限；生产发布最好单独一把钥匙。
  • 保留失败现场：测试失败自动上传日志、截图、core dump 作为 artifact，别让调试变成"再跑一遍试试"。

七、常见问题 FAQ

Q1：CI 跑一次要 20 分钟，团队已经放弃触发了，怎么办？

慢是 CI 最大的敌人。按收益排序优化：① 用缓存把依赖安装（node_modules、~/.m2、vendor）从每次跑变成增量；② 拆 Job 并行执行，单元测试不需要等打包；③ 把重型测试（E2E、性能）移到夜间或合并后再跑，PR 门禁只保留快速测试；④ 换更快的 Runner 或用本地缓存的 Docker 镜像。经验法则：PR 门禁应该在 5 分钟内出结果，否则团队一定会绕过它。

Q2：持续交付是不是意味着每次合并都上生产？

不是。持续交付强调的是"主干随时处于可发布状态"，而不是"每次合并都发布"。发布节奏可以是每周一次、每个迭代一次，区别在于：以前发布要准备两天，现在按下按钮十分钟完成。真正每次合并都上生产的是持续部署，那需要完善的自动化验收（灰度指标、自动回滚），多数团队达不到那个成熟度。

Q3：老项目没有测试，能不能先上 CI/CD？

可以，但要降低门禁要求。第一阶段只做"构建必须通过 + 部署自动化"，测试门禁先不卡；第二个阶段补关键路径的回归测试；第三个阶段再把测试纳入强制门禁。不要因为"没有完整测试"就拒绝自动化部署——先让部署过程标准化、可重复，本身就是巨大收益，测试可以渐进补齐。

八、总结

CI/CD 的本质不是某个工具，而是一种工程纪律：让每一次代码变更都被自动验证，让交付过程可重复、可追溯、可回滚。工具选型只是落地手段——GitHub Actions 适合 GitHub 生态的轻量起步，GitLab CI 适合一体化私有化团队，Jenkins 留给需要极致灵活的复杂场景。掌握了"流水线即代码、制品不可变、快速失败"这三条原则，无论换成哪款工具，迁移成本都远小于业务收益。接下来三篇文章，我们分别上手这三套工具，之后再落地到容器化与生产部署策略。
