第一条流水线怎么搭：五步落地路线、触发策略与分支匹配

🏷️ CI/CD 入门

这篇讲落地顺序：手上有一个还没有任何自动化的仓库，第一条流水线该长什么样，之后按什么顺序加东西。流水线的设计原则（阶段划分、卡点判定、DORA 度量）在主干篇里，具体工具的语法在本组的 Jenkins、GitHub Actions、GitLab CI 三篇里。

分五步落地，不要一次画完整条流水线

常见的失败路径是：第一天就照着教科书画出「检查、单测、构建、镜像、集成、预发、验收、生产」八个阶段，两周后被全员绕过。原因很简单——阶段数量决定失败点数量，而失败点多于团队的治理能力时，门禁一定会被关掉。正确做法是一步一步加，每一步都要等前一步真的被团队接受。

stateDiagram-v2 [*] --> 提交即跑单测 提交即跑单测 --> 静态检查与编译: 红灯已被当回事 静态检查与编译 --> 产出可部署产物: 检查项稳定不误报 产出可部署产物 --> 自动部署测试环境: 制品仓库与版本规则就绪 自动部署测试环境 --> 预发与生产可控发布: 部署脚本幂等且可重跑 预发与生产可控发布 --> [*] 提交即跑单测 --> 提交即跑单测: 测试不可信 先治随机失败 自动部署测试环境 --> 产出可部署产物: 环境漂移 先做配置外置 note right of 提交即跑单测 目标不是覆盖率 是让团队相信红灯代表真的坏了 end note note right of 预发与生产可控发布 这一步才需要灰度与回滚能力 前四步都不该碰生产 end note
步骤只做这些做完的判定标准常见卡点
一、提交即跑单测任何提交自动跑单元测试，结果回显到代码托管平台连续两周没有出现红灯超过 1 小时无人处理；开发承认红灯可信存量测试本来就有失败，于是第一天就把门禁设成「允许失败」，之后再也没改回来
二、加静态检查与编译格式化自动修复、静态检查按基线只卡新增、确认能编译检查项一周内零误报争议；格式问题不再出现在评审意见里规则一次性全开，几千条存量告警让人直接关掉整个检查
三、产出可部署产物构建容器镜像或包，打 sha 标签推到制品仓库，记录 digest随机取一次构建，能在任意机器上用同一 digest 拉起来跑产物里硬编码了环境地址，导致同一个产物无法在别的环境用
四、自动部署测试环境合并主干后自动部署到测试环境，跑冒烟部署脚本连续执行两次结果一致；测试环境版本可查到对应提交部署脚本不幂等，重跑会叠出两套实例或者直接失败
五、预发与生产可控发布预发验收、放行闸门、生产分批发布、回滚通道做过一次真实的回滚演练并在 10 分钟内完成没有回滚预案就先开了自动部署，第一次故障时手忙脚乱
✅
第一步的目标不是覆盖率，是建立信任

很多团队第一步就去追覆盖率数字，结果写了一批没有断言的测试。第一步真正要建立的是一条社会契约：红灯意味着代码真的坏了，看到红灯就得停下来处理。这条契约建立起来之后，后面每加一个检查项都是顺势而为；契约没建立，加得越多绕得越多。

触发策略：什么事件跑什么

把所有检查绑在「任何 push」上是最省事的写法，也是最快把流水线拖慢的写法。触发事件与检查内容要分开设计：挡在人面前的检查必须快，异步跑的检查才可以慢。

flowchart TB E["收到一个事件"] --> Q1{"是否挡在开发面前"} Q1 -- 是 --> Q2{"能否只跑受影响范围"} Q2 -- 能 --> F1["PR 轻量校验 目标 10 分钟内"] Q2 -- 不能 --> F2["拆分并行 或移到合并后"] Q1 -- 否 --> Q3{"是否产出要上生产的产物"} Q3 -- 是 --> Q4{"版本号是否需要人来决定"} Q4 -- 是 --> F3["由打标签触发 产出正式版本"] Q4 -- 否 --> F4["合并主干触发 产出 sha 版本"] Q3 -- 否 --> F5["定时任务 全量回归与依赖扫描"] F5 --> F6["结果只告警 不阻断任何人"]
触发方式该跑什么不该跑什么时长要求
PR 创建与更新格式、静态检查新增项、受影响范围单测、编译全量端到端、真实第三方调用、部署动作10 分钟以内，越快越好
推送到主干全量单测、集成测试、契约测试、构建产物推仓库、部署测试环境直接发生产（除非确实在做持续部署）30 分钟以内
打版本标签给已有 digest 加语义化版本别名、生成变更说明、触发发布流程重新构建产物分钟级，因为不该有构建
定时任务全量回归、依赖漏洞扫描、长稳测试、镜像基线刷新任何会阻断开发的门禁不限，但要有失败通知归属人
手动触发指定 digest 部署到指定环境、回滚、数据修复脚本手动构建产物（构建只能由代码事件触发）不限，但必须记录操作人与目标版本

三种触发在时间轴上的关系，以及产物如何在其中流转：

分支策略决定 CI 的上限

这是最容易被忽略的因果关系：分支活得越久，集成越痛，所以 CI 的实际效果和分支策略强相关。流水线只能验证已经合到一起的代码，一个存活两周的分支，在这两周里对它跑得再勤，也只是在验证它自己那一份，主干上别人的改动一次都没被一起验证过。

适合场景持续交付或持续部署，服务端为主迭代快、版本概念弱的产品有明确版本号、需要同时维护多个已发布版本（客户端、私有化交付）
对 CI 的实际影响集成风险被摊平到每天风险按分支寿命累积集成风险集中在版本合并点爆发
⚠️
「因为功能没做完所以不能合主干」是个伪约束

这句话背后的真实约束是「不能让用户看到未完成的功能」，而这跟代码在哪儿没关系。把代码合进主干、用开关默认关闭，用户看不到，集成风险却被消解了。真正需要长命分支的场景只有一类：要长期维护多个已发布版本，比如私有化交付或客户端产品。纯服务端业务坚持 Git Flow，通常只是习惯。

测试金字塔在流水线里的落位

测试分层不是学术分类，它决定了每一类测试该被放进哪个阶段。判据是两条：越快越稳的越靠前，失败信息越精确的越靠前。

测试类型建议占比单条耗时量级放在哪个阶段失败时说明什么
单元测试70 分左右毫秒级PR 与提交阶段某个函数或类的逻辑错了，定位精确
集成测试20 分左右秒级合并主干后模块之间的协作错了，或 SQL、序列化、配置有问题
契约测试少量但每个对外接口都要有秒级合并主干后接口形状发生了不兼容变化，会打破调用方
端到端测试10 分以下，只留关键路径数十秒到分钟部署预发后或定时某条业务流程坏了，但不告诉你坏在哪一层
发布后冒烟数条只读校验秒级每次生产发布之后这次部署本身出了问题，应立即停止扩大范围

倒金字塔（界面端到端最多、单测最少）会让流水线不可用，原因有三：一是慢，几百条端到端就是几小时；二是脆，依赖界面结构、网络、数据准备，随机失败率远高于单测；三是定位难，只告诉你流程坏了，不告诉你哪一层坏了。更糟的连锁反应是——因为它经常随机失败，团队开始习惯性重跑，于是连真实缺陷也被重跑掉了。

产物该是什么，配置放在哪

流水线的中间产物形态决定了后续能不能做到「一次构建多处部署」。判断标准很简单：这个产物拿到另一台机器上，不改它内部任何一个字节，能不能跑起来。

产物形态包含什么适合场景要注意的坑
容器镜像运行时、依赖库、应用二进制服务端应用，需要环境一致性镜像里不能带任何环境地址与密钥，否则一个环境一个镜像
可执行二进制静态链接的单文件Go、Rust 等编译型语言，裸机或容器都能用动态链接时会依赖目标机的系统库版本，跨发行版会失败
语言包（jar、wheel、npm 包）字节码或源码加依赖声明库的分发，或运行时已统一的环境依赖在部署时才解析，等于把构建的不确定性推到了生产
静态资源包编译后的 HTML、JS、CSS 与带哈希的文件名前端应用接口地址如果编译进去了，就没法一个包多环境用，要改成运行时读取
基础设施描述文件声明式的资源定义环境本身的变更与应用产物的版本对应关系要显式记录，否则回滚时不知道该回哪个

配置外置是「一次构建多处部署」的另一半。原则是配置从环境读取，产物里不含任何环境信息；配置项缺失时应该启动失败并明确报出缺了哪个，而不是悄悄用一个默认值跑起来：

// 启动时一次性加载并校验，缺失即失败退出
// 反面做法是在业务代码里到处 os.Getenv，配错了要等到调用那行才暴露
type Config struct {
    DatabaseURL string // 必填，不同环境不同
    RedisAddr   string // 必填
    ListenAddr  string // 有合理默认值
    LogLevel    string // 有合理默认值
}

func Load() (*Config, error) {
    c := &Config{
        DatabaseURL: os.Getenv("DATABASE_URL"),
        RedisAddr:   os.Getenv("REDIS_ADDR"),
        ListenAddr:  envOr("LISTEN_ADDR", ":8080"),
        LogLevel:    envOr("LOG_LEVEL", "info"),
    }
    // 必填项集中校验，一次把所有缺失的都报出来，
    // 而不是缺一个报一个让人来回改五遍
    var missing []string
    if c.DatabaseURL == "" {
        missing = append(missing, "DATABASE_URL")
    }
    if c.RedisAddr == "" {
        missing = append(missing, "REDIS_ADDR")
    }
    if len(missing) > 0 {
        return nil, fmt.Errorf("缺少必填环境变量: %v", missing)
    }
    return c, nil
}

func envOr(key, def string) string {
    if v := os.Getenv(key); v != "" {
        return v
    }
    return def
}

让流水线可信的三件事

流水线的价值建立在「它说通过就是真的通过，它说失败就是真的坏了」之上。这条信任一旦破掉，后面所有投入都白费。破坏信任的原因基本只有三类。

第一件：消灭随机失败的测试。识别手段是主动制造压力，而不是等它自己冒出来：

#!/usr/bin/env bash
# 随机失败测试的主动探测：在定时任务里跑，不要放在 PR 门禁上
set -uo pipefail

TARGET=${1:-./...}
ROUNDS=${2:-20}
FAILED=0

for i in $(seq 1 "$ROUNDS"); do
  # shuffle 打乱执行顺序，暴露「依赖测试之间顺序」的用例
  # count=1 绕过结果缓存，否则第二轮之后根本不会真的执行
  # race 暴露数据竞争，parallel 提高并发争用概率
  if ! go test -count=1 -race -shuffle=on -parallel 8 -timeout 5m "$TARGET" \
        > "/tmp/round-$i.log" 2>&1; then
    FAILED=$((FAILED + 1))
    echo "第 $i 轮失败，失败用例："
    grep -E '^--- FAIL' "/tmp/round-$i.log" | sort -u
  fi
done

echo "失败率: $FAILED / $ROUNDS"
# 稳定的测试集在 20 轮里应该 0 失败。只要有 1 次，就按缺陷登记
[ "$FAILED" -eq 0 ] || exit 1
随机失败的根因典型症状修法
固定端口或固定临时文件路径并行跑时报地址已被占用，串行跑就好了端口传 0 让系统分配，临时目录用测试框架提供的隔离目录
依赖测试之间的执行顺序单独跑通过，全量跑失败；打乱顺序后失败率上升每个用例自己准备与清理数据，禁止用包级可变状态传递
用睡眠等待异步结果构建机负载高时失败，本地从不失败改成轮询条件加超时，或用通道与回调显式同步
断言里带当前时间或随机数跨日、跨时区、跨月末时失败时间源注入成可替换的接口，随机种子固定
共享数据库没有隔离两个任务同时跑时互相踩数据每个任务用独立 schema 或独立容器实例
依赖外部网络失败原因是连接超时而非断言不符单测一律打桩，真实调用放到集成测试并标记可跳过

第二件：构建可重复。锁文件必须提交并在流水线里用「严格按锁文件安装」的模式，不允许自动升级；基础镜像固定到 digest 而非浮动标签；编译参数里去掉构建机的绝对路径与时间戳。

第三件：失败信息要能直接定位。一次失败的日志里必须能直接看出：哪个阶段、哪条用例、期望什么实际什么、相关的产物或截图在哪。做不到这一点，开发的第一反应永远是「先重跑一次看看」。

与工具无关的阶段定义

不管最后选哪个工具，阶段与依赖关系的结构是一样的。先把下面这份结构想清楚，再去翻具体工具的文档，翻译过去只是语法问题：

# 这是结构示意，不绑定任何具体产品：先确定阶段、依赖、产物流向
stages:
  - name: verify          # 提交阶段：挡在人面前，必须快
    timeout: 10m
    jobs:
      - id: lint
        run: ./ci/lint.sh              # 逻辑放脚本里，本地可复现
        cache: [deps]
      - id: unit-test
        run: ./ci/test-unit.sh
        cache: [deps, build]
        parallel: 4                    # 分片并行，把 5 分钟预算压住
      - id: compile
        run: ./ci/build.sh
        cache: [deps, build]
        artifacts: [dist/]             # 产物传给下一阶段，不重复构建

  - name: package         # 只在主干执行：产出唯一产物
    needs: [verify]
    only: [branch:main]
    jobs:
      - id: image
        run: ./ci/package.sh
        artifacts: [artifact-ref.txt]  # 记录 digest，后续按它部署

  - name: acceptance      # 可以慢，但必须并行
    needs: [package]
    timeout: 30m
    jobs:
      - id: integration
        run: ./ci/test-integration.sh
        services: [postgres, redis]    # 依赖用容器即起即用
      - id: contract
        run: ./ci/test-contract.sh

  - name: deploy-staging
    needs: [acceptance]
    jobs:
      - id: staging
        run: ./ci/deploy.sh staging "$(cat artifact-ref.txt)"
        environment: staging

  - name: deploy-prod
    needs: [deploy-staging]
    gate: manual                       # 持续交付：这里由人放行
    jobs:
      - id: prod
        run: ./ci/deploy.sh prod "$(cat artifact-ref.txt)"
        environment: prod              # 生产凭证只绑在这个环境上

注意每个 job 的 run 都指向仓库里的脚本，而不是把命令写在流水线配置里。这样做的直接收益是本地能跑同一套检查，「本地好的推上去红」这类问题大幅减少：

#!/usr/bin/env bash
# ci/local.sh —— 本地复现提交阶段。和流水线调用的是同一批脚本
set -euo pipefail

# 关键设计：把检查逻辑放在 ci/ 下的脚本里，流水线只负责调用。
# 流水线配置里一旦写了 inline 命令，本地就永远无法真正复现
export CI=true

echo "==> 1/4 检查工作区是否干净"
# 流水线是干净检出，本地常有未提交文件。这是「本地好推上去红」的头号原因
if [ -n "$(git status --porcelain)" ]; then
  echo "警告：存在未提交改动，流水线看不到这些文件"
  git status --short
fi

echo "==> 2/4 依赖严格按锁文件安装"
go mod download
# 校验锁文件没有被隐式修改；流水线里这一步应该直接失败
git diff --exit-code go.mod go.sum

echo "==> 3/4 静态检查"
./ci/lint.sh

echo "==> 4/4 单元测试"
./ci/test-unit.sh

# 仍然复现不了时，用容器跑一遍，把本机环境差异彻底排除：

「本地好的推上去红」的六个常见原因

语言或编译器小版本不同；本地有未提交文件而流水线是干净检出；本地保留了上一次的编译与测试缓存；本地环境变量或配置文件在流水线里不存在；文件名大小写敏感性不同（macOS 不敏感，Linux 敏感）；时区与语言环境不同导致时间与排序断言不一致。逐个猜很慢，把检查收敛到一个脚本并在干净容器里跑一次，差异会立刻暴露。

新手最容易踩的坑

❌
避坑指南
  • 第一天就上完整八阶段流水线，失败点多于治理能力，两周后被全员绕过。
  • 存量测试本来就在失败，于是把门禁设成允许失败先跑起来，之后再也没改回来。
  • 把全量端到端测试放进 PR 检查，反馈从 5 分钟变成 40 分钟，开发开始攒大提交。
  • 静态检查规则一次性全开，几千条存量告警让人直接关掉整个检查。
  • 发布时重新构建产物，于是上生产的东西和测试过的不是同一个。
  • 产物里硬编码了环境地址或接口域名，一个环境只能用一个镜像，配置分离形同虚设。
  • 缺少必填配置时用默认值悄悄启动，服务跑起来了但连到了错误的数据库。
  • 部署脚本不幂等，重跑一次叠出两套实例，或者第二次直接失败。
  • 依赖安装用会自动升级的命令而不是严格按锁文件安装，同一提交两天后构建结果不同。
  • 把检查命令写在流水线配置里而不是仓库脚本里，本地永远无法复现流水线行为。
  • 给随机失败的测试配自动重试，红灯从此不可信，真实缺陷也被重跑掉。
  • 因为「功能没做完」而把分支留两周，等到合并时冲突与语义不兼容一次性爆发。
  • 先开自动部署再补回滚方案，第一次线上故障时才发现没有回滚通道。

阶段划分与卡点判定的完整依据见主干篇；部署策略、灰度与回滚见部署篇。K8s 上的探针与滚动更新细节详见站内 Kubernetes，依赖漏洞扫描与密钥泄露见 OWASP Top 10，把 Git 当部署事实来源的模式见 GitOps。
