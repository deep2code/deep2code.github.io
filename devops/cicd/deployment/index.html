部署策略与发布安全：五种策略对照、金丝雀自动判定与数据库兼容演进

🏷️ CI/CD

流水线把产物送到了制品仓库，剩下的问题只有一个：怎么让这个产物安全地进入生产。这篇讲部署策略与发布安全，流水线的阶段设计见主干篇，第一条流水线怎么搭见工具选型篇。

五种部署策略的对照矩阵

选策略不是看哪个先进，而是看你的约束：能不能停机、有多少冗余资源、网关支不支持按权重分流、这次变更是否碰了数据库。

金丝雀的控制回路

金丝雀最常被误解的地方是把它当成「先发一小部分」。金丝雀的价值全在「观察什么指标、多久、谁来判定」这三个问题的答案上，动作本身不产生任何安全性。

观察指标判定口径为什么必须看只看它的盲区
业务成功率（下单成功、支付成功）金丝雀相对基线下降超过 0.5 分即回滚这是唯一直接代表用户受损的指标低峰期样本量不足，波动会误判
接口错误率（5xx 与业务错误码）相对基线上升超过 0.2 分即回滚反应最快，通常几十秒内就能看出被上游重试掩盖，看起来错误率没变但延迟升高
延迟 p99相对基线上升超过 20 分即告警，超过 50 分回滚性能回退不报错，只有分位数能发现金丝雀实例刚启动时缓存是冷的，前几分钟天然偏高
依赖调用量与慢查询数单请求的下游调用次数不应变化能抓出「循环里查数据库」这类只在真实流量下暴露的问题需要提前埋好按版本区分的埋点
CPU 与内存仅作为辅助信号能发现内存泄漏与死循环单看资源指标几乎等于不看，业务全错也可能 CPU 正常
❌
没有自动判定的金丝雀，只是手动分批重启

如果放了 5 分流量之后没人盯指标，或者只是有人扫一眼大盘觉得「没啥异常」就点了继续，那么这套机制既没有缩短故障时长，也没有降低最终影响面——它退化成了分批重启。让它真正成立需要三个明确答案：看哪些指标（业务成功率优先于资源指标）、观察多久（样本量足够且覆盖一个业务周期，低峰期要相应延长）、谁来判定（最好是程序自动比对新旧版本差异并自动回滚）。

#!/usr/bin/env bash
# 金丝雀自动判定：对比金丝雀与基线的同期指标，超阈值直接回滚
# 关键点是「和同期基线比」而不是「和固定阈值比」，否则大促当天必然误判
set -euo pipefail

PROM=${PROM:-http://prometheus:9090}
SVC=$1                      # 服务名
WINDOW=${2:-5m}             # 观察窗口
MIN_SAMPLES=${3:-500}       # 样本量下限，样本不足时不做判定

q() { # 查询单个标量值，取不到时返回 0
  curl -sG "$PROM/api/v1/query" --data-urlencode "query=$1" \
    | python3 -c 'import json,sys; d=json.load(sys.stdin)["data"]["result"]; print(d[0]["value"][1] if d else 0)'
}

# 样本量守门：请求数太少时任何比率都没有统计意义，直接延长观察
REQS=$(q "sum(increase(http_requests_total{service=\"$SVC\",track=\"canary\"}[$WINDOW]))")
if [ "$(printf '%.0f' "$REQS")" -lt "$MIN_SAMPLES" ]; then
  echo "样本不足($REQS)，继续观察，不做判定"; exit 75
fi

ERR_CANARY=$(q "sum(rate(http_requests_total{service=\"$SVC\",track=\"canary\",code=~\"5..\"}[$WINDOW]))/sum(rate(http_requests_total{service=\"$SVC\",track=\"canary\"}[$WINDOW]))")
ERR_BASE=$(q "sum(rate(http_requests_total{service=\"$SVC\",track=\"stable\",code=~\"5..\"}[$WINDOW]))/sum(rate(http_requests_total{service=\"$SVC\",track=\"stable\"}[$WINDOW]))")
P99_CANARY=$(q "histogram_quantile(0.99,sum by(le)(rate(http_request_duration_seconds_bucket{service=\"$SVC\",track=\"canary\"}[$WINDOW])))")
P99_BASE=$(q "histogram_quantile(0.99,sum by(le)(rate(http_request_duration_seconds_bucket{service=\"$SVC\",track=\"stable\"}[$WINDOW])))")

# 用 awk 做浮点比较：错误率绝对差超 0.002，或 p99 相对劣化超过 50 分，判定失败
VERDICT=$(awk -v ec="$ERR_CANARY" -v eb="$ERR_BASE" -v pc="$P99_CANARY" -v pb="$P99_BASE" \
  'BEGIN{ bad=0;
          if (ec-eb > 0.002) bad=1;
          if (pb > 0 && pc/pb > 1.5) bad=1;
          print bad }')

if [ "$VERDICT" = "1" ]; then
  echo "判定失败: 错误率 $ERR_CANARY vs $ERR_BASE, p99 $P99_CANARY vs $P99_BASE"
  # 先把权重降为零止损，但保留实例不删，用于抓取堆栈与日志取证
  ./ci/set-canary-weight.sh "$SVC" 0
  exit 1
fi
echo "判定通过，可扩大权重"

数据库变更是发布里最危险的一环

只要采用滚动、蓝绿或金丝雀，就必然存在一段新旧两版代码同时在线的时间。这段时间里，数据库只有一份。如果 schema 变更和代码变更在同一次发布里同时生效，故障是确定会发生的，不是可能。

sequenceDiagram participant U as 用户请求 participant G as 网关 participant Old as 旧版实例 participant New as 新版实例 participant DB as 数据库 Note over DB: 发布脚本先执行 ALTER 删掉旧列 改名为新列 U->>G: 请求 A G->>New: 路由到已升级实例 New->>DB: 按新列名读写 DB-->>New: 成功 New-->>U: 正常响应 U->>G: 请求 B G->>Old: 路由到尚未升级的实例 Old->>DB: 按旧列名读写 DB-->>Old: 报错 列不存在 Old-->>U: 500 错误 Note over U,DB: 灰度期间错误率等于未升级实例占比 且随批次推进缓慢下降 Note over Old,DB: 此时回滚代码也救不了 因为旧列已经不在了

正确做法是把一次逻辑变更拆成三次发布，每一步单独上线时，新旧两版代码都必须能正常工作：

阶段做什么对旧代码的影响可否单独回滚
一、先发兼容性 DDL新增可空列或带默认值的列、新建索引、新建表；不删不改不重命名完全透明，旧代码不感知可以，因为没有代码依赖它
二、再发代码新代码双写新旧字段，读取仍以旧字段为准；同时用后台任务回填历史数据旧代码继续读写旧字段，正常工作可以，回滚代码即可，数据无损
三、最后清理确认全量实例已升级且回填完成，切换读取来源，下一次发布再删除旧列此时已无旧代码在跑删除动作本身不可回滚，所以必须留足确认时间
-- 目标：把 users.phone 拆成 country_code 与 national_number
-- 反面做法：一条 ALTER 改完然后发代码 —— 灰度期间旧实例必然报错

-- ===== 第一次发布：只动结构，且必须对旧代码透明 =====
-- 新列可空，不写默认值回填（大表上 NOT NULL DEFAULT 可能触发全表重写）
ALTER TABLE users ADD COLUMN country_code varchar(8) NULL;
ALTER TABLE users ADD COLUMN national_number varchar(32) NULL;
-- 索引单独建，PostgreSQL 用 CONCURRENTLY 避免长时间持有写锁
CREATE INDEX CONCURRENTLY idx_users_national ON users (country_code, national_number);

-- ===== 第二次发布：代码双写，旧列仍是读取来源 =====
-- 历史数据分批回填，控制每批大小与间隔，避免打满主从复制延迟
-- 循环执行直到影响行数为 0；生产上把 10000 调到让单批耗时低于 1 秒的量级
UPDATE users
   SET country_code   = '86',
       national_number = substring(phone from 3)
 WHERE country_code IS NULL
   AND phone LIKE '86%'
   AND id IN (SELECT id FROM users WHERE country_code IS NULL LIMIT 10000);

-- ===== 第三次发布：确认无旧代码在跑之后才做，且单独一次上线 =====
-- 先加约束（此时数据已全部回填），再在下一次发布删除旧列
ALTER TABLE users ALTER COLUMN national_number SET NOT NULL;
-- ALTER TABLE users DROP COLUMN phone;  -- 这一步不可回滚，确认后单独执行
⚠️
数据库变更几乎不可回滚，所以回滚策略必须是「向前修复」

加列有对应的删列语句，但删列、改类型、数据迁移一旦执行，原始数据已经丢失或改写，回退语句只能恢复结构不能恢复数据。更麻烦的是回滚窗口内又写入了新数据，回退结构会让这些数据无处安放。所以工程上的正确定义是：回滚的对象是应用代码，不是数据库结构；结构确实要撤销时，那也是作为一次新的变更走完整流程。表结构演进的更多细节详见站内 数据库建模与模式演进。

回滚能力是发布安全的底线

发布安全的下限不是「不出问题」，而是出问题后能在几分钟内恢复。一键回滚听起来是个按钮，实际上是四个前提同时成立的结果，缺一个按钮就按不下去。

前提不满足时会发生什么怎么确认它真的满足
产物不可变回滚目标指向的标签已被覆盖，拉下来的还是新版本仓库开启标签不可变；部署记录里存的是 digest 而不是标签
配置与代码解耦旧版本代码读不到新加的配置项，或读到了不认识的格式而崩溃回滚演练时不动配置，直接切代码版本看能否启动
数据库变更向后兼容代码回滚了但表结构已经变了，旧代码直接报列不存在检查本次发布是否包含任何删除、改名、改类型操作
有明确的回滚判定指标没人敢拍板回滚，于是在「再观察十分钟」里耗掉半小时发布前就写死阈值：错误率或成功率超过某个数就回滚，不再讨论

这四条看起来都会满足，实际演练时往往有一条不成立。回滚演练建议按下面的清单做，并且在非故障时段做：

  • 随机选一个近期上线的服务，从部署记录里取出上一个生产版本的 digest。
  • 不改任何配置，只把版本切回该 digest，记录从下达指令到全部实例就绪的时长。
  • 验证回滚后的健康检查、关键接口、日志里没有配置缺失类报错。
  • 检查这次回滚是否触碰了数据库，如果碰了，确认兼容性是否真的成立。
  • 把实测时长写进发布预案，如果超过 10 分钟，说明回滚路径需要优化。
  • 演练过程中不要让执行人提前准备，模拟真实的「临时被叫起来处理」场景。

功能开关：部署不等于发布

这是现代发布最核心的一个观念转变：部署是把新代码放到生产运行，发布是让用户看到新功能，两者应该解耦。解耦之后，未完成的功能可以先合主干避免长命分支，功能出问题的止损时间从一次发布的分钟级降到秒级。

开关类型存活时长切换主体管理要点
发布开关（新功能灰度）数天到数周，必须清理产品或研发登记预期下线时间，超期进技术债清单
实验开关（A/B 对比）一个实验周期数据或增长团队实验结束立即收敛成一个分支，不要留着
运维开关（降级、限流、熔断）长期存在值班人员必须有默认安全值，配置中心不可用时能兜住
权限开关（按客户或套餐）长期存在业务配置这属于业务逻辑，不该混在技术开关里管理
✅
开关必须能在不发布的情况下切换

如果开关值是编译进产物或写在镜像里的环境变量，那么切换开关等于一次发布，止损时间没有任何改善，还多了一层无用的复杂度。开关值必须来自运行时可变的来源（配置中心或开关服务），且要有本地缓存与默认值：开关服务挂掉时，服务应当按默认值继续运行，而不是启动失败或全部走新逻辑。配置中心本身的高可用与推送机制见站内 配置中心。

高频小批量比低频大批量更安全

发布窗口与冻结期的直觉是「少发就少出事」，但这个直觉在数据上不成立。原因在变更失败率的构成：失败概率大致随变更包含的改动量增长，而定位成本随改动量线性甚至超线性增长。

对比项每天发一次小变更每两周发一次大变更
单次包含的改动几个提交几十到上百个提交
出问题时的定位范围几个提交里找，通常几分钟上百个提交里找，通常几小时
回滚代价只回退当天改动，业务影响小回退两周成果，往往有人不同意回滚
是否需要发布协调会不需要需要，还要拉齐多个团队
累积的未验证风险接近零两周的改动从未在生产验证过
冻结期的真实效果不适用解冻后第一次发布风险最高，恰好在最不该出事的时候

冻结期不是完全没用，但它的正确用法很窄：只在真正需要极高稳定性的窗口（大促当天、重要活动期间）限制发布，并且明确保留紧急修复通道。把它变成长期制度，等于把风险从「每天一点」攒成「两周一次大的」。

流量切换的实际手段与有状态服务

切换手段生效速度粒度主要陷阱
容器平台滚动更新分钟级，取决于批次与就绪探测按实例数参数配错会同时下线过多实例；探针与优雅退出细节详见站内 Kubernetes
网关按权重分流秒级可到百分比、请求头、用户 ID 取模长连接不会因为权重变化而断开，老连接会继续打到旧版本
服务注册中心摘除秒到十几秒按实例客户端有本地缓存，摘除后仍会有一段时间的请求打过来
DNS 切换最慢，分钟到小时按域名，全量TTL 只是建议值，运营商递归缓存与 JVM 默认永久缓存都会让旧地址长期存活，不能用于需要快速回滚的场景
客户端配置下发取决于拉取间隔按设备或用户老版本客户端可能永远不更新，需要服务端长期兼容

流量切换的另一半是应用要配合。用重启代替优雅关闭，会把正在处理的请求直接掐断，表现为客户端大量连接重置，而服务端日志干干净净什么都看不到：

func main() {
    srv := &http.Server{Addr: ":8080", Handler: router()}

    // ready 用于就绪探测：收到停止信号后先置为 false，
    // 让流量入口把本实例摘掉，之后才真正停止接收
    var ready atomic.Bool
    ready.Store(true)
    http.HandleFunc("/readyz", func(w http.ResponseWriter, r *http.Request) {
        if !ready.Load() {
            w.WriteHeader(http.StatusServiceUnavailable)
            return
        }
        w.WriteHeader(http.StatusOK)
    })

    go func() {
        if err := srv.ListenAndServe(); err != nil && err != http.ErrServerClosed {
            log.Fatalf("listen: %v", err)
        }
    }()

    stop := make(chan os.Signal, 1)
    signal.Notify(stop, syscall.SIGTERM, syscall.SIGINT)
    <-stop

    // 第一步：先摘流量，不要立刻关连接。
    // 这个等待时间要覆盖「流量入口感知到实例不可用」的延迟，
    // 通常是就绪探测周期加上负载均衡的同步时间，5 到 15 秒是常见取值
    ready.Store(false)
    time.Sleep(10 * time.Second)

    // 第二步：停止接收新连接，等已有请求处理完。
    // 超时要大于最慢接口的正常耗时，否则会掐断长请求
    ctx, cancel := context.WithTimeout(context.Background(), 30*time.Second)
    defer cancel()
    if err := srv.Shutdown(ctx); err != nil {
        log.Printf("优雅关闭超时，仍有请求未完成: %v", err)
    }

    // 第三步：关闭下游资源，顺序与初始化相反
    // 注意消费者要先停止拉取再提交位点，否则会丢消息或重复消费
    closeConsumers()
    db.Close()
}

有状态服务与数据中间件的发布不能照搬上面的策略。关键差别在于实例不可互换：数据库主从有明确角色、分布式协调服务有选举、消息队列的分区有归属。要点包括：必须按角色分批，从节点先升级、主节点最后并通过主动切主来避免被动选举；升级期间要预留足够的多数派，否则一次滚动就可能让集群失去可用性；版本兼容性要双向确认，很多中间件不支持新版本回退到旧版本读取已升级的数据格式，这意味着升级它们往往是不可回滚的单向操作，必须先在预发用同等数据量验证。这类发布应当独立成一次变更，绝不和业务代码发布混在一起。

发布前中后的检查清单

时机检查项不做的后果
发布前确认变更范围：这次包含哪些提交，有没有别人搭车上的改动出问题时不知道该怀疑什么，回滚也说不清影响谁
发布前确认依赖顺序：被调用方是否需要先发，接口是否向后兼容调用方先上线，调用了还不存在的接口
发布前确认数据库变更是否兼容，DDL 是否已在上一次发布中完成灰度期间旧实例批量报错
发布前写下回滚预案与判定阈值，确认上一个可用 digest 是什么真出事时在「要不要回滚」上耗掉黄金十分钟
发布前打开对应的监控看板，确认埋点能区分新旧版本指标混在一起，看不出是不是新版本引起的
发布中分批推进，每批之间留观察间隔，不要一次推完失去金丝雀的全部意义
发布中盯错误率与延迟 p99，同时盯核心业务成功率只看资源指标，业务已经全错了还在继续扩量
发布中留意下游依赖的负载变化与慢查询数量新版本引入了循环查询，压力传导到数据库才爆
发布后设定明确的观察期，覆盖一个完整业务周期再离开问题在流量高峰才显现，此时已无人值守
发布后清理旧版本实例、临时扩容资源与已全量的开关旧实例残留导致部分流量仍走老代码，排查时极难发现
发布后把本次发布的指标数据归档，用于调整下次的判定阈值阈值永远靠拍脑袋，误判和漏判都会持续

反模式与最容易踩的坑

反模式为什么会出现实际代价改法
没有回滚预案就发布觉得这次改动小真出事时在讨论怎么回滚，故障时长翻几倍发布前写下目标 digest 与回滚判定阈值，作为放行前置条件
同一次发布里既改数据库又改代码觉得拆成三次太麻烦灰度期间新旧实例必有一方报错，错误率等于未升级实例占比拆成兼容 DDL、代码、清理三次独立发布
金丝雀只看 CPU 与内存资源指标最容易拿到业务成功率已经掉了一半，资源指标依然平稳，继续扩量判定必须以业务成功率与错误率为主，资源指标只做辅助
周五晚上发大版本希望周末流量低时验证出问题时值班人力最薄弱，且要占用休息时间处理大变更放在有完整人力覆盖的时段，周五只发紧急修复
用重启代替优雅关闭直接杀进程最快正在处理的请求被掐断，客户端看到连接重置，服务端日志无痕迹先摘流量再等待在途请求结束，超时要大于最慢接口耗时
用 DNS 切换做回滚通道以为改了 TTL 就能快速生效递归缓存与客户端缓存让旧地址存活数小时回滚走网关权重或平台版本切换，DNS 只做长期迁移
开关值编译进产物实现最简单切开关等于一次发布，止损时间毫无改善开关值从配置中心运行时读取，带本地缓存与默认值
中间件升级和业务发布混在一起想省一个发布窗口出问题无法判断是中间件还是业务代码引起的，且中间件常不可回滚中间件升级独立成一次变更，先在同等数据量的预发验证
❌
避坑指南
  • 把「先发一小部分」当成金丝雀，没有指标、没有观察时长、没有判定人，等于分批重启。
  • 金丝雀刚启动就比延迟，缓存是冷的、连接池是空的，前几分钟天然偏高，会误判回滚。
  • 低峰期放 1 分流量就做判定，样本量不足几十个请求，任何比率都没有统计意义。
  • 把 DDL 写在应用启动时自动执行，多实例同时启动会并发改表，滚动更新时直接锁表。
  • 在大表上执行带默认值的非空加列，触发全表重写，锁表时间以分钟计。
  • 数据回填不分批，一条 UPDATE 改几千万行，主从复制延迟飙到几十分钟。
  • 代码回滚了但忘了数据库已经删列，旧代码启动即报列不存在，回滚也救不回来。
  • 依赖新配置项的版本回滚到旧版本，旧代码不认识新配置格式，启动直接失败。
  • 回滚目标用的是可变标签而不是 digest，拉下来发现还是出问题的那个版本。
  • 发布后不清理旧实例，少量流量长期走在老代码上，偶发问题查一周找不到原因。
  • 功能开关全量之后不删，两年后代码里几百个永远为真的判断，没人敢动。
  • 长连接服务只改网关权重，老连接不会自动迁移，旧版本可能持续承接数小时流量。
  • 把长期发布冻结当作稳定性措施，解冻后第一次发布携带两周改动，风险集中爆发。
