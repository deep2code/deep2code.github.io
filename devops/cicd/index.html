CI/CD 流水线设计原则：三个词的边界、分层卡点与 DORA 度量

🏷️ CI/CD

流水线好不好，跟用哪个工具关系不大。决定成败的是四件事：阶段怎么切、反馈多快、产物是否唯一、失败时谁负责。这篇只讲设计原则，具体工具的语法放在本组的 Jenkins、GitHub Actions、GitLab CI 三篇里。

先把三个词分清：集成、交付、部署

这三个词被混着用，导致讨论经常错位：一方在说「我们做了 CI」，另一方以为对方能一天上十次生产。它们其实是三个不同的工程承诺，前置条件差别很大。

  • 持续集成：每个人的改动频繁合并回主干，每次合并都自动验证。它约束的是开发协作方式，不是部署。
  • 持续交付：任何一次通过流水线的构建都处于「随时可发布」状态，但按不按发布按钮由人决定。
  • 持续部署：连这个按钮也自动化，验收通过就直接进生产。
维度 持续集成 CI 持续交付 CD 持续部署 CD
约束对象 开发的合并习惯 产物与环境的一致性 验收与观测的自动化程度
链路终点 主干上有一个绿色构建 制品仓库里有可直接上生产的产物 生产正在跑最新验收通过的产物
生产发布由谁触发 不涉及 人，通常是发布负责人点闸门 流水线自动，人只在告警时介入
硬前置条件 短命分支、单测可信、红灯必修 产物不可变、配置外置、部署脚本幂等 灰度能力、自动判定指标、自动回滚
团队成熟度要求 低，但要改工作习惯，实际最难的一步 中，需要环境与制品治理 高，需要可观测性与值班机制
典型失败形态 主干长期红灯，没人认领 「可发布」只是声称，发布时仍要手工改配置 无人工把关又没有自动判定，故障直通全量用户
做到了的客观判据 人均每天合并主干 1 次以上，红灯平均修复时间小于 1 小时 随机挑一个绿色构建，能在 30 分钟内无手工步骤发到生产 过去一个月生产发布中人工触发比例接近零
❌
大多数团队自称做 CI，其实只是「有个跑测试的任务」

装了流水线工具、推代码会跑测试，这只是 CI 的基础设施，不是 CI。持续集成这个词里的「集成」指的是把不同人的改动合到一起。如果三个人各自在分支上开发两周才合并，那么自动化跑得再勤，集成冲突依然是两周后一次性爆发，CI 想解决的问题一个都没解决。

观察项 伪 CI 的实际表现 真 CI 的要求
主干集成频率 分支存活 1 到 3 周，合并时大量冲突 每人每天至少合并主干一次，单个 PR 改动通常小于 400 行
红灯响应 主干红了好几天，大家在红灯基础上继续提交 红灯即最高优先级，修不了就回退，不允许在红灯上叠新提交
测试可信度 存在一批「偶尔失败，重跑就过」的测试，重跑是标准操作 随机失败的测试当缺陷处理并隔离，主流水线红灯百分之百可信
未完成功能 因为功能没做完不敢合主干，只能留在长命分支 用开关把未完成代码合进主干但不启用，集成与发布解耦
本地与流水线一致性 本地跑通，推上去红，原因说不清 同一套检查能在本地一条命令复现

流水线分层：阶段边界与卡点判定

流水线不是一串任务，而是按反馈成本分层的漏斗。越靠前的阶段越快越便宜，负责挡住绝大多数错误；越靠后的阶段越慢越接近真实，负责挡住前面挡不住的。同一层内的检查应该并行，层与层之间才串行。

接下来的关键判断是：哪些检查失败要让流水线变红并阻断，哪些只发通知。全部卡住会让流水线因噪音失去可信度，全部只告警等于没有门禁。判定依据不是「这个检查重不重要」，而是「它的结论是否稳定，以及它为真时代码是否真的不该往下走」。

flowchart TB S["某项检查失败"] --> Q1{"为真时代码是否确实不可用"} Q1 -- 是 --> Q2{"结论是否稳定可复现"} Q1 -- 否 --> W1["只告警 进趋势看板"] Q2 -- 稳定 --> H1["硬阻断 流水线红灯"] Q2 -- 随机失败 --> Q3{"是否已隔离到独立任务"} Q3 -- 未隔离 --> H2["先隔离 否则会训练团队忽略红灯"] Q3 -- 已隔离 --> W2["独立任务红灯 不阻断主干"] W1 --> Q4{"存量问题是否海量"} Q4 -- 是 --> W3["设基线 只对新增代码阻断"] Q4 -- 否 --> H3["限期转为硬阻断"]
检查项 处理方式 理由 常见错误做法
编译失败、单测失败 硬阻断 结论确定，代码真的不能用 配置自动重试次数，把它变成概率通过
代码格式不符 自动修复后提交，修不了才阻断 格式问题不需要人判断 让人手工改格式，占用评审注意力
静态检查新增告警 按基线阻断，仅针对本次改动 存量告警常有成千上万条，全量阻断无法落地 一次性开全部规则，两天后被整体关掉
测试覆盖率下降 只告警，或对新增代码设下限 覆盖率是代理指标，硬卡会催生无断言测试 设 80 分行覆盖硬门禁，团队开始写空测试凑数
高危依赖漏洞 按严重级别阻断，中低级只告警 漏洞基数大必须分级；细节见站内 OWASP Top 10 的依赖与 SCA 一节 任何漏洞都阻断，最后全员申请豁免
产物里检出明文密钥 硬阻断，且立即触发轮换 泄露不可撤回，删提交也没用 只在评审时靠肉眼看
性能基准回退 只告警，超过阈值再阻断 共享构建机的性能抖动可达 20 分以上 用绝对耗时做门禁，构建机一忙就全红
端到端测试失败 部署预发之后阻断，不放在提交阶段 它慢且脆，放进提交阶段会毁掉反馈速度 把 30 分钟端到端塞进 PR 检查

反馈速度是 CI 的第一指标

CI 的产出不是「测试跑过了」，而是开发在多短时间内知道自己刚提交的东西有没有问题。这决定了时间预算必须按层分配，而不是笼统追求总时长。

阶段 时间预算 超时后的实际后果 压缩手段
格式与静态检查 60 秒内 开发在本地跳过提交钩子，问题积压到评审阶段 只扫变更文件，结果按内容哈希缓存
单元测试 提交后 5 分钟内出结论 开发切走做别的事，上下文丢失，修复成本翻几倍 按包分片并行、按变更范围筛选、禁止单测碰网络与真实数据库
构建与镜像产出 10 分钟内 合并阻塞，PR 排队，集成频率直接下降 依赖缓存、多阶段构建、layer 顺序优化
集成与契约测试 30 分钟内，允许更久但必须并行 合并之后才发现问题，回溯到哪个 PR 变难 按模块切分并行任务，依赖用容器即起即用
端到端与全量回归 合并后异步跑或定时跑 放进 PR 会让整条流水线不可用 只保留少量关键路径用例，其余移到定时任务
提交到生产 小时级，不是天级 前置时间越长，单次变更越大，失败率越高 缩短闸门等待，提高发布频率来降低批量大小
⚠️
流水线超过 15 分钟，开发就会开始绕过它

这不是态度问题，是等待经济学。超过十几分钟人一定会切换任务，于是出现一整套规避行为：本地加参数跳过提交钩子、把多个改动攒成一个大提交少跑几次、失败先点重跑不看日志、给提交打上跳过标记。这些行为让 CI 失去唯一价值。优化流水线时长不是工程洁癖，而是在保护集成频率。

缓存与增量：把时间预算省出来

压缩时长的第一性手段是不重复做已经做过的事。三类缓存的失效条件完全不同，混在一起配就会出现「缓存命中了但结果是错的」这种最难查的问题。

缓存对象 缓存键应包含 典型收益 失效或出错的场景
依赖包目录 锁文件内容哈希，加语言与操作系统版本 拉依赖从数分钟降到十几秒 键里漏了语言版本，升级后复用了不兼容的编译产物
Docker layer 由指令与被拷贝文件内容自动决定，不需手工配 只改业务代码时构建从 5 分钟降到 30 秒 第一条拷贝就拷全量目录，任何改动都击穿后续所有层
编译中间产物 编译器版本、编译参数、源码哈希 大仓增量编译节省 50 分以上时间 参数变了但键没变，产出与预期编译选项不一致
测试结果 被测代码与测试代码的传递依赖哈希 无关改动直接跳过整批测试 测试读了环境变量或外部文件，哈希算不到，跳过了本该失败的用例
基础镜像 固定 digest，不用浮动标签 避免每次构建重新拉取 用了浮动标签，某天上游更新导致构建行为突变

Docker layer 缓存的收益完全取决于指令顺序，原则是变化频率低的放前面：

# 变化频率低的指令放前面，业务代码改动才只失效最后几层
FROM golang:1.23 AS build
WORKDIR /src

# 只拷依赖清单。依赖没变时这一层命中缓存，不会重新下载
COPY go.mod go.sum ./
RUN --mount=type=cache,target=/go/pkg/mod go mod download

# 源码最后拷。改一行业务代码只失效这一层往后
COPY . .
# trimpath 去掉构建机的绝对路径，是让构建可重复的关键参数之一
RUN --mount=type=cache,target=/root/.cache/go-build \
    CGO_ENABLED=0 go build -trimpath -ldflags "-s -w" -o /out/app ./cmd/app

# 运行镜像不含编译器与源码，体积小且攻击面小
FROM gcr.io/distroless/static:nonroot
COPY --from=build /out/app /app
USER nonroot:nonroot
ENTRYPOINT ["/app"]

单测按变更范围筛选能把提交阶段稳定压到 5 分钟内，但筛选逻辑写错会漏跑，规则必须保守：

#!/usr/bin/env bash
set -euo pipefail

# 基准点用 merge-base，不要用 HEAD 的上一个提交
# 分支落后主干很多时，上一个提交会漏算掉主干上已经发生的变更影响
BASE=$(git merge-base origin/main HEAD)
CHANGED=$(git diff --name-only "$BASE"...HEAD)

# 一旦动了全局影响文件，直接退化为全量跑。不要在这里追求聪明
if echo "$CHANGED" | grep -qE '^(go\.mod|go\.sum|Makefile|Dockerfile|\.ci/)'; then
  PKGS="./..."
else
  PKGS=$(echo "$CHANGED" | grep -E '\.go$' | xargs -r -n1 dirname | sort -u | sed 's|^|./|')
  if [ -z "$PKGS" ]; then echo "无 Go 变更，跳过单测"; exit 0; fi
fi

# count=1 禁用测试结果缓存，避免本地缓存让失败的用例看起来通过
# race 必须开，并发缺陷只有开了它才稳定暴露
# timeout 给死锁一个明确上界，否则任务会挂到流水线全局超时
go test -count=1 -race -timeout 5m $PKGS

一次构建，多处部署

这是整条流水线里最不该妥协的一条纪律：产物只构建一次，此后所有环境部署同一个产物，环境之间只有配置与密钥不同。违反它的直接后果是「测试通过的不是上生产的那个东西」。

sequenceDiagram participant D as 开发 participant P as 流水线 participant T as 测试环境 participant R as 生产环境 D->>P: 推送提交 abc123 P->>P: 构建 依赖范围解析到 1.2.0 P->>T: 部署本次构建结果 T-->>P: 全部测试通过 Note over P,R: 三天后发布 生产流水线按同一提交重新构建 P->>P: 再次构建 依赖范围已解析到 1.2.1 P->>R: 部署新的构建结果 R-->>D: 线上异常 测试过的不是上生产的那个东西 Note over D,R: 同一个提交两次构建产出不同内容 差异只在生产暴露

会让两次构建不一致的输入比想象的多：依赖版本范围、基础镜像浮动标签、构建机上的编译器与系统库、构建时注入的时间戳与绝对路径、从网络临时下载的脚本。全部锁死很难，所以正确策略不是「保证每次构建都一致」，而是根本不给第二次构建的机会。

#!/usr/bin/env bash
set -euo pipefail

# 版本标识只认 commit sha。分支名会被复用，latest 会被覆盖，
# 语义化版本号在预发阶段往往还没确定
GIT_SHA=$(git rev-parse --short=12 HEAD)
BUILD_TS=$(date -u +%Y-%m-%dT%H:%M:%SZ)
# 流水线号用于区分「同一提交重跑了几次」，排查构建环境差异时有用
RUN_ID=${CI_PIPELINE_ID:-local}
IMAGE=registry.example.com/team/order-service

# 标签策略：
#   sha-xxxxxxxxxxxx  唯一且禁止覆盖，部署清单只允许引用这一类
#   分支名             可变别名，仅供开发本地拉取方便
#   语义化版本号       发布时额外打一个，指向同一个 digest，不重新构建
docker build \
  --label org.opencontainers.image.revision="$GIT_SHA" \
  --label org.opencontainers.image.created="$BUILD_TS" \
  --label ci.run-id="$RUN_ID" \
  -t "$IMAGE:sha-$GIT_SHA" .
docker push "$IMAGE:sha-$GIT_SHA"

# 关键一步：记录 digest。标签可以被重新指向，digest 不能
# 后续每个环境都按 digest 部署，这才是「一次构建多处部署」的技术保证
DIGEST=$(docker buildx imagetools inspect "$IMAGE:sha-$GIT_SHA" --format '{{.Manifest.Digest}}')
printf '%s@%s\n' "$IMAGE" "$DIGEST" > artifact-ref.txt

# 发布时只加别名，绝不重新构建：
# docker buildx imagetools create -t "$IMAGE:v1.8.0" "$IMAGE@$DIGEST"
可追溯问题 没做的后果 落地做法
线上实例跑的是哪个提交 故障时无法定位代码，只能靠人回忆发布过什么 镜像标签含 sha，同时写入产物元数据与服务健康检查的响应体
某次部署由哪条流水线产出 无法区分同一提交多次构建之间的差异 部署记录里存 commit sha、镜像 digest、流水线运行号三元组
产物有没有被替换过 标签被重新指向而无人知晓 仓库开启标签不可变，部署统一按 digest 引用
依赖清单与来源 上游爆漏洞时无法回答「我们受不受影响」 构建时产出物料清单并随产物归档，签名与验签按需引入；相关风险见站内 OWASP Top 10

流水线即代码与它的代价

流水线定义进仓库，好处明显：可评审、可回溯、跟着分支一起演进、新人能看懂。但要承认它带来三个新问题，推行时经常被忽略。

  • 改流水线要走发布流程。修一行配置也得提 PR、等评审、等流水线自己跑完验证，紧急故障时这条链路会变成阻塞。需要的是一条经过审批的应急旁路，而不是给所有人开后门。
  • 配置的正确性只能在运行时验证。语法检查能挡笔误，挡不住「这个条件永远不成立」。缓解办法是把逻辑从流水线配置挪进仓库内的脚本，脚本能在本地跑，流水线只负责调用。
  • 流水线定义本身是高权限代码。能改流水线等于能在持有生产凭证的环境里执行任意命令，所以部署相关定义应该受保护分支与独立评审人约束。

权限设计的核心是分清信任级别。来自 fork 的 PR 必须被当作不可信输入：它能改流水线定义，如果这条流水线能拿到 secret，等于把凭证交给任意外部提交者。

凭证做法 风险 更好的替代
长期访问密钥裸存在流水线变量里 一次日志误打印就是永久有效的凭证，轮换还要改多处 用身份联合换取分钟级有效期的临时令牌
所有任务共用一套凭证 权限最大化，连单测任务也能删生产资源 按阶段拆分身份，提交阶段完全无凭证
把 secret 通过环境变量传给第三方步骤 第三方步骤可直接外发，这是供应链投毒的主要路径 第三方步骤固定到 commit sha 而非可变标签，并限制可见变量
fork PR 的流水线可读 secret 外部提交者改一行定义即可窃取凭证 fork 流水线在无凭证模式跑，需要凭证的检查由成员手工放行

用 DORA 四项指标度量，而不是凭感觉

「我们的流水线还行」这种判断没法讨论。DORA 四项指标有用，是因为它们两两成对：前两项衡量速度，后两项衡量稳定性，单看任意一项都能被刷分，合起来看才成立。

指标 精确定义 数据来源 常见口径错误
部署频率 单位时间内成功进入生产的部署次数，按服务统计 部署记录表，环境为生产且结果成功 把测试环境部署也算进去，数字漂亮但无意义
变更前置时间 从代码提交到该提交首次进入生产的时长 git 提交时间加部署记录，靠 commit sha 关联 从需求创建算起，混入产品排期，测的不是交付能力
变更失败率 导致服务降级并需要回滚或紧急修复的部署占比 部署记录加故障单，需要人工标注因果 只统计部署脚本失败，真正的线上故障没算进来
服务恢复时间 从故障开始影响用户到恢复正常的时长 告警触发时间与故障单关闭时间 从「有人开始处理」算起，把发现延迟藏掉了

采集的前提只有一个：部署记录里必须存 commit sha。很多团队算不出前置时间，根因就是记录里只有版本号，无法关联回提交。有了这张表，四项指标都变成 SQL 问题：

-- 前提：deployments 表记录每次部署的环境、目标 commit sha、时间、结果
-- commits 表可直接从 git log 导入，关联键是 sha
-- 用中位数与 90 分位，不要用平均值：少数几次积压的老提交会把平均值彻底带偏
SELECT
    date_trunc('week', d.deployed_at)                       AS wk,
    count(*)                                                AS deploy_count,
    percentile_cont(0.5) WITHIN GROUP (
        ORDER BY extract(epoch FROM d.deployed_at - c.committed_at) / 3600
    )                                                       AS lead_p50_hours,
    percentile_cont(0.9) WITHIN GROUP (
        ORDER BY extract(epoch FROM d.deployed_at - c.committed_at) / 3600
    )                                                       AS lead_p90_hours,
    -- 变更失败率：被标记为引发回滚或紧急修复的部署占比
    round(100.0 * sum(CASE WHEN d.caused_rollback THEN 1 ELSE 0 END) / count(*), 1)
                                                            AS change_fail_pct
FROM deployments d
JOIN commits c ON c.sha = d.commit_sha
WHERE d.environment = 'prod'
  AND d.status = 'success'
  AND d.deployed_at >= now() - interval '90 days'
GROUP BY 1
ORDER BY 1 DESC;
💡
四项指标要一起看，单看一项一定被刷

只考部署频率，团队会把一次发布拆成五次空发布。只考变更失败率，团队会把发布频率压到每月一次，因为不发布就不会失败——但那反而更危险，批量越大失败时越难定位。同理，恢复时间单独好看，可能只是因为习惯了直接重启掩盖问题。把四项放在同一张周报上，任何单点造假都会在另一项上露出来。指标怎么采集与告警怎么设计，见站内 监控告警。

反模式清单

反模式 为什么会出现 实际代价 改法
一个巨型任务从头串到尾 配置简单，复制粘贴最省事 无法并行、失败看不出卡在哪步、重跑必须从零开始 按反馈层切分阶段，同层并行，产物在阶段间传递
测试失败靠重跑通过 随机失败没人愿意认领 团队学会忽略红灯，真实缺陷被顺手重跑掉 把随机失败当缺陷立项并隔离，禁止无条件自动重试
自动流程里夹手工步骤 某一步来不及自动化，先人工顶着 整条链路的可靠性等于那个人的状态，且无法度量 把手工步骤显式建模成「等待放行的闸门」，其余全自动
每个环境重新构建 以为「同一个提交构建结果当然一样」 生产跑的产物从未被测试过 一次构建推制品仓库，各环境按 digest 部署
提交阶段跑 30 分钟端到端 希望一次把所有问题都挡住 反馈慢到没人等，开发开始规避流水线 端到端只留关键路径，移到部署预发之后或定时任务
用 latest 标签部署 省去传版本号的麻烦 不可追溯、扩容实例版本不一致、回滚无目标 标签含 sha，仓库开启标签不可变，部署按 digest
凭证裸存在流水线变量里 最快能跑通的做法 日志一次误打印即永久泄露，轮换要改多处 短时效令牌加集中密钥托管，按阶段最小权限
门禁规则一次性全开 希望立刻拉高质量标准 存量告警上万条，两天后规则被整体关掉 设基线只对新增代码阻断，存量单独排期治理

新手最容易踩的坑

❌
避坑指南
  • 把「装了流水线工具」当成做了 CI。CI 的核心是每天多次合并主干加红灯必修，工具只是前提。
  • 给失败的测试加自动重试次数，等于把不确定性永久隐藏，最终以并发或时序问题在生产重现。
  • 依赖缓存的键只用锁文件哈希，漏掉语言与操作系统版本，升级后复用了不兼容的编译产物。
  • Dockerfile 第一条就 COPY . .，任何代码改动都击穿全部缓存层，构建时间永远降不下来。
  • 基础镜像用浮动标签，某天上游更新导致构建行为突变，排查时怀疑了所有地方就是没怀疑它。
  • 部署记录只存版本号不存 commit sha，于是前置时间永远算不出来，故障时也无法反推代码。
  • 用 HEAD 的上一个提交作为变更范围基准，分支落后主干很多时漏跑受影响的包，合并后才炸。
  • fork PR 的流水线能读到 secret，外部提交者改一行流水线定义就能把凭证外发。
  • 第三方流水线步骤固定到可变标签而非 commit sha，上游被投毒时会自动拉到恶意版本。
  • 把覆盖率设成硬门禁，团队开始写没有断言的测试凑数，数字上去了质量没变。
  • 预发与生产的配置来源不同（一个读文件一个读配置中心），发布时才发现某个配置项在生产根本不存在。
  • 在红灯的主干上继续叠提交，等到有人要修时已经分不清是哪一次引入的。
