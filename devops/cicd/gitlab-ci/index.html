一、GitLab CI 的一体化优势

GitLab CI/CD 是 GitLab 仓库内置的流水线系统。与 GitHub Actions 思路相同，但对私有化部署特别友好：你在自己机房装一套 GitLab，代码和流水线都在内网，不用连外网。

二、核心概念：Pipeline / Stage / Job / Runner

GitLab CI 的模型比 Jenkins 更简洁，核心四件套：

  • Pipeline：一次提交触发的完整流水线，由若干 Stage 组成。
  • Stage：阶段分组，如 build → test → deploy。同一 Stage 内的 Job 并行，跨 Stage 串行（前一 Stage 全成功才进下一 Stage）。
  • Job：最小执行单元，定义在哪个镜像里跑什么脚本。Job 必须声明 script。
  • Runner：执行器，注册到 GitLab 的机器（shell/docker/kubernetes executor），带 tag 决定接哪类 Job。

两个容易踩坑的机制：cache（跨 Job/跨流水线缓存文件，如 node_modules）与 artifacts（Job 间传递产物，可设置 expire_in）。另一个进阶武器是 needs：跳过 Stage 顺序限制，构建一张真正的 DAG（有向无环图），让测试不必等打包就能并行跑。

三、安装 Runner：执行器怎么选

GitLab 服务本身不含 Runner，需要单独装。Runner 支持三种执行器，按隔离性和性能权衡选择：

执行器隔离速度适用
shell无最快单机个人项目，不推荐多人共用
docker容器快大多数项目，按 Job 选镜像
kubernetesPod 级中大规模共享集群，弹性伸缩
 
# Debian/Ubuntu 安装 GitLab Runner
curl -L "https://packages.gitlab.com/install/repositories/runner/gitlab-runner/script.deb.sh" | sudo bash
sudo apt install -y gitlab-runner

# 注册 Runner（交互式，按提示填 GitLab 地址和注册 token）
# token 在 GitLab: 项目 Settings → CI/CD → Runners 里生成
sudo gitlab-runner register
# 执行 executor 选 docker，默认镜像选 alpine:latest

# 验证状态
sudo gitlab-runner status
sudo gitlab-runner verify

# 常用运维命令
sudo gitlab-runner restart
sudo gitlab-runner run --debug   # 前台调试模式

四、实战示例 1：一个完整的 .gitlab-ci.yml

下面这个配置覆盖了前端 + 后端的典型场景：定义阶段、并行构建、缓存依赖、产物归档、按分支部署：

# 定义阶段顺序（同 stage 内并行）
stages:
  - build
  - test
  - deploy

# 全局变量与默认镜像
variables:
  NODE_ENV: production
  IMAGE: $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA

default:
  image: node:20-alpine

# 全局缓存：跨流水线复用 node_modules
cache:
  key: ${CI_COMMIT_REF_SLUG}
  paths:
    - node_modules/

build:
  stage: build
  script:
    - npm ci
    - npm run build
  artifacts:
    paths:
      - dist/
    expire_in: 1 day

unit-test:
  stage: test
  needs: [build]          # DAG：build 一完成立即开始，不等其他 stage
  script:
    - npm ci
    - npm run test:coverage
  coverage: '/Lines\s*:\s*(\d+%.\d+%)/'

lint:
  stage: test
  script:
    - npm ci
    - npm run lint

deploy-staging:
  stage: deploy
  script:
    - echo "部署到 staging"
  environment:
    name: staging
  only:
    - main

deploy-prod:
  stage: deploy
  script:
    - echo "部署到生产"
  environment:
    name: production
  when: manual            # 手动触发，相当于审批卡点
  only:
    - tags

设计要点：needs: [build] 让单元测试在 build 完成后立刻启动，不必等 lint——这就是 DAG 带来的并行提速；when: manual 让生产部署变成按钮式操作，配合 only: tags 实现"打 tag 才发布"的规范流程；environment 关键字让 GitLab 自动记录每次部署到哪个环境，并提供一键回滚和环境访问链接。

五、实战示例 2：Docker 镜像构建与推送

GitLab 自带 Container Registry（$CI_REGISTRY），流水线构建的镜像直接推到同平台仓库，零额外配置：

build-image:
  stage: build
  image: docker:24
  services:
    - docker:24-dind          # DinD：在 Job 里跑 Docker daemon
  variables:
    DOCKER_HOST: tcp://docker:2376
    DOCKER_TLS_CERTDIR: ""
  script:
    - docker login -u $CI_REGISTRY_USER -p $CI_REGISTRY_PASSWORD $CI_REGISTRY
    - docker build -t $IMAGE .
    - docker push $IMAGE
  only:
    - main
    - tags

# 用 Kaniko 替代 DinD（更安全，无需特权模式）
build-image-kaniko:
  stage: build
  image: gcr.io/kaniko-project/executor:latest
  script:
    - /kaniko/executor
      --context $CI_PROJECT_DIR
      --dockerfile Dockerfile
      --destination $IMAGE
  allow_failure: true

注意 DinD（Docker-in-Docker）需要 Runner 以特权模式运行，有安全风险；生产推荐用 Kaniko 或 Buildah——它们不需要 Docker daemon 就能构建镜像，安全性和隔离性都更好，是 GitLab 官方推荐的现代方案。CI_REGISTRY_USER 和 CI_REGISTRY_PASSWORD 是 GitLab 预定义变量，不用自己配。

我被 DinD 坑过一次

早期用 DinD 构建镜像，某周突然所有 build job 都超时。查了半天才发现 Runner 磁盘被镜像层占满了——DinD 的 daemon 不自动清理。换成 Kaniko 后，每个 Job 在独立容器里跑，用完即销毁，再也没出现过磁盘问题。如果你还在用 DinD，听我的，赶紧换 Kaniko。

六、最佳实践

  • include 拆分模板：项目多了以后，把通用片段抽到公共模板仓，各项目用 include:project: .../templates.gitlab-ci.yml 引入，避免复制。
  • 缓存策略要克制：cache 是"可能过期"的，别用它传递必须成功的产物（用 artifacts）；缓存 key 按分支隔离，防止不同分支互相污染。
  • 用 rules 替代 only/except：新版写法 rules: - if: $CI_COMMIT_BRANCH == "main" 更灵活可读，only/except 已进入维护模式。
  • 保护变量与环境：生产凭证存为 "Masked" + "Protected" 变量，只在受保护分支/tag 上可用；给 production 环境配"部署审批"。
  • Runner 打标签分流：重活（E2E）用带 heavy 标签的专用 Runner，轻活跑共享 Runner，互相不阻塞。
  • 预定义变量用满：CI_COMMIT_SHA、CI_COMMIT_REF_NAME、CI_PIPELINE_SOURCE 等内置变量省去大量自定义脚本。

七、常见问题 FAQ

Q1：Job 一直处于 pending，Runner 不接活，为什么？

按顺序排查：① Runner 是否在线（项目 Runners 列表看绿点）；② Runner 的 tags 是否和 Job 的 tags: 匹配——注册时如果勾了 "Run untagged jobs" 之外的选项，Job 没写 tag 就不会被接；③ Runner 并发数（concurrent）是否已满；④ Runner 所在机器磁盘/内存是否耗尽。最常见原因是 tag 不匹配：Job 里写了 tags: [docker] 但 Runner 没打这个标签。

Q2：cache 在 Job 之间时灵时不灵？

cache 的语义是"开始 Job 前下载、结束 Job 后上传"，且同一次流水线里后一个 Job 用的是前一个 Job 结束时上传的版本——所以 build 和 test 如果并行跑，test 是拿不到 build 的 cache 的。需要确定产物传递请用 artifacts；cache 只适合"下载依赖、下次更快"的场景，且依赖 key 稳定和 paths 精确匹配。

Q3：私有化 Runner 怎么避免多项目互相影响？

三道防线：① 用 docker/kubernetes executor，每个 Job 跑在独立容器里，文件系统天然隔离；② 不同团队用不同 Runner 或不同 tag，设置 Runner 的 "Run untagged jobs" 关闭，避免被无关项目抢用；③ 给 Runner 配 concurrency 上限和资源 limit，单个 Job 失控不拖垮整台机器。shell executor 只用于个人项目，绝不要多人共享。

八、总结

GitLab CI 的设计哲学是"约定优于配置"：Stage 定义顺序、needs 打破顺序、environment 自动记账、CI_REGISTRY 自带制品库。对已经私有化部署 GitLab 的团队，它几乎零边际成本——我在公司用了三年，从 5 个项目涨到 40 个，流水线配置几乎没重构过。相比 Jenkins，它少了插件自由，但换来配置简洁和维护省心；相比 GitHub Actions，它把一切数据攥在自己手里。下一篇我们把流水线产出的镜像真正送上生产，对比蓝绿、金丝雀等部署策略。
