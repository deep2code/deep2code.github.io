GitLab CI/CD 机制与实战：needs DAG、executor 选型、cache 与 artifacts 的本质差异

🏷️ GitLab CI

GitLab CI 的 YAML 看着比 GitHub Actions 简单，但它把两件事藏得很深：job 到底跑在什么东西里（executor），以及 cache 和 artifacts 是两套完全不同的机制。绝大多数「在我机器上能跑、在 CI 里就挂」和「流水线越来越慢」的问题都来自这两点。这篇只讲 GitLab CI 自己的机制与可直接抄的配置；流水线设计原则与部署策略详见站内《CI/CD 工具选型》与《容器化部署策略》。

执行模型：stage 串行、同 stage 并行、needs 打破 stage

默认模型是：stages 按声明顺序串行，同一 stage 内的 job 并行，上一个 stage 全部成功才进入下一个。这套模型的代价是木桶效应——每个 stage 的耗时等于该 stage 最慢的 job，总耗时是各 stage 最慢值之和。一个只依赖 build-api 的集成测试，会被同 stage 里慢 5 分钟的前端构建拖住。

needs 是解药，它让 job 只等真正的上游，从而把流水线从「阶段串行」变成 DAG。两个细节值得记住：needs: []（空数组）表示不等任何人，流水线一创建就调度，lint、格式检查这类 job 一律该这么写；needs 同时隐含了 artifacts 传递，默认会下载列出的上游 job 的 artifacts（不想下载要写 artifacts: false）。单个 job 的 needs 上限一般是 50 个，DAG 里也不允许出现环。

写法调度时机artifacts 行为适用坑
只用 stage等上一 stage 全绿自动下载所有前序 stage 的 artifacts3 到 4 个 job 的小项目木桶效应；artifacts 全量下载浪费带宽
needs: [job-a]job-a 成功即开跑，可跨 stage只下载 job-a 的 artifacts主力写法忘记上游没产出 artifacts 时下游取不到文件
needs: []流水线创建即开跑不下载任何 artifactslint、格式检查、静态扫描这类 job 里不能依赖任何构建产物
needs 带 artifacts: false同上只建依赖不传文件只关心上游成功与否容易漏配，导致白下载几百 MB
needs 带 optional: true上游 job 不存在也不报错存在才下载上游被 rules 过滤掉的场景不写它时上游被 rules 剔除会导致整条流水线创建失败
dependencies: []不影响调度顺序只控制 artifacts 下载老配置里降低下载量和 needs 混用时语义容易搞混，新项目直接用 needs

Runner 与 executor：GitLab CI 最该先搞懂的部分

GitLab Runner 是一个独立进程，它主动向 GitLab 的 /api/v4/jobs/request 长轮询领活，领到后交给配置好的 executor 执行。同一台机器上可以注册多个 runner，concurrent 控制这台机器同时跑几个 job，而每个 runner 的 limit 控制它自己的上限——两者取小。job 一直 pending 最常见的原因不是没资源，而是 tags 和 runner 的 tag 对不上，或者 runner 没勾选「运行未打 tag 的 job」。

executor隔离性启动开销cache 是否天然共享适用主要坑
shell无：所有 job 共用宿主机与用户环境最低本机共享，换机器就 miss只有一台构建机、需要宿主机工具链工作区残留、依赖互相污染、任何脚本都能读到别的项目代码
docker容器级：每个 job 全新容器低（镜像已缓存时几秒）否，需要配 S3 等分布式缓存绝大多数团队的默认选择需要 services 与 alias 概念；构建镜像要解决 dind 问题
docker-machine虚拟机级，按需开机高（分钟级冷启动）否弹性伸缩（已进入弃用状态）官方已不推荐，新部署改用 kubernetes 或自动伸缩组
kubernetesPod 级，可配 resource 与 securityContext中（受调度与拉镜像影响）否，必须配对象存储缓存已有 K8s 集群、需要弹性与配额治理Pod 被驱逐表现为随机失败；privileged 需求会和集群策略冲突
ssh取决于目标机低目标机本地特殊硬件、老机器功能受限，基本只用于遗留场景

services 是 docker/kubernetes executor 的能力：在 job 容器旁边再起若干容器，放进同一个网络。集成测试起个真 MySQL 就靠它。两个必须记住的点：主机名是 alias 而不是 localhost（shell executor 上没有 services 这回事）；容器起来不等于服务 ready，MySQL 初始化几秒钟，必须自己在 before_script 里轮询等待，否则会得到随机的连接失败。

⚠️
dind 的代价比多数人以为的大

用 docker:dind 构建镜像需要 runner 开 privileged = true，这等于让任意流水线脚本能突破容器边界拿到宿主机——在多租户共享 runner 上这就是提权漏洞。其次 dind 每个 job 都是全新 daemon，镜像层缓存默认全丢，构建反而更慢。挂宿主机 docker.sock 更快但更糟：容器里能看到并操作宿主机上所有容器。Kaniko 或 Buildah 不需要 daemon、不需要 privileged，并且能用 --cache-repo 把层缓存放到 registry 里跨 runner 复用，是当下的默认答案。

flowchart TB Q1{"要在流水线里构建容器镜像"} --> Q2{"runner 是共享的或跑在 K8s 上吗"} Q2 -->|是| Q3{"能接受 privileged 容器吗"} Q3 -->|"不能（应当如此）"| K["Kaniko 或 Buildah：无 daemon，--cache-repo 复用层"] Q3 -->|能| D["dind：privileged 等于交出宿主机"] Q2 -->|"否，独占的 shell runner"| S{"宿主机上已有 docker daemon 吗"} S -->|有| M["挂 docker.sock：最快，但能操作宿主机全部容器"] S -->|无| K K --> R1["层缓存在 registry，跨 runner 可复用"] D --> R2["每个 job 全新 daemon，层缓存默认丢失"]

cache 与 artifacts：这是 GitLab CI 的核心考点

两者都是「把文件从一处搬到另一处」，但设计目标完全相反。cache 是性能优化：跨流水线复用可重建的内容，允许 miss，按 key 在多个 job 甚至多个流水线之间共享，默认存在 runner 本机。artifacts 是数据契约：同一条流水线内从上游 job 传到下游 job，一定存在，存在 GitLab 侧，有过期时间，并且能被下载、能作为报告解析。

维度cacheartifacts
设计目标加速，可失败传递产物，必须成功
作用域跨流水线、跨分支，按 key 共享同一条流水线内，按 needs 或 stage 顺序传递
存储位置默认 runner 本机；配了 S3 等后端才跨 runnerGitLab 对象存储，始终跨 runner 可取
miss 行为静默跳过，job 继续取不到直接 job 失败
过期无显式过期，靠 key 变化与清理策略expire_in，默认 30 天（实例可改）
典型内容node_modules、.m2、.gomodcache、编译中间目录二进制、镜像 tar、JUnit/coverage 报告、Helm values
混用症状拿 cache 传产物：换 runner 或 key 变化后，部署 job 神秘地找不到文件拿 artifacts 传依赖：每个 job 都全量上传下载几百 MB，比重装依赖还慢，还撑爆存储配额

调优要点有三个。一是 cache:key:files：把 key 绑定到锁文件哈希，锁文件不变必定复用、变了自动换 key，比手写 key: $CI_COMMIT_REF_SLUG 靠谱得多（后者会让每个分支各存一份，很快撑爆磁盘）。二是 policy：绝大多数消费缓存的 job 应设 policy: pull，只有一个专门的 job 用 pull-push 负责更新，能省掉每个 job 结束时的压缩与上传时间。三是 artifacts:when: always：测试失败时的报告才是最需要看的，默认的 on_success 会把它丢掉。

# .gitlab-ci.yml —— 一份可直接改用的完整配置
stages: [build, test, package, deploy]

# workflow:rules 决定"整条流水线是否创建"，比在每个 job 上写 rules 更根治
# 不配它就会出现同一个提交同时跑 branch pipeline 与 MR pipeline 的双流水线问题
workflow:
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
    - if: $CI_COMMIT_TAG
    - when: never

default:
  image: golang:1.22-alpine
  interruptible: true         # 配合项目设置的自动取消冗余流水线，新推送会掐掉旧的
  retry:
    max: 2
    when: [runner_system_failure, stuck_or_timeout_failure]   # 只重试基础设施失败，不要重试脚本失败

variables:
  GIT_DEPTH: "50"             # 默认 20 的浅克隆；要 tag 或跨分支 diff 就得放大，需要全量设 0
  GIT_SUBMODULE_STRATEGY: recursive
  FF_USE_FASTZIP: "true"      # 大 cache/artifacts 的打包提速开关

.go-cache: &go-cache          # YAML 锚点只在当前文件内有效，跨文件要用 extends
  key:
    files: [go.sum]           # 按锁文件内容哈希；锁文件没变就一定复用同一份缓存
  paths: [.gocache, .gomodcache]
  policy: pull-push

build:
  stage: build
  cache:
    - <<: *go-cache
  script:
    - go build -trimpath -o dist/app ./cmd/app
  artifacts:
    paths: [dist/app]
    expire_in: 1 week         # 过期后想回滚就拿不到这个产物了，正式发布件建议单独归档

lint:
  stage: test
  needs: []                   # 空数组：不等任何上游，流水线一开始就跑，是最廉价的提速手段
  cache:
    - <<: *go-cache
      policy: pull            # 只读，省掉每个 job 结束时的缓存上传耗时
  script: [golangci-lint run ./...]

unit-test:
  stage: test
  needs: []
  cache:
    - <<: *go-cache
      policy: pull
  script:
    - go test ./... -coverprofile=cover.out
  coverage: '/total:\s+\(statements\)\s+(\d+.\d+)%/'
  artifacts:
    when: always              # 失败时也要留报告，默认 on_success 会让失败原因丢失
    reports:
      junit: report.xml

integration-test:
  stage: test
  needs: [build]              # 只等 build，不等同 stage 的 lint 与 unit-test
  services:
    - name: mysql:8.0
      alias: mysql            # 容器网络里用 alias 当主机名，写 localhost 一定连不上
      variables:
        MYSQL_ROOT_PASSWORD: root
        MYSQL_DATABASE: app
  variables:
    DB_DSN: root:root@tcp(mysql:3306)/app
  before_script:
    - until nc -z mysql 3306; do sleep 1; done   # service 容器起来不等于服务 ready，必须自己等
  script: [go test ./it/... -tags=integration]

package:
  stage: package
  needs: [build, unit-test]
  image:
    name: gcr.io/kaniko-project/executor:v1.23.2-debug
    entrypoint: [""]          # 必须清空，否则 runner 无法注入自己的 shell
  script:
    # Kaniko 不需要 privileged，也不需要 docker daemon；层缓存推到 registry，跨 runner 可复用
    - /kaniko/executor --context "$CI_PROJECT_DIR" --dockerfile Dockerfile
      --destination "$CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA"
      --cache=true --cache-repo "$CI_REGISTRY_IMAGE/cache"
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
    - if: $CI_COMMIT_TAG

deploy-staging:
  stage: deploy
  needs: [package]
  environment:
    name: staging
    url: https://staging.example.com
    deployment_tier: staging  # 让 GitLab 正确统计 DORA 指标与环境层级
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
  script: [./deploy.sh staging]

deploy-prod:
  stage: deploy
  needs: [deploy-staging]
  environment:
    name: production
    url: https://example.com
    deployment_tier: production
  resource_group: prod-deploy # 同一时刻只允许一个 prod 部署在跑，天然避免并发发布打架
  rules:
    - if: $CI_COMMIT_TAG
      when: manual
      allow_failure: false    # manual job 默认 allow_failure 为 true，不写这行流水线会"绿着"跳过
  script: [./deploy.sh prod]

rules 取代 only/except：控制 job 与整条流水线

only/except 在 GitLab 12.3 之后就处于事实弃用状态，新配置一律用 rules。rules 的语义是自上而下取第一个匹配项，命中后用该项的 when、variables、allow_failure；全都不匹配则该 job 不被创建。理解「不被创建」和「被创建但跳过」的区别很关键：when: never 是不创建，下游 needs 它的 job 会因为找不到依赖而让整条流水线创建失败，除非下游写了 needs: [{job: x, optional: true}]。

workflow:rules 是全局开关，决定这次事件要不要创建流水线。它最常用来消除「同一次 push 既跑分支流水线又跑 MR 流水线」的重复计费问题——只允许 MR 事件、默认分支与 tag 三种来源即可。

需求rules 写法要点常见错误
只在 MR 里跑if: $CI_PIPELINE_SOURCE == "merge_request_event"用 only: merge_requests 与别处的 rules 混用，直接语法错误
只在默认分支部署if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH 后跟 when: never漏掉兜底的 when: never，其他分支意外生成 job
按路径变更触发changes:paths 配 compare_to不写 compare_to，长分支上比对基准漂移；非 MR 场景 changes 可能恒为真
按版本号 tag 发布if: $CI_COMMIT_TAG =~ /^v\d+/ 加 when: manual忘了 allow_failure: false，手动 job 未点也算流水线成功
整条流水线只在特定来源创建顶层 workflow:rules在每个 job 上重复写 rules，漏一个就出现重复流水线
被 rules 剔除的上游下游用 needs 的 optional: true不写时流水线直接创建失败，报 job needs 不存在
# ---- rules 常用片段（只在 MR 跑 / 只在默认分支部署 / 按路径变更触发）----

# 1) 只在合并请求流水线里跑
rules:
  - if: $CI_PIPELINE_SOURCE == "merge_request_event"

# 2) 只在默认分支部署，其余场景连 job 都不生成
rules:
  - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
  - when: never

# 3) 按路径变更触发：monorepo 里只跑受影响的服务
rules:
  - if: $CI_PIPELINE_SOURCE == "merge_request_event"
    changes:
      paths: [services/order/**/*, go.mod, go.sum]
      compare_to: refs/heads/main   # 不写 compare_to 时是和上一次提交比，长分支上判断会漂

# 4) 只有符合语义化版本的 tag 才允许发布，并且必须人工点
rules:
  - if: $CI_COMMIT_TAG =~ /^v\d+\.\d+\.\d+$/
    when: manual
    allow_failure: false

# 5) 定时流水线跑全量回归：rules 里可以顺手覆盖变量
rules:
  - if: $CI_PIPELINE_SOURCE == "schedule"
    variables:
      TEST_SCOPE: full

# 6) 排除 draft MR，省额度
rules:
  - if: $CI_MERGE_REQUEST_TITLE =~ /^Draft:/
    when: never
  - if: $CI_PIPELINE_SOURCE == "merge_request_event"

# 注意：同一个 job 里 only/except 与 rules 不能共存，会直接报语法错误；
# 迁移时必须整段替换，不能一半 only 一半 rules。

父子流水线与多项目流水线：monorepo 的拆分手段

单仓多服务的 monorepo 如果把所有服务写进一个 .gitlab-ci.yml，很快会变成上千行且每次提交全量构建。trigger 关键字提供两种拆法：父子流水线（trigger:include）让每个服务维护自己的 CI 文件，父流水线按 changes 决定触发哪些子流水线；多项目流水线（trigger:project）跨仓库触发，适合代码仓与部署仓分离的结构。

这里有个必须写的参数：strategy: depend。不写它时，触发 job 的语义是「触发成功就算成功」，子流水线失败父流水线依然是绿的——这个默认值坑过很多团队的发布门禁。另外子流水线默认无法读取父流水线的 artifacts，跨流水线传产物要显式用 needs:pipeline:job 或走 registry。

# ---- 模板复用：include 跨文件，extends 跨 job，锚点只在同文件 ----
include:
  - project: platform/ci-templates
    ref: v3.2.0                      # 一定要 pin tag 或 sha，写 main 等于把构建交给别人改
    file: [/templates/go.yml, /templates/security.yml]
  - local: /ci/deploy.yml
  - template: Security/SAST.gitlab-ci.yml
  - component: $CI_SERVER_FQDN/org/ci-components/build@1.2.0

.base-test:                          # 以点开头的是隐藏 job，不会被调度，只做模板
  image: golang:1.22
  before_script: [go mod download]
  cache:
    - key: {files: [go.sum]}
      paths: [.gomodcache]
      policy: pull

test:unit:
  extends: .base-test                # extends 做深度合并且能跨 include 文件，优先于 YAML 锚点
  script: [go test ./... -short]

# ---- 父子流水线：monorepo 里只构建变更的服务 ----
trigger-order:
  stage: build
  trigger:
    include: services/order/.gitlab-ci.yml
    strategy: depend                 # 父流水线等子流水线结果；不写则"触发即成功"，失败被吞掉
  rules:
    - changes: [services/order/**/*]

# ---- 多项目流水线：代码仓触发独立的部署仓 ----
deploy-via-infra:
  stage: deploy
  trigger:
    project: infra/deployments
    branch: main
    strategy: depend
  variables:
    UPSTREAM_IMAGE: $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA   # 下游用 $UPSTREAM_IMAGE 读取

环境、手动部署与变量体系

environment 不只是一个标签：声明后 GitLab 会记录部署历史、在 MR 上显示「已部署到 staging」、支持一键回滚到之前的部署、并且可以给环境配保护规则（只有特定角色能部署、需要审批）。deployment_tier 告诉 GitLab 这个环境属于哪一层，DORA 指标统计依赖它。生产部署建议再配 resource_group，把同一环境的部署 job 串行化，避免两个流水线同时往生产推。

when: manual 的默认行为是个陷阱：手动 job 默认 allow_failure: true，也就是说你不点它，流水线照样显示成功。如果这个手动 job 是生产发布的门禁，就必须显式写 allow_failure: false，否则流水线绿了但什么都没部署。

变量特性含义局限 / 风险
定义层级：实例 → 组 → 项目 → 流水线 → job同名变量按就近原则覆盖，job 级优先级最高组级变量被项目同名变量悄悄覆盖，排查时要看「CI/CD 变量」的完整继承链
protected只有受保护分支与受保护 tag 的流水线才注入生产凭证必须勾；不勾等于任何分支都能拿到生产密钥
masked仅仅是日志里把匹配到的原文替换成星号不是加密：脚本里 base64、逐字符拆分或写进 artifacts 都能绕过；值还有字符集与长度限制，不满足时静默不打码
文件类型变量（File）值被写成临时文件，变量里存的是路径kubeconfig、服务账号 JSON 必须用这种；用普通变量会因换行被破坏
预定义变量CI_COMMIT_SHA、CI_PIPELINE_SOURCE、CI_ENVIRONMENT_NAME 等MR 流水线与分支流水线里可用变量不同，CI_COMMIT_BRANCH 在 MR 流水线里是空的
rules:variables按条件覆盖变量只影响该 job；和 workflow:rules:variables 的作用域容易混
复用机制作用范围合并语义什么时候用
YAML 锚点（& 与 *）仅当前文件浅合并，<< 只并一层同文件内几行配置的复制，别用于跨团队模板
extends跨 include 文件深度合并，支持多层与多父主力手段：抽 .base-test 这类隐藏 job
include:local同仓库其他文件拼接后整体解析按服务或按阶段拆分大文件
include:project跨项目模板库同上，需 ref平台团队统一管控；必须 pin tag 或 sha
include:templateGitLab 内置模板同上SAST、Dependency Scanning 等现成能力
CI/CD Components版本化的可复用组件带输入参数新项目优先，比裸 include 有明确的输入契约

排查手段

# ---- 排查 runner 与流水线问题的常用命令 ----

# 1) 本地校验语法：不提交也能验，避免"push 一次错一次"
curl -s --header "PRIVATE-TOKEN: $TOKEN" \
  --header "Content-Type: application/json" \
  --data "{\"content\": $(jq -Rs . .gitlab-ci.yml)}" \
  "https://gitlab.example.com/api/v4/projects/$PID/ci/lint?include_merged_yaml=true" | jq .

# 2) 看这个项目实际能用哪些 runner，以及它们的 tag（job 卡在 pending 通常就是 tag 对不上）
curl -s --header "PRIVATE-TOKEN: $TOKEN" \
  "https://gitlab.example.com/api/v4/projects/$PID/runners" | jq '.[] | {id, description, tag_list, online}'

# 3) runner 侧排查：确认注册、并发与执行器配置
gitlab-runner verify
gitlab-runner list
grep -E "concurrent|executor|privileged|\[runners.cache\]" /etc/gitlab-runner/config.toml

# 4) 在本地用 docker executor 复现某个 job（跑的是当前工作区的 .gitlab-ci.yml）
gitlab-runner exec docker unit-test --docker-image golang:1.22-alpine

# 5) 看清工作区被清成什么样：GIT_STRATEGY 与 GIT_CLEAN_FLAGS 决定残留
#    shell executor 上残留最常见，怀疑"上次构建的文件还在"就先看这两个变量
echo "$GIT_STRATEGY / $GIT_CLEAN_FLAGS"

# 6) 缓存到底存哪：分布式缓存没配时，cache 落在 runner 本机，换台机器必然 miss
docker volume ls | grep runner-cache
现象真实原因修法
job 一直 pendingtags 与 runner tag 不匹配，或 runner 未勾选运行未打 tag 的 job核对 tag 列表；临时用 API 查项目可用 runner
缓存在某些 job 里总是 misscache 默认存 runner 本机，多 runner 环境必然不共享配 [runners.cache] 指向 S3/MinIO 等分布式缓存
回滚时拿不到旧产物artifacts 的 expire_in 到期被清理发布件改推 registry 或包仓库；关键 artifacts 设 keep
报 only 与 rules 不能共存同一 job 里混写两套条件语法整段替换成 rules，不要半迁移
git describe 或 tag 判断失败GIT_DEPTH 默认 20 的浅克隆没拉到 tag放大 GIT_DEPTH 或设 0；必要时单独 git fetch --tags
集成测试随机连不上数据库service 容器已启动但服务未 ready；或用了 localhost用 alias 作主机名，并在 before_script 轮询等待端口
子流水线失败但父流水线是绿的trigger 缺 strategy: depend补上；发布门禁类触发必须写
手动生产部署没点，流水线却成功when: manual 默认 allow_failure: true显式写 allow_failure: false
shell executor 上「上次构建的文件还在」工作区复用，GIT_CLEAN_FLAGS 未清干净换 docker executor，或设 GIT_STRATEGY: clone
❌
最容易踩的坑

1）以为 cache 能在多台 runner 间共享：没配分布式缓存后端时它就在 runner 本机，换机器必 miss。
2）拿 cache 传部署产物：key 一变或缓存被清，发布 job 凭空找不到文件；产物只能走 artifacts 或 registry。
3）拿 artifacts 传 node_modules：每个 job 全量上传下载，比重装还慢，并且吃满存储配额。
4）cache:key 写成 $CI_COMMIT_REF_SLUG：每个分支各存一份，磁盘很快爆；应按锁文件哈希。
5）同一 job 里 only 和 rules 混用：直接语法错误，迁移必须整段替换。
6）不配 workflow:rules：一次 push 同时跑分支流水线与 MR 流水线，额度翻倍。
7）when: manual 不写 allow_failure: false：没人点生产发布，流水线照样显示成功。
8）trigger 不写 strategy: depend：子流水线失败被吞，父流水线一片绿。
9）默认 GIT_DEPTH 为 20：拿不到 tag、跨分支 diff 不全，changes 判断跟着出错。
10）集成测试用 localhost 连 service：必须用 alias 主机名，且要自己等服务 ready。
11）为了 dind 给共享 runner 开 privileged：等于把宿主机交给任何能提 MR 的人，改用 Kaniko。
12）以为 masked 等于安全：它只做日志文本替换，base64 或写进 artifacts 都能绕过；生产凭证必须同时勾 protected 并限制在受保护分支。
13）include:project 写 ref: main：平台团队一改模板，所有项目的流水线当天一起变。
