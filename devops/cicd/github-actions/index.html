GitHub Actions 执行模型与实战配置：job 隔离、缓存语义与供应链安全

🏷️ GitHub Actions

GitHub Actions 的上手门槛低，但真正让人卡住的从来不是 YAML 语法，而是三个执行语义上的事实：job 之间不共享文件系统、缓存是不可变且按分支隔离的、事件类型决定了这条流水线能不能碰到密钥。这三件事没搞清楚，写出来的流水线要么慢，要么在某个分支上诡异地失败，要么直接成为供应链攻击的入口。这篇只讲机制和可以直接抄走的配置；流水线本身的设计原则与落地节奏，详见站内《CI/CD 工具选型》。

四层模型：workflow、job、step、action 各自的边界

这四层不是命名上的层级关系，而是隔离边界的层级关系。workflow 是一个事件响应单元，一次触发产生一次 run；job 是调度与隔离单元，每个 job 独占一台 runner；step 是 job 内部的顺序执行单元，共享同一个工作区；action 只是 step 的一种实现方式（另一种是 run）。搞清楚这一点，很多困惑自动消解：为什么 cd 在下一个 step 里失效（每个 run 是独立进程，只有工作目录默认相同）、为什么 export 的变量下一步读不到（要写进 $GITHUB_ENV）、为什么上一个 job 编译的二进制在下一个 job 里找不到（压根不是同一台机器）。

层级隔离粒度共享什么不共享什么高频误解
workflow一个 YAML 文件对应一组事件仓库级 secrets、variables与其他 workflow 的运行状态（除 workflow_run）以为多个 workflow 会按文件名顺序跑
job一台全新 runner（虚拟机或容器）只有 artifact、cache、outputs 三条显式通道文件系统、环境变量、已装软件、Docker 镜像层以为 needs 之后能直接读到上游文件
step同一 runner 上的一次进程调用工作区、$GITHUB_ENV、$GITHUB_PATH、服务容器进程内状态：cd、export、shell 函数以为 export VAR=x 能传到下一步
action一个可复用 step（JS / Docker / composite）调用它的 job 的工作区与环境无独立生命周期，失败即 step 失败以为 Docker 类 action 在 macOS runner 上也能跑（不能）

job 之间为什么拿不到文件：artifact 与 cache 两条通道

这是 GitHub Actions 最高频的困惑。needs 只表达执行顺序依赖，不表达数据依赖。每个 job 启动时 GitHub 分配一台干净的托管 runner，工作区是空的，连 actions/checkout 都得重新跑一遍。上游 job 产出的东西要想传下去只有三条路：小字符串走 outputs（有 1 MB 上限，且不能放密钥，它会明文出现在日志与 API 里）、构建产物走 artifact、可重建的依赖走 cache。

⚠️
artifact v3 已停服，v4 不是无痛升级

upload-artifact@v3 已于 2025 年 1 月起停止服务。v4 的两个行为变更会直接打断老流水线：一是同一 run 内 artifact 名字必须唯一，矩阵构建里所有组合都上传 coverage 会报冲突，必须把 matrix 值拼进名字；二是 v4 的 download-artifact 不能下载 v3 上传的产物，反之亦然，混用时得到的是「找不到 artifact」而不是明确的版本错误。

触发器矩阵：pull_request_target 是真实的攻击面

事件类型决定三件事：工作流定义从哪个 ref 读取、GITHUB_TOKEN 的默认权限、fork 来的 PR 能不能拿到 secrets。pull_request 对 fork PR 做了严格降级：secrets 全部为空、GITHUB_TOKEN 只读。有人为了让 fork PR 也能跑需要密钥的步骤（打评论、上传预览），改用 pull_request_target——这个事件用的是基础分支的工作流定义，并且带完整 secrets。如果在里面显式检出 PR 的 commit 再执行构建脚本，攻击者只要在 fork 里改一行 package.json 的 postinstall，就能在带密钥的环境里执行任意代码。

pull_request 只做无密钥构建，workflow_run 做带密钥的后置动作
事件工作流定义来自fork PR 能拿 secretsGITHUB_TOKEN 默认典型用途与风险
push被推送的 ref不适用按仓库设置（建议显式最小化）主干构建、按 tag 发布
pull_requestPR 的合并结果（merge ref）否同仓 PR 可写，fork PR 只读默认选它；让 fork PR 跑测试是安全的
pull_request_target基础分支是可写只用于不检出 PR 代码的元操作（打标签、评论）；检出 PR 代码等于交出密钥
workflow_dispatch选定的分支不适用可写手动部署，支持 choice / boolean / environment 输入
schedule默认分支（只认默认分支上的定义）不适用可写定时巡检；高峰延迟可达几十分钟，仓库 60 天无提交会被自动禁用
workflow_run默认分支不适用（本身带 secrets）可写串联前一条无密钥流水线，安全地做带密钥的后置动作
❌
三种会直接泄露密钥的写法

一是 pull_request_target 里检出 github.event.pull_request.head.sha 然后执行项目脚本；二是把不受信输入（PR 标题、分支名、issue 正文）直接插进 run 的表达式里——表达式是在生成 shell 脚本之前做文本替换的，分支名里带分号和反引号就是命令注入，正确做法是先赋给 env 再用带引号的变量引用；三是公开仓库挂 self-hosted runner，任何人提个 PR 就能在你的内网机器上执行代码，而且 runner 工作区在多次构建之间是持久的。

缓存机制：key 不可变、前缀匹配、分支单向可见

actions/cache 有三条容易踩的规则。第一，缓存条目不可变：key 已存在时，job 结束时的写入会被静默忽略，日志里只有一行 Cache already exists。所以 key 里不含锁文件哈希的话，依赖更新后永远命中旧缓存，改 YAML 也救不回来，必须换 key 或手动删除。第二，restore-keys 是前缀匹配，按列表顺序尝试，同前缀下取最近创建的那条；命中 restore-keys 时 cache-hit 输出仍然不是 true，这个区分是刻意的——它意味着你拿到的是近似缓存，还需要跑一次增量安装。第三，缓存可见性是单向的：分支能读到自己和默认分支（以及父分支）的缓存，但默认分支读不到子分支写入的缓存。这解释了一个经典现象：PR 上缓存命中率很高，合进 main 之后第一次构建又慢回去了。

关于 setup-* 自带缓存与手写 actions/cache：能用内置的就用内置的。setup-node、setup-go、setup-python、setup-java 的 cache 参数会自动挑对目录、自动用锁文件算哈希，还处理了跨平台路径差异。只有三种情况需要手写：缓存内容不是包管理器目录（Rust 的 target/、Gradle 的 build/、Playwright 浏览器包）、需要只读缓存（用 cache/restore 子 action）、需要多级 restore-keys 降级策略。

        with:
          path: .venv
          key: py-${{ runner.os }}-${{ matrix.python }}-${{ hashFiles('poetry.lock') }}

矩阵构建与并发控制

矩阵的坑集中在两个默认值上。fail-fast 默认为 true：任一组合失败，同 strategy 下其余正在跑的组合会被立刻取消，这在「想知道到底哪几个版本挂了」的场景非常碍事，排查期应显式关掉。max-parallel 不设时会用尽账户可用并发数，而并发数是账户级配额（免费版约 20 个并发作业，Team 与 Enterprise 逐级放宽，macOS runner 另有更严格的单独上限），一个仓库的大矩阵可以把全组织的流水线堵住。include 与 exclude 的语义也常被弄反：exclude 先删组合，include 后补——include 里的键如果能匹配上已有组合，就是给这个组合追加变量；匹配不上才新增组合。

concurrency 解决的是另一类浪费：同一个 PR 连推三次，三条流水线并行跑，前两条的结果已经没有意义。把 group 设成含 github.head_ref 的表达式并开启 cancel-in-progress，新 run 会自动取消同组旧 run。但主干与部署 job 上不要开 cancel-in-progress——部署被中途取消会留下半完成状态，正确做法是 group 用固定串（如 deploy-prod）而 cancel-in-progress 设为 false，让部署串行排队。

权限与供应链：最小权限、OIDC、pin 到 sha

三件事按收益排序：显式写 permissions、用 OIDC 替掉长期云凭证、第三方 action 一律 pin commit sha。

GITHUB_TOKEN 是每次 run 自动签发的临时 token，随 job 结束失效。它的默认权限取决于仓库与组织设置：2023 年 2 月之后新建的仓库默认只读，但老仓库和迁移过来的仓库很可能仍是 read-write all。这意味着任何一个被投毒的第三方 action 都能推分支、改 workflow、发 release。正确做法是在 workflow 顶层写 permissions 只给 contents: read，再在真正需要写权限的单个 job 上按需提权。

OIDC 是现在部署到云的标准做法：job 向 GitHub 申请一个带 claims（仓库、分支、环境、事件类型）的短期 JWT，云端 IAM 校验这些 claims 后换发临时凭证。它彻底消除了「AK/SK 躺在 Secrets 里、泄露了没人知道、轮换全靠人肉」的问题。关键细节是云端信任策略里的 sub 条件必须写细：只约束到仓库粒度，等于允许该仓库任何分支拿到生产权限，任何有 push 权限的人建个分支就能部署生产。

做法凭证形态泄露影响面轮换成本要注意的点
AK/SK 存 Secrets长期有效全量权限，且可能永久有效人工，常年不做Secrets 在 fork PR 下不可见，但一旦被外带就无法感知
OIDC 联合身份分钟级临时凭证受 claims 与 IAM 策略双重约束无需轮换需要 id-token: write；sub 必须约束到分支或 environment
第三方 action 写 @v4—tag 可被仓库主或被盗账号重新指向任意提交—方便但不可信，等于把执行权交给上游
第三方 action pin sha—内容寻址，不可被替换靠 Dependabot 自动提 PR仍要看该 action 内部是否引用了未 pin 的子 action
self-hosted runner—工作区跨构建持久、可触达内网—公开仓库绝对不能用；私仓也建议用一次性容器化 runner
# .github/workflows/ci.yml
name: ci
on:
  push:
    branches: [main]
    tags: ['v*']              # tag 推送才进发布 job
  pull_request:               # fork 的 PR 在这个事件下拿不到 secrets，这是安全特性不是 bug
    branches: [main]
  workflow_dispatch:
    inputs:
      target:
        description: 手动部署目标
        type: choice          # choice/boolean/environment/string，UI 上会渲染成下拉框
        default: staging
        options: [staging, prod]
  schedule:
    - cron: '17 3 * * *'      # 只支持 UTC；整点排队最严重，故意错开到 17 分

# 不写 permissions 时，老仓库默认是 read-write all，等于给每个 step 一把能写仓库的钥匙
permissions:
  contents: read

concurrency:
  # head_ref 只在 PR 事件有值，回退到 ref 才能同时覆盖 push 与 PR
  group: ci-${{ github.workflow }}-${{ github.head_ref || github.ref }}
  cancel-in-progress: ${{ github.event_name == 'pull_request' }}   # main 上的构建不要互相取消

jobs:
  test:
    runs-on: ubuntu-latest
    timeout-minutes: 20       # 默认 360 分钟，卡死的 job 会白烧一整天额度
    strategy:
      fail-fast: false        # 默认 true：一个组合失败会掐掉其余组合，排查期建议关掉
      max-parallel: 4
      matrix:
        go: ['1.21.x', '1.22.x']
        os: [ubuntu-latest, windows-latest]
        exclude:
          - os: windows-latest
            go: '1.21.x'      # windows runner 按 2 倍分钟计费，只保最新版本
    steps:
      - uses: actions/checkout@08c6903cd8c0fde910a37f88322edcfb5dd907a8   # v5.0.0，pin sha
        with:
          fetch-depth: 0      # 默认 1（浅克隆）；git describe、变更文件比对都需要完整历史
      - uses: actions/setup-go@41dfa10bad2bb2ae585af6ee5bb4d7d973ad74ed   # v5.1.0
        with:
          go-version: ${{ matrix.go }}
          cache: true         # 内置缓存，key 自动取 go.sum 哈希，比手写 actions/cache 省事
      - run: go vet ./...
      - run: go test ./... -race -covermode=atomic -coverprofile=cover.out
      - name: 上传覆盖率产物
        if: matrix.os == 'ubuntu-latest' && matrix.go == '1.22.x'
        uses: actions/upload-artifact@ea165f8d65b6e75b540449e92b4886f43607fa02  # v4.6.2
        with:
          name: coverage-${{ matrix.os }}-${{ matrix.go }}   # v4 起同名 artifact 不能重复上传
          path: cover.out
          retention-days: 7   # 默认 90 天，artifact 计入仓库存储配额

  build:
    needs: [test]             # 不写 needs 的 job 一律并行启动
    runs-on: ubuntu-latest
    outputs:
      version: ${{ steps.meta.outputs.version }}
    steps:
      - uses: actions/checkout@08c6903cd8c0fde910a37f88322edcfb5dd907a8
        with: {fetch-depth: 0}
      - id: meta
        run: echo "version=$(git describe --tags --always)" >> "$GITHUB_OUTPUT"
      - run: |
          CGO_ENABLED=0 go build -trimpath \
            -ldflags "-s -w -X main.version=${{ steps.meta.outputs.version }}" \
            -o dist/app ./cmd/app
      - uses: actions/upload-artifact@ea165f8d65b6e75b540449e92b4886f43607fa02
        with:
          name: app-binary
          path: dist/app

  release:
    needs: [build]
    if: startsWith(github.ref, 'refs/tags/v')
    runs-on: ubuntu-latest
    environment: prod         # 在 environment 上挂审批人与保护规则，job 会先进 waiting 状态
    permissions:
      contents: write         # 建 release 要写权限，只在这一个 job 提权
      id-token: write         # 申请 OIDC token 的必要权限，缺了报 unable to get ACTIONS_ID_TOKEN_REQUEST_URL
    steps:
      - uses: actions/download-artifact@d3f86a106a0bac45b974a628896c90dbdf5c8093  # v4.3.0
        with:
          name: app-binary    # build job 的 runner 已销毁，产物只能从 artifact 存储取
          path: dist
      - name: OIDC 换取云端临时凭证，仓库里不存任何长期 AK/SK
        uses: aws-actions/configure-aws-credentials@e3dd6a429d7300a6a4c196c26e071d42e0343502  # v4.0.2
        with:
          role-to-assume: arn:aws:iam::123456789012:role/gha-deploy
          aws-region: ap-northeast-1
      - run: aws s3 cp dist/app "s3://my-artifacts/${{ needs.build.outputs.version }}/app"

复用：workflow_call 与 composite action 怎么选

两者解决的是不同粒度的重复。workflow_call（可复用工作流）复用的是整个 job 及其 runner 选择、权限、环境，调用方以 job 为单位引用，被调用方跑在自己的 runner 上、有自己的 permissions；它适合「整条标准构建发布链」这种大块复用，也是集中管控权限与合规检查的好位置。composite action 复用的是一串 step，跑在调用者的同一台 runner 上、能读写当前工作区，适合「装工具链、算版本号、登录镜像仓库」这类片段。选择标准很简单：需要换 runner 或独立权限就用 workflow_call，只是想少写几行 step 就用 composite action。

维度workflow_callcomposite action
引用位置job 级 uses，该 job 不能再写 stepsstep 级 uses
运行环境自己的 runner 与工作区调用方的 runner 与工作区
secrets需显式传入或 secrets: inherit作为 inputs 传，注意不会被自动打码
嵌套深度最多 4 层，超了整条 run 直接校验失败可嵌套，但调试时栈很难看
能否用 matrix调用方可以对它做 matrix自身不能带 matrix
适合场景标准化构建发布链、集中管控权限环境准备、版本计算等 step 片段
# 被调用方：.github/workflows/reusable-build.yml
# workflow_call 让整个 workflow 变成一个可调用单元，调用方以 job 为粒度引用
on:
  workflow_call:
    inputs:
      go-version: {type: string, required: true}
    secrets:
      REGISTRY_TOKEN: {required: false}
    outputs:
      image:
        value: ${{ jobs.build.outputs.image }}   # 必须从内部 job 的 outputs 冒泡上来
jobs:
  build:
    runs-on: ubuntu-latest
    outputs:
      image: ${{ steps.push.outputs.image }}
    steps:
      - uses: actions/checkout@v5
      - id: push
        run: echo "image=ghcr.io/org/app:${GITHUB_SHA::12}" >> "$GITHUB_OUTPUT"

# ----------------------------------------------------------------------
# 调用方：uses 写在 job 级别（不是 step 级别），该 job 下不能再写 steps
jobs:
  call-build:
    uses: org/repo/.github/workflows/reusable-build.yml@v1
    with:
      go-version: '1.22.x'
    secrets: inherit            # 不写这行，被调用方一个 secret 都拿不到
  use-output:
    needs: [call-build]
    runs-on: ubuntu-latest
    steps:
      - run: echo "镜像是 ${{ needs.call-build.outputs.image }}"

# ----------------------------------------------------------------------
# composite action：.github/actions/setup-env/action.yml
# 它是 step 级别的复用，跑在调用它的 job 的同一台 runner 上，能读到当前工作区
runs:
  using: composite
  steps:
    - run: echo "BUILD_TS=$(date -u +%FT%TZ)" >> "$GITHUB_ENV"
      shell: bash               # composite action 里 shell 是必填项，漏了直接校验失败

调试手段与常见报错对照

# 1. 用 gh cli 定位失败，比在网页上逐个点 step 快得多
gh run list --workflow=ci.yml --branch=main --limit 5
gh run view 1234567890 --log-failed         # 只打印失败 step 的完整日志

# 2. 打开 step 级调试日志：加仓库变量 ACTIONS_STEP_DEBUG=true
#    会额外输出 ::debug:: 行，含 action 输入的解析结果与表达式求值过程
gh variable set ACTIONS_STEP_DEBUG --body true

# 3. 缓存排查：单仓库上限 10 GB，超了按最近最少使用淘汰，7 天未访问自动过期
gh cache list --limit 30 --sort size_in_bytes --order desc
gh cache delete py-Linux-3.12-abc123        # 缓存不可变：同 key 想换内容必须先删再写

# 4. 检查某个 tag 当前指向哪个 commit（tag 可被强制重指，这正是要 pin sha 的原因）
gh api repos/actions/checkout/git/ref/tags/v4 --jq .object.sha

# 5. 本地复现：act 用 Docker 模拟 runner，注意它不支持 OIDC、部分上下文与 service container
act pull_request -W .github/workflows/ci.yml -j test --container-architecture linux/amd64

# 6. 看当前 job 实际拿到的权限，排查 403 Resource not accessible by integration
curl -sS -H "Authorization: Bearer $GITHUB_TOKEN" \
  "https://api.github.com/repos/$GITHUB_REPOSITORY" 2>&1 | head -5
报错或现象真实原因修法
Resource not accessible by integration（403）GITHUB_TOKEN 权限不足，或 fork PR 下被降级为只读给该 job 加对应 permissions；fork 场景改用 workflow_run 串联
unable to get ACTIONS_ID_TOKEN_REQUEST_URL缺 id-token: write在 job 级 permissions 补上；注意 job 级会整体覆盖顶层声明
下游 job 报文件不存在误以为 needs 能传文件上游 upload-artifact，下游 download-artifact
缓存一直命中旧依赖key 不含锁文件哈希，且缓存条目不可覆盖key 加 hashFiles；或用 gh cache delete 删掉后重跑
合并到 main 后缓存突然不命中缓存可见性单向，main 读不到子分支缓存在默认分支上定时跑一条预热 workflow 写入缓存
git describe 报 No names foundcheckout 默认 fetch-depth: 1，本地没有 tag设 fetch-depth: 0，或单独跑 git fetch --tags --unshallow
schedule 配好了不触发定时事件只读默认分支上的定义；仓库 60 天无活动会被自动禁用把 workflow 合进默认分支；用 workflow_dispatch 先手动验证
Docker 类 action 在 macOS runner 报错只有 Linux runner 支持容器 action 与 service container该 job 换 ubuntu-latest，或改写成 composite action
service container 连不上在容器里用 localhost，或没等服务 ready 就连容器内用服务名作主机名；配 options 里的健康检查参数
❌
最容易踩的坑

1）以为 needs 能传文件：每个 job 一台新机器，必须走 artifact。
2）pull_request_target 里检出 PR 的 sha 再跑项目脚本，等于把全部 secrets 交给任何人。
3）把 PR 标题、分支名这类不受信输入直接写进 run 的表达式，构成 shell 注入；应先经 env 再引用。
4）缓存 key 不含锁文件哈希：缓存不可覆盖，从此永久命中首次内容。
5）用 cache 传部署产物：某天 7 天未访问被清理，发布凭空失败。
6）第三方 action 写 @v3：tag 可被重新指向，供应链投毒就靠这个，一律 pin commit sha。
7）不写 permissions：老仓库默认 read-write all，一个投毒 action 就能改你的 workflow。
8）部署 job 开 cancel-in-progress：发布中途被取消，留下一半新一半旧的状态。
9）fetch-depth 保持默认 1，却在流水线里 git describe 或比对 base 分支，必然失败。
10）矩阵不设 max-parallel 与 timeout-minutes：占满账户并发，卡死的 job 烧 6 小时额度。
11）公开仓库挂 self-hosted runner：任何人提 PR 就能在你的内网机器上执行代码，且工作区跨构建残留。
12）以为密钥打码等于安全：日志打码只匹配原文，base64 或逐字符拆分即可绕过，安全要靠权限收敛而不是靠打码。
