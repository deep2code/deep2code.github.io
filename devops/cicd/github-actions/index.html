GitHub Actions

🏷️ GitHub Actions,CI/CD

一、GitHub Actions 是什么

GitHub Actions（GHA）是 GitHub 内置的 CI/CD 服务：你只需在仓库 .github/workflows/ 目录放一个 YAML 文件，push 或 PR 时 GitHub 的 Runner 就会自动执行。它的杀手锏不是功能多，而是零运维 + 与代码托管同处一地——代码、PR、Issue、流水线在同一个界面流转，这对开源项目和中小团队几乎是无可替代的体验。

二、核心概念：Workflow / Job / Step / Action / Runner

初学者最容易混乱的就是这套术语，其实是层层包含关系：

  • Workflow：一条完整流水线，一个 YAML 文件即一个 workflow，由 name 和 on（触发器）定义。
  • Job：一次执行中的一个独立运行单元，默认每个 Job 跑在全新的干净虚拟机上，Job 之间默认并行。
  • Step：Job 内的一步步操作，可以是一条 shell 命令，也可以是一个 Action。
  • Action：可复用的步骤封装（如 checkout、setup-node），社区市场（Marketplace）有海量现成 Action。
  • Runner：执行环境。GitHub 托管的有 ubuntu-latest / windows-latest / macos-latest；也可注册自托管 Runner 访问内网资源。

三、安装与配置：零安装起步

GHA 无需安装。准备工作只有两步：① 仓库根目录新建 .github/workflows/；② 把 YAML 提交，Actions 标签页即可看到运行记录。需要推送到私有镜像仓库或云服务器时，到仓库 Settings → Secrets and variables → Actions 配置密钥：

# 无需安装客户端，仓库内操作即可
mkdir -p .github/workflows
# 新建 ci.yml 后 push，GitHub 自动识别
git add .github/workflows/ci.yml
git commit -m "ci: add github actions pipeline"
git push origin main
# 查看运行结果
gh run list --workflow=ci.yml
gh run view --log   # 实时看日志

四、实战示例 1：Node.js 项目完整 CI

下面这个 workflow 覆盖了真实项目的高频诉求：触发条件、矩阵版本测试、依赖缓存、代码质量、产物上传：

name: ci
on:
  push:
    branches: [main]
  pull_request:

jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        node-version: [18, 20, 22]
    steps:
      - uses: actions/checkout@v4
      - name: Setup Node.js ${{ matrix.node-version }}
        uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node-version }}
          cache: 'npm'
      - run: npm ci
      - run: npm run lint
      - run: npm test -- --coverage
      - name: Upload coverage
        if: matrix.node-version == 20
        uses: actions/upload-artifact@v4
        with:
          name: coverage
          path: coverage/

关键点解读：strategy.matrix 让同一套步骤在 3 个 Node 版本上各跑一份，自动并行；cache: 'npm' 让 setup-node 自动维护 ~/.npm 缓存，第二次起依赖安装秒级完成；if: matrix.node-version == 20 表示只有 LTS 版本那一份需要上传覆盖率报告，避免重复。

五、实战示例 2：构建镜像并部署

CI 通过后进入交付环节。下面示例用 Docker Buildx 构建多架构镜像、推送到 GHCR，并通过 SSH 部署到目标服务器。这是自托管应用最常见的发布链路：

name: deploy
on:
  push:
    tags: ['v*']

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: docker/setup-buildx-action@v3
      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - uses: docker/build-push-action@v6
        with:
          context: .
          push: true
          tags: ghcr.io/${{ github.repository }}:${{ github.ref_name }}
          cache-from: type=gha
          cache-to: type=gha,mode=max

  deploy:
    needs: build
    runs-on: ubuntu-latest
    environment: production          # 可配手动审批与环境级 secrets
    steps:
      - name: SSH 部署
        uses: appleboy/ssh-action@v1.0.3
        with:
          host: ${{ secrets.DEPLOY_HOST }}
          username: deploy
          key: ${{ secrets.DEPLOY_SSH_KEY }}
          script: |
            cd /opt/myapp
            docker compose pull
            docker compose up -d
            docker image prune -f

两个容易忽略的点：① environment: production 把部署划入"生产环境"保护圈，可以配置保护规则（需要谁审批）和独立的 secrets 作用域；② cache-from/cache-to: type=gha 把 Docker 构建层缓存挂到 GitHub 的缓存服务，构建镜像时利用缓存层，第二次构建能快一个数量级。

六、自托管 Runner：访问内网与省钱

托管 Runner 跑在公网，部署到内网服务器或访问内网数据库时会受阻。这时注册一台自托管 Runner：

# 在自己的服务器上，按仓库 Settings → Actions → Runners 的指引执行
# 下载 Runner（以 linux x64 为例，版本号以官网为准）
mkdir actions-runner && cd actions-runner
curl -o actions-runner.tar.gz -L https://github.com/actions/runner/releases/latest/download/actions-runner-linux-x64.tar.gz
tar xzf actions-runner.tar.gz
./config.sh --url https://github.com/your-org/your-repo --token <TOKEN>
./run.sh
# 生产建议用 svc.sh 注册成系统服务
sudo ./svc.sh install
sudo ./svc.sh start

之后在 workflow 里用 runs-on: self-hosted（或带标签 runs-on: [self-hosted, linux, x64]）即可让任务落到自己的机器上，既解决内网访问，又节省 Actions 计费分钟数。安全警告：自托管 Runner 如果放在公开仓库，任何 fork 提交的 PR 都可能在你机器上执行代码，公开仓库严禁用自托管 Runner。

我省过的一笔冤枉钱

早期项目用 macos-latest 跑 iOS 构建，一个月烧了 300 多美元——macOS Runner 按 10 倍计费。后来我迁到自托管 Runner（一台 M2 Mac mini 放家里），成本降到几十块电费，还不用排队。如果你的 CI 任务重、跑固定平台，自托管 Runner 长期来看绝对划算。

七、最佳实践

  • 善用缓存：npm/pip/Maven/Go 都有官方 setup Action 内置缓存，Docker 层用 type=gha，构建时间立省一半。
  • 版本钉死：第三方 Action 一律用 commit SHA 或固定大版本（@v4），别用 @main，上游恶意提交会直接污染你的流水线。
  • Secrets 分级：生产凭证放到 environment: production 并配审批，不要和 PR 构建共用一把钥匙。
  • 超时与并发：每个 Job 设 timeout-minutes: 15，同一分支设 concurrency 取消旧运行，防止堆积烧钱。
  • 合并复用逻辑：跨仓库复用时抽 composite action 或 reusable workflow（workflow_call），别复制粘贴。

八、常见问题 FAQ

Q1：Job 之间怎么传递数据？

两个 Job 跑在不同机器，不能直接共享文件。用 actions/upload-artifact@v4 上传产物，下游 Job 用 download-artifact 拉取；Job 间需要传一小段元数据时用 GITHUB_OUTPUT 写 step 输出，再用 needs..outputs 读取。注意 artifact 有存储和流量成本，别拿来传大文件——大文件推镜像仓库即可。

Q2：PR 触发的流水线，fork 仓库能跑吗？安全吗？

来自 fork 的 PR 会触发 workflow，但默认拿不到 secrets，且只读 GITHUB_TOKEN，这是 GitHub 的安全设计。公开仓库不要给 fork 自动写权限，需要敏感操作的检查（如部署、扫码扫描私钥）应标为 "非必须检查" 并由维护者手动触发。

Q3：免费额度够用吗？为什么月初很快就跑超了？

免费版公开仓库无限分钟，私有仓库按账户额度（个人版 2000 分钟/月）。超支通常源于：Windows/macOS Runner 按 2 倍/10 倍计费；矩阵测试把成本乘了 N 倍；没用缓存导致每次跑满。优化顺序：换 Linux Runner、开缓存、拆矩阵、并发取消旧任务。真不够再考虑按量付费或迁自托管 Runner。

九、总结

GitHub Actions 的核心心智模型就是"事件触发 → 多 Job 并行 → Step 编排 → 产物传递"。它足够简单，半小时能跑通一条流水线；又足够强大，矩阵、缓存、自托管 Runner、环境审批、可复用 workflow 足以支撑大型团队。如果你项目就在 GitHub 上，没有强烈的私有化诉求，它通常是 CI/CD 的第一选择。
