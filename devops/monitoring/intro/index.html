监控体系落地：黑盒白盒分工、分层清单与告警阈值

🏷️ 监控告警

大多数团队的监控是「事后补」出来的：出一次故障加一条规则，两年后攒了三百条告警，值班群每天几百条消息，真出事的时候反而没人看。这篇不重复讲可观测性三大支柱的理论（那部分见站内监控与可观测性专题的总览篇），只解决一个工程问题：从零开始，按什么顺序建设、用什么手段覆盖、把阈值定在哪，才能让监控在用户投诉之前几分钟就叫醒你。

监控要回答的三个层次的问题

把监控当成一个「问题树」，比按工具划分清晰得多。任何一次故障排查，本质上都是依次回答三个问题：服务还活着吗、服务健康吗、为什么不健康。这三个问题用的技术手段完全不同，缺了哪一层就有对应的固定盲区。

flowchart TB subgraph L1["第一层：还活着吗（可用性）"] A1["外部拨测：HTTP / TCP / DNS"] A2["端口与进程存活"] A3["合成监控：模拟登录下单全流程"] end subgraph L2["第二层：健康吗（服务质量）"] B1["黄金指标：吞吐 / 延迟分位 / 错误率 / 饱和度"] B2["资源与中间件水位"] B3["业务指标：订单量 / 支付成功率"] end subgraph L3["第三层：为什么不健康（根因）"] C1["分布式链路：慢在哪一跳"] C2["日志与异常堆栈：错在哪一行"] C3["Profiling：CPU / 内存 / 锁竞争"] end L1 -->|"确认故障存在与影响面"| L2 L2 -->|"锁定异常服务与时间窗"| L3

关键点在于这三层是「判定 → 缩小范围 → 定位」的接力，不是可替换的三种方案。很多团队一上来就建链路追踪，结果第一层缺失：入口负载均衡的证书过期了，所有链路数据都完好，因为请求根本没进来。

层次 要回答的问题 主要手段 能确认的结论 这一层回答不了的
第一层 用户现在能不能用 黑盒探活、多地拨测、合成监控 可用 / 不可用、影响哪些地区与入口 哪个服务坏了、坏在什么地方
第二层 坏到什么程度、从什么时候开始 指标监控（时序库 + 告警规则） 受影响接口、错误率与延迟变化、起始时刻 具体是哪一次调用、哪一行代码
第三层 为什么坏 链路追踪、集中日志、火焰图 慢在哪一跳、抛了什么异常、卡在哪个锁 影响面有多大（样本被采样过，不能做统计口径）
⚠️
别用链路数据算成功率

链路追踪几乎一定开了采样（常见 1% 到 10%），它的绝对量没有统计意义。「Jaeger 里看着只有三个错误请求」不代表只影响了三个用户。统计口径必须来自未采样的指标（Counter），链路只用来看单条请求的结构。

黑盒与白盒：只有黑盒能回答「用户是不是真的能用」

白盒监控是从系统内部把状态暴露出来：应用埋点、exporter 读 /proc、数据库的 SHOW STATUS。它信息量大，能解释原因。但它有个致命前提——被监控对象和采集链路都必须正常工作。一旦入口层配错、机房出口断网、DNS 解析到了错误地址，内部所有指标依然绿油油，而用户 100% 失败。

黑盒监控从系统外部按真实用户路径发请求，不依赖任何内部埋点。它唯一能回答、也是白盒永远回答不了的问题是：站在用户位置，这个服务现在可用吗。代价是它只知道坏了，说不出为什么坏。

维度 黑盒监控 白盒监控
数据来源 外部发起的真实请求结果 进程内部埋点与系统计数器
探测位置 必须在用户侧网络（公网节点、多地、移动网络） 与被监控进程同机或同集群
独有的发现能力 证书过期、DNS 劫持、入口 LB 配错、机房出口故障、CDN 回源异常、整体不可达 慢查询、GC 停顿、连接池耗尽、队列堆积、线程阻塞、缓存命中率下降
盲区 不知道根因；探测覆盖不到的接口完全不可见；低频探测会漏掉短故障 进程死了或采集断了就什么都看不到；看不到用户到入口这一段网络
典型误报来源 探测节点自身网络抖动（必须多点投票）、目标做了 UA 或频率风控 指标口径错（统计了不该算的请求）、单机异常被当成整体异常
故障时的可信度 最高，通常用它决定是否宣布故障、是否启动应急 中，用它决定往哪个方向查

黑盒探活最常见的错误是只看 HTTP 状态码。现在的服务出问题时很少直接 500，更常见的是降级返回 200 加一个业务错误码，或者返回一个静态兜底页。探测必须校验响应体内容，否则这类「假活」永远发现不了。下面这份配置把 blackbox exporter 和 Prometheus 侧的 relabel 连在一起，可以直接抄走：

# ---------- blackbox.yml：探测器自身的模块定义 ----------
modules:
  http_login_probe:
    prober: http
    timeout: 5s                    # 必须小于 Prometheus 的 scrape_timeout，否则探测被外层掐断
    http:
      method: POST
      valid_status_codes: [200]    # 默认接受所有 2xx，这里收紧到只认 200
      valid_http_versions: ["HTTP/1.1", "HTTP/2.0"]
      fail_if_body_not_matches_regexp:
        - '"code"\s*:\s*0'         # 关键：只看状态码会漏掉「200 + 业务错误码」的降级页
      fail_if_body_matches_regexp:
        - '系统繁忙|服务降级'        # 兜底页特征串，命中即判失败
      headers:
        Content-Type: application/json
        User-Agent: blackbox-probe/1.0   # 给风控加白名单用，别用默认 UA
      body: '{"user":"probe","from":"blackbox"}'
      preferred_ip_protocol: ip4   # 不指定时 IPv6 优先，内网没配 AAAA 会先超时再回退，白等 5 秒
      no_follow_redirects: false
      tls_config:
        insecure_skip_verify: false  # 保持校验，证书过期本身就该被这条探测发现

# ---------- prometheus.yml：抓取 exporter，目标通过 relabel 传入 ----------
scrape_configs:
  - job_name: blackbox_http
    metrics_path: /probe
    params:
      module: [http_login_probe]
    scrape_interval: 30s
    scrape_timeout: 10s            # 要大于 module 的 timeout，给 exporter 留出返回时间
    static_configs:
      - targets:
          - https://api.example.com/login
          - https://www.example.com/health
    relabel_configs:
      - source_labels: [__address__]
        target_label: __param_target      # 把探测目标塞进 URL 的 target 参数
      - source_labels: [__param_target]
        target_label: instance            # 不做这步，instance 全是 exporter 自己的地址
      - target_label: __address__
        replacement: blackbox-exporter:9115   # 真正被抓取的是 exporter，不是目标站点

配好之后重点关注三个序列：probe_success（0 表示失败）、probe_duration_seconds（探测总耗时，突增说明变慢）、probe_ssl_earliest_cert_expiry（证书到期时间戳，用它减去当前时间做 30 天提前告警，这是投入产出比最高的一条规则之一）。

业务层是最值得投入、也最常被跳过的一层。基础设施告警的信噪比通常很差（CPU 高不一定有故障），而「支付成功率跌了」这一条，几乎不会误报，也几乎不会漏报真实故障。如果只能做一条告警，就做它。

告警阈值怎么定：固定阈值为什么必然翻车

固定阈值的根本问题是业务量有周期性：日周期（白天高、凌晨低）、周周期（工作日与周末不同）、活动周期（大促期间整体抬升一个数量级）。给绝对量指标定固定阈值，等价于假设流量是常数。凌晨 QPS 从 200 掉到 100 是正常作息，白天从 3000 掉到 1500 是 P0 故障，同一个「掉一半」，固定阈值无法区分。

定阈值方法 适用指标 会漏报的场景 会误报的场景 实现成本
固定阈值 有物理上限的水位类指标 缓慢劣化但没越线（P99 从 100ms 涨到 400ms，阈值是 500ms） 大促、批处理任务、发布期间的正常尖峰 最低
比率阈值 错误率、成功率、命中率 总量整体下跌但比率不变（入口挂了，请求进不来，错误率反而是 0） 低流量时段分母太小，1 个失败等于 50% 错误率 低，但必须加分母门槛
同比（对比昨日同时刻） 订单量、QPS 等绝对量 昨天也在故障，基线本身是坏的；大促首日与昨日不可比 节假日、活动开始与结束的第一天 低，一个 offset 就够
环比（对比 1 小时前） 突变型故障 缓慢劣化（每小时降 5%，环比永远不越线） 流量自然的早晚高峰爬升段 低
分位数动态基线 有稳定周期的核心业务指标 周期本身发生了永久性变化，基线需要重新学习 历史窗口里混入了故障数据，基线被污染 高，要预聚合 + 定期重算，还要人工剔除污染窗口

实践上不要一上来就追求动态基线。先把绝对量指标改写成比率、给比率补上分母门槛、给所有规则加持续时长，这三步能消掉 80% 的误报，成本却极低。下面三条规则分别演示三种写法：

groups:
  - name: order-service
    interval: 30s                  # 规则计算周期，默认继承全局 evaluation_interval（通常 1m）
    rules:
      # 规则 1：比率型指标可以用固定阈值，分母把流量的日周期抵消了
      - alert: OrderErrorRateHigh
        expr: |
          sum(rate(http_requests_total{job="order",code=~"5.."}[5m]))
            /
          sum(rate(http_requests_total{job="order"}[5m])) > 0.02
          and
          sum(rate(http_requests_total{job="order"}[5m])) > 1
          # 第二个条件是分母门槛：每秒不足 1 个请求时不判定，避免半夜 1 个失败刷出 100% 错误率
        for: 3m                     # 持续 3 分钟，滤掉发布瞬间的抖动
        labels:
          severity: P1
        annotations:
          summary: 订单服务 5xx 占比超过 2%
          runbook: https://wiki.example.com/runbook/order-5xx

      # 规则 2：绝对量指标必须同比。白天 3000 QPS 正常，凌晨 3000 QPS 是刷单
      - alert: OrderVolumeAbnormalDrop
        expr: |
          sum(rate(order_created_total[10m]))
            <
          sum(rate(order_created_total[10m] offset 1d)) * 0.5
        for: 10m                    # 业务量指标要给足持续时长，10 分钟以下噪声太大
        labels:
          severity: P0

      # 规则 3：趋势预测型，比「磁盘 85%」有用得多：它给的是还剩多少时间
      - alert: DiskWillFillIn4Hours
        expr: |
          predict_linear(node_filesystem_avail_bytes{fstype!~"tmpfs|overlay"}[6h], 4*3600) < 0
        for: 30m                    # 要求趋势稳定 30 分钟，避免一次大文件写入触发
        labels:
          severity: P2
        annotations:
          summary: 磁盘按当前写入速度将在 4 小时内写满

告警分级、收敛与 on-call

分级的判定标准是影响面和时效性，不是技术上的严重程度。「主库宕机」听起来很严重，但如果切换已经自动完成、用户无感，它就不是 P0；「支付成功率跌 5 个百分点」听起来温和，却是不折不扣的 P0。

级别 判定标准 通知渠道 响应时限 规则数量与静默权限
P0 用户已受损且范围在扩大，无自动兜底 电话 + 短信 + IM，未确认 5 分钟后升级到二线 5 分钟内响应，随时叫醒 控制在 10 条以内；静默需二线批准，最长 1 小时
P1 局部受损或有冗余兜底，短期内可能演变为 P0 IM 机器人 @值班人 工作时间 15 分钟，非工作时间 30 分钟 几十条；值班人可自行静默，最长 4 小时
P2 趋势性隐患，有明确的剩余时间窗口 自动建工单，日报汇总 下一个工作日处理 不限；可静默到指定日期
不该存在的级别 「有人看一下」「偶发」「先观察」类告警 无（应删除或降为看板指标） 无 这类告警是告警疲劳的主要来源，必须定期清理

光有分级不够，还得做收敛：一台机器宕机会同时触发它上面所有服务的告警；一个下游故障会让所有上游同时报错。收敛靠三个机制——分组（group）、抑制（inhibit）、静默（silence）。下面这份 Alertmanager 配置演示了这三者，注释里标注了每个参数改错的后果：

route:
  receiver: im-default
  group_by: [alertname, cluster, service]
  # 千万别把 instance 加进 group_by：100 台机器同一个故障会发 100 条独立通知
  group_wait: 30s        # 首条等 30s，把同一故障的兄弟告警攒进一条消息
  group_interval: 5m     # 同组出现新成员时，最快 5 分钟后再发一次
  repeat_interval: 4h    # 未恢复的告警多久重复提醒；设 1h 会被嫌烦，设 24h 会被遗忘
  routes:
    - matchers: [ 'severity="P0"' ]
      receiver: phone-oncall
      group_wait: 10s        # P0 单独压缩等待时间，直接影响 MTTD
      repeat_interval: 30m
      continue: true         # 关键：不写它，匹配即终止，P0 就只有接电话的人知道
    - matchers: [ 'severity="P0"' ]
      receiver: im-default
    - matchers: [ 'severity="P2"' ]
      receiver: ticket
      group_wait: 5m

inhibit_rules:
  # 机器整体不可达时，压掉它上面所有进程级告警，否则一台机器挂了刷 20 条
  - source_matchers: [ 'alertname="InstanceDown"' ]
    target_matchers: [ 'severity=~"P1|P2"' ]
    equal: [instance]        # equal 里的标签必须两边都有，写错会变成「全局压制」
  # 集群级故障压掉单实例故障
  - source_matchers: [ 'alertname="ClusterUnavailable"' ]
    target_matchers: [ 'alertname="InstanceDown"' ]
    equal: [cluster]

on-call 制度上有几条经验：值班窗口按周轮换、每次交接必须有书面的「未闭环事项」清单；每条 P0 和 P1 告警都要有 runbook 链接（哪怕只写三行「先看什么、再看什么、怎么回滚」）；每周复盘一次告警统计，对触发次数最多但从未导致任何操作的规则直接删掉或降级——这类规则每留一条，都在削弱其他告警的可信度。

一次故障的完整时间线：MTTD 与 MTTR 各被什么拖长

把「从故障发生到恢复」拆成两段：MTTD 是从发生到被发现，MTTR 是从发现到恢复（有些团队把 MTTR 定义为从发生到恢复，口径要在团队内统一）。下面这条时间线来自一个真实场景——发布时连接池上限配小了一位数：

sequenceDiagram autonumber participant U as 用户 participant S as 订单服务 participant P as 采集与时序库 participant A as 告警引擎 participant O as 值班工程师 S->>S: 10:00:00 新版本上线，连接池上限被写成 5 U->>S: 10:00:20 下单请求开始排队超时 P->>S: 10:00:45 下一个采集周期才把错误率拉走 Note over P,A: 采集间隔 30s，这里平均贡献 15s 延迟 A->>A: 10:01:00 规则评估命中，进入 Pending 计时 A->>A: 10:04:00 满足 for 3m，转为 Firing Note over A: for 通常是 MTTD 里最大的一块 A->>O: 10:04:30 group_wait 到期，电话送达 O->>O: 10:06:00 接电话、开电脑、打开看板 O->>P: 10:09:00 看板显示全实例错误，排除单机问题 O->>S: 10:11:00 从发布记录定位到刚上线的版本 O->>S: 10:14:00 执行回滚 S-->>U: 10:16:00 错误率回落，恢复 Note over U,O: MTTD 约 4.5 分钟，MTTR 约 11.5 分钟
阶段 典型耗时 被什么拖长 怎么压缩
采集延迟（MTTD） 半个采集周期，15 到 30 秒 scrape_interval 全局设成 60s；exporter 自身有缓存 核心链路的指标单独设 15s 抓取，其余保持 60s 控成本
规则评估（MTTD） 一个 evaluation_interval 规则太多导致评估变慢甚至超时 重表达式改成 recording rule 预聚合；给核心组单独设 interval
持续时长 for（MTTD） 1 到 10 分钟，通常是最大一块 为了降误报把 for 一律写成 5m 或 10m P0 规则的 for 压到 1 到 2 分钟，用分母门槛和多条件替代长时间等待
通知聚合（MTTD） group_wait，默认 30s 为了合并消息把 group_wait 设成几分钟 P0 路由单独设 10s，低优先级路由才用长等待
人到位（MTTR） 1 到 5 分钟 半夜叫不醒、通知渠道被静音、值班表过期 电话通道 + 未确认自动升级；每月演练一次叫醒流程
定位（MTTR） 3 到 30 分钟，方差最大 告警不带上下文、没有 runbook、看板要现场拼、发布记录和监控不在一起 告警正文带 runbook 与直达看板链接；把发布事件打成标注叠到看板时间轴上
止损（MTTR） 1 到 20 分钟 没有一键回滚、开关要改配置发版、需要多方审批 回滚与降级开关做成一键操作并定期演练；先止损再查根因

一个反直觉但很重要的结论：大多数团队在定位阶段花的时间远大于发现阶段，但优化精力却几乎都投在「加告警」上。把告警正文里塞进 runbook 链接和一个带好时间范围的看板地址，对 MTTR 的改善通常比再加二十条规则明显得多。

监控系统自身的监控：死人开关

这是最容易被整体忽略的一环：监控静默失效时，你收到的信号和「一切正常」完全一样。Prometheus 磁盘满了停止写入、抓取配置被误删、Alertmanager 的 webhook 地址过期、机器人 token 失效——这些故障的表现都是「告警变少了」，而告警变少通常被当成好消息。

唯一可靠的解法是死人开关（dead man's switch）：写一条永远为真的告警，让它一直处于 Firing，路由到一个外部心跳服务，并要求该服务每分钟必须收到一次推送。链路上任何一环断了，外部服务会反向通知你。

# ---------- Prometheus：一条永远触发的规则 ----------
groups:
  - name: watchdog
    rules:
      - alert: Watchdog
        expr: vector(1)            # 恒为真；不要写成 up == 1，那会随目标消失而消失
        labels:
          severity: none           # 别给它 P0/P1，避免被分级路由或抑制规则误伤
        annotations:
          summary: 本告警设计上永远处于 firing，用于验证整条告警链路是通的

# ---------- Alertmanager：路由到外部心跳服务 ----------
route:
  routes:
    - matchers: [ 'alertname="Watchdog"' ]
      receiver: heartbeat
      group_wait: 0s
      group_interval: 1m
      repeat_interval: 1m          # 必须每分钟推一次，外部服务据此判断超时
      continue: false
receivers:
  - name: heartbeat
    webhook_configs:
      # 外部心跳服务（自建接口或托管的 cron 监控服务均可），
      # 关键是它必须部署在被监控系统之外，且不依赖同一套网络与账号体系
      - url: https://heartbeat.example.net/ping/2f1c-watchdog
        send_resolved: false

除了心跳，监控组件自身的这几组信号也必须采集，括号里是失效时你会看到的现象：

  • 心跳链路：外部服务是否按期收到 Watchdog 推送（失效时告警全线静默，看起来风平浪静）。
  • 抓取健康度：健康目标数量、抓取耗时、抓取超时计数、样本被丢弃计数（失效时部分服务指标凭空消失，对应告警永不触发）。
  • 规则计算：规则组评估耗时、跳过次数、评估失败计数（失效时评估耗时超过间隔，告警延迟数分钟甚至数小时）。
  • 通知发送：通知失败计数、按 receiver 维度的失败率（失效时规则在 Firing，但消息一条没发出去）。
  • 存储：磁盘剩余量与保留期、写入阻塞、序列数量增长即基数爆炸（失效时写入停止或查询超时，看板一片空白）。
  • 通道隔离：告警通道是否依赖被监控的同一套网络、DNS、对象存储（机房整体故障时告警发不出去，与没有监控等价）。

落地顺序：按性价比排，不是按技术栈排

从零开始建设时，顺序比工具选型重要得多。下面这张表按「每单位投入能覆盖的故障比例」排序，每一档都能独立产生价值，不必等下一档完成。

顺序 做什么 投入 能独立覆盖的故障类型 为什么排这个位置
1 核心入口的黑盒探活 + 证书到期提醒 + 一个 P0 电话通道 1 人天 整体不可用、证书过期、DNS 与入口配错 不依赖任何应用改造，当天就能生效，覆盖影响面最大的故障
2 指标基础设施 + 主机与中间件 exporter + 磁盘趋势预测 2 到 3 人天 资源耗尽类故障，以及故障后的水位比对 标准化程度最高，抄现成的规则与看板即可
3 应用黄金指标埋点（QPS / 延迟分位 / 错误率），按服务出概览看板 每服务 0.5 人天 接口级异常、慢接口、依赖故障 需要改代码，但它是后续所有告警和 SLO 的数据基础
4 告警分级 + 分组抑制 + 死人开关 + runbook 模板 2 人天 不新增覆盖，但决定前三档是否真的有人响应 规则到几十条时不做收敛，告警疲劳会让前面的投入全部作废
5 结构化日志 + 集中检索 + 日志里注入 trace_id 3 到 5 人天 不新增发现能力，大幅压缩定位时间 先有 trace_id 约定，后面接链路追踪才不用返工
6 业务指标与同比基线告警 2 人天 所有「技术指标正常但业务已经受损」的故障 信噪比最高的一类告警，但依赖前面已经稳定的采集体系
7 分布式链路追踪（含采样策略与上下文传播） 1 到 2 周 跨服务调用的根因定位 改造面最大、见效最慢，放最后；具体做法见站内 OpenTelemetry 一篇
✅
用一句话检验体系是否合格

随机挑一个凌晨发生的真实故障，问三个问题：告警是在用户投诉之前还是之后到的？值班人看到告警后，不问任何人能不能判断影响面？告警正文里有没有告诉他第一步该做什么？三个都是「是」，体系就算立住了；只要有一个「否」，先补这一项，别急着加新规则。

最容易踩的坑

❌
避坑清单
  • 黑盒探测节点部署在被监控机房内网：机房出口断网时探测依然全绿，这个探测等于没有。探测必须从用户侧网络发起，并且至少三个点做多数投票。
  • 探测只校验 HTTP 状态码：服务降级后返回 200 加业务错误码，或者返回静态兜底页，探测照样成功。必须校验响应体关键字段。
  • 绝对量指标用固定阈值：「订单量低于 500 就告警」在凌晨必然误报，在大促期间必然漏报。绝对量一律走同比或动态基线。
  • 比率型告警不加分母门槛：凌晨只有 2 个请求，1 个失败就是 50% 错误率，这类误报会在几周内摧毁团队对告警的信任。
  • 内存告警用「已使用」而不是 available：Linux 会把空闲内存拿去做 page cache，按已使用算出来的水位长期在 90% 以上，规则上线第一天就得静默。
  • 磁盘只监空间不监 inode：大量小文件（日志碎片、临时文件、session 文件）会先耗尽 inode，此时 df -h 显示还有一半空间，但写文件已经报 no space left。df -i 要一起看。
  • 用平均延迟代替分位数：平均值会被大量快请求稀释，P99 从 200ms 涨到 3s 时平均值可能只从 30ms 涨到 45ms。SLO 与告警都必须用分位数。
  • 把 4xx 算进错误率：客户端参数错误、未登录、风控拒绝都是 4xx，它们随客户端版本发布而波动，混在一起会让服务端错误被淹没。4xx 与 5xx 必须分开统计并分别定阈值。
  • group_by 里带上 instance：同一个故障会按实例拆成几十上百条独立通知，值班人在消息洪流里根本看不出这是一个故障。
  • P0 路由忘写 continue: true：Alertmanager 的路由是匹配即停止，结果 P0 只进了电话通道，IM 群里没有任何记录，其他人完全不知情。
  • 抑制规则的 equal 标签写错或留空：本意是「同一台机器上的告警互相压制」，写成空列表就变成全局压制，一条机器宕机告警能把整个集群的告警全部吞掉。
  • 没有死人开关：Prometheus 磁盘满、抓取配置被误删、机器人 token 过期，表现都是「今天告警好少」，而这通常被当成系统稳定。
  • 告警只报现象不给动作：「CPU 使用率 92%」这条消息无法推动任何操作。告警正文至少要有影响面、runbook 链接、以及一个带好时间范围的看板链接。
  • 只在发布时关告警、发布后忘记恢复静默：静默一定要设过期时间，永久静默的规则等于删除，但账面上还显示「我们有 300 条告警」。
