监控入门：别等用户投诉了才知道挂了

🏷️ 监控告警

系统挂了还是用户打电话来才知道，服务器 CPU 跑满了也没发现。监控就是提前告诉你：快出问题了，赶紧处理。这篇讲监控要监控什么，怎么搭。

flowchart TD A[监控体系] --> B[指标监控] A --> C[日志监控] A --> D[链路追踪] B --> B1[CPU/内存/磁盘] C --> C1[错误日志/访问日志] D --> D1[请求耗时/调用链]

系统挂了不知道

⚠️
你遇到的问题

半夜收到用户投诉，说网站打不开，爬起来看才知道服务器 CPU 跑满了。

怎么解决？搭一套监控，CPU、内存、磁盘使用率超了就发告警到微信。

# Prometheus + Grafana
# 监控 CPU、内存、磁盘、网络
# 阈值告警：CPU > 80% 发告警

线上报错了，不知道哪错了

⚠️
你遇到的问题

用户说页面报错了，你翻日志翻半天找不到。

怎么解决？把日志收集起来，按 trace_id 搜，一下就能找到完整调用链。

# ELK / Loki
# 日志加 trace_id
# 报错了直接按 trace_id 搜

监控三大块

类型 监控什么 工具 告警时机
指标监控 CPU/内存/磁盘/QPS/RT Prometheus + Grafana 超阈值持续 5 分钟
日志监控 错误日志、异常堆栈 ELK / Loki 出现 ERROR 级别日志
链路追踪 请求耗时、服务调用链 Jaeger / SkyWalking 慢请求 > 1s

常用监控指标

指标 正常范围 告警阈值 为什么重要
CPU 使用率 30-60% > 80% 高了说明要扩容
内存使用率 40-70% > 85% 高了会 OOM
磁盘使用率 30-50% > 80% 满了服务直接挂
接口 RT < 200ms > 500ms 慢了用户体验差

新手最容易踩的坑

❌
避坑指南
  • 告警不要太多，不然大家都麻痹了，真正重要的告警才推微信
  • 告警要分级，P0 电话通知，P1 企业微信，P2 群消息就行
  • 监控大盘不要搞太复杂，常用的几个指标放首页就行
  • 日志级别要规范，ERROR 一定要真的是错误，别啥都打 ERROR
