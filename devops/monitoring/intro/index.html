可观测性三支柱

🏷️ 监控,可观测性,Prometheus,Grafana

从"监控"到"可观测性"：为什么这是个值得单独讨论的概念

很多人把监控和可观测性（Observability）混为一谈，但这两个词背后是完全不同的工程哲学。传统监控（Monitoring）是你预先想好了要问什么问题，然后埋点去收集指标——CPU 超过 80% 就告警，QPS 掉到阈值以下就告警。它假设你知道系统会以哪些方式坏掉，于是围绕这些已知失败模式建仪表盘。这套方法在单体、垂直扩容的时代非常有效。

但进入微服务、Serverless、云原生时代后，故障模式组合爆炸：一个请求可能横跨网关、鉴权、订单、库存、消息队列、支付，任何一处的超时、重试、连接池耗尽都会表现为"用户说页面慢"，而你根本无法事先枚举所有可能的故障路径。可观测性的定义是：仅通过系统的外部输出，就能理解系统内部状态的能力，并且你能回答那些你当初没有预设过的问题。它的本质是给你一套足够高保真的"系统黑匣子数据"，让你在故障现场临时发问、自由探索，而不是只能盯着早已做好的几张图。

Google SRE 书籍把监控的目标总结为四个问题：它是否正常运行（Alerts）、为什么不正常（Root-cause analysis）、正在花多少钱（Planning）、有没有被人攻击（Security）。可观测性体系就是围绕这四个目标，用三类数据协同回答。

三大支柱：Metrics、Logging、Tracing 各解决什么

业内俗称"可观测性三支柱"，但更准确的理解是三种粒度和成本不同的数据：

支柱数据形态成本回答什么问题
Metrics数值采样最低，存一年出什么事了（告警）
Logging文本事件流高，存 14~90 天当时发生了什么
Tracing调用链路中，采样 1~10%问题出在谁身上

三者是互补而非替代的：Metrics 告诉你"出事了"（告警触发），Tracing 告诉你"出事在哪一条链路上"，Logging 告诉你"这条链路上当时具体报了什么错"。成熟团队的标准排障路径就是这条三步曲。

整体架构：数据如何从服务流到你的眼睛

一个现代可观测性平台的数据面，从左到右分为采集、传输、存储、计算、展示、告警六层。下图是一个典型的自建栈（Prometheus + ELK + OpenTelemetry + Grafana）：

这张图里有几个值得记住的工程决策：

  • 采集与存储解耦：业务进程只负责暴露/发送数据，Collector 负责打标签、采样、路由，这样换存储后端不用改代码。
  • 三类数据存三个库：时序数据进 TSDB、日志进 ES、链路进 Trace DB。强行用一个大而全的数据库扛三类负载，通常两边都做不好。
  • 告警只有一条源：告警规则统一在 Prometheus/AlertManager（或 OpenTelemetry Collector），不要让 Grafana、Kibana 各自发告警，否则值班会被重复告警淹没。

最小可用落地：先用两条线跑起来

不要一上来就追求三支柱全齐。务实的路线是：第一周先上 Metrics + Logging，能告警、能查错；第二季度再补 Tracing。下面是 Go 服务同时暴露 Prometheus 指标和结构化日志的最小代码骨架：

// 一个 HTTP 服务同时产出 Metrics 与结构化日志的最小骨架
package main

import (
    "log/slog"
    "net/http"
    "github.com/prometheus/client_golang/prometheus"
    "github.com/prometheus/client_golang/prometheus/promhttp"
)

var (
    // Counter：只增不减，记录请求总数（带路由维度）
    httpReqs = prometheus.NewCounterVec(
        prometheus.CounterOpts{Name: "http_requests_total", Help: "HTTP 总请求数"},
        []string{"route", "status"},
    )
    // Histogram：记录请求耗时分布，是算 P99 的基础
    httpDur = prometheus.NewHistogramVec(
        prometheus.HistogramOpts{Name: "http_duration_seconds",
            Buckets: prometheus.DefBuckets},
        []string{"route"},
    )
)

func main() {
    prometheus.MustRegister(httpReqs, httpDur)
    // /metrics 是 Prometheus 抓取的标准端点
    http.Handle("/metrics", promhttp.Handler())

    http.HandleFunc("/pay", func(w http.ResponseWriter, r *http.Request) {
        timer := prometheus.NewTimer(httpDur.WithLabelValues("/pay"))
        defer timer.ObserveDuration()
        // 结构化日志：trace_id 贯穿三支柱，排查时用它在 ES 和 Trace 系统里互跳
        slog.Info("pay called", "trace_id", r.Header.Get("X-Trace-Id"),
            "order", r.URL.Query().Get("order_id"))
        w.Write([]byte("ok"))
        httpReqs.WithLabelValues("/pay", "200").Inc()
    })
    _ = http.ListenAndServe(":8080", nil)
}

# 本地快速验证：启动后三个端点各司其职
# 1) 指标：Prometheus 每 15s 抓取一次，长期留存、画大盘
curl -s http://localhost:8080/metrics | grep http_requests_total
# 2) 日志：Filebeat 采集 stdout，进 ES 做全文检索
# 3) 链路：OTel SDK 把 span 发进 Collector，再到 Tempo/Jaeger

最佳实践

  • 从 SLI/SLO 倒推指标，而不是从技术指标正推。先定义"用户视角的服务等级"（如：支付成功率 ≥ 99.9%，P99 延迟 ≤ 500ms），再围绕这两个目标埋点。不要为了埋而埋——每多一个高基数标签都是存储成本。
  • trace_id 必须贯穿三支柱。日志里打印 trace_id、指标里（必要时）附 exemplar、链路系统里存 trace_id，这样在 Grafana 上从一个慢请求的点可以一键跳到完整链路，再跳到相关日志。这是三支柱真正"合体"的关键，而不是三个孤岛。
  • 告警按"用户影响"组织，不按"技术组件"组织。值班收到的第一条告警应该是"支付成功率低于 99.5%"，而不是"某台机器 CPU 95%"。技术指标告警降级为二级告警。
  • 采样策略分级：Metrics 全量（便宜）；Tracing 默认 1%~10% 采样，错误请求强制 100% 采样；Logging 默认 INFO，故障期动态调 DEBUG。
  • 标签（label/tag）克制：不要把 user_id、order_id、URL 路径模板之外的变量值塞进标签，基数爆炸是 Metrics 系统最常见的死因。
我踩过的坑：告警疲劳把真正的故障淹了

新监控体系上线第一个月，团队配了 200 多条阈值告警，每天晚上响 50 次，大家开始习惯性静音。结果有天真正的数据库主从切换告警混在里面，没人看到，业务停了 20 分钟。后来我把告警砍到 30 条以内，全部按 SLO 组织（"支付成功率低于 99.5%"），加 for: 5m 窗口，每月 review 一次没触发过的告警直接删。告警多了等于没有告警。

常见问题 FAQ

Q1：监控和日志不是一回事吗？为什么要分开建两套系统？

不是一回事，它们的读写模式完全不同。Metrics 是"写少读多、聚合读"：15 秒一个点，存一年，查询是 sum by (route)(rate(...))。日志是"写多读少、全文检索"：每秒几万行，查询是 message: "timeout"。用 Elasticsearch 存指标会被聚合查询拖垮，用 Prometheus 存日志则会因为标签爆炸而 OOM。所以业界几乎都是分开存储、在展示层（Grafana）聚合。

Q2：小团队只有三四个服务，有必要上 Tracing 吗？

三四个服务时 Tracing 的 ROI 确实不高，先把 Metrics 和结构化日志做规范（必打 trace_id、error_code、duration）就够用了。判断标准：当一次"接口慢"你需要登录三台机器 grep 日志才能定位时，就该上了。注意 Tracing 的最大成本不是存储，而是代码埋点和 Context 传播——没有统一的 trace 中间件，手写埋点很快就会烂尾。

Q3：三支柱都要自建还是直接用 SaaS（Datadog/New Relic）？

看数据量和合规要求。日均日志 < 100GB、没有出网合规约束的团队，SaaS 的人力成本优势巨大（免运维 Collector/ES/Prometheus）。日均日志 TB 级、或数据不能出内网的金融/政企场景，自建（Prometheus + Loki + ES + Tempo）是必然选择。折中方案：Metrics 自建、日志用对象存储归档 + 热数据上 ES。

Q4：为什么我加了监控反而半夜告警更多了？

典型的"告警疲劳"问题。新体系刚上线时，大家把所有技术指标都配了阈值告警，结果把正常波动（发版、定时任务、缓存冷启动）全报了一遍。解法：① 告警必须带 for: 5m 以上的持续窗口，毛刺不报；② 按 SLO 告警，不按单台机器告警；③ 每月回顾一次告警历史，把连续一个月没触发的告警删掉。

总结

可观测性不是一套软件，而是一种"让系统自己说话"的工程纪律：Metrics 用最小成本告诉你"出什么事了"，Logging 用最大信息量告诉你"当时发生了什么"，Tracing 用因果链路告诉你"问题出在谁身上"。三支柱通过 trace_id 缝合，告警围绕 SLO 组织，仪表盘服务于排障而非炫技。下一篇我们从三支柱里最成熟的 Metrics 组件——Prometheus 开始，深入它的 Pull 模型与内部架构。
