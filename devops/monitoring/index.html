监控告警深度原理：可观测性三大支柱

🏷️ 监控

系统出问题了怎么快速发现？怎么定位？可观测性三大支柱：Metrics、Logging、Tracing，每个解决什么问题？这篇讲透底层原理。

核心原理1：三大支柱：各管什么？

监控不是只有一个面板，三个维度：指标看趋势、日志看细节、链路看路径，三个配合才能快速定位问题。

flowchart TD A[可观测性] --> B[Metrics 指标] A --> C[Logging 日志] A --> D[Tracing 链路] B --> B1[看趋势 率/延迟/错误] C --> C1[看细节 报错信息] D --> D1[看路径 请求走了哪些服务]

三大支柱对比

支柱 回答什么问题 常见工具
Metrics 发生了什么？趋势怎么样？ Prometheus + Grafana
Logging 为什么错了？具体错误？ ELK / Loki
Tracing 请求经过了哪里？哪一步慢？ Jaeger / SkyWalking

核心原理2：Metrics 指标原理

指标是数值，存时序数据库，聚合快，适合看趋势。四种常用指标类型：Counter、Gauge、Histogram、Summary。

flowchart LR A[指标类型] --> B[Counter 计数器 只增] A --> C[Gauge 仪表盘 可增可减] A --> D[Histogram 直方图 分桶] A --> E[Summary 摘要 分位数] B --> B1[请求数 错误数] C --> C1[内存 队列长度] D --> D1[延迟 P99]

['指标类型', '特点', '适用场景']

指标类型 特点 适用场景
Counter 只增不减 请求总数、错误数
Gauge 可增可减的瞬时值 内存、CPU、队列长度
Histogram 分桶统计，算分位数 请求延迟
Summary 客户端算分位数 高基数延迟

核心原理3：Tracing 链路追踪原理

一个请求经过几十个服务，怎么知道哪一步慢了？链路追踪给每个请求一个 TraceID，每个服务加 Span，串起来就是完整链路。

flowchart LR A[用户请求] --> B[网关 Span1] B --> C[订单服务 Span2] C --> D[库存服务 Span3] D --> E[数据库 Span4] B --> F[用户服务 Span5] style E fill:#ff6b6b,color:#fff

['概念', '含义', '例子']

概念 含义 例子
TraceID 整个请求唯一ID abc123
Span 一个服务的一段操作 订单服务调用
SpanContext 跨服务传递上下文 HTTP header 传递
上报 把 Span 上报到收集端 Jaeger / SkyWalking

新手最容易踩的坑

❌
避坑指南
  • 告警不要只看指标，要加维度过滤，不然半夜被垃圾告警吵醒
  • 日志不要打太多，INFO 太多查问题找不到，ERROR 才是重点
  • 链路追踪一定要透传 TraceID，不然跨服务串不起来
  • 监控面板不要搞太多没用的图，核心几个指标就够了
