可观测性三大支柱：成本模型、基数爆炸与告警设计

🏷️ 监控

三大支柱被讲了无数遍，但绝大多数文章停在「指标看趋势、日志看细节、链路看路径」这一层。真正决定你的监控体系能不能活下去的，是三者成本函数的形状完全不同：Metrics 的开销与业务流量近乎无关，Logging 与流量严格线性，Tracing 不采样就必然崩。这一篇讲体系与方法论——数据面怎么分层、基数为什么会乘性爆炸、黄金信号与 RED / USE 的边界在哪、分位数为什么不能求平均、错误预算怎么变成发布闸门。Prometheus 自身怎么运作与运维见站内 devops/monitoring/prometheus/，查询语言的语义陷阱见 devops/monitoring/promql/。

一、三支柱不是三个工具，而是三种成本模型

先算三笔账，后面所有架构决策都是这三笔账的推论。

Metrics 是有界的。它的存储量等于「时间序列条数 × 每条序列的采样点数 × 单点字节数」，和 QPS 没有关系。Prometheus 的 TSDB 用 delta-of-delta 编码时间戳、XOR 编码浮点值，生产环境实测单个样本压缩后平均落在 1.3 到 2 字节。按 10 万条序列、15 秒抓取间隔算，一天是 10 万 × 5760 点 × 2 字节 ≈ 1.1 GB，保留 15 天约 17 GB。业务流量从 1 万 QPS 涨到 10 万 QPS，序列数一条都不会多，存储几乎不变——这是 Metrics 最宝贵的性质，也是它敢保留一年的原因。

Logging 是线性的。一个请求至少一条访问日志，QPS 涨 10 倍存储就涨 10 倍。一条结构化 JSON 访问日志 500 字节到 2 KB，1 万 QPS 按 1 KB 算就是 10 MB/s、约 860 GB/天，进 Elasticsearch 还要再叠上倒排索引与 doc_values 的膨胀（通常 1.1 到 1.5 倍）。所以日志的降本手段只有三种：砍级别、抽样、冷热分层加短保留期。

Tracing 是乘性的。一次请求穿过 20 个服务就产生 20 到 100 个 span，每个 span 带 trace_id、span_id、起止时间和一堆属性。全量采集等价于把调用链当日志写，还要额外承担 ingest 时的索引成本。所以 Tracing 从设计上就假定采样：常见做法是头部采样（Head-based，入口按 1% 概率决定整条链路的命运，成本可预测但会丢掉罕见的慢请求）加尾部采样（Tail-based，Collector 先缓冲整条链路，看到错误或超时再决定保留，能抓到异常但 Collector 要吃内存）。

三支柱的正确协作顺序

Metrics 负责「发现并界定影响面」，Tracing 负责「把范围缩到某一跳」，Logging 负责「给出那一跳失败的具体原因」。倒过来用就是灾难：从日志全文检索开始排查一次全站故障，等于用最贵、最慢的工具做最粗的筛选。

二、数据面全景：五层分工与一次故障里的接力

三个容易被忽略的层间约束：一是采集间隔决定了告警的最小反应时间，抓取间隔 30 秒、for 写 2 分钟，实际最快发现时间是 2.5 分钟往上；二是日志管道必须有缓冲，直连 Elasticsearch 在流量尖峰时会被 bulk 拒绝，日志直接丢，Kafka 那一层不是可选项；三是三支柱要能互相跳转，指标面板上的时间点能跳到对应时段的链路，链路的某个 span 能跳到该实例这一秒的日志，这要求日志里必须带 trace_id，否则三支柱只是三个孤岛。

关键在于每一步都在缩小搜索空间：从全站缩到一个服务，从服务缩到一跳依赖，从一跳缩到具体错误。如果第一步就去日志系统全文搜 error，面对每秒几万条日志，你会在噪音里迷路。

三、基数爆炸：Metrics 体系最致命的一刀

时间序列的身份是「指标名 + 全部标签键值的组合」，任何一个标签多一个取值，就是一条全新的序列，各标签之间是乘的关系：

# 某指标的序列数 ≈ 各标签取值数之积
# http_requests_total{service, instance, method, status, endpoint}
#   service  20 个
#   instance 每服务 50 个
#   method   5 个
#   status   8 个
#   endpoint 40 个
# 序列数 = 20 * 50 * 5 * 8 * 40 = 1,600,000

# 一旦把 user_id 加进标签，假设日活 50 万：
# 序列数 = 1,600,000 * 500,000 → 天文数字，进程秒级 OOM

# Prometheus head 中每条活跃序列的常驻内存经验值约 3 KB
# 160 万序列 ≈ 4.8 GB，仅 head 部分，还没算查询临时开销
python3 -c "print(20*50*5*8*40, '条序列', round(20*50*5*8*40*3/1024/1024, 1), 'GB')"

这里有个流传很广的误解需要纠正：「加个标签而已，只多一列数据」是错的。关系型数据库里加一列是加法，时序库里加一个标签是乘法。而且危害不止于内存：序列数上去后，倒排索引的 posting list 变长，一次 sum by (service) 要遍历的序列成倍增加，查询从 200 毫秒变成 20 秒；Grafana 面板超时，告警规则求值超时，规则求值超时会导致告警漏报——这是最危险的后果，监控系统在你最需要它的时候安静了。

标签候选 取值数增长方式 判决 正确的去处
service / env / region 有界，几个到几十个 放心用 标签
method / status_code 有界，个位数到十几个 放心用 标签
instance / pod 随副本数增长，弹性伸缩下会不断产生新值 谨慎，注意历史序列堆积 标签，但聚合视图里要 without (instance)
endpoint 原始路径 /user/123/order/456 这类路径随 ID 无限增长 禁止直接使用 先归一化成 /user/:id/order/:id 再做标签
user_id / order_id 随业务量线性增长，无上限 禁止 日志字段
request_id / trace_id 每请求唯一，等于无限 绝对禁止 链路系统，日志里作为关联键
错误信息全文 含变量与时间戳，实际无限 禁止 日志 message，指标里只留有限的 reason 枚举

一条实操判据：如果一个维度的取值数会随用户数或请求数增长，它就不是标签。想按这个维度下钻，就去日志或链路，那两套系统的成本模型本来就是为高基数设计的。至于抓取侧怎么用 metric_relabel_configs 强行丢掉已经爆掉的指标，属于 Prometheus 的运维手段，见站内 Prometheus 篇。

四、黄金信号、RED / USE 与分位数

四大黄金信号来自 Google SRE：延迟（Latency，注意成功请求与失败请求的延迟必须分开统计，失败请求往往快速返回，混在一起会把 P99 拉好看）、流量（Traffic）、错误（Errors）、饱和度（Saturation，最接近「还能撑多久」的信号）。RED 和 USE 是这四个信号在不同对象上的落地方法，选错对象就会出现「指标全绿但用户在骂」。

方法 观测对象 三个指标 回答的问题 单独使用时的盲区
RED 请求驱动的对象：HTTP 接口、RPC 方法、消息消费者 Rate 请求速率 / Errors 错误数 / Duration 耗时分布 用户现在的体验好不好 知道慢但不知道为什么慢，定位不到瓶颈资源
USE 资源：CPU、内存、磁盘、网卡、连接池、线程池、队列 Utilization 利用率 / Saturation 饱和度 / Errors 错误 瓶颈在哪种资源上 资源都不满也可能全面超时，比如锁竞争、下游依赖慢
四大黄金信号 面向用户的服务整体 延迟 / 流量 / 错误 / 饱和度 该不该叫人起床 粒度粗，需要 RED 与 USE 向下展开

饱和度是四个信号里最容易做错的一个。很多团队用 CPU 使用率当饱和度，但 CPU 80% 可能完全健康，而 CPU 30% 配上一个已经排满的线程池队列已经等于宕机。真正的饱和度信号是排队长度和等待时间：连接池等待队列、线程池 queue size、Kafka 消费 lag、磁盘 I/O 队列深度。这些指标从 0 变成非 0 就是预警，不需要等到某个百分比。

分位数：平均值在骗你，而 P99 不能求平均

先看平均值为什么不能用。一万个请求里 9900 个耗时 10 毫秒，100 个耗时 3 秒，平均值 = (9900×10 + 100×3000) / 10000 ≈ 39.9 毫秒。面板上一条 40 毫秒的平线，而实际上每一百个用户就有一个在等三秒。请求延迟的分布是长尾的、右偏的，用平均值描述长尾分布本身就是方法错误。

再看一个更隐蔽、也更高频的错误：分位数不可相加，多实例的 P99 不能求平均。假设三台机器，A 的 P99 是 100 毫秒、B 是 100 毫秒、C 是 1000 毫秒，把三个数求平均得到 400 毫秒；但如果 C 只承载了 1% 的流量，整体 P99 可能还在 110 毫秒，如果 C 承载了 90% 流量，整体 P99 会接近 1000 毫秒。同样三个 P99 值，真实答案能差一个数量级——因为分位数丢掉了「各自有多少样本」这个信息，而分位数运算本身不满足线性性质。

错误做法 为什么错 正确做法
用平均耗时衡量用户体验 长尾被海量快请求稀释，故障期间曲线几乎不动 同时看 P50、P90、P99，用 P99 定 SLO
对各实例的 P99 求平均或求和 分位数非线性，忽略各实例样本量权重，误差可达数量级 先把各实例的直方图桶计数按桶边界相加，再在总分布上估算分位数
成功与失败请求的延迟混在一起统计 快速失败会拉低整体延迟，掩盖真实劣化 按状态码维度拆分，只用成功请求的延迟定 SLO
只看 P99 不看 P999 1% 的请求在高 QPS 下是巨大的绝对量，且重试会放大 核心链路补 P999，同时看最大值定位极端个例
客户端算好分位数再上报 客户端预聚合的分位数天然不可跨实例合并 上报直方图桶计数，把分位数估算留到查询时做
直方图桶边界用默认值就不管了 桶边界定错，落在同一个桶里的请求无法区分，分位数误差极大 按实际延迟分布设计桶，SLO 阈值必须正好是一个桶边界

最后一行值得展开：分位数是从桶里线性插值估算出来的，如果你的 SLO 是「300 毫秒内返回」，而桶边界是 0.1、0.5、1、5 秒，那么 300 毫秒落在 0.1 到 0.5 这个桶中间，估算结果只能靠猜。把 0.3 加进桶边界，这个数字才准确。具体的 histogram_quantile 写法和聚合顺序见站内 PromQL 篇。

五、SLI / SLO / 错误预算：把稳定性变成可花的额度

三个概念的层次是：SLI 是可测量的比例（成功请求数 / 总请求数、延迟低于 300 毫秒的请求占比），SLO 是给 SLI 定的目标（30 天窗口内不低于 99.9%），错误预算是 1 - SLO 折算出来的允许失败额度。SLA 是对外带赔偿条款的合同，通常比内部 SLO 松一档，别混用。

SLO 目标 30 天错误预算 换算成请求数（按 1 万 QPS） 达到这一档的现实要求
99% 约 7 小时 12 分 约 2.6 亿次失败额度 单实例加人工介入即可
99.9% 约 43 分钟 约 2600 万次 多副本、自动重启、健康检查
99.95% 约 21 分钟 约 1300 万次 多可用区、自动摘流、5 分钟内自动回滚
99.99% 约 4 分 20 秒 约 260 万次 全链路冗余、无人工介入的自动故障转移
99.999% 约 26 秒 约 26 万次 一次发布事故就会打穿，多数业务不该承诺

这张表的用途是反向劝退：看到 99.99% 意味着一个月只允许 4 分钟不可用，而一次 Kubernetes 滚动更新加上探针配置不当就可能超过这个数，团队就会明白目标定高不是荣誉而是负债。

错误预算真正的价值在于它给出了一个发布闸门：预算有余量时允许激进发布，预算耗尽时冻结功能发布、只允许可靠性相关变更，新周期开始预算重置。这把「还能不能发版」从吵架变成查数字。

stateDiagram-v2 [*] --> Healthy Healthy: 预算充足 发布照常 可做灰度实验 Warn: 预算告急 放慢发布 需二人评审 Empty: 预算耗尽 冻结功能发布 Fix: 可靠性整改 只允许修复类变更 Healthy --> Warn: 快速燃尽率超过阈值 Warn --> Healthy: 故障修复 燃尽率回落 Warn --> Empty: 剩余预算归零 Empty --> Fix: 触发发布闸门 Fix --> Healthy: 新统计周期开始 预算重置 Healthy --> [*]

配套的告警不该是「错误率大于 1%」这种固定阈值，而应该是多窗口多燃尽率（multi-window multi-burn-rate）：燃尽率 = 当前错误率 / 允许错误率。燃尽率 1 表示刚好在周期末花完预算，燃尽率 14.4 表示两天就能花完 30 天的额度。用长短两个窗口同时判断，短窗口保证反应快，长窗口过滤掉瞬时抖动。

# SLO: 30 天窗口内成功率 99.9%，即允许错误率 0.001
# 燃尽率阈值来自 Google SRE Workbook 的推荐组合
groups:
- name: slo-burn-rate
  rules:
  # 快烧：1 小时窗口错误率达到允许值的 14.4 倍，2 天就会烧完预算 → 立即叫人
  # 同时要求 5 分钟短窗口也在烧，避免一个早已恢复的历史尖峰持续触发
  - alert: SLOBurnRateFast
    expr: |
      (
        sum(rate(http_requests_total{job="api",code=~"5.."}[1h]))
        / sum(rate(http_requests_total{job="api"}[1h])) > 14.4 * 0.001
      )
      and
      (
        sum(rate(http_requests_total{job="api",code=~"5.."}[5m]))
        / sum(rate(http_requests_total{job="api"}[5m])) > 14.4 * 0.001
      )
    for: 2m
    labels:
      severity: critical      # 这一档才允许电话呼叫
    annotations:
      summary: "API 错误预算快速燃尽，预计 2 天内耗尽 30 天额度"
  # 慢烧：6 小时窗口达到 6 倍，约 5 天烧完 → 工作时间处理，不叫醒人
  - alert: SLOBurnRateSlow
    expr: |
      (
        sum(rate(http_requests_total{job="api",code=~"5.."}[6h]))
        / sum(rate(http_requests_total{job="api"}[6h])) > 6 * 0.001
      )
      and
      (
        sum(rate(http_requests_total{job="api",code=~"5.."}[30m]))
        / sum(rate(http_requests_total{job="api"}[30m])) > 6 * 0.001
      )
    for: 15m
    labels:
      severity: warning       # 只进 IM 群，不呼叫
    annotations:
      summary: "API 错误预算持续燃尽，需在本周内收敛"

六、告警设计：可行动、基于症状、不许有噪音

告警系统的失效模式不是「漏了一条」，而是值班人员学会了忽略它。一旦某个渠道里 90% 的消息都不需要处理，剩下 10% 的真告警就等于不存在。三条设计原则如下。

必须可行动。收到告警的人要能立刻知道做什么。如果唯一的反应是「先看看」，这条信息属于看板，不属于告警。判断方法：写告警时同步写 runbook，写不出处理步骤的就不要配。

基于症状而非原因。对用户可感知的失败告警——成功率下跌、延迟劣化、队列持续增长、订单量异常归零。原因类指标（某个节点 CPU 高、某个 Pod 重启、缓存命中率下降）应该做成看板供排查时查看。理由很直白：原因有无穷多种，症状只有几种；对原因告警会导致一次故障炸出几十条告警，真正的影响面反而被埋掉。

必须有持续时间约束。抓取抖动、GC 停顿、一次滚动重启都会让瞬时值越线。加上持续 N 分钟的判断能滤掉绝大多数误报，代价是发现时间变长，这个权衡要按 SLO 严格程度来定。

维度 坏告警 好告警
触发条件 CPU 使用率大于 80% 成功率连续 5 分钟低于 99.5%，且燃尽率超阈值
观测层次 对每个副本、每台机器分别告警 对服务整体的用户影响面告警，实例维度留给排查
触发次数 每天数十条，值班群已折叠免打扰 每周个位数，条条都需要人介入
持续时间 无 for，瞬时越线就发 for 至少覆盖 4 个抓取周期，滤掉抖动
分级 全部 critical，全部电话呼叫 critical 呼叫、warning 进 IM、info 只入看板
信息量 标题写「服务异常」，无上下文 带服务名、影响比例、当前值与阈值、runbook 链接、面板直达链接
依赖关系 数据库挂了，上游 20 个服务同时各报一条 配置抑制规则，根因告警存在时压掉派生告警
指标消失 没有配置，Exporter 挂掉后面板一片空白也不报 对目标存活与指标缺失单独告警

最后这条经常被漏掉：所有基于「值大于阈值」的告警，在指标完全没有数据时都不会触发。进程崩溃、Exporter 挂掉、抓取配置写错，都会让表达式返回空集，而空集不满足任何比较条件，于是系统看起来一片安静。必须单独对「目标不可达」和「指标缺失」告警，具体函数见 PromQL 篇的 absent 相关章节。

七、日志：分级标准与结构化

日志失控几乎总是因为级别没有客观标准，人人凭感觉打。给一套可执行的判据：ERROR 表示已经发生了需要人介入的失败（数据不一致、外部依赖彻底不可用、无法自动恢复），它的数量应该少到可以逐条看完，如果 ERROR 每秒上千条，说明级别用错了；WARN 表示降级成功、自动恢复了但值得注意（重试成功、走了兜底逻辑、参数超出预期但已纠正）；INFO 记录状态变更与关键业务事件（服务启动、配置加载、订单状态流转），不要用来记录每次循环；DEBUG 只在排障时临时开启，默认关闭，且必须做好日志量评估。一个反模式是「捕获异常后打 ERROR 然后继续抛出」，同一个错误在调用栈上被打三四遍，既放大存储又干扰统计。

结构化是另一半。文本日志靠正则解析，格式一改解析就断；JSON 日志可以直接按字段过滤聚合。下面这条包含了排障必需的最小字段集，重点是 trace_id——它是日志与链路之间唯一的桥。

{
  "ts": "2026-09-22T14:03:11.472+08:00",
  "level": "ERROR",
  "logger": "order.service.pay",
  "msg": "acquire db connection timeout",

  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "00f067aa0ba902b7",

  "service": "order-service",
  "version": "v2.14.3",
  "env": "prod",
  "instance": "order-service-7d9f8b6c5-xk2lm",

  "user_id": "1000482913",
  "order_id": "SO20260922140310884",

  "err_kind": "DBConnTimeout",
  "duration_ms": 3012,
  "retry": 2,
  "stack": "pkg/db/pool.go:142 -> pkg/order/pay.go:87"
}

几个字段选择的理由：err_kind 是有限枚举，它可以安全地变成指标标签做趋势统计，而 msg 原文含变量不能；user_id 和 order_id 放在日志里正合适，它们正是上一节明令禁止进标签的高基数维度；version 让你在发布后能一眼对比新旧版本的错误分布；时间戳带毫秒和时区，跨机器对齐时间线时这是硬要求。

最容易踩的坑

❌
避坑清单
  • 把 user_id、request_id、trace_id 或未归一化的 URL 放进指标标签。序列数是各标签取值数的乘积，一个高基数标签就能让进程从几百 MB 涨到 OOM，且先炸的是查询与规则求值，表现为告警静默。
  • 用平均耗时衡量用户体验。9900 个 10 毫秒请求加 100 个 3 秒请求，平均值只有 40 毫秒，面板一条平线，而每百个用户就有一个在等三秒。
  • 把多个实例的 P99 求平均或求和当成整体 P99。分位数非线性且丢失了样本量权重，同样三个数值真实答案能差一个数量级，必须先合并直方图桶再估算。
  • 成功请求和失败请求的延迟混在一起统计。快速失败会把 P99 拉得很好看，故障期间延迟曲线反而下降。
  • 直方图桶边界照抄默认值。SLO 阈值如果不是某个桶边界，估算出来的分位数就是插值猜的，误差可能翻倍。
  • 只对「值超过阈值」告警，不对「指标消失」告警。进程崩溃或 Exporter 挂掉时表达式返回空集，空集不满足任何比较条件，系统会一片安静。
  • 告警不加持续时间约束。一次滚动重启、一次长 GC、一次抓取抖动都会让瞬时值越线，值班群很快被训练成免打扰。
  • 对原因告警而不是对症状告警。数据库一挂，上游二十个服务各报一条，真正的影响面被噪音埋掉，还会互相误导排查方向。
  • 用 CPU 使用率当饱和度。CPU 80% 可能很健康，而 CPU 30% 配上排满的线程池队列已经等于宕机；饱和度要看排队长度和等待时间。
  • 日志管道直连 Elasticsearch 不加缓冲。流量尖峰时 bulk 请求被拒绝，日志直接丢，偏偏丢的正是故障时段那一段。
  • 日志里不带 trace_id。三支柱各自能看但无法互相跳转，排查时只能靠时间戳肉眼对齐，效率断崖下降。
  • 捕获异常后打 ERROR 再原样抛出。同一个错误在调用栈上被记录三四遍，既放大存储又让错误数统计失真。
  • SLO 定成 99.99% 却没有自动故障转移。一个月只有 4 分 20 秒预算，一次探针配置不当的滚动更新就能打穿，目标从此形同虚设。
  • Tracing 只做头部采样就宣布上线。按固定概率采样会丢掉绝大多数罕见慢请求，而需要排查的恰恰是那些请求。
