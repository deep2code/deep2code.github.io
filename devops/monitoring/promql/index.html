PromQL 查询优化

🏷️ 监控,可观测性,Prometheus,Grafana

PromQL 是什么：一门为时序数据设计的表达式语言

PromQL（Prometheus Query Language）不是 SQL，也不是 Shell 管道，它是一门面向时序集合的表达式语言。你写的每一条查询，本质都是在描述"从全部时间序列里过滤出哪些序列、怎么聚合、时间维度上怎么算"。掌握它的关键不是背函数，而是理解三种基础数据类型：即时向量（Instant Vector）、区间向量（Range Vector）、标量（Scalar）。90% 的 PromQL 报错都源于这三者用错。

即时向量是"当前这一刻的一组时间序列快照"，如 http_requests_total；区间向量是"过去一段时间的样本窗口"，如 http_requests_total[5m]，必须搭配 rate()、increase()、avg_over_time() 这类窗口函数使用；标量就是一个裸数字（100）。Grafana 的"实时刷新"场景用即时向量，"看趋势图"场景用区间向量。

核心概念：四大类常用操作

把 PromQL 的函数按用途分成四组，日常 95% 的查询都能覆盖：

这张图揭示了 PromQL 的思考顺序：先选序列 → 再做窗口运算 → 再做聚合 → 最后一步做算术。新手常犯的错误是顺序写反，比如先 sum(rate(x[5m])) 再想按 route 拆——拆不开了，聚合已经把 route 维度丢了。

实战：从业务大盘到告警的常用查询

下面是生产环境最常用的 10 条 PromQL，建议收藏。注意每条查询都遵循上面的思考顺序：

# 1. QPS：按路由统计过去 5 秒的每秒请求数（Counter 标配 rate）
sum by (route) (rate(http_requests_total[5m]))

# 2. 错误率：5xx 占比。注意两个向量用 on(route) 对齐做除法
sum by (route) (rate(http_requests_total{status=~"5.."}[5m]))
  /
sum by (route) (rate(http_requests_total[status=~"[45].."}[5m]))

# 3. P99 延迟：histogram_quantile 必须作用于 rate() 后的 bucket
histogram_quantile(0.99,
  sum by (le, route) (rate(http_duration_seconds_bucket{route="/pay"}[5m])))

# 4. 每个实例 CPU 使用率（1 - 空闲），topk 取最高的 3 台
topk(3, 1 - avg by (instance) (rate(node_cpu_seconds_total{mode="idle"}[5m])))

# 5. 预测：磁盘还剩 4 小时写满就告警（predict_linear 给斜率）
predict_linear(node_filesystem_avail_bytes[6h], 4*3600) < 0

# 6. 健康度：抓到的目标里有多少是 down 的（抓取失败率）
sum by (job) (up == 0) / sum by (job) (up)

# 7. 在线用户：Gauge 直接聚合即可，不需要 rate
sum by (status) (online_users)

# 8. 95 分位请求体大小（Summary 型指标，直接拿分位）
quantile by (route) (0.95, http_request_size_bytes)

# 把高频查询写成 Recording Rule，预计算好，Grafana 直接查结果
# 文件保存到 rules/recording.yml，Prometheus 会自动评估
groups:
  - name: business.rules
    interval: 30s
    rules:
      # 预计算每路由 QPS，大盘面板直接查 http:qps:rate5m
      - record: http:qps:rate5m
        expr: sum by (route) (rate(http_requests_total[5m]))

      # 预计算每路由错误率，告警规则直接引用
      - record: http:error_ratio:rate5m
        expr: |
          sum by (route) (rate(http_requests_total{status=~"5.."}[5m]))
            /
          sum by (route) (rate(http_requests_total[5m]))

      # 预计算 P99
      - record: http:p99_seconds:rate5m
        expr: histogram_quantile(0.99,
          sum by (le, route) (rate(http_duration_seconds_bucket[5m])))

查询优化：为什么你的 Grafana 打开要 10 秒

PromQL 查询慢，几乎都是同一个根因——扫描了不该扫的时间序列。优化手段按收益排序：

  • 缩小时间范围：rate(x[5m]) 比 rate(x[1h]) 快几十倍。图上 1 分钟一个点就够了，不要查 1 小时窗口。
  • 提前过滤标签：sum(rate(http_requests_total{route="/pay"}[5m])) 比 sum(rate(http_requests_total[5m])) 快得多，前者只扫一个 route 的序列。
  • 用 Recording Rule：上面的 YAML 例子，把复杂查询预计算成一条新指标，Grafana 面板直接查这条结果，查询延迟从秒级降到毫秒级。
  • 避免 without() 反向聚合：sum without (instance) 会保留所有其它维度，基数爆炸时极慢，能写 sum by (route) 就写 by。
  • 警惕 count_values 和 quantile：它们需要把序列全量拉到内存，序列数 > 10 万时慎用。

最佳实践

  • Counter 永远套 rate，Gauge 永远别套 rate——这两条背下来能避开 80% 的查询 bug。
  • 分位数在聚合前后各算一次：跨实例算 P99 时，先 sum by (le) 把同 le 桶加起来，再 histogram_quantile。直接对每个实例算 P99 再平均，得到的是"实例级 P99 的平均"，不是"全局 P99"，这是统计学错误。
  • 告警规则里用 for: 5m：毛刺不报，持续恶化才报。
  • 查询走 API 时带 time 和 timeout：/api/v1/query?query=...&timeout=30s，避免慢查询把 Prometheus 拖死。
我踩过的坑：P99 算出来偏低

有次大盘 P99 显示 50ms，APM 工具却显示 200ms，差了 4 倍。排查后发现是查询写反了：先对每个实例 histogram_quantile，再 avg by (route)——这算的是"各实例 P99 的平均值"，不是全局 P99。正确姿势是先 sum by (le, route) 把桶加起来，再 histogram_quantile(0.99, ...)。分位数不能平均，只能在桶上聚合。

常见问题 FAQ

Q1：rate() 和 irate() 到底用哪个？

rate() 是窗口内的平均速率，平滑、适合做 SLO 大盘；irate() 是窗口内最后两个点的瞬时速率，对突发流量更敏感，但画出来的线会抖得厉害。生产默认 rate()，只有排查"这个毛刺是不是真的"时才用 irate()。窗口大小选 4~10 倍抓取间隔：抓取 15s，窗口就选 1m~5m。

Q2：为什么 histogram_quantile 算出来的 P99 和 APM 工具不一样？

三个常见原因：① bucket 定义太粗——你埋点时桶最大到 1s，真实 P99 是 2s，函数只能线性外推；② 聚合顺序错了——应该先 sum by (le) 再 quantile，而不是先 quantile 再 avg；③ Prometheus 的 histogram_quantile 是近似值，桶数越少越粗。业务对精度要求高就换 Summary 或 OTel Exemplar。

Q3：查询返回空矩阵（no data）但指标明明存在，为什么？

最常见是标签对不上：你查 route="pay"，实际埋点写的是 route="/pay"。用 {__name__="http_requests_total"} 不带任何标签先查一下原始序列，再对照 labels。再一个常见原因是时间窗口问题：区间向量窗口内没有数据点（实例刚重启、抓取间隔 > 窗口），换 [5m] 为 [15m] 试试。

Q4：PromQL 支持 JOIN 吗？两个不同指标怎么对齐计算？

支持隐式 JOIN：两个即时向量做算术运算时，Prometheus 会按完全相同的标签集自动匹配。如果只想按部分标签对齐，用 on(route) 或 ignoring(instance)。例如"按路由算错误率"就是分子分母都按 route 聚合后自动对齐。注意：标签集不完全一致的向量对，除法结果为空——这是"no data"的另一个常见原因。

总结

PromQL 的核心心智模型只有三句话：向量选序列、窗口算速率、聚合定维度。Counter 套 rate、Gauge 直接看、Histogram 算分位——三个指标类型对应三种写法。查询慢先查基数和时间窗口，重复查询上 Recording Rule。下一篇我们离开查询语言，把这些指标用 Grafana 拼成值班同学每天盯的仪表盘。
