PromQL 语义陷阱：向量类型、rate 外推、分位数与向量匹配

🏷️ PromQL

PromQL 的函数列表很短，背下来不用一小时。真正让人写出「能跑但结果是错的」查询的是它的语义：类型系统区分瞬时向量和区间向量、rate 会做线性外推、分位数不可相加、二元运算默认要求标签完全相同。这一篇只讲这些陷阱——每一条都是线上真实误判过的。Prometheus 自身的架构与运维见站内 devops/monitoring/prometheus/，基数与告警方法论见 devops/monitoring/ 主干篇。

一、瞬时向量与区间向量：类型决定了能调用什么

PromQL 有四种表达式类型，绝大多数解析错误和「结果为空」都源于类型用错。

http_requests_total{job="api"} 是瞬时向量（instant vector）：一组序列，每条序列在查询时刻只有一个样本值。它可以直接画图、直接比较大小、直接做算术。

http_requests_total{job="api"}[5m] 是区间向量（range vector）：同样是一组序列，但每条序列携带过去 5 分钟窗口内的全部样本点。它不能直接画图，也不能直接比较大小——Grafana 里直接写区间向量会报表达式类型错误，因为一个时间点上有多个值，图表不知道画哪个。区间向量必须先经过一个接受区间向量的函数（rate、avg_over_time、max_over_time 等），变回瞬时向量才能继续用。

这就回答了那个最基础的问题：rate() 为什么只能作用于区间向量？因为速率是「变化量除以时间」，至少需要两个带时间戳的点才能做差。瞬时向量一条序列只有一个值，没有第二个点可以减。

⚠️
一个高频误解

avg_over_time(x[5m]) 和 avg(x) 完全不是一回事。前者是时间维度的平均：每条序列各自在 5 分钟内取均值，序列条数不变。后者是空间维度的聚合：把所有序列压成一条，时间点不变。想「先按时间平滑再跨实例汇总」，得写 avg(avg_over_time(x[5m]))，顺序不能反。

二、rate / irate / increase：差异、外推与区间长度

三者都只作用于 Counter 类型的区间向量，都会自动处理计数器重置（窗口内检测到值下降就认定为进程重启，只累加上升部分，不会产生巨大负值）。差别在于取哪些点。

rate 取窗口内首尾两个样本做差，除以时间跨度，得到每秒平均增长率。曲线平滑，是画图和告警的默认选择。irate 只取窗口内最后两个样本，反应极快。increase 本质就是 rate 乘以区间长度，语义是「这段时间一共增长了多少」。

irate 有个很反直觉的坑：画长时间范围的图时，Grafana 的绘图步长（step）会远大于抓取间隔，比如查 24 小时的图步长可能是 5 分钟，而 irate 每个点只反映那一刻最后两个样本之间的瞬时值——中间几十个样本被完全跳过。结果是曲线布满毛刺，而且真正的尖峰有很大概率恰好落在被跳过的区间里。所以 irate 只适合看短时间范围的瞬时波动，绝不能用于告警。

再说外推（extrapolation），这是「为什么 increase 算出来是 23.7 次」的答案。窗口边界上通常没有采样点，Prometheus 会按已知两端点的斜率把增长量线性外推到窗口的真实边界，所以结果是小数。这不是缺陷，而是为了让不同长度窗口的结果保持可比。两个推论：一是用 increase 对整数阈值告警时要留余量，外推可能让结果略大于实际观测增量；二是如果窗口内序列刚开始或刚结束（新 Pod 启动不久），外推会被限制在序列存在的时间范围内，不会无限放大。

区间长度怎么选？经验规则是至少覆盖 4 个抓取间隔。理由：rate 至少需要两个点，而抓取可能抖动、可能丢一次，留 4 倍冗余才能保证窗口里稳定有两个以上的点。抓取间隔 30 秒的时候写 rate(x[1m]) 是典型错误——窗口里理论上只有 2 个点，任何一次抓取延迟或失败都会让点数掉到 1，rate 立刻返回空（在 Grafana 里表现为断线，在告警里表现为静默），这就是「查询时不时返回 NaN 或者断断续续」最常见的原因。

# 1. 服务总 QPS：先 rate 再 sum，顺序不能反
#    先 sum 再 rate 会把单实例的 Counter 重置抹平而失真
sum(rate(http_requests_total{job="api"}[5m]))

# 2. 按状态码分组的 QPS，用于错误率分子分母
sum by (code) (rate(http_requests_total{job="api"}[5m]))

# 3. 错误率：分子分母都必须是 rate 之后的结果
sum(rate(http_requests_total{job="api",code=~"5.."}[5m]))
  / sum(rate(http_requests_total{job="api"}[5m]))

# 4. 一小时内累计失败次数：increase 而不是 rate，单位是次不是次每秒
#    注意外推会让结果带小数，阈值要留余量
sum(increase(http_requests_total{job="api",code=~"5.."}[1h]))

# 5. 只在调试时用 irate 看秒级尖峰，图表时间范围控制在 15 分钟内
irate(http_requests_total{job="api"}[1m])

# 6. Gauge 不能用 rate，看趋势用 deriv，看区间变化量用 delta
deriv(node_filesystem_avail_bytes{mountpoint="/"}[1h])   # 每秒变化量
delta(node_filesystem_avail_bytes{mountpoint="/"}[1h])   # 一小时净变化

# 7. CPU 使用率的标准写法：idle 模式的增长速率就是空闲占比
100 * (1 - avg by (instance) (rate(node_cpu_seconds_total{mode="idle"}[5m])))

三、聚合运算符：by 与 without 互为补集

聚合运算符把多条序列压成少数几条，by 和 without 决定结果保留哪些标签，二者是补集关系：by (job) 表示「结果只保留 job 标签，其余全部丢弃」；without (instance) 表示「只丢掉 instance，其余全部保留」。不写任何修饰符则聚合成单一序列，所有标签都没了。

在标签集会变化的场景里，without 比 by 更稳健：加了新标签时 by 的结果不会带上它，而 without 会自动保留。反之在做告警和预聚合时 by 更安全，因为它明确限定了输出维度，不会因为业务偷偷加了个标签就让序列数翻倍。

写法语义输出标签注意
sum(x)全部压成一条无标签丢掉所有维度，只适合看总量
sum by (job) (x)按 job 分组求和仅 job输出维度固定，推荐用于告警与 recording rule
sum without (instance) (x)去掉 instance 后分组求和除 instance 外全部业务新增标签会自动带出，可能意外增加序列
avg by (job) (x)按 job 求平均仅 job对 Gauge 有意义，对分位数无意义
count by (job) (x)数序列条数仅 job常用于统计实例数；数样本点要用 count_over_time
topk(5, x)取值最大的 5 条序列保留原序列全部标签不适合画趋势图，每个时间点的 top 成员不同，线会来回跳
bottomk(5, x)取值最小的 5 条保留原标签同上
quantile by (job) (0.9, x)在序列之间求分位数仅 job这是「实例间的第 90 百分位」，与请求延迟的 P90 是两个完全不同的概念，极易混淆

四、histogram_quantile：顺序错一步，结果全错

这是 PromQL 里出错率最高的一个函数。正确写法只有一种顺序：先 rate，再按 le 做 sum，最后才 histogram_quantile。

flowchart TB S["原始桶序列
带 le 标签 本质是累积 Counter"] S --> A1["第一步 rate
把累积计数器变成每秒速率"] A1 --> A2["第二步 sum by 含 le
把多实例的同一桶相加"] A2 --> A3["第三步 histogram_quantile
在合并后的分布上插值估算"] A3 --> OK["正确结果
整体 P99"] S --> B1["错误一 跳过 rate
直接对累积值算分位数"] B1 --> BAD1["得到进程启动至今的历史分位数
故障期间曲线几乎不动"] S --> C1["错误二 先算分位数再聚合
avg 或 sum 套在外面"] C1 --> BAD2["对分位数做二次聚合
数学上无意义 误差可达数量级"] S --> D1["错误三 聚合时丢了 le
写成 sum by job"] D1 --> BAD3["函数拿不到桶边界
返回 NaN 或直接报错"]

为什么必须按 le 聚合？因为 histogram_quantile 完全依赖 le 标签来识别桶边界，它的算法是：先从最大的那个无穷桶拿到总数，算出目标分位数对应第几个样本，找到该样本落在哪两个相邻桶之间，然后在这两个桶边界之间做线性插值。一旦 le 被聚合掉，函数看到的只是一个数字，没有任何分布信息。

另外注意：sum by (le) 把所有实例合并成整体分布，这正是跨实例聚合分位数的唯一正确方法——合并的是桶计数（可加的整数），而不是分位数（不可加）。这也是为什么 Histogram 能跨实例聚合而 Summary 不能。至于「多实例的 P99 求平均为什么错」的完整推演，见站内主干篇的分位数章节。

# 正确：整体 P99 延迟
histogram_quantile(
  0.99,
  sum by (le) (rate(http_request_duration_seconds_bucket{job="api"}[5m]))
)

# 正确：按接口分别看 P99，le 必须和分组维度一起保留
histogram_quantile(
  0.99,
  sum by (le, handler) (rate(http_request_duration_seconds_bucket{job="api"}[5m]))
)

# 错误一：漏了 rate，算的是进程启动至今的累计分布，故障时几乎不动
histogram_quantile(0.99, sum by (le) (http_request_duration_seconds_bucket))

# 错误二：漏了 le，函数拿不到桶边界，返回 NaN
histogram_quantile(0.99, sum by (job) (rate(http_request_duration_seconds_bucket[5m])))

# 错误三：先算分位数再求平均，分位数不可相加，结果无意义
avg by (job) (
  histogram_quantile(0.99, rate(http_request_duration_seconds_bucket[5m]))
)

# 平均延迟的正确算法：_sum 除以 _count，不要用 P50 冒充平均值
sum(rate(http_request_duration_seconds_sum{job="api"}[5m]))
  / sum(rate(http_request_duration_seconds_count{job="api"}[5m]))

# SLO 视角更该看的是“达标比例”而不是分位数本身：
# 300ms 内返回的请求占比。前提是 0.3 必须是一个真实存在的桶边界
sum(rate(http_request_duration_seconds_bucket{job="api",le="0.3"}[5m]))
  / sum(rate(http_request_duration_seconds_count{job="api"}[5m]))

五、向量匹配：查询返回空的头号原因

两个瞬时向量做运算时，PromQL 默认按一对一匹配：把左右两侧指标名之外的标签集合当成 key，只有完全相同的一对才能计算。任何一个标签的键或值不一致，这条序列就配不上，直接从结果里消失；全部配不上就返回空集——注意它不报错，只是安静地给你一个空结果，这是新手最崩溃的场景。

修饰符语义典型用途坑
默认，无修饰符一对一，要求标签集完全相同同一指标族的两个指标相除标签多一个就返回空，且不报错
on (a, b)只按列出的标签匹配，其余忽略跨指标族关联，如请求数除以实例数结果只保留 on 里的标签，其他维度全丢
ignoring (c)除列出的标签外全部参与匹配忽略掉一侧多出来的 le、code 等与 on 互为补集，不能同时使用
group_left多对一，左侧是多的一侧给海量序列关联一条元信息，如 kube_pod_info右侧必须唯一，否则报多对多不允许的错误
group_right多对一，右侧是多的一侧元信息在左、数据在右时使用方向记错就报错，靠试也能试出来，但要理解语义
group_left (label)额外把「一」侧的某个标签带到结果里把版本号、团队归属等元信息贴到指标上括号里的标签来自「一」侧，写错标签名不会报错，只是没带出来
and / unless / or集合运算，只做过滤不做计算多条件联合告警、排除白名单同样受标签匹配约束，标签不一致时 and 会全空
 
# 场景一：标签完全一致，直接一对一相除（同指标族，最理想）
node_filesystem_avail_bytes / node_filesystem_size_bytes

# 场景二：一侧多了 code 标签导致返回空
# 下面这句会返回空集，因为左侧有 code 标签右侧没有：
#   rate(http_requests_total{code="500"}[5m]) / rate(http_requests_total[5m])
# 正确写法：两侧都聚合到同一标签集
sum by (job, instance) (rate(http_requests_total{code=~"5.."}[5m]))
  / sum by (job, instance) (rate(http_requests_total[5m]))

# 场景三：跨指标族只按部分标签匹配，用 on
sum by (instance) (rate(http_requests_total[5m]))
  / on (instance) group_left
    count by (instance) (up{job="api"})

# 场景四：多对一，给每条容器指标贴上它所属 Pod 的节点名等元信息
# 左侧是多（每容器一条），右侧 kube_pod_info 每 Pod 一条，所以用 group_left
sum by (pod, namespace) (rate(container_cpu_usage_seconds_total{image!=""}[5m]))
  * on (pod, namespace) group_left (node, created_by_kind)
    kube_pod_info

# 场景五：集合运算做联合条件告警
# 只在“错误率高”且“流量不算太小”时才认为是真问题，避免低流量放大噪音
(
  sum by (job) (rate(http_requests_total{code=~"5.."}[5m]))
    / sum by (job) (rate(http_requests_total[5m])) > 0.05
)
and
(
  sum by (job) (rate(http_requests_total[5m])) > 10
)

# 场景六：unless 做白名单排除，排除掉标记为 canary 的实例
(up{job="api"} == 0) unless on (instance) (node_meta{role="canary"})

六、offset 与 @ 修饰符：同比环比

offset 把取值的时间点整体往前挪，用来做环比。@ 修饰符（Prometheus 2.25 引入）把取值固定在某个绝对时间戳，配合 start() / end() 可以取「查询范围起点或终点」的值，做基准线对比非常好用。子查询语法 expr[窗口:步长] 则允许把一个瞬时向量表达式的结果当成区间向量来用，典型场景是「过去 24 小时里 5 分钟 QPS 的最大值」。

写法语义用途注意
x offset 1d取一天前那一刻的值环比、同比offset 必须紧跟在选择器后面，不能放在函数外
rate(x[5m] offset 1w)一周前那 5 分钟的速率与上周同一时段对比写成 rate(x[5m]) offset 1w 是语法错误
x @ 1735660800固定取该 Unix 时间戳的值锚定某次发布前的基线时间戳是秒级；与 offset 可叠加，@ 先生效
x @ start()取查询时间范围起点的值画「相对起点的增长倍数」只在区间查询中有意义
max_over_time(rate(x[5m])[24h:5m])子查询：24 小时内每 5 分钟算一次 rate 再取最大找峰值 QPS、容量评估步长写太小会产生海量中间点，查询极慢，尽量用 recording rule 替代
x[24h:]步长省略时默认用全局 evaluation_interval快速探索依赖全局配置，不同环境结果不同，正式查询建议写明步长

七、absent 与 absent_over_time：对「指标消失」告警

这是最常被漏掉的一类告警。所有基于比较的表达式在没有数据时返回空集，而空集不满足任何条件，于是进程崩溃、采集端挂掉、标签被 relabel 改坏这些最严重的故障，反而一条告警都不会触发——面板一片空白，值班群一片安静。

absent(v) 的语义是：如果参数返回空集，就产出一个值为 1 的序列；否则什么都不返回。absent_over_time(v[5m]) 判断的是一整个时间窗内是否完全没有样本，更适合抓取间隔长或数据本身稀疏的场景，能避免单次抓取抖动造成误报。

# 1. 某个 job 的目标整体消失（服务发现挂了、标签配置被改坏）
absent(up{job="payment-api"}) == 1

# 2. 关键业务指标在 10 分钟内完全没有数据（比 absent 更抗抖动）
absent_over_time(order_created_total{env="prod"}[10m]) == 1

# 3. absent 想带出标签，必须在表达式里写死等值筛选条件
#    只有等值匹配的标签会出现在结果里，正则匹配的不会
absent(up{job="payment-api", env="prod"})        # 结果带 job 与 env
absent(up{job=~"payment.*"})                     # 结果不带 job，通知里看不出是谁

# 4. 更强的写法：结合预期实例数，既能发现“全没了”也能发现“少了几个”
count(up{job="payment-api"} == 1) < 3

# 5. 业务量归零告警：Counter 不再增长，比 absent 更贴近业务语义
#    用 increase 而不是 rate，阈值用“次数”更直观
sum(increase(order_created_total{env="prod"}[10m])) == 0

# 6. 数据陈旧告警：指标还在但已经很久没更新（常见于推送型、批处理型指标）
time() - max(push_time_seconds{job="nightly-etl"}) > 86400 * 1.5

# 7. 环比暴跌：与一周前同时段对比，跌超过 70% 就报
(
  sum(rate(order_created_total[30m]))
  / sum(rate(order_created_total[30m] offset 1w))
) < 0.3

八、常见写法错误对照表

把前面所有陷阱压缩成一张可以贴在工位上的表。每一行左边都是「能跑通、不报错、但结果是错的」写法。

错误写法错在哪正确写法
http_requests_total 直接画图Counter 原始值单调上升，故障期间照样涨，看不出任何信息rate(http_requests_total[5m])
rate(x[1m])，抓取间隔 30s窗口内只有 2 个点，丢一次抓取就返回空，表现为断线与告警静默区间至少覆盖 4 个抓取间隔，写 [2m] 或 [5m]
irate(x[5m]) 画 24 小时图绘图步长远大于采样间隔，中间样本被跳过，毛刺多且会漏掉尖峰长图用 rate，irate 只用于短范围调试
先 sum 再 rate聚合会抹平单实例的 Counter 重置，重启时数据失真；且对聚合结果加区间语法本身不成立sum(rate(x[5m]))，永远先 rate 再聚合
rate(node_memory_MemFree_bytes[5m])对 Gauge 用 rate，下降会被当成 Counter 重置处理，结果无意义用 deriv 看趋势、delta 看净变化
histogram_quantile(0.99, x_bucket)漏了 rate，算的是进程启动至今的历史分布先 rate(x_bucket[5m])
histogram_quantile(0.99, sum by (job) (rate(x_bucket[5m])))聚合时丢了 le，函数拿不到桶边界，返回 NaNsum by (job, le) (...)
avg(histogram_quantile(0.99, ...))对分位数做二次聚合，分位数不可相加，误差可达数量级先 sum by (le) 合并桶，再算一次分位数
avg(rate(x_sum[5m]) / rate(x_count[5m])) 当成整体平均对「各实例的平均值」再求平均，忽略了各实例请求量权重sum(rate(x_sum[5m])) / sum(rate(x_count[5m]))
rate(a{code="500"}[5m]) / rate(a[5m])左侧多了 code 标签，一对一匹配失败，安静返回空集两侧都 sum by 收敛到同一标签集，或用 ignoring (code)
多对一运算不写 group_left报多对多匹配不允许的错误，或匹配数量不符预期在「多」的那一侧加 group_left 或 group_right
up{job="x"} == 0 作为唯一存活告警目标从服务发现消失时 up 序列本身也没了，空集不触发任何比较再补一条 absent(up{job="x"}) == 1
用 increase(x[1h]) 卡整数阈值外推导致结果带小数且可能略大于实际增量理解外推语义，阈值留余量，或改用 rate 加时长换算
topk(5, x) 画趋势图每个时间点的 top 成员不同，线会来回跳，无法读先用 topk 找出对象，再固定标签单独画
avg_over_time(x[5m]) 与 avg(x) 混用一个是时间维度平均，一个是序列间平均，语义完全不同需要两者时写 avg(avg_over_time(x[5m]))，注意顺序
告警表达式里套多层子查询子查询按步长展开会产生海量中间点，求值耗时逼近 evaluation_interval 会导致跳过求值、告警漏报用 recording rule 预聚合，告警只读预聚合序列

最容易踩的坑

❌
避坑清单
  • 把区间向量直接当查询结果。x[5m] 不能画图、不能比较大小，必须先经过一个接受区间向量的函数变回瞬时向量。
  • 区间长度写得不到 4 个抓取间隔。抓取间隔 30 秒却写 rate(x[1m])，窗口里只有两个点，任何一次抓取抖动就让结果变空，表现为面板断线和告警静默。
  • 用 irate 画长时间范围的图或做告警。绘图步长远大于采样间隔时中间样本被整段跳过，尖峰有很大概率恰好落在跳过的区间里。
  • 对 Gauge 用 rate。数值下降会被当成计数器重置处理，得到的曲线毫无物理意义，Gauge 要用 deriv 或 delta。
  • 先聚合再 rate。聚合会把单实例的计数器重置抹平，实例重启时结果失真；顺序永远是先 rate 再聚合。
  • 以为 increase 和 rate 单位相同。increase(x[5m]) 等于 rate(x[5m]) 乘以 300，阈值照抄会差 300 倍。
  • 不知道 rate 会做线性外推，看到小数结果以为查询写错了。外推是为了让不同窗口长度可比，用 increase 卡整数阈值时要留余量。
  • histogram_quantile 漏掉 rate。算出来的是进程启动至今的累计分布，故障期间曲线几乎不动，是最隐蔽的一种错。
  • 聚合桶时丢掉 le 标签。函数靠 le 识别桶边界并做线性插值，丢了就只能返回 NaN。
  • 对多个实例的 P99 求平均或求和。分位数不可相加，正确做法是先 sum by (le) 合并桶计数，再算一次分位数。
  • 用 P50 冒充平均延迟。平均值要用 _sum 除以 _count，两者在长尾分布下差异很大。
  • 两个指标相除返回空却以为是没数据。默认一对一匹配要求标签集完全相同，配不上时不报错只返回空集，排查要先分别执行两侧比对标签。
  • 多对一运算不加 group_left，或者方向写反。给海量序列贴元信息标签时必须指明哪一侧是「多」的一侧。
  • 只用 up == 0 做存活告警。目标从服务发现中消失时 up 序列一起消失，必须补 absent 类告警才不会漏。
  • absent 里用正则匹配标签。只有等值匹配的标签会出现在结果中，用正则会让通知里看不出究竟是哪个目标不见了。
  • 告警表达式里堆子查询。子查询按步长展开会加载海量中间点，规则求值耗时逼近求值间隔时会直接跳过求值，表现为告警漏报。
