OpenTelemetry 怎么接：上下文传播、采样策略与 Collector

🏷️ OpenTelemetry

OpenTelemetry 常被介绍成「又一个链路追踪框架」，这个说法把它最重要的价值说漏了。它真正解决的问题是厂商锁定：以前选了某家 APM，业务代码里就散落着这家厂商特定的埋点调用，换一家等于所有服务重新埋一遍，成本高到根本不会去评估替代方案。OTel 把「埋点 API」和「后端实现」彻底拆开，代码只依赖中立的 API，换后端只改导出配置。这篇讲清它的分层、数据模型，以及落地时真正会踩的两个大坑——上下文传播和采样策略。

先分清四个层次：API、SDK、Collector、OTLP

大量困惑来自把这四个东西混为一谈。它们的职责边界非常清楚：

flowchart TB subgraph APP["业务进程内"] API["OTel API：只有接口与空实现
业务代码与埋点库依赖它"] SDK["OTel SDK：真正的实现
采样器 / Processor / Exporter"] INS["Instrumentation：框架埋点库
HTTP / RPC / DB / MQ 客户端"] end subgraph COL["OpenTelemetry Collector（独立进程）"] RC["Receivers：收 OTLP / Jaeger / Zipkin / Prometheus"] PR["Processors：批处理 / 脱敏 / 尾部采样 / 限流"] EX["Exporters：可同时发多个后端"] end subgraph BE["后端（可替换的那一层）"] TP["Tempo / Jaeger"] PM["Prometheus / 远程写入存储"] LK["Loki / Elasticsearch"] end INS --> API API --> SDK SDK -->|"OTLP over gRPC 4317 或 HTTP 4318"| RC RC --> PR PR --> EX EX --> TP EX --> PM EX --> LK
层次 职责 谁依赖它 不理解会怎样
API 定义 Tracer、Span、Meter、上下文等接口，默认是空实现 业务代码、第三方库的埋点 库作者若依赖 SDK 而非 API，就会把具体实现强加给使用方，版本冲突不可避免
SDK 实现 API：采样决策、span 处理器、批量导出、资源属性 只在应用启动入口装配一次 只引 API 不引 SDK 时，代码跑得通但一条数据都不会产出，非常迷惑
Instrumentation 为具体框架生成 span 并填协议属性，可以是字节码注入的 agent 或显式包装库 应用按使用的框架逐个引入 以为装了 agent 就万事俱备，结果业务语义一片空白
OTLP 标准传输协议，gRPC 默认 4317，HTTP 默认 4318 SDK 与 Collector、Collector 与后端 后端不支持 OTLP 时需要在 Collector 转换，这正是 Collector 存在的理由之一
Collector 集中做批处理、脱敏、尾部采样、限流、多后端分发、协议转换 基础设施层，与业务无关 让每个应用直连后端，之后想改采样或换后端要重新发布所有服务
语义约定 规定属性名与取值，如服务名、HTTP 方法、数据库系统等 所有埋点 各团队自定义属性名，后端无法做统一看板与统一告警，标准的价值全部丢失
⚠️
语义约定有过不兼容的改名

HTTP 相关属性在规范稳定化过程中改过名（旧版与新版的方法名、状态码字段名不同），Java 等实现提供了过渡开关，可以选择只发旧版、只发新版或同时发两套。升级 agent 前务必确认后端看板和告警用的是哪一套属性名，否则升级后曲线会突然变空——这类故障在生产里非常常见。

Trace 的数据模型：Span 里到底有什么

一条 trace 是一棵 span 树，靠三个标识串起来：TraceID（全链路唯一，16 字节即 32 位十六进制）、SpanID（本 span 唯一，8 字节即 16 位十六进制）、ParentSpanID（父 span 的 ID，根 span 为空）。

Span 字段 含义 由谁设置 常见错误
name 操作名，应是低基数的 埋点库或手动指定 把 URL 路径参数写进名字，导致后端操作名有几百万种，聚合完全失效。应该用路由模板
attributes 键值对，描述这次操作的维度 埋点库填协议属性，业务代码填业务属性 把大对象或完整 SQL 参数塞进去，单个 span 体积暴涨；敏感字段未脱敏
events span 生命周期内的时间点事件，带自己的时间戳 手动添加，异常记录也是一种 event 用 event 代替子 span 去表达一段耗时，结果看不出时间区间
status Unset、Ok、Error 三态 手动设置，或由埋点库按状态码推断 只记录了异常却没把 status 置为 Error，后端不认为这条 trace 出错，尾部采样的保留错误策略也匹配不到
links 指向其他 trace 的关联，不构成父子关系 手动设置 批处理和异步场景不用 links 而硬套父子关系，时间线被拉成几十分钟
kind SpanKind，表达这个 span 在通信中的角色 埋点库设置，手动埋点要自己指定 全部留成默认的 Internal，后端算不出服务拓扑图
SpanKind 用在什么位置 后端靠它做什么 配错的后果
SERVER 接收并处理远程请求的入口 识别服务边界、计算服务级 RED 指标 缺失时服务拓扑图上这个服务不会出现
CLIENT 发起同步远程调用，等待响应 与对端 SERVER span 配对，算出网络与排队耗时 标成 Internal 后，无法区分「自己慢」和「下游慢」
PRODUCER 向消息队列投递，不等消费结果 知道这是异步边界，不把消费耗时算进生产耗时 标成 CLIENT 会让后端误以为是同步调用，延迟统计被污染
CONSUMER 从消息队列取出并处理 与 PRODUCER 配对，算出队列停留时间 缺失时消息链路彻底断开，看不出消息从哪来
INTERNAL 进程内部的逻辑分段，如业务方法、缓存计算 展示内部耗时分布 滥用会让 span 数量暴涨，成本上升而信息没变多
sequenceDiagram autonumber participant C as 客户端 participant G as 网关 participant O as 订单服务 participant P as 支付服务 participant D as 数据库 C->>G: 发起下单请求，无追踪上下文 Note over G: 创建根 span，SpanKind 为 SERVER
生成 TraceID 并在此做采样决策 G->>O: 转发，注入 traceparent 请求头 Note over G: 网关侧还会有一个 CLIENT span
与订单服务的 SERVER span 配对 Note over O: 从请求头提取上下文
父子关系由 ParentSpanID 建立 O->>O: 业务分段，SpanKind 为 INTERNAL O->>D: 查询库存，SpanKind 为 CLIENT D-->>O: 返回结果 O->>P: 调用支付，继续透传同一个 TraceID Note over P: 又一个 SERVER span
TraceID 相同，ParentSpanID 指向订单服务 P-->>O: 支付结果 O-->>G: 下单结果 G-->>C: 响应 Note over C,D: 五个服务、七八个 span，共享一个 TraceID
靠 ParentSpanID 拼成一棵树

W3C TraceContext 规定了传播格式：请求头 traceparent 由四段用连字符拼成——版本、32 位十六进制的 trace id、16 位十六进制的 span id、两位十六进制的标志位（最低位为 1 表示已采样）。另有 tracestate 用于携带各厂商的附加状态。理解「标志位里带着采样决策」这一点很关键：下游服务是根据这个位来决定要不要记录的，采样决策在入口就已经定了。

上下文传播：最容易出问题的环节

实践中「链路断了」的报障，九成以上都是上下文传播问题。把断链场景列清楚比讲原理有用：

断链场景 为什么断 现象 怎么修
提交任务到线程池 上下文存在线程本地存储里，新线程拿不到 子任务的 span 变成一棵新树的根，与主链路毫无关联 用 OTel 提供的上下文包装执行器；Java agent 对标准线程池能自动处理，自定义线程池要手动包
异步回调与 Future 链 回调执行时原线程的上下文已被清理 span 时间戳错乱，或父子关系错挂到别的请求上 在提交点捕获上下文，在回调入口显式恢复；Go 里就是把 ctx 一路往下传
跨消息队列 MQ 协议不是 HTTP，上下文必须写进消息头 生产端和消费端是两条完全独立的 trace 生产时 Inject 进消息头，消费时先 Extract 再开 CONSUMER span，顺序不能颠倒
网关或代理剥头 部分网关只透传白名单请求头 链路在固定某一跳断开，且非常稳定可复现 在网关放行 traceparent 与 tracestate；顺手确认 CDN 与 WAF 也没有剥
传播格式不一致 一边用 W3C 标准格式，一边用旧的厂商私有格式 互相解析不了对方的头，各自新建 trace 统一配置传播器，迁移期同时启用多种格式解析，写入仍以标准格式为主
定时任务与批处理 没有天然的入口请求，也没有父上下文 每次执行都是独立 trace，但一次批处理可能对应上万条业务 每次执行开一个根 span，对每条业务用 links 关联，不要硬套父子关系
手写 HTTP 客户端 没有经过被埋点的客户端，头没被注入 下游看起来像是被人直接调用的根请求 换成被埋点的客户端，或手动 Inject 到请求头 
package order

import (
	"context"

	"go.opentelemetry.io/otel"
	"go.opentelemetry.io/otel/attribute"
	"go.opentelemetry.io/otel/codes"
	"go.opentelemetry.io/otel/trace"
)

// tracer 在包级别获取一次，名字用「埋点库或模块」的标识，后端会按它归类
var tracer = otel.Tracer("github.com/example/order")

func CreateOrder(ctx context.Context, userID string, amountCents int64) (err error) {
	// 自动埋点已经建好了 SERVER span，这里建的是业务语义的 INTERNAL span
	ctx, span := tracer.Start(ctx, "order.create",
		trace.WithSpanKind(trace.SpanKindInternal),
		trace.WithAttributes(
			// 业务属性只能手动埋，任何 agent 都猜不出来；注意用自有前缀，别和语义约定的名字撞车
			attribute.String("app.user_id", userID),
			attribute.Int64("app.amount_cents", amountCents),
		),
	)
	defer span.End() // 忘了 End 的 span 永远不会被导出，链路上就凭空缺一段

	if err = checkInventory(ctx, userID); err != nil {
		// 只 RecordError 不 SetStatus 是高频错误：后端不会把这条 trace 判定为失败，
		// 尾部采样里「保留所有错误链路」的策略也就匹配不到它
		span.RecordError(err)
		span.SetStatus(codes.Error, "inventory check failed")
		return err
	}

	// 关键：必须继续传这里返回的 ctx。
	// 传旧 ctx 或 context.Background()，下游 span 就会变成另一棵树的根
	if err = deductBalance(ctx, userID, amountCents); err != nil {
		span.RecordError(err)
		span.SetStatus(codes.Error, "deduct balance failed")
		return err
	}
	return nil
}

// 异步场景：不要把父 span 的 ctx 直接带进生命周期更长的 goroutine。
// 父 span 已经 End 之后还挂在它下面，得到的时间关系是错的。
// 正确做法是取出 span context 作为新 trace 的 link。
func AsyncNotify(parent context.Context, orderID string) {
	link := trace.LinkFromContext(parent,
		attribute.String("app.order_id", orderID))
	go func() {
		ctx, span := tracer.Start(context.Background(), "order.notify",
			trace.WithSpanKind(trace.SpanKindProducer),
			trace.WithLinks(link),
		)
		defer span.End()
		if err := sendMessage(ctx, orderID); err != nil {
			span.RecordError(err)
			span.SetStatus(codes.Error, "notify failed")
		}
	}()
}

跨消息队列是另一个必须手写的地方。即使 MQ 客户端有自动埋点，也常常只负责建 span，把上下文写进消息头这一步在不少组合下仍需自己做。核心是实现一个 carrier，把 OTel 的键值读写映射到消息头：

// kafkaCarrier 把 OTel 的 TextMapCarrier 接口映射到 Kafka 消息头
type kafkaCarrier struct {
	headers *[]kafka.Header
}

func (c kafkaCarrier) Get(key string) string {
	for _, h := range *c.headers {
		if h.Key == key {
			return string(h.Value)
		}
	}
	return ""
}

func (c kafkaCarrier) Set(key, value string) {
	// 同名 header 先删再加。重试时不处理会出现两个 traceparent，
	// 消费端按第一个解析，可能拿到上一次尝试的上下文
	kept := (*c.headers)[:0]
	for _, h := range *c.headers {
		if h.Key != key {
			kept = append(kept, h)
		}
	}
	*c.headers = append(kept, kafka.Header{Key: key, Value: []byte(value)})
}

func (c kafkaCarrier) Keys() []string {
	keys := make([]string, 0, len(*c.headers))
	for _, h := range *c.headers {
		keys = append(keys, h.Key)
	}
	return keys
}

// 生产端：在 PRODUCER span 内部注入，注入必须发生在 span 创建之后
func Publish(ctx context.Context, msg *kafka.Message) error {
	ctx, span := tracer.Start(ctx, "orders.publish",
		trace.WithSpanKind(trace.SpanKindProducer))
	defer span.End()

	otel.GetTextMapPropagator().Inject(ctx, kafkaCarrier{headers: &msg.Headers})
	return producer.Send(ctx, msg)
}

// 消费端：先 Extract 再开 span，顺序反了就会断链
func Consume(msg *kafka.Message) {
	ctx := otel.GetTextMapPropagator().Extract(
		context.Background(), kafkaCarrier{headers: &msg.Headers})

	ctx, span := tracer.Start(ctx, "orders.consume",
		trace.WithSpanKind(trace.SpanKindConsumer))
	defer span.End()

	handle(ctx, msg)
}

自动埋点覆盖什么、覆盖不了什么

范围 自动埋点是否覆盖 说明
HTTP 服务端与客户端、主流 RPC 框架 覆盖 自动生成 SERVER 与 CLIENT span，并按语义约定填好方法、路由、状态码
数据库与缓存客户端 覆盖 会记录语句模板与耗时；注意默认可能带上完整语句，含参数时需要在 Collector 脱敏
消息队列客户端 部分覆盖 span 通常有，但上下文注入与提取要确认；不同语言与版本差异很大
标准线程池与常见异步框架 部分覆盖 字节码注入型 agent 对标准实现能处理，自定义线程池与手写调度器要自己包装
业务语义：租户、风控策略、优惠命中、降级原因 不覆盖 只能手动埋，而这恰恰是定位业务问题时最值钱的信息
非标准私有协议、自研中间件 不覆盖 需要自己写埋点，重点是注入与提取，以及正确设置 SpanKind

务实的接入顺序是：先上 agent 或自动埋点库拿到八成的技术 span，再针对核心业务流程手动补十来个业务 span。反过来做（先花两周设计手动埋点规范）通常会卡在推进上。

采样策略：成本与可观测性的核心权衡

全量存 trace 在有一定规模后成本不可接受，所以采样是必答题。两条路线的差别在于决策时机：

flowchart TB S["需要降低 trace 成本"] --> Q1{"日均 span 量级"} Q1 -->|"较小，成本可接受"| A0["全量保留
最省心，也最好用"] Q1 -->|"较大，必须采样"| Q2{"能接受漏掉部分错误链路吗"} Q2 -->|"能，先跑起来"| H["头部采样
入口按比例决定，全链路继承"] Q2 -->|"不能，排障必须有错误链路"| Q3{"愿意为 Collector 加资源吗"} Q3 -->|"愿意"| T["尾部采样
Collector 侧等 trace 齐了再决策"] Q3 -->|"不愿意"| M["折中：头部采样提高比例
再对错误路径单独提升采样率"] T --> L["前置负载均衡
按 TraceID 路由到同一实例"]
维度 头部采样 尾部采样
决策位置与时机 链路入口，请求刚进来还不知结果时 Collector 侧，等一条 trace 的片段基本齐了之后
能否保留所有错误与慢链路 不能，只能按概率碰上 能，可按状态码、延迟阈值、属性规则精确保留
客户端与网络开销 最低，未采样的 span 根本不生成也不发送 高，必须先把全量 span 发到 Collector
Collector 资源 基本无额外要求 需要缓冲等待窗口内的所有 trace，内存是主要瓶颈
部署约束 无 同一 trace 的所有 span 必须进同一个 Collector 实例，需前置按 TraceID 路由的负载均衡
典型失效方式 各服务比例配得不一致，产生大量残缺 trace 等待窗口小于真实链路时长，长链路被当成不完整直接判掉
适用阶段 刚落地、规模中等、成本敏感 已经在用链路排障、且苦于「出事那条正好没采到」
❌
采样决策必须全链路一致

各服务各配一套比例，会产出大量残缺 trace：入口判定丢弃，中间某个服务自己决定保留，后端于是收到一堆找不到父节点的孤立片段——既拼不成链路，又照样花了存储。正确做法是所有服务统一使用「基于父级」的采样器，只有在没有父级时才按比例自行决策，且这个比例在所有入口服务保持一致。要对特定接口提高采样率，应该在 Collector 侧用尾部采样规则实现，不要在各服务 SDK 里各配一套。

# otel-collector.yaml —— 网关层 Collector（做尾部采样与脱敏）
receivers:
  otlp:
    protocols:
      grpc:
        endpoint: 0.0.0.0:4317
      http:
        endpoint: 0.0.0.0:4318

processors:
  # memory_limiter 必须放在 pipeline 的第一位，它靠拒绝新数据来保护自己不被 OOM
  memory_limiter:
    check_interval: 1s
    limit_percentage: 75
    spike_limit_percentage: 15

  # 脱敏与瘦身：放在采样之前，避免把敏感数据留在被采样保留的 trace 里
  attributes/redact:
    actions:
      - key: http.request.header.authorization
        action: delete
      - key: db.statement          # 很多驱动会带上含参数的完整语句
        action: delete
      - key: enduser.id
        action: hash               # 保留可聚合性，但看不到原值

  # 尾部采样：等 10 秒让同一 trace 的 span 到齐，再按规则决定去留
  tail_sampling:
    decision_wait: 10s             # 必须大于绝大多数链路的总耗时，否则长链路会被判成不完整
    num_traces: 200000             # 缓冲的 trace 数上限，直接决定内存占用
    expected_new_traces_per_sec: 2000
    policies:
      - name: keep-all-errors      # 错误链路全留，这是尾部采样最大的价值
        type: status_code
        status_code:
          status_codes: [ERROR]
      - name: keep-slow
        type: latency
        latency:
          threshold_ms: 1000
      - name: keep-key-tenant      # 重点客户全留
        type: string_attribute
        string_attribute:
          key: app.tenant
          values: [vip, internal]
      - name: baseline-sample      # 其余正常链路只留 5%
        type: probabilistic
        probabilistic:
          sampling_percentage: 5

  # batch 必须放最后：攒批能显著降低导出开销，放在采样前会被反复拆分重组
  batch:
    timeout: 5s
    send_batch_size: 8192
    send_batch_max_size: 10000

exporters:
  otlp/tempo:
    endpoint: tempo:4317
    tls:
      insecure: true
    sending_queue:
      enabled: true
      queue_size: 5000             # 后端抖动时的缓冲；满了才开始丢
    retry_on_failure:
      enabled: true
      initial_interval: 5s
      max_elapsed_time: 300s
  # 灰度换后端时，同时发两个 exporter 对比结果，这是 OTel 最实用的能力之一
  otlp/vendor-b:
    endpoint: vendor-b-gateway:4317

service:
  extensions: []
  pipelines:
    traces:
      receivers: [otlp]
      processors: [memory_limiter, attributes/redact, tail_sampling, batch]
      exporters: [otlp/tempo, otlp/vendor-b]
  telemetry:
    metrics:
      level: detailed              # Collector 自身指标必须采，重点看 refused 与 dropped 计数

# 注意：上面这份配置要求同一条 trace 的所有 span 都进到同一个实例。
# 多副本部署时，前面必须再加一层 Collector，用 loadbalancing exporter
# 以 traceID 作为路由键分发，否则尾部采样看到的永远是碎片。

span 从创建到落到后端，中间会被这些环节筛一遍，任何一环丢了都表现为「查不到链路」：

stateDiagram-v2 [*] --> Started Started --> NotRecording: 采样器判定不记录 NotRecording --> [*] Started --> Recording: 采样器判定记录 Recording --> Ended: 调用 End Recording --> Leaked: 忘记 End，永不导出 Ended --> Queued: 进入批处理队列 Queued --> DroppedFull: 队列已满，直接丢弃 Queued --> Exported: 批量发往 Collector Exported --> CollectorBuffered: 尾部采样等待窗口 CollectorBuffered --> DroppedBySampling: 未命中任何保留策略 CollectorBuffered --> Stored: 命中策略，写入后端 Stored --> [*]

三类信号的成熟度差异，以及把 trace_id 注入日志

OTel 宣称统一 Trace、Metrics、Logs 三类信号，但三者的成熟度和落地方式差别很大，按同一套预期去推进容易踩空：

信号 规范与 SDK 状态 现实中的落地方式 务实建议
Trace 最成熟，API 与 SDK 早已稳定，各语言实现完整 agent 或埋点库加少量手动埋点，经 Collector 发后端 首选切入点，收益最直接
Metrics 规范已稳定，但与 Prometheus 生态存在映射细节差异，如直方图形态、属性名转换、时间语义 多数团队仍以 Prometheus 抓取为主，用 Collector 做协议转换与桥接 已有 Prometheus 体系时不必急着迁；新系统可以直接用 OTLP 指标
Logs 数据模型已定，但主要以桥接既有日志框架的方式提供，各语言完成度不一 大部分团队保留现有日志管道，只做与 trace 的关联 不要为了统一而推翻现有日志链路，先把关联做好

把 trace_id 注入日志，是整套建设里投入产出比最高的一步，通常半天就能做完，之后从一条报错日志能直接跳到完整调用链，从一条慢链路也能反查那一瞬间所有服务打的日志，两边互为索引。

import (
	"context"
	"log/slog"

	"go.opentelemetry.io/otel/trace"
)

// 所有日志调用都带上这组字段。Java 里对应的做法是在拦截器里写 MDC，
// 并在请求结束时清理，否则线程复用会把上一次请求的 trace_id 带到下一次。
func traceAttrs(ctx context.Context) []any {
	sc := trace.SpanContextFromContext(ctx)
	if !sc.IsValid() {
		// 没有有效上下文说明这条日志不在任何链路里（比如启动日志、定时任务）
		return nil
	}
	return []any{
		slog.String("trace_id", sc.TraceID().String()), // 32 位十六进制，直接可在后端检索
		slog.String("span_id", sc.SpanID().String()),   // 16 位十六进制，定位到具体这一跳
		// 采样标记一定要记：没被采样的请求在链路后端查不到，
		// 不记的话会误判成「链路系统丢数据」，实际只是这条没采
		slog.Bool("trace_sampled", sc.IsSampled()),
	}
}

func handle(ctx context.Context, orderID string) {
	slog.LogAttrs(ctx, slog.LevelError, "create order failed")
	// 或者在自定义 Handler 里统一注入，避免每个调用点都要手写：
	slog.Error("create order failed",
		append(traceAttrs(ctx), slog.String("order_id", orderID))...)
}

反向关联同样有用：在 span 上记录关键日志的 event，或者把日志系统的查询链接作为 span 属性带上。不过更省事的做法是双方都存 trace_id，由看板负责跳转。

语义约定：为什么一个属性名这么重要

语义约定规定了属性的标准名字与取值，比如服务名、HTTP 方法、目标主机、数据库系统、消息系统等。它看起来只是命名规范，实际决定了整套体系能不能做通用化：

  • 看板与告警可复用。所有服务都用同一个属性名表示 HTTP 方法和状态码，一份服务概览看板就能套用到全部服务；各团队自定义名字时，每个服务都得单独做一份。
  • 后端的开箱能力依赖它。服务拓扑图、RED 指标、依赖分析这些功能，都是后端按约定属性算出来的。属性名不对，功能就静默失效——不报错，只是图是空的。
  • 由 span 生成指标（在 Collector 里把 span 转成请求量与延迟指标）也依赖约定属性名做维度切分。
  • 业务属性要加自有前缀，比如统一用 app. 开头，避免和将来新增的标准属性撞名。撞名之后升级 agent 就会出现同名不同义，排查起来非常难受。

最容易踩的坑

❌
避坑清单
  • 只引入 API 不装配 SDK：代码编译通过、跑得也正常，但一条数据都不会产出，日志里也没有任何报错，非常容易白查半天。
  • span 名字里带 ID：把 URL 路径参数或订单号写进 span 名，后端的操作名变成几百万种，聚合与对比全部失效。名字要用路由模板，可变部分放 attributes。
  • 忘记结束 span：未 End 的 span 永远不会导出，链路上凭空缺一段，而且还在内存里占着。Go 里 defer span.End() 要紧跟创建语句。
  • 只 RecordError 不 SetStatus：后端不会把这条 trace 判定为失败，尾部采样里「保留所有错误链路」的策略也匹配不到，等于错误链路白丢。
  • 提交任务到线程池时不带上下文：子任务成了新 trace 的根。标准线程池 agent 能处理，自定义线程池必须手动包装。
  • 把父 span 的上下文带进长生命周期的异步任务：父 span 早已结束，时间关系会变得荒谬（一个 200ms 的请求下面挂着 30 分钟的子 span）。这种场景该用 links。
  • 跨消息队列不注入上下文：生产端与消费端变成两条独立链路，而这恰恰是异步问题最需要追踪的地方。
  • 消费端先开 span 再 Extract：顺序反了，span 已经挂到空上下文下，再 Extract 也救不回来。
  • 重试时重复写入 traceparent 头：出现两个同名头，消费端按第一个解析，拿到的是上一次尝试的上下文。Set 实现要先删后加。
  • 网关或 WAF 剥掉追踪请求头：链路在固定某一跳断开，现象稳定可复现，但很少有人第一时间想到去查网关的请求头白名单。
  • 各服务各配采样比例：入口判丢、中间判留，产出大量找不到父节点的残缺 trace，既没用又花钱。统一用基于父级的采样器。
  • 尾部采样的等待窗口小于链路真实耗时：慢链路（也就是你最想看的那些）会被当成不完整直接判掉，恰好把最有价值的数据丢了。
  • 尾部采样多副本部署却没按 TraceID 路由：同一条 trace 的 span 散落在不同 Collector 实例上，每个实例看到的都是碎片，采样规则完全失准。
  • memory_limiter 不放在 pipeline 第一位、batch 不放最后：前者导致 Collector 被流量尖峰打成 OOM，后者让攒批效果大打折扣。
  • 把完整 SQL、请求体、响应体塞进 attributes：单个 span 体积暴涨，成本上升，还极易把敏感数据带到链路后端——链路后端的权限通常比数据库宽得多。
  • SpanKind 全留默认值：服务拓扑图算不出来，也无法区分「自己慢」和「下游慢」。
  • 升级 agent 不看语义约定变更：属性改名后看板和告警静默失效，图变空但没有任何报错，往往是下一次故障时才发现。
  • 用链路数据算成功率与影响面：数据经过采样，绝对量没有统计意义。统计口径要用未采样的指标，链路只用来看单条请求的结构。
