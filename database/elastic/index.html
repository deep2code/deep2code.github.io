Elasticsearch 9.0

🏷️ Elasticsearch

先说选型：别上来就 ES

我见过太多团队一上来就 Elasticsearch，结果十万级文档的项目跑了三节点集群，每月云账单好几千，运维还天天半夜起来看告警。说句实话，文档量在十万以内、单机就能扛住的全文搜索，Meilisearch 或者 Typesense 的性价比甩 ES 几条街。

我个人的选型判断

你问我什么时候才该上 ES？日志分析要挂 Kibana 出报表、商品搜索要做相关性排序和向量语义、数据量奔着亿级去要横向扩展——这种时候 ES 才真正值回票价。不然老老实实选个轻量方案，省下来的钱和精力干点啥不好。

先看看几个常见替代方案：

  • Zinc：Go 写的，单机几百兆内存就能跑
  • Meilisearch：Rust 写的，启动快，开箱即用，毫秒级返回
  • Typesense：C++ 写的，纯内存，性能猛但吃内存

Meilisearch 一条命令就能跑起来，我本地调试的时候经常用：

docker run --name ms1.0 --restart always -p 9080:7700 \
  -v $(pwd)/meili_data:/meili_data \
  -d getmeili/meilisearch:v1.0

踩过的坑：版本不对齐

Kibana 和 ES 的主版本号必须严格一致。我之前在公司环境拿 7.17 的 Kibana 连 8.x 的 ES，界面直接白屏，查了半天日志才反应过来——主版本差一个小版本都不行。Apple Silicon 的 Mac 记得选 arm64 构建，别下成 x86_64 的。

核心概念：其实就是倒排索引

很多人刚接触 ES 被一堆术语吓到，其实底层就一件事：倒排索引。你把它理解成一本书的索引页——书后面不是按页码列内容，而是按关键词列它出现在第几页。ES 就是把这个索引做得特别大、特别快。

字段类型怎么选：text 还是 keyword

这是每个新手都会踩的第一个坑。text 会分词，搜"快速"能匹配到"快速棕色狐狸"；keyword 是精确匹配，整个字符串必须一模一样。我见过有人把状态字段存成 text，结果 term 查询死活查不到数据，排查了一整天——就是因为 text 字段被分词了。

graph LR subgraph 写入流程 D[Doc：快速棕色狐狸] --> A[分词器] A --> T1[快速] A --> T2[棕色] A --> T3[狐狸] end subgraph 倒排索引 T1 --> P1[快速 → Doc1, Doc3] T2 --> P2[棕色 → Doc1, Doc3] T3 --> P3[狐狸 → Doc1] end style A fill:#fedd00,stroke:#333

2026 年的写法基本上都是 multi-fields：一个字段同时建 text 和 keyword 两个子字段。比如 title 要做全文搜索，就配一个 title.keyword 用来排序和聚合。具体类型选择我列个表：

类型什么时候用注意事项
text文章正文、商品描述，要全文搜索不要用来 term 精确匹配
keyword状态码、标签、ID，要聚合排序占内存，别什么都用 keyword
long / integer数字字段按取值范围选最小的，省空间
date时间字段格式不一致会查不到
nested嵌套对象数组不用 nested 的话数组对象会被拍平，查不准
dense_vector向量检索8.x 起原生支持 kNN
semantic_text语义搜索（9.0 GA）自动生成 embedding，不用自己调模型

查询怎么写

ES 的查询语法叫 Query DSL，本质是个 JSON 结构。最常用的就那么几个，我逐个说。

叶子查询：match、term、range

match 是全文搜索，会自动分词，你搜"golang 教程"它会拆成"golang"和"教程"分别匹配：

GET /_search
{
    "query": {
        "match": { "message": "this is a test" }
    }
}

term 是精确匹配，一个字都不能差。记住：千万别拿 term 去查 text 字段，因为 text 已经被分词了，你原文存的"Quick"被分成了"quick"，term 查"Quick"自然找不到：

GET /_search
{
    "query": {
        "term": { "user.id": { "value": "kimchy" } }
    }
}

range 用来查范围，数值、日期、IP 都行：

GET /_search
{
    "query": {
        "range": { "age": { "gte": 18, "lte": 35 } }
    }
}

bool 组合查询：生产环境 90% 长这样

真实业务查询很少是单条件的，基本上都是 bool 把几个条件拼起来：

GET /_search
{
    "query": {
        "bool": {
            "must":     [{ "match": { "title": "golang" } }],
            "filter":   [{ "term": { "status": "published" } },
                         { "range": { "publish_date": { "gte": "2026-01-01" } } }],
            "must_not": [{ "term": { "author": "spam-bot" } }],
            "should":   [{ "term": { "tags": "grpc" } }]
        }
    }
}
filter 不打分——白捡的性能优化

很多人不知道 filter 和 must 的区别。filter 只过滤不算分，而且结果能被 Query Cache 缓存。你想想，"状态=已发布"这种条件需要参与相关性打分吗？不需要。能放 filter 的就别放 must，这是我能想到的最容易拿到的 ES 性能提升，没有之一。

分布式架构：数据怎么存、怎么查

ES 能扛亿级数据，靠的就是分片。你可以把一个索引想象成一个大表，分成 N 份，每份放在不同的机器上，这就是分片。每个分片还能有副本，副本既是备份也能分担查询压力。

分片和副本

  • 主分片数量创建后不能改——这是最容易犯的错。我见过有人一开始设了 5 个主分片，后来数据涨了想改成 10 个，结果发现改不了，只能 reindex 整个索引，几百万条数据导了一晚上
  • 副本数随时能改，生产环境至少 1 个副本，不然主分片挂了数据就丢了
  • 路由规则是 shard = hash(routing) % 主分片数，默认 routing 用文档 ID。如果你按用户 ID 做查询，自己指定 routing 能少查很多分片

写入流程：为什么数据要等一秒才能搜到

很多新手问"我刚写入的数据怎么搜不到？"答案很简单：ES 是近实时的。写入流程是这样的：

sequenceDiagram participant CL as 客户端 participant CN as 协调节点 participant PN as 主分片节点 participant RN as 副本节点 CL->>CN: 写入文档 CN->>PN: 转发到主分片 PN->>PN: 先写 translog 日志 PN->>PN: 写入内存缓冲区 PN->>RN: 并行写所有副本 RN-->>PN: 确认完成 PN-->>CN: 主分片写成功 CN-->>CL: 返回结果 Note over PN: 每秒 refresh 一次
数据才变成可搜索的段

看到了吧？数据先在内存里，每秒 refresh 一次才生成可搜索的段。这就是为什么你刚写入的文档要等大概 1 秒才能搜到。如果你测试的时候急了，可以手动调 POST /index/_refresh 强制刷新。

查询的两阶段：先查ID，再取数据

查询分两阶段，很多人没搞明白这个，导致对深分页问题理解不深：

  • Query 阶段：协调节点把请求发到所有相关分片，每个分片在本地查一遍，返回匹配的文档 ID 和分数。注意，每个分片都要返回 from+size 条结果
  • Fetch 阶段：协调节点把所有分片返回的结果合并、排序，取前 from+size 条，再去对应的分片拿完整文档内容
深分页：from=10000 就是个灾难

你想想，如果你 from=10000&size=10，每个分片都得返回 10010 条数据，协调节点收上来一排序，到头来只要 10 条——前面 10000 条全扔了。这就是为什么 ES 默认限制 max_result_window=10000。深分页用 search_after，基于上一页末条的排序值往下翻，别硬用 from。

Lucene 底层：段文件和数据结构

ES 本质上是 Lucene 的分布式封装。每个分片就是一个 Lucene 索引。搞懂 Lucene 的段结构，排障和调优就有方向了。

段是不可变的

Lucene 有个核心设计：段一旦写进去就不能改。你要删除文档？不改段，而是在另一个文件里标记"这个文档被删了"。你要更新？其实是删除旧文档+写入新文档。这个设计听起来很蠢，但好处巨大：不需要加锁、可以被操作系统缓存高效利用、并发安全。

段的生命周期有三个关键动作：

  • Refresh：默认每秒把内存缓冲区刷成一个新段，新段才能被搜索。轻量，但段太多了也不好
  • Flush：把段真正写到磁盘上，同时清空 translog。这才叫持久化
  • Merge：后台线程把多个小段合并成一个大段，顺便把标记删除的文档物理删掉。这个操作很吃 IO

Lucene 内部到底用了哪些数据结构

结构存什么服务什么查询放哪
倒排表 Postings词 → 文档列表 + 词频 + 位置全文搜索、短语查询磁盘
FST 词典所有词项的有限状态机term 查询、前缀、模糊内存映射
Doc Values列式存储：字段 → 值数组聚合、排序磁盘 + OS 缓存
BKD 树多维数值坐标范围查询、地理位置磁盘
HNSW 图向量近似最近邻kNN 语义搜索磁盘 + 内存

FST 这个东西我得多说两句。它把所有词项压缩成一个状态机，共享前缀和后缀。一百万个词项可能就占几十 MB 内存，查询是 O(1)。这就是为什么 ES 的 term 查询这么快——词典根本不在磁盘上查，全在内存里。

为什么 BM25 比 TF-IDF 好

ES 默认的相关性打分算法是 BM25，替代了老的 TF-IDF。区别在哪？TF-IDF 里词频是线性的——一个词出现 10 次就是 1 次的 10 倍权重。但你想想，一篇文章里"的"出现 100 次，真的比出现 1 次重要 100 倍吗？显然不是。BM25 加了个饱和效应：词频到一定程度权重就不怎么涨了。参数 k1（默认 1.2）控制饱和速度，b（默认 0.75）控制长文档的惩罚力度。一般不用调，用默认值就行。

分片文件长什么样

有时候磁盘满了或者排查性能问题，你得知道 ES 的数据文件都存了啥。单个分片的目录结构是这样的：

点击展开完整文件列表 
elasticsearch_data/nodes/0/indices/{uuid}/0/
├── index/                    # Lucene 索引目录
│   ├── segments_1            # 段提交点，记录所有活跃段
│   ├── _0.tim / _0.tip      # 词项词典 + FST 索引
│   ├── _0.doc                # 倒排表跳跃表
│   ├── _0.pos                # 词位置信息（短语查询用）
│   ├── _0.fdt / _0.fdx       # 存储字段（原始文档）
│   ├── _0.nvd / _0.nvm       # 归一化向量
│   ├── _0.dvd / _0.dvm       # Doc Values 列式存储
│   ├── _0.kdd / _0.kdi       # BKD 树（数值/地理位置）
│   └── _0.vec / _0.vem       # 向量数据（kNN 用）
├── translog/                 # 事务日志，崩了用来恢复
│   ├── translog-1.tlog
│   └── translog.ckp
└── _state/                   # 分片元状态

如果磁盘突然满了，先看 .dvd（Doc Values）和 .fdt（原始文档）这两个文件大不大。我遇到过一次，一个文档里塞了 base64 编码的图片，_source 涨得飞快，三天磁盘从 40% 冲到 92%。后来把图片字段排除出 _source，才稳住。

性能优化：我踩过的那些坑

写入优化：批量、批量、还是批量

单条写入和批量写入的吞吐量差 10 到 100 倍。这个数字不是我编的，是实测的。原因很简单：单条写入的开销大头在网络往返和每秒 refresh，批量写把这些成本摊薄了。

优化手段怎么做实测效果（参考值）
Bulk 批量写入每批 5-15MBQPS 从 2000 涨到 8000+
临时关 refreshindex.refresh_interval=-1导入速度快 2-3 倍
导入时副本设 0number_of_replicas=0写入快约 2 倍
Translog 改 asyncdurability=async吞吐 +30%，但可能丢 5 秒数据

典型的 Bulk 请求长这样：

POST /_bulk
{ "index": { "_index": "products", "_id": "1" } }
{ "name": "iPhone 16", "price": 6999 }
{ "index": { "_index": "products", "_id": "2" } }
{ "name": "Mate 70", "price": 5999 }

注意批量大小看字节数别看条数——一个 1MB 的大文档和一个 1KB 的小文档，条数一样但压力完全不同。我一般控制在 5-15MB 一批。

查询优化

查询慢了怎么办？先看几个最常见的原因：

  • 条件放错了位置：不需要打分的条件全扔 filter，别放 must。这是零成本优化
  • 聚合桶太多：高基数字段做 terms 聚合，比如按用户 ID 聚合，几百万个用户就是几百万个桶，内存直接爆。用 composite 聚合分页处理
  • 没用 routing：多租户场景下，查询带上 ?routing=user_1001，只查这个用户的分片，不用广播到所有节点

JVM 堆：31GB 是条红线

这个坑我见过太多人踩

JVM 堆别超过 31GB。很多人觉得内存越大越好，给 ES 配 64GB 堆。但 JVM 在堆超过 32GB 的时候会关闭压缩指针（Compressed Oops），对象指针从 32 位变成 64 位，内存利用率反而下降，GC 停顿还更长。正确做法：堆给物理内存的 50%，但不超过 31GB，剩下的内存全部留给操作系统文件缓存——Lucene 重度依赖 page cache。

ES 9.0 是 8.x 之后时隔三年的大版本，基于 Lucene 10.1。截至 2026 年中，稳定线已经到 9.5.x 了。我挑几个跟你日常用得上的变化说：

许可证这块绕不开

ES 的许可证历史也挺狗血的。2021 年之前是 Apache 2.0，后来 Elastic 公司闹了一通，改成 SSPL + Elastic License 双许可，结果社区 fork 出了个 OpenSearch。2024 年又改回 AGPL v3，算是回归了 OSI 认证。2025 年 9.0 发布后是 AGPL + Elastic License 二选一。

8.x 还在用的特性

很多公司还在 8.x，我把关键特性回顾一下：

  • ES|QL：8.14 GA 的管道查询语言，比 DSL 简洁不少

ES 和 MySQL 到底怎么配合

这个问题我被问过无数次。一句话回答：MySQL 是主，ES 是从。

维度ElasticsearchMySQL
强项全文搜索、聚合分析、相关性排序事务、精确查询、数据一致性
分词丰富，中文有 IK 分词器中文支持很差
模糊查询Fuzzy / Prefix 都支持LIKE '%xx%' 全表扫描
写入近实时（1 秒）实时
数据一致性不支持事务ACID 完整

正确的架构是：MySQL 存数据，用 Canal 订阅 Binlog 实时同步到 ES。写请求走 MySQL，搜索请求走 ES。别想着用 ES 替代 MySQL，它没事务，更新还是删除+新增，干不了主存储的活。

我踩过的八个坑

  1. 分片数乱设：一开始觉得 5 个主分片稳妥，结果数据涨到几十 GB 想加分片发现改不了。经验法则：每个分片 10-50GB，每个节点分片数别超过 20 个（按每 GB 堆内存对应 20 个分片算）
  2. 动态映射翻车：第一条文档某个字段是空字符串，ES 把它推断成 text，后来第二条文档传了个数字进来，直接报类型冲突。生产环境一定要显式定义 Mapping，加 dynamic: strict 拒绝未知字段
  3. 脑裂：老版本 ES 网络分区的时候多个节点都觉得自己是 Master，集群状态直接乱掉。7.0 之后用 Raft 协议好多了，但 Master 节点还是得奇数（3 或 5 个）
  4. 堆内存给太大：上面说过了，31GB 是红线
  5. 段合并 IO 打满：批量导入数据的时候，后台段合并把磁盘 IO 跑满，线上查询延迟从 50ms 飙到 2 秒。后来导入的时候先把副本设 0、refresh 关掉，导完再打开，问题解决
  6. 熔断异常：circuit_breaking_exception 这个错我见过太多次了。大查询把堆内存吃满，ES 为了自保直接拒绝请求。解决办法：限制聚合桶数、加 timeout、优化查询
  7. 磁盘满了只读：磁盘到 95% 的时候 ES 自动把索引设成只读，你再写就报错。解除方法：PUT _all/_settings {"index.blocks.read_only_allow_delete": null}，但治标不治本，得赶紧扩容
  8. _source 太大：文档里塞了个 2MB 的 base64 图片字段，结果查询的时候光 Fetch 阶段就要传输几个 G 的数据。不搜索的大字段直接在 Mapping 里排除出 _source

FAQ

ES 和 OpenSearch 选哪个？

OpenSearch 是 2021 年从 ES 7.10 fork 出来的，用 Apache 2.0 协议。如果你公司在意许可证限制、或者已经深度用了 AWS OpenSearch Service，选它。如果你要最新的语义搜索功能、官方商业支持、持续跟 ES 主线，选 Elasticsearch 9.x。我们团队因为要做 RAG，semantic_text 这个特性太香了，结果还是留在了 ES。

为什么我刚写入的数据搜不到？

正常的。ES 是近实时写入，默认每秒 refresh 一次。你刚写完就去搜，数据还在内存缓冲区里，没生成可搜索的段。等一秒钟再试，或者调 POST /index/_refresh 强制刷新。

报 circuit_breaking_exception 怎么办？

这是 ES 觉得这个查询要把内存吃爆了，主动拒绝。先看下是不是聚合桶数太多、是不是深分页、是不是在大字段上做了 script。急着解决就调大熔断器阈值，但那是饮鸩止渴，根本上还是要优化查询。

semantic_text 和 dense_vector 有什么区别？

dense_vector 需要你自己调 OpenAI 或者 BGE 模型把文本转成向量，再存进 ES。semantic_text 是 9.0 GA 的新类型，你直接存文本，ES 自动用内置模型生成 embedding，你只管写查询。省事多了，代价是你对模型的控制力弱了。
