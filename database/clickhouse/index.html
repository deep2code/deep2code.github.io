ClickHouse 总览

🏷️ ClickHouse,OLAP

我为什么写这一系列

2026 年了，数据栈里有个角色越来越绕不开：OLAP 分析引擎。业务数据库（MySQL/PG）扛点查和事务还行，可一旦你想"按天统计过去一年的 PV/UV"、"把三亿条日志按状态码聚合出报表"，关系型数据库就开始哆嗦。这时候大家不约而同地想起 ClickHouse——单表几亿行，一条 GROUP BY 跑出来常常几百毫秒，这种体验用过就回不去了。

我第一次在生产上用 ClickHouse 是接一个日志分析需求。之前我们用 Elasticsearch 扛日志，聚合查询一上去堆就告警；换了 ClickHouse 之后，同样的查询从 8 秒降到 300 毫秒，磁盘占用还少了六成。但踩的坑也不少：第一次写入用单条 INSERT 把集群写崩了，第一次建表忘了分区结果 ALTER DELETE 跑了一整晚。这一系列就是把这些年攒下来的架构、建表、优化、实战和选型经验整理成一份能照着走的地图。

一句话说清 ClickHouse 是什么

ClickHouse 是一个列式存储的 OLAP 数据库管理系统，2016 年开源，最初出自 Yandex（俄罗斯那个搜索引擎公司）。它不是万能数据库——没有完整的事务支持、不擅长单行更新和点查、Join 能力弱于 MySQL。但在它的主场大批量数据分析（OLAP）上，它是开源里性能最猛的那一档。

核心卖点就三句话：

  • 列式存储 + 高压缩比：同列同类数据放一起，压缩率轻松到 10:1，磁盘和内存带宽都省下来。
  • 向量化执行引擎：一次处理一整列的数据块，吃满 CPU 缓存和 SIMD，而不是一行一行地磨。
  • 单表查询极快：主键索引 + 稀疏跳过索引 + 分区裁剪，亿级数据聚合经常亚秒返回。

它在数据栈里站哪个位置

很多人纠结"我要不要上 ClickHouse"，其实先搞清楚它在你架构里扮演什么角色就不纠结了。它是分析层，不是业务层。

角色典型技术擅长不擅长
业务主库MySQL / PostgreSQL事务、点查、强一致大批量聚合分析
缓存Redis毫秒点查、热点数据持久化、复杂聚合
搜索Elasticsearch全文检索、相关性打分超大规模精确聚合
分析引擎ClickHouse / Doris亿级数据 GROUP BY、实时报表单行更新、事务、点查

典型数据流是：业务写 MySQL/日志写 Kafka → 实时或批量 ETL → ClickHouse 存明细和预聚合 → BI 报表直接查 ClickHouse。业务库负责"存得对"，ClickHouse 负责"算得快"。

和 ES、Doris 比，各自什么脾气

这三个经常被放一起比，但定位其实不一样。我先给个粗印象，第五篇会展开：

  • ClickHouse：单表聚合查询天花板，写入吞吐猛，运维相对轻，但 Join 和实时更新弱。
  • Elasticsearch：全文检索和多条件过滤的王者，聚合是附赠功能，数据量大了聚合又贵又慢。
  • Doris：MPP 架构，Join 和实时导入能力强，MySQL 协议兼容好，更像"能分析的数据仓库"。
我的第一性判断

你的核心需求是"日志/行为数据的聚合报表"，闭眼选 ClickHouse；核心需求是"商品/文章的全文搜索 + 过滤"，选 ES；核心需求是"业务库直接做实时数仓、多表 Join 多"，再认真考虑 Doris。别拿一个引擎解决所有问题。

先跑起来：一条命令体验一下

想动手感受的话，Docker 一把梭：

docker run -d --name clickhouse-server \
  -p 8123:8123 -p 9000:9000 \
  -e CLICKHOUSE_PASSWORD=yourpass \
  clickhouse/clickhouse-server:24.8

# 进客户端
docker run --rm -it --network=host \
  clickhouse/clickhouse-client:24.8 \
  --query "SELECT version()"

本机装的话我一般用官方 deb 包，别用系统源里那个老掉牙的版本。生产环境我建议至少跟到 24.x 稳定线，老版本的跳数索引和 Projection 都还不完整。

FAQ

Q：ClickHouse 能当业务数据库用吗？
不建议。它没有完整事务、不擅长单行 UPDATE/DELETE、主键点查也不快。业务读写还得交给 MySQL/PG，ClickHouse 只做分析层。

Q：数据量多大才值得上 ClickHouse？
没有硬门槛。十万行的小数据量 MySQL 就够；但只要你开始频繁做"按维度聚合"的报表、单表跑到千万行以上、或者要接日志流做实时看板，ClickHouse 的优势就开始显现了。

Q：它和 Doris 比是不是 ClickHouse 更强？
不是一个维度的"更强"。ClickHouse 单表聚合更猛、更轻；Doris 多表 Join 和实时数仓更顺手。选型看你查询模型，别唯性能论。第五篇我会给一张决策树。

我的结论

ClickHouse 不是万能数据库，但它把"OLAP 聚合查询"这一件事做到了开源顶级。2026 年它已经是日志分析、用户行为分析、实时数仓这些场景的事实标准之一。这个系列我会从架构原理一路讲到生产踩坑，读完你应该能自己判断"我这个场景该不该上、怎么建表、怎么调优"。
