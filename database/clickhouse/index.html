ClickHouse 深度原理：列存、向量化与 MergeTree

🏷️ ClickHouse

「ClickHouse 比 MySQL 快 100 倍」这句话本身没错，但它是结论不是原因，而且换个场景就会反过来——同一张表，按主键查一条记录 MySQL 能比 ClickHouse 快几十倍。真正值得搞清楚的是：OLAP 的访问模式长什么样，ClickHouse 为了这种访问模式做了哪些取舍，以及这些取舍在什么情况下会反过来咬你一口。这篇从存储布局讲到向量化执行，再讲 MergeTree 与稀疏索引的设计代价。

OLAP 和 OLTP 要的是两种完全不同的存储布局

OLTP 的典型访问是「按主键或唯一键取出一条完整记录，改其中几个字段」，一次只碰一行，但要碰这一行的所有列；OLAP 的典型访问是「扫过去三个月上亿行，只用其中三四个列做聚合」，一次碰海量行，但每行只要极少数列。这两种模式对存储布局的要求正好相反：前者希望一行的所有列挨在一起，一次 IO 就把整行拿到；后者希望一列的所有值挨在一起，好让不需要的列连读都不用读。

算一笔具体的账：一张 100 列、平均每列 8 字节、共 10 亿行的表，总原始数据 800 GB。查 3 个列时，行存必须把 800 GB 全部从磁盘读出来再丢掉 97%（行存无法只读一行的一部分，最小读取单位是页）；列存只读这 3 个列文件，原始 24 GB，再叠加列存本身更高的压缩比，实际落盘 IO 可能只有 3~5 GB。这就是「快 100 倍」的第一层来源，和 CPU 有多快没关系，纯粹是少读了两个数量级的数据。

列存的三重收益：少读、高压缩、可向量化

很多介绍只讲「只读需要的列」，这其实只是三重收益里最浅的一层。第二层是压缩：同一列的值类型相同、取值分布集中、往往还单调或重复，压缩算法能吃得非常饱。时间戳这类单调递增的列用 DoubleDelta 先做二阶差分，差分后全是 0 和小整数，再套 LZ4 就能压到几十分之一；LowCardinality(String) 会把字符串做字典编码，一个平均 20 字节的国家名在列里只占 1~2 字节的字典下标，这才是「低基数列能压到几十分之一」的真正原因——不是压缩算法神奇，而是字典编码把宽的值换成了窄的整数。

第三层收益最容易被忽略：列存让一列的值在内存里是定长、连续、无间隔的数组，这正是 SIMD 指令要求的输入形态。行存里同一列的值被其他列隔开，间隔还可能不固定，编译器没法自动向量化。所以「列存」和「向量化执行」不是两个独立的优化，后者依赖前者才能成立。

编码 / 类型典型压缩比适合的数据特征代价与注意
LZ4（默认）3~5 倍什么都行，通用兜底解压速度 GB/s 级，CPU 几乎免费
ZSTD(1)5~8 倍磁盘吃紧、查询不是 CPU 瓶颈解压比 LZ4 慢 2~3 倍，扫描量大时会变成新瓶颈
ZSTD(3~5)8~15 倍冷数据、大文本 payload写入 CPU 明显上升，热数据别用高等级
DoubleDelta + LZ420~50 倍单调递增：时间戳、自增 ID数据一旦乱序，压缩比立刻掉回普通水平
T64 + ZSTD8~20 倍实际值域远小于类型宽度的整数用 UInt64 存只有几百万取值的列时收益最大
Gorilla / FPC4~10 倍相邻值接近的浮点指标随机浮点上几乎无效
LowCardinality(String)等效 10~30 倍取值数在万级以下的字符串基数超过十万反而变慢，字典维护成本吃掉收益
 
-- 一张典型的事件宽表：分区、排序键、逐列 codec 都按数据特征来定
CREATE TABLE events
(
    event_date   Date,
    event_time   DateTime CODEC(DoubleDelta, LZ4),   -- 单调递增，二阶差分后极易压缩
    app_id       LowCardinality(String),             -- 基数几百，字典编码后每行 1~2 字节
    country      LowCardinality(String),
    event_type   LowCardinality(String),
    user_id      UInt64,                             -- 高基数，不进 ORDER BY
    duration_ms  UInt32 CODEC(T64, ZSTD(1)),         -- 实际值域远小于 UInt32
    payload      String  CODEC(ZSTD(3))              -- 大文本换压缩率
)
ENGINE = MergeTree
PARTITION BY toYYYYMM(event_date)             -- 按月：一年 12 个分区，粒度足够
ORDER BY (app_id, event_type, event_time)     -- 低基数、高频过滤的列在前
-- 不写 PRIMARY KEY 时，主键就等于 ORDER BY 的全部列
SETTINGS index_granularity = 8192;            -- 默认值；点查较多可降到 2048 换更细的定位

-- 高基数列的等值过滤交给跳数索引，而不是硬塞进 ORDER BY
ALTER TABLE events ADD INDEX idx_user user_id TYPE bloom_filter(0.01) GRANULARITY 4;
ALTER TABLE events MATERIALIZE INDEX idx_user;   -- 存量数据必须显式物化，否则只对新写入生效

向量化执行：把每行的虚函数开销摊薄到几乎为零

传统数据库执行引擎是火山模型（Volcano，也叫迭代器模型）：每个算子实现一个 next()，每次调用返回一行，上层算子不断向下层拉数据。它的优点是模型极其干净、内存占用极小、首行能立刻返回；缺点是每返回一行都要穿过整条算子链的虚函数调用，1 亿行经过 5 个算子就是 5 亿次虚函数调用，加上每行都要重新判断类型、重新走一遍分支，真正用于计算的指令占比可能不到 10%。

ClickHouse 换成了向量化执行：next() 一次返回一个 block，默认 max_block_size = 65536 行。1 亿行只需要约 1526 个 block，5 个算子加起来不到八千次函数调用，框架开销直接被摊平到可以忽略。更关键的是 block 内部是按列组织的连续数组，算子对一整列做循环，编译器能自动生成 SSE / AVX2 指令一次处理 4~8 个值，CPU 流水线也不会被频繁的间接跳转打断。

维度火山模型（一次一行）向量化（一次一批）
一次 next 返回1 行1 个 block，默认 65536 行
1 亿行过 5 个算子的调用次数约 5 亿次约 7600 次
每行摊到的框架开销几十到上百纳秒接近 0，可忽略
分支预测每行判一次谓词，失败率高批内同构，可写成无分支循环
SIMD基本用不上定长列连续存放，编译器自动向量化
CPU cache逐行跨列跳跃，miss 频繁一列一段连续，硬件预取友好
内存占用极小，只有当前行一个 block 的列缓冲；调大 max_block_size 更吃内存
首行延迟可以立刻吐出第一行要等 block 攒满，小结果集反而不划算
💡
向量化不等于并行

常见误解是把向量化和多线程混为一谈。向量化解决的是单核内「一条指令处理多个数据」和「摊薄框架开销」；多线程并行是另一套机制，由 max_threads（默认等于 CPU 核数）控制读取与计算的并发度。两者叠加才是 ClickHouse 的实际吞吐。max_threads 调大能压低单查询延迟，但会让高并发场景互相抢核——这也是它「单查询猛、高并发弱」的直接原因。

MergeTree：part 的一生决定了写入姿势

MergeTree 是理解 ClickHouse 的核心。一次 INSERT 的动作是：把这批数据按 ORDER BY 排序，按列切成文件，写成一个独立的目录，这个目录就是一个 part；写完后原子改名让它变成 active，查询立刻可见。注意 part 之间是不排序的，只有 part 内部有序，所以查询要同时扫多个 part 再做归并——这就是 part 数量必须被控制的根本原因。后台 merge 线程会不断挑选相邻的小 part 合并成更大的 part，思路和 LSM Tree 一致：写入只追加，排序整理推迟到后台做。

stateDiagram-v2 [*] --> Temporary: INSERT 排序后写入临时目录 Temporary --> Active: 原子改名提交 查询立即可见 Active --> Merging: 后台线程挑中若干相邻 part Merging --> NewPart: 合并成更大的 part 并提交 NewPart --> Active: 新 part 承接查询 Merging --> Active: merge 失败或被取消 原 part 仍可用 Active --> Outdated: 已被新 part 覆盖 不再参与查询 Outdated --> Deleting: 超过 old_parts_lifetime 默认 480 秒 Deleting --> [*]: 目录删除 磁盘空间才真正释放

这个生命周期解释了几件让人困惑的事。第一，删掉数据后磁盘没变小：旧 part 要先变 outdated，等过了 old_parts_lifetime 才删目录，期间空间是双份的。第二，system.parts 查出来的行数是实际的两倍：因为没加 WHERE active，把 outdated part 也算进去了。第三，merge 期间磁盘占用会临时翻倍，所以磁盘水位长期超过 70% 的集群在大 merge 时非常危险。第四，OPTIMIZE TABLE FINAL 会强行把一个分区合成一个 part，几百 GB 的分区执行一次可能跑几小时并把 IO 打满——它不是「优化命令」而是重写命令。

-- 1. part 数量与压缩效果：ratio 就是这张表真实的列存压缩比
SELECT database, table,
       count()                                          AS parts,
       sum(rows)                                        AS rows,
       formatReadableSize(sum(data_compressed_bytes))   AS compressed,
       formatReadableSize(sum(data_uncompressed_bytes)) AS raw,
       round(sum(data_uncompressed_bytes) / sum(data_compressed_bytes), 1) AS ratio
FROM system.parts
WHERE active            -- 漏掉这个条件，outdated part 会被算进来，数字虚高一倍
GROUP BY database, table
ORDER BY sum(data_compressed_bytes) DESC
LIMIT 10;

-- 2. 单列压缩比：用来判断哪个列该换 codec
SELECT column, type,
       formatReadableSize(sum(column_data_compressed_bytes)) AS comp,
       round(sum(column_data_uncompressed_bytes) / sum(column_data_compressed_bytes), 1) AS ratio
FROM system.parts_columns
WHERE active AND table = 'events'
GROUP BY column, type
ORDER BY sum(column_data_compressed_bytes) DESC;

-- 3. merge 是否积压：running 长期不降、elapsed 很大，说明写入批次太碎或磁盘跟不上
SELECT table, count() AS running, round(max(elapsed), 1) AS max_elapsed_s,
       formatReadableSize(sum(total_size_bytes_compressed)) AS merging_size
FROM system.merges GROUP BY table;

-- 4. 确认自己这个版本的阈值，不要照抄博客里的数字（大版本之间改过好几次）
SELECT name, value, description FROM system.merge_tree_settings
WHERE name IN ('parts_to_delay_insert', 'parts_to_throw_insert',
               'max_parts_in_total', 'old_parts_lifetime', 'index_granularity');

parts_to_delay_insert（常见默认 150）到了就开始给 INSERT 人为加延迟，parts_to_throw_insert 到了直接抛 Too many parts——这个阈值旧版本是 300，新版本放宽了不少，但含义没变：它几乎总是在说「你的写入批次太小、太频繁」，而不是「ClickHouse 扛不住」。

稀疏主键索引：8192 行一个标记的取舍

ClickHouse 的主键索引是稀疏的：每 index_granularity（默认 8192）行取一个标记，记下这个 granule 起始行的主键值，写进 primary.idx。10 亿行的表只有约 12.2 万个标记，假设主键三列合计 20 字节，整个索引不到 3 MB，可以常驻内存。查询时对 primary.idx 做二分，定位出可能命中的 granule 区间，再通过 .mrk 标记文件换算成每个列文件里的偏移，只解压那几个压缩块。

代价也很直接：索引只能定位到 granule，不能定位到行。哪怕只要一行，也必须把那个 granule 的相关列段完整读出来再逐行过滤，最小读取放大就是 8192 行。这和 InnoDB 的稠密索引是完全不同的取舍——一个用极小的索引换扫描效率，一个用较大的索引换精确定位。

索引项粒度每 8192 行 1 项叶子节点每行 1 项
10 亿行的索引体积约 2~5 MB，常驻内存GB 量级，靠 Buffer Pool 换页
能定位到granule 区间，之后顺序扫精确到行
单行点查代价至少读一个 granule 的列段3~4 次页访问直接命中
数据物理顺序必须等于 ORDER BY聚簇索引有序，二级索引另存一份
二级索引没有真正的二级索引，只有「只能加速不能保证」的跳数索引可建多个，各自完整有序，代价是回表
单行更新重写整个 part 的相关列文件就地更新 + undo / redo
深入阅读本文B+树树高推演、回表与 MVCC 详见站内 MySQL 篇

ORDER BY 是最重要的设计决策，而且与 OLTP 直觉相反

在 MySQL 里建错索引可以补建一个，数据物理顺序不受影响。ClickHouse 不行：ORDER BY 决定的是数据在磁盘上的物理排列，它直接决定了能裁掉多少 granule，而改动它基本等于重建表（新版本支持给 ORDER BY 末尾追加列，但不能改前缀、不能重排）。所以它是建表时最贵的一个决定。

原则是低基数、高频过滤的列放在前面，最后再跟一个用于范围过滤的列（通常是时间）。这和 OLTP 的索引直觉正好相反：在 MySQL 里我们被反复教育「选择性高、基数大的列放前面」，因为那样一次树搜索就能把结果集缩到很小；而在 ClickHouse 里，把 user_id 这种上亿基数的列放第一位，会让数据按 user_id 彻底打散，任何按时间或按维度的查询都无法裁剪，几乎每个 granule 都得读。判断标准不是「这个列能筛掉多少行」，而是「按这个列排序后，同一个筛选条件命中的数据能不能挤在连续的少数 granule 里」。

分区与跳数索引：粗粒度裁剪和只能加速的二级过滤

PARTITION BY 和 ORDER BY 分工明确：分区是目录级的物理隔离，负责粗粒度裁剪和数据生命周期管理（按分区 DROP 一整月数据是元数据操作，秒级完成，而 DELETE 是重写）；ORDER BY 负责分区内部的细粒度排序。分区绝对不能按高基数列分：按 user_id 分区会产生上亿个目录，每个目录里只有几行数据，part 数量瞬间爆炸，merge 永远追不上，写入直接被 Too many parts 打死。分区总数控制在几十到几百个是健康的，单个分区 10~50 GB 比较合适。

跳数索引（data skipping index）是唯一的二级过滤手段，它的定位必须说清楚：它只能加速，不能保证。它不是倒排索引，不能告诉你数据在哪，只能回答「这个 granule 有没有可能包含目标值」。回答「没有」就跳过，回答「可能有」就照常读。所以它在最坏情况下是纯开销——索引读了，一个 granule 也没排除掉。

GRANULARITY 参数容易理解错：GRANULARITY 4 指的是「每 4 个 granule 聚成一个索引块」，也就是索引粒度是 4 × 8192 = 32768 行。值越大索引越小但过滤越粗，值为 1 时索引最细也最占空间。默认值是 1，实践中高基数列的 bloom_filter 常用 2~4。

最容易踩的坑

❌
这些坑几乎每个团队都会踩一遍
  • 单条 INSERT 循环写入：最常见的错误用法。每条至少一个 part，很快就 Too many parts。批量写、或打开 async_insert，没有第三条路。
  • ORDER BY 第一列放了 user_id 这类高基数列：数据被彻底打散，任何查询都裁不掉 granule，性能退回全表扫。低基数、高频过滤的列才放前面。
  • PARTITION BY 用了高基数表达式：按 user_id 或按秒分区会产生海量目录，part 爆炸、merge 追不上、写入被拒。分区总数控制在几十到几百。
  • 以为 ALTER TABLE UPDATE 是行更新：它是异步 mutation，会重写整个 part 涉及的列文件，几百 GB 的分区改一行可能跑几小时，而且没有事务回滚。
  • 把 OPTIMIZE TABLE FINAL 当例行优化：它强制把分区合成一个 part，大分区上会打满磁盘 IO 并让写入卡住。只在明确需要去重或收缩时手动执行。
  • 查 system.parts 忘了 WHERE active：outdated part 被算进来，行数和体积都虚高一倍，然后误判「数据写重了」。
  • 删数据后发现磁盘没变小：旧 part 要等 old_parts_lifetime（默认 480 秒）才真正删目录，merge 过程中磁盘还会临时翻倍。磁盘水位长期超过 70% 很危险。
  • 给所有列无脑套 ZSTD 高等级：写入 CPU 飙升、扫描时解压变成新瓶颈。热数据留 LZ4，冷数据和大文本才上 ZSTD(3) 以上。
  • 把 LowCardinality 用在高基数列上：基数超过十万后字典维护成本吃掉全部收益，反而比普通 String 更慢、更占空间。
  • 指望跳数索引像 MySQL 二级索引一样兜底：它只能排除 granule、不能定位数据，最坏情况是白付索引开销。而且 ADD INDEX 之后不 MATERIALIZE，存量数据根本不走索引。
  • 把 MySQL 的 join 写法直接搬过来：ClickHouse 的右表要整体进内存，两张大表 join 会直接 OOM。先想能不能打成宽表或换成字典。
  • 用它顶在线业务的高并发点查：单查询吃满多核的设计决定了它并发能力弱，QPS 上千的点查必须前面挡一层缓存，或者干脆换存储。
