ClickHouse 深度原理：为什么OLAP这么快？

🏷️ ClickHouse

ClickHouse 单表查询能比 MySQL 快 100 倍，是 OLAP 领域最快的开源数据库。为什么这么快？因为列式存储 + 向量化执行。这篇讲透底层原理。

核心原理1：列式存储原理：为什么快 100 倍？

MySQL 是行式存储，查 100 万行的 3 个字段，要把整行都读出来。ClickHouse 列式存储，每个列单独存，只读需要的列，磁盘 IO 少 10 倍。

flowchart TD A[存储方式] --> B[行式存储 MySQL] A --> C[列式存储 ClickHouse] B --> B1[整行存在一起] B --> B2[查3列要读所有列] C --> C1[每列单独存] C --> C2[查3列只读3列 省IO]

行式 vs 列式对比

对比项 行式存储 MySQL 列式存储 ClickHouse
存储方式 一行一行存 一列一列存
查少量列 要读整行，IO 大 只读需要的列，IO 小 10~100 倍
适合场景 OLTP 单行读写 OLAP 批量统计分析
压缩比 低，行数据杂 高，同列数据类型一样，压缩 10 倍

核心原理2：向量化执行原理

ClickHouse 不是一行一行处理，是一批一批（向量）处理，一次处理几千行，利用 CPU SIMD 指令，性能翻好几倍。

flowchart LR A[行式执行] --> B[一次一行] B --> C[循环 N 次] D[向量化执行] --> E[一次一批 几千行] E --> F[CPU SIMD 并行] F --> G[快 10 倍]

行式执行 vs 向量化执行

执行方式 原理 性能
行式执行 一次处理一行 慢，循环开销大
向量化执行 一次处理一批 快，CPU 缓存友好，SIMD 并行
编译执行 把 SQL 编译成机器码 进一步减少解释开销

核心原理3：稀疏索引原理

ClickHouse 不是每行建索引，是稀疏索引，每 8192 行建一个标记，索引很小能放内存，查找快。

flowchart TD A[稀疏索引] --> B[每8192行一个标记] B --> C[索引块] C --> D[标记1 → 行号 0] C --> E[标记2 → 行号 8192] C --> F[标记3 → 行号 16384] D --> G[查范围 先定位块 再扫块]

ClickHouse 索引类型

索引类型 原理 适用场景
主键索引 稀疏标记，每8192行一个 范围查询定位
跳数数据 跳过不需要的列 减少读取数据量
数据压缩 同列数据类型一致 压缩比高，省磁盘省 IO

新手最容易踩的坑

❌
避坑指南
  • ClickHouse 不适合频繁单行更新删除，它是 OLAP，批量插入快，更新慢
  • 不要建太多列，列存适合宽表但列太多也会影响性能
  • 高基数列不要排序键，排序键要选区分度低、经常查的列
  • 不要用 ClickHouse 当业务库，它是分析数据库，不支持事务，高并发写入不行
