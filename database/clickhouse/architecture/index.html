ClickHouse 集群架构：分片、副本与 Distributed 表

🏷️ CK 架构

关于 ClickHouse 集群，最常见的错误不是配错了参数，而是太早上集群。单机 ClickHouse 能处理的数据量远超多数人的预期，而集群会把三个新问题一次性塞给你：数据分布、跨节点查询、副本一致性。这篇讲清分片与副本的关系、ReplicatedMergeTree 到底复制什么、Distributed 表的两阶段聚合为什么会突然变慢，以及扩容时那些不会自动帮你做的事。

先把单机压到极限，再考虑集群

一台 32 核 128 GB 内存、几 TB NVMe 的机器，跑压缩后 1~2 TB 的数据、单表几百亿行是很正常的事——列存的压缩比通常在 8~15 倍，原始 20 TB 的日志压完可能只有 1.5 TB。而集群化会立刻带来额外成本：查询要跨网络汇总，Keeper 成了新的单点风险，扩分片时数据不会自动搬迁。所以正确顺序是：先调 codec 和排序键、先做冷热分层、先把单机的 IO 和 CPU 跑满，确认真的到顶了再上集群。

分片与副本是两个正交维度

这两个概念经常被混着说，但它们解决的是完全不同的问题：分片决定容量和单查询并行度，副本决定可用性和读吞吐。4 台机器可以是「4 分片无副本」（容量最大，任一台挂掉就有 1/4 数据查不到）、「2 分片 2 副本」（生产最常见）、「1 分片 4 副本」（数据量小但要求高可用和高读并发）。集群拓扑写在配置文件的 remote_servers 里，ClickHouse 不会替你决定。

ReplicatedMergeTree 复制的是 part 与 merge 任务，不是 SQL

这是最值得纠正的一个认知：ClickHouse 的复制不是把 INSERT 语句发给其他副本重放，也不是 binlog 那种逻辑日志。它的流程是：某个副本收到写入后，先在本地生成 part，然后把「这里多了一个名为 all_1_1_0 的 part，校验和是多少」这条信息写进 Keeper 的复制队列；其他副本监听到队列有新任务，主动通过 HTTP 从源副本把这个 part 的文件拉过来。merge 同理——merge 不是每个副本各自算一遍，而是由一个副本决策、把「把这几个 part 合成那一个」当作任务写进队列，其他副本要么执行同样的 merge，要么直接拉取合并结果。

这样设计的好处是各副本的 part 结构完全一致、不会因为 merge 时机不同而分叉；代价是副本之间是最终一致的：写入返回成功时，其他副本可能还没拉到数据，此时去那个副本查就会少数据。Keeper 里存的是元数据和任务队列（副本列表、part 集合、复制队列、mutation、merge 决策、各种分布式锁），不存任何业务数据，所以它的数据量很小但 QPS 很高——写入越碎，Keeper 压力越大，这是小批量写入的第二个隐性代价。

配置行为好处代价与失效场景
insert_quorum = 0（默认）写入本地成功即返回吞吐最高，写入不受其他副本影响返回成功后立刻查另一个副本可能查不到；源副本此刻宕机且 part 还没被拉走，这批数据丢失

Distributed 表：一个不存数据的视图，和它的两阶段聚合

Distributed 表引擎本身不存一个字节的数据，它只记录「集群名、库名、本地表名、分片键」，作用是把查询改写成对各分片本地表的子查询，下发、等结果、再汇总。理解它的性能只需要抓住一个问题：回传到汇总节点的是聚合中间状态，还是明细数据？前者数据量约等于分组基数，几乎不占网络；后者会把所有分片的原始行都拉到一个节点上，这个节点立刻成为瓶颈——这是分布式查询突然变慢的头号原因。

sequenceDiagram participant C as 客户端 participant I as 发起节点 持有 Distributed 表 participant S1 as 分片1 本地表 participant S2 as 分片2 本地表 C->>I: 按 app_id 分组求 sum 的查询 I->>I: 改写为对 events_local 的子查询 par 并行下发到所有分片 I->>S1: 子查询 本地分组聚合 I->>S2: 子查询 本地分组聚合 end S1-->>I: 聚合中间状态 行数约等于分组基数 S2-->>I: 聚合中间状态 行数约等于分组基数 I->>I: 二次聚合 合并各分片的中间状态 I-->>C: 最终结果 Note over I,S2: 能下推时回传的是中间状态 网络开销极小
不能下推时回传明细 发起节点的内存和网卡成为瓶颈
查询形态能否下推到分片汇总节点收到什么怎么改
GROUP BY 配 sum / count / avg / min / max能，分片本地聚合每分片一份聚合中间状态不用改，这是最理想的形态
uniq / uniqCombined（近似去重）能，HyperLogLog 状态可合并固定大小的基数估计状态不用改；能接受千分之几误差就优先用它
uniqExact / COUNT(DISTINCT x)不能，必须看到全部原值所有分片的去重值集合，可能上亿行改用 uniq；或让分片键与去重键一致，使同一 key 只落一个分片
DISTINCT 大结果集部分下推，仍需全局去重各分片去重后的明细先 GROUP BY 收敛基数，再取 DISTINCT
窗口函数基本不能，窗口要看全局有序数据明细数据先聚合到小表再开窗，别在明细上直接开窗
ORDER BY 加 LIMIT能，各分片先取 TopN 再汇总每分片 N 行不用改；但 LIMIT BY 与深分页仍会退化
两张 Distributed 表 join默认不能，右表要全量拉到每个节点右表全量见下一节：字典、GLOBAL JOIN 或共置分片

写入路径：写 Distributed 表还是直连本地表

写 Distributed 表最省事：客户端只连一个地址，分片路由由服务端按分片键算。但它有一个容易吃亏的机制——异步转发。数据先落在发起节点的本地目录里排队，再由后台线程转发给目标分片。如果目标分片长时间不可用，队列会一直堆在发起节点的磁盘上；如果这台发起节点本身坏了，队列里还没转发出去的数据就丢了。这也让「写入成功」的语义变得模糊：返回成功只代表落到了中转队列。

维度写 Distributed 表客户端直连各分片本地表（推荐）
客户端复杂度只连一个地址，无需关心拓扑要自己维护分片列表并做路由
数据落盘路径先进发起节点的转发队列，再异步送到目标分片一次网络请求直达目标分片
写入成功的含义默认只代表进了中转队列代表目标分片已生成 part
故障表现队列堆积占满发起节点磁盘；节点损坏会丢队列中数据某分片不可用时客户端直接拿到错误，可重试或降级
part 放大转发按分片切分，一批数据会被拆成多个小 part每个分片收到的就是一个完整批次
相关参数distributed_foreground_insert 开启同步转发（旧名 insert_distributed_sync），牺牲吞吐换确定性无额外参数，行为可预测
适合低频、量小、允许少量丢失的写入生产环境的主力写入链路
-- 本地表：每个分片一份数据，副本之间由 Keeper 协调
CREATE TABLE events_local ON CLUSTER ck_2s2r
(
    event_date Date,
    event_time DateTime CODEC(DoubleDelta, LZ4),
    app_id     LowCardinality(String),
    user_id    UInt64,
    amount     Decimal(18, 4)
)
ENGINE = ReplicatedMergeTree('/clickhouse/tables/{shard}/events_local', '{replica}')
-- 路径里的 {shard} 必须区分分片，{replica} 必须区分副本，否则两个副本会互相覆盖
PARTITION BY toYYYYMM(event_date)
ORDER BY (app_id, event_time);

-- 分布式表：只是视图，查询入口
CREATE TABLE events ON CLUSTER ck_2s2r AS events_local
ENGINE = Distributed(ck_2s2r, default, events_local, cityHash64(user_id));
-- 分片键的两个要求：
--   1. 分布均匀。用 toYYYYMM(event_date) 当分片键是典型错误，会让当月所有写入压在一个分片
--   2. 与高频 join / 去重的键对齐，这样同一个 user_id 只落一个分片，才能做本地 join 和精确去重

分布式 join 为什么要尽量避免

ClickHouse 的 join 实现是「右表构建 hash 表放内存，左表流式探测」，这个前提在分布式下会被放大三次。三种执行方式：

执行方式怎么执行内存与网络代价什么时候可用
普通 JOIN（右表是 Distributed 表）每个分片各自去查右表的本地部分结果错误：每个分片只看到右表的一片只有右表数据在每个分片都完整时才对
GLOBAL JOIN发起节点先把右表查成临时表，再广播给所有分片右表全量过一遍网络，且在每个分片占一份内存右表在百万行、几百 MB 以内
共置分片（colocated）两表用同一个分片键，join 完全在分片本地完成几乎无跨节点开销建表时就按 join 键分片，改不了就用不上
字典（dictGet）维表常驻每个节点内存，按 key 直接取值内存换速度，无网络维表在千万行以内、更新频率不高

所以在 ClickHouse 里，join 不是查询写法问题而是建模问题：优先把维度打平成宽表（用物化视图在写入时完成），其次把维表做成字典用 dictGet，再不行才考虑 GLOBAL JOIN，并且一定要给它加 max_bytes_in_join 之类的内存上限，否则一条 SQL 能把整个节点打 OOM。

ClickHouse Keeper、存算分离与冷热分层

早期版本必须依赖 ZooKeeper，而 ZooKeeper 在 ClickHouse 这种「高频小写入 + 大量 watch」的负载下很容易成为集群瓶颈：JVM GC 停顿、znode 数量膨胀、内存吃紧。ClickHouse Keeper 是官方用 C++ 重写的替代品，协议兼容（客户端无感）、基于 Raft、资源占用显著更低，还支持通过 clickhouse-keeper-converter 从 ZooKeeper 快照迁移。新集群没有理由再用 ZooKeeper。它可以和 clickhouse-server 混部，但生产上建议独立三节点部署，避免查询把 CPU 抢光导致 Raft 选举超时——Keeper 抖动会直接让所有副本变成只读，这是集群级故障。

另一个方向是存算分离。原生 ClickHouse 是存算一体（数据在本地盘），而 S3 磁盘和 storage_policy 让冷数据可以落到对象存储：成本可能降到本地 NVMe 的十分之一，代价是查询冷数据时的延迟明显变高（对象存储的首字节延迟在几十毫秒量级，随机小读尤其吃亏）。ClickHouse Cloud 走得更远，把存储完全放在对象存储、计算节点无状态弹性伸缩，代价是要接受托管形态与按量计费。

# /etc/clickhouse-server/config.d/storage.yaml  —— 冷热分层
storage_configuration:
  disks:
    hot:
      path: /var/lib/clickhouse/            # 本地 NVMe
    cold_s3:
      type: s3
      endpoint: https://my-bucket.s3.amazonaws.com/ck/
      access_key_id: AKIA_xxx
      secret_access_key: xxx
      # 本地缓存对象存储上的数据块，否则每次查冷数据都要走网络
      metadata_path: /var/lib/clickhouse/disks/cold_s3/
  policies:
    hot_to_cold:
      volumes:
        hot_vol:
          disk: hot
          # 单个 part 超过这个大小 直接写到下一层，避免大 part 占满本地盘
          max_data_part_size_bytes: 107374182400
        cold_vol:
          disk: cold_s3
      move_factor: 0.2                      # 本地盘剩余空间低于 20% 时开始往冷层搬

-- 建表时指定分层策略，并用 TTL 自动下沉与过期
ALTER TABLE events_local MODIFY SETTING storage_policy = 'hot_to_cold';
ALTER TABLE events_local MODIFY TTL
    event_date + INTERVAL 30 DAY TO VOLUME 'cold_vol',   -- 30 天后搬到对象存储
    event_date + INTERVAL 365 DAY DELETE;                -- 一年后删除

-- 每天都该看的四个集群健康指标
-- 1. 复制队列：queue_size 持续上升就是副本追不上；看 num_tries 和 last_exception 定位卡住的任务
SELECT database, table, replica_name, queue_size, inserts_in_queue, merges_in_queue,
       absolute_delay, last_queue_update
FROM system.replicas
WHERE queue_size > 0 OR absolute_delay > 60;

-- 2. 卡住的具体任务：反复失败的任务会堵住整个队列，后面的都不执行
SELECT database, table, type, create_time, num_tries, last_exception
FROM system.replication_queue
WHERE num_tries > 3
ORDER BY num_tries DESC LIMIT 20;

-- 3. part 数量：单分区 active part 数长期偏高，说明写入太碎
SELECT database, table, partition, count() AS parts
FROM system.parts WHERE active
GROUP BY database, table, partition
HAVING parts > 100 ORDER BY parts DESC;

-- 4. Keeper 会话与请求延迟：session_expired 持续增长说明 Keeper 不稳
SELECT event, value FROM system.events
WHERE event LIKE 'ZooKeeper%' AND value > 0;

集群运维与故障切换：哪些事 ClickHouse 不会替你做

副本层面的故障切换是自动的：Distributed 查询会跳过不可用副本（load_balancing 决定挑哪个），副本恢复后自己从队列追数据。但分片层面没有任何自动兜底：一个分片的所有副本都挂了，这个分片的数据就查不到，默认行为是整条查询报错；把 skip_unavailable_shards 设成 1 能让查询继续，但结果是不完整的——这个设置在报表场景比报错更危险，因为数字会悄悄变小。记住这条分工：副本数决定可用性，分片数决定容量与单查询并行度。

监控项查哪里健康值异常时先做什么
副本延迟system.replicas.absolute_delay持续接近 0超过几十秒先看网络与目标副本磁盘 IO，再看队列头部任务
复制队列长度system.replicas.queue_size波动但能回到个位数只涨不降说明有任务卡死，去 system.replication_queue 看 last_exception
只读副本system.replicas.is_readonly恒为 0为 1 基本都是 Keeper 会话问题，先查 Keeper 集群与网络
part 数量system.parts 按分区统计单分区几十个以内先调大写入批次，再考虑临时降低 merge 并发阈值
merge 积压system.merges 与 background pool 指标有进有出看磁盘是否打满；大 merge 期间不要再叠加 OPTIMIZE
mutation 卡住system.mutations.is_done提交后能在合理时间完成用 KILL MUTATION 取消，别让它一直重写 part
Distributed 转发队列system.distribution_queue接近 0堆积说明目标分片有问题；这也是不推荐写 Distributed 表的原因
分片数据倾斜各分片本地表行数对比差异在 10% 以内分片键选错了，需要重新分布数据，ClickHouse 不会自动均衡

扩分片是整个运维里最重的动作：新增分片后，ClickHouse 不会自动搬迁存量数据，新分片只承接新写入，老数据仍然只在老分片上。Distributed 查询依然正确（它会扫所有分片），但各分片负载长期不均。常规做法是：按分区用 FETCH PARTITION 加 ATTACH PARTITION 手工搬，或者新建一套表重新导一遍再切流量。这一点与 Doris、StarRocks 的自动均衡是明显差距，选型时要算进运维成本。

❌
集群环节最容易踩的坑
  • 为了并发 QPS 去加分片：分片提高的是单查询并行度，高并发要靠副本、缓存和预聚合。方向错了加机器也没用。
  • 只加分片不加副本：任何一个分片的机器挂掉，这部分数据就查不到。副本数决定可用性，这是两件事。
  • ReplicatedMergeTree 的 Keeper 路径写死：路径里不带 {shard}，两个分片会被认成同一份数据互相覆盖；{replica} 重复则副本互相抢同一个身份。
  • internal_replication 忘了设 true：写 Distributed 表时数据会被写进每个副本，副本间又各自复制一遍，直接产生重复数据。
  • 以为副本是强一致：默认 insert_quorum = 0，写入返回成功后马上查另一个副本可能查不到。要一致就得同时开 quorum 和 sequential consistency，并接受可用性下降。
  • 分片键用了 toYYYYMM 这类时间表达式：当月所有写入全压在一个分片，热点节点先死。分片键要高基数且均匀，常用 cityHash64(user_id)。
  • 在 Distributed 表上直接写 COUNT(DISTINCT)：无法下推，全部明细回汇总节点，内存瞬间爆掉。换 uniq，或让分片键与去重键对齐。
  • 用 Distributed 表做主力写入：异步转发队列堆在发起节点磁盘上，节点损坏就丢数据，而且一批数据被拆成多个小 part。生产直连本地表。
  • 两张 Distributed 表直接 join：不加 GLOBAL 的结果是错的（每个分片只看到右表的一片），加了 GLOBAL 则右表全量广播到每个节点，很容易 OOM。
  • Keeper 和 server 混部还不限资源：查询把 CPU 吃满导致 Raft 心跳超时，所有副本集体转只读。Keeper 独立部署三节点，节点数必须是奇数。
  • 打开 skip_unavailable_shards 当高可用方案：查询不再报错，但结果静默变少，报表数字对不上却没人发现，比直接失败危险得多。
  • 以为加了分片会自动重平衡：存量数据不会搬，需要手工 FETCH 加 ATTACH PARTITION 或重导一遍。扩容窗口要预留足够时间。
