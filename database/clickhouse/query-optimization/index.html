ClickHouse 查询优化：granule 裁剪、PREWHERE、JOIN 与预聚合

🏷️ CK 查询优化

ClickHouse 的查询优化没有一堆技巧，只有一条原则：让引擎少读 granule。一个 granule 默认覆盖 8192 行，是 ClickHouse 读取数据的最小单位——哪怕你只要一行，也要把它所在 granule 的相关列全部解压出来。后面所有手段，分区裁剪、主键前缀、跳数索引、PREWHERE、预聚合，都是这条原则的推论。至于列存为什么扫描快、稀疏索引的 mark 文件长什么样，详见站内《ClickHouse 架构与核心特性》，这里只用结论。

所有优化都是同一件事：少读 granule

一次 SELECT 到达存储层后，数据量是被逐级砍掉的。每一级砍掉的比例可以直接观测，所以优化不该靠猜：先定位是哪一级没起作用，再针对那一级改。

💡
判断优化是否有效的唯一硬指标不是耗时

同一条 SQL 第二次跑总是更快，因为页缓存命中了，这会让人误判优化生效。唯一可信的指标是 read_rows 和 read_bytes 的下降：这两个数字与缓存无关，只反映真实扫描量。优化前后各跑一次，从 system.query_log 里取这两列做对比；如果读取量没变而耗时变短了，你什么都没优化，只是把数据读进了缓存。

先量化：EXPLAIN 与 query_log 怎么读

-- 1) 看主键到底裁掉了多少 granule，这是最有信息量的一条命令
EXPLAIN indexes = 1
SELECT count() FROM events
WHERE tenant_id = 42 AND event_time >= '2026-09-01 00:00:00' AND event_time < '2026-09-02 00:00:00';
/* 关键输出片段的判读方式：
   Indexes:
     MinMax          -- 分区级 minmax，Parts 从 24 降到 1 说明分区裁剪生效
       Parts: 24/1
     PrimaryKey
       Keys: tenant_id, event_time
       Parts: 1/1
       Granules: 9184/12     -- 左边是候选 granule 总数，右边是实际要读的
   如果 Granules 两个数字接近，说明主键根本没起作用，往下看失效原因表。
   如果 Indexes 里完全没有 PrimaryKey 条目，说明 WHERE 一个前缀列都没命中。 */

-- 2) 看执行管道与并行度：Resize 之前的 stream 数就是实际并行线程数
EXPLAIN PIPELINE SELECT event_type, count() FROM events GROUP BY event_type;

-- 3) 慢查询排行 + 读取量，这个 SQL 建议直接存成运维书签
SELECT
    normalized_query_hash,
    any(substring(query, 1, 120))                AS sample,
    count()                                      AS cnt,
    round(avg(query_duration_ms))                AS avg_ms,
    formatReadableQuantity(avg(read_rows))       AS avg_read_rows,
    formatReadableSize(avg(read_bytes))          AS avg_read_bytes,
    formatReadableSize(max(memory_usage))        AS peak_mem,
    round(avg(read_rows) / greatest(avg(result_rows), 1)) AS rows_per_result  -- 读放大倍数
FROM system.query_log
WHERE type = 'QueryFinish' AND event_time > now() - INTERVAL 1 DAY AND query_kind = 'Select'
GROUP BY normalized_query_hash
ORDER BY sum(query_duration_ms) DESC   -- 按总耗时排，而不是按单次最慢排
LIMIT 20;

-- 4) 定位「读得最多」而不是「跑得最久」的查询，这类才是真正拖垮集群的
SELECT substring(query, 1, 100) AS q, read_rows, read_bytes, query_duration_ms, memory_usage
FROM system.query_log
WHERE type = 'QueryFinish' AND event_time > now() - INTERVAL 1 HOUR
ORDER BY read_bytes DESC LIMIT 10;

主键裁剪为什么失效

ClickHouse 的主键是稀疏索引，只能做前缀范围定位，它比关系库的 B+ 树更挑食。下面这些写法在 MySQL 里也许还能勉强走索引，在 ClickHouse 里则是直接退化成全表扫。

失效写法为什么失效正确写法
只过滤了 event_time，而排序键是 (tenant_id, event_type, event_time)跳过了前缀列，稀疏索引无法定位区间补上 tenant_id；确实无法补时，给 event_time 加 minmax 跳数索引
WHERE toDate(event_time) = '2026-09-01'对主键列套函数，索引表达式对不上改成半开区间 event_time >= '2026-09-01 00:00:00' AND event_time < '2026-09-02 00:00:00'
WHERE tenant_id = '42'（列是 UInt32）字符串与整数比较触发隐式转换，索引失效参数类型与列类型严格对齐，用 toUInt32(42) 明确表达
WHERE tenant_id = 42 OR country = 'CN'OR 跨列后条件无法收敛成前缀区间拆成两段 UNION ALL，或把高频维度并入排序键
WHERE event_time BETWEEN '2026-09-01' AND '2026-09-02' 但列是字符串字符串比较是字典序，跨月跨年就错时间列一律用 DateTime，不要用 String 存时间
WHERE event_type LIKE '%click%'前导通配符无法用前缀定位改成前缀匹配 LIKE 'click%'，或加 ngrambf 跳数索引
WHERE user_id IN (SELECT ...) 且 user_id 不在主键里非主键列没有索引可用加 bloom_filter 跳数索引，或走字典 / 宽表打平

分区裁剪遵守同一逻辑，但判断标准更严格：过滤条件必须能推导出分区表达式的取值。如果分区键是 toYYYYMM(event_date)，那么 WHERE event_date >= '2026-09-01' AND event_date < '2026-10-01' 可以被推导出属于 202609 这一个分区；而 WHERE toString(event_date) LIKE '2026-09%' 推导不出来，于是扫全部分区。把时间条件写成半开区间是最稳的写法，它同时满足分区裁剪和主键裁剪，而 BETWEEN 的闭区间在跨天边界上还容易多算一秒的数据。

PREWHERE：先读便宜的列，再读贵的列

PREWHERE 是列存独有的优化：先只读过滤列判断哪些行命中，再按命中行去读其余列。ClickHouse 默认开启 optimize_move_to_prewhere，会自动把部分条件搬过去，但它的启发式基于列大小估算，两种场景下需要手写：一是过滤性最强的条件涉及函数或多个列，优化器不敢搬；二是表里有超大列（长 JSON、日志原文），此时哪怕过滤列筛掉的行不多，避免读大列的收益也极大。

-- 反例：props 是几 KB 的 JSON 列，条件在 status 上，自动优化未必把它搬到 PREWHERE
SELECT event_id, props FROM events
WHERE tenant_id = 42 AND status_code = 500;

-- 手写 PREWHERE：先只解压 status_code 这一列，命中的行才去读 props
SELECT event_id, props FROM events
PREWHERE status_code = 500          -- 过滤性强且列很窄，放这里最划算
WHERE tenant_id = 42;               -- 主键前缀条件留在 WHERE，用于 granule 裁剪
-- 判断标准：用 EXPLAIN actions=1 对比两种写法的 read_bytes，通常能降一个数量级

-- 想确认自动优化搬了哪些条件
SET optimize_move_to_prewhere = 1;
EXPLAIN actions = 1 SELECT event_id, props FROM events WHERE tenant_id = 42 AND status_code = 500;

-- 去重查询：用 argMax 替代 FINAL，把归并变成一次聚合
-- FINAL 需要跨 part 做排序归并，高并发下 CPU 很快打满
SELECT
    order_id,
    argMax(status, version)  AS status,     -- 取 version 最大那一行的 status
    argMax(amount, version)  AS amount,
    max(version)             AS version
FROM orders                                  -- ReplacingMergeTree 表，不加 FINAL
WHERE tenant_id = 42
GROUP BY order_id
HAVING argMax(is_deleted, version) = 0;      -- 顺带过滤掉逻辑删除的行

JOIN：ClickHouse 最痛的地方

这是从关系库转过来的人踩得最惨的一点：ClickHouse 默认的 hash join 会把右表全量读进内存建哈希表，而且优化器不会替你自动调换左右顺序。在 MySQL 或 PostgreSQL 里，优化器基于统计信息选择驱动表，小表自动做内表；在 ClickHouse 里你写错顺序，就是把大表塞内存然后 OOM。记住一句话：小表永远放右边。

每个分片各自执行一遍 I->>S1: 下发查询, 含右表子查询 I->>S2: 下发查询, 含右表子查询 S1->>S1: 本地执行右表子查询, 只看到本分片数据 S2->>S2: 本地执行右表子查询, 只看到本分片数据 Note over S1,S2: 维度表若不是每节点全量的话
这里结果就是错的 S1-->>I: 返回部分结果 S2-->>I: 返回部分结果 I-->>C: 结果可能偏少 Note over I: GLOBAL JOIN 的差别是
先在发起节点算出右表
再把整个结果集广播给每个分片 Note over I: 正确但要付一次网络广播
右表几百万行时这一步就是瓶颈
替代手段怎么做适用场景代价与限制
dictGet 查字典把维度表定义成 Dictionary，查询里用 dictGet 取属性维表能放进内存（百万到千万行级）占常驻内存，更新有延迟，字典重载期间查询仍用旧值
宽表打平ETL 阶段把维度属性写进事实表维度属性变化很少维度改名要回刷历史数据，存储变大
IN 子查询WHERE user_id IN (SELECT id FROM dim WHERE ...)只需要过滤，不需要取维表的列子查询结果集要能放内存，几百万行以上就危险
GLOBAL JOIN / GLOBAL IN分布式查询里强制先算右表再广播分布式表 join 非全量分布的维表一次全量网络广播，右表大时代价极高
预聚合物化视图把 join 结果提前算好落成一张表固定报表、固定维度组合只对新写入数据生效，维度组合变更要重建
分布式表加 Join 引擎表右表用 Join 引擎常驻内存复用同一个右表被反复 join内存常驻，且写入语义特殊，容易被遗忘造成内存泄漏式增长
-- 用字典彻底消掉维表 join：定义一次，全集群可用
CREATE DICTIONARY dict_user
(
    user_id   UInt64,
    nickname  String,
    city      String,
    level     UInt8
)
PRIMARY KEY user_id
SOURCE(CLICKHOUSE(TABLE 'dim_user' DB 'ods'))   -- 也可以直接 MYSQL(...) 从源库拉
LAYOUT(HASHED())                                 -- 内存哈希布局，百万级最常用
LIFETIME(MIN 600 MAX 900);                       -- 10 到 15 分钟随机过期，避免所有字典同时重载

-- 查询侧：没有 join，没有内存哈希表，扫描时逐行查字典
SELECT
    dictGet('dict_user', 'city', user_id)  AS city,
    count()                                AS pv,
    uniqCombined(user_id)                  AS uv
FROM events
WHERE tenant_id = 42
  AND event_time >= '2026-09-01 00:00:00' AND event_time < '2026-09-08 00:00:00'
GROUP BY city
ORDER BY pv DESC;

-- 字典是否真的加载成功、占了多少内存、有没有加载失败
SELECT name, status, element_count, formatReadableSize(bytes_allocated) AS mem,
       last_successful_update_time, last_exception
FROM system.dictionaries;

聚合与去重的内存账

GROUP BY 的内存占用与分组基数成正比，与扫描行数关系不大。按 event_type 分组只有几十组，按 user_id 分组就是几千万组，后者会把哈希表撑爆。两个兜底开关：max_bytes_before_external_group_by 允许聚合落盘（建议设为 max_memory_usage 的一半），max_bytes_before_external_sort 对排序同理。落盘意味着慢，但比查询直接失败好。

去重函数算法误差内存量级（千万基数）什么时候用
uniqExact精确哈希集合0几 GB，随基数线性增长财务对账、必须精确的口径
uniq自适应，小基数精确、大基数 HLL约 0.5% 到 2%几 MB默认选择
uniqCombined数组 + 哈希表 + HLL 三段式约 0.8%比 uniq 更省，速度更快大基数 UV 统计的首选
uniqCombined64同上，64 位哈希同上同上基数超过 40 亿时必须用它
uniqHLL12固定 HLL约 1.6%固定几 KB内存极度受限、基数极大
uniqThetaTheta Sketch约 3%小需要对草图做交并差运算
✅
能用近似就别用精确，这是 OLAP 的基本常识

一个日活看板显示 1023 万还是 1025 万，对决策没有任何影响，但 uniqExact 与 uniqCombined 之间可能是几 GB 内存和几十倍耗时的差距。真正需要精确值的只有对账类场景，而那类场景通常数据量也小。另外 argMax、anyHeavy、quantileTDigest 这类组合与近似函数也被严重低估：argMax(status, version) 一次聚合就替代了「取每个 key 最新一行」这种通常要写窗口函数或自连接的需求。

预计算：物化视图与 PROJECTION

ClickHouse 的物化视图不是定时刷新的视图，而是一个插入触发器。每次向源表写入一个数据块，物化视图的 SELECT 就在这个块上执行一次，结果追加到目标表。由此可以推出三条必然结论：它只对新写入的数据生效，历史数据必须手动回填；它看不到源表已有的数据，所以 JOIN 在 MV 里语义很危险；源表的 DELETE 和 UPDATE 不会传递到视图。

只作用于这一个块"] M --> T2["写入 AggregatingMergeTree 聚合表"] end subgraph R["读取路径"] Q["报表查询"] --> T2 T2 --> F["-Merge 函数合并聚合状态"] end subgraph X["不会发生的事"] N1["历史数据不会自动进入视图"] N2["源表 DELETE 不会同步到视图"] N3["视图不是定时任务, 没有调度"] end 
-- 从明细表到分钟级聚合视图的完整三段
-- 1) 聚合表：数值用 SimpleAggregateFunction，需要状态的用 AggregateFunction
CREATE TABLE events_1m
(
    tenant_id  UInt32,
    event_type LowCardinality(String),
    ts_minute  DateTime,
    pv         SimpleAggregateFunction(sum, UInt64),          -- sum 可交换可结合，用 Simple 更省
    uv_state   AggregateFunction(uniqCombined, UInt64),        -- uniq 必须存中间状态
    p95_state  AggregateFunction(quantileTDigest, UInt32),
    revenue    SimpleAggregateFunction(sum, Decimal64(4))
)
ENGINE = AggregatingMergeTree
PARTITION BY toYYYYMM(ts_minute)
ORDER BY (tenant_id, event_type, ts_minute);

-- 2) 物化视图：注意写入侧用 -State 后缀
CREATE MATERIALIZED VIEW mv_events_1m TO events_1m AS
SELECT
    tenant_id,
    event_type,
    toStartOfMinute(event_time)         AS ts_minute,
    count()                             AS pv,
    uniqCombinedState(user_id)          AS uv_state,
    quantileTDigestState(duration_ms)   AS p95_state,
    sum(revenue)                        AS revenue
FROM events
GROUP BY tenant_id, event_type, ts_minute;

-- 3) 回填历史：视图建好之后才生效，历史必须自己灌，且要按分区分批避免一次性 OOM
INSERT INTO events_1m
SELECT tenant_id, event_type, toStartOfMinute(event_time) AS ts_minute,
       count(), uniqCombinedState(user_id), quantileTDigestState(duration_ms), sum(revenue)
FROM events
WHERE event_time >= '2026-08-01 00:00:00' AND event_time < '2026-09-01 00:00:00'
GROUP BY tenant_id, event_type, ts_minute;

-- 查询侧：读取必须配对使用 -Merge，否则拿到的是二进制状态而不是数字
SELECT
    toStartOfHour(ts_minute)              AS hour,
    sum(pv)                               AS pv,
    uniqCombinedMerge(uv_state)           AS uv,        -- 跨分钟合并 HLL 草图，结果仍然正确
    quantileTDigestMerge(0.95)(p95_state) AS p95_ms
FROM events_1m
WHERE tenant_id = 42 AND ts_minute >= today() - 7
GROUP BY hour ORDER BY hour;
维度物化视图PROJECTION
存储位置独立的表，可单独查询、单独设 TTL藏在源表的 part 目录里，跟随 part 生命周期
查询方式必须显式查视图表优化器自动选择，原 SQL 不用改
历史数据手动回填MATERIALIZE PROJECTION 后台自动物化
能否换排序键可以，视图就是新表可以，这是它最大的价值（一张表两种排序）
一致性源表删数据不会同步，可能长期偏差与源表 part 强绑定，删分区一起消失
失效风险视图 SQL 报错会阻塞源表写入不影响写入，但会增加写放大
适用跨表、复杂聚合、需要独立生命周期同一张表换一种排序键或加一层聚合

习惯性加 FINAL每次查询都做跨 part 归并排序换 GROUP BY 加 argMax；必须用时开 do_not_merge_across_partitions_select_final
把 LIMIT 当优化手段聚合查询里 LIMIT 不能下推，聚合仍要算全量先用 WHERE 缩小范围，再 LIMIT
在 GROUP BY 里放高基数列哈希表随基数线性膨胀直至 OOM先过滤再聚合；或换近似函数、上预聚合表

最容易踩的坑

❌
查询优化的十条高频翻车点
  • 只看耗时判断优化效果：第二次跑快是页缓存命中，必须比 read_rows 和 read_bytes。
  • 以为 ClickHouse 会自动调整 join 顺序：它不会，大表放右边就是把大表读进内存，直接 OOM。
  • 对主键列套函数：toDate(event_time) = ... 一写，granule 裁剪立刻归零，换成半开区间即可恢复。
  • 参数类型与列类型不一致：给 UInt32 列传字符串常量，隐式转换让索引静默失效，EXPLAIN 里看不到明显报错。
  • 以为物化视图会补历史：它只对建视图之后写入的块生效，历史数据要按分区分批手动回填。
  • 在物化视图里写 join：MV 只能看到当前插入的块，join 右表的时点不可控，结果随写入节奏漂移。
  • AggregateFunction 列读取时忘了 -Merge：查出来是一串二进制，或者被误当成已聚合值直接 sum，口径全错。
  • 无脑用 uniqExact：报表场景多花几 GB 内存换来无人关心的精度。
  • 跳数索引当主键索引用：它只能排除 granule，不能定位行，选择性差的列上加了等于白加还多一份写放大。
  • 拿 ClickHouse 承接高并发点查：它的设计目标是少量大查询，几千 QPS 的单行查询会让 CPU 全花在解压上。
