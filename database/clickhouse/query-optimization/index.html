查询优化与分区

🏷️ ClickHouse,查询优化

查询慢了先别急着加机器

ClickHouse 本身够快，但不代表你随便写个 SQL 都快。我见过最离谱的一条查询：业务方在一张五亿行的表上 SELECT count(*) FROM t WHERE url LIKE '%xxx%'，跑了四十秒，还把整个节点的 CPU 打满。这种问题加机器没用，得先搞清楚它扫了多少数据、用没用到索引。这篇就是我的排查工具箱。

EXPLAIN：先看查询计划

和 MySQL 一样，ClickHouse 也有 EXPLAIN。但它的输出更详细，能看到读了多少分区、跳过了多少 part：

EXPLAIN header = 1, actions = 1
SELECT toStartOfHour(event_time) AS hour, count()
FROM event_log
WHERE event_time >= '2026-09-15' AND event_time < '2026-09-16'
  AND event_type = 'click'
GROUP BY hour;

重点看几样东西：ReadFromMergeTree 节点里的 Parts 读了几个、Granules 跳过了多少。理想情况下，时间范围应该只命中当天那一个分区，granule 跳过率很高。如果 Parts 读了一堆、Granules 几乎没跳，说明你的过滤条件没走到索引或分区。

主键索引：稀疏索引怎么用

上一篇讲过，ClickHouse 的主键索引是稀疏的——每 8192 行（index_granularity）才记一条索引项。这意味着它不是精确找一行，而是"跳过一整块不相关的数据"。

主键索引生效的前提是：WHERE 条件能命中 ORDER BY 的最左前缀。比如 ORDER BY (event_type, event_time)：

-- 走主键索引：event_type 等值 + event_time 范围
SELECT ... FROM event_log
WHERE event_type = 'click'
  AND event_time >= '2026-09-15';

-- 不走主键索引：跳过了 event_type 直接查 event_time
SELECT ... FROM event_log
WHERE event_time >= '2026-09-15';

第二条虽然也能靠分区裁剪干掉大部分数据，但 part 内部的主键索引用不上。这就是为什么 ORDER BY 第一列要选高频等值过滤列。

跳数索引：主键覆盖不到的字段怎么办

主键索引只能服务 ORDER BY 前缀。但你可能还想按 url、user_id、city 这些字段过滤——它们不在 ORDER BY 里。这时候用跳数索引（Data Skipping Index）。

ALTER TABLE event_log
ADD INDEX idx_url bloom_filter(url)
TYPE bloom_filter(0.01)
GRANULARITY 4;

ALTER TABLE event_log
ADD INDEX idx_user minmax(user_id)
TYPE minmax
GRANULARITY 4;
索引类型适合字段过滤效果
minmax数值/时间范围记录 granule 内 min/max
set(N)低基数字符串/枚举记录 granule 内 distinct 值
bloom_filter等值过滤的高基数列bitmap 判断值是否可能存在
ngrambf_v1文本 LIKE 模糊匹配n-gram 布隆过滤

跳数索引不是建完立刻生效——它在建表时对已有数据不会自动建索引，要 MATERIALIZE 或等后台 merge。新写入的数据会自动带上。

跳数索引别贪多

每加一个跳数索引，写入和存储都有额外开销。我见过有人给十几个字段全加 bloom filter，写入吞吐掉了 40%。原则：只给那些"高频过滤、又不在主键里"的字段加，加完用 EXPLAIN 确认真的跳过了数据再保留。

分区裁剪：最划算的优化

分区裁剪（Partition Pruning）是成本最低、收益最大的优化——只要 WHERE 里带上了分区键（通常是时间），ClickHouse 直接不读其他分区的数据。

-- 按天分区，带 event_time 范围：只读 20260915 这一个分区
SELECT count() FROM event_log
WHERE event_time >= '2026-09-15 00:00:00'
  AND event_time <  '2026-09-16 00:00:00';

-- 忘了带时间：扫全部 90 天分区，慢 90 倍
SELECT count() FROM event_log;

检查分区裁剪有没有生效，查 system.query_log 或 EXPLAIN 里的 SelectedParts。我的经验：所有线上查询必须带时间范围，哪怕业务说"查全部"，也至少给个近 30 天的默认窗口。

物化视图：把查询预算提前算好

物化视图（Materialized View）是 ClickHouse 做预聚合的核心武器。它不是普通视图——数据真的物理存在另一张表上，新数据写入明细表时自动触发聚合。

-- 按小时预聚合的报表底表
CREATE MATERIALIZED VIEW mv_event_hourly
ENGINE = SummingMergeTree
PARTITION BY toYYYYMMDD(hour)
ORDER BY (hour, event_type)
AS
SELECT
    toStartOfHour(event_time) AS hour,
    event_type,
    count() AS pv,
    uniqState(user_id) AS uv_state
FROM event_log
GROUP BY hour, event_type;

-- 查报表直接走预聚合表，毫秒返回
SELECT hour, pv, uniqMerge(uv_state) AS uv
FROM mv_event_hourly
WHERE hour >= '2026-09-15 00:00:00'
GROUP BY hour, pv
ORDER BY hour;

注意 uniqState / uniqMerge 这对组合——聚合中间状态不直接存 UV 数字，而是存一个可合并的近似去重状态（HLL），查询时再 merge。这样不同批次的数据合并时 UV 依然准确。

Projection：自动选最佳排序

24.x 之后 Projection（投影）是个很香的特性。它允许你对同一张明细表额外维护一个"按另一套 ORDER BY 排序的物理副本"，查询时优化器自动判断用哪个排序更快，对业务透明。

ALTER TABLE event_log
ADD PROJECTION proj_by_user
(
    SELECT user_id, event_time, event_type
    ORDER BY user_id
);

比如你一张表按 (event_type, event_time) 排序，但偶尔又要按 user_id 查"某用户的所有事件"——这种查询原本要全表扫。加了 proj_by_user，优化器自动走按 user_id 排序的投影，查询快几个数量级。代价是多一份存储和写入开销。

Projection 不是银弹

Projection 会让写入变慢、存储翻倍。一个表挂三四个 Projection，写入吞吐可能腰斩。我的原则：先确认这个查询真的高频且慢，再上 Projection。低频偶发的查询，宁可让它慢一点，也别拖累写入。

GROUP BY 优化

聚合是 ClickHouse 的主场，但 GROUP BY 也有坑。最常见的是聚合键基数太高，内存爆掉：

-- 按 user_id 聚合，亿级用户，中间状态能把内存吃满
SELECT user_id, count() FROM event_log
WHERE event_time >= '2026-09-01'
GROUP BY user_id;

解决办法：让 ClickHouse 把溢写数据落盘。关键设置：

-- 内存超过 1GB 就溢写磁盘，避免 OOM
SET max_bytes_before_external_group_by = 1000000000;
SET max_memory_usage = 10000000000;  -- 单查询 10GB 上限

另外 GROUP BY 的列尽量和 ORDER BY 对齐——数据已经按那列排好序了，聚合就是顺序扫描，不用建大哈希表。这就是为什么把高频聚合列放进 ORDER BY 这么重要。

并发查询与资源控制

ClickHouse 是"少并发、大批量"的引擎。你同时塞 100 个大查询进来，每个都抢 CPU 和内存，全变慢。生产上要做并发控制：

参数作用我的建议
max_concurrent_queries节点最大并发查询数CPU 核数 ×2，别盲目调大
max_memory_usage单查询内存上限物理内存 1/4，防单查询吃满
max_threads单查询并行线程数= CPU 核数
queue_max_wait_ms排队等待超时让慢查询排队而不是挤爆

慢查询排查流程

线上遇到慢查询，我按这个顺序查：

  1. 查 query_log：SELECT query, query_duration_ms, read_rows, read_bytes FROM system.query_log WHERE ... ORDER BY query_duration_ms DESC LIMIT 20。看 read_rows 是不是远大于预期行数。
  2. 看分区裁剪：EXPLAIN 看读了几个分区。read_rows 大往往是没带时间条件。
  3. 看是否用了索引：EXPLAIN 里 granule 跳过率。没跳过就是过滤列不在主键/跳数索引里。
  4. 看是否溢写磁盘：read_from_disk 标志位。GROUP BY/JOIN 中间数据落盘就慢了，调大内存上限或优化聚合键。
  5. 看是不是大表 JOIN：ClickHouse 不擅长多表大 JOIN。能预聚合到一张表就别 JOIN。

FAQ

Q：为什么我的查询 EXPLAIN 显示读了全部分区？
大概率 WHERE 里没带分区键（event_time），或者分区键表达式和 WHERE 对不上。比如 PARTITION BY toYYYYMMDD(event_time)，但你 WHERE 里写的是 toDate(ts) 另一个字段，ClickHouse 认不出来。分区键必须和 WHERE 里的表达式能对上。

Q：物化视图建了之后，历史数据会补吗？
不会。物化视图只对建视图之后新写入的数据生效。要补历史，得手动 INSERT INTO mv SELECT ... FROM 明细表 回填。

Q：uniq 为什么结果不准？
uniq 和 uniqCombined 是近似去重（基于 HLL），有 1%~2% 误差。要精确用 uniqExact，但它吃内存。报表场景近似就够，财务对账才上 exact。

我的结论

ClickHouse 查询优化的核心就一句话：少扫数据。分区裁剪让你不读无关分区，主键索引让你不读无关 granule，跳数索引让你不读无关列块，物化视图和 Projection 让你直接读预聚合结果。剩下的就是控制并发和内存，别让一个慢查询把整个节点拖垮。下一篇我们把这些优化手段放到真实业务场景里，看看日志分析和实时报表怎么搭。
