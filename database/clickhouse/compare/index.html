OLAP 引擎选型：ClickHouse vs Doris vs Trino vs 云数仓

🏷️ CK 对比

OLAP 选型最常见的失败模式是「拿基准测试当结论」：看到某个引擎单表扫描跑赢十倍就定下来，上线后发现真实需求是三张表 join、要支持实时更新、还有几百并发的看板刷新——而这几项恰好是那个引擎最弱的地方。这篇先把 OLAP 引擎分成三个流派讲清各自的设计目标，再给出可决策的能力矩阵，最后落到几组具体的二选一和一棵决策树。

  • ① 用法：一套可执行的四步筛选流程（数据量 → 查询形态 → 更新需求 → 并发与运维能力），配从查询日志里量化这四项输入的 SQL、三个主流引擎的能力边界对照，以及「选错之后最先撞墙的地方」。
  • ② 原理：三大流派为什么能力边界不同、六类引擎的能力矩阵、ClickHouse 与 Doris 及 Elasticsearch 的逐项差异、为什么 OLAP 引擎顶不了 OLTP、实时数仓分层各层该用什么、自建与按量计费的成本结构差异。
  • ③ 场景：完整的选型决策树、已经选错之后有哪些退路与各自代价，以及什么情况下根本不需要引入 OLAP 引擎。

① 用法 · 四步筛出候选引擎

选型不要从「谁更快」开始，要从「淘汰谁」开始。下面四步每一步都有可量化的输入，走完通常只剩一到两个候选，再拿真实数据做 POC。顺序不能换：数据量决定要不要上 OLAP，查询形态和更新需求决定能不能用 ClickHouse，并发与运维能力决定自建还是托管。

第几步问清什么怎么量化这一步淘汰谁
1 · 数据量与增量最大的那张表压缩后多大、每天增量多少行、要保留多久看现有库的表体积与日增行数，估算一年后的规模单表千万行以内、报表能预先算好：淘汰全部 OLAP 引擎，一张定时刷新的汇总表或只读从库就够
2 · 查询形态生产里跑得最多的十条 SQL 里，单表过滤聚合与多表 join 各占多少用下面的 SQL 数查询日志里带 join 的比例，别靠印象join 占比超过三成：淘汰 ClickHouse，它没有成熟的代价优化器，也不会替你调换左右表
3 · 更新需求数据写完还会不会改、是否要与业务库主键保持一致看是否存在 CDC 链路、是否有按主键覆盖的语义要求需要行级 upsert 与 delete：淘汰 ClickHouse 与 Trino，走 Doris 或 StarRocks 的主键模型
4 · 并发与运维能力峰值同时在跑的查询数、有没有人能长期管分片副本与扩容按分钟统计查询数取峰值；运维能力按「能不能指定一个负责人」判断上千并发的对外看板：淘汰裸用 ClickHouse；没有专人运维：淘汰全部自建 MPP，走云数仓
补充 · 延迟要求写入到可查允许多久、查询 p99 允许多少与业务方把数字写进文档，不要用「实时」这种词要求秒级可查且关键词检索：ClickHouse 单独扛不下来，需要配 Elasticsearch

第 2 步和第 4 步最容易靠感觉下结论，直接从查询日志里数出来：

-- 查询形态：带 join 的比例、点查伪装成分析需求的比例、单次扫描量的分布
SELECT
    count()                                                       AS total,
    countIf(positionCaseInsensitive(query, 'join') > 0)           AS with_join,
    countIf(positionCaseInsensitive(query, 'group by') > 0)       AS with_group_by,
    countIf(read_rows < 10000)                                    AS point_like,
    formatReadableSize(quantile(0.99)(read_bytes))                AS p99_scan
FROM system.query_log
WHERE type = 'QueryFinish' AND query_kind = 'Select'
  AND event_time > now() - INTERVAL 7 DAY;
-- 判读：with_join 占比高就别在第 2 步选 ClickHouse；point_like 占比高说明真实需求是点查，
--       那是 MySQL 或 Redis 的活。还没有 ClickHouse 时，用 MySQL 慢日志或 digest 汇总做同样的统计

-- 并发峰值：按分钟数查询条数，比平均 QPS 有用得多，OLAP 的痛点从来是峰值
SELECT toStartOfMinute(event_time) AS minute,
       count()                     AS queries,
       max(query_duration_ms)      AS max_ms
FROM system.query_log
WHERE type = 'QueryFinish' AND event_time > now() - INTERVAL 1 DAY
GROUP BY minute
ORDER BY queries DESC
LIMIT 10;

这四步为什么是这个顺序、每条能力边界背后是什么机制，下面原理层逐个展开。

② 原理 · 先分清三大流派，再谈具体产品

市面上叫「OLAP 引擎」的东西其实解决的是不同问题，混在一起比较毫无意义。按「数据存在哪、谁负责存储格式」可以分成三类：MPP 数据库自带存储并对存储格式做了极致优化，所以单表查询最快；数据湖查询引擎不管存储、只负责计算，擅长跨源联邦与大规模 ETL；云数仓把两者打包成托管服务，用弹性和运维成本换按量计费。

下面这张表的每一行都是选型时真正会卡住项目的维度。其中最常被忽略的是「并发查询能力」：ClickHouse 单查询极快是因为它把所有 CPU 核都用来跑这一条查询，反过来就意味着并发上来以后互相抢核，几十到几百并发就需要靠缓存和预聚合来兜。做面向内部分析师的报表这不是问题，做面向 C 端用户的实时看板就会立刻暴露。

② 原理 · ClickHouse vs Doris / StarRocks：国内最常见的二选一

这两家的定位差异经常被简化成「谁更快」，但真正决定选型的是三件事：要不要 join、要不要按主键更新、团队愿不愿意手工管分片。ClickHouse 把单表扫描和压缩做到了极致，代价是 join 弱、更新弱、运维要人管；Doris 与 StarRocks 从一开始就按「实时数仓」设计，兼容 MySQL 协议、有代价优化器和 runtime filter、主键模型支持真正的行级 upsert、数据自动均衡，代价是单表极限扫描性能和压缩率通常不如 ClickHouse。

对比点ClickHouseDoris / StarRocks这条对你重要吗
单表扫描与压缩最强，日志类数据压缩比常见 8 到 15 倍略逊，但同一数量级存储成本敏感、数据量极大时重要
join 优化只有基本的 hash join，右表进内存，需要手工调整表顺序有 CBO、runtime filter、colocate join、多种分布式 join 策略只要有超过两张表的分析就很重要
主键更新ReplacingMergeTree 是「查询时去重」，新版有主键但能力有限主键模型支持行级 upsert 与 delete，写入即最新接 CDC 同步业务库时决定性
接入协议自有 HTTP 与 TCP 协议，部分 BI 工具需要专门驱动兼容 MySQL 协议，任何 MySQL 客户端与 BI 直连团队 SQL 与 BI 习惯迁移成本
数据均衡扩分片后存量数据不自动搬，需要手工重分布自动均衡与副本修复预期会频繁扩容时很重要
高并发点查弱，单查询吃满多核较强，有专门的短查询与点查优化路径做对外产品化看板时决定性
物化视图写入触发式，只能基于单表增量，维护心智负担大支持同步与异步物化视图，可覆盖多表做预聚合加速时重要
社区与版本节奏迭代非常快，大版本行为变更多，要锁定版本国内社区活跃，文档与案例中文资料多团队学习曲线
✅
给出明确结论

选 ClickHouse：日志、埋点、监控指标这类一次写入不再修改的事件数据；查询以单张宽表的过滤与聚合为主；数据量大、存储成本敏感；并发以内部分析师和少量看板为主。选 Doris 或 StarRocks：要从 MySQL 做 CDC 同步并保持可更新；分析必须跨多张表 join；要对外提供高并发的产品化报表；团队人力少、希望少管分片和均衡。两者不是替代关系，很多公司是 ClickHouse 扛日志、Doris 扛业务实时数仓并存。

② 原理 · ClickHouse vs Elasticsearch：日志场景的真实差距

这两个经常被放在一起是因为「日志分析」这个需求同时包含检索和聚合，而它们分别擅长一半。ES 的核心是倒排索引：把文档分词后建词到文档的映射，所以关键词检索、模糊匹配、相关性打分、高亮都极强，并且写入后近实时（默认 refresh_interval 1 秒）即可检索。ClickHouse 的核心是列存加稀疏索引：大范围扫描与聚合极强、压缩率高出一个档，但没有真正的倒排，复杂文本检索只能靠 ngram 跳数索引做粗糙的子串匹配。

维度ElasticsearchClickHouse日志场景的含义
索引结构倒排索引加 doc values，索引体积常与原始数据同量级甚至更大列存加稀疏主键索引，索引只有几 MB同样的日志量，ES 的存储成本可能是 ClickHouse 的数倍到十倍
压缩后占用算上副本与索引往往超过原始数据通常为原始数据的十分之一以下这是很多团队从 ES 迁到 ClickHouse 的直接动因
全文检索强：分词、短语、模糊、相关性打分、高亮弱：只有子串匹配与简单 token 过滤要按关键词翻查原始日志，ES 体验明显更好
大范围聚合高基数字段聚合极吃内存，容易触发熔断强项，几十亿行分组聚合是常规操作做趋势图、TopN、多维下钻，ClickHouse 稳定得多
写入吞吐与成本建索引 CPU 开销大，写入成本高批量写入吞吐高，CPU 主要花在压缩同等硬件下 ClickHouse 能接住更大流量
写入可见延迟近实时，默认 1 秒取决于攒批策略，通常几秒到几十秒要求秒级可查的告警链路，ES 更直接
字段灵活性动态 mapping，日志结构变了也能写schema 固定，新字段要 ALTER 或放进 Map 与 JSON 列日志字段不稳定时 ES 省事，但会造成 mapping 爆炸
运维JVM 堆与 GC 调优、分片数一旦定下不好改无 JVM，参数少但分片副本要手工规划两边都不轻松，痛点不同

日志场景的实际建议：按用途拆开。需要按关键词翻查明细、做故障排查的「热日志」（最近几天）放 ES；需要长期保留、做趋势分析与容量统计的「全量日志」放 ClickHouse，保留期可以拉到几个月甚至一年而成本仍低于 ES 存一周。如果团队只能维护一套、并且检索需求就是「按 trace_id 或几个固定字段过滤」，那 ClickHouse 完全够用，把这些字段放进 ORDER BY 或加 bloom_filter 跳数索引即可。

② 原理 · 为什么不能用 OLAP 引擎顶 OLTP

「既然 ClickHouse 这么快，业务库也用它行不行」——这个想法每隔一段时间就会冒出来。下面这张表把 OLTP 的典型动作逐条对照，看完就明白差距不是性能调优能弥补的，而是存储模型决定的。

OLTP 的典型动作行存数据库怎么做OLAP 引擎上的后果
按主键改一个字段定位到行就地更新，微秒级异步 mutation 重写整个 part 的相关列，秒级到小时级，且不保证立即可见
按唯一键点查一行B+树三四次页访问稀疏索引最少读一个 granule，即 8192 行的列段
唯一约束唯一索引直接拒绝重复写入ClickHouse 没有唯一约束，只能事后去重，写重了不会报错
多语句事务与回滚完整 ACID，失败整体回滚只有单次写入的原子性，跨语句无事务，出错只能靠幂等重放
行级锁与并发控制MVCC 加 next-key 锁没有行锁概念，并发写同一批数据靠去重窗口兜，语义不等价
上万 QPS 的短查询连接池加索引命中，常规操作单查询就要吃满多核，几百并发就要靠缓存兜
外键与级联数据库层保证引用完整性完全不支持，一致性要靠上游保证

正确的分工是：业务读写留在 MySQL 或 PostgreSQL，通过 CDC 或消息队列把变更同步到 OLAP 层做分析。InnoDB 的 B+树与 MVCC 细节详见站内 MySQL 篇，PostgreSQL 的堆表与 VACUUM 详见站内 PostgreSQL 篇。

② 原理 · 实时数仓的分层与各层选型

分层的目的不是为了好看，而是把「查询成本」挪到写入时一次性付掉。ADS 层查询之所以能做到毫秒级高并发，是因为 DWS 层已经把聚合算完了。每层的引擎可以不同，没必要全站统一。

-- Kafka 接入方案一：ClickHouse 原生 Kafka 引擎 + 物化视图（链路短，但排查困难）
CREATE TABLE kafka_events
(
    event_time DateTime,
    app_id     String,
    user_id    UInt64,
    amount     Decimal(18, 4)
)
ENGINE = Kafka
SETTINGS kafka_broker_list  = 'kafka-1:9092,kafka-2:9092',
         kafka_topic_list   = 'events',
         kafka_group_name   = 'ch_events_consumer',
         kafka_format       = 'JSONEachRow',
         kafka_num_consumers = 4,          -- 不要超过 topic 分区数，多出来的消费者空转
         kafka_max_block_size = 1048576,   -- 攒够这么多行再写一个 part，避免小 part 泛滥
         kafka_skip_broken_messages = 10;  -- 容忍少量脏数据，否则一条坏消息会卡死整条链路

-- 目标表：真正存数据的地方
CREATE TABLE events
(
    event_date Date,
    event_time DateTime CODEC(DoubleDelta, LZ4),
    app_id     LowCardinality(String),
    user_id    UInt64,
    amount     Decimal(18, 4)
)
ENGINE = MergeTree
PARTITION BY toYYYYMM(event_date)
ORDER BY (app_id, event_time);

-- 物化视图把引擎表的每批数据搬进目标表，这里可以顺手做清洗和打宽
CREATE MATERIALIZED VIEW mv_kafka_to_events TO events AS
SELECT toDate(event_time) AS event_date, event_time, app_id, user_id, amount
FROM kafka_events
WHERE user_id != 0;    -- 过滤掉脏数据，别让它进明细层

-- DWS 层：用 AggregatingMergeTree 存聚合中间状态，查询时合并
CREATE TABLE events_hourly
(
    hour     DateTime,
    app_id   LowCardinality(String),
    users    AggregateFunction(uniq, UInt64),
    amount   AggregateFunction(sum, Decimal(18, 4))
)
ENGINE = AggregatingMergeTree
ORDER BY (app_id, hour);

CREATE MATERIALIZED VIEW mv_events_hourly TO events_hourly AS
SELECT toStartOfHour(event_time) AS hour, app_id,
       uniqState(user_id) AS users, sumState(amount) AS amount
FROM events GROUP BY app_id, hour;
-- 查询时用 Merge 后缀合并状态：SELECT app_id, uniqMerge(users) FROM events_hourly GROUP BY app_id

但消费位点 重试 死信都在数据库内部 出问题难排查 K->>W: 外部程序自行消费并攒批 W->>T: 攒够一万到十万行再批量写入 W->>W: 失败重试 死信队列 限流 全部可控 Note over W,T: 生产链路更推荐这条 写入语义和故障处理都在自己手里

② 原理 · 成本模型：自建的机器账 vs 云数仓的按量账

自建和云数仓的成本结构完全不同，不能只比单价。自建是「一次性买够算力，用不满也在付钱，但用得再狠也不涨价」；云数仓是「不用不付钱，但一条写错的 SQL 可以在几分钟内烧掉一个月预算」。后者最典型的坑是按扫描量计费：BigQuery 这类产品按查询扫描的字节数收费，一旦分区裁剪没生效，一次全表扫描就是全量数据的扫描费，而且 BI 工具会定时自动刷新，等发现时账单已经产生了很多次。

维度自建 ClickHouse 集群云数仓（按量计费）
成本结构机器与机房固定支出，与查询量无关存储费加计算费，随扫描量或计算时长浮动
低负载时闲着也在付全额几乎不花钱，优势明显
高负载时成本不变，只是变慢成本线性上涨，可能反超自建数倍
扩容速度采购加部署，数天到数周；加分片还要手工搬数据分钟级，弹性伸缩
人力成本需要至少一个懂 ClickHouse 的人持续投入基本不需要运维，但需要懂成本治理
成本可预测性高，提前一年都能算出来低，需要配额、预算告警和强制分区过滤
失控风险查询写烂只会拖慢集群查询写烂直接变成账单，尤其是没做分区裁剪的定时刷新
冷数据可用 S3 分层把冷数据成本压到十分之一存储单价本来就低，冷热分层内置
-- 不管自建还是上云，先量化「每天到底扫了多少数据」，这是成本和容量规划的共同基础
SELECT toStartOfDay(event_time)                        AS day,
       count()                                         AS queries,
       formatReadableSize(sum(read_bytes))             AS scanned_total,
       formatReadableSize(quantile(0.99)(read_bytes))   AS p99_scan,
       round(avg(query_duration_ms))                   AS avg_ms
FROM system.query_log
WHERE type = 'QueryFinish' AND event_time >= now() - INTERVAL 7 DAY
GROUP BY day ORDER BY day;

-- 揪出扫描量最大的查询：在云数仓上这就是账单大头，在自建上这就是 CPU 大头
SELECT substring(query, 1, 120)            AS query_head,
       formatReadableSize(read_bytes)      AS scanned,
       read_rows, query_duration_ms, user
FROM system.query_log
WHERE type = 'QueryFinish' AND event_time >= now() - INTERVAL 1 DAY
ORDER BY read_bytes DESC LIMIT 10;
-- 判读要点：read_rows 接近表总行数，说明这条 SQL 完全没走分区与主键裁剪，先修它而不是加机器

③ 场景 · 选型决策树：先确认真的需要 OLAP

在所有分支之前，先问一个问题：这个需求真的需要 OLAP 引擎吗？相当多的「分析需求」实际上是几张固定报表，数据量千万行级别，用 MySQL 加一张定时刷新的汇总表、或者加一个只读从库专门跑报表就解决了，代价是一个定时任务，而不是一套新中间件加一个新的运维对象。引入 OLAP 引擎的隐性成本包括：数据同步链路、两套 SQL 方言、一致性对不上时的排查、以及一个必须有人懂的新系统。MySQL 侧的索引与慢查询优化手段详见站内数据库优化篇。

⚠️
用真实数据和真实 SQL 做 POC

公开的基准测试（包括官方的 ClickBench）用的是特定形状的数据和查询，结论不能直接搬到你的场景。POC 至少要满足三条：用自己的真实数据和真实的表结构、用生产里跑得最多的那几条 SQL、并且带上真实的并发度。只测单条查询的响应时间，最容易得出与上线后完全相反的结论。

③ 场景 · 选错之后的退路与不适用边界

选型很少有「重来一次」的机会，但退路的代价差别极大：有的只是改建模，有的必须新建表回灌全量。下表按「已经选了什么、现在需求变成什么」给出可行退路，代价列是必须提前拿给业务方看的东西。

现状需求变成可行退路代价
已用 ClickHouse 承接事件流要与业务库保持主键一致、支持 upsert新增一条 Doris 或 StarRocks 链路专门接 CDC，ClickHouse 继续扛日志与埋点两套系统并存，指标口径要在一处定义，运维面翻倍
已用 ClickHouse报表关联的维表越来越多不换引擎，换建模：ETL 阶段打平宽表，或维表做成字典用 dictGetETL 链路变重，维度变更要回刷历史，字典占常驻内存
已用 ClickHouse看板对外开放，并发上千加一层 ADS 结果表做预聚合，前面再挡一层缓存多一层一致性窗口，当天数据会刷新，需要和业务方约定口径
排序键或分区键定错了查询要按另一组维度过滤新建表加全量回灌再切流量；或用 PROJECTION 给同一张表加第二种排序ORDER BY 只能尾部追加、PARTITION BY 完全不能改，等于一次全量重写
云数仓账单失控成本要可预测先开强制分区过滤与预算告警，再评估迁自建迁移要重写 SQL 方言并双跑一段时间对账
自建集群长期无人运维要降低运维风险迁托管服务或云数仓，历史数据用 s3 表函数导出再导入成本结构从固定变浮动，需要重新做成本治理

不适用边界：这篇只解决「选哪个引擎」，不解决「选完怎么用好」。确定用 ClickHouse 之后，建表 DDL、列压缩与批量导入是下一步；慢查询的判读顺序在查询优化篇；星型模型、大宽表与 SCD 在 OLAP 建模篇；分片副本与 Distributed 表在集群架构篇；引擎为什么是这些能力边界，回到 ClickHouse 深度原理。另外两类需求不在本篇范围：数据量还在千万行级别时请先看 数据库性能优化 里的汇总表与索引手段；关键词检索的部分交给 Elasticsearch。

最容易踩的坑

❌
选型阶段最容易踩的坑
  • 只比单表扫描性能：这是 ClickHouse 最强的维度，但你的真实负载可能是 join、更新或高并发，赢在这一项毫无意义。
  • 忽略并发查询能力：ClickHouse 单查询吃满多核，几百并发的对外看板会直接崩，这项在选型表里几乎总被漏掉。
  • 以为 ReplacingMergeTree 等于主键更新：它是查询时去重，不加 FINAL 或不配合 GROUP BY 就会读到多个版本，和 Doris 的主键模型不是一回事。
  • 用 ClickHouse 完全替代 ES 做日志检索：ngram 跳数索引只能做粗糙的子串匹配，没有分词、相关性打分和高亮，按关键词翻查明细的体验差很多。
  • 用 ES 做高基数聚合：反方向的坑。高基数字段的 terms 聚合极吃内存，容易触发熔断，而且存储成本可能是 ClickHouse 的数倍。
  • 拿 OLAP 引擎当业务库：没有唯一约束、没有事务、没有行锁，写重了不报错，出错无法回滚。
  • 相信公开基准测试的排名：数据形状、SQL 形态、硬件、版本都不同，必须用自己的数据和 SQL 做 POC，并带上真实并发。
  • 低估 schema 演进成本：ClickHouse 加列是轻量的，但改 ORDER BY 基本等于重建表，日志字段不稳定的场景要提前想好用 Map 还是 JSON 列。
  • 云数仓没做分区裁剪就接 BI 定时刷新：按扫描量计费下，一个每 5 分钟全表扫的看板能在一天内烧掉整月预算。上线前必须开强制分区过滤和预算告警。
  • 为了统一技术栈把所有层塞进一个引擎：DWD 需要 join 与更新、DWS 需要预聚合、ADS 需要高并发，本来就该用不同的工具，硬统一的代价通常更高。
  • 在 ODS 层做清洗：脏数据被覆盖后无法追溯，也没法回溯重算。原始数据必须原样保留在 Kafka 或明细表里，Kafka 的保留策略与分区设计详见站内 Kafka 专题。
  • 忘了把人力成本算进选型：自建 ClickHouse 需要有人懂分片、副本、merge 和扩容重分布，没有这个人，再好的性能也撑不过第一次故障。
