ClickHouse 建表与写入：引擎选型、列压缩与批量导入

🏷️ CK 数据导入

ClickHouse 的 CREATE TABLE 看着和 MySQL 很像，这是个陷阱。ENGINE、ORDER BY、PARTITION BY 这三项定错了没有 ALTER 能救，只能新建表加回灌全量数据；写入姿势错了，则会在上线第三天收到 Too many parts。这篇只讲建表和写入这两件最容易做错的事：列存与向量化执行、稀疏主键索引的物理布局详见站内《ClickHouse 架构与核心特性》，副本拓扑与 Distributed 表详见站内《ClickHouse 集群与分布式表》，这里只给结论不展开。

建表时必须一次定对的三件事

ClickHouse 的 DDL 自由度比关系库低得多。加列、删列、改列类型都很便宜（元数据操作或后台异步重写），但 ORDER BY 只能在末尾追加列、不能重排已有列，PARTITION BY 和 ENGINE 完全不能改。这意味着建表评审要花的时间比写导入脚本更多。

决策项决定了什么能否事后修改定错的后果修复成本
ENGINE去重 / 预聚合 / 是否带副本的语义不能改该去重的没去重，报表口径长期偏大建新表 + 全量回灌 + 双写切换
ORDER BY磁盘物理顺序、稀疏索引、压缩率、去重用的键只能在尾部追加列主键裁剪失效，每次查询都全表扫同上，且历史分区必须重排
PARTITION BYpart 目录划分、DROP PARTITION 粒度、TTL 单位不能改分区过细导致 part 爆炸；过粗导致无法按分区重跑同上
列类型与 CODEC存储占用与扫描带宽可以改（后台重写 part）磁盘多花两三倍，扫描变慢ALTER MODIFY COLUMN，异步但可控
index_granularity一个 granule 覆盖多少行，默认 8192可以改，但需重建 part点查场景读放大明显一般不用动，除非单行特别宽

ORDER BY 的排列有三条经验：过滤最频繁的列放最左，因为主键裁剪只能用前缀；基数低的列放前面，相同值连续排列会同时改善压缩率和 granule 裁剪效果；时间列一般放中间或靠后，前面先放租户或业务维度，因为几乎所有查询都带租户条件，把时间放最左会让单租户查询退化成扫所有租户的数据。分区键在实践中只有按天和按月两个合理选项，目标是总分区数控制在一千以内、单分区压缩后在几 GB 到几十 GB。

MergeTree 家族：每个引擎在解决什么问题

MergeTree 家族的全部差异都发生在后台 merge 的那一刻：它们共用同样的列存布局和稀疏索引，只是在合并两个 part 时对排序键相同的行做了不同处理。理解这一点就能推导出所有引擎共同的认知坑——你永远不知道 merge 什么时候发生，所以引擎的语义在查询时不是立即成立的。

flowchart TB subgraph BASE["基础层, 只管存"] A["MergeTree"] B["TinyLog 与 Log, 仅测试用"] end subgraph DEDUP["merge 时折叠行"] C["ReplacingMergeTree"] D["CollapsingMergeTree"] E["VersionedCollapsingMergeTree"] end subgraph AGG["merge 时聚合行"] F["SummingMergeTree"] G["AggregatingMergeTree"] end subgraph REPL["加副本能力"] H["Replicated 系列, 依赖 Keeper"] end A --> C A --> F F --> G C --> D D --> E A --> H C --> H G --> H
引擎解决什么问题语义何时生效查询时必须注意典型场景
MergeTree纯明细存储，写入即可查无特殊语义无日志、埋点、事实明细表
ReplacingMergeTree(ver)按排序键保留一行，模拟 upsert仅后台 merge，且只在同分区内加 FINAL，或 GROUP BY 键 + argMax 自己取最新版本维度表、CDC 落地表
SummingMergeTree把非排序键的数值列自动累加仅后台 merge查询仍要写 sum()，否则未合并的行会算少计数类指标汇总表
AggregatingMergeTree存聚合中间状态，支持 uniq / quantile 等仅后台 merge写入用 -State，读取必须用 -Merge物化视图预聚合层
CollapsingMergeTree(sign)用 +1 / -1 行抵消实现更新删除merge 且两行进入同一 part 时对行到达顺序敏感，乱序会抵消错已基本被下一行替代
VersionedCollapsingMergeTree(sign, ver)带版本号的抵消，允许乱序到达merge 时按 version 判定聚合要写 sum(metric * sign)需要严格撤销语义的账务快照
Replicated 系列基于 Keeper 的副本复制与写入块去重写入时同步复制日志同一批次重发会被块级去重（默认记住最近 100 个块哈希）所有生产集群
❌
流传最广的错误说法：ReplacingMergeTree 等于唯一索引

它既不拒绝重复写入，也不保证任何时刻查到的是一行。折叠只在后台 merge 时按分区内的排序键做，触发条件是 part 的大小和数量，可能几秒也可能几天。更隐蔽的是跨分区的重复永远不会折叠：如果分区键是 toYYYYMM(update_time)，同一个订单先后两次更新落在不同月份，它就是两行。OPTIMIZE TABLE ... FINAL 能强制合并，但它会重写整张表，禁止写进定时任务当日常手段。

列类型选对，磁盘立刻省一半

列存的压缩率几乎完全由「同一列相邻值的相似度」决定，所以类型选择在 ClickHouse 里不是洁癖而是实打实的成本。下面这张表是实际项目里最高频的几个改法。

常见写法问题应该改成收益量级代价与边界
String 存状态、国家、渠道每行重复存字面量LowCardinality(String)存储省 2 到 8 倍，等值过滤明显更快基数一万以内最佳、十万以内可用，百万级反向劣化
Int64 存状态码、年龄8 字节存 0 到 100UInt8 / UInt16压缩前体积直接降到八分之一要预留业务扩展空间，改类型要重写 part
Nullable(String) 兜底额外存一列 null 掩码，且默认不允许进排序键用空串 / 0 / 哨兵值 + 注释约定省掉掩码列，函数不再走 Nullable 慢路径业务上必须区分「空值」和「未知」时才保留 Nullable
DateTime64(3) 一把梭8 字节，时间函数也更慢只要秒级就用 DateTime体积减半DateTime 上限 2106 年；毫秒级链路追踪确实需要 64
Enum8 存业务枚举新增枚举值要 ALTER，上线顺序易出错多数情况用 LowCardinality(String)免 DDL，写入端不会因未知值报错需要数据库层强约束时才用 Enum
Float64 存金额浮点误差导致对账不平Decimal64(2) 或用整数存分口径正确Decimal 的算术比整数略慢

类型定完，再给高频大列配编解码器。CODEC 的思路是先用差分或位压缩把数值的熵降下来，再交给通用压缩算法，多个 codec 从左到右依次作用。

列特征推荐 CODEC为什么有效相对默认 LZ4 的收益
单调递增时间戳、自增 IDCODEC(Delta, ZSTD(1))相邻差值几乎恒定，Delta 之后全是小整数再省 3 到 10 倍
缓慢波动的指标（CPU、温度、余额）CODEC(DoubleDelta, ZSTD(1))二阶差分把线性趋势压成接近零2 到 5 倍
浮点监控值CODEC(Gorilla, ZSTD(1))按 XOR 位模式压缩，专为时序浮点设计2 到 4 倍
窄值域整数（耗时、计数）CODEC(T64, ZSTD(1))按位转置后裁掉恒为零的高位1.5 到 3 倍
低基数字符串（已上 LowCardinality）默认 LZ4 即可字典编码后本身已经很小不必叠加
大文本、JSON 原文CODEC(ZSTD(3))文本冗余高，ZSTD 压缩比远胜 LZ43 到 6 倍，用 CPU 换磁盘
-- 一张典型的埋点明细表：类型、CODEC、排序键、分区、TTL 一次定好
CREATE TABLE events
(
    tenant_id      UInt32,                                    -- 几乎所有查询都带，放排序键最左
    event_type     LowCardinality(String),                    -- 基数几十，字典编码最划算
    event_time     DateTime CODEC(Delta, ZSTD(1)),             -- 单调递增，Delta 之后极小
    event_date     Date MATERIALIZED toDate(event_time),       -- 物化列，供分区表达式与粗过滤使用
    user_id        UInt64 CODEC(ZSTD(1)),                      -- 高基数，别上 LowCardinality
    country        LowCardinality(String),
    device         LowCardinality(String),
    duration_ms    UInt32 CODEC(T64, ZSTD(1)),                 -- T64 对窄值域整数很有效
    revenue        Decimal64(4) DEFAULT 0,                     -- 金额禁用 Float，用默认值替代 Nullable
    props          String CODEC(ZSTD(3)),                      -- 原始 JSON，重压缩
    ingest_time    DateTime DEFAULT now()                      -- 写入时间，用于版本判定和延迟监控
)
ENGINE = MergeTree
PARTITION BY toYYYYMM(event_date)                              -- 按月：两年数据也只有 24 个分区
ORDER BY (tenant_id, event_type, event_time)                   -- 低基数在前，时间在后
TTL event_date + INTERVAL 180 DAY DELETE                       -- 明细只留半年
SETTINGS index_granularity = 8192;                             -- 默认值，超宽表可适当调小

-- 高基数列加跳数索引，用于非前缀列的粗过滤（只能跳过 granule，不能定位行）
ALTER TABLE events ADD INDEX idx_user user_id TYPE bloom_filter(0.01) GRANULARITY 4;

写入的铁律：批量，且只有批量

ClickHouse 的写入模型一句话就能概括：一次 INSERT 生成一个 part，不管里面是 1 行还是 100 万行。part 是一个包含每列数据文件、标记文件和索引文件的目录，创建成本固定。逐条写入意味着每秒创建上千个目录，后台 merge 线程被迫不停合并小文件，磁盘 IO 全耗在合并上，接着写入被限速，最后直接报错。

参数 / 指标默认值含义踩线后的表现
parts_to_delay_insert150单分区活跃 part 超过此数开始人为延迟写入写入 RT 从毫秒涨到秒级，客户端大面积超时
parts_to_throw_insert300超过则直接拒绝写入抛 Too many parts，写入链路全线报错
max_insert_block_size1048576服务端解析时的切块行数单次 INSERT 过大会被拆成多个块
建议单批行数1 万 到 50 万行经验值，行数与字节双阈值取先到者小于 1000 行的批次基本等于自杀
建议单批字节10 MB 到 100 MB宽表按字节控制更准超过几百 MB 会顶到内存上限
建议提交频率每表每秒不超过 1 次官方长期给出的经验上限频率高于此，merge 追不上产生速度

批次攒在哪里有客户端和服务端两种做法。async_insert 的真正价值是：当你有几百个无状态服务实例、每个实例只有零星流量时，客户端根本攒不出大批次，这时让服务端按表维度统一攒批才合理。

方案批次在哪攒延迟丢数据风险实现成本适用
客户端攒批应用内存队列由本地 flush 间隔决定进程崩溃丢内存队列，可用本地磁盘队列缓解要自己写批量器、重试、背压写入方少、单方流量大
async_insert=1 且 wait_for_async_insert=1服务端按表攒多出一个 flush 周期（百毫秒级）无，和同步写等价改两个 setting实例多、单实例流量小

-- Kafka 接入必须是三段：源表 + 目标表 + 物化视图。少了物化视图，数据不会落盘。
-- 第一段：Kafka 引擎表，它只是一个消费者，本身不存任何数据
CREATE TABLE kafka_events_src
(
    raw String                                    -- 整条 JSON 收进来，解析交给物化视图
)
ENGINE = Kafka
SETTINGS
    kafka_broker_list       = 'kafka-1:9092,kafka-2:9092',
    kafka_topic_list        = 'app_events',
    kafka_group_name        = 'ch_app_events_v1', -- 改这个名字等于从头重新消费，灰度时务必注意
    kafka_format            = 'JSONAsString',     -- 不在引擎层解析，单条脏数据不会卡死整个消费
    kafka_num_consumers     = 4,                  -- 不要超过 topic 分区数，多出来的是空转线程
    kafka_max_block_size    = 262144,             -- 攒够这么多行落一个 part
    kafka_flush_interval_ms = 2000,               -- 或攒够 2 秒，两个条件先到先算
    kafka_handle_error_mode = 'stream';           -- 解析错误进错误流，而不是整批失败

-- 第二段：真正存数据的目标表，用 ReplacingMergeTree 吸收重复投递
CREATE TABLE events_rt
(
    event_id    String,
    tenant_id   UInt32,
    event_type  LowCardinality(String),
    event_time  DateTime CODEC(Delta, ZSTD(1)),
    user_id     UInt64,
    revenue     Decimal64(4) DEFAULT 0,
    ingest_time DateTime DEFAULT now()
)
ENGINE = ReplacingMergeTree(ingest_time)                 -- 同 event_id 保留 ingest_time 最大的一行
PARTITION BY toYYYYMM(event_time)                        -- 关键：同一 event_id 必须落同一分区才可能去重
ORDER BY (tenant_id, event_time, event_id);

-- 第三段：物化视图，它才是这条链路真正的搬运工
CREATE MATERIALIZED VIEW mv_kafka_events TO events_rt AS
SELECT
    JSONExtractString(raw, 'event_id')               AS event_id,
    JSONExtractUInt(raw, 'tenant_id')                AS tenant_id,
    JSONExtractString(raw, 'event_type')             AS event_type,
    toDateTime(JSONExtractUInt(raw, 'ts'))           AS event_time,
    JSONExtractUInt(raw, 'user_id')                  AS user_id,
    toDecimal64(JSONExtractFloat(raw, 'revenue'), 4) AS revenue,
    now()                                            AS ingest_time
FROM kafka_events_src
WHERE JSONHas(raw, 'event_id');                      -- 过滤掉结构不合法的消息

-- 巡检消费健康度：lag 持续上涨说明物化视图里的 SQL 太重，或目标表在被限速
SELECT database, table, consumer_id, num_messages_read, last_exception
FROM system.kafka_consumers;

导入完成后必须做的核对

「导入脚本没报错」不等于数据对了。至少要核对行数、part 健康度和 mutation 队列这三件事，下面几条 SQL 可以直接存成日常巡检。

-- 1) 行数与分区分布核对：拿源端行数逐分区对比，缺量通常是某个批次静默失败
SELECT partition, sum(rows) AS rows, count() AS parts,
       formatReadableSize(sum(data_compressed_bytes))   AS compressed,
       formatReadableSize(sum(data_uncompressed_bytes)) AS uncompressed,
       round(sum(data_uncompressed_bytes) / sum(data_compressed_bytes), 2) AS ratio
FROM system.parts
WHERE table = 'events' AND active        -- active 必须加，否则会把已被合并的旧 part 一起算进来
GROUP BY partition
ORDER BY partition;
-- 判读：单分区 parts 长期大于 100 说明写入批次太小；ratio 小于 3 说明类型或 CODEC 选得不好

-- 2) 找出压缩最差的列，通常就是该上 LowCardinality 或 Delta 的那几列
SELECT column, type,
       formatReadableSize(sum(column_data_compressed_bytes)) AS compressed,
       round(sum(column_data_uncompressed_bytes) / sum(column_data_compressed_bytes), 2) AS ratio
FROM system.parts_columns
WHERE table = 'events' AND active
GROUP BY column, type
ORDER BY sum(column_data_compressed_bytes) DESC
LIMIT 20;

-- 3) 卡住的 mutation 会阻塞该表后续所有变更，必须监控
SELECT database, table, mutation_id, command, parts_to_do, is_done, latest_fail_reason
FROM system.mutations
WHERE NOT is_done
ORDER BY create_time;
-- 判读：parts_to_do 长时间不降且 latest_fail_reason 非空，用 KILL MUTATION 取消，改走按分区重灌

-- 4) 写入是否已经被限速：这两个计数器只要在涨就说明 part 数出了问题
SELECT event, value FROM system.events
WHERE event IN ('DelayedInserts', 'RejectedInserts', 'InsertedRows', 'MergedRows');

更新与删除的真相

ClickHouse 里「改一行数据」这个动作在物理上不存在。part 里的列文件是压缩后顺序写入的，任何修改都意味着重写整个 part。ALTER TABLE ... UPDATE 之所以叫 mutation 而不叫 UPDATE，就是在提醒你它是一次后台的大规模数据重写：异步执行、不返回受影响行数、不保证何时可见，而且一个卡住的 mutation 会让排在后面的所有变更全部停住。

手段底层机制代价可见性什么时候用
ALTER TABLE ... UPDATE / DELETE异步 mutation，重写命中行所在的整个 part极高，等于重写这部分数据不保证，靠 system.mutations 轮询一次性历史数据修正，且必须带分区条件缩小范围
轻量级 DELETE FROM写删除掩码，查询时过滤，后续 merge 才真正清理低，但查询要多读一份掩码语句返回即可见零散删除，例如按用户 ID 做合规删除
ReplacingMergeTree 写新版本追加一行更高版本，merge 时折叠最低，就是一次普通写入需要 FINAL 或聚合去重维度表、CDC 同步的常规更新
DROP PARTITION 后重新写入删目录再灌数据，纯元数据操作秒级，几乎零成本切换瞬间不可见，可用临时表加 REPLACE PARTITION 消除窗口批处理重跑，ClickHouse 里最高效的「更新」
TTLmerge 时按表达式清理行、清空列或搬盘由后台 merge 摊薄不精确，到期后不一定立即删数据生命周期管理

用 TTL 管住数据生命周期

TTL 有三种形态经常被忽略：行级删除、列级清空（明细字段过期但维度继续保留）、以及配合多盘存储策略把冷数据搬到廉价介质。三者可以写在同一张表上。

-- 前提：config.xml 的 storage_configuration 里已定义 hot 与 cold 两个卷
ALTER TABLE events MODIFY TTL
    event_date + INTERVAL 7 DAY  TO VOLUME 'hot',            -- 最近 7 天留在 NVMe
    event_date + INTERVAL 30 DAY TO VOLUME 'cold',           -- 一个月后搬到大容量盘
    event_date + INTERVAL 90 DAY RECOMPRESS CODEC(ZSTD(6)),  -- 冷数据换更高压缩比
    event_date + INTERVAL 180 DAY DELETE;                    -- 半年后删除整行

-- 列级 TTL：原始 JSON 只留 14 天，其他维度继续保留到半年
ALTER TABLE events MODIFY COLUMN props String TTL event_date + INTERVAL 14 DAY;

-- 整个 part 都过期才删，代价从逐行判断降为常数级
ALTER TABLE events MODIFY SETTING ttl_only_drop_parts = 1;

-- 核对 TTL 是否真的写进了 part 元数据
SELECT partition, delete_ttl_info_min, delete_ttl_info_max
FROM system.parts WHERE table = 'events' AND active LIMIT 5;
✅
ttl_only_drop_parts 的前提条件

开启后 ClickHouse 只在一个 part 里所有行都过期时整目录删除，代价极低；关闭时每次 merge 都要逐行判断 TTL 并重写 part，大表上会持续占用后台线程。前提是分区键与 TTL 表达式基于同一个日期列，否则 part 里永远混着未过期的行，数据就一直删不掉。

最容易踩的坑

❌
建表与写入的十一个高频翻车点
  • 把 ReplacingMergeTree 当唯一键用：不加 FINAL 也不聚合就直接 count()，报表数字长期偏大，还随 merge 时机漂移。
  • 分区键切开了业务主键：PARTITION BY toYYYYMM(update_time) 配 ORDER BY order_id，同一订单跨月更新就永远去重不掉。
  • 用高基数列做分区：按 user_id 或按小时分区，几万个分区目录，merge 永远追不上，紧接着就是 Too many parts。
  • 逐条 INSERT：把 ClickHouse 当 MySQL 用，在循环里单行插入，写入 QPS 上千就崩。
  • 调大 parts_to_throw_insert 掩盖问题：报错消失了，但 merge 线程持续满载，查询延迟随 part 数线性恶化。
  • 只建 Kafka 引擎表就去查数据：SELECT 一次等于提交一次位点，数据被消费掉且永远不会落盘。
  • kafka_num_consumers 大于 topic 分区数：多出来的消费者纯空转，却占着线程和连接。
  • 在物化视图里写重逻辑：MV 里做 join 或复杂解析会拖慢消费让 lag 上涨，而且 MV 报错会让整条链路停住。
  • 核心数据用 wait_for_async_insert=0：客户端收到成功但数据还在内存缓冲，宕机即静默丢数据。
  • 用 ALTER UPDATE 做日常修数：mutation 队列堆积后该表所有 DDL 阻塞，且 KILL MUTATION 不会回滚已经重写的 part。
  • 把 OPTIMIZE TABLE FINAL 写进定时任务：每次都重写全表，磁盘 IO 打满还挤掉正常 merge，它只该在一次性数据治理时手动执行。
