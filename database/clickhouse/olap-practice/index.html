OLAP 场景实战

🏷️ ClickHouse,实战

从理论到落地：我搭过的三套系统

前面三篇讲了原理、建表、优化，这篇全是干货——我这几年用 ClickHouse 落地过的三类系统：日志分析、用户行为埋点、实时报表。每套都给你架构图、建表语句、真实业务查询。读完你应该能照着搭一套自己的。先说结论：ClickHouse 最适合的就是"事件流进来 → 预聚合 → 报表秒出"这种链路，别拿它干别的。

场景一：日志分析系统

这是 ClickHouse 最经典的用途。我们之前用 ELK 栈扛访问日志，日志量一天 20 亿条，ES 集群 20 个节点，聚合查询一上去就堆告警。迁到 ClickHouse 后，同样的查询 300 毫秒，节点数砍到 6 个。架构长这样：

flowchart LR NGINX[Nginx 访问日志] --> FLAUD[Filebeat 采集] APP[应用日志] --> KAFKA[Kafka 缓冲] FLAUD --> KAFKA KAFKA --> CK[ClickHouse Kafka Engine] CK --> MV[物化视图清洗解析] MV --> DETAIL[明细表 access_log] DETAIL --> AGG[按小时预聚合] AGG --> DASH[Grafana / 大屏] style CK fill:#f0682a,stroke:#fff,color:#fff

建表把 Nginx 日志解析成结构化字段：

CREATE TABLE access_log
(
    ts          DateTime64(3) CODEC(Delta, ZSTD(3)),
    remote_ip   IPv4,
    method      LowCardinality(String),
    url         String CODEC(ZSTD(1)),
    status      UInt16,
    latency_us  UInt32,
    ua_browser  LowCardinality(String),
    referer     String
) ENGINE = MergeTree
PARTITION BY toYYYYMMDD(ts)
ORDER BY (status, ts)
TTL ts + INTERVAL 30 DAY DELETE
SETTINGS index_granularity = 8192;

真实业务查询——"过去一小时各状态码的请求量和平均延迟"：

SELECT
    status,
    count() AS cnt,
    round(avg(latency_us)/1000, 1) AS avg_latency_ms,
    quantile(0.95)(latency_us)/1000 AS p95_ms
FROM access_log
WHERE ts >= now() - INTERVAL 1 HOUR
GROUP BY status
ORDER BY cnt DESC;

注意这里用了 quantile(0.95) 算 P95 延迟——这是 ClickHouse 比 ES 顺手太多的地方，一行函数搞定分位数，不用自己写百分位逻辑。

踩坑：日志字段别全塞 String

我一开始把 url、ua_browser 全用 String 存，结果一亿行表磁盘占了 800GB。后来把低基数的 method、ua_browser 改成 LowCardinality(String)，url 加 CODEC(ZSTD)，同样数据量压到 180GB。日志场景务必：枚举/低基数字段用 LowCardinality，长文本用 ZSTD 压缩。

场景二：用户行为埋点分析

埋点分析比日志多一层——你要按用户维度串行为路径，还要算留存、漏斗。表设计上多了 user_id 和 session：

CREATE TABLE user_events
(
    event_time  DateTime64(3),
    user_id     UInt64,
    session_id  String,
    event_name  LowCardinality(String),
    page_url    String,
    referrer    String,
    device      LowCardinality(String),
    properties  String CODEC(ZSTD(1))
) ENGINE = MergeTree
PARTITION BY toYYYYMMDD(event_time)
ORDER BY (event_name, event_time, user_id);

算次日留存是埋点场景的标配：

WITH
    -- 首日活跃用户
    (SELECT user_id FROM user_events
     WHERE event_time >= '2026-09-15' AND event_time < '2026-09-16'
     GROUP BY user_id) AS day1
SELECT
    count() AS day1_users,
    countIf(user_id IN (
        SELECT user_id FROM user_events
        WHERE event_time >= '2026-09-16' AND event_time < '2026-09-17'
    )) AS day2_returned
FROM day1;

漏斗分析——"访问首页 → 商品页 → 下单"每一步的转化率：

SELECT
    countIf(event_name = 'view_home')     AS step1_home,
    countIf(event_name = 'view_product')   AS step2_product,
    countIf(event_name = 'order_paid')    AS step3_paid,
    round(100.0 * step2_product / step1_home, 2) AS home_to_product,
    round(100.0 * step3_paid / step2_product, 2) AS product_to_paid
FROM user_events
WHERE event_time >= '2026-09-15' AND event_time < '2026-09-16';

这种多维分析查询在 ClickHouse 上跑就是毫秒级。在 MySQL 上同样的漏斗要自连接三次，慢得没法用。

场景三：实时报表

实时报表的关键是"秒级更新 + 亚秒查询"。用物化视图做预聚合，Grafana 直接查预聚合表：

-- 按分钟预聚合：PV、UV、各事件量
CREATE MATERIALIZED VIEW mv_realtime_minute
ENGINE = SummingMergeTree
PARTITION BY toYYYYMMDD(minute)
ORDER BY (minute, event_name)
AS
SELECT
    toStartOfMinute(event_time) AS minute,
    event_name,
    count() AS pv,
    uniqState(user_id) AS uv
FROM user_events
GROUP BY minute, event_name;

-- 大屏直接查这张表，30 秒刷新一次
SELECT
    minute,
    pv,
    uniqMerge(uv) AS uv
FROM mv_realtime_minute
WHERE minute >= now() - INTERVAL 10 MINUTE
GROUP BY minute, pv
ORDER BY minute;
flowchart LR EVT[埋点 SDK 上报] --> KAFKA[Kafka] KAFKA --> CK[ClickHouse 消费] CK --> MV[物化视图按分钟聚合] MV --> TBL[mv_realtime_minute] TBL --> GRAFANA[Grafana 大屏] style TBL fill:#f0682a,stroke:#fff,color:#fff

这套架构我们在线上跑了两年，大屏刷新延迟稳定在 5 秒以内，业务方完全无感。

用 ClickHouse 做轻量数据仓库

小团队没数仓平台，直接用 ClickHouse 当"轻量数仓"完全够用。它支持 SummingMergeTree、AggregatingMergeTree，能把明细层 → 汇总层的建模做出来。我团队的分层是这样：

层表引擎内容
ODS 明细层MergeTree原始事件，全字段保留
DWD 清洗层ReplacingMergeTree去重、补维度、清洗脏数据
DWS 汇总层Summing/AggregatingMT按天/小时预聚合
ADS 应用层MergeTree 视图直接给报表查的宽表

别一上来就建四层，数据量小的时候 ODS + 一个物化视图就够了。等查询变慢、报表变多，再逐层拆分。

和 Kafka / Flink 集成

ClickHouse 接 Kafka 有两条路：

  • Kafka Engine + 物化视图：ClickHouse 自己消费，零额外组件。简单场景首选。
  • Flink 写入：Flink 做清洗、维表关联、窗口聚合，再批量写 ClickHouse。复杂 ETL 用这条。

Flink 写 ClickHouse 的关键是用官方 JDBC 批量 sink，攒够 5000 条或攒 1 秒再写，别逐条写：

// Flink JDBC sink 批量写入配置
JdbcExecutionOptions.builder()
    .withBatchSize(5000)          // 每批 5000 条
    .withBatchIntervalMs(1000)    // 或每秒刷一次
    .withMaxRetries(3)
    .build();
Flink 写 CH 别用 exactly-once

ClickHouse 不支持真正的事务，Flink 的两阶段提交（2PC）在这里其实是 at-least-once。你要接受"可能少量重复"，在下游用 ReplacingMergeTree 或 FINAL 去重就行。追求 exactly-once 反而会把写入吞吐拖垮。

数据生命周期管理

日志/埋点数据量涨得快，必须管好生命周期。我一般用 TTL 自动分层：

ALTER TABLE user_events
MODIFY TTL
    event_time + INTERVAL 7   DAY TO VOLUME 'fast_ssd',   -- 热数据 SSD 存 7 天
    event_time + INTERVAL 90  DAY TO DISK 'hdd',         -- 温数据 HDD 存 90 天
    event_time + INTERVAL 180 DAY DELETE;                -- 冷数据 180 天后删

这套冷热分层让我团队的存储成本砍了一半——热数据查得频繁放 SSD，历史数据没人查放便宜 HDD，超过保留期自动删。不用写任何 cron 任务。

FAQ

Q：ClickHouse 能替代 Elasticsearch 做日志检索吗？
聚合分析能，全文检索不能。你要"按状态码/时间聚合出报表"，CH 秒杀 ES；但要"全文搜索 error 关键词并高亮"，CH 就很勉强（虽然有 ngram 跳数索引，但远不如 ES 成熟）。日志场景通常是 ES 做检索 + CH 做分析，两者配合。

Q：埋点数据一天几亿条，ClickHouse 扛得住吗？
单机轻松扛。我单机 16C64G 扛过一天 5 亿条的写入，查询还能保持亚秒。扛不住了加副本做读扩展，分片做写扩展。

Q：Grafana 怎么接 ClickHouse？
装 Grafana 的 ClickHouse 插件，填 JDBC 地址就能用。写 SQL 查询直接作为 panel 数据源，时间字段选 event_time，Grafana 会自动加时间 WHERE 条件。

我的结论

ClickHouse 在 OLAP 实战里的定位非常清晰：事件流进来、物化视图预聚合、报表秒出、TTL 自动清理。日志分析、用户行为、实时报表这三类场景，它是我用过最省心的组合。别拿它做全文检索，别拿它做业务点查，别追求 exactly-once——把它放在"分析层"这个位置上，它就是最好的选择。最后一篇我们横向对比 ClickHouse、ES、Doris，帮你做最终选型。
