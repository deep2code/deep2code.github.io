ClickHouse OLAP 建模：星型模型、大宽表、SCD 与分层设计

🏷️ CK OLAP

写 OLAP 表最反直觉的一点是：你在 OLTP 里学到的范式化训练，在这里基本要反过来用。OLTP 消除冗余是为了让单行更新安全且便宜，而分析型负载根本不更新单行，它只关心「一次查询要扫多少字节」。这篇讲数据怎么组织成能被高效扫描的形态。引擎的列存与向量化原理详见站内《ClickHouse 架构与核心特性》，分布式拓扑详见《ClickHouse 集群与分布式表》，与 Doris、Elasticsearch 的选型对比详见《ClickHouse vs Elasticsearch vs Doris》。

OLAP 建模的第一性原理：用冗余换扫描效率

星型、雪花，与最终的大宽表

星型模型是一张事实表（订单、事件）加一圈维度表（用户、商品、地区），维度表直接挂在事实表上；雪花模型是把维度表再规范化一层（商品挂品类，品类挂一级类目）。这套方法论来自 MPP 和数仓时代，在 ClickHouse 上会遇到一个现实问题：ClickHouse 的 join 很贵，连星型模型的单层 join 都常常慢到无法接受，所以实践里往往一路退化到大宽表（One Big Table）。

在 ClickHouse 的可行性可行，前提是维表能进字典不推荐推荐，是最终形态

宽表在列存里之所以代价没那么大，原因有两条：不查的列完全不读，一张两百列的表只查五列，IO 就只有这五列；冗余的维度属性压缩率极高，城市名这种低基数字符串上了 LowCardinality 之后，一亿行的实际占用可能只有几十 MB。真实代价也要说清楚：一是维度属性变更时必须回刷历史（用户改了城市，是否要改历史订单里的城市，这是业务口径问题不是技术问题）；二是 ETL 变重，关联逻辑从查询时挪到了写入时，链路更长也更容易出故障。折中方案是把变化极少且高频使用的维度打平进宽表，把变化频繁或属性很多的维度留在字典里用 dictGet 查。

缓慢变化维：分析历史必须用当时的值

用户九月是青铜等级、十月升到黄金，那么「九月各等级用户的消费额」应该用哪个等级算？答案是九月的青铜。这不是性能问题，而是数据正确性问题，而且是报表口径争议里最常见的一类。用 dictGet 关联当前维度表的写法，会让历史报表的数字随维度变化而变动，昨天跑出来的月报今天再跑就不一样了。

SCD 类型做法历史可追溯在 ClickHouse 的落地适用
类型 1 覆盖直接更新维度表，不留历史否ReplacingMergeTree 写新版本，或字典自动重载纠错类变更，如修正错别字
类型 2 加生效区间新增一行并带 valid_from / valid_to是维表加区间列，关联时按事实时间落在区间内匹配等级、组织架构、价格这类有业务含义的变化
类型 3 加前值列保留 prev_level 一列只保留一步宽表多加一列只关心「最近一次变化」的场景
类型 2 的简化版：事实表快照写入事实时把当时的维度值冗余进去是最推荐，ETL 阶段打平，查询零 joinClickHouse 里的默认选择

这两类指标要分开设计

「按用户当时等级统计的历史消费」和「按用户当前等级统计的历史消费」是两个不同的业务指标，都合法，但必须在表设计上区分开：前者用事实表里冗余的快照维度列（如 user_level_snapshot），后者用 dictGet 实时查当前维度。一张表同时提供两列、并在字段命名上写清 snapshot 与 current，比事后解释报表为什么对不上要省事得多。

分层：ODS、DWD、DWS、ADS 在 ClickHouse 里怎么落

分层的意义在于把「解析清洗」「关联打平」「聚合汇总」三种变更频率完全不同的逻辑隔开，出问题时能定位到层、重跑时能只重跑一层。在 ClickHouse 里，前两层通常是 MergeTree 明细表加调度任务，后两层多用 AggregatingMergeTree 加物化视图。

-- DWD 明细层：维度已打平，既存快照维度也保留外键供 dictGet 用
CREATE TABLE dwd.order_detail
(
    order_id        String,
    tenant_id       UInt32,
    paid_at         DateTime CODEC(Delta, ZSTD(1)),
    user_id         UInt64,
    user_level_snap UInt8,                       -- 下单当时的等级，口径固定不随维表变化
    city_snap       LowCardinality(String),      -- 下单当时的城市
    sku_id          UInt64,
    category_snap   LowCardinality(String),
    amount          Decimal64(4),
    status          LowCardinality(String),
    updated_at      DateTime                     -- 版本列
)
ENGINE = ReplacingMergeTree(updated_at)
PARTITION BY toYYYYMMDD(paid_at)                 -- 按天分区，因为重跑粒度是天
ORDER BY (tenant_id, paid_at, order_id);

-- DWS 汇总层：天级指标，用 AggregatingMergeTree 存中间状态
CREATE TABLE dws.order_1d
(
    tenant_id     UInt32,
    stat_date     Date,
    city_snap     LowCardinality(String),
    order_cnt     SimpleAggregateFunction(sum, UInt64),
    gmv           SimpleAggregateFunction(sum, Decimal64(4)),
    buyer_state   AggregateFunction(uniqCombined, UInt64),
    avg_amt_state AggregateFunction(avg, Decimal64(4))
)
ENGINE = AggregatingMergeTree
PARTITION BY toYYYYMM(stat_date)
ORDER BY (tenant_id, stat_date, city_snap);

-- 物化视图把 DWD 的写入增量推到 DWS，注意写入侧一律 -State
CREATE MATERIALIZED VIEW dws.mv_order_1d TO dws.order_1d AS
SELECT tenant_id, toDate(paid_at) AS stat_date, city_snap,
       count()                       AS order_cnt,
       sum(amount)                   AS gmv,
       uniqCombinedState(user_id)    AS buyer_state,
       avgState(amount)              AS avg_amt_state
FROM dwd.order_detail
WHERE status != 'closed'
GROUP BY tenant_id, stat_date, city_snap;

-- 查询侧配对 -Merge，这是最容易写错的一步
SELECT stat_date, sum(order_cnt) AS orders, sum(gmv) AS gmv,
       uniqCombinedMerge(buyer_state) AS buyers,
       avgMerge(avg_amt_state)        AS avg_amount
FROM dws.order_1d
WHERE tenant_id = 42 AND stat_date >= today() - 30
GROUP BY stat_date ORDER BY stat_date;

时间序列与指标建模：宽表还是长表

指标数据有两种组织方式：宽表每个指标一列（cpu_pct、mem_pct、qps），长表用 metric_name 加 value 两列装所有指标。二者不是对错问题，取决于指标集合是否稳定。

维度宽表（一指标一列）长表（metric_name + value）
新增指标要 ALTER TABLE 加列不用改表，写入即可
单指标查询只读一列，最快要先按 metric_name 过滤，需把它放进排序键
多指标同时对比直接同行取列要做行转列（sumIf 或 groupArray），SQL 更啰嗦
压缩率高，同列同质数据较低，value 列混了不同量纲的数值
稀疏指标浪费，多数行该列为 0天然稀疏友好
适用指标集合稳定的业务看板指标由用户自定义、数量不可控的监控平台

时间粒度上，用三级汇总（分钟 / 小时 / 天）几乎是标准解法。收益的算法很直白：假设分钟级一天 1440 行每维度组合，小时级 24 行，天级 1 行。查一年的日趋势图，走天级是 365 行，走分钟级是 52 万行，差三个数量级。存储上小时级和天级加起来不到分钟级的 5%，几乎免费。关键是不要让上层直接查明细：看板固定查 DWS 或 ADS，明细层只留给排障和下钻。另外分钟级聚合表的 TTL 可以设得比天级短很多，比如分钟级留 7 天、小时级留 90 天、天级留 3 年。

幂等重跑是 ETL 的硬要求

任何离线任务都会失败重跑，也会因为口径修正而重算。能不能安全地重跑同一个时间段，是 ETL 设计里最硬的一条要求。在 ClickHouse 里，幂等的正确实现是「按分区整体替换」：先把数据算到临时表，再用 REPLACE PARTITION 原子替换目标分区。这样重跑一百次结果都一样，且切换瞬间完成。

-- 幂等重跑的标准流程：临时表 + 校验 + 原子替换
-- 1) 临时表结构与目标表完全一致（含 ENGINE / 分区键 / 排序键，否则 REPLACE 会拒绝）
CREATE TABLE IF NOT EXISTS dws.order_1d_tmp AS dws.order_1d;
ALTER TABLE dws.order_1d_tmp DROP PARTITION '202609';   -- 清掉上次残留

-- 2) 只重算目标区间，条件必须与分区边界对齐
INSERT INTO dws.order_1d_tmp
SELECT tenant_id, toDate(paid_at) AS stat_date, city_snap,
       count(), sum(amount), uniqCombinedState(user_id), avgState(amount)
FROM dwd.order_detail
WHERE paid_at >= '2026-09-01 00:00:00' AND paid_at < '2026-10-01 00:00:00'
  AND status != 'closed'
GROUP BY tenant_id, stat_date, city_snap;

-- 3) 上线前对账：行数与核心指标都要比，只比行数会漏掉金额错位
SELECT
    (SELECT sum(order_cnt) FROM dws.order_1d_tmp WHERE stat_date >= '2026-09-01') AS tmp_cnt,
    (SELECT count()        FROM dwd.order_detail
      WHERE paid_at >= '2026-09-01 00:00:00' AND paid_at < '2026-10-01 00:00:00'
        AND status != 'closed')                                                    AS src_cnt;

-- 4) 原子替换：这一步是元数据操作，秒级，且对查询是原子可见的
ALTER TABLE dws.order_1d REPLACE PARTITION '202609' FROM dws.order_1d_tmp;
DROP TABLE dws.order_1d_tmp;

-- 反面写法：DELETE 再 INSERT。为什么错？
-- ALTER TABLE ... DELETE 是异步 mutation，返回时删除还没完成，
-- 紧跟的 INSERT 会与旧数据共存，看板在这个窗口里读到的是双倍数据，
-- 而且 mutation 要重写整个 part，代价比 DROP PARTITION 高几个数量级。
幂等方式机制中间态代价评价
临时表 + REPLACE PARTITION元数据换目录无，原子可见需要一份临时空间推荐，ClickHouse 里最干净的方案
DROP PARTITION 后 INSERT先删后写有空洞窗口极低可接受，前提是看板能容忍几分钟缺数
ALTER DELETE 后 INSERT异步 mutation双倍数据窗口极高，重写 part错误做法
ReplacingMergeTree 覆盖写更高版本去重前有多份低适合流式更新，不适合批量重算
加 batch_id 列查询时过滤最新逻辑版本无存储翻倍，查询变复杂只在无法按分区切分时才考虑

数据质量上，最少要做三件事：行数与核心指标双向对账（只比行数会漏掉金额错位这类问题）；空值语义写进字段注释（0 表示「值为零」还是「没采集到」必须约定，因为 ClickHouse 里我们用默认值替代了 Nullable，这层语义只能靠约定保留）；去重策略只选一侧——要么写入侧靠 ReplacingMergeTree 和分区替换保证幂等，要么查询侧统一用 argMax 去重，两边都做会互相掩盖问题，出错时无法定位。

实时与离线的口径一致

Lambda 架构的经典问题不是维护两套代码累，而是两条链路的口径会悄悄分叉：实时链路为了低延迟用了近似去重，离线链路用精确去重；实时链路把退款算进当天，离线链路算进原单日期。到了月底对账，差异已经无法归因。

做法一致性维护成本适用
同一段 SQL 生成两条链路好，口径只有一处定义需要 SQL 模板化与参数化调度大多数业务看板
实时只做近似，离线覆盖修正最终一致，当天数字会变低可以接受「当天数据随时刷新」的场景
只做流式，用 ClickHouse 直接承接最好，单一链路中，要保证幂等与回溯能力数据量可控、无复杂回溯需求
两套独立代码差，长期必然分叉高不推荐

落地的关键动作是把聚合逻辑写成一份可参数化的 SQL 模板，实时链路以分钟为窗口调用它、离线链路以天为窗口调用它，指标定义只存在一处。同时把「时间语义」显式写清：用事件时间还是处理时间、迟到数据的容忍窗口多长、超出窗口的迟到数据进哪个分区，这三个问题不明确，两条链路必然对不上。

漏斗、留存、路径：ClickHouse 特有的分析函数

这三类需求如果用标准 SQL 写，都要多次自连接或窗口函数，在亿级数据上基本跑不动。ClickHouse 提供了专门的聚合函数，把它们压缩成一次扫描。

-- 1) 漏斗：windowFunnel(时间窗口秒数)(时间列, 条件1, 条件2, ...)
-- 返回每个用户在窗口内按顺序命中了前几个条件，然后按命中层级统计人数
SELECT
    level,
    count() AS users,
    round(100.0 * count() / max(total) OVER (), 2) AS pct
FROM
(
    SELECT user_id,
           windowFunnel(3600)(                       -- 1 小时内完成才算同一个漏斗
               event_time,
               event_type = 'view',                  -- 第 1 步：浏览
               event_type = 'add_cart',              -- 第 2 步：加购
               event_type = 'order',                 -- 第 3 步：下单
               event_type = 'pay'                    -- 第 4 步：支付
           ) AS level,
           count() OVER () AS total
    FROM events
    WHERE tenant_id = 42
      AND event_time >= '2026-09-01 00:00:00' AND event_time < '2026-09-08 00:00:00'
    GROUP BY user_id
)
GROUP BY level ORDER BY level DESC;
-- 注意：level = 3 表示走到第 3 步，统计「到达第 N 步的人数」要累加所有 level 大于等于 N 的分组

-- 2) 留存：retention(条件0, 条件1, 条件2, ...) 返回一个 0/1 数组
-- 条件0 是基准（首日活跃），后面每个条件相对基准判断是否留存
SELECT
    sum(r[1]) AS day0,
    sum(r[2]) AS day1,
    sum(r[3]) AS day7,
    round(100.0 * sum(r[2]) / sum(r[1]), 2) AS d1_rate,
    round(100.0 * sum(r[3]) / sum(r[1]), 2) AS d7_rate
FROM
(
    SELECT user_id,
           retention(
               min_date = toDate('2026-09-01'),                    -- 基准日活跃
               has(dates, toDate('2026-09-02')),                   -- 次日回来
               has(dates, toDate('2026-09-08'))                    -- 第 7 日回来
           ) AS r
    FROM
    (
        SELECT user_id, groupArray(toDate(event_time)) AS dates, min(toDate(event_time)) AS min_date
        FROM events
        WHERE tenant_id = 42
          AND event_time >= '2026-09-01 00:00:00' AND event_time < '2026-09-09 00:00:00'
        GROUP BY user_id
    )
)
WHERE r[1] = 1;

-- 3) 路径分析：sequenceMatch(模式)(时间列, 条件1, 条件2, ...)
-- 模式里 (?1) 引用第 1 个条件，.* 表示任意中间事件，(?t<=600) 限制相邻事件间隔秒数
SELECT
    countIf(pattern_hit)                                   AS matched_users,
    countIf(NOT pattern_hit)                               AS other_users
FROM
(
    SELECT user_id,
           sequenceMatch('(?1)(?t<=600)(?2).*(?3)')(       -- 浏览后 10 分钟内加购，之后某时下单
               event_time,
               event_type = 'view',
               event_type = 'add_cart',
               event_type = 'order'
           ) AS pattern_hit
    FROM events
    WHERE tenant_id = 42 AND event_time >= today() - 7
    GROUP BY user_id
);
-- sequenceCount 同样参数可以返回匹配次数；这两个函数的时间列必须与条件同一行，不能跨表

建模反模式与最容易踩的坑

反模式后果正确做法
把 OLTP 表结构原样同步过来当分析表排序键是自增主键，分析查询全表扫；还带一堆 Nullable按分析查询重新设计排序键与分区，类型全部收窄
维度表做得很大并频繁 join右表进内存，并发一高就 OOM打平进宽表，或定义 Dictionary 用 dictGet
没有分区无法按分区重跑，也无法 TTL 删数，只能靠 mutation按天或按月分区，与重跑粒度对齐
用高基数列做分区分区目录爆炸，merge 追不上，Too many parts分区键只用日期表达式
一张表混多种粒度明细行和汇总行共存，任何 sum 都会重复计算不同粒度分表，命名里带粒度后缀
指标定义散落在各个看板 SQL 里同一个 GMV 有五种算法，对不上账指标只在 DWS 层定义一次，看板只做展示
用 DELETE 加 INSERT 做重跑异步 mutation 导致双倍数据窗口REPLACE PARTITION 原子替换
❌
OLAP 建模的十条高频翻车点
  • 用当前维度值分析历史事实：用户改了城市，上个月的地区报表跟着变，跑一次一个数。历史口径必须用事实表里的快照维度列。
  • 照搬业务库表结构：把几十张规范化小表同步过来再 join，等于把 ClickHouse 最弱的能力当主路径用。
  • 分区粒度与重跑粒度不一致：按月分区却要按天重跑，最后只能 DELETE 加 INSERT，回到错误做法。
  • 重跑不幂等：直接 INSERT 追加，失败重试一次数据就翻倍，而且很难发现。
  • 只对账行数不对账指标：行数一致但金额字段错位或单位不对，对账照样通过。
  • 0 与「未采集」不分：用默认值替代 Nullable 之后不写语义约定，下游把未上报当成零值算进均值。
  • 写入侧和查询侧都做去重：两层去重互相掩盖，数据出错时无法定位是哪一层漏了。
  • 看板直查明细表：省了建汇总层，代价是每次打开看板扫几亿行，集群被看板刷新拖垮。
  • windowFunnel 的 level 语义理解错：level 是「最多走到第几步」，统计到达第 N 步的人数要累加 level 大于等于 N 的分组，直接取等号会算少。
  • 实时与离线各写一套 SQL：上线时对得上，三个月后必然分叉，而且没人能说清哪个是对的。
