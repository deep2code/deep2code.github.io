站内搜索的实现分层与选型

🏷️ 搜索

站内搜索的技术选择被一个数字决定：文档数。几百篇的静态站和千万条业务数据，正确答案完全不同，而中间那一档（几千到百万）最容易选错——上专用搜索引擎嫌重，继续用前端子串匹配又已经明显不够。这篇按「先量数据、再定档位、最后才调相关性」的顺序讲，本站自己的前端索引会作为第一档的实测样本贯穿全文。Elasticsearch 自身的索引结构与查询代价见上一步。

💡
这篇怎么读
  • ① 用法：先量三个数再定档位的三步判断，三档实现各自的最小可用形态，以及本站 search-index.json 的实测数字与它暴露出的三条具体边界。
  • ② 原理：三层实现的能力与数据量边界、中文切分为什么决定召回上限、BM25 的直觉与七个调参陷阱、同义词与纠错与补全各属于哪一层、索引更新的近实时代价与别名切换、业务权重与相关性冲突时的分层做法。
  • ③ 场景：搜索质量的六个度量口径与对应修法、按场景给出的实现选择，以及什么时候才真的需要向量检索。

① 用法 · 先量三个数，再定实现档位

选型之前先量三个数，不要凭感觉：索引体积（压缩后）、文档数、以及查询里有没有多词和排序需求。三个数一出来档位基本就定了。下面这段可以直接对着你自己的索引文件跑：

# 第一步：量索引体积。这是「首次搜索」要让用户等的下载量，不是页面首屏体积，
# 所以判断可用性要看 gzip 之后的数——CDN 上实际传输的是它
wc -c search-index.json
gzip -c search-index.json | wc -c

# 第二步：量文档数与正文截断长度。平均值贴着上限就说明「绝大多数文章的后半部分不在索引里」，
# 这时候搜不到是召回问题，不是排序问题，调权重一点用都没有
python3 -c "
import json
d = json.load(open('search-index.json'))
ls = [len(x['text']) for x in d]
print(len(d), 'docs   max', max(ls), '  avg', sum(ls) // len(ls))"

# 第三步：用体积除以文档数得到每篇的平均开销，按业务一年的增长量推算翻倍后的体积，
# 再对着下面那张表定档。定档看的是「明年的数」，不是今天的数
量到的数落在哪一档最小可用形态这一档的硬上限
几百篇，压缩后几百 KB 以内，只要「关键词出现过」第一档：前端全量索引加子串匹配构建期产出一份 JSON，前端首次输入时整份拉取没有相关性排序；多词查询失效；正文必须截断
上千到几千篇第一档半：前端小型倒排构建期切出词元倒排，按分组或首字母分块懒加载索引体积随词汇量增长；仍然没有高亮、同义词与纠错
十万到百万行，且必须与业务库同事务第二档 a：嵌入式全文检索虚拟表加外部内容表，再补齐增删改三个触发器中文要靠字符 n-gram 或外部切分；排序能力弱
百万行，且已经在用关系库第二档 b：库内全文检索生成列存检索向量，加倒排型索引中文切分要装扩展；打分模型不是 BM25；高频更新有明显写放大
千万以上，或需要分片、高亮、聚合、同义词第三档：专用搜索引擎显式 mapping 加别名与滚动索引，写入走别名与业务库只有最终一致，必须有可重放的同步链路
用户用自然语言描述意图、同一概念多种叫法在上面任一档之上叠一层向量召回与关键词召回并行，按排名融合精确标识符、错误码、型号上倒排永远更准，它是加法不是替代

本站就是第一档的一个实测样本，把它的数字摆出来比任何经验值都直观。构建期产出 search-index.json，页面顶部的搜索框在用户第一次输入时整份拉取（带去抖），之后对标题与正文做小写化的子串比较，最多渲染 15 条。当前是 329 篇文档、未压缩 1477799 字节（约 1.41 MB）、gzip 后约 594 KB，每篇正文被截断到 2000 字符、平均 1990 字符。这几个数字直接给出三条结论：

量到的事实推出的边界下一步该做什么
gzip 后约 594 KB，且随文档数线性增长传输量已经在第一档的上沿，移动端首次搜索能感知到等待文档数再翻一倍就要分块懒加载，或者把正文换成词元化后的倒排
平均正文长度 1990，截断上限 2000几乎每篇都被截到了上限，长文后半部分根本不在索引里按章节切成多条记录并带上锚点，召回和定位一起解决
匹配用的是小写化后的子串比较「连接池 超时」这类带空格的多词查询被当成一个整串去找，命中数骤降；命中之间也没有分数先做查询切分与多词取交集，再加覆盖度打分，这一步的收益远大于扩大索引

三档各自的最小可用代码就在原理层对应的小节里：第一档半的客户端倒排见「本站的做法」一节，第二档的嵌入式与库内全文检索见「索引更新」一节，第三档的建索引最小形态见上一步的 Elasticsearch 的索引结构与查询代价。先把档位定下来，再往下看这些取舍背后的原因。

② 原理 · 三层实现与它们各自的数据量边界

站内搜索没有统一解法，只有三层实现，每层都有明确的适用区间。选型的第一步不是比较产品，而是确认自己处在哪一层——把服务端方案用在几百篇文档的静态站上是浪费，把前端子串匹配用在上万条业务数据上是灾难。

层次可用数据量能提供的能力做不到的事运维成本
前端子串匹配几百篇短文档零后端、零延迟抖动、离线可用没有相关性排序，不支持多词乱序，正文只能存摘要只有构建期产出索引
前端小型倒排上千到几千篇词元级匹配、字段权重、覆盖度打分、前缀补全索引体积随文档数线性增长，首屏或首搜要承担下载与解析需要构建期切分与分块策略
单机嵌入式全文检索十万到百万行量级与业务库同事务、无额外服务、支持短语与布尔中文需要外部切分或字符 n-gram，排序能力弱随应用部署，几乎无独立运维
关系库内置全文检索百万行量级，取决于更新频率与业务数据同库同事务、可与其他条件组合过滤中文切分要靠扩展，打分模型不是 BM25，写放大明显无新增组件，但索引维护要调
专用搜索引擎千万级以上、分片横向扩展分词插件、BM25、聚合、高亮、同义词、补全、向量字段与业务库之间只有最终一致，需要同步链路集群、分片、容量与版本管理
向量检索取决于内存与索引参数语义相近召回、跨措辞与跨语言精确标识符匹配、可解释的排序理由模型版本、索引构建、过滤与召回的平衡

② 原理 · 本站的做法：前端全量索引的真实天花板

搞清这一节能解决的现象是：站内搜索「有时候搜得到有时候搜不到」，而且换个说法就完全没结果。用法层已经给了本站的实测数字，这里把边界逐条摆出来——同样的边界会出现在每一个「先用前端搜索顶着」的项目里，区别只是你什么时候撞上。

边界具体表现成因可行的下一步
没有相关性排序结果按索引文件里的原始顺序返回子串匹配只有命中与否，没有分数加入字段权重与命中次数，按覆盖度排序
多词查询失效词之间加空格后命中数骤降整个查询串被当成一个子串去匹配切分查询，多词取交集并按命中词数加权
正文后半部分搜不到长文里靠后的内容检索不到索引为控制体积对正文做了截断按章节切成多条记录，并携带锚点
首次搜索有下载成本第一次输入后要等索引到位整份索引在首次使用时拉取按分组或首字母分块懒加载，或预热
体积随文档数线性增长文档翻倍索引也翻倍每篇都带摘要文本摘要改短、词元化后去重、或迁到服务端
无近义与纠错用词与文中不一致就零结果字面匹配构建期把标题与标签展开成别名表

如果要在不引入后端的前提下往前走一步，方向是在客户端建一个极简倒排，而不是继续优化子串匹配。中文用二元组切分就能绕开词典依赖，英文与代码标识符按非字母数字边界切，打分只要覆盖度加字段权重就足以让结果顺序变得可用。

// 构建期与运行期共用同一套切分逻辑，这是搜索能不能对上的前提。
// 中文用二元组（相邻两字）避开词典依赖；拉丁与标识符按非字母数字边界切。
function tokenize(text) {
    const out = [];
    const lower = String(text).toLowerCase();
    const latin = lower.match(/[a-z0-9_]{2,}/g) || [];
    for (const w of latin) out.push(w);
    // 只保留连续的中日韩字符，再滑动取二元组
    const cjkRuns = lower.match(/[\u4e00-\u9fff]+/g) || [];
    for (const run of cjkRuns) {
        if (run.length === 1) { out.push(run); continue; }
        for (let i = 0; i + 1 < run.length; i++) out.push(run.slice(i, i + 2));
    }
    return out;
}

// 构建期：把 {url,title,text} 列表变成「词元 -> 命中文档与字段」的倒排表。
// 存词元而不是存整段正文，能让索引体积随词汇量而不是文本长度增长。
function buildIndex(docs) {
    const postings = new Map();
    docs.forEach(function (doc, docId) {
        const add = function (token, field) {
            let entry = postings.get(token);
            if (!entry) { entry = new Map(); postings.set(token, entry); }
            const cur = entry.get(docId) || { title: 0, text: 0 };
            cur[field] += 1;
            entry.set(docId, cur);
        };
        tokenize(doc.title).forEach(function (t) { add(t, 'title'); });
        tokenize(doc.text).forEach(function (t) { add(t, 'text'); });
    });
    return postings;
}

// 运行期：多词取交集，按「命中词元覆盖度 + 字段权重」排序。
// 覆盖度放在第一位，避免某个高频词元靠词频把不相关文档顶上来。
function search(postings, docs, query, limit) {
    const tokens = Array.from(new Set(tokenize(query)));
    if (!tokens.length) return [];
    const scores = new Map();
    const covered = new Map();
    tokens.forEach(function (t) {
        const entry = postings.get(t);
        if (!entry) return;
        // 命中文档数越多的词元区分度越低，用它的倒数压一压权重
        const idf = Math.log(1 + docs.length / (1 + entry.size));
        entry.forEach(function (tf, docId) {
            const gain = (tf.title * 3 + tf.text) * idf;
            scores.set(docId, (scores.get(docId) || 0) + gain);
            covered.set(docId, (covered.get(docId) || 0) + 1);
        });
    });
    return Array.from(scores.keys())
        .filter(function (docId) { return covered.get(docId) === tokens.length; })
        .sort(function (a, b) { return scores.get(b) - scores.get(a); })
        .slice(0, limit)
        .map(function (docId) { return docs[docId]; });
}

② 原理 · 中文切分决定召回上限

打分只能在召回集合里排序，召回不到的东西永远不会出现。中文没有天然词边界，切分策略因此直接决定了召回的天花板，它比任何打分参数都重要。

切分策略召回特征精度风险索引膨胀典型失效场景
按非字母数字边界切分中文几乎不切，整段落成极少数词元—低按词检索恒为空，这是「中文搜不到」最常见的根因
单字切分召回最高，几乎不漏误召回严重，需要短语约束中常用字词元过长，查询稍长就退化成大量求交
二元组召回高，不依赖词典，新词自动覆盖跨词边界的组合会误召回较高单字查询无法命中，需要单独处理
三元组精度优于二元组同样有跨边界组合高查询短于三个字符时无法匹配，中文两字词是高频查询
词典分词（细粒度）索引期覆盖多种切法，召回好词元冗余，短语位置计算更复杂中高新词、型号、代码标识符切错，必须维护自定义词典
词典分词（粗粒度）查询期更精确漏召回，长词不匹配短查询低索引期与查询期粒度不一致时结果恒空
词典加 n-gram 双字段两路召回互补需要合并打分最高两个字段的权重没调好，n-gram 的噪声会盖住词典结果

最值得记住的一条规则：索引期与查询期的切分必须匹配。常见搭配是索引期用细粒度、查询期用粗粒度，这样既保住召回也不让查询被切碎。反过来配（索引粗、查询细）就会出现查询词元在索引里根本不存在、结果恒为空的情况。排查中文搜索问题时，第一步永远是用分词接口把同一句话在两端各切一次对比，而不是先去改字段权重。

② 原理 · 相关性打分：BM25 的直觉与调参陷阱

BM25 只做了三件直觉上的事：某个词在文档里出现得越多越相关，但收益递减；这个词在整个集合里越罕见越有区分度；同样的词频出现在短文档里比出现在长文档里更有说服力。对应的两个参数分别控制词频饱和速度与长度归一强度，常见默认值在一点二与零点七五附近。真正的问题不在这两个数字，而在下面这些容易踩空的地方。

参数或行为默认倾向调错的后果正确做法
词频饱和参数让重复词的收益迅速递减调大后长文里堆关键词就能排到前面只在关键词堆砌确实有用的语料上调大，先看样本再动
长度归一参数惩罚长文档标题字段沿用正文的归一强度，长标题被过度惩罚标题等短字段单独设更弱的归一，或关闭长度归一
文档频率统计范围按分片各自统计数据量小而分片多时，同一文档落在不同分片得分不同，排序看起来随机小索引用单分片，或查询时启用全局文档频率
分数的绝对值没有上界，不可跨查询比较用固定阈值过滤相关性，换一个查询就全被滤掉或全部通过用排名而不是分数做截断，需要归一就在应用层按当次结果做
多字段查询类型默认取单字段最佳得分查询词分散在多个字段时得分偏低，跨字段的记录排不上来按语料形态在最佳字段与跨字段模式之间选，配合字段权重
查询期同义词展开扩大召回展开出的高频词稀释了原始罕见词的区分度，排序反而变差用支持多词的同义词结构，并给展开词更低权重
字段权重全部为一正文长、关键词多，标题命中被淹没标题、标签、别名给更高权重，这一项的收益通常大于调参数

调参之前先学会读打分解释：主流引擎都提供逐项分解，能看到每个词元贡献了多少、文档长度归一起了多大作用。凭感觉改参数、改完再凭感觉判断是否变好，是搜索项目里最费时间的循环。

② 原理 · 同义词、纠错与补全分别属于哪一层

这三件事经常被打包成「搜索优化」，实际上它们的实现位置、更新代价、失效方式完全不同，混在一起做必然互相干扰。

能力应放的位置更新代价失效方式
同义词（索引期展开）写入链路的切分之后改词典要重建索引词典变更前写入的文档不具备新同义关系，新旧数据行为不一致
同义词（查询期展开）查询改写阶段改词典即时生效影响短语匹配与打分，多词同义需要支持图结构的实现
拼写纠错检索之前的查询改写依赖词典与查询日志，可独立迭代把正确的专有名词纠成常见词，必须有白名单与「不改写」出口
模糊匹配检索阶段的召回兜底无需额外数据开销大且不区分语义，把它当纠错用会既慢又不准
前缀补全独立的补全结构或前缀切分字段需要单独构建与更新用通配符前缀查询替代等于放弃倒排，数据一多就拖垮
高亮返回阶段，基于同一套切分与切分绑定切分与索引不一致时高亮位置偏移，用户一眼就能看出问题
人工干预与置顶业务层，检索之后随时可改硬塞进打分会污染相关性，应作为独立的置顶列表

② 原理 · 索引更新、实时性与整体重建

「写入之后马上能搜到」在倒排结构上不是免费的。主流引擎采用近实时模型：写入先进内存缓冲与事务日志，刷新之后才形成可被搜索的段，默认刷新间隔在秒级。把它调得很小，段数量与合并压力都会上升，吞吐与查询延迟一起变差；批量导入时反而应该临时关闭刷新，导完再恢复。

-- 嵌入式全文检索：用外部内容表，避免正文在库里存两份
-- 三元组切分不依赖词典，但它要求查询串至少三个字符，
-- 中文两字词是高频查询，这一点必须在产品层面确认能接受
CREATE VIRTUAL TABLE doc_fts USING fts5(
    title, body,
    content='doc',            -- 外部内容表，索引只存倒排结构
    content_rowid='id',
    tokenize='trigram'
);

-- 外部内容表必须自己维护同步，漏了任何一个触发器都会出现搜得到但取不到内容
CREATE TRIGGER doc_ai AFTER INSERT ON doc BEGIN
    INSERT INTO doc_fts(rowid, title, body) VALUES (new.id, new.title, new.body);
END;
CREATE TRIGGER doc_ad AFTER DELETE ON doc BEGIN
    INSERT INTO doc_fts(doc_fts, rowid, title, body) VALUES ('delete', old.id, old.title, old.body);
END;
CREATE TRIGGER doc_au AFTER UPDATE ON doc BEGIN
    INSERT INTO doc_fts(doc_fts, rowid, title, body) VALUES ('delete', old.id, old.title, old.body);
    INSERT INTO doc_fts(rowid, title, body) VALUES (new.id, new.title, new.body);
END;

-- 查询：bm25 函数的返回值越小越相关，字段权重作为参数传入
SELECT d.id, d.title, bm25(doc_fts, 5.0, 1.0) AS score
FROM   doc_fts JOIN doc d ON d.id = doc_fts.rowid
WHERE  doc_fts MATCH ?
ORDER  BY score
LIMIT  20;

-- 关系库内置全文检索：中文需要额外的切分扩展，
-- 打分函数不是 BM25，长度归一要靠归一化参数显式指定
ALTER TABLE doc ADD COLUMN tsv tsvector
    GENERATED ALWAYS AS (to_tsvector('simple', coalesce(title, '') || ' ' || coalesce(body, ''))) STORED;
CREATE INDEX idx_doc_tsv ON doc USING gin (tsv);

② 原理 · 业务权重与相关性的冲突

几乎所有站内搜索最后都要面对同一个矛盾：产品希望新内容、热门内容、自营内容排在前面，而相关性只管文本匹配。处理方式的好坏差别很大。

最糟的做法是把业务分直接加到相关性分上。相关性分没有上界、不可跨查询比较，业务分通常有自己的量纲（浏览量、时间差、库存），两者相加的结果是权重在不同查询下漂移：某些查询里业务分完全被淹没，另一些查询里业务分反过来压倒文本相关性，而且没人说得清为什么。

可控的做法是分层。第一层用相关性召回并截断，只保留文本上确实沾边的候选；第二层在候选集内用有界函数把业务信号归一后参与排序，比如把热度过一个饱和函数、把时间差过一个衰减函数，让每个信号的贡献都落在已知区间里；第三层把强干预（置顶、屏蔽、人工绑定）做成独立列表，在返回前应用，不进打分公式。这样每一层都可独立解释和回滚。

还有两个细节容易忽略：其一，业务信号必须先做单调变换再参与，原始浏览量的长尾会让头部内容锁死所有查询；其二，时效衰减的半衰期要按内容类型区分，技术文档与资讯的合理衰减速度完全不同，用一套参数一定有一边不对。

{

          }
        },

            "saturation": {},
            "boost": 1.0

        }

        { "terms": { "id": [] } }
      ]
    }
  },
  "size": 20,
  "explain": false
}

这段查询里有三个刻意的选择。文本匹配放在 must 里，保证候选一定文本相关；业务信号用有界的饱和函数进 should，浏览量再高也只贡献一个有上限的加成，不会把不相关文档顶上来；过滤条件放 filter 不参与打分，避免过滤逻辑污染相关性。置顶与屏蔽不写进这段查询，而是在应用层用独立列表处理——写进打分公式的干预，事后没人能解释为什么某条排在第三。

③ 场景 · 质量度量：先有埋点才有优化

搜索质量不能靠感觉。上线第一天就该把查询、改写后的查询、结果集标识、点击位次、是否无结果记下来，否则后面所有优化都无法验证。

③ 场景 · 按场景给出的实现选择与不适用边界

把前面的量级判断和能力取舍合到一张表上。注意第三列：每一档换来的能力都对应一项必须接受的代价，没有哪一档是纯升级。

场景该怎么做为什么代价
技术博客、文档站，几百篇内容，纯静态托管构建期产出索引，前端匹配；把预算花在切分和覆盖度打分上零后端、离线可用，这个规模下服务端化带来的是运维成本不是体验提升没有高亮、同义词与纠错；索引体积随文档数线性增长，要盯着压缩后的传输量
后台管理系统里的列表搜索用关系库的全文检索或前缀索引，别引入新组件数据必须与业务库同事务，且并发量低中文切分要装扩展；打分能力弱，通常只能按时间或业务字段排序
电商商品、内容平台的主搜索专用搜索引擎，数据库为权威源，同步链路可重放需要分词插件、字段权重、聚合、高亮、同义词，这些只有第三档齐备最终一致；同步链路是新的故障点，必须有整体重建与别名回滚路径
日志、埋点这类只按时间与关键词查的数据专用搜索引擎加滚动索引，或直接用日志系统写多读少、按时间整段淘汰要维护生命周期策略；查询不带时间范围就会扫全量
用户会用自然语言提问，或同一概念叫法很多在关键词召回之上叠向量召回，用排名融合合并两路两路分数量纲不同，直接相加没有意义要维护嵌入模型版本；过滤条件与近邻搜索的交互会拉低召回率
查询以订单号、错误码、型号、SKU 为主只做关键词层，把预算花在词典、别名与排序上精确标识符上倒排永远更准，向量会给出语义相近但实际不对的结果用户换一种说法就搜不到，需要靠查询日志持续补别名
搜索结果要带业务干预（置顶、屏蔽、自营优先）相关性召回截断后，在候选集内用有界函数参与排序；强干预做成独立列表业务分与相关性分量纲不同，相加会让权重在不同查询间漂移多了一层重排逻辑，但每层都可独立解释与回滚
已经上线但「说不清哪里不好」先补埋点，把无结果率与点击位次拿到手，再动任何参数没有度量的调参是在做随机游走埋点本身要一两周才能积累出可用样本，这段时间只能忍着不动

不适用边界：站内搜索解决的是「按内容找文档」，它替代不了按主键的读写与事务，也替代不了统计分析。主键读写与事务留在关系库，索引与执行计划的取舍见 MySQL 与 PostgreSQL 索引优化；索引设计的通用原则见 索引设计；热点读用缓存挡，见 缓存的收益与代价；Elasticsearch 自身的分片、mapping、缓存与聚合代价在上一步的 Elasticsearch 的索引结构与查询代价；向量检索的形态、索引参数与检索增强生成链路见 向量数据库、产品与索引对比、在关系库里做向量检索 与 RAG 工程结构。

这一篇是搜索这条路径的收尾：上一步讲的是引擎内部的结构与代价，这一篇讲的是「在你的规模下到底该用哪一档、以及怎么知道它好不好」。

最容易踩的坑

❌
最容易踩的坑
  • 中文用按非字母数字边界切分的分词器：整段中文落成极少数几个词元，按词检索恒为空，这是「搜不到」的第一大原因。
  • 索引期与查询期用了不同粒度的切分：查询词元在索引里根本不存在，结果恒空，而打分参数怎么调都没用。
  • 用三元组切分却没确认查询长度：查询短于三个字符时无法匹配，而中文两字词恰恰是高频查询。
  • 前端子串匹配遇到带空格的多词查询：整个查询串被当成一个子串去找，命中数骤降。必须先切分查询再取交集。
  • 索引里的正文被截断却没人知道：平均长度贴着截断上限时，长文后半部分根本没进索引，用户以为是搜索坏了。
  • 拿相关性分数做固定阈值过滤：分数没有上界也不可跨查询比较，换个查询就全滤光或全通过。用排名截断，不要用分数。
  • 小索引开很多分片：文档频率按分片独立统计，同一文档落在不同分片得分不同，排序看起来随机。
  • 把业务分直接加到相关性分上：量纲不同导致权重在不同查询间漂移，问题既无法归因也无法回滚。
  • 用通配符前缀查询做补全：等于放弃倒排索引的能力，数据一多它就是全站最慢的查询。
  • 用模糊匹配当拼写纠错：它是召回兜底手段，开销大且不理解语义，纠错应该放在查询改写阶段。
  • 同义词只在索引期展开：改一次词典就要全量重建，而且变更前后写入的数据行为不一致。
  • 把刷新间隔调到极小追求实时：段数量与合并压力上升，吞吐和查询延迟一起变差；批量导入时应该反向操作，先关掉刷新。
  • 直接替换线上索引而不是用别名切换：出问题无法快速回滚，映射变更还可能导致整段时间不可搜索。
  • 外部内容表只写了插入触发器：更新与删除不同步，出现「搜得到但取不到内容」的幽灵结果。
  • 没有埋点就开始调参：无结果率、点击位次、改写率都拿不到，所有改动都只能凭感觉判断好坏。
  • 指望向量检索解决精确匹配：订单号、错误码、型号这类查询上，它会返回语义相近但实际不对的结果。
