Elasticsearch 的索引结构与查询代价

🏷️ Elasticsearch

「Elasticsearch 快是因为倒排索引」这句话只对了三分之一。倒排索引只回答一个问题：哪些文档包含这个词。排序、聚合要的是反向问题——这个文档在某个字段上的值是多少；数值和日期的范围查询走的是另一套结构；把文档内容取回来又是第三套。一个查询慢在哪、为什么关掉某个 mapping 选项就报错、为什么聚合会把堆打满，全都取决于它落在哪套结构上。这篇按「结构决定代价」的顺序讲：三种存储结构、mapping 与分析器、segment 生命周期、分片规划、缓存与查询上下文、分页与聚合，最后是集群角色与选主。

一个分片里其实有三套存储结构

一个主分片就是一个完整的 Lucene index，内部由若干不可变的 segment 组成。每个 segment 里并排放着几类用途完全不同的数据文件，理解它们的分工是读懂查询代价的前提。

由此可以推出两条实践结论。第一，「只用来展示、不参与检索」的大字段应该同时 index: false 和 doc_values: false，它只留在 _source 里，磁盘和缓存压力都会明显下降。第二，永远不要为了对 text 字段排序去开 fielddata，正确做法是加一个 keyword 子字段——这也是 ES 默认动态映射会替你做的事。

mapping 与分析器决定了你「能查到什么」

ES 里检索能力的上限在写入时就被 mapping 锁定了：查询只能查到分析器产出的 token。同一段文本，用 standard 分析器写入的中文会被切成单字，用 ik_smart 写入会切成词；而查询时如果 search_analyzer 与写入时不一致，就会出现「明明有这条数据却查不到」。索引已经建好后改分析器不会重写历史数据，只能 reindex。

比分析器更常出事的是动态映射。ES 默认 dynamic: true，遇到没见过的字段就自动推断类型并写进 mapping。把不可枚举的东西当字段名（指标名、用户 ID、业务自定义标签作为 JSON key）就会触发映射爆炸：字段数撞上 index.mapping.total_fields.limit（默认 1000）后写入直接失败，而在撞上之前，集群状态已经因为巨大的 mapping 变得臃肿，每次 mapping 更新都要全集群同步。

这段 mapping 里有四个刻意的选择：dynamic: strict 让未声明字段直接报错而不是悄悄进 mapping；raw_payload 关掉索引与正排，只做展示；labels 用 flattened 承接业务自定义的键值对，整个对象只占一个字段位；trace_id 只做等值查询，不需要排序聚合，关掉 doc_values 省一份磁盘。另外 ignore_above: 256 是静默生效的——超过 256 字节的值不会报错，只是不进倒排索引，于是「这条数据存在但用 keyword 精确查不到」。

segment 生命周期：近实时的来源与代价

写入路径是：文档先进 in-memory buffer，同时追加到 translog；refresh 把 buffer 变成一个新 segment 并进入文件系统缓存，此刻它才能被搜索到；flush 执行 Lucene commit 与 fsync，把 segment 真正落盘并清空 translog；后台 merge 不断把小 segment 合并成大的，顺带真正回收被删除文档的空间。

stateDiagram-v2 [*] --> Buffer: index 请求 同时写 in-memory buffer 与 translog Buffer --> Segment: refresh 生成新 segment 进入文件系统缓存 此时可搜索 Segment --> Committed: flush 执行 fsync 并清空 translog Committed --> Merged: 后台 merge 合并小 segment Merged --> Merged: 继续合并 直到超过 max_merged_segment 后不再参与 Segment --> Marked: delete 与 update 只在 liv 文件里打标记 Marked --> Merged: 被删文档的空间只在 merge 时回收 note right of Buffer 崩溃恢复能力来自 translog 而不是 segment durability 为 request 时每个写请求响应前都要 fsync translog end note
参数默认值作用调错的后果
index.refresh_interval1s生成新 segment 的间隔，决定数据可见延迟调到 100ms 会产生海量小 segment，merge 压力和 CPU 一起上涨；批量导入时设 -1 再改回来才是正解
index.search.idle.after30s分片无搜索请求超过该时长后暂停后台 refresh低流量索引上「写完立刻查」会额外等一次 refresh，误判为 ES 丢数据
index.translog.durabilityrequestrequest 表示每个写请求返回前 fsync translog改成 async 后吞吐上升，但宕机会丢最近 sync_interval 内的写入
index.translog.flush_threshold_size512mbtranslog 超过该大小触发 flush调得过大时节点重启后 translog 重放时间显著变长
index.merge.policy.max_merged_segment5gb超过该大小的 segment 不再参与常规 merge调得过小会导致大量大 segment 永不合并，被删文档长期占盘
_forcemerge?max_num_segments=1手动把分片压成单个 segment，提升查询效率只能对不再写入的索引做；对活跃索引执行会产生远超 5gb 的 segment，此后被删文档永不回收

顺便纠正一个流传很广的说法：ES 并没有「每 30 分钟 flush 一次」的默认行为，那是很老版本文档留下的印象。现在 flush 主要由 translog 大小触发，具体的持久性保证由 translog.durability 决定，而不是 flush 周期。真正影响「宕机丢多少」的是 translog 策略，不是 refresh 也不是 flush 间隔。

分片规划：不可改的那个数字

主分片数在索引创建后不能原地改，因为路由公式 hash(_routing) % number_of_primary_shards 直接依赖它。能做的只有 split、shrink 或 reindex，三者都有前置条件。更重要的是分片不是免费的：每个分片是一个独立 Lucene index，有自己的词典、文件句柄、segment 元数据和 merge 线程配额，还要占一份集群状态。几百个索引每个都开 5 分片 1 副本，最后压垮集群的往往不是磁盘，而是主节点上的集群状态更新和数据节点的堆。

场景分片策略调整手段与前置条件典型失误
日志、指标等时序写入按别名加 rollover 滚动新索引，单分片控制在几十 GB用 ILM 管理 hot/warm/cold 迁移与删除建一个巨型索引开 50 分片，冷数据和热数据混在一起无法分层
业务实体检索（商品、订单）按总量估算，宁少勿多；容量不足时 splitsplit 要求目标分片数是源的整数倍，且索引先置只读为「以后扩容」预留几十个分片，小索引被分片开销吃掉性能
历史归档只读索引shrink 到 1 分片再 forcemergeshrink 要求所有主分片副本先搬到同一节点且索引只读对还在写的索引执行 forcemerge

单分片过热（写入或查询集中）增加分片数并让路由分散，或用自定义 routing 聚拢自定义 routing 后查询必须带同样的 routing加副本试图解决写入瓶颈，副本只分担读

query 与 filter：打分、执行顺序与三层缓存

bool 查询里 must/should 属于 query 上下文，要算相关性分数；filter/must_not 属于 filter 上下文，只判断「是否匹配」，不打分，因此可以被缓存。这里的关键不是「filter 更快」，而是三层缓存各有各的命中条件，绝大多数人以为命中了其实没有。

缓存层缓存什么命中条件失效与陷阱
node query cachefilter 上下文下查询在某个 segment 上的匹配位图同一 filter 反复出现且代价不低；文档数太少的 segment 会被跳过segment 被 merge 后缓存作废；偶发一次的 filter 不会进缓存
shard request cache整个请求的结果（命中数、聚合结果，不含 hits 内容）只对 size 为 0 的请求生效缓存键是完整请求体，带 now 这种动态时间值时永远不命中，必须做时间取整
filesystem cache（操作系统）segment 文件的页缓存物理内存中留给它的空间足够堆配得过大就是在挤压它；这才是 ES 延迟的主要决定因素
fielddata cachetext 字段的正排值（堆内）显式开启 fielddata 后高基数字段会直接把堆打满，circuit breaker 默认在 40% 处拦截

所以「按时间过滤最近一小时」的正确写法不是 gte: now-1h，而是 gte: now-1h/m 之类的取整形式：取整后同一分钟内的所有请求共享同一个缓存键，shard request cache 和 node query cache 才有机会命中。这是仪表盘类查询最便宜的一次优化。

深分页、search_after 与聚合的内存风险

sequenceDiagram participant C as 客户端 participant N as 协调节点 participant S1 as 分片 1 participant S2 as 分片 2 C ->> N: search from 9980 size 20 按相关性排序 N ->> S1: query 阶段 请求前 10000 条的 docid 与分数 N ->> S2: query 阶段 同样请求前 10000 条 S1 -->> N: 10000 组 docid 与分数 S2 -->> N: 10000 组 docid 与分数 Note over N: 协调节点在堆内归并 分片数乘以 from 加 size 条记录 再丢掉前 9980 条 N ->> S1: fetch 阶段 按最终 docid 取 _source S1 -->> N: 文档内容 N -->> C: 返回 20 条 Note over C,S2: 代价只与翻多深有关 与最终返回几条无关

这就是 index.max_result_window 默认卡在 10000 的原因，也是为什么把它调大是在饮鸩止渴——分片越多、页码越深，协调节点的归并内存与网络传输量线性放大。正确的替代是 search_after：用上一页最后一条的排序值做游标，每个分片只返回游标之后的 size 条。它有两个硬性要求：排序字段组合必须唯一（否则会漏数据或重复，通常追加一个 tiebreaker），以及最好配合 point in time 拿到稳定快照。

# 1) 开一个 point in time，拿到 pit id；keep_alive 只要覆盖整次翻页即可
curl -s -XPOST 'http://es:9200/orders/_pit?keep_alive=2m'

# 2) 用 search_after 翻页：sort 必须包含唯一 tiebreaker（配合 pit 时用 _shard_doc 最稳）
curl -s -XPOST 'http://es:9200/_search' -H 'Content-Type: application/json' -d '{
  "size": 100,
  "query": { "bool": { "filter": [ { "range": { "created_at": { "gte": "now-1h/m" } } } ] } },
  "pit": { "id": "PIT_ID_HERE", "keep_alive": "2m" },
  "sort": [ { "created_at": "asc" }, { "_shard_doc": "asc" } ],
  "search_after": [1758672000000, 4096],
  "track_total_hits": false
}'

# 3) 翻完必须显式关闭 pit：它会持有 segment 不被回收，忘关等于慢性磁盘泄漏
curl -s -XDELETE 'http://es:9200/_pit' -H 'Content-Type: application/json' -d '{"id":"PIT_ID_HERE"}'

聚合的风险在另一个方向：桶的数量由数据决定，不由请求决定。terms 聚合的 size 只控制返回多少个桶，分片上实际要统计的是 shard_size 个（默认比 size 更大），高基数字段加上嵌套子聚合，桶数是乘法关系，很容易撞上 search.max_buckets（默认 65536）或直接触发 circuit breaker。另外 terms 聚合在多分片下的计数本身就是近似的，响应里的 doc_count_error_upper_bound 就是误差上界；需要精确排序的 top-N 只能靠提高 shard_size 逼近，或改用 composite 聚合分页遍历全部桶。

集群角色与 7.0 之后的选主机制

节点角色要显式规划：候选主节点（master-eligible）只做集群状态管理，不该同时承担数据和聚合压力，因为一次大聚合引发的长 GC 会让它失去心跳并触发选主。协调节点（不带任何 data/master 角色）负责接请求、归并结果，是深分页和大聚合的堆压力承受者，独立出来可以保护数据节点。数据节点在 7.x 之后细分为 content/hot/warm/cold/frozen，配合 ILM 做冷热分层。

选主机制上，discovery.zen.minimum_master_nodes 已在 7.0 移除——继续在配置文件里写它不会生效，只会让人误以为脑裂被防住了。现在集群维护一个投票配置，法定人数由它自动推导，节点加入或退出时自动调整。人工只需要做两件事：首次引导集群时用 cluster.initial_master_nodes 指定初始候选列表（之后必须删掉，否则重启时可能引导出第二个集群），以及永久下线候选主节点时使用投票排除接口，避免一次性移除过多候选把法定人数打破。

❌
最容易踩的坑
  • 对 text 字段排序或聚合，靠开 fielddata 硬解，高基数字段一次请求就把堆打满。
  • 以为 refresh_interval 是 1 秒就一定 1 秒可见，忽略 search idle 在低流量索引上会暂停后台 refresh。
  • 为了「实时」把 refresh_interval 调到毫秒级，制造海量小 segment，merge 与 CPU 双双飙升。
  • 对还在写入的索引执行 _forcemerge?max_num_segments=1，产出超过 max_merged_segment 的巨型 segment，此后被删文档的空间永不回收。
  • 用不可枚举的业务值当 JSON key，映射爆炸撞上 total_fields.limit，写入直接失败。
  • 忘了 ignore_above: 256 是静默的，超长值不进倒排索引，表现为「数据存在但 keyword 查不到」。
  • 改了分析器却不 reindex，以为历史数据会自动按新分词重建。
  • 时间过滤写 now-1h 而不是取整形式，shard request cache 永远不命中。
  • 调大 max_result_window 解决深分页，协调节点内存与网络放大，最终 OOM。
  • 用 search_after 却没有唯一 tiebreaker，翻页时漏数据或重复；或者用完不关 point in time，segment 被长期持有。
  • 把 JVM 堆配到物理内存的大半（甚至超过 32GB 失去压缩指针），挤掉 filesystem cache，查询反而更慢。
  • 候选主节点同时兼任数据节点承接大聚合，一次长 GC 直接触发选主与集群抖动。
  • 配置文件里还留着 minimum_master_nodes，或首次引导后没删 cluster.initial_master_nodes，重启时引导出第二个集群。
  • 把 ES 当主库用：没有跨文档事务，refresh 前不可见，_version 冲突需要业务自己处理。
