从零理解向量检索：Embedding 与相似度的直觉

🏷️ 向量数据库

向量检索这件事，剥掉「AI」「语义」这些词之后，只剩两个动作：把一段内容变成一串固定长度的数字，然后在一堆数字串里找最接近的几个。难点不在这两步本身，而在于搞清楚这串数字表达了什么、什么时候它比关键词匹配强、什么时候它反而更差、以及那个「相似度 0.82」到底能不能拿来做判断。这篇把这些直觉建立起来，同时给出「多少数据量该用什么方案」的明确界线。

Embedding 到底是什么

Embedding 模型做的事，是把非结构化数据（一段文字、一张图、一段音频）映射成一个固定长度的浮点数组，并且这个映射满足一个关键性质：语义相近的内容，映射出来的向量在空间里距离也近。注意这个性质不是数学上自动成立的，而是训练出来的——模型见过大量「这两句话意思相同、那两句话意思不同」的样本，通过对比学习把相似的往一起拉、不相似的往外推，最后得到这个映射函数。

所以「语义距离」本质上是模型的判断，不是客观真理。换个模型、换个训练语料，同样两段文本的距离就变了。这是后面所有实践建议的根源。

它带来的能力是关键词匹配做不到的。用户搜「便宜的手机」，倒排索引只能命中包含「便宜」和「手机」的文档，而向量检索能召回「性价比高的智能机」「千元价位安卓机推荐」这类一个字都不重合的内容，因为在训练数据里这些说法经常出现在相似的上下文中。同样，搜「电脑开机后风扇狂转」能召回标题是「笔记本散热异常排查」的文档。

但反过来，精确匹配是向量检索的短板，而且是结构性的短板。Embedding 的整个设计目标是「抹掉表面差异、保留语义」，而订单号、SKU 型号、错误码、人名恰恰是「表面差异就是全部信息」的那类数据。

查询类型关键词 / 倒排检索向量检索说明

最后一行值得单独记住

「不含糖的饮料」和「含糖的饮料」在多数 Embedding 模型下向量非常接近——因为它们讨论的话题完全一样，只差一个否定词，而对比学习目标并不特别惩罚这种差异。凡是语义里带「不」「除了」「排除」的需求，都应该翻译成结构化的过滤条件，而不是塞进查询文本里。这是从「用向量解决一切」回到工程现实的第一步。

维度从哪来，为什么不同模型的向量不能混用

向量的长度不是你选的，是模型输出层决定的。常见的几档维度和它们的代价：

维度典型模型单条 float32一百万条推荐用法
384all-MiniLM-L6、bge-small-zh1.5 KB1.4 GB召回粗排、边缘设备、量大且允许精度折扣
512 至 768bge-base-zh、m3e-base、text2vec3.0 KB2.9 GB中文场景的主力档，性价比最好
1024bge-large-zh、multilingual-e5-large4.0 KB3.8 GB对召回质量敏感、数据量中等
1536text-embedding-3-small、ada-0026.0 KB5.7 GB省事的默认选择，注意它支持维度截断
3072text-embedding-3-large12.0 KB11.4 GB确认过召回收益再用，成本是 768 维的四倍

维度越高，模型能表达的细微差别越多，但存储、内存带宽和每次距离计算的开销都线性增长。实测经验是从 768 升到 1536 的召回提升通常只有一到三个百分点，而成本翻倍。新一代模型支持维度截断（Matryoshka 表示学习），可以把 3072 维的输出直接取前 512 维再重新归一化，损失很小，这个能力值得优先利用。

更重要的一条纪律：不同模型、甚至同一模型的不同版本，产出的向量不在同一个空间里，绝对不能混用、不能互相比较、不能拼在一个集合里检索。它们只是碰巧都是 1536 个浮点数而已，就像两套不同的坐标系，坐标值相同不代表位置相同。实际后果是：如果你把新模型的向量插入了旧模型的集合，系统不会报错，检索结果会变成随机噪声，而且你很难从现象上定位到原因。所以向量记录里应该带上 model_name 和 model_version 字段，查询时校验一致。

这张图里有两个容易被忽略的设计决定。

第一，入库侧和查询侧必须用同一个模型同一个版本，而且文本预处理方式也要一致。很多模型对查询和文档使用不同的指令前缀（比如 BGE 系列要求查询侧加上「为这个句子生成表示以用于检索」这类前缀，文档侧不加），漏掉这个前缀会让召回质量明显下降。这是个纯配置问题，但排查起来非常费时间，因为一切都「正常工作」。

第二，向量库里不要存正文。它只存主键 ID、向量本身、以及真正要参与过滤的少量字段（租户 ID、状态、时间分桶、分类）。原因有三个：向量库的存储单价高且要常驻内存；向量库的更新和事务能力弱，正文改一次就要同步一次；重建索引时如果正文只在向量库里，你就没有可信的数据源。

注意时序图里 topK 取的是 30 而不是 5。召回阶段多取、展示阶段少给是标准做法，因为向量相似只是一个信号，最终顺序应该由业务规则（时间新鲜度、权限、销量、人工权重）参与决定。但也不要无脑放大：取 1000 条再展示 3 条纯属浪费算力，因为 ANN 的延迟随 K 增长，而且候选越多后处理越慢。经验区间是 K 取展示条数的 3 到 10 倍。

相似度分数没有绝对含义

这是新手最常犯的错误：在代码里写 if score > 0.8 就判定相关。这个阈值几乎一定是错的，因为余弦相似度的分布完全取决于模型和语料。

现象为什么正确做法
某些模型下任意两段中文的相似度都在 0.7 以上模型的向量分布集中在一个窄锥形区域里，基线本来就高先测「随机不相关文本对」的分数分布，拿它当基线
换模型后 0.8 阈值筛不出任何结果新模型分数分布整体偏低，0.55 就已经是强相关阈值属于模型的配置项，随模型一起版本化
短查询配长文档分数偏低长度不匹配导致语义被稀释按查询长度分桶标定，或改进切分粒度
同一个分数在不同领域含义不同法律文书彼此都很像，社交短文本差异大按业务语料分别标定，不要跨领域复用
Top-1 分数很高但内容明显不相关查询里有模型没见过的专有名词，退化成噪声匹配加最低分数门槛只用于兜底，主要靠重排

正确的姿势是：用 Top-K 加业务规则或重排模型来定结果，只把相似度阈值当作「兜底截断」，并且这个阈值必须用自己的数据标定出来。标定方法很直接：

import numpy as np

def calibrate_threshold(model, pos_pairs, neg_pairs):
    """用标注好的正负样本对标定相似度阈值。
    pos_pairs: 人工确认「应该被召回」的 query 与 doc 对，50 到 200 对就够
    neg_pairs: 随机配对的不相关对，数量至少是正样本的 5 倍
    """
    def sim(pairs):
        q = model.encode([p[0] for p in pairs], normalize_embeddings=True)
        d = model.encode([p[1] for p in pairs], normalize_embeddings=True)
        return np.sum(q * d, axis=1)          # 归一化后点积即余弦相似度

    pos, neg = sim(pos_pairs), sim(neg_pairs)
    print("正样本 分位数 p05/p50/p95:", np.percentile(pos, [5, 50, 95]).round(3))
    print("负样本 分位数 p05/p50/p95:", np.percentile(neg, [5, 50, 95]).round(3))

    # 取负样本的 p99 作为兜底阈值：宁可多放进来交给重排，也不要漏
    floor = float(np.percentile(neg, 99))
    kept = float(np.mean(np.greater(pos, floor)))
    print(f"建议兜底阈值 {floor:.3f}，此时正样本保留率 {kept:.1%}")
    return floor

# 关键在于打印两个分布的重叠程度。如果正负样本分数区间大面积重叠，
# 说明这个模型在你的语料上区分度不足，换阈值没用，应该换模型或做微调。

这段脚本的价值不只是给出一个数字，更重要的是看正负样本分数分布的重叠程度。重叠严重说明模型在你的领域上区分度不够，这时候调阈值是徒劳的——该做的是换模型、加领域微调，或者改用关键词加向量的混合检索。

四类典型场景的实践参数

场景用什么度量K 取多少要不要过滤关键注意点
语义搜索（站内搜索、文档检索）余弦，或归一化后内积展示条数的 3 到 5 倍必须，租户和权限和状态要和关键词检索混排，否则精确查型号和订单号会明显变差
推荐召回（相似商品、猜你喜欢）内积，模长常编码热度200 至 1000，作为粗排候选必须，库存和地域和黑名单只是召回环节，后面一定接排序模型；要做多样性打散
去重与聚类（内容查重、图片指纹）欧氏或余弦，看特征类型K 取 1 至 10，靠阈值卡通常按时间窗过滤这是唯一强依赖高召回的场景，宁可用暴力精确扫描
RAG 检索跟着 Embedding 模型的训练目标20 至 50，交给重排取前 3 至 5需要，按知识库和文档权限分块策略和重排对效果的影响大于换向量库，详见站内 RAG 工程实践篇

第三行需要强调：去重和 1 比 N 比对这类场景，漏一条就是错一条，ANN 的 0.97 召回意味着百分之三的重复内容漏过去了。这类需求如果数据量允许，应该直接用精确暴力扫描，或者把 ANN 参数调到极高召回再配合精确复核。

最小可用方案怎么选

先说一个很多人不愿意听的结论：几万条数据根本不需要任何向量库，numpy 一个矩阵乘法就够了，而且比任何向量库都快。十万条 768 维向量总共 293 MB，全部放内存，一次查询就是一次矩阵与向量相乘，在普通服务器上几毫秒，召回率恒为 100%，没有索引要建、没有参数要调、没有新组件要运维。

import numpy as np

class BruteForceIndex:
    """几万到几十万条向量的完整可用实现。召回率 1.0，没有参数会调错。
    内存占用等于 n 乘 dim 乘 4 字节；十万条 768 维约 293 MB。"""

    def __init__(self, dim):
        self.dim = dim
        self.vecs = np.empty((0, dim), dtype=np.float32)
        self.ids = []

    def add(self, ids, vectors):
        v = np.asarray(vectors, dtype=np.float32)
        assert v.shape[1] == self.dim, "维度必须和模型输出一致"
        # 入库就归一化，之后所有检索都是纯点积，省掉每次查询的除法
        v /= np.linalg.norm(v, axis=1, keepdims=True) + 1e-12
        self.vecs = np.vstack([self.vecs, v])
        self.ids.extend(ids)

    def search(self, query, k=10, mask=None):
        q = np.asarray(query, dtype=np.float32)
        q /= np.linalg.norm(q) + 1e-12
        sims = self.vecs @ q                       # 一次 BLAS 矩阵向量乘，吃满 SIMD
        if mask is not None:                       # pre-filter：布尔数组，长度等于 n
            sims = np.where(mask, sims, -np.inf)   # 用负无穷排除，结果条数稳定
        k = min(k, len(self.ids))
        top = np.argpartition(-sims, k - 1)[:k]    # argpartition 比 argsort 快数倍
        top = top[np.argsort(-sims[top])]
        return [(self.ids[i], float(sims[i])) for i in top if np.isfinite(sims[i])]

最容易踩的坑

❌
上手向量检索的十个坑
  • 入库和查询用了不同模型或不同版本：不报错，结果变成噪声，排查极难。向量记录里必须带模型名和版本字段并在查询时校验。
  • 漏掉模型要求的查询侧指令前缀：BGE、E5 这类模型要求查询和文档用不同前缀，漏掉会让召回明显下降，但一切「看起来正常」。
  • 用内积却没归一化：模长大的向量天然占优，热门内容霸榜。要么入库就归一化，要么明确知道模长编码了什么。
  • 硬编码相似度阈值：0.8 在不同模型和不同语料下含义完全不同。阈值必须用自己的正负样本标定，并随模型一起版本化。
  • K 设成 100 却只展示 3 条：白烧算力，且 ANN 延迟随 K 增长。K 取展示条数的 3 到 10 倍即可。
  • 用向量检索查订单号和型号：Embedding 的设计目标就是抹掉表面差异，精确匹配请走主键或倒排索引。
  • 把否定语义塞进查询文本：「不含糖的饮料」和「含糖的饮料」向量非常接近，否定必须翻译成过滤条件。
  • 过滤用的元数据字段没建索引：向量检索本身几毫秒，过滤却要全表扫，整个查询慢在过滤上。
  • 把正文存在向量库里：更新代价高、重建索引时没有可信数据源。向量库只放 ID、向量和过滤字段。
  • 没为模型升级做预案：换模型意味着全量重算向量加重建索引，而且新旧向量不能共存于一个集合。要么双集合灰度切换，要么接受一段不可用窗口。
