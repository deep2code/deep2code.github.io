向量检索性能调优：召回率、延迟与成本三角

🏷️ 向量库优化

向量检索的性能问题几乎都能归到同一个三角：召回率、延迟、成本，三个里最多同时保两个。近似最近邻本质上是拿准确性换速度，所以「优化」这件事没有单一目标——任何调参动作都只是在这个三角上挪位置。这篇讲怎么量化地挪，而不是凭感觉试。ANN 索引结构本身的原理见站内「向量数据库总览」，pgvector 的具体参数与执行计划见站内「pgvector 能力边界与正确用法」，RAG 链路的工程问题见站内「RAG 检索侧数据工程」。

先把评测方法立起来，否则后面全是白干

只报 QPS 不报召回率的调优都是自欺欺人。把 ef_search 从 200 降到 10，QPS 能涨五倍，报告上漂亮得不行，而召回可能已经从 95% 掉到 55%，线上表现就是「答案越来越不靠谱，但没人说得清为什么」。所以第一步一定是造基准：关掉索引扫描、用暴力遍历算出每条 query 的真实 Top-K，落盘存下来当 ground truth。数据量大到暴力扫不动时，抽一个百万级子集单独建基准库，结论可以外推。

指标定义怎么测不看它的后果
recall@k返回的 k 条里有多少落在真实 Top-K 内与暴力检索的结果集求交，除以 k 再对 query 取平均参数越调越快，质量悄悄崩掉
P50 / P99 延迟单条查询端到端耗时分布客户端计时，覆盖真实并发下的表现只看平均值，长尾把上游超时打满
QPS（带召回约束）满足 recall 底线时的最大吞吐固定参数逐步加并发，直到 P99 触线拿低召回的数字做容量规划，上线即翻车
结果条数分布实际返回条数是否稳定等于 k统计返回行数小于 k 的请求占比带过滤检索长期少返回，被当成「数据缺失」排查
内存驻留率索引与向量数据有多少在页缓存里看缓冲区命中率、磁盘读块数压测在热缓存下通过，线上冷启动直接爆
单位成本每千次查询折算的内存与算力开销实例规格除以带约束的 QPS用三倍机器换来 2% 召回，没人算过这笔账

query 集合的取法比数量更重要：必须来自真实线上流量分布，随机生成的向量在高维空间里彼此近似等距，测出来的召回数字毫无意义。500 到 1000 条真实 query 足以把 recall 的波动压到一个百分点以内。

# 向量检索评测：先算 ground truth，再扫参画 recall-延迟曲线
import time
import numpy as np
import psycopg2

K = 10
QUERIES = np.load('queries.npy')     # 真实线上 query 的向量，不要用随机向量
conn = psycopg2.connect('dbname=app')
conn.autocommit = True

def topk(cur, q, k=K):
    cur.execute('SELECT id FROM doc_chunk ORDER BY embedding <=> %s::halfvec LIMIT %s',
                (q.tolist(), k))
    return [r[0] for r in cur.fetchall()]

# 1) ground truth：禁用索引扫描，强制走精确暴力计算，结果存下来反复复用
with conn.cursor() as cur:
    cur.execute('SET enable_indexscan = off')
    cur.execute('SET enable_indexonlyscan = off')
    truth = [set(topk(cur, q)) for q in QUERIES]

# 2) 扫参：每组参数同时量 recall@K 和延迟分布，两个数字必须成对记录
for ef in (10, 20, 40, 80, 160, 320):
    lat, hit = [], 0
    with conn.cursor() as cur:
        cur.execute('SET hnsw.ef_search = %s', (ef,))
        for i, q in enumerate(QUERIES):
            t0 = time.perf_counter()
            got = topk(cur, q)
            lat.append((time.perf_counter() - t0) * 1000)
            hit += len(truth[i] & set(got))
    lat.sort()
    print('ef_search=%-4d recall@%d=%.4f p50=%.1fms p99=%.1fms' % (
        ef, K, hit / (K * len(QUERIES)),
        lat[int(len(lat) * 0.50)], lat[int(len(lat) * 0.99)]))

调优决策路径：先判断瓶颈在哪一条边

三类参数：调大调小分别会怎样

参数要先分清生效阶段。建索引期参数（nlist、M、ef_construction、量化码本）固化在索引里，改动必须重建；查询期参数（nprobe、ef_search）是会话级的，可以按请求类型动态设。这个区别决定了上线前必须把建索引期参数定得宽裕一些——事后才发现 ef_construction 给小了，代价是几个小时的重建。

参数族生效阶段调大的后果调小的后果典型取值

nprobe / probesIVF查询召回升，延迟近似线性上升召回暴跌，默认值常常低到不可用从 nlist 的平方根起调

PQ 每子空间位数量化建索引码本更大、精度更高，训练时间涨码本粗糙，召回断崖式下跌固定 8 位，即每子空间 256 个码字

k 设大是被严重低估的成本项

很多系统习惯性取 Top-100 再在上层截断成 10 条。但 ef_search 必须不小于 k，k 从 10 涨到 100 会把索引需要遍历的候选规模整体推高一个量级，延迟涨得比想象中多。除非后面真的接了重排来消费这些条目，否则把 k 压到业务真正需要的值，往往是最省事的一次提速。

量化与降维：压缩比和召回损失怎么换

量化的收益是确定的（内存按比例下降），损失是必须实测的。经验顺序是先上 halfvec 或 SQ8 这类「几乎白拿」的压缩，再考虑 PQ 这类「必须配精排」的方案。PQ 能把 1536 维 float32 的 6KB 压到不到两百字节，压缩比上百倍，但单独使用时召回会明显下降，不配精排基本不能用于生产。

方案1536 维单条大小压缩比召回损失（经验值）是否必须精排适用场景
原始 float32（FLAT）约 6 KB1 倍0，它本身就是 ground truth不需要百万以下，或作为精排层
halfvec / float16约 3 KB2 倍通常 1 个百分点以内不需要默认就该打开的一档
SQ8（每维 1 字节）约 1.5 KB4 倍1 到 2 个百分点建议配内存吃紧但不想大改架构
PQ（192 子空间 8 位）约 192 字节30 倍以上5 到 10 个百分点甚至更多必须配亿级规模，内存是主要成本
二值化（每维 1 比特）约 192 字节32 倍损失很大必须配超大规模的第一层粗筛
Matryoshka 截断维度按截断比例线性下降2 到 4 倍模型专门训练过，损失可控看精度要求模型支持时最优雅的降维

降维这条路值得单独说。传统 PCA 降维要额外训练、维护投影矩阵，模型换代时还会全部失效。Matryoshka 表示学习让嵌入向量的前若干维就能独立使用，1536 维直接截成 512 维，检索质量只小幅下降——这是近两年最省事的降维手段，前提是模型方明确支持。判断方法很简单：用评测集分别测截断前后的 recall，能接受就截。

两阶段检索是大规模场景的标准做法，也是量化能落地的前提：粗召回阶段用压缩向量在索引上取 top-N（N 一般是 k 的 10 到 50 倍），精排阶段用原始向量对这 N 条做精确距离计算，重排出最终 k 条。内存按量化后的体积算，召回按原始向量算，两头的好处都拿到。

内存是向量检索的硬约束

这条要单独强调：HNSW 的图结构必须全量驻留内存才有性能。图遍历是典型的随机访问模式，一旦开始走磁盘，延迟会从个位数毫秒掉到几十上百毫秒，而且恶化很快——因为每跳都可能是一次新的随机读。这不是调参能解决的问题，只能从容量规划上解。

估算公式：常驻内存 ≈ 向量数 ×（每维字节 × 维度 + 8 字节头）+ 向量数 × M × 2 × 链接开销，再留 30% 以上余量给页缓存、连接和其他索引。第二项就是图结构开销，M 越大越明显。

规模维度与类型向量数据HNSW 图开销（M=16）建议实例内存装不下时的首选
100 万768 维 float32约 3 GB约 0.4 GB8 GB基本不会装不下
1000 万1024 维 halfvec约 20 GB约 4 GB48 GBhalfvec 红利已用掉，考虑分片
1000 万1536 维 float32约 60 GB约 4 GB96 GB先上 halfvec，再考虑 SQ8
1 亿1536 维 float32约 600 GB约 40 GB单机不现实PQ 加精排，或分布式分片

装不下时只有三条路，按改造代价从小到大：压缩（halfvec 到 SQ8 到 PQ，配精排补召回）、分片（按租户或时间分区，让单次检索只面对一个分片，这条常被忽略但收益巨大）、换面向磁盘的索引（DiskANN 一类方案的数据结构针对 SSD 随机读做过优化，用一部分召回和延迟换掉内存约束）。

批量、并发与 GPU：目标不同，做法相反

单条查询延迟和批量吞吐是两个不同的优化目标，很多看起来矛盾的建议其实是在说不同场景。交互式检索追求 P99，就要减少每跳等待、避免排队；离线批量打标或全库召回追求总吞吐，批量化能把连接、解析、距离计算的向量化开销全部摊薄，单条延迟变差但总时间可能缩短一个数量级。

维度在线交互式检索离线批量检索
优化目标P99 延迟总耗时与吞吐
批大小1，不要人为攒批几十到几百条一批
并发策略连接池固定，避免超过核数造成排队打满 CPU，可以适度超发
参数取法按 recall 底线取延迟最低的那档可以把 ef_search 开大换召回
扩容方式加只读副本分摊读，不动索引加分片并行跑
GPU 收益几乎没有，单条查询打不满 GPU明显，暴力计算和批量 ANN 都能吃满

GPU 的适用边界经常被夸大。GPU 擅长的是大批量密集距离计算：算 ground truth、离线全库互检、超大批量召回，这些场景加速比很可观。而在线单条查询走图索引是随机访存密集型，GPU 算力用不上，还要额外付一次主机到显存的拷贝；显存也远小于内存，能装下的数据量有限。除非有稳定的批量负载，否则 GPU 不是向量检索的优先选项。

写入与查询会互相拖累

持续写入会触发索引结构更新，和查询抢 CPU、抢页缓存，还会让内存里的图不断变动，P99 抖动是必然结果。「白天查得挺快，晚上批量导数据的时候慢得没法用」就是这个原因。两个解法：读写分离，让查询走只读副本，把抖动隔离在写侧；或者对批量导入采用影子索引加原子切换——导入期间先不动线上索引，离线建好新索引，再在一个事务里把索引名字对换，查询方完全感知不到。

-- 两阶段检索：压缩索引粗召回 200 条，再用原始向量精算 Top-10
SET hnsw.ef_search = 400;                 -- 粗召回阶段要放大，至少不小于 N
WITH rough AS MATERIALIZED (              -- MATERIALIZED 固定执行顺序，别让优化器打散
    SELECT id
    FROM doc_chunk
    ORDER BY embedding_half <=> $1::halfvec   -- 走常驻内存的压缩索引，快
    LIMIT 200
)
SELECT c.id, c.embedding <=> $2 AS dist   -- 原始 float32 精确计算，把召回补回来
FROM doc_chunk c
JOIN rough r ON r.id = c.id
ORDER BY dist
LIMIT 10;

-- 影子索引 + 原子切换：避免边写边建导致的查询抖动
CREATE INDEX CONCURRENTLY doc_chunk_emb_new ON doc_chunk
    USING hnsw (embedding_half halfvec_cosine_ops)
    WITH (m = 32, ef_construction = 200);   -- 新参数先建出来，用评测集和旧索引对比

BEGIN;                                      -- DDL 放进一个事务，查询始终看到一个有效索引
ALTER INDEX doc_chunk_emb      RENAME TO doc_chunk_emb_old;
ALTER INDEX doc_chunk_emb_new  RENAME TO doc_chunk_emb;
COMMIT;

SELECT pg_prewarm('doc_chunk_emb');         -- 切换后主动预热，避免第一批查询打到冷缓存
DROP INDEX CONCURRENTLY doc_chunk_emb_old;  -- 观察确认无需回退后再删

过滤条件的影响常常大于向量参数

带元数据过滤的向量检索有两种完全不同的执行路径，性能特征相反：过滤后候选很少（低选择率）时，先过滤再对候选精算距离是最优的，而且结果精确；过滤后候选很多（高选择率）时，先走 ANN 索引再逐个过滤更快，但可能凑不满 k 条。判断的关键在于过滤后剩余行数的估算，这正是关系型数据库承载向量检索的优势——优化器会真的算代价。

场景过滤后占比该走的路径常见错误做法正确优化手段
单租户占全库千分之一极低先过滤，再精算距离硬要走 ANN 索引，然后抱怨返回不足过滤字段建 B-tree，甚至按租户分区
按时间窗口取近一个月较低先过滤全库 ANN 之后在应用层筛时间按时间分区，只扫相关分区
只排除已下线文档很高先 ANN，再过滤为此建一堆组合索引打开迭代扫描兜底结果条数
多标签任意匹配不确定看统计信息实测凭感觉写 SQL 直接上线看执行计划里被过滤掉的行数再定
过滤字段没有索引任意—去调 ef_search先建元数据索引，收益通常大得多

性能问题排查清单：按顺序查，别跳步

线上说「向量检索慢」，按这个顺序查，八成问题在前四条就能定位，不要一上来就调参数。

顺序检查项怎么确认命中后怎么办
1索引到底有没有生效执行计划里是索引扫描，还是全表扫描加排序修 SQL 形态、核对操作符与 opclass
2索引和向量是否全量在内存看磁盘读块数与缓冲命中率扩内存、上 halfvec、或分片
3召回参数是不是给过头了ef_search 或 nprobe 当前值与曲线拐点对比按评测曲线回退到拐点
4k 是不是设得没必要地大看上层实际消费了多少条压到真正需要的值
5过滤字段有没有索引看执行计划里被过滤掉的行数建 B-tree、部分索引或分区
6是不是正在持续大批量写入看活动会话里的写入语句与复制延迟错峰、读写分离、影子索引切换
7并发是否超过 CPU 核数造成排队对比连接池上限、活动会话数与核数收紧连接池，加只读副本
8是不是每次查询都重算 Embedding拆分端到端耗时，看模型调用占比缓存 query 向量，批量调用

EXPLAIN (ANALYZE, BUFFERS)
SELECT id FROM doc_chunk WHERE tenant_id = 7
ORDER BY embedding <=> $1 LIMIT 10;

-- 2. 是不是在读磁盘：read 大、hit 小就说明没驻留内存
SELECT heap_blks_read, heap_blks_hit,
       round(100.0 * heap_blks_hit / nullif(heap_blks_hit + heap_blks_read, 0), 2) AS hit_pct
FROM pg_statio_user_tables WHERE relname = 'doc_chunk';

-- 3. 索引和表的实际体积，拿来和实例内存对照
SELECT c.relname, pg_size_pretty(pg_relation_size(c.oid)) AS sz
FROM pg_class c JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE n.nspname = 'public' AND c.relname LIKE 'doc_chunk%'
ORDER BY pg_relation_size(c.oid) DESC;

-- 4. 后台是不是有大批量写入在抢资源
SELECT pid, state, wait_event_type, now() - query_start AS run,
       left(query, 80) AS q
FROM pg_stat_activity
WHERE state <> 'idle' AND query NOT LIKE '%pg_stat_activity%'
ORDER BY run DESC LIMIT 10;

-- 5. 切换索引或重启后主动预热，避免冷缓存造成的假性能问题
SELECT pg_prewarm('doc_chunk_emb'), pg_prewarm('doc_chunk');
❌
向量检索调优最容易踩的坑
  • 只报 QPS 不报召回：把查询期参数调小，吞吐立刻翻倍，召回可能已经掉到六成，报告上完全看不出来。
  • 用随机向量做压测：高维空间里随机向量彼此近似等距，测出的召回和延迟都和线上无关。
  • 没有 ground truth 就开始调参：没有基准，任何改动都无法判断是变好还是变坏。
  • 在热缓存下压测：反复跑同一批 query，页缓存全命中，线上冷启动时延迟差一个数量级。
  • ef_search 小于 k：结果必然不全，常被误判成数据缺失而去查数据管道。
  • 习惯性取 Top-100 再截断：k 大一个量级会把候选遍历规模整体推高，而后面根本没有重排消费这些条目。
  • 只用 PQ 不做精排：压缩比上百倍的同时召回掉十个点，两阶段精排才是量化能落地的前提。
  • 以为内存不够可以靠调参解决：图结构走磁盘随机读是硬约束，只能压缩、分片或换磁盘索引。
  • 在线和离线用同一套参数：单条延迟和批量吞吐是相反的优化方向，批大小、并发、召回参数都该分开设。
  • 为在线单条查询上 GPU：打不满算力，还多一次主机到显存的拷贝，显存也装不下多少数据。
  • 边大批量写入边压测：索引更新和查询互相抢资源，量出来的 P99 没有参考价值，应改用影子索引切换。
  • 过滤字段不建索引，光调向量参数：低选择率场景下给元数据建索引的收益，通常远超把召回参数翻几倍。
  • 忽略 Embedding 调用耗时：端到端 P99 里模型调用常常占一半以上，只盯着向量库优化是找错了地方。
