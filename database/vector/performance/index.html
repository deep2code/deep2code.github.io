向量检索性能优化

🏷️ 向量数据库,性能优化

性能优化的核心矛盾

向量检索性能调优，本质是在三个变量间做权衡：召回率（recall）、延迟（latency）、资源占用（内存/CPU）。你把 recall 从 90% 拉到 99%，延迟可能翻三倍；你想把内存砍半，recall 又掉一截。

第一板斧：维度选择与降维

维度是线性成本——1024 维和 3072 维，存储和计算差 3 倍。所以降维是性价比最高的优化。两条路：

一是选支持降维的 Embedding 模型。OpenAI 的 text-embedding-3-large 支持 Matryoshka 截断，直接取前 N 维，1024 维取前 512，召回损失很小。

二是 PCA 降维。把高维向量投影到更低维子空间。注意：PCA 要用历史数据训练出投影矩阵，查询向量也要用同一个矩阵变换，否则空间不一致。

import numpy as np
from sklearn.decomposition import PCA

# 离线：用历史向量训练投影矩阵
train = np.load("train_embeddings.npy")     # (N, 1024)
pca = PCA(n_components=256).fit(train)

# 入库：降维后再存
reduced = pca.transform(train)               # (N, 256)

# 查询：同一个矩阵变换 query
def encode_query(q_vec):
    return pca.transform(q_vec.reshape(1, -1))[0]
PCA 不是免费的
降维能省一半内存和查询时间，但 recall 会有损失。我建议先用 Matryoshka 截断（零成本），不够再上 PCA。别一上来就把 1024 砍到 128，先测 recall，很多业务 512 维就够。

第二板斧：索引参数调优

HNSW 和 IVF 各有几个关键旋钮，调对了延迟能差好几倍。先把这些参数记住：

索引参数作用调大的影响
HNSWm每个节点连接数（构建期定）图更密，recall 升，内存升
HNSWef_construction建图时的搜索宽度建图质量高，构建慢
HNSWef_search查询时的搜索宽度recall 升，查询变慢
IVFlists聚类簇数一般取 sqrt(行数)
IVFnprobe查询扫几个簇recall 升，查询变慢

实战调优就两步：先固定 m/ef_construction（建图时定，m=16、ef_construction=128 是我的常用起点），然后在线上压测里调 ef_search 或 nprobe，画出 recall-延迟曲线，选你业务能接受的那个点。

# HNSW：调 ef_search，找到 recall 和延迟的平衡点
for ef in [16, 32, 64, 128, 256]:
    db.set_param("hnsw.ef_search", ef)
    recall, p99 = measure_recall_and_latency(queries, ground_truth)
    print(f"ef_search={ef}: recall={recall:.3f}, p99={p99:.1f}ms")

# IVF：调 nprobe，逻辑一样
for nprobe in [1, 5, 10, 20, 50]:
    db.set_param("ivf.nprobe", nprobe)
ef_search 别默认
默认 ef_search 往往偏小，你上线即"安全但不快"或"快但漏召回"。我每次上线都必画这条 recall-延迟曲线，再定参数。这是最被低估的一步。

第三板斧：量化（PQ/SQ/binary）

量化是把向量压缩存内存，是"内存不够、QPS 上不去"时的杀手锏。三种常见程度：

  • SQ（标量量化）：把 float32 压成 int8，体积缩 4 倍，recall 损失很小。性价比之王，先试它。
  • PQ（乘积量化）：把向量切成多段分别聚类，体积能缩 10~30 倍，但 recall 损失更大，需要重排序补偿。
  • Binary（二值化）：压成 0/1，体积缩 32 倍，用汉明距离，速度极快，recall 损失最大，适合对精度不敏感的粗筛。
量化方式压缩比recall 损失速度我的建议
无（float32）1x无基准小数据集
SQ84x很小快默认首选
PQ10~30x中等很快大数据量+重排
Binary32x大极快粗筛/海量初筛

注意：量化通常配合"先量化粗筛、再用原始向量精排"的两阶段策略。光靠量化后的距离排序，recall 不够；粗筛出候选再用原向量重排，才是标准做法。

第四板斧：分层检索

当数据量上亿、单索引扛不住，就做分层：第一层用最轻的索引（binary/PQ）从全量快速筛出几百条候选，第二层用精确索引在候选里精排。这和 RAG 里"粗召回+重排"是一个思路，只是搬到了向量层。

过滤与召回率的权衡

前面选型那篇提过，这里展开。带过滤的向量查询（"某租户/某时间范围内找相似"）有个大坑：ANN 索引是为全量建的，过滤后候选集被切碎，图上可能根本没有可达路径，recall 暴跌。

两种做法权衡：

  • 先过滤再向量搜索（pre-filter）：在过滤后的子集上做 ANN。子集小的时候准，但子集大了要重新扫。
  • 先向量再过滤（post-filter）：全量 ANN 捞出一批再过滤。简单，但过滤掉一半候选可能一个不剩。
多租户别一个大索引
我们一个多租户产品吃过亏：所有租户共用一个 HNSW 索引，按 tenant_id 过滤后小租户在图上几乎捞不到东西，recall 掉到 50%。后来改成大租户独立索引、小租户合并索引，问题解决。过滤比例极端时，按租户/分片拆索引往往更稳。

监控指标：盯什么

调优不能靠感觉，上线后至少盯这三个指标：

指标含义健康线（参考）
QPS每秒查询数看你的 SLA，持续压测水位
P50/P99 延迟中位/尾延迟P99 要单独看，别只看平均
Recall@k召回率定期用评测集回归，别让它悄悄掉
缓存命中率热点查询命中热点问题可加一层缓存

我一般单独维护一个黄金评测集（几百组 query + 标准答案），每次改索引参数、换模型、更新数据后都跑一遍 recall。很多线上事故不是"变慢"，而是"召回率悄悄掉了"，用户感觉答非所问但你没报警。

常见性能坑清单

  1. 没走索引：小表测试全走 Seq Scan，上线前先灌数据再 EXPLAIN。
  2. 度量和索引不匹配：余弦查询配了 L2 索引，等于没索引。
  3. 维度拉满：上来 3072 维，内存和延迟翻倍，先砍到 1024 试。
  4. ef_search/nprobe 用默认值：没画 recall-延迟曲线，拍脑袋上线。
  5. 过滤打碎索引：多租户/强过滤场景 recall 暴跌，要按租户拆索引。
  6. 在线建大索引：高峰期 CREATE INDEX 把 IO 打满，用 CONCURRENTLY 或低峰建。
  7. 不做 recall 回归：改完参数只看延迟，recall 掉了都不知道。

FAQ

Q：延迟和召回率到底怎么选？
先定业务底线：RAG 我一般要 recall@10 > 90%，P99 < 200ms。在这个约束下画曲线，参数往延迟最低那档靠。别追求 99% recall，那是另一个量级的成本。

Q：量化后 recall 掉多少算正常？
SQ8 掉 1~2% 以内算正常；PQ 掉 5~10% 要靠精排补；binary 掉得多，只适合粗筛。用你的评测集实测，别信厂商数字。

Q：热点查询慢怎么办？
在向量库前面加一层语义缓存——把高频 query 的向量和结果缓存起来，相似 query 直接命中。我们一个问答系统靠这个把 P99 砍了 40%。

我的结论

向量检索性能优化是一套组合拳：维度先砍（降维）、参数后调（ef_search/nprobe）、内存不够再量化（SQ 优先）、海量数据上分层检索、多租户按过滤拆索引。但一切优化的前提是——你有一个能量化 recall 和延迟的评测集。没有它，所有调参都是盲人摸象。
