pgvector 能力边界与正确用法

🏷️ pgvector

pgvector 的价值不在于「又多了一个向量库」，而在于向量列和业务表处在同一个事务、同一份备份、同一套权限体系里：一条 SQL 就能完成「向量召回 + JOIN 业务表 + 权限过滤 + 分页」。代价是它的能力边界比专用向量库窄，而且有好几个「不报错、但索引静默失效」的坑，小表上完全看不出来，数据一上量就突然慢几十倍。这篇只讲边界和正确用法：ANN 索引本身的原理与维度诅咒见站内「向量数据库总览」，与 Milvus / Qdrant 的横向选型见站内「Pinecone / Weaviate / Milvus 对比」，PG 自身的堆表与 HOT、VACUUM、EXPLAIN 判读、work_mem 这些基础见站内 PostgreSQL 系列，本文涉及时只指路不展开。

装什么版本，能存什么类型

pgvector 是 C 扩展，需要在每个 database 里单独 CREATE EXTENSION。版本差异非常大，很多网上的教程写于 0.4 时代，照抄会白白放弃这两年最重要的几项能力。上线前第一件事是查清服务端装的到底是哪个版本——托管云数据库经常落后社区一两个大版本。

版本关键新增能力没有它的后果
0.4 及以前只有 IVFFlat 索引召回-延迟曲线明显差一档，且新增数据会持续拉低召回
0.5.0HNSW 索引无法得到同延迟下更高召回的图索引
0.6.0HNSW 并行构建、向量列默认 storage 改为 external大表建索引只能单线程跑，时间乘以核数
0.7.0halfvec 半精度、sparsevec 稀疏向量、bit 汉明/杰卡德、L1 距离存储和索引内存多花一倍，稀疏检索只能自己造
0.8.0迭代索引扫描（iterative scan）、过滤场景下的计划改进带 WHERE 过滤时经常返回不足 K 条，只能在应用层打补丁

类型的选择直接决定存储量和索引能不能建起来。vector 类型本身最多支持 16000 维，但 HNSW 和 IVFFlat 对 vector 的索引维度上限是 2000 维；halfvec 用 16 位浮点，每维只占 2 字节，索引维度上限提到 4000 维。halfvec 能把存储和索引内存直接砍半，而主流文本嵌入模型的召回损失通常在一个百分点以内，这是 0.7 之后最值得无脑打开的一个开关——前提是用自己的评测集实测过。

CREATE EXTENSION IF NOT EXISTS vector;
-- 先确认版本：0.7 以下没有 halfvec，0.8 以下没有迭代扫描
SELECT extversion FROM pg_extension WHERE extname = 'vector';

-- 向量表故意做窄：只放主键、过滤字段和向量，宽业务字段留在原表 JOIN 回来
CREATE TABLE doc_chunk (
    id         bigserial PRIMARY KEY,
    doc_id     bigint        NOT NULL,   -- 增量更新和删除的抓手，没有它就只能全量重建
    tenant_id  int           NOT NULL,   -- 多租户过滤字段，查询时必须下推到 SQL
    model_ver  text          NOT NULL,   -- 向量属于哪个模型，换代灰度时用来区分
    embedding  halfvec(1024) NOT NULL    -- 半精度：存储和索引内存直接砍半
);

-- 过滤字段的 B-tree 索引：低选择率查询全靠它，收益常常大于调向量参数
CREATE INDEX doc_chunk_tenant_doc ON doc_chunk (tenant_id, doc_id);

-- HNSW：opclass 必须和查询里写的操作符对应，这里选余弦
CREATE INDEX doc_chunk_emb_hnsw ON doc_chunk
    USING hnsw (embedding halfvec_cosine_ops)
    WITH (m = 16, ef_construction = 64);

三种距离操作符与 opclass 的死规矩

这是 pgvector 最高频的生产事故，没有第二名。查询里用的距离操作符必须和建索引时声明的 opclass 严格对应，不匹配时 PostgreSQL 不会报错、不会告警，只会安静地退化成全表精确扫描。结果是完全正确的，所以测试环境里一切正常；等到线上表长到几百万行，一次查询要扫几个 GB，P99 直接崩掉。

「归一化之后余弦和内积等价，所以随便用哪个」是半句真话

对 L2 归一化过的向量，余弦距离和负内积给出的排序确实一致，这部分是对的。但索引的 opclass 匹配是按操作符符号做的，跟数学等价性无关：索引建成 vector_cosine_ops，查询写 <#> 照样不走索引。另外 <#> 返回的是负内积，直接把它当相似度展示给前端会出现「负分」。

IVFFlat 与 HNSW：真正的区别不是快慢

流传最广的错误说法是「IVFFlat 省内存所以大表用它」。实际上两者的原始向量都要落在同一张堆表里，IVFFlat 省掉的是图结构那部分开销和构建时间，查询时该读的向量页一样得读。真正的分水岭是：数据是不是一次性灌完、之后还写不写。IVFFlat 建索引时对现有数据做 k-means 聚类，聚类中心一旦定下来就不会再变，后续插入的新向量会被塞进最近的既有聚类里——能查到，但随着新数据占比上升，召回会持续下滑，需要周期性重建索引。HNSW 是增量构图，插入新点会真正参与建边，长期写入不掉召回。

参数的层次要分清：lists、m、ef_construction 是建索引时固化的，改它们必须重建索引；probes 和 ef_search 是会话级的查询旋钮，可以按请求类型动态设置。这意味着上线前必须把建索引期参数定得保守一点（宁可 ef_construction 大一些多花构建时间），因为事后调整代价高得多。

用 EXPLAIN 确认索引真的生效

向量索引的触发条件很窄：只有写成「ORDER BY 向量列 距离操作符 常量 升序 + LIMIT k」的形态才可能用上。缺 LIMIT、把排序改写成相似度降序、在距离外面套一层算术运算、或者查询参数没有被识别成同类型的向量，都会让优化器直接放弃索引。判读方法只有一条：看计划里出现的是 Index Scan using ... 配 Order By:，还是 Sort 配 Seq Scan。

SET hnsw.ef_search = 100;   -- 必须不小于 LIMIT 的 k，默认 40

-- 反例 1：没有 LIMIT，向量索引用不上，直接全表排序
EXPLAIN (ANALYZE, BUFFERS)
SELECT id FROM doc_chunk ORDER BY embedding <=> $1;
--  Sort  (actual rows=2000000 ...)
--    ->  Seq Scan on doc_chunk
-- 判读：Sort + Seq Scan = 没走索引

-- 反例 2：排序写成相似度降序（1 减距离），距离表达式被包了一层，索引失效
EXPLAIN SELECT id FROM doc_chunk
ORDER BY 1 - (embedding <=> $1) DESC LIMIT 10;
--  Limit -> Sort -> Seq Scan     仍然没走索引
-- 正确做法：SQL 里按距离升序取 Top-K，相似度在投影列里单独算给前端看

-- 反例 3：索引是 cosine，查询用 L2 操作符。不报错，静默全表扫
EXPLAIN SELECT id FROM doc_chunk ORDER BY embedding <-> $1 LIMIT 10;

-- 正例：操作符匹配 + 距离升序 + LIMIT
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, embedding <=> $1 AS dist
FROM doc_chunk ORDER BY embedding <=> $1 LIMIT 10;
--  Limit
--    ->  Index Scan using doc_chunk_emb_hnsw on doc_chunk
--          Order By: (embedding <=> $1)
-- 判读：Index Scan using ... + Order By = 真的用上了向量索引
计划片段含义该怎么办
Index Scan using xxx_hnsw + Order By:向量索引正常生效正常，接着看 Buffers 和耗时
Seq Scan + Sort完全没走向量索引检查 LIMIT、排序方向、操作符与 opclass
Rows Removed by Filter 数值很大走了向量索引但候选被过滤条件大量筛掉给过滤字段建索引，或打开迭代扫描
Bitmap Heap Scan + 上层 Sort选择了「先过滤后精算距离」的精确计划选择率低时这就是最优，不要强掰
实际返回行数小于 LIMIT索引候选耗尽，典型的过滤+ANN 问题开 iterative_scan，或调大 ef_search
Buffers 里 shared read 巨大向量数据或图结构没在内存里核对内存预算，考虑 halfvec 或换机型

过滤与向量检索结合：最大优势也是最大陷阱

这是 pgvector 相比专用向量库最实在的优势——过滤条件就是普通 SQL，优化器会真的做代价估算；也是最容易出现「结果诡异」的地方。同一条带 WHERE 的向量查询，PostgreSQL 可能生成两种完全不同的计划：

计划 A 在过滤后只剩几千行时反而是最优的，而且结果是精确的 Top-K，没有 ANN 的近似误差——很多人以为「不走向量索引就是出问题了」，这是误解。计划 B 的问题在于 HNSW 扫描只会吐出有限个候选（由 ef_search 决定），过滤掉一大半之后就凑不满 K 条，表现为「明明库里有几百条符合条件的文档，检索只返回 3 条」。0.8 引入的迭代扫描就是为这个场景准备的：候选不够时让索引继续往下扫，直到攒够 K 条或者撞到 max_scan_tuples 上限。

-- 结果不足 K 条的根治办法：0.8+ 的迭代扫描
SET hnsw.iterative_scan = relaxed_order;  -- strict_order 严格有序但更慢
SET hnsw.max_scan_tuples = 40000;         -- 迭代扫描上限，默认 20000
-- IVFFlat 对应的是 ivfflat.iterative_scan 和 ivfflat.max_probes

WITH hit AS MATERIALIZED (       -- MATERIALIZED 防止优化器把 LIMIT 推到奇怪的位置
    SELECT c.id, c.doc_id, c.embedding <=> $1 AS dist
    FROM doc_chunk c
    WHERE c.tenant_id = $2              -- 租户和权限一律下推，绝不留到应用层过滤
      AND c.model_ver = 'bge-m3-v1'     -- 换代灰度期间必须带上，否则新旧向量混在一起比
    ORDER BY c.embedding <=> $1
    LIMIT 50                            -- 粗召回放大到 50，给后面的过滤和重排留余量
)
SELECT d.id, d.title, d.updated_at, h.dist
FROM hit h
JOIN document d ON d.id = h.doc_id      -- 业务字段 JOIN 回来，同一快照，不会读到半删状态
WHERE d.status = 'published'
  AND d.acl_group = ANY($3)
ORDER BY h.dist
LIMIT 10;
✅
给元数据字段建索引，收益常常大于调向量参数

低选择率的过滤（比如单租户只占全库千分之一）最优解是让优化器走计划 A，前提是 tenant_id 上有可用的 B-tree 索引。再进一步，可以对大租户建部分索引（CREATE INDEX ... WHERE tenant_id = 7），或者直接按租户做分区表，让每次检索只面对自己那一份向量。这类改造的效果通常远超把 ef_search 从 40 调到 200。

建索引的内存、并行度与时间

HNSW 建索引是整个 pgvector 使用过程里最容易低估的一项工程成本。构图过程需要把整张图放进 maintenance_work_mem，装不下时 pgvector 会在日志里提示图已不适合放在维护内存中，然后退化成基于磁盘的构建方式，耗时可能拉长十倍以上。默认的 64MB 对任何真实规模的向量表都远远不够，建索引前一定要在会话里临时放大。

10 万行约 0.2 GB约 0.25 GB1 GB分钟级
100 万行约 2 GB约 2.5 GB4 GB十几分钟到半小时
1000 万行约 20 GB约 25 GB32 GB（或接受落盘构建）数小时
1 亿行约 200 GB约 250 GB单机基本不现实应当分区或换分布式方案

估算公式可以记成：索引大小 ≈ 行数 ×（每维字节 × 维度 + 8 字节头）+ 行数 × m × 2 × 链接开销。想避免拍脑袋，最稳的办法是先抽样 1% 的数据建一次索引，量出实际大小和耗时，再按行数线性外推——HNSW 的构建时间对行数近似线性偏超线性，这个外推偏保守，正好合适。

-- 会话级放大维护内存，不影响其他连接
SET maintenance_work_mem = '8GB';
SET max_parallel_maintenance_workers = 7;  -- 0.6+ 支持并行建 HNSW，通常设为核数减一

-- 先用 1% 样本量出真实体积和耗时，再线性外推
CREATE TABLE doc_chunk_sample AS
SELECT * FROM doc_chunk TABLESAMPLE SYSTEM (1);
\timing on
CREATE INDEX ON doc_chunk_sample USING hnsw (embedding halfvec_cosine_ops)
    WITH (m = 16, ef_construction = 128);
SELECT pg_size_pretty(pg_total_relation_size('doc_chunk_sample'));

-- 线上大表：CONCURRENTLY 不阻塞写入，但耗时约翻倍，且失败会留下 invalid 索引
CREATE INDEX CONCURRENTLY doc_chunk_emb_hnsw2 ON doc_chunk
    USING hnsw (embedding halfvec_cosine_ops) WITH (m = 16, ef_construction = 128);

-- 建完务必检查有没有残留的无效索引，有就 DROP 掉重来
SELECT indexrelid::regclass AS idx, indisvalid
FROM pg_index WHERE NOT indisvalid;

向量列的存储布局：TOAST 是隐形税

一个 1536 维的 vector 占 6152 字节，远超 PostgreSQL 约 2KB 的行内存储阈值，因此向量列会被推到 TOAST 副表里。这意味着每取一行向量都要多一次 TOAST 表的访问；在计划 A（先过滤再精算距离）里，这个开销会乘以候选行数，是「过滤后只剩几千行却还是很慢」的常见原因。

storage 模式行为对向量列的影响什么时候用
extended先压缩，再考虑外存浮点数几乎压不动，白付 CPU不推荐用于向量列
external外存但不压缩（0.6+ 的默认）省掉压缩解压，仍有一次 TOAST 访问默认保持即可
plain强制行内，不外存不压缩去掉 TOAST 访问，但整行必须装进一页向量不超过约 2000 维、且以精算距离为主的表
main优先行内，必要时压缩行为居中，收益不稳定一般不用

两条实操建议。第一，把向量表做窄：只留主键、用于过滤的少量字段和向量列，业务字段 JOIN 回原表。这样堆表页里能塞进更多元组，顺序扫描和精算距离的 IO 都会明显下降。第二，如果维度不高且确实受 TOAST 拖累，可以 ALTER TABLE doc_chunk ALTER COLUMN embedding SET STORAGE PLAIN；注意这只对之后写入的行生效，已有数据需要重写表（比如 VACUUM FULL 或用新表迁移）才会改变布局，别以为执行完 ALTER 就生效了。

同库同事务到底省了什么

「一条 SQL 搞定检索加过滤」只是表面收益，更值钱的是一致性。外挂向量库最典型的数据漂移是：业务库里的文档已经删了，向量库里的分块还在，于是检索把已下线的内容召回给用户看。在 pgvector 里，删文档和删向量可以放进同一个事务，要么一起成功要么一起回滚；备份恢复到某个时间点时，向量和业务数据天然对齐；行级权限、审计日志、连接池、慢查询监控这些 PG 生态的东西也全部复用。

能力pgvector（同库）外挂专用向量库
文档删除与向量删除的一致性同一事务，天然一致需要补偿任务或消息队列兜底
过滤和 JOIN标准 SQL，优化器代价估算依赖各家的标量过滤能力，JOIN 要在应用层做
备份与时间点恢复和业务数据一起，一套流程两套快照，恢复点不一定对齐
亿级以上规模吃力，需要分区甚至放弃原生分布式分片
建索引对业务的影响共享同一实例 CPU 和内存，需要错峰独立集群，互不干扰
运维复杂度只多一个扩展多一套集群、监控、升级流程

模型换代：向量列的灰度迁移

换嵌入模型是一定会发生的事，而且不同模型产出的向量完全不可比较——不能原地 UPDATE 逐步替换，因为替换期间新旧向量混在一张表里，距离计算得到的是毫无意义的数字；更糟的是检索结果看起来还挺正常，只是质量莫名下降，非常难查。正确做法是双写加灰度：

stateDiagram-v2 state "只有 v1 向量列" as S1 state "新增 v2 列并双写" as S2 state "历史数据分批回填中" as S3 state "v2 索引就绪" as S4 state "按比例灰度切读 v2" as S5 state "全量读 v2" as S6 [*] --> S1 S1 --> S2: 加列不建索引 写入路径同时产出两份向量 S2 --> S3: 后台任务按主键分批回填历史 S3 --> S4: 回填完成后并发建索引 S4 --> S5: 小流量对比评测集指标 S5 --> S4: 召回下降则立刻回退读路径 S5 --> S6: 指标不低于 v1 且延迟可接受 S6 --> [*]: 删除 v1 列与索引 再回收空间

几个容易忽略的细节：回填必须分批并控制事务大小，一条 UPDATE 刷千万行会撑爆 WAL、阻塞 VACUUM、把复制延迟拉到天上；model_ver 字段要和向量一起写，检索时带上它，灰度期间才不会新旧混查；回填完成之后再建索引，IVFFlat 尤其吃这一点；DROP COLUMN 只是把列标记为删除，磁盘空间要等后续的表重写才能回收，别指望执行完立刻看到容量下降。成本上要提前算清楚：一次全量重算的 Embedding 调用费用按 token 计费，千万级分块的重算往往是四位数到五位数人民币量级，这笔钱要写进换代方案里。

❌
pgvector 最容易踩的坑
  • 操作符与 opclass 不匹配：索引建成 vector_cosine_ops 却用 <-> 查询，不报错不告警，直接静默全表扫，小表上测不出来。
  • ORDER BY 没有 LIMIT：向量索引只在 ORDER BY 距离 LIMIT k 形态下生效，缺 LIMIT 就是全表排序。
  • 把排序写成相似度降序：ORDER BY 1 - (a <=> b) DESC 会让距离表达式被包一层，索引立刻失效，必须按距离升序排。
  • 在空表上建 IVFFlat 索引：聚类中心基于空数据算出来，召回差到不可用，必须数据导完再建。
  • ef_search 小于 k：默认 40，查 Top-100 时结果必然不全，还会误判成「数据缺失」。
  • 带 WHERE 过滤却没开迭代扫描：0.8 之前只能靠放大粗召回数量硬凑，返回不足 K 条会被当成 bug 排查半天。
  • 在应用层做租户和权限过滤：向量库返回的 K 条被应用层筛掉大半，既召回不足又泄露「存在某文档」的信息。
  • maintenance_work_mem 用默认值建 HNSW：64MB 会让构建落盘，时间从两小时变成一整天，日志里的提示很容易被忽略。
  • 向量列和几十个业务字段挤在一张宽表：TOAST 访问加堆表膨胀，精算距离的计划会慢得离谱。
  • SET STORAGE PLAIN 之后不重写表：新设置只对后续写入生效，老数据布局不变，改了等于没改。
  • 换模型时原地替换向量：新旧向量不可比较，混在一起排序结果无意义，而且表面看不出异常。
  • 用 <#> 的返回值当相似度：它是负内积，越小越相似，直接展示会出现负分并把排序理解反。
  • 只看 QPS 不看召回：把 probes 或 ef_search 调小当然快，但召回可能已经掉到 60%，必须先用暴力扫描算出 ground truth 再谈调优（详见站内「向量检索性能调优」）。
