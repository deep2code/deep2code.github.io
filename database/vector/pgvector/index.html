pgvector 实战

🏷️ pgvector,PostgreSQL

💡 你想搞懂这个技术到底是干嘛的，什么时候该用它，什么时候不该用。不想上来就背一堆概念。

为什么先讲 pgvector

如果你的团队已经在用 PostgreSQL，pgvector 是我能想到的最快上手路径——不用引入新中间件、不用学新查询语言、不用多维护一套服务，向量就是一个普通列。

但 pgvector 不是万能的。它本质是个扩展，能力上限绑死在 PostgreSQL 上，数据量到千万级以上、QPS 上去之后会遇到天花板。这篇先把它讲透，什么时候该迁走，文末生产注意事项里说。

flowchart LR APP[应用服务] --> SQL[一条 SQL] SQL --> BTREE[B-tree: 按租户/权限过滤] SQL --> HNSW[HNSW: 向量找最近邻] BTREE --> OPT[优化器合并计划] HNSW --> OPT OPT --> ROWS[返回带详情的 Top-K 行]
vector(1024) 是写死的。哪天你想从 1024 维换到 1536 维，得加新列、重新 Embedding、回填数据、再切流量。所以立项时把模型和维度定死，别留"以后再说"。我踩过一次，全量重建 800 万条数据花了一整晚。

建索引：HNSW 和 IVFFlat

没索引之前，ORDER BY embedding <=> query 是全表扫。索引建法两种，二选一（或对比后选）：

-- 方式一：HNSW，推荐默认。m 和 ef_construction 是构建参数
CREATE INDEX idx_documents_embedding_hnsw
    ON documents USING hnsw (embedding vector_cosine_ops)
    WITH (m = 16, ef_construction = 64);

-- 方式二：IVFFlat，适合超大数据集，lists 约等于 sqrt(行数)
CREATE INDEX idx_documents_embedding_ivf
    ON documents USING ivfflat (embedding vector_cosine_ops)
    WITH (lists = 100);

-- 查询时调 IVF 的探测数（HNSW 对应调 ef_search）
SET ivfflat.probes = 10;      -- IVF 用
SET hnsw.ef_search = 40;      -- HNSW 用

注意 vector_cosine_ops——这是余弦度量的索引算子。你用 L2 距离查询就得建 vector_l2_ops，用内积就 vector_ip_ops。三者必须和查询运算符一致：<=> 余弦、<-> L2、<#> 内积。

flowchart TD INS[插入文档] --> BULK[批量灌入向量数据] BULK --> BUILD[建 HNSW/IVFFlat 索引] BUILD --> ANALYZE[ANALYZE documents] ANALYZE --> QRY[查询: ORDER BY embedding <=> q LIMIT k] QRY --> CHK{EXPLAIN 是否走索引?} CHK -->|Seq Scan| FIX[数据太少或参数不对，先灌数据再看] CHK -->|Index Scan| OK[正常召回]

Embedding 写入与检索

用 Python 把文本转成向量再写库，再做一次语义检索。我把 psycopg 异步写法也贴出来，这是生产常用姿势：

import psycopg
from sentence_transformers import SentenceTransformer

model = SentenceTransformer("BAAI/bge-m3")
DB = "postgresql://user:pass@localhost:5432/rag"

def insert_docs(docs: list[str], tenant_id: int):
    embs = model.encode(docs, normalize_embeddings=True)
    rows = [(None, d, d, tenant_id, e.tolist()) for d, e in zip(docs, embs)]
    with psycopg.connect(DB) as conn, conn.cursor() as cur:
        cur.executemany(
            "INSERT INTO documents(title, content, tenant_id, embedding) "
            "VALUES (%s, %s, %s, %s)",
            rows,
        )

def search(query: str, tenant_id: int, k: int = 5):
    q = model.encode([query], normalize_embeddings=True)[0]
    with psycopg.connect(DB) as conn, conn.cursor() as cur:
        cur.execute(
            """
            SELECT id, content, embedding <=> %s AS distance
            FROM documents
            WHERE tenant_id = %s
            ORDER BY embedding <=> %s
            LIMIT %s
            """,
            (q.tolist(), tenant_id, q.tolist(), k),
        )
        return cur.fetchall()

这里有个细节：我把 tenant_id 过滤放在 WHERE 里，再用向量索引排序。pgvector 会先按 B-tree 把该租户的数据筛出来，再在子集上做 HNSW——这就是多租户场景的标准写法，别让它全表扫。

和关系数据 JOIN：一个 SQL 的威力

pgvector 最大的杀手锏，是向量召回能直接和业务表 JOIN。比如文档属于某个栏目、某个用户，你想检索出"和问题最相关、且我有权限看的 5 条"：

SELECT d.id, d.title, c.name AS category,
       d.embedding <=> %s AS distance
FROM documents d
JOIN categories c ON c.id = d.category_id
JOIN document_acl a ON a.doc_id = d.id
WHERE a.user_id = 42                 -- 我有权限
  AND d.status = 'published'         -- 只看已发布
ORDER BY d.embedding <=> %s
LIMIT 5;

这种"先过滤权限再语义排序"的组合查询，你在独立向量数据库里往往要自己在应用层拼，pgvector 里就是一句 JOIN，优化器帮你选执行计划。这也是它在中小项目里无可替代的原因。

场景pgvector独立向量库
向量+权限 JOINSQL 原生，省心应用层自己拼
< 500 万条性能足够杀鸡用牛刀
千万级以上开始吃力更合适
水平扩展弱（靠分片，麻烦）原生分布式

生产环境注意事项

这一节是交学费换来的，重点看。

内存

HNSW 索引要常驻内存。粗算：行数 × 维度 × 4 字节 是向量本体大小，HNSW 的图结构还要再加 1.5~2 倍。1000 万条 1024 维，光向量就要约 40GB，加上图结构轻松破百 GB。给 shared_buffers 和 work_mem 留足，别把它和一堆业务挤在一个小实例上。

磁盘

建索引是个重 IO 操作。一张大表建 HNSW 索引时临时文件能翻倍磁盘占用，高峰在线上建索引会把 IO 打满。正确做法：用 CREATE INDEX CONCURRENTLY，或者低峰期建、用批量加载再建索引。

-- 在线建索引，不锁写
CREATE INDEX CONCURRENTLY idx_doc_hnsw
    ON documents USING hnsw (embedding vector_cosine_ops)
    WITH (m = 16, ef_construction = 64);

维度选择

别用 3072 维硬撑。pgvector 里维度每翻一倍，内存和查询成本都翻倍。中文 RAG 我建议 1024 维起步，不够再上 1536。

先灌数据再建索引
空表上建索引毫无意义，而且小表优化器会直接走 Seq Scan，你测出来"索引没用"其实是数据太少。正确姿势：先批量灌入几百万条，ANALYZE，再建索引，最后用 EXPLAIN 确认走了 Index Scan。

FAQ

Q：pgvector 能扛多大数据量？
单表 500 万以内、QPS 几百，完全没问题。到千万级、亿级，延迟和内存开始吃紧，这时候考虑迁 Milvus 这类分布式方案。别在 pgvector 上硬撑分片。

Q：HNSW 和 IVFFlat 选哪个？
默认 HNSW，召回率高、参数少。只有在数据量极大、内存吃紧时才试 IVFFlat，而且记得定期重新聚类（数据分布变了 IVF 会退化）。

Q：pgvector 支持向量量化吗？
0.7+ 有 halfvec、bit、sparsevec 类型可以省空间。极致压缩要靠降维或换独立方案，pgvector 的量化能力相对有限。

我的结论

pgvector 是向量检索的"初恋"——上手快、生态熟、和业务数据天然融合，中小项目闭眼用。记住三件事：维度建表时定死、索引算子和查询度量对齐、HNSW 靠内存吃饭。当你单表过千万、QPS 过千、开始琢磨水平扩展时，就是时候看下一篇的选型对比了。
