RAG 检索侧数据工程：管道、增量更新与多租户

🏷️ RAG

这篇只讲一件事：把向量检索接进生产 RAG 系统，检索侧的数据工程要解决哪些问题。分块策略与重叠、Embedding 模型对照选型、混合检索与重排、查询改写、召回评估指标、上下文组装与 Prompt 构造，这些算法层面的内容站内「RAG 工程化实践」一篇已经写得很深，本文涉及时只给一句结论并指路，不重复展开。这里关心的是另一半——数据怎么进库、怎么更新、怎么隔离、怎么监控。经验上线上 RAG 出的故障，八成不在算法上，而在这一半。

两条链路：离线管道与在线检索

一个 RAG 系统实际上是两条独立部署、却必须严格对齐的链路。离线管道负责把数据变成可检索的向量，在线链路负责把用户问题变成一次检索。两条链路必须使用同一个模型版本和同一份预处理逻辑——任何一处不一致都会让查询向量和文档向量落在略微偏移的空间里，表现是召回质量莫名下降，而日志里什么错都没有，极难定位。

在线链路里有一步经常被漏掉：向量库只该存 id、向量和用于过滤的少量字段，正文和业务元信息应该回关系库按 id 批量补全。把整段正文塞进向量库的 payload 里，短期省事，长期会让索引体积膨胀、内存装不下，而且正文更新时要同时改两处。

数据模型：doc_id 和版本号是一切的前提

检索侧几乎所有运维能力都建立在元数据上。没有 doc_id，就没法做增量更新，只能全量重建；没有内容哈希，就没法做幂等，重试会产生重复向量；没有模型版本，换代时新旧向量会混在一起比较。这张表的字段设计值得在第一天就想清楚，事后补代价很大。

字段作用缺了会怎样
doc_id分块归属哪份文档，增量更新与删除的抓手文档更新只能全量重建，删除无从下手
chunk_seq分块在文档内的序号，用于拼接上下文无法做相邻块扩展，答案容易断句
content_hash分块内容指纹，幂等键与跳过未变更内容重试产生重复向量，重算成本翻倍
tenant_id租户隔离，检索时必须下推的过滤条件只能在应用层过滤，召回浪费且有越权风险
acl_tags可见范围标签，权限过滤下推权限回收无法及时生效
model_ver向量由哪个模型哪个版本产出换代灰度期新旧向量混查，结果无意义
src_updated_at源文档更新时间，用于增量拉取与一致性校验无法发现漏同步的文档
status软删标记与发布状态只能硬删，回滚和审计都做不了
-- 分块表：向量 + 增量运维所需的最小元数据集合
CREATE TABLE doc_chunk (
    id          bigserial PRIMARY KEY,
    doc_id      bigint        NOT NULL,
    chunk_seq   int           NOT NULL,
    content_hash char(64)     NOT NULL,   -- 内容指纹，幂等与跳过未变更内容都靠它
    tenant_id   int           NOT NULL,
    acl_tags    text[]        NOT NULL DEFAULT '{}',
    model_ver   text          NOT NULL,
    status      smallint      NOT NULL DEFAULT 1,  -- 1 有效 0 软删
    src_updated_at timestamptz NOT NULL,
    embedding   halfvec(1024) NOT NULL,
    -- 幂等的关键：同一文档同一分块同一模型只允许一条向量
    UNIQUE (doc_id, chunk_seq, model_ver)
);

-- 过滤字段必须有索引，否则带租户过滤的检索会退化
CREATE INDEX ON doc_chunk (tenant_id, status, model_ver);
CREATE INDEX ON doc_chunk (doc_id);              -- 按文档删除和更新的入口
CREATE INDEX ON doc_chunk USING gin (acl_tags);  -- 标签任意匹配

CREATE INDEX ON doc_chunk USING hnsw (embedding halfvec_cosine_ops)
    WITH (m = 16, ef_construction = 128);

增量更新：只插不删一定会出事

这是 RAG 落地最麻烦、也最容易被低估的部分。文档更新之后，旧分块的向量必须删除，否则一定会召回过期内容。而且这种故障的表现特别刺眼：某条政策条款已经在系统里改了甚至删了，用户提问时模型还在一本正经地引用旧版本——因为旧分块和新内容语义相近，照样会进 Top-K，还带着看起来很高的相似度。这不是理论风险，是真实事故。

大改一篇也往往只需重算少数块 P->>E: 批量请求变更分块的向量 E-->>P: 向量结果 P->>V: 同一事务内 按 doc_id 删旧分块 再插新分块 Note over V: 删和插必须原子
否则中间态会出现新旧混存或整篇不可检索 P->>Q: 提交位点

三种做法的取舍如下。按 doc_id 先删后插是默认答案，前提是删插能放在一个事务里——这正是把向量放在关系库里的一个实际好处。如果向量库不支持事务，就退一步用版本号软删：写入新版本后把旧版本标记失效，查询时带上版本过滤，再由后台任务异步清理。

做法一致性实现复杂度查询侧开销适用
按 doc_id 先删后插（同事务）强，无中间态低无向量存在支持事务的库里，首选

-- 更新：按 doc_id 先删后插，放在同一个事务里，不存在中间态
BEGIN;
DELETE FROM doc_chunk WHERE doc_id = $1 AND model_ver = 'bge-m3-v1';
INSERT INTO doc_chunk (doc_id, chunk_seq, content_hash, tenant_id, acl_tags,
                       model_ver, src_updated_at, embedding)
SELECT $1, seq, hash, $2, $3, 'bge-m3-v1', $4, emb
FROM unnest($5::int[], $6::char(64)[], $7::halfvec[]) AS t(seq, hash, emb)
ON CONFLICT (doc_id, chunk_seq, model_ver) DO UPDATE      -- 幂等：重试不会产生重复向量
    SET embedding = EXCLUDED.embedding,
        content_hash = EXCLUDED.content_hash,
        src_updated_at = EXCLUDED.src_updated_at;
COMMIT;

-- 删除与权限回收：要求立即生效，先让检索侧不可见
UPDATE doc_chunk SET status = 0 WHERE doc_id = $1;     -- 检索条件里带 status = 1
-- 存储回收可以异步，但不可见必须是同步的
DELETE FROM doc_chunk WHERE status = 0 AND src_updated_at < now() - interval '7 days';

-- 对账：源库里的文档数和向量库里的 doc_id 数必须对得上，漏同步靠这条查出来
SELECT d.id FROM document d
LEFT JOIN (SELECT DISTINCT doc_id FROM doc_chunk WHERE status = 1) c ON c.doc_id = d.id
WHERE d.status = 'published' AND c.doc_id IS NULL;

删除和权限回收的时效要求和普通更新不同：普通更新晚几分钟生效通常可以接受，而「这份文档不该再被看到」必须是同步生效的。做法是把「检索不可见」和「存储清理」拆成两步——前者同步完成（软删标记或直接删向量），后者交给后台。反过来做就会出现「已经撤销权限了，但用户还能问出内容」这种合规问题。

多租户与权限：过滤必须下推

❌
绝不能先检索再在应用层过滤

两个后果。第一，向量库返回的是固定 K 条，应用层筛掉大半之后可能只剩两三条，召回被白白浪费，而且这种「有时候答得好有时候答不出」的表现极难归因。第二是安全问题：过滤前的候选集合本身携带信息，攻击者能从结果条数、响应时间的差异推断出「某份文档存在」，这在多租户 SaaS 里是实打实的信息泄露。

正确做法是把 tenant_id 和权限标签作为向量检索的过滤条件下推到库里，让 ANN 只在允许可见的集合上进行。这也正是 pgvector、Qdrant 这类支持强过滤的方案相比只能做弱过滤的方案更有优势的场景——过滤条件参与执行计划，而不是事后筛。

做法召回是否被浪费是否有越权风险实现要点
应用层事后过滤严重浪费有，且会泄露存在性不要用
过滤条件下推到向量库不浪费无元数据字段建索引，必要时开迭代扫描
按租户物理分区或分集合不浪费无隔离最彻底，租户极多时管理成本上升
行级安全策略（RLS）兜底不浪费无，且防漏写应用忘记带条件时仍然安全，代价是计划复杂度

大租户和小租户要分开看：单个租户的数据只占全库千分之一时，先按 tenant_id 过滤再精算距离往往比走 ANN 更快也更准；而超大租户占了半个库时，才需要真的依赖向量索引。相关的执行计划判断见站内「pgvector 能力边界与正确用法」与「向量检索性能调优」。

Embedding 调用：批量、限流、幂等与成本

这一层的工程细节直接决定管道能不能跑完一次全量。批量大小、限流退避、幂等键三件事缺一不可：批太小会被网络往返吃掉吞吐，批太大会撞上服务端的 token 上限；没有退避重试，一次 429 就会让整个任务链失败；没有幂等键，重试会产生重复向量，而重复向量在检索里表现为「同一段内容占掉好几个 Top-K 位置」。

工程项推荐做法做错的后果
批大小按 token 总量而非条数攒批，留出安全余量按条数攒批遇到长文本直接超限失败
限流客户端主动限速 + 指数退避重试，尊重响应头里的配额信息撞满配额后整个管道雪崩
幂等以 (doc_id, chunk_seq, model_ver) 为唯一键，冲突则更新重试产生重复向量，占掉 Top-K 名额
跳过未变更比对 content_hash，相同则不调模型改一个标题重算整篇，费用和时间都翻倍
失败隔离单条失败进死信队列，不阻塞整批一条脏数据卡住整个全量任务
模型版本随向量一起落库换代时无法区分新旧向量
成本估算先用样本量出平均 token 数，乘总分块数再乘单价全量重算的账单到了才发现超预算
# Embedding 批量调用：按 token 攒批 + 退避重试 + 跳过未变更 + 幂等写入
import hashlib, time, random

MAX_TOKENS_PER_BATCH = 8000      # 留出余量，别贴着服务端上限
MODEL_VER = 'bge-m3-v1'

def content_hash(text):
    return hashlib.sha256(text.encode('utf-8')).hexdigest()

def make_batches(chunks, count_tokens):
    """按 token 总量攒批，而不是按条数——长文本混进来会直接超限"""
    batch, total = [], 0
    for c in chunks:
        n = count_tokens(c['text'])
        if batch and total + n > MAX_TOKENS_PER_BATCH:
            yield batch
            batch, total = [], 0
        batch.append(c)
        total += n
    if batch:
        yield batch

def embed_with_retry(client, texts, tries=5):
    for i in range(tries):
        try:
            return client.embed(texts, model=MODEL_VER)
        except RateLimitError:
            # 指数退避加抖动，避免多个 worker 同步重试再次打满配额
            time.sleep(min(2 ** i, 30) * (0.5 + random.random()))
    raise RuntimeError('embedding failed after retries')  # 交给死信队列，别阻塞整批

def sync_document(db, client, doc_id, chunks, count_tokens):
    known = db.fetch_hashes(doc_id, MODEL_VER)            # 库里已有的哈希集合
    todo = [c for c in chunks if content_hash(c['text']) not in known]
    if not todo:
        return 0                                          # 内容没变，一次模型调用都不发
    for batch in make_batches(todo, count_tokens):
        vecs = embed_with_retry(client, [c['text'] for c in batch])
        # 幂等写入：唯一键是 (doc_id, chunk_seq, model_ver)，重试只会覆盖不会重复
        db.upsert_chunks(doc_id, batch, vecs, MODEL_VER)
    db.delete_stale_chunks(doc_id, MODEL_VER, [c['seq'] for c in chunks])  # 旧分块必须清掉
    return len(todo)

成本结构要提前拆开算，否则优化方向会找错。一个典型的生产 RAG 系统，LLM 推理通常占总成本的大头，Embedding 只在全量重算时集中爆发，向量存储和检索算力占比最小但是固定支出。所以优化优先级依次是：压缩喂给模型的上下文长度、减少不必要的全量重算、再谈向量库的机器规格。

成本项计费方式典型占比优化手段
LLM 推理按输入输出 token最大控制上下文条数与长度，缓存高频问答
Embedding 调用按 token，全量重算时集中发生换代时很大，稳态很小哈希跳过未变更，只重算变更分块
向量存储按存储量与内存规格中半精度或量化，正文不进向量库
检索算力按实例规格小但固定参数按评测曲线取拐点，见站内性能调优篇
重排模型按调用次数或自建 GPU中只对粗召回的前若干条重排

模型升级：新增列双写，不能原地替换

换嵌入模型的迁移路径和换数据库表结构很像，但有一条额外的硬约束：不同模型的向量不可比较。原地逐条替换会导致迁移期间同一张表里混着两个空间的向量，距离计算失去意义，而且表面上看不出报错，只是检索质量莫名下降。

stateDiagram-v2 state "只有 v1 向量" as S1 state "新增 v2 列或集合 开始双写" as S2 state "历史数据分批回填" as S3 state "v2 索引就绪 未切流量" as S4 state "灰度切读 v2" as S5 state "全量读 v2" as S6 [*] --> S1 S1 --> S2: 写入路径同时产出两份向量 S2 --> S3: 后台任务按主键分批回填 S3 --> S4: 回填完成后并发建索引 S4 --> S5: 用评测集对比新旧召回 S5 --> S4: 指标下降则立即回退读路径 S5 --> S6: 指标不低于 v1 且延迟可接受 S6 --> [*]: 清理 v1 向量与索引

回填阶段的注意点：分批控制事务大小，一条语句刷千万行会撑爆日志并阻塞清理进程；回填期间检索必须带 model_ver 过滤，保证只读一个空间的向量；灰度对比要用固定的评测集而不是人工体感，否则回退与否只能靠吵架决定。全量重算的费用按前面的方法提前估出来，写进方案里。

检索质量的线上监控

没有评测集就无法判断任何改动是变好还是变坏，这是本文最想强调的一句话。一个只有几百条人工标注「查询-正确文档」对的评测集，价值远超任何调参技巧：每次改分块、换模型、调参数都跑一遍回归，指标掉了就回退。没有它的团队最后都会陷入反复摇摆——凭感觉改一版感觉好了，过两周又觉得不如从前。

指标怎么采异常信号通常的原因
离线召回回归评测集定期跑，记录每次变更后的召回相对上一版下降分块、模型、参数或过滤条件改动
无结果率统计返回 0 条或不足 k 条的请求占比突然抬升过滤条件写错、迭代扫描没开、索引失效
Top1 相似度分布按分位数记录，观察分布漂移整体下移查询分布变化，或双写期读到了错空间的向量
用户采纳率点击、复制、点赞等显式行为持续下滑召回质量退化，或内容本身过期
坏案例库人工反馈与抽检持续积累同类问题反复出现需要补评测集样本并针对性修
同步延迟源文档更新时间与向量入库时间之差P99 超过业务 SLA管道积压、限流、死信堆积
对账差异源库文档数与向量库 doc_id 数比对持续不为零漏同步或删除没同步
-- 检索日志表：线上监控全靠它，字段要一开始就留好
-- CREATE TABLE retrieval_log (ts timestamptz, tenant_id int, query_hash char(64),
--   model_ver text, hit_count int, top1_dist real, latency_ms int);

-- 1. 无结果率与召回不足率，按小时看趋势
SELECT date_trunc('hour', ts) AS h,
       count(*) AS total,
       round(100.0 * sum((hit_count = 0)::int) / count(*), 2) AS zero_pct,
       round(100.0 * sum((hit_count < 10)::int) / count(*), 2) AS short_pct
FROM retrieval_log
WHERE ts > now() - interval '2 days'
GROUP BY 1 ORDER BY 1;

-- 2. Top1 距离的分位数漂移：分布整体上移说明召回在变差
SELECT date_trunc('day', ts) AS d,
       percentile_cont(0.5) WITHIN GROUP (ORDER BY top1_dist)  AS p50,
       percentile_cont(0.9) WITHIN GROUP (ORDER BY top1_dist)  AS p90
FROM retrieval_log
WHERE ts > now() - interval '14 days'
GROUP BY 1 ORDER BY 1;

-- 3. 同步延迟：源文档更新到向量可检索之间的间隔
SELECT percentile_cont(0.99) WITHIN GROUP (
           ORDER BY extract(epoch FROM c.created_at - d.updated_at))  AS p99_sec
FROM document d JOIN doc_chunk c ON c.doc_id = d.id
WHERE d.updated_at > now() - interval '1 day';

缓存是收益最直接的一项优化，但有个必须守住的规则：缓存键必须包含权限维度。查询向量可以按「预处理后文本 + 模型版本」哈希缓存，这部分和权限无关；而检索结果的缓存键必须带上租户、角色、可见范围，否则就是一次实打实的越权。另外写入侧要有失效机制，文档更新时清掉相关缓存，否则缓存会变成过期内容的第二个来源——这个坑和「只插不删」是同一类错误的两种形态。

反模式症状正确做法
把整篇文档当一个向量长文档召回不准，答案抓不到具体段落按结构分块，策略详见站内 RAG 工程化实践
元数据字段不建索引带过滤的检索比不带慢十倍过滤字段一律建索引
没有 doc_id文档更新只能全量重建第一天就把 doc_id 和 chunk_seq 留好
在应用层过滤权限召回被浪费，并泄露文档存在性过滤条件下推到向量库
硬编码相似度阈值换模型后阈值全部失效，要么全滤掉要么全放过用相对排序和 Top-K，阈值随模型版本配置
换模型不重算向量召回质量莫名下降，查不出原因双写加灰度，带 model_ver 过滤
没有评测集靠感觉调参反复摇摆，谁也说不清哪版更好先做几百条标注的回归集
正文塞进向量库 payload索引膨胀、内存装不下、正文更新要改两处只存 id 与过滤字段，正文回关系库补全
❌
检索侧数据工程最容易踩的坑
  • 只插不删：文档改版后旧分块向量还在库里，用户看到已经作废的条款，而相似度看起来还很高。
  • 删除只做异步：权限已回收但检索仍可见，合规问题；不可见必须同步生效，存储清理才可以异步。
  • 离线和在线用了不同的预处理：大小写、空白、指令前缀任一处不一致，召回质量就会莫名下降且无从定位。
  • 忘记加指令前缀：不少模型要求文档和查询用不同前缀，漏了不报错，只是效果变差。
  • 没有幂等键：重试产生重复向量，同一段内容占掉好几个 Top-K 名额。
  • 按条数而不是 token 攒批：混进一条长文本就整批失败，重试还是失败。
  • 在应用层做租户和权限过滤：召回被浪费，还会通过结果条数泄露文档存在性。
  • 缓存键不含权限维度：A 租户的检索结果被 B 租户读到，是最典型的越权。
  • 缓存没有失效机制：文档更新了缓存还在，缓存成为过期内容的第二个来源。
  • 原地替换向量做模型升级：新旧向量不可比较，混在一起排序毫无意义，且表面看不出异常。
  • 全量重算前没算成本：Embedding 按 token 计费，千万级分块重算一次的账单常常是四五位数。
  • 没有对账任务：漏同步的文档永远查不出来，只能等用户投诉「搜不到某份文件」。
  • 没有评测集：任何改动都无法判断方向，团队会长期陷入凭感觉来回调整。
