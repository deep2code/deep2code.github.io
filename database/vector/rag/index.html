RAG 检索增强生成实战

🏷️ RAG,向量数据库

RAG 到底在解决什么问题

大模型很聪明，但它有两个死穴：不知道你公司内部的资料，上下文窗口也装不下整个知识库。RAG（Retrieval-Augmented Generation，检索增强生成）就是给它配一个"开卷考试"——先去知识库里把最相关的几段捞出来，连同问题一起塞给它，让它基于这些材料作答。

这句话背后藏着一个反直觉的事实：RAG 的答案质量，瓶颈几乎永远在检索，不在生成。检索捞错了，再强的模型也是一本正经地胡说八道。所以这一篇 80% 的篇幅在讲怎么把检索做对。

完整流程一图看清

第一步：文档分块（Chunking）

这是最容易被忽视、却最决定成败的一步。文档不能整篇直接 Embedding——太长向量会"平均化"，语义被稀释。要切成合适大小的块（chunk）。

我踩过的坑：一开始按固定 512 字硬切，结果一句话被从中间劈成两半，检索出来的半句根本读不通。后来改成按语义边界切 + 保留重叠，召回率肉眼可见地涨。

def split_text(text: str, chunk_size: int = 500, overlap: int = 80) -> list[str]:
    """按字符长度分块，块之间保留 overlap 重叠，避免切断语义"""
    chunks = []
    start = 0
    while start < len(text):
        end = start + chunk_size
        chunks.append(text[start:end])
        start = end - overlap      # 重叠窗口，上下文不丢
    return chunks

# 更稳的做法：先按句号/小标题断句，再贪心聚合成 chunk
def split_by_paragraph(text: str, chunk_size: int = 500):
    paragraphs = [p.strip() for p in text.split("\n") if p.strip()]
    chunks, buf = [], ""
    for p in paragraphs:
        if len(buf) + len(p) > chunk_size and buf:
            chunks.append(buf)
            buf = p
        else:
            buf = (buf + "\n" + p) if buf else p
    if buf:
        chunks.append(buf)
    return chunks
分块策略chunk 大小优点缺点
固定长度硬切256~512简单易切断语义
按段落+重叠500~800语义完整，我推荐需调 overlap
递归字符切分动态兼顾结构实现略复杂
父子分块（小检索大喂模型）子块 200/父块 1000召回准、上下文全存储翻倍
分块大小是调出来的
别拍脑袋定 512。把你的文档按 300/500/800 三种切块分别入库，用同一组测试问题对比最终答案。我一般 500~800 字 + 15% 重叠起步，中文文档偏长一点更好。

第二步：Embedding + 向量检索

分好块，每块 Embedding 存库（上一篇 pgvector 已讲）。用户提问时把问题也向量化，去库里找最近邻。这一步单独做就够搭一个能用的 demo，但生产我会再叠两样东西。

第三步：混合检索（BM25 + 向量）

纯向量检索有个盲区：精确的专有名词、型号、代号。用户问"v2.3.1 版本的 known bug"，向量可能把它匹配到一段"历史版本概览"，但 BM25 能精确命中含这个版本号的那一行。反过来，纯 BM25 又不懂语义。所以生产都用混合检索：

def hybrid_search(query: str, top_k: int = 20):
    # 1) 向量检索拿语义候选
    q_vec = model.encode([query], normalize_embeddings=True)[0]
    vec_hits = vector_db.search(q_vec, k=top_k)      # [{"id":..,"score":..}]

    # 2) BM25 拿关键词候选
    bm_hits = bm25_index.search(query, k=top_k)

    # 3) RRF 融合（Reciprocal Rank Fusion），不看原始分数只看排名
    def rrf(hits, k=60):
        return {h["id"]: 1 / (k + rank) for rank, h in enumerate(hits)}

    scores = {}
    for id_, s in {**rrf(vec_hits), **rrf(bm_hits)}.items():
        scores[id_] = scores.get(id_, 0) + s

    ranked = sorted(scores.items(), key=lambda x: x[1], reverse=True)
    return fetch_docs([i for i, _ in ranked[:top_k]])

我用 RRF 融合而不是加权求和，因为向量余弦分数和 BM25 分数量纲完全不同，硬加权很难调；RRF 只看排名，鲁棒得多，几乎不用调参。

第四步：Reranker 重排序

混合检索召回 20 条，但这 20 条里真正相关的可能只有 3~5 条。直接全塞给 LLM，既浪费上下文又引入噪音。这一步用一个专门的重排序模型（比如 bge-reranker）把 query 和每条候选的真实相关性算一遍，挑出最顶的几条：

from sentence_transformers import CrossEncoder

reranker = CrossEncoder("BAAI/bge-reranker-v2-m3")

def rerank(query: str, docs: list[dict], top_n: int = 5):
    pairs = [(query, d["content"]) for d in docs]
    scores = reranker.predict(pairs)
    ranked = sorted(zip(docs, scores), key=lambda x: x[1], reverse=True)
    return [d for d, s in ranked[:top_n]]      # 只留最相关的 5 条
。reranker 比 embedding 模型贵，所以只在小候选集上用，别拿来全库扫。

第五步：上下文窗口管理

重排完的片段不能无脑全塞。模型的上下文窗口是有限的，而且塞得越长，它越容易"迷失中间"（lost in the middle）——首尾看得清，中间的忽略掉。所以要做预算管理：

def build_prompt(query: str, docs: list[dict], max_tokens: int = 3000):
    used = 0
    context_parts = []
    for i, d in enumerate(docs, 1):
        piece = f"[资料{i}] {d['content']}"
        piece_tokens = len(piece) // 2        # 粗估中文 token
        if used + piece_tokens > max_tokens:
            break
        context_parts.append(piece)
        used += piece_tokens

    return f"""你是一个严谨的助手，只根据下面提供的资料回答用户问题。
如果资料里没有答案，就直接说不知道，不要编造。

{'\n'.join(context_parts)}

问题：{query}
请基于以上资料回答，并在末尾用 [资料N] 标注引用来源。"""
带引用是底线
一定要在 prompt 里要求模型标注引用来源（[资料1][资料3]）。这不是锦上添花——它让用户能核对答案，也是你排查"胡说八道"的唯一抓手。线上我们的 RAG 100% 都带引用。

一个能跑通的完整 pipeline

把上面串起来，就是最小可运行版本（向量库用之前的 pgvector 接口，这里省略连接细节）：

def rag_answer(question: str) -> str:
    # 1. 混合召回（向量 + BM25）
    candidates = hybrid_search(question, top_k=20)
    # 2. 重排，挑最相关 5 条
    top_docs = rerank(question, candidates, top_n=5)
    # 3. 控制上下文长度，组装 prompt
    prompt = build_prompt(question, top_docs, max_tokens=3000)
    # 4. 调大模型生成
    answer = llm.chat(prompt)
    return answer

这个骨架看着简单，但我线上知识库从"答非所问"到"用户觉得靠谱"，主要靠的就是在召回和重排这两步上反复调，而不是换更强的生成模型。

FAQ

Q：RAG 和微调（fine-tune）选哪个？
事实性、时效性、要引用的场景，RAG 优先——改知识库就能更新答案，便宜可追溯。要改变模型风格、语气、特定输出格式，才考虑微调。两者也能叠加。

Q：为什么我的 RAG 经常漏答？
八成是召回没覆盖。检查分块是否把答案切碎了、混合检索是否开了、reranker 阈值是否太严。先把"召回的 20 条里有没有正确答案"打日志看清楚，再谈生成。

Q：reranker 一定要加吗？
数据量小、query 简单可以先不加，靠向量+BM25 直接喂。一旦答案质量不够、上下文紧张，加 reranker 是性价比最高的一刀。

我的结论

RAG 的工程价值，集中在"把对的资料以对的方式喂给模型"这条链上：分块别切碎语义、混合检索补向量的盲区、reranker 把噪声挡在上下文外、prompt 控制长度并强制带引用。这套组合我在多个知识库项目里验证过，比单纯堆更大的模型有效得多。下一篇专门讲向量检索的性能调优——数据量上去后，速度和召回怎么兼顾。
