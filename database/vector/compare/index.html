向量库选型：四类方案的对照与决策树

🏷️ 向量库对比

向量方案的选型之所以让人纠结，是因为候选项看起来在做同一件事，实际却分属四个完全不同的产品形态，代价结构差得很远。这篇先把方案分类，把「真正有决策价值的维度」列成对照矩阵，然后给出决策树，最后说明为什么厂商跑分和公开 benchmark 基本不能作为选型依据、你必须自己压测哪三件事。

四类方案，根本取舍是数据要不要搬家

这四类的区别不在于「谁的 QPS 高」，而在于向量和业务数据是不是同一份数据、同一个事务、同一套备份。一旦选了专用向量库或托管服务，你就额外背上了一条数据管道，以及随之而来的一整套问题：谁负责把新文档的向量写进去、写失败怎么重试、删除怎么级联、两边数据不一致怎么发现、全量重建时怎么不影响线上。这条管道的工程量通常比接入向量库本身大一个数量级，而且是长期的运维负担。

sequenceDiagram autonumber participant APP as 业务服务 participant PG as PostgreSQL participant CDC as CDC 或消息队列 participant EMB as Embedding 服务 participant VDB as 专用向量库 APP->>PG: 事务内写入文档正文 PG-->>APP: 提交成功，接口已返回 PG->>CDC: WAL 变更事件 CDC->>EMB: 取正文做向量化 EMB-->>CDC: 返回向量 CDC->>VDB: upsert 向量与元数据 Note over APP,VDB: 这段窗口内文档已存在但搜不到，秒级到分钟级 APP->>PG: 删除文档 PG->>CDC: 删除事件 CDC->>VDB: delete by id Note over CDC,VDB: 删除事件丢失会留下幽灵结果，搜到了但回表查不到，必须定期对账

时序图里两条 Note 就是引入专用向量库后必然要处理的两类问题：可见性延迟和幽灵数据。前者要在产品层面做预期管理（新建内容标注「索引中」），后者要写定期对账任务比对两边的 ID 集合。用关系库扩展方案的话，这两个问题从根上就不存在。

各家在索引算法上其实高度同质化，都是 HNSW 加量化那一套，纯向量检索的性能差距通常在两三倍以内，而且可以靠加机器抹平。真正拉开差距的是带过滤条件的查询：有的库只做后过滤，导致查询返回的条数不稳定、小租户直接搜不到东西；有的库能把标量索引和图遍历真正融合，并按选择率自动切换策略。这个差异在功能列表上看不出来，必须自己测。

pgvector 的定位要写准

把 pgvector 说成「玩具」「只能做 demo」是流传很广的错误说法。实际情况是：在千万级向量以内，配合 HNSW 索引，pgvector 的召回和延迟完全够生产用。它的真正优势不是性能，而是消除了一整类问题：

问题用专用向量库用 pgvector
新文档什么时候能被搜到取决于同步链路，秒级到分钟级，要做预期管理事务提交即可见
写文档和写向量的原子性无法原子，要做补偿或重试队列同一个事务，天然原子
删除后残留幽灵结果要写对账任务定期扫不存在，外键或同表字段直接约束
带业务条件的过滤检索受限于向量库的过滤能力和元数据同步完整性任意 SQL 条件，可以 JOIN 其他表
备份与时间点恢复多为全量快照，粒度粗跟着 PG 的 WAL 和 PITR 一起走
权限控制另一套，要自己接复用 PG 的角色与行级安全

它的代价也很明确：向量检索是 CPU 密集型操作，高 QPS 的向量查询会和业务 OLTP 抢同一个实例的 CPU 和共享内存；写扩展只能靠分库或 Citus；HNSW 索引构建期间对内存和 maintenance_work_mem 敏感；单表向量数据涨到亿级后，索引不能全部进内存就会明显变慢。所以判断线是：千万级以内、且向量查询 QPS 不高于业务查询量级时选 pgvector；超出任一条再考虑搬家。具体的建表语句、索引参数和查询写法详见站内 pgvector 实战篇。

Milvus 与 Qdrant 怎么选

这两个是自建专用向量库里最常被放在一起比较的，但它们的设计哲学几乎相反。

维度MilvusQdrant
架构存算分离，查询节点、数据节点、索引节点、协调组件分离，依赖 etcd、对象存储、消息队列单体 Rust 进程，内置存储与 WAL，无外部依赖
部署最小形态standalone 单容器，但功能与分布式版拓扑不同一个二进制或一个容器，配置项少
扩展方式各类节点独立扩缩，计算和存储解耦，适合超大规模与冷热分离分片加副本，需要提前规划分片数
索引丰富度最全，含 GPU 索引、DiskANN、多种量化组合够用，HNSW 加多档量化
过滤能力支持分区键与复杂表达式，规模大时靠分区裁剪强项，payload 建索引后与图遍历深度融合
运维心智负担高，要理解组件拓扑、消息队列积压、compaction 行为低，单进程，指标直观
适合谁十亿级以上、有平台团队、需要冷热分层和 GPU 加速千万到亿级、小团队、过滤条件复杂、要求部署简单

选择逻辑很直接：如果你的团队没有专人维护这套系统，Milvus 的组件数量就是风险。它的能力上限确实更高，但代价是你要理解一整套分布式拓扑，出问题时排查路径长。反过来，如果数据规模已经到了需要冷热分层、需要 GPU 构建索引的地步，Qdrant 的单体架构会先撞墙。

已有 Elasticsearch，该不该用它的向量能力

判断标准只有一条：你的检索需求是不是「关键词加语义混排」。如果是，用 ES 几乎一定是对的——它原生支持在一条查询里同时做 BM25 和向量检索并用 RRF 融合，而用专用向量库的话，你得自己维护两套索引、自己实现融合、自己保证两边数据一致，这部分工作量不小。

场景用 ES 的向量字段用专用向量库
站内搜索，要兼顾型号与语义推荐，一条查询完成混排要自己维护两套索引和融合逻辑
纯语义召回，QPS 高内存效率和延迟不如专用库推荐
已有 ES 集群和运维经验推荐，边际成本接近零要新增一套系统
向量规模上亿堆内外内存压力大，分片规划要很小心推荐
需要复杂聚合与多字段排序推荐，ES 本来就擅长要回关系库做

ES 的倒排索引原理和查询机制详见站内 Elasticsearch 篇，这里只补一条向量相关的实践：ES 的向量字段会显著抬高节点的内存需求，因为 HNSW 图需要靠 page cache 驻留才能保证延迟，规划时要把向量占用算在堆外，而不是按平常的分片大小经验来估。

# ES 8.x 的 RRF 混排：一条查询同时跑 BM25 和向量检索，再按排名倒数融合
# rank_window_size 要明显大于 size，否则融合前的候选池太小，语义那一路容易被挤掉
# rank_constant 越大融合越平滑，头部结果受单路排名影响越小，默认 60，调小会更偏向头部
curl -s -XPOST "http://es:9200/docs/_search" -H 'Content-Type: application/json' -d '{
  "retriever": {
    "rrf": {
      "retrievers": [
        { "standard": { "query": { "bool": {
            "must":   [ { "match": { "title": "无线耳机 主动降噪" } } ],
            "filter": [ { "term": { "tenant_id": 1024 } },
                        { "term": { "status": "published" } } ] } } } },
        { "knn": { "field": "title_vec", "k": 50, "num_candidates": 500,
                   "query_vector": [0.013, -0.072, 0.108],
                   "filter": [ { "term": { "tenant_id": 1024 } },
                               { "term": { "status": "published" } } ] } }
      ],
      "rank_window_size": 50,
      "rank_constant": 20
    }
  },
  "size": 10,
  "_source": [ "id", "title" ]
}'
# 两路都必须各自带上同样的 filter，只给 BM25 加过滤会让向量那一路越过租户隔离
# num_candidates 就是 HNSW 的 ef_search，必须远大于 k，官方建议至少 10 倍

这段查询里有两个必须记住的细节：两路检索都要各自带上同样的 filter，只给 BM25 加过滤会让向量那一路越过租户隔离；num_candidates 就是 HNSW 的 ef_search，它必须远大于 k，否则召回会很低而你从接口上完全看不出来。

托管服务的取舍

考量具体风险怎么应对
数据合规向量虽然不是原文，但已被证明可以部分反演出原始文本，属于需要评估的数据出境行为敏感数据用境内区域或私有部署；先过法务和安全评审
成本结构按存储加读写单元计费，高 QPS 场景下月账单可能远超同等自建机器用真实 QPS 和 topK 做一次账单推演，别只看起步价
网络延迟跨公网或跨区调用会给每次检索加上几十毫秒确认服务区域与你的应用同区
能力锁定过滤语法、混合检索接口、索引参数都是私有的在代码里加一层薄封装，但不要抹掉过滤能力
可观测性拿不到召回率、段合并、内存水位这些内部指标自己在客户端侧埋点测召回与延迟
容量与限流元数据大小、单次 topK、写入速率都有硬上限上线前核对配额，尤其是批量重建时的写入速率

托管服务真正适合的场景是团队没有运维能力、数据不敏感、且 QPS 可预测且不高。一旦 QPS 上量，成本曲线会比自建陡得多。

选型时必须自己压测的三件事

先说结论：公开 benchmark 和厂商跑分基本不能作为选型依据。原因不是它们造假，而是它们测的东西和你要的东西不一样。ANN-Benchmarks 这类评测用的是 SIFT1M、GIST1M、DEEP1B 这类学术数据集，它们的维度、分布、聚簇程度和你的业务向量差异极大；更关键的是，这些评测几乎只测「无过滤的纯向量检索、静态数据集、单线程或固定并发」，而生产环境的三个关键行为它们都不测。

必测项为什么公开评测测不出来怎么测通过标准
用真实数据和真实查询分布测召回与延迟曲线学术数据集的向量分布和聚簇程度与业务数据完全不同，同样参数下召回可能差十个点抽样一万条真实查询，用暴力扫描生成标准答案，扫 ef_search 画曲线在目标 p99 延迟下召回率达到业务要求，且拐点位置清楚
带过滤条件的查询公开评测几乎不测过滤，而这是各家差异最大的能力按选择率分档构造查询：千分之一、百分之一、百分之十、百分之五十，各测召回与延迟与返回条数每一档都能稳定返回 K 条，且低选择率档不出现延迟暴涨
持续写入时的查询延迟抖动公开评测都是静态数据集，先建好索引再查边按生产写入速率灌数据边压查询，观察 p99 与 p999 随时间变化，跑足够长以触发 compactionp99 抖动在可接受范围，compaction 期间不出现成倍的延迟尖刺
import concurrent.futures as cf, random, time
import numpy as np

def bench(client, queries, truth, k=10, qps=50, duration=120, filters=None):
    """按固定 QPS 压测，同时统计召回与尾延迟。
    filters 传入按选择率分档的过滤条件列表，用于暴露 post-filter 问题。
    """
    lat, recalls, short = [], [], 0
    stop = time.time() + duration
    interval = 1.0 / qps

    def one(i):
        nonlocal short
        q = queries[i % len(queries)]
        flt = random.choice(filters) if filters else None
        t0 = time.perf_counter()
        res = client.search(q, k=k, filter=flt)
        lat.append((time.perf_counter() - t0) * 1000)
        if len(res) < k:
            short += 1                       # 返回条数不足，典型的 post-filter 症状
        if flt is None:                      # 只在无过滤时能和标准答案对比
            hit = len(set(r.id for r in res) & set(truth[i % len(queries)]))
            recalls.append(hit / k)

    with cf.ThreadPoolExecutor(max_workers=32) as ex:
        i = 0
        while time.time() < stop:
            ex.submit(one, i); i += 1
            time.sleep(interval)             # 恒定 QPS 而不是打满，才能看出真实尾延迟

    print(f"样本 {len(lat)}  p50 {np.percentile(lat,50):.1f}ms  "
          f"p99 {np.percentile(lat,99):.1f}ms  p999 {np.percentile(lat,99.9):.1f}ms")
    print(f"召回 {np.mean(recalls):.4f}  返回条数不足的比例 {short/max(len(lat),1):.2%}")

这段脚本里两个细节值得强调：按恒定 QPS 发压而不是打满并发，因为打满测出来的是吞吐上限，而线上真正影响用户的是恒定流量下的尾延迟；统计「返回条数不足的比例」，这一个指标就能把 post-filter 实现的库筛出来，比看文档可靠得多。

迁移与抽象的边界也值得在选型阶段就想清楚。既然选型有不确定性，很多团队会想「先加一层抽象，以后好换」，这个方向对，但很容易做过头。

抽象层该做的抽象层不该做的
统一 upsert、delete、search 三个基本操作的签名把过滤条件抽象成只支持等值匹配的字典，丢掉范围、数组包含、嵌套条件
统一 ID 空间与元数据字段命名，保证两边能对账为了统一而放弃混合检索、稀疏向量、多路召回融合这些各家特色能力
把距离与相似度的方向统一成「越大越相关」，消除各库语义差异自己实现跨库的分数归一化，不同库的分数本来就不可比
支持双写与影子读，用于灰度切换和结果对比做成运行时可插拔的通用 ORM，配置膨胀且没人真的切
把索引参数外置成配置，方便压测扫参试图屏蔽索引参数差异，HNSW 的 M 和 IVF 的 nlist 没有共同语义
from dataclasses import dataclass, field
from typing import Any, Protocol

@dataclass
class Query:
    vector: list          # 已归一化，方向统一为「分数越大越相关」
    k: int = 10
    # 过滤条件保留各库原生表达式，不要抽象成只支持等值的字典，
    # 否则范围、数组包含、嵌套条件全都表达不了，最后只能绕过抽象层写原生查询
    native_filter: Any = None
    params: dict = field(default_factory=dict)   # ef_search、nprobe 等，外置便于扫参

@dataclass
class Hit:
    id: str
    score: float          # 适配器内统一成越大越相关，但不做跨库分数归一化

class VectorStore(Protocol):
    def upsert(self, ids, vectors, metadata): ...
    def delete(self, ids): ...
    def search(self, q): ...
    def count(self): ...                         # 对账必需：两边总数要能比

class DualWriteStore:
    # 迁移期双写加影子读：写两边，读主库，按比例采样比对两边结果差异
    # 切换判据是 Top-K 重叠率稳定达标，而不是「新库看起来没报错」

    def __init__(self, primary, shadow, sampler=lambda: False):
        self.primary, self.shadow, self.sampler = primary, shadow, sampler

    def upsert(self, ids, vectors, metadata):
        self.primary.upsert(ids, vectors, metadata)
        try:
            self.shadow.upsert(ids, vectors, metadata)
        except Exception as e:
            log_async("shadow_upsert_failed", ids=ids, err=str(e))  # 不阻塞主链路

    def search(self, q):
        hits = self.primary.search(q)
        if self.sampler():                       # 采样做影子读，别全量放大负载
            shadow = self.shadow.search(q)
            a, b = {h.id for h in hits}, {h.id for h in shadow}
            log_async("shadow_diff", overlap=len(a & b) / max(len(a), 1))
        return hits

影子读那段是迁移时最有用的工具：判断能不能切的依据是两边 Top-K 的重叠率，而不是新库有没有报错。重叠率长期低于 0.9 就说明度量方式、归一化或索引参数有差异，必须查清再切流量。

另外记住迁移的成本结构：换向量库不需要重算 Embedding，只要模型没变；但一定要重建索引。所以真正的迁移成本是重建索引的时间加双写期间的对账，而不是向量本身。这也意味着从一开始就把「原文和向量都能从关系库里重新导出」当作硬要求，迁移就永远是可控的。

最容易踩的坑

❌
向量库选型的十一个坑
  • 拿公开 benchmark 的排名直接选型：SIFT、GIST 这些学术数据集的分布和你的业务向量差异极大，同样参数下召回能差十个百分点。
  • 没测带过滤的查询：这是各家差异最大的能力，也是上线后最容易出事的地方，功能列表上完全看不出来。
  • 压测只打满并发看吞吐：应该按恒定 QPS 压，看 p99 和 p999，线上影响用户的是尾延迟不是吞吐上限。
  • 压测用静态数据集：不带持续写入就测不到 compaction 和段合并期间的延迟尖刺，而这是生产上最常见的抖动来源。
  • 低估同步链路的成本：CDC、重试、删除级联、定期对账、全量重建预案，这些加起来通常比接入向量库本身工作量大。
  • 忽略删除事件丢失：会留下幽灵结果——搜到了 ID 但回关系库查不到，必须有定期对账兜底。
  • 把 pgvector 当玩具：千万级以内配合 HNSW 完全够用，而且省掉整条同步链路和一致性问题。
  • 小团队直接上 Milvus 分布式：etcd、对象存储、消息队列、多类节点，任何一个组件出问题排查路径都很长。
  • 已有 ES 还另建一套向量库做混排：要自己维护两套索引和融合逻辑，还要保证两边数据一致，多数情况不划算。
  • 只看托管服务的起步价：按读写单元计费，高 QPS 下月账单可能远超自建，上线前要用真实流量做账单推演。
  • 抽象层把过滤能力抽成只支持等值匹配：范围、数组包含、嵌套条件全丢了，最后只能绕过抽象层写原生查询，抽象反而成了负担。
