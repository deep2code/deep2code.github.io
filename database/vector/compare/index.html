Pinecone / Weaviate / Milvus 对比

🏷️ 向量数据库选型

选型这事儿别只看基准测试

向量数据库选型最容易踩的坑，是盯着一张 benchmark 图里"谁 QPS 高"就拍板。我吃过这个亏——线上选型那天 Milvus 某项跑分漂亮，结果上线才发现运维复杂度远超团队承受力，最后还是迁走了。这篇我把四家（pgvector、Pinecone、Weaviate、Milvus）在真实生产里的体感列出来，帮你按团队情况对号入座。

先放一句话结论：没有最好的，只有最匹配团队运维能力和预算的。下面这张总表是全文的核心。

云端 vs 自建：这笔账怎么算

这是选型里最实际的问题。我给一个判断框架：

考量云端托管（Pinecone/Weaviate Cloud）自建（pgvector/Milvus/Weaviate OSS）
上线速度分钟级天~周

我的真实路径
我们公司的演进路线是：pgvector 跑通 MVP → 数据涨到 800 万，单库压力大，迁到 Weaviate 自托管 → 多模态业务起来、数据破亿，又加了一套 Milvus。没有一步到位，都是数据量和团队能力推着走。你也可以这么干，别指望第一次就选对。

过滤能力：一个常被忽视的决胜点

生产检索几乎都带过滤条件——租户、时间、权限、状态。过滤和向量检索怎么配合，直接决定你的架构。

  • pgvector：WHERE + JOIN，优化器自动选计划，最灵活。
  • Pinecone / Weaviate：metadata 过滤和向量检索是融合优化的，"先过滤再找相似"不会退化成全表扫，这点做得比早期 Milvus 好。
  • Milvus：标量字段建倒排，大规模下过滤性能好，但复杂过滤表达式要会写。
过滤把召回率拖垮的坑
我见过最坑的一次：某向量库在"先按租户过滤再向量排序"时，过滤后每个分片只剩很少数据，ANN 图上根本找不到候选，召回率从 95% 掉到 60%。上线前一定要拿真实过滤比例测召回率，别只测全库召回。

FAQ

Q：能不能先上 Pinecone 以后再迁自建？
能，但要把向量和元数据格式标准化。换向量库 = 重新建索引，好在 Embedding 不用重算（只要模型不变）。我建议从一开始就用通用 schema，迁移成本会低很多。

Q：Milvus 太重，有没有轻量替代？
有。Milvus 有个 standalone 版（单 Docker 容器），小规模可以先用它，功能和分布式版一致，只是不扩展。Zilliz 还提供了托管版。

Q：开源向量库怎么对比性能？
别信厂商官网的跑分。用你自己的数据分布、自己的过滤条件、自己的 Top-K 和延迟 SLA 去压。ANN-Benchmarks 可以参考，但生产结论只能自己测。

我的结论

四家没有绝对好坏：pgvector 胜在简单融合、Pinecone 胜在省心快上、Weaviate 胜在体验+私有化平衡、Milvus 胜在规模上限。2026 年我的默认建议是——原型和小团队上 Pinecone/Weaviate Cloud，要私有化中小规模选 Weaviate 自托管，已有 PG 且数据不大用 pgvector，真到亿级再上 Milvus。选型不是一锤子买卖，跟着数据量和团队能力演进就好。下一篇我们动手写一个完整的 RAG。
