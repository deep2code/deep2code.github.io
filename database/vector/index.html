向量数据库总览

🏷️ 向量数据库,RAG

我为什么写这一系列

2023 年 RAG 火起来的时候，我手里能打的向量数据库就 pgvector 一个——它就是个 PostgreSQL 扩展，建个 vector 列、加个 HNSW 索引就跑起来了。到 2026 年，手里的项目从"几百条知识库"长到"上亿条多模态召回"，pgvector 开始顶不住，我陆续把 Milvus、Weaviate、Pinecone 都在生产上过了一遍。这一系列就是把这几年踩过的坑、调过的参数、交过的学费攒成一份地图。

向量数据库这个东西，说穿了不神秘：把文本/图片/音频用 Embedding 模型压成一串数字，再在这串数字里找"距离最近"的那几条。但真到生产，维度选多少、索引用 HNSW 还是 IVF、过滤和召回怎么权衡、为什么你的 RAG 总是答非所问——每一个都是坑。这五篇按"原理 → 上手 → 选型 → 实战 → 调优"的顺序排，建议顺着读。

从 Embedding 说起：向量到底是什么

Embedding 模型把一段文本映射成一个固定长度的浮点数组，比如 1024 维。语义越接近的文本，它们的向量在空间里离得越近。注意这不是关键词匹配——"iPhone 15 多少钱"和"苹果十五价格"字面几乎不重叠，但向量距离很近，因为模型学过语义。

flowchart LR T1[iPhone 15 多少钱] --> E1[Embedding 模型] T2[苹果十五价格] --> E1 T3[今天天气不错] --> E1 E1 --> V1[0.12, -0.34, ...] E1 --> V2[0.11, -0.30, ...] E1 --> V3[0.88, 0.21, ...] V1 -.余弦距离小.-> V2 V1 -.距离远.-> V3

常用的 Embedding 模型我列一下，后面 intro 那篇会细讲：OpenAI 的 text-embedding-3-large（3072 维，可降维）、BGE-M3（开源、中英双语、1024 维）、Cohere Embed v4。选型别只看排行榜 MTEB 分数，要看你的语种、长度、是否要私有化部署。

向量检索的原理：为什么不能全表扫

100 万条 1024 维向量，全表算余弦距离要算 100 万次 1024 维点积，单次查询几百毫秒起步，根本扛不住 QPS。向量数据库靠 ANN（近似最近邻）索引把单次查询压到亚毫秒。两大主流路线：

  • HNSW（分层可导航小世界图）：在图上做贪心搜索，召回率高、延迟稳定，是现在的默认选择。代价是内存吃得多。
  • IVF（倒排文件）：先把向量聚成 N 个簇，查询时只扫最近的几个簇，省内存但召回率依赖聚类质量和 nprobe 参数。
flowchart TD Q[查询向量 q] --> CLUSTER[IVF: 找最近的 nprobe 个簇] Q --> GRAPH[HNSW: 分层图贪心跳点] CLUSTER --> CAND[候选向量集合] GRAPH --> CAND CAND --> RERANK[精确距离重排序] RERANK --> TOPK[返回 Top-K]
先记住一句话
ANN 是"用精度换速度"。召回率（recall）和延迟永远是天平两端，后面性能优化那篇会专门讲怎么在它们之间找平衡。别迷信"零损失"的宣传。

RAG 架构：向量数据库到底解决什么问题

大模型有个硬伤——上下文窗口有限，也不知道你公司内部的文档。RAG（检索增强生成）的思路是：先把知识库切片、Embedding 存进向量库，用户提问时先检索出最相关的几段，塞进 prompt 让大模型基于这些段落回答。这样模型不用记住一切，只需要"查资料再答题"。

flowchart LR DOC[知识库文档] --> SPLIT[分块 Chunking] SPLIT --> EMB[Embedding] EMB --> VDB[('向量数据库')] Q[用户问题] --> QEMB[Embedding] QEMB --> VDB VDB --> CTX[Top-K 相关片段] CTX --> LLM[大模型生成答案] LLM --> ANS[带引用的回答]

这个流程里，向量检索质量直接决定答案质量。检索不到，模型再强也是瞎编。rag 那篇会给一个能跑通的完整 pipeline。

FAQ

Q：我只有几十万条数据，需要专门上向量数据库吗？
不需要。pgvector 甚至直接在内存里算都够了。先把业务跑起来，数据量到千万级再考虑换独立服务。

Q：Embedding 模型和大模型是一回事吗？
不是。Embedding 模型只输出向量，不生成文本。你可以用 BGE 做检索、用 GPT/Claude 做生成，两者解耦。

Q：向量数据库能替代 Elasticsearch 吗？
不能。它们解决的问题不同：BM25 擅长精确关键词，向量擅长语义。生产上我都用混合检索，两者叠加。

我的结论

向量数据库不是什么黑科技，它是"语义搜索"这条链路上的存储+检索引擎。2026 年我的建议很朴素：小业务用 pgvector，大规模自建用 Milvus，不想运维用 Pinecone/Weaviate Cloud。先把 RAG 跑通，再根据真实召回率和延迟数据决定要不要升级。下一篇我们从最基础的概念开始。
