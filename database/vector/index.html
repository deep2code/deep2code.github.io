向量检索的本质与代价：从精确 KNN 到近似 ANN

🏷️ 向量数据库

向量数据库热起来之后，很多介绍都停在「它能做语义搜索」这一层。但如果你要为线上系统选型、定参数、背 SLA，真正需要搞清楚的是一个计算问题：在几百万到几十亿条、每条上千维的向量里，找出离查询向量最近的 K 条，而且要在几十毫秒内返回。这个问题在数学上就没有既精确又快的解法，所以整个向量检索技术栈本质上是一连串「拿正确性换性能」的工程妥协。这篇讲这些妥协分别发生在哪、代价是什么、参数调错会怎样。

从「等于」到「最近」：查询范式变了

传统数据库的所有索引结构，底层都依赖一个前提：被索引的值存在全序关系。整数、时间戳、字符串都能比大小，于是 B+ 树可以把数据按序切成区间，查询时靠比较大小逐层剪掉不可能的分支，一次点查只访问三四个页面。哈希索引更极端，直接把等值查询算成一个地址。这两类索引之所以能把 O(n) 降到 O(log n) 甚至 O(1)，靠的都是「一次比较排除掉一大片数据」。

向量查询没有这个前提。查询请求不是「字段等于某个值」，而是「在 1536 维空间里，离这个点最近的 10 个点是哪些」。距离是两个向量共同决定的，不存在「这个向量比那个向量大」这种全序关系，也就没法把数据预先排成一条线。更麻烦的是，结果依赖的是全局比较：你不看完所有点，就无法断言剩下的点里没有更近的。

对比维度标量检索（B+ 树 / 哈希）向量检索（ANN）
查询谓词等于、范围、前缀，可判定真假Top-K 最近邻，只有相对排序没有真假
索引依据值的全序关系距离函数，无全序
剪枝方式比较一次排除一整个子树只能靠「邻居的邻居大概也近」这类启发式
结果确定性确定，同样的数据和查询永远同样结果受索引参数影响，可能漏掉真正的最近邻
正确性指标对或错召回率，0.9 和 0.99 都算「能用」
成本模型扫描行数、随机 IO 次数距离计算次数、访问的向量数、内存带宽
典型瓶颈磁盘随机读内存带宽与 CPU 的 SIMD 吞吐

注意最后两行：向量检索的瓶颈通常不在磁盘而在内存带宽。一次 HNSW 查询要计算几千次距离，每次要把一条 6KB 的向量读进 CPU，算的是点积这种纯算术，于是内存带宽先打满。这决定了后面所有优化手段的方向——减少要读的字节数，比减少要比较的条数更有效，这是量化压缩之所以重要的根本原因。

维度诅咒：树形索引在高维下必然失效

有人会问：空间检索不是有 KD-Tree、R-Tree、Ball Tree 吗？这些结构在二三维上确实能把最近邻查询降到对数级，地图上找最近的加油站就是这么做的。问题是它们的效率随维度升高会崩塌，而且崩得非常快。

直观的解释有三个层面。第一，空间划分的分支数爆炸：KD-Tree 每层按一个维度切一刀，要让每个维度都至少被切一次，树就得有 d 层，叶子数量是 2 的 d 次方。1536 维意味着你需要远超 2 的 1536 次方条数据，划分才有统计意义，而现实中你只有一亿条。数据量远小于维度所要求的量级时，每个叶子里的点极少，而查询球体会跨越几乎所有叶子，于是回溯阶段要访问绝大多数分支，比全扫还慢（因为多了指针跳转）。

第二，距离集中现象：在高维随机分布下，任意两点距离的方差相对于均值迅速趋近于零，也就是「最远点距离 / 最近点距离」这个比值趋向 1。当所有点跟你差不多远的时候，「排除一片区域」这个动作就不再有信息量——三角不等式给出的下界总是小于当前最优距离，剪不掉任何东西。

第三，体积集中在表面：高维球体的体积几乎全部集中在靠近表面的薄壳里，超立方体的体积几乎全在角上。这让「以查询点为中心画一个小球，球内就是候选集」这种几何直觉彻底失效。

维度量级树形索引表现实际做法
2 到 3 维R-Tree 有效，接近 O(log n)PostGIS、地理围栏，用 GiST 就够
10 到 20 维KD-Tree 开始退化，剪枝率明显下降还能勉强用，但已需要大量回溯
50 维以上基本等于全扫，且常数更大换 ANN，或先降维
384 到 3072 维完全失效只有两条路：暴力扫描，或近似最近邻
💡
这不是工程能力不足，是理论下界

精确最近邻在高维下没有亚线性算法，这是被研究了几十年的结论，不是某个数据库实现得不好。所以向量数据库的技术路线从一开始就放弃了精确性：它返回的不是「最近的 10 条」，而是「很可能是最近的那 10 条里的大部分」。这个让步是整个领域的起点，也是它和传统数据库最根本的区别——你在用一个会漏结果的索引，而且它不会告诉你漏了。

衡量「漏了多少」的指标叫召回率。定义很简单：用暴力扫描算出真正的 Top-K 作为标准答案，ANN 返回的 K 条里有几条命中标准答案，命中数除以 K 就是 recall@K。recall@10 = 0.95 意思是平均每次查询漏掉 0.5 条真正的最近邻。这个数字必须自己测，因为它完全取决于你的数据分布和参数设置，厂商文档里的数字是别人数据集上的。

三种距离度量：语义差异与归一化陷阱

选度量方式是建表时就要定的，改起来要重建索引，而且选错了不会报任何错，只会让召回质量悄悄下降。这是新手最常犯又最难发现的错误。

度量算什么取值与排序方向对向量长度敏感适合的模型踩坑点
余弦相似度 cosine两向量夹角的余弦，先做长度归一化再算点积负一到一，越大越相似不敏感OpenAI text-embedding 系列、BGE、大部分句向量模型很多库存的是「余弦距离 = 1 减相似度」，越小越相似，排序方向反了会拿到最不相关的结果
内积 inner product / dot逐维相乘求和，不做归一化无界，越大越相似敏感，长向量天然占优推荐系统里的双塔模型、显式训练了模长语义的模型向量没归一化时，热门物品因为模长大会霸榜；部分库返回的是负内积，越小越相似
欧氏距离 L2各维差值平方和再开根零到正无穷，越小越相似敏感图像特征、人脸特征、聚类与去重用在未归一化的文本向量上，结果主要被模长差异主导，语义相似度被淹没

最值得纠正的一个说法是「余弦相似度比欧氏距离更适合文本，所以更准」。在向量已经做过 L2 归一化的前提下，三种度量给出的 Top-K 排序完全一致，不存在谁更准。原因是一个两行的代数恒等式：当模长都为 1 时，欧氏距离的平方等于 2 减去 2 倍点积，所以点积越大、欧氏距离越小，两者是严格单调反向关系；而此时余弦相似度就等于点积本身。既然排序一致，选哪个只影响计算开销——内积最省，因为不用开根也不用除法。

真正的判断标准是跟模型训练时用的目标函数保持一致。模型用余弦相似度做对比学习训练出来的，检索时就用余弦或者归一化后的内积；推荐场景的双塔模型如果刻意把「物品热度」编码进了模长，那就必须用内积，归一化反而会丢掉信息。

import numpy as np

rng = np.random.default_rng(42)
q = rng.normal(size=1536).astype(np.float32)
db = rng.normal(size=(10000, 1536)).astype(np.float32)

def l2_normalize(x):
    # axis=-1 按行归一化；加 1e-12 防止零向量除零
    return x / (np.linalg.norm(x, axis=-1, keepdims=True) + 1e-12)

qn, dbn = l2_normalize(q), l2_normalize(db)

# 归一化后：内积降序 == 余弦降序 == 欧氏距离升序，三者 Top-K 完全相同
top_ip     = np.argsort(-(dbn @ qn))[:10]
top_cos    = np.argsort(-((dbn @ qn)))[:10]          # 归一化后余弦即点积
top_l2     = np.argsort(np.linalg.norm(dbn - qn, axis=1))[:10]
assert np.array_equal(top_ip, top_cos) and np.array_equal(top_ip, top_l2)

# 不归一化时，内积和余弦的结果会分叉：内积偏向模长大的向量
raw_ip  = np.argsort(-(db @ q))[:10]
raw_cos = np.argsort(-(l2_normalize(db) @ l2_normalize(q)))[:10]
print("未归一化时两者重叠条数:", len(set(raw_ip) & set(raw_cos)))   # 典型只有 2 到 5 条
print("模长区间:", np.linalg.norm(db, axis=1).min(), np.linalg.norm(db, axis=1).max())

这段代码值得在换模型时跑一遍：如果模型输出本身已经归一化（OpenAI 的 embedding 接口返回的就是单位向量，模长恒为 1），那你用哪个度量都一样；如果模长分布很散，就必须想清楚模长代表什么。

四类 ANN 索引：原理与取舍

市面上几十种索引名字，本质上只有四条技术路线，其余都是组合。

FLAT 暴力扫描被严重低估。它把所有向量放在连续内存里，一次查询就是一个矩阵乘法，能吃满 SIMD 和多核。在几万到几十万条的量级上，FLAT 的延迟往往就是几毫秒，而且召回率是 100%，没有任何参数要调、没有索引要构建、没有重建窗口。数据量在百万以内又要求高召回时，FLAT 通常是最优解，不是兜底方案。

IVF 倒排聚类的思路是先用 k-means 把向量分成 nlist 个簇，每个簇记住质心。查询时先算查询向量跟所有质心的距离，只进入最近的 nprobe 个簇里扫。理论加速比就是 nlist / nprobe。它的致命缺点是簇边界失真：真正的最近邻如果落在第 nprobe+1 近的那个簇里，就永远搜不到，而边界附近的向量占比在高维下并不低。所以 IVF 的召回率曲线在高召回区间（0.98 以上）需要把 nprobe 开得很大，加速比迅速退化。

HNSW 多层近邻图是目前查询性能与召回率综合最好的方案。它给每个向量连若干条边指向近邻，并且按概率把一部分点提升到上层，形成稀疏的「高速公路」。查询从顶层入口点开始贪心走向更近的邻居，逐层下沉，最后在底层做一次带候选队列的扩展搜索。代价是构建慢（要为每个点做一次插入搜索）、内存大（除了向量本身还要存边），以及删除困难。

量化压缩不改变搜索结构，只改变向量表示。SQ8 把每个 float32 维度线性映射到一个字节，压缩 4 倍、召回损失通常在 1 个百分点内，性价比极高，应该作为默认选项考虑。PQ 把 1536 维切成比如 96 段、每段 16 维，每段用 256 个聚类中心里最近的那个编号代替，于是一条向量压成 96 字节，压缩 64 倍，但召回明显下降，通常要配合「先用 PQ 粗排、再取原始向量精排」的两阶段策略。

HNSW 的三个参数各管什么，值得单独拆开看。它们分属两个完全不同的阶段，混淆这一点会导致「改了参数没效果」或者「必须重建索引才发现」。

参数阶段常见默认值控制什么调大的后果调小的后果
M建索引，不可改pgvector 16、Qdrant 16、Milvus 常用 16 至 32每个点在底层的最大邻居数，决定图的连通性和内存召回上限提高，内存和构建时间线性增长；超过 64 收益很小图容易断裂，某些点成为孤岛，召回怎么调 ef_search 都上不去
ef_construction建索引，不可改pgvector 64、Qdrant 100、Milvus 常用 200 至 500插入每个点时候选队列的大小，决定找到的邻居有多准索引质量提高，构建时间近似线性增长，查询时不花任何代价建出来的图边质量差，是「召回上不去」最常见的原因
ef_search查询，随时可改pgvector 的 hnsw.ef_search 默认 40查询时候选队列大小，直接换取召回率召回上升、延迟上升，接近 M 乘 n 时趋近 FLAT延迟低但召回崩，且必须不小于 K，否则返回条数都不够
⚠️
两个参数是一次性决策

M 和 ef_construction 写进了图结构，改它们意味着全量重建索引——千万级数据上这可能是几小时的事。所以上线前就要用真实数据做一次扫参：先固定 ef_search 扫 ef_construction，找到召回饱和点；再固定结构扫 ef_search，画出召回-延迟曲线。只有 ef_search 是能在线上按接口 SLA 动态调的旋钮，甚至可以按查询类型区分（离线批处理用 400，在线搜索用 64）。

召回率与延迟曲线才是唯一有意义的指标

看到「我们的向量库能做到 10 万 QPS」这种宣传，第一反应应该是问召回率是多少。因为把 ef_search 或 nprobe 调到最小，任何索引都能刷出极高的 QPS，只是返回的结果可能是错的。召回率和延迟是同一根曲线上的两个坐标，单独报一个数没有信息量。这也是为什么 ANN-Benchmarks 这类评测的横轴一定是召回率、纵轴才是 QPS。

import time, numpy as np

def ground_truth(db, queries, k=10):
    """用暴力扫描算标准答案。db 已归一化，内积降序等价于最近邻。
    数据量大时对 queries 采样 1000 条就够，不必全量。"""
    sims = queries @ db.T                      # (nq, n)，几十万条时占内存，必要时分块
    return np.argpartition(-sims, k, axis=1)[:, :k]

def recall_at_k(pred_ids, truth_ids, k=10):
    """pred_ids / truth_ids 形状均为 (nq, k)，比的是集合重叠率而非顺序。"""
    hits = [len(set(p[:k]) & set(t[:k])) for p, t in zip(pred_ids, truth_ids)]
    return sum(hits) / (len(hits) * k)

def sweep(search_fn, queries, truth, param_name, values, k=10):
    """扫参画召回-延迟曲线。延迟取 p95 而不是均值，线上看的是尾延迟。"""
    print(f"{param_name:>16} | recall@{k} | p50 ms | p95 ms")
    for v in values:
        lat, preds = [], []
        for q in queries:
            t0 = time.perf_counter()
            preds.append(search_fn(q, k=k, **{param_name: v}))
            lat.append((time.perf_counter() - t0) * 1000)
        r = recall_at_k(preds, truth, k)
        print(f"{v:>16} | {r:9.4f} | {np.percentile(lat,50):6.2f} | {np.percentile(lat,95):6.2f}")

# 用法：sweep(my_client.search, queries[:1000], truth, "ef_search", [16,32,64,128,256,512])

这条曲线在高召回区间极其陡峭，是 ANN 的普遍规律：从 0.9 提到 0.98 大概付出 2 倍延迟，从 0.98 提到 0.999 可能要付出 10 倍。所以业务上要先回答「漏掉一条最近邻的代价是什么」，再决定停在曲线哪个位置。RAG 检索里多召回几条交给重排，0.95 通常够用；而人脸 1:N 比对、专利去重这种漏了就出事的场景，要么把召回顶到 0.999，要么老老实实用 FLAT。

过滤与向量检索的结合：最大的工程难点

纯向量检索在真实业务里几乎不存在。实际需求总是「在这个租户下、状态为已发布、更新时间近三个月的文档里，找语义最相近的 10 条」。把标量过滤和 ANN 结合起来，是各家向量库实现差异最大、也最容易出事故的地方。

策略做法结果条数稳定性召回率什么时候用失效场景
pre-filter 先过滤先用标量索引取 ID 集合，再在集合内算距离稳定，够就一定返回 K 条1.0，因为是精确计算选择率低于千分之一，命中集合小选择率一高，候选集就是几千万条，退化成全表暴力扫描，延迟爆炸
post-filter 后过滤先 ANN 取 K 乘放大系数，再逐条校验不稳定，可能返回不足 K 条甚至零条取决于放大系数，条件越稀疏越糟选择率高于 50%，比如只是过滤软删除标记过滤条件命中率低时，放大 100 倍也凑不满，表现为「明明有数据却搜不到」
混合 / 带过滤的图搜索遍历 HNSW 时把不满足条件的节点当作不可达，但仍可借道较稳定比 post-filter 高，但低于无过滤时选择率在千分之一到 50% 之间，绝大多数真实场景过滤把图切成多个连通分量时，从入口点走不到某些区域，召回骤降且无任何报错
❌
post-filter 是最隐蔽的线上事故源

典型场景：多租户系统里小租户只占总量的万分之一，查询走 post-filter，ANN 先取全局 Top-100，里面大概率没有一条属于这个租户，于是接口返回空列表。这不是代码 bug，是策略选错了，日志里看不出任何异常。上线前必须专门测「小租户 + 强过滤」这一类查询，并确认所选向量库支持把过滤字段做成真正的索引、支持根据选择率自动切换策略。很多轻量级向量库只有 post-filter 一种实现。

存储成本的量级：量化不是优化而是必需

向量的存储开销算起来极其简单，但很多人第一次算完才意识到问题的严重性。

def vector_cost(n, dim, dtype_bytes=4, index="hnsw", M=16, pq_segments=0):
    """估算向量集合的常驻内存。索引必须常驻内存，落盘会让随机访问变成 SSD IO。"""
    if pq_segments:                       # PQ：每段压成一字节码本编号
        per_vec = pq_segments
    else:
        per_vec = dim * dtype_bytes
    per_idx = M * 2 * 4 if index == "hnsw" else 0     # 双向边，每条边一个 int32
    total = n * (per_vec + per_idx)
    return per_vec, total / 1024**3                   # 单条字节数，总量 GB

for label, kw in [
    ("float32 原始 + HNSW", dict(dtype_bytes=4)),
    ("float16 半精度",       dict(dtype_bytes=2)),
    ("SQ8 每维一字节",       dict(dtype_bytes=1)),
    ("PQ96 分段量化",        dict(pq_segments=96, index="ivf")),
]:
    per, gb = vector_cost(100_000_000, 1536, **kw)
    print(f"{label:22} 单条 {per:>5} B  一亿条 {gb:8.1f} GB")

572 GB 这个数字说明了两件事。第一，量化和降维在亿级规模上不是「调优手段」而是「能不能跑」的前提。第二，新一代 Embedding 模型支持的维度截断（Matryoshka 表示学习，OpenAI 的 text-embedding-3 和 BGE-M3 都支持）价值很大：直接取前 512 维再重新归一化，存储降到三分之一，召回只掉一两个点。这个手段和量化可以叠加使用。

向量库不是数据库，它更像索引服务

「向量数据库」这个名字带来了很多误解。多数向量库在数据库该有的能力上都很弱，把它当主存储用会踩一连串坑。

能力关系数据库多数专用向量库实践影响
事务完整 ACID，多语句回滚多数只有单条或单批次原子性，无跨集合事务「写业务表 + 写向量」无法原子完成，必须做补偿或对账
读一致性提交即可见常见最终一致，写入到可查有秒级延迟刚上传的文档立刻搜不到，容易被当成 bug 排查半天
更新一条向量原地 UPDATE逻辑删除加插入，图索引留下墓碑高频更新场景索引持续膨胀，召回缓慢劣化，需定期 compaction
删除立即生效并回收空间墓碑标记，空间靠后台合并回收删了一半数据内存不降；合规删除要确认物理清除时机
Schema 变更在线加列改维度或度量等于重建集合换 Embedding 模型是一次全量重算加重建，要做双写灰度
Join 与聚合原生支持基本没有必须拿 ID 回关系库做二次查询
备份恢复PITR、增量备份成熟多为全量快照，粒度粗误删数据的恢复成本远高于关系库
✅
正确的定位

把向量库当成「一个可以按相似度查询的外部索引」，而不是数据的家。主数据放关系库，向量库里只存三样东西：主键 ID、向量、以及必须参与过滤的少量元数据字段。检索返回 ID 列表后回关系库取完整数据。这样做的好处是向量库可以随时重建、随时换实现，业务数据不受影响；索引出问题时的恢复手段就是「重跑一遍 Embedding」，而不是找备份。如果你的数据量还在千万以内且已经在用 PostgreSQL，把向量放进同一个库能省掉整条同步链路，具体用法详见站内 pgvector 实战篇。

关于 RAG 场景下的分块策略、Embedding 模型选型、混合检索与重排、召回评估方法，这些属于检索链路上层的工程问题，结论是「分块与重排对最终效果的影响通常大于换向量库」，详见站内 RAG 工程实践篇，这里不重复展开。

最容易踩的坑

❌
向量检索的十二个真实坑
  • 度量方式与模型不匹配：模型按余弦训练，建表却选了 L2 且向量没归一化，召回质量掉一大截，但系统不报任何错，只表现为「搜出来的东西不太相关」。
  • 距离和相似度的方向搞反：pgvector 的 <=> 是余弦距离（越小越近），Milvus 的 COSINE 返回相似度（越大越近）。排序方向反了会稳定返回最不相关的结果，而且看起来「有结果」。
  • 只报 QPS 不报召回率：无论是自测还是看厂商跑分，没有召回率的性能数字一律无意义，因为把 ef_search 调到 1 谁都能刷高 QPS。
  • ef_search 小于 topK：候选队列比要返回的条数还小，直接导致返回条数不足，且召回率断崖下跌。规则是 ef_search 至少是 K 的 2 到 4 倍。
  • 上线后才发现 M 和 ef_construction 选小了：这两个参数写进图结构，改动等于全量重建。千万级数据重建可能要几小时，且期间召回率不可控。
  • 用 post-filter 跑强过滤查询：小租户、冷门标签这类低选择率条件下，ANN 先取的 Top-N 里一条都不满足条件，接口静默返回空列表。
  • 过滤字段没建标量索引：pre-filter 阶段要全表扫一遍才能拿到 ID 集合，整个查询的时间全花在过滤上，向量部分反而是快的。
  • 忘了给 IVF 重新训练：数据分布随时间漂移后，原来的 k-means 质心严重倾斜，某几个簇装了大部分向量，nprobe 再大召回也上不去。
  • 高频更新却用 HNSW：每次更新留一个墓碑，索引只增不减，几周后内存翻倍、召回下滑。要么定期重建，要么换成分段合并策略更好的实现。
  • 没算存储就上高维模型：3072 维 float32 是 12 KB 一条，千万条就是 114 GB，远超单机内存。选模型时维度要和数据量一起算。
  • 把向量库当主存储：出故障要靠备份恢复时才发现备份粒度是全量快照、没有 PITR。向量应当可以从关系库里的原文重新算出来。
  • 拿公开 benchmark 的结论直接选型：SIFT、GIST 这类学术数据集的分布和你的业务向量差异极大，尤其是「带过滤的查询」和「持续写入时的延迟抖动」这两项公开评测基本不测。
