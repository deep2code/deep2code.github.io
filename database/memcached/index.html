Memcached 的内存模型与适用边界

🏷️ Memcached

Memcached 的对外接口只有十几条命令，但它的实际行为几乎全部由内存分配器决定。它不是「把 key 塞进堆里」的哈希表，而是一个预先切好格子的板材仓库：格子规格固定，东西按最接近的格子放，放不进去的空格子闲着也不会借给别人。理解这一层，线上最常见的两个困惑才有答案——为什么 stats 显示还剩很多内存却在疯狂驱逐，以及为什么同样 8GB，Memcached 能装下的小对象比 Redis 多一截。缓存穿透、击穿、雪崩属于访问模式层面的问题，站内缓存架构专篇已有系统讨论，本文只讲 Memcached 自身的内存模型、并发模型与适用边界。

内存模型：page、slab class、chunk、item 四层

Memcached 启动时并不会立刻申请 -m 指定的全部内存，而是在运行中按需以 page（默认 1MB）为单位向操作系统要内存，然后把这个 page 整块划给某一个 slab class。每个 class 有固定的 chunk 规格：最小档由 -n（默认 48 字节的数据空间）加上 item 头部决定，往上每一档乘以增长因子 -f（默认 1.25），一直排到单 item 上限。一个 page 被切成 1048576 / chunk_size 个等长 chunk，此后这个 page 只能存这一档的 item。

存一条数据时，真正参与计算的长度是「item 头部（64 位上约 48 字节，启用 CAS 再加 8 字节）+ key（上限 250 字节）+ 后缀 + value」的总和，向上取到最近的 chunk 档。取整产生的差额就是 slab 内部碎片：增长因子 1.25 意味着最坏情况下浪费接近 20%，即某个 item 的总长刚好比上一档大 1 字节时，它要独占大 25% 的 chunk。

「内存没满却在驱逐」的根因与判定

这是 Memcached 最经典的线上现象：监控上 bytes 离 limit_maxbytes 还有距离，evictions 却一直在涨。根因是 page 一旦划给某个 slab class 就长期属于它，而驱逐是 class 内部的事：class 13 要写新 item 时，只会在 class 13 的 LRU 尾部踢掉一个，哪怕 class 5 有几百个空闲 chunk 也借不过来。这个现象叫 slab 钙化（calcification），典型触发条件是业务 value 的长度分布发生了变化——上线一次改版，序列化结果从 800 字节变成 1300 字节，于是新档位没 page 可用、老档位的 page 全在空转。

分段 LRU、TEMP LRU 与 lru_crawler

「Memcached 就是一条简单的 LRU 链表」这个说法在 1.5 之后已经不成立。开启 lru_maintainer（1.5 起默认开启）后，每个 slab class 内部被拆成 HOT、WARM、COLD 三段，另有一个用于极短 TTL 数据的 TEMP 段。新写入的 item 先进 HOT；HOT 有比例上限，超出后尾部 item 按「期间是否被再次访问过」分流：被访问过的搬进 WARM，没被访问的降级到 COLD。驱逐只发生在 COLD 段的尾部，COLD 里的 item 若被命中，会被异步标记并搬回 WARM。这个设计的目的和 Redis 的近似 LRU 类似——避免一次全量扫描把整个热集冲掉。

stateDiagram-v2 [*] --> HOT: set 写入 HOT --> WARM: 期间被再次访问过 HOT --> COLD: 期间未被访问 WARM --> COLD: 尾部长期未命中 COLD --> WARM: 被命中后异步搬回 COLD --> [*]: 本 class 内存不足时从尾部驱逐 [*] --> TEMP: TTL 小于 temporary_ttl 的写入 TEMP --> [*]: 到期由 lru_crawler 回收 不参与搬移 note right of COLD lru_maintainer 线程负责段间搬移 lru_crawler 线程负责主动回收过期 item 两者都是后台异步 不在请求路径上 end note

lru_crawler 是另一个常被误解的点。Memcached 的过期是惰性的：TTL 到了不等于 chunk 被释放，item 仍然占着位置，直到被访问（此时返回 miss 并释放）或被驱逐。lru_crawler 就是为此存在的后台线程，它按 class 爬取 LRU 并回收已过期的 item，对应的统计是 crawler_reclaimed。所以在一个写入量不大、但 TTL 普遍很短的实例上，如果关掉 crawler，你会看到「curr_items 里很多是死人、活数据却在被驱逐」。lru_crawler metadump all 还是唯一正当的 key 枚举方式——Memcached 没有 KEYS 命令，也不该有。

多线程模型：与 Redis 单线程的后果差异

Memcached 默认 -t 4 个 worker 线程，每个线程有独立的事件循环，新连接由主线程分派后就固定在某个 worker 上；item 与哈希桶由细粒度锁保护，所以单实例可以线性地吃掉多个 CPU 核心。Redis 的命令执行始终是单线程（io-threads 只并行化网络收发与协议解析），这不是缺陷而是取舍，但它带来几个具体后果上的差异。

维度Memcached（多线程）Redis（单线程执行）工程含义
单实例纵向扩展提高 -t 可利用多核，瓶颈通常先到网卡与内存带宽单核打满即为上限，需要多实例或 Cluster 分片大机器上跑纯 KV 缓存，Memcached 实例数可以少很多
慢操作的影响面一个连接上的大 value 读写只拖累它所属的 worker一条慢命令阻塞所有客户端Redis 侧必须严禁 KEYS、大 key 的全量取回
原子性范围单 key 命令原子（含 CAS、incr、add），没有跨 key 事务单线程天然串行，支持 MULTI 与 Lua 的跨 key 原子需要「读改写多个 key」的逻辑，Memcached 只能靠 CAS 重试或外部锁
尾延迟来源锁竞争、slab 搬移、网络缓冲另有持久化 fork、大 key 释放、过期批量清理Memcached 的延迟曲线更平，没有 RDB fork 造成的秒级抖动
线程数配置一般不超过物理核数；过多会加剧锁竞争io-threads 通常 2 到 4 就到收益拐点两边都不是「越大越好」

顺带纠正一个常见结论：「Redis 比 Memcached 快」和「Memcached 比 Redis 快」都不成立，因为它们在不同维度上快。单连接单命令的延迟两者在同一量级（都是内存操作加一次网络往返，微秒级），差异体现在单实例总吞吐（Memcached 因多线程更高）和功能密度（Redis 更高）。任何脱离并发度、value 大小、命令类型的「快 N 倍」结论都没有意义。Redis 的单线程事件循环、编码转换阈值与持久化细节，详见站内 Redis 深度原理。

客户端分片：扩缩容会打掉多少命中率

Memcached 服务端之间互相不知道彼此存在——没有集群协议，没有槽位，没有请求转发。分片完全由客户端决定，这带来一个后果：分片策略的正确性取决于「所有客户端是否算得一样」，而不是服务端配置。这是分布式缓存里最容易长期带病运行的地方。

这张图说明客户端自动摘除（auto-eject）是一把双刃剑：它把节点故障变成了分片拓扑变更，而各客户端的拓扑变更不同步，同一个 key 就有了两份寿命不同的副本。节点恢复后更糟——被摘除期间写在别处的新值不会回流，旧节点上的陈旧值重新开始服务，直到 TTL 到期。可用的取舍只有几种：不开自动摘除（节点故障时该分片直接回源，用限流保护数据库）、开自动摘除但把 TTL 压到分钟级、或者把摘除决策上移到统一的配置中心让所有客户端同时生效。

from pymemcache.client.hash import HashClient

# HashClient 默认用 Rendezvous 哈希，不是取模，加减节点只影响约 1/N 的 key
# 注意三个容易埋雷的默认值：
#   default_noreply=True 会让 set/add/cas 的返回值失去意义，务必显式关掉
#   ignore_exc=False 时节点故障会向上抛异常；设 True 则表现为 cache miss，
#     看着更平滑，但会把节点故障静默转成数据库压力，必须配合回源限流
#   dead_timeout 默认 60 秒，决定被摘除节点多久后重新探活
client = HashClient(
    [("10.0.0.11", 11211), ("10.0.0.12", 11211), ("10.0.0.13", 11211)],
    use_pooling=True,
    max_pool_size=16,
    default_noreply=False,
    ignore_exc=False,
    timeout=0.2,
    connect_timeout=0.2,
    retry_attempts=2,
    retry_timeout=1,
    dead_timeout=10,
)

# 多 key 读取要用 get_many，客户端会按分片归并成每节点一次批量请求
# 逐个 get 的开销不在服务端，而在 N 次网络往返
rows = client.get_many([b"user:1", b"user:2", b"user:3"])

无持久化、无复制的直接后果

Memcached 没有主从复制，也没有常规意义上的持久化。这条特性的真正含义不是「数据可能丢」——缓存本来就允许丢——而是它的失效是整节点、瞬时、全量的。一个 32GB 的实例重启，等于瞬间把这一分片的全部回源流量推给数据库。要评估风险，看的不是命中率，而是「假设这一片缓存现在归零，数据库能不能扛住这一片的全量 QPS」。

场景Memcached 的实际行为连带风险缓解手段
正常退出并原参数重启，且配置了 restart mode（-e 指定映射文件）缓存内容可以恢复参数或版本变化即失效，且不覆盖崩溃场景把它当滚动升级工具用，不要当可靠性方案
kill -9、宿主 OOM、掉电缓存全空本分片回源 QPS 瞬间 100%回源侧必须有并发上限或单飞合并，见站内缓存架构专篇
整集群滚动重启逐节点清空叠加起来可能形成持续数分钟的高回源逐节点间隔足够长；重启后按热 key 列表做预热
扩容加节点取模策略下接近全量重映射相当于一次自发的缓存雪崩先确认客户端是一致性哈希；扩容放在低峰并分批
节点故障被客户端摘除后恢复旧数据重新对外服务陈旧读，且不同客户端结论不一致恢复前清空该节点，或让 TTL 足够短
业务需要「缓存里的数据不能丢」Memcached 无法满足把会话、去重标记、计数器放进来就会真丢业务换 Redis 并配持久化与复制，或把权威数据落库

CAS、add 与并发更新的边界

Memcached 常被说成「不支持原子操作」，这是错的。每个 item 都带一个 64 位的 cas 版本号，gets 会连同版本号返回，cas 命令只在版本号未变时写入成功，否则返回 EXISTS（key 已不存在则返回 NOT_FOUND）。这是一个单 key 的乐观锁，足以正确实现「读-改-写」；add（仅当 key 不存在时写入）则是一个天然的抢占原语，常用于分布式互斥或防止并发回源。

from pymemcache.client.base import Client

# default_noreply=False 是必须的：pymemcache 默认 noreply=True，
# 此时 set/add/cas 一律返回 True，CAS 冲突会被静默吞掉
client = Client(("127.0.0.1", 11211), default_noreply=False,
                timeout=0.2, connect_timeout=0.2)

def bump_counter(key, max_retry=3):
    """单 key 读改写：用 CAS 保证并发安全，冲突过多则交给上层降级"""
    for _ in range(max_retry):
        value, cas = client.gets(key)
        if cas is None:
            # key 不存在：add 只会让一个并发者成功，其余返回 False 后重走一轮
            if client.add(key, b"1", expire=300):
                return 1
            continue
        new = str(int(value) + 1).encode()
        # cas 返回 False 说明期间被别人改过，必须重读，绝不能退化成 set
        if client.cas(key, new, cas, expire=300):
            return int(new)
    return None

def acquire_lock(key, token, ttl=10):
    """用 add 做互斥：成功即持有。注意 ttl 必须大于临界区最长耗时，
    否则锁提前过期会出现两个持有者；释放时应校验 token 再删"""
    return client.add(key, token, expire=ttl)

两个必须知道的边界。第一，incr / decr 只对「看起来像十进制数字」的 value 生效，对不存在的 key 返回 NOT_FOUND 而不会当 0 处理，decr 不会低于 0，而且它们不会刷新 TTL——用它做限流计数时，计数窗口的起点由第一次 add 决定。第二，exptime 的语义有个流传很久的坑：数值大于 2592000（30 天）时被解释为绝对 Unix 时间戳，而不是相对秒数。有人想设「一年有效」填 31536000，实际得到的是 1971 年的某个时刻，item 写进去立刻就是过期状态。要设超过 30 天就老老实实传时间戳。

value 上限、大对象与 extstore

单 item 默认上限 1MB，可用 -I 调整（下限 1k）。超限的 set 会收到 SERVER_ERROR object too large for cache，而不是静默截断——但很多客户端把这类 SERVER_ERROR 当成连接级错误处理，于是表现为「偶发连接重建 + 缓存写不进去」，排查时要盯客户端日志而不是服务端。1.4.29 之后 Memcached 支持把超过 slab_chunk_max 的大 item 拆成多个 chunk 链式存储，所以调大 -I 不会把 page 也变成那么大，但链式 item 的分配与释放成本更高，且更容易在大档 class 上制造钙化。

关于「Memcached 容量不能超过内存」，1.5.4 之后也需要修正：extstore 允许把较大的 value 下沉到 SSD，key 与元数据仍常驻内存。适用前提很明确——value 不能太小（元数据开销会吃掉收益，默认只下沉超过 ext_item_size 的 item），访问要有明显冷热分层（命中下沉数据的延迟从微秒级变成 SSD 级别），并且要接受写放大带来的盘寿命消耗。

选择矩阵：什么时候 Memcached 仍然更好

2026 年选缓存的默认答案是 Redis，这没错，但「Memcached 已经没用了」是懒惰的结论。Memcached 的价值恰恰在于它功能少到故障模式可以穷举：没有持久化就没有 fork 抖动，没有复制就没有主从延迟和脑裂，没有脚本就没人能在缓存层写业务逻辑。对于一层纯粹的、丢了就回源的只读缓存，这些「缺失」都是优点。

❌
最容易踩的坑
  • 把 -m 当进程内存上限，容器 limit 按它设置，结果哈希表加连接缓冲把容器撑爆被 OOM Kill。
  • 看到 bytes 没到 limit_maxbytes 就断定「内存够」，忽略 stats slabs 里 page 早已全部分完，驱逐其实是 slab 钙化。
  • value 序列化结果刚好越过 chunk 档（比如 1186 字节落进 1480 档），白扔 20% 内存却查不出原因。
  • exptime 填了大于 2592000 的秒数，被当成绝对时间戳，数据写进去就是过期的。
  • 用 incr 做限流计数，误以为它会刷新 TTL，导致窗口边界和预期不符；或忘了 key 不存在时 incr 返回 NOT_FOUND 而不是从 0 开始。
  • pymemcache 等客户端默认 noreply=True，set/add/cas 永远返回 True，CAS 冲突和写失败被静默吞掉。
  • 不同语言的服务连同一个 Memcached 集群，一边 crc32 取模一边 ketama，同一个 key 有两份互不相干的缓存。
  • 扩容时直接往客户端配置里加一台机器，取模策略下接近全量重映射，等于给数据库来一次人造雪崩。
  • 开了客户端自动摘除却没管节点恢复，故障节点回来后继续供应陈旧值直到 TTL 到期。
  • 关掉或忘了 lru_crawler，大量已过期 item 占着 chunk，活数据反而被驱逐。
  • 把会话、幂等标记、分布式锁这类「丢了就出业务问题」的数据放进 Memcached，一次重启直接变成线上事故。
  • slab_automove=2 在体积分布抖动的负载上反复搬页，CPU 和延迟毛刺同时上升。
