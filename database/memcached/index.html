Memcached：那个被Redis抢了风头的老前辈

说起来，Memcached 比 Redis 还早出生两年。我入行的时候（大概 2012 年），公司缓存清一色 Memcached，Redis 还是个小众玩具。

为啥它还活着？因为它简单。只做 KV 缓存，别的都不干——没有持久化、没有复杂数据结构、没有集群管理，全交给客户端。正因为简单，它协议解析快、内存元数据少、多线程无锁竞争。在纯缓存场景下，性能不输 Redis，内存效率还更高。

装一个跑起来

macOS 上 Homebrew 一行：

brew install memcached
brew services start memcached

Linux 上源码编译，它依赖 libevent：

wget https://memcached.org/latest
tar -zxf memcached-1.6.45.tar.gz
cd memcached-1.6.45
./configure && make && make install

启动参数我常用的几个，别记全了，记住关键的就行：

# 后台运行，分配 4GB 内存，监听 11211，4 个工作线程
memcached -d -m 4096 -p 11211 -t 4 -u nobody
参数干啥的我的建议
-m分配内存大小（MB）别超物理内存 70%，留够 OS
-t工作线程数跟 CPU 核心数对齐，别盲目设大
-I单个 Item 最大大小默认 1MB，大 value 调到 5m
-fSlab 增长因子默认 1.25，数据大小集中就调小到 1.1
-c最大并发连接默认 1024，大流量调到 8192

怎么用：telnet 就能玩

Memcached 的协议简单到什么程度？你直接 telnet 上去就能操作，不用装任何客户端。

telnet localhost 11211

连上之后，stats 看状态，quit 退出。存储命令的格式很直白：

set mykey 0 60 5
hello
STORED

get mykey
VALUE mykey 0 5
hello
END

参数拆开说：set 是命令，mykey 是 key，0 是 flags（客户端随便用），60 是过期时间（秒），5 是 value 的字节数。第二行是真正的数据。

过期时间的坑：一写就过期

这是新手最容易犯的错。Memcached 的过期时间 ≤ 30 天（2592000 秒）时，按相对时间算——60 就是 60 秒后过期。但如果你传了个大于 30 天的值，它就按 Unix 时间戳解析了。有人想设"一小时后过期"，传了 3600，结果 3600 这个 Unix 时间戳是 1970 年的——一写进去就过期了，get 直接返回 NOT_FOUND。排查了半天才发现这个坑。

几个存储命令的区别

命令行为啥时候用
set有就覆盖，没有就新增日常用这个就行
add只有不存在才存做分布式锁
replace只有存在才替换更新已有值
append / prepend往后/往前追加数据拼接日志
cas带版本号的条件更新并发更新防覆盖

CAS：乐观锁怎么用

两个人同时改同一个 key，怎么防止后写的把先写的覆盖了？Memcached 用 CAS（Check And Set）。

# gets 会返回一个 CAS 令牌
gets mykey
VALUE mykey 0 5 12345
hello
END

# 改完用 cas 提交，带上令牌
cas mykey 0 60 5 12345
world
STORED

# 如果期间别人改了，令牌对不上，返回 EXISTS
cas mykey 0 60 5 12345
world
EXISTS

计数器这种场景别用 CAS——incr 和 decr 本身就是原子的，比 CAS 绕一圈快多了。

多线程架构：为什么它能吃满多核

Redis 6.0 之前是单线程，多核 CPU 只用一个核。Memcached 从一开始就是多线程，这是它在某些场景下比 Redis 快的原因。

这个设计很妙：主线程只管 accept，接了新连接通过管道（Pipe）把 fd 扔给工作线程。每个工作线程有自己的 libevent 事件循环，互不干扰。全局数据结构用分片锁——每个 LRU 队列一把锁，不是一把全局大锁，并发性能就上去了。

Slab 分配器：内存是怎么管的

Memcached 不用系统 malloc/free 管内存，自己搞了套 Slab Allocator。为啥？malloc 频繁分配释放会产生内存碎片，Memcached 把内存切成固定大小的块，从根上解决了碎片问题。

具体怎么分的呢？内存先按 1MB 一页（Page）切，然后每个 Slab Class 管一种固定大小的 Chunk。默认增长因子 1.25：

Slab ClassChunk 大小1MB Page 能切多少个适合存什么
196 字节~10922 个短 key-value、标志位
2120 字节~8738 个小用户信息
3152 字节~7157 个中等文本
............
N1MB（最大）1 个大对象
Slab 间内存不共享——这个坑很大

这是 Memcached 最浪费内存的地方。假设你的数据大多是 100 字节左右的小对象，都落在 Slab Class 2（120 字节 Chunk）。这个 Class 把 4GB 内存全占满了，这时候来了个 500KB 的大对象，需要 Slab Class 20——但内存没了！

即使 Class 2 里有大量空闲 Chunk，也不能借给 Class 20 用。结果就是 LRU 开始淘汰小对象，大对象也存不进来。遇到这种情况只能调增长因子或者重启。

LRU 淘汰：每个 Slab Class 自己管自己

Memcached 不是全局 LRU，而是每个 Slab Class 维护自己的 LRU 链表。这意味着：1MB 的大对象 Slab 占满了，它只会淘汰自己里面的大对象，不会去动 96 字节的小对象。

过期策略是惰性过期——不会主动扫描过期 key。get 的时候才检查，如果过期了就删掉返回 NOT_FOUND。过期的 key 占的内存要等新数据来要空间时才被覆盖。1.4.11 以后加了 LRU Crawler 后台线程，定期扫描清理过期项。

集群：官方不支持，全靠客户端

Memcached 没有官方集群方案。它就是个单节点服务，水平扩展全靠客户端做分片。

最简单的分片是 hash(key) % N，但这个方案有个致命问题：加一台机器或者挂一台机器，N 变了，几乎所有 key 的映射都变了——缓存全失效，请求瞬间全打到数据库，这就是缓存雪崩。

正经做法是一致性哈希：把哈希空间想象成一个环，每个节点在环上占多个虚拟位置（一般 100-200 个虚拟节点）。key 哈希后在环上顺时针找最近的节点。加机器的时候，只有新节点相邻那一段的 key 需要迁移，影响范围大概是 1/N。

我的经验

Memcached 集群设计的关键是：把它当成"随时可以全清掉重建"的东西。应用层一定要做缓存缺失降级——缓存挂了或者数据没命中，请求应该能打到数据库返回，而不是直接报错。这样节点增减、故障转移都是无痛的。

Dragonfly 是我觉得最有意思的——它同时兼容 Redis 和 Memcached 协议，多线程共享内存架构，官方基准说单机吞吐是 Redis 单线程的好几倍。如果你的 Memcached 存量应用想升级，换 Dragonfly 几乎零改动，改个地址就行。

我踩过的坑

  1. Slab 内存浪费：数据大小集中在某一个区间，那个 Slab Class 把内存占满了，其他 Class 想要内存却没有。解法：调增长因子 -f 1.1，让 Slab Class 更密集；开 lru_maintainer 自动在 Slab 间平衡
  2. 大 Value 报错：默认最大 1MB，塞了个 2MB 的 JSON 进去，直接报 object too large for cache。解法：Value 控制在 100KB 以内，大对象拆分，或者调 -I 5m
  3. 节点故障导致缓存雪崩：一台 Memcached 挂了，它上面的 key 全失效，数据库瞬间被打满。解法：一致性哈希 + 虚拟节点减少影响范围，应用层做熔断降级
  4. 过期时间传错：前面说了，传了个 3600 以为是一小时，结果是 1970 年的时间戳，一写就过期
  5. stats 命令阻塞：大内存实例上跑 stats slabs，阻塞了几百毫秒。监控系统别采集太频繁，30 秒一次够了
  6. 命中率低还不知道：Memcached 的价值就是命中率。低于 90% 就该查原因了——是内存不够 LRU 在狂淘汰，还是 TTL 设太短，还是 key 设计不合理

FAQ

Memcached 和 Redis 到底谁快？

纯 KV get/set，Memcached 因为多线程，在多核 CPU 上确实比 Redis 单线程快。但 Redis 6.0 以后网络 IO 也多线程了，差距缩小了很多。而且 Memcached 快是因为它功能少——你不能拿它做 Hash 排序、做排行榜、做消息队列。功能越多越慢，这是 trade-off。

Memcached 重启数据会丢吗？

会，全丢。它没有持久化，设计就是纯内存缓存。别把它当数据库用。重要数据一定要有后端存储兜底。

怎么监控 Memcached 健康？

telnet 上去敲 stats，重点看这几个指标：get_hits 和 get_misses（算命中率）、evictions（被淘汰的 key 数，如果一直涨说明内存不够）、bytes（当前用了多少内存）。生产环境用 Prometheus + memcached_exporter 采集。

Memcached 支持事务吗？

不支持。只有 CAS 乐观锁能做单 key 的读-改-写原子性。多 key 的事务、Lua 脚本这些都没有。要复杂原子操作用 Redis。

为什么不用 Redis 完全替代 Memcached？

大部分场景确实可以。但 Memcached 有两个优势：一是多线程天然吃满多核，在纯缓存场景下不需要 Redis 那些复杂功能；二是 BSD 协议完全无限制，许可证上比 Redis 干净。另外，有些大厂的 CDN 边缘缓存就是用 Memcached，轻量、内存效率高。
