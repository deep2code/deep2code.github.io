数据库选型的第一性判断

MySQL · Redis · Memcached · Elasticsearch · 向量数据库 · ClickHouse

选存储不是选「最先进的」，是选「能用最少的运维复杂度满足访问模式的」。这篇讲清一个需求摆在面前时该怎么判断，以及为什么默认答案永远是关系型数据库。

先问访问模式，不是先问数据量

大多数选型讨论从「我们有 XX 亿条数据」开始，这是错的。数据量只决定同一类存储里选单机还是分布式；决定存储类型的是访问模式。四个问题按顺序问：

问题答案 A答案 B对选型的影响
查询形态按主键或索引点查、小范围扫描全列扫描做聚合分析A 指向行存储，B 指向列存储
事务边界需要跨多个实体原子更新单条记录独立，无跨实体约束A 必须关系库，B 可以考虑 KV
读写比例读远大于写（100:1 以上）写为主（日志、埋点、监控）A 可加缓存层，B 需要高写入吞吐的存储
延迟要求亚毫秒（用户点击路径上）秒级可接受（报表、离线分析）A 需要内存层，B 可以用列存或批处理
查询能力结构化条件精确过滤分词、相关性排序、语义相似A 关系库够用，B 需要搜索或向量引擎
关系深度最多两三层 join多跳路径遍历、环检测A 关系库够用，B 才考虑图库

默认选关系库的三个理由

一、它的能力边界比你以为的宽。现代 PostgreSQL 一个实例就覆盖了 JSON 文档（jsonb 加 GIN 索引）、全文检索（tsvector）、模糊匹配（pg_trgm）、向量检索（pgvector）、时序（TimescaleDB 扩展）、地理空间（PostGIS）。很多「需要 NoSQL」的场景其实是「需要 jsonb 列」。

二、它的性能上限比你以为的高。一台 32 核 128GB 内存配 NVMe 的实例，索引设计合理时可以支撑单表数亿行、读 QPS 数万、写 TPS 数千。绝大多数系统一辈子到不了这个量级。

三、它的运维成熟度无可替代。备份恢复、主从复制、慢查询分析、连接池、监控指标、故障案例——这些在关系库生态里有二十年的积累。新兴存储的「性能更好」通常是拿成熟度换来的。

能力需求能不能用关系库解决什么时候必须换
半结构化数据能，jsonb 列加 GIN 索引文档结构完全无法预测且需要复杂嵌套查询
全文检索能，tsvector 加 GIN中文分词质量要求高、或千万级文档的检索延迟成瓶颈
缓存加速部分能，靠 buffer pool 与覆盖索引需要亚毫秒 P99、或需要跨实例共享会话状态
时序数据能，分区表加 BRIN 索引写入超过每秒十万点、或需要自动降采样
分析聚合能，物化视图加定时刷新单次扫描超千万行、或分析查询影响线上延迟
向量检索能，pgvector 加 HNSW 索引向量数超千万、或需要复杂的混合过滤加重排
图遍历勉强，递归 CTE需要多跳最短路径、社区发现这类图算法

下面这段 SQL 展示了一个 PostgreSQL 实例同时承担文档、全文检索、模糊匹配、向量检索的写法。在引入第二种存储之前，先确认这些不够用：

-- 一个 PostgreSQL 实例覆盖四种「需要专门数据库」的场景
CREATE EXTENSION IF NOT EXISTS pg_trgm;   -- 模糊匹配
CREATE EXTENSION IF NOT EXISTS vector;    -- 向量检索（pgvector）

CREATE TABLE documents (
  id          bigserial PRIMARY KEY,
  title       text NOT NULL,
  body        text NOT NULL,
  -- 场景一：半结构化数据，不需要文档数据库
  attrs       jsonb NOT NULL DEFAULT '{}'::jsonb,
  -- 场景二：全文检索，不需要 Elasticsearch（中小规模）
  --   generated 列让 tsvector 随 body 自动更新，不用应用维护
  search_vec  tsvector GENERATED ALWAYS AS (
                to_tsvector('simple', title || ' ' || body)
              ) STORED,
  -- 场景三：向量语义检索，不需要 Milvus（千万级以内）
  embedding   vector(1536),
  created_at  timestamptz NOT NULL DEFAULT now()
);

-- jsonb 的 GIN 索引：支持 attrs @> '{"status":"published"}' 这类查询
CREATE INDEX documents_attrs_gin   ON documents USING gin (attrs jsonb_path_ops);
-- 全文检索索引
CREATE INDEX documents_search_gin  ON documents USING gin (search_vec);
-- 模糊匹配索引：让 title LIKE '%关键字%' 也能走索引
CREATE INDEX documents_title_trgm  ON documents USING gin (title gin_trgm_ops);
-- 向量近邻索引：HNSW 精度高但建索引慢，lists 型 IVF 建得快但召回低
CREATE INDEX documents_embed_hnsw  ON documents
  USING hnsw (embedding vector_cosine_ops) WITH (m = 16, ef_construction = 64);

-- 关键优势：混合查询能在一条 SQL 里完成，不用跨存储 join
SELECT id, title,
       1 - (embedding <=> $1::vector) AS similarity
FROM documents
WHERE attrs @> '{"status":"published"}'::jsonb   -- 结构化过滤
  AND search_vec @@ plainto_tsquery('simple', $2) -- 全文过滤
ORDER BY embedding <=> $1::vector                 -- 向量排序
LIMIT 20;

幂等写入保证重放安全

派生存储必须能被完整重建。下面是重建流程的骨架，它同时也是「派生存储数据不对了怎么办」的标准答案：

#!/usr/bin/env bash
# 派生存储全量重建：主库是唯一真相来源，派生数据随时可丢可重建
set -euo pipefail

SRC_DSN="$DATABASE_URL"
ES_URL="${ES_URL:-http://localhost:9200}"
ALIAS="documents"
NEW_INDEX="documents_$(date +%Y%m%d_%H%M%S)"

# 1. 建新索引（不直接写线上索引，避免重建期间搜索结果不完整）
curl -sS -X PUT "$ES_URL/$NEW_INDEX" \
  -H 'Content-Type: application/json' \
  -d '{"settings":{"number_of_shards":3,"refresh_interval":"-1"}}'
#    重建期间关掉 refresh 能显著提速，结束后再开

# 2. 记下重建起点的 LSN：重建完成后增量 CDC 从这里续上，不丢变更
START_LSN=$(psql "$SRC_DSN" -tAc 'SELECT pg_current_wal_lsn()')
echo "起点 LSN: $START_LSN"

# 3. 按主键游标分批导出并写入（不要一次 SELECT 全表，会打满内存）
LAST_ID=0
while :; do
  ROWS=$(psql "$SRC_DSN" -tAc \
    "SELECT json_agg(t) FROM (
       SELECT id, title, body, attrs FROM documents
       WHERE id > $LAST_ID ORDER BY id LIMIT 5000
     ) t")
  [ "$ROWS" = "" ] || [ "$ROWS" = "\\N" ] && break
  echo "$ROWS" | ./bulk-index.sh "$ES_URL" "$NEW_INDEX"
  LAST_ID=$(echo "$ROWS" | jq '[.[].id] | max')
  echo "已导入至 id=$LAST_ID"
done

# 4. 恢复 refresh 并强制刷盘，让新写入可见
curl -sS -X PUT "$ES_URL/$NEW_INDEX/_settings" \
  -H 'Content-Type: application/json' -d '{"refresh_interval":"1s"}'
curl -sS -X POST "$ES_URL/$NEW_INDEX/_refresh"

# 5. 校验数量再切别名：原子切换，搜索流量零中断
PG_COUNT=$(psql "$SRC_DSN" -tAc 'SELECT count(*) FROM documents')
ES_COUNT=$(curl -sS "$ES_URL/$NEW_INDEX/_count" | jq -r .count)
[ "$PG_COUNT" = "$ES_COUNT" ] || { echo "数量不一致 $PG_COUNT vs $ES_COUNT"; exit 1; }

curl -sS -X POST "$ES_URL/_aliases" -H 'Content-Type: application/json' -d "{
  \"actions\": [
    {\"remove\": {\"index\": \"*\", \"alias\": \"$ALIAS\"}},
    {\"add\":    {\"index\": \"$NEW_INDEX\", \"alias\": \"$ALIAS\"}}
  ]
}"
echo "重建完成，增量 CDC 请从 LSN $START_LSN 续接"

组织多存储的原则：把关系库定为唯一真相来源（source of truth），其他所有存储都必须是可以从真相来源完整重建的派生数据。这条原则带来一个实际好处——派生存储出问题时，你的兜底方案永远是「重建」，而不是「抢救」。缓存与数据库的一致性策略、双写失序、延迟双删这些细节详见站内缓存一致性篇。

三个常见的选型错误

错误一：因为「数据量大」就上分布式。分布式带来的不只是扩展性，还有跨节点事务、数据倾斜、rebalance 抖动、运维复杂度。在单机还没榨干之前引入分布式，是用确定的复杂度换不确定的收益。CAP 与一致性谱系的完整讨论详见站内分布式专题。

错误二：因为「schema 会变」就上文档数据库。schema-less 不等于没有 schema，只是把 schema 从数据库移到了应用代码里——而且是隐式的、每条记录可能不同的 schema。读取时的兼容处理代价往往高于写迁移的代价。PostgreSQL 的 jsonb 列可以在关系库里获得同等灵活性，还保留了约束能力。

错误三：为每个功能引入专门的存储。「搜索用 ES、缓存用 Redis、分析用 CK、向量用 Milvus、图关系用 Neo4j」听起来很专业，实际是五套运维、五套监控、五条同步链路、五种故障模式。中小规模团队应该反向思考：能不能用现有存储解决，代价是什么。表设计与范式反范式的权衡详见站内数据库设计专题。

✅
最容易踩的坑
  • 先问数据量而不是访问模式：数据量只决定单机还是分布式，访问模式才决定存储类型。从数据量出发容易过早引入分布式。
  • 把「性能不够」当成换存储的理由：绝大多数「数据库慢」是索引缺失、查询写法、或缺缓存导致的，不是数据库选错了。先用执行计划定位，再谈换存储。
  • 低估多存储的一致性成本：双写在部分失败时必然产生分歧，需要对账任务和分歧告警。这部分工作量通常超过同步链路本身。
  • 没把关系库定为唯一真相来源：派生存储必须能从主库完整重建。做不到重建，出问题时就只能抢救，风险不可控。
  • 用 ES 当数据库：ES 无事务、近实时可见（有 refresh 间隔）、每次更新实际是删除加新建。主数据必须在关系库。
  • 在 OLTP 库上跑大聚合：占满 IO、挤掉 buffer pool、产生长事务阻塞清理。线上库和分析库要分开，至少要分读副本。
  • 为了灵活 schema 放弃约束：文档库的 schema-less 只是把 schema 挪到应用代码里，且变成隐式的。jsonb 列能在保留约束的同时获得灵活性。
  • 引入存储时没规划备份与恢复演练：备份没做过恢复演练等于没有备份。新存储上线前必须验证恢复流程和 RTO。
  • 用向量库替代关系库做过滤：向量库的标量过滤能力弱，混合查询（先过滤再近邻）性能差。中小规模用 pgvector 可以在同一个库里做混合查询。
  • 缓存当成必需品：加缓存就引入了一致性问题和缓存穿透击穿雪崩三类故障。先确认关系库真的撑不住，再加缓存。
  • 忽略连接数上限：Serverless 和多实例部署下，每个实例的连接池叠加会轻易打满数据库连接上限。需要连接代理或 HTTP 模式驱动。
  • 选型只看基准测试：厂商基准跑的是最有利的访问模式。必须用自己的真实数据分布和查询模式做 POC，尤其要测 P99 而不是平均值。
