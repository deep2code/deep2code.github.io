Drizzle 的设计：SQL-first 的类型安全 ORM

🏷️ Drizzle ORM

选 ORM 这件事，真正要回答的不是「哪个更好」，而是你愿意让多少 SQL 生成逻辑离开自己的视野。Drizzle 的答案是：一点都不让。这篇先给「该不该用它」的自查与最小接入，再讲清 SQL-first 这个选择在类型推导、运行时体积、关系查询能力上分别换来了什么、付出了什么。

💡
这篇怎么读
  • ① 用法：判断该不该用 Drizzle 的四步自查（部署形态、团队与 SQL 的关系、关系写入复杂度、你要的是 ORM 还是 SQL 构建器），以及它与 Prisma、Kysely、裸 SQL 的分界表；外加各运行环境该配哪个驱动，和一段可直接抄的连接初始化。
  • ② 原理：SQL-first 与对象优先在调优链路上的差别、四种方案的六维对照、纯 TS 零依赖在 Edge 与冷启动上的工程意义、关系查询能力的取舍（含 relations() 不产生外键这个最常见误解）、三种数据库的支持矩阵、体积与开销该怎么正确认知。
  • ③ 场景：按项目特征选型的决策路径与矩阵、Drizzle 目前不成熟的四处，以及不适用边界。

① 用法 · 该不该用 Drizzle：四步自查

下面四步按顺序问。第一步就可能给出确定答案；如果四步都答完还在犹豫，说明这个项目用哪个都不会出大问题，那就按团队熟悉度选。每一步背后的机制见原理层。

步骤怎么确认结论
1 看部署形态目标运行时是 Cloudflare Workers、Vercel Edge、函数计算这类受限或冷启动敏感的环境，还是长驻的 Node 进程受限运行时 → Drizzle 基本是默认选项，因为它是纯 TypeScript、没有原生二进制；长驻进程 → 这一条不构成理由，继续往下
2 看团队与 SQL 的关系问一个具体问题：团队里有几个人能独立读懂并评审一条带 join 与 group by 的 SQL多数人能 → Drizzle 的心智成本最低，代码评审时看到的几乎就是最终 SQL；多数人不能且没打算补 → Prisma 的 include 更省事，代价是 SQL 不可预测
3 看关系写入的复杂度数一下典型的一次业务操作要写几张表、有没有「创建主体时顺带创建一批关联」的需求嵌套写入很多 → Prisma 一行能做完的事，Drizzle 要自己写事务并封装；能接受这层封装成本再选 Drizzle
4 看你要的到底是什么问：需不需要 schema 定义、迁移生成、关系查询这三样三样都要 → Drizzle；只要「类型安全地拼 SQL」，表结构由别人管 → Kysely；全项目只有十几条固定查询 → 直接用驱动写 SQL，引入任何 ORM 都是多一层
需求选谁为什么
一份 TS schema 同时产出类型与迁移脚本Drizzle类型从 schema 直接推导，没有代码生成这一步，改完 schema 立刻有类型报错
只想类型安全地拼 SQL，表结构由 DBA 或别的系统管Kysely它没有 schema 层也不管迁移，职责更窄，正好匹配这种分工
全项目只有十几条固定 SQL，没有模型层需求驱动加手写 SQLORM 的价值在于「大量重复的结构化查询」，量不到就只是多一层抽象
嵌套创建、关联条件过滤要写得极简Prismainclude 与嵌套 create 是它的强项，Drizzle 这两处都要手写
部署在 Cloudflare Workers 或 Vercel EdgeDrizzle纯 TS 零原生依赖，不需要额外的代理服务就能跑
团队以 CRUD 后台为主，多数成员不写 SQLPrisma心智负担更低，生态、文档与可视化工具都更成熟
同一套代码要支持 PostgreSQL、MySQL、SQLiteDrizzleschema API 按方言分离，不用一层抽象磨平差异，方言特有能力仍然可用
已经在用 Prisma 且没有遇到具体痛点继续用 Prisma迁移要逐条改写查询，收益不明确时不值得

① 用法 · 驱动怎么选与最小可用接入

Drizzle 自己不管连接，连接池、超时、重试全部归驱动。选错驱动的表现通常不是变慢，而是在目标运行时里直接报错，所以这张表要在写第一行代码之前看。

运行环境该用的驱动注意什么
长驻 Node 服务 + PostgreSQLpostgres.js 或 node-postgres连接池参数在驱动侧配置；Drizzle 只是包装层，不要指望它管连接生命周期
Cloudflare WorkersD1 绑定，或用 Hyperdrive 代理连到 PostgreSQLWorkers 没有 TCP 与原生二进制，node-postgres 一律用不了
Vercel EdgeNeon Serverless Driver 的 HTTP 模式同一个驱动的 TCP 模式在 Edge 不可用，选错的表现是运行时直接抛错
函数计算 / LambdaHTTP 驱动，或走外置连接代理每个实例各持一个连接池，实例一多就把数据库连接数打满
长驻 Node 服务 + MySQLmysql2PlanetScale 要用它自己的 Serverless 驱动
本地、内嵌或边缘 SQLitebetter-sqlite3、Bun 内置 SQLite、D1、Turso（libSQL）D1 与 Turso 各有自己的 SQL 与事务限制，不要按本地 SQLite 的能力写代码
// 长驻 Node 进程 + PostgreSQL：最小可用接入
import { drizzle } from 'drizzle-orm/postgres-js';
import postgres from 'postgres';
import * as schema from './schema';

// 连接池归 postgres.js 管，这三个参数决定了数据库侧看到的连接数与回收速度
const client = postgres(process.env.DATABASE_URL!, {
  max: 20,              // 单进程最大连接数：乘以实例数才是数据库承受的总量
  idle_timeout: 20,     // 空闲回收（秒）：云数据库常有自己的空闲断连，设得比它短
  connect_timeout: 10,  // 建连超时（秒）：没有它，数据库不可用时请求会一直挂着
});

// 传 schema 才能用 db.query 关系查询；只用 select/insert/update/delete 时可以不传
export const db = drizzle(client, { schema });

// Cloudflare Workers + D1：换 import 路径，不要引入任何 node 驱动
// import { drizzle } from 'drizzle-orm/d1';
// export const db = drizzle(env.DB, { schema });

② 原理 · SQL-first 的设计哲学

搞清这一节能解决「线上出现慢查询时，能不能直接从代码看出它执行了什么」。

Drizzle 的核心定位是「SQL-first」而不是「对象优先」。它不做持久化上下文、不做懒加载、不生成你看不懂的 SQL。查询构建器几乎是 SQL 的一对一映射：你写 select().from().where()，生成的就是 SELECT ... FROM ... WHERE ...。从 SQL 到代码的心智转换成本接近零。

这与 Prisma、TypeORM 的「对象优先」设计完全不同。Prisma 把 SQL 藏在 Rust 引擎后面，你写 findMany({ include: { posts: true } })，生成了什么 SQL 取决于查询引擎的内部优化——你无法预测。TypeORM 走 Active Record 和 Data Mapper 双模式，但 eager loading 和 lazy loading 的行为经常让人困惑。Drizzle 的哲学是：你应该知道你的代码会执行什么 SQL，因为它几乎就是你写的 SQL。

flowchart TB subgraph SQL-first["SQL-first 路径"] A1["开发者写 SQL 风格代码"] --> A2["Drizzle 一对一映射"] A2 --> A3["可预测的 SQL 输出"] end subgraph ORM-first["对象优先路径"] B1["开发者写对象操作"] --> B2["ORM 引擎翻译"] B2 --> B3["不可预测的 SQL"] end A3 --> C{"生产调优时
能直接看懂 SQL？"} B3 --> C C -->|SQL-first| D["直接定位慢查询"] C -->|对象优先| E["需要开 debug 日志
再翻译回 SQL"]

这个设计选择意味着 Drizzle 不会有「N+1 查询但你不知道」的问题——因为你写的就是你得到的。代价是你需要自己处理关联查询的写法，没有 Prisma 那种 include 一行搞定的便利。

// 同一个需求两种写法：查出有文章的用户及其文章数

// Drizzle — 代码结构与最终 SQL 逐句对应，评审时看代码等于看 SQL
const result = await db
  .select({
    id: users.id,
    name: users.name,
    // sql 模板里的 ${} 是参数化占位，不是字符串拼接；泛型只声明返回类型
    postCount: sql<number>`count(${posts.id})`.as('post_count'),
  })
  .from(users)
  .leftJoin(posts, eq(users.id, posts.authorId))
  .groupBy(users.id)
  .having(gt(sql`count(${posts.id})`, 0));
// 生成的 SQL: SELECT id, name, count(posts.id) as post_count
//             FROM users LEFT JOIN posts ON users.id = posts.author_id
//             GROUP BY users.id HAVING count(posts.id) > 0

// Prisma — 同样的需求写起来更短，但生成几条 SQL、怎么聚合，取决于引擎版本

② 原理 · 与主流 ORM 的六维对照

搞清这一节能解决「同事说某个 ORM 更好，但说不出在哪个维度上更好」。

选 ORM 不是选「最好的」，是选「最适合你项目约束的」。以下六个维度是实际选型时最关键的差异：

② 原理 · 纯 TS 零依赖的工程意义

搞清这一节能解决「为什么同一套代码在本地跑得好，部署到 Edge 就直接起不来」。

Drizzle 的 drizzle-orm 包是纯 TypeScript，没有原生二进制依赖，没有 Rust 引擎，没有 WASM。这个特性在三个场景下有决定性优势：

场景Drizzle 的表现Prisma 的问题
Cloudflare Workers直接用，搭配 D1 或 HyperdriveWorkers 不支持原生二进制，需 Prisma Accelerate（额外付费服务）
Vercel Edge Functions直接用，搭配 Neon Serverless DriverEdge Runtime 限制二进制，需要特殊适配
Docker 镜像体积node_modules 里只有 JS，镜像层更瘦引擎二进制体积不小，且多平台构建要带多个二进制
CI/CD 速度普通安装，无 postinstall 生成步骤多一步 generate 与引擎下载
冷启动时间只加载 JS 模块还要初始化引擎，多一段固定开销；具体数值以目标平台的冷启动指标为准

关键认知：Prisma 的 Rust 引擎不只是「大」，它还导致了一个架构问题——查询规划发生在 Rust 层，TS 层只是发指令。这意味着调试时你需要理解两层系统的交互。Drizzle 的所有逻辑都在 TS 层，调试链路是线性的。

② 原理 · 关系查询能力的取舍

搞清这一节能解决「relations() 写了为什么数据库里没有外键」这个新手必犯的误解。

Drizzle 的关系查询能力弱于 Prisma，这是 SQL-first 设计的代价。具体差异：

能力DrizzlePrisma影响
嵌套查询query API 的 with 嵌套，生成 JSON 聚合 SQLinclude/select 嵌套，引擎优化Drizzle 的 query API 生成单条 SQL 不是 N+1
关联过滤需手动 join + wherewhere 里直接写关联条件Prisma 写法更简洁
嵌套写入不支持，需手动事务create 里直接嵌套创建关联多表写入 Prisma 一行 vs Drizzle 多行
级联删除依赖数据库外键 ON DELETEPrisma 层面处理级联Drizzle 更依赖数据库原生能力

常见误解纠正：很多人以为 Drizzle 的 relations() 定义会在数据库创建外键——不会。relations() 只服务于 Drizzle 的 query API（关系查询），它告诉 Drizzle 表之间的逻辑关系，但不会生成任何 DDL。如果你需要数据库层面的外键约束，必须在 schema 定义里用 .references()。这是新手最容易误解的点。

stateDiagram-v2 [*] --> SchemaDefine: 定义 pgTable SchemaDefine --> Relations: relations() 定义逻辑关系 SchemaDefine --> ForeignKey: .references() 定义数据库外键 Relations --> QueryAPI: 服务于 db.query 关系查询 ForeignKey --> DDL: 生成 ALTER TABLE ADD CONSTRAINT QueryAPI --> JSONAgg: 生成带 JSON 聚合的单条 SQL note right of Relations: 不产生任何 DDL note right of ForeignKey: 真正的数据库约束

② 原理 · Drizzle 的数据库支持矩阵

搞清这一节能解决「为什么 Drizzle 不提供一套统一的跨库抽象」。

Drizzle 为每种数据库提供专属的 schema API，不是用一套抽象层去磨平差异（TypeORM 的做法），而是让你直接用每种数据库的原生能力：

数据库Schema API支持的驱动边缘支持特有能力
PostgreSQLpgTablepostgres.js、node-postgres、Neon Serverless、SupabaseNeon + Vercel Edge数组类型、JSON 操作、全文搜索
MySQLmysqlTablemysql2、PlanetScale ServerlessPlanetScaleON DUPLICATE KEY、JSON 操作
SQLitesqliteTablebetter-sqlite3、Bun SQLite、D1、Turso/libSQLD1 + CF Workers、Turso轻量内嵌、WAL 模式

② 原理 · 体积与开销该怎么认知

搞清这一节能解决「到底该不该为了性能换 ORM」——结论通常是不该，但换的理由可能另有其一。

网上流传的各种 ORM 跑分基本不可复用：数字随版本、驱动、连接方式、网络与数据库配置大幅变化。下表只给差异来自哪里和你该怎么在自己环境里量，不给具体毫秒数。

维度DrizzlePrisma驱动直写 SQL怎么在你的环境里量
安装与构建步骤普通 npm 包，无代码生成步骤需要 prisma generate，并下载对应平台的引擎二进制只装驱动在 CI 上各跑一次干净安装加构建，对比总时长
依赖与镜像体积纯 TypeScript，无原生二进制含引擎二进制，按目标平台分发最小du -sh node_modules 与容器镜像层大小
单条查询的额外开销只有拼 SQL 的 JS 开销多一次 TS 层到引擎层的跨层调用基准同一环境对同一条 SQL 压测，比较 p99 而不是平均值
冷启动只加载 JS 模块还要初始化引擎最快在目标平台看真实冷启动指标，本机数据没有参考价值
带 join 的查询与手写 SQL 等价，条数可预测由引擎决定，可能拆成多条手写，完全可控打开数据库侧语句日志，数一次业务请求实际执行了几条 SQL
受影响最大的场景几乎不受影响Edge、冷启动敏感、镜像体积敏感的场景不适用先确认瓶颈在哪一层，再决定要不要动 ORM

注意：ORM 层的开销在绝大多数场景下不是瓶颈——网络往返和数据库执行时间通常比 ORM 那点 JS 开销高出好几个数量级。所以选 ORM 不该按跑分选，而该按开发体验、SQL 可预测性、部署约束选。唯一真正因「性能」换 ORM 的合理场景是冷启动与包体积受硬约束的边缘与函数环境，那不是运行时快慢问题，是能不能跑起来的问题。

③ 场景 · 什么项目该选 Drizzle

不存在「所有项目都该用 Drizzle」的结论。选型取决于项目约束：

③ 场景 · Drizzle 的局限与不适用边界

公允地说，Drizzle 还有这些不足：

生态年轻：Prisma 2019 年发布，社区积累远超 Drizzle（2023 年才火起来）。遇到问题搜 Stack Overflow 的结果少得多。

文档质量不稳定：官方文档在快速迭代中，有些页面过时，API 变更时文档更新滞后。

迁移工具功能较少：drizzle-kit 能 generate 和 push，但没有 Prisma 的 shadow database 机制来检测 drift，也没有内置的回滚能力。

没有 Prisma Studio 这类 GUI：Drizzle Studio 存在但功能有限，不如 Prisma Studio 成熟。

最容易踩的坑

❌
前两条是新手必犯的认知错误
  • relations() 不等于外键：relations() 只服务于 query API 的关系查询，不会在数据库创建任何外键约束。需要外键必须用 .references()。
  • join 返回扁平元组：leftJoin/innerJoin 返回的是 { users: {...}, posts: {...} } 的扁平结构，不是 { ...user, posts: [...] } 的嵌套结构。需要嵌套用 query API 的 with。
  • schema 变更后忘记 generate：改了 TS schema 文件后必须跑 drizzle-kit generate 生成迁移 SQL，否则数据库表结构不会变。push 只适合本地开发。
  • sql 模板必须用参数化：用 sql`` 模板时必须用 ${variable} 传参，不能拼接字符串，否则 SQL 注入。详见站内 SQL 注入篇。
  • Prisma 迁移不能直接迁：Prisma 的 _prisma_migrations 表和 Drizzle 的 __drizzle_migrations 表格式不同，迁移历史不互通。切换时需要从当前数据库状态重新 baseline。
  • 边缘运行时的驱动选择：CF Workers 只能用 D1 或 Hyperdrive，不能用 node-postgres。Vercel Edge 只能用 Neon Serverless Driver 的 HTTP 模式，不能用 TCP。选错驱动直接运行报错。
  • db.query 需要传 schema：drizzle() 初始化时不传 schema 参数，db.query 就不可用。如果只用 select/insert 链式 API 可以不传，但 query API 的关系查询必须传。
  • $inferSelect 和 $inferInsert 的区别：$inferInsert 类型里有默认值的列是 optional，$inferSelect 里所有列都是 required。混用会导致类型错误。
  • prepared statement 缓存：Drizzle 的 prepared() 返回可复用的预编译语句，在高频查询场景下可以省去每次的 SQL 解析开销，但要注意连接池里不同连接的 prepared statement 不共享。
  • 不要在 Edge 用连接池：Edge/Serverless 环境的每次请求是独立的，连接池没有意义且可能导致连接泄漏。用 HTTP 模式的驱动（如 Neon Serverless HTTP）或连接代理（如 Supabase Pooler）。
