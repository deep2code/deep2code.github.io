Drizzle 上手：schema 定义与类型推导

Drizzle 的 schema 就是 TypeScript 代码——没有 DSL、没有 .prisma 文件、没有代码生成步骤。这个设计让类型推导变得直接：表定义本身就携带类型信息，编辑器不需要等 generate 就能给出补全。这篇讲清 schema 定义的每个环节和类型推导的实际用法。

💡
这篇怎么读
  • ① 用法：一份能直接跑起来的最小 schema——两张表、一个关系、一个 db 实例、一份配置，加上用 $inferSelect 与 $inferInsert 写出的增查函数；再给「要表达什么 → 怎么写 → 注意什么」速查表和 drizzle.config.ts 各字段的作用。
  • ② 原理：表定义三个参数的语义、列类型与约束链对 DDL 和推导类型各自的影响、两套推导类型为什么形状不同、relations() 与 .references() 的六维差异、索引与复合约束的写法与版本差异、多 schema、循环引用与自引用为什么必须延迟求值。
  • ③ 场景：按项目规模选 schema 组织方式、类型边界该放在哪里、哪些列类型选择在上线后几乎改不动，以及不适用边界。

① 用法 · 最小可用：四个文件跑通 schema 与类型推导

下面四段按顺序放进项目就能跑。先把这条链路打通，再回原理层看每个环节为什么这么写：schema 定义 → 类型导出 → 连接实例 → 迁移配置。

// 1) src/schema/index.ts —— 两张表加一个关系，够用的最小形态
import { pgTable, uuid, text, integer, timestamp, boolean, index } from 'drizzle-orm/pg-core';
import { relations } from 'drizzle-orm';

export const users = pgTable('users', {
  // 对象的 key 是 TS 属性名，字符串参数是数据库里的真实列名，两者可以不同
  id: uuid('id').primaryKey().defaultRandom(),
  email: text('email').notNull().unique(),
  displayName: text('display_name').notNull(),
  age: integer('age'),                     // 没写 notNull，所以推导出来带 null
  isActive: boolean('is_active').notNull().default(true),
  // PostgreSQL 上几乎总该带时区，否则同一时刻在不同部署地会算出不同结果
  createdAt: timestamp('created_at', { withTimezone: true }).notNull().defaultNow(),
});

export const posts = pgTable('posts', {
  id: uuid('id').primaryKey().defaultRandom(),
  title: text('title').notNull(),
  // 只有 .references() 会真的生成外键；relations() 不会
  authorId: uuid('author_id').notNull().references(() => users.id, { onDelete: 'cascade' }),
  createdAt: timestamp('created_at', { withTimezone: true }).notNull().defaultNow(),
}, (t) => [
  // 列表页「某作者的文章按时间倒序」靠这条索引，条件与排序都在索引里
  index('posts_author_created_idx').on(t.authorId, t.createdAt.desc()),
]);

// relations 只服务于 db.query 的 with 嵌套，不产生任何 DDL
export const usersRelations = relations(users, ({ many }) => ({ posts: many(posts) }));
export const postsRelations = relations(posts, ({ one }) => ({
  author: one(users, { fields: [posts.authorId], references: [users.id] }),
}));
// 2) src/schema/types.ts —— 类型只从表定义推导，不要手写接口
import type { users, posts } from './index';

export type User = typeof users.$inferSelect;      // 查出来的行：所有列都在
export type NewUser = typeof users.$inferInsert;   // 插入参数：有默认值的列是可选的
export type Post = typeof posts.$inferSelect;

// 3) src/db.ts —— 连接实例
import { drizzle } from 'drizzle-orm/postgres-js';
import postgres from 'postgres';
import * as schema from './schema';

const client = postgres(process.env.DATABASE_URL!, { max: 20, connect_timeout: 10 });
// 必须传 schema，否则 db.query 关系查询整个不可用（只影响 query API，不影响 select）
export const db = drizzle(client, { schema });

// 用推导类型写业务函数：入参出参都不用手写字段列表
export async function createUser(input: NewUser): Promise<User> {
  // input 里不需要 id、isActive、createdAt —— 它们都有默认值，所以是可选的
  const [row] = await db.insert(users).values(input).returning();
  return row;
}

await createUser({ email: 'a@b.com', displayName: '张三' });   // 通过
// await createUser({ email: 'a@b.com' });                     // 编译期报错：缺 displayName
// 4) drizzle.config.ts —— drizzle-kit 靠它找到 schema 并生成迁移
import { defineConfig } from 'drizzle-kit';

export default defineConfig({
  dialect: 'postgresql',
  schema: './src/schema/index.ts',   // 指向统一入口；拆了文件也只填这一个
  out: './drizzle',                  // 迁移 SQL 与快照的输出目录，要提交进版本库
  dbCredentials: { url: process.env.DATABASE_URL! },
  verbose: true,                     // 打印将要执行的 SQL，评审时靠它看清动作
  strict: true,                      // 危险操作前二次确认，别在 CI 里关掉
});
// 之后只有两条命令：drizzle-kit generate 生成迁移，drizzle-kit migrate 应用迁移。
// 生产流程与不可逆变更的处理见本簇最后一篇。

① 用法 · 列与约束速查：要表达什么，就怎么写

这张表覆盖日常写 schema 时九成的动作。右列是这一处最常见的翻车方式——其中一半属于「不报错但行为不对」，所以值得逐行看一遍。

要表达什么怎么写注意什么
数据库是 snake_case，代码想用 camelCase对象 key 写 displayName，字符串参数写 'display_name'报「column does not exist」时先查字符串参数，不是查 TS 属性名
一列可以为空什么都不加，不写 .notNull()它在 $inferSelect 里带 | null，在 $inferInsert 里是可选
金额numeric('amount', { precision: 12, scale: 2 })推导成字符串，这是为了不丢精度；不要 parseFloat 之后直接算
时间timestamp('created_at', { withTimezone: true })漏掉 withTimezone 会生成不带时区的类型，后期改它属于重写级变更
取值固定的状态小整数列加 check()，或用 pgEnum枚举取值以后要增删的话别用 pgEnum，它的迁移 diff 支持有限
半结构化扩展字段jsonb('metadata').$type<T>()$type 是编译期断言，运行时零校验，脏数据会以「正确类型」进入代码
复合唯一、复合主键、部分索引都写在第三个参数里，返回数组单列唯一可以用链式 .unique()，复合的一律不行
多对多中间表加复合主键，并且给中间表也定义 relations()漏掉中间表的 relations 时，with 嵌套会静默返回空数组
树形、自引用.references((): AnyPgColumn => categories.id) 并给 relations 加 relationName不标注类型会报循环引用；不配对 relationName 无法区分父与子方向
真外键与级联.references(() => users.id, { onDelete: 'cascade' })relations() 不生成外键，两者互不替代

② 原理 · 表定义的基本结构

搞清这一节能解决「同一个字段在代码里叫一个名字、在库里叫另一个名字」这类改名需求该怎么落。

每种数据库有专属的表定义函数：PostgreSQL 用 pgTable，MySQL 用 mysqlTable，SQLite 用 sqliteTable。它们的第一个参数是数据库里的真实表名，第二个参数是列定义对象，第三个参数（可选）是索引和约束的定义。

关键点：列定义里的字符串参数是数据库里的真实列名，而对象的 key 是你在 TS 代码里用的属性名。这两者可以不同——这是处理 snake_case 数据库和 camelCase 代码的标准做法。

// schema/users.ts
import {
  pgTable, serial, text, integer, timestamp, boolean,
  varchar, uuid, jsonb, pgEnum, index, uniqueIndex,
} from 'drizzle-orm/pg-core';

// 枚举：先定义数据库类型，再在列里用
export const userRoleEnum = pgEnum('user_role', ['admin', 'editor', 'viewer']);

export const users = pgTable('users', {
  // 对象 key 是 TS 属性名，字符串是数据库列名
  id: uuid('id').primaryKey().defaultRandom(),
  email: varchar('email', { length: 255 }).notNull().unique(),
  displayName: text('display_name').notNull(),   // TS: displayName / DB: display_name
  role: userRoleEnum('role').notNull().default('viewer'),
  age: integer('age'),                            // nullable，因为没有 notNull
  metadata: jsonb('metadata').$type<{ theme: string; lang: string }>(),
  isActive: boolean('is_active').notNull().default(true),
  // defaultNow() 是数据库层面的 DEFAULT now()
  createdAt: timestamp('created_at', { withTimezone: true }).notNull().defaultNow(),
  // $onUpdate 是 Drizzle 应用层的钩子，不是数据库触发器
  updatedAt: timestamp('updated_at', { withTimezone: true })
    .notNull().defaultNow().$onUpdate(() => new Date()),
}, (table) => [
  // 第三个参数：索引与复合约束（Drizzle 0.30+ 返回数组）
  index('users_role_idx').on(table.role),
  index('users_created_at_idx').on(table.createdAt.desc()),
  uniqueIndex('users_email_lower_idx').on(table.email),
]);

② 原理 · 列类型与约束的完整对照

搞清这一节能解决「这个列该选什么类型、加了约束之后插入代码要不要改」。

Drizzle 的列类型直接映射到数据库原生类型，不做抽象磨平。这意味着你需要知道目标数据库有什么类型，但也意味着你能用到所有原生能力。

② 原理 · 类型推导：$inferSelect 与 $inferInsert

搞清这一节能解决「插入时 TS 要求我传 id 和 createdAt」这类明显不对的类型报错。

这是 Drizzle 类型系统最实用的部分。同一张表有两套类型，因为「查出来的数据」和「插入时要提供的数据」形状不同。

$inferSelect：查询返回的行类型。所有列都存在，nullable 列的类型带 | null。

$inferInsert：插入时的参数类型。有默认值的列、自增主键、nullable 的列都是 optional。这意味着你写 db.insert(users).values({ email, displayName }) 时 TS 不会抱怨缺少 id 和 createdAt——这是最实用的一点。

flowchart TB A["pgTable 定义"] --> B["列定义 + 约束链"] B --> C["$inferSelect"] B --> D["$inferInsert"] C --> C1["所有列必填"] C --> C2["nullable 列带 null 联合"] D --> D1["有 default 的列 optional"] D --> D2["自增主键 optional"] D --> D3["nullable 列 optional"] D --> D4["notNull 且无 default 的列 必填"] C1 --> E["用于函数返回值类型"] D4 --> F["用于 API 入参校验"]
列定义$inferSelect 里的类型$inferInsert 里的类型
uuid('id').primaryKey().defaultRandom()string（必填）string 或省略（optional）
text('name').notNull()string（必填）string（必填）
integer('age')number 或 null（必填但可为 null）number 或 null 或省略（optional）
boolean('active').notNull().default(true)boolean（必填）boolean 或省略（optional）
timestamp('created_at').notNull().defaultNow()Date（必填）Date 或省略（optional）
serial('seq')number（必填）number 或省略（optional）
 
// schema/types.ts — 导出推导类型供全项目使用
import type { InferSelectModel, InferInsertModel } from 'drizzle-orm';
import { users, posts } from './index';

// 两种等价写法：属性访问或泛型工具类型
export type User = typeof users.$inferSelect;        // 查询结果类型
export type NewUser = typeof users.$inferInsert;     // 插入参数类型
export type Post = InferSelectModel<typeof posts>;   // 等价于 $inferSelect
export type NewPost = InferInsertModel<typeof posts>;

// 实际用法：函数签名直接用推导类型
async function createUser(input: NewUser): Promise<User> {
  // input 里不需要 id / createdAt / updatedAt / isActive
  // 因为它们都有 default，$inferInsert 把它们标成 optional
  const [row] = await db.insert(users).values(input).returning();
  return row;
}

// 编译期就能发现问题
await createUser({ email: 'a@b.com', displayName: '张三' });  // OK
// await createUser({ email: 'a@b.com' });  // 报错：缺少 displayName

// 只取部分字段时用 Pick，不要手写接口
type UserSummary = Pick<User, 'id' | 'email' | 'displayName'>;

// $type 的陷阱：它只是断言，运行时不校验
// metadata: jsonb('metadata').$type<{ theme: string }>()
// 数据库里如果是 { color: 'red' }，TS 以为是 { theme: string }
// 需要运行时校验请配合 zod 在边界处 parse

② 原理 · relations() 与真外键的区别

搞清这一节能解决「关系都定义了，为什么库里还能插进指向不存在用户的文章」。

这是 Drizzle 新手最大的误解来源。relations() 和 .references() 是两件完全不同的事：

对比项relations().references()

服务对象db.query 关系查询 API 的 with 嵌套数据库的引用完整性检查
缺失的后果db.query 的 with 不可用，但 join 仍能用可以插入指向不存在记录的孤儿行
级联行为无onDelete / onUpdate 控制级联
是否必需只用 join 的话不需要生产环境强烈建议加

// schema/posts.ts — 关系定义的正确写法
import { pgTable, uuid, text, timestamp, integer } from 'drizzle-orm/pg-core';
import { relations } from 'drizzle-orm';
import { users } from './users';

export const posts = pgTable('posts', {
  id: uuid('id').primaryKey().defaultRandom(),
  title: text('title').notNull(),
  body: text('body').notNull(),
  // 这一行才产生数据库外键 + 级联删除
  authorId: uuid('author_id')
    .notNull()
    .references(() => users.id, { onDelete: 'cascade' }),
  createdAt: timestamp('created_at').notNull().defaultNow(),
});

export const tags = pgTable('tags', {
  id: uuid('id').primaryKey().defaultRandom(),
  name: text('name').notNull().unique(),
});

// 多对多的中间表
export const postsToTags = pgTable('posts_to_tags', {
  postId: uuid('post_id').notNull().references(() => posts.id, { onDelete: 'cascade' }),
  tagId: uuid('tag_id').notNull().references(() => tags.id, { onDelete: 'cascade' }),
}, (t) => [
  primaryKey({ columns: [t.postId, t.tagId] }),  // 复合主键
]);

// relations：只服务于 db.query，不产生 DDL
export const usersRelations = relations(users, ({ many }) => ({
  posts: many(posts),
}));

export const postsRelations = relations(posts, ({ one, many }) => ({
  author: one(users, {
    fields: [posts.authorId],      // 本表的列
    references: [users.id],        // 目标表的列
  }),
  tags: many(postsToTags),
}));

export const postsToTagsRelations = relations(postsToTags, ({ one }) => ({
  post: one(posts, { fields: [postsToTags.postId], references: [posts.id] }),
  tag:  one(tags,  { fields: [postsToTags.tagId],  references: [tags.id] }),
}));
// 多对多必须为中间表也定义 relations，否则 with 嵌套查不到

② 原理 · 索引、复合约束与多 schema

搞清这一节能解决「索引写了却没出现在迁移文件里」这种静默失效。

单列的唯一约束用链式 .unique()，但复合索引、复合唯一、复合主键、部分索引都必须在 pgTable 的第三个参数里定义。

版本差异要注意：Drizzle 0.30 之前第三个参数的回调返回对象（key 是随意的标识符），0.30 之后改为返回数组。旧写法仍能工作但会有 deprecation 警告，新项目直接用数组形式。

需求写法生成的 DDL
单列索引index('idx_name').on(t.col)CREATE INDEX idx_name ON t (col)
复合索引index('idx').on(t.a, t.b)CREATE INDEX idx ON t (a, b)
降序索引index('idx').on(t.createdAt.desc())CREATE INDEX idx ON t (created_at DESC)
复合唯一uniqueIndex('uq').on(t.a, t.b)CREATE UNIQUE INDEX uq ON t (a, b)
复合主键primaryKey({ columns: [t.a, t.b] })PRIMARY KEY (a, b)
部分索引index('idx').on(t.a).where(sql`deleted_at is null`)CREATE INDEX ... WHERE deleted_at IS NULL
GIN 索引（JSONB）index('idx').using('gin', t.metadata)CREATE INDEX ... USING gin (metadata)
检查约束check('age_positive', sql`age > 0`)CHECK (age > 0)

多 schema（PostgreSQL 的 namespace）用 pgSchema 创建：

import { pgSchema, uuid, text, timestamp } from 'drizzle-orm/pg-core';

// 定义 schema（namespace），用于多租户或模块隔离
export const authSchema = pgSchema('auth');
export const billingSchema = pgSchema('billing');

// 在指定 schema 下建表
export const sessions = authSchema.table('sessions', {
  id: uuid('id').primaryKey().defaultRandom(),
  userId: uuid('user_id').notNull(),
  expiresAt: timestamp('expires_at').notNull(),
});

export const invoices = billingSchema.table('invoices', {
  id: uuid('id').primaryKey().defaultRandom(),
  amount: numeric('amount', { precision: 12, scale: 2 }).notNull(),
});
// 生成的 SQL 会带 schema 前缀：SELECT * FROM "auth"."sessions"
// drizzle.config.ts 里需要配置 schemaFilter 才能让 drizzle-kit 识别

② 原理 · schema 文件的组织方式

搞清这一节能解决「拆完文件后 drizzle-kit 少扫了表、db.query 少了几张表」。

单文件塞几十张表会变成几千行的巨石文件。推荐按业务领域拆分，然后统一导出：

// schema/index.ts — 统一导出入口
export * from './enums';
export * from './users';
export * from './posts';
export * from './orders';

// drizzle.config.ts

② 原理 · 循环引用与延迟求值

搞清这一节能解决「拆文件之后编译报 circular reference，或者运行时某张表是 undefined」。

拆分文件后必然遇到循环引用：users.ts 里的表被 posts.ts 引用，而 posts.ts 又被 users.ts 的 relations 引用。

Drizzle 的解法是所有跨表引用都用箭头函数延迟求值：.references(() => users.id) 而不是 .references(users.id)。箭头函数在实际需要时才执行，此时模块已加载完毕。同理 relations() 的回调也是延迟的。

但有一个例外场景 TS 无法自动推导：自引用表（树形结构的 parentId 指向自己）。这时需要显式标注类型或用 AnyPgColumn。

import { pgTable, uuid, text, type AnyPgColumn } from 'drizzle-orm/pg-core';

// 自引用表：categories 的 parentId 指向自己的 id
export const categories = pgTable('categories', {
  id: uuid('id').primaryKey().defaultRandom(),
  name: text('name').notNull(),
  // 自引用必须标注 AnyPgColumn，否则 TS 报 circular reference
  parentId: uuid('parent_id')
    .references((): AnyPgColumn => categories.id, { onDelete: 'set null' }),
});

// 自引用的 relations 需要 relationName 区分方向
export const categoriesRelations = relations(categories, ({ one, many }) => ({
  parent: one(categories, {
    fields: [categories.parentId],
    references: [categories.id],
    relationName: 'category_tree',   // 必须命名，否则 Drizzle 无法区分
  }),
  children: many(categories, {
    relationName: 'category_tree',   // 与 parent 用同一个名字配对
  }),
}));

③ 场景 · 不同规模与需求下的取舍

schema 层的决定分两类：组织方式随时能改，列类型选择上线后几乎改不动。下表把两类分别标出来。

场景该怎么做为什么代价
十张表以内的小项目单个 schema.ts，类型直接用 $inferInsert结构一眼看完，额外分层没有收益表一多就难导航，多人改同一文件时 git 冲突频繁
十到一百张表按业务领域拆文件，index.ts 统一 re-exportdrizzle-kit 与 db.query 都需要一个总入口来看到全部表跨文件引用必须用箭头函数延迟求值，否则循环引用
多团队 monorepo、上百张表按服务拆包，各包独立迁移目录各服务能独立发布，迁移互不阻塞跨包关系无法用 relations() 表达，只能在应用层拼装
来自 HTTP 请求体的输入先用运行时校验库解析，再把结果交给 $inferInsert 类型的参数推导类型与 $type 都只在编译期生效，运行时零校验多一层校验 schema，要和表定义保持同步
金额、税率、库存这类高精度数值numeric 列，用字符串或十进制库运算推导成字符串正是为了不产生浮点误差不能直接做算术，要封装一层计算函数
多地区部署、跨时区业务所有时间列一律带时区不带时区的类型会丢掉偏移量，同一时刻算出不同结果这属于上线后最难改的一类：改类型要重写全表并校验全部历史数据
状态取值以后会增删用小整数或文本列加 check()，不用 pgEnum枚举增删值的迁移 diff 支持有限，删值基本要手写 SQL失去数据库原生枚举的可读性，得靠列注释与应用枚举维持语义
多租户或模块隔离pgSchema 分 namespace，并配 schemaFilter不配的话 drizzle-kit 只扫默认 schema，其他 schema 的变更不进迁移每次迁移要按 schema 逐个执行，要处理执行到一半失败的中间态

不适用边界：本篇只讲 schema 与类型。select、join、db.query 的 with、事务与什么时候该直接写 SQL 在下一篇 查询构建：关系查询、join 与事务；迁移怎么生成、怎么在生产按顺序应用、不可逆变更怎么处理在 迁移管理：生成、应用与生产流程；该不该用 Drizzle 的判断在上一篇 Drizzle 的设计：SQL-first 的类型安全 ORM；表结构本身该怎么设计（范式、冗余、主键选型）在 范式与反范式：数据库设计的取舍；索引该建在哪几列、顺序怎么排在 索引设计与优化；timestamptz、numeric、jsonb 这些类型在数据库侧的存储与语义细节在 PostgreSQL 数据类型；已有数据的表怎么安全加约束、改类型在 模式演进与约束设计。

这条路径上，上一篇决定了用不用 Drizzle，本篇把表和类型定下来，下一篇开始用它们查数据。

最容易踩的坑

❌
这里大半是「不报错但行为不对」的坑
  • relations() 不生成外键：它只服务 db.query 的 with 嵌套。需要数据库外键必须用 .references()。这两者可以只有一个，也可以都有，互不影响。
  • 多对多必须给中间表也定义 relations：只给两端的表定义 relations 而漏掉中间表，with 嵌套查询会静默返回空数组，不报错。
  • timestamp 忘记 withTimezone：默认生成 TIMESTAMP WITHOUT TIME ZONE，时区信息丢失，多地区部署会算错时间。PostgreSQL 里几乎总应该用 timestamptz。
  • numeric 推导成 string 不是 number：这是故意的，避免 JS 浮点精度丢失。金额计算必须用 decimal 库，不要 parseFloat 后直接运算。
  • $type 不做运行时校验：jsonb().$type<T>() 只是编译期断言。数据库里的脏 JSON 会直接以错误类型进入代码。需要校验请在边界处用 zod parse。
  • 自引用表需要 AnyPgColumn 标注：不加会报 circular reference 编译错误。自引用的 relations 还必须加 relationName 配对，否则 Drizzle 无法区分 parent 和 children 方向。
  • pgEnum 的值改动 diff 处理不好：drizzle-kit 对 ALTER TYPE ADD VALUE 的支持有限，删除枚举值更是无法自动生成。枚举变更建议手写迁移 SQL。
  • 第三个参数的返回形式有版本差异：0.30 之前返回对象，之后返回数组。混用会导致索引没被生成，且不报错。
  • 多 schema 需要配 schemaFilter：drizzle.config.ts 不配 schemaFilter 的话，drizzle-kit 只扫 public schema，其他 schema 的表变更不会进迁移文件。
  • $onUpdate 不是数据库触发器：它只在通过 Drizzle 的 update() 时生效。直接跑 SQL 或用其他客户端改数据，updatedAt 不会变。需要强保证请用数据库触发器。
  • .unique() 对 NULL 无效：PostgreSQL 里多个 NULL 不算重复，唯一约束不会阻止插入多行 NULL。需要唯一必须同时 .notNull()。
  • 列名 key 与字符串不一致时容易写错：db 报「column does not exist」时先检查 pgTable 里的字符串参数是否与真实列名一致，而不是检查 TS 属性名。
