查询构建：关系查询、join 与事务

🏷️ Drizzle 查询

Drizzle 的查询构建器几乎是 SQL 的逐词映射。这带来一个实际好处：你不需要在脑子里维护「ORM 语法 → SQL」的翻译表；但也带来一个认知陷阱——join 的返回形状是 SQL 的形状，不是 ORM 的形状。这篇把查询构建、关系查询、原生片段、事务四块讲清。

💡
这篇怎么读
  • ① 用法：四类查询的标准写法——带可选筛选的列表查询、要嵌套形状的关系查询、要聚合统计的 join、要写多张表的事务；再给 where 能表达到哪一步、越过边界时该怎么用 sql 模板，以及先用 toSQL() 确认生成了什么的习惯。
  • ② 原理：链式方法与 SQL 关键字的逐词映射、条件构造器的九个陷阱、四种 join 的返回形状为什么是扁平元组、db.query 如何用一条 SQL 拿到嵌套结果、sql 模板的参数化边界与 sql.raw 的注入面、offset 与游标分页的差异、事务与 savepoint 的语义、prepared statement 与连接池的冲突。
  • ③ 场景：按需求选查询方式的取舍矩阵、什么时候该放弃构建器直接写 SQL，以及不适用边界。

① 用法 · 四类查询的标准写法

日常查询几乎都能归到下面四类。先按类型选形态，再抠细节：要嵌套对象就别用 join，要聚合统计就别用 db.query，要写多表就一定进事务。每种写法背后的机制见原理层。

要做什么标准写法注意什么
列表页，筛选条件有的传有的不传and() 里用三元表达式，不满足就返回 undefinedundefined 会被自动跳过，所以不需要手动拼条件数组
返回嵌套 JSON（用户带他的文章）db.query.users.findMany({ with: { posts: ... } })初始化 drizzle() 时必须传 schema，且表要定义 relations()
聚合统计（每个作者几篇文章）leftJoin 加 groupBy 加 count()select 里的非聚合列必须全部出现在 groupBy 里
一次操作写多张表db.transaction(async (tx) => ...)，内部全部用 tx回调里误用外层 db 会走另一条连接，那条语句根本不在事务里
扣库存这类先判断再写的操作.for('update') 加锁，或直接用带条件的原子更新行锁只有在事务内才有意义；更新值用 SQL 表达式而不是先读到内存再算
翻页浅分页用 limit/offset，深分页改游标排序必须带一个唯一列做 tiebreaker，否则同值行会漏或重复
插入或更新（upsert）PostgreSQL 用 onConflictDoUpdateMySQL 是 onDuplicateKeyUpdate 且没有 returning()
确认一条查询到底生成了什么对查询对象调 toSQL() 打印 SQL 与参数评审与排查都从这一步开始，比猜快得多
 
import { db } from './db';
import { users, posts, orders, inventory } from './schema';
import { eq, and, gt, gte, lt, or, ilike, desc, count, sql } from 'drizzle-orm';

// 1) 列表查询：可选筛选 + 稳定排序 + 分页
const rows = await db
  .select({ id: posts.id, title: posts.title, createdAt: posts.createdAt })
  .from(posts)
  .where(and(
    eq(posts.status, 1),
    // 条件不满足时返回 undefined，and() 会整条跳过，不用手工拼条件数组
    keyword ? ilike(posts.title, `%${keyword}%`) : undefined,
    authorId ? eq(posts.authorId, authorId) : undefined,
  ))
  // 第二个排序列是 tiebreaker：没有它，同一时间戳的行在翻页时会漏或重复
  .orderBy(desc(posts.createdAt), desc(posts.id))
  .limit(20);

// 2) 要嵌套形状：用 db.query，一条 SQL 返回嵌套对象，不是 N+1
const withPosts = await db.query.users.findMany({
  columns: { id: true, displayName: true },
  with: {
    posts: {
      columns: { id: true, title: true },
      orderBy: (p, { desc }) => desc(p.createdAt),
      limit: 5,          // 这个 limit 是「每个用户取几篇」
    },
  },
  limit: 20,             // 这个 limit 是「取几个用户」，两者语义不同
});

// 3) 要聚合统计：用 join，接受扁平结果
const stat = await db
  .select({ author: users.displayName, total: count(posts.id) })
  .from(users)
  .leftJoin(posts, eq(posts.authorId, users.id))
  .groupBy(users.id, users.displayName)   // 非聚合列一个都不能漏
  .having(gt(count(posts.id), 0));

// 4) 写多张表：事务内所有语句都必须用 tx
const created = await db.transaction(async (tx) => {
  const [order] = await tx
    .insert(orders)
    .values({ userId, totalAmount: '199.00' })   // numeric 列用字符串，避免浮点误差
    .returning();

  // 行锁只在事务内有意义，锁持有到提交
  const [stock] = await tx
    .select()
    .from(inventory)
    .where(eq(inventory.sku, sku))
    .for('update');

  if (!stock || stock.quantity < qty) {
    throw new Error('库存不足');   // 抛异常即回滚，不需要手动 rollback
  }

  await tx
    .update(inventory)
    // 用 SQL 表达式做减法，而不是把值读到内存里算完再写回去
    .set({ quantity: sql`${inventory.quantity} - ${qty}` })
    .where(eq(inventory.sku, sku));

  return order;
});

① 用法 · where 能表达到哪一步，越界了怎么写

构建器不是万能的，判断标准很简单：值能参数化的，用构建器；结构性的东西（列名、函数、窗口、CTE），用 sql 模板。下表是这条线的具体位置。

需求构建器能表达吗怎么写边界在哪
等值、范围、IN、模糊、判空能eq、gte、inArray、ilike、isNulleq(col, null) 不等于 isNull；inArray 传空数组会得到恒假条件
可选条件、条件分组能三元表达式返回 undefined，and 与 or 自动加括号不要自己拼字符串，括号漏了语义就变了
聚合与 having能count、sum 加 havinghaving 只作用于聚合结果，普通列条件要放 where
窗口函数不能sql<number>`row_number() over (...)`不写泛型时推导成 unknown，会把 unknown 一路传到调用方
方言特有操作符（JSONB 包含、全文检索、数组）部分方言辅助函数或 sql 模板这些片段换数据库就不可移植，要集中放在一层里
动态列名、动态排序字段不能参数化白名单映射到列对象再传给 orderBy标识符无法用占位符，sql.raw 拼接等于把注入面直接暴露出来
CTE 与递归查询有限db.$with(...)，复杂递归直接 db.execute(sql`...`)硬套构建器写递归会比手写 SQL 更难读，这时候就该直接写 SQL
批量写入与 upsert能values([...]) 一次插多行，冲突用 onConflictDoUpdate单条语句的参数个数有驱动上限，超大批量要自己切片
 
// 写之前先确认它生成了什么：任何查询对象都能打印 SQL 与参数
const q = db.select().from(posts).where(eq(posts.authorId, authorId));
console.log(q.toSQL());
// { sql: 'select ... where "posts"."author_id" = $1', params: [authorId] }

// 构建器表达不了的部分用 sql 模板：值走 ${} 插值会变成占位符参数，是安全的
const ranked = await db
  .select({
    id: posts.id,
    // 泛型只声明返回类型，必须写，否则下游全是 unknown
    rank: sql<number>`row_number() over (
      partition by ${posts.authorId} order by ${posts.createdAt} desc
    )`.as('rank'),
  })
  .from(posts);

// 动态排序字段：标识符不能参数化，唯一安全做法是白名单映射到列对象
const SORTABLE = { createdAt: posts.createdAt, title: posts.title } as const;
function orderByField(field: string) {
  const col = SORTABLE[field as keyof typeof SORTABLE];
  if (!col) throw new Error('invalid sort field');   // 不在白名单直接拒绝
  return desc(col);
}
// 绝对不要写 sql.raw(`order by ${field}`)：它完全绕过参数化

② 原理 · select 链与 SQL 的一对一映射

搞清这一节能解决「这段链式调用最终跑的是哪条 SQL」。

Drizzle 的链式方法名和调用顺序几乎就是 SQL 关键字的顺序。理解这个映射之后，写 Drizzle 查询等于写 SQL。

Drizzle 方法对应 SQL注意点
.select()SELECT *不传参数选全部列；传对象则只选指定列并可重命名
.select({ a: t.col })SELECT col AS a返回类型随之收窄，这是部分选择的类型安全来源
.from(table)FROM table必须紧跟 select
.where(cond)WHERE cond多次调用会覆盖而不是叠加，要叠加用 and()
.groupBy(cols)GROUP BYselect 里的非聚合列必须都在 groupBy 中
.having(cond)HAVING作用于聚合结果，不能用普通列条件
.orderBy(asc(c), desc(c))ORDER BY c ASC, c DESC不指定方向默认 ASC
.limit(n).offset(m)LIMIT n OFFSET m大 offset 性能坍塌，见分页一节
.for('update')FOR UPDATE行锁，必须在事务里才有意义
.returning()RETURNING *PG 和 SQLite 支持，MySQL 不支持
 
import { db } from './db';
import { users, posts, orders } from './schema';
import {
  eq, ne, gt, gte, lt, lte, like, ilike, inArray, notInArray,
  isNull, isNotNull, between, and, or, not, desc, asc, sql, count, sum,
} from 'drizzle-orm';

// 1. 最基础：等价于 SELECT * FROM users WHERE is_active = true
const activeUsers = await db.select().from(users).where(eq(users.isActive, true));

// 2. 部分选择 + 重命名：返回类型自动收窄为 { id, mail }
const mails = await db
  .select({ id: users.id, mail: users.email })
  .from(users);

// 3. 组合条件：and / or 可嵌套，undefined 会被自动忽略
//    这一点让「可选筛选条件」的写法非常干净
const role: string | undefined = undefined;
const keyword = '张';
const filtered = await db
  .select()
  .from(users)
  .where(and(
    eq(users.isActive, true),
    role ? eq(users.role, role) : undefined,      // undefined 被跳过
    keyword ? ilike(users.displayName, `%${keyword}%`) : undefined,
    inArray(users.role, ['admin', 'editor']),
    gte(users.createdAt, new Date('2026-01-01')),
  ))
  .orderBy(desc(users.createdAt))
  .limit(50);

// 4. 聚合 + 分组：count/sum 是 Drizzle 提供的聚合辅助函数
const perRole = await db
  .select({
    role: users.role,
    total: count(users.id),                        // 推导为 number
    avgAge: sql<number>`avg(${users.age})::float`, // 自定义聚合需标注类型
  })
  .from(users)
  .groupBy(users.role)
  .having(gt(count(users.id), 5));

② 原理 · 条件构造器全表

搞清这一节能解决「条件写了但没起作用」和「查出来的结果莫名少了一批行」。

条件构造器是纯函数，返回一个 SQL 片段对象。它们可以自由组合、提取成变量、放进数组，这让复杂筛选逻辑很容易拆分。

构造器生成的 SQL陷阱
eq(col, v)col = $1v 为 null 时生成 col = NULL，永远为假；判空要用 isNull
inArray(col, arr)col IN ($1, $2, ...)空数组生成 false 条件而不是报错；超过 1000 个元素部分驱动会报错
like / ilikeLIKE / ILIKE前缀通配 %x 无法用 btree 索引，需要 trigram 或全文索引
between(col, a, b)col BETWEEN a AND b闭区间，时间范围查询容易多算一天
isNull / isNotNullIS NULL / IS NOT NULL唯一正确的判空方式
and(...) / or(...)AND / OR 并自动加括号undefined 参数被忽略，这是可选条件的标准写法
not(cond)NOT (cond)NOT 与 NULL 组合会产生三值逻辑意外
exists(subquery)EXISTS (...)通常比 IN 子查询更快，因为可以短路
arrayContains(col, v)col @> ARRAY[...]仅 PostgreSQL；需要 GIN 索引才快

② 原理 · join 的四种形态与返回形状

搞清这一节能解决「明明只有 20 个用户，为什么返回了 60 行」。

这是从其他 ORM 转过来最容易踩的坑。Drizzle 的 join 返回扁平的元组结构，不是嵌套对象。

具体来说，db.select().from(users).leftJoin(posts, ...) 返回的每一行是 { users: {...}, posts: {...} | null }——按表名分组的两个对象。它不会把一对多关系聚合成 { ...user, posts: [...] }。如果一个用户有 3 篇文章，你会得到 3 行，每行都重复该用户的数据。这正是 SQL JOIN 的原生行为。

flowchart TB A["db.select().from(users).leftJoin(posts)"] --> B["SQL: SELECT ... FROM users LEFT JOIN posts"] B --> C["数据库返回扁平行集"] C --> D["用户A 文章1"] C --> E["用户A 文章2"] C --> F["用户B 文章3"] D --> G["Drizzle 按表名分组"] E --> G F --> G G --> H["结果: 三行元组
每行 users 对象 + posts 对象
用户A 数据重复两次"] H --> I{"需要嵌套形状？"} I -->|是| J["改用 db.query 的 with 嵌套"] I -->|否| K["手动 reduce 聚合"]
join 形态SQL右表对象的类型典型用途
.innerJoin(t, on)INNER JOIN不为 null只要两边都有匹配的行
.leftJoin(t, on)LEFT JOIN可能为 null保留左表全部，右表可缺失
.rightJoin(t, on)RIGHT JOIN左表对象可能为 null少用，通常调换表顺序改成 leftJoin
.fullJoin(t, on)FULL OUTER JOIN两边都可能为 null数据对账、找两边的差集
 
import { alias } from 'drizzle-orm/pg-core';

// join 返回扁平元组：类型是 { users: User; posts: Post | null }[]
const rows = await db
  .select()
  .from(users)
  .leftJoin(posts, eq(posts.authorId, users.id))
  .where(eq(users.isActive, true));

// rows[0].users.displayName / rows[0].posts?.title
// 注意：一个用户有 3 篇文章就会出现 3 行，users 数据重复

// 如果真的需要嵌套形状，手动聚合（或直接用 db.query）
const grouped = rows.reduce<Map<string, { user: typeof users.$inferSelect; posts: string[] }>>(
  (acc, row) => {
    const entry = acc.get(row.users.id) ?? { user: row.users, posts: [] };
    if (row.posts) entry.posts.push(row.posts.title);
    acc.set(row.users.id, entry);
    return acc;
  },
  new Map(),
);

// 自连接必须用 alias 起别名，否则 SQL 里表名冲突
const manager = alias(users, 'manager');
const withManager = await db
  .select({
    employee: users.displayName,
    managerName: manager.displayName,
  })
  .from(users)
  .leftJoin(manager, eq(users.managerId, manager.id));

// 多表 join：链式继续加，on 条件里可引用任意已加入的表
const detail = await db
  .select({
    orderId: orders.id,
    buyer: users.displayName,
    itemTitle: posts.title,
  })
  .from(orders)
  .innerJoin(users, eq(orders.userId, users.id))
  .leftJoin(posts, eq(orders.postId, posts.id))
  .where(gte(orders.createdAt, new Date('2026-09-01')));

② 原理 · query API：嵌套结果但没有 N+1

搞清这一节能解决「要嵌套 JSON 又不想在循环里查子表」。

db.query 是 Drizzle 的关系查询 API，它需要初始化时传入 schema 且表定义了 relations()。它的价值在于：返回嵌套的对象结构，但生成的是单条带 json 聚合的 SQL，不是 N+1。

PostgreSQL 下它用 json_agg 配合 lateral join，在数据库内部就把一对多聚合成 JSON 数组，一次往返返回完整嵌套数据。这是它相比手写 join 的核心优势：你既拿到了 ORM 风格的结果形状，又没有付出 N+1 的代价，也不用手动 reduce。

方案往返次数结果形状SQL 可控性适用场景
手写 leftJoin1 次扁平元组，需手动聚合完全可控需要精确控制 SQL、做聚合统计
db.query 的 with1 次嵌套对象，自动聚合Drizzle 生成，可用 toSQL 查看读取树形数据、API 返回嵌套 JSON
循环里逐个查子表1 + N 次嵌套对象完全可控反模式，不要用
先查主表再 inArray 批量查子表2 次需手动 map完全可控子表数据量大、需要分别缓存时
 
// db.query：嵌套查询，单条 SQL
const usersWithPosts = await db.query.users.findMany({
  // columns 控制主表选哪些列（等价于 select 的部分选择）
  columns: { id: true, email: true, displayName: true },
  where: (u, { eq, and, gte }) => and(
    eq(u.isActive, true),
    gte(u.createdAt, new Date('2026-01-01')),
  ),
  // with 控制嵌套关系，可多层嵌套
  with: {
    posts: {
      columns: { id: true, title: true, createdAt: true },
      where: (p, { isNull }) => isNull(p.deletedAt),
      orderBy: (p, { desc }) => desc(p.createdAt),
      limit: 5,                 // 每个用户只取最新 5 篇
      with: {
        tags: { with: { tag: { columns: { name: true } } } },  // 三层嵌套
      },
    },
  },
  orderBy: (u, { desc }) => desc(u.createdAt),
  limit: 20,
});
// 结果形状：[{ id, email, displayName, posts: [{ id, title, tags: [...] }] }]
// 生成的是一条 SQL，可以打印验证没有 N+1：
// console.log(db.query.users.findMany({ with: { posts: true } }).toSQL());

// findFirst 拿单条，找不到返回 undefined 而不是抛错
const one = await db.query.users.findFirst({
  where: (u, { eq }) => eq(u.email, 'a@b.com'),
  with: { posts: true },
});

// 注意：with 里的 limit 是「每个父记录的子记录数」

② 原理 · sql 模板：原生片段与注入防护

搞清这一节能解决「哪种写法是参数化的、哪种直接把注入面暴露出去」。

查询构建器覆盖不了的场景（窗口函数、数据库特有函数、复杂表达式）用 sql 模板。模板插值 ${} 会被转成占位符参数，是安全的；但 sql.raw() 完全绕过参数化，绝不能传用户输入。

写法是否参数化安全性用途
sql`age > ${n}`是，转成 $1安全值插值的标准写法
sql`${users.age} > 18`列引用转成标识符安全引用表列，自动加引号和表前缀
sql.raw(`age > ${n}`)否，直接拼接注入风险只用于完全可信的常量
sql.identifier(name)转义标识符较安全但仍需白名单动态表名列名
sql.join(parts, sep)各片段保持参数化安全动态拼接多个条件片段
 
// 正确：值用模板插值，Drizzle 转成 $1 占位符
const minAge = 18;
const ok = await db
  .select()
  .from(users)
  .where(sql`${users.age} > ${minAge}`);
// 生成: WHERE "users"."age" > $1   参数: [18]

// 错误：sql.raw 拼接用户输入 —— SQL 注入
// const userInput = req.query.age;  // 可能是 "0 OR 1=1--"
// await db.select().from(users).where(sql.raw(`age > ${userInput}`));
// 生成: WHERE age > 0 OR 1=1--     全表泄露
// 参数化的边界与绕过方式详见站内 SQL 注入篇

// 窗口函数：构建器不支持，用 sql 模板并标注返回类型
const ranked = await db
  .select({
    id: posts.id,
    title: posts.title,
    authorId: posts.authorId,
    rowNum: sql<number>`row_number() over (
      partition by ${posts.authorId} order by ${posts.createdAt} desc
    )`.as('row_num'),
  })
  .from(posts);

// 动态排序字段：标识符无法参数化，必须白名单
const SORTABLE = { createdAt: posts.createdAt, title: posts.title } as const;
function safeOrderBy(field: string) {
  const col = SORTABLE[field as keyof typeof SORTABLE];
  if (!col) throw new Error('invalid sort field');   // 白名单校验
  return desc(col);
}

// upsert：PG 的 ON CONFLICT
await db
  .insert(users)
  .values({ email: 'a@b.com', displayName: '张三' })
  .onConflictDoUpdate({
    target: users.email,
    set: { displayName: '张三', updatedAt: new Date() },
    // where 可以加条件更新，避免无意义的写放大
    setWhere: sql`${users.displayName} is distinct from '张三'`,
  });

② 原理 · 分页：offset 与游标

搞清这一节能解决「翻到后面越来越慢」和「翻页时有的行看两遍、有的行没见过」。

limit + offset 在大 offset 下会坍塌——数据库必须扫过并丢弃前 N 行，而且这部分工作不会因为有索引而消失。游标分页（keyset pagination）用 WHERE sort_col < last_value 代替 offset，每页都只定位一次，延迟与页码无关。

维度offset 分页游标分页
延迟随页码的变化线性增长：offset 越大，被扫过再丢弃的行越多基本不变：每页都是一次索引定位加取 N 行
深分页时的主要成本扫描并丢弃前面所有行，页码越深越贵无额外成本，代价只在必须有合适的索引
能否跳到任意页可以不能，只能上一页下一页
翻页期间有数据插入或删除结果会重复或漏行，因为偏移量的含义变了结果稳定，游标锚定在具体的行值上
能否给出总页数可以，但 count 本身在大表上也慢通常不提供，改成「还有更多」
索引要求无特殊要求排序列必须有索引，且要带唯一列做 tiebreaker
具体数值别抄别人的毫秒数：差距取决于表宽度、索引、缓存命中与页码，要用就在自己库上对同一条 SQL 实测
 
// offset 分页：简单但大 offset 慢
const page = 3, pageSize = 20;
const offsetPage = await db
  .select()
  .from(posts)
  .orderBy(desc(posts.createdAt))
  .limit(pageSize)
  .offset((page - 1) * pageSize);

// 游标分页：用上一页最后一行的排序值作为起点
// 必须带一个唯一列做 tiebreaker，否则相同时间戳的行会漏或重复
async function cursorPage(cursor?: { createdAt: Date; id: string }) {
  return db
    .select()
    .from(posts)
    .where(
      cursor
        ? or(
            lt(posts.createdAt, cursor.createdAt),
            and(eq(posts.createdAt, cursor.createdAt), lt(posts.id, cursor.id)),
          )
        : undefined,
    )
    .orderBy(desc(posts.createdAt), desc(posts.id))   // 与 where 的列顺序一致
    .limit(20);
}
// 需要 (created_at DESC, id DESC) 的复合索引才能走索引扫描
// 游标的对外编码方式（base64 opaque cursor）详见站内 API 设计篇

② 原理 · 事务、savepoint 与 prepared statement

搞清这一节能解决「事务里明明抛了异常，数据却还在」这个最隐蔽的一类 bug。

db.transaction(cb) 的回调收到一个 tx 对象。回调里必须用 tx 而不是外层的 db——用 db 的语句会从连接池取另一条连接，完全不在这个事务里。这是最隐蔽的事务 bug。

回调抛异常即回滚，正常返回即提交。嵌套 tx.transaction() 不会开新事务，而是创建 savepoint：内层失败只回滚到 savepoint，外层可以继续。

stateDiagram-v2 [*] --> Begin: db.transaction 开始 Begin --> Stmt1: tx.insert 成功 Stmt1 --> Savepoint: tx.transaction 嵌套 Savepoint --> InnerOk: 内层语句成功 Savepoint --> InnerFail: 内层抛异常 InnerFail --> RollbackToSP: ROLLBACK TO SAVEPOINT RollbackToSP --> Stmt2: 外层捕获后继续 InnerOk --> ReleaseSP: RELEASE SAVEPOINT ReleaseSP --> Stmt2 Stmt2 --> Commit: 回调正常返回 Stmt2 --> Rollback: 回调抛异常 Commit --> [*] Rollback --> [*] note right of Begin 回调里用 db 而不是 tx 语句会走另一条连接 不在事务内 end note 
// 事务：回调里所有语句必须用 tx
const result = await db.transaction(async (tx) => {
  const [order] = await tx
    .insert(orders)
    .values({ userId, totalAmount: '199.00' })
    .returning();

  // 行锁：必须在事务内才有意义，锁到提交才释放
  const [stock] = await tx
    .select()
    .from(inventory)
    .where(eq(inventory.sku, sku))
    .for('update');                 // SELECT ... FOR UPDATE

  if (!stock || stock.quantity < qty) {
    throw new Error('库存不足');     // 抛异常即回滚整个事务
  }

  await tx
    .update(inventory)
    .set({ quantity: sql`${inventory.quantity} - ${qty}` })
    .where(eq(inventory.sku, sku));

  // 嵌套事务 = savepoint：内层失败不影响外层
  try {
    await tx.transaction(async (sp) => {
      await sp.insert(auditLog).values({ orderId: order.id, action: 'created' });
      throw new Error('审计日志写失败');
    });
  } catch {
    // 只回滚到 savepoint，order 和库存扣减仍然有效
  }

  return order;
}, {
  isolationLevel: 'repeatable read',   // 默认 read committed
  // accessMode: 'read write',
  // deferrable: false,
});

// prepared statement：高频固定查询的复用
// placeholder 声明参数位，prepare 时命名，execute 时传值
import { sql } from 'drizzle-orm';
const findByEmail = db
  .select()
  .from(users)
  .where(eq(users.email, sql.placeholder('email')))
  .prepare('find_user_by_email');

const u1 = await findByEmail.execute({ email: 'a@b.com' });
const u2 = await findByEmail.execute({ email: 'c@d.com' });  // 复用计划
// 注意：连接池里不同连接的 prepared statement 不共享
// 用 PgBouncer 的 transaction pooling 模式会让 prepared statement 失效

③ 场景 · 查询方式怎么选

同一份数据有好几种取法，区别不在「能不能取到」，而在往返次数、结果形状、SQL 可控性三者的权衡。下表按真实需求排开。

场景该怎么做为什么代价
接口要返回嵌套 JSON（详情页、树形数据）db.query 的 with 嵌套一次往返拿到嵌套结果，不需要手动聚合，也不是 N+1SQL 由 Drizzle 生成，要靠 toSQL() 才看得到；复杂过滤表达力不如手写
报表、统计、分组聚合手写 join 加 groupBy聚合与分组必须精确控制 SQL，嵌套结果反而是负担返回扁平元组，展示层要自己整形
子表数据量大、或子表要单独缓存先查主表，再用 inArray 批量查子表，在应用层拼两次往返换来两份可独立缓存、独立限流的数据多一次往返，拼装逻辑要自己写且要注意顺序
在循环里按需查子表不要这么做这就是 N+1，往返次数随结果集线性增长压测时看起来还行，数据一多就把数据库连接占满
窗口函数、递归 CTE、方言特有操作符sql 模板，或整条 db.execute(sql`...`)硬套构建器写这些会比手写 SQL 更难读也更易错这些片段不可移植，要集中放在一个模块里，换库时只改这一处
用户可选排序字段白名单映射到列对象标识符无法参数化，白名单是唯一安全做法新增可排序字段要改代码，不能配置化
深分页（导出、爬取、无限滚动）游标分页，排序列加唯一 tiebreaker延迟与页码无关，且翻页期间数据变动不会漏行重行不能跳页、通常不给总数，产品形态要配合
高频固定查询（登录、鉴权这类）prepare() 复用预编译语句省掉每次的解析与规划开销与某些连接池的事务级复用模式冲突，用之前先确认部署形态
先判断再写的并发操作（扣库存、抢券）带条件的原子更新并检查影响行数，或 for('update') 加锁「先查再写」在并发下两个请求都会通过判断行锁会串行化同一行的写入，锁持有时间必须尽量短

不适用边界：本篇只讲怎么用 Drizzle 把查询写对。表和类型怎么定义在上一篇 Drizzle 上手：schema 定义与类型推导；迁移怎么生成与在生产怎么应用在下一篇 迁移管理：生成、应用与生产流程；该不该用 Drizzle 在 Drizzle 的设计：SQL-first 的类型安全 ORM；sql.raw 的注入面、参数化的真实边界与绕过手法在 SQL 注入；这条查询为什么走不上索引、执行计划怎么判读在 索引设计与优化 与 慢查询治理；隔离级别、行锁范围与 MVCC 可见性在 PostgreSQL MVCC 与事务（MySQL 侧在 MySQL 深度原理）；游标对外怎么编码、分页接口怎么设计在 RESTful 接口设计；跨服务的事务与幂等不在本篇范围，见站内分布式事务相关文章。

这条路径上，上一篇把结构与类型定好，本篇把读写写对，下一篇解决「schema 改了之后怎么安全地让生产库跟上」。

最容易踩的坑

❌
前两条最常见，且都不会报错
  • join 返回扁平元组不是嵌套对象：leftJoin 后每行是 { users: {...}, posts: {...} }，一对多会产生重复行。需要嵌套形状用 db.query 的 with，不要指望 join 自动聚合。
  • 事务回调里误用外层 db：必须用 tx。用 db 的语句从连接池取另一条连接，不在事务内，失败也不会回滚。这个 bug 在测试里很难发现。
  • 多次 .where() 是覆盖不是叠加：链式调用两次 where，第二次会替换第一次。要叠加条件必须用 and() 包起来。
  • inArray 传空数组：Drizzle 会生成一个恒假条件，查询返回空结果而不是报错。业务上如果空数组应该表示「不过滤」，必须自己判断。
  • eq(col, null) 不等于 isNull：SQL 里 col = NULL 永远是 unknown 不是 true。判空只能用 isNull / isNotNull。
  • sql.raw 拼接用户输入：完全绕过参数化，直接 SQL 注入。值永远用 ${} 模板插值；标识符必须走白名单。
  • sql 模板没标注返回类型：sql`...` 默认推导为 unknown，需要 sql<number>`...` 显式标注，否则下游类型全是 unknown。
  • db.query 的 with 里的 limit 语义：它限制的是每个父记录的子记录数，不是总数。与外层 limit 混淆会拿到意外的数据量。
  • 游标分页缺少 tiebreaker：只按 createdAt 做游标，相同时间戳的行会被跳过或重复。必须加一个唯一列（通常是主键）做次级排序。
  • 大 offset 分页：offset 很大时数据库要先扫过并丢弃前面所有行，延迟随页码线性增长，且加索引也去不掉这部分工作。深分页场景必须换游标。
  • PgBouncer 与 prepared statement 冲突：transaction pooling 模式下连接会在语句间切换，prepared statement 失效报错。要么用 session pooling，要么关掉 prepare。
  • groupBy 漏列：select 里的非聚合列必须全部出现在 groupBy 中，PostgreSQL 会直接报错（MySQL 在非严格模式下静默返回任意值，更危险）。
  • returning() 在 MySQL 不可用：MySQL 不支持 RETURNING，insert 后需要单独查一次或用 insertId。代码在 PG 上跑通换到 MySQL 会报错。
