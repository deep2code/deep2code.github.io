迁移管理：生成、应用与生产流程

🏷️ Drizzle 迁移

迁移是 ORM 里唯一会不可逆地毁掉生产数据的环节。查询写错了最多报错，迁移写错了列就没了。这篇讲清 drizzle-kit 的工作机制、危险变更的识别、以及生产环境应该怎么组织迁移流程。

drizzle-kit 的三条路径

drizzle-kit 提供三种让数据库和 schema 对齐的方式，它们的适用边界差别很大：

命令做什么留下 SQL 文件可审查可重放适用阶段
generate对比 schema 与上次快照，生成 SQL 文件是是是生产唯一正确选择
migrate读取 SQL 文件并按顺序执行未应用的迁移不产生，只执行——生产部署
push直连数据库对比并即时执行 ALTER否否否只适合本地原型
pull从现有数据库反向生成 TS schema生成 schema 文件是—接管遗留数据库
check检查迁移文件之间是否有冲突———CI 里做前置校验
up升级旧版本的迁移元数据格式改写 snapshot——drizzle-kit 大版本升级时

为什么生产绝不能用 push：push 的执行过程没有任何产物。你不知道它执行了什么 SQL，code review 里看不到 DDL 变更，出问题时无法追溯，不同环境可能执行出不同结果（因为 push 依赖当前数据库的实际状态）。更危险的是 push 遇到歧义变更（比如列重命名）时会交互式询问，在 CI 里就会卡住或选错。

generate 的工作原理与产物

generate 不是对比 schema 和数据库，而是对比当前 schema 与上一次的 JSON 快照。快照存在 drizzle/meta/ 目录下，每次 generate 会生成一个新快照和一个 SQL 文件。这个设计意味着：快照文件必须和 SQL 文件一起提交，否则下次 generate 会重新生成已有的变更。

# 1. 生成迁移（对比 schema 与上次快照）
npx drizzle-kit generate --name add_user_role
# 产物：
#   drizzle/0003_add_user_role.sql          实际执行的 DDL
#   drizzle/meta/0003_snapshot.json         本次 schema 快照
#   drizzle/meta/_journal.json              迁移清单与时间戳

# 2. 审查生成的 SQL —— 这一步绝不能跳过
cat drizzle/0003_add_user_role.sql

# 3. 检查迁移之间是否有冲突（多人并行开发时必跑）
npx drizzle-kit check

# 4. 应用迁移（生产用独立步骤，不要放在应用启动里）
npx drizzle-kit migrate

# 5. 查看数据库当前已应用的迁移
psql "$DATABASE_URL" -c \
  'SELECT id, hash, created_at FROM drizzle.__drizzle_migrations ORDER BY created_at;'

# 排查：schema 和数据库不一致时，用 pull 导出真实结构做对比
npx drizzle-kit pull --out ./tmp-introspect
# 然后 diff ./tmp-introspect/schema.ts 与你的 src/schema/
# 这能发现「有人手动改了生产库」这类漂移问题
文件作用必须提交 git丢失的后果
drizzle/NNNN_name.sql实际执行的 DDL必须无法在其他环境重放结构变更
drizzle/meta/NNNN_snapshot.json该版本的 schema 快照必须下次 generate 会重复生成已有变更
drizzle/meta/_journal.json迁移清单与顺序必须migrate 不知道该执行哪些文件
__drizzle_migrations 表数据库侧的已应用记录（含哈希）在数据库里迁移会被重复执行导致报错

危险变更识别清单

这是这篇最重要的一节。diff 工具只对比结构，不判断业务影响。以下变更 drizzle-kit 会老老实实生成 SQL，但执行后可能丢数据或锁表。

schema 变更生成的 DDL风险安全做法
删除一列ALTER TABLE DROP COLUMN数据永久丢失；仍在读该列的老版本代码直接报错先发布不读该列的代码，观察一到两周，再删列
改列类型（text 到 integer）ALTER COLUMN TYPE ... USING无法转换的值导致迁移失败；能转换但精度丢失更危险加新列、双写、回填校验、切读、删老列
给已有数据的列加 NOT NULLALTER COLUMN SET NOT NULL存在 NULL 行时迁移失败；大表全表扫描持锁先回填 NULL 值，再加约束，分两个迁移
新增 NOT NULL 列无默认值ADD COLUMN NOT NULL表非空时直接失败加 nullable 列 → 回填 → 加约束，三步
重命名列drizzle-kit 会询问是 rename 还是 drop+add选错就是删列建列，数据全丢交互式确认时看清；CI 里绝不能跑交互式命令
缩短 varchar 长度ALTER COLUMN TYPE varchar(n)超长数据导致迁移失败先查最大长度，确认无超长数据
加唯一约束ADD CONSTRAINT UNIQUE已有重复数据导致失败；建索引期间持锁先查重清理，PG 用 CREATE UNIQUE INDEX CONCURRENTLY
加索引（大表）CREATE INDEXPG 默认持 SHARE 锁阻塞写；MySQL 5.6+ 在线但仍有开销PG 改成 CREATE INDEX CONCURRENTLY（不能在事务里）
加外键ADD CONSTRAINT FOREIGN KEY校验现有数据时全表扫描并持锁；孤儿行导致失败先 NOT VALID 加约束，再单独 VALIDATE CONSTRAINT
修改枚举值ALTER TYPE / drizzle-kit 支持有限删除枚举值在 PG 里根本不支持手写迁移；或用 text + CHECK 约束替代 enum
❌
审查清单：每个生成的 SQL 文件必须过一遍

有没有 DROP COLUMN 或 DROP TABLE？有没有 ALTER COLUMN TYPE？有没有 SET NOT NULL？有没有在大表上 CREATE INDEX 而没加 CONCURRENTLY？有没有 ADD CONSTRAINT FOREIGN KEY 而没先 NOT VALID？有没有在一个迁移里混了 DDL 和大批量 UPDATE（会长时间持锁）？重命名是真 rename 还是 drop 加 add？以上任一为是，就不能直接合并。

与 expand-migrate-contract 的配合

安全的结构演进遵循三阶段模式：先扩展（expand）让新旧代码都能工作，再迁移数据和流量（migrate），最后收缩（contract）删掉旧结构。每个阶段都是独立的部署，中间有观察期。

stateDiagram-v2 [*] --> Expand: 阶段一 扩展 Expand --> ExpandDeploy: 加 nullable 新列
不删不改任何旧结构 ExpandDeploy --> DualWrite: 部署双写代码
新旧列同时写 DualWrite --> Backfill: 阶段二 迁移 Backfill --> Verify: 批量回填历史数据
分批提交避免长事务 Verify --> SwitchRead: 校验新旧列一致性 SwitchRead --> Observe: 切换读取到新列 Observe --> Contract: 观察一到两周 Contract --> DropOld: 阶段三 收缩 DropOld --> AddConstraint: 停止写旧列并删除 AddConstraint --> [*]: 给新列加 NOT NULL note right of Expand 每个阶段是独立的迁移文件 和独立的部署 end note note right of Observe 观察期内可以随时回滚代码 因为旧列还在 end note
阶段迁移内容代码变更可回滚性
Expand 1ADD COLUMN new_col（nullable）无完全可回滚（删列即可）
Expand 2无双写 old_col 和 new_col完全可回滚（回退代码）
Migrate 1分批 UPDATE 回填 new_col无可回滚（new_col 无人读）
Migrate 2无读取切到 new_col可回滚（old_col 仍在写）
Contract 1无停止写 old_col可回滚（数据尚未删）
Contract 2SET NOT NULL + DROP old_col无不可回滚

回填的关键是分批提交。一条 UPDATE posts SET new_col = old_col 在百万行表上会产生巨大的事务、大量 WAL、以及长时间的行锁。正确做法是按主键范围分批，每批几千行，批间 sleep。schema 演进的完整模式与兼容性策略详见站内模式演进篇。

-- Expand 阶段：只加 nullable 列，零风险
ALTER TABLE posts ADD COLUMN author_uuid uuid;

-- Migrate 阶段：分批回填，避免长事务和锁表
-- 在应用代码里循环调用，每批之间 sleep 100ms
UPDATE posts
SET author_uuid = u.id
FROM users u
WHERE posts.author_legacy_id = u.legacy_id
  AND posts.author_uuid IS NULL
  AND posts.id IN (
    SELECT id FROM posts
    WHERE author_uuid IS NULL
    ORDER BY id
    LIMIT 2000                    -- 每批 2000 行
    FOR UPDATE SKIP LOCKED        -- 跳过被锁行，允许并发回填
  );

-- 校验：回填完成后确认没有遗漏和不一致
SELECT count(*) AS still_null FROM posts WHERE author_uuid IS NULL;
SELECT count(*) AS mismatched
FROM posts p JOIN users u ON p.author_legacy_id = u.legacy_id
WHERE p.author_uuid IS DISTINCT FROM u.id;

-- Contract 阶段：确认无人读旧列后才执行
-- 索引用 CONCURRENTLY 避免阻塞写（注意：不能在事务块里）
CREATE INDEX CONCURRENTLY posts_author_uuid_idx ON posts (author_uuid);
-- 外键分两步：先不校验现有数据，再后台校验
ALTER TABLE posts ADD CONSTRAINT posts_author_uuid_fk
  FOREIGN KEY (author_uuid) REFERENCES users(id) NOT VALID;
ALTER TABLE posts VALIDATE CONSTRAINT posts_author_uuid_fk;
ALTER TABLE posts ALTER COLUMN author_uuid SET NOT NULL;
ALTER TABLE posts DROP COLUMN author_legacy_id;

多环境与并发部署的迁移锁

最常见的错误是把迁移写在应用启动代码里。滚动更新时 5 个 Pod 同时启动，5 个进程同时尝试执行同一个迁移，结果可能是重复执行、部分失败、或者数据库被并发 DDL 搞出死锁。

正确做法是把迁移剥离成独立的部署前置步骤，保证全局只有一个进程执行。

方案并发安全失败可见性适用场景
应用启动时跑 migrate不安全混在应用日志里难发现只适合单实例的小项目
Kubernetes Job（部署前）安全，Job 只跑一次Job 失败阻塞部署，清晰推荐，K8s 环境标准做法
initContainer不安全，每个 Pod 都跑Pod 起不来只在单副本时可用
CI/CD 流水线单独 stage安全流水线失败，最清晰推荐，任何环境通用
手动执行 + 审批安全人工确认高风险迁移、金融类系统
代码里加 advisory lock安全但复杂需自己打日志无法改部署流程时的兜底
 
// migrate.ts —— 独立的迁移脚本，不在应用启动流程里
import { drizzle } from 'drizzle-orm/postgres-js';
import { migrate } from 'drizzle-orm/postgres-js/migrator';
import postgres from 'postgres';
import { sql } from 'drizzle-orm';

async function main() {
  // 迁移连接用 max: 1，DDL 不需要连接池
  // 单连接也保证了 advisory lock 在整个迁移期间持有
  const client = postgres(process.env.DATABASE_URL!, { max: 1 });
  const db = drizzle(client);

  // 兜底的并发保护：PG advisory lock 保证全局只有一个进程在迁移
  // 常量 20260923 随便取，只要全项目一致
  const [{ locked }] = await db.execute<{ locked: boolean }>(
    sql`select pg_try_advisory_lock(20260923) as locked`,
  );
  if (!locked) {
    console.error('另一个进程正在执行迁移，退出');
    process.exit(1);
  }

  try {
    console.log('开始迁移...');
    await migrate(db, {
      migrationsFolder: './drizzle',
      migrationsTable: '__drizzle_migrations',
      migrationsSchema: 'drizzle',        // 把元数据表放独立 schema
    });
    console.log('迁移完成');
  } finally {
    await db.execute(sql`select pg_advisory_unlock(20260923)`);
    await client.end();
  }
}

main().catch((e) => {
  console.error('迁移失败:', e);
  process.exit(1);   // 非零退出码让 CI/K8s Job 感知失败并阻塞部署
});
# .github/workflows/deploy.yml —— 迁移作为独立 stage
name: deploy
on:
  push:
    branches: [main]

jobs:
  check-migrations:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: '20', cache: 'npm' }

      - run: npx drizzle-kit check
      # 校验 schema 与已有迁移一致：如果 generate 产生新文件说明有人忘了提交
      - name: 检查是否有未生成的 schema 变更

          npx drizzle-kit generate --name ci_check
          if [ -n "$(git status --porcelain drizzle/)" ]; then
            echo "schema 有变更但未生成迁移文件，请本地跑 drizzle-kit generate"
            git status --porcelain drizzle/
            exit 1
          fi

  migrate:
    needs: check-migrations
    runs-on: ubuntu-latest
    environment: production        # 走 GitHub 的审批门禁
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: '20', cache: 'npm' }
      - run: npm ci
      # 关键：迁移在应用部署之前，且只有这一个 job 执行
      - run: npx tsx migrate.ts

回滚策略：向前修复而不是回退 DDL

drizzle-kit 没有内置 down 迁移，这不是缺陷，是符合生产现实的设计。回退 DDL 在生产环境几乎总是错误的选择：

情况回退 DDL 的后果向前修复的做法
加错了一列DROP COLUMN 把已写入的数据删了写新迁移删列，但先确认无人写
删错了一列无法回退，数据已经没了只能从备份恢复，这就是为什么删列要分阶段
改错了列类型反向转换可能再次丢精度新迁移加正确类型的列并从备份回填
迁移执行到一半失败数据库处于中间状态PG 的 DDL 在事务里，整个迁移原子回滚；MySQL 8.0 之前 DDL 不可回滚，需手动清理
新代码有 bug 需要回滚版本回退结构会让新旧代码都跑不起来只回滚应用版本，保留结构（这正是 expand 阶段的价值）

核心原则：让每次结构变更都向后兼容（旧代码能在新结构上跑），这样应用版本可以独立回滚，数据库结构只需向前演进。这正是 expand-migrate-contract 的意义所在。

真正需要恢复数据时的手段是备份和 PITR（point-in-time recovery），不是 down 迁移。生产环境必须确认：备份策略是什么、PITR 窗口多长、恢复演练做过没有。删列类操作前主动打一个快照。

最容易踩的坑
  • 生产用 push：没有 SQL 文件、无法审查、无法重放、CI 里遇到歧义会卡住或选错。push 只能用于本地原型。
  • 只提交 SQL 忘了提交 meta 快照：drizzle/meta/ 下的 snapshot 和 _journal.json 必须一起提交。缺了快照，下次 generate 会把已有的变更重新生成一遍。
  • 把 migrate 写在应用启动里：滚动更新时多个实例并发执行同一迁移，可能重复执行、部分失败或 DDL 死锁。必须剥离成独立的部署前置步骤。
  • 跳过 SQL 审查：diff 工具只看结构不看业务。DROP COLUMN、ALTER TYPE、SET NOT NULL 它都会照生成，执行后数据就没了。
  • 重命名列时选错：drizzle-kit 交互式询问「这是 rename 还是 drop+add」，选错就是删列建列，数据全丢。CI 里绝不能跑交互式命令。
  • 大表上 CREATE INDEX 不加 CONCURRENTLY：PostgreSQL 默认持 SHARE 锁阻塞所有写入，百万行表能锁几十秒。但 CONCURRENTLY 不能在事务块里，需要手动改生成的 SQL。
  • 加外键不用 NOT VALID 两步走：直接 ADD CONSTRAINT 会全表扫描校验现有数据并持锁。先 NOT VALID 加约束再 VALIDATE 可以把锁时间压到最短。
  • 一次性 UPDATE 回填百万行：产生巨大事务、大量 WAL、长时间行锁，还可能触发复制延迟告警。必须按主键分批，每批几千行。
  • 把 DDL 和大批量 DML 放在同一个迁移：DDL 拿到的锁会一直持有到事务结束，混入慢 UPDATE 等于长时间锁表。拆成两个迁移。
  • 期待 down 迁移能救命：删掉的列回不来。真正的恢复手段是备份和 PITR，而防御手段是让删列走三阶段。
  • 枚举变更交给 diff 工具：drizzle-kit 对 ALTER TYPE ADD VALUE 支持有限，删除枚举值 PostgreSQL 根本不支持。枚举变更建议手写迁移，或一开始就用 text 加 CHECK 约束。
  • 多人并行开发导致迁移序号冲突：两个分支各生成 0004，合并后序号重复。CI 里必须跑 drizzle-kit check，且合并后重新生成序号。
  • 预发和生产的迁移不一致：如果预发用 push 生产用 migrate，两边结构会漂移。所有环境必须用同一套 SQL 文件。用 drizzle-kit pull 定期对比可以发现漂移。
  • MySQL 的 DDL 不可回滚：MySQL 8.0 之前 DDL 不在事务里，迁移执行到一半失败会留下中间状态，需要手动清理。PostgreSQL 的 DDL 在事务里可原子回滚，这是一个实质差异。
