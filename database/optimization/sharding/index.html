分库分表：单表千万级了怎么办

🏷️ 分库分表

单表数据量上千万了，查询越来越慢，索引都加了也没用。这时候就该分库分表了。但分库分表是个大坑，能不分就不分。

flowchart LR A[单表千万级] --> B[读写分离?] B --> C[加缓存?] C --> D[分库分表] D --> E[垂直拆分] D --> F[水平拆分]

单表数据量太大，查询慢

⚠️
你遇到的问题

一张表 1000 万行，查个数据要几秒，索引加了也没用。

怎么解决？先别急着分，先试试读写分离、加缓存、归档老数据，这些都不行再分。

# 分表前先试这些
1. 读写分离：读走从库
2. 加 Redis 缓存热点数据
3. 归档老数据：历史数据迁到归档表
4. 优化 SQL 和索引

决定分了，怎么分

⚠️
你遇到的问题

说要分库分表，结果不知道怎么分，按什么分，分几个库几个表。

怎么解决？垂直拆分按业务拆，水平拆分按某个字段（比如 user_id）哈希拆。

# 拆分方式
垂直拆分：按业务拆，用户库、订单库、商品库
水平拆分：按 user_id 哈希拆，分 8 库 64 表

分库分表方式

方式 原理 优点 缺点 适用场景
垂直拆分 按业务拆库 业务解耦 跨库 JOIN 麻烦 业务边界清晰
水平拆分 按字段哈希拆表 解决单表大 分布式事务、扩容难 单表数据量大
读写分离 主写从读 简单快 主从延迟 读多写少

新手最容易踩的坑

❌
避坑指南
  • 能不分就不分，分库分表是最后手段，拆了后面全是坑
  • 选好分片键很重要，大部分查询都要带分片键，不然要扫所有库
  • 分布式事务是最大的坑，尽量用最终一致，别搞强一致
  • 扩容是大问题，提前规划好，别等要扩了才发现要迁移所有数据
