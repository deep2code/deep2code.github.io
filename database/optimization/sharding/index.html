分库分表：决策边界、分片键选择与扩容落地

🏷️ 分库分表

分库分表是数据库优化里唯一不可逆的一步。索引建错了删掉就行，缓存加错了摘掉就行，分片一旦落地，分片键就固化进了每一条查询，跨分片能力的缺失会永久留在业务代码里，并且被之后每一个新需求继续放大。所以这篇的重点不是「怎么分」，而是「什么时候才该分」和「分了之后要付什么代价」。一句话先摆在前面：分片解决的是单机容量和写入上限，它解决不了复杂查询。

这篇怎么读

  • ② 原理：替代方案的可逆性对照、分片键为什么是最难改的决策、五种分片算法的扩容代价、把用户基因编进订单 ID 的做法与它的位数约束、分片后永久失去的八项能力、全局唯一 ID 四种方案与时钟回拨、双写加全量迁移加追平的状态机、SDK 与 Proxy 的七维差异。
  • ③ 场景：什么情况下应该直接上分布式数据库而不是自己分片、分片之后七类运维事项怎么做、以及这篇在整条优化路径里的位置与边界。

① 用法 · 动手前的三项自查：现在的瓶颈到底是什么

分片是单向门，所以第一件事不是设计分片键，而是证明你真的需要它。下面三项自查每项都有可以直接敲的取数命令，任何一项的答案是「还有余量」，这一轮就不该分。

自查项怎么确认如果答案是这样，先做这件事
瓶颈是读并发吗按下面命令取 Com_select 与 Com_insert 等写命令的速率差值（两次采样相减），算读写比读远多于写：先做读写分离加缓存，这是成本最低且完全可逆的一步
瓶颈是容量还是写吞吐看单表数据与索引体积、增长速率；再看写入速率是否已经把磁盘 IOPS 或 binlog 写入打满只是容量大而写入不高：先归档或分区，把热数据集合缩小
查询是否集中在近期数据按时间维度做分组计数，看最近一到三个月的行数占比集中在近期：归档历史数据或用分区表，可逆、风险最低
垂直拆分是否已经用尽看单库里有几块互不相关的业务表、有没有大字段（长文本、JSON、二进制）挤在主表里还能按业务边界或大字段拆：先做垂直拆分，它不需要改查询路由
SQL 与索引是否已经榨干按总耗时排序看前二十个 SQL 指纹，确认没有全表扫、深分页、N 加 1还有慢查询没治：先走 慢查询治理 与 索引治理，很多「容量问题」其实是扫描量问题
实例规格是否已到天花板对比当前规格与云厂商该系列的最高规格，看还有几档还有档位：先升配。升配完全可逆，分片不可逆
能否用分布式数据库换掉改造量评估成本预算与团队对新故障模式的接受度能接受成本与运维复杂度上升：直接上分布式数据库，省掉永久的能力缺失
 
-- 1) 体积与行数：先把「有多大」量出来，不要凭感觉
--    table_rows 是估算值，用于量级判断足够；要精确值再单独 COUNT(*)
SELECT table_name,
       table_rows,
       ROUND(data_length  / 1024 / 1024) AS data_mb,
       ROUND(index_length / 1024 / 1024) AS idx_mb
FROM information_schema.tables
WHERE table_schema = DATABASE()
ORDER BY data_length + index_length DESC
LIMIT 10;

-- 2) 读写比：分片解决的是写吞吐与容量，读高只需要读写分离加缓存
--    这些是累计值，必须隔一段时间采两次相减再除以间隔秒数才有意义
SHOW GLOBAL STATUS WHERE Variable_name IN
    ('Com_select','Com_insert','Com_update','Com_delete','Innodb_rows_inserted');

-- 3) 查询是否集中在近期：决定能否用归档或分区替代分片
SELECT DATE_FORMAT(create_time, '%Y-%m') AS ym, COUNT(*) AS rows_cnt
FROM orders
GROUP BY ym
ORDER BY ym DESC
LIMIT 12;

-- 4) 候选分片键的分布：倾斜的键不能做分片键，这一步要在决策前做
--    某个取值的占比远高于均值，就意味着分片后那一片先到顶
SELECT user_id, COUNT(*) AS cnt
FROM orders
GROUP BY user_id
ORDER BY cnt DESC
LIMIT 20;

① 用法 · 分片键检查清单与扩容的可执行步骤

三项自查都指向「必须分」之后，才轮到分片键。分片键是这套方案里唯一几乎改不回来的决策，所以它不该由讨论决定，而该由数据决定——把真实查询清单列全，逐条核对能不能带上候选键。

检查项怎么验证不通过怎么办
高频查询能否带上这个键用下面的语句按调用次数列出真实查询清单，统计「不含候选键」的那些语句的调用量占比占比超过一成就换候选键；实在换不了，必须先设计好异构索引表
会不会热点或倾斜对候选键做分组计数，看头部取值的占比；SaaS 场景重点看头部大租户倾斜就换键；只能用这个键时，对头部账号单独路由
写入会不会集中在一片如果候选键是时间或自增 ID，按范围分片时写入永远落在最后一片改成取模或哈希；确实要范围分片就接受写入集中，并按片扩容
需不需要跨片聚合列出所有 COUNT、SUM、GROUP BY、全局排序分页的入口，逐个判断能否收敛到单片不能收敛的挪到离线数仓或搜索引擎，不要留在高频接口上
是否存在第二个高频路由入口典型是「按用户查列表」与「按订单号查详情」并存用基因法把主键的低位编进第二个键，两条路径命中同一片
分片数是否一次规划够按「单片容量上限 ÷ 预估三年增量」反推，并取 2 的幂不够就直接上 32 或 64 片；预留分片几乎不增加成本，事后扩容极贵
 
-- 用真实查询清单验证候选分片键：凭印象选键是最常见的失败原因
-- has_shard_key = 0 的那些语句，分片后会退化成向所有分片扇出
SELECT LEFT(digest_text, 100)                 AS sql_template,
       count_star                             AS calls,
       digest_text LIKE '%user_id%'           AS has_shard_key
FROM performance_schema.events_statements_summary_by_digest
WHERE schema_name = DATABASE()
  AND digest_text LIKE 'SELECT%'
ORDER BY count_star DESC
LIMIT 30;

-- 判读方法：把 has_shard_key = 0 的行的 calls 累加，除以总 calls。
-- 这个比例就是分片后必须扇出的请求占比，它直接决定这个候选键能不能用。

扩容（包括第一次把单库切成分片）按下面九步走。每一步都要先确认验收标准再进下一步，并且要清楚自己当前站在哪个回滚点上：

步骤动作验收标准此刻的回滚代价
1 冻结冻结分片数与表结构变更，公告窗口期变更单里只有这一项在跑零，直接取消
2 上线双写双写开关默认关，新分片写失败只告警、不阻塞主流程灰度 1% 写流量，主流程错误率无变化零，关开关即可
3 全量迁移按主键区间分批限速拉取，进度落库以支持断点续跑线上 P99 无变化；进程重启后能从断点继续低，已迁数据可以整体丢弃重来
4 增量追平订阅 binlog 消费到新分片，直到延迟稳定延迟曲线平稳且不再单调增长低，停消费即可
5 一致性校验逐片对比行数与内容校验和（语句见原理层）两边行数与校验和完全一致低，回到第 3 步重迁差异区间
6 灰度切读按用户或分片维度放量，同时做新旧双读对比双读差异为 0，新分片延迟不高于旧分片中，切回旧分片即可，但要留意已产生的双读告警
7 全量切读读全部切到新分片，观察满一个完整业务周期覆盖月末结算、定时任务这些低频路径后无差异中，仍可整体切回读
8 切写停止写旧分片，旧分片转只读旧分片写入量归零，业务无报错这是最后一个低成本回滚点
9 下线旧分片只读保留至少一个业务周期后再下线备份已验证可恢复下线之后没有回滚路径，只能修数据

上面这些动作为什么是这个顺序、分片键选错为什么改不回来、扩容为什么是整套方案里最危险的一步，下面逐节展开。

② 原理 · 先穷尽所有替代方案

搞清这一节能解决「到底该不该分」——大多数团队真正需要的是归档、分区或读写分离，而不是分片。

② 原理 · 分片键是最关键也最难改的决策

搞清这一节能解决「上线半年后发现最高频的查询必须扇出到所有分片」这类无法补救的设计错误。

分片键的选择标准只有一条：绝大多数查询都能带上它。带不上分片键的查询会退化成向所有分片扇出再在应用层聚合，分片数越多越慢。选错之后几乎改不回来——改分片键等于把全部数据重新分布一次，同时所有查询路径重写，代价接近重做一遍分库分表。

候选分片键能精确命中单片的查询会退化成全分片扇出的查询数据分布风险
user_id我的订单列表、我的订单详情、用户维度统计按订单号查详情、商家维度查询、运营后台按时间筛选大客户或刷单账号造成单片偏大
order_id订单详情、支付回调、物流回调我的订单列表（最高频的 C 端场景直接失效）分布均匀，但热点集中在最新 ID 段（若按范围分）
时间（按月或按天）报表类的时间范围查询、按时间归档按用户或订单号的点查，必须扫全部时间分片写入永远集中在最新分片，冷分片完全空闲
tenant_id（SaaS 场景）该租户内的所有查询，天然隔离跨租户的全局统计与运营报表倾斜最严重，头部大租户可能一个就撑爆单片
user_id 加基因写入 order_id我的订单列表、按订单号查详情，两条最高频路径都命中商家维度、时间维度查询仍然要扇出与 user_id 相同，但可用的路由入口多一个

数据归属、多租户的隔离级别与分片数据模型的更细取舍，见 数据归属与多租户：分片的数据模型策略。

② 原理 · 分片算法对照与基因法

搞清这一节能解决「为什么扩容那么贵」——答案全在算法选择里，取模最省心也最难扩。

算法路由方式扩容代价热点风险适用场景
取模分片号等于键对分片数取模最高。分片数一变，几乎全部数据都要重新分布低，分布均匀一次性规划足够多分片、且不打算再改分片数
范围按键区间划分，如 ID 每一千万一片最低。加一个新区间即可，老数据不动高。写入永远落在最后一个分片写入可接受集中、以时间或自增 ID 为主键的日志类数据
一致性哈希键与分片都映射到哈希环，顺时针找归属中。扩容只影响相邻分片的部分数据需要虚拟节点才能均匀分片数会多次调整、且能接受实现复杂度
按时间按天或月建表，路由取时间字段低。新周期新建表高。热点全在最新分片，冷分片闲置账单、日志、消息、埋点这类天然冷热分离的数据
基因法取模为主，但把用户基因编进订单 ID，使两种键路由到同一片与取模相同，且基因位数受分片数约束低订单这类需要同时支持两种键查询的核心表

基因法值得单独展开，它是电商订单表的经典做法。问题背景是：订单按 user_id 分片（因为「我的订单」是最高频场景），但订单详情页是按 order_id 查的，而 order_id 里不含用户信息，只能扇出到所有分片。基因法在生成 order_id 时，把 user_id 的低几位直接写进 order_id 的低位，这几位就是「基因」。

/**
 * 基因法订单 ID 生成与路由。
 * 核心约束：分片数必须是 2 的幂，基因位数等于 log2(分片数)。
 * 这个约束意味着分片数要提前规划好，后续改分片数会让基因位数失配。
 */
public final class OrderSharding {

    private static final int SHARD_COUNT = 64;                // 一次规划够，不要只分 4 片
    private static final int GENE_BITS   = 6;                 // 2 的 6 次方等于 64
    private static final long GENE_MASK  = SHARD_COUNT - 1;   // 低 6 位全 1

    private final SnowflakeIdGenerator snowflake;             // 任意全局唯一 ID 生成器

    public OrderSharding(SnowflakeIdGenerator snowflake) {
        this.snowflake = snowflake;
    }

    /** 生成订单 ID：高位是全局唯一序列，低 6 位塞进用户基因 */
    public long nextOrderId(long userId) {
        long seq  = snowflake.nextId();
        long gene = userId & GENE_MASK;
        // 左移腾出低 6 位再写入基因；注意 seq 左移后位宽是否仍在 long 范围内要提前算
        return (seq << GENE_BITS) | gene;
    }

    /** 按 user_id 路由 */
    public static int shardOfUser(long userId) {
        return (int) (userId & GENE_MASK);
    }

    /** 按 order_id 路由：结果与 shardOfUser 一致，这是基因法的全部价值 */
    public static int shardOfOrder(long orderId) {
        return (int) (orderId & GENE_MASK);
    }

    /** 自检：任何订单 ID 都必须能路由回它所属用户的分片，上线前跑一遍 */
    public boolean selfCheck(long userId) {
        return shardOfOrder(nextOrderId(userId)) == shardOfUser(userId);
    }
}

② 原理 · 分片之后失去的能力清单

这是评估分片是否划算时最该读的一节，因为它描述的不是一次性的改造成本，而是永久性的能力损失。

失去的能力为什么缓解手段缓解手段的代价
跨分片 join两张表的关联行可能落在不同物理库，数据库无法连接把小维表做成每片一份的广播表；或冗余字段避免关联；或应用层两次查询再拼装广播表写入要同步所有分片；冗余字段带来一致性维护成本
跨分片事务的原子性涉及多个物理库，单库事务管不了柔性事务：TCC、Saga、本地消息表；或在设计上让一个事务只落一个分片需要业务实现补偿逻辑与幂等，细节见 分布式事务 与 幂等设计
跨分片排序与分页全局第 N 页无法从任一分片单独得出每片取「偏移量加页大小」条再归并；或改成游标法只支持下一页；或把列表查询收敛到单分片深分页时数据放大到不可接受，见下图
COUNT 与聚合需要所有分片的数据才能算出全局值扇出后应用层汇总；或维护单独的计数表；或用离线数仓出数扇出的耗时取决于最慢的那个分片；计数表要处理并发与一致性
全局唯一约束唯一索引只在单个物理库内生效唯一性字段本身作为分片键；或引入独立的唯一性校验服务分片键只能有一个，其他字段的全局唯一需要额外组件
自增主键各分片各自自增会产生重复值换全局唯一 ID 方案（见下一节）ID 变长、失去严格递增或引入新的依赖组件
不带分片键的查询无法路由，只能扇出建异构索引表（把「其他键到分片键」的映射单独存一份）；或把这类查询放到搜索引擎、数仓异构表要双写并保证一致；搜索引擎引入延迟与运维成本
简单的 DDL一张逻辑表对应几十上百张物理表用中间件统一下发；或用 gh-ost 逐片执行并校验一致执行时间长，中途失败会出现分片间结构不一致

缓解的方向不是优化归并算法，而是改需求：把「任意跳页」改成「只能翻下一页」的游标分页，或者在查询条件里强制要求带上分片键把范围收敛到单片，或者把这类列表需求整体搬到搜索引擎和离线数仓。

② 原理 · 全局唯一 ID 方案对照

搞清这一节能解决「分片后主键怎么发」，以及为什么用 UUID 图省事会在写入性能上付出最大代价。

方案有序性可用性风险索引友好度主要坑
数据库号段（每次取一批 ID 缓存在本地）整体趋势递增，单机内严格递增发号库挂了之后，本地号段用完即不可用；号段可调大来延长续命时间好，数值紧凑且递增服务重启会丢弃未用完的号段，造成 ID 空洞；多实例并发取号要保证原子性
雪花算法（时间戳加机器号加序列）趋势递增不依赖外部存储，可用性最好好时钟回拨会产生重复 ID，必须处理：检测到回拨就拒绝发号或切用备用位；机器号分配需要注册中心，容器化后 IP 复用容易撞号
UUID v4完全无序无外部依赖差。无序值导致页分裂与随机写，且 16 字节主键会把所有二级索引撑大最省事但对写入性能伤害最大；若要用，考虑改用前缀有序的变体并存成二进制
Redis 自增严格递增单点风险，且 Redis 持久化策略下宕机可能导致 ID 回退产生重复好依赖 Redis 可用性；主从切换时未落盘的自增值会丢，必须配合号段化使用

为什么无序主键对 InnoDB 伤害特别大（页分裂、聚簇索引与二级索引的存储放大），见 MySQL 深度原理；Redis 主从切换会丢未落盘写入的机制见 Redis 深度原理。

⚠️
时钟回拨是雪花算法最容易被忽略的坑

NTP 校时、虚拟机迁移、宿主机时钟漂移都会造成时间戳回退。一旦回退，同一毫秒内的序列号可能重复发放，产生业务上无法察觉的重复主键。可用的处理方式有三种：检测到回拨且幅度很小（几毫秒）就自旋等待时间追上；幅度较大就直接抛异常拒绝发号，让上游重试到别的实例；或者预留几位作为「时钟回拨计数」，每次回拨就递增这个值以保证不重复。绝对不要默默继续发号。

② 原理 · 扩容是整个方案里最难的一步

搞清这一节能解决「为什么老手都说一开始就多分几片」——因为事后扩容要走完下面这整个状态机。

所以最重要的结论是：预留足够的分片数比事后扩容便宜得多。一次就分 32 或 64 片，这些分片初期可以全部放在同一个物理实例上，后续按需把部分分片整体搬到新实例——这种搬迁只移动数据、不改变路由规则，风险低一个数量级。相反，分片数不足后再改分片数，取模算法下几乎全量数据都要重新分布。

每一步的要点：双写阶段旧分片仍是唯一事实来源，新分片写失败只告警；全量迁移要分批限速并记录进度以支持断点续跑；增量追平通常用 binlog 订阅，追到延迟稳定在秒级以内；校验必须同时对比行数和内容校验和，只对比行数会漏掉更新丢失；灰度切读按用户或分片维度放量，并做新旧结果的双读对比；切写之后旧分片保留只读一段时间，这是最后的回滚窗口。

-- 迁移校验：逐片对比行数与内容校验和，只比行数会漏掉「行数相同但内容被改坏」
-- 在旧库和新库分别执行，结果必须完全一致
SELECT
    COUNT(*) AS cnt,
    SUM(CRC32(CONCAT_WS('|', id, user_id, shop_id, status,
                        CAST(amount AS CHAR),
                        IFNULL(UNIX_TIMESTAMP(pay_time), 0),
                        UNIX_TIMESTAMP(create_time)))) AS checksum
FROM orders_07
WHERE create_time < '2026-09-20 00:00:00';   -- 固定一个截断点，避免增量数据干扰对比

-- 数据倾斜监控：分片间行数差异超过均值的 20% 就要介入
-- 在每个分片上跑同一条语句，把结果收集到监控系统做对比
SELECT DATABASE() AS shard, COUNT(*) AS rows_cnt,
       COUNT(DISTINCT user_id) AS users,
       MAX(create_time) AS latest
FROM orders_07;

-- 找出单片内的超级大户，这类账号是倾斜的主要来源
-- 处理方式：对头部账号单独路由，或在业务上限制单账号数据量
SELECT user_id, COUNT(*) AS cnt
FROM orders_07
GROUP BY user_id
ORDER BY cnt DESC
LIMIT 20;

② 原理 · 中间件选型：SDK 还是 Proxy

搞清这一节能解决「路由层放在哪」——它影响的是连接数、灰度粒度和故障影响面，而不只是性能。

维度应用层 SDK（ShardingSphere-JDBC、sharding-jdbc）代理层 Proxy（ShardingSphere-Proxy、Vitess、MyCat）
网络跳数无额外跳数，直连各分片多一次往返，延迟增加零点几到数毫秒
语言绑定与语言绑定，多语言栈要各自实现或放弃对客户端就是一个普通数据库，任何语言和现成工具都能连
单点风险无新增组件，随应用一起部署Proxy 本身是新的单点，需要自己做高可用与容量规划
升级与灰度需要所有应用重新发布，灰度颗粒度粗集中升级，灰度和回滚都在一处完成
连接数每个应用实例都与每个分片建连，实例多时连接数成倍放大Proxy 统一收敛后端连接，对分片更友好
可观测性指标散落在各应用，需要统一上报天然的集中埋点位置，慢查询与路由日志好收集
常见折中核心高频服务用 SDK 换取极致延迟运维脚本、数据分析、异构语言服务走 Proxy
 
# ShardingSphere-JDBC 5.x：orders 表按 user_id 分 4 库、每库 16 表，共 64 个分片
# 注意分片数是 2 的幂，与基因法的位数约束一致
rules:
  - !SHARDING
    tables:
      orders:
        # 实际物理节点：ds_0..ds_3 每个库里有 orders_0..orders_15
        actualDataNodes: ds_${0..3}.orders_${0..15}
        databaseStrategy:
          standard:
            shardingColumn: user_id
            shardingAlgorithmName: db_mod
        tableStrategy:
          standard:
            shardingColumn: user_id
            shardingAlgorithmName: tbl_mod
        keyGenerateStrategy:
          column: id
          keyGeneratorName: snowflake
    # 绑定表：分片规则完全一致的表，join 时不会退化成笛卡尔式的全分片关联
    bindingTables:
      - orders,order_items
    # 广播表：每个分片各存一份的小字典表，用来替代跨分片 join
    broadcastTables:
      - shop_dict
      - region_dict
    shardingAlgorithms:
      db_mod:
        type: INLINE
        props:
          algorithm-expression: ds_${user_id % 4}
      tbl_mod:
        type: INLINE
        props:
          # 先除库数再取表数，保证 64 个分片均匀覆盖而不是只落在 16 张表上
          algorithm-expression: orders_${(user_id.longValue() / 4) % 16}
    keyGenerators:
      snowflake:
        type: SNOWFLAKE
props:
  # 打开后会打印改写后的真实 SQL 与路由到的物理节点，排查路由问题必备
  sql-show: true
  # 单条逻辑 SQL 允许的最大分片并发度，调太大会瞬间打满所有分片
  max-connections-size-per-query: 4

③ 场景 · 什么时候该分片，什么时候该换数据库

TiDB、OceanBase、CockroachDB 这类分布式数据库把分片下沉到了存储层：数据自动按区间切分并在节点间迁移，应用看到的仍然是一张表，跨分片 join、分布式事务、全局索引由数据库自己实现。它省掉的正是分库分表最贵的那部分——业务改造和永久性的能力损失。

维度分库分表（中间件方案）分布式数据库
业务改造量大。分片键、跨片查询、全局 ID、事务全部要改小。多数场景兼容原有 SQL，改动集中在少数不支持的语法
扩容困难，需要重分布与完整的迁移流程加节点即可，数据自动再平衡
跨分片能力永久缺失，靠业务绕开数据库内置，虽然性能不如单片查询但功能完整
运维复杂度数据库本身还是熟悉的单机形态多角色集群，需要理解新的故障模式与调优手段
成本可以用小规格实例堆出来多副本带来数倍存储与机器成本，通常有最小集群规模要求
单点延迟命中单片时接近单机水平分布式事务与共识协议带来额外延迟，极致低延迟场景不占优
适合谁团队熟悉 MySQL 生态、查询形态简单且能收敛到分片键查询形态复杂、增长不确定、愿意用成本换改造量
场景该怎么做为什么代价
C 端订单、账单这类查询能收敛到用户维度按 user_id 分片加基因法，一次分 64 片最高频的两条路径都能命中单片，扇出比例可以压到很低商家维度与时间维度查询要另建异构索引表或走数仓
查询形态复杂、经常临时加新维度不要自己分片，上分布式数据库分片把「新维度查询」变成扇出，而需求会持续增加成本数倍上升，且要接受新的故障模式与调优手段
日志、埋点、消息这类只按时间查按时间分表或直接换列存引擎天然冷热分离，新周期建新表，扩容几乎零成本点查退化；分析型负载更适合 ClickHouse 这类引擎
SaaS 多租户，头部租户体量悬殊按租户分片，但给头部租户独立分片或独立库租户维度天然隔离，但均匀取模一定会被大租户压垮路由规则里出现例外条目，需要长期维护，策略见 数据归属与多租户
运营后台要任意条件查询与跳页把后台查询整体搬离分片库，走搜索引擎或数仓任意条件与跳页在分片上必然扇出加深分页放大数据有延迟，且多维护一条同步链路
只是历史数据太多归档或分区，不要分片缩小热数据集合可逆，分片不可逆要保留历史数据的查询入口
写入吞吐已到顶且必须留在 MySQL 生态水平分片，一次规划足够分片数这是分片真正成立的场景：容量与写入上限随分片数扩展接受本文第四节那份能力清单的永久缺失

不适用边界：分片解决不了任何「单次查询本身很贵」的问题——扫描量、排序、深分页在分片后只会更贵，这些先去 慢查询治理 与 索引设计与治理；瓶颈到底在哪一层、各手段的投入产出排序在 数据库性能优化主干篇；跨片事务的补偿与幂等落地在 分布式事务 与 幂等设计；分析型与报表型负载在 ClickHouse；分片间指标怎么采集与对比在 指标与监控。

③ 场景 · 分片之后的运维

分片上线不是终点，下面这七件事会长期占用人力，评估方案时就该把它们算进成本。

事项难点做法
DDL 一致性一张逻辑表对应几十上百张物理表，中途失败会导致分片间结构不一致用中间件统一下发并记录每片执行结果；执行后跑一次结构比对；把结构定义纳入版本管理
数据倾斜分片键分布不均或存在超级大户，单片先到瓶颈按片采集行数与体积做对比告警，偏离均值两成即介入；头部账号单独路由
一致性校验双写、迁移、补偿都可能产生分片间或主从间的差异定期跑行数与校验和比对；对账任务覆盖所有分片；差异自动生成修复单
备份与恢复多个物理库的备份时间点不一致，恢复后可能出现跨库不一致用全局一致性快照或统一的位点标记；恢复演练必须按分片全量走一遍
慢查询治理慢日志分散在几十个实例上集中采集后按逻辑表聚合；重点关注扇出查询的最慢分片，方法见 慢查询治理
容量规划单片容量到顶时扩容成本极高按片监控增长速率并预测到顶时间，至少提前一个季度准备
故障隔离一个分片故障会让部分用户完全不可用按分片做熔断与降级；扇出查询设置分片级超时，避免被最慢分片拖死

这条路径到这里结束：主干篇给判断顺序，索引篇解决扫描量，慢查询篇把发现与归因流程化，本篇是最后一招——只有前面全部用尽时才动它，而且动之前先读完那份能力清单。

最容易踩的坑

❌
避坑清单
  • 没穷尽替代方案就分片。归档、分区、读写分离、垂直拆分、升级规格都还有余量，却先付了不可逆的代价。
  • 指望分片解决复杂查询。分片只提升容量和写入上限，跨片 join、聚合、排序分页只会比单机更难。
  • 凭印象选分片键。没有用真实查询清单统计过「带不上分片键的调用量占比」，上线后才发现最高频的查询在扇出。
  • 一次只分 4 片。两年后扩容要走完双写、全量迁移、追平、校验、灰度切换全流程，这是整个项目里最危险的一次操作；一开始分 32 或 64 片几乎不增加成本。
  • 分片键选了 order_id。订单详情快了，但「我的订单列表」这个最高频的 C 端查询变成全分片扇出。
  • 用了基因法但没做自检。基因位数与分片数失配后，按订单号路由到的分片和按用户路由到的不是同一个，表现为「数据丢了」。
  • 扩容时改了分片数却忘了基因位数也要跟着变。旧订单 ID 的基因按旧位数生成，路由全部错位。
  • 直接沿用自增主键。各分片各自自增，很快出现重复 ID，而且发现时数据已经混了。
  • 用 UUID 做主键图省事。无序值造成页分裂与随机写，所有二级索引被撑大，写入性能损失远超预期。
  • 雪花算法不处理时钟回拨。NTP 校时或虚拟机迁移后发出重复 ID，业务层完全察觉不到。
  • 跨分片分页直接用偏移量。第 5001 页需要每片各取十万条再归并，一次请求就能把中间件的内存打满。
  • 跨分片 COUNT 放在高频接口上。每次都要扇出到所有分片，整体耗时由最慢的那一片决定。
  • 以为唯一索引还能保证全局唯一。它只在单个物理库内生效，重复数据会安静地写进不同分片。
  • 迁移校验只比行数不比内容。行数一致但某个区间的更新丢了，切读之后才暴露。
  • 全量迁移不记进度。任务中途失败只能整体重跑，窗口期被无谓拉长。
  • 切写之后立刻下线旧分片。发现问题时已经没有回滚窗口，只能硬扛着修数据。
