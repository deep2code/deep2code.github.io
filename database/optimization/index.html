数据库性能优化：瓶颈定位顺序与优化手段的投入产出

🏷️ 数据库优化

绝大多数「数据库优化」做错的地方不在技术细节，而在顺序。收到告警就去加索引、加缓存、讨论分库分表，是典型的从手段出发而不是从瓶颈出发。这篇不讲 B+ 树和 MVCC 这些原理，那些在站内 MySQL 深度原理篇里已经展开过；这篇讲的是一套可执行的排查顺序：怎么先排除数据库之外的因素，怎么区分全局慢和单条慢，怎么按投入产出比决定动手方向，以及怎么验证你的优化真的有效。

先证明这真的是数据库的问题

一次查询从业务线程发出到拿到结果，中间要经过应用进程、网络、可能存在的代理层，最后才进入数据库内部。任何一段都可能是耗时的大头，而只有最后一段是数据库的责任。

判断的方法很朴素：拿应用侧埋点的耗时和数据库侧统计的执行耗时做差。应用侧的埋点要包住「申请连接」这一步，数据库侧用语句摘要统计的平均执行时间。如果应用侧 2 秒、数据库侧 3 毫秒，这 1997 毫秒就不在数据库里，继续在数据库上找原因是白费功夫。最常见的误判源是连接池。

这张图想说清一件反直觉的事：连接池耗尽的现场，数据库侧的所有指标都可能是健康的。CPU 不高、慢查询数不多、平均耗时正常，因为真正的慢语句只有那么几条，它们把连接占住了，而被拖累的成千上万次快查询全都排在应用进程里，压根没到数据库。这时候扩容数据库毫无用处。

全局慢还是单条慢：第一个分叉

确认问题在数据库内部之后，下一个判断决定了后面所有动作：是所有语句都慢了，还是只有特定语句慢。全局慢指向资源和并发，单条慢指向执行计划。两者的排查工具完全不同，混在一起查就会得出「加了索引还是慢」这类结论。

这里有个容易忽略的读数细节：看并发压力要看正在执行的线程数，不是已建立的连接数。连接数上千但正在执行的只有两三个，说明数据库很闲；反过来正在执行的线程数长期高于 CPU 核数，就说明数据库内部已经在排队了，这时任何新语句的延迟都会被放大。下面这组命令是全局慢的第一轮分诊。

# 1) 每秒采样一次，重点看 Threads_running（正在执行），而不是 Threads_connected（已连接）
#    Threads_running 长期大于 CPU 核数，说明数据库内部已在排队
mysqladmin -uroot -p -i1 -r ext | grep -E 'Threads_running|Threads_connected|Slow_queries'

# 2) 主机侧同时看 IO 压力：%util 接近 100 且 await 上升，说明磁盘是瓶颈
iostat -x 1 5

# 3) 确认不是 swap 在拖后腿：数据库进程一旦被换出，延迟会出现无法解释的尖刺
vmstat 1 5
-- 4) 当前在跑什么：state 列直接告诉你卡在哪个阶段
--    Sending data 通常是在扫行，Copying to tmp table 是临时表
--    Waiting for table metadata lock 是被 DDL 卡住
SELECT id, user, db, command, time, state, LEFT(info, 120) AS sql_head
FROM information_schema.processlist
WHERE command NOT IN ('Sleep', 'Daemon') AND time > 1
ORDER BY time DESC;

-- 5) 缓冲池命中率：低于 99% 说明热数据装不进内存
--    这种情况下加索引的收益远不如加内存或归档冷数据
SELECT ROUND((1 - r.v / q.v) * 100, 4) AS hit_pct
FROM
  (SELECT variable_value + 0 AS v FROM performance_schema.global_status
   WHERE variable_name = 'Innodb_buffer_pool_reads') r,
  (SELECT variable_value + 0 AS v FROM performance_schema.global_status
   WHERE variable_name = 'Innodb_buffer_pool_read_requests') q;

-- 6) 有没有长事务扛着不提交：长事务会阻塞 purge，让 undo 膨胀、让别人等锁
SELECT trx_id, trx_state, trx_started,
       TIMESTAMPDIFF(SECOND, trx_started, NOW()) AS run_sec,
       trx_rows_locked, trx_rows_modified, LEFT(trx_query, 100) AS q
FROM information_schema.innodb_trx
ORDER BY run_sec DESC;

按投入产出排序的优化手段

所有手段都能提升性能，区别在于每单位收益要付出多少成本和风险。下面这张表的排序就是建议的动手顺序，收益倍数是常见量级而非保证值，风险一列比收益一列更值得读。

手段典型收益倍数实施成本主要风险可逆性
改写 SQL：去掉无用 join、拆 OR、消除隐式转换、分批处理2 到 100 倍，扫描量降一个数量级很常见低，改代码不改结构改写后语义不等价，尤其是 NULL 参与比较和 join 类型变化完全可逆
补齐或修正索引10 到 1000 倍，从全表扫变成点查低到中，大表加索引要走 Online DDL写入变慢、优化器可能选错新索引、加索引期间主从延迟可逆，删掉即可
调整表结构与字段类型：收窄类型、拆大字段、冷热分离1.5 到 5 倍，来自单页装更多行中，需要 DDL 与数据迁移类型收窄可能溢出、拆表后所有读写路径都要改较难逆，需再次 DDL
加缓存：Redis 或本地缓存10 到 100 倍，取决于命中率中，要处理失效与一致性缓存与库不一致、击穿与雪崩、缓存宕机后数据库被瞬间打满可逆但要留降级开关
读写分离读吞吐可线性扩展，写吞吐不变中，需要路由与延迟容忍设计复制延迟导致写后读不到、强一致场景必须强制走主库可逆
参数调优：缓冲池、刷盘策略、并发控制1.2 到 3 倍，个别错配场景可达 10 倍低，但部分参数需重启刷盘策略放松会丢数据，缓冲池调过大触发 OOM可逆
垂直拆分：按业务拆库、大字段拆副表2 到 5 倍，主要是降低单库压力高，跨库 join 全部要改成应用层聚合原本的单库事务变成跨库事务基本不可逆
水平分片：分库分表容量与写入上限随分片数线性扩展极高，数据迁移加业务改造跨片 join、跨片事务、跨片分页、全局唯一 ID 全部失效单向不可逆
❌
分库分表永远是最后一步

前面七项做错了可以改回来，分片做错了改不回来。分片一旦落地，分片键就固化进了所有查询，跨片能力的缺失会永久留在业务代码里，而且这份复杂度会被之后每一个新需求继续放大。判断是否该走到这一步的唯一标准是：归档、分区、垂直拆分、缓存、读写分离全部试过且明确不够，而不是「单表快到两千万行了」。完整决策路径见站内分库分表篇。

容量与性能的量级直觉

没有量级直觉就无法判断当前数字是否异常。下面这些区间对应的是常见云主机配置（8 到 16 核、32 到 64 GB 内存、NVMe SSD）上的中等宽度表。这些数字强依赖硬件、单行宽度和访问模式，只能当作判断「是否需要深究」的触发器，真正的基线必须靠自己压测得出。

维度通常没问题开始要警惕决定这个数字的真正因素
单表行数千万级以内数千万行以上且无法归档不是行数本身，而是索引与热数据能否装进缓冲池
单表数据加索引体积小于缓冲池的一半超过物理内存工作集大小，冷数据占多数时总体积大也无妨
单实例点查 QPS几千到几万接近数万且 CPU 打满每次查询的扫描行数，扫得少才谈得上高 QPS
单实例写 TPS数千上万且伴随复制延迟二级索引数量、刷盘策略、单事务大小
主键点查延迟亚毫秒到数毫秒持续超过 10 毫秒缓冲池命中率，未命中就是一次磁盘随机读
单条 OLTP 查询扫描行数数百行以内上万行索引选择性与过滤条件能否下推
单条查询返回行数几十到几百上万行业务分页设计，返回十万行本身就是设计问题
活跃连接（正在执行）小于 CPU 核数持续大于核数的两倍线程上下文切换与内部锁竞争
复制延迟亚秒级持续数秒以上大事务、从库回放并行度、从库配置弱于主库

连接池是最容易被忽视的瓶颈

连接池配置几乎没人认真算过，默认值一路带到生产，出问题时的第一反应又是调大。这里有一个反直觉但经过大量实践验证的结论：连接池越大，吞吐往往越低。原因是数据库的并行处理能力由 CPU 核数和磁盘并发度决定，超出这个上限的连接只会排队，而排队发生在数据库侧的代价比发生在应用侧更高，因为每个连接都对应一个线程和一份会话内存。

可用的起点公式是：连接池大小 ≈ CPU 核数 × 2 + 有效磁盘数。8 核加一块 NVMe 得到 17，这个数字比大多数人写在配置里的 100、200 小一个数量级。公式里乘二是为了填补线程等待 IO 的空隙，加磁盘数是为了利用存储的并发能力。如果应用有多个实例，要用「单实例池大小 × 实例数」去核对数据库侧的连接上限，这一步经常被漏掉，导致扩容应用实例时把数据库连接打满。

参数常见默认调错的后果建议做法
maximumPoolSize（HikariCP）10调到 200 后吞吐反而下降，数据库侧线程上下文切换吃掉大量 CPU按核数公式算出起点再压测微调，宁小勿大
connectionTimeout30 秒太长会让应用线程池被全部占满，故障从数据库蔓延成应用整体不可用设成 1 到 3 秒，快速失败并触发降级
maxLifetime30 分钟大于服务端 wait_timeout 时池里留着已被关闭的死连接，表现为随机报连接已关闭设成比 wait_timeout 小 30 秒以上
max_connections（数据库侧）151调大只是把排队从应用挪到数据库，还提高了内存占用上限和雪崩风险设成所有实例池大小之和再留两成余量，并预留超级用户连接
wait_timeout28800 秒太长会让异常断开的会话长期占着连接和可能持有的锁缩短到数百秒，并与连接池 maxLifetime 对齐
innodb_thread_concurrency0（不限制）高并发内部争用严重时，不限制反而更慢默认保持 0，只在确认存在内部争用时按核数附近取值试验
 
# HikariCP 生产配置示例：数据库 8 核 + 1 块 NVMe，应用共 4 个实例
# 池大小 = 8*2 + 1 = 17，四个实例合计 68 个连接，数据库侧 max_connections 设 100 足够
spring.datasource.hikari.maximum-pool-size=17
# 最小空闲与最大保持一致，避免流量突增时现场建连接带来的延迟尖刺
spring.datasource.hikari.minimum-idle=17
# 拿不到连接就快速失败，把压力挡在应用层而不是让线程无限等待
spring.datasource.hikari.connection-timeout=2000
# 必须小于服务端 wait_timeout（这里假设为 600 秒），否则会拿到已被服务端关掉的死连接
spring.datasource.hikari.max-lifetime=570000
# 泄漏检测：超过 5 秒未归还就打印持有连接的堆栈，用来定位忘记关闭连接的代码
spring.datasource.hikari.leak-detection-threshold=5000
# 单条语句的客户端读超时兜底，防止一条慢语句长期占住池里的连接
spring.datasource.hikari.data-source-properties.socketTimeout=5000

表结构设计对性能的影响

表结构的影响是乘数级的：它决定了每个页能装多少行，从而决定同样的扫描要读多少页，也影响索引树的高度。这部分的底层原理（页组织、聚簇索引、二级索引叶子存主键）详见站内 MySQL 深度原理篇，这里只给设计层面的结论。

设计选择常见误用性能后果建议
主键类型用 36 字节字符串存 UUID 当主键每个二级索引叶子都要存一份主键，索引整体膨胀数倍；无序值导致页分裂和随机写用自增整型或有序 ID；确实要用 UUID 则存成 16 字节二进制并保证前缀有序
整型宽度所有 ID 一律 BIGINT，状态位也用 INT单行变宽，页内行数变少，扫描放大按真实取值范围选；状态、类型这类小枚举用 TINYINT
字符串长度VARCHAR(255) 一把梭声明长度影响排序和临时表的内存预估，可能让内存临时表提前转磁盘按业务上限声明；索引长字符串时改用前缀索引
大字段富文本、JSON、base64 图片放在主表行溢出带来额外页跳转；SELECT * 会把大量无用数据读进缓冲池，挤掉真正的热数据拆到副表按主键关联，主表只留元信息
可空列所有列都允许 NULL额外的 NULL 标记位，统计信息与区分度受影响，NOT IN 这类谓词语义出乎意料能给默认值就设 NOT NULL，语义上确实需要「未知」时才用 NULL
浮点与金额金额用 FLOAT 或 DOUBLE精度丢失导致对账不平，等值比较失效进而查不到数据用 DECIMAL 或整型存最小货币单位
冷热混存三年历史数据和当天数据在同一张表热数据被冷数据挤出缓冲池，命中率下降，所有查询一起变慢按时间归档或分区，让热分区常驻内存
 
-- 表体检：找出单行过宽、以及索引比数据还大的表
-- avg_row_len 明显偏大的表要检查是不是塞了大字段
SELECT table_name,
       table_rows,
       ROUND(data_length  / 1024 / 1024) AS data_mb,
       ROUND(index_length / 1024 / 1024) AS index_mb,
       ROUND(index_length / NULLIF(data_length, 0), 2) AS idx_data_ratio,
       avg_row_length AS avg_row_len
FROM information_schema.tables
WHERE table_schema = DATABASE() AND table_type = 'BASE TABLE'
ORDER BY data_length + index_length DESC
LIMIT 20;

-- 列体检：把声明长度远超实际使用长度的字符串列收窄
-- 收窄 VARCHAR 能直接减少排序与临时表的内存预估，降低落盘概率
SELECT column_name, column_type, is_nullable, character_maximum_length
FROM information_schema.columns
WHERE table_schema = DATABASE() AND table_name = 'orders'
ORDER BY ordinal_position;

没有基线就没有优化

「优化后快了」如果没有基线支撑，就无法区分是你的改动生效了还是当天流量下降了。下面这份清单是需要长期采集的最小集合，采集间隔 10 到 15 秒，保留至少 30 天以便和上个月做同比。

指标取值来源健康参考异常时指向什么
QPS 与 TPSQuestions、Com_commit 的增量与业务曲线同形突增看是否有重试风暴，突降看是否已经卡住
语句延迟 P95 与 P99应用侧埋点加语句摘要统计P99 在个位数毫秒到数十毫秒P99 涨而平均不涨，说明长尾集中在少数语句
慢查询数量Slow_queries 的增量接近 0非零就要看摘要，并确认是否有新语句上线
活跃线程数Threads_running小于 CPU 核数持续高于核数说明内部排队，延迟会被放大
连接数与拒绝数Threads_connected、Connection_errors_max_connections连接数平稳，拒绝数为 0拒绝数非零说明连接上限已被打满
缓冲池命中率Innodb_buffer_pool_read_requests 与 Innodb_buffer_pool_reads高于 99%下降说明工作集超内存或有大扫描在冲刷缓冲池
行锁等待Innodb_row_lock_time_avg、Innodb_row_lock_waits接近 0上升说明存在热点行更新或长事务
临时表落盘占比Created_tmp_disk_tables 比 Created_tmp_tables低于一成偏高说明大量排序或分组无法用索引完成
复制延迟Seconds_Behind_Master 或 GTID 差值亚秒级上升说明存在大事务或从库回放能力不足
磁盘利用率与 await主机侧 iostat利用率有余量，await 稳定打满说明存储是瓶颈，此时任何 SQL 优化的收益都会被掩盖

优化的验证纪律

验证纪律的核心只有一句：一次只改一个变量。同时改索引、改 SQL、调参数，收益无法归因，出问题也无法快速定位是哪一项引起的。完整流程建议固化成下面这个状态机，每次优化都走一遍。

其中「同量级影子库」是最容易被跳过也最容易翻车的一步。在只有几万行测试数据的库上，任何执行计划都很快，优化器的选择也和生产完全不同，测出来的结论经常是反的。影子库的数据量和数据分布必须接近生产，至少要保证被优化表的行数在同一个数量级、被索引列的区分度接近真实值。

几类典型的假优化

现象为什么是假优化怎么做才算真
在测试库把查询从 800ms 优化到 20ms测试库数据量不足，热数据全在内存，生产上的磁盘随机读成本完全没有体现在同量级、同分布的库上验证，同时对比扫描行数而不只看耗时
平均耗时从 6ms 降到 5ms，宣布优化完成平均值掩盖长尾，真正伤害用户的是那百分之一的秒级查询以 P99 作为验收指标，并单独观察最慢的若干条语句
某条 SQL 优化了 50 倍，但接口 P99 没变这条语句本来就不是瓶颈，对总耗时的贡献可忽略按「单次耗时乘调用次数」排序找真正的大头，方法见站内慢查询治理篇
加了缓存后数据库 QPS 下降，认为问题解决只是把负载推迟了，缓存集中失效或缓存宕机时数据库会被瞬时打满压测缓存全失效场景下数据库是否还撑得住，并准备限流与降级
把 long_query_time 从 1 秒调回 10 秒，慢查询数归零指标漂亮了，问题一条没修阈值只在定位阶段临时调整，长期保持在能暴露问题的水平
一次性改了索引、SQL、参数三处，整体变快了无法归因，其中可能有一项是负收益，被另外两项掩盖拆成三次独立验证，每次留档
压测时用固定参数反复查同一条数据结果全部来自缓存，测出的是内存命中而不是真实混合负载用接近真实分布的参数集，并把写入混合进来
❌
最容易踩的坑
  • 看到告警先加索引，没先确认应用侧与数据库侧的耗时差。结果索引加了一堆，真正的连接池排队问题原封不动。
  • 用 Threads_connected 判断数据库忙不忙。连接数上千而正在执行的只有两个，数据库其实很闲；该看的是 Threads_running。
  • 把连接池调到 200 想「抗住并发」。数据库线程数远超核数后吞吐反降，现象是所有语句一起慢，看起来像数据库整体不行了。
  • 连接池 maxLifetime 大于服务端 wait_timeout。线上随机报连接已关闭，重试一次又好了，查半天找不到规律。
  • 忘记按应用实例数换算总连接数。扩容应用实例时把 max_connections 打满，新老实例一起连不上。
  • 在数据量不足的测试库上验收优化。生产上执行计划变了，优化器挑了另一个索引，效果与测试完全相反。
  • 只用平均耗时做基线。P99 从 200ms 恶化到 3s 时平均值几乎看不出变化，告警一声不响。
  • 一次性改多个变量后上线。整体变好了但其中一项是负收益，两个月后流量结构一变就集中爆发。
  • 字段类型一律取最大值「留余量」。单行变宽让页内行数减半，同样的范围扫描要多读一倍的页。
  • 大字段留在主表并习惯 SELECT *。一次列表查询把几十 MB 富文本读进缓冲池，把真正的热数据挤出去，全库跟着变慢。
  • 历史数据一直留在热表里不归档。表本身还能查，但缓冲池命中率一路下滑，最后表现为「没有任何改动却越来越慢」。
  • 为了让慢查询指标好看而调大 long_query_time。指标归零，问题在下一次大促原样爆出来。
  • 直接跳到分库分表。三个月改造上线后发现瓶颈其实是一条缺索引的语句，而分片带来的复杂度已经撤不回去了。
