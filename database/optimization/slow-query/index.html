慢查询治理：从发现到根治的完整闭环

🏷️ 慢查询优化

慢查询治理常见的做法是：收到告警、翻慢日志、找到最慢那条、加个索引、结束。这个流程有两个漏洞：慢日志看不到高频低耗时的语句，而那往往才是资源消耗的大头；修完一条不建立机制，下个季度同类问题会原样再来一次。这篇把慢查询当成一个闭环来写——发现、定级、归因、修复、回归、卡口。执行计划字段含义、索引失效场景、B+ 树这些底层原理详见站内 MySQL 深度原理篇，这里只用结论。

慢日志的默认配置等于没开

slow_query_log 打开之后还有一组参数决定它到底有没有用。最关键的是 long_query_time，默认 10 秒——能跑到 10 秒的语句，接口早就超时了，这个阈值只能抓到灾难，抓不到问题。

参数默认值配错的后果建议值
slow_query_logOFF什么都记不到ON，长期开启，开销可忽略
long_query_time10 秒只有灾难级语句入日志，日常问题全部漏掉先设 1 秒摸底，治理一轮后压到 0.1 到 0.5 秒；支持小数且可会话级动态改
log_queries_not_using_indexesOFF贸然开启会把小字典表的正常全表扫也记下来，日志量暴涨甚至写满磁盘仅排查窗口内临时开，必须配合下面两个参数
min_examined_row_limit0为 0 时扫 3 行的语句也可能入日志，噪声极大设 1000 以上，只记真正扫了不少行的语句
log_throttle_queries_not_using_indexes0（不限流）同一类语句每秒写几千行日志设 10 到 60，限制每分钟条数
log_slow_admin_statementsOFF大表 ALTER、ANALYZE 这类耗时 DDL 不会被记录，事后复盘缺证据ON
log_slow_replica_statementsOFF从库回放的慢语句不记录，复制延迟问题无从下手从库上设 ON
log_outputFILE设成 TABLE 时慢日志写进 mysql.slow_log，本身也会产生写入放大保持 FILE，用工具离线分析
 
-- 全部可动态生效，不需要重启；改完记得同步写进配置文件，否则重启后丢失
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 0.5;          -- 支持小数，单位秒
SET GLOBAL min_examined_row_limit = 1000;  -- 扫描行数不足 1000 的不记，过滤噪声
SET GLOBAL log_slow_admin_statements = ON; -- 把耗时 DDL 也记下来
SET GLOBAL log_output = 'FILE';

-- 会话级压到极小值，用来精确抓当前会话的每一条语句（只影响自己，不影响线上）
SET SESSION long_query_time = 0;

-- 确认当前生效值与文件位置
SHOW VARIABLES LIKE 'slow_query_log%';
SHOW VARIABLES LIKE 'long_query_time';
⚠️
慢日志记的是执行时间，不是用户感知的耗时

慢日志的耗时不包含在连接池里的排队时间，也不包含结果集回传到客户端的网络时间。所以「慢日志里一条都没有，但接口 P99 是三秒」完全可能发生，这种情况要回到站内主干篇讲的耗时差判断法，先确认瓶颈是否在数据库之外。反过来，等锁时间是计入执行时间的，所以一条执行计划完美的语句也可能出现在慢日志里。

比慢日志更重要的是语句摘要统计

慢日志按单次耗时过滤，这个过滤条件天生漏掉一整类问题：单条不慢但调用次数极高的语句。一条 8 毫秒的查询每分钟调用一百万次，总耗时是 8000 秒，比十条一秒的语句加起来还多两个数量级，但它永远不会进慢日志。这类语句几乎总是真正的资源大头，也是最容易被忽略的。

三个渠道缺一不可，但如果只能保留一个，应该保留语句摘要统计。它把参数不同的语句归并成同一个模板（digest），给出调用次数、总耗时、平均与最大耗时、扫描行数、返回行数、排序与临时表次数。排序的依据必须是总耗时，不是单次耗时。

-- MySQL：按总耗时排序找真正的资源大头
-- 重点看 rows_examined_avg 与 rows_sent_avg 的比值，比值大说明白扫了很多行
SELECT
    schema_name,
    LEFT(digest_text, 100)                          AS sql_template,
    count_star                                      AS calls,
    ROUND(sum_timer_wait  / 1000000000000, 2)       AS total_sec,
    ROUND(avg_timer_wait  / 1000000000, 2)          AS avg_ms,
    ROUND(max_timer_wait  / 1000000000, 2)          AS max_ms,
    ROUND(sum_rows_examined / count_star)           AS rows_examined_avg,
    ROUND(sum_rows_sent     / count_star)           AS rows_sent_avg,
    sum_select_scan                                 AS full_table_scans,
    sum_sort_merge_passes                           AS sort_merge_passes,
    sum_created_tmp_disk_tables                     AS tmp_disk_tables
FROM performance_schema.events_statements_summary_by_digest
WHERE schema_name IS NOT NULL
ORDER BY sum_timer_wait DESC
LIMIT 20;

-- 单独揪出「单次很快但总量惊人」的语句：平均 1 毫秒以内却排进总耗时前列
SELECT LEFT(digest_text, 80) AS sql_template, count_star AS calls,
       ROUND(avg_timer_wait / 1000000, 3) AS avg_ms,
       ROUND(sum_timer_wait / 1000000000000, 1) AS total_sec
FROM performance_schema.events_statements_summary_by_digest
WHERE avg_timer_wait < 1000000000 AND count_star > 100000
ORDER BY sum_timer_wait DESC
LIMIT 20;

-- 统计是累计值，做基线对比前先清零，跑一个业务周期后再取数

慢日志分析工具与 PG 侧的对应物

慢日志原始文件不适合人肉翻，pt-query-digest 会按模板聚合并给出排名，输出的重点不是最慢那条，而是「总耗时占比」一列。

# 基本用法：按总耗时排序输出前 20 个模板
pt-query-digest --limit 20 /var/log/mysql/slow.log

# 只看最近一小时，避免被历史数据污染结论
pt-query-digest --since '1h' /var/log/mysql/slow.log

# 只看某张表相关的语句
pt-query-digest --filter '($event->{arg} =~ m/orders/i)' /var/log/mysql/slow.log

# 把结果写回一张表做趋势对比，适合每天定时跑
pt-query-digest --review h=127.0.0.1,D=percona,t=query_review /var/log/mysql/slow.log

# 输出判读要点：
#   Response time 一列的百分比 = 该模板占总慢查询耗时的比例，先修占比最大的
#   R/Call 是单次耗时，Calls 是次数，两者相乘才是它真实的成本
#   Rows examine 与 Rows sent 差两个数量级以上，基本可以断定索引或过滤条件有问题
#   V/M 是方差均值比，数值大说明这个模板耗时极不稳定，通常是参数导致计划切换
-- PostgreSQL：pg_stat_statements 是 MySQL 语句摘要的对应物
-- 需要先在 shared_preload_libraries 里加载并 CREATE EXTENSION
SELECT
    LEFT(query, 100)                          AS sql_template,
    calls,
    ROUND(total_exec_time::numeric / 1000, 1) AS total_sec,
    ROUND(mean_exec_time::numeric, 2)         AS mean_ms,
    rows / GREATEST(calls, 1)                 AS rows_per_call,
    ROUND(100.0 * shared_blks_hit
          / GREATEST(shared_blks_hit + shared_blks_read, 1), 2) AS cache_hit_pct
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 20;

-- auto_explain：自动把慢语句的真实执行计划写进日志，比事后手工 EXPLAIN 可靠
-- 手工 EXPLAIN 时数据和参数都可能已经变了，自动记录的是当时真实发生的计划

拿到一条慢 SQL 之后的分析路径

大多数人的第一反应是 EXPLAIN，但这一步应该排在第二。第一步是看它返回多少行——如果业务真的需要一次拿十万行，那是接口设计问题，任何索引都救不了。

这条路径里有两个位置最容易走错。一是看到全表扫就加索引：小表全表扫比走索引更快，优化器的选择是对的，给几百行的字典表加索引没有意义。二是忽略等锁：等锁的语句执行计划完全正常，只看计划会得出「这条 SQL 没问题」的结论，然后陷入困惑。

六大类根因与对应治法

根因识别特征治法注意
无索引或索引失效访问类型退化为全表扫，预估扫描行数接近表总行数补索引，或消除失效写法（列上做函数、隐式类型转换、前导通配）失效场景矩阵见站内 MySQL 深度原理篇；小表全表扫属正常
返回数据量过大返回行数上万，扫描与返回行数比值接近 1，耗时随返回量线性增长改分页、收窄查询列、把导出类需求挪到离线链路这类语句加索引几乎没有收益，必须改业务
排序与分组无法利用索引执行计划出现文件排序或临时表，Created_tmp_disk_tables 上升让排序列紧跟在等值条件列之后，使索引天然有序；或收窄结果集再排序排序方向不一致（一列升一列降）在 8.0 之前无法用同一个索引消除排序
join 方式退化被驱动表上没有可用索引，出现块嵌套循环；或驱动表选错导致外层行数巨大给被驱动表的连接列建索引；用小结果集做驱动表；必要时拆成两次查询在应用层拼8.0 的 hash join 只在无索引等值连接时生效，不是万能替代
锁等待执行计划正常但耗时高，活跃事务表里有长事务，行锁等待指标上升缩短事务、把非数据库操作移出事务、拆分大批量更新、消除热点行加锁范围与死锁复盘见站内 MySQL 深度原理篇
优化器选错计划同一条语句不同参数走不同索引，或统计信息中的基数与实际差很多先 ANALYZE TABLE 更新统计信息；调整索引让选择唯一；最后才用索引提示锁定计划索引提示会固化计划，数据分布变化后反而成为新的故障源，要留注释和复查计划

SQL 没变但突然变慢

这是最让人困惑的一类：代码没动、索引没删、语句一个字符都没改，昨天 5 毫秒今天 3 秒。原因一定在语句之外。

原因怎么验证处置
数据量增长跨过优化器的成本拐点对比历史扫描行数；用极小和极大范围参数各跑一次看计划是否切换归档、分区，或补一个能把范围条件也吃掉的联合索引
统计信息过期查 information_schema.STATISTICS 的基数，与 COUNT(DISTINCT col) 实际值对比ANALYZE TABLE；频繁大批量写入的表调大采样页数
数据分布变化对索引列做分组计数，看是否出现一个占比极高的取值换更有选择性的列做前导列；对倾斜值走单独的查询路径
缓冲池被冲刷命中率曲线下滑，且时间点与某个报表或批处理任务上线对齐把大扫描任务挪到从库或离线库；热表归档冷数据
并发升高导致等锁活跃事务表里有长事务；行锁等待次数与平均等待时间上升缩短事务边界；对热点行改为队列化更新
路由到延迟大的从库同一语句在主库和各从库分别执行对比；查复制延迟剔除异常从库；对一致性敏感的查询强制走主库
硬件或云盘降级主机侧磁盘利用率与 await 上升，云厂商控制台有 IOPS 打满记录提升存储规格；确认是否触发了突发额度耗尽

SQL 改写技巧

原写法问题改写方向前提与代价
WHERE a = 1 OR b = 2两个条件在不同索引上，优化器常放弃索引改全表扫拆成两条查询用 UNION ALL 合并UNION ALL 不去重，需自行保证两个分支结果不重叠，否则要用 UNION 并承担排序去重成本
相关子查询逐行执行外层每行触发一次内层查询，行数放大后耗时线性爆炸改写成 join，让优化器一次完成连接注意 NULL 语义：NOT IN 子查询遇到 NULL 会整体返回空，改成 NOT EXISTS 或左连接判空才等价
IN 里塞几千个值解析开销大，且可能超出优化器的范围优化预算而放弃索引把候选集写入临时表再 join；或分批查询在应用层合并分批会失去一次性排序的能力，排序要在应用层做
大表 COUNT(*) 求总数需要扫完整个索引，表越大越慢，且结果下一秒就过期用近似值（统计表行数估算）、维护计数器表、或改成「是否还有下一页」的判断近似值有误差；计数器表要处理并发更新与一致性
一次性 UPDATE 或 DELETE 百万行长事务持锁、undo 膨胀、binlog 巨大、从库延迟飙升按主键区间分批处理，每批几千行并在批间短暂休眠分批期间数据处于中间状态，业务要能容忍；需要记录进度以支持断点续跑
深分页 LIMIT 1000000, 20需要先扫过并丢弃前一百万行改用上一页最后一条主键作为游标条件继续取游标法不支持跳页；具体推演见站内 MySQL 深度原理篇
SELECT *无法走覆盖索引，且把大字段读进缓冲池挤占热数据只列出需要的列，尽量让索引覆盖查询字段变更时要同步维护语句，ORM 场景需显式指定投影
ORDER BY RAND() 取随机行给全表生成随机值再排序，必然全表扫加排序先随机取主键范围再按主键定位；或预先维护随机序号列随机性略有偏差，主键有空洞时要处理取不到的情况

治理闭环：修一条不算治理

只修不建机制，同一类问题会在每个季度以不同语句的形式回来。闭环要同时具备上线前卡口、周期性复查、运行时告警三件事。

卡口是三件事里收益最高的。思路很简单：在 CI 里连一个与生产同量级的影子库，对新增或改动的 SQL 自动跑执行计划检查，访问类型退化成全表扫、预估扫描行数超阈值、出现文件排序或临时表，就让流水线失败。注意影子库必须有接近生产的数据量，否则检查会全部通过——几万行的库上任何计划都很快。

#!/usr/bin/env python3
# 上线前 SQL 卡口：对待上线的 SQL 跑 EXPLAIN FORMAT=JSON，不达标就让 CI 失败
# 前提：连接的是与生产同量级、同数据分布的影子库，小库上跑这个检查毫无意义
import json, os, sys
import pymysql

MAX_ROWS = 5000          # 单表预估扫描行数上限，OLTP 接口按业务调整
BAD_ACCESS = ('ALL', 'index')                        # 全表扫与全索引扫
BAD_FLAGS = ('using filesort', 'using temporary')    # 额外排序与临时表

def collect(node, out):
    """递归遍历 EXPLAIN FORMAT=JSON，把每个被访问表的关键字段收集出来"""
    if isinstance(node, dict):
        t = node.get('table')
        if isinstance(t, dict):
            out.append({
                'name':   t.get('table_name'),
                'access': t.get('access_type'),
                'rows':   t.get('rows_examined_per_scan') or 0,
                'key':    t.get('key'),
            })
        for v in node.values():
            collect(v, out)
    elif isinstance(node, list):
        for v in node:
            collect(v, out)

def check(cur, sql):
    cur.execute('EXPLAIN FORMAT=JSON ' + sql)
    plan = json.loads(cur.fetchone()[0])
    raw = json.dumps(plan).lower()
    tables, problems = [], []
    collect(plan, tables)
    for t in tables:
        rows = t['rows']
        # 小表全表扫是正常的，所以加行数下限，避免对字典表误报
        if t['access'] in BAD_ACCESS and rows > 1000:
            problems.append('表 %s 访问类型 %s，预估扫描 %s 行' % (t['name'], t['access'], rows))
        if rows > MAX_ROWS:
            problems.append('表 %s 预估扫描 %s 行，超过阈值 %s' % (t['name'], rows, MAX_ROWS))
        if not t['key'] and rows > 1000:
            problems.append('表 %s 没有用到任何索引' % t['name'])
    for flag in BAD_FLAGS:
        if flag in raw:
            problems.append('执行计划中出现 ' + flag)
    return problems

if __name__ == '__main__':
    conn = pymysql.connect(host=os.environ['SHADOW_HOST'],
                           user=os.environ['SHADOW_USER'],
                           password=os.environ['SHADOW_PASS'],
                           database=os.environ['SHADOW_DB'])
    cur = conn.cursor()
    failed = 0
    for path in sys.argv[1:]:
        text = open(path, encoding='utf-8').read()
        for sql in [s.strip() for s in text.split(';') if s.strip()]:
            problems = check(cur, sql)
            if problems:
                failed += 1
                print('[FAIL] ' + sql[:90])
                for p in problems:
                    print('       - ' + p)
    print('检查完成，不合格语句 %d 条' % failed)
    sys.exit(1 if failed else 0)

-- A. 谁在跑、卡在哪个阶段
SELECT id, user, db, time, state, LEFT(info, 150) AS sql_head
FROM information_schema.processlist
WHERE command NOT IN ('Sleep', 'Daemon')
ORDER BY time DESC;

-- B. 活跃事务：找出运行时间最长、持锁最多的那个
SELECT trx_id, trx_state,
       TIMESTAMPDIFF(SECOND, trx_started, NOW()) AS run_sec,
       trx_rows_locked, trx_rows_modified, trx_isolation_level,
       LEFT(trx_query, 120) AS q
FROM information_schema.innodb_trx
ORDER BY run_sec DESC;

-- C. 锁等待关系：谁在等谁（MySQL 8.0）
--    5.7 及以前用 information_schema.innodb_lock_waits
SELECT w.requesting_engine_thread_id AS waiter_thread,
       w.blocking_engine_thread_id   AS blocker_thread,
       l.object_name, l.index_name, l.lock_type, l.lock_mode, l.lock_status
FROM performance_schema.data_lock_waits w
JOIN performance_schema.data_locks l
  ON l.engine_lock_id = w.blocking_engine_lock_id;

-- D. 把等待线程映射回连接与语句，才能知道该找谁
SELECT t.processlist_id, t.processlist_user, t.processlist_time,
       LEFT(t.processlist_info, 120) AS q
FROM performance_schema.threads t
WHERE t.thread_id IN (
    SELECT blocking_engine_thread_id FROM performance_schema.data_lock_waits
);

命令关键字段怎么判读
A 进程列表stateSending data 是在扫行读数据（不是在发网络包）；Copying to tmp table 说明用了临时表；Waiting for table metadata lock 说明被 DDL 或未提交事务挡住；statistics 停留久说明优化器在选计划时统计代价过高
B 活跃事务run_sec、trx_rows_locked运行秒数大而 trx_query 为空，说明事务开着但当前没在执行语句，典型是应用在事务中调了外部接口；持锁行数远超业务预期，说明加锁范围被放大
C 锁等待index_name、lock_mode索引名告诉你锁加在哪个索引上；锁在主键上通常是精确更新，锁在二级索引上要留意间隙锁范围；加锁范围推演见站内 MySQL 深度原理篇
D 线程映射processlist_id拿到阻塞方的连接号才能定位到具体应用实例，必要时用 KILL 处理；直接 kill 等待方是无效操作
E EXPLAIN ANALYZE实际行数与预估行数的差距两者差一个数量级以上，说明统计信息不准，先 ANALYZE TABLE；循环次数乘单次耗时才是该节点的真实成本
F 引擎状态LATEST DETECTED DEADLOCK、TRANSACTIONS、BUFFER POOL死锁段只保留最近一次，出现死锁要第一时间抓取；History list length 持续增长说明 purge 跟不上，通常是长事务所致
SHOW STATUS LIKE 'Handler%'Handler_read_rnd_next这个值增长快说明大量顺序全表扫；与 Handler_read_key 的比值可以粗略衡量索引利用率
❌
最容易踩的坑
  • long_query_time 留在默认 10 秒就以为开了慢日志。日志里一年只有几条，真正的问题全在阈值之下。
  • 只看慢日志不看语句摘要统计。真正的资源大头是那条 8 毫秒、每分钟百万次的语句，它永远不会出现在慢日志里。
  • 按单次耗时排序治理。修完最慢那条，整体 P99 毫无变化，因为它一天只跑三次。
  • 把 log_queries_not_using_indexes 长期开着且不设 min_examined_row_limit。字典表的正常全表扫把磁盘写满，反过来拖慢数据库。
  • 拿到慢 SQL 直接 EXPLAIN，跳过「返回多少行」这一步。花两天加索引，最后发现接口一次要返回八万行。
  • 看到全表扫就加索引。几百行的配置表走全表扫比走索引更快，优化器的选择本来是对的。
  • 忽略等锁。等锁语句的执行计划完全正常，只看计划会得出「这条没问题」，然后在原地打转。
  • 在小数据量的测试库上验证优化。计划、索引选择、成本估算全都和生产不同，结论经常是反的。
  • 事后手工 EXPLAIN 当作现场证据。数据和参数都已经变了，看到的不是当时真实执行的计划；要靠自动记录的计划或 EXPLAIN ANALYZE。
  • 用索引提示强行锁定计划后不留复查。数据分布一变，被固化的计划本身成为新的故障源。
  • NOT IN 子查询直接改成 NOT EXISTS 之外的写法而不管 NULL。子查询结果里只要有一个 NULL，NOT IN 整体返回空，改写后行为不等价。
  • 一次性 DELETE 上百万行。长事务持锁、undo 膨胀、binlog 暴涨、从库延迟几十分钟，一条语句引发全链路故障。
  • 统计信息从不更新。大批量导入后基数严重失真，优化器持续选错索引，表现为「没改代码却越来越慢」。
  • 治理完不建卡口。三个月后新上线的接口带来同类问题，全部流程原样重跑一遍。
