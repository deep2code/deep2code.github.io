索引设计与治理：从查询模式推导索引，并管住索引数量

「哪条查询慢就给它加个索引」是索引失控的起点。这样做出来的表最后会有十几个索引，一半从来没被用过，另一半互相冗余，写入被拖慢，优化器还时不时选错。索引应该是从一张表的全部查询模式反推出来的一组设计，而不是一条条查询的补丁。B+ 树结构、回表与覆盖索引、最左前缀判定、索引失效场景这些原理详见站内 MySQL 深度原理篇，这篇只讲设计方法和治理手段。

第三步是最容易被跳过的一步，也是索引数量失控的根源。一个 (a, b, c) 索引天然能服务只用 a 和只用 a, b 的查询，所以不要把 (a)、(a,b)、(a,b,c) 三个都建出来，只留最长的那个。收集查询模式可以直接从语句摘要统计里捞。

-- 第一步：把这张表上真实发生过的语句模板全部捞出来，按频次排序
-- 比翻代码可靠，因为它包含了框架自动生成和运维临时执行的语句
SELECT LEFT(digest_text, 160) AS sql_template,
       count_star AS calls,
       ROUND(sum_timer_wait / 1000000000000, 2) AS total_sec,
       ROUND(sum_rows_examined / count_star) AS rows_examined_avg
FROM performance_schema.events_statements_summary_by_digest
WHERE digest_text LIKE '%`orders`%' OR digest_text LIKE '%orders%'
ORDER BY count_star DESC
LIMIT 50;

-- 设计前先量一下候选列的区分度：越接近 1 越适合做前导列
-- 注意要在生产数据上量，测试库的分布通常完全不同
SELECT
    COUNT(*)                                        AS total,
    COUNT(DISTINCT user_id) / COUNT(*)              AS sel_user_id,
    COUNT(DISTINCT shop_id) / COUNT(*)              AS sel_shop_id,
    COUNT(DISTINCT status)  / COUNT(*)              AS sel_status,
    COUNT(DISTINCT DATE(create_time)) / COUNT(*)    AS sel_create_day
FROM orders;

-- 检查倾斜：区分度平均值不错，但某个取值占了八成，索引对这个取值就是无效的
SELECT status, COUNT(*) AS cnt,
       ROUND(100 * COUNT(*) / (SELECT COUNT(*) FROM orders), 2) AS pct
FROM orders GROUP BY status ORDER BY cnt DESC;

完整推演：五条查询设计出两个索引

假设一张订单表 orders，列有 id、user_id、shop_id、status、amount、pay_time、create_time。业务上确定只有以下五条查询。

查询等值列范围列排序或分组列单独最优索引最终归入
Q1 我的订单列表（最高频）user_id无create_time 倒序(user_id, create_time)索引一
Q2 我的订单按状态筛选user_id、status无create_time 倒序(user_id, status, create_time)索引一（状态在扫描时过滤）
Q3 我的某段时间内订单user_idcreate_time无(user_id, create_time)索引一
Q4 商家待结算订单shop_id、statuspay_time无(shop_id, status, pay_time)索引二
Q5 商家各状态订单数shop_id无status 分组(shop_id, status)索引二的前缀

推演的关键分歧在 Q2。它单独最优的索引是 (user_id, status, create_time)，而 Q1、Q3 要的是 (user_id, create_time)，两者无法互相覆盖：把 status 插在中间，Q1 没有 status 条件，就没法用后面的 create_time 提供有序性，会退化成额外排序。

取舍依据是频次和选择性：status 通常只有几个取值，区分度极低，Q2 用 (user_id, create_time) 按时间倒序扫描、边扫边过滤 status，只要单个用户的订单数不大（这是业务事实），代价完全可接受，而且省掉了一个索引。所以最终只建两个：

-- 索引一：服务 Q1 / Q2 / Q3。前导列 user_id 是所有 C 端查询的必带条件
-- create_time 紧跟其后，让「按时间倒序」直接由索引提供，消除额外排序
ALTER TABLE orders ADD KEY idx_user_time (user_id, create_time);

-- 索引二：服务 Q4 / Q5。等值列 shop_id、status 在前，范围列 pay_time 在最后
-- Q5 只用到 (shop_id, status) 前缀，不需要额外再建一个索引
ALTER TABLE orders ADD KEY idx_shop_status_pay (shop_id, status, pay_time);

-- 验证：确认 Q1 没有出现额外排序，Q4 的扫描行数与返回行数接近
EXPLAIN SELECT id, amount, status FROM orders
 WHERE user_id = 10086 ORDER BY create_time DESC LIMIT 20;

EXPLAIN SELECT id, user_id, amount FROM orders
 WHERE shop_id = 77 AND status = 2 AND pay_time >= '2026-09-01';
💡
为什么不是五个索引

给五条查询各建一个「单独最优索引」，写入成本会是两个索引方案的两倍以上，而收益只体现在 Q2 的一次排序上。索引设计的本质是在有限的索引预算内覆盖尽可能多的查询，不是让每条查询都跑在它的理论最优路径上。判断一个索引方案好不好，要同时看它服务了几条查询、以及被迫牺牲了什么。

索引列顺序的决策

原则为什么例外与边界
等值条件列放最前等值条件能把扫描范围收敛成一个确定的区间，是定位效率最高的条件等值列自身区分度极低（如只有两个取值的标记位）时，放在最前只是浪费一层
排序或分组列紧跟等值列索引在等值前缀确定后，后续列天然有序，可以直接消除额外排序多列排序方向不一致（一列升一列降）时，8.0 之前无法用同一个索引消除排序，8.0 起可建降序索引
范围条件列放最后范围条件之后的列无法再用于定位，只能在扫描时过滤只有一个范围条件时才成立；两个范围条件必然只有一个能用于定位，另一个要靠过滤
区分度高的列优先越早收敛扫描范围，需要读的页越少这一条优先级最低。为了让多条查询复用同一个索引，经常要把区分度较低但所有查询都带的列放到前面
把所有查询都带的列放前面这是索引复用的前提，能显著减少索引总数如果该列在某些查询中会用范围条件，复用就失效了，要单独评估
高频查询的返回列可以追加在末尾做覆盖避免回表，扫描与返回行数比高的查询收益最大追加会让索引变宽、写入变贵；只对确实高频且返回列很少的查询这么做

实际工作中更常见的问题不是「列顺序怎么排」，而是「这条新查询到底要不要为它建索引」。下面这条路径能挡掉大部分不必要的索引。

索引不是越多越好：量化代价

代价维度量级说明
写放大每增加一个二级索引，单行插入要多维护一棵 B+ 树；从 2 个索引加到 6 个，写入吞吐常见下降三成到一半更新时只要改动的列在某个索引里，那个索引就要跟着改；删除则所有索引都要改
空间占用索引总体积常达数据体积的 30% 到 100%，宽索引更多二级索引叶子要存一份主键值，主键越宽索引膨胀越明显
优化器成本候选索引越多，计划评估时间上升，选错概率也上升典型症状是同一条语句不同参数走不同索引，耗时忽高忽低
内存竞争索引页与数据页共用缓冲池，无用索引被写入时也会占内存冷索引被动加载会挤掉热数据页，间接拖慢其他查询
运维成本备份体积、恢复时间、DDL 执行时间都随索引数线性增长大表重建的时间成本经常被低估
建议上限单表 5 到 6 个索引；联合索引列数一般不超过 5 列超出通常意味着这张表承担了太多形态的查询，应该考虑读写分流

前缀索引、函数索引与虚拟列

长字符串列直接建索引会让索引变得很宽。前缀索引只取前 n 个字符，代价是不能用于覆盖索引，也不能用于排序——索引里存的是截断值，取完整值必须回表，而前缀相同的行内部顺序也不确定。选 n 的方法是逐个试算区分度，找到能达到完整区分度九成以上的最小值。

-- 一次算出多个候选长度的区分度，和不截断时的区分度做对比
-- 目标：选一个达到完整区分度九成以上的最小 n
SELECT
    COUNT(DISTINCT email)              / COUNT(*) AS sel_full,
    COUNT(DISTINCT LEFT(email, 6))     / COUNT(*) AS sel_6,
    COUNT(DISTINCT LEFT(email, 10))    / COUNT(*) AS sel_10,
    COUNT(DISTINCT LEFT(email, 16))    / COUNT(*) AS sel_16,
    COUNT(DISTINCT LEFT(email, 20))    / COUNT(*) AS sel_20
FROM users;

-- 假设 sel_16 已达到 sel_full 的 95%，就取 16
ALTER TABLE users ADD KEY idx_email_pre (email(16));

-- 域名集中的邮箱、同前缀的编码，前缀区分度会很差，可以存反转值再建前缀索引
-- 反转列用虚拟列实现，不额外占用存储（MySQL 5.7 起）
ALTER TABLE users
  ADD COLUMN email_rev VARCHAR(120)
      GENERATED ALWAYS AS (REVERSE(email)) VIRTUAL,
  ADD KEY idx_email_rev (email_rev(16));

-- MySQL 8.0.13 起支持直接对表达式建索引，不必显式加虚拟列
ALTER TABLE orders ADD KEY idx_create_day ((DATE(create_time)));
-- 5.7 的等价做法：虚拟列加普通索引
-- ALTER TABLE orders
--   ADD COLUMN create_day DATE GENERATED ALWAYS AS (DATE(create_time)) VIRTUAL,
--   ADD KEY idx_create_day (create_day);
-- 注意：查询必须写成与索引定义完全一致的表达式，写法不一致就用不上

唯一索引与普通索引的隐藏成本

维度唯一索引普通索引
插入时的页读取必须把目标页读进内存判重，页不在内存时触发一次磁盘随机读页不在内存时可先记进 change buffer，稍后合并
写入吞吐写密集且目标页多数不在内存时明显更低可攒批合并，随机写被摊薄
查询性能等值查询命中后可立即停止扫描需要继续判断下一条是否仍满足条件，差异极小
约束能力数据库层保证唯一，能兜住应用逻辑漏洞不保证，需要应用或其他机制保证
并发写表现冲突插入会直接报重复键，需要业务处理；插入意向锁可能带来额外等待无判重，不产生这类冲突
适用判断唯一性是业务正确性的底线时必须用，例如身份证号、支付流水号唯一性已由上游或分布式 ID 保证时，用普通索引省下写入成本

结论是：「顺手加个唯一索引保险一点」不是零成本的，在写密集的表上这是实打实的性能损失。change buffer 的工作机制与它失效的条件详见站内 MySQL 深度原理篇。

索引治理：找出未使用与冗余的索引

-- 1) 从未被使用过的索引（sys 库，MySQL 5.7 起自带）
--    统计从上次实例重启开始累计，重启时间太近的话结果不可信
SELECT * FROM sys.schema_unused_indexes
WHERE object_schema = DATABASE();

-- 2) 冗余索引：被另一个索引的前缀完全覆盖
--    视图会直接给出建议执行的删除语句
SELECT table_name, redundant_index_name, redundant_index_columns,
       dominant_index_name, dominant_index_columns, sql_drop_index
FROM sys.schema_redundant_indexes
WHERE table_schema = DATABASE();

-- 3) 先确认统计周期够不够长：距上次重启多久
SELECT variable_value AS uptime_sec
FROM performance_schema.global_status WHERE variable_name = 'Uptime';

-- 4) 每个索引被读取的次数，用来给「删不删」排优先级
--    count_read 为 0 且周期覆盖了月末批量任务，才是安全的删除候选
SELECT object_name AS tbl, index_name, count_read, count_write,
       count_fetch, count_insert, count_update, count_delete
FROM performance_schema.table_io_waits_summary_by_index_usage
WHERE object_schema = DATABASE() AND index_name IS NOT NULL
ORDER BY count_read ASC, count_write DESC;

-- 5) 统计信息是否失真：把索引记录的基数与实际值对比
--    cardinality 与实际相差一个数量级以上，优化器就会持续选错
SELECT index_name, seq_in_index, column_name, cardinality
FROM information_schema.STATISTICS
WHERE table_schema = DATABASE() AND table_name = 'orders'
ORDER BY index_name, seq_in_index;
-- 对比实际值，差得多就 ANALYZE TABLE orders;
SELECT COUNT(DISTINCT user_id) AS real_user_card FROM orders;
⚠️
删索引前必须确认统计周期

sys.schema_unused_indexes 的统计是从实例上次启动开始累计的。刚重启两天就去删「从未使用」的索引，极可能删掉月末结算、季度对账、年度报表的唯一支撑索引，等到月底那条任务跑成全表扫才发现。安全的判断标准是：统计周期至少覆盖一个完整业务周期（含月末与大促），并且人工确认过低频批量任务清单。

MySQL 8.0 提供了比「直接删」安全得多的路径：把索引设为不可见（invisible），优化器不再使用它但索引仍然被维护，观察一段时间没有语句恶化再真正删除，中间任何时刻都能一秒钟恢复。

索引设计的反模式

反模式后果正确做法
给每个字段都建单列索引写入成倍变慢，且多条件查询仍然用不上，最多做索引合并，效率远低于联合索引按查询模式设计联合索引，单列索引只保留确实只按该列过滤的场景
在低区分度字段上建索引（性别、是否删除、状态）扫描范围仍然是表的一大部分，优化器多半直接放弃它把低区分度列放进联合索引的非前导位置，或在 PG 上用部分索引
联合索引列序拍脑袋定大量查询无法命中最左前缀，看起来「有索引却不走」先列全查询条件，按等值、排序、范围的顺序排，并验证复用情况
加了新索引却忘了删被覆盖的旧索引(a) 和 (a,b) 同时存在，前者纯粹是写入负担每次新增索引后跑一次冗余索引检查
在频繁更新的字段上建索引每次更新都要维护索引树，热点行还会造成索引页争用高频变更的列（如计数器、最后活跃时间）尽量不索引，必要时拆到单独的表
为一次性运营需求加索引，事后不清理索引长期存在却再无查询使用，成为永久的写入税临时需求走从库或离线库；必须加的话记录到期时间并复查
联合索引列数堆到七八列索引宽度接近数据行本身，空间和写入成本都上去了，收益却很有限控制在五列以内，靠回表拿剩余列通常更划算
用 UUID 之类无序值做主键所有二级索引都被撑大，插入造成页分裂与随机写用自增或有序 ID 做主键，把 UUID 作为普通唯一索引
只在测试库验证索引效果数据分布不同，优化器选择不同，上线后完全不走新索引在同量级同分布的影子库上验证，并对比扫描行数
❌
最容易踩的坑
  • 把 (a)、(a,b)、(a,b,c) 三个索引都建出来。前两个完全被第三个的前缀覆盖，只剩写入成本。
  • 为了 Q2 的一次排序单独加索引，忽略了它只占总调用量的百分之几。索引预算花在了收益最小的地方。
  • 把区分度低的状态列放在联合索引最前面。前缀无法收敛范围，索引形同虚设。
  • 忘了排序列必须紧跟等值列。中间插了一个范围条件列，额外排序怎么都消不掉。
  • 两列排序方向一升一降，还指望 8.0 之前的版本能用索引消除排序。这在 8.0 引入降序索引之前做不到。
  • 用前缀索引之后还指望覆盖索引生效。索引里只有截断值，取完整值必须回表，而且排序也用不上。
  • 为了「保险」给一堆字段加唯一索引。唯一索引无法用 change buffer 攒批，写密集表上是实打实的吞吐损失。
  • 建了表达式索引但查询写法与索引定义不一致。差一个类型转换或函数嵌套顺序，索引就用不上。
  • 刚重启两天就照着「未使用索引」列表删索引。月末对账任务一跑，唯一支撑它的索引已经没了。
  • 直接 DROP INDEX 而不先设为不可见。发现删错时，重建一个大表索引要等几十分钟。
  • 大表加索引不写 ALGORITHM=INPLACE。某些变更悄悄降级成拷贝表算法，锁表几十分钟。
  • 执行 DDL 前不检查长事务。Online DDL 首尾要拿元数据锁，被长事务挡住后，所有访问这张表的语句一起排队。
  • 只看主库的 DDL 耗时。主库并发执行几分钟，从库却是一个事务完整回放，复制延迟能到几十分钟。
  • 统计信息长期不更新。批量导入后基数严重失真，优化器持续选错索引，看起来像索引失效。
