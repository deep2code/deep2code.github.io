Redis 深度原理：为什么它这么快？

🏷️ Redis

很多人用 Redis 只会 SET/GET，但不知道它为什么比 MySQL 快 100 倍，也不知道数据结构底层怎么实现的。这篇从原理讲透 Redis。

flowchart TD A[Redis 为什么快] --> B[纯内存操作] A --> C[单线程模型] A --> D[IO 多路复用] A --> E[高效数据结构] C --> C1[无锁无上下文切换] D --> D1[epoll/kqueue] E --> E1[SDS/跳表/压缩列表]

核心原理一：单线程为什么还这么快？

很多人以为单线程性能差，但 Redis 单线程却能扛 10万 QPS，原因有三个：

flowchart LR A[网络请求] --> B[IO多路复用 epoll] B --> C[事件分发] C --> D[命令执行 单线程] D --> E[返回结果] style D fill:#ff6b6b,color:#fff
原因 解释 对比 MySQL
纯内存 所有数据都在内存，操作不涉及磁盘 MySQL 要读磁盘页
单线程 没有锁竞争，没有上下文切换开销 MySQL 多线程要加锁
IO多路复用 一个线程处理上万连接，epoll 事件驱动 MySQL 每连接一个线程
高效数据结构 SDS、跳表、压缩列表，针对场景优化 B+ 树，通用型
💡
小知识

Redis 6.0 之后网络 IO 是多线程的，但命令执行还是单线程，所以还是不用加锁。

核心原理二：五种数据结构底层怎么实现的？

很多人知道 Redis 有五种数据结构，但不知道每种底层用了什么数据结构，也不知道什么场景用哪种。

flowchart TD A[五种数据结构] --> B[String 字符串] A --> C[List 列表] A --> D[Hash 哈希] A --> E[Set 集合] A --> F[ZSet 有序集合] B --> B1[SDS 动态字符串] C --> C1[压缩列表/双向链表] D --> D1[压缩列表/哈希表] E --> E1[整数集合/哈希表] F --> F1[压缩列表/跳表+哈希表]
数据结构 底层实现 时间复杂度 典型场景
String SDS 动态字符串 O(1) 缓存、计数器、分布式锁
List 压缩列表（小）/ 双向链表（大） O(1) 头尾，O(n) 中间 消息队列、最新列表
Hash 压缩列表（小）/ 哈希表（大） O(1) 存对象、用户信息
Set 整数集合（全数字）/ 哈希表 O(1) 标签、去重、共同好友
ZSet 压缩列表（小）/ 跳表+哈希表 O(log n) 排行榜、延迟队列
⚠️
为什么 ZSet 用跳表不用红黑树？

跳表实现简单，范围查询更友好，并发更好维护，平均效率和红黑树差不多。

核心原理三：缓存三大问题原理

用 Redis 最容易踩的三个坑：穿透、击穿、雪崩，每个都是不同原理。

flowchart LR A[缓存三大问题] --> B[穿透] A --> C[击穿] A --> D[雪崩] B --> B1[查不存在的数据] C --> C1[热点key过期] D --> D1[大量key同时过期] B --> B2[布隆过滤器] C --> C2[互斥锁/永不过期] D --> D2[随机过期时间]
问题 原理 现象 解决方案
缓存穿透 查一个根本不存在的数据，缓存没有，每次都打到数据库 恶意攻击，数据库被打满 布隆过滤器 / 缓存空值
缓存击穿 一个热点 key 突然过期，瞬间大量请求打到数据库 数据库瞬间 QPS 飙高 互斥锁 / 热点数据永不过期
缓存雪崩 大量 key 同时过期，或者 Redis 挂了 数据库整体扛不住 过期时间加随机值 / 集群高可用

核心原理四：持久化 RDB vs AOF

Redis 是内存数据库，挂了数据就没了，所以要持久化到磁盘。两种方式各有优劣。

flowchart TD A[Redis 持久化] --> B[RDB 快照] A --> C[AOF 日志] B --> B1[定时全量快照] B --> B2[二进制文件 体积小] B --> B3[恢复快 但可能丢数据] C --> C1[记录每个写命令] C --> C2[文本文件 体积大] C --> C3[数据更安全 恢复慢]
对比项 RDB 快照 AOF 日志
原理 定时把内存数据快照写到磁盘 每个写命令追加到日志文件
数据安全性 差，可能丢最后一次快照后的数据 好，最多丢 1 秒数据
文件体积 小，二进制压缩 大，文本命令
恢复速度 快 慢，要重放命令
适用场景 备份、容灾 数据安全性要求高
✅
生产建议

生产环境一般 RDB + AOF 同时开，RDB 做冷备，AOF 保证数据安全。

核心原理五：主从复制原理

Redis 高可用的基础是主从复制，主写从读，主节点挂了从节点顶上。

flowchart LR A[客户端] --> B{读写分离} B -->|写| C[Master 主节点] B -->|读| D[Slave 从节点1] B -->|读| E[Slave 从节点2] C -->|1. 全量同步 RDB| D C -->|2. 增量同步 replbacklog| D C -->|2. 增量同步 replbacklog| E
阶段 做什么 原理
全量同步 从节点第一次连接主节点 主节点 bgsave 生成 RDB，发给从节点加载
增量同步 同步过程中的新写命令 主节点把新命令写到 replbacklog 缓冲区，发给从节点
命令传播 后续持续同步 主节点每执行一个写命令，就发给所有从节点

新手最容易踩的坑

❌
避坑指南
  • Redis 是单线程的，别在里面执行复杂的计算，会阻塞所有请求
  • 大 key 是大坑，一个 key 存几 MB，读写都会阻塞，要拆
  • 设置过期时间，不然内存迟早被占满
  • 缓存不是银弹，不是所有数据都该放缓存，一致性要求高的别放
  • 生产环境一定要开持久化，别裸奔
