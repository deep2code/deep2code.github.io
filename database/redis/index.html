Redis 深度原理：为什么它这么快？

🏷️ Redis

「Redis 快是因为在内存里」——这句话只答对了三分之一，而且解释不了任何线上问题。真正要搞清楚的是：单线程为什么不是瓶颈、什么操作会把它卡死、内存满了先淘汰谁、fork 一次要停多久、主从切换会不会丢数据。这篇按「线程模型 → 数据结构 → 内存管理 → 持久化 → 复制与集群 → 缓存正确性」的顺序拆开，每节都给出可以直接敲的排查命令。

核心原理一：单线程模型与事件循环

Redis 的单线程不是「只有一个线程」，而是命令执行阶段只有一个线程。这个设计的收益是：所有命令天然原子、没有锁、没有上下文切换、数据结构实现可以极度激进（不用考虑并发安全）。

一次请求在事件循环里的完整路径：

正因为执行阶段串行，任何一条慢命令都会卡住整个实例。这才是 Redis 最大的风险点，也是所有「Redis 突然全部超时」事故的共同根因：

💡
io-threads 到底提升了什么

6.0 的多线程只并行 socket 读写和协议解析，命令执行仍然串行。所以它的收益场景是「value 较大、网络 IO 占比高」——此时瓶颈本来就在内核拷贝和协议解析上。如果瓶颈是 O(n) 慢命令，把 io-threads 从 1 调到 8 一点用都没有。

经验值：io-threads 设为 CPU 核数的一半左右，通常 4 足够；超过 8 基本没有额外收益。

核心原理二：底层编码与转换阈值

五种数据类型只是对外的抽象，每种在内部有两套以上的编码实现：元素少的时候用「紧凑数组」省内存，超过阈值才换成「散列/跳表」保性能。知道阈值在哪，就能算出内存并预判性能拐点。

✅
拿阈值换内存：把大 Hash 拆成小 Hash

存 100 万个用户对象，如果用 100 万个独立 key，每个 key 自带约 100 字节的元数据开销（dictEntry + robj + expires）。改成「按 id 取模分 1 万个 Hash，每个 Hash 放 100 个字段」，每个 Hash 都在 listpack 编码内，内存可以省到原来的几分之一。

这是 Redis 内存优化里性价比最高的一招，代价是失去了单个字段的过期能力（Hash 字段级 TTL 要 7.4+ 的 HEXPIRE）。

⚠️
ZSet 为什么是「跳表 + 字典」双结构

两个需求方向不同：ZSCORE key member 要按 member 查分数，这是哈希语义，O(1)；ZRANGEBYSCORE 要按分数范围扫，这是有序语义，跳表 O(log n) 定位后顺序遍历。一份结构满足不了两边，所以两份都留，member 和 score 的存储是共享的，只是索引方式不同。

至于为什么用跳表而不是红黑树：跳表的范围查询天然是「定位 + 沿最底层链表走」，不需要中序遍历；实现和调试也简单得多——这两点在工程上比理论常数更重要。

核心原理三：过期删除与内存淘汰

这是两套完全不同的机制，经常被混为一谈：过期删除处理「设了 TTL 且已到期」的 key，内存淘汰处理「内存到了 maxmemory」的紧急情况。前者是日常清理，后者是保命手段。

定期删除是抽样而非全扫，所以「已过期但还没被删」的 key 一定存在，INFO 里的 key 数量天然偏大。要精确判断内存构成，看 MEMORY STATS 而不是 DBSIZE。

maxmemory-policy 候选范围 淘汰依据 适用场景
noeviction（默认） 不淘汰 内存满后写命令返回 OOM 错误，读仍可用 当数据库用（不能丢数据），但必须有内存告警
allkeys-lru 所有 key 最久未访问 纯缓存场景的首选

volatile-ttl 仅设了 TTL 的 key 剩余 TTL 最短 希望「快过期的先走」
allkeys-random / volatile-random 对应范围 随机 访问分布均匀无热点时，比 LRU 省 CPU
❌
volatile-* 策略的致命陷阱

如果选了 volatile-lru 但所有 key 都没设 TTL，那候选集是空的——Redis 找不到可淘汰对象，行为等同 noeviction，写入直接报 OOM。这个组合在线上出现过很多次，而且从监控上看「内存满了但 evicted_keys 一直是 0」很容易被误判为淘汰失效。

纯缓存实例请直接用 allkeys-lru，不要依赖「每个 key 都记得设 TTL」这种人工纪律。

Redis 的 LRU 是近似的：真正的 LRU 需要一条全局链表，每次访问都要移动节点，内存和 CPU 都不划算。Redis 的做法是每个对象头里存 24 bit 的时钟，淘汰时随机采样 maxmemory-samples（默认 5）个 key，挑最旧的；再用一个 16 大小的淘汰池跨轮次保留候选，让结果逼近真实 LRU。

对比 近似 LRU LFU
判定依据 最后一次访问时间 访问频率（8 bit 对数计数器）
抗扫描污染 差：一次批量遍历会把冷数据全刷成「最近访问」 好：只访问一次的 key 计数器很低，照样先被淘汰
关键参数 maxmemory-samples（调大更准也更耗 CPU） lfu-log-factor 控制计数增长速度，lfu-decay-time 控制多久衰减一次
冷启动 新 key 天然最新，不会被立刻淘汰 新 key 初始计数为 5，避免刚写入就被淘汰
怎么选 访问模式平稳、无大批量扫描 有明确热点、又有定时任务全量扫库
💡
从库不会自己删过期 key

为了保证主从一致，只有主节点执行过期删除，然后把 DEL 作为命令传播给从库。所以从库上一个已过期的 key 在物理上仍然存在，只是读取时会逻辑判断 TTL 并返回 nil。

这意味着：主从延迟大的时候，从库的 DBSIZE 会明显大于主库；用 SCAN 在从库上做数据统计会统计到过期 key。要精确数据就去主库查。

❌
fork 是 Redis 最容易被忽视的停顿源

fork() 本身不复制数据，但要复制页表，耗时与实例内存量成正比。经验量级：每 1GB 内存约 10~20ms，一个 20GB 的实例 fork 一次就可能停顿 200~400ms——这期间所有请求都在排队。

# 上次 fork 耗时（微秒），持续 > 100000 就要处理了
redis-cli INFO stats | grep latest_fork_usec

# 关闭透明大页，否则 COW 的复制单位从 4KB 变成 2MB，延迟和内存双双放大
echo never > /sys/kernel/mm/transparent_hugepage/enabled

应对思路：单实例内存控制在 10GB 以内，用分片而不是堆大单机；把 bgsave 放到低峰；从库承担持久化任务，主库只管服务。

核心原理五：复制、故障切换与脑裂

复制的核心是一对标识：replication id + offset。从库带着这两个值发起 PSYNC，主库据此判断能不能只补增量——这个判断决定了是「几十毫秒的增量同步」还是「几十秒的全量 RDB 传输」。

参数 / 指标 默认值 为什么要改
repl-backlog-size 1MB 太小了。写入量大时几秒就绕圈覆盖，一次网络抖动就触发全量同步，进而 fork + 传输，雪上加霜。按「峰值写入速率 × 可容忍断连秒数」估算，通常设 64MB~256MB

Sentinel 的故障切换分四步，每步都有坑：

阶段 机制 坑
① 主观下线 SDOWN 单个 Sentinel ping 超过 down-after-milliseconds 无响应 设太小会被 GC / fork 停顿误判，引发无谓切换
② 客观下线 ODOWN 达到 quorum 个 Sentinel 都认为挂了 Sentinel 必须奇数个且 ≥3，否则无法形成多数
③ 选举 Leader Sentinel 之间跑类 Raft 选举，由 Leader 执行切换 Sentinel 部署在同一机房/同一宿主机，等于没有冗余
④ 选新主库 依次比较：slave-priority → 复制 offset 最大 → runid 最小 offset 最大的从库也可能落后主库，切换必然丢这部分写入
❌
脑裂：两个主库同时接受写入

主库 M 因为网络分区与 Sentinel 失联，但客户端仍能连到它。Sentinel 把从库 S 提为新主，此时集群里有两个主库在收写入。网络恢复后，老主 M 被降级为从库，它会清空自己的数据去全量同步新主——分区期间写入 M 的数据全部消失。

# 至少 1 个从库、且延迟不超过 10 秒，主库才接受写入
# 否则主动拒绝写，用可用性换一致性
min-replicas-to-write 1
min-replicas-max-lag 10

注意这只是缩小窗口，不是消灭。Redis 的异步复制在理论上无法做到「不丢已确认的写」——需要强一致就别把 Redis 当唯一数据源。

核心原理六：Cluster 分片与重定向

Cluster 把 key 空间切成 16384 个 slot，每个节点负责一段。路由公式是 CRC16(key) mod 16384——不是一致性哈希，是固定槽位映射，所以扩缩容时只需搬迁 slot，不用重算全局分布。

正常请求零跳转"] ASK --> ONCE["需先发 ASKING 再发命令"]
问题 答案
为什么是 16384 而不是 65536？ 节点间心跳包要携带 slot 归属 bitmap，16384 bit = 2KB，65536 则是 8KB。Cluster 的心跳很频繁，包大小直接决定了网络开销；同时 Redis 官方认为集群规模不该超过 1000 节点，16384 够用
MOVED 和 ASK 的区别？ MOVED 是「永久搬走了」，客户端应更新本地路由表；ASK 是「正在搬，这个 key 暂时在那边」，只重定向本次请求，不能更新路由表——否则迁移未完成时路由会乱
为什么 MGET k1 k2 会报 CROSSSLOT？ 多 key 命令要求所有 key 在同一 slot，否则无法在单节点原子完成。Redis 不做跨节点事务，直接拒绝
怎么让多个 key 落到同一 slot？ 用 hash tag：只对 {} 内的部分做哈希。{user:1001}:profile 和 {user:1001}:orders 必然同 slot
Lua 脚本在 Cluster 里的限制？ 脚本访问的所有 key 必须同 slot，且必须通过 KEYS[] 声明；在脚本里硬编码 key 名会导致路由错误
Cluster 和 Sentinel 怎么选？ 数据量或写入量超过单机上限才上 Cluster。数据量不大只要高可用，Sentinel 更简单——Cluster 带来的多 key 限制会污染业务代码
⚠️
hash tag 用过头会造成数据倾斜

hash tag 很好用，但如果给一大批 key 用了同一个 tag（比如所有商品都用 {product}），它们会全挤进同一个 slot、同一个节点——分片直接失效，那个节点成为热点和内存瓶颈。tag 的粒度应该是「业务上必须一起操作的最小单元」，通常是单个用户、单个订单。

核心原理七：缓存一致性与三大问题

穿透、击穿、雪崩看着像三个词，实际是三种不同的流量形态，解法完全不通用：

flowchart TB subgraph T["缓存穿透 查不存在的数据"] T1["请求 id=-1

对比 穿透 击穿 雪崩

涉及多少 key 无穷多个不存在的 key 一个热点 key 大量 key

是攻击还是自伤 常见于恶意扫描 自身热点分布导致 自身运维设计缺陷

比三大问题更常被做错的是缓存与数据库的一致性。先说结论：不存在不依赖额外机制就保证强一致的方案，只能选择「不一致窗口有多大、出现概率有多低」。

策略 做法 不一致场景 评价
先更新库，再更新缓存 两次写 并发写时两个请求的更新顺序可能交错，缓存留下旧值且长期不一致 ❌ 不要用
先删缓存，再更新库 删 + 写 删完到写完之间，读请求会把旧值重新写回缓存，长期脏 ❌ 概率不低
先更新库，再删缓存（Cache Aside） 写 + 删 只有「读请求恰好在写之前未命中、又在删之后才回填」才会脏，要求读比写慢，概率极低 ✅ 工程首选
延迟双删 删 + 写库 + 延迟几百 ms 再删 延迟时长靠猜，主从延迟超过它就失效 ⚠️ 补丁性质，不是根治
订阅 binlog 删缓存 Canal / Debezium 监听变更后删 存在毫秒到秒级延迟，但不会漏删，且业务代码无侵入 ✅ 规模化后的正解
删除失败怎么办 删缓存操作本身可能失败 缓存长期脏 必须配消息队列重试 + 兜底短 TTL
✅
为什么是「删缓存」而不是「更新缓存」

三个理由：① 删是幂等的，并发下无顺序问题，更新则会因为执行顺序交错而留下旧值；② 缓存值往往是多表聚合的结果，更新意味着在写路径上重算一遍，成本高；③ 写完未必有人读，删掉是惰性加载，能省掉大量无人访问的计算。

再加一道保险：所有缓存都设一个兜底 TTL。即使删除彻底失败，脏数据的生命周期也被限制住了——这是成本最低、覆盖面最广的一条防线。

核心原理八：分布式锁的正确写法

用 Redis 做分布式锁，网上流传的写法大多有漏洞。逐条看清每个细节在防什么：

# ❌ 错误一：分两步，setnx 成功后进程崩溃 → 锁永不释放
SETNX lock:order:123 1
EXPIRE lock:order:123 30

# ❌ 错误二：value 固定，A 超时后锁被 B 拿到，A 执行完把 B 的锁删了
SET lock:order:123 1 NX EX 30
DEL lock:order:123

# ✅ 正确：原子加锁 + 唯一 value 标识持有者
SET lock:order:123 <uuid> NX PX 30000
-- ✅ 释放必须用 Lua 保证「校验 + 删除」原子
-- 否则 GET 和 DEL 之间锁可能已过期并被他人持有
if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])
else
    return 0
end
sequenceDiagram autonumber participant A as 客户端 A participant R as Redis participant B as 客户端 B A->>R: SET lock uuid-A NX PX 30000 R-->>A: OK（持有锁） A->>A: 开始处理业务 Note over A: 业务卡了 35 秒
比如 GC 或下游超时 R->>R: 30 秒到，锁自动过期 B->>R: SET lock uuid-B NX PX 30000 R-->>B: OK（B 也拿到了锁！） Note over A,B: 此刻两个客户端同时认为自己持有锁
这是所有超时锁无法回避的窗口 A->>R: 用 Lua 校验 value 再删 R-->>A: value 是 uuid-B，不是 uuid-A → 不删 Note over A,R: 唯一 value 至少避免了误删他人的锁
但业务重复执行的问题仍需幂等兜底
细节 为什么必须这样
NX + PX 一条命令完成 加锁和设过期必须原子，分两步就存在死锁窗口
value 用 UUID 或「线程 ID + 随机数」 释放时校验持有者，避免删掉别人的锁
释放用 Lua 脚本 GET 与 DEL 之间存在时间差，必须做成一个原子操作
看门狗自动续期 业务耗时不可预测，定时续期比「把 TTL 设得很长」更安全（Redisson 默认 30 秒锁 / 10 秒续期）
业务本身必须幂等 锁只降低并发概率，不能消灭超时窗口。幂等是最后一道防线
Redlock 要不要用 它试图靠多个独立主库解决单点问题，但在时钟漂移和 GC 停顿下的正确性存在公开争议。真正需要强互斥请用 etcd / ZooKeeper 这类基于共识算法的方案
⚠️
主从架构下的锁根本不安全

复制是异步的：客户端在主库加锁成功，主库还没把这条命令同步给从库就宕机了，从库被提为新主——锁凭空消失，另一个客户端立刻能加锁成功。这不是配置问题，是异步复制的固有属性。

所以判断标准很简单：如果「同时执行两次」的后果只是重复劳动，Redis 锁完全够用；如果后果是扣两次钱，就必须靠数据库唯一约束或状态机把幂等做到存储层，而不是指望锁。

实战：大 key、热 key 与关键参数

Redis 的线上问题有一半能归结到大 key 和热 key。先说排查手段：

# 扫大 key：内部走 SCAN + 类型对应的 LEN 命令，对线上影响可控
# -i 0.1 表示每扫 100 次休眠 0.1 秒，务必带上
redis-cli --bigkeys -i 0.1

# 按内存占用维度扫（比 --bigkeys 的元素个数维度更准）
redis-cli --memkeys -i 0.1

# 热 key：需要 maxmemory-policy 设为 allkeys-lfu 或 volatile-lfu
redis-cli --hotkeys -i 0.1

# 慢命令：阈值默认 10000 微秒，生产建议降到 1000
redis-cli CONFIG SET slowlog-log-slower-than 1000
redis-cli SLOWLOG GET 10

# 延迟归因，直接给出人话结论
redis-cli --latency-history
redis-cli LATENCY DOCTOR

# 内存构成：看 dataset / overhead / fragmentation 各占多少
redis-cli MEMORY STATS
redis-cli INFO memory | grep -E 'used_memory_human|mem_fragmentation_ratio'
问题 判定标准 危害 治法
大 key（value 过大） String > 10KB，集合元素 > 5000 序列化和网络传输阻塞主线程；删除时释放内存也阻塞；集群下造成 slot 倾斜 拆分成多个小 key 或分片 Hash；删除用 UNLINK；读取用 HSCAN 分批
热 key（访问过于集中） 单 key QPS 占实例总量显著比例 单节点 CPU/网卡打满，集群下无法靠加节点缓解 本地缓存（Caffeine）挡住大部分；key 加随机后缀打散成 N 份副本
内存碎片 mem_fragmentation_ratio > 1.5 实际占用远大于数据量，触发提前淘汰 开启 activedefrag yes，或滚动重启
连接数过高 connected_clients 接近 maxclients 新连接被拒绝 检查客户端是否用了连接池、是否有连接泄漏
参数 建议值 说明
maxmemory 机器内存的 60%~70% 必须留出余量给 fork 时的 COW 和客户端缓冲，否则触发系统 OOM Killer
maxmemory-policy 缓存用 allkeys-lru 别用默认的 noeviction，更别用 volatile-* 却不设 TTL
appendfsync everysec always 的吞吐代价通常不值得
repl-backlog-size 64MB 起 默认 1MB 太小，是反复全量同步的头号原因
lazyfree-lazy-* 全部 yes 让淘汰、过期、删除都走后台线程释放内存
timeout 300 秒 默认 0 表示永不断开，泄漏的连接会一直堆积
slowlog-log-slower-than 1000 微秒 默认 10ms 太宽松，抓不到真正的慢命令
stop-writes-on-bgsave-error yes（默认） 磁盘满导致 bgsave 失败时会拒绝写入——知道这个行为，才不会在故障时一脸茫然

最容易踩的坑

❌
避坑清单
  • 在生产敲 KEYS *：O(n) 且阻塞整个实例，百万 key 就是数秒全局卡死。永远用 SCAN。
  • 用 DEL 删大 key：释放内存也在主线程做。改用 UNLINK，并开启 lazyfree-lazy-*。
  • 选了 volatile-lru 却不给 key 设 TTL：候选集为空，行为退化成 noeviction，内存满了直接报 OOM 而 evicted_keys 始终为 0。
  • repl-backlog-size 留在默认 1MB：一次网络抖动就触发全量同步，fork + RDB 传输把主库再拖一遍，形成连锁反应。
  • 把 Redis 当唯一数据源：异步复制 + 故障切换在理论上就会丢已确认的写。重要数据必须有数据库兜底。
  • 忘了关透明大页（THP）：COW 的复制单位从 4KB 变 2MB，fork 期间延迟和内存双双放大。
  • 分布式锁只写 SETNX 不设过期，或释放时不校验 value：前者死锁，后者误删别人的锁。
  • 缓存策略选「先删缓存再更新库」：读请求会把旧值写回，造成长期脏数据。用「先更新库再删缓存」+ 兜底 TTL。
  • 在 Lua 脚本里遍历大集合：脚本执行期间整实例不可用，而且无法中途打断。
  • 单实例内存堆到几十 GB：fork 耗时与内存成正比，20GB 实例一次 bgsave 可能停顿数百毫秒。要扩容请分片。
