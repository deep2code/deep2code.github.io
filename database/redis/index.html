Redis：不只是缓存

Redis 不只是缓存，是个高性能数据结构服务器。2026 年主流版本是 Redis 8.x，比 6.x 性能提升 30%+，还在 5.x 的该升级了。

flowchart TB A[Redis 能干啥] --> B[缓存] A --> C[消息队列] A --> D[计数器] A --> E[分布式锁] A --> F[排行榜] A --> G[会话存储] style A fill:#e3f2fd style B fill:#fff9c4

装一个跑起来

macOS 上最省事，Homebrew 一行命令：

brew install redis
brew services start redis

Linux 生产环境我一般源码编译，可控性强：

wget https://download.redis.io/redis-stable.tar.gz
tar -xzvf redis-stable.tar.gz
cd redis-stable
make && make install

本地调试用 Docker 最快：

docker run -d --name redis -p 6379:6379 redis:8.10

版本怎么选

我知道很多公司还在 6.x，甚至 5.x。说句实在话，6.x 已经进入维护模式了，新功能基本不加了。如果你要做新项目，直接上 8.x。如果是老系统，7.x 是个稳妥的选择。

版本状态我评价
Redis 8.x最新稳定新项目首选，性能提升明显
Redis 7.x稳定老系统升级的好选择
Redis 6.x维护中别再用了，ACL 是唯一亮点
Redis Stack 7.x稳定需要搜索/JSON/图数据库时考虑

redis-cli：最常用的工具

别看 redis-cli 简单，里面有些小技巧我用了好多年才摸透。

# 交互式终端，Tab 补全很好用
redis-cli

# 管道喂数据
redis-cli -x set mypasswd < /etc/passwd

# 循环执行，配 -i 间隔
redis-cli -r 100 -i 1 info | grep used_memory_human

# 安全扫描，不会阻塞
redis-cli --scan --pattern 'user:*'

# 远程连接
redis-cli -h 192.168.1.100 -p 6379 -a mypassword

# 选数据库
redis-cli -n 1
千万别在生产用 KEYS *

我见过有人在生产环境敲了个 KEYS *，直接把 Redis 打挂了——它要遍历所有 key，O（n）复杂度，Redis 单线程的，一个命令堵在那，后面全排队。生产环境用 --scan，增量遍历不阻塞。

可视化工具我推荐 RedisInsight，官方出的，免费，比那些收费的客户端好用。浏览器插件也有，日常看看 key、改改 TTL 够了。

五种基本数据类型

Redis 五种基本类型，每种都有它最适合的场景。我一个个说，顺便讲讲什么时候用什么。

String：最常用，也最容易被低估

# 基础操作
SET key value
GET key
MSET key1 value1 key2 value2

# 计数器，INCR 是原子的
SET count 10
INCR count        # 11
INCRBY count 5   # 16

# 过期时间
SETEX key 60 value
SET key value EX 60

# 原子设置
SETNX key value   # 不存在才设，分布式锁就是用这个

String 不只是存字符串，还能当计数器用。我做过一个全站 PV 统计，就是用 INCR page:pv:2026-09-18，QPS 两万多毫无压力。

Hash：存对象最方便

HSET user:1 name "Alice" age "25"
HGET user:1 name
HGETALL user:1
HINCRBY user:1 age 1

存用户信息这种半结构化数据，Hash 比把整个 JSON 塞 String 里强——你可以单独改某个字段，不用读出来改完再写回去。

List：做简单消息队列

LPUSH mylist "a" "b" "c"
RPOP mylist
LRANGE mylist 0 -1
# 阻塞弹出，消息队列
BLPOP mylist 0

List 做简单队列还行，但我不推荐在生产环境用它做正经消息队列。它没有 ACK 机制，消费者挂了消息就丢了。正经的还是用 Stream 或者 Kafka。

Set：去重和交并差

SADD tags "python" "redis" "golang"
SISMEMBER tags "python"    # 判断存在
SINTER set1 set2           # 交集
SUNION set1 set2           # 并集

共同好友、共同标签这种场景，Set 的交并差操作特别方便，一行命令搞定。

ZSet：排行榜的神器

ZADD leaderboard 100 "Alice"
ZADD leaderboard 200 "Bob"
ZREVRANGE leaderboard 0 -1 WITHSCORES  # 降序
ZRANK leaderboard "Alice"               # 查排名

ZSet 是我最喜欢的类型。游戏排行榜、文章热度榜、订单按金额排序，全靠它。底层用跳表实现，范围查询 O（log n），性能没话说。

Stream：正经消息队列

XADD mystream * msg "hello"
XRANGE mystream - + COUNT 10
# 消费者组
XGROUP CREATE mystream mygroup 0
XREADGROUP GROUP mygroup c1 STREAMS mystream >
XACK mystream mygroup message-id

Stream 是 Redis 5.0 加的，有消费者组、ACK、pending 队列，终于能当正经消息队列用了。我在一些中小项目里直接用 Stream 替代了 RabbitMQ，省了一个中间件。

持久化：RDB 和 AOF 怎么选

Redis 是内存数据库，但你不能假设它重启了数据就没了。持久化有两种方式，各有取舍。

flowchart TB A[持久化方式] --> B[RDB 快照] A --> C[AOF 日志] A --> D[混合模式] B --> B1[某时刻全量快照] B --> B2[恢复快但可能丢数据] C --> C1[记录每条写命令] C --> C2[数据安全但文件大] D --> D1[前半段 RDB + 后半段 AOF] D --> D2[兼顾速度和安全] style D fill:#c8e6c9
方式原理恢复速度数据安全我的建议
RDB定时全量快照快可能丢最后一次快照后的数据做备份用
AOF everysec每秒刷盘较慢最多丢 1 秒生产推荐
混合模式RDB 全量 + AOF 增量快最多丢 1 秒8.x 默认，最佳

配置就是这几行：

# RDB 快照规则
save 900 1      # 900 秒内 1 个 key 变了就存
save 300 10     # 300 秒内 10 个 key
save 60 10000   # 60 秒内 10000 个 key

# AOF
appendonly yes
appendfsync everysec

# 混合持久化（4.0+ 默认开）
aof-use-rdb-preamble yes
fork 阻塞的坑

RDB 和 AOF 重写都要 fork 子进程。fork 这个操作，在小内存实例上毫秒级就完了，但在 32GB 内存的实例上，光复制页表就要一两百毫秒——这期间 Redis 是阻塞的，所有命令排队。我之前一个 20GB 的 Redis 实例，BGSAVE 的时候监控告警延迟飙到 200ms，就是这个原因。后来把实例拆小，问题解决。

底层数据结构：Redis 为什么快

很多人以为 Redis 快就是因为数据在内存里。不全是。Java 的 HashMap 也在内存里，但性能差远了。Redis 快的关键在于它给每种数据类型设计了多种底层编码，根据数据量自动选最优的。

类型小数据时用啥大数据时用啥什么时候切换
Stringint / embstrraw（SDS）短字符串用 embstr，长了用 raw
Hashlistpack（紧凑列表）hashtable元素超过 128 个或值超过 64 字节
Setintset（整数集合）hashtable不全是整数或数量太多
ZSetlistpackskiplist + hashtable元素超过 128 个
Listquicklistquicklist3.2 以后统一用 quicklist

SDS：Redis 的字符串

Redis 不用 C 字符串，自己搞了个 SDS（Simple Dynamic String）。为啥？C 字符串拿长度要 O（n）遍历，SDS 存了个 len 字段，STRLEN 直接 O（1）。而且 SDS 记录了已分配空间，修改字符串不用每次都重新分配内存。

字典和渐进式 rehash

Redis 的哈希表扩容不是一次性搬完的。它同时维护两个哈希表 ht[0] 和 ht[1]，rehash 的时候每次操作顺便搬几个桶过去，叫渐进式 rehash。这个设计很妙——不用一次性阻塞搬几百万个 key，而是分散到平时的请求里慢慢搬。代价是查询的时候得先查 ht[0] 再查 ht[1]，稍微慢一点。

跳表：ZSet 为啥用它不用红黑树

很多人问 ZSet 为什么用跳表而不是红黑树。Redis 作者 antirez 自己说过：跳表实现简单、范围查询方便、并发友好。红黑树做范围查询要从最小节点中序遍历，跳表直接顺着上层指针跳，快得多。

集群方案

单节点扛不住了怎么办？有几条路，我帮你理清楚。

flowchart TB A[Redis 分布式方案] --> B[主从 + 哨兵] A --> C[Redis Cluster] A --> D[代理分片] B --> B1[读写分离] B --> B2[手动分 key] C --> C1[官方原生] C --> C2[16384 槽位自动分片] D --> D1[Twemproxy] D --> D2[Codis] style C fill:#c8e6c9

主从 + 哨兵：适合数据量不大、只需要读写分离的场景。主节点写，从节点读，哨兵监控主节点挂了自动切换。问题是你得自己想办法把数据分到多个主节点上。

Redis Cluster：官方原生方案，16384 个哈希槽，key 通过 CRC16(key) mod 16384 落到某个槽，槽分布在不同节点上。至少 6 个节点（3 主 3 从）才能跑起来：

# 创建集群
redis-cli --cluster create \
  127.0.0.1:7001 127.0.0.1:7002 127.0.0.1:7003 \
  127.0.0.1:7004 127.0.0.1:7005 127.0.0.1:7006 \
  --cluster-replicas 1
Cluster 不支持跨槽多 key

这是我踩过的大坑。Cluster 模式下，MGET、RENAME、事务、Lua 脚本里操作多个 key，如果这些 key 不在同一个槽，直接报错 CROSSSLOT。解决办法是用 Hash Tag：{user:1001}:profile 和 {user:1001}:orders，大括号里的内容参与哈希计算，强制落到同一个槽。

Python 客户端怎么用

Python 生态用 redis-py 就够了，别折腾别的。

import redis

r = redis.Redis(host='localhost', port=6379, decode_responses=True)

r.set('name', 'Alice')
r.get('name')
r.hset('user:1', 'name', 'Alice')
r.zadd('leaderboard', {'Alice': 100, 'Bob': 200})

生产环境一定要用连接池，别每次请求都新建连接：

from redis import ConnectionPool, Redis

pool = ConnectionPool(host='localhost', port=6379, max_connections=50)
r = Redis(connection_pool=pool)

批量操作用 pipeline，把多个命令打包一次发出去，省网络往返：

pipe = r.pipeline()
pipe.set('key1', 'value1')
pipe.incr('counter')
pipe.get('key1')
results = pipe.execute()  # 一次执行完

几个经典应用场景

缓存：最经典的用法

def get_user(user_id):
    cache_key = f'user:{user_id}'
    cached = r.get(cache_key)
    if cached:
        return json.loads(cached)
    user = db.query(f'SELECT * FROM users WHERE id = {user_id}')
    if user:
        r.setex(cache_key, 3600, json.dumps(user))
    return user

缓存更新的策略我一般选删除缓存而不是更新缓存。更新数据库之后直接 DEL 掉缓存，下次读的时候再重建。比更新缓存安全——两个并发写更新缓存容易不一致。

分布式锁

def acquire_lock(lock_name, timeout=10):
    return r.set(f'lock:{lock_name}', '1', nx=True, ex=timeout)

def release_lock(lock_name):
    r.delete(f'lock:{lock_name}')

注意这个释放锁的写法有问题——如果你拿到锁之后业务执行时间超过了 timeout，锁自动过期了，另一个人拿到了锁，这时候你释放锁就把别人的锁删了。生产环境要用 Lua 脚本做"判断是自己的锁才删"：

# 释放锁的 Lua 脚本，原子判断
UNLOCK_LUA = """
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
"""
# 加锁时存一个唯一 token，释放时验证
token = str(uuid.uuid4())
r.set(f'lock:{name}', token, nx=True, ex=10)
r.eval(UNLOCK_LUA, 1, f'lock:{name}', token)

UV 统计和排行榜

# UV 用 HyperLogLog，不占空间
r.pfadd(f'uv:page:{date}', user_id)
r.pfcount(f'uv:page:{date}')

# 排行榜用 ZSet
r.zadd('leaderboard', {user_id: score})
r.zrevrange('leaderboard', 0, 99, withscores=True)

内存淘汰策略

Redis 内存写满了怎么办？这时候 maxmemory-policy 就起作用了。我列一下，生产环境最常用的就两个：

策略行为什么时候用
noeviction不淘汰，写命令报错当作数据库用，不能丢数据
allkeys-lru所有 key 里淘汰最久没用的纯缓存场景，最推荐
volatile-lru只在设了 TTL 的 key 里淘汰部分数据要永久保留
allkeys-lfu淘汰最不常用的（4.0+）热点数据明显的场景
近似 LRU

Redis 的 LRU 不是严格的双向链表实现。它每个 key 记录一个 24 位的时间戳，淘汰的时候随机抽 5 个 key（maxmemory-samples），把最老的删掉。不是精确 LRU，但够用了，而且内存开销极小。

我踩过的八个坑

  1. Big Key：一个 String 塞了 5MB 的 JSON，删除的时候 Redis 直接阻塞了 200ms。大 key 要用 UNLINK 异步删，别用 DEL。用 redis-cli --bigkeys 定期扫
  2. 热 Key：秒杀商品的 key 打在单个节点上，CPU 100%。解决：本地缓存挡一层、或者把热 key 复制多份随机读
  3. 缓存穿透：有人故意查不存在的用户 ID，每次都打到数据库。用布隆过滤器挡，或者缓存空值（TTL 设短点，60 秒）
  4. 缓存击穿：热点 key 过期的那一瞬间，几千个请求同时打到数据库。用互斥锁重建缓存，或者逻辑过期（不设 TTL，值里存过期时间，异步更新）
  5. 缓存雪崩：几百个 key 同一秒过期。TTL 加随机偏移，比如 3600 + random(0, 300)，别让它们同时死
  6. 事务不回滚：Redis 的 MULTI/EXEC 不是真事务，中间命令失败了不会回滚。要原子性用 Lua 脚本
  7. 内存碎片：mem_fragmentation_ratio 超过 1.5 就该整理了。4.0+ 开 activedefrag yes 自动整理
  8. 主从全量同步风暴：从节点重启的时候，如果积压缓冲区不够大，会触发全量 RDB 同步。把 repl-backlog-size 调到 256MB，从节点分批重启

2026 年 Redis 生态在干啥

  • Redis 8.x：2025 年发布，吞吐量比 6.x 提升 30% 以上，内存效率也优化了
  • Redis Stack：加了搜索、JSON、图数据库、向量搜索。做 RAG 的时候有人直接拿 Redis Stack 当向量库用
  • Functions：7.4 以后推出，替代老的 Lua 脚本，性能更好，支持跨版本持久化
  • AI 结合：Redis Stack 7.5 开始探索向量搜索和 AI 应用集成，做语义缓存、会话记忆

FAQ

Redis 和 Memcached 到底选哪个？

这个问题我被问烂了。简单说：多线程纯缓存选 Memcached，数据结构丰富选 Redis。Memcached 是多线程，CPU 核心利用好，但只能存 String，没有持久化，没有集群。Redis 单线程（6.0 后网络 IO 多线程了），但数据结构丰富、有持久化、有集群。现在新项目我基本都选 Redis，Memcached 除了一些老系统维护，新项目很少用了。

Redis 单线程为什么还这么快？

三个原因：纯内存操作、IO 多路复用（epoll）、数据结构高效。单线程避免了锁竞争和上下文切换，反而成了优势。6.0 以后网络 IO 改成多线程了，但命令执行还是单线程，所以不用操心并发安全。

缓存穿透、击穿、雪崩有啥区别？

问题现象解决办法
穿透查不存在的数据，缓存挡不住，每次打 DB布隆过滤器 / 缓存空值
击穿热点 key 过期瞬间，大量请求打 DB互斥锁 / 逻辑过期
雪崩大量 key 同时过期TTL 加随机 / 多级缓存

Redis 持久化会不会影响性能？

会，但影响可控。BGSAVE fork 子进程的时候有短暂阻塞，大内存实例尤其明显。AOF everysec 的刷盘在磁盘 IO 高的时候会有延迟。我一般建议：实例内存别超过 10GB，fork 开销就很小了；关掉 THP（透明大页），那个会让 fork 变慢。

Redis Cluster 和 Codis 选哪个？

Codis 是豌豆荚出的代理分片方案，现在基本没人维护了。新项目直接上 Redis Cluster，官方原生支持，客户端都适配了。Codis 只在一些老系统里还能见到。
