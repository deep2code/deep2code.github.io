MySQL 入门：从你遇到的问题出发

🏷️ MySQL

SQL 跑好几秒，接口超时；加了索引还是慢；数据库挂了数据丢了。这篇不讲理论，就讲你做项目时会遇到的真实问题，以及 MySQL 怎么帮你解决。

flowchart LR A[查询慢] --> B[explain 分析] B --> C[加索引] C --> D[优化SQL] D --> E[分库分表]

SQL 跑好几秒，接口超时

⚠️
你遇到的问题

一个详情页接口要 3 秒，用户都走了。

怎么解决？先 explain 看执行计划，是不是没走索引，是不是全表扫描。

-- 看执行计划
EXPLAIN SELECT * FROM orders WHERE user_id = 123;
-- type 列是 ALL 就是全表扫描，要加索引

加了索引还是慢

⚠️
你遇到的问题

索引加了，结果还是慢，甚至更慢了。

怎么解决？看看是不是索引失效了，比如对索引列用了函数、类型不匹配。

# 索引失效的常见情况
1. WHERE 里对索引列用了函数
2. 类型不匹配：user_id 是 int，传了字符串
3. 模糊查询以 % 开头

explain 关键列

列 含义 怎么判断
type 访问类型 至少要 range，const/eq_ref 最好，ALL 最差
key 实际用的索引 NULL 就是没用到索引
rows 扫描行数 越少越好
Extra 额外信息 Using filesort / Using temporary 都要优化

常见索引失效场景

场景 例子 解决方案
索引列用函数 WHERE DATE(create_time) = ... 改成范围查询
类型不匹配 user_id 是 int，传了字符串 类型保持一致
% 开头模糊查询 WHERE name LIKE %张% 全文索引或搜索引擎
OR 条件 WHERE a = 1 OR b = 2 改用 UNION 或加复合索引

新手最容易踩的坑

❌
避坑指南
  • 别在索引列上用函数、计算，不然索引直接失效
  • 联合索引要遵守最左前缀原则，别乱加
  • 不是索引越多越好，索引多了写入会慢，要权衡
  • 大表不要随便加索引，会锁表，要用 online DDL 或者 pt-osc
