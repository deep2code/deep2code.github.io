MySQL 深度原理：B+树、事务、MVCC

🏷️ MySQL

很多人用 MySQL 只会写 SQL，但不知道为什么索引能加速，不知道事务隔离级别怎么实现的，也不知道 MVCC 是什么。这篇从底层原理讲透 MySQL。

flowchart TD A[MySQL 核心原理] --> B[索引 B+树] A --> C[事务 ACID] A --> D[MVCC 多版本并发] A --> E[锁机制] B --> B1[为什么用B+树不用二叉树] C --> C1[隔离级别怎么实现] D --> D1[快照读不加锁原理] E --> E1[行锁/表锁/间隙锁]

核心原理一：索引为什么用 B+ 树？

索引是 MySQL 最重要的优化手段，但为什么用 B+ 树，不用二叉树、哈希、B 树？

flowchart TD A[索引选型] --> B[哈希表] A --> C[二叉搜索树] A --> D[B 树] A --> E[B+ 树] B --> B1[O(1) 快 但不支持范围查询] C --> C1[树太高 磁盘IO多] D --> D1[所有节点都存数据 范围查询慢] E --> E1[只有叶子存数据 范围查询快 树矮]
数据结构 查找复杂度 范围查询 磁盘 IO 为什么不用
哈希表 O(1) 不支持 少 不支持范围查询、排序
二叉搜索树 O(log n) 支持 多（树太高） 树太高，磁盘 IO 次数多
B 树 O(log n) 支持 少 所有节点存数据，范围查询要中序遍历整棵树
B+ 树 O(log n) 支持 最少 只有叶子节点存数据，叶子节点用链表相连，范围查询极快
💡
为什么 B+ 树磁盘 IO 少？

B+ 树是多叉树，一个节点存很多 key，树的高度很低，几百万行数据树高也就 3-4 层，查一次只要 3-4 次磁盘 IO。

核心原理二：事务 ACID 怎么实现的？

事务的 ACID 四个特性，每个都有对应的实现机制，不是空喊口号。

flowchart TD A[ACID 四大特性] --> B[原子性 Atomicity] A --> C[一致性 Consistency] A --> D[隔离性 Isolation] A --> E[持久性 Durability] B --> B1[undo log 回滚日志] D --> D1[锁 + MVCC] E --> E1[redo log 重做日志] C --> C1[前面三个共同保证]
特性 含义 实现机制
原子性 事务要么全做，要么全不做 undo log：出错了用 undo log 回滚
一致性 事务前后数据完整性一致 原子性 + 隔离性 + 持久性共同保证
隔离性 事务之间互不干扰 锁机制 + MVCC 多版本并发控制
持久性 事务提交后永久生效 redo log：先写日志，再写磁盘，挂了可以恢复

核心原理三：MVCC 多版本并发控制

MVCC 是 MySQL 并发性能高的关键，读不加锁，读写不阻塞。

flowchart LR A[行数据] --> B[隐藏字段] B --> B1[trx_id 最近修改事务ID] B --> B2[roll_ptr 指向undo log] A --> C[Read View 读视图] C --> C1[低水位/高水位] C --> C2[活跃事务列表] B --> D{能不能看到这个版本?} D -->|能| E[返回数据] D -->|不能| F[顺着undo log找上个版本]
隔离级别 MVCC 行为 现象
读未提交 不生成 Read View 直接读最新数据，能读到未提交的
读已提交 每次 SELECT 都生成新 Read View 能看到其他事务已提交的新数据
可重复读 事务开始时生成 Read View，一直复用 整个事务里读到的数据都一样
串行化 不用 MVCC，全加锁 最严格，性能最差

核心原理四：锁机制

MySQL 的锁分很多种，理解了锁才能解决死锁问题。

flowchart TD A[MySQL 锁] --> B[粒度] A --> C[性质] B --> B1[表锁 粒度大 性能差] B --> B2[行锁 粒度小 性能好] B2 --> B21[记录锁 锁单行] B2 --> B22[间隙锁 锁范围] B2 --> B23[临键锁 锁+间隙] C --> C1[共享锁 S锁 读锁] C --> C2[排他锁 X锁 写锁]
锁类型 锁什么 什么时候加 会导致什么问题
表锁 整张表 DDL 操作、没走索引的 UPDATE 并发差，全表阻塞
记录锁 单行记录 走唯一索引的 UPDATE/DELETE 并发好，只锁一行
间隙锁 索引记录之间的间隙 范围查询，防止幻读 插入阻塞，死锁常见原因
临键锁 记录 + 前面的间隙 可重复读级别下范围查询 Next-Key Lock，防止幻读
❌
死锁怎么来的？

两个事务互相等对方的锁：事务 A 锁了行 1 等行 2，事务 B 锁了行 2 等行 1，就死锁了。间隙锁最容易导致死锁。

新手最容易踩的坑

❌
避坑指南
  • UPDATE 一定要走索引，不然会加表锁，整个表都锁住
  • 间隙锁在可重复读级别才有，别在范围查询里乱加锁
  • 长事务是大坑，占着锁不释放，其他事务都等着，尽快提交
  • 索引不是越多越好，每个索引都要占空间，还要维护成本
  • 不要在事务里做 RPC 调用，会拉长事务时间，增加死锁概率
