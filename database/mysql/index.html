MySQL 实战：从你遇到的问题出发

🏷️ MySQL 入门

你做了个用户系统，有 10 万条数据，查询越来越慢，打开一个页面要等 3 秒。你想加个索引，但又不知道怎么加才对。

或者：你凌晨 3 点被电话叫醒，说数据库磁盘满了，服务直接挂了。你还不知道怎么查慢 SQL。

这些都是每个后端开发者迟早会遇到的问题。这篇不讲理论，就讲你真的会踩的坑，以及怎么优化。

场景一：数据量一大，查询就越来越慢

你遇到的问题

你的网站从 1 万用户涨到了 100 万用户，数据库里的订单表有 500 万条数据。原来打开订单列表只要 0.1 秒，现在要 3 秒。用户都开始投诉了。

MySQL 怎么解决？加索引。但索引不是随便加的，加错了反而更慢。

# 查看慢查询：这条 SQL 为什么这么慢？
EXPLAIN SELECT * FROM orders 
WHERE user_id = 123 AND status = 'paid' 
ORDER BY create_time DESC LIMIT 10;

EXPLAIN 会告诉你 MySQL 是怎么执行这条 SQL 的，type 列如果是 ALL 就是全表扫描，必须加索引。

# 给常用查询加联合索引
ALTER TABLE orders ADD INDEX idx_user_status_time (user_id, status, create_time);
什么时候加索引为什么
WHERE 条件里的字段过滤条件，不用全表扫
JOIN 关联的字段关联的时候更快
ORDER BY 排序的字段不用临时排序
不要加太多索引写数据的时候要同步更新索引，写会变慢

场景二：凌晨 3 点被电话叫醒，说数据库挂了

你遇到的问题

你正在睡觉，突然接到运维电话："数据库磁盘满了，服务全部挂了！"你爬起来看，发现 binlog 日志占了 100G，磁盘都红了。

怎么解决？首先清理一下无用的日志，然后配置自动清理。

# 查看 binlog 大小
SHOW BINARY LOGS;

# 自动清理：只保留7天的binlog
SET GLOBAL binlog_expire_logs_seconds = 604800;

还有，慢查询一定要开，不然你都不知道哪条 SQL 有问题。

# 开启慢查询日志，超过1秒的SQL记录下来
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 1;

场景三：翻到第 100 页的时候，慢得像蜗牛

你遇到的问题

你做了个文章列表，每页 20 条。用户翻到第 100 页的时候，打开要等 5 秒。SQL 是这样的：SELECT * FROM articles ORDER BY id DESC LIMIT 2000, 20。

为什么这么慢？MySQL 要先扫描前 2000 条，然后丢掉，只取最后 20 条。翻得越深，要扫描的越多。

怎么优化？用"上次最后一条的 ID"来翻页，而不是 OFFSET。

# 不要这样：深分页很慢
SELECT * FROM articles ORDER BY id DESC LIMIT 2000, 20;

# 要这样：记住上次最后一条的ID，下一次从这里开始
SELECT * FROM articles 
WHERE id < 10000 
ORDER BY id DESC LIMIT 20;

这样不管翻到第几页，都是直接定位到那一页，速度都一样快。

场景四：并发下单，同一个用户下了 2 个重复订单

你遇到的问题

用户点了一次下单，结果网络卡了，他又点了一次。结果数据库里多了 2 个一模一样的订单。你想：怎么防止重复提交？

怎么解决？加唯一索引，数据库层面帮你挡住重复数据。

# 给订单号加唯一索引
ALTER TABLE orders ADD UNIQUE INDEX uk_order_no (order_no);

# 插入的时候如果重复，数据库直接报错，不用你自己判断

不要靠代码逻辑去判断"有没有这个订单"，并发的时候两个请求同时进来，都查了一遍发现没有，然后都插入了。唯一索引是数据库层面的，绝对不会重复。

新手最容易踩的坑
  • 不要用 SELECT *：需要哪几个字段就查哪几个，查多余的字段浪费内存和带宽。
  • 索引不是越多越好：写数据的时候要更新所有索引，加太多索引写会很慢。
  • 不要在索引字段上用函数：WHERE DATE(create_time) = '2024-01-01' 这样索引就失效了。
  • 大表不要直接 ALTER：几百万条数据的表，直接加索引会锁表，要用 online DDL 或者 pt-online-schema-change。
