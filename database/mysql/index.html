MySQL：打了十几年交道的老伙计

MySQL 这东西，我从 5.1 时代就开始用了。那时候还是 MyISAM 一统天下，InnoDB 是个冷门选项。现在反过来了——8.4 LTS 是生产首选，5.7 已经 EOL 好几年了。这篇文章把我这些年踩过的坑、调过的参、排过的障，捋一遍。

版本怎么选

先说结论：生产环境直接上 8.4 LTS，别犹豫。8.0 还能撑几年但已经过了主要开发期，9.0 是创新版别在生产用。5.7？2023 年就 EOL 了，还在跑的赶紧规划升级。

版本状态我的建议
MySQL 8.4 LTS最新 LTS，支持到 2031新项目首选，性能比 5.7 快 2-3 倍
MySQL 8.0LTS，支持到 2028老系统稳定运行中，不急着升
MySQL 9.0创新版有向量支持但还在实验阶段，别上生产
MySQL 5.7已 EOL没安全更新了，赶紧迁

装一个

macOS 上 Homebrew 最省事：

brew install mysql@8.4
brew services start mysql@8.4
mysql_secure_installation  # 安全初始化，必跑

Docker 本地开发最快：

docker run --name mysql8 \
  -e MYSQL_ROOT_PASSWORD=your_password \
  -p 3306:3306 \
  -v mysql_data:/var/lib/mysql \
  -d mysql:8.4

基本操作速查

CREATE DATABASE mydb CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;

CREATE TABLE users (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    name VARCHAR(50) NOT NULL,
    email VARCHAR(100) UNIQUE NOT NULL,
    age INT DEFAULT 0,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    INDEX idx_email (email)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

INSERT INTO users (name, email, age) VALUES ('Alice', 'a@x.com', 25);
SELECT * FROM users WHERE age > 20 ORDER BY created_at DESC LIMIT 10;
字符集一定要用 utf8mb4

老项目里用 utf8（其实是 utf8mb3）的我见太多了，存个 emoji 直接报错。8.0 默认就是 utf8mb4 了，但如果你从老库迁过来，记得检查：SHOW VARIABLES LIKE 'character_set_database';，不是 utf8mb4 的话赶紧改。

InnoDB：MySQL 的心脏

8.0 以后 MyISAM 基本可以当历史了，所有表都用 InnoDB。InnoDB 为什么快？它的内存结构和磁盘设计是关键。

Buffer Pool：最重要的配置

InnoDB 所有数据读写都走 Buffer Pool。它够大，热点数据就在内存里，查询直接命中；它太小，每次都要读磁盘，慢得像蜗牛。

我的经验法则：Buffer Pool 设成物理内存的 50%-70%，剩下的留给操作系统和连接栈。一台 32GB 内存的机器，给 Buffer Pool 20GB 左右合适。命中率应该在 99% 以上，低于这个数就得查原因了。

# my.cnf 核心配置
innodb_buffer_pool_size = 20G
innodb_buffer_pool_instances = 8  # 大内存分多个实例减少锁竞争
innodb_log_file_size = 2G
innodb_flush_log_at_trx_commit = 1  # 1 最安全，0/2 可能丢数据
innodb_flush_method = O_DIRECT  # 跳过 OS 缓存，避免双缓存
innodb_file_per_table = 1  # 每表独立 .ibd 文件

三种日志：Redo、Undo、Binlog

这三个日志搞清楚了，MySQL 的崩溃恢复和主从复制就明白了。

日志记什么干什么用谁产生的
Redo Log页的物理修改崩溃恢复，保证已提交数据不丢InnoDB 引擎层
Undo Log修改前的旧值事务回滚 + MVCC 一致性读InnoDB 引擎层
Binlog逻辑 SQL 语句主从复制 + 时间点恢复MySQL Server 层

Redo Log 是循环写的，文件就那么几个，写满了就触发 Checkpoint 把脏页刷到磁盘。我之前遇到过 Redo Log 设太小（默认 48MB），高并发写入时频繁触发 Checkpoint，性能直接腰斩。后来调到 2GB，抖动没了。

索引：MySQL 最该懂的东西

我面试候选人必问索引。答不上来 B+ 树怎么工作的、最左前缀原则是什么的，基本上技术深度就不够。

B+ 树到底长什么样

InnoDB 的索引是 B+ 树，跟 B 树的区别：非叶子节点只存键值和指针，不存数据；所有数据都在叶子节点；叶子节点之间用双向链表连起来。范围查询为什么快？因为找到起点之后顺着链表往后扫就行，不用回到根节点重新查。

聚簇索引 vs 二级索引

  • 聚簇索引（主键索引）：叶子节点直接存整行数据。一张表只有一个，数据本身就是按主键排序存储的
  • 二级索引：叶子节点存的是索引列的值 + 主键值。查到主键之后还要再去聚簇索引查一次完整行——这叫回表
  • 覆盖索引：如果查询要的列都在二级索引里，就不用回表了。这是最重要的优化手段之一

最左前缀原则

复合索引 (a, b, c) 相当于建了 (a)、(a,b)、(a,b,c) 三个索引。但如果你 WHERE b=1 或者 WHERE c=1，这个索引用不上——因为查询条件没从最左边的列开始。

EXPLAIN 是你的好朋友

SQL 慢了别急着改，先 EXPLAIN 一下。看 type 列：const > eq_ref > ref > range > index > ALL。出现 ALL 就是全表扫描，必须优化。8.0 还有 EXPLAIN ANALYZE，直接显示实际执行时间，比 EXPLAIN 的预估靠谱多了。

索引失效的常见场景

  1. 对索引列用函数：WHERE YEAR(create_time) = 2026 会让索引失效。改成 WHERE create_time >= '2026-01-01' AND create_time < '2027-01-01'
  2. 隐式类型转换：字符串列用数字查 WHERE phone = 13800138000（phone 是 VARCHAR），MySQL 会把它转成数字比较，索引就废了
  3. LIKE 左模糊：WHERE name LIKE '%zhang' 用不上索引。右模糊 'zhang%' 可以
  4. OR 连接非索引列：OR 两边只要有一个没索引，整个查询就不走索引了

事务与隔离级别

MySQL 默认隔离级别是 REPEATABLE READ（可重复读），这跟 Oracle、PostgreSQL 默认的 READ COMMITTED 不一样。很多人不知道这个差异，出了问题都找不到原因。

隔离级别脏读不可重复读幻读谁默认用
READ UNCOMMITTED可能可能可能没人用
READ COMMITTED不可能可能可能Oracle / PG
REPEATABLE READ不可能不可能基本解决MySQL 默认
SERIALIZABLE不可能不可能不可能没人用
2026 年我的建议：改成 READ COMMITTED

说真的，我现在做的新项目都把隔离级别设成 READ COMMITTED。为啥？因为 REPEATABLE READ 下有间隙锁（Gap Lock），高并发插入的时候间隙锁冲突会导致死锁。我在一个秒杀系统里被间隙锁坑过——两个事务同时往一个范围插入记录，互相等间隙锁，直接死锁了。改成 READ COMMITTED 之后，间隙锁自动关闭，死锁问题消失，性能还涨了。

MVCC 怎么实现的

InnoDB 怎么做到"读写不阻塞"的？答案是 MVCC（多版本并发控制）。每行数据后面藏了两个隐藏列：trx_id（最后修改它的事务 ID）和 roll_ptr（指向 Undo Log 里的旧版本）。

事务开始的时候生成一个 Read View（一致性视图），里面记录了当前活跃的事务列表。查询一行数据的时候，顺着 roll_ptr 往前找版本链，找到第一个在 Read View 看来"可见"的版本返回。这就是为什么 RR 级别下同一个事务里两次查询结果一致——因为 Read View 没变。

锁：间隙锁是坑最多的地方

InnoDB 的行锁不是只锁那一行，默认是 Next-Key Lock——记录本身加上它前面的间隙一起锁。这是为了防止幻读。

  • 记录锁：锁单行。WHERE id = 10 FOR UPDATE
  • 间隙锁：锁两个记录之间的间隙，不让人插入。只在 RR 级别下有
  • Next-Key Lock：记录锁 + 间隙锁，左开右闭
间隙锁导致的死锁案例

我之前在订单表上遇到过：两个事务同时执行 UPDATE ... WHERE status = 'pending' AND amount > 100，范围查询加了 Next-Key Lock。事务 A 锁了 (100, 200] 这个区间，事务 B 锁了 (200, 300]，然后 A 想插入一条 amount=250 的记录要等 B 释放间隙，B 想插入 amount=150 的要等 A 释放间隙——经典死锁。

InnoDB 检测到后回滚了一个事务。解法要么降到 RC 级别关掉间隙锁，要么业务上避免在范围查询后插入。

性能优化实战

先开慢查询日志

很多人上来就优化 SQL，但连哪条 SQL 慢都不知道。第一步永远是开慢查询日志：

SET GLOBAL slow_query_log = 'ON';
SET GLOBAL long_query_time = 1;  -- 超过 1 秒的都记下来

-- 看看最慢的几条
SELECT start_time, query_time, sql_text
FROM mysql.slow_log
ORDER BY query_time DESC LIMIT 10;

深分页怎么优化

这是我被问最多的优化题。LIMIT 1000000, 10 为什么慢？因为 MySQL 要扫描前 100 万行再扔掉，只返回 10 条。

慢的写法：

SELECT * FROM orders ORDER BY id LIMIT 1000000, 10;

快的写法——先找到上次最大的 ID，再往后翻：

SELECT * FROM orders WHERE id > 1000000 ORDER BY id LIMIT 10;

这个优化我实测过，从 2.3 秒降到 0.03 秒。前提是有自增主键或者有序的排序字段。

批量插入

-- 慢：一条一条插
INSERT INTO users (name) VALUES ('A');
INSERT INTO users (name) VALUES ('B');

-- 快：一次插 1000 条
INSERT INTO users (name) VALUES ('A'), ('B'), ('C'), ...;

批量插入比单条快 10 倍以上。原因是减少了网络往返和事务提交次数。导入数据的时候我一般每批 500-1000 条，太大了 undo log 会膨胀。

主从复制

MySQL 的高可用基本都是基于主从复制。原理很简单：主库写 Binlog，从库 IO 线程拉 Binlog 写到 Relay Log，SQL 线程重放 Relay Log。

主从延迟是最常见的问题。大事务跑 10 分钟，从库也要花 10 分钟才能追上。监控用 Seconds_Behind_Master，但这个值不太准——它只看 SQL 线程是不是追得上 IO 线程。要精确测量主从延迟用 pt-heartbeat。

高可用方案对比

方案自动切换复杂度我推荐场景
主从 + MHA✅中传统一主多从

备份：mysqldump 和 xtrabackup

备份这个事，没做过的人觉得简单，真出一次数据丢失事故你就知道重要了。

小库用 mysqldump 就够了，逻辑备份，可以看可以改：

mysqldump -u root -p --single-transaction \
  --master-data=2 --routines --triggers \
  mydb > mydb_backup.sql

大库（100GB 以上）用 mysqldump 太慢了，导出可能要几小时。这时候用 Percona 的 xtrabackup，物理备份，快而且不锁表：

xtrabackup --backup --target-dir=/backup/full --user=root
xtrabackup --prepare --target-dir=/backup/full
xtrabackup --copy-back --target-dir=/backup/full
备份了不等于能恢复

我见过太多团队只做备份不做恢复演练。备份文件存了半年，真要恢复的时候发现文件损坏、版本不兼容、或者根本不知道怎么恢复。我的习惯是每季度做一次恢复演练，恢复到测试库，跑一遍数据校验。

8.0 以后的好用新特性

很多人还停留在 5.7 的写法，其实 8.0 加了不少好东西：

窗口函数——以前要写一大堆子查询的排名，现在一行搞定：

SELECT name, department, salary,
    AVG(salary) OVER (PARTITION BY department) as dept_avg,
    RANK() OVER (PARTITION BY department ORDER BY salary DESC) as dept_rank
FROM employees;

CTE 递归查询——查树形结构不用写存储过程了：

WITH RECURSIVE tree AS (
    SELECT id, name, parent_id FROM categories WHERE id = 1
    UNION ALL
    SELECT c.id, c.name, c.parent_id FROM categories c
    JOIN tree ON c.parent_id = tree.id
)
SELECT * FROM tree;

隐藏索引——想试试删一个索引会不会影响性能，先设成 INVISIBLE，优化器就不考虑它了，确认没问题再 DROP：

ALTER TABLE users ALTER INDEX idx_name INVISIBLE;
-- 观察一段时间，没问题就真删了
DROP INDEX idx_name ON users;

MySQL 9.0 的向量支持

9.0 开始加了向量类型，实验性的。做 RAG 的人不用再纠结用不用专门的向量库了——如果数据量不大，直接在 MySQL 里做向量搜索也行：

CREATE TABLE documents (
    id INT PRIMARY KEY,
    content TEXT,
    embedding VECTOR(768)
);

CREATE VECTOR INDEX idx_vec ON documents(embedding)
USING IVFFLAT WITH (lists = 100);

SELECT id, content, vector_distance(embedding, '[0.1, 0.2, ...]') AS distance
FROM documents ORDER BY distance LIMIT 5;

但说实话，这个还是实验阶段，性能跟专门的向量库（Milvus、Qdrant）比还差得远。生产级 RAG 还是用专用方案，MySQL 向量就是玩玩。

我踩过的八个大坑

  1. 索引失效：对索引列用了函数或者隐式类型转换，EXPLAIN 一看 type 是 ALL，全表扫描。学会看执行计划是基本功
  2. 大事务：一个事务里做了十万条 UPDATE，Undo Log 膨胀了好几个 G，Purge 线程跟不上，整个实例慢得要死。大操作分批提交
  3. Redo Log 太小：默认 48MB，高并发下频繁刷脏页，性能抖动。调到 1-2GB 立刻好转
  4. Buffer Pool 命中率低：跑了个全表扫描，把热点数据全挤出去了。监控命中率，低于 99% 查原因
  5. 间隙锁死锁：前面说过了，范围查询 + 并发插入 = 死锁。降隔离级别或者改业务逻辑
  6. 连接数耗尽：应用没配连接池，每个请求新建连接，max_connections=151 很快就满了。用 HikariCP 连接池
  7. 主从延迟没监控：从库延迟了 30 秒才发现，用户刚下完单去查订单查不到，以为数据丢了。监控 Seconds_Behind_Master 设告警
  8. 没做恢复演练：备份是做了，但从来没真恢复过。真出事的时候备份文件是坏的

FAQ

MySQL 8.0 和 5.7 差在哪？

差挺多的。8.0 有窗口函数、CTE、降序索引、隐藏索引、原子 DDL（之前 DDL 中途崩溃表就坏了）、性能提升 2-3 倍。5.7 已经 EOL 了，别新项目用。

自增主键和 UUID 哪个好？

自增主键。UUID 太坑了——InnoDB 是聚簇索引，主键是顺序插入的，UUID 是随机的，每次插入都要找位置，导致页分裂频繁，写入性能差一大截。而且 UUID 占 36 字节，自增 BIGINT 才 8 字节，二级索引还会存主键，空间浪费也大。除非你需要分布式全局 ID，否则老实自增。

count(*) 为什么慢？

InnoDB 不知道自己有多少行，因为 MVCC 的存在，每个事务看到的行数不一样。所以 count(*) 要一行一行数。MyISAM 快是因为它有个计数器，但 MyISAM 不支持事务。要快速 count 用 EXPLAIN 估算，或者单独维护一个计数表。

分库分表什么时候该做？

别一开始就分。单表数据量在千万级以内，有合适的索引，MySQL 完全扛得住。真正需要分库分表的信号：单表超过 5000 万行、写入 QPS 超过 5000、单机磁盘快满了。工具用 ShardingSphere 或者 Vitess，别自己写。

MySQL 和 PostgreSQL 怎么选？

互联网公司大部分用 MySQL，生态成熟、运维资料多、云服务都支持。PostgreSQL 在复杂查询、JSON 支持、地理空间数据上更强。我个人的经验：业务系统用 MySQL，数据分析和复杂查询用 PG。两个都用也不冲突，MySQL 存业务数据，PG 做分析仓库。
