MySQL 深度原理：B+树、MVCC、加锁范围

🏷️ MySQL

很多人用 MySQL 只会写 SQL，但不知道为什么索引能加速，不知道事务隔离级别怎么实现的，也不知道 MVCC 是什么。这篇从 InnoDB 的磁盘页布局讲到加锁范围推演，中间穿插真实的参数数值和排查命令——目标是让你下次线上出现「锁等待超时」「慢查询突然飙升」时，知道该敲哪条命令、看哪个数字。

先建立全局地图。InnoDB 不是一坨黑盒，它是「内存层 + 日志层 + 磁盘层」三段结构，所有性能问题最终都能归因到其中某一段：

核心原理一：B+ 树凭什么 3 层就装下两千万行

「索引用 B+ 树」是背答案，真正要会算的是：一棵 3 层 B+ 树到底能放多少行、查一行要几次 IO。这个数字是后面所有索引决策的基础。

InnoDB 的磁盘和内存交换单位是页（page），默认 16KB（innodb_page_size）。非叶子节点里不存数据，只存「索引键 + 子页号」，子页号固定 6 字节。以 BIGINT 主键（8 字节）为例：

常驻 Buffer Pool
约 1170 个键"] R --> N1["中间页 A
约 1170 个键"] R --> N2["中间页 B"] R --> N3["...共约 1170 个"] N1 --> L1["叶子页 1
约 16 行完整数据"] N1 --> L2["叶子页 2"] N2 --> L3["叶子页 3"] N3 --> L4["叶子页 N"] L1 <-->|双向链表| L2 L2 <-->|双向链表| L3 L3 <-->|双向链表| L4
层级 每页能放多少 计算过程 累计容量
非叶子页 ≈ 1170 个键 16384 B ÷（8 B 主键 + 6 B 页号）≈ 1170 —
叶子页 ≈ 16 行 16384 B ÷ 1KB 单行 ≈ 16 —
树高 2 根 + 叶子 1170 × 16 约 1.87 万行
树高 3 根 + 中间 + 叶子 1170 × 1170 × 16 约 2190 万行
树高 4 再加一层 1170³ × 16 约 256 亿行
💡
这个数字的真正用法

树高 3 意味着主键等值查询最多 3 次页访问，而根页和大部分中间页常驻 Buffer Pool，所以实际磁盘 IO 往往只有 0～1 次。反过来说：如果单表几百万行、主键查询还慢，问题一定不在树高，去查 Buffer Pool 命中率、锁等待或网络，而不是继续「优化索引」。

另一个推论：单行越大，叶子页装的行越少，树就越容易长高。把 TEXT/大 JSON 字段拆到副表，等价于给主表降树高。

再看为什么不选其他结构。关键不是复杂度好看，而是磁盘的代价模型：随机 IO 比顺序 IO 贵两个数量级，所以目标是「少访问页 + 尽量顺序访问」。

数据结构 等值查询 范围 / ORDER BY 百万行树高 为什么 InnoDB 不选它
哈希表 O(1)，最快 不支持 — 无序，范围查询、排序、最左前缀全废；扩容 rehash 抖动大
二叉搜索树 / 红黑树 O(log₂n) 支持但慢 约 20 层 每层一次页访问，20 次随机 IO；为内存设计，不是为磁盘设计
跳表 O(log n) 支持 层数随机 节点分散、指针多，磁盘局部性差（Redis 在内存里用它，所以合适）
B 树 O(log₁₁₇₀n) 支持但要中序遍历 3～4 层 非叶子节点也存行数据 → 扇出骤降 → 树变高；范围扫描要反复上下穿层
B+ 树 O(log₁₁₇₀n) 叶子双向链表顺序扫 3 层 / 2190 万行 非叶子只存键 → 扇出最大；叶子串成链表 → 范围查询变顺序 IO
LSM Tree 需查多层 + 布隆过滤 支持 — 写放大低、读放大高，适合写多读少（RocksDB / HBase 选它）

核心原理二：聚簇索引、回表与覆盖索引

InnoDB 的表本身就是一棵 B+ 树（聚簇索引），主键就是它的排序键，行数据直接放在叶子页。二级索引是另一棵树，叶子页存的不是行，而是主键值。理解这一点，回表、覆盖索引、主键该用什么类型，全部一目了然。

name, age, city 完整行"] end subgraph SI["二级索引 idx_name"] S1["叶子: name='张三'
→ id=100"] end Q1["SELECT * WHERE name='张三'"] --> S1 S1 -->|拿到 id=100 再查一次主键树
这一步叫回表| C1 C1 --> R1["返回完整行"] Q2["SELECT id,name WHERE name='张三'"] --> S2["idx_name 叶子已含 name 和 id"] S2 -->|字段都在索引里 不回表
Using index| R2["直接返回"]

回表的代价是「再走一次 3 层树」。所以一条二级索引范围查询命中 1000 行，最坏是 1000 次回表——这就是为什么「索引走了但还是慢」。

-- 建一张演示表
CREATE TABLE `orders` (
  `id`       BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `user_id`  BIGINT UNSIGNED NOT NULL,
  `status`   TINYINT NOT NULL,
  `amount`   DECIMAL(12,2) NOT NULL,
  `city`     VARCHAR(32) NOT NULL,
  `created_at` DATETIME NOT NULL,
  PRIMARY KEY (`id`),
  KEY `idx_user_status_created` (`user_id`, `status`, `created_at`)
) ENGINE=InnoDB;

-- 回表版本：走索引定位，但 amount 不在索引里，每行都要回表
EXPLAIN SELECT amount FROM orders
 WHERE user_id = 42 AND status = 1;
-- type=ref  key=idx_user_status_created  Extra=NULL

-- 覆盖索引版本：把 amount 塞进索引末尾，彻底消掉回表
ALTER TABLE orders
  DROP INDEX idx_user_status_created,
  ADD  INDEX idx_cover (user_id, status, created_at, amount);

EXPLAIN SELECT amount FROM orders
 WHERE user_id = 42 AND status = 1;
-- type=ref  key=idx_cover  Extra=Using index   ← 关键就是这个 Using index

联合索引 (a, b, c) 的有序性是「先按 a 排，a 相同按 b 排，b 相同按 c 排」，所以只能从最左开始连续使用。下表把最左前缀的判定规则穷举清楚：

查询条件（索引为 user_id, status, created_at） 能用到几列 原因
user_id=1 AND status=1 AND created_at>'...' 3 列 前两列等值定位，第三列范围收尾，最理想
user_id=1 AND created_at>'...' 1 列 + 索引内过滤 跳过 status，created_at 只能做 ICP 过滤（Using index condition），不能定位
status=1 AND created_at>'...' 0 列 缺最左列 user_id，整棵树无序，只能全表扫
user_id>10 AND status=1 1 列 第一列就是范围，范围之后的列失去有序性
user_id=1 ORDER BY status, created_at 3 列 索引天然有序，省掉 Using filesort
user_id=1 ORDER BY created_at 1 列 + filesort 跳过 status，排序列不连续，要额外排序
user_id IN (1,2,3) AND status=1 2 列 IN 会被拆成多段 range，每段仍能用后续列
⚠️
主键类型选错，代价是全局的

二级索引叶子存的是主键值，所以主键越大，每一棵二级索引都跟着变大。用 CHAR(36) UUID 做主键：36 字节 vs BIGINT 8 字节，5 棵二级索引就意味着索引空间多出数倍。

更致命的是 UUID 无序：聚簇索引要求按主键顺序插入，随机主键会让新行插到已满页的中间，触发页分裂——顺序写退化成随机写，页利用率从 ~94% 掉到 ~50%。业务需要 UUID 就单独建列加唯一索引，主键仍用自增或有序 ID（雪花 / UUIDv7）。

核心原理三：Buffer Pool 凭什么能挡住 99% 的磁盘 IO

所有读写都先落在 Buffer Pool 上，命中率决定了整个实例的性能天花板。它不是普通 LRU，而是分段 LRU：整条链表按 innodb_old_blocks_pct（默认 37）切成 young 区和 old 区。

flowchart LR NEW["新读入的页"] -->|插到 midpoint
而不是链表头| MID["old 区头部
约占 37%"] MID -->|1 秒后再被访问
innodb_old_blocks_time| YOUNG["晋升到 young 区
约占 63%"] YOUNG -->|再次命中| YOUNG MID -->|1 秒内不再访问| EVICT["从尾部淘汰"] YOUNG -->|长期不访问 逐步后移| MID

为什么要搞这么复杂？因为一次 SELECT * FROM big_table 全表扫描会读入海量只用一次的页。如果用朴素 LRU，这些页会全部涌进链表头，把真正的热点页挤出去——命中率瞬间崩塌，业务集体变慢。midpoint 插入 + 1 秒停留门槛，恰好让「只扫一遍」的页进不了 young 区。

-- 命中率：目标 ≥ 99%，长期低于 95% 说明内存不够或有大扫描
SELECT
  (1 - (
    SELECT VARIABLE_VALUE FROM performance_schema.global_status
     WHERE VARIABLE_NAME='Innodb_buffer_pool_reads'
  ) / (
    SELECT VARIABLE_VALUE FROM performance_schema.global_status
     WHERE VARIABLE_NAME='Innodb_buffer_pool_read_requests'
  )) * 100 AS hit_rate_pct;

-- 脏页比例：持续 > 75% 说明刷盘跟不上写入，要调 innodb_io_capacity
SHOW STATUS LIKE 'Innodb_buffer_pool_pages_dirty';
SHOW STATUS LIKE 'Innodb_buffer_pool_pages_total';
内存组件 作用 什么时候是瓶颈 怎么调
Buffer Pool 缓存数据页 / 索引页，读写都先过它 命中率 < 95%，磁盘 IOPS 打满 innodb_buffer_pool_size 设为物理内存 50%~70%
Change Buffer 非唯一二级索引的写操作先缓存，之后合并，把随机写攒成批量 写多读少、二级索引多时收益最大；读多时反而浪费内存 innodb_change_buffer_max_size（默认 25%）
Log Buffer redo log 的内存缓冲 Innodb_log_waits > 0 表示不够用 增大 innodb_log_buffer_size
Doublewrite Buffer 脏页先顺序写到一块共享区域再写回原位，防「页断裂」 写入放大 2 倍（但是顺序写，代价可接受） 存储自带原子写才考虑关闭，否则别动
❌
Change Buffer 的隐藏前提

它只对非唯一二级索引生效。唯一索引插入必须立刻读页判重，没法延迟，所以「给字段加个唯一索引保险一点」在写密集场景是实打实的性能损失——它把可以攒批的随机写，变成了每次都必须读盘。

核心原理四：三大日志与两阶段提交

ACID 不是口号，每个字母都对应一个具体机制。先把三个容易混的日志分清楚——它们的归属层、物理/逻辑性质、用途完全不同：

对比项 redo log undo log binlog
归属 InnoDB 引擎层 InnoDB 引擎层 MySQL Server 层
内容性质 物理日志：「某页某偏移改成什么」 逻辑反操作：「插入的反向是删除」 逻辑日志：SQL 或行变更事件
写入方式 循环写，空间固定会覆盖 写到 undo 表空间，事务结束后由 purge 线程回收 追加写，文件写满切下一个，永不覆盖
保证什么 持久性 D：崩溃恢复 原子性 A + MVCC 版本链 主从复制、按时间点恢复
关键参数 innodb_flush_log_at_trx_commit innodb_undo_log_truncate sync_binlog、binlog_format
没它会怎样 宕机丢已提交事务 回滚失效、快照读读不到旧版本 无法搭从库、无法误删恢复

redo 的核心思想是 WAL（Write-Ahead Logging）：改数据页时只在内存里改 + 顺序写一条 redo，脏页之后慢慢刷。提交一个事务的开销从「随机写数据页」变成「顺序写日志」，这是 InnoDB 写性能的根。

但 redo（引擎层）和 binlog（Server 层）是两个独立的日志，必须保证「要么都生效，要么都不生效」，否则主库和从库的数据会分叉。解决方案就是两阶段提交：

sequenceDiagram autonumber participant C as 客户端 participant S as Server 层 participant I as InnoDB participant R as redo log participant B as binlog C->>S: COMMIT S->>I: 准备提交 I->>R: 写 redo，标记 prepare R-->>I: 落盘完成 Note over I,R: 阶段一 Prepare
此刻崩溃：binlog 没有 → 回滚 I-->>S: prepare ok S->>B: 写 binlog 并落盘 B-->>S: 落盘完成 Note over S,B: 这是提交的分界点
binlog 写成功即视为事务成功 S->>I: 提交 I->>R: 写 redo，标记 commit Note over I,R: 阶段二 Commit
此刻崩溃：binlog 完整 → 恢复时补提交 I-->>S: ok S-->>C: 提交成功

崩溃恢复时，InnoDB 扫描 redo，对每个处于 prepare 状态的事务去查 binlog 里有没有对应的完整记录：有就提交，没有就回滚。这条规则保证了两份日志的一致性。

参数组合 含义 宕机风险 性能 用在哪

核心原理五：MVCC 的可见性判定算法

MVCC 让「读」不用加锁：读事务顺着 undo log 版本链往回找，找到一个自己「有权看见」的版本。问题是——凭什么判定有权看见？这套判定只有 4 条规则，背下来就能自己推演任何并发场景。

每行有三个隐藏字段，版本链就是靠 roll_pointer 串起来的：

Read View 字段 含义 易错点
m_ids 创建快照瞬间所有活跃（未提交）事务的 ID 列表 只读事务不分配真实 trx_id，不会进这个列表
min_trx_id m_ids 里的最小值，低水位 不是「最早的事务」，而是最早的未提交事务
max_trx_id 下一个将被分配的事务 ID，高水位 是「将要分配」，不是「当前最大」，所以判定用 >=
creator_trx_id 创建这个 Read View 的事务自己的 ID 自己改的数据自己一定看得见

RR 和 RC 的全部差别，只是什么时候生成 Read View。下面这个时序把差别演到明面上：

sequenceDiagram autonumber participant A as 事务 A（查询方） participant DB as InnoDB participant B as 事务 B（修改方） A->>DB: BEGIN Note over A: 注意：BEGIN 不生成快照 A->>DB: SELECT amount → 100 Note over A,DB: 第一次快照读，此刻才生成 Read View B->>DB: BEGIN B->>DB: UPDATE amount = 300 B->>DB: COMMIT A->>DB: SELECT amount Note over A,DB: RR：复用旧 Read View → 仍是 100

这就是「幻读」的观感来源
⚠️
快照读 vs 当前读：所有并发 bug 的分水岭

快照读（普通 SELECT）走 MVCC 读历史版本，不加锁。当前读（UPDATE/DELETE/INSERT/SELECT ... FOR UPDATE/LOCK IN SHARE MODE）必须读最新已提交版本并加锁。

这就是「先查再改」经典 bug 的根源：SELECT stock 读到快照的 10，接着 UPDATE stock = 9 却基于最新值算——超卖就这么来的。正确写法是把判断塞进 UPDATE 里让数据库原子完成：UPDATE t SET stock = stock - 1 WHERE id = ? AND stock > 0，然后检查 affected_rows。

隔离级别 Read View 时机 脏读 不可重复读 幻读 代价
READ UNCOMMITTED 不生成，直接读最新 会 会 会 几乎无隔离，生产禁用
READ COMMITTED 每条语句生成一个 不会 会 会 无间隙锁，死锁概率低，主流互联网默认选它
REPEATABLE READ（MySQL 默认） 首次快照读生成，全事务复用 不会 不会 快照读不会，当前读靠间隙锁挡 间隙锁带来更多锁冲突和死锁
SERIALIZABLE 不用 MVCC，读也加共享锁 不会 不会 不会 并发退化为串行，只在极特殊场景用
❌
长事务：undo 撑爆磁盘的元凶

purge 线程只能清理「不再被任何 Read View 需要」的 undo 版本。一个开着不提交的 RR 事务，会让它之后所有版本都无法回收——undo 表空间持续膨胀，版本链越来越长，连别的事务的快照读都要顺着长链回溯，整库变慢。

-- 揪出跑了超过 60 秒的事务
SELECT trx_id, trx_state, trx_started,
       TIMESTAMPDIFF(SECOND, trx_started, NOW()) AS run_sec,
       trx_rows_locked, trx_query
  FROM information_schema.innodb_trx
 WHERE TIMESTAMPDIFF(SECOND, trx_started, NOW()) > 60
 ORDER BY run_sec DESC;

核心原理六：加锁范围推演与死锁复盘

行锁的真相：InnoDB 锁的是索引，不是行。这一句能解释 90% 的诡异锁冲突——包括「我明明只改一行，为什么别人插不进去」。

flowchart TD A["InnoDB 锁"] --> B["表级"] A --> C["行级 锁在索引上"] B --> B1["MDL 元数据锁
DDL 与 DML 互斥"] B --> B2["意向锁 IS/IX
表级标记 加速表锁判定"] B --> B3["AUTO-INC 锁
自增主键分配"] C --> C1["Record Lock

Record + 前面的 Gap
左开右闭"] C --> C4["Insert Intention Lock
插入意向锁 与 Gap 冲突"] C3 -->|RR 下的默认形态
用来挡幻读| C2 C2 -->|RC 下没有间隙锁| D["所以 RC 死锁少得多"]

Next-Key Lock 是「左开右闭」区间。假设表里 id 有 5、10、15、20 五条记录，那么索引被切成这些区间：(-∞,5] (5,10] (10,15] (15,20] (20,+∞)。加锁规则就是在这些区间上做文章：

SQL（RR 级别，id 为主键） 实际锁定范围 别人能插入 12 吗 规则
WHERE id = 10 FOR UPDATE 仅记录 10 能 唯一索引等值命中 → Next-Key 退化为 Record Lock
WHERE id = 12 FOR UPDATE 间隙 (10,15) 不能 唯一索引等值未命中 → Next-Key 退化为 Gap Lock
WHERE id >= 10 FOR UPDATE 记录 10 + (10,15] + (15,20] + (20,+∞) 不能 范围查询逐个加 Next-Key，一直扫到第一个不满足的记录
WHERE id > 10 AND id < 15 FOR UPDATE (10,15] 不能 右边界虽不满足条件，但已被扫描到，仍加锁
WHERE status = 1 FOR UPDATE（无索引） 所有记录 + 所有间隙 不能 全表扫描，每条都加 Next-Key，效果等同锁表（但它不是表锁）
同上，改为 RC 级别 所有记录（无间隙锁） 能 RC 不加 Gap Lock，且不匹配的行会提前释放锁
⚠️
「没走索引就升级成表锁」是流传最广的错误说法

InnoDB 不会把行锁升级为表锁。真实情况是：没有索引可用时全表扫描，扫过的每一行都加 Next-Key Lock，结果在业务上看起来像锁表。区别很重要——它意味着解法是「让 SQL 走上索引」，而不是「换引擎」或「调锁粒度参数」。

顺带一提：RC 下未匹配的行锁会在语句结束前提前释放，RR 下要持有到事务结束。这是 RC 死锁率明显更低的第二个原因。

死锁的成因只有一个：两个事务以相反顺序获取同一组锁。最常见的不是教科书里的「A锁1等2、B锁2等1」，而是下面这种「唯一索引冲突 + 间隙锁」的组合，很多人踩了都不知道自己踩了什么：

sequenceDiagram autonumber participant A as 事务 A participant DB as InnoDB participant B as 事务 B A->>DB: BEGIN B->>DB: BEGIN A->>DB: SELECT * FROM t WHERE id=12 FOR UPDATE Note over A,DB: 12 不存在 → A 持有间隙锁 (10,15) B->>DB: SELECT * FROM t WHERE id=13 FOR UPDATE Note over B,DB: 13 也在同一间隙 → B 也拿到 (10,15)
间隙锁之间不冲突！这是关键陷阱 A->>DB: INSERT INTO t VALUES(12, ...) Note over A,DB: 插入意向锁与 B 的间隙锁冲突 → A 阻塞 B->>DB: INSERT INTO t VALUES(13, ...) Note over B,DB: 插入意向锁与 A 的间隙锁冲突 → B 阻塞 DB-->>B: Deadlock found when trying to get lock Note over DB: 死锁检测发现环，回滚代价较小的一方 A->>DB: 插入成功，COMMIT 
-- 死锁现场取证三件套
SHOW ENGINE INNODB STATUS\G          -- 看 LATEST DETECTED DEADLOCK 段

-- 谁在等谁（MySQL 8.0）
SELECT r.trx_id AS waiting_trx, r.trx_query AS waiting_query,
       b.trx_id AS blocking_trx, b.trx_query AS blocking_query,
       b.trx_mysql_thread_id AS blocking_thread
  FROM performance_schema.data_lock_waits w
  JOIN information_schema.innodb_trx r ON r.trx_id = w.requesting_engine_transaction_id
  JOIN information_schema.innodb_trx b ON b.trx_id = w.blocking_engine_transaction_id;

死锁场景 根因 修法
批量更新一批 ID，两个任务顺序不同 加锁顺序相反 更新前对 ID 排序，全局统一升序加锁
INSERT ... ON DUPLICATE KEY UPDATE 高并发 唯一索引冲突检测 + 插入意向锁 降到 RC，或改为先查后插并用重试兜底
先 SELECT ... FOR UPDATE 再 INSERT 间隙锁不互斥，插入意向锁互斥 直接 INSERT 靠唯一索引捕获重复，别用「先查再插」占位
两张表更新顺序不一致 跨表加锁顺序相反 约定全项目统一的表操作顺序（如按表名字母序）
DDL 期间业务全部卡死 MDL 写锁排在长事务后面，后续所有请求排它后面 改表前先清长事务，加 ALTER TABLE ... , ALGORITHM=INPLACE, LOCK=NONE 或用 gh-ost
💡
死锁不可能彻底消灭，要设计成可重试

innodb_deadlock_detect 默认开启，检测到环立刻回滚代价小的事务，报 ER_LOCK_DEADLOCK (1213)。这是秒级返回的正常错误，不是故障。而 innodb_lock_wait_timeout（默认 50 秒）管的是「等不到锁」，是另一回事——生产环境通常调到 5～10 秒，避免一次锁等待把连接池拖垮。

应用层要区别对待：1213 直接重试（幂等前提下），1205（等锁超时）则说明有慢事务，重试往往无效，该去抓长事务。

核心原理七：EXPLAIN 怎么读，索引为什么失效

慢查询优化的全部起点是 EXPLAIN。只需重点看三列：type（访问方式）、key（真实用了哪个索引）、Extra（有没有额外开销）。

type（由好到差） 含义 可接受吗
system / const 主键或唯一索引等值，最多一行 最优
eq_ref join 时被驱动表走唯一索引，每行匹配一条 很好
ref 走非唯一索引等值，匹配多行 正常线上目标
range 索引范围扫描（>、BETWEEN、IN） 可接受，关注 rows 数量
index 扫完整棵索引树 危险，除非配合 Using index 且表小
ALL 全表扫描 大表上必须消灭
Extra 内容 说明 是好事还是坏事
Using index 覆盖索引，不回表 ✅ 追求的目标
Using index condition 索引下推 ICP，在引擎层就过滤掉不匹配行，减少回表 ✅ 比回表后再过滤好
Using where Server 层还要再过滤一遍 ⚠️ 结合 rows 判断过滤效率
Using filesort 无法用索引有序性，需额外排序 ❌ 大结果集会用磁盘临时文件
Using temporary 需要临时表，常见于 GROUP BY 列无索引 ❌ 最该优先消灭的
Using join buffer join 没有可用索引，退化为 BNL ❌ 给被驱动表的关联列加索引

索引失效的场景几乎全部可以归到「对列做了变形，导致有序性被破坏」这一条原理下：

失效写法 为什么失效 改法
WHERE DATE(created_at) = '2026-09-22' 函数作用在索引列上，索引存的是原值不是函数值 created_at >= '2026-09-22' AND created_at < '2026-09-23'
WHERE amount * 100 > 5000 同上，运算破坏有序性 把运算移到右边：amount > 50
WHERE phone = 13800138000（phone 是 varchar） 隐式类型转换，等价于 CAST(phone AS ...)，函数作用在列上 参数加引号：phone = '13800138000'
WHERE name LIKE '%三' 左模糊无法定位前缀 改右模糊，或上全文索引 / ES
WHERE a = 1 OR b = 2（b 无索引） OR 任一侧无索引，整体只能全表扫 两边都建索引（可走 index merge），或拆成 UNION ALL
join 两表字符集不同 关联列字符集/校对规则不一致会触发隐式转换 统一为 utf8mb4 同一 collation
WHERE status = 1（只有两种取值） 区分度太低，优化器算出回表成本高于全表扫，主动放弃索引 不是 bug；做成联合索引的一部分或改用覆盖索引
统计信息过期导致选错索引 大量增删后 cardinality 失真 ANALYZE TABLE t; 必要时 FORCE INDEX 兜底

实战：深分页与生产参数基线

LIMIT 1000000, 10 的真实行为是：取出 1000010 行，丢掉前 1000000 行。偏移量越大越慢，而且是线性变慢。

-- ❌ 硬翻页：扫 100 万行 + 100 万次回表
SELECT * FROM orders ORDER BY id LIMIT 1000000, 10;

-- ✅ 方案一 游标定位法：把 offset 换成 where，恒定耗时（要求排序列唯一有序）
SELECT * FROM orders WHERE id > 1000000 ORDER BY id LIMIT 10;

-- ✅ 方案二 延迟关联：先在覆盖索引里翻页拿主键，只回表 10 次
SELECT o.* FROM orders o
  JOIN (SELECT id FROM orders ORDER BY id LIMIT 1000000, 10) t
    ON o.id = t.id;
💡
游标法的适用边界

游标定位法要求「排序列唯一且有序」，所以它只能做「下一页」，做不了「跳到第 500 页」。如果产品必须支持随机跳页，就用延迟关联；如果只是 App 的无限下拉，游标法是唯一正确答案——顺带还能避免翻页过程中插入新数据导致的重复/漏数据。

参数 建议值 作用 调错的后果
innodb_buffer_pool_size 物理内存 50%~70% 数据页缓存总量，第一性能参数 太小命中率崩；太大触发 OOM 或 swap
innodb_buffer_pool_instances 8（pool ≥ 8G 时） 拆多个实例减少内部互斥争抢 单实例在高并发下 mutex 成瓶颈
innodb_flush_log_at_trx_commit 1 redo 落盘策略 设 0/2 在宕机时丢事务
sync_binlog 1 binlog 落盘策略 配合上一项才是「双 1」，缺一不可
innodb_io_capacity SSD 建议 2000+ 后台刷脏页速率上限 设太低脏页堆积，突发写入时剧烈抖动
innodb_flush_neighbors SSD 设 0 刷脏页时是否连带刷相邻页 SSD 上开着纯属浪费 IO（机械盘才有收益）
innodb_lock_wait_timeout 5~10（默认 50） 等行锁的超时 50 秒太长，一次锁等待就打满连接池

最容易踩的坑

❌
避坑清单
  • 事务里做 RPC / 发消息 / 调第三方：网络抖动直接变成锁持有时间，是线上死锁和锁等待超时的头号原因。事务只包数据库操作，外部调用挪到提交之后。
  • UPDATE / DELETE 的 WHERE 没走索引：不是「升级成表锁」，而是扫过的每一行每个间隙都加锁，效果一样致命。改表前先 EXPLAIN 一遍。
  • 用 UUID 当主键：二级索引全体变胖，随机插入引发页分裂，顺序写退化成随机写。要用就单独建唯一索引列。
  • 字符串条件不加引号：phone = 13800138000 触发隐式转换，索引直接失效，而且不报错——只是悄悄变慢。
  • DDL 撞上长事务：MDL 写锁拿不到，之后所有对该表的请求全部排在它后面，几秒内打满连接池。大表改结构一律走 gh-ost / pt-osc。
  • 以为「加了索引就快」：索引走了但回表 10 万次照样慢。覆盖索引（Using index）才是终局答案。
  • 索引建太多：每个二级索引都要在写入时同步维护，写放大是实打实的。上线前用 sys.schema_unused_indexes 清掉从来没被用过的索引。
  • 用 SELECT COUNT(*) 算总数做分页：InnoDB 不存行数，大表上每次都要扫索引。改成估算值或维护计数表。
