PostgreSQL 索引选型与执行计划判读：GIN、BRIN、部分索引与 EXPLAIN

🏷️ PG 索引优化

PG 的索引能力远超「B-tree 加几个技巧」：五种索引类型对应五种完全不同的数据形态，加上部分索引、表达式索引和 INCLUDE 覆盖列，很多在 MySQL 上只能靠改表结构解决的问题在 PG 上是一行 DDL。但索引选对了不等于计划走对了，所以后半篇全部用来讲 EXPLAIN (ANALYZE, BUFFERS) 怎么读、优化器为什么不走你建的索引。

💡
这篇怎么读
  • ① 用法：拿到一条慢 SQL 之后的判读顺序——EXPLAIN (ANALYZE, BUFFERS) 只看哪三处、估行数与实际行数差多少才算统计信息问题、什么时候该建索引什么时候该改 SQL，配一张「查询形态 → 索引类型」对照表与影响索引选择的参数速查。
  • ② 原理：五种索引类型各自实现的操作符类与失效条件、部分索引与表达式索引与 INCLUDE 的前提、计划里每个字段的语义、四种扫描方式与 Bitmap 的两步结构、三种 join 与 work_mem 的分配单位、优化器不走索引的九种成因与修法、索引运维的四类巡检 SQL。
  • ③ 场景：按业务形态给出索引组合与代价矩阵，以及哪些问题不该靠索引解决、该转去站内哪一篇。

① 用法 · 拿到一条慢 SQL 之后的判读顺序

顺序是固定的，跳步就会得出错误结论：先确认这条语句值得优化，再判断统计信息可不可信，最后才决定是建索引还是改 SQL。下面这段可以直接照着敲，注释写的是为什么要这一步。

-- 第 0 步：先确认这条语句值得优化。按总耗时排序，不是按单次耗时排序
--   调用量大而单次不慢的语句，优化收益往往远高于那条偶发的慢查询
SELECT calls,
       round(total_exec_time)    AS 总耗时ms,
       round(mean_exec_time, 2)  AS 平均ms,
       rows / greatest(calls, 1) AS 每次返回行数,
       left(query, 80)           AS 语句
FROM   pg_stat_statements
ORDER  BY total_exec_time DESC
LIMIT  10;

-- 第 1 步：永远带 ANALYZE 与 BUFFERS。不带 ANALYZE 只有估算值，看不出优化器估错了；
--   不带 BUFFERS 分不清是内存命中还是真的读盘。ANALYZE 会真实执行，写语句必须包在事务里回滚
BEGIN;
EXPLAIN (ANALYZE, BUFFERS, SETTINGS) <把你要判读的语句放这里>;
ROLLBACK;

-- 第 2 步：只看三处，顺序不要乱（每一处的判定标准见下表）
--   a) 最内层节点的 rows 估算值 与 actual rows 的比值
--   b) 每个节点的 loops，因为 actual rows 与 actual time 都是「单次平均值」
--   c) Buffers 的 read 与 hit 比例，以及有没有 temp 的读写量

-- 第 3 步：统计信息可疑就先修统计信息，别急着改 SQL 也别急着建索引
ANALYZE orders;                                                -- 大量「选错计划」到这一步就结束了
ALTER TABLE orders ALTER COLUMN status SET STATISTICS 1000;     -- 单列取值倾斜，直方图精度不够
CREATE STATISTICS st_orders_city_zip (dependencies, ndistinct)  -- 多列强相关，选择率连乘导致低估
       ON city, zipcode FROM orders;
ANALYZE orders;

-- 第 4 步：验证「到底是不是优化器估错了」。这是诊断手段，绝不要写进生产配置
SET enable_seqscan = off;
EXPLAIN (ANALYZE, BUFFERS) <同一条语句>;
RESET enable_seqscan;
--   强制走索引后明显更快 → 代价模型参数不对，先查 random_page_cost
--   强制走索引后反而更慢 → 优化器判断正确，该改的是 SQL 或索引设计

第 2 步说的「只看三处」具体怎么判，照下表查。这张表是判读的骨干，看完就能决定下一步动什么：

看哪一处看到什么下一步做什么
rows 与 actual rows（从最内层节点开始看）比值在 2 倍以内统计信息可用，问题不在这里，继续往外层看
同上差一个数量级以上统计信息不可信，先 ANALYZE；仍然差就提高该列统计目标，多列 AND 才失真就建扩展统计
loopsNested Loop 内层 loops 上万真实耗时是 actual time × loops，真实行数是 actual rows × loops。根因通常是外层行数被低估，回到上一行
Rows Removed by Filter远大于该节点输出的行数过滤条件没有下推到索引，建复合索引或部分索引把它变成 Index Cond
Buffers: shared hit / readread 远大于 hit先确认不是首次访问；反复如此说明扫描量太大或 shared_buffers 偏小
Sort Method 与 Hash 的 Batches出现 external merge Disk 或 Batches 大于 1按计划里提示的 KB 数在会话级放大 work_mem，不要改全局
Index Cond 与 Filter你以为走索引的条件落在 Filter 上它没用上索引：查类型是否匹配、条件是否套了函数、排序规则是否需要 text_pattern_ops
Heap FetchesIndex Only Scan 下这个数很大visibility map 不是全可见，跑一次 VACUUM 即可，不用改索引
Heap Blocks: lossyBitmap Heap Scan 里出现 lossy位图内存不够退化成按页复核，同样是调 work_mem

判读之后最关键的一次决策是：建索引，还是改 SQL。这两条路的判据完全不同，选错就是白花一个变更窗口。

现象该建索引还是改 SQL判据
扫了几百万行只输出几千行，条件是等值加范围建索引，按等值列在前、范围列在后Rows Removed by Filter 占比极高，说明过滤完全可以下推到索引里完成
actual rows 占表总行数一成以上改 SQL 或改业务条件（加时间窗、加分页）这个选择率下顺序扫描加预读本来就更快，加索引只会更慢
条件里套了函数，如 lower(email) = ?两条都行：建同样写法的表达式索引，或把函数挪到参数一侧索引定义与查询里的表达式必须写法完全一致才会被匹配
ORDER BY 加 LIMIT 很慢，计划里有 Sort 节点建索引，让排序列紧跟等值列有序索引能把整个 Sort 节点去掉，这是收益最稳定的一类索引
一次查询往应用返回十万行改 SQL返回量本身是设计问题，索引解决不了结果集编码、网络传输与反序列化
同一条语句只有个别参数值慢先修统计信息，两条都不是取值分布倾斜，提高该列统计目标；也要看是不是通用计划与自定义计划的差别
OFFSET 100000 的深分页改 SQL，改成按上一页末尾值继续扫的游标式分页OFFSET 前面那十万行仍然要被扫出来再丢掉，索引救不了
子查询里 IN 一个很大的列表改 SQL，改成 join 或 = ANY(数组)计划形态不同，前者容易退化成逐个求值

最后是几个真正会改变优化器判断的参数。默认值随版本与发行版变化，一律以 SHOW 参数名 或 pg_settings 的输出为准，不要照抄任何文章里的数字：

参数作用默认值什么时候需要改
random_page_cost随机读一页相对顺序读的代价系数，直接决定优化器愿不愿意用索引以 SHOW random_page_cost 输出为准；历史出厂值是按机械盘假设设定的SSD 与 NVMe 上调到 1.1 到 1.5，这一项常能一次性解决一批「不走索引」

② 原理 · 五种索引类型：按数据形态选，不是按「快慢」选

先把结论说清楚：B-tree 覆盖 95% 的场景，剩下的 5% 才需要挑类型。选错的典型后果不是慢一点，而是索引根本不会被用到——因为每种索引只实现了特定的操作符类，查询里的操作符不在这个集合里，优化器就只能全表扫。

类型擅长的数据与操作体积量级写入代价什么时候它是错的选择
B-tree等值、范围、排序、IS NULL、前缀 LIKE 'abc%'；唯一约束的唯一实现约为被索引列数据的 1 到 2 倍低索引键超过页的三分之一会直接报错（约 2704 字节），长文本要改成表达式索引取哈希
Hash只支持等号略小于 B-tree低基本没有使用理由：PG 10 之前不写 WAL、不能复制；即使现在也不支持排序、范围与唯一约束，省下的空间不值得
GIN一个值里有多个键的场景：JSONB 的 @>、数组包含、全文检索 tsvector、配合 pg_trgm 做 LIKE '%中间%'常见为数据的 1 到 3 倍，全文检索下可能更大高，一行要拆成多个键分别插入写入密集表上慎用；fastupdate 打开时新条目先进待处理列表，查询要顺带扫这个列表，延迟会抖
GiST有「包含、相交、距离」语义的类型：几何与 PostGIS、tsrange 等范围类型的重叠排除、KNN 最近邻 ORDER BY 点 <-> 点中等中等等值查询上打不过 B-tree；它是有损索引，需要回堆做精确复核
BRIN只存每个块区间的最小最大值，要求数据物理有序；时序表按时间追加写是完美场景约为表的千分之一甚至更小极低数据物理无序时完全无效（每个块区间都覆盖全域，等于全表扫）；频繁更新会打乱物理顺序让它逐渐失效
SP-GiST空间划分树，适合前缀树式数据：IP 网段 inet、电话号码前缀、点数据小低使用面窄，先确认操作符类存在再用

-- JSONB：两种 GIN 操作符类的取舍
CREATE INDEX idx_doc_gin ON docs USING gin (payload);
-- jsonb_ops 默认，键和值都进索引，支持存在性 ? 与包含 @>，但体积大
CREATE INDEX idx_doc_gin_path ON docs USING gin (payload jsonb_path_ops);
-- jsonb_path_ops 只索引「路径加值」的哈希，体积小得多、更快，但只支持 @> 一族操作符

-- 中间匹配的模糊查询：只有 pg_trgm 能让 LIKE '%xxx%' 走索引
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX idx_name_trgm ON users USING gin (name gin_trgm_ops);
-- 注意：模式串短于 3 个字符时三元组不足，仍会退化成全表扫

-- 全文检索：索引生成列，避免每次查询重算 tsvector
ALTER TABLE articles ADD COLUMN tsv tsvector
      GENERATED ALWAYS AS (to_tsvector('simple', coalesce(title,'') || ' ' || coalesce(body,''))) STORED;
CREATE INDEX idx_articles_tsv ON articles USING gin (tsv);

-- BRIN：pages_per_range 越小越精确也越大，时序表按天写入时 32 到 64 是常见取值
CREATE INDEX idx_metrics_brin ON metrics USING brin (created_at) WITH (pages_per_range = 32);
-- 前提是物理有序。历史数据乱序时先按时间 CLUSTER 或用 pg_repack 重组一次
-- 检查有效性：看索引大小与查询是否真的裁掉了大部分块
SELECT pg_size_pretty(pg_relation_size('idx_metrics_brin')) AS brin大小,
       pg_size_pretty(pg_relation_size('metrics'))          AS 表大小;

-- 范围类型的重叠排除：用一个约束解决「同一房间时间段不能重叠」
CREATE EXTENSION IF NOT EXISTS btree_gist;
ALTER TABLE bookings ADD CONSTRAINT no_overlap
      EXCLUDE USING gist (room_id WITH =, during WITH &&);

② 原理 · PG 特有的三件索引利器

这三样是 PG 相比 MySQL 最实在的优势，而且都不需要改表结构。

能力写法可用版本MySQL 对照实际收益与注意点
部分索引CREATE INDEX ... WHERE deleted = false很早就有没有等价能力只索引热数据，软删表、队列表上体积能缩到百分之几。要求查询里的条件能被优化器证明蕴含索引的 WHERE，条件写成参数化的变量就用不上
表达式索引CREATE INDEX ... ON t (lower(email))很早就有MySQL 8.0 才有函数索引让函数条件也能走索引。函数必须是 IMMUTABLE，now() 这种不行；查询里的表达式要和索引定义写法一致
覆盖索引 INCLUDECREATE INDEX ... ON t (a) INCLUDE (b, c)PG 11+把列塞进联合索引非键列只挂在叶子上，不参与排序也不占内部节点，用来凑 Index Only Scan。前提是 visibility map 全可见，否则仍要回堆
多列索引顺序(a, b, c) 遵循最左前缀—规则一致PG 没有 MySQL 8.0 那样的索引跳跃扫描（PG 18 才引入类似优化），缺失前导列时只能靠位图组合或补索引
多个单列索引的 BitmapAnd无需 DDL，优化器自动组合—MySQL 的 index merge 能力弱得多这是 PG 的重要特性：WHERE a = 1 AND b = 2 可以分别走 a、b 的索引再取位图交集，所以不必为每种条件组合都建联合索引
✅
部分索引是 PG 上最被低估的优化

一张 5 亿行的订单表里只有几万行是 status = 'pending'，给全表建索引要几十 GB，而 CREATE INDEX ... WHERE status = 'pending' 只有几 MB，能常驻内存。更关键的是它减少写放大：不满足 WHERE 条件的行插入和更新时完全不碰这个索引，等于把主干篇讲的「索引个数等于写放大倍数」这个代价也一起降下来了。唯一要注意的是查询条件必须让优化器能静态判定蕴含关系，把 status 做成绑定参数就废了。

② 原理 · EXPLAIN 逐字段判读：只看 cost 是白看

永远用 EXPLAIN (ANALYZE, BUFFERS)。不带 ANALYZE 只有估算，看不出优化器估错；不带 BUFFERS 看不出是内存命中还是真的读盘。计划是一棵树，从最内层、缩进最深的节点开始往外读，每个节点的耗时都包含了它的子节点。

loops=240该节点被执行了 240 次，而 actual rows 与 actual time 都是单次平均值最常被误读的字段：真实总行数是 rows × loops，真实总耗时也要乘 loops。看到 Nested Loop 内层 loops 上万就该警惕

EXPLAIN (ANALYZE, BUFFERS, VERBOSE, SETTINGS)
SELECT o.id, o.amount, u.name
FROM   orders o JOIN users u ON u.id = o.user_id
WHERE  o.created_at >= now() - interval '7 days'
  AND  o.status = 'paid'
ORDER  BY o.amount DESC
LIMIT  50;

/* 典型输出与判读要点（缩进最深的先执行）：

                     Rows Removed by Filter: 8800000     <-- 扫了 900 万扔掉 880 万

ANALYZE orders;

② 原理 · 四种扫描方式与 Bitmap 的真正含义

很多人以为「Bitmap Heap Scan 出现就是没用好索引」，恰恰相反：Bitmap 是索引命中行数中等时的最优解。它分两步——先扫索引把所有命中的块号攒成位图，再按块号从小到大顺序读堆。这样把随机 IO 变成了接近顺序的 IO，还顺带去掉了同一页被多次访问的重复读。

sequenceDiagram autonumber participant E as 执行器 participant BI as Bitmap Index Scan participant BM as 内存位图 participant BH as Bitmap Heap Scan participant HP as 堆页 E->>BI: 按索引条件扫描 BI->>BM: 只记录命中行所在的块号 不立刻取行 Note over BM: 位图内存不够时按页粒度记录
计划里显示 lossy 需要回堆逐行复核 E->>BH: 位图构建完成 开始读堆 BH->>HP: 按块号升序批量读取 随机 IO 变顺序 IO HP-->>BH: 返回页内候选行 BH->>BH: 用 Recheck Cond 复核并应用剩余 Filter BH-->>E: 输出结果行 Note over E,HP: 多个索引可以各自出一个位图
再做 BitmapAnd 或 BitmapOr 组合
扫描方式触发条件IO 特征看到它该想什么
Seq Scan选择率高（经验上超过 5% 到 10%）、表很小、或没有可用索引顺序读，可并行小表上的 Seq Scan 是最优解，不是问题。只有在选择率明显很低时出现才要查统计信息
Index Scan选择率低，且需要按索引顺序输出每命中一行一次随机读堆命中行数一多反而比 Seq Scan 慢，这就是优化器有时故意不选它的原因
Index Only Scan查询用到的列全在索引里，且目标页在 visibility map 中标记全可见完全不碰堆最快的形态。如果计划里 Heap Fetches 很大，说明 VACUUM 没跟上，跑一次 VACUUM 就能起飞
Bitmap Index Scan 加 Bitmap Heap Scan命中行数中等，或需要组合多个索引先攒块号再按物理顺序读正常且高效。要关注 Heap Blocks: lossy 和 Rows Removed by Recheck
BitmapAnd / BitmapOr多个条件各有单列索引位图按位运算说明不需要为这个条件组合再建联合索引，PG 自己就能组合

② 原理 · 三种 join 方式与 work_mem 的分配单位

join 方式选错的代价通常比扫描方式选错大一个数量级，而且原因几乎总是行数估算不准。

Join 方式适用数据量内存条件前提失效场景
Nested Loop外层行数很少（几十到几千），内层有索引几乎不占内层能走索引，否则是笛卡尔级复杂度外层行数被严重低估时最致命：估 10 行实际 10 万行，内层就执行 10 万次，看 loops 就能确认
Hash Join两侧都不小，等值连接小表要能放进 work_mem只支持等值连接内存不够就分批落盘，计划里 Batches 大于 1；小表侧选错（估算反了）会导致把大表建哈希
Merge Join两侧都很大且已有序排序阶段吃 work_mem两侧按连接键有序，通常靠索引或显式排序提供需要额外排序时经常打不过 Hash Join；一侧数据倾斜严重时退化明显

work_mem 是每个排序或哈希节点各分配一份，不是每个查询一份。一条带三个排序节点的查询在 50 个并发下，理论峰值是 work_mem × 3 × 50。所以正确做法是全局设一个保守值（比如 16MB 到 64MB），再对已知的重查询按会话或按角色单独放大。PG 13 起还有 hash_mem_multiplier（默认 2.0），可以只给哈希类节点更多内存而不放大排序。

② 原理 · 为什么优化器不走我建的索引

先接受一个事实：大多数情况下不走索引是对的。PG 的优化器是基于代价的，当它估计要返回表里 10% 以上的行时，顺序扫描加上预读几乎一定比几十万次随机读堆更快。真正需要修的是下面这几类。

原因怎么确认修法
选择率确实太高，全表更快actual rows 占表总行数比例大不用修，这是正确决策。想减少扫描量就改业务条件或加部分索引
统计信息过期rows 与 actual rows 差一个数量级以上ANALYZE 表名；长期方案是调小 autovacuum_analyze_scale_factor
列值分布倾斜，直方图精度不够某个特定取值估得极离谱，换个值就正常ALTER TABLE ... ALTER COLUMN ... SET STATISTICS 1000
多列之间强相关，估算连乘导致低估单条件估得准，两个条件 AND 起来就差几十倍CREATE STATISTICS 建扩展统计信息（PG 10+）
random_page_cost 没按 SSD 调默认 4.0 是机械盘假设，NVMe 上随机读并不比顺序读贵 4 倍SSD 上设 1.1 到 1.5，同时把 effective_cache_size 设到内存的 50% 到 75%，这两个参数是让 PG 更愿意用索引的主开关
类型不匹配或字符集排序规则不同计划里出现隐式转换，或条件落在 Filter 而不是 Index Cond把参数类型对齐（bigint 列不要传字符串）；text_pattern_ops 才能让非 C 排序规则下的前缀 LIKE 走索引
条件里套了函数WHERE lower(email) = ... 而索引建在 email 上建同样表达式的表达式索引，写法必须完全一致
LIMIT 改变了最优计划去掉 LIMIT 走索引，加上就变 Seq Scan（或者反过来）这是启动代价与总代价权衡的正常结果。若估算失真则回到前几条修统计信息
并行计划被误判大表扫描却没有 Parallel 节点检查 max_parallel_workers_per_gather 是否为 0、表是否小于 min_parallel_table_scan_size
 
-- 验证「到底是不是优化器估错」的实验手法：只在会话里临时关某种扫描方式
-- 注意这是诊断工具不是修法，绝不要写进生产配置
SET enable_seqscan = off;
EXPLAIN (ANALYZE, BUFFERS) SELECT ... ;   -- 对比强制走索引后的实际耗时
RESET enable_seqscan;
-- 如果强制走索引后 actual time 明显更低，说明代价模型参数不对（通常是 random_page_cost）
-- 如果反而更慢，说明优化器判断正确，该改的是 SQL 或索引设计

-- 让 PG 更愿意用索引的两个主开关（SSD 环境）
ALTER SYSTEM SET random_page_cost = 1.1;          -- 默认 4.0 是机械盘假设
ALTER SYSTEM SET effective_cache_size = '48GB';   -- 设为物理内存的 50% 到 75%，只是给优化器的提示
SELECT pg_reload_conf();

② 原理 · 索引运维：找出没用的、膨胀的、最慢的

索引不是只有收益：每个索引都在吃写入性能（主干篇讲过，非 HOT 更新要维护全部索引）、吃内存、吃磁盘。一个跑了两年的库里通常躺着 20% 到 40% 从未被使用的索引。

-- 1. 从未被使用的索引：idx_scan = 0 且不是唯一约束的，基本可以删
-- 前提：统计自上次 pg_stat_reset 起累计，确认已经覆盖了完整业务周期（含月末月初）
SELECT s.schemaname || '.' || s.relname            AS 表名,
       s.indexrelname                              AS 索引名,
       s.idx_scan                                  AS 被使用次数,
       pg_size_pretty(pg_relation_size(s.indexrelid)) AS 索引大小,
       i.indisunique                               AS 是否唯一,
       pg_get_indexdef(s.indexrelid)               AS 定义
FROM   pg_stat_user_indexes s
JOIN   pg_index i ON i.indexrelid = s.indexrelid
WHERE  s.idx_scan = 0
  AND  NOT i.indisunique
  AND  pg_relation_size(s.indexrelid) > 10 * 1024 * 1024
ORDER  BY pg_relation_size(s.indexrelid) DESC;

-- 2. 重复或冗余索引：(a) 被 (a, b) 完全覆盖，前者可以删
SELECT indrelid::regclass AS 表名, array_agg(indexrelid::regclass) AS 疑似冗余组
FROM   pg_index
GROUP  BY indrelid, (indkey::text || coalesce(indpred::text, ''))
HAVING count(*) > 1;

-- 3. 最慢的查询：pg_stat_statements 是唯一可靠的入口
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;   -- 需要在 shared_preload_libraries 里
SELECT round(total_exec_time)              AS 总耗时ms,
       calls,
       round(mean_exec_time, 2)            AS 平均ms,
       round(stddev_exec_time, 2)          AS 抖动ms,
       rows / greatest(calls, 1)           AS 每次返回行数,
       round(100.0 * shared_blks_hit /
             greatest(shared_blks_hit + shared_blks_read, 1), 1) AS 缓存命中率,
       left(query, 100)                    AS 语句
FROM   pg_stat_statements
ORDER  BY total_exec_time DESC              -- 按总耗时排，不是按平均耗时
LIMIT  20;
-- 判读要点：调用量大而单次不慢的语句，优化收益往往远高于偶发的慢查询

-- 4. 索引膨胀：B-tree 在随机删改下会留下半空页
SELECT indexrelid::regclass AS 索引名,
       pg_size_pretty(pg_relation_size(indexrelid)) AS 大小,
       (SELECT avg_leaf_density FROM pgstatindex(indexrelid::regclass::text)) AS 叶子填充率
FROM   pg_index
WHERE  pg_relation_size(indexrelid) > 100 * 1024 * 1024;
-- 需要 pgstattuple 扩展；叶子填充率低于 50% 就值得重建
REINDEX INDEX CONCURRENTLY idx_orders_created_at;   -- PG 12+，不阻塞读写
-- 失败会留下 _ccnew 后缀的残留索引，重建后务必检查：
SELECT indexrelid::regclass FROM pg_index WHERE NOT indisvalid;
💡
删索引之前的正确验证顺序

直接 DROP INDEX 的风险是判断错了要重建，而大表重建索引很贵。稳妥的顺序是：先确认 idx_scan 的统计区间覆盖了完整业务周期（含月末结算这类低频路径）；再用 pg_stat_statements 里的历史语句交叉比对有没有语句依赖它；要评估「新增某个索引是否有用」可以装 HypoPG 扩展创建虚拟索引，它只影响 EXPLAIN 的估算、不占磁盘也不写 WAL；最后真正删除时用 DROP INDEX CONCURRENTLY，普通 DROP INDEX 会取 ACCESS EXCLUSIVE 锁。网上流传的「直接 UPDATE pg_index 把 indisvalid 改成 false 让索引假死」不要用，手改系统目录绕过了所有一致性检查，出问题无从排查。

③ 场景 · 按业务形态选索引组合，以及索引解决不了的问题

前面给的是单条语句的判读与单个索引的选型。落到一张表上时，决定索引方案的是这张表在业务里的角色：它承担哪几种查询形态、写入有多密集、能不能把一部分查询分流出去。下表按常见业务形态给出组合方案与它的代价。

场景该怎么做为什么代价
C 端订单或消息列表：用户维度等值加时间倒序分页一个 B-tree (user_id, created_at DESC)，返回列少时再 INCLUDE 补齐等值列在前、排序列紧跟，Sort 节点直接消失；覆盖之后可进 Index Only Scan索引变宽、写放大增加；INCLUDE 要靠 VACUUM 跟上才有效，否则 Heap Fetches 居高不下
软删除表，绝大多数查询只看未删除的行部分索引 WHERE deleted = false体积能缩到百分之几且常驻内存，还顺带减少写放大：不满足条件的行完全不碰这个索引条件必须能被优化器静态判定蕴含，把 deleted 做成绑定参数就废了
JSONB 存动态属性，按包含关系查询GIN 加 jsonb_path_ops；需要存在性 ? 操作符时才用默认的 jsonb_opsjsonb_path_ops 只索引「路径加值」的哈希，体积小得多也更快只支持 @> 一族操作符；写入放大明显，写密集表要评估
站内搜索、中文模糊匹配轻量场景用 pg_trgm 加 GIN，或 tsvector 生成列加 GIN只有三元组能让前缀不定的 LIKE 走索引；生成列避免每次查询重算 tsvector索引体积大、写入慢；模式串短于 3 字符仍全表扫。相关性排序与分词需求重的转 Elasticsearch 的索引结构与查询代价
时序指标表，按时间窗口过滤与聚合BRIN 加按时间分区，两者叠加BRIN 体积可到表的千分之一，块区间裁剪的效果接近分区裁剪依赖物理有序，回填历史数据后要 CLUSTER 或重组；重聚合分析转 ClickHouse 深度原理
后台筛选器，条件是十几个字段的任意组合给高频出现的几个字段各建单列索引，让优化器做 BitmapAndPG 能把多个位图按位组合，不必为每种条件组合都建联合索引索引个数仍要管住；位图内存不足会出现 lossy，退化成按页复核
房间预订、排班这类「同一资源时间段不许重叠」范围类型加 EXCLUDE USING gist 约束（需要 btree_gist）把不变式放在数据库层，比应用层先查后插可靠得多写入要处理约束冲突错误；并发语义的取舍见 隔离级别与并发控制
报表大扫描与在线查询混在同一张表上把报表分流到只读备库或物化视图，而不是继续给主库加索引一次大扫描会把 shared_buffers 里的热页冲掉，表现是「所有查询一起变慢」多一份延迟与运维成本，备库上还有恢复冲突要处理，见 复制与故障切换
写入密集的流水表、埋点表索引降到最少，只留主键与一个时间维度索引每个索引都是写放大，非 HOT 更新要维护全部索引查询能力弱，复杂查询只能走离线或列存链路

不适用边界：索引解决不了的问题不要在索引上找答案。元组结构、xmin 与 xmax、HOT 更新、VACUUM 与 WAL 的机制在 PostgreSQL 主干篇；字段类型本身选得对不对（jsonb 还是拆列、numeric 还是 bigint）在 PostgreSQL 数据类型选择与代价，类型选错时任何索引都救不回来；shared_buffers 与全局内存参数的设定在 PostgreSQL 生产部署与必调参数；建索引会取什么锁、CREATE INDEX CONCURRENTLY 为什么会被长事务拖住在 隔离级别与并发控制；索引数量怎么管住、怎么从查询模式反推一组索引的通用方法在 索引设计与治理，慢查询从发现到根治的闭环在 慢查询治理，而「问题到底是不是在数据库」这一层在 数据库性能优化：瓶颈定位顺序；MySQL 侧的 B+ 树树高、回表与 EXPLAIN 判读在 MySQL 深度原理。

最容易踩的坑

❌
这些坑每条都有真实事故对应
  • 只看 EXPLAIN 不加 ANALYZE, BUFFERS：光看 cost 无法发现估算偏差，也看不出是命中缓存还是在读盘，等于在猜。
  • 把 rows 当真实行数：它是估算值。rows 与 actual rows 差一个数量级以上，先 ANALYZE，不要急着改 SQL。
  • 忘了 actual rows 要乘 loops：Nested Loop 内层显示「0.01ms 返回 1 行」，乘上 loops=200000 就是 2 秒。这是最常被误读的字段。
  • 看到 Seq Scan 就想加索引：小表和高选择率查询上顺序扫描是最优解，强行走索引只会更慢。
  • 看到 Bitmap Heap Scan 以为索引没生效：它是命中行数中等时的正确选择，把随机 IO 变成了顺序 IO。该关注的是 lossy 和 Rows Removed by Recheck。
  • 在 SSD 上不改 random_page_cost：默认 4.0 是机械盘假设，会系统性地让优化器低估索引扫描的价值。改成 1.1 常常一次性解决一批「不走索引」。
  • 用 INCLUDE 凑覆盖索引却没跑 VACUUM：Index Only Scan 要求页在 visibility map 中全可见，Heap Fetches 很大时它就退化成了普通索引扫描。
  • 给 LIKE '%关键词%' 建普通 B-tree 索引：前缀不定的模糊匹配用不上 B-tree，必须 pg_trgm 加 GIN，而且模式串少于 3 个字符时仍会退化。
  • 在写入密集表上建 GIN：一行要拆成多个键插入，写放大很大；fastupdate 的待处理列表还会让查询延迟周期性抖动。
  • 对物理无序的数据建 BRIN：每个块区间都覆盖全域，索引形同虚设。BRIN 的前提是物理有序，频繁更新的表会让它慢慢失效。
  • 把 work_mem 全局调到 512MB：它是每个排序或哈希节点一份，高并发下会直接把内存打满触发 OOM。全局保守，重查询按会话放大。
  • 为每种条件组合都建联合索引：PG 能用 BitmapAnd 组合多个单列索引，索引数量上去之后写放大和内存占用的损失远大于收益。
  • 凭 idx_scan = 0 立刻删索引：统计是从上次重置起累计的，要确认覆盖了完整业务周期；唯一索引即使没被查询用到也可能在承担约束职责。
  • 用 REINDEX 而不是 REINDEX CONCURRENTLY：前者持 ACCESS EXCLUSIVE 锁，大表上等于停服；后者失败会留下 _ccnew 残留索引，事后必须检查 indisvalid。
