PostgreSQL 生产部署与必调参数

🏷️ PG 安装

PostgreSQL 的默认配置是为「能在任何机器上启动」优化的，不是为你的生产机优化的：shared_buffers 默认 128 MB，random_page_cost 默认 4.0（按机械盘假设），data-checksums 默认关闭。更要命的是，有几个选项在 initdb 那一刻就定死，之后只能重建数据目录。这篇按「不可逆决策 → 参数矩阵 → 认证与连接池 → 上线验证 → 升级路径」的顺序走一遍生产部署。

安装方式取舍：别用发行版自带的那个版本

最常见的开局错误是 apt install postgresql 就完事。Debian 12 自带的是 PG 15，Ubuntu 22.04 自带 PG 14，CentOS 7 的 AppStream 里甚至还有 PG 10。用发行版仓库意味着你的大版本被操作系统的生命周期锁死，想升级 PG 就得先升级操作系统，而 PG 每个大版本的性能与可观测性改进都很实在（PG 14 起连接与索引空间优化、PG 15 起统计信息进共享内存、PG 16 起并行与逻辑复制增强）。正确做法是加 PGDG 官方仓库，自己选大版本，小版本跟着安全更新走。

安装方式版本新鲜度可控性适合主要坑
PGDG 官方 apt/yum 仓库所有在维护的大版本都能选高，systemd 托管，路径规范绝大多数生产环境Debian 系会自动帮你 initdb 一个默认 locale 的实例，要先删掉再按自己的参数重建
发行版自带仓库落后 1 到 3 个大版本中，受操作系统生命周期绑定内网工具库、对版本无要求的场景大版本升级被操作系统卡住；扩展版本也跟着旧
源码编译任意版本，可打补丁最高，可定制 block size、编译选项需要非默认 block size、要接自研扩展依赖与升级全自理；改 block size 后所有备份与备库都必须同参数
Docker 官方镜像新中，参数靠环境变量与挂载本地开发、CI、集成测试数据卷没挂对就是删容器丢数据；POSTGRES_INITDB_ARGS 不传就拿不到 checksum 和指定 locale
云托管（RDS 等）新，但大版本由云商放行低，很多参数被锁、无超级用户不想养 DBA 的团队不能装任意扩展；shared_preload_libraries 受限；故障时只能等云商

initdb 阶段就定死的三件事

这一节是整篇最关键的。下面三个选项写进数据目录之后无法原地修改，错了只能重建集群再迁数据。

initdb 选项默认来源选错的后果建议
--encoding跟随 locale 推导，可能是 SQL_ASCII 或 LATIN1SQL_ASCII 不做任何校验，脏字节原样存入，事后无法可靠转码显式写 UTF8，不要依赖推导
--locale / --lc-collate安装机器的 LANG 环境变量排序规则决定所有文本索引的键顺序，集群级 collate 事后不能改；同一脚本在不同机器上跑出不同结果显式指定；新库优先用 ICU（PG 15 起的 --locale-provider=icu）
--data-checksums默认关闭（PG 18 起才默认开启）磁盘静默损坏（bit rot）不会被发现，坏页会被当正常数据读出并顺着备份和流复制扩散一律开启，开销通常在个位数百分比
--wal-segsize16 MB超大写入实例上段文件切换过于频繁；改动需重建集群普通业务不动；每秒 WAL 上百 MB 的实例可考虑 64 MB
block size（编译期）8 KB与备份、流复制、pg_upgrade 的兼容性全部绑定不要改，除非有实测收益且能统一所有环境

排序规则这件事值得单独展开，因为它有一个非常著名的坑：glibc 的排序规则数据会随版本变化。glibc 2.28（RHEL 8、Debian 10 那一代）对大量语言的排序规则做了调整，结果是「操作系统升级后，已有的文本 B-tree 索引里的键顺序和当前排序规则不一致」。索引不会报错，只会开始返回错误结果——查得到的行查不到、唯一约束也可能漏判。PG 会在日志里提示 collation version mismatch，正确处置是对相关索引全部 REINDEX。

C / POSIX按字节比较，大写字母排在小写前，中文按 UTF-8 字节序可以最快，字符串比较是 memcmp无
en_US.UTF-8（glibc）语言感知，忽略大小写与标点权重差异不行，需要额外建 text_pattern_ops 索引比较走 strcoll，明显更慢有，跨大版本操作系统升级需 REINDEX
zh_CN.UTF-8（glibc）中文按拼音排序不行，同上更慢有
ICU（und-x-icu 等）语言感知，规则版本被记录在系统表里不行，需 text_pattern_ops与 glibc 相当低，版本变化会被显式报出
✅
实用折中：集群用 C 或 ICU，需要语言排序的列单独指定

集群级 collate 用 C 可以拿到最快的字符串比较和可直接用于 LIKE 前缀匹配的索引，需要按拼音或忽略大小写排序的地方在列或查询上单独写 COLLATE "zh-x-icu"。列级和查询级的 collation 是可以事后修改的，集群级不行——把不可逆的决定留在最保守的那一档。

# Debian / Ubuntu：用 PGDG 官方仓库装指定大版本（这里以 16 为例）
sudo apt install -y curl ca-certificates gnupg
curl -fsSL https://www.postgresql.org/media/keys/ACCC4CF8.asc \
  | sudo gpg --dearmor -o /usr/share/keyrings/pgdg.gpg
echo "deb [signed-by=/usr/share/keyrings/pgdg.gpg] http://apt.postgresql.org/pub/repos/apt $(lsb_release -cs)-pgdg main" \
  | sudo tee /etc/apt/sources.list.d/pgdg.list
sudo apt update && sudo apt install -y postgresql-16 postgresql-contrib-16

# Debian 系会自动建一个默认 locale 的实例，先删掉，再按自己的参数重建
sudo pg_dropcluster --stop 16 main

# 关键：三个不可逆参数一次给对。checksums 必须在这里开，locale 用 C 保证可移植
sudo -u postgres /usr/lib/postgresql/16/bin/initdb \
  -D /data/pgdata \
  --encoding=UTF8 \
  --locale=C \
  --lc-messages=en_US.UTF-8 \
  --data-checksums \
  --waldir=/wal/pg_wal          # WAL 单独放一块盘：顺序写与随机写不再抢同一队列

# 确认落地情况：checksum 必须是 enabled
sudo -u postgres /usr/lib/postgresql/16/bin/pg_controldata /data/pgdata \
  | grep -E 'checksum|encoding|Collate|WAL segment size'

目录布局：哪些东西该分盘

PGDATA 里不是所有目录都同等重要。pg_wal 是纯顺序写、每次提交都要 fsync，和数据文件的随机读写抢同一块盘会互相拖累；临时文件（大排序溢出）是突发的大量写，也适合隔离。表空间（tablespace）则用来把冷热数据分到不同介质。

⚠️
表空间不能拿来做「跨机器扩容」

表空间只是数据目录之外的一个符号链接目标，它属于这个集群，不能被另一个实例挂载，也不能单独备份恢复。更重要的是：把表空间放在非持久化存储上会让整个集群无法恢复，因为 WAL 里包含对这些文件的引用。云上用临时盘放表空间是典型的踩雷方式。

内存参数矩阵：work_mem 是最容易配错的那个

先说结论：work_mem 不是每连接的配额，而是每个排序或哈希操作的配额。一条包含三次排序、两次哈希连接的查询，最坏情况会申请五份 work_mem；如果这条查询还走了并行，每个 worker 各算一份。所以内存估算公式应该是：

峰值 ≈ shared_buffers + 并发查询数 × 每查询操作数 × (1 + 并行 worker 数) × work_mem + 连接数 × 单连接常驻

把 work_mem 设成 512 MB「让报表跑快点」，然后 30 个并发查询同时到达，就是一次 OOM。正确姿势是全局保守（8 到 32 MB），对特定报表在会话里临时放大。

参数默认值建议值语义与调错后果改动是否需重启

effective_cache_size4 GB物理内存 50 到 75 percent只是给优化器的提示，不实际分配内存。设太小会让优化器以为缓存命中率低而放弃索引扫描reload 即可

WAL、检查点与优化器代价参数

IO 出现周期性尖刺、每隔几分钟延迟抖一下，八成是检查点。检查点要把上一轮以来的脏页全部刷盘，checkpoint_completion_target 控制把这些写摊平到整个周期的比例（PG 9.5 到 13 默认 0.5，PG 14 起默认 0.9）。max_wal_size 太小会导致检查点被 WAL 量触发而不是被时间触发，日志里会出现 checkpoints are occurring too frequently 的提示。

autovacuum：只能调，不能关

PG 的 UPDATE 不是原地改，而是插入新版本、把旧版本标记过期，旧版本留在堆表里。VACUUM 负责三件事：回收死元组空间、更新可见性映射（让索引-only 扫描生效）、推进事务 ID 冻结以防回卷。关掉 autovacuum 换来的写入提速，代价是表膨胀、统计信息过期导致执行计划突变、以及事务 ID 年龄逼近 20 亿时整个实例进入只读保护。

参数默认值调整方向什么信号说明该调了
autovacuumon永远保持 on没有任何值得关闭的理由；要降影响就调下面的成本参数
autovacuum_max_workers3大库调到 6 到 10（同时提高 max_worker_processes）pg_stat_progress_vacuum 长期排队、大表轮不到
autovacuum_vacuum_scale_factor0.2（表 20% 行变更才触发）亿行大表在表级设成 0.01 或改用 vacuum_threshold大表的 n_dead_tup 到了千万级还没触发
autovacuum_vacuum_cost_delay2 ms（PG 12 起）追不上时降到 0 到 1 ms死元组持续上涨、膨胀率 rising
autovacuum_vacuum_cost_limit-1（取 vacuum_cost_limit 的 200）提到 1000 到 3000同上，autovacuum 被限速
autovacuum_freeze_max_age2 亿一般不动，重点是监控 agedatfrozenxid 年龄接近该值会触发强制的 anti-wraparound vacuum，无法被取消
autovacuum_analyze_scale_factor0.1写入热表调小到 0.02计划突然变差、行数估算与实际差一个量级
❌
autovacuum 能跑，不等于能回收

只要存在一个更老的快照，VACUUM 就无法回收它之后产生的死元组，任凭你怎么调参都没用。三个典型的「持有者」是：长事务与 idle in transaction 会话、未消费的逻辑复制槽、以及开了 hot_standby_feedback 的备库上的长查询。排查顺序是先看 pg_stat_activity 里最老的 xact_start，再看 pg_replication_slots 的 xmin，最后才是调 autovacuum 参数。

认证：pg_hba.conf 的匹配顺序决定一切

pg_hba.conf 是自上而下取第一条匹配，匹配上就不再往下看，即使认证失败也不会回退到后面的规则。这条规则解释了绝大多数「我明明加了规则却连不上」的问题：前面有一条更宽泛的记录先匹配走了。四元组的匹配维度是：连接类型（local / host / hostssl / hostnossl）、数据库、用户、来源地址。

只应出现在本机 socket 的应急场景"] T -- "scram-sha-256" --> SC["挑战应答，密码不过网
要求 password_encryption 已是 scram"] T -- md5 --> MD["弱哈希，用户名参与加盐
应尽快淘汰"] T -- cert --> CE["客户端证书，配合 hostssl"] T -- reject --> RJ["立即拒绝，用于黑名单前置"] SC --> R2{"认证是否通过"} MD --> R2 R2 -- 是 --> DONE["连接建立，fork backend"] R2 -- 否 --> FAIL["连接失败
注意：不会回退到后面的规则"]

从 md5 迁到 scram-sha-256 有个顺序问题：必须先把 password_encryption 改成 scram-sha-256，再让每个用户重设一次密码，最后才改 pg_hba。因为存量密码还是 md5 哈希，直接改 hba 会导致老用户全部认证失败。检查办法是查 pg_authid.rolpassword 的前缀：SCRAM-SHA-256 开头才是新格式。

# /data/pgdata/pg_hba.conf —— 自上而下第一条匹配生效，顺序即优先级
# TYPE      DATABASE   USER        ADDRESS            METHOD

# 1. 本机 unix socket 的运维通道：peer 用操作系统用户身份，不需要密码
local       all        postgres                       peer

# 2. 显式黑名单要放最前面，否则会被后面的宽规则先匹配走
host        all        all         10.0.99.0/24       reject

# 3. 业务库只允许应用网段、强制 TLS、scram 认证
hostssl     appdb      app_rw      10.0.1.0/24        scram-sha-256
hostssl     appdb      app_ro      10.0.1.0/24        scram-sha-256

# 4. 复制连接单独开，用户只给 REPLICATION 权限，不要复用超级用户
hostssl     replication repluser   10.0.2.0/24        scram-sha-256

# 5. 兜底：拒绝其他所有来源。不写这条时默认行为也是拒绝，但显式写便于审计
host        all        all         0.0.0.0/0          reject

连接池：PgBouncer 三种 pool_mode 各破坏什么

前面算过：PG 每连接一个进程、常驻 5 到 10 MB。连接池的作用是把「几千个应用连接」收敛成「几十个真实后端连接」。关键在于 pool_mode——复用粒度越细，收益越大，被破坏的会话级特性也越多。

sequenceDiagram autonumber participant A1 as 应用连接 A participant A2 as 应用连接 B participant PB as PgBouncer
pool_mode = transaction participant S as 后端 server 连接 A1->>PB: BEGIN PB->>S: 绑定 server 连接给 A A1->>PB: UPDATE ... PB->>S: 转发 A1->>PB: COMMIT PB->>S: 提交后立刻解绑 Note over PB,S: 事务结束即归还，A 的会话状态不再保留
临时表 / 预备语句 / advisory lock 全部失效 A2->>PB: SELECT ... PB->>S: 把同一个 server 连接给 B S-->>A2: 结果返回 Note over A1,PB: A 若之后执行 DEALLOCATE 或引用之前的预备语句
会报 prepared statement does not exist
pool_mode复用粒度会失效的能力适合驱动侧注意
session客户端断开才归还几乎不破坏任何东西需要完整会话语义、只想省掉建连开销无特殊要求，但复用收益很小
transaction每个事务结束就归还会话级预备语句、临时表、advisory lock、LISTEN/NOTIFY、SET 的跨语句生效、游标跨事务绝大多数 Web 业务的默认选择JDBC 要设 prepareThreshold=0，asyncpg 要关 statement_cache_size；或用 PgBouncer 1.21 起的 prepared statement 支持
statement每条语句结束就归还连多语句事务都不允许，显式 BEGIN 直接报错纯自动提交的只读分析流量ORM 基本都不可用
⚠️
连接池不是「连接数随便开」的许可

PgBouncer 的 default_pool_size 决定每个「数据库加用户」组合占用的真实后端连接数，它乘以组合数量才是 PG 实际承担的连接。常见配置是 max_client_conn = 5000 配 default_pool_size = 25。另外 PgBouncer 是单进程单线程的，单实例上限大概在几万 QPS 和一两万连接，再往上要起多个实例（so_reuseport）或换 pgcat 这类多线程实现。

上线前的验证清单

装完不等于能上线。下面这一串跑完，才算知道这台实例是什么水平；pgbench 的基线数字尤其重要，出故障时你需要一个「正常长什么样」的参照。

# 1. 活性与版本
pg_isready -h 127.0.0.1 -p 5432            # 期望输出 accepting connections
psql -c 'SELECT version()'

# 2. 确认三个不可逆项真的生效了（checksum 一定要是 on / enabled）
psql -c 'SHOW data_checksums'              # 期望 on
psql -c 'SHOW server_encoding'             # 期望 UTF8
psql -c 'SHOW lc_collate'
psql -c 'SELECT datname, pg_encoding_to_char(encoding), datcollate FROM pg_database'

# 3. 校验和失败计数：应长期为 0，出现非 0 立刻查磁盘
psql -c 'SELECT datname, checksum_failures, checksum_last_failure FROM pg_stat_database WHERE checksum_failures > 0'

# 4. 关键参数复核：一次性把实际生效值拉出来对账
psql -c "SELECT name, setting, unit, source FROM pg_settings
         WHERE name IN ('shared_buffers','work_mem','effective_cache_size',
                        'random_page_cost','max_connections','max_wal_size',
                        'checkpoint_timeout','autovacuum','password_encryption')
         ORDER BY name"

# 5. 扩展是否装上（pg_stat_statements 必须在 shared_preload_libraries 里且 CREATE EXTENSION 过）
psql -c 'CREATE EXTENSION IF NOT EXISTS pg_stat_statements'
psql -c 'SELECT count(*) FROM pg_stat_statements'

# 6. 性能基线：先初始化 scale=100 约 1.5 GB 数据，再跑读写与只读两轮
pgbench -i -s 100 appdb
pgbench -c 32 -j 8 -T 300 -P 10 appdb          # 读写混合，记下 tps 与 latency 分位
pgbench -c 32 -j 8 -T 300 -P 10 -S appdb       # -S 只读，用来分离 WAL 与磁盘写的影响
# 判读：读写 tps 远低于只读 tps 的十分之一，通常是 fsync 或 checkpoint 配置问题
# 观察期间另开一个窗口看检查点日志：grep checkpoint /var/log/postgresql/*.log

# 7. 大版本升级演练（必须先在副本上做一遍）
#    流复制不能跨大版本，只有这两条路加逻辑复制三种选择
/usr/lib/postgresql/16/bin/pg_upgrade \
  --old-datadir=/data/pg15 --new-datadir=/data/pg16 \
  --old-bindir=/usr/lib/postgresql/15/bin --new-bindir=/usr/lib/postgresql/16/bin \
  --link --check                              # --check 先做兼容性预检，不动数据
# --link 用硬链接，停机时间与数据量无关，通常几分钟；但一旦开始就无法回退到旧目录
# 不加 --link 则复制文件，停机时间随数据量线性增长，好处是旧目录可作回滚
# 升级完成后必须重建统计信息，否则第一波查询会集体选错计划：
/usr/lib/postgresql/16/bin/vacuumdb --all --analyze-in-stages

最容易踩的坑

❌
这些坑改起来都要停机或重建
  • 忘了加 --data-checksums：默认关闭，且只能在 initdb 时开（PG 12 起有 pg_checksums 可离线开启，但要停机全量重写数据文件）。不开就等于放弃对静默坏页的检测。
  • locale 跟着机器环境变量走：同一套部署脚本在不同机器上得到不同的 lc_collate，测试环境和生产的 ORDER BY 结果不一致，排查起来极难定位。
  • 操作系统大版本升级后不 REINDEX：glibc 2.28 那次排序规则变更会让已有文本索引与当前 collation 不一致，索引不报错但返回错误结果，日志里的 collation version mismatch 提示必须当故障处理。
  • 把 work_mem 当每连接配额：它是每个排序或哈希操作的配额，并行查询还要乘 worker 数，设成几百 MB 遇上并发就是 OOM。
  • shared_buffers 设成物理内存一半：挤掉操作系统 page cache，同一份数据在两层重复驻留，检查点刷页量和崩溃恢复时间一起变差。
  • SSD 上留着 random_page_cost = 4.0：优化器系统性高估索引扫描代价，表现是有索引却走 Seq Scan，很多人误以为是「PG 不会用索引」。
  • max_connections 开几千代替连接池：进程数暴涨，快照获取与锁扫描退化，吞吐反降。
  • archive_command 失败没告警：pg_wal 会无上限增长直到磁盘写满，实例转入只读。命令必须返回非零才算失败，写 cp 时要先 test 目标不存在，避免覆盖导致备份无声损坏。
  • 留着不用的复制槽：槽会一直按住 WAL 与 xmin，既堆磁盘又阻止 VACUUM 回收，扩容磁盘只能拖延时间。
  • 先改 pg_hba 到 scram 再改密码：顺序反了会让所有存量用户认证失败，正确顺序是先设 password_encryption、再重设密码、最后改 hba。
  • pg_hba 规则写在宽规则后面：第一条匹配即生效且认证失败不回退，新加的规则被前面的 host all all 抢先匹配，表现为「规则加了却没用」。
  • PgBouncer 用 transaction 模式却没关驱动预备语句：会随机报 prepared statement does not exist，流量越高越频繁，很容易被误判为网络抖动。
  • 指望流复制做大版本升级：物理复制要求文件格式一致，跨大版本不成立；只能选 pg_upgrade、dump/restore 或逻辑复制。
  • pg_upgrade 后不跑 analyze：统计信息不会带过去，升级后第一波查询会集体选错计划，看起来像是新版本变慢了。
