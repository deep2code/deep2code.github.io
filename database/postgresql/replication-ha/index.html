PostgreSQL 复制高可用

🏷️ PostgreSQL,关系数据库

从单机到高可用：复制不是可选项

我吃过一次单点的亏：主库磁盘坏了，恢复了 6 小时，业务停摆到凌晨。从那以后我立了个规矩——只要上生产，复制和备份一起上。PostgreSQL 单机再快也有单点风险：磁盘坏、机房断电、误删表。

生产级方案有两条主线：流复制（Streaming Replication）做高可用，备份（pg_basebackup / pgBackRest / WAL 归档）做灾难恢复。二者缺一不可——复制能扛磁盘与节点故障，但扛不住 DROP TABLE；备份能回到任意时间点（PITR），但不能秒级切换。这一篇把这两件事讲清楚，收尾在性能调优。

复制模式提交行为性能丢数据风险我的选择
同步复制等至少一个备库收到 WAL略慢几乎不丢金融、对账类业务
异步复制主库写完就返回快极端情况丢少量事务大多数互联网业务

流复制架构

主库把 WAL 记录通过 walsender 进程实时发给备库的 walreceiver，备库持续回放（redo）。同步复制（synchronous_commit=on）会等至少一个备库收到 WAL 才返回提交；异步复制不等待，性能高但可能丢少量事务。金融级用同步，互联网业务用异步 + 监控复制延迟。

搭建流复制

在主库创建复制账号并放行：

-- 主库：创建复制专用账号
CREATE ROLE replicator WITH REPLICATION LOGIN PASSWORD 'repl_pass_strong';
-- pg_hba.conf 加一行：
-- host  replication  replicator  10.0.0.0/8  scram-sha-256
SELECT pg_reload_conf();

在备库用 pg_basebackup 克隆主库：

# 备库上（数据目录为空或已清空）
sudo -u postgres pg_basebackup \
    -h 10.0.0.11 -U replicator -D /mnt/pgdata/17/main \
    -Fp -Xs -P -R
# -R 自动写入 standby.signal 与 primary_conninfo
# 完成后启动备库
sudo systemctl start postgresql@17-main

# 验证：主库看 walsender，备库看 walreceiver
psql -c "SELECT client_addr, state, sync_state FROM pg_stat_replication;"   # 主库
psql -c "SELECT pg_is_in_recovery();"                                          # 备库应返回 t

逻辑复制：选择性订阅

流复制是物理层面整库复制。逻辑复制（Logical Replication）可以按表订阅、跨大版本、甚至写到其他数据库（如 Kafka、MySQL），适合分库、灰度升级、数据汇聚：

-- 主库：发布要订阅的表（需 wal_level=logical）
ALTER SYSTEM SET wal_level = 'logical';  -- 需重启
CREATE PUBLICATION app_pub FOR TABLE orders, users;

-- 订阅库：创建相同结构的表并订阅
CREATE SUBSCRIPTION app_sub
    CONNECTION 'host=10.0.0.11 dbname=appdb user=appuser'
    PUBLICATION app_pub;

-- 监控逻辑复制延迟
SELECT pid, state, sync_state, write_lag, flush_lag
FROM pg_stat_subscription;

备份与时间点恢复（PITR）

裸 pg_basebackup 只能恢复到备份时刻；WAL 连续归档 + 基础备份才能恢复到任意时间点（Point-In-Time Recovery）。生产用 pgBackRest 管理整套链路：

# postgresql.conf：开启 WAL 归档到本地/对象存储
wal_level = replica
archive_mode = on
archive_command = 'pgbackrest --stanza=main archive-push %p'
archive_timeout = 300   # 每 5 分钟强制切一个 WAL 文件，避免长时间无新 WAL

# pgBackRest 初始化 stanza 并做一次全量备份
pgbackrest --stanza=main --delta stanza-create
pgbackrest --stanza=main --type=full backup

# 列出备份
pgbackrest info

# 灾难恢复：在新机器上从全量备份 + WAL 恢复到某个时间点
pgbackrest --stanza=main --type=time --target="2026-09-17 14:30:00" restore

自动故障切换：Patroni

手工 promote 备库是运维事故的重灾区。Patroni + etcd 是 PostgreSQL 最成熟的高可用方案：它用 DCS（分布式配置存储）选主、自动监控主库健康、主挂了自动把最优备库提升，并通过 HAProxy/PgBouncer 把应用流量切过去。

我踩过的坑：脑裂双主

早年手动做过一次主库切换，旧主其实没死，只是网络断了。我们把备库 promote 成新主，结果网络恢复后两个主同时接受写入，数据直接分叉，补救花了一整天。从那以后我再也不手动 promote，一律交给 Patroni——它靠 etcd 的租约机制，旧主拿不到锁就自动降级，从根上杜绝脑裂。

一份最小 patroni.yml：

scope: pg_prod
name: pg-node1
restapi:
  listen: 0.0.0.0:8008
etcd3:
  hosts: 10.0.0.21:2379,10.0.0.22:2379,10.0.0.23:2379
bootstrap:
  dcs:
    ttl: 30
    loop_wait: 10
    maximum_lag_on_failover: 1048576   # 1MB
    postgresql:
      use_pg_rewind: true
      parameters:
        max_connections: 500
        shared_buffers: 4GB
        wal_level: replica

性能调优关键参数

说完高可用，再回到单机性能。一个"合理的生产基线"（8C/32G 云主机，OLTP 混合负载）：

shared_buffers = 8GB              # 内存 25%
effective_cache_size = 24GB       # 内存 75%，给优化器估缓存用
work_mem = 32MB                   # 每个排序/哈希操作内存，并发高别开太大
maintenance_work_mem = 1GB        # 建索引/vacuum 用
max_worker_processes = 8
max_parallel_workers_per_gather = 4
max_parallel_maintenance_workers = 4
random_page_cost = 1.1            # SSD/NVMe 上把随机读成本从 4 降到 1.1
effective_io_concurrency = 200    # SSD 并发 IO 深度
jit = off                         # 短查询 JIT 反而慢，OLTP 关

最佳实践清单

  • 至少一主两备，跨可用区：一个同城做同步/半同步，一个异地做异步 + WAL 归档。
  • 备份要定期演练恢复：没做过恢复测试的备份等于没有备份。每季度做一次 PITR 演练。
  • 监控复制延迟与 WAL 归档：pg_stat_replication 延迟、pg_stat_archiver 失败次数，超过阈值告警。
  • 用连接池收敛连接：无论主备，前面都加 PgBouncer transaction 池化。
  • 参数调整用 ALTER SYSTEM：基线先一次调好，后续微调单独追踪。

常见问题 FAQ

Q1：主库挂了，怎么把备库提升为主？

用 Patroni 就自动完成；手工场景：确认主库确实宕了（避免脑裂），在备库执行 pg_promote();，然后把应用连接串切到新主。最关键的是先确认旧主不会再被写，否则会脑裂双主。

Q2：流复制延迟越来越大怎么办？

常见原因是备库回放慢（大查询占 IO、备库硬件差）或网络带宽打满。先看 pg_stat_replication 的 replay_lag 与备库 iostat；再检查是不是备库上跑了重分析查询拖慢了回放。必要时用 hot_standby_feedback=off 配合复制槽，但要警惕主库 WAL 堆积。

Q3：pg_basebackup 会锁住主库吗？

不会。它在主库上做的是只读一致快照，用的是在线备份协议，不阻塞业务读写。它会产生额外的 IO 与 WAL，建议在业务低峰做，并监控 pg_wal 目录。

总结

PostgreSQL 的生产闭环是：单机调优打底 → 流复制做高可用 → WAL 归档做 PITR → Patroni 自动化故障切换。六篇走完，你从架构原理、安装配置、类型系统、索引优化、MVCC 事务一路走到了复制高可用，已经具备独立设计与运维一套生产级 PostgreSQL 集群的能力。剩下的，就是在真实业务里把这些原则反复打磨成肌肉记忆。
