PostgreSQL 复制与故障切换：同步级别、复制槽、pg_rewind 与 Patroni

🏷️ PostgreSQL

PG 的复制只有两种：物理流复制传的是 WAL 字节，从库是主库的逐字节副本；逻辑复制传的是解码后的行变更，粒度到表。两者的能力边界、失效模式和运维风险完全不同，而绝大多数「配了高可用反而更不可用」的事故，都出在同步复制的可用性陷阱、复制槽撑爆磁盘、以及切换后旧主库不能直接当从库这三件事上。

物理流复制：从库是字节级副本

链路是三个进程接力：主库的 walsender 把 WAL 流发出去，从库的 walreceiver 收下来写进本地 pg_wal，再由 startup 进程（持续处于恢复状态）回放。注意回放是单进程串行的，虽然 PG 15 起部分场景能并行预取，但主库多个并发写入会话产生的 WAL，在从库上是一条线回放——这是主从延迟在写入高峰期突然拉大的根本原因，和网络带宽往往无关。

因为传的是字节而不是逻辑变更，物理复制有一组无法绕过的硬限制：从库不能有和主库不同的索引（索引页也是 WAL 的一部分）、从库完全不可写（连临时表都不行，PG 14 之前连 CREATE TEMP TABLE 都会报错）、不能只复制部分表、主从大版本必须完全一致。想要这些能力就只能用逻辑复制。

# ---------- 主库 postgresql.conf ----------
wal_level = replica                  # 逻辑复制则需要 logical，改这个要重启
max_wal_senders = 10                 # 每个从库和每次 pg_basebackup 各占一个
wal_keep_size = 1GB                  # 没有复制槽时的兜底保留量，PG 13 前叫 wal_keep_segments
max_slot_wal_keep_size = 64GB        # PG 13+ 必设：槽最多拖住这么多 WAL，超了宁可让槽失效也不撑爆磁盘
archive_mode = on                    # 归档是 PITR 的前提，也是复制中断后的补救手段
archive_command = 'pgbackrest --stanza=main archive-push %p'   # 失败会让 WAL 一直堆积，必须配监控

# 同步复制：不配 synchronous_standby_names 时 synchronous_commit 的 remote_* 档位没有意义
synchronous_commit = on              # 见下一节的五档对照
synchronous_standby_names = 'ANY 1 (s1, s2)'   # 两个候选里任意一个确认即可，避免单点挂起

# ---------- 从库 postgresql.conf ----------
primary_conninfo = 'host=10.0.0.1 port=5432 user=repl password=xxx application_name=s1'
                                     # application_name 必须和 synchronous_standby_names 里的名字对上
primary_slot_name = 'slot_s1'        # 用槽保证主库不提前删 WAL
hot_standby = on                     # 允许从库接受只读查询，PG 10 起默认就是 on
hot_standby_feedback = on            # 让主库知道从库最老快照，代价是主库表膨胀，见热备冲突一节
max_standby_streaming_delay = 30s    # 回放被查询挡住时最多等 30 秒，超时就取消查询
# 存在 standby.signal 文件才会以从库身份启动，PG 12 起 recovery.conf 已合并进 postgresql.conf

同步级别五档：丢数据窗口与延迟代价

synchronous_commit 的取值不是「开关」，而是五个位置不同的确认点。理解它的唯一正确方式是问：COMMIT 返回成功时，数据最远到了哪里？

取值 COMMIT 返回时数据在哪 丢数据窗口 延迟代价 适用场景
off 只在主库内存的 WAL buffer 里 主库崩溃丢最近约三倍 wal_writer_delay（默认 200ms）的已提交事务 最低，写入吞吐可翻数倍 可重放的日志、埋点、批量导入；不会损坏数据，只会丢最近提交
local 主库磁盘已 fsync 主库整机损坏则丢全部未复制部分 一次本地 fsync 配了同步从库但某些事务不想等远端时，按会话单独设
remote_write 从库进程已 write()，但还没 fsync 从库操作系统崩溃会丢；仅从库进程崩溃不丢 一次网络往返 愿意用一点风险换延迟的折中档
on（默认） 从库 pg_wal 已 fsync 主从同时损坏才丢 一次网络往返加从库 fsync 绝大多数需要零丢失的场景
remote_apply 从库已回放完成，查询立刻能读到 同 on 最高，要等串行回放；主从延迟直接转化为提交延迟 读写分离下要求「写完立刻能在从库读到」时唯一的数据库侧解法

这里有个被反复误解的点：on 只保证 WAL 落到了从库磁盘，不保证从库已经回放。所以在 synchronous_commit = on 下写完立刻去从库读，照样可能读不到——因为那条 WAL 还排在回放队列里。要「立刻可读」只有 remote_apply，而它会把从库的回放速度变成主库的提交速度上限。

synchronous_standby_names 有两种语法，选错会直接影响可用性：FIRST 1 (s1, s2) 表示优先等 s1，只有 s1 不可用才轮到 s2；ANY 1 (s1, s2) 表示任意一个确认即可。生产上除非有明确的机房优先级需求，一律用 ANY，它的可用性明显更好。

❌
同步复制的可用性陷阱：把主库搞挂的经典姿势

只配一个同步从库、且没有候补时，这个从库一挂，主库会挂起所有提交无限期等待——不是报错，是卡住，连接池在几秒内打满，表现和主库宕机一模一样。这就是「为了更可靠而配了同步复制，结果可用性反而下降」的完整因果。正确配置有三条：候选数要严格大于要求确认数（比如两个从库配 ANY 1）；用 ANY 而不是 FIRST；并且监控里必须有「同步从库数量少于要求数」这一条告警。真的遇到从库挂了主库卡住，应急手段是把 synchronous_standby_names 改成空串再 pg_reload_conf()，这是秒级生效且不需要重启的，先救可用性。

复制槽：保证不丢 WAL，也能撑爆你的磁盘

复制槽的作用是让主库记住每个消费者的位置，在对方确认之前绝不删除对应的 WAL。没有槽时，从库断连时间稍长，主库就可能已经回收了它需要的 WAL 段，从库只能报 requested WAL segment has already been removed，然后重做基础备份。

代价是对称的：一个长期下线的从库留下的槽，会让主库的 WAL 无限堆积，直到 pg_wal 撑爆磁盘，数据库停止写入。这是 PG 生产环境最常见的「磁盘满导致停库」原因，而且下线的那台机器往往已经被人忘了。

槽类型 / 场景 它拖住什么 风险 必配的防护
物理槽，从库在线 WAL 段回收 正常，延迟内可控 监控 safe_wal_size
物理槽，从库长期下线 WAL 无限堆积 撑爆 pg_wal，主库停止写入 max_slot_wal_keep_size（PG 13+），超限后槽变 lost，宁可让从库重建也不让主库挂
逻辑槽 WAL 回收 加上 系统目录的死元组回收（catalog_xmin） 除了磁盘，还会让系统表持续膨胀 同上，另外逻辑槽不会自动跨版本升级，大版本升级前要处理
槽 + hot_standby_feedback 主库的死元组回收水位 主库表膨胀，元凶却在从库上 从库设 statement_timeout，别让长查询把主库 xmin 拉住
忘记删除的临时槽 同物理槽 pg_basebackup 异常中断可能留下槽 定期巡检 pg_replication_slots 里 active = false 的条目 
-- 1. 复制槽健康检查：safe_wal_size 是 PG 13+ 才有的关键字段
-- safe_wal_size 为负数或接近 0，意味着这个槽马上就要失效（或者已经在撑爆磁盘）
SELECT slot_name, slot_type, active,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS 落后WAL量,
       pg_size_pretty(safe_wal_size)                                     AS 还能拖多少,
       wal_status,        -- reserved / extended / unreserved / lost
       xmin, catalog_xmin -- 非空说明它在压着主库的死元组回收
FROM   pg_replication_slots
ORDER  BY pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn) DESC;

-- 2. 三种延迟的区别：这是判断「延迟到底卡在哪」的唯一依据
--    write_lag  = 发到从库并 write 完成的耗时（网络问题看这个）
--    flush_lag  = 从库 fsync 完成的耗时（从库磁盘慢看这个）
--    replay_lag = 从库回放完成的耗时（回放单进程跟不上时这个会远大于前两者）
SELECT application_name, client_addr, state,
       sync_state,                       -- async / potential / sync / quorum
       pg_size_pretty(pg_wal_lsn_diff(sent_lsn, replay_lsn)) AS 待回放字节,
       write_lag, flush_lag, replay_lag
FROM   pg_stat_replication;

-- 3. 从库侧看自己落后多久：注意主库空闲时这个值会持续增长，属于正常现象
SELECT pg_is_in_recovery()                                        AS 是从库,
       pg_last_wal_receive_lsn(), pg_last_wal_replay_lsn(),
       now() - pg_last_xact_replay_timestamp()                     AS 回放时间落后;

-- 4. 读写分离的强一致读：写完拿到 LSN，再让从库等到追上为止
-- 主库执行完写事务后取当前位置
SELECT pg_current_wal_insert_lsn();       -- 假设得到 3/AB120F80
-- 从库上判断是否已追上，没追上就退避重试或回退到主库读
SELECT pg_last_wal_replay_lsn() >= '3/AB120F80'::pg_lsn AS 可以读了;

-- 5. 兜底告警：同步从库数量少于要求数时必须告警，否则主库会在从库挂掉时静默卡住
SELECT current_setting('synchronous_standby_names') AS 配置,
       count(*) FILTER (WHERE sync_state IN ('sync', 'quorum')) AS 当前同步从库数
FROM   pg_stat_replication;

热备查询冲突：从库的长查询与 WAL 回放互相为敌

从库既要回放主库传来的 WAL，又要服务只读查询，这两件事会在同一个页上撞车：主库上 VACUUM 清掉了某些死元组，这条 WAL 传到从库要回放，但从库上有个长查询的快照还需要看到那些元组。PG 只能二选一，选择权由 max_standby_streaming_delay 控制。

策略 配置 牺牲什么 表现 适用
优先保查询 max_standby_streaming_delay 设大（如 10min）或 -1 无限等 主从延迟 回放挂起，从库越落后，切换时 RPO 越差 专职报表从库，且不承担故障切换职责
优先保延迟 max_standby_streaming_delay = 30s（默认 30s） 查询会被杀 报 canceling statement due to conflict with recovery，应用必须能重试 承担切换职责的从库，默认就该这样
从源头减少冲突 从库 hot_standby_feedback = on 主库表膨胀 从库把最老快照 xmin 上报主库，主库 VACUUM 不再清理从库还需要的元组 读多且查询较长的从库，但要接受主库膨胀并监控它
彻底隔离 从库设 statement_timeout，长查询拆小或走物化视图 业务要改 冲突概率大幅下降 最健康的做法，前三种都是补丁

要特别注意 hot_standby_feedback 的连带效应：它把从库的膨胀压力转移到了主库。见过不少案例是主库表持续膨胀、查遍主库找不到长事务，元凶其实是某台从库上跑了半小时的报表。排查时要看主库 pg_replication_slots 的 xmin 字段。

逻辑复制：能力换限制

逻辑复制走的是逻辑解码：pgoutput 插件把 WAL 还原成行级变更，按发布订阅关系投递。它解锁了物理复制做不到的事，也带来一组必须提前知道的限制。

维度 物理流复制 逻辑复制
复制粒度 整个实例，所有数据库一起 按表，可以只发布几张表、甚至只发布 INSERT
跨版本 主从大版本必须一致 可以跨大版本，这是零停机大版本升级的主流路径
目标端可写 完全只读 可写，可有额外的索引和表，可做双向与多源汇聚
DDL 自动跟随（本来就是字节复制） 完全不复制 DDL，加列必须先在订阅端加，否则复制直接中断
序列值 跟随 不复制，切换前必须手工 setval，否则新主库主键冲突
对表的要求 无 需要主键，或显式设 REPLICA IDENTITY FULL，否则 UPDATE/DELETE 无法定位行
初始化 pg_basebackup 物理拷贝 默认全表 COPY，大表上耗时长且会拖住槽，可用 copy_data = false 加手工初始化
大事务 流式跟随 PG 14 之前要等事务提交才开始解码，大事务会造成延迟尖刺；PG 14 起支持 streaming
TRUNCATE 与大对象 跟随 TRUNCATE 需 PG 11+，大对象（large object）始终不复制 
-- ============ 发布端（源库，wal_level = logical）============
CREATE PUBLICATION pub_orders FOR TABLE orders, order_items;
-- 也可以只发布部分操作，或者 PG 15+ 的行过滤与列过滤
CREATE PUBLICATION pub_insert_only FOR TABLE audit_log WITH (publish = 'insert');
CREATE PUBLICATION pub_cn FOR TABLE users (id, name, region) WHERE (region = 'cn');  -- PG 15+

-- 没有主键的表必须显式指定行标识，否则 UPDATE 与 DELETE 会报错中断复制
ALTER TABLE legacy_table REPLICA IDENTITY FULL;      -- 整行做标识，代价是 WAL 变大
-- 更好的做法是补一个唯一非空索引再指定它
ALTER TABLE legacy_table REPLICA IDENTITY USING INDEX legacy_table_uk;

-- ============ 订阅端（目标库，表结构要先自己建好）============
CREATE SUBSCRIPTION sub_orders
  CONNECTION 'host=10.0.0.1 dbname=app user=repl password=xxx'
  PUBLICATION pub_orders
  WITH (copy_data = true, streaming = on);   -- streaming 需要 PG 14+，避免大事务延迟尖刺

-- 监控：初始同步进度与复制状态
SELECT subname, srrelid::regclass AS 表, srsubstate  -- i 初始化 d 拷贝中 s 同步完 r 正常流式
FROM   pg_subscription_rel r JOIN pg_subscription s ON s.oid = r.srsubid;
SELECT subname, received_lsn, latest_end_lsn, last_msg_receipt_time
FROM   pg_stat_subscription;

-- 复制中断的典型修复：目标端缺列或有冲突数据时，先修结构再跳过冲突事务
ALTER SUBSCRIPTION sub_orders DISABLE;
-- 在订阅端补上缺失的列，然后（PG 15+ 可用 skip_lsn 精确跳过）
ALTER SUBSCRIPTION sub_orders SKIP (lsn = '3/AB120F80');
ALTER SUBSCRIPTION sub_orders ENABLE;

-- 切换到新库之前，务必同步所有序列值，这一步漏了必然主键冲突
SELECT setval('orders_id_seq', (SELECT max(id) FROM orders) + 1000);

读写分离的一致性：写完立刻读读不到

这不是 bug，是异步复制的定义。主库提交返回时，从库可能还没收到那条 WAL，更可能还没回放完。任何「先写后跳转到详情页」的流程都会撞上它。三种解法各有代价，选哪个取决于业务能接受什么。

解法 实现方式 代价 适用
关键读走主库 DAO 层按操作类型路由，写后读、支付、对账一律走主库 主库读压力回来一部分 首选。最简单、最可控，80% 的场景到这里就够了
按 LSN 等从库追上 写事务后取 pg_current_wal_insert_lsn() 带给客户端，读请求带着它，从库比较 pg_last_wal_replay_lsn()，没追上就退避或回落主库 实现复杂，多一次往返；等待期间延迟不可控 读远大于写、又必须保证单调读的场景
会话粘滞 同一用户在写操作后的 N 秒内固定读主库 N 取大了主库压力回流，取小了仍可能读旧数据 快速上线的折中方案，本质是概率性保证
synchronous_commit = remote_apply 数据库侧保证提交返回时从库已回放 提交延迟等于回放延迟，写入吞吐显著下降 写少读多且强一致要求硬的小库；写密集库上会成为瓶颈

故障切换：timeline 分叉与 pg_rewind

pg_ctl promote 把从库提升为主库时，PG 会递增 timeline ID（从 1 变成 2），并写一个 .history 文件记录分叉点。timeline 的存在是为了防止两条不同的历史被混起来用——这也直接导致了切换演练里最容易翻车的一步。

旧主库恢复后不能直接当新主库的从库。原因是旧主库在失联前可能已经写入并落盘了一些 WAL，而这些 WAL 从来没传到新主库。它的历史领先于新主库，二者在分叉点之后是两条不同的历史。直接挂上去，轻则报 timeline 不匹配拒绝启动，重则数据静默不一致。必须先用 pg_rewind 把旧主库回退到分叉点，或者干脆重做基础备份。

stateDiagram-v2 [*] --> 主库A_timeline1 主库A_timeline1 --> 从库B_跟随T1: B 流式复制 A 的 WAL 主库A_timeline1 --> A失联: 机房网络中断或宕机 从库B_跟随T1 --> 新主库B_timeline2: 执行 pg_ctl promote 时间线递增 A失联 --> 旧主A_数据可能领先: A 落盘过未传出的 WAL 旧主A_数据可能领先 --> 脑裂风险: 直接拉起 A 且 VIP 未切换干净 旧主A_数据可能领先 --> pg_rewind回退: 按 B 的时间线历史裁掉分叉后的改动 pg_rewind回退 --> A作为从库跟随B: 从分叉点开始重新拉取 timeline2 的 WAL 旧主A_数据可能领先 --> 重做基础备份: rewind 失败或不满足前提时的兜底 重做基础备份 --> A作为从库跟随B 新主库B_timeline2 --> A作为从库跟随B: 只有到这一步切换才算真正完成 note right of pg_rewind回退 前提是源库开了 wal_log_hints 或 data checksums 并且旧主必须先干净关闭一次 rewind 会丢弃旧主分叉后的本地改动 end note
切换步骤 命令或动作 最容易翻车的点
0. 确认旧主真的下线 断电、隔离网络、或停容器（fencing） 不做隔离就切换等于制造脑裂，两个都能写是最坏的结果，事后无法自动合并
1. 选延迟最小的从库 比较各从库 pg_last_wal_replay_lsn() 随手挑一台可能丢掉更多事务；异步复制下 RPO 就是这个差值
2. 等它回放完已收到的 WAL 对比 pg_last_wal_receive_lsn() 与 pg_last_wal_replay_lsn() 没放完就 promote 会白丢已经收到的事务
3. 提升 pg_ctl promote 或 SELECT pg_promote() timeline 递增，其他从库的 primary_conninfo 必须一起改指向新主
4. 切换流量 改 VIP、DNS 或连接池（PgBouncer / HAProxy）指向 应用连接池不重连；DNS TTL 太长；只改一半导致部分写仍打向旧主
5. 其他从库重新指向 改 primary_conninfo 并重启，必要时 pg_rewind 其他从库的 timeline 也可能落在分叉前，需要 recovery_target_timeline = 'latest'
6. 旧主重新加入 pg_rewind 或重做基础备份 直接挂上去必定失败或不一致；pg_rewind 要求源库开了 wal_log_hints 或数据校验和，且旧主先干净关闭过一次
7. 复制槽与同步配置 在新主库重建槽、重设 synchronous_standby_names 物理槽不会跟随切换（PG 17 才支持槽同步），忘了重建会在下一次故障时暴露 
# ---------- 切换演练脚本（务必先在预发环境跑通）----------
# 步骤 1：挑延迟最小的从库，并确认已收到的 WAL 都回放完了
psql -h standby1 -Atc "SELECT pg_last_wal_receive_lsn(), pg_last_wal_replay_lsn()"

# 步骤 2：提升。pg_promote 可以在 SQL 里做，返回后需要轮询确认已退出恢复状态
psql -h standby1 -Atc "SELECT pg_promote(wait => true, wait_seconds => 60)"
psql -h standby1 -Atc "SELECT pg_is_in_recovery()"   # 必须返回 f 才算提升成功
psql -h standby1 -Atc "SELECT timeline_id FROM pg_control_checkpoint()"  # 应该已经加一

# 步骤 3：旧主库回退后再加入。前提检查一个都不能少
#   a) 旧主必须先干净关闭：pg_ctl -D $PGDATA stop -m fast
#   b) 源库（新主）需要 wal_log_hints = on 或初始化时开了 data checksums
#   c) 先用 --dry-run 确认它打算做什么，再真跑
pg_ctl -D /var/lib/pgsql/data stop -m fast
pg_rewind --target-pgdata=/var/lib/pgsql/data \
          --source-server="host=standby1 port=5432 user=postgres dbname=postgres" \
          --progress --dry-run
pg_rewind --target-pgdata=/var/lib/pgsql/data \
          --source-server="host=standby1 port=5432 user=postgres dbname=postgres" \
          --progress
# rewind 之后 primary_conninfo 需要指向新主，并创建 standby.signal
touch /var/lib/pgsql/data/standby.signal
pg_ctl -D /var/lib/pgsql/data start

# 兜底方案：rewind 前提不满足或失败，就重做基础备份（大库耗时以小时计，要提前评估）
pg_basebackup -h standby1 -U repl -D /var/lib/pgsql/data \
              -Fp -Xs -P -R -C --slot=slot_old_primary
#   -Xs 流式取 WAL，避免备份期间 WAL 被回收
#   -R  自动生成 primary_conninfo 与 standby.signal
#   -C --slot 顺便创建复制槽，避免备份完成前 WAL 被删

# 演练结束前务必检查：新主库上的复制槽是否都重建了
psql -h standby1 -Atc "SELECT slot_name, active FROM pg_replication_slots"

自动切换：为什么不要自己写脚本

自动切换的难点从来不是「检测到主库挂了就 promote」，而是如何在网络分区下确保只有一个节点认为自己是主库。这需要一个外部的、有共识能力的仲裁者，以及对旧主的隔离手段。自己写的脚本通常只解决了检测，于是把偶发的网络抖动变成了永久的数据分叉。

⚠️
自动切换不是「越快越好」

把故障检测阈值调得过于灵敏，结果是一次 GC 停顿、一次网络抖动就触发切换，而每次切换都要付出连接中断、缓存冷启动、其他从库重新指向的代价。成熟做法是把检测窗口设在十秒量级，并且区分「主库进程没了」和「主库响应慢」——后者往往不该切。另外 Patroni 的 maximum_lag_on_failover 必须设：它限制候选从库允许落后的字节数，避免为了尽快恢复可用性而选了一个落后很多的从库，把 RPO 悄悄放大。

最容易踩的坑

❌
这些坑每条都有真实事故对应
  • 只配一个同步从库：它一挂，主库挂起所有提交无限期等待，表现和主库宕机一样。候选数必须大于要求确认数，并且用 ANY 而不是 FIRST。
  • 以为 synchronous_commit = on 就能写后立刻从从库读到：它只保证 WAL 落到从库磁盘，不保证已回放。要立刻可读只有 remote_apply。
  • 下线从库却不删复制槽：主库 WAL 无限堆积直到磁盘满、数据库停写。PG 13+ 必须设 max_slot_wal_keep_size 兜底。
  • 不监控 safe_wal_size：只看磁盘使用率往往来不及，等发现时已经只剩几 GB。
  • 在从库开了 hot_standby_feedback 却不管从库长查询：主库表持续膨胀而主库上查不到长事务，元凶在从库。要看主库 pg_replication_slots.xmin。
  • 把 max_standby_streaming_delay 设成 -1 图省事：回放会被长查询无限挂起，从库越落后，真出故障时 RPO 越差。
  • 用主从延迟的秒数当唯一指标：主库空闲时 pg_last_xact_replay_timestamp() 的差值会持续增长，这是正常现象。要同时看 LSN 字节差和 replay_lag。
  • 混淆三种 lag：write_lag 大是网络问题，flush_lag 大是从库磁盘问题，replay_lag 大是回放单进程跟不上，三者的修法完全不同。
  • 切换后把旧主库直接挂成从库：它的历史可能领先于新主，必须先 pg_rewind 或重做基础备份。而 pg_rewind 要求源库开了 wal_log_hints 或数据校验和——这个前提要在建库时就准备好，事后开启需要重启甚至重建。
  • 切换时不隔离旧主：VIP 或连接池只切了一半，两边都在写，事后无法自动合并。fencing 是切换流程的第 0 步而不是可选项。
  • 忘了切换后重建复制槽：物理槽不会跟随切换（PG 17 才有槽同步），漏了这一步会在下一次故障时才暴露。
  • 用逻辑复制做主备却忘了序列值：逻辑复制不复制序列，切换后新主的自增主键会从旧值开始，必然主键冲突。切换前必须 setval。
  • 逻辑复制的订阅端先加了列或改了表结构顺序：DDL 不被复制，发布端加列后订阅端缺列会直接中断复制，正确顺序是先订阅端、后发布端。
  • 给没有主键的表做逻辑复制：UPDATE 与 DELETE 无法定位行，复制会报错停住。必须补主键或设 REPLICA IDENTITY。
  • 用 Keepalived 加脚本当自动切换方案：VRRP 没有数据层共识，网络分区时两侧都可能认为自己是主。要么上 Patroni，要么就人工切换加演练。
