PostgreSQL 深度原理：堆表、MVCC 与 WAL

🏷️ PostgreSQL

PostgreSQL 存储层的一切行为，都能从两个设计决定推导出来：表是无序的堆，所有索引都是二级索引；行的新版本直接追加进堆表，旧版本原地留着。这两条决定了 HOT 更新为什么存在、表膨胀为什么必须靠 VACUUM、事务 ID 为什么会回卷、以及为什么 PG 只需要一份 WAL 就同时干了 MySQL 里 redo log 加 binlog 两件事。本文只讲这条主线。

堆表与 ctid：PG 没有聚簇索引

PG 的表叫 heap，物理上就是一串 1GB 一个的数据文件，每个文件按 8KB 切成页。行存在哪一页、页内哪个位置，完全由插入顺序和空闲空间决定，没有任何索引能决定行的物理顺序（CLUSTER 只是一次性按索引顺序重排，之后的更新立刻会打破它）。

行的物理地址是 ctid，6 字节，前 4 字节是块号，后 2 字节是页内行指针编号。所有索引的叶子节点存的都是 ctid，主键索引和一个普通 B-tree 索引在结构上没有任何区别。这就是 PG 与 MySQL InnoDB 最根本的分歧：InnoDB 的表本身就是主键 B+ 树，二级索引叶子存主键值，因此有回表；PG 没有回表这个概念，但代价出现在写入侧。

元组头与可见性判定

每个元组前面有 23 字节的 HeapTupleHeaderData，MVCC 全靠其中三个字段：t_xmin 是插入这个版本的事务 ID；t_xmax 是删除或更新它的事务 ID，0 表示还活着；t_ctid 正常指向自己，发生 HOT 更新时指向页内的新版本。另外 t_infomask 里有一组提交状态提示位（hint bits），用来避免每次可见性判断都去查 pg_xact（旧称 clog）。

判定规则简化后是：xmin 已提交且早于我的快照，xmax 为空或其事务未提交或晚于我的快照，则这个版本对我可见。这里有个常被忽略的后果：hint bits 是第一次读到元组时才写上去的，所以一次纯 SELECT 也会产生脏页和 WAL，刚导完数据的第一次全表扫描往往慢得异常，这不是 bug。MySQL 侧的 Read View 与可见性判定细节详见站内 MySQL 深度原理，此处不展开。

-- 直接看页内元组，确认 HOT 链是否形成（需要 pageinspect 扩展）
CREATE EXTENSION IF NOT EXISTS pageinspect;

-- t_ctid 不等于自身 (块号, lp) 时说明它指向新版本
-- lp_flags = 1 正常元组，= 2 是 HOT 剪枝后留下的重定向行指针 LP_REDIRECT
SELECT lp                 AS 行指针号,
       lp_flags,
       t_xmin, t_xmax, t_ctid,
       to_hex(t_infomask) AS infomask_hex
FROM   heap_page_items(get_raw_page('orders', 0));

-- 统计 HOT 命中率：高频更新表低于 80% 就要回头查是不是更新到了索引列
SELECT relname,
       n_tup_upd     AS 更新总数,
       n_tup_hot_upd AS HOT更新数,
       round(100.0 * n_tup_hot_upd / nullif(n_tup_upd, 0), 1) AS hot_ratio_pct,
       n_dead_tup
FROM   pg_stat_user_tables
WHERE  n_tup_upd > 10000
ORDER  BY hot_ratio_pct NULLS FIRST;

新版本留在堆里：两种 MVCC 设计的四个后果

PG 的 UPDATE 本质是「插入一条新元组 + 给旧元组写上 xmax」，旧版本原地保留在堆表里，和活数据混在同一批页中。InnoDB 则原地更新数据页，把旧版本写进 undo log，读旧版本时沿 roll pointer 回溯版本链。就这一个差别，衍生出四个方向完全相反的工程后果。

后果维度 PostgreSQL 旧版本留堆内 MySQL InnoDB 旧版本进 undo 实际影响
读旧版本的代价 旧版本就是一条普通元组，直接读，不用回溯链表 要沿版本链逐条 undo 反向重建 长事务下 PG 的读延迟基本不变，MySQL 随版本链长度线性劣化
空间回收 必须靠 VACUUM 标记复用，不会自动缩表 purge 线程自动清理 undo，对用户透明 PG 是少数需要把「表膨胀率」当常规监控指标的数据库
写放大位置 整行重写，索引列变了还要写全部索引 数据页原地改，undo 记录较小 PG 上宽表改一个小字段特别贵，靠 HOT 抢救
回滚成本 回滚几乎零成本，新元组直接变死元组 按 undo 逐条反向应用，大事务回滚可能比执行还慢 PG 上误更新 1 亿行后 ROLLBACK 是瞬间的，但留下 1 亿死元组等着 VACUUM

HOT 更新：PG 最重要的写优化

Heap-Only Tuple 的思路是：如果新版本不需要被任何索引重新指向，就干脆不动索引。触发条件只有两条，必须同时满足：本次 UPDATE 没有修改任何被索引引用的列；新版本能放进旧版本所在的同一个 8KB 页。满足时旧元组的 t_ctid 指向页内新元组，形成 HOT 链，索引仍然指向链头，扫描时沿链往下找可见版本。

这解释了两个经典现象。第一，给表加了几个索引之后 UPDATE 突然变慢——不只是索引维护本身变贵，而是被索引覆盖的列变多后，业务更新命中索引列的概率上升，HOT 命中率掉下来，一次更新从写 1 个堆页变成写 1 个堆页加 N 个索引，WAL 量同步翻几倍。第二，fillfactor 为什么要留余量——默认 100 意味着页被填满，第一次更新就因为放不下而被迫换页，HOT 直接失效；高频更新表设到 80 到 90，用一点空间换掉大量索引写入。

✅
HOT 的隐藏福利：页内剪枝不依赖 VACUUM

HOT 链上已经没人需要的中间版本，可以在普通 SELECT 顺手触发的页内剪枝（page pruning）里就地清掉，因为这些版本从来没有索引条目指向它们，不需要先删索引再删堆。所以一张 HOT 命中率高的表，膨胀速度天然就慢。反过来说，「把不参与查询条件的列从索引里摘出去」这种看似跟膨胀无关的改动，往往能显著压低膨胀率。

VACUUM 与表膨胀

三个必须分清的事实：普通 VACUUM 不缩文件，它只把死元组空间标记为可复用，表文件大小原样不动，膨胀出来的 200GB 不会还给操作系统，但后续插入会填进这些空洞；VACUUM FULL 会重写整表和全部索引，能真正缩小文件，但持有 ACCESS EXCLUSIVE 锁，期间连 SELECT 都进不来，还要一份等量的额外磁盘空间；生产上要缩表用 pg_repack，它建影子表加触发器在线追平，只在最后换名字时短暂加锁。

VACUUM 还有两件比「清垃圾」更关键的职责：维护 visibility map（Index Only Scan 能否生效的前提）和推进冻结水位（防 XID 回卷）。所以「我们表很少删数据，不用管 VACUUM」是错的。

手段 锁级别 是否缩小文件 额外空间 适用场景与失效点
VACUUM 与 autovacuum SHARE UPDATE EXCLUSIVE，不阻塞读写 否，仅尾部连续空页会截断 无 常态运行。有长事务或旧复制槽时死元组根本无法回收，跑一万次也没用
VACUUM FULL ACCESS EXCLUSIVE，读写全阻塞 是 约等于表加索引大小 只在维护窗口对小表用。磁盘快满时执行它会直接把库写挂
pg_repack 只在最后切换瞬间加 ACCESS EXCLUSIVE 是 约等于表加索引大小 生产缩表首选。表必须有主键或唯一非空索引，否则无法工作
REINDEX CONCURRENTLY 不阻塞读写 仅索引 约等于索引大小 只治索引膨胀，PG 12 起可用；失败会留下 _ccnew 后缀的残留索引要手工清
TRUNCATE ACCESS EXCLUSIVE 是，直接换新文件 无 清空表最快的方式，而且可以在事务里回滚，这点和 MySQL 不同

autovacuum 的触发公式是 autovacuum_vacuum_threshold + autovacuum_vacuum_scale_factor × 表估算行数。默认 50 + 0.2 × n 意味着一张 5 亿行的表要攒够 1 亿死元组才触发一次，而且触发时是一次巨大的 IO 冲击。大表必须单独下调。

autovacuum_vacuum_cost_limit -1，即继承 vacuum_cost_limit 的 200 限速太狠，autovacuum 永远追不上写入速度 1000 到 3000，NVMe 上可更高

-- 膨胀排查第一刀：死元组占比与上次 autovacuum 时间
SELECT schemaname || '.' || relname                  AS 表名,
       pg_size_pretty(pg_total_relation_size(relid))  AS 总大小,
       n_live_tup, n_dead_tup,
       round(100.0 * n_dead_tup / nullif(n_live_tup + n_dead_tup, 0), 1) AS dead_pct,
       last_autovacuum, last_autoanalyze
FROM   pg_stat_user_tables
WHERE  n_dead_tup > 100000
ORDER  BY n_dead_tup DESC
LIMIT  20;

-- 给大表单独调小触发阈值并放开限速
ALTER TABLE orders SET (
  autovacuum_vacuum_scale_factor  = 0.01,
  autovacuum_analyze_scale_factor = 0.02,
  autovacuum_vacuum_cost_limit    = 2000,
  fillfactor                      = 85   -- 注意：只影响之后新写入的页，老页要重组才生效
);

-- 死元组清不掉时，元凶一定在这三类里（按出现频率排序）
SELECT 'long_xact' AS 类型, pid::text AS 标识, xact_start AS 起始时间,
       now() - xact_start AS 持续, state AS 备注
FROM   pg_stat_activity
WHERE  xact_start IS NOT NULL AND now() - xact_start > interval '5 min'
UNION ALL
SELECT 'repl_slot', slot_name, NULL, NULL,

事务 ID 回卷：PG 最危险的运维问题

XID 是 32 位且循环使用的。可见性比较用的是回绕比较：当前 XID 往前 20 亿算过去、往后 20 亿算未来，因此任何元组的 xmin 都不能比当前 XID 老过 20 亿，否则会被判成「未来事务」而凭空消失。解法是冻结：VACUUM 把足够老的元组标记为 frozen，表示对所有事务永远可见，从而把水位往前推。

到了 autovacuum_freeze_max_age（默认 2 亿）时，即使你把 autovacuum 整个关掉，PG 也会强制启动 anti-wraparound vacuum，它不给普通 DDL 让路，kill 掉下一轮还会起来。继续拖下去的终点是数据库拒绝写入。

age(datfrozenxid) 水位 数据库行为 你该做什么
小于 2 亿 正常，常规 autovacuum 顺带推进冻结 保持监控即可
达到 2 亿 强制启动 anti-wraparound vacuum，无法取消，IO 明显上升 检查是否有长事务卡住冻结，调高 cost_limit 让它快点跑完
约 10 亿以上 日志开始输出 warning，提示剩余可用事务数 按故障处理：清长事务、废弃复制槽、prepared transaction
剩余约 4000 万 每次提交都告警，强烈要求立刻 VACUUM 停掉业务写入，手工对最老的表跑 VACUUM FREEZE
剩余约 300 万 拒绝一切写入，要求进单用户模式修复 停库、postgres --single 下 VACUUM，这是小时级停机 
-- 库级水位：20 亿是硬上限，超过 15 亿就该当事故处理
SELECT datname,
       age(datfrozenxid)                                AS xid_age,
       2147483648 - age(datfrozenxid)                   AS 剩余可用事务数,
       round(100.0 * age(datfrozenxid) / 2147483648, 1) AS 使用率pct
FROM   pg_database
ORDER  BY xid_age DESC;

-- 定位具体是哪张表拖住了水位，relkind 里的 t 是 TOAST 表，最容易被漏掉
SELECT c.oid::regclass                                  AS 表名,
       c.relkind,
       age(c.relfrozenxid)                              AS xid_age,
       pg_size_pretty(pg_total_relation_size(c.oid))     AS 大小
FROM   pg_class c
WHERE  c.relkind IN ('r', 'm', 't')
  AND  age(c.relfrozenxid) > 150000000
ORDER  BY age(c.relfrozenxid) DESC
LIMIT  20;

-- 对症手工冻结，PARALLEL 只加速索引部分
VACUUM (FREEZE, VERBOSE, PARALLEL 4) orders;
❌
「我们数据量小，不会回卷」是错的

回卷取决于消耗了多少事务号，和数据量无关。一个每秒 5000 TPS 的小库也能在几天内烧掉 20 亿 XID。更常见的翻车姿势是：每次轮询都开显式事务的框架、以及被忽略的子事务——每个 SAVEPOINT 和 PL/pgSQL 里的 EXCEPTION 块都会分配一个子事务 ID。另外冻结水位靠写事务推进，一个只读的备库自己不冻结，主库卡住水位备库也跟着卡。

WAL：一份日志干两件事

WAL 的核心约定是 write-ahead：任何数据页的改动在刷进数据文件之前，描述这次改动的 WAL 记录必须先落盘，这样崩溃后从最近一次 checkpoint 开始重放就能恢复。WAL 按 16MB 一个段文件写在 pg_wal/ 下，位置用 LSN 标识（形如 3/AB120F80 的 64 位字节偏移），页头的 pd_lsn 记录这一页最后被哪条 WAL 改过，回放时靠它跳过已经应用的改动。

full_page_writes 必须开着的原因是页断裂：磁盘原子写单位是 512 字节或 4KB，8KB 的页在掉电时可能只写进去一半，而 WAL 记录是增量的，往一个半新半旧的页上重放增量只会得到垃圾。所以 checkpoint 之后每个页第一次被修改时，整页镜像会被塞进 WAL 当回放基准。代价是 WAL 量显著变大，尤其在 checkpoint 刚结束那一阵——这也是 checkpoint_timeout 设得太短会让 WAL 量暴涨的原因。

参数 默认值 含义与调错后果
synchronous_commit on on 提交等 WAL fsync；local 只等本机、忽略同步备库；off 不等，崩溃丢最近约三倍 wal_writer_delay（默认 200ms）的已提交事务，但不会损坏数据。可按会话或按事务设置，日志类写入单独关掉是常见优化。远端几档见复制篇
full_page_writes on 关掉能省三成以上 WAL，但只有底层存储保证 8KB 原子写时才允许；普通文件系统上关掉等于赌永不掉电
max_wal_size 1GB 太小会频繁触发 checkpoint，全页写反复重来，写入毛刺明显；写密集库设 16GB 到 64GB，代价是崩溃恢复时间变长
checkpoint_completion_target 0.9（PG 14 起，此前 0.5） 把刷脏页摊到 checkpoint 周期的这个比例内完成。老版本的 0.5 是 IO 尖刺的常见成因
wal_compression off 压缩全页镜像，用 CPU 换 WAL 体积。PG 15 起支持 lz4 与 zstd，全页写多的库收益明显
wal_level replica minimal 无法做物理复制和 PITR；逻辑复制必须是 logical。改动需要重启

最容易踩的坑

❌
这些坑每条都有真实事故对应
  • 以为 VACUUM 会释放磁盘空间：普通 VACUUM 只标记可复用，df 上看不到任何变化。要缩文件只有 VACUUM FULL 或 pg_repack。
  • 在大表上用 VACUUM FULL 救膨胀：ACCESS EXCLUSIVE 锁把所有读写堵死，还要一份等量额外磁盘，磁盘快满时执行等于自杀。
  • 大表沿用默认 scale_factor = 0.2：5 亿行的表要攒 1 亿死元组才触发，膨胀早就发生了。必须按表调到 0.01 量级。
  • 只盯 n_dead_tup 不查长事务：只要有一个 idle in transaction 的连接持着旧快照，VACUUM 什么也回收不了，先查 pg_stat_activity。
  • 忘了下线备库留下的复制槽：它会同时阻止 WAL 删除和死元组回收，撑爆磁盘又抬高 XID 年龄，是最隐蔽的双杀。
  • fillfactor 保持默认 100：高频更新表页被填满，HOT 立刻失效，每次更新都写全部索引。改成 85，但注意只对之后新写入的页生效，老页要重组。
  • 给宽表无脑加索引：PG 里索引列一变就要更新所有索引，不是只更新相关的那个，索引个数直接等于写放大倍数。
  • 认为数据量小就不会 XID 回卷：回卷只看消耗的事务号数量，空转的显式事务和 PL/pgSQL 的 EXCEPTION 子事务都在烧 XID。
  • 看到 anti-wraparound vacuum 占 IO 就 kill：它立刻会重启，而这段时间水位继续上涨。正确做法是解除阻塞它的长事务并调高 cost_limit。
  • 为省 WAL 关掉 full_page_writes：没有 8KB 原子写保证的存储上，一次掉电就是 WAL 也修不回来的坏页，而且备份可能已被污染。
  • 把 checkpoint_timeout 调小以为能缩短恢复时间：checkpoint 变频繁会让全页写反复重来，WAL 量和 IO 毛刺一起涨。该调的是 max_wal_size 和 checkpoint_completion_target。
  • 以为 synchronous_commit = off 会损坏数据：它只丢最近几百毫秒已返回成功的事务，文件一致性不受影响。真正会损坏数据的是 fsync = off，那个参数在生产没有任何借口。
  • 导入数据后第一次查询慢就怀疑索引：那是 hint bits 首次写入加 visibility map 尚未建立，导完手工跑一次 VACUUM ANALYZE 就好。
