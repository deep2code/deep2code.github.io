PostgreSQL 数据类型选择与代价

🏷️ PG 数据类型

类型选错的代价不是「不太优雅」，而是真金白银：用 float8 存金额的系统迟早会在对账时差出几分钱；用 timestamp 存时间的系统一到跨时区或夏令时就开始错乱；把 varchar(20) 当性能优化写满全库，等到手机号要存国际号段时才发现改长度要 ALTER TABLE。这篇按「选什么、为什么、选错了迁移要付多少代价」来组织，重点是那些改起来要重写全表或者根本改不动的决定。

顺带提一个影响所有变长类型的机制：TOAST。一行超过约 2 KB（页大小的四分之一）时，PG 会把大的变长字段压缩，压不下去就挪到附属的 TOAST 表里，主表只留一个指针。好处是宽表不会撑爆页；代价是访问被 TOAST 化的字段要多一次 IO，而且更新一个大 jsonb 字段会连带整行重写，这是 jsonb 大字段高频更新场景性能塌陷的根因。

数值：钱的问题只有一个正确答案

float8 是 IEEE 754 二进制浮点，十进制的 0.1 在二进制里是无限循环小数，存进去就已经有误差。这不是「精度够不够」的问题，而是「每一笔都带误差、累加后必然对不上」的问题。

类型存储精度运算速度用在哪 / 绝对不要用在哪
smallint（int2）2 字节正负 32767最快枚举下标、小计数；容易溢出，业务量级不确定时别用
integer（int4）4 字节约正负 21 亿最快大多数计数与外键；自增主键用它的表在日活千万级会耗尽
bigint（int8）8 字节约正负 9.2 乘 10 的 18 次方快主键、订单号、以分为单位的金额；默认就选它，别为省 4 字节冒溢出风险
numeric(p,s)变长，约每 4 位十进制 2 字节加 8 字节头精确，最多 131072 位整数部分慢，软件实现的十进制运算金额、汇率、计费单价必须用它；不要拿它存自增 ID 或高频累加的计数器
real（float4）4 字节约 6 位有效数字快传感器采样、比例系数；绝不可存钱
double precision（float8）8 字节约 15 位有效数字快科学计算、地理距离中间值；绝不可存钱
-- 一分钟验证浮点为什么不能存钱
SELECT 0.1::float8 + 0.2::float8 = 0.3::float8 AS float_eq,   -- false
       0.1::numeric + 0.2::numeric = 0.3::numeric AS num_eq;  -- true
SELECT sum(0.01::float8) FROM generate_series(1, 1000000);     -- 结果不是 10000
SELECT sum(0.01::numeric) FROM generate_series(1, 1000000);    -- 精确 10000.00

-- 正确的金额建表：numeric 带精度，或 bigint 存最小货币单位
CREATE TABLE payment (
    -- identity 是 SQL 标准写法，序列由列「拥有」，删列即删序列，
    -- 也不能被误插入显式值（除非写 OVERRIDING SYSTEM VALUE）
    id          bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    amount      numeric(18, 2) NOT NULL CHECK (amount >= 0),   -- 精确到分
    amount_cent bigint         NOT NULL CHECK (amount_cent >= 0), -- 另一种流派：存分
    currency    char(3)        NOT NULL,                        -- ISO 4217 定长，char 的罕见合理用法
    rate        numeric(20, 10),                                -- 汇率要高小数位
    created_at  timestamptz    NOT NULL DEFAULT now()
);

-- serial 与 identity 的实质差别：serial 只是「建序列 + 设默认值」的语法糖
-- 它留下的序列是独立对象，容易出现三类问题：
--   1) 删列后序列残留，或改表名后序列名不一致
--   2) 应用显式插入 id 不会推进序列，后续自增撞唯一键
--   3) 权限要单独授予序列的 USAGE，漏授就报 permission denied for sequence
-- 存量表迁到 identity：
ALTER TABLE legacy_order ALTER COLUMN id DROP DEFAULT;
ALTER TABLE legacy_order ALTER COLUMN id ADD GENERATED BY DEFAULT AS IDENTITY;
SELECT setval(pg_get_serial_sequence('legacy_order', 'id'),
              (SELECT max(id) FROM legacy_order));   -- 别忘了对齐当前值

字符类型：text、varchar(n)、char(n) 在 PG 里性能相同

这是 PG 与 MySQL 最容易被误搬的一条经验。MySQL 里 char 定长、varchar 变长，行格式和索引前缀都受影响；PG 内部三者都是同一个 varlena 结构，带 1 或 4 字节长度头，存储与比较路径完全一致。varchar(n) 唯一的作用是多一条长度检查，char(n) 则会补空格到定长，既费空间又让比较语义变怪（尾部空格在比较时被忽略）。

类型实际存储性能差异长度约束改长度的代价建议
textvarlena，1 或 4 字节头加内容基准无（上限约 1 GB）不涉及默认选它，需要限长加 CHECK
varchar(n)与 text 完全相同与 text 相同，多一次长度检查字符数上限 n放大上限不重写表；缩小上限重写全表并加 ACCESS EXCLUSIVE 锁对外契约固定长度时可用
varchar（不带 n）与 text 相同相同无不涉及等价于 text，没必要专门用
char(n)补空格到 n 个字符后存储略差，比较要处理补白定长同 varchar只有 ISO 货币码、国别码这类真定长场景才用
✅
用 CHECK 约束代替 varchar(n) 更灵活

把列声明成 text，再写 CHECK (char_length(phone) BETWEEN 5 AND 32)。以后要放宽限制，只需删掉旧约束、加一条新的 NOT VALID 约束再 VALIDATE，全程只取 SHARE UPDATE EXCLUSIVE 锁，不重写表；而缩短 varchar 上限是要重写全表的。另外 char_length 数的是字符数，octet_length 才是字节数，校验中文长度时注意选对。

时间类型：默认就该用 timestamptz

先纠正一个广泛误解：timestamptz 并不存储时区。它存的是一个绝对时刻（UTC 微秒数），写入时把输入按会话 TimeZone 换算成 UTC，读出时再换算回会话时区。timestamp 存的是「字面值」，数据库完全不知道它属于哪个时区，跨时区读写时不做任何换算——这就是跨区数据错乱的来源。

与 now() 比较需要手工保证两边时区一致，容易漏直接比较，语义明确timestamptz 少一整类隐患

按业务所在地分组统计看起来简单，实际上依赖写入方一致用 date_trunc 配 AT TIME ZONE 显式指定显式转换比隐式假设可靠

存生日、纪念日这类纯日期不该用 timestamp也不该用 timestamptz用 date，时区无关的日历日期
存每天固定的营业时间不合适不合适用 time 或 time 加时区字段，或直接存文本规则
-- 复现时区行为：同一份输入，两种类型的差别一眼可见
CREATE TABLE tz_demo (id int, ts timestamp, tstz timestamptz);
SET TimeZone = 'Asia/Shanghai';
INSERT INTO tz_demo VALUES (1, '2026-03-08 10:00:00', '2026-03-08 10:00:00');

SET TimeZone = 'UTC';
SELECT ts, tstz FROM tz_demo;
-- ts   = 2026-03-08 10:00:00     字面值原样，时刻被平移了 8 小时
-- tstz = 2026-03-08 02:00:00+00  同一时刻的另一种表示，语义正确

-- 按「业务所在地的自然日」统计，必须显式转换，不要依赖会话时区
SELECT date_trunc('day', created_at AT TIME ZONE 'Asia/Shanghai') AS biz_day,
       count(*)
FROM orders
WHERE created_at >= now() - interval '7 days'
GROUP BY 1 ORDER BY 1;

-- interval 的坑：月和日不是固定长度，加法结果取决于基准日期
SELECT '2026-01-31'::date + interval '1 month';   -- 2026-02-28，被截断到月末
SELECT '2026-03-08 01:30'::timestamptz + interval '1 day' AS by_day,
       '2026-03-08 01:30'::timestamptz + interval '24 hours' AS by_hours;
-- 在有夏令时的时区里这两个结果不相等：day 是日历运算，hours 是绝对时长

-- 已有 timestamp 列想改成 timestamptz：这是重写全表的操作，且换算依赖会话时区
-- 大表务必先在会话里固定时区，再分批迁移（见文末迁移一节）
ALTER TABLE orders
  ALTER COLUMN created_at TYPE timestamptz
  USING created_at AT TIME ZONE 'Asia/Shanghai';

JSONB 与 JSON：选前者，但别当主数据模型

维度jsonjsonb影响
存储形式原始文本，逐字保留解析后的二进制jsonb 查询不需要重新解析
键顺序保留输入顺序按键长度与字典序重排需要逐字还原原文（如签名校验）时只能用 json
重复键全部保留，取值时取最后一个去重，保留最后一个jsonb 会静默丢掉重复键
写入速度快，几乎是存字符串略慢，要解析与规范化纯归档日志可以考虑 json
查询速度慢，每次访问都要解析快有任何查询需求就用 jsonb
索引只能对表达式结果建索引支持 GIN 整列索引，也支持表达式索引这是最关键的差别
包含运算符不支持支持包含与键存在判断jsonb 才能做集合式过滤

GIN 索引有两种 opclass，选错会让索引白建或者体积翻倍：

opclass索引内容支持的运算符体积适合
jsonb_ops（默认）所有的键和所有的值分别作为独立条目键存在判断、包含、路径存在与路径匹配大，键与值都进索引需要判断「某个键是否存在」的场景
jsonb_path_ops只索引「路径加值」的哈希，不单独存键只支持包含与路径类运算符，不支持单独的键存在判断明显更小，通常是默认的一半以下查询模式固定为按路径取值匹配时，首选
表达式 B-tree 索引只索引某一个提取出来的标量字段等值、范围、排序最小只有少数几个固定键要查，且需要范围与排序时
-- jsonb 的正确定位：核心字段用普通列，schema 不确定的附加属性放 jsonb
CREATE TABLE product (
    id       bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    sku      text        NOT NULL UNIQUE,
    price    numeric(18,2) NOT NULL,           -- 核心字段：要算钱、要建索引、要约束
    attrs    jsonb       NOT NULL DEFAULT '{}'::jsonb,  -- 各品类不同的规格参数
    created_at timestamptz NOT NULL DEFAULT now()
);

-- 三种索引对应三种查询模式，别只会建默认的那种
CREATE INDEX idx_product_attrs_gin  ON product USING gin (attrs);                    -- jsonb_ops
CREATE INDEX idx_product_attrs_path ON product USING gin (attrs jsonb_path_ops);     -- 更小，只做包含查询
CREATE INDEX idx_product_brand      ON product ((attrs ->> 'brand'));                -- 单字段等值与排序

-- 包含查询：走 GIN，注意右侧必须是 jsonb 字面量
SELECT id, sku FROM product WHERE attrs @> '{"brand": "acme", "color": "red"}';

-- 取值：箭头返回 jsonb，双箭头返回 text；比较前要显式转型，否则用不上索引
SELECT id FROM product WHERE (attrs ->> 'weight')::numeric > 10;   -- 需要对应的表达式索引

-- 键是否存在（仅 jsonb_ops 支持）
SELECT count(*) FROM product WHERE attrs ? 'warranty_months';

-- 部分更新：jsonb_set 只是语法上的部分更新，
-- 物理上仍然重写整行并产生一个新版本，高频更新大 jsonb 会显著增加膨胀与 VACUUM 压力
UPDATE product SET attrs = jsonb_set(attrs, '{stock}', '42'::jsonb) WHERE id = 1;

-- 把 jsonb 摊平成关系结果集，用于统计
SELECT key, count(*) FROM product, jsonb_each_text(attrs) GROUP BY key ORDER BY 2 DESC;
⚠️
jsonb 的四条硬边界

一是不能建外键，引用完整性只能靠应用层保证；二是统计信息粒度粗，优化器对 jsonb 条件的选择率估算常常偏差一两个数量级，进而选错连接方式；三是更新任意一个键都重写整行，大字段高频更新会让表快速膨胀；四是约束能力弱，类型与取值范围只能用 CHECK 加表达式勉强补。把它当主数据模型用，等于把关系数据库最值钱的那部分能力关掉。

数组、enum 与那些「看起来很方便」的类型

数组适合标签这类小集合：单行内元素不多、整体一起读写、不需要被外键引用。它的限制很硬——元素不能建外键，追加一个元素要重写整行，而且多对多关系一旦需要反向查询（「哪些文章打了这个标签、按时间排序分页」），数组加 GIN 虽然能过滤但没法高效排序与分页。判断标准很简单：如果这个集合里的元素本身是实体、需要独立属性或被引用，就必须建关联表。

enum 的坑集中在演进上：ALTER TYPE ... ADD VALUE 加值很容易（PG 12 起可以在事务里加，但加完不能在同一事务里使用该值），但删值和改值都不支持，只能新建一个类型再整列迁移；排序由定义顺序决定而不是字面值，插入到中间要用 BEFORE 或 AFTER；跨库迁移和 ORM 映射也普遍别扭。多数情况下 text 加 CHECK（可随时改）或一张小的字典关联表（可带展示名、排序权重、启用开关）更划算。enum 唯一明显的优势是存储紧凑（4 字节）且天然带约束。

-- 数组：标签这类小集合，配 GIN 索引做包含查询
CREATE TABLE article (
    id     bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    title  text NOT NULL,
    tags   text[] NOT NULL DEFAULT '{}',            -- 元素无法建外键，这是硬限制
    ip     inet,                                    -- 16 字节以内，能直接做网段运算
    uid    uuid NOT NULL DEFAULT gen_random_uuid()  -- 16 字节；存成 text 是 36 字节
);
CREATE INDEX idx_article_tags ON article USING gin (tags);
SELECT id FROM article WHERE tags @> ARRAY['postgres'];     -- 走 GIN
SELECT id FROM article WHERE tags && ARRAY['db','sql'];      -- 交集非空

-- inet 的价值：网段包含运算直接在 SQL 里做，存成 text 就只能 LIKE 前缀猜
SELECT count(*) FROM article WHERE ip << '10.1.0.0/16'::cidr;  -- 属于该网段
SELECT masklen('192.168.1.10/24'::inet), host('192.168.1.10/24'::inet);
-- inet 可带主机位，cidr 必须是合法网段（主机位为 0），选错会在写入时报错

-- 范围类型 + 排它约束：数据库层面保证同一资源时间段不重叠
CREATE EXTENSION IF NOT EXISTS btree_gist;   -- 才能在同一约束里混用等号与范围操作符
CREATE TABLE room_booking (
    id      bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    room_id bigint NOT NULL,
    period  tstzrange NOT NULL,
    -- 同一 room_id 内，任意两条记录的 period 不允许重叠
    EXCLUDE USING gist (room_id WITH =, period WITH &&)
);
-- 左闭右开：09:00-10:00 与 10:00-11:00 不算重叠，正好符合排期语义
INSERT INTO room_booking (room_id, period)
VALUES (1, tstzrange('2026-09-23 09:00+08', '2026-09-23 10:00+08', '[)'));
INSERT INTO room_booking (room_id, period)
VALUES (1, tstzrange('2026-09-23 09:30+08', '2026-09-23 10:30+08', '[)'));
-- ERROR: conflicting key value violates exclusion constraint
-- 这比「先 SELECT 查冲突再 INSERT」可靠：后者在并发下有竞态，前者由索引原子保证

-- enum 的演进限制
CREATE TYPE order_state AS ENUM ('created', 'paid', 'shipped');
ALTER TYPE order_state ADD VALUE 'refunded' AFTER 'shipped';   -- 加值可以，位置要显式指定
-- 没有 DROP VALUE，也没有 RENAME 单个值的安全路径；要删只能新建类型再整列迁移

关于 UUID 主键：uuid 类型是 16 字节，存成 text 是 36 字节，而主键会被每一个二级索引引用，膨胀是成倍放大的。更隐蔽的代价是写放大：随机 UUID（v4）每次插入落在 B-tree 的随机页上，页分裂频繁、缓存命中率差，写吞吐明显低于顺序自增的 bigint。要既保留分布式生成和不可枚举，又恢复插入局部性，用时间有序的 UUIDv7（高位是毫秒时间戳）或 ULID；PG 18 内置了 uuidv7()，更早的版本用扩展或在应用侧生成。

改类型要付多少代价：哪些转换会重写全表

判断标准是新旧类型的存储表示是否二进制兼容。兼容则只改系统表里的类型定义，秒级完成；不兼容就要重写整张表的每一行，全程持有 ACCESS EXCLUSIVE 锁，读写全部阻塞，并且所有相关索引都要重建。

flowchart TB S["ALTER TABLE ALTER COLUMN TYPE"] --> Q1{"新旧类型是否二进制兼容"} Q1 -- "是：varchar 放大上限 / varchar 与 text 互转 / numeric 放大精度不改小数位" --> F["只改系统表定义
秒级完成，不重写数据"] Q1 -- 否 --> Q2{"表有多大"} Q2 -- "小表，几十万行以内" --> D["直接 ALTER
务必先设 lock_timeout 避免堵住后续查询"] Q2 -- "大表" --> Q3{"能接受停机窗口吗"} Q3 -- 能 --> D2["维护窗口内直接 ALTER
提前估算重写耗时与 WAL 量"] Q3 -- 不能 --> N["加新列 + 分批回填 + 触发器双写
建好索引约束后短事务内改名切换"] N --> N2["或用逻辑复制迁到新结构后切流量"] F --> DONE["完成"] D --> DONE D2 --> DONE N2 --> DONE
转换是否重写全表锁级别备注
varchar(50) 放大到 varchar(200)不重写ACCESS EXCLUSIVE，但瞬间完成只放宽约束，二进制兼容
varchar(n) 与 text 互转不重写同上，瞬间底层都是 varlena
varchar(200) 缩短到 varchar(50)重写ACCESS EXCLUSIVE 全程要逐行校验长度
numeric(10,2) 到 numeric(18,2)不重写瞬间小数位不变即兼容；改小数位则重写
integer 到 bigint重写ACCESS EXCLUSIVE 全程存储宽度变化；大表要走加列切换方案
timestamp 到 timestamptz重写ACCESS EXCLUSIVE 全程换算依赖会话 TimeZone，务必显式写 AT TIME ZONE
text 到 jsonb重写ACCESS EXCLUSIVE 全程逐行解析，非法 JSON 会让整个语句失败
text 到 enum重写ACCESS EXCLUSIVE 全程存在未定义取值时直接报错
加一个可空列且无默认值不重写ACCESS EXCLUSIVE，瞬间只改系统表
加列带非易变默认值不重写（PG 11 起）瞬间老版本会重写全表，这是 PG 11 最实用的改进之一
💡
大表改类型前先设 lock_timeout

ACCESS EXCLUSIVE 锁需要等现存的所有读写事务结束，而它在等待期间会阻塞后来的所有查询——一个长查询没结束，ALTER 在排队，业务流量全部堵在 ALTER 后面，几秒钟就能把连接池打满。做法是先 SET lock_timeout = '3s'，抢不到锁就失败重试，别让它无限等待。

最容易踩的坑

❌
这些坑多数要重写全表才能修
  • 用 float8 存金额：0.1 加 0.2 不等于 0.3，百万笔累加后差值肉眼可见，而且历史误差不可逆推，是最贵的类型错误。
  • 照搬 MySQL 的 varchar 性能经验：PG 里 text、varchar(n)、char(n) 底层是同一个 varlena 实现，性能完全相同，varchar(n) 只是多一条长度检查。
  • 用 char(n) 存变长内容：会补空格到定长，既浪费空间，尾部空格在比较时被忽略又让相等语义变怪。
  • 用 timestamp 存业务时刻：跨时区读取不做换算、夏令时那一小时无法消歧，改成 timestamptz 要重写全表且换算依赖当初的时区假设。
  • 以为 timestamptz 存了时区：它只存 UTC 时刻，时区信息来自会话参数；真的需要记录「用户当时在哪个时区」要另加一列。
  • interval 的月和日按固定长度算：加 1 month 会被截断到月末，加 1 day 在夏令时地区不等于加 24 hours。
  • 继续用 serial 建自增列：序列是独立对象，容易出现删列后残留、显式插值不推进序列导致后续撞唯一键、以及漏授序列 USAGE 权限；用 IDENTITY。
  • 主键用 integer：21 亿上限总是在业务最好的时候到达，改成 bigint 要重写全表加锁。
  • 把 UUID 存成 text：36 字节对 16 字节，而主键被所有二级索引引用，空间浪费成倍放大。
  • 随机 UUIDv4 做主键还抱怨写入慢：随机插入导致页分裂与缓存命中下降，换 UUIDv7 或 ULID 恢复顺序性。
  • 用 json 而不是 jsonb：json 不能建 GIN 索引、不能等值比较、每次查询都要重新解析；除了要逐字保留原文的场景都该用 jsonb。
  • 建了默认 GIN 索引却做不了想要的查询：jsonb_path_ops 体积小但不支持单独的键存在判断，jsonb_ops 才支持；按查询模式选 opclass。
  • 把 jsonb 当主数据模型：不能建外键、选择率估算不准、更新任一键都重写整行加剧膨胀，核心字段必须拆成普通列。
  • 用数组表达多对多：元素不能建外键，反向查询要排序分页时数组加 GIN 帮不上，该建关联表。
  • 用 enum 表达会变的状态集合：没有 DROP VALUE，删值要新建类型整列迁移；text 加 CHECK 或字典表更好改。
  • IP 存成 varchar：失去网段包含运算能力，所有网段判断散落到应用层。
  • 时间段防重叠靠先查后插：并发下必然漏判，应该用 tstzrange 加 EXCLUDE 约束让索引原子保证。
  • 大表改类型不设 lock_timeout：ALTER 在等 ACCESS EXCLUSIVE 锁时会挡住它后面的所有查询，几秒就能打满连接池。
