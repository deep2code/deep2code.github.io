PostgreSQL 与 MySQL 架构差异与选型

🏷️ PostgreSQL

选 PostgreSQL 还是 MySQL，决定成败的不是「谁的功能列表更长」，而是两条硬差异：进程模型决定了你的连接架构长什么样，类型与索引能力决定了一堆业务逻辑是写在 SQL 里还是堆在应用层。这篇讲清这两条差异、PG 真实的短板，以及场景化的选型判断。涉及 InnoDB 内部细节（B+ 树树高推演、聚簇索引回表、Buffer Pool 分段 LRU、redo 与 binlog 两阶段提交）时只做对比不展开，详见站内 MySQL 深度原理一篇。MVCC 的可见性判定细节留给本组的 MVCC 事务隔离篇，这里只需要记住一句话：PG 把旧版本留在堆表里，MySQL 放进 undo log，所以 PG 需要 VACUUM 回收，MySQL 需要 purge 清理。

进程模型：fork 一个进程，还是起一个线程

PostgreSQL 是多进程架构。监听 5432 的 postmaster 收到连接请求后 fork 出一个独立的 backend 进程，这个连接此后所有的解析、优化、执行都在这个进程里完成。MySQL 是多线程架构，一个 mysqld 进程内为每个连接分配一个线程，还有线程缓存可以复用。

这个选择在 POSTGRES 年代是合理的：进程隔离让一个连接踩坏内存不会直接污染其他连接的数据结构。代价是连接成本高一个数量级。fork 本身是毫秒级的，真正贵的是每个 backend 要建自己的 catalog cache（系统表缓存）、relcache（关系描述缓存）和各类临时缓冲区，稳定跑一阵之后常驻 5 到 10 MB，执行过大查询的 backend 会更高，而且释放的内存不一定还给操作系统。

❌
流传很广的错误说法：把 max_connections 开大就能扛更多并发

连接数从 500 涨到 3000，PG 的吞吐通常是下降的。原因有三：每个进程都要被操作系统调度，上下文切换和 TLB 失效成本随进程数上升；获取事务快照要扫 ProcArray，数组长度正比于连接数；轻量锁（LWLock）和缓冲区映射表的争抢也随之加剧。正确做法是把 max_connections 压在 CPU 核数的 3 到 5 倍，用连接池承接应用侧并发。

连接开销怎么量，连接池怎么补

不要猜，直接量。下面三条命令能给出「一个连接到底吃多少内存」的真实答案。关键是 RSS 会把共享内存（shared_buffers）在每个进程里重复计一遍，所以用 RSS 求和会严重高估，要看 USS 或 PSS。

# 1. 看进程构成：一个 postmaster + N 个 backend + 若干后台进程
ps -o pid,ppid,rss,command -u postgres | head -20

# 2. 所有 postgres 进程 RSS 求和（会重复计算共享内存，只能当上界看）
ps -o rss= -u postgres | awk '{s+=$1} END {print s/1024, "MB (含共享内存重复计数)"}'

# 3. 真实私有内存：USS 才是每个 backend 独占的部分，通常 5 到 10 MB
#    需要先装 smem；PSS 把共享页按进程数均摊，适合做容量规划
smem -P 'postgres:' -k -c 'pid uss pss rss command'

# 4. 建连成本实测：1000 次短连接，看 psql 反复建连的墙钟时间
time bash -c 'for i in $(seq 1 1000); do psql -h 127.0.0.1 -U app -d appdb -c "select 1" >/dev/null; done'

-- 连接构成体检：idle 连接占比过高说明应用侧池配置不当或漏关连接
SELECT state, count(*) AS conns, max(now() - state_change) AS max_idle
FROM pg_stat_activity
WHERE backend_type = 'client backend'
GROUP BY state ORDER BY conns DESC;

-- idle in transaction 是最危险的状态：它按住快照不放，阻塞 VACUUM 回收死元组
SELECT pid, usename, application_name, now() - xact_start AS xact_age, query
FROM pg_stat_activity
WHERE state = 'idle in transaction' AND now() - xact_start > interval '1 minute'
ORDER BY xact_age DESC;

-- 后台进程一览：PG 10 起 pg_stat_activity 会列出 checkpointer、walwriter 等
SELECT pid, backend_type, backend_start FROM pg_stat_activity
WHERE backend_type != 'client backend';

BRIN 索引值得单独记一笔

对按时间近似有序写入的大表（日志、指标、订单流水），BRIN 只为每个块区间记录最小最大值，索引体积常常是 B-tree 的百分之一量级，一张 TB 级表的 BRIN 索引可能只有几十 MB。代价是只对物理有序的列有效，数据顺序被打乱后过滤效果急剧下降。索引类型的选择细节见本组的索引原理篇。

事务 DDL：迁移脚本可回滚这件事被严重低估

做过线上迁移的人都知道：一个改了五张表、加了三个字段、回填了两批数据的脚本，跑到第七步失败是什么感觉。在 MySQL 上你得自己写反向脚本，而且中间态可能已经被业务读到；在 PG 上直接 ROLLBACK 就回到原点。

-- PG：结构变更与数据回填放在同一个事务，任何一步失败都整体回滚
BEGIN;

ALTER TABLE orders ADD COLUMN settle_at timestamptz;
ALTER TABLE orders ADD CONSTRAINT orders_amount_pos CHECK (amount > 0) NOT VALID;
UPDATE orders SET settle_at = created_at WHERE settle_at IS NULL;
ALTER TABLE orders VALIDATE CONSTRAINT orders_amount_pos;   -- 只取 SHARE UPDATE EXCLUSIVE 锁

COMMIT;   -- 到这里才对外可见；中途报错就 ROLLBACK，表结构不留半成品

-- 例外：下列语句不能出现在事务块里，迁移脚本必须单独拆成一步执行
--   CREATE INDEX CONCURRENTLY / DROP INDEX CONCURRENTLY
--   VACUUM / VACUUM FULL
--   CREATE DATABASE / DROP DATABASE / CREATE TABLESPACE
--   ALTER SYSTEM
CREATE INDEX CONCURRENTLY idx_orders_settle_at ON orders (settle_at);

两个细节值得注意。一是 ADD CONSTRAINT ... NOT VALID 加上后续 VALIDATE CONSTRAINT，可以避免在加约束时对全表加 ACCESS EXCLUSIVE 锁；二是 CREATE INDEX CONCURRENTLY 虽然不阻塞写，但它失败后会留下一个 INVALID 索引，必须手动 DROP 再重建，监控里要专门查 pg_index.indisvalid = false。

PG 的劣势必须先认清

只讲优点的选型文章没有价值。下面这些是 PG 上真实会咬人的地方，选它之前要确认团队接得住。

短板具体表现触发条件与量级缓解手段
连接成本高每连接一个进程，常驻 5 到 10 MB，建连毫秒级连接数超过 CPU 核数 5 倍后吞吐开始掉PgBouncer transaction 模式，max_connections 压到 200 到 500
表膨胀与 VACUUM 压力高频 UPDATE 表的死元组堆积，索引同步膨胀，扫描变慢单表几亿行、更新热点集中时 autovacuum 容易追不上调高 autovacuum 并发与成本上限、分区拆表、pg_repack 在线重建
事务 ID 回卷风险长事务或复制槽阻塞冻结，逼近上限时实例进入只读保护age(datfrozenxid) 接近 20 亿监控 age、禁止长事务、清理无用复制槽，绝不关 autovacuum
备库结构不能定制物理流复制要求数据文件逐块一致，备库全局只读，不能加索引想搭「带专用索引的报表库」时改用逻辑复制（发布订阅），但 DDL 不会自动同步
逻辑复制相对年轻不复制 DDL、不复制序列当前值，初始快照期间复制槽堆 WAL大表首次同步、上游频繁 DDLDDL 双边手动执行、监控 pg_replication_slots 的 WAL 滞后量
分库分表生态弱能选的中间件少，运维经验积累不如 MySQL单机写入撑不住、必须水平分片时citus 或应用层分片；提前评估团队能否自维护
默认配置保守shared_buffers 128 MB、random_page_cost 4.0 等默认值不适合现代硬件装完直接上生产按本组安装配置篇的参数矩阵逐项调
⚠️
别拿「PG 写入比 MySQL 慢」当结论

单行主键点查和小事务高并发写，MySQL 通常确实更快，这来自更轻的连接模型和聚簇索引的顺序写入特性。但把 shared_buffers、checkpoint、random_page_cost 调好之后，PG 在多表复杂查询、批量分析、并行聚合上往往反超几倍。跑基准测试时如果一边是调过参的 MySQL、一边是默认配置的 PG，结论没有参考价值。

最容易踩的坑

❌
这些坑都是线上真出过事的
  • 应用直连不上连接池：20 个实例各开 200 连接，等于要 PG 常驻 4000 个进程，内存与调度先崩，表现是延迟整体抬升而 CPU 并不满。
  • max_connections 开到几千当扩容手段：ProcArray 扫描与 LWLock 争抢随连接数上升，吞吐反而下降，真连满时内存瞬间被吃干。
  • 把 work_mem 当每连接配额估内存：它是每个排序或哈希操作的配额，一条复杂查询可能同时开好几个，并行查询还要乘 worker 数，细节见本组安装配置篇。
  • 用默认配置跑基准测试后下结论：shared_buffers 默认 128 MB、random_page_cost 默认 4.0（按机械盘假设），SSD 上会让优化器低估索引扫描价值而误选全表扫。
  • 关掉 autovacuum 图省事：短期看写入变快，代价是表膨胀与事务 ID 回卷，最终实例进入只读保护，抢救要停服做全表 VACUUM FREEZE。
  • 长事务与 idle in transaction 不管：只要有一个老快照在，VACUUM 就无法回收那之后的死元组，整库膨胀速度按分钟计。
  • 指望物理备库加自己的索引：流复制要求数据文件逐块一致，备库全局只读；要定制索引只能走逻辑复制，而逻辑复制不同步 DDL。
  • 忘记清理废弃的复制槽：一个没人消费的槽会让主库无限保留 WAL，直到 pg_wal 撑满磁盘，实例转为只读。
  • CREATE INDEX CONCURRENTLY 失败后不处理：会留下 indisvalid 为 false 的无效索引，既不被查询使用又照常拖慢写入。
  • 把 MySQL 的 SQL 直接搬过来：反引号、双引号语义（PG 里双引号是标识符、单引号才是字符串）、GROUP BY 不允许选未聚合列、隐式类型转换更严格，这些都会在迁移时集中爆发。
  • 用 LIMIT 分页扫大表：这点和 MySQL 一样，OFFSET 大了必须扫完前面的行，应改用键集分页（where id 大于上一页末尾 id）。
  • 混淆 MVCC 的清理模型：PG 的旧版本在堆表里等 VACUUM，MySQL 的在 undo log 里等 purge，监控指标完全不同，照搬 MySQL 的巡检清单会漏掉膨胀监控。
