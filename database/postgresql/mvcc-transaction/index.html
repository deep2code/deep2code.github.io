MVCC 事务隔离

🏷️ PostgreSQL,关系数据库

💡 你需要存一些复杂的数据类型，JSON、数组、地理坐标，MySQL 搞不定。或者你需要写一些复杂的 SQL 查询，不想被数据库方言绑死。

MVCC：读写不打架的秘密

我被 PostgreSQL 的 MVCC 坑过好几次，最典型的就是"删了一半数据文件没变小"和"长事务把表撑爆"。多版本并发控制（MVCC）是它最核心的设计之一，理解了它，才能搞懂 PostgreSQ...

元组版本链：xmin 与 xmax

PostgreSQL 的每一行（元组）头里都藏着两个系统字段：xmin（插入这行的事务 ID）和 xmax（删除/更新这行的事务 ID，未删除为 0）。一个事务的快照记录了它开始时"哪些事务还在跑、哪些已提交"，据此判断某行对它是否可见。UPDATE 并不是原地改，而是插入新行 + 把旧行 xmax 标上当前事务——这就是 MVCC 的"多版本"。

直接看系统字段，你能"看见"MVCC 在干活：

CREATE TABLE mvcc_demo(id int primary key, amt int);
INSERT INTO mvcc_demo VALUES (1, 100);
BEGIN;
UPDATE mvcc_demo SET amt = 200 WHERE id = 1;
-- 在另一个会话：
SELECT xmin, xmax, id, amt FROM mvcc_demo WHERE id = 1;
-- 你会看到两行：
--  xmin=72  xmax=73  id=1  amt=100   <- 旧版本（已被本事务标记删除）
--  xmin=73  xmax=0   id=1  amt=200   <- 新版本
COMMIT;
-- commit 后，旧版本对新快照不可见，但物理上还在，等 Vacuum 回收

四种隔离级别

SQL 标准定义了四种隔离级别，PostgreSQL 全部支持。我把它列成表，一眼看清差别：

隔离级别快照范围能防什么我什么时候用
Read Committed（默认）每条语句防脏读绝大多数业务，默认就好
Repeatable Read整个事务防不可重复读需要事务内多次读一致
Serializable（SSI）整个事务 + 危险结构检测防写偏序 write skew双账户余额校验这类强一致场景

注意 Serializable 用的是 SSI，会让应用收到序列化失败错误，必须自己写重试循环。

-- 会话 A：转账 100 给账户 2
BEGIN ISOLATION LEVEL READ COMMITTED;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;

-- 会话 B：Repeatable Read 下的现象演示
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT sum(balance) FROM accounts;   -- 看到 A 转账前的总和
-- 此时 A 提交转账
SELECT sum(balance) FROM accounts;   -- 仍然看到旧总和（快照不变）
COMMIT;

-- 死锁检测示例：两个会话以相反顺序锁两行
-- 会话1: BEGIN; UPDATE acc1 SET ...; UPDATE acc2 SET ...;  -- 卡在等 acc2
-- 会话2: BEGIN; UPDATE acc2 SET ...; UPDATE acc1 SET ...;  -- 卡在等 acc1
-- PostgreSQL 会在 deadlock_timeout（默认 1s）后报错：
-- ERROR:  deadlock detected

Vacuum：MVCC 的清洁工

因为 UPDATE 会留旧版本，如果不清理，表会越涨越大（称为表膨胀），且事务 ID 会回卷（transaction ID wraparound）——这是 PostgreSQL 最可怕的运维事故之一。Autovacuum 自动做这件事，但对大表经常不够及时：

我踩过的坑：长事务把表撑爆

有次一个报表任务开了事务忘了 commit，挂在那跑了 3 小时。这期间它占着的快照让 Vacuum 没法清理任何比它老的死元组，一张 200GB 的表直接膨胀到 500GB，磁盘告急。后来杀掉那个 idle in transaction 连接，Vacuum 一跑空间就回来了。从那以后我专门告警 state='idle in transaction' 超过 5 分钟的连接。

# 查看死元组与 vacuum 状态
psql -c "SELECT relname, n_live_tup, n_dead_tup,
         round(n_dead_tup::numeric/nullif(n_live_tup,0)*100,1) AS dead_pct,
         last_autovacuum, last_vacuum
         FROM pg_stat_user_tables
         ORDER BY n_dead_tup DESC LIMIT 10;"

# 紧急手工 vacuum（不锁表）
psql -c "VACUUM (VERBOSE, ANALYZE) big_table;"
# 更激进：整表重写回收空间（锁写，用 pg_repack 在线替代）
psql -c "VACUUM FULL big_table;"

关键参数调整（postgresql.conf）：

# 让 autovacuum 更勤快、能并行
autovacuum = on
autovacuum_max_workers = 6
autovacuum_naptime = 15s
# 对超大表降低触发阈值（默认 scale_factor=0.2 对亿级表太迟钝）
# ALTER TABLE big_table SET (autovacuum_vacuum_scale_factor = 0.02);

性能优化与最佳实践

  • 长事务是万恶之源：一个跑了 1 小时的只读事务会阻止 Vacuum 清理它"能看到"之前的所有死元组，导致表膨胀。query_type='idle in transaction' 的连接务必清理。
  • 热点更新用 HOT（Heap-Only Tuple）更新：如果 UPDATE 不修改索引列，且新版本能和旧版本放在同一个物理页，PostgreSQL 做 HOT 链，不更新索引，开销小很多。避免频繁更新索引列。
  • 默认 Read Committed 够用就别上 Serializable：SSI 会让应用收到序列化失败错误，必须实现重试循环。只有当业务确实需要防止 write skew（如双账户余额校验）时才用。
  • 监控 xid 回卷：Wraparound 紧急时数据库会拒绝写入。把 age(datfrozenxid) 纳入告警，距离 autovacuum_freeze_max_age 还有 10 亿就该介入。

常见问题 FAQ

Q1：为什么一张表明明删了一半数据，文件大小没变？

MVCC 的 DELETE 只是把行标记为死元组，空间要等 Vacuum 才能标记为可重用，但不会还给操作系统。要物理收缩文件用 VACUUM FULL 或 pg_repack，但前者锁表。日常只需要让 Vacuum 正常运行，空间会被新数据重用，不会无限增长。

Q2：什么是 "idle in transaction"，为什么危险？

连接进入了事务但没执行任何语句。它占着一个快照不放手，导致 Vacuum 无法回收它之前产生的死元组，时间一长整张表膨胀。常见原因是连接池把用完但未 commit 的事务连接还回去。应用层务必 commit/rollback 后再归还连接。

Q3：Repeatable Read 下为什么我的 UPDATE 卡住或报错 "could not serialize"？

Repeatable Read（实际 PostgreSQL 是 Snapshot Isolation）下，如果其他事务已经更新了你正读的行，你的 UPDATE 会等待对方提交；若对方提交了，你会拿到最新行而不是你快照里的行。Serializable 下则可能直接报 40001 错误，应用必须实现重试。

总结

MVCC 是 PostgreSQL 高并发与数据一致性的基石。记住三点：UPDATE 产生旧版本、快照决定可见性、Vacuum 负责回收。生产中 80% 的"数据库变慢"都和长事务 + Vacuum 跟不上有关。下一篇，我们看如何把这套单机能力复制出去，变成高可用集群。
