PostgreSQL 隔离级别与并发控制：SSI、行锁四档与 DDL 锁队列

🏷️ MVCC

PG 的元组结构、xmin/xmax 与 VACUUM 在主干篇已经讲过，这一篇只谈并发控制的实际行为：四个隔离级别真正的语义差异、PG 的可重复读为什么会让从 MySQL 迁来的应用大面积报错、SERIALIZABLE 的代价为什么是回滚率而不是锁等待、八种表锁的兼容关系，以及 PG 运维最大的坑——一个等锁的 DDL 会把它后面所有毫不相干的查询一起堵死。

四个隔离级别，实际只有三种行为

PG 声明支持 SQL 标准的四个隔离级别，但READ UNCOMMITTED 的行为和 READ COMMITTED 完全一样：PG 的 MVCC 里根本没有「未提交版本」这种可读状态，它不实现脏读。写 SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED 不报错，但也什么都不会变。真正有区别的只有三档。

级别快照粒度不可重复读幻读PG 的实际行为与失败模式
READ UNCOMMITTED等同 RC可能可能语法合法但语义上就是 READ COMMITTED，PG 不实现脏读
READ COMMITTED（默认）每条语句取一次新快照可能可能并发更新同一行时后来者等锁，然后在新版本上重新求值 WHERE 条件，可能出现「扫到了这一行却没改」的结果
REPEATABLE READ事务第一条语句取一次快照，全程复用否否，快照隔离天然没有幻读并发更新同一行时直接报 40001 让事务失败，不等锁、不重试
SERIALIZABLE同 RR，外加读写依赖追踪否否SSI 检测到危险结构就中止其中一个事务，同样报 40001，代价是回滚率
💡
READ COMMITTED 下最容易被忽略的语义

RC 是语句级快照，所以 UPDATE t SET n = n - 1 WHERE n > 0 在等到前一个事务释放锁之后，会拿最新版本重新检查 n > 0，条件不成立就跳过这一行。这个行为是对的，但它意味着 UPDATE ... WHERE status = 'pending' 在并发下会出现「扫描时命中、最终没改」的情况，用返回的影响行数做业务判断时必须考虑到。想要「读到什么就基于什么写」，必须显式 SELECT ... FOR UPDATE，或者升到 RR 并接受失败重试。

PG 的 REPEATABLE READ 和 MySQL 的同名级别不是一回事

这是从 MySQL 迁到 PG 时最容易造成线上大面积报错的差异。两边都叫 REPEATABLE READ，行为却相反：MySQL 在 RR 下遇到并发更新同一行会阻塞等锁，等到了就在最新版本上继续；PG 用的是快照隔离加 first-updater-wins，第二个事务一旦发现这一行在自己快照之后被别人改过，立刻抛出 could not serialize access due to concurrent update，SQLSTATE 40001。没有等待，没有自动重试，事务直接死掉。原来在 MySQL 上「慢一点但会成功」的并发扣库存，迁到 PG 的 RR 下就变成大量 40001。

# 在 PG 上用 RR 或 SERIALIZABLE，重试不是可选项而是必须项
# 只重试 40001 序列化失败 与 40P01 死锁，其他错误一律上抛
import random, time
import psycopg
from psycopg import errors

RETRYABLE = (errors.SerializationFailure, errors.DeadlockDetected)

def run_serializable(conn_str, fn, max_retry=5):
    for attempt in range(max_retry):
        try:
            with psycopg.connect(conn_str) as conn:
                # 隔离级别必须在第一条语句之前设定，事务中途改会报错
                conn.isolation_level = psycopg.IsolationLevel.SERIALIZABLE
                with conn.cursor() as cur:
                    result = fn(cur)
                conn.commit()
                return result
        except RETRYABLE:
            if attempt == max_retry - 1:
                raise
            # 指数退避加抖动，避免多个事务重试时又撞在同一时刻
            time.sleep((2 ** attempt) * 0.05 * (0.5 + random.random()))

def deduct(cur):
    cur.execute("UPDATE stock SET qty = qty - 1 WHERE id = %s AND qty > 0", (1,))
    if cur.rowcount == 0:
        raise ValueError("库存不足")   # 业务异常，不能被重试逻辑吞掉
    cur.execute("INSERT INTO stock_log(item_id, delta) VALUES (%s, -1)", (1,))

SERIALIZABLE 用的是 SSI：代价是回滚率，不是锁等待

很多人以为 SERIALIZABLE 就是「读也加锁」，在 PG 上这是错的。PG 9.1 起用的是 SSI（Serializable Snapshot Isolation）：事务照样跑在快照隔离上，读操作不阻塞任何人，但内核会用谓词锁（SIReadLock，只记录不阻塞）跟踪「谁读了什么、谁写了什么」，一旦发现读写依赖形成了危险结构（一个事务既有进来的 rw 依赖又有出去的 rw 依赖，即所谓 pivot），就中止其中一个事务。

所以 SERIALIZABLE 的开销表现在三处：跟踪读集合的内存（max_pred_locks_per_transaction 默认 64，超了会把行级谓词锁升级成页级甚至表级，误杀率随之上升）、CPU 上的依赖图维护、以及最关键的事务回滚率。它的适用前提只有一条：应用必须能安全重试整个事务。如果事务里夹了发短信、调外部支付这类不可重放的副作用，就不要用 SERIALIZABLE。

维度READ COMMITTEDREPEATABLE READSERIALIZABLE（SSI）

额外内存无无谓词锁结构，受 max_pred_locks_per_transaction 限制
吞吐随并发上升的表现平稳平稳，冲突集中在热点行回滚率随冲突密度非线性上升，热点表上可能重试到崩

⚠️
只读事务也会被 SSI 中止

SSI 可能中止一个纯只读的事务（报「could not serialize access due to read/write dependencies among transactions」），这不是 bug，是 SSI 打破危险结构时挑中了它。可以用 BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE READ ONLY DEFERRABLE：这样事务会先等到一个不可能产生冲突的安全快照再开始，永远不会被中止也永远不会中止别人，代价是开头可能要等一会儿。长时间的一致性报表就该用这个写法。

快照、xmin 水位与长事务的四重危害

快照的核心是三个东西：xmin（此刻最老的活跃事务 ID，比它小且已提交的都可见）、xmax（此刻的 XID 上界）、以及中间那批正在跑的事务列表。PG 13 起用 pg_current_snapshot() 查看，老版本是 txid_current_snapshot()。

关键点在于：全局最老的那个 xmin 就是 VACUUM 的天花板。任何一个事务只要还持着快照，比它更新的所有死元组都不能被回收——哪怕这个事务在干的事情和那张表毫无关系。所以长事务在 PG 上的危害是四重的，而且每一重都能独立造成故障。

危害机制表现排查入口
阻塞死元组回收它的快照压住全局 xmin，VACUUM 不敢清比它新的死元组表和索引持续膨胀，last_autovacuum 一直在跑但 n_dead_tup 不降pg_stat_activity.backend_xmin
阻塞 XID 冻结冻结水位同样不能超过最老快照age(datfrozenxid) 持续上涨，最终触发 anti-wraparoundpg_database 的 datfrozenxid
占住复制槽推进备库上的长查询配合 hot_standby_feedback 会把主库 xmin 拉住主库膨胀，但元凶在备库上pg_replication_slots.xmin
持有锁不放事务里任何一条 DDL 或 SELECT FOR UPDATE 拿到的锁，要到事务结束才释放后续 DDL 排队，连带堵死整张表的查询pg_locks 与 pg_blocking_pids()

四类元凶里最常见的不是慢查询，而是 idle in transaction：连接池里的连接开了事务、执行完一条语句、然后应用去干别的事（发消息、调 HTTP）忘了提交。这种连接 CPU 占用为零，任何慢查询监控都发现不了它，但它照样把 VACUUM 钉在原地。

-- 长事务与空闲事务排查：按事务持续时间倒序，state 是判断元凶类型的关键
SELECT pid,
       state,                                     -- idle in transaction 是最常见元凶
       now() - xact_start  AS 事务已持续,
       now() - query_start AS 当前语句已持续,
       backend_xmin,                              -- 这个值就是它压住的快照水位
       wait_event_type || ':' || coalesce(wait_event, '-') AS 等待事件,
       left(query, 80)     AS 语句片段
FROM   pg_stat_activity
WHERE  xact_start IS NOT NULL
  AND  now() - xact_start > interval '1 min'
ORDER  BY xact_start;

-- 全局兜底：这三个超时在生产库上必须设，否则长事务迟早出现
ALTER SYSTEM SET idle_in_transaction_session_timeout = '60s';  -- 专治忘了提交
ALTER SYSTEM SET statement_timeout = '30s';                    -- 按库设，报表账号单独放宽
ALTER SYSTEM SET lock_timeout = '3s';                          -- 等锁超过就放弃，见下文 DDL 一节
SELECT pg_reload_conf();

-- 确认谁在压着 VACUUM：取全局最老 xmin 的持有者
SELECT pid, backend_type, backend_xmin, now() - xact_start AS 持续
FROM   pg_stat_activity
WHERE  backend_xmin IS NOT NULL
ORDER  BY age(backend_xmin) DESC
LIMIT  5;

表级锁：八种模式与谁跟谁冲突

PG 的表锁有八种模式，从 ACCESS SHARE 到 ACCESS EXCLUSIVE 强度递增。绝大多数事故只需要记住两条：ACCESS EXCLUSIVE 和一切冲突，包括 SELECT；SHARE UPDATE EXCLUSIVE 不阻塞读写，所以 VACUUM、ANALYZE、CREATE INDEX CONCURRENTLY 才敢在线跑。

行级锁四档与 SKIP LOCKED

行级锁不记在内存的锁表里，而是写在元组头的 xmax 上（多个持有者时才落到 multixact），所以 PG 不存在 InnoDB 那种「行锁太多升级成表锁」的问题，锁多少行都行，代价只是 WAL 与元组头的改动。四档强度从弱到强，选对了能显著降低冲突面。

子句阻止别人做什么谁在用选它的理由
FOR KEY SHARE只阻止删除该行和修改键列外键检查自动使用子表插入时只需要保证父行的键不变，不必阻塞父行其他列的更新，冲突面最小
FOR SHARE阻止任何修改，允许别人同样 FOR SHARE读后校验且不打算改的场景比 FOR UPDATE 并发度高，但两个 FOR SHARE 之后都想改会死锁
FOR NO KEY UPDATE阻止删除与更新，但允许 FOR KEY SHARE普通 UPDATE 内部就取这一档这就是为什么「更新父表非键列」不会被子表的外键检查堵住
FOR UPDATE阻止一切，包括 FOR KEY SHARE需要独占该行的业务逻辑语义最清楚，但会和外键检查互相阻塞，父表上慎用

外键为什么在 PG 8.1 之后不那么容易死锁，答案就在上表：早期版本外键检查用的是排他行锁，现在用 FOR KEY SHARE，只要父行的键没被改，子表的并发插入互不干扰。这也解释了一个常见误解——「PG 的外键会拖慢父表更新」在现代版本里只对修改键列成立。

再加两个修饰词就凑出了 PG 最好用的并发原语：NOWAIT 拿不到锁立即报错（55P03），SKIP LOCKED 跳过被别人锁住的行。后者是 PG 里实现任务队列的正确姿势，不需要额外的状态列轮询，也不会多个 worker 抢同一条。

-- 任务队列的标准写法：多个 worker 并发跑这段，彼此不会拿到同一行
-- 关键点 1：子查询里先用 SKIP LOCKED 挑出可用行，再用 ctid 精准更新
-- 关键点 2：FOR UPDATE 必须落在子查询上，外层 UPDATE 才不会再次扫描
WITH picked AS (
    SELECT id
    FROM   job_queue
    WHERE  status = 'pending'
      AND  run_after <= now()
    ORDER  BY priority DESC, id            -- 有序出队，避免饥饿
    LIMIT  20
    FOR UPDATE SKIP LOCKED                 -- 被别的 worker 锁住的行直接跳过
)
UPDATE job_queue q
SET    status = 'running', picked_at = now(), worker = pg_backend_pid()
FROM   picked p
WHERE  q.id = p.id
RETURNING q.id, q.payload;                 -- 一次往返就拿到任务内容

-- 配套索引：部分索引只覆盖待处理的行，队列表再大索引也很小
CREATE INDEX CONCURRENTLY idx_job_pending
    ON job_queue (priority DESC, id)
    WHERE status = 'pending';

-- 不想让任务被锁住时排队等待，就用 NOWAIT，拿不到立刻报 55P03 由调用方决定退避
SELECT * FROM job_queue WHERE id = 42 FOR UPDATE NOWAIT;

-- 咨询锁：把互斥语义放到「没有对应行」的场景上，比如定时任务防重入
-- pg_try_advisory_lock 立即返回布尔值，锁的生命周期是会话级，别忘了显式释放
SELECT pg_try_advisory_lock(hashtext('nightly_settlement'));
-- ... 干活 ...
SELECT pg_advisory_unlock(hashtext('nightly_settlement'));
-- 想让锁随事务自动释放就用事务级版本，更安全，不会因为连接复用而泄漏
SELECT pg_try_advisory_xact_lock(hashtext('nightly_settlement'));

DDL 的阻塞风险：一个等锁的 DDL 会堵死整张表

这是 PG 运维最大的坑，而且和 DDL 本身快不快无关。PG 的锁请求是排队的，并且队列是 FIFO 的：当一个 ALTER TABLE 在等 ACCESS EXCLUSIVE 锁时，它后面到达的所有请求——包括本来和它毫无冲突的 SELECT——都必须排在它后面等。于是一个「只改元数据、毫秒级完成」的 DDL，只要前面有一个跑了 10 分钟的报表查询挡着，就能让整张表在这 10 分钟里对所有人不可用，连接池瞬间打满，故障面扩散到整个应用。

故障从一张表扩散成整个服务不可用 R->>Q: 报表终于提交 释放 ACCESS SHARE Q-->>D: DDL 拿到锁 毫秒级完成后释放 Q-->>S1: 排队的查询才依次恢复

正确做法只有一条：所有 DDL 会话都必须先设 lock_timeout。拿不到锁就快速失败、退避重试，把「无限期堵住队列」变成「几秒内放弃」。另外 ALTER TABLE 的多个子操作会取其中最高的锁级别，所以拆成多条独立语句执行，而不是攒在一个事务里。

DDL 操作锁级别是否重写全表版本差异与规避手段
ADD COLUMN 无默认值ACCESS EXCLUSIVE否，只改目录历来都是瞬时的，唯一风险是等锁
ADD COLUMN ... DEFAULT 常量ACCESS EXCLUSIVEPG 11 起不再重写，PG 10 及以前重写全表这是重要版本分界：PG 11 之后给大表加带默认值的列是毫秒级操作
ADD COLUMN ... DEFAULT now() 等易变函数ACCESS EXCLUSIVE是，仍然重写易变默认值享受不到优化。先加空列，再分批回填，最后设默认值
ALTER COLUMN TYPEACCESS EXCLUSIVE是，且重建所有相关索引例外：varchar(n) 加长、去掉长度限制不重写。int 改 bigint 必须走新列加回填加改名
SET NOT NULLACCESS EXCLUSIVE否，但要全表扫描校验PG 12 起可先加一个等价的 CHECK (col IS NOT NULL) 约束并 NOT VALID，校验通过后再 SET NOT NULL 即可跳过扫描
ADD FOREIGN KEY父子表都取 SHARE ROW EXCLUSIVE否，但要扫全表校验分两步：先 ADD CONSTRAINT ... NOT VALID（瞬时），再 VALIDATE CONSTRAINT（只取 SHARE UPDATE EXCLUSIVE，不阻塞写）
CREATE INDEXSHARE否允许读但阻塞全部写，大表上等于停写。生产一律用 CONCURRENTLY
CREATE INDEX CONCURRENTLYSHARE UPDATE EXCLUSIVE否不阻塞读写，代价是两遍扫表、耗时约两倍，不能在事务块里执行，且会被长事务拖住
DROP COLUMNACCESS EXCLUSIVE否，只标记删除瞬时完成但不释放空间，旧数据仍在元组里，要靠重写表才回收
TRUNCATEACCESS EXCLUSIVE换新文件可在事务里回滚，这点和 MySQL 不同
⚠️
CREATE INDEX CONCURRENTLY 的三种失效模式

第一，失败会留下一个 indisvalid = false 的无效索引，它不会被查询使用，却会照常参与写入维护，必须手工 DROP INDEX CONCURRENTLY 后重建——很多库里躺着的「莫名占空间的索引」就是这么来的。第二，不能在事务块里执行，也就不能放在需要原子性的迁移脚本事务里，很多迁移框架默认包事务，要单独关掉。第三，它需要等待所有早于它的事务结束才能完成两遍扫描，一个长事务就能让它挂住几小时，而它自己又持着 SHARE UPDATE EXCLUSIVE 锁把 VACUUM 挡在外面。

-- DDL 安全模板：先卡住等锁时间，绝不允许无限期堵塞锁队列
-- 在 psql 里 \set ON_ERROR_STOP on，配合外层脚本做退避重试
BEGIN;
SET LOCAL lock_timeout = '3s';          -- 拿不到锁就报 55P03 退出，不拖累后续查询
SET LOCAL statement_timeout = '30s';    -- DDL 本身也要有上限
ALTER TABLE orders ADD COLUMN channel text;   -- PG 11+ 带常量默认值也是瞬时的
COMMIT;

-- 加非空约束而不扫全表阻塞（PG 12+）
ALTER TABLE orders ADD CONSTRAINT orders_channel_nn
      CHECK (channel IS NOT NULL) NOT VALID;      -- 瞬时，只影响新写入
ALTER TABLE orders VALIDATE CONSTRAINT orders_channel_nn;  -- 只取 SHARE UPDATE EXCLUSIVE
ALTER TABLE orders ALTER COLUMN channel SET NOT NULL;      -- 有等价 CHECK 时跳过扫描
ALTER TABLE orders DROP CONSTRAINT orders_channel_nn;      -- 清理临时约束

-- 加外键的两步法，避免长时间校验期阻塞写入
ALTER TABLE order_items
      ADD CONSTRAINT fk_items_order FOREIGN KEY (order_id)
      REFERENCES orders(id) NOT VALID;
ALTER TABLE order_items VALIDATE CONSTRAINT fk_items_order;

-- 并发建索引的正确姿势：不能在事务里，建完必须检查有效性
CREATE INDEX CONCURRENTLY idx_orders_channel ON orders (channel);
SELECT indexrelid::regclass AS 无效索引
FROM   pg_index WHERE NOT indisvalid;   -- 有输出就 DROP INDEX CONCURRENTLY 后重建

死锁检测与阻塞链定位

PG 不做预防，只做检测：每个等锁的进程在等待 deadlock_timeout（默认 1s）之后才去检查锁依赖图，发现环就中止代价最小的那个事务，报 40P01。把 deadlock_timeout 调小会让所有正常的锁等待都多付一次检测开销，调大则死锁要更久才被发现，默认值在绝大多数场景都是对的。真正该做的是打开 log_lock_waits，这样超过 deadlock_timeout 的等待会写进日志，附带阻塞者的语句。

-- 一条 SQL 定位阻塞链：谁被谁挡住，挡了多久，各自在跑什么
SELECT w.pid                            AS 被阻塞pid,
       w.wait_event_type || ':' || w.wait_event AS 等待类型,
       now() - w.query_start             AS 已等待,
       left(w.query, 60)                 AS 被阻塞语句,
       b.pid                             AS 阻塞者pid,
       b.state                           AS 阻塞者状态,
       now() - b.xact_start              AS 阻塞者事务时长,
       left(b.query, 60)                 AS 阻塞者语句
FROM   pg_stat_activity w
JOIN   LATERAL unnest(pg_blocking_pids(w.pid)) AS bp(pid) ON true
JOIN   pg_stat_activity b ON b.pid = bp.pid
WHERE  w.wait_event_type = 'Lock'
ORDER  BY 已等待 DESC;

-- 看某张表上到底压着哪些锁，granted = false 的就是在排队的
SELECT l.pid, l.mode, l.granted, a.state, left(a.query, 60) AS 语句
FROM   pg_locks l
JOIN   pg_stat_activity a USING (pid)
WHERE  l.relation = 'orders'::regclass
ORDER  BY l.granted, l.pid;

-- 先取消语句，保留连接；确实取消不掉再杀连接（会丢掉整个事务）
SELECT pg_cancel_backend(12345);
SELECT pg_terminate_backend(12345);

-- 开启锁等待日志，事后复盘的唯一可靠依据
ALTER SYSTEM SET log_lock_waits = on;              -- 等待超过 deadlock_timeout 就记一条
ALTER SYSTEM SET log_min_duration_statement = '1s';
SELECT pg_reload_conf();

最容易踩的坑

❌
这些坑每条都有真实事故对应
  • 从 MySQL 迁来直接把隔离级别设成 REPEATABLE READ：PG 在并发更新同一行时报 40001 而不是等锁，没有重试逻辑就是线上大面积失败。
  • 用 SERIALIZABLE 却不写重试：SSI 的代价就是回滚率，不重试等于把冲突直接抛给用户。而且纯只读事务也可能被中止，一致性报表应该用 SERIALIZABLE READ ONLY DEFERRABLE。
  • DDL 会话不设 lock_timeout：一个等锁的 ALTER TABLE 会把它后面所有本来不冲突的 SELECT 一起堵死，这是 PG 特有的、放大倍数最高的坑。
  • 在事务里执行 CREATE INDEX CONCURRENTLY：直接报错。而它失败后留下的 indisvalid = false 索引不被查询使用却照样吃写入开销，必须手工清理。
  • 大表上直接 CREATE INDEX：SHARE 锁允许读但阻塞全部写，等于停写，而且时间与表大小成正比。
  • 把多个子操作攒在一条 ALTER TABLE 里：锁级别取其中最高的那个，而且全程持有，拆成多条更安全。
  • 用 SET NOT NULL 给大表加约束：PG 12 之前必然全表扫描并持 ACCESS EXCLUSIVE 锁，要走 CHECK ... NOT VALID 加 VALIDATE 的两步法。
  • 加外键不用 NOT VALID：一次性加外键会在父子表上取 SHARE ROW EXCLUSIVE 并扫全表，大表上是几分钟级别的写阻塞。
  • 用「查出来再更新状态」实现任务队列：多个 worker 会抢到同一行。正确做法是 FOR UPDATE SKIP LOCKED 加一个 WHERE status = 'pending' 的部分索引。
  • 只监控慢查询，不监控 idle in transaction：这种连接 CPU 为零，却同时压住 VACUUM 回收、XID 冻结和锁释放。idle_in_transaction_session_timeout 是生产必设项。
  • 在父表上随手用 FOR UPDATE：它和外键检查的 FOR KEY SHARE 冲突，会把子表的并发插入全堵住。只需要防删除时用 FOR NO KEY UPDATE 就够。
  • 用 pg_terminate_backend 当常规手段：先用 pg_cancel_backend 取消语句，terminate 会丢掉整个事务连接，配合重试不当会引发二次故障。
  • 调小 deadlock_timeout 来「减少死锁」：它只影响检测的开始时间，不减少死锁，反而让每次正常锁等待都多付检测开销。该做的是统一业务里的加锁顺序。
