数据库设计深度原理：范式与反范式

🏷️ 数据库设计

为什么要分表？为什么三范式有时候要打破？什么时候加冗余？这篇讲透数据库设计底层原理。

核心原理1：第一第二第三范式

范式是为了减少数据冗余，避免更新异常。1NF 原子性，2NF 消除部分依赖，3NF 消除传递依赖。

flowchart TD A[数据库设计范式] --> B[1NF 字段原子性] A --> C[2NF 消除部分依赖] A --> D[3NF 消除传递依赖] B --> B1[一个字段不可分] C --> C1[非主键完全依赖主键] D --> D1[非主键不依赖其他非主键]
范式 要求 解决的问题
1NF 字段原子，不可再分 字段存多个值
2NF 非主键完全依赖主键，不部分依赖 部分依赖导致冗余
3NF 非主键不传递依赖其他非主键 传递依赖导致冗余
BCNF 每个决定因素都是候选键 主属性对候选键依赖

核心原理2：为什么要反范式？

范式越高，表越多，查询要 join，性能差。生产环境经常加冗余字段，用空间换时间，减少 join。

flowchart LR A[范式 多表] --> B[查询要 JOIN] B --> C[性能差] D[反范式 加冗余] --> E[一张表存] E --> F[不用 JOIN 查询快]
对比 范式设计 反范式设计
冗余 少 多
查询性能 慢，要 join 快，单表查
更新性能 快，改一处 慢，要改多处
一致性 强一致 最终一致
适用场景 写多读少 读多写少

核心原理3：分库分表原理

单表数据量到千万级，索引大查询慢，就要分库分表。垂直拆按业务拆，水平拆按数据拆。

flowchart TD A[分库分表] --> B[垂直拆分] A --> C[水平拆分] B --> B1[按业务拆库] B --> B2[用户库 订单库] C --> C1[按数据拆表] C --> C2[按 user_id 哈希分16张表]
拆分方式 原理 适用场景
垂直分库 按业务拆成多个库 业务边界清晰
垂直分表 把宽表字段拆成多表 冷热字段分离
水平分库 同一个表数据分到多个库 单库数据量太大
水平分表 同一个库拆成多个表 单表数据量太大

新手最容易踩的坑

❌
避坑指南
  • 范式不是越高越好，生产环境读多写少要适当反范式加冗余
  • 分库分表前先确认是不是真的需要，千万级单表 MySQL 还能扛，别上来就分
  • 水平分表选分片键很重要，选不好会有数据倾斜
  • 分库分表后分布式 ID 一定要用，不能用自增 ID
