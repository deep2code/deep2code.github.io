范式与反范式：数据库设计的取舍

🏷️ 数据库设计

数据库设计里的绝大多数争论，最后都能归到同一个问题：同一份事实，在库里存几遍。存一遍，修改时只改一处，数据永远不会自相矛盾，代价是查询要把散落在多张表里的行拼回来；存多遍，一次查询就能拿全，代价是你从此背上「让这几份副本保持同步」的债务。范式与反范式不是两种审美风格，而是这条取舍线的两端。这篇讲清楚这条线该画在哪里，以及画错之后会以什么形式还债。

① 用法 · 这张表该规范化到什么程度：四步判断

范式级别不是凭审美定的，它由两件事推出来：这张表的高频查询长什么样，以及哪些字段读到旧值会出事。下面四步按顺序问，第二步的答案经常直接否掉后面两步。每一步为什么这样问，原因见原理层。

步骤 怎么确认 结论
1 列全这张表的高频查询 把列表页、详情页、导出任务、对账任务要跑的 SQL 都写出来，标明每条取哪些列、按什么排序、翻到第几页 如果高频查询都能在单表内或一次小维度表关联内完成，直接做到 3NF，不要预先冗余；只有「排序字段跨表」「深分页加多表关联」「分库后关联做不了」这三种才需要往下走
2 标出读到旧值就会出事的字段 逐列问一个具体问题：这一列显示成 5 秒前的值，业务上会发生什么 余额、库存、可用额度、券剩余量这类既不冗余也不缓存，只保留唯一存放点，扣减用带条件的原子更新；剩下的列才进第三步
3 判断候选列是快照还是引用 问：这个值是不是交易凭证的一部分，一旦生成就不该被源表的后续变更影响 是快照 → 写入时赋值、注释里标「禁止回填」，它根本不需要同步；是引用（要跟随源表当前值）→ 进第四步
4 看源列变更频率与两表是否同库 查源列最近三个月实际变更过几次，再确认两张表能不能进同一个事务 几乎不变（单位、类目名、枚举名）→ 一次性回填脚本加低频对账；常变且同库 → 同事务双写并把写入口收成一个；常变且跨库 → 异步回填加定时对账，窗口谈不下来就放弃冗余改走聚合查询
场景 该范式化还是冗余 冗余后怎么保证不脏
订单明细列表要展示商品名与下单单价 冗余，而且是快照语义 不需要同步。写入时赋值，注释标「禁止回填」，并在代码评审里拦住任何按当前商品价回刷的脚本
员工列表要展示部门名 范式化，关联取 不涉及。部门只有几十上百行，常驻内存或被缓冲池完全装下，关联代价远低于同步代价
评论列表要展示作者当前昵称 能关联就关联；列表要按昵称排序或分库导致关联不了才冗余 昵称变更投消息，消费方按主键回填并带 updated_at 条件防乱序；再配一个每小时的增量对账
商品详情页显示类目名、计量单位 冗余 源列几乎不变，一次性回填脚本加每日对账即可，不值得为它搭消息通道
帖子列表要显示回复数 冗余成计数列（派生数据物化） 同事务自增或异步累加，另配一个可重跑的幂等重算任务按明细校准，差异行数打成监控指标
商家后台要看今日成交额 汇总表，不在订单表上冗余 随时可从明细重算，这是它最大的优点；口径变更时整体回刷，产品上标明分钟级延迟
风控规则要读用户实名手机号 不冗余 敏感且高频变更，冗余副本既是泄露面也是脏数据源，实时查权威表并做权限隔离
订单表要显示收货人与地址 冗余成快照，绝不外键指向地址表 不需要同步。用户改默认地址后历史订单必须保持原样，外键只留作溯源

① 用法 · 冗余登记四要素与最小可用建表片段

冗余本身不是错，没有登记的冗余才是错。登记的成本只是一句列注释，收益是出问题时三十秒内能判断哪个值是权威的、该找谁。这四项缺一项，半年后就没人敢动这列。

登记项 写在哪 写成什么样 缺了会怎样
权威来源 列注释第一句，同时进设计文档 冗余自 user.nickname 或 快照 取自 product.name 两个值不一致时无法判断该改哪一边，修复脚本方向可能写反
同步通道 列注释第二句 由 user 变更消息回填 / 同事务双写 / 写入时赋值 禁止回填 新增写入口的人不知道要挂同步，不一致只在特定入口产生，排查周期以周计
容忍窗口 列注释第三句 容忍 5 秒；快照列写 永不回改 没有基线就无法判断当前不一致是正常滞后还是故障，也无法配告警阈值
对账任务名 列注释末尾 对账任务 job_order_buyer_name 对账任务被下线或长期报错都没人发现，兜底层实际上是空的 
-- 最小可用骨架：先按 3NF 定下事实的唯一存放点，再把两类冗余列显式登记进注释
CREATE TABLE department (
  id         INT AUTO_INCREMENT PRIMARY KEY,   -- 代理键：部门改名、换负责人都不影响引用它的表
  name       VARCHAR(64) NOT NULL,
  owner_id   BIGINT      NOT NULL,
  -- updated_at 不是装饰：增量对账与增量同步都靠它筛出「最近变过的行」
  updated_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
  UNIQUE KEY uk_name (name)                    -- 业务唯一性交给唯一索引，不要让它去当主键
);

CREATE TABLE employee (
  id      BIGINT AUTO_INCREMENT PRIMARY KEY,
  name    VARCHAR(64) NOT NULL,
  dept_id INT         NOT NULL,                -- 只存引用，部门的任何属性都不复制过来
  KEY idx_dept (dept_id)
);

-- 快照列：属于交易凭证，写入时赋值，此后任何回填脚本都不许碰它
ALTER TABLE order_item
  ADD COLUMN sku_name   VARCHAR(128)  NOT NULL DEFAULT ''
      COMMENT '快照 取自 product.name 下单时赋值 禁止回填',
  ADD COLUMN unit_price DECIMAL(14,2) NOT NULL DEFAULT 0
      COMMENT '快照 下单时单价 禁止回填 对账口径以此列为准';

-- 冗余列：要跟随源表当前值，所以注释里四要素一项都不能省
ALTER TABLE `order`
  ADD COLUMN buyer_name VARCHAR(64) NOT NULL DEFAULT ''
      COMMENT '冗余自 user.nickname 由 user 变更消息回填 容忍 5 秒 对账任务 job_order_buyer_name';

② 原理 · 范式到底在解决什么：三类更新异常

搞清这一节能解决「宽表用着挺顺，为什么某次改名之后报表里同一个部门被拆成了两组」。

「范式是为了消除冗余」这句话只说对了一半。冗余本身不可怕，磁盘很便宜；真正致命的是冗余带来的更新异常——同一个事实存在多个位置，任何一次不完整的写入都会让数据库进入自相矛盾的状态，而数据库自己无法判断哪一份才是对的。把一张典型的「员工兼部门」宽表摊开，三类异常同时暴露出来。

-- 反面教材：一行同时描述了「员工」和「部门」两个互相独立的事实
CREATE TABLE emp_dept (
  emp_id      BIGINT        NOT NULL,
  emp_name    VARCHAR(64)   NOT NULL,
  dept_id     INT           NOT NULL,   -- 下面三列完全由 dept_id 决定，和 emp_id 无关
  dept_name   VARCHAR(64)   NOT NULL,
  dept_owner  VARCHAR(64)   NOT NULL,
  dept_budget DECIMAL(14,2) NOT NULL,
  PRIMARY KEY (emp_id)
);

-- 研发部有 300 名员工，于是「研发部叫研发部」这个事实在库里存了 300 遍。
-- 插入异常：新成立的数据平台部还没招到人，这张表里无处登记该部门。
-- 更新异常：部门改名要 UPDATE 300 行，改到第 200 行时连接断开，
--           库里于是同时存在两个部门名，且无法判断哪个是权威值。
-- 删除异常：最后一名员工离职，DELETE 掉这行的同时，部门预算信息一起消失。

异常 触发操作 库里会出现什么 根因 拆表后为什么消失
插入异常 登记一个还没有员工的部门 只能插一行 emp_id 为 0 的假员工，后续统计全错 部门事实寄生在员工行上，没有独立生存空间 department 表可以独立插入，与员工无关
更新异常 部门改名或换负责人 N 行要一起改，中途失败留下两个版本的部门名 同一事实存了 N 份，一致性靠一次大事务的原子性硬扛 事实只有一份，一行 UPDATE 天然原子
删除异常 删除部门里最后一名员工 部门预算、负责人信息随之消失，无法恢复 两个事实的生命周期被强行绑在一起 两张表生命周期独立，删员工不影响部门
统计口径衍生问题 按部门名做分组统计 同一部门被拆成两组，报表数字对不上 冗余列上没有任何唯一性约束可以保护 按 dept_id 分组，名称从单一来源关联取得

② 原理 · 1NF 到 BCNF：同一张表逐步拆

搞清这一节能解决「知道要拆表，但说不清该拆到哪一步就停」。

范式的定义都是围绕函数依赖展开的：如果知道了 A 的值就能唯一确定 B 的值，就说 B 函数依赖于 A。范式做的事情就是逐级赶走「不该出现在这张表里」的依赖。用一张订单明细宽表演示，它一次踩满了三级。

-- 起点：一张什么都往里塞的订单明细表
CREATE TABLE order_item_bad (
  order_id    BIGINT NOT NULL,
  sku_id      BIGINT NOT NULL,
  sku_name    VARCHAR(128),   -- 只依赖 sku_id，不依赖联合主键全部 → 违反 2NF
  sku_tags    VARCHAR(255),   -- 存 '手机,数码,5G' 这种逗号串      → 违反 1NF
  buyer_id    BIGINT,         -- 依赖 order_id
  buyer_city  VARCHAR(32),    -- order_id 定 buyer_id，buyer_id 定 city → 违反 3NF
  qty         INT,
  unit_price  DECIMAL(10,2),  -- 注意：这是「下单时快照」，不是冗余，见后文
  PRIMARY KEY (order_id, sku_id)
);

-- 第一步 → 1NF：逗号串拆成 sku_tag 关联表（sku_id, tag_id），
--   这样才可能对 tag 建索引、做等值过滤、加约束。
-- 第二步 → 2NF：sku_name 搬到 sku 表。判断口诀是「这列是不是只靠联合主键
--   的一部分就能决定」。注意 2NF 只在联合主键下才有意义，单列主键的表
--   天然满足 2NF；网上大量「这张表不满足 2NF」的例子其实说的是 3NF。
-- 第三步 → 3NF：buyer_city 删掉，需要时经 buyer_id 关联 user 表。
--   传递依赖的特征是「一个非主键列决定了另一个非主键列」。
范式 赶走哪种依赖 违反时的典型症状 怎么自查 业务表要不要做
1NF 列内还藏着结构 逗号分隔存多值，查询只能模糊匹配，索引完全用不上 有没有列必须在应用里切分才能用 必须。唯一例外是明确当作整体读写的 JSON 扩展列
2NF 对联合主键的部分函数依赖 关联表里混进维度表属性，改一次名要改成千上万行 逐列问「只用主键的一部分能不能决定它」 必须，但只有联合主键的表才需要检查
3NF 非主键列之间的传递函数依赖 用户表存部门名、订单表存用户当前手机号，源头一改就全脏 画一遍列之间的箭头，看有没有箭头不从主键出发 默认必须，退出要有明确理由和同步方案
BCNF 决定因素本身不是候选键的依赖 仅在存在多个互相重叠的候选键时出现，如一门课固定一位老师的排课表 列出所有候选键，检查每个决定因素是否都是候选键 基本不用管，正常的代理主键加业务唯一键结构很难违反
4NF 及以上 多值依赖、连接依赖 学术构造的例子，生产表结构里几乎不会自然出现 无需自查 不用管
💡
被广泛误传的两点

第一，「2NF 要求非主键列完全依赖主键」这句话对单列主键的表是废话，它永远成立，所以拿单列主键表举 2NF 反例的说法是错的。第二，3NF 和 BCNF 的差别只在一张表有多个重叠候选键时才显现。你的表如果是「自增 id 做主键，外加一个业务唯一索引」，做到 3NF 通常就已经满足 BCNF，不必再花时间推导。把精力放在识别传递依赖上，回报率高得多。

② 原理 · 反范式的四种手段与它们的维护义务

搞清这一节能解决「冗余加下去之后，为什么维护成本远超当初预估」。

范式化会把一个业务对象拆散到多张表，查询就要关联。关联本身不慢，慢的是「深分页加多表关联加排序字段跨表」这种组合，以及分库分表之后关联根本做不了。这时才轮到反范式上场。反范式只有四种手段，每一种都同时引入一份维护义务，把这三列摆在一起看才能做决定。

手段 适用信号 引入的维护义务 一致性风险
冗余字段
把关联表的少数列复制过来		 列表页每行都要展示它，读写比大于 10 比 1，源字段变更频率低（商品名、单位、类目名） 源表更新时必须回填，需要一次性回填脚本、一条同步通道、一个对账任务 中。漏掉一个写入入口就长期不一致，且没有任何约束能发现
合并表
把一对一或极小的一对多内联		 两张表总是一起查一起写，且从表行数固定很小（用户与用户设置） 列变多后所有全列查询都变贵，从表原有的唯一约束要重新表达 低。合并后事实仍只有一份，主要代价是行变宽
汇总表与预计算
把计数和求和落成物化行		 统计口径稳定、可接受分钟级延迟，或计数被高频读取（商家今日成交额、帖子回复数） 需要可重跑且幂等的重算任务；口径变更时要能整体回刷 低到中。属于派生数据，随时可从明细重建，这是它最大的优点
冷热拆分
大字段或历史数据另存		 行里有长文本或二进制但极少读取；或近三个月数据承担 99% 查询 访问路径变两步，归档任务要保证先复制后删除且可中断续跑 低。同一行只在一处，风险集中在搬迁过程的重复与漏搬

关键洞察

反范式不是「不做范式」，而是先做到范式，再有意识地、有记录地引入受控冗余。两者的产物在表结构上可能长得一样，区别只在三个问题上：哪些列是冗余的？每个冗余列的权威来源是谁？谁负责让它们同步、允许多大滞后？答得出来叫设计，答不出来叫技术债。最低成本的落地方式就是写进列注释，例如 COMMENT '冗余自 product.name，商品改名后由消息回填，容忍 5 秒'。

② 原理 · 冗余字段怎么同步：三种方式与不一致窗口

搞清这一节能解决「冗余列明明写了同步逻辑，线上还是持续出现对不上的行」。

先区分两种长得很像、语义却完全相反的列。快照列按定义就不该跟随源表变化：订单明细里的 unit_price 记的是下单那一刻的价格，商品后来涨价降价都与它无关，它根本不需要同步。冗余列才是要同步的那种：订单上冗余的 buyer_name 本意是展示买家当前昵称，源表一改它就该跟着改。把快照当成冗余去「修复」，是一类真实发生过的严重事故。

sequenceDiagram participant APP as 应用 participant SRC as product 源表 participant ORD as order 冗余列 participant MQ as 变更消息队列 participant JOB as 定时对账任务 APP->>SRC: 事务内 UPDATE 商品名 APP->>ORD: 同事务 UPDATE 冗余列 Note over SRC,ORD: 方式一 同事务双写
窗口为零 代价是事务变大 跨库不可用 APP->>SRC: UPDATE 后立即提交 SRC->>MQ: 投递行变更事件 MQ->>ORD: 消费者按主键回填 Note over MQ,ORD: 方式二 异步消息
窗口等于消费延迟 百毫秒到秒级 消息丢失则永久不一致 JOB->>SRC: 按更新时间增量扫描源表 JOB->>ORD: 比对差异并修复 Note over JOB,ORD: 方式三 定时对账
窗口等于调度周期 真正价值是兜住前两种的漏洞
同步方式 不一致窗口 失败模式 写路径开销 适用场景
同事务更新 零 冗余行过多时锁持有时间变长，极端情况触发锁等待超时甚至死锁 高，事务内多一次或多次写 冗余行数确定且很少（百行以内），两表同库
异步消息回填 消费延迟，正常百毫秒到秒级，积压时可到分钟级 消息丢失、消费者长期报错、乱序导致旧值覆盖新值 低，主事务不受影响 冗余行数大或跨库跨服务，业务能容忍短暂不一致
定时对账修复 调度周期，通常 5 分钟到 1 天 全表扫描压垮从库；对账逻辑本身写错，把正确值改坏 零，但占用批量窗口资源 作为兜底始终要有；单独使用仅限对时效完全不敏感的展示字段 
-- 1) 同事务双写：务必封装成唯一的修改入口，禁止任何地方裸写 product.name
START TRANSACTION;
UPDATE product SET name = ?, updated_at = NOW(3) WHERE id = ?;
-- 只回填「进行中」的订单，已完成订单按快照语义保持原值
UPDATE order_item SET sku_name = ?, updated_at = NOW(3)
 WHERE sku_id = ? AND order_status IN (0, 1);
COMMIT;

-- 2) 增量对账：只扫源表最近变更过的行，避免全表比对
--    product.updated_at 上要有索引；窗口取调度间隔的 2 倍，容忍时钟与延迟
SELECT oi.id, oi.sku_name AS stale_value, p.name AS truth
  FROM product p
  JOIN order_item oi ON oi.sku_id = p.id
 WHERE p.updated_at >= NOW() - INTERVAL 10 MINUTE
   AND oi.order_status IN (0, 1)
   AND oi.sku_name <> p.name
 LIMIT 1000;   -- 分批，永远不要用一条 SQL 扫全表

-- 3) 把差异行数打成监控指标。对账的意义在于「差异数长期为 0」这条曲线，
--    一旦抬头就说明有写入入口绕过了同步通道，而不是等用户来投诉。

② 原理 · 主键与外键：两个最贵的早期决策

搞清这一节能解决「主键选型当时觉得无所谓，分库或对外开放接口时才发现改不动了」。

主键选错的代价不是性能，而是迁移成本——它会被所有引用它的表、所有缓存键、所有对外接口固化下来。下表是四类方案的横向对照。至于「主键长度如何放大每一个二级索引」「随机主键为什么造成页分裂和写放大」这类存储层机制，站内《MySQL 深度原理》篇已经从 B+ 树和聚簇索引层面推演过，这里只取结论。

方案 有序性 索引写放大 跨库唯一 可推测性 什么时候选它
单库自增 BIGINT 严格递增 最小，8 字节且写入永远追加在索引末尾 否 高，能被遍历、能推测业务规模 单库单表默认选它，对外另给一个不可推测的编号
雪花类分布式 ID 趋势递增，同毫秒内不保序 小，8 字节且基本是追加写 是 中，能从 ID 反推大致时间 需要分库分表，或写库之前就要拿到 ID
UUID v4 完全随机 大，16 字节且随机插入引起页分裂 是 低 只在无中心协调的离线场景考虑，不建议做聚簇主键
业务字段（手机号、编码） 无规律 大，字符串通常更长且被所有二级索引带上 取决于业务规则 高，直接泄露业务信息 基本不选，改为代理键加唯一索引

业务字段做主键的痛点要等业务规则变化时才会引爆：手机号会换绑，身份证号存在补录与纠错，商品编码规则会因为新增品类而重排。主键一变，所有引用它的子表、所有缓存、所有已发出的对外单号都要跟着动，而这类改造几乎没有安全的回滚路径。正确做法是职责分离——行标识用无业务含义的代理键，业务唯一性交给唯一索引，两者互不干扰。

⚠️
外键要不要用：分场景，不要一刀切

内部管理系统、配置与字典类数据、写入量低而正确性要求高的库，建外键：让数据库兜住应用的缺陷，能省下大量排查脏数据的时间。高并发核心交易表不建：外键带来父表上的额外加锁与隐式检查，级联删除的影响范围难以预估，而且一旦分库分表，跨库外键根本无法成立。关键是要认清不建外键的真实代价：「应用层保证」如果没有配套的孤儿行扫描任务和显式的父子删除处理，它就只是一句口号，最终表现为报表里永远对不上的那几百行。

② 原理 · 软删除的代价与字段设计规范

搞清这一节能解决「加了 deleted 标记之后，唯一索引为什么开始报重复键、统计数字为什么慢慢偏了」。

软删除是被讨论最多、被低估最严重的设计。它有三笔账：第一，此后每条查询都必须带上 deleted = 0，漏一处就是数据泄露或统计错误，而这个条件完全靠人工纪律，没有任何机制强制；第二，唯一索引失效，同一个编码删了再建就会撞唯一键；第三，表无限增长，已删行和活跃行挤在相同的数据页里，拉低所有查询的缓存命中率。

-- MySQL 方案：把「删除时刻」编进唯一索引，同一 code 可以被反复删除
ALTER TABLE coupon
  ADD COLUMN deleted_at BIGINT NOT NULL DEFAULT 0
      COMMENT '0 表示未删除，删除时写入毫秒时间戳',
  ADD UNIQUE KEY uk_code_deleted (code, deleted_at);
-- 逻辑删除：UPDATE coupon SET deleted_at = UNIX_TIMESTAMP(NOW(3)) * 1000 WHERE id = ?
-- 常见错误：用 is_deleted 布尔列做联合唯一，同一个 code 只能删一次，第二次撞重复键

-- PostgreSQL 方案更干净：部分唯一索引，只对未删除行生效
CREATE UNIQUE INDEX uk_coupon_code_alive ON coupon (code) WHERE deleted_at IS NULL;

-- 推荐的替代方案：归档表。主表只装活跃数据，删除即搬迁
CREATE TABLE coupon_archive LIKE coupon;
ALTER TABLE coupon_archive
  ADD COLUMN archived_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  ADD COLUMN archived_by VARCHAR(64) NOT NULL DEFAULT '';
-- 同一事务内先复制后删除：
--   INSERT INTO coupon_archive (...) SELECT ... FROM coupon WHERE id = ?
--   DELETE FROM coupon WHERE id = ?
-- 收益：主表查询不再需要任何删除条件，唯一索引恢复正常语义，审计信息更完整
规范 具体做法 不这么做的后果
默认 NOT NULL 除了「未知」和「空」确实语义不同的列，全部 NOT NULL 并给默认值 NULL 参与比较和聚合的规则与直觉不符，按列计数会跳过 NULL，等值条件永远匹配不到 NULL 行
时间列必备 每张表都有 created_at 与 updated_at，精度到毫秒，updated_at 自动更新 无法做增量同步和增量对账，也无法回答「这行什么时候变过」
状态用小整数 TINYINT 加列注释写清每个取值，应用侧用枚举，数据库侧可加 CHECK 字符串存状态会出现大小写与拼写不一致；数据库 ENUM 则加值要 DDL、删值几乎不可能
金额与精度 DECIMAL 存金额并统一到最小货币单位，禁止 FLOAT 与 DOUBLE 浮点累加产生分位误差，对账永远差几分钱且无法复现
大字段分离 长文本、JSON、二进制与高频更新的热字段不放同一张表 行变宽导致每页装的行数骤减，顺序扫描与缓存效率同时下降
不留预留字段 禁止 ext1 到 ext5 这类占位列，需要扩展用 JSON 列或新表 预留字段一定会被不同业务混用，三个月后没人知道 ext3 存的是什么，且无法加约束和索引
命名与类型一致 同一含义的列在所有表里同名同类型，如 user_id 全站统一 BIGINT UNSIGNED 类型不一致导致关联时隐式转换、索引失效；名字不一致让新人反复问「这两个是同一个东西吗」

③ 场景 · 这个字段该不该冗余：完整决策路径

「加个冗余字段吧」这句话在评审会上出现时，要能在三十秒内判断该不该点头。下面这条路径把判断拆成几个可回答的问题，顺序很重要：先确认收益（是不是高频且必须），再确认语义（是快照还是冗余），再确认成本（源列变不变、能不能同一事务），最后才选同步方式。它是用法层四步判断的展开版，多出的两个分叉专门处理「读写比不够」和「跨库」这两种最常被忽略的否决条件。

场景 该怎么做 为什么 代价
内部管理后台，数据量小、写入量低 做到 3NF，建外键，一个冗余列都不要加 关联代价远低于同步代价，数据库能帮你挡住应用的缺陷 列表页多几次关联，几乎不可感知
C 端列表页，每行都要展示关联表的一两个名称 冗余名称列，异步回填加定时对账 关联在深分页与跨表排序下会先崩，而名称类字段变更频率极低 多一条同步通道和一个对账任务，不一致窗口等于消费延迟
交易凭证：订单、发票、结算单 把商品名、单价、收货信息全部落成快照列，注释标禁止回填 凭证内容必须凝固在成交那一刻，否则对账、发票、客诉无法举证 存储变大，且要在评审里长期拦住「顺手修一下历史数据」的脚本
高频读的计数与金额汇总 物化成计数列或汇总表，配可重跑的幂等重算 派生数据可以随时从明细重建，出错代价最低 重算窗口内数字会有偏差，产品上必须标明延迟
写入点散落在多个服务，还有脚本直连改库 不要靠业务代码同步冗余列，改成订阅数据库变更统一回填 「每个写入口都记得同步」在多团队下守不住，漏一个就是长期脏数据 多一套采集组件要做高可用，回填延迟升到百毫秒到秒级
已经分库分表，冗余的源表在另一个库 要么把这个值做成快照（如果语义允许），要么放弃冗余走聚合查询服务 跨库既没有共同事务边界，也无法用外键或对账 SQL 一次比对 聚合查询多一次网络往返，需要单独做超时与降级
余额、库存、可用额度、券剩余量 唯一存放点，不冗余不缓存，扣减用带条件的原子更新并检查影响行数 读到旧值的后果不可逆，压缩窗口没有意义 读写都压在权威表上，抗并发要靠串行化或额度分片下发
报表与检索类查询拖慢线上库 不要为它们改线上表结构，导到列式库或搜索引擎 这类查询要的是宽表与倒排，和事务库的行存目标相反 多一条数据管道，查询结果有固定延迟

③ 场景 · 表设计评审清单与不适用边界

把这张表贴在评审文档末尾，逐条打勾。它能在十分钟内拦住绝大多数上线后要付代价的设计。

检查项 不通过的典型表现 上线后的代价
每张表能用一句话说清它存什么事实 说明里出现「也可以存」「顺便放」 表会长成谁都不敢改的宽表
有没有传递依赖残留 列注释写着「同某表的某字段」但没说同步方式 源表一改就出现长期脏数据
每个冗余列都登记了来源与同步方式 注释只是列名的复述 出问题时无法判断哪个值是权威的
主键是代理键，业务唯一性由唯一索引表达 用业务编码或手机号做主键 业务规则一变就要全站迁移
写入路径是否唯一收口 多个服务各自直接更新同一张表 冗余列永远同步不全
三年后的行数与单行字节估算过 没有估算 要么过早分库分表，要么等到告警才动手
查询模式列出来了，且每条都能走索引 只有表结构没有查询清单 索引后补，且极易补成互相重叠的冗余索引
删除与归档策略明确 默认软删除，无归档计划 表无限增长，查询条件长期靠人工纪律维持

不适用边界：本篇只负责把「一份事实存几遍」这个问题的答案确定下来。怎么从需求推出实体、关系基数与四类难模式（继承、树形、状态、版本）见下一篇 业务建模：从需求到表结构；表结构上线之后怎么安全地加列删列改类型加约束见 模式演进与约束设计；多租户数据归属与分片键怎么定见 数据归属与多租户；索引列顺序怎么排、无用索引怎么识别下线在 索引设计与优化；分片算法与扩容迁移在 分库分表；单条 SQL 为什么慢在 慢查询治理；主键长度如何放大每个二级索引、随机主键为什么造成页分裂在 MySQL 深度原理；字段类型本身怎么选（timestamptz、numeric、jsonb 的边界）在 PostgreSQL 数据类型；冗余值放进缓存之后的脏数据窗口在 缓存一致性与失效。

这条路径上，本篇定的是「事实存几份、谁是权威」，下一篇才开始回答「有哪些事实、它们之间什么关系」——顺序不能反，因为关系画错了，冗余判断也就无从下手。

最容易踩的坑

❌
避坑指南
  • 把订单明细里的 unit_price 当成需要同步的冗余列，写了个「修复脚本」按当前商品价回刷，历史订单金额集体变化——这是把快照语义误当冗余的真实事故，快照列必须在注释里显式标注「禁止回填」。
  • 用逗号串存多值（tags = '手机,数码,5G'），后来要按标签筛选只能做模糊匹配，全表扫描而且会把「数码相机」一起匹配进来。
  • 软删除只加了 is_deleted 布尔列，同一个 code 删了再建撞唯一键；改成 (code, is_deleted) 联合唯一后第二次删除又撞键，必须用时间戳或部分唯一索引。
  • 预留了 ext1 到 ext5，半年后三个业务混用同一列存了三种格式，既不能建索引也不能加约束，清理时无法判断哪行属于谁。
  • 状态列用了数据库 ENUM，需要加新状态时发现要改表，删旧值则牵动历史数据，最后只能永远保留废弃值。
  • 关联列类型不一致，一边 BIGINT 一边 VARCHAR，关联时发生隐式类型转换导致索引失效，而 SQL 本身看不出任何问题。
  • 用 DOUBLE 存金额，对账长期差几分钱，差额还随数据量变化无法复现。
  • 冗余字段只在「主流程」里同步，忘了后台管理页面和运营批量工具也能改源表，于是不一致只在特定入口产生，排查数周。
  • 异步回填没做乱序保护，同一行的两次变更被乱序消费，旧值覆盖新值；回填时要带上源表的 updated_at 或版本号做条件更新。
  • 把长文本详情和高频更新的库存计数放在同一张表，每次扣减库存都要搬动整行，写吞吐远低于预期。
  • 建了外键还配了级联删除，某次运营删掉一条父配置，级联带走几十万子行，且没有任何提示。
  • 没有 updated_at，后来要做增量同步和增量对账时发现无从下手，只能全表比对。
