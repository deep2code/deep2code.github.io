数据归属与多租户：分片的数据模型策略

🏷️ 分库分表

分片有两层问题。一层是工程层面的：分片键怎么选、用什么分片算法、怎么生成全局 ID、中间件选谁、扩容迁移怎么不停机——这些站内《分库分表》篇已经完整讲过决策与落地流程。另一层是数据模型层面的：哪些数据属于同一个归属单元、主表和从表怎么一起分、两种查询维度冲突时怎么办、多租户怎么隔离。这一层决定了分片方案的上限，而且一旦定错，后期只能靠整表迁移来纠正。这篇只讲第二层。

💡

  • ① 用法：定多租户数据归属的四步判断（先问合规硬隔离、再看租户数与规模分布、再看结构变更频率、最后看资源争抢与迁出需求），三种隔离模型的速查与迁出成本，租户键与分片键的四种对应关系，外加共享表模型的建表模板与查询模板。

  • ③ 场景：按业务形态选归属与隔离的取舍矩阵、五项必做校验、生命周期与归档，以及本篇的不适用边界。

① 用法 · 多租户数据归属：四步判断

数据归属要在第一天定对，因为它决定了后面所有事：唯一索引怎么建、能不能按客户单独备份、大客户能不能被搬走。下面四步按顺序问，第一步答「是」就直接结束。每一步背后的机制见原理层。

步骤怎么确认结论
1 有没有硬隔离要求翻合同与合规条款：客户是否要求数据独立存放、独立备份、按要求彻底删除，或有数据驻留地约束有 → 这些客户直接给独立库，后面三步不用问；成本记在该客户头上，不要为了它把所有租户都改成独立库
2 看租户数与规模分布统计租户总数，以及前百分之一的租户占了多少数据量成千上万且以长尾为主 → 共享表加租户列；几十到几百且彼此规模接近 → 每租户一个 schema 也可行；存在占比三成以上的大租户 → 一定要准备独占位置
3 看结构变更频率数一数最近半年这套表上执行过多少次 DDL变更频繁 → 共享表，一次 DDL 全部生效；选 schema 方案就要接受每次变更在 N 个 schema 上循环执行，并处理「执行到第 300 个失败」的中间态
4 看资源争抢与迁出需求问两个问题：某个租户的慢查询会不会拖垮其他人？将来要不要把某个客户单独迁走或单独扩容会 → 混合模型：路由层维护一张「租户到存储位置」映射表，默认落共享表，被识别出的大客户与合规客户指向独立库
隔离模型什么时候选它租户键出现在哪迁走单个租户的成本
共享表加 tenant_id长尾小客户、免费版、租户数成千上万每张业务表的第一列、所有唯一索引的首列、所有查询的第一个条件中。要按条件导出、双写、切流、校验，且导出时要保证关联数据完整
每租户一个 schema租户数在几十到几百，需要一定隔离且规模接近不在表里，在连接的搜索路径上低。按 schema 导出导入即可
每租户一个库大客户、有合规或数据驻留要求的客户不在表里，在路由映射表上最低。库级备份恢复，甚至可以整体换机房
混合模型实践中的默认答案共享部分带 tenant_id，独立部分靠映射表低，而且可以按客户逐个迁移，不必一次性改造全部租户

① 用法 · 租户键与分片键的关系，以及建表模板

租户键和分片键是两件事，混为一谈会导致两类后果：要么大租户把单片打满，要么租户内部的查询全都变成跨片。下表给出四种情形的对应关系。

情形分片键取什么为什么
租户很多，但每个租户的数据量都不大分片键就是租户键，按 tenant_id 散列一个租户的全部数据落在同一片，租户内的任何查询都是单片操作，本地事务也成立
存在占比很高的超大租户仍按租户键散列，但用路由映射表把大租户写死到独占位置散列只能均衡「租户数量」，不能均衡「数据量」；加分片数对这种倾斜毫无帮助
单个租户内部的数据量已超单机分片键换成租户内部的业务维度（如 buyer_id），租户键退化成普通过滤列这时按租户分片等于没分片，该租户的数据仍然全在一片上
多租户又有买家、卖家两个查询维度主数据按一个维度分片，另一维度建异构索引表，索引表同样带上租户列一套分片无法同时满足两个维度，强行满足的结果是两边都变成全分片扫描加内存归并
-- 共享表模型的建表模板：tenant_id 有三个位置，一个都不能省
CREATE TABLE orders (
  tenant_id  BIGINT      NOT NULL,        -- 位置一：每张业务表都有，禁止可空，禁止用 0 当默认
  id         BIGINT      NOT NULL,
  buyer_id   BIGINT      NOT NULL,        -- 分片键：租户内部还需要分片时按它路由
  biz_no     VARCHAR(32) NOT NULL,
  status     TINYINT     NOT NULL DEFAULT 0,
  created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  PRIMARY KEY (tenant_id, id),            -- 位置二：主键与所有唯一索引都以 tenant_id 开头
  UNIQUE KEY uk_tenant_bizno (tenant_id, biz_no),
  -- 少了 tenant_id 的唯一索引会导致「第一个租户用掉这个编号，其他租户都建不了」，
  -- 用户看到的现象是「系统说编码已存在，但我的列表里没有」
  KEY idx_tenant_buyer_time (tenant_id, buyer_id, created_at)
);

-- 从表必须冗余父表的分片键，写入时赋值、此后永不更新
CREATE TABLE order_item (
  tenant_id BIGINT NOT NULL,
  id        BIGINT NOT NULL,
  order_id  BIGINT NOT NULL,
  buyer_id  BIGINT NOT NULL COMMENT '冗余父表分片键 仅用于路由 写入时赋值 禁止更新',
  PRIMARY KEY (tenant_id, id),
  KEY idx_order (tenant_id, order_id)     -- 查一张订单的明细：单片内一次索引扫描
);
-- 查询模板：位置三。租户条件永远是第一个条件，而且必须由框架注入
SELECT id, biz_no, status FROM orders
 WHERE tenant_id = ?                      -- 框架注入；取值缺失或为 0 时必须直接报错
   AND (created_at >= ? AND status = ?)    -- 业务条件整体加括号
 ORDER BY created_at DESC, id DESC
 LIMIT 20;
-- 不加括号时业务写出 "a = 1 OR b = 2" 会变成 tenant_id = ? AND a = 1 OR b = 2，
-- OR 的优先级低于 AND，租户条件被整条绕过，直接返回别人的数据。
-- 框架层怎么强制、数据库层怎么再加一道行级安全，见原理层。

② 原理 · 先确认真的需要分片

搞清这一节能解决「分完片才发现真实问题只是历史数据太多」这种白付复杂度的情况。

「单表几亿行，必须分库分表」这个判断在多数情况下是错的。因为它把两件事混在一起：数据总量大和活跃数据量大。如果几亿行里只有最近三个月的几千万行被查询，那么需要的不是分片，是归档。归档的复杂度比分片低一个数量级，而且不会引入跨片查询和分布式事务。

方案解决什么引入的复杂度什么时候它不够用
时间分区加归档历史数据挤占活跃数据的缓存与索引空间低。访问路径分近期与历史两条，归档任务要可续跑活跃窗口内的数据本身就超出单机容量
只读副本分流读压力大、重查询影响主库低。要处理复制延迟与读写分离的一致性写入吞吐已经是瓶颈
垂直拆分（按业务域拆库）不同业务互相影响，单库连接数与容量到顶中。跨库事务变成分布式事务，但不产生跨片查询单个业务域自身的数据量仍然过大
水平分片单表容量与单机写入吞吐高。跨片查询、分布式事务、扩容迁移、全局 ID 全部要处理它是最后一道，不够用时只能加分片数

② 原理 · 数据归属：先找聚合根

搞清这一节能解决「订单详情页在分片之后延迟翻了几倍」这个最典型的归属错误。

分片的第一个动作不是选分片键，而是划分数据归属：把所有表按「属于哪个业务实体」分组，同一组的数据必须落在同一分片。这个「业务实体」就是聚合根——它是外部访问这组数据的唯一入口，也是事务边界。

识别聚合根只要问两个问题：外部是通过哪个 ID 来访问这组数据的？哪些数据必须和它在同一个事务里被修改？订单和订单明细必须一起改、一起查，明细从不被单独访问，所以订单是聚合根，明细属于它。用户和用户地址同理。

数据聚合根它的分片键应该是如果按自己的主键散列会怎样
order_item 订单明细订单订单所在维度的值（如 buyer_id），冗余一列存进明细表查一张订单的明细要问遍所有分片，且无法与订单在同一本地事务里提交
order_status_log 状态流转订单同上订单详情页要并发查 N 个分片，延迟等于最慢分片
order_addr_snapshot 地址快照订单同上一对一关联变成跨片查询，白白多一跳
user_address 收货地址用户user_id用户中心页要扫全分片
product 与 sku商家shop_id商家商品管理页无法单片完成，且商品与 SKU 可能落在不同片
region 地区表、字典表无归属不分片，广播到所有分片或放公共库任何需要它的关联都变成跨片
❌
最常见也最难补救的错误

从表按自己的主键散列。order_item 按 id 取模、order_status_log 按 id 取模，看起来「分布很均匀」，实际上把一次订单详情查询变成了 N 次全分片广播，并且订单主表和明细无法在同一个本地事务里提交，必须引入分布式事务。从表的分片键必须冗余父表的分片键列，也就是明细表上除了 order_id 还要带一列 buyer_id，路由按 buyer_id 算。这一列的值在插入时确定、此后永不变化。纠正这个错误意味着整表重新迁移，所以它必须在第一天就定对。

怎么选？看哪一侧的查询更高频、更在意延迟、更难降级。C 端买家侧通常量级高一两个数量级且对延迟敏感，所以主数据按买家维度分片是更常见的选择；商家后台可以接受稍高的延迟和稍弱的实时性，用下一节的方式补上。反过来，在以商家为核心的 SaaS 型系统里，按商家分片才是对的。没有普适答案，但有一条纪律：主数据只有一个归属维度，另一个维度必须靠额外机制解决，不要试图让一套分片同时满足两边。

② 原理 · 两种查询维度的三种解法

搞清这一节能解决「商家后台列表怎么在不复制全量数据的前提下做到单片分页」。

sequenceDiagram participant W as 写入方 下单 participant P as 买家维度分片 主数据 participant MQ as 变更消息 participant IX as 卖家维度异构索引分片 participant R as 商家后台查询 W->>P: 本地事务写 order 与 order_item P-->>W: 提交成功 W->>MQ: 同事务写本地消息表 再投递 MQ->>IX: 写映射行 只含 shop_id 与 order_id 与时间与状态 R->>IX: 按 shop_id 分页 拿到本页订单号列表 IX-->>R: 返回 20 个 order_id R->>P: 按 order_id 批量回主表取详情 走买家维度路由 P-->>R: 返回本页详情 Note over IX,R: 只有映射表按卖家分片 主数据不复制
存储开销极小 但排序字段必须存在映射表上 Note over W,IX: 一致性靠本地消息表加对账
映射表丢一行的表现是商家列表少一单
解法存储成本一致性实现复杂度限制与适用
异构索引表
按另一维度存只含 ID 的映射		低，每单一行窄记录最终一致，靠本地消息表加对账中，查询变两步默认推荐。限制是所有排序和筛选字段都必须冗余进映射表，否则分页要回表后再排序，结果就错了
双写两套分片
同一份数据在两个维度各存一份完整副本		高，翻倍较难，两套都要写成功且字段全量同步高，任何加列都要改两边两个维度都要求低延迟完整查询且预算充足时用；实践中很少选
列表整体外置
数据库只做主键点查		中，检索侧另算最终一致，延迟通常秒级中高，多一套组件与索引映射筛选维度多、要做全文或多字段组合查询时唯一可行的方案；量级上来后基本都会走到这里
-- 异构索引表：按 shop_id 分片，只存卖家维度的分页与筛选所需字段
CREATE TABLE order_index_by_shop (
  shop_id     BIGINT      NOT NULL,
  order_id    BIGINT      NOT NULL,
  buyer_id    BIGINT      NOT NULL COMMENT '回主表路由用，必须带上否则无法定位主数据分片',
  order_status TINYINT    NOT NULL COMMENT '冗余：商家后台要按状态筛选',
  created_at  DATETIME(3) NOT NULL COMMENT '冗余：商家后台按下单时间倒序翻页',
  pay_amount  DECIMAL(14,2) NOT NULL DEFAULT 0 COMMENT '冗余：列表页要显示与按金额排序',
  PRIMARY KEY (shop_id, created_at, order_id),   -- 直接支撑按店铺按时间翻页
  KEY idx_shop_status (shop_id, order_status, created_at)
);

-- 第一步：在卖家维度分片上分页，注意用游标分页而不是 OFFSET
SELECT order_id, buyer_id FROM order_index_by_shop
 WHERE shop_id = 88 AND order_status = 1
   AND created_at < ?          -- 上一页最后一行的 created_at，避免深分页
 ORDER BY created_at DESC, order_id DESC
 LIMIT 20;

-- 第二步：按 buyer_id 路由回主数据分片批量取详情（按分片分组后并发查询）
SELECT * FROM orders WHERE buyer_id IN (?, ?) AND id IN (?, ?, ?);

-- 对账：主表与索引表按小时桶比对条数，差异不为零就报警并补写
SELECT DATE_FORMAT(created_at, '%Y-%m-%d %H') AS h, COUNT(*) FROM orders
 WHERE created_at >= ? AND created_at < ? GROUP BY h;   -- 各主分片求和后与索引表按店铺汇总比对
⚠️
异构索引表最容易被漏掉的一点

排序和筛选字段必须完整冗余进映射表。只存 shop_id 和 order_id 的映射表，在「按金额倒序」或「按状态筛选」这类需求下会退化成：先取出全部 order_id，回主表查详情，再在应用内存里排序分页。数据量一大就直接超时，而且分页结果在数据变动时会漂移。所以映射表的字段集合应该由列表页的排序项和筛选项决定，而不是「先存两列以后再说」。这也意味着列表页新增一个筛选项时，映射表要走一次完整的加列加回填流程。

② 原理 · 跨片关联的三种替代

搞清这一节能解决「中间件说支持跨片 JOIN，为什么一上量就打爆内存」。

分片之后跨片 JOIN 基本不可用：中间件即使支持，代价也是把参与方全部拉到内存再关联，量级稍大就失控。真正可用的只有三种替代。

替代方式怎么做适用条件代价与限制
冗余关键字段把关联表上「列表页要展示的少数列」复制到主表，查询不再需要关联被冗余的列变更频率低，或语义上是快照需要同步通道与对账；冗余列的维护义务见站内《范式与反范式》篇
广播表维表在每个分片上存一份完整副本，关联永远在本地完成行数小于几万、一年内不会被业务写入、不参与事务性更新，典型是地区表、字典表、汇率表写放大 N 倍，变更要确认所有分片都成功；被滥用在会增长的业务表上后果很严重
应用层两次查询再拼装先查主表拿到关联 ID 集合，再批量查另一侧，在应用里组装关联侧可以按主键批量查，且单页结果集有限（几十行量级）多一次往返；必须批量查而不是循环单查，否则一页 20 行会产生 20 次查询

② 原理 · 多租户的三种隔离模型

搞清这一节能解决「隔离模型选定之后，成本、越权风险与变更成本各自落在哪里」。

维度共享表加 tenant_id每租户一个 schema每租户一个库
单位成本最低，几千租户共用一套资源中，表对象数量等于租户数乘表数最高，实例或库数量等于租户数
隔离强度弱，只有逻辑隔离，一条漏条件的查询就越权中，误查另一个 schema 的概率低但仍可能强，连接层面就无法访问其他租户
结构变更一次 DDL 全部生效要在 N 个 schema 循环执行，且要处理部分失败要在 N 个库执行，通常需要专门的编排工具
资源争抢严重，一个大租户的慢查询影响全部租户存在，共享同一实例的缓冲池与连接数无，故障域按租户切开
按租户备份与恢复难，要按条件导出并保证外键完整中等，可按 schema 导出容易，库级备份恢复
适合谁长尾小客户、免费版、租户数成千上万租户数在几十到几百且需要一定隔离大客户、有合规或数据驻留要求的客户

结论是混合模型：在路由层维护一张「租户到存储位置」的映射表，默认落共享表，大客户和合规客户指向独立库。这样既控制了长尾成本，又能在客户量级上来时平滑迁走单个租户，而迁移单个租户的数据比迁移一个分片容易得多。

② 原理 · 共享表模型的越权防线

搞清这一节能解决「一条漏带租户条件的查询把别人的数据返回给了客户」这种最严重的事故。

共享表模型真正的风险不是性能，是越权。一条漏带 tenant_id 的查询就是一次跨租户数据泄露，而这种漏写在代码评审里极难发现。靠开发自觉是不成立的，必须在框架层强制。

package tenantscope

import (
	"errors"
	"fmt"
	"strings"
)

// 需要租户隔离的表必须显式登记。进程启动时用 information_schema 对比一遍，
// 发现有 tenant_id 列但没登记的表就直接启动失败 —— 让漏登记在部署时暴露，
// 而不是等到线上某个接口把别人的数据返回给用户。
var scoped = map[string]bool{
	"orders": true, "order_item": true, "invoice": true, "audit_log": true,
}

var (
	ErrNoTenant     = errors.New("tenantscope: 上下文中没有租户标识，拒绝执行")
	ErrNotRegistered = errors.New("tenantscope: 表未登记租户隔离")
)

// BuildSelect 是唯一允许拼装隔离表查询的入口，业务代码拿不到裸 SQL 通道。
func BuildSelect(tenantID int64, table string, cols []string,
	cond string, args []any) (string, []any, error) {

	// 关键点一：租户标识为零值时必须报错，绝不能退化成「查全部」。
	// 很多越权事故的根因就是默认值 0 被当成「不过滤」。
	if tenantID == 0 {
		return "", nil, ErrNoTenant
	}
	if !scoped[table] {
		return "", nil, fmt.Errorf("%w: %s", ErrNotRegistered, table)
	}

	var b strings.Builder
	b.WriteString("SELECT ")
	b.WriteString(strings.Join(cols, ", "))
	b.WriteString(" FROM ")
	b.WriteString(table)
	// 关键点二：租户条件永远是第一个条件，且由框架注入。
	b.WriteString(" WHERE tenant_id = ?")

	out := make([]any, 0, len(args)+1)
	out = append(out, tenantID)
	out = append(out, args...)

	if cond != "" {
		// 关键点三：业务条件必须整体加括号。
		// 否则业务写出 "a = 1 OR b = 2" 时会变成
		//   tenant_id = ? AND a = 1 OR b = 2
		// OR 的优先级低于 AND，租户条件被绕过，直接跨租户返回数据。
		b.WriteString(" AND (")
		b.WriteString(cond)
		b.WriteString(")")
	}
	return b.String(), out, nil
}
-- PostgreSQL 行级安全策略：在数据库层再加一道，防住框架被绕过和临时脚本直连
ALTER TABLE orders ENABLE ROW LEVEL SECURITY;
-- 注意：不加 FORCE，表的所有者会绕过策略，而应用账号往往就是所有者
ALTER TABLE orders FORCE ROW LEVEL SECURITY;

CREATE POLICY p_tenant_isolation ON orders
  USING (tenant_id = current_setting('app.tenant_id', true)::bigint)
  WITH CHECK (tenant_id = current_setting('app.tenant_id', true)::bigint);
-- USING 管读与更新可见性，WITH CHECK 管写入，两个都要给，
-- 只给 USING 时仍可以插入属于别人的 tenant_id。

-- 每个请求在事务开始时设置，SET LOCAL 随事务结束自动失效，
-- 这一点在连接池场景下至关重要：用 SET 而不是 SET LOCAL 会让设置残留在
-- 被复用的连接上，下一个请求就会读到上一个租户的数据。
BEGIN;
SET LOCAL app.tenant_id = '1001';
SELECT id, amount FROM orders WHERE created_at >= now() - interval '7 days';
COMMIT;

② 原理 · 租户倾斜与生命周期

搞清这一节能解决「散列明明很均匀，为什么某一片先满」。

按租户散列无法解决倾斜。散列只保证租户数量分布均匀，不保证数据量分布均匀。一个占总量三成的大租户，落到哪一片都会把那一片打满。解法是在路由层加映射表：默认走散列，识别出的大租户写死指向独占分片。

-- 识别倾斜租户：行数占比与近期增速一起看，只看总量会漏掉新晋大客户
SELECT tenant_id,
       COUNT(*)                                                   AS rows_total,
       ROUND(COUNT(*) * 100.0 / SUM(COUNT(*)) OVER (), 2)         AS pct_of_all,
       SUM(created_at >= NOW() - INTERVAL 7 DAY)                  AS rows_last_7d,
       MOD(CRC32(CAST(tenant_id AS CHAR)), 16)                    AS shard_no
  FROM orders
 GROUP BY tenant_id
HAVING rows_total > 1000000 OR rows_last_7d > 200000
 ORDER BY rows_total DESC
 LIMIT 50;

-- 分片维度看倾斜：理想情况各分片接近均分，最大与最小之比超过 2 就该处理
SELECT MOD(CRC32(CAST(tenant_id AS CHAR)), 16) AS shard_no,
       COUNT(DISTINCT tenant_id) AS tenants, COUNT(*) AS rows_total
  FROM orders GROUP BY shard_no ORDER BY rows_total DESC;

-- 路由映射表：默认散列，命中这张表的租户强制走指定位置
CREATE TABLE tenant_location (
  tenant_id BIGINT PRIMARY KEY,
  ds_name   VARCHAR(64) NOT NULL COMMENT '数据源名，指向独占库或独占分片',
  mode      TINYINT     NOT NULL DEFAULT 1 COMMENT '1独占库 2独占分片 3共享表',
  updated_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3)
);

③ 场景 · 按业务形态选归属与隔离

下面这张矩阵把常见的业务形态摊开。注意最后两行：它们的正确答案都是「先不要分片」。

场景该怎么做为什么代价
C 端交易，买家侧量级高一两个数量级主数据按买家维度分片，商家后台走按卖家维度的异构索引表把单片能力给到最高频、最在意延迟、最难降级的那一侧商家侧查询变两步且是最终一致，映射表新增筛选项要走一次加列回填
以商家为核心的 SaaS（收银、进销存、CRM）按商家（租户）维度分片，商家键即租户键几乎所有查询都在单个商家范围内，天然单片且本地事务成立大商家会造成倾斜，必须提前准备独占位置与路由映射表
租户成千上万、以长尾免费用户为主共享表加租户列，框架强制注入租户条件，数据库侧再加行级安全单位成本最低，一次 DDL 全部生效隔离最弱，越权只能靠机制堵；一个大租户的慢查询会影响所有人
少数大客户有合规或数据驻留要求只给这些客户独立库，其余保持共享表，靠路由映射表统一寻址合规成本只压在需要它的客户身上，不必全体改造运维对象变多，变更要在共享集群与独立库两套路径上都执行
租户数几十到几百、规模接近、变更不频繁每租户一个 schema比共享表隔离强，比独立库便宜，可按 schema 备份每次 DDL 要在 N 个 schema 循环执行，必须能处理「执行到一半失败」
筛选维度多、要做全文或多字段组合查询列表整体外置到检索服务，数据库只做主键点查异构索引表只能覆盖固定的排序与筛选组合，维度一多就撑不住多一套组件与索引映射，结果有秒级延迟，要处理索引重建
全站经营分析、跨租户报表同步到分析型数据库，绝不在分片主库上跑这类查询本身要扫大量数据，与在线分片的目标冲突多一条数据管道，分析结果有固定延迟
几亿行但只有近三个月被查时间分区加归档，不分片复杂度低一个数量级，且不引入跨片查询与分布式事务访问路径分近期与历史两条，归档任务要可中断续跑

③ 场景 · 五项必做校验与不适用边界

下面五项校验是分片方案的体检表。差异不为零时的含义那一列比校验方法更重要，它决定了报警该派给谁。

校验项怎么做差异不为零时的含义
主表与异构索引表条数按小时桶分别汇总各分片条数后比对索引写入丢失，表现为商家列表少单
广播表各副本一致性各分片计算行数与整表校验和并比对某个分片的广播写失败，该分片的关联结果错误
冗余分片键列的正确性抽样校验从表的分片键列与父表是否一致存在写入时未正确赋值的行，这些行永久查不到
租户数据不跨界按租户抽样统计各位置行数，与路由映射表期望比对迁移遗留或路由配置错误，可能已发生越权
分片容量与增速定期记录各分片行数与磁盘占用，计算增速倾斜正在形成，提前拆分而不是等告警

最后是生命周期。按时间分区加归档往往比分片更省事：主表只保留活跃窗口的数据，过期分区整体搬到归档库、对象存储或分析型数据库。这条路径不引入跨片查询和分布式事务，恢复和验证都容易得多。很多「必须分库分表」的需求其实归档就能解决，值得在动手分片前认真评估一次。

不适用边界：本篇只讲数据模型层——数据归属、租户键与分片键的关系、隔离模型与越权防线。分片算法（取模、范围、一致性哈希、基因法）、全局 ID 生成、中间件选型、扩容迁移的状态流转与不停机切流在 分库分表；冗余列与快照列的维护义务在 范式与反范式：数据库设计的取舍；实体与关系怎么定在 业务建模：从需求到表结构；给已分片的表加列改类型的执行顺序在上一篇 模式演进与约束设计：表结构上线之后怎么改；单片内的索引与执行计划在 索引设计与优化；跨分片查询本身慢在 慢查询治理；异构索引表的最终一致靠本地消息表落地，幂等与补偿见 缓存一致性与失效里的同类推演；PostgreSQL 行级安全与连接池的交互细节在 PostgreSQL MVCC 与事务。

这条路径到这里结束：第一篇定「一份事实存几遍」，第二篇画清实体与关系，第三篇解决「上线之后怎么改」，本篇回答「数据长大之后归谁」。四篇里只有本篇的决定几乎无法用前一篇的流程纠正——分片键定错要重迁全表，所以它必须在第一天就定对。

最容易踩的坑

❌
前两条只能靠整表重新迁移来纠正
  • 从表按自己的主键散列，订单明细和状态日志与订单主表不在同一片，订单详情页变成 N 次全分片广播，且无法用本地事务，只能改整表迁移来纠正。
  • 从表忘了冗余父表的分片键列，写入时无法计算路由，临时用「先查再写」兜住，并发下写错分片，这些行之后永久查不到。
  • 指望一套分片同时服务买家和卖家两个维度，最后每个列表接口都变成全分片扫描加内存归并，延迟等于最慢的那个分片。
  • 异构索引表只存了两列 ID，商家后台要按金额排序时只能全量拉回应用内存排序，翻页结果还会随数据变动漂移。
  • 异构索引表的一致性只靠「写完主表接着写索引表」，进程崩在中间就永久少一行，没有对账任务时无人发现。
  • 把会持续增长的业务表设成广播表，几个月后每个分片都背着几百万行重复数据，任何变更都要 N 次写且容易部分失败。
  • 跨片关联改成应用层两次查询，但第二次是在循环里单条查，一页 20 行产生 20 次往返，延迟比原来的关联还高。
  • 共享表模型里租户标识取默认值 0 时被当作「不过滤」，一条内部接口把全部租户数据返回给了某个客户。
  • 业务条件没加括号，拼出 tenant_id = ? AND a = 1 OR b = 2，OR 优先级低于 AND，租户条件被整条绕过。
  • PostgreSQL 开了行级安全但没加 FORCE，而应用账号正是表的所有者，策略对它完全不生效。
  • 用 SET 而不是 SET LOCAL 设置当前租户，连接归还池后设置残留，下一个请求读到上一个租户的数据。
  • 每租户一个 schema 的方案里，一次 DDL 在 800 个 schema 中执行到第 300 个失败，此后各 schema 结构不一致，且没有记录能说清哪些成功了。
  • 按租户散列就以为解决了倾斜，结果占总量三成的大客户把它所在分片打满，而扩容分片数对倾斜毫无帮助。
  • 先上分片再发现真实需求只是「历史数据太多」，归档就能解决，白白引入了跨片查询和分布式事务的长期复杂度。
