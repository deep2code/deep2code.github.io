模式演进与约束设计：表结构上线之后怎么改

🏷️ 数据库设计

建表是一次性的，改表是无限次的。绝大多数关于数据库设计的资料都在讲怎么把表建好，却几乎不讲一个更常见也更危险的问题：表结构已经上线，上面跑着几十个服务实例和几亿行数据，现在要改，怎么改才不出事。这篇只讲改表，以及改表时那些能救命的约束设计。范式与冗余的取舍见站内《范式与反范式》篇。

为什么改表比建表难：灰度期的读写错配

所有改表事故的根都在同一处：发布不是原子的。滚动发布期间，旧版本实例和新版本实例同时在跑，同时连着同一个数据库。数据库只有一个结构，代码却有两个版本的期望。这个窗口通常是几分钟到几十分钟，如果是灰度放量，可能是几天。

sequenceDiagram participant OLD as 旧版本实例 灰度中 participant NEW as 新版本实例 participant DB as 数据库 NEW->>DB: INSERT 带上新列 status_v2 DB-->>NEW: 成功 OLD->>DB: INSERT 不带 status_v2 DB-->>OLD: 报错 该列 NOT NULL 且无默认值 Note over OLD,DB: 事故一 DDL 加了非空列却没给默认值
旧实例的全部写入直接失败 NEW->>DB: SELECT status_v2 DB-->>NEW: 历史行该列为空 Note over NEW,DB: 事故二 回填还没做完就切读
线上表现为大面积空值和默认值 OLD->>DB: UPDATE 只改旧列 status NEW->>DB: UPDATE 只改新列 status_v2 Note over OLD,NEW: 事故三 同时改了读和写
两个版本各写一半 数据永久分叉且无法判断谁对

把这三类事故抽象出来，就是一条纪律：任何一步变更都不能同时改读和写。违反它，就一定存在一个窗口，两个版本的代码对同一份数据持有互相矛盾的假设。而遵守它，每一步都能找到一个明确的回滚动作。

expand-migrate-contract：唯一安全的变更骨架

这个模式在不同资料里也叫「并行变更」或「扩张收缩」，本质是把一次不兼容变更切成若干次兼容变更：先只加不减（expand），再迁移数据和读路径（migrate），最后才删除旧结构（contract）。

三个细节决定它是否真的安全。第一，阶段一的新列必须可空或带默认值，否则旧实例的插入会直接失败。第二，阶段三的回填必须在双写已经生效之后开始，否则回填过程中产生的新数据不会进入新结构，回填完还是不全。第三，阶段四和阶段五之间要留足观察期，这段时间新结构承担读，旧结构仍在写，是唯一能安全发现问题并回退的窗口。

常见变更的兼容性判定

这张表是评审时最常用的速查。关键区分两件事：是否兼容旧代码决定它能不能单独一步上线，是否锁表重写决定它能不能在业务高峰直接执行。

变更 兼容旧代码 是否重写整表 MySQL 与 PostgreSQL 差异
加可空列 兼容 否 MySQL 8.0.12 起可 INSTANT，但要求加在末尾且累计次数有上限；PG 一直是元数据操作
加带默认值的列 兼容 看版本 PG 11 之前会重写整表，11 起默认值存进目录不再重写；MySQL 8.0 INSTANT 可用，5.7 会重建
加索引 兼容 否，但要扫全表建树 MySQL 8.0 用 INPLACE 且不阻塞读写；PG 必须显式 CREATE INDEX CONCURRENTLY，否则阻塞写，且并发建索引不能放在事务里，失败会留下无效索引需手工清理
改列类型（扩长度，如 VARCHAR 64 到 128） 通常兼容 看情况 MySQL 在字符集与长度字节数不跨界时可 INPLACE，跨界要 COPY；PG 同字符集下扩长度是元数据操作
改列类型（缩长度或换类型） 不兼容 是 两边都要重写并校验数据，必须走加新列再迁移的路径，不要原地改
改列名 不兼容 否 MySQL 8.0 RENAME COLUMN 与 PG 的 RENAME COLUMN 都只改元数据，速度不是问题，问题是旧代码立刻报错，必须拆两步
删列 不兼容且不可回滚 MySQL 通常重建 PG 的 DROP COLUMN 只标记不可见，空间靠后续整理回收；MySQL 多数情况要重建表，大表需借助在线改表工具
加 NOT NULL 不兼容 需全表校验 PG 会持有排他锁全表扫描，推荐先加 CHECK 约束并标记为未验证，再 VALIDATE，最后借已验证约束快速设置非空；MySQL 需保证现有行无空值否则报错
加唯一约束 不兼容 需全表去重校验 两边都会因存量重复数据直接失败，必须先跑一遍重复扫描；PG 可用并发建唯一索引再 ADD CONSTRAINT USING INDEX 减少锁时间
加外键 兼容但有副作用 需校验存量 两边都会校验现有数据并在父表加锁；分库分表场景下跨库外键无法成立，一律不要加
⚠️
被忽略的共性风险：元数据锁排队

「这个 DDL 是 INSTANT 的，秒级完成，可以直接上」这句话只说了一半。所有 DDL 都要先拿到表级元数据锁。如果表上存在一个还没结束的长事务或长查询，DDL 会一直等在那里，而后续所有对这张表的普通查询会排在这个 DDL 之后，表现为整张表在几秒内彻底不可用，连接池瞬间打满。执行任何 DDL 之前先查一遍长事务，并给 DDL 会话设置较短的锁等待超时，拿不到锁就立刻放弃重试，而不是死等。大表在线改表的具体工具与参数，站内《索引优化》篇的索引治理部分已有展开。

改列名与删列：必须拆成两个发布周期

这两个操作在数据库层面都极快（只动元数据），所以特别容易被低估。它们的风险完全来自应用侧：灰度期间还在运行的旧实例会因为找不到列而整条 SQL 失败，不是降级，是报错。

关于改列名，还有一个更稳的选择：不改。列名只是标识符，在应用层做一次映射的成本远低于一次跨发布周期的协调。真要改，等价于「加新列、双写、回填、切读、停旧写、删旧列」六步，也就是上一节的完整流程。SELECT * 在这里是隐藏地雷——它让「哪些代码用了这一列」这个问题无法被静态回答，也让删列的影响面无法评估。

唯一约束的三个设计陷阱

唯一约束是少数能让数据库替应用兜住 bug 的机制，但它的语义细节常被误解，而误解的代价通常要等到上线后才显现。

场景 常见的错误写法 会发生什么 正确做法
软删除后重建同一编码 UNIQUE (code) 删掉的行还占着唯一键，同一个 code 永远无法重建 MySQL 用 UNIQUE (code, deleted_at) 且 deleted_at 存时间戳；PG 用只对存活行生效的部分唯一索引
软删除用布尔标记 UNIQUE (code, is_deleted) 第一次删除没问题，同一个 code 第二次被删时与第一条已删行撞键 把布尔换成删除时间戳，未删为 0，每次删除产生不同组合
多租户下的业务编码 UNIQUE (code) 第一个租户用掉 A001，其他所有租户都无法使用该编码，表现为「别人建过我就建不了」 UNIQUE (tenant_id, code)，租户维度必须是唯一键的第一列
希望「可以为空但填了就唯一」 以为可空列上的唯一索引会拦住多行空值 MySQL 与 PG 默认都允许唯一索引中出现多个空值，于是空值行可以无限插入，很多人误以为这条约束坏了 这正是标准语义。若确实要求空值也唯一，PG 15 起可用 NULLS NOT DISTINCT，其余情况把列改成非空并用哨兵值
给存量表加唯一约束 直接执行 ADD UNIQUE 存量已有重复数据，DDL 直接失败并回滚，白等一场 先跑重复扫描并清理，再在低峰执行；PG 先并发建唯一索引再转成约束

CHECK、枚举与默认值

数据库约束的价值不在于替代应用校验，而在于兜住应用的 bug 和绕过应用的直连写入。代价是改约束要走 DDL，所以约束应该只覆盖那些「几年都不会变」的规则。

枚举实现 加一个取值 删一个取值 存储与校验 建议
数据库 ENUM 类型 要执行 DDL 改列定义 几乎不可能，历史数据会失去合法取值 底层存序号，调整定义顺序会让历史数据含义漂移 不推荐，尤其不要在会演进的业务状态上用
VARCHAR 存字符串 改代码即可 改代码即可 无任何校验，会出现大小写与拼写不一致，占空间 仅在取值由外部系统定义且不可枚举时使用
TINYINT 加列注释加 CHECK 改代码，必要时改 CHECK 改代码，历史值仍合法 1 字节，CHECK 兜住越界写入 推荐默认方案，语义放在应用枚举里
外键指向字典表 插一行数据即可，无需 DDL 删字典行会被外键拦住 取值可配置、可带描述，但每次写入多一次检查 取值需要运营可配、或需要附带描述和排序时用 
-- 状态列推荐写法：小整数 + 注释 + CHECK 兜底
ALTER TABLE orders
  ADD COLUMN status TINYINT NOT NULL DEFAULT 0
      COMMENT '0待支付 1已支付 2已发货 3已完成 4已取消，新增取值只递增不复用',
  ADD CONSTRAINT ck_orders_status CHECK (status BETWEEN 0 AND 4);

-- 重要版本差异：MySQL 8.0.16 之前会解析 CHECK 但直接忽略，写了等于没写。
-- 验证方法（8.0.16 及以上才会返回行）：
SELECT CONSTRAINT_NAME, CHECK_CLAUSE
  FROM information_schema.CHECK_CONSTRAINTS
 WHERE CONSTRAINT_SCHEMA = DATABASE();

-- PostgreSQL 给大表加非空约束的低锁路径（不要直接 SET NOT NULL 扫全表）
ALTER TABLE orders ADD CONSTRAINT ck_orders_uid_nn
  CHECK (user_id IS NOT NULL) NOT VALID;      -- 只对新写入生效，秒级
ALTER TABLE orders VALIDATE CONSTRAINT ck_orders_uid_nn;  -- 只加共享锁，可被中断重试
ALTER TABLE orders ALTER COLUMN user_id SET NOT NULL;     -- PG 12 起可复用已验证约束，免全表扫描
ALTER TABLE orders DROP CONSTRAINT ck_orders_uid_nn;
默认值陷阱 具体表现 怎么避免
应用默认与数据库默认不一致 同一条业务数据，走接口创建时状态是 1，走批量导入脚本创建时状态是 0，行为随插入路径而变，排查时完全想不到 默认值只在一处定义。推荐让应用显式传全部列值，数据库默认仅作为兜底，且两者取值必须一致
误以为改默认值会回填历史行 执行 ALTER COLUMN SET DEFAULT 之后发现历史行的值没变，以为语句没生效 SET DEFAULT 只影响此后不指定该列的插入。历史行要单独写回填脚本。注意区分：新增一列并带默认值时，历史行会取到该默认值
用当前时间做默认值做业务判断 批量导入的历史数据 created_at 全部是导入时刻，按创建时间做的统计和分区全部错位 业务时间与记录时间分成两列，导入路径必须显式传入业务时间
可空列加默认值却不回填 新列上存在空值和默认值两种状态，下游判空逻辑要同时处理两种，漏一种就出错 回填完成后再把列改成非空，把两种状态收敛成一种

数据迁移脚本的工程要求

回填脚本的失败率比 DDL 高得多，因为它运行时间长、要处理存量脏数据、还会和线上写入竞争。一个能进生产的迁移脚本必须同时满足下面五条，缺一条就会在凌晨三点把人叫起来。

要求 具体做法 缺失后的表现
幂等 更新语句自带「尚未迁移」条件，重复执行不改变结果 重跑一次把已经正确的数据改坏，且无法判断改了多少行
可中断续跑 按主键顺序推进并持久化游标，重启从游标继续 跑了六小时在 90% 处失败，只能从头再来
分批提交 每批固定行数并在批间休眠，控制单事务大小 一个几亿行的大事务撑爆回滚段、拉长主从延迟、长时间持锁
有进度与限速 每批输出已处理行数与剩余估算，按主从延迟动态降速 无法判断还要多久，也无法在延迟报警时自动退让
先在影子库演练 用生产数据的近期快照跑一遍完整流程，记录耗时与差异行数 生产是第一次运行，脏数据和耗时都在意料之外 
import time
import pymysql

BATCH = 2000            # 单批行数：太小则总耗时长，太大则事务长、主从延迟高
SLEEP = 0.05            # 批间休眠：给线上写入留出窗口
DELAY_LIMIT = 5         # 主从延迟秒数上限，超过就自动降速

conn = pymysql.connect(host="127.0.0.1", user="migrator", password="***",
                       database="shop", autocommit=False)

# 旧状态到新状态的映射表。写成纯数据而不是 if 分支，
# 这样「哪些旧值没有对应新值」可以在跑之前就校验出来。
STATUS_MAP = {0: 10, 1: 20, 2: 30, 3: 40, 4: 90}

def map_status(old):
    if old not in STATUS_MAP:
        raise ValueError(f"未登记的旧状态值 {old}，先补映射再跑，不要静默跳过")
    return STATUS_MAP[old]

def replica_delay(cur):
    """读取从库延迟。生产环境应改为读监控接口，这里示意直连从库。"""
    cur.execute("SHOW SLAVE STATUS")
    row = cur.fetchone()
    return 0 if row is None else (row[32] or 0)

def load_cursor(cur):
    """游标持久化在库里，进程被杀也能续跑；表需提前建好。"""
    cur.execute("SELECT last_id FROM migrate_progress WHERE job = %s", ("order_fill_v2",))
    row = cur.fetchone()
    return row[0] if row else 0

with conn.cursor() as cur:
    last_id = load_cursor(cur)
    total = 0
    while True:
        # 1) 只取「尚未迁移」的行，这一条同时保证了幂等：重复执行不会二次改写
        cur.execute(
            "SELECT id, status FROM orders "
            "WHERE id > %s AND status_v2 IS NULL "
            "ORDER BY id LIMIT %s", (last_id, BATCH))
        rows = cur.fetchall()
        if not rows:
            break

        # 2) 按主键更新，避免范围条件二次扫描；条件里再带一次 IS NULL 防并发重复写
        cur.executemany(
            "UPDATE orders SET status_v2 = %s WHERE id = %s AND status_v2 IS NULL",
            [(map_status(s), i) for i, s in rows])

        last_id = rows[-1][0]
        cur.execute(
            "INSERT INTO migrate_progress (job, last_id) VALUES (%s, %s) "
            "ON DUPLICATE KEY UPDATE last_id = VALUES(last_id)",
            ("order_fill_v2", last_id))

        # 3) 游标和数据在同一个事务里提交，保证「已提交的进度」永远不超前于数据
        conn.commit()
        total += len(rows)
        print(f"done={total} last_id={last_id}", flush=True)

        # 4) 按主从延迟自适应退让，而不是固定休眠
        d = replica_delay(cur)
        time.sleep(SLEEP if d < DELAY_LIMIT else min(30, d))

变更流程与版本化管理

把上面所有内容压缩成一条可执行的纪律：永远先发兼容的 DDL，再发代码，最后清理。顺序反了，灰度期必然出事故；顺序对了，每一步都可以单独回滚。

DDL 评审要点 不通过的表现
变更是否兼容旧代码，能否单独上线 一个脚本里同时有加列和删列
新列是否可空或带默认值 非空且无默认值，会让灰度期旧实例写入全失败
是否评估过表行数、预计耗时与锁模式 只有 SQL，没有行数和耗时估算
回填脚本是否幂等、分批、可续跑 一条不带 LIMIT 的全表 UPDATE
回滚方案是什么 写着「回滚执行反向 DDL」，但反向 DDL 会丢数据
是否在所有分片和所有从库确认执行结果 只在主库执行，分片数据库漏掉一两个
下游是否有直读该表的报表或同步任务 没有排查，删列后下游同步任务集体失败
工具 模型 回滚支持 漂移检测 适合谁
Flyway 命令式，顺序编号的 SQL 文件依次执行 社区版无自动回滚，靠补偿脚本 校验已执行脚本的指纹，脚本被改动会报错 绝大多数团队的默认选择，心智负担最低
Liquibase 命令式，用变更集描述，支持多种方言输出 变更集可声明回滚语句 有执行记录表与校验和 需要同时支持多种数据库的产品型团队
Atlas 声明式，比较期望结构与当前结构并生成计划 生成的计划可预览，破坏性操作可拦截 原生支持结构差异对比，能直接发现手工改动 已经习惯基础设施即代码、希望结构可审计的团队
手工执行 SQL 无模型 无 无 没有人。它一定会漂移，这是时间问题不是概率问题

手工执行必然漂移的原因很具体：变更由人挑时机、挑环境执行，就一定会出现某个环境漏执行、某个分片执行两遍、某次执行的内容和仓库里的脚本对不上这三类情况，而且事后没有任何记录能证明「当前库的结构」等于「哪个版本代码期望的结构」。版本化工具的核心价值不是省事，是把执行记录落在数据库里并校验脚本指纹，让环境之间的差异能被发现。

新手最容易踩的坑

❌
避坑指南
  • 先发代码再发 DDL，灰度期新实例查询一个还不存在的列，接口整条链路报错，且回滚代码才能止血。
  • 新列直接建成 NOT NULL 且不给默认值，旧实例的所有插入立刻失败，这是最常见的一类分钟级故障。
  • 一个变更脚本里同时加新列和删旧列，等于把 expand 和 contract 合并，回滚时无论往哪个方向都会丢数据。
  • 回填先于双写开始，回填期间新产生的数据没有进入新结构，跑完校验才发现还差几十万行。
  • 代码里用 SELECT *，删列之后 ORM 映射对不上直接抛异常，而且事前根本无法静态评估影响面。
  • 用 UNIQUE (code, is_deleted) 解决软删除冲突，同一个 code 第二次删除时撞键，问题只在特定操作序列下复现。
  • 多租户表只对 code 建唯一索引，第二个租户建不了同名编码，投诉内容是「系统说编码已存在但我列表里没有」。
  • 在 MySQL 8.0.16 以下写了 CHECK 约束，以为数据库在校验，实际被静默忽略，脏数据照样写进去。
  • PostgreSQL 直接 CREATE INDEX 而不加 CONCURRENTLY，整张表写入被阻塞到索引建完；或者用了 CONCURRENTLY 但失败后没清理遗留的无效索引，之后的重试一直报名称冲突。
  • 执行 DDL 时表上有长事务，DDL 等元数据锁，后续查询全部排在它后面，表现为整张表瞬间不可用、连接池打满。
  • 回填脚本写成一条不带 LIMIT 的全表 UPDATE，主从延迟飙到几十分钟，读写分离的业务全线读到旧数据。
  • 分库分表环境只在部分分片执行了 DDL，路由到漏执行分片的请求报未知列，错误分布看起来毫无规律。
  • 执行 ALTER COLUMN SET DEFAULT 后以为历史行也被改了，报表口径因此算错一整个月。
