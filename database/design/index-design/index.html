数据库设计范式：从混乱到规范

🏷️ 数据库设计

做项目时数据库表越建越多，查询越来越慢，数据还经常重复。其实就是没按范式设计。这篇讲 1NF/2NF/3NF，什么时候该遵守，什么时候该反范式。

flowchart LR A[数据混乱] --> B[1NF 原子性] B --> C[2NF 消除部分依赖] C --> D[3NF 消除传递依赖] D --> E[反范式优化]

表设计太乱，数据重复

⚠️
你遇到的问题

一个用户表既存用户信息又存订单，改个用户名要改好几处。

怎么解决？拆成用户表和订单表，用 user_id 关联，改一处就行。

-- 用户表
CREATE TABLE users (
  id INT PRIMARY KEY,
  name VARCHAR(50),
  email VARCHAR(100)
);

-- 订单表
CREATE TABLE orders (
  id INT PRIMARY KEY,
  user_id INT,
  amount DECIMAL(10,2),
  FOREIGN KEY (user_id) REFERENCES users(id)
);

查询太慢，关联太多

⚠️
你遇到的问题

表拆太细了，查个订单列表要 JOIN 5 张表，慢得要死。

怎么解决？这时候就该反范式了，把常用字段冗余过来，用空间换时间。

-- 反范式：订单表冗余用户名
ALTER TABLE orders ADD COLUMN user_name VARCHAR(50);
-- 写入时同步更新，查询时不用 JOIN

三大范式对比

范式 要求 解决什么问题 例子
1NF 字段原子性，不可再分 一个字段存多个值 phone 拆成 phone1, phone2
2NF 消除部分依赖 联合主键下部分字段只依赖其中一个 订单表拆出订单明细表
3NF 消除传递依赖 A依赖B，B依赖C，C不应该在A里 用户表不该存部门名称

新手最容易踩的坑

❌
避坑指南
  • 不是所有场景都要严格 3NF，查询频繁的表可以适当反范式
  • 加冗余字段记得加注释，说明是冗余的，需要同步更新
  • 外键约束在大数据量下会拖慢写入，高并发场景可以不用外键，应用层保证
  • 设计表的时候先想清楚查询场景，再决定要不要拆那么细
