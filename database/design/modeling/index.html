业务建模：从需求到表结构

🏷️ 数据库建模

建模的难点从来不是「用户、订单、商品」这种一眼就能看出的实体，而是四类反复出现却很难处理的模式：继承与多态、树形结构、状态与流程、版本与历史。这四类没想清楚，表结构会在半年内变形。这篇按「从需求到表结构」的顺序走一遍，重点放在这四类上。范式与冗余的取舍见站内《范式与反范式》篇，索引设计见站内《索引优化》篇。

建模四步与每步的提问清单

建模是可流程化的工作，四步走完就能得到一版可评审的结构。关键是每一步都有明确要回答的问题，答不上来就不要往下走。

步骤要回答的问题产出物没做好的症状
识别实体它有独立生命周期吗？能被单独查询、单独授权吗？删掉它会不会让别的东西失去意义？实体清单，每个一句话定义把「收货地址」当成用户的属性，后来要支持多地址只能加 addr1 到 addr3
确定关系与基数一个 A 对几个 B？反过来呢？关系会随时间变化吗？历史关系要不要留？带基数标注的 ER 图把「用户与部门」当一对多，后来要支持兼岗，没有关联表只能改成逗号串
归属属性这个属性由谁唯一决定？它是事实、快照，还是可重建的派生值？每张表的列清单与列注释部门名存在用户表里，部门改名后所有历史用户显示旧名
处理特殊关系有没有继承、树形、状态流转、历史版本这四类？针对每类的方案选型记录用一个 type 字段硬撑多态，三个月后表里一半列是空的

三种基本关系的落地

基本关系本身不难，容易错的是边界判断：一对一到底拆不拆、多对多的属性放哪。

关系落地方式什么时候该拆 / 该合典型错误
一对一共享主键的两张表，或从表持有唯一外键拆的三个信号：有大字段、需要权限隔离、属性稀疏。反之总是一起读写且字段都小就合并为了「看起来规范」把用户和用户设置拆开，结果每次登录都要多查一次
一对多外键放在「多」的那一边永远是多的一边持有外键；需要限制数量（如最多 10 个地址）要在应用层或用约束表达在「一」的一边放逗号串存多个子项 ID，从此无法按子项反查
多对多独立的关联表，两侧外键加联合唯一关联表一旦有了自己的属性，就给它一个业务名字并升格为实体关联表没有联合唯一约束，重复点击产生多条重复关联，计数全错
💡
多对多的属性放在哪里

放在关联表上，并且这恰恰说明关联表本身就是一个实体。选课的成绩、加购的数量、授权的生效时间，都不属于任何一边，而属于「这一次关联」这个事实。判断方法是问一句：只知道左边实体或只知道右边实体，能确定这个属性吗？不能，它就属于关联。一旦确认，就把 student_course 改名成 enrollment，给它独立主键和时间列，别再把它当技术性的中间表对待。

难点一：继承与多态

需求里出现「三种支付方式」「四类通知」「个人账户和企业账户」时，就进入了继承建模。三种实现各有明确的适用边界，选错的代价随子类数量增长。

维度单表继承具体表继承类表继承
查单个子类一次查询带 type 条件，最简单一次查询，最快公共表与子表关联一次
查全部（如支付流水列表）一次查询，天然支持分页排序要 UNION ALL 所有子表，分页与排序代价高，加子类要改 SQL查公共表即可，分页排序不受影响
空间浪费高，子类专属列在其他类型行上全为空无低
约束能力弱，子类必填列无法设成 NOT NULL强，每张表都能表达自己的约束强，子表可以表达各自约束
加一个新子类加列，会影响所有已有行建新表，还要改所有 UNION 查询只建一张扩展表，公共表不动
适用场景子类少于 3 个、专属列合计不超过 5 个子类之间几乎不需要统一查询，如完全独立的业务线子类多、需要统一列表和分页，默认推荐
-- 类表继承：公共表承担统一列表、分页、排序与外键引用
CREATE TABLE payment (
  id          BIGINT PRIMARY KEY,
  order_id    BIGINT       NOT NULL,
  channel     TINYINT      NOT NULL COMMENT '1支付宝 2微信 3银行卡，决定去哪张扩展表',
  amount      DECIMAL(14,2) NOT NULL,
  status      TINYINT      NOT NULL DEFAULT 0,
  paid_at     DATETIME(3)  NULL,
  created_at  DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  KEY idx_order (order_id),
  KEY idx_created (created_at, id)   -- 统一流水列表按时间翻页，不受子类影响
);

-- 扩展表与公共表共享主键：既是主键又是外键，天然保证一对一
CREATE TABLE payment_card_ext (
  payment_id  BIGINT PRIMARY KEY,
  card_no_mask VARCHAR(32) NOT NULL,          -- 子类必填列可以真的设成 NOT NULL
  bank_code   VARCHAR(16)  NOT NULL,
  auth_code   VARCHAR(64)  NOT NULL
);

-- 查询流水列表：完全不需要知道有哪些子类，加新渠道时这条 SQL 不用改
SELECT id, order_id, channel, amount, status, created_at
  FROM payment
 WHERE created_at >= ? AND created_at < ?
 ORDER BY created_at DESC, id DESC
 LIMIT 20;

难点二：树形结构

分类树、组织架构、评论回复、地区层级，都是树。四种方案的差异集中在「查子孙」和「移动子树」这两个操作上，先确定哪个更频繁再选。

方案查全部子孙查全部祖先插入新节点移动子树额外空间
邻接表
每行存 parent_id		难，需递归；PG 与 MySQL 8.0 的递归 CTE 使它完全可用同样需递归一行插入，最便宜改一个字段，最便宜无
路径枚举
存 1/4/17 这样的路径串		容易，前缀匹配一次索引范围扫描容易，在应用层切分路径串即可一行插入，需拼父路径要重写整棵子树的路径串小，一个字符串列
嵌套集合
存左右值区间		很快，一次范围扫描很快，一次范围扫描贵，要更新大量行的左右值非常贵两个整数列
闭包表
另一张表存所有祖先后代对		最快，等值索引一次命中最快，等值索引一次命中要插入「祖先数加一」行删除并重建子树相关的全部关系行大，约为节点数乘平均深度
✅
默认从邻接表起步

网上大量文章把邻接表说成「不可用，必须上嵌套集合」，这个结论已经过时了。PostgreSQL 和 MySQL 8.0 都支持递归 CTE，一条语句就能拿到整棵子树，对几万节点、深度十几层的树完全够用，而且插入和移动都是最便宜的。真正需要换方案的信号只有两个：树大到递归查询进不了几十毫秒，或者「查任意节点的全部子孙」是核心高频接口。这时优先选闭包表，用空间换查询；嵌套集合只适合基本不写的只读目录树。

-- 方案一：邻接表 + 递归 CTE（PostgreSQL 与 MySQL 8.0 通用写法）
WITH RECURSIVE sub AS (
    SELECT id, parent_id, name, 1 AS depth
      FROM category WHERE id = 17          -- 起点节点
    UNION ALL
    SELECT c.id, c.parent_id, c.name, s.depth + 1
      FROM category c JOIN sub s ON c.parent_id = s.id
     WHERE s.depth < 20                    -- 必加深度上限，防止脏数据成环导致无限递归
)
SELECT * FROM sub ORDER BY depth, id;

-- 方案二：闭包表。ancestor 等于 descendant 的自反行必须存，否则「含自身的子树」要特殊处理
CREATE TABLE category_closure (
  ancestor   BIGINT NOT NULL,
  descendant BIGINT NOT NULL,
  distance   INT    NOT NULL COMMENT '0 表示自身，1 表示直接子节点',
  PRIMARY KEY (ancestor, descendant),
  KEY idx_desc (descendant, distance)      -- 反向查祖先链用这条
);

-- 查 17 的全部子孙：一次等值索引扫描，无递归
SELECT c.* FROM category_closure cl
  JOIN category c ON c.id = cl.descendant
 WHERE cl.ancestor = 17 AND cl.distance > 0;

-- 挂载新节点 88 到父节点 17 之下：复制父节点的祖先链并距离加一，再补自反行
INSERT INTO category_closure (ancestor, descendant, distance)
SELECT ancestor, 88, distance + 1 FROM category_closure WHERE descendant = 17
UNION ALL SELECT 88, 88, 0;

难点三：状态与流程

状态建模有一个被反复忽略的部分：状态字段只回答「现在是什么」，业务真正常问的是「什么时候变成这样的、谁改的、为什么」。所以状态字段和状态变更历史表必须成对出现。

stateDiagram-v2 state "0 待支付" as S0 state "1 已支付" as S1 state "2 已发货" as S2 state "3 已完成" as S3 state "4 已取消" as S4 state "5 退款中" as S5 state "6 已退款" as S6 [*] --> S0 S0 --> S1: 支付成功回调 S0 --> S4: 超时未付 或 用户取消 S1 --> S2: 商家发货 S1 --> S5: 发货前申请退款 S2 --> S3: 确认收货 或 自动确认 S2 --> S5: 售后申请 S5 --> S6: 退款到账 S5 --> S2: 退款被驳回 S3 --> [*] S4 --> [*] S6 --> [*] note right of S5 退款中是唯一可以回退的状态 它必须记录进入前的原状态 否则驳回时不知道该回到哪里 end note 
-- 状态变更历史表：把「状态机的每一次迁移」变成一行事实
CREATE TABLE order_status_log (
  id          BIGINT PRIMARY KEY,
  order_id    BIGINT      NOT NULL,
  from_status TINYINT     NOT NULL COMMENT '原状态，新建单用 -1 表示无前驱',
  to_status   TINYINT     NOT NULL,
  operator_id BIGINT      NOT NULL DEFAULT 0 COMMENT '0 表示系统自动流转',
  source      TINYINT     NOT NULL COMMENT '1用户端 2商家后台 3定时任务 4支付回调',
  reason      VARCHAR(128) NOT NULL DEFAULT '',
  created_at  DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  KEY idx_order_time (order_id, created_at),
  -- 同一笔订单的同一次迁移只允许发生一次，天然拦住重复回调与重复点击
  UNIQUE KEY uk_order_transition (order_id, from_status, to_status)
);

-- 状态流转必须用条件更新表达，不能先查再改，否则并发下会双写
UPDATE orders SET status = 2, shipped_at = NOW(3)
 WHERE id = ? AND status = 1;   -- 影响行数为 0 就说明状态已被别人改过，直接按幂等返回

-- 有了历史表才能回答的问题：各状态的平均停留时长
SELECT from_status, to_status,
       AVG(TIMESTAMPDIFF(SECOND, prev_at, created_at)) AS avg_seconds
  FROM (SELECT order_id, from_status, to_status, created_at,
               LAG(created_at) OVER (PARTITION BY order_id ORDER BY created_at) AS prev_at
          FROM order_status_log) t
 WHERE prev_at IS NOT NULL
 GROUP BY from_status, to_status;

难点四：版本、历史与时间维度（最常被忽略的建模需求）

这是四类难点里破坏力最大的一类，因为它在上线初期完全不会暴露问题。典型场景：订单明细只存了 sku_id，名称和价格靠关联商品表实时取。商家某天调价，所有历史订单的显示金额随之变化，对账差额、发票金额、客诉截图全部对不上。这是真实发生过的事故，而修复它意味着要从日志里反推每一笔历史订单当时的价格。

做法能回答什么问题存储成本实现复杂度适用场景
快照字段冗余
在业务行上落下当时的值		这笔交易当时的内容是什么低，只多几列最低，写入时赋值，此后永不回改交易凭证类：订单、发票、合同、结算单，默认选它
版本表
每次修改插入一条新版本行		任意时刻该对象长什么样，谁在什么时候改了哪些字段中，与修改频率成正比中，需处理「取某时刻的有效版本」查询与唯一约束商品价格、合同条款、审批模板等需要回看任意历史版本的对象
事件日志
只记录变更事件，状态由重放得出		全部历史与因果链，可重建任意时点状态高高，需要投影与快照机制审计要求极高的金融账务、需要时间旅行的领域
-- 订单明细上的快照列：这些值属于「交易凭证」，一经写入永不跟随商品表变化
CREATE TABLE order_item (
  id          BIGINT PRIMARY KEY,
  order_id    BIGINT       NOT NULL,
  sku_id      BIGINT       NOT NULL COMMENT '仅用于溯源与售后，不用于取名称和价格',
  sku_name    VARCHAR(128) NOT NULL COMMENT '快照：下单时商品名，禁止任何回填脚本修改',
  sku_spec    VARCHAR(255) NOT NULL DEFAULT '' COMMENT '快照：下单时规格描述',
  unit_price  DECIMAL(14,2) NOT NULL COMMENT '快照：下单时单价',
  qty         INT          NOT NULL,
  discount    DECIMAL(14,2) NOT NULL DEFAULT 0 COMMENT '快照：本行分摊的优惠金额',
  KEY idx_order (order_id)
);

-- 商品价格版本表：用有效期区间表达「某个时刻的价格是多少」
CREATE TABLE sku_price_version (
  id         BIGINT PRIMARY KEY,
  sku_id     BIGINT        NOT NULL,
  price      DECIMAL(14,2) NOT NULL,
  valid_from DATETIME(3)   NOT NULL,
  valid_to   DATETIME(3)   NOT NULL DEFAULT '9999-12-31 23:59:59.999'
             COMMENT '用哨兵值而不是 NULL，避免每个查询都要写 OR IS NULL',
  KEY idx_sku_from (sku_id, valid_from)
);

-- 取某一时刻的有效价格：区间左闭右开，避免边界时刻命中两行
SELECT price FROM sku_price_version
 WHERE sku_id = ? AND valid_from <= ? AND valid_to > ?;

有效期区间用 valid_from 与 valid_to 表示，关键纪律是统一成左闭右开，并且用 9999-12-31 这类哨兵值代替 NULL，否则每一条查询都要额外写一个空值判断，漏写就会查不到当前生效的那一行。PostgreSQL 还能把「区间不重叠」这条规则交给数据库强制。

-- PostgreSQL：用范围类型 + 排它约束，从数据库层面禁止同一 SKU 的价格区间重叠
CREATE EXTENSION IF NOT EXISTS btree_gist;   -- 排它约束里混用等值列需要它

CREATE TABLE sku_price (
  id       bigserial PRIMARY KEY,
  sku_id   bigint      NOT NULL,
  price    numeric(14,2) NOT NULL,
  valid    tstzrange   NOT NULL,             -- 用 '[)' 构造，天然左闭右开
  EXCLUDE USING gist (sku_id WITH =, valid WITH &&)  -- 同一 sku 区间重叠直接报错
);

INSERT INTO sku_price (sku_id, price, valid) VALUES
  (1001, 99.00, tstzrange('2026-01-01', '2026-06-01', '[)')),
  (1001, 89.00, tstzrange('2026-06-01', 'infinity',   '[)'));
-- 再插一条 2026-03-01 起的价格会被约束直接拒绝，而不是等到对账时才发现两个价格并存

-- 取某时刻有效价格：包含运算符可以走 gist 索引
SELECT price FROM sku_price
 WHERE sku_id = 1001 AND valid @> '2026-03-15'::timestamptz;

双时态是更进一步的需求：同时记录「业务上什么时候生效」和「系统什么时候知道这件事」。工资从 1 月 1 日起调整，但 HR 在 3 月 10 日才录入，那么「1 月的工资单为什么和现在算出来的不一样」只有双时态能解释——业务时间是 1 月，系统时间是 3 月。凡是涉及追溯调整、补录、对账复现的领域（薪酬、保险、税务、账务）都需要这两组时间列，只存一组的系统无法复现任何一次历史计算。PG 的时间类型选择与 timestamptz 的语义细节，见站内《PostgreSQL 数据类型》篇。

多值属性与 EAV 反模式

需求方说「这些属性以后可能随时增加」时，最容易掉进 EAV（属性名属性值表）这个坑。它看起来极其灵活，实际是把数据库最有价值的三件事全部放弃：

放弃了什么具体后果JSON 列方案如何解决
类型约束所有值挤在一个字符串列里，数字、日期、布尔都无法校验，脏数据只能等应用崩溃时发现核心属性建成真实列并带类型与 CHECK；扩展属性在 JSON 内部仍保留原生类型
查询能力按三个属性同时过滤要做三次自关联，执行计划迅速失控；排序与聚合几乎无法写一次表扫描内完成多键过滤，PG 可直接对 JSONB 做包含判断
有效索引属性值列的选择性极差，索引基本不起作用PG 用 GIN 索引支持键存在与包含查询；也可对高频键建表达式索引
可读性看一眼表数据完全不知道一个对象长什么样，新人无法上手核心列直接可读，扩展部分结构自描述
-- 正确姿势：核心属性建列（可约束、可索引、可排序），只有长尾扩展属性进 JSONB
CREATE TABLE product (
  id         bigserial PRIMARY KEY,
  shop_id    bigint      NOT NULL,
  name       varchar(128) NOT NULL,
  price      numeric(14,2) NOT NULL CHECK (price >= 0),
  status     smallint    NOT NULL DEFAULT 0,
  attrs      jsonb       NOT NULL DEFAULT '{}'::jsonb,   -- 只放无法枚举的长尾属性
  created_at timestamptz NOT NULL DEFAULT now()
);

-- GIN 索引支撑扩展属性上的包含查询
CREATE INDEX idx_product_attrs ON product USING gin (attrs);

-- 按扩展属性过滤：一次索引扫描，不需要任何自关联
SELECT id, name, price FROM product
 WHERE attrs @> '{"color": "黑色", "size": "XL"}'::jsonb AND status = 1;

-- 某个扩展属性变成高频筛选条件时，把它提升为真实列（走 expand-migrate-contract 流程）
ALTER TABLE product ADD COLUMN color varchar(32);
UPDATE product SET color = attrs >> 'color' WHERE color IS NULL AND attrs ? 'color';
CREATE INDEX idx_product_color ON product (shop_id, color) WHERE status = 1;

多值属性同理：tags = '手机,数码,5G' 这种逗号串违反 1NF，无法建索引、无法精确匹配、无法按标签统计。正确做法是关联表，或者在 PG 上用数组与 JSONB 数组配 GIN 索引。只有当属性集合完全由终端用户自定义、且需求本身就是「让用户自己建表」时，EAV 才有讨论价值，而这种需求通常应该先回到产品层面重新讨论。

建模反模式清单

反模式表现代价正确做法
一张大宽表装所有一张表上百列，大半是空的没人敢改，任何查询都要读一堆无关列，加字段要全表重建按实体和生命周期拆，一张表一句话说清它存什么事实
过度设计一个简单后台建出十几张关联表，每个枚举都有字典表查一条数据关联七八张表，新人无法上手，开发效率断崖下降取值稳定的枚举直接用小整数加注释，不要为对称性建表
逗号分隔存多值tags = '手机,数码'、role_ids = '1,3,7'无法索引、无法精确匹配、无法统计，模糊匹配还会误命中关联表；PG 上可用数组或 JSONB 数组配 GIN 索引
字段名用 f1 f2列名毫无语义，含义写在别处的文档里文档一定会过期，最终只能靠读代码反推列含义列名表达业务语义，含义写进列注释而不是外部文档
不同实体塞一张表靠 type 区分一张 record 表同时存订单、退款、结算约束无法表达，索引互相拖累，一个业务的写入压力影响所有业务确认它们是不是真的共享公共属性，是则用类表继承，否则彻底分开
预留字段ext1 到 ext5 一排占位列一定被多个业务混用成多种格式，无法加约束和索引，清理时无法归属需要扩展就用 JSON 列，高频筛选的键再提升为真实列
把派生值当事实存却不可重建订单总额只存结果，明细被后续改动，两者再也对不上对账出现无法解释的差额，且无法判断哪个是对的派生值要可从明细重算，并有定期校验；明细行一经生成不允许修改
用外键指向会变的数据当历史依据历史订单关联当前地址表、当前价格表用户改地址或商家调价后，历史凭证内容跟着变凭证类数据一律落快照，外键只留作溯源
❌
最容易踩的坑
  • 订单明细只存 sku_id，名称和价格实时关联商品表取，商家调价后所有历史订单金额显示变化，对账与发票全线对不上。
  • 订单关联地址表主键，用户修改默认地址后历史订单的收货信息跟着变，物流纠纷时无法举证。
  • 把「收货地址」当成用户表的属性，后来要支持多地址只能加 addr1 到 addr3，再后来要支持标签和默认标记彻底没地方放。
  • 多对多关联表没建联合唯一索引，用户连点两次产生两条相同关联，所有基于它的计数都翻倍。
  • 用单表继承硬撑六种支付渠道，表里一半列常年为空，而且每个子类的必填列都无法设成 NOT NULL，脏数据只能靠应用挡。
  • 邻接表的递归查询不加深度上限，某次脏数据让 parent_id 成环，一条 SQL 把数据库 CPU 打满。
  • 嵌套集合用在写频繁的组织架构上，每次调岗要更新上千行左右值，长事务导致主从延迟。
  • 闭包表忘记插入距离为 0 的自反行，「含自身的整棵子树」这类查询要写两段 SQL 拼起来，后续所有人都踩一遍。
  • 状态流转写成「先 SELECT 判断再 UPDATE」，并发下两个请求都通过判断，订单被重复发货；必须用带原状态条件的 UPDATE 并检查影响行数。
  • 只有 status 字段没有变更历史表，运营问「这单为什么昨天还是待发货今天变成已取消」时完全无法回答。
  • 有效期用 NULL 表示「永久有效」，之后每条查询都要额外写空值判断，漏写的地方查不到当前生效记录；改用哨兵日期即可。
  • 有效期区间左右都闭，边界那一刻同时命中两条记录，价格计算随机取其中一条。
  • 用 EAV 存商品扩展属性，三个属性组合筛选要三次自关联，列表页超时，最后只能整体迁到搜索引擎兜住。
  • 把「可能以后要用」的字段预留成 ext1 到 ext5，半年后三个业务混用同一列存了三种格式。
