IO

AI 导读一分钟导读，先掌握全文主干。▼

核心观点

  • Read 可返回 n < len(p) 且 err == nil，必须循环读或用 io.ReadFull
  • 返回 n > 0 时可能同时带错误，先处理 n 再判断 err
  • io.Copy 自带 32KB 缓冲并探测 ReaderFrom/WriterTo 走直拷路径

关键结论与取舍

  • 接口抽象：Reader/Writer/Seeker/Closer；便利函数覆盖开箱惯用场景
  • “能读多少读多少”是 Go IO 调用的根本心法，遇 Bug 先检查读循环
适合谁读写过 Go 但被 IO 边界坑过的开发者 读完可获得Reader/Writer 契约、类型体系与 2024—2026 新增 IO 便利函数的速查

Go IO 更新（2024-2026）

以下能力大多在 Go 1.16-1.21 落地，但 2024-2026 的工程实践普遍按这套写法组织 IO 代码，旧的 ioutil 写法已全面淘汰：

  • io/fs 自 Go 1.16 稳定，虚拟文件系统成为标准：同一套读取路径可同时作用于 os.DirFS、embed.FS 与测试用的 fstest.MapFS。
  • ioutil 已废弃，统一迁移：ioutil.ReadAll->io.ReadAll,ioutil.ReadFile->os.ReadFile,ioutil.TempFile->os.CreateTemp。
  • errors.Join(Go 1.20) 合并多个独立操作的错误，批量读取/批量校验场景很方便。
  • log/slog(Go 1.21) 结构化日志标准库，把日志流接到任意 io.Writer,测试时可直接断言写入的 buffer。

资深视角:io.Reader 的契约是"能读多少读多少"——返回 n < len(p) 且 err == nil 完全合法，必须循环读或用 io.ReadFull;反过来返回 n > 0 时也可能同时带错误，先处理 n 再判断 err 才对。io.Copy 内部自带 32KB 缓冲，还会探测 ReaderFrom/WriterTo 走直拷路径，搬数据优先交给它，别手写循环。
