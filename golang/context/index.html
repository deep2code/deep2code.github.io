Context

AI 导读一分钟导读，先掌握全文主干。▼

核心观点

  • context 是 Go 1.7 引入的控制 goroutine 生命周期、超时/取消与传递请求元数据的接口
  • 核心契约：上流广播“我要收工了”，下流通过 Done() 响应并主动退出
  • 写 HTTP 服务、调外部依赖、启后台任务时它是必传的第一参数

关键结论与取舍

  • Deadline 与 Done 配合实现超时；WithValue 只传请求级元数据，不做参数传递
  • 忘记取消会导致协程泄漏，这是线上疑难杂症的常见源头
适合谁读刚接触并发、或想治好协程泄漏的 Go 开发者 读完可获得context 接口全貌与“谁派生谁负责”的可落地检查清单

context.Context 是 Go 并发编程的地基：管理 goroutine 的生死、捎带请求级元数据、支撑超时与取消三件套，自 Go 1.7 起就是标准库常客。先一句话记住它的定位：谁派生，谁负责——调用方通过它向下游 goroutine 打信号："活儿干完了，收工"，下游盯着 Done() 一旦关闭就主动收尾退场。日常写 HTTP 接口、接外部依赖、起后台任务，谁都绕不开这个第一参数。

Context 接口定义

type Context interface {
    // Deadline 返回 context 的截止时间和是否设置了截止时间
    Deadline() (deadline time.Time, ok bool)

    // Done 返回一个 channel，当 context 被取消或超时时关闭
    Done() <-chan struct{}

    // Err 返回 context 被取消的原因
    Err() error

    // Value 返回 context 中关联的键值
    Value(key any) any
}

Context 接口拢共四个方法，实质是两条信号通道再加一个只读挂载位：Deadline()/Done()/Err() 扛的是生命周期管理，Value() 负责捎带请求元数据。不过 Done() 只是被动视角——取消这件事永远由父级发起，子级只能接收，没有反向取消父级的能力。

创建 Context

想建一棵新的 context 树，root 只有两种现成选项：

// 1. context.Background() - 通常用于 main 函数、初始化和测试
ctx := context.Background()

// 2. context.TODO() - 占位：结构上必须有 ctx 但还没决定来源
ctx := context.TODO()

Background() 是空 context：没有超时、不可取消，一切派生链的起点；TODO() 别误会成"高级版 Background"，它只是"还没想好"的占位态，上线之前务必换成真实来源。

派生 Context

从根上可以不断派生子 context，长成一棵树——取消信号顺着树往下传，但子节点捅不破父节点：

// 带超时的 context
ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
defer cancel()

// 带截止时间的 context
deadline := time.Now().Add(10 * time.Second)
ctx, cancel := context.WithDeadline(context.Background(), deadline)
defer cancel()

// 带取消信号的 context
ctx, cancel := context.WithCancel(context.Background())
defer cancel()

// 带键值对的 context
ctx := context.WithValue(context.Background(), "userID", 12345) // 仅为演示；生产代码 key 必须用自定义类型，见下方最佳实践

四个派生器里 WithTimeout 是出场率最高的；WithDeadline 适合"某时某刻之前必须交付"的硬约束（比如要对齐上游的绝对 deadline）；WithValue 只该装请求级元数据，具体取舍看下面的最佳实践。

典型使用场景

1. HTTP 请求超时控制
func handler(w http.ResponseWriter, r *http.Request) {
    ctx, cancel := context.WithTimeout(r.Context(), 3*time.Second)
    defer cancel()

    result, err := fetchFromDB(ctx, query)
    if err != nil {
        if ctx.Err() == context.DeadlineExceeded {
            http.Error(w, "Request timeout", http.StatusGatewayTimeout)
            return
        }
        http.Error(w, err.Error(), http.StatusInternalServerError)
        return
    }
    json.NewEncoder(w).Encode(result)
}

拿 r.Context() 当父链，客户端断连或者处理器超时，下游的 DB 查询跟着一起取消；收到报错先看 ctx.Err() 来判断是"超时了"还是"真的失败"，再定 504 还是 500。

2. Goroutine 取消传播
func worker(ctx context.Context, id int) {
    for {
        select {
        case <-ctx.Done():
            fmt.Printf("Worker %d stopped: %v\n", id, ctx.Err())
            return
        default:
            // 执行工作
            time.Sleep(500 * time.Millisecond)
        }
    }
}

func main() {
    ctx, cancel := context.WithCancel(context.Background())

    // 启动多个 worker
    for i := 1; i <= 3; i++ {
        go worker(ctx, i)
    }

    // 运行 2 秒后取消所有 worker
    time.Sleep(2 * time.Second)
    cancel()
    time.Sleep(500 * time.Millisecond) // 等待 worker 退出
}

这套机制叫协作式取消：cancel() 只做一件事：把 channel 关上；真正退出与否，看 worker 自己有没有读到 Done() 关闭的信号。一旦 worker 在 DB、RPC 这类阻塞调用上漏传 ctx，取消信号就卡在半路——goroutine 泄漏十有八九出在这里。

3. 请求链路追踪
type contextKey string

const (
    RequestIDKey contextKey = "requestID"
    UserIDKey    contextKey = "userID"
)

func middleware(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        requestID := generateID()
        ctx := context.WithValue(r.Context(), RequestIDKey, requestID)
        next.ServeHTTP(w, r.WithContext(ctx))
    })
}

func getFromContext(ctx context.Context, key contextKey) string {
    if v, ok := ctx.Value(key).(string); ok {
        return v
    }
    return ""
}

把 requestID、userID、traceID 这类链路信息塞进 ctx 一路传下去，日志中间件取出来统一打点——既不用全局变量，也不用手动逐层传参，漏传概率低得多。

最佳实践

  1. cancel() 永远别省：超时会自动触发，但资源还是要手动释放，记得 defer cancel() 就好。cancel 幂等、并发安全，多调几次也不碍事。
  2. 别把 context 塞进 struct：context 的归宿是函数参数列表的第一个位置：func DoSomething(ctx context.Context, ...)。
  3. nil context 是禁区：拿不准传什么就先用 context.TODO()。
  4. key 一定要自定义类型：为了不撞 key，定义 type contextKey string ，别拿 string 裸字面量硬上。
  5. Value 只装请求范围内的数据：函数参数不该走它，它只放 trace ID、认证信息这类东西，而且值要尽量是不可变的小对象。

Go 1.21+ 更新：取消传播的补全

Go 1.21 给标准库补了 context.WithoutCancel 和 context.AfterFunc 两员大将：

// WithoutCancel 返回一个不会因父 context 取消而取消的 context
// 适用于需要在请求取消后继续执行清理逻辑的场景
ctx := context.WithoutCancel(parentCtx)

// AfterFunc 在 context 取消后执行回调
stop := context.AfterFunc(ctx, func() {
    // 清理逻辑
    log.Println("Context cancelled, cleaning up...")
})
// 如果需要停止监听，调用 stop()
// stop()

Go 1.22 顺手优化了 context 的内存分配；在 HTTP 请求里，r.Context() 如今在客户端断开那一刻就自动取消。

Go 1.23 到 1.27，context 一路都是稳定期：1.23 那版主要是源码重构（AfterFunc 把收尾注册机制改了内部实现），之后再没加过 API，也没动过兼容性——代码只要兼容 1.21+，天然就兼容到 1.27。真要揪泄漏，配合 Go 1.26 的 goroutine leak profile（go tool pprof ），一眼就能看出哪些 goroutine 卡在 ctx.Done() 上不肯退出。

进阶：errgroup 与 context 组合

想要扇出一堆任务、又讲究"一个挂全员撤"，手写 select 加状态变量太容易翻车，直接上 golang.org/x/sync/errgroup 就对了：

g, ctx := errgroup.WithContext(r.Context()) // ctx 会被 Wait 的第一个错误自动取消

g.Go(func() error { return fetchA(ctx) })
g.Go(func() error { return fetchB(ctx) })
g.Go(func() error { return fetchC(ctx) })

// Wait 收集第一个非 nil 错误并取消其余任务
if err := g.Wait(); err != nil {
    http.Error(w, err.Error(), http.StatusInternalServerError)
    return
}

核心提醒：丢进 g.Go 的每个任务都得听 ctx.Done() 的话，否则"全量取消"就是句口号；errgroup.WithContext 产出的 ctx 只要察觉某个任务出错就自动取消，所有下游同步鸣金收兵。
