Context

Go context.Context 详解

context.Context 是 Go 用于控制 goroutine 生命周期、传递请求元数据和实现超时/取消机制的核心接口，自 Go 1.7 引入。一句话记住它的定位：谁派生谁负责——上层通过它向下游 goroutine 广播"我要收工了"，下游通过 Done() 响应并主动退出。写 HTTP 服务、调用外部依赖、启动后台任务时，它是必备的第一参数。

Context 接口定义

type Context interface {
    // Deadline 返回 context 的截止时间和是否设置了截止时间
    Deadline() (deadline time.Time, ok bool)

    // Done 返回一个 channel，当 context 被取消或超时时关闭
    Done() <-chan struct{}

    // Err 返回 context 被取消的原因
    Err() error

    // Value 返回 context 中关联的键值
    Value(key any) any
}

接口只有四个方法，本质是两条信号通道加一个只读挂载点：Deadline()/Done()/Err() 管生命周期，Value() 管请求元数据。注意 Done() 是只读视角——取消动作永远由父级触发，子级只能感知，不能反取消父级。

创建 Context

Go 提供了两种创建根 context 的方式：

// 1. context.Background() - 通常用于 main 函数、初始化和测试
ctx := context.Background()

// 2. context.TODO() - 占位：结构上必须有 ctx 但还没决定来源
ctx := context.TODO()

Background() 是没有超时、不可取消的空 context，是所有派生链的根；TODO() 不是"更好的 Background"，它只是"暂时不确定"的过渡态，上线前应替换成真实来源。

派生 Context

从根 context 可以派生出子 context，形成树状结构——取消沿树向下传播，子节点不会影响父节点：

// 带超时的 context
ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
defer cancel()

// 带截止时间的 context
deadline := time.Now().Add(10 * time.Second)
ctx, cancel := context.WithDeadline(context.Background(), deadline)
defer cancel()

// 带取消信号的 context
ctx, cancel := context.WithCancel(context.Background())
defer cancel()

// 带键值对的 context
ctx := context.WithValue(context.Background(), "userID", 12345)

四个派生函数里 WithTimeout 最常用；WithDeadline 适合"必须在某个时刻前完成"的外部约束（如对齐上游的绝对截止时间）；WithValue 只应携带请求级元数据，见下方最佳实践。

典型使用场景

1. HTTP 请求超时控制
func handler(w http.ResponseWriter, r *http.Request) {
    ctx, cancel := context.WithTimeout(r.Context(), 3*time.Second)
    defer cancel()

    result, err := fetchFromDB(ctx, query)
    if err != nil {
        if ctx.Err() == context.DeadlineExceeded {
            http.Error(w, "Request timeout", http.StatusGatewayTimeout)
            return
        }
        http.Error(w, err.Error(), http.StatusInternalServerError)
        return
    }
    json.NewEncoder(w).Encode(result)
}

以 r.Context() 为父派生，客户端断开或处理器超时时，下游 DB 查询同步取消——判断时先查 ctx.Err() 区分"超时"还是"业务失败"，再决定返回 504 还是 500。

2. Goroutine 取消传播
func worker(ctx context.Context, id int) {
    for {
        select {
        case <-ctx.Done():
            fmt.Printf("Worker %d stopped: %v\n", id, ctx.Err())
            return
        default:
            // 执行工作
            time.Sleep(500 * time.Millisecond)
        }
    }
}

func main() {
    ctx, cancel := context.WithCancel(context.Background())

    // 启动多个 worker
    for i := 1; i <= 3; i++ {
        go worker(ctx, i)
    }

    // 运行 2 秒后取消所有 worker
    time.Sleep(2 * time.Second)
    cancel()
    time.Sleep(500 * time.Millisecond) // 等待 worker 退出
}

这是协作式取消：cancel() 只负责关闭 channel，真正的退出由 worker 自己看到 Done() 关闭后执行。如果 worker 在阻塞调用（DB、RPC）上没把 ctx 传下去，取消信号会被一直卡住——这是 goroutine 泄漏的高发点。

3. 请求链路追踪
type contextKey string

const (
    RequestIDKey contextKey = "requestID"
    UserIDKey    contextKey = "userID"
)

func middleware(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        requestID := generateID()
        ctx := context.WithValue(r.Context(), RequestIDKey, requestID)
        next.ServeHTTP(w, r.WithContext(ctx))
    })
}

func getFromContext(ctx context.Context, key contextKey) string {
    if v, ok := ctx.Value(key).(string); ok {
        return v
    }
    return ""
}

链路追踪信息（requestID、userID、traceID）随 ctx 传递，日志中间件统一取出打印——比全局变量或显式传参更不易漏传。

最佳实践

  1. 总是调用 cancel()：即使 context 会超时，也要调用 cancel 函数来释放资源。使用 defer cancel()。cancel 幂等且并发安全，重复调用无害。
  2. 不要将 context 存储在 struct 中：context 应该作为函数的第一个参数传递：func DoSomething(ctx context.Context, ...)。
  3. 不要传递 nil context：如果不确定用什么，使用 context.TODO()。
  4. 使用自定义类型作为 key：避免键冲突，使用 type contextKey string，不要直接用 string 字面量。
  5. context.Value 只用于请求范围的数据：不要用它传递函数参数，它只适合传递 trace ID、认证信息等，且值应尽量是不可变的小对象。

Go 1.21+ 更新：取消传播的补全

Go 1.21 引入了 context.WithoutCancel 和 context.AfterFunc：

// WithoutCancel 返回一个不会因父 context 取消而取消的 context
// 适用于需要在请求取消后继续执行清理逻辑的场景
ctx := context.WithoutCancel(parentCtx)

// AfterFunc 在 context 取消后执行回调
stop := context.AfterFunc(ctx, func() {
    // 清理逻辑
    log.Println("Context cancelled, cleaning up...")
})
// 如果需要停止监听，调用 stop()
// stop()

Go 1.22 改进了 context 的性能，减少了内存分配；在 HTTP 请求中，r.Context() 现在会在客户端断开连接时自动取消。

Go 1.23 之后（含 1.23-1.27）context 包进入稳定期：1.23 主要做了源码级重构（AfterFunc 注册收尾机制内部化），此后没有新增 API、也没有破坏性变化——写兼容 1.21+ 的代码，就兼容到 1.27。排查泄漏时，配合 Go 1.26 新增的 goroutine leak profile（go tool pprof），能直接看到"卡在 ctx.Done()上没退出"的 goroutine 栈。

进阶：errgroup 与 context 组合

并发扇出多个任务、又要"任一失败即整体取消"时，手写 select + 变量同步容易出错，直接用 golang.org/x/sync/errgroup：

g, ctx := errgroup.WithContext(r.Context()) // ctx 会被 Wait 的第一个错误自动取消

g.Go(func() error { return fetchA(ctx) })
g.Go(func() error { return fetchB(ctx) })
g.Go(func() error { return fetchC(ctx) })

// Wait 收集第一个非 nil 错误并取消其余任务
if err := g.Wait(); err != nil {
    http.Error(w, err.Error(), http.StatusInternalServerError)
    return
}

要点：进 g.Go 的任务必须响应 ctx.Done()，否则"整体取消"只是空谈；errgroup.WithContext 返回的 ctx 一旦有任务出错就自动取消，下游全部收手。
