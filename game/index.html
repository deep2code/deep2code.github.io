游戏技术栈的分层：每一层的失败模式都不一样

游戏开发容易被当成「一个引擎的使用问题」，实际它是四层互不相同的工程：客户端引擎负责表现与手感，网络同步层决定多端之间看到的世界是否一致，服务端负责权威判定与持久化，工具链与资源管线决定团队每天的迭代速度。这四层的技能栈、故障形态、验收标准都不一样，出问题时先判断在哪一层，比急着改代码重要得多。

网络同步模型：先选模型，再选传输

这是整个项目最早、也最难改的一个决定。状态同步由服务端算好结果广播状态，客户端只负责表现；帧同步由服务端只转发操作指令，各端用同样的逻辑各算一遍。两者的差别不在「谁更快」，而在算力放在哪、带宽花在哪、以及作弊面在哪。中途更换等于重写战斗逻辑，所以要在立项阶段就定下来。

维度状态同步帧同步
谁做权威计算服务端算，客户端只表现各端各算一遍，服务端只转发指令并对齐帧
服务端成本高，要跑完整战斗逻辑低，本质是定时广播指令
带宽随单位数增长线性增长，单位越多状态包越大几乎不变，只与操作频率有关
对客户端的要求预测与回滚重放，逻辑与表现必须分离逻辑必须完全确定：定点数、固定随机序列、有序容器
作弊面小，关键判定在服务端；主要防透视类信息泄露大，本地内存可改，必须靠多端校验与录像比对
断线重连成本低，重新拉一次全量快照即可高，要从某个快照重放到当前帧
不一致时的表现玩家看到画面被纠正直接分叉，对局作废，且很难定位是哪一步开始差的
典型适用多数联网玩法，尤其带交易与养成的品类实时对战竞技、需要完整录像与回放的品类

传输层的选择是次要问题，但有一个常见误解要纠正：可靠 UDP 并不等于「更快的 TCP」。它之所以延迟更低，是因为把重传策略和拥塞控制换成了更激进的配置，代价是带宽浪费和对网络更不友好。非实时的业务消息用 TCP 或 WebSocket 就够，把可靠 UDP 留给真正需要低延迟的对战通道。

服务端形态：有状态长连接服务不是 Web 服务

后端工程师进入游戏项目时最大的认知落差在这里。普通 Web 服务把权威状态放在数据库，任意实例都能处理任意请求；游戏服务把权威状态放在进程内存，一个玩家或一张地图只由固定的进程处理，数据库退化成异步的持久化后端。这一个差别会连带改变路由、扩容、发布、容灾的全部做法。

维度无状态 Web 服务有状态游戏服务工程影响
权威状态数据库与缓存进程内存崩溃会丢最后一次落库之后的变更，必须显式定义丢失窗口
请求路由任意实例可处理必须投到持有该实体的进程要自建寻址层，负载均衡解决不了
并发控制事务与分布式锁单线程串行，逻辑内不加锁逻辑线程里任何阻塞调用都会让整个世界停摆
扩容加实例即分担存量流量加实例只能承接新的世界或分区热点地图的负载无法靠加机器摊薄，只能拆世界
发布滚动替换实例需要踢下线或等玩家退出状态重建能力是架构要求，不是运维技巧
落库同步写，事务保证标脏加定时批量，关键操作单独同步要按数据能否重新推导来分类，而不是一律实时写

防作弊：客户端不可信是前提，不是一个功能

防作弊的第一性原则只有一句：玩家机器上的一切都可以被修改，包括内存、本地文件、网络包和系统时间。所以它不是上线前加一个模块能解决的事，而是决定架构的前提——凡是影响结果和资产的判定都必须在服务端复算，客户端的计算只用来提前给出手感。

客户端上可被篡改的东西如果信了会发生什么服务端侧的做法
伤害、暴击、掉落结果秒杀 Boss、爆率拉满服务端复算，客户端只展示；随机种子由服务端下发
坐标与移动速度瞬移、穿墙、加速按上一次坐标与时间差做速度与可达性校验，超限拉回
系统时间绕过冷却、刷离线收益一切时间判定以服务端时间为准，客户端只做插值
请求频率与顺序脚本连点、并发重复领奖服务端限频，关键操作带幂等键，重复请求返回同一结果
下发给客户端的数据透视：地图上所有人的位置都在本地内存里按视野裁剪下发内容，不要把不该看到的数据发过去
安装包与热更包注入作弊逻辑并分发给其他玩家热更包校验摘要并签名，校验失败拒绝启动
⚠️
最常见的两个防作弊误区

第一，把客户端加固当成主要手段。加固能提高门槛，但对抗永远是此消彼长，真正兜底的只有服务端复算与数据裁剪。第二，把「服务端校验」做成事后风控。事后封号解决不了当时那一局的公平性，也退不回已经流入经济系统的道具，判定必须在操作生效之前就完成。
