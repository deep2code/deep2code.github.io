      • Compound query clauses，生产环境用得最多的组合容器：bool

        GET /_search
{
    "query": {
        "bool": {
            "must":     [{ "match": { "title": "golang" } }],
            "filter":   [{ "term": { "status": "published" } },
                         { "range": { "publish_date": { "gte": "2026-01-01" } } }],
            "must_not": [{ "term": { "author": "spam-bot" } }],
            "should":   [{ "term": { "tags": "grpc" } }]

    }
}

Elasticsearch 9.0 关键变化（2025-07）

Elasticsearch 9.0.0 于 2025 年 7 月发布，基于 Lucene 10.1，是 8.x 之后时隔三年的重大版本；8.x 系列以 8.19 收官，升级 9.x 可平滑迁移。截至 2026-08，当前稳定线为 9.5.x（9.5.2 @ 2026-08-20）。

  • rank_vectors 字段类型：late-interaction（交互式）向量检索，document embedding 与 query embedding 分离，精度更优。
  • semantic_text 字段类型 GA：内置推理模型自动生成嵌入，声明式语义搜索，告别手动 pipeline。
  • ES|QL 增强：新增 LOOKUP JOIN（技术预览），管道查询语言持续演进。
  • 安全加固：API key 存储改为 SSHA-256 散列（不再明文可读），keystore 加密升级 AES-256。
  • 非主节点支持：只读/负载均衡节点类型，适配大规模横向扩展。

数据文件存储与结构

Elasticsearch 底层基于 Lucene，每个分片是一个独立的 Lucene 索引。理解段文件和倒排索引结构是性能调优的关键。

分片目录结构

elasticsearch_data_dir/nodes/0/indices/{index_uuid}/0/
├── index/                          # Lucene 索引目录
│   ├── segments_1                  # 段提交点（记录所有活跃段）
│   ├── segments.gen                # 段生成号
│   ├── _0.cfe                      # 复合文件（封装多个小文件）
│   ├── _0.cfs                      # 复合文件数据
│   ├── _0.si                       # 段元信息
│   ├── _0.fdt                      # 存储字段数据（Stored Fields）
│   ├── _0.fdx                      # 存储字段索引
│   ├── _0.tim                      # 词项词典（Term Dictionary）
│   ├── _0.tip                      # 词项索引（Term Index，FST）
│   ├── _0.doc                      # 跳跃表（文档频率、位置）

倒排索引（Inverted Index）

倒排索引是搜索引擎的核心，将"词项 → 文档列表"建立映射。

文档集合：
  Doc1: "The quick brown fox"
  Doc2: "The lazy dog"
  Doc3: "A quick brown dog"

倒排索引（分词后）：
┌──────────┬─────────────┬──────────────────┐
│  Term    │  Doc Freq   │  Posting List    │
├──────────┼─────────────┼──────────────────┤
│  quick   │  2          │  [Doc1, Doc3]    │
│  brown   │  2          │  [Doc1, Doc3]    │
│  fox     │  1          │  [Doc1]          │
│  lazy    │  1          │  [Doc2]          │
│  dog     │  2          │  [Doc2, Doc3]    │
└──────────┴─────────────┴──────────────────┘

Posting List 还包含：
  - 词频（TF）：词在文档中出现的次数
  - 位置（Position）：词在文档中的位置（短语查询）
  - 偏移（Offset）：词的起始/结束字符位置（高亮）
  - 载荷（Payload）：自定义元数据

FST 词项词典（Finite State Transducer）

Lucene 使用 FST（有限状态转换器）压缩词项索引，将所有词项存储在一个极小的状态机中。

词项集合：mop, moth, pop, star, stop, top

FST 状态机（共享前缀和后缀）：
  (s) --m--> [1] --o--> [2] --p--> [3] (mop)
                          [2] --t--> [4] --h--> [5] (moth)
  (s) --p--> [6] --o--> [7] --p--> [3] (pop)  ← 共享后缀 "p"
  (s) --s--> [8] --t--> [9] --a--> [10] --r--> [11] (star)
                          [9] --o--> [12] --p--> [3] (stop) ← 共享
  (s) --t--> [13] --o--> [7] --p--> [3] (top)  ← 共享

优势：
  - 内存占用极小（通常几 MB 即可存储百万级词项）
  - O(1) 词项查找
  - 支持前缀查询、范围查询

Doc Values（列式存储）

Doc Values 是在索引时创建的列式存储结构，用于排序、聚合和脚本访问，避免从倒排索引中逐文档查找。

行式存储（Stored Fields .fdt）：
  Doc1: {name: "Alice", age: 30, city: "Beijing"}
  Doc2: {name: "Bob", age: 25, city: "Shanghai"}
  Doc3: {name: "Carol", age: 35, city: "Beijing"}

列式存储（Doc Values .dvd）：
  name:  [Alice, Bob, Carol]
  age:   [30, 25, 35]
  city:  [Beijing, Shanghai, Beijing]

聚合时只需读取 age 列，无需扫描所有文档的所有字段。
- 默认对非 analyzed 字段启用
- analyzed 字段需手动设置 fielddata=true（内存消耗大，不推荐）

BKD 树（Block K-D Tree）

BKD 树用于数值、日期和地理空间字段的索引，支持高效的范围查询。

BKD 树是 K-D 树的变体，将多维数据点组织成平衡树：

  根节点（分割维度 0，值 50）
  ├── 左子树（< 50）
  │   ├── 分割维度 1，值 30
  │   │   ├── 叶子块（4个点）
  │   │   └── 叶子块（4个点）
  │   └── ...
  └── 右子树（>= 50）
      └── ...

特点：
  - 每个叶子块存储 512-1024 个数据点
  - 支持 1-8 维数据（数值、经纬度等）
  - 范围查询 O(log N + 匹配点数)
  - 替代了旧的 Trie 树和 FieldCache

段合并机制

  • 不可变段：Lucene 段一旦写入就不可修改，删除是标记（.del 文件），更新是删除+新增
  • refresh：默认每秒将内存中的写入刷新为新段（近实时搜索）
  • flush：将段持久化到磁盘，清空 translog
  • force merge：手动触发段合并，将多个小段合并为一个大段（适合只读索引）
  • 合并策略：TieredMergePolicy，根据段大小分层合并

Lucene 底层架构与索引原理

Elasticsearch 的核心是 Apache Lucene，一个高性能的全文检索库。理解 Lucene 的索引结构和搜索流程，是优化 Elasticsearch 性能的基础。

Segment 与不可变段

Lucene 的索引由多个段（Segment）组成，每个段是一个独立的倒排索引：

  • 不可变性（Immutable）：段一旦写入就不再修改。删除操作不会真正删除文档，而是在 .del 文件中标记。更新操作 = 删除旧文档 + 写入新文档。不可变性带来的好处：不需要锁、可以被操作系统文件缓存高效缓存、并发安全
  • Refresh：文档写入后先在内存中，每隔 refresh_interval（默认 1s）刷新为一个新段，新段才可以被搜索。Refresh 是轻量级操作（生成段文件，不刷盘），但频繁 refresh 会产生大量小段
  • Flush：将内存中的段写入磁盘，同时清空 Translog。由事务日志大小（index.translog.flush_threshold_size=512mb）或时间触发。Flush 后数据持久化
  • 段合并（Segment Merge）：后台线程定期将小段合并为大段，减少段数量，同时物理删除已标记删除的文档。合并策略由 index.merge.policy 控制（默认 TieredMergePolicy）。合并是 IO 密集型操作，可能影响搜索性能

倒排索引深度解析

倒排索引（Inverted Index）是全文检索的核心数据结构，由两部分组成：

  • 词典（Term Dictionary）：所有文档中出现的词（Term）的有序列表。Lucene 使用 FST（Finite State Transducer，有限状态转换器）存储词典，将词映射到词的元数据（倒排表位置、词频等）。FST 是一种高度压缩的数据结构，前缀和后缀共享，可以在内存中存储整个词典
  • 倒排表（Posting List）：每个词对应的文档列表，包含文档 ID（DocID）、词频（TF，用于评分）、位置（Position，用于短语查询）、偏移量（Offset，用于高亮）。倒排表使用帧编码（Frame of Reference）压缩，DocID 用增量编码+位图压缩
  • 跳表（Skip List）：倒排表中的加速结构，用于多词查询时的交集计算。每隔 N 个文档建立一个跳跃点，跳过不可能匹配的部分

评分算法 BM25：Elasticsearch 默认的相关性评分算法，替代了旧的 TF-IDF。BM25 的公式考虑三个因素：

  • 词频（TF）：词在文档中出现的次数，但有饱和效应（出现 100 次不等于 100 倍重要），参数 k1（默认 1.2）控制饱和速度
  • 逆文档频率（IDF）：词在多少文档中出现，越罕见的词权重越高
  • 文档长度归一化：长文档中词的权重被降低（因为长文档更容易包含任意词），参数 b（默认 0.75）控制长度归一化的强度

分布式架构与读写流程

分片与副本机制

Elasticsearch 的分布式基于分片（Shard）：

  • 主分片（Primary Shard）：索引创建时指定数量（默认 1，7.0 前是 5），创建后不可修改（只能通过 Reindex 或 Split/Shrink 调整）。每个主分片是一个完整的 Lucene 索引
  • 副本分片（Replica Shard）：主分片的拷贝，可以随时修改数量。副本用于高可用（主分片故障时提升为主）和读性能（搜索可以在副本上执行）。副本数默认 1，生产环境建议至少 1
  • 分片分配：主节点（Master Node）负责将分片分配到数据节点，遵循：主分片和副本不在同一节点、尽量均匀分布、感知分配（cluster.routing.allocation.awareness，如机架感知）
  • 路由（Routing）：文档通过 shard = hash(routing) % number_of_primary_shards 计算所在分片。默认 routing 是文档 ID。自定义 routing（如按用户 ID）可以将相关数据放在同一分片，提高查询效率，但可能导致数据倾斜

写入与查询流程

写入流程（Index/Create/Update/Delete）：

  1. 客户端请求到达协调节点（Coordinating Node）（任何节点都可以是协调节点）
  2. 协调节点根据文档 ID（或 routing）计算目标分片，将请求转发到该分片的主分片所在节点
  3. 主分片节点执行写入：先写 Translog（事务日志，用于崩溃恢复），再写内存缓冲区（Indexing Buffer）
  4. 主分片写入成功后，并行转发到所有副本分片
  5. 所有副本确认后，主分片节点返回成功给协调节点，协调节点返回客户端
  6. 后台每隔 refresh_interval 将内存缓冲区刷新为新段（可搜索），每隔一段时间 Flush 到磁盘并清空 Translog

查询流程（Search）：分为两个阶段：

  • Query Phase（查询阶段）：协调节点将查询请求转发到所有相关分片（主或副本，负载均衡）。每个分片在本地执行查询，返回匹配文档的 ID 和评分（from+size 条）。协调节点收集所有分片的结果，合并排序，取全局的 from+size 条
  • Fetch Phase（获取阶段）：协调节点根据上一步的文档 ID，向对应分片请求完整文档（_source 或指定字段）。分片返回文档后，协调节点组装最终结果返回客户端

深分页问题：from=10000&size=10 需要每个分片返回 10010 条，协调节点合并排序后取 10 条，内存和 CPU 开销巨大。Elasticsearch 默认限制 index.max_result_window=10000。深分页用 search_after（基于上一页最后一条的排序值）或 scroll（已不推荐，用 PIT + search_after 替代）。

性能优化与资源管理

写入性能优化

  • 批量写入（Bulk API）：单条写入的开销主要在网络往返和刷新。Bulk 批量写入可以将吞吐量提升 10-100 倍。推荐批量大小 5-15MB（不是条数，是字节数），根据文档大小调整。用 _bulk API，动作类型：index（覆盖）、create（不存在才创建）、update（更新）、delete（删除）
  • 调整 Refresh Interval：默认 1s，对于写入密集型场景（如日志导入），可以临时设置为 -1（关闭自动刷新），导入完成后恢复。注意：关闭 refresh 期间写入的数据不可搜索
  • 减少副本：初始导入时设置 number_of_replicas=0，导入完成后再增加副本。副本会增加写入开销（每个副本都要执行写入）
  • Translog 优化：默认 index.translog.durability=request（每次请求都 fsync，最安全）。写入密集型可以设置为 async（每 5s 刷盘，可能丢 5s 数据），或增大 index.translog.flush_threshold_size（默认 512MB）减少 Flush 次数
  • 禁用 _all 和不必要的字段：_all 字段（6.0+ 默认禁用）会将所有字段内容复制一份，增加索引体积和写入时间。在 Mapping 中为不需要搜索的字段设置 index: false，不需要聚合的字段设置 doc_values: false

查询性能优化

  • Filter Context vs Query Context：Filter 上下文只过滤不评分，结果可以被缓存（Query Cache）。将不需要评分的条件（范围、精确匹配、存在性）放在 filter 子句中。Query Context 用于需要相关性评分的全文搜索
  • 避免深度聚合：聚合（Aggregation）是内存密集型操作，高基数（high cardinality）字段的 terms 聚合需要加载所有唯一值到内存。设置 size 限制返回桶数量，使用 composite 聚合分页处理高基数聚合，避免 cardinality 聚合在超大基数上的精度问题
  • 路由查询：如果查询条件包含 routing 值（如用户 ID），使用 ?routing=user_1001 只查询相关分片，避免广播到所有分片。适用于多租户场景
  • 字段数据类型选择：keyword 用于精确匹配和聚合，text 用于全文搜索。同时需要两种时用 multi-fields（fields: { raw: { type: keyword } }）。日期字段用 date 类型，数字用 long/double 而非 keyword

8大常见陷阱与最佳实践

  1. 分片数设置不当：分片过多（每个分片有开销，约 1 万字段/分片的元数据）导致集群状态大、查询慢；分片过少导致单分片过大（建议 < 50GB）、无法水平扩展。7.0+ 默认 1 个主分片，根据数据量规划：每分片 10-50GB，每节点分片数不超过 20（每GB堆内存对应不超过 20 个分片）。用 _split（翻倍）和 _shrink（减少）调整，但有前置条件
  2. Mapping 动态映射导致类型错误：Elasticsearch 默认根据第一条文档推断字段类型，可能推断错误（如数字推断为 long 后无法存小数，日期格式不匹配）。生产环境应显式定义 Mapping，设置 dynamic: strict（拒绝未定义字段）或 runtime（运行时字段，不索引）。用 _mapping API 查看当前 Mapping
  3. 集群脑裂（Split Brain）：网络分区时，多个节点都认为自己是 Master，导致集群状态不一致。Elasticsearch 7.0+ 使用新的集群协调协议（基于 Raft），需要配置 discovery.seed_hosts 和 cluster.initial_master_nodes（首次启动）。Master 节点数应为奇数（3或5），discovery.zen.minimum_master_nodes（6.x 及之前）设为 N/2+1
  4. JVM 堆内存设置不当：堆太小导致频繁 GC 和 OOM，堆太大导致 GC 停顿时间长（Full GC 可能停顿数秒）。建议堆大小为物理内存的 50%，且不超过 31GB（超过 32GB 后 JVM 无法使用压缩指针 Compressed Oops，内存效率骤降）。使用 G1GC（7.0+ 默认），监控 jvm.gc.collectors.old.collection_time_in_millis
  5. 段合并占用大量 IO：写入密集时，段合并可能占用大量磁盘 IO 和 CPU，影响搜索性能。Elasticsearch 有合并限流（indices.store.throttle.type=merge，默认 20MB/s），但可能不够。可以调整 index.merge.scheduler.max_thread_count（SSD 设为 4-8，HDD 设为 1），或在低峰期手动触发 _forcemerge（只对只读索引使用，正在写入的索引不要 forcemerge）
  6. 查询超时与熔断：Elasticsearch 有多种熔断器（Circuit Breaker）防止 OOM：父熔断器（总堆 70%）、字段数据熔断器（40%）、请求熔断器（60%）。查询触发熔断时返回 circuit_breaking_exception。大查询用 search.max_buckets（默认 65536）限制聚合桶数，用 timeout 参数限制查询时间，避免慢查询拖垮集群
  7. 磁盘水位线导致只读：Elasticsearch 有三个磁盘水位线：低水位（85%，不再分配新分片）、高水位（90%，将分片迁移到其他节点）、洪水水位（95%，索引设置为只读，index.blocks.read_only_allow_delete）。生产环境必须监控磁盘使用率，提前扩容。达到洪水水位后，清理磁盘需要手动解除只读：PUT _all/_settings { "index.blocks.read_only_allow_delete": null }
  8. _source 字段过大：_source 存储原始 JSON 文档，默认开启。大文档（如包含 base64 图片、长文本）会导致：存储开销大、网络传输慢、Fetch 阶段慢。优化：在 Mapping 中设置 _source: { excludes: ["big_field"] } 排除大字段，或使用 store: true 单独存储需要的字段。查询时用 _source_includes/_source_excludes 只返回需要的字段。注意：关闭 _source 后无法更新文档、无法 reindex、无法查看原始数据
