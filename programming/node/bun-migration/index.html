从 Node.js 迁移到 Bun：分阶段路径、行为差异清单与回退预案

迁移到 Bun 失败的项目基本都犯同一个错：把「换运行时」当成迁移的第一步。正确的顺序恰好相反——先拿走风险最低、收益最确定的部分（CI 装依赖），最后才碰生产运行时，而且每一步都要有独立的回退开关。这篇给的是可执行的清单：阶段划分、依赖体检、行为差异、Dockerfile、上线后验证项、回退预案。为什么值得迁、快多少是真的见 Bun 总览，工具链用法见 Bun 工具链上手，运行时机制与兼容层边界见 Bun 运行时机制。

💡
这篇怎么读
  • ① 用法：可以直接照着敲的分阶段清单（导出依赖树基线并 diff、CI 换装依赖、本地与测试迁移、改镜像 tag 完成切换与回退），一张「要做什么 → 怎么做 → 注意什么」表，以及一张回退触发条件表——什么信号出现就立刻切回去，不要犹豫。
  • ② 原理：五个阶段为什么必须是这个顺序、每阶段的准入线与回退成本、迁移前依赖体检的八个检查项、十一条「测试全绿但线上出事」的行为差异、多阶段 Dockerfile 与镜像变体的取舍、灰度与回退的完整动作序列。
  • ③ 场景：什么项目适合迁、迁到哪一步为止就该停，上线后必须逐项确认的验证清单，以及回退预案为什么必须在迁移之前就建好。

① 用法 · 分阶段迁移清单与回退触发条件

下面这段按阶段排好了顺序，前三个阶段今天就能执行、回退成本都极低；后两个阶段的切换与回退动作是同一条命令的两个方向。注释写的是每一步为什么不能省。

# ---- 阶段零：先留基线。没有基线，之后所有「变好了吗」都只是感觉 ----
npm ls --all --parseable | sed 's#.*node_modules/##' | sort -u > /tmp/deps-npm.txt
npx autocannon -c 50 -d 60 -w 5000 http://127.0.0.1:8080/api/orders/123 | tee /tmp/base-node.txt

# ---- 阶段一：CI 装依赖。唯一的硬要求是依赖树 diff 必须过 ----
bun install                                   # 首次会读 package-lock.json 作为版本来源
bun pm ls --all | sed 's/^[^a-zA-Z@]*//' | sort -u > /tmp/deps-bun.txt
diff /tmp/deps-npm.txt /tmp/deps-bun.txt      # 有差异就逐条确认，重点看驱动、日期、加密库
bun install --frozen-lockfile                 # 确认没问题后，CI 里用这条替换 npm ci
# 然后：提交 bun.lock，删掉 package-lock.json 之外的其他锁文件，CI 缓存 key 带上锁文件哈希

# ---- 阶段二：本地开发。只改 scripts，生产启动命令保持 node ----
bun --watch src/main.ts
bun run typecheck                             # tsc --noEmit 永远不能被 bun 替代

# ---- 阶段三：测试迁移。先拿新基线，再回去改门禁阈值 ----
bun test --coverage 2>&1 | tee /tmp/bun-test.log
grep -iE 'fail|error' /tmp/bun-test.log       # 逐条看失败用例，通过数相同不等于行为相同

# ---- 阶段四与五：切换和回退是同一条命令的两个方向 ----
# 切过去：只改镜像 tag，先让 10% 副本跑 bun 版
kubectl -n prod set image deploy/order-api app=registry.example.com/order-api:1.8.3-bun
kubectl -n prod rollout status deploy/order-api --timeout=120s

# 回退：动作必须和上线一样简单，且不需要改任何一行代码
kubectl -n prod set image deploy/order-api app=registry.example.com/order-api:1.8.3-node
kubectl -n prod rollout status deploy/order-api --timeout=120s

# 回退能力的前置条件，在阶段一就该加进 CI，一行 Bun 专有 API 都不许有
grep -rn 'Bun\.\|bun:sqlite' src/ && echo '存在专有 API：回退预案实际上不成立' && exit 1
要做什么怎么做注意什么
建立对比基线迁移前导出依赖树、压测结果、p99 与错误率快照基线要和迁移后在同一流量比例、同一时间窗下比，否则数据没有意义
CI 换成 bun 装依赖bun install --frozen-lockfile 加全局缓存只留一种锁文件；缓存 key 必须带锁文件哈希，否则会命中旧缓存
确认依赖没有静默漂移迁移前后各导一份依赖树做 diff重点看数据库驱动、日期库、加密库这类行为敏感的依赖
本地开发换执行器scripts 里用 bun run 与 bun --watch生产的 start 保持 node；带 node shebang 的 bin 要加 --bun
测试迁到 bun testbun test --coverage，先跑一遍拿新基线逐条比对失败用例；覆盖率口径变了，门禁阈值要重新设
打出两边通用的产物bun build --target=node --sourcemap=external选 bun 就等于放弃退路；sourcemap 不出，线上堆栈无法还原
准备两条镜像产线同一份 dist 分别 FROM oven/bun 与 FROM node版本写死，不要浮动 tag，否则重建会悄悄换掉运行时
灰度非核心服务10% 副本切 bun 镜像，观察窗口覆盖一个业务高峰进程活着不算通过，要确认 APM 里真的有数据
验证非 HTTP 入口定时任务、消息消费者、脚本任务逐个人工确认这些路径基本不在测试覆盖里，是最容易漏的一类
随时可回退set image 切回 node tag前提是代码里没有 Bun.*，CI 里要有这条检查

灰度期间最需要的不是「继续观察」，而是提前约定好什么信号出现就立刻切回去。回退是廉价动作，犹豫才是贵的。阈值按你自己的 SLO 定，下表给的是口径与动作。

触发信号怎么判定立即动作回退之后先查什么
p99 延迟抬高与基线在同一时间窗、同一流量比例下对比，超出约定阈值且持续两个观察周期切回 node tag先做依赖树 diff，再考虑引擎差异；不要先调参数
RSS 单调上涨连续运行 24 小时不回落，或触及容器 limit 被杀切回用业务计数器定位可疑对象，Bun 的堆快照工具链帮不上忙
出现新的错误类型错误分布里出现迁移前不存在的类型切回先确认是不是 JSC 堆栈格式变化导致错误聚合失真
APM 或追踪面板没数据span 与指标为空，只有进程存活切回判定为不满足迁移前置条件，改手工埋点后再议
发布期错误率规律性抬升每次滚动更新都出现连接被强断可先补信号处理再决定查 SIGTERM 处理与容器里进程是不是 PID 1
定时任务或消费者不执行人工确认某个非 HTTP 入口没有执行记录立即切回查这些入口的启动路径与信号依赖
无法归因的业务 bug行为变了但代码没动切回依赖版本漂移是第一嫌疑，先 diff 再看兼容层
排障超时超过约定的时间盒仍无结论切回把复现搬到预发环境，不要在生产上继续试

下面的原理层解释这五个阶段为什么必须是这个顺序，以及每一条行为差异背后的机制。

② 原理 · 分阶段迁移路径为什么必须是这个顺序

搞清这一节能避免最贵的一类错误：把三种风险一次性叠加，出问题之后无法归因。顺序的逻辑很简单——按「回退成本」从低到高排，每一步只引入一种新风险。

stateDiagram-v2 [*] --> 阶段一CI装依赖 阶段一CI装依赖 --> 阶段二本地开发: 依赖树 diff 通过 构建产物一致 阶段一CI装依赖 --> 回退到npm: 锁文件解析出可疑版本差异 阶段二本地开发 --> 阶段三测试迁移: 全员脚本可跑 无人被环境阻塞 阶段三测试迁移 --> 阶段四非核心服务: 测试全绿 覆盖率基线重新标定 阶段三测试迁移 --> 保留jest: mock 改写成本过高 阶段四非核心服务 --> 观察期: 灰度 10% 流量 观察一到两周 观察期 --> 阶段五核心服务: p99 内存 错误率 三项持平或更好 观察期 --> 回退镜像: 任一指标劣化 或出现无法定位的问题 回退镜像 --> 阶段四非核心服务: 修复后重新灰度 阶段五核心服务 --> [*] 回退到npm --> [*] 保留jest --> 阶段四非核心服务
阶段具体动作验证什么回退成本
一：CI 装依赖CI 里把 npm ci 换成 bun install --frozen-lockfile依赖树与 npm 解析结果 diff；构建产物一致；CI 耗时确实下降极低：改回一行命令，删除 bun.lock
二：本地开发scripts 用 bun run，dev 用 bun --watch全员环境能跑通；带 node shebang 的 bin 是否需要 --bun极低：scripts 换回 node
三：测试迁移jest 换成 bun test失败用例逐条比对（不是只看通过率）；覆盖率口径变化后重新标定门禁阈值低到中：用了 Bun 专有 mock 写法就要改回去
四：非核心服务运行时选一个流量小、依赖简单、无状态的服务切 Bun，灰度 10% 流量p99 延迟、RSS 曲线、错误率、APM 有无数据、优雅关闭、定时任务中：只改镜像 tag，前提是代码没用 Bun.*
五：核心服务在非核心服务稳定运行一到两周后再推进同上，外加容量重新评估（内存策略不同，副本数可能要调）中：同样靠镜像 tag 回退，但需要完整的灰度与观察流程

② 原理 · 迁移前的依赖体检

搞清这一节能在投入之前就知道「这件事有没有得谈」。有一个不可替代的 native addon，运行时迁移就可以直接放弃了，不要抱着「大概能跑」的心态往下推。

检查项怎么查阻塞级别
native addon（.node 二进制）扫 node_modules 下的 .node 文件，逐个确认包名高：N-API 兼容不覆盖全部场景，不可替代就终止
需要 node-gyp 编译的包查 package.json 里的 gypfile 与 install 脚本高：同时还受 trustedDependencies 影响
node:cluster 的使用全仓搜 cluster 与进程管理代码中高：Bun 仅部分实现，正好借机改成多容器部署
worker_threads 复杂用法搜 SharedArrayBuffer、transferList、MessageChannel中：简单用法通常可用，复杂协作需实测
AsyncLocalStorage 与链路追踪搜 async_hooks 与 APM 初始化代码中高：上下文传播行为需逐条验证
APM 探针与 profiler问供应商是否官方支持 Bun高：没有可观测性就不要迁核心服务
依赖里的 postinstall查各包的生命周期脚本中：需要加进 trustedDependencies，否则装成半成品
Docker 基础镜像与体积比对现有 node 镜像与目标 bun 镜像低：选型问题，不阻塞
 
# ---- 依赖体检与锁文件一致性检查，迁移前必须跑完 ----

# 1) 扫 native addon 与需要编译的包
find node_modules -name '*.node' -not -path '*/test/*' | sed 's#node_modules/##' | sort -u
grep -l '"gypfile": *true' node_modules/*/package.json node_modules/@*/*/package.json 2>/dev/null

# 2) 搜可能踩兼容层缺口的用法
grep -rn "node:cluster" src/ || echo "no cluster usage"
grep -rn "async_hooks\|AsyncLocalStorage" src/ || echo "no async_hooks usage"

# 3) 最关键的一步：迁移前后各导出一份依赖树做 diff
npm ls --all --parseable | sed 's#.*node_modules/##' | sort -u > /tmp/deps-npm.txt   # 迁移前
rm -rf node_modules
bun install
bun pm ls --all | sed 's/^[^a-zA-Z@]*//' | sort -u > /tmp/deps-bun.txt              # 迁移后
diff /tmp/deps-npm.txt /tmp/deps-bun.txt | head -50
# 重点看数据库驱动、日期库、加密库这类行为敏感的依赖有没有版本漂移

# 4) 锁文件策略：只留一种，且 CI 用 frozen 参数
ls -1 bun.lock bun.lockb package-lock.json 2>/dev/null   # 理想情况只剩一个
bun install --frozen-lockfile                             # 与 package.json 不一致就直接失败

② 原理 · 行为差异清单：为什么测试全绿也会出事

搞清这一节能解释一个让人措手不及的现象：CI 全绿、预发正常，上线却出问题。原因是下面这些差异大多落在单测覆盖范围之外——环境变量、构建路径、信号、时区、日志解析，没有一项是「业务逻辑」。

现象原因处理
本地跑得好，线上启动就报缺配置Bun 默认自动加载 .env，Node 不加载；本地隐式多了一批变量启动时对必填环境变量做显式校验，缺失直接退出；把变量补进部署配置
打包后模块找不到，源码直跑却正常Bun 运行时会读 tsconfig.json 的 paths 别名，Node 不会构建阶段把别名解析掉，别让运行时承担路径映射
日志解析规则全部失效，错误聚合散开JSC 的错误堆栈格式与 V8 不同（帧描述与行列位置）迁移时同步更新日志解析、错误指纹与告警规则
生产模式没生效，走了开发分支NODE_ENV 的默认值与框架读取时机存在差异在启动命令里显式设置，并在启动日志里打印当前环境
发布时出现连接被强断的错误信号处理与优雅关闭实现不同，原来依赖 Node 的 server.close 语义显式实现 SIGTERM 处理：先让就绪探针失败，再停止接新连接
时间显示或格式化结果变了时区处理与 ICU 数据完整性依镜像变体而异镜像里显式设置 TZ，并写一个断言时区与 Intl 输出的启动自检
某个包装完却报找不到二进制Bun 默认不执行非信任包的 postinstall把包名加进 package.json 的 trustedDependencies
traceId 在某些异步边界后丢失AsyncLocalStorage 的上下文传播行为在复杂链路上未必一致关键 span 手工埋点，不依赖自动插桩；补针对性的集成测试
内存比 Node 高或曲线形状不同JSC 的堆策略不同，且没有 --max-old-space-size 等价参数按压测结果重新设容器 limit 与副本数，预留更多余量
依赖版本莫名变了导致业务行为变化两种包管理器的版本求解与 peer 处理策略不同迁移前后做依赖树 diff，对差异逐条确认
定时任务或消息消费者不工作这些路径通常不在 HTTP 测试覆盖里，问题被漏掉把非 HTTP 入口单独列成验证项，逐个人工确认

② 原理 · Docker 镜像与部署

搞清这一节能解决「回退预案执行不了」的根因：退路是在构建阶段决定的，不是在出事那一刻决定的。关键只有两条——产物的 target 选 node，镜像版本写死。

基础镜像体积量级适用注意
oven/bun:1.2.21（Debian 完整）较大构建阶段不要直接当运行镜像
oven/bun:1.2.21-slim中生产推荐保留基础工具，出事能进容器看一眼
oven/bun:1.2.21-distroless小安全要求高的生产环境没有 shell，调试只能靠日志与旁路手段
oven/bun:1.2.21-alpine最小确认依赖链全兼容 musl 时基于 musl，需要 glibc 的原生依赖会出问题
node:22-slim中回退用的运行镜像保留这条产线，这就是你的退路
 
# ---- 多阶段构建：用 Bun 装依赖与构建，产物同时兼容两个运行时 ----
# 版本必须写死，浮动 tag 会让重建悄悄换掉运行时
FROM oven/bun:1.2.21 AS deps
WORKDIR /app
# 只拷锁文件与 package.json，最大化利用层缓存
COPY package.json bun.lock ./
RUN bun install --frozen-lockfile

FROM oven/bun:1.2.21 AS build
WORKDIR /app
COPY --from=deps /app/node_modules ./node_modules
COPY . .
# 类型检查不能省：Bun 只转译不校验类型
RUN bun run typecheck
# target 选 node，产物两个运行时都能跑，这是保留退路的关键
RUN bun build src/main.ts --target=node --outdir dist --sourcemap=external

# ---- 运行阶段：Bun 版 ----
FROM oven/bun:1.2.21-slim AS runtime-bun
WORKDIR /app
ENV NODE_ENV=production
ENV TZ=Asia/Shanghai
# 只装生产依赖，减小镜像并降低攻击面
COPY package.json bun.lock ./
RUN bun install --frozen-lockfile --production
COPY --from=build /app/dist ./dist
# 不要用 root 跑服务
USER bun
EXPOSE 8080
# 用 exec 形式，保证进程是 PID 1 能直接收到 SIGTERM
CMD ["bun", "dist/main.js"]

# ---- 运行阶段：Node 版，回退产线，与上面共用同一份 dist ----
FROM node:22-slim AS runtime-node
WORKDIR /app
ENV NODE_ENV=production
ENV TZ=Asia/Shanghai
COPY package.json package-lock.json ./
RUN npm ci --omit=dev
COPY --from=build /app/dist ./dist
USER node
EXPOSE 8080
CMD ["node", "--max-old-space-size=1400", "dist/main.js"]

② 原理 · 灰度与回退的动作序列

搞清这一节能解决「观察了两周也不知道观察了什么」的问题：每一步该由谁看、看什么、什么时候可以下结论。

sequenceDiagram autonumber participant OP as 发布人 participant CD as 部署系统 participant K8 as 编排系统 participant MON as 监控与 APM OP->>CD: 部署 bun 镜像 副本数占 10% CD->>K8: 滚动更新 就绪探针通过后接流量 K8->>MON: 上报 p99、RSS、错误率等指标 MON-->>OP: 观察窗口至少覆盖一个业务高峰 OP->>MON: 逐项核对 APM 里是否真的有 span 数据 Note over OP,MON: 只看进程活着是不够的
要确认埋点、日志解析、告警规则都还有效 MON--xOP: 假设 p99 抬高或 RSS 持续上涨 OP->>CD: 把镜像 tag 切回 node 版本 CD->>K8: 滚动回退 目标是几分钟内完成 K8-->>OP: 指标恢复 再回去定位原因 Note over CD,K8: 回退能成立的前提是代码里没有 Bun 专有 API
否则这一步根本执行不了

③ 场景 · 什么项目适合迁、迁到哪一步为止

「迁不迁」不是二选一，真正的问题是「迁到第几阶段就该停」。下表给的是怎么做、为什么、代价：

场景该怎么做为什么代价
依赖全是纯 JS 的无状态服务，团队有余力五个阶段走完，核心服务放最后兼容风险可控，回退只是改镜像 tag每个阶段都要留观察期，整体周期以月计
只想缩短 CI，没有人力做运行时验证停在阶段一到三收益的大头本来就在这三步拿不到运行时那部分收益，但它最小
依赖里有不可替代的 native addon永久停在阶段三N-API 兼容覆盖不到全部场景，这是硬阻塞需要定期复查该依赖有没有纯 JS 替代
APM 供应商明确不支持 Bun非核心服务可以试，核心服务停住没有可观测手段，出事那一刻只能靠日志猜手工埋点的长期维护成本
靠 node:cluster 做多进程先改成多容器，再考虑阶段四兼容层只有部分实现，行为会静默退化部署模型改造，但这件事本来就该做
Serverless 或大量短生命周期任务可以跳过灰度周期直接试运行时启动开销是这类负载的主要成本，收益最直接平台支持与日志追踪接入要先确认
团队第一次接触 Bun先选一个流量小、无状态、依赖简单的服务第一次踩坑的成本应该尽量低推进速度慢，但这是有意为之
业务正在高速迭代、发布很频繁推迟到迭代平缓期迁移期间的问题会和业务变更互相掩盖，无法归因延后收益，换取可归因性

阶段四之后，上线不等于结束，下面这八项必须逐个有结论——任何一项没结论，就不要把流量比例继续往上调。

验证项判定标准不达标怎么办
压测对比同一脚本、同一下游，p99 不劣化（不要只看 QPS 平均值）先定位是引擎差异还是依赖版本变化，别急着调参数
内存曲线连续运行 24 小时以上 RSS 平稳，无单调上涨怀疑泄漏但 Bun 堆快照工具链弱，优先用业务计数器定位可疑对象
错误率与错误类型分布与迁移前逐类对齐，没有新增的未知错误类型先确认是不是堆栈格式变化导致错误聚合失真
APM 与链路追踪面板里真的有 span 和指标数据，不是仅仅进程存活改手工埋点，或判定为不满足迁移前置条件并回退
优雅关闭发 SIGTERM 后停止接新连接、放走在途请求、退出码为 0补显式信号处理；确认进程是 PID 1 能收到信号
非 HTTP 入口定时任务、消息消费者、脚本任务逐个人工确认执行这些路径通常无测试覆盖，必须人工过一遍
日志与告警日志能被采集器正常解析，告警规则仍然生效更新解析规则与错误指纹
容量与副本数按新的内存与延迟特征重新核算调整 limit 与副本数，不要沿用 Node 时代的配置

最后是回退预案。它不是「出事了再想办法」，而是三条必须提前落实的纪律：第一，业务代码一行 Bun.* 专有 API 都不要有，只用标准 Web API 和 node: 前缀模块，这样同一份源码在两个运行时上都能跑（具体清单见 Bun 运行时机制）；第二，CI 同时产出 node 与 bun 两个镜像 tag，构建时目标选 node，让产物两边通用；第三，保留 npm 锁文件或至少保留能随时重新生成它的能力，并把切换动作做成「只改镜像 tag 的一次部署」，目标是几分钟内完成且不改任何代码。

不适用边界：如果迁移的动机是「线上性能不行」，先回到 Bun 总览 把接口耗时构成量出来，大头在数据库或下游时这整套流程都不该启动；具体的诊断方法在 Node.js 性能诊断。如果目标是「一份代码同时跑在 Node、Bun、Workers 上」，那是框架抽象层的问题，不是迁移问题，见 Hono 的跨运行时部署。只想拿工具链收益而完全不碰运行时的做法，在 Bun 工具链上手。

这是本簇的最后一篇，四篇连起来是一条完整路径：先判断值不值得引入，再把工具链用起来，然后理解运行时风险来自哪里，最后按阶段迁移并随时能退回去。

③ 场景 · 反模式与正确做法对照

反模式后果正确做法
直接把生产镜像换成 bun兼容性、可观测性、团队熟悉度三项风险一次性叠加，出问题无法归因按五个阶段推进，从 CI 装依赖开始
迁移后不做压测对比不知道 p99 与内存到底变好还是变坏，容量规划失去依据迁移前先留基线，迁移后用同一脚本复测
用了 Bun 专有 API回退需要改代码，紧急情况下根本来不及只用标准 Web API 与 node:*，把运行时当可替换组件
CI 用 Bun、本地用 Node（或反之）两套依赖解析与运行行为，bug 只在一侧复现统一运行时与包管理器，锁文件只保留一种
镜像用浮动 tag重新构建可能换掉运行时版本，且旧构建无法复现镜像与 CI 都锁具体小版本，升级走独立变更
迁移时不做依赖版本 diff传递依赖静默漂移，业务 bug 出现后查不到根因迁移前后各导一份依赖树做 diff，逐条确认差异
只跑单测就上生产优雅关闭、定时任务、消息消费这些路径没被覆盖把非 HTTP 入口与信号处理列成独立验证项
灰度期没有约定回退触发条件指标劣化时开始讨论「再观察一天」，损失被拉长上线前就把触发信号、判定口径与动作写下来
先迁核心服务没有运维经验积累，第一次踩坑就发生在最贵的地方从流量小、无状态、依赖简单的非核心服务开始

最容易踩的坑

❌
避坑清单
  • 把换运行时当第一步：它应该最后做，前面四个阶段是用来积累信心和暴露问题的。
  • 迁移前没留基线：依赖树、p99、内存、错误率都要有迁移前的快照，否则事后无从对比。
  • 不做依赖树 diff：两种包管理器可能解析出不同的传递依赖版本，业务 bug 会被归错因。
  • 依赖 Bun 自动加载 .env：本地隐式有变量，线上缺失，启动失败还算好，走进默认分支更糟。
  • 忘了 trustedDependencies：Prisma、Puppeteer 这类靠 postinstall 的包会装成半成品。
  • 镜像用 latest：某次重建悄悄换了运行时版本，且旧构建再也复现不出来。
  • 用 alpine 变体却有需要 glibc 的原生依赖：报错信息通常指向完全无关的地方。
  • 没显式处理 SIGTERM：滚动发布期间连接被强断，错误率在每次发布时规律性抬升。
  • CMD 写成 shell 形式：进程不是 PID 1，收不到信号，优雅关闭完全失效。
  • 把 --max-old-space-size 照搬到 bun 启动命令：参数不存在，内存规划失去控制手段。
  • 迁移后不看 APM 有没有数据：进程活着不等于可观测，出事时才发现没有任何埋点。
  • 不更新日志解析规则：JSC 堆栈格式不同，错误聚合与告警会静默失效。
  • 没约定回退触发条件：灰度期靠临场讨论决定要不要退，时间全花在犹豫上。
  • 代码里留了 Bun.serve 之类专有 API 却还写了回退预案：预案在紧急时刻根本执行不了。
