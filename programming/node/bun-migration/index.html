从 Node.js 迁移到 Bun：分阶段路径、行为差异清单与回退预案

迁移到 Bun 失败的项目基本都犯同一个错：把「换运行时」当成迁移的第一步。正确的顺序恰好相反——先拿走风险最低、收益最确定的部分（CI 装依赖），最后才碰生产运行时，而且每一步都要有独立的回退开关。这篇给的是可执行的清单：阶段划分、依赖体检、行为差异、Dockerfile、上线后验证项、回退预案。为什么值得迁、快多少是真的见 Bun 总览，工具链用法见 Bun 工具链上手，运行时机制与兼容层边界见 Bun 运行时机制。

阶段具体动作验证什么回退成本
一：CI 装依赖CI 里把 npm ci 换成 bun install --frozen-lockfile依赖树与 npm 解析结果 diff；构建产物一致；CI 耗时确实下降极低：改回一行命令，删除 bun.lock
二：本地开发scripts 用 bun run，dev 用 bun --watch全员环境能跑通；带 node shebang 的 bin 是否需要 --bun极低：scripts 换回 node
三：测试迁移jest 换成 bun test失败用例逐条比对（不是只看通过率）；覆盖率口径变化后重新标定门禁阈值低到中：用了 Bun 专有 mock 写法就要改回去
四：非核心服务运行时选一个流量小、依赖简单、无状态的服务切 Bun，灰度 10% 流量p99 延迟、RSS 曲线、错误率、APM 有无数据、优雅关闭、定时任务中：只改镜像 tag，前提是代码没用 Bun.*
五：核心服务在非核心服务稳定运行一到两周后再推进同上，外加容量重新评估（内存策略不同，副本数可能要调）中：同样靠镜像 tag 回退，但需要完整的灰度与观察流程

迁移前的依赖体检

这一步决定了「值不值得继续往下走」。有一个不可替代的 native addon，运行时迁移就可以直接放弃了，不要抱着「大概能跑」的心态往下推。

检查项怎么查阻塞级别
native addon（.node 二进制）扫 node_modules 下的 .node 文件，逐个确认包名高：N-API 兼容不覆盖全部场景，不可替代就终止
需要 node-gyp 编译的包查 package.json 里的 gypfile 与 install 脚本高：同时还受 trustedDependencies 影响
node:cluster 的使用全仓搜 cluster 与进程管理代码中高：Bun 仅部分实现，正好借机改成多容器部署
worker_threads 复杂用法搜 SharedArrayBuffer、transferList、MessageChannel中：简单用法通常可用，复杂协作需实测
AsyncLocalStorage 与链路追踪搜 async_hooks 与 APM 初始化代码中高：上下文传播行为需逐条验证
APM 探针与 profiler问供应商是否官方支持 Bun高：没有可观测性就不要迁核心服务
依赖里的 postinstall查各包的生命周期脚本中：需要加进 trustedDependencies，否则装成半成品
Docker 基础镜像与体积比对现有 node 镜像与目标 bun 镜像低：选型问题，不阻塞
 
# ---- 依赖体检与锁文件一致性检查，迁移前必须跑完 ----

# 1) 扫 native addon 与需要编译的包
find node_modules -name '*.node' -not -path '*/test/*' | sed 's#node_modules/##' | sort -u
grep -l '"gypfile": *true' node_modules/*/package.json node_modules/@*/*/package.json 2>/dev/null

# 2) 搜可能踩兼容层缺口的用法
grep -rn "node:cluster" src/ || echo "no cluster usage"
grep -rn "async_hooks\|AsyncLocalStorage" src/ || echo "no async_hooks usage"

# 3) 最关键的一步：迁移前后各导出一份依赖树做 diff
npm ls --all --parseable | sed 's#.*node_modules/##' | sort -u > /tmp/deps-npm.txt   # 迁移前
rm -rf node_modules
bun install
bun pm ls --all | sed 's/^[^a-zA-Z@]*//' | sort -u > /tmp/deps-bun.txt              # 迁移后
diff /tmp/deps-npm.txt /tmp/deps-bun.txt | head -50
# 重点看数据库驱动、日期库、加密库这类行为敏感的依赖有没有版本漂移

# 4) 锁文件策略：只留一种，且 CI 用 frozen 参数
ls -1 bun.lock bun.lockb package-lock.json 2>/dev/null   # 理想情况只剩一个
bun install --frozen-lockfile                             # 与 package.json 不一致就直接失败

行为差异清单

下面每一条都是「测试全绿但线上出事」的典型来源，因为它们大多不在单测覆盖范围内。

现象原因处理
本地跑得好，线上启动就报缺配置Bun 默认自动加载 .env，Node 不加载；本地隐式多了一批变量启动时对必填环境变量做显式校验，缺失直接退出；把变量补进部署配置
打包后模块找不到，源码直跑却正常Bun 运行时会读 tsconfig.json 的 paths 别名，Node 不会构建阶段把别名解析掉，别让运行时承担路径映射
日志解析规则全部失效，错误聚合散开JSC 的错误堆栈格式与 V8 不同（帧描述与行列位置）迁移时同步更新日志解析、错误指纹与告警规则
生产模式没生效，走了开发分支NODE_ENV 的默认值与框架读取时机存在差异在启动命令里显式设置，并在启动日志里打印当前环境
发布时出现连接被强断的错误信号处理与优雅关闭实现不同，原来依赖 Node 的 server.close 语义显式实现 SIGTERM 处理：先让就绪探针失败，再停止接新连接
时间显示或格式化结果变了时区处理与 ICU 数据完整性依镜像变体而异镜像里显式设置 TZ，并写一个断言时区与 Intl 输出的启动自检
某个包装完却报找不到二进制Bun 默认不执行非信任包的 postinstall把包名加进 package.json 的 trustedDependencies
traceId 在某些异步边界后丢失AsyncLocalStorage 的上下文传播行为在复杂链路上未必一致关键 span 手工埋点，不依赖自动插桩；补针对性的集成测试
内存比 Node 高或曲线形状不同JSC 的堆策略不同，且没有 --max-old-space-size 等价参数按压测结果重新设容器 limit 与副本数，预留更多余量
依赖版本莫名变了导致业务行为变化两种包管理器的版本求解与 peer 处理策略不同迁移前后做依赖树 diff，对差异逐条确认
定时任务或消息消费者不工作这些路径通常不在 HTTP 测试覆盖里，问题被漏掉把非 HTTP 入口单独列成验证项，逐个人工确认

Docker 镜像与部署

基础镜像体积量级适用注意
oven/bun:1.2.21（Debian 完整）较大构建阶段不要直接当运行镜像
oven/bun:1.2.21-slim中生产推荐保留基础工具，出事能进容器看一眼
oven/bun:1.2.21-distroless小安全要求高的生产环境没有 shell，调试只能靠日志与旁路手段
oven/bun:1.2.21-alpine最小确认依赖链全兼容 musl 时基于 musl，需要 glibc 的原生依赖会出问题
node:22-slim中回退用的运行镜像保留这条产线，这就是你的退路
 
# ---- 多阶段构建：用 Bun 装依赖与构建，产物同时兼容两个运行时 ----
# 版本必须写死，浮动 tag 会让重建悄悄换掉运行时
FROM oven/bun:1.2.21 AS deps
WORKDIR /app
# 只拷锁文件与 package.json，最大化利用层缓存
COPY package.json bun.lock ./
RUN bun install --frozen-lockfile

FROM oven/bun:1.2.21 AS build
WORKDIR /app
COPY --from=deps /app/node_modules ./node_modules
COPY . .
# 类型检查不能省：Bun 只转译不校验类型
RUN bun run typecheck
# target 选 node，产物两个运行时都能跑，这是保留退路的关键
RUN bun build src/main.ts --target=node --outdir dist --sourcemap=external

# ---- 运行阶段：Bun 版 ----
FROM oven/bun:1.2.21-slim AS runtime-bun
WORKDIR /app
ENV NODE_ENV=production
ENV TZ=Asia/Shanghai
# 只装生产依赖，减小镜像并降低攻击面
COPY package.json bun.lock ./
RUN bun install --frozen-lockfile --production
COPY --from=build /app/dist ./dist
# 不要用 root 跑服务
USER bun
EXPOSE 8080
# 用 exec 形式，保证进程是 PID 1 能直接收到 SIGTERM
CMD ["bun", "dist/main.js"]

# ---- 运行阶段：Node 版，回退产线，与上面共用同一份 dist ----
FROM node:22-slim AS runtime-node
WORKDIR /app
ENV NODE_ENV=production
ENV TZ=Asia/Shanghai
COPY package.json package-lock.json ./
RUN npm ci --omit=dev
COPY --from=build /app/dist ./dist
USER node
EXPOSE 8080
CMD ["node", "--max-old-space-size=1400", "dist/main.js"]

灰度与回退的动作序列

要确认埋点、日志解析、告警规则都还有效 MON--xOP: 假设 p99 抬高或 RSS 持续上涨 OP->>CD: 把镜像 tag 切回 node 版本 CD->>K8: 滚动回退 目标是几分钟内完成 K8-->>OP: 指标恢复 再回去定位原因 Note over CD,K8: 回退能成立的前提是代码里没有 Bun 专有 API
否则这一步根本执行不了

上线后必须逐项确认的验证清单

验证项判定标准不达标怎么办
压测对比同一脚本、同一下游，p99 不劣化（不要只看 QPS 平均值）先定位是引擎差异还是依赖版本变化，别急着调参数
内存曲线连续运行 24 小时以上 RSS 平稳，无单调上涨怀疑泄漏但 Bun 堆快照工具链弱，优先用业务计数器定位可疑对象
错误率与错误类型分布与迁移前逐类对齐，没有新增的未知错误类型先确认是不是堆栈格式变化导致错误聚合失真
APM 与链路追踪面板里真的有 span 和指标数据，不是仅仅进程存活改手工埋点，或判定为不满足迁移前置条件并回退
优雅关闭发 SIGTERM 后停止接新连接、放走在途请求、退出码为 0补显式信号处理；确认进程是 PID 1 能收到信号
非 HTTP 入口定时任务、消息消费者、脚本任务逐个人工确认执行这些路径通常无测试覆盖，必须人工过一遍
日志与告警日志能被采集器正常解析，告警规则仍然生效更新解析规则与错误指纹
容量与副本数按新的内存与延迟特征重新核算调整 limit 与副本数，不要沿用 Node 时代的配置

回退预案：在迁移之前就建好

回退预案不是「出事了再想办法」，而是三条必须提前落实的纪律：第一，业务代码一行 Bun.* 专有 API 都不要有，只用标准 Web API 和 node: 前缀模块，这样同一份源码在两个运行时上都能跑（具体清单见 Bun 运行时机制）；第二，CI 同时产出 node 与 bun 两个镜像 tag，构建时目标选 node，让产物两边通用；第三，保留 npm 锁文件或至少保留能随时重新生成它的能力，并把切换动作做成「只改镜像 tag 的一次部署」，目标是几分钟内完成且不改任何代码。

反模式对照表

反模式后果正确做法
直接把生产镜像换成 bun兼容性、可观测性、团队熟悉度三项风险一次性叠加，出问题无法归因按五个阶段推进，从 CI 装依赖开始
迁移后不做压测对比不知道 p99 与内存到底变好还是变坏，容量规划失去依据迁移前先留基线，迁移后用同一脚本复测
用了 Bun 专有 API回退需要改代码，紧急情况下根本来不及只用标准 Web API 与 node:*，把运行时当可替换组件
CI 用 Bun、本地用 Node（或反之）两套依赖解析与运行行为，bug 只在一侧复现统一运行时与包管理器，锁文件只保留一种
镜像用浮动 tag重新构建可能换掉运行时版本，且旧构建无法复现镜像与 CI 都锁具体小版本，升级走独立变更
迁移时不做依赖版本 diff传递依赖静默漂移，业务 bug 出现后查不到根因迁移前后各导一份依赖树做 diff，逐条确认差异
只跑单测就上生产优雅关闭、定时任务、消息消费这些路径没被覆盖把非 HTTP 入口与信号处理列成独立验证项
先迁核心服务没有运维经验积累，第一次踩坑就发生在最贵的地方从流量小、无状态、依赖简单的非核心服务开始
❌
最容易踩的坑
  • 把换运行时当第一步：它应该最后做，前面四个阶段是用来积累信心和暴露问题的。
  • 不做依赖树 diff：两种包管理器可能解析出不同的传递依赖版本，业务 bug 会被归错因。
  • 依赖 Bun 自动加载 .env：本地隐式有变量，线上缺失，启动失败还算好，走进默认分支更糟。
  • 忘了 trustedDependencies：Prisma、Puppeteer 这类靠 postinstall 的包会装成半成品。
  • 镜像用 latest：某次重建悄悄换了运行时版本，且旧构建再也复现不出来。
  • 用 alpine 变体却有需要 glibc 的原生依赖：报错信息通常指向完全无关的地方。
  • 没显式处理 SIGTERM：滚动发布期间连接被强断，错误率在每次发布时规律性抬升。
  • CMD 写成 shell 形式：进程不是 PID 1，收不到信号，优雅关闭完全失效。
  • 把 --max-old-space-size 照搬到 bun 启动命令：参数不存在，内存规划失去控制手段。
  • 迁移后不看 APM 有没有数据：进程活着不等于可观测，出事时才发现没有任何埋点。
  • 不更新日志解析规则：JSC 堆栈格式不同，错误聚合与告警会静默失效。
  • 代码里留了 Bun.serve 之类专有 API 却还写了回退预案：预案在紧急时刻根本执行不了。
