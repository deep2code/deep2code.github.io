Node.js 性能诊断：事件循环延迟、内存与火焰图

🏷️ Node.js 总览

先分诊，再动工具

Node 服务变慢的原因就三大类：主线程被阻塞、等下游、内存与 GC。三类的工具、指标、修法完全不同，先分诊再选工具能省掉一半时间。最常见的错误是一上来就抓火焰图——如果问题是等下游，火焰图里什么都看不到，因为等待不消耗 CPU，采样器根本采不到。

事件循环延迟：最该先接的指标

perf_hooks.monitorEventLoopDelay 返回一个原生直方图，内部用固定间隔的定时器测「本该在 t 时刻醒来，实际几点醒的」，单位是纳秒。它比 CPU 使用率灵敏得多：任何形式的主线程阻塞都会立刻体现在 p99 上，而 CPU 使用率在多核机器上被平均掉，单核打满时整机可能只有 12%。

// metrics/loop.js —— 生产可直接抄
const { monitorEventLoopDelay, performance } = require('node:perf_hooks')

// resolution 是采样间隔，单位毫秒。10 足够，1 会让直方图本身成为负担
const h = monitorEventLoopDelay({ resolution: 10 })
h.enable()

// eventLoopUtilization 是另一个维度：返回 0 到 1 的「忙碌占比」
// 延迟高 + ELU 高 = 在算；延迟高 + ELU 低 = 在等（同步 IO、换页）
let last = performance.eventLoopUtilization()

setInterval(() => {
  const ms = (v) => Math.round(v / 1e6 * 100) / 100   // 纳秒转毫秒
  const elu = performance.eventLoopUtilization(last)
  last = performance.eventLoopUtilization()

  const p50 = ms(h.percentile(50))
  const p99 = ms(h.percentile(99))
  const max = ms(h.max)

  // 阈值量级（HTTP 服务经验值，按自己 SLO 调）：
  //   p99 小于 10ms 健康；10 到 50ms 需要观察；大于 50ms 已经影响长尾；
  //   大于 200ms 基本等于「有一段代码在同步跑」，必须处理
  if (p99 > 50) {
    console.warn('[loop] p50=%s p99=%s max=%s utilization=%s',
      p50, p99, max, elu.utilization.toFixed(3))
  }

  h.reset()   // 不 reset 的话直方图是进程启动以来的累计值，毛刺会永远留在 p99 上
}, 10000)
💡
为什么看直方图而不是平均值

平均延迟会把「1000 次 0.2ms + 1 次 800ms」算成 1ms 左右，看起来完全健康，而那 1 次 800ms 已经让几百个并发请求集体超时。直方图的 max 字段尤其重要：它直接告诉你单次最长阻塞，是判断「有没有同步大计算」最快的一个数。

CPU 火焰图：怎么采，怎么读

Node 自带的 --cpu-prof 已经够用，不需要额外装东西；0x 和 clinic 的价值在于把内核栈、libuv 栈一起画进来，以及生成更好读的交互页面。

方式怎么采产物能看到 C++ / 内核栈吗适用场景
--cpu-prof启动参数，进程退出时落盘.cpuprofile，拖进 Chrome DevTools不能，只有 JS 栈压测环境、可控退出的复现脚本
Inspector 协议代码里用 inspector 模块按需开关同上不能生产按需采样 30 秒，最推荐
0xnpx 0x -- node app.js交互式 HTML 火焰图能，含 libuv 与 GC 帧怀疑瓶颈在原生层或 GC
clinic doctor / flamenpx clinic doctor -- node app.js带结论的诊断报告部分本地快速定性，不建议上生产
--prof + --prof-processV8 原生 tick 采样文本报告，按 ticks 排序能看到 C++ 汇总怀疑是 JIT 去优化或内建函数问题

读火焰图只需记住三条规则。横轴宽度是采样命中次数的占比，不是时间顺序，也不是绝对耗时；同一层左右相邻的两个框没有先后关系。要找的是平顶（plateau）——某个函数自身占了很宽的一条且上面没有子调用，说明时间花在它自己的代码里。看不见的东西同样重要：等数据库、等下游 HTTP、等线程池，这些时间进程在 epoll_wait 里睡着，采样器采不到任何 JS 栈，所以火焰图很窄但接口很慢，恰恰说明问题不在 CPU。

火焰图形状说明什么常见原因处理方向
某个 JS 函数自身很宽的平顶纯计算热点正则回溯、循环里做字符串拼接、手写序列化换算法、缓存、切片或移出主线程
JSON.parse / JSON.stringify 很宽序列化成本大响应体、日志里打整个对象裁字段、预编译序列化、日志脱敏
大量 GC 或 Scavenge 帧分配压力大每请求创建大量临时对象或大 Buffer复用缓冲、减少中间数组
整体很窄、总采样数很少进程在等下游慢、线程池排队、锁在外部转去看下游指标与连接池
栈非常深且重复递归或中间件层数过多框架插件堆叠、装饰器链精简中间件链路
compile / deoptimize 帧明显反复去优化同一函数传入形状不一致的对象固定对象形状，避免联合类型热路径

内存：堆内、堆外与容器上限

一句结论先给：堆上限不能配成容器内存上限。Node 进程的内存除了 V8 堆，还有 Buffer、原生模块、线程栈、代码与元数据，这些都在堆外，不受 --max-old-space-size 约束。把堆上限配成和容器 limit 相等，等于承诺「堆用满时进程正好占满容器」，而实际上还要加上堆外那一块，结果是被容器直接杀掉，连 OOM 堆栈都拿不到。堆上限与容器 limit 的取值关系详见 Node.js 总览。

指标含义异常形态对应问题
heapUsedV8 堆里存活对象锯齿的底部持续抬升JS 对象泄漏
heapTotalV8 已向系统申请的堆贴近堆上限且不回落即将 OOM，先确认是否泄漏再考虑调大
external / arrayBuffers堆外的 Buffer 与原生分配单独上涨而 heapUsed 平稳Buffer 未释放、流未消费、addon 泄漏
rss进程实际占用物理内存远高于 heapTotal 且持续涨堆外泄漏或内存碎片
GC 后的老生代用量真实存活基线每次 Mark-Compact 之后都更高确诊泄漏的最硬指标

三快照法是定位 JS 泄漏最实用的手段：在稳定状态拍第一张（基线），跑一段真实业务后拍第二张，再跑同样一段后拍第三张。在 Chrome DevTools 的 Memory 面板里用 Comparison 视图，先比较快照 2 与 1、再比较 3 与 2，只关注两次比较里都持续增长的构造函数——只在一次里增长的多半是缓存预热或惰性初始化。锁定对象后切到 Retainers 面板看引用链，链条的顶端就是没放手的那个人。

把请求对象塞进长生命周期结构大量 IncomingMessage 存活快照里按构造函数筛只存必要的标量字段
 
// 最常见的一个泄漏：无上限缓存。下面是可直接替换的有界实现
class BoundedCache {
  // max 是条目上限，ttlMs 是单条存活时间；两者都必须有，只有 TTL 仍会被突发流量打爆
  constructor(max = 5000, ttlMs = 60_000) {
    this.max = max
    this.ttl = ttlMs
    this.map = new Map()   // Map 的迭代顺序是插入顺序，天然可做 LRU
  }

  get(key) {
    const hit = this.map.get(key)
    if (!hit) return undefined
    if (Date.now() > hit.exp) { this.map.delete(key); return undefined }
    this.map.delete(key); this.map.set(key, hit)   // 命中即提到队尾
    return hit.val
  }

  set(key, val) {
    if (this.map.size >= this.max) {
      // 淘汰最久未使用的一条：Map 的第一个 key
      this.map.delete(this.map.keys().next().value)
    }
    this.map.set(key, { val, exp: Date.now() + this.ttl })
  }

  get size() { return this.map.size }
}

// 关键：把 size 暴露成监控指标。没有指标的缓存等于没有上限，
// 因为你不会知道它是在正常工作还是已经长到了上限并开始疯狂淘汰。
module.exports = { BoundedCache }

GC 观测与同步阻塞定位

--trace-gc 的每一行都会打印这次回收的类型和前后堆用量。判读只看两件事：Mark-Compact 之后的堆用量是否回落到一个稳定基线，以及单次停顿时长。Scavenge（新生代）通常在 1ms 量级，频繁但便宜；Mark-Compact 是几十到几百毫秒的停顿，如果每分钟出现好几次，说明老生代压力已经很大。

GC 日志形态判定动作
Scavenge 很频繁，老生代平稳正常但分配率高减少每请求的临时对象，通常不用调参
Mark-Compact 后的堆用量逐次抬升确诊泄漏三快照法定位，不要先调大堆
Mark-Compact 频繁且每次回收很多老生代被反复填满看是不是大对象直接进老生代，考虑复用
单次停顿超过 100ms 且延迟毛刺对齐GC 停顿影响长尾降低堆峰值，必要时调整新生代大小
堆用量平稳但 RSS 上涨堆外问题查 Buffer、流、原生模块

同步阻塞有两条互补的定位路径。第一条是 --trace-sync-io：进程启动完成后，任何一次同步 IO 调用都会打印警告和调用栈，直接指出代码位置——只在开发和预发环境开，因为它本身有开销。第二条是反推：事件循环延迟直方图的 max 和 p99 已经告诉你「单次最长阻塞有多久」，用这个数去对照日志时间戳，通常能定位到某个特定接口或定时任务。

压测要看什么

压测最常见的三个错误：只看 QPS、用平均延迟、以及压测客户端自己成了瓶颈。QPS 是结果而不是目标，同样 5 万 QPS，p99 是 5ms 还是 500ms 是两个完全不同的系统。更隐蔽的是协调遗漏：很多压测工具在响应变慢时会自然降低发压速率（因为连接被占住），结果「服务变慢」这件事本身减少了慢请求的样本数，测出来的延迟分布比真实情况乐观得多。对抗办法是固定发压速率（恒定 RPS 模式）而不是固定连接数，并把队列等待时间计入延迟。系统性的压测方法论与容量规划详见站内 后端性能优化 分组。

生产可观测性：暴露 Node 特有指标

通用的 QPS、延迟、错误率任何语言都一样，Node 真正需要额外暴露的是运行时自身的四类指标：事件循环延迟、堆分代用量、GC 次数与耗时、活跃句柄与请求数。最后一项经常被忽略，但它是「句柄泄漏」和「优雅关闭卡住」最直接的证据。

// metrics/index.js —— prom-client 暴露 Node 运行时指标
const { collectDefaultMetrics, Registry, Gauge } = require('prom-client')
const { monitorEventLoopDelay, performance } = require('node:perf_hooks')

const registry = new Registry()

// 默认指标已包含：nodejs_heap_size_used_bytes、nodejs_gc_duration_seconds、
// nodejs_active_handles_total、nodejs_eventloop_lag_seconds 等
collectDefaultMetrics({
  register: registry,
  // GC 耗时直方图的分桶，按毫秒量级给，默认分桶对 Node 偏粗
  gcDurationBuckets: [0.001, 0.005, 0.01, 0.05, 0.1, 0.5, 1],
})

// 默认的 lag 指标是瞬时采样，自己再加一个直方图分位数更可靠
const h = monitorEventLoopDelay({ resolution: 10 })
h.enable()

new Gauge({
  name: 'app_eventloop_delay_p99_ms',
  help: '事件循环延迟 p99，毫秒',
  registers: [registry],
  collect() { this.set(h.percentile(99) / 1e6) },   // 抓取时才计算，避免定时器
})

new Gauge({
  name: 'app_eventloop_utilization',
  help: '事件循环忙碌占比，0 到 1',
  registers: [registry],
  collect() { this.set(performance.eventLoopUtilization().utilization) },
})

// 暴露给 Prometheus 抓取；注意这个端口不要暴露到公网
async function metricsHandler(req, res) {
  res.setHeader('Content-Type', registry.contentType)
  res.end(await registry.metrics())
}

module.exports = { registry, metricsHandler }

告警配在哪里最划算

三条就够用：事件循环延迟 p99 连续 5 分钟超过 50ms；GC 后老生代用量占堆上限超过 80%；活跃句柄数在 10 分钟内单调递增。前两条覆盖了阻塞与内存，第三条能在句柄泄漏演变成 OOM 之前几个小时就报出来。

反模式对照

反模式为什么坏正确做法
只看 CPU 与 QPS线程池排队、下游等待、GC 停顿在这两个数上都看不见以事件循环延迟直方图为主指标
用平均延迟评估性能长尾被完全抹平看 p99 与 max，并盯住直方图形状
生产长期开 CPU profiling采样与写盘都有开销，且 profile 文件可能泄漏源码结构按需采 30 秒，用信号或管控接口触发
堆上限配成容器内存 limitBuffer 等堆外内存不受堆上限约束，先被容器杀掉给堆外留出余量，详见 总览
内存一涨就调大 --max-old-space-size泄漏没修，只是把 OOM 推迟先用 GC 日志确认基线是否抬升
压测客户端和服务同机客户端抢 CPU，测出来的延迟全是假的分机部署，压测时监控客户端自身负载
固定连接数压测就下结论协调遗漏让慢请求样本变少用恒定速率模式，并计入排队时间
火焰图很窄就认为「没问题」等待不消耗 CPU，采样采不到窄图恰恰指向下游或线程池
日志里 JSON.stringify 整个对象序列化成本进入请求路径，还可能泄漏敏感字段只打必要字段，用结构化日志库

最容易踩的坑

1. 直方图忘了 reset()，p99 变成进程启动至今的累计值，启动期的一次毛刺永远挂在图上。

2. 把 monitorEventLoopDelay 的返回值当毫秒用，实际是纳秒，阈值差了六个数量级。

3. resolution 设成 1ms，直方图自身的定时器变成噪声源，低负载时反而测出更高的延迟。

4. 拿火焰图去查「等下游」的慢，图里一片空白然后怀疑工具坏了。

5. 把火焰图的横轴当时间轴读，以为左边的函数先执行。

6. 只拍两张堆快照就下结论，把缓存预热和惰性初始化误判成泄漏。

7. 在生产直接开 --inspect 抓快照，调试端口暴露等于任意代码执行入口。

8. 堆上限配成容器 limit，Buffer 一涨就被容器杀掉，拿不到任何 OOM 现场。

9. 内存涨就调大堆上限，泄漏还在，只是 OOM 从每天一次变成每周一次且更难复现。

10. 缓存只加 TTL 不加容量上限，突发流量下条目数先爆内存。

11. 压测只报 QPS 不报 p99，上线后长尾超时，回头发现压测数据毫无参考价值。

12. 压测机 CPU 已经打满还在加并发，测出来的「服务瓶颈」其实是客户端瓶颈。

13. 指标端口和业务端口共用且暴露到公网，把运行时内部状态直接公开。
