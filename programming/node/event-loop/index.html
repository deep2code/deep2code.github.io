Node.js 事件循环的六个阶段与实际影响

🏷️ Node.js 总览

先纠正几个流传很广的说法

事件循环是 Node.js 面试里问得最多、讲得最糊的一块。绝大多数教程停留在「单线程 + 非阻塞 IO」这一句话上，而线上真正会咬人的细节恰恰藏在阶段边界和队列优先级里。先把几个错误认知摆出来，后面逐条展开。

流传很广的说法实际情况会导致什么后果
微任务队列每轮循环清空一次每两个阶段之间、以及每个回调执行完都会清空误以为递归 nextTick 只会拖慢一轮，实际能永久饿死 IO
setImmediate 就是「立即执行」它在 check 阶段执行，比微任务晚，比下一轮 timers 早拿它当同步用，顺序推演全错
Node 的异步 IO 全是内核原生异步只有网络 IO 走 epoll/kqueue，文件与部分 crypto、zlib 走线程池大量文件读写时延迟暴涨却查不出原因
没有事件要处理时进程在空转poll 阶段会真正阻塞在 epoll_wait 上，超时由最近的定时器决定误判空闲进程的 CPU 曲线
setTimeout(fn, 0) 等于 0 延迟最小值被钳到 1ms，且实际执行点取决于当轮阻塞情况拿定时器做精确节拍，高负载下漂移到几百毫秒

一轮循环的六个阶段

libuv 的一轮迭代按固定顺序穿过六个阶段。每个阶段有自己的回调队列，进入某个阶段后会把该阶段队列里的回调执行完（或达到系统相关的上限）才进入下一阶段。当没有任何活跃的 handle 和 request 时，循环退出，进程自然结束。

微任务的插入时机才是关键

六个阶段只是骨架。真正决定输出顺序的是两条微任务队列的清空时机：process.nextTick 队列优先于 Promise 微任务队列，而这两条队列在每个阶段切换之间、以及每个宏任务回调执行完之后都会被完整清空——不是每轮循环一次。这个细节决定了递归 nextTick 的杀伤力。

嵌套深度限制无限制，无警告无限制无限制但让路无限制但让路
适用场景在同步代码返回后立刻触发错误事件，库作者用业务代码里绝大多数「下一个微任务」需求把大任务切片，给 IO 让路需要真实时间延迟

// 完整的顺序推演：把这段直接存成 order.js 跑一遍
const fs = require('node:fs')

console.log('A 同步开始')

setTimeout(() => console.log('E timers 阶段'), 0)
setImmediate(() => console.log('F check 阶段'))

Promise.resolve().then(() => {
  console.log('D Promise 微任务')
  // 微任务里再塞 nextTick：它会插到「当前微任务队列清空之后」
  process.nextTick(() => console.log('D2 微任务里注册的 nextTick'))
})

process.nextTick(() => console.log('C nextTick 优先于 Promise'))

console.log('B 同步结束')

// 输出：A B C D D2 E F
// 关键点 1：C 在 D 之前 —— nextTick 队列整体优先于 Promise 微任务队列
// 关键点 2：D2 在 E 之前 —— 进入 timers 阶段前又清空了一次两条微任务队列
// 关键点 3：E 与 F 的先后在主模块里不稳定（见下一节），在 IO 回调里才稳定

fs.readFile(__filename, () => {
  // 这里是 poll 阶段的回调，本轮的下一站就是 check 阶段
  setTimeout(() => console.log('H timers 要等到下一轮'), 0)
  setImmediate(() => console.log('G check 就在本轮的下一站'))
  // 稳定输出：先 G 再 H
})
❌
递归 nextTick 能让整个进程假死

因为 nextTick 队列在进入下一阶段前必须清空，而清空过程中新增的项会追加到同一队列，循环永远走不到 poll 阶段。表现是 CPU 单核 100%、进程还活着、健康检查端口不响应、日志停止输出。同样的代码换成 setImmediate 递归则完全安全——每轮只执行本轮已入队的那一批，IO 回调能插进来。

// 场景：对 200 万条记录做 CPU 计算，又不想让健康检查超时
// 错误写法：nextTick 递归，poll 阶段永远进不去，服务假死
function badChunk(items, i = 0) {
  if (i >= items.length) return
  compute(items[i])
  process.nextTick(() => badChunk(items, i + 1))
}

// 正确写法：setImmediate 切片，每片之间让事件循环跑完一整轮
// batch 取多大：让单片耗时控制在 5ms 以内，避免单次阻塞抬高 p99
function goodChunk(items, i = 0, batch = 500) {
  const end = Math.min(i + batch, items.length)
  for (let k = i; k < end; k++) compute(items[k])
  if (end < items.length) {
    setImmediate(() => goodChunk(items, end, batch))
  }
}

// 注意：切片只解决「不要一次阻塞太久」，不解决「总算力不够」。
// 真正 CPU 密集的负载该移出主线程，单线程的适用边界见 Node.js 总览篇。

为什么主模块里 setTimeout 与 setImmediate 顺序不稳定

这是最经典的输出顺序题。答案不是「随机」，而是取决于进程从启动到第一次进入 timers 阶段花了多久。setTimeout(fn, 0) 被 Node 钳成 1ms，第一次进入 timers 阶段时：如果已经过了 1ms，定时器到期，先打印 timers 的回调；如果还没到 1ms，timers 阶段空过，接着走到 check 阶段先打印 immediate。机器负载、启动时加载的模块数量都会改变这个结果。

而在任何 IO 回调内部注册时，顺序是确定的：IO 回调运行在 poll 阶段，本轮的下一站就是 check，所以 setImmediate 一定先于 setTimeout 执行。结论很实用：不要让业务逻辑或单元测试依赖这两者的相对顺序，需要「给 IO 让路」就用 setImmediate，需要「同步代码结束后立刻」就用微任务。

poll 阶段阻塞多久，由最近的定时器决定

libuv 在进入 poll 前会算一个超时值，这个值就是 epoll_wait 的 timeout 参数。理解它，就能解释「为什么空闲的 Node 进程 CPU 是 0% 而不是 100%」，也能解释「为什么加了一个 1ms 的 setInterval 之后进程的系统调用次数翻了几十倍」。

当前状态poll 阻塞时长观测表现
poll 队列非空0，立即处理高负载时 CPU 跑满，延迟由回调本身耗时决定
有 setImmediate 待执行0，直接进 checkimmediate 递归时循环空转，CPU 偏高但 IO 不饿死
只有定时器到最近定时器的剩余毫秒setInterval(fn, 1) 让进程每毫秒醒一次，strace 里 epoll_wait 刷屏

无任何活跃句柄不阻塞，循环退出脚本跑完自然退出；进程不退出说明有句柄没关

libuv 线程池承担什么，不承担什么

这是排查「延迟很高但 CPU 不忙」时最容易漏掉的一层。网络 IO 由内核的 epoll / kqueue / IOCP 直接通知，不占线程；而文件系统操作、dns.lookup、部分 crypto 和 zlib 操作在操作系统层面没有可用的异步接口，libuv 只能把它们丢进线程池里用阻塞方式跑完再回调。线程池默认只有 4 个线程。

推论非常明确：并发 1000 个 fs.readFile，真正同时在跑的只有 4 个，其余全在线程池队列里排队。这时候 CPU 可能只有 20%（线程都在等磁盘），但 p99 延迟已经几百毫秒。同理，用 crypto.pbkdf2 做密码校验时，4 个线程被 CPU 密集的 KDF 占满，同一进程里的 fs 和 dns.lookup 全部跟着排队——这是最隐蔽的相互影响。

症状是否线程池饱和判定方法处理方向
CPU 单核 100%，事件循环延迟直方图 p99 极高不是火焰图里能看到一个平顶的 JS 函数找同步计算，切片或移出主线程
CPU 不高，事件循环延迟正常，但接口 p99 高很可能是统计 fs / crypto / zlib 调用并发量；把并发压到 4 以下看延迟是否线性下降调大 UV_THREADPOOL_SIZE、加并发闸门、改流式读取
CPU 不高，事件循环延迟正常，下游 RT 同步升高不是对比下游调用的客户端耗时与服务端耗时问题在下游或网络
只有域名解析偶发变慢可能是dns.lookup 占线程池，dns.resolve 不占改用 resolve，或在连接层做 DNS 缓存
压缩接口一慢，全站文件读取一起慢是zlib 与 fs 共用同一个池把压缩挪到网关层或独立进程

⚠️
UV_THREADPOOL_SIZE 不是越大越好

上限是 1024。磁盘 IO 密集场景，线程数超过磁盘队列深度后收益归零；CPU 密集的 KDF 与 zlib，线程数超过可用核数后只增加上下文切换和内存（每个线程有独立栈）。容器里更要小心：CPU limit 只有 1 核时把池调到 16，只会让所有请求一起变慢。先压测再定值，常见落点是 8 到 16。容器 CPU 配额与 Node 的关系详见 Node.js 总览。

定时器的精度与漂移

把 setTimeout 当精确定时器用，是另一个高频翻车点。定时器只保证「不早于」设定值触发，不保证「不晚于」。

行为实际表现工程含义
setTimeout(fn, 0)被钳为 1ms不存在 0 延迟定时器，想「尽快且让路」用 setImmediate
延迟上界没有上界，等于「1ms + 当轮剩余阶段的全部耗时」一次 300ms 的同步计算会让所有定时器整体推迟 300ms
setInterval 的节拍回调超时不会堆积补偿，而是丢拍需要固定节拍的任务要自己对齐墙上时钟
延迟超过 2147483647ms溢出为 1ms 并输出警告算出来的「30 天后执行」会立刻执行，长延迟必须分段
unref() 后的定时器不再算活跃句柄后台轮询定时器要 unref，否则进程无法自然退出

怎么知道事件循环被拖住了

一句结论：事件循环延迟是 Node 服务最重要的单一健康指标，比 CPU 使用率更早、更准确地反映问题，因为线程池排队和下游阻塞不会体现在 CPU 上，而任何形式的主线程阻塞都会立刻体现在延迟直方图上。采集方式用 perf_hooks.monitorEventLoopDelay，告警阈值量级、直方图 p99 的判读、以及火焰图和堆快照的配合方法，详见 Node.js 性能诊断；单线程模型的适用边界、容器里的 CPU 配额与进程模型，详见 Node.js 总览。

❌
最容易踩的坑

1. 以为微任务每轮清空一次，写出递归 nextTick，进程假死且从堆栈里看不出异常。

2. 在主模块里用 setTimeout 与 setImmediate 的相对顺序写单测，CI 机器负载一变就随机失败。

3. 用 setTimeout(fn, 0) 做任务切片，每片白等 1ms，十万次切片凭空多出 100 秒。

4. 在请求路径里调 crypto.pbkdf2 却不限并发，线程池被 KDF 占满，同进程的文件读写和域名解析一起变慢。

5. 在代码里给 process.env.UV_THREADPOOL_SIZE 赋值，但依赖早在 require 阶段就触发了 fs 操作，池已按 4 初始化，改动无效。

6. 容器 CPU limit 是 1 核却把线程池调到 32，上下文切换开销吃掉全部收益。

7. 用 dns.lookup（占线程池）而不是 dns.resolve（不占），高并发下域名解析成为隐形瓶颈。

8. 忘记给后台轮询定时器 unref()，优雅关闭时进程迟迟不退出，最后被强杀。

9. 算出一个超过 24.8 天的延迟传给 setTimeout，溢出后立刻执行，业务逻辑提前触发。

10. 用 setInterval 做定时对账，回调偶发耗时超过间隔，实际执行频率静默降低且没有告警。

11. 只监控 CPU 和 QPS，不监控事件循环延迟，线程池排队和单次长阻塞完全看不见。

12. 把 zlib 压缩和高并发文件读放在同一个进程里，两者抢同一个线程池，互相拖慢却查不到关联。
