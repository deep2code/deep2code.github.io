NestJS 架构模型与取舍：DI、请求生命周期与装饰器的代价

🏷️ NestJS

NestJS 的本质是一句话：把 Spring 那套 IoC 容器、依赖注入和模块化边界搬到了 Node。它没有发明新的运行时能力，默认情况下底层还是 Express（可换 Fastify 适配器），它带来的全部价值是「约定」——把一个中大型团队在 Express 项目里迟早要自己长出来的分层、DI、统一校验与错误处理，提前固化成框架能力。相应地，它的代价也全部来自这层约定：编译链依赖装饰器元数据、启动要扫描模块图、打包体积更大、上手门槛更高。这篇讲清它的执行模型和这些代价具体贵在哪。

💡
这篇怎么读

  • ② 原理：七个构件的归属与执行时机、一次请求里 Guard 与 Interceptor 与 Pipe 的真实顺序、DEFAULT 与 REQUEST 作用域的代价、装饰器元数据反射对编译工具链的硬约束、ValidationPipe 每个选项的安全含义、模块边界该怎么划。
  • ③ 场景：什么项目形态下这套约定能回本、什么形态下纯粹是负担，以及九条反模式各自的症状、后果与修法。

① 用法 · 最小可用骨架与「要做什么 → 写在哪一层」

NestJS 的上手成本不在语法，而在「这几个文件各写什么、哪几行不写就会在生产上出问题」。下面这份骨架是一个能跑起来的单领域服务：一个业务模块、一个 provider、一个 controller、一份带校验的 DTO、一个全局异常过滤器，再加上 main.ts 里必须显式配置的四件事。注释只说明为什么要这么写，机制解释全部留给原理层。

# 脚手架与按领域生成一组文件（controller、service、module、dto 一次生成）
npx @nestjs/cli new order-api
npx nest generate resource order

# ValidationPipe 自身不含校验实现，这两个包必须装，否则 DTO 上的装饰器不起作用
npm i class-validator class-transformer

# 默认用 tsc 编译；大项目换 SWC 提速，但它只转译不做类型检查，
# 所以 CI 里这两条必须同时存在，少一条类型错误就会一路进生产
npx nest build --builder swc && npx tsc --noEmit
// 省略 import：@Module / @Controller / @Injectable / @Body / @Post / @Catch /
// HttpException / ValidationPipe / ArgumentsHost 来自 @nestjs/common，
// NestFactory 来自 @nestjs/core，IsString 等来自 class-validator，Type 来自 class-transformer

// ---- create-order.dto.ts：校验规则只写在 DTO 上，Controller 里一个 if 都不该有 ----
export class CreateOrderDto {
  @IsString() @Length(1, 64)
  sku!: string;                 // strictPropertyInitialization 下必须加 !，否则编译不过

  @Type(() => Number)           // query 与 form 里都是字符串；这行只在 transform 打开时才执行
  @IsInt() @Min(1) @Max(999)
  quantity!: number;
}

// ---- order.service.ts：领域逻辑与事务边界在这一层，它不认识 HTTP ----
@Injectable()
export class OrderService {
  create(userId: string, dto: CreateOrderDto) {
    // 返回视图对象而不是 ORM 实体：数据库字段改动不会直接击穿接口契约
    return { id: 'o_1', userId, sku: dto.sku, quantity: dto.quantity };
  }
}

// ---- order.controller.ts：只做协议转换 ----
@Controller('orders')
export class OrderController {
  // 构造函数注入，类型本身就是 token，不需要写 @Inject
  constructor(private readonly orders: OrderService) {}

  @Post()
  create(@Body() dto: CreateOrderDto) {
    // 直接 return 领域结果，让框架去序列化；不要在这里碰 res、也不要拼响应结构
    return this.orders.create('u_1', dto);
  }
}

// ---- order.module.ts：一个业务领域一个模块 ----
@Module({
  controllers: [OrderController],
  providers: [OrderService],
  exports: [OrderService],      // 只导出别的领域真的要用的那几个，这就是本模块的公开 API
})
export class OrderModule {}

// ---- app.module.ts：根模块只做装配，不放业务 provider ----
@Module({ imports: [OrderModule] })
export class AppModule {}

// ---- all-exceptions.filter.ts：全站唯一的错误出口 ----
@Catch()
export class AllExceptionsFilter implements ExceptionFilter {
  catch(err: unknown, host: ArgumentsHost) {
    const res = host.switchToHttp().getResponse();
    const isHttp = err instanceof HttpException;
    const status = isHttp ? err.getStatus() : 500;
    res.status(status).json({
      // 前端按 code 分支，不要让它去匹配 message 文案
      code: status >= 500 ? 'INTERNAL_ERROR' : 'BAD_REQUEST',
      message: status >= 500 ? 'internal error' : (err as HttpException).message,
    });
  }
}

// ---- main.ts：这四件事必须显式写，少一件都会在生产上出问题 ----
async function bootstrap() {
  const app = await NestFactory.create(AppModule);
  app.useGlobalPipes(new ValidationPipe({
    whitelist: true,              // 未声明字段直接剥掉：这是安全项，不是代码洁癖
    forbidNonWhitelisted: true,   // 多余字段直接 400，契约错位在联调期就暴露
    transform: true,              // 不开这行 @Type 不执行，quantity 拿到的还是字符串
  }));
  app.useGlobalFilters(new AllExceptionsFilter());
  app.enableShutdownHooks();      // 不写这行，SIGTERM 时 onModuleDestroy 根本不会执行
  await app.listen(3000);
}
bootstrap();

骨架跑起来之后，日常开发里真正反复出现的问题只有一个：这段代码该放哪一层。按下表查，右列是放错层之后会付的代价。

要做什么写在哪一层注意什么
加一个接口Controller 加方法加 DTO，业务写进 ServiceController 里不写业务分支、不控制事务、不碰 res 对象
参数校验与类型转换规则写在 DTO 装饰器上，由全局 ValidationPipe 执行必须开 transform，否则 @Type 不执行，数字参数一直是字符串
鉴权、权限、租户隔离Guard，用 @UseGuards 挂或全局注册Guard 早于 Pipe，此时拿到的参数还没被校验，别在这里读 DTO 字段
耗时埋点、trace、响应统一包装Interceptor，环绕 handler可以观测异常但必须重新抛出，吞掉之后 Filter 和错误率指标全瞎
统一错误响应一个 @Catch() 的 ExceptionFilter，全局注册5xx 只回 traceId，绝不回显堆栈与内部字段
拿当前用户与 traceId自定义参数装饰器读请求上下文，或 AsyncLocalStorage不要存到单例 Service 的实例字段上，高并发下必然串号
开一个新业务领域新建 module，provider 放在模块内，exports 只放别人要用的不要按技术层次建 ControllersModule 与 ServicesModule，边界会形同虚设
连接池、消费者、定时任务的启停onModuleInit 建、onModuleDestroy 关main.ts 必须调 enableShutdownHooks()，否则关闭钩子不执行
替换时间、随机数、第三方客户端这类不可控依赖自定义 token 加 { provide, useValue } 注入在 Service 里直接 new 出来的对象，测试时没有替换点

下面这张是写 Controller 与 provider 时最常查的一组装饰器与 API。「默认行为」一列指的是不显式配置时框架实际怎么做——NestJS 的默认值普遍偏保守，多数踩坑来自「以为默认已经开了」。

装饰器或 API作用默认行为什么时候需要改
@Module({ imports, controllers, providers, exports })声明这个领域依赖谁、对外公开什么provider 只在本模块内可见别的模块要用就加进 exports；确实全站共用才考虑 @Global()
@Injectable()标记这个类可被注入DEFAULT 作用域，整个进程一个实例只有确实要按请求隔离才传 scope，代价见原理层的作用域表
@Body() / @Query() / @Param()取请求数据拿到的是字符串或 plain object要类型就配 DTO 加 @Type，并确认 transform 已开
@UseGuards / @UseInterceptors / @UsePipes在类或方法上挂横切构件不挂就不生效，作用范围止于被装饰的类或方法全站通用的改成 app.useGlobalGuards 这类全局注册
ValidationPipe执行 DTO 上的校验与转换whitelist、forbidNonWhitelisted、transform 全部为关一律显式打开，逐项后果见原理层的选项表
@Catch() 过滤器接住任意层抛出的异常不注册时返回框架的默认错误体需要稳定的错误契约就全局注册一个，收敛到唯一出口
Reflector读方法或类上的自定义元数据元数据键要自己定义并用装饰器写入免鉴权白名单、权限声明这类「按路由差异化」的逻辑靠它
app.enableShutdownHooks()打开生命周期关闭钩子关只要有连接池、消息消费者或定时任务就必须开
nest build --builder swc换编译器提速默认走 tsc编译慢到影响开发时换，但要显式开元数据发射并另跑 tsc --noEmit

用法层到此结束。为什么 Guard 拿不到校验后的 DTO、为什么不开 whitelist 就是一个越权漏洞、为什么给 provider 随手加 REQUEST 作用域会让压测时的 GC 时间明显上升、为什么换成 esbuild 之后 DI 会在运行时才报错——原因全部在下面几节。

② 原理 · 七个构件的分层与归属

搞清这一层能解决日常最费口舌的那类争论——「这段代码该写在哪」，也能解释为什么放错层之后逻辑就没法被定时任务和消息消费者复用。

NestJS 的构件不多，难点在于「什么代码该放在哪一层」。下图是一个按业务领域组织的典型结构：业务模块内部依赖方向单向（Controller 到 Service 到 Repository），横切关注点全局注册、不属于任何业务模块。

Module启动时扫描依赖边界声明：imports 是我依赖谁，exports 是我对外公开什么业务逻辑；把所有 provider 都堆进 AppModule
Controller请求命中路由协议转换：取参、调 Service、返回领域结果if/else 业务分支、事务控制、手写参数校验、直接访问数据库
Provider（Service）被注入时领域逻辑、事务边界、对外部依赖的编排HTTP 语义（状态码、header、res 对象）；直接返回 ORM 实体
Guard中间件之后、Pipe 之前「能不能进」的布尔判断：认证、角色、租户隔离改写请求体、写业务数据、依赖已校验的 DTO（此时还没校验）
InterceptorHandler 前后环绕耗时埋点、trace 上下文、响应统一包装、缓存短路吞掉异常（会让 Filter 拿不到）；在这里做鉴权
PipeHandler 执行前参数校验与类型转换，声明式规则写在 DTO 上查数据库做唯一性校验（属于业务，放 Service）
ExceptionFilter任意层抛异常后全站唯一错误出口，保证错误契约与 traceId业务补偿逻辑；把 500 的堆栈回显给客户端

② 原理 · 一次请求的真实执行顺序

这个顺序是理解 NestJS 的关键，它决定了很多「为什么拿不到某个东西」的问题。

Interceptor 前置早于校验 所以埋点不能假设参数合法

还有一个容易踩的细节：中间件运行在适配器层（Express 或 Fastify），它比 Guard 更早，也拿不到 Nest 的执行上下文。所以需要读取路由元数据的逻辑（例如按 handler 上的装饰器决定要不要鉴权）只能写在 Guard 里，写在中间件里是拿不到 ctx.getHandler() 的。

② 原理 · DI 与作用域：单例是默认，也应该是终点

先纠正一个流传很广的说法：「NestJS 因为有 DI 所以运行时慢」。DEFAULT 作用域的 provider 是进程级单例，依赖树在启动阶段解析一次，运行期调用等同普通方法调用，没有容器查找开销。NestJS 相对裸 Express 的吞吐差距主要来自默认适配器和装饰器路由的包装层，换 Fastify 适配器能拿回大部分（数字见 Express vs NestJS vs Fastify）。真正昂贵的是作用域用错。

作用域实例数量合理用途代价与坑
DEFAULT（默认）整个进程一份99% 的 Service、Repository、客户端封装不能在实例字段上存请求态数据，会造成跨请求串号
REQUEST每个请求一份，且沿依赖链向上传染确实需要按请求隔离且无法用上下文存储表达的场景，例如按租户动态切换连接依赖它的所有 provider 都被提升为请求作用域，每请求重建一棵子树，GC 压力明显；定时任务、消息消费者里无法注入
TRANSIENT每个注入点一份需要各自持有独立状态的工具类，例如带前缀的 logger实例数量随注入点线性增长；容易和单例混淆导致状态丢失

绝大多数用 REQUEST 作用域的真实动机只是「想拿到当前请求的 traceId 和用户」。这件事的正确做法是 AsyncLocalStorage：在中间件或 Interceptor 里 run() 一次，把上下文放进去，所有 provider 保持单例、按需读取。至于循环依赖，forwardRef 能让它跑起来，但它是止血而非设计——出现循环依赖通常说明两个模块的职责边界划错了，更好的解法是抽出共享的下层模块，或把一个方向改成事件通知。模块划分的原则见站内 DDD 相关内容：按业务领域划模块，不要按技术层次划。ControllersModule / ServicesModule / RepositoriesModule 这种结构里，每个模块都要导出全部内容、每个模块都被所有人 imports，模块边界形同虚设。

② 原理 · 装饰器与元数据反射：实现基础，也是全部代价来源

NestJS 的 DI 靠的是 TypeScript 的 emitDecoratorMetadata：编译器把构造函数参数的类型写进 design:paramtypes 元数据，运行时由 reflect-metadata 读出来完成注入。这条链路决定了它对编译工具链非常挑剔。

编译方式能否支持 NestJS 的 DI实际表现与注意点
tsc + experimentalDecorators + emitDecoratorMetadata完全支持，官方默认大项目编译慢是主要抱怨点；strictPropertyInitialization 下 DTO 字段要写 !
SWC（nest build --builder swc）支持编译快一个量级，但必须显式开 decoratorMetadata，且 SWC 不做类型检查，CI 里必须单独跑 tsc --noEmit；路径别名要在 SWC 配置里重复声明一遍
esbuild不支持esbuild 不实现 emitDecoratorMetadata，直接用会让 DI 拿不到参数类型；只能靠显式 @Inject(TOKEN) 全量标注绕开，成本极高
TypeScript 5 的标准装饰器（Stage 3）不支持标准装饰器没有参数装饰器的元数据发射能力，NestJS 仍然依赖 experimentalDecorators 这套旧语义，两者不能混用
ESM 输出可用但有坑reflect-metadata 必须在任何装饰器求值之前完成导入；配合 ESM 的 mock 与热重载工具链成熟度不如 CJS

另一项代价在打包体积与冷启动：装饰器元数据让静态分析无法判断哪些类真正被用到，tree-shaking 基本失效，再叠加 reflect-metadata 和模块图扫描，一个只有十几个接口的 NestJS 服务打包产物通常比等价 Fastify 服务大数倍，冷启动也慢一截。在 Serverless 场景下这两项都是真实成本。

② 原理 · 横切构件的完整写法：Guard、Interceptor、DTO 与 Controller

用法层那份骨架省掉了鉴权与埋点，这里补齐。看这段代码的重点不是抄，而是理解每个构件「只做自己那一件事」之后，责任边界长什么样。

// ---- Guard：只回答「能不能进」，不写业务，不自己写响应 ----
@Injectable()
export class JwtAuthGuard implements CanActivate {
  constructor(private readonly jwt: JwtService, private readonly reflector: Reflector) {}

  async canActivate(ctx: ExecutionContext): Promise<boolean> {
    // 白名单用元数据声明，别在 Guard 里硬编码 URL 判断
    const isPublic = this.reflector.getAllAndOverride<boolean>(IS_PUBLIC, [ctx.getHandler(), ctx.getClass()]);
    if (isPublic) return true;

    const req = ctx.switchToHttp().getRequest();
    const token = (req.headers.authorization || '').replace('Bearer ', '');
    if (!token) throw new UnauthorizedException('missing token');
    try {
      req.user = await this.jwt.verifyAsync(token);   // 挂上下文，供参数装饰器读取
    } catch {
      throw new UnauthorizedException('invalid token');  // 抛出去，交给 Filter 统一成契约
    }
    return true;
  }
}

// ---- Interceptor：环绕埋点。只观测不吞错误，否则 Filter 拿不到异常 ----
@Injectable()
export class MetricsInterceptor implements NestInterceptor {
  intercept(ctx: ExecutionContext, next: CallHandler): Observable<unknown> {
    const started = Date.now();
    const route = ctx.getClass().name + '.' + ctx.getHandler().name;
    return next.handle().pipe(
      tap(() => metrics.observe('handler_ms', Date.now() - started, { route })),
      catchError((err) => { metrics.inc('handler_error', { route }); return throwError(() => err); }),
    );
  }
}

// ---- DTO：校验规则声明在这里，Controller 里一个 if 都不该有 ----
export class CreateOrderDto {
  @IsString() @Length(1, 64)
  sku!: string;

  @Type(() => Number)              // query 与 param 都是字符串，必须显式转换
  @IsInt() @Min(1) @Max(999)
  quantity!: number;

  @IsOptional() @IsIn(['express', 'standard'])
  shipping?: string;
}

// ---- Controller：只做协议转换，返回领域结果 ----
@Controller('orders')
@UseGuards(JwtAuthGuard)
@UseInterceptors(MetricsInterceptor)
export class OrderController {
  constructor(private readonly orders: OrderService) {}

  @Post()
  create(@Body() dto: CreateOrderDto, @CurrentUser() user: AuthUser) {
    return this.orders.create(user.id, dto);   // 不要在这里拼响应结构，交给 Interceptor
  }
}

② 原理 · 校验与错误契约：whitelist 是安全项，不是洁癖

ValidationPipe 的几个选项直接决定安全边界。不开 whitelist，客户端多传的字段会原样进入 DTO 并流向下游，如果 Service 里有把 DTO 直接展开写库的写法，攻击者提交一个 role 或 isAdmin 字段就完成了越权赋值——这就是批量赋值漏洞。

选项默认值建议值不按建议配的后果
whitelistfalsetrue未声明字段透传到 Service 与 ORM，存在批量赋值越权风险
forbidNonWhitelistedfalsetrue多余字段被静默剥离，前后端契约错位要到线上才发现
transformfalsetrue拿到的是 plain object 而非 DTO 实例，@Type 转换和类方法全部失效
enableImplicitConversionfalse保持 false开了之后非法字符串会被隐式转成 NaN 并通过 @IsNumber 之外的检查，边界更难推理
forbidUnknownValues新版本已为 truetrue为 false 时未注册元数据的对象会被当作校验通过，等于校验被绕过
 
// ---- Filter：全站唯一错误出口，保证错误契约稳定 ----
@Catch()
export class AllExceptionsFilter implements ExceptionFilter {
  catch(err: unknown, host: ArgumentsHost) {
    const http = host.switchToHttp();
    const res = http.getResponse();
    const req = http.getRequest();
    const isHttp = err instanceof HttpException;
    const status = isHttp ? err.getStatus() : 500;

    // 5xx 才打 error 级别日志，4xx 打 info，否则告警会被客户端参数错误刷爆
    if (status >= 500) logger.error({ err, url: req.url, traceId: req.traceId });

    res.status(status).json({
      code: isHttp ? pickBizCode(err) : 'INTERNAL_ERROR',  // 前端按 code 分支，不要按 message 匹配
      // ValidationPipe 抛的是 BadRequestException，message 是数组，摊平成字符串再返回
      message: status >= 500 ? 'internal error' : flattenMessage(err),
      traceId: req.traceId,        // 500 只回 traceId，绝不回显堆栈
    });
  }
}

// ---- main.ts：校验、错误、关闭钩子三件事必须显式配置 ----
const app = await NestFactory.create(AppModule, { bufferLogs: true });
app.useGlobalPipes(new ValidationPipe({
  whitelist: true,
  forbidNonWhitelisted: true,
  transform: true,
  transformOptions: { enableImplicitConversion: false },
}));
app.useGlobalFilters(new AllExceptionsFilter());
app.enableShutdownHooks();   // 不写这行，SIGTERM 时 onModuleDestroy 不会执行，连接池不会优雅关闭
await app.listen(8080);

错误码与响应契约的设计原则见站内 API 设计相关文章；这里只强调一点：错误契约一旦发布就是接口的一部分，把它收敛到唯一的 Filter 里，比散落在各个 Controller 的 res.status(400).json(...) 重要得多。

② 原理 · 模块组织：让 exports 成为领域的公开 API

// 按业务领域划模块：目录结构与模块边界一致，依赖方向单向
@Module({
  imports: [DatabaseModule, LoggerModule],
  controllers: [OrderController],
  providers: [
    OrderService,
    OrderRepository,
    { provide: CLOCK, useValue: () => new Date() },  // 用 token 注入不可控依赖，测试时好替换
  ],
  exports: [OrderService],   // 只导出别的领域真正需要的，这就是本模块的公开 API
})
export class OrderModule {}

// 出现循环依赖时，forwardRef 是止血；更好的解法是把一个方向改成事件
@Injectable()
export class OrderService {
  constructor(
    private readonly repo: OrderRepository,
    private readonly events: EventEmitter2,
  ) {}

  async create(userId: string, dto: CreateOrderDto) {
    const order = await this.repo.insert(userId, dto);
    // PaymentModule 订阅这个事件，于是不需要反向注入 PaymentService，循环消失
    this.events.emit('order.created', { orderId: order.id, amount: order.amount });
    return toOrderView(order);   // 返回视图对象，不要把 ORM 实体直接抛给上层
  }
}

③ 场景 · 什么时候 NestJS 值得，什么时候是负担

前面几节给的是机制与代价，这一节把它们收成判断：先看团队与项目形态，再看部署形态，最后才看接口规模。

偏轻量函数式"| Q3{"是否 Serverless

冷启动与体积是硬约束"] Q3 -->|"否"| Q4{"接口与模块规模"} Q4 -->|"少于 20 个接口"| N3["Express 或 Fastify 直接写"] Q4 -->|"模块多 需要清晰边界"| Y2["NestJS 可行

框架定位约定强度什么时候选它
Express极简中间件链，事实标准几乎没有老项目、中间件生态依赖重、团队自己有成熟约定
Fastify高性能 HTTP 层，内置 JSON Schema 校验与序列化弱（插件与 schema 约定）吞吐敏感的 API、想要校验但不想要 IoC
Hono极轻量、面向多运行时（Node、Bun、Workers）弱边缘函数、Serverless、冷启动与体积优先
NestJS应用架构框架，IoC 加分层约定，可挂 Express 或 Fastify 适配器强人多、模块多、需要长期一致的分层与统一横切能力

上面是「选不选」，下面这张表是「已经在某种形态里了，现在该怎么办」，最后一列是代价，不是好处。

场景该怎么做为什么代价
5 人以上团队，模块数量会持续增加上 NestJS，按业务领域划模块，横切能力全局注册一次约定固化成框架能力，省下的是每次评审都要重讲一遍分层的沟通成本新人要先建立 DI 与装饰器的心智模型；编译链被绑在 experimentalDecorators 这套旧语义上
Serverless 或对冷启动敏感的函数换 Hono 或 Fastify，把分层约定自己维护成一份薄规范模块图扫描与元数据反射发生在启动期，tree-shaking 又基本失效，两项都直接计入冷启动与包体积失去统一的 DI 与横切能力，鉴权、校验、错误契约要自己搭一套并保证团队都照着写
只有十几个接口的内部工具Fastify 直接写，配一份 JSON Schema 约定模块与目录约定的学习与维护成本在这个规模上收不回来项目真长大之后要补分层，返工成本高于一开始就上框架
已有 Express 老项目，想要分层与统一错误先在 Express 里补出分层与唯一错误出口，不要直接重写成 NestJS迁 NestJS 等于同时换 DI、换中间件形态、换编译链，三件事叠在一起没法灰度迁移期两套约定并存，必须给出明确的收敛时间点，否则永远是两套
吞吐敏感，响应体 JSON 很大换 Fastify 适配器，或直接用 Fastify 并启用 schema 序列化NestJS 与裸框架的差距主要在默认适配器与装饰器路由的包装层，不在 DI少数直接操作 Express res 的中间件要重写；序列化 schema 要额外维护
需要按请求或租户隔离上下文AsyncLocalStorage 存上下文，provider 全部保持单例REQUEST 作用域会沿依赖链向上传染，每个请求重建一棵子树每个入口（HTTP、定时任务、消息消费者）都要各自 run() 一次，漏一个就读不到上下文
同一套领域逻辑要同时服务 HTTP、定时任务与消息消费逻辑全部放 Service，三个入口各写一层薄适配写在 Controller 里的业务无法被非 HTTP 入口复用，单测还被迫起 HTTP事务边界要重新界定在 Service 上；幂等性要自己保证，消息入口会重复投递

不适用边界：NestJS 解决不了运行时层面的问题。单线程被同步计算堵住、事件循环延迟、内存增长的定位在 事件循环的六个阶段 与 性能诊断；装饰器元数据依赖的那套编译配置、跨包共享类型、strict 选项的取舍在 TypeScript 工程化；框架之间的中间件模型与吞吐差异在 框架选型；接口契约、错误码与版本策略属于接口设计范畴，见 接口与协议系列。本篇只负责「构件怎么分层、代价贵在哪、什么形态下值得」。

这条路径上，上一篇比较的是各框架的中间件模型与真实开销，本篇把其中「约定最强」的那一端讲透，下一篇转向另一端——把 Web 标准 Request 与 Response 当作唯一抽象、几乎不提供任何约定的轻量框架。

③ 场景 · 反模式对照表

反模式后果正确做法
所有 provider 都注册进 AppModule模块系统等于没用，依赖关系不可见，改一处影响面无法评估按业务领域建模块，用 imports 与 exports 显式声明边界
模块按技术层次划分（ControllersModule / ServicesModule）每个模块都导出全部内容并被所有人 imports，边界形同虚设一个领域一个模块，内部自带 controller、service、repository
用 Scope.REQUEST 只为了拿 traceId依赖链整棵子树每请求重建，GC 压力上升，定时任务里无法注入用 AsyncLocalStorage 存请求上下文，provider 保持单例
Controller 里写业务分支与事务逻辑无法复用到定时任务与消息消费者，单测必须起 HTTPController 只做协议转换，业务与事务边界放 Service
Service 直接返回 ORM 实体数据库字段变更直接击穿到接口契约，还容易把敏感字段（密码哈希、内部状态）泄露出去返回显式的视图对象，字段白名单化
不用 Pipe，在 Controller 里手写 if 校验校验逻辑重复且不一致，错误响应格式五花八门，OpenAPI 文档生成不出来规则写在 DTO 装饰器上，全局 ValidationPipe 统一执行
Interceptor 里 catchError 之后返回兜底值异常被吞，Filter 无感知，错误率指标永远是 0只观测并重新抛出，让 Filter 决定响应
用 forwardRef 绕过所有循环依赖模块边界越来越糊，启动顺序问题随机出现抽共享下层模块，或把一个方向改成事件通知
忘记 enableShutdownHooksSIGTERM 时不走 onModuleDestroy，连接池强断，发布期间报错显式开启，并在 onModuleDestroy 里关连接池与消费者

最容易踩的坑

❌
最容易踩的坑
  • ValidationPipe 不开 whitelist：未声明字段透传，配合「DTO 展开写库」就是批量赋值越权漏洞。
  • 不开 transform 却在 DTO 上用 @Type：拿到的是 plain object，转换根本没执行，quantity 仍是字符串。
  • 以为 Guard 能拿到校验后的 DTO：Guard 早于 Pipe，此时参数还是原始的、未校验的。
  • 把鉴权写在中间件里还想读路由元数据：中间件在适配器层，拿不到 ctx.getHandler()。
  • Interceptor 里吞掉异常返回兜底值：Filter 收不到异常，错误率指标永远是 0，故障静默。
  • 随手给 provider 加 Scope.REQUEST：传染整条依赖链，每请求重建子树，压测时 GC 时间翻倍。
  • 在单例 Service 的实例字段上存当前用户：高并发下必然串号，这是最危险的一类 bug。
  • 用 esbuild 或 TS 5 标准装饰器编译：emitDecoratorMetadata 不生效，DI 在运行时才报「找不到依赖」。
  • 换 SWC 提速后不再跑 tsc --noEmit：SWC 只转译不做类型检查，类型错误会一路进生产。
  • 忘记 app.enableShutdownHooks()：onModuleDestroy 不执行，滚动发布期间数据库连接被强断。
  • 把 ORM 实体直接当响应返回：字段一改接口就变，还容易泄露密码哈希这类内部字段。
  • Serverless 场景直接上 NestJS：模块图扫描加元数据反射让冷启动明显变慢，打包体积也因 tree-shaking 失效而偏大。
