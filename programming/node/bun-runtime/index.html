Bun 运行时机制：JavaScriptCore、原生 API 与 Node 兼容层的边界

把运行时从 Node 换成 Bun，换掉的不只是一个命令，而是引擎、事件循环实现、系统调用封装、调试协议这一整套底座。这篇讲的就是这套底座：JSC 和 V8 差在哪、原生 API 快在哪以及代价是什么、node 兼容层是怎么实现的、边界在哪、怎么验证。工具链用法见 Bun 工具链上手，整体选型判断见 Bun 总览，迁移步骤见 从 Node.js 迁移。

Bun 的内部分层

理解兼容性问题，先要知道你的每一行代码最终走的是哪条路径。Bun 里存在三套并列的 API 表面：Bun 专有 API、Web 标准 API、node 前缀的兼容层，它们最终都落到 Zig 实现的原生层和 JSC 上。选哪一套写代码，直接决定了你还能不能退回 Node。

这里有一个和 Node 的结构性差异：Bun 没有用 libuv，事件循环与 IO 多路复用是自己用 Zig 实现的，直接调 epoll / kqueue。所以「libuv 线程池默认 4 个」「UV_THREADPOOL_SIZE 调大能提升文件 IO 并发」这类 Node 经验在 Bun 上不成立，相关的调优参数也不存在。

JavaScriptCore 与 V8 的差异

维度V8（Node）JavaScriptCore（Bun）工程后果
启动时间初始化开销较大，有快照机制缓解进入执行的路径更短，启动更快CLI、脚本、Serverless 冷启动收益明显；常驻服务无感
JIT 分层Ignition 到 Sparkplug 到 Maglev 到 TurboFanLLInt 到 Baseline 到 DFG 到 FTL长时间运行的热代码上互有胜负，性能结论必须按自己的负载实测
内存特征堆上限可用 --max-old-space-size 精确控制没有同名参数，内存策略由 JSC 决定，只有 --smol 之类的粗粒度开关容器里做内存规划的手段变弱，必须靠压测观察 RSS 曲线
GC分代式，Scavenge 加 Mark-Compact，指标可通过 perf_hooks 观测JSC 自己的回收策略，暴露给用户的可观测指标少「GC 时间占比」这类指标不容易拿到，容量评估更依赖黑盒压测
调试协议V8 Inspector（Chrome DevTools 原生支持）WebKit Inspector 协议Node 生态的调试与分析工具大多不通用
堆快照.heapsnapshot 格式，工具链成熟格式不同，Chrome DevTools 与社区分析工具无法直接读内存泄漏定位难度显著上升
引擎参数大量 --max-*、--trace-* flag多数 V8 专有 flag 不存在启动脚本里照搬 Node 参数会直接报错或被忽略

JIT 分层这件事值得单独看一眼，因为它解释了为什么「微基准跑分」和「线上表现」经常不一致：代码要反复执行足够多次才会被提升到最高优化层，而提升是有前提假设的，假设一旦被打破就会去优化回退。这也是为什么压测必须预热，以及为什么在热路径上写出类型不稳定的对象会让性能忽高忽低。

Bun 原生 API：快，但会锁死退路

Bun 的原生 API 直接落在 Zig 实现上，少了 Node 那层 stream 抽象与 JS 到 C++ 的边界开销，所以在 hello world 级别的对比里能快出倍数。代价必须说清楚：这些 API 在 Node 里不存在，用了它们，你的代码就再也回不去了。

sequenceDiagram autonumber participant CL as 客户端 participant JS as JS 侧代码 participant NT as 原生层 participant OS as 内核 Note over JS,NT: Bun.serve 的路径 CL->>OS: TCP 数据到达 OS->>NT: epoll 通知 原生层直接读取并解析 HTTP NT->>JS: 构造 Request 调用一次 fetch 回调 JS-->>NT: 返回 Response NT-->>CL: 原生层直接写回 socket Note over JS,NT: node:http 的路径 CL->>OS: TCP 数据到达 OS->>NT: 事件通知 NT->>JS: 构造 socket 与 stream 对象 多次触发 data 事件 JS->>JS: 走 stream 状态机与中间件链 JS-->>NT: 通过 stream 写回 分多次跨越边界 NT-->>CL: 响应 
// ---- 这一整段是 Bun 专有 API：性能好，但代码无法在 Node 上运行 ----
import { Database } from 'bun:sqlite';

// 内置 SQLite：无需 npm 依赖，也不需要 node-gyp 编译
const db = new Database('app.db', { create: true });
db.run('PRAGMA journal_mode = WAL');          // 并发读写表现更好
const insertUser = db.prepare('INSERT INTO users (name, pwd) VALUES (?, ?)');
const findUser = db.prepare('SELECT id, name, pwd FROM users WHERE name = ?');

Bun.serve({
  port: 3000,
  // 注意签名：一个请求对应一次 fetch 调用，入参出参都是标准 Web 对象
  async fetch(req: Request): Promise<Response> {
    const url = new URL(req.url);

    if (url.pathname === '/register' && req.method === 'POST') {
      const { name, password } = await req.json();
      // 内置密码哈希，默认 argon2id，省掉 bcrypt 这个需要编译的依赖
      const hash = await Bun.password.hash(password);
      insertUser.run(name, hash);
      return Response.json({ ok: true }, { status: 201 });
    }

    if (url.pathname === '/login' && req.method === 'POST') {
      const { name, password } = await req.json();
      const row = findUser.get(name) as { id: number; pwd: string } | null;
      // 校验失败也走同一条路径，避免用时间差泄露用户是否存在
      const ok = row ? await Bun.password.verify(password, row.pwd) : false;
      return Response.json({ ok }, { status: ok ? 200 : 401 });
    }

    if (url.pathname === '/logo.png') {
      // Bun.file 是惰性引用，不读进内存，由原生层直接零拷贝发送
      return new Response(Bun.file('./assets/logo.png'));
    }

    return new Response('not found', { status: 404 });
  },
  error(err) {                       // 顶层错误兜底，不写这个会直接 500 且无日志
    console.error(err);
    return new Response('internal error', { status: 500 });
  },
});
Bun 原生 API它替代了什么Node 上的对应写法可移植性
Bun.servenode:http 加 Express/Fastifyhttp.createServer，或用 Hono 这类支持多运行时的框架不可移植，除非套一层适配
Bun.filefs.createReadStreamfs.promises 与 stream不可移植
bun:sqlitebetter-sqlite3（需编译）node:sqlite（新版本内置，仍在演进）或 better-sqlite3不可移植，但两边都有替代
Bun.passwordbcrypt、argon2node:crypto 的 scrypt，或 npm 包不可移植
Bun.serve 的 websocket 选项ws 包ws 或 socket.io不可移植，事件回调签名完全不同
Bun.$（内置 shell）zx、execanode:child_process不可移植
Bun.envprocess.envprocess.env（Bun 也支持）可移植：直接用 process.env 就行

如果你希望「先用 Bun 提速，出问题能退回 Node」，写法上的纪律只有一条：只用标准 Web API 和 node: 前缀模块。下面这份等价实现两边都能跑。

// ---- 可移植写法：同一份代码在 Bun 和 Node 22+ 下都能跑 ----
import { createServer } from 'node:http';
import { scrypt, randomBytes, timingSafeEqual } from 'node:crypto';
import { promisify } from 'node:util';
import { readFile } from 'node:fs/promises';

const scryptAsync = promisify(scrypt);

// 用 node:crypto 的 scrypt 做密码哈希，参数显式写出来，别用库的默认值当黑盒
async function hash(password: string): Promise<string> {
  const salt = randomBytes(16);
  const key = (await scryptAsync(password, salt, 64, { N: 16384, r: 8, p: 1 })) as Buffer;
  return salt.toString('hex') + ':' + key.toString('hex');
}

async function verify(password: string, stored: string): Promise<boolean> {
  const [saltHex, keyHex] = stored.split(':');
  const key = (await scryptAsync(password, Buffer.from(saltHex, 'hex'), 64,
    { N: 16384, r: 8, p: 1 })) as Buffer;
  // 必须用恒定时间比较，直接用等号比较会泄露信息
  return timingSafeEqual(key, Buffer.from(keyHex, 'hex'));
}

const server = createServer(async (req, res) => {
  if (req.url === '/logo.png') {
    res.setHeader('content-type', 'image/png');
    res.end(await readFile('./assets/logo.png'));   // 小文件用 readFile，大文件用 createReadStream
    return;
  }
  res.statusCode = 404;
  res.end('not found');
});

// 这行在两个运行时下行为一致，优雅关闭逻辑也可以复用
server.listen(Number(process.env.PORT) || 3000);

node 兼容层的实现方式与当前边界

Bun 的 node:* 模块不是转发给 Node，而是用 Zig 与 JS 重新实现了一遍这些接口的语义。所以兼容性是逐个 API、逐个行为细节堆出来的，「模块存在」和「你用到的那个边缘行为一致」是两件事。下面这张表列的是实践中最常撞上的几处。

能力当前状态撞上时的现象应对
node:fs、node:path、node:buffer、node:crypto覆盖度高偶见冷门参数或错误码差异正常使用，靠测试套件兜底
node:http、node:net、node:stream常用路径可用底层 socket 细节、背压时序、某些事件顺序可能不同把框架层的集成测试跑全，重点测超时与中断路径
node:cluster部分实现多进程负载均衡行为不符合预期改用多容器部署（本来在 K8s 上就该这么做）
node:worker_threads部分支持复杂用法（SharedArrayBuffer 协作、transferList）可能异常把 CPU 密集任务移到独立服务，或先实测
async_hooks / AsyncLocalStorage可用，但复杂异步链路上的上下文传播需实测traceId 在某些异步边界后丢失链路追踪方案必须专门验证，别假设行为一致
node:vm不完整沙箱隔离能力不足或直接抛错用它做不可信代码执行的场景不要迁
native addon（N-API）多数常见包可用，不是全部加载报错，或运行中崩溃迁移前先扫依赖树；不可替代的就放弃迁运行时
node:v8、堆快照 API基本缺失内存诊断工具全线失效把可观测性作为前置条件评估
process.binding 等内部接口不支持老库或 APM 探针直接崩换库，或放弃迁运行时
⚠️
不要用兼容性列表做决策

列表告诉你「node:async_hooks 已实现」，但你真正依赖的是「在 Promise.all 嵌套 setImmediate 之后 AsyncLocalStorage 还能不能拿到上下文」。唯一可靠的验证方式是把你自己的完整测试套件在 Bun 下跑一遍，再在预发环境接真实流量。

# ---- 依赖与兼容性的真实验证流程，顺序不要乱 ----

# 1) 扫 native addon：有 .node 二进制或 gypfile 的包是最硬的阻塞点
find node_modules -name '*.node' -not -path '*/test/*' | head -30
grep -l '"gypfile": *true' node_modules/*/package.json node_modules/@*/*/package.json 2>/dev/null

# 2) 完整测试套件在两个运行时各跑一遍，比对失败用例（不是只看通过率）
bun test 2>&1 | tee /tmp/bun-test.log
npx jest 2>&1 | tee /tmp/node-test.log

# 3) 启动一遍真实服务，重点看启动日志里的告警与缺失模块提示
bun --print 'process.versions' src/main.ts    # 确认 versions 里 node 兼容版本号
bun src/main.ts                               # 关注任何 "not implemented" 类告警

# 4) 同一份压测脚本打两个运行时，对比 p99 与 RSS，而不只是 QPS
npx autocannon -c 50 -d 60 -w 5000 http://127.0.0.1:8080/api/orders/123

# 5) 验证最容易被测试漏掉的三条路径：优雅关闭、定时任务、未捕获异常
kill -TERM $(pgrep -f 'bun src/main.ts')      # 观察是否执行清理逻辑并正常退出

# 6) 确认调试手段可用，否则线上出问题没有抓手
bun --inspect src/main.ts                     # 协议是 WebKit Inspector，不是 V8 CDP

模块系统与全局变量的细节差异

Bun 在模块互操作上比 Node 宽松很多，这是双刃剑：它让老代码更容易跑起来，同时掩盖了真实的模块类型问题，导致「Bun 下正常、切回 Node 就炸」。

细节Node 的行为Bun 的行为想保留双运行时要怎么写
ESM 里 require CJS需要 createRequire允许直接 require按 Node 规则写，用 createRequire 或统一 import
CJS 里 require ESMNode 22.12+ 支持（有顶层 await 时仍失败）宽松允许不要依赖宽松行为，明确项目的模块类型
__dirnameESM 下不存在普遍可用统一用 import.meta.dirname（Node 20.11+）
import.meta.dir不存在Bun 专有不要用，改用 import.meta.dirname
.env 加载不自动加载（需 dotenv 或 --env-file）默认自动加载显式加载，别依赖自动行为，否则线上会缺变量
TS 路径别名运行时不识别，需打包或注册器读 tsconfig.json 的 paths构建产物里把别名解析掉，别让运行时承担
错误堆栈格式V8 格式JSC 格式，行列与帧描述不同日志解析与错误聚合规则要重新验证

可观测性：选型时最容易忽略的短板

前面所有内容都可以靠测试验证，只有这一项不行——它决定的是你在生产出事那一刻有没有抓手。

能力Node 上的常规做法Bun 上的现状建议
商业 APM 探针装 agent 自动埋点探针普遍依赖 Node 内部机制与原生扩展，多数不可用或功能受限迁移前先找供应商确认；没有支持就别迁核心服务
链路追踪OpenTelemetry 自动插桩需实测，自动插桩依赖模块拦截与异步上下文传播优先手工埋关键 span，不依赖自动插桩
CPU 火焰图--prof、0x、Clinic、CDP profiler靠 WebKit Inspector，工具链与产出格式都不同先在预发演练一次「怎么抓火焰图」，别等出事才学
堆快照与泄漏定位--heapsnapshot-signal 加 DevTools 分析格式不通用，社区分析工具基本用不上把 RSS 与自定义业务计数器的长期曲线当主要手段
事件循环延迟perf_hooks 的 monitorEventLoopDelay兼容层可能提供，但语义需实测自己用高频定时器测偏差作为兜底指标
内存上限控制--max-old-space-size 精确限制没有等价参数，只有粗粒度开关靠容器 limit 加压测确定容量，预留更多余量

反模式对照表

反模式后果正确做法
为了性能把 HTTP 层改写成 Bun.serve代码绑死运行时，回退需要重写，退路消失只用标准 Web API 与 node:*，或用支持多运行时的框架抽一层
只看官方兼容性列表就决定迁移列表粒度太粗，真正出问题的是行为细节跑完整测试套件加预发真实流量
把 Node 的启动参数照搬过来--max-old-space-size 这类 V8 flag 不存在，启动失败或被静默忽略重新确定 Bun 下的内存与并发策略，靠压测验证
沿用「调大 UV_THREADPOOL_SIZE」这类经验Bun 不用 libuv，参数无效，问题根因被掩盖按 Bun 自己的实现特征做调优
依赖 Bun 的宽松模块互操作代码在 Bun 下正常，切回 Node 抛 ERR_REQUIRE_ESM 或找不到 __dirname模块风格按 Node 规则写，宽松行为当作兜底而非依赖
依赖 Bun 自动加载 .env本地隐式拿到配置，线上缺变量直接启动失败显式加载环境变量，并在启动时校验必填项
生产上没有可用的 profiling 手段出现内存泄漏或 CPU 打满时只能靠日志猜把「怎么抓火焰图、怎么看内存」在预发先演练通
假设错误堆栈格式一致日志解析规则失效，错误聚合全部散开迁移时同步更新日志解析与告警规则
❌
最容易踩的坑
  • 用了 Bun.serve、Bun.file、bun:sqlite 就等于放弃退路，这些 API 在 Node 下不存在。
  • 把 V8 参数照搬到 Bun：--max-old-space-size 没有等价物，容器内存规划手段随之变弱。
  • 以为 Bun 也用 libuv：它自己实现了事件循环，线程池相关的 Node 调优经验全部失效。
  • 只看兼容性列表：模块存在不代表你用到的那个边缘行为一致。
  • 忽略 node:cluster 只部分实现：依赖它做多进程的服务迁过去会静默退化。
  • 假设 AsyncLocalStorage 行为一致：复杂异步链路上 traceId 可能丢，全链路追踪要专门验证。
  • 依赖里有 native addon 却没提前扫：这是运行时迁移最常见的硬阻塞。
  • 没确认 APM 探针支持：上线后没有任何自动埋点数据，等于把可观测性退回到打日志时代。
  • 没演练过怎么抓火焰图与堆快照：JSC 的格式与工具链和 Node 完全不同，出事时现学来不及。
  • 忘了 Bun 默认加载 .env：本地跑通不代表线上有那些变量。
  • 错误堆栈格式变了没改日志解析：错误聚合失效，告警变成噪音。
  • 压测不预热：JIT 还在低优化层，测出来的数字既不代表 Bun 也不代表 Node。
