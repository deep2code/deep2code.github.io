Node.js 后端的适用边界：单线程模型的硬约束

🏷️ Node.js

Node.js 在后端的位置其实很清楚：它把「高并发 IO」做到了极致，同时把「CPU 密集」彻底交了出去。所以真正值得花时间搞明白的不是它为什么快，而是它的硬约束在哪、什么业务碰上去会出事。事件循环六个阶段的调度细节请看 Node.js 事件循环，这篇只留一句结论：整个进程里只有一个线程在执行你的 JavaScript，事件循环是一个不断取出就绪 IO 事件并执行回调的循环，任何在回调里长时间不返回的代码都会让这个循环停摆。本文接下来的阻塞清单、进程模型、内存上限、错误处理、可观测性指标，全部是从这一句话推导出来的工程后果。

自查项通过的标准不通过意味着什么
单个请求里业务自己算多久主线程上的同步计算合计在 10ms 量级存在上百毫秒的同步段，就要先把它拆出请求路径，否则并发优势一条都拿不到

连接形态连接多、单连接持续算力需求低（网关、推送、BFF）每条连接都要持续计算时，连接越多越放大单线程瓶颈，换线程模型反而更稳

部署环境能做到一容器一进程，由编排系统负责重启与滚动发布只能裸机自管进程时，要额外准备进程守护、连接 draining 与日志切分
团队能力有人能讲清 Promise 的调度顺序，并愿意开 TypeScript 严格模式直接否决。技术栈很少是瓶颈，人才是

启动参数的定式如下，这段可以直接抄进 Dockerfile 的 CMD：

# 容器内存 limit 2Gi、CPU limit 1 核时的最小可用启动配置
NODE_ENV=production \
UV_THREADPOOL_SIZE=8 \
node --max-old-space-size=1400 \
     --heapsnapshot-signal=SIGUSR2 \
     server.js
# max-old-space-size 取 limit 的 65%-75%：容器里 V8 读到的是宿主机内存，不显式设就会先被 OOMKilled
# UV_THREADPOOL_SIZE 只影响走线程池的四类操作，和「能跑几个请求」无关，原因见原理层
# heapsnapshot-signal 让线上随时能落堆快照，不用预埋代码、不用重启

# 上线前必须确认这三件事，缺一件都不算就绪
# 1) 堆上限真的落上了：打印 V8 实际生效的上限，单位 MB
node -e "console.log(require('node:v8').getHeapStatistics().heap_size_limit / 1048576)"

# 2) 就绪探针真的存在且能反映事件循环状态，而不是永远返回 200
curl -sS -o /dev/null -w 'readyz=%{http_code} time=%{time_total}\n' http://127.0.0.1:8080/readyz

# 3) SIGTERM 真的走优雅关闭：本地发信号，进程应先让 readyz 失败、再在数秒内自己退出
kill -SIGTERM $(pgrep -f 'node server.js')

剩下的是那几个「撞上就出事」的硬约束。默认值随版本变化，所以第三列给的是确认方式而不是写死的数字：

约束现状怎么确认撞上之后的表现
执行 JavaScript 的线程数恒为 1，不可配置无需确认，这是模型本身任何同步计算都是全局停顿，耗时原样加到所有在途请求
libuv 线程池大小默认 4，进程启动后不可改UV_THREADPOOL_SIZE 环境变量，只能在启动前设并发文件 IO、DNS、异步 bcrypt 在线程池里排队，表现为 IO 延迟随并发线性上涨
V8 老生代堆上限随版本与可用内存推算，容器里推算依据是宿主机内存require('node:v8').getHeapStatistics().heap_size_limit 的输出为准堆溢出退出，或容器先被 OOMKilled（退出码 137，JS 侧无日志）
单进程能用的 CPU一个核os.availableParallelism() 只看 CPU 亲和性，不读 cgroup quota，不能当配额用多核机器上不多进程就浪费算力；反过来进程数超配额会触发 CFS 限流
未处理的 Promise rejectionNode 15 起默认终止进程看启动参数里有没有 --unhandled-rejections 覆盖一个 fire-and-forget 的埋点上报失败就能把整个服务打挂
stdout 写入是否同步指向文件时同步，指向管道或 TTY 时行为不同看容器里 stdout 的实际目标与 process.stdout.isTTY日志量大时写日志本身成为阻塞源，事件循环延迟与日志量同步起伏

② 原理 · 单线程加非阻塞 IO 换到了什么，代价是什么

搞清这一节能解决一个日常判断：面对某个 API 调用，你能直接说出它会不会阻塞事件循环。

传统 thread-per-connection 模型里一个连接对应一个线程，Linux 上线程栈默认 8MB（ulimit -s 通常显示 8192），一万个连接光虚拟内存就要 80GB，再叠加上下文切换与调度器压力，几千并发就是天花板。Node 的做法是一个连接只占一个 fd 加一个几 KB 的 JS 对象，所有连接共享同一个事件循环线程，十万级空闲长连接的内存开销在几百 MB 量级。API 网关、BFF 聚合层、WebSocket 推送这些场景的全部优势就来自这一点。

代价非常直接：这个唯一的线程同时也是执行业务代码的线程。一次不让出控制权的同步操作，其耗时会原样加到当时所有在途请求的延迟上。这不是「性能差一点」，而是「一个请求能打死整个进程」。下面这张图把「代码到底跑在哪个线程上」分清楚——这是判断某个操作会不会阻塞的唯一依据。

flowchart TB subgraph JS["主线程：唯一执行你 JavaScript 的地方"] A1["业务回调与 Promise 链"] A2["JSON.parse 与 JSON.stringify"] A3["同步 fs、同步 crypto、正则回溯、数组排序"] end subgraph POOL["libuv 线程池：默认 4 线程，UV_THREADPOOL_SIZE 可调"] B1["文件 IO，即 fs 的异步版本"] B2["DNS 解析 getaddrinfo"] B3["zlib 与 crypto 的异步版本"] end subgraph OS["内核事件通知：epoll 或 kqueue，不占线程"] C1["TCP 连接的读写就绪"] C2["Unix domain socket"] end A1 --> B1 A1 --> C1 B1 -->|"完成后回调入队"| A1 C1 -->|"就绪后回调入队"| A1 A2 --> D["阻塞点：耗时直接叠加到所有在途请求"] A3 --> D

很多人以为「用了 async/await 就不会阻塞」，这是最常见的误解。await 只对真正交给 libuv 或内核的异步操作有效，一个 await 包着的纯计算函数照样把线程占死。判断标准只有一条：这段代码有没有真的把控制权交回事件循环。注意上图里线程池只服务四类操作，所以调大 UV_THREADPOOL_SIZE 对纯计算和网络 IO 都没有任何帮助。

② 原理 · 一个 CPU 密集请求怎么让另外 1000 个请求同时超时

搞清这一节能解决一类最难定性的故障：错误率整片飙升，但所有监控面板看着都很健康。

这是 Node 服务最典型的生产事故形态，也是最容易误判的一种。注意下图里那 1.8 秒：连接没有断，请求也没有被拒绝，它们只是静静地待在 poll 队列里，等到网关的超时时间先到。

② 原理 · 进程模型：cluster 还是每核一个容器

搞清这一节能解决「明明扩了副本但延迟没降」和「worker 挂了却没人发现」这两类问题。

单个 Node 进程只能用满一个核，所以多核机器上必须跑多份。历史标准答案是 cluster 模块（主进程 fork worker，共享监听 fd，由内核或 round-robin 分发连接），但在容器编排环境下这个答案已经过期了。

维度cluster 模块（单容器多 worker）每核一个容器（单容器单进程）
CPU 配额感知os.cpus() 返回宿主机核数，不读 cgroup quota，极易 fork 过多 worker 并触发 CFS 限流（os.availableParallelism() 也只考虑 CPU 亲和性）Pod 的 request 与 limit 就是这个进程的全部资源，配比一目了然
内存上限N 个 worker 共享容器 limit，堆上限要除以 N 来配，极易算错一个进程独占，堆上限直接按 limit 的 70% 配
故障隔离worker 崩溃对编排系统不可见，容器状态还是 Running，流量照进进程退出等于容器退出，重启次数、退出码、事件全部进可观测体系
指标归属所有 worker 指标混在一个 Pod 里，事件循环延迟被平均掉，看不出是哪个 worker 卡了每个实例指标独立，卡住的实例一眼可见
弹性伸缩HPA 只能扩 Pod，Pod 内 worker 数固定，伸缩粒度粗且失真HPA 直接按 CPU 或自定义指标扩副本，粒度就是一个进程
滚动发布需要自己实现 worker 逐个重启与连接 draining编排系统的滚动更新、就绪探针、preStop 天然可用
适合场景裸机或单台 VM 上自己管进程；本地压测Kubernetes、ECS 等一切编排环境的默认选择
⚠️
在 K8s 上不要再叠 cluster

「一个 Pod 限 2 核，里面 cluster fork 了 os.cpus().length 也就是宿主机的 64 个 worker」是真实会发生的配置。结果是 64 个进程抢 2 核配额，每个进程各自持有 V8 堆、连接池和定时器，内存翻几十倍、上下文切换暴涨、下游连接数被打爆。如果历史代码里已经有 cluster，至少要把 worker 数改成读环境变量并在容器里显式设成 1。

② 原理 · 内存约束：堆上限必须按容器 limit 配

搞清这一节能解决那个最讨厌的现象：容器被杀了，退出码 137，但应用日志里一行异常都没有。

V8 的老生代堆有硬上限。Node 12 之前 64 位下默认约 1.5GB；Node 12 之后改成按可用内存推算，但在容器里它读到的是宿主机内存，不是 cgroup limit，所以生产环境必须显式指定 --max-old-space-size（单位 MB）。这和 JVM 早年不感知容器内存是一模一样的坑，后果也一样：被 OOMKilled，退出码 137，日志里连一条 JavaScript heap out of memory 都没有。

关键是别把堆上限设成等于 limit。RSS 等于老生代堆 加 新生代两个 semi-space 加 代码与元数据 加 堆外内存（Buffer、原生模块、TLS 会话、zlib 缓冲）。Buffer 完全不在老生代里，一个大量转发文件的服务堆外可能比堆还大。经验配比是堆上限取 limit 的 65%-75%：limit 512Mi 配 320、1Gi 配 700、2Gi 配 1400、4Gi 配 2800。

# 容器 limit 为 2Gi 时的典型启动参数
node --max-old-space-size=1400 \
     --max-semi-space-size=32 \
     --heapsnapshot-signal=SIGUSR2 \
     server.js
# max-semi-space-size 调大（默认 16MB）可减少 Scavenge 次数，
# 代价是新生代内存翻倍，只在「短命对象特别多」的服务上才值得调

# 线上怀疑泄漏：发信号直接落堆快照，文件名形如 Heap.<pid>.<seq>.heapsnapshot
kill -SIGUSR2 $(pgrep -f 'node server.js')

# 快速判断是堆内还是堆外在涨：盯 heapUsed 与 rss 的差值走势
node -e "setInterval(function(){console.log(JSON.stringify(process.memoryUsage()))},1000)"

泄漏来源线上表现怎么定位修法
模块级 Map 或对象当缓存且无淘汰heapUsed 单调上涨，重启清零，与累计 QPS 正相关堆快照按 Retained Size 排序，顶部是一个巨大的 Map换成有上限的 LRU（设 max 与 ttl）；或把缓存挪到 Redis
闭包意外持有大对象涨得慢但稳定，常见于「回调里引用了整个请求体」快照里看该对象的 retainers 链，终点通常是某个 timer 或 EventEmitter闭包里只取需要的字段，不要把 req、res、大 Buffer 塞进长生命周期结构
事件监听器未移除出现 MaxListenersExceededWarning，内存随重连次数增长emitter.listenerCount(event) 打点；快照里同名闭包成千上万个用 once；断开路径里成对 removeListener；用 AbortController 统一取消
流未被消费或未被销毁external 与 rss 上涨而 heapUsed 平稳，典型堆外泄漏看 process.memoryUsage() 里的 external 与 arrayBuffers请求中断时显式 destroy()；用 pipeline() 而不是手写 pipe，它会自动清理

② 原理 · 错误处理：三套机制并存的后果

搞清这一节能解决两个高频现象：进程莫名退出，以及错误被吃掉之后在更下游炸出来。

Node 有三套并存的错误传递机制——回调风格的 error-first、Promise rejection、EventEmitter 的 error 事件。混用它们是绝大多数「进程莫名退出」和「错误被吃掉」的根源。

错误形态默认行为版本差异正确处理
async 函数里 throw，调用方既没 await 也没 catch变成未处理 rejectionNode 15 起默认等同 uncaughtException 直接退出进程；之前只打警告所有 handler 外面包一层统一 catch；fire-and-forget 调用必须显式 .catch
EventEmitter 发出 error 但没有监听者直接抛成 uncaughtException各版本一致，最常忘的是 socket 与 stream凡是 stream、socket、连接池都必须挂 error 监听
回调风格 API 的首个 err 参数不检查就静默继续，后面读到 undefined 才报错，堆栈已丢—用 util.promisify 或 node:fs/promises 统一成 Promise，不要手写回调
setTimeout 回调里 throw没有任何调用栈能捕获，直达 uncaughtException—定时任务体整个包在 try/catch 或统一的 async 包装器里
已监听 uncaughtException 并继续运行进程活着，但内部状态不可信—记日志后必须退出，让编排系统拉起新进程
 
// 进程级错误处理与优雅关闭骨架：建议每个服务都有这一段
const http = require('node:http');

let ready = false;          // readiness 探针读这个值
let shuttingDown = false;
const server = http.createServer(route);

// 1) 业务层：async handler 统一包一层，保证 rejection 不会逃出去
function wrap(fn) {
  return function (req, res) {
    Promise.resolve(fn(req, res)).catch(function (err) {
      // 已知业务错误转成响应契约；未知错误只回 traceId，不回显堆栈
      res.statusCode = err.status || 500;
      res.setHeader('content-type', 'application/json');
      res.end(JSON.stringify({ code: err.code || 'INTERNAL_ERROR', traceId: req.traceId }));
      logger.error({ err: err, url: req.url });
    });
  };
}

// 2) 进程级兜底：状态已不可信，只能记录后退出，绝不能继续服务
function fatal(err, origin) {
  logger.fatal({ stack: err && err.stack, origin: origin });
  if (shuttingDown) return;
  shuttingDown = true;
  ready = false;
  server.close(function () { process.exit(1); });              // 不再接新连接，放走在途请求
  setTimeout(function () { process.exit(1); }, 5000).unref();  // 兜底：5 秒没关完就硬退
}
process.on('uncaughtException', function (err, origin) { fatal(err, origin); });
process.on('unhandledRejection', function (reason) { fatal(reason, 'unhandledRejection'); });

// 3) SIGTERM：先让 readiness 失败，等负载均衡摘掉端点，再关连接
process.on('SIGTERM', function () {
  ready = false;            // 让 readyz 立刻返回 503
  shuttingDown = true;
  // 这 5 秒是留给 kube-proxy 或 Ingress 更新 endpoint 的，省掉就会丢请求
  setTimeout(function () {
    server.close(function () { process.exit(0); });
  }, 5000);
});

server.listen(8080, function () { ready = true; });

② 原理 · CommonJS 与 ESM 的现状，以及它怎么影响库选型

搞清这一节能解决引入一个新依赖时的那个问题：这次是改一行 import，还是要动整条构建链。

这件事在 2023 年之前是纯粹的痛苦，现在好了很多但仍有残留。核心变化是 Node 22.12（以及 20.19 的 backport）默认允许在 CommonJS 里 require() 一个同步的 ESM 模块，这一条直接拆掉了「库作者只发 ESM，CJS 用户就用不了」这个死结的大部分。

问题表现现在的解法残留风险
CJS 项目要用纯 ESM 库抛 ERR_REQUIRE_ESM升到 Node 22.12 以上可直接 require；否则改用动态 import()库里有顶层 await 时仍然 require 不了，只能动态 import
双包问题（dual package hazard）同一个库被同时加载成 CJS 与 ESM 两份，instanceof 失效、单例失效、Symbol 注册表分裂库侧用 exports 条件导出并把状态收敛到同一处；应用侧锁定单一入口依赖树里有人 require 有人 import 时依然双份加载
__dirname 在 ESM 不存在抛 ReferenceErrorNode 20.11 以上用 import.meta.dirname 与 import.meta.filename更低版本要用 fileURLToPath(import.meta.url) 兜底
ESM 里没有 require.cache，无法替换模块Jest 的模块 mock、proxyquire 这类库行为异常换支持 ESM 的 mock 方案，或测试层保留 CJS重装饰器、依赖元数据反射的框架在 ESM 下工具链兼容性仍偏弱
包入口声明不全某些打包器解析到错误入口或直接找不到子路径package.json 里同时写 exports 条件导出与 main 兜底只写 exports 会断掉老打包器；只写 main 无法区分 import 与 require

选型上的实际影响：如果项目还在 CJS 且 Node 版本低于 22.12，引入一个纯 ESM 库的成本可能是整条构建链改造，评估依赖时先看它的 exports 字段再决定。新项目直接上 ESM 加 Node 22 LTS，除非你要用重装饰器的框架。模块格式与编译产物的配合方式见 TypeScript 工程化。

② 原理 · 可观测性：事件循环延迟才是核心健康指标

搞清这一节能解决那个致命的盲区：面板全绿、CPU 很闲，用户却在报超时。

如果一个 Node 服务只允许加一个指标，那就是事件循环延迟。理由前面已经给了：单线程跑满一个核，在 8 核机器上整机 CPU 使用率只有 12%，任何基于 CPU 使用率的告警都不会响，而此时所有请求已经在排队。perf_hooks 的 monitorEventLoopDelay 基于 libuv 定时器采样，开销极低，可以常开。

// 事件循环延迟加内存的最小可用采集，接到你的 metrics 上报即可
const { monitorEventLoopDelay } = require('node:perf_hooks');

const h = monitorEventLoopDelay({ resolution: 10 }); // 采样间隔 10ms，小于它的抖动测不出来
h.enable();

setInterval(function () {
  const p99 = h.percentile(99) / 1e6;   // 直方图单位是纳秒，除以 1e6 转毫秒
  const p50 = h.percentile(50) / 1e6;
  const max = h.max / 1e6;
  const m = process.memoryUsage();

  metrics.gauge('nodejs_eventloop_lag_p99_ms', p99);
  metrics.gauge('nodejs_eventloop_lag_p50_ms', p50);
  metrics.gauge('nodejs_heap_used_mb', m.heapUsed / 1048576);
  metrics.gauge('nodejs_external_mb', m.external / 1048576);   // 堆外：Buffer 与原生模块

  // 判读阈值：p99 小于 10ms 健康；10 到 50ms 需关注；超过 100ms 用户可感知；超过 1s 等于不可用
  if (p99 > 100) logger.warn({ msg: 'event loop stalled', p99: p99, p50: p50, max: max });

  h.reset();   // 必须 reset，否则直方图一直累积，分位值会被历史尖峰钉死
}, 10000).unref();

配套地，把 /readyz 做成「事件循环 p99 超阈值就返回 503」，卡住的实例会被自动摘掉流量而不是继续接请求。进程健康状态的完整流转是这样的：

stateDiagram-v2 [*] --> 启动中 启动中 --> 健康: 端口监听成功 readyz 返回 200 健康 --> 延迟升高: 事件循环 p99 超过 100ms 延迟升高 --> 健康: 慢操作结束或被移出请求路径 延迟升高 --> 探针失败: readyz 连续 3 次超时 探针失败 --> 已摘流量: 负载均衡移除该端点 已摘流量 --> 健康: 恢复后重新加入 健康 --> 堆接近上限: heapUsed 超过堆上限的 85% 堆接近上限 --> 频繁GC: 每秒多次 Mark-Compact 事件循环被 GC 占用 频繁GC --> 进程退出: 堆溢出退出 或容器 OOMKilled 退出码 137 健康 --> 优雅关闭: 收到 SIGTERM 优雅关闭 --> [*] 进程退出 --> [*]

怎么把「延迟升高」这个状态定位到具体的代码行——火焰图、堆快照、GC 日志的采集与判读——见 Node.js 性能诊断。

③ 场景 · 什么场景 Node 是最优解，什么场景根本不该选

前面几节是逐条约束，这里收拢成按业务形态的判断：给方案、给理由、也给代价。

Node 最优的场景都有同一个特征：请求耗时的绝大部分花在等下游，业务自身几乎不算东西。典型是 API 网关与聚合层（一个请求扇出 10 个下游再拼装，全程并发等待，线程模型在这里反而笨重）、BFF（同时还吃「前后端同栈、类型定义共享」的红利）、实时推送（几万长连接每连接内存开销极小）、SSR 与中小项目全栈开发（招人与迭代速度都占优）、以及 Serverless（启动在 50-200ms 量级，比 JVM 冷启动有量级优势）。

不该选的场景同样清楚：CPU 密集型处理（图像视频、批量加解密、复杂报表、模型推理）；需要强类型与成熟并发原语的核心领域逻辑（TypeScript 只在编译期存在，运行时拿到的仍是任意 JSON，跨进程边界必须自己做运行时校验，见 TypeScript 工程化）；重度依赖 JVM 或 Go 生态中间件的系统（客户端 SDK 成熟度差距是真实存在的）；以及团队没有 JS 工程能力——最后这条比前三条都致命，技术栈很少是瓶颈，人才是。

场景该怎么做为什么代价
聚合 10 个下游再拼装响应的网关或 BFF用 Node，并发等待全部下游，每个下游都带独立超时耗时几乎全在等 IO，单线程模型在这里是纯收益下游任一变慢都会堆积在途请求，必须配熔断与超时，否则退化成排队
几万长连接的消息推送用 Node，一容器一进程，按连接数扩副本每连接只是一个 fd 加几 KB 对象，内存开销比线程模型低一个量级连接状态分散在多副本，需要外置路由表或消息总线做跨实例投递
报表导出、图像视频处理、批量加解密不要在 API 进程里做：落任务给队列，由独立服务或 Go/Rust 进程处理单核算力就是天花板，一次长计算会拖垮同进程的全部请求接口从同步变异步，要引入任务状态存储与结果通知
核心账务这类强一致领域逻辑换强类型与成熟并发原语的栈，Node 只做接入层TypeScript 的保证只存在于编译期，运行时边界上仍是任意 JSON多一层跨语言调用与契约维护，收益是核心逻辑的错误提前到编译期
冷启动敏感的 Serverless 接口用 Node，减少依赖体积、避免启动时同步 IO启动在百毫秒量级，比 JVM 有量级优势连接池在函数实例间无法复用，数据库连接数会随并发实例数线性增长
需要跑满多核的计算密集批处理要么多进程横向扩，要么直接换栈一个进程只能用一个核，cluster 在编排环境里还会带来配额与可观测性问题横向扩只摊薄总量，单个任务的延迟一点都不会降低
依赖只有 JVM 生态客户端的中间件不要用 Node 直连，加一层稳定的服务或网关社区 SDK 在连接恢复、超时取消、指标暴露上经常不完整多一跳网络与一处运维对象，换来的是故障时有得可查

最容易踩的坑

❌
最容易踩的坑
  • 以为 await 就等于不阻塞：await 一个纯计算函数照样占满线程，只有真正交给 libuv 或内核的操作才会让出控制权。
  • CPU 使用率不报警就以为服务健康：单线程跑满一核，8 核机器整机只有 12%，必须看事件循环延迟 p99。
  • 容器里不显式配堆上限：V8 读宿主机内存推算上限，结果是退出码 137、OOMKilled，JS 侧一行日志都没有。
  • 堆上限配成等于容器 limit：忘了 Buffer 和原生模块在堆外，RSS 一定大于堆，必须留 25%-35% 余量。
  • 指望调大 UV_THREADPOOL_SIZE 提升吞吐：它只影响文件 IO、DNS、zlib、异步 crypto，对网络 IO 和纯计算毫无作用，且启动后不可改。
  • K8s 里叠 cluster：os.cpus() 返回宿主机核数，限 2 核的 Pod 可能 fork 出几十个 worker，互相抢配额还打爆下游连接池。
  • 监听了 uncaughtException 然后继续跑：此时锁没释放、事务没回滚、对象半初始化，后续的数据错误比直接崩溃难查十倍。
  • fire-and-forget 调用不加 .catch：Node 15 之后未处理 rejection 默认终止进程，一个埋点上报失败就能把服务打挂。
  • stream 和 socket 不挂 error 监听：EventEmitter 的 error 事件没有监听者会直接抛成 uncaughtException。
  • 收到 SIGTERM 立刻 server.close()：负载均衡还没摘掉端点，这段时间进来的请求全部失败，必须先让 readiness 失败再等几秒。
  • 用 setInterval 做定时任务且不 unref()：进程无法自然退出，优雅关闭永远等不到结束。
  • 把用户输入直接喂给带嵌套量词的正则：ReDoS 能用 30 个字符让事件循环卡几十秒，这是可被主动攻击的单点。
  • 指标只有服务级没有实例级：多副本下单个实例卡住会被平均值掩盖，面板一切正常但错误率在涨。
