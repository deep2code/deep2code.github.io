Hono 的跨运行时部署：Node、Bun、Deno 与 Workers

「Hono 能跑在所有运行时上」这句话的准确版本是：app.fetch 的函数形状到处一样，但托管它的方式、它能调用的东西、以及进程模型完全不一样。真正的迁移成本不在框架层，而在你写在框架之外的那些假设——有没有文件系统、能不能持有长连接、模块级变量还在不在、日志掉到哪里去了。框架定位与可移植性总览详见站内 Hono 总览篇，路由与上下文机制详见站内 Hono 路由与上下文篇，中间件的平台依赖详见站内 Hono 中间件篇；这篇只谈部署形态本身的差异。

同一个 fetch handler，四种托管方式

Hono 的 app 实例本身带 fetch 方法，签名是 (request, env, executionCtx)。Workers 期望的就是这个形状，所以 export default app 直接成立；Bun 与 Deno 需要把它交给各自的 serve；Node 没有原生的 Request/Response 服务器，必须用 @hono/node-server 做一层双向转换，这层转换是净增成本，也是「Hono 在 Node 上没那么快」的原因。

type Env = {
  // Workers 上这些来自 wrangler 配置的绑定；Node 上这里装的是底层请求响应对象
  Bindings: { DB_URL?: string; KV?: KVNamespace }

const app = new Hono<Env>()

// 配置读取必须集中一处：不同运行时来源不同，业务代码只认这个函数
function readDbUrl(c: { env: Env['Bindings'] }) {
  const fromBinding = c.env?.DB_URL
  const fromProcess = typeof process !== 'undefined' ? process.env.DB_URL : undefined
  const url = fromBinding ?? fromProcess
  if (!url) throw new Error('DB_URL missing')   // 缺配置就让第一个请求失败，别留到半夜命中
  return url
}

Workers 上不存在的那一半标准库

边缘运行时不是「精简版 Node」，它是另一套以 Web API 为主的运行时。nodejs_compat 兼容标志能补回一部分 node: 模块，但它是子集，而且有的模块是能 import 但关键函数不可用——这类问题构建期不报错，线上第一次走到那条分支才炸。

Node 里的做法在 Workers 上的状况替代方案
node:fs 读模板、读证书、写临时文件没有文件系统这个概念，开兼容标志也补不回来模板改成构建期内联；静态资源交平台托管；临时文件改用对象存储
node:net / node:tls 建 TCP 连接不能任意发起原始 TCP；只有平台提供的受限接口改用 HTTP 型数据访问，或平台的连接池代理
node:crypto 的同步哈希与随机数标准 Web Crypto 覆盖大部分需求，但接口是异步的统一用 crypto.subtle，注意它返回 Promise
Buffer 到处传需要兼容标志，且与标准流互转有额外拷贝用 Uint8Array 与 TextEncoder，这套在四个运行时上都在
process.env 读配置没有进程概念，配置在 c.env 里且只在请求内可得配置读取函数化，注册期不要求值
依赖里隐式引用了 Node 内置模块构建期报找不到模块，或运行期报某函数不是函数迁移前先过依赖树，这是最常见的真实阻塞点
AsyncLocalStorage 串上下文需要兼容标志才可用显式把 traceId 放进 Context 往下传，不依赖隐式上下文

限制的是 CPU 时间，不是墙钟时间

这是从常驻服务过来最容易搞反的一条：边缘平台约束的是你的代码真正占用 CPU 的时间，等待 I/O 的时间不计入。所以一个串行调用五个慢下游的函数通常撞不上 CPU 限制，而一个在内存里排序几万条记录的函数会。具体配额随平台与套餐变化，这里只给性质对照。

约束性质什么会撞上它规避写法
CPU 时间只计算执行时间，I/O 等待不计大 JSON 反复序列化、同步加解密、会回溯的正则、内存内排序与聚合重计算搬到常驻服务或队列消费端；正则做长度上限与锚定
总执行时长墙钟计时，含 I/O串行调用一长串下游，或等一个很慢的数据库查询并发化下游调用，给每个下游设超时并降级
单实例内存按 isolate 计，不是按机器计把大响应体或大文件整块读进内存再处理流式透传，不要 arrayBuffer() 整块接
子请求数量一次调用内能发起的外部请求有上限循环里按 ID 逐条查、N+1 式的下游调用批量接口、合并查询、把扇出搬到队列里做
顶层模块执行每个新 isolate 都要执行一次顶层构造大表、解析大 JSON、初始化重依赖顶层只放轻量常量，重的东西懒加载
请求体大小平台侧有上限，早于你的代码生效直接把大文件 POST 到函数上走预签名直传对象存储，函数只处理元数据

模块级可变状态：这是数据泄露，不是渲染问题

常驻 Node 里「模块级变量当进程内缓存」是标准做法。边缘上这个做法的语义完全变了：一个 isolate 会服务大量来自不同用户的请求，模块顶层的变量属于 isolate 而不是请求。把用户 A 的数据写进模块级变量，落到同一个 isolate 的用户 B 就能读到。这不是「缓存没生效」这种轻量问题，而是一次实打实的数据泄露，并且流量小的时候几乎不会暴露——只有 isolate 复用率上来了才开始串。

还有更硬的一层：把某个请求的 c.env 绑定或响应流存进模块级变量，之后在另一个请求里用它发起访问，运行时会直接拒绝并报「不能代表另一个请求执行 I/O」。这个报错看起来莫名，实际是平台在替你挡住跨请求状态复用。

模块级变量存了什么Node 常驻进程上的表现边缘 isolate 上的表现正确做法
当前用户、当前租户、当前请求头并发下也会串，但常被并发低掩盖跨请求串用，直接泄露到别的用户放 c.set，生命周期与请求一致
缓存的查询结果，键里没带身份命中率高，问题隐蔽跨用户返回别人的数据放平台存储，键里必须带身份维度
c.env 绑定的引用没有这个概念下个请求使用时报不能代表另一个请求执行 I/O每次从当前 c.env 取，不缓存
数据库连接或客户端实例正是连接池的正常用法连接无法复用，还可能触发跨请求 I/O 拒绝请求内构造 HTTP 型客户端，见下一节
纯计算得到的不可变结果安全安全，且能省掉每个 isolate 的重复计算这是模块顶层唯一适合放的东西
计数器、限流窗口、幂等表单机可用，多实例就不准每个 isolate 各算一份，完全不可信用 Durable Objects 或外部原子存储

waitUntil、冷启动与 isolate 生命周期

c.executionCtx.waitUntil 的语义常被夸大。它只是把一个 Promise 挂到本次调用的生命周期上，让响应返回之后还能继续执行，但仍然受执行时长与资源约束，没有重试、没有持久化、没有死信，失败了也没人知道。适合它的是丢了无所谓的补充动作：异步埋点、缓存回填、尽力而为的通知。凡业务上必须成功的动作都应该交给队列绑定，由平台负责重试与死信。另外 Node 适配器下根本没有这个句柄，访问即抛错，公共代码必须做能力探测。

冷启动方面要纠正两个直觉。第一，isolate 启动不需要拉容器，所以启动本身很轻，但顶层模块代码按 isolate 执行一次，把重初始化写在顶层等于给每个新 isolate 都上一份税。第二，边缘上「预热」基本没有意义：你无法指定预热哪个地点的哪个 isolate，空闲实例会被回收，上一次请求留下的内存状态不能假设还在。

连接复用在边缘不成立

连接池的前提是「一个长期存活、数量可控的进程」。边缘把这两条都拿掉了：实例分布在很多地点、生命周期短、数量随流量弹性变化、空闲会被回收。结果是池里的连接既无法复用也无法优雅关闭，数据库侧的连接数会被迅速打满——而且这个问题在小流量下完全看不出来，一次推广活动就能把数据库打死。

方案传输方式在边缘上是否成立代价什么时候选它
传统驱动加连接池原始 TCP 长连接不成立，实例短命且数量不可控连接数打满、连接泄漏只在常驻服务里用
HTTP 型数据访问驱动每次查询一个 HTTP 请求成立，无长连接可维护每次查询都有一次 HTTP 开销，没有会话级事务边缘上的默认选择
平台连接池代理函数到代理走平台通道，代理持有真实连接成立多一跳，且仍不能假设会话状态跨请求保留必须用既有关系库、又要部署在边缘
平台原生存储（KV / D1 / DO）平台内部通道成立绑定平台，一致性模型各不相同新项目，且数据模型能对上
边缘只做网关，数据访问回收到常驻服务函数到内部服务的 HTTP成立多一跳回源，失去就近访问的收益已有重资产后端，边缘只承担路由、鉴权、缓存

// 不需要也不应该把它提到模块顶层复用
app.get('/orders', async (c) => {
  const sql = createHttpSqlClient(readDbUrl(c))
  const rows = await sql('select id, total from orders order by id desc limit 20')
  return c.json(rows)
})

// 后台任务的能力探测：Node 适配器下访问 executionCtx 直接抛错，
// 所以不能写成 if (c.executionCtx) 这种判断
function fireAndForget(c: Context, task: Promise<unknown>) {
  try {
    c.executionCtx.waitUntil(task)
  } catch {
    // 常驻进程里退化成普通 Promise，但必须接住拒绝，
    // 否则一个未处理拒绝就可能把进程带下去
    void task.catch((e) => console.error('bg task failed', e))
  }
}

app.post('/events', async (c) => {
  const body = await c.req.json()
  // 必达的动作交队列：waitUntil 不重试、不持久化、失败无声
  await c.env.QUEUE.send(body)
  // 可丢的动作才用 waitUntil
  fireAndForget(c, bumpCounter(c.env, 'events'))
  return c.json({ accepted: true }, 202)
})

KV、D1、Durable Objects 的一致性模型差异

这三个经常被摆在一起比容量和价格，真正该比的是一致性与并发语义。选错的后果不是慢，而是数据算错：用最终一致的 KV 做计数器，并发写就是后写覆盖，丢掉的增量永远找不回来。

存储一致性并发写语义适合的数据绝对不要用它做的事
Workers KV最终一致，写入后全球可见有延迟后写覆盖，没有比较并交换配置、特征开关、读多写极少的映射计数器、余额、库存、任何读改写
D1单主关系库，读副本可能滞后单语句与批量内原子，没有交互式事务有结构、有索引、需要关联查询的业务数据依赖长事务与行锁的流程
Durable Objects每个标识全球单实例，存储强一致请求串行执行，天然有顺序计数器、分布式锁、房间与会话状态、协同状态大吞吐的无状态查询，单实例会成为瓶颈
Cache API按节点各自缓存，节点之间不共享不适用可公开的 GET 响应带身份的响应，除非键里包含身份
对象存储对象级一致整对象覆盖文件、大 payload、导出产物需要局部更新的结构化数据
外部 HTTP 数据库由该服务自身决定取决于服务已有数据资产、需要完整 SQL 能力把它当就近存储用，跨洋延迟会吃掉边缘的收益

可观测性受限之后怎么排查

边缘上最容易被忽略的成本是排查手段的退化：没有进程、没有磁盘、装不了传统 APM 探针、日志还可能被采样。这意味着可观测性必须在写代码时就设计好，而不是出事后再接。

能力常驻 Node边缘运行时替代做法
日志落盘与轮转写文件，随时 grep没有文件系统，console 输出进平台管道实时用 wrangler tail 看，长期靠日志推送到外部存储
日志完整性默认全量可能按比例采样关键路径的日志单独走一条必达通道，不要指望全量
进程指标：内存、GC、事件循环延迟可直接采集没有进程概念只能用平台指标加自埋点，延迟分位数自己算
APM 自动埋点探针劫持模块加载与异步钩子装不上手动在中间件里埋，traceId 显式沿 Context 传
堆快照与 CPU profile随时抓不可用靠缩小输入规模二分定位，把重计算搬出边缘
本地复现同一个进程模型本地跑的是同一运行时内核，但绑定是本地模拟一致性相关的问题必须连真实绑定验证，本地模拟不会重现可见延迟
请求串联AsyncLocalStorage 隐式串需要兼容标志，且跨请求不可复用请求入口生成 traceId，写进 Context 并回写响应头

最容易踩的坑
  • 用模块级变量缓存用户数据：同一个 isolate 服务多个请求，这是跨用户数据泄露而不是缓存失效，小流量下测不出来；存 c.env 或请求派生的流更糟，下个请求使用时会报不能代表另一个请求执行 I/O。
  • 把 CPU 时间限制理解成请求总耗时：慢下游不会撞它，内存里排序和跑回溯正则才会。
  • 顶层解析大 JSON 或构造大表：每个新 isolate 都要重算一次，成本按 isolate 计。
  • 在边缘上建数据库连接池：连接既复用不了也关不掉，一次流量高峰就把数据库连接打满。
  • 把 waitUntil 当消息队列：不重试、不持久化、失败无声，必达任务必须走队列绑定。
  • 在公共中间件里无条件访问 c.executionCtx：切回 Node 适配器后整站 500，必须 try 包一层。
  • 用 KV 做计数器或库存：最终一致加后写覆盖，丢掉的增量找不回来；键上不带身份维度与版本号还会跨用户串数据、schema 变更后只能手工清理。
  • 把一致性模型搞反：D1 没有交互式事务，照 MySQL 长事务思路写必然出错；Durable Objects 单实例串行，当通用数据库用会卡在这一个点上。
  • 指望 Cache API 全球共享：它按节点各自缓存，命中率的估算方式和中心化缓存完全不同。
  • 把大文件 POST 到边缘函数再处理：请求体上限与实例内存两道墙，应该走预签名直传。
  • 迁移前不过依赖树：任意一个包引了文件系统或原始 TCP 相关的 Node 模块，整条链路就被钉回 Node。
  • 指望本地模拟能复现一致性问题：本地绑定是模拟实现，不会重现全球可见延迟与副本滞后。
