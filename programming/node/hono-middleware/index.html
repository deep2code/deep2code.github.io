Hono 中间件的洋葱模型与内置中间件边界

Hono 的中间件签名只有一种：async (c, next) => { /* 请求阶段 */ await next(); /* 响应阶段 */ }。它把两个执行时机压进同一个函数体，于是线上事故的形态也很集中——大多不是业务逻辑写错，而是代码写在了错误的阶段，或者中间件挂在了错误的位置。框架定位与生态取舍详见站内 Hono 总览篇，路由匹配策略与 c.req、c.var 的机制详见站内 Hono 路由与上下文篇，运行时差异详见站内 Hono 跨运行时部署篇；这篇只谈洋葱链的执行顺序、错误传播路径和内置中间件的真实边界。

await next() 两侧是两个不同的世界

执行顺序本身很简单：先注册的中间件先进入请求阶段、最后离开响应阶段，await next() 就是分界线。真正要记的不是顺序，而是两侧能接触到的对象完全不同。请求阶段里 c.res 还不存在，你能改的只有从请求派生出来的状态；响应阶段里路由决策已经完成，c.res 才变得可读可换。

时机c.res 状态这里该做的事这里做不到的事
请求阶段（await next() 之前）尚未赋值，读它就是 undefined鉴权、限流、请求体验签、写入 c.set、记录开始时间改响应头、判断状态码、按响应结果决定是否记日志
短路（直接 return，不调 next()）由本中间件的返回值产生返回 401/403/429、CORS 预检响应内层中间件与处理函数一行都不会执行，内层埋点全是空白
响应阶段（await next() 之后）已赋值，头可改、体要整体替换补响应头、算耗时、按状态码分级打日志改路由决策；异常路径下这段代码可能压根没跑
try/finally 的 finally 块成功路径有值，异常路径可能没有释放连接、归还信号量、减并发计数、必达的指标上报不能假设 c.res 一定存在，取字段前必须判空
流式响应写出第一个字节之后头与状态码已定稿只能往流里继续写数据改状态码、改响应头——不报错，但不生效

短路这条分支值得单独强调：中间件只要 return 一个响应而不调 next()，整条链就在此终止。鉴权、限流、预检响应都靠这个机制工作，但它同时意味着任何注册在内层的埋点、审计、指标统计在短路路径上都是空白。「线上 403 一条日志都查不到」通常就是这么来的——不是日志丢了，是 logger 挂在了鉴权中间件的内层。

忘了 await 的四种症状

next() 返回的是 Promise，不 await 就等于「把下游整条链丢进微任务队列，自己立刻往下走」。响应阶段的代码于是跑在下游之前，此时 c.res 还没有被赋值。Hono 常见的表现是报 Context 未终结或读 c.res 出错，但相当多的写法是静默失效，本地小流量根本发现不了。

写法实际执行顺序线上表现怎么判定
next() 后改 c.res.headers改头跑在 c.res 被赋值之前报读取 undefined 属性，或响应头稳定性缺失抓一批响应看该头是否 100% 缺失，而不是偶发
next() 后算耗时结束时间在开始时间之后几微秒取到所有请求耗时都接近 0，慢接口也不例外看耗时字段的分布是不是全挤在 0-1ms
try { next() } catchcatch 块在 Promise 拒绝之前就已离开下游 500 但告警一条没有，异常被吞成未处理拒绝对比异常计数与 5xx 计数，前者远小于后者
next() 后释放资源下游还在用连接时就被归还或关闭并发一高就间歇性报连接已关闭低并发复现不了，压测时故障率随并发上升

规则可以压缩成一句：只要 next() 后面还有任何一行代码，就必须 await。不需要响应阶段的中间件，写 return next() 就好。

注册顺序与路径写法：鉴权被整段绕过的组合

Hono 的中间件不是「全局钩子」，而是按注册顺序压进匹配链的普通 handler。两条硬规则：中间件必须注册在对应路由之前，写在后面不报错也不生效；路径匹配和路由一样精确，/admin 不包含 /admin/users。这两条加起来就是绝大多数「鉴权中间件明明写了却没生效」的成因。

写法实际生效范围后果
app.use('/admin', auth)只匹配 /admin 这一个路径/admin/users 等全部子路径裸奔，本地点首页看不出问题
app.use('/admin/*', auth)覆盖子路径，但不覆盖 /admin 本身根路径若也返回敏感数据就漏了，两条都要写或改用前缀子应用
app.use(auth) 不带路径等价于通配全部路径健康检查、静态资源、预检请求一起被挡，探针全红
app.get('/admin/x', h) 写在 app.use 之前该路由不经过后注册的中间件不报错、不生效，代码读起来完全正常
子应用内部 app.use('*') 后用 app.route 挂载只作用于子应用自己的路由父应用上同前缀的路由不受保护，前缀重叠时最容易看错
basePath 与 use 的路径写法不一致按拼接后的完整路径匹配本地无 basePath 时正常，线上加了前缀后中间件全部落空
鉴权中间件注册在 CORS 中间件之前鉴权短路的响应上没有跨域头浏览器一律显示跨域错误，真实的 401 被掩盖

排查方法很直接：在鉴权中间件第一行打一条带请求路径的日志，然后对可疑路径直接发请求。日志没出现就是作用范围问题，日志出现了但请求仍被放行就是授权逻辑问题——两类原因的修法完全不同，先分清再动手。

错误传播：HTTPException、onError 与不可依赖的响应阶段

洋葱链靠 await 串联，异常会沿调用栈向上冒泡，不需要 Express 4 那种给每个 async handler 套捕获包装的写法。冒泡出来的异常交给 app.onError，HTTPException 自带响应对象，err.getResponse() 可以直接返回。

两条边界必须记住。第一，notFound 不是错误：没有路由命中时走 app.notFound，不进 onError，想统一响应格式两处都得写。第二，响应阶段的代码在异常路径下不保证执行。把释放连接、归还信号量、上报指标写在 await next() 之后，异常路径上就会漏掉，而这正是「压测时连接池慢慢耗尽、但没有任何报错」的常见成因；这类逻辑必须放进 try/finally。

出错方式谁产出响应onError 是否看到外层响应阶段代码适用场景
throw new HTTPException(400, ...)异常自带的响应看到，可用 getResponse() 直接返回不保证执行，清理放 finally业务主动拒绝，需要统一错误体格式
throw new Error(...)onError 兜底看到不保证执行依赖故障、代码 bug，统一降级成 500
return c.json({...}, 400)当前 handler看不到正常执行参数校验这类高频、不需要告警的拒绝
无路由命中app.notFound看不到正常执行需要单独注册，否则响应体格式与错误路径不一致
中间件自己 try/catch 吞掉异常该中间件看不到，监控上完全隐身正常执行只在确实要降级的地方用，并且必须自己打日志
流式响应写出后在流内部抛错没人，头已发出基本无能为力已经过去了流内部必须自己 try/catch，用数据帧告知客户端出错

import { Hono } from 'hono'
import { HTTPException } from 'hono/http-exception'
import { createMiddleware } from 'hono/factory'

type Env = {
  Variables: { requestId: string; startedAt: number }
}

const app = new Hono<Env>()

// 计时与请求 ID：上报写在 finally 里，而不是 await next() 之后，
// 因为异常路径上响应阶段的代码可能被整段跳过
const observe = createMiddleware<Env>(async (c, next) => {
  const id = c.req.header('x-request-id') ?? crypto.randomUUID()
  c.set('requestId', id)
  c.set('startedAt', Date.now())
  try {
    await next()          // 漏掉 await：下面的 finally 会在下游还没跑完时执行
  } finally {
    // 异常路径下 c.res 可能还没有被赋值，取字段必须判空
    console.log(JSON.stringify({
      id, path: c.req.path, status: c.res?.status,
      cost: Date.now() - c.get('startedAt'),
    }))
  }
})

// 不带路径等于通配全部：健康检查也会被包进来，确认这是你想要的
app.use(observe)

app.get('/orders/:id', (c) => {
  const id = c.req.param('id')
  // 抛 HTTPException 而不是 return：把错误体格式收敛到 onError 一处
  if (!/^[0-9]+$/.test(id)) throw new HTTPException(400, { message: 'invalid id' })
  return c.json({ id, requestId: c.get('requestId') })
})

// notFound 不走 onError，要单独注册，否则两类失败的响应体格式不一致
app.notFound((c) => c.json({ error: 'not_found', requestId: c.get('requestId') }, 404))

app.onError((err, c) => {
  if (err instanceof HTTPException) return err.getResponse()
  console.error('unhandled', c.req.method, c.req.path, err)
  // 不要把 err.message 原样回给客户端，它经常带着连接串或内部路径
  return c.json({ error: 'internal', requestId: c.get('requestId') }, 500)
})

export default app

内置中间件的真实边界

内置中间件的文档都很短，真正需要知道的是它们明确不做什么，以及依赖哪些平台能力——后者决定了同一份代码在 Workers 上能跑、在 Node 上却不行，或者反过来。

中间件实际做的事明确不做的事依赖的平台能力典型误用
logger()打印方法、路径、状态码与耗时不做结构化、不带请求 ID、不脱敏只要有 console当成生产日志方案用，结果日志无法按请求聚合
cors()处理预检、写跨域响应头不做 CSRF 防护，不校验来源合法性之外的任何事无注册顺序靠后，错误响应上没有跨域头
jwt()验签、检查时间声明、写入 jwtPayload不校验签发者、受众、作用域、撤销状态Web Crypto当成完整鉴权，越权照样发生
cache()按请求 URL 读写平台缓存不区分用户身份，不自动失效平台的 Cache API，Node 下没有缓存带鉴权的响应，跨用户串数据
compress()按协商结果压缩响应体不判断内容是否已压缩CompressionStream叠在已由 CDN 压缩的链路上，纯烧 CPU；挂到流式路由上把流缓冲住
etag()算响应体摘要并处理条件请求不能对流式响应工作摘要计算全局挂载后 SSE 与大文件下载全部被缓冲
bodyLimit()超过阈值时拒绝请求体不限制响应体，也不限制总内存无只设了它就以为上传安全了，忽略 multipart 解析仍会进内存
secureHeaders()批量写安全响应头不会自动配出可用的 CSP无默认开启后前端内联脚本被拦，回头把策略整体关掉

cache() 的默认键来自请求 URL，这意味着带鉴权的响应如果不把身份维度放进键、也不设 vary，就会跨用户串数据——这是内置中间件里后果最严重的一种误用，而且在单用户测试下完全不会暴露。compress() 与 etag() 都需要完整响应体，天生和流式输出互斥。

CORS 与 JWT：组合配置最容易错的两个

CORS 的坑不在中间件本身，而在它和错误响应、预检请求、凭据三者的组合。预检请求不携带授权头，如果鉴权中间件挂在了 OPTIONS 也会经过的位置，预检会被 401 掉，浏览器随后报的却是跨域错误。

配置组合浏览器实际行为工程后果
origin: '*' 加 credentials: true直接拒绝，通配来源不允许携带凭据带 cookie 的请求全挂，配置本身不报错
回调里把请求的 Origin 原样返回，并开 credentials请求成功等于向任意站点开放带凭据的接口，是实打实的越权面
鉴权中间件也处理 OPTIONS预检收到 401，主请求不再发出控制台只显示跨域失败，服务端看到的是一堆 401
allowHeaders 漏掉自定义头预检不通过加一个追踪头就全站跨域失败，改动看起来毫无关系
不设 maxAge每个跨域请求前都要一次预检往返跨洋链路上延迟直接翻倍
CORS 注册在鉴权与业务中间件之后错误响应缺跨域头所有 4xx/5xx 都被显示成跨域错误，真实原因被掩盖

JWT 中间件的误用更彻底：它只做验签、检查时间声明、把 payload 塞进上下文，此外什么都不做。签发者、受众、作用域、租户归属、撤销状态全要自己校验。把「挂了 jwt 中间件」当成「接口鉴权已完成」，等价于只验证了「这个令牌是我们签发的、还没过期」，而线上越权事故绝大多数发生在拿到合法令牌之后不校验资源归属这一步。

import { Hono } from 'hono'
import { cors } from 'hono/cors'
import { jwt } from 'hono/jwt'
import { createMiddleware } from 'hono/factory'
import { HTTPException } from 'hono/http-exception'

type JwtPayload = { sub: string; tenant: string; scope?: string }
type Env = {
  Bindings: { JWT_SECRET: string }
  Variables: { jwtPayload: JwtPayload }
}

const app = new Hono<Env>()

// 1) CORS 放最外层：401 与 500 也要带上跨域头，
//    否则浏览器只会报跨域失败，真实状态码在控制台里看不见
app.use('/api/*', cors({
  origin: ['https://app.example.com'],   // 开 credentials 时不能用 '*'，浏览器会直接拒绝
  allowHeaders: ['Authorization', 'Content-Type', 'X-Request-Id'],
  allowMethods: ['GET', 'POST', 'PATCH', 'DELETE', 'OPTIONS'],
  credentials: true,
  maxAge: 600,                           // 不设的话每次跨域请求都多一次预检往返
}))

// 2) 路径必须写通配前缀：写成 '/api' 只保护这一个路径本身
//    secret 放在 c.env 里的运行时（例如 Workers）注册期拿不到值，
//    要把中间件推迟到请求内构造，见下面这层包装
app.use('/api/*', createMiddleware<Env>((c, next) =>
  jwt({ secret: c.env.JWT_SECRET })(c, next),
))

// 3) jwt 只验签，授权是另一件事，必须自己写
const requireScope = (scope: string) => createMiddleware<Env>(async (c, next) => {
  const payload = c.get('jwtPayload')
  const granted = (payload.scope ?? '').split(' ')
  if (!granted.includes(scope)) throw new HTTPException(403, { message: 'forbidden' })
  await next()
})

app.get('/api/orders/:id', requireScope('orders:read'), async (c) => {
  const { sub, tenant } = c.get('jwtPayload')
  // 关键一步：把租户维度写进查询条件。验签通过不代表这条数据属于调用方，
  // 越权几乎都是在这里漏掉的，而不是签名校验被绕过
  const row = await findOrder({ id: c.req.param('id'), tenant })
  if (!row) throw new HTTPException(404, { message: 'not found' })
  return c.json({ ...row, viewer: sub })
})

流式响应与读写响应体的中间件互斥

普通响应里，响应阶段改头改体都来得及；一旦返回的是 hono/streaming 产出的流式响应，状态码与响应头在第一个字节写出时就已经定稿，后面所有中间件的响应阶段修改都无效，而且通常不报错。要区分两类冲突：一类是中间件读写响应体（压缩、摘要、自己拼装 body），它们会把流缓冲起来；另一类是中间件读请求体（验签、审计），它和上传型接口以及 bodyLimit 的组合要小心内存。

组合冲突点现象处理
compress() 加 SSE压缩流需要攒够数据客户端等很久，然后一次性收到全部事件按前缀挂载，避开流式路由
etag() 加大文件下载算摘要要读完整个响应体内存随响应体线性上涨只给小的 JSON 响应挂 etag
响应阶段改头 加 流式响应头已随首字节发出头静默不生效，本地短响应看不出来需要的头在请求阶段用 c.header() 先设好
验签中间件 加 上传接口读请求体等于全量进内存大文件把实例内存打满验签只对小 payload 做，上传走签名 URL 或分片
bodyLimit() 加 parseBody()阈值挡不住解析阶段的内存放大限额之内的 multipart 仍可能吃掉数倍内存阈值按解析后的峰值估，不按原始体积估
中间件读请求体后 handler 再读底层流只能消费一次取决于是否走了包装层缓存一律走 c.req 的方法读，细节见站内 Hono 路由与上下文篇

自定义中间件的类型扩展

中间件往下传值只有 c.set / c.get 一条路，类型则有两种声明方式，选错会让类型在包边界处直接失效。泛型 Variables 是有作用域的：new Hono<Env>() 与 createMiddleware<Env> 必须共享同一个 Env，中间件才能和 app 对上；而 declare module 'hono' 扩展 ContextVariableMap 是全局的，任何 Context 都能取到这个键，代价是丧失作用域约束——适合发布成公共包的中间件，不适合业务内部的临时值。

两个实践细节：createMiddleware 与 createFactory 的价值不只是省类型标注，它们让中间件在被 app.use 之前就完成类型检查，键名拼错当场报错；另外中间件的 Bindings 与 app 的 Bindings 不一致时，报错行号通常指向 app.use 那一行，真实原因却在中间件的泛型声明里，照着报错行改只会越改越乱。

import { Hono } from 'hono'
import { compress } from 'hono/compress'
import { streamSSE } from 'hono/streaming'
import { createFactory } from 'hono/factory'

// 方案 A：泛型声明，作用域清晰，业务代码首选
type Env = {
  Bindings: { JWT_SECRET: string }
  Variables: { userId: string }
}

// 方案 B：全局声明，任何 Context 都能取到这个键。
// 只在中间件要发布成公共包、拿不到调用方 Env 时才用
declare module 'hono' {
  interface ContextVariableMap {
    traceId: string
  }
}

// factory 绑定 Env 一次，之后 createMiddleware / createHandlers 都自动带类型
const factory = createFactory<Env>()

const withUser = factory.createMiddleware(async (c, next) => {
  const uid = c.req.header('x-user')
  // 短路：内层中间件与处理函数都不会执行，这里的日志要自己打
  if (!uid) return c.json({ error: 'unauthorized' }, 401)
  c.set('userId', uid)        // 键没在 Variables 里声明过，这行就是编译错误
  await next()
})

const app = new Hono<Env>()

// compress 要读完整响应体，和 SSE 互斥：按前缀挂，不要用通配全部
app.use('/api/*', compress())

app.get('/events', withUser, (c) => {
  // 流式路由的响应头必须在写出首字节之前设好，
  // 任何中间件在响应阶段改头对这条路由都无效
  c.header('x-accel-buffering', 'no')
  return streamSSE(c, async (stream) => {
    try {
      for (let i = 0; i < 3; i++) {
        await stream.writeSSE({ event: 'tick', data: String(i) })
        await stream.sleep(1000)
      }
    } catch (e) {
      // 头已发出，改不了状态码，只能用一个数据帧告知客户端
      await stream.writeSSE({ event: 'error', data: 'stream aborted' })
    }
  })
})

最容易踩的坑

❌
最容易踩的坑
  • 写了 next() 忘了 await：改响应头、算耗时、外层 try/catch 全部静默失效，低并发下永远发现不了。
  • 把连接释放、信号量归还写在 await next() 之后：异常路径上不执行，表现为连接池被慢慢耗尽且没有任何报错。
  • 作用范围写错：app.use('/admin', auth) 只保护 /admin 本身，子路径全裸；而 app.use 写在路由注册之后不报错也不生效，两种都读不出问题。
  • 把 logger 或审计中间件挂在鉴权内层：所有被短路的 401/403/429 一条日志都没有。
  • CORS 注册顺序靠后：4xx 与 5xx 响应缺跨域头，浏览器一律报跨域，真实状态码被掩盖。
  • origin: '*' 配 credentials: true：配置侧不报错，浏览器侧全挂。
  • 鉴权中间件把 OPTIONS 预检也 401 掉：预检不带授权头，主请求根本发不出去。
  • 以为挂了 jwt() 就鉴权完成：它不校验受众、作用域、租户与撤销，越权基本都出在这里。
  • 给带鉴权的响应挂 cache() 却不把身份写进缓存键：跨用户串数据，单用户测试完全测不出来。
  • 全局挂 compress() 或 etag()：SSE 变成一次性收全、大文件下载内存线性上涨；而首字节写出后再改状态码或响应头，不报错也不生效。
  • 只设 bodyLimit() 就认为上传安全：parseBody() 解析 multipart 时内存还会再放大一截。
  • 中间件与 app 用了两份不同的 Env 泛型：报错指向 app.use 那行，真实原因在中间件声明里。
