Bun 工具链上手：install、run、test、build 的机制与边界

Bun 最值得先用起来的不是运行时，而是工具链：它能在不改一行业务代码的前提下把 CI 的依赖安装和测试时间压掉一大截，而且随时能退回去。这篇只讲工具链——装依赖、跑脚本、跑测试、打包，以及每一项的真实边界。它是什么、能不能上生产见 Bun 总览，引擎与 Node 兼容层见 Bun 运行时特性，整体迁移路径见 从 Node.js 迁移。

安装与版本管理：先把版本锁住

Bun 的迭代速度很快，小版本之间的行为差异是真实存在的，所以第一件事不是装它，而是决定怎么锁它。本地、CI、镜像三处的 Bun 版本必须一致，否则「本地能跑 CI 不能跑」会变成日常。

# 安装（会落到 ~/.bun，记得把 ~/.bun/bin 加进 PATH）
curl -fsSL https://bun.sh/install | bash

# 锁定版本：三种方式按环境选，不要用 latest
curl -fsSL https://bun.sh/install | bash -s "bun-v1.2.21"   # 装指定版本
bun upgrade --stable                                         # 手动升级，不要写进 CI
# package.json 里声明，配合 CI 校验，团队成员一眼能看到该用哪个版本
#   "packageManager": "bun@1.2.21"

# 确认当前版本与构建号（提 issue 或比对性能时必须带上）
bun --version
bun --revision

# 常用命令速查
bun install                 # 装依赖，读 package.json，写/校验 bun.lock
bun install --frozen-lockfile   # CI 专用：锁文件与 package.json 不一致就直接失败
bun add zod                 # 加依赖
bun add -d vitest           # 加 devDependency
bun remove lodash           # 删依赖
bun outdated                # 看哪些依赖有新版本
bun pm ls                   # 看实际装出来的依赖树
bun pm cache rm             # 清全局缓存（怀疑缓存污染时用）
bun run dev                 # 跑 package.json 里的 scripts
bun x prisma migrate dev    # 等价于 npx，临时执行一个包的 bin
bun --bun run vite          # 强制用 Bun 运行时执行这个 bin，而不是 Node
💡
最后一行很关键

bun run <bin> 在执行依赖里的可执行脚本时，如果脚本头部是 #!/usr/bin/env node，默认仍然用 Node 去跑。很多人换了命令却发现性能没变化，原因就在这里。要真正用 Bun 执行，得显式加 --bun（或在 bunfig.toml 里配 [run] bun = true）。

bun install 为什么快，以及快在哪个环节

npm 慢的原因从来不是「JS 写的所以慢」，而是两个具体环节：元数据请求的往返次数和往 node_modules 里逐个文件写入。Bun 对这两处都做了替换。

sequenceDiagram autonumber participant CLI as bun install participant LK as bun.lock participant REG as npm registry participant CA as 全局缓存 ~/.bun/install/cache participant FS as 项目 node_modules CLI->>LK: 读锁文件 已锁定则跳过版本求解 CLI->>REG: 并发批量拉取元数据与 tarball REG-->>CLI: 返回包内容 CLI->>CA: 解压落全局缓存 按内容寻址 CA->>FS: 硬链接或写时复制落地 不逐个拷贝文件 CLI->>LK: 写回锁文件 保证可复现 Note over CA,FS: 省掉的正是最贵的一段
逐文件拷贝与海量 lstat mkdir 系统调用 Note over CLI,REG: 所以冷缓存的 CI 环境收益最大
本地已有完整 node_modules 时差距会明显缩小
环节npm 的做法Bun 的做法收益边界
版本求解解析 package-lock.json，锁定时跳过求解解析 bun.lock，同样跳过求解两者差别不大，不是主要差距来源
网络请求并发度有限，元数据请求多次往返高并发批量请求依赖数量越多、网络 RTT 越高，优势越明显
落地文件逐文件写入 node_modules全局缓存加硬链接或写时复制最大的差距来源；在不支持硬链接的文件系统或跨卷场景下会退化
生命周期脚本逐包执行，串行开销大默认只对信任列表内的包执行 postinstall更快也更安全，但依赖 postinstall 的包需要显式加进 trustedDependencies
缓存命中有 ~/.npm/_cacache，但仍需解压与拷贝缓存内已是解压态，直接链接CI 里把全局缓存目录纳入缓存后，二次构建几乎瞬间完成

注意 trustedDependencies 这一条：Bun 默认不跑非信任包的 postinstall，这在安全上是好事，但会让某些需要下载二进制或生成代码的包（Prisma、Puppeteer、esbuild 之类）安装后行为异常。表现通常是「装完了但运行时报找不到某个二进制」，这时要把包名加进 package.json 的 trustedDependencies 数组。

锁文件格式Bun 版本可评审性怎么迁移
bun.lockb二进制1.2 之前的默认无法 diff，冲突只能重生成用 bun install --save-text-lockfile 转成文本格式后删除
bun.lock文本（JSONC 风格）1.2 起的默认可读可 diff，能正常 review 依赖变更新项目直接用；迁移后记得更新 CI 缓存 key
package-lock.jsonJSON—可读但体积大首次 bun install 会读取它作为版本来源生成 bun.lock，迁移后必须做一次依赖版本 diff

两个锁文件不要同时提交。一旦仓库里同时存在 bun.lock 和 package-lock.json，就一定会有人用错命令，而且没人会第一时间怀疑到这里。

放到 CI 里看，一次 bun install 的状态流转是这样的——注意最后那个分叉，--frozen-lockfile 的价值就在于把「有人改了依赖却没提交锁文件」变成构建失败而不是静默通过：

bun run 与 bun x：省掉的是 Node 的启动开销

npm run 本身就是一个 Node 进程——先启动 Node、加载 npm 自己那堆 JS、解析 package.json，然后才 spawn 你的脚本，这层固定开销通常在一两百毫秒。bun run 是原生二进制直接读 scripts 执行，几乎为零。对于要反复执行的脚本（watch、pre-commit 钩子、批量任务）这个差别很直观。

原来的命令Bun 等价命令差异与注意点
npm installbun install锁文件不同；postinstall 需要 trustedDependencies 授权
npm cibun install --frozen-lockfileCI 必用，防止锁文件被静默改写
npm run devbun run dev快一两百毫秒；脚本内部调用的 bin 仍可能由 Node 执行
npx tscbun x tsc等价，缓存策略不同
node -r ts-node/register app.ts 或 tsx app.tsbun app.ts原生转译，但不做类型检查
nodemon app.jsbun --watch app.ts内置监听重启；--hot 是保留进程状态的热替换，语义不同
jestbun testAPI 大部分兼容，mock 与覆盖率口径有差异
webpack / rollupbun build核心能力可用，插件生态少很多
dotenv 显式加载无需引入Bun 默认自动加载 .env，这是行为差异的高发区

原生 TypeScript：只转译，不检查

这是关于 Bun 流传最广的误解，必须讲清楚：Bun 对 TypeScript 做的是类型擦除式转译，把类型标注删掉直接执行，完全不做类型检查。也就是说下面这段代码在 Bun 下能正常跑：把 string 赋给 number 的参数、调用不存在的方法（只要运行时刚好没走到）、类型不匹配的解构，一律不报错。

所以结论很硬：tsc --noEmit 必须继续留在 CI 和提交前钩子里，它是类型正确性的唯一保证。这一点对 SWC、esbuild 同样成立，它们都是只转译不检查。另外几个 tsconfig.json 相关的实际差异也要知道：Bun 会读 paths 别名（所以路径映射基本可用），但 target、module 这类输出相关选项对它没有意义（它按自己的策略转译），emitDecoratorMetadata 需要显式开启且历史上支持度有过变化——重度依赖装饰器元数据的框架（如 NestJS）在 Bun 下要专门验证，具体见 NestJS 架构模型与取舍 里关于编译链的那张表。

bun test：速度收益明显，边界要先确认

bun test 提供 Jest 风格的 describe / test / expect 与生命周期钩子，多数断言可以直接跑。速度收益来自两点：启动快、转译快，而测试进程本来就是大量短生命周期进程，所以大型套件常能快好几倍。要注意的是能力边界。

能力状态迁移时要做什么
基础断言与生命周期钩子兼容度高基本无需改动
模块 mock机制不同：用 mock() 与 mock.module()重度依赖 jest.mock 自动提升语义的测试需要改写，这是迁移的主要工作量
计时器 mock部分支持依赖假定时器推进逻辑的测试要逐个验证
快照支持基本快照自定义序列化器、内联快照等高级用法支持范围较窄，需实测
覆盖率--coverage 可输出文本与 lcov统计口径与 Jest 不同，质量门禁的百分比阈值必须重新标定基线
DOM 环境无内置 jsdom需要引入 happy-dom 之类的实现并在 preload 里初始化
并发与隔离默认按文件并行共享数据库或端口的测试要显式串行化，否则会随机失败

bun build 与单文件可执行程序

打包能力的核心场景有两个：一是服务端代码打成单个 JS 便于部署，二是 --compile 把运行时一起打进一个可执行文件。后者对 CLI 分发很有价值——用户不需要装 Node，也不会遇到版本不匹配，代价是产物几十 MB 到 100MB 量级（里面内嵌了整个 Bun 运行时）。

参数作用什么时候用
--target=bun产物只在 Bun 下运行，保留 Bun.* API确定不回退到 Node 时；否则用 --target=node
--target=node产出 Node 可执行的代码想保留退路时的正确选择
--compile连运行时一起打成单文件可执行程序CLI 工具分发、需要零依赖运行的场景
--minify压缩产物体积敏感时；调试期建议关掉
--sourcemap=external输出独立 sourcemap线上错误上报必须有，否则堆栈无法还原
--external把某些依赖排除在产物外native addon、体积巨大的可选依赖
--splitting代码分割（仅 ESM 输出）多入口前端产物；服务端通常不需要

bunfig.toml 常用配置

# bunfig.toml 放在项目根目录，和 package.json 同级
[install]
# 私有源：也支持按 scope 分别配置，配合 CI 的 token 注入
registry = "https://registry.npmmirror.com"
# 只装生产依赖（等价于 --production），一般在镜像构建阶段用命令行参数而不是写死在这里
production = false
# 严格按锁文件安装，CI 里更推荐用命令行的 --frozen-lockfile
frozenLockfile = false
# 依赖装到哪，保持默认即可
cache = true

[install.scopes]
# 私有 scope 的鉴权，token 用环境变量注入，不要写进仓库
"@mycorp" = { token = "$NPM_TOKEN", url = "https://npm.mycorp.com/" }

[run]
# 关键项：让 bun run 执行 bin 脚本时也用 Bun 而不是回落到 Node
bun = true

[test]
# 测试前置：注册 DOM 实现、初始化测试数据库连接等
preload = ["./test/setup.ts"]
coverage = true
coverageThreshold = 0.8

[loader]
# 自定义扩展名的处理方式，例如把 .sql 当文本读入
".sql" = "text"

最稳妥的组合：bun 装依赖跑测试，node 跑生产

这套组合把收益最确定的两项（CI 装依赖、跑测试）拿到手，同时完全不碰生产运行时，风险几乎为零，任何时候都能回退。

{
  "name": "order-api",
  "packageManager": "bun@1.2.21",
  "engines": { "node": ">=22.12.0" },
  "scripts": {
    "dev": "bun --watch src/main.ts",
    "test": "bun test",
    "test:cov": "bun test --coverage",
    "typecheck": "tsc --noEmit",
    "build": "bun build src/main.ts --target=node --outdir dist --sourcemap=external",
    "start": "node --max-old-space-size=1400 dist/main.js",
    "ci": "bun install --frozen-lockfile && bun run typecheck && bun test --coverage && bun run build"
  },
  "trustedDependencies": ["prisma", "@prisma/client", "esbuild"]
}
name: ci
on: [push, pull_request]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: oven-sh/setup-bun@v2
        with:
          bun-version: 1.2.21        # 固定版本，绝不写 latest

      # 缓存全局安装缓存，命中后 install 基本瞬间完成
      - uses: actions/cache@v4
        with:
          path: ~/.bun/install/cache
          key: bun-${{ runner.os }}-${{ hashFiles('bun.lock') }}
          restore-keys: bun-${{ runner.os }}-

      # frozen-lockfile：锁文件与 package.json 不一致就失败，防止 CI 悄悄改依赖
      - run: bun install --frozen-lockfile

      # 关键一步：转译不等于类型检查，这一行不能省
      - run: bun run typecheck

      - run: bun test --coverage

      # 生产产物用 node 运行，所以打包目标是 node
      - run: bun run build

      # 镜像里只放 node 运行时，运行时风险为零
      - run: docker build -t order-api:${{ github.sha }} .

反模式对照表

反模式后果正确做法
以为 Bun 跑 TS 就不需要类型检查类型错误一路进生产，TypeScript 的全部价值归零CI 里保留 tsc --noEmit，并作为必过门禁
仓库里同时存在两种锁文件不同人用不同命令，装出不同依赖树，出现只在某台机器复现的 bug只保留一种锁文件，并在 CI 用 --frozen-lockfile 校验
CI 里用 latest 版本的 Bun某天构建行为突然变化，且旧构建无法复现固定小版本，在 packageManager 字段里也写明
直接 bun install 就上线，不比对依赖版本传递依赖被解析成不同版本，行为差异在运行时才暴露迁移时对 bun pm ls 与 npm ls 的输出做一次 diff
忘了配 trustedDependencies需要 postinstall 的包（Prisma、Puppeteer 等）装完却缺二进制把这些包显式加进白名单
用 bun run <bin> 就以为换了运行时带 node shebang 的 bin 仍由 Node 执行，性能毫无变化需要 Bun 执行时加 --bun 或在 bunfig.toml 配 [run] bun = true
迁到 bun test 后沿用旧覆盖率阈值统计口径不同导致门禁误报或漏报先跑一次拿到新基线，再重新设阈值
用 --compile 产物做服务端镜像镜像体积暴涨几十 MB 到上百 MB，拉取变慢服务端用常规打包加官方基础镜像，--compile 留给 CLI 分发
❌
最容易踩的坑
  • 把「Bun 原生支持 TS」理解成「不用类型检查了」：它只擦类型不校验，tsc --noEmit 必须留在 CI。
  • bun run 执行依赖的 bin 时默认仍用 Node：不加 --bun 你以为换了运行时其实没换。
  • 两种锁文件并存：不同成员装出不同依赖树，这是最难定位的一类环境差异。
  • CI 不固定 Bun 版本：小版本升级会带来行为变化，旧构建再也复现不出来。
  • CI 里用 bun install 而不是 bun install --frozen-lockfile：锁文件被静默改写，等于没锁。
  • 缓存 key 没带锁文件哈希：锁文件变了仍命中旧缓存，装出的依赖与预期不符。
  • 从 bun.lockb 迁到 bun.lock 后忘了更新 CI 缓存 key 与 .gitignore：旧二进制锁文件继续生效。
  • 忘了 trustedDependencies：Prisma、Puppeteer 这类靠 postinstall 下载二进制的包会装成半成品。
  • 没注意 Bun 默认自动加载 .env：本地隐式拿到变量，线上没有对应配置就启动失败。
  • 测试并行导致共享资源冲突：默认按文件并行，同一张表或同一个端口的测试会随机失败。
  • bun build 用了 --target=bun 却打算在 Node 上运行：产物里会保留 Bun 专有能力，跑不起来。
  • 打包不出 sourcemap：线上报错堆栈全是压缩后的行号，错误上报平台无法还原。
