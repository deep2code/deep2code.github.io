Hono：Web 标准 API 之上的轻量框架

🏷️ Hono

Hono 的介绍文常常停在「轻、快、Edge 原生」这三个词上。三个词都没错，但都没说清代价。它真正的设计决定只有一条：把 Web 标准的 Request 与 Response 当作唯一的抽象，框架自己不定义请求响应对象。可移植性、体积、跟 Express 完全不同的心智模型、以及它的能力边界，全都是这一条推导出来的结果。

这篇是专题总览：先给能直接跑的最小 app 与四种运行时入口，再讲这条设计决定推导出的机制与取舍。路由匹配与上下文对象的实现细节在 路由与上下文机制，洋葱链与内置中间件边界在 中间件篇，各运行时的部署差异在 跨运行时部署。

💡
这篇怎么读
  • ① 用法：一份最小可用 app（路由、中间件、onError、notFound）加四种运行时的入口写法，一张「哪些代码可移植、哪些必须按运行时分叉」对照表，一张常用 API 与默认行为速查表。
  • ② 原理：把标准 Request 与 Response 当唯一抽象之后必然出现的后果——请求对象只读、响应必须由返回值产生、洋葱链与 Context 的生命周期、Node 适配层为什么是净增成本、可替换路由器与三个入口预设的取舍、类型驱动路由与 RPC 的收益与编译代价。
  • ③ 场景：七类常见失效的症状与修法，以及按部署目标与依赖情况判断该不该用它、不该用时换什么。

① 用法 · 最小可用 app 与四种运行时入口

Hono 的工程结构有一条铁律：app 定义与服务入口分成两个文件。业务代码只 import hono 与标准 Web API，入口文件才允许碰运行时专属模块。这样做不是为了好看，而是因为只有这样才能在不改一行业务代码的前提下换部署目标。下面这份 app.ts 是可直接跑的最小形态。

// app.ts —— 唯一一份业务代码，不 import 任何运行时专属模块
import { Hono } from 'hono'
import { HTTPException } from 'hono/http-exception'

type Env = {
  // Bindings 是平台注入的东西（Workers 下是 KV/D1 之类），不是环境变量，原因见原理层
  Bindings: { API_TOKEN?: string }
  // Variables 是中间件往下传的值，替代 Express 里往 req 上挂属性的写法
  Variables: { requestId: string }
}

const app = new Hono<Env>()

// 中间件必须注册在路由之前，写在后面不报错也不生效
app.use('*', async (c, next) => {
  const id = c.req.header('x-request-id') ?? crypto.randomUUID()
  c.set('requestId', id)
  await next()                            // 漏掉 await，下面这行会跑在响应之前
  c.res.headers.set('x-request-id', id)   // c.res 的头可写；c.req.raw.headers 是只读的
})

app.get('/users/:id', (c) => {
  const id = c.req.param('id')            // 路径参数永远是字符串，框架不做类型转换
  if (!/^[0-9]+$/.test(id)) throw new HTTPException(400, { message: 'bad id' })
  // 必须 return：响应是返回值而不是副作用，漏了会报 Context 未终结
  return c.json({ id, requestId: c.get('requestId') })
})

app.notFound((c) => c.json({ error: 'not_found' }, 404))
app.onError((err, c) => {
  if (err instanceof HTTPException) return err.getResponse()
  console.error('unhandled', c.req.method, c.req.path, err)
  // 不要把 err.message 原样回给客户端，它经常带着连接串或内部路径
  return c.json({ error: 'internal' }, 500)
})

export default app
export type AppType = typeof app          // 给 RPC 客户端用，机制见原理层

import app from './app'

// entry.deno.ts     Deno.serve({ port: 3000 }, app.fetch)
// entry.workers.ts  export default app   // app 自带 fetch，就是平台期望的形状

接下来要回答的是「哪些代码真的能跟着一起搬」。下表按代码类别划分，中间一列是可移植性，右列是用法上应该怎么写才不会把自己钉死在某个运行时；每一项的机制原因在原理层展开。

代码类别可移植性用法上怎么写
路由注册、中间件、Context、校验器完全可移植随便写，这层就是 Hono 的全部价值所在
标准 Web API：URL、Headers、FormData、Web Crypto、TextEncoder完全可移植优先用它们，能用标准 API 就不要用 node: 模块
服务入口与端口监听必须分叉每个运行时一个 entry 文件，app 定义里不出现 serve
配置读取必须分叉封装成一个 readConfig(c)，函数内部同时兜 c.env 与 process.env，业务只调它
静态文件与模板读取必须分叉静态资源交平台托管；模板改成构建期内联，不要运行时读磁盘
数据库访问取决于运行时常驻进程可以用连接池；函数型运行时改用 HTTP 型驱动，细节见 跨运行时部署
响应之后的后台任务必须分叉包一层 fireAndForget：能拿到 waitUntil 就用，拿不到退化成普通 Promise 并接住拒绝
WebSocket 升级与定时任务必须分叉把任务体抽成纯函数，触发方式按运行时各写一遍，没有统一写法
第三方 npm 依赖风险最高的一项迁移前过一遍依赖树：任何一个包引了 node:net 或 node:fs，整条链路就被钉回 Node

常用 API 只有十来个，值得记的是它们的默认行为——Hono 的默认值都很克制，大多数「怎么不生效」都源自以为框架替你做了什么。

API作用默认行为什么时候需要改
app.use(path, mw)注册中间件路径匹配和路由一样精确，/admin 不含 /admin/users；不带路径等于通配全部要覆盖子路径就写 /admin/*；健康检查不想被挡就别用通配
app.route(prefix, subApp)挂载子应用子应用内部的 use 只作用于它自己的路由按领域拆文件时用；RPC 的客户端 base 要跟这个前缀一致
c.req.param() / query() / queries()读路径与查询参数全部返回字符串；query 取单值，queries 取重复参数要数字或布尔就过一层校验器做转换，别手写 Number() 散在各处
c.req.json() / text() / arrayBuffer() / parseBody()读请求体走包装层会缓存，可以换形式再读验签这类要原始字节的场景先读 arrayBuffer()，永远别动 c.req.raw.body
c.json() / c.text() / c.body()构造响应返回值就是响应，函数到此结束需要自定义头时用第三个参数一次性给全，不要事后改
c.set() / c.get() / c.var请求内传值生命周期与请求一致，请求结束即消失要类型就在 Variables 里声明，否则取出来是 any
c.env平台注入的绑定不是 process.env；Node 适配器下装的是底层请求响应对象读配置一律走统一的 config 函数，不要在业务里直接摸它
c.executionCtx平台的调用生命周期句柄平台不提供时访问即抛错，不是返回 undefined公共代码必须 try 包一层做能力探测
app.onError / app.notFound错误与未命中的统一出口洋葱链上任何一层抛错都汇到 onError；未命中不进 onError要统一错误体格式，两个钩子都得注册
HTTPException带响应的业务异常err.getResponse() 可直接返回业务主动拒绝时抛它，而不是散落地 return c.json(..., 400)

用法层到此为止。为什么请求对象是只读的、为什么中间件漏掉一个 await 会让改响应头静默失效、为什么 c.env 在 Node 上装的是另一种东西、为什么换一行 import 就有性能差异——原因全部在下面几节。

② 原理 · 设计前提：只有 Request 与 Response 两个抽象

这一节解释用法层里所有「为什么必须这么写」的源头：请求对象为什么只读、响应为什么必须是返回值、入口为什么要单独成文件。

Express 和 Koa 的 req / res 是对 Node 的 IncomingMessage 和 ServerResponse 的包装，框架的 API 面跟 Node 的 HTTP 实现绑在一起。Hono 的处理函数签名是 (c) => Response：c.req.raw 就是标准 Request，返回值就是标准 Response，app.fetch 本身是一个 (request, env, executionCtx) 形状的函数。整个框架不需要 Node 的任何东西，于是任何实现了「传进来一个 Request、拿回一个 Response」的运行时都能直接托管它。

第一个后果是对象不可变：标准 Request 的 headers 只读，body 是只能消费一次的流，Express 里「往 req 上挂个属性往下传」不成立，要改用 c.set 与 c.get。第二个后果是响应必须一次性构造出来，没有 res.write 写了一半再回头改状态码的空间，流式响应要显式走 hono/streaming。

顺便纠正一个流传很广的说法：Hono 并不是在所有运行时上都「自带性能」。在 Workers、Deno、Bun 上它就是平台期望的那个函数形状，中间没有包装层；而在 Node 上必须由 @hono/node-server 把 IncomingMessage 转成 Request、再把 Response 的 body 写回 ServerResponse，这层转换是净增的成本。体积同理：零依赖、hono/tiny 预设在十几 KB 量级（官方口径约 14kB）对冷启动和打包产物有意义，对一个常驻的 Node 服务几乎没有意义。

② 原理 · 请求生命周期：Context 与洋葱中间件

搞清这一节能解释三类现象：报 Context 未终结、响应头改了不生效、以及 async 异常为什么不需要额外包装就能被捕获。

Hono 的中间件是 async (c, next) => { ...; await next(); ... }，跟 Koa 同构的洋葱模型，不是 Express 的线性 next() 回调。这个差别不只是写法：因为框架层用 await 串联整条链，处理函数里 throw 出来的异常（包括 async 函数里的）天然会冒泡到 app.onError，不需要像 Express 4 那样给每个 async handler 套一层捕获包装（Express 4 不自动捕获 async 异常这件事，详见站内 Node.js Web 框架选型篇）。

几个容易被忽略的生命周期细节：中间件按注册顺序入栈，app.use 必须写在对应路由之前才会生效，写在后面不报错也不生效；await next() 之后才能读到 c.res，此时改 c.res.headers 是有效的，改 body 就要整体替换 c.res；忘了 return 一个 Response、或者中间件忘了 await next()，Hono 会直接报 Context 未终结（大意是「你可能忘了返回 Response 或者忘了 await next」），这句报错基本可以当成这两类错误的专用信号。

② 原理 · 多运行时可移植性的边界

用法层那张表给的是结论，这一节给的是每一格背后的能力差异——真正决定迁移成败的是这些差异，而不是框架 API。

「一套代码到处跑」这句话要拆成两半看：可移植的是你写的框架层代码，不可移植的是运行时能力和依赖。路由、中间件、Context、校验器、以及标准 Web API（URL、Headers、FormData、Web Crypto、TextEncoder）确实一行不改就能跨运行时。而只要某个 npm 包内部引了 node:net 或 node:fs，整条链路就被钉回 Node —— 真正的移植失败几乎都发生在依赖上，不在你自己的代码里。

// runtime.ts —— 把运行时差异收敛到一个文件，业务代码只依赖这里导出的函数
import type { Context } from 'hono'

// 配置来源不同：Workers 走 c.env 的 bindings，Node/Bun/Deno 走进程环境变量
export function readConfig(c: Context) {
  const fromBinding = (c.env as Record<string, string> | undefined)?.API_TOKEN
  const fromProcess = typeof process !== 'undefined' ? process.env.API_TOKEN : undefined
  const token = fromBinding ?? fromProcess
  // 缺配置就让第一个请求直接失败，不要留到某个分支半夜才命中
  if (!token) throw new Error('API_TOKEN missing')
  return { token }
}

// executionCtx 只有 Workers 这类平台会传；Hono 在取不到时是直接抛错而不是返回空对象
export function fireAndForget(c: Context, task: Promise<unknown>) {
  try {
    c.executionCtx.waitUntil(task)
  } catch {
    // 常驻进程里没有 waitUntil，退化成普通 Promise，但必须接住错误，
    // 否则一个 unhandled rejection 就可能把整个进程带下去
    void task.catch((e) => console.error('background task failed', e))
  }
}

② 原理 · 与 Express 的心智模型差异

从 Express 迁过来，真正卡住人的是三件事：响应必须由返回值产生、请求对象只读、错误用抛而不是 next(err)。下表右列写的是差异根因，不是「哪个更好」。

Express 写法Hono 对应写法差异根因
res.json(data) 后继续执行return c.json(data)，函数就此结束响应是返回值，不是副作用
req.user = user 往下传c.set('user', user) 配合 Variables 泛型标准 Request 不可变，且这样才有类型
next(err)throw new HTTPException(状态码, 选项)控制流靠 Promise 拒绝，不靠回调参数
四参数错误中间件app.onError 全局注册一次洋葱链上任何一层抛错都汇到同一处
body-parser 后读 req.bodyawait c.req.json() 或 parseBody()body 是一次性流，Hono 内部做了缓存才允许重复读
req.query.page（可能是数组）c.req.query('page') 单值 / queries('page') 多值显式区分单值与重复参数，少一类隐式类型漂移
express.Router() 挂载app.route('/api', subApp)子应用就是另一个 Hono 实例，类型也能一起带过去
大量 Express 专用中间件必须换成 Hono 版或自己重写对象模型与控制流都不兼容，无法转接

最后一行是迁移评估里权重最大的一项。Express 的中间件生态是它最硬的资产，而这些中间件直接操作 Node 的响应流，没有任何兼容层能无损搬过来。选型时应该先把依赖列表过一遍：如果一半的中间件都得重写，迁移成本会远超预期收益。

② 原理 · 路由匹配器与三个入口预设

这一节回答「换一行 import 为什么会有性能差异」，同时说明为什么不该把它当性能优化手段。

Hono 把路由匹配做成可替换策略，官方的几个入口就是不同策略的预设组合。理解这点是为了按部署形态选对入口，不是为了提升 QPS。

路由器注册开销匹配开销支持全部路由模式该在什么场景用
RegExpRouter高，要把路由编译成少量正则低，且基本不随路由数量线性增长否，少数重叠模式不支持一次初始化、长期复用的服务
TrieRouter低中等，按路径段逐层下降是作为回退实现，保证功能完整
SmartRouter取决于被选中的实现首个请求有一次试探成本，之后固定是，靠回退保证默认选择，不确定就用它
LinearRouter极低随路由数线性增长是每个请求都要重建应用实例的平台
PatternRouter低逐个模式试匹配是产物体积是硬约束的场景
入口内部路由策略体积量级适用部署形态
honoSmartRouter（正则 + 前缀树）默认，最大常驻服务、Workers 这类实例可复用的平台
hono/quickSmartRouter（线性 + 前缀树）中每请求重新初始化的平台，注册成本比匹配成本更重要
hono/tinyPatternRouter最小，十几 KB 量级包体积敏感、路由数量不多的函数

需要纠正的一个直觉：路由匹配在真实服务里几乎从来不是瓶颈。一次请求里的时间绝大部分花在数据库、下游调用和序列化上，路由查找是纳秒到微秒级的事。选预设看的是「实例能不能复用」和「产物多大」这两个工程约束，拿它当性能优化手段基本没有收益。

② 原理 · 类型驱动路由与 RPC 模式

Hono 的类型系统做法是：链式方法每调用一次就把新路由的类型并进返回值的类型里，所以 typeof app 携带了全部路由的方法、路径、输入与输出。客户端 hc<AppType> 拿到这个类型后，调用处的路径拼写、请求体形状、返回值结构全都有编译期检查。

这里有个硬性写法约束：路由必须链式连写。把 app.get(...)、app.post(...) 拆成多条独立语句，类型不会累积，客户端只会看到一个空壳，而且不会报错，只是补全全没了。

// routes.ts —— 必须一路 .get().post() 连写，拆成多条语句类型就丢了
import { Hono } from 'hono'
import { z } from 'zod'
import { zValidator } from '@hono/zod-validator'

const routes = new Hono()
  .post(
    '/posts',
    zValidator('json', z.object({ title: z.string().min(1), tags: z.array(z.string()).default([]) })),
    (c) => {
      const body = c.req.valid('json')   // 已校验，类型直接从 schema 推导，不用手写 interface
      return c.json({ id: 1, title: body.title }, 201)
    },
  )
  .get(
    '/posts/:id',
    // 路径参数是字符串，想拿到 number 必须显式 coerce，否则永远校验失败
    zValidator('param', z.object({ id: z.coerce.number().int().positive() })),
    (c) => {
      const { id } = c.req.valid('param')
      return c.json({ id, title: 'hello' })
    },
  )

export type AppType = typeof routes
export default routes

// client.ts —— RPC 只共享编译期类型，运行时就是一次普通的 fetch

// import type { AppType } from './routes'

// if (res.ok) { const data = await res.json() }   // data 的类型来自 handler 的 c.json

两个要说清的认知问题。第一，Hono 的 RPC 和 gRPC 没有任何关系：没有 IDL、不生成代码、不跨语言、传输层就是 HTTP 加 JSON，客户端和服务端必须共享同一套 TypeScript 类型来源。第二，类型不是运行时保障：客户端的类型再完整，请求也可能来自 curl 或者旧版本的前端，服务端的校验中间件才是唯一防线。

代价也很实在：路由规模上去后，累积类型会明显拖慢编辑器与 tsc，极端情况报类型实例化层级过深。缓解手段是先把 AppType 编译成声明文件再给客户端消费，或按模块拆成子应用分别导出类型；跨包共享类型要开 declaration 与 composite，详见站内 TypeScript 工程化篇。

③ 场景 · 常见失效场景与修法

下面七行覆盖了线上绝大多数 Hono 相关的报障，左列是你看到的现象，按现象查根因比按 API 查文档快得多。

症状根因修法
报 Context 未终结处理函数忘了 return，或中间件忘了 await next()确认每条分支都返回 Response；中间件必须 await
后置逻辑在响应之后才执行，响应头没改上调了 next() 但没 await加 await；后置改头只能改 c.res.headers
c.executionCtx 抛错当前运行时没有 ExecutionContext（Node 就没有）用 try 包一层，退化成普通 Promise 并接住错误
Workers 上构建失败，提示找不到 node: 模块依赖引了 Node 内置模块开 nodejs_compat，或换掉这个依赖
Workers 上数据库连接迅速耗尽按常驻进程的思路建连接池改用 HTTP 型数据访问或平台提供的连接池
客户端 RPC 类型是空的或全是 any路由拆成了多条独立语句，类型没累积改成链式连写，并从最终变量导出 typeof
编辑器卡顿、报类型实例化层级过深路由类型规模过大编译成声明文件供客户端用，或拆分子应用

③ 场景 · 什么时候该用，什么时候不该用

判断顺序应该是先看部署目标，再看依赖能不能跟着走，最后才看团队栈。反过来先比框架跑分，基本会选错。

flowchart TB S{"部署目标是 Edge 或函数型运行时?"} S -->|是| E{"需要长连接池、本地文件或 Node 专属依赖?"} S -->|否| N{"Node 常驻服务，现状是什么?"} E -->|需要| ALT["先解决依赖：换 HTTP 型数据访问层，否则退回常驻服务部署"] E -->|不需要| HONO["Hono 适配度最高，几乎没有多余抽象"] N -->|已有大量 Express 专用中间件| KEEP["留在 Express 或 Koa，迁移成本大于收益"] N -->|需要 DI、模块边界与分层约定| NEST["NestJS"] N -->|新建轻量 API，想要端到端类型| HONO2["Hono 配校验中间件与 RPC"] N -->|吞吐敏感且响应体 JSON 很大| FAST["Fastify 的 schema 序列化更对症"]
场景适配程度原因不适配时的替代
Edge 或函数型运行时上的 API 网关、BFF高处理函数形状就是平台原生形状，冷启动包体小无需替代
同一套代码要在本地 Node 跑、线上部署到 Workers高（前提是依赖干净）业务层可移植，入口按运行时分叉即可依赖带 Node 模块就只能统一回 Node
前后端同仓、想要端到端类型高链式路由类型加 RPC 客户端，无需生成代码跨语言或跨仓库时用 OpenAPI 生成客户端
大型多团队单体，需要统一分层与依赖注入低框架不提供模块边界与 DI，约定要自己造并自己维护NestJS，详见站内 NestJS 篇
重度依赖既有 Express 中间件的老系统低中间件全部要重写，收益难以回本留在 Express 或 Koa
长连接密集型服务：数据库连接池、常驻 WebSocket、定时任务取决于运行时Node 上没问题，函数型运行时上模型不成立常驻 Node 服务部署
把框架换成 Hono 来解决性能问题不适用耗时主要在 I/O 与序列化，框架开销占比很小先做诊断，详见站内 Node.js 性能诊断篇

不适用边界：Hono 解决不了运行时层面的问题。同步阻塞会拖垮任何 Node 框架，与选型无关，见 事件循环的六个阶段；接口慢、内存涨、事件循环延迟的定位方法在 性能诊断。需要 DI、模块边界与强制分层的大型多团队单体应该用 NestJS；纯吞吐与序列化敏感的场景 Fastify 的 schema 路线更对症，横向对比见 框架选型；app.fetch 能被 Bun 直接托管，但那是另一套生产适用面判断，见 Bun 是什么、快在哪。

这条路径上，上一篇讲的是约定最强的那一端（NestJS 的 IoC 与分层），本篇讲约定几乎为零、只认 Web 标准的另一端。接下来三篇把本篇里一带而过的三层机制各自展开：路由匹配与上下文对象、洋葱链与内置中间件边界、各运行时的部署差异。

最容易踩的坑
  • 处理函数某条分支忘了 return：不是返回空响应，而是直接报 Context 未终结，错误信息看起来像框架 bug。
  • 中间件写了 next() 没写 await：后置逻辑跑在响应之后，改响应头静默失效，本地小流量几乎发现不了。
  • 按 Express 习惯往请求对象上挂属性：标准 Request 是只读的，应该用 c.set / c.get 并声明 Variables 类型。
  • 把 c.env 当环境变量读：它是平台 bindings，Node 适配器下装的是底层请求响应对象，取配置仍要走 process.env。
  • 在 Node 上直接用 c.executionCtx.waitUntil：会抛错，必须包一层降级成普通 Promise 并接住拒绝。
  • 以为「Hono 能跑在 Workers」就等于「你的项目能跑在 Workers」：任何依赖引了 node:net 或 node:fs 都会把你钉回 Node。
  • 把常驻进程的连接池思路搬到函数型运行时：实例短命且数量不可控，连接数会被迅速打满。
  • 自己先读了 c.req.raw.body，之后再调 c.req.json()：一次性流已被消费，只能拿到空。
  • 路由拆成多条独立语句后用 RPC 客户端：类型不累积，补全全空，编译却不报错。
  • 相信「快 3 倍」这类宣传去换框架：Node 上还多一层适配转换，真实收益远小于预期，先量清瓶颈在哪。
  • 以为有了 RPC 类型就不用校验：类型编译完就没了，服务端校验中间件是唯一的运行时防线。
