Bun 是什么、快在哪、能不能上生产

🏷️ Bun

Bun 的讨论里混杂了太多基准图，反而把最该问的问题盖住了：它不是一个东西，而是三个——一个运行时、一个包管理器、一套工具链，这三者的成熟度和生产风险差了一个量级。包管理器现在就可以用，运行时要非常小心。这篇只解决选型判断：它快在哪、快多少是真的、四个身份分别能不能上生产。上手命令与工具链细节见 Bun 入门，引擎与 Node 兼容层机制见 Bun 运行时特性，迁移实操见 从 Node.js 迁移。

Bun 的三个身份：它到底替代了什么

Node 生态的现状是「一个运行时 + 十几个工具」，Bun 的产品定位就是把这些收进一个二进制。理解它替代了哪些工具，就能理解你可以分几步引入它。

性能来源的诚实拆解

Bun 的快不是魔法，来源清楚且各自有明确的适用边界：

一是引擎换成了 JavaScriptCore。JSC（WebKit 的引擎）解释器启动路径比 V8 短、初始化开销小，所以进程启动快。这对 CLI、脚本、Serverless 冷启动是实打实的收益，对一个常驻运行几天的 HTTP 服务几乎没有意义。二是大量内置能力用 Zig 重写。Bun.serve、文件读写、bun:sqlite、密码哈希这些走的是原生实现，少了 JS 与 C++ 之间的边界开销。三是包安装的 IO 策略。高并发拉取元数据与 tarball，解压进全局缓存后用硬链接或写时复制落地，省掉逐文件拷贝以及 npm 生命周期里海量的 lstat、mkdir 调用。

场景相对 Node 的量级为什么在真实项目里的价值
进程启动（hello world）快数倍JSC 启动路径短，无需加载 Node 的 JS 内建模块CLI 与 Serverless 明显；常驻服务无感
冷缓存安装依赖快数倍到十倍以上并发网络请求加硬链接落地CI 上每次构建省下的分钟数，是收益最确定的一项
直接执行 TypeScript快数倍原生转译，省掉 ts-node/tsx 的额外进程与编译本地开发体验提升明显
HTTP hello world 吞吐快 2-3 倍Zig 实现的 HTTP 层，无 Node stream 与中间件包装几乎没有业务价值，因为真实接口瓶颈不在这
带数据库查询的业务接口差距通常在个位数百分比耗时被 IO 主导，运行时只占几毫秒基本无差别，不足以作为迁移理由
CPU 密集计算互有胜负，V8 在长时间运行的热代码上 JIT 优化常更好两家引擎的 JIT 分层与优化策略不同需要自己按真实负载实测，不能照搬结论
单测执行快数倍启动快加转译快，测试进程本来就是短生命周期大型测试套件收益明显，仅次于 CI 装依赖
⚠️
「比 Node 快 3 倍」这句话的出处

这类数字几乎都来自 http hello world 或纯计算的微基准。那种环境里没有数据库、没有下游调用，运行时开销就是全部耗时，所以运行时的差异会被 100% 放大。而在你的业务里，这部分开销通常只占总耗时的几个百分点。看到性能宣传时先问一句：被测的那个接口，瓶颈在哪？

sequenceDiagram autonumber participant CL as 客户端 participant RT as 运行时 Node 或 Bun participant RD as Redis participant DB as MySQL CL->>RT: 查询订单详情 RT->>RD: 读缓存 未命中 约 1ms RT->>DB: 两条查询 约 42ms DB-->>RT: 返回结果集 RT->>RT: 反序列化与业务处理 约 3ms RT->>RT: JSON 序列化响应 约 1ms RT-->>CL: 200 响应 总耗时约 48ms Note over RT,DB: 运行时能影响的只有那 4ms
就算砍掉一半 总耗时也只从 48ms 到 46ms Note over CL,RD: 而 hello world 基准里 这 4ms 就是全部耗时
差异于是被放大成 3 倍

推论很直接：如果你的接口 p99 是 200ms 且大头在数据库，换运行时不会救你，该做的是加索引、改查询、加缓存。Bun 值得投入的地方是 CI 时长和本地开发体验这两项确定收益。

怎么做一次不骗人的基准测试

# 第一步：先测 hello world，只是为了知道「上限差异」有多大，不要拿它当决策依据
bun run bench/hello.ts &                       # Bun.serve 版本
node bench/hello.js &                          # node:http 版本
npx autocannon -c 100 -d 20 http://127.0.0.1:3000/   # 连接数与时长都要固定

# 第二步：真正的决策依据是压你自己的业务接口，两边跑同一份代码、同一套依赖
#   注意三件事：预热、固定数据集、下游同一实例，否则数据没有可比性
npx autocannon -c 50 -d 60 -w 5000 \
  -H "authorization: Bearer $TOKEN" \
  http://127.0.0.1:8080/api/orders/123

# 第三步：对比的不只是 QPS，还要看内存曲线与延迟分布尾部
#   常见情况是 QPS 略涨但 p99 更抖，或 RSS 更高，这些都会影响容量规划
/usr/bin/time -l node dist/server.js     # macOS 看 maximum resident set size
/usr/bin/time -v node dist/server.js     # Linux 看 Maximum resident set size

# 第四步：确认版本，Bun 迭代很快，跨小版本的性能与兼容性都可能变
bun --revision && node -v

四个身份分别能不能上生产

用途风险上线前必须验证什么出问题时的回退成本
bun install 装依赖低依赖树版本与 npm 解析结果做一次 diff；确认 CI 里锁定了 Bun 版本；确认 bun.lock 已提交很低：改回 npm ci，删除 bun.lock
bun run 跑脚本与本地开发低脚本里如果依赖 npm_lifecycle_* 之类环境变量要逐个确认很低
bun test 跑单测中低mock 能力、快照、覆盖率报告格式能否被现有 CI 与质量门禁消费低：测试代码可能要改回 Jest 写法
bun build 打包中需要的插件是否有对应实现；产物在目标环境实际跑一遍；sourcemap 能否被错误上报平台解析中：构建配置要重写
Bun 作为生产运行时高依赖是否用到未完全兼容的 node:* 能力；有没有 native addon；APM 探针、profiler、堆快照工具是否可用；优雅关闭与信号处理行为；压测与内存曲线对比高：若代码里已用 Bun.* 独有 API，等于没有退路

分阶段采用的建议顺序是固定的：先只用它装依赖，再用它跑测试和本地开发，然后是非核心服务的运行时，最后才是核心服务。每一步都要有独立的回退开关，且不要跳步——跳过前两步直接换生产运行时，是这套技术最常见的翻车方式。

每个阶段都有一条明确的准入线，达不到就停在原地，不要靠「应该没问题」往下推。下面这组命令是各身份的最小验证动作：包管理器看依赖树是否和 npm 解析一致，测试运行器要逐条比对失败用例而不是只看通过率，打包要确认产物在目标运行时真的能起来，运行时则必须同时看启动告警、真实流量表现和优雅关闭这三件事——后两项恰恰是单测覆盖不到、又最容易在发布时炸的地方。

# ---- 四个身份各自的最小验证动作，过不了就不要往下推进 ----

# 1) 包管理器：装完之后依赖数量与关键包版本要和 npm 的结果对得上
bun install --frozen-lockfile
bun pm ls --all | wc -l                 # 与 npm ls --all --parseable | wc -l 对照

# 2) 测试运行器：只看通过率没用，要逐条核对失败用例
bun test 2>&1 | tail -30

# 3) 打包：产物必须在目标运行时真的跑起来，target 选 node 才能保留退路
bun build src/main.ts --target=node --outdir dist --sourcemap=external
node dist/main.js &
sleep 1 && curl -sf http://127.0.0.1:8080/healthz && echo 'node 产物可用'

# 4) 运行时：三件事一起看，缺一件都不算通过
bun --print 'process.versions'          # 确认兼容的 node 版本号
bun src/main.ts &                       # 盯启动日志里有无 not implemented 类告警
kill -TERM %1                           # 优雅关闭：是否执行清理逻辑并以 0 退出

与 Deno 的定位差别

Bun 和 Deno 经常被放在一起讨论，但它们解决的问题不同。Deno 从安全边界出发：默认不给网络、文件系统、环境变量权限，要靠显式参数授予，并自带一套标准库，对 npm 的兼容是后来补上的。Bun 从兼容与速度出发：目标是尽量无痛替换 Node，直接吃现有的 node_modules 和 package.json。

维度Node.jsBunDeno
引擎V8JavaScriptCoreV8
默认权限模型无限制无限制默认全部禁止，需显式授予网络、文件、环境变量权限
Node 生态兼容原生首要设计目标，直接用 npm 依赖可用但需前缀与配置，历史包袱处理更繁琐
TypeScript需要转译工具（新版本有实验性类型剥离）原生转译，不做类型检查原生支持，且自带类型检查
工具链靠社区组合内置包管理、测试、打包内置格式化、lint、测试、打包
适合谁绝大多数生产系统想把现有 Node 项目变快的团队新项目且看重权限隔离与规范统一

❌
最容易踩的坑
  • 把「Bun 比 Node 快 3 倍」当成业务提升：那是 hello world 的数字，你的接口 48ms 里运行时只占 4ms。
  • 没区分 Bun 的四个身份就整体评估：包管理器可以今天就用，运行时的风险高一个量级。
  • CI 与本地用不同包管理器：锁文件不一致会解析出不同版本，是最难查的一类环境差异。
  • 不锁 Bun 版本：迭代速度快，跨小版本的兼容性与性能都可能变，构建无法复现。
  • 用了 Bun.serve、bun:sqlite 这类独有 API：代码回不到 Node，一旦踩到兼容性问题就没有退路。
  • 只看官方兼容性列表就决定迁移：列表是粗粒度的，真正的验证方式是把完整测试套件在 Bun 下跑一遍。
  • 忽略依赖里的 native addon：node-gyp 编译的包是运行时迁移最常见的硬性阻塞点。
  • 忘了 Bun 默认会自动加载 .env：本地跑得好好的，到线上因为缺环境变量而启动失败。
  • 以为 Bun 原生跑 TS 就不需要类型检查：它只转译不校验，tsc --noEmit 仍然必须留在 CI 里。
  • 迁移前没有压测基线：换完之后 QPS 涨了还是跌了、内存高了多少，全都说不清。
  • 核心服务先迁：应该反过来，从风险最低的非核心服务开始积累运维经验。
  • 没准备回退开关：镜像 tag、锁文件、启动命令都要能在几分钟内切回 Node。
