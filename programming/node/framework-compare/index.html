Node.js Web 框架选型：中间件模型与性能的真实差异

🏷️ Node.js 总览

框架选型的讨论很容易滑向跑分截图，但真正决定半年后过得舒不舒服的是两件很少被讲清楚的事：这个框架用什么模型把中间件串起来（决定异常怎么传播、后置逻辑写在哪、响应还能不能改），以及它的性能优势具体来自哪一段代码（决定这点优势在你的真实接口里还剩多少）。这篇不贴 QPS 数字——脱离硬件、Node 版本、路由形状、keep-alive 与响应体大小的跑分没有可比性，能迁移的只有机制结论和量级判断。

五个框架，三种中间件模型

Express、Koa、Fastify、NestJS、Hono 在「中间件」这个词下面藏着三套完全不同的机制，这是选型里影响最深远、被讨论得最少的一层。

线性 next 回调（Express）：中间件是 (req, res, next)，框架维护一个有序数组，调 next() 才往下走。它没有「回程」这个概念——函数一旦调完 next() 就返回了，下游什么时候结束它不知道。所以计时、审计、统一改写响应这类后置逻辑在 Express 里只能靠监听 res 的 finish / close 事件，或者干脆猴补丁劫持 res.end、res.write（compression、response-time 这类中间件都是这么干的，也正是多个中间件互相打架的根源）。

洋葱 async（Koa、Hono）：中间件是 async (ctx, next)，await next() 之后的代码就是回程。后置逻辑、try/catch 兜住下游全部异常、finally 里打点，都是语言本身就成立的写法，不需要框架提供额外机制。代价是每一层都在调用栈上多压一个 async 帧，而且任何一层忘了 await，回程就会跑在下游还没结束的时候。

固定阶段钩子（Fastify）：Fastify 不用洋葱，它把一次请求切成语义明确的阶段，你往阶段上挂钩子。想改什么东西，必须挂在允许改它的那个阶段——这看起来啰嗦，实际是把「什么时候能改响应体」这类隐式知识变成了 API 约束。

双层结构（NestJS）：NestJS 有两套并存。底层平台（Express 或 Fastify）的中间件照常跑在最外面；Nest 自己的 Guard、Interceptor、Pipe、Filter 跑在路由匹配之后，因此拿得到「即将执行哪个 controller 方法」这类元信息，代价是没匹配上路由的请求根本走不到这些增强器。其中 Interceptor 用 RxJS 包裹 handler 的返回流，是这套里唯一有回程语义的。

// Express：线性模型下想在响应之后打点，只能挂事件
app.use((req, res, next) => {
  const start = process.hrtime.bigint()
  // finish 在响应体交给内核后触发；客户端提前断开走的是 close，两个都要接
  res.on('finish', () => {
    const ms = Number(process.hrtime.bigint() - start) / 1e6
    // 一定要用 req.route.path 这种模板化的路径，用 req.url 会把路径参数打成高基数标签
    metrics.observe(req.method, req.route?.path ?? 'unmatched', res.statusCode, ms)
  })
  next()   // 忘了调 next，请求就静默挂住，没有报错也没有响应
})

// Koa / Hono：洋葱模型下后置逻辑和异常兜底是同一段代码
app.use(async (ctx, next) => {
  const start = performance.now()
  try {
    await next()                        // 下游全部执行完才回到这一行
  } catch (err) {
    ctx.status = err.status ?? 500      // 下游任意一层的异常都在这里收口
    ctx.body = { message: '内部错误' }   // 此时响应还没序列化，改 body 完全安全
    ctx.app.emit('error', err, ctx)     // 交给集中日志，不要在这里直接打印
  } finally {
    const dur = (performance.now() - start).toFixed(1)
    ctx.set('Server-Timing', `app;dur=${dur}`)
  }
})

Express 4 的 async 异常：没人接的那个 Promise

「Express 不自动捕获 async 异常」这句话流传很广，但后果常被说成「请求挂住」就结束了，实际是两个后果同时发生。

Express 4 的路由层确实有 try/catch，但它只包住对 handler 的同步调用，并且完全忽略 handler 的返回值。你的 async 函数返回一个 promise，没人 await 它：第一，reject 不会转交给错误中间件，也没有任何响应写回，请求一直占着连接直到网关超时；第二，这是一个未处理的 rejection，而 Node 15 起 --unhandled-rejections 默认是 throw，等于抛出未捕获异常——没装 process.on('unhandledRejection') 的进程会直接退出。所以线上表现往往是「偶发 504 + 容器莫名重启」，很多人会误判成内存或健康检查问题。

结论很明确：所有现代框架都能接住 handler 里的 async 异常，只有 Express 4 不能；而没有一个框架能接住定时器和事件回调里抛出的错。进程级的 uncaughtException / unhandledRejection 处理器只该用来打日志然后优雅退出，不要用它把进程留着继续跑——那时候状态已经不可信了。

// Express 4 必备的包装器：把返回值接上 catch，交给错误中间件
const wrap = (fn) => (req, res, next) =>
  Promise.resolve(fn(req, res, next)).catch(next)

app.get('/users/:id', wrap(async (req, res) => {
  const user = await db.user.findUnique({ where: { id: req.params.id } })
  if (!user) throw Object.assign(new Error('not found'), { status: 404 })
  res.json(user)
}))

// 错误中间件必须是四个参数。写成三个就退化成普通中间件，永远收不到错误，
// 而且因为它不调 next，所有请求都会挂在这里——这个坑比漏包装器更难查
app.use((err, req, res, next) => {
  if (res.headersSent) return next(err)   // 已经开始写响应，只能交给默认处理器断开连接
  res.status(err.status ?? 500).json({ message: err.expose ? err.message : '内部错误' })
})

Fastify 的快：把 schema 编译成代码

Fastify 的性能优势不是「实现得更精致」，是把两段本来在每个请求里重复做的解释型工作，挪到启动时编译成了专用函数。

校验：注册路由时，ajv 把你的 JSON Schema 编译成一个针对这个 schema 的校验函数（生成源码再实例化），运行时只是调一个普通函数。手写 if (typeof x !== 'string') 式校验或者每请求解释一遍 schema，开销完全不是一个量级。

序列化：声明了 response schema，Fastify 用 fast-json-stringify 生成一个专用的字符串拼接函数。通用序列化必须在运行时枚举对象的键、判断每个值的类型、处理 toJSON 与循环引用；而专用函数里键名是写死的字面量，类型是已知的，直接拼。响应形状固定时这是实打实的 CPU 节省，响应体越大越明显。

代价也很具体：生成的序列化函数只输出 schema 里声明过的属性，没声明的字段被静默丢掉。这是 Fastify 最高频的「字段莫名消失」来源，好处是顺手防住了密码哈希这类内部字段泄漏。另外类型声明错了会输出被转换后的值而不是报错；响应形状不固定（任意 key 的字典、联合类型很多的 payload）时，schema 要么写不出来，要么写成 additionalProperties: true 退回通用路径，收益归零，这种接口就别硬套。

另一个容易忽略的机制是封装作用域：Fastify 的插件默认形成一个作用域，里面注册的钩子、装饰器、路由只在这个子树可见。这是它做模块边界的方式，也是「我明明装饰了 request，另一个插件里却 undefined」的答案——要跨作用域共享就得用 fastify-plugin 显式打破封装。这个模型比 Express 那种全局 app.use 可控得多，但需要先理解它才不会一路踩。

const app = Fastify({
  logger: { level: 'info' },   // pino 结构化日志，比同步写 stdout 的日志中间件开销低得多
  bodyLimit: 1048576,          // 默认 1MB。超限直接 413，不要等到 handler 里才判断大小
  trustProxy: true,            // 挂了网关才开，否则 req.ip 可被 X-Forwarded-For 伪造
})

app.route({
  method: 'GET',
  url: '/users/:id',
  schema: {
    params: { type: 'object', required: ['id'], properties: { id: { type: 'string' } } },
    response: {
      // 这份 schema 会被编译成专用 stringify 函数（启动时一次）。
      // 注意：这里没声明的字段会被静默丢弃——新增返回字段必须同步改这里
      200: {
        type: 'object',
        properties: {
          id: { type: 'string' },
          email: { type: 'string' },
          createdAt: { type: 'string', format: 'date-time' },
        },
      },
    },
  },
  handler: async (req) => usersService.get(req.params.id),   // 返回对象，别自己 JSON.stringify
})

// 埋点用 onResponse：响应已发出，这里抛错不会影响客户端
app.addHook('onResponse', async (req, reply) => {
  // routeOptions.url 是模板化路径（含 :id），用它而不是 req.url，避免指标标签基数爆炸
  metrics.observe(req.method, req.routeOptions.url ?? 'unmatched', reply.statusCode, reply.elapsedTime)
})

路由匹配：线性正则、基数树与合成大正则

路由匹配的实现差异在几十条路由时看不出来，在几百条路由加大量参数段时才会变成一个可测量的量级差。更重要的是它决定了注册顺序是否影响命中结果——这是行为语义，不是性能问题。

实现匹配方式成本随路由数变化注册顺序影响命中重复路由
Express 4 / 5（path-to-regexp）有序数组，逐条正则 test近似线性增长是，先注册先命中允许，后者永远不被命中
koa-router同样基于 path-to-regexp 的有序遍历近似线性增长是允许
Fastify（find-my-way）基数树按路径分段下降与路由总数基本无关，取决于路径深度否，静态段优先于参数段注册时直接抛错
Hono RegExpRouter首次请求时把全部路由合成一个正则，一次匹配匹配成本几乎不涨，代价在首次构建否（中间件仍按注册顺序）允许
NestJS不自己匹配，完全交给底层适配器随适配器变随适配器变随适配器变

顺序敏感带来的真实故障是这样的：Express 里先注册了 /users/:id，再注册 /users/export，那么 /users/export 永远会被前者吃掉，req.params.id 等于字符串 export，业务逻辑去查一个不存在的用户然后返回 404，看起来像数据问题。Fastify 和 Hono 的树式/合成式匹配让静态段天然优先，不会出现这个问题。反过来，Fastify 对重复注册直接抛错，迁移老项目时经常在启动阶段就炸出一批历史遗留的重复路由——这是好事，只是要有准备。

装饰器式 DI 的代价

NestJS 的 DI 容器和装饰器不是「语法糖」，它是一套有明确运行时行为的机制，收益和代价都很具体。深入的请求生命周期与模块模型见站内 NestJS 架构模型一篇，这里只列选型时要算进去的账。

机制你得到什么代价失效或翻车条件

判断标准不是项目大小，而是有多少横切逻辑需要在多人协作下保持一致。三个人维护二十个接口，DI 带来的约束收益抵不上心智成本；十几个人共享一套鉴权、审计、多租户上下文、事务边界，那这套约束省下来的 review 和返工时间会远超学习成本。

性能差异的机制归因与量级判断

把「框架性能」拆成可归因的几段，就能自己判断某个差距在你的接口里还剩多少，而不是照抄别人的倍数。

开销来源是否随请求规模增长框架间差距来自哪能否消除怎么确认它是你的瓶颈
路由匹配不随，每请求固定线性正则 vs 基数树 vs 合成正则减少路由数量收效有限，换实现才有效路由上千且延迟 P50 很低时才可能显现，先看火焰图里匹配函数的占比
请求体解析随 body 大小线性几乎没有差距，都是 JSON.parse不能，只能限大小（bodyLimit）大 body 接口的 CPU 时间随体积同步涨
请求校验随字段数编译型（ajv 预编译）vs 解释型 vs 手写 if能，换成预编译 schema火焰图里校验库函数占比明显
响应序列化随响应体大小线性专用 stringify vs 通用 JSON.stringify能，固定形状加 response schema大列表接口 CPU 高、事件循环延迟同步抬升
日志随每请求日志条数结构化异步写 vs 同步 stdout 拼字符串能，换 pino 类实现并降级别关掉日志后 QPS 明显变化
中间件层数不随，每请求固定层数与每层是否 async能，把全局中间件收敛到需要的路由上逐个摘掉中间件对比
DI 与增强器请求级作用域时随请求数容器实现能，把作用域收回单例把 provider 改回单例后对比

归纳成两句可用的判断：框架开销是每请求近似固定的 CPU 成本，所以 handler 里只要有一次数据库往返或外部调用，这个固定成本在总延迟里的占比就被大幅稀释；真正会把框架差距放大的只有两类场景——极高 QPS 的小响应（网关、健康检查、边缘转发），以及大响应体序列化，因为它既是 CPU 密集又会阻塞事件循环，把同一进程上其他请求的延迟一起拖高（事件循环的机制见站内 Node.js 事件循环篇，怎么量事件循环延迟和抓火焰图见性能诊断篇）。

还有两个常见的推理错误值得点出来。一是拿空路由跑分的倍数外推到业务接口——空路由测的是固定开销，业务接口里它可能只占百分之几。二是把运行时和框架混成一个变量：换到 Bun 上 HTTP 层实现变了，这跟你选哪个框架是两件独立的事，别把两者的收益记在同一笔账上（Bun 的取舍见站内 Bun 专题）。

耦合面与退出成本

选型真正的长期成本不是学习曲线，是三年后想换的时候要重写多少东西。按「框架侵入到你代码的哪一层」来排，结论和按性能排完全不同。

框架侵入点迁移出去必须重写可原样保留退出成本
Expresshandler 签名、res 对象、中间件生态所有中间件、错误处理、路由定义业务函数（如果没把逻辑写在 handler 里）中，但取决于你有没有把 req/res 传进 service 层
Koactx 对象中间件与路由业务逻辑，因为 ctx 通常只在最外层低到中
Fastify钩子、装饰器、插件封装、schema钩子与插件、schema 的组织方式JSON Schema 本身可复用到别处中，schema 是资产而非负债
NestJS装饰器、DI 容器、模块结构、编译链路几乎整个应用骨架，service 里的构造注入也要改纯函数与领域模型高，这是五个里最高的
HonoContext 对象路由与中间件业务逻辑；Web 标准 Request/Response 到处通用低，但换到需要 Node 原生能力的场景要补适配

有一条可以显著压低退出成本的做法，和框架无关：不要把框架对象传进领域层。service 的入参是已校验的普通对象，返回普通对象，框架只负责在边界上做解析、校验、序列化。做到这一点，任何框架的退出成本都会降到「重写边界层」；做不到，哪怕选了最轻的框架也会被拖住。

最容易踩的坑

⚠️
这些都是能复现的
  • Express 4 里写 async handler 却没有包装器：reject 之后既无响应又是未处理 rejection，Node 15 起默认会把进程打挂，表现成偶发 504 加容器重启。
  • Express 的错误中间件写成三个参数：它退化成普通中间件，既收不到错误，又因为不调 next 让所有请求挂住。
  • Express 里先注册 /users/:id 再注册 /users/export：后者永远不被命中，参数里是字符串 export，业务层报 404，看起来像数据问题。
  • 升级 Express 5 不看路由语法变更：裸星号通配、参数后内联正则、可选段写法都变了，默认 query parser 改成 simple 之后方括号嵌套参数不再解析成对象。
  • Fastify 加了 response schema 又新增返回字段却忘了改 schema：字段被序列化函数静默丢掉，不报错不打日志。
  • Fastify 里在 onRequest 读 body：这个阶段 body 还没解析，拿到 undefined；认证查库也不该放这里，未通过校验的请求会白白打数据库。
  • Fastify 里在 onResponse 补响应头：响应已经发出，什么都改不了；要改头用 onSend，要改对象用 preSerialization。
  • Fastify 插件没用 fastify-plugin 就想跨作用域共享装饰器：另一个插件里读到 undefined，这是封装作用域的既定行为不是 bug。
  • 用 esbuild 编译 NestJS：不生成装饰器元数据，启动时报无法解析依赖，容易误判成 DI 配置写错。
  • 在 NestJS 的热路径上无意引入请求级作用域：作用域会向上传染，整条依赖链变成每请求新建实例。
  • NestJS 里用了 @Res() 直接操作响应对象：Nest 的自动响应处理被关掉，Interceptor 里改返回值静默无效。
  • 指标里用 req.url 当标签：路径参数把标签基数打爆，要用模板化路径（Express 的 req.route.path、Fastify 的 routeOptions.url）。
  • 拿空路由的跑分倍数给业务接口做容量规划：框架开销是固定成本，真实接口里通常只占很小一部分。
  • 把框架对象（req / res / ctx）一路传进 service 层：框架从边界渗进领域逻辑，退出成本从「重写边界」变成「重写全部」。
