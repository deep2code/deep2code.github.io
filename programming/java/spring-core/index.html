Spring 核心机制：IoC 容器、AOP 代理与事务陷阱

🏷️ Spring

Spring 里那些「诡异问题」——事务不回滚、缓存注解没生效、配置值是 null、启动时循环依赖报错——几乎全部可以用同一件事解释：Bean 的创建顺序，以及你拿到的到底是原始对象还是代理对象。把容器启动的那几个阶段搞清楚，这些问题就从「玄学」变成了「必然」。这篇讲 IoC 容器的执行顺序、循环依赖的三级缓存、两种 AOP 代理的差异、自调用为什么让注解全部失效、事务的完整陷阱清单，以及条件装配与配置绑定的实际规则。

IoC 容器的启动顺序，以及它能解释什么

Bean 不是「new 出来就能用」。从一份配置到一个可用的 Bean，中间有七个可以插手的节点，每个节点对应一类常见问题。最关键的一条是：AOP 代理是在初始化回调之后、由 BeanPostProcessor 的后置方法生成的。这意味着在 @PostConstruct 里，this 还是原始对象，代理尚不存在。

sequenceDiagram participant R as 容器启动 participant D as BeanDefinition 注册表 participant BFPP as BeanFactoryPostProcessor participant F as BeanFactory participant BPP as BeanPostProcessor participant B as 目标 Bean R->>D: 扫描注解与解析配置类 注册 BeanDefinition Note over D: 此时只有元数据 还没有任何实例 R->>BFPP: 回调所有 BeanFactoryPostProcessor BFPP->>D: 修改定义 占位符解析 配置属性绑定都在这一步 R->>F: 开始实例化单例 F->>B: 调用构造器 完成实例化 F->>B: 属性填充 注入依赖 F->>BPP: postProcessBeforeInitialization BPP->>B: 处理 Aware 与注解注入 F->>B: 初始化回调 PostConstruct 与 InitializingBean Note over B: 注意 这时候 this 还是原始对象 代理还没生成 F->>BPP: postProcessAfterInitialization BPP-->>F: 返回代理对象 AOP 事务 缓存 异步都在这里织入 F->>R: Bean 就绪 放入单例池 Note over R,B: 容器里存的是代理 别人注入到的也是代理
而 Bean 自己内部的 this 永远是原始对象
阶段能做什么它能解释的问题
BeanDefinition 注册扫描 @Component 家族、解析 @Configuration、@ImportBean 没被扫到：包路径不在启动类之下，或者被条件注解排除了
BeanFactoryPostProcessor改 BeanDefinition：占位符替换、@ConfigurationProperties 绑定、Mapper 接口注册这一步早于任何实例化，所以在这里依赖普通 Bean 会触发过早初始化，导致该 Bean 无法被后续的代理增强
实例化调用构造器构造器里拿不到还没注入的字段；构造器注入的循环依赖在这一步直接失败
属性填充注入依赖字段注入的循环依赖靠提前暴露半成品解决
初始化回调@PostConstruct、InitializingBean、initMethod此处 AOP 还没生效：在 @PostConstruct 里调自己的事务方法完全无效
后置处理生成代理注入进来的类型和你声明的不一致、getClass() 里带 CGLIB 后缀都源于此
销毁@PreDestroy、DisposableBeanprototype 作用域的 Bean 不会收到销毁回调

循环依赖与三级缓存：为什么构造器注入解决不了

A 依赖 B，B 又依赖 A。属性注入场景下 Spring 能解决：创建 A 时先把「刚 new 出来但还没填充属性」的半成品暴露出去，B 注入这个半成品就能完成创建，然后 A 再继续填充。而构造器注入无法解决——构造 A 就必须先有完整的 B，构造 B 又必须先有完整的 A，连半成品都产生不出来，只能报错。

stateDiagram-v2 state "一级缓存 singletonObjects 成品" as L1 state "二级缓存 earlySingletonObjects 半成品" as L2 state "三级缓存 singletonFactories 工厂" as L3 state "正在创建中的集合" as ING [*] --> ING: 开始创建 A 先登记防止重复创建 ING --> L3: 实例化完成 立刻放一个能产出早期引用的工厂 L3 --> L2: B 来取 A 时 调用工厂拿到早期引用并升级缓存 L2 --> L1: A 属性填充与初始化全部完成 升级为成品 L1 --> [*]: 后续注入直接命中一级缓存 ING --> [*]: 构造器注入的循环依赖在这里失败 因为半成品都造不出来

三级缓存里的工厂不是多余设计：如果 A 需要被 AOP 代理，早期暴露出去的必须是代理对象而不是原始对象，否则 B 拿到的是没有事务、没有缓存增强的裸对象。工厂的作用就是在「有人真的来取」的时候才决定要不要提前生成代理，没人取就不提前生成。

⚠️
Spring Boot 2.6 起默认禁止循环依赖

这是官方有意的收紧：以前循环依赖被默默解决了，问题藏着；现在启动直接失败。确实存在开关可以放开，也可以给字段加延迟注入绕过去，但这两条路都只是让错误的依赖结构继续存在，并且延迟注入会把失败时机推到第一次调用，变成线上问题。正确解法只有重构：把两边共用的逻辑抽成第三个组件、把一方的反向调用改成事件发布、或者调整分层让依赖单向。循环依赖几乎总是「某个服务类什么都做」的征兆。

AOP 的两种代理，以及它们各自的限制

Spring AOP 不改字节码，它在运行期生成一个包装对象。生成方式有两种，能力边界完全不同。

维度JDK 动态代理CGLIB
实现方式运行期生成实现了同样接口的类运行期生成目标类的子类
前提条件目标类必须有接口，代理只覆盖接口里声明的方法目标类不能是 final，需要可访问的构造器
无法代理什么接口之外的 public 方法完全不被增强final 方法、private 方法、static 方法都无法覆盖，注解静默失效
注入类型限制只能按接口类型注入，按实现类注入会报类型不匹配可以按类型注入，但拿到的是子类
构造器行为不触碰目标类构造器会创建子类实例，早期版本会额外执行一次构造器，构造器里有副作用时会出问题
默认选择Spring 4 及更早，有接口时优先Spring Boot 2.0 起默认，无论有没有接口
典型报错按实现类注入时报找不到匹配的 Beanfinal 类报无法生成子类；final 方法不报错，只是不生效，最危险

注意最后一行：CGLIB 遇到 final 方法不会报任何错，只是那个方法上的事务、缓存、异步注解全部失效。Kotlin 写 Spring 时这一条特别容易踩，因为 Kotlin 的类和方法默认就是 final。

自调用绕过代理：让事务、缓存、异步集体失效的那个坑

这是 Spring 里最高频的「注解不生效」原因，而且它不报错、日志里什么都没有。原因非常直接：代理只能拦住从外面进来的调用。一旦进入目标对象内部，用 this 调另一个方法，走的是目标对象自己的方法表，代理完全不在调用链上。

sequenceDiagram participant C as 调用方 Controller participant P as 代理对象 participant T as 目标对象 this participant TX as 事务拦截器 C->>P: 调用 outer 方法 P->>TX: 进入切面 TX->>T: 执行 outer 的真实逻辑 T->>T: 内部直接 this 调 inner Note over T: 这一跳完全绕开了代理
inner 上的事务 缓存 异步注解全部无效 T-->>TX: outer 返回 TX-->>P: 提交或回滚 只针对 outer P-->>C: 返回 Note over C,TX: 外部调 inner 才会走代理
所以单测直接调 inner 能通过 线上却不生效
解法怎么做代价推荐度
拆成两个 Bean把被调方法移到另一个组件，通过依赖注入调用它多一个类，但职责反而更清晰首选。绝大多数自调用问题本质是一个类承担了两层职责
注入自己把自身作为依赖注入进来，用这个引用调用而不是 this需要延迟注入避免循环依赖报错；代码里出现「自己依赖自己」，可读性差能用但别滥用，改造成本最低时可选
取当前代理用 AopContext.currentProxy() 拿到代理对象再调必须开启 exposeProxy，业务代码被 Spring API 侵入，单测里会直接抛异常最不推荐，只适合改不动的遗留代码
 
// 反例：线上必然不生效，而且没有任何报错
@Service
public class OrderService {

    @Transactional(rollbackFor = Exception.class)
    public void createOrder(OrderCmd cmd) { /* ... */ }

    public void batchCreate(List<OrderCmd> cmds) {
        for (OrderCmd c : cmds) {
            this.createOrder(c);   // this 调用 = 绕过代理 = 每笔都没有独立事务
        }
    }
}

// 首选解法：按职责拆开，调用方持有另一个 Bean
@Service
@RequiredArgsConstructor
public class OrderBatchService {

    private final OrderWriter orderWriter;   // 构造器注入，拿到的是代理

    public BatchResult batchCreate(List<OrderCmd> cmds) {
        BatchResult r = new BatchResult();
        for (OrderCmd c : cmds) {
            try {
                orderWriter.createOrder(c);  // 走代理，每笔一个独立事务
                r.success(c);
            } catch (Exception e) {
                r.fail(c, e);                // 单笔失败不影响其他笔
            }
        }
        return r;
    }
}

@Service
public class OrderWriter {
    // 注意：批量场景要的是 REQUIRES_NEW 或本方法作为事务边界，
    // 如果 batchCreate 外面还有一层事务，REQUIRED 会让所有笔共享一个事务，
    // 任何一笔标记回滚，整批一起回滚 —— 这不是「单笔失败不影响其他」。
    @Transactional(propagation = Propagation.REQUIRES_NEW, rollbackFor = Exception.class)
    public void createOrder(OrderCmd cmd) { /* ... */ }
}

事务的完整陷阱清单

事务注解的语义比看起来复杂得多，下面这张表基本覆盖了线上因为事务出问题的全部原因。

陷阱现象根因修法
内部自调用注解像没写一样不经过代理拆 Bean，见上一节
只对运行时异常回滚抛受检异常后数据竟然提交了默认回滚规则只包含 RuntimeException 与 Error显式写 rollbackFor = Exception.class，团队内统一约定
异常被吞掉catch 之后记了日志就返回，事务正常提交代理层看不到异常要回滚就重新抛出，或手动标记回滚
方法不是 public注解无效代理无法增强非 public 方法改成 public，或把逻辑移到独立 Bean
readOnly 被误解以为能挡住写操作它是给底层的优化提示：透传到连接、让 ORM 跳过脏检查、配合读写分离路由到从库；并不阻止写 SQL当成性能与路由提示用，不要当权限控制
事务里做远程调用数据库连接被长时间占用，连接池耗尽，接口大面积超时RPC 或 HTTP 的耗时与抖动被算进事务持续时间把远程调用移出事务边界，事务只包住数据库操作
提交前发消息下游查不到数据或读到旧值，且只在线上偶发方法返回后代理才提交，消费者可能在提交前就被唤醒用事务同步回调放到提交后执行，或用本地消息表
事务里开新线程新线程里的数据库操作不在事务内，主事务回滚了它不回滚事务上下文存在线程本地变量里，不会传播到新线程异步任务放到提交后触发，并自带幂等与补偿
大事务锁持有时间长，并发下大量等待甚至死锁循环里逐条写库、事务里读大量数据、事务里做计算缩小事务范围，批量操作分批提交
嵌套方法抛异常后整体回滚外层 catch 了内层异常还是全部回滚，并报事务已标记回滚内层用 REQUIRED 时与外层是同一个物理事务，内层异常已把整个事务标记为必须回滚内层需要独立成败就用 REQUIRES_NEW 或 NESTED
传播行为语义回滚边界什么时候用
REQUIRED（默认）有事务就加入，没有就新建与外层共享同一个物理事务，内层任何一处标记回滚，整体一起回滚绝大多数业务方法。它的含义是「我和调用方是一个原子操作」
REQUIRES_NEW挂起外层事务，另开一个连接新建事务，独立提交内外互不影响，内层提交后即使外层回滚也不会撤销写操作日志、扣减配额这类「无论主流程成败都要留痕」的动作。注意它占用两个连接，循环里大量使用会耗尽连接池并可能自锁
NESTED在外层事务里打一个保存点内层失败只回滚到保存点，外层可继续；外层回滚则内层一起没了需要部分回滚且仍属于同一事务时。依赖底层保存点支持，并非所有数据访问方式都可用
其余四种SUPPORTS、NOT_SUPPORTED、MANDATORY、NEVER见文档实际项目里极少用到，看到有人用要先问清意图
 
// 事务未提交就发消息 = 下游读不到数据。正确做法是挂到提交之后。
@Service
@RequiredArgsConstructor
public class PayService {

    private final PayRepository repo;
    private final MessageSender sender;

    @Transactional(rollbackFor = Exception.class)
    public void pay(PayCmd cmd) {
        repo.insertPayment(cmd);
        repo.updateOrderPaid(cmd.getOrderId());

        // 错误写法：这里发出去时事务还没提交，
        // 消费者可能在毫秒内就查库，查到的是旧数据甚至查不到记录。
        // sender.send(new PaidEvent(cmd.getOrderId()));

        // 正确写法：注册事务同步回调，只在提交成功后才真正发送。
        TransactionSynchronizationManager.registerSynchronization(
            new TransactionSynchronization() {
                @Override
                public void afterCommit() {
                    sender.send(new PaidEvent(cmd.getOrderId()));
                }
            });
        // 如果用 Spring 事件，等价写法是给监听器加
        // @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
    }
}

// 提醒：afterCommit 里的动作失败不会回滚事务，因为事务已经提交了。
// 所以它只适合「可重试、可补偿」的动作；要求强一致就把消息写进同一个事务
// 的本地消息表，再由后台任务投递。

Bean 作用域与线程安全

默认作用域是单例，这意味着一个实例被所有请求线程共享。由此推出一条硬性约束：Bean 里不能有可变的实例状态。可以有的是构造完就不再改的依赖和配置值。这条规则被违反时的症状是「数据串到别的用户身上」，在低并发的测试环境几乎不可能复现。

作用域实例数量销毁回调典型陷阱
singleton（默认）容器内一个正常调用放了可变成员变量就是并发 bug；把 SimpleDateFormat 这类非线程安全对象当字段是经典案例
prototype每次获取新建不会被调用，容器创建完就不再管它持有需要释放的资源必须自己关；单例里注入 prototype 只会注入一次，之后永远是同一个实例，要每次拿新的必须通过工厂或方法注入
request每个请求一个请求结束时调用在异步线程、定时任务、消息消费线程里访问会直接抛异常，因为那里没有请求上下文
session每个会话一个会话失效时调用多实例部署下依赖会话状态会导致行为不一致；放大对象会撑爆会话存储

注入到单例里的 request 作用域 Bean 实际上是一个代理，每次方法调用时才去找当前请求对应的真实对象。所以它在没有请求上下文的线程里失败，而不是在注入时失败——错误出现的位置离原因很远，这是它难查的原因。

自动配置、条件装配与配置绑定的实际规则

自动配置的核心是一条顺序保证：用户自己定义的配置类先被处理，自动配置类最后处理。正因为如此，@ConditionalOnMissingBean 才能表达「用户没提供我就给个默认的」。反过来，把 @ConditionalOnMissingBean 写在自己的普通配置类里是不可靠的——普通配置类之间没有顺序保证，条件判断时机取决于加载次序。

// 一个规范的自动配置类。注意四个条件的分工。
@AutoConfiguration(after = DataSourceAutoConfiguration.class)   // 声明相对顺序
@ConditionalOnClass(RedisTemplate.class)                        // 类不在 classpath 就整个跳过
@ConditionalOnProperty(prefix = "app.cache", name = "enabled",
                       havingValue = "true", matchIfMissing = true)  // 开关，默认开
@EnableConfigurationProperties(CacheProps.class)
public class CacheAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean          // 用户自己定义了就用用户的，这是自动配置的精髓
    public CacheManager cacheManager(CacheProps props) {
        return new AppCacheManager(props.getTtl(), props.getMaxSize());
    }
}

// 注册位置在 Spring Boot 2.7 发生了变化：
// 旧：META-INF/spring.factories 里的 EnableAutoConfiguration 键
// 新：META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
//     一行一个全限定类名。Spring Boot 3 已彻底不再读旧的 spring.factories 方式，
//     这是很多老 starter 升级到 Boot 3 后「自动配置突然不生效」的唯一原因。

@ConfigurationProperties(prefix = "app.cache")
public class CacheProps {
    // 支持松散绑定：app.cache.max-size / APP_CACHE_MAXSIZE / app.cache.maxSize 都能绑进来
    private int maxSize = 10000;
    // 支持类型转换：写 30s、5m 会被转成 Duration，@Value 做不到这一点
    private Duration ttl = Duration.ofMinutes(5);
    // getter/setter 省略
}

配置来源的优先级从高到低依次是：命令行参数、SPRING_APPLICATION_JSON、Java 系统属性、操作系统环境变量、jar 包外部的 application-{profile}、jar 包内部的 application-{profile}、外部 application、内部 application、@PropertySource、代码里的默认值。同名配置高优先级直接覆盖低优先级，这是「本地能跑线上值不对」的常见原因——先用启动日志或环境端点确认实际生效值，再去翻配置文件。

💡
松散绑定只对 @ConfigurationProperties 生效

@Value 要求名字完全精确匹配，既不支持短横线与驼峰互转，也不支持时长、数据大小这类类型转换，而且写错了只会在启动时抛「无法解析占位符」，或者更糟——设了默认值于是静默用了默认值。用 @ConfigurationProperties 做成类型安全的配置对象，能顺带获得校验和 IDE 提示。另外环境变量只能用大写加下划线的形式，容器里配置注入失败十有八九是这里写成了小数点分隔。

启动慢的时候常有人开 spring.main.lazy-initialization。它确实能显著缩短启动时间，代价是把问题推迟到运行时：Bean 创建失败、依赖缺失、配置写错这些原本在启动时就暴露的错误，变成第一次请求时才抛出，而那时实例已经通过健康检查进入负载均衡了。开发期用它提速可以，生产环境要慎重；生产上更该做的是裁掉用不上的自动配置和 starter。

报错含义怎么查
NoSuchBeanDefinitionException要注入的类型容器里没有三种可能：类没加组件注解、包不在扫描路径下、被条件注解排除了。加 --debug 看条件评估报告，里面写明了每个自动配置「匹配」还是「不匹配及原因」
NoUniqueBeanDefinitionException同一类型有多个候选用 @Primary 指定默认，或在注入点用 @Qualifier 明确指定；报错信息会列出所有候选名，对着看是谁多出来的
BeanCurrentlyInCreationException循环依赖，且是三级缓存解不开的那种基本可以确定有构造器注入参与其中；报错里的依赖链要从后往前读
BeanNotOfRequiredTypeException拿到的是代理，类型和声明的对不上典型是按实现类注入却生成了 JDK 接口代理；改成按接口注入，或强制使用类代理
无法解析占位符@Value 引用的 key 不存在确认 key 拼写、profile 是否激活、配置文件是否真的被加载；容器里优先怀疑环境变量命名格式
端口已被占用上一个进程没退干净或端口冲突常见于本地；容器里出现这个要怀疑健康检查把旧实例留住了

反模式与最容易踩的坑

反模式为什么错正确做法
字段注入而非构造器注入依赖被藏在注解里，类的真实依赖数量看不出来；字段不能是 final；单测必须借助容器或反射；还会掩盖循环依赖构造器注入，单构造器不需要写注解
Bean 里放可变状态单例被所有请求线程共享，可变字段就是共享变量状态作为方法参数传递，或放进有明确清理时机的上下文
在 @PostConstruct 里做耗时 IO 或调其他服务拖慢启动、让启动成败依赖外部系统可用性；而且此时代理还没生成，自身的事务与缓存注解在这里全都无效改用启动完成事件，或做成懒加载与定时刷新
靠延迟注入绕过循环依赖把启动期错误推迟成运行期错误，错误的依赖结构被保留下来重构：抽公共组件、改成事件、让依赖单向
一个类注入十几个依赖构造器参数爆炸是职责过多的信号，不是注入方式的问题按职责拆分，而不是改回字段注入把问题藏起来
事务里调 RPC 或发消息数据库连接被远程调用的耗时占住，连接池耗尽；消息比提交更早到达下游事务只包数据库操作，外部交互放到提交之后
到处 @Transactional(readOnly = true) 当保护措施它是优化与路由提示，不阻止写入要限制写入靠数据库账号权限
用 ApplicationContext.getBean 到处取 Bean把依赖注入退化成服务定位，依赖关系不可见，测试无法替换声明式注入；确实需要动态选择实现时用工厂或策略映射
❌
最容易踩的坑
  • 同类内部 this 调用带注解的方法。事务、缓存、异步、重试全部静默失效，日志里没有任何线索。
  • 把被增强的方法写成 final 或 private。CGLIB 覆盖不了，同样不报错只是不生效，Kotlin 项目尤其容易中。
  • 只写 @Transactional 不写 rollbackFor，抛受检异常后数据照样提交。
  • catch 住异常打个日志就返回，以为记了日志就等于处理了，事务正常提交。
  • 在循环里对每条记录用 REQUIRES_NEW，每次都要一个新连接，几十条就把连接池占满，进而自己等自己。
  • 事务提交前发消息或调下游，本地测不出来，上线后随机出现「查不到刚写入的数据」。
  • 在事务方法里 new Thread 或提交异步任务做数据库操作，以为它在同一个事务里；事务上下文不会跨线程传播。
  • 在异步线程或消息消费线程里访问 request 作用域的 Bean，抛出的异常看起来和业务毫无关系。
  • 单例里注入 prototype Bean 后以为每次都是新的。注入只发生一次，之后永远是同一个实例。
  • prototype 的 Bean 里持有连接或文件句柄，指望 @PreDestroy 释放——容器不会调用它。
  • @Value 加了默认值，key 写错后静默使用默认值，上线后行为不对却找不到报错。
  • 老 starter 升级到 Spring Boot 3 后自动配置集体失效，原因只是还在用 spring.factories 注册。
  • 生产环境开懒加载提速，把启动期就能发现的配置错误推迟到线上第一次调用才暴露。
  • 在 @PostConstruct 里调自己的 @Transactional 方法，代理此时还不存在，事务一定不生效。
