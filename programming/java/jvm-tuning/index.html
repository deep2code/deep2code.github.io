JVM 调优实战：GC 选型、参数配置与 OOM 排查

🏷️ JVM

调优这件事的真相是：绝大多数 GC 问题不是收集器选错了，而是堆太小或者有泄漏。换收集器、抄一份参数模板贴上去，是最没有性价比的两个动作。这篇按「拿到现场怎么办」的顺序组织：先判断问题类型，再决定动不动参数；给出容器环境真正必配的那几个参数、一段 G1 日志的逐行判读、六种 OOM 各自的排查入口、泄漏排查的完整流程，以及堆外内存和线上诊断命令怎么用。内存区域划分与对象晋升规则见 JVM 运行时原理，这里只讲操作。

调优的正确顺序：先定位，再动参数

任何 GC 调参之前，必须先回答两个问题：停顿是否真的发生在 GC 期间，以及老年代回收后能不能回落。第二个问题把所有内存类故障切成两半：能回落的是容量与速率问题，可以用参数解决；不能回落的是泄漏，改参数只是延迟爆炸时间。

jstat -gcutil <pid> 1000 连续采样十分钟就能得出结论：看 O 列在 FGC 计数增加前后是否回落、YGC 每分钟多少次、GCT 占进程运行时间的比例。GC 总耗时占比长期超过 1% 值得关注，超过 5% 基本可以确定是主要瓶颈。不要跳过这一步直接改参数，否则你没有对照基线，改完也不知道是变好还是变差。

收集器选型：G1 是多数场景的正解

选型这件事在 2020 年之后已经没什么悬念：JDK 9 起 G1 就是服务端默认收集器，CMS 在 JDK 14 被彻底移除，因此「CMS 调优」这类资料对新项目已经没有参考价值。真正需要决策的只有一种情况：堆很大且尾延迟是硬指标时，是否上 ZGC。

收集器停顿量级吞吐适用堆大小是否需要调参版本情况什么时候选它
Serial百毫秒到秒级小堆下反而最高，没有多线程协调开销几百 MB 以内几乎不用一直保留单核容器、CLI 工具、极小内存的边缘服务
Parallel百毫秒到秒级，堆越大越长最高几 GB少一直保留离线批处理、数据计算任务，只关心总吞吐不关心单次停顿
CMS几十到几百毫秒，碎片化后会退化成长 Full GC中几 GB多，且易踩坑JDK 9 废弃，14 移除不要在新系统上选，遗留系统迁移时直接换 G1
G1几十到两百毫秒，可设目标比 Parallel 低一成左右2 GB 到几十 GB少，默认值就很好JDK 9 起默认默认选它，在线业务服务的正解
ZGC亚毫秒，几乎与堆大小无关比 G1 略低几 GB 到 TB 级少，堆够就行JDK 15 转正，21 起分代版本才建议生产使用堆十几 GB 以上且尾延迟是硬性 SLA
Shenandoah亚毫秒比 G1 低，读屏障有成本中到大堆少OpenJDK 发行版提供，Oracle JDK 不带与 ZGC 定位重叠，看发行版支持情况
❌
先别换收集器

「换了 ZGC 停顿就短了」在压测报告里成立，在故障现场基本不成立。泄漏场景下 ZGC 只是把长停顿换成了持续的高 CPU 占用和更晚到来的 OOM；堆偏小场景下它会因为回收跟不上分配而退化。换收集器是把堆配对、泄漏修完、GC 日志读明白之后的最后一步，而不是第一步。

G1 的一个完整周期，以及 MaxGCPauseMillis 的误用

G1 把堆切成 1 MB 到 32 MB 的等大 Region，每个 Region 动态扮演 Eden、Survivor、Old 或 Humongous 角色，「分代」从固定的连续空间变成了逻辑标签。这带来两个特性：一是可以只挑回收收益最高的那批 Region 来回收，从而把停顿控制在目标附近，这也是它名字里 Garbage First 的含义；二是超过半个 Region 的对象被当作 Humongous 对象特殊处理，直接占用连续 Region 并计入老年代。

参数默认值真实语义调错的后果
-XX:MaxGCPauseMillis200停顿目标，不是保证。G1 靠调整新生代大小来逼近它调小到几十毫秒会让 G1 持续收缩新生代，停顿次数暴涨、总停顿更长、晋升速率飙升，最终更容易 Full GC。这是最高频的错误调参
-XX:InitiatingHeapOccupancyPercent45老年代占比达到该值启动并发标记周期；JDK 9 起 G1 会自适应调整设太高会让并发标记来不及，出现标记失败退化为 Full GC；一般不要手动设
-XX:G1HeapRegionSize按堆自动推算Region 大小，决定 Humongous 判定阈值堆很大时 Region 过小会导致 Region 数量过多、记忆集开销上升；有大数组时过小会产生大量 Humongous 分配
-XX:G1NewSizePercent5新生代下限占比需要它通常说明 MaxGCPauseMillis 被设得太激进，应该先把后者还原
-XX:ParallelGCThreads按可用 CPU 推算STW 阶段的工作线程数容器里 CPU 感知不准会算出过多线程，造成严重上下文切换；见下文容器化小节

日志里出现 to-space exhausted 或 Pause Full，意味着 G1 已经失败退化。这两条比停顿时长更值得告警——它们说明回收速度跟不上分配速度，而 Full GC 在 G1 里是单线程整理，停顿可能是平时的几十倍。

必配的启动参数：容器环境尤其不能写死堆

参数建议为什么不配的后果
-Xms 与 -Xmx设成相等避免运行期动态扩容缩容带来的抖动与额外 Full GC；容器内存本来就是预留好的，没必要省启动后堆逐步扩张，压测前期数据不可比，扩容瞬间还会引发停顿
-XX:MaxRAMPercentage容器里用它替代写死 -Xmx，取 50 到 70堆随容器 limit 自动伸缩，改规格不用改参数规格调整后漏改参数，堆超过 limit 被内核杀掉，没有任何 Java 异常
-XX:MaxMetaspaceSize显式设置，如 256m默认不限，元空间泄漏会一路吃到容器上限进程被静默 OOMKilled，而不是抛一个可定位的 OutOfMemoryError: Metaspace
-XX:MaxDirectMemorySize显式设置默认约等于 -Xmx，等于堆外可以再吃掉一个堆的量堆加堆外一起超过容器 limit 被杀
-XX:+HeapDumpOnOutOfMemoryError 与 -XX:HeapDumpPath必配，且指向持久卷出事时自动留现场，这是最廉价的可观测性投资容器重启后现场全灭，只能等下一次复现；写到容器内层文件系统等于没配
-XX:+ExitOnOutOfMemoryError容器环境建议开OOM 后 JVM 往往处于半死状态，能接请求但处理不了，比直接挂更糟实例留在负载均衡里持续返回错误，健康检查还可能显示正常
-Xlog:gc*必配，带轮转没有 GC 日志的调优等于盲调事后无法复盘，只能靠监控图的分钟级采样猜
 
#!/usr/bin/env bash
# 容器内 JDK 17 在线服务启动参数模板。用数组组织便于逐条加注释。
OPTS=()

# --- 堆：容器里按 limit 百分比算，不要写死 Xmx ---
# 留 30% 给元空间、线程栈、直接内存、代码缓存和本地库，
# 堆外这些加起来几百 MB 很常见，不留余量就是等着被 OOMKilled。
OPTS+=(-XX:MaxRAMPercentage=70.0 -XX:InitialRAMPercentage=70.0)

# --- 非堆上限：默认不限等于故障时进程静默消失 ---
OPTS+=(-XX:MaxMetaspaceSize=256m -XX:MaxDirectMemorySize=512m)

# --- 收集器：G1 是默认，显式写出来是为了让参数自解释 ---
# 不要动 MaxGCPauseMillis，默认 200ms 适合绝大多数在线服务
OPTS+=(-XX:+UseG1GC)

# --- 出事前就要配好的现场保全三件套 ---
# HeapDumpPath 必须指向挂载出来的持久卷，否则容器一重启就没了
OPTS+=(-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/data/dump/)
OPTS+=(-XX:+ExitOnOutOfMemoryError)

# --- GC 日志：统一日志框架写法，带轮转，10 个文件各 20M ---
# filecount 和 filesize 缺一个就会无限长大，把磁盘写满
OPTS+=(-Xlog:gc*,gc+heap=debug,safepoint:file=/data/log/gc.log:time,uptime,level,tags:filecount=10,filesize=20M)

# --- 容器 CPU 感知：cpu limit 是小数时尤其要显式指定 ---
# 否则 availableProcessors 可能按宿主机核数算，GC 线程和业务线程池全都开过头
OPTS+=(-XX:ActiveProcessorCount=2)

# --- 禁止业务代码用 System.gc 触发 Full GC ---
# 注意：若用到大量直接内存且依赖显式 GC 回收堆外，开这个之前先评估
OPTS+=(-XX:+DisableExplicitGC)

exec java "${OPTS[@]}" -jar /app/app.jar
⚠️
JDK 8u191 之前的容器坑

老版本 JVM 不读 cgroup 限制，默认堆按宿主机物理内存的 1/4 推算。一台 256 GB 的机器上跑一个 limit 为 2 GB 的容器，JVM 会认为自己能用 64 GB 堆，于是完全不着急 GC，一路涨到 2 GB 被内核杀掉，日志里什么都没有，只在编排平台上看到 OOMKilled 和反复重启。8u191 起 UseContainerSupport 默认开启才解决；如果被迫停留在更老的版本，必须显式写死 -Xmx。

GC 日志逐行判读

下面是一段真实形态的 G1 统一日志。判读顺序是：先看停顿类型和耗时，再看各区域 Region 数量的变化，最后看触发原因。

[2026-09-22T10:14:03.412+0800][info][gc,start] GC(842) Pause Young (Normal) (G1 Evacuation Pause)
# 上面这行：Normal 表示普通 young 回收；括号里的 Evacuation Pause 是疏散停顿，即复制存活对象。
# 如果这里是 G1 Humongous Allocation，说明是大对象分配不下触发的回收，要去查大数组。

[...][info][gc,task] GC(842) Using 8 workers of 8 for evacuation
# 8 个工作线程全用上了。容器 cpu limit 只有 2 核却起 8 个线程，就是 CPU 感知不准，
# 表现为停顿时间莫名偏长且伴随限流，需要 ActiveProcessorCount。

[...][info][gc,heap] GC(842) Eden regions: 240->0(216)
# Eden 从 240 个 region 清空；括号里的 216 是 G1 为下一轮设定的新 Eden 目标。
# 这个目标持续下降，通常是 MaxGCPauseMillis 被设得太小，G1 正在收缩新生代。
[...][info][gc,heap] GC(842) Survivor regions: 12->24(32)
[...][info][gc,heap] GC(842) Old regions: 380->392
# 关键指标：老年代一次 young GC 涨了 12 个 region，这就是晋升量。
# 持续盯这个增量，比看 Full GC 次数能早几个小时发现问题。
[...][info][gc,heap] GC(842) Humongous regions: 6->4

[...][info][gc] GC(842) Pause Young (Normal) (G1 Evacuation Pause) 4784M->4208M(8192M) 23.412ms
# 回收前 4784M，回收后 4208M，堆总量 8192M，本次停顿 23.4ms。正常。

[...][info][safepoint] Safepoint G1CollectForAllocation, Time since last: 812ms, Reaching safepoint: 198ms, At safepoint: 23ms
# 这一行最容易被忽略：到达安全点花了 198ms，真正停顿只有 23ms，业务感知到的是 221ms。
# 这种情况换收集器完全无效，要去找没有安全点的长循环。

[...][info][gc] GC(901) To-space exhausted
[...][info][gc] GC(902) Pause Full (G1 Compaction Pause) 8150M->7920M(8192M) 3821.5ms
# 疏散失败后退化成 Full GC，单线程整理，停顿 3.8 秒，而且回收后仍然 7920M 高位不落。
# 两个信号叠加：回收跟不上分配，且老年代回收不掉，基本可以判定为内存泄漏。

六种 OOM 与各自的排查入口

报错典型成因第一步查什么常见误修
Java heap space一次性查询装载过多数据、无上限缓存、静态集合只增不减、大文件全量读进内存堆快照的支配树，看最大保留集属于哪个类；同时看是不是单次请求就能打爆直接加堆。泄漏场景下只是推迟故障
GC overhead limit exceeded连续多次 GC 只回收极少内存且耗时占比过高，是堆满或泄漏的晚期表现与上一条同源，按泄漏流程走用 -XX:-UseGCOverheadLimit 关掉这个检查，等于把告警拆了
Metaspace动态生成类、反复热部署、类加载器被长生命周期对象持有已加载类计数是否单调上升；同名类是否存在多个加载器副本无脑加大 MaxMetaspaceSize，涨得慢一点但还是会满
Direct buffer memory堆外缓冲未释放、Netty 缓冲区泄漏、上限没设或设得过大开本地内存跟踪做基线对比；看 DirectByteBuffer 实例数与容量加大上限。堆外泄漏和堆内一样不会因为空间变大而消失
unable to create new native thread线程池无界、每请求一线程、容器 pid 上限或 ulimit -u 卡住数线程总数与线程名前缀，找出是谁在无限建线程加堆，这会让可用于线程栈的内存更少，故障来得更快
Requested array size exceeds VM limit申请的数组长度接近整型上限，多数是长度计算溢出或反序列化时读到了畸形长度字段看栈轨迹里数组长度是怎么算出来的，重点查外部输入当成堆不足处理，完全跑偏

内存泄漏排查流程与常见泄漏源

处置顺序比工具重要。直接重启是最常见也最致命的错误——服务恢复了，证据全没了，下一次还会发生，而且你依然不知道原因。

sequenceDiagram participant M as 监控告警 participant O as 值班工程师 participant J as 故障实例 JVM participant K as 编排平台 participant T as 离线分析工具 M->>O: 老年代使用率持续高位 且 Full GC 频繁 O->>K: 先把这个实例从负载均衡摘除 但不要删掉它 O->>J: jstat 采样 确认回收后老年代不回落 O->>J: jcmd 导出堆快照 Note over J: 这一步会 STW 停顿数秒到数十秒
文件可能数 GB 要先确认磁盘空间足够 J-->>O: 快照落盘到持久卷 O->>K: 现场已保全 扩一个新实例并重启故障实例 O->>T: 加载快照 看支配树找最大保留集 T-->>O: 给出该对象到 GC Roots 的完整引用链 Note over O,T: 引用链上第一个业务类就是持有者
集合本身从不是原因 谁一直往里放才是 
# 0) 先确认到底是不是泄漏：看 O 列在 FGC 增加后是否回落
jstat -gcutil <pid> 1000 20

# 1) 不导出大文件的快速摸底：看实例数排前几的类是谁
#    加 :live 会先触发一次 Full GC，线上慎用；不加则包含待回收对象
jcmd <pid> GC.class_histogram | head -40

# 2) 导出完整堆快照。优先用 jcmd，它比 jmap 稳
jcmd <pid> GC.heap_dump /data/dump/heap.hprof

# 3) 确认非堆是否也在涨。需要启动时带 -XX:NativeMemoryTracking=summary
jcmd <pid> VM.native_memory baseline
jcmd <pid> VM.native_memory summary.diff

# 4) 线程数爆炸的排查：按线程名前缀聚合，一眼看出哪个池在失控
jstack <pid> | grep -oE '^"[^"]+"' | sed -E 's/-?[0-9]+"$/"/' | sort | uniq -c | sort -rn | head

# 绝对不要用 jmap -F 在活着的进程上强制导出：
# 它走调试通道，会长时间挂住进程，有把进程直接搞死的先例。
泄漏源为什么会泄漏在堆快照里的特征修法
静态集合静态字段是 GC Root，里面的对象永远可达支配树顶部是某个类的静态 Map 或 List加容量上限与过期，或改成非静态并随生命周期释放
ThreadLocal 未 remove线程池线程长期复用，ThreadLocalMap 里的 value 是强引用引用链形如线程对象到 ThreadLocalMap 再到业务对象set 与 remove 在同一个 try-finally 里成对出现
监听器与回调未注销注册进全局事件总线后对象被长期持有大量同类对象被某个注册中心的集合持有提供注销入口，并在销毁回调里调用
连接与流未关闭每个未关闭的连接背后还挂着缓冲区与本地资源连接对象数量随运行时间线性增长try-with-resources，并给连接池配泄漏检测
缓存无上限用普通 Map 当缓存，而 key 是用户 ID 之类的无限集合单个 Map 保留了绝大部分堆换成带容量与过期策略的缓存实现
类加载器泄漏旧加载器被静态字段或线程持有，它加载的类全部无法卸载元空间涨而堆不涨；同名类有多份查谁持有加载器，通常是第三方库的静态缓存或未关闭的线程
堆外缓冲泄漏引用对象被长期持有，清理动作得不到执行时机堆里看不出来，只有本地内存跟踪能看到显式释放，或改用池化并确认归还路径

「进程占了 6 GB 但 -Xmx 只有 4 GB，是不是漏了」——多数时候不是。堆之外还有一长串开销，全部算进进程常驻内存。

判断堆外是否异常的唯一可靠方法是基线对比：启动时加 -XX:NativeMemoryTracking=summary，服务稳定后打一个基线，隔一段时间做差值，看哪一类在单调上升。只有单调上升才是泄漏，来回波动是正常的。注意本地内存跟踪本身有 5% 到 10% 的性能开销，长期开启要评估。

命令看什么字段怎么判读
jps -lv进程号与启动参数第一步确认线上实际生效的参数和你以为配的是不是一回事，参数被运维脚本覆盖非常常见
jstat -gcutil <pid> 1000E O M YGC YGCT FGC FGCTO 回收后不回落是泄漏；YGC 每秒多次说明分配速率过高；FGCT 除以进程运行时间超过 5% 基本可以定为主瓶颈
jstack <pid>线程状态、死锁提示、重复出现的栈顶大量 BLOCKED 停在同一个锁上是锁竞争；大量线程栈顶相同且是 IO 等待说明下游慢；连抓三次对比，一直不动的那些才是真卡住
jcmd <pid> VM.flags -all所有生效参数的最终值确认自动推算出来的堆大小、GC 线程数、Region 大小到底是多少，比猜可靠
jcmd <pid> GC.heap_info各代当前容量与使用量比 jstat 更直观地看一眼当前水位，适合快速确认
jcmd <pid> Thread.print同 jstack部分容器环境里 jstack 受限时的替代方案
Arthas dashboard线程 CPU 占比、堆各代水位、GC 次数一屏看全局，判断问题是 CPU 型还是内存型的最快入口
Arthas thread -n 3CPU 占用最高的三个线程及其栈CPU 飙高先看这个。最忙的是 GC 线程才去查 GC，否则是业务代码或死循环
Arthas trace方法内部各调用的耗时占比定位慢在哪一层，但它有字节码增强开销，只在可疑方法上用，别对高频入口全开
⚠️
容器化之后必须补的两件事

第一，CPU limit 会影响 JVM 的并行度决策。availableProcessors 的返回值决定了 GC 线程数、JIT 编译线程数，以及几乎所有默认线程池的大小。cpu limit 是小数时取整结果常常不符合预期，用 -XX:ActiveProcessorCount 显式指定最省心。第二，内存 limit 不等于堆上限，必须给上面那一整串非堆开销留出余量，通常堆占 limit 的 50% 到 70%。至于 CPU 配额本身怎么被内核限流、为什么配额卡着会出现周期性毛刺，属于容器编排范畴，详见站内 Kubernetes 原理篇。

反模式与最容易踩的坑

反模式为什么错正确做法
一上来就换 ZGC没定位问题就换实现，泄漏和堆偏小一个都解决不了，还引入新的未知先按决策图判断类型，把堆配对、泄漏修掉
把 MaxGCPauseMillis 设成 10msG1 会疯狂收缩新生代，停顿次数暴涨、晋升速率飙升，总体更差保持默认 200，真要降先确认停顿是瓶颈
堆设得比容器 limit 还大内核直接 kill，没有 Java 异常、没有堆快照，只看到容器反复重启用 MaxRAMPercentage，并给非堆留 30% 余量
没配 HeapDumpOnOutOfMemoryError出事时现场随容器重启消失，排查只能等复现出事前就配好，路径指向持久卷
用 jmap -F 强制导出走调试通道，长时间挂住进程，有把进程搞挂的实际案例用 jcmd GC.heap_dump；进程已无响应时才考虑强制手段
只看堆不看堆外堆快照里完全看不到直接内存与本地库分配，查一整天也找不到堆水位正常但 RSS 持续涨，直接上本地内存跟踪做基线对比
GC 日志不配轮转单文件无限增长，几周后把磁盘写满，连带整台机器上其他服务出故障filecount 与 filesize 必须同时给
关掉 GC 开销检查让报错消失这是 JVM 在替你报警，关掉只是把明确的异常变成无限卡顿去查为什么回收不掉
抄一份「线上通用 JVM 参数」几十个开关大量参数在新版本里已失效、语义变了或彼此冲突，出问题时无法归因只配本文表格里那几类，其余交给默认值与自适应
❌
最容易踩的坑
  • 故障时第一反应是重启。服务恢复了，堆快照、线程栈、GC 日志全部随容器消失，下一次照样发生。先摘流量，再取现场，最后重启。
  • 把 -Xmx 写死在镜像里，容器规格从 4 GB 调成 2 GB 后忘了改，上线即 OOMKilled。
  • 元空间和直接内存都不设上限，于是 JVM 眼里内存永远够用，最后由内核来做决定。
  • HeapDumpPath 指向容器内的临时路径，快照确实生成了，容器一重启就没了。
  • 高峰期直连线上进程导出几 GB 的堆快照，STW 十几秒把所有接口打超时，把一个内存告警升级成全站故障。
  • 用 jstat 只看一眼截图就下结论。必须连续采样，单点数据分不出「正在回收」和「回收不掉」。
  • 看到 Full GC 就紧张，看到 to-space exhausted 和 Reaching safepoint 却没感觉——后两者才是真信号。
  • 容器里不设 ActiveProcessorCount，GC 线程按宿主机核数开，在 1 核配额里起十几个工作线程，停顿反而更长。
  • 把「消除报错」的参数当修复手段，比如关掉 GC 开销上限检查。
  • 在堆快照里看到字节数组占比最高就下结论。字节数组当然最大，要看的是支配树以及它到 GC Roots 的引用链上第一个业务类。
  • 只加大堆不看晋升速率。老年代涨得快往往是新生代被压得太小，加堆而不调比例，问题只是变慢了一点。
  • 压测在预热完成前就开始计数，得出「优化有效」的结论，其实是 JIT 编译完成带来的差异。
