JPA 持久化上下文与 MyBatis 选型

🏷️ Java ORM

用 JPA 写业务的人几乎都问过这三句话：为什么我只改了对象、没调 save，数据库居然更新了？为什么我调了 save，日志里当场却没有 SQL？为什么方法返回之后取一个关联字段就抛 LazyInitializationException？这三个问题的答案是同一个东西——持久化上下文（Persistence Context）。不理解它，Hibernate 的行为看起来全是玄学；理解了它，这些现象都是必然结果，而且可以提前预判。

这篇不写 CRUD 教程，只写机制和陷阱。SQL 本身怎么写快、索引怎么建、执行计划怎么读，见站内 MySQL 深度剖析 与 慢查询优化；连接池参数矩阵、真正的批量写入、事务边界与事务内 RPC 的危害，见 数据库性能优化。这几处本文只给结论，不重复展开。

持久化上下文：一级缓存、脏检查、身份映射是同一个东西

持久化上下文是 EntityManager（Hibernate 里是 Session）背后的那块内存区域。在 Spring 的默认配置下，它的生命周期与事务绑定：事务开始时创建，提交或回滚时销毁。它同时承担三个职责，而这三个职责被人用三个不同名字讨论，导致很多人以为它们是三样东西。

三个「效果」是同一个设计的三个侧面。身份映射表让同一事务内的同一行数据只有一个 Java 对象，所以第二次 findById(1L) 直接命中内存，这就是被叫做「一级缓存」的东西——注意它不是业务缓存，事务一结束就整块扔掉，也不跨请求共享，指望它扛读流量是完全错的方向。快照机制让 Hibernate 知道你改了哪些字段，所以能自动生成 UPDATE。动作队列让写操作攒起来批量发出，所以 SQL 出现的时间点和你写代码的行号对不上。

⚠️
一级缓存的隐性成本

持久化上下文里有多少 managed 实体，脏检查就要比对多少份快照。在一个事务里 findAll() 出十万条实体再做循环处理，提交时的脏检查会明显卡顿，而且这些实体在事务结束前不会被 GC 回收。批处理场景要么用 DTO 投影绕开管理，要么每处理若干条主动 flush() 加 clear()。

两个必须纠正的流传很广的说法。第一，merge 不是「把这个对象变成受管」，它是「把这个对象的字段值复制到一个受管副本上，然后返回那个副本」。写成 em.merge(user); 却继续操作原来的 user，改动会全部丢失，必须写 user = em.merge(user);。Spring Data 的 save() 同理，它内部判断主键是否为空来决定走 persist 还是 merge，所以对有主键的对象调 save() 会先发一条 SELECT 把数据库里的行加载进来做合并，这是很多人没意识到的额外查询。

第二，persist 不保证立刻发 INSERT。只有主键策略是 IDENTITY（依赖数据库自增）时，Hibernate 被迫立刻执行 INSERT 才能拿到主键填进身份映射表；用 SEQUENCE 或 TABLE 策略时它能先取号、把 INSERT 攒到 flush。这也解释了为什么 MySQL 自增主键下 JPA 的批量插入很难真正 batch ——每条都要立刻回写主键，JDBC 批处理攒不起来。真要批量写，方案见 数据库性能优化 里的批量写入一节。

flush 的三个时机，以及为什么 SQL 出现得比你想的晚

LazyInitializationException 的完整成因，和 open-in-view 的代价

先说清代理是怎么来的。getReference()（旧名 getOne()）根本不查数据库，它返回一个只填了主键的字节码代理；@OneToMany 默认 FetchType.LAZY，加载父实体时子集合也是一个代理集合。代理内部持有创建它的那个 Session 引用，第一次访问非主键字段时才去发 SQL 初始化自己。

事务在 Service 方法返回时结束，Session 关闭。此时代理仍在对象图里，Controller 或模板引擎再去 getItems().size()，代理找不到活着的 Session，抛 LazyInitializationException: could not initialize proxy - no Session。所以这个异常的本质不是「懒加载不好」，而是数据获取边界和事务边界没对齐：你在事务里没声明需要这份数据，出了事务才想要。

❌
spring.jpa.open-in-view 默认是 true

Spring Boot 启动时会打一条 warn 说明这一点，几乎所有人都忽略了它。它的作用是把 EntityManager 的生命周期从事务扩展到整个请求，代价是数据库连接被持有到视图渲染完成。对返回 JSON 的 REST 服务来说，序列化阶段的每次懒加载访问都是一条额外 SQL，而且发生在事务之外、没有一致性保证。建议显式设为 false，把暴露出来的异常逐个用查询层修掉，而不是让它兜底。

N plus 1 在 JPA 里的两种特有形态

N plus 1 的通用定义（查一次列表再逐条查关联）见 数据库性能优化，这里只讲 JPA 独有的两个触发姿势，因为它们比手写 SQL 时隐蔽得多。

形态一：LAZY 集合在循环里被访问。查出 100 个订单，然后 for (Order o : orders) o.getItems().size()，每次访问都初始化一个独立的集合代理，总共 1 加 100 条 SQL。危险在于这段循环经常不在你写的代码里，而在 Jackson 序列化、模板渲染、或者某个 toString() 里。

形态二：@ManyToOne 和 @OneToOne 默认是 EAGER。这是 JPA 规范里一个公认的坏默认值。你以为自己只查订单，实际每条订单都会带出买家、带出买家的部门、层层展开，要么变成一个巨大的 JOIN，要么变成一串额外 SELECT。正确做法是把所有关联显式声明为 fetch = FetchType.LAZY，需要的地方再用 fetch 或投影声明，把「默认不取、按需声明」变成团队规范。

识别方法很简单也很可靠：在测试环境开 logging.level.org.hibernate.SQL=DEBUG，或者接入 datasource-proxy 这类统计工具，给关键接口断言「单次请求 SQL 条数不超过 N 条」。把这条断言写进集成测试，N plus 1 就不会再悄悄回归。

JOIN FETCH 加分页：Hibernate 会把全表拉进内存排序

这是线上事故率最高的一条。当 fetch 的是集合关联时，一行父实体会被 JOIN 成多行结果，数据库的 limit 和 offset 作用在 JOIN 后的行上，切出来的页和父实体的页对不上。Hibernate 的选择是干脆不把分页下推，而是把满足条件的全部结果集取到内存，在内存里做分页，并在日志里留下一行警告：

WARN  org.hibernate.hql.internal.ast.QueryTranslatorImpl
      HHH000104: firstResult/maxResults specified with collection fetch; applying in memory!

这行 WARN 在测试环境数据量小的时候毫无症状，上线遇到百万行就是一次 OOM 或者长时间 GC。看到 HHH000104 必须当故障处理，不能当提示忽略。正确做法是两步查询：先分页查主键，再按主键集合 fetch。

public interface OrderRepository extends JpaRepository<Order, Long> {

    // 第一步：只查主键，SQL 里没有集合 join，limit/offset 能正常下推到数据库
    @Query("select o.id from Order o where o.status = :status order by o.createdAt desc")
    Page<Long> findIdsByStatus(@Param("status") OrderStatus status, Pageable pageable);

    // 第二步：按主键集合 fetch，IN 列表长度等于页大小，结果行数可控
    @Query("select distinct o from Order o left join fetch o.items where o.id in :ids")
    List<Order> findAllWithItemsByIdIn(@Param("ids") List<Long> ids);
}

@Service
@RequiredArgsConstructor
public class OrderQueryService {

    private final OrderRepository orderRepository;

    @Transactional(readOnly = true)   // 只读事务把 flush mode 设为 MANUAL，省掉脏检查
    public Page<Order> pageWithItems(OrderStatus status, Pageable pageable) {
        Page<Long> idPage = orderRepository.findIdsByStatus(status, pageable);
        if (idPage.isEmpty()) {
            return Page.empty(pageable);
        }
        List<Order> orders = orderRepository.findAllWithItemsByIdIn(idPage.getContent());
        // 第二步的 in 查询不保证顺序，必须按第一步的主键顺序重排，否则排序失效
        Map<Long, Order> byId = orders.stream()
                .collect(Collectors.toMap(Order::getId, Function.identity()));
        List<Order> ordered = idPage.getContent().stream()
                .map(byId::get)
                .filter(Objects::nonNull)
                .toList();
        // 总数直接复用第一步的 count，不要在第二步再 count 一遍
        return new PageImpl<>(ordered, pageable, idPage.getTotalElements());
    }
}

如果嫌两步查询啰嗦，退而求其次的方案是保持单次分页查询，给集合关联加 @BatchSize，让 N 条子查询合并成 N 除以 batchSize 条 IN 查询。分页正确、SQL 条数可控，代价是比两步查询多几条 SQL。

JPA 和 MyBatis 怎么选，混用的边界在哪

这个问题不该按喜好回答，而该按查询形态回答。两个框架的设计目标本来不同：JPA 是对象持久化方案，假设你的操作以领域对象为单位；MyBatis 是 SQL 映射方案，假设你要精确控制每条 SQL。

数据库可移植性好，方言层屏蔽差异差，SQL 里的函数和分页语法都绑定具体数据库要同时支持 MySQL 与 PostgreSQL 的产品，JPA 优势明显

关于混用，唯一需要死守的边界是：同一张表的写操作只能由一个框架承担。原因回到本文第一节——JPA 的一级缓存不知道 MyBatis 在同一个事务里改过数据，之后 findById 会从身份映射表返回过期实体，而脏检查还会拿过期快照生成 UPDATE，把 MyBatis 的改动覆盖掉。这类 bug 在日志里看不出任何异常，排查成本极高。

MyBatis 侧另外两个必须知道的点。第一，#{} 编译成预编译语句的占位符，参数走绑定变量；${} 是字符串拼接，值直接进 SQL 文本。表名、列名、排序方向这类结构位置无法用绑定变量，不得不用 ${} 时必须用白名单校验取值，绝不能信任前端传来的字段名——参数化的完整边界见站内 SQL 注入防御。第二，二级缓存默认关闭是件好事，开启后它以 namespace 为粒度失效，任意一条写操作会清掉整个 mapper 的缓存，命中率低且极易在多表关联场景读到脏数据。

两段可以直接抄走的代码

第一段是抓取策略的正确写法，把「要什么数据」显式声明在查询层，而不是靠 open-in-view 兜底。

public interface OrderRepository extends JpaRepository<Order, Long> {

    // @EntityGraph 让这个方法用 LEFT JOIN FETCH 一次加载 items 和 buyer
    // 适用于不分页的场景：例如导出、单个聚合根的详情
    @EntityGraph(attributePaths = {"items", "buyer"})
    List<Order> findByStatus(OrderStatus status);

    // 列表页首选 DTO 投影：实体不进持久化上下文，没有脏检查、没有懒加载风险
    // 构造器投影要求 DTO 有完全匹配的构造函数，且写全限定类名
    @Query("""
            select new com.example.order.dto.OrderSummary(o.id, o.amount, b.name)
            from Order o join o.buyer b
            where o.status = :status
            """)
    Page<OrderSummary> findSummaries(@Param("status") OrderStatus status, Pageable pageable);
}

// record 做只读 DTO 非常合适：字段不可变、无样板代码
// 注意 record 不能当 JPA 实体，Hibernate 需要无参构造和可写字段
public record OrderSummary(Long id, BigDecimal amount, String buyerName) {}

第二段是乐观锁加重试。重点在重试的位置：必须在事务之外重试，因为冲突时事务已经标记回滚，在同一个事务里重试只会拿到不可用的持久化上下文。

@Entity
@Getter @Setter                      // 实体不要用 @Data，equals 与 toString 会引发懒加载
public class Account {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)   // MySQL 显式 IDENTITY，避免 AUTO 选到 TABLE 策略
    private Long id;

    private long balance;

    @Version
    private long version;            // Hibernate 自动在 UPDATE 末尾加 and version = ? 并递增
}

@Service
@RequiredArgsConstructor
public class AccountService {

    private final AccountRepository repo;
    private final TransactionTemplate txTemplate;   // 用编程式事务，重试边界清晰

    public void deduct(Long id, long amount) {
        int attempt = 0;
        while (true) {
            try {
                txTemplate.executeWithoutResult(status -> {
                    Account a = repo.findById(id).orElseThrow();
                    if (a.getBalance() < amount) {
                        throw new InsufficientBalanceException(id);
                    }
                    a.setBalance(a.getBalance() - amount);
                    // 这里不需要 repo.save(a)：a 是 managed 状态，提交时脏检查会生成 UPDATE
                });
                return;
            } catch (ObjectOptimisticLockingFailureException e) {
                // 版本冲突说明有并发写，退避后重试；上限必须有，否则热点行会把线程全部占住
                if (++attempt >= 3) {
                    throw e;
                }
                LockSupport.parkNanos(TimeUnit.MILLISECONDS.toNanos(10L * attempt));
            }
        }
    }
}

如果冲突率本身很高（例如秒杀的同一行库存），乐观锁重试会退化成活锁，此时该换成数据库的悲观锁 select ... for update，或者把并发压力挪到 Redis 层。判断标准是压测下的重试次数分布，不是感觉。

反模式对照表

反模式后果替代做法
实体直接作为 API 返回值暴露表结构与内部字段、序列化时触发懒加载引发 N plus 1、加字段即破坏接口契约一律经 DTO 或 record 转换，用投影直接查 DTO 更好
实体里写业务逻辑却依赖 Spring Bean实体由 Hibernate 反射构造，不走容器，注入的字段为 null逻辑放 Service 或领域服务；实体只保留不依赖外部的纯计算
所有关联用 EAGER查一条带出半个库，SQL 里出现十几个 JOIN，无法按场景裁剪全部 LAZY，按查询用 fetch 或投影声明所需数据
靠 open-in-view 兜底懒加载连接被持有到渲染结束，有效并发下降，视图层偷偷发 SQL设为 false，暴露的异常在查询层逐个修掉
随手开二级缓存跨事务脏读、集群下各节点缓存不一致、失效粒度粗需要缓存就在应用层显式做，失效策略自己掌握
用 ORM 写复杂报表生成的 SQL 无法优化，执行计划失控，改需求就得重写一堆 Criteria报表走原生 SQL 或 MyBatis，只读数据源隔离
在事务里 findAll() 再循环处理上下文膨胀、脏检查耗时、实体无法回收流式或分页处理，每批 flush 加 clear，或直接投影
用 saveAll 当批量插入本质是循环单条 insert，MySQL 自增主键下还攒不起 JDBC batch见 数据库性能优化 的批量写入方案
✅
最容易踩的坑
  • 对有主键的对象调 save() 会先发一条 SELECT：Spring Data 用主键判空来选 persist 还是 merge，merge 需要先加载数据库现值。热路径上这条额外查询要避开。
  • merge 的返回值必须接住：em.merge(user) 之后继续改原 user 对象，所有改动都不会入库，且没有任何报错。
  • 日志出现 HHH000104 就是事故：集合 fetch 配分页会把结果集全量拉进内存排序，测试环境无症状，线上一次 OOM。
  • @ManyToOne 默认 EAGER：这是 JPA 规范的坏默认值，不显式写 LAZY 就会产生意料之外的 JOIN 和额外查询。
  • @Enumerated 不写参数默认是 ORDINAL：以后往枚举中间插一个常量，数据库里的历史数据语义静默错位，不报错不告警。
  • 原生 SQL 查询前不会自动 flush：同事务内先改实体再用 nativeQuery 统计，统计结果不含本次改动。
  • 双向关联只维护集合侧不写外键：内存里关联在、数据库里外键为空，重启或换事务后关联凭空消失。
  • orphanRemoval 让 list.clear() 变成 DELETE：想「换一批子项」的写法会真删数据，且级联到子项的关联。
  • 实体上用 Lombok @Data：生成的 equals、hashCode、toString 会访问所有字段，包括懒加载代理，可能直接抛异常或引发 N plus 1。
  • 乐观锁重试写在事务内部：冲突时事务已标记回滚，内层重试拿到的是不可用上下文，必须在事务外重试。
  • MyBatis 与 JPA 同时写同一张表：JPA 一级缓存读到过期实体，脏检查还会用过期快照覆盖 MyBatis 的改动。
  • 把一级缓存当业务缓存：它随事务销毁、不跨请求、不跨节点，指望它扛读流量方向完全错。
