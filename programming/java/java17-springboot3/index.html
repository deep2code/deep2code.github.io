Java 8 升 17 与 Spring Boot 2 升 3 的实战路径

🏷️ Java 17

「我们还在 Java 8 加 Spring Boot 2，要升吗、怎么升」是这几年最常被问的实际问题。它不是技术选型题，而是一次工程改造：工作量集中在几个可以提前量化的地方，风险也可以通过拆分步骤控制。这篇给的是路径和踩坑清单，不是特性罗列。

JVM 内部的内存区域划分、GC 算法细节与调优参数不在本文范围，见站内 JVM 运行时模型 与 JVM 调优。

先算清收益：升级换来什么，风险在哪

值得升的理由不是「新版本更好」这种空话，而是几个具体的东西：容器环境下的资源识别、GC 停顿的量级变化、语言特性带来的代码量削减，以及 Java 21 的虚拟线程。

目标版本关键收益主要风险适合谁
Java 11容器资源感知（按 cgroup 限额算堆与 CPU 数，不再读宿主机）、模块系统落地、G1 成为默认反射访问 JDK 内部 API 开始被警告，某些老库会炸已经没人应该停在这里，它只是中转站
Java 17G1 停顿与内存占用持续改进、ZGC 转正式可用、record 与 sealed 与模式匹配、文本块；Boot 3 的最低要求强封装默认开启，反射访问 JDK 内部包从警告变成报错，需要显式加开放参数存量系统的第一目标版本
Java 21虚拟线程正式版、分代 ZGC、switch 模式匹配转正、序列化集合接口虚拟机行为变化较大，部分 agent 与字节码增强工具需要同步升级新项目直接从这里开始；存量系统在 17 稳定后再上
Boot 2.7Boot 2 分支的最后一站，废弃项都会给出明确警告开源维护已结束，安全补丁要靠商业支持升级过程中的强制中转站
Boot 3.xJakarta EE 9 以上基线、Micrometer 统一观测、原生镜像官方支持、3.2 起支持虚拟线程一键开启三个破坏性变更（命名空间、Security API、属性重命名）都要人工处理所有还在 Boot 2 的项目，排期问题不是要不要的问题
💡
容器里最值钱的那个改进

Java 8 早期版本在容器里读的是宿主机的 CPU 核数和内存总量，于是给 Pod 限了 1 核 2G，JVM 却按 64 核算出一堆 GC 线程、按宿主机内存算默认堆，结果不是频繁 OOMKilled 就是线程数爆炸。这个问题在 Java 10 之后才被系统性解决（UseContainerSupport 默认开启）。如果你的服务跑在 K8s 上还用着 Java 8 的老小版本，升级的收益里这一条往往比语言特性更直接。

Java 17 的语言特性，哪些在业务代码里真的有用

不是每个新特性都值得推广。按「能减少多少缺陷」排序，真正有价值的是两个：record 削掉 DTO 的样板代码，sealed 加模式匹配 switch 把「漏处理一个分支」从运行期 bug 变成编译错误。

特性实际价值适用边界常见误用
record一行声明替代构造器、getter、equals、hashCode、toString；字段天然不可变，能安全跨线程传递DTO、查询结果、事件载荷、值对象拿来当 JPA 实体。Hibernate 需要无参构造和可写字段，record 两样都没有
sealed 加模式匹配 switch编译器做穷尽性检查，新增一个子类型后所有未覆盖的 switch 直接编译失败状态机、审批流、消息类型分发、结果类型建模只用 sealed 不用 switch 表达式，穷尽性检查就白费了
文本块多行 SQL 与 JSON 不再拼接加转义，格式和真实内容一致JPQL、原生 SQL、测试里的 JSON 断言把用户输入拼进文本块里的 SQL，它不提供任何注入防护
var去掉右侧已经写明类型时的重复右侧是构造调用或明确的工厂方法右侧是链式调用或泛型方法时用 var，读代码的人得跳转才知道类型
Optional把「可能没有」写进方法签名只作为返回值当参数、当字段、或者 get() 前不判断——后者比直接返回 null 更糟，因为它多绕了一层
增强的 instanceof判断与强转合并成一步，少一个中间变量处理异构输入、反序列化后的类型分发用它堆出一长串 if else，其实该改成 sealed 加 switch
// 1) record 做不可变 DTO：没有 getter 样板，字段名即访问方法名
//    紧凑构造器里做校验，保证任何实例一旦创建就是合法的
public record OrderCommand(String orderNo, BigDecimal amount, String buyerId) {
    public OrderCommand {
        if (amount == null || amount.signum() <= 0) {
            throw new IllegalArgumentException("金额必须为正");
        }
        Objects.requireNonNull(orderNo, "orderNo 不能为空");
    }
}

// 2) sealed 把「结果的所有可能」封闭起来，permits 列出全部实现
public sealed interface PayResult permits Success, Pending, Failed {
    record Success(String tradeNo, BigDecimal paid) implements PayResult {}
    record Pending(Duration retryAfter) implements PayResult {}
    record Failed(String code, String message) implements PayResult {}
}

public String describe(PayResult result) {
    // 因为 PayResult 是 sealed，switch 覆盖了全部子类型时不需要 default
    // 关键收益：以后往 permits 里加一种结果，这个 switch 会直接编译失败，而不是静默走 default
    return switch (result) {
        case Success s -> "已支付 " + s.paid() + " 流水 " + s.tradeNo();
        case Pending p -> "处理中，请在 " + p.retryAfter().toSeconds() + " 秒后重试";
        case Failed f -> "失败 " + f.code() + " " + f.message();
    };
}

// 3) 文本块写 SQL：格式与真实 SQL 一致，便于直接复制到客户端里执行
//    注意参数仍然必须用占位符，文本块不提供任何注入防护
private static final String TOP_BUYERS = """
        select b.id, b.name, sum(o.amount) as total
        from orders o
                 join buyer b on b.id = o.buyer_id
        where o.created_at >= ?
          and o.status = 'PAID'
        group by b.id, b.name
        order by total desc
        limit ?
        """;

Boot 3 破坏性变更一：javax 全面改成 jakarta

Boot 3 的升级工作量几乎全部集中在三个破坏性变更上：命名空间迁移、Security 配置 API 重写、属性重命名。它们都是编译期或启动期能发现的问题，不会在线上突然炸，但都需要人工逐处处理，没有银弹。

其中命名空间迁移的工作量最大。Jakarta EE 从 Oracle 移交给 Eclipse 基金会后，因为商标限制无法继续使用 javax 包名，全部规范接口改为 jakarta 前缀。Boot 3 的基线是 Jakarta EE 9 以上，所以整个 Web 层、持久层、校验层的 import 都要改。

正确的顺序是先扫依赖、再动代码。如果依赖树里有一个无人维护又无法替换的库还在用 javax，那这次升级的第一件事应该是解决它，而不是先把自己的 import 改完才发现走不通。

破坏性变更二：Spring Security 配置 API 重写

WebSecurityConfigurerAdapter 被彻底移除，配置方式从「继承适配器重写方法」改成「注册 SecurityFilterChain Bean」。这不只是换写法：新模型允许在一个应用里注册多条链，各自用 securityMatcher 划定作用范围，比以前用一个大 configure 方法糊在一起清晰得多。

// ========== Boot 2 的旧写法（在 Boot 3 里是编译错误，父类已被删除）==========
@Configuration
public class OldSecurityConfig extends WebSecurityConfigurerAdapter {
    @Override
    protected void configure(HttpSecurity http) throws Exception {
        http.csrf().disable()
            .authorizeRequests()
                .antMatchers("/public/**").permitAll()
                .anyRequest().authenticated()
            .and()
            .sessionManagement().sessionCreationPolicy(SessionCreationPolicy.STATELESS);
    }
}

// ========== Boot 3 的新写法 ==========
@Configuration
@EnableWebSecurity
public class SecurityConfig {

    // 多条链靠 Order 决定匹配顺序，第一条只管 /api 前缀，其余请求交给后面的链
    @Bean
    @Order(1)
    public SecurityFilterChain apiChain(HttpSecurity http) throws Exception {
        return http
                // securityMatcher 限定这条链的作用范围，取代以前一个方法配全部的写法
                .securityMatcher("/api/**")
                // 纯 Token 接口没有浏览器表单，关掉 CSRF 是合理的；有 Cookie 会话时不要照抄
                .csrf(AbstractHttpConfigurer::disable)
                // authorizeRequests 改名为 authorizeHttpRequests，antMatchers 改名为 requestMatchers
                .authorizeHttpRequests(reg -> reg
                        .requestMatchers("/api/public/**").permitAll()
                        .requestMatchers("/api/admin/**").hasRole("ADMIN")
                        .anyRequest().authenticated())
                // 无状态：不创建也不使用 HttpSession，横向扩容时不需要会话共享
                .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
                .oauth2ResourceServer(o -> o.jwt(Customizer.withDefaults()))
                .build();
    }

    @Bean
    @Order(2)
    public SecurityFilterChain webChain(HttpSecurity http) throws Exception {
        return http
                .authorizeHttpRequests(reg -> reg
                        .requestMatchers("/actuator/health/**").permitAll()
                        .anyRequest().authenticated())
                .formLogin(Customizer.withDefaults())
                .build();
    }
}
⚠️
迁移时最容易改错的一处

antMatchers 改成 requestMatchers 不只是改名：新版本的路径匹配对尾部斜杠和后缀的处理更严格，以前靠 /user 能顺带匹配 /user/ 的写法可能不再成立。权限规则改完必须有自动化测试逐条验证，尤其是「哪些路径允许匿名」这一类，改错的后果是接口裸奔，而且不会有任何报错。越权与鉴权的完整检查清单见站内 越权与鉴权。

破坏性变更三是配置属性的重命名与移除。Boot 3 清理了大量在 2.x 时代标记为废弃的属性。麻烦之处在于写错的属性名不会报错，Spring 只会静默忽略它，于是配置看起来配了、实际用的是默认值。这类问题在测试环境常常发现不了，因为默认值往往也能跑。

处理方式是临时引入 spring-boot-properties-migrator：它会在启动时扫描所有配置源，把「已重命名」的属性打印出新旧对照并临时映射，把「已移除」的属性直接报错。按它的输出改完配置后务必把这个依赖删掉，它有运行期开销，而且留着会掩盖以后的新问题。

升级顺序：一次只动一个变量

失败的升级几乎都有同一个特征：JDK、Boot、依赖一起换，跑起来报错时无法判断是哪个变量引起的。下面这条路径的每一步都只动一个变量，每一步都能独立发布和回滚。

步骤动了什么验证清单回退方式
第一步 升到 Boot 2.7只改 Boot 与 Cloud 的 BOM 版本编译零警告；全量回归；确认启动日志里的废弃提示都已处理回滚 pom 版本号，重新发布
第二步 换 JDK 17编译与运行的 JDK，CI 镜像，基础镜像启动无反射报错；GC 日志对比停顿与堆占用；字节码增强类工具（APM 探针、代码覆盖率、Mock 框架）能正常工作切回旧基础镜像；字节码版本已升到 17 的产物不能在 8 上跑，必须重新构建
第三步 升 Boot 3命名空间、Security 配置、属性名、第三方库版本全部接口的鉴权规则逐条测试；序列化格式前后对比；定时任务与消息消费验证；actuator 端点路径确认回滚整个发布；这一步改动最大，建议单独一个分支且不夹带业务需求
第四步 升 Java 21 与虚拟线程JDK 版本，一个开关先只升 JDK 不开虚拟线程观察一周；再灰度单实例开启，看线程数、延迟分布、数据库连接池等待时间关掉虚拟线程开关即可回到平台线程，不需要回滚代码
❌
升级分支不要夹带业务改动

升级 PR 里混着新功能，是这类项目最常见的失控原因：出问题时无法判断是升级导致的还是新功能导致的，回滚又会把业务需求一起回滚掉。升级分支应该做到「diff 里只有版本号、import、配置和 API 适配」，任何行为变更都要单独说明。

依赖兼容性排查：最耗时的一环

这一步的产出是一张表：项目里每个直接依赖，当前版本、支持 jakarta 的最低版本、有没有可用替代。先把表填完再动手，能避免改到一半发现走不通。

# 1) 找出依赖树里还在引用旧命名空间的包（Boot 3 的硬阻塞项）
mvn dependency:list -DoutputFile=/tmp/deps.txt -DincludeScope=runtime
grep -iE "javax\.(servlet|persistence|validation|annotation|transaction|xml\.bind)" /tmp/deps.txt

# 2) 直接扫 jar 里的字节码引用，比看坐标名更可靠：有些库坐标没变但内部仍引用 javax
for j in $(find ~/.m2/repository -name "*.jar" -newer /tmp/deps.txt); do
  unzip -l "$j" | grep -q "javax/servlet" && echo "含旧命名空间: $j"
done

# 3) 注解处理器必须同步升级，否则编译期直接失败或生成错误代码
mvn dependency:tree -Dincludes=org.projectlombok:lombok,org.mapstruct:mapstruct,com.querydsl

# 4) 检查 jar 的字节码主版本号（52 是 Java 8，61 是 Java 17，65 是 Java 21）
javap -verbose -cp target/app.jar com.example.Application | grep "major version"

# 5) 用 Boot 官方的迁移检查工具跑一遍（会给出属性重命名与 API 变更报告）
mvn -Dspring-boot.version=3.x.x spring-boot:build-info 2>&1 | tail -40
依赖类型为什么必须同步升级不升的症状
Lombok它直接操作编译器内部 AST，JDK 每升一个大版本都可能不兼容编译期抛内部错误，堆栈全是编译器类名，看不出和 Lombok 有关
MapStruct生成的映射代码里会引用 javax 注解生成的类编译不过，或运行期找不到注解类
QueryDSL依赖 JPA 元模型，注解处理器要用 jakarta 版本的 classifierQ 类根本没生成，报符号找不到
APM 探针与字节码增强 agent它们按字节码版本解析类文件启动时 agent 报错，或者静默不采集数据，监控图表变空
JSON 与序列化库反射策略受强封装影响反序列化私有字段失败，需要加开放模块参数
单元测试框架与 Mock 库要生成动态代理与操作字节码测试大面积失败，报无法定义类

虚拟线程：它解决的是一个很具体的问题

虚拟线程（Java 21 正式版，Boot 3.2 起支持一键开启）经常被说成「性能银弹」，这是误读。它解决的问题非常具体：传统的一请求一平台线程模型下，线程在等待 IO 时白占着约 1 MB 栈空间和一个操作系统线程，所以并发上限被线程数卡死在几百。虚拟线程由 JVM 调度，阻塞时会把自己从载体线程上卸下来，让载体线程去跑别的虚拟线程。

所以收益的前提是阻塞等待占了大头：调数据库、调下游 HTTP、读缓存。对 CPU 密集的计算任务，虚拟线程一点帮助都没有——CPU 本来就没闲着。

sequenceDiagram autonumber participant VT1 as 虚拟线程 A participant CT as 载体线程
ForkJoinPool 里的平台线程 participant VT2 as 虚拟线程 B participant IO as 数据库或下游 VT1->>CT: 挂载开始执行 VT1->>IO: 发起阻塞式查询 Note over VT1,CT: 正常情况 遇到阻塞点自动卸载
栈帧搬到堆上保存 VT1-->>CT: 卸载 让出载体线程 CT->>VT2: 载体线程转去执行 B IO-->>VT1: 结果返回 VT1->>CT: 重新挂载到任意可用载体线程 继续执行 Note over VT2,CT: 异常情况 B 进入 synchronized 块 VT2->>VT2: 在 synchronized 内部再阻塞 Note over VT2,CT: 载体线程被钉住 无法被别人复用
此时退化成平台线程模型 收益消失

钉住（pinning）是判断能否获得收益的关键。虚拟线程在两种情况下无法卸载：在 synchronized 块或方法内部阻塞，以及执行某些 native 方法。早期 JDK 版本里 synchronized 的限制更严格，后续版本在逐步改善，但升级前不能假设它已经不是问题——正确做法是用 JFR 的钉住事件实测。

场景虚拟线程收益原因
大量并发的数据库查询接口明显等待 SQL 返回的时间远大于计算时间；但并发上限仍受数据库连接池大小限制
聚合多个下游接口的 BFF 层明显典型的 IO 等待叠加，以前要靠异步编排才能做到的并发，现在写同步代码即可
图片处理、加解密、序列化密集几乎没有CPU 密集，瓶颈在核数不在线程数
热点路径上有 synchronized 同步块可能为负钉住载体线程，且虚拟线程的挂载卸载本身有开销
大量使用 ThreadLocal 缓存对象可能为负线程数从几百涨到几万，每线程一份副本会让内存暴涨；应改用 ScopedValue 或参数传递
依赖线程池做限流的系统需要改造线程池不再限制并发，必须换成信号量或令牌桶，否则下游会被压垮
spring:
  threads:
    virtual:
      # Boot 3.2 起的一键开关：Tomcat 的请求处理、@Async、定时任务都会改用虚拟线程
      # 建议先在单个实例上打开做灰度，观察 P99 与数据库连接池等待时间再放量
      enabled: true

  datasource:
    hikari:
      # 关键点：虚拟线程不会放大数据库的承载能力
      # 能同时执行 SQL 的数量始终等于连接数，这里才是真正的并发闸门
      maximum-pool-size: 30
      # 虚拟线程下并发请求数可能远超连接数，获取连接的等待会变多，超时要显式设短一点便于快速失败
      connection-timeout: 2000

server:
  tomcat:
    threads:
      # 开了虚拟线程后这个值不再是并发上限，但保留一个合理值以防开关被关闭时暴露问题
      max: 200

management:
  metrics:
    enable:
      all: true
    # 观察这几个指标判断效果：
    # executor.active 线程活跃数、hikaricp.connections.pending 连接等待、http.server.requests 的分位延迟
⚠️
先别全量切换

推荐的节奏是：先只升 JDK 到 21 不开虚拟线程，观察一周确认 JVM 层面没问题；再挑一个 IO 密集且不含 synchronized 热点的服务，单实例开启，对比开启前后的 P99 延迟、线程数、连接池等待队列长度；确认收益后再逐步放量。用 -Djdk.tracePinnedThreads=full 或 JFR 的钉住事件先做一次静态摸底，比上线后猜原因高效得多。

GraalVM 原生镜像：什么时候值得

原生镜像把 Java 应用提前编译成本机可执行文件，收益是启动时间从秒级降到几十毫秒、内存占用降到几分之一。代价同样清晰：所有反射、动态代理、资源加载、序列化都必须在构建期被登记，构建时间从一分钟量级涨到十分钟量级，而且失去了运行期即时编译的优化空间。

升级后的验证清单与常见报错对照

下面这张表是发布后按顺序过一遍的清单，以及遇到报错时的对照关系。多数报错的表象和真实原因离得很远，记住对应关系能省掉大量搜索时间。

报错或现象真实原因处理
ClassNotFoundException: javax.servlet.Filter某个依赖还是 Boot 2 时代的版本，仍引用旧命名空间扫依赖树定位该库，升到支持 jakarta 的版本或替换
启动报 InaccessibleObjectException 或反射访问被拒绝Java 17 的强封装默认生效，反射访问 JDK 内部包不再只是警告优先升级越界访问的那个库；实在不行才加 --add-opens 参数，并记录原因
编译期抛编译器内部错误，堆栈全是编译器类Lombok 版本与新 JDK 不兼容升 Lombok 到支持该 JDK 的版本，这类问题通常没有其他解法
接口全部返回 401 或 403，或者反过来全部可匿名访问Security 配置迁移时匹配规则写错，或多条链的顺序不对用自动化测试逐条断言路径与角色的对应关系，不要靠人工点击验证
配置项明明写了却不生效属性在 Boot 3 被重命名，Spring 静默忽略未知属性临时加 spring-boot-properties-migrator 看对照报告，改完移除
监控图表突然变空，APM 里看不到链路探针 agent 与新字节码版本不兼容，或还在用 Sleuth升级探针；链路改用 Micrometer Tracing，见 Spring Cloud 组件演进
时间字段序列化格式变了，前端解析失败Jackson 与日期模块版本变化导致默认格式不同显式配置日期序列化格式，并在契约测试里固定住
开了虚拟线程后吞吐没涨甚至下降热点路径上有 synchronized 钉住载体线程，或瓶颈本来就在数据库连接数用 JFR 钉住事件定位，把 synchronized 换成 ReentrantLock；连接池才是真正的闸门
内存占用比升级前高一截虚拟线程下 ThreadLocal 副本数量随线程数放大改用 ScopedValue 或显式参数传递，别用 ThreadLocal 缓存大对象
反模式后果正确做法
一次性升 JDK、Boot 和所有依赖出问题无法判断变量来源，回滚粒度粗，排查时间成倍增加按四步走，每步只动一个变量且能独立回滚
升级不跑全量回归，只做冒烟测试序列化格式、鉴权规则、时区、数值精度这类变化不会报错，只会算错升级前先补齐关键路径的自动化测试，把它当升级的前置任务
把 record 当 JPA 实体Hibernate 需要无参构造与可写字段，启动就失败；即使绕过也拿不到脏检查能力实体用普通类，record 用于 DTO 与投影，见 JPA 持久化上下文
开了虚拟线程还保留大线程池既失去了线程池的限流作用，又多一层无意义的排队限流改用信号量或令牌桶；线程池要么去掉要么保持很小
为了「现代化」上原生镜像构建时间暴涨、排障手段大幅减少，收益只有几秒启动时间常驻服务用 CDS 或 AOT 优化启动；原生镜像留给 Serverless 与 CLI
用 --add-opens 绕过所有强封装报错问题被推迟，下一个大版本可能彻底关闭这个后门优先升级越界的库，保留的每一条参数都要写清原因和清理计划
升级分支夹带业务需求出问题无法区分来源，回滚会连带丢掉业务改动升级 PR 的 diff 里只有版本、import、配置与 API 适配
把 spring-boot-properties-migrator 留在生产有运行期开销，且会掩盖后续新增的配置问题改完配置立刻移除依赖
✅
最容易踩的坑
  • 以为 jakarta 迁移只是改自己的 import：真正的阻塞点是第三方库，其中任何一个没有兼容版本都能挡住整次升级，所以第一步是扫依赖树而不是改代码。
  • Java 17 的强封装把反射警告变成了报错：Java 11 上只打 warning 的越界访问，在 17 上直接抛异常，这是第二步升级最常见的卡点。
  • Lombok、MapStruct、QueryDSL 必须同步升级：注解处理器直接操作编译器内部，版本不匹配时报错信息完全看不出和它们有关。
  • antMatchers 改成 requestMatchers 后匹配语义更严：尾部斜杠与路径通配的行为有变化，改错会让本该鉴权的接口裸奔且不报任何错。
  • 配置属性写错不会报错：Spring 静默忽略未知属性，看起来配了实际用默认值，测试环境往往发现不了。
  • record 不能当 JPA 实体：没有无参构造、字段不可写，Hibernate 用不了。
  • sealed 只写了不配模式匹配 switch：穷尽性检查是这个特性最大的价值，不用 switch 表达式等于白封装。
  • 虚拟线程被 synchronized 钉住：热点路径上有同步块时，载体线程无法被复用，退化成平台线程模型，收益归零。
  • 虚拟线程放大不了数据库并发：能同时执行 SQL 的数量等于连接池大小，线程再多也只是排在连接池门口等。
  • 虚拟线程下 ThreadLocal 会让内存暴涨：线程数从几百变几万，每线程一份副本，缓存大对象的写法必须改掉。
  • 第二步升级后的产物无法在旧 JDK 上运行：字节码版本已经升级，回滚必须回滚到旧构建产物，不能只换运行时。
  • 常驻服务上原生镜像：失去 jstack、JFR、agent 等全部排障手段，换来的只是几秒启动时间。
