Rust 在后端的适用边界与工程代价

🏷️ Rust

这篇不讲语法，只回答两个工程问题：Rust 用什么代价换来了什么保证，以及你手上这个后端组件值不值得付这个代价。

借用检查消灭的是「内存的时间维度」错误

释放后使用、重复释放、悬垂引用、遍历容器时又往里插元素——症状各异，本质是同一件事：某个引用的可用时间超过了被引用数据的存活时间。这类 bug 的崩溃现场和真正的错误位置相隔很远，靠 review 查不出来。Rust 把它变成编译期约束：同一时刻要么存在一个可变借用，要么存在多个共享借用；引用不得长于被借用值。2018 edition 引入的非词法生命周期让借用在最后一次使用处结束，早年「借用检查太蠢」的吐槽多半说的是这之前的编译器。

关键是把边界讲清楚，否则很容易得出「编译过了就安全」的错误结论：

问题类别编译期能否拦住拦不住时靠什么兜
悬垂引用 / 释放后使用 / 重复释放能，所有权与借用检查直接报错—
遍历中修改容器能，迭代器持有容器借用—
跨线程数据竞争能，靠 Send / Sync 约束—
死锁、加锁顺序反转不能全局统一加锁顺序、try_lock 加超时
先判断后写入的逻辑竞态不能判断与写入放进同一临界区，或改用 CAS
内存泄漏不能，Rc 循环与 mem::forget 都是安全代码子指父改 Weak、上 heap profiler
整数溢出不完全：debug 档 panic，release 档静默回绕checked_add，或 profile 开 overflow-checks
unsafe 块内的裸指针与别名违规不能，是局部豁免收窄 unsafe 面积、用 Miri 跑测试

所以它的价值不是「不出 bug」，而是把一整类无法靠测试稳定复现的错误变成了编译错误；代价是这些约束必须在动手写的时候就想清楚。

Send 与 Sync：数据竞争被写进了类型系统

Send 表示所有权可以移动到另一个线程，Sync 表示共享引用可以被多个线程同时持有。两者都是 auto trait，编译器按字段递归推导，只有 unsafe impl 能手动声明。一个常被讲错的关系：&T 能不能跨线程传取决于 T 是不是 Sync，而不是 Send——这正是 RefCell 可以被移动却不能被共享的原因。

类型SendSync你通常在哪撞上
Rc<T>否（计数非原子）否闭包里用了它，报错却指向 spawn 那一行
RefCell<T>是否Arc<RefCell<T>> 编译不过，要换 Mutex
std::sync::MutexGuard否是守卫跨 .await，整个 future 失去 Send
*const T / *mut T否否自写的 FFI 包装结构体莫名不是 Send
async 块生成的 future取决于跨 await 持有的所有值报错里出现一长串匿名类型

选机制的优先顺序是：独占借用 > 消息传递 > 原子类型 > 锁。三个容易忽略的点：RefCell 借用冲突是运行期 panic 而不是编译错误；标准库 RwLock 不保证公平，读多时可能写饥饿；thread_local! 在异步里不可靠，任务被 work-stealing 迁到另一个 worker 后数据就「消失」，要改用运行时提供的 task local。

use std::sync::Arc;
use tokio::sync::Mutex as AsyncMutex;

// Arc 负责「多所有者」，Mutex 负责「同一时刻只有一个可变访问」，两件事分开看。
// 换成 Rc 会编译失败：Rc 不是 Send，进不了 tokio::spawn 要求的 Send + 'static 闭包。
#[derive(Clone)]
struct Counter {
    inner: Arc<AsyncMutex<u64>>,
}

impl Counter {
    async fn incr_and_flush(&self) -> u64 {
        // 用异步锁的唯一理由：临界区里真的要 await（下面的 persist）。
        // 如果临界区只是 *g += 1，标准库的 Mutex 更快。
        let mut g = self.inner.lock().await;
        *g += 1;
        persist(*g).await;
        *g
    } // g 在这里 drop，锁释放

    // 反例：标准库守卫跨 await，future 失去 Send，报错会指到 spawn 那一行。
    // async fn bad(m: &std::sync::Mutex<u64>) {
    //     let g = m.lock().unwrap();
    //     tokio::task::yield_now().await;
    //     drop(g);
    // }
}

async fn persist(v: u64) { let _ = v; }

异步 Rust 的复杂度来自四个地方

一、Future 是惰性的。调用 async fn 只构造出一个状态机，没人 poll 就一行业务代码都不跑；忘写 .await 不是编译错误，只有一条 unused_must_use 警告。二、运行时不在标准库。标准库只给 Future、Waker、Context 这套接口，执行器、定时器、异步 IO 全在第三方运行时里，生态因此按运行时分裂。三、Pin 是为自引用服务的，不是性能优化。跨 .await 持有的局部变量会成为状态机的字段，指向它们的引用让状态机指向自己，一旦移动内部指针就失效。四、取消等于 drop。超时或 select! 落败会把 future 在它停住的那个 await 点直接丢掉，已产生的副作用不回滚，只有 Drop 会执行。

阻塞调用为什么会让 p99 突刺

多线程执行器的 worker 数默认等于 CPU 核数。一个 worker 上只要有任务在同步读盘、同步压缩，或者长时间占着标准库的锁，它就没法去 poll 排在同一队列里的其他任务。线上现象很有欺骗性：CPU 没跑满，p99 却飙升——瓶颈是可运行的 worker 数，不是算力。

sequenceDiagram participant W as worker-0 participant A as 任务 A 内含阻塞调用 participant B as 任务 B 排在同队列 participant P as 阻塞线程池 W->>A: poll A->>A: 同步读盘，期间线程完全不可用 Note over W,B: worker-0 被占死，任务 B 只能排队
现象是 CPU 没跑满但 p99 突刺 A-->>W: 终于返回 Ready W->>B: poll 这才开始 Note over W,P: 改法：把阻塞挪出 worker W->>A: poll A->>P: 提交到阻塞线程池 A-->>W: 立刻返回 Pending W->>B: worker 马上去跑任务 B P-->>A: 读完，通过 Waker 唤醒
阻塞来源处置方式注意事项
同步文件 IO挪进阻塞线程池tokio 的阻塞线程池上限默认 512，打满后提交会排队
CPU 密集计算交给 rayon 这类计算线程池别丢进阻塞池：它是为「等待」设计的，长期占用会撑满
只有同步驱动的数据库阻塞线程池 + 自己的连接池并发上限由线程数决定，别超过数据库连接数
标准库锁的长临界区缩短临界区锁内不做 IO 是根本解，换异步锁只是缓解
无 await 点的紧密循环循环里定期让出不让出则同 worker 上的任务被饿死
 
use std::time::Duration;
use tokio::time::timeout;

// 两个问号：第一个解 JoinError（任务 panic 了），第二个解业务错误。
async fn load_config(path: String) -> anyhow::Result<String> {
    let content = tokio::task::spawn_blocking(move || std::fs::read_to_string(path)).await??;
    Ok(content)
}

// 取消安全：timeout 会把里面的 future 直接 drop。
// 写成 timeout(d, do_transfer()) 的语义是「做到一半就不做了」，已落库的一半不回滚。
// 要原子性就把逻辑 spawn 成独立任务，让超时只作用在「等结果」上。
async fn transfer_with_deadline(from: u64, to: u64, amount: i64) -> anyhow::Result<()> {
    let task = tokio::spawn(async move { do_transfer(from, to, amount).await });
    match timeout(Duration::from_secs(3), task).await {
        Ok(joined) => joined?,
        // 这里只是不等了，后台任务仍会跑完；真要中断得显式 abort 并接受中间态。
        Err(_elapsed) => anyhow::bail!("transfer timeout, task still running"),
    }
}

async fn do_transfer(_f: u64, _t: u64, _a: i64) -> anyhow::Result<()> { Ok(()) }

错误处理：问号运算符的便利与它的边界

Result 只是普通枚举，? 做的事情是「是 Err 就提前 return，顺手用 From 转一次类型」。便利的代价是错误类型的层次要你自己设计。原则很简单但违反的人很多：库返回能被穷尽匹配的具体枚举，应用才用擦除了类型的动态错误。库里图省事对外抛 anyhow::Error，下游就只能 downcast 或者匹配错误字符串来决定要不要重试。另外 ? 会吃掉上下文，跨层传递要显式补 context；panic = "abort" 会关掉栈展开，此时 catch_unwind 兜不住任何东西。

方案调用方能否分支处理上下文与回溯该用在哪
thiserror 派生的错误枚举能，可穷尽 match靠 #[from] 保留 source 链库、领域层、要做重试判定的边界
anyhow::Error只能 downcast有回溯与 context 链可执行程序、应用层、main
Box<dyn Error + Send + Sync>只能 downcast无自动上下文不想加依赖的小库
返回 String不能无别在生产代码里这么干
panic! / unwrap不能有回溯只用于「不变量已破坏，继续跑没意义」

编译时间与依赖树是要计入工期的成本

编译单元是 crate 而不是文件：一个塞了几万行的巨型 crate，改一行注释也要整体重编加重新链接。它影响的不是「流水线慢几分钟」，而是一天能做多少次改-跑-看的循环。排查顺序是固定的：cargo build --timings 找耗时最长的单元，cargo llvm-lines 找单态化最狠的函数，cargo tree -d 找被同时编译的多版本依赖；然后按依赖方向拆 workspace、冷路径改 dyn Trait、削减过程宏面积、换链接器。日常只做类型检查时用 cargo check，能省掉代码生成和链接两步。

# Cargo.toml —— 开发档以「改一行到看到结果」的速度为优先
[profile.dev]
debug = "line-tables-only"    # 只留行号，去掉完整调试信息，链接明显变快
split-debuginfo = "unpacked"  # macOS 上避免每次构建都跑 dsymutil

[profile.dev.package."*"]     # 依赖用 opt-level 1 编，自己的代码保持 0
opt-level = 1                 # 依赖很少改，编一次受益很久，跑测试也快得多

[profile.release]
codegen-units = 16            # 默认 16；调成 1 配合 fat LTO 还能挤一点运行时性能
lto = "thin"                  # fat LTO 编译时间涨得凶，收益必须实测
# panic = "abort"             # 能缩体积，但会让 catch_unwind 与 FFI 兜底全部失效

# .cargo/config.toml —— 链接是串行瓶颈，换链接器性价比最高
[target.x86_64-unknown-linux-gnu]
rustflags = ["-C", "link-arg=-fuse-ld=mold"]

FFI 与渐进式改造：只把热点换掉

「用 Rust 重写」在多数团队都是错误决策——要重写的不只是代码，还有几年积累的补丁、边界处理和对接过的第三方 SDK。务实路线是压测定位热点，再把编解码、压缩、加解密、规则匹配、向量计算这类计算密集且接口面很窄的部分做成库：Go 走 cgo，Java 走 JNI 或 JDK 22 起正式的 FFM，Python 走 PyO3。边界有五条硬规则：只传 POD 与「指针加长度」，不要把 String、Vec 本身跨出去；谁分配谁释放，导出函数必须成对；跨界结构体加 #[repr(C)]；panic 不许越界；接口必须批量化，否则跨语言调用的固定开销会把计算收益全吃掉。

// Cargo.toml: [lib] crate-type = ["cdylib", "staticlib"]
use std::os::raw::c_int;
use std::panic::catch_unwind;
use std::slice;

/// 一次传进来一批数据，而不是每条记录调一次 —— 否则 cgo / JNI 的固定开销会盖过收益。
/// 2024 edition 起 no_mangle 这类属性必须写成 unsafe(no_mangle)。
#[unsafe(no_mangle)]
pub unsafe extern "C" fn crc32_batch(ptr: *const u8, len: usize, out: *mut u32) -> c_int {
    // Rust 1.81 起 extern "C" 里的 panic 会直接 abort 进程（此前是未定义行为），
    // 所以必须自己兜住转成错误码。前提是 profile 里没设 panic = "abort"。
    let r = catch_unwind(|| {
        if ptr.is_null() || out.is_null() {
            return -1;                        // -1：参数非法
        }
        let buf = unsafe { slice::from_raw_parts(ptr, len) };
        let v = crc32fast::hash(buf);
        unsafe { *out = v };
        0
    });
    r.unwrap_or(-2)                           // -2：Rust 侧 panic 已被捕获
}

什么场景值得用 Rust，什么场景 Go 或 Java 更合适

核心问题从来不是「Rust 快不快」，而是你的延迟被什么决定：如果 99% 的时间花在等数据库和下游 HTTP，换语言基本没有收益。

值得用的场景有共性：每个字节都要流经你的代码（网关、代理、协议转换、存储与消息组件的编解码层）、计算内核（向量检索、压缩、加解密、规则匹配）、常驻且内存敏感（边缘节点与 sidecar）、要单文件零运行时依赖分发的 CLI 与采集器，以及 WASM 目标。不值得的同样有共性：每周都在改的业务 CRUD、重事务与工作流编排、要对接一大堆云厂商与支付 IM SDK 的胶水层——这些地方决定成败的是迭代速度和生态覆盖。

❌
最容易踩的坑
  • unsafe 不关闭借用检查。它只解锁解引用裸指针、调 unsafe 函数、访问可变静态变量、实现 unsafe trait、读 union 字段这五件事，别名规则照旧生效。
  • 标准库 MutexGuard 跨 .await。future 失去 Send，报错却指向几十行外的 spawn。
  • 把异步锁当成「更好的 Mutex」。它更慢，存在理由只是「持锁期间要 await」。
  • 忘写 .await。Future 惰性，只有一条警告；CI 必须把 unused_must_use 当错误。
  • select! 落败分支的 future 被 drop。已写进数据库的一半不会回滚，要原子性就 spawn 出去只等结果。
  • 异步任务里用 thread_local! 存请求上下文。任务被迁移到另一个 worker 后数据「消失」，改用 task local。
  • 在 worker 线程上跑同步压缩或紧密循环。现象是 CPU 没跑满但 p99 飙升，先看可运行 worker 数而不是 CPU。
  • Rc / Arc 循环引用照样泄漏。Drop 永远不会被调用，子指父必须用 Weak。
  • release 档整数溢出静默回绕。debug 档 panic 给了虚假的安全感，计费与库存必须用 checked_*。
  • 库对外返回 anyhow::Error。下游只能靠匹配错误字符串判断能不能重试，库该用 thiserror。
  • panic = "abort" 与 catch_unwind 并存。栈展开被关掉，FFI 边界的兜底完全失效。
  • FFI 接口按单条记录设计。跨语言调用的固定开销会把 Rust 省下的计算全部吃掉。
