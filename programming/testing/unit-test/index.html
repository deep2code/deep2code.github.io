单元测试怎么写：结构、边界枚举与 Mock 边界

🏷️ 单元测试

这篇只谈一件事：单元测试的代码具体怎么落笔。为什么该写测试、金字塔怎么分层、可测性怎么设计，详见站内测试策略一篇；测试在流水线哪个阶段跑，详见站内 CI/CD 专题。

「单元」是一个行为，不是一个函数

「单元测试就是测一个函数」这句话是绝大多数 Mock 泛滥的源头。如果单元等于类，那么一个类被拆成三个之后，原来的一个测试就得改成三个——而外部行为一点没变。测试本该保护重构，结果它成了重构的税。

更稳固的定义是：单元 = 一个可以用业务语言描述的行为，边界在这个行为的入口上。内部由几个类协作完成不重要，重要的是这些协作对象是不是同一进程内、是不是确定的。是，就用真的。

维度粒度一：围绕单个类粒度二：围绕一个行为
测试入口某个类的某个公开方法一个用例的入口，比如「取消订单」
替身数量类的每个依赖都被替身，常见五到十个只有跨进程与不确定依赖被替身，通常一到两个
内部重构（拆类、合类、改方法名）测试必然要改，且改量与拆分程度成正比测试一行不用改
能发现的 bug只能发现「实现变了」；自家计算算错了发现不了能发现业务规则算错、状态流转错、幂等失效
失败定位定位到类，但常常是替身配置错了而不是代码错了定位到一条业务规则，直接能写进工单
覆盖率形态数字高，但很多覆盖来自替身配置数字略低，分支覆盖更真实
flowchart TB subgraph G1["粒度一：围绕单个类，Mock 泛滥"] T1["测试 OrderService"] --> M1["Mock Repo"] T1 --> M2["Mock PayClient"] T1 --> M3["Mock Validator"] T1 --> M4["Mock PriceCalc"] M4 --> N1["自家纯逻辑也被替换
业务规则根本没被验证"] end subgraph G2["粒度二：围绕一个行为，推荐"] T2["测试「取消订单」这个行为"] --> R1["真实 Validator"] T2 --> R2["真实 PriceCalc"] T2 --> F1["Fake Repo，内存实现"] T2 --> F2["Spy PayClient，只记录"] F2 --> N2["只替换跨进程依赖
内部怎么拆都不影响测试"] end

AAA 与 Given-When-Then：结构化为什么值钱

Arrange-Act-Assert 的价值不在于好看，而在于它强制你把「准备」和「验证」分开，于是一个测试只能有一个 Act。一旦你想写第二个 Act，结构就会提醒你：这是两个行为，应该是两个用例。

三段之间空一行、Act 只有一行，是最有效的可读性投资。看到某个测试的 Arrange 段有四十行，就该抽构造器；看到 Act 段有五行，就该怀疑被测接口设计得不好用。Given-When-Then 是同一结构的行为驱动说法，多一层好处是名字可以直接来自需求描述。

✅
一个测试只有一个 Act，但可以有多个断言

「一个测试只能有一个断言」是被过度传播的教条。正确的表述是一个测试只验证一个行为：验证「取消成功」这一个行为时，同时断言状态变成 cancelled、退款金额是 10000、发出了一条取消事件，这三条断言描述的是同一个行为的三个侧面，放在一起是对的。要拆开的是那种「顺便再测一下超时逻辑」的用例。

断言要具体到能直接定位

断言的质量决定了失败信息的质量，而失败信息的质量决定了排查时间。下面这张表按信息量从低到高排列。

断言写法失败时你看到什么问题什么时候可以用
assertNotNull(result)expected not null but was null几乎零信息量，逻辑算错完全抓不到只作为后续断言的前置，不能是唯一断言
assertTrue(result.isOk())expected true but was false不知道错在哪个字段、实际值是什么布尔本身就是规格时（比如 isExpired）
assertEquals(10000, r.refundFen)expected 10000 but was 8000没有问题，信息充分默认选择
assertThat(r).isEqualTo(expected)（整对象比较）逐字段 diff，一次暴露所有偏差无关字段变化会误报，需要忽略字段值对象、DTO 序列化往返
assertThatThrownBy(...).isInstanceOf(X).hasMessageContaining("shipped")异常类型加关键信息都被校验无，这是错误路径的正确写法所有异常用例
快照断言（对比整段输出文本）整段 diff快照容易被无脑更新，失去校验意义复杂报表、代码生成器输出

两个补充原则：断言的期望值必须是字面量，不要在测试里用被测逻辑的同款公式算出期望值，那等于自我验证；浮点和金额不要直接比较，金额用最小单位的整数（分），浮点用带明确容差的比较。

边界条件的系统化枚举

bug 几乎都在边界上。别靠灵感，用清单。下面这份清单可以直接贴到团队的 review 模板里，逐类问一遍「这个输入有没有对应用例」。

类别具体输入它通常暴露什么 bug
空与不存在空字符串、空集合、空 map、null、字段缺失、可选值未设置空指针；把「空集合」当成「查询失败」处理
数量的一与多单元素集合、两元素集合、恰好等于批大小、批大小加一分页少一条或多一条；单元素时不进循环体
数值边界0、1、负数、最大值、最大值加一、最小值、精度末位整数溢出；金额四舍五入丢一分；负数绕过校验

顺序与重复乱序输入、完全逆序、重复元素、重复请求（幂等）依赖输入顺序；重复消费导致重复扣款

异常与失败依赖超时、依赖返回错误码、部分成功、反序列化失败错误被吞掉；失败后状态停在中间态

表驱动测试：枚举边界的最佳形式

边界条件本质上是数据。表驱动把数据和执行逻辑分开，新增一个边界只加一行，而复制粘贴测试函数的做法会让断言逻辑在各份拷贝之间慢慢产生偏移。

func TestCalcRefundFen(t *testing.T) {
    // 边界是数据不是代码：每一行是一个独立命名、独立报告的子测试
    cases := []struct {
        name    string
        paidFen int64
        elapsed time.Duration
        wantFen int64
        wantErr error
    }{
        {"零元订单直接返回零", 0, time.Hour, 0, nil},
        {"一分钱订单不产生舍入误差", 1, time.Hour, 1, nil},
        {"整7天_边界上仍算全额", 10000, 7 * 24 * time.Hour, 10000, nil},
        {"超过7天一纳秒_进入阶梯", 10000, 7*24*time.Hour + time.Nanosecond, 8000, nil},
        {"满30天_不再退款", 10000, 30 * 24 * time.Hour, 0, nil},
        {"负数金额是脏数据_必须报错", -1, time.Hour, 0, ErrBadAmount},
        {"时间倒流_必须报错而不是算出负数", 10000, -time.Second, 0, ErrNegativeElapsed},
        {"接近最大值_不能溢出", math.MaxInt64 / 100, time.Hour, math.MaxInt64 / 100, nil},
    }
    for _, c := range cases {
        c := c // Go 1.22 之前循环变量是复用的，不重新捕获会让并行子测试全跑最后一条
        t.Run(c.name, func(t *testing.T) {
            t.Parallel() // 子测试并行的前提：不共享可变状态

            got, err := CalcRefundFen(c.paidFen, c.elapsed)

            if !errors.Is(err, c.wantErr) {
                t.Fatalf("err = %v, want %v", err, c.wantErr)
            }
            if got != c.wantFen {
                // 失败信息带上输入，不用回头翻表对照
                t.Errorf("CalcRefundFen(%d, %v) = %d, want %d",
                    c.paidFen, c.elapsed, got, c.wantFen)
            }
        })
    }
}

class RefundPolicyTest {

    // 合法输入用 CsvSource：表格贴在注解里，加一行就是加一个边界
    @ParameterizedTest(name = "[{index}] 支付 {0} 分、过了 {1} 小时，应退 {2} 分")
    @CsvSource({
        "0,     1,   0",       // 零元
        "1,     1,   1",       // 最小金额
        "10000, 168, 10000",   // 整 7 天 = 168 小时，边界内
        "10000, 169, 8000",    // 越界一小时，进入阶梯
        "10000, 720, 0"        // 满 30 天
    })
    void 阶梯退款金额(long paidFen, long hours, long expectedFen) {
        long actual = RefundPolicy.calc(paidFen, Duration.ofHours(hours));
        assertThat(actual).isEqualTo(expectedFen);
    }

    // 非法输入需要传对象和异常类型，CsvSource 表达不了，改用 MethodSource
    @ParameterizedTest
    @MethodSource("非法输入")
    void 非法输入应抛出明确异常(long paidFen, Duration elapsed,
                              Class<? extends Exception> expected) {
        assertThatThrownBy(() -> RefundPolicy.calc(paidFen, elapsed))
            .isInstanceOf(expected);
    }

    static Stream<Arguments> 非法输入() {
        return Stream.of(
            arguments(-1L,  Duration.ofHours(1),    BadAmountException.class),
            arguments(100L, Duration.ofSeconds(-1), NegativeElapsedException.class)
        );
    }
}
⚠️
表里不要出现 if

一旦表驱动的循环体里长出 if c.wantErr != nil { ... } else { ... } 这种分支，说明你把两种语义不同的用例塞进了一张表。分成两张表（成功表、失败表）比在循环体里加分支更清晰，也避免了「测试自己有 bug」的风险。同理，表里不要放函数字段去自定义断言，那已经不是表驱动了。

属性测试：让机器去找你想不到的边界

参数化测试列举的是「你想到的输入」，属性测试描述的是「不变量」，由框架生成上千组随机输入去试图推翻它，失败后自动把反例收缩到最小。Go 有标准库的 testing/quick 与第三方 rapid，Java 有 jqwik，Python 有 hypothesis。

适合的不变量长这样：序列化再反序列化必须等于原值；排序后长度不变且元素集合不变；把一笔金额按比例拆成 N 份再求和必须精确等于原金额（这条最容易被舍入打败）；同一操作执行两次的结果等于执行一次（幂等）；加密再解密等于原文。不适合的是业务规则本身——不变量会退化成规则的复述，等于用实现测实现。

用的时候必须固定或打印随机种子，否则 CI 上偶发失败一次就再也复现不出来，这比没有测试更消耗人。

Mock 的边界与「验证状态优先」

替身只用在两类依赖上：跨进程的（数据库、HTTP、消息队列、缓存）和不确定的（当前时间、随机数、UUID、机器名、环境变量）。自己写的纯逻辑、值对象、领域计算，一律用真的。

详见站内集成测试一篇"] B -->|不跨进程| F{"它的返回确定吗"} F -->|"时间、随机数、UUID、环境变量"| G["抽接口注入可控实现"] F -->|"自己写的确定逻辑"| H["直接用真的，不要替身"]
要验证的东西该验证状态还是行为怎么写写错的后果
金额、折扣、评分等计算结果状态断言返回值等于字面量用 Mock 预设返回值，等于自己给自己出答案
聚合状态流转状态用 Fake 仓储，操作后读回来断言最终状态断言 update 被调用，字段写错照样通过
库存扣减、退款发起等必须发生的副作用行为（唯一该用的场合）用 Spy 记录调用，事后断言次数与参数不验证就会漏掉「重复退款」这类事故
幂等性状态加行为连续执行两次，断言最终状态一致且副作用只发生一次只跑一次，幂等 bug 永远暴露不了
内部经过了哪些步骤都不该验证删掉这个断言把实现固化成规格，重构必然大面积变红

func TestCancel_过度Mock(t *testing.T) {
    repo, pay, mail, clock := NewMockRepo(t), NewMockPay(t), NewMockMailer(t), NewMockClock(t)

        Return(Order{Status: "paid", PaidFen: 10000}, nil).Once()

并发与时间：随机失败的两大来源

用睡眠等待并发结果是随机失败的头号来源。睡眠时长是拍脑袋定的：本地 100 毫秒够，CI 上八个任务抢 CPU 时 300 毫秒都不够。于是同一份代码时绿时红，团队开始「红了就重跑」，门禁从此失效。

sequenceDiagram participant T as 测试 goroutine participant W as Worker goroutine participant D as done 通道 Note over T,W: 坏写法：睡 100 毫秒后直接断言 T->>W: Submit 提交任务 T->>T: 睡眠 100 毫秒 W-->>T: CI 负载高，180 毫秒才处理完 T->>T: 断言失败，但代码其实没有 bug Note over T,W: 好写法：用通道做确定性同步 T->>W: Submit 提交任务 W->>D: 处理完写入结果 T->>D: 阻塞接收，最多等 2 秒 D-->>T: 结果到达，立刻断言 Note over T,D: 快的时候不浪费时间，慢的时候也不误报
等待对象错误写法正确写法说明
一组协程全部结束睡眠估计的总耗时WaitGroup 或 CountDownLatch确定性同步点，快慢都正确
一次异步回调睡眠后检查标志位带缓冲通道加超时接收超时兜底避免卡死整个套件
最终一致的状态睡眠后查一次轮询加超时（Awaitility 之类）集成测试里的标准做法，详见站内集成测试一篇
定时任务触发真的等到下一个周期注入假时钟并快进把分钟级等待压缩到微秒
竞态本身跑一次通过就算过开竞态检测并重复执行多次Go 用 -race -count=10，Java 用压力循环加断言
// 命令：go test -race -count=10 ./...
// -race 检测数据竞争；-count=10 用来暴露只偶发失败的不稳定用例
func TestCounter_并发自增不丢数(t *testing.T) {
    const n = 100
    c := NewCounter()

    var wg sync.WaitGroup
    wg.Add(n)
    for i := 0; i < n; i++ {
        go func() {
            defer wg.Done()
            c.Inc()
        }()
    }
    wg.Wait() // 确定性同步点，不是 time.Sleep(100 * time.Millisecond)

    require.Equal(t, n, c.Value())
}

func TestWorker_处理完必须回调(t *testing.T) {
    done := make(chan Result, 1) // 带缓冲，避免 worker 因为没人接收而阻塞泄漏
    w := NewWorker(func(r Result) { done <- r })

    w.Submit(Job{ID: 7})

    select {
    case r := <-done:
        require.Equal(t, 7, r.JobID)
    case <-time.After(2 * time.Second): // 超时上限，防止卡死整个套件
        t.Fatal("2 秒内没有收到回调：worker 没启动，或者回调路径没走到")
    }
}

// 定时重试逻辑：注入假时钟，快进而不是真的等
func TestRetry_三次失败后进入死信(t *testing.T) {
    clk := &FakeClock{t: fixedNow}
    r := NewRetrier(clk, 3, time.Minute) // 退避 1 分钟，真等就是 3 分钟

    for i := 0; i < 3; i++ {
        require.True(t, r.ShouldRetry())
        clk.Advance(time.Minute) // 微秒完成，且时长是确定的
    }
    require.False(t, r.ShouldRetry())
    require.Equal(t, StateDeadLetter, r.State())
}

速度红线与反模式

单测的速度红线：单个用例低于 10 毫秒，整个套件秒级完成。原因不是洁癖，而是只有这个量级开发才会在本地每改一次就跑一次；一旦套件要跑两分钟，实际反馈周期就退化成「提交后等流水线」，单测最大的价值当场消失。

判断标准很硬：只要引入了数据库、网络、文件系统、真实时钟，它就不是单元测试了。这类验证有价值，但应该改名归到集成测试目录，用独立的命令跑。

反模式症状后果修法
在单测里连数据库套件从 3 秒变 3 分钟，本地还要先启动依赖没人在本地跑，反馈推迟到流水线拆到集成测试目录，用真实容器跑
用睡眠做同步偶发失败，重跑就好门禁失去可信度，真问题被淹没WaitGroup、通道加超时、轮询等待、假时钟快进
Mock 自己写的纯函数预设了本该被计算出来的返回值计算写错完全测不出来直接调真实实现，断言返回值
断言只写 assertNotNull用例没有任何实质校验覆盖率好看，防御力为零断言具体值、具体状态、具体异常与关键信息
用例之间共享可变状态单跑绿、全量红；调整顺序结果变了无法并行执行，套件时间压不下来每个用例自造数据；静态状态提供 reset 或改为不可变
把私有方法改成公开只为了测它一批只被测试调用的公开方法封装被打破，内部结构被测试锁死通过公开行为覆盖；确实独立就抽成一个有名字的类
测试里重算期望值期望值用被测同款公式算出来公式错了测试也错，等于没测期望值必须是手写的字面量常量
一个用例测十件事用例名叫「测试下单」，两百行，多个 Act第三个断言挂了，后面七个状况不明一个行为一个用例，公共准备抽成构造器
❌
最容易踩的坑
  • Go 1.22 之前在子测试里忘记重新捕获循环变量。开了 t.Parallel 后所有子测试都用最后一条数据，表面全绿，实际只测了一条。
  • 用 time.Sleep 等异步结果。本地 100 毫秒够用，CI 上负载一高就红，然后被加进重跑名单。
  • 忘记开竞态检测。并发用例不带 -race 跑，数据竞争要等到线上偶发数据错乱才暴露。
  • 无缓冲通道加没人接收。被测协程写通道时永久阻塞，用例超时且泄漏协程，报错信息完全指不到真实原因。
  • Mock 掉时钟却只 Mock 了一处。业务里还有第二处直接调系统时间，跨天用例时好时坏。
  • 只测区间内部不测端点。大于和大于等于写反是最高频的 bug，而它只在端点上暴露。
  • 金额用浮点断言。0.1 加 0.2 不等于 0.3，测试红了却去改断言容差，掩盖了真该用整数分的问题。
  • 把被测代码的公式复制到测试里算期望值。公式写错时两边一起错，测试永远绿。
  • 状态机只测合法流转。「已发货订单被取消」这类非法流转没有用例，线上直接资损。
  • 属性测试不固定随机种子。CI 上偶发失败一次，之后再也复现不出来，最后被整体注释掉。
  • 用 setUp 准备一个大对象给所有用例共用。某个用例悄悄改了它的字段，另一个用例莫名其妙失败。
  • 断言写在异步回调里。回调没被执行时断言根本不运行，用例照样通过，等于完全没测。
