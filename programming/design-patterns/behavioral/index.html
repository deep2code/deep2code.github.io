行为型模式的现代形态：策略传函数、事件的排障代价、表驱动状态机与中间件链

🏷️ 行为型设计模式

行为型模式共享同一个动作：把「下一步由谁决定」从主流程里挪出去。挪法只有三种——查一张表（策略、状态）、发一个通知（观察者）、串一条链（责任链、中间件）。挪出去的收益是主流程不再随分支增长而膨胀，代价高度一致：控制流从静态可读变成运行期才确定，于是你在代码里搜不到调用关系，排障要靠日志而不是阅读。这篇讲每个模式在什么变化下值得付这个代价，以及现代语言里它们退化成了什么形态。

策略：三种写法的真实差别

策略模式的现代形态就是传一个函数。同一个需求写三遍就能看清差别：条件分支把规则集中但主流程会膨胀；策略类把规则分散到多个文件并引入注册与装配；闭包注册表在两者之间，保留了轻量与集中。

// 写法一：条件分支。分支少于 5 个且稳定时，这是最好的写法 —— 完整规则一屏读完
long feeCents(String channel, long amountCents) {
    switch (channel) {
        case "alipay": return amountCents * 6 / 1000;              // 0.6%
        case "wechat": return amountCents * 6 / 1000;
        case "unionpay": return Math.max(amountCents * 5 / 1000, 100);  // 0.5% 且不低于 1 元
        default: throw new IllegalArgumentException("unknown channel: " + channel);
    }
}

// 写法二：策略类。只有在策略需要自己的状态或需要注入依赖时才值得
interface FeeRule { long fee(long amountCents); }

final class UnionPayFeeRule implements FeeRule {                   // 需要注入配置与汇率服务，这才是建类的理由
    private final RateConfig config;                               // 有依赖
    UnionPayFeeRule(RateConfig config) { this.config = config; }
    public long fee(long amountCents) {
        return Math.max(amountCents * config.rateBp("unionpay") / 10000, config.minFeeCents());
    }
}

// 写法三：闭包注册表。无状态策略的默认选择，新增一行即可，不新建文件
final class FeeRules {
    private final java.util.Map<String, java.util.function.LongUnaryOperator> rules;

    FeeRules(RateConfig config) {
        this.rules = java.util.Map.of(
            "alipay",   amt -> amt * 6 / 1000,
            "wechat",   amt -> amt * 6 / 1000,
            "unionpay", amt -> Math.max(amt * config.rateBp("unionpay") / 10000, config.minFeeCents())
        );
    }

    long fee(String channel, long amountCents) {
        var r = rules.get(channel);
        // 未注册必须显式失败。静默回退到默认费率是最常见的资损来源
        if (r == null) throw new IllegalArgumentException("unknown channel: " + channel);
        long fee = r.applyAsLong(amountCents);
        log.info("fee calculated, channel={}, amount={}, fee={}", channel, amountCents, fee); // 补偿可搜索性
        return fee;
    }
}

用注册表取代分支时的三条补偿措施

一、对未注册的 key 显式抛错，不要回退默认实现；二、把选中的 key 打进日志与链路追踪标签，补上丢失的可搜索性；三、写一个用例断言注册表的 key 集合与配置里的枚举完全一致，防止上线后才发现漏注册。

观察者与发布订阅：解耦最强，排障最难

事件是解耦力度最大的手段，也是唯一一种让你无法通过阅读代码知道一个动作会触发什么的手段。调用关系在运行期由订阅注册决定，静态分析、全局搜索、IDE 调用层级全部失效。所以它的判断口径要比其他模式更严格。

两个最常见的坑：一是在事务提交前发出异步事件，消费者先到并按主键查询却查不到记录，表现为随机失败，正确做法是把发送挂到事务提交之后；二是同步事件里做远程调用，把一个可选动作变成主流程的延迟与失败来源。跨服务的投递语义、重复消费与顺序保证详见站内消息队列相关文章，这里不重复。

状态模式与表驱动状态机

订单、工单、支付这类对象的核心复杂度是状态流转规则。两种实现方式：每个状态一个类，或者一张转移表。先把流转画清楚，再看两种实现的差别。

stateDiagram-v2 [*] --> CREATED CREATED --> PAID: 支付成功回调 CREATED --> CANCELLED: 用户取消或超时未支付 PAID --> SHIPPED: 仓库发货 PAID --> REFUNDING: 发起退款 SHIPPED --> COMPLETED: 确认收货或自动确认 SHIPPED --> REFUNDING: 拒收或售后 REFUNDING --> REFUNDED: 退款成功 REFUNDING --> PAID: 退款被驳回，回到已支付 COMPLETED --> [*] CANCELLED --> [*] REFUNDED --> [*] note right of REFUNDING 退款是唯一允许回退的分支 必须记录来源状态，否则驳回后不知道回哪里 end note
维度状态模式（每状态一个类）表驱动状态机（一张转移表）
规则存在哪里散在各状态类的方法里集中在一张表，可放代码常量也可放数据库
新增一个流转改相关状态类，可能要改多个加一行数据，可不发版
全局校验能力难，无法一眼看出是否有孤立状态容易，可程序化检查可达性与死状态
行为差异大时优势明显，每个状态的行为收在一起要额外挂动作函数，表会变胖
状态数量多时类数量线性膨胀，十几个状态就难维护优势明显，表再长也还是一张表
给非开发看看不了可直接渲染成图或导出表格评审
推荐场景状态少于 6 个且每个状态行为迥异状态多、规则需要配置化、需要审计与可视化

无论选哪种实现，落库的状态流转必须是带前置状态条件的原子更新，绝不能先查后改。先查后改在并发下会出现状态回退（后到的线程用旧状态覆盖新状态）和重复推进（两个线程都认为自己是第一个）。

-- 正确：把前置状态写进 WHERE，用受影响行数判断这次流转是否由自己完成
UPDATE orders
   SET status = 'PAID',
       paid_at = NOW(3),
       version = version + 1
 WHERE id = ?
   AND status = 'CREATED';     -- 关键：前置状态条件，天然防重复推进与状态回退
-- 受影响行数为 1：本次流转成功，可以继续发事件
-- 受影响行数为 0：说明状态已不是 CREATED，可能是重复回调或已取消，必须查一次当前状态再决定，不要直接报错

-- 错误：先查后改，两个并发回调都能通过检查
-- SELECT status FROM orders WHERE id = ?;      -- 都读到 CREATED
-- UPDATE orders SET status = 'PAID' WHERE id = ?;  -- 都执行成功，事件被发两次

-- 表驱动状态机的转移表：规则变成数据，新增流转不用发版
CREATE TABLE order_transition (
    from_status VARCHAR(16)  NOT NULL,
    event       VARCHAR(32)  NOT NULL,
    to_status   VARCHAR(16)  NOT NULL,
    guard_expr  VARCHAR(128) NULL,      -- 可选的前置条件，例如 amount > 0
    PRIMARY KEY (from_status, event)    -- 同一状态同一事件只能有一条规则，避免歧义
);

状态流转的并发控制、乐观锁版本号与幂等落地的完整讨论详见站内数据建模相关文章，这里只强调一条：状态判断和状态写入必须发生在同一条语句里。

责任链的两种形态

责任链在实践中是两种完全不同的东西。中间件式：每层都能决定是否继续，并且能在下游返回后再处理一次，形成洋葱结构，这是所有 Web 框架的核心结构。审批链式：按顺序找第一个能处理的节点，或逐级审批，链条通常来自配置或数据。

维度中间件式审批链式
链的来源启动时代码装配，固定运行时按数据或配置生成，每个实例可能不同
是否有返回阶段有，下游返回后还能处理，形成洋葱一般没有，处理完即结束
终止方式某层不调用下一层即终止某节点声明自己能处理即终止，或走完全部节点
典型用途鉴权、限流、日志、恢复、超时、追踪审批流、风控规则链、消息过滤链
状态持久化不需要，请求内存活需要，每一步结果都要落库以支持断点续跑
主要风险顺序装配错（例如恢复中间件不在最外层），异常被中间层吞掉链条数据错导致卡单，某节点超时无人处理
 
// 中间件式责任链：洋葱模型。每层可决定是否调用 next，也可在 next 返回后继续处理
type Middleware func(http.Handler) http.Handler

// 倒序包装，使 ms[0] 位于最外层，执行顺序与书写顺序一致，避免装配顺序反直觉
func Chain(h http.Handler, ms ...Middleware) http.Handler {
    for i := len(ms) - 1; i >= 0; i-- {
        h = ms[i](h)
    }
    return h
}

// 必须放在最外层：只有它在外面，才能兜住内层所有 panic
func Recover(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        defer func() {
            if p := recover(); p != nil {
                log.Printf("panic recovered path=%s panic=%v stack=%s", r.URL.Path, p, debug.Stack())
                w.WriteHeader(http.StatusInternalServerError) // 不写状态码会让客户端看到连接被直接断开
            }
        }()
        next.ServeHTTP(w, r)
    })
}

// 可以终止链条：不调用 next 就是「我处理完了，后面不用走」
func Auth(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        if !validToken(r.Header.Get("Authorization")) {
            w.WriteHeader(http.StatusUnauthorized)
            return // 终止，且必须有日志或指标，否则请求被静默拦下时查不到原因
        }
        next.ServeHTTP(w, r)
    })
}

// 返回阶段做事：耗时统计必须在 next 之后，这就是洋葱的「出」那一半
func Metrics(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        start := time.Now()
        next.ServeHTTP(w, r)
        observeLatency(r.URL.Path, time.Since(start)) // 这里能拿到整个内层链路的总耗时
    })
}

命令、模板方法与访问者：适用面要看清

这三个模式在现代代码里都被更轻的手段取代了大半，只有特定形态还值得写。

模式还值得用的形态已被取代的形态关键判据
命令命令要被序列化、持久化、排队、重放、撤销时；本质上就是任务队列里的一条消息只是为了「把动作对象化」而包一层的 Command 类这个动作需要被存起来以后再执行吗
撤销与重做记录反向命令或状态快照；业务系统里更常见的是「补偿操作」而非真正的撤销指望用一个通用 undo 栈解决业务回滚反向操作是否真的存在且可安全执行
模板方法钩子多且有严格调用顺序，且框架方需要强约束只有一两个可变步骤时，传回调更轻，也避免继承可变点超过三个且彼此有顺序依赖吗
迭代器遍历外部资源需要控制分页、游标与关闭时机手写 hasNext 与 next 遍历内存集合遍历过程是否需要管理资源生命周期
访问者数据结构稳定但操作频繁新增，典型是语法树处理、SQL 解析、字节码分析业务对象上套访问者，因为业务的数据结构恰恰是最常变的节点类型是否几年都不变
解释器需要用户自定义表达式（风控规则、告警条件）时，优先用成熟表达式引擎自己从头写词法与语法分析表达式复杂度是否值得一个引擎

访问者的适用面之所以极窄，原因是它把变化的方向定死了：新增操作很便宜，新增节点类型极贵——加一种节点要改所有访问者。业务代码里最常发生的偏偏是「新增一种业务对象」，所以在业务层用访问者通常是把成本压在了最容易变化的方向上。

反模式

反模式识别信号后果修法
把所有条件分支都改成策略类原来一屏的规则变成二十个十行文件读完整规则要打开二十个文件，且从实现反查调用点只能靠日志分支少于 5 且稳定就保留分支；先用函数注册表，需要状态时再建类
事件满天飞一个下单动作发出七个事件，没人能说清都触发了什么改一个动作不知道影响谁，链路追踪里到处是断点，回归测试无法覆盖建立事件清单与订阅关系文档，主流程依赖的动作改回直接调用
状态判断散落各处各处都写 if status equals 某个值，没有统一状态机新增状态漏改某一处，出现不该发生的流转，且无法审计集中成一张转移表，所有流转必须经过统一入口
状态流转先查后改先 SELECT 查状态再 UPDATE并发下状态回退与重复推进，事件被发两次把前置状态写进 WHERE，按受影响行数判断是否由自己完成
责任链里某一环吞异常catch 后只 return，不记日志不上报指标请求被静默终止，客户端只看到空响应，排查时链路里毫无线索终止必须留痕：日志、指标、追踪标签三者至少有其一

用继承实现模板方法却在基类调用可覆盖方法基类构造器或初始化流程里调用了子类要覆盖的方法子类字段还没初始化就被调用，读到默认值改成传回调，或明确禁止在初始化流程里调用可覆盖方法

最容易踩的坑

❌
行为型模式的高频事故清单
  • 策略注册表对未知 key 静默回退默认实现：配置写错一个字母就按错误费率或错误渠道跑，事后对账才发现。
  • 把二十个短分支拆成二十个策略类：逻辑分散到二十个文件，新人读一遍完整规则要跳二十次，收益为零。
  • 闭包策略捕获了可变对象：捕获的配置对象后来被别处修改，策略行为在运行中悄悄变了。
  • 同步事件里做远程调用：一个可选的后置动作变成主流程的延迟与失败来源，P99 被它拖垮。
  • 事务提交前发异步事件：消费者先到却查不到记录，表现为随机失败，压测时几乎复现不出来。
  • 事件订阅方抛异常导致发布方事务回滚：一个通知失败把整笔业务回滚，且日志里看不出是谁抛的。
  • 异步事件不做幂等：至少一次投递是常态，重复消费直接造成重复发货或重复入账。
  • 事件名与载荷随意改：订阅方在另一个仓库，改完发版才发现对方解析失败，且没有编译期检查。
  • 状态流转先查后改：并发回调下两个线程都认为自己是第一个，事件发两次、状态被旧值覆盖。
  • 状态判断散落在十几处 if 里：新增一个状态漏改一处，出现不该存在的流转，事后无法审计是谁改的。
  • 退款流程不记录来源状态：驳回后不知道该回到已支付还是已发货，只能人工判断。
  • 责任链某一环 catch 后直接返回且不留痕：请求被静默拦下，客户端只看到空响应，排查时链路毫无线索。
  • 恢复中间件没放在最外层：内层 panic 无人兜住，进程崩溃或连接被直接断开，客户端看到的是连接重置。
  • 耗时统计中间件放在最内层：统计到的只是业务处理时间，把鉴权和限流的耗时全漏掉，指标与真实延迟长期不一致。
  • 模板方法的基类在初始化流程里调用可覆盖方法：子类字段尚未赋值就被调用，读到默认值且极难定位。
  • 在业务对象上套访问者：业务节点类型恰恰是最常新增的，每加一个类型要改所有访问者，成本压在最容易变化的方向上。
