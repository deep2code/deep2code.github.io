创建型模式的真实取舍：单例的全局状态代价、工厂的边界与对象池

🏷️ 创建型设计模式

创建型模式解决的是同一个问题：谁来决定「用哪个具体类、用哪个实例、什么时候创建」。这个决定权放在调用方手里最简单，放出去就需要一道接缝。这篇不讲单例的四种写法，而讲每个创建型模式的真实代价：单例为什么难测试、工厂在什么条件下退化成纯样板、Builder 的两种用途里只有一种不可替代、对象池在 GC 语言里什么时候反而更慢，以及为什么依赖注入是创建型模式的现代答案。

创建职责的四个去处

先把选项摆清楚。一个对象的创建职责只有四个可能的落点，模式讨论的其实是「该落在哪一格」。落点越靠右，调用方知道得越少，但装配链越长、启动期越重、静态可读性越差。

单例真正的问题：它是全局可变状态

面试里问单例，答案总是绕着线程安全转。线程安全只是写法问题，静态内部类持有者或枚举一行就解决；单例真正的问题是它是全局可变状态，这四个结构性缺陷和写法无关，换任何写法都存在。

结构性问题具体表现造成的后果怎么规避
无法替换，难以测试调用方写 Config.getInstance().get("rate")，测试里没有任何注入点单测被迫依赖真实配置或文件，要么加 setInstance 后门，用完忘了清理导致测试间互相污染把它变成注入的依赖，测试传入替身。测试替身分类详见站内后端测试那篇
隐藏依赖构造器参数是空的，但方法体里调了三个单例从签名看不出这个类依赖了数据库、缓存和配置中心，重构时才发现牵一发动全身依赖全部走构造器，让签名变丑来暴露真实复杂度
初始化顺序不可控静态初始化在类加载时执行，可能早于配置读取、日志初始化、连接建立读到空配置或默认值；异常发生在静态初始化里会变成类初始化错误，堆栈难读且不可重试交给容器按依赖关系排序初始化，或改为显式的初始化阶段
只是进程内单例容器化部署 6 个副本，就有 6 份「唯一实例」用单例做计数、序号、去重、本地限流，实际阈值被放大为副本数倍；扩容后行为突变需要全局唯一就用 Redis 或数据库承载，单例只放无状态逻辑
⚠️
最常见的线上事故形态

本地限流器写成单例，按「每秒 100 次」配置。服务扩到 6 个副本后，实际放行 600 次每秒，下游被打挂。单例的语义在多副本部署下静默改变，而代码一行都没改，这是最难复盘的一类问题。

写法只值一张表：volatile、反序列化、反射

写法这件事不值得展开，一张表加三条结论就够。结论是：Java 里首选枚举，需要懒加载就用静态内部类持有者，双重检查锁只在需要按参数创建多个实例的场景才值得手写。

写法线程安全靠什么懒加载抗反射与反序列化什么时候用
饿汉式静态字段类加载的初始化锁否不抗，反射可调私有构造器初始化极轻且一定会用到
静态内部类持有者内部类首次被引用时才初始化，仍由类初始化锁保证是不抗默认首选的懒加载写法
双重检查锁加 volatilevolatile 禁止重排并保证可见性，同步块保证只创建一次是不抗需要按 key 缓存多个实例时才手写
枚举单例JVM 保证枚举常量唯一否抗，反射创建枚举被禁止，反序列化按名字查找需要绝对唯一且不介意提前初始化
容器管理的 Bean容器在启动期单线程装配可配置延迟初始化不涉及，不通过静态入口访问框架项目里的正确答案

三条必须知道的细节：一是双重检查锁的字段必须是 volatile，因为创建对象包含分配内存、执行构造器、引用指向内存三步，后两步允许重排，别的线程可能看到一个字段还是默认值的半成品；二是实现了 Serializable 的单例会在反序列化时被创建出第二个实例，除非提供 readResolve 返回已有实例；三是反射可以绕过私有构造器，真要防就在构造器里检查实例是否已存在并抛异常，或者直接用枚举。

什么时候单例仍然合理

单例不是禁用项，它只是被用在了太多不该用的地方。判断口径很简单：无状态，或者状态不可变且初始化昂贵，这两种情况下全局共享一份是对的；只要它持有可变状态，就该交给容器并作为依赖注入。

工厂的价值边界：只有一个实现时它是纯样板

工厂的价值只在一个条件下成立：调用方不应该知道具体类型。支付渠道按商户配置切换、存储后端按环境切换、协议解析器按版本号切换，这些调用方确实不该知道。反过来，如果只有一个实现，工厂做的事就是把 new 换了个名字，代价是多一个文件、多一跳跳转、以及 IDE 里点不进真正的实现。

形态结构调用方看到什么真实适用场景业务代码出现频率
简单工厂一个静态方法内部 switch 选实现一个枚举或字符串 key实现 2 到 5 个、增删不频繁高，绝大多数场景够用
工厂方法每种产品一个工厂子类，由子类决定创建什么一个工厂接口产品与创建逻辑都要一起扩展，且由不同模块提供中低，多见于框架和 SPI
抽象工厂一个工厂接口创建一整族相关产品一个工厂接口，多个产品接口必须整族一起替换，如跨数据库方言的全套语句构造器极低，业务代码里几乎用不到
注册表加函数map 从 key 到构造函数一个 key实现多、需要按配置开关、启动时注册中，替代简单工厂的现代写法
容器条件装配按配置项决定注入哪个 Bean什么都看不到，直接拿到依赖按环境、按开关选实现高，框架项目首选
✅
一条可执行的判据

工厂里的分支数小于 2 就删掉工厂。分支数大于 5 且会持续增删，就把 switch 换成注册表；但注册表的代价是调用点无法静态搜索，务必把选中的 key 打进日志和链路追踪标签。

Builder 的两种用途，只有一种不可替代

Builder 被混为一谈的两种用途必须分开：一种是解决构造参数过多的可读性问题，另一种是需要分步构造并在最后校验不变量。前者在现代语言里有更轻的答案（命名参数、默认参数、record 加静态工厂），后者才是 Builder 真正的价值。

需求形态推荐做法不推荐做法理由
字段多但都必填，且一次给齐record 或 data class，构造器里集中校验写 BuilderBuilder 反而丢掉了编译期的必填检查，漏 set 一个字段也能 build 成功
字段多且大半可选Kotlin 或 Python 命名参数加默认值；Java 用 record 加若干静态工厂Java 里堆 8 个重载构造器重载构造器组合爆炸，且相同类型参数容易传错位置
参数来自多个阶段或多个来源Builder，build 时集中校验不变量并产出不可变对象先 new 一个可变对象再到处 setter可变中间态会被别的线程或别的方法看到，不变量无法保证
需要按顺序强制步骤分步接口，每一步返回下一步的类型普通链式 Builder让编译器而不是运行期断言来保证顺序
构造需要访问外部资源工厂或容器，不要放进 Builder在 Builder 里查数据库Builder 应当是纯内存累积，否则无法在测试中构造对象
 
// Builder 的不可替代场景：参数分阶段到达，最后统一校验不变量，产出不可变对象
public final class Shipment {
    private final String orderId;
    private final String address;
    private final int weightGram;
    private final java.util.List<String> items;

    private Shipment(Builder b) {
        this.orderId = b.orderId;
        this.address = b.address;
        this.weightGram = b.weightGram;
        this.items = java.util.List.copyOf(b.items);   // 冻结集合，构造完成后无法被外部改动
    }

    public static Builder builder() { return new Builder(); }

    public static final class Builder {
        private String orderId;
        private String address;
        private int weightGram;
        private final java.util.List<String> items = new java.util.ArrayList<>();

        // 每一步只累积，不校验跨字段规则，因为此刻信息还不全
        public Builder orderId(String v) { this.orderId = v; return this; }
        public Builder address(String v) { this.address = v; return this; }
        public Builder addItem(String sku, int gram) {
            this.items.add(sku);
            this.weightGram += gram;                   // 重量由明细累加，不允许外部直接设
            return this;
        }

        public Shipment build() {
            // 集中校验：只有这里能看到完整状态，不变量必须在产出前全部成立
            if (orderId == null || orderId.isBlank()) throw new IllegalStateException("orderId required");
            if (address == null || address.isBlank()) throw new IllegalStateException("address required");
            if (items.isEmpty()) throw new IllegalStateException("shipment must contain at least one item");
            if (weightGram <= 0 || weightGram > 30_000) throw new IllegalStateException("weight out of range: " + weightGram);
            return new Shipment(this);                 // 产出不可变对象，之后 Builder 再改也影响不到它
        }
    }
}

// 对照：如果只是「字段多、一次给齐」，record 就够了，还白拿 equals、hashCode、toString
record Address(String province, String city, String detail, String zipCode) {
    Address {   // 紧凑构造器里做校验，比 Builder 更难被绕过
        if (detail == null || detail.isBlank()) throw new IllegalArgumentException("detail required");
    }
}

原型模式在这个语境下也可以一句话说完：它的真实价值只剩「以一个已有对象为模板做拷贝」，例如按模板生成配置、按默认值生成请求对象。Java 的 clone 契约有名的难用（默认是浅拷贝、需要配合 Cloneable 标记接口、final 字段无法赋值），实践中直接写拷贝构造器或用序列化做深拷贝更清楚。要特别小心的是浅拷贝共享可变集合：模板对象里的 List 被所有拷贝共享，一个请求往里加一个元素，所有后续请求都看得到。

对象池：只有创建成本远高于管理成本时才值得

池化的收益公式很朴素：省下的创建成本要明显大于借还管理、校验、超时控制带来的成本与风险。连接和线程满足这个条件，因为它们的创建涉及系统调用、TCP 握手、TLS 协商、认证鉴权，耗时在毫秒量级；而普通对象在现代分代收集器下分配只是指针碰撞，年轻代回收接近免费，池化反而让对象长期存活、晋升老年代、增加标记与跨代引用开销，在 GC 语言里给普通对象做池化通常更慢。

连接泄漏是池化最常见的事故，它的特征是故障不在泄漏发生时爆发，而在池耗尽时爆发，因此现场堆栈指向的往往是无辜的请求。

// 一个最小但正确的有界连接池：借出超时、有效性校验、归还不阻塞
type Pool struct {
    idle     chan *Conn
    maxIdle  time.Duration // 空闲超过这个时长的连接借出前必须校验
    dial     func(context.Context) (*Conn, error)
}

func (p *Pool) Acquire(ctx context.Context) (*Conn, error) {
    for {
        select {
        case c := <-p.idle:
            // 关键：池里的连接可能已被对端关闭，必须校验；但只对空闲较久的连接校验，避免每次都加一次往返
            if time.Since(c.lastUsed) > p.maxIdle && !c.alive(ctx) {
                c.close()
                continue // 丢弃这条，继续取下一条
            }
            return c, nil
        default:
            // 池里没有空闲连接：这里必须受 ctx 约束，否则高峰期线程会无限期堆积
            return p.dialWithTimeout(ctx)
        }
    }
}

func (p *Pool) Release(c *Conn) {
    if c.broken { // 出过错的连接不要放回池里，否则它会被反复借出反复失败
        c.close()
        return
    }
    c.reset()             // 清事务状态、会话变量、超时设置，避免脏状态传染下一个使用者
    c.lastUsed = time.Now()
    select {
    case p.idle <- c:     // 归还必须非阻塞
    default:
        c.close()         // 池已满，多余连接直接关掉，不要让 Release 卡住调用方
    }
}

依赖注入：创建型模式的现代答案

把创建职责交给容器之后，单例、工厂、原型这三个模式的大半场景就消失了：作用域由容器声明，选哪个实现由条件装配决定，对象生命周期有统一的初始化与销毁回调。剩下的关键选择只有一个——依赖怎么进来。构造器注入和字段注入的差别不是风格问题，而是可测性和正确性问题。

维度构造器注入字段注入
依赖可见性写在签名上，一眼看出这个类依赖几个东西藏在字段里，依赖涨到十几个也看起来很干净
不可变性字段可声明为 final，构造完成即完全就绪无法 final，存在构造完成但未注入的中间态
单元测试直接 new 并传替身，不需要容器要靠反射设值或启动容器
循环依赖启动时直接报错，逼你改设计容器可能靠三级缓存悄悄化解，问题被推到运行期
依赖爆炸的反馈参数多到难看，形成重构压力没有任何反馈信号
与框架耦合不需要注解也能用，普通 Java 对象必须有容器或注解处理器参与
 
// 反例：字段注入 + 内部直接取单例 + 直接读系统时间，这个类几乎无法单测
public class BadCouponService {
    @Autowired private CouponRepository repo;                 // 测试要用反射塞值
    public boolean usable(String code) {
        Config cfg = Config.getInstance();                    // 隐藏依赖，签名上看不见
        Coupon c = repo.find(code);
        return c != null && c.expireAt().isAfter(java.time.LocalDateTime.now()) // 依赖真实时钟，测边界只能改系统时间
                && c.amount() >= cfg.getInt("coupon.min");
    }
}

// 正解：所有跨边界依赖都从构造器进来，包括时钟这种最容易被忽略的隐藏依赖
public final class CouponService {
    private final CouponRepository repo;
    private final java.time.Clock clock;   // 把「现在几点」也变成可注入的依赖
    private final int minAmount;

    public CouponService(CouponRepository repo, java.time.Clock clock, int minAmount) {
        this.repo = java.util.Objects.requireNonNull(repo);
        this.clock = java.util.Objects.requireNonNull(clock);
        this.minAmount = minAmount;
    }

    public boolean usable(String code) {
        Coupon c = repo.find(code);
        if (c == null) return false;
        // 用注入的 clock 取当前时间，测试里传 Clock.fixed 就能精确测过期边界的那一毫秒
        return c.expireAt().isAfter(java.time.LocalDateTime.now(clock)) && c.amount() >= minAmount;
    }
}

最容易踩的坑

❌
创建型模式的高频事故清单
  • 把本地限流器、本地计数器、序号生成器做成单例：扩容到 N 个副本后语义变成 N 倍，代码没改行为却变了。
  • 双重检查锁漏写 volatile：低概率拿到字段仍为默认值的半成品对象，表现为无法复现的空指针，压测时才偶发。
  • 单例实现了 Serializable 却没写 readResolve：反序列化凭空造出第二个实例，缓存与状态从此分裂。
  • 为测试给单例加 setInstance 后门：某个用例改了实例又没还原，后面的用例莫名失败，且失败顺序依赖于测试执行顺序。
  • 静态初始化块里读配置或建连接：异常变成类初始化错误且无法重试，同一个类之后每次访问都直接失败。
  • 只有一个实现还写工厂加接口：没有任何隔离收益，只是让每次改签名要动两个文件、跳转多一跳。
  • 工厂或注册表遇到未知 key 静默返回默认实现：配置写错时按错误的费率或渠道跑，问题在对账时才暴露。
  • Builder 没有在 build 里做必填校验：漏 set 一个字段照样构造成功，空值一路流到下游才炸。
  • Builder 复用同一个实例构造多个对象：内部集合被共享，第二个对象带上了第一个对象的明细。
  • 原型模式用浅拷贝：模板里的 List 或 Map 被所有拷贝共享，一处修改污染全部后续请求。
  • 给普通对象做池化：对象长期存活晋升老年代，GC 标记成本上升，结果比每次新建更慢，还多了状态重置的 bug 面。
  • 池化对象归还前不重置状态：上一个使用者留下的事务、会话变量、超时设置传染给下一个使用者。
  • 获取连接不设超时：下游抖动时请求线程全部堵在获取连接上，故障从局部变慢升级为整体雪崩。
  • 没有泄漏检测：连接被漏还时业务完全正常，直到池耗尽才爆发，此时现场堆栈指向的是无辜请求。
  • 空闲超时大于数据库或中间设备的断连时间：借出的是已被对端关闭的连接，报连接被重置且难以复现。
