CPython 实现细节：字节码、解释器与性能特征

🏷️ Python

站内《Python 语言核心》一篇已经讲过对象模型、引用计数与分代 GC、__slots__ 与属性查找的语义，这篇只讲执行机制：一行 Python 被编译成什么、解释器怎么跑它、3.11 之后快在哪里、以及由此推出的热路径优化手法。目标是让你在看到一段慢代码时，能说出它慢在哪条指令上，而不是只会说「Python 就是慢」。

字节码：能看见，但不是优化手段

Python 源码先被编译成字节码（code object），再由解释器逐条执行。dis 模块能把这层完全摊开，这是判断「两种写法到底有没有区别」的唯一可靠手段。

import dis

def f(obj, items):
    total = 0
    for x in items:
        total += obj.factor * x      # 每轮都要重新查一次 obj.factor
    return total

dis.dis(f)

# 3.12 的输出（节选，指令名各版本会变，结构不变）
  4       LOAD_FAST                3 (x)        # 局部变量：按数组下标取，最快
          LOAD_FAST                0 (obj)
          LOAD_ATTR                0 (factor)   # 属性查找：走类型的描述符协议加实例字典
          BINARY_OP                5 (*)
          BINARY_OP               13 (+=)
          STORE_FAST               2 (total)
  5       JUMP_BACKWARD            ...           # 循环回边，每轮重复上面全部指令

# 常用命令
python3 -m dis script.py                 # 直接看整个模块的字节码
python3 -c "import dis; dis.dis(compile('a=1+2','x','exec'))"   # 看常量折叠结果
python3 -X importtime -c "import myapp"  # 看导入耗时，找出启动慢在哪个模块

三个必须纠正的认知：

常见说法实际情况推论
「.pyc 是编译优化，能让程序跑得更快」.pyc 只缓存了「源码到字节码」这一步，执行时仍然逐条解释它只省启动时的编译时间（毫秒级），对运行期性能零影响
「加 -O 会做优化」-O 只是去掉 assert 和把 __debug__ 置假，-OO 再去掉 docstring别指望它提速；靠 assert 做业务校验的代码会在 -O 下直接失效
「字节码层面优化很重要」编译期只做常量折叠、死代码消除这类局部优化，没有跨函数内联，也没有逃逸分析优化要在数据结构与调用次数上做，不是在指令条数上抠

__pycache__ 里的文件名带上了魔数与版本号（如 mod.cpython-312.pyc），所以不同小版本互不复用。默认失效判据是「源文件的 mtime 加大小」，这意味着两个坑：容器构建时如果重置了文件时间戳、或者部署工具只改内容不改 mtime，都可能让旧字节码继续生效。生产镜像里可以用 python -m compileall --invalidation-mode checked-hash 改成按内容哈希判断，或者干脆在构建期预编译好。

3.11 之后解释器快在哪：自适应专门化

3.11 起 CPython 引入了自适应专门化解释器（specializing adaptive interpreter）。思路是：同一条泛型指令（比如 BINARY_OP 加法）在真实代码里绝大多数时候操作的是同一种类型，于是解释器先观察几次，确认类型稳定后，把这条指令原地替换成专门化版本（例如「两个小整数相加」），跳过类型分发与通用协议查找。类型一旦变了就去优化回泛型版本。

stateDiagram-v2 state "泛型指令 BINARY_OP" as Generic state "计数预热中" as Warm state "专门化版本 int 加法" as Spec state "去优化回泛型" as Deopt [*] --> Generic Generic --> Warm: 首次执行，开始记录操作数类型 Warm --> Spec: 连续若干次类型一致，原地改写指令 Warm --> Generic: 类型不稳定，放弃专门化 Spec --> Spec: 类型守卫通过，走快速路径 Spec --> Deopt: 类型守卫失败，例如突然传入 Decimal Deopt --> Generic: 回到通用实现并重新计数 note right of Spec 这是解释器层的自适应优化 不是 JIT 没有生成机器码 所以不需要预热到毫秒级 但它依赖类型稳定 同一函数处理多种类型时收益会被吃掉 end note
版本关键改动量级对写代码的影响

最省力的性能优化往往是升级版本

从 3.9 或 3.10 升到 3.12，同一份代码在 CPU 侧通常能白拿 20% 到 40%，成本只是跑一遍 CI 和确认几个 C 扩展的 wheel。相比之下，花两周重写热点函数换来 30% 的收益，还引入了新 bug。先做这件事，再谈别的优化。要注意的是异常处理与 frame 相关的行为在 3.11 有变化，依赖 sys._getframe 或自己拼帧栈的框架代码需要单独回归。

属性访问与方法调用为什么慢

「Python 慢」的具体成本大多花在这里。obj.attr 不是一次内存偏移读取，而是一整套协议：先看类型的 MRO 上有没有数据描述符，再看实例字典，再看类字典里的非数据描述符（函数就是非数据描述符），最后才轮到 __getattr__。方法调用还要额外创建一个绑定方法对象把 self 绑上去。

由此推出的热路径优化手法都很朴素：把循环内不变的查找提到循环外，本质是用一次 LOAD_FAST 替掉 N 次 LOAD_ATTR。

# 优化前：每轮循环做 3 次属性查找 + 1 次全局查找 + 1 次绑定方法创建
class Acc:
    def __init__(self):
        self.total = 0
        self.items = []

    def run_slow(self, rows):
        for r in rows:
            self.items.append(self.norm(r) * self.factor)   # self.items / self.norm / self.factor
        return self.items


# 优化后：把循环不变量全部提前绑定成局部变量
    def run_fast(self, rows):
        append = self.items.append   # 绑定方法只创建一次，之后是 LOAD_FAST
        norm = self.norm
        factor = self.factor         # 属性只查一次
        for r in rows:
            append(norm(r) * factor)
        return self.items

# 实测量级（百万次循环，3.12）：run_fast 比 run_slow 快约 25% 到 40%。
# 注意前提：factor 在循环里不会变。为了这点收益牺牲可读性并不总是划算，
# 只在 profile 指出的热点函数里这么写。
手法省掉什么典型收益代价与前提
循环不变的属性与方法提到循环外每轮的 LOAD_ATTR 与绑定方法分配20% 到 40%前提是循环内这些值不变，否则逻辑就错了
把全局函数赋成局部变量LOAD_GLOBAL 的字典查找（3.11 后已有内联缓存，收益变小）3.11 之前约 10%，之后个位数新版本上已不值得为它牺牲可读性
用 __slots__实例 __dict__ 的哈希查找与内存属性读写快一到两成，内存省 30% 以上不能再动态加属性，多继承受限，细节见站内核心篇
避免属性链 a.b.c.d每一级都是一次完整的属性协议按链长线性减少中间对象要确实稳定
把循环整体交给内置函数整个解释循环下沉到 C 层sum、map、str.join 常见 2 到 5 倍只适用于能用内置语义表达的逻辑

容器的实现决定了复杂度

dict 自 3.6 起用紧凑布局：一个小的索引数组加一个按插入顺序追加的 entries 数组。这带来两个结果——内存比旧实现省 20% 到 25%，以及插入顺序被保留。注意这在 3.6 只是实现细节，3.7 起才写进语言规范，所以在 3.7 及以上依赖顺序是安全的，而 set 从来没有顺序保证。

「从 list 头部 pop」是线上最常见的隐形二次复杂度：一个十万元素的队列用 lst.pop(0) 消费，总搬移量是五十亿次元素移动，而换成 collections.deque 的 popleft() 就是 O(1)。同理，判断成员是否存在时把 list 换成 set，通常是一行改动换来一到三个数量级。

字符串：不可变带来的代价

字符串不可变，所以每次拼接都产生新对象。循环里用 += 拼接在理论上是 O(n²)：第 k 次要复制已有的 k 个字符。CPython 对「引用计数为 1 的 str 做原地扩展」有一个特殊优化，让这种写法在很多情况下看起来是线性的，但这个优化不可依赖——只要那个字符串还被别处引用（比如存进了列表、传给了函数、在调试器里被观察），优化就失效，性能断崖式下跌，而且只在生产的大数据量下才暴露。

import timeit

# 反例：循环 += 拼接。看起来能跑，规模一大或引用数不为 1 就退化成二次复杂度
def concat_bad(parts):
    s = ""
    for p in parts:
        s += p
    return s

# 正例：join 一次性算出总长度，只分配一次内存
def concat_good(parts):
    return "".join(parts)

# 需要分段构造时用列表收集，最后 join
def build_report(rows):
    buf = []
    for r in rows:
        buf.append(f"{r.id},{r.name},{r.amount}")   # f-string 最快
    return "\n".join(buf)

parts = ["x" * 20] * 100_000
print(timeit.timeit(lambda: concat_bad(parts), number=10))
print(timeit.timeit(lambda: concat_good(parts), number=10))
# 典型结果：join 比循环拼接快数倍到数十倍，数据量越大差距越大
写法机制相对速度什么时候用
f-string编译期就展开成专门的格式化指令，不走运行期解析最快默认选它
str.format运行期解析格式串，再走方法调用约慢一倍格式串需要在运行期动态决定时
百分号格式化运行期解析，还要构造元组最慢的一档兼容老代码；日志里是例外（见下）
str.join先算总长度，一次分配批量拼接的唯一正解拼接列表、构造 CSV 与 SQL 片段
循环 +=依赖引用计数为 1 的原地扩展优化不稳定，失效时是二次复杂度不要用

日志是唯一该保留百分号风格的地方：logger.debug("x=%s", x) 在日志级别不够时不会执行格式化，而 logger.debug(f"x={x}") 无论级别都会先把字符串拼出来。热路径上的 debug 日志用 f-string，等于白付全量格式化成本。

另外，短的、看起来像标识符的字符串字面量会被 interning（驻留），于是 "abc" is "abc" 可能为 True。这只是实现细节，永远不要用 is 比较字符串或数字——语义比较一律用 ==，is 只用于 None 这类单例。需要高频比较大量重复字符串时，可以用 sys.intern 主动驻留，让比较退化成指针比较。

为什么 numpy 能快一两个数量级

numpy 快不是因为「C 比 Python 快」这么笼统，而是它同时省掉了三样东西：每个元素的对象头与装箱、每次运算的解释器分发、以及计算期间的 GIL。一次 arr * 2 只穿过解释器一次，剩下全在 C 层的连续内存上跑循环。

sequenceDiagram participant PY as Python 解释器 participant NP as numpy C 层 participant MEM as 连续内存缓冲区 PY->>NP: 执行一次乘法指令，传入数组对象 NP->>NP: 校验 dtype 与形状，选好对应的循环实现 NP->>PY: 主动释放 GIL，声明接下来不碰 Python 对象 NP->>MEM: 在连续内存上跑紧密 C 循环，可用 SIMD MEM-->>NP: 结果写入新缓冲区 NP->>PY: 重新获取 GIL，返回一个数组对象 Note over PY,MEM: 一百万个元素只付一次解释器分发成本 Note over PY,NP: 释放 GIL 期间其他线程可以真正并行执行

反过来也解释了 numpy 的失效条件：逐元素用 Python 循环访问数组时，每次索引都要把 C 里的标量装箱成 Python 对象，比原生 list 更慢；dtype 是 object 时所有优化全部失效；小数组（几十个元素）上的固定开销可能盖过收益。

numpy / polars / pyarrow数值与批量数据处理要按数组思维重写逻辑数据是不规则对象、逻辑分支很多时
Cython已有 Python 热点函数，想渐进加类型引入编译步骤与 C 工具链，调试与栈信息变差瓶颈其实在 IO 或数据库时，纯属白折腾

Numba数值循环，改动最小（加一个装饰器）只覆盖数值子集，首次调用要 JIT 预热函数里有字符串处理、字典操作、IO

free-threaded 的含义要说准：它是一个独立的构建变体（可执行文件带 t 后缀），不是默认发行版的开关。用它跑的进程里 GIL 被移除，多线程可以真并行执行字节码，代价是单线程性能下降、以及所有 C 扩展都需要重新适配并声明兼容。在它稳定之前，CPU 密集仍然走多进程或下沉到 C 层。

最容易踩的坑

❌
避坑清单
  • 把 dis 输出的指令条数当性能指标：指令少不等于快，一条 LOAD_ATTR 可能比五条 LOAD_FAST 都贵。
  • 指望 .pyc 提速运行期：它只省编译，执行仍是逐条解释。
  • 用 assert 做参数校验：线上加 -O 后整条校验消失，等于没写。
  • 构建镜像时重置文件 mtime，导致旧 .pyc 继续生效：要么预编译，要么用按内容哈希的失效模式。
  • 把自适应专门化当 JIT：它不生成机器码，且依赖类型稳定，同一个函数里混着 int 与 Decimal 会反复去优化。
  • 升级 Python 版本后不回归依赖帧栈的代码：3.11 起 frame 惰性创建，自己拼调用栈的日志或追踪代码可能拿不到期望结果。
  • 从 list 头部 pop 当队列用：十万级数据上是隐形的二次复杂度，profile 里只看到一个不起眼的 pop。
  • 依赖 set 的迭代顺序：dict 从 3.7 起有顺序保证，set 从来没有，换个 Python 版本或插入顺序结果就变。
  • 依赖 += 的字符串原地扩展优化：只要字符串被别处引用，优化立刻失效，性能断崖。
  • 在 numpy 数组上写 Python 循环逐元素操作：每次索引都要装箱，比 list 还慢。
  • 为了性能上 PyPy 却依赖 numpy 或数据库驱动：C 扩展兼容性会直接把方案否掉。
  • 把 free-threaded 构建当成默认发行版的开关就上生产：它是独立构建，单线程有回退，C 扩展需逐个确认。
