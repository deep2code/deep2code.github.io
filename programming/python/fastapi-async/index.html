asyncio 的性能陷阱

asyncio 的坑有一个共同特征：不报错。代码能跑、测试能过、单请求延迟正常，只有并发一上来才暴露，而现象又是最容易误判的「CPU 不高但延迟很高」。这篇先给一套能动手跑的判定流程——怎么证明事件循环真的被阻塞了、阻塞在哪一行、挪出去之后怎么确认有效——再把这些陷阱按机制串起来。框架层面的 async 与 sync handler 分派见《FastAPI 的机制与生产化》。

💡
这篇怎么读
  • ① 用法：四步把「是不是阻塞」变成可验证的结论（静态扫一遍、开调试模式看慢回调、常驻事件循环延迟探针、并发 10 与并发 100 的吞吐对照），以及把阻塞调用挪出事件循环的四种正确写法与一张参数速查表。
  • ② 原理：协作式调度下只有 await 才让出控制权、五类阻塞源与各自的替代库、三种探测手段各能看到什么、gather 与 as_completed 与 TaskGroup 的异常语义差异、取消为什么只能在 await 点生效、忘记 await 与 create_task 不持引用这两类静默 bug，以及协程与线程的量级对照。
  • ③ 场景：按业务形态选并发模型、限流放在哪一层、代价是什么，以及哪些问题看着像 asyncio 问题其实不是。

① 用法 · 怎么测出协程被阻塞，以及把它挪出去

「延迟高」不等于「被阻塞」，先按下面四步做判定，顺序不要跳：静态检查最便宜，压测对照最有说服力。

# ---------- 第 1 步：静态先扫一遍，不花运行时代价 ----------
# ASYNC 规则集专抓 async 函数里的同步调用（time.sleep、同步 open、阻塞 HTTP 客户端等）
# RUF006 抓 create_task 返回值没被保存的写法
uv run ruff check --select ASYNC,RUF006 src

# ---------- 第 2 步：本地或压测环境开调试模式，让慢回调自己报出来 ----------
# 超过阈值还没让出控制权的回调会打 WARNING，日志里带函数名与文件行号
PYTHONASYNCIODEBUG=1 uv run uvicorn myapp.main:app --port 8000
# 日志里出现 Executing ... took 0.5xx seconds 就是命中：括号里的位置就是阻塞点

# ---------- 第 3 步：常驻事件循环延迟指标（生产也能开，见下面的代码）----------
# 健康时是个位数毫秒；持续几百毫秒说明循环被人占着不放

# ---------- 第 4 步：压测对照，这一步才能证明「串行化」 ----------
# 同一个接口分别用并发 10 与并发 100 跑，看吞吐是否随并发上升
uv run python loadcheck.py http://127.0.0.1:8000/v1/orders/1 10
uv run python loadcheck.py http://127.0.0.1:8000/v1/orders/1 100
# 判读：并发翻十倍而吞吐几乎不变、单请求耗时同比恶化 => 事件循环被阻塞，不是算力不足
#       吞吐随并发上升直到某个拐点 => 正常，瓶颈在下游或 CPU

# loadcheck.py —— 第 4 步用的对照脚本，只依赖 httpx
import asyncio
import sys
import time

import httpx


async def main(url: str, concurrency: int, total: int = 300) -> None:
    sem = asyncio.Semaphore(concurrency)
    latencies: list[float] = []

    # 复用同一个 client：每次新建连接会把连接建立开销算进延迟，掩盖真正的差异
    async with httpx.AsyncClient(timeout=30.0) as client:
        async def one() -> None:
            async with sem:
                t0 = time.perf_counter()
                await client.get(url)
                latencies.append(time.perf_counter() - t0)

        start = time.perf_counter()
        async with asyncio.TaskGroup() as tg:
            for _ in range(total):
                tg.create_task(one())
        elapsed = time.perf_counter() - start

    latencies.sort()
    print(f"并发={concurrency} 吞吐={total / elapsed:.1f} req/s "
          f"P50={latencies[len(latencies) // 2] * 1000:.0f}ms "
          f"P95={latencies[int(len(latencies) * 0.95)] * 1000:.0f}ms")


if __name__ == "__main__":
    asyncio.run(main(sys.argv[1], int(sys.argv[2])))

# src/myapp/core/loop_probe.py —— 第 3 步：事件循环延迟探针，开销可忽略，建议常驻
import asyncio
import logging
import time

logger = logging.getLogger(__name__)


async def monitor_loop_lag(interval: float = 1.0, warn_ms: float = 100.0) -> None:
    """睡 interval 秒，测量实际唤醒时间与预期的差值。
    这个差值就是事件循环的排队延迟：没人阻塞时它接近 0，
    有人占着循环不放时它直接跳到几百毫秒。它比 CPU 使用率灵敏得多。"""
    while True:
        start = time.perf_counter()
        await asyncio.sleep(interval)
        lag_ms = (time.perf_counter() - start - interval) * 1000
        if lag_ms > warn_ms:
            # 和 P99 曲线对齐看：lag 突增的时间点就是阻塞发生的时间点
            logger.warning("event_loop_lag", extra={"lag_ms": round(lag_ms, 1)})
        metrics.gauge("asyncio.loop_lag_ms", max(lag_ms, 0.0))   # 作为容量水位指标上报


def enable_debug(threshold_s: float = 0.1) -> None:
    """只在本地与压测环境调用：调试模式会记录协程创建栈，本身有开销"""
    loop = asyncio.get_running_loop()
    loop.set_debug(True)
    loop.slow_callback_duration = threshold_s   # 超过这个时长未让出的回调会被告警

定位到阻塞点之后，按调用的性质选下面四种写法之一。判断标准是单次阻塞的量级：超过 1 毫秒才值得处理，超过 10 毫秒必须处理。

import asyncio
import functools
from concurrent.futures import ProcessPoolExecutor

import anyio
import httpx
from fastapi import APIRouter

router = APIRouter()

# ---------- 写法一：有异步替代库的，直接换掉（首选）----------
# 不要在 async 函数里用同步 HTTP 客户端；client 在 lifespan 里建一次并复用
@router.get("/a")
async def call_downstream(client: httpx.AsyncClient) -> dict:
    resp = await client.get("https://example.internal/api", timeout=3.0)
    return resp.json()


# ---------- 写法二：只有同步库可用，挪到线程里 ----------
@router.get("/b")
async def call_legacy_sdk() -> dict:
    # to_thread 用的是事件循环的默认线程池；它解决的是「不要卡住循环」，
    # 并不能提高吞吐上限——线程数就是并发上限，且 GIL 仍在
    return await asyncio.to_thread(legacy_sdk.fetch, "key")   # 传参数，不要传 lambda 闭包


# ---------- 写法三：CPU 密集，必须进程池；线程池对 GIL 无效 ----------
_pool = ProcessPoolExecutor(max_workers=2)   # 在 lifespan 里建，关闭时 shutdown


@router.get("/c")
async def heavy() -> dict:
    loop = asyncio.get_running_loop()
    # functools.partial 而不是 lambda：提交给进程池的可调用对象必须可 pickle
    result = await loop.run_in_executor(_pool, functools.partial(cpu_bound, 10_000))
    return {"result": result}


# ---------- 写法四：整段逻辑都是同步的，把 handler 写成普通 def ----------
# 框架会把普通 def handler 丢进线程池执行，反而比在 async 里同步调用安全
@router.get("/d")
def sync_handler() -> dict:
    return {"rows": legacy_orm.query_all()}      # 同步 ORM 放这里是可以的


async def tune_threadpool() -> None:
    # 线程池容量是一个全局上限：所有 def handler 与 to_thread 共用它。
    # 同步调用一多就会在这里排队，现象是延迟升高而循环延迟指标正常
    limiter = anyio.to_thread.current_default_thread_limiter()
    limiter.total_tokens = 80        # 按下游连接数与内存反推，不是越大越好

② 原理 · 协作式调度：只有 await 才让出控制权

搞清这一节能解决的现象是：QPS 上不去、延迟随并发线性恶化、CPU 使用率却只有百分之二十，于是被误判成「机器不够」。asyncio 是单线程事件循环加协程协作式调度。循环从就绪队列取一个协程跑，跑到 await 且确实需要等待时，协程交回控制权，循环再取下一个。关键推论：不 await 的代码，事件循环无法中断它。一段纯计算、一次同步 socket 调用、一个 time.sleep，期间整个循环停转，所有已就绪的协程一个都推进不了。

CPU 不高是因为大家都在等一个被阻塞的线程，而不是在算东西——这正是上面第 4 步压测对照能把它认出来的原因。

② 原理 · 并发控制：gather、as_completed 与 TaskGroup

搞清这一节能解决的现象是：一批并发任务里有一个失败，结果剩下的任务还在后台跑、连接没关、日志里也看不到异常。三个原语的差别主要在异常语义和资源边界，不是写法偏好。

import asyncio
import httpx


# ---------- 错误写法：一次 gather 上万个任务 ----------
async def fetch_all_bad(urls: list[str], client: httpx.AsyncClient):
    # 一万个任务立刻全部排进事件循环：文件描述符耗尽、下游连接被打爆、内存飙升
    # 而且默认行为下第一个异常就抛出，其余任务既不取消也不等待，留下一堆悬空任务
    return await asyncio.gather(*(client.get(u) for u in urls))


# ---------- 正确写法：限并发 + 单任务超时 + 结构化并发 ----------
async def fetch_all(urls: list[str], client: httpx.AsyncClient, concurrency: int = 20):
    # 并发上限按下游能承受的连接数反推，不是按任务数
    sem = asyncio.Semaphore(concurrency)
    results: dict[str, dict | None] = {}

    async def one(url: str) -> None:
        async with sem:
            try:
                # 3.11+ 的 asyncio.timeout 是上下文管理器，比 wait_for 更清晰，
                # 且不会因为包装层数导致取消语义混乱
                async with asyncio.timeout(3.0):
                    resp = await client.get(url)
                results[url] = resp.json()
            except (httpx.HTTPError, TimeoutError) as exc:
                # 单个失败不影响整批：这类「部分成功」语义要显式写出来
                results[url] = None

    async with asyncio.TaskGroup() as tg:      # 任一任务抛未捕获异常会取消其余任务
        for u in urls:
            tg.create_task(one(u))
    return results


# ---------- gather 的异常行为，必须清楚 ----------
async def gather_semantics():
    async def ok():
        await asyncio.sleep(0.1)
        return "ok"

    async def boom():
        raise ValueError("boom")

    # 默认：第一个异常立刻抛给调用方，但 ok() 仍在后台继续跑（不会被取消），
    # 如果它持有连接或文件句柄，就泄漏了
    try:
        await asyncio.gather(ok(), boom())
    except ValueError:
        pass

    # return_exceptions=True：异常作为结果返回，全部任务都会被等待完成
    # 代价是你必须逐个 isinstance 检查，漏检就等于吞掉错误
    res = await asyncio.gather(ok(), boom(), return_exceptions=True)
    for r in res:
        if isinstance(r, BaseException):
            ...   # 显式处理，别直接当结果用
原语版本某个任务失败时结果顺序适用
gather(*coros)全版本第一个异常立刻抛出，其余任务继续在后台跑与入参顺序一致任务少且全部必须成功
gather(..., return_exceptions=True)全版本异常作为结果收集，全部等完与入参一致需要部分成功结果
as_completed全版本由消费方逐个处理按完成先后要边完成边处理，做流式输出
TaskGroup3.11+自动取消兄弟任务，退出时抛 ExceptionGroup自己收集新代码默认选择，资源边界最清晰
wait全版本不抛，返回 done 与 pending 两个集合无序需要精细控制等待条件
裸 create_task 不等待全版本异常只在任务被回收时打一条警告—几乎总是 bug

② 原理 · 超时与取消：只能在 await 点生效

搞清这一节能解决的现象是：「设了 3 秒超时为什么还是卡了 30 秒」，以及优雅关闭时连接池里的连接一直没被归还。取消的实现方式是在协程下一次到达 await 时抛出 CancelledError。所以一段不含 await 的纯计算、或者卡在同步阻塞里的代码，无法被取消——超时时间到了也只能等它自己跑完。

stateDiagram-v2 [*] --> Pending: create_task 排入就绪队列 Pending --> Running: 事件循环调度 Running --> Suspended: 遇到 await 让出 Suspended --> Running: 等待完成，重新调度 Running --> Done: 正常返回 Suspended --> Cancelling: 收到取消请求 Cancelling --> Cleanup: 在 await 点抛 CancelledError note right of Cleanup finally 里的清理代码在这里执行 如果清理又 await 且未 shield 可能被二次取消，资源没真正释放 end note Cleanup --> Cancelled: 清理完成 Running --> Uncancellable: 正在跑纯计算或同步阻塞 note right of Uncancellable 没有 await 点可插入异常 取消请求只能排队等待 超时对这段代码完全无效 end note Uncancellable --> Running: 阻塞段结束后才响应取消 Cancelled --> [*] Done --> [*] 
import asyncio
import logging

logger = logging.getLogger(__name__)


async def with_reliable_cleanup(conn_pool):
    conn = await conn_pool.acquire()
    try:
        async with asyncio.timeout(2.0):      # 3.11+；旧版用 asyncio.wait_for
            return await conn.fetch("SELECT ...")
    except TimeoutError:
        # asyncio.timeout 超时会把 CancelledError 转成 TimeoutError 抛出，
        # 语义比 wait_for 更明确：这是超时，不是被别人取消
        logger.warning("query_timeout")
        raise
    finally:
        # 关键：清理里如果还要 await，必须防止它自己被取消打断。
        # shield 保证归还连接这个动作能跑完，否则连接泄漏，池很快耗尽
        await asyncio.shield(conn_pool.release(conn))


async def graceful_worker(queue: asyncio.Queue):
    try:
        while True:

        logger.info("worker_cancelled, draining")

def called_inside_running_loop():
    # 错误：asyncio.run 不能嵌套，在已有事件循环里调用会直接 RuntimeError
    # return asyncio.run(main())
    #
    # 正确做法要看你在哪个线程：
    # 1) 在事件循环所在线程的同步函数里 —— 把这个函数改成 async，一路 await 上去
    # 2) 在另一个线程里 —— 用下面这种方式把协程投递到循环并等结果
    loop = asyncio.get_event_loop_policy().get_event_loop()
    fut = asyncio.run_coroutine_threadsafe(main(), loop)

② 原理 · 两类最隐蔽的 bug

搞清这一节能解决的现象是：某个通知偶发不发出、某个后台任务偶发不执行，而日志里一条错误都没有。它们的共同点是不抛异常，只在日志里留一条容易被忽略的警告。

bug写法现象正确做法
忘记 awaitsend_notify(uid) 少写 await协程对象被创建但从未执行，业务静默不生效；回收时可能打 coroutine was never awaited 警告开 ruff 的 RUF006 与 ASYNC 规则；mypy 也能发现返回值未使用
create_task 不持引用asyncio.create_task(job()) 后不保存事件循环只持弱引用，任务可能在完成前被 GC 掉，表现为「偶发不执行」存进集合并在 done 回调里移除，或用 TaskGroup
后台任务异常无人看裸 create_task异常被存在 Task 里，没人 await 就只在回收时打印加 task.add_done_callback 统一记录异常
吞掉 CancelledErrorexcept Exception 之后又写了 except BaseException: pass优雅关闭失效，进程被强杀；3.8 起 CancelledError 继承 BaseException 正是为此捕获后必须 raise
每个请求 asyncio.run同步框架里调异步代码每次新建并销毁事件循环，连接池无法复用，开销巨大整条链路异步化，或用 run_coroutine_threadsafe 复用单个循环
 
_background: set[asyncio.Task] = set()

def spawn(coro) -> asyncio.Task:
    """安全地起一个后台任务：持引用防 GC，并且异常一定会被记录"""
    task = asyncio.create_task(coro)
    _background.add(task)                       # 事件循环只持弱引用，必须自己留强引用
    task.add_done_callback(_background.discard)

    def _log_exc(t: asyncio.Task) -> None:
        if t.cancelled():
            return
        exc = t.exception()
        if exc is not None:
            logging.getLogger(__name__).error("background_task_failed", exc_info=exc)

    task.add_done_callback(_log_exc)
    return task

搞清这一节能解决的现象是：为了「性能」把一个十并发的内部服务改成全异步，付出了一堆改造成本却测不出差别。

1000 个并发协程各几 KB，内存增长在 MB 级线程调度开销开始显著，上下文切换微秒级累加asyncio 明显占优

③ 场景 · 按业务形态选并发模型与限流位置

把前面的判断收拢成按形态的结论，代价一并写出来。

场景该怎么做为什么代价
接口大部分时间在等下游（典型 API 网关型服务）全链路异步库，每个外部调用都带超时等待可以重叠，这是 asyncio 唯一真正的收益来源整条链路都得换成异步库，混一个同步调用就白费
只有同步 ORM 可用，短期换不掉handler 写成普通 def，并按下游连接数调线程池额度框架会把它放进线程池，比在 async 里同步调用安全得多并发上限变成线程数；线程栈与连接数都要算进容量
请求里有一段加解密或图像处理进程池，或把这段能力拆成独立服务线程池对 GIL 无效，放在事件循环里会卡住所有请求序列化与进程启动成本；参数必须可 pickle
一次请求要扇出调几十上百个下游TaskGroup 加 Semaphore，每个子调用单独超时无界扇出会同时打爆下游与自己的句柄总耗时变长；要明确「部分失败」时接口返回什么
长连接、WebSocket、SSE 推送asyncio，单 worker 也能扛上万连接连接多但大部分时间空闲，线程模型撑不住单进程故障影响面大，要靠多副本兜
批量任务（导数据、对账）不要塞进请求生命周期，交给后台 worker 或队列请求级的取消会让任务在中途消失要引入队列组件，见站内消息队列专题
限流该放哪一层入口按 QPS 限，出口按下游连接数限，两层都要有只限入口，扇出仍会放大；只限出口，自己的内存先爆两套阈值都要随下游容量调整
并发只有几十、且团队不熟 asyncio同步栈加线程池，别改造这个量级两种模型测不出差别，改造成本却是实打实的无；这是纯粹的省钱

最容易踩的坑

❌
避坑清单
  • 在 async 函数里用 requests、同步 ORM、time.sleep：整个 worker 串行化，CPU 却看不出异常，最容易误诊为「机器不够」。
  • 只看 CPU 和 QPS 不看事件循环延迟：这个指标是 asyncio 服务最该常驻的健康信号，出问题时它先动。
  • 用单请求耗时判断有没有阻塞：必须做并发对照，吞吐不随并发上升才是串行化的证据。
  • asyncio.gather 一把提交上万任务：文件描述符耗尽、下游连接被打爆，还会因为超时重试形成二次冲击。
  • 以为 gather 抛异常后其他任务停了：默认它们还在后台跑，持有的连接和句柄全部泄漏。
  • return_exceptions=True 之后不检查返回值类型：异常被当成正常结果写进了业务数据。
  • 忘记 await：协程对象创建了却从不执行，没有异常、没有报错，只有一条容易被过滤掉的警告。
  • create_task 之后不保存引用：事件循环只持弱引用，任务可能在跑完之前被 GC，表现为「偶发丢消息」。
  • 后台任务不加 done 回调记异常：任务里的报错只在对象被回收时打印，等于没有监控。
  • 给 CPU 密集代码设超时：取消只在 await 点生效，纯计算段落根本无法被打断，超时形同虚设。
  • 用线程池跑 CPU 密集任务：GIL 让它们互相排队，换成进程池才有意义。
  • 在 finally 里直接 await 做清理：这段清理自身可能被取消打断，连接没归还，池很快耗尽。
  • 捕获 CancelledError 后不重抛：优雅关闭失效，发布期间在途请求被硬切。
  • 在已有事件循环里调 asyncio.run：直接 RuntimeError；跨线程调用要用 run_coroutine_threadsafe。
  • 每个请求新建一个 HTTP 客户端：连接池形同虚设，延迟里凭空多出建连与 TLS 握手。
  • 把 asyncio 调试模式常开在生产：它会记录协程创建栈，排查工具自己变成性能问题。
