Python 后端项目的工程骨架

Python 项目的技术债大多不在业务逻辑里，而在骨架上：目录怎么分、配置从哪来、日志谁初始化、异常在哪转成 HTTP、类型注解要不要管。这几件事在前两周定下来成本接近零，等代码长到几万行再改就得动全局。这篇先给一份可以直接照抄的目录树与最小可运行入口，再解释每个选择挡住了哪类事故。框架自身的机制在《FastAPI 的机制与生产化》，依赖与环境怎么组织在下一篇。

💡
这篇怎么读
  • ① 用法：一份可直接照抄的 src 布局目录树、只做装配的最小可运行入口（lifespan 建资源、工厂函数建 app、异常处理器注册），建环境与自检的四条命令，外加「常见任务 → 怎么做 → 注意什么」和骨架关键约定两张速查表。
  • ② 原理：依赖方向为什么必须单向、src 布局到底挡住了哪类漏检、pyproject.toml 相比 setup.py 换来了什么、为什么配置错误必须在启动那一刻就崩、dictConfig 与 contextvars 的正确初始化位置、领域异常怎么在边界统一转成响应体、类型注解运行时不生效这件事的全部推论。
  • ③ 场景：从一次性脚本到多人协作的对外服务，骨架各要做到哪一步、代价是什么，以及哪些问题不该在骨架层解决。

① 用法 · 一份可直接照抄的目录树与最小可运行入口

先把形状定下来。下面这棵树和两段代码合起来就是一个能跑、能测、能装进镜像的最小服务，每个目录的职责在注释里，为什么这么分在原理层。

# ---------- 1. 目录树：照抄即可，src 布局是其中唯一不能省的决定 ----------
myapp/
├── pyproject.toml          # 构建元数据 + ruff / mypy / pytest 配置，全部集中在这一个文件
├── .env.example            # 只提交示例；真实 .env 必须进 .gitignore
├── Dockerfile
├── src/myapp/
│   ├── __init__.py         # 保持为空，不要在这里 import 子模块
│   ├── main.py             # 进程入口：只做装配，一行业务都不写
│   ├── api/                # 只做协议转换
│   │   ├── deps.py         # 依赖装配：从 app.state 取资源、鉴权、分页参数
│   │   ├── routers/        # 路由函数，一个资源一个文件
│   │   └── schemas/        # 请求与响应模型，与数据库模型分开
│   ├── service/            # 业务规则与用例编排，禁止出现 Request / HTTPException
│   ├── repository/         # 数据访问，SQL 与 ORM 只出现在这一层
│   └── core/               # 横切：config.py / logging.py / errors.py
└── tests/                  # 与 src 同级，靠「已安装的包」导入，而不是靠当前目录
    ├── conftest.py
    └── test_orders.py

# src/myapp/main.py —— 进程入口：装配 app，不写业务
from collections.abc import AsyncIterator
from contextlib import asynccontextmanager

from fastapi import FastAPI

from myapp.api.routers import health, orders
from myapp.core.config import get_settings
from myapp.core.errors import register_handlers
from myapp.core.logging import setup_logging
from myapp.repository.pool import create_pool


@asynccontextmanager
async def lifespan(app: FastAPI) -> AsyncIterator[None]:
    settings = get_settings()          # 配置有问题就在这里抛异常，容器直接起不来
    setup_logging(settings.log_level)  # 日志必须在任何业务日志之前配好
    app.state.pool = await create_pool(settings.database_url, settings.db_pool_size)
    try:
        yield                          # yield 之前是启动阶段，之后是关闭阶段
    finally:
        # 放在 finally：启动过程中抛异常时，已经建好的资源同样要回收
        await app.state.pool.close()


def create_app() -> FastAPI:
    settings = get_settings()
    # 用工厂函数而不是模块级裸 app：测试里可以用不同配置各建一个实例，互不干扰
    app = FastAPI(
        title="myapp",
        lifespan=lifespan,
        docs_url=None if settings.env == "prod" else "/docs",  # 生产不暴露交互文档
        openapi_url=None if settings.env == "prod" else "/openapi.json",
    )
    register_handlers(app)             # 异常处理器先注册，后面注册的路由才受它保护
    app.include_router(health.router)  # 探针路由不带前缀，也不进鉴权依赖
    app.include_router(orders.router, prefix="/v1/orders", tags=["orders"])
    return app


app = create_app()                     # uvicorn 指向这个对象：myapp.main:app

写接口测试httpx.ASGITransport 直连 app，用 dependency_overrides 替掉 get_settings 与仓储测试不连真实数据库；lifespan 里的资源用 fixture 替换

提交前拦一遍pre-commit 里跑 ruff 与 mypy，CI 里再跑一遍全量本地跳过检查（--no-verify）只是把等待挪到 CI

骨架里几个关键约定的取值，抄的时候别改错方向：

约定或参数作用默认值什么时候需要改
src 布局测试导入的是已安装的包，而不是源码目录无默认，必须自己选只有一次性单文件脚本才不需要
Settings 必填字段不给默认值配置缺失时启动即失败不给默认就是必填只有「缺失时有安全回退语义」的项才给默认

lifespan启动与关闭钩子，取代已废弃的 on_event无所有会失败的初始化都必须放进来，而不是模块级执行
docs_url / openapi_url交互文档与 schema 路径/docs 与 /openapi.json生产设为 None，或放到需要鉴权的内网路径后面
disable_existing_loggersdictConfig 是否静音已创建的 loggerTrue必须显式写 False，否则第三方库的日志全没了
[tool.mypy] strict打开一组严格检查false新项目直接 true；老项目按模块用 overrides 逐个收紧

上面这些形状为什么长这样——为什么测试必须导入已安装的包、为什么配置错误要让进程直接退出、为什么日志只能在入口配一次、为什么 service 里不能抛 HTTPException——都在下面几节。

② 原理 · 分层与依赖方向

搞清这一节能解决的现象是：想给某个用例加一个消息队列入口，结果发现 service 里到处是 Request，只能把整个 HTTP 框架一起拖进来。骨架的第一条规则是依赖只能单向：接口层依赖服务层，服务层依赖仓储层，反过来不行。判断有没有做对只看一件事——service 里能不能出现 Request、HTTPException 这类框架类型。出现了就说明 HTTP 细节漏进了业务层，换协议或写单测时会立刻付出代价。

目录布局的另一半是 src 布局，它解决的不是美观问题，而是打包问题在本地测不出来：

布局包的位置pytest 导入到的是会漏掉什么问题
扁平布局（flat layout）仓库根目录下的 myapp/源码目录（当前目录被加进搜索路径）包数据文件没打进去、入口点未注册、子包漏写——本地全绿，装到别处就 ImportError
src 布局src/myapp/已安装的包（不安装就 import 不到）基本不会漏，本地测的就是真实安装形态
单文件脚本main.py自己没有包边界，模块一多必然循环引用

配套的安装方式是可编辑模式（pip install -e . 或 uv pip install -e .）：包的元数据被注册，导入走的是真实安装路径，改代码又不需要重装。

② 原理 · pyproject.toml：一个文件管住构建与工具

搞清这一节能解决的现象是：装包之前必须先执行别人的 Python 代码，以及同一个项目里 lint、类型检查、测试各有一个配置文件、规则互相打架。setup.py 是可执行代码，装包前要先跑它，既不安全也无法静态解析依赖。pyproject.toml（PEP 517/518/621）是声明式的，构建后端、元数据、依赖、以及 ruff / mypy / pytest 的配置全放一处。

    "fastapi",
    "uvicorn[standard]",

    "sqlalchemy",

[project.optional-dependencies]

dev = ["ruff", "mypy", "pytest", "pytest-asyncio", "httpx"]

[tool.hatch.build.targets.wheel]

[tool.ruff]
line-length = 100
target-version = "py312"
src = ["src"]                 # 让 isort 规则知道哪些是本项目包，第一方导入才会分组正确

[tool.ruff.lint]

ignore = ["E501"]             # 行长交给 formatter，不在 lint 里重复报

[tool.ruff.lint.per-file-ignores]

[tool.mypy]

[tool.pytest.ini_options]

② 原理 · 配置：错就错在启动那一刻

搞清这一节能解决的现象是：服务看起来正常，但连到了错误的数据库、把测试密钥用在了生产、或者某个低频分支上线两周后才报 KeyError。最该坚持的一条原则：配置错误必须让进程起不来。散落在各处的 os.environ.get("X", "default") 的真正问题不是丑，而是把「配置缺失」推迟到某个低频分支被触发时才暴露，而且往往表现为静默的错误行为。

sequenceDiagram participant K as 编排系统 participant P as 进程 participant C as Settings 实例化 participant L as lifespan 启动钩子 K->>P: 启动容器，注入环境变量 P->>C: 导入时构造 Settings C->>C: 类型转换与必填校验 C-->>P: 缺字段或类型不对，直接抛 ValidationError P-->>K: 非零退出，容器起不来，流量不会切过来 C->>L: 校验通过，进入启动钩子 L->>L: 建连接池、预热缓存、注册指标 L-->>K: 就绪探针通过，开始接流量 Note over P,L: 所有可能失败的初始化都放在接流量之前 
# src/myapp/core/config.py
from functools import lru_cache
from typing import Literal

from pydantic import Field, PostgresDsn, field_validator
from pydantic_settings import BaseSettings, SettingsConfigDict


class Settings(BaseSettings):
    model_config = SettingsConfigDict(
        env_file=".env",           # 只用于本地开发；生产靠真实环境变量
        env_prefix="APP_",         # 加前缀，避免和系统变量撞名
        extra="forbid",            # 多给了不认识的变量就报错，能抓出拼写错误
        frozen=True,               # 运行期不可改，杜绝「某处偷偷改配置」
    )

    env: Literal["local", "staging", "prod"]      # 没有默认值 = 必填
    database_url: PostgresDsn                      # 类型即校验，格式不对直接崩
    redis_url: str
    secret_key: str = Field(min_length=32)         # 长度不够启动就失败
    db_pool_size: int = Field(default=10, ge=1, le=50)
    request_timeout_s: float = Field(default=3.0, gt=0)
    log_level: Literal["DEBUG", "INFO", "WARNING", "ERROR"] = "INFO"

    @field_validator("secret_key")
    @classmethod
    def reject_placeholder(cls, v: str) -> str:
        # 把「忘了替换示例值」这类事故挡在启动阶段
        if v in {"changeme", "secret", "test"}:
            raise ValueError("secret_key 仍是占位值")
        return v


@lru_cache
def get_settings() -> Settings:
    # 缓存成单例；作为 FastAPI 依赖时测试里可以用 dependency_overrides 替换
    return Settings()
做法配置写错时的表现评价
os.environ["DB_URL"] 散落各处首次执行到该行才 KeyError能报错但时机太晚，且没有类型校验
os.environ.get("DB_URL", "localhost")静默连到错误目标，不报任何错最危险，事故常从这里开始
模块级常量 + if env 判断分支写错要靠代码评审发现环境一多就失控
pydantic-settings 集中定义启动即 ValidationError，一次列出所有问题字段推荐；配合 extra="forbid" 还能抓拼写错误

② 原理 · 日志：入口配置一次，模块只管打

搞清这一节能解决的现象是：同一条日志被打了两遍、格式对不上、asyncio 下 request_id 串号、以及进程被杀时最后几秒的日志全部丢失。两条硬规则。第一，只有应用入口能配 handler 与 level，库和业务模块只做 logger = logging.getLogger(__name__)；库里加 handler 会造成重复输出，调用方还没法统一管控。第二，不要用 print：它绕开级别控制与结构化字段，在容器里还受 stdout 缓冲影响，日志可能根本没落下来。

# src/myapp/core/logging.py
import contextvars
import logging
import logging.config

request_id_var: contextvars.ContextVar[str] = contextvars.ContextVar("request_id", default="-")


class RequestIdFilter(logging.Filter):
    """把 contextvars 里的 request_id 注入每条日志。
    用 contextvars 而不是 threading.local，是因为 asyncio 下同一线程跑多个请求，
    thread-local 会串号；contextvars 天然跟随协程上下文。"""

    def filter(self, record: logging.LogRecord) -> bool:
        record.request_id = request_id_var.get()
        return True


def setup_logging(level: str = "INFO") -> None:
    logging.config.dictConfig({
        "version": 1,
        "disable_existing_loggers": False,   # 关键：否则第三方库已创建的 logger 会被静音
        "filters": {"request_id": {"()": RequestIdFilter}},
        "formatters": {
            # 生产建议换成 JSON formatter（python-json-logger 或 structlog），
            # 采集端才能按字段检索；这里保留纯文本便于本地阅读
            "std": {"format": "%(asctime)s %(levelname)s %(name)s [rid=%(request_id)s] %(message)s"},
        },
        "handlers": {
            "console": {
                "class": "logging.StreamHandler",
                "stream": "ext://sys.stdout",   # 容器里统一写 stdout，不要自己写文件切割
                "formatter": "std",
                "filters": ["request_id"],
            },
        },
        "root": {"handlers": ["console"], "level": level},
        "loggers": {
            # 访问日志交给网关或中间件，避免同一请求被记两遍
            "uvicorn.access": {"handlers": ["console"], "level": "WARNING", "propagate": False},
            "sqlalchemy.engine": {"level": "WARNING"},   # 开 INFO 会把每条 SQL 打出来
        },
    })

request_id 的生成、透传到下游、与 trace 关联的完整做法见站内 日志与可观测性专题，日志在容器里怎么被采集、以及 PYTHONUNBUFFERED 这类必设项见《Python 服务上生产》，这里只给注入点。

② 原理 · 错误处理：异常在边界统一转成响应

搞清这一节能解决的现象是：同一个服务返回了五种不同结构的错误体，客户端只能靠状态码猜；以及接口返回 200 空数据、监控一片绿、排查时完全没有线索。业务代码里不应该出现 HTTPException。正确形态是：service 抛领域异常，框架边界有一个处理器把领域异常映射成统一的错误响应体。这样换协议、写单测、复用 service 都不受影响，错误结构也天然一致。

# src/myapp/core/errors.py
from fastapi import FastAPI, Request
from fastapi.responses import JSONResponse
import logging

logger = logging.getLogger(__name__)


class AppError(Exception):
    """项目级异常基类：业务代码只抛它的子类，不碰 HTTP"""
    code = "internal_error"
    status = 500
    message = "服务内部错误"

    def __init__(self, message: str | None = None, **extra: object) -> None:
        self.message = message or self.message
        self.extra = extra            # 结构化上下文，进日志不进响应体
        super().__init__(self.message)


class NotFound(AppError):
    code, status, message = "not_found", 404, "资源不存在"


class PermissionDenied(AppError):
    code, status, message = "permission_denied", 403, "无权访问"


class ConflictError(AppError):
    code, status, message = "conflict", 409, "资源状态冲突"


def register_handlers(app: FastAPI) -> None:
    @app.exception_handler(AppError)
    async def handle_app_error(request: Request, exc: AppError) -> JSONResponse:
        # 业务预期内的错误：warning 级别，不触发告警
        logger.warning("app_error", extra={"code": exc.code, **exc.extra})
        return JSONResponse(
            status_code=exc.status,
            content={"code": exc.code, "message": exc.message},
        )

    @app.exception_handler(Exception)
    async def handle_unexpected(request: Request, exc: Exception) -> JSONResponse:
        # 未预期异常：带 traceback 记 error，这类才该告警；响应体不能泄露内部信息
        logger.exception("unhandled_error", extra={"path": request.url.path})
        return JSONResponse(status_code=500, content={"code": "internal_error", "message": "服务内部错误"})
异常类别HTTP 状态日志级别是否告警
参数校验失败（pydantic）422info 或不记否，客户端问题
领域异常（不存在、状态冲突、余额不足）404 / 409 / 400warning，带业务上下文否，但值得看趋势突增
鉴权失败401 / 403warning否，但需要风控侧的频率统计
下游超时或熔断502 / 504error是，按错误率阈值
未捕获异常500error 且必须带 traceback是，最高优先级
裸 except: 吞掉的一切看起来正常没有日志无法告警，最糟糕的情况

② 原理 · 类型注解与工具链：注解不是校验

搞清这一节能解决的现象是：接口签名写了类型，脏数据照样进了数据库；以及 CI 里堆了五个检查工具、跑得慢还互相报同一个问题。必须先说清楚：类型注解在运行时不生效。def f(x: int) 传字符串照样执行，注解只是存在 __annotations__ 里的元数据。它的价值在静态检查与工具链（mypy、IDE、FastAPI 的签名推导）。推论很实际：所有外部输入必须另外做运行时校验，这件事交给 pydantic，别指望注解。

工具 / 特性解决什么落地建议
mypy --strict拦住类型错误、漏写返回值、隐式 Any老项目别全量开：先在 CI 里只检查改动文件，再按模块用 [[tool.mypy.overrides]] 逐个收紧
Protocol定接口不用继承，实现方无感用于模块边界解耦，以及给没有类型存根的第三方类型补描述
TypedDict描述固定形状的 dict（如第三方返回的 JSON）适合不想建模型的中间数据；需要校验就换 pydantic
Literal / Enum把「魔法字符串」变成可检查的取值集合状态、环境名、渠道号一律用它
Final / frozen 模型防止配置与常量被运行期改写配置类直接 frozen=True
pydantic 模型运行时校验与类型转换只在边界用：HTTP 入参、消息体、外部 API 响应

工具选择这件事已经收敛，三个工具就够，不需要再叠：

职责旧组合现在差别

格式化blackruff format 或 black输出高度一致，ruff format 少装一个工具
类型检查无mypy唯一能在 CI 里拦住类型错误的手段
测试unittestpytest + pytest-asynciofixture 与参数化更省样板，异步测试需要 asyncio_mode

提交前拦截人工pre-commit 跑 ruff 与 mypy把问题挡在 CI 之前，省一轮等待

③ 场景 · 不同项目形态下骨架要做到哪一步

骨架不是越全越好，它的成本是样板代码，收益要看这段代码会活多久、有几个人改。下表按真实形态给结论，也给代价。

场景该怎么做为什么代价
一次性脚本或一周内会删的 POC单文件加一个 Settings 类，其余都不要分层收益追不上样板成本，但配置校验的收益是即时的一旦它活下来，补骨架的时机很容易被业务排期挤掉
内部工具，单人维护src 布局 + core（config / logging）+ ruff目录分层收益小，配置与日志的收益与团队规模无关几乎没有；这是最低成本档
对外 API 服务，多人协作全套：分层 + 领域异常映射 + mypy strict + pytest错误结构一致性与可测性直接决定迭代速度初期样板多，需要一次约定并写进评审清单
从大单体里拆出来的服务先把 core 与异常边界立住，分层按模块逐步迁一次性重构目录会和在跑的业务改动持续冲突过渡期两套写法共存，必须写明「新代码走哪套」
要发布成库给别人装src 布局 + 完整 pyproject 元数据 + 明确构建后端打包问题必须在本地就能测出来还要定版本与发布策略，见工具链篇
同一份用例要有多个入口（HTTP、消息消费、定时）service 层必须与框架完全无关入口不同但用例相同，只有 service 无框架依赖才能复用多一层间接调用；参数对象要自己定义而不是直接传 Request
团队对 mypy 阻力大只对 core 与 service 开 strict，api 层先宽松类型收益集中在业务与横切层，先拿高价值部分检查有盲区，边界代码仍靠 pydantic 兜
多环境（local / staging / prod）同一个 Settings 类，环境之间只改注入值用 if env == 分支实现差异，环境一多必然漏改某个分支需要维护一份配置清单，并在部署侧校验字段齐全

把上面的判断反过来看，就是这张反模式表——每一条都对应一类线上事故：

反模式代价正确做法
用 print 当日志没有级别、没有结构化字段，容器缓冲下还可能丢失logging.getLogger(__name__)，入口 dictConfig 一次
配置散落在业务代码里改环境要全局搜，错配到运行时才暴露集中到 Settings，启动即校验
裸 except:连 KeyboardInterrupt、SystemExit 一起吞，进程无法正常退出捕获具体类型；兜底用 except Exception 且必须记 traceback
没有注解也不做运行时校验脏数据一路穿到数据库内部靠 mypy，边界靠 pydantic
__init__.py 写成一堆导入导入任意子模块都拉起整个包，循环引用与启动变慢保持为空或只放少量公开符号
service 里抛 HTTPException业务层绑死 HTTP，复用与单测都要装框架抛领域异常，边界统一转换
扁平布局 + 本地跑测试打包问题全部漏检，装到别处才 ImportErrorsrc 布局加可编辑安装
模块级建连接池或读远程配置导入即发起 IO，测试收集阶段就挂，还没法注入替身放进 lifespan，挂到 app.state

不适用边界：骨架解决不了依赖装错版本与镜像里装了什么的问题，那在依赖与环境管理与工具链篇；单请求慢、协程被阻塞在《asyncio 的性能陷阱》；起几个进程、怎么关得干净、探针怎么配在《Python 服务上生产》；WSGI 与 ASGI 两份契约本身的差异在《Python Web 服务的部署形态》；语言层面的默认参数、闭包、相等与哈希这类陷阱在《Python 的语义陷阱清单》；鉴权、输入过滤、密钥管理这些安全基线在站内安全专题。

这条路径上，上一篇讲的是 FastAPI 这个框架本身怎么运作，本篇把它放进一个项目的骨架里，下一篇再往外一层，处理这套骨架的依赖与环境怎么在本地、CI 与生产之间保持一致。

最容易踩的坑

❌
避坑清单
  • 扁平布局下靠 pytest 顺带把当前目录加进搜索路径：测试导入的是源码目录，包数据与入口点问题全漏检。
  • os.environ.get("DB_URL", "localhost") 这类带默认值的读法：配置缺失时静默连到错误目标，比直接报错危险得多。
  • .env 提交进仓库：本地便利换来密钥泄露，.env 必须进 .gitignore，生产只用真实环境变量。
  • 在库或业务模块里 logging.basicConfig / 加 handler：日志重复输出，格式还互相打架。
  • dictConfig 里漏写 disable_existing_loggers: False：已经创建的第三方 logger 被静音，问题发生时什么都看不到。
  • 用 threading.local 存 request_id：asyncio 下同一线程跑多个请求，日志串号，必须用 contextvars。
  • 把 sqlalchemy.engine 开到 INFO 上线：每条 SQL 都打，日志量暴涨且可能带出敏感参数。
  • 裸 except: pass：接口返回 200 空数据，监控一片绿，排查时完全没有线索。
  • 500 响应里直接带 str(exc) 或 traceback：把内部路径、SQL、依赖版本泄露给调用方。
  • 老项目一次性开 mypy --strict：报出几千条错误只能整体忽略，检查形同虚设；要按模块渐进收紧。
  • 以为类型注解能挡住脏数据：注解运行时不生效，边界必须有 pydantic 校验。
  • __init__.py 里互相导入子模块：循环引用报错信息只指向导入行，真正的环要靠人肉推。
  • 在模块级建连接池、读远程配置或做鉴权初始化：导入即执行，测试收集阶段就失败，也无法用依赖覆盖替换。
  • 生产环境忘记关 /docs 与 /openapi.json：内部字段名、枚举值、校验规则等于对外公开。
