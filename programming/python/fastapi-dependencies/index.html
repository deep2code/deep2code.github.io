依赖与环境管理：从 pip 到 uv

这篇只回答一个问题：在一个 Web 服务项目里，依赖与环境怎么组织，才能让本地、CI 与生产装出同一套东西。所以重点是目录里放哪些描述文件、依赖分成几组、镜像怎么装、配置与密钥怎么进到进程里。pip 与 Poetry 与 uv 这些工具本身的求解算法、锁定格式与代际差异不在这里重复，详见站内《Python 依赖与工程工具链：从 pip 到 uv》；这里只做一个结论性选择：新服务用 uv，老服务用 pip-tools 过渡，下面的形态两者都适用。

💡
这篇怎么读
  • ① 用法：一个服务项目的依赖描述文件长什么样（运行时 / 开发 / 测试三组怎么分）、一份能直接用的多阶段 Dockerfile、以及用 pydantic-settings 把环境变量与挂载的密钥文件读进程序的写法，配一张任务对照表和一张构建参数速查表。
  • ② 原理：每个依赖组该装在哪一层、镜像层缓存为什么会被一行代码改动打穿、配置来源的优先级与密钥为什么不能进镜像、锁文件在服务项目里到底锚定了什么、本地与 CI 与生产三套环境的漂移从哪来怎么查，以及私有源与镜像上的几条供应链防线。
  • ③ 场景：单体服务、多服务共库、带 GPU 或编译依赖、需要离线安装等形态各该怎么组织，以及哪些问题不属于依赖管理。

① 用法 · 依赖分组、多阶段构建与配置读取的最小可用形态

一个服务项目里与依赖有关的文件只有四个：pyproject.toml 声明意图，锁文件锚定结果，Dockerfile 决定装到哪一层，.env.example 说明需要哪些配置。下面三段合起来就是可用形态。

# pyproject.toml —— 只看与依赖分组相关的部分
[project]
name = "myapp"
version = "0.1.0"
requires-python = ">=3.12"

# 运行时依赖：这一组，且只有这一组，会进生产镜像
dependencies = [
    "fastapi",
    "uvicorn[standard]",
    "pydantic-settings",
    "sqlalchemy[asyncio]",
    "asyncpg",
]

[project.optional-dependencies]
# 测试单独成组：CI 的测试任务装它，生产不装
test = ["pytest", "pytest-asyncio", "httpx"]
# 本地开发工具：只在开发机与 CI 的静态检查任务里装
dev = ["ruff", "mypy", "pytest", "pytest-asyncio", "httpx", "ipython"]
# 可插拔能力：按部署环境选装，不要塞进 dependencies
otel = ["opentelemetry-instrumentation-fastapi"]

[tool.hatch.build.targets.wheel]
packages = ["src/myapp"]

# ---------- 本地：声明一次，锁一次，同步一次 ----------
uv add fastapi "uvicorn[standard]" pydantic-settings     # 写进 dependencies 并更新锁文件
uv add --dev ruff mypy pytest                            # 写进开发组，生产镜像不会装
uv lock                                                  # 解析全部传递依赖，落盘成 uv.lock
uv sync                                                  # 让 .venv 与锁文件完全一致（多余的包会被卸载）

# ---------- CI：不允许悄悄改锁文件 ----------
uv sync --frozen                    # 锁文件与 pyproject 不一致就直接失败
uv run ruff check . && uv run mypy src && uv run pytest -q

# ---------- 三个环境是否一致，用这三条命令确认 ----------
uv sync --frozen --dry-run          # 有差异就非零退出：本地环境漂移检测
uv pip check                        # 已装包之间的依赖约束是否都被满足
docker run --rm myapp:dev python -c "import importlib.metadata as m; print(m.version('fastapi'))"

# ---------- 升级依赖是一个显式动作，要进 code review ----------
uv lock --upgrade-package fastapi   # 只升这一个，diff 清晰，出问题能二分

# Dockerfile —— 多阶段：编译工具链与开发依赖都留在第一阶段
FROM python:3.12-slim AS builder

# uv 作为独立二进制拷进来，不用 pip 装，也就不污染项目环境
COPY --from=ghcr.io/astral-sh/uv:latest /uv /usr/local/bin/uv

WORKDIR /app
ENV UV_COMPILE_BYTECODE=1 \
    UV_LINK_MODE=copy

# 关键：只拷依赖描述文件。这一层只在依赖变化时失效，改业务代码不会触发重装
COPY pyproject.toml uv.lock ./
RUN --mount=type=cache,target=/root/.cache/uv \
    uv sync --frozen --no-dev --no-install-project

# 源码最后拷；--no-install-project 先装依赖、这一步再装项目本身
COPY src ./src
RUN --mount=type=cache,target=/root/.cache/uv \
    uv sync --frozen --no-dev

FROM python:3.12-slim AS runtime

ENV PYTHONUNBUFFERED=1 \
    PYTHONDONTWRITEBYTECODE=1 \
    PATH="/app/.venv/bin:$PATH"

# 非 root 运行；运行阶段一个构建工具都不装
RUN useradd --create-home --uid 10001 appuser
WORKDIR /app
COPY --from=builder --chown=appuser:appuser /app/.venv /app/.venv
COPY --from=builder --chown=appuser:appuser /app/src /app/src
USER appuser

EXPOSE 8000
CMD ["uvicorn", "myapp.main:app", "--host", "0.0.0.0", "--port", "8000"]

# src/myapp/core/config.py —— 配置与密钥的唯一入口
from functools import lru_cache
from pathlib import Path
from typing import Literal

from pydantic import Field, PostgresDsn, SecretStr
from pydantic_settings import BaseSettings, SettingsConfigDict


class Settings(BaseSettings):
    model_config = SettingsConfigDict(
        env_prefix="APP_",
        env_file=".env",            # 只服务本地开发；镜像里不打包 .env
        env_nested_delimiter="__",  # APP_DB__POOL_SIZE 可以映射到嵌套模型
        secrets_dir="/run/secrets", # 编排系统把密钥挂成文件时，直接按文件名取
        extra="forbid",
        frozen=True,
    )

    env: Literal["local", "staging", "prod"]     # 无默认值即必填
    database_url: PostgresDsn
    # SecretStr 的作用是防手滑：repr 与日志里显示成掩码，不会被整个 Settings 打出来
    db_password: SecretStr
    db_pool_size: int = Field(default=10, ge=1, le=50)

    @property
    def dsn(self) -> str:
        # 真正要用明文时显式取一次，这样「哪里用了密钥」在代码里可搜
        return str(self.database_url).replace("__PWD__", self.db_password.get_secret_value())


@lru_cache
def get_settings() -> Settings:
    return Settings()               # 启动时实例化一次；缺字段就在这里崩


if __name__ == "__main__":
    # 部署前自检：把这一行加进 CI 与容器启动脚本，配置缺失在此刻暴露而不是在流量里
    s = get_settings()
    print("config ok:", s.env, "pool =", s.db_pool_size, "secrets from", Path("/run/secrets").exists())

日常任务按下表查：

要做什么怎么做注意什么
加一个运行时依赖uv add xxx，锁文件一起提交只有服务运行真正要用的才进这一组，判断标准是「删了它接口会不会挂」
加一个只在测试里用的库uv add --dev 或写进 test extra别图省事塞进 dependencies，它会被一路带进生产镜像
构建生产镜像多阶段 + uv sync --frozen --no-dev--frozen 保证镜像里的版本就是锁文件里的版本，没有它构建期可能悄悄解析出新版本
加一个配置项Settings 加字段 → 改 .env.example → 改部署清单三处顺序反了就会出现「代码已经读了、环境还没给」，好在会在启动时立刻暴露
接一个密钥编排侧挂成文件到 secrets_dir，或注入环境变量；字段类型用 SecretStr密钥不进镜像、不进 pyproject、不进日志；轮转由编排侧负责
确认三套环境一致uv sync --frozen --dry-run 加 uv pip check，再在容器里打印关键包版本「本地能跑」不构成证据，必须拿容器里的版本做对照
升级一个依赖uv lock --upgrade-package xxx，锁文件 diff 进评审一把全量 --upgrade 会让几十个包同时变化，出问题无法二分
排查「本地好、容器里 ImportError」删掉 .venv 用 uv sync 重建，再对照容器本地环境里往往有历史残留包，锁文件里并没有它

与构建有关的几个参数，抄的时候别漏：

参数或变量作用默认值什么时候需要改
--frozen禁止更新锁文件，不一致直接失败关CI 与镜像构建一律开；只有本地主动升级时才不加
--no-dev跳过开发组依赖关（默认会装开发组）生产镜像必开，这是镜像瘦身最大的一刀
--no-install-project只装依赖，不装项目自身关多阶段构建的第一步用它，把依赖层与源码层分开
UV_COMPILE_BYTECODE安装时预编译 pyc关镜像里开：换来更快的首次启动，代价是镜像稍大
UV_LINK_MODE从缓存到环境的落盘方式（复制或链接）随平台与文件系统变化，以 uv --help 与文档为准容器里配合缓存挂载时设成 copy，避免跨挂载点硬链接失败
UV_CACHE_DIR缓存目录位置系统缓存目录CI 里指到可持久化的路径，命中后安装几乎瞬时
secrets_dir（pydantic-settings）把目录下的文件名当字段名读取不启用编排系统以文件形式挂载密钥时设置，避免密钥出现在环境变量里
pip install --no-cache-dir不在镜像层里留 wheel 缓存会留缓存仍用 pip 的镜像必加，否则白占几十到几百 MB

为什么要这么分组、为什么源码必须最后拷、为什么密钥不能写进镜像、锁文件到底锚定了什么——在下面几节。

② 原理 · 依赖分组的边界：每组装在哪一层

搞清这一节能解决的现象是：生产镜像莫名大出几百兆，或者线上进程里居然能 import pytest。分组不是整理癖，它决定了每个包会出现在哪个环境里，而每多一个包就多一条供应链路径。

框架 驱动 客户端库"] DEV["dev 组
ruff mypy ipython"] TST["test 组
pytest 插件 httpx"] OPT["extras
可插拔能力"] BLD["构建期依赖
编译工具链 头文件"] end subgraph LOCAL["本地开发机"] L1["装 dependencies 加 dev 加 test"] end subgraph CI["CI 流水线"] C1["静态检查任务装 dev"] C2["测试任务装 test"] C3["构建任务只用锁文件"] end subgraph IMG["生产镜像 runtime 阶段"] P1["只有 dependencies
与按需选装的 extras"] end RT --> L1 DEV --> L1 TST --> L1 RT --> C3 DEV --> C1 TST --> C2 RT --> P1 OPT --> P1 BLD --> C3
分组放什么安装位置混错了会怎样
运行时依赖（dependencies）框架、数据库驱动、下游客户端库生产镜像、CI、本地漏一个就是线上 ImportError，多一个就是无谓的攻击面
开发依赖（dev）ruff、mypy、调试工具本地与 CI 的检查任务，不进生产镜像进了镜像：体积涨、攻击面涨，个别库还会在被导入时打补丁改行为
测试依赖（test）pytest 与插件、假数据、测试用 HTTP 客户端CI 的测试任务；与 dev 合并也可以与运行时混在一起后，「能不能删」的判断就全靠人记
可选依赖（extras）只有部分部署环境要用的能力，如某个云厂商 SDK、链路追踪按部署形态选装塞进必装组会逼所有环境都装上，包括根本用不到它的环境
构建期依赖编译工具链、头文件、hatchling 这类构建后端多阶段构建的第一阶段留在最终镜像里，等于把编译器一起发布上线

② 原理 · 镜像层缓存：顺序决定构建时间

搞清这一节能解决的现象是：改一行代码，CI 要重新装一遍全部依赖。构建慢八成是因为 COPY . . 写在了装依赖之前——任何一行代码改动都会让这一层的哈希变化，后面所有层的缓存一起失效。顺序必须是：先拷依赖描述文件、装依赖、最后拷源码。

flowchart TB subgraph BAD["错误顺序：每次都重装"] B1["COPY . ."] --> B2["RUN 安装依赖"] B2 --> B3["改一行代码
B1 层哈希变化"] B3 --> B4["依赖层缓存全部失效
每次构建都重装"] end subgraph GOOD["正确顺序：只有依赖变了才重装"] G1["COPY 锁文件与 pyproject"] --> G2["RUN 安装依赖
可缓存层"] G2 --> G3["COPY 源码"] G3 --> G4["改代码只重建最后一层"] end
层什么情况下失效该放什么常见错误
基础镜像换 tag 或拉到新的 digest固定到具体版本，如 python:3.12-slim用 latest，某天基础镜像换了 glibc 版本，C 扩展直接跑不起来
系统包安装apt 行有改动只装编译期真正需要的，且留在 builder 阶段把编译工具链装进最终镜像
依赖描述文件拷贝pyproject.toml 或锁文件变化只拷这两个文件连同源码一起拷，缓存等于没有
依赖安装上一层失效时--frozen --no-dev，配合缓存挂载不加 --frozen，构建期解析出与锁文件不同的版本
源码拷贝任何代码改动放在最后一层把 .venv、.git、测试数据一起拷进去（用 .dockerignore 挡掉）
runtime 阶段只从 builder 拷产物虚拟环境目录与源码，非 root 用户在 runtime 阶段又装了一遍依赖，多阶段的收益归零

镜像分层、缓存挂载与 .dockerignore 的完整机制见站内容器与镜像专题，这里只讲与 Python 依赖相关的那几层。

② 原理 · 配置与密钥怎么进程序

搞清这一节能解决的现象是：同一个镜像在 staging 正常、在生产连错库；以及密钥被打进镜像层后，删掉那一行也删不掉历史层里的内容。一条总纲：镜像只包含代码与依赖，环境差异全部从外面注入。同一个 digest 的镜像必须能跑在任何环境，靠注入值区分——这也是回滚能成立的前提。

flowchart TB Q{"这个值是什么性质"} -->|"环境差异 非敏感"| E["环境变量
编排清单里声明"] Q -->|"敏感 密钥 证书"| S{"编排侧支持挂载吗"} Q -->|"所有环境都一样"| CODE["直接写进代码常量
不要伪装成配置"] S -->|"支持"| F["挂成文件
pydantic-settings 的 secrets_dir 读取"] S -->|"不支持"| SE["注入环境变量
字段用 SecretStr 防止被日志打出"] E --> V["进程启动时由 Settings 统一校验"] F --> V SE --> V V -->|"缺字段或类型不对"| FAIL["启动失败 容器起不来
流量不会切过来"] V -->|"通过"| RUN["lifespan 建连接池"] LOCAL[".env 文件
仅本地开发 必须进 gitignore"] --> V
配置来源谁负责注入适合放什么风险与注意
环境变量编排系统 / 启动脚本环境差异项：数据库地址、连接池大小、日志级别会出现在进程环境与部分诊断输出里，敏感值尽量不用它
挂载的密钥文件编排系统的密钥对象口令、私钥、证书轮转由编排侧做；进程若想感知轮转必须重启或自己重读文件
.env 文件开发者本机本地开发的便利值必须进 .gitignore，且不能打进镜像；仓库里只放 .env.example
镜像里的默认值构建时写死只有「所有环境都一样」的值写进镜像的东西改不了也回滚不掉，密钥绝对不能走这条路
远程配置中心运行期拉取需要不重启就生效的开关引入了一个启动期强依赖，必须有本地兜底值与超时
命令行参数启动命令进程形态：端口、worker 数、超时与环境变量并存时要约定谁优先，否则「改了没生效」

配置哪些能热更新、哪些必须重启，属于上线之后的话题，在《Python 服务上生产》；Settings 类本身的写法与校验器在《Python 后端项目的工程骨架》。

② 原理 · 锁文件在服务项目里锚定了什么

搞清这一节能解决的现象是：同一个提交、同一条构建命令，两周后构建出来的镜像行为不一样，而 diff 里找不到任何原因。requirements.txt 里写 fastapi>=0.110 不是锁定，只是约束：上游发新版本，明天装出来的依赖树就变了，而这个变化不在任何提交记录里。

sequenceDiagram participant D as 开发者 participant CI as CI 流水线 participant PY as 包索引 D->>PY: 周一安装，约束写的是大于等于 PY-->>D: 解析到某个版本，本地全绿 D->>CI: 提交代码，没有提交锁文件 Note over PY: 周三上游发布新版本，改了默认行为 CI->>PY: 周四重跑同一条命令 PY-->>CI: 解析到新版本 CI-->>D: 测试失败，diff 里找不到任何原因 Note over D,CI: 变更来自外部时间线
唯一的解法是把解析结果落盘并提交
做法确定性能否防篡改问题
手写 requirements.txt，只写直接依赖加 >=无不能传递依赖完全放任，重建结果不可预测
手写 == 钉住直接依赖部分不能传递依赖仍然漂移；升级要人工逐个改
工具编译出的完整锁文件（含传递依赖）有不能需要「意图文件加锁文件」的双层流程
锁文件加哈希有能内容被改动或索引源被投毒时安装直接失败
锁文件不进版本库等于没有不能最常见的错误：锁文件就是构建输入，必须提交

对一个服务项目来说，锁文件锚定的是「这次发布的镜像里到底装了什么」：出故障时能对照，回滚时能复现，审计时能查。求解器怎么回溯、各工具的锁文件格式差异、以及为什么 uv 快，都在工具链篇，这里不重复。

② 原理 · 本地、CI、生产三套环境的漂移从哪来

搞清这一节能解决的现象是：「我这儿是好的」。三套环境的共同锚点只有锁文件，除此之外的每一处差异都是潜在故障源。

# 1. 谁要求了什么范围（冲突排查的第一步，先把事实查清楚）
uv pip tree
uv pip tree --package pydantic          # 反查：哪些包依赖它

# 2. 看某个已安装包声明的约束
python -c "import importlib.metadata as m; print(m.requires('fastapi'))"

# 3. 让解析器把不兼容链条打出来
uv lock --verbose

# 4. 漂移检测，值得常驻 CI
uv pip check                            # 已装包之间的依赖是否都被满足
uv sync --frozen --dry-run              # 与锁文件有差异就非零退出

# 5. 容器与本地的版本对照（把「我这儿是好的」变成可验证的事实）
uv run python -m pip list --format=freeze > /tmp/local.txt
docker run --rm myapp:dev python -m pip list --format=freeze > /tmp/image.txt
diff /tmp/local.txt /tmp/image.txt

# 不要做的事：
# pip install --no-deps somepkg         # 跳过依赖检查，把 ImportError 推迟到运行时
# pip install --force-reinstall         # 覆盖式安装，制造出解析器不知道的环境
症状真实原因处理顺序
解析器报 no solution两个包的约束不相交升级提出严格约束的那个包 → 固定到双方都接受的中间版本 → 换库
装完能用但运行时 AttributeError有人用 --no-deps 或 --force-reinstall 绕过了检查删环境重建，用 sync 而不是 install
本地正常，容器里 ImportError本地有历史残留包，锁文件里并没有sync 会卸载多余包；删掉 .venv 重建后复测
本地正常，容器里段错误或找不到 so基础镜像的系统库与本地不同，C 扩展 ABI 对不上基础镜像固定到 digest；确认装的是 wheel 而不是现场编译的 sdist
CI 通过，生产镜像里版本不同构建时没加 --frozen，解析出了新版本构建命令一律加 --frozen，并把关键包版本打进启动日志
解析慢到几分钟候选版本回溯爆炸，通常由某个过于宽松的约束触发给关键包加下限约束缩小搜索空间

② 原理 · 供应链：索引源与镜像上的几条防线

搞清这一节能解决的现象是：装了一个名字差一个字母的包，或者某天构建产物里多了不该有的代码。服务项目的依赖清单就是它的攻击面清单。

风险手段说明
依赖里有已知漏洞CI 里跑漏洞扫描并作为门禁把结果卡在合并之前，细节见站内安全专题
包内容被篡改、索引源被投毒锁文件带哈希，安装时校验内容改过就直接安装失败，这是最有效的一道防线
仿冒包名新增依赖时人工确认项目主页与维护者装错一个字母就可能引入恶意代码，这类投毒长期存在
直接安装 git 分支或未发布地址生产构建禁止构建结果取决于别人的分支状态，回滚时复现不出当时的依赖
构建期脚本执行任意代码优先用 wheel 而不是 sdistsdist 安装会执行构建脚本，wheel 只解包
私有源与公共源混用显式指定索引优先级，或把私有包限定到私有源否则公共源上的同名包可能被优先命中，这是依赖混淆攻击的入口

③ 场景 · 不同服务形态该怎么组织

上面的形态覆盖大多数 Web 服务。下表处理不那么标准的情况，同时给出代价。

场景该怎么做为什么代价
单个 Web 服务，纯 Python 依赖本文的默认形态：uv 加分组加多阶段镜像构建快、镜像小、三套环境有唯一锚点几乎没有；这是基准形态
老服务，已有一堆 requirements.txt先引入 pip-compile 生成锁文件，产物仍是 requirements，形态不变迁移成本最低，先把「不确定性」这一项解决掉少了项目模式的便利；工具差异见工具链篇
多个服务共用一个内部库内部库单独发布到私有源并钉版本，不要用路径依赖或 git 分支路径与分支依赖让构建结果取决于别人的工作副本要维护发布流程；改一处要发一次版
依赖需要编译（图像、加解密、科学计算）多阶段的 builder 里装工具链，最终镜像只拷产物；优先选有 wheel 的版本现场编译让构建时间与失败率都不可控基础镜像与目标平台绑得更紧，跨架构要分别构建
需要 GPU 或特定系统级二进制由基础镜像提供这些二进制，Python 侧仍只管包把两类依赖交给各自擅长的层，避免一个工具管所有事基础镜像体积大，拉取与扩容变慢
生产网络无法访问公共索引CI 里构建时下载并归档 wheel，生产只从内部源安装安装过程不能依赖外网可达性需要维护内部源与同步流程
需要快速回滚到上一个版本镜像按不可变 tag 或 digest 发布，锁文件与 tag 一一对应回滚的是「代码加依赖」整体，只回代码不回依赖等于换了一个没测过的组合镜像仓库体积增长，需要保留策略
依赖升级节奏要可控定期只升安全相关的包，功能升级单独提交并跑全量回归把「必须升」与「想要升」分开，风险可归因需要一个固定的维护窗口

反过来看就是这张反模式表：

反模式后果正确做法
不锁版本，只写 >=重建结果不确定，故障来源查不到意图文件加锁文件双层，锁文件进版本库
手工维护 requirements.txt传递依赖漏写或版本对不上用工具生成，人只改意图文件
生产镜像装开发依赖体积大出几百 MB，攻击面无谓扩大分组，构建时 --no-dev
密钥写进镜像或提交进仓库删一行也删不掉历史层与历史提交，只能轮转运行期注入，字段用 SecretStr
容器里 pip install 不加 --no-cache-dirwheel 缓存固化进镜像层，白占几十到几百 MB加上它，或用 uv 配合构建缓存挂载
COPY . . 写在装依赖之前每次改代码都重装全部依赖先拷锁文件，最后拷源码
用 pip install 而不是 sync环境里残留已被移除的包，与锁文件不一致uv sync 或 uv pip sync，多余包会被卸载
把本地 .venv 一起 COPY 进镜像里面的路径与二进制属于宿主机，跨平台直接不可用写进 .dockerignore，镜像里重新装

最容易踩的坑

❌
避坑清单
  • 锁文件不进版本库：它就是构建输入，不提交等于没锁，团队每个人装出来的环境都不同。
  • 镜像构建不加 --frozen：构建期悄悄解析出比锁文件更新的版本，镜像与锁文件从此对不上。
  • 用 pip install -r 代替 sync：只新增不卸载，环境里长期留着已经从清单里删掉的包。
  • COPY . . 放在装依赖之前：每次改一行代码都重装全部依赖，CI 时间成倍增长。
  • 把 .venv 一起 COPY 进镜像：里面的路径和二进制是宿主机的，跨平台直接不可用，记得写进 .dockerignore。
  • 密钥进了镜像层或 pyproject：删掉那一行也删不掉历史层，唯一的补救是轮转密钥。
  • .env 被打进镜像或提交进仓库：本地便利换来密钥泄露，仓库里只该有 .env.example。
  • 生产镜像里带着 pytest、mypy、编译工具链：体积与攻击面都在无谓膨胀，还可能被意外导入。
  • 基础镜像用 latest：某天系统库变化，C 扩展的 ABI 对不上，同一个提交突然构建不出可用镜像。
  • 用 --no-deps 或 --force-reinstall 硬压冲突：安装成功了，ImportError 或 AttributeError 推迟到运行时爆。
  • 直接在生产构建里装 git 分支：构建结果取决于别人的分支状态，回滚时根本复现不出当时的依赖。
  • 升级依赖时一把 --upgrade 全升：几十个包同时变化，出问题无法二分定位；按包逐个升并让 diff 进评审。
  • 忽略哈希锁定：索引源被投毒或包被重新发布时没有任何拦截手段。
  • 私有源与公共源混用却不设优先级：公共源上的同名包可能被优先命中，这是依赖混淆攻击的入口。
  • 容器里 pip install 忘加 --no-cache-dir：wheel 缓存被固化进镜像层，白白几十到几百 MB。
