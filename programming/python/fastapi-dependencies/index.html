依赖与环境管理：从 pip 到 uv

Python 的依赖管理有一堆工具，但真正要解决的问题只有两个：项目之间不要互相污染，以及同一份代码在任何时间任何机器上装出完全一样的依赖树。这篇按这两个问题拆开讲清楚每种工具解决到哪一层，为什么锁文件不是可选项，以及 2026 年该用什么。

问题的本质：全局 site-packages

Python 解释器默认把包装进全局 site-packages。两个项目一个要 pydantic 1.x 一个要 2.x，就只能有一个赢——这是隔离需求的全部来源。四种隔离手段的区别在于隔离到哪一层。

uv 管理的环境Python 包 + 解释器（可代下载）能，uv python install几 MB，毫秒到秒级开发与 CI 的推荐组合
⚠️
conda 和 pip 混装是长期麻烦的来源

conda 有自己的包元数据，pip 装的东西它不认。同一个包被两边各装一次，最后加载到哪一份取决于路径顺序，表现为「明明装了却 import 到旧版本」。规则是：能用 conda 装的就全用 conda，确实只有 PyPI 才有的包最后统一用 pip 装，且记录在案。

锁文件为什么必需

requirements.txt 里写 fastapi>=0.110 不是锁定，只是约束。上游发新版本，明天装出来的依赖树就变了，而这个变化不在任何提交记录里。于是有了经典场景：昨天能装今天报错、本地正常 CI 失败、同一个镜像 tag 重建后行为不同。

sequenceDiagram participant D as 开发者 participant CI as CI 流水线 participant PY as PyPI D->>PY: 周一 pip install，约束写的是大于等于 PY-->>D: 解析到 1.4.0，本地全绿 D->>CI: 提交代码，没有提交锁文件 Note over PY: 周三上游发布 1.5.0，改了默认行为 CI->>PY: 周四重跑同一条命令 PY-->>CI: 解析到 1.5.0 CI-->>D: 测试失败，diff 里找不到任何原因 Note over D,CI: 变更来自外部时间线
唯一的解法是把解析结果落盘成锁文件
做法确定性能否防篡改问题
手写 requirements.txt，只写直接依赖 + >=无不能传递依赖完全放任，重建结果不可预测
手写 == 钉住直接依赖部分不能传递依赖仍然漂移；升级要人工逐个改
工具编译出的完整锁文件（含传递依赖）有不能需要一个「意图文件 + 锁文件」的双层流程
锁文件 + --hash有能内容被改动或镜像源被投毒时安装直接失败
锁文件不进版本库等于没有不能最常见的错误：锁文件必须提交，它就是构建输入

还有一件历史包袱值得知道：pip 直到 20.3 才有真正的回溯式依赖解析器。在那之前它按顺序安装、后装的覆盖先装的，同一份 requirements 里两个包要求冲突版本时不报错而是静默装出一个坏掉的环境。现在的 pip 会报冲突，但它仍然没有内置锁文件机制。

uv 的完整工作流与依赖分组

# ---------- 本地开发 ----------
# 装 uv（独立二进制，不依赖任何 Python 环境）
curl -LsSf https://astral.sh/uv/install.sh | sh

# 让 uv 直接管解释器版本，pyenv 可以不要了
uv python install 3.12

# 创建虚拟环境（默认 .venv，秒级完成）
uv venv --python 3.12

# 方式一：项目模式，依赖写在 pyproject.toml，uv 维护 uv.lock
uv add fastapi "uvicorn[standard]" pydantic-settings
uv add --dev pytest ruff mypy          # 进 dev 分组，生产镜像不装
uv lock                                 # 解析全部传递依赖，写入 uv.lock
uv sync                                 # 让环境与锁文件完全一致（多余的包会被卸载）
uv run uvicorn app.main:app --reload    # 自动使用项目环境，不用手动 activate

# 方式二：兼容模式，保留 requirements 流程
uv pip compile pyproject.toml -o requirements.txt --generate-hashes
uv pip sync requirements.txt            # sync 而非 install：会卸载不在清单里的包

# ---------- CI ----------
# --frozen 表示不允许更新锁文件：锁文件与 pyproject 不一致就直接失败，
# 避免「CI 悄悄解析出了新版本」
uv sync --frozen --no-dev
uv run pytest

# 缓存目录跨任务复用，命中时安装几乎瞬时完成
export UV_CACHE_DIR=/cache/uv
uv cache prune --ci                     # 只保留可复用的部分，控制缓存体积

# ---------- 升级依赖：一个显式动作，进 code review ----------
uv lock --upgrade-package fastapi       # 只升这一个，diff 清晰
uv lock --upgrade                       # 全量升，需要完整回归
分组放什么安装位置
运行时依赖（dependencies）框架、驱动、客户端库生产镜像、CI、本地
开发依赖（--dev / dev 组）ruff、mypy、pytest、调试工具本地与 CI，不进生产镜像
测试依赖pytest 插件、假数据、httpx 测试客户端CI；与 dev 合并也可以
可选依赖（extras）可插拔能力，如某个云厂商 SDK按部署形态选装
构建期依赖编译工具链、头文件多阶段构建的第一阶段，不进最终镜像

传递依赖与版本冲突

冲突的本质是两个包对同一个第三方库要求了不相交的版本范围。这种情况没有技术解法——只能降级、替换，或者等上游放宽约束。先把事实查清楚，再决定。

# 1. 看清依赖树：谁要求了什么范围
uv pip tree                      # 或 pipdeptree --warn conflict
uv pip tree --package pydantic   # 反查：哪些包依赖它

# 2. 看某个已安装包声明的约束
uv pip show --files pydantic
python -c "import importlib.metadata as m; print(m.requires('fastapi'))"

# 3. 让解析器把冲突原因打出来（uv 的报错会列出完整的不兼容链条）
uv lock --verbose

# 4. 验证环境是否与锁文件一致（漂移检测，CI 里值得常驻）
uv pip check                     # 检查已装包之间的依赖是否被满足
uv sync --frozen --dry-run       # 有差异就非零退出

# 不要做的事：
# pip install --no-deps somepkg   # 跳过依赖检查，把 ImportError 推迟到运行时
# pip install --force-reinstall   # 覆盖式安装，制造出解析器不知道的环境
症状真实原因处理顺序
解析器报 no solution两个包的约束不相交升级提出严格约束的那个包 → 固定到双方都接受的中间版本 → 换库
装完能用但运行时 AttributeError有人用 --no-deps 或 --force-reinstall 绕过了检查重建环境，用 uv pip sync 而不是 install
本地正常，容器里 ImportError本地环境有历史残留包，锁文件里并没有sync 会卸载多余包；删掉 .venv 重建验证
解析慢到几分钟候选版本回溯爆炸，通常由某个宽松约束触发给关键包加下限约束缩小搜索空间
同名包装了两份conda 与 pip 混装统一渠道，重建环境

供应链安全

风险手段说明
依赖里有已知漏洞CI 里跑 pip-audit 或 uv pip audit 类工具把结果作为门禁，细节见站内安全专题
包内容被篡改 / 镜像源被投毒锁文件带 --generate-hashes，安装时校验哈希不匹配直接失败，这是最有效的一道防线
仿冒包名（typosquatting）新增依赖时人工确认项目主页与维护者装错一个字母就可能引入恶意代码
直接安装 git 分支或未发布地址生产构建禁止构建结果取决于别人的分支状态，且无法审计
构建期脚本执行任意代码优先用 wheel 而不是 sdistsdist 安装会执行构建脚本，wheel 只解包
私有源与公共源混用显式指定索引优先级否则可能被公共源上的同名包抢先命中（依赖混淆攻击）

Docker 里的依赖层缓存

镜像构建慢，八成是因为 COPY . . 写在了装依赖之前——任何一行代码改动都会让依赖层缓存失效，每次都重装一遍。顺序必须是：先拷锁文件、装依赖、最后拷源码。

可缓存层"] G2 --> G3["COPY 源码"] G3 --> G4["改代码只重建最后一层
构建数秒"] end 
# 多阶段构建：编译工具链留在第一阶段，不进最终镜像
FROM python:3.12-slim AS builder

# uv 作为独立二进制拷进来，不用 pip 装
COPY --from=ghcr.io/astral-sh/uv:latest /uv /usr/local/bin/uv

WORKDIR /app
ENV UV_COMPILE_BYTECODE=1 \
    UV_LINK_MODE=copy

# 关键：只拷依赖描述文件，这一层只在依赖变化时失效
COPY pyproject.toml uv.lock ./
# --frozen 保证严格按锁文件装；--no-dev 把测试与 lint 工具排除在镜像外
RUN --mount=type=cache,target=/root/.cache/uv \
    uv sync --frozen --no-dev --no-install-project

# 源码最后拷，改代码不会触发重装依赖
COPY src ./src
RUN --mount=type=cache,target=/root/.cache/uv \
    uv sync --frozen --no-dev

FROM python:3.12-slim AS runtime

# 运行阶段不装任何构建工具
ENV PYTHONUNBUFFERED=1 \
    PYTHONDONTWRITEBYTECODE=1 \
    PATH="/app/.venv/bin:$PATH"

# 非 root 运行
RUN useradd --create-home --uid 10001 appuser
WORKDIR /app
COPY --from=builder --chown=appuser:appuser /app/.venv /app/.venv
COPY --from=builder --chown=appuser:appuser /app/src /app/src
USER appuser

EXPOSE 8000
CMD ["uvicorn", "myapp.main:app", "--host", "0.0.0.0", "--port", "8000"]

反模式后果正确做法
不锁版本，只写 >=重建结果不确定，故障来源查不到意图文件 + 锁文件双层，锁文件进版本库

最容易踩的坑

❌
避坑清单
  • 锁文件不进版本库：它就是构建输入，不提交等于没锁，团队每个人装出来的环境都不同。
  • 用 pip install -r 代替 sync：只会新增不会卸载，环境里长期留着已经从清单删掉的包。
  • 直接在生产构建里装 git 分支：构建结果取决于别人的分支状态，回滚时根本复现不出当时的依赖。
  • 用 --no-deps 或 --force-reinstall 硬压冲突：安装成功了，ImportError 或 AttributeError 推迟到运行时爆。
  • 容器里 pip install 忘加 --no-cache-dir：wheel 缓存被固化进镜像层，白白几十到几百 MB。
  • COPY . . 放在装依赖之前：每次改一行代码都重装全部依赖，CI 时间成倍增长。
  • conda 环境里用 pip 装同名包：两套元数据互不认账，最终加载哪一份取决于路径顺序。
  • 生产镜像里带着 pytest、mypy、编译工具链：体积与攻击面都在无谓膨胀。
  • 把 .venv 一起 COPY 进镜像：里面的路径和二进制是宿主机的，跨平台直接不可用，记得写进 .dockerignore。
  • 升级依赖时一把 --upgrade 全升：几十个包同时变化，出问题无法二分定位；按包逐个升并让 diff 进评审。
  • 忽略哈希锁定：镜像源被投毒或包被重新发布时没有任何拦截手段。
  • 私有源与公共源混用却不设优先级：公共源上的同名包可能被优先命中，这是依赖混淆攻击的入口。
