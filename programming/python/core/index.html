Python 运行时机制：对象模型、内存与 GIL

🏷️ Python

写业务代码不需要知道 CPython 怎么实现的，但排查内存只涨不降、解释「为什么这个类占了 200MB」、判断某段热路径还能不能优化，就必须知道。这篇只讲运行时层面的机制：对象怎么布局、内存怎么回收、属性怎么查找、哪些写法的开销来自实现而不是算法。GIL 对并发模型的影响见Python 做后端的适用边界与运行时约束，这里只讲它在对象层留下的痕迹。

💡
这篇怎么读
  • ① 用法：出现内存或性能问题时的动手顺序——先按现象分型，再用 Pss 确认进程真实占用、用 tracemalloc 两次快照定位到具体行、用 GC 统计与引用查询判断是循环引用还是真被持有，外加一张工具速查表（看什么、开销多大、有什么坑）。

  • ③ 场景：从症状到处置的决策矩阵、七类反模式，以及哪些问题不该在这一层解决。

① 用法 · 内存与性能问题的动手顺序

内存问题最容易走弯路的地方是顺序错了：还没确认「是 Python 堆在涨」就开始翻业务代码。下面这张表先做分型，右列是这类现象应该先做的那一件事。

现象大概率原因先做什么
RSS 单调上涨，重启才回落对象被全局容器、模块级缓存或闭包持有tracemalloc 两次快照按行比对，增量随轮次线性增长的那行就是源头
RSS 高但稳定不涨容量本身估错了，不是泄漏递归统计缓存的真实占用（sys.getsizeof 不递归），再乘 worker 数看总量
周期性的 P99 毛刺第 2 代 GC 全量扫描，或所有 worker 同时重启先看 gc.get_stats() 的各代收集次数，再查 max_requests 有没有配 jitter
多 worker 后总内存远超单进程估算preload 的共享页被引用计数与 GC 标记写花fork 前 gc.collect() 加 gc.freeze()；用 smaps_rollup 的 Pss 而不是 RSS 求和来评估
重启后内存回落，几小时后又满缓存没有上限给 lru_cache 设 maxsize，或换带 TTL 与容量上限的缓存
对象数不涨但内存在涨大块 bytes/str 缓冲，或 C 扩展自己管理的内存tracemalloc 看不到 C 层分配，改看进程级 Pss 与该库自身的统计接口
CPU 高但逻辑很简单热路径上的属性与全局查找、字符串拼接、集合选错先用 cProfile 或 py-spy 定位函数，再按原理层的写法对照表改

分型之后按下面的顺序动手。四步是有依赖关系的，跳步会得到误导性的结论：

# mem_probe.py —— 按顺序做，前一步的结论不成立就别做下一步
import gc
import sys
import tracemalloc
from collections import Counter


# 第 1 步：确认进程真实占用。ps 的 RSS 会把共享页重复计入，多 worker 下高估明显
def pss_mb() -> float:
    for line in open("/proc/self/smaps_rollup"):
        if line.startswith("Pss:"):
            return int(line.split()[1]) / 1024   # 这一列单位是 KB
    return -1.0


# 第 2 步：谁在涨。两次直方图相减只看增量，绝对值意义不大
def type_histogram(top: int = 15):
    # 只统计被 GC 追踪的容器类对象；百万对象量级这次遍历本身就会卡住几百毫秒
    return Counter(type(o).__qualname__ for o in gc.get_objects()).most_common(top)


# 第 3 步：涨在哪一行。tracemalloc 必须在分配发生之前启动
tracemalloc.start(25)              # 25 是保留栈帧数，太小只能看到框架里的调用点
base = tracemalloc.take_snapshot()
run_one_round_of_business()        # 跑一轮完整业务，让该建的缓存都建好
after = tracemalloc.take_snapshot()
for stat in after.compare_to(base, "lineno")[:10]:
    print(stat)                    # size_diff 为正且随轮次线性增长的那行才是泄漏点

# 第 4 步：是循环引用撑着，还是真有人持有引用
print("各代计数:", gc.get_count(), "阈值:", gc.get_threshold())
print("本次回收不可达对象:", gc.collect())   # 数量大说明循环引用多，考虑改弱引用
suspect = find_suspect()
print("引用计数:", sys.getrefcount(suspect) - 1)        # 减 1 是 getrefcount 自己的临时引用
print("谁引用了它:", [type(r).__qualname__ for r in gc.get_referrers(suspect)][:5])

# 注意：以上除第 1 步之外都有明显开销，只在排查时开；gc.collect() 绝不能放在请求路径里

② 原理 · 一切皆对象，代价写在对象头里

搞清这一节能解决的现象是：容量规划按元素个数乘字段长度算，结果实际占用是估算的好几倍。Python 没有「基本类型」。整数、布尔、函数、类、模块全部是堆上的对象，每个对象至少带 16 字节对象头：8 字节引用计数（ob_refcnt）加 8 字节类型指针（ob_type）。变长对象（int、str、list、tuple）再加一个 8 字节的长度字段。

对象sys.getsizeof（64 位 CPython 3.12）要注意的点
object()16 字节纯对象头，这是理论下限
0 / 25528 字节小整数有缓存池，不重复创建
10 ** 3044 字节大整数按 30 位一段扩展，没有溢出
1.524 字节float 是定长对象
"" / "abc"49 / 52 字节纯 ASCII 每字符 1 字节，含非 ASCII 会换成 2 或 4 字节编码
[] / 100 万元素 list56 字节 / 约 8MB只算指针数组，元素对象另算；append 扩容按约 1.125 倍预留
{} / 100 万条 dict64 字节 / 约 40MB同样不含 key 与 value 对象
普通类实例（1 个属性）约 150 字节（实例加 __dict__）加 __slots__ 后可降到 50 字节量级

所以「100 万条记录缓存在 dict 里」的真实成本要自己加：dict 本体约 40MB，100 万个 str 类型的 key 按平均 20 字符算约 69MB，value 如果是带三个属性的普通对象，每个约 250 字节又是 250MB。总量轻松到 350MB 以上，而 sys.getsizeof(cache) 只会告诉你 40MB——它不递归，这是内存评估最常见的误读。

import sys
from itertools import chain
from collections import deque

def deep_size(obj):
    """递归统计真实占用，处理共享对象与循环引用"""
    seen = set()
    total = 0
    queue = deque([obj])
    while queue:
        o = queue.popleft()
        if id(o) in seen:          # 同一对象被多处引用只算一次
            continue
        seen.add(id(o))
        total += sys.getsizeof(o)
        if isinstance(o, dict):
            queue.extend(chain(o.keys(), o.values()))
        elif isinstance(o, (list, tuple, set, frozenset)):
            queue.extend(o)
        elif hasattr(o, "__dict__"):
            queue.append(o.__dict__)
        elif hasattr(o, "__slots__"):
            queue.extend(getattr(o, n) for n in o.__slots__ if hasattr(o, n))
    return total

cache = {f"user:{i}": {"id": i, "name": "n" * 12} for i in range(100_000)}
print("getsizeof 只看容器本体:", sys.getsizeof(cache) / 1024 / 1024, "MB")
print("递归统计真实占用:", deep_size(cache) / 1024 / 1024, "MB")

② 原理 · 引用计数与分代 GC 的分工

搞清这一节能解决的现象是：把所有内存问题都归给「Python 的 GC 慢」，或者在请求路径上调 gc.collect() 换来几百毫秒停顿。两套机制职责完全不同。引用计数是主力：计数归零立即释放，没有停顿，del 之后内存就回到分配器。它唯一处理不了的是循环引用——互相引用的两个对象计数永远大于零。分代 GC 就只为这一件事存在。

stateDiagram-v2 [*] --> Gen0: 对象创建，登记进第 0 代 Gen0 --> Freed: 引用计数归零，立即释放 Gen0 --> Gen1: 第 0 代扫描后存活，晋升 note right of Gen1 阈值默认 700 10 10 第一个数字是分配净增量 后两个是子代触发次数 end note Gen1 --> Gen2: 第 1 代扫描 10 次后晋升 Gen2 --> Gen2: 全量扫描，代价与存活对象总数成正比 Gen2 --> Freed: 判定为不可达的循环组 Gen2 --> Frozen: 调用 gc.freeze 后移出追踪 Frozen --> [*]: 不再被任何一代扫描
机制触发时机能解决代价
引用计数每次赋值、传参、作用域退出绝大多数对象的即时回收每次操作都要改对象头，也是 GIL 存在的根源之一
第 0 代扫描分配减释放的净增量超过 700刚产生的短命循环引用微秒级，通常可忽略
第 1 代扫描第 0 代触发 10 次中等寿命的循环与该代对象数成正比
第 2 代 / gc.collect()第 1 代触发 10 次，或手动调用所有循环引用全量遍历所有被追踪对象，百万对象量级可达数百毫秒，会打穿 P99
gc.freeze()手动，通常在 fork 之前把长生命周期对象移出追踪被冻结对象里的循环引用不再回收，需确认它们本就常驻

有两个调优点在生产上是真有用的。第一，如果服务会预加载大量常驻对象（配置、词典、模型、路由表），在 fork 出 worker 之前调 gc.freeze()：否则子进程的 GC 遍历会去修改这些对象头里的标记位，把本来父子共享的内存页触发写时复制，白白让每个 worker 各自复制一份。第二，如果服务是「大量长生命周期对象 + 高频临时对象」的形态，调大阈值能减少无效的全量扫描。

import gc

# 启动阶段：加载配置、模型、路由表等常驻对象
load_everything()

# 1) 先做一次彻底回收，把启动期的垃圾清干净
gc.collect()
# 2) 把存活对象全部移出 GC 追踪，fork 后子进程的 GC 不会再扫它们，
#    避免只读遍历修改 GC 标记位触发写时复制
gc.freeze()

# 3) 阈值调整：默认 (700, 10, 10)。长驻对象多、临时对象也多的服务，
#    把第 0 代阈值抬高能显著减少全量扫描次数；代价是内存峰值略高
gc.set_threshold(50_000, 20, 20)

print(gc.get_threshold(), gc.get_count())   # 观察各代当前计数

# 排查循环引用时才开，平时别开：DEBUG_LEAK 会把不可回收对象全部留在 gc.garbage
# gc.set_debug(gc.DEBUG_SAVEALL)
💡
3.12 的不朽对象顺带帮了多进程

3.12 起 None、True、False 与小整数等单例成为「不朽对象」（immortal），它们的引用计数不再随使用变动。这条改动的直接收益就在多进程场景：以前哪怕只是读一下 None，也会改动对象头触发写时复制，现在不会了。

② 原理 · __slots__：把属性字典换成固定槽位

搞清这一节能解决的现象是：百万级实例的服务多出几百 MB 常驻内存。普通实例的属性存在实例自带的 __dict__ 里，灵活但每个实例都要多付一个字典。声明 __slots__ 后，解释器在类型对象上为每个属性分配固定偏移的槽位（底层是数据描述符），实例不再创建字典。

形态单实例内存量级（3 个属性）可动态加属性限制
普通类约 250 字节可以无，最灵活
带 __slots__ 的类约 70 字节不可以多继承时父类均有非空 slots 会冲突；默认失去弱引用，需显式加 __weakref__
@dataclass（默认）与普通类相同可以3.10 起可加 slots=True 直接生成 slots 版本
NamedTuple约 80 字节不可以不可变，字段访问按索引，序列化友好
裸 dict约 230 字节可以没有类型约束、没有属性补全、拼错 key 不报错
pydantic 模型最大（带校验元数据）看配置换来的是运行时校验，用在边界而不是内部热路径

判断标准很简单：实例数量到百万级才值得上 __slots__，几千个对象省下来的内存不值得牺牲灵活性。

② 原理 · 属性查找顺序：为什么 property 拦得住赋值

搞清这一节能解决的现象是「明明实例里有这个属性，怎么走进了 property」以及「为什么 __getattr__ 里打印日志会递归爆栈」。obj.x 不是一次字典查找，而是一条有优先级的链。

钩子调用时机典型用途风险
__getattribute__每次属性访问都调用全面拦截，如代理对象开销压在所有访问上；内部访问自身属性必须走 object.__getattribute__
__getattr__仅在常规查找失败后调用懒加载、动态字段、配置兜底访问自身未定义属性会递归；会把拼写错误变成静默默认值

② 原理 · 装饰器与闭包：执行时机比语法更容易出错

搞清这一节能解决的现象是：测试无法隔离、traceback 里全是 wrapper、循环里注册的回调全部拿到最后一个值。装饰器的本质就是 f = deco(f)，关键在于它在模块导入时就执行。所以在装饰器里连数据库、读远程配置、注册全局状态，会让导入顺序变成隐式依赖，测试时也无法绕开。

import functools
import logging
import time

logger = logging.getLogger(__name__)

def timed(threshold_ms: float = 100.0):
    """超过阈值才打日志，避免热路径被日志淹没"""
    def decorator(func):
        @functools.wraps(func)          # 不加这行会丢掉 __name__ __doc__ __module__
        def wrapper(*args, **kwargs):   # 以及类型注解，traceback 和 API 文档都会变成 wrapper
            start = time.perf_counter()
            try:
                return func(*args, **kwargs)
            finally:
                cost = (time.perf_counter() - start) * 1000
                if cost >= threshold_ms:
                    logger.warning("slow_call", extra={"func": func.__qualname__, "cost_ms": round(cost, 2)})
        return wrapper
    return decorator

@timed(threshold_ms=50)
def query_orders(uid: int) -> list[dict]:
    ...

# 闭包的经典陷阱：延迟绑定
fns = [lambda: i for i in range(3)]
print([f() for f in fns])            # [2, 2, 2]，闭包捕获变量本身而不是当时的值
fns = [lambda i=i: i for i in range(3)]
print([f() for f in fns])            # [0, 1, 2]，用默认参数在定义时求值
陷阱表现修法
不用 functools.wraps日志里全是 wrapper，FastAPI 的签名推导与文档生成直接失效固定加 @functools.wraps(func)
可变默认参数默认的 [] 或 {} 在函数对象上只创建一次，跨调用累积默认写 None，函数体内初始化
闭包延迟绑定循环里创建的回调全部拿到最后一次的值用默认参数或 functools.partial 在定义时固化
装饰器里做重初始化导入即连数据库，测试无法隔离，导入顺序变成隐式依赖把副作用推迟到首次调用或应用启动钩子里
装饰异步函数时写成同步 wrapper返回协程对象而不是结果，且从不 await为 async def 写 async 版 wrapper，或用 inspect.iscoroutinefunction 分支

② 原理 · 鸭子类型与 Protocol：比 ABC 更轻的约束

搞清这一节能解决的现象是：接口约定只能在跑到那一行时才发现没实现。Python 的接口一直靠鸭子类型，typing.Protocol 给了结构化类型：不需要继承，只要方法签名匹配就算实现，检查交给 mypy 在 CI 里做。

方案约束时机侵入性适用
纯鸭子类型运行时报 AttributeError零脚本、内部小范围
Protocol静态检查（mypy）零，实现方不需要感知为第三方类型定接口、解耦模块边界
abc.ABC实例化时报 TypeError必须继承要强制子类实现、需要共享基类逻辑
runtime_checkable 的 Protocolisinstance 可用，但只查方法名不查签名零需要运行时分支判断时，注意它给的保证很弱

② 原理 · CPython 的性能特征：开销来自实现

搞清这一节能解决的现象是：算法复杂度看着没问题，实测却慢几倍。同样的复杂度，Python 的常数因子来自三件事：每个操作都要经过对象头与类型检查、属性查找是多次字典查找、函数调用要建栈帧。所以优化方向不是「少写几行」，而是把解释器的重复工作搬出热路径。

写法相对开销原因该不该改
循环里 obj.method(x)基准每轮都做一次属性查找加绑定方法创建热路径值得提前 m = obj.method 缓存到局部变量
访问局部变量 vs 全局变量局部快约 1.5~2 倍局部变量按数组下标取，全局要查模块字典内层循环值得把全局函数绑成局部名
列表推导 vs append 循环推导快约 1.3~2 倍推导用专用字节码，省掉每轮的方法调用可读性不降就改
循环内 s += part 拼字符串可能退化为 O(n²)str 不可变，每次都要新分配并复制必须改成收集列表再 "".join
in 判断用 list vs setO(n) vs O(1)list 线性扫描，set 走哈希集合超过几十个元素就该换 set
手写循环 vs sum / map 等内置内置快数倍循环体在 C 层，不回到字节码能用内置就用
升级到 3.11 及以上整体快 10%~60%自适应专用化解释器（PEP 659）与零开销异常处理改都不用改，升级即得

③ 场景 · 症状到处置的决策矩阵

前面的机制是「点」，这里收成「面」：按真实场景给方案、给理由、也给代价。

场景该怎么做为什么代价
进程内缓存百万级记录换 __slots__ / NamedTuple，或改列式存储（array、numpy、Arrow）对象头与实例字典是主要开销，元素个数乘字段长度的估算必然偏低失去动态属性与部分灵活性；列式结构要改访问代码
预加载大模型或词典后 fork workergc.collect() 然后 gc.freeze()，再 fork避免子进程 GC 遍历改写对象头，把共享页变成私有页被冻结对象里的循环引用不再回收，必须确认它们本就常驻
大量长驻对象叠加高频临时对象抬高第 0 代阈值（如 gc.set_threshold(50_000, 20, 20)）减少无效的代际扫描次数内存峰值略高；阈值要按实测调，不是越大越好
P99 出现规律性毛刺用 gc.callbacks 打点把 GC 停顿变成指标，不要在请求里 collect()全量扫描的代价与存活对象总数成正比，百万量级可达数百毫秒要加一组指标与看板
热路径要压常数先 profile 定位，再按写法对照表改（局部绑定、join、set、内置函数）常数开销来自解释器的重复工作，不是算法问题可读性下降，收益有上限；真不够就下沉 C 扩展或换语言
入口要做数据校验pydantic 只用在边界，内部传 slots 化的 dataclass校验元数据不该进热路径多一层模型转换，要写映射代码
要求 P99 个位数毫秒不在 Python 里抠，拆出这一段换语言或下沉扩展解释器常数摆在那里，优化写法改变不了量级跨语言协作与部署成本，判断依据见适用边界篇
只想「省内存」就调 gc.collect()先确认是否真有循环引用（看 collect() 返回值）引用计数已经回收了绝大多数对象，collect 只处理循环误用的代价是纯粹的停顿，没有收益

③ 场景 · 反模式与不适用边界

反模式后果正确做法
可变默认参数状态在调用间泄漏，表现为「第二次请求带上了第一次的数据」默认 None，体内初始化
循环里用 += 拼字符串或列表相加复杂度退化，数据量一大直接超时list.append 加 join，或 extend
用类当命名空间却不加 __slots__百万实例多出几百 MB 常驻内存加 __slots__，或换 NamedTuple
滥用元类做注册导入顺序决定行为，调试链路极长用 __init_subclass__ 或显式注册函数
拿 sys.getsizeof 评估缓存内存低估一个数量级，容量规划全错递归统计，或直接看 RSS 与 Pss 变化
在请求路径上调 gc.collect()百万对象时一次全量扫描几百毫秒，P99 被打穿只在启动或空闲期调，平时调阈值
用 is 比较数值或字符串小数据侥幸正确，大数据随机出错值比较用 ==，is 只对 None 等单例

不适用边界：字节码、指令分发、专用化解释器这一层在CPython 实现细节；语义层面的坑（作用域、可变默认参数、相等与哈希）系统整理在Python 的语义陷阱清单；GIL 与三条并发路线在Python 并发的三条路线与选择；worker 数、preload、多进程内存评估属于部署层，在Python Web 服务的部署形态；进程被 OOM kill 之后的取证与容器内存约束见站内后端性能优化专题。

最容易踩的坑

❌
避坑清单
  • 把 sys.getsizeof 当真实占用：它不递归，一个 100 万条的 dict 只报约 40MB，实际可能超过 300MB。
  • 用 ps 的 RSS 之和评估多 worker 内存：共享页被重复计入，要看 smaps_rollup 的 Pss。
  • 函数签名里写 def f(items=[])：默认对象绑在函数上只创建一次，跨请求累积数据，这是最经典的「幽灵脏数据」。
  • 用 is 判断相等：负 5 到 256 的小整数和短字符串有缓存，小数据测试通过，上线换成大值就随机失败。
  • copy.copy 当深拷贝用：浅拷贝只复制最外层，嵌套的 list 与 dict 仍然共享，改子元素会串。
  • 预加载大对象后直接 fork 而不 gc.freeze()：子进程 GC 遍历会修改对象头触发写时复制，每个 worker 各复制一份常驻内存。
  • 在请求处理里调 gc.collect() 想「省内存」：换来的是几百毫秒停顿，而且引用计数本来就已经回收了绝大多数对象。
  • tracemalloc 在业务跑起来之后才 start：之前的分配一个都看不到，结论会指向错误的代码行。
  • gc.set_debug(gc.DEBUG_SAVEALL) 忘记关：所有不可回收对象被永久留在 gc.garbage 里，从排查手段变成内存泄漏源。
  • 写装饰器忘了 functools.wraps：traceback 里全是 wrapper，FastAPI 依赖签名推导的功能直接失效。
  • 在 __getattr__ 里访问自身属性做日志或兜底：一路递归到 RecursionError，而且栈信息几乎无法阅读。
  • 给已有大量实例的类加 property 做计算属性：每次访问变成函数调用，热路径上的开销可能翻数倍。
  • 以为 runtime_checkable 的 Protocol 能保证签名正确：isinstance 只检查方法名存在，参数对不上照样在调用时炸。
  • 多继承时给两个父类都写非空 __slots__：直接 TypeError，而且报错信息不会告诉你是布局冲突。
