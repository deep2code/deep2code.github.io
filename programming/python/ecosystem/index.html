🏷️ Python

先把「升级会坏在哪」分层

「该用哪个 Python」这个问题之所以难答，是因为它其实是四个不同的问题被揉在一起：语言语义变了什么、标准库少了什么、C 扩展的二进制接口能不能对上、以及构建变体（是否 free-threaded）是否改变了运行时假设。这四层的升级代价差了一两个数量级：语法层几乎总是向后兼容，而 ABI 层的一次变化能把整个升级窗口推后半年。

实践中的顺序也应该照这个分层来：先盘点依赖在目标版本上有没有轮子（第 4 层），再验证带原生扩展的依赖（第 3 层），最后才是跑测试看标准库与语义（第 1、2 层）。反过来做的团队通常在测试全绿之后才发现某个关键依赖根本装不上。

3.11 到 3.14：收益在哪，破坏在哪

3.11 是这一轮性能工作的起点，核心是自适应专门化解释器加上零开销异常处理与更廉价的调用帧，官方 pyperformance 口径给出的是平均约 1.25 倍。这个数字要会读：它衡量的是解释器执行纯 Python 字节码的速度，而典型 Web 服务的时间大量花在网络等待、序列化和 C 扩展里，所以真实服务的端到端收益通常远小于基准套件（解释器内部机制详见站内《CPython 内部原理与性能优化》）。

版本主要收益主要破坏面升级前必查维护状态（截至 2026 年 9 月）
3.11专门化解释器、零开销异常、精确到表达式的错误定位、ExceptionGroup 与 except*、TaskGroup@asyncio.coroutine、inspect.getargspec 等长期弃用接口被删老异步代码里是否还有生成器协程写法仅安全修复，2027-10 结束
3.12type 语句与新泛型语法、sys.monitoring 低开销观测接口、不朽对象、推导式内联、f-string 语法正式化distutils 移除，asyncore / asynchat / imp / smtpd 移除；Unicode 对象的旧 C API 清理依赖里是否还有 setup.py 直接 import distutils 的老包仅安全修复，2028-10 结束
3.13增量式循环 GC、新 REPL、实验性 JIT、实验性 free-threaded 构建、os.process_cpu_count()PEP 594 一次性删掉十九个历史模块（含 cgi、telnetlib、crypt 等），lib2to3 移除，locals() 语义按 PEP 667 调整有没有间接依赖 cgi.parse_header 这类老接口的 Web 中间件常规维护，2029-10 结束
3.14PEP 649/749 注解延迟求值、free-threaded 构建转为官方支持、concurrent.interpreters 暴露子解释器、模板字符串、尾调用解释器直接读写 __annotations__ 的元编程代码可能行为改变；依赖注解是字符串这一假设的库需要适配ORM、序列化、依赖注入这类重度使用注解的库版本是否已支持最新稳定版，2030-10 结束

两个要纠正的说法。第一，增量 GC 是 3.13 引入的，不是 3.14，把它当成升到 3.14 的理由是记错了版本。第二，from __future__ import annotations 与 PEP 649 不是同一回事：前者把注解全部变成字符串，后者是按需惰性求值、拿到的仍是真实对象；依赖 get_type_hints 的库在这两种模式下行为并不相同，迁移时要按库的文档确认，而不是想当然。

移除与行为变更：升级真正卡住的地方

语法向后兼容，所以升级失败几乎都发生在标准库移除和第三方包的兼容性上。这张表是排查 ImportError 与 AttributeError 的对照单。

变更生效版本典型症状处置
distutils 移除3.12装老包时报找不到 distutils，通常发生在构建隔离环境里装 setuptools 可恢复一个兜底实现；长期方案是让依赖迁到 PEP 517 后端
cgi / telnetlib / crypt 等十九个模块移除3.13老 Web 工具链在解析 multipart 或 header 时报 ModuleNotFoundError换 email、multipart 等替代库；crypt 场景改用专门的密码哈希库
locals() 语义按 PEP 667 调整3.13在函数里改 locals() 期望影响真实变量的技巧失效；部分调试与模板库受影响本来就是未定义行为，改成显式字典传参
注解延迟求值3.14在类定义期读 __annotations__ 拿到的东西与预期不同统一走 get_type_hints 或 annotationlib，不要直接读属性
Unicode 旧 C API 清理3.12老 C 扩展编译报未定义符号等上游发新轮子；自维护的扩展改用现代 API
numpy 2.0 换 C ABI与 Python 版本无关导入时报二进制不兼容，提示编译期与运行期的 numpy 版本不一致所有按 numpy 头文件编译的扩展必须重新构建；升级要整栈一起动
free-threaded 构建的独立 ABI 标记3.13 起同一个包在 cp313 上有轮子，在 cp313t 上没有，于是回退源码构建甚至直接失败先盘点轮子矩阵再决定是否启用该构建

可操作的做法是把弃用告警变成硬失败：在 CI 里用开发模式跑一遍测试，让 DeprecationWarning 直接抛异常。这样上游下一个大版本删东西之前，你已经改完了。

# ---- 升级小版本前的兼容性体检，按「先轮子、后代码」的顺序 ----

# 1. 在目标解释器上按锁文件装一遍依赖
uv sync --frozen --python 3.14
#    想让「缺二进制轮子」立刻失败而不是悄悄变成半小时编译，用 pip 侧的开关更直白
pip install --only-binary=:all: -r requirements.lock

# 2. 确认当前解释器认得哪些 ABI 与平台标记
#    输出里没有目标标记，说明对应的二进制轮子装不上
python3.14 -m pip debug --verbose | sed -n '/Compatible tags/,/^$/p'

# 3. 开发模式 + 把弃用告警升级成异常，跑全量测试
#    -X dev 会打开额外检查；-W error 让 DeprecationWarning 直接失败
python3.14 -X dev -W error::DeprecationWarning -m pytest -q

# 4. 区分「解释器慢」和「服务慢」：先量服务自身的 p99，再量解释器基准
#    不要用基准套件的倍数去预估业务收益
python3.14 -m pyperf timeit -s 'import json' 'json.dumps({"a": 1})' 2>&1 | tail -3

# 5. 只在需要评估 free-threaded 时执行：确认 GIL 状态与扩展兼容性
python3.14t -c 'import sys, sysconfig; print(sysconfig.get_config_var("Py_GIL_DISABLED"), sys._is_gil_enabled())'
# 第二个值若为 True，说明某个扩展没声明支持无 GIL，运行时把 GIL 又打开了

free-threaded 构建：现状与限制

先给结论：GIL 保证同一进程内任一时刻只有一条线程执行 Python 字节码，free-threaded 构建去掉的正是这条保证（GIL 的机制与并发模型详见站内《Python 并发编程》）。它在 3.13 作为实验性构建出现，3.14 按 PEP 779 转为官方支持的构建变体——但「官方支持」指的是这个构建被正式维护，不等于生态已经准备好。

维度free-threaded 构建的现状对工程决策的含义
分发方式独立构建，解释器与轮子都带 t 后缀的 ABI 标记不是一个开关，是另一套环境；轮子矩阵要重新盘点
单线程性能3.13 上有明显的单线程开销，3.14 已大幅收窄如果你的服务是多进程 + 单线程模型，换过去只会变慢
解释器优化3.13 的该构建关闭了自适应专门化，3.14 重新启用拿 3.13 的 free-threaded 做性能评估结论会偏悲观
C 扩展扩展必须显式声明支持无 GIL，否则导入时运行时会把 GIL 重新打开一个不兼容的间接依赖就能让整套评估失去意义，必须用 sys._is_gil_enabled() 验证
受限 API 与 abi3支持是逐版本补齐的，3.13 的该构建上用不了 abi3 轮子越依赖 abi3 轮子的项目，越晚才能试
线程安全假设原来靠 GIL 隐式保护的操作不再原子，竞态会真正暴露大量存量库的内部缓存、计数器是隐式依赖 GIL 的，问题只在高并发下偶发
适用场景共享大块只读或读多写少内存、且不能拆成多进程的 CPU 型负载多进程能解决的问题不要用它解决；能拆进程永远是更稳的选择

换句话说，free-threaded 的独特价值只在一个窄场景里成立：内存里有一份很大的共享状态（模型权重、索引、大字典），复制到多个进程代价不可接受，同时工作是 CPU 密集的。除此之外，多进程加共享内存或者把热点挪到能释放 GIL 的原生扩展，都是更成熟的路。

"""逐个导入依赖，找出哪个扩展会让 free-threaded 构建把 GIL 重新打开。
只在 python3.14t 这类 free-threaded 解释器上运行才有意义。"""
import subprocess, sys, sysconfig

PROBE = (
    "import sys, importlib;"
    "importlib.import_module(sys.argv[1]);"
    "print('GIL_ON' if sys._is_gil_enabled() else 'GIL_OFF')"
)

def check(modules: list[str]) -> list[str]:
    if not sysconfig.get_config_var("Py_GIL_DISABLED"):
        raise SystemExit("当前不是 free-threaded 构建，这个检查没有意义")
    blockers = []
    for name in modules:
        # 必须开子进程：GIL 一旦被某个扩展重新打开，本进程内无法复原
        r = subprocess.run(
            [sys.executable, "-X", "gil=0", "-c", PROBE, name],
            capture_output=True, text=True,
        )
        if r.returncode != 0:
            tail = r.stderr.strip().splitlines()[-1] if r.stderr.strip() else "unknown"
            print(name, "导入失败", tail)          # 多半是这个构建下没有轮子
        elif r.stdout.strip() == "GIL_ON":
            blockers.append(name)
            print(name, "导入后 GIL 被重新打开，该扩展未声明支持无 GIL")
    return blockers

if __name__ == "__main__":
    # 把锁文件里所有带原生扩展的包列进来，一次跑完再决定要不要继续评估
    print("blockers:", check(sys.argv[1:]))

CPython 与 PyPy 的适用边界

PyPy 的核心是 RPython 写成的追踪式 JIT：解释执行时给循环和函数计数，热到阈值之后记录一条执行轨迹并编译成机器码，运行时用守卫检查假设是否仍成立，不成立就回退解释执行。这个模型决定了它的全部优势与全部限制。

sequenceDiagram participant U as 调用方 participant IN as 解释器 participant JT as 追踪编译器 participant MC as 机器码 U->>IN: 前若干次调用，纯解释执行 IN->>IN: 给循环与函数计数 Note over IN,JT: 计数到阈值才触发编译
短命进程根本走不到这一步 IN->>JT: 提交热路径的执行轨迹 JT->>MC: 生成带类型假设与守卫的机器码 U->>MC: 后续调用直接走机器码 MC->>IN: 守卫失败，回退解释执行并重新追踪 Note over U,MC: 输入分布突变会反复触发重编译
表现为吞吐周期性下陷
场景CPython 标准构建PyPy判断依据
长驻服务，热点分散在大量纯 Python 业务代码基线通常是唯一能不改代码就提速的选择热点分散意味着没有可重写的「一小块」
短命进程：CLI、定时任务、函数计算合适不合适预热成本收不回来，反而更慢
依赖大量 C 扩展合适风险高PyPy 通过仿真层兼容 C API，跨界调用开销显著，可能整体变慢
数值计算已由 numpy 承担合适收益有限时间已在原生代码里，JIT 没有可优化的 Python 字节码
依赖析构时机（打开的文件、连接）引用计数，离开作用域即回收不保证PyPy 没有引用计数，不显式关闭会出现句柄耗尽
需要最新语言特性跟随最新版语言版本滞后一到两个小版本用了新语法就直接出局
多核并行靠多进程同样受全局锁约束换 PyPy 不解决多核问题，这是最常见的误解

还有 JVM 上的 GraalPy 等其他实现，思路类似但生态覆盖更窄，决策方式完全一样：先把依赖清单里带原生扩展的包挑出来逐个验证，再谈性能。

C 扩展与 ABI：升级节奏的真正决定者

Python 的小版本升级之所以不能「当天升」，根因是非受限 C API 的二进制接口随小版本变化，扩展必须为每个小版本单独编译一份轮子。所以新版本发布当天，纯 Python 的依赖立刻可用，而带原生扩展的依赖要等上游发布轮子——这个等待期就是你的升级窗口下限。

扩展实现方式ABI 稳定性跨小版本复用轮子能否释放 GIL适用与代价
手写 C，非受限 API随小版本变化不能，每版重编能，手动管理性能上限最高，维护成本与崩溃风险也最高
手写 C，受限 API 加 abi3稳定能，一份轮子跨多个小版本能只能用受限接口，部分优化写不出来；换来的是发布当天就能用
Cython随小版本变化默认不能能，用显式代码块改造存量 Python 代码最省力，代价是引入构建链
PyO3 加 maturin（Rust）可选 abi3开了 abi3 就能能，且编译期就能查出数据竞争内存安全由语言保证，适合新写的计算密集模块
cffi 的 ABI 模式只依赖目标库 ABI能，无需重编调用期释放包已有的共享库最合适；每次调用的边界开销比编译期绑定高
ctypes纯运行时能调用期释放零构建成本，适合胶水与原型，不适合高频调用
mypyc随小版本变化不能受限把带类型注解的 Python 编成扩展，改动小但加速幅度取决于注解质量

由此得出一条选型经验：如果你要发布一个带原生扩展的库，abi3 带来的工程收益通常大于它损失的那点性能——一份轮子覆盖多个小版本，意味着用户不必等你重新发版，也大幅缩小你的构建矩阵。反过来，如果扩展是公司内部服务专用、Python 版本由你自己控制，就没必要为 abi3 牺牲接口灵活性。

科学计算栈与纯 Python 服务栈的约束不同

同一个「Python 版本选型」问题，在这两类项目里的答案经常相反，因为约束完全不同。

约束维度纯 Python 服务栈科学计算与 AI 栈
升级窗口由谁决定少数带原生扩展的关键库整条轮子矩阵：解释器版本 × 加速器驱动 × 数值库 ABI
可升级的粒度单个依赖可独立升级数值库、框架、扩展往往必须整栈同步升级
解释器提速的收益较小，时间多在 IO 与序列化几乎为零，时间在原生内核里
多核利用方式多进程 worker原生层已释放 GIL，线程池即可并行
镜像体积与基础镜像slim 镜像足够常需完整发行版；musl 平台轮子覆盖差，Alpine 基本不可行
最易踩的环境坑宿主 PYTHONPATH 污染、系统库版本不匹配conda 与 pip 混装导致两份数值库或两份 C++ 运行时同时存在，导入期直接崩
版本策略可以较激进，跟随次新版保守，跟随框架官方支持的版本区间

一个常见误判是把服务栈的经验套到 AI 栈上：服务栈里「升一个小版本、跑通测试、发布」是几天的事；AI 栈里同一个动作可能要等上游发布新轮子、验证加速器驱动组合、重建所有自编译扩展。反过来，AI 栈的保守习惯用在纯服务上，会让项目长期停在早已只有安全修复的版本上。

性能不够时：换解释器还是换热点实现

先算一个上限再动手，能避免绝大多数无效优化。若某段代码占总耗时的比例是 p，把它优化到无限快，整体加速上限也只有 1 / (1 - p)：热点占 30% 时上限约 1.43 倍，占 80% 时才有 5 倍。没有剖析数据就重写热点，通常是在为 1.1 倍的收益承担一套新的构建链和一类新的崩溃。

"""先量再改：找出热点占比，算出加速上限，再决定值不值得换实现。"""
import cProfile, pstats, io, time

def profile_top(func, *args, topn: int = 15):
    pr = cProfile.Profile()
    pr.enable()
    func(*args)
    pr.disable()
    buf = io.StringIO()
    st = pstats.Stats(pr, stream=buf).sort_stats("tottime")   # tottime 才是自身耗时
    st.print_stats(topn)
    return st, buf.getvalue()

def speedup_ceiling(hot_ratio: float) -> float:
    """阿姆达尔上限：热点部分优化到零耗时，整体最多快多少倍。"""
    assert 0.0 <= hot_ratio < 1.0
    return 1.0 / (1.0 - hot_ratio)

def crossing_cost_ok(calls: int, work_per_call_us: float) -> bool:
    """判断把热点挪到原生扩展是否划算。
    Python 到原生的一次跨界调用开销在百纳秒量级，
    如果每次调用只干几微秒的活，收益会被调用开销吃掉：
    要么把接口改成批量传数组，要么别重写。"""
    return work_per_call_us >= 10.0

if __name__ == "__main__":
    # 真实负载下量，不要用构造的微基准；并发场景要量 p99 而不是平均
    t0 = time.perf_counter()
    # profile_top(handle_batch, payload)
    print("elapsed", time.perf_counter() - t0)
    for r in (0.3, 0.5, 0.8, 0.95):
        print(r, round(speedup_ceiling(r), 2))
剖析得到的结论首选动作为什么什么时候这条不成立
时间大头在等 IO改并发模型、复用连接、加缓存解释器再快也不会让网络变快连接建立本身成为热点时，要动的是池化策略
热点集中在少数纯 Python 数值循环向量化到 numpy，或用 numba 编这几个函数循环搬到原生层，收益一到两个数量级数据量小时向量化的内存搬运反而更慢
热点集中在少数函数，处理原生类型，可批量传参写 Rust 或 C 扩展，并在计算段释放 GIL热点边界清晰，跨界开销被批量摊薄，还能顺带拿到多核接口是「每次一个元素」时，调用开销吃掉全部收益
热点分散在大量业务代码，没有明显尖峰长驻服务可评估 PyPy；否则先升 CPython 小版本没有可重写的一小块，只能整体提速依赖大量 C 扩展，或进程是短命的
瓶颈在序列化、校验、编解码换带原生实现的库这类库的原生实现已经把活干完了，比自己重写划算得多数据结构特别不规则时，通用库的假设可能不适用
单核打满、多核空闲，且是纯 Python CPU 工作多进程最成熟、最可回滚的方案共享状态大到复制不起，才需要考虑 free-threaded
内存增长导致 GC 停顿明显先减少常驻对象数量与容器嵌套深度停顿与被追踪对象规模相关，换解释器不解决确认是循环引用堆积时，要调回收策略而非对象数
整体慢一个数量级以上且需求稳定把这个服务换语言，而不是换解释器解释器层面的优化空间是有限倍数，量级差距填不平业务仍在高频变更时，重写风险大于收益

❌
最容易踩的坑

1. 把基准套件的倍数当成业务收益：官方口径衡量的是解释器执行字节码的速度，而服务的时间大多花在 IO、序列化和原生扩展里。

2. 升级顺序反了：先跑测试再装依赖，测试全绿之后才发现某个带原生扩展的包在目标版本上根本没有轮子。

3. 以为 free-threaded 是个启动开关：它是独立构建、独立 ABI 标记，轮子矩阵要整套重新盘点。

4. 在 free-threaded 构建上评估性能却没检查 GIL 是否真的关着：一个未声明支持的扩展会让运行时把 GIL 重新打开，测出来的数毫无意义。

5. 指望换 PyPy 解决多核问题：它同样有全局锁，多核仍要靠多进程。

6. 在短命进程（CLI、定时任务、函数计算）里用 PyPy，预热成本收不回来，净变慢。

7. 迁到 PyPy 后依赖引用计数的析构时机，不显式关闭文件与连接，最终句柄耗尽。

8. 升级 numpy 大版本时只升它自己：换了 C ABI 之后，所有按其头文件编译的扩展都要重新构建。

9. 把 from __future__ import annotations 与 PEP 649 当同一件事，迁移后元编程代码拿到的注解类型与预期不符。

10. 记错版本：增量 GC 是 3.13 的变化，不是 3.14，据此规划升级会白做一轮。

11. 发布带原生扩展的库却不出 abi3 轮子，每个 Python 小版本都要重新发版，用户被迫等你。

12. 没剖析就重写热点：热点占 30% 时上限只有 1.43 倍，换来的是一套新构建链和一类新的段错误。

13. 把热点改成原生扩展但接口仍是「每次一个元素」，跨界调用开销吃掉全部收益。

14. 长期停在只剩安全修复的版本上，等到不得不升时要跨三四个小版本，破坏面一次性叠加。
