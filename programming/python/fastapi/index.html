FastAPI 的机制与生产化

🏷️ FastAPI

FastAPI 上手快，踩的坑也集中：在 async def 里调了同步库、依赖里做重 IO 没缓存、忘了 response_model 把内部字段带出去、拿 BackgroundTasks 当队列用。这些问题的根源都在机制层面——不知道一次请求在框架内部经过了什么。这篇先给一份能直接长大的最小骨架，再按处理链把机制讲清楚，最后收拢上线前的判断。项目目录、配置、日志、异常层级这些工程骨架问题见《Python 后端项目的工程骨架》。

💡
这篇怎么读
  • ① 用法：一份最小可用的应用骨架（路由、输入与输出模型、依赖注入、领域异常与全局处理器、lifespan 钩子），外加一张「要做什么 → 写在哪」对照表和一张常用参数速查表——照着写，后面几节的坑大半不会发生。
  • ② 原理：一次请求在路由匹配、依赖解析、参数校验、handler、序列化之间的完整链路；Depends 的单请求缓存与 yield 依赖的清理时机；def 与 async def 的执行位置差异与四种组合的真实并发上限；response_model 的字段过滤与 pydantic v2 迁移对照；BackgroundTasks 缺的到底是什么；lifespan、中间件、依赖、异常处理器各自的作用范围。
  • ③ 场景：上线前必须改的七项配置、反模式速查，以及哪些问题不该在框架层解决。

① 用法 · 最小骨架与「要做什么 → 写在哪」

下面这份骨架不是 Hello World，而是把「第一次上线前一定会遇到的五件事」都放到了正确位置：输入输出模型分离、依赖里管资源与鉴权、领域异常统一转换、lifespan 建连接池、生产关文档地址。照这个形态起项目，后面原理层讲的坑大部分根本不会发生。

# app/main.py —— 单文件形态的最小骨架，长大之后按 routers / models / deps 拆开即可
from contextlib import asynccontextmanager
from typing import Annotated

import httpx
from fastapi import APIRouter, Depends, FastAPI, Query, Request, status
from fastapi.responses import JSONResponse
from pydantic import BaseModel, ConfigDict, Field
from sqlalchemy.ext.asyncio import AsyncSession


# ---------- 1. 模型：输入与输出分开定义，永远不要复用同一个类 ----------
class OrderCreate(BaseModel):
    sku: str = Field(min_length=1, max_length=64)
    qty: int = Field(ge=1, le=999)          # 约束写在模型里，422 会带字段级错误


class OrderOut(BaseModel):
    # 要从 ORM 对象属性取值就必须开这个；字段列表就是「允许出去的字段」
    model_config = ConfigDict(from_attributes=True)
    id: int
    sku: str
    qty: int


# ---------- 2. 领域异常与全局处理器：错误结构只在一处定义 ----------
class AppError(Exception):
    def __init__(self, code: str, message: str, status_code: int = 400) -> None:
        self.code, self.message, self.status_code = code, message, status_code


# ---------- 3. 依赖：资源获取与鉴权都在这里，不要写进 handler ----------
async def get_db():
    async with SessionLocal() as session:   # 清理在响应发送之后执行，见原理层
        try:
            yield session
            await session.commit()          # 事务边界收敛到一处
        except Exception:
            await session.rollback()
            raise                           # 必须重抛，否则异常被吞成静默 500


DbSession = Annotated[AsyncSession, Depends(get_db)]


async def current_user(
    db: DbSession,                                  # 依赖可以嵌套依赖
    token: Annotated[str | None, Depends(bearer_token)] = None,
) -> "User":
    if token is None:
        raise AppError("unauthorized", "缺少凭证", status.HTTP_401_UNAUTHORIZED)
    return await load_user(db, token)


CurrentUser = Annotated["User", Depends(current_user)]


# ---------- 4. 路由：response_model 不是可选项 ----------
router = APIRouter(tags=["orders"])


@router.post("/orders", response_model=OrderOut, status_code=status.HTTP_201_CREATED)
async def create_order(payload: OrderCreate, user: CurrentUser, db: DbSession):
    # payload 已经过校验；user 与 db 在同一请求内只解析一次，天然同一事务
    return await insert_order(db, user.id, payload)


@router.get("/orders", response_model=list[OrderOut])
async def list_orders(
    user: CurrentUser,
    db: DbSession,
    limit: Annotated[int, Query(ge=1, le=100)] = 20,   # 分页上限必须给，否则一次拉全表
    cursor: Annotated[int | None, Query()] = None,
):
    return await query_orders(db, user.id, limit=limit, cursor=cursor)


# ---------- 5. lifespan：所有可能失败的初始化放这里 ----------
@asynccontextmanager
async def lifespan(app: FastAPI):
    # 失败就让进程起不来，比「起来了但连不上下游」好得多
    app.state.http = httpx.AsyncClient(timeout=httpx.Timeout(3.0, connect=1.0))
    yield
    await app.state.http.aclose()            # 关闭顺序与创建相反


def create_app() -> FastAPI:
    is_prod = settings.env == "prod"
    app = FastAPI(
        lifespan=lifespan,
        docs_url=None if is_prod else "/docs",
        redoc_url=None if is_prod else "/redoc",
        openapi_url=None if is_prod else "/openapi.json",   # 三个必须一起关
    )

    @app.exception_handler(AppError)
    async def on_app_error(request: Request, exc: AppError):
        # 客户端只需要解析一种错误结构；handler 里只抛领域异常，不各自拼 JSON
        return JSONResponse(
            status_code=exc.status_code,
            content={"code": exc.code, "message": exc.message},
        )

    @app.get("/healthz", include_in_schema=False)
    async def healthz():
        return {"ok": True}                  # 存活检查只看进程，不碰下游

    app.include_router(router, prefix="/api/v1")
    return app


app = create_app()

骨架之外的每一件事，都有一个「该写在哪」的固定答案。放错位置是 FastAPI 项目最常见的结构性问题，比写错一行代码更难改：

要做什么写在哪注意什么
建连接池、HTTP 客户端、预热缓存lifespan 的 yield 之前失败就让进程起不来；别放几十秒的任务，就绪探针会先超时
释放资源、关闭客户端lifespan 的 yield 之后顺序与创建相反；收到 SIGTERM 后才执行
鉴权与权限判断路由级 Depends，或 app 级 dependencies=[...]不要写在中间件里：那里拿不到路由信息与依赖结果，也进不了 OpenAPI；用全局依赖时记得排除健康检查
拿数据库会话、划事务边界yield 依赖同一请求内被缓存，多处 Depends 拿到的是同一个会话，天然同一事务
请求 ID、访问日志、耗时统计@app.middleware("http")contextvars 设了必须 reset，否则污染后续请求
统一错误结构与告警级别@app.exception_handler(领域异常)handler 里只抛领域异常；不要在每个路由里各自拼 JSON
控制响应里出现哪些字段路由装饰器的 response_model不声明就会把返回值原样序列化，这是最常见的字段泄露形态
参数校验与文档签名里的 Annotated[类型, Query()/Path()/Header()]标量默认是查询参数；/users/me 必须注册在 /users/{uid} 之前
调用还没有异步实现的库写普通 def handler，或 async def 里 await asyncio.to_thread(...)在 async def 里直接调同步库会按住整个 worker，原因见原理层
响应之后的收尾动作BackgroundTasks，且仅限「丢了也没关系」的必须成功的动作走消息队列；进程重启时进程内任务直接消失
配置与密钥pydantic-settings 的 Settings 单例，靠依赖注入传下去不要在模块各处直接读环境变量，测试时无法替换

装饰器参数里真正会影响线上行为的只有这几个，其余默认值都可以先不管：

参数作用默认值什么时候必须改
response_model过滤并校验输出字段，同时生成文档无，即不过滤所有对外接口都要给，这是硬性要求
status_code成功路径的状态码200（POST 也是 200）创建资源改 201，无响应体改 204
dependencies=[Depends(f)]只执行、不把返回值注入 handler空做统一鉴权、限流、审计；可加在路由、router 或 app 三层
Depends(f, use_cache=False)关掉单请求缓存，每个引用点重新执行use_cache=True确实需要一条独立会话时；注意会多占一条连接
include_in_schema是否出现在 OpenAPI 文档里True健康检查、内部调试接口设 False
docs_url / redoc_url / openapi_url三个文档地址/docs、/redoc、/openapi.json生产环境三个一起设 None，只关前两个等于没关
response_model_exclude_unset只输出显式设置过的字段FalsePATCH 语义的接口；会让客户端的解析变复杂
prefix / tags（include_router）统一路径前缀与文档分组空版本化路径统一在 include_router 给，不要写死在每个路由上
anyio 线程池容量def handler 的并发上限40（以所用版本的文档为准）同步库多、下游扛得住时上调；调大之前先确认数据库连接池够

这一层不解释为什么，比如「为什么同一个依赖只跑一次」「为什么 async def 里的同步调用会影响别的请求」「为什么 yield 后的清理阶段抛异常没用」，都在下面的原理层。

② 原理 · 核心是类型签名驱动

搞清这一节能解决的现象是：参数取不到、文档里的字段和实际不一致。FastAPI 本身代码量不大，能力来自两个东西：Starlette 提供 ASGI 与路由，pydantic 提供校验与序列化。它做的事是读函数签名，然后推导出参数从哪来、怎么校验、怎么序列化、文档怎么生成。理解这条推导规则，大部分定位问题就不需要猜。

sequenceDiagram participant C as 客户端 participant MW as 中间件栈 participant R as 路由匹配 participant D as 依赖解析 participant V as 参数校验 pydantic participant H as handler participant S as 响应序列化 C->>MW: HTTP 请求 MW->>R: 按注册顺序匹配 path 与 method R->>D: 解析依赖树，同一依赖单请求内只跑一次 D-->>C: 依赖里抛异常则 handler 根本不执行 D->>V: 依赖就绪，校验 path query body header V-->>C: 校验失败直接 422，带字段级错误列表 V->>H: 注入参数，调用 handler Note over H: async def 在事件循环里跑
def 被丢进线程池 H->>S: 返回对象 S->>S: 按 response_model 过滤字段并序列化 S->>MW: 响应逐层回到中间件 MW->>C: 返回；此后才执行 yield 依赖的清理与 BackgroundTasks
签名写法参数来源容易踩的点
名字出现在路径模板里路径参数路由注册顺序决定匹配，/users/me 必须写在 /users/{uid} 之前
标量类型且不在路径里查询参数不给默认值就是必填，给了 None 才是可选
pydantic 模型类型请求体两个模型参数会变成嵌套 JSON，不是并列字段
Annotated[str, Header()]请求头下划线自动转连字符，需要原样时要关掉 convert_underscores
Annotated[X, Depends(f)]依赖注入结果依赖自身的参数也会参与校验与文档
UploadFile / Formmultipart 表单需要装 python-multipart，且不能和 JSON body 混用
Request原始请求对象拿它读 body 会和已声明的 body 参数冲突，body 只能被读一次

② 原理 · 依赖注入：单请求缓存与清理时机

搞清这一节能解决的现象是：一个请求里鉴权查了好几次库，或者数据库会话在该关的时候没关。Depends 不只是「传参的糖」。它有三条机制必须知道：依赖按需解析（没被引用就不执行）、同一请求内同一依赖只解析一次（结果缓存，可用 use_cache=False 关掉）、yield 之后的代码在响应发送之后执行（0.106 起的行为）。

from typing import Annotated
from fastapi import Depends, FastAPI, Header
from sqlalchemy.ext.asyncio import AsyncSession

app = FastAPI()


async def get_db() -> AsyncSession:
    """yield 依赖做资源清理：会话一定会关，连接一定会归还连接池"""
    async with SessionLocal() as session:
        try:
            yield session
            await session.commit()        # 正常路径统一提交，事务边界收敛到一处
        except Exception:
            await session.rollback()      # handler 的异常会在 yield 处重新抛进来
            raise                         # 必须重抛，否则异常被吞，客户端拿到 500 且无日志


DbSession = Annotated[AsyncSession, Depends(get_db)]


async def get_current_user(
    db: DbSession,                                    # 依赖可以嵌套依赖
    authorization: Annotated[str | None, Header()] = None,
) -> User:
    if not authorization:
        raise AuthError("缺少凭证")                    # 依赖里抛异常，handler 不会被执行
    return await load_user(db, parse_token(authorization))


CurrentUser = Annotated[User, Depends(get_current_user)]


@app.get("/orders")
async def list_orders(user: CurrentUser, db: DbSession):
    # user 和 db 在同一请求内只解析一次：这里的 db 与 get_current_user 里的是同一个会话，
    # 所以两处操作天然在同一事务内。这正是单请求缓存的实际意义。
    return await query_orders(db, user.id)


@app.get("/audit")
async def audit(
    # 需要一个独立会话时才关掉缓存；注意这会额外占用一条连接
    db: Annotated[AsyncSession, Depends(get_db, use_cache=False)],
):
    return await write_audit_log(db)
机制行为误用后果
单请求缓存同一依赖（同一可调用对象）一次请求只执行一次误以为会重复执行而把依赖写成有副作用的
use_cache=False每个引用点都重新执行拿它做「独立事务」时会多占连接，池小的时候直接耗尽
依赖里抛异常handler 不执行，异常走全局处理器把鉴权写在 handler 里而不是依赖里，漏掉某个接口
yield 后的清理响应发送之后执行在清理阶段抛 HTTPException 想改响应，完全无效
依赖嵌套层数没有限制，按树解析四五层之后没人说得清某个值从哪来，排查成本陡增
依赖里做重 IO每个请求都执行一遍鉴权里查一次库，QPS 上来后数据库先撑不住；该加进程级缓存
全局依赖（dependencies=[...]）对所有路由生效，返回值拿不到用来做统一鉴权很合适，但健康检查接口要记得排除

② 原理 · 同步与异步 handler：最高频的性能事故

搞清这一节能解决的现象是：压测 QPS 上不去，且延迟随并发线性恶化。这是 FastAPI 上线后的首要性能问题，两种 handler 的执行位置完全不同：

  • def handler：被丢进 anyio 的外部线程池执行，默认容量 40 个线程。里面做同步阻塞不会卡事件循环，但并发上限就是线程数，第 41 个请求开始排队。
  • async def handler：直接在事件循环里跑。里面任何同步阻塞都会按住整个 worker 的所有请求。

所以「把 def 改成 async def 能提速」是彻底的误解。如果依赖库是同步的，改成 async def 会让性能断崖下跌：原本 40 个请求可以并行等 IO，现在变成严格串行。

import asyncio
import time
from concurrent.futures import ProcessPoolExecutor

import httpx
from fastapi import FastAPI

app = FastAPI()

# ---------- 错误写法：async def 里调同步库 ----------
@app.get("/bad")
async def bad():
    import requests
    # 这一行阻塞整个事件循环：本 worker 内所有在途请求全部停止推进
    r = requests.get("https://api.example.com/data", timeout=3)
    return r.json()


# ---------- 修法一：换异步客户端（首选） ----------
# 客户端在 lifespan 里创建一次并复用，每请求新建 client 会丢掉连接池
@app.get("/good-async")
async def good_async():
    client: httpx.AsyncClient = app.state.http
    r = await client.get("/data", timeout=3.0)   # 超时必须显式给，默认 5s 也要确认
    return r.json()


# ---------- 修法二：无异步实现时，显式丢线程池 ----------
_sdk_limit = asyncio.Semaphore(20)   # 别让同步调用把 40 个线程全占满

@app.get("/good-thread")
async def good_thread():
    async with _sdk_limit:
        # to_thread 内部用的就是 anyio 线程池；相比 run_in_executor 更简洁
        return await asyncio.to_thread(legacy_sdk_call, "arg")


# ---------- CPU 密集：线程池没用，必须换进程 ----------
pool = ProcessPoolExecutor(max_workers=2)

@app.get("/cpu")
async def cpu_bound():
    loop = asyncio.get_running_loop()
    # 注意参数与返回值要能 pickle，大对象传参的序列化成本可能超过计算本身
    return await loop.run_in_executor(pool, heavy_calc, 10_000_000)

组合执行位置并发上限结论
async def + 异步库事件循环受连接池与下游限制，可到数千目标形态
def + 同步库线程池（默认 40）40 个并发，超出排队可接受，且比写错的 async 安全得多
async def + 同步库事件循环实际为 1严重事故，延迟随并发线性恶化
async def + asyncio.to_thread线程池线程数，需自行限流过渡期的正确姿势
def + CPU 计算线程池受 GIL 限制，约等于 1 核吞吐上不去，要换进程池
async def + CPU 计算事件循环1，且拖垮全部请求最差组合

阻塞的成因、识别手段与并发控制细节在《asyncio 的性能陷阱》里完整展开；接口耗时该怎么拆解、连接池容量怎么算见站内后端性能优化专题。

② 原理 · response_model：字段过滤不是可选项

搞清这一节能解决的现象是：响应里出现了 password_hash、deleted_at 这类字段，而且没有任何报错。response_model 的作用被严重低估：它不只是生成文档，而是按声明的模型过滤输出字段。不声明的话，handler 返回的 ORM 对象或 dict 会被原样序列化——密码哈希、内部状态、软删除标记、关联对象的全部字段都可能一起出去。

② 原理 · BackgroundTasks 不是任务队列

搞清这一节能解决的现象是：发布期间一批「已经返回成功」的后续动作凭空消失。BackgroundTasks 的执行位置是同一个进程、响应返回之后。它没有持久化、没有重试、没有可观测性。进程重启、Pod 被驱逐、任务里抛异常，任务就消失了且没人知道。

② 原理 · lifespan、中间件与异常处理器的分工

搞清这一节能解决的现象是：鉴权写在中间件里之后，文档里看不到、也拿不到路由信息。on_event("startup") 已弃用，统一用 lifespan：它是一个异步上下文管理器，yield 之前建资源、之后释放资源，而且能保证在接流量之前完成初始化。

from contextlib import asynccontextmanager

import httpx
from fastapi import FastAPI, Request
from fastapi.middleware.cors import CORSMiddleware


@asynccontextmanager
async def lifespan(app: FastAPI):
    # 启动：所有可能失败的初始化都放这里，失败则进程起不来，流量不会切过来
    app.state.http = httpx.AsyncClient(
        base_url=settings.upstream_url,
        timeout=httpx.Timeout(3.0, connect=1.0),      # 必须显式设，连接超时单独给
        limits=httpx.Limits(max_connections=100, max_keepalive_connections=20),
    )
    app.state.db = create_engine_pool(settings)
    yield
    # 关闭：收到 SIGTERM 后执行，顺序与创建相反
    await app.state.http.aclose()
    await app.state.db.dispose()


def create_app() -> FastAPI:
    is_prod = settings.env == "prod"
    app = FastAPI(
        lifespan=lifespan,
        # 生产关掉三个地址：只关 docs 不关 openapi.json 等于没关
        docs_url=None if is_prod else "/docs",
        redoc_url=None if is_prod else "/redoc",
        openapi_url=None if is_prod else "/openapi.json",
    )
    app.add_middleware(
        CORSMiddleware,
        allow_origins=settings.cors_origins,   # 显式白名单；allow_credentials 为真时不能用通配
        allow_credentials=True,
        allow_methods=["GET", "POST", "PUT", "DELETE"],
        allow_headers=["Authorization", "Content-Type"],
    )

    @app.middleware("http")
    async def add_request_id(request: Request, call_next):
        # 中间件适合做跨请求的横切关注点：请求 ID、耗时、访问日志
        rid = request.headers.get("x-request-id") or uuid4().hex
        token = request_id_var.set(rid)
        try:
            response = await call_next(request)
        finally:
            request_id_var.reset(token)        # 必须 reset，否则 contextvars 污染后续请求
        response.headers["x-request-id"] = rid
        return response

    register_handlers(app)                      # 统一异常转换
    app.include_router(api_router, prefix="/api/v1")
    return app

③ 场景 · 反模式速查与不适用边界

反模式现象修法
async def 里用同步 IOQPS 上不去，延迟随并发线性上升换异步库，或 asyncio.to_thread 包住
不设 response_model响应里出现 password_hash、deleted_at每个对外接口都声明输出模型
用 BackgroundTasks 跑重要任务发布期间任务静默丢失上消息队列或 Celery
依赖里查库却不缓存一个请求触发多次鉴权查询，数据库先扛不住用单请求缓存（默认行为），再加进程级缓存
生产暴露 /docs内部接口被直接调用三个地址一起关
每个请求新建 httpx.AsyncClient连接无法复用，TIME_WAIT 堆积在 lifespan 里建单例
用中间件做鉴权拿不到路由与依赖信息，文档里也看不到用路由级或全局依赖

最容易踩的坑

❌
避坑清单
  • 在 async def 里调 requests、同步 ORM 或 time.sleep：整个 worker 的所有在途请求一起卡住，这是排名第一的性能事故。
  • 以为「把 def 改成 async def 能提速」：库还是同步的情况下，并发从 40 掉到 1。
  • 忘了 response_model：ORM 对象被原样序列化，密码哈希与内部字段直接出去，而且没有任何报错。
  • 输入输出复用同一个模型：加个内部字段就悄悄出现在响应里，改动评审看不出来。
  • 只关 docs_url 不关 openapi_url：拿到 openapi.json 一样能还原全部接口。
  • 用 BackgroundTasks 发邮件或扣款：滚动更新期间任务静默丢失，对账才发现。
  • 在 yield 依赖的清理阶段抛 HTTPException：响应早就发出去了，异常只会变成日志里的一条错误。
  • yield 依赖里捕获了 handler 的异常却不重抛：客户端收到 500，服务端却没有 traceback。
  • 中间件里 set 了 contextvars 却不 reset：上下文污染到后续请求，日志里 request_id 串号。
  • 路由注册把 /users/{uid} 写在 /users/me 之前：me 被当成 uid，报的是 422 而不是 404，排查方向全错。
  • 返回带懒加载关系的 ORM 对象：序列化阶段触发额外查询，异步会话下直接抛 MissingGreenlet。
  • 分页参数不设上限：客户端传一个很大的 limit 就能把全表拉出来，上限要写进 Query() 约束里。
  • 把鉴权写在中间件里：拿不到路由与依赖结果，OpenAPI 里也看不出这个接口需要认证。
  • allow_credentials=True 配 allow_origins=["*"]：浏览器会拒绝，而且这是明确的安全反模式，细节见站内安全专题。
