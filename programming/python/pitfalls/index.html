写到这种代码时怎么写才对谁替你查出来
函数签名里出现 =[]、={}、=set()，或默认值里调用了函数默认值一律写 None，在函数体内创建对象ruff B006（可变默认值）、B008（默认值里调用函数），部分可自动修
在循环里创建 lambda、闭包或注册回调用默认参数或 functools.partial 在定义处把值绑死ruff B023；这类 bug 极难靠测试发现，必开
写下 is 或 is not只对 None、True、False 和自造哨兵用；值比较一律 ==ruff F632、E711、E712；mypy 的 --strict-equality 还能查出「两个类型永远不可能相等」的比较
写 a[:]、list(a)、dict(a)、copy.copy先问「内层有没有可变对象」：有就逐层复制或 deepcopy，没有就放心用工具查不了，评审项；deepcopy 会连带复制连接与锁，别无脑上
在 for 循环体里增删容器元素改成推导式构造新对象，或倒序遍历，或对快照迭代（for k in list(d)）linter 覆盖不稳（相关规则仍在 preview），靠单测：用「含相邻重复元素」的数据才能暴露
写 except捕获具体类型；兜底用 except Exception 并 logger.exception；转换异常带 from e；finally 只做清理ruff E722（裸 except）、BLE001（盲目捕获）、B904（缺 from）、B012（finally 里跳转）、TRY400（该用 exception 却用了 error）
想写 __del__ 做清理换成上下文管理器；需要兜底用 weakref.finalize，不要把它当主路径工具查不了；用 python3 -X dev 让 ResourceWarning 显形，ruff SIM115 能查「open 没用 with」
用短字符串做高频比较或去重相等判断只用 ==；确有大量重复短字符串时用 sys.intern 主动驻留，让比较退化成指针比较ruff F632 挡住 is 比较字面量；驻留本身是性能取舍，见原理层
给类写 __eq__同时决定 __hash__：要能进 set 就按不可变字段实现，并保证这些字段之后不改；dataclass 用 frozen=True工具覆盖不稳；补一条「把对象塞进 set」的单测最省事
写 open、datetime.now、处理金额open 必带 encoding="utf-8"；时间一律 aware UTC；金额一律 Decimal 且从字符串构造ruff PLW1514（缺 encoding）、DTZ 规则组（缺时区）；金额精度靠类型约定与评审

把这十条落成代码，形态是固定的。下面这段按清单顺序给出「该怎么写」，每段都是能直接抄进项目的形态：

"""八类高频陷阱的正确形态速查。每段独立，按上表顺序排列。"""
from __future__ import annotations

import copy
from dataclasses import dataclass
from datetime import datetime, timezone
from decimal import ROUND_HALF_UP, Decimal
from functools import partial
from weakref import finalize


# 1. 可变默认参数：默认值在 def 执行时就创建好了，用 None 当哨兵
def collect(item, bucket: list | None = None) -> list:
    bucket = [] if bucket is None else bucket   # 每次调用各自一份，不会跨调用串数据
    bucket.append(item)
    return bucket


# 2. 闭包延迟绑定：在定义处把值绑死，不要指望调用时的循环变量
handlers = [partial(lambda i: i * 2, i) for i in range(3)]   # 0 2 4，而不是三个 4


# 3. is 只给单例。None 本身有业务含义时，自己造一个哨兵
MISSING = object()

def patch_name(name=MISSING) -> str | None:
    if name is MISSING:            # 这里用 is 是对的：比的就是「是不是那个对象」
        return None                # 「没传」和「显式传了 None」是两种语义
    return name


# 4. 浅拷贝只换外层。要隔离嵌套结构，逐层复制比 deepcopy 更可控
rows = [[0, 1], [2, 3]]
by_row = [r[:] for r in rows]      # 显式逐层，意图比 copy.copy 清楚
whole = copy.deepcopy(rows)        # 大结构上很慢，且会连带复制连接、锁这类不该复制的对象


# 5. 迭代中修改：构造新对象，或者先拍快照
def sweep(cache: dict[str, float], now: float) -> None:
    for key in list(cache):        # list() 拍快照，否则 del 会抛 RuntimeError
        if cache[key] < now:
            del cache[key]


# 6. 异常：捕获具体类型，转换带 from，finally 只清理
class PaymentFailed(Exception):
    pass

def charge(conn, order):
    try:
        return conn.execute(order)
    except TimeoutError as e:
        raise PaymentFailed("下游超时") from e   # 保留因果链，排查时看得到底层原因
    finally:
        conn.release()                           # 不写 return / break / continue


# 7. 不要用 __del__ 做清理：主路径走上下文管理器，finalize 只做兜底
class Session:
    def __init__(self, conn):
        self._conn = conn
        # 回调里不能引用 self，否则对象永远不会被回收，兜底反而变成泄漏
        self._closer = finalize(self, conn.close)

    def __enter__(self) -> "Session":
        return self

    def __exit__(self, *exc) -> None:
        self._closer()             # finalize 只会执行一次，重复调用是安全的


# 8. 相等与可哈希、金额、时间、编码：靠类型把约定固定下来
@dataclass(frozen=True, slots=True)              # frozen 同时给出 __eq__ 与 __hash__
class Money:
    amount: Decimal
    currency: str

price = Money(Decimal("19.99"), "CNY")           # Decimal 必须从字符串构造
total = (price.amount * 3).quantize(Decimal("0.01"), rounding=ROUND_HALF_UP)
created = datetime.now(timezone.utc)             # 一律 aware UTC，展示层才转本地
with open("data.csv", encoding="utf-8", newline="") as f:
    raw = f.read()

规则 / 规则组抓什么能否自动修建议

这一层不解释为什么，比如「为什么默认值只求值一次」「为什么 list 边遍历边删不报错」「为什么 __del__ 的时机不可依赖」，都在下面的原理层，按同样的顺序展开。

② 原理 · 默认参数与闭包：求值时机的两个坑

搞清这一节能解决的现象是：函数「有记忆」，第二次请求带上了第一次的数据。函数的默认值在函数定义时求值一次，之后所有调用共享同一个对象。所以 def f(x=[]) 里的那个 list 是整个进程共用的，调用之间会互相污染；def f(t=datetime.now()) 拿到的是进程启动那一刻的时间，永远不会变。

闭包则相反，它捕获的是变量本身而不是当时的值。循环里创建的 lambda 全都指向同一个循环变量，等到真正调用时，循环早已结束，它们读到的都是最后一个值。

from datetime import datetime, timezone

# ===== 坑 1：可变默认参数（ruff B006 能查出）=====
def add_bad(item, bucket=[]):        # 这个 list 在定义时创建一次，之后永久复用
    bucket.append(item)
    return bucket

add_bad(1)            # [1]
add_bad(2)            # [1, 2]  上一次的数据还在

def add_ok(item, bucket=None):       # 正确写法：哨兵值加函数内创建
    if bucket is None:
        bucket = []
    bucket.append(item)
    return bucket

# 同理，默认值里调用函数也是定义时求值一次（ruff B008）
def log_bad(msg, ts=datetime.now(timezone.utc)): ...    # ts 永远是进程启动时间
def log_ok(msg, ts=None):
    ts = ts or datetime.now(timezone.utc)

# ===== 坑 2：闭包捕获变量而非值（ruff B023 能查出）=====
funcs = [lambda: i for i in range(3)]
print([f() for f in funcs])          # [2, 2, 2] 全都拿到最后一个值

# 修法 A：用默认参数在定义时把值固定下来
funcs = [lambda i=i: i for i in range(3)]
# 修法 B：用 partial 显式绑定，语义更清楚
from functools import partial
funcs = [partial(lambda i: i, i) for i in range(3)]
print([f() for f in funcs])          # [0, 1, 2]
sequenceDiagram participant D as 模块导入时 participant F as 函数对象 participant C1 as 第一次调用 participant C2 as 第二次调用 D->>F: 执行 def 语句，求值默认参数表达式 D->>F: 创建那个空 list，存进 __defaults__ Note over F: 默认值从此固定，整个进程只有这一个对象 C1->>F: 不传 bucket，拿到 __defaults__ 里那个 list C1->>F: append 一个元素，直接改了默认值本身 C2->>F: 不传 bucket，拿到的还是同一个 list F-->>C2: 返回值里带着上一次调用留下的数据 Note over C1,C2: 现象是「函数有记忆」，在多请求服务里表现为数据串到别的用户

② 原理 · 拷贝、相等与可哈希

搞清这一节能解决的现象是：改了副本，原件跟着变；以及对象明明在集合里却查不到。

写法得到什么嵌套结构的表现适用
b = a同一个对象的另一个名字改 b 就是改 a只是起别名时
b = a[:] 或 list(a)浅拷贝，新外层容器内层元素仍是同一批对象，改 b[0][0] 会影响 a元素都是不可变值时
copy.copy(a)浅拷贝，等价于上一行同上自定义类的浅拷贝
copy.deepcopy(a)递归复制整棵引用图完全独立，循环引用也能正确处理确实需要隔离时；注意大结构上很慢，且会连带复制连接、锁这类不该复制的对象
[[0] * 3] * 2外层两个元素指向同一个内层 list改一行等于改所有行，经典矩阵初始化 bug永远不要这样建二维结构，用推导式

is 比较的是身份（内存地址），== 比较的是值。危险的地方在于：CPython 缓存了小整数（约 -5 到 256）和短的类标识符字符串，于是 a = 256; b = 256; a is b 是 True，换成 1000 就是 False；同一行里的字面量还可能被常量折叠成同一个对象，让交互式环境和脚本里的结果不一致。is 只能用于 None、True、False 和自定义哨兵这类单例，其余一律用 ==（ruff F632 会抓 is 比较字面量）。驻留的实现细节与它在性能上的正当用途（sys.intern）见CPython 实现细节。

flowchart TB Q0{"要比较什么"} -->|"和 None 或哨兵单例"| USE_IS["用 is，这是唯一正确场景"] Q0 -->|"和数字或字符串字面量"| USE_EQ["用 ==，用 is 只是碰巧对"] Q0 -->|"自定义对象的业务相等"| IMPL{"是否实现了 __eq__"} IMPL -->|"没有"| DEF["默认按身份比较，两个字段相同的对象也不相等"] IMPL -->|"实现了但没写 __hash__"| BROKEN["对象变成不可哈希，放进 set 或当 dict key 直接 TypeError"] IMPL -->|"实现了 __eq__ 和 __hash__"| OK["可以进 set 与 dict"] BROKEN --> FIX{"这个对象需要可哈希吗"} FIX -->|"需要"| H1["按不可变的关键字段实现 __hash__，且这些字段不能再改"] FIX -->|"不需要"| H2["保持不可哈希，别塞进 set"] OK --> WARN["注意：可变对象一旦入 set 后再改字段，哈希桶就找不到它了"]

相关的一条是可变对象不能当 dict key：list、dict、set 没有 __hash__，会直接抛 TypeError: unhashable type。需要用一组值当 key 时用 tuple 或 frozenset。反过来，@dataclass 默认生成 __eq__ 但不生成 __hash__，所以普通 dataclass 实例是不可哈希的，要么加 frozen=True，要么显式 eq=False。

② 原理 · 数值：除法、舍入与金额

搞清这一节能解决的现象是：对账差几分钱，而每一步看起来都没错。

陷阱现象原因正确写法
/ 与 //7 / 2 得 3.5，7 // 2 得 3Python 3 的 / 一律真除法返回 float，// 是向下取整要整数索引或分页用 //；注意负数是向下取整，-7 // 2 等于 -4 而不是 -3
round 的舍入方向round(0.5) 得 0，round(2.5) 得 2采用银行家舍入（四舍六入五成双），不是四舍五入需要传统四舍五入时用 Decimal 配 ROUND_HALF_UP 量化
浮点相等比较0.1 + 0.2 == 0.3 是 False二进制浮点无法精确表示十进制小数用 math.isclose(a, b, rel_tol=1e-9)
金额用 float累加一万笔后总额差几分钱，对账对不上每次运算都有舍入误差，且会累积金额一律 Decimal，数据库用 decimal 类型，接口传字符串
Decimal(0.1)得到一长串 0.1000000000000000055…先被解析成了 float 才转 Decimal必须从字符串构造：Decimal("0.1")
整数除法当取整int(-2.5) 得 -2，math.floor(-2.5) 得 -3int() 是向零截断，floor 是向下取整明确要哪种语义，别混用

② 原理 · 异常：四条容易吞掉真相的写法

搞清这一节能解决的现象是：客户端收到 500，服务端日志里什么都没有。

写法后果正确写法规则
裸 except:连 KeyboardInterrupt 与 SystemExit 一起吞掉，进程按 Ctrl-C 都停不下来，容器收到 SIGTERM 也退不干净捕获具体类型；兜底写 except Exception 并记 tracebackE722
except Exception as e 后在块外用 eNameError。Python 3 在 except 块结束时会把 e 删掉，以免它的 traceback 形成引用环需要带出去就先赋给另一个变量F821
finally 里 return 或 break正在传播的异常被直接丢弃，函数看起来正常返回，故障彻底消失finally 只做清理，不写控制流跳转B012
except X: raise Y() 不带 from原始异常仍会出现在「During handling of the above exception」里，但因果关系是隐式的；显式写 from e 表示由它引起，from None 表示故意切断raise Y() from eB904
 
import logging
logger = logging.getLogger(__name__)

# 反例集合
def bad(conn, payload):
    try:
        return conn.execute(payload)
    except:                      # 吞掉 KeyboardInterrupt 与 SystemExit
        return None              # 调用方拿到 None，完全不知道发生了什么
    finally:
        return "done"            # 致命：吞掉一切异常，连上面的 return 都被覆盖


# 正例
class PaymentFailed(Exception):
    pass

def good(conn, payload):
    try:
        return conn.execute(payload)
    except TimeoutError as e:
        # 转成领域异常时用 from e 保留因果链，排查时能看到底层原因
        raise PaymentFailed("下游超时") from e
    except Exception:
        # 兜底必须带 traceback，否则等于没记
        logger.exception("execute failed payload_id=%s", payload.id)
        raise
    finally:
        conn.release()           # 只做清理，不写 return / break / continue

② 原理 · 容器与序列：迭代中修改，以及 += 的双重身份

搞清这一节能解决的现象是：删除逻辑「漏掉了一半」，而代码看起来完全对称。迭代过程中修改容器，后果分两种：dict 和 set 会直接抛 RuntimeError: dictionary changed size during iteration，这算好事；而 list 不报错，只是静默跳过元素——删掉当前元素后，后面的元素整体前移，迭代器的下标却继续往后走，于是每删一个就漏检一个。正确做法是「构造新列表」或「倒序遍历」。

+= 对可变与不可变对象的行为完全不同：对 list 它调用 __iadd__ 就地扩展（等价于 extend，会影响所有引用这个 list 的地方）；对 tuple、str、int 这些不可变类型，它只能新建对象再重新绑定名字。由此产生一个经典报错：元组里装了一个 list，对它做 += 会先改成功、再抛异常。

# ===== 迭代中修改 =====
items = [1, 2, 2, 3, 2, 4]
for x in items:              # 反例：边遍历边删
    if x == 2:
        items.remove(x)      # 不报错，但会漏掉紧跟其后的 2
print(items)                 # [1, 3, 4] 看似对了，换数据就不对

items = [1, 2, 2, 3, 2, 4]
items = [x for x in items if x != 2]      # 正例：构造新列表，意图也更清楚
# 必须原地修改时倒序遍历，或者用切片整体赋值
for i in range(len(items) - 1, -1, -1):
    if items[i] == 2:
        del items[i]

# ===== += 的双重身份 =====
a = [1, 2]
b = a
a += [3]                     # 就地扩展，b 也跟着变成 [1, 2, 3]
print(b)                     # [1, 2, 3]

a = (1, 2)
c = a
a += (3,)                    # 不可变，新建元组后重新绑定，c 仍是 (1, 2)
print(c)                     # (1, 2)

t = ([1], [2])
try:
    t[0] += [9]              # 经典陷阱
except TypeError:
    pass
print(t)                     # ([1, 9], [2])  元素已经被改了，异常来自后续的赋值动作

② 原理 · 作用域与导入

搞清这一节能解决的现象是：报错行在赋值语句之前，或者整个项目因为一个文件名挂掉。

现象原因正确写法
函数里读一个全局变量报 UnboundLocalError函数体内任何位置对它赋值，整个函数里它就被判定为局部变量，读取时还没赋值只读就别赋值；要改全局用 global，要改外层函数的变量用 nonlocal
类体里的推导式读不到类属性类体的作用域不参与闭包，推导式有自己的作用域，只有最外层可迭代对象在类作用域求值把常量提到模块级，或在方法里计算
global 用得到处都是本质是用模块状态代替参数传递改成显式传参或类属性，ruff 的 PLW0603 会提示
脚本直接运行时 from . import x 报 ImportError直接运行文件时该模块的包上下文为空，相对导入没有基准用 python -m pkg.module 运行，或把入口做成命令行脚本
自己写的 logging.py 让整个项目挂掉脚本所在目录在搜索路径最前面，同名模块直接遮蔽标准库别用标准库名做模块名；用 src 布局能大幅降低这类风险，ruff A005 可检出
__init__.py 里堆满导入导入任意子模块都会拉起整个包，容易形成循环引用保持为空或只导出少量公开符号

② 原理 · 时间与编码：两个最贵的默认值

搞清这一节能解决的现象是：时间「差了几个小时」，而这种错法能通过全部单测。datetime 分 naive（不带 tzinfo）和 aware（带 tzinfo）两种。二者不能相互比较也不能相减，会抛 TypeError。更麻烦的是 naive 时间本身没有含义：同一个 naive 值在不同机器上代表不同的时刻，跨时区部署、夏令时切换、数据库时区配置不一致时全都会出问题。

flowchart TB IN["外部输入的时间字符串"] --> P{"带时区偏移吗"} P -->|"带，如 Z 或 加零八零零"| A1["解析成 aware，立刻转成 UTC"] P -->|"不带"| A2["必须问清它是哪个时区，补上 tzinfo 再转 UTC"] A1 --> STORE["统一以 UTC aware 存储与运算"] A2 --> STORE STORE --> CMP["比较与相减只在 UTC 之间做"] STORE --> OUT["仅在展示层按用户时区格式化"] BAD["用 datetime.now 拿本地 naive 时间"] -.->|"典型事故源"| WRONG["和 aware 值比较抛 TypeError
或者静默差几个小时"] BAD2["用 utcnow 拿到的是 naive 的 UTC"] -.->|"同样危险"| WRONG 
from datetime import datetime, timezone
from decimal import Decimal, ROUND_HALF_UP
from zoneinfo import ZoneInfo

# 时间：一律 UTC aware，展示层才转本地
now = datetime.now(timezone.utc)              # 正确：aware
# now = datetime.utcnow()                     # 错误：拿到的是 naive 的 UTC，最容易混
shown = now.astimezone(ZoneInfo("Asia/Shanghai")).strftime("%Y-%m-%d %H:%M")

# 金额：从字符串构造 Decimal，量化时显式指定舍入方式
price = Decimal("19.99") * 3
total = price.quantize(Decimal("0.01"), rounding=ROUND_HALF_UP)   # 59.97

# 文件编码：必须显式写 encoding。不写时用的是平台默认值，
# 老版本 Windows 上可能是 cp936/GBK，同一份代码读同一个文件结果不同
with open("data.csv", encoding="utf-8", newline="") as f:
    content = f.read()

# 需要容忍脏数据时显式声明策略，而不是让它在生产抛 UnicodeDecodeError
with open("legacy.log", encoding="utf-8", errors="replace") as f:
    for line in f:
        handle(line)

编码的规则很短：str 是文本、bytes 是字节，边界处显式 encode / decode；所有 open 都要写 encoding="utf-8"。Python 3.15 起默认编码会转为 UTF-8，但在那之前，不写 encoding 的代码在不同平台上行为不同，而这类 bug 通常在处理到一条中文数据时才爆发。ruff 的 PLW1514 能把所有漏写的地方一次列出来。

② 原理 · 析构：__del__ 的时机为什么不可依赖

搞清这一节能解决的现象是：文件句柄或连接「大部分时候」会释放，偶尔耗尽；以及 __del__ 里的错误在日志系统里完全查不到。CPython 的引用计数确实能做到「计数归零立即调用 __del__」，问题在于这条保证的适用范围比大多数人以为的窄得多。

你以为的实际行为该用什么
离开作用域就会调用只要还有一处引用就不会调用，异常的 traceback、日志记录、缓存都可能持有它with 语句，把释放时机写成代码结构而不是靠推断
循环引用里的对象也会按顺序析构3.4 起带 __del__ 的循环引用组可以被回收，但组内调用顺序不确定，析构里访问兄弟对象可能拿到半销毁状态把清理逻辑从析构里搬出来，改成显式 close()
进程退出时一定会执行解释器关闭阶段不保证所有 __del__ 都被调用，模块全局此时可能已被置为 Noneatexit 注册关闭钩子，或由上层框架的生命周期管理
__del__ 里抛的异常能被捕获异常被忽略，只在 stderr 打一行 Exception ignored in，结构化日志与告警链路完全看不到清理逻辑放 __exit__ 或 finally，那里的异常是可控的
换个实现也一样PyPy 等实现没有引用计数，析构时机完全不同，依赖它的代码迁移时才暴露不依赖时机；需要兜底用 weakref.finalize

weakref.finalize 与 __del__ 的关键差别是：它把清理动作与对象解耦，回调里不持有对象本身（所以不会像 __del__ 那样意外延长生命周期），并且在解释器退出时会被尽量执行。但它仍然只是兜底——真正可靠的资源释放只有一种形态，就是把生命周期写进 with。忘写 with 的地方交给 python3 -X dev：它会把 ResourceWarning 打出来，配合 -W error 就能在 CI 里变成失败。

③ 场景 · 哪些交给门禁、哪些必须靠人

这张图是上面所有条目的归类：能静态检出的一律进 CI，剩下的才需要人的注意力。

门禁开到什么程度，取决于项目形态。一次性全开对新项目是零成本，对十万行老项目则会直接让评审瘫掉：

项目形态怎么落地为什么代价
新项目第一个 commit 就把 E,F,B,A,SIM,TRY,DTZ,PLW,RUF 全开，CI 阻断存量为零，此时开规则的成本最低初期会被挡几次，熟悉规则要一两天
万行级存量项目先 ruff check --statistics 出基线，只开 B006/B008/B023/E722/B012/B904/F632，历史代码用 --add-noqa 冻结先挡住「会造成故障」的那几类，其余分批推noqa 是技术债，必须排期清，否则永久留着
对外发布的库或 SDK额外开 A005 与 DTZ，公开 API 上跑 mypy 严格档下游踩到的每个坑都会变成你的 issue 与支持成本发布流程变重，类型标注要长期维护
数据脚本与 notebook只开 B006/B008/B023/PLW1514，不上 mypy 严格档生命周期短，唯一要保的是「结果不能算错」一部分坑只能靠结果校验发现
计费、对账、金额相关模块把 Decimal 与时区约定写进类型（frozen dataclass 或 NewType），评审必看精度与时区语义是工具永远查不出来的一类多写一层模型转换代码
跨时区或多地域业务DTZ 组全开，存储层强制 aware UTC，展示层单独转换naive 时间的错法是「差几小时」，能通过全部单测每个出口都要显式转换，代码更啰嗦
高并发长驻服务迭代中修改与可变全局的相关单测带并发用例；-X dev 跑一轮集成测试静默跳过元素与句柄泄漏都只在压力下暴露测试变慢，要维护一套压力用例

不适用边界：完整的 ruff 与 mypy 配置、pre-commit 与 CI 的分工在Python 依赖与工程工具链；这些写法在性能上的含义（+= 拼接的二次复杂度、pop(0)、字符串驻留）在CPython 实现细节；对象模型、引用计数与 GC 在Python 运行时机制；多线程下的竞态与「看起来像语义坑」的并发问题不在这里，见Python 并发的三条路线与选择；框架层的坑（依赖注入的缓存范围、响应模型的字段过滤）在FastAPI 的机制与生产化。如果一个问题只在多个进程或多个请求同时发生时出现，它不是本篇覆盖的语义陷阱。

这条路径上，上一篇解释解释器为什么这么跑，本篇只管「结果对不对」，下一篇把视角从单个文件抬到版本与生态：同样的代码换个解释器、换个小版本，哪些假设会不成立。

最容易踩的坑

❌
避坑清单
  • def f(x=[]) 或 def f(t=datetime.now())：默认值在定义时求值一次，之后所有调用共享，在服务里表现为数据串到别的用户。
  • 循环里创建 lambda 或闭包直接引用循环变量：调用时全都拿到最后一个值，用默认参数或 partial 固定。
  • 用 a[:] 拷贝嵌套结构：内层还是同一批对象，改副本会影响原件。
  • [[0] * 3] * 2 建二维结构：两行指向同一个 list，改一行等于改全部。
  • 用 is 比较数字或字符串：小整数与字符串驻留让它偶然为 True，数据一变就崩。
  • 实现了 __eq__ 却不实现 __hash__：对象变成不可哈希，进 set 或当 dict key 时直接 TypeError。
  • 可变对象入 set 之后再改它的字段：哈希值变了，桶里再也找不到它，表现为「明明在集合里却查不到」。
  • 金额用 float 累加：一万笔之后对账差几分钱；Decimal(0.1) 也是错的，必须从字符串构造。
  • 以为 round 是四舍五入：它是银行家舍入，round(2.5) 等于 2。
  • 裸 except: 或在 finally 里 return：前者吞掉 Ctrl-C 和 SIGTERM，后者吞掉正在传播的异常。
  • 边遍历 list 边删元素：不报错，静默跳过元素，每删一个漏检一个；遍历 dict 时忘了用 list(d) 拍快照则会抛 RuntimeError。
  • 对元组里的 list 做 +=：元素已经被改了，异常才抛出来，状态处于半修改态。
  • 把资源清理写进 __del__：只要还有一处引用（哪怕是异常的 traceback）就不会执行，句柄泄漏偶发出现。
  • 在 __del__ 里记日志或抛异常：异常被静默忽略，只在 stderr 留一行 Exception ignored in，告警链路完全看不到。
  • 用 weakref.finalize 时在回调里引用对象自身：对象永远不会被回收，兜底手段反倒成了泄漏源。
  • 函数里给全局变量赋值却忘了 global：报 UnboundLocalError，而报错行往往在赋值语句之前。
  • 用 datetime.utcnow()：它返回的是 naive 时间，和 aware 值比较会抛 TypeError，存进库后时区信息彻底丢失。
  • 把文件名起成 logging.py、json.py、types.py：同名模块遮蔽标准库，报错信息完全指不到真正原因。
  • open() 不写 encoding：依赖平台默认编码，换机器或遇到中文数据才炸。
  • 测试环境不开 -X dev：ResourceWarning 被默认忽略，忘关的文件与连接一路带到生产。
