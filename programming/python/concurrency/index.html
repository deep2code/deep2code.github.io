Python 并发的三条路线与选择

🏷️ Python

GIL 的精确含义、三种并发模型的宏观取舍与部署形态，在Python 做后端的适用边界与运行时约束里已经讲过，这篇不重复那些结论，只做一件事：把 threading、multiprocessing、asyncio 这三条路线的具体写法与工程细节摊开——每条路线的标准骨架、平台差异，以及三者混用时那些「本地跑得好、服务器上崩」的边界。

① 用法 · 三条路线的最小骨架与选路表

会写 Python 的人缺的不是 async 语法，是「这类任务的标准骨架长什么样」。下面三段是生产里反复出现的形态，注释只说明为什么要这一行，机制解释在原理层。

import asyncio
import multiprocessing as mp
from concurrent.futures import ProcessPoolExecutor, ThreadPoolExecutor, as_completed


# 路线一：IO 为主但只有同步驱动 —— 线程池
def fan_out_sync(urls: list[str]) -> list[int]:
    out: list[int] = []
    # max_workers 不要随手填 100：目标并发 = 目标 QPS × 平均耗时秒数，再用下游连接上限封顶
    with ThreadPoolExecutor(max_workers=32, thread_name_prefix="fetch") as pool:
        futs = {pool.submit(fetch_one, u): u for u in urls}
        for fut in as_completed(futs):
            try:
                out.append(fut.result())   # 不取 result，异常会被静默吞掉：日志干净而数据已错
            except Exception:
                logger.exception("fetch failed url=%s", futs[fut])
    return out


# 路线二：纯 Python 的 CPU 计算 —— 进程池
# 任务函数必须在模块顶层：spawn 下靠「模块名加函数名」重新导入才能拿到它
def cpu_task(chunk: list[int]) -> int:
    return sum(x * x for x in chunk)


def init_worker() -> None:
    # 每个子进程启动时执行一次，重建绝对不能从父进程继承的东西
    engine.dispose(close=False)   # close=False：不碰父进程那条 socket，只丢弃本进程的池


def run_cpu(chunks) -> int:
    ctx = mp.get_context("spawn")     # 显式指定启动方式，不吃平台默认值
    with ProcessPoolExecutor(max_workers=4, mp_context=ctx, initializer=init_worker) as pool:
        # chunksize 按任务粒度给：任务太碎时 pickle 往返会吃掉全部并行收益
        return sum(pool.map(cpu_task, chunks, chunksize=8))
    # 调用方入口必须放在 if __name__ == "__main__" 之下，否则 spawn 会无限递归起子进程


# 路线三：IO 为主且整条链路都有异步驱动 —— asyncio
async def fan_out_async(urls: list[str]) -> list[int]:
    sem = asyncio.Semaphore(32)          # 不限并发就是无界 fan-out，先被打爆的是下游
    results: list[int] = []

    async def one(u: str) -> None:
        async with sem:
            async with asyncio.timeout(2):   # 3.11 起可用；每个子任务都要有自己的超时
                results.append(await client.get_status(u))

    async with asyncio.TaskGroup() as tg:    # 3.11 起：任一子任务抛错，兄弟任务一并被取消
        for u in urls:
            tg.create_task(one(u))           # 由 TaskGroup 持有引用，不会被 GC 悄悄回收
    return results

② 原理 · threading：锁的种类与线程池的正确姿势

搞清这一节能解决的现象是：用 sleep 轮询等状态、或者某次异常之后整个服务永久挂住。threading 提供五种同步原语，多数人只用 Lock，结果把本该用 Condition 或 Semaphore 表达的语义写成了轮询加 sleep。

原语语义该用它的场景误用的后果
Lock二元互斥，不可重入保护一小段临界区同一线程递归获取会立刻自锁，且没有任何提示
RLock可重入，记录持有线程与计数加锁的方法内部会调用另一个也要加锁的方法拿它掩盖糟糕的调用结构，临界区越滚越大
Condition等待条件成立，配合 notify 唤醒生产者消费者、等待状态变更改用 sleep 轮询检查标志位，延迟和 CPU 都白花
Semaphore计数信号量，限制并发数限制同时打到下游的请求数、连接数用锁加计数器手写，漏减一次就永久饿死
Event一次性广播标志通知所有工作线程退出用全局布尔变量加轮询，退出不及时

不管用哪种，获取锁必须走 with 上下文管理器。手写 acquire() 加 release() 时，只要临界区内抛了异常，release 就不会执行，程序会在下一次获取时永久挂住——而且挂住的位置离真正的 bug 现场很远，几乎无从排查。

import threading
from concurrent.futures import ThreadPoolExecutor, as_completed

# 限制打到下游的并发数：用 Semaphore 表达「最多 10 个在飞」
downstream = threading.Semaphore(10)
stats_lock = threading.Lock()
stats = {"ok": 0, "fail": 0}


def fetch_one(url: str) -> int:
    with downstream:                 # 超过 10 个时在这里排队，而不是压垮下游
        status = do_http_get(url)    # 同步阻塞调用，等待期间会释放 GIL
    with stats_lock:                 # 必须用 with：临界区抛异常也能保证释放
        stats["ok" if status < 400 else "fail"] += 1
    return status


# max_workers 怎么定：IO 密集的经验公式是 目标并发数 = 目标 QPS 乘以平均耗时秒数。
# 要撑 200 QPS、下游平均 150ms，则约需 30 个在飞请求，池给 32 足够。
# 不要随手填 100：线程栈、下游连接数、数据库连接池都是被它放大的成本。
with ThreadPoolExecutor(max_workers=32, thread_name_prefix="fetch") as pool:
    futures = {pool.submit(fetch_one, u): u for u in urls}
    for fut in as_completed(futures):
        try:
            fut.result()             # 关键：不取 result，异常会被静默吞掉
        except Exception:
            logger.exception("fetch failed url=%s", futures[fut])

线程池最常见的隐性 bug 是不取 future.result()。submit 里抛出的异常会被存进 future，如果没人读它，异常就彻底消失，日志干干净净而数据已经错了。pool.map 同理：异常在迭代到那个元素时才抛出，只调用不遍历结果，等于什么都没发生。

② 原理 · 死锁的两种成因与线程本地存储

搞清这一节能解决的现象是：服务偶发整体挂住、以及日志里的 request_id 在高并发时串号。死锁在实践中只有两个来源：加锁顺序不一致（线程 A 持 1 求 2，线程 B 持 2 求 1）和持锁期间做了会阻塞的外部操作（持锁发 HTTP 请求或等队列，下游一慢就全线挂住）。前者靠「全局统一的加锁顺序」规避，后者靠「临界区里只做内存操作」规避。真卡住时用 py-spy dump --pid PID 打出所有线程栈，谁停在 acquire 上一目了然。

另一个高频坑是线程本地存储。threading.local() 按线程隔离数据，在传统的「一请求一线程」模型下可以用来存 request_id、当前用户；但换到 asyncio 之后它就失效了——同一个线程上交替跑着成百上千个协程，它们共享同一份 thread-local，日志串号、权限串用都是这么来的，而且只在并发升高时才出现。

对比项threading.local()contextvars.ContextVar
隔离粒度线程上下文（每个 Task 自动拷一份快照）
多线程下正确正确（各线程有独立上下文）
asyncio 下串号，同线程所有协程共享一份正确，create_task 时继承父上下文
传给执行器不传递，子线程读到空值asyncio.to_thread 自动带过去，裸 run_in_executor 需手动 copy_context
结论纯同步的老代码可继续用新代码一律用它，两种模型下都对

② 原理 · multiprocessing：启动方式决定了「本地好、线上崩」

搞清这一节能解决的现象是：同一份代码在 macOS 正常、在 Linux 卡死，或者反过来。fork 直接复制父进程地址空间，速度快、子进程继承全部对象；spawn 从零起一个新解释器，只把可 pickle 的参数传过去；forkserver 先 fork 出一个干净的单线程服务进程，之后由它来 fork 工作进程，兼顾速度与安全。

启动方式默认平台子进程继承什么启动耗时危险点
forkLinux 上是历史默认；3.14 起在多线程进程中不再默认使用全部内存、已打开的描述符、锁的状态、连接最快，毫秒级父进程只要有第二个线程就不安全：可能复制到一把已被别的线程持有、且永远不会被释放的锁
spawnWindows 与 macOS 一直是默认，3.14 起 Linux 多线程场景也转向它只有可 pickle 的参数，模块会被重新导入最慢，百毫秒级（要重新 import）入口漏写主模块保护会递归创建子进程；闭包、lambda、局部类全传不过去
forkserver需显式设置，仅 Unix服务进程建立那一刻的干净状态中等服务进程的快照时机必须早于任何连接的建立

典型事故：本地 macOS 开发走 spawn，一切正常；上线 Linux 走 fork，而父进程里有个日志上报线程或指标线程，fork 出的子进程在第一次打日志时直接卡死。反方向也有：Linux 上依赖 fork 继承了全局变量，搬到 macOS 后那个全局变量在子进程里是空的。解法是显式指定启动方式，不要吃平台默认值。

import multiprocessing as mp
from concurrent.futures import ProcessPoolExecutor

# 必须是模块级顶层函数：spawn 下要能靠「模块名加函数名」重新导入拿到它
def cpu_task(chunk: list[int]) -> int:
    return sum(x * x for x in chunk)


def init_worker() -> None:
    # 每个子进程启动时执行一次：重建那些绝对不能从父进程继承的东西
    engine.dispose(close=False)   # close=False 表示不碰父进程那条 socket，只丢弃本进程的池
    reset_signal_handlers()       # 子进程要自己处理 SIGTERM，否则优雅关闭形同虚设


if __name__ == "__main__":         # spawn 下没有这行会无限递归起子进程
    ctx = mp.get_context("spawn")  # 显式指定，不依赖平台默认值
    with ProcessPoolExecutor(
        max_workers=mp.cpu_count(),   # CPU 密集按核数，给再多也只是排队
        mp_context=ctx,
        initializer=init_worker,
    ) as pool:
        # chunksize 很关键：任务太碎时每个任务都要 pickle 一轮，开销会盖掉并行收益
        total = sum(pool.map(cpu_task, chunks, chunksize=8))
    print(total)

② 原理 · 进程间通信的四种方式与 pickle 约束

搞清这一节能解决的现象是：并行之后总耗时反而变长，以及「不能 pickle 局部对象」这类报错。

方式适合的数据开销注意
Queue / Pipe中小结构化对象，任务与结果每次一轮 pickle 加一次内存拷贝队列满时 put 会阻塞；子进程没退干净会让主进程 join 挂住
shared_memory大块二进制、numpy 数组零拷贝，只传名字生命周期要自己管，漏 unlink 会残留；并发写仍要自己加锁
Value / Array少量定长标量与数组很低只支持 ctypes 类型，复杂对象放不进去
文件或对象存储超大中间结果磁盘 IO，但可跨机数据量大到 pickle 不划算时，反而是最简单可靠的方案

ProcessPoolExecutor 的所有参数和返回值都必须可 pickle，这条限制比想象中更硬：lambda 不行、嵌套函数不行、functools.partial 包住 lambda 也不行、数据库连接和打开的文件对象不行、内部带线程锁的对象不行。报错通常是「不能 pickle 局部对象」或「不能 pickle thread.lock 对象」。修法只有一条：把任务函数提到模块顶层，需要的配置用可 pickle 的简单参数传进去，或者放进 initializer 里在子进程内部自己建。

更隐蔽的是 fork 继承连接。父进程已经建好的数据库连接，fork 后父子共用同一个 socket，而服务端只认一条会话，两边同时读写就会撞在一起。

sequenceDiagram participant M as 父进程 participant DB as 数据库 participant C as 子进程 M->>DB: 建连接完成握手，socket 描述符就绪 M->>C: fork 复制地址空间，描述符一并继承 Note over M,C: 两个进程持有同一个 socket，服务端只认一条会话 C->>DB: 发送查询 A M->>DB: 同时发送查询 B DB-->>M: 响应报文交错，协议状态错乱 DB-->>C: 报文被对方读走，报 SSL error 或游标状态异常 Note over C: 修法是子进程启动后先 dispose 引擎，各自新建连接

同一条规则适用于 Redis 客户端、HTTP 连接池、gRPC channel，以及 gunicorn 的 preload_app：任何带 socket 的东西都不能跨 fork 复用，必须在子进程里重建（部署侧的表现见Python Web 服务的部署形态）。

② 原理 · 混用的边界：run_in_executor 与在线程里跑事件循环

搞清这一节能解决的现象是：加了执行器之后仍然卡、或者报「绑定到了另一个事件循环」。asyncio 自身的阻塞判定、gather 与 TaskGroup、取消语义详见站内asyncio 的性能陷阱，这里只讲跨模型的接缝。唯一正规的接缝是 loop.run_in_executor（3.9+ 更推荐 asyncio.to_thread），把同步代码丢到池里跑。选线程池还是进程池，判断标准只有两条：会不会释放 GIL、参数能不能 pickle。

要跑的东西选哪个池理由
同步 HTTP 客户端、同步数据库驱动、文件读写线程池阻塞在系统调用上会释放 GIL，线程数就是有效并发数
numpy / pandas / 图片编解码 / 压缩线程池底层 C 代码主动释放了 GIL，已经是真并行，没必要付进程开销
纯 Python 的计算循环、超大 JSON 解析进程池全程持有 GIL，放线程池等于串行还多一层调度
参数里带连接、文件句柄、闭包只能线程池pickle 传不过去
可能跑很久且要能强行终止进程池线程无法从外部杀掉，进程可以
 
import asyncio
from concurrent.futures import ProcessPoolExecutor

CPU_POOL = ProcessPoolExecutor(max_workers=4)   # 进程池要全局复用，别在函数里现建


async def handle(req):
    # 1) 同步 IO 库：线程池。to_thread 会自动带上 contextvars 上下文
    rows = await asyncio.to_thread(legacy_sync_query, req.user_id)

    # 2) 纯 Python 的 CPU 计算：必须进程池，否则整个事件循环被 GIL 拖住
    loop = asyncio.get_running_loop()
    report = await loop.run_in_executor(CPU_POOL, build_report, rows)

    # 3) 给阻塞调用套超时：注意 wait_for 只能让 await 处提前返回，
    #    池里那个线程仍会跑到底，所以必须同时给底层库自己的 timeout 参数
    try:
        extra = await asyncio.wait_for(asyncio.to_thread(slow_call), timeout=2.0)
    except TimeoutError:
        extra = None
    return report, extra

反方向——在线程里跑 asyncio——几乎总是坑。asyncio.run() 会为当前线程新建一个事件循环，于是每个线程一个循环，循环之间不能互相 await，共享的 client 和连接池跨循环使用会报「绑定到了另一个事件循环」。跨线程往循环里投递任务只有一个正确入口：asyncio.run_coroutine_threadsafe(coro, loop)，它返回的是 concurrent.futures.Future 而不是 asyncio 的 Future，不能 await，只能用 result(timeout=...) 取。

③ 场景 · 选择决策：先问单线程够不够

最该纠正的观念是「并发等于更快」。引入并发的代价是可观测性骤降、错误处理复杂度上升、部署形态变复杂。很多所谓的并发需求，用一条批量 SQL 替掉 N 次单条查询、加一层缓存、或者把循环里不变的属性查找提到循环外就解决了——先量出瓶颈在哪，再决定要不要并发。

任务类型有异步库需要共享可变状态选择
IO 密集是否asyncio，单进程即可撑上万连接
IO 密集否是ThreadPoolExecutor，共享状态加锁
IO 密集部分有否asyncio 主链路加 to_thread 包住同步部分

③ 场景 · 反模式与不适用边界

反模式会发生什么正确做法
用多线程解决 CPU 密集比串行更慢：并行度为零，还多了 GIL 争用与切换进程池，或先看能不能向量化
fork 后复用父进程的数据库连接随机报 SSL error、游标状态异常，压力越大越频繁initializer 里 engine.dispose() 重建
进程池传 lambda 或闭包pickle 直接失败；本地 fork 侥幸能过，线上 spawn 必崩任务函数提到模块顶层
asyncio 里用 threading.local 存上下文日志 request_id 串号，偶发的权限串用换 contextvars.ContextVar
线程池大小随手填 100放大下游压力，数据库连接被打满，内存和切换成本白付按「目标 QPS 乘平均耗时」估算，再压测校准
submit 后不取 result()异常被吞，日志干净而数据已错用 as_completed 逐个取结果并记日志
手写 acquire() 与 release()临界区抛异常后锁永久不释放一律 with lock
持锁期间发 HTTP 请求下游一慢，所有线程堵在同一把锁上临界区只做内存操作，IO 挪到锁外

不适用边界：并发解决不了「单个操作本身慢」——对象开销、GC 毛刺、属性查找这类常数成本在Python 运行时机制与CPython 实现细节；进程数与 worker 形态、优雅退出属于部署层，在Python Web 服务的部署形态；取消语义、gather 与 TaskGroup 的差异、阻塞源分类在asyncio 的性能陷阱；GIL 的宏观取舍与语言选型在Python 做后端的适用边界与运行时约束；语义层面的坑（可变默认参数、闭包延迟绑定）在Python 的语义陷阱清单。

最容易踩的坑

❌
避坑清单
  • 不显式设置启动方式，吃平台默认值：macOS 是 spawn、Linux 历史是 fork，同一份代码两种行为，本地测不出来。
  • 父进程里有后台线程（日志上报、指标、健康检查）还用 fork：子进程可能复制到一把永远不会被释放的锁，第一次打日志就卡死。
  • 多进程入口漏写主模块保护：spawn 会重新导入模块，于是无限递归创建子进程，几秒内打满机器。
  • 把进程池建在请求处理函数里：每个请求起一批进程，启动开销远大于计算本身。池必须全局复用。
  • 子进程内存不留余量：被 OOM killer 杀掉后整个池变 broken，之后所有提交立刻失败，而池不会自愈。
  • pool.map 只调用不遍历结果：任务里的异常永远不会抛出来，等于静默失败。
  • chunksize 用默认值处理几十万个小任务：pickle 往返次数把并行收益全吃掉，甚至比串行慢。
  • 用 sleep 轮询等待条件成立：该用 Condition 或 Event，轮询的延迟和空转都是白付的。
  • 加锁顺序不统一：两个线程各持一把锁求对方的锁，死锁且几乎不可复现，只能靠 py-spy dump 打栈才看得见。
  • shared_memory 用完不 unlink：进程退出后共享段还留在共享内存里，攒多了把内存吃光。
  • 在多个线程里各自 asyncio.run() 却共享同一个 HTTP client：报「绑定到另一个事件循环」，跨线程投递只能用 run_coroutine_threadsafe。
  • 给 to_thread 套 wait_for 就以为超时生效：超时只让 await 处返回，池里那个线程照样跑到底，线程会被慢慢耗尽。
  • 用裸 create_task 起后台任务却不留引用：任务可能被 GC 回收，表现为「有时候跑了有时候没跑」，用 TaskGroup 或自己持有引用。
