虚拟环境到底隔离了什么，又没隔离什么

python -m venv .venv 做的事情比大多数人想象的少：创建一个目录，写一份 pyvenv.cfg（里面的 home 指向创建它的那个解释器），把 bin/python 做成指向 base 解释器的符号链接（Windows 或者加了 --copies 时是拷贝），再建一个空的 site-packages。进程启动时 site 模块读 pyvenv.cfg，把 sys.prefix 指到虚拟环境，而 sys.base_prefix 仍留在原解释器——标准库是从 base 加载的。

结论很朴素：虚拟环境隔离的是第三方包的搜索路径，不是一套完整的 Python，更不是一层沙箱。下面这张表是排查「我这儿能跑」类问题的检查单。

维度是否被 venv 隔离没隔离时的典型症状
第三方包 site-packages是这是 venv 唯一真正解决的问题
标准库否，共享 base 解释器系统把 base Python 升级或卸载后，venv 整体不可用
解释器版本否，创建时就绑定了pyenv 删掉旧版本后，venv 里的 python 变成死链接
用户级 site（~/.local/lib）默认关闭（include-system-site-packages = false 且禁用 user site）venv 外执行脚本时仍会加载，产生「同一台机器两种行为」
PYTHONPATH否宿主的 PYTHONPATH 把外部包插进 sys.path，锁文件再精确也复现不出来
系统 C 库（glibc、OpenSSL、libstdc++）否导入时报缺少 GLIBC_2.28、或 cryptography 找不到 libssl 符号
编译器与头文件否同一份依赖清单在有 gcc 的开发机装得上，CI 的 slim 镜像里失败
环境变量（索引地址、代理、PIP_*）否本机走私有源解出 A 版本，CI 走公网解出 B 版本
命令行入口（console_scripts）是，但 shebang 写的是绝对路径移动或重命名 venv 目录后所有命令报 bad interpreter
发行版 dist-packages取决于 --system-site-packages打开后 apt 装的旧版本包会遮蔽 venv 里的新版本

三条自查命令：python -c "import sys; print(sys.prefix, sys.base_prefix)" 判断当前是否真在 venv 里（两者相同说明没有激活）；python -m site 打印完整 sys.path 与 user-site 状态；pip -V 的输出末尾会带上它所属的 site-packages 路径，这是判断「我 pip install 的东西装到哪去了」最快的办法。容器里还要多看一眼 ldd 的结果，导入期的符号缺失全部来自这一层。

requirements.txt 不是 lock 文件

锁文件的定义是「给定同一个目标环境，能还原出逐字节相同的依赖集合」。要做到这点需要四样东西：完整的依赖闭包、每个分发文件的哈希、这次求解所针对的环境标记、以及直接依赖与传递依赖的区分。requirements.txt 的文本格式能承载前两项，但工具不强制、也不区分第四项，所以它在实践中基本上不是锁文件。

形态记录了什么缺什么什么时候咬人
手写带区间的清单（fastapi>=0.110）直接依赖与意图传递依赖版本、哈希、平台标记上游发新版的当天 CI 变红，且和代码改动无关
pip freeze 快照当前环境全部包的精确版本直接与传递的区分、哈希、marker；还会写进只在本平台存在的包和本地可编辑路径换平台装不上；半年后没人知道哪一行可以删
pip-compile --generate-hashes全闭包、精确版本、哈希、来源注释只对一组「Python 版本 × 平台」有效Mac 开发、Linux 部署的团队各自编译出两个文件
uv.lock / poetry.lock闭包、哈希、marker，以及与声明文件的一致性关系需要同族工具读取，不能直接喂给 pip改了 pyproject 忘记重新 lock 时会被 --frozen 拦下（这是好事）

同一个 pip install -r requirements.txt 今天和下个月装出不同结果，只有三个原因：未固定的传递依赖被解成了新版本；索引上出现新版本或某个版本被 yank；环境标记（Python 版本、操作系统、平台）变了导致条件依赖的取舍不同。把这三条堵住就得到了可复现，堵不住就别指望锁定。

pyproject.toml 与 PEP 517 / 518 / 621 的分工

很多人把 pyproject.toml 当成「新版 setup.py」，其实它是若干互相独立的 PEP 叠在同一个文件里，各管一段。

PEP定义什么工程含义
518[build-system].requires 与构建隔离环境构建时另建临时环境安装 requires。没给上界的话，某天新版 setuptools 就会改变你的构建结果
517后端钩子 build_wheel、build_sdist、get_requires_for_build_*构建不再依赖 setup.py 命令行，后端可换成 hatchling、flit、pdm-backend、maturin、scikit-build-core
621[project] 表：name、version、dependencies、optional-dependencies、scripts元数据变成静态可读，求解器不执行任意代码就能拿到依赖——这是快的前提。用了 dynamic 就退回执行代码
660可编辑安装的标准钩子pip install -e 不再走 setup.py develop 与 egg-link，行为在各后端间一致
735[dependency-groups]开发依赖终于有了标准位置。塞进 optional-dependencies 的那些会作为 extras 发布出去，是过去的常见误用
440 / 508版本号与依赖说明符语法（含 environment markers）~=、==1.2.*、预发布规则、; python_version < "3.13" 的语义都在这里

依赖求解为什么比想象中难

Python 的安装模型是「一个环境里同一个包只能有一个版本」，没有 npm 那种嵌套 node_modules 的逃生通道。这让依赖求解变成一个全局约束满足问题，最坏情况是指数级的。pip 从 20.3 才默认启用回溯求解器；在那之前是「先到先得」，会静默装出互相不兼容的组合——这也是为什么老项目里常见「明明装成功了但 import 报错」。

更麻烦的是元数据的获取代价。wheel 的依赖声明躺在 zip 包里的 METADATA 文件中，可以靠 HTTP range 请求只取那一段；而源码分发（sdist）在标准上必须调用构建后端才能知道依赖，也就是说求解过程可能需要执行任意代码。再叠加 environment markers 和 extras，同一份声明在不同平台上的解可以完全不同——这就是「跨平台锁文件」必须对多组标记同时求解的原因。

pip / poetry / pdm / uv 的求解与锁定差异

工具锁产物锁的作用域哈希声明与锁一致性校验求解器实现
pip无（pip freeze 只是环境快照）当前环境需自行提供无，靠 --require-hashes 兜底回溯（resolvelib，Python）
pip-tools编译出的 requirements 文件单一 Python 版本与平台--generate-hashes无复用 pip 的求解器
Poetrypoetry.lock多平台：为不同 marker 组合各记一份解有poetry check --lock自研，Python
PDMpdm.lock可配置锁定目标（平台 / Python 版本组合）有pdm lock --checkresolvelib，Python
uvuv.lockuniversal：按 requires-python 与 marker 一次解出跨平台结果有uv lock --check / uv sync --frozenPubGrub，Rust

选型时真正区分它们的是三个问题：锁文件是「单平台解」还是「跨平台解」；CI 里能不能一条命令断言「锁文件与声明同步」；以及这个工具是不是同时管虚拟环境、Python 解释器版本和构建发布。第三点上 uv 和 PDM 把解释器安装也接管了，pip-tools 只做锁定。

uv 快在哪里：机制而不是玄学

「pip 慢得没道理」是个错误归因。pip 的时间主要花在串行网络往返、下载完整分发文件、为源码包创建构建隔离环境、以及每个虚拟环境各解压一份拷贝上。uv 的快对应的是这几处的具体改写：

uv 的机制对应的传统行为收益出现在什么场景
Rust 实现的 PubGrub 求解Python 层回溯，冲突信息也弱依赖图大、版本候选多、有冲突需要回溯时
索引请求与下载高并发并发度低，请求基本串行依赖数量多、网络 RTT 高（国内访问公网源）
对 wheel 用 range 请求只取 METADATA下载整个 wheel 才能读依赖候选版本多、包体积大（如科学计算栈）
全局内容寻址缓存 + 硬链接 / 写时复制入环境每个环境各解压拷贝一份反复重建环境、多项目共用同一批依赖、CI 缓存命中
尽量避免为候选包起 Python 子进程做构建隔离sdist 候选每个都要建临时环境依赖里有较多源码分发时
💡
哪里不会变快

只提供源码分发、必须现场编译的包（老的数据库驱动、少数图像与加密库），uv 的提速非常有限——瓶颈在编译器和链接器，不在包管理器。同理，网络已经是局域网私有源、依赖只有十几个的小项目，换工具的收益远小于换掉「每次 CI 都重新装一遍」的流程问题。

可复现构建的必要条件

「锁了版本」只是第一层。下面每一行缺一个，复现性就有缺口。

必要条件缺失后果落地做法
锁文件覆盖完整闭包传递依赖静默漂移，故障与代码改动无关锁文件进版本库，CI 用 --frozen 或 --check 断言同步
每个分发文件带哈希镜像源重打包、包被替换都无法发现--generate-hashes，或直接用自带哈希的锁文件
理解哈希模式的传染性只给一部分依赖写哈希会让整次安装直接失败要么全量生成，要么把本地路径与可编辑依赖单独剥离
构建依赖也被固定构建隔离环境拉到新版后端，同一份 sdist 产出不同 wheel[build-system].requires 给上界；或预装后端并关闭构建隔离
明确目标环境标记换平台后解出不同版本，或退化成现场编译用 universal lock，或按平台各锁一份并在 CI 校验
索引来源唯一且优先级明确依赖混淆：内部包名被公网抢注后优先装上公网版本私有源用「唯一索引 + 上游代理」模式，不要靠追加额外索引（追加的索引之间没有优先级保证）

自建 wheel 的时间戳同样的源码产出字节不同的 wheel（zip 内嵌 mtime）构建时设置 SOURCE_DATE_EPOCH

# ---- 方案一：仍用 pip 生态，把 requirements 推到「接近锁文件」 ----
# 编译时显式声明目标解释器，避免在 Mac 上编译出 Linux 装不上的解
uv pip compile pyproject.toml \
    --generate-hashes \
    --python-version 3.12 \
    --output-file requirements.lock

# 部署：哈希校验 + 禁止现场编译 + 唯一索引
pip install --require-hashes --only-binary=:all: \
    --index-url https://pypi.example.com/simple --no-cache-dir \
    -r requirements.lock

# ---- 方案二：uv 全流程 ----
uv lock                 # 解一次，产出 universal 的 uv.lock
uv lock --check         # CI 第一步：锁文件与 pyproject 不同步就失败
uv sync --frozen --no-dev   # 部署：只按锁装，绝不重新求解

# ---- 排查：本机到底支持哪些 wheel 标记 ----
pip debug --verbose | grep -A 40 'Compatible tags'
# 输出里若没有 cp313 相关标记，说明装 cp313 轮子必然回退到 sdist

wheel 与 sdist：编译依赖藏在哪

安装一个包只有两条路：拿到匹配的 wheel 直接解包，或者拿到 sdist 现场构建。绝大多数「CI 突然很慢」「依赖装不上」的事故，本质都是从第一条路掉到了第二条路。文件名就是判据，numpy-2.1.0-cp312-cp312-manylinux_2_17_x86_64.manylinux2014_x86_64.whl 的每一段都有含义：

标记段取值示例含义与影响
Python 标记cp312 / py3cp 前缀表示依赖 CPython 具体版本的 C API；py3 表示纯 Python，跨版本通用
ABI 标记cp312 / abi3 / noneabi3 是稳定 ABI，一次编译可跨多个 Python 小版本，代价是只能用受限 API；普通 cp 标记每升一个小版本都要重新编译
平台标记manylinux_2_17_x86_64数字是所需的最低 glibc 版本，宿主 glibc 更老则不可用
平台标记（musl）musllinux_1_2_x86_64Alpine 走这一支。很多包不发 musllinux 轮子，于是 Alpine 上全量现场编译
纯 Pythonpy3-none-any一份轮子通吃所有平台，没有编译依赖
只有 sdistpkg-1.2.3.tar.gz需要编译器、头文件、有时还要系统库的 dev 包；构建在隔离环境里进行，构建依赖由后端声明
free-threaded 构建cp313tt 后缀是无 GIL 构建专用 ABI，与普通 cp313 轮子不通用

实践上三条硬规则：容器基础镜像优先 Debian slim 而不是 Alpine（后者的 musl 轮子覆盖率明显更差）；升级 Python 小版本前先确认关键依赖已发布对应 ABI 的轮子；生产安装一律加上「只允许二进制」的开关，把缺轮子变成显式失败。需要自建轮子时，用 cibuildwheel 在 manylinux 容器里构建，不要在业务 CI 里临时编译。

ruff 与 mypy 在 CI 中的分层与增量

把所有检查都堆在一个 CI job 里，结果是开发者等十分钟才知道少了个逗号。合理的分层是按「反馈延迟」而不是按「工具种类」切：本地保存时跑毫秒级的，提交钩子跑秒级且只看改动文件，PR CI 跑全量且带缓存，发布前或定时任务跑昂贵的严格检查与安全扫描。

关于两个工具的边界，有两个常见误解要纠正。第一，ruff 不做类型检查：它工作在单文件的语法与作用域层面，跨模块的返回值类型是否匹配它判断不出来，所以它替代不了 mypy / pyright；反过来 mypy 也不是 linter，不管导入排序和代码风格。第二，mypy 的增量缓存比想象中脆：缓存的有效性和 mypy 版本、目标 Python 版本、配置内容都相关，改一行配置就可能全量重算，所以 CI 的缓存 key 必须包含这些；而 follow_imports = skip 虽然能让检查变快，代价是把被跳过模块的类型当成 Any，错误会静默漏掉。

# .github/workflows/ci.yml —— 按反馈延迟分层，快的先失败
name: ci
on: [push, pull_request]
jobs:
  fast:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v3
        with:
          enable-cache: true          # 缓存 uv 的全局包缓存，命中后安装接近瞬时
      - run: uv lock --check          # 第一道闸：锁文件与 pyproject 必须同步
      - run: uv sync --frozen         # 只按锁装，禁止在 CI 里重新求解
      - run: uv run ruff check --output-format=github .
      - run: uv run ruff format --check .

  types:
    runs-on: ubuntu-latest
    needs: fast
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v3
        with:
          enable-cache: true
      - run: uv sync --frozen
      - uses: actions/cache@v4
        with:
          path: .mypy_cache
          # key 必须含 mypy 版本与配置内容，否则会用到失效缓存
          key: mypy-${{ runner.os }}-${{ hashFiles('uv.lock', 'pyproject.toml') }}
      - run: uv run mypy --sqlite-cache src tests

  audit:
    runs-on: ubuntu-latest
    if: github.event_name == 'push'   # 昂贵检查不卡每次 PR
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v3
      - run: uv sync --frozen
      - run: uv run pip-audit --strict
❌
最容易踩的坑

1. 把 pip freeze 的输出当锁文件提交，半年后没人分得清哪些是直接依赖，删一行就炸。

2. 只给部分依赖加哈希：pip 的哈希模式是传染的，一旦启用，任何未固定版本或缺哈希的依赖都会让整次安装失败。

3. [build-system].requires 不给上界，某天新版构建后端改了默认行为，同一个 tag 构出的 wheel 不一样了。

4. 用「追加额外索引」的方式接私有源：多个索引之间没有优先级保证，内部包名一旦被公网抢注就会装上别人的包。正确做法是唯一索引加上游代理。

5. 基础镜像选 Alpine：musl 平台的轮子覆盖率差，结果把安装变成了半小时编译，镜像里还得留着编译器。

6. 升级 Python 小版本时忘了 ABI 标记这回事，带 C 扩展的依赖没有对应轮子，CI 静默回退到 sdist 后失败。

7. 移动或重命名 venv 目录：bin/ 下所有入口脚本的 shebang 是绝对路径，全部失效，报错却只是一句 bad interpreter。

8. 宿主设置了 PYTHONPATH，或 venv 建了 --system-site-packages，外部包遮蔽掉锁文件里的版本，「依赖锁定」变成摆设。

9. 在容器里 pip install 完不清缓存，也不用多阶段构建，镜像里留着一份完整的包缓存和编译工具链。

10. CI 缓存 .mypy_cache 时 key 只用了操作系统，配置或 mypy 版本变了仍复用旧缓存，检查结果不可信。

11. 期望 ruff 顺手做类型检查：它没有跨模块类型推导，删掉 mypy 之后类型错误直接漏到线上。

12. 一个仓库里 conda 与 pip 混装同一个二进制包，两套 libstdc++ 或 BLAS 同时存在，导入期崩溃且堆栈毫无线索。
