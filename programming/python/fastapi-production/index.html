Python 服务上生产：进程模型、优雅关闭与可观测性

这篇假设代码写完了、依赖也锁好了，只回答一个问题：这个服务上生产还缺什么。缺的通常不是功能，而是五件事——探针怎么配、怎么关得干净、日志与指标从哪里接出去、哪些配置能不重启就改、以及出事之后能不能回滚。进程模型本身（WSGI 与 ASGI 的契约差异、gunicorn 的 worker 类型、进程数与容器 CPU 配额的关系）不在这里重复，见站内《Python Web 服务的部署形态：WSGI、ASGI 与进程模型》；本文只保留与「上线」直接相关的那部分结论。

💡
这篇怎么读
  • ① 用法：一份可逐条执行的上线自检清单（探针返回值、信号能不能到进程、在途请求会不会被切断、日志有没有被缓冲、指标能不能抓、配置能不能加载、单进程内存量、退出码、回滚演练），以及探针端点、优雅关闭、日志与编排清单的最小配置。
  • ② 原理：三种探针各自的语义与「绝对不要做」的那件事、SIGTERM 到进程退出的完整链路与四个超时的对齐关系、日志与指标与追踪的接入点（含多进程指标聚合）、哪些配置能热更新哪些必须重启、发布与回滚兜不住的变更类型、内存只涨不降为什么通常不是泄漏、以及进程内定时任务在多副本下为什么会重复执行。
  • ③ 场景：不同部署环境与服务形态下这几件事各做到哪一步，以及哪些问题不该在上线这一层解决。

① 用法 · 上线自检清单与最小配置

下面九条按顺序敲一遍，任何一条不通过都不要上线。这些命令假设服务已经打成镜像、在本地以容器形式跑起来。

C=myapp-check
docker run -d --name $C -p 8000:8000 --memory=512m myapp:candidate

# ---------- 1. 探针：两个端点的语义必须不同 ----------
curl -fsS localhost:8000/healthz          # 存活：只要进程活着就必须返回 200
curl -i    localhost:8000/readyz          # 就绪：初始化没完成时应当是 503，完成后 200

# ---------- 2. 信号能不能到进程（CMD 写成 shell 形式时这一步会失败）----------
docker exec $C ps -o pid,args -p 1        # PID 1 必须是 python/uvicorn，不能是 /bin/sh
time docker stop -t 45 $C                 # 观察耗时：应远小于 45 秒，并打出关闭日志
docker inspect -f '{{.State.ExitCode}}' $C  # 期望 0；137 表示被 SIGKILL，143 表示没等到收尾

# ---------- 3. 在途请求会不会被切断 ----------
docker start $C
curl -s "localhost:8000/v1/slow?seconds=10" & sleep 1 && docker stop -t 45 $C
wait                                      # 期望这条慢请求正常返回，而不是连接被重置

# ---------- 4. 日志：不能被缓冲，且能被解析 ----------
docker start $C && curl -s localhost:8000/healthz >/dev/null
docker logs --tail 1 $C | python3 -c "import json,sys; json.loads(sys.stdin.read())"
docker exec $C printenv PYTHONUNBUFFERED   # 必须是 1，否则崩溃前的日志会丢

# ---------- 5. 指标能抓，且标签基数可控 ----------
curl -s localhost:8000/metrics | grep -c '^http_requests_total'
curl -s localhost:8000/metrics | grep -o 'path="[^"]*"' | sort -u | wc -l
# 上一行的输出应该接近路由数量；如果是请求数量级，说明 path 标签用了原始 URL

# ---------- 6. 配置能加载，缺字段会立刻失败 ----------
docker exec $C python -m myapp.core.config
docker run --rm myapp:candidate python -m myapp.core.config 2>&1 | tail -3   # 不注入变量时应报错

# ---------- 7. 单进程内存与连接数：定副本数的依据 ----------
docker exec $C sh -c 'grep -E "^(VmRSS|Threads)" /proc/1/status'
# worker 或副本上限 = (容器内存限额 × 0.8 - 共享部分) / 单进程 RSS
# 连接数上限 = 数据库 max_connections × 0.8 / (实例数 × 每实例池大小)

# ---------- 8. 文件描述符上限够不够（长连接服务尤其要看）----------
docker exec $C sh -c 'cat /proc/1/limits | grep "open files"'

# ---------- 9. 回滚演练：用上一个 digest 起一份，确认能起来 ----------
docker run --rm -d --name $C-prev myapp@sha256:上一个版本的摘要 && sleep 5 \
  && curl -fsS localhost:8001/readyz

# src/myapp/api/routers/health.py —— 探针端点：两个语义，两个实现
from fastapi import APIRouter, Response

router = APIRouter()

# 模块级标志：lifespan 设置它，探针只读它。就绪状态不查任何下游，原因见原理层
_ready = False


def mark_ready(value: bool) -> None:
    global _ready
    _ready = value


@router.get("/healthz")
async def healthz() -> dict:
    # 存活探针：只回固定响应。它的唯一含义是「这个进程还能处理请求」，
    # 这里一旦查了数据库，下游抖动就会让全部实例被反复重启
    return {"status": "ok"}


@router.get("/readyz")
async def readyz(response: Response) -> dict:
    # 就绪探针：只反映本进程的初始化状态；未就绪必须用 503 而不是 200 加错误体，
    # 编排系统只看状态码
    if not _ready:
        response.status_code = 503
        return {"status": "starting"}
    return {"status": "ready"}

# src/myapp/main.py 的关闭链路 —— 顺序是：先不就绪，再排干，最后关资源
import asyncio
import logging
from collections.abc import AsyncIterator
from contextlib import asynccontextmanager

from fastapi import FastAPI

from myapp.api.routers.health import mark_ready
from myapp.core.config import get_settings
from myapp.core.loop_probe import monitor_loop_lag

logger = logging.getLogger(__name__)


@asynccontextmanager
async def lifespan(app: FastAPI) -> AsyncIterator[None]:
    settings = get_settings()
    app.state.pool = await create_pool(settings.database_url, settings.db_pool_size)
    lag_task = asyncio.create_task(monitor_loop_lag())   # 常驻探针，持引用防被 GC
    mark_ready(True)                                     # 所有初始化完成后才置就绪
    logger.info("startup_complete", extra={"env": settings.env})
    try:
        yield
    finally:
        # 第一步：立刻置为不就绪。就绪探针下一次失败时端点就会被摘除，
        # 这一步不等待任何东西，越早越好
        mark_ready(False)
        lag_task.cancel()
        # 第二步：等在途请求。服务器自己会停止接新连接并等待，
        # 我们只需要保证这里不阻塞、不吞 CancelledError
        # 第三步：释放资源。放 finally，启动失败时也要走到
        await app.state.pool.close()
        logger.info("shutdown_complete")

# 编排侧最小配置：四个时间值的关系是「宽限期 > preStop 等待 + 优雅超时」
spec:
  terminationGracePeriodSeconds: 45      # 大于 10 + 25，留出余量
  containers:

      image: registry.internal/myapp@sha256:...   # 用摘要而不是可变 tag，回滚才可复现
      command: ["uvicorn", "myapp.main:app", "--host", "0.0.0.0", "--port", "8000",
                "--workers", "1", "--timeout-graceful-shutdown", "25"]
      env:
        - name: PYTHONUNBUFFERED          # 不设的话崩溃前的日志会留在缓冲区里
          value: "1"
        - name: APP_ENV
          value: "prod"
      lifecycle:
        preStop:
          exec:
            command: ["sleep", "10"]      # 等端点摘除生效，期间进程仍正常服务
      startupProbe:                        # 慢启动用它，而不是把存活探针的初始延迟调很大
        httpGet: {path: /readyz, port: 8000}
        failureThreshold: 30
        periodSeconds: 2
      livenessProbe:
        httpGet: {path: /healthz, port: 8000}
        periodSeconds: 10
        failureThreshold: 3
      readinessProbe:
        httpGet: {path: /readyz, port: 8000}

为什么就绪探针不能查下游、为什么四个超时必须对齐、哪些配置能热更新、为什么有些变更回滚兜不住——都在下面几节。

② 原理 · 探针：三种语义，三种失败后果

搞清这一节能解决的现象是：下游抖动了一下，所有副本同时被摘或被反复重启，局部故障被放大成整体不可用。三种探针的区别不在实现，而在失败之后编排系统会做什么。

探针检查什么失败后的动作绝对不要做
存活（liveness）进程还在、事件循环没卡死，返回固定响应即可重启容器查数据库——下游抖动会导致全部实例被反复重启
就绪（readiness）本地初始化是否完成：配置已加载、连接池已建、缓存已预热从端点表摘除，不重启级联下游依赖——下游抖一下所有副本同时不就绪，服务整体不可用
启动（startup）慢启动服务的初始化窗口在此期间不执行存活检查用超长的存活初始延迟代替它，那会让真卡死也迟迟不被发现
stateDiagram-v2 [*] --> Starting: 进程启动，Settings 校验通过 Starting --> Initializing: lifespan 开始建连接池与预热 Initializing --> Ready: mark_ready(True) Initializing --> Failed: 初始化抛异常 note right of Initializing 此阶段就绪端点返回 503 启动探针在此期间抑制存活检查 流量不会被转发过来 end note Ready --> Draining: 收到 SIGTERM 后立刻置为不就绪 Ready --> Stuck: 事件循环被长时间阻塞 note right of Stuck 存活探针超时后容器被重启 这是唯一应该触发重启的情况 end note Stuck --> Starting: 容器重启 Draining --> Closing: 在途请求处理完 note right of Draining 端点摘除是异步的 preStop 等待就是为了覆盖这段时间差 end note Closing --> [*]: 关连接池，退出码 0 Failed --> [*]: 非零退出，编排系统按策略重启

② 原理 · 优雅关闭：四个超时必须对齐

搞清这一节能解决的现象是：每次发布都有一小波 502 或超时，而代码里明明处理了关闭。原因几乎总是同一个：进程收到 SIGTERM 与上游停止转发流量之间存在时间差。端点摘除是异步生效的，等你开始拒绝新连接时，可能还有请求正在路上。

sequenceDiagram participant K as 编排系统 participant EP as 负载均衡端点表 participant P as 应用进程 participant U as 在途请求 K->>P: 发送 SIGTERM K->>EP: 同时开始摘除端点（异步，有延迟） Note over P: preStop 先睡 5 到 10 秒
让端点摘除先完成 EP-->>P: 期间仍可能有新请求打进来 P->>P: 停止接受新连接，已有连接继续处理 P->>U: 等在途请求完成，上限 = 优雅超时 U-->>P: 全部完成 P->>P: 执行 lifespan 关闭段
关连接池、flush 缓冲、注销注册中心 P-->>K: 正常退出，退出码 0 Note over K,P: 终止宽限期必须大于
preStop 等待 + 优雅超时
否则进程收尾时被 SIGKILL
层参数建议值配错的后果
容器CMD 写成 exec 形式（JSON 数组）必须写成 shell 形式时信号被 sh 吞掉，优雅关闭完全不生效
应用lifespan 关闭段先置不就绪，再关连接池、HTTP 客户端，flush 日志与指标连接不释放，下游看到一批半开连接
uvicorn--timeout-graceful-shutdown略大于最慢接口的 P99，如 25s设太小则在途请求被直接断开
gunicorn--graceful-timeout30s同上；且它与 --timeout 是两件事，后者是卡死判定
编排terminationGracePeriodSeconds大于 preStop 等待加优雅超时，如 45s进程正在收尾时被 SIGKILL，在途请求全丢，退出码 137
编排preStop 等待5 到 10s不加就会有请求被打到正在关闭的实例，表现为发布期 502
代码不吞 CancelledError捕获后必须重抛协程无法被取消，优雅关闭直接失效，细节见asyncio 篇

探针、preStop 与滚动更新在编排侧的完整机制见站内 Kubernetes 专题；信号在不同 worker 类型下怎么从主进程传到子进程见部署形态篇，这里只给与应用侧对齐的参数。

② 原理 · 日志、指标与追踪的接入点

搞清这一节能解决的现象是：故障时日志只到崩溃前几秒就断了、多 worker 下计数器会倒退、以及有日志但没法按请求串起来。可观测性的方法论不在这里展开，这一节只解决「接口在哪、接错了会怎样」。

日志侧有两个硬性前提：统一写 stdout（容器里不要自己切割文件），以及 PYTHONUNBUFFERED=1。不设第二项时 stdout 是块缓冲，进程被 kill 时缓冲区内容直接丢失——恰好丢的就是最需要的那几行。日志格式与 request_id 的注入点在工程骨架篇，采集与检索在站内日志专题。

指标侧最大的坑是多进程。默认的客户端把指标存在进程内存里，多 worker 下请求被随机分到某个进程，每次抓取只拿到其中一个的数据，计数器会跳变甚至倒退：

import os
from contextlib import asynccontextmanager

from fastapi import FastAPI
from prometheus_client import CollectorRegistry, Counter, Histogram, generate_latest, multiprocess
from starlette.responses import Response

# 必须在导入 prometheus_client 之前就设好这个环境变量（通常在 Dockerfile 或启动脚本里）
#   PROMETHEUS_MULTIPROC_DIR=/tmp/prom
# 而且容器启动时要清空该目录，否则上次运行残留的文件会被算进来
MULTIPROC_DIR = os.environ.get("PROMETHEUS_MULTIPROC_DIR")

REQUESTS = Counter("http_requests_total", "请求总数", ["method", "path", "status"])
LATENCY = Histogram(
    "http_request_duration_seconds", "请求耗时", ["method", "path"],
    # 显式给桶边界：默认桶对 Web 接口太粗，算不准 P99
    buckets=(0.005, 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1.0, 2.5, 5.0),
)


@asynccontextmanager
async def lifespan(app: FastAPI):
    yield
    if MULTIPROC_DIR:
        # 进程退出时标记自己已死，否则它的指标文件会永远被计入总量
        multiprocess.mark_process_dead(os.getpid(), MULTIPROC_DIR)


app = FastAPI(lifespan=lifespan)


@app.get("/metrics")
def metrics() -> Response:
    if MULTIPROC_DIR:
        registry = CollectorRegistry()
        multiprocess.MultiProcessCollector(registry)   # 聚合所有 worker 的文件
    else:
        from prometheus_client import REGISTRY as registry   # 单进程直接用默认注册表
    return Response(generate_latest(registry), media_type="text/plain; version=0.0.4")
维度接入点接错了会怎样
日志输出统一写 stdout，格式在入口用 dictConfig 配一次自己写文件切割时，容器重建即丢失；不设 PYTHONUNBUFFERED 则崩溃前的日志看不到
访问日志交给网关或一个中间件，只留一份网关与应用各记一份，同一请求两条记录，排查时反而更慢
指标按路由模板打计数与直方图，桶边界显式给path 标签用原始 URL 会让基数随请求数增长，能把监控系统打挂
多进程指标配 PROMETHEUS_MULTIPROC_DIR，暴露时聚合，退出时 mark_process_dead不配就跳变倒退；不清空目录则上次运行的残留被计入；不标记死亡则数值只增不减
链路追踪用自动埋点接 FastAPI、HTTP 客户端与数据库驱动，采样率显式配全采样在高 QPS 下开销可观；不埋下游客户端则链路断在本服务
日志与 trace 关联用 contextvars 把 trace_id 注入日志字段用 thread-local 在 asyncio 下会串号，关联出来的是别人的请求
事件循环健康常驻上报事件循环延迟不上报就只能靠 CPU 判断，而阻塞时 CPU 恰好不高，见asyncio 篇
进程级指标RSS、GC 各代计数、打开的文件描述符数fd 数缓慢上涨往往是连接泄漏的第一个信号，不看就只能等 OOM

② 原理 · 配置热更新的边界

搞清这一节能解决的现象是：改了配置中心的值，一半副本生效一半没生效；或者挂载的配置文件明明更新了，进程却读不到。能不能热更新，取决于这个值在进程里被谁持有：每次请求都重新读的值可以热更，启动时构造进对象的值不能。

配置类型能否热更新怎么做风险
功能开关、灰度名单、限流阈值能每次请求从一个可替换的引用里读，整份替换而不是逐字段改读到「改了一半」的中间状态，所以要整份替换
日志级别能暴露一个内部接口调 setLevel，或按信号重读调到 DEBUG 忘记调回去，日志量与成本一起爆
下游超时、重试次数视客户端而定能在每次调用时传参的可以热更；构造进客户端的要重建客户端重建客户端会丢掉连接池里的长连接，有一次抖动
连接池大小、数据库地址不能走发布流程运行期改会让新旧连接并存，最难排查的一类问题
端口、worker 数、优雅超时不能改编排清单并滚动更新原地改进程参数与声明式清单不一致，下次重建就回退了
密钥轮转取决于注入方式挂载文件时可重读；环境变量注入的只能重启新旧密钥的重叠有效期必须由下游保证，否则轮转瞬间全部失败
挂载的配置文件取决于挂载方式以整目录方式挂载并监听变化把单个文件挂进去时内容往往不会随更新变化，看起来像「改了没生效」

把配置类做成不可变（frozen=True）与热更新并不矛盾：不可变保证的是「没人偷偷改字段」，热更新的正确形态是构造一个新实例整份替换引用，而不是原地修改。Settings 类怎么写在工程骨架篇，值从哪来、密钥怎么注入在依赖与环境管理。

② 原理 · 发布与回滚：哪些变更回滚兜不住

搞清这一节能解决的现象是：回滚了代码，故障却没有恢复。回滚只能撤销「进程里的代码与依赖」，凡是已经写出去、发出去、或者被别人读过的东西都撤不回来。

变更类型回滚能不能兜住必须提前做什么代价
纯代码逻辑改动能镜像用摘要或不可变 tag 发布无；这是回滚成立的基准
数据库加列、加表能（加法是兼容的）先发迁移再发代码；新列可空或有默认值一次发布拆成两步
数据库删列、改类型、改约束不能分三步：代码先停止使用 → 观察一个发布周期 → 再删周期变长，中途要维护兼容代码
已写入的数据格式变化不能新旧格式同时可读（双读），或带版本字段读路径多一个分支，要定清理时间点
发到队列的消息格式变化不能消费方先上线能兼容新旧的版本，再改生产方两次发布，且有一段时间两种格式并存
缓存键或序列化方式变化部分换 key 前缀而不是复用旧 key发布瞬间缓存命中率归零，下游要能吃下这波流量
对外接口字段语义变化不能加新字段而不是改旧字段，旧字段按公告期下线一段时间内两个字段都要维护
配置项重命名能，但要小心新旧名同时接受一个发布周期回滚到旧版本时它只认旧名，所以两边都得留

推论有两条。第一，发布顺序由兼容方向决定：加法先行、减法最后，中间至少隔一个可观察的周期。第二，回滚要能复现，所以镜像必须用摘要或不可变 tag，锁文件与这个 tag 一一对应——不然回滚回去的是一个没人测过的新组合。灰度、流量切分与多服务之间的发布次序见站内微服务与服务治理专题。

② 原理 · 内存：只涨不降通常不是泄漏

搞清这一节能解决的现象是：上线第一天就有人报「内存在涨」，然后花两天查了个不存在的泄漏。CPython 的小对象走自带的分配器，按池和区管理，一个区只有在完全空闲时才可能还给操作系统。实际运行中总有零散的长命对象散落在各个区里，于是 RSS 停在历史峰值附近不再下降。这是分配器行为，不是泄漏。

判断标准是趋势而不是绝对值：流量平稳后曲线走平，就是正常水位；持续单调上涨、没有平台期、重启后又从低位开始重复同样的上涨，才按泄漏查。

import gc
import linecache
import tracemalloc


def start_leak_probe() -> tracemalloc.Snapshot:
    # tracemalloc 会给每次分配记录调用栈，开销明显（内存与 CPU 都涨），
    # 只在排查期临时开启，绝不常驻生产
    tracemalloc.start(10)          # 保留 10 层栈帧，够定位到业务代码
    return tracemalloc.take_snapshot()


def diff_leak_probe(baseline: tracemalloc.Snapshot, top: int = 10) -> None:
    current = tracemalloc.take_snapshot()
    # 按分配位置比较两个时间点的差异：持续为正且不断变大的那几行就是嫌疑
    for stat in current.compare_to(baseline, "lineno")[:top]:
        frame = stat.traceback[0]
        print(f"{frame.filename}:{frame.lineno} +{stat.size_diff / 1024:.1f}KB "
              f"({stat.count_diff:+d} 个对象)")
        print("   ", linecache.getline(frame.filename, frame.lineno).strip())


def object_census(top: int = 10) -> None:
    """不开 tracemalloc 时的轻量手段：看哪类对象在变多"""
    from collections import Counter
    counter = Counter(type(o).__name__ for o in gc.get_objects())
    for name, cnt in counter.most_common(top):
        print(name, cnt)

def before_fork() -> None:
    # 在 fork 出 worker 之前调用：先回收启动期垃圾，再把常驻对象移出 GC 追踪，
    # 避免子进程的 GC 遍历修改对象头的标记位而触发写时复制，

② 原理 · 定时任务与后台 worker

搞清这一节能解决的现象是：扩到三个副本之后，每天的对账任务跑了三遍。进程内调度器在多副本下会重复执行，而且这件事在单副本时完全看不出来——它是扩容那一刻才出现的故障。

sequenceDiagram participant S1 as 副本 1 内置调度器 participant S2 as 副本 2 内置调度器 participant S3 as 副本 3 内置调度器 participant DB as 数据库 Note over S1,S3: 00:00 三个副本的定时器同时触发 S1->>DB: 执行对账，写入结果 S2->>DB: 同一批数据再算一遍 S3->>DB: 第三遍 Note over DB: 非幂等任务导致重复扣款或重复发送 Note over S1,S3: 改造：抢分布式锁，只有一个副本执行 S1->>DB: 抢锁成功，执行 S2--xDB: 抢锁失败，直接跳过 S3--xDB: 抢锁失败，直接跳过
方案多副本安全可观测性适用
进程内调度器，多副本不安全，会重复执行无只有单副本时可用
进程内调度加分布式锁安全（锁必须带过期时间）一般任务少、不想加组件
独立的调度进程或平台级定时任务安全好，有独立的成功失败记录推荐，业务副本与任务解耦
专门的任务框架（调度器单实例加多 worker）安全好已有这套体系时
队列驱动的后台 worker安全最好，有积压与重试指标异步任务的标准形态，见站内消息队列专题

另外一条与关闭链路相关：后台任务必须能被取消，且取消时要把手里的活做完或标记未完成。吞掉 CancelledError 的后台循环会让优雅关闭直接超时，最后被 SIGKILL。

③ 场景 · 不同环境下这几件事各做到哪一步

上线清单不是一份通用表格，环境不同该做的事也不同。下表给结论与代价。

场景该怎么做为什么代价
容器编排环境（有负载均衡与滚动更新）三种探针都配，preStop 加宽限期对齐，每 Pod 单 worker探针语义与发布粒度都按实例算，单 worker 的归因最清晰每副本一份内存与连接池，总连接数要重算；细节见部署形态篇
虚拟机上长期运行用带进程治理能力的服务器（定期轮换 worker、静默超时强杀），由系统服务管理器负责重启没有编排系统时，进程治理只能靠服务器与 init 系统指标要开多进程模式并聚合，日志需要自己做轮转
只有一个副本的内部服务探针可以简化，但优雅关闭与日志不缓冲仍必须做关不干净与日志丢失和副本数无关无；这两项成本极低
长连接服务（WebSocket、SSE）优雅超时按最长会话设或主动通知客户端重连；fd 上限必须调在途「请求」可能是一条持续几小时的连接，等不完发布必然打断部分连接，需要客户端具备重连能力
有定时任务或后台消费从业务副本里拆出去，或加分布式锁扩副本那一刻任务就会重复执行，而这在单副本时测不出来多一个部署单元或一个锁组件
接口 P99 本来就有几十秒（导出、报表）改成异步任务加轮询结果，而不是把优雅超时拉到几十秒优雅超时越长，发布窗口越长，宽限期也要跟着放大接口契约要改，客户端要配合
需要频繁调开关做灰度开关走可热更新的路径并整份替换，其余配置走发布把「需要秒级生效」的部分和「需要可回滚」的部分分开要维护一份开关清单，否则没人知道当前生效值
发布伴随数据库变更加法先行、减法最后，中间隔一个观察周期回滚撤不回已经执行的破坏性迁移一次发布拆成两到三次，周期变长

最容易踩的坑

❌
避坑清单
  • CMD 写成 shell 形式：信号被 sh 吞掉，PID 1 不是 Python 进程，优雅关闭完全不生效，退出码永远是 137。
  • terminationGracePeriodSeconds 小于服务器的优雅超时：进程正在收尾时被 SIGKILL，在途请求全丢。
  • 不加 preStop 等待：端点摘除是异步的，SIGTERM 之后仍有请求被打进来，发布期必然出现 502。
  • 关闭时不先把就绪置为 false：明明在排干，探针还报就绪，新流量继续被转发进来。
  • 就绪探针级联下游依赖：下游抖动导致所有副本同时不就绪，把局部故障放大成整体不可用。
  • 存活探针里查数据库：下游一抖全部实例被反复重启，恢复时间被自己的探针拖长。
  • 用超长的存活初始延迟代替启动探针：真卡死时也要等同样长的时间才被发现。
  • 忘记 PYTHONUNBUFFERED=1：stdout 块缓冲，崩溃前最关键的那几行日志永远看不到。
  • 指标的 path 标签用原始 URL：带 ID 的路径让标签基数爆炸，能把监控系统打挂。
  • prometheus 多进程模式没配目录、或没在启动时清空目录：指标跳变、上次运行的残留被计入，告警彻底不可信。
  • 进程退出时不调 mark_process_dead：死掉的 worker 指标永远留在总量里，数值只增不减。
  • 把「内存只涨不降」直接当泄漏查：分配器本来就不归还内存，看趋势有没有平台期才是正确判断。
  • lru_cache 不设 maxsize：参数一多就成了无上限缓存，这是最常见的真泄漏来源。
  • tracemalloc 或 asyncio 调试模式常开在生产：排查工具本身成了性能问题。
  • 多副本各自跑进程内定时任务：对账、发券、清理这类任务被执行多遍，事后对账才发现。
  • 用可变 tag 发布镜像：tag 被覆盖之后，回滚回去的不是出问题前那份代码与依赖。
  • 把破坏性数据库迁移和代码放在同一次发布：回滚撤不回已经删掉的列，故障期只能硬扛。
  • 在运行期原地改进程参数：与声明式清单不一致，下次重建就悄悄回退，问题复现时毫无线索。
