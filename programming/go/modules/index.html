模块、包组织与依赖管理

🏷️ Go 语言总览

这篇的靶子是两类反复出现的问题：依赖侧「构建在我机器上是好的」，包组织侧「改一个功能要同时动四个包」。前者的根源是不知道 Go 的选版算法与其他语言是反的（MVS 取「被要求过的最大版本」，不是最新版本），后者的根源是把 MVC 的 models / services / utils 分层直接搬进了 Go。两件事都有固定的动手顺序和可以照抄的目录形状。

💡
这篇怎么读
  • ① 用法：从 go mod init 到发版的完整动手顺序、可照抄的目录骨架，以及命令与环境变量速查表——每一行都标出「用错的后果」，包括 CI 里必须加的两个开关和发布 v2 缺一不可的三步。
  • ② 原理：go.mod 每条指令的真实作用与作用域、MVS 为什么让构建可复现却不会自动带来安全补丁、go.sum 与 GOPROXY 的下载校验链路、按业务能力分包与 internal 的编译器级约束、接口定义在消费方如何消掉循环导入、init 的四个问题。
  • ③ 场景：单体、多二进制、公共库、monorepo 多模块、离线构建这几种形态下模块怎么切的决策矩阵，以及依赖出问题时从症状到根因的判断路径与不适用边界。

① 用法 · 从建模块到发版的动手顺序

下面这串命令是一个新服务从零开始的完整顺序，也是日常改依赖时的检查顺序。每条注释只写「不这么做会怎样」，机制原因在原理层展开。

# 0) 建模块。这个路径就是将来的 import 前缀，写错了改起来要动所有文件
go mod init github.com/acme/order-api

# 1) 目录骨架：默认把所有代码放 internal/，外部模块 import 会直接编译失败，
#    这是 Go 少数由编译器强制的可见性约束，比文档约定可靠
mkdir -p cmd/api internal/order internal/user internal/platform/mysql

# 2) 加依赖。v2 及以上的模块路径必须带主版本后缀，漏了会拿到 v1 系列且报错难懂
go get github.com/redis/go-redis/v9@v9.7.0

# 3) 每次增删 import 之后都要跑。tidy 按真实 import 补齐与删除 require，
#    不跑的后果是 go.mod 里留着不再使用的依赖，CI 开了 -mod=readonly 会直接失败
go mod tidy

# 4) 出现一个没听说过的依赖，先问它为什么在这里，别急着删
#    输出是一条导入链，链的第一段就是真正把它带进来的直接依赖
go mod why -m github.com/some/lib

# 5) 升级。默认只升补丁位，这是风险最小的方式
go get -u=patch ./...
#    对比：go get -u ./... 会把几十个依赖顶到最新次版本，出问题时无法定位是哪一个

# 6) 安全补丁不会自动来（原因见原理层 MVS 一节），必须靠工具主动扫
go run golang.org/x/vuln/cmd/govulncheck@latest ./...

# 7) 提交前两件事：校验缓存内容与 go.sum 一致，确认构建过程没偷偷改 go.mod
go mod verify
git diff --exit-code go.mod go.sum

# 8) CI 里固定加这两个开关
export GOFLAGS=-mod=readonly              # 构建不许改 go.mod，否则构建结果不可复现
export GOPROXY=https://goproxy.cn,direct  # 逗号后的 direct 是兜底；私有模块另见下面的表

# 9) 本地要同时改主服务与一个自有库时用工作区，不要用 replace
go work init . ../order-sdk
#    go.work 绝不能提交进仓库：CI 会用到本地路径，表现为「我这儿能编、流水线编不过」

发布带主版本后缀的新版本是另一件容易漏步骤的事，三步缺一不可：

# 1) module 行改成 github.com/acme/order-sdk/v2
#    漏这一步：下游 go get 拿到的永远是 v1 系列，而且提示信息完全看不出原因
# 2) 本模块内部所有「自己 import 自己」的路径也要加 /v2，漏了会同时链进两份代码
# 3) 打 tag 推送。发错了不要删 tag——已经被下载过的版本会留在代理和别人的缓存里，
#    正确做法是在 go.mod 里写 retract 声明作废
git tag v2.0.0 && git push origin v2.0.0

环境变量这一组决定了「能不能拉到依赖」和「拉到的东西可不可信」，是新人机器和 CI 镜像里最常配错的部分。

包组织侧的「定式」比命令更短，只有三条，但它决定了以后每次改动要动几个包：默认把代码放 internal/；按业务能力建包（internal/order 里放订单的模型、逻辑、存储），不要按技术分层建 models / services；接口定义在消费方，只声明自己用到的方法。这三条为什么成立、以及它们如何顺带消掉循环导入，见原理层。

② 原理 · go.mod 里每条指令的真实作用

搞清这一节，能解决一类具体现象：replace 明明写了却「对下游不起作用」，以及升 v2 之后下游拿到的还是 v1。

Go 的依赖管理表面上很简单——一个 go.mod、一个 go.sum、没有 lock 文件。但它的行为经常让从其他语言过来的人意外，因为它的选版算法和其他语言是反的。先把 go.mod 的指令过一遍。

指令作用常见误解或陷阱
module声明模块路径 也是导入前缀发布 v2 时必须在这里加斜杠 v2 忘了改是最高频错误
go声明语言版本下限 决定可用的语言特性它不是工具链版本 也会影响部分 GODEBUG 默认值
toolchain声明构建所用工具链版本 Go 1.21 起可以比 go 指令更新 让语言版本保守而工具链跟进
require声明直接与间接依赖及其版本带 indirect 注释的是传递依赖 手改版本号要跑 tidy 验证
replace把某个模块替换成另一个路径或本地目录只在主模块生效 你的库被别人依赖时 replace 完全被忽略
exclude把某个版本从选版候选里排除实际很少用 因为它管不住传递依赖硬要求该版本的情况
retract发布方声明某个已发布版本作废 Go 1.16 起这是库作者撤回错误版本的正确方式 不要删 tag
go.work多模块本地协同开发 Go 1.18 起不要提交进仓库 它是本地开发文件 会干扰 CI
 
module github.com/acme/order-api

// go 指令是语言版本下限，决定哪些语言特性可用
go 1.24

// toolchain 是构建所用的工具链版本（Go 1.21 起）。
// 和 go 指令分开的意义：语言版本可以保守，工具链可以跟进最新
toolchain go1.27.1

require (
    github.com/go-sql-driver/mysql v1.8.1
    github.com/redis/go-redis/v9 v9.7.0 // 路径里的 /v9 不是笔误：v2 及以上必须带
    google.golang.org/grpc v1.68.0
)

require (
    filippo.io/edwards25519 v1.1.0        // indirect
    github.com/cespare/xxhash/v2 v2.3.0   // indirect
)

// replace 只在主模块里生效。你的库被别人依赖时它会被完全忽略，
// 所以绝不能用 replace 来「修复」库的依赖问题——下游根本看不到
// 用途一：本地联调，指向本地目录
// replace github.com/acme/pkg => ../pkg
// 用途二：临时打补丁，指向自己的 fork
replace github.com/some/broken v1.2.3 => github.com/acme/broken v1.2.3-patch1

// exclude 把某版本从候选里剔除，选版会退到它的下一个可用版本。
// 用得少，因为解决不了「传递依赖明确要求这个版本」的情况
exclude github.com/some/lib v1.4.0

② 原理 · 最小版本选择：Go 依赖行为的根源

搞清这一节，能同时解释两个现象：为什么 Go 不需要 lock 文件，以及为什么依赖发了修复 CVE 的版本而你的构建毫无变化。

MVS 的规则只有一句：把依赖图里每个模块被 require 过的所有版本收集起来，对每个模块取最大值。注意它取的是「被要求过的最大值」，而不是「可用的最新版本」——即使 libC v1.6.0 已经发布，只要没有任何模块要求它，就绝不会被选中。

行为Go 的 MVSnpm 与 Maven 一类由此产生的差异
选版依据取被要求过的最大版本取满足约束的最新版本Go 不会因为上游发了新版就改变构建结果
可复现性go.mod 本身即可唯一确定构建列表需要 lock 文件锁定Go 不需要 lock 文件
升级方式必须显式执行 go get 才升重新安装就可能升Go 的升级是有意识动作 且会被记录进 go.mod
拿到新版的时机只有自己或依赖方提高 require 才会拿到随时可能拿到Go 里安全补丁不会自动生效 要主动升
版本冲突处理取最大值 假定向后兼容可能安装多份不同版本Go 同一主版本只会有一份 不兼容变更只能靠主版本路径隔离
典型意外某个传递依赖把版本顶高了 而你并不知情装出来的版本和别人不一样Go 侧要用 go mod why 追来源
💡
MVS 的直接推论：安全补丁不会自动生效

因为 MVS 只取「被要求过」的最大版本，某个依赖发了修复 CVE 的新版之后，你的构建结果不会有任何变化，除非你主动 go get。这和「自动取最新」的生态在心智模型上完全不同，所以 Go 项目必须把 govulncheck 放进 CI 常驻，靠工具而不是靠依赖管理器发现问题。流水线上该在哪一层设这道卡点，见 CI/CD 流水线设计原则：三个词的边界、分层卡点与 DORA 度量。

② 原理 · go.sum、GOPROXY 与私有模块

搞清这一节，能解决三类现象：私有模块必然 404、校验和不匹配导致构建中断、以及 CI 每次都重新下载全部依赖。

一个常见误解是把 go.sum 当成 lock 文件。它不是：版本由 go.mod 加 MVS 唯一确定，go.sum 只负责校验下载到的内容没被动过。删掉 go.sum 不会改变任何一个依赖的版本。

sequenceDiagram participant G as go 命令 participant C as 本地模块缓存 participant P as GOPROXY 代理 participant S as GOSUMDB 校验和数据库 participant V as 源码仓库 G->>C: 先查缓存里有没有这个模块版本 C-->>G: 命中则直接使用 不产生任何网络请求 G->>G: 判断路径是否匹配 GOPRIVATE 或 GONOPROXY G->>V: 匹配私有规则 直接走 VCS 拉取 绕过代理 G->>P: 不匹配 向代理请求 mod 文件与 zip 包 P-->>G: 返回模块内容 G->>S: 核对内容哈希 私有模块按 GONOSUMDB 跳过这一步 S-->>G: 返回官方记录的哈希 G->>G: 与 go.sum 已有记录比对 不一致立即报错终止构建 G->>C: 校验通过 写入缓存并补齐 go.sum Note over G,S: go.sum 是完整性清单不是版本锁
删掉它不会改变选版结果 只会重新下载并重新记录

关于 vendor：go mod vendor 把依赖源码复制进仓库，构建时加 -mod=vendor（有 vendor 目录时是默认行为）。它的适用场景只有三个：构建环境完全无外网、需要对依赖打本地补丁且不方便 fork、合规要求全部源码可审计。其他情况下 vendor 只会让每次依赖变更产生几千行 diff，把 code review 变成噪音。

关于语义化导入版本：v2 及以上必须在模块路径里带 /v2，这是 Go 独有的设计。原因是 Go 把不同主版本视为不同的包，这样 v1 和 v2 才能在同一个程序里共存——而「我直接依赖 v2 但某个传递依赖还在 v1」是极常见的情况。代价是升主版本时所有 import 都要改，以及库作者必须记得改 module 行。版本 tag 本身的语义与「删了 tag 为什么还能拉到」见 Git 的对象模型与常见操作的真实语义。

② 原理 · 包的组织：按业务分层，不要按技术分层

搞清这一节，能解决「改一个功能要同时动四个包」与「循环导入反复出现」这两个现象。这是 Go 项目结构上影响最大的一个决定。从 MVC 框架过来的人习惯建 models、controllers、services、utils，这在 Go 里会持续产生麻烦。

反模式具体问题推荐做法
models 包放所有结构体所有包都要导入它 它成了循环导入的中心类型定义在使用它的业务包里
controllers 与 services 分层一个功能的代码散在三个包 改动面永远是三处按业务能力建包 一个包含完整一条纵切
utils 或 common 包名字不表达职责 于是什么都往里塞 影响面不可估计按能力命名 如 retry httpx timeutil 一个包一件事
base 或 core 包同 utils 且往往还带全局状态拆成具体职责 全局状态改为显式传递
包名与目录名不一致import 之后引用名和预期不同 阅读成本上升保持一致 单数命名 不用下划线
包名带 pkg 或 lib 前缀导入后写成 pkgorder 全是噪音包名就是业务名 order 就叫 order
一上来就建十几层目录项目还没长出结构 目录先固化了错误的假设从扁平开始 出现三个以上同类文件再拆包

循环导入在 Go 里是编译错误，不是警告。这看起来很严格，实际是好事：它强迫你在设计阶段就理清依赖方向。遇到循环导入时，正确的解法有三种：把共同依赖的类型下沉到一个更基础的包、把接口定义移到消费方（下一节）、或者合并这两个本来就该在一起的包。唯一错误的解法是新建一个 common 包把纠缠的东西塞进去，那只是把循环推迟到下一次。依赖方向与接缝该切在哪的一般性讨论见 设计模式的本质与代价：接缝、SOLID 取舍与现代语言内建能力。

cmd/xxx可执行程序入口 每个子目录一个 main无 纯约定有多个二进制时才需要 单二进制项目可以把 main 放根目录
internal/只能被本模块导入的私有代码有 编译器强制默认把所有代码放这里 需要对外暴露时再挪出来
pkg/意图对外暴露的公共库无 纯约定争议最大的一个 单体应用里它等于给每个 import 加一层噪音 不建议用
api/协议定义 如 proto 与 openapi无有 IDL 时有用
configs 与 deployments配置与部署文件无按团队习惯 不影响代码结构
test 或 testdatatestdata 被 go 工具链忽略testdata 有特殊语义固定输入放 testdata 它不会被当成包编译

② 原理 · 接口定义在消费方

搞清这一节，能解决「单测要 mock 二十个方法」与「两个业务包互相导入」这两类问题。这条惯例和 Java 相反，原因是Go 的接口是隐式实现——实现方不需要知道接口存在。于是消费方可以只声明自己真正需要的方法，依赖关系从「大接口双向牵连」变成「小接口单向依赖」。

// ===== 反例：接口定义在实现方，Java 习惯 =====
// 文件 internal/storage/store.go
package storage

// 一个大而全的接口，然后自己实现它
type Store interface {
    GetUser(ctx context.Context, id int64) (*User, error)
    SaveUser(ctx context.Context, u *User) error
    ListOrders(ctx context.Context, uid int64) ([]*Order, error)
    // 再加二十个方法……
}

type mysqlStore struct{ db *sql.DB }

func New(db *sql.DB) Store { return &mysqlStore{db: db} }

// 后果：order 包只想用 GetUser，却被迫依赖整个 Store；
// 写单测要 mock 二十多个方法；接口加一个方法，所有假实现全部编译不过


// ===== 正例：接口定义在消费方，只声明自己需要的 =====
// 文件 internal/order/service.go
package order

// 只有一个方法，因为这个包只用到一个。
// storage 包完全不知道 order 包的存在，依赖方向严格单向
type UserGetter interface {
    GetUser(ctx context.Context, id int64) (*User, error)
}

type Service struct {
    users UserGetter
}

func NewService(users UserGetter) *Service { return &Service{users: users} }

func (s *Service) Create(ctx context.Context, uid int64, skus []int64) error {
    u, err := s.users.GetUser(ctx, uid)
    if err != nil {
        return fmt.Errorf("get user %d: %w", uid, err)
    }
    if u.Blocked {
        return ErrUserBlocked
    }
    return s.insert(ctx, u, skus)
}

// 文件 internal/order/service_test.go
// 假实现只需要一个方法，三行搞定；接口以后加方法也不影响这里
type fakeUsers struct{ u *User }

func (f fakeUsers) GetUser(context.Context, int64) (*User, error) { return f.u, nil }

这条原则还有一个连带好处：它天然解决了大部分循环导入。order 需要用户数据、user 需要订单数量做统计，按「接口定义在实现方」的写法这两个包会互相导入；按「定义在消费方」的写法，两个包各自声明一个单方法接口，彼此不导入对方，装配在 main 里完成。假实现与真实依赖各该用在哪一层测试，见 测试策略与可测性设计。

② 原理 · init 的危险与显式装配

搞清这一节，能解决「跑一个纯函数单测却连上了数据库」和「启动报错栈离真正的配置问题很远」这两个现象。

init() 的执行顺序是确定的：先递归初始化所有被导入的包，同一个包内先初始化包级变量再执行 init，多个文件按文件名顺序。确定不等于好用——依赖这个顺序就等于依赖了导入图的实现细节。

// ===== 反模式：用 init 做隐式初始化 =====
var db *sql.DB

func init() {
    // 问题一：不能返回 error，只能 panic 或 log.Fatal，后者跳过所有 defer
    // 问题二：只要有人导入这个包就会触发，写纯函数单测也会被迫连数据库
    // 问题三：执行顺序取决于导入图，改一处导入就可能改变行为
    // 问题四：拖慢启动，且报错栈离真正的配置问题很远
    var err error
    db, err = sql.Open("mysql", os.Getenv("DSN"))
    if err != nil {
        log.Fatal(err)
    }
}

// ===== 推荐：显式构造，错误可处理，依赖关系一眼看清 =====
type App struct {
    DB    *sql.DB
    Cache *redis.Client
    Order *order.Service
}

func NewApp(ctx context.Context, cfg Config) (*App, error) {
    db, err := sql.Open("mysql", cfg.DSN)
    if err != nil {
        return nil, fmt.Errorf("open mysql: %w", err)
    }
    db.SetMaxOpenConns(cfg.MaxConns)
    db.SetConnMaxLifetime(30 * time.Minute)
    // sql.Open 不建立任何连接，必须 Ping 才知道配置对不对。
    // 放在启动阶段失败，比线上第一个请求才失败好得多
    if err := db.PingContext(ctx); err != nil {
        return nil, fmt.Errorf("ping mysql: %w", err)
    }

    rdb := redis.NewClient(&redis.Options{Addr: cfg.RedisAddr})
    if err := rdb.Ping(ctx).Err(); err != nil {
        return nil, fmt.Errorf("ping redis: %w", err)
    }

    // 依赖关系全写在这里，谁依赖谁一目了然，不需要读 init 反推
    return &App{
        DB:    db,
        Cache: rdb,
        Order: order.NewService(storage.NewUserRepo(db)),
    }, nil
}

func (a *App) Close() error {
    // errors.Join 让多个 Close 的错误都能带出去（Go 1.20 起）
    return errors.Join(a.DB.Close(), a.Cache.Close())
}

// ===== init 仅有的两个合理用途 =====
func init() {
    // 一：把自己注册到注册表里。database/sql 的驱动就是这个模式，
    // 它的必要性来自「导入即生效」这个语义本身就是设计意图
    sql.Register("mydriver", &myDriver{})
}

// 二：包级变量的复杂初始化。但能用 var 直接写完就不要动 init，
// 下面这行比放进 init 里更清晰，且编译期就能发现正则写错
var emailLike = regexp.MustCompile(`^[^@\s]+@[^@\s]+$`)

场景该怎么做为什么代价
单体服务，代码完全自用一个模块，全部代码放 internal/，不建 pkg/internal 由编译器强制，外部模块导入直接失败，边界不靠文档以后要对外暴露某个包时要挪目录并改 import
一个仓库出多个二进制（api、worker、迁移工具）仍是一个模块，cmd/ 下每个子目录一个 main共享 internal 零成本，依赖版本天然一致所有二进制共用一份依赖版本，升级影响面是全部
要对外发布的公共库单独仓库单独模块，根目录即包，主版本靠 /v2 隔离下游只能通过路径后缀共存两个主版本每个导出符号都是长期承诺；replace 对下游完全无效
monorepo 里有多个需独立发版的单元每个单元一份 go.mod，本地 go work init 串起来版本线互不牵连，下游可以只升其中一个跨模块改动必须发版才生效；go.work 一旦提交，CI 会用到本地路径
内部 SDK 给多个团队使用独立模块 + 私有代理 + GOPRIVATE 配好三件套路径不外泄，版本可控，可回溯要长期维护 tag 与兼容性，发错版只能 retract，不能删 tag
构建机无外网，或合规要求源码可审计go mod vendor，构建加 -mod=vendor构建完全不依赖网络与代理可用性每次依赖变更几千行 diff，评审噪音大，容易漏看真实改动
上游依赖有 bug 且短期内不会修fork 后在主模块写 replace，同时记录退出条件主模块的 replace 立刻生效，不必等上游只对主模块有效，库里这么写等于没写；容易变成永久分叉
还不确定要不要拆服务先在单模块里按业务能力分包，拆包不拆模块包边界改起来是一次重命名，模块边界改起来是一次发版流程包多了要靠约定维持依赖方向，没有编译器帮你挡住包间乱引用

③ 场景 · 依赖出问题时的判断路径与不适用边界

依赖类故障的症状和根因往往离得很远，下面这张表把症状直接落到第一条该敲的命令上。

症状先敲什么输出怎么判读对应根因
CI 报 go.mod 需要更新 但本地构建正常go mod tidy 之后看 git diffdiff 非空说明本地改了 import 没同步提交漏跑 tidy 或只提交了代码没提交 go.mod
某依赖的版本比自己写的高go mod why -m 模块 与 go mod graph导入链的第一段就是把它顶高的直接依赖MVS 取被要求过的最大值 传递依赖要求了更高版本
私有模块 404 或提示找不到go env GOPRIVATE GONOPROXY GONOSUMDB三者为空说明请求被发去了公共代理私有路径规则没配 内部路径同时被外泄
提示校验和不匹配 构建中断go mod verify 并核对 go.sum 里该版本的记录本地缓存与 go.sum 不一致 或 go.sum 与官方记录不一致上游改了 tag 指向 或代理缓存被污染
升级后一大片包编译失败git checkout go.mod go.sum 回退后逐个升逐个升能定位到具体哪个依赖引入了不兼容变更一次 go get -u 顶高了太多依赖
本地能编 流水线编不过对比两边 go env 并检查仓库里有没有 go.workgo.work 或 replace 指向了只有本地存在的路径本地开发文件进了仓库
拉依赖极慢或频繁超时go env GOPROXY 与 GOMODCACHEGOPROXY 为 direct 且 CI 没缓存模块目录直连境外仓库 且每次构建重新下载全部依赖
已知漏洞一直没被修掉govulncheck ./... 看有没有进 CI本地有报告但流水线没有这一步指望依赖管理器自动升版本 而 MVS 从不自动升

不适用边界：三件事不要做。一是不要用 replace 去修一个「库」的依赖问题——它只在主模块生效，下游拿到的还是原样，正确做法是升级依赖或发一个修好的版本。二是不要为了「以后可能要拆」提前切成多模块：模块的代价是每次跨模块改动都要走一遍发版，而包的边界改起来只是一次重命名，单仓单模块按业务分包能撑到相当大的规模。三是不要把 vendor 当默认选项，它的适用条件只有无外网与合规审计两类。另外，服务真的要拆开之前先把账算清，见 微服务的代价模型：拆分前先把账算清。

回到最上面两条判断：依赖侧记住 MVS 取「被要求过的最大版本」，因此构建可复现但安全补丁必须主动升；包组织侧记住按业务能力分包、默认放 internal/、接口定义在消费方。这两组三条做到了，「在我机器上是好的」和「改一个功能动四个包」这两类问题基本消失。

本篇在簇里的位置：前面几篇讲的是单个包内部怎么写对，从这篇开始转向工程组织——代码放哪、依赖怎么管、边界靠什么守住。下一步是给这套工程加上可观察的输出。

最容易踩的坑

❌
避坑清单
  • 以为 go.sum 是 lock 文件：版本由 go.mod 加 MVS 决定，删掉 go.sum 不改变任何版本，它只管完整性校验。
  • 用 replace 修库的依赖问题：replace 只在主模块生效，你的库被别人依赖时它被完全忽略，问题原样暴露给下游。
  • 发布 v2 忘了改 module 行加 /v2：下游 go get 拿到的还是 v1 系列，而且报错信息很难懂。
  • 发错版本后删 tag：已被下载过的版本留在代理与他人缓存里，删了照样拉得到。正确做法是写 retract 并发新版。
  • 直接 go get -u ./... 升级：一次把几十个依赖顶高，出问题无法定位。用 -u=patch 或逐个升。
  • 手改 go.mod 里的版本号却不跑 go mod tidy：间接依赖没跟着调整，构建结果和你以为的不是一回事。
  • 指望依赖管理器自动带来安全补丁：MVS 不会自动升版本，必须把 govulncheck 放进 CI。
  • 私有模块不配 GOPRIVATE：模块路径被发送到公共代理和校验和数据库，内部仓库名泄露，而且构建必然失败。
  • CI 不设 -mod=readonly：构建过程悄悄改了 go.mod，产物与仓库状态不对应，不可复现。
  • CI 不缓存 GOMODCACHE：每次流水线重新下载全部依赖，慢且强依赖代理可用性。
  • 建 utils 或 common 包：名字不表达职责，最终变成什么都往里塞的垃圾场，还成为循环导入的中心。
  • 用 models 加 controllers 按技术分层：一个功能的改动永远横跨三四个包，循环导入频发。
  • 遇到循环导入就新建一个 common 包：这是把问题推迟而不是解决，正确做法是把接口移到消费方或合并这两个包。
  • 接口定义在实现方且做成大接口：每个消费者被迫依赖全部方法，单测要造一堆假方法，接口加方法就全线编译失败。
  • 用 init() 建数据库连接或读配置：不能返回 error、测试躲不开、顺序依赖导入图、报错离根因很远。改成显式 NewApp。
  • 把 go.work 提交进仓库：它是本地多模块开发文件，进了仓库会让 CI 用到错误的本地路径。
  • 一上来就照搬标准布局建十几层目录：项目还没长出结构，目录先固化了错误假设。从扁平开始，出现三个以上同类文件再拆。
  • 为了「以后可能拆」提前切多模块：跨模块改动从此都要发版，收益为零而摩擦立刻产生。
