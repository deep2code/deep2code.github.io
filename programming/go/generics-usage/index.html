Go 泛型该用在哪，以及标准库的变化

🏷️ Go 语言总览

这篇只讲用途和生态：泛型该用在哪、标准库因为它变了什么、哪些地方用了会后悔。类型参数语法、类型集、GC shape stenciling 与字典传递、以及能力边界那一整套机制，在站内《Go 泛型的机制与约束设计》里已经展开，这里不重复。

真正适合泛型的四类场景

三年多下来，泛型在生产代码里站得住脚的位置其实很集中，就四类。判断标准是：逻辑完全不依赖具体类型，但你又不想让值装箱到 interface{} 里。

一、容器与数据结构

这是泛型最无争议的用途。以前写 Set 只能 map[interface{}]struct{}，取出来还要断言；现在类型安全且零装箱。

// 类型安全的 Set，完整可用版本
type Set[T comparable] map[T]struct{}

func NewSet[T comparable](items ...T) Set[T] {
    s := make(Set[T], len(items))
    s.Add(items...)
    return s
}

func (s Set[T]) Add(items ...T) {
    for _, it := range items {
        s[it] = struct{}{}
    }
}

func (s Set[T]) Has(item T) bool {
    _, ok := s[item]
    return ok
}

// 返回 Set 而不是 slice，方便链式使用；容量按较小的那个预估
func (s Set[T]) Intersect(other Set[T]) Set[T] {
    small, big := s, other
    if len(big) < len(small) {
        small, big = big, small // 总是遍历较小的那个，复杂度 O(min(m,n))
    }
    out := make(Set[T], len(small))
    for it := range small {
        if big.Has(it) {
            out[it] = struct{}{}
        }
    }
    return out
}

// 转回有序 slice：map 遍历顺序随机，对外输出必须排序否则结果不可复现
func (s Set[T]) SortedSlice(less func(a, b T) int) []T {
    out := make([]T, 0, len(s))
    for it := range s {
        out = append(out, it)
    }
    slices.SortFunc(out, less)
    return out
}

LRU、优先队列、环形缓冲区、并发安全的 typed map 同理。注意一点：如果元素类型可能是接口，comparable 约束在编译期通得过但运行时可能 panic（接口值装了 slice、map 或函数时比较会崩），这类容器的 key 要么限定为确定的可比较类型，要么改成要求一个 Key() string 方法。

二、集合操作工具

Map、Filter、Reduce 这类函数在泛型之前只能靠复制粘贴或者反射。现在一份实现全类型通用：

// 三个最常用的集合操作。注意都预分配了容量，避免 append 反复扩容
func Map[T, U any](s []T, f func(T) U) []U {
    out := make([]U, len(s)) // 长度确定，直接按索引赋值比 append 快
    for i, v := range s {
        out[i] = f(v)
    }
    return out
}

func Filter[T any](s []T, keep func(T) bool) []T {
    // 容量按输入估，多数场景保留比例较高；极端稀疏时可以先数一遍
    out := make([]T, 0, len(s))
    for _, v := range s {
        if keep(v) {
            out = append(out, v)
        }
    }
    return out
}

func Reduce[T, A any](s []T, init A, f func(A, T) A) A {
    acc := init
    for _, v := range s {
        acc = f(acc, v)
    }
    return acc
}

// 按 key 分组，这个比 Map/Filter 更常用，业务代码里到处都是
func GroupBy[T any, K comparable](s []T, key func(T) K) map[K][]T {
    out := make(map[K][]T)
    for _, v := range s {
        k := key(v)
        out[k] = append(out[k], v) // nil slice 上 append 是合法的，不用先初始化
    }
    return out
}
✅
但先查标准库

写这类工具之前先看 slices 和 maps。去重、判断包含、找索引、取最值、排序、二分查找全都有了，自己写只是多一份要维护的代码。真正需要自己写的只有 Map、Filter、Reduce、GroupBy 这几个标准库明确没收的（社区提案被拒的理由是这些函数的形态争议太大）。

三、约束数值计算

Sum、Average、带权重的聚合这类函数确实适合泛型。但要提醒一个容易多此一举的地方：1.21 起 min 和 max 是内置函数，两个标量取最值根本不需要泛型函数；slice 取最值用 slices.Min 和 slices.Max。自己写 Max[T] 已经是重复劳动了。

// 数值聚合：真正值得自己写的是标准库没有的那些
// 注意 Sum 的溢出问题：int8 的切片求和很容易溢出，返回类型和输入同类型是有意的取舍
func Sum[T Number](xs []T) T {
    var total T
    for _, x := range xs {
        total += x
    }
    return total
}

// 平均值必须返回 float64，否则整数切片会被截断，这是个高频 bug
func Average[T Number](xs []T) float64 {
    if len(xs) == 0 {
        return 0 // 或者返回 (float64, bool)，看调用方是否需要区分空集
    }
    var total float64
    for _, x := range xs {
        total += float64(x) // 逐个转换而不是先求和再转，避免整型溢出
    }
    return total / float64(len(xs))
}

// 1.21 之后这些都不用自己写了：
// min(a, b)           内置函数，支持任意有序类型，可变参数
// max(a, b, c)        内置函数
// slices.Min(xs)      切片最小值，空切片会 panic
// slices.MinFunc(...) 自定义比较

四、减少样板的通用小工具

// Ptr：把字面量转成指针。写 JSON 可选字段和 SDK 配置时极其常用
// 以前每个类型都要写一个 aws.String/aws.Int64，现在一个搞定
func Ptr[T any](v T) *T { return &v }

// Deref：反向操作，nil 时给零值或指定默认值
func Deref[T any](p *T, def T) T {
    if p == nil {
        return def
    }
    return *p
}

// 类型安全的对象池包装：标准库 sync.Pool 的 Get 返回 any，每次都要断言
type Pool[T any] struct {
    p sync.Pool
}

func NewPool[T any](newFn func() T) *Pool[T] {
    return &Pool[T]{p: sync.Pool{New: func() any { return newFn() }}}
}

func (p *Pool[T]) Get() T  { return p.p.Get().(T) } // 断言收敛在这一处，外部不用管
func (p *Pool[T]) Put(v T) { p.p.Put(v) }

// 用法：bufPool := NewPool(func() *bytes.Buffer { return new(bytes.Buffer) })
// 注意 Pool 里存指针而不是值，否则 Put 时会装箱产生一次分配

标准库的泛型化：这才是最大的实际收益

如果只能记住这篇的一件事，就是这个：slices 和 maps 两个包基本消灭了手写循环去找最大值、去重、判断包含、排序这类样板代码。泛型语法你可能一辈子不用写，但这两个包每天都在用。

不该用泛型的场景

比「能用泛型」更重要的是知道什么时候别用。下面三类是我见过返工最多的。

一、只有一种类型在用它。为一个只处理 *User 的函数加 [T any]，除了让签名变长、报错变难读之外没有任何收益。判断标准很简单：数一下实际的实例化点，少于三个就先别抽象。

二、用泛型替代接口做多态。这是最伤可读性的误用。接口表达「行为」，泛型表达「类型参数化」——前者回答「这个东西能做什么」，后者回答「这段逻辑能用在哪些类型上」。混淆两者会写出一眼看不懂的代码：本该是 func Process(h Handler) 的地方写成 func Process[T Handler](h T)，除了让调用方拿不到统一类型、没法放进同一个 slice 之外，毫无好处。

三、业务层实体与仓储。Repository[T] 看起来能省掉一堆重复的 CRUD，实际上活不过三个月。

stateDiagram-v2 [*] --> Clean Clean : 第一周 Repository T 只有五个方法 看起来很优雅 Clean --> Leaky : 订单要按状态加时间范围查 用户不需要 Leaky : 泛型接口上开始长出各实体专属的方法 Leaky --> Casting : 某些实体要联表 泛型签名表达不了 Casting : 内部开始出现 any 断言与反射拼 SQL Casting --> Duplicated : 为了类型安全又给每个实体写了具体仓储 Duplicated : 泛型层与具体层并存 两套代码都要维护 Duplicated --> Removed : 最终删掉泛型层 回到每个实体一个仓储 Removed --> [*] note right of Leaky 根因是各实体的查询需求本质上不同 泛型只能抽象出结构相同的部分 而 CRUD 里真正相同的只有主键查询与插入 这两个方法省下来的代码远不值这套抽象的成本 end note

真正可行的折中是：只把结构确实相同的那一小块泛型化——比如按主键查询、批量插入、软删除这三个操作抽成泛型辅助函数，而每个实体仍有自己的具体仓储类型，复杂查询写在那里。这样既省掉了样板，又没有把扩展路径堵死。

给现有库加泛型 API：迁移与兼容

有一条硬约束必须先说清楚：类型参数是函数签名的一部分，增删类型参数是破坏性变更。func Do(x any) 改成 func Do[T any](x T) 对多数调用方是兼容的（推断能工作），但 func Do[T any]() 加一个参数变成 func Do[T, U any]() 就会让所有显式实例化的调用点编译失败。所以泛型 API 的类型参数列表要一次性设计好。

// 给库加泛型 API 的推荐做法：新增而不是修改，旧 API 用新实现兜底

// 旧 API 保留，标记为过时但不删除（Deprecated 注释是 gopls 与 staticcheck 识别的约定格式）
//
// Deprecated: 请改用 FindBy，它返回具体类型，调用方不再需要类型断言。
// 本函数会在 v3 中移除。
func Find(items []any, pred func(any) bool) any {
    // 内部转调泛型实现，避免两份逻辑各自演化
    idx := IndexBy(items, pred)
    if idx < 0 {
        return nil
    }
    return items[idx]
}

// 新的泛型 API：返回 (T, bool) 而不是 T，让「没找到」和「找到零值」可区分
// 这个签名细节比泛型本身更重要，很多库在这里返回了误导性的零值
func FindBy[T any](items []T, pred func(T) bool) (T, bool) {
    for _, it := range items {
        if pred(it) {
            return it, true
        }
    }
    var zero T
    return zero, false
}

func IndexBy[T any](items []T, pred func(T) bool) int {
    for i, it := range items {
        if pred(it) {
            return i
        }
    }
    return -1
}

另外两个实践要点：不要为了泛型化去动稳定跑了几年的代码（收益是零，回归风险是实的）；约束类型尽量导出，否则调用方没法基于你的约束写自己的泛型包装函数。

最容易踩的坑

❌
避坑清单
  • 把所有工具函数改成泛型：只有一个实例化点的泛型等于纯粹的阅读负担。少于三个实例化点就别抽象。
  • 写泛型 Repository：各实体的查询需求本质不同，泛型层很快会长出专属方法、退化成 any 断言，最后不得不删掉重写。只把主键查询、批量插入这类结构完全相同的操作抽成泛型辅助函数。
  • 用泛型做依赖注入：类型参数在编译期固定，无法在运行时替换实现，mock 和插件都做不了。这是接口的活。
  • 为了用新特性而重构稳定代码：跑了三年没出问题的 interface{} 代码，改成泛型的唯一确定收益是引入回归风险。
  • slices.Compact 当去重用：它只合并相邻的重复元素，不排序直接用等于没去重。必须先 slices.Sort。
  • slices.Min / Max 传空切片：直接 panic，不是返回零值。调用前判长度。
  • 以为 maps.Keys 返回切片：标准库 1.23 起返回的是迭代器，要切片必须 slices.Collect(maps.Keys(m))。从 x/exp/maps 迁移过来的代码这一行必须改。
  • slices.SortFunc 的回调返回 bool：它要的是 int（负零正三态），从 sort.Slice 迁移时直接把 less 函数搬过去会编译失败或排序结果错乱。
  • maps.Clone(nil) 返回 nil：不是空 map，后续写入直接 panic。
  • 泛型 API 的类型参数列表后期再改：增删类型参数是破坏性变更，所有显式实例化的调用点都会编译失败。一次性设计好。
  • 约束类型不导出：调用方无法基于你的约束写包装函数，只能复制一份约束定义。
  • 自己写 Max 和 Min：1.21 起它们是语言内置函数且支持可变参数，切片版在 slices 包里，自己写纯属重复劳动。
