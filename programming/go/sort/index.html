从 sort.Slice 到 slices.Sort：两套 API 的分工

Go 1.21 把 slices 包收进标准库，排序这件事有了第二套 API。新的更快也更短，原因是它不用反射：sort.Slice 接收 any 加一个 less 闭包，必须靠 reflect.Swapper 构造交换函数；slices.SortFunc 是泛型函数，编译期就知道元素类型和大小，交换是直接的内存操作。

⚠️
从 x/exp/slices 迁移时最容易出的错

golang.org/x/exp/slices 早期版本的 SortFunc 接收的是返回 bool 的 less 函数，进标准库后改成了返回 int 的 cmp 函数。直接把老代码的 func(a, b T) bool 挪过来，编译能过（因为 bool 不是 int，其实会报错）或者语义悄悄反了的情况都有。迁移时务必逐个改成 cmp.Compare 风格。

稳定性：什么时候必须要它

slices.Sort 和 slices.SortFunc 都不稳定（底层是 pdqsort），相等元素的相对顺序会被打乱。需要稳定必须显式用 SortStableFunc，代价是稳定排序需要额外的插入排序与归并步骤，通常慢一些。

场景是否必须稳定理由
两趟实现多级排序必须第二趟不稳定会把第一趟的次要键顺序打乱
列表同优先级要按提交先后展示必须业务语义就是保持输入顺序
分页查询的排序键有大量重复值必须不稳定会导致翻页时同一条记录重复出现或漏掉
一次比较里写全所有级别的键不必比较函数已构成全序 结果唯一确定
排序键是主键或唯一索引不必不存在相等元素
只为了取最大最小值不必用 slices.Max 与 slices.Min 更快 根本不用排序

注意第三行：分页配合不稳定排序是个隐蔽的线上 bug。按「状态」排序分页，状态相同的记录顺序在两次查询间可能不同，用户翻到第二页会看到第一页出现过的记录。修法是在排序键末尾追加一个唯一键（比如 ID）来保证全序，而不是依赖稳定排序——因为数据库侧的排序你也控制不了稳定性。

比较函数：严格弱序与 cmp 包

排序算法假定比较函数构成严格弱序：相等元素必须返回 0，cmp(a,b) 为负则 cmp(b,a) 必须为正，并且满足传递性。违反了会怎样？官方的说法是「结果未定义」，实际表现是结果错乱，某些输入下分区逻辑失效还可能 panic。这类 bug 极难复现，因为它取决于数据的初始排列。

错误写法为什么错后果正确写法
只判大于 否则返回 1相等时返回非零 声称 a 小于 b 且 b 小于 a结果错乱 可能 panic用 cmp.Compare 它保证相等返回 0
比较函数里带随机数或时间同一对元素两次比较结果不同 破坏传递性结果不可复现先算出排序键 再按键比较
对浮点直接相减取符号NaN 参与比较时全部判定失效 大数相减还可能溢出NaN 混入后顺序完全乱用 cmp.Compare 它把 NaN 排在最前
比较函数里访问可变的外部状态排序过程中状态变了 前后判定不一致结果错乱比较函数必须是纯函数
多级比较写成嵌套 if 但漏掉相等分支某一级相等时直接返回了非零后续级别永远不生效用 cmp.Or 串联 逐级返回
对字符串用大于小于号做本地化排序字节序不等于语言意义上的字典序中文与带音标字符顺序不符合预期需要本地化用 x/text/collate
 
type Employee struct {
    Dept   string
    Level  int
    Salary int
    Name   string
    Joined time.Time
}

// 推荐写法：一次比较里按优先级依次判定。
// cmp.Or（Go 1.22 起）返回参数里第一个非零值，正好匹配「返回负数零正数」的约定
func sortEmployees(es []Employee) {
    slices.SortFunc(es, func(a, b Employee) int {
        return cmp.Or(
            strings.Compare(a.Dept, b.Dept),                       // 一级：部门升序
            cmp.Compare(b.Salary, a.Salary),                       // 二级：薪资降序，注意 b 在前
            cmp.Compare(a.Joined.UnixNano(), b.Joined.UnixNano()), // 三级：入职早的在前
            strings.Compare(a.Name, b.Name),                       // 兜底：保证全序，结果完全确定
        )
    })
}

// 另一种思路：两趟稳定排序，先排次要键再排主要键。
// 只有 Stable 版本能这么用，slices.Sort 与 SortFunc 都不稳定，第二趟会毁掉第一趟的结果
func sortTwoPass(es []Employee) {
    slices.SortStableFunc(es, func(a, b Employee) int {
        return cmp.Compare(b.Salary, a.Salary) // 次要键
    })
    slices.SortStableFunc(es, func(a, b Employee) int {
        return strings.Compare(a.Dept, b.Dept) // 主要键，同部门内薪资顺序被保留
    })
}

// 错的比较函数：相等时也返回 1，不满足严格弱序，结果未定义
func brokenCmp(a, b Employee) int {
    if a.Salary > b.Salary {
        return -1
    }
    return 1
}

// 对的：相等必须返回 0。用 cmp.Compare 就不可能写错这一点
func goodCmp(a, b Employee) int { return cmp.Compare(b.Salary, a.Salary) }

// 二分查找必须和排序用同一套比较逻辑，否则找不到或找错位置
func findByName(sorted []Employee, name string) (Employee, bool) {
    i, ok := slices.BinarySearchFunc(sorted, name,
        func(e Employee, target string) int { return strings.Compare(e.Name, target) })
    if !ok {
        return Employee{}, false
    }
    return sorted[i], true
}

slices 包速查：哪个函数会改原切片

这张表里最需要注意的是「是否修改原切片」这一列——slices 包里有一半函数是原地操作的，把返回值当成新切片用、同时别人还持有原切片，就会读到意外变化的数据。

函数作用是否修改原切片注意事项
slices.Contains 与 ContainsFunc是否存在某元素否线性扫描 频繁查找应改用 map
slices.Index 与 IndexFunc返回下标 不存在返回负一否同上
slices.BinarySearch 与 BinarySearchFunc有序切片二分查找否必须已排序 且比较逻辑要与排序一致
slices.Compact 与 CompactFunc去掉相邻重复元素是 原地压缩只去相邻重复 必须先排序才能全局去重
slices.Insert在指定位置插入是 可能扩容并返回新切片必须接收返回值 否则插入丢失
slices.Delete 与 DeleteFunc删除区间或按条件删除是 原地移动底层数组容量不变 内存不释放 尾部槽位会被清零
slices.Clone浅复制一份新切片否元素是指针时指向的对象仍然共享
slices.Equal 与 EqualFunc逐元素比较否长度不同直接为假
slices.Max 与 Min取最值否空切片会 panic 要先判长度
slices.Reverse原地反转是无返回值 直接改原切片
slices.Concat拼接多个切片 Go 1.22 起否 返回新切片比反复 append 少一次中间分配
slices.Chunk按大小切块 返回迭代器 Go 1.23 起否产出的块是原切片的子切片 共享底层数组

切片的底层机制与真实事故

切片是「指针 + 长度 + 容量」三元组。它按值传递，但三元组里的指针指向的底层数组是共享的，几乎所有切片事故都来自这一点。

sequenceDiagram participant A as 底层数组 五个槽位 participant B as base 切片 长度五 容量五 participant H as head 切片 取前两个 长度二 B->>A: 初始内容 一 二 三 四 五 B->>H: head 等于 base 前两个元素 长度是二 但容量仍然是五 Note over H,A: 关键 子切片的容量从它的起点一直延伸到底层数组末尾
所以 head 后面还有三个可写位置 append 不会触发扩容 H->>A: append 写入底层数组下标二 A-->>B: base 的第三个元素被悄悄改掉 原数据丢失 Note over H,A: 修法 用三索引切法同时限制容量
此时 append 必然重新分配并复制 base 不受影响 
func sliceTraps() {
    base := []int{1, 2, 3, 4, 5} // 长度 5 容量 5

    // 陷阱一：子切片共享底层数组，append 会覆盖原数据
    head := base[:2]        // 长度 2，容量仍然是 5
    head = append(head, 99) // 写进了底层数组下标 2
    fmt.Println(base)       // [1 2 99 4 5] ← base 被悄悄改了

    // 修法：三索引切法把容量也限制住，append 时必然重新分配
    base = []int{1, 2, 3, 4, 5}
    safe := base[:2:2]      // 长度 2 容量 2
    safe = append(safe, 99) // 触发扩容并复制，base 保持原样
    fmt.Println(base, safe) // [1 2 3 4 5] [1 2 99]

    // 陷阱二：切片按值传递，元素改动可见，但 append 的结果不可见
    modify(base) // base[0] 变成 -1，调用方能看到
    grow(base)   // 调用方看不到新增元素，因为 append 改的是被调方的局部三元组

    // 陷阱三：从大数组截一小段长期持有，整个底层数组都无法回收
    big := make([]byte, 100<<20)
    leak := big[:16]                        // 只要 16 字节，却让 100MB 无法释放
    kept := append([]byte(nil), big[:16]...) // 显式复制，切断对大数组的引用
    _, _ = leak, kept

    // 陷阱四：slices.Delete 原地修改原切片，底层数组容量不变
    s := []string{"a", "b", "c", "d"}
    t := slices.Delete(s, 1, 2)
    fmt.Println(s[:3], t) // [a c d] [a c d] ← s 的内容也被改了
    // 新版本会把尾部空出来的槽位清零，让元素指向的对象可以被 GC 回收，
    // 但底层数组本身仍按原容量保留，所以反复 Delete 内存不会降下来

    // 想真正释放：显式复制一份，让旧数组失去引用
    shrunk := slices.Clone(t)
    _ = shrunk
}

func modify(s []int) {
    if len(s) > 0 {
        s[0] = -1 // 通过共享的底层数组写入，调用方可见
    }
}

func grow(s []int) {
    s = append(s, 6) // 只改了本函数的局部三元组，调用方完全看不到
    _ = s
}

大数据量：不要什么都全排序

数据量上来之后，「排序」这个动作本身往往就不该做。三条判断：只要前 K 个就用堆，只要判断有序就用 IsSorted，数据在数据库里就让数据库排。

需求全排序方案更好的方案差距
取最大的 K 个全排序后取前 K容量 K 的最小堆 边读边淘汰复杂度从 n 乘 log n 降到 n 乘 log k 内存只占 K 个
取最大或最小一个排序后取首尾slices.Max 与 slices.Min 一次遍历从 n log n 降到 n
只想知道是否已有序排一遍再比较slices.IsSortedFunc从 n log n 降到 n 且不改数据
数据超过内存全部读入再排分块排序落临时文件 再多路归并内存从数据量级降到块大小级
数据本来在数据库里拉到内存排用 ORDER BY 加索引让数据库排省掉全部网络传输与内存 详见站内数据库优化篇
需要分页全排序后切片游标分页 按唯一键推进避免深翻页时的大量无用排序
排序键计算昂贵比较函数里现算先算好键做成结构体 再按键排键的计算次数从 n log n 次降到 n 次
 
// 只要 Top K 时不要全排序：维护一个容量 K 的最小堆，
// 复杂度 n 乘 log k，内存只占 K 个元素，而且输入可以是流式的
type minHeap []int

func (h minHeap) Len() int           { return len(h) }
func (h minHeap) Less(i, j int) bool { return h[i] < h[j] }
func (h minHeap) Swap(i, j int)      { h[i], h[j] = h[j], h[i] }
func (h *minHeap) Push(x any)        { *h = append(*h, x.(int)) }
func (h *minHeap) Pop() any {
    old := *h
    n := len(old)
    v := old[n-1]
    *h = old[:n-1]
    return v
}

// TopK 从一个迭代器里取最大的 k 个。数据量千万级时这和全排序是能否跑动的区别
func TopK(seq func(yield func(int) bool), k int) []int {
    if k <= 0 {
        return nil
    }
    h := &minHeap{}
    seq(func(v int) bool {
        if h.Len() < k {
            heap.Push(h, v)
            return true
        }
        // 堆顶是当前这 k 个里最小的，只有比它大才有资格进来
        if v > (*h)[0] {
            heap.Pop(h)
            heap.Push(h, v)
        }
        return true
    })
    out := slices.Clone(*h)
    slices.Sort(out)
    slices.Reverse(out) // 需要从大到小时再反转一次
    return out
}

// 排序键计算昂贵时：先算键，再按键排。
// 否则比较函数会被调用 n 乘 log n 次，每次都重算一遍键
type keyed[T any] struct {
    key  string
    item T
}

func sortByExpensiveKey[T any](items []T, keyOf func(T) string) {
    ks := make([]keyed[T], len(items))
    for i, it := range items {
        ks[i] = keyed[T]{key: keyOf(it), item: it} // 键只算 n 次
    }
    slices.SortFunc(ks, func(a, b keyed[T]) int { return strings.Compare(a.key, b.key) })
    for i := range ks {
        items[i] = ks[i].item
    }
}
⚠️
最容易踩的坑

1. 以为 slices.Sort 是稳定的：它不稳定，两趟多级排序必须用 SortStableFunc，否则第二趟毁掉第一趟的结果。

2. 比较函数相等时没返回 0：结果未定义，可能顺序错乱也可能 panic，而且只在特定数据排列下复现。用 cmp.Compare 就不会犯。

3. 从 x/exp/slices 迁移时没改比较函数：标准库版本是返回 int 的 cmp，不是返回 bool 的 less，语义完全不同。

4. 分页依赖不稳定排序：排序键有重复值时翻页会重复或漏记录。排序键末尾一定要追加唯一键保证全序。

5. s[:2] 之后 append：容量延伸到底层数组末尾，直接覆盖原数据。传子切片出去前用 s[:2:2] 限容量。

6. 从大切片截一小段长期持有：整个底层数组被保活，看着只用了几十字节实际占着上百 MB。要 slices.Clone 复制。

7. 忘记接收 slices.Insert 的返回值：它可能扩容并返回新切片，不接收就等于插入没发生。

8. 以为 slices.Delete 能释放内存：它只是原地移动，底层数组容量不变，反复删也不会让内存降下来。

9. 忽略 slices.Delete 会改原切片：删除位置之后的元素在原切片里也被挪动了，别人持有原切片就会读到脏数据。

10. slices.Compact 之后仍有重复：它只去相邻重复，必须先排序。

11. slices.Max 传空切片：直接 panic，调用前必须判长度。

12. 在比较函数里做昂贵计算：它会被调用 n 乘 log n 次，先把键算好再排能把计算次数降到 n 次。

13. 为了取前十个元素就全排序千万条数据：用容量 10 的最小堆，复杂度和内存都差一个量级。

结论

新代码一律用 slices 包：slices.Sort 排基础类型，slices.SortFunc 配 cmp.Or 排结构体，需要保序时换 SortStableFunc。sort 包只在「数据不在单一切片里」这一种情况下还有用。比较函数只用 cmp.Compare 和 strings.Compare 拼，不手写大于小于判断，严格弱序这件事就不会出错。

切片那一半的注意力全花在「谁在共享这个底层数组」上：传子切片出去前限容量，长期持有前先复制，用 slices 里的原地函数时记住它会改原数据。这三条覆盖了我见过的所有切片事故。
