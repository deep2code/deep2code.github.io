结构化日志与 log/slog

🏷️ Go 语言

这篇的靶子是：日志出问题的时候，缺的从来不是日志库，而是当初没定下来的那几条约定——trace_id 靠不靠得住、手机号会不会落盘、线上想开 debug 要不要重启、错误在哪一层记录。这些决定几乎全部集中在进程启动那几十行装配代码里，写对一次就长期有效；写漏了，事后只能靠 code review 逐个调用点去追。

💡
这篇怎么读
  • ① 用法：一份可以直接抄的落地骨架（Handler 按环境选、LevelVar 加内网调级端点、ReplaceAttr 统一时间与裁剪 source、contextHandler 自动注入 trace_id、进程级 With 挂服务名与版本），加上字段命名规范表、Handler 速查表与类型级脱敏定式。
  • ② 原理：slog.Handler 作为标准接口带来的生态效应、一条日志从 Enabled 到编码写出的完整链路、三种脱敏方式为什么可靠性差距巨大、级别约定与 log.Fatal 为什么不能进库代码、和 zap 与 zerolog 的逐维度对照。
  • ③ 场景：选库与输出目的地的判断图与决策矩阵、十条上线检查项，以及什么情况下 slog 不是答案。

① 用法 · 结构化日志的落地骨架

下面这段是进程启动时装配日志的完整代码，六个决定（Handler、级别可变、时间格式、source 裁剪、兜底屏蔽、固定字段）全在这里做完。注释只写「为什么必须这么写」，机制原因在原理层展开。

// ---- 全局装配：进程启动时一次配好 ----
// LevelVar 的零值是 LevelInfo，内部用原子操作，可以在运行时安全地改
var logLevel = new(slog.LevelVar)

func setupLogger(env, version string) *slog.Logger {
    opts := &slog.HandlerOptions{
        Level:     logLevel, // 传 Leveler 接口而不是具体 Level，这是能动态调级别的前提
        AddSource: true,     // 带文件行号，代价是每条日志一次栈帧解析
        ReplaceAttr: func(groups []string, a slog.Attr) slog.Attr {
            switch a.Key {
            case slog.TimeKey:
                // 统一成毫秒精度 UTC，日志平台好解析，也比默认格式省字节
                if t, ok := a.Value.Any().(time.Time); ok {
                    a.Value = slog.StringValue(t.UTC().Format("2006-01-02T15:04:05.000Z"))
                }
            case slog.SourceKey:
                // 默认输出绝对路径，会把构建机的目录结构泄出去，裁成 pkg/file.go:12
                if s, ok := a.Value.Any().(*slog.Source); ok {
                    a.Value = slog.StringValue(filepath.Join(
                        filepath.Base(filepath.Dir(s.File)), filepath.Base(s.File)) +
                        ":" + strconv.Itoa(s.Line))
                }
            case "password", "token", "authorization", "id_card":
                // 全局兜底：无论哪一层用这些 key 写进来都不会落盘。
                // 注意这是按字段名匹配的兜底，不能替代类型级的 LogValuer
                return slog.String(a.Key, "[REDACTED]")
            }
            return a
        },
    }

    var h slog.Handler = slog.NewJSONHandler(os.Stdout, opts)
    if env == "dev" {
        h = slog.NewTextHandler(os.Stderr, opts) // 本地用人眼友好的格式
    }
    h = &contextHandler{Handler: h} // 包一层，自动注入 trace_id

    // 进程级固定字段用 With 挂一次，不要每个请求都 With
    l := slog.New(h).With(
        slog.String("service", "order-api"),
        slog.String("version", version),
    )
    slog.SetDefault(l) // 让第三方库以及 log 包的输出都汇流到这里
    return l
}

// ---- 动态调级别：线上开 debug 不用重启进程 ----
// 挂在只对内网开放的管理端口上，绝不要暴露到公网
func levelHandler(w http.ResponseWriter, r *http.Request) {
    var lv slog.Level
    if err := lv.UnmarshalText([]byte(r.URL.Query().Get("level"))); err != nil {
        http.Error(w, "level must be one of debug info warn error", http.StatusBadRequest)
        return
    }
    logLevel.Set(lv)
    slog.Info("log level changed", "level", lv.String())
}

请求域字段怎么带：不要在业务函数签名里传 logger，而是把 trace_id 放进 context，由一个包装 Handler 自动注入。context 本来就要层层传递，logger 不该污染业务签名。

type traceKey struct{}

func WithTrace(ctx context.Context, id string) context.Context {
    return context.WithValue(ctx, traceKey{}, id)
}

// contextHandler 包装任意 Handler，把 ctx 里的 trace_id 自动加到每条日志。
// 业务代码只要用 XxxContext 系列方法，就不需要传 logger 也不需要手写 trace_id
type contextHandler struct{ slog.Handler }

func (h *contextHandler) Handle(ctx context.Context, r slog.Record) error {
    if id, ok := ctx.Value(traceKey{}).(string); ok && id != "" {
        r.AddAttrs(slog.String("trace_id", id))
    }
    return h.Handler.Handle(ctx, r)
}

// 这两个方法必须转发并重新包一层，否则一旦有人调 logger.With，
// 返回的新 logger 里包装层就丢了，trace_id 从此不再注入。
// 这是写自定义 Handler 时最常见的 bug
func (h *contextHandler) WithAttrs(as []slog.Attr) slog.Handler {
    return &contextHandler{Handler: h.Handler.WithAttrs(as)}
}

func (h *contextHandler) WithGroup(name string) slog.Handler {
    if name == "" {
        return h
    }
    return &contextHandler{Handler: h.Handler.WithGroup(name)}
}

// HTTP 中间件：生成 trace_id 并塞进 context，后面所有日志自动带上
func TraceMiddleware(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        id := r.Header.Get("X-Request-Id")
        if id == "" {
            id = uuid.NewString()
        }
        w.Header().Set("X-Request-Id", id)
        next.ServeHTTP(w, r.WithContext(WithTrace(r.Context(), id)))
    })
}

① 用法 · 字段规范与类型级脱敏

字段名一旦在日志平台上被检索、被做成看板，改名的成本就很高。下面这张表是团队里该统一下来的最小集合，第三列是不遵守时的具体后果。

字段怎么写什么时候带不这么写的后果
service / version启动时 With 挂一次每条日志多服务日志混在一起分不清来源，发版前后的问题也对不上
trace_id由 contextHandler 从 ctx 注入每条请求域日志跨服务日志串不成一条链路，只能靠时间戳猜
errslog.Any("err", err)，不要 err.Error()Warn 与 Error丢掉 fmt.Errorf 包装的上下文与 errors.Join 的多个错误
业务主键（order_id 等）用独立字段，不要拼进 message该业务动作的全部日志拼进 message 后无法按 id 聚合，结构化彻底失效
耗时统一 cost_ms，整数毫秒外部调用与关键动作一处写 duration 一处写 elapsed，看板得写三个查询
message固定短语，变量全进字段每条message 里拼变量会让「同类日志」的数量统计失去意义
一组相关字段slog.Group 收成嵌套对象字段超过三四个时顶层字段爆炸，且不同业务的同名字段互相污染
敏感字段（手机号、令牌、证件号）类型实现 LogValuer，ReplaceAttr 做兜底永远敏感数据落进日志文件与它的全部备份，属于事故而不是缺陷
热路径日志logger.LogAttrs(ctx, level, msg, attrs...)每请求都会执行的路径可变参数 any 带来装箱分配，高 QPS 下能量出来

脱敏的定式是在类型上实现 slog.LogValuer——敏感字段干脆不出现在返回值里，从源头上就不可能被打出来，新人不需要知道这条规则也不会写错：

type User struct {
    ID    int64
    Name  string
    Phone string
    Email string
    Token string // 绝不能出现在日志里
}

// 实现 slog.LogValuer 之后，任何地方 slog.Any("user", u) 都只输出这里定义的内容。
// Token 不出现在返回值里，于是它从源头上不可能被打出来
func (u User) LogValue() slog.Value {
    return slog.GroupValue(
        slog.Int64("id", u.ID),
        slog.String("name", u.Name),
        slog.String("phone", maskPhone(u.Phone)),
        slog.String("email", maskEmail(u.Email)),
    )
}

func maskPhone(s string) string {
    if len(s) < 7 {
        return "***"
    }
    return s[:3] + "****" + s[len(s)-4:]
}

func maskEmail(s string) string {
    at := strings.IndexByte(s, '@')
    if at <= 1 {
        return "***"
    }
    return s[:1] + "***" + s[at:]
}

// 延迟求值的用法：LogValue 只在日志真的要被输出时才调用，
// 所以把昂贵的计算放进 LogValue 里，级别关掉时这笔开销就完全不产生
type slowStats struct{ db *sql.DB }

func (s slowStats) LogValue() slog.Value {
    n, _ := countRows(s.db) // Debug 关闭时这行根本不会执行
    return slog.GroupValue(slog.Int("rows", n))
}

func handleOrder(ctx context.Context, l *slog.Logger, u User, orderID int64) error {
    // With 派生带固定上下文的 logger，后续每条日志自动带上，不必重复写。
    // 注意：这属于「函数级」派生，不要每个请求都 With 全套字段
    l = l.With(slog.Int64("order_id", orderID), slog.Any("user", u))

    l.DebugContext(ctx, "start processing", slog.Any("stats", slowStats{db: db}))

    if err := pay(ctx, orderID); err != nil {
        // 用 slog.Any 带上整个 error 而不是 err.Error()：这样 errors.Join 与
        // fmt.Errorf 包装出来的错误链信息才不会被丢掉
        l.ErrorContext(ctx, "pay failed",
            slog.Any("err", err),
            slog.Group("pay", // Group 把相关字段收拢，JSON 里是一个嵌套对象
                slog.String("channel", "wechat"),
                slog.Int("retry", 2),
            ),
        )
        return err
    }

    // 热路径上用 LogAttrs：它接收 []slog.Attr，避免可变参数 any 的装箱分配
    l.LogAttrs(ctx, slog.LevelInfo, "order done", slog.Int64("cost_ms", 12))
    return nil
}

② 原理 · slog 进标准库改变了什么

搞清这一节，能解释为什么值得为了 slog 去改已有代码的日志门面：变的不是性能，是第三方库的日志能不能被你统一管住。

Go 1.21 把 log/slog 收进标准库，这件事的意义不在于「官方也有一个日志库了」，而在于结构化日志终于有了全生态共用的接口。以前每个库各写各的日志：有的用 log 打到 stderr，有的引 logrus，有的干脆自己造。你的服务要统一日志格式，就得给每个库单独接适配器，经常接不上。

现在 slog.Handler 是一个标准接口，库只要往 slog.Default() 输出，你的格式、级别、脱敏规则、trace_id 注入就自动作用到它们身上。这是标准库效应，第三方库永远做不到。

② 原理 · 一条日志的完整处理链路

理解这个顺序能解释很多性能和脱敏方面的疑问：级别判定在最前，所以关掉的级别几乎零开销；LogValuer 的解析和 ReplaceAttr 的改写都在 Handler 里，所以它们能拦住任何调用点写进来的值。

sequenceDiagram participant B as 业务代码 participant L as slog.Logger participant H as 自定义 Handler 链 participant E as JSONHandler 编码器 participant W as io.Writer B->>L: 调用 InfoContext 传 msg 与若干 attrs L->>H: 先问 Enabled 当前级别要不要处理 H-->>L: 级别不够 直接返回 不构造 Record L->>H: 级别足够 构造 Record 交给 Handle H->>H: contextHandler 从 ctx 取 trace_id 追加为 Attr H->>E: 转发给负责编码的 Handler E->>E: 遍历 Attr 对实现 LogValuer 的值调 Resolve E->>E: 每个 Attr 过一遍 ReplaceAttr 做改写与脱敏 E->>W: 编码成一行 并一次性写出 Note over L,H: Enabled 在最前 所以关闭 Debug 时开销接近零
但写在参数里的函数调用仍会先求值 热路径要先判 Enabled
✅
LevelVar 的真实价值

很多线上问题只在特定流量下偶发，重启进程等于毁掉现场。有了 slog.LevelVar 加一个内网管理端点，可以在问题正在发生时把级别调到 debug，看两分钟拿到关键日志，再调回 info。这个能力的成本是五行代码，收益是排查窗口从「等下次复现」变成「现在」。

② 原理 · 三种脱敏方式的可靠性差距

搞清这一节，能解释用法层为什么把 LogValuer 当主防线、ReplaceAttr 只当兜底：这两者在链路上的位置不同，失效条件也完全不同。

脱敏方式规则写在哪什么情况下会失效可靠性
调用点手动 mask每一处写日志的代码里任何人新写一行日志忘了 mask最低 不要依赖它
ReplaceAttr 按 key 名匹配全局 Handler 配置字段名换了 或 被包在 Group 里层级变了 或 整个结构体作为一个 Attr 打出中 适合做兜底
类型实现 LogValuer类型定义旁边只在有人绕过类型直接打裸字段时失效最高 首选
专门的日志 DTO转换函数里忘记调用转换函数中高 但要多维护一个类型
输出后在采集侧过滤日志平台的处理管道敏感数据已经落到本地磁盘和容器日志里低 属于合规意义上的补救

LogValuer 还有一个常被忽略的用途：延迟求值。LogValue() 只在这条日志真的要被输出时才调用，所以把昂贵的统计放进 LogValue 里，Debug 关闭时这笔开销完全不产生。反过来，直接把 expensive() 的调用写在 Debug(...) 的参数里是没用的——参数在进入 Debug 之前就已经求值完毕，级别判定发生在那之后。

② 原理 · 日志级别：约定比工具重要

搞清这一节，能解决「告警全是噪音」和「同一个失败在日志里出现三次」这两个现象。

级别什么该用它什么不该用它线上默认是否输出
Debug只在排查时需要的中间状态 请求参数 分支判定结果不要打完整请求体与响应体 量太大且可能含敏感数据不输出 靠 LevelVar 临时开
Info状态变更 外部调用结果 关键业务动作完成不要在循环里打 会把日志量放大到不可用输出
Warn降级生效 重试成功 配额接近上限 客户端参数非法客户端错误不要用 Error 否则告警全是噪音输出
Error本次请求确实失败 且需要人关注不要既打 Error 又把 error 返回上层 会重复记录同一个问题输出 且接告警
自定义更高级别需要区分 fatal 语义时用 LevelError 加 4不要用 log.Fatal 代替输出
❌
log.Fatal 不该出现在库代码里

log.Fatal 内部调用 os.Exit(1)，而 os.Exit 不执行任何 defer：在途请求被硬切断、缓冲区数据不落盘、优雅退出逻辑完全跳过、正在写的文件可能损坏。更根本的问题是库没有权力决定进程的生死，它该做的是把 error 返回给调用方。log.Fatal 唯一合理的位置是 main 函数里的启动失败分支。

级别约定还要配一条「谁记录」的约定：错误只在最终处理它的那一层记录一次，中间层只做 fmt.Errorf 包装并返回。否则一次失败会在日志里出现三四条 Error，排查的人会误判成多次失败，告警条数也随调用深度翻倍。什么阈值该接告警见 监控体系落地：黑盒白盒分工、分层清单与告警阈值。

迁移日志库是纯成本无收益"] Q3 -->|"有 logrus 成了性能瓶颈"| Q4{"改造范围可控吗"} Q4 -->|"可控"| SLOG Q4 -->|"调用点太多"| BRIDGE["先接 slog 作为新代码的门面
旧代码用桥接 Handler 逐步收敛"]

我的结论：新项目用 slog，极端性能场景用 zap 或 zerolog，已有项目不要为了换日志库而换。需要注意的是，「日志库性能」在绝大多数服务里不是瓶颈——真正把服务拖慢的是在循环里打日志、把完整请求体序列化进日志、以及同步写慢速磁盘，这三件事换任何库都救不了。性能问题该怎么定位见 后端性能优化的度量与方法论。

slog 只负责产生结构化记录，「写到哪、怎么轮转、谁来采集」是另一件事，而这件事的选择直接决定了故障时你还能不能看到日志。

场景该怎么做为什么代价与风险
容器里跑的服务JSONHandler 输出到 os.Stdout 交给采集 agent容器环境标准做法 进程不管轮转 最简单agent 挂了就丢 且 stdout 被填满时写入会阻塞
虚机或物理机部署 需要本地留档写本地文件 配按大小与天数轮转的 Writer不依赖外部 agent 本地可直接 grep轮转时机与文件句柄要处理好 磁盘满会写失败
没有采集基础设施自定义 Handler 直写远端日志服务链路最短 无需部署 agent网络抖动直接拖慢业务 必须异步加有界队列加丢弃策略
日志量极大的核心服务Handler 前置一个有界 channel 与后台 worker 批量写业务线程不被 IO 阻塞 吞吐最高进程崩溃会丢队列里的日志 退出前必须 drain
需要本地应急兜底io.MultiWriter 或多路 Handler 同时写两处远端不可用时本地还有一份任一路阻塞拖慢全部 必须给每路独立超时
错误日志要单独接告警自定义 Handler 按 Level 路由到不同 Writer错误流单独一份 告警链路不受海量 Info 影响实现复杂度上升 要正确转发 WithAttrs 与 WithGroup

容器环境的默认答案是第一条：写 stdout，轮转和采集交给平台。但有一个细节值得注意——os.Stdout 的写入是同步的，当采集侧读得慢、管道缓冲被填满时，写日志这行代码会阻塞，进而阻塞业务 goroutine。日志量很大的服务应该在 Handler 前加一层有界队列，队列满时按级别丢弃（先丢 Debug 和 Info，永不丢 Error），并在进程退出前把队列排空。

下面十条是我在上线评审里逐条问的，每一条漏掉都有过对应的真实事故。

不适用边界：日志不是万能的观测手段。需要看趋势、算比率、设阈值告警的东西应该做成指标而不是日志（见 监控体系落地：黑盒白盒分工、分层清单与告警阈值）；需要看一次请求在多个服务间的耗时分布应该用链路追踪（见 链路追踪落地：四类排查场景、依赖拓扑反推与关键路径分析）；审计类需求（谁在什么时候改了什么，需要长期保存且不可篡改）应该写专门的审计表，而不是混在应用日志里靠日志平台检索。另外，极端性能场景下 slog 不是最快的选择，但「换库」的收益远小于「不在循环里打日志」。

把 slog 用好只需要记住四件事：固定字段在进程启动时 With 一次，请求字段靠 context 加自定义 Handler 注入，敏感类型实现 LogValuer，级别用 LevelVar 以便线上动态调整。剩下的注意力放在约定上：什么该打什么级别、错误在哪一层记录、循环里绝不打日志——日志系统的价值取决于出事时能不能快速定位，而这更多由这些约定决定，而不是由你选了哪个库决定。

最容易踩的坑

❌
避坑清单
  • 库代码里用 log.Fatal：os.Exit 跳过所有 defer，在途请求被切断、缓冲不落盘。库只该返回 error。
  • 自定义 Handler 只实现 Handle 不转发 WithAttrs 与 WithGroup：一旦有人调 logger.With，你的包装层就被丢掉，trace_id 悄悄不再注入。
  • 每个请求都 logger.With(...) 派生一个新 logger：每次都复制属性切片，高 QPS 下是可观的分配。固定字段进程级 With 一次，请求级字段走 context 注入。
  • 日志里拼字符串而不用字段：slog.Info(fmt.Sprintf("user %d failed", id)) 让结构化彻底失效，日志平台没法按 user_id 聚合。
  • 只打 err.Error() 丢掉错误链：用 slog.Any("err", err)，否则 fmt.Errorf 包装的上下文和 errors.Join 的多个错误全没了。
  • 用 Level 而不是 LevelVar 配 HandlerOptions：级别被写死，线上想开 debug 只能重启，现场随之消失。
  • 把 AddSource 在超高频路径上一直开着：每条日志一次栈帧解析，量大时是实打实的开销，且默认输出的是构建机绝对路径。
  • 把昂贵的计算直接写在 Debug 的参数里：参数先求值再判级别，关掉 Debug 也省不下来。放进 LogValue 或先判 Enabled。
  • 客户端参数错误打 Error 级别：告警被噪音淹没，真问题被埋掉。4xx 类错误用 Warn 或 Info。
  • 既打 Error 又把 error 返回上层：同一个问题在日志里出现两三次，排查时误判为多次失败。约定只在最终处理处记录。
  • 在 ReplaceAttr 里做正则或反射：它对每条日志的每个属性都会被调用一次，重逻辑直接变成热点。
  • 依赖 ReplaceAttr 按 key 名脱敏就以为安全了：整个结构体作为一个 Attr 打出时 key 名对不上，敏感字段照样落盘。类型级 LogValuer 才是主防线。
  • 在循环里打 Info 日志：一次请求打出几千条，日志量和采集成本双双爆炸，还会把真正有用的日志冲掉。要么降到 Debug，要么聚合后打一条。
  • 异步日志方案不在退出前 drain 队列：崩溃或滚动重启前最关键的那几条日志正好在队列里，全丢。
  • 把调级别的端点暴露到公网：任何人都能把你的服务切到 debug，日志量瞬间放大几十倍，等于一个放大器型的拒绝服务入口。
