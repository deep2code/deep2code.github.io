io 接口与流式处理

🏷️ Go 语言

一个方法的接口，为什么是 Go 最成功的抽象

io.Reader 只有一个方法，io.Writer 也只有一个方法。这两个接口的价值恰恰来自「小」：方法越少，能实现它的类型就越多，可组合的空间就越大。文件、TCP 连接、内存缓冲、字符串、gzip 流、AES 加密流、限速器、进度条、HTTP 请求体，全都满足同一个接口，于是任何接收 io.Reader 的函数天然能处理所有这些来源。

对比一下就知道这有多难得：在需要显式声明实现关系的语言里，让一个第三方类型去满足你定义的接口通常要写适配器；而 Go 的隐式实现让「凑巧都有一个 Read 方法」就等于可互换。这也是为什么 Go 的 IO 生态里几乎看不到适配层——大家共用同一组接口。

❌
Read 的黄金法则：先处理数据，再判断 error

Read 的契约允许同时返回 n 大于 0 和一个非 nil 的 error（最典型的是最后一次读返回了数据同时带上 io.EOF）。所以正确的写法永远是先处理 p[:n]，再决定要不要因为 err 退出。写成先判 err 后处理数据，就会在读取的最后一块上丢数据，而且只在文件大小恰好落在边界上时复现。

组合管道：一条真实的流式链路

单方法接口最直接的收益是可以把处理步骤像水管一样接起来，而且全程内存占用只和缓冲区大小有关，与数据量无关。

// 一条完整管道：本地文件 -> gzip -> AES-CTR -> HTTP 请求体
// 全程流式，处理 10GB 文件的内存占用和处理 10MB 一样
func uploadEncrypted(ctx context.Context, url, path string, key []byte) error {
    f, err := os.Open(path)
    if err != nil {
        return err
    }
    defer f.Close() // 只读路径上 Close 的 error 可以忽略，写路径上不行

    block, err := aes.NewCipher(key)
    if err != nil {
        return err
    }
    iv := make([]byte, block.BlockSize())
    if _, err := rand.Read(iv); err != nil {
        return err
    }

    // http.NewRequest 要一个 Reader，而 gzip.Writer 是 Writer，
    // io.Pipe 就是用来把「只会写的生产者」和「只会读的消费者」接起来的
    pr, pw := io.Pipe()

    go func() {
        var ferr error
        // 关键：出错必须用 CloseWithError 把错误传到读端，
        // 只调 Close 的话读端看到的是正常 EOF，会把半截数据当成完整内容上传
        defer func() { _ = pw.CloseWithError(ferr) }()

        // iv 明文写在最前面，解密方按块长先读出来
        if _, ferr = pw.Write(iv); ferr != nil {
            return
        }
        enc := &cipher.StreamWriter{S: cipher.NewCTR(block, iv), W: pw}
        gz := gzip.NewWriter(enc)
        if _, ferr = io.Copy(gz, f); ferr != nil {
            return
        }
        // gzip.Writer.Close 才写 CRC 与长度尾部。漏掉这一步产出的是损坏的 gz，
        // 而且不检查它的 error 就等于放弃了发现「写了但没写成」的最后机会
        ferr = gz.Close()
    }()

    req, err := http.NewRequestWithContext(ctx, http.MethodPut, url, pr)
    if err != nil {
        return err
    }
    req.Header.Set("Content-Encoding", "gzip")

    resp, err := http.DefaultClient.Do(req)
    if err != nil {
        return err
    }
    defer resp.Body.Close()
    // 即使不关心响应体，也必须排空：不读完这条连接就没法放回连接池复用
    _, _ = io.Copy(io.Discard, resp.Body)
    if resp.StatusCode/100 != 2 {
        return fmt.Errorf("upload failed: %s", resp.Status)
    }
    return nil
}

io.Copy 的零拷贝：它到底做了什么

io.Copy 不是「分配一块缓冲然后循环读写」这么简单。它先做两次接口断言，命中就走快路径，都不命中才退化成缓冲循环。

自己包一层只实现 Write 的装饰器 快路径就失效了
条件实际执行路径中间缓冲典型组合
src 实现 io.WriterTo调 src.WriteTo(dst)无bytes.Buffer 写到任意 Writer
dst 实现 io.ReaderFrom 且 src 是普通文件net 层发起 sendfile无 数据不出内核静态文件服务器把文件发给 TCP 连接
src 与 dst 都是文件Go 1.22+ 可用 copy_file_range无同盘大文件复制
src 与 dst 都是 socketLinux 上可用 splice无TCP 代理转发
dst 是 bufio.Writer调 bufio.Writer.ReadFrom复用 bufio 自己的缓冲流式落盘
两个断言都不命中分配 32KB 缓冲循环 Read 与 Write32KB自定义装饰器之间的拷贝
src 是 io.LimitedReader 且剩余量小于 32KB缓冲按剩余量缩小小于 32KB只拷一小段

实践结论：能用 io.Copy 就不要自己写 for 循环读写，自己写的版本一定走不到内核零拷贝。反过来，如果你写了一个包装 Writer 的装饰器（比如统计字节数的），它会把 ReaderFrom 快路径挡掉，这时要么在装饰器上也实现 ReadFrom 转发下去，要么接受退化。

缓冲：为什么 bufio 不是可选项

没有缓冲的每一次 Read 或 Write 都是一次系统调用。系统调用的固定开销在几百纳秒到一微秒量级，所以逐字节读一个 1MB 文件意味着一百万次陷入内核，耗时能到秒级；包一层 bufio 之后只有几十次系统调用，耗时是毫秒级。这中间是三到四个数量级的差距，不是「优化」而是「能不能用」的区别。

读取 1MB 文件的方式系统调用次数量级相对耗时量级说明
每次 Read 一个字节 不加缓冲一百万次基准 最慢几乎全部时间花在陷入内核
每次 Read 一个字节 外层包 bufio十几次快两到三个数量级bufio 默认缓冲 4KB 可调
每次 Read 4KB 不加缓冲约 256 次快两个数量级自己管缓冲等价于 bufio
每次 Read 64KB16 次再快一点 收益变缓超过 64KB 后基本触及磁盘带宽上限
io.Copy 到文件几十次 且可能走内核直通最快命中 ReaderFrom 时完全不经用户态
io.ReadAll 一次读进内存随扩容次数增长快 但峰值内存约为数据量两倍只适合确定很小且可信的输入
❌
bufio.Scanner 的 64KB 行上限会让你静默丢数据

bufio.Scanner 默认单个 token 上限是 bufio.MaxScanTokenSize 即 64KB。遇到更长的一行时，Scan() 直接返回 false，for sc.Scan() 正常退出，看起来和读完文件完全一样，实际后面所有内容都没处理。错误藏在 sc.Err() 里（bufio.ErrTooLong），只检查 Scan() 返回值的代码永远发现不了。处理日志、CSV、JSON Lines 这类可能出现超长行的数据时，这个坑几乎必踩。

// 流式逐行处理超大文件：内存恒定，且能正确处理超长行
func processLines(path string, fn func(line []byte) error) error {
    f, err := os.Open(path)
    if err != nil {
        return err
    }
    defer f.Close()

    // 不包 bufio 的话每次 Read 都是一次 syscall，差距三到四个数量级
    br := bufio.NewReaderSize(f, 64*1024)

    for {
        // 用 ReadSlice 而不是 Scanner：行超长时返回 ErrBufferFull，
        // 由我们自己决定是拼接、截断还是报错，而不是被框架悄悄放弃
        line, err := br.ReadSlice('\n')

        if errors.Is(err, bufio.ErrBufferFull) {
            // ReadSlice 返回的切片指向 bufio 内部数组，下次读就会被覆盖，必须先 copy
            rest := append([]byte(nil), line...)
            for errors.Is(err, bufio.ErrBufferFull) {
                line, err = br.ReadSlice('\n')
                rest = append(rest, line...)
                if len(rest) > 8<<20 { // 硬上限，防止恶意的一行把内存吃穿
                    return fmt.Errorf("line exceeds 8MB limit")
                }
            }
            if e := fn(bytes.TrimRight(rest, "\r\n")); e != nil {
                return e
            }
            continue
        }

        // Read 黄金法则：先处理已读到的数据，再判断 err
        if len(line) > 0 {
            if e := fn(bytes.TrimRight(line, "\r\n")); e != nil {
                return e
            }
        }
        if err != nil {
            if errors.Is(err, io.EOF) {
                return nil
            }
            return err
        }
    }
}

// 如果坚持用 Scanner，下面这两行是必须的
func scanLines(r io.Reader) error {
    sc := bufio.NewScanner(r)
    // 默认上限是 bufio.MaxScanTokenSize 即 64KB，按业务抬高
    sc.Buffer(make([]byte, 0, 64*1024), 8<<20)
    for sc.Scan() {
        _ = sc.Bytes() // 底层数组下次 Scan 会复用，要留存必须 copy 或用 sc.Text
    }
    // 只看 Scan 返回值会把 ErrTooLong 当成读完，Err 必须检查
    return sc.Err()
}

// 下载不可信来源的大响应：不用 ReadAll，用 LimitReader 兜上限 加 流式落盘
func downloadTo(ctx context.Context, url, dst string, maxBytes int64) (err error) {
    req, err := http.NewRequestWithContext(ctx, http.MethodGet, url, nil)
    if err != nil {
        return err
    }
    resp, err := http.DefaultClient.Do(req)
    if err != nil {
        return err
    }
    defer func() {
        _, _ = io.Copy(io.Discard, resp.Body) // 排空 才能复用连接
        _ = resp.Body.Close()
    }()
    if resp.StatusCode != http.StatusOK {
        return fmt.Errorf("unexpected status %s", resp.Status)
    }

    f, err := os.Create(dst)
    if err != nil {
        return err
    }
    defer func() {
        // 写入路径上 Close 的 error 必须回传：它可能携带延迟报出的写失败
        if cerr := f.Close(); err == nil {
            err = cerr
        }
    }()

    bw := bufio.NewWriterSize(f, 256*1024)
    // 多读一个字节：这样才能区分「刚好等于上限」和「已经超过上限」
    n, err := io.Copy(bw, io.LimitReader(resp.Body, maxBytes+1))
    if err != nil {
        return err
    }
    if n > maxBytes {
        return fmt.Errorf("response exceeds %d bytes", maxBytes)
    }
    // Flush 必须在 Close 之前，且它的 error 必须检查，否则末尾数据会静默丢失
    return bw.Flush()
}

排查：IO 问题怎么定位

IO 类问题的症状往往和根因离得很远：fd 泄漏表现成「服务跑了三天突然全部报错」，缺少缓冲表现成「CPU 不高但吞吐上不去」，响应体没排空表现成「延迟毛刺随 QPS 升高」。下面这些命令可以把症状直接落到根因上。

症状排查命令输出怎么判读对应根因
报 too many open fileslsof -p 进程号 之后按类型统计同一个文件或同一个远端地址出现成百上千条某处 defer Close 漏了 或 响应体没关
吞吐上不去但 CPU 不高strace -c -p 进程号 统计系统调用read 或 write 的调用次数与数据量严重不匹配缺少 bufio 包装 每次都陷内核

内存周期性尖峰后回落pprof 抓 heap 看 inuse_space 的调用栈栈顶出现 io.ReadAll 或 bytes.Buffer 扩容一次性读入大输入

上传长时间卡住不报错抓 goroutine 栈看阻塞点栈停在 io.Pipe 的 Read 上写端出错只调了 Close 没传错误

判读顺序建议是先看 fd 再看系统调用次数再看内存栈。fd 数量是最容易确认也最容易修的；系统调用次数能一眼看出有没有缺缓冲；内存栈用来定位那些「只在特定请求上」打爆内存的 ReadAll。三步走完，绝大多数 IO 问题都能落到具体某一行代码上。

⚠️
最容易踩的坑

1. 只检查 Scanner.Scan() 不检查 Err()：超过 64KB 的行让循环正常退出，后面的数据全丢，日志处理脚本最常中招。

2. 保存 Scanner.Bytes() 或 bufio.Reader.ReadSlice() 返回的切片：底层数组下一轮会被复用，存进 map 里的内容全被覆盖成最后一行。

3. 写入路径上 defer f.Close() 却不接错误：gzip.Writer 的尾部、bufio.Writer 的缓冲都在 Close 时才写出，产出损坏文件却报成功。

4. 用了 bufio.NewWriter 忘记 Flush：文件末尾缺一段，而且缺多少取决于缓冲区大小，非常难定位。

5. io.ReadAll 读用户上传或下游响应：扩容峰值内存约为数据量两倍，几百兆输入就能打挂进程。

6. http.Response.Body 不读完就 Close：连接不能复用，QPS 上去后本地端口耗尽，同时每次都要重新 TLS 握手。

7. io.Pipe 的写端出错时只调 Close()：读端拿到的是干净的 EOF，半截数据被当成完整内容，要用 CloseWithError。

8. 先判 err != nil 再处理 n 字节：最后一次读同时返回数据和 EOF 时丢尾部，只在数据长度恰好落在边界时复现。

9. 对 net.Conn 调 Seek：网络流不可回退，需要重读就得自己缓存或用 HTTP Range。

10. 自己写 for 循环替代 io.Copy：白白放弃 sendfile 与 splice，静态文件服务场景差距明显。

11. 包了一层自定义 Writer 装饰器却没转发 ReadFrom：无意中把上游的零拷贝路径挡掉了。

12. 在 io.Copy 的目标是内存 buffer 时不限上限：等价于 ReadAll，同样会被大输入打爆。

结论

io.Reader 和 io.Writer 的价值在于它们小到几乎所有东西都能实现，于是「组合」成了默认的扩展方式：压缩、加密、限速、计数、分流，每一个都是一层装饰器，接口不变。写代码时的两条习惯足够覆盖大部分场景——函数参数永远声明成 io.Reader 或 io.Writer 而不是具体类型，能流式就绝不 ReadAll。

剩下的注意力全部花在三件事上：读的时候先处理数据再判 error；写的时候把 Flush 和 Close 的错误当成业务错误对待；来源不可信的输入一律先套 io.LimitReader。这三件事做到了，IO 相关的线上问题会少掉九成。
