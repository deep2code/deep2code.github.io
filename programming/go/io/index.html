io 接口与流式处理

🏷️ Go 语言

这篇的靶子很具体：IO 相关的线上问题几乎都不是「不会写」，而是标准写法没记牢——响应体没排空导致连接不复用、Close 的错误被丢掉产出损坏文件、bufio.Scanner 撞上 64KB 行上限静默丢数据。这几类问题都有固定的正确写法，也都能在 code review 里一眼认出来。

💡
这篇怎么读
  • ① 用法：六个可以直接抄走的读写定式（io.Copy 转发、读行、写入路径合并 Close 错误、不可信输入限长、一次读取两个用途、响应体排空），配「要做什么 → 用哪个函数 → 用错的后果」对照表与 io / bufio 速查表，外加「连接不复用」的排查步骤。
  • ② 原理：单方法接口为什么能任意组合、io.Copy 的两次接口断言与 sendfile 快路径、缓冲带来的数量级差异、Read 契约里「n 大于 0 同时带 error」的陷阱，以及从症状反查根因的命令清单。
  • ③ 场景：按数据来源与规模选定式的判断图与决策矩阵，以及哪些情况下流式反而是过度设计。

① 用法 · 读写的六个标准定式

下面是一个完整可编译的文件，六个函数覆盖了日常读写需求的绝大部分。每个定式的注释只解释「为什么必须这么写」，机制原因在原理层展开。

package streamio

import (
    "bufio"
    "crypto/sha256"
    "encoding/hex"
    "errors"
    "fmt"
    "io"
    "net/http"
    "net/http/httptrace"
    "os"
)

// 定式一：转发。能用 io.Copy 就不要自己写 for 循环读写，
// 手写版本一定走不到 sendfile 与 splice 这些内核路径（原因见原理层）
func Forward(dst io.Writer, src io.Reader) (int64, error) {
    return io.Copy(dst, src)
}

// 定式二：读行。Scanner 默认单个 token 上限是 64KB，超了就静默停止循环，
// 所以 Buffer 与 Err 这两行缺一不可
func EachLine(r io.Reader, fn func(line []byte) error) error {
    sc := bufio.NewScanner(r)
    // 第二个参数才是 token 上限，按业务里最长的一行抬高；第一个参数只是初始缓冲
    sc.Buffer(make([]byte, 0, 64*1024), 8<<20)
    for sc.Scan() {
        // sc.Bytes 的底层数组下一轮会被复用，要留存必须 copy 一份或改用 sc.Text
        if err := fn(sc.Bytes()); err != nil {
            return err
        }
    }
    // 漏掉这一行，ErrTooLong 会被当成「正常读完」，后面的数据全部无声丢失
    return sc.Err()
}

// 定式三：写入。命名返回值加 defer，把 Close 的错误并进返回值，
// 因为 bufio 的缓冲与压缩流的尾部都是在 Close 时才真正落盘
func WriteFile(path string, src io.Reader) (err error) {
    f, err := os.Create(path)
    if err != nil {
        return err
    }
    defer func() {
        // 只在业务本身没出错时才覆盖，否则会把真正的错误挤掉
        if cerr := f.Close(); err == nil {
            err = cerr
        }
    }()

    bw := bufio.NewWriterSize(f, 256*1024)
    if _, err = io.Copy(bw, src); err != nil {
        return err
    }
    // Flush 必须显式调用并检查，且要在 Close 之前，否则末尾一段会静默丢失
    return bw.Flush()
}

// 定式四：来源不可信的输入。多读一个字节，才能区分「刚好等于上限」与「已经超限」
func ReadCapped(r io.Reader, max int64) ([]byte, error) {
    buf, err := io.ReadAll(io.LimitReader(r, max+1))
    if err != nil {
        return nil, err
    }
    if int64(len(buf)) > max {
        return nil, fmt.Errorf("input exceeds %d bytes", max)
    }
    return buf, nil
}

// 定式五：一份数据两个用途。MultiWriter 让落盘与算摘要共用同一次读取，
// 网络流只能读一遍，分两次读第二遍直接是 EOF
func SaveWithDigest(path string, src io.Reader) (sum string, err error) {
    f, err := os.Create(path)
    if err != nil {
        return "", err
    }
    defer func() {
        if cerr := f.Close(); err == nil {
            err = cerr
        }
    }()

    h := sha256.New()
    if _, err = io.Copy(io.MultiWriter(f, h), src); err != nil {
        return "", err
    }
    return hex.EncodeToString(h.Sum(nil)), nil
}

// 定式六：就算完全不关心响应体，也必须先排空再 Close，
// 否则这条连接无法放回连接池，每次请求都要重新建连与 TLS 握手
func Drain(resp *http.Response) error {
    defer resp.Body.Close()
    if _, err := io.Copy(io.Discard, resp.Body); err != nil && !errors.Is(err, io.EOF) {
        return err
    }
    return nil
}

// 排查用：把连接复用情况打出来，Reused 为 false 说明上一次请求没有正确排空
func traceReuse(req *http.Request, log func(format string, args ...any)) *http.Request {
    trace := &httptrace.ClientTrace{
        GotConn: func(info httptrace.GotConnInfo) {
            log("reused=%v wasIdle=%v", info.Reused, info.WasIdle)
        },
    }
    return req.WithContext(httptrace.WithClientTrace(req.Context(), trace))
}

「连接不复用」的排查步骤：这是漏了定式六之后最常见的症状，表现是延迟毛刺随 QPS 升高，但 CPU 与下游都看不出问题。按下面三步走，十分钟内能定性。

# 1) 看 TIME_WAIT 是否与 QPS 同步增长：同步增长说明连接在被不断新建与丢弃
netstat -an | awk '$6=="TIME_WAIT"' | wc -l

# 2) 看 fd：同一个下游地址出现成百上千条，说明连接压根没回池
lsof -p "$(pgrep -f myapp)" | grep -c TCP

# 3) 看客户端指标：Go 1.11 起 http.Transport 的空闲连接数可从 expvar 或自己埋点导出，
#    更直接的证据是上面 traceReuse 打出的 reused=false
curl -s localhost:6060/debug/pprof/goroutine?debug=1 | grep -c 'net/http.(*persistConn)'

三步看下来：reused=false 长期出现、TIME_WAIT 随 QPS 线性上涨、persistConn 的 goroutine 数量剧烈波动，任意两条同时成立就可以直接去代码里找「只 Close 没排空」的调用点了。相关的下游超时与取消传播见 Go Context 的传播、取消与误用，延迟毛刺的量化方法在 可观测性与性能。

② 原理 · 一个方法的接口，为什么是 Go 最成功的抽象

搞清这一节，能解释为什么上面那些定式的参数类型全是 io.Reader 和 io.Writer，以及为什么你自己包一层装饰器就可能让性能掉一个档。

io.Reader 只有一个方法，io.Writer 也只有一个方法。这两个接口的价值恰恰来自「小」：方法越少，能实现它的类型就越多，可组合的空间就越大。文件、TCP 连接、内存缓冲、字符串、gzip 流、AES 加密流、限速器、进度条、HTTP 请求体，全都满足同一个接口，于是任何接收 io.Reader 的函数天然能处理所有这些来源。

对比一下就知道这有多难得：在需要显式声明实现关系的语言里，让一个第三方类型去满足你定义的接口通常要写适配器；而 Go 的隐式实现让「凑巧都有一个 Read 方法」就等于可互换。这也是为什么 Go 的 IO 生态里几乎看不到适配层——大家共用同一组接口。

❌
Read 的黄金法则：先处理数据，再判断 error

Read 的契约允许同时返回 n 大于 0 和一个非 nil 的 error（最典型的是最后一次读返回了数据同时带上 io.EOF）。所以正确的写法永远是先处理 p[:n]，再决定要不要因为 err 退出。写成先判 err 后处理数据，就会在读取的最后一块上丢数据，而且只在文件大小恰好落在边界上时复现。

② 原理 · 组合管道：一条真实的流式链路

搞清这一节，能解决「处理大文件内存就爆」这一类问题：管道搭对了，内存占用只和缓冲区大小有关，与数据量无关。

// 一条完整管道：本地文件 -> gzip -> AES-CTR -> HTTP 请求体
// 全程流式，处理 10GB 文件的内存占用和处理 10MB 一样
func uploadEncrypted(ctx context.Context, url, path string, key []byte) error {
    f, err := os.Open(path)
    if err != nil {
        return err
    }
    defer f.Close() // 只读路径上 Close 的 error 可以忽略，写路径上不行

    block, err := aes.NewCipher(key)
    if err != nil {
        return err
    }
    iv := make([]byte, block.BlockSize())
    if _, err := rand.Read(iv); err != nil {
        return err
    }

    // http.NewRequest 要一个 Reader，而 gzip.Writer 是 Writer，
    // io.Pipe 就是用来把「只会写的生产者」和「只会读的消费者」接起来的
    pr, pw := io.Pipe()

    go func() {
        var ferr error
        // 关键：出错必须用 CloseWithError 把错误传到读端，
        // 只调 Close 的话读端看到的是正常 EOF，会把半截数据当成完整内容上传
        defer func() { _ = pw.CloseWithError(ferr) }()

        // iv 明文写在最前面，解密方按块长先读出来
        if _, ferr = pw.Write(iv); ferr != nil {
            return
        }
        enc := &cipher.StreamWriter{S: cipher.NewCTR(block, iv), W: pw}
        gz := gzip.NewWriter(enc)
        if _, ferr = io.Copy(gz, f); ferr != nil {
            return
        }
        // gzip.Writer.Close 才写 CRC 与长度尾部。漏掉这一步产出的是损坏的 gz，
        // 而且不检查它的 error 就等于放弃了发现「写了但没写成」的最后机会
        ferr = gz.Close()
    }()

    req, err := http.NewRequestWithContext(ctx, http.MethodPut, url, pr)
    if err != nil {
        return err
    }
    req.Header.Set("Content-Encoding", "gzip")

    resp, err := http.DefaultClient.Do(req)
    if err != nil {
        return err
    }
    defer resp.Body.Close()
    // 即使不关心响应体，也必须排空：不读完这条连接就没法放回连接池复用
    _, _ = io.Copy(io.Discard, resp.Body)
    if resp.StatusCode/100 != 2 {
        return fmt.Errorf("upload failed: %s", resp.Status)
    }
    return nil
}

② 原理 · io.Copy 的零拷贝：它到底做了什么

搞清这一节，能解释「为什么加了一层统计字节数的 Writer 之后吞吐掉了一半」——快路径是靠接口断言命中的，装饰器会把它挡掉。

io.Copy 不是「分配一块缓冲然后循环读写」这么简单。它先做两次接口断言，命中就走快路径，都不命中才退化成缓冲循环。

自己包一层只实现 Write 的装饰器 快路径就失效了
条件实际执行路径中间缓冲典型组合
src 实现 io.WriterTo调 src.WriteTo(dst)无bytes.Buffer 写到任意 Writer
dst 实现 io.ReaderFrom 且 src 是普通文件net 层发起 sendfile无 数据不出内核静态文件服务器把文件发给 TCP 连接

src 与 dst 都是 socketLinux 上可用 splice无TCP 代理转发
dst 是 bufio.Writer调 bufio.Writer.ReadFrom复用 bufio 自己的缓冲流式落盘
两个断言都不命中分配 32KB 缓冲循环 Read 与 Write32KB自定义装饰器之间的拷贝
src 是 io.LimitedReader 且剩余量小于 32KB缓冲按剩余量缩小小于 32KB只拷一小段

实践结论：能用 io.Copy 就不要自己写 for 循环读写，自己写的版本一定走不到内核零拷贝。反过来，如果你写了一个包装 Writer 的装饰器（比如统计字节数的），它会把 ReaderFrom 快路径挡掉，这时要么在装饰器上也实现 ReadFrom 转发下去，要么接受退化。

② 原理 · 缓冲：为什么 bufio 不是可选项

搞清这一节，能解决「CPU 不高但吞吐上不去」这类问题：多数情况下时间全花在系统调用的固定开销上。

没有缓冲的每一次 Read 或 Write 都是一次系统调用。系统调用的固定开销在几百纳秒到一微秒量级，所以逐字节读一个 1MB 文件意味着一百万次陷入内核，耗时能到秒级；包一层 bufio 之后只有几十次系统调用，耗时是毫秒级。这中间是三到四个数量级的差距，不是「优化」而是「能不能用」的区别。

读取 1MB 文件的方式系统调用次数量级相对耗时量级说明
每次 Read 一个字节 不加缓冲一百万次基准 最慢几乎全部时间花在陷入内核
每次 Read 一个字节 外层包 bufio十几次快两到三个数量级bufio 默认缓冲 4KB 可调
每次 Read 4KB 不加缓冲约 256 次快两个数量级自己管缓冲等价于 bufio
每次 Read 64KB16 次再快一点 收益变缓超过 64KB 后基本触及磁盘带宽上限
io.Copy 到文件几十次 且可能走内核直通最快命中 ReaderFrom 时完全不经用户态
io.ReadAll 一次读进内存随扩容次数增长快 但峰值内存约为数据量两倍只适合确定很小且可信的输入
❌
bufio.Scanner 的 64KB 行上限会让你静默丢数据

bufio.Scanner 默认单个 token 上限是 bufio.MaxScanTokenSize 即 64KB。遇到更长的一行时，Scan() 直接返回 false，for sc.Scan() 正常退出，看起来和读完文件完全一样，实际后面所有内容都没处理。错误藏在 sc.Err() 里（bufio.ErrTooLong），只检查 Scan() 返回值的代码永远发现不了。处理日志、CSV、JSON Lines 这类可能出现超长行的数据时，这个坑几乎必踩。

定式二给的是「抬高上限」这条路。如果超长行本身就是要防御的输入，就得换成下面这种自己掌控拼接与截断的写法。

// 流式逐行处理超大文件：内存恒定，且能正确处理超长行
func processLines(path string, fn func(line []byte) error) error {
    f, err := os.Open(path)
    if err != nil {
        return err
    }
    defer f.Close()

    // 不包 bufio 的话每次 Read 都是一次 syscall，差距三到四个数量级
    br := bufio.NewReaderSize(f, 64*1024)

    for {
        // 用 ReadSlice 而不是 Scanner：行超长时返回 ErrBufferFull，
        // 由我们自己决定是拼接、截断还是报错，而不是被框架悄悄放弃
        line, err := br.ReadSlice('\n')

        if errors.Is(err, bufio.ErrBufferFull) {
            // ReadSlice 返回的切片指向 bufio 内部数组，下次读就会被覆盖，必须先 copy
            rest := append([]byte(nil), line...)
            for errors.Is(err, bufio.ErrBufferFull) {
                line, err = br.ReadSlice('\n')
                rest = append(rest, line...)
                if len(rest) > 8<<20 { // 硬上限，防止恶意的一行把内存吃穿
                    return fmt.Errorf("line exceeds 8MB limit")
                }
            }
            if e := fn(bytes.TrimRight(rest, "\r\n")); e != nil {
                return e
            }
            continue
        }

        // Read 黄金法则：先处理已读到的数据，再判断 err
        if len(line) > 0 {
            if e := fn(bytes.TrimRight(line, "\r\n")); e != nil {
                return e
            }
        }
        if err != nil {
            if errors.Is(err, io.EOF) {
                return nil
            }
            return err
        }
    }
}

② 原理 · 症状到根因：IO 问题的排查路径

IO 类问题的症状往往和根因离得很远：fd 泄漏表现成「服务跑了三天突然全部报错」，缺少缓冲表现成「CPU 不高但吞吐上不去」，响应体没排空表现成「延迟毛刺随 QPS 升高」。下面这些命令可以把症状直接落到根因上。

判读顺序建议是先看 fd 再看系统调用次数再看内存栈。fd 数量是最容易确认也最容易修的；系统调用次数能一眼看出有没有缺缓冲；内存栈用来定位那些「只在特定请求上」打爆内存的 ReadAll。三步走完，绝大多数 IO 问题都能落到具体某一行代码上。

场景该怎么做为什么代价
静态文件或大对象转发给 HTTP 客户端http.ServeContent 或 io.Copy 直接写 ResponseWriter命中 ReaderFrom 可走 sendfile，数据不出内核中间插任何装饰器（限速、计数、加密）都会让快路径退化成 32KB 循环
请求体或上传来自外部用户http.MaxBytesReader 或 io.LimitReader 套死上限，边读边落盘峰值内存与数据量脱钩，攻击者无法用一个大 body 打爆进程要自己处理超限时的状态码与半截临时文件的清理
逐行处理 GB 级日志bufio.Reader.ReadSlice 自己处理超长行内存恒定，超长行由你决定截断还是报错代码比 Scanner 长，返回切片必须 copy 才能留存
同一份输出要送到多个目的地io.MultiWriter源只读一遍，落盘与转发共用同一次拷贝任一 Writer 报错整个 Copy 就中断，最慢的目的地决定整体速度
生产侧只会写、消费侧只要读（gzip 接 HTTP body）io.Pipe 加 CloseWithError不必先在内存里攒出完整包体多一个 goroutine 与一条必须正确传播错误的路径，写错就是永久阻塞
配置、证书、模板这类确定很小的可信输入os.ReadFile 或 io.ReadAll代码最短，流式在这里是过度设计一旦这个路径被换成用户可控的文件，就变成内存事故
并发读同一文件的不同区间（分片下载、zip 解析）io.NewSectionReader 配 io.ReaderAtReadAt 不共享偏移量，可以安全并发调用net.Conn 不实现 ReaderAt，只能对本地文件或已落盘内容用

不适用边界：流式不是万能选项。对象小于几十 KB 且来源可信时，os.ReadFile 一把读完远比搭一条管道清晰；需要随机访问或反复回退时，流式接口帮不上忙，应该先落盘或读进内存再用 bytes.Reader；io.Pipe 引入的 goroutine 在高并发下本身就是成本，能用 bytes.Buffer 解决的小包体不值得上管道。日志的结构化输出不要自己拼 io.Writer，用 结构化日志与 log/slog；缓冲区大小与复用的量级判断见 算法与数据结构在后端工程中的位置；给流式代码写测试时 strings.Reader 与 iotest 的用法在 测试策略与可测性设计；吞吐与延迟的量化定位在 可观测性与性能。

回到最上面那两条习惯：函数参数永远声明成 io.Reader 或 io.Writer 而不是具体类型，能流式就绝不 ReadAll。剩下的注意力全部花在三件事上——读的时候先处理数据再判 error；写的时候把 Flush 和 Close 的错误当成业务错误对待；来源不可信的输入一律先套 io.LimitReader。这三件事做到了，IO 相关的线上问题会少掉九成。

最容易踩的坑

❌
避坑清单
  • 只检查 Scanner.Scan() 不检查 Err()：超过 64KB 的行让循环正常退出，后面的数据全丢，日志处理脚本最常中招。
  • 保存 Scanner.Bytes() 或 bufio.Reader.ReadSlice() 返回的切片：底层数组下一轮会被复用，存进 map 里的内容全被覆盖成最后一行。
  • 写入路径上 defer f.Close() 却不接错误：gzip.Writer 的尾部、bufio.Writer 的缓冲都在 Close 时才写出，产出损坏文件却报成功。
  • 用了 bufio.NewWriter 忘记 Flush：文件末尾缺一段，而且缺多少取决于缓冲区大小，非常难定位。
  • io.ReadAll 读用户上传或下游响应：扩容峰值内存约为数据量两倍，几百兆输入就能打挂进程。
  • http.Response.Body 不读完就 Close：连接不能复用，QPS 上去后本地端口耗尽，同时每次都要重新 TLS 握手。
  • io.Pipe 的写端出错时只调 Close()：读端拿到的是干净的 EOF，半截数据被当成完整内容，要用 CloseWithError。
  • 先判 err != nil 再处理 n 字节：最后一次读同时返回数据和 EOF 时丢尾部，只在数据长度恰好落在边界时复现。
  • 对 net.Conn 调 Seek：网络流不可回退，需要重读就得自己缓存或用 HTTP Range。
  • 自己写 for 循环替代 io.Copy：白白放弃 sendfile 与 splice，静态文件服务场景差距明显。
  • 包了一层自定义 Writer 装饰器却没转发 ReadFrom：无意中把上游的零拷贝路径挡掉了。
  • 在 io.Copy 的目标是内存 buffer 时不限上限：等价于 ReadAll，同样会被大输入打爆。
