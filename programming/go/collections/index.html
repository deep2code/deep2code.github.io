集合操作与数据聚合的惯用法

🏷️ Go 语言

这篇的靶子是：Go 做数据聚合没有语法糖，但有固定的标准写法——分组就是 map[K][]V 加一个循环，计数就是 map[K]int 自增，去重就是 map[T]struct{}。真正出事的地方不在「怎么写」，而在三个隐蔽处：分组 key 的类型选错（time.Time 把同一天拆成好几组）、依赖 map 的遍历顺序（输出每次都不一样）、分组基数失控（按用户 ID 分组的 map 直接吃光内存）。这三件事都能在动手前用一张清单挡掉。

💡
这篇怎么读
  • ① 用法：七个可以直接抄走的定式（分组、计数与求和、多字段分组、去重、稳定输出、交集、分组基数上限），配「要做什么 → 怎么写 → 用错的后果」对照表，以及动手前必过的「map key 选错」自查清单。
  • ② 原理：Go 为什么刻意不提供完整流式 API、maps 与 slices 包把返回值改成迭代器带来的迁移坑、map key 可比较性在编译期与运行期的两套规则、range over func 里 yield 返回 false 的逐层传递，以及显式循环在七个维度上的对比。
  • ③ 场景：聚合该放数据库还是应用层的判断图与决策矩阵，集合用 map 表示的两种不适用情况。

① 用法 · 分组、聚合、去重的七个定式

下面是一个完整可编译的文件，七个定式覆盖日常聚合需求的绝大部分。注释只解释「为什么必须这么写」，机制原因在原理层展开。

package agg

import (
    "fmt"
    "maps"
    "slices"
    "time"
)

type Order struct {
    ID          int64
    Channel     string
    Status      string
    AmountCents int64 // 金额一律用整数分，浮点做累加会攒出对不上账的尾差
    CreatedAt   time.Time
}

// 定式一：分组就是 map 键到切片。对 nil 切片 append 是合法的，
// 所以不需要「先判断 key 存不存在」那一步，分组代码只有三行
func GroupBy[T any, K comparable](items []T, keyFn func(T) K) map[K][]T {
    out := make(map[K][]T)
    for _, it := range items {
        k := keyFn(it)
        out[k] = append(out[k], it)
    }
    return out
}

// 定式二：只要计数或求和就别先分组。分组会把所有元素留在内存里，
// 而直接累加的内存只和分组数量有关，与元素数量无关
func CountBy[T any, K comparable](items []T, keyFn func(T) K) map[K]int {
    out := make(map[K]int)
    for _, it := range items {
        out[keyFn(it)]++ // 缺失键的零值是 0，直接自增即可
    }
    return out
}

func SumBy[T any, K comparable, N int64 | float64](
    items []T, keyFn func(T) K, valFn func(T) N) map[K]N {
    out := make(map[K]N)
    for _, it := range items {
        out[keyFn(it)] += valFn(it)
    }
    return out
}

// 定式三：多字段分组用「字段全部可比较」的结构体做 key。
// 时间字段必须先格式化成字符串再进 key（原因见原理层的可比较性一节）
type dayChannel struct {
    Day     string
    Channel string
}

func GroupOrders(orders []Order) map[dayChannel][]Order {
    return GroupBy(orders, func(o Order) dayChannel {
        return dayChannel{
            Day:     o.CreatedAt.Format("2006-01-02"),
            Channel: o.Channel,
        }
    })
}

// 定式四：去重用空结构体做值，零字节；顺序靠 out 切片保留首次出现次序，
// 因为 map 本身完全不记顺序
func Unique[T comparable](items []T) []T {
    seen := make(map[T]struct{}, len(items))
    out := make([]T, 0, len(items))
    for _, it := range items {
        if _, ok := seen[it]; ok { // 必须用双赋值判断存在，不要把值当布尔
            continue
        }
        seen[it] = struct{}{}
        out = append(out, it)
    }
    return out
}

// 定式五：要给人看、要写文件、要被测试断言的输出，一律先排序。
// map 的遍历顺序是随机化的，不排序就得到一份每次运行都不同的结果
func ReportByChannel(orders []Order) []string {
    sums := SumBy(orders,
        func(o Order) string { return o.Channel },
        func(o Order) int64 { return o.AmountCents })
    lines := make([]string, 0, len(sums))
    for _, ch := range slices.Sorted(maps.Keys(sums)) { // Go 1.23 起 maps.Keys 是迭代器
        lines = append(lines, fmt.Sprintf("%s\t%.2f", ch, float64(sums[ch])/100))
    }
    return lines
}

// 定式六：交集永远遍历较小的那个集合，在较大的里查。
// 反过来写结果一样，但白跑的查找次数等于两个集合的大小差
func Intersect[T comparable](a, b map[T]struct{}) map[T]struct{} {
    small, large := a, b
    if len(b) < len(a) {
        small, large = b, a
    }
    out := make(map[T]struct{}, len(small))
    for v := range small {
        if _, ok := large[v]; ok {
            out[v] = struct{}{}
        }
    }
    return out
}

// 定式七：分组基数是会爆的。按渠道分组只有几十个键，按用户 ID 分组可能几百万个。
// 把上限写进代码，超了明确报错，而不是等着进程被 OOM 杀掉
func SumByCapped[T any, K comparable](
    items []T, keyFn func(T) K, valFn func(T) int64, maxGroups int,
) (map[K]int64, error) {
    out := make(map[K]int64)
    for _, it := range items {
        k := keyFn(it)
        if _, ok := out[k]; !ok && len(out) >= maxGroups {
            return nil, fmt.Errorf("too many groups (%d), aggregate in the database instead", len(out))
        }
        out[k] += valFn(it)
    }
    return out, nil
}

要做什么怎么写用错的后果
按某个字段分组map[K][]T 加一个循环，直接 append先写 if _, ok := m[k]; !ok 再初始化：多四行代码，且容易漏掉某条分支
只要每组的条数或金额map[K]int 自增 或 map[K]int64 累加先 GroupBy 再取 len：把全部元素留在内存里，数据量一涨就 OOM
按多个字段分组字段全可比较的结构体做 key拼字符串做 key：分隔符出现在字段值里就会把两个不同组合并成一组
分组维度里含时间先 Format 成日期字符串或取 Unix() 再取整直接用 time.Time：单调时钟与时区指针让同一天被拆成好几组
去重map[T]struct{} 加一个保留次序的 out 切片用 map[T]bool：每条多占一字节；直接 slices.Compact：只去相邻重复
输出报表、写文件、写单测断言slices.Sorted(maps.Keys(m)) 后再遍历直接 range map：顺序随机，diff 与断言全都写不了
求交集、差集、子集遍历较小的集合，在较大的里查遍历较大的那个：白跑的查找次数等于两集合大小差
聚合的数据量不确定流式边读边累加，并给分组数硬上限全表读进切片再聚合：今天跑得动不代表下个季度跑得动
迭代中要往外传 erroriter.Seq2[T, error]，或干脆改成显式循环用单值 iter.Seq：错误没地方放，只能 panic 或悄悄吞掉

① 用法 · 「map key 选错」自查清单

分组出错有一半源头在 key 的类型上，而且症状都不像「key 的问题」。动手写 map[K]... 之前先过一遍这张表：左边一列是你打算用的类型，后面三列告诉你会不会出事、出事长什么样。

打算用的 key 类型能不能用出事的症状该怎么改
整型、字符串、布尔能，无坑—首选
字段全部可比较的结构体能—多字段分组的标准做法，比拼字符串安全
定长数组（如 [16]byte）能—数组可比较、切片不可比较，这两个最容易混
含切片、map 或函数字段的结构体不能，编译期直接失败报错指向 map 声明处而不是那个字段把该字段换成它的摘要：拼成字符串或算哈希
time.Time语法上能，结果不可靠同一天被拆成三四个组，且只在部分数据上复现Format("2006-01-02") 或 Unix() 按粒度取整
接口类型能编译，动态类型不可比较时运行期 panic线上偶发 comparing uncomparable type换成具体类型，或提取一个可比较的标识
浮点数能，但 NaN 会漏NaN 不等于自身，每次写入都是新条目，map 无限增长入口就拦掉 NaN，或改用定点整数
指针能，但比的是地址两个内容相同的对象被分进不同组用对象里的业务主键做 key
大结构体（几十个字段）能，但每次读写都要整体比较热路径上哈希与比较成为开销只取参与分组的那几个字段组成小结构体

另外两个必须在动手时就决定、事后很难补的问题：输出要不要稳定（要，就固定写 slices.Sorted(maps.Keys(m))），分组基数上界是多少（估不出来，就说明这个聚合应该放在数据库侧，理由见场景层）。

② 原理 · Go 没有 Stream，这是刻意的

搞清这一节，能解释为什么上面全是循环而不是链式调用，以及什么时候破例用迭代器是划算的。

从 Java 或 C# 过来的人第一件事就是找 stream().filter().map().collect()，然后发现 Go 什么都没有。这不是标准库没做完——Go 刻意不提供完整的流式 API，理由有三个，而且每一个都站得住脚。

第一，错误处理：Go 的错误是返回值，链式调用里没有地方放它。第二，可读性：链式写法从里往外读，和执行顺序相反，调试时断点不好下。第三，性能：每一环都是一层闭包调用，还容易在中间产生临时切片，而一个显式循环可以一次遍历做完全部工作并且一次分配到位。

② 原理 · maps 与 slices 包带来的变化

搞清这一节，能解决一类具体现象：从 golang.org/x/exp/maps 迁移过来的代码突然编译失败，报「不能把迭代器当切片用」。

Go 1.21 的 slices 与 maps 包，加上 1.23 的迭代器，把原来要手写的东西补齐了一大半。但注意 maps.Keys 在标准库里返回的是迭代器，不是切片——从 golang.org/x/exp/maps 迁移过来的代码会编译失败。

去掉相邻重复slices.Compact更短的切片 原地压缩只去相邻 必须先排序才能全局去重

② 原理 · 分组 key 的可比较性：两套规则，两类症状

搞清这一节，能解释用法层那张自查清单为什么长这样：Go 对 map key 的约束分编译期与运行期两套。编译期看静态类型——切片、map、函数不可比较，含这些字段的结构体也不可比较，所以直接编译失败；运行期只对接口类型生效——接口的静态类型是可比较的，但装进去的动态类型如果不可比较，读写那一刻才 panic。这就是为什么「含切片字段的结构体做 key」是编译错误，而「map[any]T 里塞了一个切片」是线上偶发崩溃。

可比较不等于可靠。相等语义由类型自己决定：结构体逐字段比较、指针比地址、浮点遵循 IEEE 754（于是 NaN != NaN，每次写入都是一个新条目，这个 map 会一直长）。time.Time 是这类问题里最常见的一个。

❌
拿 time.Time 直接做分组 key

time.Time 内部有三个字段：墙上时钟、单调时钟读数、以及一个 *Location 指针。两个表示同一时刻的 time.Time 用等号比较可能不相等——来自 time.Now() 的带单调读数，从数据库读出来的不带；时区不同的两个值即使时刻相同也不相等。用它做 key 的症状是「同一天被分成了三四个组」。正确做法是先 Format 成日期字符串，或者取 Unix() 时间戳再按粒度取整。

还有一层常被忽略的成本：key 的大小直接影响每次读写的开销。map 的每次查找都要算一遍哈希并做一次相等比较，key 是几十个字段的大结构体时这两步都不便宜。所以分组 key 只放真正参与分组的字段，不要图省事把整个业务对象塞进去。

② 原理 · 迭代器：range over func 的真实控制流

搞清这一节，能解决「自己写迭代器包装层却 panic 提示 yield 在返回 false 后又被调用」这一类问题。

Go 1.23 的迭代器不是为了让你写链式，它的设计目的是让自定义容器能被 range 遍历。iter.Seq[V] 的定义就是 func(yield func(V) bool)——一个接收回调的函数，没有任何魔法。

sequenceDiagram participant C as 消费端的 range 循环 participant M as Map 包装层 participant F as Filter 包装层 participant S as 源 slices.Values C->>M: range 开始 把循环体包装成 yield 传进去 M->>F: 用自己的 yield 再包一层继续往下传 F->>S: 继续往下传 直到最内层的源 S->>F: 产出第一个元素 调用 yield F->>F: 判定是否保留 不保留就直接继续下一个 F->>M: 保留则调用上层的 yield M->>C: 应用映射函数后交给消费端的循环体 C-->>M: 循环体执行 break yield 返回 false M-->>F: 把 false 原样往下传 F-->>S: 收到 false 后必须立刻 return Note over F,S: 每一层收到 false 都必须立刻返回
忘记这一步会 panic 提示 yield 在返回 false 后又被调用 Note over C,S: 全程惰性 只遍历一次 不产生任何中间切片 
// Filter 返回一个惰性的过滤迭代器：它只是包装，不产生中间切片
func Filter[T any](seq iter.Seq[T], keep func(T) bool) iter.Seq[T] {
    return func(yield func(T) bool) {
        for v := range seq {
            if !keep(v) {
                continue
            }
            // yield 返回 false 表示消费端不要了（通常是 break 或 return）。
            // 这里必须立刻 return，继续调 yield 会直接 panic
            if !yield(v) {
                return
            }
        }
    }
}

func Map[T, U any](seq iter.Seq[T], f func(T) U) iter.Seq[U] {
    return func(yield func(U) bool) {
        for v := range seq {
            if !yield(f(v)) {
                return // 同样必须把提前退出的信号往下传
            }
        }
    }
}

func demoLazy(orders []Order) {
    // 三环链：切片到迭代器、过滤、映射。全程惰性，只遍历一次
    paid := Filter(slices.Values(orders),
        func(o Order) bool { return o.Status == StatusPaid })
    ids := Map(paid, func(o Order) int64 { return o.ID })

    for id := range ids {
        if id > 1000 {
            break // 这个 break 会一路传到最内层 让源提前停止产出
        }
        fmt.Println(id)
    }

    // 需要真的物化成切片时才 Collect，这一步会分配
    _ = slices.Collect(ids)
}

// 带 error 的迭代：用 iter.Seq2 的第二个值传错误。
// 这是 Go 里「流式处理加错误传播」唯一不别扭的写法
func ReadRows(rows *sql.Rows) iter.Seq2[Order, error] {
    return func(yield func(Order, error) bool) {
        defer rows.Close()
        for rows.Next() {
            var o Order
            if err := rows.Scan(&o.ID, &o.Channel, &o.AmountCents); err != nil {
                yield(Order{}, err) // 错误交给消费端决定中断还是跳过
                return
            }
            if !yield(o, nil) {
                return
            }
        }
        // 这一步最容易漏：迭代被中断的错误只有 rows.Err() 才拿得到
        if err := rows.Err(); err != nil {
            yield(Order{}, err)
        }
    }
}

标准库提供的算子只有 Collect Sorted Values All 这类最基础的filter map reduce flatMap 等一整套Go 的 Filter 与 Map 要自己写 而且社区不鼓励到处用
错误传播靠 iter.Seq2 的第二个值只能抛异常Go 侧类型更诚实 但签名更啰嗦
并行化没有 parallel 对应物parallelStream 一行开启Go 要自己用 goroutine 与 channel 编排

迭代器的并发编排、errgroup 与取消传播不在这篇展开，见 Go 并发原语与常见并发 bug 与 Go Context 的传播、取消与误用。

② 原理 · 为什么显式循环通常是更好的选择

搞清这一节，能在 code review 里给出可辩护的理由，而不是「我觉得循环更好」。这是本篇最想传达的判断：在 Go 里，除非数据源本身就是流，显式循环几乎总是更好的选择。

维度链式写法显式循环
阅读顺序从里往外读 与执行顺序相反从上往下 与执行顺序一致
错误处理没地方放 除非改成 Seq2 让签名复杂一倍直接 return 并用 fmt.Errorf 包上下文
提前退出要在每层包装里正确传递 false 漏了就 panic一个 break 就完事
调试断点落在闭包里 调用栈全是包装层断点落在业务逻辑那一行
分配次数每层一次闭包 物化时还要一次切片分配一次 make 到位 循环里不再分配
多个操作合并每加一个操作多一层同一个循环体里顺手就做了
可测试性要测的逻辑藏在匿名函数里把循环体提成命名函数即可单测
什么时候链式更好数据源是无界流 或者要在多处复用同一条处理管道其余全部场景
 
// ===== 链式写法：看着优雅，三个问题 =====
func chainStyle(orders []Order) []string {
    return slices.Collect(Map(Filter(slices.Values(orders),
        func(o Order) bool { return o.Status == StatusPaid }),
        func(o Order) string { return o.Channel }))
    // 问题一：要从最内层往外读，和执行顺序相反
    // 问题二：中间任何一步要返回 error 都没地方放
    // 问题三：每层一次闭包调用，热路径上这笔开销不是零
}

// ===== 显式循环：在 Go 里通常是更好的选择 =====
func loopStyle(orders []Order) ([]string, error) {
    out := make([]string, 0, len(orders)) // 一次分配到位
    for _, o := range orders {
        if o.Status != StatusPaid {
            continue
        }
        ch, err := normalizeChannel(o.Channel) // 需要 error 直接写，毫无障碍
        if err != nil {
            return nil, fmt.Errorf("order %d: %w", o.ID, err)
        }
        out = append(out, ch)
    }
    return out, nil
}

// ===== 大数据量：边读边聚合，内存只和分组数有关 =====
func aggregateStream(ctx context.Context, rows *sql.Rows) (map[string]int64, error) {
    const maxGroups = 100_000
    sums := make(map[string]int64)
    for o, err := range ReadRows(rows) {
        if err != nil {
            return nil, err
        }
        sums[o.Channel] += o.AmountCents
        // 分组基数本身也会爆：按渠道分组只有几十个键，
        // 按用户 ID 分组可能有几百万个，那个 map 就是内存杀手。
        // 给一个硬上限，超了明确报错，而不是等着被 OOM 杀掉
        if len(sums) > maxGroups {
            return nil, fmt.Errorf("too many groups (%d), aggregate in the database instead",
                len(sums))
        }
        if err := ctx.Err(); err != nil { // 长任务要响应取消
            return nil, err
        }
    }
    return sums, nil
}

做法内存占用适用条件风险
数据库 GROUP BY应用侧几乎为零逻辑能用 SQL 表达没有合适索引时会拖慢数据库 要先看执行计划

分批读取 每批聚合后合并批大小加分组数数据源支持分页或游标分页要用游标而不是偏移量 否则深翻页极慢

判断顺序固定是这样：能下推到数据库就下推（执行计划怎么看见 数据库性能优化：瓶颈定位顺序与优化手段的投入产出），下推不了再看数据量能不能装进内存，装不进就看分组基数——基数决定了流式聚合能不能成立，因为流式省掉的是原始数据的内存，省不掉那个结果 map。

③ 场景 · 集合运算与「不该用 map 当集合」的两种情况

标准库里没有 Set 类型，惯用法是 map[T]struct{}。交集、并集、差集这些运算也没有现成函数，都要自己写，但每个都只有五六行，而且写法有讲究——关键是永远遍历较小的那个集合，这能把复杂度从两个集合大小的乘积降到较小者的大小。

运算正确写法要点常见的低效或错误写法
判断元素是否存在用双赋值取第二个返回值对 map 键到 bool 直接当布尔用 无法区分不存在与存的是 false
并集先把较大的集合 maps.Copy 过来 再补较小的从空 map 开始逐个插入 多做一遍无用的哈希
交集遍历较小的集合 在较大的里查遍历较大的集合 白跑很多次查找
差集遍历被减集合 跳过在减集合里出现的先求交集再从并集里减 多走两遍
判断子集遍历小集合 发现一个不在大集合里就立刻返回假求完整交集再比长度 没必要走完
两个切片去重后求并建一个 map 边插入边判断是否新元素先各自去重再拼接再去重 遍历三遍
大规模集合运算两个切片都排序后做双指针归并建 map 在元素数极大时哈希与内存开销都更高
元素类型不可比较提取一个可比较的标识作为 key试图直接把切片当 key 编译失败

还有一个常被忽略的点：用 map 做集合时，写入顺序完全不保留。所以任何需要输出给用户、写进文件、或者参与后续比较的集合结果，都必须在最后显式排序，否则你会得到一个每次运行都不同的输出，diff 和测试断言全都没法写。这也是 slices.Sorted(maps.Keys(m)) 这个组合在实际代码里出现频率如此高的原因。

不适用边界：两种情况不该用 map 当集合。一是元素数量极大且元素本身很小（比如几千万个整数），这时排序后用双指针归并在内存和速度上都更优，因为 map 每个条目都有哈希桶的额外开销，量级判断见 算法与数据结构在后端工程中的位置；二是集合需要持久化或跨进程传递，那时有序切片是更自然的表示形式，序列化后也是稳定的。另外，聚合逻辑本身能用 SQL 表达时就不要搬到应用层，排序与切片操作的写法在 排序与切片操作的现代写法，给聚合函数写表驱动测试的方法在 测试策略与可测性设计。

回到最上面三样工具：map[K][]V 做分组、map[K]数值 做累加、map[T]struct{} 做去重，配上泛型写一次 GroupBy、CountBy、SumBy，覆盖日常九成需求。maps 与 slices 包省掉的是琐碎的辅助函数，不是改变了做法；迭代器值得知道，但它的价值在于让自定义数据源可被 range 以及用 iter.Seq2 传 error，不是拿来当 Stream 用。

本篇在簇里的位置：排序与切片操作的现代写法 解决的是「一个切片内部怎么排、怎么查、怎么改」，这篇往上走一层处理「多条记录之间的归并与聚合」，下一步离开数据操作，转向把这些代码组织成包与模块。

最容易踩的坑

❌
避坑清单
  • 拿 time.Time 直接做分组 key：单调时钟与时区指针让同一时刻的两个值不相等，同一天被拆成好几组。先 Format 或取时间戳。
  • 用含切片字段的结构体做 key：直接编译失败，报错指向 map 声明处而不是那个字段，第一次遇到会找半天。
  • map[any]T 里塞进切片或 map：编译能过，读写那一刻 panic 提示比较了不可比较的类型，而且只在特定数据上复现。
  • 依赖 map 的遍历顺序：它是随机化的，每次运行都不同。要稳定输出必须 slices.Sorted(maps.Keys(m))。
  • 用浮点数做 key 却没拦 NaN：NaN 不等于自身，每次写入都是新条目，这个 map 会一直长到把内存吃光。
  • 拼字符串当复合 key：分隔符一旦出现在字段值里，两个不同的组合被并成同一组。用字段全可比较的结构体。
  • 从 x/exp/maps 迁移时以为 maps.Keys 还返回切片：标准库版本返回迭代器，要 slices.Collect 才是切片。
  • 用 map[T]bool 做去重集合：每个条目多占一个字节，元素多时是实打实的浪费。用 map[T]struct{}。
  • 只想计数却先 GroupBy 再取 len：白白把所有元素保留在内存里。直接用 map[K]int 自增。
  • 以为 slices.Compact 能全局去重：它只去相邻重复，必须先排序。
  • 长期持有 slices.Chunk 产出的块：它们是原切片的子切片，共享底层数组，会把整个大数组保活。
  • 求交集时遍历较大的那个集合：结果对，但白跑的查找次数等于两个集合的大小差，在热路径上很显眼。
  • 写迭代器包装层时忽略 yield 的返回值：消费端 break 之后你还在调 yield，直接 panic。
  • 用 iter.Seq 却要传 error：单值迭代器没地方放错误，需要就用 iter.Seq2，或者干脆改成显式循环。
  • 从 sql.Rows 迭代时漏掉 rows.Err()：迭代中途断开的错误只在那里，不检查就把不完整的结果当成完整结果。
  • 在应用层对高基数字段分组：按用户 ID 分组可能产生几百万个键，map 本身就把内存吃光。给分组数设硬上限并改到数据库侧聚合。
  • 先把全表读进内存再聚合：数据量是会长的，今天跑得动不代表下个季度跑得动。一开始就写成流式。
