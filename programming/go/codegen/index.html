代码生成与 go:generate 工程实践

🏷️ Go 语言总览

为什么 Go 需要代码生成

Go 刻意不提供宏，也没有运行时反射之外的元编程能力。这让语言保持了简单，代价是有一类需求在语言内无解：需要读取标识符名字、遍历方法签名、或者从另一种语言的定义推导出 Go 代码。泛型解决不了这些，因为泛型参数化的是类型，不是代码结构。

所以「构建之前先跑一个程序把代码写出来」在 Go 生态里不是权宜之计，而是一等公民：标准库的 go generate 命令、stringer、protoc-gen-go、sqlc、wire 都建立在这个模式上。

stringer：给枚举生成 String 方法

stringer 解决的是两个很具体的问题。第一，枚举打日志时是数字：日志里写着 status=3，排查时得回头翻常量定义。第二，新增枚举值时手写的 switch 忘了加 case，编译器不会提示，表现是那个新状态显示成空串。

//go:generate go tool stringer -type=OrderStatus -trimprefix=OrderStatus -output=order_status_string.go

// OrderStatus 订单状态。iota 生成的是连续整数，
// 不转字符串的话日志和接口响应里看到的就是 0 1 2 3 这种读不懂的数字
type OrderStatus int

const (
    OrderStatusPending  OrderStatus = iota // 待支付
    OrderStatusPaid                        // 已支付
    OrderStatusShipped                     // 已发货
    OrderStatusDone                        // 已完成
    OrderStatusCanceled                    // 已取消
)

跑一次 go generate ./...，得到下面这个文件。注意里面那个空函数 _()——这是 stringer 埋的编译期断言，很多人不知道它的作用：

// Code generated by "stringer -type=OrderStatus -trimprefix=OrderStatus"; DO NOT EDIT.

package order

import "strconv"

// 这个空函数是编译期断言。如果有人改了某个常量的值，
// 下面的数组下标就会越界，编译直接失败并提示重新跑 stringer。
// 但注意：在末尾「追加」新常量不会触发它，因为已有下标都还有效
func _() {
    var x [1]struct{}
    _ = x[OrderStatusPending-0]
    _ = x[OrderStatusPaid-1]
    _ = x[OrderStatusShipped-2]
    _ = x[OrderStatusDone-3]
    _ = x[OrderStatusCanceled-4]
}

// 所有名字拼成一个字符串常量，配一个偏移表，
// 这样 String 不产生任何分配，也不需要 map 查找
const _OrderStatus_name = "PendingPaidShippedDoneCanceled"

var _OrderStatus_index = [...]uint8{0, 7, 11, 18, 22, 30}

func (i OrderStatus) String() string {
    if i < 0 || i >= OrderStatus(len(_OrderStatus_index)-1) {
        // 越界时返回 OrderStatus(7) 这种形式，而不是空串或 panic。
        // 这个输出形式本身就是「有人加了枚举值但没重新生成」的信号
        return "OrderStatus(" + strconv.FormatInt(int64(i), 10) + ")"
    }
    return _OrderStatus_name[_OrderStatus_index[i]:_OrderStatus_index[i+1]]
}

枚举形态stringer 能否处理怎么办
iota 连续整数能 最佳场景直接用 配 trimprefix 去掉类型名前缀
手动指定的非连续整数能 但生成的是分段查找可以用 但值跨度过大时生成物会变大
位掩码 每个值是一个 bit不能正确表达组合值手写方法 遍历 bit 拼接名字用竖线连接
底层类型是 string不需要 本身就可读需要校验合法性时手写一个 Valid 方法
需要同时支持 JSON 序列化只生成 String 不生成 Marshal手写 MarshalJSON 内部调 String 或用支持这个的生成器
需要从字符串反解回枚举不生成反向映射手写一个 map 或换用能生成双向映射的工具
⚠️
stringer 只生成 String 方法，不生成序列化

实现了 String() 之后，fmt 和 slog 会输出可读名字，但 encoding/json 不看 Stringer 接口，序列化出来的仍然是数字。接口响应里要返回名字必须自己实现 MarshalJSON，而且别忘了配套的 UnmarshalJSON——只做单向会导致「返回的是名字，但接收时只认数字」这种不对称。

常用生成器清单

生成器解决什么代价是什么
stringer为整型枚举生成 String 方法只覆盖单值枚举 位掩码与反解要自己写
mockgen为接口生成可设置期望的假实现接口一改所有 mock 要重新生成 且过度 mock 会让测试变脆
sqlc从真实 SQL 生成类型安全的查询函数与结构体表结构变更后必须重新生成 动态拼条件不如手写灵活
protoc-gen-go 与 grpc 插件从 proto 定义生成消息类型与客户端服务端桩代码需要 protoc 工具链 插件版本要和运行时库匹配
wire编译期依赖注入 按类型自动拼出构造顺序依赖图复杂时报错信息不直观 学习成本明显
easyjson 一类序列化生成器为结构体生成无反射的序列化代码字段一改要重新生成 代码量膨胀 只在序列化确实是热点时才值得
enumer 一类增强枚举生成器同时生成 String JSON 序列化与字符串反解比 stringer 多一个依赖 生成物更大
oapi-codegen 一类 API 生成器从 OpenAPI 定义生成服务端骨架与客户端定义与实现容易漂移 需要把定义作为唯一真源

关于 sqlc 为什么比 ORM 更受推崇，值得单独说一句：它让你写真实的 SQL，因此数据库的全部能力都能用，执行计划完全可预测，不存在「一个方法调用背后生成出意料之外的查询」这种问题；同时它解析 SQL 和表结构生成带具体类型的参数与返回结构体，字段名写错或类型不匹配在编译期就报错。这正好是 Go 社区偏好的组合：显式、可预测、错误尽早暴露。查询优化与执行计划判读本身是另一个话题，见本站数据库优化相关文章。

工程规范：四条不能省的规则

规范为什么不做的后果
生成物提交进仓库构建只依赖 Go 工具链 审查时能看到影响面新同事和 CI 首次构建失败 不同机器产出可能不同
文件头带 Code generated 与 DO NOT EDIT这是 Go 工具链识别生成文件的约定格式lint 与覆盖率统计把生成物当手写代码 报告全是噪音
CI 重跑生成并检查 diff 为空唯一能百分之百发现不一致的手段源改了生成物没改 线上出现奇怪的枚举数字或缺方法的 mock
工具版本锁定不同版本的生成器产出不同 diff 会变成噪音每个人本地生成的结果都不一样 git 冲突不断
go:generate 注释紧贴被处理的声明读代码时能立刻知道这个文件是怎么来的生成关系散落 没人知道某个文件该怎么重新生成
生成文件命名有统一后缀便于 lint 忽略与 CI 批量校验无法区分手写与生成 规则写不出来
生成物不做人工修改下次生成会被覆盖改动悄悄消失 而且是在别人重新生成时消失 极难定位

工具版本锁定这一条在 Go 1.24 之后有了官方答案：go.mod 支持 tool 指令记录工具依赖，用 go get -tool 添加，用 go tool 名字 执行。这样生成器的版本和 go.sum 里记录的一致，团队成员和 CI 用的完全是同一个版本，不再需要在 README 里写「请先 go install 某个工具」。

#!/usr/bin/env bash
set -euo pipefail

# 1. 工具版本由 go.mod 的 tool 指令锁定（Go 1.24 起）。
#    初始化一次：go get -tool golang.org/x/tools/cmd/stringer
#    之后 go:generate 里写 go tool stringer 即可，无需全局安装
go mod download

# 2. 全量重新生成
go generate ./...

# 3. 关键一步：检查工作区是否干净。
#    有人改了源文件却忘记重新生成，这里就会有 diff，流水线直接失败。
#    这是防止「生成物与源文件不一致」的唯一可靠手段
if ! git diff --exit-code; then
  echo "生成物与源文件不一致：请在本地执行 go generate ./... 并提交结果" >&2
  exit 1
fi

# 4. 顺带校验所有生成文件都带 DO NOT EDIT 头，
#    grep -L 列出「不含匹配内容」的文件
files=$(git ls-files '*_string.go' '*_gen.go' '*.pb.go' 'mock_*.go')
if [ -n "$files" ]; then
  missing=$(grep -L 'Code generated .* DO NOT EDIT\.' $files || true)
  if [ -n "$missing" ]; then
    echo "以下生成文件缺少 DO NOT EDIT 头：$missing" >&2
    exit 1
  fi
fi

go build ./... && go vet ./... && go test ./...

go:embed：不需要生成器的那一档

把静态文件变成 Go 代码曾经是生成器的经典用途：读文件、转义、写成一个巨大的字符串常量。go:embed（Go 1.16 起）让编译器直接做这件事，静态文件在仓库里保持原样，可以正常编辑、diff、被编辑器高亮。模板、前端资源、迁移脚本、默认配置这些场景一律用它，不要再写生成器。

场景用 go:embed用生成器选哪个
HTML 与文本模板一行注释加一个 embed.FS把模板转成字符串常量go:embed 模板文件保持可编辑
数据库迁移脚本嵌整个目录 交给迁移库逐个文件生成常量go:embed
前端构建产物嵌 dist 目录做单二进制部署不现实 产物太大go:embed
默认配置文件嵌成 byte 切片再解析生成一个配置结构体字面量go:embed 除非要在编译期校验配置
需要从数据推导出类型或方法做不到生成器的本职生成器
需要在编译期做校验做不到生成时校验 失败即构建失败生成器
 
import (
    "embed"
    "html/template"
)

// go:embed 注释必须紧贴变量声明，中间有空行就会被当成普通注释静默忽略——
// 这是最常踩的坑，因为不报错，只是变量变成空的 FS
//go:embed templates/*.tmpl
var templateFS embed.FS

//go:embed migrations
var migrationFS embed.FS

// 单个文件可以直接嵌成 byte 切片或 string，不必用 embed.FS
//go:embed config/default.yaml
var defaultConfig []byte

// 默认不包含以点或下划线开头的文件（比如前端构建产物里的 .well-known）。
// 需要全部包含时加 all: 前缀
//go:embed all:assets
var assetFS embed.FS

// 模板在包初始化时一次解析完：模板写错会在启动瞬间 panic，
// 而不是等到某个页面第一次被访问
var tmpl = template.Must(template.ParseFS(templateFS, "templates/*.tmpl"))

// 路径规则：相对当前包目录，不能用两个点跳出包外，也不能是绝对路径。
// 想嵌上层目录的文件只能在那个目录里另建一个包，或者构建前拷进来
⚠️
最容易踩的坑

1. 生成物不提交进仓库：新同事和 CI 首次构建直接失败，而且错误信息通常是「找不到某个方法」，离根因很远。

2. 手改生成文件：下次谁跑一遍 go generate 改动就消失，而且是在别人的提交里消失，排查极其痛苦。

3. CI 里不检查 git diff：这是防止生成物与源文件脱节的唯一可靠手段，少了它规范就是纸面上的。

4. 生成器版本不锁定：不同版本产出不同，每个人本地生成的结果都有 diff，git 冲突不断。用 go.mod 的 tool 指令锁住。

5. 在枚举末尾追加值后忘记重新生成：编译期断言抓不到追加，运行期表现为日志里出现 OrderStatus(5) 这种输出。

6. 改了已有枚举常量的值却不重新生成：这个会被编译期断言抓到直接编译失败，反而是好事——不要为了让它编译过而去删那个断言函数。

7. 以为实现了 String() JSON 就会输出名字：encoding/json 不看 Stringer，要自己写 MarshalJSON 和配套的 UnmarshalJSON。

8. 用 stringer 处理位掩码枚举：组合值会被当成未知值输出成数字形式，位掩码必须手写遍历 bit 的方法。

9. //go:embed 和变量声明之间留了空行：注释被当成普通注释，变量成了空 FS，运行时报「找不到文件」，而编译完全正常。

10. //go:embed 想用两个点跳出包目录：不允许，会编译报错。需要的话在那个目录另建一个包。

11. 生成文件不带 DO NOT EDIT 头：lint 报告和测试覆盖率统计会把它当手写代码，报告里全是无意义的噪音。

12. 把代码生成当万能解：给每个结构体都生成序列化、给每个接口都生成 mock，代码量翻几倍，构建变慢，而收益往往只在极少数热点上。

13. 过度 mock 导致测试变脆：接口一改所有 mock 要重新生成，测试改的比业务代码还多。能用真实实现或简单假实现的地方不要上 mock 框架。

结论

代码生成在 Go 里不是补丁而是设计的一部分：语言不给你宏，于是给了 go generate 这个统一入口和一整套约定。用好它只需要守住四条——生成物提交进仓库、带 DO NOT EDIT 头、工具版本用 go.mod 的 tool 指令锁住、CI 里重跑一遍并检查 git diff 为空。最后一条是整套规范的地基，没有它前三条都会慢慢腐化。

另一半的判断力在于知道什么时候不用它：静态文件用 go:embed，同逻辑不同类型用泛型，能接受运行期报错的简单场景用反射。生成器解决的是「必须产出新声明」这一类问题，超出这个范围就是在给自己加构建步骤和维护成本。
