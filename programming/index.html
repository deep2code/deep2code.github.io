编程语言与代码功底

Go · Node.js · Python · 算法与数据结构 · Java · 设计模式 · 测试 · Rust（共 69 篇）

这个分类收什么，不收什么

这里只回答两类问题：这门语言的运行时会怎么执行我写的代码，以及代码本身的功底——数据结构与复杂度、设计模式带来的接缝与代价、测试策略与可测性设计。它对应的是一个人打开编辑器之后能直接决定的那部分质量。

几类紧邻但已不在这个分类里的内容：跨服务的设计与治理（服务拆分、消息中间件、一致性、Kafka、注册发现与熔断限流）在 架构与分布式；对外契约与安全（REST、GraphQL、RPC、认证授权、Web 安全）在 接口、协议与安全；系统跑起来之后怎么看清它在 可观测性与性能；状态的存放与检索在 数据库与缓存。

分清这条边界不是分类洁癖，而是排查顺序问题：语言层可调的空间其实很小。一次线上超时里，运行时能解释的通常只占很小一块，其余落在下游容量、连接池与数据访问上。先判断归属再决定读哪一类，比按技术名字乱翻快得多。

接口 P99 抖动，但服务自身 CPU 与内存都很闲可观测性与性能，再看 熔断限流与舱壁隔离等待型延迟的来源在下游与排队，语言侧再优化也不会变
改了一个字段，几个调用方同时报错API 版本与兼容性演进这是契约问题，不是序列化库的用法问题

语言选型真正受约束的六个维度

关于语言的争论大多停留在语法和性能上，但线上系统里做决定的通常是另外六件事。判断方法很朴素：逐条问一遍，如果没有任何一条明显偏向新语言，就沿用主栈。引入第二语言的成本不是学习成本，而是从此每套工具链、每个中间件客户端、每次安全升级都要做两遍。

约束维度要回答的问题忽略它的真实后果
团队与招聘现有主栈是什么？出问题时半夜能上手改的人有几个？招人时这门语言的候选池有多大新服务写完人走了，一年后没人敢动，最终被整体重写
生态一等公民用到的数据库驱动、消息客户端、链路追踪 SDK、配置中心客户端，在这门语言里是官方维护还是社区孤儿自己维护客户端与埋点，每次中间件升级都要跟一次
运行模型业务是 IO 等待为主还是 CPU 计算为主？阻塞一次的代价是一个协程、一个线程还是整个进程把阻塞写法套进事件循环，或用线程池扛高并发 IO，尾延迟无法收敛
部署形态镜像多大、冷启动多久、常驻内存多少、是否需要预热才进入稳态弹性扩容的速度赶不上流量爬升，扩了也救不了当前这波
线上可观测能不能在不重启的情况下抓到 CPU 火焰图、堆快照、阻塞栈线上问题只能靠重启掩盖，同一个故障反复发生
退出成本如果三年后要换掉它，需要改动多少跨服务边界与运维脚本语言绑死在某个框架的私有约定上，迁移预算等于重写

运行模型如何反过来决定架构

同一套业务需求，用不同运行时写出来的架构不会相同，因为「阻塞一次的代价」不同，容量规划的单位也不同。这张对照表是选型讨论里最该先摊开的一页，也是这个分类里所有语言系列的公共底座。

运行时并发单位与调度一次阻塞的代价CPU 密集怎么办容量规划的单位
Gogoroutine，运行时做 M 比 N 调度，初始栈只有几 KB 且按需增长网络 IO 被运行时转为非阻塞并交给网络轮询器；阻塞系统调用会让当前 P 与 M 解绑，代价可控直接开 goroutine，用 GOMAXPROCS 控制并行度，用信号量控制并发连接池大小与下游可承载并发，而不是 goroutine 数量
Java平台线程与内核线程一比一（默认栈约 1MB），靠线程池复用；JDK 21 起可用虚拟线程平台线程阻塞就占住一个内核线程，池满即排队；虚拟线程把这个代价降到接近协程线程池加 ForkJoin，JIT 进入稳态后吞吐很高线程池上限、堆大小与 GC 停顿预算
Python（CPython）线程受 GIL 约束，同一时刻只有一个线程执行字节码；asyncio 是单线程事件循环不释放 GIL 的阻塞调用会让整个进程停摆，而不只是当前线程多进程按 CPU 配额横向堆，或把热点交给 C 扩展进程数乘以进程内协程数
Node.js单线程事件循环加 libuv 线程池（线程池默认 4，由 UV_THREADPOOL_SIZE 控制）同步阻塞直接卡住事件循环，所有在途请求一起变慢worker_threads 或多进程，主循环只做编排进程份数与事件循环延迟预算
⚠️
四个会直接算错容量的误解

goroutine 便宜所以可以无限开：协程便宜，它持有的连接不便宜，上限来自连接池与下游容量。GIL 让 Python 不能并发：GIL 限制的是并行执行字节码，IO 等待期间会释放，纯 IO 服务用协程照样吃满带宽。虚拟线程等于免费的高并发：它只让阻塞变便宜，连接池与下游限额一点没变；早期版本在 synchronized 内阻塞还会固定载体线程，直到 JDK 24 才解决。Node 单线程所以性能差：单线程指的是 JS 执行线程，真正的风险是大对象序列化、同步加密、正则回溯把事件循环占死。

还有一类问题不属于语言而属于容器：运行时看到的资源和 cgroup 给的不是一回事。Go 运行时长期只按机器可见 CPU 数设置 GOMAXPROCS，不看 cgroup 的 CPU limit（Go 1.25 起才开始感知容器限制），此前限额一核的容器跑在多核宿主机上会被 CFS 周期性限流，打出规律的长尾。JVM 从 8u191 与 JDK 10 起默认开启容器支持，默认最大堆约为限额内存的四分之一，所以给容器加内存不等于给堆加内存。

代码功底的三块：算法、设计模式、测试

这三块常被当成面试内容，但它们的工程落点很具体：算法与数据结构决定复杂度是否可控，设计模式决定改需求要不要动一大片代码，测试决定你敢不敢改。三者的判据都是代价，不是优雅。

这一块工程里的真实判据用过头的代价对应内容
算法与数据结构先做量级估算：数据规模一年后是多少，这个实现的复杂度还撑不撑得住；再看容器选择带来的内存布局与分配次数为一个一千条数据的列表写复杂结构，维护成本远超收益算法与数据结构在后端工程中的位置、复杂度分析的工程用法
设计模式只在「已经出现第二个变化方向」时加接缝；接缝的收益是替换成本下降，代价是调用栈变长、排障变难三层工厂套装饰器，读代码要跳七八个文件才能找到真正干活的地方设计模式的本质与代价、创建型模式的真实取舍
测试与可测性按反馈速度分层：单元测试覆盖分支与边界，集成测试覆盖真实依赖的契约；Mock 只用于替换不可控的外部世界全用集成测试，跑一次十几分钟，最后没人在提交前跑它测试策略与可测性设计、单元测试怎么写、集成测试怎么写

一条常被跳过的顺序：先做量级估算，再选数据结构，最后才谈优化。很多「性能优化」在优化一个只有几百条数据的循环，真正的代价却在一次 N 加一的数据访问上——那属于 应用侧的数据库访问优化。

这个分类各二级方向怎么读

不建议按顺序通读。三条常见路线：接手一个存量服务，先读它所用语言的总览，再读该语言的并发与性能篇；要新写一个服务，先读上面的选型维度与运行模型两节，再按测试分层把可测性一开始就设计进去；系统补基础或准备面试，按算法、设计模式、测试三块自测，缺哪块补哪块。

❌
这个分类里最容易走错的判断
  • 把「语言性能」当成选型第一原则，忽略生态一等公民与招聘半径，最后维护成本压过性能收益
  • 压测用宿主机、上线跑容器，两边的 CPU 与内存默认值不同，压测数据完全不可迁移
  • 并发上限按「能开多少协程或线程」估，而不是按连接池与下游可承载并发反推
  • 把等待型延迟当成语言问题，在代码里反复微调，真实瓶颈一直留在下游与排队上
  • 数据结构凭手感选，没做量级估算，数据涨一个数量级后复杂度直接失控
  • 先加接缝再等变化：模式套了三层，变化方向却始终只有一个，只剩下排障变难的代价
  • 测试全压在集成层，跑一次十几分钟，最后演变成提交前跳过、合并后再修
