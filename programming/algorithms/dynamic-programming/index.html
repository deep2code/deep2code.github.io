动态规划的识别、状态设计与工程边界

🏷️ 算法,动态规划

把动态规划说成「递归加缓存」是个害人的简化。缓存只解决重复计算，而 DP 能成立靠的是两个更硬的前提：最优子结构（全局最优可以由子问题最优拼出来）和无后效性（一个状态一旦确定，后续决策与「怎么走到这个状态」无关）。前者决定转移方程写出来是对的，后者决定状态定义是完整的。这篇按三段组织：先给工程里遇到最优化需求时的标准动作——自查、估规模、套模板、做对照，再展开状态设计与各类模型的机制，最后收拢「什么时候该放弃 DP」的判断。

① 用法 · 三问自查、规模阈值与两个模板

遇到一个「求最优」的需求，标准动作是四步：自查能不能用 DP、算状态空间、套模板、用第二种实现做对照。四步都很便宜，跳过任何一步的代价都比走完贵。

第一问：子问题的最优解能拼出全局最优吗？拿不准就别推理，直接写十行穷举，对小规模随机数据跑一百组对照——这是成本最低的否证手段。

第二问：同一个状态下，两条不同的到达路径会让后面能做的决策不同吗？会，就说明状态漏了信息，必须把缺的补进状态；补完之后回到第三问重算规模。典型的例子是「路径不能重复经过节点」，补上访问集合后状态数变成指数级——那它已经不是 DP 问题了。

第三问：状态空间多大？把各维度的取值个数相乘。这一步必须真的算出数字，因为它同时决定「能不能写 DP」和「写哪一种」。下面这段代码把自查和阈值判断固定下来，顺手给出两个模板：

"""DP 的标准动作：先自查，再估规模，最后从两个模板里挑一个。"""
from functools import lru_cache
from math import inf

# ---- 第一步：三问自查。写成常量是为了逼自己逐条回答，而不是凭手感开写 ----
CHECKLIST = (
    "最优子结构：子问题最优能拼出全局最优吗，拿不准就先写小规模穷举做对照",
    "无后效性：同一状态的两条到达路径会让后续决策不同吗，会就说明状态漏了信息",
    "状态空间：各维度取值个数相乘有多大，超线就不要写 DP",
)


# ---- 第二步：算状态空间，据此决定走哪条路 ----
def plan(dims, value_bytes=8, mem_budget_mb=256):
    """dims 是各维度的取值个数，例如 (物品数加一, 预算档位数加一)。
    返回 (状态数, 建议)。阈值是工程刻度，要按自己服务的内存与延迟预算调，
    但「动手前先算一遍」这件事不能省——它能在写代码之前否掉方案。
    """
    states = 1
    for d in dims:
        states *= d
    mem_mb = states * value_bytes / 1024 / 1024
    if mem_mb > mem_budget_mb:
        return states, "超内存预算：先降维或把离散粒度放粗，仍超就换求解器或启发式"
    if states <= 10 ** 5:
        return states, "在线直接算：自底向上，DP 表用连续数组，别用哈希表"
    if states <= 10 ** 7:
        return states, "在线算要压 p99：优先滚动数组，否则离线预计算成版本化查表"
    return states, "状态太多：离线预计算加查表，或整数规划求解器，或贪心加局部搜索"


# ---- 第三步之一：记忆化模板。状态稀疏、维度多、要先写出来验证想法时用 ----
def min_packs_memo(target, sizes):
    """把 target 拆成给定箱规的最少箱数；凑不出返回 -1。
    记忆化只计算真正可达的状态，代价是递归深度由 target 决定，深了要换下面那个模板。
    """

    @lru_cache(maxsize=None)
    def f(rest):
        if rest == 0:
            return 0
        best = inf  # 不可达用 inf 表示，绝不能用 0：否则「凑不出」会被当成「代价为零」
        for s in sizes:
            if s <= rest:
                best = min(best, f(rest - s) + 1)
        return best

    r = f(target)
    f.cache_clear()  # 请求级缓存要显式释放，常驻进程里别让它无限长大
    return -1 if r == inf else r


# ---- 第三步之二：自底向上加滚动数组。状态稠密、内存要可控、不想有栈风险时用 ----
def min_packs_tab(target, sizes):
    """同一个问题的自底向上写法：无递归、内存连续、耗时可预测。
    这里是完全背包（同一箱规可重复使用），所以容量维正序遍历；
    如果是 0-1 背包（每个物品只能用一次）必须倒序，原因见原理层。
    """
    dp = [0] + [inf] * target
    for cap in range(1, target + 1):
        for s in sizes:
            if s <= cap and dp[cap - s] + 1 < dp[cap]:
                dp[cap] = dp[cap - s] + 1
    return -1 if dp[target] == inf else dp[target]


# ---- 第四步：两种实现互为对照，这是 DP 最便宜的正确性验证 ----
if __name__ == "__main__":
    import random

    for _ in range(200):
        t = random.randint(0, 60)
        sz = tuple(random.sample(range(1, 20), 4))
        assert min_packs_memo(t, sz) == min_packs_tab(t, sz)
    print(plan((200, 10001)))

怎么验证选对了：正确性靠三重对照——记忆化与自底向上互相对照、小规模与穷举对照、一维压缩版与二维版对照，随机跑几百组，三者不一致就是实现错了而不是「精度问题」；规模靠上面的 plan 先算一遍，别等写完才发现表开不出来；性能压 p99 且要用真实分布的输入（真实金额往往集中在几个档位，均匀随机会低估命中率）；线上要把状态数、求解耗时、是否降级打进日志，预计算表要带版本号。

这些动作背后的道理——为什么倒序、为什么不能用浮点、为什么背包不是多项式算法——在下面几节。

② 原理 · DP 成立的四个前提与不满足时的表现

搞清这一节能解决一类最难查的问题：代码跑得又快又不报错，但答案是错的。

工程上最常见的翻车是无后效性不成立却没察觉。判定方法很直接：把状态写出来，问一句「同一个状态下，两条不同的到达路径会导致后面能做的决策不同吗」。如果答案是会，那状态就漏了信息，必须把缺的那部分补进状态里——而补进去往往意味着维度爆炸。需要记录「已访问过哪些节点」的路径问题就是典型：补上集合维度后状态数变成指数级，这时候它已经不是 DP 题，而是搜索或整数规划题。

第二个容易忽略的前提是依赖关系必须是有向无环的。记忆化递归在状态互相依赖时不会报错，它会死循环，或者在用「计算中」标记时给出一个看起来合理但错误的值。写记忆化之前先确认状态的依赖能排出拓扑序，这一步比写转移方程重要，拓扑序的求法与环检测见 图算法在后端系统中的落地形态。

② 原理 · 记忆化还是自底向上：这不是风格问题

搞清这一节能解释用法层两个模板的分工，也能避免「压完一维才发现要输出方案」这种返工。

两种写法算的是同一个东西，但工程属性差别很大。记忆化递归只计算可达状态，当状态空间名义上很大而实际可达的部分很稀疏时，它可能比自底向上快一个数量级；代价是递归深度等于状态链长度，深度由输入决定，栈风险和函数调用开销都实打实存在。自底向上遍历整个状态空间，没有栈风险，内存访问连续、缓存命中率高，而且只有它能做滚动数组压缩。

关于滚动数组有两个坑值得单独说。第一，0-1 背包压成一维后必须倒序遍历容量，正序会让同一个物品被重复选，结果变成完全背包——这是最常见的 DP 实现错误，而且在小数据上经常测不出来。第二，压成一维之后就无法回溯出方案。业务上几乎总是既要最优值也要「选了哪些」，这时要么保留二维表，要么额外记录每个状态的决策位。先压缩再发现要输出方案，等于重写。

维度记忆化递归自底向上二维滚动一维状态压缩（位掩码）
计算的状态只算可达状态全部状态全部状态全部子集
内存缓存加调用栈状态数一到两行二的元素数次方
栈风险有，深度由输入决定无无无
能否回溯方案能，沿缓存反推能不能，需额外记决策能但要记前驱
缓存局部性差，哈希表随机访问好最好一般
并行化难按层可并行受依赖限制按子集大小分层可并行
适用场景状态稀疏、维度多、写着快需要方案或多次查询同一表只要最优值且内存紧元素数不超过二十几

② 原理 · 状态设计决定一切

搞清这一节能解释为什么同一个需求有人写出毫秒级实现、有人写出跑不动的版本：差别几乎总在状态定义上，而不是在代码质量上。

同一个业务问题，状态定义不同，复杂度可以差出指数级。设计状态时有三条实操准则。能放进下标的约束不要放进循环条件：把「已用预算」「剩余库存」这类连续约束离散化成维度，是 DP 得以成立的关键一步。维度越少越好，但少一维通常要换一个更强的观察：例如「必须相邻」这类限制可以用「上一步选了什么」这一维承载，而不是记录整个历史。值域也是成本：背包类问题的复杂度是物品数乘容量，这是伪多项式——容量按分计的金额动辄上亿，表就开不出来。

顺带纠正一个流传很广的误解：背包问题不是多项式时间可解的。它的复杂度含容量这个数值而非输入位数，所以是伪多项式，容量一大就不可行。真实业务里遇到大额金额约束，要么把金额粒度放粗（按元或按十元离散化并接受误差），要么改整数规划求解器。

另一个必须注意的工程细节是浮点金额不能直接做 DP 下标或状态键。0.1 加 0.2 不等于 0.3，本应相同的状态会因为浮点误差被当成两个状态，命中率下降、结果抖动。所有金额、比例、时长在进入 DP 之前统一整数化（以分、以毫秒为单位），出口再还原。

② 原理 · 背包与区间 DP 在业务里的真身

搞清这一节能把「背包」这个教学词翻译成你实际会接到的需求单：预算分配、库存拆单、套餐选购、阶梯计费。

背包家族在后端的对应物非常具体：营销预算在多个渠道间的分配是分组背包（每组最多选一个档位），库存拆单成若干箱规是完全背包或多重背包，云资源选购套餐是多重背包加上一个「不能低于需求」的下界约束。区间 DP 对应的是阶梯计费和分段聚合：给定用量把账期切成若干段、每段套一个费率，让总费用最低。

模型业务问题状态定义复杂度落地注意
0-1 背包固定预算下挑选一批一次性投入项前 i 项、已用预算 j 时的最大收益项数乘预算档位数预算必须整数化并放粗粒度
完全背包库存拆单成可重复使用的箱规凑出数量 j 所需的最小箱数箱规数乘目标数量要区分「凑不出」与「代价为零」，初始值用一个不可达大数
多重背包每种规格有库存上限的采购同上加规格已用数量可用二进制拆分降一维直接三重循环容易超时，先做二进制拆分
分组背包每个渠道只能选一个投放档位前 g 组、预算 j 时的最大收益组数乘预算乘组内档位组内循环必须在容量循环之内
区间 DP阶梯计费分段、账期切分区间 i 到 j 的最优代价长度的立方，可用决策单调性优化区间数大时先合并同费率相邻区间
树形 DP组织架构上的预算下发、依赖包裁剪以 u 为根的子树在给定配额下的最优值与节点数乘配额成正比递归深度等于树高，深树要改迭代

下面是分组背包的完整落地版本，它比用法层的模板多了两件业务上必需的事：金额整数化加放粗、以及记决策位以便回溯出方案。

package alloc

// Allocate 分组背包：每个渠道只能选一个投放档位，总预算有限，最大化预期收益。
// 金额一律用整数分，并按 step 放粗粒度：预算按分建表会直接把内存打爆。
type Option struct {
	Name   string
	CostFen int64 // 花费，单位分
	Gain   int64  // 预期收益，整数化后的值
}

func Allocate(groups [][]Option, budgetFen, stepFen int64) (int64, []string) {
	W := int(budgetFen / stepFen) // 档位数，决定表宽；step 越粗越省内存但误差越大
	dp := make([]int64, W+1)
	// pick[g][w] 记录第 g 组在预算 w 下选了哪个选项，-1 表示没选。
	// 只保最优值时一维就够，但业务要输出方案，必须额外记决策。
	pick := make([][]int16, len(groups))
	for g := range groups {
		pick[g] = make([]int16, W+1)
		for w := range pick[g] {
			pick[g][w] = -1
		}
	}
	for g, opts := range groups {
		// 分组背包：容量在外层且倒序，保证每组最多选一个
		for w := W; w >= 0; w-- {
			best, bestIdx := dp[w], int16(-1)
			for i, o := range opts {
				c := int(o.CostFen / stepFen)
				if c > w {
					continue
				}
				if v := dp[w-c] + o.Gain; v > best {
					best, bestIdx = v, int16(i)
				}
			}
			dp[w], pick[g][w] = best, bestIdx
		}
	}
	// 回溯方案：从最后一组、满预算往前推
	chosen, w := []string{}, W
	for g := len(groups) - 1; g >= 0; g-- {
		i := pick[g][w]
		if i < 0 {
			continue
		}
		o := groups[g][i]
		chosen = append(chosen, o.Name)
		w -= int(o.CostFen / stepFen)
	}
	return dp[W], chosen
}

② 原理 · 编辑距离：对的算法，错的用法

搞清这一节能解决一个具体事故形态：一个「字段对齐」的功能上线后把 CPU 打满，而算法本身抄得完全正确。

编辑距离在后端的真实用途是数据比对与模糊匹配：两份导入文件的字段对齐、地址与商户名归一、日志模板聚类、配置漂移检测。算法本身是教科书级的二维 DP，问题全出在用法上——它的代价是两串长度之积，一旦放到「拿一个输入去比一百万个候选」的场景，复杂度就是灾难。

正确的形态是两级：先用廉价手段粗筛，再对少量候选算精确距离。粗筛手段有 n-gram 倒排（按字符三元组建倒排，取共享 gram 数达阈值的候选）、SimHash 加汉明距离（适合长文本去重）、以及 BK 树（在度量空间里按距离分支，适合词典纠错）。精算阶段还有两个必用优化：阈值早停（只关心距离是否不超过 k 时，只需计算主对角线附近的带状区域，复杂度降到长度乘 k，而且一旦整行都超过 k 就能提前退出）和长度差剪枝（两串长度差已超过 k 就直接判否）。倒排与相关性排序的工程细节见 检索与搜索引擎。

顺便纠正一个常见假设：git 的 diff 不是朴素的 LCS 动态规划。朴素 LCS 的时间和内存都是两边长度之积，大文件上不可接受；git 用的是 Myers 差分算法，复杂度与「编辑脚本长度」相关，对差异很小的大文件极快。这也提示了一个通用思路：当输入很大但差异很小时，找一个复杂度与差异量相关的算法，而不是与输入规模相关的算法。

手段代价能否阈值早停适合的比对对象主要限制
Levenshtein 全表两串长度之积能，带状加行内剪枝短字符串精确判定候选多时必须先粗筛
Damerau 变体同上略高能含相邻字符换位的人工输入实现比 Levenshtein 微妙，易写错
加权编辑距离同上能键盘邻近键、形近字、同音字权重表要业务维护，否则不如不加
LCS 动态规划两串长度之积不便短文本相似度大文件要改 Myers 这类差分算法
n-gram 倒排粗筛与候选命中数成正比不适用百万级候选的第一级筛选只给候选集，不给精确距离
SimHash 加汉明距离常数级比较不适用长文本近重复检测短文本上区分度差
 
def bounded_levenshtein(a: str, b: str, k: int) -> int:
    """带阈值的编辑距离：只在主对角线附近 2k+1 的带状区域内计算。
    返回真实距离，或在确定超过 k 时返回 k+1（调用方只需判定是否相似）。
    复杂度从 len(a)*len(b) 降到 len(a)*(2k+1)，并且能整行早停。
    """
    if abs(len(a) - len(b)) > k:
        return k + 1                      # 长度差剪枝，最便宜的一刀
    if len(a) > len(b):
        a, b = b, a                       # 保证 a 较短，内存只需 O(len(a))
    INF = k + 1
    prev = list(range(len(a) + 1))
    for j in range(1, len(b) + 1):
        cur = [INF] * (len(a) + 1)
        cur[0] = j
        lo, hi = max(1, j - k), min(len(a), j + k)   # 带状边界
        row_min = cur[0] if lo > 1 else INF
        for i in range(lo, hi + 1):
            cost = 0 if a[i - 1] == b[j - 1] else 1
            cur[i] = min(prev[i] + 1,        # 删除
                         cur[i - 1] + 1,     # 插入
                         prev[i - 1] + cost) # 替换或匹配
            if cur[i] < row_min:
                row_min = cur[i]
        if row_min > k:
            return k + 1                  # 整行都超过阈值，后面不可能变小
        prev = cur
    return prev[len(a)] if prev[len(a)] <= k else k + 1

③ 场景 · 什么时候写 DP，什么时候换掉它

DP 的边界很清楚：状态空间一旦随输入指数增长，它就不再是工具而是陷阱。位掩码状态压缩的上限是元素数二十几个，再往上二的幂次就把内存吃光。排班、装箱、路径规划、资源编排这类问题在真实规模下几乎都越过了这条线，继续硬写 DP 的结果是先写两天、再调一周、最后发现只能跑玩具数据。

越线之后的选项有三类：交给求解器（把问题描述成整数线性规划或约束满足模型，让 CP-SAT、商业 MIP 求解器去做分支定界，它们内置的剪枝和割平面远强于手写搜索）、用启发式换确定性（贪心加局部搜索、模拟退火、束搜索，接受次优但可控时间）、或者改问题（把硬约束放松成软约束加惩罚项，或者把规模切小分批求解）。判断标准不是优雅，而是线上有没有时间预算——在线请求里任何无界搜索都必须带超时与降级路径。

状态空间量级可行手段典型响应时间预期注意
十万以内自底向上 DP，可在线计算毫秒级注意内存连续性，别用哈希表当 DP 表
百万到千万DP 加滚动压缩，或离线预计算成查表在线查表毫秒，离线构建分钟级预计算表要有版本与灰度切换
元素数二十几的子集枚举位掩码状压 DP秒级再多一个元素内存翻倍，没有余量
组合爆炸但约束清晰整数规划或约束求解器秒到分钟，需设时限必须设求解时限并接受可行解而非最优解
规模无上界或目标含软约束贪心加局部搜索、束搜索可控，由迭代次数决定要能报告解的质量，否则无法评估
场景该怎么做为什么代价
营销预算在十几个渠道各选一档，要求秒级返回并给出方案分组背包 DP，金额按元或十元放粗，记决策位回溯方案状态数落在十万量级，在线算得动且结果可解释放粗粒度带来误差；预算档位一细内存立刻上去

最容易踩的坑

❌
避坑清单
  • 把 DP 当成「递归加缓存」：缓存只解决重复计算，最优子结构与无后效性不成立时，加了缓存只是更快地算出错误答案。
  • 动手前不算状态空间：各维度取值个数相乘是一行代码的事，跳过它常常意味着两天之后才发现表开不出来。
  • 状态漏信息却没察觉：判据是「同一状态下不同到达路径是否影响后续决策」，会影响就说明状态不完整。
  • 对有环依赖写记忆化：不会报错，而是死循环或返回一个看似合理的错误值，写之前先确认能排拓扑序。
  • 0-1 背包压成一维后正序遍历容量：同一物品会被重复选，退化成完全背包，小数据往往测不出来。
  • 先压成一维再发现要输出方案：一维表无法回溯选择，必须保留二维或额外记录决策位，否则只能重写。
  • 只写一种实现就上线：记忆化与自底向上互为对照、再加小规模穷举，是 DP 最便宜的正确性验证。
  • 认为背包是多项式算法：复杂度含容量数值本身，属于伪多项式，金额按分建表会直接爆内存。
  • 用浮点金额做状态键或下标：精度误差会把同一状态拆成两个，命中率下降且结果抖动，必须整数化。
  • 完全背包求最小数量时把不可达状态初始化为零：「凑不出」和「代价为零」被混为一谈，要用不可达大数初始化。
  • 多重背包直接三重循环：数量上限大时必然超时，先做二进制拆分把它转成 0-1 背包。
  • 用哈希表当自底向上的 DP 表：随机访问毁掉缓存局部性，同样的复杂度实际慢很多。
  • 在线对全量候选算编辑距离：必须先用 n-gram 倒排或 SimHash 粗筛，再对少量候选做带阈值的精算。
  • 大文件比对用朴素 LCS：时间与内存都是两边长度之积，应改用复杂度与差异量相关的差分算法。
  • 状态空间越线了还硬写 DP：位掩码上限只有二十几个元素，越线就该转求解器或启发式，并给在线路径加超时与降级。
