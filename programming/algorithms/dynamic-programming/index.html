动态规划的识别、状态设计与工程边界

🏷️ 算法,动态规划

先判断题目配不配得上 DP

把动态规划说成「递归加缓存」是个害人的简化。缓存只解决重复计算，而 DP 能成立靠的是两个更硬的前提：最优子结构（全局最优可以由子问题最优拼出来）和无后效性（一个状态一旦确定，后续决策与「怎么走到这个状态」无关）。前者决定转移方程写出来是对的，后者决定状态定义是完整的。

工程上最常见的翻车是无后效性不成立却没察觉。判定方法很直接：把状态写出来，问一句「同一个状态下，两条不同的到达路径会导致后面能做的决策不同吗」。如果答案是会，那状态就漏了信息，必须把缺的那部分补进状态里——而补进去往往意味着维度爆炸。需要记录「已访问过哪些节点」的路径问题就是典型：补上集合维度后状态数变成指数级，这时候它已经不是 DP 题，而是搜索或整数规划题。

第二个容易忽略的前提是依赖关系必须是有向无环的。记忆化递归在状态互相依赖时不会报错，它会死循环，或者在用「计算中」标记时给出一个看起来合理但错误的值。写记忆化之前先确认状态的依赖能排出拓扑序，这一步比写转移方程重要。

记忆化还是自底向上：这不是风格问题

两种写法算的是同一个东西，但工程属性差别很大。记忆化递归只计算可达状态，当状态空间名义上很大而实际可达的部分很稀疏时，它可能比自底向上快一个数量级；代价是递归深度等于状态链长度，深度由输入决定，栈风险和函数调用开销都实打实存在。自底向上遍历整个状态空间，没有栈风险，内存访问连续、缓存命中率高，而且只有它能做滚动数组压缩。

关于滚动数组有两个坑值得单独说。第一，0-1 背包压成一维后必须倒序遍历容量，正序会让同一个物品被重复选，结果变成完全背包——这是最常见的 DP 实现错误，而且在小数据上经常测不出来。第二，压成一维之后就无法回溯出方案。业务上几乎总是既要最优值也要「选了哪些」，这时要么保留二维表，要么额外记录每个状态的决策位。先压缩再发现要输出方案，等于重写。

状态设计决定一切

同一个业务问题，状态定义不同，复杂度可以差出指数级。设计状态时有三条实操准则。能放进下标的约束不要放进循环条件：把「已用预算」「剩余库存」这类连续约束离散化成维度，是 DP 得以成立的关键一步。维度越少越好，但少一维通常要换一个更强的观察：例如「必须相邻」这类限制可以用「上一步选了什么」这一维承载，而不是记录整个历史。值域也是成本：背包类问题的复杂度是物品数乘容量，这是伪多项式——容量按分计的金额动辄上亿，表就开不出来。

顺带纠正一个流传很广的误解：背包问题不是多项式时间可解的。它的复杂度含容量这个数值而非输入位数，所以是伪多项式，容量一大就不可行。真实业务里遇到大额金额约束，要么把金额粒度放粗（按元或按十元离散化并接受误差），要么改整数规划求解器。

另一个必须注意的工程细节是浮点金额不能直接做 DP 下标或状态键。0.1 加 0.2 不等于 0.3，本应相同的状态会因为浮点误差被当成两个状态，命中率下降、结果抖动。所有金额、比例、时长在进入 DP 之前统一整数化（以分、以毫秒为单位），出口再还原。

背包与区间 DP 在业务里的真身

背包家族在后端的对应物非常具体：营销预算在多个渠道间的分配是分组背包（每组最多选一个档位），库存拆单成若干箱规是完全背包或多重背包，云资源选购套餐是多重背包加上一个「不能低于需求」的下界约束。区间 DP 对应的是阶梯计费和分段聚合：给定用量把账期切成若干段、每段套一个费率，让总费用最低。

完全背包库存拆单成可重复使用的箱规凑出数量 j 所需的最小箱数箱规数乘目标数量要区分「凑不出」与「代价为零」，初始值用一个不可达大数
多重背包每种规格有库存上限的采购同上加规格已用数量可用二进制拆分降一维直接三重循环容易超时，先做二进制拆分
分组背包每个渠道只能选一个投放档位前 g 组、预算 j 时的最大收益组数乘预算乘组内档位组内循环必须在容量循环之内
区间 DP阶梯计费分段、账期切分区间 i 到 j 的最优代价长度的立方，可用决策单调性优化区间数大时先合并同费率相邻区间
树形 DP组织架构上的预算下发、依赖包裁剪以 u 为根的子树在给定配额下的最优值与节点数乘配额成正比递归深度等于树高，深树要改迭代
 
package alloc

// Allocate 分组背包：每个渠道只能选一个投放档位，总预算有限，最大化预期收益。
// 金额一律用整数分，并按 step 放粗粒度：预算按分建表会直接把内存打爆。
type Option struct {
	Name   string
	CostFen int64 // 花费，单位分
	Gain   int64  // 预期收益，整数化后的值
}

func Allocate(groups [][]Option, budgetFen, stepFen int64) (int64, []string) {
	W := int(budgetFen / stepFen) // 档位数，决定表宽；step 越粗越省内存但误差越大
	dp := make([]int64, W+1)
	// pick[g][w] 记录第 g 组在预算 w 下选了哪个选项，-1 表示没选。
	// 只保最优值时一维就够，但业务要输出方案，必须额外记决策。
	pick := make([][]int16, len(groups))
	for g := range groups {
		pick[g] = make([]int16, W+1)
		for w := range pick[g] {
			pick[g][w] = -1
		}
	}
	for g, opts := range groups {
		// 分组背包：容量在外层且倒序，保证每组最多选一个
		for w := W; w >= 0; w-- {
			best, bestIdx := dp[w], int16(-1)
			for i, o := range opts {
				c := int(o.CostFen / stepFen)
				if c > w {
					continue
				}
				if v := dp[w-c] + o.Gain; v > best {
					best, bestIdx = v, int16(i)
				}
			}
			dp[w], pick[g][w] = best, bestIdx
		}
	}
	// 回溯方案：从最后一组、满预算往前推
	chosen, w := []string{}, W
	for g := len(groups) - 1; g >= 0; g-- {
		i := pick[g][w]
		if i < 0 {
			continue
		}
		o := groups[g][i]
		chosen = append(chosen, o.Name)
		w -= int(o.CostFen / stepFen)
	}
	return dp[W], chosen
}

编辑距离：对的算法，错的用法

编辑距离在后端的真实用途是数据比对与模糊匹配：两份导入文件的字段对齐、地址与商户名归一、日志模板聚类、配置漂移检测。算法本身是教科书级的二维 DP，问题全出在用法上——它的代价是两串长度之积，一旦放到「拿一个输入去比一百万个候选」的场景，复杂度就是灾难。

正确的形态是两级：先用廉价手段粗筛，再对少量候选算精确距离。粗筛手段有 n-gram 倒排（按字符三元组建倒排，取共享 gram 数达阈值的候选）、SimHash 加汉明距离（适合长文本去重）、以及 BK 树（在度量空间里按距离分支，适合词典纠错）。精算阶段还有两个必用优化：阈值早停（只关心距离是否不超过 k 时，只需计算主对角线附近的带状区域，复杂度降到长度乘 k，而且一旦整行都超过 k 就能提前退出）和长度差剪枝（两串长度差已超过 k 就直接判否）。

顺便纠正一个常见假设：git 的 diff 不是朴素的 LCS 动态规划。朴素 LCS 的时间和内存都是两边长度之积，大文件上不可接受；git 用的是 Myers 差分算法，复杂度与「编辑脚本长度」相关，对差异很小的大文件极快。这也提示了一个通用思路：当输入很大但差异很小时，找一个复杂度与差异量相关的算法，而不是与输入规模相关的算法。

手段代价能否阈值早停适合的比对对象主要限制
Levenshtein 全表两串长度之积能，带状加行内剪枝短字符串精确判定候选多时必须先粗筛
Damerau 变体同上略高能含相邻字符换位的人工输入实现比 Levenshtein 微妙，易写错
加权编辑距离同上能键盘邻近键、形近字、同音字权重表要业务维护，否则不如不加
LCS 动态规划两串长度之积不便短文本相似度大文件要改 Myers 这类差分算法
n-gram 倒排粗筛与候选命中数成正比不适用百万级候选的第一级筛选只给候选集，不给精确距离
SimHash 加汉明距离常数级比较不适用长文本近重复检测短文本上区分度差
 
def bounded_levenshtein(a: str, b: str, k: int) -> int:
    """带阈值的编辑距离：只在主对角线附近 2k+1 的带状区域内计算。
    返回真实距离，或在确定超过 k 时返回 k+1（调用方只需判定是否相似）。
    复杂度从 len(a)*len(b) 降到 len(a)*(2k+1)，并且能整行早停。
    """
    if abs(len(a) - len(b)) > k:
        return k + 1                      # 长度差剪枝，最便宜的一刀
    if len(a) > len(b):
        a, b = b, a                       # 保证 a 较短，内存只需 O(len(a))
    INF = k + 1
    prev = list(range(len(a) + 1))
    for j in range(1, len(b) + 1):
        cur = [INF] * (len(a) + 1)
        cur[0] = j
        lo, hi = max(1, j - k), min(len(a), j + k)   # 带状边界
        row_min = cur[0] if lo > 1 else INF
        for i in range(lo, hi + 1):
            cost = 0 if a[i - 1] == b[j - 1] else 1
            cur[i] = min(prev[i] + 1,        # 删除
                         cur[i - 1] + 1,     # 插入
                         prev[i - 1] + cost) # 替换或匹配
            if cur[i] < row_min:
                row_min = cur[i]
        if row_min > k:
            return k + 1                  # 整行都超过阈值，后面不可能变小
        prev = cur
    return prev[len(a)] if prev[len(a)] <= k else k + 1

什么时候不该写 DP

DP 的边界很清楚：状态空间一旦随输入指数增长，它就不再是工具而是陷阱。位掩码状态压缩的上限是元素数二十几个，再往上二的幂次就把内存吃光。排班、装箱、路径规划、资源编排这类问题在真实规模下几乎都越过了这条线，继续硬写 DP 的结果是先写两天、再调一周、最后发现只能跑玩具数据。

越线之后的选项有三类：交给求解器（把问题描述成整数线性规划或约束满足模型，让 CP-SAT、商业 MIP 求解器去做分支定界，它们内置的剪枝和割平面远强于手写搜索）、用启发式换确定性（贪心加局部搜索、模拟退火、束搜索，接受次优但可控时间）、或者改问题（把硬约束放松成软约束加惩罚项，或者把规模切小分批求解）。判断标准不是优雅，而是线上有没有时间预算——在线请求里任何无界搜索都必须带超时与降级路径。

状态空间量级可行手段典型响应时间预期注意

百万到千万DP 加滚动压缩，或离线预计算成查表在线查表毫秒，离线构建分钟级预计算表要有版本与灰度切换

规模无上界或目标含软约束贪心加局部搜索、束搜索可控，由迭代次数决定要能报告解的质量，否则无法评估

最容易踩的坑

1. 把 DP 当成「递归加缓存」——缓存只解决重复计算，最优子结构与无后效性不成立时，加了缓存只是更快地算出错误答案。

2. 状态漏信息却没察觉——判据是「同一状态下不同到达路径是否影响后续决策」，会影响就说明状态不完整。

3. 对有环依赖写记忆化——不会报错，而是死循环或返回一个看似合理的错误值，写之前先确认能排拓扑序。

4. 0-1 背包压成一维后正序遍历容量——同一物品会被重复选，退化成完全背包，小数据往往测不出来。

5. 先压成一维再发现要输出方案——一维表无法回溯选择，必须保留二维或额外记录决策位，否则只能重写。

6. 认为背包是多项式算法——复杂度含容量数值本身，属于伪多项式，金额按分建表会直接爆内存。

7. 用浮点金额做状态键或下标——精度误差会把同一状态拆成两个，命中率下降且结果抖动，必须整数化。

8. 完全背包求最小数量时把不可达状态初始化为零——「凑不出」和「代价为零」被混为一谈，要用不可达大数初始化。

9. 多重背包直接三重循环——数量上限大时必然超时，先做二进制拆分把它转成 0-1 背包。

10. 在线对全量候选算编辑距离——必须先用 n-gram 倒排或 SimHash 粗筛，再对少量候选做带阈值的精算。

11. 大文件比对用朴素 LCS——时间与内存都是两边长度之积，应改用复杂度与差异量相关的差分算法。

12. 状态空间越线了还硬写 DP——位掩码上限只有二十几个元素，越线就该转求解器或启发式，并给在线路径加超时与降级。
