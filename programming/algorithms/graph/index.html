图算法在后端系统中的落地形态

🏷️ 算法,图论

后端工程师很少写「图算法题」，但几乎天天处理图：服务调用关系、模块编译依赖、Terraform 资源引用顺序、账号设备关联网络、Kubernetes Owner 引用对象树、工单流转。

它们共同的特征是节点间的连接是数据而不是结构——边由业务产生、随时变化，而且经常在运行时才能确定。

这类问题真正的难点不在算法本身（Dijkstra 和拓扑排序都不到五十行），而在三件事：图的规模与更新频率决定了能用哪种存储。

遍历的内存峰值决定了服务会不会被一次请求打爆，以及图一旦被分片就几乎没有算法可以「原样搬过去」。

先给遇到关系类需求时的标准动作，再展开机制，最后收拢选型。

先确认是图问题，再决定用 SQL 还是自己遍历

关系类需求一上来就建图、就上图数据库，是这个领域最贵的错误。先用五问过一遍，八成需求在第二问或第三问就该停下。

第一问：连接是数据还是结构？边由业务产生、运行时才确定、随时变（好友、依赖、引用）才是图；代码写死层级（父子、分类）是树甚至几张表，别按图处理。

第二问：跳数固定吗？固定且不超过两跳，就是几次带索引的 join，不需要任何图算法——这一问能拦掉绝大多数「关联查询」需求。

第三问：我要的只是顺序吗？要的是「谁必须在谁之前」（部署编排、构建依赖、数据血缘调度），那是拓扑排序，几十行代码，不需要图存储。

第四问：我要的只是「是否同组」吗？账号合并、团伙聚类、影响域划分只问连通性，用并查集就够，实现见 树形结构的工程选型。

第五问：真的需要路径吗？要最短路、带权路径、可变跳数或路径模式匹配时才是真正的图算法。这时先估三个数：节点数、边数、最大出度；

再估最宽一层——粗略就是平均出度的跳数次方，平均出度 30 的三跳就是两万七千量级，这个数决定 BFS 队列会不会把内存吃掉。估完再写代码。

要做什么怎么做注意什么
查某个账号的直接关联（一到两跳）关系表加联合索引，写成普通 join索引按查询方向建；双向关系要存两条边或查两次
查三到四跳的关联，且能接受深度上限递归 CTE，见下面的 SQL必须同时限深度、去重、限结果数，三者缺一就可能扫全表
解析依赖并给出执行顺序Kahn 拓扑排序，按批输出以支持并行同批节点要排序，否则构建产物不可复现
依赖有环要报错失败时再跑一次 DFS 三色标记，输出环上节点只报「存在循环依赖」等于把定位成本丢给使用者
判断两个 ID 是否在同一关联团体并查集（离线全量）或限跳 BFS（在线单点）边要先分级，弱信号边不参与传导

全图迭代类计算（PageRank、社区发现）离线图计算框架，结果回写成标签延迟按小时计，不要挂在在线请求路径上

浅层关系查询的标准答案是一条 SQL，不是一套新存储。下面这条可以直接改表名用，四个限制项一个都不能删：

-- 有限跳数的关系展开：必须同时限制深度、去重、限制结果数，
-- 否则一个超级节点就能让这条查询扫掉整张表。
WITH RECURSIVE reach(account_id, depth, path) AS (
    SELECT :root, 0, ARRAY[:root]
    UNION ALL
    SELECT e.dst, r.depth + 1, r.path || e.dst
    FROM reach r
    JOIN account_edge e ON e.src = r.account_id
    WHERE r.depth < 3                   -- 深度硬上限，别用「查到底」
      AND e.weight >= 10                -- 边分级：弱关联边不参与传导
      AND NOT (e.dst = ANY(r.path))     -- 去重，避免在环上无限展开
)
SELECT account_id, MIN(depth) AS hops
FROM reach
GROUP BY account_id
ORDER BY hops
LIMIT 500;                              -- 结果集上限，保护调用方与数据库

依赖解析是高频需求，最小实现只有两个函数：成功用 Kahn 输出可并行批次，失败用 DFS 打出环。环检测价值全在能否指出环在哪，见原理层。

from collections import defaultdict


def toposort(nodes, deps):
    """Kahn 拓扑排序；返回可并行执行的批次列表。
    deps[x] 是 x 依赖的前置节点集合。
    对同批节点排序，保证同样输入得到同样的输出顺序（构建产物可复现）。
    """
    indeg = {n: 0 for n in nodes}
    nxt = defaultdict(list)
    for n, ps in deps.items():
        for p in ps:
            nxt[p].append(n)
            indeg[n] += 1
    batches, cur = [], sorted([n for n in nodes if indeg[n] == 0])
    seen = 0
    while cur:
        batches.append(cur)
        seen += len(cur)
        nxt_batch = []
        for n in cur:
            for m in nxt[n]:
                indeg[m] -= 1
                if indeg[m] == 0:
                    nxt_batch.append(m)
        cur = sorted(nxt_batch)
    if seen != len(nodes):
        raise ValueError("存在循环依赖: " + " -> ".join(find_cycle(nodes, deps)))
    return batches


def find_cycle(nodes, deps):
    """DFS 三色标记找出一条具体的环，用于报错定位。
    0 未访问 1 在栈上（灰） 2 已完成（黑）；遇到灰色节点即为回边。
    """
    color, stack, path = {n: 0 for n in nodes}, [], []

    def dfs(u):
        color[u] = 1
        path.append(u)
        for v in deps.get(u, ()):
            if color[v] == 1:
                return path[path.index(v):] + [v]
            if color[v] == 0:
                r = dfs(v)
                if r:
                    return r
        color[u] = 2
        path.pop()
        return None

    for n in nodes:
        if color[n] == 0:
            r = dfs(n)
            if r:
                return r
    return []

只要遍历的是业务数据驱动的图，下面四个上限就必须显式设置，因为图的形状由数据决定，而数据里一定会出现你没想到的形态：

限制项作用怎么定不设的后果
跳数上限控制层宽爆炸与 SQL 递归深度按业务语义定，通常二到四跳；再深的关联业务上也解释不清一次请求遍历全图，队列或临时表吃掉内存
访问节点数上限兜住跳数之外的意外形态按可接受的单请求耗时反推一个硬数字低跳数也可能因为超级节点扫到百万节点
结果条数上限保护调用方与序列化开销配合分页或「只返回 Top-N 加总数估计」响应体过大，网关超时或客户端 OOM
单点度上限把超级节点排除出传导通道按度分布的高分位截断，超过就不再展开公共出口 IP、明星账号把结果污染成一团
遍历超时在线路径的硬约束把预算传进遍历循环，超时返回部分结果并标记截断请求悬挂，连接池被慢查询耗尽
递归深度或改迭代防栈溢出与栈内存暴涨数据驱动的图一律用显式栈的迭代实现Go 表现为栈内存暴涨与 GC 压力，JVM 直接栈溢出

验证选对了：正确性上四类脏输入各跑一遍——自环、重复边、多个连通分量、一条真实环；拓扑排序与朴素实现两次运行一致；

规模用真实数据的度分布算最宽一层，别用平均出度，最大度节点单独取样；性能必须用含超级节点样本压，均匀随机图测不出任何问题；

线上要把「本次遍历访问了多少节点、是否被截断、截断原因」放进响应或日志，否则结果变差时无法区分是数据变了还是限制生效了。

这些动作为什么长这样——为什么两跳查询的扇出等于第一跳邻居数、为什么 BFS 比递归更容易爆内存、为什么环检测必须报出节点——在下面几节。

两种表示与它们的内存账

边数据本身只有几百兆，进程内存却涨了好几个 G。

教科书给的是邻接矩阵和邻接表，工程上真正在用的还有两种：CSR（把邻接表压成两个连续数组）和关系表（把边存在数据库里）。

选择标准不是「稠密还是稀疏」这么粗——要同时看判断某条边是否存在的频率和边的更新频率。

表示法内存量级遍历邻居判边存在增删边适用场景
邻接矩阵节点数的平方，与边数无关要扫一整行一次数组访问改一个位节点数几千以内且极稠密，或需要矩阵乘法
邻接表（指针或切片）与边数成正比，额外指针开销大顺序遍历，最自然要在邻居里查找追加或删除元素规模中等、边频繁变化的内存图
CSR 压缩邻接表与边数成正比，最紧凑连续内存，缓存最友好可二分，需邻居有序基本不支持，要整体重建离线构建、在线只读的快照图
边列表与边数成正比需要先排序或建索引不支持追加最便宜数据交换、批处理输入、Bellman-Ford
关系表加索引看索引膨胀一次索引范围扫描一次点查事务内可靠更新边要持久化、要一致性、跳数很少

一个常被忽略的成本是邻接表的指针与对象头开销：用「map 套 slice」表示百万级边的图，真实内存往往是边数据本身的数倍。

节点重编号成连续整数、用 CSR 存并整体原子替换，内存降一个量级，不能增量改边——匹配「离线算好、在线只读」的绝大多数在线场景。

BFS 与 DFS：内存峰值决定成败

一次两三跳的查询凭什么能把服务打爆。

「BFS 比 DFS 费内存，DFS 比 BFS 危险」这种笼统说法帮不上忙，得算具体数字。

BFS 内存峰值是最宽一层的节点数。社交、调用链图平均出度几十，第二跳几千、第三跳十万量级，队列直接吃掉堆。

DFS 的内存与深度成正比，但递归实现的深度就是调用栈深度。

递归 DFS 栈风险与语言强相关：Go goroutine 栈按需增长（64 位默认上限 1GB），常见内存暴涨、GC 压力而非立刻崩；JVM 线程栈默认几百 KB 到 1MB，几万层递归就抛 StackOverflowError；C/C++ 默认 8MB 栈，爆了就段错误。

任何外部数据驱动的图，递归遍历都必须显式限制深度并改迭代实现，因深度由数据决定，数据一定会出现没想到的形态。

遍历方式内存峰值回答的问题典型失效点
BFS最宽一层的节点数最少跳数、按层展开、影响范围高出度节点让队列爆炸，要限跳数与节点上限
递归 DFS与最大深度成正比可达性、环检测、拓扑序深度由数据决定，栈溢出或栈内存暴涨
迭代 DFS 加显式栈同上但可控同递归 DFS忘记在入栈前标记访问，导致同节点重复入栈
双向 BFS两侧各自较小的前沿两点间最短跳数需要反向边；有向图上反向邻接常常没建
迭代加深与深度成正比深度受限搜索且要最优解重复展开浅层，耗 CPU 换内存

最短路：算法只是约束里最简单的一环

改权重把最短路改写了、SPFA 在特定数据上集中超时、以及「大部分请求结果对、少数请求路线明显绕」。

Dijkstra 加二叉堆是默认答案，但它有三个前提在业务里经常不成立。第一，边权必须非负。

常见错误修法是「所有权重加常数变非负」，结果会变：路径边数不同，加常数就是按边数惩罚，最短路被改写。真有负权（退款、补贴、反向收益），用 Bellman-Ford 或 Johnson 重标定。

第二，权重必须是静态的。路径服务边权是「此刻通过该路段所需时间」，随路况每分钟变；目标通常多维：时间、费用、红绿灯、限行、货车限重。

多目标不能简单加权求和就当成单一权重，因为权重系数一变最优路径就跳变，用户会看到「刷新一下路线就换了」。

工程上的常规做法是离线做分层预处理（把图按层级收缩，长距离走高等级路网），在线只在小范围内做修正，并对结果做缓存与稳定性约束。

第三，A 星的最优性依赖启发函数可采纳。直线距离当启发值，只有边权也是距离才成立；边权为时间，启发值必须是直线距离/全网最高速度，否则高估丢最优解。

这个细节在自研路径服务里踩得最多，症状是「大部分请求结果对，少数请求路线明显绕」。

算法负权预处理成本单次查询代价边权变更代价适用场景
Dijkstra 加二叉堆不支持无与边数乘对数成正比无，每次重算通用单源最短路，图规模中等
Dijkstra 加桶队列不支持无权重为小整数时接近线性无权重是有界整数，例如以秒为单位的路段耗时

package shortest

import "container/heap"

// Edge 用 CSR 风格存储：head[u] 到 head[u+1] 是 u 的出边区间
type Graph struct {
	Head []int32 // 长度为节点数加一
	To   []int32
	W    []int32 // 必须非负；有负权请改用 Bellman-Ford
}

type item struct {
	node int32
	dist int64
}

type pq []item

func (p pq) Len() int            { return len(p) }
func (p pq) Less(i, j int) bool  { return p[i].dist < p[j].dist }
func (p pq) Swap(i, j int)       { p[i], p[j] = p[j], p[i] }
func (p *pq) Push(x any)         { *p = append(*p, x.(item)) }
func (p *pq) Pop() any           { o := *p; n := len(o); it := o[n-1]; *p = o[:n-1]; return it }

// Dijkstra 返回从 src 出发的最短距离；dist 为 -1 表示不可达。
// 采用惰性删除：不做 decrease-key，而是允许同一节点多次入堆，
// 出堆时用 done 标记跳过过期项。代码简单且实际更快，代价是堆里元素上限是边数。
func Dijkstra(g *Graph, src int32, limit int64) []int64 {
	n := len(g.Head) - 1
	dist := make([]int64, n)
	done := make([]bool, n)
	for i := range dist {
		dist[i] = -1
	}
	h := &pq{{src, 0}}
	dist[src] = 0
	for h.Len() > 0 {
		it := heap.Pop(h).(item)
		if done[it.node] {
			continue // 过期项，已经用更短的距离处理过
		}
		done[it.node] = true
		if limit > 0 && it.dist > limit {
			break // 半径剪枝：线上查询必须有上界，否则一次请求可能遍历全图
		}
		for i := g.Head[it.node]; i < g.Head[it.node+1]; i++ {
			v, nd := g.To[i], it.dist+int64(g.W[i])
			if dist[v] == -1 || nd < dist[v] {
				dist[v] = nd
				heap.Push(h, item{v, nd})
			}
		}
	}
	return dist
}

拓扑排序：环检测的价值在于能否指出环在哪

正常路径和失败路径用的不是同一个算法。

任务依赖、构建系统、数据血缘调度、启动顺序编排，本质都是在有向图上求拓扑序。

两种实现差别不在复杂度，在失败时给的信息量：Kahn 按入度归零逐个出队，结束后仍有节点没出队即有环，但不知环是哪几个；

DFS 三色标记在遇到「指向灰色节点的回边」时，栈上从该节点到当前节点就是环，可以原样打印出来。

这差别决定工程可用性。只报「检测到循环依赖」，人在几百个模块里手工二分；报出 order-service 依赖 user-service 依赖 coupon-service 依赖 order-service 一条环路径，立刻定位。

生产代码通常两者都用：Kahn 走正常路径、天然支持并行调度（同批入度为零任务可并发），DFS 只在失败时跑一遍出环。并发度控制见 Go 并发原语与常见并发 bug。

连通分量：关系分析里最常用也最容易做错的一步

分量算出来了，里面装着几十万个不相关的账号。

风控做团伙识别、账号体系做同人合并、资产盘点做影响域划分，第一步几乎都是求连通分量。

离线全量算用并查集最省事（详见 树形结构的工程选型 对并查集的展开），在线增量查某个节点所属分量则用限跳 BFS。

做错处通常不在算法，在边定义太宽：同 IP、同 UA、同 WiFi 名全当强关联边，几个公共出口 IP 把几十万账号连成巨大分量，毫无区分度。

正确做法：边分级、节点度设上限（超级节点不作传导通道），分量大小设阈值：超阈值的判为基础设施共享，不算团伙。

分布式环境下的图：分片是真正的断点

「先跑通单机版，之后再分片」这个计划在图上基本不成立。

图算法搬到分片存储，三个硬问题。跨分片遍历：两跳查询单机是内存随机访问，分片后变两轮网络往返，第二轮请求数即第一跳邻居数，扇出放大。

超级节点：明星账号、公共出口 IP、热门标签这类节点的度可能比平均值高几个数量级，无论怎么按节点哈希切分，它所在的分片都会成为热点。

一致性：遍历过程中边在变，拿到的结果既不是开始时刻的快照也不是结束时刻的，对账类场景不可接受。

可行的缓解手段都不优雅但有效：按社区或业务维度切分、不按节点哈希切，让多数边落在分片内；超级节点拆分，邻居按桶分散或跳过；

批量一跳接口代替逐节点请求，N 次往返压成一次；每次遍历带版本或时间戳，只读快照保证自洽。分片与一致性取舍见 分布式系统专栏。

图数据库、关系库还是内存图

「关系查询就该用图数据库」是个过度简化的结论。

分界线是跳数是否固定：固定在一到两跳时，关系表加合适联合索引通常比图数据库快、好运维，只是几次索引范围扫描；

跳数不定、需要路径模式匹配或可变长路径查询时，SQL 的递归 CTE 会写得很难看且优化器难以控制，图数据库的收益才显现。

场景该怎么做为什么代价
展示「和我有共同好友的人」这类固定两跳关系表加联合索引，或预计算一张邻居宽表两跳就是两次索引范围扫描，不需要图结构预计算要维护更新链路，漏更新会让结果长期错误

部署编排、构建依赖、数据血缘调度Kahn 拓扑排序输出并行批次，失败时报环只需要顺序，不需要图存储要保证同批排序以复现；增量变更要重新校验环
在线做任意跳数关系探索离线构建 CSR 只读快照，定期原子替换，查询带半径连续内存最省也最快，快照保证结果自洽数据新鲜度受构建周期限制；不能增量改边
路径规划与最小耗时路由离线分层预处理，在线小范围修正并缓存在线跑全图 Dijkstra 无法满足毫秒级预算预处理是小时级；路况更新后要重算受影响层
社区发现、PageRank、全图标签传播离线图计算框架，结果回写成节点标签供在线查全图迭代天然是批处理，不适合请求路径延迟按小时计；标签有时效，要带计算时间
边已经放不进单机内存按社区或业务维度分片，提供批量一跳接口按节点哈希切分会让每一跳都跨网络分片键选错就得重导数据；跨分片一致性只能靠快照版本
存在明星账号、公共出口 IP 这类超级节点先做度上限与节点拆分，再谈选存储度高几个数量级的节点在任何存储上都是热点截断会牺牲一部分召回，要向业务说明并留开关

不适用边界：只问「是否同组」不要上图遍历，用并查集，见 树形结构的工程选型；单跳关联的索引设计与执行计划判读在 MySQL 与 PostgreSQL 专栏；

关系数据的缓存与失效策略在 Redis 专栏；跨分片一致性、超时与重试的通用模型在 分布式系统专栏；遍历的复杂度与常数因子怎么算在 复杂度分析；

「最短路本身是一类 DP」这个视角以及状态设计在 动态规划；带剪枝的路径搜索与时间预算在 贪心与回溯。

最容易踩的坑

❌
避坑清单
  • 关系需求一来就建图：先过一遍自查，固定两跳是 join、只要顺序是拓扑排序、只问同组是并查集，都不需要图算法。
  • 为了让 Dijkstra 能跑，把所有边权加一个常数变成非负：不同路径边数不同，加常数等于按边数惩罚，最短路会被改写。
  • 线上服务依赖 SPFA：它平均快但最坏退化到节点数乘边数，网格图和对抗数据都能触发，超时会集中爆发。
  • 用直线距离给「以时间为权重」的 A 星当启发值：必须除以全网最高速度才可采纳，否则会高估并丢掉最优解。
  • 认为 BFS 一定比 DFS 省内存：BFS 峰值是最宽一层，社交图第二跳就到十万量级，比递归深度危险得多。
  • 对外部数据驱动的图用递归 DFS 且不限深度：深度由数据决定，Go 表现为栈内存暴涨，JVM 直接 StackOverflowError。
  • 迭代 DFS 在出栈时才标记访问：同一节点会被重复入栈，栈长度可能膨胀到边数级别。
  • 遍历不设节点数上限与超时：限了跳数不等于限了规模，一个超级节点就能让低跳数查询扫到百万节点。
  • 环检测只报「存在循环依赖」：必须用 DFS 三色标记输出环上节点序列，否则定位成本全丢给使用者。
  • 拓扑排序不对同批节点排序：同一份依赖每次得到不同顺序，构建产物不可复现，问题极难追。
  • 关系分析把同 IP、同 UA 都当强关联边：几个公共出口 IP 就能把几十万账号连成一个巨大分量。
  • 只用均匀随机图做压测：真实图的度分布是长尾的，不含超级节点的样本测不出任何问题。
  • 分片图按节点哈希切分后指望本地性：两跳查询的扇出等于第一跳邻居数，必须改批量一跳接口。
  • 忘记给超级节点设度上限：无论换哪种存储，度高几个数量级的节点都会把它所在分片变成热点。
  • 递归 CTE 不加深度上限、不去重、不限结果数：一个高度节点就能让这条 SQL 扫掉整张关系表。
