栈与队列的语义边界与并发实现

🏷️ 算法,栈,队列

栈首先是执行模型，其次才是数据结构

后端工程师和栈打交道最多的场合不是算法题，而是调用栈：它决定了递归能走多深、异常栈能打印多少层、协程要占多少内存。每个栈帧要放返回地址、参数、局部变量和寄存器保存区，所以「深度」是有成本的，而这个成本在不同运行时上差异巨大。

关键区别在于栈是固定的还是可增长的。JVM 线程栈由 Xss 决定，默认在几百 KB 到 1MB 量级，几千到几万层递归就抛 StackOverflowError；C/C++ 线程默认 8MB，爆掉直接是段错误，还可能先踩坏别的内存。Go 的 goroutine 栈从 2KB 起按需翻倍增长，上限由运行时设定（64 位上默认 1GB），所以常见表现不是立刻崩，而是内存悄悄涨上去、GC 扫栈变慢，等到触碰上限才 fatal error。这个差异决定了排查方式：JVM 看异常栈深度，Go 要看 goroutine 数量与栈内存指标。

由此得到一条硬规则：递归深度只要由外部数据决定，就必须改显式栈并设上限。解析上传的 JSON、遍历目录树、展开依赖图都属于这一类。显式栈还能随时中断保存进度，并把占用变成可监控的量。

单调栈与单调队列：滑窗聚合的底层结构

单调栈解决的是一类固定形状的问题：为每个元素找它左边或右边第一个比它大（或小）的元素。柱状图最大矩形、接雨水、股票跨度都是它的变形。单调队列解决的是另一类：固定窗口内的极值，每个元素进出各一次，整体线性。

它们在后端的对应是监控与限流的滑动窗口聚合。算「最近一分钟最大 RT」，朴素做法每次遍历窗口内全部样本，用单调队列则每次推进摊销常数。注意求和与计数不要用单调队列，那是环形缓冲加增量累加的活；分位数两者都不行，要用分桶直方图或 t-digest。

结构解决的问题形状后端对应场景易错点
单调递减栈右边第一个更大元素告警抬升点定位、峰值区间划分相等元素的处理决定区间端点归属，要和业务定义对齐
单调递增栈左右第一个更小元素柱状图最大矩形、容量水位的连续低谷分析需要在两端补哨兵，否则末尾区间算不出来
单调队列固定窗口极值滑窗最大 RT、最近 N 秒峰值 QPS必须按下标判断过期，只看值会留下窗外元素
环形缓冲加累加窗口求和与计数滑窗 QPS、错误率、令牌桶计数浮点累加会漂移，长期运行要定期重算
分桶直方图或 t-digest窗口分位数P99 延迟、SLO 计算分位数不可跨实例简单平均，要合并原始桶
 
package window

// MaxWindow 单调队列维护滑动窗口最大值：每个样本进出各一次，推进代价摊销常数。
// 典型用途是监控里的「最近 N 个采样点的最大响应时间」。
type MaxWindow struct {
	size int
	idx  []int   // 存下标而不是值，因为判断过期必须靠下标
	val  []int64
	n    int     // 已推入的样本总数，充当逻辑下标
}

func NewMaxWindow(size int) *MaxWindow {
	return &MaxWindow{size: size, idx: make([]int, 0, size), val: make([]int64, 0, size)}
}

func (w *MaxWindow) Push(v int64) int64 {
	// 从队尾弹出所有不大于新值的元素：它们不可能再成为最大值。
	// 这里用「小于」而不是「小于等于」，保留相等元素可以让过期判断更稳，
	// 代价是队列略长；若业务要求最左侧的最大值下标，必须用这个版本。
	for len(w.val) > 0 && w.val[len(w.val)-1] < v {
		w.val = w.val[:len(w.val)-1]
		w.idx = w.idx[:len(w.idx)-1]
	}
	w.val = append(w.val, v)
	w.idx = append(w.idx, w.n)
	// 队首过期判断：只看值永远发现不了窗外元素，必须比较下标
	for len(w.idx) > 0 && w.idx[0] <= w.n-w.size {
		w.idx = w.idx[1:]
		w.val = w.val[1:]
	}
	w.n++
	return w.val[0]
}

队列的三种语义：缓冲、削峰、解耦

「加个队列」这句话在设计评审里出现时，往往没人追问是要哪一种语义，而三者的成立条件完全不同。缓冲处理的是速率抖动，前提是长期平均消费速率高于平均生产速率；削峰处理的是有限时长的高峰，前提是峰值的总量有界，而且业务能接受延迟；解耦处理的是可用性与发布节奏，前提是下游不可用期间数据可以先攒着，且顺序与重复语义已明确。

最常见的误用是拿队列解决「消费能力长期不足」。队列救不了，它只把拒绝变成延迟：按 Little 定律排队长度等于到达率乘停留时间，产能不足时停留时间无上界增长，最后所有请求排到超时，既没成功也没快速失败，还占着上游的连接与线程。

语义成立前提失效时的表现必须配套的机制
缓冲，吸收抖动平均消费速率高于平均生产速率队列水位长期不回落水位与排队时间告警，容量按抖动幅度而非峰值定
削峰，摊平尖刺峰值总量有界且可容忍延迟请求在队列里排到超时，全部失败入队时带截止时间，出队先判是否已过期
解耦，隔离故障与发布下游恢复后能追上积压，语义已定义积压追不上，或重复消费引发脏数据幂等消费、积压追赶速率评估、死信通道
误用：掩盖产能不足不成立延迟无上界，最后全超时没有补救，必须扩容或降级限流

有界与无界：无界队列是把背压换成 OOM

这是整篇最该记住的一条：无界队列不是更安全，它只是把「拒绝请求」这个显式故障，换成了「内存耗尽」这个隐式故障。有界队列满时你有明确的决策点——阻塞生产者、丢弃最老的、丢弃最新的、或者返回错误；无界队列没有这个决策点，问题会一直积累，直到 OOM 把整个进程连带那些本来正常的请求一起干掉。

另一个被低估的代价是延迟失控：客户端超时是固定的，排队时间一旦超过它，消费者处理的每一条都是已经没人要的请求，系统进入活性很高但有效吞吐为零的状态。防这一手只要一件事：入队打截止时间，出队先判过期，过期直接丢并计数。

故障形态局部失败，可观测可降级OOM，进程级故障波及无关请求

关键监控指标排队时间分位数、拒绝率、水位只能看内存，发现即晚
容量怎么定按可接受的排队时间乘消费速率反推无法定

还要纠正一点：拿队列长度当健康指标是不够的。长度稳定可能是一直满的，长度为零可能是生产者早被拒了。真正对应用户体验的是排队时间分位数与拒绝率。

阻塞队列与线程池拒绝策略的配合

线程池的行为完全由队列决定，而顺序常被记反。正确顺序是：核心线程未满则新建核心线程，核心线程满了先入队，队列满了才扩到最大线程数，最大线程数也满了才触发拒绝策略。很多人以为是先把线程扩到最大再入队，于是配出「最大线程数永远用不上」的池子。

这就能解释 Java 的两个著名陷阱。Executors.newFixedThreadPool 的队列容量是整型最大值，队列几乎不可能满，于是最大线程数无效、拒绝策略永不触发，压力堆在队列里直到 OOM。newCachedThreadPool 用不存元素的同步移交队列加无上限最大线程数，压力大时线程爆炸。正确替代都是手写 ThreadPoolExecutor 并显式给出有界队列与拒绝策略。

队列类型核心与最大线程的实际行为拒绝策略何时触发主要风险
同步移交队列（不存元素）每个任务都要一个线程接手，最大线程数会被用满线程数达上限立即触发最大值设太大会线程爆炸
有界数组队列核心满入队，队列满扩到最大队列满且线程达上限容量与线程数要一起算，否则延迟不可控
无界链表队列最大线程数形同虚设几乎永不触发内存耗尽，故障范围是整个进程
优先级队列同有界队列，但出队顺序按优先级同上低优先级任务可能永久饿死，需加入队时间兜底
延迟队列任务到期才可被取出取决于容量实现到期时刻集中会造成脉冲式压力
拒绝策略行为背压效果适用与风险
抛异常直接失败由调用方决定重试最清晰，但必须真的处理异常并上报
调用方执行提交线程自己跑这个任务最强，天然限速会拖慢接收线程，网关类入口要谨慎
丢弃新任务静默丢掉当前任务无必须自己加计数，否则问题完全不可见
丢弃最老任务挤掉队首无适合只关心最新状态的场景，不能用于必达任务
自定义降级转投兜底队列或返回缓存结果取决于实现推荐，但要保证降级路径本身不依赖同一线程池
 
import java.util.concurrent.*;
import java.util.concurrent.atomic.AtomicLong;

public final class Pools {
    private static final AtomicLong REJECTED = new AtomicLong();

    /**
     * 不要用 Executors.newFixedThreadPool：它的队列容量是 Integer.MAX_VALUE，
     * 导致 maximumPoolSize 与拒绝策略永不生效，压力全堆在队列里直到 OOM。
     * 队列容量的定法：可接受的排队时间乘以稳定消费速率，而不是凭感觉给个 10000。
     */
    public static ThreadPoolExecutor build(String name, int core, int max, int queueCap) {
        ThreadFactory tf = r -> {
            Thread t = new Thread(r, name + "-" + System.nanoTime());
            t.setDaemon(false);          // 需要优雅关闭的池子不要用守护线程
            return t;
        };
        ThreadPoolExecutor ex = new ThreadPoolExecutor(
                core, max,
                60L, TimeUnit.SECONDS,
                new ArrayBlockingQueue<Runnable>(queueCap),   // 必须有界
                tf,
                (r, p) -> {                                   // 自定义拒绝：先计数再决定
                    REJECTED.incrementAndGet();
                    if (p.isShutdown()) {
                        throw new RejectedExecutionException(name + " already shutdown");
                    }
                    // 让提交线程自己执行，把背压顶回上游；入口网关请改成快速失败
                    r.run();
                });
        ex.allowCoreThreadTimeOut(false);
        return ex;
    }

    public static long rejected() { return REJECTED.get(); }

    /** 优雅关闭：先停收新任务，再等存量，最后强制中断。顺序错了会丢任务。 */
    public static void shutdown(ThreadPoolExecutor ex, long waitSec) throws InterruptedException {
        ex.shutdown();
        if (!ex.awaitTermination(waitSec, TimeUnit.SECONDS)) {
            ex.shutdownNow();
            ex.awaitTermination(waitSec, TimeUnit.SECONDS);
        }
    }
}

双端队列与工作窃取

双端队列让「本地快、窃取也快」同时成立。每个工作线程有自己的双端队列，自己从一端后进先出取（刚产生的子任务还在缓存里，局部性最好），空闲线程从另一端先进先出偷（偷最老的任务，粒度更大，一次能干更久）。Go 运行时的每 P 本地队列与 Java 的 ForkJoinPool 都是这个模式。

要注意三点：本地队列有容量上限（Go 每 P 本地队列是 256 个，满了把一半挪到全局队列）；窃取本身是原子操作，任务粒度过细时调度开销会盖过并行收益；任务之间不能阻塞式互相等待，否则工作线程被占满形成自死锁，这也是 ForkJoinPool 里不做阻塞 IO 的原因。

无锁队列：ABA 与内存序

无锁队列的价值是没有线程被挂起，因此不会出现「持锁线程被调度出去导致全体等待」的情况，尾延迟更可预测。但要先纠正一个普遍误解：无锁不等于更快。在争用激烈时，CAS 失败重试会让多个核心互相打断，缓存行在核间来回弹跳，吞吐可能低于一把简单的互斥锁；无锁的真正优势在低到中等争用、且要求延迟稳定的路径上。

实现层面有四个绕不开的问题。ABA：指针从 A 变到 B 又变回 A，CAS 察觉不到中间的变化，要用带版本号的标记指针或双字 CAS。内存序：必须先写好节点内容再发布指针，写侧用释放语义、读侧用获取语义，否则消费者会看到新指针配旧数据。内存回收：摘下的节点可能还有线程在读，需要 hazard pointer 或纪元回收。伪共享：头尾指针同缓存行会让生产者与消费者互相失效缓存。

问题症状解决手段注意
ABA极低概率的数据错乱，压测难复现版本号标记指针、双字 CAS、或改用索引而非指针Java 里用带戳的原子引用，Go 里优先改成基于索引的环形数组
内存序不足消费者读到未初始化完成的数据发布用释放语义，读取用获取语义不要依赖「先写后写不会重排」这种直觉
内存回收偶发野指针或崩溃hazard pointer、纪元回收，或托管语言交给 GC这是自己写无锁结构最大的隐性成本
伪共享核数增加吞吐反而下降头尾指针与计数器按缓存行填充填充会让结构变大，只对热字段做
高争用退化CPU 占满但吞吐下降退化为加锁、加退避、或按键分片减少争用先压测对比互斥锁版本，别默认无锁更快

进程内队列与消息中间件的分界

分界线很硬：进程内队列的数据在进程消失的那一刻就没了。它只能承担「丢了能接受或上游能重试补回」的工作：批量聚合、异步日志、本地限速、请求内并行。需要跨进程扩展、重启后继续、多方订阅或投递语义保证的场景，必须落到中间件。

最典型的错误是用本地队列做「异步保证」：塞进队列就返回成功，实例重启时数据静默丢失而调用方以为成功。正确形态是先落库或先写消息队列（本地消息表、事务消息），再异步消费。分区与顺序、投递语义、重平衡、积压治理等细节详见 后端 · 消息队列专栏。

}

// Pipe 用有界 channel 做进程内队列。channel 本身就是有界阻塞队列，
// 容量按「可接受排队时间乘以稳定消费速率」反推，不要凭感觉写 10000。
type Pipe struct {
	ch       chan Task
	Rejected uint64 // 拒绝必须计数，静默丢弃等于故障不可见
	Expired  uint64
}

func New(cap int) *Pipe { return &Pipe{ch: make(chan Task, cap)} }

// Submit 非阻塞投递：满了立刻失败，把背压顶回上游，而不是无限等待。
func (p *Pipe) Submit(t Task) error {
	select {
	case p.ch <- t:
		return nil
	default:
		p.Rejected++
		return ErrBusy
	}
}

// Run 消费循环：出队先判过期，避免把 CPU 与下游配额花在没人要的请求上。
func (p *Pipe) Run(ctx context.Context, handle func(Task)) {
	for {
		select {
		case <-ctx.Done():
			return // 关闭顺序：先停投递方，再让消费者把存量排空，最后退出
		case t := <-p.ch:
			if !t.Deadline.IsZero() && time.Now().After(t.Deadline) {
				p.Expired++
				continue
			}
			handle(t)
		}
	}
}
❌
最容易踩的坑

1. 对深度由外部数据决定的结构用递归——JVM 几千层就栈溢出，Go 表现为栈内存暴涨与扫栈变慢，必须改显式栈并设上限。

2. 单调队列只按值判断出队——过期判定必须用下标，否则窗外元素会一直留在队首。

3. 用单调队列算滑窗求和或分位数——求和是环形缓冲加累加的活，分位数要用分桶直方图或 t-digest。

4. 用队列掩盖长期产能不足——按 Little 定律停留时间会无上界增长，最终所有请求排到超时，比直接拒绝更糟。

5. 用无界队列「保证不丢」——它把可控的拒绝换成了不可控的 OOM，还让延迟失去上界。

6. 入队不打截止时间——积压时消费者处理的全是客户端已放弃的请求，CPU 和下游配额白烧。

7. 拿队列长度当健康指标——长度稳定可能是一直满的，真正有意义的是排队时间分位数与拒绝率。

8. 记反线程池顺序——正确顺序是核心线程、入队、扩到最大线程、拒绝策略；以为先扩线程会配出最大线程数永不生效的池子。

9. 用 Executors 的固定或缓存线程池——前者队列容量是整型最大值导致拒绝策略永不触发，后者线程数无上限会爆炸。

10. 在工作窃取线程池里做阻塞 IO——工作线程被占满后子任务无人执行，形成自死锁。

11. 默认无锁队列更快——高争用下 CAS 重试与缓存行弹跳会让它慢于互斥锁，先压测再选。

12. 用本地队列实现「异步成功」语义——实例重启即静默丢数据，需要保证就先落库或先写中间件。
