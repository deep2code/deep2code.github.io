贪心与回溯：可证明的近似与可控的穷举

🏷️ 算法,贪心,回溯

「每一步取局部最优，最后得到全局最优」——这句话不是解释，而是需要被证明的结论。绝大多数线上跑着的贪心规则既没有证明，也没有近似界，只有「上线后看着还行」。危险的地方在于贪心失效不会报错：它照样返回一个解，只是那个解可能比最优差很多，而且坏在哪里没人知道。这篇按三段组织：先给「上线前怎么验、上线时怎么兜」的标准动作，再展开证明手段与剪枝机制，最后收拢方法选择与在线搜索的工程要求。

💡
这篇怎么读
  • ① 用法：验证贪心的三个动手动作（小规模穷举找反例、与暴力解对比最坏比、与下界对比算差距）与一段可直接跑的否证脚本，外加一套带时间预算、可中断、中断后仍返回可用解的回溯骨架，以及必须随结果一起返回的质量字段。
  • ② 原理：交换论证与拟阵两种证明手段各能得出什么结论、业务里常见的伪贪心长什么样、近似比与启发式的本质区别、搜索空间怎么估、七种剪枝各自写错会怎样、手写回溯与求解器的分界。
  • ③ 场景：具体业务形态该用可证明贪心、近似算法、启发式、回溯还是求解器，以及在线路径上的降级与状态上报要求。

① 用法 · 上线前先否证贪心，上线时先设预算

面对一个「怎么分配、怎么排、怎么装」的需求，标准动作只有三个，加起来不到一小时，但能把「上线后看着还行」变成「知道最坏能差多少」。

动作一：先花十分钟否证，不要先证明。写一个小规模暴力枚举，随机生成几百组输入，把贪心和暴力的结果比一遍，记下最坏比和第一个反例。找到反例，需求讨论立刻结束；找不到反例，也只说明这批随机数据没打中它——没找到反例不等于证明了最优，接着做动作二。

动作二：给规则定性，分成三类。能用交换论证或拟阵证明最优的，可以放心用，但要把「依赖哪些约束」写进注释；有已证明最坏比的近似算法，可以把那个倍数写进容量规划；剩下的一律归为启发式，允许用，但必须能报告解的质量。三类都合法，混为一谈才是问题。

动作三：算一个下界，把「差多少」变成数字。装箱的下界是总体积除以箱容，调度的下界是「总工时除以机器数」与「最长单任务耗时」的较大者。有了下界，线上就能持续上报「当前解最多比最优差百分之几」，这是启发式能被允许进生产的前提。

"""上线前的十分钟：用小规模穷举否证贪心，再用下界把「差多少」变成数字。"""
import itertools
import random


def brute_makespan(tasks, m):
    """暴力枚举每个任务放哪台机器，返回最小的最大完工时间。
    只用于对照，规模必须小：复杂度是 m 的 n 次方，m 等于 3、n 等于 8 已经是六千多种。
    """
    best = sum(tasks)
    for assign in itertools.product(range(m), repeat=len(tasks)):
        load = [0] * m
        for t, a in zip(tasks, assign):
            load[a] += t
        best = min(best, max(load))
    return best


def greedy_makespan(tasks, m, sort_desc):
    """待验证的贪心：可选先按耗时降序，然后每个任务放到当前最空的机器。
    sort_desc 为 False 就是线上最常见的那种写法——按到达顺序放最空的机器。
    """
    load = [0] * m
    order = sorted(tasks, reverse=True) if sort_desc else list(tasks)
    for t in order:
        i = load.index(min(load))  # 「当前最空」这个规则本身没有最优性保证
        load[i] += t
    return max(load)


def falsify(m=3, n=6, trials=500, seed=1, sort_desc=True):
    """找反例：返回 (观测到的最坏比, 一个具体反例)。
    种子固定，反例必须能复现——不能复现的反例没法进回归测试。
    """
    rnd = random.Random(seed)
    worst, worst_case = 1.0, None
    for _ in range(trials):
        tasks = [rnd.randint(1, 20) for _ in range(n)]
        g = greedy_makespan(tasks, m, sort_desc)
        b = brute_makespan(tasks, m)
        if b and g / b > worst:
            worst, worst_case = g / b, tasks
    return worst, worst_case


def lower_bound(tasks, m):
    """下界：总量均摊向上取整，与最长单任务取较大者。
    启发式上线的前提是能回答「现在这个解最多比最优差多少」，靠的就是它。
    """
    if not tasks:
        return 0
    return max(-(-sum(tasks) // m), max(tasks))


if __name__ == "__main__":
    for desc in (False, True):
        ratio, case = falsify(sort_desc=desc)
        label = "先降序再放最空" if desc else "按到达顺序放最空"
        print(label, "观测最坏比", round(ratio, 3), "反例", case)
        if case:
            print("  下界", lower_bound(case, 3), "暴力最优", brute_makespan(case, 3))

确实需要精确解、决定写回溯的时候，在线服务里第一件事不是写剪枝，而是写预算与降级。下面这套骨架把「随时可中断、随时有解、返回值自带质量信息」固定下来，剪枝细节由具体问题实现：

package search

import (
	"context"
	"errors"
	"time"
)

// ErrInfeasible 必须与「超时未确定」区分开：前者提示调用方放松约束，后者只能重试或降级。
var ErrInfeasible = errors.New("infeasible: 连一个可行解都构造不出来")

// Result 随解一起返回质量信息，否则线上出问题时无法区分「算法差了」和「数据变了」。
type Result struct {
	Best     []int
	Value    int64
	LowerBnd int64
	Proved   bool // 是否证明了最优；预算耗尽就是 false
	Nodes    int64
	Elapsed  time.Duration
}

// GapPercent 当前解与下界的相对差距，用于上报与告警
func (r Result) GapPercent() float64 {
	if r.LowerBnd <= 0 {
		return 0
	}
	return float64(r.Value-r.LowerBnd) / float64(r.LowerBnd) * 100
}

type Problem interface {
	Depth() int                              // 决策层数
	Greedy() (sol []int, value int64, ok bool) // 先给可行解与初始上界，让上界剪枝一开始就生效
	LowerBound() int64                       // 下界，用于早停与质量上报
	Options(depth int, partial []int) []int  // 该层候选决策；实现里负责去掉等价分支
	Cost(partial []int) (cost int64, feasible bool) // 部分解的代价下界与可行性
}

func Solve(ctx context.Context, p Problem, budget time.Duration) (Result, error) {
	start := time.Now()
	ctx, cancel := context.WithTimeout(ctx, budget) // 预算比调用方超时留一点余量
	defer cancel()

	sol, val, ok := p.Greedy()
	if !ok {
		return Result{}, ErrInfeasible
	}
	res := Result{Best: sol, Value: val, LowerBnd: p.LowerBound(), Proved: true}
	partial := make([]int, 0, p.Depth())

	var dfs func(depth int)
	dfs = func(depth int) {
		if ctx.Err() != nil {
			res.Proved = false // 预算检查放在递归入口：放在循环末尾时一个深分支就能吃掉整个预算
			return
		}
		res.Nodes++
		cost, feasible := p.Cost(partial)
		if !feasible || cost >= res.Value {
			return // 上界剪枝用大于等于：等于当前最优的分支也没有展开价值
		}
		if depth == p.Depth() {
			res.Best, res.Value = append(res.Best[:0:0], partial...), cost
			return
		}
		for _, o := range p.Options(depth, partial) {
			partial = append(partial, o)
			dfs(depth + 1)
			partial = partial[:len(partial)-1]
			if res.Value == res.LowerBnd || !res.Proved {
				return // 已达下界，或预算已耗尽，继续搜索没有意义
			}
		}
	}
	dfs(0)

	res.Elapsed = time.Since(start)
	return res, nil // 即使 Proved 为 false 也返回解：质量可以降级，响应时间不能
}

按下表对照你手上的需求，决定该做哪些动作：

要做什么怎么做注意什么
手上有一个「看起来合理」的排序规则先写暴力枚举跑几百组随机对照，记下最坏比与反例找不到反例不等于最优，只说明这批数据没打中
需要向业务承诺解的质量只有可证明最优或有已证明最坏比的方法才能承诺启发式不能写进 SLA，只能上报实测差距
只能用经验规则（多目标、软约束）算下界并上报差距，把规则抽成可替换的策略接口没有下界就无法回答「现在差多少」，以后也换不动
规模小且必须拿最优解回溯，先跑贪心拿初始上界再进搜索动手前先估搜索空间量级，别指望剪枝救一切
在线接口里要做搜索用上面的预算骨架，返回是否降级、差距与耗时预算检查放递归入口；超时返回当前最好解而不是报错
约束多且经常变更交给整数规划或约束求解器，只描述约束与目标必须设求解时限，并区分最优、可行、无解、未确定四种状态
问题里有大量等价分支（同构机器、同规格库位）对称性消除，同一层只试一个代表等价性必须能证明，机器一有差异就会漏掉最优解
规模会随业务持续增长把求解抽成独立接口或服务，留替换空间调用方不应该知道背后是贪心、回溯还是求解器

在线搜索的这几个参数，每一个设错都会变成事故，逐条对一遍：

参数或约定作用怎么定设错的后果
时间预算搜索的硬上限比调用方超时留余量，给序列化与网络留时间请求悬挂，上游超时后本地还在烧 CPU
预算检查位置决定中断的粒度放在递归入口，每展开一个节点都检查放循环末尾时，一个深分支能吃掉整个预算
初始上界来源让上界剪枝立刻生效先跑一遍贪心，用它的解当上界从无穷大开始搜，前期几乎没有剪枝效果
上界比较符决定剪枝强度与正确性用大于等于，等于当前最优的分支无需展开写成严格小于会白跑，写反方向会剪掉最优解
下界早停与质量上报按问题结构给（均摊、最长单项、总量除容量）没有下界就无法早停也无法报告差距
返回字段让调用方知道能不能信这个解至少含是否证明最优、与下界差距、耗时、访问节点数只返回一个解时，线上变差无法定位原因
无解与未确定的区分决定业务怎么提示用户用两种不同的错误或状态码混成一种失败：该放松约束的去重试，该重试的去改单

怎么验证选对了：正确性上，回溯实现必须与暴力枚举在小规模上完全一致，尤其是加了对称性消除和约束传播之后——这两类剪枝写错时不抛异常，只会静默漏解；质量上，把「解值除以下界」这个比值持续上报，规则退化或数据分布变化会先在这个曲线上出现；性能上，压测输入要含最坏形态（大任务集中、约束互相冲突），均匀随机数据测不出剪枝失效；降级路径要专门测：把预算调到极小跑一遍，确认返回的是可用解并且标记了未证明最优。

这些动作背后的道理——为什么交换论证会断、为什么近似界值钱、为什么剪枝写错不报错——在下面几节。

② 原理 · 贪心不是思路，是一个待证明的命题

搞清这一节能解决一个组织层面的问题：评审时把「这个贪心为什么对」变成一个可回答的问题，而不是各凭直觉。

对待贪心的正确姿态是三分法：能证明最优的（可以放心用，并且知道哪些约束一变就失效）、能给出近似界的（不最优但知道最坏差多少，可以写进 SLA）、什么都没有的启发式（可以用，但必须能报告解的质量，并且允许被更好的方法替换）。三类都合法，混为一谈才是问题。

② 原理 · 两种证明手段：交换论证与拟阵

搞清这一节能提前回答一个总会到来的问题：业务下周要加一条约束，现在这个贪心还成不成立。

交换论证是最常用的一招：假设存在一个最优解与贪心解在某一步不同，把最优解里的那个选择换成贪心的选择，证明替换后解不会变差，于是可以逐步把最优解改造成贪心解。区间调度按「最早结束时间」排序之所以正确，就是因为把最优解里第一个结束更晚的区间换成结束最早的区间，剩余可用时间只会变多。注意这里的关键是换完之后必须仍然可行，这一步一旦不成立，整个证明就断了，而业务约束（切换成本、优先级、依赖）恰恰经常让它不成立。

拟阵是更结构化的判据：如果可行解的集合满足遗传性（子集仍可行）和交换性质，那么按权重从大到小的贪心一定得到最优解。Kruskal 能成立就是因为「森林」构成图拟阵。拟阵视角真正的价值不是证明本身，而是告诉你改约束时哪一条会破：加上「每类边至多选 k 条」通常仍可行（拟阵的截断），但加上「选了 A 就必须选 B」这种依赖约束，遗传性立刻不成立，贪心随之失效。

证明手段适用结构能得出什么结论失败信号
交换论证解是一个序列或一批选择贪心解与某个最优解等价替换后不可行，说明有隐藏约束没纳入
贪心始终领先解可按前缀比较每步的部分解都不差于最优解的对应前缀找不到可比较的量，通常是目标函数不可分解
拟阵性质可行解族满足遗传性与交换性质按权贪心即最优，且可推断改约束后是否仍成立存在依赖或互斥约束时遗传性被破坏
反例小规模穷举任何情况，用于否证只能证伪，但成本最低、最该先做穷举规模过大时无法覆盖，别当成证明
经典贪心贪心准则正确性来源加上什么约束就失效
区间调度最大化数量按结束时间最早交换论证区间带权重，改成带权区间调度后必须用 DP
最小延迟调度按截止时间最早交换论证任务间有依赖或存在切换成本
Huffman 编码每次合并两个最小频率交换论证加归纳要求码长上界或等长分组
最小生成树按边权升序且不成环图拟阵与割性质要求度数上界或必须包含指定边集
分数背包按单位价值降序可分割性加交换论证物品不可分割，即 0-1 背包，贪心立刻有反例
找零钱每次取最大面额仅对特定面额体系成立面额体系任意时反例极易构造，必须用 DP

② 原理 · 业务里的伪贪心：看着对，就是错

搞清这一节能让用法层的否证脚本更有针对性：知道反例通常藏在哪，就不必靠纯随机去碰。

最经典的反例是「按单位价值贪心装 0-1 背包」。容量 10，物品甲重 6 价值 12（单位价值 2），乙丙各重 5 价值 9（单位价值 1.8）。贪心先拿甲，剩余容量 4 装不下任何东西，总价值 12；最优是乙加丙，总价值 18。不可分割性一旦引入，单位价值贪心就失去依据，而业务里的物品几乎都不可分割：优惠券不能拆、机器不能半台、库位不能半格。这类问题的正解是把预算离散化后用 DP，见 动态规划的识别、状态设计与工程边界。

业务贪心规则看起来的理由反例形态正确做法
按单位收益挑选投放项性价比最高先上高性价比项占满预算，挤掉两个组合更优的项预算离散化后用分组背包 DP
把任务分给当前最空的机器负载看起来最均衡大任务最后到达，只能放到已有负载的机器上，最大完工时间被拉长先按耗时降序再分配，或用回溯加上界剪枝求最优
按截止时间最早排产先救最急的存在换型时间时，频繁切换导致整体产能下降把切换成本纳入目标，转成带约束的调度模型
缓存淘汰永远淘汰最久未用时间局部性一次全表扫描把热点全部冲走分段 LRU 或带频率的策略，详见 Redis 专栏
限流永远放行先到的请求公平大请求先到把配额吃光，小请求全部超时按代价计费的令牌桶，或按租户分桶
选择剩余容量最小且够用的库位减少碎片制造大量无法再利用的小碎片按规格分区，或定期整理，别指望在线贪心解决碎片

② 原理 · 近似比与启发式的差别，比听起来重要

搞清这一节能解释为什么用法层坚持要算下界：它是启发式唯一能拿出来的质量证据。

近似算法有被证明的最坏比：装箱问题的首次适应递减，用箱数不超过最优解的 11/9 倍加一个常数；集合覆盖的贪心是对数级近似，而且在合理假设下这个界不可能被显著改进；顶点覆盖取任意极大匹配的两端，一定不超过最优解的两倍。这些结论的价值是可以写进容量规划和 SLA：知道最坏情况下要多准备多少资源。

启发式没有界，它的质量只能靠实测。这不代表不能用——大量在线场景就是靠启发式撑着的——但必须补上两件事：一是与下界对比（装箱问题的下界是总体积除以箱容，调度问题的下界是总工时除以机器数与最长单任务耗时的较大者），有了下界就能报告「当前解最多比最优差百分之几」；二是可替换，把规则抽成策略接口，以后能换成求解器而不用改调用方。

方法是否有保证最坏情况如何报告解的质量
可证明最优贪心最优无不需要，但要记录约束假设
近似算法有最坏比按定理给出的倍数直接给出理论上界
启发式规则无可能任意差与问题下界对比，输出差距百分比
局部搜索或退火无依赖初始解与迭代次数记录迭代曲线与最好解出现时间
回溯加剪枝最优，前提是跑完指数时间中断时给出当前最好解与已探明下界
整数规划或约束求解最优或可行可能超时求解器直接给出最优性差距

下面是「可证明最优」那一类的标准形态，注意注释里写明了它依赖哪个前提——前提一变就要换方法：

package sched

import "sort"

type Interval struct {
	ID    string
	Start int64 // 统一用毫秒时间戳，避免时区与浮点问题
	End   int64
}

// MaxNonOverlapping 区间调度：选出最多的互不重叠区间。
// 贪心准则必须是「结束时间最早」，这是能用交换论证证明最优的唯一准则之一：
// 把任意最优解里第一个区间换成结束最早的区间，剩余可用时间只会变多。
// 反例提醒：按开始时间最早或按时长最短贪心都能构造出反例，别用。
// 注意本函数只在「所有区间等权」时最优；一旦区间带权重就必须改 DP。
func MaxNonOverlapping(in []Interval) []Interval {
	s := make([]Interval, len(in))
	copy(s, in)
	sort.Slice(s, func(i, j int) bool {
		if s[i].End != s[j].End {
			return s[i].End < s[j].End
		}
		return s[i].Start < s[j].Start // 保证结果稳定可复现
	})
	out := make([]Interval, 0, len(s))
	var lastEnd int64 = -1 << 62
	for _, iv := range s {
		if iv.Start >= lastEnd { // 左闭右开语义：前一个的 End 等于后一个的 Start 视为不冲突
			out = append(out, iv)
			lastEnd = iv.End
		}
	}
	return out
}

② 原理 · 回溯：先估搜索空间，再决定要不要写

搞清这一节能回答一个立项问题：这个回溯到底能不能在预算内跑完，还是必然要降级。

回溯就是在决策树上做 DFS，配合剪枝把不可能产生更优解的子树砍掉。写之前必须先做一件事：估算搜索空间的数量级。n 个任务分给 m 台机器是 m 的 n 次方，n 个元素的排列是 n 的阶乘。十个任务三台机器是五万九千种，可以穷举；二十个任务五台机器接近一万亿，纯枚举没戏，只能靠剪枝，而剪枝能砍掉多少完全取决于问题结构——这就是为什么回溯的性能无法事先承诺，也是为什么用法层的骨架一定要带预算。

剪枝手段实现成本效果写错时的后果
上界剪枝（当前解已不优于已知最优）低通常最显著比较符用错会把最优解剪掉，结果偏差且难发现
约束剪枝（剩余资源不可能满足）低显著估得过紧会漏解，估得过松等于没剪
对称性消除（等价分支只走一条）中阶乘级缩减等价性没证明就会漏掉唯一最优解
变量序启发（先选可选值最少的变量）中数独排班类问题效果巨大只影响速度不影响正确性，可放心试
约束传播（选定后立即缩减其他变量域）高把搜索变成推理为主传播规则写错会静默漏解，必须与朴素实现对照
状态去重（等价局面记忆化）中取决于重复率哈希键漏字段会把不同局面判为相同
先跑一个贪心得初始上界最低让上界剪枝一开始就生效无风险，应作为默认动作

把上面的剪枝落到具体问题上是这样的，它是用法层骨架的一个具体实现：

import time


def min_makespan(durations, machines, budget_ms=200):
    """把任务分配到若干台同构机器，最小化最大完工时间。
    返回 (最优或最好解, 是否已证明最优)。
    在线服务里调用搜索必须满足三件事：有时间预算、可中断、中断后仍给可用解。
    """
    tasks = sorted(durations, reverse=True)      # 大任务先放，能更早触发上界剪枝
    load = [0] * machines
    # 先用贪心拿一个初始上界：最长处理时间优先，本身也是常用启发式
    greedy = [0] * machines
    for d in tasks:
        i = greedy.index(min(greedy))
        greedy[i] += d
    best = [max(greedy)]
    # 下界：总量均摊与最长单任务取较大者，用于报告解的质量
    lower = max(sum(tasks) // machines + (1 if sum(tasks) % machines else 0), tasks[0] if tasks else 0)
    deadline = time.monotonic() + budget_ms / 1000
    proved = [True]

    def dfs(i):
        if time.monotonic() > deadline:
            proved[0] = False                    # 预算耗尽，放弃证明最优
            return
        if i == len(tasks):
            best[0] = min(best[0], max(load))
            return
        seen = set()
        for m in range(machines):
            if load[m] in seen:
                continue                         # 对称性消除：负载相同的机器彼此等价
            seen.add(load[m])
            if load[m] + tasks[i] >= best[0]:
                continue                         # 上界剪枝：注意是大于等于，等于也无需展开
            load[m] += tasks[i]
            dfs(i + 1)
            load[m] -= tasks[i]
            if best[0] == lower or not proved[0]:
                return                           # 已达下界或已超时，立即收敛
    dfs(0)
    return best[0], proved[0] and best[0] >= lower

② 原理 · 手写回溯与求解器的分界

搞清这一节能避免一种慢性成本：每次业务加一条约束，就要重新设计剪枝并重新验证正确性。

判断标准不是问题难不难，而是约束是否复杂且会变。手写回溯的剪枝是和约束耦合在一起的：业务加一条「同一租户的任务不能排在同一台机器」，就得重新设计剪枝并重新验证正确性，而漏解这种 bug 不会抛异常，只会让结果悄悄变差。现代求解器把这件事反过来做：你只描述约束和目标，剪枝由求解器负责。SAT 求解器的冲突驱动学习、约束求解器的传播与割平面，效果远超手写的几条剪枝规则。

用求解器时有两个必须掌握的工程细节。第一，一定要设求解时限，否则它会一直找更优解。第二，必须区分求解状态：得到最优解、得到可行解但未证明最优、证明了无解、以及在时限内什么都没确定——最后两种的业务处理完全不同，「无解」要提示用户放松约束，「未确定」只能降级并重试。把这两种混成一个「失败」返回，是接入求解器最常见的错误。

问题形态手写回溯求解器判断依据
约束少且固定，规模小合适不必引入不想加依赖，剪枝也就两三条
约束多且经常变更不合适合适每次改约束都要重验剪枝正确性，成本不可控
目标含多项加权或软约束不合适合适软约束用惩罚项表达是求解器的标准用法
只需判定可行性可行更强可满足性问题上求解器的冲突学习优势明显
要求毫秒级在线响应看剪枝效果需要预热与时限两者都必须带时间预算与降级
规模随业务持续增长会越来越差可换更强求解器把求解抽成独立服务和接口，留出替换空间

③ 场景 · 在线服务里做搜索：时间预算是硬约束

把搜索放进在线请求路径，性质就变了：结果的质量可以降级，响应时间不能。必须实现的是一套「随时可中断、随时有解」的机制——进入递归先检查预算、先用贪心拿一个可用解、搜索过程中不断刷新最好解、预算耗尽立刻返回并标记为未证明最优。返回体里要带上解的质量信息（与下界的差距、是否降级、求解耗时），否则线上出问题时无法判断是算法差了还是数据变了。

场景该怎么做为什么代价
会议室或资源档期排满，所有预约等权按结束时间最早的贪心，可证明最优交换论证成立，实现只有十几行一旦预约带权重（VIP、时长收益）证明失效，必须改 DP
把一批任务分给若干同构机器，要压最大完工时间先按耗时降序的启发式，再用带预算的回溯在余量内改进降序启发式质量明显好于按到达顺序，且有下界可报不保证最优；机器异构后对称性消除立刻失效
订单装箱、集装与库位分配首次适应递减这类有近似界的算法最坏比已被证明，可直接写进容量规划近似不是最优，紧张场景要额外留余量
多目标流量分配（转化率、成本、稳定性）归为启发式，算下界并持续上报差距，规则做成可替换策略多目标加权没有最优性概念，只能实测要维护评估链路；权重调整会让历史对比失效
排班、带租户隔离的资源编排约束求解器，设时限并区分四种求解状态约束多且经常变，手写剪枝的维护成本不可控多一个依赖与预热成本；只能接受可行解
在线接口必须毫秒级返回一个方案用带预算的骨架：贪心兜底、随时可中断、返回质量字段质量可降级，响应时间不能要额外实现并测试降级路径，返回协议变复杂
离线批量算最优（对账、月度规划）放宽预算跑完整回溯或求解器，结果落库并留证据没有在线预算约束，可以追求真正最优耗时按分钟甚至小时计；要保证可复现，输入与版本都要留档
用户提交的约束互相冲突明确返回「无解」并指出冲突约束，而不是返回一个凑出来的解无解与超时是两种不同事实，处理方式完全不同要做冲突定位（松弛哪条约束可行），实现成本不低

不适用边界：状态能压下来、且满足最优子结构与无后效性的问题不要用搜索，用 DP，见 动态规划的识别、状态设计与工程边界；路径与依赖类搜索的图表示、拓扑序与环检测在 图算法在后端系统中的落地形态；搜索里要反复取极值、判连通、做等价类合并时的结构选择在 树形结构的工程选型；「m 的 n 次方」「n 的阶乘」这类量级估算与摊销分析在 复杂度分析；排序在贪心里是前置动作，稳定性与自定义比较的坑在 排序算法；超时预算怎么一路传下去、搜索放进后台任务时的生命周期管理在 Go 并发原语与常见并发 bug；离线求解服务的部署与资源隔离在 Kubernetes 专栏。

这是这条路径的最后一步。回头看整条线：复杂度给了度量尺，数组与链表、栈与队列、树、图给了数据的组织方式，动态规划给了决策的组织方式，而本篇处理的是「组织不下来」之后的两条退路——用可证明的贪心换速度，用可控的穷举换最优，并且无论选哪条都要能说出自己离最优有多远。

最容易踩的坑

❌
避坑清单
  • 把「局部最优导致全局最优」当解释而不是待证明命题：线上大量贪心既无证明也无近似界，失效时不报错只是结果变差。
  • 上线前不做小规模穷举对照：十分钟的暴力枚举能否掉一半的规则，比事后看监控便宜得多。
  • 把「没找到反例」当成证明：随机数据没打中而已，要么补证明，要么按启发式对待并上报质量。
  • 用单位价值贪心解 0-1 背包：容量 10、物品重 6 价值 12 与两个重 5 价值 9 就是反例，贪心得 12，最优是 18。
  • 区间调度按开始时间或最短时长贪心：只有按最早结束时间能用交换论证证明，其余都有反例。
  • 区间带上权重后继续用贪心：带权区间调度必须用 DP，等权的证明在带权时直接失效。
  • 把任务分给当前最空的机器就认为负载均衡：大任务最后到达时最大完工时间被拉长，应先按耗时降序。
  • 把近似算法和启发式混为一谈：前者有被证明的最坏比可以写进容量规划，后者可能任意差。
  • 启发式不与下界对比：没有下界就无法回答「现在这个解到底差多少」，出问题时无从判断。
  • 写回溯前不估搜索空间：二十个任务五台机器接近一万亿分支，是否可行取决于剪枝而不是代码质量。
  • 不先跑贪心就进搜索：初始上界是无穷大时前期几乎没有剪枝效果，这是最便宜的优化却最常被漏掉。
  • 上界剪枝的比较符写成严格小于：等于当前最优的分支也无需展开，写反则要么白跑要么剪掉最优解。
  • 对称性消除没有证明等价：空机器互换是安全的，一旦机器有差异（规格、租户绑定）就会漏掉最优解。
  • 时间预算检查放在循环末尾：必须放在递归入口，否则一个深分支就能吃掉整个预算。
  • 超时了返回错误而不是当前最好解：在线路径上质量可以降级、响应不能，但必须明确标记为未证明最优。
  • 把求解器的「证明无解」和「超时未确定」当成同一种失败：前者要提示放松约束，后者只能降级重试，处理方式完全不同。
