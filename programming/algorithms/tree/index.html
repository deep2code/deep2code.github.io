树形结构的工程选型：从二叉搜索树到 B+ 树

🏷️ 算法,树,二叉树

后端工程师真正需要判断的不是「二叉树怎么遍历」，而是：当我把一份数据组织成树，我付出了什么代价，换回了什么保证。树的共同承诺只有一条——把一次查找从「扫描 n 个元素」变成「沿着 h 层下降」。所有分歧都出在后面：h 的上界靠什么维持、维持它需要多少次写操作、一层下降的成本是一次指针解引用还是一次磁盘随机读、范围扫描要不要回到根。这篇按三段组织：先给工程里遇到这类需求时的标准动作，再把每一族结构的机制展开，最后收拢成可执行的选型判断。

💡
这篇怎么读
  • ① 用法：把需求翻译成访问形态之后该用哪个现成结构，一张「要做什么 → 用什么 → 注意什么」对照表，堆做延时队列、并查集、前缀树三段可直接抄的最小实现，以及「怎么估规模、怎么验证选对了、什么时候该把活交给数据库索引」。

  • ③ 场景：具体场景下选哪个结构、代价是什么，以及什么时候不该自己维护结构而应该换索引、换存储或换专门的中间件。

① 用法 · 四类访问形态的标准动作与最小实现

遇到「这份数据用什么结构装」的时候，按三步走，能省掉九成纠结。

第一步：把需求翻译成访问形态，而不是翻译成结构名。只问一句「查询是怎么发起的」，答案只有五类：按键精确取一条（点查）、按区间或按序取一批（范围）、按开头匹配（前缀与多模式）、只要最小或最大的那几个（极值与 Top-K）、只问两个元素是否同组（连通性）。形态定了，结构基本就定了，剩下的只是规模问题。

第二步：先判断这活该不该自己干。绝大多数「要按范围查」最终应该落成数据库的一条联合索引，而不是一棵自研树。三个判据只要有一个成立就交给数据库：数据要持久化、要跨进程或跨实例共享、按真实规模估出来的内存放不进单机。估法很粗但够用——元素数乘以「单元素字节数加上结构的每元素额外开销」，指针结构的额外开销是每个节点两三个指针加对象头，map 套小对象的实际占用往往是裸数据的数倍。只有当这份数据是进程内派生的、可以随时重建、且规模确定时，自己维护结构才是划算的。

第三步：按下表挑结构，然后立刻做三件验证——写一个朴素实现（线性扫描或排序数组）做对照测试、按真实规模算一遍内存、压测只看 p99 不看均值。三件都做完再合并代码，否则你只是把一个没验证的假设放进了生产。

要做什么用什么注意什么
按 ID 精确取一条，不需要任何顺序哈希表（Go 的 map、Python 的 dict）别上树。「为了快用了 TreeMap」而访问全是精确取值，是最常见的过度设计
按范围或按时间区间取一批，数据要持久化数据库索引（B+ 树），按查询写联合索引用 EXPLAIN 确认真的走了索引且不是全索引扫描，细节见 MySQL 专栏
进程内要保持有序、且要范围遍历只读时用排序数组加二分；要并发写用跳表排序数组在只读场景全面优于任何平衡树，先排除掉它再考虑指针结构
按前缀匹配（路由、补全、IP 段）Radix 树或 map 子节点的 TrieTrie 的子节点用哈希或小数组，不要按码点开定长数组
一遍扫描同时命中多个模式（敏感词、关键词打标）AC 自动机，离线构建后原子替换输入归一化必须前置，否则全角、繁简、零宽字符直接绕过
要访问量最大的 K 个容量为 K 的小顶堆方向别搞反：小顶堆的堆顶是候选里最小的，新元素大于堆顶才替换
最近到期的先处理（延时任务、超时管理）进程内用堆加一个 timer；十万级连接超时用时间轮跨进程或要重启恢复就别用进程内结构，改 Redis zset 或数据库表加轮询
判断两个 ID 是否同组（账号合并、团伙、影响域）并查集需要撤销合并就不能用路径压缩，这个取舍要在实现前定

下面三段是上表里最常自己写的三个结构的最小可用形态，注释只说明为什么这么写，机制解释见原理层。

package pick

import (
	"container/heap"
	"time"
)

// ---- 形态一：最近到期的先出来 —— 用堆，而且只用一个外部 timer ----

type job struct {
	Key      string
	Deadline time.Time // 用绝对时间：相对时间在 GC 暂停或调度延迟之后会漂移
}

type jobHeap []job

func (h jobHeap) Len() int           { return len(h) }
func (h jobHeap) Less(i, j int) bool { return h[i].Deadline.Before(h[j].Deadline) }
func (h jobHeap) Swap(i, j int)      { h[i], h[j] = h[j], h[i] }
func (h *jobHeap) Push(x any)        { *h = append(*h, x.(job)) }
func (h *jobHeap) Pop() any          { o := *h; n := len(o); it := o[n-1]; *h = o[:n-1]; return it }

// DueJobs 弹出所有已到期任务，并返回「下次该睡多久」。
// 调用方只需要一个 time.Timer 等这个返回值：n 个任务开 n 个 timer 是最常见的写法错误。
func DueJobs(h *jobHeap, now time.Time) ([]job, time.Duration) {
	var due []job
	for h.Len() > 0 && !(*h)[0].Deadline.After(now) {
		due = append(due, heap.Pop(h).(job))
	}
	if h.Len() == 0 {
		return due, time.Hour // 空堆时给一个长等待，避免空转唤醒
	}
	return due, (*h)[0].Deadline.Sub(now)
}

// ---- 形态二：这两个 ID 是不是同一组 —— 并查集，别用 map 套 set 反复合并 ----

type DSU struct{ parent, size []int32 }

func NewDSU(n int) *DSU {
	d := &DSU{parent: make([]int32, n), size: make([]int32, n)}
	for i := range d.parent {
		d.parent[i], d.size[i] = int32(i), 1 // 业务 ID 先映射成 0 到 n-1 的连续下标
	}
	return d
}

func (d *DSU) Find(x int) int {
	r := int32(x)
	for d.parent[r] != r {
		d.parent[r] = d.parent[d.parent[r]] // 路径减半：顺手压缩，不需要第二遍遍历
		r = d.parent[r]
	}
	return int(r)
}

// Union 返回是否真的发生了合并，调用方据此维护分量数
func (d *DSU) Union(a, b int) bool {
	ra, rb := int32(d.Find(a)), int32(d.Find(b))
	if ra == rb {
		return false
	}
	if d.size[ra] < d.size[rb] {
		ra, rb = rb, ra // 小树挂大树，避免树高失控
	}
	d.parent[rb] = ra
	d.size[ra] += d.size[rb]
	return true
}

// ---- 形态三：按前缀查 —— Trie 用 map 存子节点 ----

type Trie struct {
	children map[rune]*Trie
	word     string // 非空表示这里终止了一个完整词
}

func NewTrie() *Trie { return &Trie{children: map[rune]*Trie{}} }

func (t *Trie) Insert(w string) {
	cur := t
	for _, ch := range w { // 按 rune 迭代：按 byte 会把一个汉字拆成三层节点
		nxt, ok := cur.children[ch]
		if !ok {
			nxt = NewTrie()
			cur.children[ch] = nxt
		}
		cur = nxt
	}
	cur.word = w
}

// HasPrefix 只回答「存不存在以 p 开头的词」。
// 要把所有补全结果列出来是另一件事：那要遍历子树，代价与结果数成正比，必须限条数。
func (t *Trie) HasPrefix(p string) bool {
	cur := t
	for _, ch := range p {
		nxt, ok := cur.children[ch]
		if !ok {
			return false
		}
		cur = nxt
	}
	return true
}

怎么验证选对了：正确性靠对照测试，同一批操作分别喂给新结构和朴素实现（线性扫描、全量排序），三类输入各跑一遍——随机、完全有序、大量重复值，有序输入是暴露退化的关键；内存靠算而不是靠感觉，按真实条数乘单元素开销估一遍，指针结构记得算上每节点的指针与对象头；性能只看 p99 与最坏，均值会把结构退化和 GC 抖动全部抹平，而且基线必须是「排序数组加二分」或「直接线性扫描」，跑不赢基线就不要引入复杂结构；线上要把结构的元素数、深度或层数、命中率暴露成指标，离线构建的结构（AC 自动机、双数组 Trie）还要带版本号，切换用双缓冲换指针而不是原地改。

上面这些动作为什么长这样——为什么有序输入危险、为什么数据库统一选 B+ 树、为什么中文 Trie 会内存失控、为什么路径压缩不可撤销——全部在下面几节。

② 原理 · 树不是一种结构，而是一族工程折中

搞清这一节能解决一个具体问题：面对一个新需求时，知道候选结构总共只有这么几族，不会在「用 AVL 还是红黑树」这种细节上卡住而漏掉更合适的一族。

把四个问题当坐标轴，树会自然分成四族：内存里维护有序性的平衡树、按页组织的 B 族与 LSM 族、沿字符下降的前缀结构、只维护偏序或连通性的堆与并查集。它们不是替代关系，一个中等规模的服务往往同时跑着这四族。

② 原理 · BST 退化的真实代价与两种平衡口味

搞清这一节能解释两个现象：为什么标准库里找不到裸 BST，以及为什么「红黑树插入更快」这句流传很广的话会让你在删除密集的场景上做错选择。

未平衡的 BST 会退化成链表，工程上危险的地方在于触发条件恰好是最常见的输入形态：自增主键、按时间插入的事件、按字典序导入的词表，全都是有序输入，全都把 BST 变成一条右斜链。BST 的最坏情况不是运气不好，而是生产环境的默认情况——这也是标准库里找不到裸 BST 的原因。

关于 AVL 和红黑树，流传最广的说法是「红黑树插入删除最多 3 次旋转，AVL 要旋转很多次」。这个说法一半对一半错，值得掰开看：插入时两者都是常数次旋转（AVL 最多一次单旋或一次双旋，红黑树最多两次旋转），真正的差别在两处——一是红黑树插入可能需要沿路径向上重新染色，次数是 O(log n) 但染色只是改一个 bit，比旋转便宜得多；二是删除，AVL 删除后可能需要一路回溯做 O(log n) 次旋转，红黑树删除的旋转次数有常数上界。所以准确的判断是：写多删多选红黑树，读多写少且想压低树高选 AVL。

另一个被反复抄错的结论是「Redis 有序集合底层是红黑树」。不是。zset 用的是跳表加哈希表的双结构（小集合时是 listpack 紧凑编码），跳表每层提升概率 1/4、最大层数 32。选它的理由很实际：范围查询顺着最底层链表走，改动影响的节点局部化，做并发和持久化都更容易。

还有个容易忽略的事实：数据只读时，任何平衡树都不如排好序的连续数组，缓存命中与内存占用都全面更优。这正是用法层把「排序数组加二分」放在候选第一位的原因。

② 原理 · 从内存走向磁盘：扇出决定一切

搞清这一节能回答两个线上问题：为什么亿级表的点查只要几次 IO，以及为什么把主键换成 UUID 之后索引体积和响应时间会一起变差。

二叉结构在磁盘上的致命问题不是复杂度，而是一层下降等于一次随机 IO。红黑树存一亿条数据树高约 30 层，最坏就是 30 次随机读；B+ 树把节点做成一页（InnoDB 默认 16KB），一个内部页放上千个「键加子页号」，三层就能覆盖亿级行，而且上面两层几乎必然常驻内存。

B 树与 B+ 树的分工也常被混淆：B 树的内部节点也携带数据，B+ 树的数据只在叶子且叶子间有双向链表。后果是 B+ 树内部页只存键、扇出更大树更矮，范围与全索引扫描可沿叶子链表推进而不必回父节点；B 树只在恰好命中靠上层热点键时更早返回。OLTP 的形态是点查加范围扫描，不是赌命中根附近。

② 原理 · LSM 树：把随机写换成顺序写之后的账单

搞清这一节能解释一个经常被当成 bug 上报的现象：删了一大批数据，磁盘水位却一点没降。

B+ 树的写是就地更新：改一行要把所在页标脏并最终整页刷盘，「改 20 字节写 16KB」是常态。LSM 树拒绝就地更新：写先进内存表（通常是跳表），写满后整块顺序落盘成不可变文件，后台再压实合并，写路径只剩 WAL 追加加内存插入，随机写被转成顺序写。

代价写在三张账单上。读放大：一个键可能同时存在于内存表、L0 的多个重叠文件和每层各一个文件，点查最坏要看多个文件，靠布隆过滤器挡掉「肯定不存在」。写放大：每条数据会被压实反复重写，分层策略下总写入量是原始写入的十几倍量级。空间放大：删除只写墓碑，空间要等压实才释放，所以「删了一批数据磁盘没降」是正常现象而非 bug。

所以选型不是「LSM 更现代」，而是看写入是否真的以随机小更新为主：日志与时序这类写多读少的负载选 LSM，账务库存这类要求稳定尾延迟的负载，B+ 树的可预测性更值钱。

② 原理 · 前缀树：路由匹配与敏感词过滤的内存账

搞清这一节能解决两类事故：中文词表把 Trie 的内存打爆，以及敏感词换了更快的结构却依然被轻松绕过。

前缀结构的价值是把「和 n 个模式逐一比较」变成「按输入长度一次下降」，复杂度与模式数量无关。后端有两个刚需场景：HTTP 路由匹配（路径段前缀共享，还要支持通配与参数捕获），以及敏感词、黑名单、关键词打标这类多模式匹配。

但教科书式 Trie 在中文场景会内存失控：每个节点用定长子节点数组、按 Unicode 码点开槽，等于每节点上万个空槽。三条出路——哈希表或有序小数组存子节点（省内存，每层多一次哈希或二分）、把单孩子链路压缩成一条边（Radix 树，httprouter 一类路由库就这么做）、构建期压成两个整型数组（双数组 Trie，最快最紧凑，代价是几乎不能增量更新）。

方案单次查询内存特征增量更新适合的场景
定长数组 Trie按输入长度，常数最小中文场景浪费严重容易字符集很小，例如纯数字或小写字母
哈希子节点 Trie每层一次哈希与实际边数成正比容易词表频繁变动的业务黑名单
Radix 压缩树按输入长度，比较次数更少节点数大幅下降需要分裂边，实现稍复杂HTTP 路由、IP 前缀匹配
双数组 Trie最快，两次数组访问一层最紧凑几乎不支持，需整体重建词库固定的分词与词典
AC 自动机一遍扫描定位所有命中Trie 加每节点一个失配指针失配指针需重建敏感词、关键词打标、日志规则

关键取舍是更新频率：按天更新就用构建期压缩的结构加原子替换实例（双缓冲切指针，不要在线改）；随运营实时变就退一步用哈希子节点版本。另外真实的绕过几乎都发生在匹配之前——全角半角、繁简、零宽字符与插空，归一化不前置，换什么结构都白搭。下面是最小可用的 AC 自动机：

from collections import deque


class ACAutomaton:
    """多模式匹配：构建一次，扫描一遍拿到全部命中。
    典型用法是每天离线构建，然后原子替换线上实例（双缓冲），
    不要在请求线程里边查边改词表。
    """

    def __init__(self, words):
        # goto 用 dict 而不是定长数组：中文码点空间太大，定长数组会把内存打爆
        self.goto = [{}]
        self.fail = [0]
        self.out = [[]]          # 该状态匹配结束的词，支持一个位置命中多词
        for w in words:
            self._insert(w)
        self._build_fail()

    def _new_state(self):
        self.goto.append({})
        self.fail.append(0)
        self.out.append([])
        return len(self.goto) - 1

    def _insert(self, word):
        cur = 0
        for ch in word:
            nxt = self.goto[cur].get(ch)
            if nxt is None:
                nxt = self._new_state()
                self.goto[cur][ch] = nxt
            cur = nxt
        self.out[cur].append(word)

    def _build_fail(self):
        # BFS 逐层构建失配指针：失配后跳到「最长的、同时是某模式前缀的后缀」
        q = deque()
        for ch, s in self.goto[0].items():
            self.fail[s] = 0
            q.append(s)
        while q:
            r = q.popleft()
            for ch, s in self.goto[r].items():
                f = self.fail[r]
                while f and ch not in self.goto[f]:
                    f = self.fail[f]
                self.fail[s] = self.goto[f].get(ch, 0)
                # 把失配链上的输出合并过来，避免查询时再沿 fail 链回溯
                self.out[s].extend(self.out[self.fail[s]])
                q.append(s)

    def find(self, text):
        """返回 (结束下标, 命中词) 列表；时间与文本长度加命中数成正比"""
        hits, cur = [], 0
        for i, ch in enumerate(text):
            while cur and ch not in self.goto[cur]:
                cur = self.fail[cur]
            cur = self.goto[cur].get(ch, 0)
            for w in self.out[cur]:
                hits.append((i, w))
        return hits


if __name__ == "__main__":
    ac = ACAutomaton(["内部资料", "资料外泄", "外泄"])
    print(ac.find("这份内部资料外泄了"))

② 原理 · 堆：延时队列、限流窗口与 Top-K

搞清这一节能避免两个高频错误：Top-K 的堆方向选反，以及为几万个延时任务开了几万个定时器。

堆只维护偏序：父节点不大于子节点，兄弟之间没有任何关系。定位因此很清楚——只关心极值、不关心整体有序时用堆。它是数组式完全二叉树，没有指针开销，缓存局部性远好于指针树。

最常写错的是 Top-K 的堆方向。求「访问量最大的 K 个接口」要用容量为 K 的小顶堆：堆顶是候选里最小的那个，新元素大于堆顶就替换并下沉。反过来用大顶堆装全部 n 个再弹 K 次，空间 O(n)，流式场景根本放不下。另一个易错点是以为堆永远最优——K 接近 n 或数据能一次性放内存时，直接排序或快速选择更快，排序本身的取舍见 排序算法。

定时任务是堆的另一个主战场，但堆不总是赢。堆定时器插入删除 O(log n)、取最近到期 O(1)；分层时间轮插入删除 O(1)，代价是精度受 tick 限制并需要分层进位。连接超时、心跳这类「数量巨大、精度要求不高、多数任务到期前会被取消」的场景，时间轮更合适（Netty 与 Kafka 都这么选）；任务少而延时跨度大的业务任务，堆更简单。

结构插入取最近到期按键取消精度适用规模与场景
二叉堆O(log n)O(1) 查看需辅助索引表才能 O(log n)无损，精确到时间戳万级以内、跨度大的业务任务
四叉或 d 叉堆O(log n) 但树更矮O(1)同上无损上浮多于下沉时更友好
分层时间轮O(1)O(1) 推进O(1)，持有槽位引用即可受 tick 限制十万级连接超时与心跳
Redis zset 当延时队列O(log n)按分值范围取O(log n)取决于轮询间隔跨进程共享、需重启恢复
数据库表加索引轮询一次写入一条范围查询一条更新取决于轮询间隔量小、需可审计可干预

用法层给的是最小骨架，下面是带按键取消与幂等重排的完整版本，重点仍在三处注释：用绝对时间、只为堆顶保留一个系统定时器、用索引表支持按键取消。

package delayq

import (
	"container/heap"
	"sync"
	"time"
)

type Task struct {
	Key      string
	Deadline time.Time // 用绝对时间：相对时间在阻塞或 GC 暂停后会漂移
	index    int       // 在堆数组中的下标，使 Remove 能 O(log n) 完成
}

type taskHeap []*Task

func (h taskHeap) Len() int            { return len(h) }
func (h taskHeap) Less(i, j int) bool  { return h[i].Deadline.Before(h[j].Deadline) }
func (h taskHeap) Swap(i, j int)       { h[i], h[j] = h[j], h[i]; h[i].index, h[j].index = i, j }
func (h *taskHeap) Push(x any)         { t := x.(*Task); t.index = len(*h); *h = append(*h, t) }
func (h *taskHeap) Pop() any {
	old := *h
	n := len(old)
	t := old[n-1]
	old[n-1] = nil // 置空，否则底层数组仍持有指针，任务对象无法被回收
	*h = old[:n-1]
	return t
}

type Queue struct {
	mu    sync.Mutex
	h     taskHeap
	idx   map[string]*Task
	timer *time.Timer // 全局只有一个定时器，指向当前堆顶；n 个任务不要开 n 个 timer
	Ready chan *Task
}

func New(buf int) *Queue {
	q := &Queue{idx: map[string]*Task{}, Ready: make(chan *Task, buf)}
	q.timer = time.NewTimer(time.Hour)
	go q.loop()
	return q
}

func (q *Queue) Add(key string, d time.Duration) {
	q.mu.Lock()
	defer q.mu.Unlock()
	if old, ok := q.idx[key]; ok { // 幂等：同一 key 重复投递视为重排期限
		heap.Remove(&q.h, old.index)
	}
	t := &Task{Key: key, Deadline: time.Now().Add(d)}
	heap.Push(&q.h, t)
	q.idx[key] = t
	if q.h[0] == t { // 只有堆顶变化时才需要重置定时器
		q.timer.Reset(d)
	}
}

func (q *Queue) Cancel(key string) bool {
	q.mu.Lock()
	defer q.mu.Unlock()
	t, ok := q.idx[key]
	if !ok {
		return false
	}
	heap.Remove(&q.h, t.index)
	delete(q.idx, key)
	return true
}

func (q *Queue) loop() {
	for range q.timer.C {
		q.mu.Lock()
		now := time.Now()
		for len(q.h) > 0 && !q.h[0].Deadline.After(now) {
			t := heap.Pop(&q.h).(*Task)
			delete(q.idx, t.Key)
			select {
			case q.Ready <- t:
			default: // 下游堆积时丢弃或转投兜底队列，绝不在持锁时阻塞
			}
		}
		next := time.Hour
		if len(q.h) > 0 {
			next = time.Until(q.h[0].Deadline)
		}
		q.timer.Reset(next)
		q.mu.Unlock()
	}
}

② 原理 · 并查集：路径压缩买到了什么

搞清这一节能避免一个改起来等于重写的决策失误：在需要撤销合并的场景里用了带路径压缩的实现。

并查集在后端出现得比想象中多：账号合并与设备指纹聚类、风控团伙识别、灰度分组的等价类合并、增量构建里的变更影响域划分。它只回答一个问题——两个元素是否同组——但回答得极快。

两种优化作用不同：按秩合并控制树高不失控，路径压缩把查询路径上的节点直接挂到根。单用任何一种都是 O(log n) 量级，两种同时用才降到反阿克曼函数级别，现实规模下可当常数看。一个常被忽略的细节：压缩之后 rank 数组不再是真实树高，只是打破平衡用的上界估计，所以叫 rank 不叫 height。

真正会咬人的边界是：带路径压缩的并查集不支持删除也不支持回滚。要在回溯中撤销合并（离线动态连通性、带撤销的图算法），必须放弃压缩、只按秩合并，并把每次改了哪个父指针记进操作栈，撤销时逐条还原，复杂度回到 O(log n)。这个取舍要在实现前定，改起来是重写。回溯本身的预算与中断设计见 贪心与回溯。

优化组合单次操作复杂度能否撤销适用场景
都不用最坏 O(n)可以只有教学价值
仅路径压缩摊销 O(log n) 量级不能一次性离线聚类
仅按秩合并O(log n)可以需要回滚的搜索过程
路径压缩加按秩合并近似常数不能绝大多数在线聚合与连通性判断
加权并查集（带偏移量）近似常数不能需要维护元素间相对关系，例如汇率或差分约束
 
package dsu

// DSU 路径压缩加按大小合并。用于账号合并、团伙聚类这类「只问是否同组」的场景。
// 注意：压缩后 size 不再代表树高，只是打破平衡用的权重。
type DSU struct {
	parent []int32
	size   []int32
	groups int // 当前连通分量数，合并成功时递减
}

func New(n int) *DSU {
	d := &DSU{parent: make([]int32, n), size: make([]int32, n), groups: n}
	for i := range d.parent {
		d.parent[i] = int32(i)
		d.size[i] = 1
	}
	return d
}

// Find 迭代实现：n 达到百万量级时递归版会有栈深度风险
func (d *DSU) Find(x int) int {
	r := int32(x)
	for d.parent[r] != r {
		d.parent[r] = d.parent[d.parent[r]] // 路径减半，无需第二次遍历
		r = d.parent[r]
	}
	return int(r)
}

func (d *DSU) Union(a, b int) bool {
	ra, rb := int32(d.Find(a)), int32(d.Find(b))
	if ra == rb {
		return false
	}
	if d.size[ra] < d.size[rb] {
		ra, rb = rb, ra
	}
	d.parent[rb] = ra
	d.size[ra] += d.size[rb]
	d.groups--
	return true
}

func (d *DSU) Groups() int { return d.groups }

场景该怎么做为什么代价
订单按时间范围查、按状态过滤，数据要持久化建联合索引交给数据库，不要在应用里维护有序结构B+ 树三四层覆盖亿级行，事务、备份、恢复全是现成的要按查询形态维护索引，写入多一份索引维护成本

敏感词与关键词打标，词表按天更新离线构建 AC 自动机，双缓冲切指针，输入先归一化一遍扫描定位全部命中，构建期压缩最省内存不能实时增词；归一化规则要单独维护和回归

账号合并、风控团伙、变更影响域并查集，边先分级再合并只问是否同组时它近似常数，比反复求交集快得多不支持删除与回滚；边定义过宽会把一切连成一个巨大分量
写入以随机小更新为主、写远多于读选 LSM 系存储，并把压实窗口纳入容量规划随机写被转成顺序写，写吞吐提升明显读放大与空间放大，压实抢 IO 导致尾延迟毛刺

不适用边界：需要事务、持久化、跨实例共享的有序数据，不要自己实现树，交给数据库索引（MySQL、PostgreSQL）；全文检索与相关性排序不是树能解决的，见 检索与搜索引擎；缓存淘汰与过期策略虽然也用到堆与链表，但工程结论在 Redis 专栏；结构选完之后单次操作的复杂度怎么算、常数因子为什么有时反而决定成败，在 复杂度分析；底层的连续内存与指针跳转差异在 数组与链表；并发访问同一棵树的锁粒度问题属于并发范畴，见 Go 并发原语与常见并发 bug。

这条路径上，上一篇讲的是只维护「进出顺序」的线性结构，本篇把顺序升级成「按键有序」与「按偏序」，下一篇把节点间的连接从父子关系放开成任意边——并查集与堆在那里会作为图算法的零件再次出现。

最容易踩的坑

❌
避坑清单
  • 认为 BST 退化罕见：自增 ID、时间序、字典序导入全是有序输入，退化是默认结果不是意外，对照测试必须包含有序输入。
  • 记成「红黑树插入最多三次旋转所以比 AVL 快」：插入两者都是常数次旋转，区别在删除——红黑树旋转有常数上界，AVL 可能一路回溯。
  • 抄「Redis 有序集合底层是红黑树」：实际是跳表加哈希表，小集合时是 listpack 编码。
  • 用平衡树存只读数据：排序数组加二分在内存与缓存命中上全面更优，指针结构的收益只在频繁增删时出现。
  • 该交给数据库索引的活自己实现了一棵树：只要数据要持久化、要跨实例共享或内存装不下，自研结构就是在重复实现一遍事务与恢复。
  • 以为 B 树和 B+ 树只差「叶子有没有链表」：B 树内部节点带数据会降低扇出、抬高树高，这才是数据库统一选 B+ 树的原因。
  • 用长字符串或 UUID 当主键还期待树高不变：内部页每条目变大，扇出下降、树高上升、页分裂率上升。
  • 把 LSM 的删除当成立即释放空间：墓碑记录在压实前不回收，删数据后磁盘不降是预期行为。
  • 只看 LSM 写吞吐不算压实开销：压实会和前台读写抢 IO，尾延迟毛刺往往出现在压实窗口。
  • 中文场景用定长子节点数组的 Trie：按码点开槽会让内存膨胀到不可接受，要换哈希子节点或压缩实现。
  • 敏感词匹配只换结构不做输入归一化：全角、繁简、零宽字符与插空绕过跟算法无关，归一化必须前置。
  • Top-K 的堆方向选反：求最大的 K 个要用容量 K 的小顶堆，用大顶堆装全量在流式场景根本放不下。
  • 为 n 个延时任务开 n 个定时器：只该为堆顶保留一个 timer，并在堆顶变化时 Reset。
  • 在需要回滚的搜索里用带路径压缩的并查集：压缩不可撤销，要改成只按秩合并并记录操作栈。
