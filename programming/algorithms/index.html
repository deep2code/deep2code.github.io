算法与数据结构在后端工程中的位置

这篇是本专题的总览，但它不是刷题路线图。对已经在写线上服务的人来说，算法与数据结构的价值集中在三件事：判断一个方案在目标数据量下是否可行、知道你依赖的组件内部用了什么结构以及它在哪里退化、在复杂度相同的候选之间靠常数因子和内存布局做决定。能不能十分钟手写一个反转链表，和这三件事关系不大。

后端系统里真正会出现的结构

把常见后端场景摊开看，会发现反复出现的结构只有十来种，而且它们几乎都不是你自己写的——是你用的组件替你写了。真正需要你判断的是：这个结构擅长的操作，和业务真正高频的操作是不是同一个。下面这张表可以当选型时的第一层筛子。

从 QPS 与数据量反推可行结构

复杂度在工程里的正确用法不是给算法贴标签，而是做可行性判断：把数据量代进复杂度表达式，算出单次请求的操作次数，再按量级折算成时间。这里只需要两个粗糙的经验尺度——现代单核每秒完成亿级别的简单内存操作，一次随机磁盘访问的代价相当于几十万次内存操作。有这两个尺度，多数选型在写代码之前就能否掉。

数据量与请求量能用的结构必须放弃的做法判据
一万条以内，纯内存随便选，包括每次全量扫描不必引入索引和分片一万次比较在微秒量级，复杂结构的收益被常数吃掉
百万条，要求亚毫秒响应哈希表、有序数组二分、内存跳表每次请求重新排序或全量过滤百万次操作已到毫秒量级，乘上 QPS 直接打满 CPU
亿条，需要范围查询磁盘 B+ 树或 LSM，配游标分页全量加载进进程内存一亿行按每行一百字节算已是十 GiB 量级
十亿 key 的存在性判断布隆过滤器，按位存储存全量 key 的哈希集合每 key 约十比特对比几十字节，差两个数量级
十万 QPS 写入且要求有序读顺序追加加后台归并写路径上同步维护全序索引每次写都触发随机页写，写放大与锁竞争同时爆发
跨天的大批量聚合外部排序加流式归并一次性载入内存排序数据量超过可用内存时进程是被 OOM 杀掉，不是变慢

把折算方式写成脚本比背表靠得住。下面两个函数分别估算布隆过滤器的内存和 B+ 树的树高，是做容量方案时最常用的两个数：

import math


def bloom_sizing(n: int, fp: float):
    """布隆过滤器容量估算。
    位数 m = -n*ln(p) / (ln2)^2，最优哈希个数 k = (m/n)*ln2。
    注意 fp 是设计目标：实际插入量超过 n 之后误判率会迅速恶化，
    所以容量必须按业务峰值预估，而不是按当前值。
    """
    m = -n * math.log(fp) / (math.log(2) ** 2)
    k = (m / n) * math.log(2)
    return math.ceil(m), max(1, round(k))


def bplus_height(rows: int, row_bytes: int, page: int = 16384,
                 key_bytes: int = 8, ptr_bytes: int = 6) -> int:
    """B+ 树树高估算：叶子页放整行，内部页放 key 加下层页指针。
    树高等于一次点查最多的页访问次数，命中内存缓冲池才不算磁盘 IO。
    """
    leaf_fanout = max(1, page // row_bytes)
    inner_fanout = max(2, page // (key_bytes + ptr_bytes))
    nodes = math.ceil(rows / leaf_fanout)
    height = 1
    while nodes > 1:
        nodes = math.ceil(nodes / inner_fanout)
        height += 1
    return height


if __name__ == "__main__":
    bits, k = bloom_sizing(1_000_000_000, 0.01)
    print(f"10 亿 key 误判 1%: {bits / 8 / 2**30:.2f} GiB, k={k}")
    bits, k = bloom_sizing(1_000_000_000, 0.001)
    print(f"10 亿 key 误判 0.1%: {bits / 8 / 2**30:.2f} GiB, k={k}")
    print("1 亿行每行 128B 的树高:", bplus_height(10**8, 128))
    print("10 亿行每行 128B 的树高:", bplus_height(10**9, 128))

跑出来的结论值得记住：十亿 key 想把误判率压到百分之一，只需要一个多 GiB 的位图；误判率再降一个数量级，内存只涨五成左右——布隆过滤器的内存对误判率是对数敏感的，所以不要把 fp 设得过分保守。而十亿行表的 B+ 树也只有四层，这正是为什么关系库单表几亿行时，点查的瓶颈从来不是树高，而是回表与随机 IO。索引结构的细节详见 MySQL 专篇。

近似结构：用可控误差换一个数量级的内存

后端最常被重新发明的一类结构是近似结构。它们的共同点是放弃精确性，换来与数据量几乎无关的内存占用。判断能不能用只需要问三个问题：能容忍哪一侧的错误、要不要删除、要不要取回明细。

结构回答的问题误差方向内存量级能否删除与取明细典型误用
布隆过滤器这个 key 存在过吗只会假阳性，不会漏判每元素约十比特不能删，不能取明细当成精确集合用于扣库存这类不可逆操作
布谷鸟过滤器同上，但要支持删除假阳性；装载率过高时插入失败与布隆同量级，略高可删，不能取明细不处理插入失败，导致数据静默丢失
HyperLogLog大约有多少个不同值双向相对误差，百分之一量级固定十几 KB不能删，不能取明细用它算金额或做对账
Count-Min Sketch某个 key 出现了多少次只会高估，不会低估与宽度乘深度成正比不能取明细用于计费；或不做衰减让历史热点永久占位
t-digest 类分位数结构p99 大概是多少尾部精度高，中部误差大与压缩参数成正比不能取明细把多个实例的分位数直接取平均
精确哈希集合这个 key 存在吗无误差每元素几十字节起可删，可遍历在十亿量级硬上，然后被 OOM

限流算法的选择逻辑和这张表同源——滑动窗口日志精确但内存随请求数增长，固定窗口计数省内存但有临界突发，令牌桶在两者之间。具体实现与分布式下的原子性问题详见站内 限流专篇，缓存淘汰策略详见 缓存专篇，这里不重复展开。

分片与路由：少数需要自己实现的结构

一致性哈希和前缀树是后端为数不多经常要自己写的结构。前者决定扩容时有多少数据要搬，后者决定网关在路由表涨到几千条时还能不能保持与条数无关的匹配代价。下面是一致性哈希环的可用实现，重点在虚拟节点数这个参数上：

package main

import (
	"crypto/sha1"
	"encoding/binary"
	"sort"
	"strconv"
)

// Ring 一致性哈希环。vnodes 是每个物理节点的虚拟节点数：
// 取 1 时负载偏差可达数倍，工程上常取 100 到 200；
// 节点数越少越要往大取，代价是环上元素数等于节点数乘 vnodes，
// 内存与构建时间都线性增长。
type Ring struct {
	vnodes int
	keys   []uint32          // 升序排列的虚拟节点哈希值
	owner  map[uint32]string // 虚拟节点哈希到物理节点的映射
}

func NewRing(vnodes int) *Ring {
	return &Ring{vnodes: vnodes, owner: make(map[uint32]string)}
}

func hash32(s string) uint32 {
	sum := sha1.Sum([]byte(s))
	return binary.BigEndian.Uint32(sum[:4])
}

func (r *Ring) Add(node string) {
	for i := 0; i < r.vnodes; i++ {
		// 分隔符必须固定且不会出现在节点名里，否则节点 a 的第 11 个
		// 虚拟节点会和节点 a1 的第 1 个撞在一起
		h := hash32(node + "#" + strconv.Itoa(i))
		r.keys = append(r.keys, h)
		r.owner[h] = node
	}
	sort.Slice(r.keys, func(i, j int) bool { return r.keys[i] < r.keys[j] })
}

// Get 顺时针找第一个不小于 key 哈希的虚拟节点，代价是对数级二分。
// 加节点时只有落在新虚拟节点区间上的 key 需要迁移，
// 期望迁移量约为总量的 1/N，这就是一致性哈希的全部意义。
func (r *Ring) Get(key string) string {
	if len(r.keys) == 0 {
		return ""
	}
	h := hash32(key)
	i := sort.Search(len(r.keys), func(i int) bool { return r.keys[i] >= h })
	if i == len(r.keys) {
		i = 0 // 绕回环首
	}
	return r.owner[r.keys[i]]
}

流传很广的一个误解是「一致性哈希天然均衡」。它保证的只是扩缩容时迁移量小；均衡性完全依赖虚拟节点数量，虚拟节点太少时单节点负载偏离均值数倍是常态。另一个坑是先用取模分片再想扩容——hash % N 在 N 变化时几乎所有 key 都要重新落位，这是许多系统扩容必须停机搬数据的根本原因。

为什么渐进更优的结构反而更慢

只看复杂度表就下结论，是后端选型里最常见的错误。渐进复杂度刻意丢掉了三样在真实数据量下常常占主导的东西——单次操作的常数开销、内存访问模式、内存分配与 GC 压力。

对比渐进复杂度小数据量下谁赢机制什么时候反转
切片线性查找与哈希表线性对常数切片哈希表要算哈希、可能分配、还要跳一次桶指针；切片是顺序访存，预取有效元素数到几十上百之后哈希表稳定胜出
数组遍历与链表遍历都是线性数组，且差距是量级级别一个缓存行能装多个数组元素，硬件预取能提前取下一行；链表每步都是不可预测的随机访问基本不反转，除非节点很大且遍历比例极低
插入排序与快排平方对线性对数插入排序没有递归与分区开销，几乎全是顺序比较与移动元素数超过十几个，标准库正是按这个阈值切换
跳表与平衡树都是对数相近，跳表的实现与并发处理更简单跳表插入只改局部指针，没有旋转；平衡树旋转会影响整条祖先路径内存紧张时平衡树更省，因为跳表要存多层指针
二分查找与哈希查找对数对常数小数组上二分二分完全在连续内存上做且无哈希计算；但后期几次跳跃距离大，缓存不友好数据量大且只需点查时哈希胜出；要范围查询则只能二分
值类型数组与指针数组相同值类型数组指针数组多一次间接寻址，对象分散在堆上，还多出对象头与 GC 扫描成本元素极大、拷贝代价高于寻址代价时才用指针

这些机制在线性结构篇里有完整展开，包括缓存行、预取和对象头开销的具体表现，详见 线性结构的内存布局与真实代价。

❌
最容易踩的坑
  • 拿复杂度当结论而不代入数据量：一千万条上的线性扫描是十毫秒量级，一千条上是微秒量级，同一个复杂度在两个场景里是完全不同的决定。
  • 在循环里做「看起来是常数」的事：正则编译、拼字符串 key、序列化、反射取字段、每次新建客户端，都会把线性变成平方，而且不体现在代码形状上。
  • 把布隆过滤器当精确集合：它只保证「判定不存在就真的不存在」，反过来不成立；用它守扣库存或幂等键会直接吞掉合法请求。
  • 以为一致性哈希自带均衡：均衡靠虚拟节点数，只配几个虚拟节点的环，单节点负载偏离均值数倍是常态。
  • 用 hash % N 做分片：N 一变几乎全量 key 换位置，扩容只能停机搬数据。
  • 用 HyperLogLog 或 Count-Min 的结果做金额、对账、计费——这些结构的误差是设计目标，不是缺陷。
  • 把多个实例的 p99 取平均当整体 p99：分位数不可线性合并，必须合并原始分布或使用可合并的分位数结构。
  • 只看平均延迟做容量评估：动态数组扩容、哈希表 rehash、存储层合并、GC 都只在 p99 以上可见，平均值会把它们完全抹平。
  • 为了「更优复杂度」把小集合的切片换成哈希表或树，结果因为哈希计算与堆分配变慢，还多了一层 GC 压力。
  • 忘了内存里还有对象头与指针开销：装一亿个小对象时，光对象头和指针就可能超过数据本身，估容量必须算进去。
  • 分片键上线后才发现选错：跨片查询、跨片事务和数据重分布的长期成本，远高于当初多花两天选结构。
  • 把「标准库已经很快」当成不用估算的理由：标准库优化的是常数，不会把平方降成线性，量级问题只能靠换结构解决。
