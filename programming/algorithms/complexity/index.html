复杂度分析的工程用法与失效场景

🏷️ 算法,复杂度分析

渐进复杂度是个好工具，但它在工程里经常被用错：被当成给算法贴的标签，而不是可行性判断的输入。这篇不讲怎么推导大 O——假定你已经会了——而是讲三件更要紧的事：渐进符号把什么成本藏起来了、摊还结论为什么在 p99 上不成立、以及怎么把复杂度变成一个能拍板的数字。

💡
这篇怎么读
  • ① 用法：容量估算的四步动手法、一段能直接跑的估算脚本、一张量级对照表，以及用 go test -benchmem、perf stat、pprof、gctrace 把常数量出来而不是猜的命令与判读方法。
  • ② 原理：渐进符号隐藏的四类成本、摊还与平均与期望与最坏各自需要什么假设、扩容与 rehash 怎么变成尾延迟尖刺、空间复杂度里的布局与分配次数、递归深度对应的栈上限、随机化算法成立的前提。
  • ③ 场景：复杂度相同却实测差一个量级时按什么顺序排查、典型场景该用哪种结论（摊还还是最坏），以及哪些问题算复杂度是白算。

① 用法 · 容量估算的四步动手法与怎么用 benchmark 验证

工程里用复杂度的标准动作只有一个：一次估算加一次验证。四步顺序固定，任何一步不过关就换结构，而不是先把代码写完再压测。

步骤必须落到纸上的东西怎么算这一步最常出的错
一、写清输入规模元素数量 n、每元素实际字节数、目标 QPS、单次请求的结果集条数能查监控就查，查不到先埋点，不要用「应该不多」代替把 n 当成唯一变量，漏掉键长度、结果条数、并发度、批大小
二、算操作次数候选结构的单次请求操作次数表达式，不是一个复杂度标签点查记 1，有序定位记对数，全量过滤记 n，每次重排记 n 乘对数把循环里的一次查库也记作「一次操作」，量级立刻错四五个数量级
三、乘上单次操作的量级这些操作分别落在内存、磁盘页读还是网络往返上内存操作按每秒两亿次折算，一次随机页读按一百微秒，跨机往返按亚毫秒起三类混在一起算总量，结论被最慢的那一类完全支配却看不出来
四、对比预算三个判定：耗时乘 QPS、常驻内存、最坏单次延迟耗时乘 QPS 不超核数的一半，内存不超配额的七成，最坏单次要满足 SLA只验平均延迟就宣布通过，扩容与 GC 的尖刺全被平均值抹掉

把这个流程写成十几行脚本，比每次口算靠得住。下面这段直接输出「单次耗时」和「可承载 QPS」两个决策数：

import math

CORE_OPS_PER_SEC = 2e8   # 单核每秒简单内存操作数，保守取两亿
PAGE_READ_SEC = 1e-4     # 一次随机页读按一百微秒算
SAFETY = 0.5             # 只允许用掉单机能力的一半，余量给尖峰、GC 与扩容


def per_request_ops(n: int, kind: str) -> float:
    """把结构选型写成可计算的表达式，而不是一个复杂度标签。"""
    table = {
        "hash": 1.0,                             # 哈希点查
        "binary": math.log2(max(n, 2)),          # 有序结构二分
        "scan": float(n),                        # 全量扫描或过滤
        "sort": n * math.log2(max(n, 2)),        # 每次请求重新排序
    }
    return table[kind]


def capacity(n: int, kind: str, cores: int, page_reads: int = 0):
    """返回单次请求耗时（秒）与该方案在给定核数下可承载的 QPS。"""
    ops = per_request_ops(n, kind)
    sec = ops / CORE_OPS_PER_SEC + page_reads * PAGE_READ_SEC
    return sec, cores * SAFETY / sec


if __name__ == "__main__":
    n = 10_000_000
    for kind in ("hash", "binary", "scan", "sort"):
        sec, qps = capacity(n, kind, cores=8)
        print(f"{kind} 单次 {sec * 1000:.3f} ms, 8 核可承载约 {qps:.0f} QPS")
    # 同一份一千万行数据：点查可承载的 QPS 比全表扫描高五到六个数量级。
    # 这不是「优化幅度」，而是可行与不可行的分界线。

其中「单机能力的一半」和「配额的七成」不是玄学：留出的余量给的是流量尖峰、GC、扩容拷贝和邻居干扰。下面这张量级表配合这个流程用，可以省掉大部分压测：

指数级问题的改写方法详见 动态规划 与 贪心与回溯，这里只给一条结论：看到指数级，先找重叠子问题，再考虑剪枝。

估算给的是数量级，常数只能量。下面四条命令对应四类问题，关键是知道输出怎么判读——这一步做了，「优化有没有效」才是结论而不是感觉：

# 1) 量常数与分配：同阶实现之间的真实差距
go test -bench='Build' -benchmem -count=5 ./... | tee bench.txt
# 判读：ns/op 是单次耗时，B/op 与 allocs/op 是每次操作分配的字节数与次数。
# allocs/op 随输入规模增长，说明循环里在分配；两个同阶实现 ns/op 差三倍以上，
# 差距一定来自常数或访存模式，不可能来自复杂度。

# 2) 判断是不是访存问题
perf stat -e cycles,instructions,cache-references,cache-misses,LLC-load-misses ./server
# 判读：instructions 除以 cycles 明显低于 1，且 cache-misses 占 cache-references 比例高，
# 说明 CPU 在等内存，优化方向是数据布局而不是换算法。

# 3) 定位到函数级：CPU 与堆 profile
go tool pprof -http=:8080 http://127.0.0.1:6060/debug/pprof/profile?seconds=30
go tool pprof -http=:8081 http://127.0.0.1:6060/debug/pprof/heap
# 判读：热路径上出现 regexp.Compile、reflect、json、fmt，说明循环里藏了常数很大的操作；
# memmove 占比高，说明大对象按值拷贝或容器在反复扩容。

# 4) 区分尾延迟尖刺来自 GC 还是扩容
GODEBUG=gctrace=1 ./server 2>&1 | head -50
# 判读：每行里的 STW 阶段耗时若与 p99 尖刺时间点吻合，问题在分配速率；
# 不吻合则更可能是扩容拷贝、锁等待或下游抖动。
旗标或命令作用默认值什么时候需要改
-bench=正则选择要运行的基准函数不跑任何基准只比较两个实现时把正则收窄，避免整包基准把时间耗光
-benchmem额外输出 B/op 与 allocs/op关任何涉及容器、拼接、序列化的对比都必开，分配次数是主要差异来源
-benchtime每个基准跑多久，也可写成 100x 指定次数1s单次操作很慢时改成固定次数，否则默认时长里只跑到个位数轮
-count=N整组基准重复 N 轮，给显著性判断提供样本1做优化前后对比时至少 5 到 10 轮，单轮结果的波动经常大于差异
-cpu=1,2,8用不同的 GOMAXPROCS 各跑一遍当前 GOMAXPROCS对比并发数据结构时必加，单核下看不出争用与伪共享
-memprofile 与 -cpuprofile把采样落成文件供 pprof 分析关基准显示有差距但看不出原因时，用它定位到函数与行
benchstat old.txt new.txt比较两组基准结果，给出差异百分比与波动需单独安装任何写进结论或 PR 描述的性能数字都应该出自它，而不是肉眼比两行输出
GOGC 与 GOMEMLIMIT调整触发 GC 的堆增长比例与软内存上限随版本变化，以 go env 与运行时文档为准确认瓶颈是分配速率之后，用它验证「少分配」的收益方向

为什么两个同阶实现能差三倍、为什么摊还常数会在 p99 上现形、为什么预分配是最便宜的尾延迟优化——原因在下面几节。

② 原理 · 渐进复杂度隐藏了什么

搞清这一节能解释一个常见现象：换了「更优」的结构反而变慢。大 O 的定义里只留下了增长趋势，被丢掉的常数因子在真实数据量下往往就是全部差距。更麻烦的是，被丢掉的不只是一个乘性常数，而是四类性质完全不同的成本：

被隐藏的成本为什么渐进符号看不见典型表现怎么观测
单次操作的常数哈希计算、接口动态派发、反射、边界检查都算「一次操作」小集合上哈希表比线性扫描慢CPU profile 里指令数集中在少数函数
内存访问模式访问一个元素记作一次操作，不区分命中缓存还是落到主存链表遍历与数组遍历同阶但差一个量级perf 的 cache-misses 与 LLC-load-misses
内存分配次数分配被当作常数，实际会触发分配器加锁、清零、GC 标记吞吐随堆增长下降，GC 占用 CPU 上升Go 的 benchmem 与 allocs/op，JVM 的 GC 日志
系统调用与 IO一次读写记作一次操作，实际跨越用户态与设备循环里逐条查库，接口延迟随结果条数线性上升链路追踪里同一 SQL 出现 N 次

把这四类成本放到同一个尺度上看，才能理解为什么「操作次数」这个说法本身就有歧义——一次操作的代价可以差七个数量级：

这张图的实用含义很直接：如果你的接口里有一次跨服务调用，那么把某段内存计算从平方降成线性，通常一点都感觉不到；反过来，把循环里的 N 次查询合并成一次，效果立刻可见。量级之间的换算只是数量级参考，不同硬件差一两倍不影响结论。

② 原理 · 摊还、平均、期望、最坏：四个词不是同义词

搞清这一节能避免一类错误结论：拿一个需要前提的结论去写不该有前提的承诺。这四个词在中文资料里经常混用，但它们的适用条件完全不同，用错会直接得出错误的容量结论。

概念定义对象需要什么假设典型结构对 p99 的意义
摊还（amortized）一串操作的总代价除以操作数不需要概率假设，对任意输入成立动态数组追加、并查集路径压缩不保证单次；扩容那一次仍然是线性
平均（average）按输入分布求期望需要输入分布假设，分布一变就失效哈希表查找、朴素快排攻击者或热点数据能让假设不成立
期望（expected）对算法自身随机数求期望只需随机源不可预测，与输入无关随机主元快排、跳表层数坏运气概率极小，但随机源泄露则退化
最坏（worst case）单次操作的上界无假设堆排序、平衡树、归并排序唯一能直接支撑 SLA 的量

结论是：做容量规划可以用摊还，写 SLA 只能用最坏。这也是为什么对延迟敏感的系统宁可选一个平均更慢但最坏有界的结构——比如用堆排序而不是快排、用预分配数组而不是让它自己长。

② 原理 · 扩容与 rehash：摊还常数是怎么变成尾延迟尖刺的

搞清这一节能解释线上最常见的一类曲线：平均延迟平稳，p99 却规律性地跳一下。动态数组的追加是摊还常数的教科书例子，但线上表现是绝大多数请求很快、偶尔一个请求慢十倍。原因就在下面这个状态机里——昂贵的那一步没有消失，只是被平均掉了。

不同运行时的扩容策略决定了尖刺的高度和频率，这些是必须知道的细节：

运行时增长策略迁移方式尾延迟表现规避手段
Go 切片小容量翻倍，超过阈值后按约 1.25 倍递增；阈值在 1.18 之后从 1024 个元素改为 256一次性拷贝单次尖刺与长度成正比make([]T, 0, n) 预分配
Go map装载因子超过 6.5 或溢出桶过多时翻倍；1.24 起换成 Swiss Table 实现增量迁移，写操作顺带搬尖刺被摊平，但扩容期间整体变慢且内存翻倍make(map[K]V, n) 预估容量
Java ArrayList约 1.5 倍增长一次性 Arrays.copyOf单次尖刺，大对象可能直接进老年代构造时给 initialCapacity
Java HashMap容量翻倍，阈值为容量乘装载因子 0.75一次性 rehash，在某次 put 里完成尖刺明显，链表转红黑树还有额外抖动按预期条目数除以 0.75 设初始容量
Python list约 1.125 倍加常数的温和增长一次性 realloc，可能原地扩展尖刺较小但扩容次数更多用列表推导一次建好，或预填充
Redis 字典翻倍渐进式 rehash，命令与定时任务分批搬避免长阻塞，代价是 rehash 期间两张表并存控制单实例键数量，详见 Redis 专篇

预分配是成本最低的尾延迟优化，而且是可以量化的。下面是一段能直接用的观测与预分配代码：

package sizing

import "testing"

// 关键点：预分配把「摊还常数加偶发线性尖刺」变成「稳定常数」。
// 用 go test -bench=. -benchmem 跑，看 allocs/op：
// 未预分配版本的 allocs/op 随 n 增长（每次扩容一次分配），
// 预分配版本恒为 1。这个差值就是你在 p99 上省掉的东西。

func buildNaive(n int) []int {
	var out []int // cap 为 0，后续会经历 log 级别次数的扩容与拷贝
	for i := 0; i < n; i++ {
		out = append(out, i)
	}
	return out
}

func buildPrealloc(n int) []int {
	out := make([]int, 0, n) // 长度 0、容量 n：不会再扩容
	for i := 0; i < n; i++ {
		out = append(out, i)
	}
	return out
}

// map 同理：不给 hint 会在装载因子超限时反复扩容，
// 扩容期间新旧两套桶并存，内存峰值接近两倍。
func indexByID(rows []int) map[int]int {
	m := make(map[int]int, len(rows)) // hint 按最终条目数给，不是按字节
	for i, id := range rows {
		m[id] = i
	}
	return m
}

func BenchmarkBuildNaive(b *testing.B) {
	b.ReportAllocs()
	for i := 0; i < b.N; i++ {
		buildNaive(10000)
	}
}

func BenchmarkBuildPrealloc(b *testing.B) {
	b.ReportAllocs()
	for i := 0; i < b.N; i++ {
		buildPrealloc(10000)
	}
}

注意 map 的容量提示是条目数而不是字节数，而且给了 hint 也不能完全避免扩容——只是把扩容次数降到最少。另外，切片预分配时 make([]T, 0, n) 和 make([]T, n) 语义完全不同，后者长度就是 n，再 append 会追加到第 n 个之后，这是每个人都会犯一次的错。

② 原理 · 空间复杂度：额外内存之外还有布局

搞清这一节能解决一个具体症状：容量估算算出来是够的，上线之后却超配额。空间复杂度通常被写成「额外用了多少内存」，但在工程里有三个更具体的问题：峰值内存是多少、这块内存的访问是否连续、分配了多少次。第三个问题常常比前两个重要，因为分配次数直接决定 GC 压力。

空间维度渐进符号是否体现失控时的症状控制手段
峰值额外内存体现容器被 OOM 杀掉，不是变慢流式处理、分批、外部排序
内存布局与局部性不体现CPU 利用率高但吞吐低，cache-misses 高结构体数组代替数组结构体、紧凑编码、避免指针海
分配次数不体现GC 频率与停顿上升，p99 抖动预分配、对象复用池、减少逃逸
每元素固定开销不体现估算差两三倍，上线就超配额算清对象头、指针、哈希桶与对齐填充
临时副本常被忽略内存翻倍，尤其在扩容与序列化时就地操作、复用缓冲区

一个具体例子：装一亿个整数，用紧凑的整型切片大约几百 MB，用装箱对象加指针的容器可能超过 GiB，而两者的空间复杂度都写作线性。所以估容量时一定要算「每元素实际字节数」，而不是只看数量级。缓存行、预取和对象头开销的机制详见站内 线性结构的内存布局与真实代价。

② 原理 · 递归深度与栈：一个被漏算的空间维度

搞清这一节能堵住一类可用性风险：一个精心构造的深层嵌套输入就能把进程打崩。递归的空间复杂度等于最大递归深度乘每帧大小，而栈空间是有硬上限的。处理用户可控深度的数据时，这不是性能问题而是可用性问题。

运行时栈的行为超限表现可控手段
Go协程栈从 2 KB 起，按需拷贝式增长触及运行时最大栈限制后直接终止进程，无法恢复改迭代加显式栈；对入参深度设上限
JVM每线程固定栈，由 -Xss 决定，通常几百 KB 到一 MB抛出 StackOverflowError，可捕获但状态难保证调大 -Xss 只是拖延；深度校验才是解法
CPython有递归层数上限，默认一千层量级抛 RecursionError；强行调高上限会因 C 栈耗尽而崩溃迭代化；解析类场景限制嵌套层数
Node.jsV8 栈大小有限且由启动参数决定抛 RangeError迭代化或分片让出事件循环

实际排查要点：平衡的树递归深度是对数级，退化的链状结构是线性级。所以「递归处理树形数据没问题」的前提是树是平衡的；解析外部传入的 JSON、XML、表达式时没有这个前提，必须显式限深。遍历与平衡的细节详见 树与二叉树，改成显式栈的写法详见 栈与队列。

② 原理 · 随机化：期望复杂度的前提是随机源不可预测

搞清这一节能防住一类以小博大的攻击：少量请求打满 CPU。很多结构的优良复杂度依赖随机性——快排随机选主元避免退化，跳表用随机层数替代旋转，哈希表依赖哈希函数把键打散。这些结论只在随机源不可被输入方推测时成立。

sequenceDiagram autonumber participant A as 攻击者 participant S as 服务 participant M as 哈希容器 A->>S: 探测哈希实现与种子是否固定 S-->>A: 响应时间差异泄露碰撞信息 A->>S: 批量提交大量同桶键，例如表单字段或 JSON 键 S->>M: 逐个插入 M->>M: 所有键落入同一桶，插入退化为线性扫描 M-->>S: 单请求 CPU 时间随键数平方增长 S-->>A: 少量请求即打满 CPU Note over S,M: 防线有三层：每进程随机哈希种子
单桶过长时转为有序结构
以及对请求参数个数设上限

现代运行时默认给哈希容器加了随机种子，一些实现还会在单桶链表过长时转成红黑树，把最坏从平方压到对数。但这三层防线里只有第三层是你自己的责任：对外部输入的字段数、数组长度、嵌套深度设上限。另一个方向的例子是排序库：随机主元只能给出期望保证，所以工业实现会在递归过深时切换到堆排序，用确定性的最坏兜底，细节详见 排序的工程现实。

不适用边界：算复杂度解决不了三类问题。一是访存与内存布局造成的同阶差距，机制在 线性结构的内存布局与真实代价；二是并发正确性与锁争用，原语选择与 race 检测在 Go 并发原语与常见并发 bug；三是线上到底慢在哪一跳，采样与判读方法在 性能分析 与 指标体系，执行计划层面的判断在 MySQL 专篇。

最容易踩的坑

❌
避坑清单
  • 把摊还常数当成单次常数写进 SLA：扩容、rehash、合并那一次的代价与当前规模成正比，p999 上一定能看见。
  • 用平均复杂度给哈希表背书，却没限制外部输入的键数量与来源，结果被碰撞构造打成线性。
  • 在循环里编译正则、拼字符串 key、做反射或格式化日志：代码只有一层循环，实际是平方。
  • 循环里逐条查库或调接口：复杂度分析算的是内存操作，这里每一步都是十万倍代价的往返。
  • 切片预分配写成 make([]T, n) 再 append：长度已经是 n，结果数据多出一倍且前半是零值。
  • 给 map 的容量提示传字节数而不是条目数，或者干脆不传，让它在热路径上反复扩容并让内存峰值翻倍。
  • 忘了估每元素固定开销：对象头、指针、哈希桶与对齐填充加起来经常比数据本身还大。
  • 递归处理外部输入的嵌套结构而不限深：Go 里直接终止进程，CPython 里调高递归上限会变成段错误。
  • 只用平均延迟验证优化效果：分配次数、扩容尖刺、锁竞争带来的影响全在尾部，平均值会抹平。
  • 基准只跑一轮就下结论：不加 -count 与 benchstat，波动经常大于你要证明的差异。
  • 在有网络往返的链路里花一周把某段内存计算从平方优化到线性，收益被一次 RPC 完全吃掉。
  • 拿小数据量的实测结论去推大数据量：常数因子主导的区间和渐进主导的区间结论经常相反。
  • 把 n 当成唯一变量：键长度、结果集大小、并发度、批大小都可能是真实的增长维度，漏掉哪个都会得出错误的可行性判断。
