Redis（Remote Dictionary Server）是内存级键值存储，同时也是数据结构服务器，强项在缓存、消息队列、实时计数、会话存储这些场景。这篇是长期迭代的实操笔记：正文记的是基础安装、版本演进和常用命令，文末更新节 末尾汇总 2025–2026 年 Redis 8 系列的现状。

Redis 4 引入自动内存碎片整理

# 开启自动内存碎片整理（总开关），默认 no
activedefrag yes
# 当碎片达到 100mb 时，开启内存碎片整理
active-defrag-ignore-bytes 100mb
# 当碎片超过 10% 时，开启内存碎片整理
active-defrag-threshold-lower 10
# 内存碎片超过 100%，则尽最大努力整理
active-defrag-threshold-upper 100
# 内存自动整理占用资源最小百分比
active-defrag-cycle-min 1
# 内存自动整理占用资源最大百分比
active-defrag-cycle-max 25

4.0 引入、8.x 沿用。开不开先看 INFO memory 的 mem_fragmentation_ratio ：持续高于 1.4 又内存吃紧再开；删大 Key 优先用 UNLINK 异步释放。

Notice：开了之后，某些时段可能拖慢 Redis 响应

Redis 5 带来 Stream

Redis 对消息队列（MQ）的实现已经相当完整。注意：Pub/Sub 是广播即焚、消息不落地；Stream 会把消息持久化，消费组内竞争、组间广播，再配上 XACK 能做到"至少一次"可靠消费。要消息不丢就上 Stream，纯事件通知用 Pub/Sub。

Redis 6 增加多线程

# io-threads 4
# Setting io-threads to 1 will just use the main thread as usual.
# io-threads-do-reads no

何时值得开：网络 I/O 撞墙的时候——6.0 的多线程只管网络 I/O（读请求解析 + 写响应），命令执行还是主线程单线程跑。大 value（100KB+）或高频 pipeline 场景收益明显，普通小命令场景意义不大。

  • XREADGROUP 和 XACK 配合用：读到消息（XREADGROUP ）处理完一定要 XACK ，否则计数不清、重启后会重复投递——这就是"至少一次"语义的来源。
WHILE true
    entries = XREADGROUP $GroupName $ConsumerName BLOCK 2000 COUNT 10 STREAMS mystream >
    if entries == nil
        puts "Timeout... try again"
        CONTINUE
    end

    FOREACH entries AS stream_entries
        FOREACH stream_entries as message
            process_message(message.id,message.fields)

            # ACK the message as processed
            XACK mystream $GroupName message.id
        END
    END
END

常见问题：雪崩 / 击穿 / 穿透

graph TB subgraph 缓存雪崩 A1[大量key同时过期] --> A2[请求全部打到DB] A2 --> A3[DB崩溃] end subgraph 缓存击穿 B1[热点key过期] --> B2[大量并发请求] B2 --> B3[DB压力骤增] end subgraph 缓存穿透 C1[查询不存在的key] --> C2[DB也无数据] C2 --> C3[每次都查DB] end style A3 fill:#ef4444,stroke:#fff,color:#fff style B3 fill:#f59e0b,stroke:#fff,color:#fff style C3 fill:#8b5cf6,stroke:#fff,color:#fff
  1. 缓存雪崩：一大堆 key 在同一时刻集体过期，瞬时请求全砸到 DB。
    1. 对策：过期时间加随机抖动；热点数据走"逻辑过期"（永不过期 + 后台异步刷新）；叠多级缓存。
  2. 缓存击穿：单个热点 key 失效那一瞬，高并发同时穿透到 DB。
    1. 对策：重建时加互斥锁（SET NX 抢锁）；热点 key 永不过期 + 异步更新。
  3. 缓存穿透：查的 key 在 DB 里压根不存在，缓存永远命中不了。
    1. 对策：布隆过滤器挡在缓存前；空结果也缓存（短 TTL）；入口参数做校验。

这三个名字容易混：雪崩=大面积同时失效；击穿=单个热点失效的瞬间；穿透=查的东西压根不存在。

批量删除

--批量删除msg开始的键值
EVAL "return redis.call('del', unpack(redis.call('keys', ARGV[1])))" 0 'msg*'

生产环境慎用 KEYS + EVAL：KEYS 是 O(N) 全库扫描，会卡住主线程。量大时改用 SCAN + DEL 分批删（或者 UNLINK 异步删）。上面那套只适合开发机和明确少量 Key 的场景。

Redis 通讯协议 RESP

  • 请求协议
    1. * 后面的数字是参数个数（也就是有几个 $）
    2. $ 后面的数字是该字符串的字节长度
    3. 每项用 \r\n 分隔
*3\r\n$3\r\nSET\r\n$5\r\nmykey\r\n$7\r\nmyvalue\r\n

pipeline 的实现就是一条连接里连续发多条命令，不用等每条都返回

RESP2 是经典文本协议，上面就是它的报文格式；Redis 6.0 起支持 RESP3 （客户端 HELLO 3 协商），多了服务端主动推送能力——客户端缓存（Client-side Caching）和 Pub/Sub push 都靠 RESP3 。2026 年主流客户端已经默认或自动协商 RESP3。

Redis 8 系列时代（2025-2026）

许可回归：Redis 再次开源

2024 年 3 月 Redis 把主线切到 RSALv2/SSPLv1 双许可，一度震动社区；同年 11 月创始人 antirez（Salvatore Sanfilippo）回归，力推"Redis is open source again"。从 Redis 8 起，官方给出三种许可选项：RSAL v2、SSPL v1、AGPL v3 ，其中 AGPL v3 是 OSI 认证的真正开源许可。

  • Redis Open Source（社区版）继续免费可用，核心功能不打折
  • AGPLv3 面向网络服务场景，分发或修改后得开源，适合自托管用户
  • 云厂商托管仍走 RSAL/SSPL 的商用授权路子

一句话：现在能用 AGPLv3 把它当"真开源"用了；但代码改完对外提供服务，得把改动开源出来。

Redis 8.0："One Redis"模块内置（2025 年发布）

8.0 把 RediSearch、RedisJSON、RedisTimeSeries、RedisBloom 等模块深度揉进核心，不用再单独装模块、对版本、愁兼容性。

  • 内置全文搜索：RediSearch 成了核心功能
  • 内置向量搜索：支持 FLAT、HNSW、SVS-VAMANA 三种索引
  • 内置 JSON 文档存储：JSON 升格为一等数据类型
  • 8 种新增数据结构：向量集（Vector Sets）、JSON、时间序列，外加 5 种概率结构（Bloom/Cuckoo Filter、Count-min Sketch、Top-k、t-digest）
  • 性能重构：官方基准 149 项里 90 项更快，p50 延迟降 5.4%–87.4%；多核 IO 线程吞吐最高 +112%，复制时间 -18%
  • 十亿向量能力：10 亿向量规模下每秒能维持约 6.6 万次向量插入，配合 Query Engine，查询能力比 7.x 提升约 16 倍

版本节奏：8.0 到 8.10（截至 2026-08）

Redis 8 系列发版明显提速：到 2026 年 8 月已经连发 6 个主要版本，当前稳定线是 8.10.x（8.10.1，2026-08-17） ，同时还在并行维护 7.2 / 7.4 LTS：

  • 8.0 （2025 年）：One Redis 模块内置、Vector Sets（测试版）、性能重构
  • 8.2 / 8.4：向量集与 Query Engine 迭代、内存占用优化、复制和集群面增强
  • 8.6：Vector Sets 等功能转正 GA，AI 相关能力（语义缓存、混合搜索、AI 工具链）加强
  • 8.8 / 8.10 （2026 年）：延续性能和 AI 能力迭代，8.10 是当前最新稳定线

升级建议：新项目直接上 8.x 最新稳定版（8.10）；从 7.2 / 7.4 升级时配置项基本兼容，但模块类命令已内置、行为有变，先跑 redis-benchmark 做回归。

7.2 引入可扩展的向量相似性索引；8.x 起 Vector Sets 升格为独立数据类型，专为向量存储 + 相似检索设计，内存更省、索引管理更简单。

# Redis 8.x 原生命令（无需加载模块）
VADD myset item1 0.51 0.96 0.23 ...     # 向向量集添加元素
VSIM myset 0.42 0.80 0.11 ... COUNT 10  # 与查询向量相似度 Top-10

Python 侧用官方 redis-py （5.x+），靠 VectorField + KNN 查询做语义搜索 / 推荐系统：

from redis import Redis
from redis.commands.search.field import VectorField, TextField
from redis.commands.search.indexDefinition import IndexDefinition
from redis.commands.search.query import Query

r = Redis(host='localhost', port=6379)
schema = (TextField("title"),
          VectorField("embedding", "HNSW", {"TYPE": "FLOAT32", "DIM": 768,
                                            "DISTANCE_METRIC": "COSINE"}))
r.ft("doc_index").create_index(schema, definition=IndexDefinition(prefix=["doc:"]))

Redis 7.x 关键特性回顾

  • ACL v2：细粒度权限控制，支持用户、命令、Key 三维度授权
  • Function：持久化 Lua 脚本，顶替易失的 EVAL/EVALSHA
  • Multi-part AOF：AOF 分片存储，避免重写卡住主线程
  • Sharded Pub/Sub：分片发布订阅，消息只在持有对应 slot 的节点上传播
  • LISTPACK：更紧凑的内存编码，顶替 ziplist

Redis Stack 退场

Stack 发行版已被 8.0 完整吸收进主线，不再作为独立产品维护 ；要搜索 / JSON / 时序 / 概率结构的用户直接升到 8.x 就行。

生态：Valkey 与 Dragonfly

2024 年那场许可风波催生了社区分支，2026 年选型绕不开它们：

  • Valkey：Linux 基金会托管（Google、AWS、Oracle、腾讯等共建），基于 7.2.4 fork；Valkey 9 加入集群多逻辑库、原子 slot 迁移、官方 JSON / Bloom / 向量模块，命令集与 Redis 7.2 兼容
  • Dragonfly：多线程共享内存架构，单节点吞吐号称是 Redis 单线程的数倍，协议同时兼容 Redis 和 Memcached，能无缝替换

选型建议：认官方血统就用 Redis 8.x；对开源许可和治理有硬约束就上 Valkey；单机要极致吞吐可评估 Dragonfly。
