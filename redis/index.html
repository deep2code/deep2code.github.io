Redis（Remote Dictionary Server）是内存级键值存储，也是数据结构服务器，强项在缓存、消息队列、实时计数、会话存储等场景。2026 年 Redis 8.x 是主流版本，Redis Stack 7.x 提供搜索、JSON 等扩展能力。

数据文件存储与结构

Redis 是内存数据库，但通过 RDB 和 AOF 两种机制将数据持久化到磁盘。理解文件格式和内存数据结构是性能调优的基础。

持久化文件结构

redis_data_dir/
├── dump.rdb              # RDB 快照文件（二进制格式）
├── appendonly.aof         # AOF 追加文件（文本格式，RESP 协议）
├── redis.conf             # 配置文件
├── nodes.conf             # 集群节点信息（集群模式）
├── dump.rdb.backup        # 备份文件
└── redis.log              # 日志文件

RDB 文件格式（二进制快照）

RDB 是某一时刻的内存数据快照，采用紧凑的二进制格式。

┌──────────────────────────────────────────┐
│  Magic Number: "REDIS" (5 bytes)         │
├──────────────────────────────────────────┤
│  Version: 4 bytes (如 0009)              │
├──────────────────────────────────────────┤
│  AUX 字段（可选）                          │
│  - redis-ver: 版本号                      │
│  - redis-bits: 32/64 位                  │
│  - ctime: 创建时间                        │
│  - used-mem: 已用内存                     │
├──────────────────────────────────────────┤
│  SELECTDB: 数据库编号                      │
├──────────────────────────────────────────┤
│  Key-Value 对（循环）                      │
│  ┌────────────────────────────────────┐  │
│  │  Value Type (1 byte)               │  │  0=string,1=list,2=set...
│  │  Key (长度编码 + 字符串)            │  │
│  │  Value (根据类型编码)               │  │
│  │  - String: 长度 + 数据             │  │
│  │  - List: 长度 + 逐个元素           │  │
│  │  - Set: 长度 + 逐个元素            │  │
│  │  - ZSet: 长度 + (元素+分数)        │  │
│  │  - Hash: 长度 + (field+value)      │  │
│  └────────────────────────────────────┘  │
├──────────────────────────────────────────┤
│  EOF: 0xFF (1 byte)                       │
├──────────────────────────────────────────┤
│  Checksum: CRC64 (8 bytes)                │
└──────────────────────────────────────────┘

AOF 文件格式（命令追加）

AOF 以 RESP 协议文本格式记录每条写命令，追加写入文件。

*3
          # 3 个参数
$3
SET
   # 命令 SET (3 字节)
$5
name
  # key "name" (5 字节)
$5
Alice
 # value "Alice" (5 字节)

*2

$3
INCR

$7
counter
  • always：每条命令都 fsync，最安全，性能最差
  • everysec：每秒 fsync（默认），最多丢 1 秒数据
  • no：由 OS 决定何时刷盘，性能最好，可能丢更多数据
  • AOF 重写：BGREWRITEAOF，压缩冗余命令，生成最小化 AOF
  • 混合持久化（Redis 4.0+）：AOF 重写时前半段用 RDB 格式，后半段用 AOF 格式，兼顾加载速度和数据安全

内存数据结构

Redis 每种数据类型底层使用多种编码结构，根据元素数量和大小自动转换。

数据类型底层编码结构转换条件
StringSDS（简单动态字符串）、int、embstr整数用 int，短字符串用 embstr，长字符串用 raw
Listquicklist（双向链表 + 压缩列表）Redis 3.2+ 默认，替代 ziplist + linkedlist
Hashlistpack（紧凑列表）、hashtable元素少且值短用 listpack，否则用 hashtable
Setintset（整数集合）、hashtable全是整数且数量少用 intset，否则用 hashtable
ZSetlistpack + skiplist、hashtable + skiplist元素少用 listpack，否则用 skiplist + hashtable

SDS（简单动态字符串）

struct sdshdr {
    int len;       // 已使用长度
    int free;      // 剩余空间
    char buf[];    // 数据数组（以 \0 结尾）
};
// 优势：O(1) 获取长度、杜绝缓冲区溢出、减少修改时的内存重分配、二进制安全

字典（哈希表）

typedef struct dict {
    dictType *type;     // 类型特定函数
    void *privdata;     // 私有数据
    dictht ht[2];       // 两个哈希表（用于 rehash）
    long rehashidx;     // rehash 进度，-1 表示未在 rehash
} dict;

typedef struct dictht {
    dictEntry **table;  // 哈希表数组
    unsigned long size; // 表大小
    unsigned long sizemask; // 大小掩码 = size-1
    unsigned long used; // 已有节点数
} dictht;
// 渐进式 rehash：在 ht[0] 和 ht[1] 之间逐步迁移，避免一次性 rehash 阻塞

跳表（Skip List）

Level 3:  1 ──────────────────────────────────→ 100
Level 2:  1 ───────────→ 30 ─────────────────→ 100
Level 1:  1 ──→ 10 ──→ 30 ──→ 50 ──→ 70 ──→ 100

9.2 分布式锁

# 分布式锁
import redis
import time

r = redis.Redis(decode_responses=True)

def acquire_lock(lock_name, timeout=10):
    lock_key = f'lock:{lock_name}'
    # SET NX EX 原子操作
    result = r.set(lock_key, '1', nx=True, ex=timeout)
    return result is not None

def release_lock(lock_name):
    lock_key = f'lock:{lock_name}'
    r.delete(lock_key)

# 使用
def process_order(order_id):
    lock_name = f'order:{order_id}'
    
    if acquire_lock(lock_name):
        try:
            # 处理订单
            pass
        finally:
            release_lock(lock_name)
    else:
        print('获取锁失败，订单正在处理中')

底层数据结构深度解析

Redis 的高性能不仅来自内存存储，更来自其精心设计的底层数据结构。每种 Redis 对象类型（String/List/Hash/Set/ZSet）都有多种底层编码，Redis 会根据数据量和内容自动选择最优编码。

底层编码与自动转换

  • String：int（整数，8字节长整型）、embstr（短字符串，≤44字节，连续内存分配）、raw（长字符串，SDS）。embstr 的优势是内存连续，一次分配一次释放，缓存友好
  • List：quicklist（Redis 3.2+ 默认），是双向链表和压缩列表的混合。每个节点是一个 listpack（紧凑列表），节点之间用双向链表连接。兼顾了链表的插入效率和压缩列表的内存效率
  • Hash：listpack（小Hash，元素少且值短）、hashtable（大Hash）。listpack 是连续内存，遍历快但插入/删除需要内存搬移；hashtable 是哈希表，O(1) 查找但内存开销大
  • Set：intset（整数集合，全是整数且数量少）、hashtable（其他情况）。intset 是有序整数数组，支持二分查找，内存紧凑
  • ZSet：listpack（小ZSet）、skiplist+hashtable（大ZSet）。跳表实现 O(log n) 的范围查找，hashtable 实现 O(1) 的成员分数查询，两者配合

编码转换阈值由配置控制：hash-max-listpack-entries=128、hash-max-listpack-value=64、zset-max-listpack-entries=128、zset-max-listpack-value=64。超过阈值自动转换为 hashtable/skiplist，但不会自动转回（删除元素后也保持大编码）。

核心数据结构：SDS 与字典

SDS（Simple Dynamic String）：Redis 的字符串实现，相比 C 字符串的优势：

  • 存储长度（len），STRLEN 是 O(1) 而非 O(n)
  • 记录已分配空间（alloc），预分配空间减少内存重分配（增长时翻倍，≤1MB 时翻倍，>1MB 时加 1MB）
  • 二进制安全（不依赖 \0 结尾，可以存储图片、序列化对象等）
  • 兼容 C 字符串函数（末尾仍有 \0）

字典（Dict/HashTable）：Redis 的哈希表实现，用于数据库键空间、Hash 对象、Set 对象等：

  • 使用链式哈希解决冲突，每个桶是一个链表
  • 渐进式 Rehash：扩容时不一次性迁移所有键，而是在每次操作时迁移一部分桶，避免阻塞。同时维护两个哈希表（ht[0] 和 ht[1]），查询时先查 ht[0] 再查 ht[1]
  • 负载因子（load factor）= 已用节点数 / 桶数。超过 1 时扩容（翻倍），低于 0.1 时缩容
  • 扩容条件：没有 BGSAVE/BGREWRITEAOF 时负载因子 ≥1；有子进程时 ≥5（减少写时复制的内存开销）

持久化机制深度解析

Redis 提供三种持久化方式，各有适用场景：

  • RDB（Redis Database）：快照方式，在某个时间点将内存数据写入 dump.rdb。触发方式：SAVE（阻塞）、BGSAVE（fork子进程，非阻塞）、配置 save 900 1（900秒内至少1次修改）。优点：文件紧凑、恢复快；缺点：可能丢失最后一次快照后的数据
  • AOF（Append Only File）：日志方式，记录每个写命令。刷盘策略：always（每条命令都刷，最安全最慢）、everysec（每秒刷，默认，最多丢1秒）、no（由OS决定，最快最不安全）。AOF 文件是文本格式，可以用 redis-check-aof 修复
  • 混合持久化：Redis 4.0+，AOF 重写时前半段是 RDB 格式的全量数据，后半段是增量命令。兼顾 RDB 的恢复速度和 AOF 的数据安全性。由 aof-use-rdb-preamble=yes 控制，默认开启

AOF 重写（Rewrite）：AOF 文件会不断增长，重写生成一个最小化的新 AOF 文件。原理：遍历当前内存数据，生成等效的写命令，而不是读取旧 AOF。使用 BGREWRITEAOF 或配置 auto-aof-rewrite-percentage=100（增长100%时触发）、auto-aof-rewrite-min-size=64mb。重写期间的新命令同时写入旧 AOF 和重写缓冲区。

Redis Cluster 架构

Redis Cluster 是官方的分布式方案，采用无中心节点架构：

  • 数据分片：16384 个哈希槽（slot），每个 key 通过 CRC16(key) mod 16384 计算 slot。每个主节点负责一部分 slot。可以用 {hashtag} 强制多个 key 落在同一 slot（如 user:{1001}:profile 和 user:{1001}:orders）
  • 节点通信：使用 Gossip 协议，每个节点定期向随机节点发送 PING/PONG，交换集群状态信息。节点之间通过 TCP 端口（客户端端口+10000）通信。集群元数据（slot 分配、节点状态）最终一致
  • 故障转移：每个主节点有多个从节点。主节点故障时，从节点通过选举（Raft 算法的变种）提升为主节点。超过半数主节点投票同意才能完成故障转移。cluster-node-timeout 控制节点超时判定（默认 15 秒）
  • 重定向：客户端请求的 key 不在该节点时，返回 MOVED（永久重定向，slot 已迁移）或 ASK（临时重定向，slot 迁移中）。智能客户端（如 Jedis Cluster、go-redis）会缓存 slot 映射，避免每次重定向

内存管理与淘汰策略

键过期与内存淘汰

Redis 的内存管理包含两个机制：

过期键删除：

  • 惰性删除：访问 key 时检查是否过期，过期则删除。优点：CPU 友好；缺点：过期 key 不访问就永远占内存
  • 定期删除：每隔 100ms（hz 控制，默认 10）随机抽取一批设置了过期时间的 key，删除其中已过期的。如果过期比例超过 25%，重复抽取（有时间上限，避免阻塞）
  • 两种方式配合，保证过期 key 最终被删除，但不保证实时性

内存淘汰策略（maxmemory-policy）：当内存达到 maxmemory 时：

  • noeviction：不淘汰，写命令报错（默认）
  • allkeys-lru：所有 key 中淘汰最近最少使用（推荐缓存场景）
  • volatile-lru：设置了过期时间的 key 中淘汰 LRU
  • allkeys-lfu：所有 key 中淘汰最不经常使用（Redis 4.0+）
  • volatile-lfu：过期 key 中淘汰 LFU
  • allkeys-random / volatile-random：随机淘汰
  • volatile-ttl：淘汰 TTL 最短的 key

LRU 实现：Redis 的 LRU 是近似 LRU，不是严格的双向链表。每个 key 记录最后访问时间（24位，精确到秒），淘汰时随机采样 N 个 key（maxmemory-samples=5），淘汰其中最旧的。7.0 引入了 LRU 池（pool），提高淘汰精度。

8大常见陷阱与最佳实践

  1. Big Key 问题：单个 key 的 value 过大（String > 10KB，集合元素 > 5000）会导致：网络传输慢、删除阻塞（大 key 删除是 O(n)）、内存碎片、集群数据倾斜。用 redis-cli --bigkeys 扫描。大 key 拆分：Hash 拆为多个小 Hash，List 用分页，String 压缩后存储
  2. 热 Key 问题：单个 key 访问量过大（秒杀、热点商品），导致单节点 CPU 飙高。解决方案：本地缓存（Caffeine、Go sync.Map）、热 key 复制（key:1、key:2... 随机读）、读写分离（从节点读）、使用 Redis 7.0 的 CLIENT-TRACKING 服务端协助缓存
  3. 缓存穿透/击穿/雪崩：穿透（查询不存在的 key，每次都打到 DB）→ 布隆过滤器或缓存空值（短 TTL）；击穿（热 key 过期瞬间大量请求打到 DB）→ 互斥锁（SETNX）或逻辑过期；雪崩（大量 key 同时过期）→ TTL 加随机偏移、多级缓存、熔断降级
  4. 事务不是原子的：Redis 的 MULTI/EXEC 只是将命令排队批量执行，不支持回滚。如果队列中有命令语法错误，所有命令不执行；如果执行中某命令失败（如类型错误），其他命令继续执行。需要原子性用 Lua 脚本（EVAL），Lua 脚本在 Redis 中是原子执行的
  5. 持久化导致的延迟尖刺：BGSAVE 和 BGREWRITEAOF 都需要 fork 子进程，fork 时会复制页表（大内存实例 fork 耗时可达数百毫秒），期间 Redis 阻塞。降低 fork 开销：控制实例内存（建议 < 10GB）、关闭 THP（Transparent Huge Pages）、使用 rdb-save-incremental-fsync。AOF 的 everysec 刷盘也可能因磁盘 IO 慢导致阻塞
  6. 集群模式下的多 key 操作：Redis Cluster 不支持跨 slot 的多 key 操作（MGET、RENAME、事务、Lua 脚本中的多 key）。如果 key 不在同一 slot，返回 CROSSSLOT Keys in request don't hash to the same slot。解决方案：使用 Hash Tag（{user:1001}:profile）强制同 slot，或在客户端拆分请求
  7. 内存碎片率高：mem_fragmentation_ratio > 1.5 表示碎片严重。原因：频繁更新导致大小变化、Big Key 删除后留下空洞。解决：Redis 4.0+ 支持 ACTIVEMEMORYDEFRAG（自动碎片整理，有 CPU 开销），或重启实例（从节点切换）。jemalloc 的内存分配策略也会影响碎片率
  8. 主从复制风暴：从节点初次同步或断线重连时，如果 repl_backlog_size（复制积压缓冲区，默认 1MB）不够大，会触发全量同步（RDB 传输）。大量从节点同时全量同步会导致主节点带宽和 CPU 飙升。建议增大 repl-backlog-size（如 256MB），从节点分批重启，使用磁盘less复制（repl-diskless-sync=yes，Redis 2.8.22+）
