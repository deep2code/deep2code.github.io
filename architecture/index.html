还有一类问题最好在入手前就排除掉：它其实不属于这个分类。判据与邻接分类的分界见下一节。

② 原理 · 这个分类只谈「跨服务」的设计与治理

「架构」这个词在各处的含义不同。这里把它收窄成一个判据：一旦你的决定需要两个以上的服务同时改、或者涉及消息投递语义与一致性取舍，它就属于这里。语言选型与代码功底在 编程语言与代码功底，对外契约与安全在 接口、协议与安全，发布与运行环境在 运维与云原生，运行中的观测在 可观测性与性能。

这条边界的实际收益是：很多线上问题不是「架构设计不好」，而是某一层的执行细节没对齐——查询慢是数据库层的事、证书过期是运维层的事、接口不兼容是契约层的事。先判断归属，才不会把每个问题都变成「要不要重新架构」。

② 原理 · 服务拆分的代价模型

拆分的收益看得到——独立发布、独立扩容、故障隔离。但代价常被低估：每拆一个服务，就多出一对网络跳、一份独立的部署清单、一套需要发现与路由的地址、一条需要跨服务追踪的链路、以及一个可能在分布式事务里出问题的参与方。决定要不要拆之前，先算清楚这个边界上每天经过多少次调用和回滚时两边能不能独立回退。

一条实用的判据：如果两个模块的变更总是同时发布才能生效，它们就不该是两个服务。这比「领域边界」更容易验证——翻最近二十次变更记录就能看出来。

拆分的收益附带的代价代价的放大条件
独立发布，改动范围缩小每次跨服务调用都是一次网络往返，增加延迟与失败概率调用路径越长、跨服务调用越频繁，放大越明显
独立扩容，资源按需分配多出一套编排清单、一套监控看板、一套值班规则团队人数小于服务数时，运维负担无人承接
故障隔离，一个挂不影响别的跨服务一致性退化为最终一致或需要补偿涉及资金或库存等不能丢的场景时，补偿机制比单体事务复杂一个数量级
技术栈自由选择多语言、多框架的工具链与中间件客户端加倍每多一种语言，安全升级、链路追踪、监控接入都要再做一遍

② 原理 · 一致性与可用性的取舍

CAP 定理被引用了无数遍，但实际系统里的选择不是「CP 或 AP」一刀切。真正要回答的问题是：这一笔数据在写成功后多久被读到，对业务来说可不可接受。从强一致到弱最终一致是一个谱系，每往弱的方向退一步，可用性和延迟都会好一些，但需要在应用层补更多处理。

一致性级别读写的约束常见的实现手段适用场景
线性一致写完后任何读都能看到最新值Raft / Paxos 多副本共识、2PC资金余额、库存扣减这类一笔都不能差的
因果一致有因果关系的操作保持顺序向量时钟或逻辑时钟、会话一致消息流中「先发的先看到」的用户体验
最终一致不承诺延迟，最终能收敛异步复制、消息补偿、定时对账推荐、搜索索引、非关键状态同步

一条常被忽略的事实：两阶段提交（2PC）的不确定态。协调者发出 prepare 后、在 commit 之前挂了，参与者既不能提交也不能回滚，这个状态持续到协调者恢复为止。生产中通常不直接用 2PC，而是用本地事务加消息表实现柔性事务，把不确定性从数据库锁降级为可查询、可重试的消息。详细推演见 柔性事务的实现细节。

② 原理 · 消息中间件在架构里的位置

消息队列最容易被当成「异步化」工具引入，但它真正改变的是时间耦合：调用方不再等待结果。这个收益的另一面是代价：你需要处理消息丢失、重复、乱序，以及消费积压时的止损。

Kafka 在消息中间件里的位置比较特殊：它不删消息、按偏移量重放，这让它同时承担了消息总线、事件日志、流处理输入三种角色。RabbitMQ 和 RocketMQ 在「任务分发」这个场景上更直接——消费即确认、支持优先级与延迟投递。选型时先问业务：是「投递一次、消费即忘」还是「可回溯、可重放」。

② 原理 · 服务治理：让拆出去的服务还能管得住

服务治理不是一套中间件的名字，而是三块需要同时回答的问题：怎么找到对方（注册发现）、配置怎么下发与更新（配置中心）、对方挂了或慢了怎么办（熔断限流与降级）。三者缺一块，拆出去的服务就会变成分布式单点。

治理能力解决的问题不做的后果详细内容
注册发现调用方不硬编码地址，上线即可被发现每次扩容或故障迁移要人工改配置，半夜出问题要先翻 IP服务注册发现的机制与故障模式
配置中心配置与代码分离，热更新不重启改一个超时要发版，开关按钮要跑流水线配置中心的服务端机制 与 应用侧实践
熔断限流下游故障时快速失败而不是跟着一起拖死一个服务变慢，调用方线程池全排队，级联拖垮整条链路熔断限流降级与舱壁隔离
API 网关统一入口层的鉴权、限流、灰度路由每个服务各自实现鉴权和限流，标准不一且难以全局止损API 网关的责任边界

② 原理 · 有状态服务的特殊性

无状态服务可以随意扩缩容和重建，但数据库、消息 broker、分布式缓存这类有状态组件不行——它们的数据必须持久化且与特定实例绑定。在容器编排场景下，有状态服务要额外处理三件事：数据归属（磁盘和网络存储的绑定）、身份稳定（StatefulSet 保证 Pod 名和存储对应关系）、拓扑约束（副本不能落在同一节点）。

一条经验判据：如果一个组件挂了之后，重启需要从某个特定的磁盘恢复数据，它就是有状态的，不能用普通 Deployment 管。具体的 K8s 存储抽象见 Kubernetes 存储抽象与有状态服务。游戏服务器里的有状态进程是极端场景——连接绑定在进程内存上，断了就是状态丢失，见 ET 框架的服务端架构。

场景该怎么做为什么代价
多团队抢同一条发布流水线按限界上下文拆 3 到 8 个粗粒度服务部署单元耦合是拆分唯一能直接解决的问题七类新成本一次性到账，基础设施必须先就位
主链路串了多个非核心下游把非核心步骤收敛成一条领域事件，异步承接下游故障从「整单失败」降级成「消息积压」每个消费组都要自己实现幂等、重试与死信告警
跨服务写入既不能丢也不能重本地事务加 outbox，消费端按业务唯一键幂等，不要用 2PC2PC 的不确定态会把参与方长时间锁住中间态对用户可见，必须配对账与人工补偿入口
资金余额、库存扣减放在同一个关系库的本地事务里，优先不拆线性一致最便宜的实现就是「不跨服务」这块业务的独立伸缩自由度被牺牲掉
搜索索引、缓存、数仓等派生数据单向订阅领域事件，并保证能从头全量重建派生数据的正确性靠可重建保证，不靠每条都不丢保留期花存储钱，重放要限速否则压垮上游
一个下游变慢就拖垮整条链路熔断加舱壁隔离，阈值按下游实测容量反推调用方线程池被排队占满是级联故障的主要形态阈值要随容量变化持续维护，配错比不配更糟
全链路超时没有预算入口定总预算，每跳只能用剩余预算并留收尾余量每层各写死超时，入口预算必被下游突破需要框架层统一透传，改造面覆盖所有服务
数据库、消息 broker、游戏服这类有状态组件用有身份的编排对象或直接用托管服务数据必须与实例绑定，重建后要挂回同一块盘滚动更新变慢，缩容遗留的卷要显式清理
已经拆了服务但几个服务连同一批表停止继续拆：按 schema 隔离、收回直连权限、逐表转交所有者这是分布式单体最典型的形态迁移期要双写并对账，进度会明显变慢
团队不到十人、没有专职 SRE停在模块化单体，先把可观测性与流水线做好运维面是乘性增长的，没人承接就会失控发布仍需协调，但成本远低于维护一套微服务底座

③ 场景 · 五个子方向各自什么时候该读

三条常见路线：要做服务拆分，先读微服务代价模型、再读分布式一致性的取舍、最后进消息通信确定异步边界；已经拆好了但治理不住，先读服务治理再读 Kafka 可靠性；要补分布式基础，从 CAP、Raft、柔性事务读起。

二级方向篇数它解决的问题什么时候该读它
服务治理7注册发现、配置中心、网关、熔断限流降级服务拆出去后发现找不到、配置改不动、一个服务慢全链路拖死时
Kafka7提交日志模型、分区设计、消息可靠性、性能调优要引入事件驱动或消息总线，需要确定投递语义与消费积压处理时
分布式一致性6CAP 与 Raft、幂等的完整实现、柔性事务、限流的分布式实现要在跨服务场景下做可靠写入或一致性保证时

最容易踩的坑

❌
这些坑都要按月计成本才能纠正
  • 按技术分层拆服务（控制层一个、数据层一个），结果每个业务改动都要跨服务发布
  • 两个服务的变更总是一起上线，说明拆错了，但没人敢合回去
  • 只在消费端做幂等、不在生产端做重试，消息丢了没人知道
  • 消息队列引进来了但没人监控消费滞后，积压到磁盘满才暴露
  • 全链路超时没有预算：每层各设 3 秒，五层串起来客户端要等十几秒，重试翻倍
  • 直接用 2PC 做跨服务事务，协调者挂了参与者死锁
  • 有状态服务用无状态方式管，重建后数据丢失才发现没有持久化绑定
  • 熔断阈值凭感觉设，不按下游容量反推，要么太松没保护、要么太紧正常请求也被拦
