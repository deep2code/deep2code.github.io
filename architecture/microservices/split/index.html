微服务拆分实操：绞杀者模式与数据库拆分四阶段

🏷️ 微服务入门

「该不该拆」的账在站内《微服务的代价模型》里算过了。这篇假定账已经算清、决定要拆，讲第一次动手的具体操作：先做什么准备、用什么路径迁移、数据库怎么分步剥离、失去 join 之后查询怎么写、第一个服务该挑哪个、以及怎么判断拆完了。全文围绕一个原则：每一步都必须能在十分钟内回滚。做不到这一点的方案，无论架构图画得多漂亮，都不要采用。

动手之前必须完成的三件事

这三件事没做完就开始拆，基本等于在没有麻醉和监护设备的条件下做手术。它们的共同点是：都可以在单体时代完成，而且单体本身也会因此受益——所以不存在「等拆的时候再一起做」的理由。

准备项具体产出物验证方式（做到这个才算完成）跳过的后果
理清单体内部的模块边界 一份模块清单，标明每个模块对外暴露的接口、拥有的表、依赖的其他模块 CI 里跑架构测试，禁止跨模块直连内部实现与共用领域实体，全绿通过 拆出来的服务边界就是随机的，三个月后发现要重拆
找出所有跨模块的数据库访问 一份跨模块 join 与跨模块写入的清单，逐条标注替代方案 把待拆模块的表放进独立 schema 并收回其他账号权限，全量回归无报错 上线后才发现某个报表任务在直连你的表，一改表结构就炸
基础设施先就位 注册发现、配置中心、网关、链路追踪、日志聚合、指标告警、流水线模板、本地联调编排 新建一个空服务，从生成代码到上线加可观测，全流程半天内走通 第一次线上慢请求就定位不了，然后有人在代码里写死下游 IP

第二件事最容易被低估。跨模块查询往往藏在报表、定时任务、运营后台和数据同步脚本里，这些代码没人维护、没有测试、但一旦断掉就会有人来找你。先把它们扫出来：

# 1. 扫代码里跨模块直读对方表的 SQL（示例：找 order 模块里出现 user_ / item_ 表的地方）
grep -rInE 'from[[:space:]]+(user_|item_|promo_)' --include='*.java' --include='*.xml' \
     --include='*.go' --include='*.py' src/main/java/com/shop/order/ | tee cross_module_sql.txt

# 2. 更可靠的办法：从数据库侧看谁在碰待拆模块的表（MySQL 8.0，需开启 performance_schema）
mysql -e "SELECT DIGEST_TEXT, COUNT_STAR, SUM_ROWS_EXAMINED
          FROM performance_schema.events_statements_summary_by_digest
          WHERE DIGEST_TEXT LIKE '%inventory_stock%'
          ORDER BY COUNT_STAR DESC LIMIT 50"

# 3. 揪出连库的应用账号与来源 IP，确认到底有几个系统在读这批表
mysql -e "SELECT user, SUBSTRING_INDEX(host,':',1) AS ip, COUNT(*) AS conns
          FROM information_schema.processlist GROUP BY user, ip ORDER BY conns DESC;"

# 判读要点：
#   COUNT_STAR 高但 SUM_ROWS_EXAMINED 也高的语句，迁移后很可能需要 CQRS 读模型；
#   只出现在凌晨时段的账号通常是报表或对账任务，这类调用方最容易被遗漏。

绞杀者模式：唯一可行的渐进路径

迁移路径只有两个选项：绞杀者模式（Strangler Fig），或者停下来重写。后者失败率极高，原因有三条，每一条都足以致命：业务不会停，老系统持续加需求，新系统永远在追一个移动的目标；老代码里的怪异逻辑多半是历史故障的补丁，重写时这些隐性规则会集体丢失，上线后以线上事故的形式逐条重现；大爆炸切换没有中间态，出问题只能硬扛，没法回滚。绞杀者模式的全部价值就在于：它把一次巨大的不可逆风险，切成几十次可回滚的小风险。

下面是绞杀者路由的最小可用 nginx 配置，三种分流维度都给了：路径前缀（新功能）、灰度比例（按用户 ID 哈希稳定分流，避免同一用户来回抖动）、以及请求头强制指定（供测试和排障用）。

# ========== 绞杀者路由：新服务与老单体共存 ==========
upstream monolith    { server 10.0.1.11:8080 max_fails=2 fail_timeout=10s; keepalive 64; }
upstream order_svc   { server 10.0.2.21:8080 max_fails=2 fail_timeout=10s; keepalive 64; }

# 按用户 ID 哈希做稳定灰度：同一用户永远落在同一侧，避免一会儿新一会儿老
# 取 cookie 里 uid 的末两位，00 到 09 即为 10% 灰度
map $cookie_uid $uid_bucket {
    default            "99";
    "~(?P<b>\d{2})$"   $b;     # 命名捕获取末两位
}
map $uid_bucket $order_canary {
    default      "off";
    "~^0[0-9]$"  "on";          # 放量时把这行改成 0[0-9]|1[0-9] 即 20%
}

# 请求头强制指定，优先级最高，给测试和排障用：X-Route-Target 取值 new 或 old
map $http_x_route_target $route_override {
    default  "";
    "new"    "new";
    "old"    "old";
}

server {
    listen 80;

    # --- 规则1：新功能路径 只存在于新服务，直接路由 ---
    location /api/v2/orders/ {
        proxy_pass http://order_svc;
        include proxy_common.conf;
    }

    # --- 规则2：老功能路径 按灰度与强制头决定去向 ---
    location /api/v1/orders/ {
        set $target "monolith";
        if ($order_canary = "on")     { set $target "order_svc"; }
        if ($route_override = "new")  { set $target "order_svc"; }
        if ($route_override = "old")  { set $target "monolith"; }
        proxy_pass http://$target;
        include proxy_common.conf;

        # 新服务出问题时自动回落老单体：这是绞杀者期间最有价值的一行
        proxy_next_upstream error timeout http_502 http_503 http_504;
    }

    # --- 规则3：其余全部回落单体，保证没迁的功能零影响 ---
    location / {
        proxy_pass http://monolith;
        include proxy_common.conf;
    }
}

# proxy_common.conf 该写什么：
#   proxy_http_version 1.1;          必须，否则上游长连接失效
#   proxy_set_header Connection "";  清掉 close，让 keepalive 生效
#   proxy_set_header X-Request-Id $request_id;   与链路追踪对齐
#   proxy_set_header X-Route-Side  $target;      让日志能看出这次走了哪一侧
#   proxy_connect_timeout 1s; proxy_read_timeout 3s;   超时预算必须显式设
⚠️
灰度分流最常见的两个错误

第一，用随机数或轮询做灰度。同一个用户这次走新服务、下次走老单体，如果两侧数据还没完全同步，用户会看到数据一会儿有一会儿没有，客诉会立刻爆。必须按用户 ID 之类的稳定键哈希。第二，灰度只切读不切写就宣布完成。读路径通过说明查询逻辑对了，写路径才是真正的风险点，它涉及事务边界、唯一约束冲突和补偿逻辑，必须单独灰度并配影子比对。

数据库拆分：四个阶段，每阶段一个验证动作

这是整个拆分里最难、最慢、最容易半途而废的一步。半途而废的结果就是分布式单体：代码拆了，几个服务还连着同一批表。四个阶段必须按顺序走，每阶段有明确的验证动作，验证不过就不许进下一阶段。

阶段做什么验证方式回滚成本典型卡点
1 共享库共享表 新服务先连老库，代码层约定只读写属于自己的表 审计 SQL 日志，确认新服务没有写别人的表、没有跨模块 join 接近零，改回单体调用即可 约定靠自觉，很容易被一句「先临时 join 一下」破掉
2 按 schema 隔离 表迁进独立 schema，回收其他账号对它的读写权限 全量回归加跑一遍所有定时任务与报表，越权访问必须报错而非静默成功 低，重新授权即可恢复 会暴露出一批没人知道的调用方，这正是本阶段的目的
3 独立实例双写 新库独立部署，业务写两边，读仍以老库为准 影子读：同一请求同时读两边并比对，差异率与差异样本上报监控 中，关掉双写并切回单读 双写的原子性问题：两边写一边失败怎么办，必须有补偿与对账任务
4 完全独立 切读到新库，停写老库，老库转只读 切读按灰度比例推进；老库连接数与 QPS 降到零维持一周 高，需要反向补数据 历史数据迁移的存量与增量衔接，以及自增 ID 冲突

阶段 2 的权限收口是几条命令的事，但效果最大——它把「看不见的依赖」变成「立刻报错的依赖」：

-- 阶段2：把待拆模块的表迁入独立 schema，并只给它自己的账号授权
CREATE DATABASE inventory_db DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;

-- 在线搬表：RENAME 是元数据操作，通常毫秒级完成，但会等待现有事务与 MDL 锁，
-- 务必在低峰执行，并先确认没有长事务（查 information_schema.innodb_trx）
RENAME TABLE shop_db.inventory_stock TO inventory_db.inventory_stock,
             shop_db.inventory_lock  TO inventory_db.inventory_lock;

-- 只给库存服务自己的账号完整权限
GRANT SELECT, INSERT, UPDATE, DELETE ON inventory_db.* TO 'app_inventory'@'10.0.%';

-- 其他服务的账号：一律不授权。它们的越界查询会立刻收到 1142 权限错误，
-- 报错总比悄悄读到脏数据好，这就是本阶段的全部意义
REVOKE ALL PRIVILEGES ON inventory_db.* FROM 'app_order'@'10.0.%';

-- 过渡期兜底：只读账号加视图，给报表与对账任务一条临时通道，并登记在案，
-- 便于后续逐个改造成走接口（视图不给写权限，避免又变成隐式写依赖）
CREATE VIEW shop_db.v_inventory_stock_ro AS
    SELECT sku_id, available_qty, updated_at FROM inventory_db.inventory_stock;
GRANT SELECT ON shop_db.v_inventory_stock_ro TO 'app_report'@'10.0.%';

FLUSH PRIVILEGES;

阶段 3 的双写要配影子读，否则你永远不知道两边到底一致没有。下面这段是可以直接抄的写法，重点在三处注释标出的判断：主写失败要立即抛错、影子写失败只告警不影响主流程、以及差异采样必须限流。

// 阶段3 双写加影子读比对。原则：老库是唯一真相源，新库失败绝不影响业务
type DualWriteRepo struct {
    old, new  StockRepo
    diffRate  *ratelimit.Limiter // 差异日志限流，防止不一致时日志把磁盘打满
    metrics   Metrics
}

func (r *DualWriteRepo) Deduct(ctx context.Context, skuID string, qty int) error {
    // 主写：失败直接返回，业务语义以老库为准
    if err := r.old.Deduct(ctx, skuID, qty); err != nil {
        return err
    }
    // 影子写：异步加独立超时，绝不让新库的抖动拖慢主流程
    go func() {
        c, cancel := context.WithTimeout(context.Background(), 500*time.Millisecond)
        defer cancel()
        if err := r.new.Deduct(c, skuID, qty); err != nil {
            r.metrics.Inc("dual_write_new_fail") // 靠对账任务补齐，不在这里重试到死
        }
    }()
    return nil
}

func (r *DualWriteRepo) Get(ctx context.Context, skuID string) (Stock, error) {
    got, err := r.old.Get(ctx, skuID) // 读仍以老库为准
    if err != nil {
        return got, err
    }
    go func() { // 影子读比对：只统计差异率，不参与返回
        c, cancel := context.WithTimeout(context.Background(), 300*time.Millisecond)
        defer cancel()
        shadow, e := r.new.Get(c, skuID)
        switch {
        case e != nil:
            r.metrics.Inc("shadow_read_err")
        case shadow.AvailableQty != got.AvailableQty:
            r.metrics.Inc("shadow_read_diff")
            if r.diffRate.Allow() { // 采样打印，便于定位而不刷爆日志
                log.Printf("shadow diff sku=%s old=%d new=%d", skuID, got.AvailableQty, shadow.AvailableQty)
            }
        default:
            r.metrics.Inc("shadow_read_same")
        }
    }()
    return got, nil
}

// 进入阶段4 的判据：shadow_read_diff 连续七天为 0，
// 且这七天覆盖过一次大促或月结这类极端流量场景。只跑三天的比对不算数。

双写本身不是原子的，两边写一边成功一边失败是常态，所以必须有独立的对账任务兜底。这类一致性方案的取舍（本地消息表、TCC、Saga、幂等的四种落地）详见站内分布式一致性深度原理，这里不重复。

失去 join 之后：跨服务查询的三种替代

拆库之后最先撞墙的不是写路径，而是「订单列表要显示商品名和用户等级」这种再普通不过的查询。三种替代方案的适用场景差别很大，选错会直接体现在接口延迟上。

方案一致性延迟影响实现复杂度适用场景失效条件
API 聚合调用 强，读到的是各服务当前值 各次调用延迟之和；并行化后取最大值再加聚合开销 低 字段少、单条或小批量、对实时性要求高 需要按对方字段过滤或排序分页时彻底失效，因为你无法在内存里正确分页

❌
聚合调用最经典的翻车姿势

订单列表一页 100 条，对每条记录各调一次用户服务查昵称。原来一次 join 变成 100 次 RPC：延迟从 5 毫秒变成 200 毫秒以上，而且用户服务的 QPS 被放大 100 倍，稍有抖动整页就失败。正确做法是收集全部 ID 后调一次批量接口，并在批量接口上限制单次 ID 数量（通常 100 到 500），超出就分批。这个坑在拆分后的第一周必然出现，最好在契约设计阶段就规定：任何跨服务查询接口都必须提供批量版本。

第一个拆出来的服务该选哪个

第一次拆分一定会犯错：契约设计会返工、部署方式会调整、监控埋点会漏、回滚流程会在真出事时才发现不通。所以第一个服务的选择标准不是「最需要拆的」，而是「拆坏了也不影响核心业务的」。用下面这张打分表评估候选模块，四项全绿才动手。

候选模块边界清晰度对外依赖数变更频率在主链路上结论
通知中心（短信、推送、站内信）高，输入就是一条消息少，只被调用不调用别人高，渠道和模板常改否，失败可重试最佳首选
文件与图片服务高，职责单一少中否好选择
导出与报表高，纯读多但都是读高否好选择，顺带验证 CQRS 读模型
营销活动页中中极高，一次大促改十次否，可降级为不展示可选，变更频繁收益明显
商品中心中多，几乎人人读它中是第二轮再拆
用户中心低，鉴权与资料与权限常混在一起极多，全站依赖源头低是不要第一个拆
订单低，数据关系最密集极多，报表与对账都直连它的表高是，核心中的核心不要第一个拆

为什么用户中心和订单是最差的起手：用户中心是依赖源头，几乎每个接口都要查它，它一抖动全站抖动，而且第一次拆分时你的熔断降级配置一定还没调好；订单是数据关系最密集的模块，它的表被大量报表、对账、风控任务直连，拆它等于把「最难的数据迁移」和「最高的故障影响」叠在一起做。这两个应该放在第三、第四轮，那时你已经踩完了所有基础设施的坑。

还有一条容易被忽略的判据：宁可先拆粗。边界划错时，合并两个服务只需要把代码搬到一起、把两个库合成一个，是一次可控的重构；而把一个服务再拆开，要重做数据迁移、契约设计和调用方改造，成本差一个数量级。所以有疑虑时就往粗的方向选，粗粒度服务将来发现内部确实需要独立伸缩，再切一次也不晚。

拆分过程中必须同步建立的四件事

这四件事不是「拆完再补」的收尾工作，而是和拆分动作同时进行的配套。缺任意一件，拆分都会退化成协同发布地狱。

配套最低要求落地方式缺失时的现场
契约管理 接口定义有单一来源，变更可评审、可追溯 proto 或 OpenAPI 文件独立仓库管理，代码由它生成而不是反向导出 文档和实现不一致，调用方按文档写完发现字段名不对
版本兼容策略 只加不删、不改语义；删字段前先确认无调用方 CI 卡住破坏性变更；新增字段给默认值；路径带 v1 v2 并行一段时间 任何变更都要多个服务同时发布，这就是分布式单体
集成与契约测试 提供方每次提交都验证自己没破坏已知消费者的期望 消费者驱动契约（Pact 之类）在提供方流水线里回放；关键主流程保留端到端用例 破坏性变更要等到联调或线上才发现
灰度与回滚 流量比例可秒级调整，任何变更都能在十分钟内回退 灰度开关放配置中心；数据变更遵循先兼容读、再切写、最后清理 出问题只能硬改代码重新发布，故障时长从分钟变成小时

拆分完成的判定标准，以及假拆分的识别

很多团队宣布「微服务改造完成」，其实只完成了代码目录的拆分。用下面四条硬标准自查，全部满足才算真的拆完。

判定标准怎么验证（可执行的动作）假拆分的表现
能独立发布 翻最近 10 次上线记录，看有几次需要协调其他流水线；再问能否单独回退一个版本 上线要按顺序协调三条流水线，回滚必须一起回
有独立数据 查数据库账号授权，确认它的表只有它自己的账号能写；搜代码里有无跨服务 join 几个服务连同一批表，改表结构要群里通知
故障能隔离 在预发环境把它停掉，看主流程还能不能通过降级走通 停掉任一服务全站不可用，等于强依赖没治理
团队独立负责 问一句：这个服务的需求、发布、值班、容量规划是不是同一个小队的 服务有五个团队提交代码，出事故没人是 owner
✅
一份可以照着走的迁移检查单

动手前：模块清单与架构测试全绿、跨模块查询清单逐条有替代方案、新建空服务半天能上线并带全套可观测。迁移中：网关插好且能按稳定键灰度、影子比对指标在看板上、每一步都验证过回滚路径真的可用。收尾时：老库连接数归零并保留两周、老单体路由摘除后观察一周、跨模块临时视图逐个改成走接口、把这次踩的坑写进下一个服务的脚手架模板。

最容易踩的坑

❌
这些坑每一条都会让拆分停在半路
  • 停下来重写：业务不停、隐性规则丢失、没有中间态可回滚，三条叠加基本必败，只能用绞杀者模式。
  • 只拆代码不拆数据：几个服务连同一批表，这是分布式单体最典型的形态，也是最常见的半途而废。
  • 灰度用随机数而不是稳定哈希：同一用户一会儿走新服务一会儿走老单体，数据未完全同步时客诉立刻爆。
  • 只灰度读不灰度写：读通过只证明查询逻辑对了，写路径才涉及事务边界、唯一约束和补偿，必须单独灰度。
  • 把一次 join 改成多次 RPC：列表页对每条记录各调一次下游，延迟涨几十倍且把下游 QPS 放大百倍。
  • 冗余了不该冗余的字段：库存可用量、账户余额这类强实时数据一旦冗余，业务就会基于过期值做决策。
  • 双写没有对账任务：两边写一边失败是常态，不做定时对账，不一致会一直累积到有人来投诉。
  • 影子比对只跑三天就宣布一致：必须覆盖一次大促或月结，极端流量下才会暴露并发与时序问题。
  • 第一个就拆用户中心或订单：一个是全站依赖源头，一个是数据关系最密集，初期基础设施还不成熟时风险最高。
  • 一上来就拆细：粒度错了合并比再拆便宜一个数量级，所以有疑虑时一律往粗的方向选。
  • 老库迟迟不下线：保留「以防万一」的双份数据超过一个月，就一定会有人偷偷去读它，拆分等于没做完。
  • 迁移期不做双向回落：网关没配上游失败自动回落老单体，新服务一次发布事故就变成一次线上故障。
  • 忘记报表与定时任务：凌晨跑的对账脚本直连了你要拆的表，切库当晚才发现，而那时没人值班。
