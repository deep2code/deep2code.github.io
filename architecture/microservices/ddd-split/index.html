DDD 战略设计：限界上下文怎么找

🏷️ DDD 拆分

服务边界划在哪里，决定了拆分之后是获得独立演进能力，还是得到一堆必须同时发布的分布式模块。DDD 是目前唯一成体系的边界发现方法，但它被误用的程度也惊人。这篇只谈一件事：限界上下文怎么找。该不该拆见站内《微服务的代价模型》，怎么动手迁移见《微服务拆分入门》。

先澄清最大的误解：DDD 值钱的是战略设计

绝大多数「我们落地了 DDD」的项目，做的事情是：建三个包——domain、application、infrastructure，把原来的 DAO 改名叫 Repository，给每个实体加一个只有 getter 和 setter 的类，然后宣布完成。半年后代码依然改一处崩三处，因为从头到尾没人讨论过边界应该划在哪。战术模式是在边界内部组织代码的手法，它替换成别的写法系统照样能跑；战略设计决定的是边界本身，划错了后面所有工作都在错误的地基上进行。

统一语言：同一个词含义漂移的地方就是边界

统一语言不是「建一个术语表」，而是「在一个上下文内，同一个词只有一个含义，且开发说的和业务专家说的是同一件事」。注意前半句的限定语：它只要求在上下文内部统一，不要求全公司统一。恰恰相反，跨上下文的含义差异是正常的、健康的，而且它正是边界的信号。拿最常见的「商品」举例：

上下文商品指什么关键属性不变量变更原因
商品中心可售卖的 SKU 与它的类目规格标题、类目、规格项、图文详情、上下架状态同一类目下规格项必须完整；下架商品不可被搜索运营编辑商品资料、类目体系调整
库存一个编码加一个可用数量SKU 编码、可用量、预占量、仓库维度可用量不得为负；预占量之和不超过总量出入库、下单预占、取消释放
订单下单那一刻的名称与价格快照商品名、单价、数量、优惠分摊金额一旦生成永久不可变，否则历史订单会被改价只在下单时写入一次
营销一个可参与活动的对象活动资格、互斥关系、限购数、参与门槛同一订单不可叠加互斥活动活动创建与调整，与商品资料无关
搜索推荐一篇待索引的文档分词字段、权重、销量与评分等排序特征索引可重建，允许与源库存在秒级延迟特征工程调整、索引结构升级

五个上下文说的都是「商品」，但属性集、不变量、生命周期、变更原因全都不同。如果强行用一个商品类同时满足五种含义，它会长到两百个字段、被五个团队同时修改、任何字段变更都要通知所有人——这就是上帝模型的来历。判断信号很具体：当你为了让一个模型适应另一个场景而不断加字段、加可空判断、加分支时，你正在跨越一条本该存在的边界。

限界上下文的四种识别方法

四种方法互相印证，不要只用一种。事件风暴负责穷举、业务流程负责验证、名词漂移负责定界、组织结构负责校准落地可行性。

第四种方法最常被忽略，也最致命：康威定律——系统结构会趋同于组织沟通结构。如果你画的服务边界和团队边界不一致，最终一定是架构被改回去迁就组织，而不是反过来。一个由前端组、后端组、DBA 组横向切分的团队，去做纵向的业务服务拆分，每个服务上线都要三个组协作，那么这些服务本质上还是一个部署单元。组织不改，架构改不动。反过来这也给了一条实用推论：想验证边界是否可行，就看能不能给每个上下文指派一个唯一的、端到端负责的小队；指派不出来，这个边界就是纸上的。

上下文数量的一个经验刻度

一个中等规模的电商系统，限界上下文通常在 8 到 15 个之间。少于 5 个，说明粒度太粗，多半只是把「前台后台」这类技术划分当成了上下文；多于 25 个，几乎必然是把聚合误当成了上下文——聚合是事务边界，上下文是模型与语言边界，前者通常一个上下文里有好几个。一个可以自查的标准：如果两个所谓的上下文共用同一份术语表、同一个业务负责人、且需求总是成对出现，它们其实是一个。

上下文映射：五种最实用的模式

上下文映射原书有九种模式，实际项目里用得最多的是下面五种。选错模式的后果通常不是立刻报错，而是半年后发现两个服务永远要一起发布。

模式关系本质耦合程度适用场景真实代价与失效条件
共享内核 Shared Kernel 两个上下文共同拥有并共同维护一小块模型 最高 仅限极稳定的概念：用户标识、金额与币种、时间与时区、错误码协议 任何改动要双方同时评审与发布，等于把两个服务的发布周期绑在一起；一旦有人往里塞业务规则，它会迅速膨胀成上帝模块，此时共享内核就失效了
客户与供应商 Customer-Supplier 上游供应能力，下游提需求，双方就接口协商排期 中 同一公司内有明确上下游关系且沟通顺畅，例如订单对库存 依赖上游团队的排期意愿；上游一旦被公司重点项目占满，下游需求会被无限期挂起，此时要退化成防腐层自保
防腐层 Anticorruption Layer 下游自建一层翻译，把上游模型转成自己的模型 低 对接遗留系统、第三方服务、无法协商的强势上游 要额外写和维护翻译层，且翻译层本身需要测试；但这是对接不可控上游时唯一能保住自己模型的方式
发布语言 Published Language 约定一套公开的、版本化的交换格式，多方按它集成 低 一个事实要被多方消费：领域事件、开放平台接口、对外 API 格式演进必须严格向后兼容，只加不删；版本管理跟不上时，加一个字段就会打断所有消费者
各行其道 Separate Ways 干脆不集成，各自实现 无 集成收益低于集成成本，例如内部工具各自做简易报表 会产生重复实现与数据口径不一致；但当集成的协调成本高到离谱时，这往往是理性选择

防腐层是这五种里最该无条件采用的一种。第三方支付回调是最典型的场景：字段名混乱、金额是以分为单位的字符串、状态是含义过期的数字枚举、还会重复回调。如果把它的响应对象直接在业务代码里传递，那么对方一次升级你就要改十几处，而且你的领域模型会永久携带一堆与自己业务无关的概念。

// 防腐层：把第三方支付的报文翻译成自己的领域概念
// 收益在更换供应商时最明显——新增一个 Adapter 实现，领域代码一行不动
public interface PaymentGateway {                 // 这是「我的」语言
    PaymentResult charge(PaymentCommand cmd);
    Optional<PaymentResult> parseCallback(String rawBody, Map<String, String> headers);
}

@Component
class AlipayAdapter implements PaymentGateway {   // 这是防腐层

    @Override
    public Optional<PaymentResult> parseCallback(String rawBody, Map<String, String> headers) {
        // 1. 验签必须在最外层，未验签的报文一律不进入领域模型
        if (!signer.verify(rawBody, headers.get("X-Signature"))) {
            throw new IllegalCallbackException("signature mismatch");
        }
        AlipayNotify raw = json.read(rawBody, AlipayNotify.class);

        // 2. 单位换算收口在这里。对方用「分」的字符串，我的领域用 Money 值对象，
        //    绝不允许分值裸奔到业务代码里，那是精度事故的源头
        Money amount = Money.ofCents(Long.parseLong(raw.getTotalAmountCents()), raw.getCurrency());

        // 3. 状态映射收口在这里。对方的数字枚举文档常年过期，
        //    遇到未知值必须显式失败并告警，而不是 default 成成功
        PaymentStatus status = switch (raw.getTradeStatus()) {
            case "TRADE_SUCCESS", "TRADE_FINISHED" -> PaymentStatus.PAID;
            case "WAIT_BUYER_PAY"                  -> PaymentStatus.PENDING;
            case "TRADE_CLOSED"                    -> PaymentStatus.CLOSED;
            default -> throw new UnknownUpstreamStatusException(raw.getTradeStatus());
        };

        // 4. 重复回调去重也在这里。支付方通常只保证至少一次投递，
        //    以对方流水号做唯一键，重复则直接返回空，不打扰领域层
        if (!dedup.firstSeen("alipay:" + raw.getTradeNo())) {
            return Optional.empty();
        }
        return Optional.of(new PaymentResult(
                PaymentId.of(raw.getOutTradeNo()), status, amount, raw.getGmtPayment()));
    }
}

聚合设计：三条规则与过大聚合的真实代价

聚合是 DDD 战术模式里唯一影响到架构层面的概念，因为它定义了事务边界。三条规则：聚合是一致性边界，所以一个事务只修改一个聚合实例；聚合之间用 ID 引用而不是对象引用；聚合尽量小，理想是一个聚合根加少量直接受其不变量约束的子实体。

设计选择看起来的好处实际后果正确做法
店铺作聚合根，几万商品放进同一聚合 「一个店的数据都在一起」 改一个商品价要加载并锁住整个店铺聚合，同店铺修改全部串行，乐观锁冲突率极高并引发重试风暴 商品自己就是聚合根，店铺只保留店铺 ID 引用
订单聚合内直接持有商品对象 「取商品名方便」 加载订单时把商品整棵树拽进内存；商品改名会影响历史订单显示 持有 SKU 编码加下单时的名称价格快照，快照天然不可变
一个事务里同时改订单与库存两个聚合 「强一致，省事」 两个聚合若在同一库还能跑，拆服务时这段代码必须重写；跨库则直接退化成分布式事务 改一个聚合，另一个用领域事件驱动，接受最终一致
聚合内集合无上限，例如订单含万级明细 「建模自然」 每次加载都全量读取集合，内存与延迟随集合增长线性恶化 为集合设上限并做业务约束，超限则拆成多个聚合或另建关联 
// 聚合根示范：一个事务只改它自己，跨聚合通过 ID 引用与领域事件协作
public class Order {                  // 聚合根
    private final OrderId id;
    private OrderStatus status;
    private final List<OrderLine> lines;   // 子实体：受订单不变量约束，随订单一起加载
    private final BuyerId buyerId;         // 跨聚合：只存 ID，不存整个买家对象
    private final List<DomainEvent> events = new ArrayList<>();
    private long version;                  // 乐观锁版本号，聚合是并发控制的单位

    // 业务规则写在聚合内部，而不是散落在 service 里——这才是充血模型的意义
    public void pay(Money paid, Instant at) {
        if (status != OrderStatus.CREATED) {
            throw new IllegalStateTransition(id, status, OrderStatus.PAID);
        }
        if (!paid.equals(totalAmount())) {         // 不变量：支付金额必须等于应付
            throw new AmountMismatch(id, totalAmount(), paid);
        }
        this.status = OrderStatus.PAID;
        // 库存扣减、发货、发通知都不在这个事务里做，只发事件
        events.add(new OrderPaid(id, buyerId, snapshotLines(), paid, at));
    }

    // 注意没有 setStatus。任何能让聚合进入非法状态的写方法都不该存在，
    // 加上 setter 之后，状态机约束就形同虚设了
    public List<DomainEvent> pullEvents() {
        List<DomainEvent> out = List.copyOf(events);
        events.clear();
        return out;
    }
}

// 应用服务：加载一个聚合、调用它、保存它、发布事件。就这四步，不要在这里写业务规则
@Transactional
public void payOrder(OrderId id, Money paid) {
    Order order = orderRepo.loadForUpdate(id);        // 按聚合加载，带版本号
    order.pay(paid, clock.instant());
    orderRepo.save(order);                            // 版本号冲突则整体回滚，由调用方重试
    // 与业务数据同事务写入本地消息表，保证「改了聚合」与「发了事件」不会只发生一半
    outbox.append(order.pullEvents());
}

上面最后两行是关键：聚合状态变更与事件发送必须原子，否则会出现「订单已支付但库存永远收不到通知」。实现手法是本地消息表配合独立投递进程，这类方案的对比与幂等的四种落地详见站内分布式一致性深度原理，本文不展开。

DDD 的适用边界：什么项目上了纯属负担

DDD 有明确的成本：建模会议要占用业务专家的时间、代码量比直接写 CRUD 多三成、团队需要一段共同学习期。这些成本只有在业务规则足够复杂时才能被收益覆盖。

项目类型值不值得上 DDD判据更合适的做法
后台管理、数据录入、配置系统不值得业务逻辑基本是字段校验加权限判断，没有状态机也没有跨实体不变量直接分层加 CRUD，把精力放在权限与审计上
报表与数据分析不值得纯读、无写模型、无不变量直接写 SQL 或建读模型，别硬套聚合
交易、履约、结算、风控值得状态机复杂、有大量跨实体不变量、规则会持续演化且改错要赔钱完整用战略加战术设计
保险、医疗、供应链值得领域术语专业且业务专家不可替代，开发无法凭常识猜规则先做统一语言与事件风暴，再谈代码
早期创业产品，需求每周推翻暂时不值得模型还没稳定，建模成果的折旧速度快于产出速度先快速验证业务，稳定后再补建模

还有两个前置条件常被忽略：需要业务专家持续参与——如果建模会只有开发在场，产出的统一语言只是开发的自我想象；团队要有共同语言基础——一半人理解聚合是一致性边界、另一半人理解聚合是一个大对象，讨论会永远在打转。这两条不满足时，DDD 会退化成一套没人真正遵守的目录规范。

✅
落地顺序：先做能立刻见效的那三件

不要从代码结构改起。顺序是：先开一次有业务专家在场的事件风暴，产出事件时间线与术语表；再据此画上下文地图，并为每个上下文指派唯一归属团队，指派不出来的边界当场重划；最后才在模块化单体里按上下文分包，用 CI 里的架构测试守住依赖方向。走完这三步，就算一个微服务都没拆，团队沟通成本和改一处崩三处的问题也会明显改善——而且此时若要拆分，边界已经是现成的。

反模式对照表

反模式典型表现为什么没用修正方向
DAO 改名叫 Repository 接口方法还是按条件查询、按主键更新，参数是表字段 仓储的语义是「按聚合整体存取」，按字段增删改查只是换了个名字的 DAO 仓储只暴露按聚合根 ID 加载与保存整个聚合，查询需求走独立的查询模型
贫血模型套聚合外壳 聚合类只有 getter 和 setter，规则全在领域服务里 加了 setter 就等于任何人都能让聚合进入非法状态，不变量无处可守 把状态变更方法写进聚合并删掉 setter，业务规则跟着不变量走
按技术分层而不是按业务分包 顶层包是 controller、service、mapper，业务模块散落在每层里 一个业务变更要横跨所有层的目录，边界在物理结构上不可见，也无法用架构测试守护 顶层按上下文分包，每个上下文内部再分层，跨上下文只允许依赖对方的 api 子包
一个限界上下文拆成十个微服务 同一个上下文内的实体各自成服务，它们共享不变量却分布在不同进程 同一致性边界被拆开后，本地事务变成分布式事务，收益为零成本翻倍 一个限界上下文默认对应一个服务，只有确有独立伸缩需求时才在内部再切
全公司一套统一模型 建一个公共 domain 包，所有服务共用商品类与用户类 共享模型等于共享耦合，改一个字段要全体回归，这是最隐蔽的分布式单体成因 每个上下文持有自己的模型，跨界只传输发布语言定义的数据结构
把事件当远程方法调用用 事件名叫「创建发货单命令」，发出后还要等对方回结果 这是伪装成事件的同步调用，既没有解耦也丢了可追溯性 事件必须是已发生的事实且用过去式命名，需要立即结果就老实用同步接口

最容易踩的坑

❌
这些坑几乎每个号称落地 DDD 的项目都踩过
  • 只搬战术模式不做战略设计：建了三个包、改了类名，边界一如既往混乱，还多背了一层样板代码。
  • 追求全公司统一模型：共享商品类与用户类，改一个字段全体回归，这是最隐蔽的分布式单体成因。
  • 建模会没有业务专家参与：产出的统一语言只是开发的自我想象，上线后被业务方一句话推翻。
  • 把共享内核当便利工具：一旦往里塞业务规则，它会膨胀成人人都要改的上帝模块，两个服务从此绑定发布。
  • 对接第三方不建防腐层：对方字段名一改你就要动十几处代码，领域模型里长期躺着一堆外部概念。
  • 聚合设计过大：店铺聚合含几万商品，改一个价锁住整店，乐观锁冲突率飙升并引发重试风暴。
  • 聚合之间用对象引用：加载一个订单顺带把商品、用户、店铺整棵树拽进内存，延迟随数据增长恶化。
  • 一个事务改多个聚合：同库时侥幸能跑，拆库后直接退化成分布式事务，这段代码必须全部重写。
  • 聚合里保留 setter：状态机约束形同虚设，总会有人绕过业务方法直接改状态，然后出现不可能存在的订单。
  • 聚合变更与事件发送不在同一事务：出现订单已支付但库存永远收不到通知，且没有任何报错。
  • 事件用命令式命名：叫「创建发货单」这种名字暗示调用关系，实际上应该是「订单已支付」这样的已发生事实。
  • 忽视康威定律：按业务纵向划边界但团队仍横向分组，每个服务上线都要三个组协作，等于没拆。
  • 一个限界上下文拆成十个服务：同一致性边界被拆散，本地事务变分布式事务，成本翻倍收益为零。
  • 在 CRUD 系统上硬套 DDD：没有状态机也没有跨实体不变量，聚合与仓储只是给团队增加负担。
