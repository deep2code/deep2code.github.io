消息可靠投递：五个丢失点与跨产品通用防法

🏷️ 可靠投递

「消息不丢」不是一个开关，而是链路上五个独立环节各自都要做对。任何一环漏掉，其他四环配得再完美也会丢。这篇讲跨产品通用的原理，并落到 RabbitMQ 与 RocketMQ 的具体机制上；Kafka 侧的 acks 与 min.insync.replicas 组合、幂等 Producer、事务边界见站内 Kafka 可靠性专篇，这里只给结论。

① 用法 · 五个丢失点逐点验证：这张清单跑完再上线

可靠性不是配完就算完，是每一点都要有一次能复现的验证。顺序按链路从前往后走，前一点没验过就不要验后一点——前面丢了，后面的机制根本收不到消息。每一点的配置为什么是这样，见原理层。

验证点怎么配（跨产品通用）怎么验证（可直接执行）通过标准
1 生产确认用带确认的发送并检查返回状态；RabbitMQ 额外加 mandatory，RocketMQ 判 sendStatus 的四种取值，Kafka 用 acks=all故意用一个没有任何 binding 的 routing key 发一条；再用防火墙丢包断开生产端与集群 30 秒路由失败必须报错而不是静默成功；断网期间的消息全部留在 outbox，恢复后补发，总条数无缺口
2 Broker 落盘与副本副本数至少 3 且跨机架分布，写入要求多数派确认；刷盘方式按可靠性等级选持续发送的同时 kill -9 主节点进程；另起一次用大文件把数据盘填到水位线以上切换完成后收发条数无缺口；磁盘越线后生产端收到明确拒绝而不是成功
3 消费提交时机关闭自动确认，处理成功之后再确认或提交位点在消费者处理到一半时强杀进程被中断的消息重新投递并最终被处理；条数一条不少，允许出现重复
4 重试与死信区分可重试错误与毒消息；失败走 requeue=false 加死信交换机，重投由延迟队列按退避执行把下游停 10 分钟；再单独投一条必填字段缺失的毒消息退避生效且 CPU 不飙升；毒消息第一次就进死信并告警，不参与重试
5 消费端幂等业务唯一键加去重表或唯一索引，或状态机单向流转把同一条消息人工投两次；再触发一次主从切换或消费组重平衡结果表去重后条数不变，可见副作用（发券、扣款、发短信）只发生一次
6 outbox 与对账（兜底）业务与消息记录写在同一个本地事务；对账任务独立于消息链路，并提供一键补偿在业务事务 Commit 之后立刻 kill 生产进程；再人为删掉一条消费结果进程重启后消息被自动补发；对账能算出差集、告警并触发补偿

丢失点典型现场跨产品通用防法仍然存在的残留风险
1 业务成功但消息未发出订单表有数据，下游完全没收到；日志里能看到发送异常被 catch 后只打了一行 warn业务与消息记录写在同一个本地事务（outbox 表），投递线程扫表重发直到确认成功outbox 表本身要清理与索引，扫表延迟构成端到端延迟下限（落地细节见站内分布式一致性篇）
2 网络中丢失发送超时，不确定 Broker 是否已写入；重试则可能产生重复必须用带确认的发送并检查返回状态；超时按「可能已成功」处理，靠消费端幂等消化重复超时语义天然不确定，这就是「至少一次」的来源，无法消除
3 收到但未持久化就宕机生产端拿到了成功，Broker 进程被 kill 后消息不见了要么同步刷盘，要么多副本同步确认；两者至少有一个纯异步刷盘加单副本时这个窗口是几百毫秒量级，看起来很小但大流量下就是成百上千条
4 持久化了但只有单副本磁盘损坏或整机报废，消息随机器一起消失副本数至少 3，写入要求多数派确认（Quorum Queue、同步主从、ISR 机制）同机架同电源的三副本抗不住机架级故障，重要业务要跨机架或跨可用区
5 拿到消息但处理失败却已确认开了自动确认，或先 ack 再处理；消费者一崩溃这批消息就永久消失处理成功后再确认；失败走重试与死信；关闭自动确认处理成功但确认前崩溃会产生重复，所以幂等是必需品

② 原理 · 生产端确认的三种形态

三家的 API 名字完全不同，但要解决的是同一件事：让客户端知道 Broker 到底收没收到。区别在于确认的粒度和失败时能拿到多少信息。

产品机制失败信息粒度必须额外处理的场景
RabbitMQpublisher confirm：信道开启确认模式后，Broker 对每条消息回 basic.ack 或 basic.nack；可用异步回调批量处理按 delivery tag 精确到单条，multiple 标志可批量确认路由不到队列是独立的丢失场景：消息被 Broker 接受（ack）但没有任何队列匹配，消息被静默丢弃。必须加 mandatory 标志接收 basic.return，或给交换机配 alternate exchange
RocketMQ同步发送返回 SendResult，sendStatus 有四种取值；异步发送用回调状态区分刷盘超时、从节点超时、从节点不可用只判断没抛异常是错的：FLUSH_DISK_TIMEOUT 等三种非 OK 状态表示消息已写入主节点但可靠性未达标，需要按业务重要性决定是否重发（重发会重复）
Kafkaacks 取 0 / 1 / all，配合 min.insync.replicas回调里拿到 metadata 或异常组合语义与幂等 Producer、事务边界见站内 Kafka 可靠性专篇，这里不重复

# RabbitMQ 生产端：confirm 与 mandatory 必须同时处理，否则有两类静默丢失
import pika, json, uuid

conn = pika.BlockingConnection(pika.ConnectionParameters(host="127.0.0.1"))
ch = conn.channel()
ch.confirm_delivery()   # 开启后 basic_publish 会同步等待确认，失败抛异常

props = pika.BasicProperties(
    delivery_mode=2,               # 消息持久化，三件套之一，缺了就只在内存里
    message_id=str(uuid.uuid4()),  # 便于排查
    headers={
        "bizKey": "O20260923001",  # 业务唯一键，消费端据此幂等
        "retryCount": 0,           # 重试次数放消息头，不要放消息体
        "traceId": trace_id,
    },
    content_type="application/json",
)

def publish(payload: dict) -> bool:
    try:
        ch.basic_publish(
            exchange="order.topic",
            routing_key="order.created",
            body=json.dumps(payload).encode(),
            properties=props,
            mandatory=True,   # 路由不到队列时退回，否则 Broker 会静默丢弃
        )
        return True
    except pika.exceptions.UnroutableError:
        # 交换机存在但没有 binding 匹配：这是配置事故，告警而不是重试
        alert("routing key 无匹配队列，检查 binding")
        return False
    except pika.exceptions.NackError:
        # Broker 明确拒绝（如磁盘告警触发流控），退避后重试
        return False
    except pika.exceptions.AMQPError:
        # 连接类异常：消息可能已写入也可能没有，按"可能成功"处理
        # 保留 outbox 记录让兜底线程重发，重复由消费端幂等消化
        return False

② 原理 · Broker 端持久化的通用取舍

三种策略的本质区别是「返回成功」这句话的含金量。这里有一个现代共识值得强调：多副本比单机同步刷盘更划算。

策略返回成功意味着延迟量级能防住什么 / 防不住什么
写内存立即返回消息在一台机器的进程内存里亚毫秒只防客户端重试；进程崩溃即丢。仅适合可丢的埋点与日志
单机同步刷盘数据已 fsync 到本机磁盘毫秒到十毫秒，机械盘更差且抖动大能防进程崩溃与操作系统崩溃；防不住磁盘损坏、整机故障、机架断电
多副本同步复制加异步刷盘数据在多台机器的内存与页缓存中，多数派已确认毫秒级，同机房网络往返通常快于 fsync能防整机与机架级故障；防不住多数副本同时断电这种极端情况
多副本加同步刷盘多台机器都已落盘最高，两项延迟叠加接近零丢失，代价是吞吐显著下降。只有账务类场景值得
💡
为什么共识是「多副本加异步刷盘」而不是「单副本加同步刷盘」

一是故障覆盖面：生产中丢数据更常见的原因是磁盘坏、机器没了、机架断电，同步刷盘对这三类完全无效。二是延迟成本：一次 fsync 在机械盘上是毫秒到十毫秒量级，SSD 上也有明显抖动；而同机房一次网络往返通常在亚毫秒级——把数据送到另一台机器的内存往往比落到本机磁盘更快。所以主流做法是靠副本数换可靠性，靠异步刷盘保延迟。前提是副本要真的分散：三个副本放在同一台物理机的三个容器里，等于没有副本。

② 原理 · RabbitMQ 的持久化三件套与 Quorum Queue

「我配了持久化怎么还会丢」几乎都是因为只配了其中一件。三件套缺任何一个都会丢，而且丢的方式各不相同：

要件怎么配缺了它会怎样
Exchange 持久化声明时 durable=TrueBroker 重启后交换机定义消失，生产端继续往一个不存在的交换机发，消息直接被丢；此时连 mandatory 也救不了，因为报的是 channel 级错误
Queue 持久化声明时 durable=TrueBroker 重启后队列消失，队列里所有消息一起没，绑定关系也要重建
Message 持久化发布时 delivery_mode=2队列还在但消息只存在内存，重启后队列变空。这是最容易漏的一项
多副本x-queue-type=quorum，副本数 3 或 5三件套齐了也只防重启不防整机故障；单副本队列所在节点报废，消息无法恢复

即使三件套齐全，经典队列仍然是先写内存再批量落盘，宕机存在数百毫秒量级的丢失窗口。Quorum Queue 的价值就在这里：它用 Raft 把写入变成多数派确认，只要多数副本存活，已确认的消息就不会丢，故障切换也不需要人工介入。代价是单队列吞吐低于经典队列、不支持全局 QoS、队列数量极多时内存开销更高（详见机制对比篇）。

② 原理 · RocketMQ 的四种组合与丢失窗口

flushDiskType 与 brokerRole 正交，四种组合的丢失窗口差别很大：

组合返回成功时消息在哪丢失窗口延迟与适用
SYNC_MASTER 加 ASYNC_FLUSH主从两台机器的页缓存中两台机器同时断电才丢，概率极低毫秒级，生产环境默认推荐
ASYNC_MASTER 加 ASYNC_FLUSH仅主节点页缓存主节点宕机即丢未复制未落盘部分，量级为数百毫秒内的消息吞吐最高，只适合日志与埋点
SYNC_MASTER 加 SYNC_FLUSH主从都已 fsync 落盘接近零延迟最高，吞吐显著下降，账务类才值得
ASYNC_MASTER 加 SYNC_FLUSH仅主节点磁盘整机损坏即丢全部未复制数据性价比最差的组合：付了 fsync 的延迟，却没买到整机级保护
 
# broker.conf 关键可靠性项，注释说明为什么这么配
brokerClusterName=DefaultCluster
brokerName=broker-a
brokerId=0

# 主从角色：SYNC_MASTER 表示消息复制到从节点后才返回成功
# 从节点不可用时发送会返回 SLAVE_NOT_AVAILABLE，客户端必须识别这个状态
brokerRole=SYNC_MASTER

# 刷盘方式：ASYNC_FLUSH 配合 SYNC_MASTER 是可靠性与延迟的最佳折中
# 改成 SYNC_FLUSH 后每条消息都等一次 fsync，吞吐会掉一个档

# 磁盘水位保护：超过阈值后 Broker 拒绝写入而不是丢消息
# 默认 0.90 偏高，大流量场景留更多余量，给清理与告警留时间
diskMaxUsedSpaceRatio=85

# 消息保留时长（小时）。回溯与故障重放都依赖它，不要为了省盘调太小
fileReservedTime=72

# 允许自动创建 Topic 在生产环境必须关掉：
# 打错一个字母就会凭空多出一个 Topic，消息进去无人消费且难以发现

# 事务消息回查参数：回查间隔与最大次数，超过次数按回滚处理
transactionCheckInterval=60000
transactionCheckMax=15

② 原理 · 消费端确认：唯一原则是先处理后确认

自动确认（auto-ack）等于放弃可靠性——Broker 一投递出去就删除消息，消费者崩溃时这批消息永久消失，而且你连丢了哪些都不知道。下面这张表是 RabbitMQ 三个确认动作的语义差异，requeue 参数是事故高发点：

动作语义Broker 行为什么时候用
basic.ack处理成功删除消息；multiple=true 时确认该 tag 之前的所有消息唯一的成功路径。批量确认要确保前面的消息真的都处理完了
basic.nack 加 requeue=false处理失败，不要回队若配了死信交换机则进死信，否则丢弃推荐的失败路径。前提是必须配死信交换机，否则等于丢消息
basic.nack 加 requeue=true处理失败，放回队列立刻重新入队并马上再次投递，没有任何延迟几乎不该用。确定性失败会形成毫秒级死循环，打满 CPU 并刷爆日志
basic.reject拒绝单条消息同 nack 但不支持批量毒消息（结构错误）时直接 reject 加 requeue=false
连接断开（未确认）消费者失联该消费者所有 unacked 消息自动重新投递给其他消费者这是可靠性的基础机制，也是重复的主要来源之一
❌
requeue=true 的死循环

失败消息带 requeue=true 会立刻回到队列并马上被再次投递。如果失败原因是确定性的（字段缺失、下游持续不可用），这条消息就会在毫秒级里被无限次投递与拒绝：CPU 被空转打满、日志几分钟内涨到几十 GB、后面的正常消息全被这一条挤住。正确做法是 requeue=false 加死信交换机，再由延迟重试队列按退避策略重投。另外要注意 unacked 消息会占 Broker 内存，prefetch 乘以消费者数就是上限估算；prefetch 设得很大又处理很慢时，消费者断连会导致大批消息同时重投，形成二次冲击。

// RocketMQ 并发消费：返回值即确认语义，绝不要 try-catch 后无条件返回 SUCCESS
consumer.registerMessageListener(new MessageListenerConcurrently() {
    @Override
    public ConsumeConcurrentlyStatus consumeMessage(
            List<MessageExt> msgs, ConsumeConcurrentlyContext ctx) {
        for (MessageExt m : msgs) {
            String bizKey = m.getKeys();   // 业务唯一键，发送时用 setKeys 设置
            try {
                // 幂等第一位：先用唯一键占位，重复消息直接跳过
                if (!dedup.tryLock(bizKey)) {
                    continue;              // 已处理过，视为成功
                }
                handle(m);
            } catch (PoisonMessageException e) {
                // 结构错误重试无意义：主动落库加告警，然后按成功返回放行
                deadLetterRepo.save(m, e);
                alert("poison message", bizKey);
                continue;
            } catch (Exception e) {
                // 可重试错误：返回 RECONSUME_LATER 进入重试主题
                // 默认按延迟级别递增重试，达到 16 次后自动进死信主题
                // 注意重试与死信主题是按消费组划分的，别找错地方
                log.warn("consume fail, will retry, key={}, times={}",
                         bizKey, m.getReconsumeTimes(), e);
                return ConsumeConcurrentlyStatus.RECONSUME_LATER;
            }
        }
        return ConsumeConcurrentlyStatus.CONSUME_SUCCESS;
    }
});

② 原理 · 「至少一次」是现实中唯一可靠的语义

三种语义里，最多一次会丢，精确一次只在「单个系统内部、且状态更新与位点提交能落进同一个事务」这个前提下成立——一旦消费逻辑要写外部数据库、调外部接口、发短信，端到端的精确一次就不存在了。所以现实选择只有至少一次，消费端幂等因此是必需品而不是可选项。

重复的四个来源都不是配置能消除的：发送超时但服务端已写入导致重试产生第二条；处理成功但确认前进程被杀；消费组重平衡或消费者断连导致未确认消息重新投递；运维做主从切换或从备份恢复导致位点回退。幂等的具体落地（唯一索引、去重表、状态机单向流转、乐观锁版本号四种方式）站内分布式一致性篇已展开，这里只强调两点工程约束：幂等键必须是业务唯一键（订单号加事件类型），不能用每次重试都会变的随机 ID；去重表要有保留期与清理任务，并且清理窗口要大于消息最大可能延迟，否则超期的迟到重复会被当成新消息处理一遍。

② 原理 · 一条消息的完整状态机

把上面所有环节合起来，一条消息的生命周期是这样。值得注意的是有三条回边：发送失败回到待发送、消费者断连回到 Broker 待投递、人工处理后回到待投递——这三条回边正是重复投递的来源。

② 原理 · 故障注入与监控：证明配置真的生效

配置写对了不等于生效。唯一可信的验证方式是在预发环境边发消息边制造故障，然后核对收发条数。下面每一项都要先写下预期现象，实测与预期不符的地方就是真实风险点。

故障注入操作预期现象不符预期说明什么
杀掉主节点对主节点进程发 KILL，持续发送不停发送短时失败并明确报错，客户端重试后切到新主；切换完成后总条数无缺口若生产端收到成功但消息不见了，说明确认机制没生效或副本配置无效
断开网络用防火墙规则丢弃生产端到 Broker 的包 30 秒发送超时并触发重试，超时消息落 outbox，网络恢复后补发，消费端出现少量重复若出现丢失，说明超时被当成失败后未落兜底；若无重复，说明可能压根没重发
磁盘写满用大文件填满数据盘到 90% 以上Broker 进入只读或触发流控，生产端收到明确的拒绝若生产端仍收到成功，检查磁盘水位阈值配置，这是静默丢消息的高危场景
消费者 OOM给消费者设小堆并强杀进程未确认消息在超时后重新投递给其他实例，无消息丢失，可能有重复若消息丢失，说明开了自动确认或先确认后处理
主从切换手动触发切换或让主节点失联切换期间生产短暂失败，消费位点可能小幅回退，出现少量重复若位点回退很多（比如几万条），说明位点提交间隔过长或复制严重滞后
下游持续不可用把消费逻辑依赖的下游停掉 10 分钟消费失败进重试队列，退避生效，重试耗尽后进死信并告警若 CPU 被打满，检查是否用了立即回队；若死信无告警，监控缺失
✅
必须上看板的六个指标
  • 生产失败率与失败分类：区分超时、拒绝、路由失败（RabbitMQ 的 return 数必须单独看，它在 ack 里是不可见的）。
  • 未确认消息数：RabbitMQ 的 unacked、RocketMQ 的处理中数量。持续上涨说明消费者卡在处理逻辑里。
  • 队列深度与增长斜率：只看绝对值会在大促时天天误报，斜率才是判断依据。
  • 重试速率与死信速率：死信速率任何非零都应该有人看；重试速率突增通常早于下游故障告警。
  • 端到端延迟：消息里带发送时间戳，在消费端算差值。这是唯一能反映用户感受的指标。
  • outbox 滞留条数与最老记录年龄：这是丢失点 1 的唯一可观测信号，比任何 Broker 指标都靠前。

对账是必须有的兜底，不是可选加分项。原因是链路上永远有配置覆盖不到的极端情况：运维从旧备份恢复导致位点回退、网络分区期间的异常写入、毒消息被误判为可丢弃、死信堆积无人处理、以及人为重置位点。最小实现是生产方把已发出的业务单据落一张流水表，消费方把处理结果落一张结果表，每小时或每天比对差集，差集非空就告警并触发补偿。两条硬要求：对账逻辑必须独立于消息链路（不要用消息去驱动对账，否则消息链路故障时对账一起失效）；对账发现的差异要能一键补偿，只告警不提供修复入口的对账在真出问题时依然救不了场。

③ 场景 · 按业务类型定可靠性等级

可靠性是买来的，不是白送的。下表把前面的机制按业务类型收成一组默认配置，第四列是你实际要付的账——只看第二列会得出「全都上最高档」的结论，而那通常撑不住吞吐。

场景该怎么配为什么是这个组合代价
账务、资金结算、合规留痕outbox 加多副本同步复制加同步刷盘，消费端强幂等，每日全量对账丢一条就是资损或合规问题，要把所有丢失点全部堵死吞吐与延迟都要打折，对账与补偿是一套要长期维护的工程
订单状态流转、库存变更outbox 加多副本同步复制加异步刷盘，幂等加小时级对账多副本已覆盖磁盘损坏与整机故障，fsync 的边际收益低于它的延迟代价留下「多数副本同时断电」的极小窗口，用对账兜住
支付回调这类金额相关但吞吐很高的链路outbox 加多副本加异步刷盘，强幂等加准实时对账同步刷盘撑不住这个量级，可靠性靠副本与对账两层叠加准实时对账本身是一套独立系统，还要处理对账自身的延迟
短信、站内信、推送等通知生产确认加死信告警即可，可以不做 outbox晚到可接受，丢一条的业务代价有限，不值得为它上全套少量丢失通常只能靠用户反馈发现
搜索索引、缓存刷新等派生数据可靠性可以降级，但必须保证能全量重建，并演练过一次派生数据的正确性靠重建能力保证，不靠每条都不丢重建期间数据不一致，需要一个对外可见的降级开关
埋点、访问日志、行为流异步复制加异步刷盘，优先吞吐统计层面允许小比例丢失，为它付延迟不划算故障期间的缺口无法补回，报表要标注异常时段
跨机房或跨可用区容灾副本跨可用区分布，接受跨机房网络往返同机架的三副本抗不住机架级断电，副本数是账面数字写延迟按跨机房往返计算，吞吐下降，且要处理分区期间的写入策略
大促前的临时保障提前压测、磁盘水位留足余量、预置扩容脚本、关闭自动建 Topic、死信值班到人磁盘写满与自动建 Topic 是两类最典型的静默丢消息要预留资源成本，且这些动作必须在流量来之前完成

不适用边界：这篇解决的是「消息进出链路不丢」，不解决「该不该用消息」——那在 主干篇；消息该定成命令还是事件、契约怎么演进在 消息通信模式；产品能力差异与选型流程在 MQ 选型方法论；Kafka 的 acks 与 min.insync.replicas 组合、幂等 Producer 与事务边界在 Kafka 消息可靠性落地；幂等的四种落地写法与柔性事务在 幂等的完整工程实现 与 柔性事务。需要「精确一次」且消费逻辑要写外部系统的场景，这里给不出方案，因为端到端精确一次并不存在。

最容易踩的坑

❌
这些坑都会表现为「监控一切正常但消息没了」
  • 只配了消息持久化没配队列持久化：Broker 重启后队列直接消失，消息一起没。三件套必须齐：Exchange、Queue、delivery_mode=2。
  • RabbitMQ 不加 mandatory：路由不到队列时 Broker 照样回 ack，消息被静默丢弃，看监控一切正常。
  • RocketMQ 只判断 send 没抛异常：FLUSH_DISK_TIMEOUT 与 SLAVE_NOT_AVAILABLE 都不是完全成功，重要消息要单独处置。
  • 用 requeue=true 做重试：确定性失败会形成毫秒级死循环，CPU 打满、日志刷爆、正常消息被挤住。
  • 开了自动确认：Broker 一投递就删消息，消费者一崩就永久丢失，而且不知道丢了哪些。
  • 先确认再处理：为了「防止重复」把 ack 挪到处理之前，等于用丢消息换重复，方向完全错了——重复能靠幂等解决，丢失不能。
  • 三副本放在同一台物理机或同一机架：整机或机架故障时三个副本一起没，副本数是账面数字。
  • 以为同步刷盘就万无一失：它防不住磁盘损坏和整机故障，优先级应该低于多副本。
  • 配了死信交换机但没人看死信：死信队列堆了几千条，发现时只能写一次性脚本。死信必须告警并有重投入口。
  • prefetch 设得很大且处理很慢：unacked 堆积占 Broker 内存，消费者一断连大批消息同时重投，形成二次冲击。
  • 去重表没有清理任务或清理窗口太短：前者磁盘被打满，后者超期的迟到重复被当新消息处理一遍。
  • 生产环境开着自动创建 Topic：打错一个字母就凭空多一个 Topic，消息进去无人消费，排查时极难发现。
  • 没有对账：以为配置到位就零丢失。任何 MQ 方案都要有独立于消息链路的定时对账与一键补偿。
