消息通信模式：命令、事件与编排协同

🏷️ MQ 模式

这篇不谈任何具体产品，只谈消息该怎么用——这部分知识换 MQ 不会失效，而且是实际项目里出问题最多的地方。选型与产品机制见选型与机制对比，可靠投递见可靠投递篇。经验上，一个消息架构走向混乱的起点几乎总是同一件事：没有区分「命令」和「事件」。

五种基础通信模式

所有复杂的消息拓扑都是这五种的组合。区分它们的关键不是图长什么样，而是一条消息被几个人消费以及发送方是否等结果。

模式一条消息被谁消费适用场景实现要点与陷阱
点对点队列恰好一个消费者实例任务派发、异步作业，如生成报表、转码实现简单；陷阱是多实例部署时误以为每个实例都会收到，把广播需求做成了点对点
发布订阅每个订阅方各拿一份状态变更扩散，如订单已支付通知多个下游订阅方数量对生产方透明；陷阱是订阅方越多，一次生产端字段变更影响面越大
竞争消费者同组内只有一个实例拿到，组间各拿一份水平扩容消费能力，这是最常用的扩容手段并发度上限受分区或队列数限制；并发会破坏顺序，需要按键路由补偿
请求回复一个处理方，回复投到发送方指定的回调队列确实需要结果但要跨网络解耦，如跨机房调用、长耗时任务查询必须带关联 ID 与超时；陷阱是把它当同步 RPC 用，延迟和复杂度都劣于直接调用
消息路由与分发由路由规则决定进哪些队列按业务维度分流，如按地区、按优先级、按事件类型路由规则放在 Broker 侧可以让消费方少收无关消息；陷阱是规则散落无人维护，几个月后没人说得清一条消息会去哪

请求回复是这五种里最容易被误用的，看清它的往返结构就明白代价在哪：

命令、事件、文档：最重要的一组区分

三者在技术上都是一条消息，但语义完全不同，混用会直接导致架构失控。判断方法只有一句：如果没有任何人订阅这条消息，发送方是否算出错？答案为「是」就是命令，为「否」就是事件。

维度命令 Command事件 Event文档 Document
语义请你去做某事某事已经发生了这是一份数据，你自己决定怎么用
命名方式动词祈使式：CreateOrder、DeductStock、SendSms过去式：OrderCreated、StockDeducted、PaymentFailed名词：ProductCatalog、DailySalesReport
接收方数量恰好一个，且发送方知道是谁零到多个，发送方不知道也不关心通常多个，订阅方按需取用
耦合方向发送方依赖接收方（知道对方能做这件事）接收方依赖发送方（知道对方会发布这类事实）共享数据契约，双方都依赖格式
发送方是否关心结果关心，失败需要知道并可能补偿不关心，谁处理失败是谁自己的事不关心
失败处理责任在发送方或流程协调者，需要超时与补偿完全在消费方，靠重试与死信在消费方
能否重放不能随意重放，等于重复执行动作可以重放，因为它描述的是已发生的事实可以重放，通常是最新覆盖
❌
混用命令和事件的两种具体事故

把命令当事件发：定义了一个叫 order.deduct 的主题让多个服务订阅，结果库存服务和风控服务都执行了一遍扣减；换个说法就是「一条命令被执行了 N 次」，典型表现是重复扣款、重复发券。把事件当命令发：生产方发出 OrderCreated 之后开始等待某个特定消费者的处理结果，于是在生产端写下「如果积分服务没处理成功就回滚订单」，解耦彻底失效，还引入了一条隐式的同步依赖。前者的根因是把「有唯一接收方」的消息做成了广播，后者的根因是发送方关心了消费结果。

事件驱动的三种成熟度

「用事件」不是一个开关，而是三个层次，成本和收益差别巨大。很多团队直接上最贵的那个，然后被复杂度压死。

层次消息里放什么优点代价适用边界
事件通知只有事件类型、实体 ID、发生时间消息小、契约极稳、不泄漏内部字段每条消息都触发回查，上游被打成查询热点；消费方与上游产生运行时依赖，上游挂了消费也停消息量不大、消费方少、数据敏感不宜外传
事件携带状态转移事件加消费方需要的完整字段快照消费方自治，无需回查，上游宕机也能继续处理消息变大（可能十几倍）、字段一旦暴露就难改、数据可能已过期绝大多数业务场景的默认选择
事件溯源事件流本身是唯一事实来源，当前状态由重放得出完整审计轨迹、可回到任意历史时点、天然支持多种读模型需要快照机制、事件版本迁移、投影重建工具；查询要走物化视图；调试和排查门槛极高成本极高，绝大多数系统不需要。只有强审计要求（账务、风控、合规）且团队有经验时才考虑

编排与协同：同一个流程的两种写法

下单流程要走「创建订单 → 扣库存 → 支付 → 发货」，有一个中心协调者按序驱动，还是各服务自己监听事件接力？这是分布式流程设计最核心的一个分叉。先看编排：

sequenceDiagram autonumber participant S as 订单流程协调者 participant O as 订单服务 participant I as 库存服务 participant P as 支付服务 participant D as 履约服务 S->>O: 命令 创建订单 O-->>S: 订单已创建 S->>I: 命令 扣减库存 I-->>S: 库存已扣减 S->>P: 命令 发起支付 P--xS: 支付失败 Note over S: 协调者知道完整流程
因此能准确执行反向补偿 S->>I: 命令 回滚库存 S->>O: 命令 关闭订单 Note over S,D: 流程状态在协调者一处可查
代价是协调者持续膨胀且是单点

再看协同，没有协调者，每个服务只认自己关心的事件：

sequenceDiagram autonumber participant O as 订单服务 participant EB as 事件总线 participant I as 库存服务 participant P as 支付服务 participant D as 履约服务 O->>EB: 发布 OrderCreated EB->>I: 投递 I->>EB: 发布 StockReserved EB->>P: 投递 P->>EB: 发布 PaymentFailed EB->>I: 投递 I->>I: 自行释放库存 EB->>O: 投递 O->>O: 自行关闭订单 Note over O,D: 没有任何地方能看到完整流程
排查要跨四个服务拼日志 Note over EB,D: 新增参与方只需订阅 不动别人
但容易形成隐式依赖环
维度编排 Orchestration协同 Choreography
流程可见性集中在协调者，可画出、可查状态、可人工干预无处可见，只能靠 trace 拼凑，新人看不懂全貌
排查成本低，看协调者的流程实例状态即可高，要跨多个服务按 traceId 与业务键串日志
耦合度协调者知道所有参与方，参与方彼此不知参与方之间通过事件隐式耦合，改事件语义会连环影响
新增参与方要改协调者，走一次发布自助订阅，不动任何现有代码
补偿逻辑集中在协调者，容易保证补偿完整分散在各服务，容易漏掉某条失败路径
主要风险协调者膨胀成上帝服务并成为流程单点形成隐式依赖环（A 的事件触发 B，B 的事件又触发 A），出现自激循环
推荐用法关键交易流程，且把流程状态机显式落库通知类、扩散类流程，参与方不影响主流程成败
⚠️
不要在一个流程里混用两种风格

最难维护的形态是「一半编排一半协同」：协调者驱动前三步，第四步靠某个服务监听事件自行接力。这时流程状态在协调者里显示为「已完成」，实际第四步可能还没跑或已经失败，没有任何地方持有真相。同一个业务流程要么全程编排，要么全程协同；跨流程之间可以用事件衔接，但衔接点必须是明确的流程边界。TCC 与 Saga 两种补偿事务的具体落地见站内分布式一致性篇。

消息契约与版本演进

消息一旦有第二个消费方，它就是公开 API，改它的难度和改 HTTP 接口一样。核心约束是生产方和消费方永远不可能同时发布，所以每次变更都必须能在「新生产旧消费」和「旧生产新消费」两种交错状态下工作。

变更类型兼容性能否直接上线正确做法
新增可选字段（带默认值）向后兼容，旧消费方忽略它即可可以必须可选且有默认值；不要在新增字段上立刻加必填校验
新增必填字段破坏兼容，旧生产方发不出该字段，新消费方校验失败不可以先作为可选字段上线，等生产方全量补齐后再收紧校验
删除字段破坏兼容，仍在读它的消费方会拿到空值不可以先标记废弃并监控是否还有人读，确认无人使用再删
字段改名等于一删一增，破坏兼容不可以新旧字段并存一段时间，双写双读，再摘掉旧的
字段语义变更（如金额单位从元改成分）最危险，格式校验通不出问题，静默产生错误数据绝对不可以必须换新字段名或升主版本号，并在新旧之间做显式转换
类型收窄（字符串改数字）破坏兼容不可以升版本号，用新主题或新 schemaVersion 分流

Schema Registry 的作用正是把上面这张表变成上线时的自动拦截：生产方注册新版本时，注册中心按配置的兼容模式（向后、向前、全兼容）检查新旧 schema，不通过就直接拒绝注册，而不是等消息到了消费端才炸。此外它还能把 schema 从消息体里剥离出去，消息只带一个 schema ID，省掉大量重复的字段名开销。没有注册中心时，退而求其次的做法是把消息结构定义放进独立仓库、用 CI 做兼容性 diff。

// 消费端的三条硬规则：容忍未知字段、幂等去重、按版本丢弃过期消息
// 这三条缺任何一条，生产方一次发布就能把你的消费全部打进死信

// 1) 信封与业务数据分离；未知字段静默忽略是默认行为，不要开严格模式
type Envelope struct {
    EventType        string          `json:"eventType"`
    EventID          string          `json:"eventId"`          // 幂等键
    SchemaVersion    int             `json:"schemaVersion"`
    AggregateID      string          `json:"aggregateId"`
    AggregateVersion int64           `json:"aggregateVersion"` // 用于丢弃旧消息
    TraceID          string          `json:"traceId"`
    Data             json.RawMessage `json:"data"`             // 延迟解析
    // 故意不写 DisallowUnknownFields：新增字段不能让老消费者失败
}

func (h *OrderHandler) Handle(ctx context.Context, raw []byte) error {
    var env Envelope
    if err := json.Unmarshal(raw, &env); err != nil {
        return ErrPoison // 结构都解不开，直接进死信，重试也没用
    }

    // 2) 幂等：先占位再处理。唯一索引冲突说明处理过，直接确认
    if err := h.dedup.Insert(ctx, env.EventID); err != nil {
        if errors.Is(err, ErrDuplicate) {
            return nil // 幂等的四种落地方式见站内分布式一致性篇
        }
        return err
    }

    // 3) 版本兼容：老版本走转换，未来版本不要直接报错
    switch {
    case env.SchemaVersion < 3:
        raw = upgradeV2ToV3(env.Data) // 显式迁移，不要靠默认零值糊过去
    case env.SchemaVersion > 3:
        // 比自己新的版本：字段只增不减的前提下可以继续处理
        // 若发现依赖的必填字段缺失，再退回死信并告警
    }

    var evt OrderPaid
    if err := json.Unmarshal(raw, &evt); err != nil {
        return ErrPoison
    }

    // 4) 用实体版本号对抗乱序：比当前状态旧的消息直接丢弃
    // 这比强行保证消息顺序可靠得多，因为重试天然会打乱顺序
    cur, err := h.repo.LoadVersion(ctx, env.AggregateID)
    if err != nil {
        return err
    }
    if env.AggregateVersion <= cur {
        return nil // 过期消息，安全忽略
    }
    return h.repo.Apply(ctx, evt, env.AggregateVersion)
}

顺序性与并发的根本矛盾

这是消息系统里少数无法两全的问题：要严格顺序就必须让同一条流被单线程处理，要提高并发就一定会乱序。常见的错误是嘴上说「我们保证了顺序」，实际只是在低并发下侥幸没乱。

方案顺序保证范围并发上限失效条件
单队列单消费者全局严格有序1，吞吐被锁死一条慢消息就会拖住整条流；消费者重启期间完全停滞
按业务键哈希到固定处理单元同一键有序，不同键无序处理单元数量处理单元数变化（扩容、队列扩容）会改变映射；热点键成为单点瓶颈
并发消费加版本号丢弃不保证顺序，但最终状态正确不受限要求消息带单调版本且操作可按版本判定新旧；增量型操作（如余额加减）不适用
消费端排序缓冲窗口内有序受缓冲大小限制缺失的消息不到就会一直等，需要超时放行，复杂度高，一般不值得

按键哈希的实现思路很简单但有三个细节决定成败：哈希键必须选业务实体 ID（订单号、用户 ID）而不是消息 ID；处理单元数量要固定，扩容前必须排空在途消息；每个处理单元前面要有独立的有界缓冲，避免一个慢键把整体拖住。具体代码见主干篇的 worker 池示例。更推荐的做法是第三行——不依赖顺序：在消息里带上实体版本号，消费端丢弃比当前状态旧的消息，把「顺序问题」转化成「幂等与冲突检测问题」。因为无论你怎么保序，失败重试都会重新打乱顺序，而版本号方案对重试天然免疫。

死信与重试的通用设计

重试策略不是「多试几次」，而是要区分可重试错误和不可重试错误：下游超时可以重试，反序列化失败重试一万次也是失败，后者应该立刻进死信。

错误类型判断方式处置重试间隔
瞬时故障（下游超时、连接重置、限流）异常类型或错误码可枚举重试，逐级退避指数退避加抖动，如 1s 5s 30s 2m 10m，避免所有消费者同时重试造成二次冲击
依赖数据未就绪（查不到关联实体）业务判断有限次延迟重试固定延迟，重试上限要小（3 到 5 次），否则可能是上游根本没发那条消息
毒消息（结构错误、必填字段缺失）反序列化或校验失败立刻进死信，不要重试不适用。重试毒消息是消费端 CPU 被打满的常见原因
业务规则拒绝（订单已取消）业务判断确认并记录，不算失败不适用。这类消息重试永远不会成功

三条通用约定：重试次数放消息头（不要放消息体，否则每次重试都要改业务载荷，也没法在不反序列化的情况下判读）；死信必须告警且有人工重投入口，一个只能看不能操作的死信队列等于没有；死信消息要保留原始头信息与失败原因，包括最后一次异常摘要、失败时间、重试次数，否则重投时无从判断该不该投。各产品内置的重试队列分级与死信配置（Kafka 侧的重试主题设计、RocketMQ 的重试等级、RabbitMQ 的 x-delivery-limit）见站内 Kafka 可靠性篇与机制对比篇。

常见反模式

反模式表面理由真实后果正确做法
用 MQ 做同步 RPC（发消息然后轮询等结果）「这样就解耦了」延迟比直接调用高一个数量级，还要维护等待表、超时清理、结果表清理需要结果就直接 RPC，配熔断与超时；确实要跨网络解耦再用请求回复模式
消息里放大对象或整个文件「消费方不用再查一次」消息体从 1KB 涨到 1MB，吞吐掉一个数量级，可能超过单条上限直接发送失败大内容放对象存储，消息里只带引用与校验和
把 MQ 当数据库查历史「消息都在里面」顺序扫描全量消息找一条，位点被搅乱，还可能触发大量磁盘读影响生产消息落库或落数仓后再查；需要按键查单条用产品提供的索引能力
一个 Topic 承载多种语义不同的消息「省得建那么多主题」消费方写大分支、无法按类型独立扩容限流、一种消息卡住会阻塞其他、监控无法归因按业务语义拆主题，同族事件放一起，细分用标签或路由键
消费端不幂等「我们配了恰好一次」任何一次重试、重平衡、主从切换都会重复，直接导致重复扣款发券业务唯一键加去重表，或状态机单向流转
用消息顺序保证业务因果「先发的肯定先到」失败重试、分区变化、并发消费都会打乱顺序，且问题只在高并发时出现消息里带版本号或因果 ID，消费端自行判断新旧与依赖是否就绪
在消费逻辑里做同步远程调用且无超时「顺手就查了」下游一慢，消费线程全部挂住，积压瞬间起来每个远程调用都设超时与熔断；能预取的数据提前批量取
生产端为了「保证发出去」无限重试「不能丢消息」Broker 故障时生产端线程全部阻塞，业务接口一起被拖死有限重试后落本地 outbox 表，由后台投递线程兜底
把内部数据库表结构直接当消息格式「省一层转换」一次加字段或改类型就波及所有消费方，内部实现彻底泄漏定义独立的事件契约，与内部表结构解耦
事件命名用现在时或动词原形（OrderCreate）「都能看懂」读者分不清这是通知还是指令，逐渐演变成命令与事件混用事件一律过去式，命令一律祈使式，在代码评审里当硬规则执行
❌
最容易踩的坑
  • 命令和事件用同一套命名：半年后没人分得清 order.process 是让人去处理还是告知已处理，最终变成多个消费者各执行一遍。
  • 事件里塞了「请下游做什么」的指令字段：比如事件里带 needSendSms: true，这是命令伪装成事件，生产方重新耦合了下游行为。
  • 只发 ID 的事件通知打爆上游：十个消费方各自回查，一条消息变成十次查询，上游成了查询热点。默认带上核心字段。
  • 直接上事件溯源：没有快照、没有投影重建工具、没有事件版本迁移方案，三个月后连当前状态都算不准。绝大多数系统只需要事件携带状态转移。
  • 消费端开启严格反序列化：生产方一加字段，所有未升级的消费方集体进死信。未知字段必须静默忽略。
  • 改字段语义但不改字段名：金额单位从元改成分，格式校验一切正常，错误数据静默入库，这类事故往往几周后才发现。
  • 一半编排一半协同：协调者显示流程已完成，实际最后一步靠某个服务监听事件接力，没有任何地方持有真相。
  • 协同模式下形成事件环：A 的事件触发 B，B 的事件又触发 A，上线后表现为消息量自激增长直到打满集群。
  • 毒消息进入重试循环：反序列化失败的消息被无限重试，消费端 CPU 打满、日志刷爆。结构错误必须立刻进死信。
  • 重试次数记在消息体里：每次重试都要反序列化再改载荷，还破坏了原始消息。放消息头。
  • 死信队列只能看不能重投：发现问题时只能写一次性脚本，且没有原始头信息判断该不该重投。死信要告警、可查、可重投、可标记忽略。
  • 宣称保证顺序但用了多消费者并发：低流量时侥幸正确，大促时乱序集中爆发。要顺序就按键路由到固定处理单元，或者干脆改用版本号方案。
