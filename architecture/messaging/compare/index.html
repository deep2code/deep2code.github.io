MQ 选型方法论与 RabbitMQ / RocketMQ 机制拆解

🏷️ MQ 对比

所有「哪个 MQ 更快」的对比都不可信：吞吐数字取决于消息体大小、批量参数、刷盘策略和副本数，换一组参数就能让任意一款赢。真正能决定选型的是能力有无——路由是否够灵活、延迟消息是否原生、顺序保证的粒度、能不能重放历史。这篇先给筛选方法，再拆 RabbitMQ 的 Exchange 路由模型与 RocketMQ 的存储和事务机制，Kafka 部分只给结论，内部实现见站内 Kafka 专题。

被问烂的那句「万级 / 十万级 / 百万级」

这组数字来自很多年前的单机对比，今天引用它只会误导：RabbitMQ 3.12 的经典队列 v2 在小消息下单节点也能做到每秒数万，而 Kafka 在 acks 等于 all、同步副本要求 2、消息 10KB 的配置下也不过每秒几万条。量级对比只能用于排除明显不匹配的选项（比如每秒五十万条日志显然不该用 RabbitMQ），不能用于「A 比 B 快所以选 A」。要具体数字就用自己的消息体和参数压一遍。

RabbitMQ 的差异化能力：Exchange 路由模型

RabbitMQ 和日志型 MQ 最大的结构差异在于：生产者从不直接发到队列，而是发到 Exchange，由 Exchange 按 Binding 规则决定消息进哪些队列。路由决策在 Broker 侧完成，这是它相比「消费端自己筛」的核心优势。

Exchange 类型路由规则典型用途什么时候不要用它
direct消息的 routing key 与 binding key 完全相等才投递；同一 key 绑多个队列则都收到任务分发、按明确类型分流，如 sms / email 两个队列订阅方需要按前缀或维度组合订阅时，binding 会爆炸式增长
topicrouting key 按点号分段，binding key 中 * 匹配恰好一个段，# 匹配零个或多个段最常用。路由键设计成 业务域.实体.动作，新订阅方自助绑定，生产端不改代码路由键没有分层设计时，topic 退化成 direct 还多一层匹配开销
fanout忽略 routing key，投给所有绑定队列全节点广播，如本地缓存失效通知、配置刷新订阅方只关心一部分消息时会造成大量无效消费
headers按消息 headers 的键值匹配，x-match=all 要求全部命中，any 要求任一命中；忽略 routing key需要多维度组合匹配且维度无法编码进路由键几乎所有场景。匹配开销大、管理界面上不直观、排查路由问题极痛苦

# RabbitMQ 一套可直接用的声明与消费骨架（pika 1.3）
# 要点：topic exchange + 死信路由 + prefetch + 手动确认
import pika, json

conn = pika.BlockingConnection(pika.ConnectionParameters(
    host="127.0.0.1",
    heartbeat=30,                   # 默认 60s；消费慢的场景心跳超时会导致连接被断开
    blocked_connection_timeout=60,  # Broker 因内存或磁盘告警阻塞连接时不要无限挂着
))
ch = conn.channel()

# 业务 exchange 与死信 exchange 都必须 durable，否则 Broker 重启后定义消失
ch.exchange_declare("order.topic", exchange_type="topic", durable=True)
ch.exchange_declare("order.dlx", exchange_type="topic", durable=True)

# 业务队列：绑定死信交换机，并限制投递次数上限
ch.queue_declare("audit.queue", durable=True, arguments={
    "x-dead-letter-exchange": "order.dlx",
    "x-dead-letter-routing-key": "audit.failed",
    "x-queue-type": "quorum",   # 新项目直接用 Quorum Queue，别用镜像队列
    "x-delivery-limit": 5,      # Quorum Queue 专属：投递超过 5 次自动进死信
    # 注意：经典队列没有 x-delivery-limit，只能自己在消息头里记重试次数
})
ch.queue_bind("audit.queue", "order.topic", routing_key="order.#")

ch.queue_declare("audit.dead.queue", durable=True)
ch.queue_bind("audit.dead.queue", "order.dlx", routing_key="audit.#")

# prefetch 必须显式设置：默认值 0 表示无限预取，
# 一个消费者会把整个队列的消息全部拉到本地缓冲，其他消费者空转
ch.basic_qos(prefetch_count=20)

def on_msg(channel, method, props, body):
    try:
        handle(json.loads(body))                 # 幂等处理，用业务唯一键去重
        channel.basic_ack(method.delivery_tag)   # 成功后才确认
    except RetryableError:
        # requeue=False：交给死信而不是立刻回队，否则会形成打满 CPU 的死循环
        channel.basic_nack(method.delivery_tag, requeue=False)
    except Exception:
        channel.basic_reject(method.delivery_tag, requeue=False)

# auto_ack 一定为 False，开了就等于放弃可靠性
ch.basic_consume("audit.queue", on_msg, auto_ack=False)
ch.start_consuming()

RabbitMQ 的队列形态与堆积应对

队列类型选错是 RabbitMQ 事故最集中的来源。下表第四列是实际会踩到的边界：

队列形态复制机制适用与否边界与代价
经典队列（单副本）无复制，数据只在一个节点可用于允许丢失的旁路通知节点宕机期间队列完全不可用，未消费消息要等节点恢复
镜像队列（classic mirrored）主从异步同步，靠策略配置镜像数已不推荐，3.9 起标记废弃，4.0 移除网络分区恢复后可能丢消息；新增镜像触发全量同步会阻塞队列；不要在新项目里用
Quorum QueueRaft 日志复制，写入需多数派确认新项目默认选它，副本数 3 或 5（奇数）单队列吞吐低于经典队列；不支持全局 QoS 与非持久化；队列数量极多时内存开销更大；消息优先级到 4.0 才支持
惰性队列（x-queue-mode=lazy）与队列类型无关的存储策略：尽快落盘，内存只留少量预期会长时间堆积百万条以上时使用单条延迟略高；3.12 起经典队列 v2 已统一为类似行为，该参数变成无操作，别再当成调优手段
Stream（3.9 起）仅追加日志，支持多消费者独立位点与回放需要重放、扇出到很多消费者时协议与队列不同，客户端要用 stream 插件；语义更接近日志型 MQ，不要和普通队列混用同一套代码

prefetch 的影响被严重低估。默认 prefetch_count=0 意味着无限预取：第一个连上来的消费者会把队列里的消息一口气拉到本地缓冲区，后来的消费者拿不到任何消息，看起来像「扩容无效」。但 prefetch 设成 1 又会让每处理一条都多一轮网络往返，吞吐掉到十分之一。经验值是处理耗时 50ms 左右时取 10 到 50；处理耗时超过 1 秒时取 1 到 5。另外 unacked 消息会占用 Broker 内存，prefetch 乘以消费者数就是内存上限的估算基数。

RabbitMQ 做延迟队列：TTL 加死信的致命缺陷

「消息 TTL + 死信交换机」是流传最广的延迟队列做法，也是最容易翻车的做法。原因在于队列是 FIFO 的，Broker 只检查队首那条消息是否过期。

❌
队头阻塞让按消息设置 TTL 的方案彻底不可用

先发一条 TTL 为 30 分钟的消息，再发一条 TTL 为 10 秒的消息。10 秒后第二条不会被投到死信交换机，它必须等队首那条 30 分钟到期出队之后才会被检查。结果是「延迟 10 秒的订单超时关单」实际在 30 分钟后才触发。只要同一个队列里存在不同 TTL 的消息，这个方案就是错的。

延迟方案实现方式能支持的延迟代价与风险
固定档位多队列为 5s / 30s / 1m / 5m / 30m 各建一个队列，TTL 设在队列上（x-message-ttl），业务按档位投递只有预置档位，需要 17 分钟就得拆成 15 分钟档再重投队列数量随档位线性增长；跨档位组合逻辑要自己写；仍是最稳的自建方案
延迟消息插件装 rabbitmq_delayed_message_exchange，交换机类型设为 x-delayed-message，发送时带 x-delay 头任意毫秒级延迟未到期消息存在发布节点本地，该节点故障这些消息就没了；延迟消息量大时会拖慢该节点；插件不随主版本保证兼容
外部调度器延迟任务写数据库或时间轮，到点再投普通消息任意，精度取决于扫描间隔多维护一套调度组件，但可靠性和可观测性最好，延迟任务可查可改可取消
换成原生支持RocketMQ 的延迟级别或 5.x 定时消息18 个固定档位或任意时间换中间件的成本，但省掉一整类自研逻辑

RocketMQ 的存储设计：一条 CommitLog 走天下

维度RocketMQ 单 CommitLog每分区独立日志（Kafka 系）实际后果
Topic 与队列数量扩展新增只是多几个小索引文件，写入仍是一条顺序流每分区一个日志目录，分区上千后变成大量并发写单机承载上万 Topic 时 RocketMQ 明显更稳，适合业务域多、每域流量不大的场景
读取模式先读 ConsumeQueue 再回 CommitLog，一次逻辑随机读分区内连续读，可直接零拷贝发送冷数据读放大在 RocketMQ 上更明显，靠 warmMapedFileEnable 预热与页缓存缓解
单 Topic 极限吞吐受单机 CommitLog 顺序写带宽约束可靠增加分区把压力摊到多机多盘超大流量单 Topic 场景日志型存储更有优势
消息过滤ConsumeQueue 条目里存了 Tag 哈希，Broker 侧先按哈希过滤，客户端再精确比对过滤基本在消费端做Tag 过滤能省下大量网络传输；但哈希冲突会让少量多余消息到客户端，所以客户端必须再判一次
索引重建ConsumeQueue 可由 CommitLog 完整重建依赖各分区日志自身RocketMQ 索引损坏是可恢复的，代价是重建期间不可用

NameServer 为什么是无状态且节点间不通信：每个 Broker 每 30 秒向所有 NameServer 注册一次全量路由信息，NameServer 超过 120 秒收不到心跳就摘除该 Broker；客户端每 30 秒从其中一台拉取路由。因为路由数据在每台 NameServer 上都是全量的，节点之间不需要复制，也就不需要选主和一致性协议，运维上任意增减节点都不影响。代价是路由信息最终一致：Broker 刚下线的那几十秒内，客户端可能还拿着旧路由发消息，所以生产端必须依赖发送重试（同步发送默认重试 2 次，会自动切换到其他 Broker）。

RocketMQ 的三个特色能力

延迟消息、顺序消息、事务消息是 RocketMQ 相比其他产品最省事的地方——它们都不需要自研。

能力4.x 的实现与限制5.x 的变化使用时的坑
延迟消息18 个固定级别（1s 5s 10s 30s 1m 2m 3m 4m 5m 6m 7m 8m 9m 10m 20m 30m 1h 2h），用 setDelayTimeLevel(n)，n 从 1 开始支持任意时间定时消息，精度约 1 秒，基于时间轮实现4.x 里级别表是 Broker 配置项 messageDelayLevel，改它需要重启且影响全集群；级别号写错会延迟成完全不同的时长
顺序消息生产端用 MessageQueueSelector 把同一业务键投到同一队列，消费端用 MessageListenerOrderly 单线程消费该队列机制不变，客户端 API 简化顺序消费时某条消息一直失败会阻塞整个队列；重试也是串行的，必须设重试上限并让失败消息进死信
事务消息半消息写入内部主题，加本地事务，加 commit 或 rollback，加状态回查；默认回查间隔 60 秒、最多 15 次机制不变回查接口必须能按事务 ID 查到本地事务真实结果，业务表里要存事务 ID；一直返回 UNKNOWN 会在次数耗尽后按回滚处理
消息过滤Tag 过滤在 Broker 侧按哈希预筛；SQL92 过滤需要开 enablePropertyFilter=true同单条消息只能有一个 Tag，多维度要用属性加 SQL92；SQL92 过滤有额外 CPU 开销且默认关闭
重试与死信并发消费返回 RECONSUME_LATER 后进入重试主题，按延迟级别递增重试，默认 16 次后进死信主题同重试与死信主题是按消费组而非按 Topic 的；死信主题默认只有写权限，要消费它得先手动改权限，很多团队因此不知道死信已堆了几千条

事务消息的完整流程值得单独看一遍，它把「本地事务与消息发送的原子性」做进了中间件：

// RocketMQ 事务消息：关键在 checkLocalTransaction 必须真的能查出结果
// 常见错误是这里直接返回 UNKNOW，导致回查 15 次后消息被静默丢弃
public class OrderTransactionListener implements TransactionListener {

    private final JdbcTemplate jdbc;

    @Override
    public LocalTransactionState executeLocalTransaction(Message msg, Object arg) {
        CreateOrderCmd cmd = (CreateOrderCmd) arg;
        // 事务标识必须随业务数据一起落库，否则回查时无从判断
        String txId = msg.getProperty("UNIQ_KEY");
        try {
            jdbc.update(
                "INSERT INTO t_order(id, user_id, amount, tx_id) VALUES(?,?,?,?)",
                cmd.getOrderId(), cmd.getUserId(), cmd.getAmount(), txId);
            return LocalTransactionState.COMMIT_MESSAGE;
        } catch (DuplicateKeyException e) {
            // 重复执行说明上一次已成功，直接提交，保证幂等
            return LocalTransactionState.COMMIT_MESSAGE;
        } catch (Exception e) {
            return LocalTransactionState.ROLLBACK_MESSAGE;
        }
    }

    @Override
    public LocalTransactionState checkLocalTransaction(MessageExt msg) {
        String txId = msg.getProperty("UNIQ_KEY");
        Integer cnt = jdbc.queryForObject(
            "SELECT COUNT(1) FROM t_order WHERE tx_id = ?", Integer.class, txId);
        if (cnt != null && cnt > 0) {
            return LocalTransactionState.COMMIT_MESSAGE;   // 业务已成功 放行消息
        }
        // 只有"确定业务不会再成功"时才回滚；不确定就返回 UNKNOW 等下次回查
        return isTimeout(msg) ? LocalTransactionState.ROLLBACK_MESSAGE
                              : LocalTransactionState.UNKNOW;
    }
}

// 生产者侧：事务生产者必须设置 producerGroup，Broker 靠它找到回查对象
TransactionMQProducer producer = new TransactionMQProducer("order_tx_group");
producer.setNamesrvAddr("127.0.0.1:9876");
producer.setTransactionListener(new OrderTransactionListener(jdbc));
producer.start();
producer.sendMessageInTransaction(
        new Message("order.created", "PAID", payload), cmd);
// 顺序消息：同一订单的所有消息进同一队列，消费端单线程按序处理
// 选择器返回的队列必须稳定，用订单号取模，不要用随机数或时间戳
producer.send(msg, (mqs, m, arg) -> {
    long orderId = (Long) arg;
    // mqs 是该 Topic 在各 Broker 上的队列列表，长度变化会破坏历史映射
    // 所以线上扩队列数之前必须确认没有在途的顺序消息
    return mqs.get((int) (orderId % mqs.size()));
}, orderId);

// 顺序消费：MessageListenerOrderly 内部对队列加锁，同一队列串行
consumer.registerMessageListener(new MessageListenerOrderly() {
    @Override
    public ConsumeOrderlyStatus consumeMessage(
            List<MessageExt> msgs, ConsumeOrderlyContext ctx) {
        for (MessageExt m : msgs) {
            try {
                handle(m);   // 必须幂等：挂起重试后整批会重投
            } catch (RetryableException e) {
                // 返回 SUSPEND 会挂起整个队列，默认间隔 1 秒重试
                // 危险：一条坏消息能把整条队列堵死，务必配重试上限加死信
                if (m.getReconsumeTimes() > 16) {
                    sendToDlq(m);          // 自己搬走，放行队列
                    continue;
                }
                return ConsumeOrderlyStatus.SUSPEND_CURRENT_QUEUE_A_MOMENT;
            }
        }
        return ConsumeOrderlyStatus.SUCCESS;
    }
});

选型的现实考量与共存

需求没有被硬指标卡死时，下面三条比技术参数更决定结果——这不是妥协，而是因为长期成本主要发生在运维和故障处置上。

现实因素为什么它权重更高怎么判断
团队熟悉度凌晨三点集群异常时，能救回来的只有懂它的人。不熟悉的产品会把一次十分钟故障拖成两小时问团队：谁做过这个产品的扩容和版本升级？出现队列不可用时第一条命令敲什么？
已有基础设施公司已有一套集群和监控告警模板时，复用的边际成本接近零；新引入一套要走安全审计、容量申报、备份方案看现有集群的余量与隔离手段（能否独立 vhost 或命名空间），能隔离就优先复用
云托管可用性托管版把版本升级、磁盘扩容、副本修复都接走了，相当于省掉一个人的工作量确认托管版支持的具体版本与特性是否阉割（常见阉割点：插件、SQL92 过滤、Stream）

迁移与共存：确实需要换或需要同时用两套时，做法是在应用侧抽一层薄接口，只抽象「发送一条带 key 的消息」和「订阅并幂等处理」这两件事，把事务消息、延迟级别、Exchange 绑定这类各家特有的能力显式暴露出去，而不是硬塞进统一接口。过度抽象的典型后果是：为了统一接口放弃了 RocketMQ 的事务消息和 RabbitMQ 的路由能力，最后得到一个功能等于交集的最小实现，两边的优势都用不上。切换期建议双写一段时间并对账，确认新链路的消息量与处理结果一致后再摘掉旧链路。

❌
最容易踩的坑
  • 拿「万级 / 十万级 / 百万级」当选型依据：这组数字来自多年前的单机测试，不同消息体和刷盘配置下结论会反转。要数字就用自己的参数压。
  • 新项目还在用镜像队列：3.9 起已废弃、4.0 已移除，且分区恢复后可能丢消息。直接用 Quorum Queue，副本数取 3 或 5。
  • RabbitMQ 不设 prefetch：默认无限预取，第一个消费者吃掉所有消息，后加的消费者空转，看起来像「扩容没效果」。
  • 用按消息 TTL 加死信做延迟队列：队首长 TTL 消息会阻塞后面的短 TTL 消息到期，延迟完全失控。改用固定档位队列或延迟插件。
  • 以为延迟插件是高可用的：未到期消息存在发布节点本地，该节点故障这些消息就没了，重要的延迟任务不要只依赖它。
  • 只声明队列持久化就以为消息不丢：Exchange、Queue、Message 三处都要持久化，缺一个都会丢，细节见可靠投递篇。
  • 把 RocketMQ 延迟级别当成秒数传：setDelayTimeLevel(3) 是第 3 级即 10 秒，不是 3 秒。4.x 里级别表还是 Broker 配置，改动要重启全集群。
  • 顺序消费里对失败消息无限重试：顺序消费是串行的，一条坏消息会把整个队列堵死，后面全部积压。必须有重试上限并主动搬去死信。
  • 线上给顺序消息的 Topic 扩队列数：按队列数取模的映射会整体变化，在途消息的顺序保证立刻失效。扩容前要先排空。
  • 事务消息的回查接口固定返回未知：回查 15 次后按回滚处理，消息被静默丢弃且没有任何业务报错。业务表必须存事务 ID 供回查。
  • 不知道 RocketMQ 死信主题默认不可读：死信主题默认只有写权限，不手动改权限就永远看不到死信，等发现时已经堆了几千条。
  • 抽象层做得太厚：为了「随时能换 MQ」抹平所有差异，结果事务消息、延迟消息、Exchange 路由全都用不上，白白付出两倍复杂度。
