熔断限流降级与舱壁隔离：状态机参数、慢调用熔断与容量反推

🏷️ 熔断降级

绝大多数「服务治理配了但没生效」的故障，根因不是没配，而是四件事被当成一件事在配：限流当熔断用、熔断没配降级、隔离压根没做、阈值靠感觉填。这篇按工程落地的顺序讲清楚：四个概念各自的作用方向、熔断器每个参数配错的具体后果、为什么慢调用比例比失败率更重要、线程池与信号量隔离怎么选、限流阈值怎么从压测反推出来。

一、限流、熔断、降级、隔离：四个不同方向的保护

先把概念钉死。这四者的区别不是「差不多的三板斧」，而是保护方向完全不同：限流管入口，熔断管出口，降级管功能取舍，隔离管资源边界。

手段保护谁不被谁伤害触发条件作用方向典型实现缺了它会发生什么
限流保护自己不被上游流量打死QPS 或并发数超过阈值入口方向令牌桶、漏桶、并发数信号量大促或爬虫流量直接把实例压到 OOM，所有请求一起变慢
熔断保护自己不被下游故障拖死对某下游的失败率或慢调用比例超阈值出口方向熔断器状态机加降级回调下游变慢时你的线程和连接被逐个占满，最终自己也挂
降级保护核心功能不被非核心功能拖累人工开关，或熔断、限流被触发后自动进入功能维度兜底数据、关功能、有损服务熔断打开后直接给用户抛 500，用户感受和服务挂了没区别
隔离保护资源池不被单个依赖耗尽无需触发，是常态的结构约束资源维度按依赖分线程池、分信号量、分实例组一个非核心依赖变慢就能占满共享线程池，核心链路陪葬

它们在一次调用里是层层叠加的，缺任何一层都留下一条故障放大的通路：

⚠️
两个默认值等于「你以为配了其实没配」

resilience4j 的 slowCallDurationThreshold 默认 60 秒、slowCallRateThreshold 默认 100%。如果你只改了失败率阈值就上线，慢调用熔断这条路径实际上完全没有开启——而生产上超过一半的下游故障是「变慢但不报错」。同样，minimumNumberOfCalls 默认 100 对很多内部接口来说过大，凌晨低峰期一分钟都不到 100 个请求，熔断器在最需要它的时段反而不工作。这两个参数必须显式设置，不要依赖默认值。

三、失败率不够用：慢调用才是主要死因

这是这篇文章最想纠正的一个认知：大家配熔断时第一反应都是配失败率，但真实故障里下游更常见的表现是变慢而不是报错。

下游故障形态下游返回什么失败率熔断能否触发慢调用熔断能否触发调用方实际发生什么
进程崩溃、端口不通连接被拒绝能，立刻触发能快速失败，影响可控
慢 SQL 上线、索引失效正确的 200，但耗时 3s不能能线程逐个被占住，池满后整体不可用
Full GC 或长时间停顿200，间歇性长尾不能，除非已经超时能P99 抬升，上游超时开始零星出现
下游线程池排队200，排队时间计入延迟不能能延迟随队列线性增长，直到上游超时
缓存击穿打到数据库200，耗时从 5ms 涨到 500ms不能能并发数按小定律成倍上升，连接池先被打满
下游返回业务错误码200 加业务失败码取决于是否被判为失败不能这种不该熔断，必须显式忽略

为什么慢调用比报错危险？因为并发数等于 QPS 乘以平均延迟（小定律）。下游延迟从 30ms 涨到 3s，在 QPS 不变的前提下，你需要的并发数直接涨 100 倍。1000 QPS 下 30ms 只需要 30 个并发，3s 就需要 3000 个并发——任何线程池和连接池都撑不住。所以慢调用会把调用方拖死，而报错反而是快速失败，负载不升反降。

四、舱壁隔离：所有依赖共用一个池是头号故障放大器

上面那张图的根因不是推荐服务变慢——变慢是不可避免的，根因是推荐和库存共用了同一个线程池。舱壁隔离要做的就是让这两者在物理上抢不到对方的资源。

维度线程池隔离信号量隔离
能否中断阻塞调用能。业务线程带超时等结果，超时就放弃，不管工作线程是否还卡着不能。被卡住的调用一直占着许可，直到它自己返回
额外开销一次线程切换加上下文拷贝，约 0.2ms 到 1ms一次原子操作，接近零
ThreadLocal 传递会丢，traceID 和用户上下文必须显式装饰后传递不丢，同线程执行
线程数膨胀严重。20 个依赖各 20 线程就是 400 线程，光栈内存就是几百 MB 量级无
适用场景远程调用，且客户端超时不可靠，比如老 HTTP 客户端、JDBC、某些厂商 SDK本地计算、纯内存操作、客户端超时可靠的调用
容量怎么算线程数约等于目标 QPS 乘以正常 P99 秒数再乘 1.5许可数用同一个公式算，但要卡在更小的值上
flowchart TB Q1{"这个依赖是远程调用还是本地计算"} -->|本地计算，不会长时间阻塞| S1["信号量隔离，开销最小"] Q1 -->|远程调用| Q2{"客户端的超时机制可靠吗"} Q2 -->|可靠，连接超时与读超时都能生效| S2["信号量隔离加严格客户端超时"] Q2 -->|不可靠或无法确认| Q3{"这个依赖的调用量大吗"} Q3 -->|调用量不大但必须能强制放弃| S3["线程池隔离，池子可以很小"] Q3 -->|调用量很大| S4["线程池隔离并按小定律算池大小
同时收紧超时以降低线程数"] S1 --> R1["无论哪种，绝不允许多个下游共用同一个池"] S2 --> R1 S3 --> R1 S4 --> R1
💡
比隔离更根本的一步：先收紧超时

线程池要多大由小定律决定，而延迟是你能控制的那一项。把某个依赖的超时从 5s 收到 500ms，同样 QPS 下需要的线程数直接降到十分之一。很多团队在「线程池该配多大」上纠结很久，实际上真正的问题是超时配得太松——5s 的超时意味着你愿意为一个非核心的推荐位卡住用户 5 秒，这在业务上根本不合理。先把超时按业务可接受值收紧，隔离的资源需求会自然降下来。

五、限流算法与阈值：单机还是分布式

算法能否平滑能否容忍突发内存代价失效场景
固定窗口计数否否一个计数器临界问题：阈值 100 时，第 0.99 秒来 100 个、第 1.01 秒再来 100 个，跨窗口的一秒内实际通过 200，瞬时是 2 倍阈值
滑动窗口计数近似平滑，取决于分桶粒度否N 个桶的计数，桶越细越准也越占内存桶粒度过粗仍有临界问题；单维度百万级 key 时内存不可忽视
漏桶是，出水速率恒定否，突发只能排队一个队列排队会把延迟拉长，对超时敏感的接口等于把快失败变成慢失败，往往更糟
令牌桶近似平滑是，桶容量即突发额度两个数：令牌数与上次补充时间桶容量设太大时，一次突发能打穿下游；容量应不超过 1 到 2 秒的补充量
并发数限制不控速率，只控在飞请求数不适用一个计数器最被低估的一种：它天然适配小定律，下游变慢时自动收紧放行量，比 QPS 限流更贴合真实容量

在选算法之前更该先想清楚限流计数放在哪：

方案准确性额外延迟主要风险适用
单机限流，总阈值除以副本数低，扩缩容后总阈值漂移0负载不均时部分副本提前误限；自动扩容后总容量意外翻倍副本数稳定、阈值不需要很精确
分布式限流，Redis 集中计数高每请求 1ms 到 3ms 往返Redis 成为新的强依赖，抖动直接传导到业务；必须约定计数失败时放过需要精确总量，如对外开放 API 的配额
本地预扣加定期同步中高，误差不超过一个批次摊薄后接近 0批次给太大时突发会超额；同步周期建议 200ms 到 1s大多数内部服务的推荐选择

六、降级的三个层次，以及没演练过的开关不敢按

层次做法用户感受前提条件典型例子
一、返回兜底数据用缓存快照、静态默认值、上一次成功结果几乎无感，数据略旧兜底数据必须在语义上安全推荐位返回运营配置的固定列表；配置项返回上次有效值
二、关闭非核心功能直接跳过该步骤，接口仍然成功少了某个模块调用链上这一步必须是可选的下单时跳过积分计算、跳过增强风控、隐藏「猜你喜欢」
三、有损服务降低精度或改成异步能用但打折业务侧提前同意这种折损库存只显示「有货」不给准确数字；写请求先入队列稍后落库；搜索只查最近 7 天
❌
兜底数据在语义上必须安全，不要返回零值

库存查询熔断后返回 0，会让全部可售商品显示售罄，直接损失订单；风控查询熔断后返回「通过」，等于在故障期间完全关闭风控；余额查询熔断后返回 0，用户会以为账户被清空并大量投诉。正确的兜底是返回「未知」并让调用方决定——对下单流程，库存未知时可以放行并由后续扣减兜底；对风控，未知时必须走保守策略拒绝或转人工。降级方向的选择是业务决策，不是技术默认值。

两条关于降级开关的硬要求：必须能不发布就切换，靠改代码重新发版的降级在故障现场毫无价值（发布链路本身通常也在故障影响范围内），所以开关要放配置中心并有本地缓存兜底，见站内配置中心篇；必须定期演练，没有在演练环境按过的开关，没人知道按下去会发生什么，故障时的真实反应一定是「不敢按」。演练要覆盖开关打开后的功能表现、开关关闭后能否恢复、以及开关推送失败时的行为。

七、代码：熔断加降级回调加指标暴露

先看 Java 侧。resilience4j 的关键点不是 API 怎么写，而是三处容易写错的地方：慢调用阈值要显式设、业务异常要忽略、指标要绑到 Micrometer 否则线上熔断了监控上看不见。

@Configuration
public class ResilienceConfig {

    @Bean
    public CircuitBreakerRegistry circuitBreakerRegistry(MeterRegistry meterRegistry) {
        CircuitBreakerConfig config = CircuitBreakerConfig.custom()
            // 时间窗口比计数窗口更适合流量稳定的接口：故障恢复后统计会自然滚出去
            .slidingWindowType(CircuitBreakerConfig.SlidingWindowType.TIME_BASED)
            .slidingWindowSize(60)                              // 统计最近 60 秒
            .minimumNumberOfCalls(20)                           // 低于 20 次不判定，防低峰误熔断
            .failureRateThreshold(50f)
            // 下面两行是重点：默认 60s 与 100% 等于慢调用熔断没开
            .slowCallDurationThreshold(Duration.ofMillis(800))  // 取正常 P99 的 2 到 3 倍
            .slowCallRateThreshold(50f)
            .waitDurationInOpenState(Duration.ofSeconds(15))
            .permittedNumberOfCallsInHalfOpenState(5)           // 半开必须限量试探
            .automaticTransitionFromOpenToHalfOpenEnabled(true) // 无流量时也能自动转半开
            .recordExceptions(IOException.class, TimeoutException.class)
            // 业务异常绝不能算熔断失败，否则用户输错参数就能把下游熔断
            .ignoreExceptions(BusinessException.class, IllegalArgumentException.class)
            .build();

        CircuitBreakerRegistry registry = CircuitBreakerRegistry.of(config);
        // 不绑指标等于线上熔断了你在 Grafana 上看不到，排查时只能猜
        TaggedCircuitBreakerMetrics.ofCircuitBreakerRegistry(registry).bindTo(meterRegistry);
        return registry;
    }

    @Bean
    public ThreadPoolBulkheadRegistry bulkheadRegistry() {
        // 舱壁：线程数按 目标QPS 乘 P99秒数 乘 1.5 估算，不要所有依赖共用
        return ThreadPoolBulkheadRegistry.of(ThreadPoolBulkheadConfig.custom()
            .maxThreadPoolSize(24)
            .coreThreadPoolSize(16)
            .queueCapacity(50)   // 队列不能无界，无界队列会吃穿内存且延迟无上限
            .build());
    }
}

@Service
public class InventoryClient {

    private final CircuitBreaker breaker;
    private final MeterRegistry meters;
    private final InventoryRpc rpc;

    public InventoryClient(CircuitBreakerRegistry registry, MeterRegistry meters, InventoryRpc rpc) {
        // 每个下游一个独立熔断器实例，名字就是依赖名，便于监控分组
        this.breaker = registry.circuitBreaker("inventory-rpc");
        this.meters = meters;
        this.rpc = rpc;
        // 状态变更打点，这是事后复盘唯一可靠的依据
        this.breaker.getEventPublisher().onStateTransition(e ->
            meters.counter("cb.transition",
                "name", e.getCircuitBreakerName(),
                "to", e.getStateTransition().getToState().name()).increment());
    }

    public InventoryView query(long skuId) {
        Supplier<InventoryView> decorated =
            CircuitBreaker.decorateSupplier(breaker, () -> rpc.query(skuId));
        try {
            return decorated.get();
        } catch (CallNotPermittedException e) {
            // 熔断已打开：这条分支不代表下游挂了，代表我们主动不打它
            return fallback("circuit-open");
        } catch (Exception e) {
            return fallback(e.getClass().getSimpleName());
        }
    }

    private InventoryView fallback(String reason) {
        meters.counter("inventory.fallback", "reason", reason).increment();
        // 关键：返回 UNKNOWN 而不是 0。返回 0 会让全部商品显示售罄
        return InventoryView.unknown();
    }
}

Go 侧用 gobreaker，它本身只有失败率判定，慢调用必须靠「给每次调用一个硬超时，超时即记失败」来间接实现——这也是所有轻量熔断库的通用做法。

package inventory

import (
	"context"
	"errors"
	"time"

	"github.com/sony/gobreaker"
)

// 每个下游一个熔断器实例，绝不要全局共用一个
var breaker = gobreaker.NewCircuitBreaker(gobreaker.Settings{
	Name:        "inventory-rpc",
	MaxRequests: 5,                // HalfOpen 状态允许放行的试探请求数，必须限量
	Interval:    60 * time.Second, // Closed 状态下计数清零周期，等价于统计窗口
	Timeout:     15 * time.Second, // Open 持续时间，到期自动转 HalfOpen
	ReadyToTrip: func(c gobreaker.Counts) bool {
		// 最小请求数阈值：样本不足时失败率没有统计意义，直接不判定
		if c.Requests < 20 {
			return false
		}
		failRatio := float64(c.TotalFailures) / float64(c.Requests)
		return failRatio >= 0.5
	},
	OnStateChange: func(name string, from, to gobreaker.State) {
		// 状态变更一定要上报，否则线上熔断过你完全不知道
		breakerState.WithLabelValues(name).Set(stateCode(to))
		log.Warnf("breaker %s state %s to %s", name, from, to)
	},
})

// QueryInventory 对外不返回错误，而是返回降级结果，让调用方链路不被打断
func QueryInventory(ctx context.Context, skuID int64) View {
	// 硬超时是慢调用熔断的前提：没有超时，慢调用永远不会被计为失败
	callCtx, cancel := context.WithTimeout(ctx, 800*time.Millisecond)
	defer cancel()

	v, err := breaker.Execute(func() (interface{}, error) {
		res, err := rpcClient.Query(callCtx, skuID)
		if err != nil {
			return nil, err
		}
		// 业务失败码不算熔断失败：用户传了不存在的 SKU 不该把下游熔断
		return res, nil
	})

	if err != nil {
		reason := "rpc_error"
		if errors.Is(err, gobreaker.ErrOpenState) {
			reason = "circuit_open"
		} else if errors.Is(err, context.DeadlineExceeded) {
			reason = "timeout"
		}
		fallbackCounter.WithLabelValues("inventory", reason).Inc()
		// 降级返回 Unknown，由调用方决定放行还是保守处理
		return View{Status: StatusUnknown}
	}
	return v.(View)
}

八、阈值不能拍脑袋：用压测反推

拍脑袋定阈值有两种错法，而且都会导致整套保护形同虚设：定得比正常业务波动还低，高峰期天天误触发，最后团队把熔断限流全关掉；定得远高于真实容量，出事时压根不生效。

# 1) 阶梯加压，找单实例的拐点。关键是「阶梯」而不是一次打满
#    每档持续 3 分钟以上，观察吞吐是否还在涨、P99 是否开始非线性抬头
for c in 10 20 40 80 160 320; do
  echo "=== concurrency $c ==="
  wrk -t8 -c$c -d180s --latency --timeout 5s \
      -s post_order.lua http://10.0.1.21:8080/api/order/create
  sleep 60   # 必须留恢复时间，否则下一档测的是上一档的余波
done

# 2) 同时在被压实例上看饱和度信号，判断瓶颈在哪
#    线程池活跃数接近上限、队列开始堆积  => 瓶颈在下游调用
#    CPU 到 90% 而线程池仍有空闲         => 瓶颈在本地计算
jcmd $(pgrep -f order-service) Thread.print | grep -c "http-nio.*runnable"

# 数据库侧同时看有多少事务在等锁，判断瓶颈是否已经下移到 DB
mysql -h db -N -e "select count(*) from information_schema.innodb_trx where trx_state='LOCK WAIT'" 2>&1

# 3) 从拐点反推阈值
#    假设拐点为：单实例 1200 QPS、此时 P99 等于 180ms、并发约 220
#    单机限流阈值 = 1200 * 0.7 = 840 QPS   留 30% 余量给突发与 GC
#    并发数限制   = 220 * 0.8  = 176       比 QPS 限流更贴合真实容量
#    慢调用阈值   = 180 * 2.5  = 450ms     正常 P99 的 2 到 3 倍
#    调用超时     = 450 * 1.5  约 700ms    大于慢调用阈值，小于上游剩余预算
#    集群限流阈值 = 840 * 副本数           每次扩缩容后必须复核这一项

拐点的判定标准是吞吐不再随并发增长，而 P99 开始加速上升。很多人把「刚开始报错」当成上限，那已经晚了——过了拐点之后系统实际处在排队状态，再加压只会让延迟爆炸而处理能力不变，这个区间的数据不能作为容量依据。

九、反模式清单

反模式现场表现正确做法
熔断阈值比正常波动还低每天高峰期都有熔断告警，团队麻木后直接关掉失败率不低于 40%，慢调用阈值取 P99 的 2 到 3 倍，并配最小请求数
熔断后直接抛错给用户用户看到 500，体感与服务挂掉无差别每个熔断点都必须配兜底回调，且兜底值语义安全
只在网关限流，服务自身无保护内网调用、定时任务、数据回刷绕过一切保护把实例打死服务侧也要有接口级并发与 QPS 限制
所有接口共享一个限流阈值一个低价值的导出接口把整个实例的额度吃完按接口分组配额，核心接口单独保留额度
所有下游共用一个线程池非核心依赖变慢，核心链路一起失败按依赖隔离，并优先收紧超时以降低线程需求
无界队列加长超时队列里堆了几万个已经超时的任务，处理完也没人要了队列有界，并在出队时检查剩余时间，过期直接丢弃
熔断状态不上报事后复盘只能看到「那段时间接口成功率低」，不知道是自己熔断了状态转换打点加降级次数打点，并按依赖名分组
业务异常计入熔断失败大量用户输错参数导致下游被熔断，真实下游完全健康显式忽略业务异常，只统计技术失败
降级开关只能靠发布切换故障时发布链路也受影响，开关按不下去开关走配置中心热更新，并有本地兜底
降级从未演练故障时没人敢按，开关等于不存在纳入定期故障演练，验证打开、关闭、推送失败三种情况

熔断降级解决的是「下游坏了我怎么活」，而跨服务的数据一致性、幂等、补偿是另一个维度的问题，站内分布式系统核心已完整展开 TCC、Saga、本地消息表与幂等的四种落地方式，这里不再重复。

❌
最容易踩的坑

1. 只配失败率不配慢调用比例，下游变慢但不报错时熔断器全程不动，直到自己线程池耗尽。
2. resilience4j 的 slowCallDurationThreshold 保持默认 60s、slowCallRateThreshold 保持默认 100%，慢调用熔断实际没开。
3. 漏配最小请求数阈值，凌晨两个偶发失败就把失败率算成百分之百，误熔断整条链路。
4. 半开状态不限制试探请求数，全量流量瞬间涌向刚恢复的下游，造成熔断反复震荡。
5. 把参数校验、余额不足这类业务异常算作熔断失败，用户输错参数就能熔断下游。
6. 兜底返回 0 而不是「未知」，库存 0 让全站商品显示售罄，风控放过等于关闭风控。
7. 所有下游共用一个线程池，一个非核心依赖的 5s 超时把核心链路全部拖死。
8. 线程池用无界队列，请求在队列里排到早已超时，处理完的结果没人接收，内存还被吃穿。
9. 远程调用不配硬超时，慢调用永远不会被计为失败，熔断器没有任何输入。
10. 熔断状态和降级次数不打点，事后完全无法区分「下游挂了」和「我自己熔断了」。
11. 单机限流阈值按副本数均摊后忘了跟自动扩缩容联动，扩容一倍总容量也翻倍，等于限流失效。
12. 分布式限流不配「Redis 失败时放过」，Redis 一抖动全站请求被拒，限流组件自己成了故障源。
13. 降级开关从未演练，故障现场没人敢按，等于这个开关不存在。
14. 把拐点之后的压测数据当成容量上限，实际那已经是排队区间，阈值定得远高于真实承载。
