网关的数据面实现与部署形态

🏷️ API 网关

本篇只写实现层与部署层：两条技术路线的架构差异、xDS 动态配置、与服务网格的关系、部署拓扑与容量规划、配置发布流程。网关的责任边界（责任链模型、为什么不放业务逻辑、认证与鉴权的分工、重试风暴、超时预算分配、六种网关选型）在 API 网关的责任边界 里写透了；Nginx 的 11 个处理阶段、location 优先级、proxy_buffering、上游长连接与 limit_req 三形态见 Nginx 深入；三块治理基础设施的共性见 服务治理的三块基础设施。

两条技术路线：多进程加 Lua，与单进程加 xDS

市面上所有网关，数据面本质只有两条路线。第一条是 Nginx 血脉：master 加多 worker 的多进程模型，配置来自静态文件，扩展通过 Lua（OpenResty、APISIX、Kong）实现。第二条是 Envoy 血脉：单进程多线程，配置完全由控制面通过 xDS 协议动态下发，扩展通过 WASM 或 C++ filter 实现。这个差异决定了两类网关在「配置变更能不能不重启生效」这件事上的根本不同。

关键点在于四类资源可以独立推送：一次扩容只会推送 EDS，路由调整只推 RDS，监听端口不变就不动 LDS。数据面收到后在内存里构建新的配置快照并原子切换，worker 线程下一个请求就读到新配置，已有连接不受任何影响。对比 Nginx 修改 upstream 后必须 reload，差异不是「快一点」，而是「有没有中断」。

xDS 为什么关键，以及 reload 的隐性代价

「改配置 reload 一下」在实例数少、变更不频繁时完全够用。问题出现在两个条件叠加之后：后端实例数量多且经常变化（容器环境里扩缩容与滚动更新是常态），网关实例本身也有几十台。此时每次变更都要在所有网关实例上执行 reload，动作放大、耗时不可控，而且 reload 有实打实的副作用。

sequenceDiagram autonumber participant K as 编排系统 participant C as 控制面 participant E as Envoy 数据面 participant N as Nginx 数据面 Note over K,E: 路线一：xDS 推送 K->>C: Pod 就绪，端点列表变化 C-->>E: 只推送 EDS 增量，含新增与删除的端点 E->>E: 构建新集群快照并原子替换（毫秒级） Note over E: 已建立的连接完全不受影响
下一个请求即用新端点 Note over K,N: 路线二：改文件加 reload K->>N: 变更被写入配置文件，触发 reload N->>N: master 校验配置，拉起新 worker N->>N: 旧 worker 停止接收新连接，等待存量请求完成 Note over N: 长连接不会自然结束
worker_shutdown_timeout 到期后被强制关闭 N->>N: 旧 worker 退出，期间内存占用接近翻倍
⚠️
把 reload 当成无损热更新，是长连接业务最常见的事故来源

reload 对短连接几乎无感，于是很多人以为它无损。但 WebSocket、gRPC 流、SSE 这类长连接不会自然结束：旧 worker 会一直等到 worker_shutdown_timeout 到期（默认 240 秒），然后强制关闭剩余连接。很多团队为了让 reload 快点完成把这个值调到几秒，结果每次 reload 都批量掉线。另一个隐性代价是频繁 reload 时大量旧 worker 并存，内存占用接近翻倍，配合 Lua 的共享字典还可能触发额外的内存压力。长连接业务要么用 xDS 路线，要么至少把网关按协议拆组，让长连接组的配置尽量不变。

# Envoy bootstrap：把全部配置交给控制面，本地只保留「怎么找到控制面」

Nginx 路线要做到免 reload 的动态 upstream，标准解法是 balancer_by_lua：把端点列表放进共享内存，由一个后台定时器从注册中心同步，请求阶段再从共享内存里选址。APISIX 与 Kong 的动态能力本质就是这套机制的产品化。

-- OpenResty 动态 upstream：端点放共享内存，请求阶段现选，改后端不需要 reload
-- nginx.conf 需先声明：lua_shared_dict upstream_cache 10m;
-- 以及 upstream 占位：upstream dyn_backend { server 0.0.0.1; balancer_by_lua_file /path/balancer.lua; }

local balancer = require "ngx.balancer"
local cjson = require "cjson.safe"
local cache = ngx.shared.upstream_cache

-- init_worker 阶段起一个定时器同步端点；只在 worker 0 上跑，避免 N 个 worker 重复拉取
local function sync(premature)
    if premature then return end
    local http = require "resty.http"
    local httpc = http.new()
    httpc:set_timeout(1000)                      -- 同步是后台行为，超时要短，绝不影响请求
    local res, err = httpc:request_uri(
        "http://nacos.internal:8848/nacos/v1/ns/instance/list?serviceName=order-service")
    if res and res.status == 200 then
        local body = cjson.decode(res.body)
        if body and body.hosts and #body.hosts > 0 then   -- 关键：空列表不覆盖，防止一次异常摘空
            cache:set("order-service", cjson.encode(body.hosts))
        end
    else
        ngx.log(ngx.ERR, "sync endpoints failed: ", err or res.status)  -- 失败保留旧值
    end
    ngx.timer.at(5, sync)                        -- 5 秒一轮，兼顾摘除延迟与注册中心压力
end
if ngx.worker.id() == 0 then ngx.timer.at(0, sync) end

-- balancer 阶段：只读共享内存，绝不发起任何网络请求
local raw = cache:get("order-service")
local hosts = raw and cjson.decode(raw)
if not hosts or #hosts == 0 then
    return ngx.exit(503)                         -- 无可用端点时明确失败，不要瞎转发
end

local state, code = balancer.get_last_failure()
local tries = ngx.ctx.tries or 0
if state then                                    -- 上一次尝试失败了，换一台重试
    ngx.ctx.tries = tries + 1
    if tries < 2 then balancer.set_more_tries(1) end  -- 重试上限必须设，否则会放大成重试风暴
end

local h = hosts[(ngx.worker.pid() + tries) % #hosts + 1]
local ok, err = balancer.set_current_peer(h.ip, h.port)
if not ok then ngx.log(ngx.ERR, "set_current_peer failed: ", err) return ngx.exit(502) end
balancer.set_timeouts(1, 3, 5)                   -- 连接、发送、读取超时，必须小于上游预算

网关与服务网格：南北向与东西向

两者经常被混为一谈，划清边界其实很简单：网关处理南北向流量（外部进入内部），关注认证、对外协议、统一入口与外部限流；网格处理东西向流量（服务之间互相调用），关注重试、超时、熔断、双向 TLS 与调用拓扑。Envoy 能同时扮演两者，Istio 的入口网关本身就是一个 Envoy，只是配置的是南北向策略。

网格最被低估的成本是排障复杂度：流量被透明劫持后，一个 503 可能来自应用、来自本端 sidecar、来自对端 sidecar，也可能来自控制面下发的配置。团队需要专门积累这类经验，也要习惯用代理的 admin 接口去看当前生效的配置。服务数不多时，这个成本换不回相应收益。

部署拓扑：为什么要拆多组网关

网关在 LB 之后还是之前？标准答案是四层 LB 在前、网关在后：LB 只做四层转发与健康检查，负责把流量均摊到网关实例，网关做七层处理。公有云环境通常是云 LB 加网关组，自建则是 LVS 或硬件负载均衡加网关组。网关实例必须无状态，会话、限流计数、缓存都不能只存在于单实例内存里，否则实例替换就会丢状态。

更重要的决策是拆成几组。全站一组网关的问题非常直接：任何一个业务线的配置错误、插件异常、流量突增都会影响所有业务。按维度拆多组是常见且正确的做法，代价是实例数与配置管理成本上升，所以拆分维度要对齐故障隔离诉求，而不是对齐组织架构。

拆分维度怎么拆隔离了什么风险代价建议
按业务线交易、内容、支付各一组一个业务线的配置错误或流量洪峰不影响其他业务线实例数倍增，配置模板要统一维护最推荐的第一刀，尤其是有核心与非核心之分时
按流量性质对外开放 API 与内部管理后台分开管理后台的弱认证与调试接口不暴露在对外入口上多一组域名与证书管理安全收益很高，强烈建议拆
按协议普通 HTTP 与 WebSocket、gRPC 流分开长连接组的配置尽量不变，避免被别人的 reload 波及需要区分域名或端口长连接量大时必拆
按机房或可用区每个机房一组，各自对接本机房注册中心机房级故障被隔离，跨机房调用显式化需要上层 DNS 或全局 LB 做机房级调度多机房部署的标准做法
按大客户或租户为个别超大流量客户单独一组大客户流量波动不影响公共入口运维对象增多，容易失控只在确有超大单一来源时才做

容量规划：短连接看 CPU，长连接看内存与句柄

网关是全站流量的必经点，不能按满负载规划。常态单实例负载建议控制在五成以下，才有空间承接单实例故障时的流量转移与突发。估算分两类场景，瓶颈完全不同。

场景主要瓶颈量级参考估算方式容易忽略的点
短连接、纯七层转发CPU单核每秒几千到上万请求，取决于插件数量与日志量峰值 QPS 除以单核能力，再乘二倍冗余访问日志同步写盘会显著吃掉吞吐，高 QPS 下必须缓冲或异步
启用 TLS 终止握手时的 CPU新建 TLS 连接的开销是复用连接的几十倍按每秒新建连接数单独估算，而不是按总 QPS会话复用与 OCSP 装订没配好时，握手成本被成倍放大
长连接，如 WebSocket 与 SSE内存与文件句柄单连接在网关侧常占几 KB 到几十 KB，十万连接可达数 GB并发连接数乘以单连接内存，加上缓冲区配置系统级与进程级句柄上限都要调；连接数还受端口与连接跟踪表限制
大请求体或文件上传内存与磁盘缓冲缓冲区配置不当时单请求可占用数 MB并发上传数乘以缓冲区大小缓冲落盘时磁盘 IO 成为新瓶颈，必要时直接流式透传
上游连接池与上游的连接数每个网关实例对每个上游维持几十到几百条长连接网关实例数乘以上游数乘以每上游连接数网关实例越多，上游承受的总连接数越大，扩网关可能压垮后端
💡
扩网关实例可能反而压垮后端

这是容量规划里最反直觉的一条：上游总连接数等于网关实例数乘以每实例连接池大小。把网关从 10 台扩到 40 台，如果每实例对每个上游保持 100 条长连接，上游承受的连接数就从 1000 涨到 4000。对连接敏感的后端（例如按连接分配线程或内存的服务）可能直接被打挂。扩容网关时必须同步下调单实例连接池上限。

限流、灰度与流量镜像的数据面实现

限流的算法与参数在 限流 和 Nginx 深入 里已经写过，这里只讲数据面的一个实现选择：计数放在哪里。这个决定直接影响阈值准不准以及每请求的开销。

方案怎么工作阈值准确度每请求开销失效场景
纯本地计数每个网关实例独立计数，阈值按实例数均分低：实例数变化或流量倾斜时实际阈值漂移近乎为零，纯内存操作网关扩缩容后没有同步调整均分值，实际总阈值翻倍或腰斩
集中式计数每请求去 Redis 等共享存储做原子增减高：全局视图准确每请求多一跳，通常 0.3 到 1 毫秒，且引入外部依赖共享存储抖动时限流组件变成故障源，必须设计好降级为本地计数
本地预扣加定期同步本地先扣一小批配额，周期性与中心对账并领取新配额中高：允许小幅超发，但总量可控接近本地计数，同步在后台进行配额批次给得太大时，突发流量会在一个周期内超发较多

实践上第三种是默认选择：请求路径不引入外部依赖，同时总阈值可控。这与前面「控制面不进请求路径」是同一个原则的不同表现。

灰度与流量镜像在数据面的实现都依赖路由的加权与复制能力。灰度是按权重或请求属性把流量分给不同的上游集群，按请求头或用户标识做一致性分流比纯随机百分比更实用，因为同一用户始终落在同一版本上，体验一致也便于排查。流量镜像是把请求复制一份异步发给影子集群，并丢弃其响应，用于用真实流量验证新版本。镜像有两个必须注意的点：镜像流量不能触达写接口或真实的下游依赖，否则会产生脏数据；镜像本身会给网关增加约一倍的出向连接开销，要计入容量。

可观测性：网关是最佳采集点，但标签要收敛

网关能看到所有外部请求的完整信息：状态码、耗时、上游、路由、客户端特征，是采集黄金信号的最佳位置——业务侧指标可能因为各服务埋点不一致而无法横向比较，网关侧则天然统一。但正因为流量全打这里，指标基数是第一号风险。

标签选择基数量级后果正确做法
原始请求路径与请求数同阶，可达百万级时间序列爆炸，监控系统内存耗尽甚至被打挂用路由模板，例如把路径中的编号替换为占位符
客户端 IP十万到百万级同上，且对排障几乎无帮助不进指标，需要时查访问日志或链路
User-Agent 原文数万级基数高且值本身很长，存储放大归一化成几类客户端，如 iOS、Android、Web、爬虫
路由模板加方法加状态码路由数乘以方法数乘以状态码数，通常几千级可接受，且足以支撑绝大多数告警与看板推荐的默认组合
上游集群名与服务数同阶，几百级可接受，定位「哪个后端在拖后腿」非常有用建议保留
# 网关侧黄金信号：四条查询覆盖流量、错误、延迟与饱和度
# 前提：指标标签只用 route 模板、method、status、upstream，绝不用原始 path

# 1. 错误率，按路由排序，直接定位是哪个路由在报错
topk(10,
  sum by (route) (rate(gateway_requests_total{status=~"5.."}[5m]))
  / sum by (route) (rate(gateway_requests_total[5m]))
)

# 2. 延迟 P99，按上游聚合，用来区分「网关慢」还是「后端慢」
histogram_quantile(0.99,
  sum by (le, upstream) (rate(gateway_request_duration_seconds_bucket[5m]))
)

# 3. 网关自身耗时占比：总耗时减去上游耗时，异常升高说明是网关侧问题
sum(rate(gateway_request_duration_seconds_sum[5m]))
  - sum(rate(gateway_upstream_duration_seconds_sum[5m]))

# 4. 饱和度：活跃连接数占上限比例，长连接场景下这条比 CPU 更早预警
max by (instance) (gateway_active_connections) / 100000

# 配置停止更新的告警（Envoy）：控制面断连后配置会静默僵化，必须单独监控
min by (instance) (envoy_control_plane_connected_state) == 0

配置发布：全站风险最高的一次变更

一次错误的网关配置能让全站 502，而且故障是瞬时全量的，没有任何缓冲。因此网关配置必须像代码一样管理：入库、评审、自动校验、灰度、可自动回滚。手工登录机器改配置文件是最危险的做法——它既没有评审，也没有版本，故障时没人知道改了什么。

# 网关配置发布的最小可用流水线：校验 -> 灰度一台 -> 看指标 -> 推全或回滚
set -euo pipefail

# 1. 语法校验：这一步在 CI 里跑，不通过不允许合并
nginx -t -c /etc/nginx/nginx.conf                      # Nginx 系
envoy --mode validate -c /etc/envoy/envoy.yaml         # Envoy 系，只校验不启动

# 2. 语义检查示例：禁止出现指向空 upstream 的路由（这类错误语法校验查不出来）
grep -rn 'proxy_pass' /etc/nginx/conf.d/ | awk '{print $NF}' | tr -d ';' \
  | sed 's|http://||' | sort -u \
  | while read -r up; do
      grep -qr "upstream[[:space:]]\+$up" /etc/nginx/conf.d/ || echo "!! upstream 未定义: $up"
    done

# 3. 灰度一台：先摘掉 LB 上的权重，再 reload，确认无误后恢复权重
CANARY=10.0.3.11
curl -sS -X POST "http://lb-admin/weight?node=${CANARY}&weight=1"   # 只给约 1% 流量
ssh "$CANARY" 'nginx -t && systemctl reload nginx'

# 4. 观察 3 分钟，比较灰度实例与集群整体的 5xx 率，超阈值立即回滚
sleep 180
RATE=$(curl -sS --data-urlencode \
  "query=sum(rate(gateway_requests_total{instance=\"${CANARY}\",status=~\"5..\"}[3m]))/sum(rate(gateway_requests_total{instance=\"${CANARY}\"}[3m]))" \
  http://prom:9090/api/v1/query | python3 -c 'import sys,json;r=json.load(sys.stdin)["data"]["result"];print(r[0]["value"][1] if r else 0)')
echo "canary 5xx rate=$RATE"
awk -v r="$RATE" 'BEGIN{exit !(r+0 > 0.01)}' && {
  ssh "$CANARY" 'cp /etc/nginx/nginx.conf.bak /etc/nginx/nginx.conf && systemctl reload nginx'
  echo "已自动回滚灰度实例"; exit 1
}

# 5. 逐批推进，每批之间留观察窗口，绝不一次性全推
for batch in "10.0.3.12 10.0.3.13" "10.0.3.14 10.0.3.15 10.0.3.16"; do
  for h in $batch; do ssh "$h" 'nginx -t && systemctl reload nginx'; done
  sleep 120
done

反模式

反模式为什么有人这么做后果正确做法
网关配置手工改不入库紧急处理时图快没有版本与评审，故障时无人知道改了什么；机器重装后配置丢失配置入仓库，走评审与流水线，机器上的配置只由流水线产生
所有业务共用一组网关省机器、省运维一个业务线的配置错误或洪峰影响全站至少按业务线与流量性质拆组，核心与非核心分离
把 reload 当无损热更新短连接场景下确实看不出问题长连接被 worker_shutdown_timeout 强制切断，每次发布批量掉线长连接走 xDS 路线或单独拆组，并显式设置足够的关闭超时
网关里做重逻辑或查数据库「反正请求都经过这里」网关变成有状态、有慢依赖的组件，一次慢查询拖垮全站入口网关只做通用横切能力，业务逻辑回到服务里，详见责任边界篇
限流阈值全站共用一个配置简单一个接口被刷会把整体配额吃光，正常业务一起被限按路由与调用方分别设阈值，核心接口单独预留配额
升级不灰度觉得网关无状态、随便换新版本的兼容性问题瞬间全量暴露，且回滚期间仍在故障先灰度一台并观察，再按批次推进，保留一键回滚
指标用原始路径做标签看板上能看到每个 URL 很方便时间序列爆炸，监控系统被网关自己的指标打挂用路由模板收敛标签，明细查日志与链路
❌
最容易踩的坑
  • 为了让 reload 更快把 worker_shutdown_timeout 调成几秒，长连接业务每次发布都批量掉线。
  • Envoy 与控制面之间不开 keepalive，NAT 静默断连后配置停止更新，进程看起来完全正常。
  • 不监控控制面连接状态，配置僵化数天后才在一次扩容不生效时被发现。
  • 网关扩容后没有下调单实例上游连接池上限，上游总连接数翻几倍把后端打挂。
  • 启用 TLS 终止后只按总 QPS 估算容量，忽略新建握手的 CPU 开销，大促时网关先被打满。
  • 长连接场景只调了进程级句柄上限，忘了系统级上限与连接跟踪表，连接数卡在某个值上不去。
  • 流量镜像打到了带写操作的影子环境，产生了一批脏数据。
  • 把限流计数放 Redis 且没有降级路径，Redis 抖动时网关整体拒绝请求。
  • 灰度分流用纯随机百分比，同一用户在新旧版本之间来回跳，用户投诉且难以复现。
  • 访问日志同步写本地磁盘且没有缓冲，高峰期磁盘 IO 成为瓶颈，请求延迟整体抬升。
  • 网关只做了一组且与后端服务混部，后端把节点资源打满时入口一起不可用。
  • 配置只做了语法校验没有语义校验，一个指向不存在 upstream 的路由通过了流水线，上线即 502。
