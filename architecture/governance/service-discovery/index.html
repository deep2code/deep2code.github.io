服务注册发现的机制与故障模式

🏷️ 服务发现

本篇写注册发现的实现机制与故障模式：三种发现模式、健康检查的盲区、摘除延迟的四段叠加、优雅下线、保护模式、就近路由与多机房。三块治理基础设施的共性与 AP 选型结论见 服务治理的三块基础设施；配置中心的服务端机制见 配置中心的服务端机制与选型；重试与熔断的参数细节见 熔断与重试；K8s 的 Service 与 Endpoints 语义见 Kubernetes 核心资源。

注册发现解决的是「地址随时在变」

单体时代地址写在配置文件里就够了，因为一年也不改几次。微服务加容器之后，实例地址变化成了常态：扩缩容、故障自愈替换、滚动更新、节点驱逐、单元切换，每一次都在改变「某个服务当前有哪些可用地址」。注册发现要做的就是把这份随时在变的地址清单，及时、准确地送到每一个调用方手里。

注意这句话里有三个互相冲突的要求：及时（延迟要低）、准确（不要给死实例）、送到每个调用方（扇出大）。后面所有的机制和故障，本质都是在这三者之间做取舍。

注册的两种来源：自注册与平台注册

应用自注册是应用启动后自己调注册中心的接口把自己加进去，再靠心跳维持。优点是不依赖平台、任何部署形态都能用；缺点是注册逻辑散落在每个应用里，注册的地址由应用自己决定，最常见的事故就是注册了一个不可达的地址：容器里注册了 Docker 的内部 IP、多网卡机器上选错了网卡、或者注册了容器端口而不是映射后的主机端口。

平台自动注册是编排系统替应用完成注册。K8s 的 Endpoints 与 EndpointSlice 就是典型：Pod 通过就绪探针后，控制器把它的地址写进去；Pod 进入终止状态时自动移除。应用里没有一行注册代码，也就不会出现注册错地址的问题。这也是为什么全量跑在 K8s 上时往往不需要额外的注册中心，除非你需要跨集群发现、实例级元数据路由，或者框架强绑定了某个注册中心的生态。K8s 侧的控制循环与探针语义见 Kubernetes 核心资源。

⚠️
平台注册不代表没有摘除延迟

很多人以为用了 K8s Service 就不存在摘除延迟。实际上 Pod 终止时，EndpointSlice 的变更要经过 API Server、控制器、再到每个节点的 kube-proxy 或 CNI 更新转发规则，这个链路同样是几百毫秒到几秒；如果前面还有 Ingress 或自建网关，又多一段缓存。所以无论平台注册还是自注册，preStop 里的等待与优雅下线都必须做。

健康检查的四种机制与各自盲区

注册中心判断「一个实例还活着吗」只有四种手段，每一种都有明确的盲区。选择健康检查方式，实际上是在选择你愿意接受哪一类误判。

业务健康接口实例自己判断依赖是否可用后返回状态取决于探测方的周期最准，但要求应用实现；接口里串行检查所有下游依赖是典型错误，会造成一个非核心依赖抖动导致全部实例被判不健康的雪崩K8s readinessProbe，默认 periodSeconds 10、failureThreshold 3

// 这个接口挂了意味着要重启进程，所以绝不能因为数据库抖动而失败
func liveness(w http.ResponseWriter, r *http.Request) {
    w.WriteHeader(http.StatusOK)
    _, _ = w.Write([]byte("ok"))
}

// 就绪检查：回答「现在该不该给我发流量」，检查强依赖，且必须带缓存与超时
type Readiness struct {
    db       *sql.DB
    mu       sync.RWMutex
    lastOK   bool
    lastTime time.Time
    draining atomic.Bool // 优雅下线开始后置为 true，让探测立刻失败
}

func (rd *Readiness) Handler(w http.ResponseWriter, r *http.Request) {
    if rd.draining.Load() {
        http.Error(w, "draining", http.StatusServiceUnavailable) // 下线中：主动拒绝新流量
        return
    }
    if !rd.check() {
        http.Error(w, "dependency down", http.StatusServiceUnavailable)
        return
    }
    w.WriteHeader(http.StatusOK)
}

func (rd *Readiness) check() bool {
    rd.mu.RLock()
    // 结果缓存 2 秒：探测方可能是注册中心加网关加 K8s 三家同时来探，不能每次都真查一遍
    if time.Since(rd.lastTime) < 2*time.Second {
        ok := rd.lastOK
        rd.mu.RUnlock()
        return ok
    }
    rd.mu.RUnlock()

    // 超时必须远小于探测方的超时，否则探测方先超时，你的检查结果毫无意义
    ctx, cancel := context.WithTimeout(context.Background(), 800*time.Millisecond)
    defer cancel()
    err := rd.db.PingContext(ctx) // 只查强依赖：没它就真的处理不了请求

    rd.mu.Lock()
    rd.lastOK, rd.lastTime = err == nil, time.Now()
    rd.mu.Unlock()
    return err == nil
}

摘除延迟：服务发现最核心的指标

如果只允许用一个指标衡量注册发现做得好不好，那就是摘除延迟：从实例真正不可用，到最后一个调用方不再向它发请求，一共过了多久。这个时间不是单一环节，而是四段延迟的叠加，任何一段配置不当都会把总时长拉长到分钟级。

💡
这就是「下游重启时我这边报了一批错」的全部原因

很多人第一反应是注册中心有 bug，其实这是机制的必然结果：摘除必须靠观测来推断，而观测有周期。摘除延迟不可能降到零，所以工程上只有两条路——被调方通过优雅下线把「实例消失」变成一个提前通知的、有序的过程；调用方通过连接失败快速重试与熔断兜住剩余失败。把希望寄托在「把心跳调到 1 秒」上只会换来抖动误摘。

优雅下线：把摘除延迟从被动观测变成主动通知

优雅下线的核心思路是先让调用方知道我要走，再真的走。顺序错了整个机制就失效：先停服务再注销，或者直接强杀，都会让调用方在摘除窗口里继续发请求。

// 优雅下线的完整实现，顺序就是上图：注销 -> 就绪置失败 -> 等推送 -> 停新请求 -> 排空 -> 退出
func main() {
    srv := &http.Server{Addr: ":8080", Handler: router}
    go func() {
        if err := srv.ListenAndServe(); err != nil && err != http.ErrServerClosed {
            log.Fatal(err)
        }
    }()

    stop := make(chan os.Signal, 1)
    signal.Notify(stop, syscall.SIGTERM, syscall.SIGINT)
    <-stop

    // 第一步：主动注销，这一步把「被动等租约过期」变成「主动通知」，省下最长的那段延迟
    if err := registry.Deregister(instanceID); err != nil {
        log.Warn("deregister failed, will fall back to lease expiry", err)
    }
    // 第二步：就绪检查立刻失败，让 K8s 与网关同步停止派发新流量
    readiness.draining.Store(true)

    // 第三步：等待摘除信息扩散到所有调用方。这个 15 秒不是拍脑袋，
    // 它必须大于「推送延迟 + 调用方 SDK 缓存刷新周期」，否则等于没等
    time.Sleep(15 * time.Second)

    // 第四步：停止接收新请求并排空存量。Shutdown 会先关监听再等连接处理完
    ctx, cancel := context.WithTimeout(context.Background(), 30*time.Second)
    defer cancel()
    if err := srv.Shutdown(ctx); err != nil {
        log.Warn("graceful shutdown timeout, force closing", err) // 超时兜底，避免永不退出
    }

    // 第五步：先停消费再关连接池，顺序反了会出现「消息已取出但连接池已关」的丢消息
    consumer.Stop()
    db.Close()
}

# 容器环境里等待摘除的标准做法：preStop 里睡够，terminationGracePeriodSeconds 要更长
apiVersion: apps/v1
kind: Deployment
spec:
  template:
    spec:
      # 必须大于 preStop 等待 + 请求排空时间，否则 kubelet 会在排空前发 SIGKILL
      terminationGracePeriodSeconds: 60
      containers:
      - name: app
        lifecycle:
          preStop:
            exec:
              # SIGTERM 与 Endpoints 移除是并发发生的，没有这段等待就必然有请求打到正在退出的 Pod
              command: ["/bin/sh", "-c", "sleep 15"]
        readinessProbe:            # 只有就绪探针失败才会摘流量，存活探针失败是重启
          httpGet: { path: /readyz, port: 8080 }
          periodSeconds: 3         # 缩短这一段能显著降低摘除延迟
          failureThreshold: 2
          timeoutSeconds: 1        # 必须大于应用侧健康检查的内部超时
        livenessProbe:
          httpGet: { path: /livez, port: 8080 }
          periodSeconds: 10
          failureThreshold: 3      # 存活探针要比就绪探针宽松，否则抖动时会被反复重启

保护模式：宁可留着死实例，也不能把列表摘空

假设注册中心在一分钟内发现 80% 的实例都没有续约，最合理的推断是什么？不是「80% 的实例同时挂了」，而是「注册中心自己的网络出问题了」。真实世界里成百上千个实例同时失联的概率极低，而注册中心与机房之间断网的概率高得多。

如果注册中心此时照常摘除，结果是实例列表被清空，调用方拿到空列表，一个注册中心的网络问题被放大成全站不可用。这正是 Eureka 自我保护模式要解决的问题：当最近一段时间的续约成功率低于阈值时，停止摘除任何实例。这也是 AP 取向在工程上的具体落地——宁可给出包含死实例的列表，也不给出空列表。

实现保护机制触发条件生效后的行为副作用与注意点
Eureka自我保护模式最近一分钟实际续约数低于期望值的 85%，阈值可配停止摘除任何实例，界面出现红色告警横幅小集群极易误触发：实例数少时统计噪声大，测试环境经常长期停留在保护模式，死实例一直不摘
Nacos实例保护阈值，按服务粒度配置健康实例数占比低于设定阈值，例如 0.6把不健康实例也返回给调用方，避免列表被摘空默认值是 0，即不开启，需要为核心服务显式配置；开启后调用方必须能容忍不健康实例
Consul无等价机制，依赖检查失败即标记 critical—失败实例被标记，查询时默认过滤大面积检查失败时确实可能返回空列表，需要在客户端侧做「空列表保留旧值」保护
K8s Service无保护阈值—就绪的 Pod 全部失败时 EndpointSlice 为空，流量直接失败这也是为什么就绪探针绝不能检查非核心依赖，否则一次外部依赖抖动会让整个 Service 没有端点
客户端 SDK 侧空列表保护拉取或推送得到的实例列表为空保留上一次的非空列表，并打告警指标这是最后一道防线，也是最应该确认的一条：无论服务端用什么实现，客户端都不该接受空列表

元数据、就近路由与多机房

注册信息里除了地址，还应带上一组元数据标签，它们是流量治理的基础：版本号用于金丝雀、分组标签用于灰度、区域与可用区标签用于同区域优先路由。

同区域优先的收益非常具体：跨可用区调用的网络往返通常比同可用区高 0.5 到 2 毫秒，一条链路上有十几次内部调用时，累积延迟差异可达十几毫秒；更直接的是跨可用区流量在公有云上是要计费的，把内部调用限制在同可用区里，这部分账单可以显著下降。实现方式是负载均衡时先过滤出同区域实例，只有同区域没有健康实例时才回退到跨区域——回退逻辑必须有，否则同区域全挂时流量无处可去。

元数据用途标签示例消费方常见做法易错点
金丝雀与灰度version 为 v2、tag 为 canary调用方 SDK 或 sidecar 的路由规则按请求头或用户标识匹配到特定标签的实例灰度实例权重没调低，新版本一上线就承接了平均流量
同区域优先zone 为 cn-east-1a负载均衡策略优先同 zone，无健康实例时回退没有回退逻辑，单 zone 故障时请求全部失败
单元化路由unit 为 unit-01网关与内部调用同一用户的请求闭环在一个单元内跨单元调用没有兜底，数据不在本单元时直接报错
权重与容量weight 为 100负载均衡新扩容实例先给低权重预热，避免冷启动被打爆预热逻辑缺失时，JIT 未热的实例延迟高，表现为「某个实例的 P99 特别差」
下线标记enabled 为 false调用方 SDK运维手动标记实例下线，比注销更可控，可随时恢复标记后忘记恢复，扩容后某些实例长期不接流量

多机房部署要先回答一个问题：注册信息要不要跨机房同步。全同步的好处是任何机房都能发现全部实例，可以做跨机房容灾；代价是同步链路本身成为故障点，且一旦跨机房调用变成常态，延迟与流量成本都会上升。更稳的做法是每个机房一套注册中心，各自只管本机房实例，机房之间通过网关或专门的跨机房入口互通，这样机房级故障天然被隔离，代价是跨机房调用要显式声明，不能像本机房一样透明。

排障清单

现象最可能的原因怎么确认处理
不同调用方拿到的实例列表不一致注册中心节点间数据未同步完，或调用方连到了不同节点且缓存刷新时间不同直接查注册中心各节点的实例接口做对比，再看客户端的缓存刷新时间戳短暂不一致是 AP 的正常表现，持续不一致要查节点间同步链路与时钟
实例已停但流量还在打过去摘除延迟四段中的某段过长，最常见是客户端缓存周期太长或推送链路已断看客户端与注册中心之间是否有活跃长连接；对比注册中心里的状态与客户端内存中的列表修复推送连接，缩短兜底拉取周期，补上优雅下线
新扩容的实例没有流量注册失败、注册了不可达地址、被手动标记下线、或权重为 0查注册中心里是否有这个实例及其元数据；从调用方所在机器直连该实例的健康接口修正注册地址来源，清理残留的下线标记与权重
某个实例流量明显高于其他实例负载均衡策略是长连接加轮询时的分配不均，或其他实例被判不健康，或权重配置不同看各实例的连接数与权重；确认健康实例数是否与预期一致调整为最少连接策略，或对长连接做定期再均衡
实例反复上下线抖动心跳间隔过短加网络抖动，或健康接口检查了不稳定的外部依赖查注册中心的状态变更记录频率，查健康接口的耗时分布放宽心跳与失败阈值，把非核心依赖从健康接口里移除
注册中心界面显示实例健康，但调用一直失败TCP 探测的盲区：端口在听但服务不可用；或注册的地址在调用方网络里不可达从调用方机器上直接请求该地址的业务接口把检查换成业务健康接口，修正注册地址
实例列表突然变成空注册中心大面积检查失败且没有保护阈值，或客户端接受了空列表看注册中心的健康实例占比指标与保护模式状态配置保护阈值，客户端加空列表保留旧值的保护
# 一、注册中心视角：这个服务现在有哪些实例，各自什么状态
curl -sS "http://nacos.internal:8848/nacos/v1/ns/instance/list?serviceName=order-service&namespaceId=env-prod" | python3 -m json.tool
# 判读要点：healthy 为 false 说明心跳已断但还在保护窗口内；
# ip 字段若是 172.17 开头的 Docker 内网地址，说明注册了不可达地址；
# weight 为 0 的实例不会收到流量，常见于手动操作后忘记恢复

# 二、逐节点对比，确认是不是集群内数据不一致
for h in 10.0.1.11 10.0.1.12 10.0.1.13; do
  echo -n "$h: "
  curl -sS "http://$h:8848/nacos/v1/ns/instance/list?serviceName=order-service" | grep -o '"ip"' | wc -l
done

# 三、K8s 场景：Service 背后到底有没有端点，这一步能立刻区分「没注册」与「路由错」
kubectl get endpointslice -l kubernetes.io/service-name=order-service -o wide
kubectl get pod -l app=order-service -o custom-columns='NAME:.metadata.name,READY:.status.containerStatuses[*].ready,IP:.status.podIP'
# READY 为 false 的 Pod 不在端点里；端点为空而 Pod 都在 Running，几乎一定是就绪探针在失败

# 四、客户端视角：推送连接是否还活着（最常见的静默故障）
ss -tanp | grep -E ':8848|:9848' | awk '{print $1, $5}' | sort | uniq -c
# 没有 ESTABLISHED 说明已退化为纯拉取，摘除延迟会比预期长一个拉取周期

# 五、从调用方所在机器验证目标地址真的可达，排除注册地址不可达
curl -sS -m 2 -o /dev/null -w 'code=%{http_code} connect=%{time_connect}s total=%{time_total}s\n' http://10.0.2.31:8080/readyz

反模式

反模式为什么有人这么做后果正确做法
用 CP 型注册中心做服务发现觉得实例列表必须强一致网络分区时整个集群既不能注册也不能发现，小故障被放大成全站故障选 AP 型，或在 CP 组件上叠加客户端缓存与空列表保护
不做优雅下线，直接强杀进程发布脚本图省事每次发布都必然产生一批连接被拒的失败请求注销、等待推送、排空、退出，容器里用 preStop 等待
客户端缓存周期过长为了降低注册中心压力摘除延迟被拉长到分钟级，下游发布期间错误量成倍增加启用推送，兜底拉取周期控制在 10 到 30 秒
健康检查只用 TCP 探测默认配置就是这个，改起来麻烦线程池打满、下游全挂、返回全部 500 时实例仍被判健康用业务健康接口，只检查强依赖并缓存结果
注册的是容器内网 IP应用自注册时取了容器网卡地址注册中心里一切正常，调用方却连不上，排查方向容易被带偏显式指定对外可达地址与端口，或改用平台自动注册
把注册中心当配置中心用元数据字段很方便，顺手就塞了实例元数据膨胀到几十 KB，每次心跳与推送都放大流量，注册中心内存吃紧元数据只放路由所需的少量标签，配置放配置中心
就绪探针检查所有下游依赖觉得依赖不可用就不该接流量一个非核心依赖抖动导致全部实例同时不就绪，端点被摘空，全站不可用只检查强依赖，非核心依赖走降级而不是摘流量
❌
最容易踩的坑
  • K8s 里只写了 SIGTERM 处理却没有 preStop 等待，Endpoints 移除与 SIGTERM 是并发的，仍然会有请求打到正在退出的 Pod。
  • terminationGracePeriodSeconds 小于 preStop 等待加排空时间，kubelet 在排空完成前就发 SIGKILL，优雅下线白做。
  • 把心跳间隔调到 1 秒想缩短摘除延迟，结果网络轻微抖动就误摘实例，出现上下线抖动。
  • Eureka 在实例数很少的测试环境长期停留在自我保护模式，死实例一直不被摘除，误以为注册中心坏了。
  • Nacos 的实例保护阈值默认为 0 即不开启，核心服务没有显式配置，大面积检查失败时列表被摘空。
  • 客户端 SDK 接受了空实例列表并覆盖了内存缓存，注册中心一次异常导致调用方彻底无地址可用。
  • 健康接口里串行调用了五个下游，接口本身耗时 3 秒，超过探测方超时，被判不健康。
  • 用 kill -9 直接杀实例来做「故障演练」，然后得出「注册中心摘除太慢」的错误结论，忽略了租约机制本就如此。
  • 同区域优先路由没有写回退分支，单可用区故障时同区域无健康实例，请求直接全失败。
  • 新扩容实例不做权重预热，冷启动阶段就承接平均流量，表现为该实例 P99 异常高。
  • 多网卡机器上自注册选错网卡，注册了一个只有内部管理网可达的地址。
  • 调用方只重试超时不重试连接被拒，摘除窗口内的连接拒绝错误全部透传给了用户。
