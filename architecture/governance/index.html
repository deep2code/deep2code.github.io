服务治理的三块基础设施：注册发现、配置、网关

🏷️ 配置中心

本篇是专题主干，只讲三者的共性、边界与可用性设计，具体机制分别在三篇子文里展开：服务端存储模型与推送实现见 配置中心的服务端机制与选型，注册发现的健康检查与摘除延迟见 服务注册发现的机制与故障模式，网关的数据面实现与部署形态见 网关的数据面实现与部署形态。应用侧怎么用配置（配置四分类、能否热更新的判断、两阶段变更）见 微服务配置中心的应用侧实践，网关该放什么不该放什么见 API 网关的责任边界，Nginx 的请求处理阶段与限流形态见 Nginx 深入。

三块基础设施其实是同一种架构

很多人把注册中心、配置中心、网关当成三门独立技术来学，结果是每换一个组件就要重新踩一遍坑。它们的内部结构其实完全同构：一个保存权威数据的控制面，一个在请求路径上真正干活的数据面，中间是一条把变更同步过去的传播链路。注册中心的权威数据是实例列表，配置中心的是配置版本，网关的是路由与插件规则，仅此而已。

缺了哪一块会发生什么

三块基础设施不是「架构好看」才加的，每一块都对应一个没有它就绕不过去的具体痛点。下表是常见的真实绕法，以及绕法后来一定会付出的代价。

缺失项直接后果团队实际会怎么绕绕法的代价
没有注册发现调用方不知道被调方的实例地址把 IP 写死在配置里，或挂一个内网 LB，或用 DNS 轮询扩缩容要改配置重发布；DNS 有缓存 TTL，摘除比注册中心还慢；LB 多一跳且看不到实例级指标
没有配置中心调一个超时时间、开一个开关都要走发布流程参数写进配置文件随镜像一起发布止损时间被发布耗时绑定，一次回滚从半分钟变成十几分钟；参数散落在各服务仓库里无人能全局审计
没有网关认证、限流、审计每个服务自己实现一遍抽一个公共 SDK，或者让前端直连各服务SDK 升级要所有服务配合发布，多语言要写多套；没有统一入口就没有统一的流量画像和一键封禁能力
三块都有但各自为政网关不知道实例列表，配置不影响路由网关里再维护一份静态 upstream实例变更后网关继续打到死实例，出现「业务内部调用正常，从外部进来就 502」的诡异现象

核心要求：基础设施挂了，业务也要能继续跑

这三个组件有一个共同的危险属性：全站都依赖它们。一个业务服务挂了影响一个功能，注册中心挂了可能影响所有调用。既然无法把它们做成永不故障，唯一正确的设计方向就是让业务对它们保持弱依赖。落地下来只有三条，但很少有团队三条都做到。

✅
弱依赖的三条硬要求

第一，本地缓存加启动兜底：拿到的数据必须落盘，进程冷启动时若控制面不可达就读快照，绝不因为拉不到数据而退出。第二，控制面故障时数据面继续用最后有效值，不要把「拉取失败」误当成「数据被删除」，这是清空实例列表引发全站雪崩的典型成因。第三，绝不在请求路径上同步调用控制面，所有远程交互都放在后台线程。

细节见站内熔断与重试篇

注意后半段：弱依赖不是没有代价，代价是故障期间数据面会持有脏数据。所以「本地缓存兜底」和「客户端侧的失败摘除、重试、熔断」是一套组合拳，只做前者会把问题从「全站不可发现」换成「持续打到死实例」。重试策略与熔断阈值见 熔断与重试。

// 三块基础设施的客户端都该长这样：内存副本 + 快照兜底 + 后台刷新
type Cache struct {
    mu       sync.RWMutex
    data     map[string][]string // 服务名 -> 实例地址列表；配置中心换成 map[string]string 同理
    snapPath string              // 快照目录，例如 /data/registry/snapshot
}

// Bootstrap 决定了控制面挂掉时能否冷启动，是最容易被写错的地方
func (c *Cache) Bootstrap(ctx context.Context) error {
    ctx, cancel := context.WithTimeout(ctx, 3*time.Second) // 启动阶段也要有超时，别无限等
    defer cancel()
    if err := c.pullRemote(ctx); err == nil {
        return c.writeSnapshot() // 拉成功就刷新快照，供下一次冷启动使用
    }
    // 关键：控制面不可用时不 panic、不阻塞启动，降级读快照
    log.Warn("control plane unreachable on boot, fallback to local snapshot")
    return c.loadSnapshot() // 快照也没有才返回错误，由上层决定是否强依赖
}

// 请求路径上的读取：只读内存，不发网络请求，不加写锁
func (c *Cache) Pick(service string) (string, bool) {
    c.mu.RLock()
    defer c.mu.RUnlock()
    list := c.data[service]
    if len(list) == 0 {
        return "", false // 交给上层熔断或默认值，绝不在这里临时去查控制面
    }
    return list[rand.Intn(len(list))], true
}

// 后台刷新：推送负责低延迟，定时全量拉取兜底漏推送
func (c *Cache) Run(ctx context.Context) {
    go c.watchPush(ctx) // 长轮询或 gRPC 双向流，断线指数退避重连
    t := time.NewTicker(30 * time.Second)
    defer t.Stop()
    for {
        select {
        case <-ctx.Done():
            return
        case <-t.C:
            if err := c.pullRemote(ctx); err != nil {
                metrics.RefreshFail.Inc() // 必须有指标：静默失败是这类 SDK 最常见的故障
                continue                  // 失败保留旧值，绝不清空
            }
            _ = c.writeSnapshot()
        }
    }
}

推送还是拉取：延迟与连接数的直接交换

变更怎么从控制面到数据面，只有三种实现，选择本质上是拿服务端资源换变更延迟。结论是生产环境应该同时用推送和定时拉取，前者拿延迟，后者防止推送链路静默失败——只靠推送的系统几乎无法发现漏推，往往要等到排障时才发现某几个实例的配置停留在一周前。

机制变更可见延迟服务端连接数服务端资源特征典型实现什么情况下会失效
定时全量拉取等于轮询周期，通常 30 秒到 5 分钟0 条常驻连接无状态，QPS 等于实例数除以周期，易水平扩容Spring Cloud Config、K8s ConfigMap 卷同步实例数上万且周期短时，服务端 QPS 与出流量成为瓶颈
HTTP 长轮询约 1 秒以内每客户端 1 条挂起连接连接数等于实例数，需要异步 Servlet 或事件驱动才撑得住Nacos 1.x 配置监听，挂起 29.5 秒；Apollo客户端激增时文件句柄与内存耗尽；中间的 LB 或代理空闲超时更短，连接被提前掐断
gRPC 双向流百毫秒级每客户端 1 条长连接，多路复用连接复用后内存优于长轮询，但要处理 keepalive 与半开连接Nacos 2.x、Apollo 新版、Envoy xDSNAT 或防火墙静默丢弃空闲连接，未配 keepalive 时表现为「连接看着是通的但推送不再到达」

一致性取舍：服务发现应该选 AP

这是三块基础设施里最容易选错的一处。很多人凭直觉觉得「注册信息当然要强一致，不然读到过期的实例怎么办」，于是选了 ZooKeeper 或强一致读的 etcd 来做注册中心。这个直觉是错的。

❌
一个真实故障形态：CP 注册中心把小故障放大成全站故障

三节点 ZooKeeper 跨两个机房部署，A 机房 2 台、B 机房 1 台。某次 A 机房内部交换机抖动，两个节点之间通信异常，集群失去多数派。此时 ZooKeeper 拒绝写入，会话超时后临时节点被判失效，客户端读也无法保证。结果是：所有服务的实例都无法注册，所有调用方无法解析地址，正在扩容的实例进不来，已有实例的会话陆续过期。真正故障的只是一个交换机，但全站服务调用同时中断。若选 AP 型，后果仅仅是这段时间的注册变更暂不可见。

判断标准很简单：服务发现的数据本身就是「可能过期」的——即使注册中心告诉你某个实例是健康的，它也可能在你发请求的那一微秒宕机，所以调用方必须有重试与熔断。既然过期数据的处理链路本来就存在，为一致性牺牲可用性就是纯亏。配置中心不一样：它写入极少、要求准确、还需要审计和版本，用强一致存储是合适的。CAP 与 PACELC 的完整推演见 CAP 定理。

维度AP 型：Eureka、Nacos 临时实例CP 型：ZooKeeper、etcd 线性读、Consul 默认
节点故障或网络分区时继续提供读写，各节点数据可能短暂不一致失去多数派即拒绝写入，强一致读也不可用
最坏结果读到已下线实例，调用失败一次后被熔断摘除整个集群无法注册与发现，故障范围被放大
写入吞吐高，无需多数派确认受日志复制与 fsync 限制，注册风暴时容易被打满
适合承载心跳型的实例列表：高频、可过期配置、选主、分布式锁、元数据：低频、要准
结论服务发现的默认选择配置与协调场景的默认选择，不要拿来做注册中心

注册与配置要不要合到一个组件

Nacos、Consul、etcd 都能同时承担注册和配置，所以这是个真实的选择题。合一的收益是少运维一套组件，代价是共享了故障域和容量：一次配置发布把服务端打满，注册链路一起受影响；一次为配置做的版本升级，风险范围覆盖了服务发现。

方案运维成本故障域权限与审批一致性适配适合谁
合一，Nacos 同时做两件事最低，一套部署一套监控共享，注册风暴与配置操作互相影响需确认能按命名空间分别授权，否则改配置的人也能改注册数据临时实例用 Distro 协议偏 AP，持久数据用 Raft，算是分别适配服务数几十到几百、运维人力有限的团队
合一，etcd 同时做两件事低，但要自己包一层发现语义共享，且 etcd 是 CP，注册风暴会撞上写入吞吐上限依赖 RBAC 前缀授权，粒度够用不理想：用 CP 存储承载高频心跳，容量和可用性都吃亏已深度使用 K8s 生态、注册量不大的场景
分开，Nacos 做注册加 Apollo 做配置高，两套部署、两套告警、两套升级隔离，一边挂了另一边正常配置侧可以有独立的审批流与操作审计各取所长：注册走 AP，配置走强一致加关系库对配置审计与灰度要求高、有平台团队的组织
不引入独立注册中心，用 K8s Service 与 Endpoints最低，平台自带与集群控制面共享走 K8s RBACEndpoints 由控制器维护，语义足够全量容器化、不需要跨集群发现的团队

除了技术维度，选型里有一半是组织因素，而且往往更决定成败：技术栈语言分布，只有 Java 时 Nacos 或 Apollo 的 SDK 体验最好，多语言时更应该把发现下沉到 sidecar 或直接用 K8s 原生机制；谁负责值班，没有专职平台团队就不要选需要维护 MySQL 加多个独立进程的方案；是否已有存量，半个集群在用 Eureka 时，比起一次性替换，更稳的是新服务接新注册中心加双注册过渡。

反模式：这三块最常被做错的地方

反模式为什么有人这么做后果正确做法
把控制面放进请求关键路径实现最省事，每次用到时查一下最新的控制面 QPS 变成业务 QPS 的倍数，控制面一抖动全站超时请求路径只读内存副本，远程交互放后台线程
拉取失败就清空本地数据把「没返回数据」当成「数据已删除」控制面重启时全站实例列表被清空，比控制面宕机本身严重得多只接受完整且校验通过的全量结果才整体替换，失败保留旧值
启动时拉不到数据就退出进程觉得配置不完整不该启动控制面故障期间任何一次重启或扩容都拉不起来，故障无法自愈降级读本地快照启动，同时打告警指标
三套基础设施各用一套技术栈与运维方式各阶段由不同团队引入三套监控、三套告警、三种排障姿势，值班同学记不住统一指标命名与告警口径，至少统一变更审批入口
基础设施自己不做监控觉得「它是用来监控别人的」推送延迟、连接数、拉取失败率无人可见，故障靠业务报障发现对控制面自身埋点：推送耗时、活跃连接数、客户端失败率、配置版本分布
三块之间互相强依赖网关从配置中心取路由，配置中心又从注册中心找地址形成环状依赖，冷启动时互相等待，一个挂全挂控制面之间的依赖必须可降级，冷启动路径上用静态配置打破环
❌
最容易踩的坑
  • 用 ZooKeeper 做注册中心且跨机房三节点部署，一次网络抖动失去多数派后全站无法发现服务。
  • 配置 SDK 不落本地快照，配置中心宕机期间任何业务实例重启都起不来，故障从「不能改配置」升级为「不能重启」。
  • 把控制面地址写成单个域名且没有多地址容错，DNS 故障时三块基础设施同时失联。
  • SDK 的刷新失败既没有指标也没有日志，推送链路静默中断几天后才在排障中发现配置是旧的。
  • 业务代码在每次请求里调用 SDK 的同步刷新接口，压测时 QPS 上不去，瓶颈其实在注册中心。
  • 网关维护一份静态 upstream 而不接注册中心，实例缩容后外部请求 502，内部调用却正常，排查方向被带偏。
  • 基础设施与业务混部在同一批节点，业务把节点 CPU 打满后基础设施跟着失联，故障相互放大。
  • 基础设施的告警发到与业务同一个通道，故障时几千条业务告警把控制面的根因告警刷没了。
  • 做了本地缓存兜底但没做失败摘除和熔断，控制面故障期间持续把流量打到已死实例上。
  • 认为「合一能少一个组件」就把所有元数据都塞进注册中心，单实例元数据膨胀到几十 KB，推送流量放大几十倍。
  • 控制面没有容量保护，一次全站滚动重启时所有实例同时拉全量，把控制面打挂形成雪崩。
  • 基础设施升级不灰度，一次性替换全部节点，客户端兼容性问题在生产才暴露且无法回退。
