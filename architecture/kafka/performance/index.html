Kafka 性能调优与压测：基线、瓶颈定位与 MQ 性能对照

🏷️ Kafka 性能优化

零拷贝在什么条件下会失效、分段日志与稀疏索引怎么支撑顺序写，这些原理详见站内 Kafka 深度原理一篇。这篇只讲操作层面：怎么测出基线、怎么定位瓶颈在哪一侧、每个旋钮往哪个方向拧、以及「Kafka 更快」这个结论的边界在哪里。

没有基线的调参就是猜

调优最常见的失败模式是：一次改五个参数，跑十几秒压测，看到数字变好就发布上线，三天后出问题完全不知道回滚哪一项。正确流程是先固定变量测出一组基线数字，然后一次只动一个参数、重跑同样的压测、只比较与基线的差值。

# ---------- 生产端基线：固定速率，测延迟分布 ----------
kafka-producer-perf-test.sh \
  --topic perf-test --num-records 5000000 --record-size 1024 \
  --throughput 100000 \
  --producer-props bootstrap.servers=kafka-1:9092,kafka-2:9092 \
                   acks=all linger.ms=10 batch.size=65536 compression.type=zstd \
  --print-metrics

# 典型输出，最后一行是汇总：
# 5000000 records sent, 98765.4 records/sec (96.45 MB/sec), 12.31 ms avg latency,
#   412.00 ms max latency, 8 ms 50th, 27 ms 95th, 58 ms 99th, 183 ms 99.9th.

# ---------- 饱和吞吐：throughput 设 -1 打满，只看吞吐不看延迟 ----------
kafka-producer-perf-test.sh --topic perf-test --num-records 5000000 \
  --record-size 1024 --throughput -1 \
  --producer-props bootstrap.servers=kafka-1:9092 acks=1 linger.ms=50 batch.size=131072

# ---------- 消费端基线 ----------
kafka-consumer-perf-test.sh --bootstrap-server kafka-1:9092 \
  --topic perf-test --messages 5000000 --threads 1 \
  --consumer-props fetch.min.bytes=65536 max.partition.fetch.bytes=2097152

# 输出为 CSV 表头加一行数据：
# start.time, end.time, data.consumed.in.MB, MB.sec, data.consumed.in.nMsg,
#   nMsg.sec, rebalance.time.ms, fetch.time.ms, fetch.MB.sec, fetch.nMsg.sec
输出字段含义怎么判读
records/sec条数吞吐与业务峰值 QPS 对比。条数吞吐低而 MB/sec 高，说明消息体偏大，瓶颈在带宽而不在请求数
MB/sec字节吞吐直接和网卡带宽对比。千兆网卡理论上限约 125MB/s，压到 100MB/s 以上就别再调客户端参数了，先换万兆
avg latency从 send 进缓冲到收到确认的平均耗时它包含 linger.ms 的等待，所以调大 linger 后它上升是正常现象，不代表变慢
max latency最大单次耗时参考价值低，一次 GC 或 leader 切换就能把它拉到几秒
99th 与 99.9th尾部延迟真正要盯的指标。平均值低而 p99 高一个数量级，几乎都是 Broker 侧 GC 停顿或磁盘抖动，调客户端参数没用
rebalance.time.ms消费端建组耗时超过几秒说明分区多或 session.timeout.ms 偏大，会显著拖慢发布期间的恢复速度
fetch.MB.sec剔除建组时间后的纯拉取速率它和 MB.sec 差距大，说明时间主要花在建组上，不是拉取慢

五个旋钮：吞吐与延迟是一对矛盾

旋钮调大的方向对吞吐对单条延迟副作用
linger.ms0 调到 5 至 20显著提升，攒批变大、请求数下降、压缩率上升最多增加所设的毫秒数崩溃时缓冲区丢失窗口变大
batch.size16KB 调到 64 至 128KB提升，但 linger.ms 为 0 时几乎无效基本不变单请求变大，p99 抖动加剧；buffer.memory 更易被少数分区吃满
fetch.min.bytes1 调到 64KB 至 1MB消费侧提升，Broker 请求数下降明显最多增加 fetch.max.wait.ms低流量 Topic 上只增延迟不增吞吐
acks从 all 降到 1提升，尤其跨机房部署时降低用可靠性换性能，leader 换届即丢消息，绝大多数业务不该动这一项
压缩none 改为 lz4 或 zstd网络与磁盘吞吐显著提升增加压缩与解压耗时，通常在毫秒级以内Producer 与 Consumer 的 CPU 上升；Broker 端算法设错会解压重压并让零拷贝失效
✅
只改一项的话，改 linger.ms

默认 0 意味着几乎不攒批，一条消息一个请求，网络往返数被放大到极致，压缩也压不出效果。调到 10 毫秒通常能让吞吐翻几倍，代价是每条消息最多多等 10 毫秒。这是整个 Kafka 调优里投入产出比最高的一个改动，而且风险极低。

指标健康区间异常含义对应动作
UnderReplicatedPartitions稳定为 0非零说明有副本跟不上，此时 acks=all 的写入会变慢甚至被拒先排查是网络还是磁盘；持续非零则调大 num.replica.fetchers 到 2 至 4，并检查副本分布是否不均
RequestHandlerAvgIdlePercent大于 0.3低于 0.3 说明 IO 处理线程快饱和了，请求开始排队调大 num.io.threads，起步值可取 CPU 核数的一倍到两倍；同时确认不是磁盘慢导致线程被拖住
NetworkProcessorAvgIdlePercent大于 0.3低于 0.3 说明 socket 读写线程不够，常见于连接数很多或开了 SSL调大 num.network.threads；SSL 场景下它的开销远高于明文，要额外留余量
LogFlushRateAndTimeMsp99 在个位数毫秒耗时飙升说明磁盘顶不住，或有人调了刷盘间隔换 SSD、把数据目录分散到多块盘、检查是否误配了 log.flush.interval.messages
RequestQueueSize接近 0持续堆积说明 IO 线程处理不过来，会反压到网络层并拉高 p99与 RequestHandlerAvgIdlePercent 一起看，先扩 IO 线程再考虑扩机器
Full GC 次数长时间为 0出现 Full GC 时 Broker 会短暂失联，可能触发 ISR 收缩和 leader 切换堆控制在 6 到 8GB，把剩余物理内存全部留给 page cache，用 G1 并设合理的停顿目标
TotalTimeMs 各阶段分解以本地处理为主如果时间集中在 remote 阶段，说明在等副本确认，不是 Broker 慢去看复制链路而不是加线程。这个分解能避免大量误判

压缩算法选型与 Broker 端的致命默认值

算法压缩率压缩速度CPU 开销适用场景
gzip最高最慢很高，可能比不压缩高出数倍只有带宽极贵、CPU 极富余的跨地域传输才考虑
snappy中快低老集群的常见选择，均衡但已被 lz4 与 zstd 覆盖
lz4中最快最低对 CPU 敏感、消息体小、追求最低延迟的场景
zstd高，接近 gzip快中等，可通过压缩级别调节现在的首选。压缩率接近 gzip 而速度接近 lz4，JSON 这类文本型消息收益最大
none无无无消息本身已是压缩过的二进制，例如图片、已压缩的 Protobuf 负载
❌
Broker 的 compression.type 必须保持 producer

这个参数默认值是 producer，意思是原样保存 Producer 送来的压缩格式。一旦你在 Broker 上指定了具体算法而它与 Producer 不同，Broker 就要把每一个批次解压再重新压缩，后果有两个：CPU 消耗成倍上升；消费时无法再用 sendfile 直接把 page cache 里的数据送到网卡，零拷贝失效。同样的机制也解释了为什么老版本客户端接入会让集群 CPU 莫名升高——消息格式向下转换同样会让零拷贝失效。

page cache、冷读与分区数

sequenceDiagram participant C1 as 实时消费者 participant C2 as 追历史的消费者 participant B as Broker 进程 participant PC as 操作系统 page cache participant D as 磁盘 C1->>B: Fetch 请求 位点接近 LEO B->>PC: 定位活跃段 数据刚写入仍在缓存 PC-->>B: 命中 B-->>C1: sendfile 直接从缓存送到网卡 零拷贝 C2->>B: Fetch 请求 位点落后数小时 B->>PC: 查找历史段 PC-->>B: 未命中 B->>D: 触发磁盘读 并把数据填入 page cache D-->>PC: 加载历史数据 挤出热数据 PC-->>B: 返回 B-->>C2: 返回数据 Note over C1,D: 冷读不仅慢 还会把活跃段从缓存里挤出去
导致实时消费者也开始读磁盘 整个 Broker 被拖慢
要点结论为什么
JVM 堆大小6 到 8GB，不要更大Kafka 几乎不在堆里缓存消息，全靠 page cache。堆开大只会拉长 GC 停顿，还抢走本该属于缓存的内存
剩余物理内存全部留给 page cache，越多越好热数据能不能全落在缓存里，直接决定读路径是走内存还是走磁盘
冷读隔离历史数据回溯任务要限速，或安排在业务低峰一个追几小时前数据的消费者足以把整个 Broker 的缓存命中率打穿
log.segment.bytes默认 1GB，一般不动调太小会让段文件数量和文件句柄暴涨，索引与清理开销上升；调太大则清理粒度变粗，磁盘回收不及时
retention 设置按业务最坏恢复时间设，不要盲目留 7 天以上保留期越长，冷数据越多，一次误操作的全量重放代价也越大
分区数按目标吞吐估算后留一到两倍余量，单 Broker 尽量不超过两千分区多则同时被追加写的文件多，顺序写在磁盘层面退化成随机写，机械盘上退化尤其剧烈；还会推高句柄数与 Rebalance 耗时
多数据目录log.dirs 配多块独立物理盘而不是一个 RAID 卷Kafka 自己会把分区分散到不同目录，等效获得并行 IO，且单盘故障只影响部分分区

Consumer 侧调优：大多数时候瓶颈不在 Kafka

症状先看什么真实原因正确动作
Lag 持续上涨，消费进程 CPU 很低下游接口或数据库的 p99下游 IO 是瓶颈，消费端只是在等改批量写入、异步化、加下游容量。加 Consumer 实例完全无效，只会把下游压得更慢
加了实例但新实例不消费分区数与实例数并发度上限等于分区数，多出来的实例空转先扩分区再扩实例；扩分区会改变 key 的哈希分布，有顺序要求的要评估影响
频繁 Rebalance 且伴随重复消费单条处理耗时乘以 max.poll.records超过 max.poll.interval.ms 被踢出组降 max.poll.records 或把处理改成批量；不要靠调大 session.timeout.ms，那个参数管的不是这件事
吞吐低但延迟也低，网络请求数很高fetch.min.bytes 与 max.partition.fetch.bytes每次拉得太少，请求数被放大调大这两项，让单次拉取带回更多数据
Lag 只集中在少数分区各分区 Lag 分布key 分布倾斜造成热点分区换分区键或加盐；单纯扩分区不解决倾斜
消费很快但内存吃紧max.partition.fetch.bytes 乘以分区数单次拉取的总量等于它乘以被分配的分区数，分区多时内存占用可观按被分配分区数反算总量，必要时降低单分区上限

⚠️
「Kafka 最快」只在批量吞吐场景成立

Kafka 的高吞吐来自攒批、顺序写和零拷贝，这三项都需要一定的流量密度才能发挥。单条消息、低 QPS、要求亚毫秒响应的场景下，攒批反而成了纯粹的延迟来源，此时 RabbitMQ 的逐条投递模型更快也更稳。选型时先问清楚场景是「管道」还是「任务分发」：前者选 Kafka，后者 RabbitMQ 往往是更省心的答案。拿一个量级完全不同的压测结果去证明某个 MQ「更快」，基本没有参考价值。

❌
最容易踩的坑
  • 用全速模式去测延迟：把 throughput 设为 -1 时客户端一定被打到饱和，测出来的延迟只反映排队，没有任何参考价值。
  • 压测只跑十几秒：page cache 还没进稳态，数据全在缓存里，得到的是一个永远达不到的乐观值。
  • 一次改五个参数：结果好坏都不知道是哪一项带来的，出问题时无法回滚。
  • 没先确认网络带宽：MB/sec 已经贴着千兆网卡的上限了，还在反复调 batch.size。
  • 在 Broker 上写死 compression.type：触发解压重压，CPU 成倍上升并让零拷贝失效。
  • 把 JVM 堆调到 32GB：Kafka 靠 page cache 而不是堆，堆越大 GC 停顿越长，还抢走了缓存内存，p99 直接恶化。
  • 靠 log.flush.interval.messages 提高可靠性：吞吐掉一个数量级，而持久性该靠副本数和机架分散来保证。
  • 无限加分区：分区多到同时有大量段文件被追加写，顺序写退化成随机写，吞吐反而下降，Rebalance 也变慢。
  • Lag 涨了就加 Consumer 实例：实例数超过分区数后纯属空转，真瓶颈在下游 IO 时加实例只会让下游更慢。
  • 用调大 session.timeout.ms 来解决处理慢：管处理耗时的是 max.poll.interval.ms，改错参数等于没改。
  • 忽略 max.partition.fetch.bytes 乘以分区数的内存开销：被分配几十个分区时消费端内存占用会成倍放大，容易 OOM。
  • 调优时顺手把 acks 降到 1：拿可靠性换来的性能提升，在第一次 leader 切换时就要还回去。
