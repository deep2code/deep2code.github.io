Kafka 深度原理：存储、副本、Rebalance 与投递语义

🏷️ Kafka

「Kafka 快是因为顺序写磁盘」只是四个原因之一，而且解释不了它更重要的部分：怎么在异步复制的前提下做到不丢消息。这篇按「存储引擎 → 写入与副本 → 生产端语义 → 消费组与 Rebalance → offset 与投递语义 → 积压诊断」的链路拆开，每节都给出真实参数名和排查命令。

核心原理一：存储引擎——分段日志与稀疏索引

一个 Partition 在磁盘上就是一个目录，里面是一组分段（Segment）文件。文件名是该段第一条消息的 offset，天然有序：

$ ls -l /kafka-logs/order-events-0/
00000000000000000000.log        # 消息本体，只追加
00000000000000000000.index      # offset → 物理位置，稀疏
00000000000000000000.timeindex  # 时间戳 → offset，稀疏
00000000000000368769.log        # 下一段，名字是起始 offset
00000000000000368769.index
00000000000000368769.timeindex
leader-epoch-checkpoint         # 记录 Leader 任期，用于截断对齐

索引是稀疏的：默认每写入 4KB 数据（log.index.interval.bytes）才记一条索引项。这是空间与时间的折中——索引文件小到可以整个 mmap 进内存，代价是最后一小段需要顺序扫描。而顺序扫描恰好是磁盘和 Page Cache 最擅长的事。

性能手段 机制 量级 什么情况下失效
顺序追加写 只在段末尾 append，从不原地修改 机械盘顺序写可达随机写的百倍量级 分区数过多时，多个分区并发写会把顺序写退化成随机写
Page Cache 写只写内核页缓存，由 OS 决定刷盘；读也优先命中缓存 热数据读写接近内存速度 消费者读取很老的数据（冷读），会击穿缓存打到磁盘
零拷贝 sendfile 数据从 Page Cache 直接进网卡，不经过用户态 省掉 2 次拷贝和 2 次上下文切换 开启 TLS 加密时失效（必须在用户态加密）；broker 需要转换消息格式或压缩格式时也失效
批量 + 压缩 Producer 攒批压缩，Broker 原样存储，Consumer 取回解压 网络和磁盘用量降到几分之一 Broker 的 compression.type 与 Producer 不一致时会解压重压，CPU 飙升且零拷贝失效
分区并行 Topic 拆多个 Partition，分散到不同 broker 线性扩展写入和消费能力 分区数超过消费者数时无法进一步并行；单 key 的顺序要求会限制分区利用率
💡
Kafka 的 JVM 堆不需要调大

Kafka 把缓存完全交给操作系统 Page Cache，自己几乎不在堆里缓存消息。所以 broker 的 heap 给 6GB 左右就够，剩下的物理内存全部留给 Page Cache。给 broker 配 64GB 堆是典型的反向优化：堆越大 GC 停顿越长，而可用于缓存的内存反而变少。

同理，vm.swappiness 建议设 1 而不是 0——完全禁止 swap 会让内存紧张时直接触发 OOM Killer，留一点余量更稳。

核心原理二：ISR、HW/LEO 与「真正不丢」的参数组合

acks=all 不等于不丢数据。要理解为什么，得先分清两个水位：

概念 含义 为什么重要
LEO（Log End Offset） 该副本已写入的下一个 offset 衡量单个副本的进度
HW（High Watermark） ISR 中所有副本 LEO 的最小值 HW 之前的消息才算「已提交」，才对消费者可见
ISR 与 Leader 保持同步的副本集合（含 Leader） 决定 HW 推进速度，也决定 acks=all 等多少个副本
OSR 落后超过 replica.lag.time.max.ms（默认 30s）被移出的副本 不参与 HW 计算，也不能被选为 Leader（除非开 unclean）
LSO（Last Stable Offset） 事务场景下，最早一个未完成事务的起始 offset read_committed 的消费者只能读到 LSO
❌
acks=all 单独用是假的安全感

acks=all 的语义是「ISR 中当前所有副本都写入才返回」。如果 3 个副本里有 2 个因为网络或 GC 落后被移出 ISR，ISR 就只剩 Leader 自己——此时 acks=all 退化成了 acks=1。Leader 一挂，这批消息全丢，而 Producer 收到的是成功响应。

# Broker / Topic 端：ISR 少于 2 个就拒绝写入，宁可不可用也不丢
min.insync.replicas=2
default.replication.factor=3
# 禁止落后副本当选 Leader（默认已是 false，务必别改）
unclean.leader.election.enable=false

# Producer 端：三者必须同时配齐
acks=all
enable.idempotence=true
delivery.timeout.ms=120000

这套组合的含义是：3 副本、至少 2 个同步、不允许脏选举。能容忍 1 台 broker 故障且不丢数据；2 台同时故障时主动拒写而不是悄悄丢数据。

acks=1 Leader 切换时丢 重试时会 高 可重放的数据管道
acks=all + min.insync.replicas=1 ISR 收缩后仍会丢 重试时会 中 ❌ 最危险的组合：给了安全的错觉

核心原理三：幂等、事务与顺序的相互制约

幂等 Producer 的实现只有两个字段：PID（Producer ID）+ 分区级递增序号。Broker 为每个「PID + 分区」维护最近 5 个 batch 的序号，重复序号直接丢弃，序号跳跃则报错。

sequenceDiagram autonumber participant P as Producer participant B as Broker（分区 Leader） P->>B: InitProducerId B-->>P: 分配 PID = 1001 P->>B: batch seq=0，acks=all B-->>P: ack P->>B: batch seq=1 Note over P,B: 网络超时，ack 丢失
但 Broker 其实已经写入 P->>B: 重试 batch seq=1 B->>B: 发现 seq=1 已存在 → 丢弃，不重复写 B-->>P: ack（幂等生效） P->>B: batch seq=2 B-->>P: ack Note over B: 若收到 seq=4 而期望 seq=2
报 OutOfOrderSequenceException
说明中间有 batch 彻底失败了

这里藏着一个被反复问到的约束：max.in.flight.requests.per.connection 为什么必须 ≤ 5？因为 Broker 只缓存 5 个 batch 的序号窗口。超过 5 个未确认请求在飞，一旦中间某个失败重试，Broker 就无法判断顺序，只能报错——顺序性会被打破。

目标 必需配置 作用范围 不成立的情况
单分区不重复 enable.idempotence=true 单个 Producer 会话、单个分区 Producer 重启后 PID 会变，跨会话不去重
单分区严格有序 幂等 + max.in.flight ≤ 5 同一分区内 不同分区之间永远无序
按 key 有序 相同 key 路由到同一分区（默认分区器即可） 同一 key 的消息序列 分区数一变，key 的映射就变，历史顺序被打破
跨分区原子写 transactional.id + initTransactions 一个事务内的所有分区 写入外部系统（数据库、HTTP）不在事务范围内
端到端精确一次 上面全部 + 消费端 isolation.level=read_committed 仅 Kafka → Kafka（Streams 的 processing.guarantee） 下游是数据库或第三方接口时必须靠业务幂等
⚠️
「Kafka 支持 Exactly Once」这句话的适用范围很窄

Kafka 事务的本质是「消费 Kafka → 处理 → 写回 Kafka + 提交 offset」这一整套操作的原子性，由 TransactionCoordinator 用两阶段提交在 __transaction_state 里记录状态实现。它是闭环内的精确一次。

一旦下游是 MySQL 或外部 HTTP 接口，Kafka 的事务管不到那一侧：消息提交了但数据库写失败、或数据库写成功但 offset 提交失败，都会破坏语义。这种场景唯一可靠的做法是至少一次投递 + 消费端幂等（唯一键、状态机、去重表），不要指望配置参数。

核心原理四：Consumer Group 与 Rebalance

Rebalance 是 Kafka 消费端最大的稳定性风险：期间整个消费组停止消费（经典协议下是 stop-the-world）。要控制它，先得知道它被什么触发。

或等待超时 CompletingRebalance --> Stable: Leader 完成分配
SyncGroup 下发方案 Stable --> PreparingRebalance: 成员加入 / 主动离开 Stable --> PreparingRebalance: 心跳超时 session.timeout.ms Stable --> PreparingRebalance: poll 间隔超时 max.poll.interval.ms Stable --> PreparingRebalance: 订阅的 Topic 分区数变化 Stable --> Empty: 最后一个成员离开 note right of PreparingRebalance 这个状态期间消费完全停止 经典协议下所有分区都被回收 end note
参数 默认值 管什么 调错的症状
session.timeout.ms 45s（3.x） 心跳线程多久没心跳算掉线 设太小 → GC 一停顿就被踢出、频繁 Rebalance
heartbeat.interval.ms 3s 心跳发送间隔，应为 session 的 1/3 左右 比 session.timeout 还大 → 必然误判掉线

group.instance.id 未设 静态成员身份（KIP-345） 不设的话，滚动重启每个实例都触发一轮 Rebalance
❌
「心跳正常却被踢出组」的真相

心跳由独立后台线程发送，所以业务线程卡住时心跳依然正常。真正踢人的是 max.poll.interval.ms：Consumer 必须周期性调用 poll() 才证明自己还在消费。一次 poll 拉回 500 条，每条处理 1 秒 = 500 秒 > 默认 5 分钟，直接被判定为「卡死」踢出组，触发 Rebalance；重启后继续超时，形成无限 Rebalance 循环——表现就是 lag 不断涨、消费却几乎停滞。

两个方向解决：把 max.poll.records 降到「单批能在超时内处理完」的量；或把重活扔进业务线程池、让 poll 循环保持快速空转（但这样就必须自己管 offset 提交时机）。

分配策略 行为 Rebalance 代价 建议
RangeAssignor 按 topic 逐个把分区连续切分给消费者 全量重分配 订阅多 topic 时容易分配不均
RoundRobinAssignor 所有分区轮流发 全量重分配 均衡性好于 Range，但仍是 stop-the-world
StickyAssignor 尽量保留原有归属，同时保持均衡 仍会先回收全部分区 比前两者少搬动，但没消除停顿
CooperativeStickyAssignor 增量协作式：只回收需要迁移的那几个分区，其余继续消费 无全局停顿 ✅ 新项目直接用这个；升级需按官方两步走流程

核心原理五：offset 提交与投递语义

消费位点存在内置 topic __consumer_offsets 里（默认 50 分区，compact 策略）。三种投递语义的差别，完全取决于「提交 offset」和「处理业务」的先后顺序：

核心原理六：积压诊断与容量决策

Lag 的定义很简单：Lag = 分区 LEO − 已提交 offset。但看 lag 的方式决定了你能不能定位问题——要看每个分区的 lag，而不是总和。

# 逐分区查看 lag，重点看分布是否均匀
kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --group order-consumer --describe

# 输出示例：
# TOPIC          PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG    CONSUMER-ID
# order-events   0          150000          150020          20     consumer-1
# order-events   1          98000           480000          382000 consumer-2   ← 只有这个分区堆积
# order-events   2          150010          150015          5      consumer-3

# 重置位点（必须先停掉消费组，否则报错）
kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --group order-consumer --topic order-events \
  --reset-offsets --to-datetime 2026-09-22T10:00:00.000 --execute
Lag 分布形态 说明什么 怎么处理
所有分区均匀上涨 整体消费能力不足 加消费者（上限 = 分区数）；优化单条处理耗时；批量写下游
只有个别分区堆积 数据倾斜：某个 key 的消息量远超其他 换分区键或给热点 key 加随机后缀；顺序要求允许的话改用无 key 轮询
Lag 周期性尖刺后回落 上游定时批量任务 正常现象，确认恢复时间在 SLA 内即可，不必扩容
Lag 涨但消费者 CPU 很低 卡在下游 IO（数据库、HTTP） 提高消费端并发或异步化，加 Kafka 消费者是无效的
Lag 涨且反复 Rebalance max.poll.interval.ms 超时循环 降 max.poll.records，见上一节
Lag 突然变成负数或归零 位点被重置，或 topic 被重建 查 auto.offset.reset 与运维操作记录
⚠️
分区数不是想加就能加

只能增加不能减少，而且增加分区会立刻改变 hash(key) % 分区数 的映射——同一个订单 ID 的新消息会落到新分区，与它在老分区里未消费完的消息并行处理，顺序性当场失效。对顺序敏感的 topic，扩分区必须在业务低峰、确认积压清零后进行。

分区数也有上限：每个分区在每台 broker 上占若干文件句柄，Producer 为每个分区维护独立 batch 缓冲（batch.size × 分区数 可能吃满 buffer.memory），节点故障时的 Leader 选举时间也随分区数线性增长。经验上单 broker 控制在数千分区以内，别为了「以后可能要扩」上来就开 200 个分区。

最容易踩的坑

❌
避坑清单
  • 只设 acks=all 就以为不丢：ISR 收缩到只剩 Leader 时它等价于 acks=1。必须同时配 min.insync.replicas=2 和 RF=3。
  • 开了 unclean.leader.election.enable=true：允许落后副本当 Leader，等于主动接受丢数据。默认就是 false，别改。
  • 单批处理耗时超过 max.poll.interval.ms：心跳正常却被踢出组，陷入 Rebalance 死循环，lag 只涨不降。
  • 对顺序敏感的 topic 随手扩分区：key 的映射立刻改变，同一业务实体的消息被并行处理。分区数只增不减，扩容前必须清空积压。
  • 消费者数量多于分区数：多出来的消费者完全空闲，加机器不会提升吞吐。
  • 依赖 Kafka 事务做跨系统一致性：事务只覆盖 Kafka 内部。写数据库、调接口一律靠业务幂等兜底。
  • 给 broker 配几十 GB 的 JVM 堆：Kafka 依赖 Page Cache，堆大反而挤占缓存、拉长 GC 停顿。6GB 左右足够。
  • 开了 TLS 还期待零拷贝：加密必须在用户态完成，sendfile 直接失效，吞吐会明显下降，容量规划要按加密后的数据算。
  • Broker 与 Producer 的 compression.type 不一致：broker 会解压重压，CPU 飙升且零拷贝失效。统一设为 producer。
  • 用 Kafka 发几 MB 的大消息：要同时改 message.max.bytes、replica.fetch.max.bytes、max.request.size、fetch.max.bytes 四处，且内存和延迟都会恶化。正确做法是消息里只放对象存储的引用。
