Kafka 深度原理：存储、副本、Rebalance 与投递语义

🏷️ Kafka

「Kafka 快是因为顺序写磁盘」只是四个原因之一，而且解释不了它更重要的部分：怎么在异步复制的前提下做到不丢消息。这一篇是整条 Kafka 路径的主干，既是集群出问题时的入口，也是后面六篇共同依赖的机制底座。

① 用法 · 集群出问题时先敲的四条命令

Kafka 的故障现象高度重复：要么写入被拒，要么 LAG 只涨不降，要么消费者反复重分配。这三类问题都能用下面四条命令在两分钟内定位到环节。注释说明的是「为什么要看这一行」，字段含义的由来在原理层展开。

# ① 副本健康：Isr 列表短于 Replicas 就说明冗余已经在流失
bin/kafka-topics.sh --bootstrap-server localhost:9092 --describe --topic order-events
# Topic: order-events  Partition: 0  Leader: 1  Replicas: 1,2,3  Isr: 1,2,3   正常
# Topic: order-events  Partition: 1  Leader: 2  Replicas: 1,2,3  Isr: 2       只剩 Leader，此刻 acks=all 等价于 acks=1

# ② 全集群一次捞出副本不足的分区。这是 Kafka 最该配告警的单一信号
bin/kafka-topics.sh --bootstrap-server localhost:9092 --describe --under-replicated-partitions

# ③ 消费侧：LAG 必须逐分区看，看总和会把热点分区完全掩盖掉
bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 --group order-consumer --describe
# TOPIC         PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG     CONSUMER-ID
# order-events  0          150000          150020          20      consumer-1
# order-events  1          98000           480000          382000   consumer-2   只有这个分区堆积
# 若同一分区的 CONSUMER-ID 每次执行都在变，说明消费组正在反复 Rebalance

# ④ 控制面：KRaft 下先确认 quorum 有 Leader、各节点的复制进度没有掉队
bin/kafka-metadata-quorum.sh --bootstrap-server localhost:9092 describe --status

# ⑤ 任何参数都别凭记忆，直接问集群当前生效值（默认值随版本变化）
bin/kafka-configs.sh --bootstrap-server localhost:9092 --describe --entity-type topics --entity-name order-events
bin/kafka-configs.sh --bootstrap-server localhost:9092 --describe --entity-type brokers --entity-name 1

② 原理 · 存储引擎：分段日志与稀疏索引

搞清这一节能解决两个现象：磁盘占用为什么是阶梯式下降而不是平滑下降，以及开了 TLS 之后吞吐为什么会掉一截。一个 Partition 在磁盘上就是一个目录，里面是一组分段（Segment）文件，文件名是该段第一条消息的 offset，天然有序：

$ ls -l /kafka-logs/order-events-0/
00000000000000000000.log        # 消息本体，只追加
00000000000000000000.index      # offset 到物理位置，稀疏
00000000000000000000.timeindex  # 时间戳到 offset，稀疏
00000000000000368769.log        # 下一段，名字是起始 offset
00000000000000368769.index
00000000000000368769.timeindex
leader-epoch-checkpoint         # 记录 Leader 任期，用于截断对齐

索引是稀疏的：默认每写入 4KB 数据（log.index.interval.bytes）才记一条索引项。这是空间与时间的折中——索引文件小到可以整个 mmap 进内存，代价是最后一小段需要顺序扫描。而顺序扫描恰好是磁盘和 Page Cache 最擅长的事。删除也发生在段这一级：retention 到期删的是整个段文件，所以磁盘释放是阶梯式的。

性能手段机制量级什么情况下失效
顺序追加写只在段末尾 append，从不原地修改机械盘顺序写可达随机写的百倍量级分区数过多时，多个分区并发写会把顺序写退化成随机写
Page Cache写只写内核页缓存，由 OS 决定刷盘；读也优先命中缓存热数据读写接近内存速度消费者读取很老的数据（冷读），会击穿缓存打到磁盘
零拷贝 sendfile数据从 Page Cache 直接进网卡，不经过用户态省掉 2 次拷贝和 2 次上下文切换开启 TLS 加密时失效（必须在用户态加密）；broker 需要转换消息格式或压缩格式时也失效
批量加压缩Producer 攒批压缩，Broker 原样存储，Consumer 取回解压网络和磁盘用量降到几分之一Broker 的 compression.type 与 Producer 不一致时会解压重压，CPU 飙升且零拷贝失效
分区并行Topic 拆多个 Partition，分散到不同 broker线性扩展写入和消费能力分区数超过消费者数时无法进一步并行；单 key 的顺序要求会限制分区利用率
💡
Kafka 的 JVM 堆不需要调大

Kafka 把缓存完全交给操作系统 Page Cache，自己几乎不在堆里缓存消息。所以 broker 的 heap 给 6GB 左右就够，剩下的物理内存全部留给 Page Cache。给 broker 配 64GB 堆是典型的反向优化：堆越大 GC 停顿越长，而可用于缓存的内存反而变少。

同理，vm.swappiness 建议设 1 而不是 0——完全禁止 swap 会让内存紧张时直接触发 OOM Killer，留一点余量更稳。

② 原理 · ISR、HW/LEO 与「真正不丢」的参数组合

搞清这一节能解决用法层第一行那个现象：为什么写入会被 broker 主动拒绝，以及为什么 acks=all 配了却还是丢了数据。先分清两个水位：

概念含义为什么重要
LEO（Log End Offset）该副本已写入的下一个 offset衡量单个副本的进度
HW（High Watermark）ISR 中所有副本 LEO 的最小值HW 之前的消息才算「已提交」，才对消费者可见
ISR与 Leader 保持同步的副本集合（含 Leader）决定 HW 推进速度，也决定 acks=all 等多少个副本
OSR落后超过 replica.lag.time.max.ms（常见默认 30 秒）被移出的副本不参与 HW 计算，也不能被选为 Leader（除非开 unclean）
LSO（Last Stable Offset）事务场景下，最早一个未完成事务的起始 offsetread_committed 的消费者只能读到 LSO
❌
acks=all 单独用是假的安全感

acks=all 的语义是「ISR 中当前所有副本都写入才返回」。如果 3 个副本里有 2 个因为网络或 GC 落后被移出 ISR，ISR 就只剩 Leader 自己——此时 acks=all 退化成了 acks=1。Leader 一挂，这批消息全丢，而 Producer 收到的是成功响应。

# Broker / Topic 端：ISR 少于 2 个就拒绝写入，宁可不可用也不丢
min.insync.replicas=2
default.replication.factor=3
# 禁止落后副本当选 Leader（默认已是 false，务必别改）
unclean.leader.election.enable=false

# Producer 端：三者必须同时配齐
acks=all
enable.idempotence=true
delivery.timeout.ms=120000

这套组合的含义是：3 副本、至少 2 个同步、不允许脏选举。能容忍 1 台 broker 故障且不丢数据；2 台同时故障时主动拒写而不是悄悄丢数据。

参数组合丢消息重复消息吞吐用在哪
acks=0随时可能不会最高指标埋点、日志采集，丢几条无所谓
acks=1Leader 切换时丢重试时会高可重放的数据管道
acks=all 加 min.insync.replicas=1ISR 收缩后仍会丢重试时会中最危险的组合：给了安全的错觉
acks=all 加 min.insync.replicas=2 加 RF=3不丢（容 1 节点故障）重试时会中订单、支付等业务消息的标准配置
上一行再加 enable.idempotence=true不丢单分区单会话内不重复中（几乎无损耗）3.0+ 默认开启，没理由关掉
再加事务 transactional.id不丢跨分区原子较低Kafka 到 Kafka 的流处理闭环

② 原理 · 幂等、事务与顺序的相互制约

搞清这一节能解决一类争论：「Kafka 支持 Exactly Once，所以我不用做幂等了」这句话错在哪。幂等 Producer 的实现只有两个字段：PID（Producer ID）加分区级递增序号。Broker 为每个「PID 加分区」维护最近 5 个 batch 的序号，重复序号直接丢弃，序号跳跃则报错。

sequenceDiagram autonumber participant P as Producer participant B as Broker 分区 Leader P->>B: InitProducerId B-->>P: 分配 PID = 1001 P->>B: batch seq=0，acks=all B-->>P: ack P->>B: batch seq=1 Note over P,B: 网络超时，ack 丢失
但 Broker 其实已经写入 P->>B: 重试 batch seq=1 B->>B: 发现 seq=1 已存在，丢弃，不重复写 B-->>P: ack（幂等生效） P->>B: batch seq=2 B-->>P: ack Note over B: 若收到 seq=4 而期望 seq=2
报 OutOfOrderSequenceException
说明中间有 batch 彻底失败了

这里藏着一个被反复问到的约束：max.in.flight.requests.per.connection 为什么必须不大于 5？因为 Broker 只缓存 5 个 batch 的序号窗口。超过 5 个未确认请求在飞，一旦中间某个失败重试，Broker 就无法判断顺序，只能报错——顺序性会被打破。

目标必需配置作用范围不成立的情况
单分区不重复enable.idempotence=true单个 Producer 会话、单个分区Producer 重启后 PID 会变，跨会话不去重
单分区严格有序幂等加 max.in.flight.requests.per.connection 不大于 5同一分区内不同分区之间永远无序
按 key 有序相同 key 路由到同一分区（默认分区器即可）同一 key 的消息序列分区数一变，key 的映射就变，历史顺序被打破
跨分区原子写transactional.id 加 initTransactions一个事务内的所有分区写入外部系统（数据库、HTTP）不在事务范围内
端到端精确一次上面全部加消费端 isolation.level=read_committed仅 Kafka 到 Kafka（Streams 的 processing.guarantee）下游是数据库或第三方接口时必须靠业务幂等
⚠️
「Kafka 支持 Exactly Once」这句话的适用范围很窄

Kafka 事务的本质是「消费 Kafka 到 处理 到 写回 Kafka 加提交 offset」这一整套操作的原子性，由 TransactionCoordinator 用两阶段提交在 __transaction_state 里记录状态实现。它是闭环内的精确一次。

一旦下游是 MySQL 或外部 HTTP 接口，Kafka 的事务管不到那一侧：消息提交了但数据库写失败、或数据库写成功但 offset 提交失败，都会破坏语义。这种场景唯一可靠的做法是至少一次投递加消费端幂等（唯一键、状态机、去重表），不要指望配置参数。落地写法见 幂等设计。

② 原理 · Consumer Group 与 Rebalance

搞清这一节能解决用法层里最常见的那条：LAG 涨而 CONSUMER-ID 不停变化。Rebalance 是 Kafka 消费端最大的稳定性风险：期间整个消费组停止消费（经典协议下是 stop-the-world）。要控制它，先得知道它被什么触发。

partition.assignment.strategy3.x 默认含 Range 与 CooperativeSticky分区分配策略用 Range 时扩缩容会全量重分配，抖动大
group.instance.id未设静态成员身份（KIP-345）不设的话，滚动重启每个实例都触发一轮 Rebalance
❌
「心跳正常却被踢出组」的真相

心跳由独立后台线程发送，所以业务线程卡住时心跳依然正常。真正踢人的是 max.poll.interval.ms：Consumer 必须周期性调用 poll() 才证明自己还在消费。一次 poll 拉回 500 条、每条处理 1 秒就是 500 秒，超过默认的 5 分钟，直接被判定为「卡死」踢出组，触发 Rebalance；重启后继续超时，形成无限 Rebalance 循环——表现就是 lag 不断涨、消费却几乎停滞。

两个方向解决：把 max.poll.records 降到「单批能在超时内处理完」的量；或把重活扔进业务线程池、让 poll 循环保持快速空转（但这样就必须自己管 offset 提交时机，写法见 生产者与消费者实战）。

分配策略行为Rebalance 代价建议
RangeAssignor按 topic 逐个把分区连续切分给消费者全量重分配订阅多 topic 时容易分配不均
RoundRobinAssignor所有分区轮流发全量重分配均衡性好于 Range，但仍是 stop-the-world
StickyAssignor尽量保留原有归属，同时保持均衡仍会先回收全部分区比前两者少搬动，但没消除停顿
CooperativeStickyAssignor增量协作式：只回收需要迁移的那几个分区，其余继续消费无全局停顿新项目直接用这个；从旧策略升级需按官方两步走流程

② 原理 · offset 提交与投递语义

搞清这一节能解决「消息明明处理了却又来一遍」和「位点莫名跳走」这两类现象。消费位点存在内置 topic __consumer_offsets 里（默认 50 分区，compact 策略）。三种投递语义的差别，完全取决于「提交 offset」和「处理业务」的先后顺序：

② 原理 · 积压诊断与容量决策

搞清这一节能解决「该加消费者还是加分区」这个每次堆积都要吵一遍的问题。Lag 的定义很简单：Lag = 分区 LEO 减去已提交 offset。但看 lag 的方式决定了你能不能定位问题——要看每个分区的 lag，而不是总和。

# 逐分区查看 lag，重点看分布是否均匀
kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --group order-consumer --describe

# 重置位点（必须先停掉消费组，否则报错）
kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --group order-consumer --topic order-events \
  --reset-offsets --to-datetime 2026-09-22T10:00:00.000 --execute

# 对比每个分区当前最早可用位点，判断历史数据是否已被 retention 清掉
kafka-run-class.sh kafka.tools.GetOffsetShell \
  --bootstrap-server localhost:9092 --topic order-events --time -2
Lag 分布形态说明什么怎么处理
所有分区均匀上涨整体消费能力不足加消费者（上限等于分区数）；优化单条处理耗时；批量写下游
只有个别分区堆积数据倾斜：某个 key 的消息量远超其他换分区键或给热点 key 加随机后缀；顺序要求允许的话改用无 key 轮询
Lag 周期性尖刺后回落上游定时批量任务正常现象，确认恢复时间在 SLA 内即可，不必扩容
Lag 涨但消费者 CPU 很低卡在下游 IO（数据库、HTTP）提高消费端并发或异步化，加 Kafka 消费者是无效的

⚠️
分区数不是想加就能加

只能增加不能减少，而且增加分区会立刻改变 key 到分区的映射——同一个订单 ID 的新消息会落到新分区，与它在老分区里未消费完的消息并行处理，顺序性当场失效。对顺序敏感的 topic，扩分区必须在业务低峰、确认积压清零后进行。

分区数也有上限：每个分区在每台 broker 上占若干文件句柄，Producer 为每个分区维护独立 batch 缓冲（batch.size 乘以分区数可能吃满 buffer.memory），节点故障时的 Leader 选举时间也随分区数线性增长。定量的估算步骤见 分区设计。

最容易踩的坑

❌
主干上的十个高频翻车点
  • 只设 acks=all 就以为不丢：ISR 收缩到只剩 Leader 时它等价于 acks=1。必须同时配 min.insync.replicas=2 和 RF=3。
  • 开了 unclean.leader.election.enable=true：允许落后副本当 Leader，等于主动接受丢数据。默认就是 false，别改。
  • 单批处理耗时超过 max.poll.interval.ms：心跳正常却被踢出组，陷入 Rebalance 死循环，lag 只涨不降。
  • 对顺序敏感的 topic 随手扩分区：key 的映射立刻改变，同一业务实体的消息被并行处理。分区数只增不减，扩容前必须清空积压。
  • 消费者数量多于分区数：多出来的消费者完全空闲，加机器不会提升吞吐，监控上却是一片 Running。
  • 依赖 Kafka 事务做跨系统一致性：事务只覆盖 Kafka 内部。写数据库、调接口一律靠业务幂等兜底。
  • 给 broker 配几十 GB 的 JVM 堆：Kafka 依赖 Page Cache，堆大反而挤占缓存、拉长 GC 停顿。
  • 开了 TLS 还期待零拷贝：加密必须在用户态完成，sendfile 直接失效，容量规划要按加密后重新算。
  • Broker 与 Producer 的 compression.type 不一致：broker 会解压重压，CPU 飙升且零拷贝失效。broker 端统一设为 producer。
  • 用 Kafka 发几 MB 的大消息：要同时改 message.max.bytes、replica.fetch.max.bytes、max.request.size、fetch.max.bytes 四处，且内存和延迟都会恶化。正确做法是消息里只放对象存储的引用。
  • 只监控总 LAG 不看分区分布：总量一万可能是均匀堆积，也可能是一个热点分区堆了一万，两者处理方式完全相反。
