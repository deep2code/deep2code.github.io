Kafka 生产级部署：KRaft 组建、监听器与容量规划

🏷️ Kafka 安装

解压加启动这件事，官方 quickstart 五分钟就能讲完，网上也不缺复制粘贴的命令清单。真正让人半夜起来的是另外几件事：监听器配错导致客户端「连得上但发不出」、漏了格式化步骤导致启动直接失败、堆内存配了 32GB 反而变慢、上线三个月后发现磁盘规划少算了副本数。这篇只讲这些——部署阶段需要做的决策，以及上线前必须做完的验证。

① 用法 · 一条能照着走完的 KRaft 部署路径

下面这条路径覆盖从零到可以接业务流量的全部动作。先看任务清单，再抄配置，最后跑验证。每一步「为什么是这样」都在原理层对应小节。

要做什么怎么做注意什么
规划角色与节点数3 台专用 controller 加 N 台 broker；小集群也可以 3 台混部controller 必须是奇数，3 台与 4 台的容错能力完全一样
生成 cluster idbin/kafka-storage.sh random-uuid全集群共用同一个 id，每台各自生成会导致节点被拒绝加入
格式化数据目录bin/kafka-storage.sh format -t ID -c 配置文件KRaft 新增的一步，漏了会报 No readable meta.properties files found
目录里已有数据还要再格式化加 --ignore-formatted不加会报 already formatted；确认要重建数据才清目录
确认集群「真的」起来了bin/kafka-metadata-quorum.sh ... describe --status进程存活不等于 quorum 形成，quorum 没成时建主题会一直超时
让内网与外网客户端都能连配两套监听器并分别 advertise 不同地址advertised.listeners 里绝不能出现 0.0.0.0，三台也不能写成同一个地址
建第一个业务 topicbin/kafka-topics.sh --create --partitions 6 --replication-factor 3副本数不能超过存活 broker 数，否则直接报 InvalidReplicationFactor
停一台做故障演练systemctl stop kafka 后立刻 --describe 看 LeaderLeader 应秒级迁走、客户端只有短暂重试；这一步不做就等于让真故障来验证
留下压测基线kafka-producer-perf-test.sh 与 kafka-consumer-perf-test.sh基线数字要写进部署文档，用法见 性能调优与压测

配置分两类节点。三台 controller 之间只有 node.id 不同，三台 broker 之间只有 node.id 与 advertised 地址不同，其余逐字相同：

########## 角色 A：专用 controller，3 台，node.id 取 1 / 2 / 3 ##########
process.roles=controller
node.id=1
# 这一行在全部 6 台机器上必须逐字相同，不一致会导致 quorum 永远选不出 Leader
controller.quorum.voters=1@kafka-c1.internal:9093,2@kafka-c2.internal:9093,3@kafka-c3.internal:9093
controller.listener.names=CONTROLLER
listeners=CONTROLLER://:9093
# controller 不服务客户端，所以这里没有 advertised.listeners
log.dirs=/data/kraft-metadata
listener.security.protocol.map=CONTROLLER:PLAINTEXT

########## 角色 B：broker，3 台，node.id 取 11 / 12 / 13 ##########
process.roles=broker
node.id=11
# 与 controller 节点那一行完全一致，照抄
controller.quorum.voters=1@kafka-c1.internal:9093,2@kafka-c2.internal:9093,3@kafka-c3.internal:9093
controller.listener.names=CONTROLLER

# 本进程真正 bind 的地址。留空主机名表示监听所有网卡
listeners=INTERNAL://:9092,EXTERNAL://:9094
# 写进元数据发给客户端的地址。每台 broker 这两个值都指向自己，三台各不相同
advertised.listeners=INTERNAL://kafka-b1.internal:9092,EXTERNAL://kafka-b1.example.com:9094
listener.security.protocol.map=CONTROLLER:PLAINTEXT,INTERNAL:PLAINTEXT,EXTERNAL:SASL_SSL
# 副本同步固定走内网明文：TLS 会让零拷贝失效，这一行能省下可观的 CPU
inter.broker.listener.name=INTERNAL

# 一块数据盘对应一个目录，不要做成 RAID 5 再只给一个目录
log.dirs=/data/kafka-logs-1,/data/kafka-logs-2

# 三个内部主题的副本因子，开发环境的 1 搬到生产就是一次全站消费停摆
offsets.topic.replication.factor=3
transaction.state.log.replication.factor=3
transaction.state.log.min.isr=2
default.replication.factor=3
min.insync.replicas=2

# 拼错主题名时宁可报错，也不要静默建出一个新主题
auto.create.topics.enable=false
# 它是用丢数据换可用性的开关，永远保持 false
unclean.leader.election.enable=false

log.retention.hours=168
log.segment.bytes=1073741824
# ① 生成 cluster id，只生成一次，后面所有节点共用这一个值
KAFKA_CLUSTER_ID=$(bin/kafka-storage.sh random-uuid)

# ② 在每台节点上格式化它自己的 log.dirs，往里写 meta.properties
#    漏掉这步启动就报 No readable meta.properties files found
bin/kafka-storage.sh format -t "$KAFKA_CLUSTER_ID" -c config/kraft/server.properties

# ③ 先起 3 台 controller，再起 broker。顺序反了 broker 会一直重试连 controller
bin/kafka-server-start.sh config/kraft/controller.properties   # 在 3 台 controller 上
bin/kafka-server-start.sh config/kraft/server.properties       # 在 broker 上

# ④ 确认 quorum 已经选出 Leader，这才算「真的起来了」
bin/kafka-metadata-quorum.sh --bootstrap-server kafka-b1.internal:9092 describe --status
#    LeaderId 有值、CurrentVoters 数量与规划一致、HighWatermark 在增长，三者同时满足

# ⑤ 建第一个业务 topic 并确认副本分布
bin/kafka-topics.sh --bootstrap-server kafka-b1.internal:9092 --create \
  --topic orders --partitions 6 --replication-factor 3
bin/kafka-topics.sh --bootstrap-server kafka-b1.internal:9092 --describe --topic orders
#    Isr 必须与 Replicas 完全一致，元素顺序可以不同

# ⑥ 全集群健康扫描，这两条在健康集群上都应该毫无输出
bin/kafka-topics.sh --bootstrap-server kafka-b1.internal:9092 --describe --under-replicated-partitions
bin/kafka-topics.sh --bootstrap-server kafka-b1.internal:9092 --describe --unavailable-partitions

内外网双监听是这一步最容易配错的地方，而且错了之后的症状极具误导性：能连上、能列主题，一发消息就超时。下面三条命令专门用来验证监听器，别靠肉眼读配置：

# 验证一：让集群把它「告诉客户端的地址」打印出来。这是最直接的验证手段
bin/kafka-broker-api-versions.sh --bootstrap-server kafka-b1.internal:9092 | grep -i 'id:'
# 期望看到三行，分别是三台 broker 各自的内网地址
# 出现 0.0.0.0、出现容器内部主机名、或者三行是同一个地址，都是配错了

# 验证二：从真正的外网客户端侧再验一遍，走 EXTERNAL 端口与它自己的安全协议
bin/kafka-broker-api-versions.sh --bootstrap-server kafka-b1.example.com:9094 \
  --command-config client-sasl-ssl.properties

# 验证三：端到端闭环。列主题成功而这一步超时，几乎一定是 advertised 地址不可达
echo "smoke-test" | bin/kafka-console-producer.sh \
  --bootstrap-server kafka-b1.internal:9092 --topic smoke
bin/kafka-console-consumer.sh --bootstrap-server kafka-b1.internal:9092 \
  --topic smoke --from-beginning --max-messages 1 --timeout-ms 10000

# 验证四：确认危险开关是关着的
bin/kafka-configs.sh --bootstrap-server kafka-b1.internal:9092 \
  --entity-type brokers --entity-default --describe | grep -i unclean

步骤怎么取数常见错误
① 量平均消息字节数用 kafka-log-dirs.sh --describe 拿分区实际占用字节，用首尾位点差拿条数，两者相除拿业务对象的 JSON 长度估算，忽略了消息头、key 与批次开销
② 量压缩比取一批真实样本，用你打算用的算法（lz4 或 zstd）压一次，看前后体积抄别人的压缩比。二进制或已加密的数据几乎压不动
③ 代入公式日均条数乘平均字节乘副本数乘保留天数，除以压缩比，除以节点数，再乘 1.4 余量漏乘副本数（RF=3 时总量是原始数据的三倍）、漏留余量
④ 反算分区规模用分区总数除以 broker 数，核对单 broker 承载的分区副本数是否在可控量级只算磁盘不算分区数，句柄与选举耗时会先到上限
 
# 第①步取数：每个分区在磁盘上的真实字节数（含索引文件）
bin/kafka-log-dirs.sh --bootstrap-server kafka-b1.internal:9092 \
  --topic-list orders --describe

# 条数用首尾位点差算：--time -1 是最新位点，--time -2 是最早可用位点
bin/kafka-run-class.sh kafka.tools.GetOffsetShell \
  --bootstrap-server kafka-b1.internal:9092 --topic orders --time -1
bin/kafka-run-class.sh kafka.tools.GetOffsetShell \
  --bootstrap-server kafka-b1.internal:9092 --topic orders --time -2

② 原理 · KRaft 的角色模型与 controller quorum

搞清这一节能解决「进程都活着，为什么建主题一直超时」。KRaft 把元数据也做成了一个 Raft 复制的日志，因此集群里出现了两类角色：controller 负责复制和提交元数据，broker 负责承载分区数据。一个进程扮演什么角色由 process.roles 决定。

process.roles 取值进程做什么适用场景注意
broker只承载分区数据，作为元数据日志的订阅方生产环境的数据节点必须通过 controller.quorum.voters 指向 controller 集合，自己不投票
controller只参与元数据 Raft 复制与提交生产环境的专用 controller 节点，3 台或 5 台不处理客户端请求，机器规格可以小，但磁盘延迟要低
broker,controller两者兼任，混部开发机、测试环境、极小规模集群broker 侧的磁盘与网络压力会推高元数据提交延迟，元数据卡顿会放大成全集群分区不可用

quorum 数量必须是奇数，通常 3 台，超大集群用 5 台。原因是 Raft 需要多数派确认：3 台的多数派是 2，容忍 1 台故障；4 台的多数派是 3，同样只容忍 1 台故障，却多花一台机器并增加一份复制开销。偶数节点唯一的作用是让你多付钱。

② 原理 · 监听器：listeners 与 advertised.listeners 的分工

搞清这个两段式流程能解决那个最有误导性的症状：listeners 和 advertised.listeners 只差一个词，但职责完全不同——前者是「我在本机绑哪个地址和端口」，后者是「我告诉客户端该怎么连我」。客户端配的 bootstrap.servers 只用于第一次取元数据，之后所有生产与消费请求都改用元数据里返回的 advertised 地址。

sequenceDiagram autonumber participant C as 宿主机上的客户端 participant B as 容器内的 Broker C->>B: 用 bootstrap 地址连 127.0.0.1 端口 9092，成功 C->>B: 发送 Metadata 请求 B-->>C: 返回 advertised.listeners 的值，内容是容器名加端口 Note over C,B: 坑就在这一步
bootstrap 只负责取元数据
之后的读写一律使用元数据里的地址 C->>C: 解析容器名失败，或解析到容器内网地址不可路由 C--xB: Produce 请求建连失败，进入重试 Note over C: 典型症状是能连上能列主题
但一发消息就超时，日志里只有连接重试
环境listeners 怎么写advertised.listeners 怎么写为什么
裸机单网卡PLAINTEXT://:9092PLAINTEXT://kafka-1.internal:9092advertise 一个客户端能解析的主机名，换 IP 时不用改配置
Docker，客户端在宿主机INTERNAL://:9092,EXTERNAL://:29092INTERNAL://kafka-1:9092,EXTERNAL://127.0.0.1:29092容器之间用容器名走 9092，宿主机客户端走映射出来的 29092，两套地址必须分开 advertise
K8s 内部访问INTERNAL://:9092INTERNAL://pod-name.svc-headless.ns.svc.cluster.local:9092必须用 headless Service 的稳定 DNS，不能用 ClusterIP，否则元数据里的地址会指向负载均衡后的随机 Pod
K8s 对外暴露再加一个 EXTERNAL://:9094每个 Pod advertise 自己独立的外部地址，如各自的 NodePort 或 LB 地址Kafka 客户端必须能直连到具体某个 broker，共用一个入口无法满足分区级路由
内外网流量分离INTERNAL://:9092,EXTERNAL://:9094，配合 listener.security.protocol.map=INTERNAL:PLAINTEXT,EXTERNAL:SASL_SSL内网 advertise 内网地址走明文，外网 advertise 公网地址走加密加认证副本同步走内网免去加密开销，用 inter.broker.listener.name=INTERNAL 指定；外部流量强制 TLS 加 SASL
❌
三条监听器铁律

第一，advertised.listeners 里绝不能出现 0.0.0.0，那是绑定地址不是可达地址，客户端拿到后无法使用。第二，每台 broker 的 advertised 地址必须各不相同且唯一指向自己，三台写成同一个地址会让客户端把所有请求打到一台上并不断报 leader 不匹配。第三，controller.listener.names 指定的监听器只用于内部 Raft，不要把它加进 advertised.listeners，也不要让客户端去连它。三条都可以用用法层的验证命令当场证伪。

② 原理 · 磁盘、文件系统与主机层参数

搞清这一节能解决一类「查不出原因」的 ISR 抖动。Kafka 是顺序写加 page cache 命中读的负载，主机层配置对它的影响比大多数 Java 服务更直接。

项目推荐值默认值或常见错误配错的后果
磁盘组织多块独立盘，每块一个目录写进 log.dirs做成 RAID 5 或 RAID 6RAID 5 的写惩罚拖垮顺序写，重建期间性能雪崩；副本机制已提供冗余，不需要再叠一层
文件系统XFS，挂载加 noatimeext4 也能跑，但大文件顺序写与删除吞吐更差ext4 在段文件集中删除时容易出现毛刺；不加 noatime 会产生大量无用元数据写
存储介质本地 SSD 或 NVMeNFS 等网络文件系统网络文件系统的锁语义和延迟抖动会造成难以定位的复制滞后与 ISR 抖动
JVM 堆-Xms6g -Xmx6g，初始堆与最大堆相等给 64GB 机器配 32GB 堆堆越大 page cache 越小，消费者更容易落到磁盘读；GC 停顿变长还会拖出无谓的副本抖动
垃圾回收器G1，暂停目标 20ms 左右沿用老教程的 CMS 或不显式指定长停顿会让 broker 被 controller 判为失联，触发不必要的 Leader 切换
vm.swappiness1多数发行版默认 30 或 60一旦 page cache 被换出，读写延迟抖动一到两个数量级；设成 0 则在内存紧张时可能直接触发 OOM kill
vm.max_map_count262144常见默认 65530每个段的索引文件都会 mmap，分区多时会报 Map failed，表现为启动或滚动段时崩溃
文件句柄 nofile100000 以上常见默认 1024每个段文件和每个连接都占句柄，几百分区就会报 Too many open files 并导致分区离线
# --- JVM：堆要小，内存留给 page cache ---
# Kafka 的写入先进 page cache 由内核异步刷盘，消费近期数据直接命中缓存
# 所以可用内存越多越好，而堆只服务网络缓冲与元数据
export KAFKA_HEAP_OPTS="-Xms6g -Xmx6g"
export KAFKA_JVM_PERFORMANCE_OPTS="-XX:+UseG1GC -XX:MaxGCPauseMillis=20 \
  -XX:InitiatingHeapOccupancyPercent=35 -XX:+ExplicitGCInvokesConcurrent \
  -Djava.awt.headless=true"

# --- 内核参数，写进 /etc/sysctl.d/99-kafka.conf ---
# 几乎禁止换出，但保留 1 而不是 0，避免内存紧张时直接被 OOM killer 干掉
vm.swappiness=1
# 每个段的索引文件都要 mmap，默认值在分区多时不够用
vm.max_map_count=262144
# 让脏页刷盘更平滑，避免集中刷盘造成写入毛刺
vm.dirty_background_ratio=5
vm.dirty_ratio=60
# 提高网络缓冲上限，跨机房复制时收益明显
net.core.somaxconn=32768

# --- 文件句柄，写进 /etc/security/limits.d/kafka.conf ---
# 句柄消耗约等于 段文件数 加 连接数，默认 1024 远远不够
kafka  soft  nofile  128000
kafka  hard  nofile  128000

# 上线前确认实际生效值，改了配置但没重启服务是最常见的假调优
cat /proc/$(pgrep -f kafka.Kafka)/limits | grep 'open files'

② 原理 · 容量公式里最常漏掉的三项

搞清这一节能避免最难临时处置的故障之一：磁盘写满导致分区全部离线。估算公式本身不复杂：

单节点磁盘需求 = 日均消息条数 乘 平均消息字节数 乘 副本数 乘 保留天数 除以 压缩比 除以 节点数 再乘 1.4 余量

三个漏项按出现频率排序：副本数必须乘进去，RF 等于 3 时集群总占用是原始数据的三倍；压缩比必须实测，JSON 日志用 zstd 常能压到几分之一，已经是二进制或加密的数据几乎压不动，抄来的比例会让你少买一半磁盘；余量至少留 40%，因为分区重分配期间数据会临时双写、突发流量会让保留期内数据量超预期，而磁盘写满的后果不是变慢而是 broker 直接把分区标为离线。举例：日均 5 亿条、平均 800 字节、RF 3、保留 7 天、压缩比 4、6 个节点，单节点约需 5e8 乘 800 乘 3 乘 7 除以 4 除以 6 乘 1.4，约 3.4TB。

另一条容量约束是分区总数。单台 broker 承载的分区副本数受文件句柄、生产端批次缓冲、故障恢复时的选举耗时三重限制；KRaft 模式下集群可承载的分区规模比 ZooKeeper 时代高出若干量级，但仍要监控 controller 的元数据提交延迟。分区数的具体推导与上限约束见下一篇 分区设计。

② 原理 · 上线前四项验证与输出判读

部署完成不等于可以上线。下面四项验证的价值在于：它们会在你还能从容处理的时候暴露问题。

# 验证一：副本健康。Isr 必须与 Replicas 完全一致
bin/kafka-topics.sh --bootstrap-server kafka-1:9092 --describe --topic orders
# Topic: orders  Partition: 0  Leader: 1  Replicas: 1,2,3  Isr: 1,2,3

# 验证二：压出基线数字并留档，日后性能怀疑时才有对比基准
bin/kafka-producer-perf-test.sh --topic perf-test --num-records 5000000 \
  --record-size 1024 --throughput -1 \
  --producer-props bootstrap.servers=kafka-1:9092 acks=all linger.ms=10 batch.size=65536
bin/kafka-consumer-perf-test.sh --bootstrap-server kafka-1:9092 \
  --topic perf-test --messages 5000000
# 关注 records/sec、MB/sec 和 p99 延迟三个数，写进部署文档

# 验证三：故障演练。手动停掉一台 broker，确认 Leader 自动迁移
sudo systemctl stop kafka          # 在 broker-2 上执行
bin/kafka-topics.sh --bootstrap-server kafka-1:9092 --describe --topic orders
# Leader 应从 2 迁到 1 或 3，Isr 剩两个成员
# 同时观察客户端：只应出现短暂重试，不应出现持续报错或数据丢失
sudo systemctl start kafka
# 等 under-replicated 回到 0，再做一次优先副本选举把 Leader 均衡回来
bin/kafka-leader-election.sh --bootstrap-server kafka-1:9092 \
  --election-type PREFERRED --all-topic-partitions

# 验证四：确认危险开关处于关闭状态
bin/kafka-configs.sh --bootstrap-server kafka-1:9092 \
  --entity-type brokers --entity-default --describe | grep -i unclean
# 期望看到 unclean.leader.election.enable=false
验证项怎么判读输出不正常时先查什么
Isr 完整性Isr 列表与 Replicas 完全一致，顺序可以不同查该 broker 磁盘是否饱和、网络是否丢包、replica.lag.time.max.ms 是否被调得过小
quorum 状态LeaderId 有值，CurrentVoters 数量等于规划数，HighWatermark 在增长各节点的 controller.quorum.voters 是否完全相同、controller 端口是否互通
生产基线关注 records/sec、MB/sec 与 p99，三个数一起记录才有意义先确认是不是 acks 与 linger.ms 的配置差异，再怀疑硬件，方法见 性能调优与压测
Leader 切换停机后 Leader 在秒级内换人，客户端只有短暂重试切换慢通常是分区数过多或 controller 混部被拖慢
Leader 分布各 broker 的 Leader 数量大致均衡重启后 Leader 全堆在一台上，跑优先副本选举；长期倾斜检查 auto.leader.rebalance.enable

② 原理 · 滚动重启与两阶段升级

搞清这一节能解决「升级到一半发现有问题还能不能退回去」。

stateDiagram-v2 [*] --> PreCheck PreCheck: 确认全集群 under-replicated 分区数为 0 PreCheck --> Pin: 条件满足 PreCheck --> Wait: 存在未同步副本 Wait: 先修复复制滞后再继续 Wait --> PreCheck Pin: 第一阶段把 inter.broker.protocol.version 显式固定为旧版本 Pin --> StopOne StopOne: 优雅停止一台 broker，Leader 自动迁走 StopOne --> StartOne StartOne: 替换二进制后启动该节点 StartOne --> Catchup Catchup: 该节点追赶日志并重新进入 Isr Catchup --> NextOne: under-replicated 回到 0 NextOne: 还有节点未处理则继续下一台 NextOne --> StopOne NextOne --> Bump: 全部节点已替换 Bump: 第二阶段提升 inter.broker.protocol.version 再滚一轮 Bump --> [*] note right of Catchup 这一步绝对不能省 连续重启两台会让同一分区同时缺两个副本 配合 min.insync.replicas 等于 2 就直接不可写 end note

两阶段的意义是保留回退能力：第一阶段协议版本仍是旧的，新旧 broker 可以共存，发现问题可以把二进制换回去；第二阶段提升协议版本后，旧版本 broker 无法识别新协议写下的数据，这一步之后不可回退。所以第二阶段要等第一阶段稳定运行一段时间再做。

形态适用阶段真实成本在哪什么时候会翻车
本地单机 KRaft开发调试几乎为零，单进程兼任 broker 与 controller把它的配置直接搬到生产：副本因子 1、内部主题副本 1，任何一次重启都是数据不可用
Docker Compose集成测试、本地多节点验证时间几乎全花在 advertised.listeners 上，容器内外地址不一致宿主机客户端拿到容器内主机名，连不通；用 host 网络绕过后又在 CI 机器上不可用
K8s 加 Operator已有 K8s 平台的生产环境Operator 本身省了很多事，但存储类、反亲和、对外暴露、滚动更新策略都要自己想清楚用了网络存储导致复制滞后；Pod 漂移后 advertised 地址变化；节点亲和没配导致三个副本落在同一台物理机
裸机或虚机集群吞吐要求高、要压榨硬件的生产环境装机、配置管理、监控、升级流程全要自己搭缺少标准化，三台机器的内核参数和磁盘布局不一致，故障表现无法复现
托管服务团队没有专职运维，或不想背升级与值班单价明显高于自建，但省掉的是人力与事故；跨可用区流量费常被低估需要深度定制 broker 参数或用特殊插件时受限；跨云或跨账号访问的网络打通比想象中麻烦
💡
一个常被忽略的算账方式

自建三节点集群的机器成本可能只有托管服务的三分之一，但要算上：一个人熟悉 Kafka 运维的时间、7 乘 24 的值班、每年至少一次的版本升级、磁盘扩容与分区重分配的操作窗口，以及第一次事故的业务损失。日消息量在千万条以下、团队少于二十人时，托管几乎总是更划算；量级上去之后自建的成本优势才会真正显现。

③ 场景 · 启动与运行失败对照表

启动或运行失败的表现直接原因怎么修
No readable meta.properties files foundKRaft 模式下没有执行存储目录格式化先 random-uuid 生成 cluster id，再对每个 log.dirs 执行 kafka-storage.sh format
Log directory is already formatted目录里已有 meta.properties 又重复格式化确认要保留数据就跳过格式化，或加 --ignore-formatted；确认要重建才清空目录
cluster id 不匹配，节点拒绝启动节点用了与集群不同的 cluster id，通常是复制配置时忘了同步让所有节点使用同一个 cluster id，清掉错误节点的 meta.properties 重新格式化
建主题或元数据操作一直超时，但进程存活controller quorum 没有形成 Leader用 kafka-metadata-quorum.sh describe --status 看状态，核对各节点的 controller.quorum.voters 是否完全一致、controller 端口是否互通
客户端能列主题但生产消费超时advertised.listeners 指向客户端不可达的地址用用法层的验证命令把实际 advertise 的地址打印出来；内外网不同就配两个监听器分别 advertise
Address already in use端口被上一个未退干净的进程或其他服务占用确认旧进程已退出再启动；KRaft 下注意 9092 与 9093 是两个不同用途的端口
Too many open files 后分区离线nofile 限制太低调高 limits 并重启服务，之后用 /proc 下的 limits 确认实际生效
Map failed 或直接 OOMvm.max_map_count 不足，段索引文件无法 mmap调到 262144 并持久化到 sysctl 配置
创建主题报副本因子无效副本数大于当前存活 broker 数先补节点再建主题；单机环境把副本因子改成 1
磁盘写满后分区全部离线容量规划漏算副本数或保留期，且没留余量紧急时缩短 retention.ms 让清理线程释放段文件，之后扩盘并重新做容量规划

不适用边界：这一篇只负责把集群按生产标准立起来。要不要用 Kafka 在上一篇 选型边界；topic 建几个分区、分区键怎么选是下一步的事；客户端参数怎么配在 生产者与消费者实战；压测怎么做与瓶颈怎么定位在 性能调优与压测；ISR、水位与 acks 的机制回到 主干篇。ACL、SASL 机制选择与证书轮换属于安全域，不在本篇范围。

集群起来、验证通过之后，下一步是决定每个 topic 开几个分区——这个决定一旦做错，后面只能在破坏顺序性和继续堆积之间二选一。

最容易踩的坑

❌
部署阶段的十四个高频翻车点
  • 把开发环境的配置直接搬到生产。三个内部主题的副本因子留在 1，其中一台节点故障就会让所有消费组位点不可用，全站消费停摆。
  • advertised.listeners 写成 0.0.0.0 或三台写成同一个地址。症状是能连上能列主题但一发消息就超时，日志里只有连接重试，非常难定位。
  • 漏掉 kafka-storage.sh format。这是 KRaft 相对 ZooKeeper 时代新增的一步，照抄老教程必然踩。
  • controller quorum 配成偶数台。4 台和 3 台的容错能力完全一样，只是多花钱多一份复制开销。
  • 把 controller 与高负载 broker 混部。broker 磁盘打满时元数据提交跟着变慢，进而放大成全集群的分区不可用。
  • 给 Kafka 配几十 GB 堆。这是反向优化：page cache 被挤小、GC 停顿变长，吞吐不升反降。
  • 用 RAID 5 或网络文件系统放 log.dirs。写惩罚与延迟抖动会表现成莫名其妙的 ISR 抖动和复制滞后。
  • 忘了改 nofile 和 vm.max_map_count。小流量时一切正常，分区涨到几百个之后突然大面积分区离线。
  • 容量规划漏乘副本数或漏留余量。磁盘写满不是性能下降而是分区直接离线，属于最难临时处置的故障之一。
  • 压缩比照抄别人的数字。加密或已压缩的数据几乎压不动，按 5 比 1 规划会直接少买一半磁盘。
  • 开着 unclean.leader.election.enable 上线。它允许落后副本当 Leader，等价于默认接受静默丢数据。
  • 滚动重启时连续停两台。同一分区同时缺两个副本，配合 min.insync.replicas=2 会立刻变成不可写。
  • 跳过两阶段直接提升 inter.broker.protocol.version。升级过程中一旦出问题无法回退，只能硬着头皮往前修。
  • 上线前不做 kill broker 演练。Leader 切换和客户端重连是否真的正常，只有故障演练能回答，等真故障时再验证代价太大。
  • 不留压测基线。三个月后有人说「Kafka 变慢了」，没有基线数字就只能靠感觉争论。
