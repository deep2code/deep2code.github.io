Kafka 分区设计：分区数、分区键与顺序性代价

🏷️ Kafka 分区

Kafka 的绝大多数参数都能在线改，改错了改回来就行。分区数和分区键不是——分区只能增不能减，而增加分区会立刻改变 key 到分区的映射；分区键一旦上线，改了就等于换一套顺序性语义。这两个决策做错，代价是一次主题级别的数据迁移。这篇只谈这两件事怎么定。分段日志、稀疏索引、ISR 与水位机制不在这里展开，详见站内 Kafka 深度原理一篇。

分区数决定什么，以及怎么估

分区数决定的事具体机制估算方式
消费并行度上限同一消费组内一个分区只能被一个实例占有，多出的实例空转分区数不小于该主题预计的最大消费者实例数，并为未来扩容预留
单分区吞吐上限一个分区的写入落在单台 broker 的单个日志目录上，受单盘顺序写与单线程复制限制在自己硬件上实测单分区吞吐，通常每秒几十 MB 量级，不要抄别人的数字
有序性粒度只有分区内有序，同一 key 落同一分区才能保证该实体的事件顺序由分区键设计决定，不是由分区数决定；分区数只影响这个粒度的分布
存储分布均匀度分区是分配到 broker 与磁盘上的最小单位分区数最好是 broker 数的整数倍，否则各节点负载天然不均

可操作的估算顺序是：先算吞吐下限（目标峰值吞吐 ÷ 实测单分区吞吐），再算并行度下限（预计最大消费者实例数），取两者的最大值，最后向上取整并留三到五成余量。举例：目标峰值 300 MB/s、实测单分区 25 MB/s，吞吐下限是 12；消费端预计最多跑 10 个实例，并行度下限是 10；取大值 12，留余量取 16，同时 16 正好是 8 台 broker 的整数倍。

# 第一步：在目标硬件上实测单分区吞吐，这是所有估算的基准
bin/kafka-topics.sh --bootstrap-server kafka-1:9092 --create \
  --topic probe-1p --partitions 1 --replication-factor 3
bin/kafka-producer-perf-test.sh --topic probe-1p --num-records 2000000 \
  --record-size 512 --throughput -1 \
  --producer-props bootstrap.servers=kafka-1:9092 acks=all linger.ms=10
# 记下输出里的 MB/sec，这才是你环境的单分区吞吐，与网上的数字无关

# 第二步：按估算结果建主题，顺手把 min.insync.replicas 一起定下来
bin/kafka-topics.sh --bootstrap-server kafka-1:9092 --create \
  --topic orders --partitions 16 --replication-factor 3 \
  --config min.insync.replicas=2

# 第三步：需要扩容时只能增加，且必须在低峰且积压清零后执行
bin/kafka-topics.sh --bootstrap-server kafka-1:9092 \
  --alter --topic orders --partitions 24
# 想减少会直接被拒：The number of partitions for a topic can only be increased

# 查看分区分布是否均衡，Leader 分散在不同 broker 上才算正常
bin/kafka-topics.sh --bootstrap-server kafka-1:9092 --describe --topic orders

分区数的上限约束

「分区越多吞吐越高」只在拐点之前成立。下面这三条约束是拐点的来源，也是线上事故的来源。

约束为什么会成为瓶颈经验量级超限后的症状
文件句柄与 mmap每个分区在所在 broker 上至少有一组段文件加索引文件，索引文件全部 mmap；副本也算单 broker 分区副本数控制在两千到四千以内Too many open files 或 Map failed，分区批量离线，重启也起不来
生产端批次内存Producer 为每个分区维护一个独立的 batch 缓冲，batch.size 乘以分区数是理论峰值占用，超过 buffer.memory（默认 32MB）就会阻塞单个 Producer 实例写入的分区数乘以 batch.size 不要超过 buffer.memory 的一半send() 阻塞或抛出超时，表现为业务线程被拖住，而 broker 侧毫无压力
故障恢复时的选举耗时一台 broker 宕机后，它上面所有 Leader 分区都要重新选举，耗时随分区数近似线性增长单 broker 的 Leader 分区数控制在千级，避免单点故障造成长时间不可写宕机后客户端出现秒级到十秒级的持续报错，而不是预期的短暂重试
端到端延迟分区多则每个分区的写入速率低，攒满一个批次要等更久低延迟场景宁少不多，靠加大 linger.ms 之外的手段提升吞吐吞吐没提升，p99 延迟反而上涨
⚠️
被忽略最多的一条是生产端内存

一个 Producer 实例往 1000 个分区写、batch.size 保持默认 16KB，理论峰值缓冲需求是 16MB，已经占掉默认 buffer.memory 的一半；如果有人把 batch.size 调到 256KB 去「优化吞吐」，需求就变成 256MB，远超默认值，结果是 send() 在缓冲区满时阻塞住业务线程。这类故障的排查方向常常一开始就跑偏，因为 broker 的所有指标都正常。

Kafka 不会为了修正映射而搬迁任何已有数据，老分区里的老消息原地不动。所以这个窗口期的长度就是「老分区里还有未消费消息」的时长，把积压清零就等于把窗口压到零。至于分区为什么不能减少：删掉一个分区就必须决定里面的数据怎么办，搬到别的分区会破坏 offset 连续性与分区内有序，直接丢弃是静默丢数据，两种都不可接受，于是 Kafka 干脆禁止。真的需要减少时，唯一办法是新建一个分区数正确的主题做一次迁移。

分区键与分区器

分区选择完全发生在客户端。默认分区器的行为分两种情况，而无 key 的那一种在 2.4 版本发生过一次容易被忽略的变化。

  • 有 key：partition = Utils.toPositive(Utils.murmur2(keyBytes)) % numPartitions。注意哈希的是序列化后的字节，所以换序列化方式会改变分区归属；取模的是当前分区总数，所以扩分区会改变映射。
  • 无 key，2.4 之前：轮询。每条消息进入不同分区的批次，批次很难攒满，请求数多且延迟更差。
  • 无 key，2.4 及之后：粘性分区器。不再是轮询，而是粘住一个分区持续写入，直到当前批次被发出才切换下一个分区。这样批次更容易攒满，吞吐与延迟同时改善，长期看分布依然均衡。
💡
粘性分区器会造成一种假倾斜

用秒级粒度观察单个分区的写入速率时，粘性分区器会让某个分区在一小段时间内明显高于其他分区，这是攒批策略的正常表现，不是数据倾斜。判断倾斜要看分钟级以上的累计量或 offset 增速，并且只有在使用了 key 的主题上才需要认真怀疑倾斜。

// 场景：九成流量来自少数几个大商户，直接用 merchantId 做 key 会把单分区打满
// 策略：热点 key 追加随机偏移打散，非热点 key 保持默认行为以维持有序
public class HotKeySaltingPartitioner implements Partitioner {

    // 热点清单在生产中应从配置中心动态下发，硬编码只是为了演示
    private static final Set<String> HOT_KEYS = Set.of("m_10001", "m_10002");
    // 每个热点 key 打散到多少个分区；越大越均匀，但该 key 的有序性彻底放弃
    private static final int SALT_BUCKETS = 8;

    private final Random random = new Random();

    @Override
    public int partition(String topic, Object key, byte[] keyBytes,
                         Object value, byte[] valueBytes, Cluster cluster) {
        int numPartitions = cluster.partitionsForTopic(topic).size();
        if (keyBytes == null) {
            // 无 key 时交回默认逻辑，不要在这里自己轮询，会破坏粘性攒批
            return Utils.toPositive(random.nextInt()) % numPartitions;
        }
        String k = new String(keyBytes, StandardCharsets.UTF_8);
        int base = Utils.toPositive(Utils.murmur2(keyBytes)) % numPartitions;
        if (HOT_KEYS.contains(k)) {
            // 热点 key：在基准分区之后的连续若干个分区里随机落点
            return (base + random.nextInt(SALT_BUCKETS)) % numPartitions;
        }
        // 普通 key：与默认分区器完全一致，同 key 必定同分区
        return base;
    }

    @Override
    public void configure(Map<String, ?> configs) { }

    @Override
    public void close() { }
}
// 启用方式：
// props.put(ProducerConfig.PARTITIONER_CLASS_CONFIG, HotKeySaltingPartitioner.class.getName());
// 注意：打散后该热点实体的事件会被多个消费者并行处理，
// 下游必须能容忍乱序，或者自己按版本号与时间戳做幂等与覆盖判断。

判定信号常见原因治法代价
某分区 offset 增速是其他分区数倍，且 LAG 长期集中在它身上热点 key：少数实体贡献了大部分流量自定义 Partitioner 对热点 key 追加随机偏移打散该 key 的严格有序性彻底放弃，下游必须能容忍乱序或自己做幂等
部分分区几乎无数据，部分分区满载，分布呈明显阶梯key 的基数太小或取值分布不均，例如用省份、渠道、状态码做 key换一个基数更大、分布更均匀的键，例如用订单号或用户 id 替代省份有序性粒度改变，原先「同省有序」的假设不再成立，需要确认业务是否依赖
分区分布看起来随机但长期不均，且主题里存在大量无 key 消息同一主题混用了有 key 与无 key 消息，两套分区策略互相叠加拆主题，或统一为全部带 key，或确认无需有序后全部不带 key拆主题要改上下游；统一策略需要一次协调上线
倾斜只发生在秒级观察窗口，分钟级累计是均衡的粘性分区器的正常攒批行为不需要处理，改用分钟级指标观察无
分区数据量均衡，但某台 broker 负载明显偏高Leader 分布不均，多个主题的 Leader 恰好堆在同一节点执行优先副本选举，必要时用重分配调整副本落点重分配期间有额外网络开销，必须限流

顺序性的四个层级与代价

层级怎么实现并行度代价与失效条件
全局有序整个主题只建 1 个分区1吞吐被单分区上限锁死且无法横向扩展；该分区所在 broker 故障期间全主题不可写；任何一条慢消息都会阻塞全部后续消息
分区内有序Kafka 默认保证，不需要额外配置等于分区数生产端 max.in.flight.requests.per.connection 大于 1 且允许重试时，重试会导致分区内乱序，必须开启幂等 Producer 才安全
按 key 有序用业务实体 id 做 key，让同实体落同分区等于分区数，同时保住实体级顺序扩分区会立刻改变映射并打断顺序；热点 key 会造成倾斜；消费端如果把同分区消息丢进线程池并发处理，顺序当场失效
完全无序不设 key，交给粘性分区器等于分区数，分布最均匀不能对任何两条消息的先后顺序做假设，下游必须自己处理乱序与幂等
❌
最常见的顺序性幻觉

「我用了 key，所以顺序是保证的」——这句话只在消费端也是串行处理的前提下成立。很多实现会在 poll() 拿到一批消息后丢给线程池加速处理，这一步直接把分区内的顺序抹掉了。如果要并发又要保序，必须在消费端按 key 的哈希把消息路由到固定的工作线程，让同一 key 始终由同一个线程串行处理。另外生产端也要注意：允许重试且 in-flight 请求大于 1 时，失败重试会让后发的消息先落盘，必须靠幂等 Producer 兜住，幂等与事务的边界详见站内 Kafka 深度原理一篇。

副本数、min.insync.replicas 与机架感知

RF 与 min.insync 组合能容忍几台故障仍可写能容忍几台故障不丢数据评价
RF=3, min.insync=2, acks=all11标准生产配置，写可用性与持久性平衡得最好
RF=3, min.insync=3, acks=all02任何一台节点重启都会让写入直接失败，包括正常滚动升级，几乎不可运维
RF=3, min.insync=1, acks=all20acks=all 形同虚设，只要 Leader 确认就返回成功，Leader 挂掉即丢数据
RF=2, min.insync=2, acks=all01典型误配，看起来省了一份磁盘，实际挂一台就完全不可写
RF=2, min.insync=110只适合可重建的日志类数据，不要放业务事件
RF=100仅限本地开发；磁盘损坏就是永久丢失

机架感知靠 broker.rack：给每台 broker 标注机架或可用区标识，Kafka 在分配副本时会尽量让同一分区的副本分散在不同机架上，从而让整机架掉电只损失一个副本。注意两点：标注必须在建主题之前完成，已有主题的副本分布不会自动调整，需要用重分配工具手动改；跨可用区的副本同步会产生跨区流量，云上这部分费用常常被漏算，而且 RTT 增加会让 acks=all 的写入延迟上升，必要时配合 replica.selector.class 让消费者就近读副本。

Topic 级配置与 compact 语义

配置项默认值什么时候要覆盖覆盖错了会怎样
retention.ms7 天需要更长回溯窗口，或数据敏感需要尽快清理设得短于「消费者最长停机时间加故障响应时间」，重启后位点越界，直接丢数据
retention.bytes不限单分区要设容量上限防止写满磁盘与 retention.ms 是或的关系，任一满足即删，设小了会导致数据提前消失
cleanup.policydelete主题语义是「状态快照」而非「事件流」时改成 compact对事件流用 compact 会让同 key 的历史事件被吃掉；对无 key 消息用 compact 则完全无效
min.insync.replicas1生产环境全部覆盖为 2留 1 会让 acks=all 失去意义；设成等于 RF 会让滚动重启变成不可写
max.message.bytes约 1MB确实有大消息时上调，但优先考虑把大对象存对象存储只传引用只改 broker 没改 topic 或客户端，会在另一环节被拒绝
segment.bytes1GB需要更细的删除与压实粒度时调小调太小会让段文件数量暴增，句柄和 mmap 压力上升
delete.retention.ms24 小时compact 主题上，慢速消费者需要更长时间才能看到墓碑设太短，慢消费者错过删除事件，下游本地状态留下永久幽灵数据
stateDiagram-v2 [*] --> Latest Latest: 该 key 的当前最新值 压实后一定保留 Latest --> Obsolete: 同一 key 写入了更新的值 Obsolete: 旧版本仍在日志里等待清理 Obsolete --> Removed: 清理线程压实所在段 Removed --> [*] Latest --> Tombstone: 写入 value 为空的墓碑消息表示删除 Tombstone: 下游据此删除自己的本地状态 Tombstone --> Purged: 超过 delete.retention.ms 后彻底移除 Purged --> [*] note right of Tombstone 墓碑必须保留足够久 否则慢速消费者永远看不到删除事件 下游本地状态会留下幽灵数据 end note

compact 与 delete 的语义差异可以这样记：delete 回答「最近这段时间发生了什么」，compact 回答「现在的状态是什么」。compact 主题的核心价值是可重建：一个新下游从头读完整个主题，就得到了全量状态快照，这也是 CDC 最终态、配置下发、维表同步的标准做法。三个容易踩的点：compact 只保证每个 key 的最新值必定保留，不保证旧版本立刻消失（活跃段不参与压实，所以短期内仍会读到多个版本）；无 key 消息在 compact 主题里是无意义的，无法被去重；两种策略可以同时写成 compact,delete，语义是先按 key 压实再按时间清理，适合状态量大但历史 key 会彻底废弃的场景。

命名治理与分区重分配

规范写法示例为什么
分段式命名，域加实体加事件类型trade.order.created能从名字判断归属团队与数据语义，便于做 ACL 前缀授权与配额
环境不要混在同一集群，也不要靠名字区分集群隔离而非 orders-prod靠命名隔离时，一次配置失误就会让测试流量写进生产主题
分隔符统一，全小写统一用点号，不要点号与下划线混用Kafka 的指标名会把点号与下划线做等价处理，混用可能造成监控指标冲突
版本进名字而不是靠兼容硬扛trade.order.created.v2不兼容的结构变更用新主题双写再切换，比强行兼容旧消费者安全
禁止自动创建auto.create.topics.enable=false拼错名字会静默建出一个默认配置的新主题，分区数和副本数都不对，且没人知道
主题元信息登记负责人、保留期、峰值量级、下游清单没有登记时，没人敢删任何主题，集群里会长期堆积僵尸主题占用句柄与分区配额
sequenceDiagram autonumber participant OP as 运维 participant CT as Controller participant NEW as 新副本所在 broker participant OLD as 原副本所在 broker participant CLI as 生产与消费客户端 OP->>CT: 提交 reassignment 方案并同时设置限流 CT->>NEW: 把新副本加入该分区的副本集合 NEW->>OLD: 从当前 Leader 全量拉取历史数据 Note over NEW,OLD: 这是整个过程唯一的重负载
不限流会占满机间带宽
正常复制随之滞后 Isr 被打散 NEW-->>CT: 追上水位后进入 Isr CT->>OLD: 从副本集合中移除旧副本 CT-->>CLI: 推送更新后的元数据 CLI->>NEW: 后续请求改连新的 Leader OP->>CT: verify 通过后自动清除限流配置 
# 1. 生成方案，只生成不执行；Current assignment 必须先存档用于回滚
bin/kafka-reassign-partitions.sh --bootstrap-server kafka-1:9092 \
  --topics-to-move-json-file topics.json \
  --broker-list "1,2,3,4,5,6" --generate
# topics.json 内容形如 {"topics":[{"topic":"orders"}],"version":1}
# 把 Proposed assignment 存成 reassign.json，人工检查副本落点是否跨机架

# 2. 执行时必须带限流，单位是字节每秒
#    不限流会让迁移流量把机间带宽打满，正常生产消费一起被拖死，
#    还会因为复制滞后把 Isr 打散，配合 min.insync.replicas=2 变成不可写
bin/kafka-reassign-partitions.sh --bootstrap-server kafka-1:9092 \
  --reassignment-json-file reassign.json --execute \
  --throttle 50000000

# 3. 反复 verify 直到全部完成，未完成前不要手动撤限流
bin/kafka-reassign-partitions.sh --bootstrap-server kafka-1:9092 \
  --reassignment-json-file reassign.json --verify
# 全部分区显示 completed successfully 后，verify 会自动移除限流配置
# 中途放弃则要手动清理，否则限流配置会长期残留并拖慢日后的正常复制

# 4. 迁移完成后把 Leader 均衡回优先副本
bin/kafka-leader-election.sh --bootstrap-server kafka-1:9092 \
  --election-type PREFERRED --all-topic-partitions
❌
分区设计最容易踩的坑
  • 上线前随便填了分区数。它只能增不能减，填小了只能靠扩分区（打断顺序），填大了只能新建主题迁移。
  • 在业务高峰或有积压时扩分区。同一实体的新旧消息被并行处理，顺序性当场失效，而且这类乱序很难在事后发现。
  • 以为加分区就能提升消费速度。已有积压不会被重新分配到新分区，新分区只接新数据，老分区的积压还得靠老消费者慢慢啃。
  • 用低基数字段做 key。省份、渠道、状态码这类字段做 key，必然把数据压到少数几个分区上。
  • 把粘性分区器的攒批波动误判成倾斜。秒级看单分区速率一定不均，要看分钟级累计。
  • 只看总 LAG 不看分区分布。热点分区堆了十六万而其他分区为零，与十六个分区各堆一万，处置方式完全不同。
  • RF=2 配 min.insync=2。看着省了一份磁盘，实际任何一台节点重启就完全不可写。
  • min.insync 设成等于 RF。连正常滚动升级都做不了，每次重启都是一次写入中断。
  • 标了 broker.rack 就以为已有主题会自动跨机架。只对新建主题生效，存量主题必须手动重分配。
  • 对事件流误用 compact。同一 key 的历史事件会被吃掉，等于静默丢数据；对无 key 消息用 compact 则完全无效。
  • compact 主题的 delete.retention.ms 设得太短。慢消费者错过墓碑消息，下游本地状态永远留着已删除的数据。
  • 重分配不加 throttle。迁移流量打满机间带宽，正常复制滞后、Isr 被打散，直接演变成写入不可用。
  • 重分配后不做优先副本选举。Leader 全堆在少数节点上，集群负载长期倾斜。
  • 消费端把同分区消息丢进线程池。生产端辛苦维持的按 key 有序，在这一行代码里全部作废。
