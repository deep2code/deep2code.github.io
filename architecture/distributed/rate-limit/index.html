限流的分布式实现与多维配额

🏷️ 限流

固定窗口、滑动窗口、令牌桶、漏桶四种算法的原理与对照，以及熔断状态机、舱壁隔离、用容量反推阈值的方法，站内熔断与限流篇已经讲透，本篇不重复。这里只讲算法之外真正难落地的部分：集群里的阈值怎么才准、Redis 脚本怎么写才原子、Redis 挂了怎么办、多个维度怎么一次判完、以及限流之外还有什么手段。

单机限流在集群下会漂移

最常见的实现是每个实例用本地令牌桶限流。它在单实例时完全正确，但一旦扩容成 N 个实例，实际总阈值就变成 N × 单机阈值，而这个 N 会随扩缩容、滚动发布、实例故障不停变化——也就是说你真正的限流阈值是一个你并不掌握的数字。

flowchart TB subgraph P1["问题一：阈值随实例数漂移"] A1["设计目标：下游总容量 1000 QPS"] --> A2["10 个实例，每个配 100"] A2 --> A3["扩到 20 个实例（未改配置）"] A3 --> A4["实际放行 2000 QPS，下游被打穿"] end subgraph P2["问题二：流量不均导致提前触发"] B1["总流量 800 QPS，未达总阈值"] --> B2["长连接或哈希导致分布不均"] B2 --> B3["某实例承担 150 QPS"] B3 --> B4["该实例先限流，用户随机报错"] end subgraph P3["问题三：滚动发布期间总量翻倍"] C1["新旧实例并存"] --> C2["瞬时实例数超过稳态"] C2 --> C3["总阈值短时上浮，正好撞上发布期"] end
集群限流方案准确性每请求开销可用性依赖适用场景
单机均分（总阈值除以实例数）低：流量不均时提前触发，实例数变化时总阈值漂移0，纯内存无外部依赖，最高阈值本身很宽松、只做粗粒度兜底
集中式计数（Redis 加 Lua）高：全局视角，误差只来自客户端时钟与网络抖动一次往返，同机房 0.3 到 1 毫秒强依赖 Redis，必须设计降级需要准确配额的对外 API、付费套餐、按用户配额
本地预扣加定期同步中：短窗口内可能小幅超发，长期准确摊薄后接近 0弱依赖，Redis 故障时仍能按上次配额跑超高 QPS 场景，能接受几个百分点误差
💡
先问一句：这个限流到底在保护谁

保护本实例不被打垮（线程池、内存、CPU）的限流应该做在单机，因为约束本来就是每实例的；保护共享下游（数据库、第三方接口）或者分配用户配额的限流必须集中式，因为约束是全局的。把这两类需求混在一个限流器里配置，是阈值永远配不对的根源。

Redis 加 Lua 的原子实现

为什么必须用 Lua：限流的本质是「读当前状态、判断、写回新状态」三步。用多条 Redis 命令实现时，两个并发请求可能都读到剩余 1 个令牌、都判定放行、都扣成 0，实际放过了 2 个。单条命令原子，但多条命令之间不原子。用 WATCH 加事务虽然正确，但高并发下冲突重试率极高。Lua 脚本整体执行不被打断，且只要一次网络往返。

-- 令牌桶限流（KEYS[1] = 桶的键）
-- ARGV[1] 桶容量（允许的突发量）
-- ARGV[2] 每秒填充速率
-- ARGV[3] 当前时间戳（毫秒，必须由客户端传入，脚本内绝不能读时钟）
-- ARGV[4] 本次请求需要的令牌数（批量请求可以大于 1）
-- 返回 {是否放行, 剩余令牌数, 建议等待毫秒}
local capacity   = tonumber(ARGV[1])
local rate       = tonumber(ARGV[2])
local now        = tonumber(ARGV[3])
local requested  = tonumber(ARGV[4])

local bucket = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local tokens = tonumber(bucket[1])
local ts     = tonumber(bucket[2])

if tokens == nil then          -- 首次访问：桶是满的
  tokens = capacity
  ts = now
end

-- 按经过的时间补充令牌；max(0, ...) 防止客户端时钟回拨算出负值
local elapsed = math.max(0, now - ts) / 1000.0
tokens = math.min(capacity, tokens + elapsed * rate)

local allowed = 0
local waitMs = 0
if tokens >= requested then
  tokens = tokens - requested
  allowed = 1
else
  -- 告诉调用方还要等多久才够，用于生成 Retry-After
  waitMs = math.ceil((requested - tokens) / rate * 1000)
end

redis.call('HMSET', KEYS[1], 'tokens', tokens, 'ts', now)
-- TTL 取「填满整桶所需时间」的两倍，保证空闲键能自动回收，又不会误删活跃桶
redis.call('PEXPIRE', KEYS[1], math.ceil(capacity / rate * 2000))

return {allowed, math.floor(tokens), waitMs}

-- 滑动窗口限流（ZSet 版，KEYS[1] = 窗口键）
-- ARGV[1] 窗口长度（毫秒）  ARGV[2] 窗口内允许的最大请求数
-- ARGV[3] 当前时间戳（毫秒，客户端传入）  ARGV[4] 本次请求的唯一 ID
-- 精度高于固定窗口，不会出现临界点双倍突刺；代价是内存与窗口内请求数成正比
local window = tonumber(ARGV[1])
local limit  = tonumber(ARGV[2])
local now    = tonumber(ARGV[3])
local reqId  = ARGV[4]

-- 1) 先清理窗口外的旧成员，这是 ZSet 方案能成立的关键一步
redis.call('ZREMRANGEBYSCORE', KEYS[1], 0, now - window)

local count = redis.call('ZCARD', KEYS[1])
if count >= limit then
  -- 取窗口内最早一条的时间，算出它何时滑出窗口，作为 Retry-After 依据
  local earliest = redis.call('ZRANGE', KEYS[1], 0, 0, 'WITHSCORES')
  local waitMs = window - (now - tonumber(earliest[2]))
  return {0, 0, math.max(1, waitMs)}
end

-- 2) 成员必须唯一，否则同一毫秒的多个请求会互相覆盖，导致少计数
redis.call('ZADD', KEYS[1], now, reqId)
redis.call('PEXPIRE', KEYS[1], window + 1000)
return {1, limit - count - 1, 0}
实现细节为什么必须这样写错的后果
时间戳由客户端传入脚本复制到从节点时重放会取到不同时间；集群里各节点时钟也不一致主从数据不一致；主从切换后时间倒退，令牌数计算异常
用 math.max(0, now - ts) 兜住时间回拨客户端时钟可能被 NTP 校正回调算出负的经过时间，令牌数被减少甚至变负，限流突然全拒
每次都重设 TTL没有 TTL 的键会永久驻留用户维度的键数量等于历史用户总数，内存无上限增长
ZSet 成员用唯一请求 IDZSet 成员唯一，同分值同成员会被覆盖同一毫秒的并发请求只计一次，实际放行量远超阈值
返回建议等待时长调用方需要它生成 Retry-After调用方只能盲目重试，形成重试风暴
同一限流单元的键落在同一槽Redis Cluster 的脚本不能跨槽操作多个键多维合并判定时报 CROSSSLOT 错误

Redis 挂了：fail-open 还是 fail-close

集中式限流把 Redis 变成了主链路依赖，所以必须先回答：限流组件自己不可用时，请求放行还是拒绝。这个问题没有统一答案，取决于限流在保护什么。

sequenceDiagram autonumber participant A as 应用实例 participant L as 本地兜底限流器 participant R as Redis 限流 participant D as 下游（数据库 / 第三方） A->>R: 执行限流脚本，超时 50 毫秒 alt Redis 正常 R-->>A: 返回放行与剩余配额 A->>D: 转发请求 else Redis 超时或不可达 R--xA: 超时 A->>A: 熔断限流器，进入降级模式 A->>L: 改用本地阈值（总阈值除以实例数，再打七折） alt 本地判定放行 A->>D: 转发请求 else 本地判定超限 A-->>A: 直接返回 429 end A->>A: 上报降级指标并告警 end Note over A,R: 降级期间定期探测 Redis，恢复后切回集中式
限流目的Redis 故障时理由
保护脆弱下游（单点数据库、第三方接口）fail-close 或降级到保守本地阈值放行会把一次缓存故障放大成全站故障，下游被打穿的恢复时间远长于限流误拒
分配用户配额、防刷fail-open 并告警业务本身承压能力足够，不能让限流组件成为可用性短板
付费套餐配额（涉及计费）降级到本地计数并事后补对既不能超发太多，也不能直接拒绝付费用户
秒杀、强约束场景fail-close超发的业务后果（超卖）无法通过重试弥补
// 集中式限流客户端：超时要短、必须有本地兜底、降级要可观测
type Limiter struct {
    rdb        *redis.Client
    script     *redis.Script  // 令牌桶脚本，用 EVALSHA 复用
    local      *rate.Limiter  // 本地兜底：总阈值 / 实例数 再打七折
    failOpen   bool           // 由限流目的决定，见上表
    degraded   atomic.Bool    // 降级标志，避免故障期每次都去打超时
}

// 超时必须远小于接口 SLA。50 毫秒是常用值：Redis 同机房正常在 1 毫秒内，
// 超过 50 毫秒说明已经异常，继续等只是把故障传导给调用方。
const redisTimeout = 50 * time.Millisecond

func (l *Limiter) Allow(ctx context.Context, key string, cost int) (bool, time.Duration) {
    if l.degraded.Load() {
        return l.fallback(cost)
    }
    cctx, cancel := context.WithTimeout(ctx, redisTimeout)
    defer cancel()

    // 时间戳由客户端传入：脚本里读时钟在主从复制下会导致不一致
    now := time.Now().UnixMilli()
    res, err := l.script.Run(cctx, l.rdb, []string{key},
        l.capacity, l.rate, now, cost).Slice()
    if err != nil {
        metrics.LimiterDegraded.Inc()          // 降级必须可观测，否则悄无声息地失效
        l.enterDegradedFor(5 * time.Second)    // 短暂熔断，定期探测恢复
        return l.fallback(cost)
    }
    allowed := res[0].(int64) == 1
    waitMs := res[2].(int64)
    return allowed, time.Duration(waitMs) * time.Millisecond
}

func (l *Limiter) fallback(cost int) (bool, time.Duration) {
    if l.failOpen {
        return true, 0
    }
    // 本地兜底：精度下降但方向正确。这段代码必须定期演练，
    // 否则真故障时才发现本地限流器的参数从来没配过。
    if l.local.AllowN(time.Now(), cost) {
        return true, 0
    }
    return false, time.Second
}

多维限流：生产环境的必需品

只按接口限流在生产上是不够的。一个大客户就能打满全局配额，一个异常脚本就能耗尽某接口的额度。实际需要同时按多个维度判定，任一维度超限即拒绝。

维度典型阈值来源拦的是什么键的设计
全局（接口级）压测得出的系统容量整体过载rl:api:{apiId}
应用 / 租户合同或套餐约定单一客户挤占公共资源rl:app:{appId}:{apiId}
用户正常用户行为上限的若干倍账号被盗刷、脚本批量操作rl:user:{userId}:{apiId}
IP经验值，注意 NAT 出口共享匿名爬虫与撞库rl:ip:{ip}:{apiId}
资源粒度热点资源的承载能力单个热点商品或文档被打爆rl:res:{resourceId}

维度一多就出现新问题：每请求要打好几次 Redis。五个维度就是五次往返，同机房也要 2 到 5 毫秒，在网关这种每请求都过的位置是不能接受的。解决办法是把所有维度合并成一次脚本调用：

-- 多维限流合并判定：一次往返判完所有维度
-- KEYS 是各维度的键（必须带相同 hash tag 才能在 Cluster 下同槽）
-- ARGV 布局：[1] 当前时间戳毫秒，之后每 3 个一组对应一个 KEY：容量、速率、消耗
-- 返回 {是否放行, 触发限流的维度下标, 建议等待毫秒}
local now = tonumber(ARGV[1])

-- 第一遍：只读判断，任一维度不足就整体拒绝。
-- 关键：绝不能边判边扣，否则前几个维度扣了、后一个维度拒了，
-- 已扣的令牌白白浪费，高并发下会造成远低于阈值就开始拒绝。
local snapshot = {}
for i = 1, #KEYS do
  local capacity = tonumber(ARGV[(i-1)*3 + 2])
  local rate     = tonumber(ARGV[(i-1)*3 + 3])
  local cost     = tonumber(ARGV[(i-1)*3 + 4])
  local b = redis.call('HMGET', KEYS[i], 'tokens', 'ts')
  local tokens = tonumber(b[1]) or capacity
  local ts     = tonumber(b[2]) or now
  tokens = math.min(capacity, tokens + math.max(0, now - ts) / 1000.0 * rate)
  if tokens < cost then
    local waitMs = math.ceil((cost - tokens) / rate * 1000)
    return {0, i, waitMs}   -- 返回下标，便于监控知道是哪个维度在拦
  end
  snapshot[i] = {tokens - cost, capacity, rate}
end

-- 第二遍：全部通过才真正扣减
for i = 1, #KEYS do
  redis.call('HMSET', KEYS[i], 'tokens', snapshot[i][1], 'ts', now)
  redis.call('PEXPIRE', KEYS[i], math.ceil(snapshot[i][2] / snapshot[i][3] * 2000))
end
return {1, 0, 0}
⚠️
边判边扣是多维限流最隐蔽的 bug

顺序对每个维度执行「判断并扣减」，一旦后面的维度拒绝，前面已扣的令牌不会归还。表现为实际通过率明显低于配置阈值，而且维度越多偏差越大。必须像上面这样先全量判定再统一扣减，或者在拒绝时对已扣维度做回补。

限流响应：429 加 Retry-After 加配额头

被限流的响应写错会直接引发重试风暴，或者让调用方的熔断器把你整个服务判死。正确的响应是一组约定：

HTTP/1.1 429 Too Many Requests
Retry-After: 2
X-RateLimit-Limit: 1000
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1790000000
Content-Type: application/json

{"code":"RATE_LIMITED","message":"请求过于频繁，请 2 秒后重试","dimension":"app"}
做法调用方与运维的反应结论
429 加 Retry-After 与配额头客户端按提示退避，SDK 能自动平滑速率，网关能统计限流率正确
429 但不带 Retry-After客户端立即重试，重试量与被拒量相同，形成持续压力不完整，等于没限住
503调用方熔断器判定服务故障，切断全部流量；监控告警误报为宕机错误：限流是拒绝超额请求，服务本身健康
200 加业务错误码网关与监控无法区分正常响应与被限流，限流率指标统计不出来错误：可观测性直接丢失
直接断开连接客户端看到网络错误，会按网络故障策略激进重试错误：最坏的一种

还要区分限流与过载两种语义：限流是「你超出了分配给你的配额」，属于调用方的问题，返回 429；过载是「系统当前处理不过来」，属于服务端的问题，返回 503 并带 Retry-After。两者的处置动作完全不同——前者调用方要降速，后者需要扩容或降级。具体的错误码与响应体规范可以参考站内 API 设计相关内容。

维度直接拒绝排队等待
资源占用请求立刻释放连接与线程等待期间持续占用连接、线程或协程，以及请求上下文内存

用户体验看到明确的「稍后重试」短队列体验更好；长队列变成「转圈半分钟后超时」
故障放大不放大会放大：队列里的请求可能早已被客户端超时放弃，处理它们纯属浪费
必备配置阈值与 Retry-After队列深度上限 + 单请求排队超时，两者缺一不可

队列深度的估算方式很简单：深度 = 下游每秒处理能力 × 可接受等待秒数。下游能跑 500 QPS、可接受等待 1 秒，队列就只能放 500 个，多了立刻拒。另外出队时要先检查请求是否已经过期（比较入队时间与客户端超时），过期的直接丢弃，否则系统会花全部算力处理没人等结果的请求——这是雪崩里最典型的无效功。

准入控制与自适应限流

固定阈值最大的问题是它一定会过时：代码变更、依赖升级、机器规格调整、缓存命中率变化都会改变真实容量，而阈值往往几个月无人复核。自适应方案不设固定数值，而是根据实时信号动态调整并发上限。

自适应不能替代配额

自适应限流保护的是本服务不被压垮，它不知道也不关心这些流量属于哪个客户。按用户、按应用的配额分配必须单独做，两者是叠加关系：先用配额保证公平，再用自适应兜住整体过载。只上自适应的系统，会在一个大客户突增时对所有人一起降速。

热点与公平性

只有全局阈值时，一个大客户可以合法地占满全部配额，其余客户全部被拒——这在限流器看来是完全正常的。解决手段有两类：

手段做法优点代价
分层配额全局阈值之下，为每个租户设保底配额与上限，空闲配额允许借用规则清晰，容易向客户解释与计费挂钩配置项多，新客户接入要分配额度
加权公平队列按租户分队列轮转出队，权重决定份额自动适应客户数变化，无需逐个配置实现复杂，需要维护队列状态，网关内存开销上升
热点资源单独限流对热点 key（爆款商品、热门文档）加独立维度把热点影响限制在局部需要热点识别机制，通常靠滑动窗口统计 topN
优先级准入过载时优先保障高优先级请求（付费用户、核心链路）过载时仍能保住最重要的流量需要全链路传递优先级标识

阈值怎么定，以及必须定期复核

阈值的来源只能是压测：阶梯加压，观察延迟随并发上升的曲线，找到延迟开始明显拐头的那个点，取其安全余量作为阈值（具体方法与容量反推见熔断与限流篇）。这里要强调的是复核：

触发复核的事件为什么影响容量复核动作
机器规格或副本数变更单机容量与总容量都变了重新压测单机容量，按新实例数换算总阈值
依赖升级或 SQL 变更单请求成本变化，容量可能腰斩对受影响接口重新压测
缓存命中率下降命中率从 95% 掉到 80%，数据库压力翻数倍按最坏命中率估算容量，调低阈值
业务量自然增长阈值相对流量变紧，误拒率上升看限流率指标趋势，提前扩容与调阈值
连续三个月未复核累积漂移作为固定巡检项纳入季度稳定性评审

反模式清单

反模式为什么出现实际后果正确做法
集群里只做单机限流本地限流器实现简单、零依赖实际总阈值等于单机阈值乘实例数，扩容后下游被打穿保护共享下游的限流必须集中式
用多条 Redis 命令做限流不熟悉 Lua，或觉得脚本难维护读判断写之间被插入，并发下放行量超出阈值用 Lua 脚本保证原子，一次往返完成
Lua 脚本里读时钟觉得由服务端取时间更准主从复制下取到不同时间，主从数据不一致；切换后时间倒退时间戳由客户端传入并做回拨保护
限流返回 503 且不带 Retry-After随手用了通用错误调用方熔断整个服务，且立刻重试形成风暴返回 429 加 Retry-After 与配额头
所有接口共用一个阈值配置省事重接口拖垮系统，轻接口被无谓限制按接口成本分组设阈值，核心与非核心分开
排队没有上限与超时只想着别拒绝用户连接与线程被耗尽，延迟无上限增长，等来的结果没人要了队列深度按可等待秒数乘处理能力，出队先检查是否过期
阈值定了就再不复核没人负责这件事容量早已变化，阈值要么形同虚设要么误拒大量正常流量把复核绑定到变更事件与季度巡检
多维限流边判边扣顺序实现最直观后置维度拒绝时前面已扣的令牌浪费，通过率显著低于阈值先全量判定再统一扣减
限流键没有 TTL只关注判定逻辑用户维度的键数量等于历史用户数，Redis 内存无上限增长每次判定都重设 TTL
❌
最容易踩的坑
  • 扩容后忘了改单机阈值：实例从 10 个变 20 个，总放行量直接翻倍，限流形同虚设，而配置文件看起来毫无问题。
  • 用多条 Redis 命令实现令牌桶：压测时偶尔超出阈值几个百分点，以为是统计误差，实际是读写不原子。
  • Lua 里调用时间函数：单机测试完全正常，上了主从或 Cluster 后出现限流数据不一致，且主从切换后令牌数异常。
  • ZSet 滑动窗口用时间戳当成员：同一毫秒的并发请求成员相同被覆盖，计数偏小，实际放行量远超阈值。
  • 限流键不设过期：按 userId 建键，几个月后 Redis 里堆了上千万个僵尸键，内存告警却找不到大 key。
  • Redis 调用不设超时或超时过长：Redis 抖动时每个请求卡 1 秒，限流器本身成了故障源。
  • 写了降级逻辑但从没演练：真故障时才发现本地兜底限流器的阈值是默认值 0，所有请求被拒。
  • 被限流返回 503：上游熔断器把整个服务标记为故障并切流，一个局部限流演变成全链路不可用。
  • 不带 Retry-After：客户端立即重试，被拒的流量原地翻几倍，Redis 的限流调用量也随之翻倍。
  • 排队队列没有上限：突发时队列涨到几万，内存与连接耗尽，且处理的全是客户端已超时放弃的请求。
  • 只有全局阈值没有租户维度：一个大客户的批量任务合法占满配额，其他所有客户被拒，客服全量爆单。
  • 阈值拍脑袋定：没压测就写个 1000，高峰期正常流量被误拒，排查半天发现阈值本来就比实际容量低一个量级。
  • 限流没有指标：不上报限流率、触发维度、降级次数，出问题时无法判断是限流误拒还是真故障。
