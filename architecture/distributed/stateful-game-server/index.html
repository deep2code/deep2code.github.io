ET 框架的服务端架构与分布式设计

🏷️ 游戏开发

ET 是开源的 C# 双端游戏框架，客户端跑在 Unity 里，服务端跑在 .NET 上，两端共用同一套实体与消息定义。但真正值得讨论的不是「它有哪些 API」，而是它代表的那一类架构：状态在内存、逻辑单线程、进程间靠消息寻址。这篇先给这类服务的最小落地形态——会话怎么恢复、邮箱怎么收、什么时候落库，都是可以直接照着搭的；再讲这套架构的机制与它与无状态 Web 服务的镜像关系。

① 用法 · 最小落地形态：九项清单与参数怎么取

下面九项是有状态长连接服务的地基。它们互相咬合：少了消息序号，会话恢复就只能做半套；少了邮箱上限，单线程串行的好处会被内存问题吃掉。

要做什么怎么做漏了会怎样
1 把「连接」和「会话」分开断线后会话进入「等待重连」，实体仍留在内存，期间的推送进待发队列进隧道断网十秒回来，副本进度全没了
2 推送带消息序号客户端上报已收到的最后序号，服务端据此补发缺失的推送重连之后丢推送，客户端与服务端状态长期不一致
3 上行操作带幂等键服务端据此识别「这条我已经执行过了」重连时客户端重发，道具被扣两次
4 邮箱有界且溢出策略显式有界队列 + 明确的丢弃或拒绝策略 + 溢出告警热点实体投递快于处理，内存无声上涨直到进程被杀
5 逻辑线程里零阻塞一路 await 到底，禁止同步等待结果、同步读写文件与数据库、线程睡眠一次同步等待就让整个世界的所有玩家一起无响应
6 落库按数据分级资产类同步落库并记流水号；进度类标脏批量落；可推导的运行态完全不落全实时落库打爆存储；全定时落库丢的是真金白银
7 下线与切图强制刷脏会话状态机的离线出口里先刷一次脏数据，再释放实体并从位置服务注销丢掉最后一个定时周期内的全部变更
8 寻址缓存有失效机制迁移完成时主动通知失效，同时给缓存加短过期兜底玩家切图后偶发操作无响应，容易被误判成网络抖动
9 状态重建路径定期演练把崩溃恢复与滚动重启纳入固定演练项它是发布与故障恢复的唯一依赖，平时没人走，真出事才发现它本身是坏的

这些机制的参数不存在通用默认值，按下表的依据推出来：

参数作用怎么取什么时候需要改
等待重连超时会话在服务端存活多久按玩法定：副本与战斗类要覆盖常见的短时断网，挂机与经营类可更长太短体验差；太长会积压僵尸会话，占着内存和实体
邮箱容量与溢出策略背压边界单实体峰值消息速率乘以可容忍的积压秒数；溢出策略必须显式选择出现热点实体或加了高频推送之后

① 用法 · 两段可直接用的代码：有界邮箱与标脏落库

第一段是一个逻辑世界的处理循环。「不加锁」的前提就是这一个执行流，所以它换来的约束是里面绝不能出现同步阻塞：

// 一个逻辑世界的串行处理循环：所有业务代码都在这一个执行流里跑，因此内部完全不需要加锁
// 换来的约束是：这里绝对不能出现同步阻塞调用（同步等待结果、同步读写文件与数据库、Thread.Sleep）
private readonly Channel<Msg> _mailbox =
    Channel.CreateBounded<Msg>(new BoundedChannelOptions(4096)
    {
        FullMode = BoundedChannelFullMode.DropWrite   // 有界且明确溢出策略，避免无背压把内存吃光
    });

public async Task RunLoop(CancellationToken ct)
{
    while (await _mailbox.Reader.WaitToReadAsync(ct))
    {
        while (_mailbox.Reader.TryRead(out var msg))
        {
            var sw = Stopwatch.StartNew();
            try
            {
                await Dispatch(msg);              // 单条消息处理耗时过长会直接拖慢整个世界
            }
            catch (Exception e)
            {
                // 一条消息处理失败不能让整个世界停掉，但必须落日志并带上消息类型与实体 ID
                Log.Error($"dispatch failed: {msg.GetType().Name} id={msg.EntityId} {e}");
            }
            if (sw.ElapsedMilliseconds > 50) Log.Warn($"slow handler: {msg.GetType().Name} {sw.ElapsedMilliseconds}ms");
        }
    }
}

第二段是标脏批量落库。注意先摘脏标记再发起写入、失败要回滚脏标记这个顺序，顺序写反就是静默丢数据：

// 标脏加定时批量落库：丢数据窗口 = 定时周期，写放大被合并次数摊薄
// 注意三件事：下线必须强制刷、崩溃前来不及刷要能接受、幂等键必须在业务侧生成
public sealed class DirtySaver
{
    private readonly HashSet<long> _dirty = new HashSet<long>();   // 只存 ID，不存对象引用
    private readonly int _batch = 200;

    public void MarkDirty(long unitId) => _dirty.Add(unitId);       // 同一周期内改一万次也只落一次

    // 由逻辑世界的定时器调用，仍然跑在逻辑线程上，因此这里不需要加锁
    public async ETTask FlushAsync()
    {
        if (_dirty.Count == 0) return;
        var ids = new long[System.Math.Min(_batch, _dirty.Count)];
        int n = 0;
        foreach (var id in _dirty) { ids[n++] = id; if (n == ids.Length) break; }

        // 先把这批从集合里摘掉，再发起写入；写失败要重新标脏，否则这批变更会被静默丢弃
        for (int i = 0; i < n; i++) _dirty.Remove(ids[i]);
        try
        {
            await SaveBatchAsync(ids);
        }
        catch
        {
            for (int i = 0; i < n; i++) _dirty.Add(ids[i]);   // 失败回滚脏标记，下个周期重试
            throw;
        }
    }
}

资产类数据不能走这段代码：它必须在返回成功前确认已持久化，并带幂等流水号。哪类数据走哪条路径，见原理层的落库分级图。

② 原理 · 有状态游戏服务和普通 Web 服务的分界

搞清这一节，能解释为什么后端那套「加实例就能扛」的直觉在这里全部失效。这套架构和后端熟悉的无状态 Web 服务几乎是镜像关系。

维度无状态 Web 服务有状态游戏服务由此产生的约束
权威数据位置数据库与缓存进程内存进程崩溃会丢掉最后一次落库之后的全部变更
请求路由任意实例都能处理必须路由到持有该实体的进程需要自己的寻址层，负载均衡解决不了这件事
扩容方式加实例即分担存量流量加实例只能承接新的世界或新的分区单个热点地图的负载无法靠加机器摊薄
连接模型短连接，请求响应长连接，服务端主动推送要自己管会话、心跳、重连与消息序号
并发控制数据库事务与分布式锁单线程串行，逻辑内不加锁逻辑线程里任何阻塞调用都会拖垮整个世界
发布方式滚动发布，实例随意替换需要踢下线或等玩家自然退出发布窗口与状态可重建能力是架构要求
数据库角色同步的事实来源异步的持久化后端读走内存，写是批量与延迟的
💡
为什么不做成无状态的

因为一次战斗结算要同时读写施法者、目标、地图、队伍、背包，把这些状态放进 Redis 再逐个加锁，延迟和复杂度都会失控，而游戏逻辑的每一帧都在做这种宽面的读写。有状态不是偷懒，是这类负载的合理解法。代价就是所有分布式问题都要自己解一遍。

② 原理 · 进程、Scene 与线程模型

搞清这一节，能判断一次调用该写成直接方法调用还是必须走消息——这个判断错了，要么破坏串行前提，要么白白把同进程调用变成异步。ET 的部署单元是进程，进程内部用 Scene 划分逻辑世界。一个 Scene 可以是一张地图、一个匹配池、一个公会所在的域；它是状态的归属边界，也是消息处理的串行边界。这个划分决定了两件事：哪些对象可以直接互相调用（同一 Scene 内），以及哪些必须走消息（跨 Scene、跨进程）。

要提醒的是，ET 不同大版本的线程模型差异很大：早期以单线程为主，后续版本引入了把逻辑世界绑定到独立执行单元的做法。所以「它是单线程还是多线程」没有统一答案，以你所用版本的源码为准。不变的规律是：一个世界内部串行，世界之间靠消息，不共享可变状态。

存储代理批量读写、屏蔽存储细节否按分片加落库积压，内存态仍可服务但丢数据窗口变大

② 原理 · ECS：组件即状态，System 即行为

搞清这一节，能解释一类难查的崩溃：定时器还在回调一个已经被销毁的对象。ET 用实体加组件的组织方式，但它和 Unity 的 DOTS 那种为内存布局与并行设计的 ECS 不是一回事。服务端这边主要解决状态的组合与生命周期：实体是树上的节点，功能以组件形式挂上去，逻辑写在对应的处理器里。好处很实际——背包、buff、任务可以独立挂载与卸载，不必往一个巨型玩家类里继续加字段。

关键点在于组件的生命周期必须显式。组件被添加、被反序列化载入、被销毁这几个时机要各自有钩子，因为这三种情况的初始化内容不同：新建时要设默认值，载入时要重建那些不落库的运行期字段，销毁时要把定时器、事件订阅、未完成的协程一并收干净。

时机应该做什么漏了会怎样
组件新建设置默认值、注册到索引字段为零值，业务表现为数据异常但不报错
从存储载入后重建不落库的运行期字段、恢复定时器玩家上线后 buff 不走时间、任务不推进
组件销毁取消定时器、反注册事件、标记协程失效定时器仍在回调已销毁的对象，表现为偶发空引用崩溃
实体被移出世界先落库再释放，并从位置服务注销寻址仍指向旧进程，消息投递到不存在的实体

② 原理 · Actor 邮箱模型与位置服务

搞清这一节，能解释用法层为什么把「邮箱有界」和「寻址缓存失效」并列成两项——它们是同一个模型的两个薄弱点。同一个世界内部，对象之间直接调用方法，因为它们本来就串行执行。跨世界与跨进程统一走消息：每个可寻址实体有一个邮箱，消息按顺序进入，由该实体所在的执行单元逐条处理。Actor 模型在这里最大的收益不是并发能力，而是「一个实体的所有请求天然串行」，省掉了全部锁。

问题在于寻址。发送方只有实体 ID，不知道对方在哪个进程，所以需要一个位置服务来维护 ID 到进程的映射。玩家切地图时实体要在进程间搬家，这段时间发给它的消息不能丢也不能投给旧进程，必须先排队、迁移完成后再按序投递。

失效场景现象根因修法
寻址缓存不失效玩家切图后偶发操作无响应网关仍按旧位置转发迁移完成时主动通知失效，并给缓存加短过期
迁移期间不排队切图瞬间的操作静默丢失消息投给了已经不持有实体的进程迁移前锁定投递，完成后按序放行
迁移中途失败没有回滚实体在两个进程都存在或都不存在缺少明确的所有权交接点所有权以位置服务的注册为唯一事实，失败则回滚到源进程
把位置服务当普通缓存压测正常，线上高峰全局报错它在每次跨进程调用的关键路径上按 ID 分片、本地缓存、并为查询失败设计降级
邮箱无背压某个热点实体内存持续上涨直到进程被杀投递速度长期高于处理速度邮箱设上限，超限丢弃低优先级消息并告警

② 原理 · 消息定义与代码生成

搞清这一节，能避免一类只在灰度期出现的故障：旧客户端遇上新服务端，数据解析出来全是错的却不报错。双端框架的一个真实优势在这里体现：消息用一份中间格式定义（ET 用的是 proto 风格的定义文件），由工具生成两端的消息类与消息号，客户端和服务端引用的是同一份生成结果。这消除了游戏项目里最常见的一类联调成本——两边各写一遍结构体，字段顺序或类型对不上，表现为解析出来的数据莫名错位。

要立规矩的地方是兼容性：生成代码只保证两端一致，不保证新旧版本一致。客户端还是旧包而服务端已发新版本时，字段增删改就是故障源。规则和后端一样——字段只增不删、编号不复用、语义不原地改、未知字段必须容忍；再加一条游戏特有的：消息号一旦发布不能重排，热更包与安装包里的映射可能不同步。

变更旧客户端遇到新服务端是否安全做法
追加可选字段忽略未知字段安全直接加，新逻辑要能处理缺省值
删除字段但不保留编号编号被后来的字段复用，数据被解释成别的含义危险只停用不删除，编号写进保留列表
修改字段语义或单位不报错，数值全错危险新增字段并存，旧字段留一个版本后再废弃
重排消息号旧包的消息号对应到别的处理器危险消息号显式指定，不依赖生成顺序
把必填改成可选旧客户端仍按必填解析视实现而定协议层面统一按可选设计，业务层自己校验

② 原理 · 协程与 async/await：单线程内的并发

搞清这一节，能解释一类只在高峰出现、压测永远复现不了的崩溃与超发。这里的协程和 Web 的异步目的不同：Web 用异步是为了少占线程提高吞吐，这里是为了在不引入多线程的前提下把等待写成顺序代码。ET 自带一套轻量的可等待类型而不直接用标准库的任务类型，原因是后者默认把续体丢回线程池，而游戏逻辑必须回到原来那个逻辑线程，否则单线程无锁的前提就破了。

由此产生一条最重要的纪律：await 会让出执行权，等它返回时世界已经变了。await 之前拿到的实体引用可能已被销毁，玩家可能已经下线，地图可能已经切换。恢复执行后必须重新校验所有前置条件，这也是新人最容易漏掉的一点。

// 跨进程调用的通用写法：让出前记 ID，恢复后重新取实体并重新校验
// 不要跨 await 持有实体引用，也不要跨 await 相信之前校验过的条件
public async ETTask<bool> TryBuyItem(long unitId, int itemId, int count)
{
    var unit = GetUnit(unitId);
    if (unit == null || !unit.Bag.CanHold(itemId, count)) return false;

    // 让出执行权：这里可能是查询另一个进程，也可能是等存储返回
    var priceOk = await QueryPriceAsync(itemId, count);

    // 关键：恢复执行后世界可能已经变了，必须重新取实体并重新校验一次
    unit = GetUnit(unitId);
    if (unit == null) return false;              // 玩家可能已经下线或切了地图
    if (!priceOk || !unit.Bag.CanHold(itemId, count)) return false;
    if (unit.Money < priceOk.Total) return false; // 余额在等待期间可能被别的流程扣掉

    unit.Money -= priceOk.Total;
    unit.Bag.Add(itemId, count);
    unit.MarkDirty();                             // 只标脏，不在这里直接写库
    return true;
}
陷阱线上表现为什么发生修法
跨 await 持有实体引用偶发空引用，且只在高峰出现等待期间实体已被销毁只记 ID，恢复后重新取并判空
await 之后不重新校验条件余额扣成负数、道具被超发等待期间状态被其他流程改过把校验放在真正修改状态的那一刻之前
在逻辑线程里同步等待异步结果整个世界卡住，所有玩家一起无响应逻辑线程只有一个，被自己阻塞一路 await 到底，禁止同步等待
跨进程调用不设超时大量协程永久挂起，内存缓慢上涨下游不回包且没有取消机制每个调用配超时与取消，超时按业务语义兜底
发出去就不管的协程没有异常捕获逻辑静默中断，日志里一片干净没有人 await，异常无处抛顶层统一包一层捕获并记日志
同一实体的两个流程并发改同一份状态数值对不上，复现概率极低await 把「看起来的原子操作」切成了两段给该实体加逻辑层的处理中标记，或把操作合并成一步

② 原理 · 内存态权威与落库时机

搞清这一节，就知道用法层第 6 项「按数据分级」具体该怎么分。这套架构里数据库不是事实来源，内存才是。读永远走内存，写是批量且延迟的。于是唯一需要认真设计的问题变成：每一类数据能接受多大的丢失窗口。把所有字段一视同仁地实时落库，写放大会把存储打爆；全都靠定时落库，充值和交易一旦丢就是真金白银的客诉。

仅在关键事件落库两次事件之间很低中关卡结算、离线收益结算
仅下线时落库整个在线时长最低低只有能接受全丢的临时数据才行
完全不落库不适用零低位置、血量、冷却等可重新推导的运行态

② 原理 · 会话恢复：连接与会话必须分开

搞清这一节，能把用法层前三项（会话分离、消息序号、幂等键）串成一条完整的重连协议。长连接服务必须把「连接」和「会话」分开：连接断了，会话还要在服务端存活一段时间，这段时间内重连可以接回原状态，否则进隧道断网十秒回来副本进度就没了。关键是等待重连这个中间态的超时时长——太短体验差，太长会积压僵尸会话。

重连要做对，协议层要有两样东西：消息序号和幂等键。客户端上报自己已收到的最后一个序号，服务端据此补发缺失的推送；客户端重发的操作携带幂等键，服务端据此识别「这条我已经执行过了」。缺了这两样，重连之后必然出现丢推送或重复扣道具。幂等键本身怎么设计、服务端怎么回放首次结果，见 幂等的完整工程实现。

③ 场景 · 按规模与玩法选架构形态

这类系统最贵的错误是过早分布式。下表按具体场景给出该做什么与它的代价：

场景该怎么做为什么代价
几千人同时在线，单区玩法单进程加多个逻辑世界，先不拆进程拆进程会把所有调用变成异步、所有状态变成需要寻址的，复杂度不是翻倍而是翻十倍单机故障即全区下线，所以状态重建路径必须可用且演练过
单张地图成为热点（万人同屏）不要指望加机器；改玩法承载方式或做视野分片一个逻辑世界的负载无法靠加实例摊薄分片边界上的跨片交互要自己实现，是新的一类 bug 来源
需要跨服匹配、排行、赛事分区负责承载与强一致玩法，独立跨服集群负责弱一致玩法按数据切分能天然隔离容量问题，弱一致玩法不需要待在区内两套部署与数据同步链路，后期合服是高风险迁移
变更涉及资产：充值、交易、开箱返回成功前同步落库，并记幂等流水号这类数据丢了是真金白银，事后无法推导写放大与延迟，需要限制这类操作的频率或走独立存储
位置、血量、冷却、当前帧完全不落库，重连时整包重新下发服务端可以重新推导，落库纯属浪费重连协议必须支持整包状态同步，客户端要能接受被纠正
玩家频繁切地图或跨进程迁移期锁定投递、以位置服务注册为所有权唯一事实、完成后主动失效缓存否则消息会丢或出现两份实体迁移本质是一次简化的分布式事务，失败必须能回滚到源进程
要求不停服发布数值走配置热加载，逻辑变更走滚动重启加状态可重建服务端本来就能重启，替换方法体的收益低而风险高发布窗口要和运营对齐，状态重建路径要定期演练

③ 场景 · 分区分服、热更新与不适用边界

分区分服本质上是按数据切分而不是按负载切分：每个区是一份独立的数据与一套独立部署，容量问题被天然隔离。代价是跨服玩法要单独设计，并且后期合服是一次高风险的数据迁移。常见折中是分区负责承载与强一致玩法，跨服集群负责匹配、排行、赛事这类弱一致玩法。

热更新在服务端要摆正期望：客户端受商店审核约束才需要整套代码热更；服务端本来就能重启，真正需要的是不停服替换的能力，而不是替换方法体的能力。可靠顺序是：数值走配置热加载、逻辑变更走滚动重启加状态可重建、只有必须在线修补时才考虑替换实现。ET 生态里客户端的代码热更通常依赖 HybridCLR 一类方案，服务端用同一套框架的价值主要在双端共用消息与实体定义。

不适用边界：这一篇的结论只适用于「状态在内存、必须路由到特定进程」的服务。同簇前几篇的做法在这里要重新检查：跨服务写的 Saga 与 TCC 骨架假设参与方是无状态的、可以随时重试，见 柔性事务的实现细节与失败处理；重复请求的处理在这里退化成重连时的幂等键与消息序号，完整的键设计在 幂等的完整工程实现；限流在这里主要挡登录与匹配这类入口，而不是每条帧消息，做法见 限流的分布式实现与多维配额；一致性档位在这里的含义变了——权威在内存，所以要问的是「丢多少」而不是「读到多旧」，对照 一致性模型的工程含义；该不该引入分布式、以及更轻的替代顺序仍然适用，见 分布式一致性深度原理。此外：Unity 侧的工程问题在 Unity 工程；落库批量与索引设计在 MySQL 深度原理；内存持续上涨与进程被杀的取证在 性能分析；进程编排与滚动重启在 Kubernetes（注意有状态服务不能照搬无状态的滚动策略）。

这是本簇的最后一篇。前五篇处理的是无状态服务的一致性、事务、幂等与自我保护；这一篇说明当状态搬进内存之后，哪些结论仍然成立、哪些必须换一套做法。

最容易踩的坑

❌
有状态游戏服务的高频事故清单
  • 在逻辑线程里同步等待异步结果：一次同步等待就能让整个逻辑世界的所有玩家一起无响应，而监控上看只是「某个进程 CPU 不高但不处理消息」。
  • 跨 await 持有实体引用：恢复执行时对象可能已经被销毁，表现为高峰期偶发空引用崩溃，压测阶段几乎不可能复现。
  • await 之后不重新校验前置条件：让出执行权期间余额已被别的流程扣过，恢复后照原样扣一次，数值被扣成负数。
  • 发出去就不管的协程没有顶层异常捕获：异常被静默吞掉，现象是某个玩家的某个流程走到一半停住，日志里干干净净。
  • 邮箱不设上限：热点实体的投递速度长期高于处理速度，内存无声上涨，且崩溃点通常出现在别的无关代码里。
  • 邮箱有界但溢出策略没想清楚：默认丢最新消息会把玩家刚发的操作丢掉，必须按消息优先级决定丢谁并上报指标。
  • 寻址缓存没有失效机制：玩家切地图之后偶发操作无响应，因为网关还在按旧位置转发，这类问题很容易被误判成网络抖动。
  • 批量落库时先发起写入再摘脏标记：写失败后这批变更既不在集合里也没进库，静默丢失，事后连丢了哪些都查不出来。
  • 只依赖定时落库来保护资产：充值、交易、抽奖这类操作必须在返回成功前确保已持久化，并带幂等流水号，否则一次进程崩溃就是真实客诉。
  • 断线即销毁会话：网络抖动十秒就丢掉副本进度；反过来把等待重连的超时设得过长，又会积压大量僵尸会话占着内存和实体。
  • 重连不带消息序号：服务端不知道该补发哪些推送，客户端要么缺一段状态，要么收到一堆重复推送。
  • 状态重建路径从不演练：滚动重启和崩溃恢复都靠它，但平时没人走，真出事时才发现它本身就是坏的。
  • 过早上分布式：几千人在线用单进程加多个逻辑世界通常就够，提前拆成多进程会把所有调用变成异步、把所有状态变成需要寻址的，复杂度不是翻倍而是翻十倍。
