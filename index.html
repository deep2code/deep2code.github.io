这个站写给谁

站内现有 317 篇技术文章，不是入门教程的合集。默认读者是已经在生产环境里维护过服务的工程师：知道 Redis 怎么用，但想弄清近似 LRU 在什么采样参数下会误删热 key；能写出一个 Deployment，但想弄清 apply 之后到 Pod 真正就绪之间有几个控制器在参与。所以每篇的落点固定是三件事——机制层面为什么是这样、参数默认值调错的后果、这个方案在什么边界条件下会失效。

组织方式是两层：9 个一级分类，每个分类下是主题目录。主题目录的首页是这个主题的总览，负责讲清分层地图与选型判据；它下面的子页面才写具体机制。因此正确的读法是先读总览再进子页，而不是从搜索结果直接跳进某个细节页。总览里那张分层图决定了你还需不需要往下读。

主题簇参与的分类为什么必须连着读
一致性与幂等数据库与缓存、后端（分布式、消息队列）只看缓存章节，结论会停在「先删缓存还是先写库」；把幂等键与消息重投放进来，才知道脏数据窗口最终由谁兜底
过载保护与尾延迟运维（Nginx、监控）、后端（微服务、性能）限流阈值来自容量反推，而容量数字来自分位数指标；分位数判读错，就会把问题定位到错误的那一层
交付与回滚运维（CI/CD、GitOps）、数据库（设计与演进）发布策略能回滚到什么程度，上限由数据库变更的兼容性决定，而不是由发布工具决定
检索与 RAG数据库（向量、ES）、AI（RAG、LangChain）召回率与延迟成本三角，是同一个问题在存储侧和应用侧的两个视角，只看一侧会得出相反的调优方向
端到端类型安全后端（API 设计、tRPC）、数据库（Drizzle）、前端（Next.js）类型链路从数据库 schema 一路推到前端组件，中间任何一段退化成 any 或手写 DTO，整条链的收益就归零
