前端性能优化

🏷️ 性能优化

一、性能是功能，不是锦上添花

Google 数据显示：页面加载时间从 1 秒到 5 秒，移动用户跳出率增加 90%。我亲手优化过一个活动落地页，LCP 从 4.2s 压到 1.8s，当天转化率涨了 23%——这不是玄学数字，是老板看得见的钱。

二、核心指标：Web Vitals

Google 定义的三个核心指标，代表用户的真实体验：

  • LCP（Largest Contentful Paint）：最大内容绘制，衡量加载速度，目标 < 2.5s。
  • INP（Interaction to Next Paint）：交互到下一次绘制，衡量响应性，目标 < 200ms。（2024 年起替代 FID）
  • CLS（Cumulative Layout Shift）：累积布局偏移，衡量视觉稳定性，目标 < 0.1。

优化之前先测量。用 Lighthouse、Chrome DevTools Performance 面板、或真实用户监控（RUM）工具拿到基线数据，否则优化就是盲人摸象。

三、浏览器渲染流水线：性能优化的理论基础

理解浏览器如何把 HTML/CSS/JS 变成像素，才能知道每个优化手段为什么有效：

flowchart LR HTML[HTML] --> DOM[DOM 树] CSS[CSS] --> CSSOM[CSSOM 树] DOM --> RENDER[渲染树 Render Tree] CSSOM --> RENDER RENDER --> LAYOUT[布局 Layout
计算几何位置] LAYOUT --> PAINT[绘制 Paint
填充像素] PAINT --> COMPOSITE[合成 Composite
GPU 合成图层] COMPOSITE --> SCREEN[屏幕显示] JS[JavaScript] -.修改 DOM/样式.-> DOM JS -.触发重排/重绘.-> LAYOUT style LAYOUT fill:#f59e0b,color:#fff style PAINT fill:#8b5cf6,color:#fff style COMPOSITE fill:#10b981,color:#fff

性能优化的核心原则：尽量只触发 Composite，避免 Layout 和 Paint。修改 transform/opacity 只触发合成（GPU 加速），修改 width/top/margin 会触发 Layout（重排），修改 background-color 触发 Paint（重绘）。

我踩过的动画坑

我早年做一个轮播动画，用 JS 每帧改 left 属性，低端机直接掉到 15fps。后来换成 transform: translateX() + will-change: transform，立刻跑到 60fps。浏览器能把 transform 交给 GPU 合成，完全绕过 Layout 和 Paint——记住这一条，动画性能问题解决一半。

4.2 运行时性能：避免卡顿

// 长列表虚拟滚动：只渲染可视区域
import { useVirtualizer } from "@tanstack/react-virtual";

function VirtualList({ items }: { items: string[] }) {
  const parentRef = useRef<HTMLDivElement>(null);
  const rowVirtualizer = useVirtualizer({
    count: items.length,
    getScrollElement: () => parentRef.current,
    estimateSize: () => 35,
  });

  return (
    <div ref={parentRef} style={ height: 400, overflow: "auto" }>
      <div style={ height: rowVirtualizer.getTotalSize(), position: "relative" }>
        {rowVirtualizer.getVirtualItems().map(virtualRow => (
          <div key={virtualRow.index}
               style={ position: "absolute", top: virtualRow.start, height: virtualRow.size }>
            {items[virtualRow.index]}
          </div>
        ))}
      </div>
    </div>
  );
}

4.3 状态管理：选择合适的方案

状态管理方案的选择直接影响重渲染频率。以下是三种主流方案对比：

// Zustand：极简、无 Provider、选择器精确订阅
import { create } from "zustand";

interface BearStore {
  bears: number;
  addBear: () => void;
}
const useBearStore = create<BearStore>((set) => ({
  bears: 0,
  addBear: () => set((s) => ({ bears: s.bears + 1 })),
}));

// 组件只订阅需要的字段，bears 不变就不重渲染
function BearCounter() {
  const bears = useBearStore((s) => s.bears);
  return <h1>{bears} 只熊</h1>;
}
// React Context：低频、小型共享（主题、用户）
import { createContext, useContext } from "react";

const ThemeContext = createContext<"light" | "dark">("light");
function Layout() {
  const theme = useContext(ThemeContext);
  return <div class={`theme-${theme}`}>...</div>;
}
// 注意：Context 值变化会触发所有消费组件重渲染，
// 高频更新的状态不要放 Context。
方案体积重渲染粒度适合场景我的评分
useState + Context0粗（全消费组件）主题、用户信息等低频够用就别加库
Zustand~1KB细（选择器）中大型应用默认起点我的首选
Jotai~2KB原子级原子化状态模型灵活但上手略绕
Redux Toolkit~10KB细（选择器）需时间旅行调试、中间件大团队严格数据流
Recoil-原子级已停止维护别用新项目

五、最佳实践

  • 测量先行：优化前用 Lighthouse 跑分，优化后再跑一次对比。没有数据的优化是自嗨。
  • 图片优化收益最大：现代格式（WebP/AVIF）、响应式 srcset、懒加载、占位符（LQIP）。图片通常占页面 60% 以上字节。
  • 代码分割按路由，不按组件：按路由拆分是最自然的分割点。过度拆分组件级 chunk 会增加请求数。
  • 状态管理最小化：能放 useState 就不要放全局 store。全局状态每多一个字段，重渲染风险就多一分。
  • 用选择器订阅，不要整个 store 订阅：Zustand/Jotai/Redux 都支持 selector，只订阅需要的字段。
  • 避免布局抖动：不要在循环里读 DOM 样式再写样式——先批量读，再批量写。
  • 监控真实用户数据：实验室数据（Lighthouse）和真实用户数据（RUM）经常不一致。接入 web-vitals 库上报真实指标。

六、常见问题 FAQ

Q1：首屏加载很慢，但打包分析显示 JS 不大，瓶颈在哪？

按优先级排查，我一般按这个顺序问：

  • 服务器 TTFB——首字节时间。后端慢比前端慢更常见，我踩过好几次；
  • 关键渲染路径——CSS 阻塞渲染，检查有没有大的未内联 CSS；
  • 字体加载——webfont 阻塞文本渲染，记得 font-display: swap；
  • 第三方脚本——埋点、客服、广告脚本常常阻塞，用 async/defer 或动态注入。

Q2：React 应用卡顿，怎么定位？

用 Chrome DevTools Performance 面板录 3 秒操作，看主线程有没有长任务（>50ms 的红色块）。常见原因：

  • 大列表全量渲染——上虚拟滚动；
  • 每次渲染都新建对象/函数——useMemo/useCallback；
  • 重型计算在渲染里——挪到 useEffect 或 useMemo；
  • 状态更新太频繁——节流/防抖。

Q3：Redux、Zustand、Jotai、Recoil 怎么选？

我的选型口诀：小项目 useState + Context 够；中大型直接 Zustand（API 简洁、TS 友好、1KB）；要原子化模型用 Jotai；要时间旅行调试和严格数据流上 Redux Toolkit。Recoil 已停维护，新项目别碰。选标准是「团队上手成本 + 调试需求」，不是「哪个最酷」。

七、总结

前端性能优化是一个系统工程：加载性能看资源体积和关键渲染路径，运行时性能看主线程任务和渲染频率，状态管理影响重渲染范围。三者不是孤立的——不合理的状态结构会导致多余重渲染，多余重渲染又会让主线程任务变长。养成"测量 → 定位 → 优化 → 再测量"的闭环，比记住 100 个优化技巧更重要。至此，前端框架五篇文章完结：从 TypeScript 类型基础，到 React/Vue 框架，再到工程化和性能优化，形成完整的现代前端知识图谱。
