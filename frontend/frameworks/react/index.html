React Hooks

🏷️ React

一、React 的设计哲学：UI = f(state)

我用 React 从 16.8 到 React 18，最大的体会是它十年核心理念没变：把界面描述为状态的纯函数。同一个状态，就该渲染出同样的 UI。你不用再手动操作 DOM，只要描述"界面该长什么样"，React 负责把它同步到浏览器。React 18 的并发渲染、自动批处理、Suspense 数据获取，是这十年最激进的一次架构升级——我团队从 17 升到 18 后，列表滚动卡顿少了一大半。

二、Hooks：函数组件的状态与副作用

Hooks（16.8 引入）是 React 我最喜欢的 API 设计。它让函数组件拥有了类组件的全部能力——状态、生命周期、上下文——同时甩掉了类的 this 绑定地狱和 HOC 嵌套地狱。我当年从类组件迁到 Hooks，一个 400 行的 class 组件瘦到 120 行。

2.1 useState：组件内的快照状态

import { useState } from "react";

function Counter() {
  // count 是"这一次渲染"的快照，不是实时值
  const [count, setCount] = useState(0);

  return (
    <button onClick={() => setCount(c => c + 1)}>
      点击了 {count} 次
    </button>
  );
}

关键认知：每次渲染都是独立的"快照"。setState 不会改变当前渲染里的 count，而是触发一次新的渲染，新渲染里 count 才是新值。这就是为什么闭包里读到旧值是"正常行为"，不是 bug。

我踩过的快照坑

我早年写过一个「点按钮后立刻 alert 新值」的需求，点完弹出来还是旧值，以为 React 坏了。其实是当前渲染的 count 快照没变——alert 读的是这次渲染的旧值。后来用 setTimeout 包一层或读事件对象才对。这个「快照」心智模型理解了，React 一半的诡异行为都能解释。

2.2 useEffect：与外部系统同步

useEffect 不是"生命周期"的替代品，它的真正语义是把组件与外部世界同步：订阅、定时器、手动 DOM 操作、数据请求。依赖数组决定了"什么时候重新同步"：

useEffect(() => {
  const controller = new AbortController();

  fetch(`/api/user/${userId}`, { signal: controller.signal })
    .then(res => res.json())
    .then(data => setUser(data));

  // 清理函数：组件卸载或依赖变化时调用
  return () => controller.abort();
}, [userId]); // userId 变化时重新请求

2.3 useMemo 与 useCallback：什么时候才需要

这两个 Hook 是"性能优化"工具，不是"必须用"的语法。大多数情况下你不需要它们。它们的适用场景很窄：

  • useMemo：昂贵计算（如对 10 万条数据做排序/过滤）且每次渲染都会执行时。
  • useCallback：把函数传给被 React.memo 包裹的子组件，避免子组件无谓重渲染时。
const sorted = useMemo(
  () => items.slice().sort((a, b) => b.score - a.score),
  [items]
);
const handleRemove = useCallback((id: string) => {
  setItems(prev => prev.filter(i => i.id !== id));
}, []);

2.4 useRef：跨渲染保持可变引用

useRef 有两个用途：访问 DOM 节点，以及存储"不需要触发渲染"的可变值（如定时器 ID、上一次的值）。

三、架构原理：Fiber 与并发渲染

React 15 的 reconciliation 是同步递归——一旦开始就不能中断，大组件树会阻塞主线程。React 16 重写为 Fiber 架构：把渲染工作拆分成可中断、可优先级排序的小单元。React 18 在此基础上启用并发渲染：高优先级更新（用户输入）可以打断低优先级更新（数据列表渲染）。

理解这个流程能解释很多我以前觉得"玄学"的现象：

  • 为什么 useEffect 在 commit 之后才跑——因为 DOM 已经就绪；
  • 为什么 setState 后立刻读 state 还是旧值——render 阶段还没开始；
  • 为什么 StrictMode 下副作用执行两次——故意双重调用，逼你写纯净的副作用。

五、实战：一个类型安全的自定义数据请求 Hook

下面这个 useFetch 是真实生产级代码，展示 TypeScript 泛型 + React Hooks 的结合：

import { useState, useEffect, useCallback } from "react";

interface FetchState<T> {
  data: T | null;
  loading: boolean;
  error: Error | null;
}

function useFetch<T>(url: string | null) {
  const [state, setState] = useState<FetchState<T>>({
    data: null, loading: !!url, error: null,
  });

  const fetchData = useCallback(async () => {
    if (!url) return;
    setState({ data: null, loading: true, error: null });
    try {
      const res = await fetch(url);
      if (!res.ok) throw new Error(`HTTP ${res.status}`);
      const data = (await res.json()) as T;
      setState({ data, loading: false, error: null });
    } catch (e) {
      setState({ data: null, loading: false, error: e as Error });
    }
  }, [url]);

  useEffect(() => {
    fetchData();
  }, [fetchData]);

  return { ...state, refetch: fetchData };
}

// 使用
interface Article { id: number; title: string }
function ArticleList() {
  const { data, loading, error } = useFetch<Article[]>("/api/articles");
  if (loading) return <p>加载中...</p>;
  if (error) return <p>出错: {error.message}</p>;
  return <ul>{data?.map(a => <li key={a.id}>{a.title}</li>)}</ul>;
}

六、最佳实践

  • 状态尽量下沉，计算尽量上提：多个组件共享的状态放到共同父级或全局 store；纯计算放组件外或 useMemo，不要在 render 里做副作用。
  • 副作用要纯净且可清理：useEffect 里不要修改外部变量（除非是订阅/定时器），return 清理函数。
  • 把组件拆小，而不是把逻辑塞进 useMemo：一个 300 行的组件，拆成 5 个 60 行的子组件，比任何性能优化都有效。
  • 用 React DevTools Profiler 找瓶颈：不要凭感觉优化，先看火焰图确认确实有重渲染问题。
  • 服务端组件（RSC）优先：React 18+ 支持 Server Components，能在服务端渲染不包含交互的组件，大幅减少客户端 JS。新项目应优先考虑 Next.js App Router。

七、常见问题 FAQ

Q1：为什么我在 useEffect 里 setState 后组件无限重渲染？

最常见原因是依赖数组里放了每次渲染都新建的对象或函数。比如 useEffect(..., [options])，而 options 是每次 render 字面量新建的。解决：把依赖拆成原始值（options.id、options.page），或用 useMemo/useCallback 稳定引用。

Q2：useEffect 和 useLayoutEffect 有什么区别？

useEffect 在浏览器绘制之后异步执行，不阻塞渲染；useLayoutEffect 在 DOM 变更之后、绘制之前同步执行，会阻塞绘制。绝大多数场景用 useEffect，只有需要"读取 DOM 布局并同步修改，避免闪烁"时才用 useLayoutEffect（如模态框定位、动画测量）。

Q3：Redux、Zustand、Context 选哪个？

方案重渲染粒度适合我的建议
useState 局部组件内表单、开关等局部状态永远首选
Context粗（全消费组件）主题、用户信息等低频别放高频状态
Zustand细（选择器）中大型应用全局状态无 Provider、1KB
Redux Toolkit细（选择器）需时间旅行、中间件生态超大型团队严格数据流

我团队默认 Zustand。不要为了"全局状态"而滥用状态库——组件局部 useState 永远是第一选择，跨组件共享再上 Zustand。

八、总结

React 的学习曲线不在 API，而在"心智模型"：理解快照、单向数据流、副作用同步这三件事，比背熟 10 个 Hook 更重要。React 18 的并发渲染让"性能优化"从手动避坑变成框架自动调度，但前提是你的组件是纯净的、副作用是可预测的。下一篇我们进入 Vue 3，看另一种响应式思路如何用更轻量的语法实现同样的目标。
