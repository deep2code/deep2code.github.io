React 渲染模型与 Hooks 机制

🏷️ React

后端工程师转过来写 React，最容易低估的不是语法而是执行模型：函数组件不是「对象的一个方法」，而是每次渲染都被重新调用一次的纯函数，所有变量、闭包、事件处理函数都是那一次调用的产物。React 里绝大多数诡异 bug（定时器拿到旧值、effect 无限循环、memo 不生效、列表数据和筛选条件对不上）都是从这一条推导出来的。这篇按「机制 - 推论 - 错误写法与正确写法」的顺序讲清楚。

函数组件的执行模型：每次渲染是一次独立的快照

一次渲染 = 一次函数调用 + 一组当那一刻的 state 和 props 值 + 一批在那次调用中创建的闭包。这些闭包捕获的是那一次渲染的值，不是「变量的最新值」。state 不是可变容器，它更像每次渲染都重新绑定一次的常量。理解这点之后，最经典的坑「过期闭包」就变得显而易见：任何被长期持有、跨越多次渲染的回调（定时器、事件监听、Promise 回调、订阅函数），只要它引用了 state，读到的就是创建时那一帧的值。

// 坏例子：计数器停在 1，永远不动
function BrokenCounter() {
  const [count, setCount] = useState(0);

  useEffect(() => {
    const id = setInterval(() => {
      // 这个闭包捕获的是「第一次渲染的 count」，值恒为 0
      // 所以每秒都在执行 setCount(0 + 1)，state 从 0 变 1 之后再也不变
      setCount(count + 1);
    }, 1000);
    return () => clearInterval(id);
  }, []); // 空依赖数组：定时器只创建一次，闭包也就永远停在第一帧

  return <span>{count}</span>;
}

// 解法一（首选）：函数式更新，不再依赖闭包里的 count
setCount(prev => prev + 1); // prev 由 React 传入，一定是最新值

// 解法二：把「会变但不该触发重新订阅」的值放进 ref
function RefCounter({ step }) {
  const [count, setCount] = useState(0);
  const stepRef = useRef(step);
  useEffect(() => { stepRef.current = step; }, [step]); // 每次渲染同步最新值

  useEffect(() => {
    const id = setInterval(() => setCount(c => c + stepRef.current), 1000);
    return () => clearInterval(id);
  }, []); // 依赖仍为空，但读到的 step 永远是最新的
  return <span>{count}</span>;
}

// 解法三：把逻辑移出组件——定时器只负责「触发」，状态计算交给 reducer
const [state, dispatch] = useReducer(reducer, initial);
useEffect(() => {
  const id = setInterval(() => dispatch({ type: 'tick' }), 1000);
  return () => clearInterval(id);
}, []); // dispatch 的引用是稳定的，reducer 内部总能拿到最新 state
💡
判断闭包是否过期的一条速查规则

问自己：这个函数会在「创建它的那次渲染」之后才被调用吗？如果会（定时器、订阅、Promise then、addEventListener、requestAnimationFrame），它引用的每一个 state 和 props 都有过期风险。事件处理函数通常安全，因为它在每次渲染时都被重新创建并重新挂到元素上。

Hooks 规则为什么存在：状态存在链表的槽位里

React 并不知道你调用的是哪个 hook——没有名字、没有 key，它只按调用顺序把每次 hook 调用的数据挂到当前 fiber 的一条链表上：第一次调用取第一个槽位，第二次取第二个槽位。这就是为什么 hook 必须在每次渲染中以完全相同的顺序、相同的数量被调用。把 hook 放进 if 或循环，等于在某些渲染里跳过一个槽位，后面所有 hook 全体错位一位：useState 返回别人的值，useEffect 绑上别人的依赖数组，而报错位置往往和真正原因毫无关系。

useEffect 是被误用最多的 hook

它的语义是「把 React 状态与外部系统同步」，外部系统指 DOM 事件监听、定时器、WebSocket、第三方图表实例、浏览器 API 这些不受 React 管理的东西。它不是「监听某个值变化然后做点事」的通用钩子。把它当 watch 用，会得到多余的渲染轮次、中间态闪烁、以及一整类难以复现的时序 bug。

误用类型 典型写法 产生的问题 正确做法
用 effect 派生状态 依赖 items 变化后 setTotal(sum) 每次数据变化渲染两轮，第一轮 total 是旧值，出现闪烁 渲染中直接算 const total = sum(items)，昂贵时才包 useMemo
用 effect 同步 props 到 state 依赖 props.user 变化后 setUser(props.user) 两份数据源，中间一帧显示旧用户；父子更新顺序一乱就不一致 直接用 props；确实需要重置内部状态时给组件传 key 让它重建
用 effect 响应用户事件 点击后 setSubmitted(true)，再用 effect 监听 submitted 发请求 事件与副作用被状态间接耦合，无法区分「用户点了」和「状态恰好变了」 副作用直接写在事件处理函数里
手写数据获取 effect 里 fetch 后 setState，无取消无去重 竞态覆盖、切页面重复请求、请求瀑布、无缓存 用 TanStack Query 或 SWR；必须手写时按下一节处理竞态
依赖数组漏项 用了 filter 但依赖数组只写了 page filter 变化后不重新执行，界面与状态不一致 开启 exhaustive-deps 规则并真正修复，而不是加注释关闭它
用空依赖数组骗 lint 本该依赖多个值却写成空数组「只跑一次」 闭包永久过期，行为随机；后续维护者完全看不出来 用函数式更新或 ref 消除依赖，而不是隐藏依赖
在 effect 里无条件 setState effect 依赖 data，内部又 setData 渲染与 effect 互相触发，无限循环直到浏览器卡死 加终止条件，或意识到这个值本该是派生值不该是 state

竞态条件：数据获取里最隐蔽的错误

这是手写数据获取必然遇到的问题，而且在开发环境本地接口很快时几乎不会复现。用户快速切换筛选条件，effect 连续发出请求 A 和 B；如果 A 因为网络抖动晚于 B 返回，A 的 setState 就会覆盖 B 的结果，界面上显示的数据与当前筛选条件不符，而且不会有任何报错。

让上一次请求的回调不再写入状态 
// 可直接抄走：带取消与竞态防护的数据获取 hook
import { useEffect, useReducer, useRef } from 'react';

type State<T> =
  | { status: 'idle' | 'loading' }
  | { status: 'success'; data: T }
  | { status: 'error'; error: Error };

export function useFetch<T>(url: string, init?: RequestInit) {
  const [state, setState] = useReducer(
    (_: State<T>, next: State<T>) => next,
    { status: 'idle' } as State<T>
  );
  // init 每次渲染都是新对象，放进依赖会导致无限请求，所以用 ref 兜住
  const initRef = useRef(init);
  initRef.current = init;

  useEffect(() => {
    const ctrl = new AbortController();
    let ignore = false; // 双保险：abort 之后仍可能有微任务在跑

    setState({ status: 'loading' });
    fetch(url, { ...initRef.current, signal: ctrl.signal })
      .then(async (res) => {
        // fetch 只在网络层失败才 reject，4xx 5xx 必须自己判断
        if (!res.ok) throw new Error('HTTP ' + res.status);
        return (await res.json()) as T;
      })
      .then((data) => { if (!ignore) setState({ status: 'success', data }); })
      .catch((error: unknown) => {
        // 主动取消不是错误，不要把它渲染成错误态
        if (ctrl.signal.aborted) return;
        if (!ignore) setState({ status: 'error', error: error as Error });
      });

    return () => { ignore = true; ctrl.abort(); }; // 依赖变化或卸载时执行
  }, [url]); // 只依赖真正决定「请求身份」的值

  return state; // 判别联合：外部必须先判断 status 才能访问 data
}

// 它在此基础上还提供缓存、去重、重试、失效、窗口聚焦重取、分页与预取。

useMemo 与 useCallback：它们本身是有成本的

这两个 hook 被滥用得最厉害。它们不是「加了就变快」的开关：每次渲染都要创建新函数、做依赖数组浅比较、额外占内存，还让代码变难读。只有在结果被 memo 组件消费、被其他 hook 当依赖、或者计算确实昂贵时才有价值；随手包一层，绝大多数情况是净亏损。React 19 的编译器方向就是把这类手动优化自动化掉，正说明手写它是工程债。

场景 加 useMemo / useCallback 净收益 说明
计算是一次加法或字符串拼接 不需要 负 比较依赖数组的成本高于重新计算
上千条数据的排序或过滤 需要 正，可能几十毫秒 依赖必须精确，漏项会拿到过期结果
结果作为 props 传给 memo 子组件 需要 正 否则新引用每次击穿浅比较，memo 完全无效
结果作为 useEffect 的依赖项 需要 正，属于正确性问题 不稳定的引用会让 effect 每次渲染都重跑
子组件没有被 memo 包裹 不需要 负 子组件本来就会重渲染，稳定引用毫无用处
创建 Context 的 value 对象 需要 正 行内字面量会让所有消费者在每次父渲染时重渲染
保存 DOM 实例或第三方对象 都不合适 —— useMemo 不保证不被丢弃，该用 useRef 或惰性初始化

effect 的生命周期与 StrictMode 双调用

把 effect 想成「订阅」而不是「生命周期钩子」：它在依赖变化时先清理旧订阅再建立新订阅，卸载时清理。开发环境的 StrictMode 会在挂载后立刻执行一次「卸载再挂载」，这是故意的，用来暴露没写清理函数的副作用——重复添加监听、重复建连、重复启动定时器都会当场显形，而不是等用户来回切页面时才变成内存泄漏。生产构建不会双调用。应对方式是补齐清理函数让 effect 幂等，而不是用 ref 标记跳过第二次。

stateDiagram-v2 [*] --> 首次渲染 首次渲染 --> 已挂载: 提交 DOM 后异步执行 effect 已挂载 --> 清理中: 依赖数组中任一值变化 清理中 --> 已挂载: 执行 cleanup 后再执行新 effect 已挂载 --> 开发环境双调用: StrictMode 立即模拟一次卸载重挂 开发环境双调用 --> 已挂载: 未写 cleanup 的副作用在此暴露 已挂载 --> [*]: 组件卸载 执行最后一次 cleanup note right of 清理中 cleanup 里读到的是上一次 effect 的闭包值 所以取消请求、解绑监听时拿到的对象一定配对 end note note right of 开发环境双调用 生产构建不会双调用 用 ref 标记跳过第二次是在掩盖问题 end note

批处理与更新的异步性

setState 不是「立刻改变量」，它是「排一次更新请求」。同一个事件处理函数里连续调用多次，React 18 会自动合并为一次渲染；而且合并范围从 React 17 的「仅 React 事件内」扩大到了 Promise、setTimeout、原生事件回调里（自动批处理）。所以在 setState 之后立刻读同名变量，拿到的必然是本次渲染的旧值——不是 bug，是模型决定的。

写法 React 17 行为 React 18 行为 结论
onClick 里连续 setCount(count + 1) 三次 合并一次渲染，结果只加 1 同上 三次都基于同一个快照值，要加 3 必须用函数式更新
onClick 里连续 setCount(c => c + 1) 三次 合并一次渲染，结果加 3 同上 函数式更新在队列里依次应用
setTimeout 里连续两次 setState 不批处理，渲染两次 自动批处理，渲染一次 升级到 18 后中间态不再可见，依赖中间态的代码会改变行为
fetch 的 then 里多次 setState 不批处理 自动批处理 同上，加载态与数据态可以放心一起 set
setState 之后立刻 console.log 该变量 旧值 旧值 要读新值就在下一次渲染里读，或用函数式更新的参数
需要在 DOM 更新后同步测量 需手动 flush 用 flushSync 包住，但会牺牲批处理 只在必须同步读布局时使用，属于逃生舱

受控与非受控：表单该选哪一种

受控意味着每次按键都触发一次 setState 和一次渲染，好处是任何时刻 state 就是唯一真相，方便做联动校验与格式化；非受控把值留在 DOM 里，提交时统一读取，代价是无法实时响应。大表单全受控是常见的卡顿来源，尤其在低端机上每个字符都要重渲染几十个字段。

维度 受控组件 非受控组件
值的真源 React state DOM 节点自身
每次输入的渲染次数 一次（可被防抖但会丢失即时回显） 零
实时校验与联动 天然支持 需要额外读取 DOM
大表单性能 字段多时明显变慢，需要拆组件或按字段隔离 基本无成本
与 key 错位的关系 值由 state 控制，不受 diff 复用影响 用 index 当 key 时用户输入会串到别的行
推荐场景 需要即时反馈、字段间互相影响 字段多、只在提交时校验，或用 React Hook Form 这类库 
// 可直接抄走：正确的防抖 hook（常见实现有三个 bug，这里都修掉了）
import { useEffect, useRef, useState, useCallback } from 'react';

// 1) 防抖「值」：适合搜索框，配合 useFetch 使用
export function useDebouncedValue<T>(value: T, delay = 300): T {
  const [debounced, setDebounced] = useState(value);
  useEffect(() => {
    const id = setTimeout(() => setDebounced(value), delay);
    return () => clearTimeout(id); // 关键：值再变时取消上一个定时器
  }, [value, delay]);
  return debounced;
}

// 2) 防抖「回调」：必须解决三个问题
//    a. 回调引用每次渲染都变，不能放进依赖数组，否则定时器被反复重建
//    b. 卸载时必须清理，否则组件已销毁还在 setState，开发环境会告警
//    c. 调用方拿到的函数引用必须稳定，否则传给 memo 子组件会失效
export function useDebouncedCallback<A extends unknown[]>(
  fn: (...args: A) => void,
  delay = 300
) {
  const fnRef = useRef(fn);
  fnRef.current = fn; // 每次渲染同步最新逻辑，但不改变下面返回的函数引用

  const timer = useRef<ReturnType<typeof setTimeout> | null>(null);
  useEffect(() => () => { if (timer.current) clearTimeout(timer.current); }, []);

  return useCallback((...args: A) => {
    if (timer.current) clearTimeout(timer.current);
    timer.current = setTimeout(() => fnRef.current(...args), delay);
  }, [delay]); // 引用只在 delay 变化时改变
}

// 注意：输入框的 value 本身不要防抖，否则用户打字会看到字符延迟出现。
// 正确做法是 value 立即更新，只对「请求」或「昂贵计算」防抖。

反模式速查

反模式 表面症状 根因 正确做法
在 useEffect 里 setState 且依赖该 state 页面卡死，CPU 跑满 渲染触发 effect，effect 触发渲染 改为派生值、加终止条件，或把逻辑移到事件处理函数
给依赖数组加注释关闭 lint 数据偶发不更新，难以复现 隐藏了真实依赖，闭包过期 用函数式更新或 ref 真正消除依赖
随手 useMemo 与 useCallback 代码难读，性能没变好 优化成本高于收益，且子组件未被 memo 先用 Profiler 定位，只包昂贵计算与被 memo 消费的引用
把 props 复制进 state 父组件更新后子组件显示旧数据 两份真源，初始值只在首次渲染生效 直接用 props；需要重置就传 key 让组件重建
手写 effect 做数据获取 竞态、重复请求、无缓存、请求瀑布 自己实现了一个不完整的数据层 用 TanStack Query 或 SWR，或框架的数据加载机制
用 ref 跳过 StrictMode 第二次执行 开发环境「正常」，生产出现泄漏 掩盖了缺失的清理函数 补 cleanup，让 effect 可重复执行且幂等
把整个 store 或 Context 取出来用 无关字段变化也重渲染 订阅粒度是整个对象 用 selector 只取需要的字段，多字段用浅比较包装

最容易踩的坑

❌
避坑清单
  • 在 setInterval 或事件监听里用 setCount(count + 1)。闭包捕获的是那一帧的值，计数器会停在 1，必须改成函数式更新。
  • setState 后立刻读同名变量并据此做判断。拿到的一定是旧值，正确位置是下一次渲染或函数式更新的参数。
  • 把 hook 写进 if、循环或早返回之后。槽位错位后报错位置和真正原因无关，排查成本极高。
  • 用 useEffect 把 props 同步进 state。中间会有一帧旧数据，需要重置状态时应该给组件传 key。
  • 用 useEffect 派生状态（items 变了就 setTotal）。多一轮渲染并闪烁，直接在渲染中计算即可。
  • 手写数据获取但不处理竞态。开发环境接口快到永远不复现，线上快速切筛选就显示错数据。
  • fetch 之后只在 catch 里处理错误，忘了 4xx 与 5xx 不会 reject，必须自己判断响应状态。
  • 把 AbortController 的取消异常渲染成错误态，切换页面时界面闪出一个「请求失败」。
  • 依赖数组里放对象或数组字面量、内联函数，每次渲染都是新引用，effect 每次都重跑。
  • 给没有被 memo 包裹的子组件传 useCallback，纯粹增加开销；反过来给 memo 子组件传行内箭头函数，memo 直接失效。
  • 用 useMemo 保存必须长期存在的实例（图表对象、WebSocket）。React 不保证它不被丢弃，该用 useRef。
  • 给输入框的 value 加防抖，用户打字看到字符延迟出现。防抖应该加在请求或昂贵计算上，不是回显上。
  • 用 ref 标记跳过 StrictMode 的第二次 effect，把「缺少清理函数」这个真问题藏到生产环境。
  • 列表用 index 当 key 又放了非受控 input，用户输入的内容会跟着排序串到别人行上，详见站内前端框架原理篇。
