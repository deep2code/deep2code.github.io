Vue 3 响应式机制与选型

🏷️ Vue

Vue 3 的两个核心机制是基于 Proxy 的运行时响应式和基于模板的编译期优化，它们共同决定了 Vue 的使用方式和它相对 React 的差异。这篇讲机制与选型：响应式在哪些写法下会悄悄失效、依赖收集为什么可能漏掉、编译器做了什么让 diff 变便宜，以及团队该如何在 Vue 与 React 之间做决定，而不是介绍怎么写一个组件。

Composition API 解决的是代码组织问题

Options API 按选项类型组织代码：所有数据在 data 里，所有方法在 methods 里，所有监听在 watch 里。组件小的时候没问题，一旦一个组件承载三四个功能，同一个功能的代码就被强行切碎散落在四五个位置，读代码要在文件里反复跳转，复用只能靠 mixin，而 mixin 的命名冲突和来源不明是出了名的难查。Composition API 按关注点组织：一个功能的状态、派生值、监听、生命周期钩子写在一起，可以整段抽成一个组合式函数复用，且来源明确、返回值显式。

// 同一个组件的两种写法：分页列表 + 搜索关键字
// —— Options API：两个功能的代码被选项类型切碎 ——
export default {
  data() {
    return { page: 1, keyword: '', list: [], loading: false }; // 两个功能的状态混在一起
  },
  computed: {
    hasMore() { return this.list.length < this.total; },       // 属于分页
  },
  watch: {
    keyword() { this.page = 1; this.fetch(); },                 // 属于搜索
    page() { this.fetch(); },                                   // 属于分页
  },
  methods: {
    fetch() { /* 两个功能共用 */ },
    reset() { this.keyword = ''; this.page = 1; },
  },
  mounted() { this.fetch(); },
};

// —— Composition API：按关注点聚合，可整段抽走复用 ——
// usePagination.js
import { ref, computed } from 'vue';
export function usePagination(fetcher) {
  const page = ref(1);
  const list = ref([]);
  const total = ref(0);
  const loading = ref(false);
  const hasMore = computed(() => list.value.length < total.value);

  async function load() {
    loading.value = true;
    try {
      const res = await fetcher(page.value);
      list.value = res.items;   // 整体替换也能触发更新，这是 ref 的优势
      total.value = res.total;
    } finally {
      loading.value = false;    // 放 finally，否则请求失败后 loading 永远为真
    }
  }
  return { page, list, total, loading, hasMore, load };
}

响应式的实现细节：ref、reactive 与响应性丢失

reactive 返回的是对象的 Proxy，拦截的是对这个代理对象的操作。一旦你把属性值取出来放进普通变量，就再也没有拦截的机会——这就是「解构丢响应性」的全部原因，和框架有没有 bug 无关，是 JavaScript 的值语义决定的。ref 用一个带 value 的包装对象绕开这个限制：传递的是包装对象本身，读写都经过 value 这个 getter 和 setter，因此可以持有原始值，也可以整体替换。

import { reactive, ref, toRefs, isRef, shallowRef } from 'vue';

const state = reactive({ count: 0, user: { name: 'Ann' } });

// 陷阱 1：解构原始值属性 -> 断开
let { count } = state;
count++;              // state.count 不变，模板也不会更新
// 修法：
const { count: countRef } = toRefs(state); // 变成 ref，保持与源对象双向关联
countRef.value++;                          // state.count 同步变成 1

// 陷阱 2：整体替换 reactive 变量 -> 断开
let list = reactive([]);
list = await fetchList();   // list 现在指向一个普通数组，模板不再更新
// 修法 a：用 ref，整体替换没问题
const list2 = ref([]);
list2.value = await fetchList();
// 修法 b：保留同一个代理对象，只换内容
list.splice(0, list.length, ...(await fetchList()));

// 陷阱 3：ref 在模板里自动解包，在 JS 里必须写 .value
const n = ref(0);
// 模板中：{{ n }} 直接可用；但仅限「顶层」ref，嵌在对象里就不会自动解包
const wrap = { n };          // 模板里要写 wrap.n.value
console.log(n + 1);          // JS 里这样写得到 [object Object]1，必须 n.value + 1
if (isRef(n)) { /* 写通用工具函数时用它判断 */ }

// 陷阱 4：大对象与第三方实例不要深度代理
const chart = shallowRef(null);        // ECharts 实例：深度代理会遍历上万个内部属性
const bigTable = shallowRef(rows);     // 上万行数据：只在整体替换时触发更新，避免逐行建立依赖
// 若用 reactive(rows)，首次访问时递归代理 + 每个单元格建立依赖，内存与时间都会明显上涨
写法 是否仍然响应 失效原因 修法
解构 reactive 对象的原始值属性 否 值被拷贝，与 Proxy 断开 toRefs 或直接访问 state.xxx
解构 reactive 对象的嵌套对象属性 是 取出的仍是子对象的 Proxy 无需处理，但易误判，建议统一用 toRefs
给 reactive 变量整体赋新对象 否 变量指向普通对象 改用 ref，或用 splice 与 Object.assign 原地更新
把 ref.value 传进函数 否 只传了当时的值 传 ref 本身，或传 getter 函数
ref 嵌在普通对象里用于模板 需手写 value 自动解包只作用于顶层 顶层暴露，或用 reactive 包一层
reactive 包裹 ECharts 或地图实例 是但严重拖慢 递归代理第三方对象的全部内部属性 shallowRef 或 markRaw
上万行表格数据用 reactive 是但内存与耗时大涨 逐字段建立依赖 shallowRef 加整体替换，配合列表虚拟化

依赖收集发生在运行时：条件分支里的依赖可能收不到

这是 Vue 响应式最隐蔽的一个坑。依赖不是静态分析出来的，而是effect 实际运行时读到哪个属性就订阅哪个属性。如果这一轮因为短路或提前返回没有访问某个属性，那这一轮就没有对它的订阅，之后单独改它不会触发任何反应。而每次重新运行 effect 都会重新收集，所以症状是「改 A 没反应，先改 B 再改 A 就好了」——非常难定位。

import { reactive, watchEffect, watch, computed } from 'vue';
const state = reactive({ enabled: false, keyword: '', page: 1 });

// 坏例子：短路导致 keyword 在首轮没有被收集
watchEffect(() => {
  if (!state.enabled) return;          // 提前返回，下面一行没执行
  search(state.keyword);               // 所以首轮不订阅 keyword
});

// 修法 a：把所有需要监听的值在分支之前先读一遍（显式建立依赖）
watchEffect(() => {
  const { enabled, keyword } = state;  // 这里的解构只是读取，会正常 track
  if (!enabled) return;
  search(keyword);
});

// 修法 b（更推荐）：用 watch 显式声明监听源，依赖不再依赖运行路径
watch(
  () => [state.enabled, state.keyword], // 源函数每次都会完整求值
  ([enabled, keyword], [prevEnabled]) => {
    if (!enabled) return;
    if (enabled !== prevEnabled) resetScroll(); // watch 才能拿到旧值
    search(keyword);
  },
  { immediate: true }                  // watch 默认不立即执行，需要时显式打开
);

// 顺带一个常见错误：computed 里写副作用
// 错：computed 会被缓存，副作用执行次数不可预测，SSR 时更混乱
const bad = computed(() => { track('view'); return state.page * 10; });
// 对：computed 只做纯推导
const good = computed(() => state.page * 10);

模板编译优化：Vue 相对 React 的结构性优势

模板是受约束的语法，编译器可以做静态分析，这是 JSX 做不到的——JSX 是完整的 JavaScript 表达式，编译器无法假设任何结构。Vue 3 编译器由此产出三类优化：静态提升把永不变化的节点提到渲染函数外部，只创建一次并永久复用；patch flag 在动态节点上标注「哪一类会变」，运行时只比较被标注的部分，比如只比较 class 而完全跳过属性和子节点；block tree 把一棵模板里的动态节点收集成扁平数组，更新时不再递归整棵树，而是直接遍历这个数组。

这解释了一个常见疑问：为什么 Vue 不需要写 memo。因为「哪里会变」在构建期就已经确定了，运行时不必靠开发者提示。代价是模板的表达能力弱于 JSX：动态性极强的结构（根据配置生成任意层级）在模板里写起来别扭，此时可以退回渲染函数或 JSX，但也就同时失去了这些编译优化。

v-if 与 v-for、v-model 的实际语义

Vue 与 React 的团队选型

这不是「谁更好」的问题，两者的性能在真实业务中的差距远小于「有没有做列表虚拟化」带来的差距。决策依据应该是团队技能、招聘市场与要用的组件库生态。

反模式速查

反模式 表面症状 根因 正确做法
解构 reactive 对象 改了值但界面不更新 原始值被拷贝，脱离 Proxy 拦截 toRefs 或直接访问属性
在 computed 里写副作用 埋点重复或丢失，SSR 行为不一致 computed 有缓存，执行次数不可预测 副作用放 watch，computed 只做纯推导
用 watch 做本该 computed 的派生 两份数据，偶尔不一致，多一轮更新 把推导写成了同步流程 能推导出来的值一律用 computed
对大对象开 deep watch 输入或滚动明显卡顿 递归建立依赖并深比较 只监听需要的字段，或改用 shallowRef 加整体替换
在 await 之后注册生命周期钩子 钩子静默不执行 已脱离当前组件实例的同步上下文 所有钩子与 inject 在 setup 同步阶段完成
把 ECharts 实例放进 reactive 首次渲染卡住数百毫秒 递归代理第三方对象的全部内部结构 shallowRef 或 markRaw

最容易踩的坑

❌
避坑清单
  • 解构 reactive 对象后修改变量，源对象完全不变，界面「莫名不更新」；需要解构就先过一遍 toRefs。
  • 给 reactive 变量整体赋新值（请求回来后 list = res.data），响应性直接断开；这类场景一律用 ref。
  • 在 JS 里忘写 ref 的 value，得到的是包装对象，字符串拼接后出现 object Object 却不报错。
  • 以为模板里所有 ref 都自动解包。只有顶层绑定会解包，嵌在普通对象里的 ref 仍要写 value。
  • watchEffect 里提前 return 或用短路运算，某些依赖首轮收集不到，表现为「改 A 不生效，先改 B 再改 A 才生效」。
  • 在 computed 里发请求或改其他状态。缓存机制会让副作用执行次数变得不可预测。
  • 用 watch 加一个额外 ref 去存派生数据，两份真源迟早不一致，能推导的值一律用 computed。
  • 对整个大对象开 deep watch，且以为回调里能拿到不同的旧值——深度监听时新旧值是同一个引用。
  • 把 ECharts、地图、播放器实例放进 reactive，递归代理上万个内部属性，首屏直接卡住。
  • 同一个元素上同时写 v-if 与 v-for，Vue 3 里 v-if 先执行，根本访问不到循环变量。
  • v-for 用 index 当 key，列表排序后子组件状态和用户输入串到别的行。
  • 在 setup 的 await 之后调 onMounted 或 inject，静默失效且没有任何报错。
  • 子组件里直接修改 props 实现双向绑定，Vue 会告警且值会在父组件下次更新时被覆盖。
