前端工程化：构建、依赖与发布

🏷️ 前端工程化

前端工程化听起来像一堆工具的集合，实际上它只解决四个问题：模块化与依赖管理（代码怎么拆、依赖怎么装得可重现）、构建与产物优化（源码怎么变成浏览器能高效加载的文件）、质量保障（错误怎么在合并前被拦住）、发布与回滚（产物怎么安全地换到线上并能退回去）。后端工程师对这四件事本来就熟，差异在于前端的运行环境不在你手里：产物被下载到成千上万台设备上执行，旧版本会在用户浏览器里继续存活几十分钟。这篇讲的就是这个差异带来的那些工程决策。

构建工具的代际变化：开发期到底要不要打包

三代构建工具的核心差异只有一句话：开发阶段是否需要先把整个依赖图打包出来。Webpack 必须先打包才能提供服务，所以启动时间与项目规模成正比；Vite 利用浏览器原生 ESM，开发时按请求转译单个文件，启动时间与项目规模几乎无关，热更新只失效改动的那个模块；Rspack 与 Turbopack 走的是另一条路——保持打包模型但用 Rust 重写，靠并行与缓存把速度提上来，代价换成了对 Webpack 生态的兼容程度。

依赖管理：可重现构建才是底线

「昨天能构建今天不行」几乎总是版本范围导致的：package.json 里的插入号范围允许安装新的次版本与补丁版本，任何一个间接依赖发新版都可能改变行为。三条纪律：lock 文件必须入库、CI 用严格按 lock 安装且不修改 lock 的命令（npm 用 ci，pnpm 加 frozen-lockfile）、Node 版本固定并写进仓库。pnpm 额外解决的是幽灵依赖：npm 与 yarn 把间接依赖平铺到顶层，导致代码可以导入没有声明过的包，直到某天依赖树变化才突然失败。

维度 npm yarn（经典版） pnpm
node_modules 结构 扁平提升 扁平提升 符号链接严格树，包体存全局内容寻址仓库
幽灵依赖 可能，未声明也能导入 可能 基本不可能，未声明导入直接失败
磁盘占用 每个项目一份 每个项目一份 相同版本全局仅一份，靠硬链接
安装速度 中 中 快，尤其多项目复用缓存时
CI 严格安装命令 npm ci yarn install 加 immutable 参数 pnpm install 加 frozen-lockfile 参数
workspace 支持 有 有 有，并可强制内部包用 workspace 协议引用
已知摩擦点 —— —— 假设扁平结构的旧工具需要配置提升白名单

packages:
  - "apps/*"        # 可部署的应用
  - "packages/*"    # 内部共享库：UI 组件、工具函数、生成的接口类型

#   "dependencies": { "@acme/ui": "workspace:*" }

# .npmrc：几个会直接影响构建稳定性的开关
# strict-peer-dependencies=true   # peer 不匹配时失败，而不是留到运行时报错
# save-exact=true                 # 保存精确版本，构建工具链尤其需要
# engine-strict=true              # Node 版本不符直接拒绝安装
# public-hoist-pattern[]=*eslint* # 少数假设扁平结构的工具需要提升

#   适合：多个应用共享同一套组件库与类型，且需要原子提交（改库同时改用法）
#   不适合：两个几乎不相关的项目，只是为了「代码放一起方便」
#   代价：需要任务编排与缓存（Turborepo 或 Nx），否则 CI 会全量跑所有包

产物优化：分包、摇树与体积预算

产物优化的目标不是「总体积最小」，而是首屏需要下载和解析的 JS 最少。解析与执行 JS 的成本在低端设备上远高于下载成本，这也是为什么「加了 CDN 还是慢」。加载与缓存层面的量化对照（缓存头、压缩、HTTP/2 与 /3、资源提示）详见站内《前端性能：加载与缓存》一篇，这里只讲构建侧能做的事。

手段 生效前提 典型收益 失效场景
按路由代码分割 路由用动态导入 首屏 JS 常能降一半以上 路由组件在顶层被静态导入一次就全部合并回主包
tree shaking 依赖提供 ESM 产物，且包标注 sideEffects 去掉未引用导出 CommonJS 依赖、整体导入命名空间、模块顶层有副作用
第三方库分包 手动配置 chunk 划分 依赖不变时长缓存命中 把所有依赖塞进一个 vendor 包，任一升级导致全量失效
按需引入组件库 库支持子路径导入或有插件 大型 UI 库能省数百 KB 从包根整体导入，或样式文件仍然全量引入
替换重量依赖 有轻量替代品 moment 换 dayjs、lodash 换按函数导入 替换后行为差异（时区、深拷贝语义）需要回归测试
体积预算卡口 CI 中比对阈值 唯一能防止体积缓慢膨胀的办法 只在本地看分析报告，没人会主动去看
polyfill 按目标裁剪 明确 browserslist 目标现代浏览器可省几十 KB 目标写得过宽，为极少数旧浏览器让所有人付费 
// vite.config.ts：分包策略 + 动态导入失败兜底 + 体积预算
import { defineConfig } from 'vite';

export default defineConfig({
  build: {
    // 超过阈值就在构建日志里告警，配合 CI 检查形成卡口
    chunkSizeWarningLimit: 600,
    rollupOptions: {
      output: {
        // 按「更新频率」分包，而不是把所有依赖塞进一个 vendor
        manualChunks(id) {
          if (!id.includes('node_modules')) return;
          if (id.includes('react') || id.includes('scheduler')) return 'framework';
          if (id.includes('echarts') || id.includes('zrender')) return 'charts';
          if (id.includes('lodash') || id.includes('dayjs')) return 'utils';
          return 'vendor';
        },
        // 内容哈希：内容不变则文件名不变，可以长期强缓存
        entryFileNames: 'assets/[name].[hash].js',
        chunkFileNames: 'assets/[name].[hash].js',
        assetFileNames: 'assets/[name].[hash][extname]',
      },
    },
  },
});

#!/usr/bin/env bash
# CI 体积预算卡口：把「体积只能降不能涨」变成流水线规则
set -euo pipefail

BUDGET_KB=350          # 首屏入口 JS 预算（gzip 后），按项目实际水位设定
npm run build

# 找到入口 chunk，统计 gzip 后体积
ENTRY=$(ls dist/assets/index.*.js | head -n 1)
SIZE_KB=$(gzip -c "$ENTRY" | wc -c | awk '{print int($1/1024)}')

echo "入口 JS gzip 体积: ${SIZE_KB} KB / 预算 ${BUDGET_KB} KB"
if [ "$SIZE_KB" -gt "$BUDGET_KB" ]; then
  echo "::error::体积超出预算，请检查新引入的依赖或分包配置"
  # 排查命令：npx vite-bundle-visualizer  或  npx source-map-explorer "$ENTRY"
  exit 1
fi

# 说明：预算要卡「首屏必须下载的入口与共享 chunk」，
# 懒加载路由单独设更宽的阈值；只看总体积会掩盖首屏膨胀。

环境变量：构建时注入与后端的一次构建多处部署冲突

前端默认做法是构建时注入：变量在打包阶段被替换成字面量，零运行时成本，还能参与摇树（把某个环境的分支整段删掉）。代价是一份产物只对应一个环境——测试环境验证过的那份产物不能原样提升到生产，必须重新构建一次；这和后端习惯的「构建一次、部署到任何环境」直接冲突，也意味着「测过的东西」和「上线的东西」严格来说不是同一个产物。要么接受这点（多数团队如此），要么把配置改成运行时读取。

方式 一份产物多环境 运行时成本 能参与摇树 适合放什么
构建时注入（define 或 import.meta.env） 不能 零 能 功能开关、构建版本号、编译期常量
独立配置文件（不缓存的 config.js） 能 一次极小请求，阻塞启动 不能 接口地址、租户标识、上报开关
服务端渲染 HTML 时注入全局变量 能 零额外请求 不能 同上，前提是 HTML 由服务端动态产出
启动时调用配置接口 能 一次网络往返，首屏变慢 不能 需要动态下发且允许延迟的配置
把密钥放进任意前端变量 —— —— —— 绝对不行：产物对用户完全可见，等于公开

发布：新旧资源共存与白屏事故

这是前端发布最容易被忽略、又最容易被用户投诉的坑。带内容哈希的文件名意味着每次发布 chunk 名都变了；而用户浏览器里可能还停留着十分钟前甚至几小时前的那份 HTML。如果发布时把目录清空只留新文件，这些用户一旦触发路由跳转或打开懒加载的弹窗，动态导入会请求一个已经不存在的文件，表现为白屏或点了没反应，而且刷新之后就好了——典型的「无法复现」。

资源类型 文件名策略 缓存策略 发布时如何处理
index.html 固定名 不缓存或极短缓存，必须回源校验 最后一步更新，它是版本切换的开关
带内容哈希的 JS 与 CSS 名字含内容哈希 长期强缓存并标记不可变 先上传，保留旧版本，不要清空目录
图片与字体 名字含哈希 长期强缓存 同上
运行时配置 config.js 固定名 不缓存 按环境生成，不随产物版本变化
Service Worker 脚本 固定名 不缓存 缓存策略写错会让旧版本长期存活，回滚也无效
source map 名字含哈希 —— 不要公开暴露，上传到错误监控平台即可

动态导入失败的兜底写法

给路由的动态导入包一层重试：捕获加载错误后先重试一次（可能只是网络抖动），仍失败则判定为版本已更新，用一个会话级标记防止无限刷新，然后调用页面重载拿到新的 HTML。这段代码不到二十行，能消掉一整类线上白屏工单。

微前端的适用边界

只有一个理由足够强：多个团队需要在同一个页面容器里各自独立发布，互不阻塞。其他动机（代码量大、想升级框架、想同时用两个框架）通常撑不起它的代价。

诉求 更便宜的方案 需要微前端吗 微前端的代价
首屏太大 按路由代码分割 不需要 ——
多个应用共享组件与类型 monorepo 加内部包 不需要 ——
老系统渐进式重写 按页面切分，用链接跳转到新应用 通常不需要 ——
多团队在同一页面内并行发布 无 需要 运行时集成、样式隔离、多份框架运行时、跨应用路由与状态协同
同一页面必须混用 React 与 Vue Web Components 封装 看情况 体积翻倍，调试栈跨应用，问题定位成本高
想尝试新技术 在独立页面或内部工具里试 不需要 为尝鲜付长期架构税，最不值当

最容易踩的坑

❌
避坑清单
  • lock 文件不提交，或 CI 用普通 install 而不是严格按 lock 安装，于是同一份代码在不同时间构建出不同产物。
  • 依赖里导入了没在 package.json 声明的包，在 npm 下靠扁平提升侥幸可用，换成 pnpm 或依赖树一变就构建失败。
  • Node 版本不固定。同一份 lock 在不同大版本 Node 下装出的原生模块并不一致，本地能跑 CI 报错。
  • 发布时把静态资源目录清空。停留在旧 HTML 的用户请求已删除的 chunk，白屏且无法复现。
  • 给 index.html 配了长缓存。它是版本切换的开关，一旦被缓存，发布和回滚都会失效。
  • 动态导入没有失败兜底。一次 CDN 抖动或一次发布就让用户卡在空白页面上，而错误监控里只看到一条模块加载失败。
  • Service Worker 的缓存策略写错，旧版本在用户设备上长期存活，回滚也救不回来，这是最难处理的一类事故。
  • 把所有第三方依赖塞进一个 vendor chunk，升级一个小工具库导致全部用户重新下载几百 KB。
  • 以为 tree shaking 总会生效。依赖是 CommonJS、包没标注 sideEffects、或代码整体导入命名空间时，它完全不工作。
  • 用构建时注入的变量却指望一份产物多环境复用，产物发到生产仍然指向测试接口。
  • 把密钥、内部地址写进前端环境变量。产物对用户完全可见，等同于公开发布。
  • 没有体积预算，只在本地偶尔看分析报告，半年后首屏体积翻倍且无从追溯。
  • source map 直接发到公网，源码与内部逻辑一起泄漏；应只上传给错误监控平台。
