前端工程化

🏷️ 前端工程化

一、为什么需要前端工程化

十年前我写前端就是"HTML + 引 jQuery"，刷新一下看效果。现在一个中型项目的工具链能列一长串：包管理器、构建工具、类型检查、Lint、单测、E2E、CI/CD、容器化。我在 10 人团队维护过一个 10 万行的前端 monorepo，没有工程化根本玩不转——谁装错依赖版本、谁漏了类型，全靠人肉兜底，一周能出三次线上事故。

这篇我只讲三件我每天都在用的：Vite（构建）、pnpm（包管理）、Monorepo（多包组织）。

二、核心工具：Vite、pnpm、Monorepo 各自解决什么

2.1 Vite：为什么比 Webpack 快

Vite 的快来自一个简单洞察：开发环境不需要打包。浏览器原生支持 ES Module，Vite 直接把源文件按 ESM 甩给浏览器，只有被请求的文件才编译。启动时间从"打包整个依赖图"变成"启动一个服务器"。我从 Webpack 4 迁到 Vite 的那个下午，冷启动从 40 秒降到 1 秒，团队整个都精神了。生产构建时 Vite 还是用 Rollup 打包，产物体积没吃亏。

2.2 pnpm：磁盘高效的包管理器

npm/yarn 的 node_modules 是嵌套结构——同一个 React 可能被复制好几份，我最早一个项目装完依赖 node_modules 干到 1.2GB。pnpm 用内容寻址存储 + 硬链接：全局 store 只存一份，项目里硬链接引用，我那 1.2GB 直接缩到 300MB。

我踩过的幽灵依赖坑

pnpm 还强制"严格依赖"：你只能 import package.json 里声明的包。我早年用 npm 时，代码里偷偷 import 了一个没声明的工具函数包（它是别人的间接依赖），上游一升级把它删了，我的线上页面直接白屏。pnpm 从根上杜绝了这种幽灵依赖——你没声明的包，根本 import 不到。

2.3 Monorepo：一个仓库管多个包

当你有一个组件库、一个 React 应用、一个 Vue 应用、一个工具函数库，它们之间有共享代码。把它们放在一个仓库里，统一版本、统一 CI、互相引用源码而不是发 npm，这就是 Monorepo。我所在团队从「多仓库互相发版本」迁到 Monorepo 后，改一个工具函数从「发版 → 各应用升级」变成直接改源码，两周的活一天干完。

方案冷启动node_modules 体积幽灵依赖我的推荐
Webpack + npm30-60s大（嵌套/平铺）有老项目维护
Vite + npm1-3s大有不推荐组合
Vite + pnpm1-3s小（硬链接）无我的默认组合
Vite + pnpm + Turborepo1-3s小无多包 Monorepo

关键设计：开发态追求"秒级启动 + 热更新"，生产态追求"产物最小 + 长期缓存"，两者用不同的优化目标。Monorepo 则把跨包依赖从"npm 版本锁定"变成"源码直接引用"，让重构和类型同步变得无痛。

四、配置实战

4.1 初始化 Monorepo 与 pnpm workspace

# 安装 pnpm（如未安装）
npm install -g pnpm

# 初始化仓库
mkdir my-monorepo && cd my-monorepo
pnpm init

# 安装共享的 TypeScript / ESLint
pnpm add -Dw typescript eslint prettier

根目录 pnpm-workspace.yaml：

packages:
  - "apps/*"
  - "packages/*"

根目录 package.json 用 workspaces 字段声明脚本：

{
  "name": "my-monorepo",
  "private": true,
  "scripts": {
    "dev": "pnpm --filter web dev",
    "build": "pnpm -r build",
    "lint": "eslint . --ext .ts,.tsx",
    "test": "pnpm -r --parallel test"
  },
  "packageManager": "pnpm@9.0.0"
}

4.2 Vite 应用配置

// apps/web/vite.config.ts
import { defineConfig } from "vite";
import react from "@vitejs/plugin-react";
import path from "node:path";

export default defineConfig({
  plugins: [react()],
  resolve: {
    alias: {
      "@ui": path.resolve(__dirname, "../../packages/ui/src"),
      "@utils": path.resolve(__dirname, "../../packages/utils/src"),
    },
  },
  build: {
    rollupOptions: {
      output: {
        manualChunks: {
          vendor: ["react", "react-dom"],
        },
      },
    },
  },
});

4.3 共享包配置

// packages/ui/package.json
{
  "name": "@my/ui",
  "version": "0.1.0",
  "type": "module",
  "main": "./src/index.ts",
  "types": "./src/index.ts",
  "peerDependencies": {
    "react": ">=18"
  }
}

注意 main 直接指向 src/index.ts——在 Monorepo 开发态不需要构建，应用直接消费 TypeScript 源码，类型同步即时生效。

五、实战：Turborepo 任务编排

当包数量变多，按拓扑顺序构建、缓存已完成任务就很关键。Turborepo 是最流行的方案：

// turbo.json
{
  "$schema": "https://turbo.build/schema.json",
  "pipeline": {
    "build": {
      "dependsOn": ["^build"],
      "outputs": ["dist/**"]
    },
    "test": {
      "dependsOn": ["build"]
    },
    "dev": {
      "cache": false,
      "persistent": true
    }
  }
}
# 只构建受影响的包及其依赖
npx turbo run build --filter=web...

# 缓存命中后秒级完成（第二次构建）
npx turbo run build

六、最佳实践

  • 包管理器锁死版本：用 packageManager 字段 + corepack，确保团队所有人用同一版 pnpm。
  • 严格依赖：开启 pnpm strict-peer-dependencies，不要 import 未声明的包。
  • 共享 ESLint / Prettier 配置：在根目录放一份，各包继承，避免风格分裂。
  • 环境变量用 .env 文件：Vite 支持 .env、.env.local、.env.[mode]，不要把密钥硬编码。
  • 产物分包策略：把 React/Lodash 等大依赖拆成独立 chunk，利用浏览器缓存。但不要过度分包——太小的 chunk 会增加 HTTP 请求。
  • CI 里用 pnpm store 缓存：GitHub Actions 里缓存 ~/.pnpm-store，安装时间从分钟级降到秒级。

七、常见问题 FAQ

Q1：Vite 真的能替代 Webpack 吗？

新项目几乎可以。Vite 在 HMR 速度、配置简洁度上全面领先。但有两类坑我踩过：

  • 依赖某些老牌 loader 或复杂 SSR 定制的老项目，迁移要逐个验证；
  • 需要 webpack 特有的 Module Federation 时，Vite 得用别的方案。

除此之外 Vite 2+ 能覆盖 90% 业务场景，包括 SSR、Library 模式、Electron。我现在起新项目默认 Vite。

Q2：pnpm 的幽灵依赖问题是什么？

npm/yarn 会把所有依赖（包括间接依赖）平铺到 node_modules，导致你能 import 一个没在 package.json 声明的包——它是别人的间接依赖。一旦上游升级把它删了，你的代码就炸。pnpm 用符号链接结构，只有你声明的包才在顶层，从根上杜绝。

Q3：Monorepo 会不会让 CI 变慢？

不会，前提是用对工具。Turborepo/Nx 帮我做三件事：

  • 增量构建：只构建受影响的包；
  • 远程缓存：CI 之间共享构建产物；
  • 并行执行：无依赖的任务同时跑。

我手上一个几百个包的 Monorepo，CI 时间从 30 分钟压到 3 分钟。反模式是「每次全量构建所有包」——那才会慢。

八、总结

我用下来的体会：前端工程化不是炫技，是把重复的手动操作自动化，把隐性的约定显性化。Vite 解决"开发体验"，pnpm 解决"依赖一致性"，Monorepo + Turborepo 解决"多包协作效率"。这三者组合就是我 2024-2026 起新项目的默认技术栈。下一篇看工程化之上的应用层：性能优化与状态管理。
