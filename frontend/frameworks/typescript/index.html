🏷️ TypeScript

一、为什么 JavaScript 需要 TypeScript

JavaScript 是动态弱类型：变量运行时才定类型，同一个函数入参既能传字符串又能传数字。小脚本里这是灵活，在中大型工程里就是灾难——接口字段拼错、返回值假设错误，这些 bug 往往要到用户点了按钮、白屏了才发现。我早年用纯 JS 写过一个后台系统，一个字段名打错，线上跑了三天才被用户反馈。TS 的核心价值就是把类型检查从运行时提前到编译时，让 IDE 敲代码瞬间标红。

而且 TS 早就不是"可选增强"了：React/Vue 官方脚手架默认生成 TS 项目，npm 上 90% 热门库都带 d.ts，VS Code 的补全、跳转、重构全靠类型信息。我现在招人简历上写"熟练 TypeScript"是基本门槛，不是加分项。

二、核心概念：类型系统不是枷锁，是文档

2.1 基础类型与类型注解

TS 在 JS 语法之上增加了类型注解。变量、函数参数、返回值都可以标注类型，编译器据此做静态检查：

// 基础类型
const username: string = "junjunyi";
const age: number = 30;
const isActive: boolean = true;
const tags: string[] = ["ts", "react"];

// 函数类型注解：参数与返回值都要标
function greet(name: string): string {
  return `Hello, ${name}!`;
}

// 可选参数与默认值
function createUser(name: string, role: "admin" | "user" = "user") {
  return { name, role };
}

2.2 接口与类型别名

interface 和 type 是描述对象结构的两种方式。我日常的分工是：对象契约用 interface，联合/交叉/元组用 type。

特性interfacetype
声明合并（同名自动合并）支持不支持
extends 继承支持交叉类型 &
联合/交叉/元组不支持支持
我的使用场景对象、组件 props、API 契约工具类型、事件 map
 
interface User {
  id: number;
  name: string;
  email?: string;          // 可选属性
  readonly createdAt: Date; // 只读
}

type UserRole = "admin" | "editor" | "guest";

// 交叉类型：把多个类型合并
type WithTimestamp = { updatedAt: Date };
type UserWithTs = User & WithTimestamp;

// 工具类型：Partial / Pick / Omit 是日常高频
type UserDraft = Partial<User>;
type UserSummary = Pick<User, "id" | "name">;

2.3 泛型：类型层面的函数参数

泛型让你写出"类型可复用"的代码——像函数参数接收值一样，泛型参数接收类型。一个经典例子是 API 请求封装：

// 定义泛型响应包装
interface ApiResponse<T> {
  code: number;
  message: string;
  data: T;
}

// 泛型函数：传入什么类型，返回什么类型
async function request<T>(url: string): Promise<ApiResponse<T>> {
  const res = await fetch(url);
  return res.json();
}

// 使用时指定 T，TS 自动推导后续类型
interface Article { id: number; title: string; }
async function loadArticles() {
  const resp = await request<Article[]>("/api/articles");
  // resp.data 自动是 Article[]，map 里有完整提示
  return resp.data.map(a => a.title);
}

2.4 类型收窄：让 TS 学会"缩小范围"

联合类型（A | B）在运行时具体是哪个？TS 通过 typeof、instanceof、自定义判别函数来"收窄"类型，这是写出安全分支逻辑的关键：

type Shape =
  | { kind: "circle"; radius: number }
  | { kind: "square"; size: number };

function area(s: Shape): number {
  switch (s.kind) {
    case "circle":
      return Math.PI * s.radius ** 2; // s 自动收窄为 circle
    case "square":
      return s.size ** 2;             // s 自动收窄为 square
  }
}

三、架构与原理：TS 编译器做了什么

很多人以为 TS 只是"给 JS 加类型然后编译掉"，但它的内部流水线其实相当精巧。理解这个流水线，才能理解为什么"改了类型却没报错""tsc 比 webpack 还慢"等问题：

flowchart LR SRC[.ts/.tsx 源码] --> SCAN[词法扫描
Scanner] SCAN --> PARSE[语法解析
Parser → AST] PARSE --> BIND[绑定模块
Binder: 建立符号表] BIND --> CHECK[类型检查
Checker: 推导/校验] CHECK --> EMIT[代码生成
Emitter: 输出 .js + .d.ts] EMIT --> JS[JavaScript 产物] EMIT --> DTS[类型声明 .d.ts] style CHECK fill:#8b5cf6,color:#fff style EMIT fill:#10b981,color:#fff

关键点：类型检查和代码生成是两阶段的。类型检查阶段完全不关心运行时值，只分析类型关系；代码生成阶段把类型注解擦除，输出纯 JS。这意味着 TS 的类型系统是"结构化"的——不关心你叫什么类名，只关心结构是否匹配，这就是鸭子类型在静态语言里的实现。

四、安装与配置

# 全局或项目内安装
npm install -D typescript @types/node

# 初始化 tsconfig.json
npx tsc --init

一份生产级 tsconfig.json 关键配置：

{
  "compilerOptions": {
    "target": "ES2022",
    "module": "ESNext",
    "moduleResolution": "bundler",
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "exactOptionalPropertyTypes": true,
    "noImplicitOverride": true,
    "esModuleInterop": true,
    "skipLibCheck": true,
    "forceConsistentCasingInFileNames": true,
    "outDir": "./dist",
    "rootDir": "./src"
  },
  "include": ["src/**/*"],
  "exclude": ["node_modules", "dist"]
}

strict: true 是最重要的开关，它一次性打开 strictNullChecks、noImplicitAny 等八项严格检查。新项目务必打开，否则 TS 的价值损失一半。

别用 any 糊弄编译器

我见过太多人一报错就 as any，那 TS 跟 JS 没区别了。正确姿势是用 unknown——它强制你在使用前收窄类型，等于在说"我暂时不知道类型，用之前得查清楚"。我 code review 看到 : any 基本直接打回。

五、实战：用 TS 写一个类型安全的事件总线

下面是一个真实可运行的类型安全事件总线示例，展示泛型、keyof、映射类型的综合运用：

type EventMap = {
  "user:login": { userId: string; timestamp: number };
  "user:logout": { userId: string };
  "order:paid": { orderId: string; amount: number };
};

type Handler<T> = (payload: T) => void;

class TypedEventBus<Events extends Record<string, unknown>> {
  private handlers = new Map<keyof Events, Set<Handler<Events[keyof Events]>>>();

  on<K extends keyof Events>(event: K, handler: Handler<Events[K]>): () => void {
    if (!this.handlers.has(event)) this.handlers.set(event, new Set());
    this.handlers.get(event)!.add(handler as Handler<Events[keyof Events]>);
    return () => this.off(event, handler);
  }

  off<K extends keyof Events>(event: K, handler: Handler<Events[K]>): void {
    this.handlers.get(event)?.delete(handler as Handler<Events[keyof Events]>);
  }

  emit<K extends keyof Events>(event: K, payload: Events[K]): void {
    this.handlers.get(event)?.forEach(h => h(payload));
  }
}

// 使用：事件名和 payload 类型完全绑定
const bus = new TypedEventBus<EventMap>();
const off = bus.on("order:paid", (p) => {
  console.log(`订单 ${p.orderId} 支付 ${p.amount} 元`);
});
bus.emit("order:paid", { orderId: "A100", amount: 99 }); // OK
// bus.emit("order:paid", { orderId: "A100" });         // 编译报错：缺少 amount

六、最佳实践

  • 始终开启 strict 模式：strictNullChecks 能消灭约 40% 的线上空指针类 bug。
  • 用 unknown 而不是 any：any 会关闭类型检查，unknown 强制你收窄后再用，是"我暂时不知道类型"的正确写法。
  • 避免过度类型体操：类型应该服务于代码可读性，不是炫技。复杂的条件类型嵌套超过 3 层就该考虑重构。
  • 善用类型推导：不要在每个变量上都写类型，让 TS 自己推。只在函数返回值、导出 API、对象字面量歧义处标注。
  • 为第三方库写 d.ts：如果库没有类型声明，自己写 declare module 声明，比在业务代码里到处 as 强。
  • 用 ESLint + typescript-eslint：配合 @typescript-eslint/no-unnecessary-type-assertion 等规则，捕获多余的类型断言。

七、常见问题 FAQ

Q1：TS 写起来太重了，小项目有必要上吗？

如果是一两百行的脚本或原型，JS 完全够用。但一旦涉及多人协作、接口对接、长期维护，TS 的类型文档价值会迅速超过"多写几个冒号"的成本。现在 Vite/CRA 脚手架都默认 TS，迁移成本已经很低。

Q2：为什么我明明传了正确的值，TS 还是报类型错误？

最常见原因是"对象字面量 freshness 检查"——直接传字面量给函数时 TS 会严格检查多余属性。把对象先赋值给一个变量再传，或者在函数参数里用索引签名放宽。另外注意 as 断言不会做类型转换，只欺骗编译器，运行时类型不变。

Q3：tsc 编译很慢怎么办？

大型项目我按这个顺序优化：

  • 增量编译：开 --incremental，只重新检查改动文件；
  • 类型检查和打包分离：Vite/esbuild 只转译不检查，类型检查单独跑 tsc --noEmit；
  • 跳过库检查：skipLibCheck 跳过 node_modules 类型；
  • 终极方案：用 Go 重写的 tsgo，我 50 万行项目从 40 秒降到 2 秒，提升 10 倍以上。

八、总结

TypeScript 的本质是在 JavaScript 之上构建了一层静态类型契约：它不改变运行时行为，但把大量错误从"用户遇到"提前到"开发者在 IDE 里看到"。掌握类型注解、接口、泛型、类型收窄这四块核心，就能覆盖 90% 的日常开发场景。进阶方向是条件类型、模板字面量类型、infer 推断——这些是写工具库和高级抽象的利器。下一篇我们将进入 React 18+，看类型系统如何与组件模型结合。
