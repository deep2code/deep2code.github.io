TypeScript 的类型边界与工程落地

🏷️ TypeScript

TypeScript 的核心价值是把一类运行时错误提前到编译期：字段拼错、参数顺序反了、忘处理某个分支、把可能为空的值当对象用。对后端工程师来说它的语法不难，真正需要建立的是两个认知：类型在运行时完全不存在，以及类型的正确性依赖于你在系统边界上说的是不是真话。这篇只谈这两件事的工程后果，不做语法教程。

最关键的一条：类型只在编译期存在

编译产物里没有任何类型信息，也不会生成一行校验代码。给一段 JSON 标注类型，本质上只是你对数据来源的单方面断言。后端改了字段名、某字段在特定条件下返回 null、网关超时时返回了另一种错误结构、缓存里存着半年前旧版本的数据——编译器一概不知道，代码会带着「我确定它是 User」的信念一路跑下去，最后在某个访问属性的地方抛出错误，而堆栈指向的位置离真正的错误源可能隔着好几层。

// 反面写法：断言式「类型安全」——编译期漂亮，运行时裸奔
interface User { id: number; name: string; email: string; role: 'admin' | 'user'; }

async function getUserBad(id: number): Promise<User> {
  const res = await fetch('/api/users/' + id);
  // as 只是让编译器闭嘴，没有任何检查：
  // 后端把 id 改成字符串、email 变成 null、role 多了 'guest'，这里全都一声不响
  return (await res.json()) as User;
}

// 正确写法：在信任边界做运行时校验，并让类型从 schema 推导（单一真源）
import { z } from 'zod';

const UserSchema = z.object({
  id: z.number().int(),
  name: z.string().min(1),
  // 后端可能给 null，就如实声明，把处理空值的责任交给编译器
  email: z.string().email().nullable(),
  role: z.enum(['admin', 'user']),
});
// 类型由 schema 推导出来，schema 一改类型跟着改，不会出现两份定义漂移
export type User = z.infer<typeof UserSchema>;

export async function getUser(id: number): Promise<User> {
  const res = await fetch('/api/users/' + id);
  if (!res.ok) throw new Error('HTTP ' + res.status); // fetch 不会因 4xx 5xx 而 reject
  const json: unknown = await res.json();            // 显式标成 unknown，禁止直接使用

  const parsed = UserSchema.safeParse(json);
  if (!parsed.success) {
    // 关键收益：错误在边界暴露，且能指出是哪个字段不符合预期
    console.error('用户接口响应不符合约定', parsed.error.issues);
    throw new Error('响应格式非法');
  }
  return parsed.data;
}

// 值得校验的边界（而不是每个函数都校验）：
// HTTP 响应、WebSocket 消息、localStorage 与 URL 参数、表单提交、
// 第三方 SDK 回调、跨窗口 postMessage、以及所有 JSON.parse 的结果

as 断言 关闭该处检查 无 静默通过，错误在远处才暴露 仅用于确实比编译器知道更多的极少数情况
非空断言感叹号 声称一定不为空 无 真为空时抛出属性访问错误 初始化顺序确定的私有代码，慎用
自定义类型守卫 正确收窄 有，逻辑由你写 取决于你的判断是否完备，容易漏字段 结构简单、字段少的判断

any 与 unknown：一个关闭检查，一个强制收窄

any 的真正危害是传染性：它可以赋值给任何类型、访问任何属性、当函数调用，一个 any 会沿着调用链把类型安全一路污染掉，而且不留任何痕迹——没有报错、没有告警，代码看起来还是有类型的。unknown 相反：它能接收任何值，但在收窄之前不允许任何操作，编译器强迫你先确认它是什么。

操作 any unknown
接收任意值 可以 可以
赋值给其他具体类型 可以，这是污染的起点 不可以，必须先收窄或断言
访问属性或调用 可以，全部不检查 不可以，编译报错
参与算术与拼接 可以 不可以
对重构的影响 改动无法被检查覆盖，是最大的类型黑洞 所有使用点都被迫显式处理
推荐用途 仅限迁移期临时使用，并写明原因与清理计划 catch 的异常、JSON.parse 结果、通用工具入参
strict 子项 作用 收益 老项目打开的代价
strictNullChecks null 与 undefined 不再能赋给任意类型 最大：空值是运行时错误占比最高的一类 报错量最多，建议按目录分批开
noImplicitAny 未标注且推导不出的参数报错 大：堵住隐式类型黑洞的入口 中等，主要是补参数标注
strictFunctionTypes 函数参数按逆变检查 中：避免回调签名不兼容被放过 小，改动集中在回调与事件处理
strictPropertyInitialization 类字段必须在构造时确定有值 中：避免读到 undefined 字段 小，多为加初值或明确可选
useUnknownInCatchVariables catch 的变量从 any 变 unknown 中：逼你正确判断异常类型 小，改错误处理分支
noUncheckedIndexedAccess（不属于 strict 但强烈建议） 下标访问结果自动带 undefined 大：数组越界与字典缺键是常见线上错误 较大，很多下标访问需要判空

类型收窄与判别联合：让漏分支变成编译错误

判别联合是 TypeScript 里表达「多种状态」最有工程价值的模式，远比几个布尔标志组合可靠：不可能存在的状态组合在类型层面就写不出来（比如「正在加载且已有错误且有数据」），而且每个分支只携带该状态下确实存在的数据。配合 never 做穷尽检查，未来有人新增一种状态却忘了处理时，编译会直接失败而不是在运行时静默走到 default。

stateDiagram-v2 [*] --> idle idle --> loading: 发起请求 loading --> success: 校验通过 携带 data 字段 loading --> error: 网络失败或 schema 不匹配 携带 error 字段 loading --> idle: 请求被取消 success --> loading: 重新获取 error --> loading: 重试 note right of loading 每个状态只携带该状态下存在的字段 所以不可能出现 既在加载又有错误又有数据 的非法组合 end note note right of error 新增一种状态时 穷尽检查会让所有未处理分支编译失败 这正是判别联合的主要收益 end note 
// 判别联合 + never 穷尽检查：可直接抄走的状态建模方式
type RequestState<T> =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'success'; data: T }            // data 只在 success 分支存在
  | { status: 'error'; error: Error; retryable: boolean };

// 反面对照：三个布尔标志能表达出 8 种组合，其中 5 种是非法状态
// { loading: boolean; error?: Error; data?: T }  -> 必须靠约定维护，编译器帮不上忙

function render<T>(state: RequestState<T>): string {
  switch (state.status) {
    case 'idle':
      return '待发起';
    case 'loading':
      return '加载中';
    case 'success':
      // 这里 state 已被收窄，能直接访问 data；在其他分支访问 data 会编译报错
      return '共 ' + String((state.data as unknown[]).length) + ' 条';
    case 'error':
      return state.retryable ? '失败 可重试' : '失败';
    default:
      // 穷尽检查：所有分支都处理完时 state 的类型是 never，赋值成立
      // 一旦给 RequestState 增加了 'refreshing' 却忘了在上面处理，这里立刻编译失败
      return assertNever(state);
  }
}

function assertNever(x: never): never {
  // 运行时兜底：类型被绕过（比如数据来自未校验的外部输入）时给出可诊断的错误
  throw new Error('未处理的分支: ' + JSON.stringify(x));
}

// 三种常用收窄手段，按可靠性排序：
// 1) 判别字段：if (state.status === 'success')        —— 最可靠，推荐
// 2) typeof 与 Array.isArray 与 instanceof             —— 适合原始值与类实例
// 3) 自定义守卫：function isUser(v: unknown): v is User —— 自己保证逻辑完备，容易漏字段
//    注意守卫的返回类型是你的承诺，写错了编译器不会发现，这点和 as 一样危险

泛型与类型体操的合理边界

泛型解决的是「同一套逻辑作用于多种类型」，和 Java 的泛型动机一致。问题出在 TypeScript 的类型系统本身是图灵完备的，于是很容易写出没人看得懂、编辑器提示一坨的类型。判断标准很实用：这段类型代码是给业务代码用的，还是给库的使用者用的。业务项目里 90% 的需求只需要泛型函数、泛型参数约束、以及 Partial 与 Pick 与 Omit 这几个内置工具类型；条件类型、映射类型、模板字面量类型、递归类型主要是写库时才需要。

类型能力 业务代码 库代码 过度使用的代价
泛型函数与泛型组件 常用 常用 无，但别给只用一次的函数加类型参数
约束 extends 与默认类型参数 常用 常用 约束过紧导致调用方无法复用
Partial、Pick、Omit、Record 常用 常用 用 Omit 剪裁生成类型时，后端改名不会报错
条件类型与 infer 少用 需要 报错信息变得无法阅读，新人无法维护
映射类型与键重映射 少用 需要 编辑器提示退化成一大段展开，定位困难
模板字面量与递归类型 基本不用 偶尔 类型检查耗时显著上升，大项目里 tsc 会明显变慢

与后端接口的类型同步：最有工程价值的一节

手写后端接口类型必然漂移，只是时间问题：字段改名、可空性变化、枚举新增值，都不会有任何提示。唯一可靠的做法是从后端的契约生成类型，并把生成动作放进 CI 校验。

编译与构建：谁负责类型检查

这是从后端转过来最容易踩的一个工程坑：esbuild、SWC、以及 Vite 默认的转译链都不做类型检查。它们的速度优势正来自跳过这一步——逐文件删掉类型标注并降级语法，不做跨文件推导。于是类型错误的代码照样构建成功、照样上线，本地编辑器的红线只是编辑器自己跑的检查，拦不住任何人合并代码。CI 必须单独跑一次只做类型检查、不输出文件的命令，并设为合并的必过项。

isolatedModules 与类型导入

逐文件转译的工具看不到其他文件，无法判断一个导入名到底是类型还是值。因此要开启 isolatedModules，并把仅用于类型的导入写成显式的类型导入形式（import type）。否则被擦除后可能留下一个指向「只有类型的模块」的无效运行时引用，表现为线上报某个模块不存在，而本地开发却完全正常。

最容易踩的坑

❌
避坑清单
  • 把 JSON.parse 或接口响应直接断言成业务类型。这是「类型安全」幻觉的头号来源，后端一改字段全线静默失效。
  • 以为 fetch 会在 4xx 与 5xx 时 reject。它只在网络层失败才 reject，状态码必须自己判断，否则会把错误页 HTML 当 JSON 解析。
  • 用 any 消灭报错。它会沿调用链传染且不留痕迹，是重构时改漏代码的主要原因，改用 unknown 逼自己收窄。
  • catch 里直接访问 err.message。异常可以是任何值，开启 useUnknownInCatchVariables 后必须先判断类型。
  • 关闭 strictNullChecks 图省事。这一项的收益最大，关掉等于放弃对空值问题的全部检查。
  • 不开 noUncheckedIndexedAccess，于是数组下标与字典取值都被当作一定存在，越界和缺键在运行时才炸。
  • 用几个布尔标志表示请求状态，界面出现「加载中且有错误且有数据」的非法组合。
  • 自定义类型守卫里只判断一两个字段就宣称它是某个类型，效果和 as 一样不可靠。
  • 在业务代码里写条件类型与递归类型，导致报错信息无法阅读，且 tsc 检查时间显著上升。
  • 用 Omit 从生成类型里剪裁字段，后端把该字段改名后 Omit 静默失效，剪裁不再生效也不报错。
  • 只依赖编辑器的类型提示，CI 里没有类型检查步骤，esbuild 与 SWC 会把类型错误的代码正常构建出来。
  • 没开 isolatedModules 也不写类型导入，转译后留下指向纯类型模块的运行时引用，线上报模块不存在。
  • 手工修改生成的接口类型文件，下次生成时被覆盖，或者永远不再重新生成。
  • 发布内部 npm 包时没有输出 d.ts，使用方拿到的一切都是 any，等于类型收益归零。
