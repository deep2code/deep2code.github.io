Islands 架构：水合策略与跨框架组合

岛屿架构的全部工程决策都落在一个问题上：哪些组件要把代码发到浏览器，以及什么时候发。客户端指令就是这个决策的表达方式。这篇把五个指令的差异、进入视口才水合的完整时序、跨岛通信的三种办法，以及混用框架的真实代价讲清楚。模型背景见《Astro 的零 JS 默认与适用边界》。

三个要点。第一，组件在服务端执行过一次，所以岛屿也有服务端渲染的初始内容，除非你选了仅客户端渲染。第二，props 被序列化进了 HTML，这意味着它们是公开可见的，而且会计入 HTML 体积。第三，静态区域与岛屿完全解耦，某个岛屿的脚本加载失败不会影响页面其余部分——这是这个模型在健壮性上的额外收益。

五个指令的对照

指令下载与执行时机服务端是否渲染初始内容适合的组件对首屏的影响典型误用
立即水合页面解析到即开始，尽快执行是首屏之上、用户可能立刻操作的控件占用启动期主线程，会推迟可交互时间给页面上所有组件都用，等于回到全量水合
空闲水合浏览器空闲时，或达到超时兜底是次要交互：分享按钮、反馈入口基本不影响首屏用于用户很快会点的主按钮，点上去没反应
进入视口水合元素接近或进入视口时是首屏之下的一切交互区块无影响，代价是滚动到时的短暂延迟给首屏可见元素用，反而增加一次观察开销
条件水合满足媒体查询条件时是只在某类设备生效的组件，如移动端抽屉菜单无影响条件写得过宽，等于无条件水合
仅客户端渲染立即加载，且服务端不渲染否强依赖浏览器环境的组件，如画布、地图该区域首屏为空，容易造成位移用于本可以服务端渲染的内容，白白牺牲首屏

需要强调「服务端是否渲染初始内容」这一列：除仅客户端渲染之外，其他四种都会先给出静态内容，用户在水合完成前就能看到并阅读。也就是说延迟水合牺牲的是可交互时间，不是内容可见时间。这一点常被误解成「延迟水合会让内容出现变慢」。

进入视口才水合的完整时序

sequenceDiagram participant U as 用户 participant D as 文档 participant O as 视口观察器 participant N as 网络 participant I as 岛屿运行时 D->>D: 解析 HTML 得到岛屿占位
占位内含服务端渲染的静态内容 D->>O: 为该占位注册观察 Note over U,D: 此时内容已可见可读
但还没有任何组件代码 U->>D: 向下滚动 O->>N: 元素接近视口 触发请求 N-->>I: 返回框架运行时与组件分块 I->>D: 在占位处挂载组件 I->>D: 用序列化的 props 还原初始状态 Note over D,I: 水合完成 该区域开始响应事件 U->>I: 点击操作 I-->>U: 正常响应 Note over U,I: 若用户滚动极快 可能在下载完成前先点击
这段空档是延迟水合的固有成本

最后那条注解是实践中真正会被用户投诉的点：滚动很快的用户可能在代码到位之前就点了按钮。缓解手段有两个：把观察的触发边界往上提，让元素还没进入视口就开始加载；或者在服务端渲染的占位里就给出可用的降级形态，例如一个指向独立页面的普通链接，水合后再接管成弹层。

  <MobileFilter client:media="(max-width: 48rem)" />

  <div style="min-height: 320px">
    <PriceChart sku={id} client:only="react" />
  </div>
</Base>

这段代码里每个指令的选择都有理由，而不是随手写。注意仅客户端渲染那一项必须显式声明框架名，因为服务端不渲染它，加载器无法从渲染结果推断该用哪个运行时；同时外层包了最小高度，否则水合前那块区域高度为零，图表出现时整页会往下跳。

岛屿之间不共享状态

岛屿各自独立挂载，没有共同父树，因此不存在能穿透两个岛屿的组件状态。头部的购物车数量和详情页的加入购物车按钮属于两个岛屿，后者点击后前者不会自动更新。可选方案只有三条。

方案适合的状态跨页是否保留是否与框架无关代价
地址栏参数筛选条件、分页、排序、标签页保留，且可分享可回退是状态必须能表达为字符串，改变会触发导航
框架无关的外部 store购物车、主题、通知计数不保留，除非自己持久化是需要引入一个小体积库，每个岛屿各自订阅
自定义事件一次性通知：提交成功、关闭弹层不保留是没有当前值概念，晚挂载的岛屿收不到早先的事件
持久化存储用户偏好、草稿保留是读取时机晚于首帧，可能闪烁；不能放敏感数据
同框架单一大岛屿确实高度耦合的区域不保留否范围一旦扩大就退化成全量水合
// src/stores/cart.ts —— 与框架无关的极小 store，两个岛屿都能订阅
import { atom, computed } from 'nanostores'

export type CartItem = { sku: string; qty: number }

// 状态本身不属于任何框架，所以 React 岛屿和 Vue 岛屿可以共用这一份
export const cartItems = atom<CartItem[]>([])
export const cartCount = computed(cartItems, (items) =>
  items.reduce((sum, i) => sum + i.qty, 0),
)

export function addToCart(sku: string, qty = 1) {
  const items = cartItems.get()
  const hit = items.find((i) => i.sku === sku)
  // 不要就地修改数组，订阅者靠引用变化判断是否需要重渲染
  cartItems.set(
    hit
      ? items.map((i) => (i.sku === sku ? { ...i, qty: i.qty + qty } : i))
      : [...items, { sku, qty }],
  )
}

// 可选的持久化：注意只在浏览器端执行，服务端渲染阶段没有存储对象
if (typeof localStorage !== 'undefined') {
  const saved = localStorage.getItem('cart')
  if (saved) cartItems.set(JSON.parse(saved))
  cartItems.subscribe((items) =>
    localStorage.setItem('cart', JSON.stringify(items)),
  )
}
// 方案三：一次性通知用自定义事件，不需要引入任何库
// 发送方（任意岛屿或普通脚本）
window.dispatchEvent(
  new CustomEvent('cart:added', { detail: { sku: 'A-100', qty: 1 } }),
)

// 接收方：注意晚挂载的岛屿收不到此前派发的事件，
// 所以事件只适合表达「刚刚发生了什么」，不适合表达「当前是什么」
window.addEventListener('cart:added', (e) => {
  const { sku, qty } = (e as CustomEvent).detail
  showToast(`已加入 ${qty} 件 ${sku}`)
})

// 反例：用事件同步购物车数量。刷新或延迟水合后，
// 头部岛屿没有任何办法知道当前数量，只能显示零

混用框架的代价

组合客户端运行时份数压缩后额外体积量级工程代价什么时候可以接受
只用模板语法，无框架组件零接近零最低纯内容站，交互靠少量原生脚本
单一框架，多个岛屿一份几十 KB 加各组件自身低常规选择
两个框架同页两份两份运行时叠加高：两套状态方案与调试方式迁移过渡期，或必须复用某框架独有组件
两个框架但不同页按页各一份单页不叠加中站点内不同板块由不同团队维护
同框架但多个大版本可能两份叠加且容易冲突很高基本不要出现

结论很直接：岛屿数量不是体积的主要变量，框架种类才是。一页上放十个同框架的小岛屿，通常比放两个不同框架的岛屿更省。做体积核查时应该先数运行时份数，再看组件分块。

服务端岛屿：另一种延迟

客户端岛屿延迟的是「代码下载与水合」，服务端岛屿延迟的是「这一块内容的渲染」。后者的用途是：让页面主体保持可缓存的静态内容，同时在页面里留一个由服务端稍后单独渲染的区块，用来放个性化推荐、库存、价格这类不能缓存的内容。它不向客户端增加任何框架代码。

维度客户端岛屿服务端岛屿
延迟的对象组件代码下载与水合该区块在服务端的渲染
客户端 JS 增量框架运行时加组件代码仅极小的加载逻辑
能否访问服务端资源不能，只能调接口能，可直接读数据库与密钥
对整页缓存的影响无，页面仍可全量缓存无，主体仍可全量缓存
失败时的表现该区域不可交互，内容仍在该区块空缺，必须自己设计兜底
适合的内容需要用户操作的控件个性化或实时但只读的内容
额外成本主线程执行开销一次额外的网络往返

三者组合起来才是完整方案：页面主体静态、只读的动态内容走服务端岛屿、真正需要交互的控件才用客户端岛屿。很多人一遇到「这块内容会变」就把整页改成按请求渲染，那是最浪费的做法。

水合不是免费的

成本项发生时机表现控制手段
框架运行时下载与解析第一个岛屿激活时一次性的网络与主线程开销统一框架，能不水合就不水合
组件代码与依赖各岛屿激活时随依赖体积线性增加把重依赖挪到服务端，岛屿只做交互
props 序列化服务端渲染阶段HTML 变大，且内容公开可见只传标识符，数据让岛屿自己取
挂载与首帧渲染水合瞬间可能出现短暂闪烁或位移让服务端标记与水合首帧一致
布局偏移延迟水合的岛屿出现时页面内容跳动预留高度，尤其是仅客户端渲染的组件
交互空档代码到位之前点击无响应提前触发加载，或提供可用的降级形态
✅
一条实用原则

把岛屿的职责限制在交互上，数据处理、格式化、大依赖的计算全部留在服务端。一个只负责响应点击并调用接口的岛屿可能只有几 KB，而一个顺手引入了日期库与图表库的岛屿轻易就是它的几十倍。

❌
最容易踩的坑
  • 给所有组件都用立即水合：启动期主线程被占满，可交互时间甚至比全量水合方案更差。
  • 给首屏主按钮用空闲水合：用户点上去没反应，这是最影响转化的低级错误。
  • 用仅客户端渲染代替可服务端渲染的组件：白白牺牲首屏内容，还引入布局偏移。
  • 仅客户端渲染不写框架名：服务端没有渲染结果，加载器无法推断运行时，组件不会挂载。
  • 延迟水合区域不预留高度：岛屿出现时整页跳动，视觉稳定性指标直接恶化。
  • 期望两个岛屿共享组件状态：它们没有共同父树，必须通过地址栏、外部 store 或事件通信。
  • 用自定义事件表达当前值：晚挂载的岛屿收不到早先事件，刷新后状态归零，这类状态要放 store。
  • store 里就地修改对象：订阅者依赖引用变化判断更新，原地修改会导致界面不刷新。
  • store 模块在服务端访问存储对象：服务端渲染阶段没有浏览器存储，必须先判断环境。
  • 把大块数据当 props 传给岛屿：HTML 体积暴涨，而且数据在源码里完全公开。
  • 把密钥或内部字段传给岛屿：props 序列化后明文可见，等于公开泄露。
  • 同页混用两个框架：两份运行时叠加，体积优势基本被吃掉，还带来双倍工程复杂度。
  • 岛屿里顺手引入重依赖：一个图表库或日期库就能让这块的体积超过页面其余部分之和。
  • 关键功能只存在于岛屿里：脚本加载失败时该功能完全不可用，核心路径应该有非脚本的降级方案。
