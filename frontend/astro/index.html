Astro 的零 JS 默认与适用边界

🏷️ Astro

Astro 的核心主张只有一句：默认不向浏览器发送 JavaScript。组件在构建期或请求期在服务端执行，产出 HTML；只有显式标记的组件才会把代码和框架运行时送到客户端。这个默认值决定了它擅长什么，也决定了它在什么场景下是逆流而上。这篇讲模型本身与适用边界，上手细节见《Astro 上手》，水合策略见《Islands 架构》。

关键差异不在「有没有服务端渲染」，两边都有；而在于客户端是否需要重建整棵组件树。全量水合模型里即使页面只有一个按钮需要交互，整棵树的组件代码也要下载并执行一遍；部分水合模型里，没有标记的区域在客户端根本不存在对应代码。

这张图解释了为什么内容站用 Astro 的指标提升往往很夸张：内容出现的时刻从「三次往返之后」变成「第一次响应就有」。但也要看清它没有解决什么——如果数据本身很慢，构建期取数只是把慢转移到了构建阶段，服务端渲染模式下该慢的还是慢。

三种输出模式与渲染时机

模式渲染时机能否读请求信息部署形态适合的页面代价
静态构建期一次性全部生成不能纯静态托管，可全量走 CDN文档、博客、营销页内容更新要重新构建，页面极多时构建时间线性上升
服务端渲染每次请求渲染能需要运行时环境与适配器个性化页、需要登录态的页失去整页静态缓存，需要关注服务端耗时
混合：整站静态加少数动态路由按路由区分动态路由能需要适配器内容站带少量会话相关页面要清楚每个路由属于哪类，容易配错
按需渲染的服务端岛屿页面静态，局部延迟渲染局部能需要适配器静态页里的用户态区块与推荐位额外一次请求，需要处理占位与失败态

第四行是很多人忽略的选项：当只有页面上一小块内容依赖用户或实时数据时，不需要把整页降级成按请求渲染。把那一块做成服务端延迟渲染的区块，页面主体仍然可以全量缓存在 CDN 上。这个取舍在内容站加「推荐给你」这类模块时非常实用。

// astro.config.mjs：模式与适配器的最小配置
import { defineConfig } from 'astro/config'
import node from '@astrojs/node'
import react from '@astrojs/react'

export default defineConfig({
  // static 表示全部构建期生成；改成 server 后默认按请求渲染
  output: 'static',
  adapter: node({ mode: 'standalone' }),   // 只有需要服务端渲染时才配
  integrations: [react()],                 // 每多一个框架集成就多一份潜在运行时
  build: {
    // 把内联脚本限制在体积很小的情况，避免 HTML 变大影响首屏
    inlineStylesheets: 'auto',
  },
})
---
// src/pages/posts/[slug].astro
// 这段 frontmatter 只在服务端执行：构建期或请求期，绝不会进客户端产物
import Layout from '../../layouts/Base.astro'
import Comments from '../../components/Comments.tsx'
import { getCollection } from 'astro:content'

export async function getStaticPaths() {
  const posts = await getCollection('posts')
  return posts.map((p) => ({ params: { slug: p.slug }, props: { post: p } }))
}

const { post } = Astro.props
const { Content } = await post.render()
---

<Layout title={post.data.title}>
  <article>
    <h1>{post.data.title}</h1>
    <!-- 正文是纯 HTML，零 JS -->
    <Content />
  </article>

  <!-- 唯一的交互区域：滚动到视口才下载并水合 -->
  <Comments slug={post.slug} client:visible />
</Layout>

这段代码体现了模型的全部要点：frontmatter 里的取数与渲染逻辑不会进入客户端产物；正文是纯 HTML；页面上唯一需要 JavaScript 的评论区被单独标记，而且推迟到进入视口才加载。整页的客户端 JS 只有评论组件那一块。

它改善哪些指标，不改善哪些

「换成 Astro 分数就上去了」这种说法需要拆开看。部分水合直接作用的是主线程上的脚本工作量，因此交互相关的指标改善最明显；而与网络和资源本身有关的指标，它帮不上忙。

指标是否改善原因还要做什么
可交互延迟与长任务显著改善没有全树水合，主线程几乎没有启动期脚本控制岛屿数量与第三方脚本
JS 传输体积显著改善未标记的组件根本不进客户端产物统一框架，避免两份运行时
内容出现时间改善内容在首个响应的 HTML 里，不需要等取数图片与字体仍需自己优化
最大内容绘制取决于资源瓶颈通常是首屏大图或自定义字体，与框架无关图片尺寸与格式、字体加载策略
首字节时间基本不改善由托管与网络决定，静态模式下取决于 CDN缓存头与就近分发，见站内前端性能相关文章
布局偏移不自动改善偏移来自未预留尺寸的图片与延迟插入的岛屿给岛屿占位预留高度

最后一行值得注意：延迟水合本身可能引入新的布局偏移。一个滚动到视口才加载的岛屿，如果占位高度与水合后的真实高度不一致，用户会看到内容跳动。这是部分水合特有的成本，不预留尺寸就会踩到。

代价与限制

三条真实限制。第一，默认整页导航：站内跳转是浏览器级别的页面切换，虽然可以开启视图过渡来平滑观感，但它不是客户端路由，跨页保持播放器或滚动位置这类需求要额外处理。第二，岛屿之间天然隔离：没有共同的组件树，状态无法通过 props 或 context 传递，必须借 URL、框架无关的 store 或自定义事件，细节见《Islands 架构》。第三，混用框架的代价是复利的：两个框架就是两份运行时，同一页面同时出现时体积优势会被吃掉大半。

# 验证「零 JS」是不是真的：直接数产物里的脚本
npm run build

# 1. 看某个页面 HTML 里引入了几个模块脚本
grep -o 'type="module"' dist/index.html | wc -l

# 2. 看客户端 JS 总量（压缩后才有意义）
find dist -name '*.js' -exec cat {} + | gzip -c | wc -c

# 3. 找出哪些页面带了岛屿：产物 HTML 里会出现 astro-island 标记
grep -rl 'astro-island' dist | head

# 判读：纯内容页应该完全搜不到模块脚本；
# 若某个本该静态的页面出现了岛屿标记，去源码里找漏加或误加的客户端指令
💡
一句话结论

Astro 的价值来自一个默认值的翻转：把「发送 JavaScript」从默认变成显式选择。当页面上绝大多数区域本来就不需要交互时，这个翻转带来的收益是数量级的；当绝大多数区域都需要交互时，它只是给你增加了标记与通信的工作量。

❌
最容易踩的坑
  • 给整个布局加客户端指令：等于把全页都变成岛屿，框架运行时与全部组件代码照样下载，零 JS 优势直接消失。
  • 同一页面混用两个框架：两份运行时都要下载，体积往往比统一用一个框架的全量水合方案还差。
  • 以为零 JS 就是没有脚本：分析脚本、第三方组件、视图过渡都会发送代码，做体积核查要看产物总量而不是只看框架。
  • 在 frontmatter 里写浏览器专属逻辑：frontmatter 在服务端执行，访问文档对象或窗口对象会直接报错。
  • 给岛屿传不可序列化的 props：函数、类实例、带方法的对象无法跨越服务端到客户端的边界，需要传纯数据。
  • 用整页按请求渲染解决局部动态：整页失去静态缓存能力，正确做法是把动态部分收进服务端延迟渲染的区块。
  • 拿 Astro 做重交互应用：岛屿越多模型优势越小，而岛屿间通信成本与调试难度持续上升。
  • 期待跨页保持客户端状态：默认整页导航会销毁所有岛屿状态，需要的话得落到 URL 或存储里。
  • 构建期取数当成永久新鲜：静态模式下数据凝固在构建那一刻，需要更新就得重新构建或改用按请求渲染。
  • 页面数量极多仍坚持全量静态：构建时间随页面数线性上升，上万页级别要考虑按需渲染或增量构建。
  • 只在开发模式验证体积：开发模式的脚本与产物完全不同，必须跑生产构建再核查。
  • 忽略禁用脚本时的表现：岛屿承载的关键功能在脚本失败时不可用，核心内容与导航不应该依赖岛屿。
