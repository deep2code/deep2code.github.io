大型项目里的 Tailwind 实践

小项目里 Tailwind 基本不需要「最佳实践」，写就完了。问题出现在项目变大之后：一个按钮在十七个地方出现七种写法、暗色模式改一次要动两百个文件、CSS 体积莫名涨到 80 KB、新人不知道什么时候该写自定义 CSS。这篇给出对应的工程手段，全部是可以直接落进代码与 CI 的做法。

方案取舍见《Tailwind 的设计取舍》，工具类体系与层叠机制见《工具类体系》，安装与生成机制见《Tailwind 上手》。

这张图的关键是类串的密度应该自上而下递减：基元组件里类串最长最密，业务组件里只剩组合和少量间距，页面层理想状态下只有栅格与响应式类。如果你在页面层看到颜色、圆角、阴影这类视觉属性，说明有本该沉到基元层的东西漏出来了，这是后期样式失控的早期信号。

用变体声明集中管理组件

// components/ui/button.ts —— 变体集中声明，调用方只传语义参数
import { cva, type VariantProps } from 'class-variance-authority'
import { cn } from '@/lib/cn'   // cn 是 twMerge 包 clsx 的封装

export const buttonVariants = cva(
  // 基础类：所有变体共享。焦点环放在基础类里，避免某个变体忘写
  'inline-flex items-center justify-center gap-2 rounded-md font-medium ' +
    'transition-colors disabled:pointer-events-none disabled:opacity-50 ' +
    'focus-visible:outline-2 focus-visible:outline-offset-2 focus-visible:outline-brand-500',
  {
    variants: {
      // 语义维度：颜色全部引用语义令牌，换主题时这里一行都不用改
      tone: {
        primary: 'bg-brand-600 text-white hover:bg-brand-700',
        subtle: 'bg-slate-100 text-slate-900 hover:bg-slate-200',
        danger: 'bg-rose-600 text-white hover:bg-rose-700',
        ghost: 'text-slate-700 hover:bg-slate-100',
      },
      // 尺寸维度：与语义维度正交，组合由工具自动处理
      size: {
        sm: 'h-8 px-3 text-sm',
        md: 'h-10 px-4 text-sm',
        lg: 'h-12 px-6 text-base',
      },
      block: { true: 'w-full' },
    },
    // 组合修正：只在特定组合下生效，避免为此新增一个变体值
    compoundVariants: [
      { tone: 'ghost', size: 'sm', class: 'px-2' },
    ],
    defaultVariants: { tone: 'primary', size: 'md' },
  },
)

export type ButtonProps = VariantProps<typeof buttonVariants> & { className?: string }

// className 放在最后传给 cn，保证调用方永远能覆盖同属性的默认值
export const buttonClass = (p: ButtonProps = {}) =>
  cn(buttonVariants({ tone: p.tone, size: p.size, block: p.block }), p.className)
封装方式适合的复杂度优点什么时候会失效
直接写类串一次性页面、只出现一次的结构零抽象，改动直观出现第二处需要保持一致时
条件表达式拼类一个维度、两三个取值不引入依赖维度增加到两个，分支组合爆炸
变体声明工具两个以上正交维度组合自动处理，类型安全维度超过四个时声明本身变难读，该拆组件
语义类加 apply不推荐HTML 短失去可删除性与可覆盖性，回到传统 CSS 的问题
交给第三方组件库标准控件如下拉与日期省掉无障碍与交互细节实现需要深度定制视觉时，覆盖成本高于自研

令牌与主题：两种实现的取舍

维度类变体方案（每处写暗色类）CSS 变量方案（语义令牌换值）
组件代码改动量每个颜色都要加一份暗色类零，组件只引用语义令牌
新增第三套主题所有组件再写一遍只加一组变量值
运行时切换可行，切根节点属性可行，且闪烁风险更低
产物体积暗色变体让候选类数量接近翻倍几乎不增加
可读性类串里能直接看出暗色表现需要去令牌层查语义令牌的值
适用规模组件少于二十个、只有明暗两套组件多、主题多、有品牌定制需求
迁移成本后期改成变量方案要重写所有组件起步时多花半天设计语义层
/* 令牌分两级：原始色板只出现在这里，组件一律引用语义令牌 */
@import "tailwindcss";

@theme {
  --color-slate-50: oklch(0.985 0.002 250);
  --color-slate-900: oklch(0.21 0.02 250);
  --color-brand-600: oklch(0.55 0.16 250);

  /* 语义令牌：组件里只写 bg-surface text-fg 这类语义类 */
  --color-surface: var(--color-slate-50);
  --color-fg: var(--color-slate-900);
  --color-border-subtle: oklch(0.92 0.004 250);
}

/* 暗色只在这一处换值，所有组件自动跟随，无需任何 dark 变体 */
@layer base {
  [data-theme="dark"] {
    --color-surface: oklch(0.21 0.02 250);
    --color-fg: oklch(0.97 0.002 250);
    --color-border-subtle: oklch(0.32 0.01 250);
  }
  /* 跟随系统但允许用户覆盖：只在未显式设置时生效 */
  @media (prefers-color-scheme: dark) {
    :root:not([data-theme]) {
      --color-surface: oklch(0.21 0.02 250);
      --color-fg: oklch(0.97 0.002 250);
      --color-border-subtle: oklch(0.32 0.01 250);
    }
  }
}

注意最后那段：:root:not([data-theme]) 解决的是「跟随系统」与「用户手动选择」的优先级冲突。如果直接把系统偏好写在根节点上，用户手动切成亮色后刷新页面又会被系统偏好覆盖，这是主题功能最常见的缺陷。

「共享同一个变更理由」这个判据比「出现三次就抽」可靠得多。营销页的卡片和后台列表的卡片长得一样，但它们几乎一定会分道扬镳，过早抽象的结果是一个带十个布尔参数的组件，而每个调用方只用其中两个。

与组件库的配合

维度安装依赖包式组件库复制源码式组件库
定制深度受限于库暴露的入口无限，直接改代码
样式冲突需要与库的选择器竞赛权重不存在，样式就是你的代码
升级一条命令，但可能引入视觉回归需要手动比对合并，工作量真实存在
安全修复随版本自动获得要自己跟进上游变更
体积可能引入未使用的组件与运行时只有你复制进来的部分
适合的层无障碍实现复杂的无样式交互原语有视觉表现、需要贴合品牌的组件
团队要求低需要有人负责维护这套代码

成熟的组合是分层的：交互原语（下拉、弹层、组合框这类键盘与焦点处理复杂的部分）用依赖包，视觉层用复制源码的方式落进项目。这样既不用自己实现焦点陷阱与键盘导航，又能对视觉有完全控制权。

团队约定与执行手段

约定执行手段不执行的后果
类名顺序统一格式化插件强制排序并纳入 CI 检查diff 不可读，同一组件的并行改动频繁冲突
禁止无理由的任意值lint 规则拦截，需要时用注释豁免并写明原因设计约束失效，散落的数值无法批量调整
禁止叠加同属性冲突类lint 检测冲突类，组件统一走合并函数条件样式行为不确定，线上偶发视觉缺陷
自定义 CSS 限定场景把允许的四类场景写进约定，其余走 review两套样式体系并存，覆盖关系混乱
颜色只能用语义令牌lint 禁止在组件里直接用原始色板类换主题时要逐个组件排查，暗色模式无法收口
焦点可见样式必须有把焦点环写进基元组件的基础类键盘用户完全失去焦点指示，无障碍回归
# CI 里的三道检查：格式、约定、体积。任一失败即阻断合并

# 1. 类名顺序与格式（check 模式只检查不改写）
npx prettier --check "src/**/*.{ts,tsx,html}"

# 2. 约定检查：冲突类、任意值、被禁用的原始色板类
npx eslint "src/**/*.{ts,tsx}" --max-warnings 0

# 3. 体积回归：记录压缩后体积并与基线比较
npm run build
SIZE=$(gzip -c dist/assets/*.css | wc -c | tr -d ' ')
BASE=$(cat .size-baseline 2>/dev/null || echo 0)
echo "css gzip: ${SIZE} bytes, baseline ${BASE}"
# 单次提交增量超过 2048 字节就要求说明原因，通常是扫描范围或色板出了问题
if [ "$BASE" -gt 0 ] && [ $((SIZE - BASE)) -gt 2048 ]; then
  echo "CSS 体积增量超过阈值，请检查扫描范围与新增令牌"
  exit 1
fi
体积现象量级判定首查方向
压缩后 10 到 18 KB中型项目常态正常无需处理
压缩后超过 40 KB异常配置问题扫描范围是否包含依赖目录
单次提交增量超过 2 KB异常需要解释是否新增全量色板或通配 safelist
规则数量突增数千条异常候选集爆炸是否有循环生成类名或过宽的 safelist
体积正常但首屏慢与 CSS 无关排查方向错了见站内《前端性能优化》与缓存相关文章

自定义 CSS 的允许清单

「什么时候可以写 CSS」必须有一份明确清单，否则这条约定要么形同虚设，要么变成教条。可以写的只有四类：全局重置与字体声明，它们天然是全局的；令牌定义，这是设计决策的唯一来源；无法加类名的结构，包括富文本正文、第三方组件注入的 DOM、以及邮件与打印这类目标环境；复杂关键帧动画，用工具类表达多段关键帧只会更难读。

除此之外一律用工具类。这份清单要写进仓库的约定文件，并且每一段自定义 CSS 都要带注释说明它属于哪一类、以及什么条件下可以删除。少了后半句，这些 CSS 就会长成新的死代码——注意这正是传统 CSS 最难解决的那个问题，它不会因为你用了工具类就自动消失，只是被压缩到这四类场景里。实践中一个健康的中型项目，自定义 CSS 总量通常不超过一百行，超出这个量级就该回头检查是不是有本该用工具类表达的东西跑进了样式表。

❌
最容易踩的坑
  • 页面层出现视觉类：颜色、圆角、阴影漏到页面层，后期改主题要在几百个文件里找，这是样式失控最早的信号。
  • 组件直接用原始色板类：没有语义令牌层，暗色模式和品牌定制都会变成全项目搜索替换。
  • 暗色模式先用类变体后期再改：先写了两百处暗色变体，改成变量方案时等于重写所有组件。
  • 主题优先级写错：系统偏好直接写在根节点上，用户手动选择的主题刷新后被覆盖。
  • 出现三次就抽组件：忽略变更理由是否相同，抽出来的组件很快长出十个布尔参数。
  • 组件不接受外部类名：调用方无法做局部微调，只能在外面包一层容器或用权重竞赛覆盖。
  • 接受外部类名但不做合并：外部类与默认类冲突时结果由产物顺序决定，覆盖行为不可靠。
  • 焦点环写在变体里：某个变体忘写就整类按钮失去键盘焦点指示，应该放在基础类里。
  • 约定只写在文档里：没有 lint 与 CI 执行的约定，三个月内必然失效。
  • 体积只在出问题时才看：没有基线就无法定位是哪次提交引入的膨胀，应该每次构建都记录压缩后体积。
  • 迁移时先开完整预检：预检重置会改变旧页面默认样式，造成大面积版式错乱，应该按需关闭再逐步开启。
  • 删旧 CSS 不做引用确认：删掉的规则还被未改写的页面依赖，缺陷往往几周后才被发现。
  • 复制源码式组件库无人维护：复制进来就再没人跟进上游修复，久了变成一堆带已知缺陷的代码。
