工具类体系：布局、间距、响应式与状态变体

🏷️ Tailwind 速查

工具类的清单可以查文档，没必要在文章里抄一遍。真正决定你写得对不对的是四件事：scale 的组织方式、响应式前缀的语义、变体如何表达状态，以及工具类之间根本没有优先级。最后一条是封装组件时必踩的坑，放在本文重点位置。

方案层面的取舍见《Tailwind 的设计取舍》，安装与生成机制见《Tailwind 上手》，组件库级别的封装模式见《大型项目里的 Tailwind 实践》。

这张图解释了一个常被忽略的事实：变体是可以叠加在任意工具类上的正交维度，不是一组固定的类名。写 md:dark:hover:bg-brand-600 时你组合了三个维度的条件，框架按顺序展开成嵌套的媒体查询与选择器。理解这个结构以后，需要什么写什么，不必去记清单。

scale：约束是怎么落地的

令牌类别步长与分布典型档位越界时的正确做法
间距基础步长 0.25rem，小区间细分，大区间跳跃1 等于 0.25rem，4 等于 1rem，12 等于 3rem先问设计能不能收敛到档位，确实不行再加令牌
字号每档绑定默认行高，形成垂直节奏sm 约 0.875rem，base 1rem，lg 1.125rem新增字号时必须同时定义行高，否则节奏错乱
颜色每色 11 个亮度阶梯，数字越大越深50 最浅，500 中间，950 最深品牌色只声明真正会用的三到四个阶梯
圆角与阴影少量语义化档位而非连续值sm md lg xl 与 full把组件级圆角定义成单独令牌，便于整体调整
断点四到五个最小宽度档位sm 40rem，md 48rem，lg 64rem，xl 80rem自定义断点要少，每加一个都让组合数上升
层级有限的 z 档位0 10 20 30 40 50把弹层层级集中成令牌，禁止随手写数字

约束的执行力来自「越界需要显式写方括号语法」这一点：它让绕过行为暴露在代码里，review 时一眼能看见。如果团队大量出现任意值，说明令牌与设计规范脱节，该修的是令牌而不是继续写任意值。

响应式：移动优先的最小宽度

⚠️
最常见的理解错误

md:flex 的含义不是「在中等屏幕上是 flex」，而是「视口宽度大于等于 md 断点时是 flex」，包括大屏和超大屏。不带前缀的类是所有尺寸共享的基线，也就是移动端样式。把它理解成「区间生效」会导致大屏上样式意外消失或残留。

写法实际生效范围展开后的条件适用场景
无前缀所有宽度无条件移动端基线，必须先写对
md 前缀大于等于 md，含更大屏最小宽度媒体查询渐进增强到平板与桌面
max-md 前缀小于 md最大宽度媒体查询只想改小屏且不愿动基线时
md 与 max-lg 同时用md 到 lg 之间的区间两个条件相交真正的区间样式，少用
容器查询变体取决于最近的容器宽度容器查询组件在不同栏宽里复用，比视口断点更准确

最后一行值得单独说：很多「响应式很难写」的抱怨，根因是用视口宽度去描述组件宽度。同一个卡片放在主栏和侧栏里应该有不同布局，而视口宽度对这两种情况毫无区分能力。容器查询变体是更贴合组件化的表达方式，遇到组件在多种栏宽下复用的场景优先考虑它。

状态变体与关系变体

变体表达的关系方向限制典型用途易错点
hover focus active元素自身状态无交互反馈只写 hover 不写 focus，键盘用户失去指示
focus-visible仅键盘触发的焦点无焦点环用 focus 会让鼠标点击也出现焦点环
focus-within后代获得焦点时作用于容器祖先响应后代输入框容器整体高亮与 focus 混用导致双重高亮
disabled aria-disabled可用性状态无禁用态只改视觉没改属性，屏幕阅读器仍认为可点
group 前缀祖先状态传递给后代祖先到后代，单向卡片悬浮时标题变色忘了给祖先加 group 标记，整组变体静默失效
peer 前缀兄弟状态传递只能作用于标记元素之后的兄弟勾选框控制紧随的标签把 peer 元素写在后面，选择器无法匹配
data 属性变体自定义状态无组件库的开关态与方向属性值拼写与选择器不一致时无提示
has 变体父级根据后代存在与否变化父到子的条件判断含图片的卡片换布局老浏览器不支持，需要降级

<a href="#" class="group/card block rounded-lg border p-4 hover:border-brand-500">
  <h3 class="font-semibold text-slate-900 group-hover/card:text-brand-600">季度报告</h3>
  <span class="text-slate-400 group-hover/card:translate-x-1 transition-transform">箭头</span>
</a>

<!-- peer：只能向后作用。输入框必须写在前面，提示写在后面 -->
<div class="grid gap-1">
  <input id="email" type="email" required
         class="peer rounded border px-3 py-2
                focus-visible:outline-2 focus-visible:outline-brand-500
                invalid:border-rose-400" />
  <!-- 只在输入框处于非法状态且已被用户交互过时显示 -->
  <p class="hidden text-sm text-rose-600 peer-[&:not(:placeholder-shown):invalid]:block">
    邮箱格式不正确
  </p>
</div>

<!-- 任意值的正确用法：运行时数值走 CSS 变量，不要拼类名 -->
<div class="h-2 rounded bg-slate-200">
  <div class="h-full rounded bg-brand-500 w-[var(--pct)]" style="--pct: 62%"></div>
</div>

关键机制：工具类之间没有优先级

这是封装组件时最容易翻车的地方。两个工具类如果控制同一个 CSS 属性，它们的选择器权重完全相同，胜负只由产物 CSS 里谁在后面决定，而产物顺序是框架按工具类分类固定生成的，与你在 class 属性里的书写顺序毫无关系。

下一层想再覆盖时无解"] 
// 组件封装的标准形态：默认类 + 调用方类，用合并工具消解冲突
import { twMerge } from 'tailwind-merge'
import { clsx, type ClassValue } from 'clsx'

// 这个 cn 函数几乎是每个 Tailwind 项目都要有的工具
export function cn(...inputs: ClassValue[]) {
  // clsx 负责条件拼接，twMerge 负责同属性冲突消解，顺序不能颠倒
  return twMerge(clsx(inputs))
}

type Props = { className?: string; dense?: boolean; children?: unknown }

export function Panel({ className, dense, children }: Props) {
  return {
    // 默认值写在前，调用方的 className 放最后，于是调用方总能覆盖
    class: cn(
      'rounded-card border border-slate-200 bg-white p-4 shadow-sm',
      dense && 'p-2',        // 条件类：与默认 p-4 冲突，由 twMerge 去掉 p-4
      className,             // 外部覆盖：同属性时保留外部的
    ),
    children,
  }
}

// 反例：不做合并，结果由产物顺序决定，dense 时可能完全不生效
// class: `rounded-card p-4 ${dense ? 'p-2' : ''} ${className ?? ''}`
覆盖手段是否可靠副作用什么时候用
叠加冲突类不可靠，取决于产物顺序行为看似随机，难复现永远不要
类名合并工具可靠极小的运行时开销所有可被外部覆盖的组件
条件渲染不同类串可靠分支多时类串重复变体只有两三种的小组件
变体管理工具集中声明可靠多一层抽象有尺寸与语义两个维度以上的组件
important 标记可靠但过强污染层叠，下游无法再覆盖只用于对抗第三方注入样式
提高选择器权重的自定义 CSS可靠回到传统 CSS 的权重竞赛不得不覆盖无法修改的结构时

层叠顺序：产物的分层与自定义 CSS 的落点

上一节说「胜负由产物顺序决定」，那就必须知道产物是怎么排的。框架把产物划成三层：基础层放重置与元素默认值，组件层放你自己声明的可被工具类覆盖的类，工具层放所有工具类。层的先后是固定的，后面的层整体胜过前面的层，与选择器权重无关——这是 CSS 层级机制带来的行为，也是很多人以为「工具类权重更高」的真实原因。

自己声明的语义类 第三方基线"] L3["工具层

未声明层的自定义 CSS"] end L1 --> L2 --> L3 --> L4 subgraph R["两条实践结论"] R1["想被工具类覆盖的样式

两个直接可用的结论：一是你写的语义类要想「能被调用方用工具类覆盖」，必须声明在组件层里，否则它会跑到层外从而反过来压住工具类；二是层外的自定义 CSS 胜过所有工具类，所以那些「明明加了工具类却不生效」的疑难问题，八成是有一段没有声明层的全局 CSS 在压着，检查时先去产物尾部看有没有这类规则。

apply 的适用与滥用

@apply 把工具类展开到一条自定义 CSS 规则里。它的问题不在语法，而在于它把之前解决掉的问题原样退回：你重新得到了一个需要起名字的类、一段无法确认是否还有人用的规则、以及「看 HTML 不知道样式长什么样」的间接性。

场景用 apply 是否合适理由
把常用类串包装成语义类不合适命名成本与死代码问题全部回归，收益只有 HTML 短一点
无法控制的 HTML（富文本、第三方组件）合适没有地方写 class，只能靠选择器
全局基线（表单控件统一焦点环）合适确实是全局约定，且数量极少
打印样式或邮件模板合适目标环境不支持完整工具类流程
为了复用一组类而在组件内 apply不合适组件本身就是复用单位，抽组件比抽类更好
覆盖第三方库的深层选择器合适但克制写清楚注释说明被覆盖的库与版本，便于日后清理
✅
判断标准

问一句：这段样式的使用者是不是一段我能直接加 class 的 HTML？能加就别用 apply，抽成组件；不能加（富文本、第三方结构、邮件）才用它。按这个标准执行，项目里的 apply 通常不超过十处。

❌
最容易踩的坑
  • 把断点当区间：以为 md 前缀只在中等屏生效，结果大屏上样式意外保留或消失，布局在超宽屏崩掉。
  • 先写桌面再补移动：把桌面样式写成无前缀基线，于是每个组件都要用小屏变体反向覆盖，类串翻倍且容易漏。
  • 叠加两个同属性类：以为写在后面的会赢，实际由产物顺序决定，条件样式表现随机且难复现。
  • 忘记给祖先加 group 标记：所有 group 变体静默失效，没有任何报错，只是交互反馈消失。
  • peer 元素写在响应元素之后：兄弟选择器只能向后匹配，顺序写反则永远不生效。
  • 用 focus 代替 focus-visible：鼠标点击也出现焦点环，设计会要求去掉，去掉后键盘用户彻底失去焦点指示。
  • 只改禁用态的视觉不改属性：看起来禁用但仍可点击与聚焦，辅助技术也拿不到禁用信息。
  • 用任意值微调间距：约束立即失效，这些散落的数值日后无法随设计系统批量调整。
  • 用 important 解决覆盖问题：当次生效但污染层叠，下一层调用方想再覆盖时没有任何办法。
  • 大量 apply 包装语义类：把命名成本、不可删除、跨文件查找三个问题一起请回来，还失去了可读性收益。
  • 自定义断点过多：每加一个断点，变体组合数就上升一档，类串变长且团队难以记住边界。
  • 用视口断点描述组件宽度：同一组件在主栏和侧栏需要不同布局，视口宽度无法区分，应该用容器查询变体。
