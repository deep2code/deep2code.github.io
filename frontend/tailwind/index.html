Tailwind 的设计取舍：原子类为什么不是倒退

🏷️ Tailwind CSS

原子类（utility-first）最常见的反对意见是「HTML 变脏了」。这个批评本身没错，但它只看了成本的一半。工具类换来的东西是具体的、可度量的：不用给每个块起名字、样式和结构同处一地因而可以安全删除、设计约束以 scale 的形式被强制执行、产物体积与项目规模脱钩。这篇把两边的账都算清楚，并给出「什么项目适合、什么项目别用」的判断依据。

本文只讨论样式方案本身的工程取舍。构建工具代际、包管理与体积预算详见站内《前端工程化》，渲染性能与重排重绘详见《前端性能优化》，这里不重复展开。

传统 CSS 的三个真实成本

讨论 Tailwind 之前要先承认传统 CSS 的成本不在「写起来慢」，而在这三处：

第一是命名。CSS 的作用域是全局的，所以命名不是审美问题而是隔离机制。BEM 之类的规范存在的唯一理由就是用命名约定模拟作用域。给 card__header--highlighted 这种东西起名、并让五个人起得一致，是持续消耗注意力的工作，而它对最终产品没有任何价值。

第二是删除。这是核心问题：你无法安全删除一条 CSS 规则。删之前要证明整个代码库里没有任何模板、任何动态拼接的字符串、任何第三方内容会用到那个类名，而这个证明在有服务端模板或富文本内容的项目里基本做不到。结果是 CSS 文件只增不减，两年后没人知道哪一半是死的。

第三是约束缺失。只要能写 padding: 13px，就一定会有人写 13px，另一个人写 14px。设计系统文档拦不住它，因为文档没有执行力。

上图的「僵尸规则」状态是传统 CSS 的稳定态：一旦进入就很难离开。工具类方案的价值就在于它把这个状态机砍掉了一半——样式写在使用它的元素上，删元素等于删样式，不存在「无法证明无人引用」的情形。

产物体积为什么与项目规模脱钩

Tailwind 的生成逻辑是：扫描源文件里出现过的字符串，只为真实出现的类生成规则。所以产物体积正比于项目里用到的不同工具类的数量，而不是页面数。由于常用类（间距、颜色、flex、字号）在所有页面高度重合，体积会很快趋于饱和。

项目阶段页面/组件量级传统 CSS 压缩后量级工具类压缩后量级增长形态
原型5 页5-15 KB6-9 KB工具类有固定起点
中型产品50 页 / 200 组件80-200 KB10-18 KB工具类接近饱和
大型产品300 页以上300 KB 以上且含大量死代码15-30 KB工具类仅随新用法缓慢上升
长期维护 3 年多次改版只增不减，删除风险高随代码删除同步下降

注意两点。第一，工具类有「固定起点」：预检样式与基础层是必然开销，所以极小项目上它不占优势。第二，上表的传统 CSS 数字包含死代码，这恰恰是重点——它不是理论体积而是真实线上体积。

# 核查 CSS 产物真实体积（gzip 后才是用户感知的大小）
npx tailwindcss -i src/input.css -o /tmp/out.css --minify
wc -c /tmp/out.css
gzip -c /tmp/out.css | wc -c

# 统计产物里有多少条规则，判断是否有配置导致的过度生成
grep -o '^\.[^ {]*' /tmp/out.css | sort -u | wc -l

# 若体积异常偏大，先看是不是 content 扫描范围包含了 node_modules
# 或者 safelist 里写了通配，把整组颜色阶梯都生成了出来

判读方式：中型项目 gzip 后超过 40 KB 基本可以断定配置有问题，最常见的原因是扫描范围包含依赖目录、safelist 使用了过宽的正则、或者自定义了巨大的色板与间距 scale。

需要强调的是：这四种并非互斥。常见的稳态组合是「工具类做九成布局与视觉 + 一个薄薄的全局 CSS 层放令牌和重置」。真正要避免的是工具类与 CSS-in-JS 并存，两者都想管同一个属性时，谁赢取决于注入顺序，调试成本极高。

三个「谨慎」分支值得多说一句。组件库场景的问题不是技术不可行，而是把构建期依赖传递给了使用方；主题场景的问题是工具类的令牌默认是编译期决定的，运行时换肤必须落到 CSS 变量上；动态值场景的问题是类名是静态字符串，无法表达连续数值。

v4 带来的变化

变化点v3 的做法v4 的做法迁移注意
配置载体JavaScript 配置文件导出 theme 对象在 CSS 里用 @theme 声明令牌需把 theme 配置逐项翻译，JS 配置仍可通过显式引入兼容
引入方式三条指令分别引入 base、components、utilities一条 @import 引入框架自定义层的插入位置改为用 CSS 层级语法控制
内容扫描必须手写 content 路径数组自动发现项目文件，可显式追加来源不在项目目录内的模板（如依赖包里的组件）仍需显式声明
令牌暴露需插件或手写才能拿到 CSS 变量@theme 里的令牌自动生成 CSS 变量换肤实现方式可以简化，旧的变量命名要对齐
引擎PostCSS 为主的实现Oxide，核心部分用 Rust 重写构建更快；自定义 PostCSS 插件链要重新验证
浏览器基线覆盖较旧浏览器依赖较新的 CSS 特性（层级、变量、颜色函数）需要支持老旧浏览器的项目先评估再升
/* v4：配置就是 CSS。令牌在这里定义，自动变成可用的工具类与 CSS 变量 */
@import "tailwindcss";

/* 若模板不在默认扫描范围内（例如依赖包里的组件），显式追加来源 */
@source "../node_modules/@acme/ui/dist/**/*.js";

@theme {
  /* 只声明项目真正需要的阶梯，色板越大产物越大 */
  --color-brand-50:  oklch(0.97 0.02 250);
  --color-brand-500: oklch(0.62 0.17 250);
  --color-brand-700: oklch(0.48 0.15 250);

  /* 间距 scale 决定了团队只能用这些值，这就是约束的执行力 */
  --spacing-gutter: 1.25rem;

  /* 字号与行高成对定义，避免各处单独写 leading */
  --text-body: 0.9375rem;
  --text-body--line-height: 1.7;
}

/* 主题切换落在 CSS 变量上：类名不变，变量换值 */
@layer base {
  :root { --surface: var(--color-brand-50); }
  [data-theme="dark"] { --surface: oklch(0.21 0.02 250); }
  body { background: var(--surface); }
}

这段配置里有两个可以直接复用的决策：色板只声明用到的阶梯（默认全量色板会让候选类数量成倍增加），以及把主题切换做在 CSS 变量而不是两套类名上（后者会让每个组件都要写 dark 变体，维护量翻倍）。

同一个卡片的两种写法

<!-- 传统写法：需要三个名字，样式在另一个文件，删除时要回去清理 -->
<article class="promo-card promo-card--featured">
  <h3 class="promo-card__title">季度报告</h3>
  <p class="promo-card__desc">本季度关键指标与同比变化</p>
</article>

<!-- 工具类写法：值全部来自 scale，删掉这段样式即消失 -->
<article class="rounded-lg border border-slate-200 bg-white p-5 shadow-sm
                hover:shadow-md focus-within:ring-2 focus-within:ring-brand-500">
  <h3 class="text-base font-semibold text-slate-900">季度报告</h3>
  <p class="mt-2 text-sm leading-relaxed text-slate-600">本季度关键指标与同比变化</p>
</article>

对比要看的不是字符数，而是三件事：工具类版本里没有出现任何新名字；padding 与 margin 的值只能从 scale 里取；focus-within:ring-2 这类状态样式不需要在另一个文件里再开一个选择器。代价同样清楚：这段 HTML 读起来比左边慢。

💡
一句话结论

原子类不是「把 CSS 写回 HTML」，而是用可读性换可删除性与约束执行力。如果你的项目会活很多年、会多次改版、有多人同时改样式，这笔交易划算；如果是一次性交付的页面或对外发布的组件库，它的收益就小得多。

❌
最容易踩的坑
  • 用字符串拼类名：把颜色或尺寸拼进类名，生成器扫不到这个字符串，线上样式直接缺失。必须写完整类名，或用映射表把变量映射到完整类名。
  • 扫描范围漏目录：某个目录没有被扫描到，那个目录下所有页面样式整片丢失，而本地开发时因为缓存往往看不出来。
  • 扫描范围包含依赖目录：把依赖目录纳入扫描，构建变慢且产物里混入大量无用规则，体积膨胀几倍。
  • 叠加两个冲突类：同时写两个控制同一属性的类，谁生效取决于产物里的源码顺序，不是你书写的顺序，条件样式必须用合并工具消解冲突。
  • 把 apply 当成万能解药：大量用 apply 把工具类打包成语义类，等于把死代码和命名问题原样搬回来，还多了一层间接。
  • 自定义全量色板：为了「以后可能用到」把十几种颜色各十一个阶梯全配上，候选类数量成倍上涨，产物体积随之上升。
  • 用任意值绕过 scale：随手写任意像素值，约束立刻失效，而且这些值散落各处，后续统一调整时无法批量修改。
  • 与 CSS-in-JS 混用管同一属性：两套机制争夺同一属性，胜负取决于样式注入顺序，本地与生产表现可能不一致。
  • 不锁类名顺序：不装排序插件，每个人写的顺序不同，合并冲突频发且 diff 无法阅读。
  • 忘掉焦点可见样式：只写 hover 不写 focus，键盘用户完全失去焦点指示，这是最常见的可访问性回归。
  • 升级 v4 不看浏览器基线：v4 依赖较新的 CSS 特性，需要兼容老旧浏览器的项目升级后会出现整体样式异常。
  • 只看未压缩体积做判断：CSS 的 gzip 压缩率很高，用未压缩数字评估传输成本会得出错误结论，核查时一定看压缩后大小。
