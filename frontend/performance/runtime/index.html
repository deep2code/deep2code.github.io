浏览器渲染管线与运行时性能

🏷️ 前端性能

这篇只讲浏览器运行时与渲染性能：主线程上发生了什么、哪些操作会把一帧的预算吃光、内存去哪了。网络与加载层面的内容（Core Web Vitals 三指标定义、TTFB 构成、缓存头与压缩、HTTP/2 与 /3、资源提示、SSR 与 CSR 的成本对照）详见站内《前端性能：加载与缓存》一篇，本文一律不重复。

一个前提数字：屏幕按 60 Hz 刷新时，每帧的总预算是 16.7 ms，浏览器自身开销之后留给你的通常不到 10 ms。JS 执行、样式计算、布局、绘制的大部分工作都在同一条主线程上串行完成，所以运行时性能问题基本都可以归结为一句话：这一帧里主线程做的事太多了。

主线程与长任务：50 ms 是分界线

任务执行期间主线程无法响应输入，用户的点击与按键只能排队。超过 50 ms 的任务被记为长任务，因为算上后续的事件处理与渲染，用户感知的响应延迟就会突破可容忍范围。真正反映体验的指标是「交互到下一次绘制」的延迟，它由三段组成：输入延迟（主线程正忙，事件在排队）、事件处理时长（你的回调 + 框架渲染）、以及渲染与呈现时长。

强制同步布局：循环里交替读写

浏览器会把样式与布局的计算攒到帧末统一做。但如果你在修改样式之后立刻读取几何信息，浏览器为了返回准确值必须当场完成样式计算与布局——这就是强制同步布局。放进循环就成了布局抖动：每次迭代强制一次完整重排，几十个元素就能让一帧超过 100 ms。在性能面板里表现为密集的布局块，并带有强制重排的告警标记。

// 坏例子：读 - 写 - 读 - 写 交替，每次迭代强制一次重排
// 200 个元素在中端手机上可以轻松跑到 150 ms 以上
function resizeAllBad(items) {
  for (const el of items) {
    const w = el.offsetWidth;        // 读：强制浏览器完成布局（前一次的写还没结算）
    el.style.width = w * 1.1 + 'px'; // 写：布局失效
  }
}

// 好例子：先批量读，再批量写，全程只有一次布局
function resizeAllGood(items) {
  // 阶段一：只读，浏览器可以复用同一次布局结果
  const widths = items.map((el) => el.offsetWidth);
  // 阶段二：只写，所有失效合并到帧末一次性结算
  items.forEach((el, i) => { el.style.width = widths[i] * 1.1 + 'px'; });
}

// 更稳的做法：把「写」放进下一帧的回调，和浏览器的节奏对齐
function alignToFrame(items) {
  const rects = items.map((el) => el.getBoundingClientRect()); // 读
  requestAnimationFrame(() => {                                // 写
    items.forEach((el, i) => {
      el.style.transform = 'translateY(' + rects[i].top * 0.1 + 'px)'; // 用 transform 而不是 top
    });
  });
}

长列表虚拟化：单项收益最大的优化

渲染一万行意味着创建一万套 DOM 节点，样式计算、布局与内存占用都与节点数成正比，框架层的 memo 或 diff 优化改变不了这个量级。虚拟化只渲染可视区加少量缓冲，节点数从上万降到几十，滚动时替换内容而不是增删节点。

指标 全量渲染 10000 行 虚拟化（可视 20 行 + 缓冲） 备注
DOM 节点数 数万（每行含多个子节点） 数十到数百 这是所有后续差异的根源
首次渲染耗时 秒级，必然是长任务 与一屏内容相当，通常十几毫秒 中端设备差距更大
内存占用 随行数线性增长 基本恒定 移动端可能直接被系统回收标签页
滚动流畅度 合成层过大、重绘范围大，易掉帧 稳定 配合内容可见性提示效果更好
实现复杂度 无 中：定高简单，不定高需测量缓存 用现成库，不要从零写
副作用 无 页内查找与无障碍读屏只能看到可视项；打印需特殊处理 需要全量导出时走后端生成 
// 虚拟化的核心只有三件事：撑高度、算区间、平移窗口
// 这段是定高版本的最小实现，用来理解原理；生产请用成熟库
function createVirtualList({ container, total, rowHeight, overscan = 5, renderRow }) {
  const spacer = document.createElement('div');
  spacer.style.height = total * rowHeight + 'px'; // 一 撑出总高度 让原生滚动条正确
  const viewport = document.createElement('div');
  viewport.style.position = 'relative';
  spacer.appendChild(viewport);
  container.appendChild(spacer);

  let raf = 0;
  function update() {
    const scrollTop = container.scrollTop;          // 读 集中在这一处
    const height = container.clientHeight;
    // 二 由滚动位置算出要渲染的区间，两端各留缓冲避免快速滚动露白
    const start = Math.max(0, Math.floor(scrollTop / rowHeight) - overscan);
    const end = Math.min(total, Math.ceil((scrollTop + height) / rowHeight) + overscan);

    viewport.innerHTML = '';                        // 写 集中在这一处
    const frag = document.createDocumentFragment();
    for (let i = start; i < end; i++) {
      const row = renderRow(i);
      // 三 用 transform 定位而不是 top，位移只走合成不触发重排
      row.style.transform = 'translateY(' + i * rowHeight + 'px)';
      row.style.position = 'absolute';
      row.style.height = rowHeight + 'px';
      frag.appendChild(row);
    }
    viewport.appendChild(frag);
  }

  // 滚动回调里只做一次 rAF 节流，绝不在这里读取 getBoundingClientRect
  container.addEventListener('scroll', () => {
    if (raf) return;
    raf = requestAnimationFrame(() => { raf = 0; update(); });
  }, { passive: true }); // passive 告知浏览器不会阻止默认滚动，避免滚动被延迟

  update();
  return () => { container.innerHTML = ''; }; // 清理：移除节点与监听，防止泄漏
}

内存问题：泄漏的四个典型形态

单页应用不像后端进程那样有明确的请求边界，一个标签页可能开着一整天。泄漏的后果不只是内存占用上涨，还包括 GC 停顿变长、旧组件的监听器继续执行导致行为诡异。

泄漏形态 典型代码 现象 定位方法
未移除的事件监听 组件里给 window 或 document 加监听但没有清理 切换页面若干次后同一逻辑执行多遍 DevTools 的事件监听器面板查看数量随操作增长
游离 DOM 用变量或闭包持有了已从文档中移除的节点 内存持续上涨且不回落 堆快照中筛选 detached 关键字，看保留路径是谁在引用
定时器与订阅未清理 setInterval、WebSocket、IntersectionObserver 没有关闭 后台标签页仍在发请求与重渲染 性能面板录制时看周期性的任务尖峰
无上限的缓存 用普通对象缓存接口结果或图片，永不淘汰 使用越久越慢，最终标签页崩溃 堆快照对比两次操作间的对象数量差
💡
堆快照的正确用法

单看一次快照没有意义。做法是：进入页面拍快照一，执行怀疑泄漏的操作若干次（比如打开关闭弹窗十次）并手动触发垃圾回收，拍快照二，然后用比较视图看哪些对象数量只增不减。重点看保留路径，它会告诉你是哪个闭包、哪个数组、哪个全局变量在持有这些对象。游离 DOM 用 detached 关键字筛选最快。

动画性能

做法 与刷新率同步 后台标签页行为 评价
CSS 过渡与关键帧动画（transform、opacity） 是 自动暂停 首选，可由合成线程独立运行，主线程繁忙时仍然流畅
Web Animations API 是 自动暂停 需要用 JS 精细控制时的首选，同样可脱离主线程
requestAnimationFrame 是，每帧回调一次 暂停 适合逐帧计算的动画；回调里绝不要读几何属性
setTimeout 或 setInterval 驱动 否，会与刷新错位 被限流但仍执行 会出现抖动与丢帧，高刷屏上更明显，不要用来做动画
动画 top、left、width、height —— —— 每帧一次重排，最常见的动画卡顿原因
will-change 常驻在大量元素上 —— —— 每层占显存，层管理本身有成本，低端设备反而掉帧

will-change 的正确用法：只在交互即将开始时临时加上（如按下或悬停），动画结束后立即移除；或只作用于确实持续变化的少数元素。不要写在通用类上，更不要给列表的每一项都加。是否真的多出了图层，可以在浏览器的图层工具里核对层数量与显存占用。

度量：从火焰图到线上分布

性能面板的读法：顶部的帧条看有没有红色（掉帧）；主线程轨道里宽而带红色三角的块就是长任务，向下展开是调用栈，宽度代表耗时而不是次数；紫色的布局块密集出现说明有布局抖动；把 CPU 降速设为 4 倍或 6 倍再录一遍，才接近真实用户设备。本地录制只能发现问题，真实分布必须靠线上采集。

// 生产环境采集：长任务 + 交互延迟，找出真正拖慢用户的代码
// 1) 长任务：定位「谁占着主线程」
if ('PerformanceObserver' in window) {
  try {
    const longTaskObserver = new PerformanceObserver((list) => {
      for (const entry of list.getEntries()) {
        // entry.duration 超过 50 ms 才会被记录
        // attribution 只能给到容器级别（是否来自 iframe），定位仍需结合采样
        report('long-task', {
          duration: Math.round(entry.duration),
          startTime: Math.round(entry.startTime),
          page: location.pathname,
        });
      }
    });
    // buffered 让页面加载早期已发生的长任务也能被收到
    longTaskObserver.observe({ type: 'longtask', buffered: true });
  } catch (e) { /* 部分浏览器不支持 longtask，静默降级 */ }

  // 2) 交互延迟：取本次访问中最慢的那次交互，这才是用户抱怨的来源
  let worst = 0;
  const eventObserver = new PerformanceObserver((list) => {
    for (const entry of list.getEntries()) {
      // duration 覆盖「输入延迟 + 事件处理 + 下一次绘制」
      if (entry.duration > worst) {
        worst = entry.duration;
        report('slow-interaction', {
          name: entry.name,                 // pointerdown、keydown、click 等
          duration: Math.round(entry.duration),
          target: entry.target?.tagName ?? 'unknown',
        });
      }
    }
  });
  // durationThreshold 默认 104 ms，设小一些能看到更多样本
  eventObserver.observe({ type: 'event', durationThreshold: 40, buffered: true });
}

function report(kind, data) {
  // 用 sendBeacon：页面关闭时也能发出，且不阻塞卸载
  navigator.sendBeacon?.('/api/rum', JSON.stringify({ kind, ...data }));
}

反模式速查

反模式 表面症状 根因 正确做法
滚动或动画回调里读几何属性 滚动掉帧，手指跟不上 强制同步布局，把可走合成的滚动拖回主线程 IntersectionObserver 或 ResizeObserver，读写分离
用 top 与 left 做位移动画 动画抖动，低端机明显 每帧触发重排与重绘 改用 transform，配合 CSS 过渡或 Web Animations
长列表全量渲染 首次渲染秒级卡死 DOM 节点数与数据量成正比 虚拟化，用成熟库
will-change 加在所有元素上 内存与显存上涨，滚动更卡 图层数量爆炸，管理成本超过收益 交互前临时加，结束即移除
用 setInterval 驱动动画 动画不流畅，高刷屏上更差 与刷新率不同步，后台仍执行 CSS 动画或 requestAnimationFrame
在前端做大数据量聚合排序 交互后长时间无响应 主线程被独占 下推到服务端，或移入 Web Worker
只在高配开发机上测性能 线上投诉与本地表现完全不符 开发机单核性能是中端手机的数倍 CPU 降速 4 到 6 倍复测，并采集线上分布

最容易踩的坑

❌
避坑清单
  • 在滚动或 requestAnimationFrame 回调里调用 getBoundingClientRect 或读 offsetWidth，每帧强制一次重排，本可由合成线程完成的滚动被拖回主线程。
  • 在循环里交替读几何属性和写样式，造成布局抖动；正确姿势是先批量读进数组，再批量写。
  • 用 top 与 left 做位移动画。改 transform 才能只走合成，这是动画卡顿最常见的单一原因。
  • 长列表全量渲染，然后花几天给行组件加 memo。节点数量级不变，优化不可能生效。
  • 把 will-change 写在通用类或列表每一项上。每个图层占显存，低端设备上直接掉帧。
  • 用 setInterval 做动画，与屏幕刷新不同步，在高刷屏上抖动更明显，后台标签页也仍在执行。
  • 滚动监听没有加 passive 选项，浏览器必须等回调返回才能决定是否滚动，输入延迟直接上升。
  • 组件卸载时忘了移除 window 监听、清定时器、断开 observer 与 WebSocket，切几次页面后同一逻辑执行多遍。
  • 用普通对象做无上限缓存（接口结果、图片、大数组），页面开得越久越慢，最后标签页崩溃。
  • 把 ECharts、地图这类第三方实例放进框架的深度响应式结构，递归代理上万内部属性，首屏直接卡住。
  • 在前端做本该由后端完成的排序、分组、聚合，一次交互就是一个几百毫秒的长任务。
  • 只看平均耗时。平均值会被大量快速交互稀释，要看 75 分位与最差样本。
  • 只在开发机上验证性能，不开 CPU 降速，也不采集线上数据，于是永远修不到真正慢的那部分用户。
  • 把渲染性能问题当成网络问题来治（继续加 CDN、继续压缩），而瓶颈其实在主线程的 JS 执行上。
