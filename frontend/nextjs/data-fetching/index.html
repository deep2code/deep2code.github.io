数据获取与缓存：四层缓存与失效

Next.js 最容易出事的地方就是缓存。不是因为它做得差，而是因为它在四个不同的层次上各有一套缓存，默认值还随版本变过，而使用者以为自己在跟一层打交道。「改了数据页面不更新」「明明设了缓存数据库还是被打满」「刷新几次内容在新旧之间跳」这三类问题，根因几乎都是把层搞混了。

这篇的目标是让你以后遇到缓存问题时，能先定位到层，再决定清哪一层。渲染时机与静态动态判定见 Next.js 的渲染模型，自托管下的缓存共享配置见 部署形态与运行时约束。HTTP 层的缓存头与 CDN 策略站内 前端性能：从后端视角看 已写透，这里只讲框架内部这四层。

四层缓存全景

用后端的话对齐一下

① 是一次请求内的本地 map 去重，相当于 DataLoader；② 是应用层的结果缓存，相当于自己写的 Redis 缓存；③ 是页面级整体缓存，相当于反向代理缓存整页 HTML，只不过它在应用进程里；④ 是客户端 SDK 的本地缓存，服务端没法直接清掉它。四层各管一段，清哪一层取决于旧数据是从哪一层拿到的。

① Request Memoization：省掉重复查询，但别指望太多

同一次渲染里，布局要用户信息，页面也要，侧边栏也要。写三次 fetch('/api/me')，实际只发一次——这一层解决的就是「组件级取数导致同一份数据被重复查」的问题。它不需要配置，键是 URL 加上请求方法与关键选项。

情形是否去重原因
同一渲染内两处 fetch 同一 GET URL是命中记忆化
URL 多了一个无关的时间戳参数否键不同，这是最常见的失效原因
POST 请求否非幂等，不做去重
用 ORM 或数据库驱动查询否不经过 fetch
在 Route Handler 里否不属于一次组件渲染过程
两个不同用户的并发请求否作用范围是单次渲染，不跨请求

② Data Cache 与 fetch 的缓存语义：注意版本默认值反转

这是升级时最容易出事的一处。Next 14 的 fetch 默认缓存，Next 15 改成默认不缓存。同一份代码，升级后行为完全相反：在 14 上你可能困惑「数据怎么一直是旧的」，在 15 上你可能困惑「数据库 QPS 怎么突然翻了几倍」。

写法Next 14 行为Next 15 行为对路由渲染方式的影响
fetch(url) 不带选项缓存，等同 force-cache不缓存，等同 no-store14 下可静态，15 下这条 fetch 不再帮你保持静态
fetch(url, { cache: 'force-cache' })缓存缓存路由可保持静态
fetch(url, { cache: 'no-store' })不缓存不缓存路由降级为动态渲染
fetch(url, { next: { revalidate: 60 } })缓存 60 秒缓存 60 秒路由可静态，到期后台重新生成
fetch(url, { next: { tags: ['posts'] } })缓存并打标签需配合 force-cache 或 revalidate 才会缓存可被 revalidateTag 精确失效
路由段 export const revalidate = 60该段内默认 60 秒同样生效比逐个 fetch 写更好维护
// lib/data.ts —— 跨版本安全的写法：任何一个 fetch 都显式声明意图
// 判断依据只有一条：这份数据允许旧多久

// 1. 商品目录：允许旧 5 分钟，且要能被后台编辑后立刻刷新
export function getCatalog() {
  return fetch('https://api.internal/catalog', {
    // 显式写 force-cache，不依赖版本默认值
    cache: 'force-cache',
    next: {
      revalidate: 300,          // 兜底的时间失效，防止标签失效漏调用
      tags: ['catalog'],        // 后台保存时按标签精确失效
    },
  }).then((r) => r.json())
}

// 2. 账户余额：必须实时，明确接受「这条路由变成动态渲染」这个代价
export function getBalance(token: string) {
  return fetch('https://api.internal/balance', {
    cache: 'no-store',          // 注意：这一行会让整条路由退出静态生成
    headers: { authorization: `Bearer ${token}` },
  }).then((r) => r.json())
}

// 3. 汇率：可以旧一点，但绝不能因为下游抖动而让页面整体失败
export async function getRate() {
  const res = await fetch('https://api.internal/rate', {
    cache: 'force-cache',
    next: { revalidate: 60 },
  })
  // Data Cache 只缓存成功响应；4xx 与 5xx 不会被缓存，
  // 所以下游持续报错时这里会持续真打，要自己兜住
  if (!res.ok) return { rate: null, stale: true }
  return res.json()
}

③ Full Route Cache 与动态渲染的互斥关系

整路由缓存存的是渲染完的整页产物。它只对静态路由存在——一旦路由被判定为动态渲染，这一层直接不可用。这就是为什么个性化页面不可能整页缓存，只能靠第二层缓存数据部分。

路由特征Full Route CacheData Cache结论
纯静态内容可用，整页命中可用服务端成本接近零
静态加时间失效可用，到期后台重生成可用ISR，性价比最高
用了 cookies()不可用可用每请求都要渲染，但下游调用可被缓存挡住
用了 searchParams不可用可用同上
某个 fetch 用了 no-store不可用这条不缓存，其他仍可缓存只为一处实时数据牺牲了整页缓存，值不值得要算
声明 force-dynamic不可用可用显式选择

所以有一个很实用的重构手法：把需要 cookies() 的那一小块下推。页面主体保持静态可整页缓存，用户头像、未读数这些个性化部分交给客户端组件在 hydration 后拉一次，或者等 PPR 成熟后交给它。代价是那一小块会有短暂的空态。

④ Router Cache 与四种失效手段各清哪一层

这张表是本篇最实用的东西。「改了数据页面不更新」几乎都是清错了层。

手段调用位置① 记忆化② Data Cache③ Full Route Cache④ Router Cache
revalidate = N 到期路由段或 fetch 选项不涉及清该条目清该路由不清
revalidateTag('x')Server Action 或 Route Handler不涉及清所有带此标签的条目清依赖这些数据的路由不清，仅当次响应携带刷新指令
revalidatePath('/p')Server Action 或 Route Handler不涉及清该路径用到的条目清该路由同上，只影响发起这次请求的客户端
router.refresh()客户端组件不涉及不清不清清当前浏览器的路由缓存并重取 payload
硬刷新页面浏览器不涉及不清不清清
重新部署发布流程不涉及默认保留清空重建客户端下次加载新资源后失效

两个最容易误解的点：revalidatePath 清不掉别人浏览器里的 Router Cache，它只能让发起这次请求的那个客户端刷新；而 router.refresh() 清不掉服务端的 Data Cache，服务端如果还持有旧值，刷新回来的还是旧值。这两个方向搞反，就会出现「我明明清了缓存」但现象毫无变化。

// app/admin/actions.ts —— 写操作之后按标签失效，而不是无脑清整站
'use server'

import { revalidateTag, revalidatePath } from 'next/cache'
import { requireAdmin } from '@/lib/auth'
import { db } from '@/lib/db'

export async function updateProduct(id: string, patch: { name?: string; price?: number }) {
  await requireAdmin()   // Action 是公开端点，鉴权必须在这里做

  await db.product.update({ where: { id }, data: patch })

  // 标签失效：所有带 catalog 标签的 fetch 条目，以及依赖它们的路由产物一起清
  revalidateTag('catalog')
  // 细粒度标签：只清这一个商品的详情页数据
  revalidateTag(`product:${id}`)
  // 路径失效：列表页如果不走 fetch 而是直接查库，标签管不到它，只能按路径清
  revalidatePath('/admin/products')

  // 注意：以上三行清的都是服务端缓存。
  // 其他用户浏览器里的 Router Cache 不会被远程清空，
  // 他们最多等约 30 秒到 5 分钟，或者自己触发一次刷新。
  return { ok: true }
}

不走 fetch 的数据源不受 Data Cache 管

这点后端工程师尤其容易想当然。Data Cache 是挂在 Next 扩展过的 fetch 上的，直连数据库、用 ORM、用 Redis 客户端、用 gRPC，全都绕过这一层。你在路由段写了 revalidate = 300，只影响整路由缓存与 fetch 条目，不会让你的 db.query 少执行一次。

数据来源自动进 Data Cache怎么缓存能否按标签失效
fetch 内部或外部 HTTP 接口按选项决定cache 与 next.revalidate能，加 tags
ORM 或数据库驱动不进用 unstable_cache 包一层能，包装时传标签
Redis 客户端直连不进本身就是缓存，注意别叠两层过期时间自己管理
文件系统读取不进unstable_cache 或进程内缓存同上
第三方 SDK 内部用了自己的 http 客户端不进包一层，或改成裸 fetch 调用包装后可以
// lib/cached-queries.ts —— 让 ORM 查询也能被缓存与按需失效
import { unstable_cache } from 'next/cache'
import { db } from '@/lib/db'
import { toProductDTO } from '@/lib/dto'

// 第二个参数是键的组成部分，函数参数会自动并入键；
// 键设计错了就是缓存串号，这跟自己写 Redis 缓存要考虑的完全一样
export const getProduct = unstable_cache(
  async (id: string) => {
    const row = await db.product.findUnique({ where: { id } })
    return row ? toProductDTO(row) : null
  },
  ['product-by-id'],
  {
    revalidate: 300,                 // 兜底过期，防止标签失效漏调用导致永久旧数据
    tags: ['catalog'],               // 与 fetch 侧共用同一套标签命名，失效时一起清
  },
)

// 重要边界：
// 1. 缓存的是返回值，必须可序列化，别在里面返回 ORM 实体或类实例
// 2. 里面不要读 cookies 或 headers，缓存键不包含它们，会导致用户之间串数据
// 3. 与用户相关的查询要么别缓存，要么把 userId 作为参数进键
export const getMyOrders = async (userId: string) =>
  unstable_cache(
    async (uid: string) => db.order.findMany({ where: { userId: uid } }),
    ['orders-by-user'],
    { revalidate: 30, tags: [`user:${userId}`] },
  )(userId)

多实例部署下的缓存一致性

这是自托管最容易被忽略的一步，也是「刷新几次内容跳来跳去」的标准根因：Data Cache 与整路由缓存默认写在实例本地的文件系统里。三个副本就是三份互不相识的缓存。

sequenceDiagram participant A as 管理后台 participant LB as 负载均衡 participant P1 as 副本 1 participant P2 as 副本 2 participant P3 as 副本 3 A->>LB: 保存商品，触发按需失效 LB->>P2: 请求只落到一个副本 P2->>P2: 清掉本地缓存并重新生成 Note over P1,P3: 副本 1 与副本 3 仍持有旧产物 A->>LB: 刷新前台页面 LB->>P1: 轮询落到副本 1 P1-->>A: 返回旧价 A->>LB: 再刷新一次 LB->>P2: 这次落到副本 2 P2-->>A: 返回新价 Note over A,P3: 现象就是内容在新旧之间跳来跳去
方案一致性改造成本适用注意
只用时间失效，不用按需失效最终一致，窗口等于 revalidate零内容对时效不敏感各副本过期时间点不同，仍会短暂不一致
配置共享 cacheHandler 指向 Redis强一致中，要自己实现或用社区实现多副本自托管的标准答案Redis 挂了会退化，要考虑降级路径
缓存后端放对象存储强一致中产物体积大、读多写少延迟高于 Redis，注意列举成本
失效请求广播到所有副本接近强一致低，但脆弱副本数很少且固定扩缩容时漏广播，新副本仍是旧数据
单副本部署天然一致零流量小的内部系统失去水平扩展与滚动发布能力

最容易踩的坑
  • 从 Next 14 升到 15 后没有逐个检查 fetch，默认值反转让原本被静默缓存的请求全部变成真调用。
  • 在 URL 上拼时间戳来「保证拿到新数据」，顺手破坏了同一次渲染内的请求去重，一个页面查了五次同样的数据。
  • 以为路由段的 revalidate 能管住 ORM 查询，结果数据库压力与 PV 同阶。
  • revalidateTag 的标签名写错一个字符，没有任何报错，缓存就是不失效。
  • 只配按需失效不配过期兜底，某次失效调用因为异常被跳过，页面永久停在旧数据。
  • 在 unstable_cache 的回调里读 cookies() 或 headers()，缓存键不含身份，直接串用户。
  • 把 ORM 实体从 unstable_cache 返回，缓存序列化时报错或悄悄丢字段。
  • 以为重新部署会清掉 Data Cache。整路由缓存会重建，但 Data Cache 默认跨部署保留。
  • 多副本自托管不配 cacheHandler，按需失效只清一个副本，现象是内容跳来跳去。
  • Data Cache 只缓存成功响应，下游持续 500 时这一层等于不存在，页面会持续把错误暴露出去。
  • 在动态路由上花力气优化整页缓存。用了 cookies() 的路由根本没有这一层，只能优化数据层。
  • 给私有数据设了 force-cache，多个用户共享同一份缓存条目，等于横向越权。
