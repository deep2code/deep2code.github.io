部署形态与运行时约束

Next.js 的部署问题，本质上是选一种形态，然后接受它的约束。这些约束不是配置项，是硬的：静态导出拿不到服务端，Edge 运行时连不上 TCP 数据库，多副本不共享缓存就必然出现内容跳变，NEXT_PUBLIC_ 变量在构建期就被写死进产物。这些在托管平台上被平台替你解决掉了，自托管时全部要自己面对。

这篇从运维视角把四种形态、两种运行时、以及容器化落地的细节讲清楚。渲染时机见 Next.js 的渲染模型，四层缓存的语义见 数据获取与缓存。

⚠️
静态导出是单向门

选了 output: 'export' 之后，一旦业务需要「登录后展示」「内容编辑后立刻生效」「表单直接提交到服务端」，就得整体退回到 Node 服务形态。这不是加个开关的事——代码里所有依赖服务端的写法都要重做。评估时按「一年内会不会有这些需求」来判断，而不是按当前这一版有没有。

选形态之前先把资源量级算清楚。一个中等规模的 Next.js 进程常驻内存大致在 200 到 400 MB，动态渲染一条中等复杂度的路由约占 10 到 50 毫秒 CPU，于是单核能扛的动态渲染 QPS 就落在 20 到 100 这个量级——比大多数人的直觉低一个档。静态命中几乎不耗 CPU，所以容量估算要按动态路由的 QPS 算，而不是按总 PV 算，这两个数字在有缓存的站点上可能差一两个数量级。构建机要单独评估：构建期同时跑类型检查、打包与静态预渲染，内存峰值经常超过 2 GB，比运行时还高，CI 上内存给少了会以一个看不出原因的进程被杀收场。

选择规则很简单：middleware 天然在 Edge，其他一切默认留在 Node。只有确认这段代码不需要数据库、不需要 Node 模块、且冷启动敏感时，才考虑给某个路由声明 Edge 运行时。

容器化自托管：可抄的 Dockerfile

output: 'standalone' 会在 .next/standalone 下产出一个自带裁剪后依赖的最小运行目录，入口是 server.js。注意它不包含 public/ 与 .next/static/，这两个目录要自己拷进去或交给 CDN。

# syntax=docker/dockerfile:1
# ---------- 阶段 1：只装依赖，利用层缓存 ----------
FROM node:20-alpine AS deps
WORKDIR /app
# 只拷锁文件，依赖没变时这一层直接命中缓存
COPY package.json package-lock.json ./
RUN npm ci --ignore-scripts

# ---------- 阶段 2：构建 ----------
FROM node:20-alpine AS builder
WORKDIR /app
COPY --from=deps /app/node_modules ./node_modules
COPY . .
# 关键：NEXT_PUBLIC_ 变量在这一步被内联进客户端产物，
# 所以它属于构建期输入，运行时改环境变量不会生效
ARG NEXT_PUBLIC_SITE_URL
ENV NEXT_PUBLIC_SITE_URL=$NEXT_PUBLIC_SITE_URL
ENV NEXT_TELEMETRY_DISABLED=1
RUN npm run build

# ---------- 阶段 3：运行，镜像里不带源码与开发依赖 ----------
FROM node:20-alpine AS runner
WORKDIR /app
ENV NODE_ENV=production
ENV NEXT_TELEMETRY_DISABLED=1

# 非 root 运行：容器逃逸的第一道成本
RUN addgroup -g 1001 -S nodejs && adduser -u 1001 -S nextjs -G nodejs

# standalone 产物自带裁剪后的 node_modules 与 server.js
COPY --from=builder --chown=nextjs:nodejs /app/.next/standalone ./
# 这两个目录不在 standalone 里，必须单独拷
COPY --from=builder --chown=nextjs:nodejs /app/.next/static ./.next/static
COPY --from=builder --chown=nextjs:nodejs /app/public ./public

# ISR 与缓存产物的落盘目录，多副本场景下应该换成共享后端
RUN mkdir -p .next/cache && chown -R nextjs:nodejs .next/cache

USER nextjs
EXPOSE 3000
ENV PORT=3000
# 不设成全零地址，容器外访问不到，这是最常见的容器化翻车点
ENV HOSTNAME=0.0.0.0

# 直接 exec node，让进程拿到 PID 1 并能收到 SIGTERM；
# 用 npm start 会多一层 shell，信号可能传不下去
CMD ["node", "server.js"]

构建时环境变量与「一次构建多处部署」的冲突

变量类型何时确定改值是否需要重新构建是否进客户端产物能否一份镜像多环境
NEXT_PUBLIC_ 前缀构建时内联成字面量需要是默认不能
普通服务端变量运行时读取不需要否能
next.config 里的 env 字段构建时需要看使用位置不能
服务端读取后通过 props 下发运行时不需要是，但值来自运行时能，推荐
启动脚本替换产物占位符启动时不需要是能，但要小心替换范围

这一条跟后端奉行的「一次构建、多处部署」直接冲突。三种折中，按侵入性从低到高：

#!/bin/sh
# docker-entrypoint.sh —— 方案二：构建时写占位符，启动时替换
# 适合把接口域名、埋点 ID 这类非敏感配置做成运行时可变
set -eu

: "${RUNTIME_API_BASE:?RUNTIME_API_BASE must be set}"

# 只替换客户端产物目录，避免误改服务端代码；占位符要足够独特
find ./.next/static -type f -name '*.js' -print0 \
  | xargs -0 sed -i "s|__RUNTIME_API_BASE__|${RUNTIME_API_BASE}|g"

# 千万不要把密钥用这种方式注入客户端产物：它对任何访客都是可见的
exec node server.js

更干净的是方案三：把这类配置放在服务端，由根布局读 process.env 后通过 props 传给需要它的客户端组件。这样值在运行时确定，产物与环境彻底解耦，代价是多传一层 props。

ISR 与缓存在自托管下的落地

默认行为是把 ISR 产物与 Data Cache 写进 .next/cache，也就是容器本地文件系统。两个直接后果：容器重建缓存全丢；多副本各持一份，按需失效只清到其中一个。

sequenceDiagram participant CMS as 内容后台 participant LB as Service 或 Ingress participant A as Pod A participant B as Pod B participant R as 共享缓存后端 Note over A,B: 未配共享缓存时 CMS->>LB: 触发按需失效 LB->>A: 只命中一个 Pod A->>A: 清本地 .next/cache 并重建 Note over B: Pod B 仍返回旧产物，用户刷新看到内容跳变 Note over A,R: 配置 cacheHandler 指向 Redis 后 CMS->>LB: 触发按需失效 LB->>B: 命中任意一个 Pod B->>R: 删除对应键并写入新产物 A->>R: 下次请求读到的是同一份新产物 Note over A,B: 所有副本视图一致，容器重建也不丢缓存 
// next.config.ts
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  // 容器化必备：产出自带依赖的最小运行目录
  output: 'standalone',

  // 多副本的关键一步：把缓存读写指向共享后端。
  // cacheHandler 指向一个实现了 get / set / revalidateTag 的模块，
  // 社区有现成的 Redis 实现，也可以自己写一百行接到对象存储。
  cacheHandler: require.resolve('./cache-handler.mjs'),
  // 用了自定义 handler 就要关掉内存兜底，否则单实例内存副本会掩盖不一致
  cacheMaxMemorySize: 0,

  images: {
    // 必须显式白名单，否则等于开放一个任人调用的转码服务
    remotePatterns: [{ protocol: 'https', hostname: 'cdn.example.com' }],
    // 收窄尺寸集合：每个尺寸都是一次独立的 CPU 转换与一份缓存
    deviceSizes: [640, 828, 1200, 1920],
    imageSizes: [64, 128, 256],
    // 转换结果的最小缓存时间，避免热点图片被反复重算
    minimumCacheTTL: 86400,
  },

  // 反向代理或 CDN 之后要正确拿到客户端信息时，别自己猜，用标准头
  poweredByHeader: false,
  compress: false,   // 压缩交给前面的 Nginx 或 CDN 做，省 Node 的 CPU
}

export default nextConfig

如果暂时没条件上共享缓存，退一步的做法是只用时间失效、放弃按需失效，并接受各副本过期时间点不同带来的短暂不一致；这比配了按需失效却只生效在一个副本上要可预测得多。

# k8s 片段：探针、优雅下线、资源与安全上下文
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
  template:
    spec:
      terminationGracePeriodSeconds: 30
      securityContext:
        runAsNonRoot: true
        runAsUser: 1001
      containers:
        - name: web
          image: registry.example.com/web:1.4.2
          ports:
            - containerPort: 3000
          env:
            - name: HOSTNAME
              value: 0.0.0.0
            - name: NODE_OPTIONS
              # 容器内存上限之下留出余量，避免 OOMKilled
              value: --max-old-space-size=768
          readinessProbe:
            httpGet:
              # 健康检查路由要轻量：不查数据库，只证明进程能渲染
              path: /api/healthz
              port: 3000
            periodSeconds: 5
          livenessProbe:
            httpGet:
              path: /api/healthz
              port: 3000
            initialDelaySeconds: 20
            periodSeconds: 10
          lifecycle:
            preStop:
              exec:
                # 先等摘流，再让 SIGTERM 到达，避免滚动发布期间 502
                command: ["/bin/sh", "-c", "sleep 5"]
          resources:
            requests:
              cpu: 250m
              memory: 512Mi
            limits:
              memory: 1Gi

日志一律以结构化 JSON 打到标准输出，由采集侧处理，不要在容器里写日志文件。链路追踪用 instrumentation.ts 接 OpenTelemetry，把渲染耗时、下游调用、缓存命中标记成 span，这样「某条路由为什么慢」才有答案。探针语义、preStop 与 SIGTERM 的配合细节见站内 Kubernetes 专题，追踪体系的搭法见站内可观测性相关文章。

自托管时至少要盯四组指标：按路由维度的渲染耗时分位数（并且区分静态命中与动态渲染）、Data Cache 与整路由缓存的命中率、图片优化任务的排队长度与耗时、以及进程的堆内存与事件循环延迟。前两组回答「该不该加缓存、缓存配得对不对」，后两组回答「该不该扩容」。缺了缓存命中率这一项，所有关于性能的讨论都只能靠猜。

最容易踩的坑
  • 选了静态导出，半年后要加登录，只能整体推回 Node 形态重做。
  • 在 middleware 或 Edge 路由里 import 了数据库客户端，构建期不报错，部署后才炸。
  • 多副本没配共享 cacheHandler，按需失效只清一个 Pod，用户看到内容跳来跳去。
  • 配了自定义 cacheHandler 却没把内存缓存上限设为零，单实例内存副本掩盖了不一致，排查时现象飘忽。
  • 把 NEXT_PUBLIC_ 变量当运行时配置用，测试镜像直接推生产后接口域名还是测试环境的。
  • 用启动脚本替换产物占位符时把敏感值也替进去了，那份值对所有访客可见。
  • Dockerfile 里只拷了 .next/standalone，忘了 .next/static 与 public，页面裸奔没有样式。
  • CMD 写成 npm start，多一层 shell 导致 SIGTERM 传不到 Node 进程，滚动发布时在途请求被直接掐断。
  • 忘了设监听地址为全零，容器内 curl 通、Service 转发不通。
  • 不配 preStop 等待，Pod 删除后 Endpoints 还没同步完，客户端拿到一串 502。
  • 存活探针打的是会查数据库的接口，数据库一抖动全部副本连环重启。
  • 没给 Node 设堆上限，容器内存到顶后直接 OOMKilled，而日志里什么都看不到。
  • next/image 不配 remotePatterns 白名单，等于对外开放一个免费转码服务。
