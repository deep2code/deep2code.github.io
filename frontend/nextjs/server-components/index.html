Server Components 的边界与数据流

🏷️ Server Components

Server Components 解决的问题，用后端的话说就是省掉一层为自家页面服务的内部 API。以前写一个列表页要三步：写查询、包一个 HTTP 接口、在前端 fetch 这个接口并处理加载与错误。现在组件本身就跑在服务端，直接 await 数据库就行，那个只有自家页面调用、还要维护序列化与类型的接口层可以不存在。

代价是引入了一条新的边界：一部分组件在服务端执行，一部分在浏览器执行，两边靠序列化通信。这条边界跟远程调用的边界性质完全一样——有序列化约束、有安全边界、有延迟成本。搞不清边界在哪，就会出现「本地跑得好，上线密钥泄漏」「把 ORM 实体传下去直接报错」「整页标了 'use client' 于是 RSC 白用」这几类问题。

'use client' 是边界声明，不是文件标记

最常见的误解：以为这行指令只影响当前文件。实际上它声明的是边界的起点——从这个文件开始，它自己加上它 import 进来的整个模块子树，全部被划到客户端。

跨边界只能传可序列化的数据

这一点对后端工程师最有实际意义，因为它跟「实体不要直接当接口响应体」是同一条工程原则，只是这次编译器会替你把违规行为变成报错。

值类型能否跨边界传说明
字符串、数字、布尔、null能基础类型
纯对象、数组能要求属性本身也可序列化
Date、Map、Set、BigInt能RSC 协议支持，但要注意时区与精度在客户端的处理
Promise能这是「下传 Promise 配 Suspense」的基础
由 'use server' 定义的函数引用能传过去的是端点引用，不是函数体
普通函数、箭头函数、回调不能服务端函数体无法送到浏览器执行
类实例、ORM 实体不能带方法、原型链，常含懒加载代理
含循环引用的对象不能父子互相引用是 ORM 的常态
Symbol、WeakMap、流、连接对象不能没有序列化表示
// lib/dto.ts —— 边界处必须有这么一层，理由和后端不要直接返回实体一模一样
import 'server-only'   // 这个包的作用：一旦被客户端组件导入，构建期直接报错

import type { Order } from '@prisma/client'

// 客户端真正需要的字段，显式列出。多一个字段就是多一份泄漏面与 payload
export type OrderDTO = {
  id: string
  no: string
  amountText: string     // 金额在服务端就格式化好，避免客户端再引一个货币库
  createdAt: string      // 统一成 ISO 字符串，跨边界最省心
  canCancel: boolean     // 把「能不能取消」这个判断也在服务端算完
}

export function toOrderDTO(row: Order & { items?: unknown[] }): OrderDTO {
  return {
    id: row.id,
    no: row.orderNo,
    // 注意 Prisma 的 Decimal 是类实例，直接传会报不可序列化
    amountText: row.amount.toFixed(2),
    createdAt: row.createdAt.toISOString(),
    canCancel: row.status === 'PENDING',
    // 故意不带：internalRemark、riskScore、userId、items 里的反向引用
  }
}

组合模式：把交互下推到叶子

方向是单向的：Server Component 可以渲染 Client Component，反过来不行。但客户端组件可以通过 children 接收服务端渲染好的内容——这个口子是保持大部分树留在服务端的关键手法。

// components/collapsible.tsx —— 只有「展开收起」这一点交互过边界
'use client'
import { useState, type ReactNode } from 'react'

export default function Collapsible({ title, children }: { title: string; children: ReactNode }) {
  const [open, setOpen] = useState(false)
  return (
    <section>
      <button onClick={() => setOpen((v) => !v)}>{title}</button>
      {/* children 是服务端已经渲染好的结果，客户端只负责决定显不显示。
          这里没有把数据查询拉到客户端，也没有把子组件拖进 bundle */}
      {open && children}
    </section>
  )
}

// app/orders/page.tsx —— 服务端组件，把客户端组件当容器用
import Collapsible from '@/components/collapsible'
import { listOrders } from '@/lib/db'
import { toOrderDTO } from '@/lib/dto'

export default async function Page() {
  const rows = await listOrders()   // 直接查库，不经过任何 HTTP
  return (
    <Collapsible title="历史订单">
      {/* 这段在服务端渲染，bundle 里没有它的代码 */}
      <ul>
        {rows.map(toOrderDTO).map((o) => (
          <li key={o.id}>{o.no} · {o.amountText} · {o.createdAt}</li>
        ))}
      </ul>
    </Collapsible>
  )
}
组合方向是否可行原因替代手法
Server 里渲染 Client可以服务端输出里留一个客户端组件的占位引用—
Client 里 import Server 组件不行导入即把它拉进客户端子树，服务端能力全失改成通过 children 或 props 传入
Client 通过 children 接收服务端内容可以传过去的是已渲染结果，不是组件代码—
Client 调用服务端函数可以只能通过 Server Action 这个受控通道或走 Route Handler
Server 给 Client 传回调函数不行函数不可序列化传 Server Action 引用

写代码时的实用顺序是：默认一切都留在服务端，只有当某个元素需要响应用户输入时，才把那个元素单独抽成一个文件并在它上面标边界。按这个顺序写出来的树，客户端 bundle 通常只有反过来做的三分之一到一半。

Server Actions 本质是自动生成的 RPC 端点

这句话必须先立住：加了 'use server' 的函数，在构建时会被编译成一个带唯一 ID 的 HTTP 端点。客户端调用它，实际上是向当前路径 POST 一个带 action ID 与序列化参数的请求。它跟你手写的接口没有本质区别，唯一区别是路由和序列化代码由框架生成。

sequenceDiagram participant U as 用户 participant F as 客户端表单组件 participant N as Next 服务端 participant A as Action 函数 participant D as 数据库 U->>F: 点击提交 F->>N: POST 当前路径，携带 action ID 与序列化参数 N->>A: 按 ID 找到对应函数并调用 A->>A: 第一步取会话并校验身份 A->>A: 第二步校验参数 schema A->>D: 写入，同时校验这条记录属于当前用户 D-->>A: 结果 A->>N: 调用 revalidatePath 标记该路径失效 N-->>F: 返回序列化结果，并附带重新渲染后的 RSC payload F-->>U: 表单状态更新，页面数据同步刷新 Note over F,N: 攻击者可以跳过表单页面，直接构造这个 POST 请求
❌
这是本篇最重要的一条

Server Action 必须当成公开 API 对待。它可被直接调用，所以「只有登录后的页面才渲染这个按钮」提供不了任何保护。鉴权、越权检查、输入校验、速率限制，全部要写在 action 函数内部。授权模型与常见越权场景见站内 认证与授权。

// app/orders/actions.ts
'use server'

import { z } from 'zod'
import { revalidatePath } from 'next/cache'
import { getSession } from '@/lib/session'
import { db } from '@/lib/db'

const CancelInput = z.object({
  orderId: z.string().uuid(),
  reason: z.string().max(200).optional(),
})

export async function cancelOrder(raw: unknown) {
  // 1. 鉴权：不能假设「只有页面会调它」，这是一个公开端点
  const session = await getSession()
  if (!session) return { ok: false, code: 'unauthorized' as const }

  // 2. 输入校验：参数完全由客户端控制
  const parsed = CancelInput.safeParse(raw)
  if (!parsed.success) return { ok: false, code: 'invalid_input' as const }

  // 3. 越权检查：把归属条件写进 where，而不是先查出来再比对
  //    这样即便有并发更新也不会出现「查到时是自己的、写入时已易主」
  const affected = await db.order.updateMany({
    where: { id: parsed.data.orderId, userId: session.userId, status: 'PENDING' },
    data: { status: 'CANCELLED', cancelReason: parsed.data.reason ?? null },
  })
  if (affected.count === 0) return { ok: false, code: 'not_cancellable' as const }

  // 4. 失效对应路径的缓存，否则页面还是旧数据
  revalidatePath('/orders')

  // 5. 返回可序列化的结果对象，而不是抛异常：
  //    生产环境下抛出的错误消息会被脱敏，客户端拿不到有用信息
  return { ok: true as const }
}
维度Server ActionRoute Handler
调用方只为自家页面交互设计任何 HTTP 客户端，含移动端与第三方
HTTP 语义固定 POST，状态码不可控方法、状态码、响应头全可控
与页面缓存的联动可直接调 revalidatePath 并回传新 payload需要客户端自己刷新
渐进增强表单在 JS 未加载时也能提交需要自己写表单目标
文件上传与流式受 body 大小限制，默认 1 MB 量级可处理流式与大文件
鉴权责任在函数内部，无人代劳在 handler 内部，同样无人代劳
适合表单提交、状态切换、点赞收藏Webhook、开放接口、导出下载

数据流方向与瀑布问题

数据流是单向的：服务端取数 → 序列化进 RSC payload → 客户端 hydration 复活交互。这个模型很干净，但它天然鼓励「在需要数据的组件里就地 await」，于是瀑布几乎必然出现——父组件不 await 完，子组件根本不会开始渲染。

sequenceDiagram participant N as Next 渲染进程 participant D as 数据层 Note over N,D: 反模式：逐层就地 await，延迟累加 N->>D: 查用户 200ms D-->>N: 返回 N->>D: 查订单列表 200ms D-->>N: 返回 N->>D: 查推荐位 200ms D-->>N: 返回 Note over N: 总耗时约 600ms Note over N,D: 改法：无依赖的请求同层并行发起 N->>D: 同时发起三个查询 D-->>N: 三个结果陆续返回 Note over N: 总耗时约等于最慢那个 200ms
瀑布形态典型写法修法注意
同层串行连续三个 awaitPromise.all 并行确认它们之间真的没有数据依赖
父子串行父 await 完才渲染子，子再 await父层发起请求但不 await，把 Promise 当 props 传给子，子用 use() 取值并包 SuspensePromise 必须在服务端创建
列表里逐项查询map 里每项一个查询批量查询一次取回，或用 DataLoader 式聚合这就是后端的 N 加一问题，见站内 GraphQL 专题
客户端二次取数hydration 后再发一轮请求能在服务端拿到的就在服务端拿个性化内容有时确实只能这样
// app/dashboard/page.tsx —— 两种手法都在这里
import { Suspense } from 'react'
import Reviews from './reviews'

export default async function Page({ params }: { params: Promise<{ id: string }> }) {
  const { id } = await params

  // 手法一：同层无依赖的请求并行发起，总耗时等于最慢那个
  const [user, orders] = await Promise.all([getUser(id), listOrders(id)])

  // 手法二：慢查询不在这里 await，把 Promise 下传给子组件
  //         页面其余部分立刻可以流式输出，不被它拖住
  const reviewsPromise = listReviews(id)

  return (
    <main>
      <h1>{user.name}</h1>
      <OrderList items={orders} />
      <Suspense fallback={<p>评价加载中</p>}>
        {/* Reviews 内部用 use(promise) 取值；Promise 必须在服务端创建 */}
        <Reviews promise={reviewsPromise} />
      </Suspense>
    </main>
  )
}

还有一个容易被忽略的成本：服务端组件的产出是要通过网络传输的 RSC payload。你在服务端查回来一个上千行的列表，即便页面只展示前二十条，整份序列化结果也会进响应体。分页、字段裁剪、聚合这些后端习惯在这里完全适用，只是它们影响的是响应体积与客户端解析耗时，而不是数据库耗时。判断方法很直接：在网络面板里看这条路由的 payload 大小，动辄几百 KB 就说明你把整张表传下来了。

环境变量与密钥：泄漏总是间接发生的

场景是否进客户端 bundle何时确定值风险
Server Component 读 process.env.DB_URL不进运行时安全
该模块被任意客户端组件 import进构建时被内联密钥直接出现在浏览器可读的产物里
NEXT_PUBLIC_ 前缀变量进，设计如此构建时内联成字面量改值必须重新构建，一份镜像不能多环境复用
Route Handler 与 Server Action 内读私密变量不进运行时安全
middleware 读私密变量不进，但在边缘节点运行时注意密钥分发范围变大了

防线有两道：服务端专用模块顶部写 import 'server-only'，被客户端导入时构建期就失败；纯客户端模块顶部写 import 'client-only'，被服务端引用时同样报错。这比靠人工评审可靠得多。构建产物里搜一遍密钥字面量应该纳入发布前检查，具体的构建与体积治理手段见站内 前端工程化。

最容易踩的坑
  • 以为 'use client' 只影响当前文件，于是在一个被处处引用的基础组件上加了它，客户端 bundle 一次涨几百 KB。
  • 把 Prisma 的 Decimal、Mongoose 文档、Sequelize 实例当 props 传下去，运行期才报不可序列化。
  • DTO 转换时用了 ...row 展开，顺手把 passwordHash、riskScore 这类字段送到了浏览器。
  • Server Action 里只校验了参数没校验归属，改一下请求里的 ID 就能操作别人的数据。
  • 先 findUnique 查出来比对 userId，再 update。并发下存在窗口，应该把归属条件直接写进更新语句的 where。
  • Server Action 写完忘了 revalidatePath，用户提交成功但页面显示的还是旧数据。
  • 在客户端组件里 async function Component()，得到一堆看不懂的 hydration 报错。
  • 客户端组件顶层直接读 window 或 localStorage，服务端预渲染阶段就崩了，必须放进副作用里。
  • 用 Server Action 做文件上传，超过默认 body 上限后才发现应该用 Route Handler。
  • 给 NEXT_PUBLIC_ 变量赋了一个「反正只有前端用」的第三方密钥，它在产物里是明文字面量。
  • 没装 server-only 这道防线，全靠代码评审拦截服务端模块被客户端导入。
  • 把 Promise 在客户端组件里创建再传给 use()，每次渲染都新建一个，导致无限挂起。
