Next.js 的渲染模型：App Router 与四种渲染时机

🏷️ Next.js

后端工程师看 Next.js，最该抓住的不是组件怎么写，而是一段代码在哪台机器上、什么时候被执行。同一个 page.tsx 文件，可能在 CI 机器上跑一次就结束，也可能在每个请求里跑一遍并顺手打一次数据库，也可能被打包送到用户浏览器里执行。这个问题回答不清楚，后面的缓存、鉴权、容量估算全是猜。

这篇把渲染模型讲清楚：四个执行位置各自能访问什么、静态与动态是怎么被自动推导出来的、流式渲染换来了什么又付出了什么、以及一条新路由该选哪种渲染时机。缓存的四层结构在 数据获取与缓存 单独展开，服务端与客户端的边界在 Server Components 的边界与数据流 展开，部署形态在 部署形态与运行时约束 展开。

四个执行位置：代码在哪里跑决定它能访问什么

Next.js 把「渲染」这件事拆到了四个位置。它们不是互斥的选项，而是同一次页面加载里可能同时参与的四个阶段。

用后端的话翻译一遍

构建时相当于「预生成物料入 CDN」，Node 服务端相当于「一个会渲染 HTML 的 BFF」，边缘运行时相当于「网关上的 Lua 脚本」，浏览器相当于「客户端 SDK」。你在后端做容量规划时，只需要关心第二类：它才是唯一会随 QPS 线性消耗 CPU 和数据库连接的部分。

App Router 与 Pages Router 的根本差异

这两套路由不是语法糖的区别，是三处根本重做：默认组件类型、布局与输出方式、缓存模型。

维度Pages RouterApp Router对后端的实际影响
默认组件类型全是客户端组件，服务端只做一次 HTML 预渲染默认 Server Component，不进客户端 bundle数据可以直接在组件里查库，少写一层内部 API
数据获取入口页面级 getServerSideProps / getStaticProps，一个页面一个口子任意 Server Component 内 await，组件级分散好处是就近取数，坏处是瀑布问题更容易出现
布局_app 全局一层，切页面整棵树重渲染layout 可嵌套，导航时不重新渲染布局里的连接与状态跨页面保留，注意别在布局做请求级取数
输出方式整页渲染完一次性返回支持分块流式输出，配 SuspenseTTFB 与总时长解耦，监控口径要改
缓存模型只有页面级 ISR，心智简单四层缓存，默认值随版本变过排查「数据不更新」要先定位命中哪一层
错误处理_error 页面兜底每层可放 error.tsx 边界局部降级成为可能，但边界层级放错会整页白屏

迁移判断很简单：新项目直接 App Router，没有理由再开新的 pages/ 目录。老项目两套路由可以在同一个应用里共存，按 URL 前缀逐个模块迁，pages/ 里的路由优先级高于 app/ 里的同名路由。真正需要重写的只有数据获取层和全局布局，组件本身大多能原样复用。不要为了「用上新特性」做一次性大重写——这类重写的收益极难量化，而回归风险是确定的。

静态还是动态：这个判定是自动推导的

这是 App Router 最反直觉的一点。你没有一个开关叫「这个页面是 SSR」，Next.js 在构建时静态分析你的渲染路径：只要碰到了任何依赖本次请求的 API，整条路由就从静态降级成动态渲染。

触发因素降级结果为什么想保持静态该怎么做
cookies() / headers()整条路由动态渲染，退出整页缓存输出依赖请求，构建期无法预生成把读 cookie 的部分下推到客户端组件，或用 middleware 改写
使用 searchParams同上查询串属于请求数据能进路径参数就进路径参数，静态生成才有可能
fetch 带 cache: 'no-store'该路由动态渲染显式声明不可缓存换成 next: { revalidate: N }
export const dynamic = 'force-dynamic'强制动态显式声明去掉它，或改成 'force-static' 定位问题
generateMetadata 里读请求数据整条路由动态渲染metadata 也是输出的一部分动态标题尽量只依赖路径参数
Route Handler 用了 request.url 的查询串该 handler 每次执行同上明确这是接口而非页面，通常无需静态

路由段配置可以把隐式行为变显式，出问题时也更容易定位。下面这段是我在每个关键路由上都会写的声明：

// app/marketing/page.tsx
// 显式声明预期，和构建输出对不上就会在构建期报错，而不是上线后被 QPS 教育

export const dynamic = 'force-static'   // 本路由必须能静态预渲染
export const revalidate = 300           // 5 分钟后台重新生成一次
export const fetchCache = 'default-cache'
// runtime 留默认的 nodejs：这里要查库，edge 用不了 TCP 驱动

export default async function Page() {
  // 注意：这里一旦写 cookies()，上面的 force-static 会让构建直接失败
  // 这正是我们要的效果——把隐式降级变成显式错误
  const rows = await getFeaturedPosts()
  return <PostList items={rows} />
}

最高频的线上事故长这样

为了埋点或 A/B 实验，有人在根 layout.tsx 里加了一行 cookies()。这一行让整站所有路由全部退出静态生成，数据库 QPS 从几乎为零涨到跟 PV 同阶，CDN 命中率归零。代码评审时这一行看起来无害，只有构建输出的路由表能立刻暴露它。

流式渲染：改善首字节，代价是错误处理

App Router 的流式输出是「先把能确定的外壳发出去，慢的部分用占位符顶住，数据就绪后再追加分块替换」。对 TTFB 的改善是真实的，但它不会让慢查询变快。

sequenceDiagram participant B as 浏览器 participant N as Next 服务端 participant D as 下游数据服务 Note over B,D: 非流式：所有 await 完成后才输出 B->>N: GET /dashboard N->>D: 查用户概要 约 80ms D-->>N: 返回 N->>D: 查报表聚合 约 900ms D-->>N: 返回 N-->>B: 首字节与完整 HTML 同时到达 约 1000ms Note over B,D: 流式：shell 先走，慢块后补 B->>N: GET /dashboard N->>D: 查用户概要 约 80ms D-->>N: 返回 N-->>B: 首字节 shell 与骨架屏 约 90ms N->>D: 查报表聚合 约 900ms D-->>N: 返回 N-->>B: 追加分块替换占位 约 1020ms Note over B,N: 响应头已发出，此刻出错无法改状态码
指标非流式流式说明
TTFB约等于最慢查询约等于最快可确定的外壳流式的主要收益在这里
全部内容可见1000ms1020ms 左右分块与二次布局有额外开销，总时长不降反略升
HTTP 状态码可以按结果返回 500 / 404头已发出，只能是 200错误只能以内联脚本触发客户端错误边界
可缓存性整页可进缓存分块响应难被中间层缓存CDN 与反向代理的缓冲策略要确认
反向代理无特殊要求必须关掉响应缓冲Nginx 开着 proxy_buffering 会把流式攒成一次性返回，收益全没了
监控口径状态码即成败200 里可能藏着错误要额外埋「分块渲染失败」计数
// app/dashboard/page.tsx
import { Suspense } from 'react'
import { Summary, Report, ReportSkeleton } from './parts'
import ReportBoundary from './report-boundary'   // 内部是 error.tsx 风格的客户端边界

export default async function Page() {
  // 概要很快，直接 await，它构成首字节能确定的 shell
  const summary = await getSummary()   // 约 80ms

  return (
    <main>
      <Summary data={summary} />
      {/* 慢查询包进 Suspense：shell 先发，这块后补 */}
      {/* 必须再包一层错误边界：分块阶段抛错时状态码已经是 200，
          没有边界就是整页白屏且监控看不到 */}
      <ReportBoundary>
        <Suspense fallback={<ReportSkeleton />}>
          <Report />
        </Suspense>
      </ReportBoundary>
    </main>
  )
}

反向代理侧要记得放开缓冲，否则流式在生产环境等于没开：

location / {
    proxy_pass http://next_upstream;
    proxy_http_version 1.1;

    # 关键三行：不关掉缓冲，Nginx 会攒满再一次性下发，TTFB 收益归零
    proxy_buffering off;
    proxy_cache off;
    chunked_transfer_encoding on;

    # 流式响应整体时长可能远大于首字节，读超时别按普通接口配
    proxy_read_timeout 60s;
    proxy_set_header X-Accel-Buffering no;
}

PPR：让一个 cookies 调用不再毁掉整页缓存

前面那个事故的根因是渲染粒度与缓存粒度绑死在路由级：一处动态就整页动态。PPR（Partial Prerendering，部分预渲染）就是来解耦这件事的——构建期生成一份带「洞」的静态外壳，洞的位置对应 Suspense 边界，请求时只渲染洞里的内容并流式填进去。外壳可以进 CDN，动态部分该算的还是算，但不再拖累整页。

方案外壳来源个性化部分整页可缓存成熟度
全静态 SSG构建期做不到可以稳定
全动态渲染每请求服务端直出不行稳定
静态外壳加客户端补数据构建期hydration 后再请求外壳可以稳定，当前推荐的过渡做法
PPR构建期请求时服务端流式填洞外壳可以Next 15 仍为实验特性

现状是：PPR 需要显式开启实验开关，并且要求动态部分严格落在 Suspense 边界内，配套的自托管支持也还在演进。生产上如果现在就要这个效果，用第三行那个等效手法：外壳静态、个性化部分交给客户端组件在 hydration 后拉一次。收益接近，风险低得多。

四种渲染时机怎么选

flowchart TB A["新增一条路由"] --> B{"输出是否随用户身份变化"} B -- 否 --> D{"内容更新频率"} B -- 是 --> C{"个性化部分能否拆成叶子节点"} D -- "小时级或更慢" --> E["构建期 SSG，产物进 CDN"] D -- "分钟级" --> F["SSG 加 revalidate，即 ISR"] D -- "秒级且必须准确" --> G["动态渲染，靠数据层缓存兜住下游"] C -- 能 --> H["静态外壳，个性化下推到客户端或流式补"] C -- 不能 --> I["整页动态渲染，同时评估服务端容量"] E --> J{"是否需要改写、灰度、鉴权前置"} F --> J J -- 是 --> K["在边缘 middleware 处理，注意不能连数据库"] J -- 否 --> L["直接由 CDN 命中"]
渲染时机内容更新频率能否个性化SEO服务端成本缓存能力典型场景
构建期 SSG随发布不能最好接近零整页可进 CDN文档、营销页、博客
ISR分钟到小时不能好只在重新生成时消耗整页缓存加后台刷新商品详情、榜单
请求时服务端渲染实时能好随 QPS 线性增长只有数据层缓存控制台、订单页
边缘渲染实时能，但受 API 限制好低单价、冷启动快可配合上游缓存改写、灰度、地域分流
客户端渲染实时能差零浏览器缓存登录后的强交互面板

SSR、SSG、CSR 在 TTFB 与带宽上的成本对照、缓存头怎么配、Core Web Vitals 怎么读，站内 前端性能：从后端视角看 已经写透了，这里不重复。React 本身的虚拟 DOM、Fiber 与并发渲染机制见 React 机制。

最容易踩的坑
  • 在根 layout.tsx 里调 cookies()，导致整站退出静态生成，且代码评审几乎看不出来。
  • 只在开发模式验证渲染方式。next dev 每次请求都重新渲染，静态与动态的差别在开发模式下根本看不出来，必须跑生产构建。
  • 把 next build 输出的路由表当日志噪音忽略，上线后才从数据库监控发现问题。
  • 用了流式但没在 Suspense 外层放错误边界，分块阶段抛错就是整页白屏，而 HTTP 状态码还是 200，告警不触发。
  • 前置 Nginx 没关 proxy_buffering，流式改造做完等于没做。
  • 以为 export const dynamic = 'force-static' 能把动态路由变静态。它的作用是让违反静态约束的代码在构建期报错，不是帮你绕过约束。
  • 在 middleware.ts 里做资源级鉴权，既连不上数据库，也会把每个静态资源请求都拖进边缘函数。
  • 给 searchParams 做分页，然后指望这些页面被静态预渲染——只要读了查询串就是动态路由。
  • generateMetadata 里读了 headers()，整条路由静默降级成动态，比 cookies() 更难发现。
  • Pages Router 与 App Router 共存时忘了 pages/ 优先级更高，迁移后新页面一直不生效。
  • 把边缘运行时当成「更快的 Node」。它是受限运行时，连不了传统数据库，依赖体积也有上限。
  • 容量估算时按 PV 算服务端 CPU，却没区分静态命中与动态渲染，结果预算差一个数量级。
