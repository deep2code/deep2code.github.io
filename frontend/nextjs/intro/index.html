Next.js 上手：App Router 的文件约定与布局

🏷️ Next.js 入门

App Router 是一套约定式框架：目录结构就是路由表，文件名就是这段代码在渲染树里的角色。对后端工程师来说，这跟看一份注解驱动的 Web 框架配置是一个路子——关键不是记住文件名，而是搞清楚每个文件对应渲染树上的哪一层、由谁包住谁、谁在什么时候执行。搞错层级的代价很实际：一个放错位置的 loading.tsx 会让每次导航整页闪屏，一个放在布局里的数据查询会让整站退出静态生成。

四种渲染时机与静态动态的判定见 Next.js 的渲染模型，服务端与客户端的边界见 Server Components 的边界与数据流。

app 目录里的特殊文件与渲染层级

一条 URL 对应的不是一个文件，而是从根目录到叶子目录一路累加起来的一棵组件树。

文件在树里的位置导航时是否重建执行位置最常见的用错方式
page.tsx叶子，唯一对应 URL 的可访问段是默认服务端与 route.ts 放在同一目录，构建冲突
layout.tsx包住本层及所有子路由不重建默认服务端在里面做请求级取数，整站变动态
template.tsx在 layout 内、page 外每次导航都重建默认服务端当 layout 用，导致状态被反复清空
loading.tsx自动包在本层 children 外的 Suspense—服务端流式输出放在根层，每次导航整页闪骨架屏
error.tsx包在本层 children 外的错误边界—必须是客户端组件指望它捕获同层 layout 的错误
not-found.tsx本层的 404 展示—服务端以为它能接住所有 404，实际只响应 notFound() 与未匹配路由
route.ts接口段，不产出 HTML—Node 或边缘，按声明不校验输入、把鉴权托付给 middleware
middleware.ts在路由匹配之前，不属于这棵树—边缘运行时在里面查数据库

布局不随导航重新渲染：好处与陷阱都来自这一条

这是 App Router 与 Pages Router 最容易被忽略的行为差异。客户端导航时，Next.js 只请求变化的那几段路由的 RSC payload，共享的布局既不重新执行也不重新挂载。

需求放 layout放 template放 page结论
侧边栏保持展开状态正确每次导航被重置不共享用 layout
进入子页面播放进场动画只有首次生效正确可行但重复代码用 template
读取当前用户的未读消息数导航后数字不更新每次导航重查，但整站都要付这次查询正确请求级数据放 page
全站导航埋点回调只触发一次正确要在每个页面重复写用 template
鉴权拦截不可靠，子路由可被直接命中同样不可靠在每个数据入口做鉴权跟着数据走，不跟着布局走
⚠️
别把鉴权写在布局里

「在 layout.tsx 里检查登录态，未登录就重定向」看起来很自然，但它不是安全边界：布局不随导航重新执行，而 Route Handler、Server Action 与直接命中的子路由根本不经过这个布局。鉴权必须写在每个真正读写数据的入口内部。授权模型与常见越权见站内 认证与授权。

路由组、并行路由、拦截路由各解决什么问题

机制写法对 URL 的影响解决的真实问题代价
路由组目录名加圆括号无，不出现在路径里营销页与控制台页需要完全不同的根布局，但又想共用同一个应用两个组里出现同名路由会构建冲突
并行路由目录名以 at 符号开头无，作为布局的命名插槽一个仪表盘里多个面板各自有独立的加载与错误状态，互不阻塞每个插槽都要配 default.tsx，否则刷新后 404
拦截路由目录名用点号前缀表示向上几层无，改变的是渲染目标列表里点图片弹浮层、地址栏同时变成详情页 URL，刷新或分享时展示完整页面必须与并行路由配合，心智负担最高
动态段目录名加方括号成为路径参数详情页批量静态生成，配 generateStaticParams参数过多会让构建时间线性膨胀
私有目录目录名加下划线前缀不生成路由把组件与工具函数就近放在路由目录里而不产生可访问 URL无

并行路由这个机制被低估了：它本质上是把一个页面拆成若干可以独立失败、独立加载的区块，相当于后端的接口聚合层在渲染层的等价物。某个面板的下游挂了，只有那块显示错误，其余照常。

loading.tsx 没什么神秘的，它就是在这一层的 children 外面自动包一个 Suspense。所以放的层级越靠外，被骨架屏替换掉的面积就越大。放在根层的后果是每次导航整页闪一下，用户感知比不加更差。更精确的做法是不要这个文件，手写 Suspense 只包住真正会等数据的那个子树。

Route Handler：一个标准的 Request 进、Response 出

这是后端最熟悉也最该用好的部分。route.ts 导出的就是以 HTTP 方法命名的函数，参数是标准 Request，返回标准 Response，没有框架自己的一套上下文对象。把它当轻量 BFF 用很合适：聚合几个内部服务、遮蔽掉不该暴露给浏览器的字段、把内网协议翻译成前端好消费的 JSON。

// app/api/orders/route.ts
import { NextResponse } from 'next/server'
import { z } from 'zod'

// 显式声明，不依赖版本默认值：这个接口读 cookie 与查询串，必须每次执行
export const dynamic = 'force-dynamic'
export const runtime = 'nodejs'   // 要用 TCP 数据库驱动，不能是 edge

const CreateOrder = z.object({
  sku: z.string().min(1).max(64),
  qty: z.number().int().positive().max(99),
})

export async function GET(req: Request) {
  // 读查询串意味着这个 handler 不可能被静态化
  const page = Number(new URL(req.url).searchParams.get('page') ?? '1')
  if (!Number.isInteger(page) || page < 1 || page > 1000) {
    return NextResponse.json({ error: 'bad_page' }, { status: 400 })
  }

  // 鉴权写在这里，不能依赖 middleware：handler 是可被直接调用的公开端点
  const user = await requireUser()
  if (!user) return NextResponse.json({ error: 'unauthorized' }, { status: 401 })

  const rows = await listOrders(user.id, page)
  return NextResponse.json(
    { items: rows.map(toDTO), page },
    // 私有数据必须显式声明不可共享缓存，否则中间层可能替别人缓存
    { headers: { 'Cache-Control': 'private, no-store' } },
  )
}

export async function POST(req: Request) {
  let raw: unknown
  try {
    raw = await req.json()
  } catch {
    // 客户端发了非 JSON，这里不处理就是一个未捕获异常加 500
    return NextResponse.json({ error: 'invalid_json' }, { status: 400 })
  }

  const parsed = CreateOrder.safeParse(raw)
  if (!parsed.success) {
    return NextResponse.json(
      { error: 'validation_failed', fields: parsed.error.flatten().fieldErrors },
      { status: 422 },
    )
  }

  const user = await requireUser()
  if (!user) return NextResponse.json({ error: 'unauthorized' }, { status: 401 })

  // 幂等键交给客户端传，重复提交不会重复下单
  const key = req.headers.get('idempotency-key')
  const order = await createOrder(user.id, parsed.data, key)
  return NextResponse.json({ id: order.id }, { status: 201 })
}

POST / PUT / PATCH / DELETE从不缓存从不缓存本来就不缓存

跨版本最稳的姿势是别猜默认值：要缓存就写 export const revalidate = N，不要缓存就写 export const dynamic = 'force-dynamic'。接口的版本化、错误码设计、幂等语义见站内 API 设计，这里不展开。

middleware：跑在边缘，且在路由匹配之前

middleware 不属于那棵组件树。它在请求进入路由匹配之前执行，位置上等价于网关插件，运行时是受限的边缘运行时。

能做为什么适合不能做为什么不行
校验 token 签名、判断有没有会话 cookie纯 CPU 计算，Web Crypto 够用查数据库确认权限边缘没有 TCP，驱动跑不起来
重写路径、按地域或灰度分流在匹配前改写最省事读写文件、用 Node 内置模块运行时不提供
补安全响应头、设置 cookie全站统一一处引入体积大的 SDK打包体积有上限，通常约 1 MB 量级
未登录时重定向到登录页省掉一次无用的页面渲染作为唯一的鉴权手段它不知道这条记录属于谁
拒绝明显异常的请求成本最低的一道拦截复杂业务逻辑每个请求都要付这笔延迟
// middleware.ts
import { NextResponse, type NextRequest } from 'next/server'
import { jwtVerify } from 'jose'   // 选 Web Crypto 实现，Node 专属库在 edge 跑不了

const secret = new TextEncoder().encode(process.env.SESSION_SECRET!)

export async function middleware(req: NextRequest) {
  const token = req.cookies.get('session')?.value
  if (!token) return redirectToLogin(req)

  try {
    // 只做签名与过期校验，这是无状态的、边缘能做的事
    const { payload } = await jwtVerify(token, secret)
    const res = NextResponse.next()
    // 把身份透传给下游，省掉一次重复解析；注意这不能替代下游的再次校验
    res.headers.set('x-user-id', String(payload.sub))
    return res
  } catch {
    return redirectToLogin(req)
  }
}

function redirectToLogin(req: NextRequest) {
  const url = req.nextUrl.clone()
  url.pathname = '/login'
  url.searchParams.set('from', req.nextUrl.pathname)
  return NextResponse.redirect(url)
}

// matcher 很关键：不写会让静态资源与图片请求也走一遍边缘函数，白付延迟和费用
export const config = {
  matcher: ['/dashboard/:path*', '/settings/:path*'],
}
❌
为什么资源级鉴权不能放在 middleware

middleware 只看得到 URL 与请求头，它能回答「这个人登录了吗」，但回答不了「这张订单是不是他的」——后者需要读库，而边缘读不了库。更要紧的是，Server Action 与 Route Handler 都可以被直接调用，绕过你以为必经的页面路径。所以 middleware 只是一道减少无效渲染的粗筛，真正的授权判断必须贴着数据访问写。越权的具体形态见站内 安全专题。

metadata 与 SEO：小心它把路由拖成动态

静态元信息直接导出 metadata 对象；需要按路径参数生成标题就用 generateMetadata。有个坑很隐蔽：generateMetadata 里一旦读了 headers() 或 cookies()，整条路由就退出静态生成，而路由表以外几乎没有任何提示。

// app/posts/[slug]/page.tsx
import type { Metadata } from 'next'
import { notFound } from 'next/navigation'

// 这里只依赖路径参数，路由仍可静态预渲染
export async function generateMetadata(
  { params }: { params: Promise<{ slug: string }> },   // Next 15 起 params 是 Promise
): Promise<Metadata> {
  const { slug } = await params
  const post = await getPost(slug)   // 与页面里同一个 fetch 会被请求级去重，不会查两次
  if (!post) return { title: '内容不存在' }
  return {
    title: post.title,
    description: post.summary.slice(0, 160),
    alternates: { canonical: `https://example.com/posts/${slug}` },
    openGraph: { title: post.title, type: 'article' },
  }
}

// 批量预生成，配合 revalidate 就是 ISR
export const revalidate = 600
export async function generateStaticParams() {
  const slugs = await listPublishedSlugs({ limit: 500 })   // 别一次生成十万条，构建时间会爆
  return slugs.map((slug) => ({ slug }))
}

export default async function Page({ params }: { params: Promise<{ slug: string }> }) {
  const { slug } = await params
  const post = await getPost(slug)
  if (!post) notFound()   // 走最近的 not-found.tsx 并返回 404
  return <Article post={post} />
}

反模式对照表

反模式症状根因正确做法
把业务逻辑塞进 middleware本地跑通、部署报错，或全站延迟上升边缘运行时受限，且每个匹配请求都要付这笔开销只留无状态判断，matcher 收窄到需要的路径
error.tsx 放错层级报错时整页白屏，边界形同不存在error 捕获不到同层 layout 的错误按「谁可能抛错，边界就放它的上一层」布置
在 layout 里做请求级数据获取整站变动态渲染，且导航后数据不刷新布局不随导航重新执行请求级数据放 page 或更内层组件
Route Handler 不校验输入偶发 500，日志里是 JSON 解析异常把客户端输入当可信数据schema 校验加显式 4xx 返回
loading.tsx 放在根层每次导航整页闪骨架屏Suspense 边界包住了整棵树下移到会等数据的那一段，或手写 Suspense
用 layout 做登录拦截直接请求接口或 Action 可绕过布局不是安全边界鉴权贴着数据访问写
page.tsx 与 route.ts 同目录构建报路由冲突同一路由段只能有一种响应形态接口放到独立段，例如 api/ 下
✅
最容易踩的坑
  • 把 template.tsx 当 layout.tsx 用，导航时状态被反复清空；或者反过来，指望 layout 里的副作用每次导航都跑一遍。
  • 在 app/dashboard/error.tsx 里等着接 app/dashboard/layout.tsx 的异常，永远接不到。
  • 忘了 error.tsx 必须是客户端组件，漏写 'use client' 直接构建失败。
  • 根布局漏了 html 与 body 标签，或者在 global-error.tsx 里漏了它们，出错时页面结构直接崩。
  • middleware 不写 matcher，结果每张图片、每个静态资源请求都进边缘函数，账单和延迟一起涨。
  • 在 middleware 里 import 了一个间接依赖 Node 模块的工具库，构建期不报错、运行期才炸。
  • 并行路由的槽位没配 default.tsx，客户端导航正常，用户一刷新就 404。
  • Route Handler 里返回私有数据却不设 Cache-Control: private，中间层可能把 A 的数据缓存给 B。
  • Next 15 起 params 与 searchParams 变成 Promise，升级后忘了 await，拿到的是一个对象而不是值。
  • generateMetadata 里读了 headers()，整条路由静默退出静态生成。
  • generateStaticParams 一次返回几万条，构建时间从两分钟涨到半小时。
  • 把 notFound() 写在 try catch 里，它靠抛特殊异常工作，被吞掉后 404 就失效了。
