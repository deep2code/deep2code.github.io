客户端发布流程的工程约束

🏷️ 前端发布

后端同学第一次深度参与 App 发布时，最容易低估的不是打包流程，而是发布这件事的可撤回性差异。Web 侧一次错误发布，改一行、重新构建、CDN 刷新，几分钟就消失了；客户端侧一次错误发布，产物已经躺在用户设备上，你既不能删除它，也不能让它降级，只能等用户愿意更新。所有客户端发布流程的怪规矩，本质上都是从这一条约束推导出来的。

可撤回性是 Web 与 App 的分水岭

把发布看成一个「写操作」，Web 是可回滚事务，App 是只能追加的日志。这个差别会一路传导到接口设计、监控口径、事故处置流程上。

客户端事故的第一止损手段永远是远程开关，不是发版。所以「有没有开关」必须在功能设计阶段就决定，而不是出事后再加——那时候新代码还要走一遍审核，而开关本身也在新版本里。工程上的硬规矩是：任何有外部依赖或有风险的新功能，上线时必须自带一个能把它关回旧行为的开关。

版本共存：最老的在线版本决定接口能否下线

这是后端最直接受影响的一点。Web 时代「接口改造完，前端跟着发一版」的模式在客户端不成立：线上同时活着的版本是一个集合，不是一个值。任何破坏性接口变更，影响面等于「所有还在用旧结构的版本的活跃用户之和」。

把兼容逻辑收在网关或 BFF 这一层，下游服务只维护最新模型，是唯一能长期维持的结构。反面做法是让每个业务服务自己写 if version < x，三个月后没人知道哪些分支还能删。

下线前置条件判断依据不满足时的后果
旧结构的活跃调用量降到阈值以下按版本维度拆分的接口调用监控，看的是绝对量不是比例比例看着很小，绝对值仍是每天几万次失败
已有一个版本能强制升级掉旧版最低支持版本接口已上线且旧版本会被拦旧版用户永远留在那里，接口永远删不掉
观察期内没有回流下线前先返回降级响应观察，不要直接删节假日或海外时区的低频用户会在下线后集中爆
失败行为是可接受的旧客户端拿到未知结构时的表现已验证解析异常直接导致旧版本闪退，比接口报错严重得多
有回退开关下线动作本身可以一键撤销下线后只能紧急重新部署，止损时间以小时计
package api

import (
    "net/http"
    "strconv"
    "strings"
)

type ClientInfo struct {
    Platform            string
    Major, Minor, Patch int
}

// 客户端版本一律放独立请求头，不要从 User-Agent 里抠：
// UA 会被各家 WebView 和网络中间件改写，解析规则迟早失效。
// 解析失败时返回零值，语义上等于「最老的版本」，保证未知客户端走兼容分支。
func ParseClient(r *http.Request) ClientInfo {
    c := ClientInfo{Platform: strings.ToLower(r.Header.Get("X-App-Platform"))}
    parts := strings.SplitN(r.Header.Get("X-App-Version"), ".", 3)
    nums := [3]int{}
    for i := 0; i < len(parts) && i < 3; i++ {
        nums[i], _ = strconv.Atoi(strings.TrimSpace(parts[i]))
    }
    c.Major, c.Minor, c.Patch = nums[0], nums[1], nums[2]
    return c
}

func (c ClientInfo) atLeast(major, minor, patch int) bool {
    if c.Major != major {
        return c.Major > major
    }
    if c.Minor != minor {
        return c.Minor > minor
    }
    return c.Patch >= patch
}

// 业务代码只问「有没有这个能力」，不直接比版本号。
// 好处是能力与版本的映射集中在一处，删兼容分支时有唯一的清理点。
func (c ClientInfo) Supports(feature string) bool {
    switch feature {
    case "coupon_struct_v2":
        switch c.Platform {
        case "ios":
            return c.atLeast(6, 2, 0)
        case "android":
            return c.atLeast(6, 3, 0)
        default:
            return true // web 随时可发版，默认具备新能力
        }
    }
    return false
}

分阶段发布：平台机制与自建开关各管一段

平台提供的分阶段发布控制的是「多少人拿到这个安装包」，远程开关控制的是「拿到包的人里多少人走新逻辑」。两者解决的问题不同，缺一个都不行：只有平台灰度时，你没法在不发版的情况下关掉新功能；只有开关时，你没法控制崩溃类问题的暴露面——崩在启动阶段的代码，开关还没拉下来就已经崩了。

机制控制对象推进方式能中止吗关键限制
iOS 分阶段发布自动更新的用户比例按天逐步放大，总共约一周可以暂停只作用于自动更新；手动去商店点更新的用户立刻拿到新版
Play 分阶段发布可获取新版本的用户比例百分比由你设定，手动推进可以 halthalt 只阻止继续下发，已升级的设备不会退回旧版本
国内安卓商店各家机制不统一部分支持灰度，部分只能全量看各家多渠道包版本节奏难以对齐，问题版本可能长期挂在某一家
远程开关新逻辑的启用范围任意维度，秒级生效可以，最快救不了启动期崩溃；开关服务自己也要有降级默认值
服务端兼容兜底响应结构与业务规则随服务发布可以只能兜服务端能控制的部分，改不了客户端本地逻辑

强制更新与热更新：边界在哪，风险在哪

强制更新是唯一能真正收掉旧版本的手段，但它是一个高破坏性操作：一旦最低支持版本配错，会把所有用户挡在启动页外面。工程上的硬要求是最低版本接口必须免鉴权、必须有客户端本地默认值、拉取失败时一律放行——否则这个接口挂了就等于全站不可用。

// 客户端侧：三条硬性约束写在代码里，而不是靠约定
const FALLBACK = { forceBelow: '0.0.0', noticeBelow: '0.0.0' }; // 拉不到就放行

export async function checkUpdate(current: string, platform: string) {
  let cfg = FALLBACK;
  try {
    // 1) 免鉴权，避免「登录依赖版本检查、版本检查依赖登录」的死循环
    // 2) 带超时，绝不让启动流程被这个请求卡住
    const res = await fetchWithTimeout(`/api/v1/app-version?platform=${platform}`, 1500);
    cfg = { ...FALLBACK, ...(await res.json())[platform] };
  } catch {
    // 3) 任何异常都按放行处理：配置中心故障不能升级成全站不可用
  }

  if (compare(current, cfg.forceBelow) < 0) return { action: 'force' };
  if (compare(current, cfg.noticeBelow) < 0) return { action: 'notice' };
  return { action: 'none' };
}

热更新的边界比很多团队以为的窄。两家平台的共同底线是：不能下载并执行新的可执行代码。资源、文案、配置、布局数据这类「数据」更新没有争议；解释执行的脚本处于有条件允许的区间，条件是不改变应用的主要用途；而预编译字节码、动态库、可执行文件属于明确禁止或高度灰色的范围。

更新内容iOS 侧定性Android 侧定性工程建议
文案、图片、配置、开关没有争议没有争议放心用，这是绝大多数「热更新需求」的真实内容
服务端下发的布局与表单结构属于数据，但不能开出未审核的新功能同可以做，但功能范围要在审核版本内
解释执行的脚本（JS 一类）有条件允许，不得改变主要用途限制较松能做，但把它当「修补」用，不要当「发版替代品」
预编译字节码是否算可执行代码有争议限制较松风险自担，至少要有一条随时切回内置包的路
动态库、原生补丁、可执行文件明确禁止违反平台的代码下载政策不要做，被查到的后果是下架级别
用开关放出审核时不存在的功能属于隐藏功能，明确违规同样违规开关只能在已审核的行为之间切换

签名、证书与描述文件：发不出版的第一大原因

这一类故障的特点是「平时完全看不见，到期当天全线红」。它不是技术难题，是资产管理问题：你需要一份清单，知道每项资产什么时候过期、谁持有、丢了怎么办。

资产典型有效期过期后果丢失后果
iOS 分发证书数年无法签名，CI 打包失败可吊销重签，但需同步更新所有描述文件
iOS 描述文件一年打包失败；企业内部分发场景下已安装应用会无法启动可重新生成，需要账号权限
APNs 推送凭证证书形式一年；密钥形式不过期推送整体失效，且往往靠用户投诉才发现密钥形式无法二次下载，丢了只能重新创建并换配置
Android 上传密钥自定义，需足够长无法上传新版本启用了应用签名服务时可申请重置
Android 应用签名密钥需远超应用生命周期无法更新应用未托管给平台时，等于这个包名永久失去更新能力
商店账号与协议年度续费与协议签署协议未签、账号欠费会直接下架或停止分发主体变更流程漫长，需提前规划

崩溃监控与符号表：没有符号的崩溃等于没有崩溃

客户端崩溃栈默认是一串地址。符号文件缺失时，你会在监控后台看到一堆无法归并、无法定位的崩溃分组，等于失去了发布期最重要的观测手段。符号文件必须由 CI 在构建的同一次任务里上传，而不是靠人记得。

平台符号文件产生位置缺失时的表现
iOSdSYM 包构建产物旁，与构建号一一对应崩溃栈只有地址，同一个 bug 被拆成多个分组
Android 的 Java 与 Kotlin 层混淆映射文件开启代码压缩后的构建输出栈里是混淆后的短类名，无法反推源码位置
Android 原生层原生调试符号NDK 构建产物中的未裁剪 so只有偏移量，原生崩溃基本无法定位
跨端框架层框架自己的 source map 或符号文件随打包生成只能看到胶水层调用，看不到业务代码

额外一条容易忽略的规矩：每次构建都要保留产物与符号文件的对应关系，包括版本号、构建号、提交哈希。发布后第三天才暴露的崩溃，你需要回到当时那个确切的构建去找符号，而不是拿最新的 dSYM 去解一个老版本的栈。

审核被拒的工程原因

被拒里真正跟工程有关的，大多数不是「代码写得不好」，而是提交材料与运行时行为不自洁。这类问题都能在提交前用清单挡住。

被拒类型触发条件工程侧的修法
审核环境跑不起来审核网络访问不到你的测试环境；接口有 IP 白名单；强制定位或强制权限后白屏提交前用干净设备加外网环境跑一遍；准备可用的演示账号并保证它长期有效
登录门槛过高与账号无关的功能也强制登录；只提供手机验证码且审核收不到短信提供游客可浏览路径；给审核备注固定验证码账号
权限与隐私声明不一致调用了需要声明用途的接口却没写用途说明；隐私清单缺项；SDK 采集的数据没申报把权限用途、隐私清单、数据申报做成发版前自动校验项，而不是人工检查
支付与虚拟商品数字内容绕过平台内购；页面内引导到外部付款把付费能力做成服务端下发的配置，按地区与平台规则开关，不同版本不重复打包
隐藏功能用远程开关在审核后开出新功能；带有测试后门与内部入口开关默认值必须等于审核时的行为；内部入口靠构建变体剥离，而不是靠条件判断藏起来
用户内容合规有 UGC 却没有举报、屏蔽、内容过滤能力把举报与屏蔽当成 UGC 功能的一部分，同期上线
国内合规缺少软件著作权材料、应用备案、隐私政策弹窗或首启前置采集初始化 SDK 一律延后到用户同意隐私政策之后，做成框架层约束

App 没有回滚，只有前滚

「回滚」这个词在客户端语境里是失效的：你无法把用户设备上的 6.4.0 变回 6.3.0。能做的只有四件事，按止损速度排序是：关开关、改服务端、发新版本、请求加急审核。

❌
最容易踩的坑
  • 把「接口下线」按比例判断：旧版本占比 0.5% 听起来可以删，但换算成绝对调用量往往还是每天几万次，且集中在某类低频但高价值用户上。
  • 新功能上线不带开关：出事后才发现唯一的止损手段是发版，而发版要走审核，时间从分钟级变成天级。
  • 开关默认值与审核时的行为不一致：审核通过后靠开关放出新功能，这属于隐藏功能，是明确的违规项。
  • 最低版本接口需要鉴权或没有超时：接口一挂，所有用户卡在启动页；正确做法是免鉴权、短超时、拉取失败一律放行。
  • 以为 Play 的 halt 等于回滚：halt 只阻止继续下发，已经升级的设备不会退回旧版本，它们只能靠开关或下一版救。
  • 以为 iOS 分阶段发布能保护所有用户：它只作用于自动更新，主动去商店点更新的用户会立刻拿到新版本，崩溃会在第一天就出现。
  • 版本号复用或回退：构建号必须单调递增，Android 的版本号一经发布不可重复使用，写错了只能往上加。
  • 符号文件不随构建上传：三天后暴露的崩溃需要回到当时那个构建的符号去解，拿最新符号解老版本栈只会得到错误的行号。
  • 把混淆映射当可选项：不上传映射文件的崩溃分组会被混淆名打散，同一个 bug 看起来像十个 bug。
  • 证书与描述文件没有到期告警：这是发版失败最常见的单一原因，而且总是发生在最不该发版的时候。
  • 把应用签名密钥只存在某个人的电脑上：未托管给平台且密钥丢失，等于这个包名永久失去更新能力。
  • 热更新越界：下发动态库或可执行文件属于明确禁止的行为，被查到是下架级别的后果，不是改一版的事。
  • 只在自己设备上验证提交包：审核环境的网络、地区、权限拒绝路径与你的机器完全不同，白屏和崩溃大多出在这三处。
  • 把隐私政策同意做成弹窗贴纸：只要在用户同意前初始化了采集类 SDK，就已经构成违规，必须在框架层约束初始化时机。
