Vite 上手：项目结构、依赖预构建与环境变量

npm create vite 之后的项目能直接跑，所以很多人从没搞清那几个目录和文件各自的命运。这一篇讲的就是这些具体机制：入口为什么是 HTML、资源放哪里、预构建缓存在哪、环境变量怎么注入、为什么类型错误不报。架构层面的原理见 Vite 的架构，插件与配置细节见 配置与插件机制。

入口是 index.html，不是 JS

这是与 Webpack 最直观的结构差异。Webpack 的入口是 JS，HTML 由插件根据模板生成；Vite 的入口就是项目根目录下那个真实的 index.html，开发期浏览器直接加载它，里面那个 type="module" 的 script 标签就是模块图的根。它是构建产物的一部分，不是模板。

⚠️
别把 index.html 放进 public

放进去它会被原样拷贝，不参与构建，于是 script 标签里的源码路径不会被改写成产物路径，线上打开就是 404 或空白页。index.html 必须在项目根目录（或 root 指定的目录）下。多页应用要在 build.rollupOptions.input 里显式列出每个 HTML 文件。

静态资源：加哈希还是原样拷贝

维度import 引入放 public 目录
是否加内容哈希加，文件变了 URL 就变不加，URL 恒定
缓存策略可以配 immutable 长缓存只能配短缓存或协商缓存
小文件处理小于 assetsInlineLimit（默认 4KB）会内联成 base64不处理
未被引用时不会进产物，自动瘦身永远进产物，哪怕没人用
路径写法代码里 import 拿到变量代码里写以斜杠开头的绝对路径
部署到子路径自动带上 base 前缀要手动拼 import.meta.env.BASE_URL
适合放什么组件用到的图片、字体、图标、样式robots.txt、站点地图、需要固定 URL 被外部引用的文件
// 1. 正常资源：import 拿到构建后的 URL，自动带哈希与 base 前缀
import logoUrl from './assets/logo.svg'
<img src={logoUrl} alt="站点标志" />

// 2. 运行时拼接的资源路径：不要写死斜杠开头的字符串
// 错误写法，部署到子路径就 404
const bad = `/icons/${name}.svg`
// 正确写法，BASE_URL 由 base 配置决定，本地是斜杠，线上可能是 /app/
const good = `${import.meta.env.BASE_URL}icons/${name}.svg`

// 3. 需要一批资源时用 glob，这是可被静态分析的动态导入
// eager 为 false 时返回的是懒加载函数，会被自动分包
const icons = import.meta.glob('./assets/icons/*.svg', { eager: true, query: '?url' })

// 4. 只要 URL 不要内容，且希望参与哈希
const workerUrl = new URL('./heavy.worker.ts', import.meta.url).href

依赖预构建的实际影响

预构建是让「开发期不打包」这个模型能成立的前提（原理见 架构篇）。日常开发中你会以三种形式感受到它：首次启动慢一点、缓存目录会脏、以及页面偶尔自动刷新一次。

现象原因怎么确认处理
首次启动比后续慢几秒到几十秒正在预构建依赖启动日志出现正在优化依赖的提示正常，产物缓存在 node_modules/.vite/deps
点进某个路由时页面白一下并刷新依赖藏在动态导入里，启动扫描没发现，运行时才补做预构建控制台出现新依赖被优化并需要重载的提示把它写进 optimizeDeps.include
切分支后各种莫名报错lockfile 变了但预构建缓存还是旧的.vite/deps/_metadata.json 里的 hash 与当前依赖不符先试 vite --force，别急着删 node_modules
monorepo 里改了本地包不生效本地包被当成依赖预构建并缓存了改源码无反应，重启才生效加入 optimizeDeps.exclude 并配 server.watch
某依赖的 default 导出是 undefined纯 CommonJS 包的互操作差异dev 正常 build 报错，或反之显式 optimizeDeps.include，必要时配 build.commonjsOptions
依赖里引用了 Node 内置模块导致报错该包只能在服务端跑报错信息提到 fs、path 等无法外部化换浏览器可用的包，或在 SSR 场景配 ssr.noExternal

环境变量：注入机制与安全含义

Vite 的环境变量不是运行时读取的，而是构建时做字面量替换：import.meta.env.VITE_API_URL 在产物里变成了字符串常量。理解这一点能同时解释安全边界和部署限制。

文件加载时机是否该进 git优先级
.env所有模式进最低
.env.local所有模式，但测试模式下不加载不进，写进 gitignore高于 .env
.env.[mode]指定模式，如 development、production进高于 .env.local
.env.[mode].local指定模式且本地不进最高（文件类）
系统环境变量进程启动时不适用高于所有 .env 文件
❌
带 VITE_ 前缀等于公开

前缀机制的设计目的是防止无前缀的服务端密钥被误打进前端，但它的另一面必须记牢：加了前缀的变量会被明文写进 JS 产物，用户打开开发者工具搜索就能看到。任何数据库密码、第三方 API 的私有 key、签名 secret 都不能加前缀，也就意味着它们根本不该出现在前端代码里——需要用到时必须由自己的后端代理转发。

另一个必须知道的限制：构建时注入意味着一份产物不能多环境复用。测试环境和生产环境的接口地址不同，就得构建两次，无法做到「构建一次、到处部署」。要复用产物只能改成运行时注入——把配置放进一个不带哈希的小 JS 文件或由服务端渲染进 HTML，启动时读。这套方案的权衡见站内 前端工程化。

# .env —— 所有环境共享的默认值，进 git
VITE_APP_NAME=控制台

# .env.development —— 开发期指向本地代理前缀，进 git
VITE_API_BASE=/api

# .env.production —— 生产地址，进 git
VITE_API_BASE=https://api.example.com

# .env.local —— 个人机器上的覆盖，必须写进 .gitignore
# 这里最容易出事：忘了它的存在，然后怀疑 .env.development 不生效
VITE_API_BASE=http://192.168.1.50:8080

# 没有前缀的变量不会注入客户端，只能在 vite.config 里用 loadEnv 读
DB_PASSWORD=never-goes-to-browser

# 指定模式构建：会加载 .env.staging 系列
npx vite build --mode staging
// src/env.d.ts —— 给环境变量补类型，否则全是 string 且拼错不报错
/// <reference types="vite/client" />

interface ImportMetaEnv {
  readonly VITE_APP_NAME: string
  readonly VITE_API_BASE: string
  // 内置变量已由 vite/client 提供：MODE、BASE_URL、PROD、DEV、SSR
}

interface ImportMeta {
  readonly env: ImportMetaEnv
}

// 使用处：注意这些在产物里是字面量，不是运行时读取
console.log(import.meta.env.VITE_API_BASE)   // 构建后变成 "https://api.example.com"
console.log(import.meta.env.MODE)            // development 或 production 或自定义 mode
console.log(import.meta.env.BASE_URL)        // base 配置值，拼运行时资源路径必须用它

// 这种写法会被 tree shaking 整块删掉，适合埋开发期调试代码
if (import.meta.env.DEV) {
  void import('./devtools').then((m) => m.mount())
}

CSS 与 TypeScript

CSS 方面 Vite 基本零配置：装上 sass 或 less 就能直接 import 对应文件；文件名带 .module.css 就自动启用 CSS Modules；根目录有 postcss.config.js 就自动接管 PostCSS 流水线。

方案需要装什么作用域隔离注意
普通 .css无无，全局生产构建会合并，样式顺序可能与开发期不同
.module.css无有，类名被哈希类名要用驼峰或配 localsConvention，否则得用方括号访问
Sass 或 Less对应预处理器包看写法全局变量用 css.preprocessorOptions.additionalData 注入
PostCSS 与 Tailwind配置文件即生效原子类内容扫描路径写错会导致类名被摇掉，线上样式丢失
?inline 后缀无不注入拿到 CSS 字符串而不插入页面，用于 Shadow DOM

TypeScript 方面有一条必须记住的硬事实：Vite 只转译，不做类型检查。esbuild 擦掉类型语法就返回，速度极快，代价是类型错误在开发期和构建期都完全静默。CI 里必须单独跑 tsc --noEmit 并让它成为卡口，否则类型系统等于没有。同时建议开启 verbatimModuleSyntax，让「仅类型的导入没写 import type」这类问题在编辑器里就报出来——它在生产构建时可能表现为把整个模块打进产物。

开发期跨域：server.proxy

代理的原理是让 dev server 代替浏览器去请求后端，浏览器眼里所有请求都是同源的，于是不触发跨域检查。它只在开发期生效，生产环境的同源问题要靠 Nginx 或网关解决。

sequenceDiagram participant B as 浏览器 participant V as Vite Dev Server participant A as 后端 api.internal B->>V: fetch 走 api 前缀 同源 不触发预检 V->>V: 匹配 server.proxy 规则 V->>V: rewrite 去掉 api 前缀 V->>V: changeOrigin 为真 把 Host 改成目标域名 V->>A: 转发请求 带上原始 cookie 与头 A-->>V: 响应 Set-Cookie 可能带 domain 属性 V->>V: cookieDomainRewrite 改写 domain V-->>B: 浏览器视为同源响应 cookie 能写入 Note over B,A: 生产环境没有这一层
要靠 Nginx 或网关做同源 
// vite.config.ts
import { defineConfig, loadEnv } from 'vite'
import react from '@vitejs/plugin-react'
import path from 'node:path'

export default defineConfig(({ mode }) => {
  // 第三个参数传空字符串才能读到无前缀变量，用于配置文件内部
  const env = loadEnv(mode, process.cwd(), '')

  return {
    plugins: [react()],
    // 部署到子路径时必须配，否则产物里的绝对路径全部 404
    base: env.VITE_PUBLIC_PATH || '/',
    resolve: {
      // 要与 tsconfig 的 paths 保持一致，否则编辑器能跳转但构建失败
      alias: { '@': path.resolve(__dirname, 'src') },
    },
    server: {
      port: 5173,
      // 设为 true 才能被局域网其他设备访问，真机调试必备
      host: true,
      proxy: {
        '/api': {
          target: env.DEV_API_TARGET ?? 'http://127.0.0.1:8080',
          changeOrigin: true,                       // 不开的话按 Host 路由的后端会 404 或 403
          rewrite: (p) => p.replace(/^\/api/, ''),  // 后端没有 api 这层前缀时去掉
          // 后端下发的 cookie 带 domain 时浏览器会拒收，改写成空表示当前域
          cookieDomainRewrite: '',
          // WebSocket 必须单独开，否则实时功能在开发期全挂
          ws: true,
          // 本地后端用自签证书时才需要
          secure: false,
        },
      },
    },
  }
})

常用命令与各自的作用范围

这几个命令背后是两套完全不同的构建路径，搞混它们会让排查方向从一开始就错。dev 走按需转译那一套，build 走 Rollup 全量打包，preview 只是一个托管 dist 的静态服务器——它是用来验证产物的，不是用来开发的。

命令实际做什么常被误解的地方
vite 或 vite dev起开发服务器，按需转译，带热更新它不产出任何文件，dist 里的东西是上次 build 留下的
vite build用 Rollup 全量打包到 dist不做类型检查；大项目耗时按分钟算是正常的
vite preview用静态服务器托管已有产物它不会重新构建，改了代码必须先 build；也没有热更新
vite --force丢弃预构建缓存重新优化依赖不会清理 dist，也不等于删 node_modules
vite --host监听所有网卡，允许局域网访问真机调试必备，但这会把开发服务器暴露给同网段所有设备，公共网络下要慎用
vite build --mode staging以指定模式构建，加载对应的 env 文件mode 与 NODE_ENV 是两件事，自定义 mode 下仍按生产方式打包

最后一行的区别值得单独记住：mode 决定加载哪些 .env 文件，NODE_ENV 决定依赖库内部走开发分支还是生产分支。用 --mode staging 构建时 Vite 仍然按生产方式打包，所以不会意外把框架的开发版打进产物；但如果有人在 .env.staging 里手写了一个开发用的 NODE_ENV，就会得到一个又慢又大、还带完整警告输出的产物，这类问题往往要等到线上性能异常才被发现。

反模式后果正确做法
把密钥放进 VITE_ 变量明文进产物，等于公开发布密钥密钥只留在服务端，前端通过自己的后端代理调用
以为 Vite 会做类型检查类型错误全量流到生产CI 单独跑 tsc --noEmit 作为卡口
资源路径写死斜杠开头部署到子路径后全部 404用 import 或拼 import.meta.env.BASE_URL
普通图片放 public没有内容哈希，无法做长缓存，改图后用户看到旧图放 src 下用 import 引入
改 .env 后不重启以为配置没生效，反复怀疑写错了环境变量在启动时读取，必须重启 dev server
忘记本地有 .env.local团队配置被本地文件静默覆盖，两人环境行为不一致排查配置问题第一步先看有没有 local 文件

❌
最容易踩的坑
  • 把密钥写成 VITE_ 变量：构建时被替换成明文字面量，前端产物里搜一下就能看到，属于真实的泄露事故。
  • 指望 Vite 报类型错：esbuild 只擦除类型语法，CI 里不单独跑 tsc --noEmit 的话类型系统形同虚设。
  • 静态资源路径写死以斜杠开头：部署到 /app/ 这类子路径后全部 404，必须用 BASE_URL 拼。
  • 把 index.html 放进 public：它会被原样拷贝、不参与构建，线上直接白屏。
  • 改完 .env 只等热更新：环境变量在启动时读取，必须重启服务器。
  • 忘了自己有 .env.local：它优先级高于 .env，会静默覆盖团队配置，是「我这儿好的你那儿不行」的常见根因。
  • 测试里依赖 .env.local：测试模式下这个文件不会被加载，这是刻意设计。
  • alias 与 tsconfig paths 不同步：症状是编辑器能跳转但构建失败，或反过来，两边必须一起改。
  • proxy 忘开 changeOrigin 或 ws：前者导致后端 404 或 403，后者让开发期所有实时功能失效。
  • monorepo 里本地包被预构建缓存：改了源码要重启才生效，要把它加进 optimizeDeps.exclude。
  • Tailwind 的内容扫描路径写漏目录：那部分类名被当成未使用摇掉，表现为线上局部样式全丢。
  • 依赖样式的 import 顺序：开发期逐个注入、生产期合并，优先级可能反转，线上出现被覆盖的样式。
