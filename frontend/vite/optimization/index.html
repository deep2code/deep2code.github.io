生产构建优化：分包、体积预算与产物分析

构建优化最常见的错误不是配错参数，而是没看产物就开始优化。凭感觉加 manualChunks、凭感觉开压缩选项，忙了一天体积没降多少，甚至因为分包过细让首屏更慢了。这一篇按真实的排查顺序来：先看清产物，再决定改什么。开发期与生产期走两条构建路径这件事见 架构篇，配置项与插件钩子见 配置与插件机制。

产物分析是起点

先装 rollup-plugin-visualizer，构建后会生成一张可交互的体积图。务必看 gzip 或 brotli 之后的数字——未压缩体积会把你引向错误的优化点，因为重复文本的压缩率极高，一个未压缩 200KB 的文件压完可能只有 15KB。

看的顺序找什么典型根因收益量级
1. 最大的单个依赖占比最高的第三方包为一个功能引入了全功能库，如日期库、富文本、图表常见几十到几百 KB
2. 重复打包的库同名包的两个版本共存子依赖锁定了不同版本，或 monorepo 里多份 node_modules等于那个包的完整体积
3. 未被摇掉的部分整包引入的工具与图标用了命名空间导入，或包本身不支持摇树几十 KB 到上百 KB
4. 首屏 chunk 的成分本该懒加载的路由代码某处不小心用了静态导入，懒加载被击穿整个页面模块的体积
5. 业务代码分布单个路由 chunk 异常大页面内没有二次拆分，或内联了大量常量数据看具体情况
6. 资源文件超大图片、未裁剪的字体直接放了设计稿原图，字体没做子集化图片常是最大单项

分包策略与长缓存

分包的唯一目的是让用户下次访问时尽可能多地命中缓存。因为文件名带内容哈希，内容不变哈希就不变，浏览器直接用本地副本。所以分包的原则是按「更新频率」切，而不是按「代码类型」切。

// vite.config.ts
import { defineConfig } from 'vite'
import react from '@vitejs/plugin-react'
import { visualizer } from 'rollup-plugin-visualizer'

export default defineConfig({
  plugins: [
    react(),
    // 只在需要分析时启用，避免每次构建都生成报告
    process.env.ANALYZE && visualizer({
      filename: 'dist/stats.html',
      gzipSize: true,        // 必须开：未压缩体积会误导判断
      brotliSize: true,
      open: true,
    }),
  ].filter(Boolean),

  build: {
    // 默认值较新；设太低会引入大量降级代码与 polyfill，设太高老设备白屏
    target: 'es2020',
    // 默认 4KB 以下资源内联成 base64，内联的东西无法被单独缓存
    assetsInlineLimit: 4096,
    // 提高警告阈值不等于解决问题，真正的卡口应该放在 CI 脚本里
    chunkSizeWarningLimit: 600,
    rollupOptions: {
      output: {
        // 用函数形式而不是对象形式：对象形式无法表达按目录的规则
        manualChunks(id) {
          if (!id.includes('node_modules')) return undefined

          // 框架单独一个 chunk：升级频率最低，缓存命中率最高
          if (/[\\/]node_modules[\\/](react|react-dom|scheduler)[\\/]/.test(id)) {
            return 'framework'
          }
          // 体积大且稳定的依赖单独拆，避免它污染其他 chunk 的哈希
          if (/[\\/]node_modules[\\/](echarts|monaco-editor)[\\/]/.test(id)) {
            return 'heavy-vendor'
          }
          // 其余依赖合并成一个 vendor，不要按包名一个个拆
          // 按包名全拆会产生上百个小文件，压缩率下降且请求数暴涨
          return 'vendor'
        },
        // 产物文件名带内容哈希，这是长缓存的前提
        entryFileNames: 'assets/[name]-[hash].js',
        chunkFileNames: 'assets/[name]-[hash].js',
        assetFileNames: 'assets/[name]-[hash][extname]',
      },
    },
  },

  esbuild: {
    // 生产去掉 console 与 debugger；注意这会让线上排查少一批信息
    // 保留 console.error 通常更实用
    drop: process.env.NODE_ENV === 'production' ? ['debugger'] : [],
    pure: process.env.NODE_ENV === 'production' ? ['console.log', 'console.debug'] : [],
  },
})
分包策略缓存命中表现请求数适用
完全不配 manualChunks依赖与业务混在一起，改业务代码就让依赖缓存失效少小项目、依赖很少时可以接受
所有依赖一个 vendor任意依赖升级导致整包失效，用户重下全部第三方代码少不推荐，是最常见的错误配置
框架加通用 vendor 两层框架长期命中，其余依赖按季度失效适中推荐的默认策略
再把超大依赖单独拆大依赖不污染其他 chunk 的哈希适中有图表库、编辑器这类重依赖时
按包名逐个拆命中率高但请求数与总体积都变差很多基本不推荐
业务代码按路由拆改一个页面只失效一个 chunk按需加载，首屏少必做
⚠️
过度分包的三个代价

一是请求数：HTTP/2 的多路复用缓解了队头阻塞，但每个请求仍有头部与优先级调度成本，几十上百个小 chunk 会把首屏瀑布拉长。二是重复依赖：切得太碎时被多处引用的模块可能被复制进多个 chunk，总体积反而上升。三是压缩率下降：小文件各自压缩明显不如合并后压缩，几十个几 KB 的文件加起来常比一个大文件更大。缓存头、压缩与 HTTP/2 的细节见站内 前端性能优化。

导出必须能静态分析库内部用动态属性访问导出看库源码是否存在运行时拼接导出名换库，或只引它的子模块
模块顶层不能有注册副作用导入即执行，打包器不敢删看被保留模块的顶层是否有语句执行把注册逻辑改成显式调用

懒加载与加载失败：一个真实事故

按路由懒加载是首屏优化的基础，但它有一个必须处理的失败路径，而绝大多数项目都漏了。用户打开页面时加载的是旧版本入口，里面记着旧版本 chunk 的文件名；部署新版本后旧 chunk 被清理，用户点进一个未访问过的路由，请求到 404，动态导入的 Promise 被拒绝，没有捕获就是整页白屏。

sequenceDiagram participant U as 用户浏览器 已加载旧入口 participant C as CDN 或静态服务 participant D as 部署流水线 U->>C: 请求首页 拿到旧版 entry 哈希 a1b2 D->>C: 发布新版本 上传新产物并清理旧文件 U->>C: 用户点击订单页 请求 order-a1b2.js C-->>U: 404 该文件已被清理 U->>U: 动态导入 Promise 被拒绝 Note over U: 无捕获则整页白屏
用户只看到点击没反应或空白 U->>U: 兜底一 捕获失败并提示刷新 U->>C: 刷新后拿到新版 entry 与新 chunk 名 Note over C,D: 兜底二 部署保留旧产物一段时间
兜底三 响应头回传版本号主动提示 
// router/lazy.ts —— 带失败兜底的懒加载封装
import { lazy, type ComponentType } from 'react'

// 新版本发布后旧 chunk 404 是必然会发生的，不是边界情况
export function lazyWithRetry<T extends ComponentType<any>>(
  factory: () => Promise<{ default: T }>,
  chunkName: string,
) {
  return lazy(async () => {
    try {
      return await factory()
    } catch (err) {
      // 用 sessionStorage 标记，避免刷新后仍失败造成无限刷新循环
      const flagKey = `chunk-retry:${chunkName}`
      const alreadyRetried = sessionStorage.getItem(flagKey) === '1'

      if (!alreadyRetried) {
        sessionStorage.setItem(flagKey, '1')
        // 重新加载页面即可拿到新版本的 entry 与正确的 chunk 名
        window.location.reload()
        // 返回一个永不 resolve 的 Promise，等页面被替换掉
        return new Promise<{ default: T }>(() => {})
      }

      // 已经刷过一次还失败，说明是真的网络或部署问题，给用户明确提示
      sessionStorage.removeItem(flagKey)
      throw err
    }
  })
}

// 使用：路由表里统一走这个封装，不要裸写动态导入
const OrderPage = lazyWithRetry(() => import('../pages/Order'), 'order')
const ReportPage = lazyWithRetry(() => import('../pages/Report'), 'report')

// 注意：懒加载会被静态导入击穿
// 如果别处存在对同一模块的静态导入，它会被并入首屏 chunk，懒加载完全失效
// 排查方式是在产物分析图里确认该页面代码是否出现在 entry 里

target 与压缩

build.target产物特征体积影响什么时候该用
es2015 或更低大量语法降级，异步函数被改写成状态机明显变大，常见增加一到两成确实要支持很老的设备时
es2018保留 async 但降级新语法略增需要兼容较老的移动端浏览器
es2020保留可选链与空值合并较小常见的安全选择
Vite 默认基线只做必要处理最小用户群是现代浏览器时的默认
esnext几乎不降级最小Electron、内部工具、已知运行环境

把 target 设成 es5 却并不需要，是一种很常见的无意义膨胀：可选链、空值合并、async 这些语法一旦降级，会引入辅助函数和状态机代码，还会让压缩效果变差。判断依据应该是真实访问数据里的浏览器分布，而不是「保险一点」。如果确实有少量老设备，更合理的做法是给它们单独产出一份降级包，而不是让全部用户承担。

体积预算做成 CI 卡口

这是唯一能真正阻止体积缓慢膨胀的手段。原因很简单：每次需求只多几十 KB，没有任何人会因此拒绝合并，但一年下来首屏就翻倍了。人工 review 拦不住这种渐变，只有自动化卡口能拦。

// scripts/size-budget.mjs —— 构建后执行，超预算则退出码非零让 CI 失败
import { readdir, readFile, stat } from 'node:fs/promises'
import { gzipSync } from 'node:zlib'
import path from 'node:path'

// 阈值按 gzip 后体积定，因为那才是用户实际下载量
// 数值取当前值加少量余量，目的是防膨胀而不是立刻迫使大重构
const BUDGET = [
  { pattern: /^assets\/index-.*\.js$/,     maxKb: 120, label: '入口 JS' },
  { pattern: /^assets\/framework-.*\.js$/, maxKb: 60,  label: '框架 chunk' },
  { pattern: /^assets\/vendor-.*\.js$/,    maxKb: 220, label: '通用依赖 chunk' },
  { pattern: /^assets\/index-.*\.css$/,    maxKb: 40,  label: '入口 CSS' },
  // 懒加载 chunk 用统一的宽松上限，只拦异常膨胀
  { pattern: /^assets\/(?!index|framework|vendor).*\.js$/, maxKb: 180, label: '路由 chunk' },
]

const dist = 'dist'
const files = []
async function walk(dir) {
  for (const e of await readdir(dir, { withFileTypes: true })) {
    const full = path.join(dir, e.name)
    if (e.isDirectory()) await walk(full)
    else files.push(path.relative(dist, full).split(path.sep).join('/'))
  }
}
await walk(dist)

let failed = false
for (const rel of files) {
  const rule = BUDGET.find((b) => b.pattern.test(rel))
  if (!rule) continue
  const buf = await readFile(path.join(dist, rel))
  const gzipKb = gzipSync(buf, { level: 9 }).length / 1024
  const over = gzipKb > rule.maxKb
  if (over) failed = true
  // 输出必须说清是哪个文件超了多少，否则同事只会来问构建为什么挂了
  console.log(
    `${over ? 'FAIL' : ' ok '} ${rule.label.padEnd(14)} ${rel}  ${gzipKb.toFixed(1)}KB / ${rule.maxKb}KB`,
  )
}

if (failed) {
  console.error('\n体积超出预算。要么优化，要么在本文件里显式上调阈值并在 PR 里说明原因。')
  process.exit(1)
}

资源处理与预加载

项目关键点常见错误
内联阈值assetsInlineLimit 默认 4KB，小于它的资源变成 base64调太大导致关键 JS 膨胀，且内联内容无法被单独缓存
图片构建工具不会帮你压缩图片，需要插件或构建前处理直接放设计稿原图，单张就超过全部 JS 体积
字体中文字体必须做子集化，全量字体常有几 MB引入全量字体并设为首屏阻塞资源
预加载指令Vite 会为入口的直接依赖自动生成 modulepreload手工再加一堆 preload，抢占带宽反而拖慢首屏
CSS 代码分割默认开启，每个异步 chunk 的 CSS 单独产出关掉它得到一个大 CSS，首屏被迫加载全站样式
sourcemap生产建议产出但不部署到公开路径，上传给错误监控平台直接部署到 CDN，等于公开源码

产物文件名哈希与缓存头的配合方式（不可变资源用长 max-age、HTML 用协商缓存）结论明确，细节见站内 前端性能优化；发布期新旧资源共存的部署策略见 前端工程化。

反模式对照

反模式后果正确做法
不做产物分析凭感觉优化花一天时间砍掉 5KB，真正的大头没动先看 gzip 后的体积图，按占比从大到小处理
把所有依赖塞进一个 vendor任意依赖升级让全量第三方缓存失效至少分成框架与通用依赖两层，重依赖单独拆
manualChunks 按包名逐个拆上百个小文件，压缩率下降、请求数暴涨首屏关键 chunk 控制在个位数
target 设成 es5 但并不需要引入大量降级代码，体积无谓增加一两成按真实浏览器分布定，必要时单独产降级包
动态导入不处理失败新版本发布后老用户点击即白屏统一封装懒加载，捕获失败并提示刷新
部署时直接清空旧产物放大上面那个事故的影响面保留旧版本产物一段时间再清理
靠调高 chunkSizeWarningLimit 解决告警告警消失，问题留下，体积继续增长把预算做成 CI 卡口
把 sourcemap 部署到公开路径等于公开全部源码构建产出但不发布，上传给错误监控平台
用命名空间形式整包导入工具库tree shaking 完全失效具名导入或按子路径导入
❌
最容易踩的坑
  • 看未压缩体积做决策：重复文本压缩率极高，未压缩的排序常和实际下载量的排序不一致。
  • 所有依赖一个大 vendor：升级一个小工具库就让用户重下几百 KB，这是最常见的错误配置。
  • manualChunks 拆得过细：请求数、重复依赖、压缩率三方面同时变差，可能比不拆更慢。
  • 动态导入没有失败兜底：新版本上线后老标签页点击即白屏，而且只有部分用户遇到，极易被当成偶发问题忽略。
  • 重试逻辑没有防循环标记：刷新后仍失败会导致无限刷新，比白屏更糟。
  • 懒加载被静态导入击穿：别处对同一模块的静态导入会把它并进首屏 chunk，配置看起来没问题但完全无效。
  • target 设成 es5 却没有老设备：无谓引入降级代码与辅助函数，还降低压缩效果。
  • drop_console 一刀切：把 console.error 也删掉后，线上错误监控失去上下文。
  • 调高 chunk 警告阈值当成优化：告警静音了，体积照旧增长，半年后首屏翻倍。
  • 内联阈值调得过大：资源被塞进 JS，既让关键脚本变大，又失去单独缓存的能力。
  • 中文字体不做子集化：几 MB 的字体常常是页面最大的单项资源，比所有 JS 加起来还大。
  • sourcemap 直接部署上线：任何人都能还原出完整源码，属于真实的信息泄露。
