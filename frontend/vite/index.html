Vite 的架构：为什么开发期不打包

🏷️ Vite

「Vite 比 Webpack 快」这句话本身没错，但把原因归结为「用 Rust 或 Go 写的所以快」就完全跑偏了。Vite 的开发服务器主体是 JavaScript 写的，它快的根因是换了一套开发期模型：不打包。理解这个模型，才能理解它的全部优势，以及它带来的那个绕不开的代价——开发和生产走的是两条不同的构建路径。

核心洞察：浏览器自己就会加载模块

打包这件事最初是被迫的：浏览器不认识 require，也不支持模块化，所以必须有工具把几百个文件拼成一个能在 <script> 里跑的大文件。但现代浏览器已经原生支持 ESM——你给它一个 <script type="module" src="/src/main.tsx">，它会自己解析里面的 import 语句，再去请求被引用的模块，递归下去。

既然浏览器会自己加载，开发期的工具就不需要做打包了，只需要一个能按请求返回单个模块的服务器：浏览器请求 /src/App.tsx，服务器把这个文件用 esbuild 转译掉 TS 语法和 JSX，把 import 'react' 这种裸模块名重写成预构建产物的路径，返回。整个过程只碰一个文件。

HMR 为什么能做到精确更新

Vite 的 HMR 不是「刷新页面」，而是沿着模块图找到最近的 HMR 边界，只替换那一段。所谓边界就是调用了 import.meta.hot.accept 的模块：React 项目里这件事由 react-refresh 自动完成（组件文件天然是边界），Vue 由 SFC 插件完成。如果向上一直找不到边界，就退化成整页刷新。

accept 了吗"} A -->|是| S1["只替换本模块
组件状态保留"] A -->|否| P["沿引用方向向上传播"] P --> B{"父模块
accept 了吗"} B -->|是| S2["替换父模块子树
子组件状态丢失"] B -->|否| C{"到达入口
仍无边界"} C -->|是| S3["整页刷新
所有状态丢失"] F2["修改 utils.ts 纯函数模块"] --> P F3["修改 vite.config.ts"] --> S4["服务器重启
整页刷新"] F4["修改 .env"] --> S4

这解释了两个常见困惑。一是为什么改某些文件会整页刷新：因为你改的是一个没有边界、且所有引用方都不是边界的模块（典型是 constants.ts、store.ts）。二是为什么改组件后状态有时保留有时丢失：react-refresh 只在文件里全是组件导出时才能做到状态保留，一旦你在组件文件里同时导出了一个普通函数或常量，边界会退化到上层。

// 需要手动声明边界的典型场景：一个非组件的运行时模块
// 比如某个全局配置或状态容器，希望改完不整页刷新
export const config = { theme: 'dark', pageSize: 20 }

if (import.meta.hot) {
  // accept 自身：模块被替换时执行回调，newModule 是新版本
  import.meta.hot.accept((newModule) => {
    if (!newModule) return               // 新模块有语法错误时为 undefined
    applyConfig(newModule.config)        // 手动把新值应用到运行时
  })

  // dispose 用来清理副作用，不写会造成定时器与监听器泄漏
  // 症状是改十次代码后出现十个并行的轮询
  import.meta.hot.dispose(() => {
    clearInterval(timer)
    window.removeEventListener('resize', onResize)
  })
}

生产必须打包：双引擎架构与它的代价

如果原生 ESM 这么好，为什么生产不也这样？因为开发期能接受的请求数，生产期完全不能接受：一个中型项目有几千个模块，让用户的浏览器逐个请求，加上深层 import 链会串行化、同域并发连接有上限，首屏时间会退化到不可用。而且 tree shaking、作用域提升、压缩、内容哈希这些优化都需要看到完整依赖图。

这个双引擎设计带来一个必须正面承认的风险：开发时跑通不代表能构建成功，构建成功也不代表行为一致。这不是 bug，是架构选择的直接后果。对策只有一个：把 vite build 和 vite preview 放进 CI，每个提交都跑，不要留到发版前。

现象根因为什么 dev 没暴露修法
build 报类型错误esbuild 只擦除类型，不做检查dev 完全不跑类型检查CI 里单独跑 tsc --noEmit
某依赖 default 导出变成 undefinedCommonJS 与 ESM 互操作差异dev 下该依赖走 esbuild 预构建，已被规范成 ESMoptimizeDeps.include 显式纳入，或改用命名导入
循环依赖导致运行时 undefinedRollup 整图打包后执行顺序变了dev 下逐个模块加载，顺序恰好可用用 rollup-plugin-visualizer 或 madge 找环并解开
仅类型的导入被当成值打进产物没有用类型导入语法，打包器保留了引用dev 下该模块也能加载，不报错开启 verbatimModuleSyntax，类型一律用 import type
动态 import 在生产找不到模块路径是完全动态拼接的，无法静态分析dev 下服务器按实际路径直接返回改用 import.meta.glob 或让路径含静态前缀
顶层 await 报错build.target 过低，不支持该语法dev 直接给现代浏览器，无降级抬高 target，或把顶层 await 包进函数
CSS 优先级在生产变了打包后样式合并顺序与逐个请求时不同dev 下 CSS 按 import 顺序单独注入避免依赖样式顺序，用 CSS Modules 或提高选择器确定性
process.env.XXX 是 undefined浏览器没有 process，Vite 只替换显式声明的变量某些依赖在 dev 下恰好没走到该分支改用 import.meta.env，或用 define 显式注入

依赖预构建：不做不行的一步

预构建（pre-bundling）常被误认为是「为了快的优化」，其实它是让不打包模型能成立的前提，有两个硬需求：

第一是格式。node_modules 里仍有大量只提供 CommonJS 的包，浏览器不认 require，必须先转成 ESM。第二是请求数。很多库把自己拆成几百甚至上千个小文件（图标库、lodash-es 这类工具库是典型），如果让浏览器逐个请求，光一个依赖就能产生上百个请求，开发体验会被彻底毁掉。Vite 用 esbuild 把每个依赖预打包成一个 ESM 文件放进 node_modules/.vite/deps，并让浏览器对它做 immutable 强缓存，于是这部分开销只在首次启动付一次。

# 看预构建产物：每个依赖被压成一个文件，请求数从上百降到 1
ls node_modules/.vite/deps/ | head
# react.js  react-dom_client.js  lodash-es.js  _metadata.json

# _metadata.json 里记录了每个依赖的 hash，依赖或配置变化时才重新预构建
# 判断是否命中缓存：启动日志里有没有出现 "optimizing dependencies"

# 怀疑缓存脏了（常见于切分支、改 lockfile、手动改过 node_modules）
npx vite --force          # 丢弃缓存重新预构建

# 彻底清理
rm -rf node_modules/.vite

# 排查首屏请求数是否失控：开发期打开网络面板过滤 JS
# 超过一两千个请求时，瀑布本身就成了瓶颈，该拆路由懒加载了
⚠️
页面突然自动刷新一次，是预构建在补课

最常见的现象是：某个依赖只在动态 import 的分支里被用到，启动扫描没发现它，等你点进那个路由时 Vite 才现场预构建，完成后强制刷新页面。表现就是「点某个菜单页面会白一下然后刷新」。修法是把这类依赖写进 optimizeDeps.include，让它在启动时就被预构建。

纠正一个流传很广的说法：冷启动与规模无关

「Vite 的启动速度与项目大小无关」这句话只对了一半。服务器启动确实与规模无关，但首屏加载与规模强相关：浏览器要为首屏用到的每个源码模块发一次请求，模块数上千时请求瀑布本身就是瓶颈，深层 import 链会串行化，浏览器对同一域名还有并发连接上限。在几千个模块的巨型单页应用里，Vite 开发期的首屏有可能比 Webpack 的 bundle 更慢。

这也正是社区在推进全量 bundle 模式和依赖预热的原因。判断方法很直接：开发期打开网络面板，看首屏 JS 请求数，超过一两千就该拆路由懒加载，或者用 server.warmup 提前转译热点文件。

❌
最容易踩的坑
  • 只测 dev 不测 build：双引擎架构下这两条路径必然有行为差异，不跑 build 等于把风险全押在发版日。
  • 以为 Vite 帮你做类型检查：esbuild 只擦除类型语法，类型错误在开发期完全静默。
  • 期待生产构建也很快：生产是 Rollup 全量打包加压缩，大项目几分钟是正常的，别按 dev 的体感估 CI 时间。
  • 页面莫名自动刷新：通常是动态导入的依赖没被启动扫描发现，触发了运行时补做预构建，用 optimizeDeps.include 提前声明。
  • 组件文件里混着导出普通函数或常量：react-refresh 的状态保留失效，HMR 边界上移，改一行就整页刷新。
  • 手写 import.meta.hot.accept 忘了 dispose：定时器与监听器不断累积，症状是越改越卡、请求越来越多。
  • 用 process.env 读环境变量：浏览器里没有 process，Vite 只替换显式声明的变量，要用 import.meta.env。
  • 依赖样式的引入顺序：dev 下逐个注入、生产下合并，优先级可能反转，表现为线上样式被覆盖。
  • 循环依赖在 dev 侥幸能跑：Rollup 整图打包后执行顺序变化，生产才暴露成 undefined，排查成本极高。
  • 完全动态拼接的 import 路径：dev 能返回文件，生产无法静态分析导致模块缺失，要用 import.meta.glob。
  • 切分支后不清预构建缓存：lockfile 变了但 .vite 里还是旧依赖，症状千奇百怪，先试 --force。
  • 巨型项目不拆路由懒加载：开发期首屏上千个模块请求，瀑布本身成为瓶颈，这时候「Vite 快」不再成立。
