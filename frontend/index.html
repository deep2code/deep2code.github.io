先决定渲染发生在哪里

后端同学看前端容易从框架开始，其实框架是最后一步。前端架构的第一个分叉是HTML 在哪里产生：构建机、机房里的渲染进程、CDN 边缘节点，还是用户的浏览器。这个选择一旦定下来，接口形态、缓存策略、部署拓扑、甚至值班范围都跟着变——服务端渲染意味着后端多了一个需要扩容和监控的常驻进程。

渲染位置首屏内容来自哪里对后端接口的要求缓存放在哪一层什么时候会翻车
静态生成构建时已经写死在 HTML 里构建期能批量取数；运行期可以完全不依赖接口CDN 强缓存，按发布或增量再生成失效数据更新频繁或因人而异时，构建时间和失效范围失控
服务端渲染请求时由渲染进程取数据拼出内网接口，延迟低但会串成瀑布，必须能并行调用并接受更短超时页面级缓存要按登录态分片，接口结果缓存在服务端接口慢或抖动直接变成首字节慢，渲染进程还会被拖垮
流式渲染先发骨架，数据到了再补对应片段接口必须按区块拆分，慢区块不能阻塞整页骨架可缓存，数据片段按区块各自缓存中间任何一层缓冲住响应，分块就退化成一次性返回
客户端渲染JS 执行后再发接口请求要聚合接口，减少公网往返；跨域与鉴权规则必须明确浏览器 HTTP 缓存加客户端内存缓存串行请求瀑布叠加公网延迟，弱网下首屏迟迟不可用

构建产物与缓存失效

前端工程化的核心产物只有三类：入口 HTML、带内容指纹的静态资源、按路由或组件切出来的异步分包。三者的缓存策略必须不同，配反了就会出现「发布完成但用户还在跑旧代码」或者「每次发布全站资源都失效」两种极端。

产物类型文件名策略缓存头怎么失效常见事故
入口 HTML固定名字禁止强缓存，用协商缓存回源校验每次请求都校验，发布后立即生效被 CDN 或浏览器强缓存住，新版本迟迟不生效
主包与样式文件名带内容指纹长期强缓存并标记为不可变内容变则文件名变，天然失效把公共依赖和业务代码打进同一个包，任何小改动都让全量缓存失效
路由异步分包文件名带内容指纹，路径按路由划分长期强缓存同上，但必须保留旧版本一段时间发布时清空旧产物，长时间停留的页面点击路由后分包 404
图片与字体带指纹或带版本目录长期强缓存换名字或换目录字体未做预加载，首屏文字闪烁或位移

代码分割的收益不在「包更小」，而在让缓存的失效范围可控：公共依赖单独成包，业务代码按路由切分，一次业务改动只让一个小分包失效。反过来，分包过细也有代价，几十个小请求在弱网上的握手与优先级开销可能吃掉收益。

数据获取与状态的分层

「状态管理选什么库」这个问题问错了方向。真正要先分清的是状态的归属层级：服务端权威数据、HTTP 层缓存、客户端服务端数据缓存、页面导航状态、组件内临时状态。归错层是前端最常见的复杂度来源——把服务端数据塞进全局状态容器，就得自己手写失效、重试、并发去重，而这些本来是数据获取层该做的事。

一个实用判据：能从服务端重新取回来的数据，不要长期存在全局状态里；只有纯客户端状态（当前选中项、折叠状态、未提交的表单）才属于界面层。可分享、可刷新恢复的状态应该放进路由参数，而不是内存。

前后端契约：真正省时间的四件事

联调时间长，绝大多数不是因为难，而是因为契约没定死。以下四项在项目开始时定清楚，后期能省掉大量来回。

契约项推荐做法后端必须保证的部分破坏契约时的症状
类型来源由接口描述文件或 IDL 生成两端类型，禁止手抄字段只增不改语义；删除字段前先标记废弃并给过渡期前端按旧类型解析，某个字段突然变成空值却不报错
错误约定传输层状态码表达协议级失败，业务失败用稳定业务码加可展示文案业务失败不要返回 500，错误码枚举保持稳定且可穷举前端只能靠匹配错误文案做分支，文案一改就失效
分页语义列表用游标分页，返回下一页游标与是否还有更多游标要基于稳定有序的键；避免偏移量深翻页扫描大量行翻到后面越来越慢，翻页期间有插入就重复或漏数据
鉴权载体同站用 Cookie 并明确站点策略，跨站或多端用请求头携带令牌跨域时预检与凭证策略要匹配；凭证模式下不能用通配来源本地联调正常，上线跨子域后请求不带凭证，接口全部未授权

性能指标里后端真正能影响的部分

前端性能指标不要全部背在后端身上，也不要全部推给前端。按「谁能改」拆一下，投入方向就清楚了：首字节时间是所有指标的地板，几乎完全由后端与链路决定；最大内容绘制受首字节与首屏资源获取速度影响，后端能出一半力；交互响应性主要看前端主线程；布局偏移基本是前端的尺寸占位问题。

指标它在量什么后端能影响的部分可落地的手段
首字节时间从发起导航到收到第一个字节，含 DNS、连接、服务端处理几乎全部接口聚合减少串行、服务端缓存、连接复用与长连接、开启现代传输协议、就近接入
最大内容绘制视口内最大内容元素完成渲染的时刻约一半首屏图片与字体走 CDN 并设置优先级与预连接、压缩与合适格式、避免首屏资源被低优先级请求挤占
交互到下一次绘制用户交互到界面给出视觉反馈的延迟较小接口延迟要给上界并允许乐观更新，避免交互必须等网络返回
布局偏移页面元素的意外位移程度很小接口返回图片与媒体的宽高等元信息，方便前端预留占位

最值得后端先做的一件事是减少公网往返次数。一个页面在公网上串行发五个请求，弱网下光是往返就能吃掉一两秒，任何前端微优化都补不回来。聚合接口、BFF，或者用查询语言让前端一次取全，都是同一个动机（站内后端专题里的 GraphQL 系列讲的就是这件事的代价与边界）。

这个专题各子方向怎么读

三条常见路线：后端要临时接手前端，先看上面的渲染位置与契约两节，再读框架选型与工程化；要优化一个慢页面，先按指标表定位归属，再读性能优化篇；要做跨端或重计算场景，直接看跨端与新技术组。下表给每个子方向一句「什么时候该读它」。

子方向它解决的问题什么时候该读它
框架选型对比主流框架的取舍维度与团队适配新项目定技术栈、或需要向团队解释为什么不换框架时
React Hooks函数式组件的状态与副作用模型接手 React 项目后被重复渲染和依赖数组困住时
Vue 3 组合式 API响应式原理与逻辑复用方式维护 Vue 项目、或要把选项式写法迁移到组合式时
TypeScript 类型系统类型建模与类型安全的边界要把接口契约变成可编译校验的类型时
前端工程化构建工具、产物切分与流水线发布流程不可复现、或构建时间开始拖慢迭代时
性能优化首屏加载与运行时体验的具体手段指标已经量出来、需要按归属逐项落地时
Flutter一套代码覆盖多端的渲染与工程模型移动端人力不足、界面一致性优先于平台原生观感时
WebAssembly在浏览器里跑接近原生速度的计算有图像、音视频、加解密这类重计算要搬到端上时
Firefox 开发者视角另一套渲染与调试实现的差异遇到只在某个浏览器复现的问题、需要交叉验证时
应用发布打包、签名、渠道与上架流程第一次把客户端交付到应用市场、或发布被审核卡住时
❌
前后端协作里最容易踩的坑
  • 入口 HTML 被强缓存，发布后新旧资源清单错配，用户刷新多次才恢复
  • 发布时清空旧版本产物，仍开着旧页面的用户一点路由就遇到分包加载失败
  • 把服务端数据塞进全局状态容器，然后自己重写一遍失效、重试与并发去重
  • 客户端渲染页面里五六个接口串行调用，弱网下首屏时间被往返次数吃掉
  • 上了流式渲染但代理层缓冲没关，分块输出退化成一次性返回，改动等于白做
  • 业务失败用 500 返回，前端无法区分「该重试」和「该提示用户」
  • 列表用偏移量深翻页，页码越大越慢，翻页期间有新增还会重复或漏数据
  • 跨子域上线后才发现凭证与跨域策略不匹配，本地联调时完全看不出问题
  • 字体与首屏图片没有预留尺寸和优先级，指标里表现为持续的布局偏移
