浏览器渲染与加载路径：后端能影响的部分

🏷️ 浏览器原理

「前端性能」这个说法掩盖了一个事实：用户看到首屏之前的大半时间，控制权在后端和运维手里。DNS、连接、首字节、响应头、缓存分层、协议版本、压缩策略，全都不是改 JS 能解决的。这篇把从请求到像素的路径切成段，逐段说明谁能改、改了影响哪个指标、以及常见的无效优化为什么无效。渲染位置（客户端渲染、服务端渲染、静态生成）的选型不在本篇，一句话结论是内容型页面优先在服务端产出 HTML，细节详见站内 Next.js 篇。

先把时间切段，再谈优化

所有加载性能讨论的第一步都应该是「这一段时间花在哪」。浏览器已经把答案放在 Navigation Timing 里了，不需要猜。

# 检查是否真在流式输出：如果 HTML 是一次性到达，说明中间有缓冲
curl -sS --no-buffer https://example.com/ | head -c 2000

首字节不是「服务端耗时」的同义词

把首字节当成业务耗时是最常见的误判。它至少包含四段：客户端到边缘的网络往返、边缘到源站的回源往返、源站的排队等待、真正的业务处理。只优化最后一段，常常发现首字节几乎没动。

让这四段可观测的标准手段是 Server-Timing 响应头：它能把服务端内部的分段耗时带到浏览器，前端真实用户监控可以直接读到，等于把后端的火焰图接到了线上指标上。跨域读取时需要 Timing-Allow-Origin，否则前端拿到的详细字段全是 0。

⚠️
HTML 用 no-cache，不是 no-store

这两个头经常被搞混。no-cache 的语义是「可以存，但每次使用前必须回源校验」，配合 ETag 时命中就是一个不带响应体的 304，很省流量；no-store 是「完全不许存」，每次都要传完整响应体。除了包含敏感信息的响应，HTML 一律用 no-cache。顺带一提，304 仍然需要一次完整往返，所以它省的是带宽而不是延迟。

流式传输：为什么早期收益常常被缓冲吃掉

HTML 是流式解析的：浏览器拿到第一块字节就开始建 DOM，并由预加载扫描器提前去抓后面出现的脚本、样式、图片。这意味着服务端先刷出 head 再慢慢算 body，能让关键资源的下载与业务计算并行。但这条收益极其容易被链路上的缓冲抹平——反向代理的响应缓冲、压缩模块的缓冲区、模板引擎的一次性渲染，任何一处攒够整包再发，浏览器就只能在原地等。

# 指纹化的静态资源：长缓存 + immutable，让浏览器连协商都不做
location ~* \.(?:js|css|woff2|avif|webp)$ {
    # 前提是文件名里带内容哈希，内容变了文件名一定变
    add_header Cache-Control "public, max-age=31536000, immutable" always;
    # 静态资源不要带 Set-Cookie，很多 CDN 见到它就直接不缓存
    more_clear_headers 'Set-Cookie';
    gzip_static on;
    brotli_static on;      # 预压缩落盘，避免每次请求现压消耗 CPU
}

# HTML：必须协商，且要带上正确的 Vary，否则压缩版本会串给不支持的客户端
location / {
    add_header Cache-Control "no-cache" always;
    add_header Vary "Accept-Encoding" always;

    proxy_pass http://app_upstream;
    # 需要流式输出的路径必须关掉缓冲，否则服务端先刷 head 的收益归零
    proxy_buffering off;
    proxy_request_buffering off;
    proxy_http_version 1.1;          # 与上游保持长连接，省掉每次握手
    proxy_set_header Connection "";
    # 注意 gzip 在动态响应上也会攒缓冲区，流式接口要单独评估
}

Nginx 的缓冲参数全景与上游长连接三件套详见站内 Nginx 篇，这里只强调一点：流式输出是一条端到端的性质，链路上任何一环缓冲，整条链就不是流式的。上线前用不带缓冲的 curl 验证一次，比读配置可靠。

关键渲染路径：阻塞的真实代价

资源与写法阻塞 HTML 解析阻塞首次渲染执行顺序注意
外链样式表不阻塞阻塞不适用首屏用不到的样式应拆出去，或用媒体条件让它不阻塞

带 async 的脚本不阻塞执行时会抢主线程下载完就执行，顺序不定只适合互不依赖的独立脚本

这里有一个流传很广的错误说法：「把脚本放 body 末尾就等于 defer」。放末尾只是让它在前面的 DOM 解析完之后才下载，而 defer 是解析期间就并行下载、解析完再执行——前者白白浪费了下载与解析的重叠时间。另一个错误说法是「样式表不阻塞」，样式表不阻塞解析但阻塞渲染，而且会间接卡住后面的同步脚本。

两个要纠正的认知：第一，HTTP/2 并没有解决队头阻塞，它只是把阻塞从 HTTP 层移到了 TCP 层，真正解决的是基于 QUIC 的 HTTP/3；第二，服务器推送不是「没人用」，而是已经被移除，它的正确替代是 103 提前提示——在服务端还在计算业务逻辑时，先让浏览器去连接和预取关键资源。

需要澄清一个常见误解：接口慢并不会直接抬高交互指标。交互指标衡量的是从用户输入到下一次绘制的时间，只要前端在点击后立刻给出加载态反馈，这个值就是短的。接口慢影响的是用户主观体验和业务转化，别把它和这个指标混为一谈，否则优化方向会完全跑偏。

// 真实用户监控的最小可用版本：一次采集，页面隐藏时上报
const nav = performance.getEntriesByType('navigation')[0];
const seg = {
  dns: nav.domainLookupEnd - nav.domainLookupStart,
  conn: nav.connectEnd - nav.connectStart,
  tls: nav.secureConnectionStart ? nav.connectEnd - nav.secureConnectionStart : 0,
  ttfb: nav.responseStart - nav.requestStart,
  download: nav.responseEnd - nav.responseStart,
  // 服务端分段耗时：跨域时需要 Timing-Allow-Origin，否则这里是空数组
  server: nav.serverTiming.map(t => `${t.name}=${t.duration}`),
};

let lcp = 0;
new PerformanceObserver(list => {
  // 会多次触发，最后一个值才是最终的最大内容绘制
  for (const e of list.getEntries()) lcp = e.startTime;
}).observe({ type: 'largest-contentful-paint', buffered: true });

// 不要用 unload 事件，移动端不可靠；visibilitychange 才是正确的上报时机
addEventListener('visibilitychange', () => {
  if (document.visibilityState !== 'hidden') return;
  navigator.sendBeacon('/api/rum', JSON.stringify({ ...seg, lcp }));
}, { once: true });

字体与图片：后端与 CDN 侧的决定

字体有一条已经变化但很多团队没跟上的事实：浏览器缓存按站点分区之后，公共字体 CDN 的「跨站点共享缓存」收益已经消失了。也就是说用第三方字体域名不再能省下下载，反而多付一次 DNS 加连接。现在的最优解是自托管字体、加内容指纹、设一年长缓存，并对首屏真正用到的那一两个字重做预加载。

预加载字体有一个高频错误：忘记加跨域属性。字体请求默认以匿名跨域模式发出，预加载时属性不匹配会导致浏览器下载两次——预加载那一份完全被浪费。另外 font-display 的选择是在「文字不可见」和「字体替换造成跳动」之间取舍，配合度量覆盖属性把替代字体的行高与字宽对齐，能把这类跳动压到很小。

指令语义适合滥用代价
dns-prefetch只做域名解析确定会用但不紧急的第三方域名成本很低，但数量多了也是无效解析
preconnect解析加连接加 TLS首屏关键的少数几个域名每个都占用连接与握手开销，移动端还耗电；用不到就是纯浪费
preload按指定类型高优先级下载首屏关键字体、LCP 图片、关键样式类型写错或跨域属性不匹配会下载两次；预加载太多会挤掉真正关键的资源
prefetch低优先级预取，供后续导航使用高概率的下一跳页面资源浪费用户流量，弱网下与当前页面抢带宽
103 提前提示在正式响应前先给出预连接与预加载源站计算耗时较长的动态页面提示错了等于让浏览器白做工作；需要 CDN 支持
fetchpriority调整单个资源的优先级把首屏主图提到高优先级到处标高等于没标，优先级信息失去意义

图片侧后端能做的三件事：按请求头协商现代格式（注意让缓存键包含格式维度，否则会把 AVIF 发给不支持的客户端）；在接口或模板里输出图片的原始宽高，让浏览器提前留出位置；给首屏主图提高优先级。对应的反面操作是给首屏主图加懒加载——这会让它排到最后才下载，直接把最大内容绘制指标拖垮，而且这是目前最常见的一类自伤式优化。

❌
最容易踩的坑
  • 把首字节等同于业务耗时：它还包含客户端到边缘、边缘到源站的往返和源站排队，不加 Server-Timing 就只能靠猜。
  • HTML 用 no-store 代替 no-cache：前者每次重传整个响应体，后者命中时只是一个不带响应体的 304。
  • 指望 304 省延迟：它省的是带宽，往返一次照样要付；真正消掉请求的只有带指纹的长缓存加 immutable。
  • 给没有内容指纹的文件设一年长缓存：发布后新旧资源混用，页面会以最难排查的方式报错。
  • 静态资源响应里带 Set-Cookie：很多 CDN 见到它就完全不缓存，命中率莫名归零。
  • Vary 带上 User-Agent：缓存键被打散成无数份，等于关掉了 CDN。
  • 按请求头返回不同图片格式却没把格式纳入缓存键：会把 AVIF 发给不支持的客户端，表现为部分用户图裂。
  • 以为 HTTP/2 消除了队头阻塞：它只是把阻塞从 HTTP 层移到 TCP 层，真正解决的是 HTTP/3。
  • 上了 HTTP/2 还保留域名分片和大文件合并：这两个曾经的优化在多路复用下变成了反模式。
  • 还在研究服务器推送：它已经被移除，正确替代是 103 提前提示。
  • 服务端先刷 head 但链路上有缓冲：代理响应缓冲、压缩缓冲区、模板一次性渲染，任一处攒包，流式收益全部归零。
  • 把脚本放 body 末尾当成 defer：放末尾放弃了解析期间并行下载的时间，而 defer 两者都有。
  • 预加载字体忘了跨域属性：属性不匹配会导致下载两份，预加载那份完全浪费。
  • 给首屏主图加懒加载：它会被排到最后下载，直接拖垮最大内容绘制。
  • 把 preconnect 撒在所有第三方域名上：每个都要付握手与连接开销，用不到就是净损失。
  • 把接口慢当成交互指标差：交互指标衡量的是输入到下一次绘制，只要立刻给出加载态它就是短的，混淆两者会让优化方向整体跑偏。
