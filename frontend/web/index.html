Web 技术：从敲下回车到画面出现

我带新人时常问一个问题：你在浏览器敲完回车按 Enter，到页面出现，中间发生了什么？十个人里有八个答不全。这篇就把这条链路从头讲清楚——理解这条链路，性能优化才有方向，不然都是瞎调。

全链路一张图

DNS 解析 → TCP 连接 → TLS 握手 → HTTP 请求 → 服务端处理 → 返回 HTML → 浏览器解析渲染。每一步都可能是瓶颈，定位性能问题就是定位「时间花在哪一步」。

flowchart LR A[DNS 解析] --> B[TCP 三次握手] B --> C[TLS 握手 HTTPS] C --> D[HTTP 请求] D --> E[服务端处理] E --> F[返回 HTML] F --> G[浏览器解析渲染]

HTTP：从 1.1 到 3.0

别觉得 HTTP 是老东西，这两年变化很大。核心是「连接复用」的演进：

版本连接模型解决什么
HTTP/1.1串行，队头阻塞多资源要开多个连接
HTTP/2二进制分帧，多路复用一个连接并发多个请求
HTTP/3基于 QUIC（UDP）解决 TCP 队头阻塞，弱网更快

我对 HTTP/3 的体感是：移动弱网下差别明显。办公室 WiFi 下 HTTP/2 和 3 差不多，但地铁里刷网页，HTTP/3 的 QUIC 建立连接更快、丢包影响小。2026 年主流浏览器和 CDN 都默认支持了。

别迷信版本

上 HTTP/3 前先确认你的 CDN 和服务器支持。我见过团队把精力花在 HTTP/3 上，结果瓶颈根本在后端响应慢，换什么传输协议都没用。先量再优化。

浏览器渲染：像素是怎么画出来的

拿到 HTML 后，浏览器要把它变成屏幕上的像素。这条流水线是性能优化的核心：

flowchart LR A[HTML → DOM] --> B[CSS → CSSOM] B --> C[样式计算] C --> D[布局 Layout] D --> E[绘制 Paint] E --> F[合成 Composite GPU]

关键认知：不是每改一次样式都要跑完全部六步。这是性能优化的核心：

  • 改 width/top → 触发布局+绘制+合成，最贵；
  • 改 box-shadow/color → 只绘制+合成；
  • 改 transform/opacity → 只合成，最便宜。

所以做动画永远用 transform 和 opacity——浏览器直接在 GPU 合成层处理，不触发布局。我见过有人动画用 top，60 帧动画变成 30 帧还发热，就是没理解这条流水线。

缓存：CDN 和浏览器缓存

缓存是 Web 性能的大头。分两级：

层级控制方式适合缓存
CDN 边缘Cache-Control静态资源、HTML
浏览器强缓存max-age / immutable带哈希的 JS/CSS
协商缓存ETag / Last-Modified更新频繁的资源

我的原则：带内容哈希的 JS/CSS，强缓存一年；HTML 文件，协商缓存每次验证。这样资源更新时哈希变、文件名变，自动刷新；HTML 不缓存，确保用户拿到最新入口。我见过无数事故是「JS 缓存了一年，发版后用户还在跑旧代码」。

必坑

HTML 千万别强缓存！我早期图省事把 HTML 也设了 max-age=31536000，结果发版后老用户死活不更新，只能在 CDN 后台手动 purge。教训：HTML 永远 no-cache 或短缓存，带哈希的资源才长缓存。

Core Web Vitals：浏览器官方的性能指标

Google 定了三个指标，直接影响 SEO，必须达标：

指标含义良好值
LCP最大内容绘制< 2.5s
INP交互到下次绘制< 200ms
CLS累积布局偏移< 0.1

INP 是 2024 年 3 月正式替代 FID 的，反映页面响应性。CLS 那个「元素突然跳动」的烦人体验，根源是图片没设宽高。我给所有 img 都加 width/height 和 aspect-ratio，CLS 立刻从 0.3 降到 0.02。

第三方脚本：性能的隐形杀手

我踩过的

一个页面塞了六个第三方脚本：统计、客服、广告、AB 测试……首屏 JS 体积翻了三倍。后来全部加 async 或 defer，非关键的延迟加载，LCP 从 4s 降到 1.8s。第三方脚本一律异步，别让它们阻塞首屏。

  • async：下载完立即执行，不阻塞解析，但执行时机不定；
  • defer：HTML 解析完后按顺序执行，推荐用于需要 DOM 的脚本。

生产环境一个 Nginx 缓存头配置示例，直接能用：

# 带哈希的静态资源：强缓存一年
location ~* \.(js|css|png|jpg|woff2?)$ {
    add_header Cache-Control "public, max-age=31536000, immutable";
}

# HTML：每次协商，确保发版即时生效
location = /index.html {
    add_header Cache-Control "no-cache";
}

FAQ

Q：HTTPS 为什么更慢？
TLS 握手要多几个往返。但 HTTP/2 和 3 出来后，连接复用摊薄了这个成本。现代浏览器还有 TLS 会话恢复，第二次访问几乎无感。别为「快」用 HTTP，安全是底线。

Q：首屏白屏怎么定位？
用 Chrome DevTools 的 Performance 面板看时间线，定位是「网络慢」「JS 执行久」还是「渲染久」。不同瓶颈优化手段完全不同。别瞎猜。

Q：HTTP/3 一定要上吗？
CDN 支持就开着，成本为零。但别指望它解决一切——后端慢、JS 体积大，HTTP/3 救不了。

Q：2026 了，View Transitions API 是什么？
原生页面过渡动画，路由切换不用写 JS。浏览器直接提供 document.startViewTransition()，配合 CSS 伪元素做动画。SPA 和 MPA 都能用，省掉一堆过渡库。

小结

Web 性能不是玄学，是「量到时间花在哪，再针对性优化」。记住三件事：动画只动 transform/opacity、缓存分清强缓存和协商、第三方脚本一律异步。下一篇 WebAssembly，看怎么把 C/C++ 搬到浏览器里跑。
