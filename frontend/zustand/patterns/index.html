状态组织模式与常见陷阱

Zustand 的自由度是它的优点，也是项目变大后的风险来源：怎么切 store、方法放哪、异步怎么建模，库本身不给答案。这篇给出可执行的组织模式，并重点讲一个会造成用户数据串台的服务端渲染陷阱。上手与选择器写法见《Zustand 上手》，设计取舍见《Zustand 的设计》。

// src/stores/workspace.ts —— 切片模式：每个切片是一个函数，最后组合起来
import { create, type StateCreator } from 'zustand'

type DraftSlice = {
  title: string
  body: string
  setTitle: (t: string) => void
  setBody: (b: string) => void
}

type FilterSlice = {
  keyword: string
  tags: string[]
  setKeyword: (k: string) => void
  toggleTag: (t: string) => void
}

type Workspace = DraftSlice & FilterSlice

// 切片签名里把完整状态类型带上，这样切片内部也能读到别的切片
const createDraftSlice: StateCreator<Workspace, [], [], DraftSlice> = (set) => ({
  title: '',
  body: '',
  setTitle: (t) => set({ title: t }),
  setBody: (b) => set({ body: b }),
})

const createFilterSlice: StateCreator<Workspace, [], [], FilterSlice> = (set, get) => ({
  keyword: '',
  tags: [],
  setKeyword: (k) => set({ keyword: k }),
  toggleTag: (t) =>
    set((s) => ({
      tags: s.tags.includes(t) ? s.tags.filter((x) => x !== t) : [...s.tags, t],
    })),
})

export const useWorkspace = create<Workspace>()((...a) => ({
  ...createDraftSlice(...a),
  ...createFilterSlice(...a),
}))
组织方式适合优点代价
单个大 store状态字段少于十几个的小应用没有跨 store 协调问题领域边界消失，改任何东西都要通读全文件
按领域多 store中型以上应用，默认选择边界清晰，可独立测试与持久化跨领域流程需要外部函数来编排
单 store 加切片组合领域间联系紧密但文件太长文件可拆，共享状态仍然容易切片之间容易互相依赖，边界名存实亡
每个组件一个 store复杂表单或编辑器实例实例隔离，卸载即回收需要工厂函数与提供者，样板略多
按页面拆 store页面间状态毫无关联清理时机明确跨页共享的东西会被迫复制

方法放 store 还是放外部

这段逻辑放哪理由
只改一个 store 的状态store 的方法数据与操作在一起，调用方不用额外找函数
需要读写多个 store外部函数依赖关系显式，避免 store 之间互相导入形成环
多步流程带回滚外部函数流程编排不属于任何单一领域
纯计算的派生值选择器或外部函数存进状态就要负责在每个更新处同步，漏一处就自相矛盾
格式化与校验外部纯函数不依赖状态，便于单独测试
与接口交互并更新状态store 的方法结果要落到状态上，放外面会多一次转发
开销大的派生计算外部记忆化函数放选择器里每次渲染都算，放状态里又要同步
✅
一条简明规则

改状态的放 store，只读不改的放外部；跨 store 的一律放外部。按这条执行，store 之间就不会互相导入，也就不会出现循环依赖和「改一个 store 引发另一个 store 连锁更新」这类难以追踪的问题。

store 里做异步：把状态显式建模

// 异步写操作：加载中与错误都要是状态，而不是临时变量
import { create } from 'zustand'

type SubmitState = 'idle' | 'submitting' | 'success' | 'error'

type FormStore = {
  status: SubmitState
  error: string | null
  submittedAt: number | null
  submit: (payload: { email: string }) => Promise<void>
  reset: () => void
}

export const useForm = create<FormStore>((set, get) => ({
  status: 'idle',
  error: null,
  submittedAt: null,

  submit: async (payload) => {
    // 并发保护：正在提交时忽略后续调用，否则快速连点会发出多个请求
    if (get().status === 'submitting') return
    set({ status: 'submitting', error: null })
    try {
      const res = await fetch('/api/subscribe', {
        method: 'POST',
        headers: { 'content-type': 'application/json' },
        body: JSON.stringify(payload),
      })
      if (!res.ok) {
        // 区分业务错误与网络错误，界面上要给不同的提示
        const msg = res.status === 429 ? '操作过于频繁，请稍后再试' : '提交失败，请重试'
        set({ status: 'error', error: msg })
        return
      }
      set({ status: 'success', submittedAt: Date.now(), error: null })
    } catch {
      // 网络层异常也要落到状态上，不要让 Promise 静默失败
      set({ status: 'error', error: '网络异常，请检查连接' })
    }
  },

  reset: () => set({ status: 'idle', error: null }),
}))
建模方式问题推荐做法
只用一个布尔加载标记无法表达失败，重试逻辑没处放用有限的状态枚举
加载中与错误各一个布尔能同时为真，出现不可能的组合枚举天然互斥
错误只在控制台打印用户看不到任何反馈错误信息存进状态并渲染
不做并发保护快速连点发出多个请求，结果竞态提交中直接忽略，或取消先前请求
成功后不重置再次进入表单时仍显示上次的成功态提供重置方法并在合适时机调用
把读取数据也这样写缓存、失效、重取全要自己实现读取交给数据获取库

服务端渲染陷阱：单例会让用户数据串台

❌
这是安全问题，不只是渲染错乱

用模块顶层创建的 store 在服务端只有一份，而服务端进程被所有请求共用。甲用户请求期间写进 store 的数据，会被乙用户的请求读到并渲染进页面。本地开发时只有你一个人访问，这个问题完全看不出来，上线后才以「偶发看到别人的信息」的形式暴露。

sequenceDiagram participant U1 as 用户甲 participant U2 as 用户乙 participant P as 服务端进程 participant M as 模块级单例 store U1->>P: 请求页面 P->>M: 写入甲的用户信息 M-->>P: 渲染甲的页面 P-->>U1: 返回正确内容 U2->>P: 几乎同时请求页面 P->>M: 读取 store M-->>P: 返回的仍是甲写入的数据 P-->>U2: 乙看到了甲的信息 Note over M: 进程内只有一份实例
请求之间没有任何隔离 Note over P,M: 正确做法是每请求新建实例
通过提供者注入组件树 
// src/stores/createSessionStore.ts —— 工厂函数：每次调用都是独立实例
import { createStore } from 'zustand/vanilla'

export type SessionState = {
  userId: string | null
  cart: { sku: string; qty: number }[]
  addToCart: (sku: string) => void
}

// 注意这里没有在模块顶层创建实例，只导出创建函数
export const createSessionStore = (init?: Partial<SessionState>) =>
  createStore<SessionState>()((set) => ({
    userId: null,
    cart: [],
    ...init,                       // 服务端把该请求的初始数据传进来
    addToCart: (sku) =>
      set((s) => ({ cart: [...s.cart, { sku, qty: 1 }] })),
  }))
// src/stores/SessionProvider.tsx —— 通过上下文把实例注入组件树
'use client'
import { createContext, useContext, useRef, type ReactNode } from 'react'
import { useStore } from 'zustand'
import { createSessionStore, type SessionState } from './createSessionStore'

type Store = ReturnType<typeof createSessionStore>
const SessionContext = createContext<Store | null>(null)

export function SessionProvider({
  children,
  initial,
}: { children: ReactNode; initial?: Partial<SessionState> }) {
  // 用 ref 保证同一次挂载只创建一次；不要写在渲染体里直接创建
  const ref = useRef<Store>()
  if (!ref.current) ref.current = createSessionStore(initial)
  return <SessionContext.Provider value={ref.current}>{children}</SessionContext.Provider>
}

// 组件通过这个钩子取状态，仍然支持选择器，订阅粒度不受影响
export function useSession<T>(selector: (s: SessionState) => T): T {
  const store = useContext(SessionContext)
  if (!store) throw new Error('useSession 必须在 SessionProvider 内使用')
  return useStore(store, selector)
}
方案请求间是否隔离能否在组件外读写适用风险
模块级单例纯客户端渲染时可以，服务端渲染时不隔离能，直接导入纯客户端应用一旦引入服务端渲染就会串台
工厂加提供者隔离需要把实例传进去任何含服务端渲染的项目样板稍多，组件外访问要额外设计
只存放非用户相关状态无所谓能主题这类与身份无关的偏好边界容易被后来的人破坏
把用户数据全放数据获取库隔离由数据层负责按库的方式大多数含身份的数据仍需注意服务端缓存的作用域

还有一个常被忽略的点：即使你确定某个 store 只放主题之类的无害状态，这个边界也只存在于你的记忆里。半年后有人往里面加了当前用户字段，串台就发生了。只要项目有服务端渲染，就统一用工厂加提供者，不要给自己留判断的空间。

跨 store 的协调

多 store 之后必然出现「一个操作要动两个 store」的需求，例如退出登录要同时清掉会话、清掉草稿、并把界面偏好里的账号相关项复位。此时最容易犯的错是让一个 store 导入另一个 store 并在方法里调用它——这会形成隐式依赖，两边都改的时候没人说得清执行顺序，而且很容易在打包时构成循环引用。

正确做法是把编排放在外部函数里，让依赖关系写在同一个地方：这个函数按顺序调用各个 store 的重置方法，需要回滚时也只有它知道完整上下文。这样每个 store 仍然只对自己负责，跨领域的知识集中在一处，读代码的人一眼能看到这个操作到底影响了哪些状态。另一个好处是测试变简单：编排函数可以单独测，各 store 也可以单独测，不需要构造一整棵组件树。

持久化与测试

持久化的机制与版本迁移在《Zustand 上手》里给了完整配置，这里只强调两条与组织方式相关的结论：持久化的白名单要按字段写死，不要用排除法，否则将来新增敏感字段时会默认被存进去；令牌与身份凭据不进普通本地存储，它对同源的任何脚本都是可读的。

// 测试隔离：store 是模块级的，用例之间必须重置
import { beforeEach, expect, test, vi } from 'vitest'
import { useForm } from '@/stores/form'

// 把初始状态抓下来作为基准。注意方法也在状态对象里，
// 所以重置时用替换而不是只覆盖数据字段
const initial = useForm.getState()

beforeEach(() => {
  useForm.setState(initial, true)   // 第二个参数表示整体替换
  vi.restoreAllMocks()
})

test('重复提交只发出一个请求', async () => {
  const fetchMock = vi.fn().mockResolvedValue(new Response('{}', { status: 200 }))
  vi.stubGlobal('fetch', fetchMock)

  // 不等待第一次完成就再调一次，验证并发保护生效
  const p1 = useForm.getState().submit({ email: 'a@b.com' })
  const p2 = useForm.getState().submit({ email: 'a@b.com' })
  await Promise.all([p1, p2])

  expect(fetchMock).toHaveBeenCalledTimes(1)
  expect(useForm.getState().status).toBe('success')
})
测试问题成因处理
用例之间互相影响store 是模块级共享的每个用例前整体替换回初始状态
断言到的是中间态没等异步方法完成等待返回的 Promise，或等到状态变为终态
持久化污染测试环境中间件读写了真实存储测试环境替换存储实现，或关闭该中间件
重置后方法丢失用整体替换却只传了数据字段把完整初始状态含方法一起保存下来
订阅在用例间累积组件外订阅没有取消在清理钩子里调用取消函数

什么时候该换更重的方案

换库的成本不在换库本身，而在重新梳理状态归属，所以判断要基于真实痛点而不是风格偏好。下面这张表给出信号与对应动作；注意大多数情况下正确答案是「不换，先把状态归属理清楚」。

信号缺的是什么动作成本
出问题时无法回溯状态怎么变成这样的变更的可追溯性换成动作模型的方案，或自建变更日志中间件中，日志中间件成本远低于换库
一次操作牵动多模块的长流程与回滚副作用编排机制引入状态机或专门的副作用库中到高
非法状态组合反复出现状态转移的强制约束用状态机描述转移，store 只存当前状态与上下文中，但收益明确
同一份状态要在多个独立应用间共享跨应用的状态层抽成独立服务或走存储与消息通道高
团队各写各的，结构越来越乱约定与执行手段先定切片划分与命名规范，用 lint 与 review 执行低，优先做这个
只是觉得写法太自由没缺什么用类型收紧接口，不必换库很低
❌
最容易踩的坑
  • 服务端渲染项目用模块级单例：状态跨请求共享导致用户数据串台，这是数据泄露而不是渲染问题，必须改成工厂加提供者。
  • 在提供者的渲染体里直接创建 store：每次重渲染都新建实例，状态会莫名丢失，要用引用持有。
  • store 之间互相导入：形成循环依赖，还会出现改一个引发另一个连锁更新的追踪难题，跨 store 逻辑一律放外部函数。
  • 把派生值存进状态：每个相关更新处都要同步它，漏一处就得到自相矛盾的状态。
  • 只用一个布尔表示加载：无法表达失败与重试，界面上没有地方展示错误。
  • 加载中与错误各用一个布尔：两者可以同时为真，产生不可能出现的状态组合。
  • 异步操作不做并发保护：快速连点发出多个请求，结果按返回顺序覆盖，界面与服务端不一致。
  • 捕获异常后只打日志：用户看到界面卡在加载中，没有任何反馈也无法重试。
  • 把数据读取也塞进 store：缓存、去重、失效重取全要自己写，很快就写不动了。
  • 持久化用排除法配置白名单：将来新增的敏感字段会默认被存进本地存储。
  • 令牌写进本地存储：同源的任何脚本都能读取，凭据等于公开。
  • 测试不重置 store：用例顺序一变结果就变，排查时极难定位。
  • 重置时漏掉方法：用整体替换只传数据字段，方法全部消失，后续用例报错在无关的地方。
  • 为了减少样板把所有东西塞一个 store：领域边界消失，任何改动都要通读整个文件并担心影响面。
