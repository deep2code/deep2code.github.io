Zustand 上手：store、selector 与订阅粒度

🏷️ Zustand 入门

Zustand 的接口很小，坑却集中在两处：更新的合并语义和选择器的比较方式。这两点理解错了，表现分别是「同级字段莫名消失」和「组件疯狂重渲染」。这篇按上手顺序把它们讲透，并给出中间件的组合方式。设计取舍见《Zustand 的设计》，组织模式与服务端渲染陷阱见《状态组织模式与常见陷阱》。

建一个 store

// src/stores/editor.ts
import { create } from 'zustand'

type Filters = { keyword: string; tags: string[]; onlyMine: boolean }

type EditorState = {
  title: string
  filters: Filters
  savedAt: number | null
  setTitle: (t: string) => void
  setKeyword: (k: string) => void
  toggleTag: (tag: string) => void
  resetFilters: () => void
  save: () => Promise<void>
}

// 初始值单独抽出来，重置与测试都要用到它
const initialFilters: Filters = { keyword: '', tags: [], onlyMine: false }

export const useEditor = create<EditorState>((set, get) => ({
  title: '',
  filters: initialFilters,
  savedAt: null,

  setTitle: (t) => set({ title: t }),

  // 嵌套字段：合并是浅层的，所以必须把上一层完整展开
  setKeyword: (k) => set((s) => ({ filters: { ...s.filters, keyword: k } })),

  toggleTag: (tag) =>
    set((s) => ({
      filters: {
        ...s.filters,
        tags: s.filters.tags.includes(tag)
          ? s.filters.tags.filter((t) => t !== tag)
          : [...s.filters.tags, tag],
      },
    })),

  resetFilters: () => set({ filters: initialFilters }),

  // 方法里可以直接写异步；用 get 读当前值，不要依赖外部闭包
  save: async () => {
    const { title, filters } = get()
    const res = await fetch('/api/draft', {
      method: 'POST',
      headers: { 'content-type': 'application/json' },
      body: JSON.stringify({ title, filters }),
    })
    // 失败不要静默：要么抛出让调用方处理，要么在状态里留下错误标记
    if (!res.ok) throw new Error(`保存失败：${res.status}`)
    set({ savedAt: Date.now() })
  },
}))

这段定义里有四个可以直接照搬的决策。初始值单独抽出来：重置功能与单元测试都需要一份干净的初值，写在字面量里就只能复制一遍。方法与状态放在同一个对象里：调用方拿到的就是「数据加操作」，不需要额外去某个文件找对应的处理函数。异步直接写在方法里：不需要任何中间件承载副作用，但要自己决定失败怎么表达——这里选择抛出异常交给调用方，另一种做法是在状态里放错误字段，两者不要混用，否则调用方不知道该看哪里。方法内部用 get 读当前值：不要捕获模块作用域里的变量，那些值在异步等待期间可能已经过期。

更新的合并语义

写法当前状态结果是否符合预期
传顶层字段对象title 与 filters 并存只替换 title，filters 不动是，顶层合并按字段生效
传嵌套对象但不展开filters 含三个字段filters 被整体替换，另两个字段丢失否，这是最常见的数据丢失原因
展开上一层后再改同上只有目标字段变化是
就地修改后再传同一对象任意引用未变，订阅者可能不更新否，必须产生新引用
传函数式更新任意基于最新状态计算是，依赖当前值时的唯一正确写法
显式要求整体替换任意不做合并，未提及的字段全部消失仅在重置整个 store 时使用
场景错误写法的后果正确写法
计数器自增同批次调用两次只生效一次函数式更新，用参数里的最新值
数组追加基于过期数组计算，丢项函数式更新并展开成新数组
开关取反快速连点时状态错乱函数式更新
依赖另一字段做校验闭包里的值可能已过期在方法里用 get 读当前状态

import { useShallow } from 'zustand/react/shallow'
import { useEditor } from '@/stores/editor'

// 坏例子一：返回对象字面量。每次执行都是新引用，比较永远不等，
// 组件重渲染 -> 再执行选择器 -> 又是新对象 -> 无限循环
function BadHeader() {
  const { title, savedAt } = useEditor((s) => ({ title: s.title, savedAt: s.savedAt }))
  return null
}

// 坏例子二：在选择器里做过滤，每次返回新数组，同样的问题
function BadTagList() {
  const tags = useEditor((s) => s.filters.tags.filter((t) => t !== 'draft'))
  return null
}

// 修法一（首选）：拆成多个选择器，各返回原始值，按值比较
function GoodHeader() {
  const title = useEditor((s) => s.title)
  const savedAt = useEditor((s) => s.savedAt)
  return null
}

// 修法二：确实要一次取多个字段时，用浅比较让比较落到字段级别
function GoodToolbar() {
  const { keyword, onlyMine } = useEditor(
    useShallow((s) => ({ keyword: s.filters.keyword, onlyMine: s.filters.onlyMine })),
  )
  return null
}

// 修法三：派生逻辑移出订阅。选择器只取原始数据，派生在组件内做，
// 这样比较仍然是按值进行的，也不会每次产生新数组
function GoodTagList() {
  const tags = useEditor((s) => s.filters.tags)
  const visible = tags.filter((t) => t !== 'draft')
  return null
}

// 只需要方法时单独取，方法引用在 store 生命周期内稳定，不会触发多余渲染
function SaveButton() {
  const save = useEditor((s) => s.save)
  return null
}
写法比较方式表现结论
返回单个原始值按值只在该值变化时渲染最优，优先用
返回对象字面量，无包装按引用每次都判定为变化，无限重渲染禁止
返回对象字面量，加浅比较逐字段按值字段都没变则不渲染可用，适合一次取多个字段
选择器里过滤或映射按引用每次新数组，同样重渲染改成取原始数据后在外面派生
不传选择器取整个状态整个状态对象任何字段变化都渲染只在极少数场景可接受
只取方法按引用，但引用稳定不会因状态变化而渲染推荐，事件处理器这样取
⚠️
浅比较不是万能的

浅比较只比较对象的第一层。如果你返回的对象里某个字段本身是每次新建的数组或对象，浅比较照样判定为变化。真正的解法是让选择器返回的每一项都是稳定引用或原始值，而不是靠比较函数去兜底。

订阅粒度为什么值得花心思

选择器写得对不对，决定的不是代码好不好看，而是状态变更的影响半径。举个具体场景：一个后台页面顶部有搜索框、左侧有筛选树、右侧是一张两百行的表格，三者都从同一个 store 取状态。如果表格的选择器顺手取了整个筛选对象，那么用户在搜索框里每敲一个字，表格都会重渲染一次——两百行乘以每秒若干次按键，主线程立刻被占满，用户的直观感受是「输入卡顿」。

这类问题的难点在于定位：症状出现在表格上，原因在搜索框的按键上，而代码里两者毫无关联。排查顺序是先确认「哪个组件在重渲染」，再看它的选择器取了什么，最后反查是谁在改那部分状态。把选择器收窄到真正用到的字段，通常一行改动就能解决。反过来说，如果一开始就遵守「只取用到的字段、返回原始值」这两条，这类问题根本不会出现。

组件外订阅

store 不依赖组件树，所以可以在任意模块里读写与监听。订阅方法返回一个取消函数，回调在每次状态更新时执行——注意是每次，不是「你关心的字段变化时」，所以要自己做比较。

import { useEditor } from '@/stores/editor'

// 用途一：把状态同步到别处。自己比较关心的字段，避免每次更新都做无用工作
let lastKeyword = useEditor.getState().filters.keyword
const unsubscribe = useEditor.subscribe((state) => {
  const next = state.filters.keyword
  if (next === lastKeyword) return       // 不比较就会在任何字段变化时都执行一遍
  lastKeyword = next
  // 这里做真正的副作用：上报、同步地址栏、通知另一个系统
  reportSearch(next)
})

// 用途二：在非组件代码里读写，例如接口层的统一错误处理
export async function request(input: RequestInfo) {
  const res = await fetch(input)
  if (res.status === 401) {
    // 直接调用 store 的方法，不需要任何组件上下文
    useEditor.getState().resetFilters()
  }
  return res
}

// 记得在合适的时机取消订阅：模块热替换、组件卸载、或应用关闭前
// 长期存活的订阅会持有闭包引用，阻止相关对象被回收
unsubscribe()

import { create } from 'zustand'
import { persist, createJSONStorage, devtools } from 'zustand/middleware'

type Prefs = { theme: 'light' | 'dark'; density: 'cozy' | 'compact'; token?: string }

export const usePrefs = create<Prefs & { setTheme: (t: Prefs['theme']) => void }>()(
  // 调试在最外层：它能看到持久化还原等所有变更
  devtools(
    persist(
      (set) => ({
        theme: 'light',
        density: 'cozy',
        setTheme: (t) => set({ theme: t }),
      }),
      {
        name: 'prefs',
        storage: createJSONStorage(() => localStorage),
        // 白名单：只持久化该存的字段。令牌之类的凭据绝不能进来
        partialize: (s) => ({ theme: s.theme, density: s.density }),
        // 版本与迁移：结构变更后旧数据要能升级，否则用户会读到不兼容的状态
        version: 2,
        migrate: (persisted: any, from) => {
          if (from < 2) {
            // 一版里 density 叫 compactMode 且是布尔值
            return {
              theme: persisted.theme ?? 'light',
              density: persisted.compactMode ? 'compact' : 'cozy',
            }
          }
          return persisted
        },
        // 还原完成的回调：用它驱动界面从骨架切到真实内容
        onRehydrateStorage: () => (state, error) => {
          if (error) console.warn('偏好还原失败，使用默认值', error)
        },
      },
    ),
    { name: 'prefs-store', enabled: import.meta.env.DEV },
  ),
)

关于是否引入中间件，有一条判断值得记住：持久化和调试是在解决真实问题，不可变辅助往往是在掩盖设计问题。当你发现必须靠它才能写出可读的更新代码时，先问一句状态为什么嵌套了四层——把结构拍平、或者按领域拆成多个 store，通常比加一层中间件更划算。至于持久化，它的复杂度全部集中在版本迁移上：只要你的状态结构还会演进，版本号和迁移函数就必须从第一天就写上，事后补是补不回来的，因为线上已经存在一批无法识别版本的旧数据。

排查对照

现象原因确认方式修法
组件不停重渲染直到卡死选择器返回了新建对象或数组把选择器改成只取一个原始值，症状消失拆选择器，或加浅比较
改了嵌套字段，同级其他字段消失误以为是深合并打印更新后的状态，看兄弟字段是否还在展开上一层再改
连续两次更新只生效一次用了对象式更新，基于过期闭包值快速连续触发两次，看结果是否只加一改成函数式更新
界面没反应但状态确实变了就地修改对象导致引用未变比较更新前后的引用是否相同产生新对象或新数组
刷新后短暂显示默认值持久化还原在首帧之后观察是否总在首帧后跳变还原完成前渲染骨架
升级后读到不兼容的旧数据没有版本号与迁移函数清空存储后问题消失即可确认加版本与迁移，并保留兜底默认值
组件外的订阅回调执行得异常频繁回调在任何字段变化时都会触发在回调里打印触发次数自己比较关心的字段，或用选择器增强
❌
最容易踩的坑
  • 选择器返回对象字面量：每次新引用导致无限重渲染，这是新手第一大坑，优先拆成多个选择器。
  • 在选择器里做过滤或映射：同样每次产生新数组，应该取原始数据后在组件里派生。
  • 以为更新是深合并：嵌套对象被整体替换，同级字段静默丢失，数据问题往往很晚才被发现。
  • 依赖当前值却传对象：同批次连续更新丢失，快速连点或循环调用时必然复现。
  • 就地修改状态里的数组：引用没变，订阅者不更新，看起来像「状态没生效」。
  • 不传选择器直接取整个状态：退化成任何变化都重渲染，等于放弃了订阅粒度。
  • 持久化存了敏感字段：令牌、身份证号、银行卡号进了本地存储，任何脚本都能读取。
  • 持久化不加版本与迁移：状态结构调整后老用户读到不兼容数据，表现为界面错乱或直接报错。
  • 还原完成前就渲染依赖状态的界面：出现闪烁，服务端渲染场景下还会导致标记不一致。
  • 生产环境启用调试中间件：内部状态结构与字段名对任何人可见。
  • 中间件包裹顺序写反：调试面板漏掉变更，或持久化存下了中间形态的数据。
  • 用不可变辅助掩盖过深的结构：写法变短了但状态设计问题仍在，后续选择器与订阅都会更难写。
  • 订阅后不取消：闭包长期被持有，相关对象无法回收，热替换场景下还会叠加多个回调。
