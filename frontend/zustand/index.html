Zustand 的设计：为什么它比 Redux 轻

🏷️ Zustand

「Zustand 比 Redux 轻」这句话如果只停在感觉上没有价值。它的轻可以拆成三件可验证的事：概念数量更少、订阅粒度更细、与组件树解耦。这篇先给一份「该用它还是该用别的」的现场自查与最小可用写法，再讲这三点的机制，最后把状态归属与选型判断收成矩阵。

状态管理的整体选型脉络见站内《前端框架》一文，这里只聚焦 Zustand 的设计取舍。上手与选择器写法见《Zustand 上手》，组织模式与陷阱见《状态组织模式与常见陷阱》。

💡
这篇怎么读
  • ① 用法：七条「这份状态该不该进全局 store、该不该用 Zustand」的现场自查，一个最小可用 store（选择器怎么写、组件外怎么读写），以及常见任务与 API 速查表。
  • ② 原理：动作与归约器模型多出来的那层间接换到了什么、两种 store 的更新链路差别、订阅比较为什么是引用相等（这是无限重渲染的成因）、以及「与组件树解耦」在代码上意味着什么。
  • ③ 场景：状态归属决策矩阵（哪些该进 store、哪些该去数据获取库或地址栏）、与 Redux Toolkit、Jotai、Valtio、Context 的多维对照，以及该换更重方案的六个信号。

① 用法 · 先做三分钟自查，再写第一个 store

选型上真正会返工的决定只有两类：这份状态该不该是全局的，以及你要不要那套可回放的变更记录。下表每行都是能当场执行的判断，不需要先理解任何机制。

要判断什么怎么当场判断答案为是答案为否
这份状态真的需要全局吗数一下有几个不相邻的组件要读或写它两个以上：进 store只有一个：留在组件内部，不要提升
事实来源在服务端吗问一句「我不操作页面，这份数据会不会被别人改掉」会：交给数据获取库，别进 store不会：是客户端状态，可以进 store
需要时间旅行调试与操作审计吗问「线上出故障时，要不要回放用户的操作序列来定位」要：选动作模型的方案，或自建变更日志中间件不要：Zustand 够用，这是它省掉的那层
状态转移有合法性约束吗试着列出「绝不该同时出现」的状态组合能列出来：用状态机描述转移，store 只存当前状态列不出来：store 里直接写方法改
项目有服务端渲染吗看页面 HTML 是不是服务端产出的有：必须工厂函数加提供者，模块级单例会跨请求串用户数据没有：模块级单例最省事
刷新后要保留吗问「刷新丢了会不会有人投诉」会：加持久化中间件并按字段写白名单不会：不要引入持久化，它的复杂度全在版本迁移上
要在多个独立应用间共享吗看这份状态是否跨越了部署单元是：超出单应用范围，走存储或消息通道否：一个 store 就够

自查通过之后，一个 store 的全部要素就是下面这段：状态、改状态的方法、导出。注释写的是「为什么要这行」，机制解释都在原理层。

// 安装：npm i zustand
// src/stores/counter.ts
import { create } from 'zustand'

type Counter = {
  count: number
  inc: (n?: number) => void
  reset: () => void
}

export const useCounter = create<Counter>((set) => ({
  count: 0,
  // 依赖上一个值时用函数式更新：同一批里连调两次才不会都基于同一个旧值
  inc: (n = 1) => set((s) => ({ count: s.count + n })),
  // 不依赖当前值时可以直接传对象；注意这是浅合并，不是替换
  reset: () => set({ count: 0 }),
}))

// 组件外读写：不需要任何上下文，接口层、事件监听、测试里都能直接调
export const bumpTen = () => useCounter.getState().inc(10)
// src/components/Counter.tsx
import { useCounter } from '@/stores/counter'

function Badge() {
  // 选择器只取真正用到的字段，并且返回原始值：比较按值进行，最安全
  const count = useCounter((s) => s.count)
  return <span>{count}</span>
}

function IncButton() {
  // 方法单独取：它的引用在 store 生命周期内不变，取它不会带来额外渲染
  const inc = useCounter((s) => s.inc)
  return <button onClick={() => inc()}>加一</button>
}

// 不要这样写：返回对象字面量 = 每次新引用 = 无限重渲染，原因见原理层
// const { count, inc } = useCounter((s) => ({ count: s.count, inc: s.inc }))

上面这些默认值——为什么比较是按引用做的、为什么合并是浅的、为什么方法引用稳定——下面逐节展开。

② 原理 · 概念数量：三段式的间接成本

搞清这一节能回答一个具体问题：那层被省掉的间接，原本是在为谁服务。

要做的事动作与归约器模型Zustand差异的本质
定义一次状态变更定义动作类型、创建动作、在归约器里处理在 store 里写一个方法直接改是否需要把「意图」与「执行」拆成两处
触发变更派发动作，由归约器匹配调用方法是否需要一层运行时的分发机制
读取状态通过选择器钩子读取通过选择器读取基本相同
处理异步需要中间件或工具封装的异步动作方法里直接写异步是否需要额外机制承载副作用
组件外读写需要拿到 store 实例并派发直接调用导出的读写方法是否与组件树耦合
拆分模块归约器组合，结构由工具约定切片函数组合，结构由团队约定约束强度与自由度的取舍
调试可追溯性强：每次变更都有类型与载荷需要接入调试中间件并自己命名这是重方案的真实优势

注意最后一行。动作模型的间接层不是白加的：它换来了可追溯性——每次变更都有名字和载荷，于是可以录制、回放、审计。如果你的业务确实需要这个，那个「重」是在买东西，不是在浪费。轻方案的取舍是放弃这份规范，换取更短的代码路径。这也是用法层第三条自查的全部依据。

② 原理 · 两种 store 结构

搞清这一节能解释一个现象：为什么 Zustand 通常不需要额外的记忆化层，而动作模型里选择器旁边常常跟着一个记忆化工具。

② 原理 · 订阅粒度：一次更新之后发生了什么

搞清这一节能解决两个最高频的现象：「组件疯狂重渲染直到卡死」和「明明改了状态界面却没反应」。

sequenceDiagram participant C as 组件或普通函数 participant S as store participant L as 订阅者列表 participant A as 组件甲 取用 count participant B as 组件乙 取用 theme C->>S: 调用 increment S->>S: 计算下一个状态并与旧状态浅合并 S->>L: 通知所有订阅者 L->>A: 执行甲的选择器 A-->>L: count 由 1 变成 2 结果不同 L->>B: 执行乙的选择器 B-->>L: theme 未变 结果相同 Note over A: 甲重渲染 Note over B: 乙不重渲染 即使状态对象是新的 Note over L: 比较方式默认是引用相等
所以选择器返回新建对象会永远判定为变化

最后那条注解是最高频的坑的成因：比较是按引用做的。选择器如果每次都返回新建的对象或数组，比较永远不相等，组件就会不停重渲染。反过来，如果你就地修改了状态里的数组再传回去，引用没变，订阅者会认为什么都没发生——这就是「状态改了界面不动」。两个症状同源，修法在《Zustand 上手》里给出完整的坏例子与正确写法。

// src/stores/ui.ts —— 一个 store 的全部要素：状态、方法、导出
import { create } from 'zustand'

type UIState = {
  sidebarOpen: boolean
  theme: 'light' | 'dark'
  toasts: { id: string; text: string }[]
  toggleSidebar: () => void
  setTheme: (t: UIState['theme']) => void
  pushToast: (text: string) => void
  dismissToast: (id: string) => void
}

// create 接收一个函数，它返回状态与修改状态的方法，这就是 store 的全部
export const useUI = create<UIState>((set, get) => ({
  sidebarOpen: false,
  theme: 'light',
  toasts: [],

  // 依赖当前值时用函数式更新，避免拿到过期的闭包值
  toggleSidebar: () => set((s) => ({ sidebarOpen: !s.sidebarOpen })),

  setTheme: (t) => set({ theme: t }),

  pushToast: (text) => {
    const id = crypto.randomUUID()
    set((s) => ({ toasts: [...s.toasts, { id, text }] }))
    // 方法里可以直接写异步与副作用，不需要额外机制
    setTimeout(() => get().dismissToast(id), 4000)
  },

  dismissToast: (id) =>
    set((s) => ({ toasts: s.toasts.filter((t) => t.id !== id) })),
}))

// 组件外也能读写：事件回调、工具函数、测试里都可以直接用
export const notify = (text: string) => useUI.getState().pushToast(text)

这段代码说明了「与组件树解耦」的实际价值：最后一行的通知函数可以在任何地方调用——接口层的错误处理、键盘事件监听、甚至另一个库的回调里，都不需要拿到组件上下文。这在上层框架的状态方案里通常要绕一圈才能做到。代价在服务端渲染时才显现：模块顶层这一句意味着进程内只有一份实例，细节见组织模式那篇。

③ 场景 · 状态归属：什么该进全局 store

大多数「状态管理很复杂」的抱怨，根因不是库选错了，而是把服务端数据当客户端状态在管。服务端数据需要的是一整套同步策略：缓存有效期、重复请求合并、聚焦时刷新、失败重试、分页与预取、写操作后的失效重取。把它塞进全局 store，意味着这些你全都要自己实现一遍，而且状态会从「远端事实的一份副本」退化成「任何代码都能改的本地数据」。

状态例子归属理由放错的后果
商品列表、用户资料、订单详情数据获取库事实在服务端，需要缓存与失效策略自己实现同步逻辑，界面与服务端不一致
侧边栏展开、弹层开关、当前标签页全局 store 或组件内部纯界面状态，跨组件读写时才提升放进上下文导致大范围重渲染
主题、语言、密度偏好全局 store 加持久化跨页共享且需要刷新后保留每个页面各存一份，切换时不一致
购物车（未登录阶段）全局 store 加持久化客户端事实，登录后再与服务端合并只放内存里，刷新即丢
多步表单草稿全局 store，谨慎持久化跨路由共享，但可能含敏感字段持久化了身份证号或银行卡号
输入框当前值组件内部只有自己用，高频变化提升到全局，每次按键触发全局通知
列表筛选与分页参数地址栏优先可分享、可回退、刷新后仍在只放 store，刷新丢失且无法分享链接
登录令牌安全存储，不进普通持久化敏感凭据写进本地存储，任何脚本都能读取

这张表照着执行，一个中型应用的全局 store 通常只剩下十几个字段。剩下的复杂度去了该去的地方：服务端数据交给专门的数据层，界面局部状态留在组件里，可分享的视图参数落在地址栏。

// 正确的分工：服务端数据走数据获取库，客户端状态走 store
import { useQuery } from '@tanstack/react-query'
import { useUI } from '@/stores/ui'

export function ProductList({ category }: { category: string }) {
  // 服务端事实：缓存、重试、失效重取都由数据层负责，不要抄进 store
  const { data, isPending, error } = useQuery({
    queryKey: ['products', category],
    queryFn: () => fetch(`/api/products?c=${category}`).then((r) => r.json()),
    staleTime: 60_000,          // 一分钟内复用缓存，避免重复请求
  })

  // 客户端状态：只订阅用到的字段，返回原始值所以不会引发多余渲染
  const density = useUI((s) => s.density)
  const pushToast = useUI((s) => s.pushToast)

  if (isPending) return <Skeleton rows={8} />
  // 错误处理留在数据层的返回值里，不要把 error 也存进全局 store
  if (error) return <Retry onRetry={() => pushToast('正在重试')} />

  return <Grid items={data} density={density} />
}

// 反例：把列表数据 loading 与 error 全塞进全局 store，
// 于是缓存、并发请求去重、失效重取都要自己写，
// 并且任何模块都能直接改 products，界面与服务端很快就不一致了

⚠️
Context 不是状态管理方案

用上下文放高频变化的状态，问题在于上下文的消费者无法只订阅其中一个字段：值一变，所有消费者全部重渲染。它适合放低频变化的东西——主题、当前用户、国际化字典、依赖注入的实例。把表单状态或列表筛选条件放进去，就会得到一个到处重渲染而且很难定位原因的应用。

团队各写各的，结构失控自由度的代价开始显现先定切片与命名约定，见组织模式那篇
只是觉得写法太随意不构成技术理由用类型与约定收紧，不必换库

不适用边界：需要审计与回放、需要强制状态转移、或状态要跨应用共享时，Zustand 省掉的那层恰好是你需要的，别用约定去补。反过来，如果全局状态只是若干界面开关与用户偏好，它一直够用。

💡
一句话结论

Zustand 的轻来自去掉了一层间接：没有动作与归约器的分离，没有派发机制，store 也不依赖组件树。它拿掉的那层恰好是重方案用来换取可追溯性的部分，所以判断很简单——你需要审计与回放吗？需要就付那份成本，不需要就别付。

这条路径上，本篇负责判断「要不要用、什么该进 store」，下一篇进入具体写法：store 怎么建、选择器怎么写才不会无限重渲染、中间件怎么叠。

最容易踩的坑

❌
最容易踩的坑
  • 把服务端数据放进全局 store：你会被迫自己实现缓存、重试、失效重取，而且很快出现界面与服务端不一致。
  • 选择器返回对象字面量：每次返回新引用，比较永远不相等，组件无限重渲染。
  • 不写选择器直接取整个状态：任何字段变化都会触发重渲染，订阅粒度的优势全部丢掉。
  • 用上下文承载高频状态：消费者无法只订阅一个字段，值一变全体重渲染。
  • 依赖当前值却用对象式更新：并发更新时会基于过期值计算，应该用函数式更新拿到最新状态。
  • 以为更新是深合并：合并是浅层的，嵌套对象必须自己展开，否则同级其他字段会被整体替换掉。
  • 就地修改状态里的数组再传回去：引用没变，订阅者判定为无变化，表现成「状态改了界面不动」。
  • 把筛选分页只放在 store 里：刷新丢失且链接无法分享，这类状态应该优先放地址栏。
  • 把令牌写进普通持久化存储：任何脚本都能读到，等于把凭据公开。
  • 生产环境开着调试中间件：内部状态结构与业务字段会暴露给任何打开控制台的人。
  • 为了少写代码把所有状态塞一个 store：领域边界消失后，任何改动都要通读整个文件。
  • 模块级单例配服务端渲染：状态会跨请求共享导致用户数据串台，这是安全问题，必须每请求新建。
  • 用它替代状态机：方法可以把状态改成任何组合，非法状态照样能出现，有严格转移要求时要用状态机。
