Zustand 的设计：为什么它比 Redux 轻

🏷️ Zustand

「Zustand 比 Redux 轻」这句话如果只停在感觉上没有价值。它的轻可以拆成三件可验证的事：概念数量更少、订阅粒度更细、与组件树解耦。这篇讲清这三点的机制，给出与同类方案的对照，并交出一条能消灭大半「状态管理很复杂」问题的判断标准。

状态管理的整体选型脉络见站内《前端框架》一文，这里只聚焦 Zustand 的设计取舍。上手与选择器写法见《Zustand 上手》，组织模式与陷阱见《状态组织模式与常见陷阱》。

概念数量：三段式的间接成本

要做的事动作与归约器模型Zustand差异的本质
定义一次状态变更定义动作类型、创建动作、在归约器里处理在 store 里写一个方法直接改是否需要把「意图」与「执行」拆成两处
触发变更派发动作，由归约器匹配调用方法是否需要一层运行时的分发机制
读取状态通过选择器钩子读取通过选择器读取基本相同
处理异步需要中间件或工具封装的异步动作方法里直接写异步是否需要额外机制承载副作用
组件外读写需要拿到 store 实例并派发直接调用导出的读写方法是否与组件树耦合
拆分模块归约器组合，结构由工具约定切片函数组合，结构由团队约定约束强度与自由度的取舍
调试可追溯性强：每次变更都有类型与载荷需要接入调试中间件并自己命名这是重方案的真实优势

注意最后一行。动作模型的间接层不是白加的：它换来了可追溯性——每次变更都有名字和载荷，于是可以录制、回放、审计。如果你的业务确实需要这个，那个「重」是在买东西，不是在浪费。轻方案的取舍是放弃这份规范，换取更短的代码路径。

两张图的差别集中在最后两步：一边是「状态树整体更新，再由订阅者自己裁剪」，另一边是「更新后逐个订阅者比较选择器结果」。后者把裁剪内建进了订阅机制，这就是为什么 Zustand 通常不需要额外的记忆化层。

订阅粒度：一次更新之后发生了什么

sequenceDiagram participant C as 组件或普通函数 participant S as store participant L as 订阅者列表 participant A as 组件甲 取用 count participant B as 组件乙 取用 theme C->>S: 调用 increment S->>S: 计算下一个状态并与旧状态浅合并 S->>L: 通知所有订阅者 L->>A: 执行甲的选择器 A-->>L: count 由 1 变成 2 结果不同 L->>B: 执行乙的选择器 B-->>L: theme 未变 结果相同 Note over A: 甲重渲染 Note over B: 乙不重渲染 即使状态对象是新的 Note over L: 比较方式默认是引用相等
所以选择器返回新建对象会永远判定为变化

最后那条注解是最高频的坑的成因：比较是按引用做的。选择器如果每次都返回新建的对象或数组，比较永远不相等，组件就会不停重渲染。修法在《Zustand 上手》里给出完整的坏例子与正确写法。

// src/stores/ui.ts —— 一个 store 的全部要素：状态、方法、导出
import { create } from 'zustand'

type UIState = {
  sidebarOpen: boolean
  theme: 'light' | 'dark'
  toasts: { id: string; text: string }[]
  toggleSidebar: () => void
  setTheme: (t: UIState['theme']) => void
  pushToast: (text: string) => void
  dismissToast: (id: string) => void
}

// create 接收一个函数，它返回状态与修改状态的方法，这就是 store 的全部
export const useUI = create<UIState>((set, get) => ({
  sidebarOpen: false,
  theme: 'light',
  toasts: [],

  // 依赖当前值时用函数式更新，避免拿到过期的闭包值
  toggleSidebar: () => set((s) => ({ sidebarOpen: !s.sidebarOpen })),

  setTheme: (t) => set({ theme: t }),

  pushToast: (text) => {
    const id = crypto.randomUUID()
    set((s) => ({ toasts: [...s.toasts, { id, text }] }))
    // 方法里可以直接写异步与副作用，不需要额外机制
    setTimeout(() => get().dismissToast(id), 4000)
  },

  dismissToast: (id) =>
    set((s) => ({ toasts: s.toasts.filter((t) => t.id !== id) })),
}))

// 组件外也能读写：事件回调、工具函数、测试里都可以直接用
export const notify = (text: string) => useUI.getState().pushToast(text)

这段代码说明了「与组件树解耦」的实际价值：最后一行的通知函数可以在任何地方调用——接口层的错误处理、键盘事件监听、甚至另一个库的回调里，都不需要拿到组件上下文。这在上层框架的状态方案里通常要绕一圈才能做到。

Context 不是状态管理方案

用上下文放高频变化的状态，问题在于上下文的消费者无法只订阅其中一个字段：值一变，所有消费者全部重渲染。它适合放低频变化的东西——主题、当前用户、国际化字典、依赖注入的实例。把表单状态或列表筛选条件放进去，就会得到一个到处重渲染而且很难定位原因的应用。

最重要的一条判断：什么该进全局 store

大多数「状态管理很复杂」的抱怨，根因不是库选错了，而是把服务端数据当客户端状态在管。服务端数据需要的是一整套同步策略：缓存有效期、重复请求合并、聚焦时刷新、失败重试、分页与预取、写操作后的失效重取。把它塞进全局 store，意味着这些你全都要自己实现一遍，而且状态会从「远端事实的一份副本」退化成「任何代码都能改的本地数据」。

这张表照着执行，一个中型应用的全局 store 通常只剩下十几个字段。剩下的复杂度去了该去的地方：服务端数据交给专门的数据层，界面局部状态留在组件里，可分享的视图参数落在地址栏。

// 正确的分工：服务端数据走数据获取库，客户端状态走 store
import { useQuery } from '@tanstack/react-query'
import { useUI } from '@/stores/ui'

export function ProductList({ category }: { category: string }) {
  // 服务端事实：缓存、重试、失效重取都由数据层负责，不要抄进 store
  const { data, isPending, error } = useQuery({
    queryKey: ['products', category],
    queryFn: () => fetch(`/api/products?c=${category}`).then((r) => r.json()),
    staleTime: 60_000,          // 一分钟内复用缓存，避免重复请求
  })

  // 客户端状态：只订阅用到的字段，返回原始值所以不会引发多余渲染
  const density = useUI((s) => s.density)
  const pushToast = useUI((s) => s.pushToast)

  if (isPending) return <Skeleton rows={8} />
  // 错误处理留在数据层的返回值里，不要把 error 也存进全局 store
  if (error) return <Retry onRetry={() => pushToast('正在重试')} />

  return <Grid items={data} density={density} />
}

// 反例：把列表数据 loading 与 error 全塞进全局 store，
// 于是缓存、并发请求去重、失效重取都要自己写，
// 并且任何模块都能直接改 products，界面与服务端很快就不一致了

一句话结论

Zustand 的轻来自去掉了一层间接：没有动作与归约器的分离，没有派发机制，store 也不依赖组件树。它拿掉的那层恰好是重方案用来换取可追溯性的部分，所以判断很简单——你需要审计与回放吗？需要就付那份成本，不需要就别付。

❌
最容易踩的坑
  • 把服务端数据放进全局 store：你会被迫自己实现缓存、重试、失效重取，而且很快出现界面与服务端不一致。
  • 选择器返回对象字面量：每次返回新引用，比较永远不相等，组件无限重渲染。
  • 不写选择器直接取整个状态：任何字段变化都会触发重渲染，订阅粒度的优势全部丢掉。
  • 用上下文承载高频状态：消费者无法只订阅一个字段，值一变全体重渲染。
  • 依赖当前值却用对象式更新：并发更新时会基于过期值计算，应该用函数式更新拿到最新状态。
  • 以为更新是深合并：合并是浅层的，嵌套对象必须自己展开，否则同级其他字段会被整体替换掉。
  • 把筛选分页只放在 store 里：刷新丢失且链接无法分享，这类状态应该优先放地址栏。
  • 把令牌写进普通持久化存储：任何脚本都能读到，等于把凭据公开。
  • 生产环境开着调试中间件：内部状态结构与业务字段会暴露给任何打开控制台的人。
  • 为了少写代码把所有状态塞一个 store：领域边界消失后，任何改动都要通读整个文件。
  • 模块级单例配服务端渲染：状态会跨请求共享导致用户数据串台，这是安全问题，必须每请求新建。
  • 用它替代状态机：方法可以把状态改成任何组合，非法状态照样能出现，有严格转移要求时要用状态机。
