帧预算：把每帧 16.7 毫秒当成 SLO 来分解

后端给接口定 P99，客户端定的是帧预算，本质是同一件事，只是周期固定：目标 60 帧就是每帧 16.7 毫秒，30 帧是 33.3 毫秒。这点时间里要塞进输入、脚本逻辑、物理、动画、UI 重建、渲染提交，以及你不想要但一定会来的垃圾回收和资源加载。超预算在服务端表现为延迟毛刺，在客户端表现为掉帧，区别只是没人给客户端上 APM。

所以第一件事是把预算按子系统拆开写下来，而不是等美术和逻辑都堆完再来「优化一下」。怎么分配没有标准答案：卡牌和策略类的大头通常在 UI 与内存分配，竞技类在逻辑与物理。下面这张表是可以照着填的模板，数字必须在目标机型上自己压出来。

预算项主要占用来源超支时的现象观测入口
脚本逻辑Update、协程、事件派发、寻路与 AICPU 满而 GPU 空闲，持续性掉帧PlayerLoop 下的 Update 与 ScriptRunBehaviourUpdate
物理Collider 数量、连续碰撞检测、固定步长过小帧率一旦下滑就越来越慢，形成雪崩FixedUpdate 与物理模拟采样

💡
预算要按最坏帧算，不是按平均帧

平均 55 帧但每两秒掉到 20 帧的项目，玩家的评价是「卡」；稳定 30 帧的项目，玩家的评价是「流畅」。这和后端只看平均响应时间会漏掉长尾是同一个错误。所以验收指标应该是「最差 1% 帧的耗时」，而不是平均帧率。

资源与场景的组织：引用就是依赖

项目变大后最先失控的从来不是代码，而是资源引用与场景依赖。原因很简单：在 Inspector 里把一个对象拖到另一个字段上，就建立了一条构建期强依赖，这个动作不写代码、不进 code review、也没有工具会拦你。半年后的结果是：一个登录界面预制体顺着引用链拉进整套战斗特效和高清贴图。

Addressables 与打包边界：group 划分决定下载粒度

Addressables 最容易被误解的一点是：它不是一个「加载 API」，而是一套打包边界的声明。group 怎么划，直接决定了包的数量、单个包的体积、以及玩家更新一个小改动要下载多少字节。划得太碎，清单文件变大、请求数变多；划得太粗，改一个图标就得让玩家重下几十兆。

另一个高频事故是重复依赖。两个 group 里的预制体都引用同一张共享贴图，而这张贴图自己没有被显式分配到任何 group，结果它会被打进两个包，内存里出现两份互不相认的实例。这类问题必须靠工具做定期扫描，肉眼发现不了。

生命周期与 Update 的真实成本

顺序背下来就好，值得讲的是成本模型：每个组件的 Update 都是引擎从原生侧跨到托管侧的一次调用。一千个什么都不做的空 Update 也有可观的固定开销，而且在 Profiler 里被摊成一千个小条目，很难发现。通用做法是让一个管理器统一驱动，需要每帧更新的对象注册进列表。

回调调用时机应该放什么放错的后果
Awake实例化时，未启用也会调自身组件引用缓存、不依赖别人的初始化放了依赖别的对象的逻辑，会拿到空引用
OnEnable每次启用事件注册、池化对象的状态重置在这里做一次性初始化，池化复用后会重复执行
Start首帧之前，且脚本已启用依赖其他对象已就绪的初始化指望它先于别人的 Awake 执行，顺序不成立
FixedUpdate按固定步长，与帧率不同步施力、速度设置等物理操作写输入采样会丢帧或重复采样
Update每帧一次输入、状态机推进、表现层插值写物理操作会随帧率变化而行为不一致
LateUpdate所有 Update 之后相机跟随、骨骼修正写业务逻辑会比 Update 晚一帧，产生抖动
OnDisable每次禁用，含被销毁前事件反注册、手动停协程不写就是事件泄漏，对象没了回调还在触发
⚠️
两个流传很广的错误说法

第一，「禁用对象会停掉它的协程」。协程由启动它的组件驱动，跨对象启动的协程完全不受影响，正确做法是在禁用回调里显式停掉。第二，「物理步长调小更精确」。步长越小，一帧内要补算的物理次数越多，帧率下滑就进入「越慢越要补、越补越慢」的正反馈；引擎为此设了单帧最大累积时间上限，把它一起调大等于打开雪崩开关。

GC 压力的真实来源

后端做 Java 的人对 GC 有直觉，但这里的直觉要改一条：Unity 的托管堆不做压缩，一次回收需要扫描整个堆，堆越大，单次停顿越长，而堆一旦涨上去也不会还给系统。所以目标不是「少分配」，是稳态帧内零分配：加载阶段随便分配，进入战斗后每帧的分配量应该是 0。

分配来源典型写法为什么会分配消除方式
字符串每帧拼接血量、计时、日志字符串不可变，拼接与数值转文本都会产生新对象只在数值变化时重建；用可复用的字符串构造器
装箱枚举当字典键、结构体经接口调用、变长对象参数值类型被塞进引用类型的位置时会在堆上复制一份给字典传比较器；避免让结构体经接口调用；日志接口按类型重载
闭包与委托在每帧执行的代码里写捕获局部变量的匿名函数捕获会生成闭包对象，委托本身也是对象把委托缓存成字段，只创建一次
返回数组的接口获取全部组件、物理范围查询、射线检测这类接口每次调用都新建数组返回换成写入预分配缓冲区的非分配版本
协程的等待对象在循环里每次新建等待指令每次都是一个新对象，长时间运行累积很可观把等待对象缓存复用
枚举遍历对某些集合类型或接口变量做 foreach取到的迭代器是引用类型时会分配热路径改用下标循环，或用具体类型而非接口类型
 
using System.Collections;
using System.Text;
using UnityEngine;

// 目标不是「少分配」，而是稳态零分配：堆不压缩，一次回收要扫全堆，堆越大停顿越长
public class EnemyScanner : MonoBehaviour
{
    private readonly Collider[] _hits = new Collider[32];       // 复用缓冲区，避免每次查询新建数组
    private readonly WaitForSeconds _tick = new WaitForSeconds(0.2f); // 等待对象只建一次
    private readonly StringBuilder _sb = new StringBuilder(64);
    private int _lastHp = -1;
    private Transform _tr;

    void Awake() => _tr = transform;   // 组件引用一次性缓存，别在每帧里反复获取

    IEnumerator Start()
    {
        while (enabled)
        {
            // 非分配版本把结果写进已有数组，返回实际命中数；数组满了会静默截断，容量要按上限给
            int n = Physics.OverlapSphereNonAlloc(_tr.position, 8f, _hits);
            for (int i = 0; i < n; i++)
            {
                // 处理 _hits[i]；注意数组里超过 n 的槽位是上一次的残留，不能遍历整个数组
            }
            yield return _tick;   // 每 0.2 秒扫一次就够，不需要每帧扫
        }
    }

    // 只在数值真的变化时才重建字符串，而不是每帧刷一次界面
    public string FormatHp(int hp)
    {
        if (hp == _lastHp) return null;
        _lastHp = hp;
        _sb.Clear();
        _sb.Append("HP ").Append(hp);
        return _sb.ToString();
    }
}

对象池的适用边界经常被搞错：池化解决的是创建与销毁带来的抖动，不是对象数量多。值得池化的有三个特征——生命周期短、频率高、创建成本明显，典型是子弹、飘字、特效和列表格子。全局唯一的管理器池化只会多出状态残留风险。

using System.Collections.Generic;
using UnityEngine;

public class SimplePool
{
    private readonly GameObject _prefab;
    private readonly Transform _root;
    private readonly Stack<GameObject> _idle = new Stack<GameObject>();
    private readonly HashSet<GameObject> _busy = new HashSet<GameObject>();  // 防重复归还

    public SimplePool(GameObject prefab, Transform root, int prewarm)
    {
        _prefab = prefab;
        _root = root;
        // 战斗开始前预热，不要在开火那一帧扩容，扩容本身就是一次尖刺
        for (int i = 0; i < prewarm; i++) _idle.Push(Create());
    }

    private GameObject Create()
    {
        var go = Object.Instantiate(_prefab, _root);
        go.SetActive(false);
        return go;
    }

    public GameObject Rent()
    {
        var go = _idle.Count > 0 ? _idle.Pop() : Create();
        _busy.Add(go);
        go.SetActive(true);   // 启用回调会再次触发，所以状态重置统一写在 OnEnable 里最安全
        return go;
    }

    public void Return(GameObject go)
    {
        if (!_busy.Remove(go)) return;   // 归还两次会让同一实例同时被两个调用方持有，现象极难复现
        go.SetActive(false);             // 注意：禁用不等于清理，挂在上面的定时逻辑要自己收尾
        go.transform.SetParent(_root, false);
        _idle.Push(go);
    }
}

序列化与预制体：字段改名即丢数据

这一节是后端转过来的人最容易吃暗亏的地方。Unity 的序列化按字段名匹配，没有版本号、没有字段编号、也没有兼容性检查。把 atk 改成 attackPower，等价于「删掉一个字段、新增一个字段」，所有场景和预制体上填好的数值在下次保存时静默归零。习惯了 Protobuf 那种字段编号约定的人，会完全预料不到这件事。

using UnityEngine;
using UnityEngine.Serialization;

public class WeaponConfig : MonoBehaviour
{
    // 改名时必须留下旧名字的映射，且要等所有场景和预制体都被重新保存过一轮之后才能删这两行
    [FormerlySerializedAs("atk")]
    [FormerlySerializedAs("attack")]
    [SerializeField] private int attackPower = 10;   // 私有字段必须显式标注才会被序列化

    [SerializeField] private WeaponKind kind;        // 枚举按整数存，中间插入成员会让历史数据错位

    public int AttackPower => attackPower;           // 属性不参与序列化，只有字段会
}

public enum WeaponKind
{
    Sword = 0,   // 显式写死数值，避免以后插入成员导致存量数据含义改变
    Bow   = 1,
    Staff = 2,
}
操作实际结果是否报错修法
重命名已填值的字段旧值丢失，变回默认值不报错加旧名映射标注，全量重存后再移除
私有字段没加序列化标注完全不保存，每次运行都是默认值不报错显式标注，或改用公开字段
用属性代替字段暴露配置Inspector 里看不到，也不保存不报错用私有字段加标注，属性只做只读封装
字段类型用字典默认不被序列化，运行时为空不报错存两个并行列表，运行时组装成字典
字段类型是接口或抽象类默认不保存具体实现不报错用支持多态引用的标注，或改成具体类型
在中间插入枚举成员存量数据整体错位，武器类型全变不报错枚举值显式写死，新成员只能追加
同时改预制体和场景里的同名覆盖值覆盖值优先，改预制体看不出效果不报错确认改的是预制体本体还是实例覆盖

构建管线与平台差异

「我本机能跑」在这里比后端更危险：编辑器用即时编译，移动端发布走提前编译，没有运行期生成代码的能力。靠反射、动态构造泛型、运行时生成类型的写法，在真机上可能直接抛类型找不到，而且往往只在正式包里出现。

更隐蔽的是托管代码剥离：构建时会把「看起来没人调用」的类型和方法删掉，而通过反射调用的部分静态分析看不见。表现就是编辑器里功能正常，真机上一个功能点静默失效。这类问题必须靠显式的保留配置解决，而不是靠改代码绕。

维度编辑器 / 开发包移动端正式包工程上的影响
代码执行方式即时编译，支持运行期生成提前编译，无运行期代码生成反射与动态泛型要在构建期显式登记
未引用代码全部保留按静态分析剥离反射用到的类型需要写保留规则
纹理格式按导入设置，可能未压缩按平台重新压缩首次构建极慢，导入缓存目录不能随便删
内存上限桌面内存充裕受设备与系统限制，超限直接被杀必须在低端机型上验收内存峰值
日志与符号完整堆栈需要符号表还原每次出包必须归档符号文件，否则崩溃无法定位

Profiler：先看哪几个数

规则只有一条：在目标真机上抓，不看编辑器数据。编辑器里有额外开销、有不同的资源格式、有完全不同的内存环境，拿编辑器数据做优化决策基本等于瞎猜。连真机时要出开发包并打开自动连接，抓完立刻存档，后面所有优化都对着这份基线比。

与服务端的联动：时间、随机数与断线重连

只要有联网，客户端就必须接受一个前提：客户端是不可信的表现层，权威在服务端。这带来三个具体的工程约束，每一个都能在上线后变成事故。

时间不能用本地时钟。玩家可以随意改系统时间，所以冷却、倒计时、活动开关必须以服务端时间为准；本地只允许用单调递增的时间做插值和动画。常见做法是登录时估算一次时钟偏移，之后用本地单调时间加偏移推算服务器时间，并在长时间挂后台恢复时重新校准。

随机数不能用引擎自带实现做一致性判定。它不保证跨版本、跨平台产生相同序列，用它算暴击或掉落会让两端结果不一致。需要多端一致时自己实现固定算法的发生器，种子由服务端下发。帧同步还要面对浮点跨平台不一致，通常靠定点数或整数运算解决。

断线重连不是「把连接建回来」。难点是表现层的状态重建：重连后先拉一次全量快照，用它重建表现层并丢弃所有未确认预测，然后才接增量消息。图省事直接续着原状态跑，会出现血量、位置、冷却各错一点的诡异现象，线上极难复现。

sequenceDiagram participant C as 客户端表现层 participant L as 客户端逻辑层 participant S as 权威服务端 C->>L: 输入采样，附带本地序号 L->>S: 上行操作意图 L->>C: 本地预测先出手感 S-->>L: 权威状态、服务器时间、已确认序号 L->>L: 用已确认序号比对预测结果 L->>C: 一致则继续，不一致则回滚并重放未确认输入 Note over L,S: 网络恢复后不要就地续跑 S-->>L: 下发全量快照与当前序号 L->>C: 重建表现层，丢弃过期预测

状态同步与帧同步的横向对比见游戏开发总览，这里不重复展开。要记住的分工是：不论哪种同步模型，影响结果的判定都必须在服务端复算，客户端的计算只用来提前出手感。

最容易踩的坑

❌
这些坑每一条都能在上线后变成线上问题
  • 在 Inspector 里直接拖跨模块引用：建立了一条不进 code review、搜不出来的构建期依赖，半年后登录界面顺着引用链拉进整套战斗资源，包体和首屏内存都莫名变大。
  • 把资源丢进 Resources 目录图方便：这个目录无条件进包且无法按引用裁剪，等到包体超标时再迁移，要改的不是加载代码而是整套引用关系。
  • 共享资源不显式归组：同一张贴图被两个资源包各打一份，内存里出现两个互不相认的实例，肉眼永远发现不了，只能靠工具扫。
  • 加载了不释放，或者释放了还在用：前者表现为切场景内存不回落，后者表现为贴图变紫且只在低内存机型偶发，两者都不会抛异常。
  • 重命名序列化字段：等于删一个加一个，所有场景和预制体上填好的数值静默归零，不报错，通常打包后才发现。
  • 调小物理固定步长追求精确：帧率下滑时一帧内要补算更多次物理，进入「越慢越补、越补越慢」的正反馈；把单帧最大累积时间上限一起调大等于打开雪崩开关。
  • 几千个组件各自写空 Update：跨原生与托管边界的调用开销是真实存在的，而且在分析器里被摊成几千个小条目，看不出总量。
  • 用枚举当字典的键：默认比较器会走装箱路径，热路径上每次查询都在堆上留垃圾，稳态分配永远清不到零。
  • 重连后接着原状态跑：不拉全量快照就续跑，会出现血量、位置、冷却各错一点的诡异状态，且线上极难复现。
  • 用引擎自带随机数做需要两端一致的判定：跨版本跨平台的序列不保证一致，暴击和掉落会在客户端与服务端算出两个结果。
