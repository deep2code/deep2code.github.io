后端工程师真正需要的 OS 知识地图

后端不需要能手写调度器，但需要能在故障现场判断「这件事是操作系统在拒绝我，还是我的代码写错了」。下面这张地图只保留了会直接变成线上故障的部分：调度与等待、内存与页缓存、文件写入的持久化边界、网络栈的队列与状态、以及容器给进程加的那两道限制。每一项后面都跟着一个具体的故障形态和一个观测入口。

知识点不懂会出什么线上故障观测入口怎么判读
负载与不可中断睡眠把「负载 20」当成 CPU 不够而盲目扩容，实际瓶颈在存储运行队列长度与阻塞进程数可运行数不高但阻塞数高，方向是 IO 而非 CPU
上下文切换线程池配得过大，吞吐不升反降每秒上下文切换次数与自愿或非自愿之分非自愿切换占比高说明线程数超过了可用核心
页缓存与脏页回写写入毛刺周期性出现，应用侧完全查不到原因脏页水位与回写相关参数写延迟尖刺与脏页触发阈值对齐即可确认
刷盘语义以为写成功就是落盘，掉电后丢最近一段数据是否调用了刷盘、以及刷到哪一层按下一节的写入路径逐层确认
全连接队列压测到一定并发就有连接被拒，应用日志干净监听套接字的队列长度与溢出计数队列接近上限且溢出计数增长，就是应用来不及接受连接
连接状态大量连接堆在半关闭状态，最后文件描述符耗尽按状态统计连接数堆积在哪个状态直接指出是哪一方没有正确关闭
连接跟踪表偶发丢包与建连失败，抓包看不出问题跟踪表用量与内核日志内核日志里出现表满丢包，就是这一项
容器 CPU 限制平均使用率只有一半，P99 却规律性抖动限流次数与被限时长限流次数持续增长即被限，和平均使用率无关
容器内存限制进程无声消失，应用日志里没有任何异常内存用量与上限、内核的杀进程记录被内核杀掉不会有应用层堆栈，只能从内核侧看
信号与优雅退出发布时连接被硬断，正在处理的请求全部失败容器停止时的信号与宽限期进程是否收到终止信号、是否在宽限期内退出

写入路径：「写成功」到「不会丢」之间还有三层

这是后端最值钱、也最常被想错的一段知识。应用调用写入返回成功，只意味着数据进了内核页缓存；进程此时崩溃数据还在，机器此时掉电数据就没了。要让数据继续往下走，必须显式刷盘，而刷盘也只保证送到设备，设备自己的写缓存是否已经落到介质，取决于硬件配置。

三个高频误解

第一，绕过页缓存不等于持久化：直接 IO 只是不经过页缓存，数据仍可能停在设备写缓存里。第二，刷了文件不等于文件名也安全：新建文件后只刷文件本身，目录项可能还没落盘，崩溃后文件存在但名字不在，正确做法是重命名之后连父目录一起刷。第三，只刷数据和连元数据一起刷是两个不同的调用，前者更快但在文件长度变化的场景下需要格外小心，数据库类程序对这两者的选择都是刻意的。

网络栈：连接从来不只有「通」和「不通」

后端排查连接问题时最常见的错误，是把「建连失败」和「传输中断」当成同一类问题。它们分别对应内核里不同的资源：建连阶段看两个队列和端口资源，传输阶段看连接状态机和中间设备的空闲超时。下面这张表把最容易踩的几项列出来。

现象内核侧的真实原因常见的错误归因正确的处理方向
并发一上来就有连接被拒，应用日志干净全连接队列溢出，应用来不及接受连接怪网络抖动或客户端同时加大监听队列与应用的接受能力，两者取小值生效
大量连接停在等待应用关闭的状态对端已关闭，本端代码没有关闭连接以为是内核不回收这是应用侧的资源泄漏，内核帮不了，必须修代码
主动关闭方堆积大量等待超时的连接协议设计要求等待两倍报文最大生存期去调所谓的关闭超时参数那个参数管的是另一个状态；正解是用长连接减少关闭次数
做客户端时报无可用端口临时端口范围耗尽或被大量等待态占用以为是对端限流扩大端口范围、复用连接池、必要时增加出口地址
偶发丢包，抓包看不出规律连接跟踪表满，超出后直接丢包怀疑丢包是链路问题查内核日志中的表满记录，调大表容量或缩短跟踪超时
空闲一段时间后第一次请求必失败中间设备静默回收了空闲连接，两端都不知道以为是服务端重启连接池的空闲回收时间必须小于中间设备的空闲超时

容器里的 OS：cgroup 限制与信号是两个重灾区

容器没有改变操作系统，只是给进程套了一层限制与视图。问题在于很多工具读到的仍是宿主机的数据，于是「看着都正常」和「实际被限制」同时成立。下面这些都是排查时会真的把人带偏的点。

看到的现象真相观测点
容器内看到几十个核、几百 GB 内存那是宿主机的规格，和你的限额无关直接读 cgroup 的限额文件，不要信通用工具的输出
平均 CPU 使用率只有一半，延迟却规律性抖动被 CPU 配额限流，一个周期内用完额度就被暂停到下个周期限流次数与被限总时长，持续增长即确诊
进程无声消失，没有任何异常栈超过内存上限被内核直接杀掉，不给进程反应机会内核的杀进程记录与容器的退出原因
内存用量一直贴着上限但业务内存不高容器的内存统计包含页缓存，读写文件多时会被算进去分别看常驻内存与缓存部分，不要只看总量
发布时正在处理的请求全部失败进程没有处理终止信号，或宽限期内没退完，最后被强杀是否注册了信号处理、宽限期与实际退出耗时
进程根本没收到终止信号入口是脚本包装的子进程，脚本不转发信号确认容器里的一号进程是不是你的程序本身
僵尸进程越积越多一号进程没有回收子进程的职责实现进程状态统计，必要时用带回收能力的初始化进程

排查入口与阅读路径

故障现场最重要的不是记住命令，而是先站对分支：进程是否还活着、请求有没有进到应用、CPU 是真忙还是在等。下面这张图是这个判断顺序。

# 1) 先分清「CPU 忙」还是「在等 IO」：r 是可运行队列长度，b 是不可中断睡眠的进程数
vmstat 1 5
#    r 低而 b 高、wa 列明显 —— 瓶颈在存储，扩 CPU 无用
#    cs 列是每秒上下文切换次数，配合线程数判断是否线程池开太大

# 2) 容器 CPU 是否被限流（cgroup v2 路径；v1 在 cpu,cpuacct 目录下）
cat /sys/fs/cgroup/cpu.stat
#    nr_throttled 与 throttled_usec 持续增长就是被限，和平均使用率无关

# 3) 容器内存用量与上限；进程被杀不会有应用层异常，只能从这里和内核记录看
cat /sys/fs/cgroup/memory.current /sys/fs/cgroup/memory.max

# 4) 连接状态分布：堆在等待应用关闭的状态是自己没 close，堆在等待超时的状态在主动关闭方
ss -s

# 5) 监听队列是否溢出：Recv-Q 接近 Send-Q 就是应用接受连接的速度跟不上
ss -ltn

# 6) 哪个进程在读写磁盘、量有多大
pidstat -d 1 5
