API 风格选型：REST、GraphQL、gRPC 与流式推送的适用边界

🏷️ API 设计

「REST 还是 GraphQL」这个问题被问了十年，但它本身问错了。这两者不在同一个决策层：REST 是资源接口风格，GraphQL 是查询聚合层，gRPC 是内部方法调用，SSE 与 WebSocket 是推送通道。一个真实系统几乎必然同时用到三种以上。这篇只讲选型：每种风格真正解决什么问题、代价是什么、在什么边界上失效，以及混用时怎么分层。REST 的落地细节、版本演进、错误与分页等横切规范，分别在本目录另外三篇里展开。

先分清定位，再谈优劣

把四种风格摊在同一张架构图上，会发现它们的位置完全不同。对外接入层面对的是不可控客户端——第三方系统、装了三年前版本的 App、别人写的爬虫，你无法要求它们跟着你升级；内部调用层面对的是可控客户端——同一个发布流水线里的服务，可以约定同时升级。这一条差异决定了几乎所有后续取舍：契约能不能强制、能不能用二进制、能不能随时改字段、版本要不要长期共存。

注意最右边那一列：每种风格的真正差异不在传输协议，而在契约的强制力和它能自动生成什么。OpenAPI 是「写文档描述已有 HTTP 接口」，proto 是「写契约生成双端代码」，前者可以和实现背离，后者不可能背离——这是内部服务间选 gRPC 最实际的理由，比性能重要得多。

四种风格的完整对照

维度 REST over HTTP/1.1 或 HTTP/2 GraphQL gRPC SSE 与 WebSocket
契约强度与代码生成 弱。OpenAPI 是描述性的，实现可以和文档不一致，靠契约测试兜 中强。Schema 强类型且可 introspection，但只约束字段不约束 HTTP 语义 最强。proto 直接编译出 server stub 与 client stub，字段类型编译期检查 无契约。消息体格式全靠团队口头约定，最容易腐化
传输效率 JSON 文本，字段名重复传输，gzip 后可接受；易过度获取 按需取字段减少冗余，但查询语句本身也要传，且响应仍是 JSON Protobuf 二进制，同数据量通常比 JSON 小 30% 到 60%，序列化 CPU 更低 单连接复用，省掉每次握手；SSE 是文本帧，WebSocket 可二进制
浏览器友好度 最高。fetch 直接调，DevTools 直接看 高。就是一个 POST 请求 低。必须经 grpc-web 与 Envoy 代理转换，读不到 trailer SSE 用 EventSource 原生支持；WebSocket 原生支持但要自己管连接
缓存能力 最强。GET 可被浏览器、CDN、网关三级缓存，ETag 做条件请求 基本失效。统一 POST 同一个端点，HTTP 缓存完全用不上，只能做应用层或持久化查询 无 HTTP 缓存，需要自己在客户端或中间层做 不适用，本质是流
版本演进方式 URL 路径版本或媒体类型协商，多版本长期共存 不发版本，靠字段级 deprecated 标记加用量监控逐步下线 不发版本号，靠 proto 字段编号的兼容规则加 package 名带 v1 靠消息体里的 type 与 schema 字段自行区分
调试便利性 最好。curl 一行复现，日志里 URL 即语义 中。需要 GraphiQL 或带上完整查询语句，日志里全是同一个 URL 差一档。需要 grpcurl 加 reflection，抓包看不出内容 差。要专门的长连接调试工具，重连后状态难复现
流式支持 仅分块响应，没有真正的双向流 subscription 依赖 WebSocket 或 SSE 承载，实现方案不统一 原生四种模式，一元、服务端流、客户端流、双向流 这就是它们存在的理由
学习与运维成本 最低，网关、限流、WAF、APM 全套生态就绪 高。要额外建复杂度限制、字段级鉴权、按 operation 的监控 中。要建代码生成流水线、proto 仓库、负载均衡要做客户端侧或用 xDS 中高。连接数、心跳、优雅重启、水平扩容后的会话保持都要额外设计
典型适用场景 对外开放平台、后台管理、资源型 CRUD、可被 CDN 缓存的读接口 多端 BFF、字段组合频繁变化的前端、需要聚合多个下游的页面 内部高频服务间调用、跨语言强契约、需要流式的通道 通知推送、任务进度、大模型 token 流式输出、协同编辑、对局同步
⚠️
「gRPC 比 REST 快很多」是被滥用的结论

压测里 gRPC 领先，主要来自三件事：HTTP/2 多路复用省掉队头阻塞、Protobuf 序列化更省 CPU、长连接省掉 TCP 与 TLS 握手。但在一个典型业务接口里，端到端耗时的大头是数据库查询和下游调用，序列化通常只占几百微秒。如果你的接口 P99 是 200ms，换 gRPC 大概率看不到肉眼可见的收益。真正值得为之切换的是：调用量极大的内部链路（省的是 CPU 和带宽成本）、需要跨语言强契约、需要双向流。

REST 与 RPC 的哲学差异，以及那些「披着 REST 外衣的 RPC」

REST 的世界观是资源状态转移：系统由一堆可寻址的资源组成，客户端通过标准方法改变资源状态，语义全在方法和状态码里。RPC 的世界观是远程方法调用：服务暴露一组命名动作，参数进、结果出，语义全在方法名里。这不是对错之争，是建模粒度之争。

业务动作 REST 式建模 RPC 式建模 哪种更顺手
查询订单 GET /orders/1001 OrderService.GetOrder REST。天然可缓存、可带 ETag、URL 即日志语义
取消订单 POST /orders/1001/cancellations 或 PATCH /orders/1001 改 status OrderService.CancelOrder RPC。取消带一堆前置校验与副作用，把它压成状态字段会丢语义
批量导入一万条记录 需要自己定义批量资源与部分失败语义 ImportService.BatchImport，客户端流式 RPC。REST 的批量语义本来就是补丁
转账 POST /transfers，把转账本身建成资源，天然适合幂等键 AccountService.Transfer REST 略优。把动作变成资源后，重试与查询结果都有地址可用
实时下发行情 做不了，只能轮询 MarketService.Subscribe 服务端流 RPC 或 SSE

现实里大量接口是 POST /order/cancel 这种「REST 外衣下的 RPC」。教条主义者会说它错，但从工程角度看，它的真实代价只有一个：丢掉了 HTTP 的缓存与幂等语义。而取消订单本来就不可缓存、本来就需要幂等键，所以损失接近于零。真正致命的是不一致：同一个系统里一半接口用名词资源、一半用动词端点，新人每次都要翻文档猜；或者 GET /order/delete?id=1 这种 GET 带副作用的写法，会被浏览器预取、被 CDN 缓存、被爬虫触发。一致性的收益远大于符合教条的收益，但一致性本身不能豁免 HTTP 方法语义。

GraphQL 真正解决的问题，和它带来的五张账单

把 GraphQL 说成「解决过度获取」是把它讲小了。字段多传几个，gzip 之后成本极低，没人会为这个重构一遍架构。它真正解决的是前端字段需求多变导致的接口膨胀：首页要用户名加头像，个人中心要全量资料，订单列表页要用户名加等级加优惠券，于是后端出现 /users/1/profile、/users/1/summary、/users/1/brief 三个接口，改一次字段要动三处，每上一个新页面就再加一个。GraphQL 把「字段组合」这个决策权交给前端，后端只维护一张图。

代价不是「学习成本高」这种笼统说法，而是五件必须自己补的事：

代价 具体表现 必须做的对策 不做的后果
HTTP 缓存失效 所有请求都是 POST 同一个 /graphql，CDN 与网关无法按 URL 区分，ETag 也无从谈起 持久化查询把查询哈希成 ID 后改用 GET、应用层按实体 ID 做缓存、给客户端上 Apollo 或 Relay 的规范化缓存 原本被 CDN 挡住的读流量全部打到源站，QPS 可能上涨一个数量级
N+1 查询 列表字段的解析器逐条执行，十条订单查十一次库；嵌套两层就是乘法关系 所有跨表字段一律走 DataLoader，per-request 创建，合并成 IN 查询 一个看起来很小的查询打出上千次 SQL，连接池耗尽，数据库先挂
查询复杂度不可控 schema 里存在自引用路径（用户到好友再到好友），深嵌套查询能放大成笛卡尔积；同字段用多个别名可放大 N 倍 深度限制 7 到 10 层、复杂度评分预算、别名与批量查询条数上限、生产关闭 introspection 一个匿名请求即可打满后端，属于可被直接利用的拒绝服务面
权限要下沉到字段级 REST 里在接口入口判一次就够；GraphQL 里同一个 User 类型可能从任意路径被访问到 在解析器或指令层做字段级鉴权，且要覆盖「通过别的对象间接拿到该对象」的路径 典型越权：从自己的订单穿到买家对象再读到手机号。越权细节详见站内 devops/security 的认证授权篇

// Apollo Server 上线前必须加的三道闸；缺任何一道都等于把 DoS 面暴露出去
import { ApolloServer } from '@apollo/server';
import { createComplexityRule, simpleEstimator } from 'graphql-query-complexity';
import { maxDepthPlugin, maxAliasesPlugin, costLimitPlugin } from '@escape.tech/graphql-armor';

const server = new ApolloServer({
  schema,
  validationRules: [
    // 复杂度预算：每个字段默认 cost 1，可用 schema 指令给重字段加权
    // 1000 是经验起点，先按线上真实查询分布统计 P99 再定值，别拍脑袋
    createComplexityRule({
      maximumComplexity: 1000,
      estimators: [simpleEstimator({ defaultComplexity: 1 })],
      onComplete(cost) { metrics.observe('graphql_query_complexity', cost); },
    }),
  ],
  plugins: [
    // 深度限制：自引用路径（用户 至 好友 至 好友）必须截断，7 到 10 层足够覆盖真实业务
    maxDepthPlugin({ n: 8 }),
    // 别名限制：同一字段用 100 个别名可以把开销放大 100 倍且绕过深度限制
    maxAliasesPlugin({ n: 15 }),
    costLimitPlugin({ maxCost: 5000, objectCost: 2, scalarCost: 1, depthCostFactor: 1.5 }),
  ],
  // introspection 在生产必须关：否则整张 schema 加所有内部字段名直接对外公开
  introspection: process.env.NODE_ENV !== 'production',
});

# DataLoader 的两个铁律：按入参顺序返回、必须 per-request 创建
from strawberry.dataloader import DataLoader

async def batch_load_products(ids):
    # 一次 IN 查询替代 N 次单条查询；注意去重由 DataLoader 内部完成
    rows = await db.fetch(
        "SELECT id, name, price FROM products WHERE id = ANY($1)", ids)
    by_id = {r["id"]: r for r in rows}
    # 返回列表长度必须与 ids 等长、顺序必须一致，查不到的位置补 None
    # 顺序错了不会报错，只会静默串数据，这是最难查的一类线上事故
    return [by_id.get(i) for i in ids]

def build_context(request, user):
    # 放到模块级单例上会跨请求复用缓存，导致 A 用户读到 B 用户已鉴权的对象
    # 这是 GraphQL 服务最常见的越权成因，务必每个请求新建
    return {
        "user": user,
        "product_loader": DataLoader(load_fn=batch_load_products, max_batch_size=200),
    }

gRPC 的适用边界

gRPC 在内部服务间通信上几乎没有对手，理由按重要性排序是：proto 文件是唯一事实来源且能编译出双端代码（改错字段名编译就红，不用等联调）、跨语言一致（Go 服务和 Java 服务共用一份契约）、HTTP/2 多路复用加长连接、Protobuf 体积小、原生支持四种流式模式。它的边界也很清楚。

流式模式 典型用途 浏览器可用性 要注意的坑
一元调用 unary 绝大多数业务查询与写入 经 grpc-web 可用 默认无超时，客户端必须显式设 deadline，否则下游抖动会拖死上游线程
服务端流 大结果集分批下发、行情推送、日志尾随 经 grpc-web 可用 流上的错误只能在结束时通过 status 返回，中途失败要自己设计续传点
客户端流 批量上报、大文件分块上传 grpc-web 不支持 服务端要限制总量，否则单连接可以打满内存
双向流 协同编辑、对局同步、语音转写 grpc-web 基本不可用 需要自己定义应用层心跳与消息序号，负载均衡器的空闲超时会切断连接

另外三个常被忽略的运维成本：负载均衡——gRPC 用长连接，四层负载均衡会把一个客户端的所有请求钉在同一个后端上，必须做客户端侧负载均衡或经支持 HTTP/2 的七层代理；中间件生态——HTTP 世界里现成的 WAF、限流、鉴权插件大多不认 gRPC 帧；可观测性——抓包看不到明文，排查要靠日志和 grpcurl。

  -d '{"order_id":"1001"}' 10.0.1.20:9090 order.v1.OrderService/GetOrder

最容易踩的坑

❌
选型阶段最容易踩的坑
  • 为了「统一技术栈」把所有接口都换成 GraphQL，结果原本被 CDN 挡掉九成的读流量全部回源，数据库 QPS 翻十倍。
  • GraphQL 上线不配深度限制与复杂度评分，任何人构造一个八层嵌套查询就能打满连接池，这是可直接利用的拒绝服务面。
  • DataLoader 放在模块级单例里，跨请求复用缓存，A 用户读到 B 用户的对象，越权事故且很难复现。
  • DataLoader 的 batch 函数没按入参顺序等长返回，结果静默串数据，没有任何报错，排查成本极高。
  • 生产环境忘关 GraphQL introspection，整张 schema 连内部字段名一起对外公开，等于送出一份内部数据模型说明书。
  • GraphQL 不强制客户端带 operation name，监控里全是同一个 /graphql，出问题时完全定位不到是哪个页面。
  • gRPC 客户端不设 deadline，下游一抖动调用方线程全部堆积，故障沿调用链向上蔓延。
  • 用四层负载均衡代理 gRPC，长连接把流量钉死在少数几个 Pod 上，扩容后新实例没有流量。
  • 让浏览器直连 gRPC，忘了它读不到 trailer，必须经 grpc-web 与 Envoy 转换，客户端流和双向流还不支持。
  • 用 WebSocket 做只需要单向推送的场景，白白背上心跳、重连、鉴权续期、连接数治理的全部成本，SSE 本可以零成本搞定。
  • 把文件上传塞进 GraphQL 或 gRPC，丢掉分片续传、预签名直传、CDN 回源这些现成能力。
  • 同一个系统里名词资源和动词端点各占一半，还有 GET 带副作用的接口，被浏览器预取和 CDN 缓存后产生真实的数据变更。
  • 拿压测里 gRPC 的序列化优势去说服团队重写业务接口，而接口 P99 的大头是数据库耗时，改完收益接近零、迁移成本极高。
