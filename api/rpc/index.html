RPC 框架的抽象层次与选型

🏷️ 其他

RPC 最贵的不是序列化和网络，而是它把一次跨网络交互伪装成了函数调用。伪装带来的所有工程成本——三态失败、超时预算、重试放大、服务发现——都发生在框架抽象的不同层次上。这篇讲抽象层次与选型判断；gRPC 的传输细节见站内 gRPC 的传输机制与工程落地，编码与兼容性见站内 Protobuf 的编码与模式演进。

同步调用的第三态：不是成功也不是失败

本地函数调用只有两种结果：返回或抛异常。跨网络调用有三种：成功、明确失败、未知。第三态是所有分布式故障处理的起点——超时、连接中断、对端重启，你都无法判断请求到底执行没执行。

「未知」不可消除，只能转化。工程上只有两条路：要么让操作幂等，把「未知」转成「可以安全重试」；要么引入对账或补偿，把「未知」转成「事后收敛」。没有第三条路，而不设计就等于默认选了「靠运气」。这也解释了为什么「加个重试」经常让事故变严重：重试只在第一条路上成立。

观察到的现象 请求可能已执行吗 能否自动重试 需要的落地手段
连接被拒绝、DNS 解析失败 否 可以，直接重试 无需幂等设计
被限流或入队前拒绝 否 可以，必须退避 无需幂等设计，但要防重试风暴
请求发出后连接中断 可能 仅在幂等时可以 调用方生成幂等键，服务端唯一键去重
超时 很可能已执行 仅在幂等时可以 幂等键加状态机 CAS，避免与迟到的首次响应互相覆盖
明确的业务错误（参数非法、余额不足） 执行了但无副作用 不应重试 无需，重试只会浪费预算
内部错误、未知错误 可能已产生副作用 不应自动重试 对账与补偿任务，人工兜底

RPC、REST 与消息队列：选错的是语义

这三者的差别常被简化成「二进制比 JSON 快」「异步比同步抗压」，真正的分野是时间耦合与失败归属：同步调用要求双方同时在线，失败由调用方承担；消息传递允许错峰，失败由消费侧与重投机制承担。选型错了，后面的所有治理手段都在打补丁。

维度 同步 RPC REST over HTTP 消息队列
时间耦合 双方必须同时可用 同 RPC 生产与消费可错峰
失败归属 调用方立即面对三态 同 RPC，但 HTTP 语义更标准 转成投递与消费重试，调用方只管发出
压力表现 压力回传给调用方，需限流与熔断 同 RPC，可借缓存与 CDN 卸载 队列吸收，表现为堆积与延迟
顺序保证 无，并发调用天然无序 无 分区或队列内可有序
契约演进 强类型，破坏性变更需双端协调 弱约束，易演进也易失控 需兼容历史消息，回放时旧格式仍会出现
典型场景 需要立刻拿到结果的读与写 对外 API、浏览器直连 削峰、扇出、异步补偿、最终一致

API 风格本身的取舍（资源建模、版本化、分页、错误体）详见站内 API 设计；消息中间件的投递语义与堆积治理详见站内 消息队列。

抽象三层：序列化、传输、服务治理

看懂任何一个 RPC 框架，只要把它拆成四段：契约与代码生成、序列化、传输、服务治理。四段各自可替换，替换成本从右到左递增。这个视角比记住框架名字有用得多——它直接告诉你换框架时哪些代码会被波及。

层次 职责 替换成本 越层写代码的后果
契约与代码生成 定义方法、消息、错误；产出多语言 stub 最高，牵动所有调用方 手写编解码，两端定义慢慢漂移，没人敢改
序列化 编码格式、字段兼容性、跨语言类型映射 中，可与传输解耦切换 把数据库实体直接当传输对象，改一个列就破坏线上契约
传输 连接、多路复用、流控、加密 中，接口稳定时可整体替换 业务代码里判断连接状态、自己写重连与心跳
服务治理 注册发现、负载均衡、超时重试、限流熔断、观测 最低，可下沉到 sidecar 或控制面 每个服务一套策略，无法统一调参，故障时无处下手

超时预算：自上而下分配，而不是各层自己拍

最常见的错误配置是每层各设一个「看起来合理」的超时。结果是入口先超时、下游还在跑，资源被幽灵请求占着。正确模型是预算：入口定总量，每层扣掉自己的开销后把剩余传给下游。

校验规则只有一条：本层的所有下游超时之和，加上本层自身处理开销，必须小于本层拿到的预算。并行调用取最大值而不是求和。有重试时还要再加一条：单次尝试超时必须明显小于本层剩余预算，否则第一次尝试就吃光预算，重试根本不会发生——这是「配了重试但日志里从没出现过第二次尝试」的原因。

层级 拿到的预算 自身开销预留 传给下游 配错时的现象
入口网关 800ms（由产品体验定） 50ms 750ms 网关超时大于客户端，用户已放弃而链路还在跑
订单服务 750ms 80ms（编排与序列化） 并行两路各 300ms 下游超时之和大于预算，自己永远先超时
库存 / 风控服务 各 300ms 各 60ms DB 或缓存 120ms，留出重试空间 单次尝试就设 300ms，重试没有机会执行
存储层 120ms — — 不设语句超时，慢查询把连接池占满

重试放大与幂等前提

重试的危险在于它是乘法。每层最多 3 次，两层串联最坏 9 次，三层 27 次，再叠上客户端 SDK 自带重试就是几十倍。下游本来只是变慢，重试直接把它压成不可用，然后所有上游一起超时——这是典型的重试型雪崩。

sequenceDiagram autonumber participant C as 客户端 participant A as 订单服务 participant B as 库存服务 participant D as 数据库 C->>A: 下单，整体预算 800ms A->>B: 扣库存，未做预算分配，自己设了 800ms B->>D: 写库，存储抖动导致 600ms 未返回 A->>B: 第 2 次尝试，上一次仍在执行 A->>B: 第 3 次尝试 Note over A,D: 一层 3 次、两层就是 9 次，压力在最下游被平方放大 C--xA: 客户端到点先放弃 A->>B: 在途重试继续进行，成为没人要的幽灵请求 B->>D: 幽灵写入，没有幂等键就是重复扣减
链路层数 每层最大尝试 最坏放大倍数 抑制手段
1 层 3 3 倍 退避加抖动即可
2 层 各 3 9 倍 只在一处重试，通常放在最接近故障点的一侧
3 层 各 3 27 倍 改用按比例的重试预算，限制重试并发占比
任意层数加 SDK 自带重试 再乘 2 数十倍 先把框架与 SDK 的默认重试全部显式关掉，再统一开一处
✅
比「重试 3 次」更可靠的两个开关

一是重试预算：限制重试请求数占正常请求数的比例（例如 20%），故障面扩大时重试会自动退场，不需要人工调参。二是熔断：下游明确不可用时直接快速失败，把排队变成立即报错，前提是调用方准备好了降级路径，否则只是把错误更快地抛给用户。

stateDiagram-v2 state "Closed 正常放行" as CLOSED state "Open 快速失败" as OPEN state "HalfOpen 试探放量" as HALF [*] --> CLOSED CLOSED --> CLOSED: 失败但未达阈值，仅累计统计 CLOSED --> OPEN: 窗口内失败率或连续失败超阈值 OPEN --> HALF: 冷却时间到 HALF --> CLOSED: 试探请求全部成功 HALF --> OPEN: 试探请求出现失败，重新计时 note right of OPEN 统计窗口要按时间滑动而不是按固定计数 低流量服务用计数窗口会长期停在 Open end note 
-- 幂等的前提是「同一业务意图有一个稳定的键」，由调用方生成，重试时保持不变
CREATE TABLE payment_request (
  request_id   VARCHAR(64) NOT NULL,   -- 幂等键：调用方生成，不能用自增 ID 或时间戳
  order_id     VARCHAR(64) NOT NULL,
  amount_cents BIGINT      NOT NULL,
  state        VARCHAR(16) NOT NULL,   -- INIT / SUCCEED / FAILED
  created_at   DATETIME    NOT NULL,
  PRIMARY KEY (request_id)
);

-- 第一次插入成功的人拿到执行权；重试撞唯一键，直接去读已有结果
INSERT INTO payment_request (request_id, order_id, amount_cents, state, created_at)
VALUES (?, ?, ?, 'INIT', NOW())
ON DUPLICATE KEY UPDATE request_id = request_id;  -- Postgres 用 ON CONFLICT DO NOTHING

-- 状态推进必须带前置状态，防止「超时重试」与「迟到的首次响应」互相覆盖
UPDATE payment_request SET state = 'SUCCEED'
WHERE request_id = ? AND state = 'INIT';
// 预算内重试：单次尝试超时由剩余预算和剩余次数推出，保证重试真的有机会发生
func callWithBudget(ctx context.Context, do func(context.Context) error) error {
    dl, ok := ctx.Deadline()
    if !ok {
        return errors.New("refuse to call without a deadline") // 没预算就不发起调用
    }
    const maxAttempts = 3
    var last error
    for i := 0; i < maxAttempts; i++ {
        remain := time.Until(dl)
        if remain <= 0 {
            break
        }
        per := remain / time.Duration(maxAttempts-i) // 把剩余预算切给本次尝试
        try, cancel := context.WithTimeout(ctx, per)
        err := do(try)
        cancel()
        if err == nil {
            return nil
        }
        last = err
        if !retryableAndIdempotent(err) { // 未知类失败一律不重试，除非调用本身幂等
            return err
        }
        backoff := time.Duration(1<<i) * 50 * time.Millisecond
        jitter := time.Duration(rand.Int63n(int64(backoff))) // 抖动，避免同时重试
        select {
        case <-time.After(backoff/2 + jitter/2): // 退避时间也算在预算里
        case <-ctx.Done():
            return ctx.Err()
        }
    }
    return last
}

服务发现与健康检查

服务发现的难点不在「怎么拿到地址列表」，而在列表什么时候是错的。三类错位反复出现：注册早于就绪、下线晚于摘流、注册中心自身不可用。

第一类：进程起来就注册，但缓存没预热、连接池没建好，流量一进来全是超时。解法是把注册动作绑在就绪检查之后。第二类更隐蔽：正确的下线顺序是先反注册、等一个传播周期、再停止接收新请求、最后优雅关闭；顺序颠倒就会有一段时间流量打向已关闭的实例。第三类：注册中心抖动时，客户端必须用本地缓存的地址列表兜底，并且不能因为拿不到列表就把已有连接全摘掉——这是注册中心故障引发全站不可用的经典路径。

检查手段 判据 覆盖不到什么
TCP 端口连通 能建连 进程假死、线程池打满、依赖不可用时仍判为健康
HTTP 就绪探针 业务自定义逻辑 通常只查自身，把下游状态写进探针又会造成故障扩散
RPC 层健康检查（如 gRPC 的 Health 服务） 按服务名粒度上报状态 需要客户端或负载均衡器支持，否则只是摆设
被动摘除（真实流量失败率） 连续失败或错误率超阈值 没有流量的冷启动实例判不出来；必须限制最大摘除比例
注册中心心跳 会话保活 心跳线程独立于业务线程池，业务已阻塞时心跳仍正常 
# 集群级治理：比「每次调用重试 3 次」安全得多的两个开关
circuit_breakers:
  thresholds:
  - priority: DEFAULT
    max_connections: 1024
    max_pending_requests: 256
    max_requests: 1024
    retry_budget:
      budget_percent:
        value: 20            # 重试并发最多占正常请求并发的 20%，自动抑制重试放大
      min_retry_concurrency: 3
outlier_detection:           # 被动健康检查：按真实流量摘除坏实例
  consecutive_5xx: 5
  interval: 10s
  base_ejection_time: 30s
  max_ejection_percent: 30   # 最多摘掉三成，防止全摘之后剩余实例被打死
# 路由级：单次尝试超时必须小于整体超时，否则重试根本来不及发生
retry_policy:
  retry_on: connect-failure,refused-stream,unavailable
  num_retries: 2
  per_try_timeout: 0.3s

框架定位矩阵

选框架的实际约束往往是「团队语言栈 + 是否需要开箱治理 + 调用方能不能是浏览器」，而不是基准测试数字。

框架 传输 序列化 内置治理 浏览器可达 定位
gRPC HTTP/2 Protobuf（可换） 弱，依赖 xDS 或服务网格 需 gRPC-Web 或网关 云原生与多语言的事实标准
Thrift 自定义 TCP，transport 与 protocol 可组合 Thrift 二进制 / Compact 弱 不可达 内部高吞吐、语言覆盖广
Dubbo 3（Triple） HTTP/2，兼容 gRPC Protobuf / Hessian2 强：注册中心、路由、限流 需网关 国内 Java 体系的服务治理
tRPC 多协议：私有协议 / HTTP / gRPC 多编解码可插拔 强，插件化 需网关 多语言、强插件生态的企业内网
brpc 多协议：baidu_std、HTTP、Redis 等 多种 中：内置负载均衡与熔断 不可达 以 C++ 为主的高性能服务
JSON-RPC 2.0 传输无关：HTTP、WebSocket、stdio JSON 无 天然可达 工具链协议、插件协议、无代码生成的轻量场景
Connect HTTP/1.1 与 HTTP/2 Protobuf 或 JSON 弱 可直连 既要 gRPC 生态又要浏览器直调

跨语言方面有一个常被忽略的成本：治理策略必须跨语言一致。同一套超时、重试、熔断规则要在 Go、Java、C++ 客户端里表现一致，靠各语言 SDK 各自实现几乎做不到，这才是服务网格和 xDS 控制面真正的价值所在——把治理从 SDK 里拿出来。

什么时候不该用 RPC

RPC 不是通信的默认答案。以下几类场景用 RPC 都会付出隐性代价：

  • 对外开放的 API：第三方需要最低的接入成本、可读的调试方式和稳定的版本策略，应走 HTTP 加 JSON，接口风格详见站内 API 设计。
  • 需要削峰、扇出或可重放的链路：用消息传递而不是同步调用，细节详见站内 消息队列。
  • 跨服务的强一致写：用同步 RPC 串起多个写操作，本质是分布式事务，应改用 Saga、TCC 或本地消息表，详见站内 分布式系统。
  • 细粒度、高频的数据读取：一次页面渲染触发几十次 RPC（N+1 调用）时，该做的是批量接口或数据本地化，而不是优化单次调用延迟。
  • 大文件与批量数据传输：走对象存储传引用，RPC 只传地址，不要把几十 MB 的 payload 塞进调用。
  • 调用链蔓延：如果一个业务动作要穿过五六个服务，问题在服务边界而不在通信方式，拆分原则详见站内 微服务。

最容易踩的坑

❌
避坑清单
  • 把 RPC 当本地调用写，在循环里逐条调用。单次 1ms 也架不住上千次，必须改批量接口。
  • 每层各自拍一个超时值，不做预算分配。入口先超时、下游继续执行，资源被幽灵请求占满。
  • 单次尝试超时等于本层总预算。第一次尝试就把预算用光，配了重试却从未真正重试过。
  • 框架默认重试、SDK 默认重试、业务代码自己的重试同时开着，放大倍数是三者相乘。
  • 对超时做自动重试却没有幂等键。超时属于「未知」，重复扣款和重复发货就是这么来的。
  • 幂等键用时间戳或自增 ID 生成，重试时键就变了，去重逻辑形同虚设。
  • 去重只做了唯一键插入，状态推进没带前置状态。迟到的首次响应会把重试写好的终态覆盖回去。
  • 熔断只配了打开条件，没有降级路径。结果是把「慢」换成了「更快地报错给用户」。
  • 低流量服务用固定计数窗口做熔断统计，几次失败后长期停在 Open，恢复不了。
  • 下线顺序写反：先停服务再反注册。正确顺序是先反注册、等传播、再优雅关闭。
  • 注册中心抖动时把地址列表清空。应该用本地缓存兜底，宁可用旧列表也不要把所有连接摘掉。
  • 就绪探针里检查所有下游依赖。一个下游抖动就让整组实例被摘除，故障从此扩散。
