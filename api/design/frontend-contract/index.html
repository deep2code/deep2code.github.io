前后端协作的契约与边界

🏷️ 前端与客户端

前后端协作出问题，绝大多数时候不是「谁不配合」，而是契约没有被表达成机器能校验的东西，边界没有被明确写下来。于是同一个字段两边理解不同、错误码各写一套、时区各按各的、重复提交各自防一半。这篇讲的是接口这层的工程机制与代价：契约怎么表达、错误怎么分类、会话怎么选、哪些东西必须在服务端定死，以及发布节奏错配会带来什么。

先划清范围：框架选型、渲染位置（客户端渲染、服务端渲染、静态生成）、构建工具、状态管理这些属于前端内部决策，一句话结论是「内容型站点优先静态生成或服务端渲染，后台系统用客户端渲染没问题」，细节详见站内 Next.js、框架对比 与 状态管理 几篇，本篇不重复。

契约的三种表达，保证的东西完全不同

「接口文档」是最弱的一种契约，因为它不参与构建，也不会在你改错时报错。真正有约束力的契约必须落在两个位置：构建期的类型检查和CI 里的校验。

表达方式它保证什么它不保证什么失效场景
手写文档或聊天记录人能读懂任何机器可验证的约束改了代码没改文档，且没人知道文档过期了
OpenAPI 描述文件 + 生成类型字段名与形状在编译期对齐语义正确，也不保证服务真的这么返回描述文件是事后手写的，与实现脱节
运行时 schema 校验（在边界解析）进入业务逻辑前数据形状可信不保证上游不改校验只做在前端，服务端不校验，脏数据照样入库
契约测试服务真实响应与描述一致不保证业务语义与性能只在合并时跑一次，线上配置差异没覆盖
CI 兼容性比对破坏性变更无法静默合入不能替你判断「破坏了谁」规则配得太松，删字段被当成普通修改放过去
💡
生成的类型只保证形状，不保证语义

从描述文件生成的类型能挡住「字段名拼错」和「少传参数」，挡不住「这个 amount 的单位是分还是元」。语义只能靠约定加命名表达：金额字段一律带单位后缀、时间字段一律带时区语义后缀、枚举一律显式列值而不是写成字符串。类型系统能做的检查，永远不要靠人去 review。

错误约定：状态码管协议，业务码管领域

常见的两种极端都不好用：全部返回 200，靠 body 里的 code 表达一切，会让所有 HTTP 层设施失效——网关重试、CDN 缓存、监控告警、SDK 的错误分支全都判断不了；把业务错误硬塞进 HTTP 状态码，则会出现「优惠券已过期」找不到合适状态码的窘境。正确的分工是：状态码表达协议层语义（能不能重试、要不要重新鉴权、是不是客户端错），业务码表达领域内的具体原因。

分页：offset 的代价与游标的约束

翻页方案的选择不是风格问题，它直接决定数据库的扫描量和结果的正确性。深翻页时 offset 的代价（扫描并丢弃前面所有行）详见站内 MySQL 篇，这里只讲对接口契约的影响。

方案能跳页吗翻页期间数据变动深翻代价对契约的要求
页码加每页条数能会重复或漏掉记录随页码线性增长需要总数，而总数本身可能很贵
游标（基于排序键）不能稳定，不会重复基本恒定游标必须是不透明字符串，前端不得解析或构造
时间戳当游标不能同一毫秒内多条会漏恒定必须是「时间加唯一 ID」的复合键，单靠时间一定出错
快照式滚动不能完全一致服务端要维持上下文要有过期时间，且前端必须处理上下文失效

两个最常见的错误认知：第一，「游标分页更快」不是因为它魔法般更快，而是因为它把查询变成了「从某个键之后取 N 条」，能直接走索引；第二，只要排序键不唯一，游标就必须加上一个唯一字段兜底，否则边界处必然漏数据——这类 bug 在测试环境几乎不可能复现。

鉴权与会话：选型代价与刷新风暴

方案XSS 下的暴露面CSRF 风险跨站场景服务端能主动失效吗适合
服务端会话 + HttpOnly Cookie脚本读不到凭证需要显式防护受 Cookie 分区影响大能，删会话即生效同站的 Web 应用，最省心
自包含令牌放 Cookie脚本读不到需要显式防护同上只能靠短有效期或黑名单无状态服务但仍是纯 Web 端
令牌放 Authorization 头存储位置可被脚本读取天然免疫不受 Cookie 策略影响同上多端共用一套接口、跨域场景
短令牌 + 刷新令牌取决于存储位置取决于载体灵活能，吊销刷新令牌需要长期登录态又要能吊销

Cookie 侧有几条必须写死的规则：跨站携带必须 SameSite=None 且 Secure，两者缺一个就不生效；不要依赖浏览器的 SameSite 默认值，各家取值并不完全一致，一律显式声明；会话 Cookie 优先用 __Host- 前缀，它强制要求 Secure、不带 Domain、路径为根，能挡掉子域写入的一整类攻击。Cookie 与同源策略的安全细节详见站内 安全 系列。

刷新令牌最典型的工程事故是并发刷新风暴：页面同时发了 6 个请求，凭证刚好过期，6 个请求同时拿到 401，于是并发发起 6 次刷新。如果服务端启用了刷新令牌轮换，后到的刷新会因为令牌已被使用而失败，结果是用户被踢下线——现象是「页面一进来偶发掉登录」，极难复现。

轮换策略下后到的刷新失败，用户被踢下线 
let refreshing: Promise<string> | null = null;

// 单飞：并发的 401 共用同一次刷新，而不是各刷一次
function refreshOnce(): Promise<string> {
  if (!refreshing) {
    refreshing = doRefresh().finally(() => {
      refreshing = null; // 无论成败都要清空，否则失败后永远卡在旧 Promise 上
    });
  }
  return refreshing;
}

export async function request(input: RequestInfo, init: RequestInit = {}, retried = false) {
  const res = await fetch(input, { ...init, credentials: 'include' });
  if (res.status !== 401 || retried) return res;

  try {
    await refreshOnce();
  } catch {
    redirectToLogin();       // 刷新失败是终态，不要再递归重试
    return res;
  }
  // 只重放一次：retried 标记防止「刷新成功但接口仍返回 401」时无限递归
  return request(input, init, true);
}

服务端配合点同样关键：刷新接口应对「同一个刷新令牌在极短时间内的重复请求」给一个宽限窗口，返回同一批新凭证而不是直接判定为重放攻击，否则客户端再怎么写单飞，多标签页场景仍然会互相踢。

序列化边界：时间、金额、ID、空值

数据线上表示踩坑点约定
时间点带时区偏移的 ISO 8601 字符串非标准格式的日期字符串解析行为由实现决定，各引擎不一致服务端统一输出 UTC 加偏移，前端只负责按用户时区展示
业务日期与跨天口径单独的日期字段「今天的订单」在不同时区是不同集合，夏令时地区还会变长变短按天聚合一律由服务端用业务时区算，且时区用地区名不用固定偏移
金额最小单位整数，或十进制字符串浮点数做金额运算必然出现精度误差字段名带单位，前端只做展示格式化，不做加减
大整数 ID字符串JavaScript 的数字安全整数上限约为 9 千万亿量级，64 位 ID 用数字会静默丢低位所有 ID 一律字符串，包括看起来还很小的自增 ID
枚举稳定的字符串标识服务端新增枚举值，老客户端解析不了直接异常契约里声明「可能出现未知值」，客户端必须有兜底分支
空值明确区分缺失与空字段缺失、null、空字符串被当成同一种处理可空字段显式标注，不要用空字符串或 0 表达「没有」

幂等与重复提交：键由谁生成

「防重复提交」在前端只能做到按钮置灰，那是体验优化，不是正确性保证——网络超时重发、用户强制刷新、移动端弱网重试都绕过它。真正的保证只能在服务端，而且幂等键必须由客户端在首次发起时生成：如果由服务端生成，客户端重试时带不上同一个键，幂等就无从判断。

stateDiagram-v2 [*] --> Absent : 客户端生成幂等键 Absent --> InFlight : 服务端抢占键成功，开始处理 Absent --> Conflict : 抢占失败，说明已有同键请求 Conflict --> Replay : 已有结果，直接返回首次响应 Conflict --> Pending : 首次请求仍在处理中，返回冲突让客户端稍后重试 InFlight --> Done : 处理成功，落盘结果与响应 InFlight --> Failed : 处理失败，释放键允许重试 Done --> Replay : 后续同键请求命中缓存 Failed --> Absent : 键已释放 Replay --> [*] Pending --> [*] note right of Failed 失败必须释放键 否则用户重试会一直拿到 一个不存在的成功结果 end note 
// 幂等中间件：键的作用域必须包含用户与接口，否则不同用户的键会互相撞
func Idempotent(rdb *redis.Client, ttl time.Duration, next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        key := r.Header.Get("Idempotency-Key")
        if key == "" || r.Method == http.MethodGet {
            next.ServeHTTP(w, r)
            return
        }
        cacheKey := fmt.Sprintf("idem:%s:%s:%s", userID(r), r.URL.Path, key)

        // SetNX 抢占：占位值表示「处理中」，抢到才真正执行
        ok, err := rdb.SetNX(r.Context(), cacheKey, "PENDING", ttl).Result()
        if err != nil {
            // 幂等存储不可用时的取舍：宁可拒绝也不要重复扣款
            http.Error(w, "idempotency store unavailable", http.StatusServiceUnavailable)
            return
        }
        if !ok {
            if cached, _ := rdb.Get(r.Context(), cacheKey).Result(); cached != "PENDING" {
                w.Header().Set("Content-Type", "application/json")
                w.Header().Set("Idempotent-Replay", "true") // 让客户端和日志能识别重放
                _, _ = w.Write([]byte(cached))
                return
            }
            http.Error(w, "request in progress", http.StatusConflict)
            return
        }

        rec := &recorder{ResponseWriter: w, buf: &bytes.Buffer{}, status: 200}
        next.ServeHTTP(rec, r)

        if rec.status >= 500 {
            rdb.Del(r.Context(), cacheKey) // 失败必须释放，否则重试永远拿不到真实结果
            return
        }
        rdb.Set(r.Context(), cacheKey, rec.buf.String(), ttl)
    })
}

跨域与预检：真实成本和常见误判

跨域不是「浏览器不让请求」，而是浏览器发了请求但不把响应给你（简单请求场景）或者先发一个预检问一句（非简单请求场景）。这个区别决定了排查方向：服务端日志里明明有请求记录，前端却报跨域错误，是完全正常的现象，不是代理配置玄学。

情况会不会发预检成本可优化点
GET、HEAD、表单式 POST 且无自定义头不发零额外往返无需优化
JSON 请求体或带自定义头发每次多一个往返，首次尤其明显用 Access-Control-Max-Age 缓存预检结果
带凭证的跨域请求按上面规则额外约束响应必须回显具体来源且不能用通配，同时要加 Vary: Origin
预检缓存时长不适用各浏览器有各自上限，超出部分被截断设一个较大的值让浏览器自己截断即可，但要注意它按来源加路径加方法缓存
同源反向代理不涉及跨域多一跳延迟与运维成本能收敛到同源就不要折腾 CORS，尤其是带凭证的场景

两个高频误判：把 Access-Control-Allow-Origin: * 和携带凭证一起用，浏览器会直接拒绝——带凭证时必须回显具体来源；以及回显了来源却忘了 Vary: Origin，一旦中间有缓存层，A 站点会拿到给 B 站点的响应头，表现为「有时候好有时候跨域」。

BFF 的真实收益有两个：把「多端差异」和「客户端版本兼容」这两类易变逻辑从领域服务里赶出去；让前端团队能独立发布聚合逻辑而不用等后端排期。代价也很实在：多一跳网络与一个部署单元、超时与重试策略需要重新设计（上下游超时叠加会把故障放大）、契约从一份变成两份、以及最容易发生的组织问题——没人愿意长期维护它，半年后它变成谁都不敢改的中间层。

联调、mock 与发布节奏错配

如果前端发布是分钟级、客户端发布是周级，那么接口的演进规则必须按最慢的那一端来定。这条规则推导出一套很具体的变更纪律。

变更类型兼容性能直接发吗前置条件
新增可选字段兼容能客户端解析必须忽略未知字段，这一点要在 CI 里验证
新增接口兼容能无
新增枚举值有风险看客户端老客户端必须有未知值兜底，否则可能直接崩
字段含义变更破坏性不能必须新增字段并行一段时间，旧字段保持旧语义
字段类型变更（数字改字符串）破坏性不能等价于新增字段加下线旧字段的两步走
删除字段或接口破坏性不能先确认旧版本调用量、有强制升级能力、走观察期，详见客户端发布那一篇
收紧校验规则破坏性不能老客户端发来的数据会突然失败，需要先按版本放宽

联调阶段的工程做法：mock 应该由契约文件生成，而不是手写一份 JSON——手写 mock 的问题是它永远只覆盖成功路径，前端于是从来没见过错误态、空态和分页边界。CI 里再加一道兼容性比对，把破坏性变更拦在合并之前。

# CI 里的两道契约门禁，都能在合并前拦住问题

# 1) 破坏性变更检测：拿目标分支的契约文件与当前分支比
#    删字段、改类型、收紧必填都应该在这里失败
oasdiff breaking origin/main:openapi.yaml openapi.yaml --fail-on ERR

# 2) 契约与实现一致性：用契约文件起 mock，再用同一份用例打真实服务
#    两边响应都必须通过 schema 校验，才能说明契约没有腐化
prism mock openapi.yaml --port 4010 &
newman run api-tests.json --env-var base=http://127.0.0.1:4010
newman run api-tests.json --env-var base="$STAGING_BASE"
❌
最容易踩的坑
  • 所有响应都返回 200，错误只在 body 里：网关重试、监控告警、客户端 SDK 的错误分支全部失效，线上错误率永远是 0。
  • 没有 401 与 403 的分工：把无权限当成未登录，用户会被反复踢到登录页，然后登录成功又回到无权限页面。
  • 超时和断连当成失败处理并自动重试：这两种情况的真实语义是「结果未知」，不带幂等键时重试等于可能重复下单。
  • 幂等键由服务端生成：客户端重试时带不上同一个键，幂等逻辑等于没写。
  • 幂等键作用域没带上用户与接口：不同用户用同一个键会互相命中对方的结果。
  • 处理失败后不释放幂等键：用户重试时一直拿到一个「成功」的空结果，比报错难查十倍。
  • 并发 401 各刷一次令牌：启用刷新令牌轮换后，后到的刷新失败，表现为偶发掉登录，本地几乎无法复现。
  • 64 位 ID 用数字类型传：超过安全整数范围后低位被静默改写，症状是「偶尔查不到这条数据」。
  • 金额用浮点数：累加后出现分位误差，对账时才发现。
  • 时区用固定偏移而不是地区名：夏令时切换当天所有按天统计都会错，且一年只错两次，没人会怀疑代码。
  • 让前端解析游标：游标一旦被当成可构造的参数，服务端就再也不能改内部实现了。
  • 游标只用时间戳：同一时刻的多条记录会在页边界被漏掉，测试环境数据量小永远发现不了。
  • 带凭证的跨域用通配来源：浏览器直接拒绝；回显了具体来源又忘了 Vary: Origin，则会在缓存层串号。
  • 新增枚举值不打招呼：老客户端没有未知值兜底时会直接崩溃，而这类崩溃通常在灰度里看不到。
  • mock 手写且只有成功路径：上线后第一次遇到空态、错误态、末页边界都是在生产环境。
  • BFF 加了但没人维护：一年后它既有业务逻辑又有转发逻辑，成了谁都不敢改的第二个单体。
