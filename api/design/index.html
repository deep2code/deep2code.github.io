接口设计

资源建模 · 方法语义与状态码 · 横切规范 · 版本演进 · 前后端契约

接口发出去之后，别人按它写代码，改不动的那部分就不再由你决定。四篇各管一类问题：资源怎么命名与建模、跨接口的规范统一什么、已上线的接口怎么演进、前后端之间由谁保证什么。

篇目它回答什么什么时候读
RESTful 落地细节：资源建模、方法语义、状态码与条件请求名词与层级深度、非 CRUD 动作怎么建模、方法的安全与幂等语义、状态码判断树、ETag 并发新建一组资源接口，还在纠结动作放哪、返回哪个状态码
API 横切规范：响应结构、错误契约、分页、幂等与治理卡口统一包装与 HTTP 状态码之争的失真来源、错误结构、深分页代价、幂等键与原子更新、规范落成卡口接口已有存量，团队在同一件小事上反复吵：错误怎么返、分页怎么定
API 版本与兼容性演进：兼容判定、版本承载、废弃与下线版本升级与兼容性演进的区别、兼容判定表、四种版本承载、下线流程、Protobuf 编号规则要给线上接口加字段或撤掉旧版本，或内部服务之间定兼容约定
前后端协作的契约与边界契约三种表达各自保证什么、状态码与业务码分工、时间与金额的序列化边界、跨域预检成本、BFF 代价联调阶段扯皮：谁生成幂等键、空值怎么传、mock 与发布节奏对不上

四篇反复切同一条界：协议层和领域层各说各的话。4xx 与 5xx 描述请求本身成不成立，业务码描述领域里发生了什么。混在一层里，监控读不出信号，客户端只能解析字符串。

另一条界是「谁保证」。契约写在文档里、类型里还是运行时校验里，保证强度不同；幂等键由客户端生成还是服务端去重，失败后的行为不同。选型不是选写法，是选把责任压给哪一方。

认证与授权本身、GraphQL 与 tRPC 的协议取舍不在这一组，在 接口、协议与安全 的另外几组里。
