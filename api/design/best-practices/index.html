API 横切规范：响应结构、错误契约、分页、幂等与治理卡口

🏷️ API 最佳实践

这篇的定位是一套能直接抄进团队规范文档的具体约定：响应结构、错误契约、分页、幂等、并发控制、数据格式、观测与限流，全是跨接口的横切规则。这些东西的价值不在于「哪个方案更优雅」，而在于全站统一——不统一的时候，客户端要为每个接口写一套解析逻辑，网关和监控也无法做任何通用处理。风格选型见本目录主干篇，REST 的方法与状态码细节见 RESTful 篇，版本演进见版本篇。

统一包装还是 HTTP 状态码

这是国内团队争得最凶的一条。两派都有真实论据，不是品味问题。

维度 统一包装派（响应体固定为 code、message、data） HTTP 语义派（状态码加 Problem Details）
客户端处理成本 低。一套解包逻辑吃所有接口，前端拦截器统一弹错误提示 中。要分别处理状态码与错误体，但 HTTP 客户端库大多已内置
错误表达能力 强。业务错误码空间完全自主，可细到几千个 同样强。状态码表达类别，错误体里的 type 与 code 表达业务细节
基础设施可用性 取决于状态码是否同步。若一律 200，网关限流、熔断、错误率监控全部失效 好。网关、CDN、APM、SDK 重试策略开箱生效
与第三方生态的契合 差。所有对接方都要先读你的私有约定 好。开放平台的通行做法，对接成本最低
响应体开销 每个响应多一层嵌套，流式与二进制场景不好套 成功响应就是资源本身，最省
推荐 对内可用，但 HTTP 状态码必须与业务结果一致 对外一律用这种，配 RFC 7807
❌
「一律返回 200，靠 body 里的 code 判断成败」的四条硬代价

一是网关与 APM 统计的错误率永远是 0，熔断、告警、错误看板全部失真，线上出事时监控一片绿。二是客户端 SDK 与 HTTP 库的重试策略基于状态码（5xx 该重试、4xx 不该），全 200 之后要么不重试、要么连参数错误也无脑重试。三是 CDN 与缓存会把错误响应当正常响应缓存下来，故障被固化，清缓存前一直返回错的。四是访问日志无法分流，排查只能靠解析响应体，网关层面的限流与降级也失去判断依据。

错误响应设计

错误体的结构建议直接用 RFC 7807 Problem Details（媒体类型 application/problem+json），它的好处是字段语义有标准定义，再按需扩展业务字段。

字段 含义 怎么填才有用
type 错误类型的 URI，是稳定标识 指向可访问的文档页。它是客户端做分支判断的依据，一旦公布就不能改
title 错误类型的简短说明，与 type 一一对应 面向开发者、不随具体请求变化，不要往里塞变量
status 与 HTTP 状态码相同的数字 冗余但有用，便于日志与响应体对照；两者必须一致
detail 本次请求的具体信息，给开发者看 写清哪个字段、什么值、为什么不通过。绝不能放堆栈、SQL、内部服务名与 IP
instance 本次出错的请求标识 放请求路径或 trace 相关标识，方便回溯
扩展 code 业务错误码，分层编码 服务标识加模块加序号，如 ORD.PAY.10009，便于按前缀聚合告警
扩展 message 给终端用户看的文案 必须与 detail 分开：一个可直接展示给用户，一个进日志。混在一起就会把内部细节弹到用户脸上
扩展 trace_id 链路追踪 ID 必填。用户截图报错时，它是唯一能把前端现象与后端日志对上的线索
扩展 errors 字段级错误列表 校验失败必须一次返回全部，而不是只报第一个，否则用户要来回提交十次 
{
  "type": "https://docs.example.com/probs/validation-failed",
  "title": "Request validation failed",
  "status": 422,
  "detail": "字段 items[1].quantity 的值 0 小于最小值 1；字段 coupon_id 指向的优惠券已过期",
  "instance": "/v1/orders",
  "code": "ORD.CREATE.10021",
  "message": "商品数量至少为 1，且所选优惠券已过期",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "errors": [
    { "field": "items[1].quantity", "code": "min", "message": "数量至少为 1" },
    { "field": "coupon_id", "code": "expired", "message": "优惠券已过期" }
  ]
}

错误码的分层编码不要只图好看，它的实际用途是聚合与告警：按 ORD.PAY 前缀就能看出支付模块整体错误趋势，按完整码能定位单一原因。此外要区分「可重试」和「不可重试」，最省事的做法是在文档里为每个 type 标注重试语义，让调用方 SDK 可以自动处理。安全方面只说一句：堆栈、SQL、内部 IP、依赖服务名绝不能进响应体，这类信息泄露的危害与利用方式详见站内 Web 安全系列。

适用场景 后台列表、数据量可控、要跳页 无限下拉、高频变动、大数据量 对外开放 API、需要长期保留演进空间 
-- offset 深分页：数据库必须先取出 100020 行再丢掉前 100000 行
-- 在千万级表上这条查询通常要几百毫秒到几秒，而且越翻越慢
SELECT id, title, created_at FROM articles
 WHERE status = 'published'
 ORDER BY created_at DESC, id DESC
 LIMIT 20 OFFSET 100000;

-- 游标分页：把「上一页最后一条」作为起点，走索引直接定位，耗时与页码无关
-- 注意必须用行值比较，且排序方向与比较方向要一致，否则会漏数据
SELECT id, title, created_at FROM articles
 WHERE status = 'published'
   AND (created_at, id) < ('2026-09-20 11:03:07', 88231)
 ORDER BY created_at DESC, id DESC
 LIMIT 20;

-- 前提是有匹配的复合索引，否则游标分页同样会退化成全表扫
-- 索引列顺序必须与 ORDER BY 完全一致（索引原理详见站内 MySQL 索引篇）
CREATE INDEX idx_articles_status_created_id
    ON articles (status, created_at DESC, id DESC);

-- 大表的总数不要用精确 count，PostgreSQL 里可以读统计信息拿估算值
SELECT reltuples::bigint AS estimate FROM pg_class WHERE relname = 'articles';

幂等与并发控制

哪些接口需要幂等键？判据很简单：所有创建类的 POST、所有涉及资金与库存的写操作、所有异步任务提交接口。因为 POST 不幂等，客户端在网络超时后无法判断服务端是否已经执行，而它一定会重试。

sequenceDiagram autonumber participant C as 客户端 participant S as 服务端 participant I as 幂等记录表 participant B as 业务库 C->>S: POST 创建订单 携带 Idempotency-Key 值 k1 S->>I: 插入 k1 记录 依赖唯一索引 I-->>S: 插入成功 状态置为处理中 S->>B: 在同一事务内创建订单 1001 B-->>S: 提交成功 S->>I: 写回状态 完成 以及首次响应的状态码与响应体 S-->>C: 201 Created 订单 1001 Note over C,S: 此处响应在网络上丢失 客户端只看到超时 C->>S: 用同一个 k1 重试 S->>I: 插入 k1 冲突 读取已有记录 I-->>S: 状态 完成 附带首次响应内容 S-->>C: 回放首次响应 201 与订单 1001 Note over S,C: 关键 必须回放首次结果
回一个重复请求错误会让客户端误判为下单失败 C->>S: 并发的另一次 k1 请求 首次仍在处理中 S->>I: 插入冲突 读到状态 处理中 S-->>C: 409 Conflict 并带 Retry-After 提示稍后重试
stateDiagram-v2 [*] --> Processing Processing --> Done Processing --> Failed Failed --> [*] Done --> Expired Expired --> [*] note right of Processing 插入成功即进入该状态 依赖唯一索引保证只有一个进入 必须设处理超时 否则进程崩溃会留下永久卡住的键 此状态下的重复请求返回 409 而不是排队等待 end note note right of Done 保存首次响应的状态码与响应体 用于回放 回放时要连状态码一起还原 不能统一回 200 end note note right of Failed 业务失败也要落状态 但要区分可重试与不可重试 参数错误属于不可重试 应允许客户端换新键重新提交 end note note right of Expired 幂等键需要有效期 通常 24 小时到 7 天 按过期时间建索引并定时清理 否则这张表会无限膨胀 end note 
-- 幂等的核心不是代码逻辑，而是这条唯一索引：并发下由数据库来裁决谁是第一个
CREATE TABLE idempotency_records (
    id              BIGSERIAL PRIMARY KEY,
    -- 幂等键由客户端生成（UUID 或业务唯一串），服务端不能自己造，
    -- 否则重试时生成的是新键，幂等就失效了
    idem_key        VARCHAR(128) NOT NULL,
    -- 必须把作用域一起纳入唯一约束：同一个 key 在不同接口、不同用户下是不同语义
    scope           VARCHAR(64)  NOT NULL,
    user_id         BIGINT       NOT NULL,
    -- 请求指纹：同一个 key 配不同请求体应当报错，防止客户端错误复用
    request_hash    CHAR(64)     NOT NULL,
    status          SMALLINT     NOT NULL,   -- 1 处理中 2 完成 3 失败
    response_status SMALLINT,                -- 首次响应的 HTTP 状态码，回放时还原
    response_body   JSONB,                   -- 首次响应体，回放时原样返回
    created_at      TIMESTAMPTZ  NOT NULL DEFAULT now(),
    expires_at      TIMESTAMPTZ  NOT NULL,
    CONSTRAINT uk_idem UNIQUE (scope, user_id, idem_key)
);

-- 清理任务按 expires_at 走索引分批删，不要一条 DELETE 删全表
CREATE INDEX idx_idem_expires ON idempotency_records (expires_at);

幂等键的作用域必须包含接口与用户，否则「客户端在两个接口上复用了同一个 UUID」会导致第二个接口直接回放第一个接口的响应。另外要落请求指纹：同一个键配不同请求体时应当返回 422，这能抓出客户端复用键的 bug。幂等的其他实现路径（去重表、状态机、乐观锁、分布式锁）以及各自的失效边界，详见站内分布式一致性篇。

并发控制与幂等是两个问题：幂等解决「同一个操作被提交多次」，并发控制解决「不同操作同时改一份数据」。乐观锁有两种承载方式。

承载方式 做法 优点 代价
版本号字段 资源体里带 version，更新时作为条件，冲突返回 409 实现直观，内部服务与 RPC 风格都能用；字段就在业务模型里，调试方便 版本号污染了资源表示，客户端必须记得回传；不同资源的实现容易不一致
ETag 加 If-Match GET 拿 ETag，写入时用 If-Match 带回，冲突返回 412 更 RESTful，并发控制信息走在 HTTP 头里不污染模型，且能顺带获得 304 能力 需要网关与客户端都不吞掉这两个头；对非 HTTP 的调用方不适用

两者都要注意同一件事：判断必须落在数据库的一条原子 UPDATE 上，先查后改之间的窗口会让乐观锁形同虚设。丢失更新的完整时序演示与 ETag 的实现细节见本目录 RESTful 篇。

参数校验与数据格式约定

校验有三条硬规则：在边界一次校验干净（进入业务逻辑后不再出现半可信数据）、一次返回全部错误（不要只报第一个，否则用户要来回提交十次）、必填与默认值写进契约（可选参数的默认值必须与老行为一致，改默认值是破坏性变更）。

数据类型 约定 不这么做会怎样
时间 RFC 3339 带时区的字符串，统一用 UTC 传输、由客户端本地化展示 不带时区的本地时间字符串会在跨时区场景下差几小时；秒与毫秒时间戳混用会差一千倍
金额 最小单位整数（分），或十进制字符串；同时带上货币码 用浮点会累积误差，对账时差分；只给数字不给货币码在多币种场景下必然出错
大整数 ID 一律用字符串 JavaScript 在 2 的 53 次方以上丢精度，雪花 ID 到前端会变成末尾为 0 的错值
枚举 用有意义的字符串常量，并约定客户端遇到未知值按 unknown 处理 用数字枚举时任何人都读不懂日志；不约定未知值处理时新增枚举值就变成破坏性变更
布尔 真正的 JSON 布尔，不要用 0 与 1 或 Y 与 N 弱类型语言里字符串 0 是真值，判断结果与预期相反
空值 明确 null 与字段缺失的语义差别并写进规范 二者混用时 PATCH 无法表达「把某字段清空」，客户端也无法判断是没查到还是值为空
数组 空集合返回空数组而不是 null，并给出稳定排序 null 会让客户端遍历时崩溃；排序不稳定会让分页与快照对比出现诡异差异
字段命名 全站统一 snake_case 或 camelCase，选一个 混用会让客户端的自动映射失效，每个接口都要手写映射

契约先行与可观测性

契约先行的要点不是「先写文档」，而是让契约成为唯一事实来源：OpenAPI 规格文件进版本库、由它生成客户端 SDK 与 mock 服务、前端在后端还没写完时就能对着 mock 开发、CI 里用它做兼容性检查（检查细节见版本篇）。手工维护的文档必然腐化，唯一的解法是让它参与构建产物的生成——没人会让编译失败的代码合进主干，但所有人都能容忍一份过期的 wiki。

可观测性上最重要的一条是：按路由模板打点，不要按具体 URL。把 /orders/1001 当标签值会让时间序列数量等于订单数量，Prometheus 的内存和查询会先被打爆。同理，用户 ID、trace ID、幂等键都绝不能进指标标签，它们属于日志和链路追踪。必须采集的四个黄金信号：流量（QPS）、错误率（按状态码分类，这也是为什么不能一律返回 200）、延迟分布（看 P95 与 P99，均值毫无意义）、饱和度（连接池、线程池、队列长度）。

限流与配额要素 约定 理由
限流维度 同时按应用、用户、IP 三个维度独立计数，取最严者 只按 IP 会误伤同一出口的整个企业；只按用户挡不住批量注册的脚本
被限流的响应 429 加 Retry-After，值给秒数或确切时间 没有 Retry-After 时客户端只能盲目退避，往往越重试越拥塞
配额可见性 正常响应里也带剩余配额与重置时间的响应头 让调用方能主动限速，而不是撞墙之后才知道；批处理调用方尤其需要
写与读分开 写接口阈值远低于读接口，资金类接口单独配 一套阈值要么挡不住写风暴，要么把正常读打成 429
限流位置 网关做粗粒度，服务内做业务维度细粒度 网关看不懂业务身份，服务内挡不住已经打进来的流量洪峰。网关限流参数详见站内 Nginx 篇

把规范变成可执行的卡口

规范落地失败的原因几乎从来不是「大家不认同」，而是规范只存在于一份没人看的文档里。可执行的检查项才有约束力。

# Spectral 规则：把团队约定写成机器可判的规则，评审人就不用再重复提同样的意见
# 放进 pre-commit 与 CI，两处都跑，本地就能挡住大部分问题
extends: ["spectral:oas"]
rules:
  # URL 里不许出现动词（动词端点要走白名单单独审批）
  path-no-verb:
    description: 路径中不应包含动词，请用资源名词
    given: "$.paths[*]~"
    severity: error
    then:
      function: pattern
      functionOptions:
        notMatch: "/(get|create|update|delete|query|list|save)[A-Za-z]*(/|$)"

  # 每个写操作都必须声明 4xx 响应，避免只写 happy path
  operation-4xx-response:
    description: 写操作必须定义至少一个 4xx 响应
    given: "$.paths[*][post,put,patch,delete]"
    severity: error
    then:
      field: responses
      function: schema
      functionOptions:
        schema:
          type: object
          anyOf:
            - required: ["400"]
            - required: ["422"]

  # 错误响应必须使用 problem+json，保证全站错误结构一致
  error-media-type:
    given: "$.paths[*][*].responses[?(@property.match(/^[45]/))].content"
    severity: error
    then:
      field: "application/problem+json"
      function: truthy

  # 列表接口必须声明分页参数，禁止无上限返回
  list-must-paginate:
    given: "$.paths[?(@property.match(/s$/))].get.parameters"
    severity: warn
    then:
      function: schema
      functionOptions:
        schema: { type: array, minItems: 1 }

最容易踩的坑

❌
横切规范最容易踩的坑
  • 所有响应一律 HTTP 200，靠 body 里的 code 判断成败，于是监控错误率永远是 0，故障期间看板一片绿。
  • 错误响应把异常堆栈、SQL 语句、内部服务名直接塞进 detail，既泄露实现细节又让前端无法展示。
  • 只有一个 message 字段同时充当用户提示和开发者排查信息，结果「数据库连接超时」被原样弹给了终端用户。
  • 错误响应不带 trace_id，用户发来一张报错截图后完全无法定位对应的后端日志。
  • 参数校验只报第一个错误，用户改一次提交一次，十个字段来回十轮。
  • 后台列表用 offset 分页且不限制最大 offset，有人翻到第五千页，一条查询拖垮整个库。
  • 无限下拉用 offset 分页，翻页期间有新数据插入，用户看到重复条目，也会漏掉内容。
  • 游标分页的排序键选了不唯一的 created_at 却没拼主键兜底，同一秒内的数据被跳过。
  • 游标分页没有配对应顺序的复合索引，看着实现对了但性能仍然随页码劣化。
  • 幂等键由服务端生成，客户端重试时拿到的是新键，幂等形同虚设。
  • 幂等键重复时返回「重复请求」错误而不是首次结果，客户端把已成功的下单判成失败。
  • 幂等记录只存键不存首次响应，无法回放，也就无法告诉客户端订单号是多少。
  • 幂等键唯一约束只有键本身不含作用域，客户端在两个接口复用同一个 UUID 后串了响应。
  • 幂等记录没有过期清理，表无限膨胀，几个月后唯一索引写入开始变慢。
  • 处理中状态没设超时，服务进程崩溃后留下永久卡住的键，该业务从此无法再提交。
  • 乐观锁先 SELECT 查版本再比较再 UPDATE，两步之间的窗口让并发下照样丢更新。
  • 金额用浮点数传输，对账时出现几分钱的差额，排查成本远高于当初改成整数的成本。
  • 时间传不带时区的本地字符串，跨时区用户看到的时间全部偏移若干小时。
  • 雪花 ID 用数字类型返回，JavaScript 客户端丢精度后末尾几位变成 0，而后端查不到这个 ID。
  • 监控按具体 URL 打点，路径参数导致时间序列基数爆炸，监控系统比业务先挂。
  • 限流返回 429 但不带 Retry-After，客户端固定间隔重试，把限流变成持续冲击。
  • 规范只写在 wiki 里没有任何 lint 与 CI 卡口，半年后线上同时存在三种错误结构与两种分页参数。
