Web 安全总览：威胁建模、SSRF、上传漏洞与纵深防御

🏷️ Web 安全

「不要信任用户输入」这句话人人会说，但它同时被理解成了三件不同的事——输入校验、输出编码、参数化查询——而这三件事的作用层、作用时机、能防的漏洞类型完全不同。把它们混为一谈，就会写出「我都过滤过了怎么还被注入」的代码。

这篇是安全专题的主干：先建立威胁建模和信任边界这个统领视角，再给出分层防御的全景和优先级排序；XSS、SQL 注入、CSRF、认证授权、HTTPS、OWASP Top 10 各有专篇细讲，本篇重点补两个没有专篇但线上高频的漏洞：SSRF 和文件上传。

① 用法 · 上线前的安全基线清单

先给一份能当天做完的基线：八件事，每件都带一个可执行的验证动作。安全防护最典型的失效方式不是没配，而是配了却不生效——nginx 的头被子 location 覆盖、CSP 一直停在 report-only、越权校验只写在了列表接口上。所以下面每一行都要求你能拿到一个「被拒绝」或「头存在」的观测结果。原因与机制见下一节。

# 上线前基线自检：逐条跑，输出符合预期才算过（把 example.com 换成你的域名）

# 1) 安全响应头在不在
curl -sSI https://example.com/ | grep -Ei 'strict-transport|content-security|x-content-type|referrer-policy'

# 2) 4xx 也必须带头 —— nginx 漏写 always 时这里返回 0
curl -sSI https://example.com/this-path-does-not-exist | grep -c 'Strict-Transport-Security'

# 3) 证书剩余有效期：留出续期窗口，别等浏览器先报错
echo | openssl s_client -connect example.com:443 -servername example.com 2>/dev/null   | openssl x509 -noout -enddate -subject -issuer

# 4) 明文入口是否被 301 收走
curl -sSI http://example.com/ | grep -Ei '^HTTP/|^location'

# 5) 依赖漏洞：让高危直接卡住流水线，不要只看输出
govulncheck ./... ; npm audit --audit-level=high

# 6) Git 历史里的密钥 —— 删掉当前文件不算删，历史里还在
gitleaks detect --source . --log-opts="--all"
要做什么 怎么做 怎么验证它真的生效了
全站强制 HTTPS 80 端口 301 到 443，加 HSTS（先小 max-age 再放大） curl -I 明文地址看到 301；再请求一个 404 路径确认头仍在（验 always）
SQL 全部参数化 值一律走占位符；表名、列名、ORDER BY 走白名单映射 测试库打开全量 SQL 日志，用带单引号的正常输入发一次请求，日志里该值应作为参数出现而不是拼进语句
XSS 输出编码 按输出上下文选编码函数；CSP 先 Content-Security-Policy-Report-Only 跑一段时间 全仓搜 innerHTML / v-html / dangerouslySetInnerHTML 应只剩白名单用法；违规上报归零后再切强制
CSRF 防护 会话 Cookie 设 SameSite=Lax，写接口再校验 Token 或 Origin 带上有效会话 Cookie、不带 Token、Origin 改成外站域名发一次 POST，必须被拒
越权（资源归属）校验 查询条件里带上 owner_id，归属信息从会话取，不从请求参数取 用账号 A 的会话请求账号 B 的资源 id，必须 403 或 404；把这条固化成自动化用例
上传文件不落可执行位置 存对象存储或非 Web 目录；独立域名；强制 Content-Disposition: attachment 上传一个 .html 再访问它的 URL，必须触发下载而不是被渲染，且响应带 nosniff
出站请求收口（防 SSRF） 解析成 IP 后判网段、禁止跟随重定向、云元数据切 IMDSv2 分别用指向环回地址、云元数据地址、以及一个 302 跳内网的 URL 各试一次，三次都必须被拒
密钥移出代码库 改走环境变量或密钥管理服务，CI 里加密钥扫描卡点 扫全量 Git 历史返回 0 条命中；再做一次密钥轮换，确认服务不需要改代码即可生效

这张表里最容易被跳过的是第二列做了、第三列没做。没有验证动作的安全配置，等价于没有配置——因为它会在下一次改 nginx、换框架、加中间件时静默失效，而失效那天不会有任何报错。

响应头 / 配置项 作用 不设置时的默认行为 什么时候需要改
Strict-Transport-Security 强制浏览器后续只用 HTTPS 访问本域 不发送则浏览器允许明文访问，首次请求可被降级劫持 灰度期用小 max-age；确认全站含所有子域都已上 HTTPS 后再加 includeSubDomains
Content-Security-Policy 限制脚本、样式、frame 的来源，是 XSS 的兜底层 不发送则页面可加载任意来源脚本并执行内联脚本 老项目先用 Report-Only 收集违规；引入第三方统计或支付 SDK 时要加对应来源
X-Content-Type-Options: nosniff 禁止浏览器猜测响应类型 不发送则浏览器可能把文本当 HTML 或脚本解析 基本不需要改，用户上传内容的域名上必配
X-Frame-Options / frame-ancestors 控制谁能把你的页面放进 frame，防点击劫持 不发送则任意站点可嵌入你的页面 需要被合作方嵌入时改成显式白名单，不要为此整段删掉
Referrer-Policy 控制跳转时带出多少来源信息 各浏览器默认策略不同，以目标浏览器当前版本行为为准 URL 里带 Token 或订单号时必须收紧到不带路径的策略
Cookie 的 HttpOnly / Secure / SameSite 分别阻止脚本读取、限制只走 HTTPS、限制跨站携带 不写 SameSite 时按浏览器当前默认处理，以目标浏览器版本为准，不要依赖默认 需要跨站携带（嵌入式场景、第三方登录回跳）时才放宽，且必须同时加 Secure
server_tokens off（nginx） 不在响应头与错误页暴露版本号 默认输出 nginx 版本，等于给攻击者一份精确的漏洞匹配依据 一次配置，全站生效，无需再改
client_max_body_size（nginx） 限制请求体大小，挡上传型资源耗尽 默认值随版本变化，以 nginx -V 与官方文档对应版本为准 只在上传接口的 location 里单独放大，不要全站放大

② 原理 · 先画信任边界，再谈防御

搞清信任边界，能解决「校验写了一堆却总有一处漏掉」这个现象——漏的那处往往是因为没人说清校验该发生在哪一刻。

安全设计的第一步不是选工具，而是回答一个问题：数据在哪一刻从「不可信」变成了「可信」。这条线就是信任边界，所有校验都必须发生在线上，而不是线内某个「感觉该做校验」的地方。

常见误解 实际情况
「前端已经校验过了」 前端校验只是交互体验。攻击者直接构造 HTTP 请求，前端代码根本不执行。服务端校验是唯一有效的校验
「内网接口不用做安全」 一旦有 SSRF 或任一机器被打穿，内网就是攻击者的局域网。内部服务之间也要认证（mTLS 或签名）
「登录了就是可信用户」 认证只回答「你是谁」。绝大多数数据泄露事故出在授权：登录用户 A 改个 id 就看到了用户 B 的数据
「有 WAF 就安全了」 WAF 是基于特征的补充手段，对 DOM 型 XSS、逻辑越权、业务漏洞完全无效。它买的是时间，不是安全
「请求头不是用户输入」 User-Agent、Referer、X-Forwarded-For、Cookie 全部可任意伪造。把它们直接拼进 SQL 或写进日志同样会出事

② 原理 · 校验、编码、参数化：三件不同的事

搞清这三者的分工，能解决最常见的一类困惑：「我都过滤过了怎么还被注入」「我转义了怎么还是能改别人的数据」。

这是整个 Web 安全里最值得先搞清的一张表。混淆这三者是大量「防了但没防住」的根因。

手段 作用时机 作用对象 防什么 不能防什么
输入校验（validation） 数据进入系统时 格式、类型、长度、枚举、范围 脏数据、超长内容、非法状态、业务规则违背 防不住注入。合法的姓名里就可能含引号和尖括号
输出编码（encoding） 数据离开系统、写入某个解释器时 按目标上下文转义特殊字符 XSS（HTML/JS/URL/CSS 上下文各不相同） 防不住 SQL 注入，也防不住越权
参数化查询 拼 SQL 时 把值和语句结构彻底分离 SQL 注入（根治） 表名、列名、ORDER BY 字段无法参数化，要靠白名单
授权校验 每次访问资源时 当前身份与资源归属的关系 越权（IDOR、垂直越权） 上面三个都防不住越权，这是独立一层
❌
「在输入时统一转义存库」是错的

很多项目在接收参数时统一把 < 转成 &lt; 再存库，以为一劳永逸。两个问题：① 数据被污染了，用户真名叫「A&B」存进去变成「A&amp;B」，导出到 Excel、发短信、拼 JSON 时全是乱码；② 编码必须按输出上下文决定——同一个字符串输出到 HTML 文本、HTML 属性、JS 字符串、URL 参数里需要四种完全不同的编码方式，在输入时你不可能知道它以后会输出到哪。

正确做法：输入只做校验（合法性），输出才做编码（按上下文）。库里存的永远是用户输入的原始值。

② 原理 · SSRF：从一个图片下载接口到云凭证泄露

搞清 SSRF 的提权链，能解决「一个内部下载接口而已，有什么危害」的轻视——它的终点通常是云账号凭证。

SSRF（服务端请求伪造）是危害被严重低估的漏洞。表面上只是「服务器帮我下载一个 URL」，实际上攻击者借用了服务器的网络身份——而服务器通常在内网，而且在云上还能访问元数据服务。

这才是 SSRF 真正的破坏力
SSRF 常见入口 业务外观 容易被忽略的原因
图片 / 文件「按 URL 导入」 头像上传支持填网址 功能太普通，没人把它当安全入口
Webhook 回调地址 用户自己配置通知地址 地址由用户填写，本质就是让服务端访问任意 URL
网页截图 / PDF 生成 渲染服务加载页面 无头浏览器还能读 file://，危害更大
XML 解析（XXE） 导入 XML 数据 外部实体会发起网络请求，等价于 SSRF
后台「接口测试」工具 运维自用功能 通常完全没有校验，权限还很高 
// SSRF 防御的关键：先解析 IP 再校验，且必须锁住重定向
// 只校验字符串里有没有 "127.0.0.1" 是无效的：
//   DNS 可以把域名指向内网 IP、可以用十进制或八进制写法、
//   还可以用 302 跳转绕过（第一次是公网、跳转后是内网）
func safeHTTPClient() *http.Client {
    dialer := &net.Dialer{Timeout: 5 * time.Second}
    return &http.Client{
        Timeout: 10 * time.Second,
        // 关键点一：禁止跟随重定向，否则白名单在跳转后失效
        CheckRedirect: func(r *http.Request, via []*http.Request) error {
            return errors.New("redirect not allowed")
        },
        Transport: &http.Transport{
            // 关键点二：在真正连接前拿到解析后的 IP 再判断
            // 这样能防住 DNS rebinding（校验时是公网 IP，连接时变内网）
            DialContext: func(ctx context.Context, network, addr string) (net.Conn, error) {
                host, port, _ := net.SplitHostPort(addr)
                ips, err := net.DefaultResolver.LookupIPAddr(ctx, host)
                if err != nil {
                    return nil, err
                }
                for _, ip := range ips {
                    if isPrivateOrReserved(ip.IP) {
                        return nil, fmt.Errorf("blocked internal address: %s", ip.IP)
                    }
                }
                return dialer.DialContext(ctx, network, net.JoinHostPort(ips[0].IP.String(), port))
            },
        },
    }
}

// 必须全部拦掉的网段，漏一个就等于没防
func isPrivateOrReserved(ip net.IP) bool {
    if ip.IsLoopback() || ip.IsPrivate() || ip.IsLinkLocalUnicast() ||
        ip.IsUnspecified() || ip.IsMulticast() {
        return true
    }
    // 云元数据服务，最高危目标
    if ip.String() == "169.254.169.254" || ip.String() == "100.100.100.200" {
        return true
    }
    return false
}
⚠️
除了代码，还要动架构和云配置

① 协议只允许 http 和 https，明确拒绝 file://、gopher://、dict://；② 响应内容不要原样回显给调用方，否则等于给攻击者一个内网代理；③ 云上把实例元数据切到 IMDSv2（需要先 PUT 拿 token，简单 GET 拿不到凭证），这一条配置能挡掉绝大多数 SSRF 提权；④ 把需要外呼的服务放进独立的出网代理或单独安全组，从网络层面让它根本没有到内网的路由——这是最彻底的一层。

② 原理 · 文件上传：危险在「能被解释执行」

搞清上传漏洞的成因，能解决「扩展名都白名单了为什么还出事」——问题从来不在校验那一层，而在文件最终躺在哪。

文件上传漏洞的本质不是「上传了坏文件」，而是上传的文件落在了一个会解释执行它的位置。理解这一点，防御方向就很清楚了。

防御手段 挡住什么 单独用是否足够
扩展名白名单（不是黑名单） 大部分脚本文件 不够，还要看存储位置
校验文件真实类型（magic number） 改扩展名伪装 不够，图片马仍是合法图片
服务端重命名为随机值 + 丢弃原始路径 路径穿越、覆盖已有文件 必做项
存到对象存储或非 Web 目录 上传即执行 最关键的一层，有它前几层失效也不致命
独立域名 + 强制 Content-Disposition: attachment svg/html 造成的存储型 XSS、Cookie 同源窃取 必做项
限制大小、数量、频率 磁盘打满、上传型 DoS 容量与稳定性层面必做
图片二次渲染（重新编码输出） 图片马里嵌入的代码 高安全场景值得做，有 CPU 成本

② 原理 · 纵深防御：每一层该做什么

搞清每层的职责，能解决「这个防护到底该加在网关还是代码里」的反复争论，以及重复加了三遍仍有缺口的浪费。

没有任何单点措施能覆盖全部风险。合理的做法是每层各拦一部分，让单点失效不至于直接导致事故。

# 安全响应头一次配齐（放 http 块，全站生效）
# always 参数很重要：没有它，4xx/5xx 响应不会带上这些头
add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
add_header X-Content-Type-Options "nosniff" always;          # 禁止 MIME 嗅探
add_header X-Frame-Options "SAMEORIGIN" always;              # 防点击劫持（旧标准）
add_header Referrer-Policy "strict-origin-when-cross-origin" always;
add_header Permissions-Policy "camera=(), microphone=(), geolocation=()" always;
add_header Content-Security-Policy "default-src 'self'; script-src 'self'; frame-ancestors 'self'; object-src 'none'; base-uri 'self'" always;

# 别把版本号告诉攻击者，能省掉一轮针对性的漏洞匹配
server_tokens off;

# 请求体大小要按接口分别设，全站放大等于给上传型 DoS 开门
client_max_body_size 1m;
location /api/upload { client_max_body_size 20m; }
💡
这些头里只有两个真正有「防御」能力

CSP 和 HSTS 是有实际拦截能力的（限制脚本执行、强制加密信道），其余多数是「降低危害面」的辅助项。X-XSS-Protection 已被主流浏览器移除，别再配它；X-Frame-Options 在支持 CSP 的浏览器上已被 frame-ancestors 取代，但为兼容老浏览器通常两个都留。

注意 nginx 的 add_header 在子级 location 中一旦出现，会覆盖掉父级的全部 add_header，而不是合并——这个行为导致过很多「明明配了却没生效」的事故。子 location 里加头时，父级的头需要一并重写。

③ 场景 · 按投入产出排序的防御优先级

安全工作永远资源不足，所以顺序比清单更重要。下面按「单位投入能消除的风险量」从高到低排：

优先级 要做的事 为什么排这么前 成本
P0 全站 HTTPS + HSTS，证书到期监控 证书过期是最高频的低级生产事故，且明文传输让其他防御全部无意义 极低
P0 所有 SQL 走参数化查询，代码扫描禁止字符串拼接 SQL 一条规则根治一整类漏洞，可以用 lint 强制 低
P0 每个接口的授权校验（资源归属），写进接口模板 越权是数据泄露的头号原因，且自动化扫描基本扫不出来 中，但必须做
P0 密钥、Token 从代码库里彻底移除，改走密钥管理 代码库泄露是不可逆事故，Git 历史里的密钥会一直存在 中
P1 密码用 bcrypt / Argon2id 存储 库被拖走时决定损失是「有限」还是「全部账号沦陷」 低
P1 依赖漏洞扫描接入 CI，卡住高危 间接依赖是最大的未知风险面，人工完全跟不上 低
P1 上传文件存对象存储 + 独立域名 + 强制附件下载 一次配置消灭上传 getshell 和存储型 XSS 两类风险 低
P1 出站请求白名单 + 云元数据切 IMDSv2 SSRF 提权链的关键一环，配置改动即可 低
P2 CSP（从 report-only 起步逐步收紧） XSS 的兜底层，但老项目直接上会大面积报错，需要迭代 中到高
P2 审计日志 + 异常行为告警 不防攻击，但决定了事故的发现时间和能否复盘 中
P3 WAF、渗透测试、红蓝对抗 前面几层没做好时，这些基本是花钱买安慰 高 
# 依赖漏洞扫描：接 CI，让高危直接卡住流水线
# Node
npm audit --audit-level=high
# Python
pip-audit -r requirements.txt
# Go
govulncheck ./...
# 容器镜像（连基础镜像里的系统包一起扫）
trivy image --severity HIGH,CRITICAL myapp:latest
# 扫 Git 历史里的密钥 —— 删掉当前文件是不够的，历史里还在
gitleaks detect --source . --log-opts="--all"

③ 场景 · 什么规模该做到什么程度

上一节给的是顺序，这一节给的是边界：同一份清单，五个人的项目和跨团队的内网平台该停在不同的位置。做过头会把迭代速度吃掉，做不够则是在赌没人扫到你。

场景 该做到什么程度 为什么是这个程度 代价
个人项目 / MVP，单实例 HTTPS 加证书到期监控、SQL 全参数化、密码用 bcrypt 或 Argon2id、上传进对象存储、密钥出代码库 这五条对应的是全网自动化扫描器随手就能打穿的面，缺一条就等于公开挂号 一天以内，之后基本零维护
有真实用户、无敏感数据的 SaaS 加上每个接口的资源归属校验、依赖漏洞扫描进 CI、关键操作审计日志、CSP 先跑 Report-Only 这个阶段的损失主要来自越权翻别人数据和间接依赖漏洞，两者都扫不出来也传不开，但一出就是全量数据 一个迭代，主要成本在给所有接口补归属校验
涉及支付、实名、健康数据 再加 CSP 强制模式、敏感字段加密与展示脱敏、密钥托管与定期轮换、云侧最小权限、出站白名单 这里的损失不可逆也不可赔，且监管要求的是「能证明做了」，不是「确实做了」 持续投入，需要专人跟合规
多团队多服务的内网 服务间 mTLS 或请求签名、统一网关做认证、安全响应头集中下发、依赖与代码扫描做成流水线卡点 「内网默认可信」是横向移动的唯一前提，打掉它比加固每个服务便宜得多 需要平台团队，业务方要配合改调用方式
面向公网的文件 / 图片服务 独立域名、强制附件下载、图片二次渲染、大小与频率限制，全部做满 上传是唯一能把「任意字节」放进你自己域名下的入口，这里省一层就等于把前面所有层的效果清零 低，但要在架构上把它拆出主域
仅办公网可达的内部工具 认证、授权、审计三项照做，浏览器侧加固可降级 内部工具通常权限最高、校验最少，是打进来之后最好用的跳板 低，主要是别给它开「反正是内部的」特例
已出过事故或被监管关注 在上面基础上引入 WAF、渗透测试、集中日志与告警平台 这些手段提升的是发现与响应速度，不是防御强度；只有前面几层做完了，它们才有边际收益 高，且需要长期人力值守
⚠️
这篇不适用的地方

本篇只覆盖「应用自己能改的部分」。三类问题不在这里解：一是网络与主机层，比如安全组、堡垒机、内核加固，它们决定的是被打穿之后的活动范围；二是人和流程，权限审批、离职回收、供应商准入，绝大多数真实事故的起点在这里而不在代码里；三是业务风控，刷单、薅券、爬虫，这些请求每一个都「合法」，靠输入校验和输出编码一个都拦不住，要用规则引擎与行为模型。

几条相邻主题只给结论，不在本篇展开：认证授权要先想清楚设计视角（会话还是 Token、单点登录怎么落地），见 接口认证与鉴权；接口的版本与契约治理决定了老客户端能不能被安全地淘汰，见 API 设计；TLS 套件、证书加载与限流的具体配置落在网关上，见 Nginx 实践；把依赖扫描与密钥扫描做成发布卡点属于流水线设计，见 CI/CD；依赖与供应链（锁版本、私有仓库、历史密钥清理）见 版本控制与协作。

最容易踩的坑

❌
避坑清单
  • 在输入时统一转义存库：数据被污染，而且输出上下文不同需要的编码也不同。输入只校验，输出才编码。
  • 只做认证不做授权：登录用户把 URL 里的 id 改一下就看到别人的数据。每个接口都要校验「这个资源是不是当前用户的」。
  • 信任前端传来的价格、折扣、用户 ID、角色：这些必须在服务端从库里查，不能从请求里取。
  • 用黑名单过滤：无论是 SQL 关键字、脚本标签还是上传扩展名，黑名单的绕过面永远大于你能想到的。一律换白名单。
  • SSRF 只校验 URL 字符串：DNS 可指向内网、IP 可用十进制写法、302 跳转能绕过白名单。必须解析成 IP 后再判断，并禁止重定向。
  • 上传文件存在 Web 可解析目录：其他几层防御一旦失效就是直接 getshell。存对象存储、独立域名、强制附件下载。
  • 密钥硬编码进代码或配置文件：提交进 Git 之后就永久存在于历史里，删文件没用。用 gitleaks 扫一遍历史。
  • 报错堆栈直接返回给前端：框架版本、文件路径、SQL 语句全暴露，等于给攻击者一份地图。生产环境统一返回脱敏错误。
  • 登录失败提示区分「用户不存在」和「密码错误」：这让攻击者可以批量枚举有效账号。统一提示。
  • 日志里记了密码、完整卡号、Token：日志的访问权限通常远宽于数据库，这等于绕过了所有存储层加密。
  • 只在 nginx 子 location 里加 add_header：会覆盖掉父级全部 add_header 而不是合并，安全头静默失效。
  • 把 WAF 当成安全方案：它挡不住逻辑越权、DOM 型 XSS 和业务漏洞。它买的是修复时间。
