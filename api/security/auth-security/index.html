认证授权安全：密码哈希参数、会话与 JWT 陷阱、越权防护

🏷️ 认证安全

先把一个判断说在前面：绝大多数真实发生的安全事故不是「密码被破解」，而是授权环节漏了一层校验。认证做得再漂亮，只要某个接口忘了判断「这条数据是不是你的」，攻击者用一个完全合法的自有账号就能把别人的数据翻个遍。下面按认证、会话、令牌、授权、登录对抗、委托授权的顺序展开，每一节都给出参数量级和失效边界。

认证与授权：事故为什么集中在后者

认证（Authentication）回答「你是谁」，授权（Authorization）回答「你能做什么」。两者在代码里通常由不同层负责，也因此产生了责任空档：认证一般由统一的中间件或网关兜住，全站只有一份实现，容易做对；授权却散落在每一个业务接口内部，写一百个接口就有一百次漏判的机会。

❌
前端隐藏按钮不是授权

「这个删除按钮只对管理员显示」在安全上等于零。浏览器里的一切都是可修改的展示层，接口地址从打开开发者工具的网络面板就能抄走。判断权限的唯一有效位置是服务端在执行操作之前。同理，把资源 id 换成 UUID 只是让猜测变难，不构成授权——UUID 会在分享链接、导出文件、日志、第三方埋点里流出去，一旦泄露就和自增 id 没有区别。

密码存储：加盐的 SHA-256 仍然不合格

「加盐哈希」只解决了彩虹表问题，没解决速度问题。盐让攻击者无法一次性破解全库，但他仍然可以针对单个高价值账号离线暴力尝试，而通用哈希算法的设计目标恰恰是快。一张消费级显卡跑 SHA-256 的量级在每秒百亿次，八位小写字母加数字的口令空间约 2.8 万亿，单卡几分钟就能穷尽。

所以密码哈希必须换一类算法：专门设计成慢、并且难以用 GPU 或专用硬件并行加速的算法。判据是它是否「内存密集」——GPU 的算力优势建立在大量小核心之上，而每个核心可用的显存带宽有限，把单次计算的内存占用拉到几十兆字节，并行度就被压下来了。

调参有一个统一的目标：让服务端单次校验耗时落在 200 毫秒到 1 秒之间。低于这个区间等于没挡住离线爆破；高于这个区间，攻击者会拿你的登录接口当 CPU 炸弹用——每个请求逼服务端算一秒，几百个并发就能把机器打满，这是一个真实存在的拒绝服务面。因此登录接口必须同时有限流，两者是配套的。

// password.go —— Argon2id 为首选，bcrypt 用于存量兼容
package auth

import (
    "crypto/rand"
    "crypto/sha256"
    "encoding/base64"
    "fmt"

    "golang.org/x/crypto/argon2"
    "golang.org/x/crypto/bcrypt"
)

// Argon2id 参数。内存与时间可以互换，两组常见配置：
//   m = 19 MiB, t = 2, p = 1   资源受限环境的下限
//   m = 64 MiB, t = 3, p = 4   服务端算力允许时优先这组
// 上线前务必在目标机型上实测：目标是单次校验 200ms 到 1s。
const (
    argonMemory      = 64 * 1024 // 单位 KiB，即 64 MiB
    argonIterations  = 3
    argonParallelism = 4
    argonKeyLen      = 32
    argonSaltLen     = 16 // 128 位盐，足够避免碰撞
)

func HashPassword(plain string) (string, error) {
    salt := make([]byte, argonSaltLen)
    // 必须用 crypto/rand。math/rand 是可预测的伪随机，
    // 盐可预测会让攻击者重新获得批量破解的能力。
    if _, err := rand.Read(salt); err != nil {
        return "", err
    }
    key := argon2.IDKey([]byte(plain), salt,
        argonIterations, argonMemory, argonParallelism, argonKeyLen)

    // 把算法与参数一起存进字符串，这样将来调高参数时
    // 可以在用户下次登录成功的瞬间静默重算，不需要强制全员改密。
    return fmt.Sprintf("$argon2id$v=19$m=%d,t=%d,p=%d$%s$%s",
        argonMemory, argonIterations, argonParallelism,
        base64.RawStdEncoding.EncodeToString(salt),
        base64.RawStdEncoding.EncodeToString(key)), nil
}

// bcrypt 只处理密码的前 72 字节，多出来的部分被静默丢弃。
// 后果很具体：一个 80 字符的强口令，把最后 8 位改成任何内容都能登录成功。
// 用 passphrase 或把用户名拼进密码的实现最容易踩到。
// 解法是先压成固定长度：SHA-256 得到 32 字节，再 base64 成 44 字节。
// 必须 base64，因为原始摘要里可能出现 0x00，而 bcrypt 遇到 0x00 就截断。
func HashPasswordBcrypt(plain string) (string, error) {
    sum := sha256.Sum256([]byte(plain))
    pre := base64.StdEncoding.EncodeToString(sum[:]) // 固定 44 字节
    h, err := bcrypt.GenerateFromPassword([]byte(pre), 12) // cost 12 是当前合理下限
    return string(h), err
}

// 校验时顺手做升级：参数变更后无需通知用户。
func VerifyAndMaybeUpgrade(stored, plain string) (ok bool, newHash string) {
    ok = compareHash(stored, plain) // 内部按存储的算法标识分发，用常量时间比较
    if !ok {
        return false, ""
    }
    if needsRehash(stored) { // 算法过时或参数低于当前基线
        if h, err := HashPassword(plain); err == nil {
            newHash = h
        }
    }
    return true, newHash
}

胡椒（pepper）与密钥管理

盐随记录存库，胡椒是一份全局密钥，存在代码配置或 KMS 里而不入库。它的价值只在「数据库被拖走但配置没泄露」这一种场景下成立，成本是轮换困难：换胡椒意味着所有哈希失效，只能在用户下次登录时逐个迁移。实现上不要把胡椒直接拼进密码再哈希，而是对哈希结果做一次 HMAC，这样不受 bcrypt 的 72 字节限制影响。能上 KMS 或 HSM 的团队再考虑，否则优先把 Argon2id 参数调对。

会话管理：三个必须做的动作

会话安全有三件事最常被漏掉：Session ID 的随机性、登录成功后重新生成 ID、以及登出时在服务端真正销毁记录。中间那条对应会话固定攻击（Session Fixation）：攻击者先让受害者浏览器持有一个自己已知的 Session ID（通过带参数的链接、子域写 Cookie 或响应头注入），受害者随后正常登录，如果服务端沿用了这个 ID，攻击者手里那个 ID 就自动获得了登录态，全程不需要窃取任何东西。

// login.go —— 登录成功后的会话处理
func (h *Handler) Login(w http.ResponseWriter, r *http.Request) {
    started := time.Now()
    user, err := h.verifyCredentials(r.FormValue("username"), r.FormValue("password"))
    if err != nil {
        // 统一文案 + 统一耗时：既不区分「用户不存在」和「口令错误」，
        // 也不能因为用户不存在就提前返回，否则响应时间差本身就是枚举信号。
        h.padTo(started, 300*time.Millisecond)
        h.counter.Fail(r.FormValue("username"), clientIP(r))
        http.Error(w, "用户名或口令错误", http.StatusUnauthorized)
        return
    }

    // 关键一步：先销毁旧会话，再生成全新 ID，防会话固定攻击。
    // 注意是「新建记录」而不是「改写旧记录的用户字段」。
    _ = h.store.Destroy(r)
    sid, err := h.store.New(user.ID) // 内部用 crypto/rand 取 32 字节
    if err != nil {
        http.Error(w, "internal", http.StatusInternalServerError)
        return
    }

    http.SetCookie(w, &http.Cookie{
        Name:     "__Host-session", // 前缀强制 Secure、Path=/、禁止 Domain
        Value:    sid,
        Path:     "/",
        Secure:   true,
        HttpOnly: true,                    // 脚本读不到，XSS 无法直接外带凭证
        SameSite: http.SameSiteLaxMode,    // 挡住跨站的 POST
        MaxAge:   0,                       // 会话 Cookie，关浏览器即失效
    })
    // 绝对超时与空闲超时都记在服务端会话记录里，不依赖 Cookie 的过期时间，
    // 因为 Cookie 的 Max-Age 是客户端自觉遵守的，攻击者可以改。
    h.counter.Reset(user.Name, clientIP(r))
    h.audit(user.ID, "login", r)
}

JWT 的安全陷阱

JWT 的问题几乎全部来自一个设计：它把「用哪个算法验签」写在了由客户端提供的令牌头里。如果服务端照着这个字段选算法，攻击面就打开了。最经典的两种利用是 alg 设为 none，以及把 RS256 降级成 HS256 后拿公钥当 HMAC 密钥用。

「无法吊销」这条值得多说一句，因为它是用 JWT 换来无状态之后必然要付的代价。一旦签发，令牌在有效期内就是合法的，服务端没有任何记录可以撤销它。工程上的处理是把有效期压到 5 到 15 分钟，配一个长效刷新令牌，并且刷新令牌必须一次性轮换：每次刷新签发新的、作废旧的，如果检测到同一个刷新令牌被用了两次，说明它已经泄露，立即吊销整条令牌家族并强制重新登录。真正需要即时封禁的场景（风控拉黑、员工离职）必须落一份黑名单，这时你已经有状态了，就该重新评估当初选 JWT 的理由是否成立。

令牌放在哪里：没有全胜的选项

这个问题没有标准答案，它是在 XSS 风险和 CSRF 风险之间做交换。关键区别是：脚本能读走的凭证可以被带到攻击者自己的机器上离线重放，脚本读不到的凭证只能在受害者浏览器里被借用。前者的危害持续到令牌过期，后者随浏览器关闭结束。

推荐组合

访问令牌放 JS 内存变量、有效期 5 到 15 分钟；刷新令牌放 __Host- 前缀的 HttpOnly Secure SameSite=Lax Cookie，并且只对刷新接口这一个路径做 CSRF 防护。这样 XSS 拿不走刷新令牌，页面刷新可以静默续期，CSRF 的暴露面被收窄到单个接口。代价是需要实现刷新逻辑和并发请求的排队，多写几十行代码换掉一整类风险。

越权：需要逐接口审计的那一层

越权分两个方向。水平越权（IDOR）是同级用户之间的穿越，最典型的就是把 URL 里的 /orders/1024 改成 /orders/1025 看到别人的订单；垂直越权是低权限用户直接调用高权限接口。它们难被发现的共同原因是：工具不知道哪条数据本该属于谁，必须有业务语义才能判断。

批量接口越权批量导出或批量删除时只校验了第一条单条接口测试通过就以为批量接口也安全对集合中每一个 id 逐条校验，或用带归属条件的批量查询
字段级越权更新资料时顺便提交 role 或 is_admin后端直接把请求体绑定到实体对象用白名单 DTO，只允许绑定明确列出的字段
文件与对象越权直接访问对象存储的路径拿到他人文件鉴权只做在业务接口，没做在文件访问链路预签名 URL 加短有效期，或经业务接口代理并鉴权
// orders.go —— IDOR 的错误写法与正确写法
// 反例：只按主键查，归属校验靠后续代码「记得写」，一旦忘了就是漏洞。
//   row := db.QueryRow("SELECT id, amount, status FROM orders WHERE id = ?", orderID)
//
// 正解：把归属条件写进 WHERE。查不到就是查不到，不给「先取出再判断」留出漏判的机会。
// tenant_id 同样必须带上，多租户系统里跨租户越权比跨用户更致命。
const getOrder = `
    SELECT id, amount, status
    FROM orders
    WHERE id = ? AND tenant_id = ? AND owner_id = ?`

func (s *Service) CancelOrder(ctx context.Context, orderID int64) error {
    actor := auth.FromContext(ctx) // 用户身份只从会话或令牌推导，绝不接受请求参数里的 user_id

    var o Order
    err := s.db.QueryRowContext(ctx, getOrder, orderID, actor.TenantID, actor.UserID).
        Scan(&o.ID, &o.Amount, &o.Status)
    if errors.Is(err, sql.ErrNoRows) {
        // 这里返回 404 而不是 403。返回 403 等于告诉攻击者
        // 「这个 id 存在但不属于你」，可以被用来枚举资源规模与 id 分布。
        return ErrNotFound
    }
    if err != nil {
        return err
    }

    // 状态机校验与权限校验是两件事，都要做。
    if o.Status != StatusPending {
        return ErrConflict
    }

    // 写操作同样带全部归属条件，避免并发窗口内归属被改动。
    res, err := s.db.ExecContext(ctx,
        `UPDATE orders SET status = ? WHERE id = ? AND tenant_id = ? AND owner_id = ? AND status = ?`,
        StatusCancelled, orderID, actor.TenantID, actor.UserID, StatusPending)
    if err != nil {
        return err
    }
    if n, _ := res.RowsAffected(); n == 0 {
        return ErrConflict
    }

    s.audit(actor, "order.cancel", orderID) // 授权类操作必须留审计，事后才查得清
    return nil
}
💡
怎么系统性地消灭 IDOR

靠「每个接口都记得写校验」是不可靠的，人总会漏。有效的做法是把归属条件下沉到数据访问层：所有查询都强制经过一个带租户与用户上下文的 Repository，不提供裸的按主键查询方法；ORM 层面可以用全局过滤器或行级安全策略（PostgreSQL 的 RLS）兜底。再配一个回归测试模板：每个资源型接口都用「用户 A 的令牌访问用户 B 的资源」跑一遍，断言返回 404。这类测试很容易批量生成，收益远高于逐个人工审计。

登录接口的对抗：暴力破解、用户枚举与 MFA

登录是唯一一个攻击者可以无限次免费尝试的接口，防护要同时覆盖三件事：限制尝试速率、不泄露账号是否存在、以及给高价值账号加第二因素。

注册与找回口令接口同样统一文案与耗时加频率限制登录口堵住了，从这两个口子照样枚举

用户枚举常被当成低危问题忽略，但它是撞库的前置步骤：先确认哪些邮箱在你这里注册过，再拿这批账号去撞其他站泄露的口令库，命中率会高一个数量级。麻烦的是注册接口天然要告诉用户「该邮箱已被占用」，这条信息本身就是枚举通道。折中做法是注册时不直接回显占用状态，而是统一回复「验证邮件已发送」，把「此邮箱已注册，请直接登录」放进邮件正文。

第二因素方面，TOTP 的原理是双方共享一个密钥，各自用当前 Unix 时间除以 30 秒得到计数器，再做 HMAC-SHA1 并截断成 6 位数字。它不需要网络，也不怕短信劫持。实现上有三个必须处理的细节：允许前后各一个时间窗（容忍约 30 秒的时钟偏移，窗口开太大会线性放大爆破成功率）；记录已用过的计数器值，同一个 6 位码在窗口内不允许第二次使用，否则被中间人看到就能立即重放；恢复码必须像口令一样哈希存储，并且一次性使用。另外 6 位数字只有一百万种组合，TOTP 校验接口同样需要限流，否则窗口期内可以直接穷举。

OAuth2 委托授权：state 与 PKCE 各解决什么

这两个参数经常被一起提到，但防的是完全不同的攻击，不能互相替代。

state 防的是针对授权回调的 CSRF，也叫授权码注入：攻击者先用自己的账号走到一半，拿到一个属于他的授权码，然后构造回调链接诱导受害者点击。受害者的客户端拿这个码去换令牌，结果是受害者的账号被绑定到了攻击者的第三方身份上，之后攻击者就能用那个第三方账号登录受害者。state 是客户端生成并存在自己会话里的随机值，回调时必须比对一致，不一致直接丢弃。

PKCE 防的是授权码在传输途中被截获后被冒用。授权码要经过浏览器地址栏、App 的自定义 scheme 回调、可能还有中间件日志，这些位置都可能泄露；而公开客户端（SPA 和移动 App）没法安全保存 client_secret，光有码就能换令牌。PKCE 让客户端先生成一个随机的 code_verifier，把它的 SHA-256 摘要作为 code_challenge 发给授权服务器，换令牌时再出示原始 verifier。截获授权码的人拿不到 verifier，码就是废的。

### 第一步：跳转授权端点（为了可读性换行展示，实际是一行 URL）

    &client_id=spa-web
    &redirect_uri=https%3A%2F%2Fapp.example.com%2Fcallback
    &scope=openid%20profile
    &state=7f3a9c1e4b8d2f60
    &code_challenge=E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM
    &code_challenge_method=S256

上线前的自查清单

口令用 Argon2id 或 bcrypt cost 12 存储，并在目标机型上实测过单次校验耗时；登录成功后重新生成了 Session ID，登出在服务端删记录；JWT 校验写死了期望算法，并校验 exp、aud、iss；访问令牌短有效期，刷新令牌一次性轮换且检测重复使用；每个资源型接口都有「用户 A 访问用户 B 资源返回 404」的回归测试；登录失败按账号与 IP 双维度计数，失败文案与响应耗时统一；OAuth2 回调强制校验 state，公开客户端一律走 PKCE 的 S256。
