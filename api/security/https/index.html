HTTPS 部署工程实践：证书链、TLS 加固与续期监控

🏷️ HTTPS 加密

这篇不讲握手（对称与非对称加密、TLS 1.3 的 1-RTT 握手、证书如何证明身份，都在站内 HTTPS/TLS 深度原理 一篇里），只讲部署和运维阶段真正会让你半夜被叫起来的东西：证书链为什么在某些客户端校验失败、文件格式该配哪一个、TLS 版本与套件怎么选、HSTS 的哪个参数是不可逆的、混合内容怎么收尾、以及证书过期这种「最低级但最经典」的生产事故怎么用监控兜住。

部署视角的 HTTPS：四个互不相干的问题域

线上 HTTPS 出故障时，先定位它属于哪个域，能省掉大半时间。这四个域的排查手段、修复位置、生效时机完全不同：证书链问题改文件和 reload 即刻生效；协议与套件问题要考虑客户端兼容性；策略响应头问题有浏览器缓存，改了不会立即生效；生命周期问题只能靠自动化和监控。

证书链校验失败：缺中间证书是最高频的一种

最容易让人误判的故障：浏览器访问一切正常，但 curl 报 unable to get local issuer certificate，Java 客户端抛 PKIX path building failed，移动端 App 部分机型白屏。很多人会怀疑是客户端信任库太旧，其实九成情况是服务端漏发了中间证书。

原因在于校验路径的补全能力不同。信任链是「叶子 → 中间 CA → 根 CA」，只有根证书在客户端本地信任库里，中间证书必须由服务端在握手时一起发下来。浏览器有两个补救机制：缓存过去在别的站点见过的中间证书，以及按证书里的 AIA 扩展去下载缺失的中间证书。命令行与服务端语言的客户端基本都不做这两件事。

sequenceDiagram autonumber participant B as 浏览器 participant J as curl 或 Java 客户端 participant S as 服务器 只发了叶子证书 participant CA as 中间 CA 的 AIA 地址 B->>S: 建立连接 S-->>B: 只返回 1 张叶子证书 B->>B: 查本地缓存 命中之前访问其他站点缓存的中间证书 B->>CA: 若缓存未命中 按 AIA 扩展主动下载中间证书 CA-->>B: 返回中间证书 B->>B: 链补全 校验通过 显示小锁 J->>S: 建立连接 S-->>J: 同样只返回 1 张叶子证书 J->>J: 不查缓存 也不走 AIA J-->>J: 报错 unable to get local issuer certificate Note over B,J: 同一台服务器 浏览器正常 客户端全挂
这就是漏配 fullchain 的典型现象

❌
用浏览器验收 HTTPS 是不可靠的

因为浏览器会替你补全证书链，「我用 Chrome 打开是小锁，说明证书配好了」这个结论在工程上无效。验收必须用不做补全的客户端：openssl s_client 看服务端实际发了几张证书，再用 curl -v 走一遍。反过来也有一个坑：本机 curl 之前跑过 -k 或者系统装过公司根证书，也可能给出假阳性结果，所以最终验收应该在一台干净的机器或容器里做。

证书文件格式：nginx 到底要哪个文件

ACME 客户端签发完会在目录里丢下四五个文件，名字相似，配错就是上面那一串报错。核心只要记住一句：nginx 的 ssl_certificate 要的是「叶子 + 中间」拼在一起的 fullchain，顺序不能反，根证书不要放。

文件 / 格式内容谁会用到它配错的后果
cert.pem只有叶子证书一般不直接用配给 nginx 就是缺中间证书，命令行客户端全部报错
chain.pem只有中间 CA 证书OCSP Stapling 的 ssl_trusted_certificate当成证书配上去，nginx 直接启动失败
fullchain.pem叶子在前、中间在后nginx 的 ssl_certificate、Apache 2.4.8 以上顺序写反部分客户端会校验失败
privkey.pem私钥ssl_certificate_key权限过宽（如 644）等于把私钥交出去
PEM 格式Base64 文本，带 BEGIN CERTIFICATE 头nginx、Apache、大多数 Linux 服务把 DER 当 PEM 配会报无法解析
DER 格式二进制编码，常见后缀 .der 或 .cerJava 老工具、部分硬件设备需要 openssl x509 -inform der 转换
PKCS#12（.pfx / .p12）证书链加私钥打包，带口令Windows IIS、Java（转 JKS）导出时漏带中间证书，链依然不完整
✅
私钥权限与备份的硬性要求

私钥文件必须 chmod 600 且属主是启动进程的用户，绝不进 git（就算是私有仓库也不行，一旦进了历史就要重新签发）。容器化部署时私钥应该通过 Secret 挂载而不是打进镜像层，因为 docker history 和镜像仓库里的任何一层都能被拿到。另外注意：泄露的私钥无法靠「改权限」补救，只能吊销并重签。

用 openssl 实测：一套能直接抄的验收命令

下面这组命令覆盖了上线验收和故障定位的绝大多数场景。重点是 -servername：现在同一个 IP 上跑几十个域名是常态，不带 SNI 测出来的结果毫无意义，你拿到的可能是 default_server 的证书。

# 0) 变量：域名与端口
D=example.com

# 1) 看服务端到底发了几张证书（判断链是否完整的唯一可靠手段）
#    正常应该看到至少 2 张：叶子 + 中间。只有 1 张就是漏配 fullchain
openssl s_client -connect "$D:443" -servername "$D" -showcerts </dev/null 2>/dev/null \
  | grep -c "BEGIN CERTIFICATE"

# 2) 链的层级与校验结果：Verify return code 必须是 0 (ok)
openssl s_client -connect "$D:443" -servername "$D" </dev/null 2>/dev/null \
  | grep -E "depth=|Verify return code|subject=|issuer="

# 3) 有效期与剩余天数（线上实际返回的证书，而不是磁盘文件）
openssl s_client -connect "$D:443" -servername "$D" </dev/null 2>/dev/null \
  | openssl x509 -noout -dates -subject

# 4) SAN 列表：域名不在 SAN 里就会报 hostname mismatch（CN 已被现代客户端忽略）
openssl s_client -connect "$D:443" -servername "$D" </dev/null 2>/dev/null \
  | openssl x509 -noout -ext subjectAltName

# 5) 协议支持情况：1.0 / 1.1 应当失败，1.2 / 1.3 应当成功
for v in tls1 tls1_1 tls1_2 tls1_3; do
  printf '%-9s ' "$v"
  openssl s_client -connect "$D:443" -servername "$D" "-$v" </dev/null >/dev/null 2>&1 \
    && echo "支持（1.0/1.1 支持即为不合格）" || echo "不支持"
done

# 6) OCSP Stapling 是否生效：应出现 OCSP Response Status: successful
openssl s_client -connect "$D:443" -servername "$D" -status </dev/null 2>/dev/null \
  | grep -A 2 "OCSP response"

# 7) 校验私钥与证书是否配对（两个 modulus 的 md5 必须一致，否则 nginx 起不来）
openssl x509 -noout -modulus -in fullchain.pem | openssl md5
openssl rsa  -noout -modulus -in privkey.pem   | openssl md5

# 8) 本地文件的链校验：用中间证书作为 untrusted 一起校验
openssl verify -untrusted chain.pem cert.pem

TLS 版本与套件：该禁什么、该留什么

先纠正一个常见误解：在 nginx 里写一长串 ssl_ciphers 对 TLS 1.3 是无效的。1.3 的套件由 ssl_conf_command Ciphersuites 单独控制，而且 1.3 只保留了五个套件、全部强制前向保密与 AEAD，实际上不需要你调。ssl_ciphers 真正作用的对象是 TLS 1.2。

前向保密（ECDHE）的价值在于把「私钥泄露」和「历史流量被解密」解耦：静态 RSA 密钥交换下，攻击者只要抓存流量、日后拿到私钥就能解密全部历史会话；ECDHE 每次握手生成临时密钥，私钥只用于签名，历史流量无法回溯解密。这就是为什么必须禁掉所有非 ECDHE 的套件。

场景最低 TLS 版本套件策略代价与注意
纯内部服务 / 新系统TLS 1.3 only默认即可，无需配 ciphersJava 8 早期小版本、旧 OpenSSL 1.0.x 客户端连不上
面向公众的主流站点TLS 1.2 + 1.31.2 只留 ECDHE 加 AES-GCM 与 CHACHA20推荐基线，兼容性与安全的平衡点
必须兼容老旧终端TLS 1.2 + 1.3额外保留 ECDHE-RSA-AES128-SHA256 之类 CBC 套件CBC 套件有历史攻击面，要限期下线并记录例外
金融或合规要求TLS 1.2 + 1.3只留 AEAD，开启 HSTS 与证书透明度监控PCI DSS 明确要求禁用 TLS 1.0，1.1 也已被主流浏览器移除
已废弃TLS 1.0 / 1.1、SSLv3全部禁用存在即扣分项，扫描器会直接判不合格
# HTTP 站点：唯一职责是 301 跳转，不要在这里提供任何业务内容
server {
    listen 80;
    listen [::]:80;
    server_name example.com www.example.com;

    # ACME HTTP-01 校验路径要放行，否则自动续期会失败
    location /.well-known/acme-challenge/ { root /var/www/acme; }

    # 必须是 301 永久跳转：302 不会被浏览器长期记住，也不利于 SEO 权重传递
    location / { return 301 https://$host$request_uri; }
}

server {
    listen 443 ssl;
    listen [::]:443 ssl;
    http2 on;                      # nginx 1.25.1+ 的写法，旧版是 listen 443 ssl http2
    server_name example.com www.example.com;

    # 关键：fullchain 而不是 cert，否则命令行客户端会报找不到签发者
    ssl_certificate     /etc/letsencrypt/live/example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/example.com/privkey.pem;

    # 只留 1.2 与 1.3。ssl_ciphers 只对 1.2 生效，1.3 的套件由协议本身限定
    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_ciphers ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256:ECDHE-ECDSA-AES256-GCM-SHA384:ECDHE-RSA-AES256-GCM-SHA384:ECDHE-ECDSA-CHACHA20-POLY1305:ECDHE-RSA-CHACHA20-POLY1305;
    # TLS 1.3 下客户端优先更合理（移动端选 CHACHA20 更省电），1.2 建议服务端优先
    ssl_prefer_server_ciphers off;

    # 会话复用：降低握手开销。ticket 默认开启但密钥不轮转会削弱前向保密，建议关掉
    ssl_session_cache shared:SSL:10m;
    ssl_session_timeout 1d;
    ssl_session_tickets off;

    # OCSP Stapling：由服务端代取吊销状态，省掉客户端一次外部查询
    ssl_stapling on;
    ssl_stapling_verify on;
    ssl_trusted_certificate /etc/letsencrypt/live/example.com/chain.pem;
    resolver 1.1.1.1 8.8.8.8 valid=300s;
    resolver_timeout 5s;

    # HSTS：只在 HTTPS 响应里下发。always 保证 4xx/5xx 响应也带上这个头
    add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;

    root /var/www/html;
}

HSTS：唯一有「不可逆」风险的那个配置

HSTS 的作用是告诉浏览器「以后这个域名只准用 HTTPS」，从而消掉首次访问的明文跳转窗口（SSL Stripping 攻击面）。它的三个参数风险等级完全不同，preload 是全篇唯一一个「上线容易、下线极难」的配置。

参数含义典型值风险与回退成本
max-age浏览器记住强制 HTTPS 的秒数，每次访问会刷新上线观察期 300，稳定后 31536000（一年）可回退：改成 0 后老访客再访问一次即清除
includeSubDomains规则覆盖所有子域名，包括还没上 HTTPS 的确认全部子域名有证书后再加中等风险：内部测试子域、老旧系统会立刻打不开
preload申请进入浏览器内置列表，首次访问也强制 HTTPS只有长期稳定的主域才值得做几乎不可逆：列表编译进浏览器发行版，移除要等数月以上
下发位置只能在 HTTPS 响应里下发加 always 保证错误响应也带在 HTTP 响应里下发会被浏览器忽略，属无效配置

暂不开 HSTS"] B -->|没有| C["max-age=300 观察一周"] C --> D{"错误率与反馈是否正常"} D -->|异常| C1["改 max-age=0 回退
排查后重来"] D -->|正常| E["max-age=31536000"] E --> F{"全部子域名都有有效证书吗"} F -->|否| F1["不要加 includeSubDomains
先给子域名补证书"] F -->|是| G["加 includeSubDomains"] G --> H{"确定未来数年不需要回退 HTTP 吗"} H -->|不确定| H1["停在这一步
不提交 preload"] H -->|确定| I["提交 preload 列表

⚠️
preload 之前必须想清楚的两件事

第一，preload 列表的条目是编译进浏览器发行版的，提交移除申请后要等下一个大版本发布并逐步铺开，现实中通常是几个月量级，这期间无法让任何用户走 HTTP。第二，preload 要求必须带 includeSubDomains，意味着所有子域名——包括那台还在跑 HTTP 的内部 Jenkins、某个临时 demo 域名——都会被强制 HTTPS 而打不开。想撤销时的正确顺序是：先把响应头的 max-age 改成 0 让已访问过的用户尽快过期，再提交移除申请，然后长期等待。

混合内容与响应头加固的全景

页面本身是 HTTPS，却引用了 http:// 的资源，就是混合内容。浏览器分两类处理：脚本、样式、iframe、XHR 属于主动混合内容，直接拦截（因为它们能改写页面、窃取数据）；图片、音视频属于被动混合内容，现代浏览器也已改为默认自动升级或拦截。

响应头作用推荐值常见踩坑
Strict-Transport-Security强制后续访问走 HTTPSmax-age=31536000; includeSubDomains在 HTTP 响应里下发无效；preload 不可逆
CSP upgrade-insecure-requests把页面内 HTTP 子资源请求改写为 HTTPS迁移期开启，作为兜底目标域不支持 HTTPS 时请求直接失败，不会回落
CSP default-src 等限制资源加载来源，防 XSS 扩散先用 Content-Security-Policy-Report-Only 观察一上来就强策略必然打断内联脚本与第三方统计
X-Content-Type-Options禁止浏览器猜测 MIME 类型nosniff后端返回错误的 Content-Type 时资源会直接不加载，属预期
Referrer-Policy控制跳转时带出的来源信息strict-origin-when-cross-origin设成 no-referrer 会让第三方统计的来源分析失效
Permissions-Policy关闭不需要的浏览器能力camera=(), microphone=(), geolocation=()取代了已废弃的 Feature-Policy，语法不同不要混写
X-Frame-Options防点击劫持SAMEORIGIN已可由 CSP 的 frame-ancestors 取代，两者同时存在时后者优先
# 安全响应头基线：放进 snippet 后在各 server 块 include，避免各处漏配
# 注意 nginx 的 add_header 有继承陷阱：子 location 里一旦出现 add_header，
# 父级的所有 add_header 都会失效，所以要么统一在 server 级配置，要么在子块里重复 include
add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
add_header X-Content-Type-Options "nosniff" always;
add_header Referrer-Policy "strict-origin-when-cross-origin" always;
add_header Permissions-Policy "camera=(), microphone=(), geolocation=()" always;
add_header X-Frame-Options "SAMEORIGIN" always;

# 迁移期：先用 Report-Only 收集违规，确认不影响业务后再换成正式头
add_header Content-Security-Policy-Report-Only "default-src 'self'; img-src 'self' data: https:; script-src 'self'; style-src 'self' 'unsafe-inline'; upgrade-insecure-requests; report-uri /csp-report" always;

自动续期与到期监控：证书过期是最经典的低级事故

证书过期几乎是所有团队都踩过的事故，而且它的特点是故障范围 100%、无法灰度、只能靠提前发现。更常见的不是「忘了续」，而是「续了但没生效」：ACME 客户端成功写入了新文件，nginx 进程还拿着内存里的旧证书，直到过期那一刻全站白屏。

把上图翻译成工程动作就三件事：续期自动化、reload 自动化、监控看的是线上端口而不是磁盘文件。第三点最容易被忽略——检查 /etc/letsencrypt/live/ 下的文件有效期只能证明「续期成功」，证明不了「生效了」。

#!/usr/bin/env bash
# ---------- 1) 续期：把 reload 绑在 deploy-hook 上，只在真正续成功后执行 ----------
# --deploy-hook 只在证书实际更新后触发，比 --post-hook 每次都跑更合理
certbot renew --quiet \
  --deploy-hook 'nginx -t && systemctl reload nginx || echo "RELOAD FAILED" | logger -t certbot'

# acme.sh 的等价写法（--reloadcmd 同样只在续期成功后执行）
# acme.sh --install-cert -d example.com \
#   --key-file /etc/nginx/ssl/example.com.key \
#   --fullchain-file /etc/nginx/ssl/example.com.crt \
#   --reloadcmd "nginx -t && systemctl reload nginx"

# ---------- 2) 监控：检查线上端口实际返回的证书，而不是磁盘文件 ----------
check_cert() {
  local host="$1" port="${2:-443}" warn_days="${3:-21}"

  # 注意必须带 -servername，否则一机多域时拿到的是 default_server 的证书
  local pem
  pem=$(echo | openssl s_client -connect "${host}:${port}" -servername "$host" \
        -showcerts 2>/dev/null)

  # 链完整性：服务端应至少返回 2 张证书（叶子 + 中间）
  local n
  n=$(echo "$pem" | grep -c "BEGIN CERTIFICATE")
  if [ "$n" -lt 2 ]; then
    echo "CRITICAL $host 证书链不完整 只返回 ${n} 张证书 可能漏配 fullchain"
    return 2
  fi

  # 剩余天数
  local end_ts now_ts left
  end_ts=$(echo "$pem" | openssl x509 -noout -enddate | cut -d= -f2)
  end_ts=$(date -d "$end_ts" +%s 2>/dev/null || date -jf "%b %e %T %Y %Z" "$end_ts" +%s)
  now_ts=$(date +%s)
  left=$(( (end_ts - now_ts) / 86400 ))

  if   [ "$left" -lt 7 ]; then echo "CRITICAL $host 证书剩余 ${left} 天"; return 2
  elif [ "$left" -lt "$warn_days" ]; then echo "WARNING $host 证书剩余 ${left} 天"; return 1
  else echo "OK $host 证书剩余 ${left} 天 链含 ${n} 张证书"; return 0
  fi
}

# 所有对外域名都要检查，包括 API 域、CDN 回源域、内部网关
for d in example.com api.example.com cdn.example.com; do check_cert "$d"; done

证书有效期在持续变短，手工流程一定会崩

公共信任证书的最长有效期已从早年的 3 年压缩到 398 天，Let's Encrypt 一直是 90 天，行业方向是进一步缩短到 45 天甚至更短。这意味着任何「每年人工续一次、写在日历上」的流程都注定失败，必须做成自动化加监控。同时注意监控要覆盖容易被遗忘的对象：内部网关、CDN 回源证书、gRPC 服务的 mTLS 客户端证书、以及埋在某台老机器上的第三方回调域名。

吊销机制的现实局限

很多人以为「私钥泄露就吊销证书」是一个可靠的补救手段，实际上吊销在浏览器侧的执行效果相当弱。理解这点能帮你正确评估泄露事件的真实风险。

机制原理现实问题结论
CRL 吊销列表客户端下载 CA 的全量吊销名单文件可达数 MB，更新有延迟，移动端基本不用已基本退出浏览器场景
OCSP 在线查询客户端逐个向 CA 查询证书状态增加一次外部往返；查询失败普遍按软失败放行；且把访问行为暴露给 CA能被攻击者用阻断查询的方式绕过
OCSP Stapling服务端预取签名状态随握手一起发给客户端依赖服务端能出网访问 CA；配错 ssl_trusted_certificate 会静默不生效值得开，主要收益是性能与隐私
CRLite 等浏览器侧方案浏览器厂商聚合吊销信息下发覆盖范围与更新频率受厂商控制方向正确但不由你掌控
缩短有效期用 90 天甚至更短的证书压缩风险窗口要求续期必须完全自动化当前行业实际依赖的手段

所以私钥泄露的正确处置顺序是：立刻重签并替换（不要等吊销生效）、吊销旧证书、排查泄露路径、轮转所有可能一起泄露的凭证。把「吊销」当成主要防线是危险的。

上线前的五条最小验收

一是 openssl s_client -showcerts 返回至少两张证书且 Verify return code 为 0；二是 TLS 1.0 与 1.1 连接失败、1.2 与 1.3 成功；三是 curl -I http://域名 返回 301 并指向 HTTPS；四是 HTTPS 响应里有 HSTS 且在错误页上也存在（确认写了 always）；五是到期监控已经配好并人为压低阈值触发过一次真实告警。第五条最容易被跳过，而没演练过的告警等于没有告警。握手层面的原理与证书为什么能证明身份，见站内 HTTPS/TLS 深度原理；应用层的整体风险清单见 OWASP Top 10。
