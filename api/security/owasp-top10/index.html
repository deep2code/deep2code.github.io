OWASP Top 10 2021 风险清单与上线自查表

🏷️ OWASP Top 10

OWASP Top 10 不是漏洞列表，而是风险类别的统计排序。2021 版相比 2017 版最大的变化是把「注入」从第一位挤到第三位，权限控制失效升到 A01，并新增了 A04 不安全设计与 A08 软件和数据完整性失效。这个排序变化本身就说明了一件事：随着 ORM 和模板引擎普及，纯语法层面的注入已经被框架大面积消灭，剩下的高频风险都是「框架帮不了你」的业务逻辑和工程配置问题。

这篇按后端工程师的实际工作面组织：先给一张十项全景对照表，再挑工程上最高频、最容易在 code review 里漏过的五项深入展开，最后收在一张上线前自查清单和一组能直接跑的扫描命令上。

A01 权限控制失效：IDOR 是最高频的线上漏洞

先纠正一个流传很广的说法：「我们在网关统一做了鉴权，所以不存在越权问题」。这句话混淆了两件事。网关能回答的是「你是谁」（authentication），回答不了「这条数据是不是你的」（authorization 中的资源归属），因为归属关系只存在于业务数据库里。JWT 校验通过、角色也是普通用户，接口照样能把别人的订单返回给你，这就是 IDOR（不安全的直接对象引用），也是渗透测试里成本最低、成功率最高的一类攻击。

校验放在哪里典型写法为什么会失效结论
网关 / 鉴权中间件只校验 token 签名与角色不掌握数据归属关系，无法判断资源属主必要但不充分
请求参数前端传 user_id，服务端直接使用参数完全可篡改，等于把鉴权交给客户端严重错误
Service 层内存判断先按 ID 查出来，再在内存里比较属主能防住，但重构或新增查询路径时极易漏写，批量接口尤其容易可用但脆弱
SQL / ORM 查询条件WHERE id = ? AND user_id = ?基本不会被绕过，除非手写 SQL 绕开统一封装推荐
数据库行级安全PostgreSQL RLS，按 session 变量过滤需要连接池按用户设置变量，连接复用时容易串号多租户场景可选，成本较高

// 正例：把「资源归属」下推到 SQL，由数据库保证过滤
const qOrder = `SELECT id, user_id, amount, status
                FROM orders WHERE id = ? AND user_id = ? AND tenant_id = ?`

func (h *Handler) GetOrder(c *gin.Context) {
    // 身份只从服务端解析出的 token 取，绝不读 query 或 body 里的 user_id
    uid, tid := auth.UserIDFromCtx(c), auth.TenantIDFromCtx(c)
    id := c.Param("id")

    var o Order
    err := h.db.QueryRowContext(c, qOrder, id, uid, tid).
        Scan(&o.ID, &o.UserID, &o.Amount, &o.Status)

    // 关键：越权与不存在都返回 404。
    // 若越权返 403、不存在返 404，攻击者能靠状态码差异枚举出哪些 ID 真实存在
    if errors.Is(err, sql.ErrNoRows) {
        c.JSON(404, gin.H{"code": "NOT_FOUND"})
        return
    }
    if err != nil {
        // 不要把 err.Error() 直接返给前端，可能带库名表名
        log.Error("query order failed", "err", err, "order_id", id)
        c.JSON(500, gin.H{"code": "INTERNAL"})
        return
    }
    c.JSON(200, o)
}
⚠️
这个方案会在什么情况下失效

归属条件下推只能防住「按 ID 取单条」。真正容易漏的是三类场景：批量接口（前端传 ID 数组，服务端用 IN 查询却只校验了第一个）、导出与报表（走另一套 SQL，常由数据团队维护，完全没接鉴权上下文）、消息队列消费者（没有 HTTP 上下文，习惯性用管理员身份操作任意数据）。这三处建议在 DAO 层强制要求传入租户与用户上下文，缺失时直接报错退出，而不是默默放过。

A02 加密失败：不只是「没上 HTTPS」

2021 版把这项从「敏感数据泄露」改名为「加密机制失效」，是为了强调这是原因而不是结果。实际排查按四个维度看：存储是否加密、传输是否加密、算法是否还安全、密钥放在哪里。前三项容易查，最后一项最常出事——密钥硬编码在代码里、写在配置文件里提交进仓库、或者留在镜像层里被 docker history 翻出来。

❌
加盐的 SHA256 不等于安全

「加了盐就防彩虹表了」这句话没错，但它解决的不是主要问题。密码哈希的核心诉求是慢：bcrypt 在 cost=12 时单次计算约 250 毫秒量级，而 SHA256 是纳秒量级，两者抗离线爆破的能力差好几个数量级。盐只防批量预计算，不防针对单个用户的定向爆破。所以密码必须用专为此设计的慢哈希（bcrypt、scrypt、argon2id），而不是「通用哈希加点料」。HMAC-SHA256 的正确用途是盲索引和消息认证，不是存密码。

A05 安全配置错误：默认值就是攻击面

这一类的特点是代码完全正确，但环境把门开着。它也是唯一能靠自动化基线检查大面积消灭的一类。经验上最容易出事的是「开发环境的便利设置被带到生产」——调试开关、管理端点、宽松的跨域、详细错误页，在开发机上都是提效工具，进了生产就是入口。

// CORS 白名单：唯一正确的写法是精确匹配完整 Origin
var allowedOrigins = map[string]struct{}{
    "https://app.example.com":   {},
    "https://admin.example.com": {},
}

func CORS() gin.HandlerFunc {
    return func(c *gin.Context) {
        origin := c.GetHeader("Origin")
        if _, ok := allowedOrigins[origin]; ok {
            // 回显的是白名单里命中的那个值，而不是无条件回显请求头
            c.Header("Access-Control-Allow-Origin", origin)
            c.Header("Access-Control-Allow-Credentials", "true")
            c.Header("Access-Control-Allow-Headers", "Content-Type, Authorization")
            c.Header("Access-Control-Max-Age", "600") // 预检缓存 10 分钟，减少 OPTIONS
            // 带凭证时必须声明 Vary，否则 CDN 可能把 A 站的响应缓存给 B 站
            c.Header("Vary", "Origin")
        }
        if c.Request.Method == http.MethodOptions {
            c.AbortWithStatus(http.StatusNoContent)
            return
        }
        c.Next()
    }
}

A06 组件已知漏洞：间接依赖才是主要风险面

一个中型 Node 服务的 package.json 里可能只写了 30 个依赖，装完却有 900 多个包；Java 与 Go 稍好，但也是数倍关系。直接依赖通常只占依赖树的一到两成，剩下八成你从没听过名字，却和业务代码跑在同一个进程里。Log4Shell 影响面之所以巨大，正是因为绝大多数受影响的项目并没有直接声明 log4j-core。

# 依赖与制品安全扫描：可直接放进 CI 的 security 阶段
set -euo pipefail

# 1) 语言生态漏洞扫描：Go 走可达性分析，噪声最低
go install golang.org/x/vuln/cmd/govulncheck@latest
govulncheck ./...

# 2) 生成 SBOM 并归档。下次 CVE 披露时靠它在几分钟内查出哪些服务受影响
syft dir:. -o spdx-json > sbom.spdx.json

# 3) 拿 SBOM 直接查漏洞，避免重复解析依赖树；high 及以上直接失败
grype sbom:./sbom.spdx.json --fail-on high

# 4) 镜像扫描：--ignore-unfixed 过滤掉上游还没修的，避免噪声淹没结论
trivy image --severity HIGH,CRITICAL --ignore-unfixed --exit-code 1 "myapp:${GIT_SHA}"

# 5) 密钥泄露：扫全量历史，--redact 避免把密钥本身打进 CI 日志
gitleaks detect --source . --redact --exit-code 1

# 6) 基础镜像锁到 digest，避免同一个 tag 明天指向不同内容（供应链防护）
#    FROM gcr.io/distroless/static:nonroot@sha256:abcd1234...
✅
无法升级时的现实解法

经常遇到「漏洞在间接依赖里，上游中间那层迟迟不发版」。不用干等：Node 用 package.json 的 overrides、Yarn 用 resolutions、Go 用 go.mod 的 replace、Maven 用 dependencyManagement，都能强制把传递依赖提到安全版本，代价是可能破坏 API 兼容性，必须配合回归测试。真正卡死时，退一步评估可达性：如果漏洞函数在你的调用链里根本不可达，就记录豁免（写清评估结论和复查日期），而不是让扫描报告长期挂着几百条红色告警、最后所有人都不看了。

A09 日志与监控不足：该记什么、绝不记什么

这一项排在最后，但它决定的是「事故发生后你要多久才知道」。行业统计里从入侵到被发现的中位时间是以周为单位的，而不少团队最终是被外部通报才知道出事。工程上要同时解决两个相反方向的问题：该记的没记（登录失败、权限拒绝、敏感操作没有审计），以及不该记的记了（密码、token、卡号进了日志系统）。

类别必须记录绝对不能记录折中做法
认证登录成功与失败、来源 IP、User-Agent、失败原因分类明文密码、验证码原文只记「密码错误」这类枚举化原因，不记用户输入值
会话会话创建与吊销、异地与异设备登录完整 token 或 JWT 原文记 token 前 8 位加哈希指纹，足够串联排查
授权权限拒绝事件、被访问资源的类型与 ID——权限拒绝单独打点并配阈值告警，这是越权扫描最强的信号
支付与个人信息操作类型、操作人、时间、结果完整卡号、CVV、身份证号卡号只记后四位，证件号做掩码
请求体trace_id、接口路径、耗时、状态码无条件全量打印 request body按字段白名单打印，或对敏感键名自动掩码
变更配置与权限变更的前后值、操作人变更内容里夹带的密钥新值密钥类字段只记「已变更」与版本号

另一个被严重低估的问题是日志注入。只要把用户输入原样拼进单行文本日志，攻击者就能用回车换行在日志文件里伪造出一行看起来完全合法的系统日志，污染审计记录，甚至误导告警规则和分析平台。

sequenceDiagram autonumber participant A as 攻击者 participant APP as 应用 participant LOG as 日志文件 participant SIEM as 日志分析平台 A->>APP: 用户名填入正常值 后面接换行与一段伪造日志文本 APP->>LOG: 原样拼接写入一行 Note over LOG: 一次写入产生了两行
第二行看起来像系统自己打的日志 LOG->>SIEM: 按行采集与解析 SIEM-->>A: 审计链被污染 真实攻击被噪声淹没 Note over APP: 修复方向 写入前过滤 CR 与 LF
或改用 JSON 结构化日志由序列化器负责转义 
import logging, re, json

SENSITIVE_KEYS = {"password", "passwd", "token", "authorization",
                  "id_card", "card_no", "cvv", "secret", "private_key"}
# 控制字符集合：CR、LF 以及其他不可见字符
_CTRL = re.compile(r"[\r\n\x00-\x08\x0b\x0c\x0e-\x1f]")

def scrub(value):
    """递归脱敏并过滤控制字符，防止日志注入伪造出新的日志行"""
    if isinstance(value, dict):
        return {k: ("***" if k.lower() in SENSITIVE_KEYS else scrub(v))
                for k, v in value.items()}
    if isinstance(value, list):
        return [scrub(v) for v in value]
    if isinstance(value, str):
        # 关键一步：把 CR 与 LF 换成可见转义，攻击者就造不出「新的一行」
        # 顺带截断到 512 字符，避免超长输入把日志盘打满
        return _CTRL.sub(lambda m: "\\x%02x" % ord(m.group()), value)[:512]
    return value

def mask_phone(p: str) -> str:
    return p[:3] + "****" + p[-4:] if len(p) >= 7 else "***"

class JsonFormatter(logging.Formatter):
    def format(self, record):
        payload = {
            "ts": self.formatTime(record, "%Y-%m-%dT%H:%M:%S%z"),
            "level": record.levelname,
            "msg": scrub(record.getMessage()),
            "trace_id": getattr(record, "trace_id", "-"),
            "extra": scrub(getattr(record, "extra_fields", {})),
        }
        # JSON 序列化本身会转义换行，单条日志永远只占一行
        return json.dumps(payload, ensure_ascii=False)

其余四项的边界条件速查

A04、A07、A08、A10 在前面的全景表里已经列了检测与修复，这里只补充最容易被忽略的那一处。

类别最容易漏的那个点具体表现与修法
A04 不安全设计限流只做了「接口级 QPS」，没做「业务动作级次数」短信接口整体限流 1000 QPS 看起来很安全，但单个手机号可以被刷 500 条，因为没按手机号维度计数。限流键必须包含业务主体
A07 认证失效改密码或强制下线后，已签发的 JWT 仍然有效无状态 JWT 天生无法吊销。把口令版本号写进 token，校验时与库里的版本比对，不一致即拒绝；或把 access token 有效期压到 15 分钟以内
A08 完整性失效CI 流水线信任了未校验的外部脚本与浮动镜像 tag把远端脚本直接管道给 shell 执行、镜像用 latest，构建结果不可复现且可被上游替换。应锁 digest、校验签名、固定工具链版本
A10 SSRF只校验了 URL 字符串，没校验 DNS 解析结果，也没禁止重定向攻击者用解析到 127.0.0.1 的域名绕过字符串黑名单，或用 302 跳转到云元数据地址窃取临时凭证。必须在建连前校验解析后的 IP，并禁止跟随重定向

怎么用这份清单

不要指望一次做完十六项。按投入产出排，优先级最高的是第 1、4、7、11 四项：资源归属校验拦住最高频的数据泄露，密钥扫描拦住最不可逆的泄露，关闭调试端点砍掉最大的免费入口，依赖扫描把持续性风险变成自动化。这四项落地之后，把它们做成 CI 门禁而不是人工检查——任何依赖人记得去做的安全措施，半年后一定会失效。剩下的按业务敏感度逐步补齐。传输层与证书的部署加固见 HTTPS 与 CSP 一篇，TLS 握手与证书信任链的原理见站内 HTTPS/TLS 深度原理。
