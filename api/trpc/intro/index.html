tRPC 上手：Router、Context 与客户端调用

tRPC 的 API 面非常小，真正需要理解的只有三个服务端概念和一条客户端 link 链。这篇不讲它为什么能做到类型安全（那部分在 tRPC 的端到端类型安全），只讲怎么从零搭起一个能跑、能排查、错误结构统一的服务。

💡
这篇怎么读
  • ① 用法：一套能直接跑的最小骨架——context、initTRPC、router、适配器挂载、客户端调用，五段代码接起来就是一个可用服务，每步都给验证方法。
  • ② 原理：三件套的生命周期差异为什么决定性能与越权风险、transformer 与 errorFormatter 的取舍、link 链的组合规则、各适配器拿到的 context 不同、错误 code 到状态码的映射、中间件与 input 校验的真实顺序、createCaller 为什么不等于直接调 resolver。
  • ③ 场景：Express、Fastify、Next.js 两种路由、边缘运行时、WebSocket 各该怎么配，以及 transformer 与 batch 开不开的判断。

① 用法 · 最小可用：context、router、挂载与客户端调用

下面五段代码接起来就是一个能跑的服务。顺序是固定的：先有 context 类型，才能初始化 initTRPC；有了 t 才能定义 router；router 类型导出给客户端。每段的机制解释在下一节起的原理部分。

// ===== server/context.ts —— 每个请求执行一次，必须保持轻量 =====
import type { CreateExpressContextOptions } from '@trpc/server/adapters/express'
import { randomUUID } from 'node:crypto'
import DataLoader from 'dataloader'
import { db } from './db'          // 连接池在模块顶层创建，绝不放进 createContext
import { verifyJwt } from './auth'

export async function createContext({ req, res }: CreateExpressContextOptions) {
  // 只做解析，不查库：公开接口不该为鉴权付一次数据库往返
  const token = req.headers.authorization?.slice('Bearer '.length)
  const session = token ? await verifyJwt(token).catch(() => null) : null

  return {
    db,
    res,
    requestId: req.headers['x-request-id'] ?? randomUUID(),
    session,                       // 类型是 Session 或 null，收窄留给中间件做
    // DataLoader 必须是请求级的：进程级会跨请求缓存，导致用户 A 看到用户 B 的数据
    loaders: {
      userById: new DataLoader(async (ids: readonly string[]) => {
        const rows = await db.user.findMany({ where: { id: { in: [...ids] } } })
        const map = new Map(rows.map((r) => [r.id, r]))
        return ids.map((id) => map.get(id) ?? null)
      }),
    },
  }
}

export type Context = Awaited<ReturnType<typeof createContext>>
// ===== server/trpc.ts —— 进程级，只执行一次 =====
import { initTRPC } from '@trpc/server'
import type { Context } from './context'

// context 类型必须在这里绑定，之后所有 procedure 里的 ctx 才有类型
const t = initTRPC.context<Context>().create()

export const router = t.router
export const publicProcedure = t.procedure
export const middleware = t.middleware

// ===== server/routers/_app.ts —— router 只负责命名空间，不写业务逻辑 =====
import { z } from 'zod'
import { router, publicProcedure } from '../trpc'

const userRouter = router({
  byId: publicProcedure
    // 没有 input schema 就等于完全没有运行时校验，这一行不是可选项
    .input(z.object({ id: z.string().uuid() }))
    .query(({ ctx, input }) => ctx.loaders.userById.load(input.id)),
})

export const appRouter = router({
  user: userRouter,   // 客户端路径就是 user.byId
})

// 客户端唯一需要引用的东西：这一个类型
export type AppRouter = typeof appRouter

要做什么怎么做怎么验证它真的生效了
搭起最小服务按 context → trpc → router → 适配器的顺序写四个文件用上面第一条 curl 打通；返回 404 先查挂载前缀与客户端 url 是否一致
保证 context 轻量只解析 token，不在里面查库、不建连接池对比一个公开接口与一个鉴权接口的 P50：差距应该只出现在中间件之后
DataLoader 放对层在 createContext 内 new，绝不放模块顶层在批函数里打 requestId，同一个 loader 实例不应出现两个不同的 requestId
每个 procedure 都有 input逐个写 .input(zod schema)，在 CI 里加检查用第二条 curl 发畸形参数，必须得到 400 而不是 500 或空结果
只用类型导入客户端 import type { AppRouter }产物里搜数据库驱动名，必须搜不到；体积也不应因为接 tRPC 而明显变大
两端 transformer 一致服务端与客户端配同一个 transformer，或都不配返回一个 Date 字段，客户端 instanceof Date 应为 true；拿到字符串就是只配了一端
错误结构统一业务错误一律抛 TRPCError，并配 errorFormatter 补 requestId故意抛一个 FORBIDDEN：响应体里应有 data.code 与 requestId，且生产环境没有 stack
服务端内部复用SSR 与定时任务用 createCaller，并为每次调用单独构造 context传一个 session 为 null 的 context，鉴权 procedure 必须返回 UNAUTHORIZED——证明中间件确实被执行了
API / 选项作用默认值什么时候需要改
initTRPC.context<Ctx>().create()绑定 context 类型并生成 router、procedure、middleware不启用 transformer；默认 errorFormatter 会带 stack需要 Date/Map 保真时配 transformer；上生产必须改 errorFormatter
createContext构造请求级上下文每个 HTTP 请求执行一次；batch 下整批一次永远保持轻量；需要按 procedure 取数据时放中间件而不是这里
适配器的 endpoint / 挂载前缀决定 procedure 的 URL 路径无默认，必须与客户端 url 对齐换框架或换路由前缀时两端一起改
httpBatchLink 的 maxURLLength超长 URL 自动分批随版本不同，以所用版本文档为准链路上有老代理限制 URL 长度时显式设小
transformer（如 superjson）让 Date、Map、Set、undefined 跨 JSON 边界保真不启用确实需要非 JSON 原生类型时才开，两端必须一致
errorFormatter决定错误响应体结构默认结构含 stack生产环境去 stack、补 requestId、扁平化 zod 错误
createCaller进程内直接调用 procedure，完整执行中间件与校验context 要你自己构造SSR 预取、定时任务、集成测试；不要用它做 procedure 之间的互调
splitLink按条件把调用分流到不同 link不启用要区分慢接口与普通接口，或把 subscription 分到 WebSocket 时

② 原理 · 服务端三件套的生命周期差异

搞清这三层的执行次数，能解决「全站接口平白多一次数据库往返」和「偶发读到别人的数据」这两类问题。

几乎所有 tRPC 项目的服务端都是同一个骨架：一个全局的 initTRPC 实例、若干嵌套的 router、一个每请求执行一次的 createContext。三者的生命周期完全不同，混淆它们是新手最大的性能坑。

概念执行次数负责什么绝不该放什么
initTRPC.create()进程启动一次绑定 Context 类型、注册 transformer 与 errorFormatter任何和单个请求有关的状态
router 定义模块加载一次组织 procedure 的命名空间，决定客户端调用路径可变的全局变量（会被所有请求共享）
createContext每个 HTTP 请求一次（batch 下整批一次）解析会话、构造请求级 DataLoader、带上 requestId建连接池、查全量配置、无条件查用户表
middleware每个 procedure 调用一次认证、角色校验、日志、事务包裹资源归属级鉴权（要放 resolver）
resolver每个 procedure 调用一次业务逻辑与数据访问解析 token 这类每个接口都要做的事

transformer 与 errorFormatter"] end subgraph M["模块级 加载时构建"] TT --> BP["publicProcedure"] TT --> RT["appRouter 嵌套 userRouter postRouter"] end subgraph Q["请求级 每次请求新建"] CTX["createContext
session requestId dataloader"] end DB --> CTX RD --> CTX CTX --> MW["middleware 链"] BP --> MW RT --> MW MW --> RS["resolver 执行"]
❌
DataLoader 放错层会变成数据泄露

DataLoader 自带缓存，如果在模块顶层只建一个实例，它的缓存会跨请求生效：用户 A 请求过的记录会被用户 B 的请求命中，权限过滤全部失效。DataLoader 必须在 createContext 里 new，这是它唯一正确的位置。

② 原理 · transformer 与 errorFormatter 的取舍

搞清这两个选项，能解决「Date 字段莫名变成字符串」和「堆栈被发到浏览器」。

// server/trpc.ts 的完整版：把两个全局选项都配上
import { initTRPC, TRPCError } from '@trpc/server'
import { ZodError } from 'zod'
import superjson from 'superjson'
import type { Context } from './context'

const t = initTRPC.context<Context>().create({
  // transformer 让 Date、Map、Set、undefined 能跨 JSON 边界保真
  // 代价是客户端必须配同一个 transformer，否则反序列化对不上
  transformer: superjson,
  errorFormatter({ shape, error, ctx }) {
    return {
      ...shape,
      data: {
        ...shape.data,
        // 生产环境必须删掉 stack：它会暴露服务端目录结构和依赖版本
        stack: process.env.NODE_ENV === 'production' ? undefined : shape.data.stack,
        requestId: ctx?.requestId,
        // 把 zod 错误扁平化成字段到提示的映射，前端表单可以直接消费
        fieldErrors:
          error.cause instanceof ZodError ? error.cause.flatten().fieldErrors : null,
      },
      // 不要把内部错误原文透出去，数据库报错常含表名和 SQL
      message:
        error.code === 'INTERNAL_SERVER_ERROR' && process.env.NODE_ENV === 'production'
          ? '服务暂时不可用，请稍后重试'
          : shape.message,
    }
  },
})

export const router = t.router
export const publicProcedure = t.procedure
export const middleware = t.middleware

关于 transformer 有一个常被忽略的判断：它不是免费的。superjson 会把返回值遍历一遍并生成元数据，大数组响应上有可观开销。如果接口返回的都是字符串与数字，不配 transformer 反而更快；只有确实需要在前端拿到 Date 对象或 Map 时才值得开。而且服务端和客户端的 transformer 必须一致，只改一边会得到「字段全变成 undefined」这种极难定位的症状。

router 组织上还有一条经验值：嵌套层级控制在三层内。层级越深，类型推导的实例化量上升越快，表现是编辑器补全从毫秒级掉到秒级，tsc 也明显变慢。按业务域横向拆分比纵向嵌套划算。

② 原理 · 客户端 link 链的组合规则

搞清 link 链，能解决「慢接口拖慢整页」和「日志里看不到请求耗时」。

客户端只有两个概念：一个带 AppRouter 类型参数的 client，和一条 link 链。link 是可组合的中间件，从上到下依次处理请求，最末端必须是一个「终结型」link（真正发 HTTP 请求的那个）。

开发期打印请求与耗时"] B --> C{"splitLink 条件判断
是否慢接口或大响应"} C -->|是| D["httpLink
单请求 不合并"] C -->|否| E["httpBatchLink
同 tick 合并"] D --> F["fetch 发出 HTTP"] E --> F F --> G["响应经 transformer 反序列化"] G --> H["按 AppRouter 推导出的类型返回"] 
// 生产配置：在最小版本上加 loggerLink 与 splitLink
import { createTRPCClient, httpBatchLink, httpLink, splitLink, loggerLink } from '@trpc/client'
import superjson from 'superjson'
import type { AppRouter } from '../server/routers/_app'

export const trpc = createTRPCClient<AppRouter>({
  links: [
    loggerLink({ enabled: () => process.env.NODE_ENV === 'development' }),
    splitLink({
      // 明显慢的 procedure 不参与合并，避免拖慢同批的快查询
      condition: (op) => op.path.startsWith('report.'),
      true: httpLink({ url: '/trpc', transformer: superjson }),
      false: httpBatchLink({
        url: '/trpc',
        transformer: superjson,
        maxURLLength: 2083,          // 超长自动分批，兼容老代理的 URL 限制
        headers: () => ({ authorization: `Bearer ${getToken()}` }),
      }),
    }),
  ],
})

② 原理 · 适配器：挂到不同框架上的差异

搞清这张表，能解决「同一份 context 代码换个框架就编译不过」和「Next.js 里设不了 cookie」。

运行环境适配器createContext 收到什么要特别注意
ExpresscreateExpressMiddlewarereq 与 res（Node 原生）能直接写响应头与 cookie；body 解析中间件不要重复配
FastifyfastifyTRPCPluginFastify 的 req 与 res默认请求体上限约 1MB，上传类接口要调 bodyLimit
Next.js App RouterfetchRequestHandler标准 Request，没有 res设 cookie 必须通过返回的 Response；路由文件放 app/api/trpc/[trpc]/route.ts
Next.js Pages RoutercreateNextApiHandlerNextApiRequest 与 Response与老项目兼容好，但无法用 React Server Component 预取
Hono 或边缘运行时fetchRequestHandler标准 Request不能用 Node 专有 API，连接池要换成 HTTP 型数据库客户端
独立 WebSocket 服务applyWSSHandler建连时的 reqcontext 在连接建立时算一次，token 过期不会自动重算

最后一行是个真实的坑：WebSocket 上的 context 只在建连时计算一次，长连接跑了两小时后 ctx.session 里的 token 早就过期了，但 subscription 还在推数据。需要在订阅逻辑里定期重新校验会话，或者给连接设置最大存活时间强制客户端重连。

还有一个跨适配器的共性问题值得提前说：请求体大小限制与超时是由宿主框架和反向代理决定的，不是 tRPC 管的。上传类接口报 413、长耗时 procedure 被网关掐断，排查都要先看宿主框架与代理的配置，而不是去翻 tRPC 文档。可靠的做法是在 errorFormatter 里带上 requestId，同时把这个 id 写进服务端访问日志，这样一条报错能横跨网关、框架、tRPC 三层被串起来。代理侧的超时与请求体限制参数见站内 Nginx 实践。

② 原理 · 错误处理：code、状态码与统一结构

搞清这一节，能解决「前端拿到的全是 500 和中性文案，没法区分参数错还是服务挂了」。

tRPC 的错误模型只有一个入口：抛 TRPCError。适配器按内置映射表把 code 转成 HTTP 状态码，errorFormatter 决定响应体结构。任何不是 TRPCError 的异常都会被包成 INTERNAL_SERVER_ERROR，原始信息进日志但不返回给客户端。

TRPCError codeHTTP 状态码什么时候用客户端该怎么反应
BAD_REQUEST400参数不合法；input 校验失败会自动用这个展示字段级错误提示，不要重试
UNAUTHORIZED401没有身份或 token 失效跳登录，清本地会话
FORBIDDEN403身份有效但无权限提示无权限，不要跳登录
NOT_FOUND404资源不存在，也用于 procedure path 不存在展示空状态；若是 path 不存在说明版本不一致
CONFLICT409唯一约束冲突、乐观锁版本不符提示刷新后重试
PRECONDITION_FAILED412状态机前置条件不满足刷新当前实体状态
PAYLOAD_TOO_LARGE413请求体超限提示缩小内容，不要重试
TOO_MANY_REQUESTS429限流命中退避重试，读 Retry-After
CLIENT_CLOSED_REQUEST499客户端主动取消无需处理，不要计入错误率
INTERNAL_SERVER_ERROR500未捕获异常的兜底展示中性文案加 requestId

// 客户端错误收窄：只有先判断类型才能安全读 data.code
import { TRPCClientError } from '@trpc/client'
import type { AppRouter } from '../server/routers/_app'

function isTRPCError(err: unknown): err is TRPCClientError<AppRouter> {
  return err instanceof TRPCClientError
}

try {
  await trpc.post.create.mutate({ title: '' })
} catch (err) {
  if (!isTRPCError(err)) throw err                 // 网络层错误交给上层处理

  switch (err.data?.code) {
    case 'BAD_REQUEST':
      // errorFormatter 里补的 fieldErrors，这里可以直接填到表单上
      setFieldErrors(err.data.fieldErrors ?? {})
      break
    case 'UNAUTHORIZED':
      redirectToLogin()
      break
    case 'TOO_MANY_REQUESTS':
      toast('操作过于频繁，请稍后再试')
      break
    default:
      // requestId 让用户截图报错时能直接定位服务端日志
      toast(`${err.message}（追踪号 ${err.data?.requestId ?? '未知'}）`)
  }
}

② 原理 · 一次调用的完整链路

把上面的部件串起来。这张图里有一个反直觉的顺序值得单独记住：中间件在 input 校验之前执行，所以中间件里拿到的输入还没被 schema 验证过，不能假设它的结构。

② 原理 · 服务端内部调用与单元测试

搞清 createCaller 与直接调 resolver 的区别，能解决「测试全过但线上越权」和「日志里出现看起来重复的请求」。

有三类场景需要在服务端直接执行 procedure，而不是绕一圈发 HTTP 请求：服务端渲染时预取数据、定时任务复用已有业务逻辑、以及写测试。tRPC 为此提供了 createCaller，它接受一个 context 对象，返回一个与客户端形状完全一致、但直接在进程内调用的对象。它会完整执行中间件链与 input 校验，所以鉴权和参数规则不会被绕过，这一点和「直接调用 resolver 函数」有本质区别。

方式是否走 HTTP是否执行中间件与校验context 从哪来适合
HTTP 客户端是是适配器从请求构造浏览器、其他服务
createCaller否是你手动构造SSR 预取、定时任务、集成测试
直接调 resolver 函数否否不涉及不推荐，会绕过鉴权与校验
复用下沉的业务函数否不涉及不涉及逻辑抽成纯函数后最干净的复用方式

用 createCaller 写测试有个实际好处：构造 context 就等于构造身份。想验证「未登录应该返回 401」只要传一个 session 为 null 的 context，想测管理员分支就传一个 role 为 admin 的 context，不需要起 HTTP 服务、不需要造真实 token。代价是它拿不到真实的 req 与 res，任何依赖请求头或写 cookie 的逻辑都要在 context 里用假对象补上——这反过来说明了为什么不该在 resolver 里直接读 req，那会让业务逻辑绑死在 HTTP 上。测试组织方式见站内 测试工程。

还有一个容易忽略的点：SSR 里用 createCaller 预取时，不要跨请求复用同一个 context 实例。context 里通常挂着请求级的 DataLoader，跨请求复用会让缓存串到别的用户身上，症状和前面提到的 DataLoader 放错层完全一样，但更难发现，因为它只出现在服务端渲染这条路径上，本地单用户开发时永远复现不出来。

另外，createCaller 常被误用来在一个 procedure 里调另一个 procedure。能跑通，但代价是整条中间件链被重复执行一遍，鉴权、日志、事务都会被算两次，日志里还会出现看起来像重复请求的记录。procedure 之间的复用应该下沉到业务函数层：把逻辑写成接受明确参数的普通函数，两个 procedure 各自调用它，这样既没有重复开销，调用关系也是显式的。

最容易踩的坑

❌
避坑清单
  • 在 createContext 里做重 IO：它每个请求都跑一次，一次多余的查库会均摊到全站所有接口上。
  • DataLoader 建成进程级单例：缓存跨请求命中，直接导致越权读到他人数据，而且难以复现。
  • 把 AppRouter 写成值导入：服务端依赖被打进前端产物，体积暴涨甚至泄露服务端代码。
  • 只有一端配了 transformer：症状是 Date 变字符串、undefined 字段消失，抓包看不出明显错误，排查成本很高。
  • 忘记配 errorFormatter：默认错误体带 stack，把服务端目录结构和依赖版本发给浏览器。
  • 把内部错误原文返回给前端：数据库异常常包含表名和 SQL 片段，等于免费送上库结构。
  • 以为中间件在 input 校验之后执行：顺序相反，中间件里读输入必须自己做防御性判断。
  • 业务错误抛普通 Error：会被统一包成 500，前端无法区分「参数错」和「服务挂了」。
  • Fastify 下没调 bodyLimit：默认约 1MB，稍大的富文本提交就直接 413，且报错信息不指向 tRPC。
  • Next.js App Router 里想用 res 设 cookie：context 里只有标准 Request，没有 res，必须走返回的 Response。
  • WebSocket 的 context 只算一次：长连接上 token 过期后订阅仍在推送，需要定期重新校验会话。
  • router 层级嵌四五层：类型推导量指数上升，编辑器补全从毫秒级掉到秒级，还会显著拖慢 tsc。
  • 客户端 link 的 url 与服务端挂载前缀不一致：全部调用 404，而编译期完全没有提示。
  • 用 createCaller 在一个 procedure 里调另一个：整条中间件链被执行两遍，鉴权、日志、事务全部重复计数。
