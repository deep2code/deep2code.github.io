tRPC 的端到端类型安全：原理与适用边界

🏷️ tRPC

关于 tRPC 流传最广的一句介绍是「TypeScript 版的 RPC 框架」，这句话几乎每个词都会把人带偏。tRPC 没有定义任何新协议，网络上跑的就是普通的 HTTP POST 加 JSON；它也不做代码生成，没有 .proto、没有 schema 文件、没有 codegen 命令。它真正做的事只有一件：把 TypeScript 的类型系统本身当成前后端之间的契约。理解这一点，就能推导出它全部的优点和全部的限制。

💡
这篇怎么读
  • ① 用法：一张「这个项目适不适合 tRPC」的自查表——是否同仓或能共享类型包、调用方是否全是可控的 TS、是否要对外开放或被非 TS 消费、前后端能否同步发布，每条都给怎么确认和判定结论。
  • ② 原理：为什么这些条件是硬约束——类型只在编译期流动、传输层其实就是 HTTP 加 batch 合并、类型擦除后运行时防线只有 input schema、契约只有一份导致前后端部署耦合。
  • ③ 场景：与 GraphQL、REST 加 OpenAPI 生成、gRPC-web 的契约能力对照，适用与绝对不适用的场景清单，以及常见反模式的替代做法。

① 用法 · 先判断这个项目适不适合 tRPC

tRPC 的取舍几乎全在选型这一步决定，选对了后面很省事，选错了后面每个月都要还债。下面这张表按顺序过一遍，任何一条判定为「不满足」就不要在这条边界上用 tRPC。每条背后的机制在下一节起的原理部分。

自查项怎么确认不满足时的结论
前后端是否同仓，或能共享一个内部类型包在客户端目录下跑一次类型检查，看能不能解析到服务端导出的 AppRouter 类型不满足就不要用。跨仓库共享类型会变成「类型包版本」与「服务端部署版本」两条独立的线，编译通过而线上 400
所有调用方是否都是可控的 TypeScript 客户端列清楚未来两年会有哪些调用方：Web、小程序、Electron、移动原生、数据团队脚本出现 Python、Go、Java、iOS 原生等任何非 TS 调用方，这条边界就得另出一层 REST 或 OpenAPI
是否需要对第三方开放接口问一句「对方能不能引用我们的类型包，且接受我们随时改类型」需要开放就不要直接暴露 tRPC，在它之上加一层薄 REST 门面
是否需要长期并存的版本化契约看有没有「v1 与 v2 要同时在线半年」这类要求有就选 Protobuf 或 OpenAPI：tRPC 没有字段编号，也没有 deprecated 语义
前后端能否同步发布看部署流水线：前端产物和服务端是不是同一次发布上线不能同步也可以用，但只允许向后兼容的变更，并且必须做版本提示
接口是按用例设计还是按资源设计看现有接口命名：出现 getList、getListV2 这类就是 REST 习惯没转过来坚持资源建模的话 tRPC 的收益会大幅缩水，不如直接用 REST
团队能否守住「每个 procedure 必须有 input schema」看 CI 里有没有这条检查，而不是看规范文档里有没有写守不住就等于没有运行时校验，这是 tRPC 最危险的失守点

自查通过、决定要用之后，有三件事必须在第一个迭代里就落地，晚做的代价会越来越大：

要做什么怎么做怎么验证它真的生效了
类型只走编译期通道客户端一律用 import type 引用 AppRouter，不要值导入在构建产物里搜服务端依赖名（数据库客户端、密钥读取工具），必须搜不到；产物体积不应因为接了 tRPC 而明显变大
每个 procedure 都有 input schema在 CI 里遍历 router 检查 input 是否为空，而不是只写进规范文档故意提交一个没有 .input() 的 procedure，流水线必须失败
确认网关与观测链路认得它用 curl 直接打接口，确认路径、请求体、状态码都能被现有网关与 APM 处理batch 请求整体返回 200 时，监控里应仍能按 procedure path 看到单个失败，而不是一片绿
只允许向后兼容的线上变更新增字段必须可选；改名要两个字段并存一个发布周期；删 procedure 要留别名拿上一个版本的前端产物打新服务端，所有交互必须照常可用
慢接口不进 batch用 splitLink 按条件把慢 procedure 分流到不合并的链路观察首屏：一个慢查询不应再拖住同页其他区块的渲染
 
# 它就是 HTTP，可以直接 curl —— 这也是确认网关、WAF、APM 能否处理它的最快方式
# query 默认走 POST，也可以配成 GET（httpLink 的 methodOverride）
# 注意 input 在 GET 下是 URL 编码的 JSON，这是能利用 HTTP 缓存的唯一形态
curl 'http://localhost:3000/trpc/user.byId?input=%7B%22id%22%3A%2242%22%7D'

# mutation 一定是 POST，body 直接是 input
curl -X POST 'http://localhost:3000/trpc/post.create' \
  -H 'content-type: application/json' \
  -d '{"title":"hello","body":"world"}'

# batch 模式：URL 上用逗号连接多个 path，body 是以下标为键的对象
curl -X POST 'http://localhost:3000/trpc/user.byId,post.list?batch=1' \
  -H 'content-type: application/json' \
  -d '{"0":{"id":"42"},"1":{"cursor":null}}'

# 关键验证点：batch 下返回的是数组，整体 HTTP 状态码通常是 200
# 某个 procedure 失败只体现在对应数组元素的 error 字段里，按状态码做的告警会漏报
链路（link）选项作用默认行为什么时候需要改
httpBatchLink把同一事件循环 tick 内的多个调用合并成一个请求脚手架模板里通常是默认选择，合并开启页面里有明显慢的 procedure 时改用 splitLink 分流
httpLink一个调用一个请求，不合并不合并慢接口、需要独立超时或独立缓存策略的接口走它
splitLink按条件（path、操作类型）把调用分发到不同链路不启用要同时用 batch 与非 batch，或要把 subscription 分到 WebSocket 时
query 的 HTTP 方法决定能不能被 HTTP 缓存默认 POST公开且可缓存的列表数据改成 GET，并配 Cache-Control
output schema限定返回字段，防止 ORM 对象整个下发不声明即原样返回 resolver 的返回值返回值来自 ORM 或包含敏感字段时必须声明
errorFormatter决定错误结构里暴露什么默认结构可能带堆栈信息生产环境必须去掉 stack 与内部路径
subscription 的传输实时推送需要单独配 WebSocket 或 SSE 链路有实时需求时才引入，它的运维成本与 HTTP 完全不同

② 原理 · 类型是怎么从服务端流到客户端的

搞清这条通道，就知道为什么「能不能共享类型」是第一道硬门槛，也知道为什么写错 import 会把数据库驱动打进浏览器包。

传统的类型共享方案都要经过一次「序列化契约」：后端写 OpenAPI 或 proto，跑生成器，产出客户端代码。tRPC 把这一步整个删掉了，取而代之的是一行 export type AppRouter = typeof appRouter。服务端 router 的结构、每个 procedure 的 input schema 推导出的入参类型、resolver 返回值推导出的出参类型，全部编码在这个类型里。客户端 import type 它，再通过 createTRPCClient<AppRouter>() 把类型注入一个 Proxy 对象，你写 client.user.byId.query(...) 时，属性访问链会在运行期被拼成路径字符串 user.byId，而在编译期由 TS 逐级校验。

图里最关键的是中间那层：类型通道只存在于编译期。import type 是 TS 的纯类型导入语法，编译后整条 import 语句连同模块引用一起消失，所以前端产物里不会打进服务端代码，也不会因为 router 文件引用了数据库驱动而把驱动打进浏览器包。这也是 tRPC 唯一能成立的前提——如果你写成普通的值导入并且被打包器保留，就会把服务端依赖拖进前端包，这是新手最常见的构建体积事故。router 与 context 的具体写法见站内 tRPC 上手：Router、Context 与客户端调用。

② 原理 · 传输层真相：它就是 HTTP

搞清这一节，能解决「私有协议不好抓包、网关不认」这类评估期的顾虑，也能解释 batch 带来的木桶效应与告警失真。

tRPC 的 HTTP 适配器只做三件事：从 URL 取 procedure path、从 query string 或 body 取输入、把结果包成约定格式。用法层那几条 curl 命令就是全部真相。

⚠️
batching 的真实代价

合并请求省下的是连接数，付出的是「木桶效应」：一个 800ms 的报表查询和三个 20ms 的查询合并后，四块 UI 全都要等 800ms。同时因为整批返回 200，网关和 APM 按 HTTP 状态码统计的错误率会失真。明显慢的 procedure 应该单独走一条 httpLink（用 splitLink 按条件分流），并把监控打点下沉到 procedure path 粒度。

② 原理 · 类型安全的真实边界：编译期与运行期

搞清这条，能解决「端到端类型安全」这个名字带来的最大误解——它保护的不是你的服务端。

这是必须纠正的第一号错误认知。TypeScript 的类型在编译后被完全擦除，运行期不存在任何类型信息。tRPC 的类型安全保护的是「你自己写的调用代码」，不保护「服务端收到的数据」。服务端收到的永远只是一段 JSON，攻击者用 curl 想发什么就发什么。

能力光靠 TS 类型加了 input zod schema失守时的后果
阻止前端写错 procedure 名能能编译报错，无风险
阻止前端漏传字段能能编译报错，无风险
阻止 curl 发畸形请求体不能能resolver 收到 undefined，往下炸在数据库层
阻止字符串冒充数字 id不能能查询条件类型错误或全表扫描
阻止超长文本、越界分页不能能（加 max 与 clamp）内存打满或慢查询
阻止 resolver 意外返回密码哈希不能需要额外 output schema敏感字段泄露到前端
import { initTRPC, TRPCError } from '@trpc/server'
import { z } from 'zod'

const t = initTRPC.context<Ctx>().create()

// 反例：没有 input schema，类型看起来很安全，实际是完全敞开的
const badProcedure = t.procedure
  .query(({ input }) => {
    // input 的静态类型是 undefined，但运行期可能是任意 JSON
    // 如果这里强转再去查库，等于把查询参数的控制权交给调用方
    return db.user.findUnique({ where: { id: (input as any).id } })
  })

// 正例：input 是唯一的运行时防线，必须逐个 procedure 声明
const goodProcedure = t.procedure
  .input(z.object({
    id: z.string().uuid(),                                // 格式校验挡掉大部分畸形输入
    limit: z.number().int().min(1).max(100).default(20),  // 上界必须写，否则 limit 传十万会打穿库
  }))
  .output(z.object({                                      // output 可选，但能防止字段意外泄露
    id: z.string(),
    name: z.string(),
  }))
  .query(async ({ input }) => {
    const user = await db.user.findUnique({ where: { id: input.id } })
    if (!user) throw new TRPCError({ code: 'NOT_FOUND' })
    // 即使 user 上带着 passwordHash，output schema 也会把它剥掉
    return user
  })

关于 TS 类型只在编译期存在、跨越进程边界的数据必须做运行时校验，这套原则的完整推演详见站内 TypeScript。而 input schema 的常见写法、output 的取舍、中间件如何做类型收窄与鉴权，见站内 Procedure 设计：输入校验、中间件与鉴权。

② 原理 · 版本演进：前后端部署耦合是最大的运维约束

搞清这一节，能解决「本地一切正常，上线后老用户的提交按钮全部失效」这类事故。

gRPC 有字段编号，GraphQL 有 deprecated 标记，OpenAPI 有版本化 URL。tRPC 什么都没有——因为类型就是契约，而类型只有一份，服务端一改，「正确的调用方式」立刻变了。这在服务端到服务端的调用里问题不大（一起编译一起发），但客户端是浏览器时会立刻暴露：用户标签页里可能跑着几天前加载的旧 JS。

sequenceDiagram participant O as 旧客户端 浏览器里的旧 JS participant N as 新服务端 O->>N: post.create 传 title 与 body N->>N: 新 schema 要求 categoryId 必填 N-->>O: 400 BAD_REQUEST zod 校验失败 Note over O: 编译期完全发现不了
用户看到的是提交永远失败 O->>N: 请求头携带构建版本号 N-->>O: 响应头回传当前服务端版本 Note over O: 版本不一致就提示刷新
这是唯一可靠的兜底
变更类型旧客户端表现是否可以直接上线正确做法
input 新增可选字段正常可以默认值在服务端给
input 新增必填字段全部 400不可以先加可选并写默认值，下个版本再收紧
input 字段改名全部 400不可以两个字段并存一个发布周期
output 新增字段正常（多余字段被忽略）可以无需处理
output 删字段或改类型渲染出 undefined 或整页崩不可以先标记废弃，确认无调用后再删
删除或重命名 procedure404 NOT_FOUND不可以保留旧 path 作为转发别名
校验规则收紧（如 max 变小）部分请求 400谨慎先在日志里统计越界比例
// 客户端：把构建版本号带上，服务端回传线上版本，不一致就提示刷新
// 这是解决「旧标签页打不开新接口」的通用兜底，在 tRPC 下尤其必要
const BUILD_ID = import.meta.env.VITE_BUILD_ID ?? 'dev'

export const trpcClient = createTRPCClient<AppRouter>({
  links: [
    httpBatchLink({
      url: '/trpc',
      headers: () => ({ 'x-build-id': BUILD_ID }),
      // 包一层 fetch 才能读到响应头做版本比对
      fetch: async (input, init) => {
        const res = await fetch(input, init)
        const server = res.headers.get('x-build-id')
        if (server && server !== BUILD_ID) {
          // 不要直接 reload，那样会丢掉用户正在填的表单
          window.dispatchEvent(new CustomEvent('app:stale-version'))
        }
        return res
      },
    }),
  ],
})

③ 场景 · 与 GraphQL、OpenAPI 生成、gRPC-web 的对照

选型时真正要比的是契约能力，而不是性能——它们的传输层差异对业务几乎没有影响。

维度tRPCGraphQLREST + OpenAPI 生成gRPC-web
契约形式TS 类型（代码即契约）SDL schema，运行时可自省OpenAPI 文档（事后描述）proto 文件（编译期强约束）
是否需要代码生成不需要客户端类型通常要生成必须生成或手写必须生成
跨语言只支持 TS支持支持支持
版本演进机制无内建机制，靠纪律字段 deprecated 标记URL 或 header 版本号字段编号，规则最明确
运行时开销极低，JSON 加一层 Proxy解析与执行查询有成本极低需要 Envoy 类代理转换
浏览器可直连可以可以可以不可以，必须经代理
是否能被 HTTP 缓存仅 GET 形态的 query默认不能（POST 单端点）天然可以不能
心智成本落点几乎为零，会写函数就会用schema 设计与复杂度防护资源建模与文档同步工具链与构建流程

这张表最该带走的一句结论是：tRPC 省掉的是「维护契约文件加跑代码生成」这一步，代价是彻底失去语言无关性。它不是在跨语言这条赛道上赢了 gRPC，而是主动退出了这条赛道。评估时问自己一句「我未来两年会不会有非 TS 的调用方」，答案是「会」就别选它。REST 与 GraphQL 之间的取舍见站内 REST 与 GraphQL 的取舍，gRPC 那一侧的契约机制见站内 Protobuf 的编码与模式演进。

③ 场景 · 该用、不该用、以及反模式的替代做法

既然契约是 TS 类型，那么所有「拿不到这份类型」或「不认这份类型」的场景都直接出局。这不是生态成熟度问题，是机制决定的，不会随版本迭代改善。

场景该怎么做为什么代价
全栈 TS 的 monorepo、内部管理后台直接用，接口按用例设计调用方 100% 可控，改字段可以前后端一起改一起发低；但要在 CI 里守住 input schema 这条线
Next.js 这类前后端同构项目直接用，配合服务端渲染时的预取类型共享和部署同步天然成立低，见站内 Next.js 实践
给自家小程序或 Electron 客户端供接口可以用，但客户端发版慢，必须只做兼容变更客户端版本长期滞留，旧版本会一直打新服务端中，要做版本提示与兼容期管理
对第三方开放的 API不要直接暴露；在 tRPC 之上加一层薄 REST 门面，或用插件从 procedure 生成 OpenAPI第三方拿不到类型，也不接受你随时改类型多一层门面与一套文档，见站内 API 版本治理
有 Python 或 Go 数据团队要消费另出一层 HTTP 加 JSON 接口，或直接给数据出口TS 类型对非 TS 调用方等于没有契约要维护两套接口定义
iOS、Android 原生客户端用 REST 或 gRPC，不要让原生端去对齐 TS 类型原生端无法消费类型，且发版周期比 Web 长得多另一套契约与文档

最容易踩的坑

❌
避坑清单
  • 没有 input schema 的 procedure 等于没有校验：类型编译后全部擦除，服务端拿到的只是 JSON，必须靠 zod 兜住。
  • 把 AppRouter 当值导入而不是类型导入：会把服务端依赖拉进前端产物，前端包突然多出几百 KB，严重时泄露服务端代码。
  • 给 input 加必填字段后直接发布：旧标签页的请求全部 400，且编译期毫无提示，这是 tRPC 最常见的线上事故。
  • 删除或重命名 procedure 不留别名：旧客户端拿到 NOT_FOUND，表现是某个按钮永久失效而不是报错弹窗。
  • 整批 batch 返回 200 导致告警漏报：错误藏在响应数组元素里，必须在 errorFormatter 或链路层按 procedure path 单独打点。
  • 把慢查询和快查询放同一批：木桶效应让整页数据一起等最慢的那个，用 splitLink 分流。
  • 期待 tRPC 有版本管理能力：它没有字段编号也没有 deprecated 语义，兼容性完全靠团队纪律和 code review。
  • resolver 直接把 ORM 对象返回：这类对象常带 passwordHash、deletedAt 字段，不声明 output schema 就会整个下发。
  • 把 mutation 当 query 用：query 可能被 GET 缓存、被 React Query 预取和重试，副作用会重复执行。
  • errorFormatter 忘了在生产去掉 stack：默认错误结构里的堆栈会把文件路径和依赖版本暴露给浏览器。
  • 以为 tRPC 比 REST 更快：传输层完全一样，性能差异只来自 batch 减少了请求数，不是协议优势。
  • monorepo 里让前端 tsconfig 包含整个后端源码：类型检查时间会随后端代码量线性增长，编辑器补全变卡，应该用 project references 限定范围。
  • 选型时只看「开发效率高」一条：先把自查表里的调用方清单列完；两年内会出现非 TS 调用方的边界，一开始就别用它。
