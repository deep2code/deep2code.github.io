React 集成：查询缓存、失效与乐观更新

@trpc/react-query 这个包名已经把答案写出来了：tRPC 的 React 集成本质上是 TanStack Query 的一层类型化包装。它做的事就是把 trpc.user.byId.useQuery(input) 翻译成一个 useQuery({ queryKey: [['user','byId'], { input, type: 'query' }], queryFn })。所以这一篇几乎所有内容都不是 tRPC 特有的，你遇到的问题也基本都是 Query 缓存模型的问题——但正因为被包了一层，很多人从没读过 Query 的文档，于是踩遍所有坑。

缓存模型：queryKey、staleTime 与 gcTime

三个概念必须分清。queryKey 决定「这是不是同一份数据」，tRPC 自动用 procedure path 加输入生成，所以你几乎不用手写 key，但也因此要注意输入的稳定性。staleTime 决定「要不要重新发请求」，gcTime 决定「缓存条目什么时候被丢掉」——后两者经常被搞混，而它们的默认值组合恰好是「最容易产生冗余请求」的那一组。

参数默认值管什么设错的后果
staleTime0 毫秒数据多久后被视为过期保持默认时，任何重挂载或窗口聚焦都会重新请求，路由来回切几次就是十几个请求
gcTime5 分钟无订阅的缓存条目多久被回收设太小会让返回上一页时没有缓存可用，白屏一闪；设太大占内存但通常无害
refetchOnWindowFocustrue窗口重新聚焦时是否刷新过期数据配合 staleTime 为 0 时，每次切回标签页就全量刷新
refetchOnMounttrue组件挂载时是否刷新过期数据列表页与详情页来回跳会反复请求同一数据
refetchOnReconnecttrue网络恢复时是否刷新地铁里网络抖动会引发请求风暴
retry3 次，指数退避查询失败重试次数对 401、403、404 这类确定性错误重试是纯浪费，应按错误码短路
refetchIntervalfalse轮询间隔被当成实时方案时会产生持续的无效流量
// app/providers.tsx —— 全局默认值是收益最高的一处配置
import { QueryClient, QueryClientProvider } from '@tanstack/react-query'
import { TRPCClientError } from '@trpc/client'

const queryClient = new QueryClient({
  defaultOptions: {
    queries: {
      // 默认 0 是绝大多数重复请求的根源，30 秒是通用起点
      // 强实时性数据（余额、库存）单独在调用处覆盖为 0
      staleTime: 30_000,
      gcTime: 5 * 60_000,
      // 对确定性错误不重试：重试 401 只会多三次失败请求
      retry: (failureCount, error) => {
        if (error instanceof TRPCClientError) {
          const code = error.data?.code
          if (code === 'UNAUTHORIZED' || code === 'FORBIDDEN' || code === 'NOT_FOUND') return false
          if (code === 'BAD_REQUEST') return false
        }
        return failureCount < 2
      },
      // 表单页频繁切标签时不希望输入区被后台刷新打断
      refetchOnWindowFocus: true,
    },
    mutations: {
      // mutation 默认不重试，这是对的：写操作重试需要幂等保证
      retry: 0,
    },
  },
})

一条 query 的状态流转

stateDiagram-v2 [*] --> fetching: 组件首次挂载 fetching --> fresh: 请求成功 写入缓存并记时间戳 fetching --> failed: 请求失败 failed --> fetching: 按 retry 策略退避重试 failed --> [*]: 重试耗尽 交给 error 分支渲染 fresh --> stale: 超过 staleTime stale --> fetching: 窗口聚焦 组件重挂载 网络恢复 或手动失效 fresh --> inactive: 最后一个订阅组件卸载 stale --> inactive: 最后一个订阅组件卸载 inactive --> stale: 组件重新挂载 先返回旧数据再后台刷新 inactive --> [*]: 超过 gcTime 被回收 note right of stale stale 只表示可以刷新 不代表数据不能用 UI 依然渲染缓存里的值 end note

这张图里最该记住的是 inactive --> stale 这条边：重新挂载时组件会先拿到缓存里的旧数据立刻渲染，再在后台发请求。这就是为什么列表页返回时不会白屏，也是为什么很多人误以为「没发请求」——实际上请求发了，只是 UI 没有 loading 态。判断是否在后台刷新要看 isFetching 而不是 isLoading，后者只在没有任何缓存数据时为真。

失效：写操作之后最重要的一步

mutation 成功后服务端数据已经变了，但客户端缓存不会自己知道。trpc.useUtils() 返回的对象按 router 路径分层，可以在任意粒度上调用 invalidate()。失效范围的选择直接决定一次点击会引发几个请求。

⚠️
过度失效是最隐蔽的性能问题

写 utils.invalidate() 永远不会出功能 bug，所以它会在代码库里无声扩散。后果是一次点赞触发十几个请求，配合 httpBatchLink 合并后，其中任何一个慢 procedure 都会让整页数据一起卡住。审查时把「根失效」和「router 级失效」当成需要解释的写法，默认只允许精确失效。

乐观更新的完整正确写法

乐观更新有四个回调，缺任何一个都会留下一类问题：缺 onMutate 就没有即时反馈，缺 cancel 会让飞行中的旧请求覆盖你的乐观值，缺 onError 会让失败后的界面与服务端长期不一致，缺 onSettled 会让本地计算与服务端的细微差异永久留存。

回调职责漏掉的后果
onMutate 里的 cancel()取消同 key 的进行中请求飞行中的旧响应落地，把乐观值覆盖回旧数据，表现为「点了又跳回去」
onMutate 里的 getData()保存回滚快照并 returnonError 拿不到快照，无法回滚
onMutate 里的 setData()写入预期结果没有即时反馈，乐观更新本身失去意义
onError用快照回滚并提示请求失败但界面显示成功，用户以为改动已保存
onSettled无论成败都失效重拉本地推算的计数、排序、时间戳与服务端不一致且永不纠正
sequenceDiagram participant U as 用户 participant C as 组件 participant Q as Query 缓存 participant S as 服务端 U->>C: 点击点赞 C->>Q: onMutate cancel 同 key 的进行中请求 C->>Q: getData 保存快照 C->>Q: setData 写入 liked 为真 计数加一 Q-->>U: UI 立刻变化 无等待 C->>S: post.like mutate 发出 S-->>C: 失败 例如 409 或网络中断 C->>Q: onError 用快照 setData 回滚 Q-->>U: UI 恢复原状 并提示失败 C->>Q: onSettled 失效该 query Q->>S: 重新拉取 以服务端为最终真相 
function LikeButton({ postId }: { postId: string }) {
  const utils = trpc.useUtils()

  const like = trpc.post.like.useMutation({
    async onMutate({ id }) {
      // 1. 必须先取消：否则飞行中的旧请求返回后会覆盖乐观值
      await utils.post.byId.cancel({ id })

      // 2. 保存快照，它会作为 context 传给 onError 与 onSettled
      const previous = utils.post.byId.getData({ id })

      // 3. 写入预期结果，UI 立刻更新
      utils.post.byId.setData({ id }, (old) =>
        old ? { ...old, liked: true, likeCount: old.likeCount + 1 } : old,
      )

      return { previous }
    },
    onError(err, { id }, context) {
      // 4. 回滚。没有这一步，失败后界面会长期与服务端不一致
      if (context?.previous) utils.post.byId.setData({ id }, context.previous)
      toast.error('点赞失败，已撤销')
    },
    onSettled(_data, _err, { id }) {
      // 5. 无论成败都失效：本地推算的 likeCount 可能和服务端差几个并发点赞
      void utils.post.byId.invalidate({ id })
      // 列表里的点赞数也要同步，显式列出而不是用根失效
      void utils.post.list.invalidate()
    },
  })

  return <button onClick={() => like.mutate({ id: postId })} disabled={like.isPending}>点赞</button>
}

分页与无限滚动

服务端多取一条来判断有没有下一页，返回 nextCursor；客户端用 useInfiniteQuery 配 getNextPageParam 消费。这里必须用游标分页而不是 offset 分页：列表在翻页过程中有插入时，offset 会让同一条记录在两页里重复出现，也会漏掉记录。游标分页的必要性与实现细节见站内 API 设计最佳实践。

// 服务端：多取一条判断是否还有下一页
list: publicProcedure
  .input(z.object({
    cursor: z.string().uuid().nullish(),
    limit: z.number().int().min(1).max(50).default(20),
  }))
  .query(async ({ ctx, input }) => {
    const rows = await ctx.db.post.findMany({
      take: input.limit + 1,                       // 多取一条作为探针
      cursor: input.cursor ? { id: input.cursor } : undefined,
      skip: input.cursor ? 1 : 0,                  // 跳过游标本身，否则会重复
      orderBy: { id: 'desc' },                     // 排序字段必须唯一且有序
    })
    let nextCursor: string | null = null
    if (rows.length > input.limit) {
      nextCursor = rows.pop()!.id                  // 探针不返回给客户端，只用来给游标
    }
    return { items: rows, nextCursor }
  })

// 客户端
const { data, fetchNextPage, hasNextPage, isFetchingNextPage } =
  trpc.post.list.useInfiniteQuery(
    { limit: 20 },
    {
      getNextPageParam: (lastPage) => lastPage.nextCursor,
      // 无限列表的缓存很宝贵，返回时不希望从第一页重新开始
      staleTime: 60_000,
      gcTime: 10 * 60_000,
    },
  )

// 注意 data 是分页结构，渲染时要摊平；不要在渲染里每次新建数组做重计算
const items = useMemo(() => data?.pages.flatMap((p) => p.items) ?? [], [data])
❌
无限列表上不要用 invalidate

对 useInfiniteQuery 调失效会让已加载的所有页一起重新拉取：用户滚了十页，一次写操作就触发十个请求，并且滚动位置往往会跳。正确做法是用 setInfiniteData 精确修改目标那一页里的那一项，只有在列表结构发生变化（删除、重排）时才失效。

SSR 与预取

预取的价值是消掉「首屏白屏加转圈」。Next.js 下有两种形态：服务端组件里用 await 直接拿数据再 hydrate，或者在服务端发起预取把结果塞进 QueryClient 随 HTML 一起下发。

方案首屏表现代价适用
服务端预取加 hydration无 loading，数据随 HTML 到达HTML 体积增加，服务端要承担查询耗时首屏关键数据、SEO 需要的内容
客户端 prefetch（悬停时）点进去几乎瞬开可能预取用户最终没点的内容列表到详情的跳转
initialData无 loading不会被记为已获取，staleTime 过后仍会刷新；数据陈旧时会闪一下已经从别处拿到完整实体时
placeholderData先显示占位结构不写入缓存，仅当次渲染有效骨架屏式过渡
不预取白屏加转圈体验差，但实现最简单后台管理系统的非首屏页面

initialData 与 placeholderData 的区别是高频面试题也是高频 bug 源：initialData 会被真正写入缓存并被其他组件复用，placeholderData 不会。如果你手上的对象只是列表里的简化版（缺少详情字段），用 initialData 会把这个残缺对象污染进缓存，其他组件读到后可能直接崩在缺失字段上，这种情况必须用 placeholderData。

反模式对照

反模式后果正确做法
不设 staleTime冗余请求占请求总量一半以上全局 30 秒起步，强实时数据单独覆盖
mutation 后 utils.invalidate()一次写操作引发全页刷新显式列出受影响的两三个 query
乐观更新不写 onError失败后界面与服务端长期不一致onMutate 存快照，onError 回滚
乐观更新不写 onSettled本地推算的计数永远偏差无论成败都失效一次
把副作用放进 query被缓存跳过、被预取提前触发、被重试重复执行任何有副作用的都用 mutation
用 refetchInterval 做实时持续无效流量，延迟仍有一个轮询周期用 subscription，或至少按页面可见性暂停轮询

❌
最容易踩的坑
  • staleTime 保持默认 0：这是重复请求的头号原因，光调这一个参数常能砍掉一半请求。
  • 把 gcTime 当成 staleTime 用：改 gcTime 不会减少请求，只会影响缓存能不能复用。
  • mutation 后用根失效：功能永远正确，所以没人会去修，但一次点击就是十几个请求。
  • 乐观更新忘了 cancel()：飞行中的旧响应落地覆盖乐观值，表现是「点完变了又跳回去」。
  • 乐观更新没有回滚：失败后界面显示成功，用户离开页面前都不会发现改动没保存。
  • 对无限查询调 invalidate：已加载的十页会一起重拉，滚动位置丢失。
  • queryKey 里混入不稳定输入：每次渲染新建的对象让缓存永不命中，还会撑爆缓存条目数。
  • 用 isLoading 判断后台刷新：它只在没有任何缓存时为真，后台刷新要看 isFetching。
  • 慢接口和快接口共用一个 batch：整批耗时等于最慢那个，四块 UI 一起卡住。
  • 对 401、404 也重试三次：纯浪费，且会把用户卡在转圈里多等几秒。
  • 用 refetchInterval 当实时推送：流量持续消耗，延迟仍有一个周期，该用 subscription。
  • initialData 塞进列表里的简化对象：残缺实体被写入缓存并被详情页复用，直接崩在缺失字段上。
