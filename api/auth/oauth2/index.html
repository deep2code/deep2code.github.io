OAuth 2.0 与 OIDC 的协议细节

🏷️ OAuth2

OAuth 2.0 的接入门槛很低，跟着一份 SDK 文档抄二十行代码就能跑通第三方登录，这导致绝大多数人从没真正看过它的报文。而这个协议的所有坑都在参数层面：redirect_uri 怎么匹配、state 校验放在哪一步、code_verifier 和 code_challenge 是怎么绑定的、id_token 和 access_token 的受众为什么不同。这篇按报文把流程拆开讲，并把 OIDC 相对 OAuth2 增加的部分单独讲清。攻击面与危害范围（state 缺失、PKCE 绕过的具体利用）见站内 越权与鉴权安全，令牌格式与验签细节见站内 JWT 的结构与验签机制。

先纠正最根本的误解：OAuth2 是授权协议

OAuth 2.0 要解决的原始问题是：让第三方应用在不知道用户密码的前提下，代表用户访问用户在另一个服务上的资源。它的输出是一个访问令牌，语义是「某应用被允许在某范围内访问某资源」。它没有规定如何表达「用户是谁」，也没有规定应用如何确认用户已经完成认证。

于是把 OAuth2 当认证协议用会踩一个很隐蔽的陷阱：访问令牌的受众是资源服务器，不是你的应用。如果你的登录逻辑是「拿到 access_token，调一下接口能取到用户信息就认为登录成功」，那么一个在别处（比如另一个恶意应用）签发给同一个资源服务器的令牌也能通过这套逻辑，攻击者由此可以冒充任意用户登录。这正是 OIDC 存在的原因：id_token 的受众是你的客户端，并且带 nonce 与签名，专门用来回答「用户是谁」。

❌
把访问令牌当身份凭证是高危错误

判断方法很简单：如果你的登录流程里没有任何一步在校验「这份断言是签给我这个 client_id 的」，那么它就是可被令牌替换攻击的。OIDC 的做法是校验 id_token 的 aud 等于自己的 client_id、iss 等于预期签发方、nonce 等于本次流程存下的值。

四个角色与它们之间的信任关系

协议里有四个角色，把它们的信任方向理清，后面所有参数的作用都会变得自然：资源拥有者（用户）只信任授权服务器，因此认证必须发生在授权服务器的页面上而不是客户端的表单里；客户端不被信任，所以它拿到的是有范围限制的令牌而不是密码；资源服务器只信任授权服务器的签名或内省结果，不信任客户端的任何说法。

授权码模式：逐参数看报文

授权码模式是当前唯一推荐给用户登录场景的模式。它的核心设计是把浏览器能看到的东西和能换令牌的东西分开：浏览器只经手一个短命的、一次性的授权码，真正的令牌在客户端后端与令牌端点之间直接传输，浏览器完全接触不到。

# 1) 生成 PKCE 材料（code_verifier 43-128 字符，challenge 是它的 SHA-256）
VERIFIER=$(openssl rand -base64 60 | tr -d '\n=+/' | cut -c1-64)
CHALLENGE=$(printf '%s' "$VERIFIER" | openssl dgst -binary -sha256 | openssl base64 \
  | tr '+/' '-_' | tr -d '=\n')
STATE=$(openssl rand -hex 16)
# VERIFIER 与 STATE 必须存进服务端会话，不能只放在前端内存或 localStorage

# 2) 把用户重定向到授权端点（这一步由浏览器完成，这里只是把 URL 拼出来看）
echo "https://idp.example.com/authorize?response_type=code&client_id=web-app\
&redirect_uri=https%3A%2F%2Fapp.example.com%2Fcallback&scope=openid%20profile%20email\
&state=$STATE&code_challenge=$CHALLENGE&code_challenge_method=S256&nonce=$(openssl rand -hex 16)"

# 3) 回调拿到 code 后，在后端用 code 换令牌；redirect_uri 必须与上一步完全一致
curl -s -X POST https://idp.example.com/oauth2/token \
  -u "web-app:$CLIENT_SECRET" \
  -d grant_type=authorization_code \
  -d "code=$CODE" \
  -d "code_verifier=$VERIFIER" \
  -d 'redirect_uri=https://app.example.com/callback' \
  | jq '{token_type, expires_in, scope, has_id_token: (.id_token != null)}'
# 判读要点：
#   expires_in 一般 300-3600；拿不到 id_token 说明 scope 里漏了 openid，
#   此时你手上只有授权凭证没有身份断言，不能用于登录判断。
#   用同一个 code 再请求一次必须返回 invalid_grant，这是授权码一次性的验证方法。

其余授权模式与两个已废弃的模式

模式 流程特征 适用场景 状态
授权码 + PKCE 浏览器拿码，后端换令牌 Web 应用、SPA、原生 App，一切有用户参与的场景 唯一推荐
客户端凭证 客户端直接用自己的凭证换令牌，无用户参与 服务间调用、定时任务、后台数据同步 推荐（仅限机密客户端）
设备码 设备显示短码，用户在手机或电脑上输入并授权，设备轮询令牌端点 电视、机顶盒、CLI 工具、无浏览器设备 推荐用于输入受限设备
刷新令牌 用刷新令牌换新的访问令牌 延长登录态，配合轮换使用 推荐，但必须轮换
隐式模式 授权服务器直接在重定向片段里返回访问令牌 历史上给无后端的 SPA 用 已废弃，改用授权码加 PKCE
密码模式 客户端收集用户名密码，直接换令牌 历史上给自家一方应用用 已废弃

废弃的理由值得记住，因为它们解释了整个协议的设计意图。隐式模式把访问令牌放进重定向地址，令牌于是出现在浏览器历史里、可能被页面脚本读到、也可能通过 Referer 外泄；同时它没有后端参与，既无法安全使用客户端密钥，也拿不到刷新令牌，只能靠不断跳转续期。密码模式的问题更根本：它让客户端直接接触用户在授权服务器的凭证，这恰恰是 OAuth2 诞生要消灭的事情，一旦客户端被攻破，泄露的是密码本身而不只是令牌，而且它天然无法支持多因素与验证码这类交互式认证步骤。

PKCE：把授权码绑定到发起它的客户端

公开客户端（SPA、原生 App）无法保存 client_secret——代码可以被反编译、可以被查看源码，所以「用 code 加 secret 换令牌」这一层保护对它们不成立。此时如果授权码在回调链路上被截获（自定义 URL scheme 被同设备恶意应用抢注、日志或 Referer 泄露、中间人），截获者就能直接换到令牌。

PKCE 的机理是把一次性授权码和发起这次流程的那个客户端实例绑定：客户端先生成高熵随机串 code_verifier，把它的 SHA-256 摘要经 base64url 编码后作为 code_challenge 发到授权端点；授权服务器把 challenge 与授权码存在一起；换令牌时客户端必须提交原始 code_verifier，服务端重算哈希比对。截获授权码的人没有 verifier，而从 challenge 反推 verifier 在计算上不可行，所以码变成了废纸。

✅
PKCE 现在对所有客户端都推荐

包括有后端、能保管 client_secret 的机密客户端。理由是它防的不只是「secret 缺失」，还包括授权码被注入到另一个用户会话中的一类问题。实现成本是几行哈希代码，code_challenge_method 必须用 S256，plain 等于没做。

令牌类型、端点分工与 scope 设计

端点 谁来调 作用 注意
授权端点 浏览器（重定向） 用户认证与同意，返回授权码 必须走 HTTPS，且 redirect_uri 精确匹配
令牌端点 客户端后端 换取与刷新令牌 要做客户端认证与限流，是被爆破的主要目标
内省端点 资源服务器 查询不透明令牌是否有效及其元数据 必须加缓存，否则每请求多一次往返
撤销端点 客户端后端 登出时主动作废刷新令牌与访问令牌 登出只清本地会话不调它，等于令牌还活着
公钥端点 资源服务器与网关 发布验签公钥集合 缓存并设 TTL，配合密钥轮换
发现文档 客户端与资源服务器 一次性获取以上所有端点地址与支持的算法 启动时拉取并缓存，不要硬编码端点
维度 JWT 形态的访问令牌 不透明访问令牌
资源服务器校验方式 本地验签，零网络调用 调内省端点，一次网络往返
即时撤销 做不到，只能靠短有效期 天然支持，撤销后下次内省即失效
体积 数百字节到数 KB，每请求重传 几十字节
信息泄露面 payload 可被任何持有者解码 本身不含信息
对授权服务器的压力 仅公钥拉取 与业务调用量同阶，必须缓存
适用 内部微服务、高频接口 对外开放平台、需要随时断掉授权 
# 发现文档：一次拿到全部端点，避免把地址硬编码在各个服务里
curl -s https://idp.example.com/.well-known/openid-configuration \
  | jq '{issuer, authorization_endpoint, token_endpoint, introspection_endpoint,
         revocation_endpoint, jwks_uri, id_token_signing_alg_values_supported,
         code_challenge_methods_supported}'
# 判读要点：
#   code_challenge_methods_supported 里必须有 S256，没有就说明这家 IdP 不支持 PKCE；
#   issuer 的值要和你校验 id_token 时配置的 iss 完全一致，含尾部斜杠差异也不行。

# 不透明令牌的内省：资源服务器侧校验
curl -s -X POST https://idp.example.com/oauth2/introspect \
  -u "resource-server:$RS_SECRET" \
  -d "token=$ACCESS_TOKEN" | jq '{active, sub, scope, exp, client_id}'
# active 为 false 就必须拒绝；不要只看 HTTP 200 就放行，这是常见实现疏漏。
# 内省结果建议缓存 30-60 秒，兼顾撤销及时性与授权服务器负载。

# 登出时撤销刷新令牌，否则它在有效期内仍可继续换新令牌
curl -s -X POST https://idp.example.com/oauth2/revoke \
  -u "web-app:$CLIENT_SECRET" \
  -d "token=$REFRESH_TOKEN" -d 'token_type_hint=refresh_token' -o /dev/null -w '%{http_code}\n'
# 规范要求即使令牌不存在也返回 200，所以 200 不代表「刚才那个令牌确实存在过」。

scope 不等于权限。scope 表达的是「用户授予这个应用的能力范围」，而不是「这个用户有什么权限」。这两件事的区别在资源服务器上体现得最清楚：令牌带着 orders.read 只说明这个应用被允许读订单接口，它不说明可以读哪些订单。具体某条订单是否属于当前用户、当前用户在其所属租户里是否有查看权限，仍然必须由资源服务器自己判断。把 scope 当权限用的直接后果就是水平越权：换个订单 ID 就能读别人的数据，而令牌校验全程通过。越权的完整分类与防护见站内 越权与鉴权安全。

scope 粒度 示例 好处 代价
按资源加动作 orders.read 与 orders.write 语义清晰，最小授权好落地 数量随业务线性增长，同意页会很长
按业务域 orders 与 billing 同意页简洁，易于对外沟通 粒度粗，读写不分导致过度授权
按角色打包 merchant.basic 接入方省事 包内容一变所有接入方的实际权限都变，难以审计
OIDC 标准 scope openid 与 profile 与 email 跨 IdP 通用，字段语义标准化 只覆盖身份信息，业务范围仍需自定义

OIDC 在 OAuth2 上加了什么

能力 纯 OAuth 2.0 OIDC 增加的部分
身份断言 没有，只有访问令牌 id_token：JWT 格式，aud 是客户端自己，sub 是用户标识
用户信息 各家自定义接口，字段名五花八门 /userinfo 端点与标准化 claims（name、email、email_verified 等）
防重放 state 只防流程绑定 nonce 写入 id_token，客户端比对本次流程的值
端点发现 靠文档与人工配置 .well-known/openid-configuration 自动发现
认证上下文 无 auth_time、acr、amr：何时认证、认证强度、用了哪些因素
会话与登出 无 前端通道与后端通道登出规范（可靠性仍有限，见工程实践篇）

实践中最容易漏的是 amr 与 auth_time：做敏感操作二次确认时，你需要知道用户是多久以前认证的、有没有用第二因素，而不是简单地看「有没有登录」。email_verified 同理，见下一节。

接入第三方登录的实操清单

事项 具体做法 不做会怎样
回调地址注册 每个环境单独注册完整地址，精确匹配，不用通配也不带动态参数 配合开放重定向可导致授权码外泄
外部身份唯一键 用「提供方标识 + 提供方内用户 ID」做唯一键，与内部用户表一对多关联 用邮箱做键，用户换邮箱即身份错乱
账号合并策略 邮箱相同也不自动合并；要求先用原方式登录再绑定，或走邮箱验证 在弱验证的提供方注册同邮箱账号即可接管他人账号
首次登录信息补全 缺昵称、头像、手机号时走一次补全流程，并允许跳过 数据不完整导致后续业务分支到处判空
解绑保护 至少保留一种可登录方式，解绑最后一个身份源时强制先设置密码或绑手机 用户解绑后再也登不进来，只能走人工找回
提供方不可用降级 登录页明确提示某入口暂不可用，并保留其他入口 单一提供方故障导致全站无法登录
撤销通知处理 处理用户在提供方侧解除授权的回调或定期校验 用户以为已断开，你这边的绑定仍然有效

反模式与最容易踩的坑

反模式 后果 正确做法
用 OAuth2 当认证协议，不引入 OIDC 访问令牌被当身份凭证，可被令牌替换攻击冒充登录 用 id_token 并校验 iss、aud、nonce、签名
redirect_uri 用通配或前缀匹配 结合开放重定向把授权码送到攻击者手上 逐个精确注册，代码里也再校验一次
不校验 state，或只判断非空 用户被诱导完成攻击者发起的授权，账号被绑定到攻击者身份 与会话绑定存储、一次性使用、用完即删
client_secret 放在前端或移动端包里 等于公开，任何人都能冒充你的客户端换令牌 公开客户端不用 secret，改用 PKCE
访问令牌有效期设成数天 撤销无从生效，一次泄露长期可用 访问令牌分钟级，长期性交给刷新令牌
刷新令牌不轮换 泄露后可长期反复换新令牌且无从察觉 每次刷新换新，检测到旧令牌复用即作废整个令牌家族
直接信任第三方返回的邮箱做账号合并 在弱验证提供方注册同邮箱即可接管账号 检查 email_verified，并要求显式绑定确认
登出只清本地会话，不调撤销端点 刷新令牌仍然有效，别处仍可继续获取新访问令牌 登出时撤销刷新令牌，并清理服务端会话记录
❌
避坑清单
  • scope 里忘了 openid：整个流程照样成功，但不会返回 id_token，你手上只有授权凭证而没有身份断言。
  • 换令牌时的 redirect_uri 与授权请求那次不完全一致：包括尾部斜杠和端口，差一个字符就 invalid_grant。
  • iss 校验按包含或前缀写：尾部斜杠的差异是这类实现最常见的失败点，必须精确相等比较。
  • 把 state 存在浏览器 localStorage 里校验：攻击者能控制的存储没有校验价值，必须放服务端会话或用带签名的 Cookie。
  • code_challenge_method 用了 plain：等于把 verifier 明文发出去，PKCE 形同虚设。
  • 授权码重复兑换时没有作废已签发的令牌：这是识别授权码被截获的关键信号，白白丢掉。
  • 内省接口不缓存：业务量一上来，授权服务器先被自家资源服务器打挂。
  • 把 id_token 当访问令牌去调业务接口：它的受众是客户端，资源服务器正确实现时会拒绝，错误实现时会造成权限判断失据。
  • 设备码模式按固定间隔疯狂轮询：规范要求遵守 interval 并处理 slow_down，否则会被限流或封禁。
  • 同意页面的 scope 一次全要：用户同意率下降，且一旦令牌泄露影响面覆盖全部能力，应按需增量授权。
  • 回调处理函数没做失败分支：用户在授权页点了拒绝会带 error=access_denied 回来，不处理就白屏。
  • 多个环境共用一个 client_id 与回调地址：测试环境的一个配置失误会把生产的授权码引到测试域名上。
