OAuth 2.0 与 OIDC 的协议细节

🏷️ OAuth2

OAuth 2.0 的接入门槛很低，跟着一份 SDK 文档抄二十行代码就能跑通第三方登录，这导致绝大多数人从没真正看过它的报文。而这个协议的所有坑都在参数层面：redirect_uri 怎么匹配、state 校验放在哪一步、code_verifier 和 code_challenge 是怎么绑定的、id_token 和 access_token 的受众为什么不同。这篇按报文把流程拆开讲，并把 OIDC 相对 OAuth2 增加的部分单独讲清。攻击面与危害范围（state 缺失、PKCE 绕过的具体利用）见站内 越权与鉴权安全，令牌格式与验签细节见站内 JWT 的结构与验签机制。

  • ② 原理：为什么 OAuth2 不是认证协议、四个角色的信任方向、报文逐参数拆解、PKCE 把授权码绑定到客户端的机理、端点分工与 scope 不等于权限、OIDC 补上的身份层。

① 用法 · 授权码 + PKCE 的完整落地：每步参数与每步校验点

先把结论摆前面：有用户参与的登录，现在只有一种选择——授权码模式加 PKCE，且 code_challenge_method 必须是 S256。隐式模式（让授权服务器把访问令牌直接放进重定向地址）已不推荐，密码模式（客户端自己收集用户在授权服务器的密码）同样已废弃，两者的废弃理由见下文原理层。机密客户端也要用 PKCE，它多出的成本只有几行哈希代码。

下面这段是一条能直接跑起来的最小实现，重点不在「跳转过去」，而在回调回来之后那五个校验：少任何一个，流程都照样能登录成功，而安全性已经没有了。

// 授权码 + PKCE 的服务端落地（Express + jose）。公开客户端去掉 client_secret，其余完全一致
import crypto from 'node:crypto'
import { createRemoteJWKSet, jwtVerify } from 'jose'

const ISS = 'https://idp.example.com/'                  // 与发现文档的 issuer 完全一致，尾部斜杠也算
const CLIENT_ID = 'web-app'
const REDIRECT_URI = 'https://app.example.com/callback' // 与 IdP 注册值逐字符相同，含端口与斜杠
const JWKS = createRemoteJWKSet(new URL(ISS + '.well-known/jwks.json'))
const b64url = (b: Buffer) => b.toString('base64url')

app.get('/login', (req, res) => {
  const state = b64url(crypto.randomBytes(16))
  const nonce = b64url(crypto.randomBytes(16))
  const verifier = b64url(crypto.randomBytes(32))       // 编码后落在规范要求的 43 到 128 字符内
  const challenge = b64url(crypto.createHash('sha256').update(verifier).digest())
  // 三个值必须存服务端会话：放 localStorage 等于交给攻击者可控的存储保管
  req.session.oauth = { state, nonce, verifier, next: req.query.next ?? '/' }

  const u = new URL(ISS + 'authorize')
  u.searchParams.set('response_type', 'code')           // 写成 token 就退回已废弃的隐式模式
  u.searchParams.set('client_id', CLIENT_ID)
  u.searchParams.set('redirect_uri', REDIRECT_URI)
  u.searchParams.set('scope', 'openid profile email')   // 漏掉 openid 就拿不到 id_token
  u.searchParams.set('state', state)
  u.searchParams.set('nonce', nonce)
  u.searchParams.set('code_challenge', challenge)
  u.searchParams.set('code_challenge_method', 'S256')   // plain 等于没做 PKCE
  res.redirect(u.toString())
})

app.get('/callback', async (req, res) => {
  const saved = req.session.oauth
  delete req.session.oauth                              // 一次性：先删再校验，避免重放同一次回调
  if (!saved) return res.status(400).send('no flow')
  // 用户在授权页点了拒绝会带 error 回来，没有这个分支就是白屏
  if (req.query.error) return res.redirect('/login?denied=1')
  if (req.query.state !== saved.state) return res.status(400).send('state mismatch')

  const r = await fetch(ISS + 'oauth2/token', {
    method: 'POST',
    headers: {
      authorization: 'Basic ' + Buffer.from(CLIENT_ID + ':' + process.env.CLIENT_SECRET).toString('base64'),
      'content-type': 'application/x-www-form-urlencoded',
    },
    body: new URLSearchParams({
      grant_type: 'authorization_code',
      code: String(req.query.code),
      redirect_uri: REDIRECT_URI,                       // 必须与授权请求那次逐字符一致，否则 invalid_grant
      code_verifier: saved.verifier,                    // PKCE 的另一半，服务端重算哈希比对
      client_id: CLIENT_ID,
    }),
  })
  if (!r.ok) return res.status(502).send('token exchange failed')
  const tok = await r.json()

  // 身份判断只能用 id_token：access_token 的受众是资源服务器，拿它当身份凭证可被令牌替换
  const { payload } = await jwtVerify(tok.id_token, JWKS, {
    algorithms: ['RS256'],
    issuer: ISS,
    audience: CLIENT_ID,                                // 受众必须是自己的 client_id
    clockTolerance: '60s',
    requiredClaims: ['sub', 'exp', 'iat'],
  })
  if (payload.nonce !== saved.nonce) return res.status(400).send('nonce mismatch')

  // 外部身份唯一键 = 提供方标识 + 提供方内用户 ID；邮箱相同也不自动合并账号
  const user = await upsertIdentity({
    provider: 'idp',
    providerUid: String(payload.sub),
    email: payload.email as string | undefined,
    emailVerified: payload.email_verified === true,     // 未标记已验证的邮箱不能用于合并
  })
  await startSession(req, user, tok)                    // 建自己的会话，不要把 IdP 的令牌当会话凭证
  res.redirect(saved.next)
})
步骤 这一步发什么 这一步必须校验或确认什么
1 准备 生成 state、nonce、code_verifier，全部写入服务端会话 三者都来自密码学安全随机源；都不能放在浏览器可写的存储里
2 跳授权端点 response_type=code、client_id、redirect_uri、scope（含 openid）、state、nonce、code_challenge code_challenge_method 是 S256；redirect_uri 与注册值逐字符一致；敏感入口另加 prompt 与 max_age
3 用户认证与同意 全程在授权服务器页面完成 自己的页面里不得出现对方的账号密码输入框；原生 App 用系统浏览器而不是内嵌 WebView
4 回调 收到 code 与原样回传的 state，或收到 error state 与会话中存的值相等且用完即删；error=access_denied 必须有分支
5 换令牌 后端 POST 令牌端点：code、code_verifier、redirect_uri、客户端认证 redirect_uri 与第 2 步完全相同；用同一个 code 再换一次必须返回 invalid_grant
6 校验身份 验 id_token：签名、iss、aud、nonce、exp aud 等于自己的 client_id；nonce 等于本次流程存的值；iss 精确相等
7 建立本地会话 用内部不可变用户 ID 建自己的会话 外部身份键是「提供方 + 提供方内 UID」；邮箱相同不自动合并；未验证邮箱不参与合并
8 登出 调撤销端点作废刷新令牌，清本地会话，必要时再走 end_session_endpoint 只清本地会话等于令牌还活着；撤销端点即使令牌不存在也返回 200，不能据此判断令牌存在过
你的情况 该用哪种 grant 注意
有用户参与的登录：Web 应用、SPA、原生 App、桌面端 授权码 + PKCE（S256） 机密客户端同样要用 PKCE；公开客户端不配 client_secret
没有用户参与：服务间调用、定时任务、数据同步 客户端凭证模式 仅限能保密的机密客户端；令牌要缓存并提前 30 到 60 秒续取，别每个业务请求换一次
输入受限设备：电视、机顶盒、CLI 工具 设备码模式 轮询必须遵守返回的 interval 并处理 slow_down，否则会被限流
要延长登录态，减少反复跳转 刷新令牌，且必须轮换 检测到旧刷新令牌被复用就作废整个令牌家族；并发刷新问题见本簇工程实践篇
纯前端应用，没有任何后端 仍然是授权码 + PKCE；更稳的做法是加一个 BFF 代持令牌 不要用隐式模式；令牌放在前端时，无论存哪里都在 XSS 的影响范围内
自家 App 想直接收用户名密码「省一步跳转」 不要这么做，密码模式已废弃 它让客户端接触用户在 IdP 的凭证，且无法支持多因素与验证码这类交互步骤
对接企业客户的身份提供方 OIDC 授权码；只支持 SAML 的客户走独立适配层 内部只认一种协议，别让 XML 断言校验渗进业务代码
参数或配置 作用 默认值 什么时候必须改
code_challenge_method PKCE 的哈希方法 规范同时允许 plain 与 S256，各家 IdP 的默认与支持情况以发现文档的 code_challenge_methods_supported 为准 一律显式传 S256；文档里没有 S256 说明这家不支持 PKCE
state 的存储位置与生命周期 把回调绑定到本次流程与本次会话 无默认行为，完全取决于实现 一律放服务端会话或带签名的临时 Cookie，一次性使用、用完即删
scope 申请的授权范围 无默认；不含 openid 时不会返回 id_token 登录场景必须含 openid；其余按需增量授权，不要一次全要
prompt 与 max_age 控制是否强制重新认证、可接受的认证时效 不传即沿用 IdP 侧现有会话静默通过 改密、改绑、提现等敏感操作前必须传，并结合 auth_time 判断
访问令牌有效期 撤销无法生效的窗口 由授权服务器决定，以令牌响应里的 expires_in 为准 压到分钟级；长期性交给刷新令牌
刷新令牌轮换 每次刷新换新并检测复用 部分授权服务器默认不轮换 一律开启；同时给并发刷新留 10 到 30 秒宽限期
内省结果缓存 降低不透明令牌校验对授权服务器的压力 无默认，不加就是每请求一次往返 缓存 30 到 60 秒，兼顾撤销及时性与负载
发现文档缓存 端点地址与支持的算法列表 无默认 启动时拉取并定期刷新，不要把端点硬编码到各个服务里

② 原理 · 先纠正最根本的误解：OAuth2 是授权协议

搞清这一点，能解决一类很隐蔽的高危实现：登录流程全程通过，却从未验证「这份断言是签给我的」。

OAuth 2.0 要解决的原始问题是：让第三方应用在不知道用户密码的前提下，代表用户访问用户在另一个服务上的资源。它的输出是一个访问令牌，语义是「某应用被允许在某范围内访问某资源」。它没有规定如何表达「用户是谁」，也没有规定应用如何确认用户已经完成认证。

于是把 OAuth2 当认证协议用会踩一个很隐蔽的陷阱：访问令牌的受众是资源服务器，不是你的应用。如果你的登录逻辑是「拿到 access_token，调一下接口能取到用户信息就认为登录成功」，那么一个在别处（比如另一个恶意应用）签发给同一个资源服务器的令牌也能通过这套逻辑，攻击者由此可以冒充任意用户登录。这正是 OIDC 存在的原因：id_token 的受众是你的客户端，并且带 nonce 与签名，专门用来回答「用户是谁」。

❌
把访问令牌当身份凭证是高危错误

判断方法很简单：如果你的登录流程里没有任何一步在校验「这份断言是签给我这个 client_id 的」，那么它就是可被令牌替换攻击的。OIDC 的做法是校验 id_token 的 aud 等于自己的 client_id、iss 等于预期签发方、nonce 等于本次流程存下的值。

② 原理 · 四个角色与它们之间的信任关系

把信任方向理顺，后面每个参数的存在理由都会变得自然，也就不需要死记清单。

协议里有四个角色，把它们的信任方向理清，后面所有参数的作用都会变得自然：资源拥有者（用户）只信任授权服务器，因此认证必须发生在授权服务器的页面上而不是客户端的表单里；客户端不被信任，所以它拿到的是有范围限制的令牌而不是密码；资源服务器只信任授权服务器的签名或内省结果，不信任客户端的任何说法。

② 原理 · 授权码模式：逐参数看报文

搞清报文往返，能解决排查阶段最常见的两类失败：invalid_grant 到底是哪一步不一致，以及授权码被重复兑换意味着什么。

授权码模式是当前唯一推荐给用户登录场景的模式。它的核心设计是把浏览器能看到的东西和能换令牌的东西分开：浏览器只经手一个短命的、一次性的授权码，真正的令牌在客户端后端与令牌端点之间直接传输，浏览器完全接触不到。

sequenceDiagram participant B as 浏览器 participant C as 客户端后端 participant A as 授权服务器 participant R as 资源服务器 C->>C: 生成 state 与 code_verifier 存入会话 C-->>B: 302 跳转授权端点 带 client_id redirect_uri scope state code_challenge B->>A: 打开授权页 A->>B: 要求登录并展示同意页 B->>A: 用户完成认证并同意授权 A-->>B: 302 回调 带 code 与原样回传的 state B->>C: 访问回调地址 C->>C: 比对 state 一致 否则直接拒绝 C->>A: POST 令牌端点 code client_secret code_verifier redirect_uri A->>A: 校验码未使用未过期 且 code_verifier 哈希匹配 A-->>C: 返回 access_token refresh_token 与 id_token C->>R: 调用业务接口 携带 access_token R-->>C: 返回资源 Note over B,A: 浏览器只经手一次性授权码
令牌始终不进入浏览器地址栏
授权端点参数 作用 写错的后果
response_type 固定为 code，声明走授权码模式 写成 token 就退化成已废弃的隐式模式
client_id 客户端标识，公开信息 与注册信息不符直接报错，不构成安全问题
redirect_uri 回调地址，授权服务器按注册值精确匹配 允许通配或开放重定向会让授权码被送到攻击者服务器
scope 申请的授权范围，多个用空格分隔 一次要过多范围会降低用户同意率，也放大泄露影响
state 与用户会话绑定的随机值，原样回传用于校验 不校验会被诱导完成攻击者发起的授权流程
code_challenge 与 code_challenge_method PKCE 的挑战值与哈希方法，方法用 S256 用 plain 等于没做 PKCE；缺失则授权码谁截获谁能用
nonce OIDC 专用，会写进 id_token 用于防重放 不校验则旧的 id_token 可被重放完成登录
prompt 与 max_age 控制是否强制重新认证、可接受的认证时效 敏感操作不加 prompt 会直接用旧会话静默通过 
# 1) 生成 PKCE 材料（code_verifier 43-128 字符，challenge 是它的 SHA-256）
VERIFIER=$(openssl rand -base64 60 | tr -d '\n=+/' | cut -c1-64)
CHALLENGE=$(printf '%s' "$VERIFIER" | openssl dgst -binary -sha256 | openssl base64 \
  | tr '+/' '-_' | tr -d '=\n')
STATE=$(openssl rand -hex 16)
# VERIFIER 与 STATE 必须存进服务端会话，不能只放在前端内存或 localStorage

# 2) 把用户重定向到授权端点（这一步由浏览器完成，这里只是把 URL 拼出来看）
echo "https://idp.example.com/authorize?response_type=code&client_id=web-app\
&redirect_uri=https%3A%2F%2Fapp.example.com%2Fcallback&scope=openid%20profile%20email\
&state=$STATE&code_challenge=$CHALLENGE&code_challenge_method=S256&nonce=$(openssl rand -hex 16)"

# 3) 回调拿到 code 后，在后端用 code 换令牌；redirect_uri 必须与上一步完全一致
curl -s -X POST https://idp.example.com/oauth2/token \
  -u "web-app:$CLIENT_SECRET" \
  -d grant_type=authorization_code \
  -d "code=$CODE" \
  -d "code_verifier=$VERIFIER" \
  -d 'redirect_uri=https://app.example.com/callback' \
  | jq '{token_type, expires_in, scope, has_id_token: (.id_token != null)}'
# 判读要点：
#   expires_in 一般 300-3600；拿不到 id_token 说明 scope 里漏了 openid，
#   此时你手上只有授权凭证没有身份断言，不能用于登录判断。
#   用同一个 code 再请求一次必须返回 invalid_grant，这是授权码一次性的验证方法。

② 原理 · 其余授权模式，以及两个废弃模式的废弃理由

搞清废弃理由，能解决「老项目还在用隐式模式，到底有多急」这个排期问题——理由本身就是整个协议的设计意图。

模式 流程特征 适用场景 状态
授权码 + PKCE 浏览器拿码，后端换令牌 Web 应用、SPA、原生 App，一切有用户参与的场景 唯一推荐
客户端凭证 客户端直接用自己的凭证换令牌，无用户参与 服务间调用、定时任务、后台数据同步 推荐（仅限机密客户端）
设备码 设备显示短码，用户在手机或电脑上输入并授权，设备轮询令牌端点 电视、机顶盒、CLI 工具、无浏览器设备 推荐用于输入受限设备
刷新令牌 用刷新令牌换新的访问令牌 延长登录态，配合轮换使用 推荐，但必须轮换
隐式模式 授权服务器直接在重定向片段里返回访问令牌 历史上给无后端的 SPA 用 已废弃，改用授权码加 PKCE
密码模式 客户端收集用户名密码，直接换令牌 历史上给自家一方应用用 已废弃

废弃的理由值得记住，因为它们解释了整个协议的设计意图。隐式模式把访问令牌放进重定向地址，令牌于是出现在浏览器历史里、可能被页面脚本读到、也可能通过 Referer 外泄；同时它没有后端参与，既无法安全使用客户端密钥，也拿不到刷新令牌，只能靠不断跳转续期。密码模式的问题更根本：它让客户端直接接触用户在授权服务器的凭证，这恰恰是 OAuth2 诞生要消灭的事情，一旦客户端被攻破，泄露的是密码本身而不只是令牌，而且它天然无法支持多因素与验证码这类交互式认证步骤。

② 原理 · PKCE：把授权码绑定到发起它的客户端

搞清它的绑定机理，能解决「有后端、能保管 secret，还需要 PKCE 吗」这个每次评审都会被问到的问题。

公开客户端（SPA、原生 App）无法保存 client_secret——代码可以被反编译、可以被查看源码，所以「用 code 加 secret 换令牌」这一层保护对它们不成立。此时如果授权码在回调链路上被截获（自定义 URL scheme 被同设备恶意应用抢注、日志或 Referer 泄露、中间人），截获者就能直接换到令牌。

PKCE 的机理是把一次性授权码和发起这次流程的那个客户端实例绑定：客户端先生成高熵随机串 code_verifier，把它的 SHA-256 摘要经 base64url 编码后作为 code_challenge 发到授权端点；授权服务器把 challenge 与授权码存在一起；换令牌时客户端必须提交原始 code_verifier，服务端重算哈希比对。截获授权码的人没有 verifier，而从 challenge 反推 verifier 在计算上不可行，所以码变成了废纸。

✅
PKCE 现在对所有客户端都推荐

包括有后端、能保管 client_secret 的机密客户端。理由是它防的不只是「secret 缺失」，还包括授权码被注入到另一个用户会话中的一类问题。实现成本是几行哈希代码，code_challenge_method 必须用 S256，plain 等于没做。

② 原理 · 令牌类型、端点分工与 scope 设计

搞清端点分工与 scope 的语义边界，能解决两个真实缺陷：登出后令牌还活着，以及「令牌校验通过」被误当成「有权访问这条数据」。

端点 谁来调 作用 注意
授权端点 浏览器（重定向） 用户认证与同意，返回授权码 必须走 HTTPS，且 redirect_uri 精确匹配
令牌端点 客户端后端 换取与刷新令牌 要做客户端认证与限流，是被爆破的主要目标
内省端点 资源服务器 查询不透明令牌是否有效及其元数据 必须加缓存，否则每请求多一次往返
撤销端点 客户端后端 登出时主动作废刷新令牌与访问令牌 登出只清本地会话不调它，等于令牌还活着
公钥端点 资源服务器与网关 发布验签公钥集合 缓存并设 TTL，配合密钥轮换
发现文档 客户端与资源服务器 一次性获取以上所有端点地址与支持的算法 启动时拉取并缓存，不要硬编码端点
维度 JWT 形态的访问令牌 不透明访问令牌
资源服务器校验方式 本地验签，零网络调用 调内省端点，一次网络往返
即时撤销 做不到，只能靠短有效期 天然支持，撤销后下次内省即失效
体积 数百字节到数 KB，每请求重传 几十字节
信息泄露面 payload 可被任何持有者解码 本身不含信息
对授权服务器的压力 仅公钥拉取 与业务调用量同阶，必须缓存
适用 内部微服务、高频接口 对外开放平台、需要随时断掉授权 
# 发现文档：一次拿到全部端点，避免把地址硬编码在各个服务里
curl -s https://idp.example.com/.well-known/openid-configuration \
  | jq '{issuer, authorization_endpoint, token_endpoint, introspection_endpoint,
         revocation_endpoint, jwks_uri, id_token_signing_alg_values_supported,
         code_challenge_methods_supported}'
# 判读要点：
#   code_challenge_methods_supported 里必须有 S256，没有就说明这家 IdP 不支持 PKCE；
#   issuer 的值要和你校验 id_token 时配置的 iss 完全一致，含尾部斜杠差异也不行。

# 不透明令牌的内省：资源服务器侧校验
curl -s -X POST https://idp.example.com/oauth2/introspect \
  -u "resource-server:$RS_SECRET" \
  -d "token=$ACCESS_TOKEN" | jq '{active, sub, scope, exp, client_id}'
# active 为 false 就必须拒绝；不要只看 HTTP 200 就放行，这是常见实现疏漏。
# 内省结果建议缓存 30-60 秒，兼顾撤销及时性与授权服务器负载。

# 登出时撤销刷新令牌，否则它在有效期内仍可继续换新令牌
curl -s -X POST https://idp.example.com/oauth2/revoke \
  -u "web-app:$CLIENT_SECRET" \
  -d "token=$REFRESH_TOKEN" -d 'token_type_hint=refresh_token' -o /dev/null -w '%{http_code}\n'
# 规范要求即使令牌不存在也返回 200，所以 200 不代表「刚才那个令牌确实存在过」。

scope 不等于权限。scope 表达的是「用户授予这个应用的能力范围」，而不是「这个用户有什么权限」。这两件事的区别在资源服务器上体现得最清楚：令牌带着 orders.read 只说明这个应用被允许读订单接口，它不说明可以读哪些订单。具体某条订单是否属于当前用户、当前用户在其所属租户里是否有查看权限，仍然必须由资源服务器自己判断。把 scope 当权限用的直接后果就是水平越权：换个订单 ID 就能读别人的数据，而令牌校验全程通过。越权的完整分类与防护见站内 越权与鉴权安全。

scope 粒度 示例 好处 代价
按资源加动作 orders.read 与 orders.write 语义清晰，最小授权好落地 数量随业务线性增长，同意页会很长
按业务域 orders 与 billing 同意页简洁，易于对外沟通 粒度粗，读写不分导致过度授权
按角色打包 merchant.basic 接入方省事 包内容一变所有接入方的实际权限都变，难以审计
OIDC 标准 scope openid 与 profile 与 email 跨 IdP 通用，字段语义标准化 只覆盖身份信息，业务范围仍需自定义

② 原理 · OIDC 在 OAuth2 上加了什么

搞清增量部分，能解决「敏感操作前怎么知道用户是多久以前认证的、用了几个因素」。

能力 纯 OAuth 2.0 OIDC 增加的部分
身份断言 没有，只有访问令牌 id_token：JWT 格式，aud 是客户端自己，sub 是用户标识
用户信息 各家自定义接口，字段名五花八门 /userinfo 端点与标准化 claims（name、email、email_verified 等）
防重放 state 只防流程绑定 nonce 写入 id_token，客户端比对本次流程的值
端点发现 靠文档与人工配置 .well-known/openid-configuration 自动发现
认证上下文 无 auth_time、acr、amr：何时认证、认证强度、用了哪些因素
会话与登出 无 前端通道与后端通道登出规范（可靠性仍有限，见工程实践篇）

实践中最容易漏的是 amr 与 auth_time：做敏感操作二次确认时，你需要知道用户是多久以前认证的、有没有用第二因素，而不是简单地看「有没有登录」。email_verified 同理，见下一节。

③ 场景 · 不同客户端形态的落地方式与代价

协议只有一套，落地形态却差别很大，区别集中在令牌最终存在哪里。这一列决定了你的风险面，也决定了要额外维护什么。

场景 该怎么做 为什么是这样 代价
有后端的 Web 应用 授权码 + PKCE，令牌只存服务端，浏览器只拿自己的会话 Cookie 浏览器全程不接触访问令牌与刷新令牌，风险面最小 需要服务端会话存储与它的高可用
纯 SPA，没有自己的后端 授权码 + PKCE；更稳的形态是加一个 BFF 代持令牌，前端只留会话 Cookie 令牌放在前端时，无论放内存、localStorage 还是 Cookie，都落在 XSS 的影响范围内 多一层 BFF 要部署与运维（存放位置的取舍见 越权与鉴权安全）
原生 App 授权码 + PKCE，用系统浏览器组件而非内嵌 WebView；回调优先用受平台校验的通用链接 内嵌 WebView 里宿主应用能看到用户在 IdP 的输入，等于回到密码模式；自定义 scheme 可被同设备应用抢注 回调注册与平台差异要逐平台验证
CLI 工具、电视、机顶盒 设备码模式，用户在手机上完成授权，设备按 interval 轮询 没有浏览器或输入极不方便，重定向流程走不通 要处理 slow_down 与用户迟迟不授权的超时分支
服务间调用、定时任务 客户端凭证模式，令牌缓存并提前续取；或直接用 mTLS 这里没有用户，复用用户令牌会让审计分不清调用发起方 客户端密钥要纳入密钥管理并轮换
企业客户只支持 SAML 独立适配层承接 SAML，转成内部 OIDC 语义后再进业务 存量企业身份系统改不动，但复杂度可以被隔离在一个服务里 适配层要长期维护，XML 签名校验必须用成熟库的严格模式
自己作为授权服务器，对外开放 API 不透明令牌 + 内省 + 增量授权 + 可撤销，redirect_uri 逐个精确注册 对外授权必须能随时断掉某个接入方，自包含令牌做不到 内省要缓存与限流，同意页与配额体系都要自己建

不适用边界：OAuth2 与 OIDC 只管「谁授权了什么范围」和「用户是谁」，它们不解决三件事——数据级的权限判断（这条订单是否属于当前用户、当前用户在其租户里能不能看），必须由资源服务器自己做，见 越权与鉴权安全；令牌格式与验签细节（算法白名单、kid 轮换、即时失效），见 JWT 的结构与验签机制；上线后的工程问题（刷新并发、会话列表、单点登出、认证服务降级），见 认证系统的工程实践。整条路径的选型与分层回到 认证与授权的协议全景。

事项 具体做法 不做会怎样
回调地址注册 每个环境单独注册完整地址，精确匹配，不用通配也不带动态参数 配合开放重定向可导致授权码外泄

最容易踩的坑

❌
避坑清单
  • scope 里忘了 openid：整个流程照样成功，但不会返回 id_token，你手上只有授权凭证而没有身份断言。
  • 换令牌时的 redirect_uri 与授权请求那次不完全一致：包括尾部斜杠和端口，差一个字符就 invalid_grant。
  • iss 校验按包含或前缀写：尾部斜杠的差异是这类实现最常见的失败点，必须精确相等比较。
  • 把 state 存在浏览器 localStorage 里校验：攻击者能控制的存储没有校验价值，必须放服务端会话或用带签名的 Cookie。
  • code_challenge_method 用了 plain：等于把 verifier 明文发出去，PKCE 形同虚设。
  • 授权码重复兑换时没有作废已签发的令牌：这是识别授权码被截获的关键信号，白白丢掉。
  • 内省接口不缓存：业务量一上来，授权服务器先被自家资源服务器打挂。
  • 把 id_token 当访问令牌去调业务接口：它的受众是客户端，资源服务器正确实现时会拒绝，错误实现时会造成权限判断失据。
  • 设备码模式按固定间隔疯狂轮询：规范要求遵守 interval 并处理 slow_down，否则会被限流或封禁。
  • 同意页面的 scope 一次全要：用户同意率下降，且一旦令牌泄露影响面覆盖全部能力，应按需增量授权。
  • 回调处理函数没做失败分支：用户在授权页点了拒绝会带 error=access_denied 回来，不处理就白屏。
  • 多个环境共用一个 client_id 与回调地址：测试环境的一个配置失误会把生产的授权码引到测试域名上。
