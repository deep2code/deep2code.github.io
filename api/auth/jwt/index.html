JWT 的结构与验签机制

🏷️ 认证

JWT 的麻烦之处在于它太容易「用起来」：引一个库、调一次 sign、调一次 verify，功能就通了。真正的问题全藏在细节里——验签通过并不代表这个令牌是发给你的，header 里的算法字段是攻击者可控的输入，密钥轮换的步骤顺序颠倒就是一次全站 401。这篇只讲格式与验签机制本身：JWS 与 JWE 的区别、每个字段的语义、必须校验哪些声明、公钥怎么分发与轮换、以及令牌体积的真实代价。至于算法混淆与无签名攻击的利用细节、令牌该存在浏览器哪里，见站内 越权与鉴权安全。

① 用法 · 验签的正确写法：必校验项、kid 轮换与撤销的落点

验签代码里真正决定安全性的不是「调了 verify」这一行，而是传进去的那几个参数。绝大多数线上缺陷都长成同一个样子：签名校验通过，于是放行，而没人问过这个令牌是不是发给本服务的、是不是还在有效期内、算法是不是本服务期望的那一种。下面这段可以直接抄进项目，六个参数一个都不能少，原因见下一节起的原理部分。

// 验签中间件（Node + jose）：算法白名单 + 全部必校验声明 + JWKS 缓存 + 撤销落点
import { createRemoteJWKSet, jwtVerify } from 'jose'

// 公钥只从配置好的地址取；令牌 header 里的 jku 与 x5u 一律忽略，
// 否则等于允许对方自带密钥来证明自己
const JWKS = createRemoteJWKSet(new URL('https://idp.example.com/.well-known/jwks.json'), {
  cacheMaxAge: 10 * 60 * 1000,   // 决定轮换后多久拿到新公钥，也决定旧公钥要保留多久
  cooldownDuration: 30 * 1000,   // 未命中回源的最小间隔：没有它，随机 kid 的请求会压到授权服务
})

export async function verifyAccessToken(raw: string) {
  const { payload } = await jwtVerify(raw, JWKS, {
    algorithms: ['RS256'],              // 硬要求：本服务只接受这一种，不让 header 的 alg 参与决策
    issuer: 'https://idp.example.com/', // 精确相等比较，尾部斜杠差一个字符也要判失败
    audience: 'order-service',          // 缺这一行就是跨服务重放，很多库默认不校验
    clockTolerance: '60s',              // 吸收多机 NTP 漂移，否则会出现查无规律的零星 401
    requiredClaims: ['sub', 'exp', 'iat', 'jti'],
    typ: 'at+jwt',                      // 区分访问令牌与身份令牌，取值按签发方实际下发的值填
  })
  // 关键：验签只证明「没被篡改、来自可信签发方」，不代表「现在还该放行」。
  // 需要封禁即时生效时，必须在这里再查一次失效状态，判定方式见下方提示框
  if (await isInvalidated(payload)) throw new Error('token invalidated')
  return payload
}

// 用户级失效：一条记录顶掉该用户全部在途令牌，存储量与用户数同阶而不是与令牌数同阶
async function isInvalidated(p: { sub?: string; jti?: string; iat?: number }) {
  if (!p.sub || !p.iat) return true
  const invalidBefore = await cache.getNumber(`uid:${p.sub}:invalid_before`)
  return invalidBefore ? p.iat < invalidBefore : false
}
# 三条验收命令，上线前各跑一次；前两条是安全验收，第三条是轮换演练
# 1) 拿一个签给「另一个服务」的令牌来调本服务：必须 401（这就是 aud 校验的验收方式）
curl -s -o /dev/null -w 'aud 不匹配 %{http_code}\n' \
  -H "Authorization: Bearer $TOKEN_FOR_ANOTHER_SERVICE" https://order.example.com/api/me

# 2) 拿一个已过期的令牌：必须 401，且响应体里不能出现「过期」「签名不匹配」这类校验细节
curl -s -H "Authorization: Bearer $EXPIRED_TOKEN" https://order.example.com/api/me | head -3

# 3) 轮换演练：切换签发密钥之前，JWKS 里必须已经同时能看到新旧两把 key
curl -s https://idp.example.com/.well-known/jwks.json | jq '[.keys[] | {kid, kty, alg}]'
# 只看到一把 key 就去切签发密钥，等于给自己安排一次全量 401；
# 反之在旧令牌还没全部过期时删掉旧公钥，表现是「刚登录的用户忽然被登出」
要做什么 怎么写 漏了会怎样
算法白名单 验签时显式传入期望算法（示例里的 algorithms），只接受一种，绝不读 header 的 alg 来选择验签方式 算法混淆与无签名令牌被接受，等于验签形同虚设
iss 精确匹配 与配置里的签发方字符串完全相等比较，不做前缀或包含匹配 信任了非预期的签发方，包括对方自建的签发端
aud 包含本服务 把本服务标识作为期望受众传给库；注意 aud 可能是字符串也可能是数组 跨服务重放：一个低敏感服务的令牌可以直接调核心服务
exp 与 nbf 加时钟偏移容忍 启用库的时间校验并要求 exp 必须存在，容忍值设 30 到 60 秒 过期令牌仍可用；或多机时钟不同步导致查无规律的随机 401
签名密钥来源固定 公钥只从配置好的 JWKS 地址取，忽略令牌里的 jku 与 x5u 对方自带密钥自签自证，签名校验变成走过场
令牌类型区分 校验 typ 或自定义声明，区分访问令牌、身份令牌与刷新令牌 身份令牌被当访问令牌使用，权限判断失去依据
kid 路由与公钥缓存 按 header 的 kid 从本地缓存取公钥，缓存设 TTL，未命中回源要限流并加负缓存 无缓存则每请求打授权服务；无 TTL 则轮换后永远取不到新公钥
失效判定（如业务需要即时生效） 验签通过后再查一次用户级失效时间点或 jti 名单，命中即拒 封禁、降权、改密码都要等到令牌自然过期才生效
⚠️
JWT 做不到即时失效，撤销必须另外落地

自包含令牌的定义就是「验签方不联系任何人即可确认有效」，所以它天然不具备吊销能力——「登出接口清掉前端存储」不是吊销，令牌在有效期内仍然可用。可选的落点只有三个，按生效延迟从宽到严：一，短有效期加刷新令牌轮换，访问令牌 5 到 15 分钟，封禁时让刷新失败，延迟最长一个有效期，零额外开销；二，用户级失效时间点，缓存里记一条 userID 到 invalidBefore 的映射，验签后比较令牌的 iat，一条记录顶掉该用户全部在途令牌，改密码与封禁的首选；三，按 jti 维护吊销名单，粒度最细但存储量与令牌数同阶。后两者都要付一次缓存查询（同机房约 0.2 到 1 毫秒）并承认自己需要服务端状态，各自的适用范围见下文原理层的对照表。

参数或配置 作用 默认值 什么时候必须改
算法白名单 限定本服务接受的签名算法 多数库在不传时会按 header 的 alg 处理，等于没有白名单 永远显式传；换算法时按「先加后删」的顺序临时接受两种
期望受众（audience） 声明本服务标识，拒绝签给别人的令牌 很多库默认不校验 aud 只要同一个授权服务器下有第二个资源服务，就必须传
时钟偏移容忍 吸收 NTP 漂移，避免零星 401 多数库默认为 0 设 30 到 60 秒；更大就等于变相延长了有效期
JWKS 缓存 TTL 决定轮换后多久所有验签方拿到新公钥 各库不同，以所用库文档为准 取 5 到 15 分钟；旧公钥的保留时长要覆盖「最长令牌有效期 + 这个 TTL」
JWKS 回源冷却与限流 限制未命中时的回源频率 部分库不做限制 一律配；否则随机 kid 的请求会让网关把授权服务打满
访问令牌有效期 它就是「无法吊销」的窗口长度 由签发方决定，以令牌响应的 expires_in 与 exp 实际值为准 压到 5 到 15 分钟；不要靠调长它来减少刷新请求
HMAC 密钥长度 决定能否被离线爆破 无强制，库通常不校验长度 随机源生成且至少 32 字节；绝不用口令或配置项里的短字符串
请求头大小上限（网关与容器） 决定令牌多大时请求会被直接拒 随服务器与版本变化，以所用服务器配置的实际值为准（Tomcat 与 Nginx 都有各自的默认上限） payload 变大或出现 400 与 431 时，先缩令牌再考虑调上限

② 原理 · JWT 只是容器：先分清 JWS 与 JWE

搞清这两者的分工，能解决一个很常见的误解引发的事故：把敏感字段写进 payload，以为签名等于加密。

JWT 是一种声明的传递格式，它的具体承载有两种形态：JWS 是签名，内容公开可读但不可篡改；JWE 是加密，内容对持有者以外不可读。绝大多数人说「JWT」时指的都是 JWS，这直接带来一个必须记住的结论：payload 只是 base64url 编码，不是加密。任何拿到令牌的人都能一行命令解出全部内容，所以手机号、证件号、内部角色描述、金额这类东西不能放进去。

# 把任意 JWT 的前两段解出来看（不需要密钥，这正是它不是加密的证明）
T='eyJhbGciOiJSUzI1NiIsImtpZCI6IjIwMjYtMDkifQ.eyJzdWIiOiJ1XzEwMDEifQ.c2ln'
for i in 1 2; do
  echo "$T" | cut -d. -f$i | tr '_-' '/+' | base64 -d 2>/dev/null; echo
done
# 判读要点：
#   第一段能看到 alg 与 kid；第二段能看到全部业务声明。
#   如果这里出现了手机号、真实姓名、内部权限码，就是一个需要立刻整改的问题。

# 顺手核对签发方的公钥集合，确认 kid 在里面
curl -s https://idp.example.com/.well-known/jwks.json | jq '.keys[] | {kid, kty, alg}'
# 典型输出会有两把甚至三把 key，这是正在做密钥轮换的正常现象

② 原理 · 三段结构逐字段拆开

搞清每个字段的语义，能解决「上面那张必校验清单为什么是这几项」——每一项都对应一个具体的失效方式。

三段分别是 header、payload、signature，前两段是 base64url 编码的 JSON，第三段是对「前两段拼接后的字符串」做签名的结果。注意签名的输入是编码后的字符串而不是原始 JSON，所以同一份声明用不同的 JSON 序列化方式会得到不同的令牌，这也是为什么不能自己拼 JSON 再复用别人的签名。

header 字段 含义 实际怎么用
alg 签名算法标识 必填。它是不可信输入，验签方只能用它做日志，绝不能用它决定验签方式
kid 密钥标识 多密钥并存时的路由键。轮换体系里没有 kid 就只能对所有公钥逐个试签，性能和正确性都糟
typ 令牌类型 一般是 JWT。OAuth2 访问令牌的规范建议写成更具体的类型以区分用途，避免把身份令牌当访问令牌用
cty 内容类型 嵌套令牌时才用，日常极少见到
jku 与 x5u 指向密钥的 URL 危险字段。绝不能按令牌里给的 URL 去取公钥，否则攻击者指向自己的密钥就能自签自证
标准声明 语义 验签时是否必校验 不校验的后果
iss 签发方标识 必须 接受了其他签发方（甚至攻击者自建 IdP）签出的令牌
sub 主体标识，即「这是谁」 必须存在并映射到内部不可变用户 ID 用邮箱等可变字段定位用户，改邮箱后身份错位
aud 受众，即「这个令牌是给谁用的」 必须 跨服务重放：给 A 服务的令牌能直接调 B 服务，这是最常见的线上缺陷
exp 过期时间，秒级 Unix 时间戳 必须 令牌永久有效，一次泄露永久可用
nbf 生效时间 存在则必须校验 预先签发的令牌提前可用
iat 签发时间 建议校验（配合最大年龄） 无法识别过于陈旧的令牌，也无法在改密码后按时间点批量失效
jti 令牌唯一标识 做吊销或一次性令牌时必须 无法按单个令牌吊销，也无法防重放一次性令牌
⚠️
本篇最重要的一条

大量实现只做了「签名对不对」这一步就放行。签名正确只说明令牌来自持有签名密钥的一方，不说明它是发给当前这个服务的、也不说明它还在有效期内。在同一个授权服务器下有多个资源服务时，缺少 aud 校验等价于所有服务共用一张通行证，一个低敏感服务的令牌泄露会直接扩散到核心服务。

② 原理 · 签名算法族：选哪一类由信任关系决定

搞清算法与信任关系的对应，能解决「为什么我们这套 HS256 不能再加第二个服务进来验签」。

选算法不是选「哪个更安全」，而是选谁有能力签发。HMAC 系是对称的，验签方手里的密钥同时也能签发令牌，因此只适合签发方与验签方属于同一信任域的场景。一旦有多个团队、多个服务甚至外部方需要验签，就必须换非对称：私钥只在授权服务器，公钥可以随便发。

算法 类型 密钥要求 签名长度 相对开销 适用
HS256 / HS384 / HS512 对称 HMAC 随机密钥至少 32 字节，不要用口令 32 / 48 / 64 字节 最低，微秒级 单体应用、签发与验签同属一个服务
RS256 非对称 RSA PKCS1v1.5 RSA 2048 位起步 256 字节（2048 位） 签名慢、验签快 兼容性最好，第三方 IdP 默认值
PS256 非对称 RSA-PSS RSA 2048 位起步 256 字节 与 RS256 接近 新系统在库都支持时优于 RS256
ES256 非对称 ECDSA P-256 32 字节私钥 64 字节 签名快，验签略慢于 RSA 验签 令牌体积敏感的移动端与高频接口
EdDSA（Ed25519） 非对称 32 字节私钥 64 字节 签验都快 自建体系且确认各端库都支持时的最优选
none 无签名 无 空 — 永远不要启用；库的白名单里不能出现

② 原理 · 密钥分发与轮换：工程上最容易出事的一环

搞清轮换的步骤顺序，能解决两种自伤型故障：切换瞬间全量 401，以及旧公钥删太早导致在线用户集体掉线。

非对称方案下，验签方需要拿到公钥。标准做法是授权服务器暴露一个 JWKS 端点（通常是 /.well-known/jwks.json），里面是一组 JWK，每个带 kid。验签方读令牌 header 的 kid，从本地缓存里取对应公钥；缓存未命中才回源拉取。这里有两个必须做的保护：回源要限流（否则伪造随机 kid 就能让授权服务器被自家网关打挂），缓存要有 TTL（否则轮换后永远拿不到新公钥）。

sequenceDiagram participant V as 资源服务 participant K as 本地公钥缓存 participant I as 授权服务 JWKS 端点 V->>V: 解析 header 取出 kid 与 alg V->>V: 先按白名单否决不期望的算法 V->>K: 按 kid 查公钥 K-->>V: 命中则直接返回公钥 V->>V: 验签 再校验 iss aud exp nbf V->>I: 仅在未命中且未被限流时回源 I-->>V: 返回公钥集合 通常含新旧两代 V->>K: 覆盖缓存 设置 5-15 分钟 TTL Note over V,I: 未命中回源必须限流并加负缓存
否则随机 kid 的请求会直接压到授权服务

// 可直接抄的验签中间件：算法白名单 + 完整声明校验 + JWKS 缓存
// 依赖：github.com/golang-jwt/jwt/v5 与 github.com/MicahParks/keyfunc/v3
var jwks keyfunc.Keyfunc

func initJWKS(ctx context.Context) error {
    var err error
    // keyfunc 内部按 kid 取键并周期刷新；RefreshInterval 决定轮换后多久能拿到新公钥
    jwks, err = keyfunc.NewDefaultCtx(ctx, []string{
        "https://idp.example.com/.well-known/jwks.json",
    })
    return err
}

func AuthMiddleware(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        raw := strings.TrimPrefix(r.Header.Get("Authorization"), "Bearer ")
        if raw == "" {
            http.Error(w, "unauthorized", http.StatusUnauthorized)
            return
        }
        tok, err := jwt.Parse(raw, jwks.Keyfunc,
            // 关键一：算法白名单。不读 header 的 alg 做决策，none 与算法混淆在此被挡住
            jwt.WithValidMethods([]string{"RS256"}),
            // 关键二：签发方与受众都必须显式校验，很多库默认不校验 aud
            jwt.WithIssuer("https://idp.example.com/"),
            jwt.WithAudience("order-service"),
            // 关键三：容忍 60 秒时钟偏移，避免多机 NTP 漂移引发随机 401
            jwt.WithLeeway(60*time.Second),
            jwt.WithExpirationRequired(),
        )
        if err != nil || !tok.Valid {
            // 不要把 err 原文返回给客户端，只记日志，避免泄露校验细节
            http.Error(w, "unauthorized", http.StatusUnauthorized)
            return
        }
        claims := tok.Claims.(jwt.MapClaims)
        sub, _ := claims["sub"].(string)
        jti, _ := claims["jti"].(string)
        // 需要即时封禁时在这里查一次吊销名单：命中即拒
        if sub == "" || isRevoked(r.Context(), sub, jti) {
            http.Error(w, "unauthorized", http.StatusUnauthorized)
            return
        }
        next.ServeHTTP(w, r.WithContext(withUser(r.Context(), sub)))
    })
}

② 原理 · jti 与吊销：三条路都要付代价

搞清代价的构成，能解决「到底该不该为了封禁功能放弃无状态」这个必须在设计阶段回答的问题。

自包含令牌按设计就不可吊销：验签方不需要联系任何人就能确认令牌有效，这既是它的优点也是它的上限。补救只有三条路，选择标准是业务能容忍多长的生效延迟。

方案 生效延迟 每请求额外开销 放弃了什么 适用
短有效期加刷新令牌轮换 最长一个访问令牌有效期（建议 5-15 分钟） 无；只有刷新时才有一次网络调用 无法做到秒级封禁 普通业务、内容型产品
按 jti 维护吊销名单 接近实时 每请求一次缓存查询，0.2-1 ms 无状态性；吊销存储成为关键依赖 金融、涉密、强合规场景
按用户维度记录失效时间点 接近实时 同上，但可与用户信息缓存合并 同上，粒度较粗 改密码与封禁要立刻踢掉全部设备

第三种做法实践中最划算：缓存里只存 userID 到 invalidBefore 的映射，验签后比较令牌的 iat 是否早于这个时间点即可，一条记录顶掉该用户全部在途令牌，存储量和用户数同阶而不是和令牌数同阶。

② 原理 · 令牌体积的真实代价

搞清体积从哪来，能解决「接口忽然开始返回 400 或 431」以及「网关内存随并发线性上涨」。

令牌在每一个请求的请求头里重传，这件事常被忽略。base64url 会让原始字节膨胀约三分之一，签名本身在 RS256 下就有 342 个字符。往 payload 里塞几十个权限字符串，令牌很容易过 2 KB，而不少服务器默认的请求头上限只有 8 KB（Tomcat 的 max-http-header-size 默认 8 KB，nginx 的 large_client_header_buffers 默认 4 个 8 KB 缓冲），超限会直接得到 400 或 431，且错误信息通常很不直观。HTTP/2 的头部压缩只在同一连接上重复发送相同头部时才有效，令牌一变（每次刷新后都会变）压缩收益就归零。

payload 内容 HS256 下大致长度 RS256 下大致长度 说明
最小集合：iss sub aud exp iat 约 230-280 字节 约 520-580 字节 推荐形态；差值几乎全在签名段
加上角色与租户等 3-5 个短声明 约 300-360 字节 约 600-680 字节 可接受
加上 30 条权限字符串 约 900-1200 字节 约 1.2-1.5 KB 开始明显影响带宽，且权限变更无法生效
再加用户资料、头像地址、偏好设置 2-3 KB 2.5-3.5 KB 接近请求头上限，网关连接内存随并发线性放大
💡
payload 的取舍原则

只放身份标识与授权判断必需的最小集合：不可变的用户 ID、租户 ID、粗粒度角色、以及协议要求的标准声明。用户资料由前端单独调接口获取（可缓存），细粒度权限由资源服务现查。判断标准是问一句：这个字段变更后，能容忍它在令牌里保持旧值到过期吗？不能，就不该放进去。

③ 场景 · 不同系统形态该验到哪一步、吊销做到哪一档

前面几节给的是机制，这一节给投入顺序。判断依据只有两条：有几方需要验签，以及封禁的生效延迟容忍度是多少。这两条一定下来，算法、公钥分发方式、吊销档位基本没有自由度。

场景 该怎么做 为什么停在这里 代价
单体应用，签发与验签都在同一个服务里 HS256，密钥纳入密钥管理并定期轮换；校验 iss、exp、typ 没有第二方需要验签，非对称带来的收益为零，只增加运维面 一旦要把密钥分发给第二个服务，就必须改成非对称，改造要停机或双算法并存
一个授权服务器 + 多个资源服务 RS256 或 ES256，公钥走 JWKS；每个服务校验属于自己的 aud 私钥只在授权服务器，任何资源服务被入侵都不能伪造令牌；aud 把泄露影响限制在单个服务 每个服务都要接验签库、公钥缓存与时钟容忍，新服务上线多一项接入清单
对外开放平台，需要随时断掉某个接入方 不透明令牌加内省，或短有效期 JWT 配严格 scope 与撤销端点 对外授权必须可被立即收回，而自包含令牌做不到 内省要缓存 30 到 60 秒，否则授权服务器被自家资源服务打挂
金融、涉密、强合规，封禁要求秒级生效 JWT + 用户级失效时间点（首选）或 jti 吊销名单 生效延迟容忍度是零，这一条直接否决纯自包含方案 每请求一次缓存查询，且吊销存储成为关键依赖，要做高可用
移动端为主，流量与电量敏感 ES256 或 EdDSA，payload 只放最小集合 签名段 64 字节对 256 字节，而令牌在每个请求里都要重传 要先确认各端与各语言的库都支持所选算法，否则联调阶段才发现
网关统一验签，下游只读身份头 网关验签并清空外部同名头后注入身份；下游只监听内网 下游接入成本几乎为零，小语言栈的服务也能接 下游一旦能被绕过网关直连，加一个请求头就是任意用户（见 认证与授权的协议全景）
令牌要经过不可信中间方，且内容必须保密 JWE，或干脆改用不透明令牌加内省 JWS 的 payload 任何持有者都能解码，编码不是加密 JWE 的实现与排查成本明显更高，日志里也不再能直接看内容

JWT 解决不了的事要说清楚，否则很容易把它当万能容器用：它不管会话管理（设备列表、登出其他设备、刷新并发），这些要靠服务端记录，见 认证系统的工程实践；它不管授权范围怎么设计（scope 与权限的区别、授权码与 PKCE 的流程），见 OAuth 2.0 与 OIDC 的协议细节；它不管令牌该存在浏览器哪里以及算法混淆的具体利用条件，见 越权与鉴权安全；放请求头免疫 CSRF 的前提与 SameSite 语义见 CSRF 与点击劫持。另外它不是缓存：用户资料、权限明细、业务状态塞进 payload 换来的只是体积与过期失真。

③ 场景 · 反模式对照：每条都对应一次真实故障

反模式 后果 正确做法
payload 里放手机号、证件号等敏感数据 任何拿到令牌的人（含前端日志、错误上报平台）都能解出明文 只放标识符；确实要保密就用 JWE，但先问是否必要
按 header 的 alg 选择验签方式 算法混淆与无签名令牌绕过校验 传入算法白名单，只接受一种算法
不校验 aud 一个服务的令牌可以调用所有服务，泄露影响面成倍扩大 每个资源服务显式校验自己的受众标识
访问令牌有效期设成几天 把「无法吊销」的窗口放大到几天 访问令牌 5-15 分钟，长期性交给刷新令牌
权限列表全塞进 JWT 降权后旧令牌仍带旧权限；令牌体积失控 令牌只带粗粒度信息，细粒度权限在资源服务判断
自己实现签名与验签 base64url 边界、时间比较、常量时间比较都容易写错 用成熟库，把精力放在校验参数配置上
JWKS 无缓存或无 TTL 无缓存则每请求打授权服务；无 TTL 则轮换后永远取不到新公钥 缓存 5-15 分钟，未命中回源并限流
用户口令直接当 HMAC 密钥 熵不足，可离线爆破出密钥进而伪造任意令牌 密钥来自随机源且至少 32 字节，纳入密钥管理

最容易踩的坑

❌
避坑清单
  • 验签库默认不校验 aud：不显式传期望受众就等于没校验，各服务间互相可用对方的令牌。
  • aud 可能是字符串也可能是数组：自己解析时只按字符串比较，遇到数组形态会直接判失败或误判通过。
  • 忘记设时钟偏移容忍：多台机器 NTP 漂移几秒就会出现零星 401，日志里看不出规律，极难定位。
  • 轮换时先切签发再发公钥：验签方缓存里没有新 kid，全量请求 401，属于典型的自伤型故障。
  • 旧公钥删得太早：在途令牌集体失效，表现为「刚登录的用户忽然被登出」。保留时长要覆盖最长有效期加缓存 TTL。
  • 按令牌里的 jku 或 x5u 去取公钥：等于让攻击者自带密钥，务必只用配置好的地址。
  • exp 用毫秒时间戳：规范要求秒级，写成毫秒会让令牌被判为遥远未来生效，或校验直接异常。
  • 用非对称算法却把私钥同时下发给各服务验签：任何服务被入侵都能伪造任意用户令牌，等于退化成对称方案的最坏形态。
  • 身份令牌当访问令牌用：身份令牌的受众是客户端而不是资源服务，混用会让权限判断失去依据。
  • 刷新令牌也做成自包含 JWT 且不轮换：泄露后在有效期内无限次可换新令牌，且服务端无从发现。
  • 把验签失败的详细原因返回给客户端：等于告诉攻击者哪一步卡住了，统一返回 401 并把细节留在日志里。
  • 令牌写进 URL 查询参数：会进访问日志、Referer 和浏览器历史，必须放在请求头里传输。
