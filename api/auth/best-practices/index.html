认证系统的工程实践

认证系统的功能列表很短，但上线之后暴露的问题一个比一个难缠：用户莫名被登出、会话列表里显示不出真实设备、单点登出只登出了一半、权限改了但用户手里的令牌还是旧的、认证服务抖一下全站都进不去。这些都不是协议知识能解决的，而是工程设计问题。这篇讲的就是这一层：令牌续期的并发、多端与会话管理、账号体系的表结构、权限模型的取舍、可观测性与降级。协议细节见站内 OAuth 2.0 与 OIDC 的协议细节 与 JWT 的结构与验签机制，密码哈希参数、登录限流阈值、多因素的安全机理见站内 越权与鉴权安全。

这篇怎么读

  • ② 原理：并发刷新为什么会把用户踢下线、会话管理的状态下限在哪、单点登出为什么天生不可靠、账号表该怎么分、权限点与角色怎么分离、认证故障该怎么降级。
  • ③ 场景：从 MVP 到强合规的五个阶段各该做到哪一步，以及自建、私有化、托管、云 IAM 的隐性成本对比。

① 用法 · 上线前的认证自检清单：每条都给验证方法

认证系统的问题有个共同特征：功能测试全过，问题只在真实流量里出现。所以这份清单的每一条都不是「要注意」，而是「用什么命令确认它在线上是对的」。按五组来查：凭证存储、会话与令牌生命周期、令牌存放位置、限流维度、越权检查落在哪一层。为什么这些地方会出问题，见下一节起的原理部分。

# ===== 1) 改密码与封禁必须失效「其他设备」：安全评审必查项 =====
curl -s -c /tmp/devA -o /dev/null -X POST https://app.example.com/login \
  -d 'username=alice' -d 'password=REDACTED'
curl -s -c /tmp/devB -o /dev/null -X POST https://app.example.com/login \
  -d 'username=alice' -d 'password=REDACTED'
curl -s -b /tmp/devA -o /dev/null -X POST https://app.example.com/account/password \
  -d 'old=REDACTED' -d 'new=REDACTED2'
curl -s -b /tmp/devB -o /dev/null -w '改密后另一台设备 %{http_code}\n' https://app.example.com/api/me
# 期望 401。返回 200 说明改密码只改了密码表，没有按用户维度失效会话与刷新令牌

# ===== 2) 限流必须是双维度：只按 IP 挡不住分布式撞库，只按账号会被用来锁死别人 =====
for i in $(seq 1 30); do
  curl -s -o /dev/null -w '%{http_code}\n' -X POST https://app.example.com/login \
    -d 'username=alice' -d 'password=wrong'
done | sort | uniq -c
# 期望超过阈值后出现 429 或验证码挑战；全部 401 说明没有账号维度限流。
# 再用 30 个不同用户名跑一遍，应触发 IP 或设备维度限流；缺任一维度都不算做完。
# 注意锁定策略要分级（先验证码、再延迟、最后才锁），否则它本身就是一种拒绝服务手段

# ===== 3) 越权自检：换一个不属于自己的资源 ID =====
curl -s -o /dev/null -w '别人的订单 %{http_code}\n' -b /tmp/devA \
  https://app.example.com/api/orders/999999
# 期望 403 或 404，绝不能是 200。多租户系统还要用另一个租户的资源各试一次

# ===== 4) 刷新并发自检：同时发起多个刷新，用户不应因此被登出 =====
for i in 1 2 3 4 5; do
  curl -s -o /dev/null -X POST -b /tmp/devA https://app.example.com/auth/refresh &
done; wait
curl -s -o /dev/null -w '并发刷新后 %{http_code}\n' -b /tmp/devA https://app.example.com/api/me
# 最后一行必须是 200。出现 401 说明并发刷新被判成令牌复用、整个家族被作废，成因见下一节
-- 凭证存储自检：算法标识分布里不该出现裸哈希或可逆加密
SELECT substring(credential from 1 for 10) AS algo_prefix, count(*)
FROM user_identities
WHERE credential IS NOT NULL
GROUP BY 1 ORDER BY 2 DESC;
-- 期望只有一种现代口令哈希的标识前缀。出现多种说明有历史遗留，
-- 要在用户下次登录成功时静默重算升级；具体算法与代价参数取值见站内安全篇

-- 会话表自检：有没有永不过期的会话、有没有只增不删
SELECT
  count(*) FILTER (WHERE revoked_at IS NULL AND expires_at > now())          AS alive,
  count(*) FILTER (WHERE expires_at < now() - interval '30 days')            AS should_be_archived,
  max(expires_at - last_seen_at)                                             AS max_window
FROM user_sessions;
-- should_be_archived 不为 0 说明缺归档任务，表迟早膨胀到查询变慢；
-- max_window 异常大说明只有滑动过期、没有绝对上限，被盗会话可以靠定时请求无限续命

-- 刷新令牌是否明文入库：只应存哈希，长度与字符集一看就知道
SELECT length(refresh_hash) AS len, count(*) FROM user_sessions GROUP BY 1;
-- 长度参差不齐或明显长于哈希长度，基本可以断定存了原文
自检项 要做到什么 怎么验证
口令存储形态 只存现代口令哈希，不存可逆加密、不存裸摘要，历史数据在下次登录时静默升级 上面的算法前缀分组 SQL；再测一次单账号登录耗时，口令校验快到毫秒级通常意味着代价参数被调得过低（参数取值见 越权与鉴权安全）
登录响应不泄露账号是否存在 用户不存在与密码错误返回同一个结果，耗时也不应有系统性差异 用一个不存在的账号与一个存在的账号各请求若干次，比较响应体、状态码与耗时分布
会话双超时 空闲超时与绝对超时同时生效，绝对超时不随活跃度延长 会话表 max_window 查询；再放一个会话空转到超时，确认之后请求是 401
登录后换标识 Cookie 会话在登录成功后换新 ID 并删旧记录；令牌方案每次刷新轮换刷新令牌 登录前后对比 Set-Cookie 的值；刷新两次确认旧刷新令牌不可再用
改密与封禁的影响面 按用户维度一次性失效全部会话与刷新令牌，用户表上有「此刻前签发的令牌全部失效」的时间点字段 脚本第 1 段：另一台设备必须变成 401
登出的完整性 清服务端会话记录、撤销刷新令牌，必要时再调 IdP 的登出端点 登出后用旧访问令牌调接口应 401，用旧刷新令牌换新应失败
令牌存放位置（Web） 有后端就把令牌留在服务端，浏览器只拿 HttpOnly 会话 Cookie DevTools 里 localStorage 与 sessionStorage 不应出现令牌；document.cookie 读不到会话 Cookie
令牌存放位置（App） 放系统提供的加密存储，不落明文文件，不进日志与崩溃上报 抓一份完整日志与一次崩溃上报，全文搜索令牌片段与 Authorization 字样，必须为空
限流维度 账号维度与 IP 或设备维度同时存在，措施分级：先验证码、再延迟、最后才锁定 脚本第 2 段的两种跑法；同时确认锁定不会变成锁死他人账号的手段
认证与业务资源隔离 认证服务有独立的限流与连接资源，不与业务共命运 压测业务接口的同时观察登录成功率与认证延迟分位数，不应受影响
越权检查的落点 归属与租户条件强制注入在数据访问层，不是只在网关或前端判断 脚本第 3 段；再把请求里的租户参数改成别的值，结果必须不变（租户只能来自服务端身份）
权限判断方式 代码只判断权限点，角色是配置数据；数据范围落在查询条件里 全仓搜索角色名字符串，命中即是硬编码；新增一个角色应当不需要改代码
敏感操作的认证新鲜度 改密、改绑、提现要求二次验证，并检查最近一次认证的时间与强度 用一个放了很久的会话直接发起敏感操作，必须被二次验证拦住
告警与降级 登录成功率与刷新失败率有独立告警；降级路径不包含「放行未授权请求」 演练：断开外部 IdP，在线用户应仍可访问、新登录明确失败；关掉验证码通道，告警必须响
参数或策略 作用 默认值 什么时候必须改
口令哈希的代价参数 决定离线爆破的成本 各库默认值随版本变化，且常低于当下推荐值，以所用库文档与实测单次校验耗时为准 换机型或升级库时重新实测；参数变更后靠登录时静默重算逐步迁移
会话空闲与绝对超时 限制无操作与单会话的最长寿命 框架默认常只有空闲超时，绝对超时多数需要自己实现 两者必须同时存在；管理端与资金类后台把空闲超时压到分钟级
访问令牌有效期 它等于「无法吊销」的窗口 由签发方决定，以令牌响应的 expires_in 为准 压到 5 到 15 分钟；不要用调长它来减少刷新请求
刷新令牌轮换宽限期 容忍并发刷新，避免误判成复用 多数授权服务器不提供宽限期，需要自己实现 取 10 到 30 秒，并且客户端必须同时做单飞刷新
登录失败阈值与维度 抵挡撞库同时避免锁死他人账号 无通用默认，阈值取值见站内安全篇 账号与 IP 两个维度都要配，措施要分级而不是直接锁定
二次验证的认证新鲜度上限 敏感操作要求「最近认证过」 无默认，取决于实现；OIDC 场景可用 auth_time 与 max_age 资金与账号变更类操作一律设置，通常取分钟级
会话记录归档周期 控制会话表体量与查询延迟 无默认，不做就是只增不删 一律配定时任务；软删记录保留期按审计要求定
公钥缓存与刷新限流 认证服务抖动时的降级基础 各库不同，以所用库文档为准 公钥缓存 TTL 与旧公钥保留期要覆盖最长令牌有效期；刷新接口一律限流并要求客户端退避

② 原理 · 令牌续期的并发问题：最容易带上线的坑

搞清这条链路，能解决一类几乎无法复现的客服问题：用户说自己「莫名被登出」，而日志里只有一次 invalid_grant。

这个问题在本地几乎复现不出来，因为它需要多个请求同时撞上令牌过期。真实环境里这种情况非常常见：页面首屏并行发六七个接口、App 冷启动同时拉配置与用户信息、弱网下请求堆积后一起重发。每个请求各自发现 401，各自去调刷新接口，而刷新令牌通常是一次性的——第一个请求换走新令牌并作废旧的，后面的请求带着已作废的旧令牌去换，服务端把这判定为令牌复用，按安全策略作废整个令牌家族，用户直接被登出。

日志里只看到一次 invalid_grant 很难联系到并发
解法 实现位置 效果 代价与边界
客户端单飞刷新 客户端 HTTP 拦截器 根治同进程内的并发；只有一个请求真正去刷新，其余等待其结果 多标签页或多进程仍会并发，Web 端需要配合跨标签广播或共享锁
服务端刷新宽限期 授权服务 旧刷新令牌在轮换后 10-30 秒内仍可用，并返回同一批新令牌 宽限期内令牌被真正窃取时无法区分复用与并发，窗口要尽量短
按令牌家族容忍 授权服务 记录家族与代际，同一家族内短时间的重复兑换视为并发而非攻击 需要额外存储与代际判定逻辑，是三种里实现成本最高的 
// 客户端单飞刷新：无论多少请求同时 401，只有一个真正去刷新
let refreshing: Promise<string> | null = null

async function getFreshToken(): Promise<string> {
  // 已有刷新在途，直接复用同一个 Promise，避免并发兑换刷新令牌
  if (refreshing) return refreshing
  refreshing = doRefresh().finally(() => {
    // 无论成败都要清空，否则失败后永远返回同一个 rejected Promise
    refreshing = null
  })
  return refreshing
}

async function doRefresh(): Promise<string> {
  const res = await fetch('/auth/refresh', { method: 'POST', credentials: 'include' })
  if (!res.ok) {
    // 刷新失败要走登出，不要静默重试，否则会把失败放大成刷新风暴
    await logout()
    throw new Error('refresh failed')
  }
  const { access_token } = await res.json()
  saveToken(access_token)
  return access_token
}

// 拦截器：401 只允许重试一次，防止刷新后仍 401 造成无限循环
async function request(input: string, init: RequestInit = {}, retried = false) {
  const res = await fetch(input, withAuth(init))
  if (res.status !== 401 || retried) return res
  const token = await getFreshToken()
  return request(input, withAuth(init, token), true)
}
// Web 端补充：多标签页可用 BroadcastChannel 或 Web Locks API 让锁跨标签生效，
// 仅靠模块级变量时，五个标签页同时唤醒仍会产生五次刷新。

② 原理 · 多端登录与会话管理

搞清会话管理的状态下限，能解决「我们用的是无状态 JWT，为什么做不了登出其他设备」。

「同一个账号能不能在多个设备上登录」是产品决策，但它决定了技术实现的下限：只要产品要展示会话列表或提供「登出其他设备」，就必须有服务端会话记录，纯无状态令牌做不到。折中方案是只给刷新令牌建记录——一条记录代表一个设备会话，访问令牌仍是短有效期自包含令牌，踢设备就是删记录，最长一个访问令牌有效期后彻底生效。

策略 实现方式 适用产品 常见抱怨
不限制多端 每次登录新增一条会话记录 内容型、工具型产品 账号共享难以控制
同类型设备互踢 按设备类型维度唯一，新登录作废同类型旧会话 IM、金融、游戏 用户换设备频繁时被迫反复登录
限制并发数量 超出上限时踢掉最早活跃的会话 会员订阅制 上限判定要考虑同设备重装导致的重复记录
全端互踢 任何新登录作废全部旧会话 高敏感后台系统 体验最差，一般只用于管理端
💡
设备识别不要指望完全准确

会话列表要显示「小米手机、上海、两小时前活跃」这种信息，靠的是 User-Agent、客户端上报的设备型号和 IP 归属库，三者都不可靠：UA 可伪造、重装应用会产生新的设备标识、IP 归属在移动网络下经常偏差几百公里。设计时要接受同一台设备出现多条记录，并给用户「登出全部其他设备」这个一键选项作为兜底，而不是指望他逐条辨认。

② 原理 · 单点登录容易，单点登出很难

搞清两者的方向差异，能解决「用户点了登出，回到另一个子系统却还在登录状态」。

单点登录是单向的一次性流程：各子系统信任同一个身份提供方即可。单点登出要反过来通知所有已建立会话的子系统清理自己的会话，而身份提供方既不可靠地知道哪些子系统还活跃，通知也可能失败。结果就是用户点了登出，回到某个子系统发现自己还在登录状态。

登出方式 可靠性 对子系统的要求 现实建议
只清身份提供方会话 最低：子系统会话照旧有效 无 只适合子系统会话本来就很短的场景
前端通道登出 中：受第三方 Cookie 策略与页面生命周期影响 提供一个可被嵌入访问的登出地址 可作为辅助手段，不作为唯一手段

② 原理 · 账号体系设计：把可变的东西挪出主键

搞清这层结构，能解决两个迟早会来的需求：换绑邮箱手机号，以及同一个人绑多个身份源。

最常见的设计错误是用邮箱或手机号当用户主键。它们都会变：换手机号、换公司邮箱、号码被运营商回收后重新分配给别人。一旦作为主键，所有引用它的表都要跟着迁移，历史数据的归属也会错乱。正确结构是内部不可变 ID 做主键，登录标识放在独立的身份表里，一个用户可以绑定多个身份源。

-- 用户主表：只放稳定不变的东西，主键无业务含义
CREATE TABLE users (
    id            BIGINT PRIMARY KEY,            -- 雪花或序列，不可变，对外可再包一层不可枚举的外部 ID
    status        SMALLINT NOT NULL DEFAULT 0,   -- 0 正常 1 停用 2 注销待清理
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    -- 令牌校验时比较其 iat 是否早于此时间点，即可一次踢掉该用户全部在途令牌
    tokens_invalid_before TIMESTAMPTZ
);

-- 身份表：每一种登录方式一行，邮箱手机号第三方账号统一在这里
CREATE TABLE user_identities (
    id            BIGINT PRIMARY KEY,
    user_id       BIGINT NOT NULL REFERENCES users(id),
    provider      VARCHAR(32) NOT NULL,          -- local_email local_phone wechat google saml_acme
    provider_uid  VARCHAR(190) NOT NULL,         -- 提供方内的唯一标识，本地方式则是邮箱或手机号
    verified_at   TIMESTAMPTZ,                   -- 未验证的身份不能用于账号合并
    credential    VARCHAR(255),                  -- 仅本地密码方式使用，存哈希结果
    UNIQUE (provider, provider_uid)              -- 关键：唯一性在提供方维度，而不是全局邮箱唯一
);
CREATE INDEX ON user_identities (user_id);

-- 会话表：一行等于一个设备会话，这是登出其他设备能力的前提
CREATE TABLE user_sessions (
    id               BIGINT PRIMARY KEY,
    user_id          BIGINT NOT NULL REFERENCES users(id),
    family_id        UUID NOT NULL,              -- 刷新令牌家族，用于检测复用
    refresh_hash     CHAR(64) NOT NULL,          -- 只存刷新令牌的哈希，不存原文
    device_label     VARCHAR(120),               -- 展示用，来源不可靠，允许重复
    ip               INET,
    last_seen_at     TIMESTAMPTZ NOT NULL,
    expires_at       TIMESTAMPTZ NOT NULL,
    revoked_at       TIMESTAMPTZ                 -- 软删便于审计，清理任务定期归档
);
CREATE INDEX ON user_sessions (user_id, revoked_at);
CREATE UNIQUE INDEX ON user_sessions (refresh_hash);
设计点 推荐做法 踩坑版本
用户标识 内部不可变 ID 做主键，对外暴露不可枚举的外部 ID 邮箱或手机号做主键，换绑即灾难
同一邮箱多身份源 不自动合并，要求先登录再绑定或走邮箱验证 按邮箱自动合并，弱验证提供方即可接管账号
账号拆分 合并操作记录可回溯的审计日志，保留原身份映射 合并时直接删掉一侧记录，出错无法恢复
注销与数据保留 先置注销待清理状态并停止登录，按合规期限延迟物理删除，保留必要的交易与账务记录 立即物理删除，导致账务与审计数据断链
手机号回收复用 注销后释放唯一约束需要检查该号是否曾绑定过其他账号并留痕 直接复用，新用户登录进了老用户的账号

② 原理 · 权限模型：先想清楚要不要角色

搞清模型差异，能解决「每加一个角色都要改代码发版」以及「数据范围该不该塞进 RBAC」。

模型 判定依据 优势 失效场景
RBAC 角色 用户的角色是否包含某权限 直观、易配置、审计清楚 出现「除了某个部门的某类单据之外都能看」这类需求时，角色数量爆炸
权限点加角色分离 角色只是权限点的集合，代码里只判断权限点 新增角色不改代码，是大多数系统的最优解 权限点数量多时需要管理界面与分组，否则配置易错
ABAC 属性 用户属性、资源属性、环境属性共同决定 表达力强，能描述数据范围 规则难以测试与审计，用户问「为什么我看不到」时很难解释
关系型授权 用户与资源之间是否存在某种关系链 适合协作类产品的共享与继承 需要专门的关系存储与查询，自研成本高

实践建议很明确：代码里只判断权限点，不判断角色。角色是权限点的容器，属于配置数据。判断角色会让每次新增角色都要改代码并发版，而且很容易写出「管理员例外」这种散落各处的特判。数据范围（能看哪些记录）不要硬塞进 RBAC，它本质是资源归属判断，应该落在查询条件里。

⚠️
多租户下权限必须带租户维度

任何权限判断和任何数据查询都要带上租户标识，并且租户标识只能来自服务端确认过的身份，绝不能取自请求参数。缺失租户维度的权限判断在单租户测试环境永远是对的，上线后表现为跨租户数据泄露。稳妥做法是在数据访问层强制注入租户条件，让漏写变成编译期或运行期的显式错误，而不是靠每个开发记得加 where。

② 原理 · 登录体验与安全的平衡：按风险分级

搞清风险信号与措施的对应，能解决「加强安全就一定掉转化」这个假两难。

把所有用户都按最高风险对待会直接降低转化，正确做法是按风险分级触发额外验证。风险信号来自设备是否可信、IP 与常用地的偏离、行为频率、以及本次操作的敏感度。

风险信号 触发的措施 体验影响 注意
常用设备加常用地登录 直接通过，可用「记住我」延长会话 无 记住我要绑定设备标识，且有绝对上限（如 30 天）
新设备首次登录 登录后发通知，敏感操作再要求二次验证 低 通知必须包含时间地点与一键冻结入口
异地或异常时段 要求第二因素 中 IP 归属不准，不要作为唯一判据
连续失败达到阈值 分级：先加验证码，再按账号与 IP 维度延迟或锁定 中 具体阈值维度见站内安全篇，注意不要因此造成账号锁定型拒绝服务
敏感操作（改密、改绑、提现） 无条件二次验证，并校验最近一次认证时间 可接受 只看「已登录」是不够的，要看认证有多新

② 原理 · 可观测性与降级：认证挂了就是全站挂了

搞清该看哪些指标，能解决「接口全是 200，但没有一个用户能登录进来」这种监控盲区。

认证是所有请求的前置依赖，它的故障不会表现为「登录功能不可用」，而是表现为全站不可用。因此它的监控要按最高级别做，并且必须提前想好降级路径。

# 1) 登录成功率：跌破 95% 立即告警，按身份源拆分才能定位是哪家出问题
sum(rate(auth_login_total{result="success"}[5m])) by (provider)
  / sum(rate(auth_login_total[5m])) by (provider)

# 2) 令牌刷新失败率：它直接对应「用户莫名被登出」，也是刷新并发问题的探针
sum(rate(auth_refresh_total{result="invalid_grant"}[5m]))
  / sum(rate(auth_refresh_total[5m]))
# 经验阈值：持续高于 0.5% 就该去查客户端有没有做单飞刷新

# 3) 外部身份源可用性与延迟，第三方登录入口通常是首个故障点
histogram_quantile(0.99, sum(rate(idp_request_duration_seconds_bucket[5m])) by (le, provider))

# 4) 异常登录模式：同一账号多地登录、单 IP 大量失败
sum(rate(auth_login_total{result="failure"}[5m])) by (client_ip) > 5

# 5) 公钥拉取失败：一旦缓存过期且拉取持续失败，验签会全量失败
sum(rate(jwks_fetch_total{result="error"}[5m])) > 0
故障 可行降级 不能做的事
授权服务不可用 依赖已缓存的公钥继续验签，让在线用户不掉线；临时上调访问令牌有效期减少刷新依赖 跳过鉴权直接放行
会话存储不可用 短时间内接受本地缓存的会话判定结果，并把写操作降级为只读 会话查不到就当已登录
第三方身份源不可用 登录页禁用该入口并提示，保留其他登录方式 入口保留但点了就白屏或超时
短信或邮件通道不可用 切换备用通道，或临时改用其他第二因素 直接跳过第二因素校验
恢复瞬间的刷新风暴 刷新接口限流加抖动重试，客户端退避 让全部客户端同时重试把刚恢复的服务再打挂

③ 场景 · 不同阶段的系统该做到哪一步

上面的清单是完整形态，但一次做完既不现实也不必要。判断依据是「你现在有几种客户端、封禁的生效延迟容忍度、以及有没有外部身份源」，这三条决定了该停在哪一档。

场景 该做到哪一步 为什么停在这里 代价
MVP 阶段：一个 Web 应用，团队两三人 Cookie 会话加双超时、登录后换 ID、改密码失效全部会话、登录成功率告警 吊销能力天然具备，框架半天就能落地，此时引入令牌体系只是提前付成本 接入 App 时要补一整条令牌链路，界面上的会话列表也要另做
有了 App 或小程序，跨域成为常态 访问令牌 5 到 15 分钟 + 刷新令牌轮换 + 客户端单飞刷新 + 会话表一行一设备 多端拿不到 Cookie 的自动携带，但「踢设备」的能力必须保住，所以令牌只做传输载体 要长期维护刷新并发与设备识别不准确带来的产品体验问题
接入了第三方登录 身份表按「提供方 + 提供方内 UID」唯一、邮箱相同不自动合并、解绑保护、提供方故障时入口降级 外部身份源不可控，账号接管风险几乎全部集中在合并逻辑上 首登信息补全与解绑规则要产品配合，登录页要能按提供方灰度
开始卖给企业客户，需要 SSO 内部统一 OIDC，SAML 走适配层，支持按客户配置身份源，登出走后端通道并配重试队列 采购清单常把协议支持写成硬性要求，而协议适配是最耗人力的部分 每个客户一套配置，要做配置化、灰度与专门的对接文档
强合规或资金类业务 用户级失效时间点做到秒级封禁、敏感操作校验认证新鲜度与第二因素、认证与授权全链路审计 生效延迟容忍度是零，这一条直接否决纯自包含方案 每请求一次失效查询，审计数据的存储与保留期都要按合规算
规模上来，认证成为全站前置依赖 认证独立部署与独立限流、公钥本地缓存、刷新接口限流加客户端退避、会话表归档 认证的故障不表现为「登录不可用」而是「全站不可用」，必须先与业务解耦 多一套部署与容量规划，降级演练要定期做
预计将来会更换实现（自建换托管或反之） 第一天就把认证收敛到一个服务，业务只依赖内部统一的身份接口 更换实现时改动集中在一处，而不是散落在每个业务服务的登录逻辑里 抽象层本身要维护，早期会显得「多写了一层」

不适用边界：本篇只覆盖认证系统自己的工程问题。三类相邻问题不在这里解决——攻防参数与漏洞机理（口令哈希取值、多因素、越权分类、令牌存放位置的攻击面）见 越权与鉴权安全 与 CSRF 与点击劫持；协议报文层面的参数与校验点见 OAuth 2.0 与 OIDC 的协议细节 与 JWT 的结构与验签机制；指标采集与告警落地见 指标与监控，网关侧限流与超时参数见 Nginx 实践。整条路径的选型与分层回到 认证与授权的协议全景，本篇是这条路径的最后一环。

③ 场景 · 反模式对照：每条都对应一次真实事故

反模式 后果 正确做法
邮箱或手机号当用户主键 换绑即牵动所有外键，号码回收后新用户进了老账号 内部不可变 ID 做主键，登录标识放身份表
用纯无状态 JWT 却要做会话管理 会话列表和登出其他设备无法实现，最后靠临时黑名单打补丁 为刷新令牌保留服务端记录，访问令牌保持短有效期
刷新逻辑不处理并发 弱网与首屏并发下用户被莫名登出，客服问题难以复现 客户端单飞刷新，服务端加宽限期或家族容忍
没有登出其他设备能力 用户怀疑账号被盗时只能改密码，改密码又没有失效旧会话 提供会话列表与一键登出全部，改密码同时失效全部会话
角色硬编码在代码里判断 每次新增角色都要改代码发版，「管理员例外」散落各处 代码只判断权限点，角色作为配置数据
权限判断不带租户维度 单租户环境测不出来，上线后跨租户数据泄露 数据访问层强制注入租户条件，租户标识只取自服务端身份
认证服务没有降级方案 认证抖动直接等于全站不可用 公钥本地缓存、刷新限流、登录入口分级提示，但绝不放行未授权请求
刷新失败后静默无限重试 把一次故障放大成刷新风暴，恢复后又被打挂一次 失败即走登出流程，重试带退避与抖动

最容易踩的坑

❌
避坑清单
  • 刷新令牌单飞锁只做在模块级变量里：多标签页各有一份变量，五个标签页同时唤醒就是五次并发刷新。
  • 刷新失败不登出而是继续重试：一次网络抖动就能变成客户端对认证服务的持续压测。
  • 401 重试没有次数上限：刷新后仍 401 会导致无限递归，表现为浏览器卡死或流量激增。
  • 改密码只失效了当前会话：其他设备仍在线，这是安全评审必查项。用户表加一个失效时间点字段即可一次解决。
  • 会话记录只增不删：表膨胀到千万级后会话查询变慢，要有过期归档任务。
  • 刷新令牌原文存库：库一泄露等于所有用户的长期凭证泄露，只存哈希。
  • 按邮箱自动合并第三方身份：在允许任意填写邮箱的提供方注册同邮箱账号就能接管他人账号，必须检查已验证标记并要求显式绑定。
  • 解绑最后一个身份源没有拦截：用户解绑后失去全部登录方式，只能走人工找回。
  • 注销立即物理删除用户：账务、工单、审计日志的外键全部断裂，应先置状态再按合规期限清理。
  • 敏感操作只判断「已登录」：必须同时判断最近一次认证的时间与强度，否则一个长期会话就能完成改绑与提现。
  • 单点登出只清了身份提供方的会话：各子系统会话照旧有效，用户以为退出了其实没退。
  • 认证服务与业务服务共用一套限流与线程池：业务高峰把认证一起拖垮，故障范围立刻变成全站。
  • 监控只看接口成功率不看登录成功率：验证码通道故障时接口全是 200，但没人能登录进来。
