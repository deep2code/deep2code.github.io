GraphQL 的 N+1 与批量化：DataLoader 原理、失效场景与复杂度限制

🏷️ N+1 问题

N+1 是 GraphQL 上线后一定会遇到的问题，不是「如果代码写得不好才会遇到」。它源自执行模型本身：resolver 按字段独立取数，父层返回多少条记录，子字段的 resolver 就被调用多少次。理解这一点很重要，因为它决定了治理方式——你没法靠 code review 可靠地消灭它，只能靠架构上的批量化机制，加上限流兜底。

这篇讲透四件事：N+1 的结构性来源和它的乘性爆炸规模、DataLoader 的攒批原理与两个容易写错的致命约束、DataLoader 根本解决不了的四类场景该怎么办、以及为什么深度和复杂度限制是必需品而不是可选项。执行模型和 resolver 参数的基础见站内 GraphQL 类型系统与执行模型一篇。

为什么 N+1 是结构性的

看一个最普通的查询：取 10 个订单，每个订单要用户昵称。执行器先跑 Query.orders 拿到 10 条记录，然后对每一条记录分别调用一次 Order.user 的 resolver。这个 resolver 不知道自己正在被批量调用，它只看到一个 parent，于是老老实实发一次查询。1 次列表查询加 10 次用户查询，这就是 1+N。

sequenceDiagram autonumber participant E as 执行器 participant R1 as Query.orders participant R2 as Order.user participant DB as 数据库 E->>R1: 执行根字段 R1->>DB: 查订单列表 取 10 条 DB-->>R1: 返回 10 行 Note over E,R2: 执行器拿到 10 个父对象
对每个父对象独立调用子 resolver E->>R2: parent 是第 1 个订单 R2->>DB: 按 id 查用户 7 E->>R2: parent 是第 2 个订单 R2->>DB: 按 id 查用户 9 E->>R2: 第 3 到第 10 个订单 R2->>DB: 再发 8 次同样形状的查询 Note over R2,DB: 11 次往返 · 每个 resolver 都不知道
还有 9 个兄弟在做同样的事 E-->>E: 组装结果树

真正致命的是嵌套时的乘性放大：查询每加一层，查询数就乘以那一层的扇出。「20 个订单、每单 10 条明细、每条明细带商品和商家」这种再正常不过的页面需求，算式是 1 + 20 + 20 乘 10 + 200 乘 2 = 621 次查询。而这个查询在 Schema 上完全合法，客户端写起来只有十几行。

DataLoader 的攒批与分发

DataLoader 的机制出人意料地简单：load(key) 不立刻执行，而是把 key 推进待处理队列并返回一个 Promise；在当前事件循环 tick 结束时（Node 里是微任务队列排空的那个点），把攒到的所有 key 合成数组，调用一次你提供的 batchLoad(keys)；拿到结果后按下标把值分发回各个 Promise。

它能生效的前提正好和 GraphQL 的执行模型吻合：同一层字段是并行发起的，10 个 Order.user resolver 在同一个 tick 内都调了 load，所以能攒进同一批。这也解释了一个常见困惑——如果你在 resolver 里先 await 了别的异步操作再调 load，就可能错过攒批窗口，一批会被拆成好几批。

sequenceDiagram autonumber participant R as 10 个 Order.user resolver participant L as DataLoader 队列 participant B as batchLoad 函数 participant DB as 数据库 R->>L: load 7 返回 pending 的 Promise R->>L: load 9 重复 key 直接复用同一个 Promise R->>L: 其余 8 次 load 陆续入队 Note over L: 本 tick 内只攒 key
一次查询都不发 L->>B: tick 结束 一次性传入去重后的 keys 数组 B->>DB: 用一条 IN 查询取回这批 key DB-->>B: 返回若干行 顺序由数据库决定 Note over B: 关键一步 按 keys 顺序重排
查不到的位置补 null B-->>L: 与 keys 等长且同序的结果数组 L-->>R: 按下标逐个 resolve 对应的 Promise

整个机制只有几条约束，但每一条写错都有实际后果。

约束写错的样子后果怎么保证
返回值与 keys 等长同序直接 return 数据库返回的 rows某个 id 查不到时后面数据整体前移，A 用户拿到 B 用户的数据，而且不报任何错先建 Map 再按 keys 遍历取值，缺失位置显式填 null
loader 实例必须请求级在模块顶层创建后长期复用请求级缓存变成进程级缓存，跨请求脏读；带权限过滤的 loader 直接变成越权漏洞在 context 工厂里创建，随请求生灭
一对多要返回数组没有子项时返回 null客户端拿到 null 而不是空列表，非空列表类型还会触发错误冒泡按 key 预建空数组再填充
单条失败不要整批抛异常batchLoad 里直接 throw这一批所有 key 全部失败，一条坏数据拖垮整页把 Error 实例放在对应下标上
对象 key 要给 cacheKeyFn直接拿对象当 key默认按引用相等比较，缓存永不命中，还会重复入批提供 cacheKeyFn 把对象序列化成字符串
写后读要关缓存同一请求里改完再读同一个 key读到本请求早先缓存的旧值该字段的 loader 关缓存，或写操作后 clear 对应 key
❌
等长同序这条约束值得单独强调

它是唯一一类不报错、不崩溃、监控也看不出来，但会把数据串到别人身上的 bug。测试环境里数据齐全时永远正常，一旦线上有一条记录被软删除或权限过滤掉，返回数组就少一个元素，后面所有位置整体错位。写 batchLoad 时的固定动作就是：先把结果装进 Map，再 keys.map 逐个取，取不到填 null。Java 侧优先用 MappedBatchLoader，返回 Map 就从机制上避免了这个问题。

// loaders.js —— 每个请求创建一次，绝不能提到模块顶层做成单例
import DataLoader from 'dataloader';

export function createLoaders(db, remote) {
  return {
    // 1) 按主键批量：返回值必须与 keys 等长且同序，这是 DataLoader 唯一的硬契约
    userById: new DataLoader(async (ids) => {
      const rows = await db.query(
        'SELECT id, nickname, avatar_url FROM user WHERE id IN (?)', [ids]);
      const byId = new Map(rows.map((r) => [String(r.id), r]));
      // 必须按 keys 顺序逐个取，查不到的位置填 null。
      // 如果图省事写成 return rows：缺一条数据后面全部前移一位，
      // A 用户会拿到 B 用户的昵称，而且不报任何错 —— 最危险的一类实现 bug
      return ids.map((id) => byId.get(String(id)) ?? null);
    }, { maxBatchSize: 500 }),   // IN 列表过长时优化器会放弃索引，主动拆批

    // 2) 一对多：每个 key 返回一个数组，没有子项的位置填空数组而不是 null
    itemsByOrderId: new DataLoader(async (orderIds) => {
      const rows = await db.query(
        'SELECT id, order_id, title, quantity FROM order_item WHERE order_id IN (?)', [orderIds]);
      const grouped = new Map(orderIds.map((id) => [String(id), []]));
      for (const r of rows) grouped.get(String(r.order_id)).push(r);
      return orderIds.map((id) => grouped.get(String(id)));
    }),

    // 3) 批量里单条失败：把 Error 实例放到对应下标，只有那一次 load 会 reject，
    //    其余 key 照常返回。整批抛异常会让所有等待者一起失败，不要那么做
    profileById: new DataLoader(async (ids) => {
      const settled = await Promise.allSettled(ids.map((id) => remote.getProfile(id)));
      return settled.map((r, i) =>
        r.status === 'fulfilled' ? r.value : new Error('profile 加载失败 id=' + ids[i]));
    }, { cache: false }),   // 同一请求内写后立即读的字段要关缓存，否则读到旧值

    // 4) 复合 key：DataLoader 默认用严格相等比较 key，对象 key 必须给 cacheKeyFn
    stockBySkuAndWarehouse: new DataLoader(async (keys) => {
      const rows = await db.query(
        'SELECT sku_id, warehouse_id, qty FROM stock WHERE (sku_id, warehouse_id) IN (?)',
        [keys.map((k) => [k.skuId, k.warehouseId])]);
      const m = new Map(rows.map((r) => [r.sku_id + ':' + r.warehouse_id, r.qty]));
      return keys.map((k) => m.get(k.skuId + ':' + k.warehouseId) ?? 0);
    }, { cacheKeyFn: (k) => k.skuId + ':' + k.warehouseId }),
  };
}

// context 工厂里挂上去，随请求生灭
export const context = async ({ req }) => ({
  viewer: await auth(req),
  loaders: createLoaders(db, remote),
});

Java 侧的对应实现，以及跨服务场景下把攒批窗口调大的做法：

// graphql-java / Spring GraphQL：优先用 MappedBatchLoader，返回 Map 就天然不会顺序错位
@Component
public class UserBatchLoader implements MappedBatchLoaderWithContext<Long, User> {

    private final UserRepository repo;
    // 阻塞式 JDBC 不要跑在 ForkJoinPool.commonPool 上，会把公共池占死
    private final Executor executor;

    public UserBatchLoader(UserRepository repo, @Qualifier("loaderExecutor") Executor executor) {
        this.repo = repo;
        this.executor = executor;
    }

    @Override
    public CompletionStage<Map<Long, User>> load(Set<Long> keys, BatchLoaderEnvironment env) {
        return CompletableFuture.supplyAsync(() -> {
            List<User> users = repo.findAllByIdIn(keys);          // 一次 IN 查询
            // 缺失的 key 不出现在 Map 里，框架会自动补 null，不存在错位风险
            return users.stream().collect(Collectors.toMap(User::getId, Function.identity()));
        }, executor);
    }
}

// 注册：registry 必须每请求新建，然后放进 GraphQLContext
// 跨服务场景默认的“每批次结束就 dispatch”会攒不满，可以配一个几毫秒的调度窗口
DataLoaderOptions options = DataLoaderOptions.newOptions()
        .setMaxBatchSize(500)
        .setCachingEnabled(true);          // 请求级缓存，请求结束即丢弃

ScheduledDataLoaderRegistry registry = ScheduledDataLoaderRegistry.newScheduledRegistry()
        .register("userById", DataLoaderFactory.newMappedDataLoader(userBatchLoader, options))
        .schedule(Duration.ofMillis(2))    // 2ms 攒批窗口，换更大的批次
        .build();

// resolver 侧：拿 loader 而不是直接查库
@SchemaMapping(typeName = "Order", field = "user")
public CompletableFuture<User> user(Order order, DataFetchingEnvironment env) {
    DataLoader<Long, User> loader = env.getDataLoader("userById");
    return loader.load(order.getUserId());
}

DataLoader 解决不了的四类场景

DataLoader 的能力边界很明确：它只能把「一堆同形状的按 key 取数」合成一次调用。一旦每个父对象需要的不是「一个对象」而是「一段结果集」，攒批就失效了。这四类场景必须单独设计，硬套 DataLoader 只会写出一个假批量。

单个对象还是一段结果集"} Q1 -->|"单个对象或全部子项"| D1["标准 DataLoader

一条 SQL 取回所有父对象的前 N 条"] Q2 -->|"不支持"| D3["UNION ALL 拼接
或退化为受控并发查询"] Q1 -->|"只要个数或求和"| D4["GROUP BY 批量聚合
结果里缺失的 key 补 0"] Q1 -->|"过滤条件因父对象而异"| Q3{"条件能不能收敛成少数几组"} Q3 -->|"能"| D5["按条件分组 每组一次查询"] Q3 -->|"不能"| D6["改建模
把条件提到父层参数或预计算"] Q1 -->|"数据在别的服务"| Q4{"下游有批量接口吗"} Q4 -->|"有"| D7["网关侧 loader 调批量接口"] Q4 -->|"没有"| D8["受控并发加信号量
同时推动下游提供批量接口"]
场景为什么 DataLoader 不够解法代价
子列表要分页，每个父对象各取前 N 条攒批只能攒 key，攒不出「每个 key 各自的前 N 条」窗口函数一条 SQL 搞定；老版本数据库用 UNION ALLSQL 复杂度上升，UNION ALL 在 key 多时语句很长，必须拆批
需要聚合，比如每个订单的评论数逐个 count 就是 N 次查询一次 GROUP BY 批量算，loader 侧给缺失 key 补 0基本没代价，但要记得补 0 而不是留 null
过滤条件因父对象而异条件不同就没法合并成一条 IN 查询条件收敛成少数几组时按组批量；否则把条件上移到父层参数可能要改 Schema 设计，或引入预计算字段
跨服务调用下游只提供单条查询接口推动下游提供批量接口；短期用受控并发加信号量限制并发数跨团队协调成本；并发方案会放大下游压力，必须限流
子项本身还要再嵌套过滤排序批量结果无法表达每个父对象独立的排序窗口把这类字段改成独立的根查询，让客户端分两次请求牺牲一次往返，换来可控的查询形状
-- 场景一：每个订单各取最新 3 条物流轨迹。
-- DataLoader 能把 order_id 攒成一批，但攒不出“每个父对象各自的前 N 条”，
-- 直接 IN 查询再在内存里裁剪，会把全部轨迹都拉回来，数据量大时更糟。
-- MySQL 8.0 / PostgreSQL 用窗口函数一次搞定：
SELECT * FROM (
  SELECT t.order_id, t.happened_at, t.node_name,
         ROW_NUMBER() OVER (PARTITION BY t.order_id ORDER BY t.happened_at DESC) AS rn
  FROM logistics_trace t
  WHERE t.order_id IN (101, 102, 103)          -- 这一批 key 由 DataLoader 攒出来
) x
WHERE x.rn <= 3;

-- 场景二：每个订单的评论数。逐个 count 就是典型 N+1，一次 GROUP BY 批量算完，
-- 返回结果里没出现的 order_id 说明计数为 0，在 loader 侧补 0 而不是留 null。
SELECT order_id, COUNT(*) AS cnt
FROM comment
WHERE order_id IN (101, 102, 103)
GROUP BY order_id;

-- 场景三：MySQL 5.7 没有窗口函数，退化为 UNION ALL。
-- key 多了 SQL 会非常长，必须配合 maxBatchSize 拆批，一般 20 到 50 个一组。
(SELECT order_id, happened_at, node_name FROM logistics_trace
   WHERE order_id = 101 ORDER BY happened_at DESC LIMIT 3)
UNION ALL
(SELECT order_id, happened_at, node_name FROM logistics_trace
   WHERE order_id = 102 ORDER BY happened_at DESC LIMIT 3);

-- 判读：执行计划里 IN 列表过长导致 type 从 range 退化成 ALL 时，
-- 说明 maxBatchSize 设得太大，索引与执行计划判读见站内 MySQL 相关文章。

批量化之外的三种手段

DataLoader 解决的是「次数」，下面三种解决的是「每次的成本」。它们不互斥，但引入顺序有讲究：先把 DataLoader 铺满，再考虑这些，否则容易在错误的层次上做优化。

手段做什么收益代价与失效场景
分层缓存DataLoader 管请求内去重，外部缓存管跨请求复用热点对象查询量下降一个数量级多了一致性问题：写操作要精确失效；带权限的数据缓存要把身份维度带进 key，否则越权
投影下推用 info 解析客户端实际请求的字段，只 SELECT 需要的列避免 select 星号，宽表场景能省掉大量 IO 和网络传输实现复杂度高：要处理片段、别名、接口多态；字段与列的映射一旦维护不住就会漏字段，建议只对少数宽表做
预加载 JOIN在父 resolver 里一次 JOIN 把子数据取出来塞进 parent，子 resolver 直接读 parent连 loader 的一次往返都省了，层数固定的场景最划算客户端没请求子字段时白做了 JOIN；关系是一对多时行数会膨胀，要在内存里去重
字段级超时与降级给每个外部调用设独立超时，超时返回 null一个慢下游不会拖死整个查询要求该字段是可空的，否则错误冒泡把父对象打成 null

投影下推这条要特别说一句：它经常被当成 GraphQL 的标配收益宣传，实际落地成本很高。info 里的字段节点要处理内联片段、命名片段、别名、以及接口和联合的多态分支，还要维护字段到列的映射表。更稳妥的做法是只对确实很宽的表做下推，其他表把列写死在 service 层。想彻底解决就上支持投影的查询层，但那又引入了另一套复杂度。

深度与复杂度限制是必需品

只要你的 GraphQL 端点对外可达，就必须假定有人会构造恶意查询。GraphQL 的特性使得一个几十字节的查询能让后端产生指数级的工作量：任意两个互相引用的类型（用户有好友，好友也是用户）就能让攻击者写出无限深的嵌套；即使没有循环引用，深度嵌套加上大 first 参数也足以打满数据库连接池。

更要紧的是，这类请求在 HTTP 层面看完全正常：一个 POST、一个 200、一个正常大小的请求体，WAF 和网关限流都不会拦它。只按 QPS 限流对 GraphQL 是无效的，因为一个请求的成本可以是另一个请求的一万倍。

深度限制8 到 12 层，按业务最深合法查询加两层循环引用造成的无限嵌套浅而宽的查询，比如一层里要 500 条并各带明细
复杂度评分标量 1 分、关联对象 2 到 5 分、列表字段乘 first；总上限先设线上 p99 的两倍宽查询与大分页的组合权重设得不准时会误杀正常查询，需要按数据先跑影子模式
别名与体积限制请求体不超过 100KB，同名字段别名数量设上限用别名把同一个昂贵字段请求上千次单个合法但昂贵的字段

持久化查询白名单构建期生成 manifest，生产只接受 hash几乎一切构造型攻击，这是最彻底的方案不适用于对外开放的公共 API，那种场景只能靠评分加配额
自动持久化查询省带宽用，不要当安全机制什么都拦不住，客户端可以先注册任意查询常被误认为等价于白名单，这是个流传很广的误解
// server.js —— 深度和复杂度限制必须挂在执行之前，此时还没有任何数据库查询发出去
import { ApolloServer } from '@apollo/server';
import depthLimit from 'graphql-depth-limit';
import { getComplexity, simpleEstimator, fieldExtensionsEstimator } from 'graphql-query-complexity';
import { GraphQLError } from 'graphql';
import manifest from './persisted-manifest.json' assert { type: 'json' };

const MAX_DEPTH = 10;         // 业务查询超过 8 层基本都是写错了或在探测
const MAX_COMPLEXITY = 1000;  // 先按线上 p99 的两倍设，再按周收紧

const complexityPlugin = {
  async requestDidStart() {
    return {
      // didResolveOperation: AST 和变量都有了，但还没开始执行 —— 算分的正确时机
      async didResolveOperation({ request, document, schema }) {
        const complexity = getComplexity({
          schema, query: document, variables: request.variables,
          estimators: [
            // 字段上通过 extensions.complexity 声明权重，列表字段按 first 做乘算：
            // orders 字段权重 2，first=100 时这一支就是 200 分
            fieldExtensionsEstimator(),
            simpleEstimator({ defaultComplexity: 1 }),
          ],
        });
        if (complexity > MAX_COMPLEXITY) {
          throw new GraphQLError('查询过于复杂 ' + complexity, {
            extensions: { code: 'QUERY_TOO_COMPLEX', complexity, max: MAX_COMPLEXITY,
                          http: { status: 400 } },
          });
        }
      },
    };
  },
};

// 最彻底的方案：只放行构建期登记过的查询。注意这和 APQ 不是一回事，
// APQ 允许客户端先注册任意查询再按 hash 调用，只省带宽，不是安全机制。
const ALLOWED = new Map(Object.entries(manifest));   // sha256 -> query 文本
const persistedOnlyPlugin = {
  async requestDidStart({ request }) {
    if (process.env.NODE_ENV !== 'production') return;
    const hash = request.extensions?.persistedQuery?.sha256Hash;
    if (!hash || !ALLOWED.has(hash)) {
      throw new GraphQLError('查询不在白名单中', {
        extensions: { code: 'PERSISTED_QUERY_NOT_ALLOWED', http: { status: 400 } },
      });
    }
    request.query = ALLOWED.get(hash);   // 用服务端登记的文本，忽略客户端传来的
  },
};

export const server = new ApolloServer({
  schema,
  validationRules: [depthLimit(MAX_DEPTH)],   // 校验阶段拦深度
  plugins: [complexityPlugin, persistedOnlyPlugin],
  // 还要配超时：单次执行超过 3 秒直接掐掉，避免慢查询堆积把连接池占满
});

怎么发现线上已经存在的 N+1

N+1 的隐蔽之处在于它在小数据量下完全不显形。开发环境十条测试数据，1+10 次查询也就几毫秒，接口看起来挺快；上线后列表页一页 50 条、每条带三层关联，同一段代码就变成几百次查询。所以不能靠「感觉慢了再查」，要主动检测。

手段怎么做怎么判读
链路追踪打开一次慢请求的 trace，展开 resolver span同一个父 span 下出现几十个同名子 span，且数量约等于父层返回条数，就是 N+1。链路追踪的接入与采样见站内链路追踪一篇
SQL 按 digest 聚合查 performance_schema 的语句摘要表，或用 pt-query-digest 跑慢日志同一 digest 的执行次数远高于请求数，形状又是按主键单条查，基本可以确定没批量
DataLoader 命中率统计每个 loader 的 load 调用次数与 batch 触发次数两者比值接近 1 说明每次只攒到一个 key，攒批没生效，通常是 resolver 里提前 await 了别的东西
开发环境查询计数断言在集成测试里包一层数据源计数器，断言单次请求的查询数不超过阈值这是唯一能防止 N+1 回归的手段，新加字段时会直接把测试打红
字段级耗时统计用插件按 operationName 加字段名统计总耗时与调用次数调用次数异常高的字段就是嫌疑字段，实现见站内 Apollo Server 工程实践一篇
压测时观察连接池压测中看数据库连接等待与活跃连接数并发不高但连接池被打满，通常是单请求内查询次数过多，不是并发问题
✅
把查询计数写进测试是性价比最高的一步

在测试里给数据源包一层计数器，对关键查询断言「查询次数不超过 6 次」。这条断言会在有人新加一个没走 loader 的关联字段时立刻失败，比任何 code review 都可靠。阈值按查询层数设，不要按数据条数设，因为正确批量化之后次数就该和数据量无关。

反模式速查

反模式表现后果正确做法
关联字段不用 DataLoaderresolver 里直接按 parent.xxxId 查一次数据量一上来查询次数线性爆炸所有关联字段一律走 loader
DataLoader 做成全局单例在模块顶层创建后复用跨请求缓存污染，权限数据泄露，属于安全问题在 context 工厂里每请求创建
batchLoad 返回值不补齐直接 return 查询结果缺失记录导致数据整体错位，静默串号建 Map 后按 keys 顺序取，缺失填 null
整批抛异常batchLoad 里遇到一条坏数据就 throw整页字段一起失败把 Error 放在对应下标
没有深度与复杂度限制端点裸奔一个几十字节的查询就能打满连接池校验阶段挂深度限制加复杂度评分
对外开放自省生产环境自省查询可用攻击者拿到完整 Schema，能精确构造最贵的查询对外关闭或加认证
把自动持久化查询当白名单以为开了 APQ 就安全了客户端仍可注册任意查询，防护等于零用构建期 manifest 做真正的白名单
resolver 里串行调多个下游连续 await 三个远程调用耗时相加，且破坏 DataLoader 的攒批窗口能并行的用并行，跨服务批量走 loader
只按 QPS 限流网关按请求数限流就算完事请求成本相差几个数量级，限流形同虚设按复杂度分数计费式限流
❌
最容易踩的坑

1. batchLoad 直接返回数据库结果。少一条记录，后面全部错位，A 用户看到 B 用户的数据，不报错、不告警，靠肉眼永远发现不了。

2. DataLoader 提到模块顶层。跨请求缓存污染，带权限过滤的数据直接泄露给其他用户，这是安全事故而不是性能问题。

3. 一对多的 loader 在没有子项时返回 null。非空列表类型立刻触发错误冒泡，把整个父对象打成 null。

4. 在 resolver 里先 await 一个远程调用再 load。攒批窗口被打断，10 个 key 分成 10 批，DataLoader 形同没装。

5. maxBatchSize 不设或设得过大。IN 列表几千个 id，执行计划从范围扫描退化成全表扫描，比 N+1 还慢。

6. 用 GROUP BY 批量算计数后，没给结果里缺失的 key 补 0。前端拿到 null，展示成空白而不是 0。

7. 以为窗口函数到处都能用。MySQL 5.7 不支持，必须退化成 UNION ALL 或受控并发，迁移前要确认版本。

8. 给缓存的 key 里不带用户身份维度。带权限过滤的数据被其他用户命中，又是一次越权。

9. 只做深度限制不做复杂度评分。一层深、500 条宽、每条再带明细的查询轻松绕过深度限制。

10. 复杂度上限凭感觉拍。上线即误杀正常查询，应该先跑影子模式只记录不拦截，按线上分布定阈值。

11. 生产环境留着自省和调试沙盒。等于把「哪些字段最贵」的说明书交给攻击者。

12. 开发环境数据太少，从来没触发过 N+1。上线当天列表页直接把数据库打满，必须用查询计数断言在 CI 里卡住。
