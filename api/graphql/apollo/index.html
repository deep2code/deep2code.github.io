Apollo Server 4 工程实践：context、插件、错误脱敏与安全必配项

🏷️ Apollo

Apollo Server 是目前最常用的 GraphQL 服务实现，4.x 相比 3.x 是一次不小的重构：不再内置各框架的集成，生命周期钩子全部收进插件体系，错误处理接口也变了。这篇不讲「怎么跑起来 hello world」，讲的是一个对外提供服务的 Apollo Server 上线前必须配好的那些东西：context 的边界、插件埋点、错误脱敏、自省与沙盒的关闭、缓存为什么基本失效、订阅怎么水平扩展、以及字段使用统计怎么采集。

类型系统、可空性和错误模型的基础见站内 GraphQL 类型系统与执行模型一篇；DataLoader 与复杂度限制的原理见站内 N+1 与批量化一篇，这里只讲在 Apollo 里怎么落地。

Server 4 变了什么

方面Server 3Server 4迁移时要注意
框架集成内置 express、koa、lambda 等一堆包核心与框架解耦，只提供 startStandaloneServer 与 expressMiddleware，其余由社区包提供不要再 import apollo-server-express，改用 @apollo/server 加对应中间件
启动方式构造后直接 listen必须先 await server.start 再挂中间件，standalone 模式除外忘了 await start 会在第一个请求时报错
生命周期钩子部分在构造参数上，部分在插件里统一收进插件体系原来的 formatResponse、didEncounterErrors 等参数要改写成插件
错误类ApolloError、UserInputError 等一组子类统一用 GraphQLError 加 extensions.code错误码从类名改为字符串常量，客户端契约要同步
堆栈输出默认带 stacktrace生产模式默认不带，由 includeStacktraceInErrorResponses 控制不要为了排查方便在生产打开这个开关
落地页默认 GraphQL Playground默认 Apollo Sandbox，可用插件禁用生产必须显式禁用，默认是开的

下面这份初始化代码把必配项都写进去了，可以直接当模板用：

// server.js —— Apollo Server 4 完整初始化，可直接跑
import { ApolloServer } from '@apollo/server';
import { expressMiddleware } from '@apollo/server/express4';
import { ApolloServerPluginLandingPageDisabled } from '@apollo/server/plugin/disabled';
import { unwrapResolverError } from '@apollo/server/errors';
import express from 'express';
import http from 'http';
import { GraphQLError } from 'graphql';

const isProd = process.env.NODE_ENV === 'production';
const app = express();
const httpServer = http.createServer(app);

const server = new ApolloServer({
  typeDefs, resolvers,
  // 生产必须关自省：开着等于把完整 Schema 和所有参数送给攻击者
  introspection: !isProd,
  // 生产必须禁掉落地页沙盒，否则任何人都能在浏览器里直接打查询
  plugins: [
    ...(isProd ? [ApolloServerPluginLandingPageDisabled()] : []),
    metricsPlugin, complexityPlugin,
  ],
  validationRules: [depthLimit(10)],
  // formatError 是唯一的对外出口，脱敏只在这里做一次
  formatError: (formattedError, originalError) => {
    const raw = unwrapResolverError(originalError);
    // 业务侧主动抛的 GraphQLError 带了稳定 code，原样透出
    const code = formattedError.extensions?.code;
    if (code && code !== 'INTERNAL_SERVER_ERROR') {
      return { message: formattedError.message, path: formattedError.path,
               extensions: { code, traceId: currentTraceId() } };
    }
    // 系统错误：内部记全量堆栈，对外只给一句通用文案加 traceId
    logger.error({ err: raw, path: formattedError.path }, 'graphql internal error');
    return {
      message: isProd ? '服务异常，请稍后重试' : formattedError.message,
      path: formattedError.path,
      // 绝不能把 stacktrace 带出去，Server 4 在生产模式下默认不带，
      // 但只要有人设了 includeStacktraceInErrorResponses 就会漏，这里再兜一层
      extensions: { code: 'INTERNAL_SERVER_ERROR', traceId: currentTraceId() },
    };
  },
});

await server.start();

app.use('/graphql',
  express.json({ limit: '128kb' }),   // 请求体上限，防超大查询文本
  expressMiddleware(server, {
    // context 函数每个请求执行一次，请求级依赖都在这里创建
    context: async ({ req }) => {
      const token = req.headers.authorization;
      // 注意：这里做重 IO 会拖慢每一个请求，包括不需要身份的公开查询。
      // verifyToken 必须是本地验签或带本地缓存，不要每请求查一次用户表
      const viewer = token ? await auth.verifyToken(token) : null;
      return {
        viewer,
        traceId: req.headers['x-trace-id'] ?? randomUUID(),
        loaders: createLoaders(db, viewer),   // 请求级 DataLoader，随请求销毁
        log: logger.child({ traceId: req.headers['x-trace-id'] }),
      };
    },
  }));

httpServer.listen(4000);

context 函数：每请求一次，别在里面做重活

context 函数每个请求执行一次，这是它最重要的性质，也是它最容易被滥用的原因。放在这里的东西天然具有请求级生命周期，正好适合三类依赖：认证解析出来的身份、DataLoader 实例、数据库连接或事务句柄。

反过来，它也是全局路径上的串行瓶颈：任何放进去的 IO 都会加到每一个请求的耗时上，包括那些根本不需要它的公开查询。常见的错误是在 context 里同步查一次用户表、查一次权限表、拉一次配置中心。正确做法是认证走本地验签，权限和配置走带 TTL 的本地缓存，真正需要按用户查的数据交给 resolver 按需触发。

放进 context 的东西是否合适原因
解析后的当前用户身份合适字段级鉴权必须用它；前提是本地验签或带缓存，不要每请求查库
DataLoader 实例必须放这里请求级缓存的唯一正确位置，做成全局单例会导致跨请求越权
traceId 与带上下文的 logger合适排障时靠它把一次查询的所有日志串起来
数据库连接或事务句柄合适，但要小心连接在整个请求生命周期内被占用，慢查询会放大连接池压力
每请求查一次用户完整档案不合适大部分查询用不到，白付一次 IO；应交给 loader 按需加载
每请求拉一次远端配置不合适把配置中心的抖动直接传导到所有请求上，应本地缓存加定时刷新
可变的共享状态不合适并发字段解析会同时读写它，容易写出难复现的竞态

插件体系与请求生命周期

Server 4 把所有埋点能力都交给插件。理解钩子的触发顺序很重要，因为做什么事必须挂在对的钩子上：复杂度校验要在执行之前，否则算完分数数据库查询已经发出去了；响应改写只能在最后一步。

sequenceDiagram autonumber participant C as 客户端 participant S as Apollo Server participant P as 插件链 participant E as 执行器 C->>S: POST 带 query 与 variables S->>P: requestDidStart 开始计时 S->>S: 解析查询文本为 AST S->>P: didResolveSource 与 parsingDidStart S->>S: 对着 Schema 做校验 含自定义规则 S->>P: validationDidStart 深度限制在这里生效 S->>P: didResolveOperation 拿到 operationName
复杂度评分与白名单校验挂这里 Note over P: 此刻还没有任何数据库查询发出
是唯一能低成本拒绝请求的时机 S->>E: 开始执行 E->>P: executionDidStart 可返回 willResolveField 做字段级埋点 E-->>S: data 与 errors S->>P: didEncounterErrors 按错误码计数 S->>P: willSendResponse 记录耗时与响应大小 P-->>C: 返回响应
钩子能拿到什么适合做什么注意
requestDidStart请求头、原始请求体开始计时、透传 traceId还拿不到 operationName，不要在这里打业务标签
validationDidStartAST深度限制等校验规则的观测校验规则本身通过 validationRules 传入更合适
didResolveOperationoperationName、operation 类型、变量复杂度评分、持久化查询白名单、按 operation 的配额在这里抛错的成本最低，因为还没执行
executionDidStart执行上下文返回 willResolveField 做字段级耗时全量开启开销明显，必须采样
didEncounterErrorserrors 数组按 extensions.code 分类计数与告警这是唯一能可靠统计错误率的地方，状态码永远是 200
willSendResponse最终响应体耗时直方图、响应体大小、慢查询日志、响应改写改写响应要小心，别把 errors 吞掉

监控这件事有一条必须强调：所有指标都要按 operationName 打，不能按 URL 打。GraphQL 只有一个端点，按 URL 打点的结果是一条毫无用处的曲线。顺带一定要给匿名查询单独留一个标签，线上如果匿名查询占比很高，说明客户端没给查询命名，后续所有分析都会失去抓手。

// plugins/metrics.js —— 监控必须按 operationName 打点，不能按 URL
// 所有查询都打在同一个 /graphql 上，按 URL 统计等于没有统计
export const metricsPlugin = {
  async requestDidStart(ctx) {
    const start = process.hrtime.bigint();
    // 此时还没解析出 operationName，只能在后面的钩子里拿
    let opName = 'unknown';
    let opType = 'unknown';

    return {
      // 解析完成：拿到 AST，可以做深度检查
      async didResolveOperation({ operationName, operation }) {
        opName = operationName ?? 'anonymous';   // 匿名查询要单独统计，通常是漏配
        opType = operation.operation;            // query / mutation / subscription
      },

      // 执行期出现的错误，逐条按错误码计数
      async didEncounterErrors({ errors }) {
        for (const e of errors) {
          metrics.counter('graphql_errors_total', {
            op: opName, code: e.extensions?.code ?? 'UNKNOWN',
          }).inc();
        }
      },

      // 响应即将发出：唯一能同时拿到耗时和结果的地方
      async willSendResponse({ response }) {
        const ms = Number(process.hrtime.bigint() - start) / 1e6;
        const body = response.body;
        const hasErrors = body.kind === 'single'
          ? Boolean(body.singleResult.errors?.length)
          : false;
        // 关键指标三件套：按 operation 的耗时分布、是否含错误、响应体大小
        metrics.histogram('graphql_duration_ms', { op: opName, type: opType }).observe(ms);
        metrics.counter('graphql_requests_total',
          { op: opName, status: hasErrors ? 'partial_or_failed' : 'ok' }).inc();
        if (ms > 1000) ctx.contextValue.log.warn({ op: opName, ms }, 'slow operation');
      },

      // 字段级耗时：用 executionDidStart 返回 willResolveField，
      // 只在采样命中时开启，全量开会带来可观的开销
      async executionDidStart() {
        if (Math.random() > 0.01) return;        // 1% 采样
        return {
          willResolveField({ info }) {
            const t0 = process.hrtime.bigint();
            return () => {
              const cost = Number(process.hrtime.bigint() - t0) / 1e6;
              // 字段级调用次数就是发现 N+1 的直接证据
              metrics.histogram('graphql_field_ms',
                { field: info.parentType.name + '.' + info.fieldName }).observe(cost);
            };
          },
        };
      },
    };
  },
};

错误处理：formatError 是唯一出口

Server 4 统一用 GraphQLError 加 extensions.code 表达错误，formatError 是响应发出前的最后一道处理。它的职责只有两件：脱敏和保证错误码稳定。

错误来源extensions.codeformatError 该怎么处理日志级别
业务主动抛出的校验失败BAD_USER_INPUT原样透出 message 与 code，message 要能直接给用户看info
未登录或权限不足UNAUTHENTICATED 或 FORBIDDEN原样透出，配合 extensions.http.status 让 HTTP 层也带上状态warn，突增要告警
下游超时熔断自定义如 DOWNSTREAM_UNAVAILABLE透出通用文案，带上 traceId 便于用户反馈时定位error
数据库异常、空指针等INTERNAL_SERVER_ERROR内部记全量堆栈，对外只给一句通用文案加 traceIderror 并告警
查询语法或校验错误GRAPHQL_PARSE_FAILED 等开发环境详细提示，生产简化，因为正常客户端不该发出非法查询warn
❌
生产环境泄漏堆栈是最常见的 GraphQL 信息泄露

直接 return formattedError 等于把内部错误原文交出去。真实案例里泄漏过数据库表名和 SQL 片段、内部服务域名与端口、文件系统路径与项目结构、依赖库版本号。Server 4 在生产模式下默认不带堆栈，但只要有人为了排查方便打开 includeStacktraceInErrorResponses，或者把原始异常 message 直接塞进 GraphQLError，就一样会漏。稳妥做法是在 formatError 里对 INTERNAL_SERVER_ERROR 一律换成固定文案，只保留 traceId。

⚠️
自动持久化查询不是安全机制

APQ 的流程是：客户端先只发查询的 hash，服务端没见过就让客户端把完整文本补上来注册，之后同一 hash 直接复用。任何客户端都能注册任意查询，所以它的作用只有省请求带宽、以及配合 GET 让查询可以被 CDN 缓存。真正的防护是构建期白名单：查询清单随服务一起发布，生产环境只认清单里的 hash，不在清单里的一律拒绝。把 APQ 当白名单用，是我见过传播最广的 GraphQL 安全误解。

缓存：为什么基本失效，以及怎么找回一部分

REST 的缓存能力大半来自 HTTP 语义：GET 加 URL 天然是缓存键，配上 ETag 和 Cache-Control，CDN 和浏览器就能替你挡掉大量流量。GraphQL 默认把这套全丢了——同一个 URL、POST 方法、查询在请求体里，缓存中间件无法区分两个请求，只能全部穿透到源站。

缓存层次在 GraphQL 里怎么用能挡住多少代价与坑
CDN 与浏览器缓存只读查询改用 GET 加 APQ，把 hash 和变量放进查询串热点公共查询命中率可以做得很高URL 长度限制；带身份的查询不能进共享缓存，必须标 private
整响应缓存responseCache 插件配合 cacheControl 指令，按 Schema 声明的 maxAge 缓存整个响应公共内容型查询效果好缓存键必须带上身份维度，漏了就是越权；任一字段标 private 会让整个响应不可共享缓存
字段级 maxAge在 Schema 上给字段标 cacheControl，整体 maxAge 取所有字段的最小值决定上面两层的有效期只要有一个字段标了 maxAge 为 0，整个响应就不缓存，排查时容易找不到是哪个字段
请求内去重DataLoader 的缓存消除同一请求内的重复取数必须请求级，细节见站内 N+1 一篇
跨请求数据缓存loader 背后接 Redis 等外部缓存热点对象的主要挡量层写操作要精确失效；缓存键必须带权限维度

结论是：GraphQL 的缓存要靠应用层自己搭，而且每一层都要处理「带身份的数据不能进共享缓存」这个问题。如果你的业务本来严重依赖 CDN，这件事的成本要提前算进选型账单。

订阅的生产化

订阅在单机开发时毫无难度，水平扩展时才暴露真正的问题：内存里的 PubSub 只在单进程内有效。用户连在 A 实例，事件由处理写请求的 B 实例发出，A 上的订阅者收不到任何东西。这个 bug 在本地和单实例测试环境永远不会出现。

B 的事件永远到不了 A 上的订阅者
生产化事项做法不做的后果
传输协议用 graphql-ws；仅需服务端单向推送时用 SSE 更省事老的 subscriptions-transport-ws 已停止维护，存在已知缺陷
外部 PubSubRedis 或 Kafka 做事件广播多实例下订阅者随机收不到消息
建连鉴权在连接初始化消息里校验凭证，拒绝就直接断开未认证连接可以订阅任意 topic，直接数据泄露
推送前二次鉴权每次推送前检查订阅者当前是否仍有权限权限被撤销后仍在持续收数据
连接数与心跳压测确定单实例上限，配心跳与空闲超时文件描述符耗尽；半开连接堆积
反压处理推送速率超过消费能力时丢弃或合并事件慢客户端把服务端内存吃满

重构成本改名要手工同步两处低，IDE 重命名即可
大型 Schema 的组织按域拆文件再合并，结构清晰依赖代码组织能力，容易散
前端参与度高，前端可以直接读和提意见低，前端只能看生成产物
适合谁多团队协作、Schema 需要评审后端单团队掌控、语言类型系统强

不管选哪条路线，两件事都必须做。第一是CI 里的破坏性变更检测：把上一版 Schema 存成快照，每次提交做 diff，删字段、改类型、参数由可选变必填这些一律拦下，需要放行时走显式审批。第二是字段级使用统计，它是安全删字段的唯一前提。采集方式就是上面那个插件里的 willResolveField，把 父类型名.字段名 作为标签计数；成本敏感时可以只对标了废弃的字段全量统计，其余采样。

测试上有两层。resolver 单测直接调函数，注入假的 parent 和 context，验证取数与权限逻辑；集成测试用 server.executeOperation，不必起 HTTP 服务，还能顺手注入一个查询计数器，把「防 N+1 回归」变成一条断言。

// __tests__/order.test.js —— 集成测试用 executeOperation，不用起 HTTP 服务
import assert from 'node:assert';
import { ApolloServer } from '@apollo/server';

test('订单详情返回明细，且越权时 email 为 null', async () => {
  const server = new ApolloServer({ typeDefs, resolvers });
  let sqlCount = 0;
  const db = { query: (...a) => { sqlCount++; return fakeDb.query(...a); } };

  const res = await server.executeOperation({
    query: `query Q($id: ID!) { order(id: $id) { id items { id } user { nickname email } } }`,
    variables: { id: '1001' },
  }, {
    // 第二个参数就是 contextValue，测试里可以直接注入假身份与假 loader
    contextValue: { viewer: { id: 'u2' }, loaders: createLoaders(db, { id: 'u2' }), log: noopLog },
  });

  assert.equal(res.body.kind, 'single');
  const { data, errors } = res.body.singleResult;
  assert.equal(errors, undefined);
  assert.equal(data.order.user.email, null);    // 非本人，字段级权限返回 null 而不是抛错

  // 防 N+1 回归的断言：阈值按查询层数设，不按数据条数设。
  // 有人新加一个没走 loader 的关联字段时，这里会立刻变红
  assert.ok(sqlCount <= 4, '查询次数超标 ' + sqlCount);
});

反模式速查

反模式表现后果正确做法
生产开着自省与沙盒线上能拉 Schema，能打开调试页面攻击者拿到完整字段清单，直接对生产库构造查询introspection 设 false，挂 LandingPageDisabled
DataLoader 放模块顶层全局单例复用跨请求缓存污染，权限数据泄露在 context 函数里创建
formatError 直接返回原始错误一行 return formattedError堆栈、表名、内部域名全部泄漏对内部错误统一换成固定文案加 traceId
监控按 URL 打点网关按路径统计所有流量一条曲线，且错误率恒为零按 operationName 打点，单独统计 errors 数组
没有复杂度限制只配了 depthLimit 或什么都没配浅而宽的查询轻松打满连接池在 didResolveOperation 里算分并拒绝
把 APQ 当白名单开了自动持久化查询就认为安全客户端仍可注册任意查询，防护为零构建期 manifest 做真白名单
订阅不鉴权建连时不校验凭证任何人可订阅任意 topic，持续窃取数据连接初始化校验，推送前再校验一次
context 里做重 IO每请求查用户表与权限表所有查询都被拖慢，包括公开查询本地验签加本地缓存，按需数据交给 loader
字段级鉴权靠网关指望 API 网关拦网关看不见字段，等于没有鉴权在 resolver 或指令里逐字段判断
❌
最容易踩的坑

1. 忘了 await server.start 就挂中间件。Server 4 的硬要求，第一个请求才会报错，本地偶尔能蒙过去。

2. 生产环境留着自省。这是对外暴露的 GraphQL 服务最常见的配置疏漏，等于把内部数据模型完整交出去。

3. 生产环境留着 Sandbox 落地页。默认是开的，必须显式挂插件禁用。

4. formatError 直接返回原始错误。堆栈里带着表名、SQL 片段、内部服务地址和文件路径。

5. 为了排查方便打开 includeStacktraceInErrorResponses 然后忘了关。这类临时开关最容易留在生产。

6. 在 context 函数里每请求查一次数据库。所有请求付这个成本，包括不需要身份的公开查询。

7. DataLoader 在模块顶层创建。跨请求命中别人的数据，是越权而不是脏读。

8. 指标按 URL 或按路径打。GraphQL 只有一个端点，必须按 operationName，还要给匿名查询留标签。

9. 以为状态码能反映成败。执行阶段错误固定返回 200，错误率只能靠 didEncounterErrors 统计。

10. 把 APQ 当成查询白名单。它只省带宽，任何客户端都能注册新查询。

11. 订阅只在建连时鉴权。权限撤销后连接还活着，数据继续推送。

12. 多实例部署用内存版 PubSub。用户连在 A 实例、事件从 B 实例发出，订阅静默失效，本地测试永远复现不了。

13. 给字段标了 cacheControl maxAge 为 0 却没意识到它会让整个响应不可缓存。排查时很难定位是哪个字段拉低了整体有效期。
