GraphQL 类型系统与执行模型：Schema、resolver 与错误冒泡

🏷️ GraphQL

很多人认识 GraphQL 是从「前端可以自己挑字段」开始的，然后就去背 query 语法。这个切入点会让你在上线后被一连串问题打脸：为什么一个下游服务抖动，整个订单对象变成了 null；为什么监控面板上所有请求都是 200，错误率永远是零；为什么一个明显没人用的字段，谁也不敢删。这些问题的答案全在类型系统和执行模型里，跟查询语法没什么关系。

这篇把 GraphQL 当成「一套强类型 Schema 加一个逐字段执行器」来讲：Schema 为什么是前后端唯一契约、可空性怎么决定一次报错的破坏半径、执行器怎么把一次查询展开成 resolver 调用树、错误为什么不能靠 HTTP 状态码判断、以及「不做版本只做增删」这套演进哲学成立的前提条件。N+1 在这里只点明结构性来源，完整展开见站内 GraphQL 性能与 N+1 一篇；REST 与 GraphQL 的选型账单见站内 API 风格选型一篇。

Schema 是契约本身，不是文档

SDL 写出来的 Schema 在服务启动时会被编译成一张可执行的类型图，包含每个类型、字段、参数、返回值和可空性。关键差别在于这份类型信息在运行时是可被查询的：客户端发一个自省查询（__schema、__type），就能在完全不看服务端代码的前提下拿到完整契约。

REST 当然也能有契约，但 OpenAPI 是「另外写的一份文档」，实现改了文档不一定改，漂移是默认状态。GraphQL 的 Schema 就是执行时真正在用的那一份，字段名、类型、可空性不可能和实现不一致。需要说清楚的是：Schema 只锁死了形状，resolver 的业务语义仍然会漂移（比如 totalCount 到底含不含已取消订单），这部分靠字段描述和评审，不是类型系统能管的。

三个根类型和两套类型世界

三个根类型的差别不只是命名约定，执行语义是真的不同：Query 的同层字段并行执行；Mutation 的根字段严格串行（规范要求，因为写操作之间有顺序依赖），但 mutation 返回对象内部的子字段又回到并行；Subscription 一个操作只允许一个根字段，因为它对应一条事件流。

内置标量只有五个，其中两个是常年踩坑点。Int 是32 位有符号整数，上限 2147483647；毫秒时间戳的量级是 1.7 乘以 10 的 12 次方，用 Int 承载必然溢出报错，这个坑在把老接口包成 GraphQL 时特别常见。Float 是 IEEE 754 双精度，金额字段用它做累加分账迟早出现精度尾差。ID 在传输上就是字符串，语义是「不透明标识符」，不要对它做算术或大小比较。

所以日期和金额必须上自定义标量。不定义的后果不是「少一点类型安全」，而是整个契约退回到字符串口头约定：格式靠文档、校验靠每个调用方自觉、时区靠猜，这正是 REST 时代最烦的那类问题，换个协议一点没解决。

接口和联合解决的是「返回值可能是多种类型」。interface 用于一组类型共享字段并支持多态，Relay 的 Node 接口加全局 ID 是最典型的用法，客户端拿 id 就能重新拉取任意对象。union 用于几种结构完全不同的结果，成员必须是对象类型、不能包含标量，客户端要靠 __typename 配内联片段分支；后面讲的「预期失败放进 data」就是 union 最好的用途。

最后是新手困惑最集中的地方：GraphQL 有两套互不相通的类型世界。输出类型（object、interface、union）不能出现在参数位置，输入类型（scalar、enum、input object）不能出现在返回值位置。Order 和 CreateOrderInput 必须写两份，没法复用。这不是设计疏漏，而是刻意限制：input 的字段不允许带参数，也不允许多态，否则服务端无法确定客户端传来的到底是哪个具体类型。想少写重复定义只能靠 codegen 或 SDL 组合，类型定义本身必须分开。

类型种类典型用途只能出现在常见误用与后果
object业务实体与聚合结构返回值拿它当参数类型，Schema 直接编译失败
interface共享字段加多态，如 Node返回值忘写 __resolveType，运行时报抽象类型无法解析
union多种可能结果，如成功与各类业务失败返回值成员里塞标量；客户端漏查 __typename 导致拿不到字段
enum有限状态集合两边都行新增枚举值对输出是破坏性变更，客户端分支没覆盖会崩
内置标量 Int计数、数量两边都行存毫秒时间戳或雪花 ID，超过 32 位上限直接报错
内置标量 Float比率、评分两边都行存金额，累加出现精度尾差，对账时才发现
自定义标量DateTime、Decimal、URL两边都行不定义就退回字符串约定；只实现 parseValue 漏掉 parseLiteral
input objectmutation 的参数载体参数试图复用输出类型；给 input 字段加参数，编译失败
# 一份能直接跑的 Schema 片段：自定义标量 / 接口 / 联合 / input / Connection 全部到位
scalar DateTime      # 序列化为 RFC 3339 字符串，服务端负责校验，不要用 String 糊过去
scalar Decimal       # 金额用字符串承载，禁止用 Float，否则累加分账迟早出现精度尾差

"Relay 的 Node 接口：客户端拿到全局 id 就能重新拉取任意对象，缓存归一化依赖它"
interface Node {
  id: ID!
}

enum OrderStatus {
  CREATED
  PAID
  SHIPPED
  CANCELLED
}

type User implements Node {
  id: ID!
  nickname: String!          # 业务保证一定有值，标非空
  avatarUrl: String          # 可能没上传，保持可空
  email: String              # 字段级权限：非本人查询返回 null，而不是抛错
}

type OrderItem {
  id: ID!
  title: String!
  quantity: Int!
  unitPrice: Decimal!
}

type Order implements Node {
  id: ID!
  status: OrderStatus!
  createdAt: DateTime!
  totalAmount: Decimal!
  # 跨服务关联字段保持可空：用户服务抖动时只丢这个字段，不会把整个 order 打成 null
  user: User
  # 明细来自本服务同一事务，缺失就是 bug，列表和元素都标非空
  items: [OrderItem!]!
}

# 输入类型必须单独定义，不能复用 Order；input 字段不能带参数，也不能是接口或联合
input CreateOrderInput {
  clientToken: String!       # 业务幂等键，重试时服务端据此去重
  items: [CreateOrderItemInput!]!
  couponId: ID
}

input CreateOrderItemInput {
  skuId: ID!
  quantity: Int!
}

# 预期内的业务失败用 union 放进 data，而不是丢进 errors，客户端能穷举处理
union CreateOrderResult = CreateOrderSuccess | StockShortage | CouponInvalid

type CreateOrderSuccess { order: Order! }
type StockShortage { skuId: ID!  available: Int! }
type CouponInvalid { couponId: ID!  reason: String! }

type OrderEdge {
  cursor: String!            # 游标描述的是“该元素在这个列表里的位置”，所以挂在 edge 上
  node: Order!
}

type PageInfo {
  hasNextPage: Boolean!
  hasPreviousPage: Boolean!
  startCursor: String
  endCursor: String
}

type OrderConnection {
  edges: [OrderEdge!]!
  pageInfo: PageInfo!
  totalCount: Int            # 可空：大表精确 count 很贵，允许降级返回 null
}

type Query {
  node(id: ID!): Node
  order(id: ID!): Order
  orders(first: Int = 20, after: String, status: OrderStatus): OrderConnection!
  legacyOrderList: [Order!]! @deprecated(reason: "改用 orders，调用量归零后删除")
}

type Mutation {
  # 一个 mutation 只做一件事，参数收成单个 input 便于后续加字段
  createOrder(input: CreateOrderInput!): CreateOrderResult!
}

type Subscription {
  orderStatusChanged(orderId: ID!): Order!
}

自定义标量的实现必须把三个钩子都写全，parseLiteral 最容易漏——它处理的是查询文本里硬编码的字面量，只在有人不走 variables 时才触发，测试往往覆盖不到。

// scalars.js —— 没有自定义标量，日期和金额就退回“字符串口头约定”，跟 REST 的老问题一样
import { GraphQLScalarType, Kind, GraphQLError } from 'graphql';

export const DateTimeScalar = new GraphQLScalarType({
  name: 'DateTime',
  description: 'RFC 3339 时间字符串，例如 2026-09-23T10:00:00Z',
  // serialize: 服务端 -> 客户端。统一输出 UTC，杜绝“每台机器时区不同”导致的差一天
  serialize(value) {
    const d = value instanceof Date ? value : new Date(value);
    if (Number.isNaN(d.getTime())) throw new GraphQLError('DateTime 序列化失败');
    return d.toISOString();
  },
  // parseValue: 客户端通过 variables 传进来的值，这里拿到的是 JSON 值
  parseValue(value) {
    if (typeof value !== 'string') throw new GraphQLError('DateTime 必须是字符串');
    const d = new Date(value);
    if (Number.isNaN(d.getTime())) throw new GraphQLError('非法时间 ' + value);
    return d;   // 往下游传 Date 对象，resolver 里不用再解析一遍
  },
  // parseLiteral: 查询文本里硬编码的字面量，拿到的是 AST 节点，最容易漏掉的就是它
  parseLiteral(ast) {
    if (ast.kind !== Kind.STRING) throw new GraphQLError('DateTime 字面量必须是字符串');
    return this.parseValue(ast.value);
  },
});

// 内置 Int 是 32 位有符号整数，上限 2147483647。毫秒时间戳量级 1.7e12，用 Int 必然溢出
// 毫秒时间戳、雪花 ID、金额分，一律走自定义标量或 String，不要塞进 Int
export const DecimalScalar = new GraphQLScalarType({
  name: 'Decimal',
  serialize: (value) => String(value),
  parseValue: (value) => {
    if (!/^-?\d+(\.\d{1,8})?$/.test(String(value))) throw new GraphQLError('非法金额');
    return String(value);
  },
  parseLiteral: (ast) => {
    if (ast.kind !== Kind.STRING && ast.kind !== Kind.INT) throw new GraphQLError('金额请用字符串传');
    return String(ast.value);
  },
});

可空性默认是反的，而且错误会向上冒泡

这是 GraphQL 最反直觉的一条规则：字段默认可空，加叹号才是非空。Java、Go、Kotlin、开了 strict 的 TypeScript 都是反过来的，默认不可空。于是很多团队上手时会「为了严谨」把所有字段都标成非空，然后在生产环境收获一个很难理解的故障现象。

原因是执行器的错误传播规则：非空字段解析失败时，错误会向上冒泡，直到遇到最近的一个可空位置，把那个位置整体置为 null。如果一路上都是非空，就一直冒到根，data 整体变成 null。也就是说，你在 Order.user 上多打的那个叹号，决定了用户服务抖动时是「少一个字段」还是「整页数据全没了」。

类型写法含义某个元素解析失败时的后果适用场景
String可空标量该字段为 null，兄弟字段不受影响默认选择
String 加叹号非空标量错误冒泡到父对象，父对象整体变 null业务上永远存在的字段，如 id
列表可空 元素可空方括号内外都不加叹号坏的那条变 null，列表长度不变元素来自不可靠下游
列表可空 元素非空只在元素后加叹号一条坏掉，整个列表变 null元素来自同一事务，要么全对要么算故障
列表非空 元素非空方括号内外都加叹号一条坏掉，冒泡到列表所在的父对象本服务强一致数据，最常见的写法
列表非空 元素可空只在方括号外加叹号坏的变 null，列表本身一定存在批量按 id 查询的返回，缺失位置留 null
⚠️
非空不是「更严谨」，而是「故障半径更大」

判断标准只有一个：这个字段缺失时，父对象还有意义吗？id 缺了对象就是废的，标非空合理。user、logistics 这类跨服务关联字段缺了，订单号和金额照样能渲染，就该保持可空，让前端做局部降级。跨服务字段标非空，等于把下游的可用性直接乘进自己的可用性里。

执行模型：解析、校验、逐字段执行

一次请求走三步。解析把查询文本变成 AST，语法错误在这一步返回。校验拿 AST 对着 Schema 跑一遍规则：字段是否存在、参数类型是否匹配、片段是否有效；这也是挂自定义规则的地方——查询深度限制和复杂度评分都必须挂在校验阶段，因为它在执行之前，此时还没有任何数据库查询发出去。执行从根字段开始，逐字段调用 resolver。

执行的形状是一棵树：同一层的字段并行发起，子字段必须等父字段拿到值之后才能展开，因为子 resolver 的第一个参数就是父字段的返回值。没有显式写 resolver 的字段走默认实现，等价于从父对象上取同名属性。

sequenceDiagram autonumber participant E as 执行器 participant RQ as Query.orders participant RU as Order.user participant RI as Order.items participant DS as 数据源 E->>RQ: 执行根字段 orders RQ->>DS: 查订单列表 DS-->>RQ: 返回 10 个 Order Note over E: 父字段拿到值之后
才能展开子字段 E->>RU: 用第 1 个 Order 作为 parent 调用 RU->>DS: 按 userId 查用户 E->>RU: 第 2 到第 10 个 Order 各调用一次 RU->>DS: 再发 9 次查询 E->>RI: 每个 Order 各调用一次 items RI->>DS: 每个订单各查一次明细 Note over RU,DS: 同层字段并行发起
但每个父对象都要独立调一次 resolver E-->>E: 按查询形状组装结果树

这张图就是 N+1 的结构性来源：它不是谁写错了代码，而是「resolver 按字段独立取数」这个模型的必然结果。父层返回 N 条记录，子字段的 resolver 就会被调用 N 次；再嵌一层就变成 N 乘 M。解法（DataLoader 攒批、投影下推、深度与复杂度限制）见站内 GraphQL 性能与 N+1 一篇，这里只需要记住：这个坑是内建的，任何 GraphQL 服务上线前都必须处理。

顺着执行模型往下看，每个 resolver 拿到的四个参数决定了它能做什么：

参数是什么典型用途踩坑点
parent父字段的返回值拿 parent.userId 去查关联对象根字段上是 undefined；它只是上一层 resolver 返回的东西，不一定是完整实体
args该字段的参数，已按 Schema 完成类型校验和默认值填充分页游标、过滤条件只校验了类型，没校验业务约束；分页 size 上限必须服务端强制
context整个请求共享的对象，由 context 工厂每请求创建一次当前用户、DataLoader 实例、数据库连接、traceId在 context 工厂里做重 IO 会拖慢每一个请求，包括根本用不到它的查询
info本次执行的元信息：AST 字段节点、路径、Schema、变量投影下推、按字段埋点、判断客户端到底要了哪些子字段结构复杂且随版本变动，手撸解析很脆，尽量用现成库

context 是放请求级依赖的唯一正确位置。当前登录用户、DataLoader 实例、数据库连接或事务句柄、链路 traceId，全都应该在 context 工厂里创建，随请求生灭。其中 DataLoader 尤其关键：它自带按 key 的缓存，做成模块级全局单例会导致 A 用户的数据被 B 用户的请求命中——这不只是正确性问题，是实打实的越权漏洞。

// resolvers.js —— resolver 只做“取数 + 组装”，业务逻辑留在 service 层
import DataLoader from 'dataloader';
import { GraphQLError } from 'graphql';

// context 工厂每个请求执行一次，所以放在这里创建的 DataLoader 天然是请求级的
export function buildContext({ req, deps }) {
  return {
    viewer: deps.auth.verify(req.headers.authorization),   // 认证结果，字段级鉴权靠它
    traceId: req.headers['x-trace-id'],
    // 绝不能把 loader 提到模块顶层做成全局单例：会跨请求缓存污染，等于越权漏洞
    loaders: {
      userById: new DataLoader((ids) => deps.userService.batchGet(ids), {
        maxBatchSize: 200,   // IN 列表过大时 MySQL 执行计划会退化，主动拆批
      }),
    },
    deps,
  };
}

export const resolvers = {
  Query: {
    // 根字段上 parent 是 undefined；args 只过了 Schema 的类型校验，业务约束要自己兜
    orders: async (_parent, args, ctx, info) => {
      if (!ctx.viewer) {
        throw new GraphQLError('未登录', {
          // extensions.code 是给客户端做分支的稳定错误码，别让前端去匹配 message 文案
          extensions: { code: 'UNAUTHENTICATED', http: { status: 401 } },
        });
      }
      const first = Math.min(args.first ?? 20, 100);   // 分页上限必须服务端强制
      return ctx.deps.orderService.page({ userId: ctx.viewer.id, ...args, first });
    },
  },

  Order: {
    // 关联字段走 loader：同一个事件循环 tick 内的 N 次 load 会被攒成一次 batchGet
    user: (order, _args, ctx) =>
      order.userId ? ctx.loaders.userById.load(order.userId) : null,
    // 没写 resolver 的字段走默认实现，等价于 parent[fieldName]，不必逐个手写
  },

  User: {
    // 字段级权限失败返回 null 而不是抛错：email 是可空字段，抛错会把整个 User 打成 null
    email: (user, _args, ctx) => (ctx.viewer?.id === user.id ? user.email : null),
  },

  // union 和 interface 必须能判定具体类型，否则运行时报 Abstract type must resolve
  CreateOrderResult: {
    __resolveType: (obj) =>
      obj.order ? 'CreateOrderSuccess' : obj.skuId ? 'StockShortage' : 'CouponInvalid',
  },
};

错误模型：永远 200，而且允许部分成功

GraphQL 的错误模型和 REST 没有一点相似之处。只要请求进入了执行阶段，HTTP 状态码就是 200，失败信息放在响应体的 errors 数组里，同时 data 可以有值——这就是「部分成功」：十个字段里两个挂了，另外八个照常返回。

直接后果是网关、负载均衡和监控系统全部失灵。按状态码统计的错误率永远是 0，按 5xx 配的告警永远不响，按 URL 维度打的点全部聚合在同一个 /graphql 上。正确做法是在服务内部按 operationName 打点，并把 errors 数组是否非空、错误码分布作为独立指标上报（采集实现见站内 Apollo Server 工程实践一篇）。HTTP 语义本身的讨论见站内 API 设计一篇。

错误分类上有一条现在已成主流的实践：把预期内的业务失败建模成返回类型，只让意外错误进 errors 数组。库存不足、优惠券失效这类情况是业务的正常分支，用 union 返回 StockShortage 这样的类型，客户端就能靠类型系统穷举处理，而且不会触发可空性冒泡；真正该进 errors 的是参数非法、未认证、下游超时、代码 bug。

错误类别放在哪extensions.code客户端该做什么要不要告警
查询语法或校验错误errors，data 为 nullGRAPHQL_PARSE_FAILED 或 GRAPHQL_VALIDATION_FAILED这是发版前就该拦住的 bug要，说明有客户端在发非法查询
参数不合法errorsBAD_USER_INPUT提示用户修改输入不用，看趋势即可
未认证或无权限errorsUNAUTHENTICATED 或 FORBIDDEN跳登录，或提示无权限突增要看，可能是撞库或越权探测
预期内业务失败data，用 union 承载不进 errors按 __typename 分支渲染不用，这是正常分支
下游超时或熔断errors，对应字段为 null自定义如 DOWNSTREAM_UNAVAILABLE局部降级，保留已返回的其他字段要，且按字段维度统计
未捕获异常errorsINTERNAL_SERVER_ERROR展示通用错误文案要，且生产环境必须剥掉堆栈

客户端分支一定要基于 extensions.code，不要去匹配 message 文案。message 是给人看的，随时会被改、会被翻译、会被脱敏，把它当契约用等于埋一颗定时炸弹。

Mutation 与 Connection：两套值得照抄的约定

Mutation 的设计约定不是风格偏好，每一条都对应一个具体的演进或缓存问题。

约定反面写法为什么
一个 mutation 只做一件事updateOrder 里塞进改地址、改状态、退款参数组合爆炸，权限和审计无法按动作区分
参数收成单个 input 对象把十几个标量参数平铺在字段上加字段时只改 input 定义，不动字段签名，老客户端不受影响
返回受影响的对象，且带 id只返回布尔值或一句 message客户端归一化缓存靠 id 自动更新，否则只能手工失效或整页刷新
预期失败用 union 建模全部抛进 errors客户端能穷举分支，且不会触发非空冒泡
幂等键由调用方传入依赖服务端猜测去重网络重试和用户连点在移动端是常态，细节见站内 API 设计最佳实践一篇

还有一条容易忽略的执行语义：同一个请求里的多个根 mutation 是串行执行的，而多个根 query 是并行的。所以不要指望把两个 mutation 塞在一个请求里就获得事务性——它们只是顺序执行，前一个成功、后一个失败时，不会有任何回滚。

分页的 Connection 规范看起来啰嗦，但每一层都有存在理由：edges 是「关系」的集合而不是「对象」的集合，所以 cursor 挂在 edge 上——游标描述的是该元素在这个特定列表中的位置，换个排序方式游标就变了，它不是对象自身的属性。edge 层还能放关系专属的数据，比如用户加入群组的时间、在群里的角色，这些既不属于 User 也不属于 Group。pageInfo 让客户端在不知道总数的情况下也能翻页，这对深分页性能至关重要。

Connection 字段含义实现要点
edges关系列表通常列表和元素都非空，因为它来自本服务的一次查询
edges.node真正的业务对象这一层才是实体，客户端缓存按 node.id 归一化
edges.cursor该元素在本列表中的位置用排序键加主键编码后再 base64，不要直接暴露自增 id
pageInfo.hasNextPage还有没有下一页多查一条来判断，比再发一次 count 便宜得多
pageInfo.endCursor下一次请求要传的 after 值空列表时为 null，客户端要处理这个情况
totalCount总数标成可空，大表精确 count 很贵，允许降级或返回估算值

游标分页相比 offset 分页的具体优势（深分页不退化、并发插入不漏不重）见站内 API 设计最佳实践一篇，这里不展开。

Schema 演进：不做版本，只做增删

GraphQL 的设计哲学是不要 v1、v2，而是在同一份 Schema 上持续增删字段。这在 REST 那边确实是个真实优势：客户端只会拿到它显式请求的字段，所以加字段对所有现有调用方都是零影响的——不像 REST 响应体加个字段，可能撞上某个客户端的严格反序列化。

但这套哲学有个前提，很多团队接受了结论却没建设前提：你必须有字段级的使用统计。没有统计，「不做版本」的实际效果是「所有字段永远不敢删」，Schema 只增不减地烂下去，最终变成一份谁都不敢碰的巨型类型定义。有了统计，删除流程才能闭环：标废弃并写明替代字段，观察调用量归零，再等足够长的客户端发版周期，然后删。

变更类型对输出字段对输入参数处理方式
新增安全，客户端不请求就不受影响安全，前提是新参数可空或有默认值直接加，CI 无需拦截
删除破坏性破坏性先标废弃，等字段调用量归零并过完发版周期
可空改非空安全，客户端本来就能处理 null破坏性，老客户端不传该参数会被校验直接拦下输入参数改必填等同于删旧参数加新参数
非空改可空破坏性，客户端代码假设了一定有值安全输出字段放宽约束要当破坏性变更走流程
新增枚举值破坏性，客户端分支没覆盖会走到未知值安全客户端从第一版起就要写兜底分支
改字段类型破坏性破坏性加新字段并行跑，迁移完再删老字段
重命名字段或类型破坏性破坏性等于一次删加一次增，走完整流程

订阅的传输选择与适用边界

Subscription 是三个根类型里最被滥用的一个。传输层面，早期的 subscriptions-transport-ws 已停止维护且存在已知缺陷，新项目应该用 graphql-ws 协议；只需要服务端单向推送时用 SSE 更省事，能省掉 WebSocket 的连接管理成本，也更容易穿过各种代理。

场景建议方案理由
订单状态变更、消息通知Subscription低频、面向单个在线用户、需要即时性，正是它的主场
列表页数据准实时刷新轮询加客户端缓存连接成本远高于收益，轮询间隔可按页面可见性动态调整
行情、日志流等高频推送专用 WebSocket 或 SSE 通道不要让每条消息都走一遍 GraphQL 执行器，开销不划算
服务之间传递事件消息队列Subscription 是面向客户端的，不要拿它当内部 MQ 用
大批量数据导出异步任务加文件下载长连接推大量数据，中间任何一跳断开都得从头再来

生产化的三个硬成本：水平扩展必须引入外部 PubSub（用户连在 A 实例、事件从 B 实例发出，不广播就收不到）；每条连接都占用文件描述符和内存，连接数要压测并设上限；鉴权不能只在建连时做一次，长连接期间权限可能被撤销。具体配置见站内 Apollo Server 工程实践一篇。

反模式速查

反模式表现后果正确做法
REST 端点一一映射成字段Query 里出现 getUserById、getUserList、getUserDetail丢掉了图的关联能力，只是换个协议重复 REST 的问题按实体和关系建模，让客户端自己组合
所有字段都标非空整个 Schema 满是叹号任一下游抖动就把整页 data 打成 null只对业务上永远存在的字段标非空
resolver 里直接写数据库查询SQL 散落在几十个 resolver 中N+1 无法统一治理，权限和缓存也没地方挂resolver 只调 service 或 loader
一个巨型 Query 类型Query 上挂了上百个根字段没人能判断字段归属，权限和使用统计全乱按域拆分 Schema 模块，必要时上联邦
缺自定义标量日期、金额、URL 全是 String格式靠口头约定，时区和精度问题反复出现定义 DateTime、Decimal 并实现三个钩子
错误全塞进一个 messageerrors 里只有一句中文提示客户端只能做字符串匹配，改个文案就崩用 extensions.code 提供稳定错误码
生产环境开着自省任何人都能拉走完整 Schema攻击者直接拿到全部字段和参数清单对外关闭或加认证，细节见站内 Apollo 一篇
❌
最容易踩的坑

1. 把跨服务关联字段标成非空。用户服务超时，订单列表整体变成 null，前端白屏，线索只剩一条被埋在 errors 数组里的超时记录。

2. 用 Int 存毫秒时间戳。量级 1.7 乘 10 的 12 次方远超 32 位上限 2147483647，序列化直接报错，而且往往只在真实数据上才暴露。

3. 用 Float 存金额。累加分账后出现精度尾差，对账时才发现，追查成本极高。

4. DataLoader 在模块顶层创建成全局单例。A 用户的数据被 B 用户的请求命中，这是越权而不只是脏读。

5. 在 context 工厂里做重 IO，比如每请求查一次权限表还不加缓存。所有查询都被这次 IO 拖慢，包括完全不需要权限的公开查询。

6. 监控按 URL 打点。所有流量都聚合在一个 /graphql 上，无法定位是哪个 operation 变慢，必须改成按 operationName 统计。

7. 用 HTTP 状态码判断成败。执行阶段的错误固定返回 200，按 5xx 配的告警永远不会触发，错误率面板永远是零。

8. 客户端按 errors 里的 message 文案做分支。后端改一次提示语或加一层脱敏，前端逻辑全部失效，只能依赖 extensions.code。

9. 自定义标量只实现 parseValue，漏掉 parseLiteral。走 variables 的请求正常，查询里硬编码字面量的请求在生产才炸。

10. 以为一个请求里的多个 mutation 有事务性。规范只保证根 mutation 串行执行，前一个提交、后一个失败时没有任何回滚。

11. 加枚举值时没当破坏性变更处理。老客户端没有兜底分支，遇到未知值直接崩，移动端还得等发版才能修。

12. 接受了「不做版本只做增删」，却没建字段级使用统计。结果是字段只增不减，Schema 膨胀成谁都不敢改的样子。
