REST 还是 GraphQL：同一需求的两种实现与迁移决策

🏷️ GraphQL

关于 REST 和 GraphQL 的对比，市面上大多停留在「一个多端点固定返回、一个单端点按需查询」这种层面。这种对比没法支撑决策，因为它只算收益不算账单。站内 API 风格选型一篇已经给过四种风格的九维对照和 GraphQL 要付的五张账单，这里换一个更贴近落地的角度：拿同一个业务需求分别用两种方式实现，逐项算代码与运维成本，然后回答一个更实际的问题——什么时候从 REST 迁到 GraphQL 是个错误决定。

需求：订单详情页要五块数据

贯穿全篇的需求很具体：订单详情页要展示订单主体、商品明细、收货地址、物流轨迹、优惠券五块数据。这五块的性质差异很大，这正是它值得当例子的原因。

数据块来源变化频率能否缓存首屏是否必需失败可否降级
订单主体订单服务，自有库状态变更时私有短缓存必需不可，失败即整页失败
商品明细订单服务同库创建后基本不变可缓存较久必需不可
收货地址用户中心极少变可缓存，含隐私需脱敏必需可降级为只显示收件人
物流轨迹第三方物流网关分钟级短缓存，外部依赖不稳定非必需可，显示暂无轨迹
优惠券营销服务下单后不变可缓存非必需可

注意最后两列：差异化的超时与降级策略，是任何聚合方案都必须处理的核心问题，跟用什么协议无关。很多人把「聚合」想成简单的并行调用，忽略了这部分才是真正的工作量。

REST 的两种做法

第一种是前端自己调五个端点。移动端上这个方案的问题不在请求数本身，而在依赖链：地址和物流的参数藏在订单响应里，所以必须先拿订单，再并行拿其余四块，至少两个串行阶段。弱网环境下每个阶段都要吃一次完整的往返延迟。

第二种是后端做一个聚合端点，也就是 BFF。前端只发一次请求，串行链路留在机房内部，服务间调用延迟通常是 1 到 5ms，比公网一次往返小一到两个数量级。

sequenceDiagram autonumber participant C as 客户端 participant B as BFF 聚合端点 participant O as 订单服务 participant U as 用户中心 participant L as 物流网关 Note over C,L: 方案一 前端自己调五个端点 C->>O: 取订单主体 O-->>C: 返回订单 含地址 id 与运单号 Note over C: 必须等订单返回
才知道后面四个请求的参数 C->>O: 取商品明细 C->>U: 取收货地址 C->>L: 取物流轨迹 C-->>C: 前端组装五份响应 处理各自的失败 Note over C,L: 方案二 后端聚合端点 C->>B: 一次请求拿订单详情 B->>O: 取订单与明细 B->>U: 取地址 超时 500ms 降级 B->>L: 取物流 超时 500ms 降级 B-->>C: 一份按页面需要拼好的响应

方案二的实现并不复杂，核心就是并行加差异化超时加降级：

// bff/order-detail.js —— REST 聚合端点：一个端点搞定订单详情页的五块数据
// 这是和 GraphQL 对标的方案，前端只发一次请求，但形状由后端决定
import express from 'express';

const router = express.Router();

// 超时要分字段设：核心数据等久一点，边缘数据快速失败
const withTimeout = (p, ms, fallback) =>
  Promise.race([p, new Promise((r) => setTimeout(() => r(fallback), ms))]);

router.get('/api/orders/:id/detail', async (req, res) => {
  const { id } = req.params;
  const uid = req.user.id;

  // 订单是后续查询的前提，必须先拿到，也是唯一必须成功的一块
  const order = await orderService.get(id);
  if (!order) return res.status(404).json({ code: 'ORDER_NOT_FOUND' });
  if (order.userId !== uid) return res.status(403).json({ code: 'FORBIDDEN' });

  // 其余四块互不依赖，并行取；单块失败降级为 null，不要让整页 500
  const [items, address, logistics, coupon] = await Promise.all([
    withTimeout(itemService.listByOrder(id), 800, []),
    withTimeout(addressService.get(order.addressId), 500, null),
    withTimeout(logisticsService.trace(order.shipmentNo), 500, null),
    order.couponId ? withTimeout(couponService.get(order.couponId), 300, null) : null,
  ]);

  // HTTP 缓存仍然可用：这是聚合端点相比 GraphQL 最实在的优势
  res.set('Cache-Control', 'private, max-age=10');
  res.set('ETag', etagOf(order.updatedAt, items.length));
  res.json({ order, items, address, logistics, coupon });
});

export default router;

GraphQL 的做法

GraphQL 版本的客户端查询是这样的，形状由前端决定，后端不需要为这个页面准备任何专用端点：

# 客户端：一次查询拿完五块数据，形状由前端决定
query OrderDetail($id: ID!) {
  order(id: $id) {
    id
    status
    totalAmount
    items { id title quantity unitPrice }
    address { receiver phoneMasked detail }
    logistics { latestNode happenedAt }     # 下游慢就让它返回 null，字段必须可空
    coupon { name discountAmount }
  }
}

服务端要做的是把这些字段的 resolver 接上，所有关联字段走 DataLoader。执行时序和 BFF 很像，区别是调用的字段集合由查询决定，而不是由后端写死。

sequenceDiagram autonumber participant C as 客户端 participant G as GraphQL 服务 participant V as 校验与复杂度检查 participant O as 订单服务 participant U as 用户中心 participant L as 物流网关 C->>G: 一次 POST 带查询与变量 G->>V: 解析 校验 算复杂度分 V-->>G: 通过 未超上限 G->>O: 执行 Query.order O-->>G: 订单主体 Note over G: 拿到父对象后
并行展开子字段 各自走 loader G->>O: 批量取明细 G->>U: 批量取地址 G->>L: 取物流 失败则该字段为 null G-->>C: 返回 data 加可能存在的 errors 数组 Note over C,G: 状态码恒为 200
物流失败时属于部分成功

最后一条 Note 是两种方案在运维上最大的分歧点：REST 聚合端点里物流挂了，你可以选择返回 200 加 null，也可以返回 5xx 让监控知道；GraphQL 里这件事只能是 200 加 errors 数组，可观测性必须自己从零搭一套。

对比前两列和第三列：请求数、首屏耗时这两项聚合端点和 GraphQL 基本打平，而它保留了 HTTP 缓存、现成的监控、按端点限流、端点级权限。GraphQL 真正不可替代的收益只有三条：多端字段需求差异大、前端改字段不需要后端发版、客户端归一化缓存。如果这三条对你都不成立，那 GraphQL 换来的就只有账单。先写一个 50 行的聚合端点，是成本最低、也最容易回退的选择。

场景结论理由
多端并存，Web 要全量、移动端要精简、大屏只要三个字段该上这是唯一无法用聚合端点低成本模拟的场景，端多了聚合端点会退化成端点爆炸
前端迭代频率远高于后端该上加字段不需要后端排期和发版，节省的是协调成本而不是代码量
关联数据多、页面组合形态多变该上图形建模天生适合表达关联，客户端自由组合
平台型 API 要开放给不确定的消费方该上，但要严控自省文档和类型契约是真实优势；同时必须上复杂度评分与配额，否则会被打爆
只有一个 Web 端不该上没有多端差异，收益只剩省往返，而这个聚合端点也能做
以写操作和流程编排为主不该上mutation 相比 POST 端点没有任何优势，还多一层抽象；事务、幂等、编排全得自己做
团队没人懂 GraphQL 运维不该上复杂度限制、字段级监控、字段级权限、Schema 评审都是新增职责，没人接就是裸奔
强依赖 HTTP 缓存与 CDN不该上单端点 POST 让边缘缓存基本失效，找回来要付持久化查询与 GET 化的代价
接口本来就很少，只有十来个不该上治理成本远大于收益，十几个端点根本不需要一套类型系统来管

「接口太乱所以换 GraphQL」是错误动机

这是我见过最常见也最昂贵的错误决策。逻辑通常是这样的：接口有三百多个、命名混乱、有五个功能重复的用户查询端点、没人知道哪个还在用，于是决定上 GraphQL 重新梳理一遍。

问题在于接口乱是建模和治理的问题，不是协议的问题。换协议不会让混乱自动变整齐，只会把混乱搬到 Schema 里，而且换了个更难收拾的地方：

REST 时代的症状换成 GraphQL 之后为什么更糟
五个功能重复的用户端点Query 上五个功能重复的根字段没人敢删，因为删字段是破坏性变更，而你还没有字段级统计
响应体字段命名不统一Schema 里同一个概念有三种类型名类型名是全局唯一的，重名冲突会在联邦阶段直接炸
端点职责不清巨型 Query 类型挂上百个根字段权限、限流、使用统计全部失去归属，无法按模块治理
没有文档有了自动生成的文档，但描述全是空的看起来有文档了，实际信息量为零，反而更容易误用
不知道哪些端点还在用不知道哪些字段还在用问题原地不动，除非你额外建设字段级统计

真正该做的顺序是：先按域梳理模型、合并重复能力、建立使用统计、砍掉无人调用的接口。这些事做完之后，如果多端差异的问题依然存在，再上 GraphQL 才有意义。把治理欠债当成技术选型问题来解，代价是同时背上两笔债。

迁移路径：包一层，再下沉

决定要上之后，最忌讳的是一次性替换。正确路径是先用 GraphQL 把现有 REST 服务包一层，resolver 里只做编排，一行数据库代码都不写。这一步就能拿到聚合收益，而且随时能退回去。

// 迁移第一步：GraphQL 只做编排，resolver 里调现有 REST 服务，一行数据库代码都不写
// 这一步就能拿到聚合收益，而且随时可以退回去
export const resolvers = {
  Query: {
    order: (_p, { id }, ctx) => ctx.loaders.orderById.load(id),
  },
  Order: {
    // 关联字段全部走 loader，即使下游只有单条接口也先包一层，
    // 等下游提供批量接口时只改 batchLoad，resolver 不用动
    items: (order, _a, ctx) => ctx.loaders.itemsByOrderId.load(order.id),
    address: (order, _a, ctx) =>
      order.addressId ? ctx.loaders.addressById.load(order.addressId) : null,

    // 不可靠下游：超时降级成 null，绝不能让它把整个 order 打没
    // 前提是 Schema 里 logistics 声明为可空，否则错误会冒泡
    logistics: async (order, _a, ctx) => {
      try {
        return await ctx.deps.logistics.trace(order.shipmentNo, { timeoutMs: 500 });
      } catch (e) {
        ctx.log.warn({ traceId: ctx.traceId, err: e.message }, '物流查询降级');
        return null;
      }
    },
  },
};

// loader 里对接尚未提供批量接口的老服务：受控并发，别把下游打挂
export const addressById = (deps) => new DataLoader(async (ids) => {
  const limit = pLimit(8);            // 并发上限，等下游出批量接口后删掉这段
  const settled = await Promise.allSettled(ids.map((id) => limit(() => deps.address.get(id))));
  return settled.map((r) => (r.status === 'fulfilled' ? r.value : null));
});

这就是绝大多数团队最终落到的形态：对外 REST，对内 gRPC，BFF 层 GraphQL。三者不是竞品，边界很清楚——外部集成方需要稳定契约和 HTTP 缓存，服务间通信需要低开销和强类型，端上需要按需取数。三种风格各自的适用边界与混用架构，见站内 API 风格选型一篇。

最容易踩的坑

1. 因为「REST 接口太多太乱」而换 GraphQL。混乱会原封不动搬进 Schema，而且删字段比删端点更难，等于同时背上两笔债。

2. 没先试聚合端点就上 GraphQL。请求数和首屏耗时这两项收益，50 行的 BFF 就能拿到，而且保留了 HTTP 缓存和现成监控。

3. 以为 GraphQL 能省后端代码量。实际是把「写端点」换成「写 Schema 加 resolver 加 loader 加限流插件」，代码总量通常更多。

4. 一次性替换所有 REST 端点。中途出问题无处可退，正确做法是先包一层、resolver 里不写业务逻辑，保留随时切回的能力。

5. 迁移后立刻把 resolver 下沉到直连数据库。应该只对耗时占比最高的少数字段下沉，其余继续调服务，否则绕过了服务自身的业务规则。

6. 上线时没做复杂度限制。GraphQL 的请求成本由客户端决定，成本差一万倍的两个请求在按 QPS 的限流器眼里完全一样。

7. 监控沿用按 URL 打点。所有流量都落在一个端点上，错误率永远是零，因为执行错误也返回 200。

8. 把前端字段权限交给网关。网关看不见字段，字段级鉴权只能在 resolver 里做，而且必须逐字段落实。

9. 忘了物流这类不可靠下游的字段必须声明可空。标了非空，下游一超时整个订单对象变成 null，整页白屏。

10. 以为上了 GraphQL 就不需要 REST 了。Webhook、第三方集成、需要 CDN 缓存的内容接口，都还得用 REST。

11. 没人长期负责 Schema 治理。半年后 Query 类型上挂了两百个根字段，命名三套风格，谁都不敢改。

12. 用写操作为主的业务去验证 GraphQL 的价值。mutation 相比 POST 端点没有优势，验证结论一定是负面的，但结论本身没意义。
