GraphQL 的执行模型与运维成本

🏷️ GraphQL

这一篇是 GraphQL 专题的总览，但不讲 SDL 怎么写、resolver 怎么挂——那些在入门篇里。这里只回答一个问题：把 GraphQL 放到生产上之后，多出来的运维负担具体是什么，以及哪些配置项不补上就一定会出事。

一个端点、一个 200：复杂度被挪到了服务端

REST 体系里，URL 本身就是运维的抓手：限流按路径、缓存按路径、审计按路径、鉴权按路由、慢接口排行按路径。GraphQL 把这个维度整个抹掉了——所有请求都打到同一个端点，真正的意图藏在请求体里。于是每一项运维能力都得往下沉一层，重建在「操作」和「字段」两个新维度上。

顺手纠正两个流传很广的说法。GraphQL 并不是只能用 POST：规范允许用 GET 传查询，这也是让 CDN 有机会参与缓存的唯一途径，只是受 URL 长度限制，要配合持久化查询才好用。也不是永远返回 200：传统的 application/json 响应固定 200，而规范定义的 application/graphql-response+json 允许请求级失败用 4xx 表达（解析或校验不通过返回 400）。真实行为取决于服务端实现和客户端发的 Accept 头，监控要同时覆盖两种形态。

schema 即契约：没有版本号，只有可加不可减

很多人第一反应是「为什么不搞个 /v2」。原因是版本号的粒度和 GraphQL 对不上：一个查询可以任意组合字段，做版本就得把整个 schema 复制一份，两份之间的 resolver、权限规则、缓存声明全部双写。GraphQL 选的是字段级演进——加字段永远安全，删字段必须走 deprecation 流程。

最容易搞错的是方向性：输出位置和输入位置的兼容方向是相反的。输出字段从可空收紧成非空是兼容的，因为客户端本来就在处理 null；输入字段从可空收紧成非空是破坏性的，因为老客户端根本不会传它。还有一条几乎所有人都会踩：给输出位置的枚举新增一个值也是破坏性变更，老客户端的分支里没有这一项。

这条链上最容易断的是「用量观测」。没有字段级用量统计，@deprecated 就只是一句注释，字段永远删不掉。移动端尤其要注意最后一步：老版本 App 可能在线上挂两三年，字段的真实下线周期由它决定，不由你的发布节奏决定。SDL 写法与可空性冒泡规则见入门篇。

# 契约演进的规则全都能从 SDL 上读出来，关键是记住输入和输出的方向是相反的

type Order implements Node {
  id: ID!
  status: OrderStatus!

  # 加字段永远安全：老客户端不请求它，就完全不受影响
  refundedAmount: Money

  # 输出字段从可空改成非空是兼容的（客户端本来就在处理 null）；
  # 反过来把 String! 放宽成 String，会打挂所有做了非空解包的客户端
  buyerNote: String

  # 删字段之前必须先 deprecated，reason 里写清替代品和计划下线时间
  amount: Int @deprecated(reason: "精度不足，改用 totalMoney，2026-12 后移除")
  totalMoney: Money!

  # 列表一律走 Connection，first 给默认值并在服务端设硬上限，
  # 这是把「一次拉全表」这个放大源直接堵在契约层
  items(first: Int = 20, after: String): OrderItemConnection!

  # 字段级缓存声明：整份响应的可缓存时间取所有被请求字段里最小的那个。
  # 只要混进一个 PRIVATE 字段，整份响应就不可公共缓存 —— 所以要把它拆到独立查询里去。
  shippingAddress: Address @cacheControl(maxAge: 0, scope: PRIVATE)
  product: Product @cacheControl(maxAge: 300, scope: PUBLIC)
}

# 输入类型方向相反：给 input 加一个非空且没有默认值的字段，是破坏性变更
input CreateOrderInput {
  items: [OrderItemInput!]!
  couponId: ID          # 新增可选字段安全；写成 couponId: ID! 会让所有老客户端直接校验失败
}

enum OrderStatus {
  CREATED
  PAID
  # 反直觉：给输出位置的枚举「加」值也是破坏性的，老客户端的分支里没有这一项
  PARTIALLY_REFUNDED
}

执行器怎么跑一个查询：字段级 resolver 与并发边界

执行分三步：解析成 AST、对着 schema 校验、然后逐字段递归执行。这里有个普遍误解：「只有我自己写了 resolver 的字段才有开销」。实际上每个字段都有 resolver，没写就用默认解析器去读父对象的同名属性，字段数本身就是成本——一个请求 500 个字段就是 500 次函数调用加 500 次错误捕获。

并发规则也常被讲反：同一层的多个字段是并行执行的（graphql-js 用 Promise.all 推进），但 Mutation 的根字段规范要求串行，这是为了让一个请求里的多个写操作有确定顺序。所以指望「一个请求里塞三个 mutation 来并行提速」是无效的，反而会让这个请求的耗时变成三者之和，超时预算要按串行算。

resolver 拿到的第四个参数 info 里有当前字段的 AST 和完整的 selection set，这是唯一能做投影下推的地方——想只 SELECT 客户端真正请求的列，只能从这里读。另一个容易漏的点是取消不会自动传播：客户端断开连接后，多数实现的 resolver 会继续跑到底，下游调用一个不少。要真正止损，得自己把中断信号从 HTTP 层串到每个数据源调用上。

资源放大有四个来源，量级完全不同：字段总数是线性的（同一个昂贵字段起 50 个别名就放大 50 倍，而且别名计数必须在片段展开之后做）；列表乘积是指数的（三层各取 100 条就是百万级 resolver 调用）；嵌套层数在环形关系下可以无限累乘；逐元素取数就是 N+1，成因与攒批手段详见性能篇。内省查询本身也是一个深嵌套查询，生产环境应当关闭。

必配的闸门：复杂度上限、持久化查询、超时预算

graphql-js 默认什么都不限：没有深度上限、没有复杂度上限、没有请求超时。这三项是必须自己补的，不补就等于把数据库的执行能力开放给了公网。

参数默认值建议起点调错的后果
最大查询深度无10 到 12 层设太小会砍掉合法的多级嵌套页面查询
最大静态复杂度无先观测线上分布的 p99 再定拍脑袋定值会误杀报表类查询，且看不到误杀
列表 first 上限无每个 Connection 单独定不设则单个请求可以拉全表
别名与字段总数无数百量级不设则同一昂贵字段起 50 个别名即可放大 50 倍
请求体大小取决于框架100 KB 量级设太小会挡住批量 mutation 与大 variables
每请求超时无与下游预算对齐，留出重试余量不设则慢查询会一直占着连接和内存
introspection多数实现默认开启生产显式关闭开着会泄露内部字段名与未发布能力

静态复杂度只是估算：它不知道某个 id 背后是 3 条数据还是 30 万条。所以它挡的是「明显不合理的形状」，真实资源保护还得靠执行期的超时和下游并发上限兜底，两者缺一不可。

import { ApolloServer, type ApolloServerPlugin } from '@apollo/server';
import { GraphQLError, separateOperations } from 'graphql';
import { getComplexity, simpleEstimator, fieldExtensionsEstimator } from 'graphql-query-complexity';
import depthLimit from 'graphql-depth-limit';

// 复杂度要算在 didResolveOperation 这一步：文档已经解析校验完、variables 已经拿到，
// 但一个 resolver 都还没跑 —— 这是唯一既算得准、又还来得及拒绝的位置。
// 放到 resolver 里熔断就晚了，钱已经花出去了。
const complexityPlugin = (max: number): ApolloServerPlugin => ({
  async requestDidStart() {
    return {
      async didResolveOperation({ request, document, schema }) {
        const complexity = getComplexity({
          schema,
          // 一个文档里可能有多个 operation，必须按 operationName 切出来单算
          query: request.operationName
            ? separateOperations(document)[request.operationName]
            : document,
          variables: request.variables,   // first / limit 这类乘数全在 variables 里
          estimators: [
            fieldExtensionsEstimator(),               // 字段在 schema 里自己声明权重，优先级最高
            simpleEstimator({ defaultComplexity: 1 }) // 兜底：没声明权重的字段算 1
          ],
        });
        // 必须打成直方图。日后收紧上限的唯一依据是线上真实分布，不是拍脑袋。
        metrics.observe('gql_query_complexity', complexity, {
          signature: request.extensions?.persistedQuery?.sha256Hash ?? 'adhoc',
        });
        if (complexity > max) {
          throw new GraphQLError('query too complex', {
            extensions: { code: 'QUERY_TOO_COMPLEX', max, actual: complexity },
          });
        }
      },
    };
  },
});

const server = new ApolloServer({
  schema,
  // graphql-js 本身不限深度、不限复杂度、也没有请求超时，这三件事都得自己补
  introspection: false,               // 生产关掉；IDE 与 codegen 改用发布出去的 schema 文件
  validationRules: [depthLimit(12)],  // 深度是纯静态的，放校验阶段最省
  plugins: [complexityPlugin(1000)],  // 1000 只是起点，先观测再收紧
});

持久化查询这块有个必须分清的边界：自动持久化查询是性能手段，不是安全手段。它的流程是客户端先发哈希、服务端没见过就回一个未找到的错误码、客户端再把全文发上来注册——任何人都可以注册任意查询。要当安全机制用，必须换成构建期生成清单、运行期只放行清单内哈希、并关闭动态注册的白名单模式。

sequenceDiagram participant C as 客户端 participant E as 边缘缓存 participant G as GraphQL 服务 C->>E: GET 带查询哈希与 variables E->>G: 边缘未命中，回源 G-->>C: extensions 里返回未找到该持久化查询 Note over C,G: 只有首次上线或缓存冷启动才会走到这一步 C->>G: POST 带查询全文与同一个哈希 G-->>C: 注册成功并返回数据 C->>E: 后续一律 GET 带哈希 E-->>C: 边缘直接命中，不回源 Note over E,G: 能进边缘缓存的前提是查询幂等
且响应里不含任何用户态字段

换成白名单模式后要接受两个工程约束：发布顺序变严格（必须先让服务端拿到新清单，再放量新客户端），以及清单只能加不能删（要一直兼容还在线上的最老客户端版本）。移动端团队尤其要把这两点写进发布流程，否则灰度期会大面积报「查询未注册」。

缓存为什么难，以及能找回哪几层

难点有三个，都不是实现问题而是模型问题：请求意图在 body 里，HTTP 中间层看不懂；响应是按查询形状临时拼出来的，不对应任何稳定资源标识；同一个字段在不同查询里的合理 TTL 不一样。缓存只能自己分层重建。

缓存层键是什么命中率来源失效手段会脏在哪
边缘 / CDNGET 的 URL：查询哈希 + variables公共内容、高重复查询TTL 与主动 purge带用户态字段的查询被跨用户命中，必须按鉴权维度分桶或干脆不缓存
服务端全响应缓存查询哈希 + variables + 鉴权作用域同一形状的重复请求取所有被请求字段声明 TTL 的最小值鉴权作用域算错就是越权，作用域必须进键
实体 / 对象缓存类型名 + id跨不同查询复用，命中率最高写路径主动删除写路径漏删，或同一实体有多个键写法
请求内攒批去重本次请求内的取数键同一请求里的重复取数请求结束即销毁误当成跨请求缓存，或复用了跨请求的实例导致串数据
客户端归一化缓存__typename + id同一对象在多个视图间共享mutation 返回完整对象拿不到 id 的类型无法归一化，写完列表不刷新

字段级 TTL 声明有个容易忽略的传播规则：整份响应的可缓存时间取所有被请求字段里最小的那个。只要一个查询里混进了一个不可缓存的用户态字段，整份响应就不可公共缓存。所以真正有效的做法是把用户态字段从公共查询里拆出去，让公共部分能进边缘缓存，私有部分单独一条链路。Apollo 侧的具体配置见实战篇。

可观测性：按 operation 聚合，而不是按 URL

上线第一天就会发现：所有 access log 的 path 都一样，原来那套按 URL 排序的慢接口面板彻底失效。重建时的第一个决策是选什么当主维度。答案不是客户端自报的 operationName——它可以缺失、可以重名、也可以伪造。主维度应该是把文档规范化（去空白、排序、剥离字面量）之后算出的签名，operationName 只作可读标签挂在旁边。

指标维度用来回答什么高基数风险
请求量与失败率查询签名 + 客户端版本哪个查询在报错、是哪批客户端签名数量受发布控制，可接受
端到端延迟直方图查询签名哪个查询的 p99 在恶化同上
字段耗时与调用次数父类型 + 字段名慢在哪个字段、哪个字段被调了 N 次基数由 schema 决定，是有限集合
字段用量父类型 + 字段名 + 客户端版本能不能删这个字段加了客户端版本后要控制版本标签的取值数
静态复杂度分布查询签名上限该定在哪、谁贴着上限可接受
下游调用放大比查询签名有没有 N+1，比字段耗时更早暴露可接受
禁止：variables 内容——用户 id、关键词直接把时序库打爆

失败率的算法必须重写，否则会出现「仪表盘全绿但用户在报错」。至少分四类：

响应形态含义客户端该怎么做监控归类
4xx，或 200 但只有 errors 且无 data 字段解析或校验失败不要重试，这是调用方 bug调用方错误，按客户端版本告警
200，data 为 null，errors 非空根字段抛错并向上冒泡可按错误码决定是否重试服务端错误，进 SLO 分子
200，data 部分字段为 null，errors 带 path部分成功，非空约束把 null 冒泡到了某一层按字段降级渲染单独一条曲线，不能算成功也不能算全挂
200，errors 为空成功—成功
200，extensions 里是持久化查询未找到协议协商的一步补发全文注册不算错误，但要看突增
 
# 维度用规范化后的查询签名，不要用 URL —— URL 全是同一个端点，按 path 的面板直接瞎掉。
# 也不要只用客户端自报的 operationName：它可以缺失、可以重名、也可以伪造。

# 1. 真实失败率：HTTP 200 里带 errors 的必须算进分子
sum by (signature) (rate(gql_requests_total{result="error"}[5m]))
  / sum by (signature) (rate(gql_requests_total[5m]))

# 2. 部分成功单独一条线：data 有值但 errors 非空，既不能算成功也不能算全挂
sum by (signature) (rate(gql_requests_total{result="partial"}[5m]))

# 3. 下游放大比：每个请求平均触发多少次数据层调用，这是发现 N+1 最直接的指标
sum by (signature) (rate(gql_datasource_calls_total[5m]))
  / sum by (signature) (rate(gql_requests_total[5m]))

# 4. 字段级耗时排行：type.field 的基数由 schema 决定，是有限集合，可以放心当标签
topk(20, sum by (parent_type, field) (rate(gql_field_duration_seconds_sum[5m])))

# 5. 死字段清单：连续 30 天调用为零的字段才有资格进入移除流程
sum by (parent_type, field) (increase(gql_field_calls_total[30d])) == 0

鉴权必须落在字段与实体层

网关能做的只有认证：验签、解 token、把调用者身份放进上下文。授权不能在网关做，因为网关看不见这次请求实际取了哪些字段，而 GraphQL 允许任意组合字段——路径不再代表资源。

落点能防住什么防不住什么结论
HTTP 中间件未认证请求、全局限流对字段毫无感知必要但远远不够
schema 指令把规则写在契约上，可被审计和 diff指令实现仍要落到取数处；输入参数与深层嵌套字段容易漏标适合做声明与静态检查
resolver 内判断粒度够细散落各处，新增一个 resolver 就多一个遗漏点只适合字段级的特殊规则
数据访问层强制带身份所有取数入口统一过滤，漏不掉需要改造取数层接口唯一可靠的位置

最典型的漏点是反向遍历：查「我的订单」这条路径做了校验，但从某个订单对象反向取它的所有者字段、再取所有者的其他订单，这条路径上往往没人管。第二个漏点是 mutation 的返回对象：写操作本身鉴权了，但返回的对象上挂着一堆本来读不到的字段。第三个是错误信息泄露存在性——无权访问应当返回 null 加统一错误码，而不是「该订单属于其他用户」。联邦架构下还有实体解析入口这一类绕过路径，详见微服务篇。

这个专题怎么读

五篇子文各自独立，按下面顺序读最省力。总览解决的是「要不要上、上了之后补哪些配置」，机制细节都在子篇里。

  • GraphQL 入门——schema 契约、三个根类型、可空性冒泡、执行三阶段、错误模型、Connection 约定。动手写第一个 resolver 之前读。
  • 与 REST、gRPC 的取舍——同一个页面需求下三种方案的逐项成本对照、错误的采用动机、迁移路径。做选型汇报之前读。
  • Apollo Server 与 Client 实战——Server 4 的变化、context 函数、插件生命周期、formatError、安全与性能必配项。搭服务和定配置项时读。
  • 性能与 N+1——N+1 为什么是结构性的、攒批的攒法、攒不了批的四类场景、线上怎么发现。压测发现下游调用量异常时读。
  • 联邦与微服务架构——三种组合方式、实体所有权、二次查询的代价、跨服务越权、什么时候不该上联邦。要把多团队子图合成一张图时读。

最容易踩的坑
  • 只按 HTTP 状态码算失败率。响应体里带 errors 的 200 才是绝大多数线上错误，仪表盘会一直绿着。
  • 把自动持久化查询当白名单。它允许客户端注册任意查询，挡不住任何恶意查询；白名单必须是构建期清单加关闭动态注册。
  • 上线不设深度与复杂度上限。graphql-js 默认两者都不限，一条合法查询就能打满连接池。
  • 列表字段不给 first 默认值和服务端硬上限。等于允许单个请求拉全表。
  • 给输出位置的枚举加新值。这是破坏性变更，老客户端的分支里没有这一项，不是「加字段都安全」的那一类。
  • 把输入字段从可空改成非空。输入和输出的兼容方向相反，这一改会让所有老客户端直接校验失败。
  • 标了 @deprecated 却没有字段用量统计。字段永远删不掉，最后 schema 只增不减。
  • 拿客户端自报的 operationName 当唯一监控维度。它可以缺失、重名、伪造，必须用规范化后的查询签名做主维度。
  • 把 variables 内容打进 metric 标签。用户 id 和搜索词会直接把时序库基数打爆。
  • 边缘缓存没按鉴权维度分桶。一个带用户态字段的查询被缓存后，会跨用户命中，这是最严重的一类事故。
  • 只在网关做授权。反向遍历和 mutation 返回对象这两条路径会绕过检查，授权必须下沉到取数层。
  • 指望一个请求里的多个 mutation 并行。规范要求 Mutation 根字段串行，耗时是三者之和，超时预算要按串行算。
  • 以为客户端断开后 resolver 会停。多数实现会继续跑完所有下游调用，中断信号要自己串到数据源。
  • 生产环境留着 introspection。内省本身就是一个深嵌套查询，还会泄露未发布的内部字段名。
