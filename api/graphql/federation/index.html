GraphQL 与微服务：Federation 的实体机制、往返代价与治理

🏷️ GraphQL 微服务

把 GraphQL 放进微服务架构，真正要解决的问题是：一次查询要跨多个服务，但对客户端必须表现为一张完整的图。谁来组合、组合发生在哪一层、组合的代价谁付，这三个问题的不同答案就是三种方案。

这篇按落地顺序讲：三种组合方式的取舍、Federation 的实体机制与它的往返代价、实体所有权为什么是成败关键、跨服务 N+1 为什么比单体更严重、Schema 治理与 CI 检查、以及网关到子图的身份透传里一个真实存在的越权风险。GraphQL 本身的执行模型见站内类型系统与执行模型一篇，DataLoader 原理见站内 N+1 与批量化一篇。

方案一被低估了。它的最大问题是发布耦合——三个团队改字段都要提同一个仓库的 PR，冲突和排队会随团队数增长；但在服务少于五个、或者只有一两个后端团队时，它的运维成本远低于联邦，而且下游根本不需要改造。不要因为「微服务」这个词就默认上联邦。

Federation 的核心机制

Federation 的全部思路可以归结为一句话：每个子图声明自己拥有哪些实体、实体的主键是什么，网关按主键把跨子图的字段拼成同一个对象。围绕这件事有四个关键指令和一个隐藏查询入口。

机制作用什么时候用代价与风险
@key声明实体主键，网关用它标识和拼接对象任何需要被其他子图扩展的类型主键必须全局稳定，用业务主键不要用自增 id 以外的可变字段
_entities 查询网关用它按一批主键向子图取实体字段，是拼接的实际执行入口由框架生成，业务代码通常只实现 __resolveReference子图内部仍逐个调用解析函数，不加 loader 就是 N+1
@external标记这个字段由别的子图拥有，本子图只是引用配合 requires 或 provides 使用被引用字段改类型时，两个子图要同时改，跨团队协调
@requires声明本子图的字段计算依赖别的子图的字段需要用别人的数据算出自己的字段时每次都多一次跨子图往返，滥用会让一次查询变成三四跳
@provides声明本子图在返回某关联对象时能顺带提供哪些外部字段本地已有冗余数据，能帮网关省掉一次往返数据冗余就有一致性风险，冗余字段过期会返回旧值
@shareable允许同一字段在多个子图定义确实需要多处提供同一字段时很容易掩盖所有权不清的问题，用之前先怀疑服务边界
# ---------- 订单子图：Order 的拥有者 ----------
extend schema @link(
  url: "https://specs.apollo.dev/federation/v2.3",
  import: ["@key", "@external", "@requires", "@provides", "@shareable"])

type Order @key(fields: "id") {      # @key 声明实体主键，网关靠它把跨子图的字段拼到一起
  id: ID!
  status: OrderStatus!
  totalAmount: Decimal!
  createdAt: DateTime!
  # 只放一个 id 指针，不要在这里定义 User 的业务字段，所有权归用户子图
  user: User
}

# 引用别的子图拥有的实体：只声明 key，字段由拥有者提供
type User @key(fields: "id", resolvable: false) {
  id: ID!
}

type Query {
  order(id: ID!): Order
  orders(first: Int = 20, after: String): OrderConnection!
}

# ---------- 用户子图：User 的拥有者 ----------
extend schema @link(
  url: "https://specs.apollo.dev/federation/v2.3",
  import: ["@key", "@external", "@requires"])

type User @key(fields: "id") {
  id: ID!
  nickname: String!
  avatarUrl: String
}

# ---------- 营销子图：只扩展自己关心的字段 ----------
extend schema @link(
  url: "https://specs.apollo.dev/federation/v2.3",
  import: ["@key", "@external", "@requires"])

type Order @key(fields: "id") {
  id: ID!
  # @external 表示这个字段由别的子图拥有，本子图只是引用它做计算
  totalAmount: Decimal! @external
  # @requires 声明本字段的计算依赖上面那个外部字段，
  # 网关会先去订单子图取 totalAmount，再连同 key 一起送进来
  # 代价很直接：多一次跨子图往返，滥用 requires 会让往返次数迅速膨胀
  estimatedPoints: Int! @requires(fields: "totalAmount")
}

二次查询就是 Federation 的性能代价

拼接不是免费的。网关先向订单子图取到订单列表和其中的用户主键，然后才能用这批主键去用户子图取昵称。这两步天然串行，因为第二步的输入是第一步的输出。

sequenceDiagram autonumber participant C as 客户端 participant G as 联邦网关 participant A as 订单子图 participant B as 用户子图 participant M as 营销子图 C->>G: 一次查询 要订单 加用户昵称 加积分 G->>G: 按组合后的 Schema 生成查询计划 G->>A: 第一跳 取订单列表与 user 的主键 A-->>G: 20 个订单 含 20 个 userId Note over G: 必须等第一跳返回
才知道要拿哪些 key 去下一跳 G->>B: 第二跳 一次 _entities 带 20 个 key B-->>G: 20 个用户的昵称 G->>M: 第三跳 积分字段声明了 requires totalAmount
网关连同金额一起送过去 M-->>G: 20 个订单的预估积分 G->>G: 按主键把三份结果合并成一棵结果树 G-->>C: 返回 Note over G,M: 跨子图字段越多 串行跳数越多
耗时是各跳之和 不是最大值

所以 Federation 的性能账要这么算：耗时约等于串行跳数乘以单跳耗时，而跳数由查询里涉及几个子图、以及有多少 @requires 决定。三跳、单跳 30ms，就是 90ms 起步，加上网关自身的查询计划与结果合并开销。优化方向只有两个：减少跨子图字段（把常一起查的字段放进同一个子图），以及用 @provides 在能接受冗余的地方省掉一跳。

实体所有权：Federation 成败的关键

技术机制都不难，难的是划分。一条规则：一个实体必须有唯一的拥有者服务，负责它的核心字段与生命周期；其他子图只扩展自己关心的字段。用户的昵称头像归用户子图，订单的状态金额归订单子图，营销子图可以给 Order 加一个「预估积分」字段，但不能去定义 status。

判断说明违反后的症状
谁负责写这个实体谁能改它的状态，它就归谁两个服务都能改同一条记录，状态机被绕过
谁是它的存储真相来源核心字段的库在谁那里，实体就归谁同一字段两处存储，长期不一致，对账对不平
其他子图只加自己的字段扩展字段必须是本子图能独立算出或独立存储的扩展字段依赖一堆 requires，往返膨胀
两个服务都想拥有同一实体这说明服务边界划错了，不是 Federation 的配置问题到处用 shareable 掩盖冲突，Schema 组合频繁失败
实体主键要全局稳定用不会变的业务主键主键变更导致网关拼接到错误对象，数据串号

最后一行的第四条值得强调：如果两个团队为「User 到底归谁」争论不下，问题不在 Federation 的用法，而在服务拆分本身。这类冲突的正确解法是回到领域边界去讨论，聚合根和上下文边界的划分见站内 DDD 相关文章。用 @shareable 把两边都满足，只是把冲突推迟到下一次 Schema 组合失败的时候。

跨服务的 N+1 更严重，而且要在两层都治

单体 GraphQL 里 N+1 的代价是多几次数据库查询；Federation 里同样的形状变成多几次跨服务 HTTP 往返，单次成本从亚毫秒跳到几十毫秒。更麻烦的是它需要两层批量同时到位，只做一层等于没做。

层次要做的事只做这一层的结果
网关侧把同一子图的实体引用攒成一次 _entities 调用网关发一次请求带 20 个 key，子图内部却逐个查库，数据库照样 20 次
子图侧__resolveReference 里走 DataLoader，把一批 key 合成一次查询子图内部批量了，但网关逐个发 HTTP 请求，20 次跨服务往返
子图对下游子图自己调别的服务时同样要批量把问题推到更下游，链路越长放大越明显
// 用户子图：__resolveReference 是网关调 _entities 时的入口
// 网关会把一批 key 打包进一次 _entities 查询，但框架仍然逐个调 __resolveReference，
// 所以子图侧照样要用 DataLoader，否则网关批量了、子图还是 N+1
export const resolvers = {
  User: {
    __resolveReference: (ref, ctx) => ctx.loaders.userById.load(ref.id),
  },
};

// 网关侧同样要有 loader：两层都做，缺一层就前功尽弃
// 第一层 网关把同一子图的实体引用攒成一次 _entities 调用
// 第二层 子图把 _entities 里的 key 攒成一次数据库查询
export const createSubgraphLoaders = (clients) => ({
  userEntities: new DataLoader(async (ids) => {
    const res = await clients.userSubgraph.request({
      query: `query($reps: [_Any!]!) {
                _entities(representations: $reps) { ... on User { id nickname avatarUrl } }
              }`,
      variables: { reps: ids.map((id) => ({ __typename: 'User', id })) },
    });
    // _entities 的返回与 representations 等长同序，直接按下标对齐即可；
    // 但要显式处理 null：某个 id 在下游被删了，这里会是 null 而不是报错
    return res.data._entities;
  }, { maxBatchSize: 100 }),
});

Schema 治理：破坏性变更会打挂整个网关

联邦最大的运维风险在这里：一个子图的破坏性变更不只影响自己，可能让整个 Schema 组合失败，网关起不来或退回旧版本。单体服务发错版只影响自己，联邦发错版影响全站。所以治理不是锦上添花。

治理事项具体做法不做的后果
组合校验进 CI子图提交时用当前其他子图的 Schema 做一次组合，组合失败直接拦合并后网关组合失败，全站受影响
破坏性变更检测与线上快照 diff，删字段、改类型、参数变必填一律拦下客户端静默报错，移动端要等发版才能修
类型命名冲突类型名在组合后的 Schema 里全局唯一，共享概念要么统一定义要么加业务前缀两个子图各自定义 Address，组合直接失败
共享枚举与标量抽成共享包统一发布，或约定由唯一子图定义其他子图引用同一枚举两处定义且值不同，组合失败或语义漂移
Schema Registry存每个子图的历史版本与组合结果，支持回滚与变更审计出问题时不知道是哪个子图哪次变更引入的
字段级使用统计网关统一采集，按子图和字段汇总删字段全靠猜，没人敢动，Schema 只增不减
子图上线顺序先发提供方再发消费方，@requires 的依赖方向要在流程里体现消费方先上线，引用的外部字段还不存在，组合失败

可观测性上有一个联邦特有的需求：要能把客户端的一次查询关联到各子图的调用。网关必须把 traceId 透传给每个子图，子图再往下游传，这样一条链路才能串起来；再配合按字段统计耗时，才能回答「这次查询慢在哪个子图的哪个字段」。链路追踪的采样与落地见站内链路追踪一篇。另外网关自身的查询计划耗时、每跳的耗时分布、以及子图错误率都要单独出指标，否则一旦某个子图变慢，只能看到「网关慢了」。

认证授权：一个真实存在的越权风险

标准做法是网关做认证，把解析出来的身份用可信请求头透传给子图，字段级鉴权在子图内部做。这个模型本身没问题，问题出在「可信」这两个字上。

❌
子图暴露在外部网络加上只信请求头，等于任意用户伪造

子图信任 x-user-id 这类请求头，是因为它假设请求只可能来自网关。一旦子图的端口在集群外可达——测试环境图方便开了公网、Ingress 配错、或者同集群内其他工作负载可以直接访问——任何人都能自己构造一个带 x-user-id 的请求，变成任意用户。这不是理论风险，是 Federation 部署里反复发生的事故。防护必须两层：网络层用 NetworkPolicy 或安全组限制来源，应用层校验网关凭证或 mTLS 客户端证书。只做一层不够，两层里任何一层配错都还有另一层兜着。

另外还有两点容易忽略：网关绝不能直接转发客户端的原始认证头给子图，要转发的是网关自己验签后重新生成的身份信息，否则子图会各自重复验签，且各子图的验签逻辑一旦不一致就出现权限判定分歧。以及字段级鉴权必须放在子图——网关看到的是查询计划和实体主键，它没有能力判断某个用户能不能看某个字段。

// ---------- 网关：认证在这里做一次，把身份用可信请求头透传给子图 ----------
const gateway = new ApolloGateway({
  buildService: ({ url }) => new RemoteGraphQLDataSource({
    url,
    willSendRequest({ request, context }) {
      // 只透传服务端自己解析出来的身份，绝不能把客户端原始头直接转发
      request.http.headers.set('x-user-id', context.viewer?.id ?? '');
      request.http.headers.set('x-user-roles', (context.viewer?.roles ?? []).join(','));
      request.http.headers.set('x-trace-id', context.traceId);   // 链路串联靠它
      // 子图之间的信任凭证：共享密钥或 mTLS 客户端证书，二者至少有一个
      request.http.headers.set('x-gateway-token', process.env.GATEWAY_TOKEN);
    },
  }),
});

// ---------- 子图：必须假设「有人能直接访问我」 ----------
// 子图只认网关来的请求。如果子图暴露在外部网络又只信请求头，
// 任何人都能伪造 x-user-id 变成任意用户 —— 这是 Federation 部署里真实发生过的越权
app.use('/graphql', (req, res, next) => {
  // 第一层：网络层面只允许集群内访问，用 NetworkPolicy 或安全组限制来源
  // 第二层：应用层校验网关凭证，两层都要，别只靠一层
  if (req.headers['x-gateway-token'] !== process.env.GATEWAY_TOKEN) {
    return res.status(403).json({ code: 'DIRECT_ACCESS_FORBIDDEN' });
  }
  next();
});

// 子图 context：身份来自可信头，字段级鉴权在子图内部做，网关管不了字段
export const context = async ({ req }) => ({
  viewer: req.headers['x-user-id']
    ? { id: req.headers['x-user-id'], roles: (req.headers['x-user-roles'] ?? '').split(',') }
    : null,
  traceId: req.headers['x-trace-id'],
  loaders: createLoaders(),
});

三种典型的「不该上」值得单独说。服务少于五个时，联邦引入的 Registry、组合校验、两层批量、跨子图追踪，成本大于它解决的发布耦合问题。跨服务实体关联很少时，更简单的做法是按域提供几个独立的 GraphQL 端点，或者给每个端做一个 BFF，客户端多发一次请求比全站背一套联邦便宜得多。团队里没人长期负责网关时，网关会迅速变成一个谁都不敢改、出问题谁都不认领的单点。

反模式速查

反模式表现后果正确做法
子图之间互相直接调用订单子图直接发 GraphQL 请求问用户子图绕过网关，形成服务间隐式依赖网，查询计划不可见，追踪断链跨子图关联交给网关组合，子图只管自己的实体
实体所有权不清两个子图都定义同一实体的核心字段，靠 shareable 糊数据长期不一致，Schema 组合频繁失败回到领域边界重新划分，一个实体一个拥有者
子图暴露给外部网络子图端口公网可达，只靠请求头判断身份任意用户伪造，直接越权网络层限制来源加应用层校验网关凭证，两层都要
网关里写业务逻辑在网关 resolver 里做计算、拼装、甚至写库网关变成新的单体，发布又耦合回去了网关只做路由与组合，业务逻辑留在子图
没有组合兼容性检查子图各自发布，不做组合校验一个子图的破坏性变更让整个网关组合失败CI 里做组合校验加破坏性变更 diff
跨服务字段设计随意一个常用查询要跨四个子图每次都三四跳串行往返，延迟无法优化把常一起查的字段收进同一子图，或用 provides 省一跳
只在一层做批量网关或子图只有一侧用了 loader另一侧照样 N 次，跨服务场景代价极高网关和子图两层都上 DataLoader
滥用 requires大量扩展字段依赖外部字段往返次数随之膨胀，耗时线性增长能本地算的就本地算，必要时接受冗余用 provides
网关转发客户端原始认证头把 Authorization 原样丢给子图各子图重复验签且逻辑可能不一致，权限判定分歧网关验签后重新生成身份头再透传
❌
最容易踩的坑

1. 因为用了微服务就默认上 Federation。服务少于五个、团队只有一两个时，单体 GraphQL 网关的总成本低得多。

2. 子图端口在集群外可达，身份又只靠请求头判断。任何人都能伪造 x-user-id 变成任意用户，这是真实发生过的越权事故。

3. 只做网络隔离或只做凭证校验。两层里任何一层配错就全线敞开，必须都做。

4. 网关直接转发客户端的 Authorization 头。各子图重复验签，逻辑一旦不一致就出现权限判定分歧。

5. 只在网关做批量，子图的 __resolveReference 没走 loader。网关一次请求带 20 个 key，子图内部照样查 20 次库。

6. 大量使用 requires。每个依赖外部字段的扩展字段都多一次跨子图往返，耗时线性叠加。

7. 用 shareable 掩盖所有权冲突。两个子图都想拥有同一实体，说明服务边界划错了，配置层面解决不了。

8. 实体主键用了可变字段。主键一变，网关拼接到错误对象上，数据串到别人身上。

9. 没有组合兼容性检查。一个子图删字段，整个网关组合失败，全站受影响，而单体服务发错版只影响自己。

10. 共享枚举各子图各自定义。值不一致时组合失败，或者更糟，组合成功但语义悄悄漂移。

11. 子图上线顺序反了。消费方先发布，它引用的外部字段还不存在，组合直接失败。

12. 网关不透传 traceId。一次查询在各子图的日志里彼此孤立，出问题只能看到网关慢，定位不到具体子图和字段。

13. 在网关里写业务逻辑。网关慢慢变成新的单体，当初为解决发布耦合而上联邦，最后又耦合回去了。
