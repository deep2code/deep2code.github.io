WSGI 与 ASGI

graph LR subgraph WSGI 同步 C1[客户端] --> W1[WSGI Server
gunicorn] W1 --> A1[WSGI App
Django/Flask] A1 --> W1 W1 --> C1 end subgraph ASGI 异步 C2[客户端] --> W2[ASGI Server
uvicorn] W2 --> A2[ASGI App
FastAPI] A2 -->|async| W2 W2 --> C2 end

WSGI/ASGI 是 Python Web 应用（应用层）与 Web 服务器（协议层）之间的接口契约：服务器解析请求、构造环境信息，调用应用对象；应用处理完返回响应给服务器写回客户端。

  • WSGI ——同步 Web 应用接口

    • python-web-app 实现 WSGI 接口，作为请求 handler
    • python-web-server（如 gunicorn）解析请求、整理环境信息
    • 服务器加载 app 并调用其 WSGI 接口处理请求，app 返回结果
    • 服务器写回响应给用户
def application(environ, start_response):
    start_response('200 OK', [('Content-Type', 'text/plain')])
    return [b'Greetings universe']

  • ASGI ——异步 Web 应用接口

    • 在 WSGI 基础上支持 asyncio 机制
    • 解决 WSGI 难以支持 WebSocket 等长连接的问题
    • 执行流程与 WSGI 类似，由事件循环驱动
async def application(scope, receive, send):
    event = await receive()
    ...
    await send({"type": "websocket.send", ...})

2026 年：FastAPI + uvicorn 是 ASGI 最主流组合；httpx 成为 async HTTP 客户端首选。

Wheel（轮子）

wheel 是 Python 新的发行标准，替代传统 egg。wheel 是一个 zip 压缩文件（把 .whl 后缀换成 .zip 即可解压查看）。优点：

  • 纯 Python 与 C 扩展包安装更快（无需现场编译）
  • 避免安装时执行任意代码（不跑 setup.py）
  • C 扩展安装不需要目标机器有编译工具链
  • 更好的缓存，利于 CI/CD 复用
  • 安装时生成与解释器匹配的 .pyc，跨平台更一致
# 制作 wheel 安装包
python setup.py bdist_wheel
# 或
pip wheel --wheel-dir=/root/whl ./

类型注解（Type Hints）

  • Python 3.5（PEP 484）引入函数类型注解；3.6（PEP 526）引入变量注解。
  • 语法：变量后加 : 类型；函数返回值用 -> 类型。
  • PEP 8 格式：冒号后跟一个空格；箭头左右各留一个空格。
  • 注解本质是元数据，运行时不影响逻辑（可用 typing.get_type_hints 读取）。
  • 2026 重要演进：Python 3.14 起 PEP 649 使注解默认惰性求值，不再在定义时立即计算注解表达式——大幅减少启动开销并消除循环导入问题（旧写法需 from __future__ import annotations）。

Python 3.14（2025 年 10 月发布）

  • 自由线程（free-threaded）转正：PEP 703 / PEP 779，3.14 起官方支持无 GIL 构建（需显式安装 free-threaded 版本或 --disable-gil 编译），多线程可真正利用多核；默认发行版仍保留 GIL。
  • 注解惰性求值（PEP 649）：注解默认不在定义时求值，启动更快、循环导入问题缓解。
  • 增量垃圾回收：长请求/长连接服务 GC 停顿从几十毫秒级降为多次小步进。
  • JIT 持续改进：3.13 引入的 copy-and-patch JIT 在 3.14 进一步稳定。

Python 3.13（2024 年 10 月发布）

  • 实验性 JIT：基于 copy-and-patch，热点函数动态编译。
  • 自由线程构建（PEP 703）：no-GIL 实验模式。
  • 改进的交互式 REPL：多行编辑、语法高亮、历史浏览。
  • typing 增强：TypeVar 默认值、ReadOnly、typing.TypeIs 等。

Python 内部原理深度解析

CPython 执行模型

CPython 是 Python 的官方实现（C 语言编写），理解其内部执行模型是写出高性能 Python 代码的基础：

  • Python 代码执行流程：
    1. 词法分析（Lexing）：将源代码文本分解为 Token（关键字、标识符、运算符、字面量、标点符号）。CPython 的词法分析器由 tokenizer.c 实现，处理缩进（Python 用缩进而非花括号表示代码块，词法分析器生成 INDENT/DEDENT Token）、注释、字符串前缀（f-string、b-string、r-string）等
    2. 语法分析（Parsing）：将 Token 流解析为抽象语法树（AST，Abstract Syntax Tree）。CPython 3.9+ 使用 PEG（Parsing Expression Grammar）解析器（替代了之前的 LL(1) 解析器，PEG 更强大，可以表达更复杂的语法，如 match-case 模式匹配）。AST 是源代码的结构化表示（每个语法结构对应一个 AST 节点，如 FunctionDef、ClassDef、BinOp、Call）
    3. 编译（Compilation）：将 AST 编译为字节码（Bytecode）。字节码是 Python 虚拟机（PVM，Python Virtual Machine）的指令集，是一种低级的、与平台无关的中间表示。编译过程包括：符号表分析（确定变量的作用域——局部/全局/闭包/内置）、控制流分析、字节码生成（将 AST 节点翻译为字节码指令序列）、常量折叠（编译时计算常量表达式，如 2 + 3 编译为 5）、优化（如死代码消除、断言在 -O 模式下移除）。编译结果是 code object（包含字节码、常量池、变量名、文件名、行号等）
    4. 解释执行（Interpretation）：Python 虚拟机（ceval.c 中的 _PyEval_EvalFrameDefault 函数，是一个巨大的 switch 循环）逐条执行字节码指令。虚拟机是栈式的（Stack-based VM），使用求值栈（Evaluation Stack）存储操作数和中间结果。每条字节码指令从栈中弹出操作数，执行操作，将结果压回栈。例如 BINARY_ADD 弹出两个操作数相加，结果压栈。Python 3.11+ 引入了 specializing adaptive interpreter（自适应特化解释器），在运行时根据操作数类型特化字节码（如 BINARY_ADD 在操作数都是 int 时特化为快速 int 加法路径），性能提升约 10-60%
    注意：Python 是解释型语言，但实际上有编译步骤（编译为字节码），只是编译在运行时自动完成（对用户透明）。字节码缓存在 .pyc 文件中（__pycache__ 目录），下次运行时如果源文件未修改，直接加载 .pyc（跳过编译步骤，加快启动速度）。
  • Python 对象模型：
    • 一切皆对象：Python 中所有数据都是对象（整数、字符串、函数、类、模块、甚至类型本身都是对象）。每个对象在堆上分配（CPython 使用私有堆，通过 PyObject_Malloc 分配），有：引用计数（ob_refcnt，用于垃圾回收）、类型指针（ob_type，指向对象的类型对象，决定对象的行为）、对象的值（不同类型有不同的数据结构）
    • 可变 vs 不可变：不可变对象（int、float、str、tuple、frozenset、bytes）创建后值不能修改——"修改"实际上是创建新对象。可变对象（list、dict、set、bytearray、自定义类实例）可以原地修改。不可变对象的优势：可以哈希（作为 dict 的 key 或 set 的元素）、线程安全（不需要锁）、可以被 intern（小整数和字符串驻留，节省内存）。可变对象的优势：原地修改效率高（不需要复制整个对象）
    • 引用计数（Reference Counting）：CPython 的主要垃圾回收机制是引用计数——每个对象有一个引用计数，被引用时 +1，引用解除时 -1，计数归 0 时立即销毁对象（释放内存）。引用计数的优势：对象可以被立即回收（不需要等到 GC 周期）、实现简单。缺点：无法处理循环引用（A 引用 B，B 引用 A，计数永远不为 0）——需要分代 GC 辅助。频繁的引用计数增减有开销（特别是多线程下需要原子操作或 GIL 保护）
    • 分代 GC（Generational GC）：用于回收循环引用的对象。CPython 将对象分为 3 代（Generation 0、1、2），新对象在 Gen 0，经过一次 GC 回收后仍存活的对象晋升到下一代。GC 频繁扫描年轻代（Gen 0 对象多、生命周期短，回收效率高），较少扫描老年代（Gen 2 对象少、生命周期长）。GC 使用标记-清除（Mark-Sweep）算法检测循环引用：从根对象（栈上的引用、全局变量、活跃的帧）开始标记所有可达对象，未标记的对象（包括循环引用组）被回收。GC 可以通过 gc 模块控制（gc.disable() 禁用、gc.collect() 手动触发、gc.set_threshold() 设置触发阈值）
    • GIL（Global Interpreter Lock，全局解释器锁）：CPython 有一个全局锁（GIL），同一时刻只有一个线程执行 Python 字节码——即使在多核 CPU 上，多线程 Python 程序也无法真正并行执行 CPU 密集型任务（因为 GIL 的存在）。GIL 的存在是因为 CPython 的内存管理不是线程安全的（引用计数需要原子操作，加锁开销大，GIL 是简单的解决方案）。GIL 的影响：CPU 密集型任务用多线程无法加速（甚至更慢，因为线程切换和 GIL 竞争开销）；IO 密集型任务（网络请求、文件读写、数据库查询）用多线程可以加速（因为 IO 等待时 GIL 会被释放，其他线程可以执行）。绕过 GIL 的方案：多进程（multiprocessing，每个进程有独立的 GIL，真正并行，但进程间通信开销大）、C 扩展（C 代码可以释放 GIL，如 numpy、pandas 的底层 C 实现释放 GIL 实现并行）、concurrent.futures.ProcessPoolExecutor、asyncio（单线程异步，适合 IO 密集型，避免线程切换开销）

8大常见陷阱与最佳实践

  1. 可变默认参数导致意外行为：Python 函数的默认参数在函数定义时求值一次（而不是每次调用时求值）。如果默认参数是可变对象（list、dict、set），且在函数内被修改，那么修改会在多次调用之间累积（因为所有调用共享同一个默认对象）。这是 Python 最经典的陷阱之一。例如：def append_to(item, target=[]): target.append(item); return target，第一次调用 append_to(1) 返回 [1]，第二次调用 append_to(2) 返回 [1, 2]（而不是预期的 [2]），因为 target 列表在多次调用间共享。解决：使用不可变的哨兵值作为默认参数（通常用 None），在函数内检查并创建可变对象：def append_to(item, target=None): if target is None: target = []; target.append(item); return target。这样每次调用 target 为 None 时都会创建新的空列表，不会累积。同样适用于 dict 默认参数：def func(config=None): if config is None: config = {}; ...。为什么 Python 这样设计？因为默认参数是函数对象的一个属性（func.__defaults__），在函数定义（def 语句执行时）就创建并存储了，而不是每次调用时创建。这种设计对于不可变默认参数（int、str、tuple）没有问题（因为不可变，修改会创建新对象，不影响默认值），但对可变对象就会有累积问题。注意：这个陷阱不仅限于函数默认参数，还包括类属性（可变类属性被所有实例共享，修改一个实例的类属性会影响所有实例——除非实例重新赋值该属性）、闭包中的可变变量等
  2. 循环引用导致内存泄漏：虽然 CPython 有分代 GC 回收循环引用，但在某些情况下循环引用会导致内存泄漏：循环引用的对象定义了 __del__ 方法（析构函数）——Python 2 中 GC 无法回收有 __del__ 的循环引用（因为无法确定安全的销毁顺序，__del__ 可能引用循环中的其他对象），这些对象会被放入 gc.garbage 列表（永远不回收）。Python 3.4+ 改进了 GC（PEP 442），可以回收有 __del__ 的循环引用，但仍有边缘情况。其他内存泄漏原因：全局变量/缓存持有对象引用（对象不再使用但仍被全局列表/dict 引用，GC 无法回收）、闭包持有大对象引用（闭包的 __closure__ 持有外部变量，即使外部函数已返回，闭包仍持有引用）、C 扩展的内存泄漏（C 代码分配的内存不受 Python GC 管理，如果 C 扩展有 bug 会泄漏）、循环引用中的对象持有外部资源（文件句柄、网络连接、数据库连接，即使对象被 GC 回收，资源可能未正确释放）。解决：避免循环引用：使用弱引用（weakref，weakref.ref(obj) 或 weakref.WeakKeyDictionary、weakref.WeakValueDictionary）打破循环——弱引用不增加引用计数，不会阻止对象被回收。常见的循环引用场景：父对象引用子对象，子对象又引用父对象（如树结构的 parent 指针、观察者模式的双向引用）——子对象对父对象用弱引用。避免定义 __del__：除非必要，不要定义 __del__ 方法（它会影响 GC 回收循环引用的效率，且 __del__ 的执行时机不确定——可能在程序退出时才执行，资源释放不及时）。需要资源清理时使用上下文管理器（with 语句，__enter__/__exit__）或 try/finally，确保资源及时释放。内存泄漏排查：使用 gc 模块（gc.get_objects() 查看所有对象、gc.garbage 查看无法回收的对象、gc.set_debug(gc.DEBUG_LEAK) 打印泄漏信息）。使用 memory_profiler（逐行内存分析）、objgraph（对象引用图可视化，找出循环引用和意外引用）、tracemalloc（Python 3.4+ 内置，跟踪内存分配，找出哪些代码分配了最多内存）、py-spy（采样分析器，查看内存和 CPU 热点）。缓存管理：使用 functools.lru_cache 时设置 maxsize（默认 128，不设置的话用 None 表示无限缓存——会缓存所有调用结果，内存持续增长）。自定义缓存使用 weakref.WeakValueDictionary（值对象不再被其他地方引用时自动从缓存中移除）。注意：Python 的内存管理通常是自动的，但理解引用计数和 GC 有助于写出不泄漏的代码。对于长时间运行的服务（如 Web 服务器、守护进程），内存泄漏是严重问题（内存持续增长最终 OOM），需要定期监控和排查
  3. GIL 导致多线程 CPU 密集型任务无法加速：CPython 的 GIL（全局解释器锁）使得同一时刻只有一个线程执行 Python 字节码，因此多线程无法并行执行 CPU 密集型任务（如数学计算、数据处理、图像处理）。很多开发者从 Java/C++ 转来 Python，习惯性地用多线程加速 CPU 任务，结果发现不仅没加速，反而更慢（线程切换和 GIL 竞争的开销）。解决：CPU 密集型任务用多进程：使用 multiprocessing 模块或 concurrent.futures.ProcessPoolExecutor，每个进程有独立的 Python 解释器和 GIL，可以真正并行执行（利用多核 CPU）。多进程的代价：进程间通信需要序列化/反序列化（pickle），开销比线程大；进程创建开销大（比线程重）；内存占用大（每个进程独立内存空间）。适合：计算密集、数据量不大（或可以分块处理）、任务之间独立（不需要频繁通信）。使用释放 GIL 的 C 扩展：numpy、pandas、scipy、opencv-python 等库的底层是 C/C++ 实现，在执行计算时会释放 GIL（Py_BEGIN_ALLOW_THREADS），因此多线程调用这些库可以实现并行（因为 C 代码执行时 GIL 被释放，其他线程可以执行 Python 代码或其他 C 计算）。例如 numpy 的矩阵运算、pandas 的数据处理在多线程下可以加速（库内部也可能用 OpenBLAS/Intel MKL 的多线程）。使用 Cython/C 扩展：将性能关键的代码用 Cython 编写（编译为 C 扩展），在 Cython 中可以释放 GIL（with nogil: 块），实现多线程并行。Cython 还可以通过静态类型声明大幅提升速度（比纯 Python 快 10-100 倍）。IO 密集型任务用多线程或 asyncio：GIL 在 IO 等待时会被释放（线程调用阻塞 IO 时，CPython 会自动释放 GIL，让其他线程执行），因此多线程对 IO 密集型任务（网络请求、数据库查询、文件读写）有效。asyncio（单线程异步 IO）是更现代的方案——用事件循环调度协程，避免线程切换开销和 GIL 竞争，适合高并发 IO（如 Web 服务器、爬虫），但需要使用支持异步的库（aiohttp、asyncpg、aioredis）。选择合适的并发方案：CPU 密集 → 多进程（ProcessPoolExecutor）或 C 扩展/numpy；IO 密集（少量并发）→ 多线程（ThreadPoolExecutor，简单，代码改最少）；IO 密集（高并发，几千上万连接）→ asyncio（性能好，资源占用少，但需要异步库和异步编程思维）。注意：Python 3.13 引入了实验性的 free-threaded mode（--disable-gil，PEP 703），可以禁用 GIL 实现真正的多线程并行，但目前还不稳定，很多 C 扩展不兼容，生产环境暂不推荐
  4. Python 代码性能优化方向错误：很多 Python 开发者优化性能时方向错误：盲目使用"Pythonic"写法（如列表推导式确实比 for 循环快，但差距不大，通常不是瓶颈）、过度微优化（如局部变量缓存、避免点号访问，这些优化在大多数场景收益很小）、忽略算法复杂度（O(n²) 的算法即使优化常数也比 O(n log n) 慢）、不测量就优化（凭直觉猜测瓶颈，结果优化了不关键的代码）。解决：先测量，再优化：使用性能分析工具找到真正的瓶颈：cProfile（内置函数级分析器，python -m cProfile -s cumulative script.py，按累计时间排序，查看哪些函数耗时最多）、line_profiler（逐行分析，@profile 装饰器标记函数，kernprof -l -v script.py，查看每行的执行时间和命中次数——找到函数内的热点行）、py-spy（采样分析器，非侵入式，可以附加到运行中的进程，py-spy top --pid 1234 实时查看热点函数，py-spy record --pid 1234 --output flame.svg 生成火焰图）、memory_profiler（内存分析）。测量后找到瓶颈（通常 80% 的时间花在 20% 的代码上——帕累托法则），只优化瓶颈代码。选择正确的数据结构和算法：这是最重要的优化——算法复杂度的差异（O(n) vs O(n²)）比任何微优化都大。常见优化：成员检查用 set/dict（O(1)）而不是 list（O(n)）；排序用内置的 sorted()（Timsort 算法，O(n log n)，高度优化的 C 实现）而不是自己写排序；字符串拼接用 ''.join(list)（O(n)）而不是 += 循环（O(n²)，因为字符串不可变，每次 += 都创建新字符串复制所有内容）；遍历大文件用 for line in file（逐行读取，内存 O(1)）而不是 file.readlines()（一次性读取所有行到内存，O(n) 内存）；使用生成器（generator，yield）处理大数据流（惰性求值，内存 O(1)）而不是列表（一次性生成所有元素，O(n) 内存）。使用内置函数和标准库：Python 的内置函数（len、sum、max、min、any、all、map、filter、zip、enumerate）和标准库（itertools、functools、collections、heapq、bisect）都是用 C 实现的，比纯 Python 循环快很多。例如 sum(nums) 比 total = 0; for n in nums: total += n 快（C 循环 vs Python 循环）。collections.Counter 比自己写字典计数快。itertools 提供高效的迭代器工具（chain、product、combinations、groupby）。向量化计算：数值计算用 numpy（向量化操作，C 实现，释放 GIL，比纯 Python 循环快 10-100 倍）。例如 np_array * 2 比 [x * 2 for x in py_list] 快很多，特别是大数组。pandas 用于表格数据处理（底层是 numpy，向量化操作）。编译为 C：对于纯 Python 的计算瓶颈，可以用 Cython（添加静态类型，编译为 C 扩展，速度提升 10-100 倍）或 Numba（@jit 装饰器，JIT 编译 Python 函数为机器码，不需要改代码，速度提升 10-100 倍，适合数值计算）。注意：过早优化是万恶之源（Premature optimization is the root of all evil）——先写清晰正确的代码，测量找到瓶颈后再优化。优化后的代码通常更复杂、更难维护，只有在性能确实不达标时才优化
  5. 异常处理（try/except）使用不当：Python 的异常处理机制强大，但使用不当会导致：异常被静默吞掉（bare except 或 except Exception 后不记录，bug 被隐藏，难以排查）、异常粒度太粗（大段代码包裹在一个 try 中，无法定位具体哪行出错）、异常类型用错（捕获了不应该捕获的异常，如 KeyboardInterrupt、SystemExit）、在循环中用异常控制流程（用 try/except 代替条件判断，异常处理有开销，且代码不清晰）、 finally 中的 return 覆盖正常返回（finally 块中的 return 会覆盖 try 块中的 return 和异常）。解决：捕获具体异常：不要用 bare except:（会捕获所有异常，包括 KeyboardInterrupt、SystemExit——这些是控制流异常，不应该被业务代码捕获）。不要用 except Exception: 除非你确实想捕获所有业务异常（且要记录日志）。应该捕获具体的异常类型（如 except ValueError:、except FileNotFoundError:、except (TypeError, KeyError):），只捕获你预期的、能处理的异常。不预期的异常应该向上传播（让程序崩溃或上层处理，暴露 bug 而不是隐藏）。异常处理粒度：try 块尽量小，只包裹可能抛出异常的代码（如文件打开、网络请求、类型转换），不要把整个函数都包在 try 中。这样可以精确定位异常来源，且不会意外捕获其他代码的异常。记录异常：捕获异常后至少要记录日志（logging.exception("message") 会自动记录异常堆栈，比 print(e) 信息全）。不要静默吞掉异常（except: pass 是最糟糕的——完全隐藏错误，程序可能在错误状态下继续运行，导致更难排查的问题）。如果确实需要忽略某些异常（如清理时的文件不存在），要注释说明原因，并只捕获具体异常。用条件判断代替异常控制流程：异常应该用于处理异常情况（错误、意外），而不是正常的控制流。例如检查字典 key 是否存在用 if key in dict:（O(1)，清晰）而不是 try: dict[key] except KeyError:（异常处理有开销，且不清晰——除非 key 大多数时候存在，此时 EAFP 风格可能更快，但可读性差）。Python 社区推崇 EAFP（Easier to Ask for Forgiveness than Permission，先操作再处理异常）风格，但 EAFP 适用于"异常情况很少发生"的场景（如文件大多数时候存在，偶尔不存在），如果异常情况经常发生（如检查用户输入是否为数字，很多输入不是数字），用 LBYL（Look Before You Leap，先检查再操作）更高效。finally 和资源清理：使用 with 语句（上下文管理器）管理资源（文件、网络连接、数据库连接、锁），with 会自动调用 __exit__ 释放资源（即使发生异常），比 try/finally 更简洁。如果必须用 try/finally，确保 finally 中的代码不会抛出新异常（会覆盖原异常）或 return（会覆盖原返回值和异常）。注意：Python 3.11+ 引入了 ExceptionGroup（异常组，可以同时抛出多个异常，如并发任务中多个失败）和 except* 语法，用于处理并发场景中的多个异常
  6. Python 包管理和虚拟环境混乱：Python 的包管理（pip）和虚拟环境（venv/virtualenv/conda）是初学者和有经验开发者都容易踩坑的地方：全局安装包（污染系统 Python，不同项目依赖冲突）、虚拟环境未激活就安装包（包装到了错误的环境）、requirements.txt 不精确（没有锁定版本，不同时间安装得到不同版本，导致"在我机器上能跑"问题）、依赖冲突（A 包需要 requests==2.20，B 包需要 requests>=2.30，pip 可能安装一个不兼容的版本）、conda 和 pip 混用（conda 环境中用 pip 安装包可能破坏 conda 的依赖管理）、Python 版本混乱（系统 Python 2.7、Python 3.8、brew 安装的 3.11、pyenv 的 3.12，不知道用的是哪个）。解决：始终使用虚拟环境：每个项目一个独立的虚拟环境（python -m venv .venv 创建，source .venv/bin/activate 激活，deactivate 退出）。虚拟环境隔离了项目依赖（每个项目有独立的 site-packages），不会污染系统 Python，也不会与其他项目冲突。不要在全局 Python 中安装项目依赖（除了 pipx 安装的全局 CLI 工具）。使用现代包管理工具：传统的 pip + requirements.txt 有很多问题（依赖解析慢、不精确、容易冲突）。推荐使用现代工具：Poetry（Python 依赖管理和打包工具，使用 pyproject.toml 声明依赖，poetry.lock 锁定精确版本（包括传递依赖的版本和哈希），依赖解析器比 pip 强大（能检测冲突），支持虚拟环境管理（自动创建和激活）、项目打包和发布。Poetry 是目前最流行的现代 Python 包管理工具。uv（Astral 开发的极速 Python 包安装器和虚拟环境管理工具，Rust 编写，比 pip 快 10-100 倍，支持 pip 兼容的命令、虚拟环境管理、依赖解析，是 pip 的现代替代品，可以和 Poetry/pyproject.toml 配合使用）。PDM（另一个现代包管理工具，支持 PEP 582（__pypackages__ 目录，不需要虚拟环境）、PEP 621（pyproject.toml 项目元数据）、依赖组）。conda（适合数据科学场景，因为 conda 可以管理 Python 版本和非 Python 依赖（如 CUDA、cuDNN、C 库），但 conda 的依赖解析慢，且与 pip 混用容易出问题。建议：数据科学项目用 conda 管理 Python 和系统级依赖，用 pip/Poetry 管理 Python 包，或者用 mamba（conda 的快速 C++ 实现）替代 conda）。锁定依赖版本：生产环境必须锁定所有依赖的精确版本（包括传递依赖），确保可复现构建。Poetry 的 poetry.lock、Pipenv 的 Pipfile.lock、pip 的 pip freeze > requirements.txt（但 pip freeze 只记录当前安装的版本，不记录依赖关系，且可能包含不必要的包）。推荐用 Poetry 或 uv（生成 uv.lock）。Python 版本管理：使用 pyenv（管理多个 Python 版本，pyenv install 3.12.0 安装，pyenv local 3.12.0 设置项目 Python 版本，自动切换）或 asdf（多语言版本管理器）。不要用系统 Python 开发（系统 Python 可能被系统工具依赖，修改它可能破坏系统；且系统 Python 版本通常较旧）。macOS 上不要用系统 Python（/usr/bin/python 是 Python 2.7，已废弃），用 brew 安装的 Python 或 pyenv。注意：Python 包管理是 Python 生态的痛点之一，社区一直在改进（PEP 517/518 构建系统、PEP 621 项目元数据、PEP 665 锁文件标准——虽被拒绝但推动了工具改进）。选择一个现代工具（Poetry 或 uv）并坚持使用，不要混用多种包管理工具
