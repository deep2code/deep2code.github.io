音视频工程：从名词到落地

🏷️ 音视频

这个分类收的是后端工程师会真正碰到的音视频问题：一个上传的文件为什么播不了、转码参数该怎么定、命令行为什么不按预期工作、转码服务的容量怎么算、直播延迟为什么压不下去。不收剪辑技巧、不收画质主观评测、也不深入编码算法的数学推导——需要的是能支撑决策的模型，不是能写论文的细节。

这块的入门障碍很特殊：不是算法难，而是名词混乱。封装格式和编码格式被混为一谈，于是「换成 MP4 就能播」这种无效方案反复出现；码率和分辨率被当成一回事，于是提了分辨率不提码率，产物反而更糊；延迟被当成一个数字，于是所有人都在讨论「能不能做到几秒」，却没人说清那几秒分别花在哪几段上。名词没对齐时，所有技术讨论都会失焦，最后变成互相说服而不是做判断。

所以这个分类只有一条主线：名词先理清，再谈编码取舍，再落到工具与分发。跳过第一步直接查命令，最常见的结局是抄来的命令能跑，但为什么用、什么时候会失效完全不知道，遇到边界情况只能再抄一条。

三类名词混淆，以及它们各自的工程代价

下面三组是工单和需求文档里出现频率最高的混淆。每一组都不只是「说法不严谨」，它们会直接导致方案选错、成本估错、或者排查方向反了。

混淆实际关系它导致的错误决策该读哪篇
封装格式当成编码格式容器负责「怎么装、怎么索引」，编码负责「怎么压小」，是两套独立命名空间把「播不了」当容器问题反复重封装；需求里只写容器，上线才发现编码不兼容音视频基本名词与数据模型
码率与分辨率当成一回事码率除以像素率才是画质的直接支配量，分辨率与帧率共同决定像素率提分辨率不提码率，产物比低分辨率版本更糊，还多付了转码与带宽基本名词 与 编码原理与编解码器选型
延迟当成一个数字延迟是采集编码、上行、转码切片、CDN、播放器缓冲五段之和，各段性质不同把工作量花在占比最小的那段；或者承诺了一个做不到的延迟目标流式传输与点播分发
关键帧与 I 帧当成同义词只有清空参考缓冲的 IDR 才是安全的随机访问入口切片边界或 seek 点对齐到非 IDR，起播花屏，却以为是编码器有问题基本名词
「换编码就能省一半带宽」压缩增益依赖内容、分辨率与编码配置，没有恒定比例按固定比例做容量规划，实际偏差很大；忽略了解码端兼容与转码成本编码原理与编解码器选型

与站内其他分类的边界

音视频链路会穿过好几个技术栈，容易和其他分类重叠。这里的划分原则是：协议与媒体数据本身的判断留在这个分类，服务器配置、通用工程能力和前端运行时放到各自分类。

主题在哪为什么不放这里
Nginx 的 RTMP 模块、HLS 切片配置、四层代理与防盗链运维与云原生 / Nginx 流媒体与四层代理那是具体服务器的配置与指令语义，换一个服务端实现就不适用；本分类只讲协议层判断
转码任务的队列、重试、幂等与分布式一致性架构与分布式这些是通用的异步任务问题，转码只是其中一种负载
首屏、卡顿率的指标定义、埋点与分位数统计可观测性与性能指标口径、基数控制与告警设计是可观测性的通用问题
浏览器端解码、WebAssembly 播放器、媒体源扩展前端与客户端那是前端运行时与浏览器能力边界的问题
对象存储、CDN 账单与冷热分层的通用策略运维与云原生本分类只讲多档位存储与按需转码这一处取舍
 
# 进入这个分类之前，先用一条命令把手上的文件看清楚。
# 这些字段对应基本名词那篇讲的每一层，排查任何问题都从它开始。
ffprobe -v error -of json -show_entries \
  'format=format_name,duration,bit_rate:stream=index,codec_type,codec_name,profile,width,height,pix_fmt,r_frame_rate,avg_frame_rate,time_base,start_time,sample_rate,channels' \
  input.mp4

# 判读顺序（顺序反了就是浪费时间）：
#   codec_name / profile   先看编码，「播不了」绝大多数在这一层
#   pix_fmt                色度采样与色深，非 8bit 4:2:0 时兼容性风险明显上升
#   format_name            最后才看容器，它与能否播放的因果关系最弱
#   width/height + 帧率 + bit_rate  算出每像素比特数，判断码率配不配得上分辨率
❌
这个分类反复纠正的判断
  • 把「播不了」当容器问题：先看编码与像素格式，容器是最后才看的一层
  • 提分辨率不提码率：每像素比特数被摊薄，产物比低分辨率版本更糊
  • 把关键帧等同于 I 帧：只有 IDR 是安全的随机访问入口，切片与 seek 都要对齐它
  • 以为加滤镜还能直通不重编码：滤镜工作在解码后的原始帧上，与直通互斥
  • 转码服务按 QPS 做容量规划：它的单位是并发进程数，一个任务会占住一段时间的 CPU
  • 把延迟当成一个数字谈：不拆成五段就无法判断该压哪里，也无法承诺目标
  • 切片和索引用同一套缓存策略：索引被长缓存会让直播停在某个时间点
  • 按固定比例估算换编码的收益：增益依赖内容与配置，还要算上转码成本与解码端兼容
