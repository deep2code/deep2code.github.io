音频处理：采样、压缩与响度

🏷️ 音视频

音频在多数团队里是被当作视频的附属品处理的：视频反复调参数，音频「随便给个 128k AAC」。结果是线上问题有相当比例出在音频侧——音量忽大忽小、对白听不清、延迟下不来、下混后声音发虚。这篇只讲音频，从 PCM 数据模型讲到响度归一化和实时链路。视频侧的名词与数据模型见站内《音视频基本名词与数据模型》，视频编码原理与选型见《编码原理与编解码器选型》，具体命令写法见《FFmpeg 的命令行模型》。

PCM 与采样定理：两个参数各自决定什么

PCM 是把连续声压在时间上离散化、在幅度上量化的结果。它只有三个参数：采样率、位深、声道数，而未压缩码率就是三者相乘——这是整条链路里唯一完全可预测的码率。

采样定理给出的结论很硬：能无歧义表示的最高频率是采样率的一半，超过这个上限的成分在采样时会折叠成低频假信号，所以采集前必须有抗折叠滤波。位深决定的是另一回事：动态范围与量化噪声本底，每增加 1 bit 大约多 6 dB 动态范围。把这两个参数混为一谈是常见错误——提高位深不会让高频回来，提高采样率也不会降低本底噪声。

由此可以判断「该不该提高采样率」。语音的可懂度能量集中在低频，宽带语音采样率已经覆盖到擦音所需的频段，再往上提采样率带来的主观收益极小，而数据量、算法开销、内存占用都成倍增长。把这份预算花在回声消除和抖动缓冲上，体验提升明显得多。

参数决定什么调大的收益与代价调小的后果不匹配时的表现
采样率可表示的最高频率为其一半覆盖更高频段；数据量与处理开销线性增长高频被截断，音色变闷；语音场景影响小，音乐场景明显按错误采样率播放会同时改变时长与音高，即变调

有损音频编码到底在丢什么

有损音频编码不是「按比例削减数据」，而是把量化噪声藏到听不见的地方。它依据心理声学模型算出一条掩蔽阈值曲线：绝对听阈之下的成分可以直接丢；强分量会掩蔽频率相邻的弱分量（同时掩蔽）；强瞬态前后很短的时间窗内也会掩蔽弱信号（时域掩蔽）。比特分配的目标就是让每个频带的量化噪声刚好压在掩蔽阈值以下。

这个机制决定了伪声的形态。码率不够时，编码器只能抬高量化噪声或者干脆放弃高频，于是出现频带截断（听起来变闷）、预回声（瞬态前出现一小段噪声）、高频成分抖动（细碎的金属声）、以及立体声联合编码过度导致的声场塌缩。知道成因才能判断该调什么：预回声要靠更短的变换窗口，声场塌缩要靠放宽联合立体声，频带截断只能靠加码率或换更高效的编码器。

Opus 的低延迟从哪来，AAC 的地位为什么难替代

Opus 的低延迟不是实现上的优化，而是结构上的设计。它把面向语音的线性预测编码和面向音乐的变换编码合成一套，按内容自动切换或混合；支持从很短到较长的一组帧长，规范允许的最小帧长在毫秒量级，因此编码固有延迟可以压得很低；同时它内建带内前向纠错、静音期不连续传输、以及丢包补偿。这三件事合起来，才是它在实时通信里难以替代的原因——不只是「延迟低」，而是「在丢包的真实网络上延迟低且还能听清」。

代价同样明确：帧长越短，每帧的头部与边信息开销占比越高，同样音质需要更高码率；带内前向纠错会额外占用码率；在苹果生态、电视、以及大量硬件解码链路上 Opus 并不通用。

AAC 的地位来自另一侧：容器支持、硬件解码器覆盖、以及整条点播与广播工具链的默认选择都是它。一个现实的架构是两段式——实时侧用 Opus 保证交互体验，进入分发侧时在网关转码为 AAC 并封装进切片，这类转码的服务端形态与资源核算见《FFmpeg 服务端转码的工程化》，切片与自适应码率见《流式传输与点播分发》。

声道、下混与重采样

多声道下混是把若干声道按系数相加，看起来简单，坑全在细节里。中置声道承载大部分对白，系数不当直接导致对白相对变弱；不同声道之间存在相位关系时相加会部分抵消，听起来发虚；相加后的电平很容易超过满刻度，必须预留衰减；低频效果声道在下混时通常被丢弃或大幅衰减。下混必须用规范给出的系数，并在下混后检查真峰值，不能自己随手平均。

场景现象根因正确做法
多声道下混后对白变小背景音乐正常，人声偏弱中置声道系数不当，或直接丢弃中置按规范系数下混，必要时对中置单独提权
下混后声音发虚整体像隔着一层声道间相位关系导致相加时部分抵消检查各声道极性；对有相关性的声道谨慎相加
下混后出现破音响处发糙相加后超过满刻度，采样峰值看不出真峰值超限预留衰减余量，并用真峰值检测把关
声道错位环绕内容跑到主声道声道布局元数据缺失或标错，按默认顺序解释显式指定声道布局，不依赖默认推断
单声道被当立体声只有一侧出声声道数与布局不一致转换时显式指定目标声道数与布局

重采样是另一个高频问题源。采样率转换本质是重建再抽样，需要滤波器逼近理想低通；非整数倍的转换（例如常见的两个标准采样率之间）对滤波器要求更高，低质量实现会带来高频镜像和相位问题，高质量实现则更吃 CPU。工程上要记住两点：一是能不转就不转，链路里统一采样率比到处重采样更可靠；二是必须转时把质量档位显式写出来，不要依赖默认值，尤其是批量转码流水线。

采样率不匹配有两种截然不同的表现，不要混淆。把样本按错误的采样率播放，时长与音高同时改变，这是变调，属于配置错误；采集与播放标称采样率相同但物理时钟有微小偏差，长时间运行后缓冲区持续累积或持续消耗，表现为规律出现的爆音、卡顿或音画漂移，这是时钟漂移，必须用自适应重采样追时钟来解决（视频侧的对应现象见《音视频基本名词与数据模型》里的三类不同步成因）。

# 显式指定重采样质量与目标声道布局，不要依赖默认值
ffmpeg -i src.mkv   -af "aresample=48000:resampler=soxr:precision=28,pan=stereo|c0=0.707*FL+0.5*FC+0.354*BL|c1=0.707*FR+0.5*FC+0.354*BR"   -c:a aac -b:a 160k -ar 48000 -ac 2 out.m4a
# 说明：
#   resampler 与 precision 决定滤波器质量，批量流水线必须显式写死
#   pan 的系数是示例写法：中置进两个声道、环绕按较低权重进入
#   下混系数应以目标规范为准，并在下混后复测真峰值，避免叠加后削波
#   若源本来就是立体声 48 kHz，整条 -af 都应省掉，能不转就不转

响度归一化：峰值和响不是一回事

最常见的音频工程错误就是用峰值归一化冒充响度归一化。峰值归一化只是把最大样点值拉到某个上限，它完全不反映人耳感受到的响：两段峰值都顶到满刻度的音频，感知响度可以差很多，因为响度取决于一段时间内的平均能量以及不同频率的加权。这就是「播放列表里前后两段音量差一大截」的直接原因。

业界标准的做法是按 ITU-R BS.1770 定义的响度测量：对信号做 K 加权（近似人耳对频率的敏感度差异），求能量均值，并用门限剔除静音段，得到以 LUFS 为单位的响度值。在此之上，EBU R128 规定了广播交付的目标响度与真峰值上限，各流媒体平台也各有自己的目标值。工程上要同时管两个量：响度对齐用 LUFS，上限保护用真峰值——真峰值考虑了采样点之间的插值峰，采样峰值看起来没超限的素材，真峰值可能已经超了，解码或重采样后就会削波。

指标含义工程用途误用后果
采样峰值样点绝对值的最大值粗略检查是否接近满刻度据此判断「没削波」，实际重采样或解码后仍会削波
真峰值考虑采样点之间插值后的峰值上限保护，交付前的硬性门槛不留余量会在不同解码路径上出现破音
整体响度（以 LUFS 计）整段的 K 加权门限平均响度不同素材之间对齐音量不做归一化会导致列表内忽大忽小
短时与瞬时响度较短时间窗内的响度定位具体段落过响或过轻只看整体值，掩盖了局部问题
响度范围响度的统计分布宽度判断动态是否被压得过死忽略它会交付出听觉疲劳严重的成品
链路类型响度目标的工程含义典型约束注意
广播与专业交付按 EBU R128 一类规范统一交付响度，并限制真峰值目标响度较低，保留较大动态余量以交付方最新技术规范为准，规范版本会更新
音乐与视频流媒体平台平台侧会对上传内容做响度归一化，超出目标的会被整体衰减各平台目标值不同，且会调整母版不要预先压到极限，以平台最新规范为准
自建点播与直播由自己定义目标值并全链路一致执行需同时约束响度目标与真峰值上限目标值一旦定下要写进转码流水线，避免逐个文件手调
语音会议与通话依赖自动增益控制在实时侧收敛，不做离线归一化关注可懂度与稳定性而非绝对值自动增益与噪声抑制互相影响，需联调

动态范围压缩（把响的部分压低、整体提上来）能让内容在嘈杂环境下更听得清，但副作用必须知道：动态被压死后听觉疲劳明显；瞬态被削弱，鼓点与齿音失去冲击力；本底噪声被一起抬起来变得可闻；平均能量升高会挤压有损编码的掩蔽余量，在低码率下反而更容易听出伪声。在平台会做响度归一化的今天，把母版压得很响并不能换来更大音量，只是白白损失动态。

# 第一步：测量。ebur128 输出在标准错误，要重定向后再看
ffmpeg -hide_banner -nostats -i input.wav   -af ebur128=peak=true -f null - 2>&1 | tail -n 20
# 判读：Integrated loudness 是整体响度，用于对齐；
#       Loudness range 反映动态宽度，过小说明被压得太狠；
#       True peak 是上限保护指标，采样峰值合格不代表它合格

# 第二步：两遍归一化。第一遍只测量并输出机器可读结果
ffmpeg -hide_banner -i input.wav   -af loudnorm=I=-16:TP=-1.5:LRA=11:print_format=json -f null - 2>&1 | tail -n 14

# 第三步：把上一步得到的 measured 值代入，做线性归一化（不引入动态压缩）
ffmpeg -i input.wav -af   loudnorm=I=-16:TP=-1.5:LRA=11:measured_I=-21.3:measured_TP=-3.1:measured_LRA=9.2:measured_thresh=-31.6:linear=true   -c:a aac -b:a 160k out.m4a
# 说明：单遍模式是动态归一化，会随时间调整增益，可能听出起伏；
#       两遍加 linear=true 是整体固定增益，适合成品交付；
#       目标 I 与 TP 应按交付方最新规范填写，示例值不要照抄上线

语音场景与音乐场景的取舍差异

语音链路的目标是可懂度与低延迟，音乐链路的目标是保真度与动态，两者的技术选择几乎处处相反。

环节语音场景音乐场景冲突点
回声消除必需，依赖播放参考信号并与采集严格对齐通常不用参考信号不对齐或时钟不同源会让回声消除失效，反而吞掉人声
噪声抑制必需，可接受一定音质损失禁用，会破坏音乐细节算法把稳态乐器成分误判为噪声
静音检测与不连续传输常开，省带宽也省电不适用阈值过激会吞掉句首和轻辅音
自动增益控制常开，让不同说话人音量接近禁用，破坏动态与噪声抑制、压缩互相耦合，必须联调
帧长与缓冲短帧短缓冲，优先延迟长帧，优先压缩效率短帧带来更高的相对码率开销
丢包应对丢包补偿加前向纠错，宁可失真不要等待重传或缓冲，宁可等待不要失真同一套参数无法同时服务两种场景

音频延迟的构成与逐段排查

端到端延迟是一串可加项，排查时必须逐段测量，否则很容易把播放设备的缓冲问题当成网络问题。下表按链路顺序列出每一段的来源与可压缩性。

环节延迟来源可压缩性压缩的代价
采集缓冲音频设备的块大小与块数有限，受操作系统与驱动约束块太小导致回调来不及，出现爆音
前处理回声消除与噪声抑制的滤波器与分析窗低，算法结构决定缩短分析窗会降低抑制效果
编码帧长加编码器前瞻可选更短帧长相对码率开销上升，压缩效率下降
网络传播时延、排队、抖动靠选路与拥塞控制，不可消除激进的拥塞控制会牺牲音质稳定性
抖动缓冲为吸收抖动而主动等待可调空间最大的一环水位调小后缓冲重建变频繁，卡顿可感
解码与丢包补偿解码本身开销较小，补偿需要上下文低削弱补偿会让丢包时出现明显断音
播放缓冲播放设备与混音层的缓冲有限过小会欠载，表现为周期性爆音

排查顺序建议是：先确认帧长与采集块大小（这是延迟下限，改不了就别指望端到端能降下来），再看抖动缓冲水位的实际分布，最后才看网络指标。很多「延迟高」的工单最终落在两个地方：采集块设得过大，或者抖动缓冲为了掩盖丢包被调到了很高的水位。

❌
最容易踩的坑

1. 用峰值归一化冒充响度归一化，结果播放列表里前后两段音量差一大截，而波形看起来都很「满」。

2. 只检查采样峰值不检查真峰值。采样峰值合格的素材在重采样或解码后照样削波，不同播放器表现还不一致。

3. 母版被压到极限求「响」。平台会做响度归一化并整体衰减，压缩换来的只有动态损失和更容易听出的编码伪声。

4. 给语音链路提采样率当优化手段。可懂度几乎不变，数据量与算法开销翻倍，真正该调的是前处理与抖动缓冲。

5. 混淆变调与时钟漂移。前者是采样率配置错，后者是物理时钟偏差，必须用自适应重采样追时钟，改配置没用。

6. 下混时自己随手平均各声道。对白变弱、相位抵消、叠加削波三个问题会同时出现。

7. 不显式指定声道布局，依赖默认推断，多声道内容声道错位而程序不报任何错。

8. 转码链路里到处重采样。每一次都引入一次滤波误差，能在链路里统一采样率就不要转。

9. 丢弃容器里的音频延迟补偿信息，拼接或转封装后出现固定音画偏移与接缝处静音。

10. 实时链路用长帧编码器省码率，延迟下限被帧长锁死，后面怎么调网络参数都没用。

11. 在音乐链路上开噪声抑制与自动增益，稳态乐器被当成噪声抹掉，动态也被抹平。

12. 把抖动缓冲水位一路调大来掩盖丢包，卡顿指标变好但延迟指标变差，交互体验反而更糟。
