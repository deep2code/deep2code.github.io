流式传输与点播分发

🏷️ 音视频

分发是音视频链路的最后一段，也是最容易把前面所有工作作废的一段：编码参数调得再好，索引的缓存头配错一行，观众看到的就是停在某个时间点不动的直播间。这篇不讲某个服务器怎么配——Nginx 的 stream 模块、RTMP 与 HLS 配置见站内《Nginx 流媒体与四层代理：RTMP、HLS 与 stream 模块》——只讲协议与分发层面的工程判断：点播为什么也要切片、HLS 与 DASH 的差异究竟落在哪几处、档位阶梯怎么排、延迟由哪几段构成又该压哪一段、缓存策略配错时现场长什么样。

渐进式下载与切片分发：点播为什么也要切片

渐进式下载就是「一个普通文件放在 HTTP 服务器上，播放器边下边播」。它能工作靠两个条件：索引在文件头部（MP4 的 moov 必须前置，否则要下载完才能起播），以及服务端支持字节区间请求，让 seek 变成一次带区间的请求。这套方案简单、缓存友好、没有任何额外服务端组件，小体积短视频用它完全够。

切片分发把一个资产拆成「一份索引 + 一串独立可解码的切片」，索引告诉播放器有哪些档位、每个档位有哪些切片、每片多长。它比渐进式下载多出来的能力只有一条，但这一条决定性：切换的粒度。渐进式下载的一个文件对应一个固定码率，换清晰度只能换 URL 重新起播；切片分发下，播放器可以在每个切片边界重新决定下一片取哪个档位，网络变化在几秒内被吸收掉。

所以「点播不需要切片，一个 MP4 加区间请求就够了」只在单码率场景成立。一旦要做多档位自适应，就必须切片，因为区间请求无法表达「下一段换一个码率」；一旦要做加密与授权，切片给了按片换密钥、按片鉴权的天然边界；一旦要做广告插入或多语言音轨独立分发，切片让音视频可以各自独立成流而不是绑死在一个文件里。

HLS 与 DASH：差异落在哪几处

两者的核心思路完全一样：一份描述档位与切片的索引，加一串独立可解码的切片。差异不在「谁更先进」，而在索引的表达方式、切片容器的历史包袱、加密体系、以及终端生态。工程上真正需要判断的只有一个问题：要不要为两套索引各存一份切片。

维度HLSDASH对工程的实际影响
索引格式m3u8 纯文本播放列表，逐行标签mpd，XML 描述树m3u8 易于手写与排查；mpd 结构表达力强但必须用库生成
档位组织主播放列表引用各档位的媒体播放列表，两层结构Period 下 AdaptationSet 再下 Representation，一个文件描述全部HLS 起播多一次索引往返；DASH 单文件但体积更大
切片 URL 表达逐条列出每个切片的 URI可用编号或时间模板由播放器推算 URI直播长窗口时 m3u8 体积随窗口线性增长，DASH 模板几乎恒定
切片容器历史上是 MPEG-TS，现在支持 fMP4基本只用 fMP4只有都用 fMP4 才有共用切片的可能
时间轴靠每片时长累加推算，直播用媒体序号标识窗口有显式的可用起始时间与时间线描述DASH 更依赖客户端与服务端时钟接近，时钟偏差会导致取不到片
加密与 DRM整段 AES 或样本级加密，配 FairPlay通用加密容器格式，配 Widevine 与 PlayReady只有统一到同一种样本加密模式，一套切片才能同时服务三家 DRM
终端生态iOS 与 Safari 原生只认 HLS桌面与 Android 浏览器靠媒体源扩展播放面向全网就必须提供 m3u8，这一条没有绕过的办法

CMAF 的价值就在最后这几行里：把切片统一成 fMP4，一套切片配两份索引，存储、回源、预热的量都少一半。但它有前提，最常被忽略的是加密模式必须统一——如果 HLS 侧和 DASH 侧用了不同的样本加密模式，切片就不能复用，必须各存一份，「共用切片」的省钱预期会在上线时落空。另一个前提是初始化段与媒体段的编码参数必须严格一致，参数集不匹配的表现是切档时黑闪或首帧花屏。

切片时长是这一层最重要的单个参数，它同时决定四件事：延迟下限、单位时间请求数、索引体积、以及编码效率（每片必须以一个 IDR 开头，片越短 I 帧占比越高，同码率下画质越差，原因见《音视频基本名词与数据模型》）。

切片时长延迟含义请求数与索引编码与缓存代价适用
亚秒级（仅配合分块传输）只有配合部分切片与分块传输才有意义，否则请求开销吃掉收益请求数最高，索引刷新最频繁I 帧占比高，边缘连接数与回源合并压力大低延迟 HLS / LL-DASH 专用
一到两秒常规协议能稳定达到的下限量级请求数明显上升，直播索引窗口需同步缩短I 帧开销可接受，多数 CDN 能扛住互动性较强的直播
四秒左右兼容性与延迟的常见折中请求数适中编码效率与缓存命中都不错大多数直播场景的默认值
六到十秒延迟明显变大，但最省资源请求数最低，长窗口下 m3u8 体积需要注意编码效率最好，边缘命中最稳点播、赛事回放、对延迟不敏感的分发

这里要纠正一个说法：「切片越短延迟越低」只在播放器缓冲片数不变的前提下成立。播放器起播通常要缓冲若干个切片，端到端延迟近似等于切片时长乘以缓冲片数，再加上其余各段。只把切片从四秒压到一秒、而播放器仍然缓冲三片，收益是有的；但如果播放器为了防卡顿把缓冲片数相应调大，延迟会几乎回到原点，同时请求数翻了几倍。压延迟必须两个量一起看。具体到 Nginx 自建链路的量级数字，见站内 Nginx 流媒体那篇的延迟构成表。

自适应码率：档位阶梯与切换决策

自适应码率的工作方式是：播放器估计当前可用吞吐，结合缓冲水位，决定下一个切片取哪个档位。所以档位阶梯是播放体验的上限——阶梯排错了，再好的决策算法也只能在错的选项之间挑。

阶梯设计有三条可操作的原则。第一，相邻档位的码率要拉开距离，经验上大致在一点五到两倍之间；间隔太密时，两个档位的实际观感差别很小，而吞吐估计的噪声就足以在它们之间反复触发切换，用户看到的是画质忽好忽坏。第二，降码率必须同时降分辨率；只降码率不降分辨率会让每像素比特数崩掉，低档位表现为大面积块效应，还不如直接给一个更低分辨率的版本。第三，最低档要真的够低，它的职责不是好看，而是在目标弱网条件下保证不卡；最高档则受源片真实清晰度限制，源是上采样的就不要加更高档位，只是白付存储和带宽。

切换决策的依据也常被误解：主流播放器不是只看带宽。纯吞吐驱动的算法在启播和网络抖动时表现很差，实际实现普遍是吞吐估计与缓冲水位混合——缓冲很浅时保守（宁可低档也要先把水位建起来），缓冲充足时才敢试探升档；并且加上滞回与最小停留时间，避免在边界反复跳。

现象最可能的根因怎么验证修法

直播延迟的构成：压哪一段收益最大

「延迟」被当成一个数字是最常见的沟通事故。它是五段之和，每段的性质、可压缩空间和压缩代价都不一样，不拆开谈就没法决定动哪里。

环节延迟性质能压到什么量级压它的代价收益排序
采集与编码基本固定，由编码器结构决定禁用 B 帧、降低前瞻与缓冲后可到帧级量级同码率下压缩效率下降，画质变差低：占比小，但必须做，否则是固有下限
上行推流方差最大，取决于链路质量与重传好网络下是一个往返量级，弱网下取决于重传策略抗抖动缓冲减小会导致上行断流与花屏中：弱网场景下是主要不稳定源
转码与切片固定：必须收满一个切片才能发布下限是一个切片时长，转码本身是流水线增量切片变短则请求数与 I 帧占比上升高：与播放器缓冲共同构成主要部分
CDN 分发命中后很小，回源时增加一跳边缘命中时可忽略，首次回源明显更大预热与回源合并增加架构复杂度中：主要影响首屏与开播瞬间
播放器缓冲固定：通常若干个切片可减到一个切片量级，再低要靠分块传输缓冲越浅，卡顿率越高，这是直接取舍最高：延迟里占比最大的一块

结论很明确：标准 HLS 与 DASH 的延迟被「切片时长乘以播放器缓冲片数」锁死，其余各段的优化大多被这一项掩盖。先把这个乘积压下来，再去抠编码与上行；顺序反了，工作量全花在看不见的地方。要突破这个乘积，必须换机制——要么让发布单位小于切片，要么换协议。

低延迟 HLS 与 LL-DASH：把延迟拆到切片以下

两者的共同思路是解耦「编码单位」与「发布单位」。切片仍然是 GOP 对齐的完整单位，但服务端不再等整片写完才发布：把切片内部再分成很小的块（每块只含少量帧），用分块传输边生成边发，播放器在切片尚未完成时就开始拉取并解码。于是延迟不再受整片时长约束，而是受一个块的时长约束。

低延迟 HLS 在此之上还加了两个机制。一是部分切片在索引里单独声明，播放器知道当前正在生成的片已经有哪些块可取。二是阻塞式索引刷新：播放器请求索引时带上「我要比这个版本更新的」，服务端把请求挂住，直到有新内容才响应，从而消掉轮询间隔带来的那段等待。LL-DASH 主要靠分块传输配合可用时间偏移来表达同样的语义。

代价要说清楚。第一，也是上线后延迟没降的最常见原因：CDN 必须支持分块透传，边缘如果要收完整片才回给客户端，所有低延迟机制原地归零，看起来一切配置都对但延迟和标准 HLS 一样。第二，阻塞式索引刷新把索引请求从「短请求高频率」变成「长挂起连接」，边缘的并发连接数模型完全变了，容量评估要重做。第三，请求数上升，回源合并必须做，否则一个块会被大量边缘同时回源。第四，播放器侧的实现差异比标准 HLS 大得多，兼容性验证成本高。

WebRTC 的适用边界

WebRTC 换来的是端到端的亚秒级延迟：传输走 UDP，媒体不切片，丢包恢复与拥塞控制做在媒体层（重传请求、前向纠错、关键帧请求），编码侧禁用 B 帧并能按拥塞反馈动态调码率。互动类场景没有替代品。

代价在分发模型上，而且是结构性的：它不是 HTTP 缓存模型。切片分发里一个切片被缓存一次就能服务成千上万观众，成本被缓存摊薄；WebRTC 的每个观众都是一条独立会话，边缘要为每个人维护状态并转发媒体，成本随并发观众数线性增长，规模化还要做级联转发与就近接入。另外它无法直接复用已有的点播产物与 CDN，录制与回看需要再搭一条链路；网络受限环境下还要准备中继回退。

判断标准可以很简单：需要「双向」或「亚秒级互动」才上 WebRTC；只是想「延迟低一点」，低延迟 HLS 的性价比高得多。把只需要单向观看的大规模直播做成 WebRTC，通常在观众量涨起来之后才发现成本曲线不对。

CDN 与缓存策略：索引和切片必须分开对待

这一层的错误最廉价也最致命：改一行响应头就能修，但配错时的现象完全不像缓存问题。原则只有一句——切片是不变对象，索引是易变对象，两者的缓存策略必须不同。

回源侧有两件事必须做。一是回源合并：同一个切片在生成瞬间会被大量边缘同时请求，不合并就等于让源站承受一次并发放大。二是预热：点播首发内容和活动开播前的初始化段与首几片提前推到边缘，否则开播瞬间所有请求同时回源，这一下的抖动直接体现在首屏指标上。另外如果保留了渐进式下载入口，要确认边缘支持区间缓存，否则每个区间请求都回源拉整个文件。

HTTP/1.1 200 OK
Content-Type: video/iso.segment
Cache-Control: public, max-age=31536000, immutable
# 切片：内容永不改变，长缓存 + immutable，让浏览器连校验请求都省掉

HTTP/1.1 200 OK
Content-Type: application/vnd.apple.mpegurl
Cache-Control: no-cache
ETag: "seq-1489"
# 直播索引：no-cache 表示每次都要校验，命中 ETag 时返回 304，体积极小
# 千万不要写成 max-age 大于一个切片时长，那会让画面停在某个时间点

HTTP/1.1 200 OK
Content-Type: application/vnd.apple.mpegurl
Cache-Control: public, max-age=600
# 点播索引：内容固定，可以中等时长缓存；换档位配置时改 URL 版本号而不是改内容

点播的存储与分发取舍

点播多档位有两种极端做法：全部预转码存起来，或者按需转码。它们的成本函数形状不同，所以没有普适答案，只有按内容热度分布做的判断。

维度全量预转码按需转码热冷分层（混合）
存储成本随档位数线性增长，冷内容也全额付费只存源片与已缓存产物热内容全档位，冷内容只留源与一个中间档
转码成本按资产数付一次按播放请求付，重复播放靠缓存摊薄两者都有，但都只花在有人看的内容上
首次播放延迟最低，产物已就绪首次请求要等转码，冷启动明显热内容最低，冷内容首播稍慢
失败面转码失败在离线阶段发现，不影响播放转码故障直接变成播放失败，是在线依赖冷内容仍有在线依赖，但影响范围可控
长尾利用率最差：大量档位从未被请求最好：没人看就不花转码钱好，取决于热度判定是否准确
适用资产少、播放量集中、延迟要求苛刻海量长尾、播放极度不均、存储是主要成本大多数真实业务的落点

选按需转码要接受一个事实：转码从离线任务变成了在线依赖，它的排队、超时、失败处理会直接反映成播放失败率，容量模型、并发上限与幂等产物的设计见《FFmpeg 服务端转码的工程化》。另外无论哪种做法，档位数量本身就是成本项——统计各档位的真实播放占比，删掉长期无人选择的档位，通常比优化编码参数省得更多。

首屏时间与卡顿率各受什么支配

这两个指标经常被放在一起说，但它们的影响因素几乎不重叠，混着优化就会互相打架（缩短缓冲改善首屏，却抬高卡顿率）。

首屏时间由起播路径上的串行步骤决定：域名解析与连接建立、主索引请求、媒体索引请求（HLS 的两层结构在这里多一次往返）、初始化段、第一个切片、解码到第一帧。可优化的点集中在减少串行往返（预连接、把主索引与首档媒体索引尽量少一跳）、让起播档位不要过高（首片太大直接拖慢首屏）、保证初始化段与首片在边缘命中、以及确保首片开头就是 IDR 与完整参数集，否则解码器要等下一个入口。

卡顿率本质是缓冲水位耗尽的次数，受 ABR 决策质量、最低档是否足够低、切片时长（片越大单次下载的抖动越大）、边缘命中率与回源抖动、以及播放器缓冲上限共同影响。压延迟必然抬高卡顿率，这是同一个缓冲水位的两端，不存在同时最优。

埋点口径比数值更重要：首屏要按「用户触发播放到第一帧渲染」统计，而不是「请求发出到响应返回」；卡顿要把起播缓冲与播放中缓冲分开，否则首屏差会被算成卡顿；两者都要按档位、地区、运营商分维度看，整体平均值会把区域性故障完全抹平。指标定义、分位数与基数控制见《可观测性与性能》。

# 一、直播卡在某个时间点：先看索引的缓存行为，而不是先看播放器
curl -sD - -o /dev/null "https://cdn.example.com/live/room1/v0/index.m3u8" \
  | grep -iE 'cache-control|age|etag|x-cache'
# 判读：age 接近或超过一个切片时长，或 cache-control 带较大的 max-age，
# 基本可以确定是索引被错误缓存；x-cache 命中标识说明这一份来自边缘而非源站

# 二、确认上游是否还在推进：连续取两次索引，比对窗口首片序号
for i in 1 2; do
  curl -s "https://cdn.example.com/live/room1/v0/index.m3u8" \
    | grep -E 'EXT-X-MEDIA-SEQUENCE|EXT-X-PART|EXTINF' | head -n 5
  sleep 5
done
# 判读：序号不变说明上游断流或转码停了；序号变了但播放器仍旧卡，就是客户端侧问题

# 三、确认切片确实被长缓存（这是回源带宽失控的第一嫌疑）
curl -sD - -o /dev/null "https://cdn.example.com/live/room1/v0/seg-1489.m4s" \
  | grep -iE 'cache-control|age|x-cache'
# 判读：切片上出现 no-cache 或很短的 max-age，就是源站被打爆的直接原因

# 四、点播 MP4 是否适合边下边播：索引在头部才行
ffprobe -v error -show_entries format=format_name,duration,start_time \
  -of default=noprint_wrappers=1 vod.mp4
ffmpeg -hide_banner -v verbose -i vod.mp4 -c copy -f null - 2>&1 \
  | grep -iE 'moov|faststart' | head -n 5
# 判读：提示需要在文件后部寻找索引，说明必须重封装前置索引，否则首屏要等整个文件
❌
最容易踩的坑

1. 直播的媒体播放列表被设了较大的 max-age。表现不是加载失败，而是画面停在某个时间点，随后请求已清理的切片得到 404，排查时却一直在怀疑播放器。

2. 切片被设成 no-cache 或极短缓存。边缘几乎不命中，回源带宽接近观众总带宽，源站在流量高峰第一个倒。

3. 只把切片时长压短却不动播放器缓冲片数认定的延迟。延迟近似等于两者之积，只改一个，收益会被另一个吃掉，而请求数已经翻了几倍。

4. 相邻档位码率只差一点。吞吐估计的噪声就能触发来回切换，用户看到画质忽好忽坏，指标上表现为切换次数异常高。

5. 降码率不降分辨率。低档位每像素比特数崩掉，出现大面积块效应，还不如直接给更低分辨率的版本。

6. 最低档位定得不够低。弱网用户降到底仍然卡，ABR 无处可退，卡顿率怎么调都下不来。

7. 各档位编码参数不一致或切档时不取新档位的初始化段。切换瞬间黑闪或首帧花屏，容易被误判成网络抖动。

8. 音频跟着视频档位一起切，且切片边界不对齐。切档时音频断一下，比画质变化更容易被用户察觉。

9. 打算让 HLS 与 DASH 共用一套 CMAF 切片，却让两侧用了不同的样本加密模式。切片无法复用，存储和回源省不下来。

10. 上了低延迟 HLS 但 CDN 不支持分块透传。边缘等整片收完才回客户端，所有机制归零，延迟和标准 HLS 一样。

11. 没做回源合并。切片生成瞬间被大量边缘同时回源，源站看到的是一次并发放大，而不是一次请求。

12. 缓存键里忽略了区分内容的查询参数。不同房间或档位互相串流，这是内容错乱类事故里最难复现的一种。

13. 大规模单向直播选了 WebRTC。成本随并发观众线性增长，缓存摊薄的优势完全失去，通常在观众量涨上来后才发现。

14. 首屏与卡顿用同一个缓冲配置去优化。它们是同一个水位的两端，只能按业务取舍，不存在同时最优。
