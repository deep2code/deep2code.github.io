FFmpeg 的命令行模型

🏷️ 音视频

FFmpeg 难用，不是因为参数多，而是因为它的命令行不是一串扁平开关，而是一张对象图压平成的一行文本：一个全局作用域、若干个输入对象、若干个输出对象，每个对象各自挂着一组只对它生效的选项。同一个 -ss 写在 -i 前面和后面是两件不同的事；同一个 -t 挂在输入上是「只读这么长」，挂在输出上是「只写这么长」。命令记不完，但理解这张图之后，大部分参数可以推出来，行为不符合预期时也知道该怀疑哪一层。

本篇只讲处理模型与工程判断。PTS/DTS、GOP 与关键帧、色彩空间这些名词详见站内《音视频基本名词与数据模型》；编解码器选型与码率控制详见《编码原理与编解码器选型》；采样率与响度详见《音频处理：采样、压缩与响度》。把 ffmpeg 进程放进线上服务之后的并发、超时、安全边界问题，见《FFmpeg 服务端转码的工程化》。

命令行是一张对象图

一条完整命令的骨架永远是四段：可执行文件、全局选项、重复 N 次的「本输入的选项 + -i 输入地址」、重复 M 次的「本输出的选项 + 输出地址」。选项没有命名空间，它归谁管完全由位置决定：出现在某个 -i 之前且在上一个输入或输出之后的选项，属于这个输入；出现在某个输出路径之前的选项，属于这个输出。

这解释了一个很常见的现象：把参数「整理」成看起来更整齐的顺序之后，命令行为变了，而 FFmpeg 一句警告都不给。因为它没错——你只是把选项挂到了另一个对象上，而那也是合法组合。也解释了为什么同样的参数在网上抄来的两条命令里表现不同：它们的位置不一样。

输出可以有多个，这一点经常被忽略。一次解码的结果可以喂给多个输出，写出多档位产物或同时产出预览图，比起跑三遍命令能省掉重复的解复用与解码开销。这是服务端多档位转码最基础的省 CPU 手段。

-ss解复用层直接跳到目标位置附近再开始读，只解码切点之后的内容，快从头解码并丢弃切点之前的帧，输出精确到指定时刻放输出侧做长视频截取会白解码前面几十分钟；放输入侧在某些容器上起点会偏到前一个关键帧

-pix_fmt基本无意义指定编码前的像素格式不写就由编码器和源共同决定，可能产出很多播放器不支持的格式

五个阶段：哪些能跳过决定了成本

不管命令多复杂，数据流永远走同一条流水线：解复用把容器拆成若干条流的压缩包，解码把压缩包还原成原始帧，滤镜在原始帧上做加工，编码把帧压回包，复用把包写进目标容器。CPU 几乎全花在解码和编码上，其中编码通常是解码的数倍。

工程判断的关键就是：这次任务能跳过哪几段。只换容器（比如 MKV 换成 MP4）可以跳过解码、滤镜、编码三段，成本从「按视频时长的几分之一」降到「按文件大小的 I/O 时间」，量级差距非常大。只改音量不改画面，可以让视频侧走直通、音频侧走完整链路，这是很多人不知道的写法：-c:v copy -c:a aac，编码器是按流分别指定的。

-ss 的两种语义：这是最值得讲清的一条

「-ss 放前面不准、放后面准」是流传最广的说法，今天已经不完全对了。现代 FFmpeg 在输入侧 -ss 上会做关键帧定位后再解码丢弃到精确位置，输出通常也是准的；真正的差别在解码了多少无用数据，以及重封装时切点只能落在关键帧上这个物理约束。

所以要分两种情况判断。重编码时，输入侧 -ss 既快又准，是首选；输出侧 -ss 只在需要保留原始时间戳语义的少数场景才用。重封装（-c copy）时，起点必然被吸附到切点之前或之后的关键帧，想要「精确到帧」的切割在不重编码的前提下不可能实现，这不是参数问题。要么接受起点偏移，要么只对切点附近重编码、中间段直通，要么整段重编码。

# 场景一：从第 30 分钟起截 10 秒，重编码。-ss 在 -i 之前，只解码需要的那一小段
ffmpeg -hide_banner -ss 00:30:00 -t 10 -i in.mp4 \
  -c:v libx264 -preset veryfast -pix_fmt yuv420p -c:a aac out.mp4

# 场景二：同样的截取但不重编码。注意 -c copy 时切点被吸附到关键帧，
# 起点可能早于 00:30:00；-avoid_negative_ts 防止首包时间戳为负导致播放器卡在开头
ffmpeg -hide_banner -ss 00:30:00 -t 10 -i in.mp4 \
  -c copy -avoid_negative_ts make_zero cut.mp4

# 场景三：确认实际切到了哪里。对比 start_time 与你要的 30 分钟差多少
ffprobe -v error -select_streams v:0 \
  -show_entries stream=codec_name,start_time,r_frame_rate,avg_frame_rate,nb_frames \
  -show_entries format=duration -of default=noprint_wrappers=1 cut.mp4

# 场景四：只改音频、视频直通。编码器按流指定，视频侧完全跳过解码与编码
ffmpeg -hide_banner -i in.mp4 -c:v copy -c:a aac -b:a 128k -af loudnorm out_audio_fixed.mp4

重封装的前提条件与它失败的原因

-c copy 是 FFmpeg 里性价比最高的开关，也是最容易产出「能生成但播不对」的开关。它的前提有三条，任何一条不满足都会出问题，而且多数情况下不会以报错的形式出现。

第一是编码必须被目标容器接受。MP4 不接受 Vorbis 和 PCM 的某些变体，也不接受 SRT 文本字幕（需要转成 mov_text）；WebM 只接受有限的几种编码。这一类通常会报错，是三类里最友好的。第二是时间戳必须可用。源文件时间戳跳变、为负、不单调递增，搬到新容器里就变成音画不同步、进度条乱跳、开头卡住。第三是切点必须落在关键帧上，否则切点后的那个 GOP 缺少参考帧，表现为开头一两秒花屏、灰屏或干脆黑一段。

-map：默认流选择是丢轨的根源

不写 -map 时，FFmpeg 会执行一套默认流选择：对每一类流（视频、音频、字幕）各挑一条「最好的」，视频按分辨率、音频按声道数，同分时取序号小的那条。注意是每类一条——这就是为什么一个带国语、粤语、英语三条音轨和两条字幕的文件，转完只剩一条音轨、字幕全没了。命令没报错，因为这是设计行为。

-map 的语法是「输入序号 : 流类型 : 该类型内的序号」。-map 0:a:1 意思是第 0 个输入里第 2 条音频流（序号从 0 起），注意这个 1 是音频流之间的相对序号，不是文件里的全局流序号，这是最常见的理解错误。想按全局序号选就写 -map 0:3。选中的顺序决定了输出里流的排列顺序，第一条同类流通常被播放器当作默认轨。

目标不写 -map 的实际行为正确写法备注
保留全部流每类只留一条，其余静默丢弃-map 0再配合 -c copy 才是真正的「原样换容器」
只要第二条音轨拿到的是声道数最多的那条，不一定是你要的-map 0:v:0 -map 0:a:1冒号后的序号是同类型内相对序号
视频取自文件 A、音频取自文件 B只会用到 A 的流，B 被当成无用输入-map 0:v:0 -map 1:a:0两个输入时长不同要决定用 -shortest 还是补齐
丢掉所有字幕可能带上一条也可能不带-map 0 -map -0:s负号表示从已选集合里排除
某类流可能不存在时不要报错指定不存在的流会直接失败-map 0:a?问号表示可选，批处理管道里很重要
一次解码产出多档位只能写一个输出一条命令写多个输出，各自带自己的 -map 与编码参数省掉重复解复用与解码，详见工程化篇

滤镜图：-vf 与 -filter_complex 的分界

分界线很清楚：-vf（以及音频的 -af）是单输入单输出的线性滤镜链，隐式地把当前输出所选的那条流接进来，处理完再接出去；-filter_complex 是任意输入任意输出的图，必须自己用方括号标签把流接起来。只要涉及第二个输入（叠水印、画中画、拼接）或者要产出多路结果（一次解码分出两个分辨率），就只能用 -filter_complex。

标签语义是这样的：[0:v] 表示第 0 个输入的视频流作为某个滤镜的输入；一个滤镜后面紧跟 [名字] 表示把它的输出命名，供后面的滤镜或 -map 引用。[0:v][1:v]overlay[out] 读作「拿输入 0 的视频和输入 1 的视频做叠加，结果叫 out」。-filter_complex 产出的命名标签必须用 -map 引用才会写进输出，这是初学者最容易漏的一步：图写对了但输出里没有它。

还有一个必须内化的结论：滤镜介入就不可能 -c copy。滤镜工作在原始帧上，而 copy 意味着根本不解码，两者在流水线上互斥。同理，缩放、加水印、烧字幕、改帧率、改色彩空间，全部注定要重编码。看到有人写「加水印但用 copy 省 CPU」，那条命令要么报错，要么水印根本没生效。

像素格式与时间戳：两类静默出错

-pix_fmt yuv420p 几乎成了肌肉记忆，原因值得说清。H.264 允许 yuv444p、yuv422p 这些色度不抽样或半抽样的格式，x264 在源是 RGB 或高色深时也会自然选择它们；但大量硬件解码器和浏览器只实现了 yuv420p 的 High profile 解码路径。结果就是：文件在你的桌面播放器上一切正常，用户在手机或浏览器里黑屏、只有声音。同样，源是 10bit 而输出没有显式降到 8bit，也会撞上同一类兼容性墙。所以这不是「习惯」，而是对未知播放端做的显式收敛。

时间戳问题的根源在于，源文件的时间戳可能带负偏移（编辑软件导出的常见现象）、可能缺失（裸流、某些网络流）、可能不均匀（手机录制的可变帧率）。转码时这些问题会被继承甚至放大。可变帧率转固定帧率是一个必须显式表达的动作，靠输出 -r 让 FFmpeg 丢帧补帧是可行的，但要清楚它在做什么：复制或丢弃整帧来凑目标节奏，画面上表现为轻微顿跳。

参数作用什么时候需要副作用与注意
-pix_fmt yuv420p强制输出 8bit 4:2:0产物要给未知播放端消费时，默认就该加色度抽样有损，对纯色图形和文字画面有可见劣化
-avoid_negative_ts make_zero把首包时间戳平移到从 0 开始剪切后 copy、或源带负偏移平移是整体的，不修内部跳变
-fflags +genpts为缺失 PTS 的包重新生成时间戳输入是裸流或时间戳损坏的录制文件生成值是推算的，若源本来有部分正确时间戳可能反而更乱
-copyts保留输入时间戳不做归零需要多路产物时间轴严格对齐，或要与外部时间线对账会把负时间戳和空洞一起保留，通常要配合上面两个参数
输出 -r 或 -fps_mode cfr把可变帧率规整为固定帧率下游要求恒定帧率，或做逐帧处理丢帧补帧会造成节奏轻微不均；新版用 -fps_mode，-vsync 是旧写法
-shortest以最短的那条输入流结束输出音视频来自不同输入且时长不等可能意外截短正片，确认哪条流最短再用

跑完没报错但结果不对：判读方法

这是 FFmpeg 使用中最耗时的一类问题。要点是别靠肉眼看视频，而是用 ffprobe 把输入和输出的流结构都打出来做逐字段比对，再配合把 -loglevel 提到 verbose 看 FFmpeg 自己是怎么选流、怎么建滤镜图的。启动时打印的那段流信息与 Stream mapping 行，已经回答了一半的问题：它明确写了每条输入流去了哪个输出、用了什么编码器，或者标着 copy。

还有一个很有用的技巧：用 -f null - 让 FFmpeg 走完整解码与滤镜链但不写文件，可以在不产出垃圾的前提下验证输入是否能被完整解码、有多少解码错误，用来分辨「输入本身坏了」还是「参数写错了」。

# 一、把输入输出的流结构拉平做比对，先看流的条数和类型是否符合预期
for f in in.mp4 out.mp4; do
  echo "=== $f"
  ffprobe -v error -show_entries stream=index,codec_type,codec_name,profile,pix_fmt,width,height,r_frame_rate,avg_frame_rate,time_base,start_time,duration,channels \
    -of csv=p=0 "$f"
done

# 二、看 FFmpeg 到底选了哪些流、建了什么滤镜图。Stream mapping 那几行是关键
ffmpeg -hide_banner -loglevel verbose -i in.mp4 -c copy -f null - 2>&1 | sed -n '/Stream mapping/,/^$/p'

# 三、完整解码但不落盘，用来判断输入是否损坏。统计解码告警条数
ffmpeg -hide_banner -v warning -i in.mp4 -f null - 2>&1 | wc -l

# 四、列出关键帧时间点，判断 copy 剪切的切点会被吸附到哪里
ffprobe -v error -select_streams v:0 -skip_frame nokey \
  -show_entries frame=pkt_pts_time -of csv=p=0 in.mp4 | head -50
ffprobe 字段含义出现什么值要警惕
codec_name / profile编码与档次profile 高于 High 或带 4:4:4 标记，兼容性风险大
pix_fmt像素格式不是 yuv420p 时，未知播放端黑屏概率明显升高
r_frame_rate 与 avg_frame_rate标称帧率与实际平均帧率两者差异明显说明是可变帧率，直接 copy 剪切容易不同步
start_time该流第一个包的时间非零或为负，说明有偏移，copy 后播放器行为不可预期
duration（流级）与 format.duration流时长与容器声明时长两者不一致，说明索引或时间戳有问题
nb_frames帧数（部分容器才有）为 0 或与时长乘帧率严重不符，说明索引不完整
channels / channel_layout声道数与布局多声道源在默认流选择下会被优先挑走，可能不是你想要的那条轨
「没报错但不对」的现象最可能的成因验证动作
音轨少了、字幕没了默认流选择每类只取一条对输出跑 ffprobe 数流条数，与输入比对
水印或缩放没生效滤镜标签没被 -map 引用，或参数挂在了错误的输出上看 verbose 日志里的滤镜图与 Stream mapping
输出时长远超预期-t 挂错侧，或两个输入时长不等且没用 -shortest比对 format.duration 与预期
某些设备黑屏但有声音像素格式或 profile 超出设备支持看输出的 pix_fmt 与 profile 字段
开头卡住几秒才开始播首包时间戳为负或有偏移看输出流的 start_time
画面卡顿但码率不高可变帧率没规整，或帧率被输出 -r 改成不匹配的值比对 r_frame_rate 与 avg_frame_rate
第二个输出文件空或极小第二个输出没有 -map，默认流选择在多输出下不符合直觉给每个输出显式写 -map
❌
最容易踩的坑

1. 把输出侧参数写到 -i 前面：不报错，但作用对象变了。改命令顺序永远等于改语义。

2. 用 -c copy 做精确剪切：切点必然吸附到关键帧，「加个参数就能精确」是不存在的，只能重编码或局部重编码。

3. 不写 -map 就转多音轨文件：每类流只留一条，多语言音轨和全部字幕静默消失。

4. 把 -map 0:a:1 的序号当成全局流序号：它是音频流之间的相对序号，要用全局序号得写 -map 0:3。

5. 以为滤镜可以和 -c copy 共存：滤镜工作在原始帧上，两者在流水线上互斥。

6. -filter_complex 里定义了命名标签却没用 -map 引用：图正确，输出里却没有它。

7. scale=-1:720 算出奇数宽度，遇上 yuv420p 直接报错；用 -2 对齐偶数。

8. 忘记 -pix_fmt yuv420p：桌面播放正常，手机和浏览器黑屏只有声音。

9. 剪切后不加 -avoid_negative_ts make_zero：负时间戳让播放器开头卡住或进度条错乱。

10. 可变帧率源直接 copy 剪切：音画一开始同步，越播偏差越大。

11. 写管道输出忘了输出侧 -f：FFmpeg 无法从路径猜格式，直接失败。

12. 多档位转码跑多遍命令：应当一条命令多输出，共享一次解复用与解码。
