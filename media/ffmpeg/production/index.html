FFmpeg 服务端转码的工程化

🏷️ 音视频

命令本身怎么写——参数位置语义、五阶段流水线、-c copy 的分界、-map 与滤镜图——父页《FFmpeg 的命令行模型》已经讲透。本篇假定命令是对的，只谈把 ffmpeg 当成一个受控的、必然会失败的、单任务就能吃满整机 CPU 的外部进程来运营的工程问题：并发怎么限、任务怎么排、卡住怎么判、孤儿进程怎么收、不可信输入怎么隔离、失败怎么分类、该埋什么指标。

资源模型：容量的单位是并发数，不是 QPS

软件编码是最纯粹的 CPU 密集负载，编码器内部本身就是多线程的，一个任务在合适的预设下就能把整台机器的核占满。于是有了一个与普通后端服务完全相反的结论：加机器不会让你「扛住更多并发」，只会让总吞吐按机器数线性增加。容量只能用「同时能跑几个任务」描述，且必须显式设定并强制执行——让请求量决定并发的系统在高峰时不是变慢，是所有任务一起慢到全部超时，已烧掉的 CPU 全部作废。

分工要分清：-threads 控制单任务内部并行度，队列消费并发控制同时有几个任务，两者相乘才是真正的 CPU 需求。最常见的错误是两边都放开，十六核机器上跑八个任务、每个都让 FFmpeg 自动决定线程数，上百个线程抢十几个核，上下文切换与缓存抖动让总吞吐低于只跑四个任务。怎么分配取决于优化目标：用户在前台等就少并发多线程；离线批量入库就多并发少线程，因为编码的多线程加速比明显次线性，而独立进程之间几乎不争抢。

容器环境还有一个必须知道的事实：FFmpeg 不感知 cgroup 配额。它和编码库通过系统接口拿到的是宿主机核数，不是容器的 CPU limit。于是在限额两核的容器里它可能按几十核开线程池，很快用光每个调度周期的份额然后被限流，表现是倍速剧烈抖动、同样的源每次耗时差很多，而 CPU 使用率看着「还没到上限」。不查到 cgroup 层永远解释不通，解法却只是把 -threads、-filter_threads、-filter_complex_threads 显式写成与配额匹配的值。

同步转码接口是设计错误

转码耗时与输入时长成正比，从几秒到几小时跨三四个数量级，而 HTTP 请求的合理生命周期是秒级。做成同步接口的后果是连锁的：网关超时先断，客户端按常规策略重试，同一份输入被转好几遍——自己的重试吃掉自己的 CPU，越是高峰越严重；而且没有削峰、没有优先级、没有恢复点，一次滚动发布就丢掉所有在跑任务的进度。正确形态只有一种：提交立刻返回任务 id，状态靠轮询或回调获取。队列的投递语义与它带来的新问题详见《消息队列到底解决什么问题，又带来什么问题》。

队列建起来之后的真问题是长任务饿死短任务。先进先出时一个三小时的源会长时间占住并发槽位，而槽位总数是硬限的。解法不是调参，是按预估时长分池：用源时长或文件大小粗分类，两个池各持独立并发额度、互不挤占，短任务的排队时间分位数才可控。优先级只影响「谁先被取走」，不影响「已经在跑的」——抢占一个跑了四十分钟的任务等于扔掉四十分钟 CPU，所以只在入队侧调度。

分片转码（切成若干段并行转码再拼接）常被当成万能加速手段，适用条件其实很窄：必须能在关键帧边界切分；各段必须用完全相同且固定 GOP 的参数并关闭自适应插关键帧，否则拼接处会出现肉眼可见的画质跳变；恒定质量模式下各段独立决定码率，段间画质有差异，要求严格一致就得改用多遍或固定量化；段数也不能太多，每段的启动、探测与拼接开销会吃掉并行收益。只有「单个源很长且交付时延敏感」才值得。

进度、超时与「卡住不等于慢」

进度只有一个正确来源：-progress。它把结构化键值对写进文件或管道，含 frame、fps、total_size、out_time_us、speed，每块以 progress=continue 结尾。去解析那行用回车覆盖刷新的人类可读进度是常见但错误的做法，格式随版本变化。配套两个开关：-nostats 关掉人类可读输出，-nostdin 阻止 FFmpeg 读标准输入——它默认把 stdin 当交互控制通道，在服务里表现为抢掉父进程输入或一拿到 EOF 就退出。百分比用 out_time_us 除以源时长，而源时长可能缺失或不准，此时只报绝对进度，不要造假进度条。

超时设计的核心是区分卡住和慢，两者处理方式完全相反。「慢」是 speed 很低但 out_time_us 仍在推进，通常因为分辨率高、预设慢或 CPU 被限流，杀掉它等于扔掉已完成的部分。「卡住」是 out_time_us 一段时间完全不动，而它还占着宝贵的并发槽位，必须尽快回收。所以超时必须两个维度：无进展看护超时识别卡住，阈值要大于一次网络重试的量级；总耗时硬超时只做兜底，且应按源时长乘系数动态给。更好的是入队时就估一次预算，明显超预算的直接拒绝或降档，而不是跑到超时再丢弃。

观察到的组合最可能的原因该做什么
speed 低，out_time_us 正常推进，CPU 打满正常的慢：预设慢、分辨率高或源复杂不要杀。调预设或换机型，在入队侧修正预算
speed 低且剧烈抖动，CPU 使用率看着没到上限cgroup 限流，线程数远超配额显式设置 -threads 与滤镜线程数，与配额对齐
out_time_us 完全不动，CPU 接近零等 I/O：取源阻塞、写存储阻塞无进展超时触发，杀进程组并按可重试处理
out_time_us 不动但 CPU 打满解码器在畸形数据上打转，或病态滤镜参数杀掉并按输入不合法处理，重试没有意义
frame 推进但 out_time_us 不推进时间戳异常，输出时间轴没有前进先用 ffprobe 查源时间戳，这类源要先修再转
进度到某个百分比就不动，且源时长可疑源时长元数据不准，百分比的分母本身是错的改看绝对进度，不要以百分比作为卡住判据
进程已退出但任务状态仍是运行中worker 崩溃后状态没有回收任务上加租约与心跳，过期自动回到队列

孤儿进程：父进程退出，ffmpeg 不会跟着死

这是服务端最容易留下的资源泄漏，而它泄漏的是 CPU 和存储空间。FFmpeg 既不监控父进程是否存活，写文件输出时也不会因管道关闭而退出。于是 worker 崩溃、容器主进程退出、滚动更新只终止 PID 1，都会留下继续吃满 CPU 并往存储写垃圾产物的孤儿进程，而它们对应的任务已被重新投递，等于同一份活同时跑两遍。

防御按重要性排：每个任务独立成进程组或会话，清理时对整个进程组发信号；不要用 shell 包一层启动，否则拿到的进程号是 shell 的，杀它根本杀不到 ffmpeg（这也是不该拼命令字符串的第二个理由，第一个是注入）；先 SIGTERM 再 SIGKILL，给它几秒写完容器尾部索引，直接 SIGKILL 会留下无法播放的 MP4；worker 启动时扫残留，找出没有对应活跃任务的 ffmpeg 并清掉；容器里放一个能回收僵尸的 init 进程，宽限期要大于 SIGTERM 等待时间。

#!/usr/bin/env bash
# 服务端启动 ffmpeg 的最小正确形态。重点不在转码参数，而在这几个开关。
set -euo pipefail

SRC="$1"; DST="$2"; TASK_ID="$3"
THREADS="${FF_THREADS:-2}"                 # 必须显式给：容器里 ffmpeg 看到的是宿主核数，不是 CPU limit
PROGRESS="/tmp/${TASK_ID}.progress"

# -nostdin  不去读标准输入。默认它会把 stdin 当交互控制通道，在服务里会吞掉父进程的输入，
#           或者一拿到 EOF 就自己退出，排查成本极高。
# -nostats  关掉给人看的覆盖式进度行，日志才是可解析的。
# -progress 结构化进度写到文件，这是唯一适合程序消费的进度来源。
# -y        覆盖已有输出，否则会停下来等交互确认，配合 -nostdin 就直接失败。
# setsid    新建会话与进程组，超时清理时可以对整个组发信号。
exec setsid ffmpeg -hide_banner -nostdin -nostats -y \
  -loglevel warning \
  -progress "$PROGRESS" \
  -threads "$THREADS" -filter_threads "$THREADS" -filter_complex_threads "$THREADS" \
  -i "$SRC" \
  -c:v libx264 -preset veryfast -crf 23 -pix_fmt yuv420p \
  -c:a aac -b:a 128k \
  -movflags +faststart \
  "$DST" 2>>"/tmp/${TASK_ID}.stderr"

# 进度文件长这样，每块以 progress=continue 结尾，最后一块是 progress=end：
#   frame=12480
#   fps=58.2
#   total_size=41533440
#   out_time_us=416000000
#   speed=2.31x
#   progress=continue
# 判读规则：speed 低但 out_time_us 在推进，是慢，不要杀；
#           out_time_us 长时间不变，是卡住，必须回收并发槽位。

# 队列 worker 的核心骨架：幂等产物 key、进程组隔离、双维度超时、孤儿清理。
import hashlib, json, os, signal, subprocess, time

PIPELINE_VERSION = "2026-09-a"   # 升级 ffmpeg 或改参数模板就 bump，让旧产物自然失效
NO_PROGRESS_LIMIT = 120          # 无进展超时（秒），要大于一次网络重试的量级
SAMPLE_INTERVAL = 5

def artifact_key(src_digest: str, params: dict) -> str:
    # 同输入加同参数得到同一个 key，重复提交直接复用产物。三个要点：
    # 1) 用输入内容摘要，不要用 URL 或文件名，同一个 URL 的内容可能已经变了；
    # 2) 参数必须规范化（排序并补全默认值），否则同语义的两种写法会算出两个 key；
    # 3) 带上流水线版本，方便整体失效而不用改 key 结构。
    canon = json.dumps(params, sort_keys=True, separators=(",", ":"), ensure_ascii=False)
    raw = PIPELINE_VERSION + "|" + src_digest + "|" + canon
    return hashlib.sha256(raw.encode("utf-8")).hexdigest()[:32]

def last_progress(path: str) -> dict:
    # -progress 是追加写的 key=value 文本，这里取每个键的最新值
    try:
        with open(path, encoding="utf-8", errors="replace") as fp:
            lines = fp.read().splitlines()
    except FileNotFoundError:
        return {}
    return dict(l.split("=", 1) for l in lines if "=" in l)

def run(cmd: list, progress_path: str, err_path: str, hard_timeout: float):
    # 不要 shell=True：一是避免拼字符串引入注入，二是这样拿到的才是 ffmpeg 自己的 pid，
    # 隔一层 sh 的话 kill 到的是 sh，ffmpeg 会活下来继续吃 CPU。
    # 标准错误直接落文件，不要用管道等到最后才读，大量告警输出会把进程堵死。
    with open(err_path, "wb") as errf:
        p = subprocess.Popen(cmd, stdin=subprocess.DEVNULL,
                             stdout=subprocess.DEVNULL, stderr=errf,
                             start_new_session=True)   # 等价于 setsid，独立成进程组
        started = last_change = time.monotonic()
        last_out = None
        try:
            while p.poll() is None:
                time.sleep(SAMPLE_INTERVAL)
                now = time.monotonic()
                cur = last_progress(progress_path).get("out_time_us")
                if cur != last_out:
                    last_out, last_change = cur, now          # 有推进，重置看护计时
                elif now - last_change > NO_PROGRESS_LIMIT:
                    raise TimeoutError("stalled at out_time_us=%s" % last_out)
                if now - started > hard_timeout:
                    raise TimeoutError("hard timeout")
            return p.returncode
        finally:
            if p.poll() is None:
                pgid = os.getpgid(p.pid)
                # 先 TERM，让它有机会写完容器尾部索引；直接 KILL 会留下无法播放的残缺 MP4。
                os.killpg(pgid, signal.SIGTERM)
                try:
                    p.wait(timeout=10)
                except subprocess.TimeoutExpired:
                    os.killpg(pgid, signal.SIGKILL)

def sweep_orphans(active_ids: set):
    # worker 启动时与定期执行：命令行里带任务 id 但该任务已不活跃的 ffmpeg 一律清掉。
    # 清出来的数量要作为指标上报，它长期不为零就说明清理链路有漏洞。
    out = subprocess.run(["pgrep", "-a", "ffmpeg"], capture_output=True, text=True).stdout
    for line in out.splitlines():
        pid, _, cmdline = line.partition(" ")
        if "task-" in cmdline and not any(t in cmdline for t in active_ids):
            os.killpg(os.getpgid(int(pid)), signal.SIGKILL)

不可信输入是攻击面，转码等于在沙箱里解析不可信数据

用户上传的媒体文件属于最脏的一类输入：它要交给一大批用 C 写的解复用器与解码器解析，这些代码路径历史上出过大量内存安全问题；更麻烦的是有些格式允许引用外部资源，内容里可以写路径和地址。所以正确的心态不是「防一下畸形文件」，而是把每次转码都当成在沙箱里执行不可信数据，并假定进程会崩。

按性价比从高到低：入口侧只接受白名单容器格式，用显式 -f 指定输入格式而不依赖内容探测，限制大小、时长、分辨率与流条数，先用 ffprobe 做一次廉价校验——但 ffprobe 本身也在解析不可信数据，必须在同样受限的环境里跑。能力侧用 -protocol_whitelist 把可达协议收敛到业务真正需要的那几个。这一条对 -f concat 清单、播放列表这类内容里带路径与地址的输入格式尤其关键：接受用户提供的这类输入等于把「读什么」的决定权交给上传者，最稳的做法是只使用自己生成的清单。镜像侧用「先全部禁用再按白名单开启」的方式编译。

再往下是进程与环境：加地址空间、CPU 时间、输出大小与进程数上限（输出大小上限专防「小输入解出巨大产物」这类放大）；根文件系统只读，只挂任务专属临时目录并在结束时销毁；非 root 运行、丢弃全部多余能力；出网默认拒绝，只白名单到对象存储，尤其挡住云上的实例元数据地址。最后一条是心态：解析畸形文件导致进程异常退出是常态而不是事故，监控上要能把「输入不合法」和「系统故障」分开，前者不重试、直接回传明确原因。

防御措施挡住的是什么代价与注意
容器格式白名单 + 显式 -f靠内容探测走到冷门解复用器的路径业务要扩展格式时需要同步维护白名单
ffprobe 预校验大小、时长、分辨率、流条数资源放大型输入：超长、超大分辨率、几百条流ffprobe 也解析不可信数据，必须同样受限
-protocol_whitelist 收敛协议输入内容里的地址被当成可访问资源，导致任意文件读取与内网探测需要读远端源时按业务最小集开放，不要图省事放开全部
不接受用户提供的清单类输入把「读哪些文件」的决定权交给上传者拼接类需求改为服务端生成清单，只引用已入库对象
镜像只编译需要的解码器与解复用器大量从不使用但仍可被触发的解析代码需要自建镜像与发版流程，不能用现成通用包
地址空间、CPU 时间、输出大小、进程数上限内存暴涨、死循环、产物放大把整台机器拖下水上限要按业务最大合法输入留足余量，否则误杀正常任务
只读根文件系统 + 任务专属临时目录写入非预期路径、任务之间互相污染、读到凭证要确认 FFmpeg 的临时文件与日志路径都落在可写目录内
非 root、丢弃能力、出网默认拒绝单个任务被利用后的横向移动与元数据凭证窃取回源与上传的出网白名单要跟着对象存储域名变化维护

#!/usr/bin/env bash
# 不可信输入的预校验与受限解析环境。原则：贵的操作（编码）之前先做便宜的校验（探测）。
set -euo pipefail
SRC="$1"

# 一、进程级资源上限。畸形文件的典型表现就是内存暴涨或长时间不退出。
ulimit -v $((2 * 1024 * 1024))    # 地址空间 2 GiB，超了被内核终止，而不是把 worker 一起拖死
ulimit -t 1800                    # CPU 时间上限（秒），兜底防死循环
ulimit -f $((8 * 1024 * 1024))    # 单文件写出上限，防止小输入解出巨大产物
ulimit -u 64                      # 进程数上限

# 二、协议白名单。这一条决定了输入内容里的路径与地址有没有被当成资源访问的机会。
SAFE="-protocol_whitelist file"

# 三、只读元信息，不解码画面。-of json 便于程序判读。
META="$(ffprobe -v error -hide_banner $SAFE \
  -show_entries format=format_name,duration,size \
  -show_entries stream=codec_type,codec_name,width,height \
  -of json -- "$SRC")"

printf '%s' "$META" | python3 -c '
import json, sys
m = json.load(sys.stdin)
fmt = m.get("format") or {}
streams = m.get("streams") or []
ALLOW = {"mov,mp4,m4a,3gp,3g2,mj2", "matroska,webm"}
assert fmt.get("format_name") in ALLOW, "container not allowed"
dur = float(fmt.get("duration") or 0)
assert 0 < dur <= 4 * 3600, "duration zero or too long"
assert len(streams) <= 8, "too many streams"
vid = [s for s in streams if s.get("codec_type") == "video"]
assert len(vid) == 1, "unexpected video stream count"
assert (vid[0].get("width") or 0) * (vid[0].get("height") or 0) <= 3840 * 2160, "resolution too high"
print("ok", fmt["format_name"], round(dur, 3))
'
# 四、通过校验才进入编码阶段。容器侧还要补：根文件系统只读、只挂任务专属临时目录、
#     非 root 运行、丢弃全部多余能力、出网默认拒绝且只白名单对象存储。

失败分类、重试与幂等产物

转码的重试成本远高于普通接口：一次重试就是再烧一遍整段 CPU。所以「统一重试三次」在这里是有害策略，它把确定性失败的损失直接乘三。可重试的只有外部瞬时因素：取源超时与连接重置、对象存储的服务端错误与限流、临时磁盘不足、节点被驱逐。不可重试的是确定性失败：输入无法解析、文件截断、编码器不支持该输入特性、参数组合非法——重试一万次结果一样，应立刻落终态并回传原因。还有一类不该二选一：产物生成了但时长偏离或预期音轨缺失，应标记可疑走复核。

幂等是省钱的第一手段，因为重复提交与消息重放都会让同一份活干多遍。产物 key 由三部分构成：输入内容摘要（不要用文件名或 URL，同一个 URL 的内容可能已经变了）、规范化后的参数摘要（必须排序并补全默认值，否则同语义的两种写法算出两个 key）、流水线版本号。落地上先写临时对象再原子提交，任务表上对这个 key 加唯一约束，就同时拿到去重与并发提交互斥。幂等的完整落地方式详见《幂等的完整工程实现》。

成本结构：三项开销的增长维度不同

成本是三块：转码 CPU、多档位产物存储、回源与分发带宽。关键不在哪块更贵，而在它们随不同的量增长，所以抄别人的优化顺序通常是错的。CPU 与「入库量乘档位数」成正比，只花一次；存储与「入库量乘档位数乘保存时长」成正比，持续花；带宽与「播放量乘码率」成正比，和入库量无关。

由此得到两个几乎相反的策略。内容库以长尾冷内容为主时主要成本是存储，应减少常备档位、低档位按需生成、冷数据降存储级别。热内容集中时主要成本是带宽，此时应在编码上多花 CPU 换更低码率——更慢的预设、更高效的编码器——这是唯一能同时降带宽又不掉画质的方向。档位数是乘数项，每加一档 CPU 和存储都线性增加，而只有一部分用户真正用到；档位阶梯设计见《流式传输与点播分发》，编码器与码率控制的取舍见《编码原理与编解码器选型》。

硬件编码也常被误判：吞吐远高于软件编码，但同码率画质通常不如慢速软件编码，参数与档位灵活性也更受限。判断标准是算总账——省下的 CPU 是否抵得过多出来的分发带宽。

成本项随什么增长一次性还是持续有效的降低手段副作用
转码 CPU入库量乘档位数乘预设复杂度一次性一条命令多输出共享解码；低档位按需生成；幂等复用产物按需生成会让首次访问变慢，需要兜底档位
产物存储入库量乘档位数乘保存时长持续，且随时间累积削减常备档位；冷数据降级存储；长期不访问的档位淘汰淘汰后再访问要重新转码，需要明确的重建路径
分发带宽播放量乘实际播放码率持续，且随热度放大更慢的预设与更高效的编码器压低码率；档位阶梯合理化转码 CPU 上升；新编码器要考虑播放端兼容与兜底档位
回源带宽边缘未命中次数乘切片大小持续切片可长缓存，热内容预热；索引与切片分开设置缓存策略预热本身产生回源，冷内容预热是净浪费
重复转码重试率加重复提交率纯浪费产物 key 幂等；失败分类正确；同步接口改异步需要内容摘要，大文件摘要本身有 I/O 成本
闲置容量为峰值预留的机器数持续用队列把峰值摊平；低优先级批量任务填谷排队时间上升，需要与业务约定交付时延
硬件编码替代软件编码吞吐随硬件单元数增长，单位时间成本低一次性，但影响持续的带宽支出直播与时延敏感链路优先用；点播热门内容仍值得软编慢压同码率画质通常不如慢速软编，参数与档位灵活性受限，带宽会上升

可观测：先能回答「是容量不够还是变慢了」

转码系统和普通服务的监控差别在于：CPU 使用率几乎永远是满的，不含任何信息量。真正能指挥行动的是下面这些，且都要看分位数——转码耗时分布跨数量级，均值没有意义。排队时间分位数是容量是否足够的第一信号，比任何资源指标更早恶化，要按任务池分别统计。实时倍速衡量单任务效率，按机型、档位、预设分维度看，它突然下降通常不是源变复杂了，而是机型混杂或被 cgroup 限流。

失败率必须按原因分类，只有一个总失败率没法行动：要能分开输入不合法（可能是上游校验缺失）、依赖故障（该告警）、超时（容量或参数问题）。重试率与重试成功率要一起看，重试率高而成功率低说明失败分类判错了，正在持续烧钱。产物体积比是画质事故最早的自动信号。此外是队列深度、在跑任务数与并发上限的比值，以及孤儿进程计数——它长期不为零就说明清理链路有漏洞。

日志侧每个任务留一条结构化记录：任务 id、产物 key、完整参数、FFmpeg 版本、退出码、墙钟时长、CPU 时间、峰值内存、最后一次进度快照、标准错误尾部若干行。全量存标准错误不值得，但失败任务的尾部必须留，它几乎总是直接包含根因；FFmpeg 版本必须入库，因为「同样的参数换了版本行为变了」是真实存在的事故。指标与埋点方法论详见可观测性与性能。

指标为什么必须有异常形态与解读
排队时间 P50/P95/P99（按任务池）容量是否够的最早信号，早于任何资源指标P99 抬头而 P50 不动：长任务挤占，说明分池策略没生效
实时倍速（按机型、档位、预设）唯一能横向对比的单任务效率指标方差变大而均值不变：机型混杂或 cgroup 限流；整体下移：参数模板或源特性变了
任务耗时分位数（按源时长归一化）不归一化的耗时随内容分布漂移，无法做对比归一化后仍上升，才是真的变慢
失败率按原因分类只有总失败率就无法决定该改代码、扩容还是找上游输入不合法占比突增：上游校验缺失或有人在批量试探
重试率与重试成功率重试在这里是真金白银的 CPU重试率高、成功率低：失败分类判错，在持续烧钱
产物体积比与码率偏差画质事故最早的自动信号整体突变基本可以确定是参数模板被改动了
在跑任务数与并发上限的比值确认限流是否真的生效长期贴着上限且队列深度增长：需要扩容而不是调参数
孤儿 ffmpeg 进程数直接对应 CPU 与存储的静默泄漏不为零就是清理链路有漏洞，不要设阈值容忍

部署形态：常驻服务、队列 worker、按需函数

三种形态的差别不在技术新旧，而在谁来承担「并发必须被硬限」这个约束。常驻服务把并发控制放在自己的进程池里，控制力最强，适合稳定负载与长任务；队列 worker 交给消费并发度，弹性与隔离更好，是点播转码的默认答案；按需函数把资源管理交给平台，代价是执行时长上限、CPU 规格上限与冷启动，这三项恰好都打在转码的痛点上。

函数形态的正确用法不是跑整段转码，而是跑那些短小、并发高、单次成本低的活：抽封面、提取元信息、生成缩略图雪碧图、做预校验、处理分片转码中的单个片段。把一小时的源丢进函数里整段转码，几乎一定撞上时长上限，且失败时损失的是全部进度。

维度常驻转码服务队列 worker按需函数
并发控制自建进程池，控制力最强消费并发度，简单可靠由平台弹性决定，最难约束
适合的任务长任务、直播常驻转码、需要预热与本地缓存点播批量转码，长短分池抽帧、封面、元信息、预校验、单个分片
时长上限无硬上限，自己设超时无硬上限，受租约与宽限期约束平台硬上限，超时即失败且进度全丢
冷启动与预热无，可常驻缓存字体等资源拉起容器一次，之后复用每次可能冷启动，还要现拉输入
成本模型按预留机器付费，闲置就是浪费按机器付费但可用低优先级任务填谷按调用与时长付费，突发便宜、稳定负载不划算
失败与回收需要自己做孤儿进程清理与残留扫描同上，但租约过期可自动回队平台回收进程，但难以做优雅收尾
典型坑发布滚动时留下孤儿进程，任务进度全丢长短任务混池，短任务排队时间不可控用它跑长视频整段转码，撞时长上限且无法续跑
❌
最容易踩的坑

1. 并发由请求量决定：单任务就能吃满机器，不硬限并发的结果不是变慢，是所有任务一起超时。

2. 进程并发与 -threads 两边都放开：线程总数远超核数，总吞吐反而下降，时延分位数全线恶化。

3. 容器里不写 -threads 和 -filter_threads：FFmpeg 看到的是宿主核数，被 CFS 限流，表现为倍速抖动而 CPU 使用率「看着没满」。

4. 做成同步 HTTP 接口：网关超时后客户端重试，同一份输入被转好几遍，自己的重试吃掉自己的 CPU。

5. 长短任务混在一个池：一个三小时的源占住并发槽位，短任务排队时间彻底不可控。

6. 解析标准错误取进度：格式随版本变、用回车覆盖刷新。应当用 -progress 并加 -nostats 与 -nostdin。

7. 超时只做总耗时一个维度：慢任务被误杀，真正卡住的任务却白占一个并发槽位直到超时。

8. 以为父进程退出 ffmpeg 就会死：它不监控父进程，会继续吃满 CPU 并往存储写垃圾产物。

9. 用 shell 包一层启动再杀那个进程号：杀到的是 shell，信号必须发给整个进程组。

10. 直接 SIGKILL：MP4 没写完容器尾部索引，产物根本无法播放。

11. 接受用户提供的清单类输入或不收敛协议：等于把「读什么文件、访问什么地址」的决定权交给上传者。

12. 统一重试三次、产物 key 用 URL、退出码为零就算成功：三者分别把浪费乘三、返回过期产物、把画质事故直接发给用户。
