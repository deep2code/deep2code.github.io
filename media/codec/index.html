编码原理与编解码器选型

🏷️ 音视频

编码选型的讨论常常退化成「哪个编码更好」，而这个问题没有答案。编码器是一组在质量、码率、编码耗时、解码端普及度、授权成本之间的取舍，任何一次选型都必须先说清约束在哪一侧。这篇先把压缩是怎么发生的讲清楚——因为只有知道比特花在哪里，才能判断参数改动的方向；再给出码率控制和编解码器的判断矩阵。名词与数据模型见站内《音视频基本名词与数据模型》，音频编码单独见《音频处理：采样、压缩与响度》，命令与参数细节见《FFmpeg 的命令行模型》。

有损压缩的三个来源：只有一步真正丢信息

视频编码器把数据变小靠三件事：预测去掉时间与空间冗余，变换把能量集中到少数系数上，熵编码按概率给符号分配更短的码字。这三步里只有量化真正丢信息——预测只是把「像素值」换成「与预测值的差」，变换在整数实现下近乎可逆，熵编码是严格无损的。量化是把变换系数除以一个步长再取整，取整丢掉的部分永远回不来。

这个结论有很强的实用价值：所有「画质」参数最终都作用在量化步长上，或者作用在「同样的量化步长下残差能有多小」。CRF、QP、码率上限，本质都是在控制量化步长的分布。preset、运动搜索范围、块划分深度这些参数不直接改画质，而是改「编码器有多努力地找到一个更小的残差」。

压缩来源做了什么是否丢信息主要可调参数调错的后果
预测（帧内与帧间）用已重建的像素或参考帧预测当前块，只编码残差不丢，残差仍是完整信息参考帧数、块划分、运动搜索范围与精度搜索太弱导致残差大，同码率下画质下降；搜索太强只是耗时暴涨
变换与量化把残差变到频域集中能量，再除以量化步长取整量化这一步丢信息，且不可逆CRF、QP、量化矩阵、自适应量化步长过粗出现块效应与色带；过细则码率暴涨而无可感收益
熵编码按符号概率分配码长，算术编码或变长码完全无损熵编码器类型（算术编码与变长码）、上下文模型为兼容旧设备选了较弱的熵编码器，同质量下码率上升

帧内与帧间预测：编码耗时都花在哪

帧内预测从同一帧内已重建的邻块外推，方向模式的数量随标准演进大幅增加，HEVC 与 AV1 的模式数远多于 H.264，这是它们压缩效率更高的来源之一，也是编码耗时更高的来源之一——每多一种模式就多一次率失真评估。

帧间预测的开销主要在运动估计：对每个块在参考帧里搜索最匹配的位置，还要做子像素插值以获得更精确的匹配。搜索范围、搜索算法、参考帧数量、块划分的递归深度共同决定了搜索空间大小，而这个空间是组合爆炸的。所以编码耗时的大头不是变换和熵编码，而是「找最优预测」的搜索。

这就解释了 preset 到底是什么：它是一组搜索强度的预设组合，用时间换同质量下更低的码率。preset 不会凭空提高画质上限——在固定 CRF 下，慢 preset 的产物码率更低而质量相近；在固定码率下，慢 preset 的质量更好。判断要不要换 preset，只需要问：你的瓶颈是转码机时，还是分发带宽。

preset 变慢时实际改了什么对码率或质量的影响对耗时的影响什么时候不值得
运动搜索算法更彻底、搜索范围更大残差变小，同质量下码率下降增长最显著的一项静态画面为主的内容（屏幕录制、PPT）收益很小
块划分递归更深、划分形状更多复杂纹理与边缘区域受益明显显著增长低分辨率素材可划分空间本就有限
参考帧数量与 B 帧金字塔层数增加压缩效率提升中等增长，且解码端内存与延迟上升低延迟链路本来就要禁用 B 帧
率失真决策更接近穷举、开启网格量化比特分配更优中等到显著码率已经高到接近无损时收益趋零
多遍分析与自适应量化更精细暗部与平缓区域的主观质量提升中等实时编码没有时间预算

码率控制模式的判断矩阵

码率控制回答的是「每一帧给多少比特」。它的核心矛盾是：质量恒定与码率恒定不可兼得。内容难度随时间变化，要么让码率浮动以保住质量，要么让质量浮动以保住码率，没有第三种可能。所有模式都只是在这条线上选一个点，外加「是否预先知道整段内容的难度」。

模式控制目标输出码率是否可预测适用场景不可兼得之处与失效方式
恒定质量（CRF）主观质量大致恒定不可预测，随内容波动点播存档、母版、内容难度差异大的片库遇到高噪点或高动态素材时码率可能远超预算，需要配峰值上限
恒定量化（固定 QP）量化步长恒定不可预测算法对比实验、需要严格可复现的测试压缩效率最差，不做自适应量化，生产环境基本不用
单遍平均码率（ABR）整段平均码率接近目标大致可预测对体积有要求但不能两遍的流水线开头段落因为还没看到后文而分配失当，常出现前段质量偏低
恒定码率（CBR 加缓冲约束）每个缓冲窗口的比特数恒定可预测且有峰值上限直播、固定带宽信道、广播链路简单画面浪费比特、复杂画面质量骤降；缓冲设太小会周期性劣化
两遍 VBR总体积精确命中，按难度分配非常可预测已知目标体积的点播转码必须完整读两遍，耗时翻倍，不适用于流式与直播
capped CRF（CRF 加峰值与缓冲上限）质量优先，同时不突破峰值有上限，平均值不定大规模点播与自适应码率档位的主流做法难素材会被峰值上限压住，质量下降到 CRF 目标之下

还有一个被反复忽略的约束：解码缓冲。码率控制不只要管平均值，还要保证任意时刻解码端的缓冲不溢出、不欠载。直播链路里只设平均码率而不设峰值与缓冲大小，遇到场景切换时瞬时码率会冲高，表现为观众端集中卡顿；这类现象在带宽受限的移动网络上尤其明显。自适应码率的档位设计与切换策略见《流式传输与点播分发》。

profile 与 level：设备播不了的真正原因

profile 决定允许使用哪些编码工具（例如是否允许 B 帧、是否支持高色深与 4:2:2/4:4:4），level 决定规模上限（最大采样吞吐、最大码率、参考帧缓冲大小，进而约束分辨率与帧率的组合）。解码器按 profile 加 level 声明能力，超出即不保证可解，表现可能是黑屏只有声音、可能回落到软解卡顿、也可能直接报错。

硬件编码与软件编码：代价在哪一侧

硬件编码器是固定功能管线：运动搜索、块划分、率失真决策都被简化以适配电路实现，能暴露给用户的参数也远少于软件编码器，很多心理视觉优化根本没有对应开关。它换来的是极低的 CPU 占用、稳定的实时吞吐和可预测的延迟。同码率质量不如成熟软件编码器的慢档，是硬编的固有代价，不是配置没调好。

另一个容易被忽视的点是厂商差异：不同厂商、甚至同一厂商不同世代的硬件编码器，输出质量和可用特性都不一样，把一套参数从一个平台搬到另一个平台通常需要重新验证。此外消费级显卡对并发编码会话数有驱动层限制，做集中式转码集群时必须把这个限制算进容量模型，部署形态与资源核算见《FFmpeg 服务端转码的工程化》。

#   1) 点播档位：capped CRF，质量优先且峰值受限
ffmpeg -i src.mp4 -c:v libx264 -preset slow -crf 21   -maxrate 6M -bufsize 12M -pix_fmt yuv420p -profile:v high -level 4.1   -c:a copy out_vod.mp4

#   2) 直播档位：CBR 加缓冲约束，禁用 B 帧，固定关键帧间隔
ffmpeg -i src.mp4 -c:v libx264 -preset veryfast -tune zerolatency   -b:v 3M -minrate 3M -maxrate 3M -bufsize 3M -bf 0 -g 50 -keyint_min 50   -c:a aac -b:a 128k -f flv rtmp://example.invalid/live/stream
# 说明：bufsize 越小码率越平滑但质量波动越大；bf 0 去掉重排延迟；
#       g 与切片时长必须成整数倍关系，否则切片边界对不上关键帧

从观看场景反推参数，而不是抄参数表

网上流传的「各分辨率推荐码率表」只能当起点，因为它没有你的内容难度、没有你的用户带宽分布、也没有你的设备约束。可操作的反推顺序是：先定观看场景（屏幕尺寸与观看距离决定有效分辨率上限）、再定带宽预算（取用户带宽分布的低分位而不是平均值）、再定设备约束（最老要支持的解码器决定 profile 与 level），最后才用每像素比特数作为锚点校验分辨率、帧率、码率三者是否匹配。

几个可判断的边界：源片本身是上采样得来的，提高分辨率只增成本不增信息；内容运动量低（讲座、访谈）时提高帧率纯属浪费；噪点重的素材在低码率下会把比特全花在噪声上，先做适度降噪再编码往往比加码率更有效；屏幕内容（大量文字与锐利边缘）与自然图像的比特需求分布完全不同，套用同一张参数表必然有一头错。

转码代价与「能不能不转」

每次转码都是一次不可逆的世代损失：解码出来的已经是有损结果，再编码一次会在此基础上继续量化。所以工程原则是从母版一次性产出所有档位，绝不拿产物再转产物。级联转码是画质莫名变差的高频原因，而这种劣化在参数表上完全看不出来。

判断项满足则可只重封装不满足时的最小处理
视频编码与 profile、level在目标播放端支持范围内必须重编视频，音频仍可直通
像素格式与色深为常规 8 bit、4:2:0必须重编视频
分辨率与帧率不超过目标档位上限缩放或抽帧，属于重编
码率与峰值在带宽预算内且峰值可控重编并施加峰值与缓冲约束
关键帧间隔与切片时长成整数倍关系必须重编视频，仅改封装无法插入关键帧
音频编码与声道目标端支持且声道布局正确仅重编音频，视频直通
容器与索引位置容器可换、索引可前置重封装即可解决

这张表的用法是逐项打勾：只要有一项不满足就落到「重编对应的那一条流」，而不是整个文件重编——音频不合规时视频可以直通，反之亦然。具体的直通开关、切片参数与批处理写法见《FFmpeg 的命令行模型》；推流入口侧的模块配置见站内《Nginx RTMP 与 HLS 模块》。

❌
最容易踩的坑

1. 拿公开测试的「省一半码率」比例做容量规划。增益强依赖内容与配置，必须用自己的素材实测出经验区间。

2. 直播只设平均码率不设峰值与缓冲上限。场景切换时瞬时码率冲高，表现为观众端集中卡顿。

3. 用 CRF 跑大批量未知素材且不加峰值上限。遇到高噪点素材时单个文件码率远超预算，带宽账单当月爆掉。

4. 关键帧间隔与切片时长不成整数倍。切片边界对不上关键帧，播放端起播和码率切换都会出问题。

5. 低延迟链路忘了禁用 B 帧。重排延迟是编码结构决定的固有延迟，调网络和缓冲都消不掉。

6. 只降码率来适配老设备。设备播不了通常是 profile、level 或像素格式越界，与码率无关。

7. 把 10 bit 或 4:2:2 素材直接当分发档位。硬件解码器大多只吃 8 bit、4:2:0，回落软解后发热掉帧。

8. 拿转码产物再次转码生成其他档位。世代损失叠加，参数表上看不出来，主观质量持续变差。

9. 为了省机时全线用硬编，包括归档母版。母版一旦质量打折，后续所有档位都继承这个损失。

10. 把一个平台调好的硬编参数照搬到另一厂商或另一世代，输出质量和支持的码率控制方式并不一致。

11. 上采样的源片按目标分辨率重新编码。分辨率数字变大而信息没变多，只是成本变高。

12. 忘了保留兜底档位就全量切换到新编码，老设备与老浏览器用户直接播不了，且监控里只体现为播放失败率上升。
