音视频基本名词与数据模型

🏷️ 音视频

音视频这套名词体系的麻烦之处在于：每个词单独看都简单，混用之后所有讨论都会失焦。「MP4 播不了」「码率调高点就清楚了」「音画不同步是网络卡了」在工单里天天出现，而它们指向的往往不是同一层的问题。这篇不讲工具怎么用，只把数据模型钉死：一段音视频从像素和采样变成可分发的文件，中间经过哪几层、每层持有哪些属性、改动某个属性会在哪一层产生什么可观测的后果。后续的编码选型见站内《编码原理与编解码器选型》，音频细节见《音频处理：采样、压缩与响度》，命令与参数见《FFmpeg 的命令行模型》，分发链路见《流式传输与点播分发》。

容器与编码是两套独立的命名空间

容器（封装格式）解决的问题是「怎么把已经压缩好的码流放进一个文件，并且能被随机访问」：它记录有几条流、每条流用的是什么编码、每个数据包的时间戳与字节位置、可选的章节与附件。编码格式解决的问题是「怎么把一帧像素或一段采样压小」。两者的唯一交集是容器要知道每条流的编码标识，且部分容器只允许有限的编码集合。

所以「MP4 播不了」这句话本身没有信息量。MP4 只是个盒子，播不了通常是盒子里装了播放端解不了的编码——HEVC、AV1、10 bit 像素格式、或者音频是 AC-3 而浏览器只认 AAC；少数情况是索引位置不适合流式播放（moov 在文件尾部，必须下载完才能起播）；极少数才是容器结构损坏。排查顺序永远是先看编码与像素格式，再看容器。

容器常见可承载编码索引与随机访问直播与流式适配最常见的「播不了」原因

这张图里藏着一条经常被忽略的事实：换容器不需要重新编码。把 TS 里的 H.264 加 AAC 原样搬进 MP4，只是拆包、重打包、改时间戳，开销是 I/O 级别的；换编码则必须完整解码再编码，开销高两三个数量级。判断一次转换属于哪一类，是所有转码成本优化的第一步，判断条件见《编码原理与编解码器选型》，具体命令见《FFmpeg 的命令行模型》。

分辨率、帧率、码率：三个正交的旋钮

分辨率是每帧的像素数，帧率是每秒的帧数，码率是每秒的比特数。三者可以独立设置，但前两者共同决定「像素率」，也就是宽乘高乘帧率；码率除以像素率得到每像素比特数，这个派生量才是画质的直接支配者。记住这个关系，大部分「参数该怎么调」的问题就变成算术题。

由此得到两个可判断的结论。第一，提高分辨率或帧率而不提高码率，画质必然下降：同样的比特摊到更多像素上。拿 1080p 的码率去编 4K，结果通常比原生 1080p 更糊，这就是「4K 版本反而不如 1080p 清晰」的根源。第二，码率不是无限有效的：当码率高到量化步长接近无损，继续加码率只增大文件，画质不再变化，编码器还可能把多余比特浪费在填充上。所谓「码率越高越清晰」只在瓶颈确实在码率时成立。

改动直接影响码率不变时的连带后果典型失效表现怎么判断该不该动
分辨率提高一档像素率按面积比增长每像素比特数按同比例下降大面积块效应、纹理被抹平、边缘振铃看源片真实清晰度；上采样的源提分辨率只增成本不增信息
帧率提高一档像素率线性增长每帧可用比特线性减少运动画面糊，静止画面反而正常只有运动剧烈的内容（体育、游戏）值得高帧率
码率降低文件与带宽线性下降量化步长变粗先丢高频细节，再出现块与色带用同源不同码率做主观对比，找到劣化拐点
码率升高到过量文件线性增大无收益体积翻倍而肉眼无差别改用恒定质量模式，让编码器自己决定比特
关键帧间隔缩短I 帧占比上升可用于 P/B 帧的比特减少整体画质下降，但首屏与 seek 变快按分发形态定：直播与切片要短，点播可长

CBR 与 VBR 属于码率控制模式，不是码率自身的属性：前者让每个时间窗口的比特数尽量恒定以适配固定带宽信道，后者允许复杂场景多分比特。它们与 CRF、capped CRF、两遍编码的取舍在《编码原理与编解码器选型》里有完整判断矩阵，这里只留一句。

GOP 与 I/P/B 帧：seek 精度与首屏延迟的来源

视频编码的绝大部分压缩来自帧间预测：只有少数帧独立编码（I 帧），其余帧存的是与参考帧的差异。P 帧向前参考已解码帧，B 帧同时参考前后两个方向。从一个 I 帧到下一个 I 帧之前的序列称为 GOP。

这里有个流传很广的误解：关键帧不等于 I 帧。真正能作为随机访问入口的是 IDR 帧，它会清空参考帧缓冲，保证后续帧不会跨过它参考更早的数据。H.264 与 HEVC 都允许存在非 IDR 的 I 帧，open GOP 结构里很常见，从这种帧起播会因为缺少参考而输出几帧花屏。所以 seek 点、切片边界、直播接入点都必须对齐 IDR，而不是「任意 I 帧」。

帧类型参考依赖能否作为起播点体积量级对延迟的影响
IDR 帧无，且清空参考缓冲可以，唯一安全入口最大，常是 P 帧的数倍到数十倍无额外延迟，但间隔决定首屏等待
非 IDR 的 I 帧自身无预测，但后续帧可跨越它参考不安全，可能花屏与 IDR 同量级open GOP 下参与重排，可能增加延迟
P 帧向前参考一帧或多帧不可以中等无重排延迟
B 帧前后双向参考不可以最小引入固有重排延迟，深度由重排帧数决定
参考 B 帧（可被参考的 B 帧）双向参考且自身被参考不可以小延迟更大，丢包影响范围扩散
sequenceDiagram participant U as 用户 participant P as 播放器 participant X as 解封装器 participant D as 解码器 U->>P: 拖动进度条到时间点 t P->>X: 在索引中查找不晚于 t 的最近 IDR X-->>P: 返回位置 t0，t0 不晚于 t P->>D: 从 t0 开始按 DTS 顺序送包 D->>D: 解码 t0 到 t 之间的帧但丢弃输出 D-->>P: 首个 PTS 不早于 t 的帧可显示 P-->>U: 画面出现 Note over X,D: 关键帧间隔越大，t0 距离 t 越远，seek 与首屏越慢

直播首屏必须等一个 IDR，原因同上：新观众接入时缓冲区里可能全是 P/B 帧，没有独立可解的入口。把关键帧间隔从若干秒压到一两秒能显著改善首屏，代价是 I 帧占比上升、同码率下整体画质下降。这个取舍与 HLS/DASH 的切片时长直接绑定（每个切片必须以 IDR 开头），细节见《流式传输与点播分发》；用 Nginx 做 RTMP 转 HLS 的配置见站内《Nginx RTMP 与 HLS 模块》。

B 帧带来的是与网络无关的固有延迟：解码顺序和显示顺序不一致，解码器必须先解出后向参考帧才能输出中间的 B 帧，重排队列深度就是延迟下限。这就是实时通信链路普遍禁用 B 帧、而点播乐于使用 B 帧的原因。

PTS、DTS 与时间基：同步的数据模型

时间戳不是秒，而是「以 time_base 为单位的整数」，秒数等于时间戳乘以时间基。DTS 指示什么时候把包送进解码器，PTS 指示解出来的帧什么时候显示；没有 B 帧时两者相等，有 B 帧时 PTS 相对 DTS 顺序出现回跳。两者的最大差值就是重排延迟，可以直接测出来。

时间基是最容易出错的环节：MPEG-TS 固定用 90 kHz，MP4 每条 track 有自己的 timescale，编码器内部又常用帧率倒数作为时间基。重封装时必须做有理数换算；用浮点秒中转、或者把数值直接搬过去，都会导致播放速度不对或长时间累积漂移。

# 时间基换算：容器、编码器、封装器各有自己的 time_base
# 用有理数运算，避免浮点误差在长视频上累积成可感知的音画偏移
from fractions import Fraction

tb_src = Fraction(1, 90000)   # MPEG-TS 固定 90 kHz
tb_dst = Fraction(1, 15360)   # MP4 track 常见 timescale 之一
pts_src = 1234567

# 正确做法：先换算成秒（有理数），再除以目标时间基，最后一次取整
seconds = pts_src * tb_src
pts_dst = round(seconds / tb_dst)

print(f"源时间戳 {pts_src} -> {float(seconds):.6f}s")
print(f"目标时间戳 {pts_dst} -> {float(pts_dst * tb_dst):.6f}s")
# 两个秒值之差就是本次换算的量化误差；每次重封装都会引入一次
# 如果误差乘以总帧数已经接近一帧时长，说明时间基选得太粗

音画不同步常被笼统归因为「网络问题」，但可复现的不同步几乎都不是网络导致的。按下面三类成因排查，能覆盖绝大部分现场。

成因类别现象特征根因验证方法修法方向

ffprobe -v error -select_streams v:0 -show_packets   -show_entries packet=pts_time,dts_time,flags,size   -of csv=p=0 input.mp4 | head -n 40

# 判读规则：
#   flags 第一位为 K 表示该包是关键帧，可作为 seek 与切片边界
#   dts_time 必须单调递增；不递增说明码流或封装有问题
#   pts_time 相对 dts_time 出现回跳，说明存在 B 帧参与重排
#   max(pts_time - dts_time) 就是解码重排引入的固有延迟
#   相邻两个 K 包的 pts_time 之差即真实关键帧间隔，别只看编码参数

# 确认两条流的起始时间戳是否对齐（音画固定偏移的第一嫌疑）
ffprobe -v error -show_entries stream=index,codec_type,start_time,time_base   -of csv=p=0 input.mp4

音频侧的数据模型

采样率决定可表示的最高频率，上限是采样率的一半；位深决定动态范围与量化噪声本底，每 bit 约换来 6 dB；声道数与声道布局决定空间信息；帧长（每个编码帧包含多少采样）决定时间粒度与编码固有延迟。未压缩 PCM 的码率是个确定值：采样率乘位深乘声道数，没有任何压缩带来的不确定性。

每个参数改动都有可判断的后果。把语音从 16 kHz 提到 48 kHz，人声能量集中在低频，几乎没有可感收益，数据量却成倍增加；位深从 16 提到 24 只在有大量后期增益调整的制作链路里有意义，最终分发基本不需要；声道布局标错（例如把 6 声道当成 3 个立体声对）不会报错，只会声道错位；帧长直接决定实时通信的延迟下限，所以实时编码器普遍用短帧。采样定理的完整推论、心理声学模型、响度归一化与实时语音链路见《音频处理：采样、压缩与响度》，本文不重复展开。

视频侧的像素模型：YUV 采样与色彩描述

编码器几乎不直接处理 RGB，而是用 Y 加两个色差分量的表示：把亮度与色度分离，再利用人眼对色度分辨率不敏感的特性对色度下采样。这里要纠正一个常见误解：YUV 本身不是压缩格式，它只是分量表示与像素排列；真正减少数据量的是色度下采样，而下采样是有损且不可逆的。

色深每个分量的比特数8 bit 在平缓渐变上出现色带；转码链路中间用 10 bit 可减少累积误差

流与轨道：容器内部的组织方式

一个容器可以有任意多条流，每条流有独立的索引、编码参数、时间基和元数据标记。常见的额外语义包括：默认标记（播放器优先选哪条）、强制标记（字幕必须显示）、语言标签、以及标题。多音轨影片的「切不了语言」多半不是转码问题，而是转封装时只保留了第一条音频流，或者丢了语言标签。

字幕要分三类看，因为它们的处理代价完全不同。文本字幕（外挂的常见文本格式、容器内的文本轨）体积极小，可改样式、可被检索，转封装时只需注意目标容器支持哪种文本编码；位图字幕是一张张图片，无法改样式也无法检索，转成文本需要 OCR；烧录字幕（硬字幕）已经变成像素的一部分，必须重新编码整条视频才能去掉，属于不可逆操作。分发链路里的默认选择应当是文本字幕独立成流或独立文件，而不是烧进画面。

容器还承载章节、封面、附件字体、以及各种键值元数据。MP4 的索引位置（moov 在头部还是尾部）决定能否边下边播，这属于封装参数而非编码参数，用重封装即可修复，具体开关见《FFmpeg 的命令行模型》；服务端批量处理这类问题的资源模型与并发控制见《FFmpeg 服务端转码的工程化》。

名词误用清单与一次性判读命令

下面这些说法在需求文档和缺陷单里出现频率极高，每一条都会把排查带偏。

常见说法实际情况工程后果
「这是 MP4 编码」MP4 是容器，编码是 H.264 等需求里只写容器，实现时选了不兼容的编码，上线才发现播不了
「换成 MP4 就能播了」换容器不改编码，解不了的还是解不了白做一次重封装，问题照旧
「码率越高越清晰」超过当前分辨率与编码器的收益拐点后不再提升带宽成本翻倍而主观质量无变化
「关键帧就是 I 帧」只有 IDR 才是安全的随机访问点切片或 seek 对齐到非 IDR，出现花屏
「帧率越高越流畅」还受快门时间、显示刷新率、以及同码率下每帧比特数的制约提帧率后画面更糊，主观体验反而变差
「YUV 是一种压缩」YUV 是分量表示，压缩来自色度下采样与编码把像素格式和编码格式混为一谈，选型时说不清代价
「采样率就是音频码率」PCM 码率等于采样率乘位深乘声道数；有损编码后码率与采样率解耦按采样率估带宽，结果差一个数量级
「音画不同步是网络问题」固定偏移与线性漂移都与网络无关反复调网络参数，根因在时间戳或时钟
「H.265 一定比 H.264 小一半」增益依赖内容、分辨率与编码配置，没有恒定比例按固定比例做容量规划，实际严重偏差
「无损就是码率很高」无损是数学可逆，与码率高低不是一回事把高码率有损当成无损素材进入制作链路，误差累积

ffprobe -v error -of json -show_entries   'format=format_name,duration,bit_rate,start_time:stream=index,codec_type,codec_name,profile,level,width,height,pix_fmt,color_primaries,color_transfer,color_space,color_range,r_frame_rate,avg_frame_rate,time_base,start_time,sample_rate,channels,channel_layout,nb_frames'   input.mp4

# 字段与本文概念的对应关系：
#   format_name            -> 容器层，与能否播放的因果关系最弱
#   codec_name / profile   -> 编码层，播不了先看这两个
#   pix_fmt                -> 色度采样与色深，yuv420p10le 这类会卡住硬件解码
#   color_* 四个字段        -> 色彩描述，颜色不对时只看这几个
#   r_frame_rate           -> 容器声明帧率；avg_frame_rate 是实际平均，两者不等说明变帧率
#   time_base / start_time -> 时间模型，音画固定偏移从这里查
#   width / height + 帧率 + bit_rate -> 算出每像素比特数，判断码率是否配得上分辨率
❌
最容易踩的坑

1. 把「播不了」当容器问题，反复重封装。先看 codec_name、profile、pix_fmt，再看容器，顺序反了就是浪费时间。

2. 用 r_frame_rate 当真实帧率。变帧率素材的容器声明值可能与实际平均帧率差很多，按它算码率和时长都会错。

3. 提分辨率不提码率。每像素比特数被摊薄，产物比低分辨率版本更糊，还多付了转码与带宽成本。

4. 把 seek 点或切片边界对齐到非 IDR 的 I 帧，起播花屏；open GOP 素材尤其容易中招。

5. 只看编码参数里的关键帧间隔，不验证实际码流。场景切换插入的关键帧、以及编码器的自适应决策都会让实际间隔与设定不一致。

6. 低延迟链路忘了关 B 帧。重排延迟是固有的，与网络无关，调缓冲参数永远调不掉。

7. 重封装时用浮点秒中转时间戳。长视频上量化误差累积成可感知的音画偏移，必须用有理数换算。

8. 忽略容器里的延迟补偿信息（编辑列表、音频前导样本），转封装后出现固定音画偏移。

9. 丢掉色彩描述四元组。转码后颜色发灰或肤色偏色，排查时却一直在看码率和分辨率。

10. 8 bit 全程处理带渐变的素材，中间环节反复量化后出现色带；转码链路中间用 10 bit 能明显缓解。

11. 转封装只保留第一条音频流和视频流，多音轨与字幕轨静默丢失，语言标签也一起丢。

12. 把字幕烧进画面当默认做法。硬字幕不可逆，改一个错别字要重编整条视频，且无法做多语言与检索。
